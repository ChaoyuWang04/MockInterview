# vLLM 17|确定性推理与批不变性

同一条 prompt、同样的采样种子,只因为它这次和别的请求拼在了一个 batch 里,就吐出了另一段话。这一章讲清这件事为什么会发生、vLLM 用什么把它按住、以及按住之后要付多少钱。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 痛点:同一条 prompt,换个并发就换个答案

压测时一切正常,上线之后同一个问题在高并发时段给出了不同的答案。重试、加锁、固定随机种子,全都没用。

这不是玄学,而是一条完整的因果链,本章沿着它走:

| 痛点 | 根子在哪 | 本章在哪回答 |
|---|---|---|
| 同一条请求,单独跑和混在 batch 里跑,结果不一样 | 浮点加法不满足结合律,而 GPU 会按 batch 规模改变加法的次序 | 1.2 到 1.4 |
| 明明只差 $10^{-8}$,整段话却完全变了 | 自回归解码是离散化加反馈,小扰动会被逐级放大 | 1.7 |
| 固定种子、加同步、开确定性算法开关,都不管用 | 这三样管的都不是「加法按什么次序做」 | 1.5 到 1.6 |
| 那到底要钉死什么 | 不是「配置固定」,而是「归约维的切分固定」 | 1.13 到 1.26 |
| 钉死之后会慢多少 | 每一类手段都在拿性能换次序稳定 | 贯穿 1.13 之后各节 |

一句话概括这条线: **问题出在「配置选择」,不在「执行同步」** 。后面每一节都是这句话的一个具体形态。

### 1.2 地基:浮点加法不满足结合律

实数的加法满足结合律,$(a+b)+c = a+(b+c)$ 。浮点数的不满足,因为每一步加法之后都要 **舍入到最近的可表示浮点数** ,而舍入误差取决于当时两个操作数的相对大小。

先说清「可表示」。IEEE-754 单精度用 1 位符号、8 位指数、23 位尾数。在 $[1.0, 2.0)$ 区间内,相邻两个可表示数之间的间隔是

$$
\text{spacing}(1.0) = 2^{-23} \approx 1.1921 \times 10^{-7}
$$

这个量常被称为 **机器精度** 。含义很朴素:在 1.0 附近,单精度能分辨的最小差异就是 $1.19 \times 10^{-7}$ ,比它更小的增量会被吸收掉。

为什么会吸收?把 $1.0 + 10^{-8}$ 写成二进制:$1.0$ 的尾数 23 位全零;$10^{-8}$ 要对齐到指数 $2^0$ ,需要右移约 27 位才能与 $1.0$ 对齐;而尾数只有 23 位,右移 27 位之后有效位全部被移出寄存器,加数变成 0,结果仍是 $1.0$ 。

这叫 **大数吞小数** 。它的严重程度取决于两个操作数的指数差,而指数差取决于你先加了谁 —— 所以次序决定结果。

bf16 更糟。它是 1 位符号、8 位指数、 **7 位尾数** ,在 1.0 附近的间隔是 $2^{-7} \approx 7.8 \times 10^{-3}$ 。也就是说,在 1.0 附近 bf16 分辨不出比 0.0078 更小的增量。这正是为什么 LLM 推理对归约次序格外敏感:权重和激活普遍用 bf16 或 fp16 存,一次加法的舍入误差就可能达到 $10^{-3}$ 量级。

这也解释了 vLLM 的一个设计选择:所有批不变 kernel 内部 **一律用 fp32 累加器** ,只在写回时才转回 bf16 或 fp16。但要注意, **fp32 累加降低了单步舍入误差,并不消除次序依赖** —— 下一节那个例子就是纯 fp32 的。用 fp32 累加是必要条件,不是充分条件。

### 1.3 一个 K=4 的点积:三种走法,两种答案

后面每一节都会回到这个例子。

设一个矩阵乘的 K 维长度为 4(真实模型里是几千,这里缩到 4 便于手算)。取一行 $a$ 和一列 $b$ :

$$
a = [1.0,\ 10^{-8},\ -1.0,\ 10^{-8}], \qquad b = [1.0,\ 1.0,\ 1.0,\ 1.0]
$$

要算的是 $\sum_{k=0}^{3} a_k b_k$ ,数学真值是 $2 \times 10^{-8}$ 。全程 fp32。

**走法 A:一个线程按 $k=0 \to 3$ 串行累加**

| 步 | 运算 | 存储值 | 说明 |
|---|---|---|---|
| 0 | $0 + 1.0$ | 1.0 | — |
| 1 | $1.0 + 10^{-8}$ | 1.0 | $10^{-8}$ 被吞,它小于间隔的一半 $5.96\times10^{-8}$ |
| 2 | $1.0 + (-1.0)$ | 0.0 | 大数抵消,但那个 $10^{-8}$ 已永久丢失 |
| 3 | $0.0 + 10^{-8}$ | $10^{-8}$ | 这次没有大数,保留下来 |

结果 $10^{-8}$ 。

**走法 B:split-K = 2,两个线程块各算两个元素再相加**

| 线程块 | 负责 | 局部和 | 说明 |
|---|---|---|---|
| 第一个 | $k=0,1$ | $1.0 + 10^{-8} \to 1.0$ | 被吞 |
| 第二个 | $k=2,3$ | $-1.0 + 10^{-8} \to -1.0$ | 被吞 |
| 合并 | — | $1.0 + (-1.0) \to 0.0$ | — |

结果 0.0 。

**走法 C:split-K = 4,用原子加按完成次序合并**

原子加保证不丢更新,但 **不保证次序** 。四个局部值的到达次序由 GPU 调度决定,属于运行期物理事件。

把 24 种到达次序全部算一遍,结果只有三个值,且分布并不均匀:

| 结果 | 有多少种次序落到它 | 一个代表次序 |
|---|---|---|
| 0.0 | 12 | $10^{-8},\ -1.0,\ 10^{-8},\ 1.0$ |
| $1 \times 10^{-8}$ | 8 | $10^{-8},\ -1.0,\ 1.0,\ 10^{-8}$ |
| $2 \times 10^{-8}$ | 4 | $-1.0,\ 1.0,\ 10^{-8},\ 10^{-8}$ |

只有 4/24 的次序能拿到数学真值,而拿到真值的条件很具体: **必须让 $1.0$ 和 $-1.0$ 先抵消掉,两个小数才活得下来** 。反过来,如果先把两个 $10^{-8}$ 加在一起再遇上大数,那个 $2\times10^{-8}$ 照样会被吞掉,结果是 0.0 而不是真值。

### 1.4 三种确定性,vLLM 只承诺中间那层

上一节的三种走法对应两类完全不同的问题,把它们分开是理解本章的前提:

- A 与 B 的差异是 **确定但不同** :两条路径各自跑一万次都稳定,只是 kernel 按 batch 规模选了不同的切分,于是结果不同。
- C 是 **真不确定** :同一次调用重跑都可能变。

「确定性推理」这个词被滥用了,至少要区分三个强度递增的层次:

| 层次 | 名称 | 含义 | 不满足时的现象 |
|---|---|---|---|
| L1 | 同批复现 | 同一进程、同一 batch 组成、同样的输入,跑两次结果逐位相同 | 同一个请求重跑结果就不一样 |
| L2 | **批不变性** | 某条请求的输出与它同批的其他请求无关:单独跑和混在一批里跑,结果逐位相同 | 压测时正常,线上高并发时同一 prompt 答案变了 |
| L3 | 跨硬件、跨版本 | 换卡、换驱动版本、换并行度,结果仍逐位相同 | 换一代 GPU 之后评测分数变了 |

vLLM 的批不变模式 **只承诺 L2** ,顺带把 L1 里由 kernel 选择导致的抖动一起消掉。它 **不承诺 L3** 。官方文档把这个特性标为 beta,并挂着一个跟踪 issue。

「逐位相同」是这一章全程的判定口径,不是「误差在 $10^{-5}$ 以内」。测试里用的是逐位相等的判定函数,不是近似比较。

### 1.5 不是竞态,也不是种子没固定

工程上遇到「输出不一致」,最先想到的两个解释往往都不对。先排除掉,否则会一直修错地方。

**解释一:GPU 有竞态,加锁或加同步就好了。**

不对。走法 B 里根本没有竞态:两个线程块各写各的局部结果,再做一次确定的合并,跑一万次都是 0.0。它是完全确定的,只是和单条请求时选的走法 A 不一样。加锁、加显式同步、把 kernel 启动改成阻塞式,全部无效。

真正的因果链是: **batch 里 token 总数变了 → kernel 的启发式算出的切分变了 → 归约次序变了 → 结果变了** 。

**解释二:设了种子就该一样。**

种子只控制采样那一步的伪随机数,不控制前向里的归约次序。两者管的是不同的东西,而且互补:

- 种子保证「给定 logits,选择过程可复现」 —— 这条链路在 07 章 1.21 与 1.24 讲过。
- 批不变性保证「给定输入,logits 可复现」。

缺任何一个都不够。真实的失效场景是:种子固定、骰子完全相同,但 logits 因 batch 组成差了 $10^{-3}$ 量级,恰好某一步 top-1 与 top-2 的间距小于这个差值,取最大值时翻转,吐出不同的 token;下一步输入序列已经不同,之后完全发散。

vLLM 的端到端测试正是 **两样同时固定** :一个自动生效的夹具把批不变开关打开,采样参数里再写死种子。值得一提的是,那条测试的默认温度是 0.0,种子是给非零温度场景兜底用的。

### 1.6 PyTorch 那个确定性开关为什么不够

第三种解释是「用 PyTorch 的确定性算法开关一把梭」。

它解决的是 L1:禁掉 PyTorch 里带原子加、带非确定归约的算子实现。但它 **不要求算子对 batch 大小不变** —— 一个用 split-K、且 split 数随 M 变化的矩阵乘,完全可以既通过它的检查,又不满足批不变性。

这正是 L1 与 L2 的分界: **前者要求「同一个输入跑两次一样」,后者要求「同一条请求在不同邻居里一样」** 。后者严格更强,而且强出来的那部分恰好是那个开关管不到的。所以 vLLM 没走这条路,而是自己替换算子实现。

### 1.7 $10^{-8}$ 怎么变成完全不同的一段话

上面那些误差看着都很小($10^{-8}$ 到 $10^{-3}$)。为什么它们能把一整段话改掉?因为自回归解码是一个 **离散化加反馈** 的系统,有三级放大。

**第一级:层间累积。** 一个 decoder 层里,注意力输出经输出投影、再进 FFN 的三个矩阵,每一步都是一次矩阵乘归约加一次归一化归约。误差不是相互抵消而是随层数累积(近似随机游走,量级正比于 $\sqrt{L}$),残差连接会把误差直接搬到下一层。

**第二级:取最大值的离散跳变。这是关键的一级。** 最后一层输出 logits,贪心解码取最大值。设 top-1 与 top-2 的 logit 间距为 $\Delta$ ,扰动为 $\epsilon$ ,则翻转概率约为 $P(\Delta < \epsilon)$ 。

单个 token 上这个概率很小,但有两点要注意:词表很大,「恰好有两个候选贴得极近」在自然文本里非常常见(同义词、大小写变体、带空格前缀的同一个词、多语言 tokenizer 里的近似 token);而一次回答要生成成百上千个 token,是独立试验的重复 —— 哪怕单 token 翻转概率只有千分之一,128 步下至少翻一次的概率就是 $1 - 0.999^{128} \approx 12\%$ 。

**第三级:反馈发散。** 一旦第 $t$ 步吐出不同 token,第 $t+1$ 步的输入序列就不同了 —— 这不是「小扰动」,是 **输入变了** 。之后两条轨迹彻底无关。所以最终现象是「前半句一样,后半句完全不同」。

这条链的后两级值得单独记:vLLM 有一条专门的 **反向测试** ,把批不变关掉之后,断言单条跑与成批跑的 logprob 必须出现差异,全部相同反而算测试失败。它的文档字符串写得很直白:检测到差异才算通过,因为那证明批不变性确实在做事。

### 1.8 批不变性到底是什么:一个形式化定义

设 $f$ 是模型的一步前向,输入是一个请求集合 $\{x_1,\dots,x_n\}$ ,输出 $\{y_1,\dots,y_n\}$ 。批不变性要求:

$$
\forall i,\ \forall \text{任意其他请求集合} S,\quad f(\{x_i\})_i \ =\ f(\{x_i\} \cup S)_i \quad (\text{逐位相等})
$$

即 **每条请求的输出只依赖它自己** ,与同批伙伴的数量、长度、顺序、位置全部无关。

这正是 vLLM 端到端测试的写法,即所谓 **针测试** :把一条固定的探针 prompt 先单独跑出基线,再把它插到几十上百条随机长度 prompt 组成的 batch 的随机位置上重跑,要求生成文本完全一致。

### 1.9 比固定种子强在哪,比逐位复现弱在哪

- 比固定种子 **强** :种子只锁采样,批不变性锁的是前向数值。
- 比逐位复现 **弱** :它不承诺跨硬件、跨并行度、跨后端一致。

以下改动都会 **合法地** 改变结果,不算 bug:

| 改动 | 为什么结果会变 |
|---|---|
| 换 GPU 架构 | 老架构整体走手写 Triton kernel,新架构仍用厂商库,两者数值不同(1.16) |
| 改张量并行度 | 切分方式变了,每个 rank 的局部归约范围随之变 |
| 换注意力后端 | 各后端的数值实现本来就不同 |
| 换 dtype 或量化方案 | 舍入行为直接变了 |

一句话记忆: **批不变性是横向一致(同一份部署内,不受邻居影响),不是纵向一致(不同部署之间)** 。

### 1.10 为什么值得付这个代价

批不变模式一定更慢。官方文档列了四条动机,逐条展开为什么这些场景非它不可:

| 动机 | 不确定时会怎样 |
|---|---|
| 框架调试 | 输出本身是随机的,就无法做 A/B 对比 —— 打开批不变后,任何输出变化都必然由你的改动引起,二分定位才成立 |
| 模型实现调试 | 移植新模型时要和参考实现逐层对齐隐状态;若输出随 batch 抖动,「误差是实现 bug 还是数值噪声」根本没法判断 |
| 强化学习训练 | 见下 |
| 把 vLLM 当组件的大系统 | 上游做缓存、做回归 diff、做多副本一致性校验时,需要「同输入同输出」这个契约 |

第三条是最硬的需求,值得单独说。在 RLHF 这类流程里,生成用推理引擎、训练用训练引擎,算法上假设两侧对同一序列给出同一个对数概率。若推理侧的对数概率依赖 batch 组成,那么重要性比值就带上了 **与算法无关的噪声** :本该是 1.0 的比值变成 0.98 或 1.03,裁剪被无意义地触发,梯度被污染。表现是训练曲线不稳、复现不出别人的结果。这正是批不变性最近被重视起来的直接原因。

> 「评测可信度」这条动机同样成立,但它是本章补的,不在官方文档那一段里。

### 1.11 非确定性的六大来源

把 1.3 的玩具例子放大到真实推理栈,能造成「同一请求、不同 batch、不同结果」的机制一共六类。它们不是并列的六个 bug,而是同一条原理在六个地方的分身:

| # | 来源 | 为什么它依赖 batch | vLLM 的处理 |
|---|---|---|---|
| 1 | 矩阵乘的 split-K 与 tile 划分随 M 变 | M 就是 batch 内的 token 总数:单条 decode 时 M=1,128 条时 M=128,带预填充时 M 可达数千。厂商库按形状查启发式表选 kernel,M 小时算力浪费严重就 split-K 拉并行度,M 大时不 split | 老架构换成自写的常驻 kernel;新架构掐 workspace(1.13 与 1.16) |
| 2 | 注意力的 split-KV | decode 时 query 只有 1 个 token 但 KV 有几千个,为了不让流处理器空转,会把 KV 序列切成若干段并行算再合并。切几段通常按「批内序列数乘序列长度乘流处理器数」算出来 | 所有支持的后端一律把 split 数固定为 1(1.18) |
| 3 | 原子加归约 | 即 1.3 的走法 C。用原子加的实现连 L1 都不满足 | 常驻 kernel 内单个 program 独自完成整个 K 归约,不用原子加 |
| 4 | 厂商库的启发式选核与 workspace 大小 | 同一个形状,库会在若干候选 kernel 里挑一个,选择依赖可用 workspace 等运行期状态;workspace 一大就可能启用 split-K 变体 | 把 workspace 掐到极小,逼它只能选非 split-K 的实现(1.16) |
| 5 | 集合通信 | 张量并行下每层都要跨卡求和。通信库的算法、通道数、是否走特定加速路径、消息是否被切块,都会改变求和次序;而这些又依赖消息大小,消息大小正比于 token 数 | 关掉所有按规模自适应的快路径,把通信库的十一个旋钮全部钉死(1.12) |
| 6 | 降精度累加与 TF32 | 框架默认允许在半精度矩阵乘里做部分累加以提速,会放大次序敏感性;TF32 让单精度矩阵乘降到 10 位尾数算,开关状态还与 kernel 选择耦合 | 关掉降精度累加,把单精度路径强制设成严格标准 |

看完这张表可以回头确认 1.1 那句话: **六类全部是「配置选择」层面的问题,没有一类是「执行同步」层面的** 。

### 1.12 一个开关,三类手段

用户侧只有一个环境变量。离线用法要在导入 vLLM **之前** 设好,因为不少模块在导入时就把这个值读成了模块级常量 —— 注意力的 Triton 实现和 LoRA 的工具模块都是这样写的,导入之后再改环境变量对它们无效。

开关背后是三类手段:

| 手段 | 做什么 | 典型例子 |
|---|---|---|
| A. 替换算子实现 | 在框架的分发器层用批不变实现覆盖原算子;在 vLLM 自己的代码里用分支切到批不变函数 | 矩阵乘、批量矩阵乘、softmax、对数 softmax、求均值全部重定向;归一化层与线性层走专用分支 |
| B. 关掉「按规模自适应」的优化 | 凡是「根据 batch 或序列长度选不同 kernel、不同算法」的优化,一律固定或关闭 | 注意力 split 数固定为 1、MoE 的 split 固定为 1、级联注意力关闭、自写 all-reduce 关闭、提前编译关闭、新版注意力回退旧版 |
| C. 固定运行期配置 | 用环境变量把库的行为钉死 | 矩阵乘库的 workspace 配置、通信库的算法与通道数、单精度按严格标准算 |

手段 C 在通信这一侧尤其密集。开关打开后一次性钉死的通信库变量有十一个,覆盖四个维度:

| 维度 | 钉死成什么 |
|---|---|
| 算法 | all-reduce 强制走树形 |
| 并行度 | 最小与最大通道数都设成 1,线程数与套接字线程数都设成 1 |
| 协议与路径 | 协议设成 Simple,关掉网内计算与多播加速,禁用点对点走网络 |
| 启动方式 | 启动模式设成分组 |

被关掉的还不只是通信库自己的快路径。vLLM 为小消息手写过一个 all-reduce(它为什么值得写、什么时候才生效,见 09 章 1.14),批不变模式会把它连同另外两条加速路径一起禁掉 —— 它们都带着「按消息大小走不同分支」的逻辑,而消息大小正比于 token 数。

讲一个重要的架构判断:vLLM **没有** 做「批不变编译 pass」,也没有做全局的分发模式拦截,而是走了两条更朴素的路 —— 在分发器上直接替换算子实现,以及在几十处热点代码里插一个环境变量判断。代价是这些判断散落在注意力、MoE、量化、LoRA、通信各处,好处是零抽象开销、易于逐点放开。

### 1.13 批不变矩阵乘:让每个输出元素自己把 K 加完

这是整个特性的技术核心。

**目标** :让输出矩阵 $C$ 的每一个元素 $C_{ij} = \sum_k A_{ik}B_{kj}$ 的求和次序只依赖 $(i, j, K)$ ,不依赖 $M$ 。

**普通实现为什么做不到** :它按形状挑一套 tile 配置和 split-K 数。M 小的时候 tile 数少、流处理器填不满,就靠 split-K 补并行度;M 大就不 split。K 方向的分段数一变,加法树就变了。

**常驻 kernel 的做法** 分三步:

1. 只启动「流处理器个数」个 program,而不是「每个输出 tile 一个」。启动网格取的是流处理器数与 tile 总数的较小值。
2. 每个 program 用一个外层循环,以流处理器数为步长轮流领取输出 tile。这叫常驻风格:program 不退出,一直驻留着领活。
3. **关键** :对每个领到的 tile,program 在内层循环里把整个 K 维从头到尾归约完,累加器全程留在寄存器里,不落地、不与其他 program 交换。

于是三件事同时成立:

- **没有 split-K** :K 归约不跨 program,自然没有跨线程块的合并次序问题。
- **没有原子加** :每个输出 tile 只被一个 program 写一次,用的是普通写入。
- **归约次序** 由内层循环下标 $k_i = 0,1,\dots,\lceil K/\text{BLOCK\_K}\rceil - 1$ 给出,只由 $K$ 与 K 方向的块大小决定。

这样一来,M 变了会改变「tile 总数」和「哪个 program 领哪个 tile」,但不改变「每个 tile 内部的 K 归约次序」。program 领活次序变了只影响执行时间,不影响任何一个 $C_{ij}$ 的算法。

### 1.14 调优表按 M 分桶,为什么还算批不变

看源码会撞见一个像是自相矛盾的东西:批不变模式带着一张调优表,表里按 $M$ 分桶给不同的块大小与并行参数。M=1 和 M=100 落在不同桶、用不同的块大小 —— 这不是又回到「配置随 M 变」了吗?

不是。因为数据结构本身就是按这个区分设计的:表的外层键是 **形状** ,里层才是 M 桶;而 K 方向的块大小挂在 **外层** ,不随 M 桶变化。源码注释把意图写得很直白:超出调优范围的值复用最大的那个桶,而形状级的 K 块大小让这件事保持批不变。

推理链条是:

- $C_{ij}$ 的归约次序只由 K 方向的块大小与 $K$ 决定(1.13 的第 3 点)。
- M 与 N 方向的块大小只决定 **哪些 $(i,j)$ 被分到同一个 tile** ,即「谁和谁一起算」,不改变「每个 $(i,j)$ 内部怎么加」。
- 所以改 M 方向的块大小不影响任何单个输出元素的值。

这条不变式有专门的测试守着:参数化四个跨不同桶的 M 值、并覆盖两种内存布局,断言取第一行单独算与整批算的结果逐位相等。测试注释直接点明意图 —— 调优过的 M 桶必须保住每一行的 K 归约次序。

> 这是本章最值得记住的一条设计洞察: **批不变性要求的不是「配置固定」,而是「归约维的切分固定」** 。只要 K 方向的切法不变,M 与 N 方向怎么调优都是安全的 —— 这给性能优化留出了空间。

### 1.15 同一条原则的第二个实例:共享内存决定 N 方向块大小

上一节那条原则不是只用了一次。开关打开时还有一处:vLLM 会查一次设备的共享内存容量,据此把 N 方向的块大小定成 256 或 128;单精度且 N=1 这种细长形状再单独降一档,源码注释点名某个具体架构在这个组合上会因资源不足编译失败。

这同样是「按设备属性改配置」,同样不破坏批不变性,理由和上一节一模一样: **改的是 N 不是 K** 。

两个实例合起来能看出这套设计的分寸:调优的自由度全部留在 M 与 N 两个方向,K 方向一寸不让。也因此,它换来的是 L3 的丧失 —— 换一张共享内存容量不同的卡,块大小就变,数值随之变。1.9 那张表里「换 GPU 架构」一行,这里是它的一个具体机制。

### 1.16 新架构为什么不换 kernel,只掐 workspace

读代码会发现一个不对称:只有 Ampere 家族注册自写的常驻矩阵乘,更新的架构走另一条路。源码注释解释了原因:

- Ampere **不能** 只靠厂商库的确定性保证,所以必须整体换成自写 kernel。
- Hopper 与 Blackwell 上,批不变性的 **唯一** 破坏源是 split-K 变体;而 split-K 需要额外的 workspace 存局部结果。把 workspace 配置压到极小,split-K 变体就没有落脚之地,厂商库只能选非 split-K 的实现。

这个选择的性能意义很大: **新架构上仍然用厂商高度优化的库,只是禁用一小类 kernel;老架构上要整体退回手写 kernel,性能损失自然更大。**

而且损失比讲到这里更深一层。那张按形状分桶的调优表只覆盖三个架构族,而且 **只对 bf16 生效** ;Ampere 恰好不在覆盖范围内。也就是说,Ampere 是唯一被迫整体走自写 kernel 的架构族,却又拿不到调优表,只能吃默认的通用配置。 **两件事叠在一起,才是老架构上代价最大的完整理由。**

### 1.17 两次设置打架,后设的那次赢

有一处执行顺序造成的覆盖,只看其中一处会误判。

初始化时依次做三件事:先解析调优表,再统一覆盖一批环境变量,最后才启用批不变模式。而矩阵乘库的 workspace 配置在 **第二步和第三步各被写了一次** ,值还不一样:第二步统一设成一个较大的值,第三步的新架构分支把它改成极小值。

于是最终生效的是:新架构上是极小值(1.16 要的那个),Ampere 上是第二步那个较大值 —— 因为 Ampere 分支不覆盖它。

这类「同一个配置被写两次」的坑在排障时很典型:搜到第一处就下结论,会得到和运行期完全相反的判断。

### 1.18 注意力:为什么必须把 split 数固定成 1

注意力的归约维是 KV 序列长度。decode 时 query 长度为 1,若不切 KV,一个请求只能用很少几个线程块,大量流处理器空转 —— 所以会把 KV 切成若干段,各段算局部的分子分母,再用一个合并公式拼回去。这条 decode 侧的切分路径在 02 章 2.7.5 讲过,本章只关心它对批不变性的影响。

合并本身是确定的,但 **分几段是按 batch 规模算出来的** 。段数变则合并树变,结果就变。所以批不变模式的做法整齐得近乎粗暴: **所有支持批不变的后端都把 split 数固定为 1** 。

各后端的具体手法不同,但目标一致:

| 后端家族 | 做法 |
|---|---|
| FlashAttention | 最大 split 数与调用时传入的 split 数都设成 1,并关掉提前编译的调度(它依赖批内最大序列长度) |
| FlashAttention 新版 | 新版在特定架构上用依赖 batch 形状的调度启发式,直接强制回退旧版 |
| Triton 注意力 | 强制走二维 kernel,禁用按 KV 切段的三维 kernel |
| Triton 版 MLA | KV 方向的 split 数固定为 1,否则会按最大序列长度与流处理器数动态算 |
| FlashAttention 版 MLA | 构造器与每次调度各设一次最大 split 数为 1 |
| MLA 的预填充子路径 | split 数设成 1;某架构上 split 数不为 1 直接判定不支持 |
| 灵活注意力 | 两个方向的块大小都固定,并禁掉依赖形状的「整除快路径」 |

注意最后一行还有一条配套约束:灵活注意力的块大小不能超过 KV 缓存的块大小,超了直接在构造时报错,错误信息里就写着这是为了批不变。

### 1.19 真正能用的是五个后端

上一节那张表容易读出一个过强的结论:这些后端在批不变模式下都能用。实际不是。

后端是否可用由一个 **能力声明** 决定 —— 基类上有个方法默认返回「不支持」,各后端显式覆盖成「支持」。选择器把批不变开关塞进选择配置,校验时发现开关打开而后端不支持,就把「批不变不支持」加进失败原因;这条校验在自动选择与显式指定两条路径上都会执行。能力声明与失败原因这套机制在 05 章 1.4 与 2.1 讲过。

在基准上, **只有五个后端声明支持批不变** :FlashAttention、Triton 注意力、灵活注意力、Triton 版 MLA、FlashAttention 版 MLA。

所以上一节那张表里的七行其实是三类东西,读代码时要分清:

| 类别 | 有哪些 | 开了批不变还选得中吗 |
|---|---|---|
| 声明支持的顶层后端 | 上面那五个 | 能 |
| 有批不变代码、但没声明支持的顶层后端 | FlashInfer、FlashMLA | **不能** —— 校验会拒掉,那些代码在这条路上够不着 |
| 不是顶层后端,而是被上面某个后端复用的子路径或公共工具 | MLA 的预填充子路径、新版回退的判定、某些融合注意力的门控 | 能,因为它们由能被选中的后端调用 |

Mamba 一类的后端更直接:不支持就在选择时抛异常,不进入失败原因那套流程。

### 1.20 顺带被关掉的两个功能

开批不变会连带关掉两个用户可能以为还开着的功能。

**级联注意力** 。它把「公共前缀」和「各自后缀」分两次算再合并,合并方式依赖 batch 里有多少请求共享前缀 —— 这是天然的批相关(它是什么见 05 章 1.5)。所以配置校验阶段直接把它置成禁用并打一条 warning。

**前缀缓存** 。在某些后端下前缀缓存与批不变尚未打通,vLLM 会自动把它关掉并 warning。这是一个 **静默的性能悬崖** :用户以为开着前缀缓存,实际被降级了。

这里有一个读代码容易读错的地方:那段逻辑里点名了两个后端,但其中一个按 1.19 的结论 **在批不变模式下根本选不中** ,所以真正会触发这段的只有 Triton 版 MLA 那一个。看到「两个后端都有这个坑」会高估影响面。

### 1.21 归一化为什么也要重写

除矩阵乘与注意力外,凡是沿某个维度做归约的算子都有同样的问题。它们的归约维不是 batch 维,但实现上常按「总行数」决定每行分几个线程块、用多大的块大小 —— 行数一变,行内加法的分段就变。

vLLM 的统一手法是: **一行(一个归约单元)交给一个 program 串行做完,块大小写成常量** 。

| 算子 | 批不变实现 | 关键点 |
|---|---|---|
| 对数 softmax | 自写 Triton kernel | 一个 program 一行;三趟扫描(求最大值、求指数和、写结果);块大小硬编码成常量 |
| softmax | 纯框架算子组合(求最大值、减、指数、求和、除) | 不用融合 kernel;减最大值保数值稳定 |
| 求均值 | 先转单精度,再对排序后的维度逐个调自写 kernel | 多维均值拆成一串单维均值(1.22) |
| 归一化层(无残差) | 自写 Triton kernel | 平方和用单精度累加;块大小写成常量 |
| 归一化层(带残差) | **直接调 C++ 实现** | 说明该 C++ kernel 本身已批不变,有专门的测试守着 |
| 批量矩阵乘 | 自写 Triton kernel | 每个 program 算一个「批索引加两个 tile 索引」,K 次序固定 |

有一个细节值得注意:softmax 没用自写 kernel,对数 softmax 用了。从代码形态可以推测原因( **此为推断,源码未注释** ):批不变的 softmax 只需要求最大值和求和两个归约,这两个在固定维度上本身就批不变;而对数 softmax 的框架实现是融合 kernel,内部分段策略不可控,只能整体替换。

### 1.22 求均值为什么要先把维度排序

多维均值的实现里有一步排序:把要归约的维度取模规整后 **从大到小** 排,然后逐维归约,循环里保持形状,最后统一压掉。

这一步是必要的,但它同时服务两件不同的事,读的时候容易混成一件:

- **排序本身** 保证归约次序唯一。不排序的话,同一个调用写成两种维度顺序会按不同次序归约,浮点结果不同 —— 这是批不变要的那一半。
- **从大到小这个方向** 是为了最后压维度时下标不失效。源码注释说的正是这一件,与批不变无关。

把这两件事分清很重要,因为有一个看似合理的解释是错的: **不能说「不排序会经历不同的中间形状序列」** 。循环里每一步都保持形状,两种写法的中间形状完全相同;真正不同的是 **加法的次序** 。

### 1.23 换个硬件后端,这四个算子天然就批不变

上面两节是在 NVIDIA GPU 这个前提下讲的。基准上还支持 Intel 的 GPU,而在那条路径上,对数 softmax、softmax、求均值、批量矩阵乘这四个算子 **根本不注册覆盖** 。

源码注释给的理由很干脆:这四个算子在那个平台上本来就是批不变的,底层数学库无论 batch 上下文如何都给出逐位相同的结果。

这条事实的价值不在于多支持了一种硬件,而在于它把本章的性质说清楚了: **批不变性不是一个普适的工程难题,它是特定 kernel 实现方式的产物** 。同一个数学运算,换一套底层实现,这个问题可以压根不存在。vLLM 要做这么多替换,不是因为「归约必然不确定」,而是因为 NVIDIA 这条路径上的实现为了性能普遍采用了按规模自适应的切分。

顺带,矩阵乘那条路在这个平台上走的是另一份 kernel(基于张量描述符的常驻实现),配置也另有一套按形状的选择逻辑 —— 与 1.14 的 M 桶表是两张表。

### 1.24 MoE 的三处隐藏依赖

MoE、量化、LoRA 这三块最容易被忽略,因为它们的「batch 依赖」不在浮点归约上,而在 **配置查表和排序** 上。先看 MoE。

**依赖一:调优配置按 M 查表。** 平时会按专家数、中间维、数据类型等去加载一份调优表,表内再按 batch 大小分桶。批不变模式直接返回空,放弃调优,注释就写着「批不变这一档不要为它做优化,用默认配置」。

**依赖二:默认配置里的 split。** 批不变模式返回一套固定的块大小配置,其中 K 方向的 split 数固定为 1。

**依赖三:选专家时的排序参数,这是最隐蔽的一处。** 路由器用 top-k 选专家。不排序更快,但 **并列值的返回次序不保证** ;专家编号的次序会影响后续分组与收集散射的累加次序,最终影响输出。所以批不变模式统一要求排序。同一个标志在分组路由器里用了三处,带偏置的路由器里也用了一处。

MoE kernel 的能力声明与注意力 **完全同构** :基类上一个默认返回「不支持」的静态方法,支持的实现覆盖成「支持」,不支持的在配置校验里被拒,理由字符串就是「批不变」。基准上覆盖成支持的有三个实现。

> 同构不是巧合:两处面对的是同一个问题 —— 一堆可替换的 kernel 实现里只有一部分满足批不变,需要一个统一的方式把不满足的挡在选择之外。

### 1.25 量化:固定挑一条数值路径

量化 kernel 往往有多条实现,彼此归约结构不同,且部分实现按 M 切换策略。批不变模式的原则是 **固定挑一条** ,不再让它按规模自适应:

| 场景 | 批不变模式下的选择 |
|---|---|
| FP8 线性层 | 优先走直接 FP8 的路径,否则退回半精度反量化 |
| FP8 在线量化 | 走专门分支 |
| NVFP4 线性层 | 强制某一套模板库实现;平台不支持则强制走模拟实现 |
| AWQ | 走半精度矩阵乘那一支 |
| 两类专用的缩放矩阵乘 | 各走专门分支 |

kernel 候选是怎么筛出来的,11 章 2.2 讲过,这里只是给那套筛选加了一条新的约束。

有一处日志措辞值得单独记: NVFP4 那一档会明确告诉用户,批不变开关 **覆盖了** 你用命令行指定的后端。这类「环境变量静默胜过命令行参数」的行为是排障时的常见困惑点 —— 好在这一处并不静默,它打了日志。

### 1.26 LoRA:一行教科书式的反例

LoRA 的降维投影输出维度很小,为了并行度,默认用的策略是「batch 小于某个阈值时 split 成 64 段,否则 8 段」。

这一行代码本身就是「按 batch 选归约段数」的教科书式反例:归约段数直接写成了 batch 的函数。批不变模式把它置成 1。

同一个模块里还有一处配套处理:用户自己提供的调优配置目录,在批不变模式下会被忽略 —— 否则用户的调优表可能又把段数改回去。 **关掉一个自适应,还要堵住能把它打开的那扇门** ,这个模式在本章出现了不止一次(1.24 的调优表、1.25 的命令行后端,都是同一件事)。
