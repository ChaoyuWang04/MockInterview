# vLLM 07|采样机制

模型前向交出来的是一张十几万列的分数表,采样要从里面挑出一个 token。这一章讲这条从分数到 token 的流水线:每一步在改什么、为什么是这个顺序,以及为什么它全程不许有一次同步。后三分之一换一个提法——**一次能不能定下好几个 token**,那是推测解码的拒绝采样,从 1.36 起。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与方法,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 挑一个 token,难在哪

一次前向的最后一步是 LM head,产出 `[请求数, 词表大小]` 的 **logits** ——每个 token 一个未归一化的分数,词表大到十几万列。采样要做的事一句话就说完:**从这一行里挑一个**。

难的不是「挑」,是挑的方式要同时满足五件互相牵制的事:

| 痛点 | 采样层的应对 | 本章位置 |
|---|---|---|
| 永远挑分数最高的那个,输出重复、呆板 | 给「挑哪个」装上一组可调旋钮 | 1.11 起 |
| 旋钮一放开,概率极低的胡话也会被选中 | 先裁掉候选集,再在裁剪后的分布里随机 | 1.14 起 |
| 同一批里每个请求的旋钮位置都不同,GPU 却要一次算完 | 参数全部张量化,kernel 按请求下标间接寻址 | 1.26 |
| 这些旋钮互相影响,顺序错了语义就变 | 执行顺序被写死,而且在文档字符串里立了规矩 | 1.2、1.10、1.13 |
| **一次只挑一个太慢,而一次挑好几个又会把分布挑歪** | 让草稿先猜,再用拒绝采样逐个验证 | 1.36 起 |

前四条是「**从一行分数里挑一个**」这件事内部的张力,占本章前三分之二。**最后一条是把问题整个换了个提法**:既然 decode 的算力大量闲着(06 章算过),能不能一次前向就定下好几个 token?能,但验证方式稍有不慎就会让输出分布偏离模型本身——**这就是拒绝采样要解决的事,从 1.36 起另起一条线。**

还有一条贯穿全章的暗线:**采样坐在热路径的最末端**。06 章算过那笔账——decode 一步里 CPU 下发已经快压不住 GPU 了,这时候采样这边只要出现一次 GPU 到 CPU 的同步,整条流水线就断在这里。所以这一章里有好几个看上去绕的写法,动机都是同一个:**不排序、不同步、不回 CPU** 。

### 1.2 顺序本身就是设计

采样不是一个函数,是一条有严格先后的流水线。这个顺序不是实现的偶然产物——源码把它写进了采样器类的文档字符串,九步一条不落,注释里管它叫 canonical order(规范顺序)。

一次采样从头走到尾:

```text
logits: [请求数, 词表大小]
  │
  ├─ 若请求了 logprob:先把原始分数拍个快照   ← 在任何加工之前(1.27)
  ├─ 转成 float32
  │
  ├─ ① 划掉不该选的:白名单、禁词          (1.4 – 1.7)
  ├─ ② 惩罚已经说过的:三种 penalty        (1.8 – 1.9)
  ├─ ③ 温度缩放                            (1.11)
  ├─ ④ 裁剪候选集:min_p → top_k → top_p    (1.14 – 1.19)
  ├─ ⑤ softmax → 概率分布                  (1.20)
  ├─ ⑥ 采样:贪心 / 随机                    (1.21 – 1.25)
  │
  └─ sampled_token_ids: [请求数, 1]
```

① 到 ④ 全都是在往 logits 上写 `-∞` 或者做算术,**没有一步会改变张量形状** 。这是整条管线能做成「原地改一块 GPU 内存」的前提。

后面 1.10 和 1.13 会证明其中两处相邻关系换不得。**换了不会报错,只会让参数的语义悄悄变成另一个意思** ——这类 bug 最难发现,所以才值得把顺序写进文档字符串。

### 1.3 两套采样器,顺序不完全一样

06 章说过执行层有两套模型运行器,V2 是默认。采样器跟着分成两套,**而且这两套的步骤顺序不一样** 。

先说相同的部分:两套都遵守 1.2 那条主干,①②③④⑤⑥ 的大顺序一致,温度一定在惩罚之后、裁剪之前。差别在细处:

| | V1 采样器 | V2 采样器(默认) |
|---|---|---|
| 白名单 | 单独一句掩码填充,硬编码在函数体里 | 与 logit 偏移、最少 token 数合并成**一个** kernel |
| 禁词 | 排在惩罚**之前** | 排在惩罚**之后** |
| 参数加工 | 逐个张量操作,每步产生中间结果 | 逐个 Triton kernel,原地改 |
| 总闸 | 无 | 全批都不需要加工时,连 float32 拷贝都跳过 |

禁词那一行值得多看一眼:**两套的相对顺序是反的,而结果相同** 。因为禁词做的是把 logit 设成 `-∞` ,而三种 penalty 要么是减法、要么是乘一个正数——`-∞` 减掉任何有限值还是 `-∞` ,乘正数也还是。两个操作可交换,所以谁先谁后无所谓。**但这不是普遍规律** ,1.10 那对就不可交换。

> 本章后面凡是两套实现有实质差别的地方都会标明说的是哪一套,只说「采样器」时指两套都成立。

### 1.4 第一道加工:把不该选的直接划掉

最强硬的一种控制是 **allowed_token_ids(白名单)** :给出一份 token id 清单,不在清单里的全部设成 `-∞` 。

为什么是 `-∞` 而不是删掉那些列:因为后面要做 softmax,而 `e^{-∞} = 0` ——被划掉的 token 概率精确为 0,**永远不可能被选中** ,同时张量形状一个字都没变。整条管线都靠这个技巧做「删除」。

举例说明它有多硬。设词表只有五个 token,这一步的分数是:

```text
猫: 2.5  |  狗: 1.8  |  鱼: 3.0  |  鸟: 0.5  |  人: 1.2
```

正常采样多半会挑「鱼」(分数最高)。但如果白名单只给了「猫」和「狗」:

```text
猫: 2.5  |  狗: 1.8  |  鱼: -∞  |  鸟: -∞  |  人: -∞
```

softmax 之后鱼、鸟、人的概率都是 0,模型只能在猫和狗之间选。**这是一个保证,不是一个倾向。**

### 1.5 白名单是结构化输出的底座

白名单最主要的用途不是让用户手写清单,而是给结构化输出当底层机制。语法引擎每生成一个 token 就重算一次「当前位置哪些 token 合法」,把结果交给采样器,采样器照着划掉其余的。

以输出 `{"age": <number>}` 为例,当模型已经写到 `"2"` 时,合法的下一个 token 只有数字 `0`–`9`(继续写数字)和 `}`(结束),字母、空格、标点全部非法。语法引擎算出这个集合,这一步就只剩下这十一个候选。

这条链路的上游—— 位掩码怎么生成、缓冲区怎么跨 step 复用、为什么压 `-∞` 这个动作发生在 GPU Worker 而不是引擎进程、以及语法没跟上时那一步怎么推迟采样—— **01 章已经完整讲过** ,这里不重复。采样这一侧要知道的只有一件事:**它收到的就是一份普通的白名单,不区分是用户给的还是语法引擎给的。**

V2 给白名单加了一道 V1 没有的限制:**单个请求的白名单最多 1024 个 token** ,超了直接抛错。原因在两套的存法不同——V1 存的是一整行按词表长度的布尔掩码,多长都装得下;V2 存的是 token id 列表,得按上限预分配定长的一行。**同一个功能,两套实现的代价结构不一样** ,这在本章会反复出现。

### 1.6 白名单与 logit 偏移:一个是限制,一个是倾向

和白名单容易混的是 **logit_bias** :给指定的 token id 加一个偏移量,正值提高概率、负值降低。

| | 白名单 | logit 偏移 |
|---|---|---|
| 做的事 | 名单外的分数设成 `-∞` | 指定 token 的分数加减一个值 |
| 效果 | 硬限制,名单外概率恒为 0 | 软倾向,被压低的 token 仍可能被选中 |
| 用途 | 结构化输出、分类任务限定值域 | 引导风格,让模型偏好或回避某些词 |
| 给多大的值管用 | 不需要调,是开关 | 要试,取决于原始分数的量级 |

最后一行是实用上的差别:偏移量该给 3 还是 30,得看这个位置上的分数差本来有多大,没有通用值;白名单没有这个问题,它不是程度而是有无。

**要「保证」就用白名单,要「倾向」才用偏移。** 拿偏移去做保证是个常见错误——给个 `-100` 看起来足够狠,但只要合法候选全都更低,它照样会被选中。

### 1.7 禁词:白名单的反面,但要看历史

**bad_words(禁词)** 是把指定的 token 序列禁掉。它和白名单形状相似(都是设 `-∞` ),但多了一个维度:**禁的是序列,不是单个 token** 。

禁单个 token 很简单,每步无脑划掉就行。禁「北京烤鸭」这样的多 token 序列就不能这么干——总不能把「北京」两个字彻底禁了。实现的办法是**只在最后一刻拦** :每步检查已经生成的尾巴是不是正好匹配到禁词的倒数第二个 token,匹配上了才把最后那个 token 划掉。前缀照常允许生成,只在它要凑成完整禁词的那一步才动手。

代价是这一步**必须读已生成的 token 序列** 。白名单只看参数,禁词还要看历史——这就引出了下一组更依赖历史的参数。

### 1.8 三种 penalty:只有一种看 prompt

penalty(惩罚)解决的是最原始的那条痛点:**模型会车轱辘话来回说** 。三种惩罚从三个角度压制重复。

| 参数 | 算法 | 数的是什么 | 直觉 |
|---|---|---|---|
| `repetition_penalty` | 乘法式:分数为正就除以它,为负就乘以它 | 该 token **出现过没有** | 说过的词整体降权 |
| `frequency_penalty` | 加法式:分数减去「惩罚值 × 出现次数」 | 该 token **出现了几次** | 说得越多罚得越狠 |
| `presence_penalty` | 加法式:分数减去「惩罚值 × 是否出现过」 | 该 token **出现过没有** | 说过一次就罚,不管几次 |

乘法式那个的分段写法值得解释一下:为什么分数为正要除、为负要乘?因为目标是**让分数变小** 。正数除以大于 1 的数会变小,负数除以它反而会变大(更接近 0),所以负数那边必须改成乘。一句 `where` 就把两种情况都盖住了。

**这张表里最容易想当然的是「数的是什么」那一列。** 三种惩罚里 **只有 repetition 会看 prompt** ——它取的是「出现在 prompt 里,或者出现在已生成的输出里」;frequency 和 presence 只数已生成的输出,prompt 说过什么完全不影响它们。

这个不对称不是疏忽。源码注释直接给了出处:frequency 和 presence 这两个 **按 OpenAI API 的定义实现** ,而 OpenAI 那边的语义就是只管输出。repetition 不是 OpenAI 的参数,它来自另一支社区实现,语义本来就包含 prompt。**两个参数长得像,血统不同。**

实用后果:想让模型别照抄 prompt 里的词,`frequency_penalty` 是没用的,得用 `repetition_penalty` 。

### 1.9 penalty 的账怎么记:一套回 CPU,一套不回

三种惩罚都要知道「每个 token 出现了几次」,也就是一张按词表长度的计数表。这张表怎么来,是两套实现差别最大的地方,也是 V2 存在的理由之一。

| | V1 | V2 |
|---|---|---|
| 历史 token 在哪 | Python 嵌套列表,在 CPU 上 | 一直在 GPU 上 |
| 每步做什么 | 把列表补齐成定长张量,再传上 GPU | 直接在 GPU 上数 |
| 计数 | 传上去之后再统计 | 自带的计数 kernel |
| 三种惩罚 | 三段张量运算 | 一个融合 kernel 一次算完 |

V1 那条路每一步都要把**整个请求的历史 token** 重新打包上传一次。序列越长、batch 越大,这笔开销涨得越快。源码注释自己认了账,原话是说这个实现目前相当低效、反正之后要重做。

V2 把这件事整个挪到 GPU 上:历史 token 本来就留在显存里(06 章 1.44 讲过采样结果根本不回 CPU),那么数它们也在显存里数就行,**CPU 一个字节都不用碰** 。这是那条原则的又一次应用——**能不过 PCIe 就不过。**

代价记在另一本账上:那张计数表的形状是 `[并发上限, 词表大小]` ,源码里挂着一条 TODO,说它很少用到但可能大到几个 GB。**一个默认关闭的功能,预分配的显存却是按开着算的。**

### 1.10 为什么惩罚必须排在温度之前

这是第一对换不得的相邻步骤。理由很直白:**加法式的惩罚会被温度缩放稀释** 。

用具体数字看。词表 `[A, B, C]` ,原始分数 `[2.0, 1.0, 0.5]` ,B 已经出现过 2 次,`frequency_penalty=0.5` ,`temperature=0.5` 。

正确顺序(先惩罚,再温度):

```text
① 惩罚:B 减去 0.5 × 2 = 1.0  →  [2.0, 0.0, 0.5]
② 温度:全部除以 0.5           →  [4.0, 0.0, 1.0]
③ softmax                      →  [0.936, 0.017, 0.047]
```

颠倒顺序(先温度,再惩罚):

```text
① 温度:全部除以 0.5           →  [4.0, 2.0, 1.0]
② 惩罚:B 减去 1.0             →  [4.0, 1.0, 1.0]
③ softmax                      →  [0.910, 0.045, 0.045]
```

B 的概率一个是 0.017,一个是 0.045,**差 2.6 倍** 。原因看第二步就清楚了:温度先把 B 的分数从 1.0 放大到 2.0,再减掉 1.0 只等于削掉了一半;而正确顺序是在原始尺度上减掉 1.0,把它整个抹平。

**用户设 `frequency_penalty=0.5` 时,心里想的是「在模型原本的尺度上减半个单位」,不是「在被温度放大过的尺度上减」。** 顺序保住的是这个预期。

乘法式的 repetition 其实不受影响(除法和乘法可交换),但两种惩罚在同一步里做,顺序只能按更严格的那个定。

### 1.11 温度:一个除法,改的是分布的尖锐度

**temperature(温度)** 是全部参数里最常被调的一个,而它的实现就是一句逐元素除法:所有分数除以温度值。

除法为什么能改变随机性,看 softmax 的形状就明白:softmax 放大的是**分数之间的差距** 。除以一个小于 1 的数,所有差距被同比放大,最高分和次高分拉得更开,概率集中到头部;除以大于 1 的数,差距被压缩,分布变平,尾巴上的 token 也分到了可观的概率。

| 温度 | 对分数做什么 | 分布 | 行为 |
|---|---|---|---|
| `T < 1` | 差距放大 | 更尖锐 | 保守,高概率 token 更容易被选 |
| `T = 1` | 不变 | 原样 | 模型原始分布 |
| `T > 1` | 差距压缩 | 更平坦 | 发散,低概率 token 也有机会 |
| `T = 0` | —— | —— | 特殊档:直接取最大值,不走随机路径(1.21) |

`T = 0` 是特殊档而不是极限值,因为除以零没有意义。实现上,一批里只要不是全部请求都要随机,就先把等于 0 的温度换成 1.0 再做除法——**换掉只是为了让这一行的除法不炸,这些请求的结果稍后会被贪心那条路的结果覆盖掉** 。

### 1.12 温度 kernel 的两个早退

V2 的温度是个 Triton kernel,它开头有一个判断:**温度等于 0.0 或者等于 1.0 时直接返回** 。注释写明了理由——早退是为了**连 logits 都不加载** 。

这两个值都是恒等操作:等于 1 就是除以 1,等于 0 的请求反正要走贪心。但如果老老实实走完 kernel,代价是把这一行十几万个 float 从显存读进来、除一遍、再写回去。词表 15 万、float32,一行就是 600KB 的读加 600KB 的写;batch 里若有一半请求是这两种情况,省下的带宽相当可观。

**判断放在加载之前,是这个优化的全部内容。** 同样的手法在 min_p 的 kernel 里又出现了一次(`min_p == 0` 直接返回),在 penalty 的 kernel 里也有。**在 memory-bound 的 kernel 里,「不读」就是最有效的优化。**

值得注意的是这个早退是**逐请求**的:kernel 的每个程序实例负责一个 token,各自判断各自的温度,所以同一批里有的请求早退、有的照算,互不影响。这依赖参数按请求下标间接寻址,见 1.26。

### 1.13 为什么温度必须排在裁剪之前

第二对换不得的相邻步骤。理由和 1.10 是对称的:**top_p 的截断点取决于概率分布的形状,而温度正是改变形状的那一步。**

词表 `[A, B, C, D, E]` ,原始分数 `[3.0, 2.5, 2.0, 1.5, 1.0]` ,`top_p = 0.8` 。

```text
T = 0.5:  分数除以 0.5 → [6, 5, 4, 3, 2]
          softmax      → [0.636, 0.234, 0.086, 0.032, 0.012]
          累积到 0.8:  A=0.636, A+B=0.870 ≥ 0.8   → 保留 {A, B}

T = 2.0:  分数除以 2.0 → [1.5, 1.25, 1.0, 0.75, 0.5]
          softmax      → [0.310, 0.241, 0.188, 0.146, 0.114]
          累积到 0.8:  A+B+C=0.739, +D=0.886 ≥ 0.8 → 保留 {A,B,C,D}
```

同一个 `top_p = 0.8` ,低温留 2 个候选,高温留 4 个。这正是它应该有的行为:**温度先决定「模型有多确定」,top_p 再据此决定「留多少候选」** 。

反过来先裁剪再调温度,top_p 就是在 `T = 1` 的原始分布上做的截断,截完再调温度——得到的既不是低温该有的紧候选集,也不是高温该有的宽候选集,**这个参数组合失去了可解释的语义** 。

**top_k 不受这个顺序影响** :它只看分数排序,而除以一个正数不改变排序。但 top_k 和 top_p 在同一个函数里做(1.18),所以照样排在温度之后。

### 1.14 三把裁剪的刀

裁剪这一步要回答同一个问题的三种问法:**这一步允许模型在多大的候选集里挑?**

| 参数 | 判据 | 候选集大小 | 关掉时的值 |
|---|---|---|---|
| `top_k` | 分数最高的 k 个 | **固定个数** | 等于词表大小 |
| `top_p` | 累积概率**首次达到** p 的最小集合 | 随分布变 | 1.0 |
| `min_p` | 概率 ≥ `min_p × 最大概率` | 随分布变 | 0 |

`top_p` 那行的「首次达到」要写成 **累积 ≥ p** 而不是 ≤ p:取 ≤ p 的话,p 比最大概率还小时会选出空集。顺带一提,`top_k=1` 就等价于贪心 —— 只剩一个候选,随机采样也只能采它。

三者是并联的过滤器,不是三选一:同时设了就依次都过一遍,交集就是最终候选集。执行顺序固定为 **min_p → top_k → top_p** 。

前两把刀的直觉容易建立。min_p 需要单独解释一句:它的阈值是**相对于当前这一步的最大概率**算出来的,所以同一个 `min_p` 值,在不同的 step 上对应着不同的绝对阈值。它问的不是「留几个」也不是「留多少概率质量」,而是 **「允许比最优选项差多少倍」** 。

### 1.15 同一个分布,三把刀给出三种答案

把三把刀放在同一个分布上比,性格差异立刻显出来。设 `top_k=3` 、`top_p=0.9` 、`min_p=0.05` ,分别作用在一个尖锐分布和一个平坦分布上。

![同样三把裁剪刀在两个分布上的对比:上半是概率柱状图,左边是尖锐分布 0.90/0.05/0.03/0.01/0.01、右边是平坦分布 0.40/0.30/0.15/0.10/0.05,两边同一刻度;下半每行是一把刀留下的候选,实心格子表示保留、空心表示被设成负无穷。top_k 那一行在两边完全相同,而 top_p 与 min_p 两行从左到右各自变长并双双越过 top_k,严格度的次序整个翻转](/opensource/vllm/07a-cutoff-flip.svg)

六个结果是这么算出来的:

| 参数 | 尖锐分布 | 平坦分布 |
|---|---|---|
| `top_k=3` | 固定三个,不管概率多低 | 仍是固定三个 |
| `top_p=0.9` | A 自己就是 0.90,已经够 0.9 | 前三个只有 0.85,得加上 D 才够 |
| `min_p=0.05` | 阈值 = 0.05 × 0.90 = 0.045,B 的 0.05 刚好过线 | 阈值 = 0.05 × 0.40 = 0.02,最小的 E 也远高于它 |

三种性格由此显出来:

- **`top_k` 是绝对的** 。分布长什么样它都留三个。对分布形状完全不敏感,这既是它的稳定性也是它的缺点。
- **`top_p` 盯的是概率质量** 。分布尖锐时它最狠(一个 token 就够 0.9),分布平坦时反而放宽。
- **`min_p` 盯的是相对差距** 。分布尖锐时最大概率大、阈值高、过滤严;分布平坦时阈值低、几乎不过滤。

于是 **top_p 和 min_p 在两张表里的严格度正好相反** 。这解释了 min_p 的设计意图:它不试图控制候选集大小,而是保证被选中的 token 不会比最优选项差太多——**模型没主意的时候,就别乱裁。**

### 1.16 min_p 不影响贪心,而这个分类有实际用处

采样器把所有 logits 加工步骤分成两类,判据是一个方法:**这一步会不会改变「分数最高的是谁」** 。

- **会改变的(非 argmax 不变)** :白名单、禁词、最少 token 数、logit 偏移、三种 penalty。它们都可能把原本的第一名压下去。
- **不会改变的(argmax 不变)** :min_p。

min_p 为什么一定不改变第一名,一行就能证明:它的阈值是 `min_p × 最大概率` ,而最大概率本身显然 ≥ `min_p × 最大概率` (只要 `min_p ≤ 1` )。**第一名永远过得了自己设的线。**

这个分类不是为了分类学,它有一处直接的用途:**贪心请求可以整组跳过 argmax 不变的那些步骤** 。贪心只关心第一名是谁,而这些步骤按定义不会改变第一名——跑它们纯属浪费。省下的是一次全词表的 softmax 加一次全词表的比较,对十几万列的词表不是小数目。

这个「跳过」在主循环里具体长什么样,见 1.21。

### 1.17 min_p 的两种算法:一个要概率,一个不要

min_p 的定义里写着「概率」,所以直觉上它必须先有概率分布。V1 就是这么实现的:softmax 算出整行概率、取最大值、乘上 min_p 得阈值、把低于阈值的设 `-∞` 。

**V2 根本不做 softmax。** 它在 logit 空间里直接比:

```text
        p_i ≥ min_p · p_max
⟺  e^{l_i}/Z ≥ min_p · e^{l_max}/Z        ← 配分函数 Z 两边约掉
⟺      e^{l_i} ≥ min_p · e^{l_max}
⟺        l_i ≥ l_max + ln(min_p)
```

于是阈值变成 **最大分数加上一个常数** ,那个常数是 `ln(min_p)` (min_p 小于 1,所以是个负数)。kernel 扫两遍:第一遍求这一行的最大分数,第二遍把低于阈值的设 `-∞` 。

两者的差别不在指令数,在**中间张量** :V1 那条 softmax 要 materialize 一整个 `[请求数, 词表大小]` 的概率张量——batch 128、词表 15 万、float32 就是 76MB,写出来只为了比一下大小,然后扔掉。V2 一个字节都不分配。

这也顺带给 1.13 的结论补了一个更锐的说法:阈值是 `l_max + ln(min_p)` ,而温度会把所有 `l` 同比缩放,**缩放之后这个常数偏移对应的概率比值就变了** ——所以 min_p 必须在温度之后跑,先后颠倒会得到完全不同的候选集。

### 1.18 top_k 与 top_p 合在一次升序排序里

两把刀写在同一个函数里,因为它们要解决的是同一个问题:**在十几万个分数里划一条线。**

划线有两种办法,vLLM 两种都有,**判据只有一个 —— Triton 装没装上** 。装了走 Triton kernel,没装才回落到 PyTorch 版本。和 batch 大小无关。

先讲 PyTorch 那条,因为它直白:**对整行分数做一次升序全排序**,在排好的序列上先做 top_k 再做 top_p,最后把结果散射回原来的词表顺序。

> Triton 那条**根本不排序** ,它去找一个阈值。那是默认路径,也是更有意思的一条,放在 3.2 讲。

排序这条路上有两个技巧值得单独看:

**一是升序而不是降序。** 直觉上 top_p 要的是「累积概率达到 p 的头部」,该用降序。但换成升序之后,要**丢弃**的恰好是累积概率 ≤ `1-p` 的那个前缀——一次前缀和就够了,不需要先算总和再反向减。要找的东西从「保留哪些」翻成了「丢弃哪些」,代价从两遍变成一遍。

**二是强制保底。** 极端情况下(比如某个 token 概率就是 1.0,或者 p 特别小),掩码可能把整行都标记为丢弃,候选集为空,采样无从下手。实现里有一行专门把升序末位(也就是概率最大的那个)的掩码强制置回「保留」。**一行代码换掉一整类边界崩溃。**

丢弃条件用的是「累积 ≤ `1-p`」,取的是**小于等于**而不是小于 —— 所以累积恰好等于 `1-p` 的那个边界 token 会被丢掉。这和 1.14 说的「累积 ≥ p」是同一件事的两面:保留侧取 ≥,丢弃侧就得取 ≤,两边合起来才不重不漏。

### 1.19 只有 top_k 时的快路径,和它要付的同步

回到排序那条路。如果一个 batch 里只设了 top_k、没设 top_p,那么整行全排序就是浪费——只需要第 k 大的那个值当阈值,不需要知道剩下十几万个的确切次序。

于是有一条快路径:取出每行最大的 `max_k` 个(`max_k` 是本批所有请求 k 值里最大的那个),从中按各自的 k 取出阈值,再一次比较完成过滤。省掉了全词表排序。

但它有一个代价,而这个代价决定了它默认用不上:**求 `max_k` 需要把一个 GPU 上的值读到 CPU** 。这是一次 GPU 到 CPU 的同步——CPU 必须停在这里等 GPU 把当前排队的活干完,才能拿到这个数。

源码的文档字符串把这一点写得很明白,说它会引入一次 GPU 到 CPU 的同步,**对异步调度的性能有害** 。这正是 06 章那条主线:一次同步就把好不容易铺起来的流水线断在这里,省下的排序时间远远补不回来。

所以这条快路径**只在 CPU 平台上启用** 。GPU 上的取舍很清楚:**宁可多排一次序,也不打断异步流水线。** 这和 06 章那条「宁可多算一点,也不要在热路径上加分支」是同一种克制,只是这里换成了「宁可多算,也不要同步」。

### 1.20 softmax 不是单独的一步

管线图上 softmax 画成第 ⑤ 步,实现里它并不是一个独立阶段——**裁剪、softmax、随机采样三件事写在同一个函数里连着做完** 。

这么安排是因为它们之间没有任何可以插手的余地:裁剪刚把该丢的设成 `-∞` ,softmax 立刻把它们变成 0,采样紧接着就用这个分布。中间拆开只会多几个中间张量。

两个实现细节:

**softmax 显式指定用 float32 算** ,即使输入的 logits 是 bf16 或 fp16。因为 softmax 要算指数再归一化,低精度下小概率值会直接下溢成 0——本来就小的概率被抹成不可能,分布的尾巴整个丢了。

**归一化自动正确。** 被设成 `-∞` 的那些列,`e^{-∞} = 0` ,既不进分子也不进分母。如果反过来先 softmax 再裁剪,就得在概率空间把它们置零,然后**重新归一化一遍** ——多一步,而且数值上更容易出问题。**在 logit 空间设 `-∞` ,然后做一次 softmax,是这条管线里最省事的顺序。**

### 1.21 贪心与随机:一批里两条路都算

同一个 batch 里,有的请求 `temperature=0` 要贪心,有的要随机。GPU 不喜欢分支,采样器的办法是**两条路都算,最后按请求挑结果** 。

```text
sample()
  │
  ├─ not all_random     ──► 先算一遍 argmax,得到贪心结果
  │
  ├─ all_greedy         ──► 当场返回,温度与裁剪全部跳过
  │
  ├─ temperature → min_p → top_k / top_p → softmax → 随机采样
  │
  └─ where(temp < 1e-5) ──► 逐请求在贪心结果与随机结果之间二选一
```

两个短路值得注意:**全批随机就不算 argmax,全批贪心就当场返回** 。只有真正混合的批次才两条都跑。而在线服务里混合批是常态,所以「两条都算」也是常态。

这看起来浪费,但 argmax 在这里是最便宜的一个 kernel(一遍扫描、无排序、无中间张量),而换来的是**采样路径上一个分支都没有** 。又一次是同一个取舍。

最后的二选一用的是「温度小于 1e-5」而不是「温度等于 0」——浮点数不该用等号比。这个 1e-5 在源码里是个具名常量,管线里凡是判断「这个请求是不是贪心」都用它。

### 1.22 随机采样为什么不用现成的 multinomial

PyTorch 自带按概率分布抽样的 `multinomial` ,vLLM 不用它。理由写在替代函数的文档字符串里,一句话:**它会引入 CPU-GPU 同步。**

这个理由上一次出现是在 1.19 —— 那条快路径明明能省掉全词表排序,却因为要同步而在 GPU 上默认不启用。**两次都是同一个判断:宁可多算,也不打断流水线。** 采样是一次 step 的最后一个动作,紧接着调度器就要排下一步;这里卡一下,06 章费尽周折搭起来的重叠就全白搭。

所以需要一个满足三个条件的替代品:**结果分布必须和按概率抽样完全一致、全程不许同步、最好连排序都不要。** 下一节就是这个替代品。

### 1.23 指数噪声除法:一次采样变成一次 argmax

做法出奇地简单:给每个 token 生成一个独立的指数分布随机数 `q_i ~ Exp(1)` ,然后取 **`p_i / q_i` 最大的那个** 。

这看着像个偏方,但它精确等价于按 `p` 做多项分布采样。推导三行:

令 `q_i ~ Exp(1)` ,则 `−ln q_i ~ Gumbel(0,1)` 。于是

$$
\arg\max_i \frac{p_i}{q_i} = \arg\max_i \left(\ln p_i - \ln q_i\right) = \arg\max_i \left(\ln p_i + g_i\right), \quad g_i \sim \mathrm{Gumbel}(0,1)
$$

右边正是标准的 **Gumbel-max trick** ,它的结果分布恰好就是 `Categorical(p)` 。

代价结构因此变成:**一次填随机数 + 一次除法 + 一次 argmax** 。三个都是逐元素或一遍扫描的操作,GPU 上高度并行,**全程没有排序,也没有任何一步需要 CPU 知道结果** 。这就是要的那三个条件。

实现上还有一处讲究:随机数张量和概率张量的 dtype 不一致时(下一节的 fp64 开关会造成这种情况),不是把概率提升到高精度再除,而是**先对随机数取倒数、再乘以概率** 。这样被提升 dtype 的只有噪声那一个张量,概率张量原样不动,省掉一次全词表的类型转换和它的显存。

### 1.24 带种子的请求:先批量填,再逐行覆盖

`seed` 参数要求同样的输入每次得到同样的输出,这意味着那一行的随机数必须来自该请求专属的生成器,而不是全局的。

难点在于批量填随机数是一次 kernel 调用就能搞定的事,而每请求专属的生成器只能一行一行来。实现的办法是**赌大多数** :

```text
① 先假设「所有请求都没有自己的种子」,一次 kernel 把整个张量填满
② 再逐行覆盖那些确实带种子的请求(Python 循环,一行一次)
```

线上绝大多数请求不带种子,所以第一步一次就填完了,第二步空转;只有少数带种子的请求才付那个逐行的代价。还有一个小优化:**如果这一批所有请求都带种子,第一步整个跳过** ——反正全都要被覆盖,填了是白填。

源码在第二步那个循环上留了一条 TODO,承认它慢。这是个诚实的取舍:**为不常见的情况优化会拖累常见情况,所以先保常见的,并把欠账记在代码里。**

### 1.25 fp64 噪声开关

有一个开关能把噪声张量提升到 float64。它针对的是一个很细的问题:**fp16 和 bf16 在极小值附近的分辨率不够。**

指数分布的随机数里会出现非常接近 0 的值,而 `p_i / q_i` 里除以一个极小的 `q` 会得到极大的商——这正是低概率 token 偶尔被选中的机制,也是采样保真度的来源。低精度浮点在这个区间能表示的不同值太少,极小值被量化成几个离散档,**极低概率 token 的实际采样概率因此偏离理论值** 。

fp64 消除这个偏差,代价是噪声张量的显存和带宽翻倍。默认关着——对绝大多数应用,尾部 token 的采样概率差个几个百分点无所谓;要做严格的分布保真度实验才值得打开。

打开它还有一个连带后果:**FlashInfer 那条融合采样路径会被绕过** ,退回通用实现(1.26)。

### 1.26 六个 forward,绑定发生在构造期

top-k/top-p 采样器一共有六个平台实现。选哪个**在对象构造时就定死** ,把其中一个方法赋给 `self.forward` ,之后每步直接调,不再判断。

| 实现 | 什么时候用 | 特点 |
|---|---|---|
| 通用版 | 默认,也是所有 fallback 的落点 | 裁剪 → softmax → 指数噪声采样 |
| CUDA 版 | N 卡,且不需要返回加工后的 logprob | 调 FlashInfer 的融合 kernel |
| CPU 版 | CPU 平台(RISCV 和 PowerPC 除外) | 无种子时走一个编译好的融合函数 |
| ROCm 版 | A 卡,且开了 aiter | 调 aiter 的采样算子 |
| XPU 版 | Intel GPU,且开了对应开关 | —— |
| 通用版(兜底) | 上面都不成立 | 同第一行 |

CUDA 那条路的排除条件分两个时机,**这个区分容易看漏** :

- **构造期** 排除的是 logprob 模式。FlashInfer 的融合 kernel 不暴露裁剪之后的中间分数,所以只要配置要求返回「加工后的 logprob」,构造时就不绑 CUDA 版。
- **运行期** 还有三个 fallback:top_k 和 top_p 都没设(没活可干)、这一批有请求带种子(FlashInfer 不支持每请求生成器)、开了 fp64 噪声。这三个每步都可能变,所以只能运行时判。

CUDA 版函数体里还有一句断言,检查的正是构造期已经排除掉的那个 logprob 条件。**它是防御性的,正常路径永远走不到** ——构造期没绑上就根本不会进这个函数。

两条讲稿之外的分支值得记一笔:CPU 上 RISCV 和 PowerPC 架构要退回通用版,注释附了 PR 链接,说 PowerPC 上 argmax 配 `torch.compile` 会算错;ROCm 那条路是惰性 import,**import 失败时会把 `self.forward` 当场改绑回通用版** ,自愈之后打一条警告——绑定虽然发生在构造期,但不是绝对不可改。

至于同一批里每个请求的参数怎么各取各的:所有参数打包成按请求索引的张量,kernel 里按请求在常驻状态表中的下标间接读取。**这套两级编号和它的映射表是 06 章 3.6 的内容,这里只是它的又一个使用者。**

### 1.27 logprob 取的是哪一步的分数

最后回到管线图开头那个括号。用户请求 logprob 时,返回的是**哪一步的**分数,是个真问题——原始 logits、加了 penalty 之后、还是裁剪之后,数值完全不同。

采样器的默认答案是:**原始的那份** 。而且实现方式是在**任何加工开始之前**就把 logits 拍一份快照,后面所有步骤都在别的张量上改,不影响它。

源码注释特意点明这与 V0 不同——V0 返回的是用于采样的那份(加工后的)。这个改动的道理:用户要 logprob 通常是想知道**模型认为什么最可能** ,而不是「我把参数调成这样之后,采样器眼里什么最可能」。penalty 和温度是用户自己设的,把它们的效果混进 logprob 里,这个数就没法用来判断模型本身了。

配置项也允许要加工后的版本,共四档(原始 logprob、原始 logits、加工后 logprob、加工后 logits)。**选了加工后的两档会有连带后果** :FlashInfer 那条融合路径拿不到中间分数,于是构造期就被排除(1.26)。

所以 1.2 那张管线图上的括号要这么读:**快照发生在最前面,末尾那一步只是从快照里 gather 出用户要的那几个。** 它不是管线的第六步,它是第零步。

### 1.28 logprob 返回的到底是什么

上一节说了取哪一步的分数,这一节说取出来之后长什么样。用户要 `logprobs=N` ,拿到的不止 N 个。

收尾那一步做三件事:取出 top-N 的 token 与它们的 logprob;单独取出**被采样中的那个 token** 的 logprob;再算一个**排名**。三样拼成一个结果对象。

| 返回的东西 | 是什么 | 怎么来的 |
|---|---|---|
| top-N 的 token 与 logprob | 这一步模型最看好的 N 个 | 对快照做一次 topk |
| 被采样 token 的 logprob | 实际选中的那个的分数 | 按 token id 从快照里 gather |
| 被采样 token 的排名 | 它在整个词表里排第几 | 数「有多少个 token 的 logprob 比它大」 |

被采样的那个被 `cat` 到 top-N **前面** ,所以这一步产出的是 **N+1 列** 。但用户最终看到的可能是 N 也可能是 N+1 —— 如果被采样的那个本来就在 top-N 里,输出处理阶段会把重复的合并掉。采样器的文档字符串专门写明了这一点,因为它是个很容易被当成 bug 的行为。

排名那一步值得单独看:它不是排序出来的,而是**数出来的** —— 拿被采样 token 的 logprob 去和整行比大小,数有多少个比它大。一次比较加一次求和,比排序便宜得多,而且照例不需要同步。

还有一个特殊值:**`logprobs` 给 -1 表示「把整个词表的 logprob 原样返回」** ,这时候 topk 整个跳过,快照直接塞进结果对象。做分布分析时用得上,代价是每步搬回十几万个浮点数。

最后一处细节和采样本身无关,但很典型:算排名之前有两行专门把 batch 维**标成完全符号化** ,注释写明了理由 —— 防止编译器在 batch 从 1 变成 2 的时候认为形状变了、把那个函数**重新特化编译一遍** 。在线服务的 batch 每步都在变,不做这一下会反复触发重编译。**这是一条很具体的反重编译措施,不是通用技巧。**

### 1.29 采样参数一共有哪些

前面十几节是按管线顺序讲的,这里按字段列一遍。所有参数装在一个结构体里,跟着请求从 API 进程传到引擎进程。

| 分组 | 参数 | 默认 | 作用 |
|---|---|---|---|
| 基础 | `n` | 1 | 同一个 prompt 返回几条结果 |
| | `temperature` | 1.0 | 分布尖锐度;**0.0 才是贪心** |
| | `seed` | 无 | 该请求专属随机种子 |
| 裁剪 | `top_p` | **1.0** | 1.0 表示不过滤 |
| | `top_k` | **0** | 0 表示不过滤 |
| | `min_p` | **0.0** | 0.0 表示不过滤 |
| 惩罚 | `repetition_penalty` | **1.0** | 乘法式;1.0 表示不惩罚 |
| | `frequency_penalty` | 0.0 | 加法式,按次数 |
| | `presence_penalty` | 0.0 | 加法式,按有无 |
| 截断 | `max_tokens` | 16 | 最多输出多少 token |
| | `min_tokens` | 0 | 至少输出多少 |
| | `stop` / `stop_token_ids` | 无 | 遇到就停 |
| | `ignore_eos` | False | 忽略结束符继续生成 |
| 输出 | `logprobs` | 无 | 返回 top-N;-1 表示全词表 |
| | `prompt_logprobs` | 无 | 连 prompt 的也返回 |
| 控制 | `logit_bias` | 无 | 逐 token 偏移 |
| | `allowed_token_ids` | 无 | 白名单 |
| | `bad_words` | 无 | 禁词 |
| | `structured_outputs` | 无 | 结构化输出 |
| | `extra_args` | 无 | 给自定义 processor 的参数 |

**三个最容易记反的默认值挤在一起** :`top_p=1.0` 、`top_k=0` 、`min_p=0.0` 三个值长得毫无共同点,但表达的是同一件事 —— **不过滤** 。它们都不是 `None` ,所以代码里判断「这个请求要不要裁剪」不能用判空,得和各自的哨兵值比。

这个结构体还有一个容易被忽略的实现选择:**它不是普通的 dataclass,是一个 msgspec 结构体** ,并且开了「省略默认值」。原因是它每条请求都要跨进程序列化一次 —— 省略默认值意味着绝大多数请求只序列化用户真正设过的那两三个字段,其余一个字节都不传。

### 1.30 两个不在字段里的东西

看一个参数表,同样要看**什么不在上面** 。

**没有 `best_of`。** 这是 OpenAI API 里「生成 k 条取最好的一条」那个参数。它不在字段里,但结构体的文档字符串又写着「我们支持 beam search,这是 OpenAI 所没有的」—— 两句话看起来矛盾,实则是**功能还在、入口挪了** :beam search 走的是独立的离线入口,不再是采样参数的一个字段。1.5 提到的那个白名单上限,就是在那条路径上又抄了一份。

**没有逐请求的 `logits_processors`。** 用户不能在请求里塞一个自定义函数。这是个刻意的设计,下一节讲它为什么必须如此。

### 1.31 processor 是批级对象,不是逐请求回调

「自定义 logits 处理」最直觉的形态是:用户给一个函数,签名是「输入已生成的 token 序列和当前 logits,输出改过的 logits」,引擎对每条请求调一次。

vLLM 不这么做,**它要求处理器是一个引擎级的批处理对象** ,抽象基类规定**四个必须实现的方法,外加一个可选的参数校验钩子**:

| 方法 | 干什么 | 为什么需要它 |
|---|---|---|
| 构造 | 拿到引擎配置、设备、是否锁页内存 | 状态张量要建在正确的设备上 |
| 应用 | 拿到 **整批** logits,改完还回去 | 一次 GPU 操作覆盖全批 |
| 是否 argmax 不变 | 回答 1.16 那个分类问题 | 决定它进哪一组、贪心时要不要跑 |
| 状态更新 | 接收批组成变化的通知 | 见下一节 |
| 参数校验(可选) | 看一眼请求参数合不合法 | 非法参数在入口就拒掉,不等到采样时才炸 |

**关键是「应用」拿到的是整批。** 逐请求回调意味着 batch 里有多少条请求就要发多少次 kernel —— 而 1.9 已经算过这笔账:在热路径上按请求循环,正是 V1 那条 penalty 路径慢的原因。批级对象让一个 Triton kernel 覆盖全批,每条请求靠索引各取各的参数。

代价是写起来麻烦:处理器得自己维护「每条请求的参数」那张表,而 batch 的组成每一步都在变。

### 1.32 批的组成变了怎么办

常驻的 batch 每步都在增删:新请求进来占一个槽位,完成的请求腾出槽位,还有请求被搬到别的槽位上去。处理器手里那张 per-request 参数表必须跟着动。

做法不是每步重建,而是**发事件** :每步给处理器送一个更新包,里面装三类事件。

| 事件 | 含义 | 处理器要做什么 |
|---|---|---|
| 移除 | 这些槽位上的请求结束了 | 清掉对应行,更新计数 |
| 新增 | 这些槽位来了新请求 | 写入新参数 |
| 搬移 | 某个槽位的内容挪到另一个槽位 | 对应行跟着搬,支持单向与对调两种 |

**顺序是有讲究的** :先处理移除,再处理新增,最后处理搬移 —— 新增和搬移都可能落在刚被移除的槽位上,顺序反了会覆盖掉不该覆盖的东西。

这套事件机制也正好回答了 1.4 留下的那个问题:白名单和禁词为什么没做成处理器。它们的 per-request 状态**确实存在** ,只是不由处理器自己维护,而是挂在输入批次对象上 —— 于是增、删、换位三处都得由输入批次同步。**两条路都要维护状态,区别只是这份状态归谁管。**

### 1.33 装配:三条分支

引擎启动时组装处理器链,一共三条路。

| 情况 | 结果 |
|---|---|
| 池化模型 | **空链** 。这类模型不产 token,处理器无从谈起;此时若还传了自定义处理器,直接抛错 |
| 开了推测解码 | **只保留最少 token 数这一个** ,其余全部丢掉;传了自定义处理器直接抛错 |
| 其余 | 内置三个加上自定义的,按注册顺序应用 |

内置的就是 1.16 提过的那三个:最少 token 数、logit 偏移、min_p。**注册顺序即应用顺序。**

第二条分支是下一节的主题 —— 它比看上去要微妙。

### 1.34 推测解码下,哪些参数还活着

开了推测解码,引擎会打一条警告:**min_p 和 logit_bias 不生效** 。自定义处理器则直接报错。

先说为什么。这两个处理器的 per-request 状态都按「一步出一个 token」建模,而推测解码一步要验证 k 个草稿 token —— 状态和形状对不上。

**但这个理由只说对了一半。** 最少 token 数那个处理器同样是 per-request 状态,同样面对「一步 k 个」,它却留下来了 —— 因为它专门写了一个推测解码专用的应用方法,把「一步 k 个」这件事处理掉了。验证路径里还会再筛一遍,明确只认这一个类。

所以真相是:**状态确实对不上,但这是可以解决的;最少 token 数解决了,另外两个只是没人实现。** 这也解释了为什么是警告而不是报错 —— 它不是原理上的不可能,是一个功能缺口。

更要紧的是另一半:**讲「哪些失效」容易让人以为整条链都废了,其实没有。** 下面这些在推测解码下照常生效,各自有专门的草稿版本:

| 参数 | 在推测解码下 | 怎么做到的 |
|---|---|---|
| 白名单 | **照常** | 把每请求的掩码按草稿数展开成每 token 一份 |
| 禁词 | **照常** | 专门的带草稿版本,历史里要算上本步的草稿 |
| 三种 penalty | **照常** | 同样按草稿数展开索引 |
| 温度 | **照常** | 每请求温度展开到每个草稿位置,原地除 |
| `top_k` / `top_p` | **照常** | 展开后调用和主路径同一个裁剪函数 |
| `min_p` / `logit_bias` | 失效 | 没有草稿版本 |
| 自定义处理器 | 报错 | 同上,而且引擎不敢替用户猜 |

温度展开时有个熟悉的动作:**贪心的 0 被换成 1** ,和 1.11 是同一个避免除零的手法;而整批都贪心时这一段直接早退,原样返回。

> 这张表里的「照常」是照着代码核的 —— 采样器的类注释还写着推测解码不支持 `top_k` / `top_p` ,但同一个文件下方就在调裁剪函数。**注释比代码旧了。**

### 1.35 自定义处理器的两种注册,和一个慢的兼容层

自定义处理器来自**引擎级配置** ,不是请求字段(1.30)。两种注册方式:

| 方式 | 怎么用 | 什么时候加载 |
|---|---|---|
| 插件 | 在包的元数据里声明一个约定好的入口点组 | 启动时自动发现 |
| 全限定类名 | 把 `"包.模块.类名"` 字符串传给引擎 | 启动时反射加载 |

逐请求的参数则走那个 `extra_args` 字段,由处理器自己的校验方法检查。**分工很清楚:处理器的「代码」是引擎级的,处理器的「参数」才是请求级的。** 这条边界让用户无法往引擎里注入任意代码,同时又保留了逐请求调参的能力。

那么手上已经有老式逐请求函数的人怎么办?有一个适配器基类:它在内部维护一张「请求槽位到该请求的处理函数」的表,批级的应用方法里按槽位**逐行调用** 。

这条路能用,但要知道它的代价:**每条请求一次 Python 调用** ,正是 1.31 想避免的那件事。适配器存在的意义是兼容,不是推荐。一句话概括这一节:**能向量化就写批级处理器,实在写不了才用适配器兜底。**

### 1.36 为什么需要拒绝采样

到这里采样管线讲完了。**从这一节起是 1.1 那张表的最后一行** ——前面所有内容都在回答「从一行分数里挑一个」,接下来要问的是「能不能一次挑好几个」。

痛点是自回归本身:一次前向只出一个 token,而 decode 的瓶颈在访存不在算力(06 章算过),GPU 的算力大量闲置。推测解码的思路是拿闲置算力换延迟 —— 让一个小模型先猜 k 个 token,大模型一次前向把这 k 个位置**并行验证** 。猜对了就白赚几个 token。

**但前面二十几节建立的东西一样不能丢**:温度、裁剪、penalty 在这条路上照常生效(1.34),Gumbel-max 那个技巧会被原样复用(1.39),而「不许同步」的纪律只会更严(3.10)。**拒绝采样不是另起炉灶,是把同一套管线搬到「一次验 k 个」的场景下。**

问题出在「验证」两个字上。最朴素的验证是**比 token 字面** :草稿猜的和目标模型自己会选的一样就接受。贪心时这没问题,因为目标模型的选择是确定的。

**随机采样时这么做是错的。** 举个例子,词表只有猫狗鸟:

```text
草稿模型 q:  猫 0.9   狗 0.05  鸟 0.05    ← 草稿偏爱猫
目标模型 p:  猫 0.5   狗 0.3   鸟 0.2     ← 目标真正想要的分布
```

草稿大概率猜「猫」,目标采样也可能抽到「猫」,字面相同。但如果「字面相同就 100% 接受」,最终输出里「猫」的频率会趋近草稿的 0.9,而不是目标的 0.5 —— **分布被草稿带偏了。** 用户以为自己在从目标模型采样,实际拿到的是一个被污染的分布。

所以随机模式必须**比概率** :对「猫」,接受概率取 `min(1, p/q) = min(1, 0.5/0.9) ≈ 0.56` 。即使字面相同也只有 56% 的概率接受。验算一下就知道为什么是这个数:草稿猜中猫的频率 0.9,乘以接受率 0.556,**正好等于 0.5,也就是 p(猫)** 。

一句话:**贪心比 token,随机比概率;比概率是为了让最终分布和「直接用目标模型采样」完全一致。** 这个保证是推测解码敢用的前提 —— 它不是近似加速,是**无损** 加速。

### 1.37 接受准则

把上一节的直觉写成规则。设草稿分布 `q` 、目标分布 `p` 、草稿提议的 token 是 `x̃` 。

**随机模式**:抽一个 `u ~ Uniform(0,1)` ,当

$$
u \le \frac{p(\tilde{x})}{q(\tilde{x})}
$$

时接受,否则拒绝。等价说法是接受概率为 `min(1, p/q)` 。

- `p > q` :目标比草稿更想选这个 token,比值大于 1,**必接受** 。
- `p < q` :草稿过度自信,**打折接受** ,折扣正好是两者的比值。

**贪心模式**:草稿等于目标的 argmax 就接受,否则拒绝并改用 argmax。

贪心那条的实现有个值得一提的写法:**它没有分支** 。kernel 一律把目标的 argmax 写进输出,「接受」只不过是「写进去的值恰好和草稿相同」。判断接受与否只用来决定要不要继续往下走,不用来决定写什么。**又一次是那条原则:宁可无条件算,也不要在 kernel 里分叉。**

还有一处防御:草稿概率为 0 时直接拒绝。注释说明了理由 —— 那是个不该出现的值,但真出现了,除法会得到 NaN。

### 1.38 拒绝之后,不能直接从目标分布重采

拒绝了要补一个 token,最自然的想法是从 `p` 里重新采一个。**这会算重。**

因为被接受的那条路径**已经贡献了一部分概率质量** 。沿用猫狗鸟:草稿猜猫的频率 0.9,接受率 0.556,猫已经通过「接受」这条路拿到了 0.5 的输出频率 —— 恰好就是 p(猫) 的全部。如果拒绝之后再从完整的 `p` 里采,猫还有 0.5 的机会被抽中,最终频率就超了。

正确做法是从**修正分布**采:

$$
p_{\text{rec}} \propto \max(0,\ p - q)
$$

只补「目标比草稿多出来的那部分」。还是猫狗鸟:

```text
              猫      狗      鸟
p:           0.5     0.3     0.2
q:           0.9     0.05    0.05
max(0,p−q):   0      0.25    0.15     ← 替补只可能是狗或鸟,猫被排除
```

猫的修正概率是 0 —— 它已经在接受路径上被喂饱了。真正欠缺的是狗(目标要 0.3,草稿只给 0.05)和鸟。

正确性一行就能看出来:

$$
\min(p,\ q) + \max(0,\ p - q) = p
$$

左边第一项是接受路径贡献的,第二项是补偿路径贡献的,**两条路加起来精确还原 `p`** 。这就是「无损」二字的全部内容。

### 1.39 修正分布不用归一化

`max(0, p−q)` 算出来是一组非负数,但它们加起来不等于 1 —— 按定义应该除以总和才是个分布。

**实现里没有这一步。** 源码注释直接说明了为什么:不需要归一化,因为后面取的是 argmax。

这句话要连上 1.23 才能读懂:补偿重采样用的也是**指数噪声除法** ,采的是 `argmax(p_rec / q_noise)` 。而给 `p_rec` 整体乘一个常数,不改变 argmax 的结果 —— 归一化常数在比较中被约掉了。

**这已经是本章第三次用同一个论证了** :

| 出现在 | 被约掉的是什么 |
|---|---|
| 1.17 min_p 在 logit 空间比较 | softmax 的配分函数 |
| 1.23 指数噪声除法等价于 Gumbel-max | 概率的归一化 |
| 本节 修正分布不归一化 | 修正分布的总和 |

三处形状完全一样:**要比大小的时候,公共的正因子可以不算。** 而每一次省掉的都是一遍全词表的读写。在一个 memory-bound 的管线里,这类省略比任何指令级优化都值钱。

补偿路径还顺带复用了 1.25 那个 fp64 噪声开关 —— 主路径打开时它也跟着打开,保真度口径一致。

### 1.40 贪心与随机,谁更严

直觉上贪心更严:它只认一个 token。但**两者的严格度不是简单的强弱关系,而是在不同 token 上各有更严的时候。**

沿用猫狗鸟(`q` :猫 0.9 / 狗 0.05 / 鸟 0.05,`p` :猫 0.5 / 狗 0.3 / 鸟 0.2,目标的 argmax 是猫):

| 草稿猜中 | 贪心 | 随机 | 谁更严 |
|---|---|---|---|
| 猫(= argmax) | 必接受 | 接受率 `min(1, 0.5/0.9) ≈ 0.56` | **随机更严** |
| 狗(≠ argmax) | 必拒绝 | `min(1, 0.3/0.05) = 1` ,必接受 | **贪心更严** |
| 鸟(≠ argmax) | 必拒绝 | `min(1, 0.2/0.05) = 1` ,必接受 | **贪心更严** |

规律很清楚:**贪心只放过 argmax 一个 token,但对它无条件放过;随机放过所有 `p ≥ q` 的 token,但对 `p < q` 的要打折。**

草稿越自信(`q` 高)而目标越不认同(`p` 低)的那个 token,随机模式罚得越重 —— 这正是它能保住分布等价性的原因,也正是上一节那个验算成立的原因。

实用后果:**草稿模型和目标模型的分歧模式,决定了哪种模式的接受率更高**,不能一概而论说贪心的加速比更好。

### 1.41 两个 kernel 都不提前退出

一条草稿链上某个位置被拒绝之后,它后面的所有草稿 token 都作废 —— 因为它们是基于那个被否掉的 token 往下猜的。

朴素写法是 `break` 。**实现里没有 break** :循环照常跑完所有草稿位置,只是用一个标志位挡住后续的写入。

原因是 GPU 的执行模型。同一个 warp 里的线程共用一条指令流,不同请求的草稿链在不同位置被拒绝 —— 真要提前退出,就成了 warp 内的分支发散,反而更慢。让循环空转到底,每个位置多判一次标志位,比发散便宜。

**这条和 06 章那句「宁可多算一点,也不要在热路径上加分支」是同一条原则**,只是那边省的是 CPU 下发,这边省的是 warp 发散。本章 1.21 的「两条路都算」、1.37 的「无分支写 argmax」也都是它。

顺带记一个上限:**单条请求单步最多 128 个草稿 token** ,这是个硬编码的常量,注释说这个值「足够覆盖典型用法」。

### 1.42 一次验证产出三种 token

验证走完,这一步的输出可能包含三类东西,源码的类注释给了一套明确的叫法:

| 叫法 | 从哪来 | 什么时候有 |
|---|---|---|
| **接受的** | 草稿提议的,按原始的草稿与目标概率判定通过 | 每个通过判定的位置 |
| **替补的** | 从修正分布采出来的 | 只在发生拒绝时,且只有一个 |
| **附赠的** | 只从目标分布采,不经过判定 | **只在整条链全部被接受时** |

三者相加就是这一步的产出:**输出 = 接受的 + 替补的 + 附赠的。**

附赠的那个是加速比的上限来源:草稿猜了 k 个全中,这一步就能吐出 k+1 个 token —— 多出来的那个是目标模型在验证时顺手算出的下一个位置。**它不要额外的前向,是白捡的。**

它还有一个容易忽略的性质:**它是在拒绝采样器外面采好、再传进来的** 。这么安排是为了让它能走完整的采样管线(温度、裁剪、种子全都照常),而不必受验证路径的约束。

## Part 2|图解

### 2.1 一个草稿 token 的验证流程

Part 1 把判定规则讲清了,但两种模式的分支结构还是文字。把一个位置上发生的事画出来:

```text
                草稿提议一个 token,来自草稿分布 q
                              │
                              ▼
                     ┌─────────────────┐
                     │    greedy ?     │
                     └─────────────────┘
                       │           │
                      yes          no
                       │           │
                       ▼           ▼
        ┌─────────────────┐   ┌─────────────────┐
        │ draft == argmax │   │   u <= p / q    │
        └─────────────────┘   └─────────────────┘
              │      │             │       │
             yes    no            yes     no
              │      │             │       │
              ▼      ▼             ▼       ▼
           accept  reject       accept  reject
```

右边那条路上的 `u` 是每个位置现抽的一个 `U(0,1)` 随机数,`p` 与 `q` 分别是目标与草稿在**草稿提议的那个 token** 上的概率。

两条路最后汇到同一件事:**这个位置写下一个 token,并且给出「接受了没有」这个布尔量** 。后者决定链条要不要继续。

两个 `reject` 的去向不同,这是图上看不出来的:贪心那边一律写目标的 argmax,随机那边要从修正分布 `max(0, p−q)` 采一个替补。

还有一处图与实现的差别:**贪心那一支在代码里没有分支**(1.37)。不管接不接受都写 argmax,判定只用来产出那个布尔量。画成菱形是为了讲清语义。

### 2.2 一条链的验证:拒绝会截断后面全部

单个位置讲完,看一条 k=4 的链。**关键在于拒绝的影响是往后传染的。**

```text
草稿猜了 4 个 [A, B, C, D],目标一次前向算出 5 个位置的分布

位置      0       1       2       3       4
草稿      A       B       C       D       -
判定      ok      ok      REJECT  drop    drop
输出      A       B       R       -       -
                          ^ 从 max(0, p2-q2) 采来的替补

本步产出 3 个:接受 2 + 替补 1,没有附赠
--------------------------------------------------------
全部接受的情况

位置      0       1       2       3       4
草稿      A       B       C       D       -
判定      ok      ok      ok      ok      bonus
输出      A       B       C       D       E

本步产出 5 个:接受 4 + 附赠 1,加速比最高
```

三件事值得记住:

- **一旦某个位置被拒绝,它之后的草稿全部丢弃** ,用替补 token 填上该位置就停止。后面那些草稿是基于被否掉的 token 往下猜的,已经没有意义。
- **附赠 token 只在全接受时出现** 。链越长,全中的概率越低,所以草稿数不是越大越好。
- 本步产出的 token 数因此落在 **1 到 k+1** 之间:最坏是第一个就被拒(只剩一个替补),最好是全中加附赠。

上图的「丢弃」在实现里不是提前退出,而是空转不写(1.41);而「目标一次前向算出 5 个位置的分布」正是推测解码省时间的地方 —— **验证 k 个 token 和生成 1 个 token,前向的次数是一样的。**

### 2.3 验算:三条路加起来正好是目标分布

1.38 给了恒等式 `min(p,q) + max(0, p−q) = p` 。恒等式是对的,但它把两条路压成了一行符号。把猫狗鸟的数字完整走一遍,才看得出这个机制是怎么「刚好」还原分布的。

设草稿 `q` 为猫 0.9 / 狗 0.05 / 鸟 0.05,目标 `p` 为猫 0.5 / 狗 0.3 / 鸟 0.2。修正分布 `max(0, p−q)` 是猫 0 / 狗 0.25 / 鸟 0.15,归一化的分母是 0.40。

**猫只有一条路** ——被草稿猜中并且接受:

```text
P(输出猫) = q(猫) × 接受率
          = 0.9 × min(1, 0.5/0.9)
          = 0.9 × 0.556
          = 0.50            正好是 p(猫)
```

**狗有两条路** ——自己被猜中并接受,或者草稿猜了猫但被拒、替补抽到狗:

```text
途径 1  草稿猜中狗并接受
        = q(狗) × min(1, 0.3/0.05) = 0.05 × 1.0 = 0.05

途径 2  草稿猜猫被拒,替补补到狗
        = q(猫) × 拒绝率 × P(替补=狗)
        = 0.9 × 0.444 × (0.25 / 0.40)
        = 0.9 × 0.444 × 0.625
        = 0.25

合计    = 0.05 + 0.25 = 0.30            正好是 p(狗)
```

鸟同理约 0.20。

这个验算里最值得盯住的是**途径 2 的第三个因子** 。如果拒绝之后从完整的 `p` 重采,那个因子会是 `p(狗) = 0.3` 而不是 `0.625` ,合计就变成 `0.05 + 0.9 × 0.444 × 0.3 = 0.17` —— **不但不等于 0.3,还偏得离谱** 。1.38 说的「算重」在这里有了具体的数字:**修正分布不是个可有可无的讲究,它是让等式成立的那一项。**

### 2.4 整体数据流

把 Part 1 散落在十几节里的东西接成一张图。左右两条 kernel 路径互斥,由每条请求自己的温度决定走哪条。

```text
draft_token_ids (+ draft_probs q)          ◄── 草稿模型给出,q 可能没有
        │
logits  ├──► bonus_logits  ──► sampler ──► bonus_token_ids
        │                                  走完整采样管线
        └──► target_logits
                 │
                 ├──► penalty / allowed_token_ids / bad_words
                 ├──► temperature / top_k / top_p
                 └──► softmax ──► target_probs p
                          │
        ┌─────────────────┴─────────────────┐
        ▼                                   ▼
   greedy kernel                      random kernel
   argmax compare                     u <= p / q
        │                                   │
        │                                   │   拒绝时取预先采好的替补
        └────────► output_token_ids ◄───────┘
                   [batch, max_spec_len+1]
                          │
                          ▼
                   parse_output            过滤占位值,全程唯一一次 D2H
```

三处分岔值得留意:

- **bonus 那一支走的是普通采样器** ,所以它享受完整的温度与裁剪(1.42)。
- **目标那一支的加工顺序和主管线一致** ,只是每个参数都按草稿数展开过(1.34)。
- **两个 kernel 是并列的两次发射,不是一个 kernel 里的分支** ,理由见 3.5。

### 3.1 两套采样器的分界不是硬件,是哪一代运行器

1.3 说过有两套采样器,这里补上它们真正的分界线。**不是「N 卡走这套、CPU 走那套」** ,而是:

| | 第一代 | 第二代 |
|---|---|---|
| 形态 | **无状态** ,每步接收一份现攒的元数据 | **有状态** ,采样参数按请求下标常驻 GPU |
| 每步开销 | 重建元数据 | 只发 kernel,不重建 |
| 谁在用 | 第一代运行器,以及 CPU / XPU 的运行器(继承复用同一套) | 第二代运行器及其子类 |

所以在 CPU 上跑也是「第一代采样器」——它跟的是运行器的代际,不是设备。两代共用同一批底层算子(裁剪、FlashInfer 调用),差的是**参数怎么送到 kernel 手里** 。

第二代那套持有七个状态对象(采样参数、penalty、logit 偏移、禁词、logprob token、思考预算,还有一个默认关着的轨迹重放)。它们的共同点是:请求进来时写一次,之后每步只被 kernel 按下标读。

第一代还有两处 dtype 转换值得一提:采样结果先统一成 64 位(因为 FlashInfer 返回 32 位而 PyTorch 的 argmax 返回 64 位,后面要拿它当索引),**最后又压回 32 位** ——注释说明理由是缩小要搬回 CPU 的张量体积。**连返回值的位宽都是按「要过多少字节 PCIe」定的**,这是 1.22 那条暗线最细的一处体现。

还有一个只在推测解码时才有意义的参数:为 bonus 位置采样时,penalty 与禁词的统计要**把本步的草稿 token 也算进已生成序列** ,否则会漏数。而且只在真的用到 penalty 或禁词时才去拼那个列表,避免白白构造。

### 3.2 免排序的裁剪:不排全表,只找一条线

这是本章最值得单独读的一段实现。1.18 讲的全排序是**没装 Triton 时的回落路径** ;默认路径根本不排序。

道理其实很朴素:**要的只是「第 k 大的那个值」,这是一个选择问题,不需要全序信息。** 全词表排序是 `O(V log V)` 还要写回一个 V 大小的索引张量,而词表通常十几万到二十几万列。

kernel 的做法是找一个**阈值(pivot)**,低于它的一律掩掉。分四遍:

| 遍 | 做什么 | 关键 |
|---|---|---|
| 第 0 遍 | 估一个 pivot 的起点 | **只读第一个数据块** ,算均值与标准差 |
| 第 1 遍 | 全量扫一遍,收集候选 | 把高于起点的值紧凑地存进一个小缓冲 |
| 第 2 遍 | 在候选缓冲上搜索精确 pivot | 三分搜索,见 3.3 |
| 第 3 遍 | 需要时再做 top_p | **复用同一份候选缓冲** ,不重扫全词表 |

第 0 遍怎么从均值和标准差猜出 pivot:把 `k / 词表大小` 当成一个分位数,去查一张硬编码的**正态分位数表**(200 项),得到一个 σ 倍数,pivot 就是「均值加上这么多个标准差」。logits 的分布当然不是正态,只是「近似」——所以这一步之后还要有第 2 遍去精确化。

有两个细节是这一段的灵魂:

**一是故意把 pivot 压低 15%。** 估出来的 pivot 若偏高,真正的 top-k 成员就会被漏在候选缓冲外面,后面再也找不回来;偏低只是多收一些候选、后面多筛一遍。**宁可多收,不能少收** ——这是所有「先粗筛再精筛」结构的共同纪律。

**二是统计时显式排除负无穷。** 注释点名了原因:**结构化输出的语法位掩码会往 logits 里塞进大量负无穷**(1.5)。不排除的话,均值和方差会直接算成 NaN,pivot 就废了。

> 这是白名单那条链路在 kernel 深处留下的痕迹:一个上层功能往张量里写了特殊值,三层之下的一个统计量就得为它加一道防护。

### 3.3 三分搜索为什么比二分划算

第 2 遍要在候选缓冲上找精确 pivot。区间搜索的常规做法是二分,这里用的是**三分** ——每轮同时试 1/3 和 2/3 两个候选,一次把区间缩到 1/3。

关键在于「每轮的成本」。这一步是**内存带宽受限**的:主要开销是把候选缓冲扫一遍,而不是做比较。源码注释写明了这个设计——把两个 pivot 的统计量**融进同一遍扫描** ,避免第二次扫描数据。

于是账很好算:

| | 二分 | 三分 |
|---|---|---|
| 每轮扫描次数 | 1 | **1**(两个 pivot 共用一次加载) |
| 每轮区间缩到 | 1/2 | **1/3** |
| 总轮数 | log₂ | **log₃** |

**每轮成本不变,轮数变少,净收益。** 这个取舍只在「扫描远贵于比较」时成立 —— 换个内存不受限的场景,多算一个 pivot 就是纯浪费。

终止条件也值得看一眼,它比「找到第 k 大」要讲究:**大于 pivot 的个数 ≥ k,并且减掉「与最小值相等的那一批」之后 < k** 。第二个条件是为了处理**重复值** ——第 k 大的值可能有好几个相同的,简单按阈值掩码会保留超过 k 个 token。所以搜索过程一路追踪「严格大于 pivot 的最小值及其出现次数」,最后据此精确保留其中几个。

### 3.4 小 batch 的那条岔路

1.18 说过裁剪的分发只看 Triton 装没装,和 batch 大小无关。那是**入口那一层**的实话。但进了 Triton 之后,**batch 大小确实会再分一次岔**。

问题出在单体 kernel 的并行方式:**一行一个程序实例** 。batch 一小,绝大多数流处理器就闲着,而每次全词表扫描都是延迟受限的。设计注释给了一个具体量级:在某代硬件上一次扫描约 25 微秒,**纯 top_p 的场景下,pivot 搜索可能撞上迭代上限、反而慢过 PyTorch 的排序** 。

解法不是退回 PyTorch,而是换一条**分裂行的流水线**:把同一行拆给多个程序实例,pivot 搜索改成固定轮数的并行局部归约。

| | 单体 kernel | 分裂流水线 |
|---|---|---|
| 并行粒度 | 一行一个程序 | 一行拆给多个程序 |
| 适用 | 有 top_k 的行(截断路径本来就快) | **纯 top_p 且 batch ≤ 64 且在 N 卡上** |
| 搜索 | 边扫边缩,轮数不定 | 固定轮数的并行归约 |
| 约束 | —— | 无主机同步,CUDA Graph 安全 |

最后一行是这条流水线能存在的前提:它把搜索状态**完全不落盘** ,每轮的合并是一个纯函数,所有程序各自从已存的局部量重算一遍。这么做既确定(同样输入同样结果),又比再扫一遍词表便宜,还省掉一次 kernel 发射 —— **而「无主机同步」意味着它能被录进 CUDA Graph** ,不会把 06 章费劲建起来的图给废掉。

### 3.5 贪心与随机是两次发射,不是一个 kernel 里的分支

验证阶段的两条路径写成了**两个独立 kernel** ,各自在开头按「这条请求是不是贪心」早退。混合批次会把两个 kernel 都发一遍,每个 kernel 里不属于自己的请求直接退出。

看起来是在做无用功,但比写成一个 kernel 里的分支更好,理由是**两条路的工作量差着量级**:随机那条要读整张 `[token 数, 词表大小]` 的概率张量,贪心那条只读一个 argmax 的结果。塞进同一个 kernel,整个线程块会被慢的那条拖住。

**分开发射,等于让两种工作量各自独立地占满机器。** 这和 1.41 那条「不要在 kernel 里分叉」是同一条原则的另一种用法:能在**发射层**分开的,就不要留到 kernel 里去分。

纯贪心的批次还能再省一大截:提前返回之后,目标概率的 softmax(整张 `[token 数, 词表大小]`)和整个替补词采样**全部跳过** ,连均匀随机数都不生成。

> 这已经是本章第四处「早退省掉一整遍全词表」了:1.3 的整批总闸、1.12 的温度、1.16 的贪心跳过一整组、这里。**判断放在加载之前,是这套代码最常用的一个动作。**

### 3.6 替补词给每个位置都提前采好

一条草稿链上最多只有一个位置会用到替补(第一个被拒的那个),后面的位置全被丢弃。但实现里**给每个位置都预先采好了一个替补** 。

这是标准的「用无用功换并行度」:kernel 里只做一次加载、读走那个预先算好的值,不必临场再去修正分布里采一个。要是留到 kernel 里临场采,判定 kernel 就得在「接受」和「拒绝」两条路上做完全不同的工作量 —— 又回到 3.5 那个问题。

**把不确定的工作提前做成确定的工作,是这一片代码反复出现的手法。** 1.21 的「两条路都算」、1.41 的「空转不退出」、这里的「都先采好」,三处形状一样。

### 3.7 噪声按请求发,不按 token 发

采替补要一组指数噪声。直觉上噪声张量该是 `[token 数, 词表大小]` ——每个草稿位置各采各的。实际是 **`[请求数, 词表大小]`** ,注释写明了:**每个请求只创建一个分布。**

推测解码下 `token 数 ≈ 请求数 × k` ,所以这一下把噪声的显存与生成开销**省了 k 倍** 。

代价是同一请求内各个位置的替补采样不再互相独立。之所以能接受,正是 3.6 那个事实的另一面:**一次前向里每个请求最多只有一个位置真正用到替补,其余位置的替补都被丢弃** ——独立性无从体现,也就无所谓。

**一个统计学上的让步,靠一个调度上的事实兜住了。**

### 3.8 均匀随机数必须用 float64

接受判定要一个 `[0,1)` 的均匀随机数。这个张量用的是 **float64** ,注释给了一条很具体的理由,还附了 PyTorch 的 issue 编号:

**float32 下,`torch.rand` 有不可忽略的概率返回精确的 `0.0`。**

而接受条件是 `p/q >= u` 。`u` 一旦是 0,**任何非负的比值都满足它** ——这个草稿 token 就被无条件接受了。1.36 费那么大劲论证的分布等价性,会被这个浮点细节直接击穿:高频出现的、目标其实不认可的 token,会以本不该有的概率混进输出。

float64 把这个概率压到可忽略。**代价是一个 `[token 数]` 的小张量翻倍,换的是一个数学保证不被浮点实现悄悄破坏。**

> 这是全章最值得记住的一条:**一个数学证明成立与否,可能取决于随机数发生器的尾部行为。** 论文里写 `u ~ Uniform(0,1)` 时,没人会想到 0 这个端点。

### 3.9 空请求不抽随机数,否则不可复现

上面那两个随机张量的生成代码里,都有一句「草稿数为 0 的请求跳过」的检查,注释都写着同一个词:**为了可复现性。**

理由要绕一下才想明白:给一个零草稿的请求也抽一次随机数,会**推进那个请求专属生成器的状态** 。于是这条请求后续拿到的随机序列,就取决于「它之前那些批次里有没有出现过空请求」——而这是调度器的动态行为,用户完全控制不了。

**结果就是:同样的输入、同样的种子,换一个负载就可能得到不同的输出。** 种子的承诺被批处理的动态性悄悄破坏了。

这条和 1.24 那个「先批量填、再逐行覆盖」放在一起看很有意思:两处都是在处理「**逐请求的随机性,怎么活在一个批处理系统里**」。批量填是为了快,跳过空请求是为了准,**两个约束都得满足,所以代码才长成那个样子**。

### 3.10 输出用占位值预填,全程只做一次拷回

最后一条是整条验证链路的收口。

输出缓冲在 kernel 之前就用 **`-1`** 整体预填。kernel 只写它真正接受或恢复的位置,被截断的位置**保持 `-1` 不动** 。

好处是 kernel 里**不需要为「这一行写了几个」做任何通信** ——没有原子计数,没有额外的长度张量,也不必让不同请求的程序实例互相协调。写多少写多少,读的人自己认。

认的人是收尾那一步:它把整批结果一次性拷回 CPU,然后用一个掩码过滤。掩码有两个条件:**不等于占位值**(滤掉被截断的位置),以及**小于词表大小**(兜底越界 id,对应 1.39 提到的那两道防护)。

还有一个细节值得学:某些请求整行要被丢弃时,做法是**把那一行的掩码整体置假**,而不是事后从结果列表里删掉那一行。**这样输出的行数始终与批次对齐** ,上游按下标取结果永远不会错位。

而最要紧的是那个「一次」:**整批的接受与拒绝判定全部在 GPU 上完成,从头到尾只有这一次拷回。** 这一章从 1.12 的早退、1.19 的快路径、1.22 的采样方式、3.1 的位宽选择一路数下来,所有取舍最终都指向同一件事 —— **让这条路径上只剩这一个同步点。**

## Part 4|对比与决策

前面三部分讲的是这条管线怎么造的。这一部分讲怎么用它:参数面和别家差在哪、几个典型场景怎么配、出了问题先怀疑什么。

### 4.1 和别的引擎比,参数面差在哪

下表 vLLM 那一列是本章全程对着源码核过的;**另外三列不在本仓库内、无法用源码校验** ,是讲稿的定位参考,看个大概就行。

| 参数 | vLLM | HuggingFace | TGI | OpenAI API |
|---|---|---|---|---|
| `temperature` / `top_p` | 有 | 有 | 有 | 有 |
| `top_k` | 有 | 有 | 有 | **无** |
| `min_p` | 有 | 有 | 有 | **无** |
| `presence` / `frequency_penalty` | 有 | **无** | 有 | 有 |
| `repetition_penalty` | 有 | 有 | 有 | **无** |
| `logprobs` | 有(top-N,**-1 给全词表**) | 有 | 有 | 有(top-N) |
| `seed` | 有 | 有 | 有 | 有(尽力而为,不保证跨模型版本) |
| `bad_words` | 有 | 有 | **无** | **无** |
| `allowed_token_ids` | 有 | **无** | **无** | **无** |

一句话:**vLLM 的参数面基本是这几家的并集。** 这不奇怪——它要同时兼容 OpenAI 协议和社区习惯。

但这带来一个本章已经撞见过的后果:**同一张表里的参数血统不同。** `frequency_penalty` 与 `presence_penalty` 的源码注释写明是按 OpenAI 的定义实现的,而 `repetition_penalty` 来自社区、不是 OpenAI 的参数——**于是就有了 1.8 那个不对称:三个 penalty 里只有 repetition 会看 prompt。** 参数表是并集,语义却不是统一设计出来的。

最后两行值得单独看:`allowed_token_ids` 是四家里 vLLM 独有的,而它正是结构化输出的底座(1.5)。**能把这个能力暴露成一个普通采样参数,是 vLLM 把语法约束和采样管线打通的直接结果。**

### 4.2 几个场景怎么配

下表是**经验值,不是本仓库实测,也不是源码里的推荐** 。放在这里是因为它能把前面几节的机制串成可操作的东西。

| 场景 | 起点 | 为什么 |
|---|---|---|
| 代码生成 | `temperature=0.2` ,`top_p=0.95` | 语法必须正确、token 间强依赖,低温保确定性;留一点点候选,防个别位置排序不稳 |
| 创意写作 | `temperature=0.8` ,`top_p=0.95` | 要意外感,高温让低概率 token 有机会;`top_p` 截掉概率极低的尾巴,避免语法不通 |
| 事实问答 | `temperature=0~0.3` ,`top_p=0.9` | 纯贪心最稳但可能陷进重复,留一点随机性打破僵局;`top_p` 比创意场景更严 |
| 多轮对话 | `temperature=0.7` ,`top_p=0.9` ,`repetition_penalty=1.05` | 要自然但不跑题;轻度抑制复读同一措辞 |
| JSON 输出 | `temperature=0` ,配结构化输出 | 双重保证:白名单保证**合法** ,贪心保证**稳定** |

三条配套的提醒,都是前面的机制直接推出来的:

- **`repetition_penalty` 不要往高了调。** 它对所有出现过的 token 一视同仁,而标点、常用虚词本来就该高频重复(1.8)。1.05 已经是「轻度」,再往上模型会开始回避该用的词。
- **事实问答那行的 `0~0.3` 不是连续的。** `temperature=0` 走的是完全不同的代码路径(1.21),不是「非常小的温度」。想要确定性就给 0,想要一点随机性就给 0.1 以上,中间没有过渡地带。
- **JSON 那行的两件事是正交的。** 白名单管的是「合法」,温度管的是「稳定」——语法引擎保证输出能被解析,贪心保证同样的输入得到同样的输出。缺哪一半都不够。

### 4.3 出了问题先查什么

| 症状 | 先怀疑 | 为什么 |
|---|---|---|
| 输出一直复读 | penalty **数的是谁** | 三个 penalty 里只有 repetition 看 prompt(1.8)。想让模型别抄 prompt 里的词,调 `frequency_penalty` 是没用的 |
| 设了种子但结果对不上 | 批次里有没有**零草稿的请求** | 推测解码下,给零草稿请求也抽随机数会推进它的生成器状态(3.9);另外种子只保证同一实现内可复现 |
| 开了推测解码,某个参数像没生效 | 查 1.34 那张表 | `min_p` 和 `logit_bias` 确实不生效,**其余照常** 。引擎启动时会打一条警告,不是悄悄失效 |
| 参数设了但完全没反应 | 是不是**和哨兵值相同** | `top_p=1.0` / `top_k=0` / `min_p=0.0` 都表示不过滤(1.29),它们不是 `None` |
| 延迟比预期高 | 有没有要 `logprobs` | 它要多一次全词表 topk 加一次排名统计(1.28),N 大或 batch 大时代价明显 |
| 低概率 token 的分布不对 | fp64 噪声开关 | 低精度浮点在极小值附近分辨率不足,会让极低概率 token 的实际采样概率偏离理论值(1.25) |

最后补一条本章没法从症状倒推、但值得记住的:**几乎所有性能相关的设计都在避开同一件事——GPU 到 CPU 的同步。** 看到采样路径上出现意料之外的延迟,先问「这一步是不是要 CPU 知道 GPU 的某个值」(1.19、1.22、3.10)。

### 4.4 常见误区

每条都是容易想当然、而源码给出相反答案的地方。

| 误区 | 真相 |
|---|---|
| `temperature=0` 只是「非常低的温度」 | 不。它走的是另一条路径:直接取最大值,**不经过 softmax 和随机采样** 。判断用的是「小于 1e-5」而不是等于 0 |
| `top_k` 和 `top_p` 互斥,只能选一个 | 不。两者并联,同时设了就依次都过一遍,交集是最终候选集 |
| 不想过滤就把 `top_p` / `top_k` 设成 `None` | 不。它们的默认值是 `1.0` 和 `0` ,这两个值才表示不过滤 |
| `repetition_penalty` 越高输出越好 | 不。过高会让模型回避必要的重复,标点和常用词首当其冲 |
| 要 `logprobs` 是免费的 | 不。要多一次全词表 topk 加一次排名统计 |
| `min_p` 一定比 `top_p` 更严格 | 不。分布尖锐时 top_p 更严,分布平坦时反过来——两者的严格度次序会翻转 |
| 开了推测解码,采样参数全部失效 | 不。只有 `min_p` 与 `logit_bias` 失效,白名单、禁词、三种 penalty、温度、`top_k` / `top_p` 都照常生效 |
| `min_p` 失效是悄悄发生的 | 不。引擎启动时会打一条明确的警告;传了自定义处理器则直接报错 |
| `logprobs` 返回的是采样时用的那份分数 | 不。默认返回的是**加工之前**的原始分数,快照在管线最开头就取了 |
| 用户要 N 个 logprob 就返回 N 个 | 不一定。被采样中的那个会被拼进去,所以可能是 N 也可能是 N+1 |
| 裁剪要先排序 | 不。默认路径根本不排序,它去找一个阈值;全排序是没装 Triton 时的回落路径 |
| 拒绝之后从目标分布重新采一个就行 | 不。必须从修正分布采,否则被接受路径已经贡献过的概率会被算第二遍 |
| 推测解码是近似加速,会损失质量 | 不。拒绝采样保证最终分布与「直接用目标模型采样」**完全一致** ,是无损加速 |
