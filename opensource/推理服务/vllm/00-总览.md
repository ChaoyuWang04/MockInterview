## 一、vLLM 是什么

**vLLM** 是 UC Berkeley 主导开源的大语言模型高吞吐、低延迟推理与服务框架。它要解决的根本矛盾是:GPU 显存有限、单卡算力有限、用户请求潮汐波动,却要把一个百亿到千亿参数的模型以 **高吞吐** (throughput,单位时间处理的 token 数)、**低延迟** (latency,单 token 生成时间)服务成百上千个并发请求。

与训练框架(Megatron-LM、DeepSpeed)相比,推理框架的优化对象完全不同:

| 维度 | 训练框架(Megatron / DeepSpeed) | 推理框架(vLLM) |
|---|---|---|
| 目标 | 一次前向 + 一次反向 + 一次优化器更新 | 只有前向,但要重复跑几百到几十万次(每生成一个 token 跑一次) |
| 批处理 | 静态 batch,整个训练过程不变 | 动态 batch:每 step 都可能增减请求(continuous batching,连续批处理) |
| 显存大头 | 激活值、优化器状态、梯度 | KV Cache(KV 缓存):历史 token 的 Key/Value 张量,随序列长度线性增长 |
| 核心指标 | TFLOPS 利用率、迭代时间 | 吞吐(tokens/s)、首 token 延迟(TTFT)、单 token 延迟(TPOT) |
| 并行维度 | TP/PP/DP/EP/SP/CP(多维) | TP/PP/EP/DP 为主,另有 SP 与 CP。推理没有反向,不需要为梯度和优化器状态切分;SP 以编译期 pass 的形式存在,CP 分 prefill 侧的 PCP 与 decode 侧的 DCP |

一句话定位:**vLLM 把「显存管理 + 动态调度 + 注意力 kernel + 分布式执行 + 采样」五件事做成了一套完整、高性能、易部署的推理服务栈。** 它和 SGLang、TensorRT-LLM、HuggingFace TGI 是当前主流的四个 LLM 推理引擎(讲稿观点)。

顶层入口(仓库根 `vllm/`):

- `vllm.LLM(...)`:离线批量推理(同步),最常用的 Python API。
- `vllm.AsyncLLMEngine` / v1 的 `AsyncLLM`:在线服务(异步流式),配合 OpenAI 兼容 HTTP server。前者只是别名,真身是 v1 的 `AsyncLLM`。
- `vllm serve <model>`:命令行启动 OpenAI 兼容 server,入口在 `vllm/entrypoints/`。

代码组织上,vLLM 只有一套实现,在 `vllm/v1/`:

- 调度器、引擎进程架构(ZMQ 多进程)、注意力后端注册机制、Worker 与 ModelRunner 全部在 `vllm/v1/` 下。
- 顶层不存在 `vllm/core/`、`vllm/worker/`、`vllm/attention/` 这三个目录。
- `vllm/engine/` 只剩 4 个模块文件(`arg_utils.py`、`async_llm_engine.py`、`llm_engine.py`、`protocol.py`),其中 `llm_engine.py` 全文只有一句别名 `LLMEngine = V1LLMEngine`。真正的引擎实现在 `vllm/v1/engine/llm_engine.py`。CLI 参数 `EngineArgs` 则实打实地住在 `vllm/engine/arg_utils.py`,不在 `v1/` 下,这是唯一需要注意的例外。

读代码时不必区分 V0/V1 路径,`vllm/v1/` 就是全部。从体量看,模型实现占了整个仓库近一半,真正的引擎骨架在 `v1/`,其中注意力后端和 worker 又是 `v1/` 里最大的两块。

## 二、六大核心创新:先建立全局图景

理解 vLLM 的关键,是先看清它把一次推理服务 **沿哪些维度优化** 。这些优化可以叠加,一个生产部署通常同时用其中 4 到 6 项:

```text
            客户端并发请求 (HTTP/gRPC, n=100~10000)
                        |
            ┌───────────┴───────────┐
            ▼                       ▼
    [1] 连续批处理            [2] PagedAttention
    (Continuous Batching)     (KV Cache 分块)
    每 step 动态增减请求       KV Cache 按 block 管理
    不等整批完成               显存利用率 → 接近 100%
            |                       |
            └───────────┬───────────┘
                        ▼
            [3] Chunked Prefill + Prefix Caching
            长 prompt 分块喂入;公共前缀 KV 复用
            prefill 与 decode 同 batch 调度
                        |
            ┌───────────┼───────────┐
            ▼           ▼           ▼
    [4] 推测解码    [5] 注意力后端   [6] 量化 / 分布式
    (Speculative    FlashAttn /     FP8 / AWQ / GPTQ
     Decoding)      FlashInfer /    TP / PP / EP / DP
    小模型猜多 token MLA / Mamba    多卡 / 多节点
    大模型并行验证
```

> 🖼️ 占位:六大创新叠加总图。回答「一个请求从进门到出 token,依次经过哪六层优化、每层动的是算力还是显存」;外围能力(API 层、connector、LoRA、多模态、投机解码)标灰。

一句话记忆:

- **连续批处理**:动态调度,提高 GPU 利用率和吞吐。
- **PagedAttention**:KV Cache 按 block(块)分配,显存利用率接近 100%,零碎片。
- **Chunked Prefill**:长 prompt 切块,prefill(预填充)和 decode(解码)混排,避免 prefill 阻塞 decode。
- **Prefix Caching**:公共前缀复用,省重复计算(系统 prompt、few-shot)。
- **推测解码**:小模型或草稿猜,大模型一次验证多 token,降单 token 延迟。
- **量化 + 分布式**:低精度 + 多卡,进一步降显存、提吞吐。

## 三、推理框架特性清单(每个解决什么问题)

下面逐个列出 vLLM 的核心特性、它解决什么问题、以及代码大致在哪。

### 3.1 连续批处理 Continuous Batching(迭代级动态调度)

- **解决的问题**:朴素批处理(static batching,静态批处理)必须等 batch 内所有请求生成完毕才能加新请求。有的请求输出 10 个 token 就结束,有的要 1000 个,整个 batch 被「长请求」拖累,GPU 大量空转。
- **做法**:每个 decode step(解码步)都重新决策:哪些请求继续、哪些结束、哪些新请求加进来。一个请求生成完 EOS(结束符)就立刻移出 batch,腾出 KV Cache 空间给新请求。结合 chunked prefill 后,连 prefill 阶段的请求都能与 decode 请求同 batch。
- **代码位置**:`vllm/v1/core/sched/scheduler.py`(核心是 `schedule()` 方法)、`vllm/v1/core/sched/request_queue.py`(FCFS 与 Priority 两种请求队列)。
- **对比**(讲稿观点):HuggingFace TGI 也做连续批处理,但调度实现较简单;vLLM 的调度器与 PagedAttention 深度耦合,能在显存压力下抢占(preempt)低优先级请求,把 KV Cache 重算或换出。
- **典型开关**:`--max-num-seqs`(最大并发数,默认 128)、`--max-num-batched-tokens`(每 step 最大 token 数,默认 2048)、`--scheduling-policy fcfs/priority`。

> 🖼️ 占位:静态批处理与连续批处理的时间线对比。回答「同样四条长短不一的请求,两种调度下 GPU 各空转了多少 step」。

### 3.2 PagedAttention(KV Cache 虚拟内存化)

- **解决的问题**:朴素 KV Cache 管理为每个请求预分配一整块连续显存(按 `max_model_len` 上限)。问题有二:内部碎片,请求实际只用了 100 个 token,却占着 2048 个 token 的空间;外部碎片,长请求显存不够,但累计碎片总和够。朴素管理下显存利用率常低于 30%(讲稿观点)。
- **做法**:受操作系统虚拟内存(paging,分页机制)启发,把 KV Cache 切成固定大小的 block(块),用 **block table** (块表)把逻辑 token 位置映射到物理 block。请求需要更多空间时按需分配 block,结束时立刻归还。显存利用率可接近 100%,且支持跨请求共享 block,这是 prefix caching 的基础。
- **代码位置**:
  - Python 层:`vllm/v1/core/kv_cache_manager.py`(`KVCacheManager`)、`vllm/v1/core/block_pool.py`(`BlockPool`,物理 block 的分配与回收)、`vllm/v1/core/kv_cache_utils.py`(block hash、prefix caching 工具)、`vllm/v1/core/kv_cache_coordinator.py` 与 `single_type_kv_cache_manager.py`(混合 attention 与 mamba 等多种 KV 类型的协调层;后者按 KV 类型分出九个子类:全注意力、RSWA、滑动窗口、环形缓冲、Kpool 尾部、分块局部注意力、Mamba、交叉注意力、带 sink 的全注意力)。
  - C++/CUDA 层:`csrc/cache.h` + `csrc/libtorch_stable/cache_kernels.cu`(`reshape_and_cache` 等把新算出的 K/V 写进 block 的 kernel)。注意 `csrc/attention/` 下只剩几个 dtype 头文件,没有任何 `.cu`:CUDA 平台上并没有 vLLM 自研的经典 paged attention kernel,block table 的实际消费者是 FlashAttention、FlashInfer、Triton 后端。仍保留自研 attention kernel 的只有 ROCm 路径 `csrc/rocm/attention.cu`,以及 `csrc/libtorch_stable/attention/mla/` 下针对 SM100 的 MLA kernel。
- **对比**(讲稿观点):SGLang 的 RadixAttention(基数树注意力)也做块化,但用 Radix Tree(基数树)组织共享前缀;vLLM 用更简单的 hash-based block table,部署更轻。TensorRT-LLM 用 `KVCacheManager` 但块大小可变。
- **典型开关**:
  - `--block-size`:`CacheConfig.block_size` 的字段默认是 `None`,未显式指定时由一个校验器回落到 16,平台层还可能再覆盖。所以「默认 16」是 **回落值** 而非字段默认值。读 config 决议链时要注意这个区别:字段定义处的默认值不等于实际生效值。
  - `--gpu-memory-utilization`:默认 0.92。
  - CPU 换出不是 `CacheConfig` 的字段:`swap_space` 在配置与 CLI 中都不存在。KV 下沉走 `vllm/v1/kv_offload/` 与 kv_connector 里的 offloading connector。

> 🖼️ 占位:一条请求的逻辑 token 位置到物理 block 的映射。回答「块表长什么样、两条共享前缀的请求怎么指向同一批物理块」。

### 3.3 Chunked Prefill(长 prompt 分块预填充)

- **解决的问题**:一个 batch 里如果同时有 prefill 请求(处理长 prompt,几千到几万 token)和 decode 请求(每步 1 个 token),朴素做法是串行:先做完整个 prefill(耗时数百 ms),decode 请求全部阻塞等待。这导致 decode 的 TPOT(time per output token,单 token 延迟)出现尖峰。
- **做法**:把长 prompt 切片,每 step 只处理 chunk_size 个 token(如 512),剩余 token 留到后续 step。prefill 请求和 decode 请求 **同 batch 调度** ,每 step 都让 decode 请求拿到计算资源。vLLM V1 进一步取消了 prefill/decode phase 的概念,所有请求只有「已计算 token 数 vs 总 token 数」的差别,调度器统一处理。
- **代码位置**:`vllm/v1/core/sched/scheduler.py` 的 `schedule()` 方法(核心逻辑:token 预算在 running 和 waiting 队列间分配)、配置项在 `vllm/config/scheduler.py` 的 `SchedulerConfig`(`max_num_batched_tokens`、`long_prefill_token_threshold`)。
- **对比**(讲稿观点):TensorRT-LLM 用 inflight batching 实现类似机制;SGLang 也支持 chunked prefill;TGI 早期不支持,近期加入。vLLM 的 V1 实现最激进,彻底统一了 phase 概念。

> 🖼️ 占位:一个 step 的 token 预算如何在 decode 请求与分块中的 prefill 请求之间切分。回答「预算 2048 时,3 条 decode 加 1 条 5000 token 的 prompt 各拿多少」。

### 3.4 Prefix Caching(前缀缓存复用)

- **解决的问题**:很多请求共享相同的前缀:系统 prompt(system prompt)、few-shot examples(少样本示例)、长文档 QA 的文档内容。朴素做法下每个请求都要重新算一遍 prefill,浪费计算和延迟。
- **做法**:把每个 block 的 KV 内容用 hash(哈希)标识,相同的 block 在 cache 里只算一次,后续请求命中则直接复用。哈希是链式的:输入是父块的哈希、本块的 token ids 和额外键(LoRA id、多模态内容、prompt embeds 等混进去以免张冠李戴),所以只有从头开始完全相同的前缀才命中。Prefix cache 跨请求、跨 batch 生效;vLLM 还有 **automatic prefix caching** (自动前缀缓存),不需要用户标注哪些是 prefix,调度器自动识别。
- **代码位置**:`vllm/v1/core/kv_cache_utils.py`(`KVCacheBlock`、`hash_block_tokens`、`get_request_block_hasher`、`generate_block_hash_extra_keys`、`FreeKVCacheBlockQueue` 这个 LRU 双向链表)、`vllm/v1/core/block_pool.py`(`BlockPool`、`get_cached_block`、`cache_full_blocks`、`cache_partial_block`)。命中查询的唯一入口是 `BlockPool.get_cached_block()`。
- **对比**(讲稿观点):SGLang 的 RadixAttention 用 Radix Tree 显式组织前缀树,命中率更高但实现复杂;vLLM 用 hash + LRU(最近最少使用)回收,简单高效。生产场景命中率通常在 60% 到 90%,取决于请求模式,这是量级参考,不是本仓库实测数据。
- **典型开关**:`--enable-prefix-caching` / `--no-enable-prefix-caching`(默认开)、`--prefix-caching-hash-algo`(默认 `sha256`,另可选 `sha256_cbor`、`xxhash`、`xxhash_cbor`)。

> 🖼️ 占位:块哈希链与共享块。回答「两条请求前 512 个 token 相同时,哪些块被共用、从第几块开始分叉」。

### 3.5 推测解码 Speculative Decoding(草稿-验证双模型)

- **解决的问题**:自回归(autoregressive)生成的根本瓶颈是每步只生成 1 个 token,需要串行跑几百到几千次前向。GPU 算力严重浪费,batch=1 时利用率常低于 5%(讲稿观点)。
- **做法**:用一个小而快的 draft model(草稿模型)先猜 k 个 token(如 k=4),再用 target model(目标大模型)一次前向并行验证这 k 个 token。验证通过的 token 直接采纳,验证失败则丢弃后重新采样。理想情况下,每 step 输出 k 个 token,TPOT 降到 1/k。vLLM 支持多种 proposer:
  - EAGLE / EAGLE3(主流):自回归 draft model,结合 hidden state(隐藏状态)预测。
  - MTP(Multi-Token Prediction):DeepSeek V3 风格,单模型多 token 头。
  - n-gram:无需 draft model,用 n-gram 表猜,适合代码、对话重复模式场景。
  - Medusa:在 target model 上加多个解码头。
  - Suffix Decoding:基于后缀树的推测,适合结构化输出。
  - 另有若干模型或方案专用的 proposer(dflash、gemma4、step3p5、dspark 等),以及动态推测长度策略。
- **代码位置**:
  - 调度集成:调度器用 `request.num_tokens_with_spec` 替代 `num_tokens` 参与 token budget 计算。spec token 在调度器眼里就是「还没算的 token」。
  - Proposer(CPU 或调度侧算法):`vllm/v1/spec_decode/`,每种 proposer 一个文件,加上 metadata、metrics、vocab mapping 等公共设施。
  - Worker 端(GPU 侧执行与验证):`vllm/v1/worker/gpu/spec_decode/`,按 eagle、mtp、autoregressive 等分子目录,配 rejection sampler 与自适应验证。MTP 只在 worker 侧有目录,`vllm/v1/spec_decode/` 下没有 mtp。
  - 拒绝采样有两份实现:通用的 `vllm/v1/sample/rejection_sampler.py` 与 spec decode 专用的 `vllm/v1/worker/gpu/spec_decode/rejection_sampler.py`。
- **对比**(讲稿观点):SGLang 早期以 EAGLE 实现著名;TensorRT-LLM 用 Medusa / SpecDecode;vLLM 支持多种 proposer 混用。

> 🖼️ 占位:一次「猜 k 个、验一次」的循环。回答「草稿 token 在调度预算、KV 块、拒绝采样三处各怎么被记账」。

### 3.6 注意力后端 Attention Backends(多 kernel 抽象层)

- **解决的问题**:不同硬件(NVIDIA / AMD / Intel / TPU)、不同模型架构(标准 MHA、GQA、MQA、MLA、Mamba)、不同精度(FP16 / BF16 / FP8)需要不同的 attention kernel;没有「一个 kernel 走天下」的银弹。
- **做法**:定义统一的 `AttentionBackend` 抽象层,让上层模型代码不用关心底层 kernel。vLLM 支持的后端:
  - FlashAttention(`flash_attn.py`):最常用,Dao 系列经典实现。
  - FlashInfer(`flashinfer.py`):NVIDIA 后发的整合库,在 Hopper / Blackwell 上对 MLA、PagedAttention 支持更好。
  - Triton Attention(`triton_attn.py`):开源 Triton 实现,便于二次开发。
  - MLA backends(`mla/` 子目录):DeepSeek V2/V3 的 Multi-Latent Attention(多隐注意力),有 flashattn、flashinfer、flashmla、triton、cutlass、cpu、amx、rocm 等十余个实现,外加一整套 sparse 变体,那是 DeepSeek V3.2 稀疏注意力的落点;`mla/prefill/` 下另有 MLA prefill 阶段专用的 backend 与 selector。
  - Mamba / SSM(`mamba_attn.py`、`mamba1_attn.py`、`mamba2_attn.py`、`linear_attn.py`、`gdn_attn.py`、`short_conv_attn.py`):状态空间与线性注意力架构,非标准 attention。
  - ROCm / XPU / CPU:硬件专用后端(`rocm_attn.py`、`rocm_aiter_fa.py`、`rocm_aiter_unified_attn.py`、`cpu_attn.py`)。
  - 另有 `flex_attention.py`(PyTorch FlexAttention)、`turboquant_attn.py`,以及 K/V 头维不同的 diffkv 变体。
- **代码位置**:`vllm/v1/attention/backends/`(各后端实现)、`vllm/v1/attention/selector.py`(自动选择)、`vllm/v1/attention/backends/registry.py`(注册表)、`vllm/v1/attention/backend.py`(`AttentionBackend` 抽象基类)。
- **对比**(讲稿观点):SGLang 也基于 FlashInfer / FlashAttention;TensorRT-LLM 用自家 closed-source kernel。vLLM 的优势是抽象层清晰,第三方 kernel 容易接入。

### 3.7 模型并行 Model Parallelism(推理版 TP/PP/EP/DP)

- **解决的问题**:百亿到千亿参数模型单卡放不下;单卡算力不足以满足延迟要求。
- **做法**:与训练版并行类似但精简:
  - TP(Tensor Parallel,张量并行):与训练版完全一样,列/行切权重矩阵,前向 all-reduce。推理时没有反向,所以 TP 的开销纯粹是每层 1 次 all-reduce,比训练便宜。
  - PP(Pipeline Parallel,流水线并行):层切分,但推理没有 1F1B 调度,所有 micro-batch 顺序穿过 stages。PP 在推理中较少用(气泡大),主要是 TP 不够时,如 200B+ 模型在 8 卡 TP 后仍放不下。
  - EP(Expert Parallel,专家并行):MoE 模型用,与训练版类似但只前向。vLLM 支持 DeepSeek V2/V3、Mixtral、Qwen MoE 等的 EP。
  - DP(Data Parallel,数据并行):多个 model replica(模型副本)并行处理不同请求,每个 replica 独立调度;常与 EP 组合(DP attention + EP MoE)或配合 PD 分离使用。
- **代码位置**:
  - 并行状态:`vllm/distributed/parallel_state.py`(进程组、TP/PP/DP/EP rank 管理)。
  - 并行层:`vllm/model_executor/layers/linear.py`(`ColumnParallelLinear` / `RowParallelLinear` / `MergedColumnParallelLinear` / `QKVParallelLinear`)、`vllm/model_executor/layers/vocab_parallel_embedding.py`。
  - Worker 组织:`vllm/v1/worker/worker_base.py`、`vllm/v1/executor/`(uniproc / multiproc / ray 三种执行器)。
  - DP 相关辅助:`vllm/v1/worker/dp_utils.py`、`vllm/v1/worker/gpu/dp_utils.py`。
- **对比**(讲稿观点):Megatron 训练版要处理反向通信、梯度分桶、优化器分片;vLLM 推理版只需前向,所以并行实现更简单、更轻量。

### 3.8 量化 Quantization(低精度推理)

- **解决的问题**:FP16/BF16 模型显存大、带宽吃紧;用更低精度(INT8 / FP8 / INT4)可以显存减半到四分之一、带宽减半到四分之一、计算加速 1.5 到 2 倍(Hopper 起 GPU 有 FP8 tensor core)。
- **做法**:量化方案的名字空间由 `QuantizationMethods` 这个 `Literal` 唯一定义(在 `vllm/model_executor/layers/quantization/__init__.py` 里),三十个合法取值。按热度看主要几类:
  - FP8(float8):Hopper / Ada / Blackwell 原生支持,最常用。权重 + 激活都 FP8(W8A8),精度损失极小。
  - compressed-tensors:当前事实上的「通用容器格式」,W8A8 / W4A16 / INT8 / FP8 / NVFP4 都可以用它描述。也是 AWQ/GPTQ checkpoint 的常见落点。
  - AWQ / GPTQ 家族:`awq`、`auto_awq`、`awq_marlin`、`gptq`、`auto_gptq`、`gptq_marlin` 六个方法名共存。`awq` / `gptq` 是朴素反量化路径,`*_marlin` 是 Marlin kernel 加速路径,两者由 config 自动挑选。文件是 `auto_awq.py` / `auto_gptq.py`(不是 `awq.py` / `gptq.py`),另有 `awq_triton.py` 提供 Triton 实现。
  - modelopt 系列:`modelopt`、`modelopt_fp4`、`modelopt_mxfp8`、`modelopt_mixed`,NVIDIA TensorRT Model Optimizer 导出的格式。
  - mxfp4 / gpt_oss_mxfp4:微缩放 FP4,gpt-oss 类模型常用。
  - online 在线量化:`online` 与一组简写(`fp8_per_tensor`、`fp8_per_block`、`fp8_per_channel`、`int8_per_channel_weight_only`、`nvfp4_per_token`、`mxfp8`),不需要预量化 checkpoint,加载 BF16 权重时现场量化。
  - 其余:`quark`(AMD Quark)、`torchao`、`inc`(Intel Neural Compressor)、`experts_int8`、`moe_wna16`(MoE 专用 W-N-A16)、`humming`、`deepseek_v4_fp8`。
  - 已标记弃用的两个:`fbgemm_fp8`、`fp_quant`。
  - bitsandbytes 不在支持列表内:`QuantizationMethods` 里没有它,配置、CLI 与 model loader 里也没有对应实现。想跑 4-bit,走 AWQ / GPTQ / compressed-tensors / mxfp4。
- **代码位置**:`vllm/model_executor/layers/quantization/`(每种方案一个文件,`compressed_tensors/`、`online/`、`quark/`、`inc/` 等各自成子目录)、量化 GEMM kernel 的选择在 `vllm/model_executor/kernels/`。
- **对比**(讲稿观点):TensorRT-LLM 用自家 INT8/FP8 方案;SGLang 也用 AWQ/GPTQ/FP8。vLLM 的优势是统一抽象层:`QuantizationConfig` 与 `LinearMethodBase` 两个基类让同一份模型代码可挂任意量化方案,模型实现里看不到量化细节。

### 3.9 结构化输出 Structured Output(语法约束生成)

- **解决的问题**:很多场景需要模型输出符合 schema 的内容:JSON、正则、上下文无关文法。朴素做法是模型自由生成再用代码解析,但模型可能生成语法错误的 token,导致解析失败。
- **做法**:在每个 token 采样前,用 grammar(文法)信息计算一个 bitmask(位掩码),只保留语法合法的 token id,把非法 token 的 logits 设为负无穷。合法 backend 由 `StructuredOutputsBackend` 定义,共 5 个:
  - `auto`(默认值):它不是某个具体实现,而是一条试探链,在 `SamplingParams` 的请求级校验里执行:先试 xgrammar,能过就用 xgrammar;schema 里有 xgrammar 不支持的特性就退到 guidance;如果 tokenizer 是非 tekken 的 Mistral、或 schema 含 guidance 不支持的特性,则退到 outlines。选中后会打上「这是自动选的」标记,以便同一个 `SamplingParams` 被复用时不误报「请求级 backend 选择不支持」。
  - `xgrammar`:C++ 实现,最快。
  - `guidance`。
  - `outlines`。
  - `lm-format-enforcer`:不支持 Mistral tokenizer,直接报错。
  - backend 是引擎级而非请求级:`StructuredOutputManager` 只持有一个 backend 实例,请求里指定与引擎启动值不一致会直接报错。
- **代码位置**:`vllm/v1/structured_output/`(四个 backend 文件加 `request.py`、`backend_types.py`;`auto` 不是文件)、掩码下发在 `Scheduler.get_grammar_bitmask()`,内部调 `StructuredOutputManager.grammar_bitmask()`。
- **对比**(讲稿观点):SGLang 也用 xgrammar / outlines;vLLM 的实现集成度更高,掩码由 scheduler 统一产出后随 batch 一起下发到 worker。

### 3.10 多模态 Multimodal(视觉 / 音频输入)

- **解决的问题**:现代 LLM 越来越多模态:LLaVA、Qwen-VL、Pixtral 等接受图像或音频输入。需要把多模态输入编码成 token embedding 喂给 LLM。
- **做法**:`MultiModalConfig` 管配额与缓存开关,`BaseMultiModalProcessor` 管「原始媒体 → placeholder token + 张量」的转换,每个多模态模型通过 `vllm/multimodal/registry.py` 注册自己的 processor。视觉或音频 encoder 的前向在 worker 侧驱动,产出的 embedding 由 model runner 按 placeholder 位置合并进 `input_embeds`:合并发生在 runner,不在模型 `forward` 里。生产路径在 `gpu_model_runner.py` 里;讲稿说的 encoder runner 属于实验中的 Model Runner V2,见第四节。
- **代码位置**:`vllm/multimodal/`(processing、registry、cache、hasher、inputs、encoder_budget,以及 image / audio / video 三种模态的解析)、`vllm/v1/worker/gpu/mm/`(V2 的 encoder runner 与 encoder cache)、`vllm/v1/core/encoder_cache_manager.py`(调度侧的 encoder cache 记账)、模型实现散在 `vllm/model_executor/models/`(`llava*.py`、`qwen*_vl.py`、`gemma3_mm.py` 等)。
- **能力边界**:vLLM 的多模态是输入侧能力,不支持文生图、图生图、文生视频、TTS。输出只有三类:文本、pooling 向量或分数、以及 `--mm-encoder-only` 模式下交给下游进程的视觉 embedding。ASR 走独立端点 `vllm/entrypoints/speech_to_text/`。
- **对比**(讲稿观点):SGLang 也支持多模态;TensorRT-LLM 支持较少。

### 3.11 引擎进程架构 Engine Architecture(V1 多进程 + ZMQ)

- **解决的问题**:在线服务场景,API server 必须高并发、低延迟响应;同时 GPU 计算必须不被 IO 阻塞。单进程架构下,tokenization、model forward、detokenization、HTTP 互相阻塞。
- **做法**:V1 把引擎拆成多进程:
  - API 进程:处理 HTTP 请求、tokenize、detokenize、流式返回。
  - EngineCore 进程:跑 scheduler + model executor 主循环。
  - 之间用 ZMQ socket(序列化用 msgspec 的 msgpack)通信。EngineCore 进程里用两个线程分别收发输入输出队列,主线程跑忙循环,让 GPU 计算(释放 GIL)与 IO、序列化重叠。
- **代码位置**:
  - EngineCore:`vllm/v1/engine/core.py`(`EngineCore` 是主循环,`EngineCoreProc` 是 ZMQ 多进程封装,DP 模式另有 `DPEngineCoreProc`)。
  - AsyncLLM:`vllm/v1/engine/async_llm.py`(API 进程侧异步入口)。
  - 客户端层级:`vllm/v1/engine/core_client.py`(`InprocClient` / `MPClient` / `SyncMPClient` / `AsyncMPClient`)。
  - 序列化:`vllm/v1/serial_utils.py`。
- **对比**(讲稿观点):SGLang 用类似的多进程架构(scheduler / executor / detokenizer 分进程);TensorRT-LLM 用 Python + triton server。vLLM V1 的设计借鉴了 SGLang,但更紧凑(用线程而非全多进程)。

> 🖼️ 占位:进程与线程边界图。回答「API 进程、EngineCore 进程、worker 进程各持有什么,哪条边是 ZMQ、哪条是 NCCL」。

### 3.12 PD 分离与 KV 传输 Prefill-Decode Disaggregation

- **解决的问题**:在线服务中,prefill(首 token 计算)是 compute-bound(计算密集),decode 是 memory-bound(访存密集),两者的最优 batch size、最优硬件配置完全不同。混合部署会互相拖累。
- **做法**:把 prefill 和 decode 部署到不同节点:prefill 节点专门跑 prompt prefill,然后把生成的 KV Cache 通过高速网络(NVLink / RDMA)传给 decode 节点继续生成。vLLM 提供 `kv_transfer` 抽象层支持这种 disaggregated(解耦)部署。
- **代码位置**:`vllm/distributed/kv_transfer/kv_connector/v1/`(connector 家族:`nixl/`、`mooncake/`、`moriio/`、`hf3fs/`、LMCache 的 connector 与集成层、`offloading_connector.py`、`simple_cpu_offload_connector.py`、`flexkv_connector.py`、`multi_connector.py` 等);worker 侧接入点 `vllm/v1/worker/kv_connector_model_runner_mixin.py`(生产 runner)与 `vllm/v1/worker/gpu/kv_connector.py`(V2)。
- **对比**(讲稿观点):DistServe、Mooncake 等专门做 PD 分离;SGLang 也有类似机制。vLLM 走 connector 插件化路线,`multi_connector.py` 还允许多个 connector 串联,例如先查本地 CPU 池、再查远端 Mooncake。

> 🖼️ 占位:PD 分离的数据流。回答「一条请求的 KV 从 prefill 节点的显存到 decode 节点的显存经过哪几只手」。

### 3.13 LoRA(Low-Rank Adaptation,低秩适配)

- **解决的问题**:服务多个微调任务时,为每个任务部署一个完整模型副本不现实(显存爆炸)。LoRA 通过低秩矩阵加到原模型上,每个 LoRA 适配器只有几 MB 到几十 MB。
- **做法**:运行时动态加载多个 LoRA 适配器,每个请求用 `lora_request` 指定用哪个。核心是 Punica 风格的分组 GEMM:所有 adapter 的 `lora_a` / `lora_b` 拼在一张大张量里,靠一组索引张量(`token_lora_mapping` 等)让一个 Triton kernel 同时服务 batch 里用不同 adapter 的 token。
- **代码位置**:`vllm/lora/`(`model_manager.py` 两级 LRU、`punica_wrapper/` 索引元数据、`ops/` 里的 lora_shrink / lora_expand Triton kernel、`layers/` 各并行层的 LoRA 包装、`resolver.py` 动态解析 adapter 路径)、worker 侧 `vllm/v1/worker/lora_model_runner_mixin.py` 与 `vllm/v1/worker/gpu/lora_utils.py`。`vllm/lora/` 不是「V0 遗留」,它就是当前唯一的 LoRA 实现。
- **典型开关**:`--enable-lora`、`--max-loras`、`--max-lora-rank`、`--lora-dtype`、`--fully-sharded-loras`、`--lora-target-modules`、`--default-mm-loras`。

### 3.14 采样 Sampling(temperature、top_p、top_k、penalty)

- **解决的问题**:模型输出 logits 后,如何采样出最终 token?需要支持多种采样策略、logits processor(如 repetition penalty 重复惩罚)、speculative decoding 的 rejection sampling(拒绝采样)。
- **做法**:`SamplingParams`(temperature / top_p / top_k / min_p / penalty 等)+ logits processor 链 + GPU 上的融合 sampler。注意 `top_k` 的「关闭」值是 0 而不是 -1。请求级默认值还会被 `--generation-config auto` 影响(默认会读模型自带的 `generation_config.json`),要拿到中性默认值须显式写 `--generation-config vllm`。
- **代码位置**:`vllm/sampling_params.py`(参数定义与校验)、`vllm/v1/sample/sampler.py`(GPU 采样器)、`vllm/v1/sample/logits_processor/`(处理器链)、`vllm/v1/sample/ops/`(top-k / top-p 等 kernel)、`vllm/v1/sample/rejection_sampler.py`(拒绝采样;spec decode 另有 worker 侧的一份)。

### 3.15 确定性推理与批不变性 Batch Invariance

- **解决的问题**:同一条 prompt、同样的 seed,在不同 batch 组成下可能生成不同的文本。根因是浮点加法不满足结合律,而 GPU kernel 会按 batch 规模改变归约(reduction)顺序:logits 上 1e-8 量级的差异足以在 argmax 处翻转一个 token,之后整段输出发散。
- **做法**:把所有参与前向的 kernel 换成「归约顺序只依赖张量形状、不依赖 batch 里有多少条请求」的实现。开关只有一个环境变量 `VLLM_BATCH_INVARIANT`(按整数解析,非 0 即开)。打开后:SM80 走 Triton persistent matmul(覆盖注册 `aten::mm` / `addmm` / `matmul` / `linear`),SM90 / SM100 主要靠固定 `CUBLAS_WORKSPACE_CONFIG=":16:8"`;FlashAttention 后端强制 `num_splits=1`;同时连带关掉一批依赖 batch 形状的优化,散布在注意力后端、通信、MoE 与量化层(具体禁了哪些,留到专页逐条核)。采样侧没有批不变分支,靠 `SamplingParams.seed` 保证可复现。
- **代码位置**:`vllm/model_executor/determinism/`(`batch_invariant.py`、`batch_invariant_configs.py`),入口 `init_batch_invariance()` 由 `vllm/v1/worker/gpu_worker.py` 调用;开关定义在 `vllm/envs.py`。

## 五、端到端一次推理服务(各特性如何协作)

把第三节的十五个特性放回一条请求的生命周期里看,它们各自站在哪个位置就清楚了:

```text
客户端 HTTP 请求 (POST /v1/chat/completions, prompt="...")
            |
            ▼
┌──────────────────────────────────────────────────┐
│ API 进程 (AsyncLLM)                               │
│   renderer 套聊天模板                             │
│   InputProcessor                                 │
│     - tokenize                                   │
│     - 多模态预处理 (图像/音频)                     │
│     - 构造 Request 对象                           │
│            │ ZMQ DEALER → ROUTER                  │
└────────────┼─────────────────────────────────────┘
             ▼
┌──────────────────────────────────────────────────┐
│ EngineCore 进程 (EngineCoreProc)                  │
│   input_thread → input_queue → run_busy_loop     │
│                                                  │
│   while not shutdown:      # EngineCore.step()   │
│     ① Scheduler.schedule():                      │
│         - 从 waiting/running 选请求               │
│         - chunked prefill + decode 混排           │
│         - KVCacheManager.allocate_slots          │
│           (PagedAttention block 分配)            │
│         - 命中 prefix cache 则复用 block          │
│         - 显存不够则 preempt 低优先级请求          │
│         - 推测解码: 按 num_tokens_with_spec 计账  │
│                                                  │
│     ② ModelExecutor.execute_model(non_block=True)│
│         立刻返回 future, 不阻塞:                  │
│         - GPU Worker 取 batch                    │
│         - Attention backend 用 block table 查 KV │
│         - 多卡 TP/PP/EP 并行                      │
│         - 量化 (FP8/AWQ) 前向                     │
│         - LoRA 适配器叠加                         │
│         - 产出 logits + hidden states            │
│                                                  │
│     ③ Scheduler.get_grammar_bitmask()            │
│         与 ② 的 GPU 计算重叠执行 (CPU 侧算掩码)   │
│                                                  │
│     ④ future.result() → sample_tokens(bitmask):  │
│         - logits processor 链                    │
│         - 应用结构化输出 bitmask                  │
│         - temperature/top_p/top_k 采样            │
│         - spec decode rejection sampling         │
│                                                  │
│     ⑤ Scheduler.update_from_output():            │
│         - append token 到 request                │
│         - 检测 EOS / max_tokens                  │
│         - 完成的 request 移出 batch              │
│         - 释放 KV Cache block                    │
│                                                  │
│   output_queue → output_thread → ZMQ PUSH        │
└────────────┬─────────────────────────────────────┘
             ▼
┌──────────────────────────────────────────────────┐
│ API 进程 (AsyncLLM)                               │
│   OutputProcessor:                               │
│     - detokenize (token → text), 检测 stop string │
│     - 流式 chunk 交给 generate 协程推给 client     │
│   HTTP 响应 (SSE 流式)                            │
└──────────────────────────────────────────────────┘
            |
            ▼
        客户端收到 token 流
```

> 🖼️ 占位:一条请求的时序图。回答「从 HTTP 进门到 SSE 出第一个 token,经过 API 进程、EngineCore 进程、worker 进程哪几只手,哪一跳是 ZMQ、哪一跳是 future」;②③ 的重叠要画成并行泳道。

这里有个容易看漏的设计:**执行与掩码计算是重叠的。** `execute_model(non_block=True)` 先把前向丢给 executor 拿一个 future,然后在等 GPU 的同一段时间里,CPU 侧去算结构化输出的 bitmask(`get_grammar_bitmask`),最后才 `future.result()` 并调 `sample_tokens(grammar_output)` 完成采样。所以「采样」在架构上是 executor 的一次独立调用,不是前向的尾巴。

两个进程各管一半的「结束」:EOS 和 max_tokens 由 EngineCore 里的调度器判;stop string 要先把 token 变回文字才能比对,所以在 API 进程的增量 detokenizer 里判。聊天模板同理:它在 API 进程里由 renderer 先套好,InputProcessor 拿到的已经是一段完整的 prompt。

PagedAttention(3.2)和连续批处理(3.1)是地基,没有它们,其他优化都无法动态调度。Chunked prefill(3.3)和 prefix caching(3.4)建立在 PagedAttention 之上,需要 block 化的 KV 才能精确控制 token budget 和共享前缀。推测解码(3.5)与 chunked prefill 共享同一个 `schedule()` 主循环,spec token 在预算里也算「未计算 token」。量化(3.8)和并行(3.7)发生在 model_executor 内部,对调度器透明。结构化输出(3.9)在 sampler 阶段插入 bitmask。确定性推理(3.15)横切前面全部环节,它要求每个 kernel 的归约顺序与 batch 组成无关。

> 🖼️ 占位:特性依赖图。回答「十五个特性谁建立在谁之上、谁对调度器透明、谁横切全部环节」。

## 七、关键配置对象(贯穿全框架)

`vllm/config/` 下有三十多个模块,每个对应一个配置域,最终由 `vllm/config/vllm.py` 的 `VllmConfig` 组装成一个总配置对象。深入任何特性前,先认识下面这几个,几乎所有调度、显存、模型开关都挂在这里:

- `vllm/config/scheduler.py` 的 `SchedulerConfig`:`max_num_seqs`(默认 128)、`max_num_batched_tokens`(默认 2048;batched DP 场景另有一个 256 的常量)、`enable_chunked_prefill`(默认开)、`long_prefill_token_threshold`(默认 0 表示不限)、`policy`(fcfs / priority)、`async_scheduling`(默认不指定,由引擎决议)、`watermark`、`max_model_len`(不是它自己的字段,由 ModelConfig 传入)。
- `vllm/config/cache.py` 的 `CacheConfig`:`block_size`(字段默认 None,回落 16)、`gpu_memory_utilization`(0.92)、`cache_dtype`(默认 auto,即 KV 与激活同精度)、`enable_prefix_caching`(开)、`prefix_caching_hash_algo`(sha256)、`kv_cache_memory_bytes`(设了就绕过 `gpu_memory_utilization`,直接指定 KV 显存字节数)。
- `vllm/config/model.py` 的 `ModelConfig`:模型路径、`dtype`、`max_model_len`、`quantization`、`generation_config`、tokenizer 相关。
- `vllm/config/parallel.py` 的 `ParallelConfig`:`tensor_parallel_size`、`pipeline_parallel_size`、`data_parallel_size`、`enable_expert_parallel`、`distributed_executor_backend`。
- `vllm/config/vllm.py` 的 `VllmConfig`:把上面所有 config 聚合,`__post_init__` 里有大量跨 config 的联合决议与覆写(按平台和显卡能力回退、按 O-level 填编译档位、KV connector 的默认与降级等)。**很多「默认值」实际是在这里决定的,不是在字段定义处。** 排查「为什么我没设这个参数它却不是文档写的默认值」时,先来这里看。

其余按需查阅:`speculative.py`(推测解码)、`lora.py`、`multimodal.py`、`structured_outputs.py`、`load.py`(权重加载)、`compilation.py`(torch.compile 与 CUDA Graph)、`kv_transfer.py`(PD 分离)、`offload.py`、`quantization.py`、`attention.py`、`mamba.py`、`pooler.py`、`observability.py`、`device.py` 等。

> 🖼️ 占位:配置对象的组装图。回答「CLI 参数怎么变成各域 config、再怎么被 VllmConfig 联合决议成生效值」。
