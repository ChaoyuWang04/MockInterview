# vLLM 框架总览

源码基准:官方仓库 <https://github.com/vllm-project/vllm>,分支 `main`,commit `08426d51ef`,核对日期 2026-09-10。全篇的「当前」「默认」都指这组基准,每条都在源码上核对过;竞品对比与经验数字标为「讲稿观点」。每节对应源码的哪个文件与方法,见代码索引页。

## 一、vLLM 是什么

**vLLM** 是 UC Berkeley 主导开源的大语言模型高吞吐、低延迟推理与服务框架。它要解决的根本矛盾是:GPU 显存有限、单卡算力有限、用户请求潮汐波动,却要把一个百亿到千亿参数的模型以 **高吞吐** (throughput,单位时间处理的 token 数)、**低延迟** (latency,单 token 生成时间)服务成百上千个并发请求。

与训练框架(Megatron-LM、DeepSpeed)相比,推理框架的优化对象完全不同:

| 维度 | 训练框架(Megatron / DeepSpeed) | 推理框架(vLLM) |
|---|---|---|
| 目标 | 一次前向 + 一次反向 + 一次优化器更新 | 只有前向,但要重复跑几百到几十万次(每生成一个 token 跑一次) |
| 批处理 | 静态 batch,整个训练过程不变 | 动态 batch:每 step 都可能增减请求(continuous batching,连续批处理) |
| 显存大头 | 激活值、优化器状态、梯度 | KV Cache(KV 缓存):历史 token 的 Key/Value 张量,随序列长度线性增长 |
| 核心指标 | TFLOPS 利用率、迭代时间 | 吞吐(tokens/s)、首 token 延迟(TTFT)、单 token 延迟(TPOT) |
| 并行维度 | TP/PP/DP/EP/SP/CP(多维) | TP/PP/EP/DP 为主,另有 SP 与 CP。推理没有反向,不需要为梯度和优化器状态切分;SP 以编译期 pass 的形式存在,CP 分 prefill 侧的 PCP 与 decode 侧的 DCP |

一句话定位:**vLLM 把「显存管理 + 动态调度 + 注意力 kernel + 分布式执行 + 采样」五件事做成了一套完整、高性能、易部署的推理服务栈。** 它和 SGLang、TensorRT-LLM、HuggingFace TGI 是当前主流的四个 LLM 推理引擎(讲稿观点)。

顶层入口(仓库根 `vllm/`):

- `vllm.LLM(...)`:离线批量推理(同步),最常用的 Python API。
- `vllm.AsyncLLMEngine` / v1 的 `AsyncLLM`:在线服务(异步流式),配合 OpenAI 兼容 HTTP server。前者只是别名,真身是 v1 的 `AsyncLLM`。
- `vllm serve <model>`:命令行启动 OpenAI 兼容 server,入口在 `vllm/entrypoints/`。

代码组织上,vLLM 只有一套实现,在 `vllm/v1/`:

- 调度器、引擎进程架构(ZMQ 多进程)、注意力后端注册机制、Worker 与 ModelRunner 全部在 `vllm/v1/` 下。
- 顶层不存在 `vllm/core/`、`vllm/worker/`、`vllm/attention/` 这三个目录。
- `vllm/engine/` 只剩 4 个模块文件(`arg_utils.py`、`async_llm_engine.py`、`llm_engine.py`、`protocol.py`),其中 `llm_engine.py` 全文只有一句别名 `LLMEngine = V1LLMEngine`。真正的引擎实现在 `vllm/v1/engine/llm_engine.py`。CLI 参数 `EngineArgs` 则实打实地住在 `vllm/engine/arg_utils.py`,不在 `v1/` 下,这是唯一需要注意的例外。

读代码时不必区分 V0/V1 路径,`vllm/v1/` 就是全部。从体量看,模型实现占了整个仓库近一半,真正的引擎骨架在 `v1/`,其中注意力后端和 worker 又是 `v1/` 里最大的两块。

## 二、六大核心创新:先建立全局图景

理解 vLLM 的关键,是先看清它把一次推理服务 **沿哪些维度优化** 。这些优化可以叠加,一个生产部署通常同时用其中 4 到 6 项:

```text
            客户端并发请求 (HTTP/gRPC, n=100~10000)
                        |
            ┌───────────┴───────────┐
            ▼                       ▼
    [1] 连续批处理            [2] PagedAttention
    (Continuous Batching)     (KV Cache 分块)
    每 step 动态增减请求       KV Cache 按 block 管理
    不等整批完成               显存利用率 → 接近 100%
            |                       |
            └───────────┬───────────┘
                        ▼
            [3] Chunked Prefill + Prefix Caching
            长 prompt 分块喂入;公共前缀 KV 复用
            prefill 与 decode 同 batch 调度
                        |
            ┌───────────┼───────────┐
            ▼           ▼           ▼
    [4] 推测解码    [5] 注意力后端   [6] 量化 / 分布式
    (Speculative    FlashAttn /     FP8 / AWQ / GPTQ
     Decoding)      FlashInfer /    TP / PP / EP / DP
    小模型猜多 token MLA / Mamba    多卡 / 多节点
    大模型并行验证
```

一句话记忆:

- **连续批处理**:动态调度,提高 GPU 利用率和吞吐。
- **PagedAttention**:KV Cache 按 block(块)分配,显存利用率接近 100%,零碎片。
- **Chunked Prefill**:长 prompt 切块,prefill(预填充)和 decode(解码)混排,避免 prefill 阻塞 decode。
- **Prefix Caching**:公共前缀复用,省重复计算(系统 prompt、few-shot)。
- **推测解码**:小模型或草稿猜,大模型一次验证多 token,降单 token 延迟。
- **量化 + 分布式**:低精度 + 多卡,进一步降显存、提吞吐。

## 三、十五个特性,各自解决什么

下表是 vLLM 的核心特性清单。**这里只回答「它存在是为了解决什么」**;展开讲解在各章,代码在哪见代码索引页。

| 特性 | 不这么做会怎样 | 做法一句话 | 详见 |
|---|---|---|---|
| 连续批处理 | 整批请求被里面最长的那条拖住,先算完的白占着位置,GPU 大量空转 | 每个 step 重新决策谁继续、谁结束、谁新进来 | 02 章 |
| PagedAttention | 按最大长度给每条请求预留整块连续显存,实际只用一点点,碎片吃掉一半以上显存 | 学操作系统分页:KV 切成定长块,用块表映射,按需分配、用完就还 | 03 章 |
| Chunked Prefill | 一条长 prompt 的 prefill 独占几百毫秒,所有 decode 请求跟着卡住,用户看到吐字卡顿 | 把长 prompt 切块,每步只算一块,和 decode 请求同批调度 | 02 章 |
| Prefix Caching | 系统提示词、few-shot 示例、长文档这些公共前缀,每条请求都要重算一遍 | 每块 KV 按内容做链式哈希,命中就直接复用 | 04 章 |
| 推测解码 | 每出一个 token 就要完整读一遍模型权重,而 decode 是访存瓶颈,算力几乎闲置 | 让草稿先猜 k 个,目标模型一次前向并行验完,把这遍读取摊给 k+1 个 token;用拒绝采样保证输出分布不变 | 08 章 |
| 注意力后端 | 不同硬件、不同注意力结构、不同精度各要一套 kernel,没有银弹 | 定义统一抽象层,上层模型不关心底下用哪个 kernel | 05 章 |
| 注意力机制本身 | decode 被 KV 读带宽卡死,算力利用率不到 1% | 各家分别去压 KV 头数、表示维度、参与计算的 token 数,或干脆换成固定大小的状态 | 05 章 Part 5 |
| 执行层与 CUDA Graph | decode 一步只算十几毫秒,CPU 却要下发两千次 kernel,GPU 一半时间在等派活 | 请求状态常驻 GPU 只改增量;把整轮 kernel 录成图,每步一次重放 | 06 章 |
| 模型并行 | 百亿千亿参数单卡放不下,单卡算力也追不上延迟要求 | TP / PP / EP / SP / CP / DP 六种切法各切一维,推理版比训练版精简 | 09 章 |
| 量化 | 半精度模型显存大、带宽吃紧 | 用更低精度存权重甚至算矩阵乘,三十种方案由一个类型定义收口 | 详见 11 章 |
| 结构化输出 | 模型自由生成再拿代码解析,随时可能吐出语法错误的内容 | 请求到达时把约束编译成一张图,之后每步查表得到一张位掩码,把语法上不可能的 token 压成负无穷 | 详见 12 章 |
| 多模态 | 图像、音频要变成能喂给语言模型的东西 | 占位符把媒体在 token 账本上占住位置,三级缓存让同一份媒体不被反复计算,编码器预算决定它和 decoder 谁先谁后 | 详见 13 章 |
| 引擎进程架构 | 单进程里 tokenize、前向、detokenize、HTTP 互相阻塞 | 拆成多进程,用 ZMQ 通信,让 CPU 活儿藏进 GPU 计算窗口 | 01 章 |
| PD 分离与 KV 传输 | prefill 吃算力、decode 吃带宽,挤一张卡上互相拖累;而拆开之后,那份原本不用动的 KV 必须整份搬过去 | 拆到不同节点,prefill 算完把 KV 传给 decode 节点;搬运交给一层 connector 抽象,十六个内置实现按推、拉、经中转三种方向各行其是 | 10 章 |
| LoRA | 每个微调版本起一份副本,显存乘 N 只是表象,真正致命的是 KV cache 被切碎;而把适配器合并进权重又与连续批处理从根上冲突 | 适配器按槽位堆成一张大张量,token 到槽位的索引每步重算,再把适配器维放进 kernel 的 grid,于是一次下发算完整批的多个适配器 | 详见 14 章 |
| 采样 | 永远取分数最高的那个,输出重复呆板;一放开随机性,低概率的胡话又会冒出来 | 一条定序的加工管线:先划掉不该选的、惩罚说过的、再调温度裁候选集,最后不排序不同步地抽一个 | 07 章 |
| 批不变性 | 同样的输入同样的种子,换个 batch 组成就可能吐出不同的文本 | 换成归约顺序只看张量形状、不看 batch 里有几条请求的 kernel | — |

**为什么会不一样**:浮点加法不满足结合律,而 GPU kernel 会按 batch 规模改变归约顺序。分数上 1e-8 量级的差异,足以在取最大值时翻转一个 token,后面整段就跑偏了。

「详见」列空着的,说明还没单独成章。
## 四、一条请求怎么把这些特性串起来

一条请求进来后依次落在三类进程手里:**API 进程**套聊天模板、切词、构造请求对象;**EngineCore 进程**的主循环做调度(这里用上连续批处理、chunked prefill、前缀缓存、PD 分离),再把这一批发给 worker;**GPU Worker 进程**跑前向与采样(这里用上注意力后端、量化、模型并行、推测解码、结构化输出的掩码)。结果沿原路回到 API 进程,detokenize 后流式吐给客户端。

decode 阶段就是把中间那两步循环几百次,每转一圈吐一个 token。

完整走读(每一跳落在哪个进程、哪个线程,四个阶段各发生几次)见 **01 章**。

## 五、与竞品的整体对比

| 维度 | vLLM | SGLang | TensorRT-LLM | HuggingFace TGI |
|---|---|---|---|---|
| 核心创新 | PagedAttention | RadixAttention | 自家 kernel | 连续批处理 |
| 引擎架构 | 多进程 + ZMQ | 多进程 + 多线程 | Python + Triton | Rust + Python |
| 支持模型数 | 380 余个架构名(注册表实测) | 未在本仓库验证 | 未在本仓库验证 | 未在本仓库验证 |
| MLA 支持 | 完整(含 sparse MLA) | 完整 | 完整 | 部分 |
| MoE(EP) | 完整 | 完整 | 完整 | 部分 |
| 推测解码 | EAGLE / MTP / n-gram / Medusa / Suffix | EAGLE | Medusa / SpecDec | 部分 |
| 量化 | 三十个方法名(FP8 / AWQ / GPTQ / compressed-tensors / mxfp4 / online 等;不含 bitsandbytes) | FP8 / AWQ / GPTQ | INT8 / FP8 / INT4 | bitsandbytes |
| 多模态 | 视觉 / 音频(仅输入侧) | 视觉 | 视觉(少) | 视觉 |
| 结构化输出 | xgrammar / guidance / outlines / lm-format-enforcer + `auto` 试探链 | xgrammar / outlines | 部分 | outlines |
| PD 分离 | 内置 connector 家族(NIXL / Mooncake / LMCache / MoRIIO 等) | 内置 | DistServe | 无 |
| 典型场景 | 通用、生产部署 | 推测解码、复杂控制流 | NVIDIA 优化极致 | HF 生态 |

vLLM 一列的每项都在本仓库源码上核对过(架构名来自注册表去重,量化方法名来自那个 `Literal`)。其余三列只做能力层面的定性判断,是讲稿观点:它们的模型数与量化方案数无法在本工作区核实,要横向比应直接查各家的 supported models 文档。

## 六、关键配置对象

`vllm/config/` 下三十多个模块各管一个配置域,最终由 `VllmConfig` 组装成一个总对象。深入任何特性前先认识这五个,几乎所有调度、显存、模型开关都挂在它们身上。

| 配置对象 | 管什么 | 关键字段(默认值) |
|---|---|---|
| `SchedulerConfig` | 一步算多少、并发多少 | `max_num_seqs`(128)、`max_num_batched_tokens`(2048)、`enable_chunked_prefill`(开)、`long_prefill_token_threshold`(0,不限)、`policy`(fcfs)、`async_scheduling`(不指定) |
| `CacheConfig` | KV cache 怎么分、占多少显存 | `block_size`(字段为空,回落 16)、`gpu_memory_utilization`(0.92)、`cache_dtype`(auto)、`enable_prefix_caching`(开)、`prefix_caching_hash_algo`(sha256)、`kv_cache_memory_bytes`(设了就绕过显存占比) |
| `ModelConfig` | 模型本身 | 模型路径、`dtype`、`max_model_len`、`quantization`、`generation_config`、tokenizer 相关 |
| `ParallelConfig` | 怎么切到多卡 | `tensor_parallel_size`、`pipeline_parallel_size`、`data_parallel_size`、`enable_expert_parallel`、`distributed_executor_backend` |
| `VllmConfig` | 把上面全部聚合 | 无独立字段,但 `__post_init__` 里有大量跨配置的联合决议与覆写 |

**最值得记住的一条**:`VllmConfig.__post_init__` 里会按平台与显卡能力回退、按优化档位填编译配置、给 KV connector 兜默认与降级——**很多「默认值」实际是在这里决定的,不在字段定义处**。排查「我没设这个参数,它怎么不是文档写的默认值」时,先来这里看。

其余按需查阅:LoRA、多模态、结构化输出、权重加载、编译与 CUDA Graph、PD 分离、显存下沉、量化、Mamba、池化、可观测性、设备等,每项一个模块,文件名见代码索引页。
