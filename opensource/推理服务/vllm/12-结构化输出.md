# vLLM 12|结构化输出

要模型吐出严格合法的 JSON,靠的不是生成完再校验,而是在每一步采样之前就把语法上不可能的 token 全部掐掉。这一章讲这套掐法怎么算出来、怎么存、怎么送到 GPU。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与方法,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 模型不保证吐得出能解析的东西

让模型返回 `{"ok": true}`,它很可能返回这个:

````text
好的,用户已通过审核,结果如下:
```json
{"ok": true
````

前面多了一句自然语言,中间多了代码块围栏,末尾少了一个右花括号。解析器直接抛异常。

朴素的应对是「生成完再校验,失败就重试」。它不是不能用,而是**成本结构很差**:

1. **失败是概率性的,而且不可控。** 一个三十字段的嵌套 schema,每个 token 都有出错机会,长输出下累积失败率很高。
2. **重试是整条请求重算。** 一次失败浪费掉的是完整的一轮预填充加解码,远贵于每步做一次检查。
3. **失败模式集中在结尾。** 少一个右括号、多一个逗号,往往要到最后几个 token 才暴露,此时全部算力已经付出。
4. **P99 延迟不可预期。** 重试几次说不准,SLA 无从保证。

更麻烦的是失败花样太多:前缀废话、代码块围栏、少括号、多逗号、把布尔写成字符串、多写一个字段……**每一种都要写一段清洗代码,而且清洗不完。**

于是这一章的整条线是这样的:

| 不这么做会出什么事 | 于是有了 |
|---|---|
| 模型可能吐出解析不了的东西,而事后校验是概率性失败、整条重算、且失败集中在结尾 | 把「事后校验」换成「事前禁止」:语法上不可能出现的 token,根本不给模型采样的机会 |
| 事前禁止要每一步问一遍「现在能出哪些 token」,而词表有十几万,逐个问吐吞吐 | 把判断从运行期挪到编译期:请求到达时把约束编译成一张图,运行期只查表 |
| 查表的结果每步都要跨进程搬到 worker,按一个 token 一个字节存,大 batch 一步就是几十 MB | 按位打包成整数,搬运量降到八分之一,代价是 GPU 上要解包 |

三条合起来就是 vLLM 的做法:**编译一次,之后每步查表得到一张位掩码,把非法位置的 logit 写成负无穷。** 剩下的事情交给采样管线,它看到的只是几个位置变成了负无穷,不需要知道为什么。

### 1.2 先把两个词定死:schema 与文法

**schema(格式说明书)不是数据本身,而是对数据「长什么样」的描述。** 数据库的建表语句是 schema,表里的行是数据;TypeScript 的接口是 schema,具体对象是数据;表单的校验规则是 schema,用户填的内容是数据。

JSON Schema 是描述 JSON 结构的业界标准,它本身也用 JSON 写。要紧的是它描述的是**一整类**字符串而不是某一个:一份要求「有个布尔字段 `ok` 且不可省略」的 schema,`{"ok":true}` 和 `{"ok":false}` 都符合它。

**文法(grammar)是「什么样的字符串算合法」的规则集合。** 类比自然语言:「主语加谓语加宾语」是一条语法规则,它没规定你说什么内容,只规定句子怎么搭。形式文法是同一件事,只是精确到机器可以逐字符照着检查。写文法最常用的记法是 EBNF,一条规则形如「boolean 定义为字面量 true 或者 false」。

两者的关系是:**schema 是给人写的声明,文法是给机器执行的规则。** 编译的第一步就是把 schema 翻成文法。正则和 EBNF 属于用户直接写文法,少了这一步转换。

本章里「schema」多数时候特指 JSON Schema;广义上正则、EBNF、枚举列表也都是「对输出形状的描述」,在 vLLM 里走同一套机制,统称**约束**。约束一共六种,它们互斥,一条请求只能挑一种。

### 1.3 代码里的 grammar 有三个意思

这个词在代码里同时指三样东西,混起来很容易读晕:

| 出现的地方 | 指的是 |
|---|---|
| 请求参数对象的 `grammar` 字段 | 用户传进来的 EBNF 字符串,是六种约束类型之一 |
| 运行时的文法对象 | 编译产物,每请求一个,持有「现在走到哪了」这个状态 |
| 正文里说的「文法」 | 广义的规则概念 |

后文凡是说「文法对象」,指的都是第二种。

顺带把命名也定死:约束解码在这套代码里统一叫 **structured outputs(结构化输出)**,命令行、引擎级配置字段、请求级参数三处用的是同一个词根。网上教程里常见的 `guided_decoding` 命名在引擎内部已经不存在,只在 OpenAI 兼容层残留一个不再驱动逻辑的入参,别拿它当开关用。

### 1.4 三条路线:差别不在要不要禁,而在什么时候判

先用一个生活化的类比。要让一个人填一张格式严格的表格:

- **路线 A** 等于让他随便写,写完你再检查,不合格就撕了重写。
- **路线 B** 等于他每写一个字,你翻一遍整本字典,逐个字问「这个字接在这儿合不合规」,然后告诉他能用哪些。
- **路线 C** 等于你事先在表格每个位置贴好路标(「这里只能填数字」「这里只能填是或否」),他照着路标写,一次成型。

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 后处理加重试 | 自由生成,解析失败就重试 | 零侵入,不改推理栈 | 成本与延迟不可控,见 1.1 |
| B. 运行时逐个判 | 每步用解析器判断合法 token 集合 | 实现简单 | 每步一次全词表判断,吞吐杀手 |
| C. 编译期文法加运行期位掩码 | 请求到达时编译成一台状态机,运行期查表得到位掩码 | 每步开销百微秒级,还能与前向重叠 | 需要编译期,需要缓存 |

**三条路线的差别不在「要不要禁非法 token」,而在「这个判断什么时候做」**:A 事后做(浪费已完成的计算),B 每步做(吞吐崩塌),C 提前做一次然后反复查表(几乎免费)。

### 1.5 运行期逐个问为什么吐不动

路线 B 的思路和 C 其实一模一样,都是把非法 token 的 logit 压到负无穷。问题只在于它把判断放在了运行时:每一步、每个请求,都要遍历整个词表,对每个候选 token 拼出「已生成前缀加上它」,再跑一次解析判断还能不能构成合法输出。

这笔账算得出来。以 Qwen 系列约 15 万的词表为例,**即使每次判断只要 100 纳秒**:

- 单请求单步:151936 次判断约等于 **15.2 毫秒**
- batch 为 256 时:约等于 **3.9 秒一步**

解码一步本来只要几十毫秒。功能是对的,吞吐没了。

**真正被浪费掉的是「前缀没变多少」这个事实。** 生成第 5 个 token 和第 5000 个 token 时,合法集合的变化都只取决于新增的那几个字节,而路线 B 每步都把整件事从头算一遍。路线 C 的全部价值就是把这件事预先算好、存成可查的表。

### 1.6 vLLM 选的是编译期那条

引擎侧发生的事情分两段,一段一次性、一段每步都做:

```text
请求到达时(一次性,可跨请求复用)
  schema  --编译-->  状态图, 外加每个状态允许哪些 token 的预计算结果

每个解码 step(每请求)
  查表     -->  一张位掩码
  GPU 上一次 kernel, 把非法位置的 logit 写成负无穷
```

编译那一步是几十毫秒量级,查表那一步是百微秒量级,写负无穷那一步是微秒量级。**量级差三到四个数量级,这就是路线 C 成立的全部理由。**

这之上还有两个工程决策,它们是「结构化输出几乎不掉吞吐」的原因:编译被放进线程池异步做,请求先进一个专门的等待状态,编译好了才允许被调度;位掩码在引擎进程的 CPU 上算,而这段时间 GPU 正在跑前向。后者不是本章发明的机制 —— 一个 step 内「前向」与「算掩码」两条路并行跑、在采样处合流,01 章 2.4 已经把这条分叉与合流讲透了,那里也解释了为什么算掩码既不看 logits 也不看 KV cache,因而能真正并行。请求的那个等待状态则是调度器三个阻塞态之一,机制见 02 章 2.1 与 2.6.4。

### 1.7 掩码怎么存:按位打包成整数

掩码本质上是「每个 token 一个布尔值」。最省的存法是一位一个,但 CPU 与 GPU 的最小可寻址整数单元是 32 位,于是打包进 int32 数组:

```text
word[0]     bit0..bit31    token 0..31
word[1]     bit0..bit31    token 32..63
word[2]     bit0..bit31    token 64..95
...
word[4747]  bit0..bit31    token 151904..151935
```

一个 int32 的第 k 位表示 `token_id = 32 * word_idx + k` 合不合法:1 是合法,0 是非法,非法位置的 logit 会被写成负无穷。所以整张掩码的形状是「掩码行数乘以词表大小除以 32 向上取整」,类型是 int32。

**为什么要向上取整**:词表大小不一定是 32 的倍数。词表为 100 时取 3 个 word 只覆盖到 token 95,剩下 4 个 token 无处安放,必须进到 4 个 word,最后一个 word 有 28 位浪费。代码里用整数运算写成「加 31 再整除 32」,两处实现写法不同但等价。

省下来多少,值得算清楚,因为这里有个很容易记反的地方。仍以 15 万词表为例:

| 存法 | 每请求每步 | 相对 |
|---|---|---|
| 逐个布尔值 | 151936 字节,约 148 KiB | 基准 |
| 按位打包 | 4748 个 int32 共 18992 字节,约 18.6 KiB | **八分之一** |

**省的是八倍,不是三十二倍。** 三十二是「一个 int32 装得下 32 个 token」这个打包密度,它本身没错;但拿来比的那份布尔张量,一个布尔值本来就只占一个字节、也就是八位,所以位打包相对它只赚了八倍。把打包密度直接当成节省倍数,是这一段最常见的读错。

八倍仍然很关键,因为这张掩码要**跨进程序列化**再拷到 GPU。batch 为 256 时,逐布尔版一步要搬约 38 MB,打包版约 4.9 MB。

代价是 GPU 上要解包,这就是位运算 kernel 干的事:把每个 int32 右移 0 到 31 位再取最低位,还原成 32 个布尔值。**这里有一处容易读错**:kernel 里那个还原出来的布尔量,语义和位是**相反**的 —— 位 1 表示合法,而这个布尔量为真表示「该写负无穷」,因为它在取位之后还做了一次等于零的比较。位运算在 GPU 上极便宜,用它换带宽是稳赚的。

被写成负无穷的这些位置,之后就交给采样管线了。它们对后续步骤不是完全透明的:07 章 3.2 讲免排序裁剪时,统计分位点要显式把负无穷排除在外,源码注释点名的正是这条语法位掩码。

### 1.8 没填的那些行天然是放行的

掩码张量的初值填的是 −1。int32 的 −1 补码是全 1,也就是**所有 token 都合法**、等价于不约束。

这个选择不是随手挑的。一批里既有要约束的请求也有不约束的,还有已经写完、文法已终止的请求。管理器持有一个「全放行」的常量,在文法已终止或这一步本就不该约束时,拿它把整行覆盖掉。于是**没被填过的行天然是放行的,不会误杀 token**,填与不填共用同一条写路径,不需要另外维护一张「哪些行有效」的名单。

### 1.9 一个贯穿全篇的例子

后面几节都用这一个例子,先把设定摆出来。

**约束**是一份最小的 JSON Schema:输出必须是一个对象,含一个名为 `ok` 的字段且不可省略,其值必须是布尔类型。

**期望输出**是形如 `{"ok":true}` 的一行 JSON。注意 `ok` 是字段名、由 schema 钉死,`true` 与 `false` 才是模型真正的回答内容 —— **schema 只锁结构,不锁值**,两者都合法。

**提示词**是「用户是否通过审核?请回答。」模型在无约束时极可能回一句自然语言,比如「用户已通过审核」。

**词表**真实约 15 万,这里只列与本例相关的几个,id 是虚构的,但「多字符 token 跨语法边界」这一点完全真实:

| token id | token 文本 | 说明 |
|---|---|---|
| 0 | `<eos>` | 结束符 |
| 1 | `{` | 单独的左花括号 |
| 2 | `{"` | 合并 token:花括号加引号 |
| 3 | `"` | 引号 |
| 5 | `ok` | |
| 6 | `ok"` | 合并 token:key 名加收尾引号 |
| 7 | `":` | 合并 token:引号加冒号 |
| 10 | `true` | |
| 11 | `false` | |
| 12 | `}` | |
| 14 | 空格 | |
| 15 至 17 | `是` / `用户` / `已通过` | 自然语言 token |

本例涉及的 token id 都小于 32,所以整张掩码里**只有第 0 个 word 会变化**,其余 4747 个 word 全为 0,也就是那 15 万个 token 全部禁止。

### 1.10 把生成过程想成走一张地图

编译产物可以当成一张地图来读:

- **地图**就是编译产物。图上每个**路口**代表合法输出里的一个位置,每条**路**上标着一个字符。
- **状态**是你现在站在哪个路口。要紧的是状态**不记录你走过的路**,只记录你现在在哪。
- **推进**是顺着某条路走到下一个路口。
- **允许的 token**是站在当前路口时哪些路是通的。
- **走不动**是你想走的那个方向没有路。

整张地图上「能走通到终点」的所有路径集合,就是这份 schema 允许的所有合法输出。**约束解码做的事,就是每一步只让模型在有路可走的方向里选。**

严格说,JSON 的地图还要配一个栈来记「进了几层括号」,那种带栈的机器叫下推自动机;代码和社区习惯统称有限状态机,本章沿用。

本例编译出的地图(省略允许空白的自环):

```text
S0    起点,期待左花括号
 v    读 {
S1    期待 key 的开引号
 v    读 "
S2.0  key 里已匹配 0 个字符
 v    读 o
S2.1  key 里已匹配 1 个字符
 v    读 k
S2.2  key 里已匹配 2 个字符
 v    读 "
S3    key 写完,期待冒号
 v    读 :
S4    岔路口,模型在这里才真的有得选
 |
 +--> S5.0 -> S5.1 -> S5.2         读 t, r, u, e
 |
 +--> S5'.0 -> S5'.1 -> S5'.3      读 f, a, l, s, e
 |
 v
S6    值写完,期待右花括号
 v    读 }
S7    终点
```

这张图解释了第一步为什么只剩三个候选。站在 S0,词表里能走通的 token 只有左花括号、合并 token `{"`、以及前导空格三个 —— JSON 默认允许前导空白,所以空格那条自环也通。模型原本最想输出的「用户」「是」「已通过」全被压成负无穷:

| token | 原始 logit | 掩码位 | 应用后 |
|---|---|---|---|
| `用户` | 9.4 | 0 | 负无穷 |
| `是` | 8.7 | 0 | 负无穷 |
| `已通过` | 7.1 | 0 | 负无穷 |
| `{"` | 1.2 | 1 | 1.2 |
| `{` | 0.9 | 1 | 0.9 |
| 空格 | −0.3 | 1 | −0.3 |

这一步就是整个机制的价值所在:无约束时模型会开口说人话,加了掩码之后它只能开始写 JSON。**注意掩码不改变合法 token 之间的相对概率** —— 1.2 比 0.9 比 −0.3 的关系保持不变,所以模型仍然在「自己的偏好里」选,只是选择空间被裁剪了。

这也正是 07 章 1.5 说的那件事的另一面:白名单机制的最大用户不是手写清单的人,而是结构化输出。

### 1.11 一个 token 往往走好几步

地图上的路是按**字符**标的,而模型一次吐一个 **token**,一个 token 可能是好几个字符。所以采样一个 token 等于连续走好几段路。

接着上面,假设这一步采出 token 2 也就是 `{"`,它有两个字节:读入左花括号,沿 S0 到 S1 那条边走,同时栈上压一层「未闭合的对象」;再读入引号,沿 S1 到 S2.0 走。**一个 token,走了两步。**

于是「当前允许哪些 token」的真正判据是:把这个 token 的**全部字节依次喂进去,中途每一步都得有路**。只要有一个字节卡住,这个 token 就非法。

这就是「token 级状态机」与「字符级文法」的落差所在 —— 文法的边是按字节画的,模型的步伐是按 token 走的,中间这层换算正是编译期要预先算好的东西。

### 1.12 状态存在哪里:每请求一个文法对象

每个用了结构化输出的请求持有一个**文法对象**,它就是「你站在哪个路口」这件事的宿主。抽象接口规定了六件事,前四件正好对应地图上的四个动作:

| 方法 | 地图上的动作 |
|---|---|
| 推进 `accept_tokens` | 拿真正采样出来的 token 沿路走过去 |
| 校验 `validate_tokens` | 试着走一遍看能走多远,但**不推进** |
| 回退 `rollback` | 退回上几个路口 |
| 填掩码 `fill_bitmask` | 看当前路口哪些方向是通的,抄进掩码的某一行 |
| 判终止 `is_terminated` | 是否已经走到终点 |
| 复位 `reset` | 把状态清回起点 |

推进发生在采样结果回到调度器之后,用**真实采样出的 token** 去走。要留意它和「校验」的分工:校验只回答「这串 token 能被接受多少个」而不改状态,它服务的是一次给出多个候选 token 的场景。

**校验的实现方式很值得看一眼:它不是另写一套只读判断,而是真的走一遍再退回来** —— 逐个 token 往前试、记下被接受的前缀,然后按接受的个数回退同样多步。所以回退不只是「出错时的补救」,它还是「不推进的校验」能成立的基础,这也是它必须进抽象接口的原因。

不同 backend 在这个接口上的实现风格差别不小。以推进为例,主流实现除了逐个喂 token,还多做三件事:开头先看文法是否已终止,终止了就**直接忽略后续 token 并返回成功**;中途被拒绝时会打一条 error 日志而不是静默返回;每接受一个 token 就重新判一次是否已到终点,到了就立刻跳出。

### 1.13 状态不随生成长度变大

一个自然的担心:状态会不会越生成越大?

**不会。** 状态只有「当前在哪个路口」加上 JSON 的栈深,它跟已经生成了多少 token 无关。生成第 5 个 token 和第 5000 个 token 时,推进一步的成本是一样的,都正比于**新增的字节数**。

那为什么不干脆「存下已生成的文本,每次重新解析一遍」?可以,而且确实有 backend 就是这么做的 —— lm-format-enforcer 不维护「当前位置」,它保存完整的 token 前缀,每次从头重放一遍。功能等价,但每步成本从「正比于新增字节」变成「正比于已生成长度」,越写越慢。

主流 backend 不这么干有两个理由:一是每步重放本身就是 O(n);二是重放走的是「字符串到解析器」的慢路径,而走图是查表。**地图这个抽象的全部意义,就是把「这段文本合法吗」这种整体判断,换成「从这个路口能不能走这条路」这种局部查询。**

### 1.14 走不动会怎样:直接终止,不静默继续

正常情况下**不该发生**。掩码已经把没路的方向全禁掉了,模型采不出非法 token。

真发生了就说明有 bug,比如推理内容被误喂给了文法。代码的处理是**直接终止这条请求并记一条 error 日志**,而不是静默继续:请求状态置为出错,`stopped` 置真。

还有一处容易忽略的收尾:终止的同时会把这条请求的**可恢复标记显式关掉**。02 章 3.2 讲过「判出停止不等于请求结束,还要再问一句这条请求可不可恢复」—— 流式会话就是可恢复的,它停的是这一轮而不是整条请求。文法被违反属于真出错,所以这条路必须把那个口子明确关上,否则这条坏请求会被当成「本轮结束」重新入队。

### 1.15 走一遍:六步写完一个对象

接着 1.10 的第一步,把 `{"ok":true}` 整条走完。每一步都是同一个动作:看当前路口哪些方向通,模型在通的方向里选一个,走过去。

| 步 | 采样出的 token | 状态转移 | 累积输出 | 掩码第 0 个 word | 合法 token 数 |
|---|---|---|---|---|---|
| 1 | `{"` | S0 到 S2.0 | `{"` | 0x00004006 | 3 |
| 2 | `ok"` | S2.0 到 S3 | `{"ok"` | 0x00000070 | 3 |
| 3 | `:` | S3 到 S4 | `{"ok":` | 0x00000100 | 1 |
| 4 | `true` | S4 到 S6 | `{"ok":true` | 0x00000E00 | 3 |
| 5 | `}` | S6 到 S7 | `{"ok":true}` | 0x00001000 | 1 |
| 6 | `<eos>` | 已终止 | `{"ok":true}` | 全 1 | 151936 |

每个掩码值都是「允许的 token id 各自取一位」加起来:第 2 步允许 `o`、`ok`、`ok"` 三个(id 4、5、6),于是第 0 个 word 是 2⁴ 加 2⁵ 加 2⁶ 等于 112,写成十六进制正是 0x70。

**五步生成完毕,全程零次重试,输出必定可解析。** 对照无约束那条路:模型先写一句「用户已通过审核,JSON 如下:」,再写 JSON,可能还带代码块围栏,要写清洗代码剥离,而且有概率格式出错。

有两步值得单独看。

**第 2 步同时有三个合法候选,说明约束解码不强制最长匹配。** 模型可以一个字符一个字符地写 key(先 `o` 再 `k` 再 `"`),也可以一口气写完(`ok"`)。走哪条路由模型自己的概率分布决定,掩码只负责保证**每条路都通向合法输出**。实践中长 token 概率通常更高,所以一般一步写完。

**第 2 步禁掉单独的引号这件事,比「保证是合法 JSON」更强。** 单看 JSON 语法,`{""` 是合法前缀(一个空字符串 key);但 schema 声明了 `ok` 必填且没有别的属性,所以空 key 走不通。**约束来自 schema 而不仅仅是 JSON 语法** —— 这正是结构化输出比「保证输出是合法 JSON」更值钱的地方。

### 1.16 同一个语法位置,能出哪些 token 取决于之前怎么切

第 3 步只剩一个合法 token,而且这件事很能说明问题。

词表里 `":` 和 `:` 两个 token 在**字符层面都包含冒号**,但第 2 步采的是 `ok"`,收尾引号已经被消耗掉了,所以这一步只有裸冒号合法。**如果第 2 步采的是 `ok`(不带引号),这一步就反过来** —— `":` 和 `"` 合法,而裸冒号不合法。

同一个语法位置,允许的 token 集合**完全取决于之前的 token 切分路径**。这是 1.11 那个「一个 token 走好几步」的直接后果:状态机走到哪里由字节决定,而字节由 token 切分决定。

也正因如此,合法集合没法按「语法位置」预先列一张表了事 —— 它是「状态」的函数,而状态比语法位置细得多。

### 1.17 类型错误在这个机制下不可能发生

第 4 步的合法集合是 `t`、`true`、`false` 三个,因为 schema 说 `ok` 是布尔,从这个路口出发只有两条分支。

把 schema 改成整数类型,这一步允许的就变成负号和数字开头的 token,`true` 会被禁掉。**类型错误在这个机制下不可能发生** —— 不是「事后检查发现类型不对」,而是错类型的 token 根本没有出现的机会。

第 5 步同理:`required` 已满足、schema 没有别的属性,所以只剩右花括号。假如 schema 还有第二个可选属性,这一步就是右花括号和逗号**两个都合法** —— 要不要继续写字段交给模型自己决定。**约束解码只禁止非法,不强迫选择。**

### 1.18 文法终止之后必须放手

第 5 步把栈弹空、走到终点,文法终止。下一步填掩码时走的是另一条分支:**整行覆盖成全 1,完全不约束**(就是 1.8 讲的那个常量)。

于是模型可以自由输出结束符收尾,或者被最大长度、停止条件截断。

**这一步不是可有可无的收尾,是必须的** —— 不放手的话,模型连结束符都发不出来,请求会一直写下去直到撞上长度上限。

### 1.19 「推进」在代码里有两处,只有一处是真的

到这里「推进」这个词已经用了很多次,但它在代码里发生在两个完全不同的场合,混起来会读错:

| 场合 | 动作 | 是不是真的 |
|---|---|---|
| 拿到真实采样结果之后 | 推进 | 真实,永久生效 |
| 算掩码时,为了给后面几个位置也算出掩码,先假设草稿被接受 | 推进之后立刻回退 | 投机,算完就撤销 |

第二种只在一次采好几个 token 的场景下出现,前面走查的六步全是第一种。

第二处的实现比「推进完再撤销」讲究一点,有两个细节容易漏。

**一是回退的量是「成功推进了几次」,不是笼统撤销。** 代码一路数着成功次数,最后按这个数回退同样多步。

**二是这里有两条接受路径,对失败的容忍度不同。** 一般情况下直接推进,**被拒绝就是断言失败**,因为掩码已经保证了合法性,拒绝意味着有 bug。但推理段刚在这个窗口里结束时,走的是另一条:先用「不推进的校验」试一下,通过了才真推进,而且**容忍拒绝**。注释写明了理由 —— 那些草稿产生在这次掩码之前,本来就不保证合法。

这正是 1.12 说的那件事的第二个用武之地:回退不只是出错时的补救,它是「先假设、再撤销」这套算法能成立的基础。

### 1.20 为什么必须编译:五个问题一次说清

前面每一步都轻描淡写地说「当前允许的集合是某某」。这个集合是怎么来的,为什么不能在运行时现算?

| 问题 | 答案 |
|---|---|
| 编译发生在什么时候 | 请求刚进引擎时,一次。注释写明它只在输入处理线程里调 |
| 每个解码步都要编译吗 | 完全不需要。解码循环里只有查表和写掩码,没有任何编译动作 |
| 编译要多久 | 首次几毫秒到几百毫秒,看 schema 复杂度;命中缓存约等于零 |
| 谁来承担这个耗时 | 独立线程池,不占解码循环。请求在等文法的那个阻塞态里待着,编译好了才允许被调度 |
| 产物长什么样 | 一个只读的「状态图加每个状态允许哪些 token」的结构。运行时每请求配一个轻量游标在上面走 |

### 1.21 编译不在每步的开销里

「编译在不在每 token 延迟里」这个问题特别值得强调,它是这一章最容易误解的地方。把时间轴摊开:

```text
请求刚到达(一次性)
 |
 +-- 丢给线程池编译                          编译只在这里
 |   请求处在等文法的阻塞态
 |   此时它还没进 batch,不影响任何人的每 token 延迟
 |
 +-- 编译完成,请求转为可调度

进入解码循环(每 token,重复几百次)
 |
 +-- 填掩码(查表,百微秒)     前向     采样     推进(走图,微秒)
 |
 +-- 填掩码                    前向     采样     推进
 |
 +-- ... 重复
     全程没有编译
     而且填掩码这段 CPU 工作与 GPU 前向并行,基本被完全掩盖
```

一个类比:编译像开工前印刷施工图纸,一次,慢;解码每一步像工人瞄一眼图纸,每次都做,但极快。**图纸不会每砌一块砖就重印一遍。**

**极端情况下编译会不会影响每 token 延迟?间接地会。** 编译线程池占 CPU,大小是 CPU 核数的一半左右;同时涌入大量**不同 schema** 的新请求时,CPU 争抢可能拖慢调度线程。但这是资源竞争,不是「解码里插了编译步骤」。生产环境 schema 通常是少数固定模板,命中缓存后连这点争抢也没有。

源码注释还解释了为什么线程池要压到一半 CPU:线程池默认大小是 CPU 数乘五,那是给 IO 密集型任务定的,而文法编译是 CPU 密集型,开那么多只会互相抢。

### 1.22 编译为什么便宜:路口有限,路径无限

先把一件事摆正:运行时逐个 token 试算贵在哪,1.5 已经算过账了 —— 每步遍历十几万个 token,一步十几毫秒,batch 满载时几秒一步。而模型采的是 token、文法认的是字符这个落差,1.11 也讲过。

那么问题来了:**编译不也要遍历十五万个 token 吗,为什么它就便宜了?**

这是最该问的问题。编译并没有让「遍历十五万个 token」这件事变快,**它是让这件事的次数从「跟流量成正比」变成「跟 schema 复杂度成正比」**。

关键在于**路口的数量是有限的,而走过路口的次数是无限的**:

| | 运行时逐 token 试算 | 编译 |
|---|---|---|
| 遍历词表的时机 | 每请求乘每步 | 每个状态一次 |
| 成本随什么增长 | 流量,也就是并发乘输出长度 | schema 复杂度 |
| 落在关键路径上吗 | 是,每步都卡解码 | 否,异步线程池,请求在阻塞态等 |
| 能否跨请求复用 | 不能 | 能,同 schema 同词表的请求共享 |
| 每步实际做的事 | 十几万次字节推进 | 查表加拷贝十几 KB |

代入数字:256 个请求各写 200 个 token,运行时方案要做约 78 亿次字节推进;而本例的状态图只有二十来个状态,编译方案约 300 万次,**差了两千五百多倍**,而且这一次是离线的。

为什么状态数这么少?因为**不同的输出会反复经过同一批路口**。第一个请求生成 `{"ok":true}` 经过 S0 到 S7,第二个请求生成 `{"ok":false}` 经过的还是这批路口,只在那个岔路口选了另一条;第一千个请求还是这批路口。

**合法输出的数量可以是无限的**(schema 里有个字符串字段就无限了),**但路口数量是固定的**,只由 schema 的复杂度决定,跟输出多长、来多少请求都无关。所以「给每个路口做一次路标」这笔钱花得起,「每走一步现场勘测一次」花不起。

> 编译不是「提前把所有合法输出列出来」,那是列不完的;编译是「提前把每个路口的路标做好」。

### 1.23 编译的输入是一对:规范加词表

编译入口看起来只吃一个 schema 字符串,外加一组可选的停止符。但**最关键的第二个输入藏在 backend 实例里** —— 分词器和词表大小是 backend 的构造字段。

所以编译真正的输入是一对:**(schema 或正则或 EBNF 规范,分词器词表)**,输出是一个运行时文法对象。

这解释了缓存的粒度:缓存键必须同时含这两样。outlines 那条路把它写得很直白,缓存键就是「词表哈希加正则串」拼出来的。换个模型就得重编译,哪怕 schema 一个字没改。

### 1.24 产物分两半:贵的跨请求共享,便宜的每请求新建

这个划分是理解全流程的关键。返回的文法对象内部是两半:

| 成员 | 是什么 | 生命周期 | 能否共享 |
|---|---|---|---|
| 编译产物 | 文法乘词表的预计算结果,只读 | 由编译器的缓存持有,跨请求存活 | 能,同 schema 同词表的请求共享 |
| 运行游标 | 指向产物里某个状态的游标,加上栈和回滚历史 | 每请求一个,请求结束即弃 | 不能,每请求独立 |

outlines 是完全一样的划分:索引是编译产物进缓存,导引对象是每请求的状态游标。

**「编译一次,服务所有请求」就是靠这个划分实现的**:贵的部分跨请求复用,便宜的部分只是几个指针,每请求新建。

顺带一提,创建游标时会把**最大回滚步数**设成推测解码的草稿长度 —— 1.19 那个「先假设再撤销」的算法,它能回退多少步在这里就定死了。

### 1.25 阶段一:把验收标准翻成施工图

编译整体是一个入口加三个阶段。第一阶段解决的是一个视角问题。

JSON Schema 是一张**验收标准**:「结果必须是个对象,必须有 `ok` 字段,它的值必须是布尔。」但生成是一个 token 一个 token 往外吐的,每一步要回答的是完全不同的问题:「我已经写了 `{"ok`,下一个字符允许写什么?」

**验收标准回答不了这个问题。** 所以要把它翻译成一张施工流程图,图上每个位置都明确写着从这里往下能走哪些字符。

第一小步是 schema 翻成 EBNF 规则。本例的 schema 翻出来是三条:

```text
root    ::= "{" ws "\"ok\"" ws ":" ws boolean ws "}"
boolean ::= "true" | "false"
ws      ::= "" | " " | "\n" | "\t" | ...
```

第一行就是全部答案:合法输出等于左花括号、可选空白、字面量 `"ok"`、可选空白、冒号、可选空白、一个布尔值、可选空白、右花括号,按这个顺序拼起来。schema 的三条语义正好各自落进规则里:

| schema 里的写法 | 落到规则的形式 |
|---|---|
| `ok` 必填 | 字面量直接写死在序列里,绕不过去 |
| 值是布尔 | 单独一条规则,只有两个字面量 |
| 只有 `ok` 一个属性 | 序列里没有逗号分支,写不出第二个字段 |

**这一步之后,运行时再也不需要「理解」schema 了** —— 所有语义都变成了规则里的字面量和分支。

第二小步是规则变成状态图,做法很机械:**把规则右边的内容按字符摊平,在每两个字符之间放一个状态**。状态的含义就是「我已经写到规则的哪个位置了」。

| 状态 | 已经写到哪了 | 允许读入 | 读完到哪 |
|---|---|---|---|
| S0 | 什么都没写 | 左花括号 | S1 |
| S1 | 写完左花括号 | 引号 | S2.0 |
| S2.0 | 字面量写了 0 个字符 | `o` | S2.1 |
| S2.1 | 写了 `o` | `k` | S2.2 |
| S2.2 | 写了 `ok` | 引号 | S3 |
| S3 | key 部分完成 | 冒号 | S4 |
| S4 | 等布尔值的第一个字符 | `t` 或 `f`,这是岔路 | S5.0 或另一支 |
| S5.0 到 S5.2 | `true` 写了 1 到 3 个字符 | `r` / `u` / `e` | 下一个 |
| S6 | 值写完了 | 右花括号 | S7 |
| S7 | 全部写完 | 终止态 | — |

这张表就是 1.10 那张地图的文字版。三条构造规律:**多字符的字面量摊成一串状态**,每字符一步;**分支变成一个状态两条出边**;**可选项变成自环**,读入空白而状态不变。

为什么非要拆到这么细?因为要回答的问题是「下一个字符能写什么」。摊平成一个字符一个状态之后,这个问题就退化成「看当前状态那一行的第三列」—— 查表,常数时间。**这就是状态图相对于规则文本的全部价值,也是相对于验收标准式 schema 的全部价值。**

### 1.26 嵌套要栈,于是正则那条路天然做不到

上面的例子是一条直线加几个岔路,有限个状态够用。换成嵌套 schema 就不行了 —— 一条规则可以引用别的规则,而被引用的那条又能引回自己,这就是递归。

生成三层嵌套对象时,读到第三个左花括号意味着**同一条规则被嵌套进入了三次**。每次进入都要记住一件事:「这一层的右花括号读完之后,手指该回到哪里继续。」**这跟函数调用栈是一回事** —— 递归调用要靠栈保存返回地址。于是左花括号压栈、右花括号弹栈,栈空就是整个输出完成,也就是 1.18 说的那个终止条件。

**纯状态图做不到这件事**:它只有有限个状态,而嵌套深度没有上限,记不住「当前欠了几个右花括号」。加了栈的状态机才够用,那种机器叫下推自动机。

这一条直接解释了不同 backend 的能力差距。**outlines 把一切转成正则**,而正则只有状态图没有栈,所以它无法表达递归 schema,也不支持 EBNF —— **不是实现偷懒,是理论表达力的差距**。它的编译入口只认三种约束类型,其余直接抛错。

同一条也解释了另一件事:为什么状态图能全量预表而下推自动机不能。状态图的状态数有限,可以提前把每个状态的掩码都算好存起来;下推自动机的「状态」要连栈内容一起算,递归 schema 下是无限的,只能预计算能预计算的那部分,剩下的运行时按当前栈解算并缓存。

### 1.27 阶段二:把词表翻成字节

这一步一句话说清:**把词表里十几万个 token 逐个翻译成「它到底代表哪几个字节」**,好让下一阶段能拿它们去地图上试走。

为什么需要这一步?阶段一造出的地图,路上标的是**字节**;而分词器的词表存的是**字符串形式的 token**,两者对不上。更麻烦的是词表的字符串格式脏得超乎想象 —— 同一个空格,不同分词器能有三四种写法:有的直接就是空格,有的用一个特殊下划线代表前导空格,有的用十六进制转义写成尖括号形式,还有的把字节映射到可打印字符、于是空格变成了一个看起来完全无关的符号。

不做规范化的话,地图上「读一个空格」这条路,就会因为词表写法不同而认不出对应的 token。

vLLM 自己实现了这一步,那段代码很能说明脏活具体脏在哪:普通 token 直接按 UTF-8 编码;带特殊下划线前缀的要补回丢掉的前导空格;十六进制转义的空格在同一段补丁里显式判等;表示残缺 UTF-8 的 token 要先认出「解码出替换字符」这个特征,再取十六进制转成单字节;把字节映射到可打印字符的那种,要用反查表逐字符还原。特殊 token 整个跳过。

产物类型值得注意:它是**字节串到 id 列表**的映射,而不是到单个 id。因为不同的 token id 可能解码出同一个字节串,它们在状态机看来完全一样,必须合并处理。

**结束符不进这张映射表** —— 但它没有被丢掉,而是作为**单独的参数**交给词表对象。这两件事要一起记,只记前半句会以为结束符失踪了。

xgrammar 那条路把同样的活交给它自己的库做。只有 Mistral 因为格式特殊,vLLM 手工构造词表信息并显式指定词表类型,告诉 xgrammar 该怎么解释这些字节;同一个原因让另一个 backend 干脆不支持 Mistral。顺带一提,Mistral 这条路取词表大小用的是词表长度而不是分词器自报的那个数,注释说后者会把所有解码错误坍缩成一个 token。

### 1.28 阶段三:文法乘词表,这才是真正的编译

这一步一句话说清:**拿阶段二的字节化词表,去阶段一的地图上每个路口都试走一遍,把「这个路口能走哪些 token」记下来。**

为什么这才叫真正的编译:前两阶段只是把两边的原料准备好,一边是地图、一边是字典,它们各自都还回答不了「下一个 token 能是什么」。这一步把两者对撞,产出的才是运行时真正要用的东西。

以状态 S2.0 为例,编译期做的正是 1.15 那张表第 2 行的来源:拿 `o` 去试,走得通,记下转移;拿 `ok` 去试,连走两步走得通,记下;拿 `ok"` 去试,连走三步到 S3,记下;拿单独的引号去试,死路;拿一个中文 token 去试,第一个字节就死路。十五万个 token 全部试完,产物是这个状态的允许集合(也就是那个 0x70)加上一张「从这个状态、吃这个 token、到哪个状态」的转移表。

成本因此是「词表大小乘以平均 token 字节数」再乘以状态数。这就是编译要花几毫秒到几百毫秒的原因,也是「schema 越复杂编译越慢」的原因。

还有一层收益值得一提:编译期可以利用**词表里大量 token 共享前缀**这一点来摊薄成本 —— `o`、`ok`、`ok"` 走的前几个字节是同一段路,中间结果可以复用;而运行时逐 token 试算是每个 token 从当前状态重新起跑,没法共享。这类优化发生在 backend 库的原生扩展内部,本仓库只通过 Python 接口调用它们,看不到实现。

### 1.29 三个阶段的复用粒度不一样

三个阶段的耗时与复用粒度并不一致,这决定了「换个 schema 要重编译什么」:

| 阶段 | 做什么 | 耗时量级 | 复用粒度 |
|---|---|---|---|
| 一 | schema 到文法到状态图 | 亚毫秒到数毫秒,只跟 schema 大小有关 | 随编译产物一起缓存 |
| 二 | 词表字节化 | 数十到数百毫秒 | **整个进程只做一次**,挂在分词器上 |
| 三 | 状态乘词表试走 | 主要开销,几毫秒到几百毫秒 | 随 schema 与词表这一对缓存 |

**阶段二的复用粒度最粗**:它只跟分词器有关、跟 schema 无关,所以整个进程生命周期内只做一次,不同 schema 的请求都共用。两个 backend 都把它放在自己的初始化钩子里建一次,outlines 那条更直白 —— 结果直接挂在分词器对象上,下次来先看有没有。

所以「换个 schema 要重新编译」实际重跑的是阶段一和三,**不含最重的词表字节化**。

以上都是量级参考,不是本仓库实测。

### 1.30 两个请求走一遍,看缓存在哪里生效

把编译和运行串起来,用两个请求对照着看:

```text
请求 1 到达, schema 首次出现
 |
 +-- 丢进线程池编译
 |     阶段一, 阶段二, 阶段三                   约 50 ms
 |     新建一个游标, 指向起点                   微秒级
 +-- 期间请求停在等文法的阻塞态
 +-- 编译完成, 转为可调度

每个解码步
 |
 +-- 填掩码  = 问游标「你现在在哪, 允许哪些」, 抄一行     约百微秒
 +-- 推进    = 让游标沿转移表走到下一个路口              微秒级

请求 2 到达, 同一个 schema
 |
 +-- 编译入口内部命中缓存
 |     直接拿到同一份编译产物, 不重跑三个阶段            约 0
 +-- 新建一个游标, 一个新的独立位置                     微秒级
```

**两个请求共享编译产物、各自持有游标**,所以它们的生成内容互不干扰,但都不必重复付编译成本。这就是 1.24 那个划分在时间轴上的样子。

### 1.31 产物以什么形态存在:三个容易误会的点

| 疑问 | 实际情况 |
|---|---|
| 是不是生成了一个文件 | 不是。产物是常驻内存的只读结构,活在 backend 库的原生堆上,Python 侧只持有一个句柄。**唯一会落盘的是 outlines 的磁盘缓存**,那是为了重启后免于重编译 |
| 会不会传给 worker 进程 | 不会。文法对象只存在于引擎进程。**跨进程传输的只有每步生成的那张掩码**,而且交出去之前会先转成 numpy 数组,源码注释写明理由就是序列化效率 |
| 用户能拿到吗 | 不能,也不需要。用户只传约束本身,其余全在引擎内部 |

一句话概括形态:**引擎进程里一份只读的「路标大全」**(每 schema 一份,可共享),**加上每个请求一个几十字节的游标**(记录「我在哪个路口」),每步从路标里抄一行掩码发给 GPU。

### 1.32 成本摊销:第一个请求和第一千个请求

设编译一次约 50 毫秒,一个请求生成 200 个 token,每步填掩码约 100 微秒:

- **单个请求**:50 加上 200 乘 0.1 等于 **70 毫秒**,编译占 71%。
- **同 schema 的第一千个请求**(命中缓存):0 加 20 等于 **20 毫秒**,编译占 0%。

生产环境里 schema 通常是少数几个固定模板,命中率很高,所以**编译成本在稳态下趋近于零**。而首个请求的那 50 毫秒也不落在关键路径上 —— 它被异步线程池吸收了。

> 编译是把「每步十几万次文法判断」这个运行时代价,前置并摊销成「每个 schema 与词表的组合一次的预计算」。

以上数字是量级参考,不是本仓库实测。

### 1.33 把词表缩成 100 个 token

前面的数字(151936、4748、15 毫秒)量级太大,不好在脑子里过。这一节把词表缩到 **100 个 token**,其他都不变,所有数字都可以自己验算。

设定:词表 100 个;schema 还是那份最小的;额外关掉空白(例子更干净);期望输出仍是 `{"ok":true}`。词表里与本例相关的仍是 1.9 那批 token,另外多一个 id 18 的 `k"`;其余 82 个是自然语言 token。

掩码形状变成每行 4 个 int32,也就是 **16 字节**:

```text
word[0]   token  0.. 31
word[1]   token 32.. 63
word[2]   token 64.. 95
word[3]   token 96.. 99   外加 28 位填充, 浪费
```

**这里顺带把 1.7 那条「省八倍」验算实一遍。** 缩小例里逐布尔版是 100 字节,打包版是 16 字节,**只省 6.25 倍** —— 因为 4 个 word 覆盖 128 个槽位,装 100 个 token 白白浪费了 28 位。把这 28 位的浪费去掉,100 个 bit 等于 12.5 字节,**省的正好是 8 倍**。真实词表 151936 恰好被 32 整除、一位不浪费,所以它就是满的 8 倍。**词表越小,填充浪费占比越高,实际倍数越低于 8。**

编译三个阶段的机制 1.25 到 1.28 已经讲过,这里只看数字。关掉空白之后规则里的空白项全部消失,按字符摊平**一共 16 个状态**:骨架 7 个,`true` 分支 3 个,`false` 分支 4 个,再加收尾 2 个。阶段二把 100 个 token 逐个翻成字节串(结束符按规矩跳过)。阶段三拿这 100 个 token 去 16 个状态上各试走一遍,**一共 1600 次试走**。

### 1.34 编译产物就是这张表

阶段三跑完,产物是这样一张表,每个数字都能自己对:

| 状态 | 允许的 token id | 第 0 个 word | 其余三个 word |
|---|---|---|---|
| S0 | 1, 2 | 0x00000006 | 全 0 |
| S1 | 3 | 0x00000008 | 全 0 |
| S2.0 | 4, 5, 6 | 0x00000070 | 全 0 |
| S2.1 | 18 | 0x00040000 | 全 0 |
| S2.2 | 3, 7 | 0x00000088 | 全 0 |
| S3 | 8 | 0x00000100 | 全 0 |
| S4 | 9, 10, 11 | 0x00000E00 | 全 0 |
| S6 | 12 | 0x00001000 | 全 0 |
| S7 | 全部,终止不约束 | 全 1 | 全 1 |

**这张表有多大**:16 个状态乘 4 个 word 乘 4 字节等于 **256 字节**。

换成真实词表:16 乘 4748 乘 4 字节约等于 **297 KB**。这就是一个简单 schema 的编译产物量级,常驻内存完全不心疼,也解释了为什么那个缓存上限参数设成几十上百兆就能装下几十上百个 schema。

运行时这 16 个状态各占一行,六步走完,每步只搬 16 字节;batch 为 256 时每步传 4 KB。真实词表下同一件事是每步 18.6 KB、batch 256 时约 4.9 MB。

### 1.35 词表变大,状态不会变多

这是最值得单独记住的一条。**状态数和词表大小完全无关。**

产物表是二维的,两个维度由两件不同的事决定:

```text
             列宽 = 词表大小除以 32 向上取整
             +----------------------------------------+
             |  S0    word[0] word[1] word[2] word[3] |
             |  S1    ...                             |
             |  S2.0  ...                             |
             |  ...                                   |
             |  S7    ...                             |
             +----------------------------------------+
             行数 = 状态数, 由 schema 结构决定
```

- **行来自文法**:`{ " o k " : t r u e }` 这些字符位置,数出来就是 16 个。词表里有 100 个还是十几万个 token,跟这 16 个位置一点关系都没有。
- **允许集合(行里的内容)才是「文法乘词表」的产物**:词表变大,是**每一行变宽**,不是行数变多。

验算一下:词表从 100 涨到 151936 是 **1519 倍**,状态数不变,产物从 256 字节涨到 297 KB 是 **1187 倍** —— 差的那一点正是缩小例里那 28 位填充。产物大小约等于「状态数乘以词表除以 32 向上取整再乘 4 字节」,两个因子各自独立。

### 1.36 什么才会让状态变多:只有 schema 结构

| 让状态变多的因素 | 例子 | 影响 |
|---|---|---|
| 字面量(字段名)越长 | key 从两个字符换成十几个字符 | 那一段从 3 个状态变成十几个 |
| 字段越多 | 三十个字段的对象 | 线性叠加,几百个 |
| 枚举或联合分支多 | 二十个选项的枚举 | 每个选项各一串 |
| 递归或数组嵌套 | 对象里套对象再套数组 | 见下 |

粗算一个真实场景:三十个字段、字段名平均十个字符的 schema,骨架状态约四百个,产物约 **7.6 MB**。仍然是可以常驻内存的量级。

**唯一会爆的情况是递归。** 1.26 说过下推自动机的「状态」要连栈内容一起算:同一个图上位置,配上深度不同的栈,就是不同的状态;而嵌套深度没有上限,所以状态种类无限。

**所以递归 schema 无法把所有状态预先枚举成表。** 这才是两条 backend 路线分道扬镳的真正原因:状态图的状态数有限,可以全量建表;下推自动机只能「预计算 token 级转移,运行时按当前栈求解,再自适应缓存」。那个缓存上限参数限制的正是这类运行期缓存 —— **它缓存的是运行中实际遇到过的状态,而不是全部可能状态**。

一句话:**词表大小只影响「每行多宽」,schema 结构才影响「有多少行」**;而递归 schema 让行数变成无限,只能按需算、按需缓存。

### 1.37 死路必须在编译期剪掉

上面那张表里 S2.1 的允许集合只有一个 token。假如词表里**根本没有**以 `k` 开头的 token,S2.1 就成了死胡同 —— 模型走进去就再也出不来。

所以编译期必须连上一层的 `o` 一起剪掉:**一个 token 能不能走,不只看它自己能不能被接受,还要看走完之后落到的状态是不是死状态。**

outlines 的代码注释把这个约束写得很明白:它的「能否接受」只检查当前这批 token 是否被接受,而真正的「推进」还要额外检查全部 token 吃完之后的下一个状态 —— 注释原话是**文法必须在不含死状态的前提下构造出来**。

这也是「编译」和「逐 token 试算」的又一处差别:试算天然只看一步,而编译能看到全局,才做得了剪枝。

### 1.38 算总账:375 倍,而且倍数随流量增长

用缩小例把两条路线的总账摆出来:

| | 编译方案 | 运行时逐 token 试算 |
|---|---|---|
| 一次性成本 | 16 个状态乘 100 个 token 等于 1600 次试走,异步不占解码 | 无 |
| 每步做什么 | 查表抄 16 字节,再走一步,微秒级 | 遍历 100 个 token 逐个判断 |
| 一千个请求各六步的总试走次数 | **仍然是 1600**,与请求数无关 | 1000 乘 6 乘 100 等于 **60 万** |

比值是 **375 倍**。把 100 换回真实的 151936、六步换成两百步、请求数不变,就回到 1.22 那组数字 —— **2560 倍**。

**倍数随流量增长而拉大**,这就是编译的全部价值:它的成本是常数,对手的成本正比于流量。

### 1.39 六种约束类型

前面一直说「约束一共六种」,这里把它们一次列清。一个请求只能选一种,参数对象在构造时就做互斥校验,多选直接抛错。

| 枚举值 | 请求里的字段 | 说明 |
|---|---|---|
| JSON | `json` | JSON Schema,字符串或字典都行 |
| JSON_OBJECT | `json_object` | 任意 JSON 对象,不限字段 |
| REGEX | `regex` | 正则表达式 |
| GRAMMAR | `grammar` | EBNF,Lark 语法会被自动转成 EBNF |
| CHOICE | `choice` | 枚举选项 |
| STRUCTURAL_TAG | `structural_tag` | 标签触发式约束,用于工具调用与思考段 |

约束类型加上它的规范字符串,合起来就是**编译缓存的键**。从请求参数推导这个键时用的是一条**固定优先级**:JSON 最先,然后依次是 JSON_OBJECT、正则、枚举、EBNF、structural tag;一个都没有就抛错。

**structural tag 值得单独说一句**,因为它描述的是「分段输出」:某个触发字符串出现之后,后续内容必须符合某个 schema,直到结束标记为止。工具调用和思考模型的「思考段自由生成、答案段受约束」都是这个形状。

### 1.40 枚举其实走的不是自己那条分支

这是一处很容易读错的地方。枚举虽然有自己的枚举值,但在主流 backend 上**它根本到不了编译入口的枚举分支** —— 校验阶段就把它**改写成了一段 EBNF**:把选项拼成若干个字面量的或分支,然后把请求上的枚举字段清空、EBNF 字段填上改写结果。

所以那个 backend 的编译入口里压根没有枚举分支,只有五个。另外两个 backend 则各自原生实现:一个拼成正则,一个用专门的联合解析器。

这解释了 1.26 那个「只认三种」的观察 —— 同一个枚举约束,在三个 backend 上分别被当成 EBNF、正则、和原生联合来处理,**六种约束类型是请求层的分类,不是编译层的分类**。

### 1.41 从请求到 logits:十步链路

把整条路串起来。注意它横跨三类进程:API 进程、引擎进程、worker 进程。

```text
[1]  前端把请求里的约束字段翻译成内部参数对象
      六种约束六选一
[2]  参数校验, 这是关键的提前失败环节
      拒绝不支持的模型类型, 拒绝没有词表的情况
      定下 backend, 并按 backend 做试编译校验
      非法 schema 在这里就返回 4xx, 而不是让引擎在生成中途崩
[3]  引擎侧构造请求对象
      只要有任一约束字段非空, 就创建结构化输出子对象
      请求初始状态直接置成等文法, 而不是普通等待
[4]  首次用到时惰性创建全局唯一的 backend 实例
      把编译任务丢进线程池, 拿到一个 Future 挂在请求上
[5]  调度器把它放进跳过队列, 而不是等待队列
[6]  每个调度步轮询一次: 编译好了吗
      好了就转成普通等待, 随后正常调度为运行
[7]  每步生成掩码
      先非阻塞地把前向发出去, 再在 CPU 上算掩码, 然后等前向回来
[8]  worker 侧把掩码作用到 logits
      异步拷贝加一次 kernel
[9]  采样得到 token, 回到调度器推进状态机
      推进失败就终止请求, 不静默继续
[10] 文法终止之后, 该行掩码填全 1, 不再约束
```

### 1.42 四个容易忽略的点

**① 校验发生在前端进程,不是引擎。** 所以非法 schema 是同步的 4xx,**不消耗 GPU**。structural tag 还有一道单独的前端校验,注释写明理由:引擎侧会把畸形的标签报成生成失败,而在请求解析阶段拦下来才能正确地归类成客户端错误。

**② 编译任务是在输入处理线程里提交的,和调度线程分离。** 注释明确说明了这一点。每个请求的文法对象各自独立,所以不需要加锁。

**③ 第 6 步是轮询而不是通知。** 调度器每步主动查一次状态,最多一个 step 的延迟。这和 PD 分离里等远端 KV 的处理方式一致 —— 02 章 2.6.4 讲的那个「三个阻塞态的统一出口」,等文法就是其中一支。

**④ backend 是全局唯一的。** 源码注释写得很直白:V1 **不支持** per-request backend。所以一个引擎实例只会有一个 backend 实例,惰性创建,之后所有请求共用。

### 1.43 为什么编译必须异步

文法编译不是常数时间:一个深嵌套 schema 编译出来可能要几十到几百毫秒。如果在请求入队时同步编译:

- 引擎的**输入处理线程被卡住**,所有请求(包括不带约束的)入队都被延迟;
- 更糟的是如果放在调度线程,整个解码循环停摆,**全 batch 的每 token 延迟出现尖峰**。

所以编译被丢进线程池,立刻返回一个 Future 挂在请求上,请求状态置成等文法。

**Future 怎么被消费而不阻塞?** 请求对象上那个文法属性内部是这样的:如果还是 Future,就用 **100 微秒的超时**去取一次结果;超时就返回「还没好」,请求继续待在跳过队列里,下个 step 再探。**整个过程调度线程最多浪费 100 微秒。**

这里还有一条讲稿容易漏的分支:取结果时如果拿到的是**异常**,异常会被存回那个字段。于是调度器下一步读到的不是文法对象而是一个异常,据此把这条请求记进「编译失败」集合 —— 这就是 1.20 说的「编译失败只 fail 这一条请求」的实现。

三个阻塞态(等文法、等远端 KV、等流式输入)被统一归类成「阻塞等待」,进的是跳过队列而不是等待队列,**避免每次扫等待队列时反复检查这些注定还不能跑的请求**。

### 1.44 唯一的例外:确定性要求压过延迟

异步编译有一个开关会被强制关掉:**外部启动器模式**。

源码注释把理由写得很完整:这个模式下**每个张量并行 rank 都有自己的调度器**,异步编译会导致「等文法转为普通等待」这个迁移**在不同 rank 上发生在不同时刻**,破坏该模式依赖的确定性假设 —— 各个 rank 必须做出完全相同的调度决策 —— 进而死锁。

所以这种模式下改成同步编译,连异常也包装成一个已经置好异常的 Future,让下游逻辑不用分叉。**牺牲延迟换确定性。**

这条值得记住,因为它是个很好的例子:**一个看起来纯粹是性能优化的设计(异步编译),在特定并行模式下会变成正确性问题。**

### 1.45 什么时候这层重叠会失效

1.6 说过掩码在 CPU 上算、与 GPU 前向重叠,机制见 01 章 2.4。这里只补代码里实际的先后:**先非阻塞地把前向发出去,再算掩码,然后等前向回来,最后带着掩码去采样。** 四步的顺序就是重叠能成立的全部。

结论是:只要算掩码比前向快,结构化输出对**吞吐**的影响接近零;真正暴露成延迟的只有最后那次 kernel 把负无穷写进 logits 的时间,微秒级。

但有三种情况会让它暴露成瓶颈:

1. **batch 很大且 schema 很复杂** —— 单个填掩码变慢,串行累加超过前向时间。
2. **小模型加短 prompt** —— 前向本身只有一两毫秒,掩盖不住掩码生成。
3. **backend 是纯 Python 实现** —— 有全局解释器锁争抢,并行填充也救不了。

这也解释了为什么 backend 的**实现语言**在选型里权重这么高:重要的不是总耗时,而是 **能不能被前向掩盖** ,以及 **是否持有解释器锁** 。

以上三条是推论,不是本仓库实测。

### 1.46 并发一上去,填掩码就盖不住了

1.45 列的第一种失效情况值得展开,因为它是这一段唯一真正做了优化的地方。

回到机制本身:**每个解码步、每个结构化请求,都要单独查一次自己的路标,把结果写成一行掩码。** 这件事有两个性质:

1. **它是纯 CPU 工作。** GPU 那边在算注意力和前馈,填掩码这边在 CPU 上查表。
2. **它的成本正比于并发请求数。** 128 个结构化请求就查 128 次,256 个就查 256 次。**而前向的耗时并不随 batch 线性增长** —— GPU 本来就是批量算的。

两条曲线的斜率不一样,所以迟早会相交:

```text
耗时
 |                                /    串行填掩码, 正比于并发数
 |                             /
 |                          /
 |                       /
 |  -----------------/--------------   前向, 近似平坦
 |                /
 |             /      交点: 从这里往右, 填掩码不再被掩盖
 +----------------------------------->  并发请求数
                ~128
```

一笔粗账:单个请求填一次掩码大约二十到五十微秒,取决于 schema 复杂度和词表大小。

| 并发结构化请求数 | 串行填掩码总耗时 | 小模型前向 | 是否被掩盖 |
|---|---|---|---|
| 16 | 约 0.5 毫秒 | 约 2 毫秒 | 完全掩盖 |
| 128 | 约 4 毫秒 | 约 2 毫秒 | 已经掩盖不住 |
| 256 | 约 8 毫秒 | 约 2 毫秒 | 成了主要瓶颈,每 token 延迟翻数倍 |

所以并行填充要解决的就是:**把这条线性增长的 CPU 曲线压平,让它重新缩回前向的时间窗口里。** 以上数字是量级参考,不是本仓库实测。

### 1.47 这活儿为什么拆得开

并行化不是随便就能做的,得先确认任务之间真的没有依赖。这里满足两个条件。

**① 写入位置天然不重叠。** 每个请求在掩码张量里占独立的一行,行号逐请求递增。任务 A 写第 0 到 15 行,任务 B 写第 16 到 31 行,物理上碰不到一起 —— 所以**整个并行路径一把锁都没有**。

**② 每个请求的状态是私有的。** 1.24 讲过产物分两半:编译产物只读、跨请求共享;游标每请求一份。查表这个动作**只读共享的那一半、只读自己的游标**,不写任何共享状态。

一句话:**这是一个 map,不是 reduce。** 所以直接切开丢给线程池就行。

### 1.48 怎么切:攒够一批再投

并行路径的逻辑只有二十几行,做四件事:遍历请求攒任务、**攒满 16 个就投出去**、末尾把不满一批的尾巴也投出去、最后等全部完成。

线程里执行的就是原来串行循环的那个循环体 —— 查路标写第 index 行,或者按 1.8 的规矩把整行填成放行。

**为什么要攒 16 个再投,而不是一个请求一个任务?** 因为提交任务本身有开销(加锁、进队列、唤醒线程、创建 Future),量级和一次填掩码差不多,都是几十微秒。一请求一任务的话,调度开销就把并行收益吃掉了。攒成 16 个一批,调度开销被摊薄到十六分之一:256 个请求变成 16 个任务,8 个线程各领 2 个。

三个参数:

| 参数 | 值 | 说明 |
|---|---|---|
| 并行阈值 | 128 | 结构化请求数超过它才并行 |
| 每批大小 | 16 | 每个线程任务处理 16 个请求 |
| 线程数上限 | CPU 核数的一半,且不超过 8 | 最多 8 个线程 |

**为什么阈值取 128?** 请求数少的时候,提交加跨线程同步的固定成本反而比直接串行做完更贵。128 是经验值,对应上面那张曲线图的交点位置附近。

还有一点容易忽略:**这是一次同步的分发与汇合,不是异步后台任务。** 掩码装配函数返回时所有行必须已经写好,因为下一步采样就要用。所以整体耗时取决于**最慢的那个线程**。

### 1.49 为什么 Python 线程池在这里真的有效

这是最容易被质疑的一点:Python 有全局解释器锁,多线程不是假并行吗?

对纯 Python 代码是这样,但这里不是。**填掩码最终落到各 backend 的原生实现**:

| backend | 实现语言 | 填掩码落到哪 |
|---|---|---|
| xgrammar | C++ | 匹配器的 `fill_next_token_bitmask` |
| guidance | Rust | 同名入口,外加一次错误检查 |
| outlines | Rust | 导引对象的 `write_mask_into`,直接写进张量的数据指针 |
| lm-format-enforcer | 纯 Python | 取允许集合再整行赋值 |

原生扩展在进入 C++ 或 Rust 之前会释放全局解释器锁,算完再拿回来。这段时间内其他 Python 线程可以自由运行 —— 所以 8 个线程真的在 8 个核上同时查表。

**这里要标一句:调用名在本仓库可见,但「释放全局解释器锁」是那几个外部库的性质,本仓库看不到它们的实现。** 结论合理,证据不在这个仓库里。

**推论**:用纯 Python 那个 backend 时,并行填充这条路径起不了作用,线程只会在锁上排队。这也正是 1.45 说 backend 实现语言在选型里权重很高的原因之一。

### 1.50 两个约束

并行路径有两道门,任一不满足就走串行。

**① 阈值不满足时,线程池根本不创建。** 判断用的是**配置的并发上限**而不是当前请求数:并发上限本来就不超过 128 的部署,连线程都不会起 —— 不浪费资源。反过来说,如果你的并发上限没配到 128 以上,这条优化对你完全不存在,那个线程池属性甚至不会被赋值。

**② 开了投机解码就禁用并行。** 这条要单独讲,见下一节。

### 1.51 投机解码为什么拆不开

先说清一个容易混淆的点:「填一行、推进一步、再填一行」这个节奏两种情况都有,**区别在于这个循环发生在哪个尺度上**。

**不开投机解码时,填和推进被 GPU 隔开,分属两个函数。** 装配掩码那一次调用里,每个请求恰好填 1 行、它的游标恰好被读 1 次、一次都不写;推进发生在采样结果回来之后的另一个函数里。**请求之间零依赖,这就是标准的 map**,切开丢线程池天然安全。

**开了投机解码,填和推进被压进同一次调用,而且是试探性的。** 假设草稿模型提了 2 个 token,目标模型要在一次前向里同时验证 3 个位置,所以掩码也必须在前向之前一次性备好 3 行。但第 2 行的合法集合取决于「假如第 1 个草稿被接受」之后的状态 —— 而这时候还没前向,根本不知道会不会被接受。于是只能**先假设接受,算完再撤销**,也就是 1.19 讲的那套。

两个独立的理由,任一条都足以否决并行:

| 理由 | 说明 |
|---|---|
| 行与行之间有数据依赖 | 第 1 行的内容依赖第 0 行之后的那次推进,不能同时算,只能排队 |
| 多行共享同一个游标 | 同一个请求的 3 行都在读写同一个游标对象,哪怕分给 3 个线程也会互相踩状态 |

对比就很清楚:

| | 不开投机解码 | 开投机解码 |
|---|---|---|
| 每请求的掩码行数 | 1 | 1 加上草稿数 |
| 装配时写不写游标 | 不写 | 写,试探推进再回滚 |
| 依赖形态 | 请求间无依赖,是 map | 请求内部是串行链,拆不开 |

### 1.52 掩码作用到 logits 的两条路径

worker 侧有两套实现,对应两代模型运行器。**两者语义等价**,差别全在怎么搬数据。

**路径 A 是 vLLM 自带的 Triton kernel**,新运行器走这条:

- **常驻缓冲加异步拷贝**:GPU 上那块掩码张量在构造时就分配好,每步只覆盖前若干行,不重复分配;拷贝走**独立的拷贝流**。
- **要先算一张映射**:掩码的行序是按「有结构化输出的请求」排的,而 logits 的行序是按输入批次排的,两者不一致。要紧的是映射里存的**不是绝对 logits 下标**,而是「请求下标乘以行距再加位置」这个编码 —— 绝对下标要到 kernel 里再用 GPU 上的累计 logits 数还原。注释说明了理由:自适应验证会在设备侧压缩每请求的 logits 偏移,CPU 不必跟着算。
- **双向等待**:发 kernel 前等拷贝流完成,函数结束时反向再等一次,防止缓冲在 kernel 用完前被复用。
- **kernel 本身**按「掩码行乘以词表分块」铺 grid,解包之后**只写非法位置**,合法位置的 logits 一个字节都不碰;另有一个开关挡掉「本请求实际 logits 数不足这个位置」的行。

**路径 B 直接调 xgrammar 的预编译 kernel**,旧运行器走这条:

- 同样要做行重排,但**做法相反**:先在 CPU 上构造一个与 logits 逐行对齐的张量(初值全放行),把掩码按批次顺序填进去,再整块异步拷过去。
- 如果长度正好对齐,可以**省掉下标参数**。
- 下标本身要预先异步搬到 GPU,注释说明这是为了**避免 xgrammar 内部触发一次 CPU 同步**。
- CPU 后端有特殊处理:老版本的 xgrammar CPU kernel 只支持单精度,所以非单精度的 logits 要先转、应用、再拷回去。

核心差异:

| 维度 | 路径 A | 路径 B |
|---|---|---|
| kernel 来源 | vLLM 内置 Triton | xgrammar 预编译 |
| 重排在哪做 | GPU 上用下标间接寻址 | CPU 上先物理重排成对齐张量 |
| 主机到设备的数据量 | 只传实际的掩码行 | 传整块,含全放行的行 |
| 拷贝流 | 专用拷贝流 | 默认流上非阻塞拷贝 |

**路径 A 更省带宽也更省 CPU**,是新运行器的方向。

### 1.53 投机解码要多行掩码,行与行之间有依赖

投机解码一个步会验证「1 加上草稿数」个位置的 logits,所以**每个请求需要多行掩码**。掩码张量在分配时就按「并发上限乘以 1 加草稿数」开好,1.34 讲过。

行的语义是按草稿 token 顺序来的:对每个草稿位置,先填这一行的合法集合,再**假设该草稿被接受**、推进状态机;所有草稿位置走完之后,再填一行给 bonus token;最后**把这些试探性推进全部回滚**。

**为什么必须回滚**:这里的推进是投机性的 —— 草稿到底会不会被采样器接受,此刻还不知道。掩码生成阶段必须假设「前面都接受」才能算出后面位置的合法集合;算完立刻回滚,等真实接受结果回来之后,再用真实 token 推进一次。

这要求文法支持**有界回滚**,所以各 backend 在构造时都传入了「最大回滚步数等于草稿数」:两个 backend 各自把它传给自己的匹配器或导引对象,而纯 Python 那个**直接报错拒绝** —— 它不支持投机解码。

### 1.54 语法上不可能的草稿提前扔掉

还有一处协同优化值得记。草稿生成之后、进入批次之前,调度器会用**不推进的校验**砍掉不合法前缀之后的部分 —— 1.12 说过,校验的语义正是「返回被接受的最长前缀,且不推进状态机」。

被砍掉的位置用 −1 填充,掩码生成时遇到 −1 就停止约束,那一行填成全放行。

这条链是这样串起来的:输出里把无效草稿填成 −1,记下无效的数量;装配掩码时遇到 −1 就把后续的「施加掩码」和「推进」两个开关一起关掉。

**语法上不可能的草稿提前扔掉,等于避免浪费验证位置,也就等于提高了投机接受率的上界。**

### 1.55 思考段必须放行

思考模型的输出分两段:先是一段自由文本的思考过程,遇到结束标记之后才是必须符合 schema 的答案段。

**如果从第一个 token 就套上 JSON 文法,模型会被迫立刻输出左花括号,思考能力直接失效。** 所以结构化输出必须跳过思考段。

判定逻辑分三档:

| 情况 | 行为 |
|---|---|
| 没配思考解析器 | 一律约束,走到末尾直接返回真 |
| 配了,且显式要求连思考段一起约束 | 也一律约束 |
| 配了,默认档 | 看「思考是否已结束」这个标记;还没结束就填全放行的掩码、也不推进状态机 |

有个实现细节值得记:**思考解析器是按请求持有的,不是全局一份。** 注释解释了原因 —— 某些解析器的行为依赖请求级的聊天模板参数,不能跨请求共享实例;管理器只持有类,实例懒加载并缓存到请求上。

### 1.56 最微妙的地方:思考段在一个步中间结束

这一节的复杂度基本全部来自一件事:**思考段与答案段的边界可以落在一个步的内部。** 有三处代码专门处理它。

**① 推进判定在思考结束的那一步就返回真。** 它拿本步新增的那一小段 token 去问解析器「思考是不是在这段里结束了」,一旦触发就置好标记,并把结束标记的绝对下标记下来供第二处使用。这里还有个推算的讲究:优先直接用调用方传来的新 token 列表,拿不到才退回去用计数器推算 —— 注释指出后一种推算有个前提假设,在「异步调度加投机解码且部分草稿被拒」时会把窗口起点算到结束标记之后,所以调用方应当直接传新 token 列表。

**② 推进之前要先裁掉思考内容。** 正因为第一处在同一个步就推进,这一步的新 token 往往是「思考内容 + 结束标记 + 答案开头」的混合块。直接拿整块去推进,文法会拒绝结束标记从而**杀掉请求**。所以有一个专门的函数按刚才记下的下标算出要丢弃的前缀长度,只把标记之后的部分喂给文法;整段都落在标记之后时原样返回。

**③ 装配掩码时还要在窗口内部再检测一次。** 投机解码的草稿窗口内也可能思考结束。串行路径里对每个草稿 token 问一次解析器,一旦触发就把窗口剩余位置改为受约束,**但不推进状态机**(因为标记本身是思考内容),并置一个标志以容忍后续草稿被拒 —— 这正是 1.19 讲的那条「容忍拒绝」的来路,那些草稿是在掩码之前产生的,不保证合法。

> 这一节的复杂度几乎全部来自那个边界。如果既不用投机解码、也不用分段标签,实际路径要简单得多:一个布尔量就够了。

### 1.57 auto 是一条回退链

backend 配置项的默认值是 **auto**,不是某个具体 backend。auto 的语义是「vLLM 替你做有主张的选择,并且允许回退」:

```text
backend == auto
 |
 +-- 先试 xgrammar 的校验
 |     通过  ->  定为 xgrammar          绝大多数请求走这里
 |     抛错 (schema 用了它不支持的特性)
 |
 +-- 判断要不要跳过 guidance
 |     tokenizer 是非 tekken 的 Mistral, 或者
 |     schema 含 guidance 不支持的特性
 |
 +-- 要跳过  ->  校验 outlines  ->  定为 outlines
 |
 +-- 不跳过  ->  校验 guidance  ->  定为 guidance      默认回退目标
 |
 +-- 最后统一置一个「这是 auto 推出来的」标记
```

**显式指定 backend 时没有回退。** 指定了哪个就只跑哪个的校验,失败直接抛错 —— 源码注释写得很直白。这个设计是对的:用户明确指定了 backend,静默换成别的会让性能特征不可预期。

**那个「auto 推出来的」标记解决什么问题?** 采样参数对象可能被复用,同一份参数发多个请求。第一次 auto 推出结果后会把它写回参数;第二次校验时会看到「配置说 auto、参数里却写着具体 backend」,如果没有这个标记就会误报成「不支持请求级指定 backend」。

### 1.58 xgrammar 不支持什么,以及一处「静默丢弃」

触发回退的条件是一组 JSON Schema 特性检查,而且检查是**递归**的,嵌套对象或数组里出现同样的关键字也会触发:

| 类型 | 不支持的关键字 |
|---|---|
| 整数与数字 | 倍数约束 |
| 数组 | 元素唯一、包含、最少包含、最多包含 |
| 字符串 | 格式取值不在白名单内,白名单共 14 项 |
| 字符串 | 模式或格式与长度上下界**混用** |
| 对象 | 按模式匹配的属性名、属性名约束 |

**倒数第二行值得单独看,它不是「不支持」,而是「会悄悄错」。** 源码注释说明:xgrammar 会编译模式或格式那一侧,却**静默丢掉长度上下界**,于是输出可能违反长度约束而不报任何错。更值得记的是注释后半句 —— **作者是对着编译产出的 EBNF 验证过的**:带与不带长度关键字时,模式或格式的文法逐字节相同;而单独给最大长度时能正确降解。所以这里主动判为「不支持」让它回退,**而不是产出一个悄悄错的结果**。

guidance 那边不支持的只有一项:按模式匹配的属性名。所以「xgrammar 不行就转 guidance」这条回退能覆盖大部分场景。

另外两个 backend **完全不支持 EBNF**,遇到那个字段直接抛错。

**tokenizer 兼容性也是一道坎**:xgrammar 对 Mistral 做了特殊适配(1.27 讲过手工构造词表信息);guidance 只支持 tekken 那一种;纯 Python 那个完全不支持 Mistral。

### 1.59 四个 backend 的能力矩阵,以及四种「终止」

| 能力 | xgrammar | guidance | outlines | lm-format-enforcer |
|---|---|---|---|---|
| 底层实现 | C++ | Rust | Rust | 纯 Python |
| JSON Schema | 支持 | 支持 | 支持 | 支持 |
| 任意 JSON 对象 | 支持 | 支持 | 不支持 | 支持 |
| 正则 | 支持 | 支持 | 有限制 | 支持 |
| EBNF | 支持 | 支持 | 不支持 | 不支持 |
| 枚举 | 支持,转成 EBNF | 支持 | 支持 | 支持 |
| 分段标签 | 支持 | 支持 | 不支持 | 不支持 |
| 投机解码 | 支持 | 支持 | 支持 | 显式报错 |
| 编译缓存 | 内存,大小可配 | 无显式缓存 | 内存加磁盘 | 只缓存词表数据 |
| Mistral 词表 | 支持,特殊适配 | 仅 tekken | 支持 | 不支持 |

**最容易踩的细节是「终止」这个语义,四家的实现完全不同:**

- **xgrammar**:每次推进之后同步一次匹配器的终止状态,存进自己的字段。
- **guidance**:靠结束符出现在 token 里来判定,还维护一个**回滚补偿量**,因为结束符那一步要单独扣。
- **outlines**:底层库在状态图到达接受态时就报完成,但 vLLM 期望「结束符之后才算完」,所以它**人为延迟一步** —— 返回的是上一次的值,而不是这一次的。
- **lm-format-enforcer**:检查 token 前缀的最后一个是不是结束符。

同一个接口方法,一个查字段、一个数结束符加补偿、一个故意延迟一拍、一个看前缀末尾。**接口统一不代表语义自动统一**,这是读多 backend 抽象时最容易想当然的地方。

最后一条共性:**所有 backend 的正则编译都包了超时保护**,防止恶意或病态正则把 CPU 打满 —— 这是面向公网服务的安全考虑。outlines 还额外做了静态特性检查,拒绝反向引用、环视、以及需要前置上下文才能匹配的锚点模式,因为它的底层库要求正则有一个**通用起始状态**。
