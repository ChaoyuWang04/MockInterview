# vLLM 16|配置系统与参数全览

一条 `vllm serve` 命令怎么变成每个 worker 手里那份配置对象:谁解析它、谁往里填默认值、谁有权覆盖谁。这一章讲清这条流水线,以及为什么「查一张参数表」这件事本身就是错的做法。**它分三段**:前半讲这条流水线**怎么走** —— 三个名字空间、四层默认值、一条十二关的路;中间讲照着源码读出来的**实现细节与覆写链**;后半讲**怎么用** —— 哪些值不能按字面理解、参数没生效怎么查、调参从哪一层开始。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:把参数当一张表来记,会在四个地方翻车

### 1.1 把参数当一张表来记,会在四个地方翻车

绝大多数人是这么用 vLLM 的参数的:遇到一个不认识的开关,去文档或源码里搜一下,记下「名字」和「默认值」两列。这个做法在四个地方会失效,而且失效时不报错。

| 你以为 | 实际 | 后果 |
|---|---|---|
| 一个参数一个名字 | 同一个东西在命令行、参数对象、配置对象上**三个名字** | 搜一个名字命中三层,误以为存在两个不同的参数 |
| 「默认值」是一个确定的数 | 这个词有**四种含义**,你抄到的通常是最没用的那种 | 参数表系统性误导 —— 同一条命令在两台机器上差四倍 |
| 参数各管各的 | 参数之间**互相改写**,而且是单向、有顺序的 | 你显式写的值被静默清掉,日志里只有一行 |
| 配置全都在命令行参数里 | 还有**另一套输入通道**(环境变量)、**另一组归前端的参数**,而配置本身还会产出一个看不见的东西(编译缓存目录) | 在错的地方找参数;或者只改了一个参数却触发了整套重新编译 |

**前三条是同一件事的三个侧面** —— 它们都在说「参数不是一张表,是一条流水线」,而流水线的性质查表查不出来。**第四条换了个方向**:不是这条流水线内部怎么走,而是它的入口不止一个、出口也不止一个。

这决定了全章的组织:先把一条命令行变成配置对象的完整过程讲清(Part 1 到 Part 3),再补上那条并行的输入通道(Part 4)与一张全景图(Part 5);之后是照源码读出的实现细节(Part 6 到 Part 8),最后才是速查与决策(Part 9 到 Part 11)—— **速查里每个默认值都标注它来自哪一层,而不是笼统写一个数字**。

### 1.2 第一处:同一个东西有三个名字

拿 KV cache 的数据类型举例。命令行上它叫 `--kv-cache-dtype`;引擎参数对象上,字段名跟着命令行叫 `kv_cache_dtype`;而真正存放它的缓存配置对象上,字段名叫 `cache_dtype`。

三者之间的连接发生在构造配置对象时的一次手写赋值 —— 把解析出来的值算成一个最终类型,再填进缓存配置的那个字段。

于是你在源码里搜 `cache_dtype` 会同时命中三层。如果不知道这是三个名字空间,就会以为存在两个不同的参数,甚至以为其中一个是废弃的。

**为什么会有三层。** 命令行的名字要对用户友好,所以带 `kv` 前缀说清是哪个 cache;配置对象的字段已经在缓存配置类里了,再带 `cache` 前缀就是重复。中间那层引擎参数对象是纯粹的搬运工,它跟命令行对齐。这不是历史包袱,是三层各自的命名习惯撞在一起。

### 1.3 名字撞车但语义不同的反例

反过来也有陷阱:推测解码的配置对象里**也有**一个 `kv_cache_dtype` 字段。它是草稿模型专用的、和缓存配置里那个平行的另一个设置。

名字撞车但语义不同,这比「一个东西三个名字」更危险 —— 前者搜出来你会觉得多余,后者搜出来你会觉得找到了。

判断方法只有一个:看它挂在哪个配置对象上。挂在缓存配置上的管主模型,挂在推测配置上的管草稿模型。

### 1.4 第二处:「默认值」这个词有四种含义

以并发上限为例,同一个概念在四个地方各有一个「默认值」:

| 层 | 这一层写的是什么 | 值 |
|---|---|---|
| 配置类的字段默认值 | 一个静态常量 | 128 |
| 引擎参数对象的初值 | 哨兵 —— 表示「用户没说」 | 空 |
| 按硬件与场景分档的决议表 | 真正会被填进去的值 | 看卡和用法 |
| 决议之后的夹取 | 不许超过单步 token 预算 | 取两者较小 |

第三层才是你实际跑到的值。那张分档表按显存容量分三挡:显存不低于 160 GiB 的卡一档,不低于 70 GiB 且不是 A100 的卡一档,其余一档;每一档里再按「离线批量」还是「在线服务」分两种用法。在一张 80 GB 的 H100 上跑在线服务,并发上限的默认值是 **1024**,不是 128。

所以「`--max-num-seqs` 默认 128」这句话在 H100 上是错的。**而它在什么时候才对,比它错在哪里更值得说清** —— 见下一节。

> 这里只讲「默认值是怎么决议出来的」。并发上限本身怎么影响调度、和 KV cache 容量与 token 预算怎么互相卡,02 章 3.1 已经讲透,本章不重复。

### 1.5 那个 128 到底什么时候生效

分档表是一个字典,键只有「离线批量」和「在线服务」两个。决议时用这个字典去查当前的使用场景,**查不到才回落到配置类里那个静态常量 128**。

于是 128 真正的生效条件是:**使用场景没给**。不是「没有 GPU」—— 探测不到设备时走的是「其余」那一档,那一档给的并发上限是 **256**,不是 128。另一个能拿到 128 的真实入口是 CPU 平台且并行规模为 1,那条分支把并发上限算成 128 乘以并行规模。

这个区分不是抠字眼。它决定了你在容器里、在 CI 里、在没装驱动的机器上做参数实验时,拿到的基线是哪个数。

### 1.6 第三处:参数之间互相改写

`--enforce-eager` 的名字听起来只是「关掉 CUDA Graph」。它实际在配置容器的初始化里连着改三个字段:先把编译模式和图模式双双置空,之后又把最大捕获尺寸清零、把捕获尺寸列表清空。

于是你同时传 `--enforce-eager` 和一份自定义的捕获尺寸,后者会被静默清掉 —— 日志里只有一行「eager 模式下 CUDA Graph 已禁用」。

**这条改写是单向且有顺序的**:先执行的填不进已经有值的字段,后执行的可以直接覆盖。哪些改写属于哪一类,是 5.2 那张四层瀑布要回答的问题。

> CUDA Graph 本身的三个档、五条硬约束、分桶与区间映射,06 章 2.4 至 2.7 已经讲完。本章只关心「这个开关在配置流水线的哪一步、以什么方式改掉了它」。

## Part 2|解法:类型注解就是参数定义

### 2.1 为什么不能靠手写参数解析解决

先看不做任何抽象的代价。每个参数老老实实写一行注册:名字、类型、默认值、帮助文字;然后在配置类里再写一遍同样的默认值。

这就有了**两处需要同步的默认值、两处需要同步的帮助文字**。基准上参数注册有 251 处、分布在 15 个参数组里,配置字段总数在 500 以上。两处同步乘以 500,就是一千个漂移机会 —— 而「命令行默认值和配置默认值不一致」这种 bug **不会报错**,只会让某些人的服务和文档不符。

更麻烦的是类型。有的参数只接受固定几个字符串;有的收一个 JSON 字典;有的收一整个嵌套配置对象的 JSON;有的收逗号分隔的整数列表;还有的希望能写 `16k` 这种人类可读的写法。每一种都要配一个转换函数。

### 2.2 vLLM 的解法:类型注解就是参数定义

把这些信息全部放进配置类的**类型注解**里,再由一个反射函数把注册参数需要的那套关键字算出来。规则有五条:

| 字段的类型注解 | 自动变成 |
|---|---|
| 布尔 | 一对 `--x` 与 `--no-x` 开关 |
| 固定取值的字面量类型 | 一份候选值清单 |
| 另一个配置类 | 接受 JSON 字符串,并用 pydantic 按那个类的结构校验 |
| 类型里含空值 | 外面包一层,允许显式传「空」 |
| 名字在人类可读整数的白名单里 | 接受 `16k` 这种写法,并把说明追加进帮助文字 |

默认值不再写两遍:参数对象上的字段直接**引用**配置类里那个字段的默认值。**默认值的唯一真实来源就是配置类的字段定义。**

### 2.3 帮助文字从注释来,而且是惰性的

帮助文字直接取字段下方的文档字符串。但解析文档字符串是有成本的,而绝大多数启动根本不需要帮助文字。

所以它加了一道判断:只有命令行里真的出现了求助开关、或者正在生成文档时,才去解析。平时启动一次都不付这个代价。

### 2.4 代价:读参数注册处看不到默认值

反射不是白来的。**你不能靠读参数注册的那段代码知道一个参数的默认值** —— 那里只有一个「把算好的关键字展开」的写法,具体的值在反射结果里。

这直接决定了后面速查表的写法:所有默认值一律引用**配置类**里的字段定义,而不是参数注册处。后者更容易漂移,而且不含信息量。

### 2.5 贯穿全篇的那条命令

后面所有小节围绕同一条命令展开。机器是两张 80 GB 的 H100,模型是一个 8B 的稠密模型,张量并行开到 2,最大长度设成 32768,KV cache 用 FP8,开 LoRA 并给定上限,用点号语法指定一个 CUDA Graph 模式,再换一个端口。

它的特点是把本章要讲的几类输入凑齐了:有普通的散装参数、有需要按硬件决议的参数、有用点号语法写进嵌套配置的参数、还有一个归前端而不归引擎的参数。

### 2.6 一条命令要过十二关

从进程启动到每个 worker 拿到配置,中间有十二道关卡:

| # | 关卡 | 做了什么 |
|---|---|---|
| 1 | 命令分发 | 认出子命令,构造那个增强过的解析器 |
| 2 | argv 预处理 | 展开配置文件、折叠点号参数、试解析值、告警重复键 |
| 3 | 参数解析 | 得到一个命名空间,没指定的参数大多还是空 |
| 4 | 拆成两组 | 前端参数归前端,其余归引擎 |
| 5 | 引擎参数的初始化后处理 | 把点号语法收上来的字典提升成配置对象,解析量化配置,加载插件 |
| 6 | 构造模型配置 | 拉模型自带的配置,定下最大长度与计算精度 |
| 7 | 默认值决议 | 按模型能力开关分块预填充与前缀缓存,按硬件与场景定批大小 |
| 8 | 构造其余配置 | 缓存、并行、调度、LoRA…… |
| 9 | 装进容器 | 触发容器的初始化后处理 |
| 10 | 全局覆写与校验 | 应用优化级别的默认、算 CUDA Graph 捕获尺寸、校验各种兼容性 |
| 11 | 算哈希 | 决定编译缓存目录 |
| 12 | 分发给 worker | 每个 worker 拿到同一份配置 |

**第 7 步和第 10 步是全篇的重点**:用户没写的参数在这两步被填上,用户写了的参数在这两步可能被改掉。

## Part 3|两个贯穿全章的约定:哨兵与配置对象

### 3.1 「没设置」与「设成了默认值」必须能分开

第 3 步埋了一个关键细节:解析完命令行之后,并发上限还是空的,而不是 128。这是贯穿整个配置系统的一条约定:

> 凡是「默认值需要看别的东西才能定」的参数,引擎参数对象上的初值一律是空;**空的含义是「用户没有指定」,不是「取零值」**。

必要性可以用分块预填充的开关说明。它是三态的:

| 用户给的值 | 行为 |
|---|---|
| 没给 | 取模型自己声明的能力 |
| 显式要开 | 模型不支持也照开 |
| 显式要关 | 模型本该支持也照关 |

**三种情况下用户的意愿都被尊重,一个值都不改** —— 后两种只是多打一条警告。而那条警告什么时候真的会打,还有一个藏起来的前提,见 7.5。

如果初值写成「关」,第一种和第三种情况就无法区分,引擎也就没法既尊重模型能力又尊重用户意愿。

同样的三态约定还用在前缀缓存开关、异步调度开关、混合 KV cache 管理器开关、块大小、分布式执行后端等一大批参数上。

### 3.2 三态的代价:同一个字段名在两层是两种类型

调度配置上那个分块预填充字段的类型是**纯布尔且默认为真**,而引擎参数对象上的同名字段是**布尔或空、初值为空**。

这两个不矛盾,只是分工不同:前者是「最终一定有值」的存储,后者是「可能没值」的输入。看源码时要注意自己读的是哪一层 —— 这是本章最容易读错的地方之一。

### 3.3 哨兵的第二种用法:只填空白

还有一层更隐蔽的用法。容器上有一个专门的写默认值的小工具,它**只在字段当前为空时才写入**,并且允许默认值本身是一个待求值的函数 —— 那些「要看别的配置才能定」的默认值就写成函数,到这一步才求值。

这就是「优化级别的默认值不覆盖用户显式设置」的实现方式。所以有一批字段的类型注解写着「布尔」、初值却故意放空,并配一条让类型检查器闭嘴的注释 —— 类型标注上是布尔,初值放空,就是为了让这个工具能区分「没设」和「设成了假」。

**这一条和 1.6 的强制覆写正好是一对**:一个只填空白、绝不覆盖用户;一个直接赋值、会覆盖用户。5.2 把它们放在同一层里对照。

### 3.4 配置对象全景:三十个类装进一个容器

配置模块下有 34 个文件。真正会被用户直接触碰的配置类有三十个,按它们管什么分组:

| 组 | 配置类 | 怎么设 |
|---|---|---|
| 模型与加载 | 模型、加载、模型架构覆写 | 散装参数 |
| 显存与调度 | 缓存、调度 | 散装参数 |
| 并行 | 并行、专家负载均衡 | 散装参数 / JSON |
| 算子与后端 | 注意力、Mamba、kernel | JSON 或专用开关 |
| 特性 | LoRA、多模态、推测解码、结构化输出、推理解析、池化 | 散装参数或 JSON |
| 编译 | 编译 | 点号语法或 JSON |
| KV 周边 | KV 传输、KV 事件、卸载、编码器缓存、编码器缓存传输 | JSON 或散装参数 |
| 运维 | 可观测性、profiler、容错、权重热更新 | JSON 或散装参数 |
| 其他形态 | 扩散式、语音转文字、结构化量化描述 | JSON 或模型侧定义 |
| 设备 | 设备 | 不可直接设,由平台探测 |

它们全部装进一个容器对象,容器共 31 个字段 —— 除了上面这些配置对象,还有量化配置、优化级别、性能模式、附加配置、实例标识和关停超时。

### 3.5 一个例外:多模态配置要跳三跳

容器里**不存在**多模态配置这个字段。多模态配置挂在模型配置下面。

它的命令行参数走的是一条绕路:先从多模态配置类反射出注册用的关键字(所以默认值仍然来自多模态配置类),注册在多模态参数组里;但这些值先落到**模型配置上的 24 个「仅初始化用」字段**,再由模型配置的初始化后处理收集起来,构造出真正的多模态配置对象。

所以查一个多模态参数要跳三跳:命令行名字 → 模型配置的初始化字段 → 多模态配置的最终字段。中间那一跳是纯粹的中转,查文档时最容易在这里断线。

## Part 4|另一套输入通道:环境变量

### 4.1 环境变量与命令行参数各管什么

这里开始是 1.1 第四条痛点的正面回答:**配置的入口不止命令行一处**。

基准上声明了 287 个环境变量。它们和命令行参数不是二选一的关系,分工大致是:

| 类别 | 走哪条 | 为什么 |
|---|---|---|
| 影响模型语义与调度的 | 命令行 | 属于这次服务的定义,要能被记录和复现 |
| 需要在导入之前生效的 | 环境变量 | 命令行还没解析,构建期的开关只能走这条 |
| 要传给子进程与 worker 的底层开关 | 环境变量 | 环境天然会被子进程继承 |
| kernel 级选择与逃生舱 | 环境变量 | 出问题时要能不改命令就绕过 |
| 实验性、随时会删的 | 环境变量 | 不进命令行就不构成兼容性承诺 |
| 两条路都有的 | 都有 | 前缀缓存保留间隔、多模态哈希算法、编译缓存保存格式等少数几个 |

最后一类要小心:同一件事有两个入口时,谁覆盖谁取决于它在流水线的哪一步生效,不能想当然。

而最后这一类**比直觉少得多** —— 最容易被想当然归进去的注意力后端,恰恰只有命令行一条路,见 10.3。

### 4.2 拼错的环境变量会被抓出来

有一个校验函数会遍历整个环境,凡是以 vLLM 前缀开头、但不在已知变量字典里的,就报警;另有一个开关能让它直接抛错而不是只警告。它的调用点在构造配置的第三行,很靠前。

所以像把注意力后端的变量名记错这种情况,你会看到一条「检测到未知的 vLLM 环境变量」,**而不是静默无效** —— 这一条对排障很有用,因为环境变量拼错是最难自查的一类错误。

### 4.3 环境变量默认参与编译缓存,想不参与要显式剔除

编译产物必须在「能复用」和「不能复用」之间划一条准确的线。做法是把影响计算图结构的配置摘成一个哈希,而环境变量这一侧的策略是:**先取全部已知变量,再从中剔除一份名单,剩下的全部参与哈希**。

被剔除的名单有五十余项,不止是路径与身份类:

| 被剔除的类别 | 例子 |
|---|---|
| 纯路径与身份 | 缓存根目录、配置根目录、主机地址、端口、对象存储凭证 |
| 日志 | 日志级别、前缀、输出流、配置文件、着色、统计间隔 |
| 超时 | 引擎迭代超时、连接保活、执行超时、各类媒体抓取超时 |
| 媒体缓存 | 媒体缓存开关、容量、存活时间、重试次数 |
| 用量统计 | 统计服务器地址、关闭统计、不追踪 |
| 调优缓存目录 | 调优配置目录、自动调优缓存目录 |

**「默认参与、显式剔除」这个方向选得很保守**:新增一个环境变量时,如果作者忘了考虑缓存,结果是多编译一次(安全),而不是复用了错误的编译产物(危险)。

### 5.2 默认值决议的四层瀑布

同一个字段的值可能来自四个不同的地方。**越靠下越晚执行,越晚执行的越优先**,但第 4 层内部还分两种截然不同的写法。

```text
第 0 层:配置类的字段默认值
  |  性质:静态常量。这一层的值经常不是你实际跑到的值
  v
第 1 层:硬件 / 平台 / 使用场景分档
  |  例:按显存容量三挡,再按离线还是在线分两种用法
  |  例:块大小由平台按注意力后端决定
  |  性质:只在第 0 层是空(或用户未给)时生效
  v
第 2 层:模型自身声明的能力
  |  例:分块预填充与前缀缓存取模型声明的支持情况
  |  性质:用户显式给了就不覆盖,但会警告
  v
第 3 层:用户显式指定
  |  来源:命令行 / 配置文件 / SDK
  |  性质:优先于第 0 至 2 层
  v
第 4 层:优化级别与全局覆写
     (a) 只填空白:逐字段调那个小工具,只在当前是空时写入
         -> 不会覆盖用户设置
     (b) 强制覆写:eager 开关、兼容性回退、KV 传输约束
         -> 会覆盖用户设置,只留一条日志
```

**第 4 层里 (a) 和 (b) 的区别是全篇最容易踩的坑。** 两个对照的例子:

- 你用点号语法指定了一个图模式,同时用的是默认优化级别 —— 默认级别恰好也是同一个图模式,但**即使不同**,走的也是 (a) 路径:那个小工具看到你已经写了值就跳过,你的设置保留。
- 你用点号语法指定了一个图模式,同时又传了 eager 开关 —— 走 (b) 路径,直接赋值清空,你的设置被丢弃。

差别不在参数本身,在它被写进去的**那一步是哪一类**。

### 5.3 批大小决议走一遍

以 2.5 那条命令为例,两张 80 GB 的 H100、在线服务场景、模型最大长度 32768,两个批大小参数用户都没给:

| 步 | 做什么 | 本例的结果 |
|---|---|---|
| 0 | 算并行规模 | 流水线并行 1 乘张量并行 2,等于 2 |
| 1 | 查分档表 | 显存约 80 GiB、设备名不含 A100,命中中间那档;在线服务取单步 8192、并发 1024 |
| 2 | 填单步 token 预算 | 用户没给,填 8192(若开了批量数据并行的专家并行,改用另一个更小的常量) |
| 3 | 填并发上限 | 用户没给,填 1024 |
| 4 | 性能模式若是吞吐优先 | 两个值各翻倍 —— **但只对用户没给的那个翻**;本例是默认的均衡模式,跳过 |
| 5 | 修正单步预算 | 关了分块预填充时抬到最大长度;多模态前缀语言模型抬到单个多模态条目的 token 数;最后夹一刀,不超过并发上限乘最大长度 |
| 6 | 夹取并发上限 | 不超过单步预算,取两者较小 |

本例第 5 步的夹取是 1024 乘 32768 与 8192 取小,仍是 8192;第 6 步是 1024 与 8192 取小,仍是 1024。最终:**单步预算 8192、并发上限 1024**。

第 4 步那个「只对用户没给的那个翻倍」的前提容易被漏掉 —— 它意味着吞吐模式下,你手动指定的那个值不会被翻倍,只有另一个会,两者的比例因此和你预期的不同。

### 5.4 同一条命令在两台机器上差四倍

把同一个模型放到一张 24 GB 的消费级卡上,分档表走「其余」那一档,在线服务取单步 2048、并发 256;第 6 步夹取后并发仍是 256。

**同样的命令行,两台机器上的实际调度容量差四倍。** 这就是「默认值必须标注来源层」的原因,也是 Part 4 的速查表不写单个数字的原因。

第 6 步那个夹取还有一个反直觉的后果:**并发上限的默认值永远不会超过单步 token 预算**。在小显存机器上给一个短上下文模型服务时,如果你手工把单步预算压到 128,并发上限会跟着掉到 128 —— 除非你也显式写了并发上限,这时第 6 步整块跳过。

### 5.5 配置哈希怎么决定编译缓存命中

这是 1.1 第四条痛点的另一半:**配置除了变成配置对象,还会产出一个你看不见的东西** —— 编译缓存目录。它决定了「这次启动能不能复用上次的编译产物」。

编译产物的复用边界由一个哈希决定,它由两部分拼起来:

```text
配置容器的哈希
  |
  +-- 版本号
  +-- 模型配置的哈希(精度 / 量化 / 架构)
  |     +-- 编译多模态编码器且确有多模态时,追加多模态配置
  +-- 缓存配置的哈希(块大小 / KV 数据类型)
  +-- 并行配置的哈希(张量并行与流水线并行度数)
  +-- 调度配置的哈希(单步 token 预算与并发上限)
  +-- 设备 / 加载 / 卸载 / 注意力配置
  +-- LoRA / 推测解码 / 结构化输出配置
  +-- profiler 配置
  |
  v
环境变量的哈希(见 4.3:默认全参与,显式剔除一份名单)
  |
  v
缓存目录名
```

**调度配置为什么必须进哈希**,源码注释给了两条理由,而讲清这两条正好解释了为什么这条边界不能靠直觉划:

1. LoRA 会按单步 token 预算创建静态缓冲区,张量的尺寸与步长被显式录进编译图。
2. 编译器按数据规模决定用 32 位还是 64 位的索引整数,单步 token 预算会影响这个判断。

并发上限同样进哈希,理由是另一类组件会按请求数分配静态缓冲区,形状一样被录进图。

**实践含义**:改单步 token 预算会让编译缓存失效并重新编译(几十秒到几分钟),改端口不会。反过来,如果你发现「什么都没改却每次都重新编译」,先怀疑是不是有个进了哈希的环境变量在变 —— 比如某些调度系统会注入随机的变量名。

## Part 6|机制之外:解析器与反射

**接下来三个 Part 放同一类东西**:照着源码读下来,机制层面看不见、但真实存在的细节。前面讲过的机制这里一概不重复 —— 四层瀑布、十二关、三态约定、分档表的数字前面都已经讲完。每条只答一件事:它是什么,以及**不知道它会怎么误判**。

这一个 Part 讲最前面那一段:命令行文本怎么被拆开,以及类型注解怎么变成参数定义。

> 每条对应源码的哪个文件与符号,见代码索引页,正文不写。

### 6.1 配置文件是展开成 argv,不是读进对象

处理配置文件最直觉的做法是「读 YAML,然后逐个赋值到对象上」。实现不是这样:它把 YAML **展开成一串命令行参数,插回原来的参数列表里**。

插入位置是精心选的:**配置文件的参数放在前面,命令行原有的参数放在后面**。标准库对同名参数是后者覆盖前者,于是「命令行优先于配置文件、配置文件优先于默认值」这条优先级**不需要额外实现,是插入顺序的自然结果**。源码注释直接写了这个优先级。

这个设计还有一个副作用:配置文件里的键**可以带也可以不带前导横线**,补齐由加载函数负责;而「配置文件里写了、命令行也写了」时,你在 `--help` 或报错信息里看到的是展开后的样子,不是你写的样子。

三条边界处理:配置文件参数只允许出现一次、后面必须跟文件名、子命令下模型名可以在位置参数里也可以在 YAML 的键里但两处都没有就报错。

### 6.2 点号参数的实现:折叠成一个 JSON 再塞回去

嵌套配置的字段有几十个,要在命令行里改其中一个,本来必须写完整 JSON。点号语法让你可以只写要改的那一项。

实现方式是:凡是以横线开头且含点的参数,按点切成第一段和其余段,造出嵌套字典;**同一个第一段的多个点号参数合并成一个字典**;最后把合并好的字典序列化成一个普通的 JSON 参数追加回参数列表。所以「写三个点号参数」和「写一个完整 JSON」在下游是同一个东西。

重复的点号键**会告警但不会报错**,语义是最后一次生效。这一条要记住:点号参数写重了不会拦你,只会在日志里留一行。

### 6.3 追加一个加号,值就当成列表

点号参数末尾可以带一个加号,含义是「把逗号分隔的值当成列表」:去掉尾部的加号,把值按逗号切开再序列化。没有加号时,值先试 JSON 解析。

这解释了一个容易困惑的现象:同一个字段,有时要写加号有时不用 —— 取决于它是不是列表类型,而命令行本身看不出来。

### 6.4 人类可读整数:大小写是两种进制

点号参数的值先试 JSON,失败再试人类可读整数,都失败就当字符串。所以 `80g` 这种写法在嵌套配置里到处能用。

但**非点号的普通参数不是这样**:可读整数是逐个白名单开启的,白名单里只有四个与批量和预取相关的字段,外加一个单独处理的最大长度(它还要接受「自动」这个取值)。所以给单步 token 预算写 `16k` 合法,给 LoRA 上限写 `2k` 不合法,会被整数解析直接拒绝。

还有一个细节值得记:**小写的 k/m/g/t 是十进制(一千进),大写的 K/M/G/T 是二进制(1024 进)**。这在算显存和字节数时差得不少。

### 6.5 帮助信息的顺序和注册顺序不一样

帮助信息经过一次按字母排序,参数名拼错时还会给出「最接近的合法参数」提示。两者都不影响运行语义,但它解释了一件容易困惑的事:**你在帮助输出里看到的顺序,和源码里注册的顺序对不上**,所以按帮助输出去源码里找一个参数会很费劲。

### 6.6 类型映射的判断顺序本身携带信息

2.2 给了五条反射规则。完整规则有十条,而且**是按顺序判断的**,顺序本身就是语义:嵌套配置类排最前,然后是「布尔或字符串或空」这种三态、纯布尔、固定取值、集合类型、整数、浮点、字典、字符串,最后兜底直接报「不支持的类型」。

排在前面的先匹配。所以一个既是布尔又带空值的字段,走的是三态那一档而不是纯布尔那一档 —— 前者生成的是「裸写开关得到真、带值得到字符串」,后者生成的是一对正反开关。**同样标着布尔,命令行行为不同,差别只在类型注解里有没有那个空值。**

最后两条是通用后处理:类型本身是固定取值时再走一次取值清单;类型里含空值且不是布尔时包一层可选类型并把「空」加进候选清单 —— 这就是「给某个参数显式传 None」这种写法能工作的原因。

### 6.7 三个实用推论

| 推论 | 说明 |
|---|---|
| **每个布尔参数都有一个反义词形式** | 即使文档只写了正面那个。想显式关掉某个开关,写它的反义形式,而不是给它传一个「假」字符串 |
| **读取默认值会真的执行工厂函数** | 对配置容器这种字段,工厂函数就是配置类的构造过程,构造时会打日志。所以那一步被一个抑制日志的上下文包住 —— 否则每次求助都会喷一屏初始化日志 |
| **帮助文字的权威出处是字段下方的文档字符串** | 想知道某个参数的官方解释,最可靠的地方是配置类里字段下面那段文字,而不是搜文档站 |

第一条最常用:关掉一个默认开启的特性,写反义形式才有效。

### 6.8 反射结果被缓存,但每个调用方拿到的是副本

反射本身挂了一个容量三十的缓存,而外层入口在返回前做一次深拷贝。

这是必要的:调用方经常要在拿到结果后改几笔(比如给某个参数额外加一个短选项)。**没有这次深拷贝,一处改动会污染缓存,影响后面所有调用方。**

### 6.9 参数组的边界就是求助输出的分节

参数被分进十五个组。这个分组不只是代码组织 —— **它同时就是求助输出里的分节**,因此是查参数时最有用的索引:先想清楚你要找的东西属于哪个配置对象,再去那一节里找,比全文搜快得多。

组和配置类基本一一对应,只有两处不是:卸载那组由两个配置类共同供给;最后一组对应配置容器本身,装的是推测解码、KV 传输、优化级别、性能模式这些跨对象的参数。

### 6.10 数据并行那组是「默认值看配置类」的唯一例外区

全篇的规则是「默认值的唯一真实来源是配置类的字段定义」。**有一处例外**:数据并行组里有一批参数是手写注册的,没走反射。

它们在命令行层面的默认值大多是空,只有后端那一个写了具体值;真正的兜底发生在构造配置时那一大段数据并行校验里。所以查这几个参数的默认值,要看参数注册处而不是配置类 —— 和全篇其余地方**正好相反**。

## Part 7|机制之外:构造顺序与覆写链

上一个 Part 停在「参数被解析出来了」。这一个 Part 讲之后发生的事:十几个配置对象按什么顺序构造,以及那条会改掉你设置的覆写链具体改了什么。

### 7.1 提升字典的十处,和唯一一处「给了细节就自动开总开关」

用 SDK 时传字典比构造配置对象方便,所以初始化后处理会把**十个**字段挨个检查:是字典就用它构造对应的配置对象。

其中一个有额外副作用:**用户给了容错的细节配置但没开容错总开关时,引擎会自动把总开关打开并打一条警告**。这是全篇少见的「给了细节配置就自动开总开关」的设计 —— 其他配置都不这样,比如给了专家负载均衡的细节配置不会自动开它的总开关。

不知道这一条,你会在「我只是想看看这个配置长什么样」的时候意外把一个功能打开。

### 7.2 插件在一切配置构造之前加载

初始化后处理的末尾做三件事:把量化的简写和结构化描述合成一个对象;**加载插件**;离线模式下把模型标识换成本地缓存路径(云存储地址跳过)。

中间那件事的位置很关键:**插件早于任何配置对象的构造就被加载**,所以插件可以注册新的模型架构、新的量化方法、新的平台 —— 这些东西在后面构造配置时就已经是「已知的」了。位置晚一点,这套扩展性就不成立。

### 7.3 构造顺序里三个值得单独记住的点

5.1 给了十三步的顺序。三个点在那张图上看不出来:

**缓存配置在并行配置之前构造,但块数不在这一步定。** KV cache 的实际块数要等 worker 侧实测显存才知道,所以那个字段被标成「不参与构造」的后填字段。配置阶段只定「占多少比例显存」,不定「多少个块」。块数怎么量出来,03 章 3.4 已经讲完。

**KV cache 的数据类型在配置阶段就被解析成具体值。** 用户写的「自动」在这一步被换成实际类型,传进缓存配置的是解析后的字符串。所以在 worker 里读到的那个字段**永远不会是「自动」** —— 想在 worker 里判断「用户有没有显式指定」是做不到的。

**特性支持性检查只查一件事**:流水线并行度大于一时,执行器后端必须支持流水线并行。名字听起来像一道通用检查,实际只有这一条。

### 7.4 数据并行的校验占了最长的一段

构造配置里最长的一段是数据并行的一致性校验,一百三十多行。原因是数据并行的启动组合太多 —— 内部负载均衡、外部负载均衡、混合模式,各自再乘单机与多机、乘两种执行后端。

**而很多组合的错误只有在真跑起来死锁时才暴露**,所以宁可在配置阶段就拦下来。这解释了为什么这一段的代码密度和它在机制里的分量完全不成比例。

### 7.5 三态的两条警告各自带一个前提

3.1 说三态的后两种情况「照做但打警告」。**那条警告什么时候真的会打,带一个模型类别的前提**:

| 用户给的值 | 模型能力 | 额外前提 | 结果 |
|---|---|---|---|
| 显式要关 | 支持 | 是生成类模型 | 照关,打警告 |
| 显式要开 | 不支持 | 是池化类模型 | 照开,打警告 |
| 其余组合 | —— | —— | 照做,**一条警告都没有** |

倒过来读才看得出要害:**一个生成类模型不支持分块预填充、你却强行打开,这条路径上没有任何警告。** 值照样按你说的设,引擎可能崩溃或产出错误输出,而日志里什么都没有。前缀缓存那一侧同样只对池化类模型打警告。

排障时不要把「没有警告」当成「配置没问题」。

### 7.6 唯一会覆盖用户显式设置的那条分支

三态的整套设计是「尊重用户 + 必要时警告」。**只有一处例外**:在 RISC-V 架构的 CPU 上,分块预填充与前缀缓存都被无条件关掉,各打一条信息级日志。

这是平台级的强制关闭,和 1.6 的强制覆写属于同一类。值得单独记一笔,是因为它是这两个开关唯一一处不讲道理的地方。

顺带一条同段的短逻辑:**只要给了推理解析器的名字,就会自动创建对应的配置对象**并把名字写进去。所以这两个参数是可以只给前者的。

### 7.7 模型自己也能改配置

排查「我明明设了某个参数却没生效」时,除了 5.2 的四层瀑布,还有第三条通路:配置容器的初始化后处理里有一步是「让模型自己改配置」的入口,改完会在模型配置上立一个「已被改写」的标记。

**某些模型 —— 尤其是混合注意力、MLA、Mamba 这几类 —— 会在这一步改块大小、注意力后端、CUDA Graph 模式。** 这条通路在参数表里完全看不见,因为它不属于任何一个参数。

### 7.8 一个不带前缀的环境变量能关掉整套编译

覆写链里有一步读的是 PyTorch 官方的编译禁用环境变量,置位时把编译模式清空,日志里写「这等价于把编译模式设成无」。

它的特别之处在于:**它不是 vLLM 自己的前缀**,所以 4.2 那道拼写校验抓不到它,它也不在环境变量声明表里。你在排查「为什么没编译」时,按 vLLM 的前缀去搜环境变量是搜不到它的。

同段还有一个小默认值:配置了 KV 传输但没给角色时,角色会被设成「收发都做」。

### 7.9 优化级别到底改了什么

优化级别有四档,默认是第三档;文档字符串明写最高那档「目前与第三档相同」。四档各自是一份默认值字典,**只覆盖三块内容**:编译配置里的一批融合开关、CUDA Graph 模式、图分割开关,加上 kernel 配置里的一个自动调优开关。

逐级对照的大致形状是:最低档全关且图模式置空;第二档打开基础的几个融合并把图模式设成分段;第三、四档在此之上再加通信与注意力相关的融合,图模式设成整图与分段并存。

关键在于**这些「开关」的取值不是布尔常量,而是函数**。写默认值的那个小工具支持「默认值本身是待求值的函数」,于是高档位的默认值可以依赖运行时信息 —— 比如某个融合只有当对应算子走了自定义实现(而不是让编译器自己融合)时才开;另一个融合要求并行度大于一、特定平台、装了特定库,**并且在批不变性开关打开时直接返回假**(源码注释说明融合后的通信加归一化不满足批不变性)。最后这条和「确定性推理」那一章讲的是同一件事。

### 7.10 表里写着「开启」,实际是常量假

上一节那张对照表有一处最容易误判:**三个高档位的融合开关,对应的不是函数,而是两个硬编码为假的常量**。源码里保留了注释掉的正确实现,并链接了一个 issue。

也就是说:表格里写着「第三档开启」,实际值是常量假,这三个优化**当前处于关闭状态**。

这一条的价值不在这三个开关本身,而在于它示范了一种读表方式:**对照表里的「开启」可能指向一个函数,也可能指向一个常量,两者在表上长得一样。** 要确认一个优化到底开没开,得看那一栏指向的东西是什么。

### 7.11 两个「只填空白」串起来,效果等同强制覆写

优化级别走的是「只填空白」的路径,所以它不会把你显式写的值改回去 —— 最低档配上显式指定的分段图模式,是一个可行的组合。

**但最低档仍然会在另一步把编译模式设成无。** 再往后有一步兼容性检查:发现图模式需要分段编译、却没有编译,于是把图模式打回空。

**两个「只填空白」的步骤串起来,效果等同于强制覆写** —— 而这类间接覆写只能靠读日志发现,日志里写的是「图模式与编译模式不兼容,已覆盖为无」。

由此也能说清一个常被混淆的区别:**最低优化档和 eager 开关不是一回事**。前者是第十一步与第十四步的填默认,后者是第七步的强制覆写,连捕获尺寸列表都清空。想要「完全不编译不捕图」,用 eager 开关更可靠。

## Part 8|机制之外:哈希、环境变量与请求级参数

这一个 Part 收尾三件事,它们的共同点是**都在配置对象之外**:配置算出来的那个哈希、环境变量表自身的结构,以及跟着每条请求走的那一小份参数。

### 8.1 CUDA Graph 捕获尺寸的上界是怎么算出来的

06 章 2.6 与 2.7 讲了有了桶之后怎么分桶、怎么做区间映射。**桶列表本身从哪来,在那一章之外**:

上界取两者较小 —— 「并发上限乘以单次解码的 query 长度再乘二」与一个按设备能力定的常量(数据中心级新架构是 1024,其余 512);之后再和单步 token 预算取一次较小。

用 2.5 那条命令代入:非新架构所以常量是 512,并发上限 1024,无推测解码所以 query 长度是 1 —— 第一次取小得到 512,第二次和 8192 取小仍是 512。**开推测解码会把第一项推高,但在这个例子里被平台常量卡住,看不出差别**;要在小并发的场景才看得出来。

尺寸列表本身有三条路:用户显式给了就去重、滤掉超过单步预算的、升序排列(**注意过滤阈值是单步 token 预算,不是上一步算出的那个上界**);性能模式是交互优先时,1 到 32 每个都捕,为小批量彻底消除填充浪费;否则走默认阶梯 —— 1、2、4,然后 8 的倍数到 256,然后 16 的倍数到上界,单步 token 预算若能塞进上界之内也会被单独追加,保证最大批量这个尺寸一定被捕到。

**捕获列表越密,填充浪费越小、显存与启动时间开销越大** —— 这就是交互优先模式的取舍,也是 1.4 说的「性能模式是叠加在分档之上的乘数」在另一侧的体现。

### 8.2 哈希的边界由一条给贡献者的规则划定

5.5 讲了哈希由哪些部分拼起来。**每个配置类自己实现这个方法,各自决定哪些字段算「影响计算图」** —— 这就把边界的判断分散到了各个配置类里。

判断依据写在一条文档字符串里,是给贡献者的规则:新增字段时必须判断它是否影响「从输入 token 到最终隐状态」这一段的图结构,影响就加进因子列表。

这条规则同时解释了边界:tokenizer 相关、采样相关、HTTP 相关的配置都不进哈希,**因为它们在这段区间之外**。最干脆的例子是结构化输出的配置 —— 它的因子列表是一个**空列表**,并配了一行注释说明这个配置不影响计算图。空列表不是忘了写,是显式声明「我确实什么都不影响」。

### 8.3 环境变量表的两段之间靠人工同步

环境变量文件是三段式:声明段只提供类型和「名义默认值」给编辑器和读者,**运行时不生效**;求值段才是每个变量一个求值函数、从环境读取并转换,**真正的默认值在这一段**;最后是工具段。

**两段之间靠人工同步。** 这是一个真实存在的漂移源:声明段写的默认值和求值段实际用的默认值可以不一致,而且不会报错。读环境变量的默认值时,要读求值段那一份。

### 8.4 一批环境变量是默认开启的,它们是逃生舱不是功能开关

容易误解的一点:**很多环境变量是默认开启的**,比如若干个 kernel 选择和多进程相关的开关。

它们的用法是「设零来关掉」,属于**逃生舱**而不是功能开关。排障时挨个关掉这些是有效手段 —— 但前提是你知道它们本来就是开的。按「环境变量默认关闭」的直觉去读,会把整批东西理解反。

### 8.5 前端参数的默认值偏向方便而非安全

HTTP 服务侧的参数不在引擎参数里,而在另一个文件的前端参数类里 —— 这是查参数时最容易找错地方的一处。

它的两个默认值值得单独提出来:**认证密钥默认为空**,意味着服务默认没有任何认证;**监听地址默认为空**,在这里的语义是绑定所有网卡。两者叠加,一个默认启动的服务对同网段是完全敞开的。

这不是缺陷 —— 它把认证责任交给了部署方。但**默认值的方向是「方便」而不是「安全」**,生产部署至少要做两件事之一:显式给认证密钥,或者只监听回环、走本地套接字再由反向代理接管认证。

### 8.6 一个同名环境变量,服务端也认

前一节那个认证密钥还有一个同名的环境变量。它容易被当成「客户端命令行读它去请求远端服务」的那一个 —— **但服务端同样会读它**:注册中间件时,命令行给的密钥优先,没给就回落到这个环境变量,源码注释就写着这条优先级。

这一条要记准,因为两个方向的误判都有代价:以为设了环境变量服务端不认,于是重复配置;或者以为服务端没认证,其实环境里早就有一个。

### 8.7 采样参数的「默认」还要再看模型自带的那份

07 章 5.1 列全了请求级采样参数的字段与默认值。**那张表给的是 vLLM 的中性默认,而它不一定是你实际跑到的值**。

引擎启动时会决定「这个部署的中性默认」来自哪里,有四档:用 vLLM 的中性默认;读模型自带的生成配置(**这是默认档**);读指定目录里的;以及在上述结果之上再额外覆盖一层。

能被模型那份覆盖的字段只有六个:重复惩罚、温度、两个截断参数、最小概率阈值,以及最大新增 token 数(它在两边的名字不同,会被改名对齐)。发生覆盖时会打一条警告,并告诉你想要中性默认就显式指定那一档。

**实践含义**:同一份客户端代码,请求里不带温度,打到两个不同模型上得到的实际温度可能不同 —— 因为两个模型自带的生成配置不同。要拿到可复现的「教科书默认值」,得显式把这一档设成 vLLM 的中性默认。**很多「换了模型输出风格突变」的问题根源就在这里**,而它在任何参数表上都看不出来,因为它不是某个参数的值,是那张表本身被换掉了。

## Part 9|参数速查:先看这四张表

### 9.1 这一部分不打算给你一张全表

按惯例,最后一部分该是一张覆盖所有参数的速查表。**这里不这么做**,有三个理由:

1. **和全章的论点冲突。** 1.1 讲的就是「把参数当一张表来记会翻车」,末尾再给一张表等于自己拆自己的台。
2. **和别的章重复。** 调度那组的参数 02 章讲过怎么调、KV cache 那组 03 章讲过、注意力后端 05 章、CUDA Graph 06 章、推测解码 08 章、量化 11 章、结构化输出 12 章、多模态 13 章、LoRA 14 章 —— 它们回答的是「调这个参数会怎样」,那是各自章节的主场。
3. **全集本来就有更好的出处。** 每个配置类的字段远多于任何一张表能列的,而字段下方的文档字符串就是官方说明(6.7)。要全集,读配置类。

所以这一部分只收**别处没有、也只有读完这条流水线才答得出来的东西**:哪些参数的字面默认值不是你实际跑到的值、哪些名字根本不存在、哪些只能走 JSON。

**三条读法约定:**

- 说「默认值」时指配置类字段定义里那个值,也就是 5.2 的第 0 层。**凡是这个值在运行时会被改写的,下面单独标出并说明是第几层改的。**
- 布尔参数一律有反义形式(6.7),不重复列。
- 参数名用命令行形式;它在配置对象上叫什么、在哪个文件,见代码索引页。

这是本章最该被记住的一张表 —— 它把 5.2 的四层瀑布落到了具体参数上。**下面每一个参数,你在文档里看到的默认值都不是你实际跑到的值。**

倒数第三条最容易错:很多人按「张量并行度、流水线并行度」的类比去找「专家并行度」,**而它不是一个度数**。

### 9.5 只能走 JSON 或点号的那些

有一批配置没有散装的命令行参数,**整个配置对象只有一个 JSON 入口**:推测解码、KV 传输、KV 事件、权重热更新、容错、profiler、编码器缓存管理与传输、专家负载均衡、算子优先级。

编译配置是个中间态:它有一个 JSON 入口,同时**每个字段都能用点号形式单独设**(6.2),这是最好用的形态。注意力配置也类似,但只有后端那一个字段另有独立的短路径。

一个实用推论:**看到一个字段在文档里但命令行上找不到,先想它是不是某个 JSON 配置的内部字段**,然后用点号形式试。

## Part 10|参数速查:按组过一遍

上一个 Part 的四张表是横着切的(按「哪里容易错」分)。这一个 Part 竖着切一遍(按参数组分),每组只写三样:入口是什么形态、这组里哪些值会被改写、哪些名字容易记错。

### 10.1 模型与加载:两处值得单独记

这一组的参数最多,但绝大多数是直白的。两处例外:

**信任远程代码这个开关会执行模型仓库里的 Python 代码**,只对可信来源开。它是这一组里唯一有安全含义的参数。

**加载格式的枚举里没有 bitsandbytes 相关的格式**,本仓库也没有对应的加载器。想按别处文档里写的那样指定它会直接失败 —— 这是 15 章讲的加载器家族在参数侧的投影。

### 10.2 调度与 KV cache:两个查不到的字段

调度那组的调参口径 02 章 9.3 已经讲全,KV cache 那组 03 章 7.3 讲全,这里只补两件事。

**有两个字段不可从命令行设**,它们被标成「不参与构造」,并在初始化后处理里**双双被赋成单步 token 预算**:一个是编码器单步输入上限,一个是编码器缓存容量。

这就是 13 章说的「编码器缓存容量跟着批大小走」的来源 —— **想给多模态编码器更多缓存,唯一的旋钮是调大单步 token 预算**,没有专门的参数。

另外几个 02 章那张表没收、但实际会调的:每几步才允许调度一次预填充(调大可保护解码延迟)、为完整输入长度预留、每几个 token 推一次流式输出(请求级可覆盖)、禁止把一个多模态条目切开跨步。

KV cache 侧则有一组运行时后填字段:GPU 与 CPU 的块数、KV cache 能装多少 token、最大并发、布局。**启动日志里那句「GPU KV cache size: N tokens」就是其中一个字段** —— 它不是算出来给你看的,是记录下来的。

### 10.3 参数与环境变量的对应关系有一处例外

4.1 说过少数参数「两条路都有」。**注意力后端不是其中之一** —— 它只有命令行这一条路,没有对应的环境变量。

这一条值得单独拎出来,因为它是最容易被想当然归错的:按「kernel 级选择走环境变量」的分类直觉,注意力后端看起来最该有一个环境变量,而它恰恰没有。想在不改命令的前提下换后端,做不到。

反过来,真正「两条路都有」的是前缀缓存保留间隔、多模态哈希算法、编译缓存保存格式这几个不起眼的。

### 10.4 并行:数据并行那组的参数最多也最容易配错

并行是参数最多的一组,而其中数据并行的组网参数又占了大半。6.10 讲过它们是手写注册的、默认值要看参数注册处。这里补它们**互相之间的约束**:

| 约束 | 内容 |
|---|---|
| 外部负载均衡与混合模式 | 互斥,不能同开 |
| 多节点时 | 后端必须是多进程那种 |
| 无头模式下 | 混合负载均衡不可用 |
| 给了本节点 rank | 就进入外部负载均衡模式,而且非 MoE 模型不支持 |
| 所有节点 | 远程调用端口必须一致 |

这些约束就是 7.4 说的那一百三十行校验在做的事。它们全都是**配置阶段就能拦下、跑起来才暴露就是死锁**的那一类。

### 10.5 量化:一个字符串表达不了的事

量化没有独立的参数组,入口只有三个,散在模型与缓存两组里。合法的方案名由一个字面量类型唯一定义,**共 30 个取值**。

值得记的是那个结构化描述的存在理由:它的结构是线性层与 MoE 层各一份规格,外加一个忽略列表。**这允许对线性层和 MoE 层用不同的量化方案** —— 而一个字符串简写表达不了这件事。所以两个入口不是冗余,是表达力不同。

KV cache 的量化是独立的另一个参数,**和权重量化互不影响**。

### 10.6 推测解码与 LoRA:配置形态的两个极端

推测解码是「一个 JSON 装全部」的典型:除了方法、模型、token 数三个短参数,其余二十来个字段只能写在 JSON 里。**而它还有一处自动行为**:如果给的模型本身就是一个推测器权重,引擎会把模型改写成它的目标模型并自动填好推测配置(云存储地址跳过这个探测)。机制细节在 08 章。

LoRA 正好相反,几乎全是散装参数。它这一组要注意的是**不开总开关时整个配置对象是空的**,要开了才构造 —— 所以「我设了 LoRA 的某个参数但没生效」,先看总开关。

LoRA 还有四个环境变量值得知道:一个开运行时热加载的 HTTP 端点,两个配置按名字自动拉取,还有两个是 kernel 层开关。

### 10.7 多模态:限制媒体规模的旋钮不在命令行

多模态这一组的参数很多,但**生产环境最该配的那几个不在这里** —— 图片、视频、音频的抓取超时,单次下载大小上限,最大像素数,媒体缓存容量,是否允许跳转,**全都是环境变量**。

这是 4.1 那张分工表的一个具体印证:这些是「要传给子进程」和「出问题时要能不改命令就绕过」的性质,所以走环境变量。想限制用户提交的媒体规模,改这些,不是改命令行。

### 10.8 编译与 kernel:两个全局旋钮加一堆点号字段

这一组有两个全局旋钮:优化级别(7.9)和性能模式。性能模式有三档,**它同时影响批大小(乘数,见 5.3 第 4 步)和捕获尺寸(交互档改成 1 到 32 全捕,见 8.1)** —— 一个参数管两处,而两处在源码里离得很远。

编译配置的字段几乎全都会被第 4 层改写,9.2 那张表里占了一半。其中一个细节:自定义算子清单**总会被追加**一项,追加的是「全不开」还是「全开」取决于编译走哪条路。

至于运行器的选择,它**没有命令行开关**,只有一个默认为空的环境变量,空表示自动判断。自动判断的链路是:有水印配置就强制用新运行器(用户设了关也会被覆盖并打日志);否则环境变量给了就听它;否则依次检查平台与架构、有没有装 Triton、有没有用到新运行器不支持的特性,任何一项不满足就回落。

### 10.9 权重卸载:和 KV 卸载是两套东西

卸载这一组由三部分组成:一个后端选择,一套「把权重放 CPU、由 GPU 直接寻址」的配置,一套预取配置。

**要紧的是别和 KV cache 的卸载搞混** —— 那是另一组参数、另一套机制,03 章讲的是它。两者名字相近、都叫「卸载」,但一个搬的是权重、一个搬的是 KV。15 章也为这个术语做过一次消歧。

这一组还有三个环境变量:两个是权重卸载侧的逃生舱(禁用锁页内存、禁用统一寻址),一个管 KV 卸载的批描述符上限。

### 10.10 可观测性:几个只在排障时才用的开关

这一组全是默认关闭的观测开关,平时不用管。四件事值得知道:

**请求日志的方向是反的。** 默认**不打**请求日志,要打就显式开;**不存在关闭它的那个参数**。按「默认打开、需要时关掉」的直觉去找,会找不到。

**JIT 监控能抓「本该编译好却在跑时编译」。** 它有两档,调到报错档时运行期一旦发生即时编译就直接抛错 —— 这是排查「为什么第一次请求特别慢」「为什么偶发卡顿」的直接手段。

**KV cache 的那几个指标默认只按 1% 采样。** 读绝对计数之前要先看采样率,否则会把数量级看小两个数量级。04 章记过这一条。

**profiler 选 proton 时有两条硬约束**:必须是 CUDA 平台,且 CUDA Graph 必须关掉 —— 任一不满足**直接抛错**,不是降级。这是配置校验里少见的硬失败。

### 10.11 HTTP 服务侧还有四个防御性上限

8.5 讲了前端参数的默认值偏向方便而非安全。补一组容易被忽略的:服务端有**四个纯防御性的上限**,全是环境变量 —— 单请求最多几条序列、补全接口最多几个 prompt、最多几个停止串、最多几个禁词。

它们不是功能开关,是**用来挡「一个请求里塞一万个停止串」这类放大攻击的**。默认值已经给得相当宽,真要收紧得自己改。

另外两个生产环境明确不要开的:开发模式端点(开了会暴露调试接口)、不安全的序列化开关。

### 10.12 日常真正会用到的环境变量

声明了两百多个,日常会碰到的不到三十个。按用途分组:

| 用途 | 变量 | 值得记的点 |
|---|---|---|
| 看默认值怎么决议的 | 日志级别 | 调到调试档才能看到批大小与两个三态开关的决议过程 |
| 超时 | 单步超时、启动就绪超时、执行超时 | **加载大模型时要调大启动就绪超时**,否则还没加载完就判失败 |
| 路径 | 缓存根目录、配置根目录、模型重定向表 | **配置根目录不是缓存根目录的子目录**,两者分别在各自的惯例位置 |
| 进程 | worker 多进程方式、V1 多进程开关 | 前者与某些库冲突时改成另一种;**后者关掉可让引擎跑在主进程里,便于打断点调试** |
| 确定性 | 批不变性总开关、浮点矩阵乘精度 | 前者是「确定性推理」那一章的主角 |
| 编译 | 禁用编译缓存 | 怀疑缓存脏了就开 |
| kernel 逃生舱 | 若干默认开启的 kernel 选择开关、按名字禁用 kernel | **这些默认是开的,用法是设零关掉**(8.4) |
| 抓问题 | 检查 logits 里的 NaN、意外同步点检查、引擎挂了保留进程 | 最后一个便于事后检查现场 |

还有一个**不带 vLLM 前缀**的:PyTorch 官方那个编译禁用变量。7.8 说过它绕开了拼写校验,这里再强调一次 —— **它不在任何 vLLM 的变量清单里**,排障时按前缀搜是搜不到的。

## Part 11|决策:排障、场景与优先级

前面都在讲「是什么」。最后这个 Part 讲「怎么办」:参数没生效怎么一步步查、典型场景里哪个决定最容易配错、调参该从哪一层开始。

### 11.1 误区:只有读完这条流水线才答得出的那些

误区表里绝大多数条目,前面的 9.2 到 9.4 三张表已经答过了(默认值被改写、反直觉默认、不存在的名字)。这里只留**必须理解流水线才能答对**的那几条:

| 误区 | 真相 |
|---|---|
| 最低优化档和 eager 开关等价 | 不等价。eager 是强制覆写且清空捕获尺寸;最低档只是填默认,**而且能被点号参数部分抵消(但会触发兼容性回退)**,见 7.11 |
| 某个优化级别会覆盖我手写的点号设置 | 不会。优化级别走的是「只填空白」,见 3.3 与 5.2 |
| 高档位表里写着开启的融合项都真的开了 | 有三项是硬编码的常量假,见 7.10 |
| 改端口会导致重新编译 | 不会,端口在剔除名单里;但改单步 token 预算**会**,见 5.5 |
| 给了细节配置就会启用对应功能 | 一般不会,**只有容错那一个有「自动开总开关」的特例**,见 6.10 |
| 布尔参数要写「参数 False」 | 写反义形式,见 6.7 |
| 不带温度的请求一定用 1.0 | 默认取模型自带的生成配置,换模型可能变,见 8.7 |
| 编码器缓存大小可以单独配 | 不能,它等于单步 token 预算且不可从命令行设,见 10.2 |

这张表和 9.2 到 9.4 的分工是清楚的:那三张回答「这个值是什么」,这一张回答「这件事为什么是这样」。

### 11.2 参数没生效怎么查

这是全章的收口。**按代价从低到高**,八步:

**第一步,确认参数名存在。** 拼错的参数解析器会报错并提示最接近的合法名,所以「没报错」至少说明名字对。**但拼错的环境变量不会阻止启动**,只打一条警告 —— 怀疑是环境变量问题时,把那个开关打开让它变成硬错误。

**第二步,看启动日志里的最终配置。** 配置容器有一个字符串化方法,会把关键字段打成一行。**这是「引擎实际用了什么」的权威来源,比任何推理都可靠。**

**第三步,把日志级别调到调试档。** 两组决议只在这一档打印:两个三态开关的默认值来源、批大小的最终值与使用场景。

**第四步,搜「覆写」类日志。** 下列消息意味着你的设置被改了:

| 日志说的 | 谁改的 |
|---|---|
| eager 已设置,禁用编译与 CUDA Graph | 1.6 的强制覆写 |
| 图模式与编译模式不兼容,已覆盖为无 | 7.11 的间接覆写 |
| 编译禁用变量已设置,禁用编译 | 7.8 的那个不带前缀的变量 |
| 编译被用户设置关闭,只在编译期生效的优化将被忽略 | 同上的连带效应 |
| eager 模式下 CUDA Graph 已禁用 | 1.6 的第二段 |
| 某某要求,把图模式覆盖为分段 | KV 传输侧的约束触发 |
| 该模型不官方支持…… | 7.5 的三态警告(注意它带 runner 类别前提) |
| 发现重复的键 | 6.2 的点号参数写重了 |
| 检测到未知的 vLLM 环境变量 | 4.2 的拼写校验 |

**第五步,定位是哪一层改的。** 按 5.2 的四层顺序自查:是不是模型在「模型可以改配置」那一步改的(换一个同类模型试,行为不同就是这层,见 7.7)?是不是平台默认改的(换硬件,或读对应平台的实现)?是不是优化级别填的(显式指定最低档对比)?还是被强制覆写了(第四步的日志会说)?

**第六步,看是不是三态语义问题。** 如果你传的是「假」或零,而这个参数是三态的,检查一下你是不是想表达「不设置」却表达成了「显式关闭」—— **空与假在只填空白那一步的待遇完全不同**(3.1、3.3)。

**第七步,编译缓存。** 改了参数但行为完全没变(尤其是 kernel 层面的),试着禁用编译缓存,排除复用了旧图。反过来,每次都重新编译,就检查有没有变动的环境变量进了哈希(5.5)。

**第八步,读配置类里字段下方的文档字符串。** 那就是求助输出的内容来源(6.7),**而且比任何二手文档都新**。

八步的顺序不是随意的:前两步几乎不花时间,第三四步只要重启一次,第五步开始才需要动手做对照实验。

### 11.3 场景组合里,那些只有读完本章才知道的决定

按场景给一份配置模板意义不大 —— 具体数值取决于负载,得压测。但每个典型场景里,**都有一个「不读这一章就会配错」的决定**:

| 场景 | 那个决定 |
|---|---|
| 单卡离线批量 | **通常不需要手调批大小** —— 离线场景的分档默认已经是最大的那一档(1.4) |
| 单机多卡在线服务 | 一旦**显式**给了并发上限,5.3 第 6 步的夹取整块跳过,单步预算保持分档值 |
| 低延迟交互 | 交互档让 CUDA Graph 把小尺寸逐个捕获,代价是捕获时间与显存(8.1);再配合调大预填充间隔保护解码延迟 |
| 多机 | 节点数大于一时**强制要求多进程后端**,且总并行规模必须能被节点数整除;跨机链路慢时要调大分布式超时,否则初始化阶段就超时 |
| MoE 加专家并行 | 专家并行是开关不是度数(9.4);**负载均衡必须显式开,给了它的细节配置不会自动开它**(6.10 的反例) |
| PD 分离 | 解码侧要显式把拉取失败策略设成重算,否则默认是让请求失败(9.3);另外 KV 传输会把图模式降级成分段,这是预期行为 |
| 多 LoRA | 并发数是 GPU 槽位数,CPU 侧另有一个容量;**运行时增删适配器还要额外开一个环境变量** |
| 视觉多模态 | 每模态条目上限是**收紧**默认值而不是放开(9.3);而单步 token 预算在这里要留足 —— 它同时是编码器缓存的容量(10.2) |
| 结构化输出 | 后端默认是自动挑选,一般不需要手工固定 |
| 确定性复现 | 除了批不变性开关,还要把生成配置显式设成中性默认,**排除模型自带那份的干扰**(8.7);批不变性会连带禁用十余项优化,是拿吞吐换可复现性 |
| 配置文件 | 键可带可不带前导横线;**同时给位置参数模型名和文件里的模型名时,位置参数胜出** |

### 11.4 调参优先级:按「改错了会不会跑不起来」排序

| 层 | 参数 | 性质 |
|---|---|---|
| 1 | 并行度、量化、最大长度、显存占比 | 改错了是启动失败或显存溢出,**反馈明确** |
| 2 | 批大小两项、性能模式 | 决定吞吐与延迟的量级。**默认值已经按硬件调过,盲目手调常常不如默认** |
| 3 | 长预填充阈值、预填充间隔、调度策略、流式间隔 | 不影响总吞吐,只影响首 token 与 token 间延迟的分布 |
| 4 | 优化级别、图模式、捕获尺寸 | 默认档已经是全量优化,**主要用途是排障时降级,不是加速** |
| 5 | 按场景启用的功能 | 推测解码、LoRA、多模态、PD 分离、结构化输出,各有各的显存与延迟代价 |
| 6 | kernel 级逃生舱 | 只在怀疑某个 kernel 有问题时用,日常不要设 |

第 2 层和第 4 层最容易被误用:前者因为「默认值看起来像随便填的」而被手调,后者因为名字像「优化」而被当成加速手段。

### 11.5 一条贯穿全章的原则

**vLLM 的默认值不是「随便填的中间值」,而是按硬件与场景查表算出来的**(5.3 走了一遍完整过程)。

由此得出调参的正确起点:**先跑默认,压测,再针对瓶颈改一个参数** —— 而不是照抄一份别人的长命令行。别人命令行里的参数,一半可能在你的硬件上会被第 1 层默认值算得更好,另一半则可能压根不是当前代码里的参数名(9.4)。
