# vLLM 03|PagedAttention 与 KV Cache 管理

KV cache 是推理显存的大头,管不好就直接压住并发。这一章讲清它为什么必须存在、朴素地存会浪费在哪、vLLM 用分页怎么救回来,以及这套账在真机上怎么算。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与方法,见代码索引页;正文不写路径与行号。

## Part 1|原理:不缓存要重算,缓存了显存又成瓶颈

### 1.1 不缓存 K/V:每生成一个 token 都在重算全部历史

Transformer 自回归生成时,每出一个新 token,attention 层要拿当前 token 的 Q 去和**所有历史 token 的 K** 做点积,再用得分加权历史的 V。

如果不把算过的 K/V 留下来,生成第 N 个 token 时就得把前面 N−1 个 token 的 K/V 投影重算一遍。整段生成下来,K/V 投影的总次数是 1+2+…+N:

$$\sum_{i=1}^{2048} i = 2{,}098{,}176$$

生成 2048 个 token,K/V 投影要算两百万次 —— **每个 token 的 K/V 平均被重复算了 1024 次**。

**KV cache 就是为此存在的**:每步算出的 K/V 存进显存,下一步直接读,不重算。总次数从 O(N²) 落到 O(N) —— 生成 2048 个 token 就只算 2048 次。

### 1.2 缓存的到底是什么:只有 K 和 V

「把算过的存下来」听着简单,但存什么、存多少,直接决定了后面所有的显存账。这一节先把对象定清楚。

KV cache 存的不是 token id,也不是 embedding,而是**每个 token 经过每层 attention 的 K 和 V 投影后的向量**。

一个 token 进到某一层,embedding 会被三个权重矩阵各投影一次,得到 Q、K、V。之后 attention 拿 Q 和全部历史 K 算分,再用分数加权全部历史 V。**三个里只有 K 和 V 进 cache**:

| | 是什么 | 缓存吗 | 为什么 |
|---|---|---|---|
| Q | 当前 step 这个新 token 的查询向量 | 否 | 每步都换一个新 token,历史的 Q 再也用不上 |
| K | 历史 token 的「被查询」编码 | **是** | 每一步都要和全部历史 K 做点积 |
| V | 历史 token 的「被取用」编码 | **是** | 每一步都要按分数加权全部历史 V |

所以 KV cache 的本质是**一份只增不改的历史编码**。这一点后面会反复用到:正因为它只增不改、且内容完全由「前缀 token 序列」决定,同样的前缀才能在请求之间共享。

### 1.3 这笔交换为什么划算

KV cache 是典型的**用空间换时间**:拿 GPU 显存换 GPU 算力。

| | 没有 KV cache | 有 KV cache |
|---|---|---|
| K/V 投影计算 | O(N²),每步重算所有历史 | O(N),每步只算 1 个新 token |
| 显存占用 | O(1),不存历史 K/V | O(N),存所有历史 K/V |
| 每步 attention | O(N),Q 乘所有 K | O(N),Q 乘从 cache 读的 K |
| 瓶颈 | 算力(compute-bound) | 访存(memory-bound) |

但「省了计算」这句话得拆开看,否则容易得出错误的直觉:

**① decode 阶段本来就卡在访存,不卡在算力。** 每步只算 1 个 token 的 Q/K/V 投影,计算量极小;而 attention 要读所有历史 K/V,访存量随序列长度线性涨。真正的大头是 attention 的 QKᵀ 点积,那部分缓不缓存都要算。

**② 重算 K/V 投影比读 cache 贵一个数量级以上。** 以 Llama-3-70B 单层为例:K 投影是一次矩阵乘,hidden 8192、GQA 8 个 KV head、head_dim 128,所以 W_K 的形状是 [1024, 8192],重算一个 token 的 K 与 V 投影合计约 33.6 MFLOPs;而读一个 token 的 K+V cache 只要 4096 字节。按 ~1000 TFLOPS 算力、~3 TB/s 带宽估,重算约 34 ns,读 cache 约 1.4 ns —— **差二十多倍**。

**③ prefill 阶段一分钱都不省。** prefill 是一次性算完所有 prompt token 的 K/V,计算量本来就是 O(N),不是逐 token 生成。**KV cache 省的只有 decode 阶段的重复计算**。

### 1.4 代价:显存成了新的瓶颈

缓存的代价是显存。每 token 的 KV cache 大小:

$$\text{KV size per token} = 2 \times n_{\text{layer}} \times n_{\text{kv head}} \times d_{\text{head}} \times \text{dtype\_size}$$

以 Llama-3-70B(FP16、80 层、GQA 8 个 KV head、head_dim 128)算:每 token 是 2 × 80 × 8 × 128 × 2 = 327,680 B ≈ **320 KB**。

这 320 KB 是**整模型 80 层的总量**。TP=8 时 KV head 也被切开,单卡只承担八分之一。做显存核算时必须先统一口径,否则会差 8 倍:

| 口径 | 每 token KV | 单请求(2048 token) | 并发 100 请求 | 同口径的权重 |
|---|---|---|---|---|
| 整模型(8 卡合计) | 320 KB | 640 MB | 64 GB | 140 GB |
| 单卡(TP=8) | 40 KB | 80 MB | 8 GB | 17.5 GB |

单卡上 100 并发的 KV cache(8 GB)还不到权重(17.5 GB)的一半,看着不吓人。但**权重是常量,KV cache 随并发和序列长度线性增长** —— 并发提到 400、或平均长度翻到 8192,KV cache 就反超权重了。

于是问题从「要不要缓存」变成了「这几十 GB 怎么管」。

### 1.5 朴素管理这几十 GB:三种浪费

朴素做法是给每个请求**预先分配一块连续显存**,大小按最坏情况算:`max_model_len × 每 token KV 大小`。三种浪费随之而来。

**① 内部碎片:预留了但没用上。** 请求实际生成的 token 数远小于 `max_model_len` 时,预分配的空间大量闲置:

```text
GPU 显存:
┌──────┬─────────────┬─────────────┬─────────────┬─────┐
│ 权重  │ Req A(2048) │ Req B(2048) │ Req C(2048) │ ... │
└──────┴─────────────┴─────────────┴─────────────┴─────┘

请求 A 实际只生成 100 token:
┌──────┬─────────────┬─────────────┬─────────────┬─────┐
│ 权重  │▓░░░░░░░░░░░░│ Req B       │ Req C       │ ... │
└──────┴─────────────┴─────────────┴─────────────┴─────┘
        ↑ 100 token 用,1948 token 白占
```

对话类负载的平均输出长度通常只占 `max_model_len` 的一小部分(具体比例取决于业务,要按自己的日志统计),所以这部分往往是主要的浪费。

**② 外部碎片:总量够但拼不出连续块。** 空闲显存被已分配的请求切得东一块西一块,总和有 4000 token 的空间,新请求要 3000 token 的**连续**空间却分不出来。

**③ 无法共享:公共前缀被存了很多份。** 多个请求共享同一段 system prompt 或 few-shot 示例时,朴素管理下每个请求都存一份完整的 KV,内容完全相同却各占各的。

## Part 2|分页:把逻辑连续和物理连续拆开

### 2.1 PagedAttention:把「逻辑连续」和「物理连续」拆开

这三种浪费在操作系统里是老问题,答案也是现成的:**分页**。PagedAttention 的灵感直接来自虚拟内存。

| OS 虚拟内存 | PagedAttention |
|---|---|
| 进程看到连续的虚拟地址空间 | 请求看到连续的 token 序列(逻辑位置 0,1,2,…) |
| 物理内存按 4 KB page 分配 | KV cache 按 16-token block 分配 |
| page table 映射虚拟 → 物理 | **block table** 映射逻辑 token → 物理 block |
| 按需 page-in / page-out | 按需 allocate / free block |
| 多进程共享内存 page | 多请求共享 KV block(prefix caching 的基础) |

**核心思想:把「逻辑连续」和「物理连续」解耦。** 请求看到的 token 序列在逻辑上仍然连续,底层的物理 block 可以散落在显存任何位置,由 block table 维护映射。

三种浪费于是逐一消解:按需分配,内部碎片最多只剩最后一个没填满的 block;不要求连续,外部碎片消失;block 可以被多个 block table 同时指向,前缀天然能共享。

**代价有两处**:一是多了一层间接寻址,attention kernel 必须能消费 block table,不能再假设 K/V 在显存里连续;二是多了一套记账逻辑(谁在用哪个 block、引用计数、什么时候回收),这套账就是后面 block 池在做的事。

### 2.2 block table:一次查表、两步定位

解耦之后,「第 37 个 token 的 K/V 在显存哪里」就不再是一次加法能回答的了。每个请求配一张 block table,存的是它按逻辑顺序用到的物理 block id:

```text
请求 A:已生成到第 100 个 token
逻辑位置:  0 1 2 ... 15 │ 16 17 ... 31 │ 32 ... 47 │ ... │ 96 ... 100
                         │              │           │     │
block_table: [    5      ,      12      ,     8     , ... ,    3    ]
                  ↑              ↑            ↑                ↑
             物理 block#5   block#12     block#8         block#3
             (token 0-15) (token 16-31) (token 32-47)  (token 96-111,后 11 个空)
```

attention kernel 要定位逻辑位置 `pos` 的 K/V,做两步:

1. **查表**拿物理块号:`block_table[pos // block_size]`
2. **算块内偏移**:`pos % block_size`

block table 是 PagedAttention 的核心数据结构。它在 GPU 上是一个 int32 的二维张量,行是并发请求、列是每请求最多用多少块,由 attention kernel 直接读取。

### 2.3 收益:显存利用率从一成提到九成

到这里可以把账算完了。设请求实际长度 L、块大小 B,分页之后**每请求的浪费上限是 B−1 个 token**(只有最后一块可能没填满),和请求有多长完全无关。

拿一组典型数字对比(`max_model_len` 2048、平均实际长度 200、块大小 16):

| | 朴素预分配 | PagedAttention |
|---|---|---|
| 内部碎片 | 每请求浪费 max_len − L,约 (2048−200)/2048 ≈ **90%** | 每请求最多浪费 15 个 token,15/200 ≈ **7.5%** |
| 外部碎片 | 严重,长请求用不上零散空间 | **完全消除**,block 可散布任意位置 |
| 共享前缀 | 不支持 | 多个 block table 指向同一块即可 |

**显存利用率从 ~10% 提到 ~92%** —— 这是 PagedAttention 最直接的收益,也是它值得多付那一层间接寻址的理由。

剩下的几节是这套方案的落地细节:一个 block 具体长什么样、归谁、多大合适、总共有多少块、状态怎么流转。

### 2.4 一个 block 在显存里长什么样

「一个 block 存 16 个 token 的 K 和 V」这句话不够用。稀疏 MLA 会把多个 token 压进一个存储单元,Whisper 的 block pooling 反过来让一个 token 占多个单元,某些 backend 还会重新打包 head —— 这些都得塞进同一套描述里。vLLM 的办法是定义一组**逻辑五维**,所有变体都表达成它的参数:

| 维度 | 名称 | 含义 | 普通 attention 下的值(Llama-3-70B、TP=8、FP16) |
|---|---|---|---|
| L | layer | 共用同一块 buffer 的层数 | 该 KV cache tensor 覆盖的层数 |
| B | block | block 数 | 由显存推算,见 3.4 |
| H | head slot | 头槽位数,默认等于 KV head 数 | 1(8 个 KV head ÷ TP=8) |
| N | state | 一个 block 内存了多少个「状态」 | 16(等于 block_size,每 token 一个状态) |
| C | content | 每个 (head slot, state) 单元的**字节数** | 512 =(128 + 128)× 2 B |

按这组数字,一个 block 在单层就是 1 × 16 × 512 B = **8 KB**:16 个槽位,每个槽位放一个 token 的 K(128 维)紧接着它的 V(128 维),共 256 个 FP16。

三个最容易记错的点:

- **C 的单位是字节,不是元素。** K 和 V 拼在同一个 C 轴里,前一半 K、后一半 V。底层 buffer 本身是一块扁平的 `int8` tensor,各层的 4 维视图由字节 stride 切出来。把 C 当成「256 个元素」记,就必须再乘一次 dtype_size,两种写法都得到 8 KB,混用就会差 2 倍。
- **N 不一定等于 token 数。** 它是 `block_size ÷ 每个状态覆盖的 token 数`。普通 attention 是一 token 一状态,所以 N = block_size;DSv4 的稀疏 MLA 把多个 token 压成一个状态;Whisper 的 block pooling 则是一个 token 存多个状态(用分数表示)。
- **H 不一定等于 KV head 数。** backend 可以申报一个自定义的头槽位数来改写打包方式。

K 和 V 拼在同一个 C 轴的好处是:**一次内存分配、一次 block table 索引**就同时覆盖 K 和 V,少一半碎片和索引开销。代价是 attention kernel 里要现场把 C 轴切成 K/V 两半。

还有两条贯穿全局的设计。**每一层各有一份独立的 KV cache**:80 层模型就是 80 个独立的四维视图,token 在第 L 层算出的 K/V 写进第 L 层的那一份。但**整个模型只有一块 backing allocation** —— 所有层从同一块 `int8` 大 buffer 上按字节偏移切视图,同一个 block id 在 80 层里各占一段。不同 cache group 之间甚至可以互相 overlay(不同 spec 的视图指向同一段字节),这正是混合 attention 模型(full + sliding window、attention + Mamba)能共用一个 block 池的基础。

顺带把一个会遇到两次的数字说清楚:**把层这一维也算进来,整份 KV cache 的逻辑形状是五维** `[L, B, H, N, C]` —— 下一节那些 `LBNHC` 式的 layout 名正是这五维的排布顺序(五个字母对应五维);**摘掉 L,每层的视图就是上面那个四维。** 两个说法都对,说的是两级,源码里也同时提供了这两种视角(布局枚举上有一个属性专门做这个换算)。

### 2.5 一个 block 只属于一个请求

既然 block 散落在显存各处、又能被共享,很自然会问:一个 block 里能不能前 8 个位置放请求 A 的 token、后 8 个放请求 B 的?

**不能。block 是分配的原子单位** —— 一个 block 里的 16 个位置必须是同一个请求的连续 16 个 token。三条理由,每一条都足以否决混装:

1. **block table 是按请求维护的。** 定位方式是 `block_table[pos // block_size]` 加块内偏移 —— 这个算式本身就假设了「块内第 k 个位置 = 本请求的第 (块号 × 16 + k) 个 token」。混装之后这个映射无从表达。
2. **kernel 依赖这个假设。** attention kernel 拿到块号后按连续内存读整块,并按逻辑位置做因果掩码。块内混了别的请求,掩码和读取都会错。
3. **释放是整块的。** 请求结束时整块归还,混装会连带毁掉另一个请求的 KV。

**唯一的「共享」是 prefix caching,而它不是混装。** 如果请求 A 和 B 的前 16 个 token 完全相同,两张 block table 可以指向同一个物理 block,引用计数变成 2。这块里的 KV 内容对 A 和 B 来说**完全相同** —— 相同的 token 序列经过相同的权重,必然得到相同的 K/V 投影。所以它仍然满足「块内是同一段连续前缀」,只是这段前缀同时属于两个请求。

## Part 3|一个 block 的布局、大小与状态

### 3.1 物理排列:六种 layout,默认为什么是 LBNHC

上面五个维度只是**逻辑**顺序,真正的内存排布是它的一个置换。vLLM 把六种可用置换定义成一个枚举:

| 名称 | 物理顺序 | 特点 |
|---|---|---|
| `LBHNC` | [L, B, H, N, C] | 恒等置换;同一个 head 的所有 token 连续 |
| `LBNHC` | [L, B, N, H, C] | 同一个 token 的所有 head 连续(**默认首选**) |
| `LHBNC` | [L, H, B, N, C] | 层内先按 head 分区;破坏了 page 连续,backend 要主动申报才用 |
| `BLHNC` / `BLNHC` / `BHLNC` | B 提到最外 | 牺牲层内紧凑,换来同一 block 的所有层相邻 |

枚举上挂了四个布尔属性,是各处约束检查的判据:L 在最外层(层内整块连续)、[H, N, C] 恰好是最内三维(block 内完全连续)、L 和 B 是最外两维(每个 page 的字节是一段连续区间)、B 在最外层。

**为什么默认偏好 LBNHC**,只要盯住三类访问就明白:

- **B 必须靠外。** block table 是一个 int32 数组,kernel 通过它定位物理 block,这个访问天然是随机的(同一请求的 block 散落在显存各处)。B 靠外意味着「一次跳转 + 之后在块内连续读」;B 要是在内层,每读一个 block 都要跨越大段内存。
- **C 必须最内。** Q·K 是向量点积,一个 (head, token) 单元的 head_size 个元素必须连续,才能用宽指令一次装载。六个枚举值都满足这一条。
- **N 和 H 的相对次序才是真正的分歧点。** `LBNHC` 把 token 放在 head 外面,固定 block 后同一个 token 的所有 head 连续;`LBHNC` 反过来,同一个 head 的所有 token 连续。

两者各有所长,所以**两个都在默认偏好序里**,由 backend 申报决定用哪个:写侧一次写入一个 token 的全部 head,`LBNHC` 让这次写入落在一段连续内存里;读侧若 kernel 按 head 划分线程块并沿 token 扫描,`LBHNC` 的合并访问更好。完整的默认偏好序是 `LBNHC → LBHNC → BLNHC → BLHNC → BHLNC → LHBNC`。

布局在 engine core 里**全模型只解析一次**,流程是:各 worker 上报自己 backend 支持的布局列表(基类默认返回空,表示任意布局都行),然后按四级优先决议 ——

| 优先级 | 来源 | 不满足时 |
|---|---|---|
| 1 | `cache_config` 上已经定下的布局 | 直接胜出,后面都不看 |
| 2 | `VLLM_KV_CACHE_LAYOUT` 环境变量(`NHD`/`HND` 是 `LBNHC`/`LBHNC` 的旧别名) | 不在候选集就直接报错 |
| 3 | KV connector 的偏好 | 不兼容时打 warning 并回退 |
| 4 | 默认偏好序的第一个 | — |

两个容易读错的地方:各 worker 上报的列表不是「取交集」,而是**必须完全一致**,不一致直接抛错(理由是所有 rank 跑的是同一套 backend,列表本就该相同);另外,若不同 spec 的形状不一致(混合 attention 类型),候选会先被收窄到「每个 page 的字节连续」的那几种布局 —— 只有这样,混合 spec 才能在同一页上以不同方式解释同一块内存。

### 3.2 block_size 定多大:四个维度在拉扯

块大小的默认值是 16。这个数字有点特别:它不是某个配置字段的默认值 —— 字段的默认值其实是「未指定」,表示交给平台和 backend 决议,16 只是兜底的回落值。

先说**硬约束**:可选的块大小不来自任何形状检查函数,是 backend 主动申报的。FlashAttention 声明自己的 kernel 支持「16 的任意倍数」,上层再按各 backend 的申报为每个 KV cache group 挑一个实际的 kernel block size。根子在 kernel 内部:FlashAttention 把 K/V 按 16 个 token 一组载入做分块矩阵乘,所以一个 block 的 token 数必须是 16 的整数倍,否则最后一组会跨 block 边界。head_size=256 的 FA4 路径要求的是页对齐,于是它直接申报一个固定尺寸,而不是「16 的倍数」。注意 kernel block size **可以比管理侧的 block 小**:一个管理 block 会被切成若干个 kernel block,这只是一层视图,要求整除。

硬约束之内,具体定多大是四个维度的拉扯:

**① 内部碎片 —— 越小越好。** 一个请求占用的槽位是 `⌈L / block_size⌉ × block_size`,最坏浪费 `block_size − 1` 个 token:

| block_size | 20 token 请求占用槽位 | 浪费 | 浪费率 | 单请求最坏浪费 |
|---|---|---|---|---|
| 16 | 32 | 12 | 37.5% | 15 token |
| 32 | 32 | 12 | 37.5% | 31 token |
| 64 | 64 | 44 | 68.8% | 63 token |
| 128 | 128 | 108 | 84.4% | 127 token |

20 这个长度下 16 和 32 恰好打平,但**最坏值差 2 倍**。请求长度分布越分散,最坏值出现得越频繁。

**② prefix caching 命中粒度 —— 越小越好。** 前缀缓存的 key 是按固定长度的 token 单元算的,两个请求在第 N 个 token 处分叉时,只有**完整命中的单元**才算数,分叉点所在的那一个单元整个作废:

| block_size | N=20 时命中 | N=100 时命中 | 粒度 |
|---|---|---|---|
| 16 | 16 token(80%) | 96 token(96%) | 细 |
| 32 | 0 token(0%) | 96 token(96%) | 中 |
| 64 | 0 token(0%) | 64 token(64%) | 粗 |
| 128 | 0 token(0%) | 0 token(0%) | 很粗 |

短前缀下差距是灾难性的:N=20 时 block_size 从 16 换到 32,命中率直接从 80% 掉到 0。

**③ block table 大小 —— 越大越好,但可以忽略。** 每请求的 block table 长度是 `⌈seq_len / block_size⌉`。`max_model_len` 8192 时,块大小 16 是 512 个 int32(2 KB/请求),128 是 64 个(0.25 KB/请求);256 并发下两者相差不到半兆,相对 GB 级的 KV cache 可以忽略。

**④ kernel 内存访问效率 —— 越大越好,但已被优化覆盖。** 块越大,单次连续读取的内存越大,GPU 合并访问效率越高(块大小 16 时每次读约 4 KB,64 时约 16 KB)。但 FlashAttention 已经针对 16 做过优化,实际差异不大。

**所以默认 16:**

| 维度 | 16 | 64 | 128 | 谁赢 |
|---|---|---|---|---|
| 单请求最坏浪费 | 15 token | 63 token | 127 token | **16** |
| 20 token 请求的浪费率 | 37.5% | 68.8% | 84.4% | **16** |
| prefix caching 命中(N=20) | 80% | 0% | 0% | **16** |
| block table 大小 | 2 KB | 0.5 KB | 0.25 KB | 128(差异可忽略) |
| kernel 访问效率 | 中 | 高 | 高 | 128(但 FA 已优化 16) |

**前两个维度受 block_size 影响最大,后两个要么在 KB 级、要么已被 kernel 优化抹平** —— 所以 16 是碎片率与命中率的综合最优。

什么时候值得调大:

| 场景 | 建议 |
|---|---|
| 序列都很长(>4096)且长度均匀 | 碎片影响小,可用 32 或 64 |
| 不用 prefix caching | 命中率不再是考虑因素 |
| backend 有硬性要求 | 按 backend 申报的走 |
| 混合模型(full + sliding window、attention + Mamba) | 为对齐 page 被迫用大 block,见下一节 |

### 3.3 命中粒度能不能和 block 粒度解耦

上一节里 block_size 同时背了两个包袱:它既是**分配粒度**,又是**前缀命中粒度**。混合模型被迫用大 block 时,这就成了问题 —— 分配上不得不粗,命中上却想细。

vLLM 为此把两者拆成了两个量:调度器用的块大小,和算前缀哈希用的单元长度。但**拆开是有前提的**:

**单 group 模型下根本拆不开。** 普通 Llama 加 FlashAttention 就是单 group,这时哈希单元直接等于块大小,`prefix_match_unit` 这个参数被完全忽略 —— 单 group 的协调器里还有一条断言把这件事钉死:开了缓存就必须两者相等。

**多 group 时也未必拆得开。** 默认的哈希单元是各 group 块大小的最大公约数,但有三条前提得同时成立,少一条就退回「哈希单元 = 调度块大小」:

| 前提 | 不成立时 |
|---|---|
| 有多个 KV cache group | 单 group 直接返回,参数被忽略 |
| 前缀缓存或 KV connector 至少开了一个 | 都没开就没人消费哈希,直接返回 |
| 没有非 `align` 模式的 Mamba group | 这类 group 破坏整除关系,直接返回 |

另外,求最大公约数时**只对「可做前缀缓存」的那些 group 求**,不是对全部 group 求(一个可缓存的都没有才退回全部)。显式指定 `prefix_match_unit` 时也是按这批 group 校验整除,不满足直接报错。

**就算拆开了,覆盖面也比想象的窄。** 细粒度命中的实现不是把 block 拆小,而是**给已有 block 多挂一个 lookup key**:注册一个 partial 条目,记下这个 key 覆盖了前缀的多少个 token,**不额外分配 block、也不拷贝 KV 数据**。但注册的时机只有一个 —— prompt 尾部那一个哈希边界:

- 只注册 **prompt 尾部**那一个边界,同一个 block 内部的中间边界**是故意跳过的**(源码注释明写 intentionally skipped)
- decode 过程中新产生的块内边界不会被注册
- 边界正好落在 block 边界上时也不注册(那是满块缓存的活)

举个例子:两个 group 的块大小分别是 1024 和 64,哈希单元取 64;一个 1000 token 的 prompt,尾部边界落在 960。于是给覆盖 token 0–1023 的那个 block 注册一个「覆盖前 960 个 token」的 partial 条目。后续请求若前 960 token 相同就能命中它、复用整个 block —— 代价是复用的是整块的引用,块内 960–1023 的槽位对新请求不可用。

**结论**:单 group 模型下,想提高命中率只能靠调小 block_size,`prefix_match_unit` 帮不上忙;混合模型被迫用大 block 时它能改善 prompt 尾部的复用,但不要指望它等价于小 block。

### 3.4 显存里能放多少 block:启动时量一次

block 总数不是用户直接配的,它由显存占比间接决定,在启动时由一次 **profile run** 自动算出来。这是 vLLM 启动慢的原因之一,也是调参时最该理解的一条链路:

| 步 | 做什么 | 本例(8×H100 80 GB,占比取 0.9) |
|---|---|---|
| ① | 按显存占比划出总预算 | 80 GB × 0.9 = 72 GB |
| ② | profile run 实测非 KV 显存 | 权重 17.5 + 激活 2 + CUDA Graph 1 = 20.5 GB |
| ③ | 相减得到 KV 可用显存 | 72 − 20.5 = 51.5 GB |
| ④ | 算每 block 的字节数(全模型各层之和) | 80 × 8 KB = 640 KB |
| ⑤ | 相除取整 | 51.5 GB ÷ 640 KB ≈ 82000 |
| ⑥ | 写回配置,block 池按此初始化 | 82000 |

反推回去能对上:每层的 4 维视图是 [82000, 1, 16, 512],每层 82000 × 8 KB = 656 MB,80 层合计 52.5 GB,与可用显存吻合。

两点要说明。第一,**这里的 0.9 是举例,基准上的默认值是 0.92**。第二,第 ④ 步在源码里的口径是「最大的那个 cache group 的各层页大小之和」——单一 attention 模型下等价于「层数 × 单层单 block 字节」,混合 spec 模型下不等价。

### 3.5 block 的三种状态:两个字段隐式编码

最后一块是记账:这 82000 个 block 怎么流转。

**vLLM 没有给 block 定义状态枚举**,状态是由两个字段隐式编码出来的 —— 引用计数,和这个块有没有内容哈希:

| 状态 | 引用计数 | 块哈希 | 在哪 | 含义 |
|---|---|---|---|---|
| FREE | 0 | 无 | 空闲队列**队首** | 全新块,或刚被释放且没有哈希的块 |
| CACHED | 0 | 有 | 空闲队列**队尾** | 已缓存但当前没人引用,可被命中复用,也可被驱逐 |
| ALLOCATED | >0 | 见下 | 不在队列里 | 正在被一个或多个请求使用 |

ALLOCATED 的块有没有哈希**不是可有可无**,它取决于这个块是怎么变成 ALLOCATED 的:

| 进入 ALLOCATED 的路径 | 此刻有没有哈希 | 为什么 |
|---|---|---|
| 新分配 | **必然没有** | 从队首取出后立刻清掉旧哈希再交出去 |
| 前缀命中后复用 | **必然有** | 能被查到,正是因为哈希还挂在缓存索引里 |
| 新分配后被填满、登记 | 从无变有 | 块填满 16 个 token 之后才注册哈希 |

这个区分很关键:**一个 ALLOCATED 且没有哈希的块,是「正在被写、还没满」的尾块;有哈希的则是「内容已定、可被别人共享」的满块。** 释放时走哪条分支,就是靠它判断的。

**半满的尾块释放后回队首。** 释放时的分流只看有没有哈希,**不看填了多少 token**:没有哈希的放到队首,有哈希的放到队尾。源码注释把动机写得很直白 —— 没哈希的块走 LIFO 是为了 **GPU 局部性**(刚被写过的块缓存行还热,马上给下一个请求用,比翻到队尾划算);有哈希的块必须去队尾,才能形成 LRU(队首最久未用者先被驱逐)。而新分配总是从队首取,所以刚释放的半满块下一轮就会被立刻捡走。

两个容易漏掉的前提:

- **半满块在请求活着的时候根本不在队列里。** 它是 ALLOCATED,引用计数大于 0;只有请求结束或被抢占、计数归零之后才入队。所谓「在队首」,描述的是它**释放之后**的位置。
- **「半满 ⇒ 没有哈希」不是绝对的。** 混合模型且哈希单元小于块大小时,prompt 尾部所在的半满块会被注册一个 partial 条目(见 3.3),此时它是有哈希的,释放后去队尾当 LRU 候选。单 group 模型下这条路走不到。

三个关键操作合起来就是全部流转:

| 操作 | 做什么 |
|---|---|
| 新分配 n 块 | 从队首取 n 个,引用计数各加一;取出的块若带哈希,先驱逐(清掉哈希并从缓存索引摘除) |
| 命中复用 | 引用计数加一,并把块从空闲队列里摘除 |
| 释放 | 引用计数各减一;归零的块按有无哈希分流:没有的回队首(立即可用),有的回队尾(作为 LRU 缓存候选) |

## Part 4|显存见底之后:watermark 与多级缓存

### 4.1 显存见底之后:watermark 这道默认关闭的闸门

块用完了会怎样?调度器会**抢占**已经在跑的请求,把它的块全部释放出来(抢占的完整机制在 02 章,这里只用结论:被抢占的请求丢掉已算的 KV,回等待队列重排)。

问题在于抢占之后。释放出来的块进了空闲池,而**等待队列里的新请求和正在 decode 的老请求会一起来抢** —— 新请求一次要几百块,老请求一次只要一块。结果是抢占腾出的空间立刻被新请求吃掉,running 集合的余量始终是 0,下一次跨块边界又触发抢占。**抢占 → 释放 → 新请求吃掉 → 再抢占**,系统在抖动。

`watermark` 就是为此存在的:在 running 请求和 waiting 请求之间设一道**单向屏障**。

**先说清默认值:0,也就是关闭。** 它是一个可选的稳定性旋钮,不是默认生效的机制。配置上是一个比例,构造 KV cache 管理器时换算成绝对块数(比例 × 总块数,向下取整);比例为 0 时换算结果是 0 块,这道闸门完全不起作用。

**它只拦准入,不拦续跑。** 分配槽位时,水位只在两个条件**同时**满足才计入需求:

| 请求来源 | 本 step 已有请求被调度 | 是否施加水位 |
|---|---|---|
| RUNNING 中的请求继续追加(decode / chunked prefill 续算) | — | **否** |
| WAITING / PREEMPTED 请求准入 | 是 | **是** |
| WAITING / PREEMPTED 请求准入 | 否(本 step 一个都没排上) | **否** |

第三行是**防死锁的兜底**:本 step 还没有任何请求被调度时,不能因为水位把最后一个请求也拦住,否则引擎会空转。

这个「只拦准入、不拦续跑」就是 watermark 的全部意义 —— **它不是给突发需求留 buffer,而是在 running 和 waiting 之间设优先级**。抢占释放出来的块于是只能被 running 请求消化,不会被新请求抢走。

**一个容易记反的细节:水位是加到需求侧的,不是从可用侧减的。** 判断式是「要分配的块数 + 水位 > 可用块数」;而从可用块数里扣掉的是另一个量 `reserved_blocks`。两种写法的不等式等价,但记混了会在读源码时找不到对应。另外这样的检查在分配路径上有**两处**:一处是「整条序列必须装得下」的前置检查,另一处是常规路径,只有后者会扣 `reserved_blocks`。

**真正为 running 请求预留空间的是另外两个参数**,水位不管这件事:

| 参数 | 作用 | 怎么生效 |
|---|---|---|
| `num_lookahead_tokens` | 投机解码要多留的槽位 | 直接算进这一轮要分配的块数 |
| `reserved_blocks` | 为「在飞行中」的序列预留的空块 | 比较前先从可用块数里扣掉 |

所以 running 请求的 KV 需求突增时(decode 跨块边界、投机解码的草稿 token、chunked prefill 续算),水位一概不为它们兜底 —— 真到了可用块为 0 的那一步,水位设成多少都救不了,照样抢占。**抑制这种触底抢占靠的是限制并发本身**(并发上限与 token 预算),让 running 集合的稳态需求本来就装得下。

两点特别容易记错:

1. **水位不给 running 请求留 buffer。** 可用块照样会被 decode 用到 0,然后照样触发抢占。它保护的不是「不抢占」,而是「抢占释放的块不外流」。
2. **水位不是逻辑上不分配的预留区。** 那批块对 running 请求始终完全可用,**KV cache 的物理利用率一点没降** —— 只有准入检查会假装它们不存在。

一句话:**watermark 是 running 请求相对 waiting 请求的优先级旋钮** —— 调高它,系统更偏向「把已收进来的请求跑完」,而不是「多收请求」。默认 0 表示 vLLM 出厂不做这个偏向。

怎么调(拦截线按 82000 块总量算):

| 比例 | 拦截线 | 新请求准入难度 | 抢占后释放块的外流 | 稳态吞吐 |
|---|---|---|---|---|
| **0(默认)** | 0 块 | 最容易 | 全部可被新请求抢走 | 最高,但抖动最大 |
| 0.001 | 82 块 | 几乎无变化 | 基本仍会外流 | ≈ 默认 |
| 0.01 | 820 块 | 明显变难 | 基本不外流 | 略降 |
| 0.05 | 4100 块 | 很难 | 不外流 | 明显降 |
| 0.10 | 8200 块 | 极难,长 prompt 可能长期排队 | 不外流 | 降很多 |

- **保持 0**:追求吞吐、请求长度均匀、能接受偶发抢占
- **调到 0.01~0.05**:观察到抢占计数居高不下,且首 token 延迟的抖动比平均吞吐更让你难受时。**先看指标里的抢占次数再决定,不要盲调**
- **不要调到 0.1 以上**:总块数里 10% 被排除在准入之外,长 prompt 请求可能永远等不到那么大的空间,表现为个别请求超时

上面这些效果是按机制推演的量级,不是本仓库的实测数字。

**和 prefix caching 是互补的,作用在抢占的两端:水位管「抢占多久发生一次」,prefix caching 管「抢占一次多疼」。** 被抢占请求的块带着哈希回到空闲队列**队尾**,而新分配从队首取 —— 所以只要这期间的分配没把整条队列翻过去,这些块就还在,重新调度时能命中,只需重算分叉后的新 token。反过来,如果抢占后系统继续高压分配,这些块照样会被清掉,重新调度就退化成全量 prefill。**prefix caching 降低的是期望代价,不是保证。** 默认配置下只有后者生效。

### 4.2 让 KV 在被丢弃前先留一份副本:多级缓存

抢占和 prefix caching 都是在 **GPU 显存内**周旋:抢占是丢弃 KV 再重算,prefix caching 是哈希命中才能复用 —— 没命中的块被驱逐后,KV 就真的没了,重新算一遍 prompt 要几十到几百毫秒。

**多级缓存(offload)解决的是这个**:让 KV 在被 GPU 丢弃之前,**先在更慢但更大的存储层留一份副本**。GPU 上那份被驱逐后,需要时从副本换回来,而不是重算。

三层各自的角色:

| 层 | 容量与速度 | 谁管 | 进入这一层的时机 |
|---|---|---|---|
| GPU 显存 | ~80 GB/卡,带宽 ~3 TB/s | block 池 | KV cache 的主存储 |
| CPU 内存(页锁定) | ~256 GB+,PCIe ~32 GB/s | CPU offload 管理器 | **主动提前备份**:每个调度 step 末尾把新算出的 KV 拷一份过来 |
| 文件系统(NVMe) | 几 TB,~7 GB/s | 文件系统层管理器 | **满了才驱逐**:CPU 层空间不够时换下来 |

**两个 hop 的触发机制不一样**,这是最容易看反的一点:GPU→CPU 是提前备份(write-behind),CPU→磁盘 才是满了才驱逐(write-on-evict)。所以一个块被 GPU 驱逐时,它的副本往往**早就在 CPU 上了**。

**最值得看的是这套东西的解耦方式:block 池完全不知道 offload 的存在。** 它的驱逐逻辑里没有任何 offload 调用 —— 驱逐就是驱逐,哈希直接从缓存索引摘掉(整个 block 池的源码里 `offload` 这个词出现零次)。真正驱动 offload 的是一个 **connector**,它挂在调度器的 KV connector 钩子上,在每个 `schedule()` 末尾扫描「这一步新算出 KV 的部分」,把它们主动拷到 CPU。

**粒度是 chunk 不是 block。** 若干个 GPU block 合并成一个 offload chunk,CPU 层的分配、驱逐、查找全部以 chunk 为单位 —— CPU 侧管理器的源码里根本不出现 block 这个词。记成「单个 block」会在读源码时对不上名字。

**往下写(store)** 的流程是:connector 算出这一步哪些 chunk 的 KV 已经算完且已分配块、且在推进游标之后(避免重复拷贝),交给 CPU 管理器准备存储 —— 先滤掉已经存过的 key,算出还差多少 chunk,不够就按策略驱逐,分配槽位并登记映射;然后 worker 侧用一个 Triton kernel 做真正的显存到内存拷贝,拷完回调落定状态。之后 GPU 端那个块被正常驱逐时,block 池不做任何 offload 动作,但 CPU 上那份副本还在。

**往上读(load)** 的流程是:调度器先走正常的前缀缓存查询,GPU 端没命中;再问 connector 有多少 token 能从外部拿到,connector 逐 chunk 查 CPU 管理器,返回命中、待命中或未命中;然后调度器**照常分配 GPU 块**,再把新块交给 connector 组装传输两端,由 worker 做内存到显存的 DMA。

这里有个反直觉的点:**没有「改 block table 把旧块换成新块」这回事。** GPU 侧的块是正常分配流程给的,block table 本来就指向新块,offload 只负责把字节填进去。

代价上,一个块在 80 层合计 640 KB,按 PCIe 带宽算纯传输约 20 μs,加上每次传输的固定开销在几十 μs 量级 —— 而重算 16 个 token 过 80 层是毫秒量级,**load 比 recompute 快约两个数量级**。

驱逐策略有两种,都在 CPU 层:

| 策略 | 原理 | 适用 |
|---|---|---|
| LRU | 驱逐最久未访问的 chunk | 通用 |
| ARC | 自适应平衡最近性与频率 | 访问模式变化大 |

驱逐有两道保险:本次要存的那批 key 一律排除在驱逐候选之外(已经存过的块必须在这次调用后仍留在缓存里);需驱逐数超过可驱逐数时连尝试都不做,直接放弃整批 store。

**三条路怎么选:**

| | 重算 | prefix caching | 多级缓存 |
|---|---|---|---|
| 块被驱逐后 | KV 丢失,重算 | 哈希还在就能直接复用 | 副本已提前存在 CPU/磁盘,可换回 |
| 恢复成本 | 重算整个 prompt,几十到几百毫秒 | 0(直接复用) | 一次传输,几十 μs 量级 |
| 额外占用 | 无 | 无(只留哈希) | CPU 内存 + PCIe 带宽 |

**vLLM 默认走「重算 + prefix caching」,不开 offload。** 理由很实际:前缀缓存命中时重算代价极低(只重算分叉后的新 token),而 offload 要额外的 CPU 内存和 PCIe 带宽。

### 4.3 offload 的三条收益,每条都有前提

上一节给的对比是理想情况。真要决定开不开,得知道每条收益在什么条件下才兑现 —— 这三条前提里有一条被误读得特别厉害。

**收益一:恢复变快,但「两个数量级」是保守说法,也是乐观说法。**

传输量算对是前提:一个块在单层占 8 KB,在 80 层合计 **640 KB** —— 换回来必须把 80 层都搬回去,否则这个块不可用。按 PCIe 带宽算纯传输约 20 μs,加上每次传输的固定开销(kernel 启动、描述符组装、同步)合计在几十 μs;而重算是毫秒量级。

但这个倍数**不是能稳定拿到的加速比**,它取决于两件事:

- **能不能批量传输。** 固定开销对 640 KB 这个量级和带宽项是同一量级,把多个块攒成一次传输才能摊薄它 —— 有一个专门的环境变量控制批量传输描述符的上限,存在的理由正是这个。
- **重算能不能蹭上现成的 batch。** 如果本来就有 forward 在跑,多算 16 个 token 的边际成本远低于单独重算一次。这时候 offload 的优势会被压缩很多。

**收益二:有效容量扩大,但换算分母别搞错。**

不开 offload 时,有效 KV cache 就是 GPU 显存那么多(本例 51.5 GB ≈ 82000 块),超过就只能重算。开了 CPU 层之后,容量是两者之和 —— CPU 侧给 50 GB 的话,**除以 640 KB** 约等于再加 80000 块,几乎翻倍。

**分母必须是 640 KB(80 层合计),不是 8 KB(单层)** —— 按单层算会把容量高估 80 倍。CPU 侧到底给多少由所选 spec 的配置决定,不是下一节要说的那个同名参数。

**收益三:长上下文的必需品 —— 但它不是「无限长 context」的银弹。**

这是最容易踩坑的一条。直觉上会以为:开了 offload,GPU 侧只需要留「本 step attention 要读的窗口」,其余下沉到 CPU,于是长上下文和高并发就能兼得。

**这个说法只对滑动窗口 attention 成立。** full attention 的 decode **每一步都要读全部历史 KV** —— 一个 100K token 的请求换算成 6250 个块,这些块在每个 decode step 都必须在 GPU 上。offload 对它的帮助是**在请求之间轮换**(这个请求不在跑的时候把它的块换下去),不是**在 step 内部按需拉取**。

把这条记反,就会在长文档 RAG 这类场景上做出错误的容量规划。

**代价:**

| 代价 | 说明 |
|---|---|
| CPU 内存 | 按 640 KB/块算,8 万块就是约 50 GB;而且是页锁定内存,不可换页,会挤占系统可用内存 |
| PCIe 带宽 | 与权重加载、输入拷贝等竞争同一条链路 |
| 延迟 | 比重算快但非零;落在关键路径上时无法被隐藏 |
| 复杂度 | 多级管理、驱逐策略、异步传输状态机 |

**所以建议开的条件是四条同时成立**:KV cache 装不下期望的并发、上下文长(3 万 token 以上)、不想频繁重算、CPU 内存有富余。反过来,显存充足、序列短(4 千以内)、CPU 内存紧张,或者追求极致低延迟,就不要开。

### 4.4 怎么开:先别配错那个参数

**一个高频误解要先排除:`--cpu-offload-gb` 和 KV cache offload 没有关系。**

它属于另一套配置,文件第一行 docstring 写得明明白白:这是**模型权重**的 offload。它把权重放到 CPU 页锁定内存,靠统一虚址让 GPU 零拷贝访问,用来在小显存卡上塞进大模型 —— 代价是每次前向都要从 CPU 内存往 GPU 搬一部分权重,所以要求 CPU-GPU 互联够快。跟 KV cache 一个字节关系都没有。

KV cache 的多级缓存走的是**完全独立的另一条通路**:KV connector 加 offloading spec。装配入口从连接器的额外配置里读一个 spec 名字(默认是 CPU 那一档)来决定用哪个后端,而这份额外配置是通过 `--kv-transfer-config` 传进去的。

| 想配的东西 | 真正的入口 |
|---|---|
| 启用 KV offload | `--kv-transfer-config` 里选 offloading connector,并给出 spec 名字 |
| 选 LRU / ARC | 所选 spec 的额外配置,经策略工厂按名字解析 |
| 加磁盘层 | tiering spec |
| 批量传输上限 | 环境变量 `VLLM_KV_OFFLOAD_MAX_BATCH_DESCRIPTORS` |
| **模型权重**下沉 CPU(与 KV 无关) | `--cpu-offload-gb` |

两点补充:**驱逐策略不由环境变量控制** —— 整个 `envs.py` 里只有一个 `VLLM_KV_OFFLOAD` 开头的变量,就是上表那个批量上限;策略是按名字从注册表取的,也可以直接给一个模块路径加载外部实现,不需要改 vLLM 源码。另外,额外配置里具体有哪些键、CPU 侧容量怎么给,由所选 spec 自己解释;规整之后的结构里放的是每块字节数、每个哈希覆盖多少 token、几个块合成一个 chunk 这类**推导出来的量**,不是用户直写的字段。

## Part 5|图解

### 5.1 从调度器到 kernel:五层分工

前四部分是按问题展开的,这里把参与者按调用顺序摞起来看一遍 —— 每一层只做一件事,往下委托:

```text
┌──────────────────────────────────────────────────────┐
│ 调度器  schedule()                                     │
│   ↓ 调用                                              │
├──────────────────────────────────────────────────────┤
│ KV cache 管理器                                        │
│   · 分配槽位 → 返回块,或 None(触发抢占/停止拉新)        │
│   · 查已算过的块 → 命中的前缀块                          │
│   · 释放请求                                           │
│   ↓ 委托                                              │
├──────────────────────────────────────────────────────┤
│ 协调器(每个 KV cache group 一个类型管理器)              │
│   · 单 group 走 Unitary,多 group 走 Hybrid            │
│   · 找最长前缀命中 / 分配新块                            │
│   ↓ 持有                                              │
├──────────────────────────────────────────────────────┤
│ block 池                                              │
│   · 所有物理块的数组                                    │
│   · 空闲队列(侵入式双向链表)                            │
│   · 哈希 → 块 的映射表                                  │
└──────────────────────────────────────────────────────┘
                    ↓ 调度器产出
┌──────────────────────────────────────────────────────┐
│ 调度输出                                               │
│   块 id 不是顶层字段,分两处下发:                        │
│   · 首次调度的请求 → 全量块列表                          │
│   · 已调度过的请求 → 只发新增的块                        │
│   还带:每请求这轮算多少 token、公共前缀块数              │
└──────────────────────────────────────────────────────┘
                    ↓ 传给 model runner
┌──────────────────────────────────────────────────────┐
│ GPU:attention kernel 读 block table                   │
└──────────────────────────────────────────────────────┘
```

**「块 id 分两处下发」值得单独记一笔。** 首次调度时下发全量,之后每轮只下发增量 —— 这样每步的调度输出不会随着序列变长而线性膨胀。worker 侧自己维护每个请求的块表,收到增量就往后追加。

### 5.2 三个并发请求的 block table

拿一个能一眼看完的例子(块大小按 4 算,实际是 16):

```text
GPU 显存的物理块池:
 Block 0   Block 1   Block 2   Block 3   Block 4   Block 5   Block 6   Block 7
 [■■■■]    [■■■■]    [■■■■]    [░░░░]    [■■■■]    [■■■■]    [░░░░]    [■■■■]
  已用      已用      已用      空闲      已用      已用      空闲      已用

请求 A(8 token,prompt 已算完):
  逻辑位置:  0 1 2 3 │ 4 5 6 7
  block table: [1, 5]              ← 用了物理块 1 和 5

请求 B(6 token):
  逻辑位置:  0 1 2 3 │ 4 5 (6 7 空)
  block table: [0, 7]              ← 用了物理块 0 和 7

请求 C(4 token,与 A 共享前 4 个 token 的前缀):
  逻辑位置:  0 1 2 3
  block table: [1]                 ← 复用块 1,该块引用计数为 2
```

三件事在这张图上同时成立:**块号完全无序**(A 用的是 1 和 5,不相邻);**每个请求的逻辑位置仍然连续**(块表按顺序排);**共享是靠两张块表指向同一个块号**,不是把内容复制一份。

### 5.3 一个 block 的一生

把 3.5 的三态放进一条真实的时间线走一遍:

| 步 | 发生了什么 | 之后的状态 |
|---|---|---|
| 1 | 启动:所有块串成空闲队列 | 全部 FREE |
| 2 | 请求 A 到达,prefill 100 token,要 7 块 | 从队首取 B0–B6,各引用计数 1 → ALLOCATED;B7 之后仍 FREE |
| 3 | A 生成中,每填满一块就登记哈希 | B0–B6 仍 ALLOCATED,但**多了哈希** |
| 4 | 请求 B 到达,前 4 块与 A 相同,命中复用 | B0–B3 引用计数 1→2。**注意这一步没动空闲队列** —— 它们引用计数本来就不是 0,根本不在队列里 |
| 5 | A 完成,释放 | B0–B3 引用计数 2→1(B 还在用,不归还);B4–B6 归零且带哈希 → 回**队尾**,成为 CACHED |
| 6 | 请求 C 到达,与 A 的公共前缀比 B 更长,命中到第 5 块 | 前 4 块引用计数 1→2;第 5 块引用计数 0→1,并从队列**中间**摘出来(解链是 O(1)) |
| 7 | 显存吃紧,要驱逐一个 CACHED 块 | 清掉它的哈希、从映射表移除 → 退回 FREE |

第 4 步和第 6 步的对比是这条时间线最值得看的地方:**同样是「命中复用」,块在不在队列里决定了要不要动队列** —— 还有别人在用的块压根不在队列中,只有引用计数归零的块才在里面等着被捡走或被驱逐。

### 5.4 kernel 侧看到的是什么

attention kernel 的输入里多了一样东西:block table。除此之外,它对物理布局**一无所知**。

它按逻辑顺序一块一块地走:拿块表查出物理块号,读出这一块的 K 和 V(同一个内容轴,前一半 K 后一半 V),算这一块的分数,然后**逐块更新**运行中的最大值和分母 —— 也就是 online softmax。这一点容易被伪码误导:真实实现**不是**先把所有块的分数拼起来再做一次 softmax,那样需要与序列长度成正比的中间存储,正是 FlashAttention 要避免的。对理解块表而言两者等价,但别把「拼接后 softmax」当成真实实现。

**这就是 PagedAttention 的「零侵入」特性**:分页这件事没有渗进注意力算法本身,只是在取数那一步多查了一次表。

### 5.5 把时间线串起来:谁在什么时候碰 KV cache

前面各节回答的都是「怎么工作」。这一节换一个问法:**在引擎的时间线上,KV cache 在哪些时刻被谁读、被谁写。** 拿一个 100 token 的 prompt 走一遍,块大小 16。

(请求经过哪些进程、每一跳落在哪,是 01 章的端到端生命周期;这里只看 KV cache 这一条线。)

```text
   启动           请求到达         Prefill          Decode          完成
   ────           ────────         ───────          ──────          ────
 profile run    调度选中 R       跑 forward       跑 forward      检测到结束
 算出块总数     查前缀缓存        ↓                ↓               ↓
 分配大 buffer  命中的块 touch   ★ 写 KV cache   ★ 读 KV cache   释放块
 切每层视图      ↓               ↓                ↓               ↓
 绑定到各层     分配新块         算 attention     采样 1 个 token  引用计数减一
 块池初始化      ↓               ↓                ↓               ↓
 全部 FREE      构造块表         ★ 注册满块哈希   追加 token      有哈希 → 队尾
                构造槽位映射      ↓                ↓               无哈希 → 队首
                 ↓              采样首 token      下一个 step
                进 running                        (循环)
```

**阶段 0 · 启动**:profile run 探一次显存,推算出块总数(见 3.4),分配那一整块 buffer 并按布局切出每层的四维视图、绑定到各层的 attention 模块;然后创建调度器,块池按块总数造出全部块对象并串成空闲队列。此刻 GPU 上是一块全零的 buffer,块表是空的。

**阶段 1 · 请求到达**:请求先进等待队列。下一个 step 被选中后做四件事 —— 查前缀缓存(命中的块引用计数加一)、给剩余 token 分配新块、构造块表、构造**槽位映射**(每个 token 要写到哪个物理位置:块号 × 块大小 + 块内序号)。假设前 48 个 token 命中缓存,剩下 52 个需要 4 块。

**阶段 2 · Prefill:写**。这一步只算 52 个 token —— **命中的那 48 个一个字节都不重算、也不重写**。逐层前向时,算出的 K/V 按槽位映射逐 token 写进对应块,K 和 V 拼在同一个内容轴里。写入这一步有三层落点:后端里的调用、Python 包装、C++ 声明,另有一份 Triton 实现。

这里有一个**反直觉的点,值得单独记住**:

> **哈希注册发生在调度阶段,不在 forward 之后。**

分配槽位的最后一步就是把填满的块注册进前缀缓存索引 —— 也就是说,**KV 还没算出来,哈希就已经登记了**。这看着像是在缓存空数据,但它成立的前提很硬:**同一个 step 内的 forward 一定会把这些槽位写满**,所以等到别人能查到这个哈希时,数据已经就绪。

前提不成立的场景是 PD 分离 —— KV 要从远端收,不是本地算。所以分配槽位有一个「延迟注册」开关,把登记推迟到 KV 真正到位之后。

注册只针对**满块**:100 个 token 对应 6 个满块,其中前 3 个在命中时就已注册过会被跳过,尾巴上不满 16 个的那块不注册。

**阶段 3 · Decode:读**。每步只算 1 个新 token,尾块还有空位就不分配新块。这一步有个容易记错的地方:

> **decode 不走单独的 kernel 入口。** prefill 和 decode 用的是**同一个变长接口**,区别只在 query 的长度 —— decode 时每请求 1 个,投机解码时 1+k 个。

kernel 拿着块表逐块读:7 个块共 112 个槽位的空间,但按已用长度只读前 101 个。读完算出 logits、采样出下一个 token、追加进请求,然后进入下一个 step。

**阶段 4 · 完成**:引用计数逐块减一,归零的按有无哈希分流回空闲队列 —— 这条路径 5.3 已经走读过,不重复。只补一个实现细节:**释放是按倒序做的**,这样尾块排在更靠前的驱逐位置。

还有一个特别容易误解的点:

> **不是「哈希匹配才复用、不匹配才覆盖」。**

新分配从队首取块时,会**无条件**清掉这块的旧哈希再交出去。所以一个 CACHED 块能不能被复用,取决于**它被取走之前**有没有请求通过哈希查到它并引用 —— 一旦被取走,里面的内容就直接被覆盖了,不存在"比对一下发现不匹配"这个环节。

**阶段 5 · 抢占**(异常路径):释放该请求的全部块,状态置为 `PREEMPTED`(不是 `WAITING`),已算 token 数归零,投机 token 清空,抢占计数加一 —— 除此之外还要清掉一串在途状态(编码器缓存、在途 prefill 标记、异步调度的过期输出标记)。抢占的完整机制归 02 章,这里只记 KV 侧的结论:**块全还回去了,下一步重新调度时走和新请求一样的准入路径**(所以 watermark 会施加在它身上,见 4.1);如果前缀缓存还命中,公共前缀不用重算。

一个细节值得纠正常见的读法:把请求**从 running 队列摘出来**是调用方的事(方法的注释明确写了),但**放回等待队列队首**是这个方法自己做的,就在它的最后一行。

| 时机 | 操作 | 谁做 |
|---|---|---|
| 启动 | 创建 KV cache 张量并绑定到各层 | model runner |
| 启动 | 创建块池、块对象全部入空闲队列 | KV cache 管理器 |
| 请求调度 | 查前缀缓存 | 管理器 → 协调器 |
| 请求调度 | 命中的块引用计数加一、移出队列 | 块池 |
| 请求调度 | 分配新块、构造块表与槽位映射 | 管理器 → 块池 |
| **请求调度(分配的最后一步)** | **把满块注册进前缀缓存索引** | 协调器 → 块池 |
| Prefill forward | **写** KV cache | attention 后端的写入 kernel |
| Prefill forward | **读** KV cache(因果注意力) | 变长 attention kernel |
| Decode forward | **写** 1 个 token 的 KV | 同一个写入 kernel |
| Decode forward | **读** 全部历史 KV | 同一个变长 kernel(query 长度为 1) |
| 请求完成 | 释放块,按有无哈希分流 | 管理器 → 块池 |
| 抢占 | 释放块 + 重置计数 + 状态置 PREEMPTED | 调度器 |

这张表里最反直觉的是第六行:**哈希注册在调度阶段,不在 forward 之后** —— 和「KV 要先算出来才能缓存」的直觉正好相反,原因见上面阶段 2。

## Part 6|机制之外:源码里额外读到的

前四部分讲了「为什么这么设计」,Part 5 讲了「每一步落在哪」。这一部分只放**机制层面看不见、但真实存在的细节**:实现里的例外、为省一点开销做的取舍、为绕开某个具体麻烦加的小设计。前面讲过的一概不重复。

### 6.1 数据结构上的四个取舍

**① 块对象用 `slots` 省掉实例字典。** 块的元数据类声明了固定字段集合,以此替代每个实例的属性字典 —— 省下的是每实例约百字节的量级(具体值随 Python 版本和字段数变化)。块数十万级时这项优化才有意义。

**② 哈希是只读的,写入必须走 setter。** 两个哈希相关字段都只暴露只读访问,写入走一个专门的方法,**方法内部断言这个块尚未有哈希**;清除走另一个方法。这样「一个块同时挂两个哈希」这种状态在类型层面就写不出来。

**③ 块池有第四张表,前面没提过:块 id → 哈希集合的反向索引。** 正向表回答「这个哈希对应哪个块」,反向表回答「这个块身上挂了哪些哈希」—— 驱逐时要把一个块的所有哈希一次清干净,没有反向索引就得全表扫描。

**④ 有一个 null block,是从队首摘走的 0 号块。** 它用作占位(比如滑动窗口外的位置),源码注释特别提醒:**它的引用计数不维护,要特别小心别把它释放了** —— 所以块池里几乎每个循环都带一个 `is_null` 判断。

### 6.2 一个哈希可以对应多个块:刻意不去重

这是整个块池最反直觉的设计。直觉上,前缀缓存的索引应该是「哈希 → 唯一的块」,内容相同就该复用同一块。**但 vLLM 明确选择不去重** —— 一个块填满要缓存时,**不去检查缓存里是否已有内容相同的块**。

理由写在类的注释里,只有一句但很硬:**要保证已分配的块 id 不会变,这样块表才能是 append-only 的。** 块表是一个数组,某个逻辑位置一旦写进了块号就不能再改;如果因为「发现别人已经缓存过相同内容」就把已分配的块换掉,块表就不再是只追加的了,worker 侧的增量下发(见 5.1)也就不成立。

代价是同一份内容可能在缓存里存在多份,所以索引的值必须能装下多个块。这里又有一个小取舍:**值是个联合类型 —— 单个块就直接存块对象,有多个才退化成内层字典。** 理由是**降低 GC 开销**:绝大多数键只对应一个块,如果每个键都套一层字典,就会凭空多出几万个需要 GC 追踪的容器对象。代价是读取侧每次都要做一次类型分支。

**这不是哈希冲突。** 多值的来源是「相同内容被独立缓存了多次」,是设计上的取舍,不是碰撞处理。

### 6.3 空闲队列为什么是手写的

空闲队列没有用 Python 标准库的双端队列,而是把前驱/后继指针**直接放在块对象上**,手写了一个侵入式双向链表。理由是前缀缓存命中时要把一个位于链表**任意位置**的块摘出来 —— 用列表需要 O(n) 查找,标准库的双端队列干脆不支持中间删除。有了指针,摘节点就是改前后两个指针,O(1)。

还有一层前面没点破:3.5 说的那两种分流(无哈希回队首、有哈希回队尾),本质上是**同一条队列同时承担了两种语义,靠「从哪一端进」区分** —— 出队端始终是队首,所以从队首进的那批是 LIFO,从队尾进的那批是 FIFO(即 LRU)。

由此得到一个容易记反的结论:「队首是最久未用的块」**只对有哈希的那部分成立**。队首同时也是最新释放的无哈希块所在的位置 —— 两类块混在同一条链表里,靠进入端不同实现两种完全相反的复用策略。

### 6.4 注册哈希时的四个例外

**① 哈希不是块池算的。** 块池只负责把哈希写进查找表;哈希值由请求对象在**创建时以及每次追加新 token 时**就算好了 —— 这一点在注册方法的注释里写得很明确。

**② 有一个掩码参数用来跳过某些块**:null block,以及滑动窗口的尾窗、Mamba 对齐模式下要排除的块。

**③ 唯一合法的「块已有哈希还要再注册」情形,是同一个块从 partial 升级为 full。** 代码在这里加了一条断言:旧哈希覆盖的 token 数**必须严格小于**新的 —— 升级只能往前走。这时要先把旧哈希摘掉再插新的,否则同一个块会被两个键指着。

**④ 每个哈希都记着它覆盖了前缀的多少个 token。** 这个数字是未满块也能参与缓存的基础(见 3.3 的 partial 条目),也是上面那条断言的判据。

### 6.5 三个没提过的小动作

**① 前缀最多命中到倒数第二个 token。** 查找时的上限是「总 token 数减一」,不是总数 —— 因为**最后一个 token 必须重算才能拿到 logits**。全命中会导致这一步没有任何东西可算。

**② 新分配的块要先清零。** 一个块之前可能存着别人的 KV(刚被驱逐的),所以 KV cache 管理器有一个专门的方法,把这一轮新分配的块 id 排空交出去,由 model runner 在使用前清零。

**③ 哈希状态的清除不在驱逐函数里。** 驱逐函数本身只做两件事:摘哈希、广播事件。真正把块上的哈希字段复位,发生在「摘哈希」那个函数的末尾 —— 先把正反两张表里的条目都摘掉,最后才复位块上的字段。读代码时在驱逐函数里找复位会找不到。

另外一个小细节:分配新块的函数里,开缓存和关缓存走了两段**几乎一样的循环**。这不是疏忽 —— 源码注释写着这是为了**只遍历一次列表**而故意重复的代码。

## Part 7|对比与决策

前面六部分讲的是这套机制怎么来、怎么跑、代码里长什么样。这一部分回答实操里的四个问题:别人怎么做的、我这张卡能撑多少、哪几个参数该动、哪些说法是错的。

### 7.1 别人怎么做:三种前缀复用的取舍

同一个问题(怎么让公共前缀不重算),三家给了三种答案:

| 维度 | vLLM PagedAttention | SGLang RadixAttention | TensorRT-LLM |
|---|---|---|---|
| 数据结构 | 哈希表 + 侵入式双向链表 | 基数树 | 哈希表 + 链表 |
| 分配粒度 | 由 backend 申报(FA 是 16 的倍数) | 固定 | 可变 |
| 匹配粒度 | 单 group 等于块大小;多 group 可压细但只覆盖 prompt 尾部边界 | 树上任意 token 边界 | — |
| 共享前缀 | 哈希匹配 + 引用计数 | 树路径匹配 | 不支持自动 |
| 驱逐 | LRU(有哈希的块队尾进、队首出) | LRU + 树剪枝 | LRU |
| 内容去重 | **不做**(见 6.2) | 树天然去重 | — |
| 块内部命中 | 支持(partial 条目) | 支持(树分裂) | 不支持 |
| 实现复杂度 | 中 | 高 | 低 |

(竞品两列是讲稿观点,不在本仓库的源码核对范围内。)

**最值得对比的是「块内部命中」这一行,因为两家走的是完全不同的路。**

SGLang 的树分裂是**真的把一个节点拆成两个**。vLLM 选的是「一个块挂多个 key」——给已有块多注册一个指向自己的 lookup key,配合那个「覆盖到第几个 token」的字段,**不分配新块、不拷贝 KV 数据**(见 3.3)。这**不是 copy-on-write**。

代价说清楚:**命中方只能引用整个块** —— 块里超出命中长度的那些槽位对它不可用。换来的是块池结构完全不动、kernel 侧零感知。

一句话总结两边的优势:**vLLM 胜在实现简单、块大小固定(对 kernel 友好)、哈希查找 O(1)**;**SGLang 胜在能精确匹配任意长度的共享前缀,命中率更高,树结构天然支持增量更新。**

### 7.2 这张卡能撑多少并发:一个只看比值的公式

设可用 KV 显存为 M(算法见 3.4)、每 token 的单卡 KV 字节数为 p、上下文上限 max_len、请求平均长度 T、块大小 b,那么:

$$N_{\text{朴素}} = \left\lfloor \frac{M}{\text{max\_len} \times p} \right\rfloor \qquad N_{\text{分页}} = \left\lfloor \frac{M}{(T + b - 1) \times p} \right\rfloor$$

朴素管理按**最坏情况**(上限)给每个请求留空间,分页按**实际长度加最多一块的浪费**。拿本章一直在用的例子(可用 51.5 GB、单卡每 token 40 KB、上限 8192、平均 1024、块大小 16):朴素约 165 个请求,分页约 1300 个。

**关键不在这两个数,在它们的比值:**

$$\frac{N_{\text{分页}}}{N_{\text{朴素}}} = \frac{\text{max\_len}}{T + b - 1} = \frac{8192}{1039} \approx 7.9$$

M 和 p 全约掉了。**这个倍数只由「上限与实际长度之比」决定,和模型多大、显存多少完全无关。** 所以两条实践推论直接成立:上下文上限设得越离谱、请求实际越短,分页的收益越大;反过来,如果你的请求长度本来就接近上限,分页在并发数上几乎不带来提升(它仍然消除外部碎片、仍然支持前缀共享)。

还有一条必须说清楚:**算出来的 1300 是显存允许的上限,不是真能同时跑 1300 条。** 实际并发还会被并发上限、token 预算和计算吞吐卡住(02 章的三道闸门)。这个数字的意义是「**KV cache 不再是瓶颈**」。

### 7.3 关键参数:默认值与往哪边拧

这一章涉及的参数不多,但每个都有一个「默认值是什么、动它会伤到什么」的答案 —— 集中列在这里,省得回前面翻:

| 参数 | 默认值 | 作用 | 往哪边拧 |
|---|---|---|---|
| `gpu_memory_utilization` | **0.92** | GPU 显存使用比例 | 太高(0.95+)会因激活波动超出实测值而 OOM 崩溃;太低则 KV cache 不够。往 0.85~0.88 降是给激活留余量 |
| `block_size` | 未指定(兜底 16) | 每块的 token 数 | **通常不动**,让 backend 决议(见 3.2) |
| `enable_prefix_caching` | **True** | 是否开前缀缓存 | 可关,但通常不建议 |
| `cache_dtype` | `"auto"`(跟模型) | KV cache 的数据类型 | 设成 FP8 让每 token 字节数减半、块数约翻倍;代价是量化误差,长上下文场景要实测精度 |
| `prefix_match_unit` | `None` | 哈希粒度(代码里叫哈希块大小) | **仅在多个 KV cache group 时生效**,单 group 被直接忽略(见 3.3) |
| `watermark` | **0.0(关闭)** | 准入时额外留出的空闲块比例 | 默认先别动;只在指标里看到抢占次数持续偏高、且你更在意首 token 延迟稳定性时才试 0.01~0.05(见 4.1) |
| `max_num_seqs` | 128 | 并发请求数上限 | 显存充足时,真正卡住并发的往往是它而不是块数 |
| `mamba_block_size` | `None` | 混合模型里 Mamba 状态的块大小 | 一般不动 |

调参的次序建议是:**先看 7.2 算出来 KV cache 是不是瓶颈**。如果算出能撑上千并发,那瓶颈几乎一定不在块池里,去查并发上限和 token 预算,别在这一页的参数上打转。

(上面的调参方向是经验判断,不是本仓库的实测结论。)

### 7.4 常见误区

下面这几条在社区里传得很广,但拿源码一核就站不住。每条都标了正文里对应的出处:

| 误区 | 真相 |
|---|---|
| 「PagedAttention 让 attention 更快」 | 不。它解决的是**显存管理**问题;attention kernel 速度不变,甚至略慢(多了一次查表)。收益在并发数上,不在单次延迟上 |
| 「块越大越好」 | 错。块越大内部碎片越大、最坏浪费越多,前缀命中粒度也越粗(见 3.2) |
| 「配 `swap_space` 就能把 KV 换到 CPU」 | **这个字段不存在**,命令行也没有对应开关。被抢占的请求靠重算,跨层级缓存走 offload 那一套(见 4.2) |
| 「`--cpu-offload-gb` 能把 KV cache 换到 CPU」 | 不。它 offload 的是**模型权重**,和 KV 无关(见 4.4) |
| 「watermark 默认 0.01,给突发需求留了 1% buffer」 | 默认是 **0,即关闭**。而且即便开启,它也只加在准入检查上,running 请求的 decode 照样能把空闲块用到 0(见 4.1) |
| 「prefix caching 只能在块边界命中」 | 单 group 模型确实如此(协调器里有断言钉死)。多 group 混合模型下可以让 prompt 尾部那一个边界也命中,但块内其他边界仍会被跳过(见 3.3) |
| 「把 `prefix_match_unit` 调细就能提高任何模型的命中率」 | 不。单 group 时这个参数被直接忽略 |
| 「prefix caching 要手动开」 | 反了,**默认就是开的** |
