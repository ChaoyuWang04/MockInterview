# vLLM 13|多模态

一张图片要进到一个只认 token 的引擎里去。这一章讲它凭什么进得去、进去之后又为什么会把前缀缓存带沟里,以及那三层缓存各自省的是什么。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 引擎只认 token,而图片不是 token

前面十二章讲的每一样东西 —— 连续批处理、PagedAttention、前缀缓存、推测解码 —— 都站在同一个假设上:**一次请求的输入是一串 token,输出是下一个 token 的分布**。调度按 token 记账,KV cache 按 token 分块,缓存命中按 token 比对。

图片不满足这个假设。它是一段字节,要先过一个完全不同的网络才能变成向量;它变出来的向量个数不固定;而且两张内容完全不同的图,在 prompt 里留下的 token 完全一样。

于是整章要回答的是同一个问题的两半:

| 痛点 | 具体表现 | 对应机制 |
|---|---|---|
| **对齐**:一个媒体 item 到底占 prompt 里哪几个位置、占几个 | 图片变出来的向量要和文本 token 排在同一个张量里,位置必须精确 | 占位符扩展与掩码覆盖(1.19–1.26) |
| **复用**:同一个媒体 item 被反复用到时,哪些中间结果可以不重算 | 同一张图在一次请求里被几百步 decode 反复需要,在多轮对话里被几十条请求反复需要 | 三级缓存(1.27–1.36) |
| **正确性**:两张不同的图留下相同的 token,缓存会认错 | 上传的是狗,回答描述的是猫,而且完全静默 | 把媒体身份补进缓存的键(1.16–1.18) |

剩下的全是这三件事的工程化:预算与切分怎么和调度器协作(1.37–1.43),位置编码、编码器并行、视频剪枝、跨实例共享(1.44–1.48)。

### 1.2 「多模态」在 vLLM 里只指输入

最容易误解的一点先讲明白:**vLLM 的「多模态」指的是多模态输入,不是多模态生成**。进来的花样很多 —— 文本、图像、视频、音频、预计算好的 embedding;出去的只有三类:token 序列(最终 detokenize 成文本)、向量或分数、转写文本。

这一点在官方文档的排版里就能读出来:四种模态字母 T / I / V / A 是在「多模态语言模型」一节开头定义的,用法是模型表里名为 **Inputs** 的那一列;而输出维度是另一套分节 —— 文本生成、转写、实时转写、pooling。**模态是输入维度,输出维度另有分类。**

两个符号的含义要记住,后面的模型表全靠它们:`+` 表示可组合(`T + I` 是文本、图、图文都行),`/` 表示互斥(`T / I` 是文本单独或图单独,不能一次给图文对)。

于是「文生图 / 图生文 / 图生图」这套常见分类,落到 vLLM 上的答案是:

| 常见叫法 | 输入 | 输出 | vLLM |
|---|---|---|---|
| 文生文 | 文本 | 文本 | 支持。多模态模型同时保留纯文本能力,`T + I` 里的 `+` 就表示「文本单独也行」 |
| 图生文 | 图加可选文本指令 | 文本 | 支持,且是主线场景 |
| 视频生文 | 视频帧序列加文本 | 文本 | 支持 |
| 音频生文 | 音频加文本 | 文本 | 支持,另有专门的转写端点 |
| 多模态生向量 | 图、视频或文本 | 定长浮点向量或标量分数 | 支持,需显式指定 pooling 运行模式 |
| 多模态生动作 | 机器人相机图加指令 | 离散动作 token | 支持,本质仍是 token |
| **文生图 / 图生图 / 文生视频 / 语音合成** | — | 图像像素、视频帧、音频波形 | **不支持** |

多模态模型的注册表在基准上有 **120 个条目**(讲稿写的 115 是旧数)。

### 1.3 为什么出不去:三个核心机制都假设了自回归

不支持图像生成,不是「还没人写这个模型」。**vLLM 的三个核心机制都建立在自回归 token 生成这一假设上,而扩散式图像生成和它们全都不兼容。**

| vLLM 的核心机制 | 它假设了什么 | 扩散式图像生成的实际形态 |
|---|---|---|
| 采样器 | 输出是词表上的一个离散分布,采一个 token id | 输出是连续的 latent 张量,词表里没有像素这个符号 |
| PagedAttention 与 KV cache | 序列单向增长,第 t 步只依赖前面,算过的 KV 可以永久复用 | 定长 latent 反复迭代去噪,每步重算全部位置,没有「只追加」的结构,也没有可复用的 KV |
| 连续批处理与前缀缓存 | 调度单位是 token,成本随 token 数线性累加;相同前缀可跨请求复用 | 调度单位是「去噪步数乘分辨率」,成本与 token 数无关,前缀复用无从谈起 |

这张表是本章第一条痛点线的正面论证:**「引擎只认 token」不是巧合,是地基。**

代码层面有一处干净的证据。BAGEL 是一个上游支持「理解加生成」的统一模型,vLLM 接入时把生成分支的权重显式丢掉了 —— 加载权重时按关键字过滤掉 MoE 生成权重、VAE 的 latent 位置嵌入、两个方向的 LLM–VAE 投影、扩散用的时间步嵌入,以及带特定前缀的 VAE 编解码器(注释特意说明这个前缀是为了避开视觉编码器,别误伤)。同一文件的模块注释与类注释也把边界写死了:vLLM 只做图像理解那一半,图像生成部分不支持。模型表里还有一个同类的标注,某个模型的名字后面直接跟着「understanding tower」。

一句话:**vLLM 把自己定位在理解侧** —— 它要解决的是「如何把媒体高效地塞进 LLM 的上下文」,而不是「如何生成媒体」。

### 1.4 六种输入形态,走的是几条路

「支持」的那几类里,引擎侧其实只有一条主路加几条岔路:

| 形态 | 输入怎么进来 | 引擎侧走哪条路 |
|---|---|---|
| **A · 图/视频/音频加文本 → 文本** | 在线走聊天补全端点,消息内容里混排文本与媒体;离线在生成调用里放 PIL 图或列表 | **主线**,本章后面讲的全是这条 |
| **B · 音频 → 文本** | 独立的转写与翻译端点,表单上传音频文件 | 模型往往是 encoder-decoder 或专门微调的音频 LLM,调度上分叉 |
| **C · 多模态 → 向量或分数** | 向量端点,图像以 base64 传入 | **不经过采样器**,取最后一层隐状态池化的结果 |
| **D · 多模态 → 动作 token** | 机器人相机图加自然语言指令 | 结构上和普通视觉语言模型完全一样,只是输出的解释方式不同 |
| **E · 预计算 embedding 直接当输入** | 调用方自己在外面跑完编码器,把浮点张量喂进来 | **跳过 tower**,其余同 A |
| **F · 只跑 encoder,输出给另一个进程** | 媒体 | **跳过 language model**,输出视觉 embedding 传给下游进程 |

有几处值得单独点一句。

**B 的「翻译」不是语音转语音。** 那个端点指的是「语音转外语文本」,输出仍然是文本。转写端点还有两档更详细的返回形态:带时间戳的,以及带说话人分离的;流式时以分片事件返回。

**C 必须显式指定 pooling 运行模式**,否则同一个架构会被当成生成模型加载 —— 因为不少架构两种都能做。pooling 侧有六种任务:分类、向量、奖励、token 级分类、token 级向量、打分。这里也是 `/` 互斥符号最典型的用处:图文检索模型一次请求只能编码文本或只能编码图,不能编码「图文对」—— 两侧分别编码成向量再算余弦相似度,这恰好就是它的用法。

**D 说明了输出通道的本质。** 模型仍然吐词表里的 token id,但这些 token 被约定映射到离散化的动作区间,客户端再反量化成机械臂控制量。**引擎只负责在词表上产生 token 分布,token 代表什么语义是模型和调用方的约定。** 谁都可以给 token 赋予新含义,但引擎物理上不可能吐出像素或波形 —— 词表里没有这些东西。

**E 是一个把裸张量当输入的接口**,注释里带一句全大写的警告:形状传错了引擎可能直接崩,只对可信调用方开放。它还有一个省显存的用法:把某个模态的数量上限设成 0,该模态的数量校验会被跳过、编码器模块干脆不加载,但仍可用 embedding 作为输入。这一条能成立,靠的是一个容易漏掉的分支 —— 见 1.10。

**F 是唯一一个「输出不面向最终用户」的场景**,它的消费者是另一个 vLLM 进程。

### 1.5 术语:先把后面反复出现的词说清楚

| 术语 | 一句话 |
|---|---|
| **patch(图块)** | 把图片切成固定大小的小方块(常见 14×14 像素),视觉 Transformer 把每个小方块当成一个「词」 |
| **ViT(Vision Transformer)** | 输入是 patch 序列、输出是每个 patch 的向量的 Transformer。和 LLM 的关键区别是它用**双向注意力**,每个 patch 都能看到所有 patch,没有因果掩码 —— **所以它不能分块算**,这是后文很多约束的根源 |
| **patch merger(图块合并器)** | 把相邻的几个 patch 向量拼起来过一层 MLP、输出一个向量。作用是**降 token 数**:2×2 合并能让 decoder 侧的序列长度直接省四倍 |
| **tower(塔)** | 那个视觉或音频编码器子网络。叫 tower 是因为它像「挂在 LLM 旁边的一座塔」,权重独立、可以单独不加载 |
| **connector(连接器)/ projector(投影层)** | tower 的输出维度和 LLM 的隐层维度不一样,中间需要一层线性或 MLP 做维度对齐加语义对齐 |
| **embedding(嵌入向量)** | 一个 token 位置对应的隐层维浮点向量。文本 token 的从查表来,视觉 token 的从 tower 加 connector 算来 —— **两者最终在同一个张量里并排躺着,decoder 不区分它们的来源** |
| **feature size(特征长度)** | 一个多模态 item 最终占用多少个 embedding。有的模型固定,有的随分辨率变化 |
| **placeholder token(占位符 token)** | prompt 里预留给多模态数据的 token。它们会被 tokenizer 正常编码成 token id,但在前向之前,它们的 embedding 会被**覆盖**成视觉 embedding |
| **encoder cache(编码器缓存)** | 缓存 tower 加 connector 的输出,避免同一张图重复过 ViT。注意它缓存的是 **embedding,不是 KV cache** |

### 1.6 tower 与 ViT 不在同一个维度上

这两个词经常混着用,但它们回答的是不同的问题:

| 维度 | ViT | tower |
|---|---|---|
| 词性 | **架构名**:一类网络长什么样 | **角色名**:这块子网络在组合模型里担任什么职责 |
| 谁定义的 | 学术界 | vLLM 的代码约定 |
| 能否互换 | 换成别的结构后就不叫 ViT 了 | 换成任何编码器,它仍然是 tower |
| 关系 | ViT 是目前最常见的 tower 实现 | tower 是更大的那个集合 |

基准上 tower 至少有三种实际形态,足以说明它确实不等于 ViT:视觉 ViT(最常见);**音频编码器** —— 某些模型的音频塔是「卷积下采样加 Transformer」的结构,没有 patch、没有二维位置,**不是 ViT**,但在角色划分里是标准的 tower;以及从通用图像骨干库里取来的骨干网。

**那么代码里怎么判定「这块是不是 tower」?不是看属性名。** 各家取名毫无统一:有的叫 `vision_tower`,有的叫 `visual`,有的叫 `audio_tower`,有的叫 `vision_backbone`,还有的干脆叫 `encoder` 或 `whisper_encoder`。真正的判据是**它是否在那个标记 tower 的上下文管理器里被构造**;至于这座塔叫什么名字,由它负责的模态集合推导 —— 模态恰好是图像加视频时叫视觉塔,否则把模态名和 `tower` 拼起来。

一句话记法:**ViT 回答「它长什么样」,tower 回答「它站在哪里、能不能被摘掉」。**

### 1.7 三段结构:两个预训练模型加一座新训的小桥

主流开源多模态 LLM 几乎都是同一个骨架。下图把「哪一段由谁主导」标了出来:

```text
图片字节
   │
   ▼
 ① 预处理(CPU,不属于任何一个模型)
   │  解码 → resize → normalize → 切 patch → 像素张量
   ▼
 ② TOWER:视觉或音频编码器(GPU)
   │  patch embed → 编码器 Block × L(双向注意力)→ patch merger
   │  权重来源:独立预训练的视觉模型
   │  输出维度 d_vis,是【视觉模型的隐层维度】
   ▼
 ③ CONNECTOR:唯一的缝合层(GPU)
   │  linear_1(d_vis → d_llm)→ 激活 → linear_2(d_llm → d_llm)
   │  多模态微调阶段唯一必须新训的一段,参数量最小
   │  职责有两个:维度对齐,以及把视觉特征翻译进 LLM 的词嵌入空间
   ▼
 ④ 拼接(由 runner 主导,不属于任何一个模型)
   │  文本:token id → 查词嵌入表
   │  覆盖:按布尔掩码把视觉 embedding 写进对应的那些行
   │  ★ 联结点在这里:不是「网络连线」,而是往同一个张量的指定行里写数据
   ▼
 ⑤ LANGUAGE MODEL:LLM decoder(GPU)
      权重来源:独立预训练的纯文本 LLM
      输入已含视觉信息,它【看不出】哪几行来自图片
      因果注意力 + PagedAttention + KV cache
      decoder layer × N → norm → 输出头 → logits → 采样 → 自回归 decode
      (decode 阶段 tower 与 connector 完全不参与)
```

connector 的两层在代码里是**列切分加行切分**的一对并行线性层 —— 也就是标准 MLP 的张量并行写法,中间不需要通信。第一层的激活函数**由配置决定,不是写死的**。

顺带纠正一个常见的参数量估算:connector 不能按「两层都是 `d_llm × d_llm`」算。**第一层是 `d_vis → d_llm`,是长方形的**,所以参数量是 `d_vis × d_llm + d_llm × d_llm`,而不是 `2 × d_llm²`。以 `d_vis = 1280`、`d_llm = 3584` 为例约 1740 万,而不是按方阵算出来的 2570 万。占全模型的比例仍在千分之几这个量级,结论不变,但算式不能照抄。

### 1.8 三个缝合点,只有一个在网络里

多模态模型不是「把两个网络串成一个大网络」,而是在三个维度上各打了一个补丁:

| 缝合维度 | 问题 | 解法 | 在哪一层 |
|---|---|---|---|
| ① 维度缝合 | tower 输出 `d_vis` 维,LLM 要 `d_llm` 维 | connector 投影 | **网络结构** |
| ② 位置缝合 | 视觉向量该放在序列的哪几行 | 占位符扩展加布尔掩码覆盖 | 推理框架 |
| ③ 生命周期缝合 | tower 只在 prefill 跑一次,LLM 每步都跑 | 编码器缓存把 tower 输出存起来跨 step 复用 | 推理框架 |

**只有 ① 是网络结构层面的连接,② 和 ③ 都是推理框架层面的工程。** 这解释了一件乍看反常的事:**vLLM 的多模态代码量绝大部分不在模型文件里**,而在多模态包与 runner、scheduler 里。

这张表也是本章第一条痛点线的落点:1.1 说的「对齐」就是 ②,「复用」就是 ③。

### 1.9 谁是 tower:代码里有两套各自独立的答案

1.6 说判据是「在不在那个标记 tower 的上下文管理器里被构造」。这话对,但只对了一半 —— **基准上「谁是 tower」这个问题有两套互不相干的登记方式,服务于两件不同的事**:

| 登记方式 | 形式 | 服务于 |
|---|---|---|
| 标记 tower 的上下文管理器 | `with` 块,构造期生效 | 权重加载与显存:**整段跳过不加载**;以及走 offload 路由 |
| 模块前缀映射 | 一个返回三元组的方法,声明 language / connector / tower 各是哪些模块前缀 | **LoRA 模块过滤** |

两套的口径**对 connector 的归属正好相反**。以某个音频模型为例:它的 `with` 块里既建了音频编码器**又建了 connector**,所以在加载与显存的口径下 connector 属于塔的一部分;而同一个类的前缀映射里,connector 被单列成一类,和塔并列。视觉侧同样如此 —— 那个把视觉塔和投影层建在同一个 `with` 块里的写法是通例,不是个别模型的疏忽。

**所以「tower」这个词在讨论加载与显存时指的是「视觉侧整体(编码器加投影层)」,只有在讨论网络结构或 LoRA 时才特指编码器本体。** 读代码时看到两处结论不一致,先分清在问哪一件事。

上下文管理器那一路还有一个注释点明的额外职责:被标记的组件会**一并路由进当前的 offload 器**(在它支持塔卸载时),因为构造层栈的那个工具只看得见 decoder 的层堆叠、看不见塔。所以这个标记不只决定「加不加载」,也决定「能不能被卸载到别处」。

### 1.10 权重加载:三段前缀映射,以及它买到了什么

checkpoint 的键名到 vLLM 模块路径的映射里,能一眼看出三段结构 —— 视觉塔的权重、connector 的权重、LLM 的权重各有各的前缀,分别映射过去。

有了 1.9 的标记加这套前缀映射,框架就知道哪些权重属于塔,可以**整段跳过不加载**。「只加载语言模型」这个开关的省显存效果就是这么实现的,反过来「只跑编码器」那个开关跳过的是语言组件 —— 正好相反的一半。

判定走哪条路的那个函数不在模型注册表里,而是多模态注册表上的一个方法(**同名文件有两处,核对时容易走错**)。它的逻辑比讲稿说的多一个分支:

- 模型本身不是多模态的 → 文本模式;
- 建不出处理信息 → 文本模式,并打一条 warning。但**推测解码的草稿模型是个例外**:有些草稿模型声明自己支持多模态,只是为了消费目标模型合并好的 embedding,它们从来不跑自己的多模态处理器 —— 对它们来说文本模式是预期结果,所以这条 warning 被特意跳过了;
- 所有支持的模态上限都是 0 → 通常是文本模式,**但如果打开了预计算 embedding 那个开关,仍然返回「是多模态」** —— 因为即使编码器不跑,处理预计算 embedding 也还需要多模态那套基础设施。

**最后这一条正是 1.4 场景 E 那个「limit 设 0 省显存但还能喂 embedding」的实现依据。** 讲稿在讲场景 E 时描述对了行为,在讲加载时又漏了让它成立的分支;两处合起来看才完整。

### 1.11 一次请求的算力与显存花在哪

| 阶段 | 主导模块 | 设备 | 瓶颈类型 | 可缓存 |
|---|---|---|---|---|
| ① 预处理 | HF 处理器(非模型) | **CPU** | 单线程、纯 CPU | 是 —— 处理器缓存 |
| ② tower | 编码器 | GPU | **compute-bound**(双向注意力,小算子密集) | 是 —— 编码器缓存 |
| ③ connector | MLP | GPU | 可忽略 | 与 ② 一起缓存 |
| ④ 拼接 | runner(非模型) | GPU | 一次掩码写入 | — |
| ⑤ prefill | LLM | GPU | compute-bound | 是 —— KV 前缀缓存 |
| ⑥ decode × N | LLM | GPU | **memory-bound** | KV 复用 |

**② 与 ⑤⑥ 的瓶颈类型不同,但它们共享同一张卡、同一个 step。** 编码器是双向注意力的小算子密集型,LLM 的 decode 是权重带宽型;两者挤在一起,正是编码器需要一份独立计算预算的原因(那份预算在调度器的记账里是独立一项,见 02 章 3.1 与 3.3)。

这一节给的是定性归属,具体数字留到本章的成本量化一节。

### 1.12 朴素做法的四堵墙

假设不做任何工程优化,最直白的实现是:**每次前向之前,把该请求所有图片过一遍 tower,拼进 embedding,然后跑 decoder。** 单机脚本就是这么干的。

放进 vLLM 这种连续批处理的服务里,它会立刻撞上四堵墙。前三堵是效率问题,第四堵是**正确性**问题 —— 而且它完全静默。

### 1.13 墙一:每个 decode step 都重算 tower

decode 阶段每步只算一个 token,但朴素实现为了拿到完整的输入 embedding,会把图片再过一遍编码器。

量级上,一次视觉塔前向的算力相当于**几百步 decode**(按「两倍参数量乘 token 数」的口径,一张高分辨率图的塔前向是数 TFLOPs,而 7B 模型 decode 一步是十几 GFLOPs)。如果这条请求要输出几百个 token 而每步都重算,等于把整个请求的算力放大了两三个数量级。

对策是把编码器的执行限制在 prefill 阶段,输出存进编码器缓存。**这是「生命周期缝合」(1.8 的 ③)存在的唯一理由。**

### 1.14 墙二:同一张图跨请求重算

多轮对话里,第二轮会把第一轮的图片连同历史一起重发;检索或 agent 场景里,同一张示意图会被几十个请求引用。朴素实现按请求隔离,每次都重算。

对策是让编码器缓存用**内容哈希**作键,而不是请求 id。**这是 vLLM 与很多实现的关键差异** —— 键选错了,跨请求复用就无从谈起,而这类复用恰恰是多模态服务里占比最大的一类。

### 1.15 墙三:预处理在 CPU 上,而且在 API 进程里

解码 JPEG、resize、normalize、切 patch,有些模型还要动态切图 —— 这些是纯 CPU 且单线程的。官方设计文档直接点名:某些模型的 HF 处理器**非常慢**,并链到了对应的 issue,紧接着就说明了对策是缓存处理器的输出。

这一步还在 **API 进程**里跑,会挤占请求接入本身。基准上有两个独立的池分别兜这两件事:媒体加载线程池(默认 8),以及音频预处理工作进程数 —— 后者被**死死压在 2 以内**(取 CPU 核数与 2 的较小者)。两个数字差这么多,说明瓶颈被拆成了「下载与解码」和「预处理」两段,而真正吃 CPU 的那段不敢放开。

### 1.16 墙四:前缀缓存会张冠李戴

这是最凶险的一堵。tokenize 之后,**两个图片完全不同的请求,其 token id 序列可能一模一样**:

```text
请求 1: [<|vision_start|>, <pad> x16, <|vision_end|>, "这", "是", "什", "么"]   传的是猫
请求 2: [<|vision_start|>, <pad> x16, <|vision_end|>, "这", "是", "什", "么"]   传的是狗
```

token id 一样 → 块哈希一样 → 请求 2 命中请求 1 留下的 KV cache → **用户传的是狗,模型读到的是猫的 KV,于是回答描述的是猫。**

### 1.17 为什么「内容都一样」却会出错:KV 不是 token id 的函数

关键在于**占位符 token 的 token id,与它实际参与计算的向量之间没有任何关系**。把两条链路摆在一起就清楚了:

```text
纯文本 token
   token id --查词嵌入表--> 向量 v
       v 由 token id 唯一决定
   v --decoder 层--> K/V 写入 block

占位符 token
   token id --查词嵌入表--> 向量 v0
       v0 被丢弃
   图片字节 --tower + connector--> 向量 v'
       v' 由【图片内容】决定,与 token id 无关
   v' 覆盖进 inputs_embeds 的对应行
   v' --decoder 层--> K/V 写入 block
```

于是:

- **纯文本场景**:`token id 前缀相同 ⇒ 每个位置的输入向量相同 ⇒ KV 相同`。这条蕴含关系成立,所以只按 token id 算哈希是安全的。
- **多模态场景**:这条蕴含关系**被打破**。占位符的 token id 恒定不变,但它们对应的输入向量取决于是猫还是狗 —— 同一个 token id 序列可以对应无穷多种输入向量,从而对应无穷多种 KV。此时按 token id 算出的哈希不再是 KV 内容的可靠标识,**它变成了一个会碰撞的键**。

一句话:**前缀缓存的正确性前提是「前缀 token 相同 ⇒ 前缀 KV 相同」,占位符机制把这个前提打破了。**

走查一遍错误是怎么发生的(设块大小 16,请求 1 先跑完):

```text
① 请求 1(猫)prefill
     tower(猫) → v_cat,覆盖进占位区
     decoder 前向 → 某个块的 K/V 里编码的是【猫】的信息
     块哈希 = hash(前块哈希, token_ids)      注意:只喂了 token id
     登记:该哈希 → 该块

② 请求 2(狗)到达,查前缀缓存
     块哈希' = hash(前块哈希, token_ids)
     token_ids 与请求 1 逐个相同 → 两个哈希相等 → 命中
     复用该块,已算 token 数直接跳到 16

③ 连锁反应:tower 也不跑了
     调度器按【已算 token 数】去框这一步要编码哪些多模态 item
     狗这张图的占位区落在「已计算」区间之前
     → 该 item 不进入调度窗口 → tower(狗) 从头到尾没有被执行
     → v_dog 从未产生,更没写进任何地方

④ decode 阶段
     注意力读到的全是猫的 K/V
     模型据此生成 → 输出描述的是猫
     用户看到的现象:上传了狗,回答却在讲猫,而且完全静默、没有任何异常
```

**第 ③ 步是这个 bug 最隐蔽的地方:它不是「两份 embedding 弄混了」,而是狗的 embedding 压根没被计算过。** 缓存命中让调度器认为这段前缀无需重算,连编码器都被顺带跳过 —— 而这个「跳过」在正常情况下恰恰是一项优化。

### 1.18 对策:把媒体身份补进键,让前提重新成立

既然「token id 相同」不足以判定「KV 相同」,就把决定 KV 的另一个因素 —— **媒体内容** —— 也放进键里。

块哈希的输入本来就不只有 token id:它还接一串**附加标识**,按固定顺序拼成一个列表。多模态输入的标识是其中一项,和 LoRA 标识、缓存盐、prompt embeddings 指纹并列。**这套附加标识的机制、顺序与它解决的问题,04 章 1.4 已经完整展开,这里不重复** —— 本节只补它在多模态这一侧特有的两点。

**第一,多模态那一项不是一个哈希,是一串二元组。** 每一项形如「媒体内容哈希加它在本块 token 里的起始偏移」,因为一个块里可能坐落着多个媒体 item,也可能只装得下一个 item 的一部分。加进去之后,猫和狗的块哈希不再相等,请求 2 正常 miss、正常调度自己的 tower、正常算自己的 KV。

**第二,起始偏移也是必需的,不是凑数。** 同一张图放在 prompt 开头,和放在 prompt 中间,因果注意力看到的前文不同,算出来的 KV 就不同,必须区分开。

实现上还有一处值得记一笔:这段扫描是**带游标推进的**,它假定媒体 item 已按位置排好序,并且在块的起始 token 已经越过最后一个 item 的尾巴时**直接返回** —— 这在 prefill 后期和整个 decode 阶段是常态,省掉了每块都遍历一遍全部 item 的开销。

官方设计文档里有专门一节讲这个机制,是文档中少数几处把多模态与前缀缓存放在一起讲的地方。

### 1.19 占位符扩展:把一个标记扩成 N 个 token

回到 1.1 的第一条痛点:**对齐**。

用户写的 prompt 里只有一个图像标记,但视觉 embedding 有 N 个。这 N 个 embedding 必须在 prompt 的 token 序列里**真实占位**,否则位置编码、注意力掩码、KV cache 的块划分全都会错位。

所以 vLLM 做的是**占位符扩展**:

```text
① 用户 prompt
     "<vision_start><image_pad><vision_end>这是什么?"

② 预处理器处理图像,算出这张图占多少个 embedding
     feature size = 16

③ 把 1 个占位标记扩成 16 个,这是 token 级替换
     [vision_start, pad x16, vision_end, 这, 是, 什, 么]

④ 记录占位区的位置:起点 1,长度 16

⑤ 前向之前,用视觉 embedding 覆盖这一段的 embedding
```

注意第 ③ 步发生在 **tokenize 之后、进引擎之前**,是一次纯粹的序列长度对齐。

### 1.20 占位 token 不是虚拟的

占位 token **不是标记位,也不是占坑用的假东西,它是词表里真实存在的 token id**。它们经过 tokenizer、进入调度器的记账、占 KV cache 的块、参与位置编码,一路和普通文本 token 待遇完全相同。

唯一的特殊之处发生在前向之前的最后一刻:这些位置对应的 embedding 行被视觉 embedding **覆盖**掉,它们自己查表得到的值从来不会被真正用到。

理解占位机制的关键在于看清一个事实:**LLM 的输入是一个「序列长度乘隐层维度」的向量序列**,视觉信息要进 LLM,就必须变成这个序列里的若干行。而 vLLM 整条流水线 —— 调度预算、分块预填充的切分、KV cache 块分配、位置编码、前缀缓存哈希 —— **唯一的计量单位是 token**。

于是问题变成:一张图要占 16 行向量,这件事怎么让「只会数 token」的引擎知道?答案就是占位 token:**给图片在 token 账本上开 16 个条目**。图片本身不是 token,但它在 token 世界里有 16 个影子,引擎数影子就等于数了图片。

有一个实现细节侧面印证了「占位 token 的 embedding 值本身毫无意义」:**有些模型的多模态 token id 超出了语言模型的词表范围**(判据就是一句「有没有 token id 大于等于词表大小」)。这时查表会越界,所以框架先把这些位置的 id 掩成 0 再查表。那个开关的注释把理由写得很干脆:既然多模态 embedding 随后会散布到结果上,算文本 embedding 时就**显式地把所有多模态 token 掩掉**。**它只是个位置。**

### 1.21 不占位会发生什么:逐个子系统看后果

假设省掉扩展这一步,prompt 里只留一个标记,指望在 embedding 层直接把 16 行插进去。那么:

| 子系统 | 它以为的长度 | 实际长度 | 后果 |
|---|---|---|---|
| 调度器 token 记账 | 7 | 22 | 已算 token 数与每步预算全线偏小;prefill 什么时候算完判断错,请求可能永远不结束或提前进 decode |
| KV cache 块分配 | 7 | 22 | 按 7 个 token 申请的块装不下 22 个位置的 K/V,越界写或覆盖别人的块 |
| 分块预填充的切分 | 按 7 切 | 需按 22 切 | chunk 边界落在错误位置,切出来的 token 区间与实际前向的行数对不上 |
| 前缀缓存哈希 | 对 7 个 token id 算哈希 | — | 「图 A 加同一问题」和「图 B 加同一问题」的 token 序列完全相同,哈希相同,直接张冠李戴(这正是 1.16 那个坑的另一半) |
| 位置编码 | 图后面的文本从位置 2 开始 | 应从位置 17 开始 | 位置编码整体错位;而且训练时是按展开后的序列训的,不展开就是分布外输入 |
| 预处理器校验 | — | — | 直接抛错:预处理器普遍要求占位符数量与图像特征数严格一致 |
| runner 的写入定位 | — | — | 视觉 embedding 靠布尔掩码写进去,而掩码是从「哪些 token id 是多模态 token」匹配出来的。**没有占位 token,就没有掩码,也就无处可写** |

把这张表倒过来看,就是占位机制真正买到的东西:**用预处理阶段一次「长度对齐」,换取整个引擎不需要区分文本 token 和视觉 token。** 调度器、块管理器、注意力核、前缀缓存全都不知道多模态的存在,它们只看到一段普通的 token 序列。这是「占位」这个看似笨拙的做法能撑起一百二十个模型架构的原因。

### 1.22 代价:一条必须精确成立的硬不变量

好处不是免费的。既然引擎按占位 token 数分配一切资源,那么**占位 token 数必须精确等于视觉 embedding 数,多一个少一个都是 bug**。全链路多处断言它:预处理阶段有一道校验,写入阶段还有一次 —— 后者的报错信息直接写出「试图把 M 个多模态 token 赋给 N 个占位符」。

这条不变量也是接入新模型时最容易翻车的地方:模型侧声明「这张图占多少个 token」的那个方法,必须和 tower 实际输出的行数完全一致。漏算 patch 合并带来的四倍缩减、或者忘了算图像里那些夹缝分隔 token,都会在运行时直接报错。

**报错是好事。** 这条不变量的价值恰恰在于它是硬的:错了当场炸,而不是像 1.16 那个缓存坑一样静默地给出错误答案。

### 1.23 一个贯穿后文的例子

后面的走查都用这个例子,参数取一个真实的视觉语言模型配置量级:patch 边长 14,2×2 合并,视觉维度 1280,LLM 隐层 3584。

```text
图 A:112 x 112 像素
    patch 数 = (112/14) x (112/14) = 8 x 8 = 64
    2x2 合并后视觉 token = 64 / 4 = 16
    视觉 embedding 张量 [16, 3584],bf16 约 114 KB
    预处理器输出的像素张量 [64, 1176],bf16 约 150 KB

图 B:224 x 112 像素
    patch 数 = 16 x 8 = 128
    视觉 token = 32
    视觉 embedding [32, 3584] 约 229 KB

三条请求
    R1 = 图 A 加「这是什么?」
    R2 = 图 A(同一张,同 URL)加「图里有几只猫?」
    R3 = 图 B 加「这是什么?」
```

R1 扩展后是 22 个 token:下标 0 是视觉起始符,1 到 16 是占位区,17 是视觉结束符,18 到 21 是四个文本 token。

### 1.24 16 不是上限,是这张图算出来的结果

**每张图占多少个 embedding 完全由它自己的分辨率决定,没有全局固定值。** 图 B 就是 32 个,处理方式和图 A 一模一样,只是所有长度换成 32。通用算式是「时间乘高乘宽的网格数,除以合并边长的平方」。

固定长度还是动态长度**取决于模型**:有的模型把任何输入图都缩放到固定尺寸,所以永远是同一个数;走动态分辨率的模型不缩放,于是每张图长度不同。

变长带来三处真实的工程处理:

- **张量拼接不能用堆叠。** 同一批次里图 A 和图 B 的像素张量第一维不同,堆不成规整的三维张量。所以这类字段被声明成「按尺寸列表扁平拼接」:沿第一维直接拼成一个大张量,再靠一个记录各图网格尺寸的数组标出每个 item 的边界,反向切分时按尺寸还原。
- **tower 内部用累计长度做变长注意力。** 拼在一起的 patch 属于不同的图,注意力不能跨图串扰。做法和 02 章 2.7.4 讲的变长注意力**完全同构** —— 从网格尺寸算出累计长度边界传给注意力核,每张图只在自己的区间内做双向注意力。
- **显存预留按最坏情况。** 既然长度不定,显存探测阶段就用「特征最多的那张图」造假数据,预算里的每批最多 item 数也按最坏单 item 算。副作用是 tower 的输入形状**数据相关**,CUDA Graph 需要按 token 数分桶,视频路径干脆禁用(见 1.47)。

### 1.25 占位区里还夹着真文本 token

上面的例子里占位区的每个位置都要被视觉 embedding 覆盖。但**有些模型会在视觉 token 之间插入真正的文本 token 当分隔符** —— 比如每行结束插一个换行标记、图像结束插一个结束标记。

这些分隔 token 的 embedding 必须走文本词嵌入表,不能被视觉 embedding 覆盖。于是占位区的记录里多了一个布尔掩码,逐位标出「这个位置要不要被覆盖」。

```text
某模型风格:图 A 切成 4x4 个合并后的 patch,每行末尾插 1 个分隔符

占位区共 20 个 token 位置
    V V V V B  V V V V B  V V V V B  V V V V B
    掩码      = [T,T,T,T,F, T,T,T,T,F, T,T,T,T,F, T,T,T,T,F]
    占位区长度 = 20    在 prompt 里占 20 个 token 位置
    需要的向量 = 16    但只需要 16 个视觉 embedding
```

### 1.26 两个数字的分工

上一节那两个数字必须分开记,后文的预算与切分逻辑全靠它们区分:

| 量 | 含义 | 谁在用 |
|---|---|---|
| 占位区长度 | 占多少个 prompt token 位置 | 调度器的 token 预算、KV 块分配、分块预填充的切分 |
| 需要的向量数 | 需要多少个编码器输出向量 | 编码器缓存的容量与计算预算 |

编码器缓存的类注释特意强调了这一点:它**按多模态 embedding 计量,而不是按编码器 token 计量**,夹在 embedding 之间的分隔或文本 token **不占缓存额度**。

实现上,那个布尔掩码预先算好了前缀和,并且缓存起来只算一次,这样「prompt 的第 i 到第 j 个位置对应第几个到第几个向量」可以常数时间查表。分块预填充把占位区切两半时,就靠这个映射算出本块该取编码器输出的哪一段(见 1.41)。

### 1.27 三级缓存:它们是串联的

现在转到 1.1 的第二条痛点:**复用**。

多模态路径上串了三层各自独立的缓存,它们分别消掉 1.12 那四堵墙里的第三、第一加第二、第四堵:

| 级别 | 缓存内容 | 键 | 位于 | 容量单位 |
|---|---|---|---|---|
| **预处理器缓存** | 预处理器输出的像素张量与网格元数据 | 媒体内容哈希 | API 进程,加上引擎进程的一份镜像 | 字节(默认 4 GiB) |
| **编码器缓存** | tower 加 connector 的输出,即视觉 embedding | 内容哈希,挂了 LoRA 时带前缀 | GPU worker,元数据在调度器 | **embedding 个数** |
| **KV 前缀缓存** | decoder 的 KV cache 块 | 块哈希,里面混了媒体哈希 | GPU worker | 块 |

**关键在于它们是串联的**:命中第三层时可以完全跳过这段 prefill,连编码器都不用跑(这里有一个反直觉的例外,见 1.38);只命中第二层时跳过 tower;只命中第一层时跳过 CPU 预处理。

### 1.28 第一级:跨进程的镜像缓存

vLLM 是多进程架构:API 进程做 tokenize 与多模态预处理,引擎进程做调度,worker 进程做前向。预处理结果要跨进程送过去,而一张百万像素图的像素张量可能有几十 MB —— **序列化本身就成了瓶颈**。

所以这一级不是一个缓存,是**一对互为镜像的缓存**:

```text
API 进程                          引擎进程
  发送侧缓存                        接收侧缓存
    哈希 -> 只存「大小」               哈希 -> 存真实张量
    (元数据,不存数据)
       |
       |  先问一句:这些哈希缓存了吗
       |
       +--- 只把答「没有」的那些 item 的张量放进跨进程消息
            已缓存的 item:数据字段置空
```

**发送侧只存元数据不存数据。** 它的作用只是知道「对面那份有没有」,所以只需要记住每个哈希的字节数用于容量核算,真张量在对面。

不过「4 GiB 只吃一份」这个说法**只在默认的单 API 进程配置下成立**。配置项自己的注释给的是通式:总占用等于这个值乘以「API 进程数加数据并行度」—— 因为镜像关系一旦不成立(见本节末尾),每个 API 进程都会退化成持有真数据的独立缓存。**配额是按进程算的,不是全局一份。**

还有一条边界值得记:**单个 item 大于整个预算时不会失败**,而是降级成不走缓存并打一条警告。

数据字段可以为空这件事在源码注释里写明了用途:**item 已缓存时跳过 API 进程与引擎进程之间的传输**。这就是命中时省下序列化的机制。

### 1.29 镜像为什么必须严格同步驱逐

这一对缓存的契约很硬:**查询可以在发送侧随便调多少次,但「取用并更新」必须在两侧一前一后各调一次。**

理由是驱逐。两边都用最近最少使用的淘汰策略,而这个策略依赖访问顺序。**顺序错了,两边的访问序就不一致**,于是出现发送侧认为「对面有」、而对面已经淘汰掉了的漂移。

这种漂移真的会发生,代码里专门有一个错误类型处理它:接收侧发现要的 item 没有数据、又没随消息带数据时抛出,并把**这条请求里所有漂移的哈希一次性回传**,让发送侧一把丢弃全部陈旧条目 —— 而不是一个一个来回试。

这一级还有两种后端(进程内字典加跨进程省传,或共享内存对象存储直接零拷贝共享),以及几种直接失效的情况:多个 API 进程时、或数据并行且无外部负载均衡时,一对一的镜像关系根本不成立,于是退化成只在 API 进程侧缓存 —— **省 CPU 但不省传输**;把容量配成 0 则整层关掉。

### 1.30 第二级:键是内容哈希,不是请求 id

这是本章最核心的机制。

键取的是媒体 item 的**内容标识**。所以例子里 R1 和 R2 用的是同一张图 A,R2 被调度时直接命中,**完全跳过 tower**。类注释写得很明确:缓存的存在就是为了让**不同请求之间**共享同一个媒体 item 的 embedding。

这正是 1.14 那堵墙的解法。键要是选成请求 id,多轮对话里第二轮重发的同一张图就一次也复用不上。

容量单位是 **embedding 个数**,不是字节也不是 token 数 —— 呼应 1.26。默认值跟着每步 token 预算走。按例子 E 算:预算 8192 时能存 8192 个视觉 embedding,约合 512 张图 A;真实显存占用约 56 MB,相对 KV cache 很小。

### 1.31 惰性驱逐:先进可回收队列,需要时才真删

缓存条目有三种状态,靠三个集合区分:被引用的、引用为空可回收的、本步真正被驱逐的。

```text
不存在 --分配--> 被引用 {R1}
                   |
                   |  R1 用完这张图
                   v
               引用为空,仍在显存里,进可回收队列
                   |
    +--------------+---------------+
    |                              |
新请求 R2 又要这张图            空间不够触发驱逐
    |                              |
从可回收队列弹出,复活           真删,记进「本步已驱逐」
零成本                          容量加回
```

**「先进可回收队列、需要时才真删」是为了让刚用完的图还能被后续请求捡回来。** 驱逐时按**先进先出**淘汰,即最早变成可回收的先被牺牲。

### 1.32 控制面记账,数据面延后执行

上一节的「驱逐」只是调度器侧的记账,**显存不会立刻释放**。真正的删除发生在 worker:被驱逐的哈希随调度输出下发,worker 收到后才真的释放。源码注释直接点明了这个分工 —— 驱逐在这里发生,但物理内存要等模型运行器被调度输出通知之后才释放。

这和 PD 分离里 KV 块的引用计数归还语义是**同一种思路:先在控制面记账,数据面延后执行**。

延后还带来一个顺手的好处:一个在调度过程中早早被驱逐的条目,**可能在同一轮里又被重新分配**。所以真正下发给 worker 的「已驱逐」列表会先过滤一遍,把那些又活过来的剔掉,免得 worker 白删一次再重算。

### 1.33 编码器和 decoder 共享同一个 step

有一个流传很广的说法是「视觉编码器有单独的运行器,不影响 decode 的批次」—— **这是错的**。

真实情况是:tower 前向和 decoder 前向在**同一个执行调用里顺序执行** —— 预处理阶段先跑编码器,然后才跑 decoder。所以:

- **tower 的耗时直接加到这个 step 的延迟上**,会推高同批次里所有 decode 请求的每 token 时延。这和 02 章 1.3 讲的「prefill 阻塞 decode」是同一类问题 —— 只是这次挤进来的不是 prefill chunk,而是一次视觉塔前向。
- 正因如此,才需要一份**编码器计算预算**来限制单步最多跑多少编码器计算(见 1.37)。

### 1.34 第三级:媒体身份怎么混进块哈希

这一级的机制 1.18 已经讲完,**04 章 1.4 也完整展开过附加标识本身**,这里只补两条由「二元组加起始偏移」这个形式直接推出的性质:

**只有覆盖到占位区的块才被「污染」。** 例子 E 里块大小取 16 时,覆盖 token 0 到 15 的那一块会带上图 A 的哈希;如果 prompt 后面还有一百个纯文本 token,那些块的哈希**不含媒体哈希,跨请求依然可共享**。换句话说,多模态只让前缀缓存在图片所在的那几块上失去通用性,不影响后面的纯文本部分。

**带上起始偏移是为了区分「同一张图出现在不同位置」。** 同一张图放在 prompt 开头和放在中间,因果注意力看到的前文不同,KV 就不同。

### 1.35 三个 ID 各管一级

三者容易混,但代码里分得很清:

| 字段 | 含义 | 用于 | 含 LoRA 前缀 |
|---|---|---|---|
| 媒体内容哈希 | 媒体内容加预处理器参数的哈希 | 预处理器缓存的键 | 否 |
| 标识符 | 媒体哈希,或加上适配器名前缀 | **编码器缓存的键** | 是 |
| 用户传的 uuid | 用户自己声明的媒体 ID | 直接当作媒体哈希用,免哈希计算 | 否 |

**为什么编码器缓存要加 LoRA 前缀**:如果给 tower 或 connector 挂了 LoRA,同一张图在不同适配器下的视觉 embedding **是不同的**。而预处理器的输出与 LoRA 无关,所以第一级可以共享、第二级必须区分。这是两个 ID 分开的唯一原因。

**用户 uuid 的用途**:客户端如果知道「这张图我上次已经发过」,可以只传 uuid 而把媒体内容置空,服务端从缓存里取 —— 省掉整个上传加预处理链路。有一个坑:如果同时传了预处理器参数,系统**仍然会把参数混进哈希**,因为不同参数出来的张量不同,不能共用一个键。

顺带一提,当第一级容量配成 0 且前缀缓存关闭时,用户 uuid 会被**直接忽略**、换成一个合成 ID —— 因为此时没人会用这个键,算内容哈希纯属浪费。

### 1.36 三级命中率怎么叠乘

设一个多轮对话场景:平均每轮重发历史(含一张图),平均四轮。以下全部是**按参数量与带宽推的量级参考,不是实测**:

| 阶段 | 单次成本 | 无缓存四轮 | 三级全命中后 |
|---|---|---|---|
| 预处理(CPU) | 25 ms | 100 ms | 25 ms(后三次命中第一级) |
| tower 前向(GPU) | 39 ms | 156 ms | 39 ms(后三次命中第二级) |
| decoder prefill(GPU) | 56 ms | 224 ms | 56 ms 加三次增量(命中第三级前缀) |
| **合计** | — | **约 480 ms** | **约 130 ms** |

**真实收益取决于图片重复率。** 如果每个请求的图都不一样(比如批量文档识别),前两级命中率接近 0,此时那 4 GiB 的预处理器缓存纯属浪费内存,应该关掉。

### 1.37 编码器预算:两个量,一道闸门

调度器要回答两个独立的问题:**这一步能跑多少编码器计算**(防止一个 step 里塞太多 tower 前向,把 step 延迟拉爆),以及**算完的 embedding 放得下吗**(显存约束)。前者是计算预算,后者是缓存容量,两者默认都跟着每步 token 预算走。

两个量的合成方式都是「配置值与单 item 最大值取较大者」。取较大是一道**安全兜底**:如果用户把预算设得比单个 item 还小,那个 item 永远调度不上去、请求会永久卡住,所以强行抬到至少能装下一个。「单 item 最大占多少 embedding」由显存探测阶段用最坏情况假数据跑出来。

**讲法上要小心:它们是两个量,但在调度器眼里是一道闸门。** 判断能不能分配的那个方法里,计算预算先查、缓存容量后查,**任何一个不过,处理方式完全相同** —— 回退到这个媒体 item 之前,或者干脆给 0 个 token。而且比较时还要加上**本步已经排进去的量**,不是只看这一个 item。

由这两个量还会反推出每批最多几个 item:计算与容量取较小者除以单 item 最大值,得到编码器侧的上限;再和「最大并发请求数乘每条 prompt 最多几个 item」取较小,最后至少为 1。按例子 E 代入(每步预算 8192、最大长度 32768、最大并发 64、单图上限取默认、探测得出最坏单图 1024 个 embedding):

```text
计算预算  = max(8192, 1024) = 8192
缓存容量  = max(8192, 1024) = 8192
合成预算  = min(8192, 8192) = 8192
编码器侧  = 8192 // 1024 = 8           一个 step 最多 8 张大图
每 prompt = max(1, min(999, 32768 // 1024)) = 32
decoder 侧 = 64 x 32 = 2048
每批上限  = max(1, min(8, 2048)) = 8
```

这个 8 会被显存探测用来构造最坏情况的假批次,从而给 tower 的激活值预留显存。

### 1.38 反直觉:前缀缓存命中了,编码器可能仍然要跑

1.27 说三级是串联的,命中第三层就能跳过前两层。**有一个例外,而且它会让请求这一步一个 token 都排不上。**

场景:R2 用图 A,它占位区的 KV 已经在前缀缓存里(因为 R1 跑过)。那 R2 的已算 token 数一上来就越过了占位区末尾,理论上根本不需要视觉 embedding。

但如果这时**编码器缓存恰好没命中**(图 A 的 embedding 已被驱逐),而这段占位区仍在本块要计算的范围内,调度器就**无法回退** —— 已算 token 数已经越过了占位区起点,没法「只调度到图之前」。源码注释把这个处境写得很清楚:因为前缀缓存,已算 token 数大于起始位置,即便它的编码器输入并不可用。此时只能给这个请求 0 个 token,等下一步编码器缓存腾出空间。

**根因是两级缓存的生命周期彼此独立**:KV 前缀缓存的驱逐策略和编码器缓存的驱逐策略互不相干,于是会出现「KV 还在、embedding 没了」(被上面这段逻辑挡住)或「embedding 还在、KV 没了」(正常重算)。排障时如果看到多模态请求的首 token 时延抖动大,**可以先查编码器缓存是不是太小**。

### 1.39 「分块」这个词同时指两件事

这一节容易糊的根源是「分块」同时指两件不同的事:

| | 谁在算 | 能不能切 | 为什么 |
|---|---|---|---|
| **编码器侧**:tower 前向 | tower 加 connector | **不能切** | tower 用双向注意力,第 3 个 patch 的输出依赖第 100 个 patch。切成两半分别算,注意力的可见范围就变了,结果**不等于**一次算完 |
| **decoder 侧**:prefill | language model | **可以切** | 因果注意力加 KV cache。某个位置的输出只依赖它之前的位置;切成两步后,第二步从 KV cache 读到第一步算好的 K/V,结果**等于**一次算完 |

所以「分块预填充遇到多模态」的正确表述是:**tower 永远一次跑完整个 item,被切的只是 decoder 的 prefill。** 切开占位区,切的不是 tower,而是「这 16 个已经算好的 embedding 分几次搬进输入张量」。

**是否需要保证数学等价性?需要,而且等价性正是「哪个能切、哪个不能切」的判据。** 源码里那句关键注释说的正是这件事:编码器输入应当整体处理,因为编码器通常用双向注意力。

### 1.40 模式 A(默认):切开占位区

用例子 E 的 R1 走一遍。R1 共 22 个 token,占位区起点 1、长度 16。假设本轮 token 预算只够给它 9 个 token:

```text
step 1:调度 token [0, 9)
    占位区被覆盖的相对区间 = [0, 8)
    需要的 embedding 行     = [0, 8)
    tower 跑一次,产出全部 16 行,整块写进编码器缓存
    本 step 只把第 0 到 7 行写进输入张量
    算出下标 0 到 8 这 9 个位置的 KV

step 2:调度 token [9, 22)
    占位区被覆盖的相对区间 = [8, 16)
    编码器缓存命中,tower 不重跑
    把第 8 到 15 行写进输入张量,后面接文本 token 的查表结果
    注意力读得到 step 1 留下的 KV
```

注意 step 1 里 **tower 一次算完 16 行**,只是本步用掉 8 行 —— 这正是 1.39 那条「不能切的是 tower」的具体形态。

逐项核对等价性:每一行视觉 embedding 的数值来自同一次完整的 tower 前向,两个 step 用的是缓存里同一份张量,逐位相同;每个位置的 KV 只依赖它之前的输入 embedding,step 2 需要的前文已经在 step 1 算好存进 KV cache;输入相同、可见范围相同,注意力输出也相同。

**所以模式 A 在代数意义上完全等价。** 唯一的差别是浮点归约顺序:两个 step 的批次形状不同,核的分块策略可能不同,而浮点加法不满足结合律,于是末位可能有极小差异。这是分块预填充**通用**的批不变性问题,与多模态无关。

### 1.41 索引映射:为什么需要一个专门的函数

「占位区的第几个 token」和「embedding 张量的第几行」**不是同一个下标** —— 占位区里可能夹着不吃 embedding 的分隔 token(1.25)。所以需要靠 1.26 那个前缀和,把 token 区间翻译成行区间。

调度器侧的调用先把绝对下标转成相对占位区的下标(前端取「已算 token 数减起始位置」与 0 的较大者,后端取「窗口末尾减起始位置」与占位区长度的较小者),再查映射得到行区间。

映射函数本身有一条捷径:**没有掩码时 token 下标就是行号**,直接原样返回,连前缀和都不查。

还有一个顺手的优化值得单独看:如果本块**只落在不吃 embedding 的位置上**,返回的行区间长度为 0,说明这一步压根不需要视觉 embedding,**编码器不用调度**。

### 1.42 模式 B:不许切开

调度器发现本块会切开一个 item 时,主动把本步的 token 数**缩回到该 item 之前**,让整个 item 落在下一个 step 里。

既然模式 A 是等价的,为什么还要这个开关?**它买的不是正确性而是简单性**:模型侧永远不会遇到「这一步只拿到半张图的 embedding」这种输入形态,对自定义注意力或需要整块视觉序列的 tower 实现更稳妥;调试时每个 step 的多模态边界也更整齐。代价是这一步的 token 预算被提前收尾、浪费掉一部分。

开启后有个硬约束:**单 item 最大 embedding 数必须不超过每步 token 预算,否则启动直接报错** —— 因为整块放不进一个 step,就永远调度不出去。

### 1.43 encoder-decoder 是唯一被强制进模式 B 的场景

讲稿把模式 B 说成一个纯粹的用户开关。**基准上还有一条强制路径**:配置校验阶段发现是 encoder-decoder 模型时,会**同时**打开「不许切开多模态输入」、关闭分块预填充、并把长 prefill 阈值清零,三件事一起做。

02 章 2.5.4 记录过后两件,当时的结论是「强制关掉分块预填充的唯一场景是 encoder-decoder 模型」。**那一条仍然成立,只是还漏了第三件**:同一个分支把多模态这一侧的开关也一起扳了。两章合起来才是完整的一句话 —— 这类模型被整体排除在「切分」这件事之外,不论切的是 decoder 的 prefill 还是占位区。

这类模型在编码器调度里还有两处专门分支:所有编码器输入都坐落在序列开头,所以窗口起点被强制归零;而一旦已经算过任何 decoder token,就说明编码器输入早已算完,直接跳过。它们也**完全不走编码器缓存** —— 注释里那个「yet」说明这是当前的临时状态,不是终局设计(1.3 提到过这个临时实现)。

### 1.44 M-RoPE:为什么图像需要三维位置

普通旋转位置编码给每个 token 一个标量位置。图像被拉平成 patch 序列后,「第 17 个 patch」这个标量**丢掉了它原本的二维空间关系**(第 2 行第 1 列)。

M-RoPE 的做法是把位置拆成时间、高、宽三个维度:

```text
文本 token:  三维取同一个位置索引,退化成普通一维编码
图像 patch:  时间维固定,高与宽取该 patch 在图里的行号列号
视频 patch:  时间维取帧号,高与宽取行号列号
```

隐层维度被切成三段,各段用各自维度的角度做旋转。这样模型就能「看出」两个 patch 是上下相邻还是左右相邻。

源码注释明写了那条退化性质:**纯文本输入时每一维的位置 id 完全相同,此时 M-RoPE 在功能上等价于一维编码** —— 并附了论文出处。所以这不是「文本走一条路、图像走另一条路」,而是**同一套编码在文本上自动退化**。

用例子 E 的图 A 走一遍(4×4 个合并后的 patch,占位区下标 1 到 16):

```text
下标 :  0        1  2  3  4  5  6 ... 16   17        18
时间 :  0        1  1  1  1  1  1 ... 1    2         3
高   :  0        1  1  1  1  2  2 ... 4    5         6
宽   :  0        1  2  3  4  1  2 ... 4    5         6
        文本         图像:时间恒定,高与宽走行列       文本恢复三维相同
```

注意视觉结束符之后,文本的位置从 5 和 6 继续,**而不是从 17 继续** —— M-RoPE 让图像「压缩」了位置空间:16 个 patch 只消耗 4 个位置增量。这是这类模型能处理超长多图上下文的原因之一。

### 1.45 M-RoPE 的三处工程处理

- **prefill 时一次性算好整条序列的三维位置并存下来**,由模型自己提供算法。
- **decode 时只存一个增量。** decode 阶段每步生成一个文本 token,其三维位置相同且线性递增,所以不必存表,只需「上一个位置加增量」。这个增量就是「图像压缩掉的位置数」。
- **故意多留一个无用位置。** 位置张量被分配成比实际需要多一格。注释说明这是为了让张量**非连续**,以便配合编译器 —— 一个纯粹为编译服务的小手段。

### 1.46 编码器并行:切权重还是切数据

tower 相比 LLM 很小。在八卡张量并行下把它也按权重切分很不划算:每层通信开销固定,而每卡的计算量小到打不满硬件。

| 模式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **切权重**(默认) | tower 权重按并行度切分,所有卡合作算同一批图 | 不额外占显存 | 小算子加频繁通信,效率低 |
| **切数据** | tower 权重在每张卡上复制,一批图分给各卡各算一部分,最后汇总 | **无层间通信** | 权重复制,每卡多占一份 tower 显存,可能显存溢出 |

切数据有个前置条件:**模型必须显式声明自己支持**,不支持的模型设了也不生效。这不是个别模型的特权 —— 基准上有十几个模型文件声明了它。

分片逻辑写在**模型内部**,不在 worker 里;worker 只负责调模型那个统一的多模态编码入口,怎么并行是模型自己的事。**这个分层是有意的**:不同 tower 的并行策略差别太大(三维卷积、窗口注意力、动态分辨率),塞进框架反而绑手。

相关的还有两个编码器专属开关:可以给 tower **单独指定注意力后端**(因为它是双向注意力,最优后端和 decoder 不一样),以及让 tower 的注意力**单独跑低精度**。

### 1.47 视频剪枝:剪了为什么还要重算位置

视频是 token 数的灾难:几十帧高清视频轻松产生几万个视觉 token。剪枝的思路是相邻帧之间大部分 patch 是重复的(静态背景),把冗余 patch 直接丢掉。开关是一个剪枝率,取值在 0 到 1 之间,默认不开。

实现上是四步:按剪枝率算保留多少 token、基于帧间相似度算出哪些 patch 保留、为剪枝后的媒体重算三维位置、把整条序列的位置按剪枝结果平移。

**为什么必须重算位置**:prefill 开始时,位置是按**未剪枝**的序列算的。一旦剪掉一部分视觉 token,后面所有 token 的位置都要前移,否则位置编码与实际序列错位。模型侧通过实现一个专门的剪枝协议参与这个过程,runner 在汇总完 embedding 之后调用它,然后重新计算并上传位置。

两个连带影响:

- **token 数变成「数据相关」。** 剪多少取决于视频内容,编译期不可知,于是视频路径的 tower **CUDA Graph 被自动禁用**。
- **前缀缓存语义变复杂。** 同一个视频在不同剪枝率下产生不同 token 数,缓存不能混用。

### 1.48 把编码器输出也做成可传输资源

最后一层是把编码器缓存**跨实例**共享。它是一套与 KV 传输**完全平行**的抽象,只不过传的不是 KV cache 而是 embedding。

动机很直接:如果一个集群里多个 vLLM 实例都在处理同一批热门图片(比如同一个商品图被多路请求命中),每个实例各算一遍 tower 很浪费。

抽象接口分成两半,**和 10 章 1.4 讲的 KV connector 同构** —— 连分界线都一样,按「它在哪个进程里跑」切:调度器侧负责探测远端有没有这个 item、确保数据可用、分配后同步状态、打包元数据下发;worker 侧负责实际加载与保存,以及查询异步传输的完成情况。

调度器的集成点非常轻:如果远端有这个 item,就把它归入「从外部加载」而不是「本地编码」—— **占缓存空间,但不占计算预算**,因为不用跑 tower,只需搬数据。两条路径最后都会走同一个分配动作。

基准上注册了三个实现:一个模板、一个卸载到 CPU 共享内存的,以及一个对接外部 KV 存储的。这个特性尚未在本机验证生产可用性,但它的存在说明一个趋势:**编码器输出正在被当作和 KV cache 同等地位的一类可调度、可迁移资源。**
