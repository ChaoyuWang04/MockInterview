# vLLM 04|Prefix Caching

03 章把 KV cache 装进了分页显存,但有件事它没管:系统提示词、few-shot 示例、RAG 文档这些**公共前缀**,每来一条请求都要从头算一遍。这一章讲清 vLLM 怎么自动认出算过的前缀、凭什么敢复用、以及复用带来的新麻烦怎么收场。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与方法,见代码索引页;正文不写路径与行号。

## Part 1|原理:同一段前缀不该算第二遍

### 1.1 同一段前缀,每条请求都要重算一遍

真实负载里,请求之间往往共享一大段开头:

| 场景 | 公共前缀 | 典型长度 |
|---|---|---|
| 系统提示词 | 「You are a helpful assistant…」 | 50–500 token |
| few-shot | 几个示例对话 | 500–5000 token |
| RAG | 检索到的文档片段 | 1000–10000 token |
| 多轮对话 | 整段历史 | 数千至数万 token |
| 代码补全 | 已有的代码上下文 | 数千 token |

朴素做法下,每条新请求都要 prefill 整个前缀 —— 哪怕这段的 K/V 在上一条请求里刚算完、此刻还躺在显存里。**prefill 是算力密集的**,这笔重复账直接吃掉整机吞吐。

Prefix caching 要做的就是把这部分省掉:让新请求只 prefill 它独有的那一段。收益有三项(数字是讲稿按一张 70B / TP=8 卡估的量级参考,不是本仓库实测):

- **TTFT 大幅下降**:5000 token 的文档前缀原本要几百毫秒 prefill,全命中后只剩最后一块要算,是毫秒量级
- **吞吐上升**:省下的算力直接服务更多请求 —— 这一项通常比 TTFT 更值钱
- **显存不涨**:复用靠的是多张块表指向同一个物理块、引用计数加一,不复制数据(见 03 章)

代价在后面几节里逐条出现:要有一套判据证明「这段真的算过」,要处理命中边界落在块内部的情况,还要在显存吃紧时决定丢谁。

### 1.2 怎么判断「这段 token 算过」:链式哈希

复用的前提是查得快。vLLM 的做法是给每一段固定长度的 token 算一个哈希,拿它当缓存的键。

关键在于**这个哈希不是孤立的**,它把前面所有段的哈希一起卷了进来。每个哈希单元由三样东西决定:

$$\text{hash}_i = H\left(\text{hash}_{i-1} \,\|\, \text{token\_ids}_i \,\|\, \text{extra\_keys}_i\right)$$

- 前一个单元的哈希(第一个单元没有前驱,用一个哨兵值顶上)
- 本单元内的那批 token id
- 附加标识 —— 下一节之后再说它装什么

三样东西作为**一个整体元组**丢进哈希函数,不是拼接字符串。

这样定义之后,匹配前缀就退化成了一次普通的查表:**只要最后一个单元的哈希命中,它前面所有单元必然也命中**。不需要逐段比对 token,也不需要树形结构 —— 链式性把「前缀完全相同」这件事直接编码进了哈希值本身。

那么,凭什么要求「前缀完全相同」?只看本段的 token 相同不行吗?这是下一节要证明的事,也是整套机制正确性的地基。

### 1.3 只看本段 token 行不行:一次分叉会污染它之后的每一层

朴素想法是拿本段的 token id 当键就够了。**不行,会算出错误结果。**

先看一层的 K/V 依赖什么。以 RoPE 位置编码的模型(Llama、Qwen 这一类)为例,每一层的 K 是「本层输入投影后按绝对位置旋转」,V 是「本层输入直接投影」——注意 RoPE 作用在投影**之后**,而且 V 完全不涉及位置。所以:

- **第 1 层**的输入就是 token 的 embedding,只看 token 自己。于是第 1 层的 K/V 只取决于「这个 token 是什么」加「它在第几个位置」
- **第 2 层及以上**的输入是上一层的输出,而上一层的输出经过了 attention,依赖前面所有 token

现在假设两条序列在第 N 个 token 处分叉(前面完全相同,第 N 个不同),逐个位置看各层的 K/V 是否相同:

| 位置 | 第 1 层的 K/V | 第 2 层及以上的 K/V |
|---|---|---|
| 分叉点之前(0 至 N−1) | 相同 | 相同 |
| 分叉点 N | 不同(token 不同) | 不同 |
| 分叉点之后的 N+1,**哪怕 token 恰好又相同** | 相同 | **全部不同** |

最后一行就是答案。位置 N+1 的 token 一样、位置一样,所以第 1 层的 K/V 确实一样;但它的 attention 要看位置 N,而位置 N 的 K 已经变了 —— attention 输出随之不同,第 2 层的输入不同,从第 2 层起的 K/V 全部不同。L 层里有 L−1 层对不上,这一块的 KV cache 根本不能复用。

**结论:只要前缀有任何一处不同,从分叉点开始,后面所有位置的 KV cache 都是不同的值。** 拿本段 token 相同就复用,等于用错误的 K/V 去算 attention,输出会错而且不报错。

链式哈希正是为堵这个洞而设计的:前一段的 token 变了 → 前一段的哈希变了 → 本段的哈希跟着变 → 查不到 → 不会误命中。递归下去,只有整条前缀逐段相同,最后那个哈希才会相同。

### 1.4 哈希的另外两个输入:隔离谁,以及能不能跨进程复现

哈希公式里除了 token id,还有两样东西值得单独说 —— 它们决定了**谁该被隔离开**,以及**这份缓存能不能被别的进程认**。

**附加标识解决的是「token 相同但 KV 不该共享」。** 它是一个列表,按固定顺序拼起来:LoRA 适配器的标识、多模态输入的标识、用户自带的缓存盐、prompt embeddings 的指纹。任何一项不同,哈希就不同,两条请求的缓存互不相干 —— 这既是正确性(挂了不同 LoRA 的同一段 token,K/V 本来就不一样),也是多租户下的隔离手段(缓存盐让不同租户的相同 prompt 落在不同的键上)。

这里有个容易漏的细节:**缓存盐只在第一个哈希单元里参与计算**,后面的单元不再带它。看起来像是只隔离了开头,实际上因为哈希是链式的,第一个单元变了之后所有后继单元跟着变 —— 加一次就够了。

**哨兵值解决的是「第一个单元没有前驱」。** 它不是常量,而是从一个种子派生出来的,种子怎么定分三档:

| 情形 | 种子 | 跨进程一致 |
|---|---|---|
| 设了 `PYTHONHASHSEED` | 用它 | 是 |
| 没设,且哈希函数是密码学的 | 一个固定默认串 | 是 |
| 没设,且哈希函数是非密码学的 | 32 字节随机数,同时打一条 warning | **否** |

第三档是刻意的。非密码学哈希抗碰撞弱,攻击者若能预测种子就能构造碰撞去污染别人的缓存,所以这里宁可牺牲可复现性也要随机化。可选的四种算法正对应这两类:

| 取值 | 序列化 | 哈希函数 | 跨进程种子 |
|---|---|---|---|
| `sha256`(默认) | pickle | SHA-256 | 固定 |
| `sha256_cbor` | canonical CBOR | SHA-256 | 固定 |
| `xxhash` | pickle | xxh3_128,快得多 | 每进程随机 |
| `xxhash_cbor` | canonical CBOR | xxh3_128 | 每进程随机 |

`_cbor` 后缀的意思是**确定性序列化**:默认路径下 Python 对象转字节的结果可能随版本变化,而 CBOR 有确定的编码规则。要跨节点共享 KV(PD 分离、offload 到共享存储)时,两端必须对同一段 token 算出同一个哈希,这时才需要这两个变体。

所以选 `xxhash` 系就等于放弃跨实例复用,除非显式把 `PYTHONHASHSEED` 设成同一个值。**但它不会静默出错**:P2P 传输层在握手时会把本端解析出的种子发给对端比对,不一致直接抛错,错误信息里就写着让你对齐 `PYTHONHASHSEED`。种子失配的后果是连不上,不是读到脏数据。

### 1.5 用户要不要标注哪段是前缀:不需要

vLLM 的 prefix caching 是 **automatic** 的 —— 没有任何 API 让用户声明「这一段是公共前缀」。做到这一点靠的是把算哈希这件事挪到了请求对象自己身上:

1. **请求一构造出来,就把所有满单元的哈希算好**;之后每次追加新 token 再增量补算,只算新凑满的那些
2. 调度时拿这串哈希去查最长命中前缀
3. 命中的块引用计数加一,不重算
4. 没命中的照常 prefill,块填满后注册进缓存

算哈希用的那个函数由引擎进程在初始化时装配一次,再传给每一个请求 —— 请求本身不知道用的是哪种哈希算法。这里有个实现上的讲究:**函数存进请求对象时刻意没有绑定请求自己**,否则会形成「请求 → 闭包 → 请求」的引用环,让请求无法靠引用计数立即回收。几万个请求的量级上,这决定的是内存曲线的形状。

用户视角因此是完全透明的:两条请求只要开头相同,就自动命中。

### 1.6 为什么最后一个 token 永远命不中

查找命中时有一条硬上限:**最多命中到倒数第二个 token**,最后一个必须过一次 forward。

原因不在 KV。哪怕这个 token 的 K/V 确实已经在缓存里(上一条请求算过完全相同的 prompt),仍然得跑:**forward 要产出的是 logits**。KV 齐全只意味着 attention 的 K/V 都在,Q 的投影、FFN、LM head 这一串还没跑,没有 logits 就采样不出第一个输出 token,生成无法开始。

如果不加这条限制,已算 token 数会等于总 token 数,调度器认为 prefill 已完成、直接进 decode —— 然后发现没有第一个输出 token,卡住。

**代价可能不止一个 token。** 分配槽位时要求已算 token 数按块对齐,所以这个「减一」会把命中长度从块边界拽回上一个边界,实际重算的是整整一个块。prompt 恰好是块大小整数倍时最吃亏:1024 token 的全命中 prompt(块大小 16)上限变成 1023,对齐后只能命中到 1008,要重算 16 个 token 而不是 1 个。源码注释把这条明确列为已知的可优化点。

**PD 分离下是同一条规则,只是触发位置不同。** PD 分离指把 prefill 和 decode 拆到不同节点上跑(见 02 章)。P 节点算完**全部** token 的 KV 传给 D 节点,D 收到后已算 token 数会被置成总数,随即又被减回总数减一 —— 注释写得很直白:全 prompt 命中时需要重算最后一个 token 才能采样下一个。

区别只在这一次 forward 做的事:正常场景下它可能真的在算新的 K/V;PD 分离下 K/V 已经由 P 算好传来,forward 只需要算一个 token 的 Q、做一次 attention、出 logits,顺带把已有的 KV 覆盖成相同的值。一个 token 的 forward 是毫秒级,而完整 prefill 是几百毫秒 —— 这正是 PD 分离想要的效果。

## Part 2|命中、复制与回收

### 2.1 命中落在哪:四种类型

命中不是「有」和「没有」两档,按命中长度落在什么位置分四种:

| 类型 | 含义 | 处理 |
|---|---|---|
| 全命中 | 整个 prompt 都在缓存里(除最后一个 token) | 几乎零 prefill,只算最后一个块 |
| 块对齐的部分命中 | 前 N 个物理块命中,命中长度正好落在块边界 | 命中的块引用计数加一,剩下的分配并 prefill |
| **块内部的部分命中** | 命中长度落在某个物理块的中间 | 命中的块引用计数加一,**尾块要复制一份私有副本** |
| 未命中 | 一块都没中 | 全量 prefill |

前两种是常态,也没有额外机制。第三种是本章后半段的全部内容。

它什么时候会出现?**命中长度只能落在哈希单元的边界上**,而哈希单元默认就等于块大小 —— 两者相等时,命中必然块对齐,第三种根本不会发生。只有当哈希单元被配得比块小(03 章 3.3 讲了这是怎么解耦的、前提有多苛刻),命中才可能落进块内部。

源码里有一个开关专门管这件事,开启条件比 03 章讲的那层解耦还要窄:必须存在一个处在对齐模式的 Mamba group,且它的块大小严格大于哈希单元。这里有个讲稿没提的分支 —— **比较符随 DCP 并行度变化**:非 DCP 时要求严格大于,DCP 开着时允许相等,因为 DCP 会去放大全注意力那一侧的有效块大小。开启之后还要复查一遍:任何一个可做前缀缓存、却不支持细粒度查找、且块大小与哈希单元不等的管理器,都会让整体退回块对齐并打一条 warning。

推论很干脆:**纯 attention 模型走不到这条路**,命中永远块对齐,后面几节讲的复制机制一次都不会触发。只有混合模型(对齐模式的 Mamba 配全注意力)才需要它。

### 2.2 命中边界落进块内部时,那一块为什么必须复制

问题出在这个尾块同时有两个身份:

1. **它是缓存里的已注册块** —— 缓存索引里挂着它的哈希,任何其他请求都可能随时命中它、把引用计数加一
2. **它是新请求的待写块** —— 新请求要从命中边界继续往后填 token,写入位置正好在这个块的后半段

举个具体的:哈希单元 32,某个 Mamba group 的块大小 128。缓存里存着一个块,注册的哈希声称它承载 token 0 到 95。新请求前 96 个 token 与它一致、第 96 个起分叉,于是在哈希边界 96 处命中 —— 而 96 除以 128 除不尽,命中落在这个块的内部。

如果让新请求直接复用这个块、往第 96 个槽位之后写:块的内容变成「token 0 到 95 的状态,加上新请求私有的后续状态」,但它注册的哈希**仍然声称自己是 token 0 到 95**。哈希与内容脱钩了。下一个前 96 token 相同的请求命中这个哈希时,读到的是别人的数据 —— **不报错,输出却是错的**。

vLLM 的选择是**不让写方碰缓存块**:给写方一份私有副本,缓存块保持只读、哈希语义不变。这就是写时复制(Copy-on-Write,下称 CoW),只不过触发时机不是「运行中检测到有人要写」,而是**分配阶段就判定「这个请求注定要写这个共享块」,提前复制**。

判定条件极简:有命中块,且命中的 token 数除以块大小除不尽。

**注意它不看引用计数。** 哪怕此刻只有这一个请求引用该块,只要块还在缓存里注册着,就必须复制 —— 否则未来任何一次对该哈希的命中都会读到被污染的内容。这与教科书式 CoW(共享者多于一个才复制)有本质区别:**这里的「共享者」包含未来可能命中的请求**,而不只是当前持有引用的请求。

### 2.3 复制这件事横跨四个阶段

CoW 不是一个函数,而是从调度器一路走到 worker 的四段流程:

| 阶段 | 时机 | 做什么 |
|---|---|---|
| ① 记账 | 命中之后立刻 | 记下「哪个下标上的哪个块要被换掉」;同时把这个请求的已缓存块数从「含尾块」压回到只算满块 |
| ② 预留 | 算容量时 | 需求块数加一 |
| ③ 重定向 | 真正分配时 | 取一个新块,改块表指向副本、把这对源块与副本排进待复制队列 |
| ④ 执行 | worker 上,forward 之前 | 按队列做块间拷贝 |

**阶段 ① 的第二件事容易被跳过。** 把已缓存块数压回满块数,是为了让后续的缓存注册流程把**私有副本**在填满时重新注册进缓存,而不是误以为它已经缓存过。

**阶段 ② 必须提前算进容量检查**,否则真要复制时可能一个空闲块都没有。

**阶段 ③ 有个反直觉的地方:源块的引用计数没有减一。** 两端都被刻意保留住 —— 源块保留它的命中引用,副本在交给请求的那一份之外**再加一份**。理由写在注释里:复制还没在 worker 上执行,此刻若有另一个请求结束并触发释放,源块或副本可能被回收进空闲队列并被别人覆盖,复制就复制到垃圾数据了。这两份额外引用要等复制真的跑完才归还。

**阶段 ④ 的顺序不能反。** worker 侧的执行点卡在两件事中间:**先给新分配的块清零**(块里可能残留着刚被驱逐的别人的 KV),**再做 CoW 拷贝**,最后才 forward。反过来的话,刚拷进来的内容会被清零抹掉。

拷贝本身是逐层做的索引拷贝,并且用「设备加数据指针」去重,避免跨层共享 KV 的别名视图被重复拷贝;张量布局允许时还会走一条整块存储一次性拷贝的快路径。讲稿把它描述成单纯的逐层遍历,实际实现比这多一档优化。

归还那两份保留引用的时机,是挂一个栅栏到「运行这次复制的那个 step 之后」—— 但这条延迟路径只在延迟释放开关打开时才走,否则当场就还。

### 2.4 反过来的一条路:写方想留住已注册的哈希

上一节是「命中方要写 → 把写方挪到副本上」。还有一条方向相反的路径:**写方自己想保住已经注册出去的哈希**。

场景是对齐模式的 Mamba 作为生产方:它在某个 prompt 边界上注册了尾块的哈希,但请求还要继续往这个块里写。这次的解法是把**缓存内容搬到副本上**,而不是把写方挪走 —— 源块继续被请求写(它已经不在缓存里了),副本成为缓存的只读快照。

搬迁动作把源块在缓存索引里的所有条目重新指到副本上,**条目保持有效、不发驱逐事件** —— 对外看起来什么都没发生,只是同一个哈希背后换了一个物理块。方向与上一节正好相反,但用的是同一套待复制队列与保留引用机制。

这条路径还会把副本交给外部 KV connector 去 offload。原因是**副本不在请求的块表上**,没人替它保命,必须由调用方先 pin 住 —— 这一点在源码注释里写得很明确。

### 2.5 CoW 值不值:一次全层拷贝,和与远端命中的仲裁

**单次代价是一次全层的索引拷贝。** 以 80 层的 70B 模型为例,每层每块的 KV 约 8 KB,一个块的全部层合计约 640 KB,走显存内部拷贝是微秒量级,相对毫秒级的 forward 可以忽略。

真正要警惕的不是带宽,**是它多占了一个块**。显存紧张时这会加剧驱逐 —— 为了一个不满的尾巴,挤掉一个本可以被别人命中的缓存块。

正因为如此,调度器里有一道显式仲裁。本地拿到一个不满块的尾巴时,如果远端 connector 能提供更长的前缀,就没必要为这个尾巴付 CoW 的代价:

- 先把本地命中长度**按块对齐截断**,只把对齐后的长度报给 connector
- 远端返回的长度**严格超过**那截尾巴 → 丢掉本地尾巴、不做 CoW,让远端加载覆盖它
- 远端没有更长 → 保留本地尾巴走 CoW,不加载任何远端数据

只报块对齐长度是故意的:否则 connector 看到的本地长度已经含了那个尾巴,「远端严格更长」这个判断就失去了意义,永远也压不过本地。

### 2.6 缓存块什么时候被回收

前缀缓存的块并不是永久的。空闲块用尽时,必须驱逐一些已缓存但当前没人引用的块 —— 这套机制(空闲队列的双向链表、无哈希块走后进先出、有哈希块走先进先出形成 LRU、队首为什么往往不是缓存块)在 03 章的 3.5、5.3 和 6.3 已经讲透,这里不重复。

只补两件本章相关的:

**驱逐是两步,不是一步。** 先把这个块名下的所有哈希条目摘掉(块自身字段上的主哈希,加反向索引里的附加哈希),**一条都没摘到就说明它本来就不是缓存块,直接返回、不算驱逐**;摘到了才广播一条块移除事件,供外部 KV 网关同步。

**一个哈希可以对应多个物理块**,这是 vLLM 有意不去重的结果(理由见 03 章 6.2)。对本章的影响是:查询时任取其一即可,不存在「哪个才是正确的那块」的问题 —— 内容相同才会挂同一个哈希。

被驱逐之后,下次有请求命中该哈希时会 miss,要重新 prefill。**所以驱逐是有代价的**,这也是 2.5 那个「多占一个块」值得警惕的原因。

## Part 3|PD 分离下,前缀复用还成立吗

### 3.1 拆成两个实例之后,前缀复用还成立吗

到这里为止讲的都是一个进程内部的事。PD 分离(把 prefill 和 decode 拆到不同实例上跑,见 02 章)一下子把它变成了两个进程、两份缓存 —— 前面这套还成立吗?

先把拓扑摆清楚。**P 和 D 是两个完全独立的 vLLM server**,各有自己的 API 层和引擎进程。把一条请求拆成两半发出去的是一个**外部路由 proxy**,不是 vLLM 自己:

- 给 P 发一份 prefill 请求,标记「这条的 decode 在别处做」,并把输出长度**限成 1 个 token**
- 给 D 发一份 decode 请求,标记「这条的 prefill 在别处做」,附上 P 的地址、端口、引擎标识,以及这条请求在 P 那边的 id

两份都是普通的 HTTP 请求。**connector 不转发请求**,它只负责传 KV 数据和握手元信息;D 侧的 connector 在请求到达时只是读一读这些坐标做记账 —— 至于「P 那边的 KV 别被提前回收」,靠的是 P 侧挂的一个租约,而这个租约由 D 侧的心跳续期(见 3.3)。

由此得到本节的答案:**D 收到的是一份完整的请求,带着完整的 prompt token。** 于是 D 会用自己的 hasher 把哈希算出来 —— 不是 P 传过来的 —— 再查自己的本地缓存。**D 的 prefix cache 因此是有意义的**:它省下的不是计算,而是「这一段连传都不用传」。

P 和 D 各有自己的块池和缓存索引,**不共享任何缓存状态**。两边各查各的。

### 3.2 D 怎么把「本地已有」和「远端能给」拼起来

D 的调度器在等待队列里遇到一条新请求时,要凑出一个总的「已算 token 数」,分三步:

| 步 | 做什么 | 结果 |
|---|---|---|
| ① | 查 **D 自己**的本地前缀缓存 | 本地已有多少 token |
| ② | 问 connector:远端还能补多少 | 远端能补多少,以及要不要异步接收 |
| ③ | 两者相加,断言不超过请求总长 | 这条请求的已算 token 数 |
| ④ | 需要异步接收的转入等待状态 | 插回等待队列队首,下一轮再看 |

第 ① 步里有个分叉:如果 connector 声明自己**容得下命中边界的分歧** —— 也就是本地命中比各 group 一致边界更深 —— 就走一条专门的查询;否则走普通查询,并直接报告「没有分歧」。两条路查的都是 D 自己的块池。

第 ② 步就是 2.5 那道仲裁:只把**块对齐后**的本地长度报给 connector。它返回「无法判定」时,这一轮干脆不调度这条请求。

混合模型上还有一条回退:**本地命中更深、但远端一个 token 都补不上时**,那个更深的边界会没有有效的 Mamba 状态给它兜底,于是整体退回到所有 group 都认可的边界重查一次。源码注释把理由写得很直白 —— 更深的恢复点若没有对应状态,就是个假的恢复点。

第 ④ 步是收尾:需要异步接收的,请求转入等待远端 KV 的状态并插回等待队列队首,已算 token 数**先记上**(此刻 KV 还没到,这个数在传输完成前不会被任何人用)。

### 3.3 KV 实际怎么从 P 走到 D

先分清两种模式:**拉**(D 主动从 P 读)和**推**(P 主动往 D 写,由一个专门的写线程发起)。两者的路由长得一样,但传输方向相反。下面走的是拉。

**调度器侧决定拉哪些。** connector 报数时分两条分支:

- 标了「prefill 在远端」→ 拿远端能提供的 prompt token 数减去本地已算的,差值为正就要拉
- 标了「decode 在远端」→ 这是**反过来的场景**:P 从已经持有部分 KV 的 D 那边拉。这条分支多一道**重算阈值**闸门:远端能给的 token 数低于阈值就直接返回 0,让本地重算。理由是一次传输有固定开销(握手、描述符组装、完成通知),只省下几十个 token 并不划算,本地重算反而更快
- 两条都不匹配就返回 0,这条请求走普通的本地 prefill

分配完块之后通知 connector 记下**用哪些块来接收**。这里只取**没有哈希的那些块** —— 本地已经命中的块不参与传输,这正是 3.1 说的「连传都不用传」落地的地方。全命中时这个列表是空的,但**仍然要走一趟通知**,好让远端知道可以释放它那边的内存。

**worker 侧实际拉。** 第一次和某个 P 通信要先**握手**:D 通过一条独立的控制通道问 P 要 GPU 内存注册信息,P 那边常驻一个应答线程,回送自己的基地址、块数、块长与布局。握手在后台线程里做,**本轮先跳过这条请求**,握手完成后再补发传输。握过手之后,D 的传输代理就知道了 P 的显存布局,可以直接发起 GPU 到 GPU 的远程读。

这里有个容易读错的地方:**远端块号在下发时保持逻辑编号**,要到真正发起读取时才按对端引擎自己的物理比例展开 —— P 和 D 的「一个逻辑块对应几个物理块」可以不一样。

传输方式取决于硬件,下面是量级参考而非实测:

| 场景 | 方式 | 带宽量级 | 单次延迟量级 |
|---|---|---|---|
| 同机 | NVLink 点对点直读 | ~300 GB/s | ~1 μs |
| 跨机有 RDMA | RDMA over InfiniBand | ~50 GB/s | ~5 μs |
| 跨机无 RDMA | TCP 加主机内存中转 | ~10 GB/s | ~50 μs |

**传完之后**,worker 把完成的请求 id 报给调度器,调度器把它记进已完成集合;下一个 step 里这条请求被提升回可调度状态,同时把收到的 KV **注册进 D 的本地前缀缓存** —— 下一条共享同样前缀的请求,才能在 D 本地命中。

**P 侧怎么知道 D 要来拉?拉模式下它不主动推。** P 在请求结束时把块 id、控制通道地址和引擎标识打包进返回参数交给 proxy,proxy 再塞进发给 D 的 HTTP 请求里。P 这边的块也不会立刻释放,而是**挂一个按时长计的租约**,过期才回收 —— 给 D 留出来读的时间窗。

租约还要能**续期**,否则 D 拉得慢一点就会读到已经被回收的块。续期由 D 发起:D 每步给对端引擎发一条心跳,列上自己还在等的那些请求;P 收到之后延长这些请求对应块的租约。**所以「谁保住了 P 的 KV」这个问题的答案是两半 —— P 挂租约,D 发心跳续租**,协议的版本历史里也把「用心跳续 KV 块的租约」单独记成一条。

心跳有两条边界:它只跟踪**标了「prefill 在远端」的请求**,源码注释明说双向传输(一个实例同时当 P 和 D)下心跳等于关闭;而且只有拉模式发心跳,推模式那一侧只负责停掉跟踪。

最后纠正一处容易想当然的地方:这条链路上**没有逐层流水线**。NIXL connector 的逐层等待钩子是空实现,注释写明它不做逐层保存 —— 它是整请求异步读,完成后一次性报告。

### 3.4 这套机制在 PD 分离下省下什么

拿两条共享系统提示词的请求走一遍,就能看出 D 的本地缓存值多少。参数取一张 70B 模型 / TP=8 的卡,块大小 16,单 rank 每块跨全部 80 层约 640 KB(数字是量级估算):

| | 请求 1(D 的缓存是空的) | 请求 2(D 已有系统提示词) |
|---|---|---|
| prompt | 系统提示词 1000 + 查询 A 100 | 系统提示词 1000 + 查询 B 100 |
| D 本地命中 | 0 token | 1000 token |
| 需要从 P 接收 | 1100 token | 100 token |
| 对应块数 | 69 块 | 7 块 |
| 单 rank 传输量 | ~45 MB | ~4.6 MB |
| 8 个 rank 合计 | ~360 MB | ~37 MB |
| 传输耗时(各 rank 并行,按 50 GB/s 估) | ~0.9 ms | ~0.1 ms |

**省掉的是网络,不是算力。** P 那边也在省:请求 2 在 P 上同样命中了系统提示词的缓存,只 prefill 了查询 B 的 100 个 token,于是也只准备了这 100 个 token 的 KV 等 D 来拉。两端的前缀缓存**各自独立地生效**,叠加起来就是这张表里的九成。

## Part 4|图解

前三部分讲的是每个机制为什么存在。这一部分把它们放进具体的数字和时间线里走一遍,只补具体性,不引入新结论。

### 4.1 一条 prompt 被切成什么:只有满块才算哈希

这是块粒度带来的一条硬约束,前面一直没点破:**不足一块的尾巴不算哈希**。算哈希的循环一旦发现「再取一个单元就超出当前 token 数」,就直接停;不会 padding,也不会给残缺的尾巴编一个哈希。

看一个小例子(哈希单元取 4,便于数)。请求 A 的 prompt 是 6 个 token,前 4 个是系统提示词、后 2 个是问题:

```text
S = 系统提示词 token,X / Y = 各自的问题 token

请求 A:  [ S S S S | X X ]
          \_______/ \___/
           满块      尾巴(只有 2 个,不足 4)

  满块 -> hash_0 = H(哨兵, [S,S,S,S])
  尾巴 -> 不算哈希
  => 这条请求的哈希列表长度 = 1

请求 B:  [ S S S S | Y Y ]
          \_______/ \___/
           满块      尾巴

  满块 -> 四个 token 与 A 完全相同 -> hash_0 相同 -> 命中
  尾巴 -> 同样没有哈希可查 -> 必然重算
```

尾巴那两个 token 的 KV 照常写进物理块,只是这个块暂时进不了缓存 —— 要等后续生成的 token 把它填满,才会补注册。请求 B 这边同样不足一块、没有哈希可查,**必然重算**。

于是 A 和 B 的公共前缀虽然是 4 个 token,能复用的也正好是这 4 个。**尾巴上不足一块的部分永远命中不了,与前缀是否相同无关** —— 这是块粒度的固有损失,也是 03 章 3.2 讨论块大小时那条「小块命中率高」的来源。

链式哈希在这里换来一个很实用的性质:**某个位置的哈希不同,其后所有哈希必然不同**。所以前缀匹配可以**从前向后线性扫描,遇到第一个未命中就停**,不需要往后再试 —— 源码注释把这条写在扫描循环的头上。

细粒度命中开着时(见 2.1),扫描完满块还有第二阶段:在第一个未满块的内部,**从高到低**探它的哈希边界,探到就停 —— 高到低是为了拿最长的那个命中。

### 4.2 一次命中的完整走读

换成真实尺寸:块大小和哈希单元都是 16,请求 B 的 prompt 是「系统提示词 2000 + 用户问题 50」共 2050 个 token,前一条请求刚好用过同一段系统提示词。

| 阶段 | 发生了什么 | 数字 |
|---|---|---|
| 构造请求 | 按满块算哈希 | 2050 ÷ 16 = 128 个满块,余 2 个 token 不算 |
| 查命中上限 | 总数减一(见 1.6) | 2049,可扫 2049 ÷ 16 = 128 块 |
| 线性扫描 | 逐个查,遇到第一个未命中就停 | 前一条请求覆盖了前 125 块;第 126 块起是用户问题,内容不同 → miss |
| 命中结果 | | 命中 125 块 = 2000 个 token |
| 分配 · 复用 | 命中的块引用计数各加一,挂进这条请求的块表 | 已缓存块数记为 125 |
| 分配 · 新块 | 总共需要 ⌈2050/16⌉ = 129 块,已有 125 | 新分配 4 块,第 129 块只装 2 个 token |
| GPU 前向 | 只 prefill 50 个 token,前 2000 个的 KV 直接从命中块读 | |
| 前向之后 | 注册新填满的块 | **只注册 3 个哈希**,第 129 块不满、不注册 |

最值得看的是倒数第二行:**新分配了 4 块却只注册 3 个哈希**。这和 4.1 里那个「6 个 token 只产生 1 个哈希」是同一条规则,只是换了个尺寸。

### 4.3 驱逐时序:无哈希的块是缓冲垫

把 03 章讲的两种分流放进一条具体的队列里看。队列里混着两类块,`(h)` 表示带哈希、属于前缀缓存:

```text
初始:   B9  ->  B5(h) -> B8(h) -> B2(h) -> B7(h)
        ^       ^                          ^
        |       |                          |
        |       |                          +-- 队尾:最近用过
        |       +-- 有哈希,队内顺序即最近使用顺序
        +-- 队首:没有哈希,纯粹是垫子

新请求要 2 块,从队首连取两个 ==>

结果:   B8(h) -> B2(h) -> B7(h)
```

两次取用的结局完全不同。取 B9 时,试着驱逐它却**一条哈希都摘不出来** —— 于是返回「没驱逐」,缓存内容零损失。取 B5 时摘掉了哈希条目、广播了一条块移除事件,返回「已驱逐」—— 这一次是真驱逐,后续再有请求命中 B5 那个哈希就会 miss。两块最后引用计数各加一,交给请求。

**无哈希的块排在队首,就是为了让它们先被消耗掉。** 它们本来也不可能被任何请求命中,留着没有价值;只有这批垫子用完,驱逐才会真正伤到缓存。这解释了为什么「驱逐」在负载不极端时其实很少发生。

### 4.4 复制一次尾块的时间线

把 2.2 和 2.3 放进一条带块号的时间线。前置条件是混合模型且开了细粒度命中(见 2.1):Mamba group 的块大小 128,哈希单元 32;缓存里的块 B 承载 token 0 到 95,哈希边界 96 已注册。请求 R 命中到 token 96,而 96 除以 128 除不尽 —— 落进了 B 的内部。

| 步 | 动作 | 状态变化 |
|---|---|---|
| ① 记账 | B 的引用计数加一,R 暂时持有 B;记下「第 0 个下标上的 B 要被换掉」 | 已缓存块数压回 0,好让副本填满后能重新注册 |
| ② 预留 | 需求块数加一 | 为副本留出容量 |
| ③ 重定向 | 取新块 B′;R 的块表第 0 项改指 B′;把 (B, B′) 排进待复制队列;B′ 引用计数再加一 | **B 的引用计数不减** —— 两端都被保留住,防止复制前被回收 |
| ④ 组装 | 调度器抽干复制队列,连同保留引用一起下发 | 归还保留引用挂在「复制真的跑完」之后 |
| ⑤ worker | 先给新块清零,**再**把 B 的内容拷到 B′,然后才 forward | 顺序反了的话,刚拷进来的内容会被清零抹掉 |

R 随后往 B′ 的第 96 个槽位之后写自己的状态。最终:**B 仍在缓存里,内容仍是 token 0 到 95 的干净快照;B′ 只有 R 在用,被写脏也不影响任何人。** 哈希与内容始终一致 —— 这正是 2.2 要的那个结果。

## Part 5|机制之外:源码里额外读到的

前三部分讲了每个机制为什么存在,Part 4 把它们放进了具体数字。这一部分只放**机制层面看不见、但真实存在的细节**:同名方法在不同层次上的分工、为绕开某个具体麻烦加的修正、以及几处容易读反的实现取舍。前面讲过的一概不重复。

### 5.1 「最长前缀匹配」不是一个函数,是三层同名方法

前面一直把「查最长命中前缀」当成一个动作。源码里它是**三个层次上的同名方法**,职责完全不同:

| 层次 | 谁 | 干什么 | 返回 |
|---|---|---|---|
| 协调器 · 单 group | 单一协调器 | 直通转调下层,对齐单位直接给块大小 | 三元组 |
| 协调器 · 多 group | 混合协调器 | **仲裁**:迭代收敛到所有 group 都认可的长度 | 三元组 |
| 管理器 | 全注意力管理器等 | 单一 attention 类型的**实际查表** | 二元组 |

顶上还有第四个实现:关掉前缀缓存时用的那个协调器,它的同名方法直接返回空块和 0,连查都不查 —— 开关做在类型层面,而不是在调用点写 if。

两层返回值不同,是理解这套分层的钥匙:**管理器只回答「我这一类命中到哪」,协调器要在多个答案之间调和,所以多出第三项。** 那第三项是什么,5.3 单说。

### 5.2 混合模型为什么必须迭代,以及它凭什么会停

不同 group 的块大小不同、命中规则也不同 —— 全注意力是「从头连续命中」,滑动窗口只关心窗口内那一段。同一条 prompt 问下去,各 group 报出的命中长度**会不一致**。

取最小值一次了事不行:把长度压低之后,原先报得更短的那个 group 在新长度下的答案可能又变了。所以代码走的是**不动点迭代** —— 拿当前候选长度去问每一种 attention 类型,要么它接受,要么它把长度压得更低;一旦有人压低,就带着新长度重新问所有类型,直到一轮下来没人再压低为止。

它凭什么会停?因为**候选长度单调递减,而且下界是 0**,不可能无限迭代下去。

有一条快路径:只有一个全注意力加一个别的类型(这是绝大多数混合模型的形状)时,**一轮就够**,代码直接 break —— 全注意力总是排在第一个,它给出的长度已经是上界。

### 5.3 第三个返回值不是「块内的部分命中」

看到协调器多返回一个 token 数,很容易以为是「最后那个块内部命中了多少」。**不是。** 它的算法是:各 group 里**最长的那个命中长度**,减去**调和之后的命中长度**。

它要解决的是稀疏保留带来的一个麻烦。Mamba、滑动窗口这类 group **不会保留每一个边界上的状态** —— 它们按策略只留一部分检查点。于是可能出现这种局面:全注意力那边明明缓存了更长的公共前缀,但稀疏保留的那个 group 恰好没在这个接合点上留状态,跨请求复用就在这里断了。

把这个差值报出来,上层就能把这个位置**钉住**,让稀疏保留策略别把这个关键接合点淘汰掉。上层拿它算出一个「共享前缀边界」:有差值就记成「调和后的命中长度加上这个差值」,没有就记 0。

非混合模型下这一项恒为 0,整套机制不出场。

### 5.4 查表末尾还有两次修正

管理器那一层扫完两个阶段之后,命中长度还要再过两道:

**① 推测解码要倒退一格。** 开了 EAGLE 这类 draft 头时,会主动把命中长度减掉一个单元 —— 细粒度模式下减一个哈希单元,否则减一整块。理由写在注释里:**生成点前面那几个 token 必须重算**,draft 头要用它们。注释还补了一句细粒度下为什么减一个单元就够:尾块的 KV 是只追加的,缩短之后它仍然覆盖得住。

这一条在混合模型的迭代里还有个配套:每个 EAGLE group 在同一个候选长度上**最多只倒退一次**,而一旦有人把长度压得更低,先前记下的「已倒退过」就作废重来。少了这条,迭代里会反复扣。

**② 向下取整到对齐单位。** 保证交上去的命中长度落在调度器要求的边界上。注释明说两种情况下这一步是空操作:细粒度模式下命中本来就落在哈希边界上,以及对齐单位恰好等于块大小时。取整完还要把超出新长度的块从列表尾部删掉。

### 5.5 算哈希这一路上的三个实现细节

**① 哈希函数不拼字节缓冲区。** 上层把「父哈希、本段 token、附加标识」这个元组**原样**交给哈希函数,怎么变成字节是哈希函数自己的事 —— 这才是 1.4 那四个取值的真正分水岭:默认档用 pickle 的最高协议序列化,`_cbor` 档用 CBOR 的规范编码。xxhash 那两档还要额外装包,缺了会抛一个直接告诉你怎么装的错误。

**② 哈希函数本身不带种子。** 默认实现的注释明写:它不使用哈希种子,需要种子得自己拼进输入里。这正好解释了 1.4 的哨兵值为什么是「把种子字符串单独哈希一次」得来的 —— 种子不是哈希函数的参数,只能当成普通输入喂进去。

**③ 增量 hasher 上有一个提前返回。** 进循环之前先判断一次「从上次算到的地方往后,凑不凑得满一整块」,凑不满直接返回空列表。decode 阶段每个 step 都会调一次这个函数,而块通常十几个 token 才满一次 —— 少了这道判断,绝大多数 step 都在白跑一遍循环。

同一个函数里还有个只对多模态生效的小动作:**续算时把多模态输入的游标置成「最后一个」**。能走到续算这一步,说明这块是被生成出来的 token 填满的,前面的多模态输入早已编码进旧哈希,只需要看最后一个。

### 5.6 注册哈希时,主哈希和额外哈希分开放

插入一条哈希条目的函数逻辑与直觉相反,值得逐条看。它按四种情况分支:

| 情况 | 动作 |
|---|---|
| 这就是该块当前的主哈希 | 什么都不做 |
| 这个「哈希 + 块号」组合已经在表里 | 幂等返回 |
| 该块还没有主哈希 | 写进**块自身的字段** |
| 该块已有主哈希 | 才写进**反向索引** |

**主哈希存在块对象的字段上,反向索引只承载「额外的」那些。** 这是空间优化:绝大多数块一辈子只有一个哈希,给它们每个都建一个集合是纯浪费。

什么时候一个块会有多个哈希?来自细粒度命中 —— 同一个大物理块内部有多个哈希边界都被注册了(见 03 章 3.3)。

对应地,驱逐时必须把**两处一起清**,这也是 2.6 说的「摘不到哈希就不算驱逐」能成立的前提:判据查的是这两处的并集。

### 5.7 什么情况下根本不查缓存

查之前有一道两条件的闸门,两条都过才查:

| 条件 | 含义 | 谁来关 |
|---|---|---|
| 全局开关 | 前缀缓存本身开着 | 命令行关掉(默认开) |
| 逐请求否决 | 这条请求没被标记为「跳过读缓存」 | 标记挂在采样参数或池化参数上 |

第二条的触发场景写在注释里:**请求要 prompt logprobs**,或者**调用池化模型且做全量 pooling**。这两种都需要所有 prompt token 真实过一遍前向才能拿到逐 token 的输出 —— 复用缓存等于跳过计算,输出就缺了。

还有一个容易忽略的配套:**统计命中率时用的是同一道闸门**。跳过查询的请求不被算进分母,注释写得很直白 —— 否则命中率会被这些根本没查过的请求稀释掉。

最后补一句 CoW 那边的小细节:收集待复制操作的函数返回的是**两个**列表,一个是给 worker 执行的源块与副本 id 对,另一个是被多保留了一层引用的**两端块**(2.3 阶段 ③ 那两份额外引用)。前者随调度输出下发,后者要等复制真的跑完才能释放。

## Part 6|对比与收益账

前面五部分讲的是这套机制怎么来、怎么跑、代码里长什么样。这一部分回答上线时真正会问的问题:和别人比差在哪、块粒度到底损失多少、命中率能到多少、容量这根杠杆怎么拧、哪些参数该动、以及怎么看线上的真实数字。

### 6.1 和 SGLang 比,真正的分歧是「要不要改结构」

三家的横向对比表在 03 章 7.1,这里不重复。值得单独拎出来的是**同一件事在两种数据结构上的代价差别**:

| 操作 | vLLM:哈希表 | SGLang:基数树 |
|---|---|---|
| 查一次命中 | 每个单元一次字典查询,命中 n 块就查 n 次 | 一次树遍历,深度是共享前缀长度除以段长 |
| 注册新内容 | 字典插入,**结构不变** | 可能触发节点分裂,要改指针 |
| 驱逐 | 队首弹出加摘哈希条目 | 从叶子往上剪枝,可能级联 |
| 并发友好度 | 高(只改字典条目和引用计数) | 低(树结构变更需要更粗的锁) |

先把两个术语说清楚:**基数树**是前缀树的压缩变体,把只有单个子节点的连续路径合并成一个节点 —— 用在 KV cache 上,一条从根到叶的路径就是一个 token 序列,公共前缀天然共享同一段路径。**树分裂**是新序列与已有路径在中途分叉时,把原节点在分叉点切成两个:前半段成为共享父节点,后半段和新内容各成一个子节点。这正是它能做到 token 级粒度的原因,代价是每次分叉都要改树结构。

**哈希表方案的核心优势不是常数更小,而是没有结构变更。** 注册、命中、驱逐都只碰字典条目和引用计数,不动指针拓扑 —— 这让它更容易保证块表的只追加语义(03 章 6.2 那条「刻意不去重」是同一个取舍的延伸)。基数树的优势是天然的 token 级粒度和天然去重,代价是每次分叉都要改结构。

一句话:**vLLM 走的是「结构极简、需要时再用哈希单元补细粒度」,SGLang 走的是「结构本身承载精度」。**

### 6.2 块粒度到底损失多少

vLLM 的命中边界必须落在哈希单元的整数倍上。纯 attention 模型下这个单元就等于块大小(默认 16),于是**分叉点落在块内部时,这个块里已经相同的那些 token 会被一起浪费掉**。

举个最小的例子:两条请求前 15 个 token 相同、第 16 个才分叉。块内哈希覆盖的是 token 0 到 15,其中有一个不同 —— 哈希就不同,整个块不命中,那 15 个相同的 token 白算了。同样的情形在基数树上会在第 15 个 token 之后分叉,前 15 个全部复用。

分叉点在块内均匀分布时,**期望损失约为半个块**。关键在于它是个**固定损失**,前缀越长占比越小:

| 公共前缀长度 | 期望损失(块大小 16) | 相对损失 |
|---|---|---|
| 2000 token | 约 8 token | 0.4% |
| 50 token | 约 8 token | 16% |

所以块粒度的代价主要压在**短前缀、高频分叉**的场景(大量短对话),长系统提示词和 RAG 文档几乎无感。

**能不能把它调细?** 可以,但前置条件很硬。允许把哈希单元设得比块大小小(前提是能整除),可块内探测那一阶段只在细粒度开关点亮时才启用,而这个开关只由「存在对齐模式的 Mamba group」点亮(见 2.1)。**纯 attention 模型即使把哈希单元调小,也只是让哈希算得更密,命中依然块对齐** —— 多花哈希开销却拿不到更细的命中。

### 6.3 命中率能到多少:一个可以代入的公式

设公共前缀长度为 $L$、prompt 总长为 $N$、哈希单元为 $b$,能复用的 token 数是:

$$\text{hit} = \left\lfloor \frac{\min(L,\ N-1)}{b} \right\rfloor \cdot b \qquad\qquad \text{savings} = \frac{\text{hit}}{N}$$

$\min(L, N-1)$ 里那个减一来自 1.6 的「最后一个 token 必须重算」;向下取整带来的期望损失就是 6.2 的半个块;而那个减一在 $L = N$ 且 $N$ 恰好是 $b$ 的整数倍时最伤,会额外吃掉整整一个 $b$。

代入几组典型配置($b = 16$):

| 场景 | prompt 总长 $N$ | 公共前缀 $L$ | 可复用 | savings |
|---|---|---|---|---|
| 长系统提示词加短问题 | 2050 | 2000 | 2000 | 97.6% |
| RAG(文档加短查询) | 3100 | 3000 | 2992 | 96.5% |
| 短多轮对话 | 120 | 64 | 64 | 53.3% |
| 完全相同的 prompt 重复 | 1024 | 1024 | 1008 | 98.4% |

最后一行是那条减一规则的直接体现:prompt 完全相同、总长又正好是块大小整数倍时,命中从 1024 被拽到 1008,硬性重算一整个块。

**这些数字是公式的代入结果,不等于端到端加速比。** 真实收益还取决于命中块是否已被驱逐(6.4)、prefill 在总延迟里的占比、以及同一批里其他请求的挤占。要拿线上的真实命中率,只能读指标,怎么读见 7.4。

### 6.4 容量怎么一路传导到 TTFT

命中率不只取决于请求模式(前缀重不重复),还取决于**KV cache 装得下多少块** —— 容量不够时旧的缓存块被驱逐,后续请求就 miss 了。这条因果链是单向的、方向确定的:

**容量越大 → 能留住的缓存块越多 → 驱逐越少 → 命中率越高 → 需要重算的 prefill 越少 → 首 token 延迟越低。**

把 KV cache 量化到 FP8 就是拧这根杠杆最直接的办法。仍用 03 章一直在用的那张卡(70B、80 层、TP=8、块大小 16):

| | FP16(默认) | FP8 |
|---|---|---|
| 每块每层字节(单 rank) | 8 KB | 4 KB |
| 一个块跨 80 层 | 640 KB | 320 KB |
| 可用 KV 显存 | 约 51 GiB | 约 51 GiB(不变) |
| 块总数 | 约 82000 | 约 164000 |
| 能缓存的 token | 约 130 万 | 约 260 万 |
| 平均 2000 token 时能缓存的请求数 | 约 650 | 约 1300 |

**FP8 的收益不只来自「计算更快」。** 在前缀重复度高的负载里,「容量翻倍 → 命中率提升 → prefill 更少」这条路对首 token 延迟的影响往往比峰值算力更大。提高显存占比参数走的是同一条链路,只是幅度小得多。

反过来有一条容易搞反的:**把块大小调大反而会降低命中率**。默认情况下哈希单元等于块大小,块越大,分叉点越容易落在单元内部,整个单元不命中(就是 6.2 那条)。而块大小变大时块总数等比例减少,能缓存的总 token 数不变 —— **受损的只有匹配粒度,不是容量。**

### 6.5 offload 把容量往外扩,但只有一层真的划算

多级缓存的三层结构、write-behind、chunk 粒度和开关怎么配,03 章 4.2 到 4.4 已经讲完,这里只回答一个 prefix caching 视角的问题:**多一层,到底值不值。**

比较必须统一到「每块」,否则会得出荒谬的结论。仍按一个块跨 80 层约 640 KB 算(数字是硬件量级估算,不是实测):

| 恢复方式 | 每块耗时 | 依据 |
|---|---|---|
| GPU 层命中 | ~0 | 只改引用计数,无数据搬运 |
| CPU 层命中,回填 GPU | ~0.03 ms | 640 KB ÷ PCIe 4.0 x16 有效约 25 GB/s |
| 磁盘层命中,回填 CPU 再回 GPU | ~0.2–1 ms | 640 KB ÷ NVMe 约 1–3 GB/s,再加 I/O 延迟 |
| 全部 miss,重算 | ~0.5–1 ms | 16 token × 每 token 约 140 GFLOP ÷ 8 张 H100 的有效算力 |

**CPU 层收益显著**:比重算快二三十倍,而且省下的是**算力**(可以让给别的请求),不只是延迟。

**磁盘层收益有限**:和重算是同一量级。它的价值主要不在「更快」,而在**容量** —— 让那些本来会彻底丢失的前缀仍然可命中,且不占 GPU 与 CPU 内存。磁盘若是网络存储或本身负载高,命中反而可能比重算还慢,这时就该关掉它。

**判据只有一条:该层的回填耗时要小于重算耗时。** 这个门槛随模型和硬件浮动 —— 块越大(层数多、head 多)搬运越贵,但重算也越贵,两者比值不固定,需要实测。

配置上只补两点 03 章没说的:CPU 侧容量那个参数是**必填的**,拿不到会直接抛异常;而它填的是**字节数**,能装多少由它除以对齐后的 chunk 大小得出 —— 不存在一个直接指定块数的开关。

**offload 的定位因此很清楚**:它扩的是前缀缓存的**有效容量**,把「被 GPU 驱逐即永久丢失」变成「降级到更慢的层但仍可命中」。速度收益只在 CPU 层明确,磁盘层要具体测。

## Part 7|参数、开关与误区

### 7.1 参数:只有一个是前缀缓存专属的

KV cache 相关参数的默认值与调向,03 章 7.3 那张表已经列全,这里不重复。前缀缓存自己新增的只有一个:

| 参数 | 默认值 | 往哪边拧 |
|---|---|---|
| 哈希算法 | `sha256` | 单机保持默认。跨节点共享 KV(PD 分离、offload 到共享存储)换成 `_cbor` 变体,保证序列化可复现;追求哈希吞吐可换 `xxhash`,但要额外装包,且**必须同时把 `PYTHONHASHSEED` 设成同一个值**才能跨进程复用(见 1.4) |

有一条两章方向相反、值得单独说清:**显存占比参数**。03 章从「别 OOM」出发,建议往 0.85 到 0.88 降,给激活波动留余量;本章从「命中率」出发,提高它能换更大的缓存、更少的驱逐。两个方向都对,冲突点在于**它同时是安全边际和缓存容量**。所以顺序应该是:先按 03 章 7.2 算一下 KV cache 到底是不是瓶颈 —— 不是瓶颈就别动它,去查并发上限和 token 预算;是瓶颈再在 OOM 余量允许的范围内往上调,并优先考虑改用 FP8(6.4),因为那条路不吃安全边际。

### 7.2 什么时候该关掉它

默认开着,绝大多数生产场景也应该开着。但有三种情况关掉更好:

| 场景 | 为什么 |
|---|---|
| 请求之间完全没有前缀重叠(比如随机 token 的压测) | 缓存永远 miss,白付哈希计算和块记账的开销 |
| prompt 极短且 QPS 很高 | prompt 不足一个块时**连哈希都不会算**(见 4.1),但块记账照跑,收益为零 |
| 调试内存问题 | 关掉之后块的生命周期可预测得多,不会有已缓存块滞留干扰判断 |

### 7.3 常见误区

前三条在 03 章 7.4 已经列过(块边界命中、哈希单元调细的适用范围、默认是否开启),这里只补本章独有的:

| 误区 | 真相 |
|---|---|
| 「前缀缓存能省显存」 | 不直接省。命中的块靠引用计数共享,**块总数不变**,省下的是重复计算,换来的是同样显存服务更多请求。反过来 CoW 还会**多占**一块(见 2.5) |
| 「token 相同就一定命中」 | 错。链式哈希保证只有**整条前缀**相同才命中 —— `[A,B]` 和 `[C,B]` 的第二块哈希不同(见 1.3)。此外 LoRA 标识、多模态输入、缓存盐也参与哈希(见 1.4) |
| 「多轮对话追加 token 会触发 CoW」 | 错。CoW 只在**块内部命中**时触发,而块内部命中只在混合模型(对齐模式的 Mamba)下才可能出现。**纯 attention 部署根本走不到 CoW**(见 2.1) |
| 「CoW 会先检查引用计数大于 1」 | 错。判定只看命中长度除以块大小除不除得尽,**与引用计数无关** —— 要防的是未来命中该哈希的请求,不是当前持有引用的那个(见 2.2) |
| 「prompt 完全相同就零 prefill」 | 错。最后一个 token 必须过一次前向才能产出 logits,而且块对齐会把这个损失放大到整整一个块(见 1.6) |
| 「命中率越接近 100% 越好」 | 不一定。100% 命中说明请求模式高度重复,这往往意味着**应用层还有优化空间** —— 比如把共享同一段系统提示词的请求合并成一个批次,连查缓存都省了 |

### 7.4 怎么看真实命中率

前面所有的命中率数字都是推算。真要看线上实际值,只有指标这一条路,而这条路上有三处容易踩空。

**命中率要自己算。** 指标端点暴露的是两个计数器而不是现成的比率,单位都是 **token 数**:被查询的 token 总数,和其中命中的 token 数,相除才是命中率。跨实例共享(offload、PD 分离)另有一对独立的外部计数器,分开看 —— 本地命中率高不代表远端拉取少,反过来也一样。另有一个占用率指标可以看 KV cache 用掉了多少。

**驱逐相关没有「驱逐次数」计数器**,取而代之的是三个时长直方图:块从分配到被驱逐活了多久、被驱逐前空闲了多久、两次复用之间隔了多久。**空闲时间普遍很短,就说明缓存太小** —— 块还没等到复用就被挤掉了。

这三个直方图默认不开,要打开的开关是 **KV cache residency 指标**那一个,而**不是** KV 事件流那个开关(后者管的是 2.6 那条块移除事件,是给外部 KV 网关同步用的,两者没有关系)。还有两个前提容易忽略:它要求日志统计没被关掉,而且**默认只按 1% 采样**,读绝对计数前先看清采样率。

**手动清空缓存**有一个调试端点,带一个查询参数可以连外部 connector 的缓存一起清。有件事讲稿没说但很重要:**它会失败。** 只要还有块被占着(正在跑的请求、在途的异步 offload 传输),返回的就是失败,调用方需要重试 —— 另一个查询参数可以连正在跑的请求一起重置。
