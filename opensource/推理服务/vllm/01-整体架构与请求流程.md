## Part 1|原理

### 1.1 推理服务的延迟分解:为什么进程架构重要

一个在线 LLM 推理服务的端到端延迟(latency)由四部分组成:

$$
T_{\text{total}} = T_{\text{network}} + T_{\text{tokenize}} + T_{\text{model}} + T_{\text{detokenize}}
$$

- $T_{\text{network}}$:HTTP/gRPC 网络往返(通常 1 到 10 ms)
- $T_{\text{tokenize}}$:把 prompt 字符串转成 token ids(CPU,约 0.1 到 10 ms,取决于 prompt 长度)
- $T_{\text{model}}$:GPU 模型前向( **主要瓶颈** ,prefill 50 到 500 ms,decode 每 token 5 到 50 ms)
- $T_{\text{detokenize}}$:token id 转回字符串(CPU,每 token 约 0.1 到 1 ms)

以上数字是讲稿给的量级参考,不是本仓库实测。

朴素的 **单进程架构** (如 HuggingFace `generate`)按顺序串行执行这四步:

```text
单进程串行:
  HTTP recv → tokenize → [GPU 空闲等 CPU] → model forward → [CPU 空闲等 GPU] → detokenize → HTTP send
                ↑********************↑           ↑********************↑
                    CPU 工作 GPU 等                   GPU 工作 CPU 等
```

**问题**:CPU 和 GPU 互相阻塞。当 $T_{\text{tokenize}} = 10$ ms、$T_{\text{model}} = 50$ ms 时,串行总耗时 60 ms;如果 CPU 和 GPU 能 **重叠** (overlap),理论最短 50 ms(GPU 是瓶颈)。

**目标**:让 GPU 持续满载,CPU 工作(tokenize / detokenize / HTTP IO)藏在 GPU 计算的「背后」。

### 1.2 三种重叠策略对比

| 策略 | 做法 | 优点 | 缺点 | 代表实现 |
|---|---|---|---|---|
| A. 异步 IO + 单进程 | 用 `asyncio`,tokenize / detokenize 在 thread pool | 简单 | Python GIL 限制 CPU 并行;GPU 还是会被阻塞 | 早期 TGI |
| B. 多线程 + 单进程 | tokenize / detokenize / forward 各一个线程 | 改动小 | GIL 让 CPU 密集线程无法真正并行;tensor 在线程间共享需小心同步 | TensorRT-LLM Python 部分 |
| C. 多进程 + IPC | API 进程与 EngineCore 进程分离,用 ZMQ / 共享内存通信 | GIL 完全隔离;CPU 与 GPU 真并行;进程崩溃不互相拖累 | 启动开销大;序列化成本 | **vLLM** 、SGLang |

vLLM 选 **C** :把引擎拆成两个独立进程,用 **ZMQ** (ZeroMQ,一种高性能异步消息库)做进程间通信(IPC,inter-process communication)。「代表实现」一列是讲稿观点。

### 1.3 为什么选 ZMQ

ZMQ 相比其他 IPC 机制的优势(讲稿观点):

| 维度 | ZMQ | Python `queue.Queue` | Redis / RabbitMQ | 共享内存 |
|---|---|---|---|---|
| 跨进程 | ✓ | ✗(同进程) | ✓ | ✓ |
| GIL 释放 | ✓(C 实现) | ✗(Python) | ✓ | ✓ |
| 零拷贝 | ✓(`copy=False`) | ✗ | ✗ | ✓ |
| 部署灵活 | ✓(TCP / IPC / inproc) | ✗ | ✓(但需中间件) | ✗(单机) |
| 复杂度 | 中(需学 socket 模式) | 低 | 高(需部署 broker) | 高(手动同步) |

vLLM 的用法(以下均已在源码核对):

- **ROUTER ↔ DEALER** 模式:API 进程是 ROUTER(接收多客户端),EngineCore 进程是 DEALER(一个客户端)。请求从 API 进程的 ROUTER 发往 EngineCore 进程的 DEALER。
- **PUSH ↔ PULL** 模式:EngineCore 进程 PUSH 输出,API 进程 PULL。
- 序列化用 **msgpack** (由 msgspec 提供,比 JSON 快、比 pickle 安全);多模态张量不走 ZMQ 拷贝,而是走 `tensor_ipc` 的共享内存通道(`TensorIpcSender` / `TensorIpcReceiver`)。
- 所有 socket 都由 `vllm/utils/network_utils.py` 的 `make_zmq_socket()` 统一创建,`core.py` 与 `core_client.py` 各自调用它。

### 1.4 三种入口的职责划分

vLLM 对外暴露三种使用方式,对应三种入口类:

| 入口 | 同步 / 异步 | 进程模型 | 典型用法 |
|---|---|---|---|
| `LLMEngine` | 同步 | `InprocClient`(同进程)或 `SyncMPClient`(多进程) | 离线批量推理:`llm = LLM(...); llm.generate(prompts)` |
| `AsyncLLM` | 异步 | `AsyncMPClient`(多进程 + asyncio;DP 场景换成 DP 版的异步 client) | 在线服务:OpenAI 兼容 HTTP server |
| `EngineCore` | 内部类 | 不直接对外暴露 | 跑 scheduler + model_executor 主循环,被上面两种入口包装 |

层级关系(UML 简化):

```text
┌──────────────────────────────────────────────────────────┐
│ 用户代码                                                  │
│   llm = LLM(...)                    async_llm = AsyncLLM(...) │
│       │ generate() / chat()               │ generate() / ... │
│       ▼                                   ▼                  │
│   LLMEngine ◄──────┐                  AsyncLLM               │
│       │            │                      │                  │
│       │   EngineCoreClient (抽象) ◄───────┘                  │
│       │       ▲          ▲          ▲                        │
│       │       │          │          │                        │
│       └─► InprocClient  SyncMPClient  AsyncMPClient          │
│               │          │          │                        │
│               │(同进程)   │(子进程 ZMQ)│(子进程 + asyncio)      │
│               ▼          ▼          ▼                        │
│           EngineCore (调度 + 执行)                            │
│               │                                              │
│               ▼                                              │
│           ModelExecutor → GPU Workers                        │
└──────────────────────────────────────────────────────────────┘
```

**关键设计**:用户代码从不直接接触 `EngineCore`,而是通过 `EngineCoreClient` 抽象层。这让「同进程」和「多进程」两种模式可以无缝切换(调试时用 InprocClient,生产用 AsyncMPClient)。

### 1.5 单进程 vs 多进程:何时用哪个

vLLM 通过 `EngineCoreClient.make_client(multiprocess_mode=..., asyncio_mode=...)` 工厂方法选择,两个参数都是布尔值:

| `multiprocess_mode` | `asyncio_mode` | 选择的类 | 进程数 | 何时用 |
|---|---|---|---|---|
| `False` | `False` | `InprocClient` | 1 | 调试、单测、内存敏感场景 |
| `True` | `False` | `SyncMPClient` | 2+ | 离线批量推理(`LLM` 类的默认) |
| `True` | `True` | `AsyncMPClient` | 2+ | 在线服务(HTTP server) |
| `False` | `True` | 不支持,直接抛 `NotImplementedError` | | |

两点补充:`LLM` 类默认就是多进程,环境变量 `VLLM_ENABLE_V1_MULTIPROCESSING` 默认开,设成 0 才退回 InprocClient;`AsyncLLM` 不经过这个工厂,直接调用异步多进程 client 的构造入口。

多进程模式额外开销(讲稿量级参考):

- 进程启动(fork / spawn):约 100 到 500 ms
- ZMQ socket 握手:约 10 ms
- 每条消息 msgpack 序列化:约 0.01 到 1 ms(取决于 tensor 大小)

但对于 **长生命周期** 的推理服务(运行几小时到几天),启动开销可忽略;多进程换来的 GIL 隔离和 IO 重叠价值远大于此。

## Part 2|图解

### 2.1 进程拓扑总图

vLLM 在线服务(`AsyncLLM` + TP=2 为例)实际会拉起 **3 类进程** :1 个 API 进程、1 个 EngineCore 进程、N 个 GPU Worker 进程(N = TP × PP,严格说还要乘 prefill 侧的 CP)。三类进程各司其职,用不同的通信机制连接。

一个边界情况值得先知道:单卡时执行器默认是 uniproc,worker 就住在 EngineCore 进程里,整个服务只有 2 个进程;多卡时默认 multiproc,每张卡一个 worker 进程。

#### 2.1.2 三类进程职责对照

| 进程 | 数量 | 负载类型 | 核心职责 | 通信 |
|---|---|---|---|---|
| **API 进程** | 1 | CPU(IO 密集) | HTTP 收发、套聊天模板、tokenize、detokenize、流式分发 | 对外 HTTP,对内 ZMQ |
| **EngineCore 进程** | 1 | CPU(调度密集) | 调度、KV cache 记账、发起前向与采样、把 batch 派给 Worker | 对 API 用 ZMQ,对 Worker 用共享内存消息队列 RPC |
| **GPU Worker 进程** | N = TP × PP | GPU(计算密集) | model forward、attention kernel、采样、持有 KV cache | Worker 间 NCCL(TP all-reduce / PP P2P) |

注意采样发生在 Worker:sampler 是 ModelRunner 的一部分,EngineCore 只是在 step 里发起 `sample_tokens` 这次调用。

#### 2.1.3 为什么这样分:三层重叠

三类进程的边界正好对应三种资源,让它们能 **流水线重叠** :

```text
时间线 ──────────────────────────────────────────────────►

API 进程:     [tokenize 请求 B] ──────────── [detokenize 请求 A 的上个 token]
                    │ CPU                          │ CPU
EngineCore:         └─► [schedule] ─────────────────────────────┐
                            │ CPU                               │
GPU Worker:                 └────► [model forward 请求 A] ──── GPU
                                            │
                                    这段时间 GPU 满载,
                                    API / EngineCore 的 CPU 活儿并行进行
```

**GIL 释放是关键** :ZMQ 的收发和 GPU 的 CUDA kernel 调用都会释放 Python GIL。所以:

- EngineCore 主线程在等 GPU forward 时(GIL 释放),input_thread 与 output_thread 能并行做 ZMQ 收发。
- API 进程的 tokenize 与 detokenize,跟 EngineCore 的调度、GPU 的计算完全并行。

**EngineCore 进程内的三线程模型** :

1. **input_thread** :阻塞在 ZMQ socket 上,收到请求后 msgpack 反序列化,推入 `input_queue`。
2. **主线程(busy loop)** :从 `input_queue` 取请求交给调度器,调 `step_fn()` 跑一个 step,把输出推入 `output_queue`。
3. **output_thread** :从 `output_queue` 取输出,msgpack 序列化,ZMQ 发回 API 进程。

       CPU                    GPU                    CPU
                               │
  ─────────────────────────────┼──────────────────────────────

                               │

                               │ 推入 input_queue(主线程下个 step 处理)

### 2.3 端到端请求生命周期

一个请求从 HTTP 进来到流式输出完毕,跨 3 类进程、分 4 个阶段。 **关键区别** :阶段 A(接入)和阶段 B(prefill)对每个请求只发生一次;阶段 C(decode)是循环,生成几十到几千次;阶段 D(返回)在 B 和 C 的每一步都发生(流式)。

#### 2.3.1 四阶段总览

```text
阶段 A          阶段 B            阶段 C(循环)        阶段 D
接入            Prefill           Decode 每次 1 token  流式返回
 ────►           ────►             ────►               (贯穿 B、C)

HTTP+tokenize   算完整个 prompt    逐 token 自回归生成   每步 detokenize
(一次)          (一次或几次 step)  (几十到几千 step)    并推给客户端
   │               │                 │                   │
   ▼               ▼                 ▼                   ▼
约 1 到 10 ms   约 50 到 500 ms   约 5 到 50 ms/token   首 token = TTFT
                                                       后续 = TPOT
```

```text

│      ⋮  阶段 C 的一次循环(decode 1 个 token)
│      ⋮  约 5 到 50 ms

│      ⋮  …重复…
├ 收到第 t 个 token
│
└ 收到 [DONE](total = TTFT + (输出长度 - 1) × TPOT)
```

- **TTFT** :阶段 A 加 B 的总耗时。主要成本在 prefill(步骤 ⑦⑧)。开 prefix caching 命中公共前缀可大幅降低。
- **TPOT** :阶段 C 单次循环耗时(步骤 ⑩→⑰)。主要成本在 decode 的 GPU forward(步骤 ⑪)。开推测解码可让单步产出多个 token,等效降低 TPOT。

#### 2.3.4 一句话串起来

接入(把文字变 token)→ prefill(一次性算完整个 prompt 的 KV,吐第 1 个 token)→ decode(拿着上一个 token 加全部历史 KV,反复算下一个 token)→ 每吐一个 token 就流式推回客户端,直到 EOS。整个过程 API 进程管 IO、EngineCore 进程管调度、GPU Worker 进程管算,三者靠 ZMQ 加 GIL 释放并行重叠。

### 3.1 `EngineCore`:纯推理内循环

> **代码位置** :`vllm/v1/engine/core.py` 的 `EngineCore`。

它是不涉及任何 IPC 的纯逻辑层,给它请求和配置,它跑 scheduler 加 model_executor 循环。

#### 3.1.1 构造:七步,顺序有讲究

```text
① 加载插件(LoRA、外部 hook)
② 创建 ModelExecutor        ← GPU Worker 在这一步被 fork/spawn
③ 探测显存,算出 KV cache 配置(block 数量)
④ 创建 StructuredOutputManager
⑤ 创建 Scheduler            ← 类本身可被 --scheduler-cls 换掉
⑥ 按并发批次数决定要不要建 batch_queue
⑦ 绑定 step_fn              ← 构造时就选好,后续不再判断
```

两个要点:

- **② 在 ③ 之前** :必须先把 worker 拉起来,才能在它上面跑显存探测。
- **⑦ 是提前绑定的** :`step_fn` 在构造时就指向普通版或 batch queue 版,busy loop 里只管调,不用每次判断。

`max_concurrent_batches` 有两个来源,不只是流水线并行:PP 需要 PP 个并发批次来填满流水线;开了异步调度也要 2 个并发批次才能让调度与执行重叠。两者都不开时它等于 1,`batch_queue` 就是空。

#### 3.1.2 `step()`:调度、执行、更新三段

一次 step 的八步:

```text
① 没有未完成请求 → 直接返回
② scheduler.schedule()            → 选请求、分配 KV block
③ execute_model(non_block=True)   → 立即返回 Future,不阻塞 ┐ 并行
④ get_grammar_bitmask()           → CPU 算结构化输出掩码    ┘
⑤ future.result()                 → 阻塞等 GPU
⑥ 若返回 None → sample_tokens(bitmask)  → 补一次采样调用
⑦ 处理 ③~⑥ 期间到达的 abort
⑧ update_from_output()            → 追加 token、检测结束
```

这里有个不容易注意到的分工: **采样不是前向的尾巴,而是 executor 的另一次调用。** `execute_model` 可能直接返回采样完的结果,也可能只算到 logits 就返回空,把采样推迟到 `sample_tokens`。 **只有后一条路径才需要 bitmask** ,这也正是 ④ 能与 ③ 重叠的前提。

两个相关方法:`_should_throttle_prefills` 用于数据并行的 prefill 均衡,基类实现恒返回假,只有 DP 版才真的按节拍节流;`post_step` 负责回收 draft token,它不在 `step()` 里,而是由 busy loop 在 `step_fn()` 返回后调用。

#### 3.1.2.1 CPU/GPU 重叠原理:fork-join 模式

`step()` 的 ②③④⑤ 构成一个经典的 fork-join 结构:② 产出的 `SchedulerOutput` 同时是 GPU forward 和 grammar mask 的独立输入,两者并行执行后在 ⑤ 处合流。

```text
        ② scheduler.schedule()
        │
        │ 产出: SchedulerOutput
        ├─ token_ids, positions, block_table   (GPU forward 的输入)
        ├─ 哪些请求需要 structured output       (grammar mask 的输入)
        └─ 每个请求已生成的 token 序列          (grammar 状态机的输入)
        │
        ├─ fork ──────────────────────────────────┐
        │                                         │
        ▼ ③ 路径                                  ▼ ④ 路径
execute_model(non_block=True)          get_grammar_bitmask()
├─ 把 SchedulerOutput 派给              ├─ 遍历每个 structured 请求
│  GPU Worker                          │  查询 grammar 状态机:
├─ GPU Worker 构造 input tensor         │  「当前 token 序列后,
├─ model.forward()                     │   哪些 token id 合法?」
│  产出 → logits                        ├─ 产出 → bitmask [num_reqs, vocab]
│                                      │  纯 CPU 计算(xgrammar C++)
│  (CUDA kernel 释放 GIL)               │  (不碰 GPU)
│                                      │
▼                                      ▼
Future<logits>                         grammar_bitmask
        │                                         │
        ├─ join ──────────────────────────────────┘
        ▼
⑤ future.result()   ← 等两边都完成(取 max(GPU 时间, CPU 时间))
        │
        ▼
⑥ 把 grammar_bitmask 应用到 logits: logits[mask==0] = -inf
        │
        ▼
⑦ sampler 采样
```

**为什么 ③ 和 ④ 没有依赖关系** ,看它们的输入和输出:

| | 步骤 ③ GPU forward | 步骤 ④ grammar mask |
|---|---|---|
| 输入 | `SchedulerOutput` 里的 token_ids / positions / block_table | `SchedulerOutput` 里的「哪些请求要 structured output」加每请求已生成的 token 序列 |
| 输入来源 | 都来自 ② 的 `schedule()`,在 ② 结束时已确定 | 同上,也来自 ②,② 结束时就固定了 |
| 输出 | logits(每请求一个 `[vocab_size]` 向量) | bitmask(标记每个 token id 在当前位置是否合法) |
| 输出用途 | 喂给 ⑥ 的 sampler | 在 ⑥ 前与 logits 做元素级 mask 运算 |

**关键洞察** :③ 的输入和 ④ 的输入都来自 ②,彼此不互为输入。③ 不需要 ④ 的 bitmask 才能算 forward(模型前向只看 token_ids 和 KV cache);④ 不需要 ③ 的 logits 才能算 mask(grammar 状态机只看 token 序列)。两者只在 ⑥ 处合流:bitmask 把 logits 里非法 token 的值压成负无穷,sampler 才不会采出非法 token。

**为什么能在 Python 单线程里并行** ,靠 GIL 释放:

1. ③ 调 `execute_model(non_block=True)`:立即返回一个 `Future`,不等 GPU 算完。底层是 Worker 进程通过 RPC 异步提交 forward,CUDA kernel 开始在 GPU 上跑。
2. CUDA kernel 在 GPU 上执行时,Python GIL 被释放(kernel 启动是 C 调用,不持 GIL)。
3. 此时 Python 主线程可以继续往下跑 ④ 的 `get_grammar_bitmask()`,它在 CPU 上执行 xgrammar 的 C++ 代码,也释放 GIL。
4. 于是 GPU 跑 forward 和 CPU 跑 grammar mask 物理并行,互不阻塞。
5. ⑤ `future.result()` 才阻塞等 GPU。如果 ④ 比 ③ 快(grammar mask 通常约 0.1 到 1 ms,GPU forward 5 到 50 ms),⑤ 时 CPU 已经闲着等 GPU 了,重叠是完全免费的。

**什么时候重叠不免费** :如果 grammar mask 计算比 GPU forward 还慢(极端情况:超复杂 JSON schema 加巨大词表加长 token 序列),⑤ 时 GPU 已经算完 logits 了,但 CPU 还在算 mask,此时主线程阻塞等 CPU,GPU 闲置。不过这种情况极少见,xgrammar 的 C++ 实现极快。以上耗时都是量级参考。

还有一个前提值得补:这条 fork-join 只对带结构化输出的请求成立。`get_grammar_bitmask` 在本 step 没有任何结构化请求时直接返回 `None`,普通请求走的是「前向顺带采样」那条路,没有可重叠的 CPU 活儿。

**一句话总结** :② 的 `schedule()` 是 fork 点,它产出的 `SchedulerOutput` 同时是 GPU forward 和 grammar mask 的独立输入,两者输出在 ⑥ 处 join。`non_block=True` 加 GIL 释放,让 Python 单线程也能把 CPU 和 GPU 的活儿并行起来。

#### 3.1.2.2 `get_grammar_bitmask()` 到底在算什么

要理解为什么 ④ 和 ③ 没有依赖,需要看清楚 `get_grammar_bitmask()` 的输入、输出和内部逻辑。它定义在 `vllm/v1/core/sched/scheduler.py`,四段结构:

1. 整个 batch 都没有结构化输出请求就直接返回,零开销。
2. 筛出本 step 需要结构化输出的请求——仍在分块 prefill 中的不算,它这轮还轮不到出 token。
3. 把这批请求交给 `StructuredOutputManager` 算 bitmask。
4. 包成一个 `GrammarOutput` 返回:请求 id 列表加 bitmask 数组。

**输入** (全部来自 ② 的 `SchedulerOutput` 加请求自身状态, **不涉及 logits** ):

- `scheduler_output.num_scheduled_tokens`:本 step 调度了哪些请求。
- `req.use_structured_output`:该请求是否要求结构化输出(JSON、正则等)。
- `req.is_prefill_chunk`:是否还在分块 prefill 中(这时还没轮到它出 token,不需要 mask)。
- 请求已经生成的 token 序列(grammar 状态机据此推进)。注意它不是形参,而是从传进去的请求对象里读。
- `scheduler_output.scheduled_spec_decode_tokens`:推测解码的 spec token,需要为每个 spec 位置各算一个 mask。

**输出** :一个 `GrammarOutput`,里面装着请求 id 列表和一个 bitmask 数组,每一行是一个请求的合法 token 掩码,bit 为 1 表示该 token id 在当前位置合法,为 0 表示非法。列数按每 32 个 token id 打包成一个整数来算。

有个实现细节值得记一笔: **这个 bitmask 缓冲区是预分配并跨 step 复用的** ,不是每步新建。行数按「最大并发请求数 × (1 + 最大 spec token 数)」一次性分配好,每步只填前面用到的那几行。

**内部逻辑** (`StructuredOutputManager.grammar_bitmask`):

1. 对每个结构化输出请求,取出它的 grammar 对象(在请求创建时由 xgrammar 编译 JSON schema 得到)。
2. 调用 matcher 的 `fill_next_token_bitmask()`(xgrammar 与 guidance 两个后端各有实现):grammar 内部维护一个 **状态机** ,根据请求已生成的 token 序列推进到当前状态,然后查询「从当前状态出发,哪些 token id 是合法的后继」。请求多时还会并行填充。
3. 把结果写入预分配的 bitmask 的对应行。
4. 返回整个 bitmask。

**关键** :整个过程是纯 CPU 计算(xgrammar 的 C++ 实现),输入是「已生成的 token 序列」(在 ② 结束时就已确定), **完全不碰 GPU、不需要 logits** 。

#### 3.1.2.3 例子:JSON schema 的 grammar mask 演进

假设用户请求模型输出一个 JSON 对象,schema 为:

```json
{"type": "object", "properties": {"name": {"type": "string"}}}
```

xgrammar 把这个 schema 编译成一个 **有限状态机** 。模型每生成一个 token,状态机推进一次,并输出「当前位置允许哪些 token」的 bitmask。

以下用 Llama-3 tokenizer(词表 12 万多)为例,追踪 grammar mask 在 4 个 decode step 中的变化(只展示关键 token,实际 mask 覆盖全部 token id;token id 为示意值):

```text
请求 R: structured_output = {"json": {"type":"object","properties":{"name":{"type":"string"}}}}
已生成 token 序列: []   (刚开始 decode)

── Step 1(生成第 1 个 token)──
grammar 状态机: 初始状态 → 期望 "{"
  查询: "从初始状态,哪些 token 合法?"
  bitmask[R]:
    token "{"   的 id  → bit = 1  ✓ 合法
    token "}"   的 id  → bit = 0  ✗ 非法(JSON 对象必须先有 "{")
    token " "   的 id  → bit = 1  ✓ 合法(空白允许)
    token "abc" 的 id  → bit = 0  ✗ 非法
    ...(其余全部 token 的 bit)

  同时 GPU forward 算出 logits[R] = [..., v_{"{"}=2.1, ..., v_{"}"}=-0.3, ...]

  合并(step ⑥): logits[R][bitmask==0] = -∞
    → logits[R]["}"]   = -∞  ("}" 被屏蔽)
    → logits[R]["abc"] = -∞  ("abc" 被屏蔽)
    → logits[R]["{"]   = 2.1 ("{" 保留)

  sampler 采样 → 选中 "{"
  请求 R 的 token 序列变为: ["{"]

── Step 2(生成第 2 个 token)──
grammar 状态机: 看到 "{" → 推进到「期望 key 或 }」
  查询: "看到 '{' 后,哪些 token 合法?"
  bitmask[R]:
    token "name" 的 id → bit = 1  ✓(JSON key)
    token "{"    的 id → bit = 0  ✗(不能嵌套 "{")
    token "\""   的 id → bit = 1  ✓(字符串开头)
    ...

  GPU forward 算 logits[R](只看上一个 token "{" 加全部历史 KV)
  合并: logits[R][bitmask==0] = -∞
  sampler → 选中 "\""
  序列: ["{", "\""]

── Step 3(生成第 3 个 token)──
grammar 状态机: 看到 "\"" → 推进到「字符串内容」
  bitmask[R]:
    token "name" 的 id → bit = 1  ✓
    token "\""   的 id → bit = 1  ✓(字符串可以结束)
    token "}"    的 id → bit = 0  ✗(字符串还没闭合)
    ...

  GPU forward 算 logits[R](看 "\"" 加历史 KV)
  合并 + 采样 → 选中 "name"
  序列: ["{", "\"", "name"]

── Step 4(生成第 4 个 token)──
grammar 状态机: 看到 "name" → 推进到「期望 \" 结束 key」
  bitmask[R]:
    token "\""   的 id → bit = 1  ✓(闭合字符串)
    token "name" 的 id → bit = 0  ✗(key 已结束)
    ...

  GPU forward + 合并 + 采样 → 选中 "\""
  序列: ["{", "\"", "name", "\""]
  ... 继续生成 ":", " ", "\"", "Alice", "\"", "}"
```

#### 3.1.2.4 从例子看依赖关系

对照上面的 4 个 step,可以清楚看到两条路径的输入来源:

| | GPU forward(步骤 ③) | grammar mask(步骤 ④) |
|---|---|---|
| Step 1 的输入 | token 序列 = prompt(② 已确定) | token 序列 = 空(② 已确定) |
| Step 2 的输入 | token 序列 = prompt + ["{"](上一步 ⑦ 已追加) | token 序列 = ["{"](上一步 ⑦ 已追加) |
| Step 3 的输入 | token 序列 = prompt + ["{", "\""] | token 序列 = ["{", "\""] |
| 需要 logits 吗? | 不需要(它产出 logits) | **不需要** (只需要 token 序列) |
| 需要 KV cache 吗? | 需要(读历史 KV 算 attention) | **不需要** (grammar 是纯字符串状态机) |

**为什么没有依赖** :

- GPU forward 的输入是 token_ids 加 KV cache。token_ids 来自 ② 的 `SchedulerOutput`,KV cache 是之前 step 积累的。它 **产出** logits,但不 **消费** grammar mask。
- grammar mask 的输入是已生成的 token 序列。这个序列在 ② 结束时就固定了(② 之后的 ③④⑤ 都不会修改 token 序列,要等到 ⑦ 的 `update_from_output` 才追加新 token)。它 **产出** bitmask,但不 **消费** logits。
- 两者输出在 ⑥ 处合流:把 logits 里非法 token 的值压成负无穷,然后 ⑦ 的 sampler 才从修改后的 logits 里采样。

依赖图:

```text
② SchedulerOutput ─────────────┬──────────────┐
  (token_ids, positions,       │              │
   block_table, 请求列表)       │              │
                               ▼              ▼
                      ③ GPU forward      ④ grammar mask
                      输入: token_ids     输入: 已生成 token 序列
                            + KV cache          (来自 ② / 上轮 ⑦)
                      输出: logits        输出: bitmask
                               │              │
                               └──────┬───────┘
                                      ▼
                      ⑥ logits[bitmask==0] = -∞
                                      │
                                      ▼
                      ⑦ sampler 采样 → 新 token
                                      │
                                      ▼
                      ⑧ 追加 token 到序列(下轮 ③④ 的输入)
```

③ 和 ④ 之间 **没有箭头** ,这就是它们能并行的原因。两者的唯一共同上游是 ②,唯一共同下游是 ⑥。

还要注意一点: **⑥ 的合流发生在 GPU Worker 里** 。EngineCore 只是把算好的 bitmask 随 `sample_tokens` 一起下发,真正把非法位置压成负无穷的那步在 worker 的采样路径上执行。

#### 3.1.2.5 grammar mask 和 logits 为什么能叠加

一个常见困惑:grammar mask 是根据 **过去** 已生成的 token 序列算出来的,而 logits 是模型对 **当前** 的预测,「用过去算的 mask 去屏蔽当前的 logits」为什么合理?

关键在于: **grammar mask 和 logits 回答的是同一个问题,即「下一个 token 是什么」** ,只是角度不同。

| | 看什么 | 回答的问题 | 输出 |
|---|---|---|---|
| grammar mask | 过去已生成的 token 序列 | 「根据语法规则,下一个 token **可以** 是什么?」 | 合法或非法的布尔掩码(硬约束) |
| GPU logits | 过去已生成的 token 加 KV cache | 「根据模型学到的语言规律,下一个 token **大概率** 是什么?」 | 每个 token 的概率分布(软偏好) |

两者都指向同一个「下一个 token」位置,所以可以把 grammar 的硬约束叠加到 logits 的软偏好上,让 softmax 自动把非法 token 的概率归零,采样器只在合法 token 里按模型偏好选。

**为什么「看过去」能判断「下一个」** :grammar 是一个 **有限状态机** ,其特性就是「给定当前状态(由过去的输入序列决定),能精确判定下一个输入是否合法」。这就像编译器的语法分析:编译器看到 `int x =` 后,知道下一个必须是数字或标识符,不能是 `}`。这不是「判断过去」,而是「用过去推导未来」。

**grammar 和 logits 可能冲突,冲突时 grammar 赢。** 以 schema `{"type":"object"}` 为例:

```text
已生成序列: ["{"]

grammar 状态机看到 "{" → 状态推进到「期望 } 或 key」
  bitmask:
    "}"   合法 ✓   (闭合对象)
    " "   合法 ✓   (空白)
    "{"   非法 ✗   (JSON 对象里 { 后面不能直接再 {)
    "abc" 非法 ✗   (key 必须用引号)

GPU forward 也看 ["{"] 加 KV cache,预测下一个 token:
  logits:
    "}"   = 1.9    (模型觉得闭合概率高)
    " "   = 0.2    (空白也有可能)
    "{"   = 1.5    ← 模型很想选 {!训练数据里 { 后面经常再跟 {
    "abc" = 0.8    ← 模型想直接写 key

合并 logits[bitmask==0] = -∞:
  "}"   = 1.9    (保留)
  " "   = 0.2    (保留)
  "{"   = -∞     ← 屏蔽!语法禁止
  "abc" = -∞     ← 屏蔽!语法禁止

采样 → "}" 概率最大 → 选中 "}" → 语法正确
```

模型很想选 `{`(因为训练数据里 `{` 后面经常再跟 `{`),但 grammar 说不行,JSON 对象里 `{` 后面不能直接再跟 `{`。 **grammar 是语法规则,logits 是模型的语言直觉,两者可能冲突,冲突时 grammar 赢。**

**为什么设负无穷而不是直接过滤 token 列表** :

1. GPU 上的 softmax 加采样器是对 **整个词表** 做的固定形状操作,改词表大小要重新分配张量,开销大。
2. 把非法位置赋值为负无穷是一个 **元素级赋值** ,GPU 上一条 kernel 完成,不改形状。
3. 数学上等价:$e^{-\infty} = 0$,softmax 自动让非法 token 概率归零,剩余合法 token 的概率自动重新归一化,复用已有采样管线。

### 3.1.3 `step_with_batch_queue()`:流水线并行的气泡消除

> **代码位置** :同一文件的 `EngineCore.step_with_batch_queue()`。

启用条件是并发批次数大于 1。前面 3.1.1 提过它的取值规则:默认等于流水线并行度;开了异步调度且用 V2 model runner 则是 PP 加 1;开了异步调度、用 V1 model runner 且 PP 不超过 1 则是 2。也就是说 batch queue 并非「只有 PP 大于 1 才启用」,单卡开异步调度同样会走这条路径。

它和普通 `step()` 的区别在于「不阻塞等结果」:

```text
每次调用:
  ① 若队列没满且还有请求可排 → 排一批、提交前向、把 future 塞进队列 → 直接返回
  ② 队列满了(或没请求可排)  → 阻塞等最老的那批完成 → 更新状态
```

**收益** :当队列容量等于流水线级数时,气泡接近 0。

这里还有个 `step()` 里没有的机制: **采样延迟** 。当请求带结构化输出、而 grammar 状态机还在等上一步产出的 token 时,本 step 只提交前向、不提交采样,把这一批挂起;等这一轮的输出把 token 写回请求后,才补算 bitmask 并发起采样。带草稿 token 时还要先过滤掉无效的 spec token,再算 bitmask。

> 🖼️ 占位:batch queue 的流水线时序。回答「队列容量为 PP 时,连续几个 step 的调度、前向、采样、更新如何错开,气泡消在哪里,采样延迟那一批是怎么补上的」。

### 3.2 `EngineCoreProc`:ZMQ 多进程封装

> **代码位置** :同一文件的 `EngineCoreProc`,继承 `EngineCore`,在子进程中运行。

#### 3.2.1 构造与握手

顺序是:建两个线程间队列 → **ZMQ 地址握手** → 调父类构造 → 起 input/output 两个线程。

**握手必须在父类构造之前** ,因为父类构造会创建 executor(也就是拉起 GPU Worker),而 ZMQ 地址要在那之前谈定。

#### 3.2.2 busy loop 主循环

循环体只有两步:处理输入队列里的请求,然后跑一个 step。 **`while` 的条件本身就是 shutdown 状态机** ——返回假即退出,不是在循环体里 `break`。

`_process_input_queue` 的关键是既不空转也不失去响应:只要「没活儿干且引擎还在跑」,就用一个可配置的阻塞标志去取队列,取不到就跳出;等到有活儿干了,再用非阻塞方式把队列剩余请求一次排空。那个阻塞标志是字段不是常量,DP 等场景会改它。

请求分发按类型分四支: **唤醒** 直接返回; **添加** 解出请求与 DP wave 号后交给调度器; **中止** 批量处理; **工具调用** 走一套通用的远程方法调用(profile、sleep、reset prefix cache 都走这条)。

`_process_engine_step` 比名字看上去多做两件事:调 `step_fn()` 后把输出逐条推入输出队列,再调 `post_step()`;如果本轮没真正执行模型但调度器里还有请求(例如在等远端 KV),它会主动睡 1 毫秒让出 GIL,给后台传输线程留出推进机会。

#### 3.2.3 input_thread:ZMQ 接收与反序列化

流程是:建 DEALER socket → **先发一条 ready 消息** → poll 循环收包 → 按类型选解码器 → 推入输入队列。

三个设计要点:

- **ready 消息是 DEALER 到 ROUTER 这个模式的硬要求** 。ROUTER 按 identity 路由,必须先收到对端的消息才知道这个 identity 存在,所以子进程要先主动报到。消息里带着 `max_model_len`、`num_gpu_blocks` 等前端需要的信息。
- **收包用零拷贝** :ZMQ 消息不复制到 Python 对象,直接用 buffer 视图,避免大张量的拷贝开销。
- **类型单独一帧** :请求类型用一个字节标识占一帧,不用解析整个 msgpack 就能分发,而且不同类型可以用不同的解码器。

#### 3.2.4 output_thread:零拷贝 ZMQ 发送

流程是:从输出队列取 → 回收 ZMQ 已发完的 buffer → 把 msgpack 编码进复用的 buffer → 发送并拿到 tracker。

**为什么需要 tracker** :ZMQ 的 send 是异步的,函数返回时数据可能还在内核缓冲区,立刻回收 buffer 会数据错乱。tracker 让代码能精确知道何时可以复用。

判断方向容易记反: **没发完才挂进待回收队列等下一轮,发完了才立即还池** 。另外它专门取第一帧的 tracker,因为复用的正是第一帧那块 buffer,而 ZMQ 自带的多帧发送只返回最后一帧的 tracker。

### 3.3 `EngineCoreClient`:客户端抽象层

> **代码位置** :`vllm/v1/engine/core_client.py` 的 `EngineCoreClient` 抽象基类。

#### 3.3.1 工厂方法

`make_client` 按两个布尔参数选具体实现:

| 多进程 | asyncio | 结果 |
|---|---|---|
| ✗ | ✗ | `InprocClient` |
| ✓ | ✗ | `SyncMPClient` |
| ✓ | ✓ | 转交 `make_async_mp_client` 再选一层 |
| ✗ | ✓ | **显式抛错** ,不存在「异步同进程」客户端 |

异步那一支还要按数据并行配置三选一:DP 为 1 给 `AsyncMPClient`;开了 DP 且用外部负载均衡(每个 DP rank 一个 client)给 `DPAsyncMPClient`;开了 DP 且用内部负载均衡(一个 client 均衡到所有 rank)给 `DPLBAsyncMPClient`。

四种具体客户端的层级:

```text
EngineCoreClient (ABC)
├── InprocClient              (同进程,直接调用 EngineCore)
└── MPClient                  (多进程基类,管理子进程)
    ├── SyncMPClient          (同步包装)
    └── AsyncMPClient         (asyncio 包装)
        └── DPAsyncMPClient   (数据并行扩展)
            └── DPLBAsyncMPClient  (数据并行 + 内部负载均衡)
```

`DPLBAsyncMPClient` 继承的是 `DPAsyncMPClient`,不是与它并列的兄弟类。

#### 3.3.2 `InprocClient`:同进程直调

最简单的客户端, **没有 ZMQ、没有 busy loop** ,直接持有 `EngineCore` 实例;拉输出就是同步调一次 `step_fn()` 再调 `post_step()`。

用途:单元测试、调试、嵌入式集成。 **生产不用** ,因为没有 IO 重叠。

#### 3.3.3 `MPClient`:多进程基类

它做三件事:建 ZMQ context、装资源守卫、决定地址来源。

三个容易看漏的点:

- **context 不是裸的** :底层是一个带 2 个 IO 线程的同步 context,asyncio 模式下再用异步 context 包装 **同一个** 底层 context,这样同步与异步 socket 共享 IO 线程。
- **子进程不是在这里 spawn 的** :进程创建收敛在 `vllm/v1/engine/utils.py` 的引擎启动器里。`EngineCoreProc.run_engine_core` 是静态方法,在子进程里创建实例并调用 busy loop。
- **资源守卫用 `weakref.finalize` 挂钩** ,保证 client 被垃圾回收时 socket 与子进程一起收掉;构造中途抛异常也能回收已建的部分。

地址来源二选一:外部传了地址就说明引擎由外部托管,本 client 只连不拉;否则自己决定 IPC 或 TCP 地址并拉起子进程。

### 3.4 `AsyncLLM`:在线服务异步入口

> **代码位置** :`vllm/v1/engine/async_llm.py` 的 `AsyncLLM`,OpenAI 兼容 HTTP server 的直接后端。

#### 3.4.1 `generate()` 流式生成器

两步:把请求送进 EngineCore 拿到一个输出收集器,然后循环从收集器取、`yield` 出去,直到标记完成。取的时候先试非阻塞,取不到才 `await`。

这里的收集器是 `RequestOutputCollector`, **不是 `asyncio.Queue`** :它内部只存一个待取的输出对象加一个 asyncio 事件,`put` 时若上一个还没被取走会 **就地合并** 而不是排队。这对流式很关键,客户端消费慢时不会堆积出一长串待发块,而是自动合并成一块。

#### 3.4.2 `_run_output_handler`:后台 asyncio task

一个持续运行的后台循环,是 API 进程侧的「消费者」:异步拉 EngineCore 的输出 → 交给 `OutputProcessor` 处理(detokenize 等)→ 推入各请求的收集器。

注意它是 **尝试性启动** 的:构造时先探一下当前有没有事件循环,有才立刻起 task,没有就推迟到第一次真正用到时再起。

### 3.5 `LLMEngine`:离线批量同步入口

> **代码位置** :`vllm/v1/engine/llm_engine.py` 的 `LLMEngine`,是 `LLM` 类的引擎。

它用 `SyncMPClient` 或 `InprocClient` 包装 EngineCore,提供同步 API。一次 `step()` 四步:同步拉一个 step 的输出 → 交给 `OutputProcessor` 处理 → **把因 stop string 结束的请求反向 abort 回 EngineCore** → 记录统计。

第三步值得单独看: **stop string 是在 API 侧判出来的,所以要反向发一条 abort 回去** 。EOS 和长度上限由调度器自己判,不需要这条回路。这也解释了为什么两处停止条件要分开实现。

离线批量的驱动循环在 `vllm/entrypoints/offline_utils.py` 里,逻辑就是「只要还有未完成请求就一直 `step()`,把完成的收集起来」。

### 3.6 `InputProcessor` 与 `OutputProcessor`

> **代码位置** :`vllm/v1/engine/input_processor.py` 与 `output_processor.py`。

#### 3.6.1 InputProcessor

职责:把用户的原始输入(字符串、token 列表、多模态字典)规范化为引擎请求对象。核心方法做四件事:经 renderer 调 tokenizer 编码、多模态预处理与缓存注入、校验采样参数与 LoRA 请求、构造 `EngineCoreRequest`。

有两件事 **不在** 这里做,容易记混: **chat template 由 renderer 在更外层套好** ,InputProcessor 拿到的已经是完整 prompt; **prompt 的 block hash 在 EngineCore 进程算** ,不在 API 进程。

#### 3.6.2 OutputProcessor

职责:把 EngineCore 的输出(token ids 加采样结果)转化为用户可见的 `RequestOutput`。核心方法做五件事:增量 detokenize(避免每次从头)、 **检测 stop string** (EOS 与长度上限由调度器判,不在这里)、计算 logprobs、处理 n 大于 1 的并行采样(靠父请求关联)、汇总推测解码的接受与拒绝统计。

辅助类 `RequestOutputCollector` 每个请求一个,作为流式产出的中转;单个请求的状态机是 `RequestState`;最终的 `CompletionOutput` 定义在 `vllm/outputs.py`。

## Part 4|对比与决策

### 4.1 与竞品的多进程架构对比

| 维度 | vLLM V1 | SGLang | TensorRT-LLM | HuggingFace TGI |
|---|---|---|---|---|
| 进程模型 | 2 进程(API + EngineCore) | 3 进程(API + Scheduler + Detokenizer) | 2 进程(Python + Triton) | 2 进程(Router + Python) |
| IPC | ZMQ + msgpack | ZMQ + msgpack | gRPC + 共享内存 | Rust channel + Python |
| 线程模型 | 3 线程(input / main / output) | 每进程单线程 | 单进程多线程 | Rust async + Python |
| GIL 隔离 | 完全(独立进程) | 完全 | 部分(Python 单进程) | Rust 部分隔离 |
| 零拷贝 tensor | 走 tensor_ipc 的共享内存通道 | 类似 | 共享内存 | 无 |
| 崩溃恢复 | EngineCore 崩溃 API 仍可响应 | 同 | 需重启 | 需重启 |

只有 vLLM 一列在本仓库核对过,其余三列是讲稿观点。另外 vLLM 那个「2 进程」不含 GPU Worker:多卡时每张卡还有一个 worker 进程,单卡走 uniproc 则 worker 就在 EngineCore 进程内。

**核心差异** (讲稿观点):

- vLLM 和 SGLang 都用 ZMQ 多进程,但 vLLM 把 detokenize 放在 API 进程(共享 OutputProcessor),SGLang 单独开 Detokenizer 进程,所以 vLLM 进程数更少、启动更快。
- TensorRT-LLM 用 gRPC,跨网络部署更友好(PD 分离场景),但单机内 ZMQ 的延迟更低。
- TGI 用 Rust 实现 Router,性能极好但开发门槛高。

### 4.2 何时用哪种入口

| 场景 | 推荐入口 | 代码 |
|---|---|---|
| 离线批量推理(评测、数据生成) | `LLM` 加 `LLMEngine` | `llm = LLM("meta-llama/Llama-3-8B"); llm.generate(prompts)` |
| 在线 HTTP 服务(生产部署) | `AsyncLLM` | `vllm serve <model>`(内部用 AsyncLLM) |
| 嵌入到其他 Python 应用 | `LLM`(把多进程开关置 0 走 InprocClient) | 调试或单测场景 |
| 嵌入到异步框架(FastAPI 等) | `AsyncLLM` | `async for out in async_llm.generate(...)` |
| 多 GPU 推理 | 任一(并行配置在 `ParallelConfig`) | `LLM("...", tensor_parallel_size=8)` |
| PD 分离部署 | `AsyncLLM` 加 KV connector | prefill 与 decode 分节点部署,跨节点传 KV cache |

### 4.3 调试技巧

1. **看进程拓扑** :`ps -ef | grep vllm`,应该看到 API 进程加 EngineCore 进程,多卡时还有 N 个 GPU Worker 进程。
2. **看 ZMQ 流量** :用 `tcpdump` 或 `ss -t` 监控 ZMQ 端口(默认随机端口,可在日志里搜 zmq)。
3. **单进程调试** :设 `VLLM_ENABLE_V1_MULTIPROCESSING=0`(默认开)再直接用 `LLM(...)`。`LLMEngine` 把这个值传给 `make_client` 的多进程开关,开关为假时工厂落到最后一行返回 `InprocClient`,此时 EngineCore 在同进程内, **断点能直接命中** 。
4. **性能分析** :profiling 走配置项而不是环境变量,用 `--profiler-config` 设 profiler 类型(torch / cuda / proton)和输出目录。两者有强制配对校验:设了目录但 profiler 不是 torch 会报错,反之选了 torch 却没给目录也会报错。

### 4.4 常见误区

| 误区 | 真相 |
|---|---|
| 「AsyncLLM 比 LLMEngine 快」 | 不一定。异步只影响 IO 重叠,模型前向速度一样。单请求时异步略慢(asyncio 开销)。 |
| 「多进程更耗内存」 | 每进程多出一份 Python 解释器开销,但相对 KV cache(GB 级)可忽略。 |
| 「ZMQ 序列化是大瓶颈」 | msgpack 极快,张量走共享内存零拷贝。瓶颈永远是 GPU forward。 |
| 「InprocClient 没用」 | 单测、嵌入式集成、调试断点都需要它。生产才用 AsyncMPClient。 |

本表中的量级判断是讲稿观点。

### 4.5 关键配置参数

本篇涉及的参数:

| 参数 | 默认值 | 作用 | 本篇相关场景 |
|---|---|---|---|
| `--tensor-parallel-size` | 1 | TP 并行度 | Worker 数 |
| `--pipeline-parallel-size` | 1 | PP 并行度(启用 batch_queue) | `step_with_batch_queue` |
| `--data-parallel-size` | 1 | DP 并行度 | 选择 DP 版的 EngineCoreProc 与 client |
| `--max-num-seqs` | 128 | 最大并发请求数 | scheduler 容量 |
| `--max-num-batched-tokens` | 2048 | 每 step 最大 token 数 | scheduler 容量 |
| `--profiler-config` | profiler 为空 | 选 profiler 类型与输出目录 | 性能分析 |
| `VLLM_ENABLE_V1_MULTIPROCESSING` | 开 | 置 0 则 `LLMEngine` 走 `InprocClient`(单进程) | 入口与客户端选择 |

注意两点: `--max-num-seqs` 与 `--max-num-batched-tokens` 的字段默认值只是 **起点** ,启动时会按显存分档上调(大显存的 server 场景会显著高于 128 与 2048),所以实际生效值要看启动日志而不是这张表。另外没有 `--use-v2` 这个命令行开关(要切 V2 model runner 走的是环境变量),也没有 `--disable-async-output-processing`,异步输出处理不是可开关的选项。
