# vLLM 01|整体架构与请求流程

一条请求从 HTTP 进来到 token 吐出去,要跨三类进程、经过十几次交接。这一章讲清为什么要拆成多进程、每一跳落在谁手里,以及入口该怎么选。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与方法,见代码索引页;正文不写路径与行号。

## Part 1|原理:一个 step 里 CPU 和 GPU 都不该等对方

### 1.1 推理服务的延迟分解:为什么进程架构重要

一个在线 LLM 推理服务的端到端延迟(latency)由四部分组成:

$$
T_{\text{total}} = T_{\text{network}} + T_{\text{tokenize}} + T_{\text{model}} + T_{\text{detokenize}}
$$

- $T_{\text{network}}$:HTTP/gRPC 网络往返(通常 1 到 10 ms)
- $T_{\text{tokenize}}$:把 prompt 字符串转成 token ids(CPU,约 0.1 到 10 ms,取决于 prompt 长度)
- $T_{\text{model}}$:GPU 模型前向( **主要瓶颈** ,prefill 50 到 500 ms,decode 每 token 5 到 50 ms)
- $T_{\text{detokenize}}$:token id 转回字符串(CPU,每 token 约 0.1 到 1 ms)

以上数字是讲稿给的量级参考,不是本仓库实测。

用户最先感知到的是首字延迟 TTFT。把它单独拆开会发现它不只是 prefill:排队、tokenize、prefill、返回四段各落在不同的进程上,能缩短它的手段也分别散在后面各章。

![TTFT 拆成排队、tokenize、prefill、返回四段的时间条,每段标注它什么时候最长,下方列出各段能靠什么缩短以及本项目在哪一章展开](/opensource/vllm/01h-ttft-breakdown.svg)

朴素的 **单进程架构** (如 HuggingFace `generate`)按顺序串行执行这四步:

![串行与重叠:同一条请求的 CPU 段与 GPU 段各占哪段时间](/opensource/vllm/01a-overlap-timeline.svg)

[打开交互版](/opensource/vllm/01a-overlap-timeline.html)

**问题**:CPU 和 GPU 互相阻塞。当 $T_{\text{tokenize}} = 10$ ms、$T_{\text{model}} = 50$ ms 时,串行总耗时 60 ms;如果 CPU 和 GPU 能 **重叠** (overlap),理论最短 50 ms(GPU 是瓶颈)。

**目标**:让 GPU 持续满载,CPU 工作(tokenize / detokenize / HTTP IO)藏在 GPU 计算的「背后」。

### 1.2 三种重叠策略对比

知道该让 CPU 和 GPU 重叠是一回事,**怎么重叠**是另一回事。三种做法的代价差得很远,而 vLLM 选了最重的那个——得说清为什么值得。

| 策略 | 做法 | 优点 | 缺点 | 代表实现 |
|---|---|---|---|---|
| A. 异步 IO + 单进程 | 用 `asyncio`,tokenize / detokenize 在 thread pool | 简单 | Python GIL 限制 CPU 并行;GPU 还是会被阻塞 | 早期 TGI |
| B. 多线程 + 单进程 | tokenize / detokenize / forward 各一个线程 | 改动小 | GIL 让 CPU 密集线程无法真正并行;tensor 在线程间共享需小心同步 | TensorRT-LLM Python 部分 |
| C. 多进程 + IPC | API 进程与 EngineCore 进程分离,用 ZMQ / 共享内存通信 | GIL 完全隔离;CPU 与 GPU 真并行;进程崩溃不互相拖累 | 启动开销大;序列化成本 | **vLLM** 、SGLang |

vLLM 选 **C** :把引擎拆成两个独立进程,用 **ZMQ** (ZeroMQ,一种高性能异步消息库)做进程间通信(IPC,inter-process communication)。「代表实现」一列是讲稿观点。

为什么 A、B 两条路走不通、C 又为什么能行,根子都在 Python 的全局解释器锁(GIL):一个进程里不管开多少线程,同一时刻只有一个能跑 Python 代码。把三件事画在一起:

![为什么要拆成两个进程:上段是三个线程轮流持有 GIL 的时间条,中段是单进程里 GPU 每步之后都空一段的时间条,下段是 API 进程与 EngineCore 进程各持一把 GIL、用 ZMQ 相连、GPU 不再停的结构与时间条](/opensource/vllm/01f-why-two-processes.svg)

### 1.3 为什么选 ZMQ

拆成两个进程之后,新问题是它们怎么说话。**通信方式选错,省下来的重叠时间会被序列化和拷贝吃回去**,拆进程就白拆了。

ZMQ 相比其他 IPC 机制的优势(讲稿观点):

| 维度 | ZMQ | Python `queue.Queue` | Redis / RabbitMQ | 共享内存 |
|---|---|---|---|---|
| 跨进程 | ✓ | ✗(同进程) | ✓ | ✓ |
| GIL 释放 | ✓(C 实现) | ✗(Python) | ✓ | ✓ |
| 零拷贝 | ✓(`copy=False`) | ✗ | ✗ | ✓ |
| 部署灵活 | ✓(TCP / IPC / inproc) | ✗ | ✓(但需中间件) | ✗(单机) |
| 复杂度 | 中(需学 socket 模式) | 低 | 高(需部署 broker) | 高(手动同步) |

vLLM 的用法(以下均已在源码核对):

- **ROUTER ↔ DEALER** 模式:API 进程是 ROUTER(接收多客户端),EngineCore 进程是 DEALER(一个客户端)。请求从 API 进程的 ROUTER 发往 EngineCore 进程的 DEALER。
- **PUSH ↔ PULL** 模式:EngineCore 进程 PUSH 输出,API 进程 PULL。
- 序列化用 **msgpack** (由 msgspec 提供,比 JSON 快、比 pickle 安全);多模态张量不走 ZMQ 拷贝,而是走 `tensor_ipc` 的共享内存通道(`TensorIpcSender` / `TensorIpcReceiver`)。
- 所有 socket 都由 `vllm/utils/network_utils.py` 的 `make_zmq_socket()` 统一创建,`core.py` 与 `core_client.py` 各自调用它。

### 1.4 三种入口的职责划分

离线批量和在线服务对引擎的要求正相反:一个要吞吐、可以阻塞着等一批算完;一个要并发、一步都不能阻塞。**用同一个入口伺候两边,总有一边别扭**,所以 vLLM 对外给了三种。

对应三种入口类:

| 入口 | 同步 / 异步 | 进程模型 | 典型用法 |
|---|---|---|---|
| `LLMEngine` | 同步 | `InprocClient`(同进程)或 `SyncMPClient`(多进程) | 离线批量推理:`llm = LLM(...); llm.generate(prompts)` |
| `AsyncLLM` | 异步 | `AsyncMPClient`(多进程 + asyncio;DP 场景换成 DP 版的异步 client) | 在线服务:OpenAI 兼容 HTTP server |
| `EngineCore` | 内部类 | 不直接对外暴露 | 跑 scheduler + model_executor 主循环,被上面两种入口包装 |

层级关系:

![入口与 client 的层级:三种入口各经过哪个 client 到达 EngineCore,哪一层开始跨进程](/opensource/vllm/01b-entry-client-layers.svg)

[打开交互版](/opensource/vllm/01b-entry-client-layers.html)

**关键设计**:用户代码从不直接接触 `EngineCore`,而是通过 `EngineCoreClient` 抽象层。这让「同进程」和「多进程」两种模式可以无缝切换(调试时用 InprocClient,生产用 AsyncMPClient)。

## Part 2|图解:进程拓扑、单 step 时序与请求生命周期

### 2.1 进程拓扑总图

vLLM 在线服务(`AsyncLLM` + TP=2 为例)实际会拉起 **3 类进程** :1 个 API 进程、1 个 EngineCore 进程、N 个 GPU Worker 进程(N = TP × PP,严格说还要乘 prefill 侧的 CP)。三类进程各司其职,用不同的通信机制连接。

一个边界情况值得先知道:单卡时执行器默认是 uniproc,worker 就住在 EngineCore 进程里,整个服务只有 2 个进程;多卡时默认 multiproc,每张卡一个 worker 进程。

#### 2.1.1 进程与通信全景

![进程与通信全景:三类进程各持有什么,四种边分别走什么](/opensource/vllm/01d-process-topology.svg)

[打开交互版](/opensource/vllm/01d-process-topology.html)

#### 2.1.2 三类进程职责对照

| 进程 | 数量 | 负载类型 | 核心职责 | 通信 |
|---|---|---|---|---|
| **API 进程** | 1 | CPU(IO 密集) | HTTP 收发、套聊天模板、tokenize、detokenize、流式分发 | 对外 HTTP,对内 ZMQ |
| **EngineCore 进程** | 1 | CPU(调度密集) | 调度、KV cache 记账、发起前向与采样、把 batch 派给 Worker | 对 API 用 ZMQ,对 Worker 用共享内存消息队列 RPC |
| **GPU Worker 进程** | N = TP × PP | GPU(计算密集) | model forward、attention kernel、采样、持有 KV cache | Worker 间 NCCL(TP all-reduce / PP P2P) |

注意采样发生在 Worker:sampler 是 ModelRunner 的一部分,EngineCore 只是在 step 里发起 `sample_tokens` 这次调用。

#### 2.1.3 为什么这样分:三层重叠

三类进程的边界正好对应三种资源,让它们能 **流水线重叠** :

```text
时间线 ──────────────────────────────────────────────────►

API 进程:     [tokenize 请求 B] ──────────── [detokenize 请求 A 的上个 token]
                    │ CPU                          │ CPU
EngineCore:         └─► [schedule] ─────────────────────────────┐
                            │ CPU                               │
GPU Worker:                 └────► [model forward 请求 A] ──── GPU
                                            │
                                    这段时间 GPU 满载,
                                    API / EngineCore 的 CPU 活儿并行进行
```

**GIL 释放是关键** :ZMQ 的收发和 GPU 的 CUDA kernel 调用都会释放 Python GIL。所以:

- EngineCore 主线程在等 GPU forward 时(GIL 释放),input_thread 与 output_thread 能并行做 ZMQ 收发。
- API 进程的 tokenize 与 detokenize,跟 EngineCore 的调度、GPU 的计算完全并行。

**EngineCore 进程内的三线程模型** :

1. **input_thread** :阻塞在 ZMQ socket 上,收到请求后 msgpack 反序列化,推入 `input_queue`。
2. **主线程(busy loop)** :从 `input_queue` 取请求交给调度器,调 `step_fn()` 跑一个 step,把输出推入 `output_queue`。
3. **output_thread** :从 `output_queue` 取输出,msgpack 序列化,ZMQ 发回 API 进程。

### 2.2 单 step 时序图(连续批处理视角)

一个 step(约 5 到 50 ms)内的事件顺序:

```text
时间轴 ──────────────────────────────────────────────────────────►

EngineCore 主线程:
  ┌ schedule() ┐   ┌──── execute_model() ────┐   ┌ update ┐
  │ 选请求+分 KV │   │  GPU forward(释放 GIL)  │   │ 从输出  │
  │  约 0.5 ms  │   │      约 5 到 50 ms      │   │ 更新状态 │
  └────────────┘   └─────────────────────────┘   └────────┘
       CPU                    GPU                    CPU
                               │
  ─────────────────────────────┼──────────────────────────────
                               │ GIL 释放期间, input/output 线程并行:
                               │
input_thread:     收新请求 ─────┐
                               │ 推入 input_queue(主线程下个 step 处理)
output_thread:              ┌──┘
                            │ 从 output_queue 取上个 step 的输出
                            └─► ZMQ send → API 进程
                               │
API 进程 (asyncio):             └─► OutputProcessor.detokenize
                                     → 交给该请求的输出收集器
                                     → HTTP SSE stream yield
```

**核心收益** :CPU 工作(调度、序列化、detokenize)全部藏在 GPU 计算窗口里,GPU 利用率接近 100%。

### 2.3 端到端请求生命周期

一个请求从 HTTP 进来到流式输出完毕,跨 3 类进程、分 4 个阶段。 **关键区别** :阶段 A(接入)和阶段 B(prefill)对每个请求只发生一次;阶段 C(decode)是循环,生成几十到几千次;阶段 D(返回)在 B 和 C 的每一步都发生(流式)。

#### 2.3.1 四阶段总览

```text
阶段 A          阶段 B            阶段 C(循环)        阶段 D
接入            Prefill           Decode 每次 1 token  流式返回
 ────►           ────►             ────►               (贯穿 B、C)

HTTP+tokenize   算完整个 prompt    逐 token 自回归生成   每步 detokenize
(一次)          (一次或几次 step)  (几十到几千 step)    并推给客户端
   │               │                 │                   │
   ▼               ▼                 ▼                   ▼
约 1 到 10 ms   约 50 到 500 ms   约 5 到 50 ms/token   首 token = TTFT
                                                       后续 = TPOT
```

#### 2.3.2 详细流程(标注进程归属)

![一条请求的四个阶段:每一跳落在哪个进程、哪个线程](/opensource/vllm/01c-request-end-to-end.svg)

[打开交互版](/opensource/vllm/01c-request-end-to-end.html)

两个归属容易记反,值得单独点出来: **block hash 在 EngineCore 进程算,不在 API 进程** ,API 进程只负责把文字变成 token id;**采样在 GPU Worker 里跑** ,EngineCore 主线程只是发起那次调用。停止条件也是分开的:EOS 与长度上限在 EngineCore 判,stop string 要先把 token 变回文字,所以在 API 进程判。

#### 2.3.3 两个核心延迟指标怎么来的

```text
时间轴: 客户端视角
│
├ 发出请求(①)
│      ⋮  阶段 A + 阶段 B(tokenize + 整个 prompt 的 prefill)
│      ⋮  约 50 到 500 ms(取决于 prompt 长度)
├ 收到第 1 个 token(⑰ 首次)  ◄──── TTFT (Time To First Token)
│      ⋮  阶段 C 的一次循环(decode 1 个 token)
│      ⋮  约 5 到 50 ms
├ 收到第 2 个 token            ◄──── TPOT (Time Per Output Token)
│      ⋮  …重复…
├ 收到第 t 个 token
│
└ 收到 [DONE](total = TTFT + (输出长度 - 1) × TPOT)
```

- **TTFT** :阶段 A 加 B 的总耗时。主要成本在 prefill(步骤 ⑦⑧)。开 prefix caching 命中公共前缀可大幅降低。
- **TPOT** :阶段 C 单次循环耗时(步骤 ⑩→⑰)。主要成本在 decode 的 GPU forward(步骤 ⑪)。开推测解码可让单步产出多个 token,等效降低 TPOT。

#### 2.3.4 一句话串起来

接入(把文字变 token)→ prefill(一次性算完整个 prompt 的 KV,吐第 1 个 token)→ decode(拿着上一个 token 加全部历史 KV,反复算下一个 token)→ 每吐一个 token 就流式推回客户端,直到 EOS。整个过程 API 进程管 IO、EngineCore 进程管调度、GPU Worker 进程管算,三者靠 ZMQ 加 GIL 释放并行重叠。

## Part 3|机制之外:源码里额外读到的

Part 1 和 Part 2 讲清了「为什么拆成多进程、每一跳落在哪」,Part 4 讲「怎么选入口、怎么调」。这一部分只放**机制层面看不见、但真实存在的细节**:实现里的例外、前面没提的动作、为绕开某个具体麻烦加的小设计。前面讲过的一概不重复。

### 3.1 让 CPU 和 GPU 真正并行,靠的是四件事

**① 两条路的输入都在 `schedule()` 结束时就定死了。** 前向要的是 token id、位置、块表;算语法掩码要的是「哪些请求要结构化输出」加它们已生成的 token 序列。**谁也不是对方的输入**,所以能同时跑(见 2.4 的菱形图)。

**② 语法掩码不看 logits,也不看 KV cache。** 这是「无依赖」的根本原因,也是最容易想不通的一点:掩码是拿**已经生成的 token 序列**去推进一台有限状态机算出来的,纯字符串层面的事,GPU 上那堆东西它一个都不碰。

**③ 掩码和 logits 能叠加,是因为它们指向同一个位置。** 掩码说的是「按语法,下一个 token **可以**是哪些」,logits 说的是「按模型,下一个 token **多半**是哪个」——都在回答同一个「下一个」。有限状态机的特性正是「看过去就能约束下一个」,所以用过去的 token 序列算出来的掩码,恰好能用在这一步的 logits 上。

**④ 掩码缓冲区预分配一次、跨 step 复用**,不是每步新建;而**把非法位压成负无穷发生在 GPU Worker 上**,EngineCore 只负责把掩码随采样调用下发。

### 3.2 EngineCore 进程的四个讲究

**① 握手必须排在父类构造之前。** 子进程起来后的顺序是:建两个线程间队列 → ZMQ 地址握手 → 调父类构造 → 起收发两个线程。顺序不能换,因为**父类构造会创建执行器,也就是真的去拉起 GPU Worker**——地址还没谈定就拉起来,Worker 不知道该连谁。

**② 主循环既不空转也不失去响应。** 只有「没活儿干且引擎里也没有请求」时才阻塞等新请求;一旦手里有请求,就改成非阻塞地把队列排空,立刻回去算下一步。阻不阻塞由一个字段控制,不是写死的。

**③ 请求分发是四支不是三支。** 除了添加、中止、工具调用,第一支是**唤醒**,直接返回什么也不做。添加那一支还要多解一个数据并行的波次号出来。

**④ 单步处理多做两件事。** 除了跑一步、把输出推进队列,它还会调 `post_step` 回收草稿 token;并且在「这一步没真的算模型、但队列里还有请求」时**睡 1 毫秒主动让出 GIL**——不让的话这个忙等循环会把两个 IO 线程饿死。

### 3.3 两个 IO 线程的零拷贝技巧

**① 收线程起来后必须先发一条 ready 消息。** 这是 DEALER 到 ROUTER 这个模式的硬要求:ROUTER 按对端身份路由,对端不先开口,它根本不知道往哪发。

**② 收包不复制成 Python 对象**,直接用 buffer 视图;请求类型用单独一帧的一个字节标识,不必解析整个 msgpack 就能选对解码器。

**③ 发送用 buffer 复用池加 tracker,方向极易记反。** ZMQ 的发送是异步的,函数返回时数据可能还在内核缓冲区里——所以是**没发完才挂进待回收队列等下一轮,发完了才立即还池**。另外取的是第一帧的 tracker,因为复用的正是第一帧那块 buffer。

### 3.4 客户端分层

**① 四种组合里有一种是显式抛错的。** 多进程加 asyncio、只多进程、都不要,各对应一种客户端;而「只要 asyncio 不要多进程」**没有对应实现,工厂直接抛错**——不存在异步同进程这种东西。

**② 继承层级容易看成并列。** 数据并行加内部负载均衡那个类,继承的是数据并行那个类,不是和它平级的兄弟。

**③ 多进程基类有三个看漏点:** 底层 context 带 2 个 IO 线程,asyncio 模式只是在它外面再包一层、共享同一个;**子进程不是在这里创建的**,进程创建收敛在另一个工具文件里;资源守卫用 `weakref.finalize` 挂钩,保证 client 被回收时 socket 与子进程一起收掉。

另外地址来源是二选一的:**外部传了地址就说明引擎由外部托管**,这个 client 只连不拉。

### 3.5 两端的输入输出处理

**① 流式输出的通道不是队列。** 每个请求一个收集器,内部只存**一个**待取对象加一个 asyncio 事件。上一个还没被取走时,新的会**就地合并**进去——所以客户端消费慢不会让待发块堆积。

**② 后台输出处理是尝试性启动的。** 构造时先探一下当前有没有事件循环,有才立刻起;没有就推迟到第一次用的时候。

**③ 输入处理有两件事不在它这里做**,容易记混:chat template 由更外层的 renderer 套好;块哈希在 EngineCore 进程建请求对象时才算。

**④ 停止判定分在两个进程,所以有一条反向通路。** stop string 必须先把 token 变回文字才判得出来,只能在 API 侧判;判出来之后要**反向发一条中止消息**通知 EngineCore。而 EOS 和长度上限在 EngineCore 自己就判了,不走这条回路。

### 3.6 流水线并行时的另一种 step

并发批次数大于 1 时,引擎换一个 step 实现:**不阻塞等结果**——队列没满就排一批、提交前向、把 future 塞进队列;队列满了才阻塞等最老的那批。队列容量等于流水线级数时,气泡接近 0。

它还有个普通 step 没有的机制:**采样延迟**。请求带结构化输出、而语法还在等上一步的 token 时,这一步只提交前向,把调度输出挂起来,等结果回来写进 token 之后再补算掩码、再发采样。

## Part 4|对比与决策

### 4.1 与竞品的多进程架构对比

| 维度 | vLLM V1 | SGLang | TensorRT-LLM | HuggingFace TGI |
|---|---|---|---|---|
| 进程模型 | 2 进程(API + EngineCore) | 3 进程(API + Scheduler + Detokenizer) | 2 进程(Python + Triton) | 2 进程(Router + Python) |
| IPC | ZMQ + msgpack | ZMQ + msgpack | gRPC + 共享内存 | Rust channel + Python |
| 线程模型 | 3 线程(input / main / output) | 每进程单线程 | 单进程多线程 | Rust async + Python |
| GIL 隔离 | 完全(独立进程) | 完全 | 部分(Python 单进程) | Rust 部分隔离 |
| 零拷贝 tensor | 走 tensor_ipc 的共享内存通道 | 类似 | 共享内存 | 无 |
| 崩溃恢复 | EngineCore 崩溃 API 仍可响应 | 同 | 需重启 | 需重启 |

只有 vLLM 一列在本仓库核对过,其余三列是讲稿观点。另外 vLLM 那个「2 进程」不含 GPU Worker:多卡时每张卡还有一个 worker 进程,单卡走 uniproc 则 worker 就在 EngineCore 进程内。

**核心差异** (讲稿观点):

- vLLM 和 SGLang 都用 ZMQ 多进程,但 vLLM 把 detokenize 放在 API 进程(共享 OutputProcessor),SGLang 单独开 Detokenizer 进程,所以 vLLM 进程数更少、启动更快。
- TensorRT-LLM 用 gRPC,跨网络部署更友好(PD 分离场景),但单机内 ZMQ 的延迟更低。
- TGI 用 Rust 实现 Router,性能极好但开发门槛高。

### 4.2 何时用哪种入口

三种入口的差别,落到底层就是 EngineCoreClient 这层插座后面接的是哪一种 client:同一个进程直接调函数、两个进程同步等、还是两个进程加 asyncio 不等。按你在用 vLLM 干什么来选:

![EngineCoreClient 三种接法并排:InprocClient 一个进程里直接调函数,SyncMPClient 与 AsyncMPClient 把 EngineCore 放进子进程用 ZMQ 相连;每列下方写明适用场景,分别是调试单测、离线批量、对外 HTTP 服务](/opensource/vllm/01g-client-choice.svg)

| 场景 | 推荐入口 | 代码 |
|---|---|---|
| 离线批量推理(评测、数据生成) | `LLM` 加 `LLMEngine` | `llm = LLM("meta-llama/Llama-3-8B"); llm.generate(prompts)` |
| 在线 HTTP 服务(生产部署) | `AsyncLLM` | `vllm serve <model>`(内部用 AsyncLLM) |
| 嵌入到其他 Python 应用 | `LLM`(把多进程开关置 0 走 InprocClient) | 调试或单测场景 |
| 嵌入到异步框架(FastAPI 等) | `AsyncLLM` | `async for out in async_llm.generate(...)` |
| 多 GPU 推理 | 任一(并行配置在 `ParallelConfig`) | `LLM("...", tensor_parallel_size=8)` |
| PD 分离部署 | `AsyncLLM` 加 KV connector | prefill 与 decode 分节点部署,跨节点传 KV cache |


两个容易问到的点:**`LLM` 类默认就是多进程**(开关环境变量默认开),想走同进程只能显式关掉;而「只要 asyncio 不要多进程」这种组合**不存在**,工厂会直接抛错。

多进程的额外开销(讲稿量级参考):进程启动约 100 到 500 ms、ZMQ 握手约 10 ms、每条消息的序列化约 0.01 到 1 ms。对跑几小时到几天的推理服务来说,这些都可以忽略——换来的是 GIL 完全隔离和崩溃不互相拖累。

### 4.3 调试技巧

1. **看进程拓扑** :`ps -ef | grep vllm`,应该看到 API 进程加 EngineCore 进程,多卡时还有 N 个 GPU Worker 进程。
2. **看 ZMQ 流量** :用 `tcpdump` 或 `ss -t` 监控 ZMQ 端口(默认随机端口,可在日志里搜 zmq)。
3. **单进程调试** :设 `VLLM_ENABLE_V1_MULTIPROCESSING=0`(默认开)再直接用 `LLM(...)`。`LLMEngine` 把这个值传给 `make_client` 的多进程开关,开关为假时工厂落到最后一行返回 `InprocClient`,此时 EngineCore 在同进程内, **断点能直接命中** 。
4. **性能分析** :profiling 走配置项而不是环境变量,用 `--profiler-config` 设 profiler 类型(torch / cuda / proton)和输出目录。两者有强制配对校验:设了目录但 profiler 不是 torch 会报错,反之选了 torch 却没给目录也会报错。

### 4.4 常见误区

| 误区 | 真相 |
|---|---|
| 「AsyncLLM 比 LLMEngine 快」 | 不一定。异步只影响 IO 重叠,模型前向速度一样。单请求时异步略慢(asyncio 开销)。 |
| 「多进程更耗内存」 | 每进程多出一份 Python 解释器开销,但相对 KV cache(GB 级)可忽略。 |
| 「ZMQ 序列化是大瓶颈」 | msgpack 极快,张量走共享内存零拷贝。瓶颈永远是 GPU forward。 |
| 「InprocClient 没用」 | 单测、嵌入式集成、调试断点都需要它。生产才用 AsyncMPClient。 |

本表中的量级判断是讲稿观点。

### 4.5 关键配置参数

本篇涉及的参数:

| 参数 | 默认值 | 作用 | 本篇相关场景 |
|---|---|---|---|
| `--tensor-parallel-size` | 1 | TP 并行度 | Worker 数 |
| `--pipeline-parallel-size` | 1 | PP 并行度(启用 batch_queue) | `step_with_batch_queue` |
| `--data-parallel-size` | 1 | DP 并行度 | 选择 DP 版的 EngineCoreProc 与 client |
| `--max-num-seqs` | 128 | 最大并发请求数 | scheduler 容量 |
| `--max-num-batched-tokens` | 2048 | 每 step 最大 token 数 | scheduler 容量 |
| `--profiler-config` | profiler 为空 | 选 profiler 类型与输出目录 | 性能分析 |
| `VLLM_ENABLE_V1_MULTIPROCESSING` | 开 | 置 0 则 `LLMEngine` 走 `InprocClient`(单进程) | 入口与客户端选择 |

注意两点: `--max-num-seqs` 与 `--max-num-batched-tokens` 的字段默认值只是 **起点** ,启动时会按显存分档上调(大显存的 server 场景会显著高于 128 与 2048),所以实际生效值要看启动日志而不是这张表。另外没有 `--use-v2` 这个命令行开关(要切 V2 model runner 走的是环境变量),也没有 `--disable-async-output-processing`,异步输出处理不是可开关的选项。
