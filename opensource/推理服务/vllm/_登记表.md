## 二、一句话核心

vLLM 把「显存管理 + 动态调度 + 注意力 kernel + 分布式执行 + 采样」五件事做成一套推理服务栈。93 万行 Python 里,模型实现(`model_executor/` 加 `models/`)占近一半;真正的引擎骨架是 `v1/` 的 16 万行,其中注意力后端 5.4 万、worker 4 万、调度与 KV 记账 1.3 万、引擎进程 1.1 万。理解 vLLM 的顺序是:先看它沿哪些维度优化(总览第 2 节),再看每个特性解决什么问题、代码在哪(第 3 节),最后才进具体调用链。

## 四、已确认的事实(后续页面直接引用)

1. 只有一套实现:引擎、调度、worker、注意力后端全在 `vllm/v1/`;`vllm/engine/llm_engine.py` 与 `async_llm_engine.py` 各只是一行别名(S1-9、S1-5)。
2. CLI 参数不在 v1 下:`EngineArgs` 在 `vllm/engine/arg_utils.py:427`,前端参数 `FrontendArgs` 在 `vllm/entrypoints/launchers/cli_args.py:250`(S1-11、S4-8)。
3. 调度默认值:一轮 2048 个 token、128 条请求(`vllm/config/scheduler.py:42-44`);策略 fcfs 或 priority(S3.1-4、S3.1-5)。
4. 块大小是回落值不是字段默认值:`block_size` 字段默认 `None`,`_apply_block_size_default` 回落 16,平台层还会覆盖(S3.2-5、S3.2-6)。
5. 显存占比默认 0.92;前缀缓存默认开、哈希默认 sha256,可选 sha256_cbor、xxhash、xxhash_cbor(S3.2-7、S3.4-5)。
6. 块哈希是链式的:父块哈希 + 本块 token ids + 额外键(LoRA、多模态等),不含块序号(S3.4-4)。
7. 没有 swap_space:KV 下沉走 `vllm/v1/kv_offload/` 与 offloading connector(S3.2-8、S3.2-9)。
8. CUDA 上没有经典的自研 paged attention kernel,块表由 FlashAttention、FlashInfer、Triton 后端消费;例外是 `csrc/libtorch_stable/attention/mla/` 的 SM100 MLA kernel 与 ROCm 的 `csrc/rocm/attention.cu`(S3.2-4)。
9. 量化方法 30 个,由一个 Literal 唯一定义;bitsandbytes 不在其中;`LinearMethodBase` 在 `linear.py` 不在 `base_config.py`(S3.8)。
10. 结构化输出 backend 是引擎级单例,`auto` 的试探链在 `SamplingParams._validate_structured_outputs`:先 xgrammar,失败退 guidance,非 tekken Mistral 或 guidance 不支持的 schema 退 outlines(S3.9-3、S3.9-5)。
11. 两个 model runner 并存:生产路径 `vllm/v1/worker/gpu_model_runner.py`(7629 行);`vllm/v1/worker/gpu/` 是实验中的 V2(2229 行)。多模态合并、LoRA、KV connector 在两条路径各有接入文件(S4-3、S3.10-4、S3.12-2、S3.13-5)。
12. 模型实现分两处:老位置 `vllm/model_executor/models/`(282 个文件),新位置 `vllm/models/<模型族>/`(267 个文件),注册表 `_VLLM_MODELS` 合并后 382 个唯一架构名(S4-4、S4-5)。
13. 引擎进程:`EngineCoreProc` 用两个线程分别收发 ZMQ 输入输出,主线程跑 `run_busy_loop`;序列化用 msgspec 的 msgpack;DP 模式用 `DPEngineCoreProc`(S3.11)。
14. 批不变性:SM80 用 Triton 覆盖四个 aten 矩阵算子,SM90/100 只改 cuBLAS workspace;FlashAttention 后端强制 `num_splits=1`;开关按整数解析(S3.15)。
15. 一次 step 的骨架:schedule → execute_model(non_block=True) 拿 future → get_grammar_bitmask(与 GPU 重叠)→ future.result() → sample_tokens(grammar_output) → update_from_output;采样是 executor 的独立调用,不是前向的尾巴(S5-2、S5-4)。
16. ZMQ 拓扑:输入侧 EngineCore 是 DEALER、客户端是 ROUTER;输出侧 EngineCore 是 PUSH、客户端是 PULL。EngineCore 内两个 `queue.Queue` 配两个线程,主线程跑 `run_busy_loop`(S5-5、S5-6)。
17. 聊天模板由 `vllm/renderers/` 在 API 进程里先套好,InputProcessor 再经 renderer 做 tokenize 并构造 `EngineCoreRequest`;输出侧 `RequestOutputCollector` 用 asyncio 事件把结果交给 generate 协程,SSE 由 chat_completion 路由发出(S5-7、S5-10)。

21. 进程数:worker 数 = PP × TP × PCP;单卡默认 uniproc,worker 住在 EngineCore 进程里(C1-11、C1-12)。
22. 所有 ZMQ socket 由 `vllm/utils/network_utils.py` 的 `make_zmq_socket` 创建;张量走 `tensor_ipc` 的共享内存通道,仓库里没有 TensorZmq(C1-4、C1-5)。
23. EngineCore 直接持有 Scheduler、StructuredOutputManager、ModelExecutor;KVCacheManager 挂在 Scheduler 下;executor 到 worker 的 RPC 走共享内存消息队列;采样 kernel 在 worker 的 ModelRunner 上跑(C1-15 至 C1-18)。
24. `EngineCore.__init__` 七步:加载插件 → 建 ModelExecutor(worker 在此 fork/spawn)→ `_initialize_kv_caches` 探显存定 block 数 → 建 StructuredOutputManager → 按 `get_scheduler_cls()` 建 Scheduler(可用 `--scheduler-cls` 换)→ 按 `max_concurrent_batches` 决定要不要建 batch_queue → 绑定 `step_fn`(C2-12、C2-13)。
25. `max_concurrent_batches` 有两个来源:PP 大小,以及异步调度(V2 runner 为 pp+1,否则 pp ≤ 1 时为 2);batch_queue 不只为藏 PP 气泡(C2-14)。
26. `step()` 里 `execute_model` 返回 `None` 表示只算到 logits,采样推迟到 `sample_tokens(grammar_output)`;这条路径才需要 bitmask,也是 CPU 与 GPU 重叠的前提。`get_grammar_bitmask` 在本 step 无结构化请求时直接返回 `None`,普通请求没有可重叠的 CPU 活儿(C2-16、C2-18、C2-19)。
27. busy loop 的一轮是 `_process_input_queue` → `_process_engine_step`(内部调 `step_fn()`、把输出推 `output_queue`、再调 `post_step`);`post_step` 只在异步调度**关闭**且本 step 真的执行过模型时回收 draft token(C2-2、C2-17)。
28. block hash 在 EngineCore 进程建 `Request` 时算,不在 API 进程;API 进程只做套模板、tokenize、多模态预处理(C2-3、C2-4)。
29. grammar bitmask 缓冲区预分配一次并跨 step 复用,行数按「最大并发请求数 × (1 + 最大 spec token 数)」;`GrammarOutput` 里装 id 列表与 numpy int32 的 bitmask;把非法位压成负无穷这一步在 worker 侧的 `apply_grammar_bitmask`,不在 EngineCore(C3-4、C3-8)。
30. `step_with_batch_queue` 比 `step()` 多一个采样延迟机制:请求带结构化输出且 grammar 还在等上一步 token 时,本 step 只提交前向,把 `scheduler_output` 挂在 `deferred_scheduler_output` 上,等 `update_from_output` 写回 token 后再补算 bitmask 并 `sample_tokens`;带 draft token 时先 `take_draft_token_ids` 过滤无效 spec token(C3-9、C3-11)。
31. `EngineCoreProc.__init__` 顺序:先建两个 `queue.Queue` → ZMQ 地址握手 → `super().__init__()`(此时才拉起 GPU Worker)→ 起 input/output 两个线程。地址必须在建 executor 之前谈定(C3-13)。
32. input_thread 起来后要先向 ROUTER 发一条 ready 消息,DEALER 不先开口 ROUTER 就无法回消息;收包用 `recv_multipart(copy=False)` 零拷贝,类型用单独一帧的一个字节标识,按类型选不同解码器(C3-18、C3-19)。
33. output_thread 用 buffer 复用池加 tracker:`encode_into` 写进复用 buffer,发送后若 tracker 未完成就挂进 pending 等下轮回收,完成了才立即还池;取的是第一帧的 tracker,因为复用的正是第一帧那块 buffer(C3-20、C3-21)。
34. `_handle_client_request` 四分支:WAKEUP、ADD(解包请求与 DP wave)、ABORT、UTILITY;`_process_engine_step` 除 `step_fn()` 与 `output_queue.put_nowait` 外还调 `post_step`,并在「没执行模型但仍有请求」时睡 1 毫秒让出 GIL(C3-16、C3-17)。
35. `make_async_mp_client` 按 DP 配置三选一:DP=1 给 AsyncMPClient,DP 加外部负载均衡给 DPAsyncMPClient,DP 加内部负载均衡给 DPLBAsyncMPClient;后者继承前者(C3-23、C3-24)。
36. `InprocClient.get_output()` 就是同步调 `step_fn()` 再 `post_step`;`MPClient` 底层是带 2 个 IO 线程的同步 ZMQ context,asyncio 模式再包一层共享它;子进程由 `vllm/v1/engine/utils.py` 的 `launch_core_engines` 起,`EngineCoreProc.run_engine_core` 是子进程入口;`BackgroundResources` 加 `weakref.finalize` 保证 client 被回收时 socket 与子进程一起收掉(C4-1 至 C4-3)。
37. `AsyncLLM` 的输出通道是 `RequestOutputCollector` 而非 `asyncio.Queue`:内部只存一个待取对象加一个 asyncio 事件,`put` 时若上一个还没被取走会**就地合并**,所以客户端消费慢不会堆积待发块。后台 `output_handler` task 是**尝试性启动**的,不在事件循环里时会推迟到首次使用(C4-5、C4-6)。
38. `LLMEngine.step()` 里有一条回路:stop string 在 API 侧判出,所以要反向 `abort_requests` 通知 EngineCore;EOS 与长度上限由调度器的 `check_stop` 自己判(EOS 与 stop_token_ids 记 FINISHED_STOPPED,超 max_model_len 或 max_tokens 记 FINISHED_LENGTH_CAPPED),不走这条回路(C4-7、C4-10)。
39. 离线批量的驱动循环在 `vllm/entrypoints/offline_utils.py` 的 `_run_engine`,不在 `vllm/llm.py`;`LLM.generate` 末尾调它(C4-8)。
40. 两个 batch 参数的字段默认值只是起点,`get_batch_defaults()` 会按显存分档上调,实际生效值看启动日志;没有 `--use-v2` 命令行开关(走环境变量 `VLLM_USE_V2_MODEL_RUNNER`),也没有 `--disable-async-output-processing`;profiler 走 `--profiler-config`,profiler 类型与输出目录有强制配对校验(C4-16、C4-18、C4-19)。
41. 调度的统一 token 模型:每个请求只有 `num_computed_tokens`(已算过、KV 就绪)与 `num_tokens_with_spec`(= `_all_token_ids` 即 prompt 加已生成 output,再加 `spec_token_ids`)两个计数器,调度就是让前者追上后者。本 step 要算的量是两者之差 **加上 `num_output_placeholders`**(仅异步调度非零),再被 `long_prefill_token_threshold`、token budget、`input_budget - draft_slots`、max_model_len 逐层压小(D1-8 至 D1-10)。
42. 两条预算线:`token_budget` 初值取 `max_num_scheduled_tokens`(未显式设时回落成 `max_num_batched_tokens`),`input_budget` 始终取 `max_num_batched_tokens`;RUNNING 循环先扣,WAITING 循环取剩,两处都是 `token_budget -= num_new_tokens`(D2-1、D2-2、D2-7)。
43. 三道闸门都在 WAITING 循环里,且卡住时全是 `break` 不是 `continue`:并发数上限(running 数还要加上暂停的流式会话)、`allocate_slots` 拿不到 block、`token_budget > 0`。实际并发是三者的最小值(D2-10 至 D2-12)。
44. 抢占只由 RUNNING 循环里的请求触发(它要写新 token 却拿不到 block),牺牲的是别的 running 请求;WAITING 拿不到 block 只 break、不抢占。FCFS 抢 running 队尾,Priority 抢优先级最低、同级最晚到达的;抢到自己就 break,本轮不调度(D2-14 至 D2-17)。
45. KV 容量链路:`requested_memory` = 总显存 × `gpu_memory_utilization`(free 不够直接抛 ValueError)→ profile run 用 dummy forward 量出非 KV 显存 → 相减得 `available_kv_cache_memory_bytes` → `get_kv_cache_configs` 换成 block 数 → BlockPool。`page_size_bytes` 是按 KV 类型分别定义的属性(基类抛 NotImplementedError),不是一条全局整式(D3-2 至 D3-7)。
46. `watermark` 默认 0,即**默认关闭**,不会让可用 block 打折(D3-8)。
47. 抢占只有 recompute:`vllm/v1/` 下无任何 swap 符号。`_preempt_request` 释放 block、状态置 `PREEMPTED`(不是 WAITING)、`num_computed_tokens` 归零、清空 `spec_token_ids`、抢占次数加一,最后 `prepend_request` 插到 waiting **队首** (D3-12、D3-13、D3-17)。
48. 两种队列:FCFS 是 `deque` 子类,Priority 是 `heapq`;排序键由 `Request.__lt__` 定义,四级依次为 priority、arrival_time、request_id、对象地址,数值小等于高优先。入队取最小、抢占取最大,同一把尺子两个方向(D3-18 至 D3-20)。
