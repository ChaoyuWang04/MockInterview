# vLLM 09|分布式并行

一个 70B 的模型,权重就有 141 GB,任何一张卡都装不下。这一章讲清 vLLM 沿哪几个维度把模型拆开、每一次拆开要还多少通信的债,以及这笔债在 prefill 和 decode 两种场景下为什么是两个完全不同的量级。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 一张卡装不下,于是每一维都被切过一遍

分布式并行不是一个特性,是**六个不同痛点**各自逼出来的六种切法。它们唯一的共同点是:**切开之后,被切散的中间结果得想办法拼回来** ——那就是通信的代价。

| 痛点 | 提出了什么 | 切的是哪一维 | 要还的通信 | 展开在 |
|---|---|---|---|---|
| 单卡放不下权重,而且单卡算得慢 | 张量并行 TP | 权重矩阵(按输出维或输入维) | all-reduce | 1.5–1.17 |
| TP 已经用满整机,模型还是放不下 | 流水线并行 PP | 层(按层分段) | 点对点 send/recv | 1.18–1.27 |
| MoE 的专家太多,「切单个专家」这条路失效 | 专家并行 EP | 专家(整个专家分到卡上) | all-to-all | 1.28–1.55 |
| 激活值随序列长度涨,TP 切不动它 | 序列并行 SP | 序列维(搭在 TP 上) | reduce-scatter / all-gather | 1.56–1.70、1.83–1.85 |
| 超长上下文的首 token 太慢,KV cache 还每卡一份 | 上下文并行 CP | 序列与 KV cache | all-gather / reduce-scatter | 1.71–1.82 |
| 单个实例已经打满,还要更多吞吐 | 数据并行 DP | 请求(多副本各跑各的) | 几乎不通信 | 1.86–1.90 |

这张表也是本章的骨架 —— 最后一列给出每条痛点线在哪几节展开。本节之后先回答「这六种里哪几种真的在占 GPU」,然后从 1.5 起沿着 TP 这条线走完一遍完整的「切开—还债—还得更便宜」,后面五种并行都是在这条线上换一个维度重做一次。

**全章的耗时、带宽与显存数字都是量级参考,不是本仓库实测**;凡引自外部材料的另行标注。

![六种并行各切哪一维:TP 沿 hidden 维竖切、SP 与 CP 沿 seq 维横切,两条切线在同一个激活张量上互相垂直,因为它们切的本来就是两个不同的轴;EP 切的是专家集合而不是张量的某一维;PP 的切口落在层与层之间;DP 把整张图整体复制若干份。切线的方向标记被切的轴,切口所在的框层级标记作用的尺度。](/opensource/vllm/09a-cut-axes.svg)

这张图把上表的第三列画了出来。**两种编码同时在承载信息**:切线的**方向**标记它切的是哪一根轴 —— TP 沿 hidden 维竖切、SP 与 CP 沿 seq 维横切,两条线在同一个张量上互相垂直;切口所在的**框层级**标记它作用在什么尺度 —— EP 切的是一个集合而不是张量的某一维,PP 的切口在层与层之间,DP 的切口干脆在整个模型之外。

### 1.2 推理的并行只有前向,这改变了所有代价

训练里讲并行,讲的是梯度怎么同步、优化器状态放在哪、激活要不要重算。**推理一件都没有** ——没有反向传播,没有梯度,没有优化器状态。并行层的实现里连一个自动求导的包装都不存在,从头到尾就是前向。

这不是省了点事而已,它把通信的性质换掉了:训练里的集合通信大多是**为了让各卡的参数保持一致** ,推理里的集合通信只有一个用途,**把被切开的那一层中间结果拼回完整** 。所以它的位置是确定的(每一处切分的下游),尺寸是确定的(等于那一层激活的大小),而且**跟模型多大没关系,只跟这一步算多少 token 有关** 。1.13 和 1.15 的两个量级差就全是从这一条推出来的。

### 1.3 六种并行里,只有三种真的在乘 GPU 数

「六种并行」听起来像六个可以各自调大的旋钮,实际不是。一个引擎实例的进程数是这样来的:

$$
\text{world\_size} = \text{PP} \times \text{TP} \times \text{PCP}
$$

只有这三项在乘积里。剩下三种各有各的原因:

| 并行 | 在不在乘积里 | 为什么 |
|---|---|---|
| PP、TP、PCP | 在 | 它们各自要求一批独立的 GPU |
| DP | **不在** | 每个副本默认是一个独立的引擎进程,各有各的 `world_size` |
| SP、DCP | **不在** | 它们复用 TP 的那组 rank,不额外占卡 |
| EP | **不在** | 它根本不是一个独立维度,见 1.4 |

DP 那一行最容易读错。总 GPU 数确实是 `DP × (PP × TP × PCP)`,但**这个乘积不是任何单个引擎的 `world_size`** ——它是几个互不相干的引擎加起来的规模。只有一种例外:执行后端设成外部启动器时,所有 rank 由外面统一拉起,这时 DP 才被乘进 `world_size`。

**外部启动器**(external launcher)指的是由 `torchrun` 这类工具在外部把全部进程一次拉齐、vLLM 自己不再负责起进程的模式。

### 1.4 EP 不是一个新维度,它是被压平的 TP

专家并行的规模不是一个独立参数,它等于:

$$
\text{ep\_size} = \text{TP} \times \text{DP} \times \text{PCP}
$$

这是本章最容易踩的一处。直觉上 EP 应该等于 TP —— 一个 MoE 层就在这 TP 张卡上,专家分到这几张卡上就完了。实际不是:代码里有一个「压平」动作,把 DP 和 PCP 两个维度**合并进 TP** 再去分专家,注释把理由写得很直白:实际上有 `dp_size × pcp_size × tp_size` 个设备,所以要更新 TP 的规模与序号,好让分片铺满全部设备。

换句话说,**同一批 GPU 在两个层里的身份是不同的** :

| 从哪一层看 | DP 副本之间是什么关系 |
|---|---|
| 注意力层 | 互不相干,各算各的请求 |
| MoE 层 | 同一个专家池的不同分片,专家要在全部设备上摊开 |

开启专家并行之后还有第二个动作:**MoE 层内部的 TP 被置为 1** 。也就是说专家是整个整个地分卡的,不再对单个专家的权重做张量切分。源码注释说得很干脆:在 EP 下,每个设备完整拥有一组专家,没有张量并行这回事。

这里有个讲稿之外的事实值得单独记一笔:**压平动作与 EP 无关,它是无条件执行的** ——在判断要不要走 EP 之前就做完了。所以哪怕专家并行是关着的,MoE 层看到的 TP 规模也已经是压平后的那个数。类文档里给的例子写得很清楚:TP=2、DP=2、EP 关闭时,0 号设备上的 TP 是 `{规模 4, 序号 0}` 而不是 `{规模 2, 序号 0}`。

专家并行由 `--enable-expert-parallel` 打开,还有一个容易忽略的前提:**总设备数必须大于 1** 。单设备上把这个开关打开也不会进 EP 分支。

### 1.5 TP 切的到底是哪几个矩阵

从这一节起是 TP 这条线。先看清痛点有多具体 —— 以 Llama-3-70B 为例(hidden 8192、64 个查询头、8 个 KV 头、头维 128、中间维 28672),一个 Transformer 层里有四个大权重:

| 权重 | 形状 | bf16 显存 | 切法 |
|---|---|---|---|
| QKV 投影 | `[10240, 8192]` | 168 MB | 列切(q/k/v 各自按头切) |
| 输出投影 | `[8192, 8192]` | 134 MB | 行切(沿输入维 8192 切) |
| gate+up 投影 | `[57344, 8192]` | 940 MB | 列切(两段各自按列切) |
| down 投影 | `[8192, 28672]` | 470 MB | 行切 |
| 单层合计 | | **约 1.71 GB** | |

80 层就是约 137 GB,再加上词嵌入与输出头(各 `[128256, 8192]`,合计约 4.2 GB),总共约 141 GB。**任何一张现役单卡都装不下,这就是 TP 存在的全部理由。**

顺带解释一个后面会用到的比例:**FFN 占了单层的 82%** 。注意力的参数量是 $O(h^2)$,FFN 是 $O(h \cdot i)$,而这个模型的中间维是 hidden 的 3.5 倍、还摊在三个矩阵上,所以 $i/h$ 越大 FFN 越占主导。这决定了 1.12 里 FFN 那次 all-reduce 更值得优化。

### 1.6 两个形状很容易记错

上表里有两个数字和「课本版 Transformer」对不上,都能在源码里直接找到答案。

**QKV 不是 `[3h, h]`** 。这个模型用分组查询注意力,只有 8 个 KV 头,所以 K 和 V 各只占 $8 \times 128 = 1024$ 而不是 8192,三段加起来是 10240 不是 24576。融合后的 QKV 层是按 `[q, k, v]` 三段分别记录宽度的,只有在多头注意力(KV 头数等于查询头数)时才退化成 `[3h, h]`。

**SwiGLU 的 FFN 有三个矩阵而不是两个** 。门控分支和上投影分支是两个独立的权重,vLLM 把它们融合成一个列切层,宽度写成「中间维乘以 2」。融合的目的是把两次矩阵乘合成一次,少一轮 kernel 启动和一次激活值的读写。所以列切那一侧的权重是 $2i$ 宽,不是 $i$ 宽。

### 1.7 列切:沿输出维切,切完不拼

列切(column parallel)把权重沿**输出维**切开。每张卡拿到输出维的一段,输入是完整复制的,各卡独立算出自己那段输出。

把这些分片拼起来就是完整结果,但 QKV 这一层**写死了不拼** ——直接把分片传给下一层的注意力计算,省掉一次 all-gather。这一步能省掉,靠的是分组查询注意力的分组关系在切分后依然成立:每卡拿到的若干个查询头,和它们共享的那个 KV 头**落在同一张卡上** ,所以注意力可以完全本地算完。

切分的粒度是**按头**,不是把总宽度对半砍。q、k、v 三段各自按头切完再拼成本卡的分片,源码里专门有一对方法按段记录偏移与宽度,权重加载时才能把 HuggingFace 里分开存的三个矩阵各自切好、塞进同一个融合张量的对应区间。

这两种算法在常见配置下结果相同,但有一档它们会分叉,而那一档恰恰重要:**当 TP 大于等于 KV 头数时,KV 头不再被切分,而是被复制** 。此时每卡持有 1 个 KV 头,复制份数等于「TP 除以 KV 头数」。后果是融合张量被撑得比真实权重更宽,每卡分片也比「总宽除以 TP」更大 —— Llama-3-70B 在 TP=16 下每卡是 $512 + 128 + 128 = 768$,而不是 $10240 / 16 = 640$。

### 1.8 行切:沿输入维切,算完求和

行切(row parallel)反过来,把权重沿**输入维**切开。它的输入正好是上一层列切吐出来的分片,所以不需要额外的数据搬运;每卡算出的是一个**部分和** ——形状已经是完整的输出形状,但数值只算了一部分。

要拿到正确结果,必须把各卡的部分和加起来,这就是 all-reduce。**这是 TP 里唯一真正要通信的地方。**

### 1.9 为什么顺序必须是先列后行

列切和行切不是两种可选方案,是一对必须按这个顺序出现的搭档。把 FFN 这一段的数据流摊开看:

```text
X [B, seq, h]                                    各卡持有完整输入
  |
  v
gate_up (column parallel, gather_output=False)
  |  per card: [B, seq, 2i/N]
  |  split -> gate_i, up_i     each [B, seq, i/N]
  |
  v
SiLU gating   H_i = silu(gate_i) * up_i          逐元素,各卡独立,不通信
  |
  v
down (row parallel, input_is_parallel=True)
  |  per card: Y_i = H_i @ W_down_i^T   [B, seq, h]   这是部分和
  |
  v
all-reduce    Y = sum_i Y_i                      整层唯一的一次通信
```

中间那个激活函数是整件事的关键。列切让每张卡持有的是「**不同输出维度上的完整数据** 」—— $H_i$ 是 $H$ 沿输出维的一个切片,每个元素的值都是最终值。激活函数是逐元素操作,每个元素只依赖它自己,所以各卡独立做就行。

如果换成行切,每张卡持有的是「**所有维度上的不完整数据** 」,这时就不能独立做激活了,因为非线性函数不满足分配律:

$$
\mathrm{act}(H_1 + H_2) \ne \mathrm{act}(H_1) + \mathrm{act}(H_2)
$$

拿 SiLU 代一组数就很直观:$\mathrm{silu}(-1+3) = \mathrm{silu}(2) = 1.73$,而 $\mathrm{silu}(-1) + \mathrm{silu}(3) = -0.27 + 2.86 = 2.59$。

一句话:**列切让元素级激活可以各卡独立做,行切必须先求和才能做激活。** 先列后行,才能在两层之间插进一个激活函数而不通信。

### 1.10 门控还多一个条件:gate 和 up 要切得一模一样

SwiGLU 的门控是把 gate 的第 $j$ 个元素乘上 up 的第 $j$ 个元素,两个操作数必须来自**同一个中间维下标** 。所以第 $r$ 张卡拿到 gate 的哪几列,就必须拿到 up 的同样那几列,否则乘错位。

这解释了融合列切层的两个实现选择:

- 它**不能把拼接后的 $2i$ 直接对半砍** ,必须两段各自分别切。类文档里就写着这一句 —— 加载权重时,不同的分区是分开切分的。
- 它要求**每一段都能被 TP 整除** ,而不是只要求总和能被整除。代码里是对每个分段各查一遍整除,不是对总宽查一遍。

第二条是第一条的直接后果:既然要分段切,每一段就得自己切得动。

### 1.11 注意力走的是同一个模式

注意力这一半和 FFN 完全同构:QKV 用列切,注意力计算在各卡本地做,输出投影用行切,合计**一次 all-reduce** 。

它能本地算完的理由和 FFN 略有不同,但同样干净:列切 QKV 天然是按头分的,每卡拿到自己那几个头;查询只和自己头内的键值做注意力,不需要跨头的数据。**注意力从来不跨头,所以按头切就等于按卡切。**

### 1.12 一层两次,八十层一百六十次

把两半合起来,一层 Transformer 的前向通信就清楚了:

| 子模块 | 列切 → 行切的配对 | all-reduce 次数 |
|---|---|---|
| 注意力 | QKV 投影列切 + 输出投影行切 | 1 次 |
| FFN | gate+up 投影列切 + down 投影行切 | 1 次 |
| 单层合计 | | **2 次** |

80 层模型就是 **160 次 all-reduce** ,全部在前向。三个关键开关控制着这条链路:

| 开关 | 值 | 作用 |
|---|---|---|
| `gather_output` | 列切层为假 | 不做 all-gather,直接把分片传给下一层 |
| `input_is_parallel` | 行切层为真 | 输入已经是分片,不再切一次 |
| `reduce_results` | 行切层为真 | 算完部分和之后做 all-reduce |

这 160 次 all-reduce 是能被 CUDA Graph 录进去的 —— 它的形状只取决于本步的 token 总数,详见 06 章 1.20。

### 1.13 decode 的通信量很小,但小的原因不是带宽

每次 all-reduce 搬的是 `[批大小, 序列长度, hidden]` 这么大一块激活值。**它跟模型有多少参数完全无关** ,只跟这一步算多少 token 有关 —— 这正是 1.2 那条性质的直接后果。

以 decode 为例(批 32、每条 1 个 token、hidden 8192、bf16),一次就是 512 KB。按 NVLink 约 600 GB/s 的带宽算:

$$
T^{\text{带宽项}} \approx \frac{2 \times 512\,\text{KB}}{600\,\text{GB/s}} \approx 1.7\ \mu s
$$

系数 2 来自环形 all-reduce:它跑 reduce-scatter 和 all-gather 两轮,每张卡实际收发 $\frac{2(N-1)}{N}S$ 字节,8 卡时是 $1.75S$,取 2 是个略偏保守的上界。

**但这 1.7 µs 只是带宽项,不是真实耗时。** 512 KB 远在 NVLink 的带宽饱和点以下,实测耗时由固定开销主导 —— kernel 启动、rank 间同步、通信库的算法切换阈值,量级在 5 到 15 µs。所以更现实的估计是 160 次乘以约 10 µs,约 1.6 ms,而不是纯带宽推算出的 0.27 ms。

即便按 1.6 ms 算,相对于 decode 一步 20 到 50 ms 的前向仍然只占 3% 到 8%。结论方向不变 —— **decode 阶段的 TP 通信开销小** ——但「不到 1%」是纯带宽推算的产物,不能当实测值用。本节所有耗时都是量级参考,不是本仓库实测。

### 1.14 于是 vLLM 自己写了一个 all-reduce

上一节那个「固定开销主导」的结论,正是 vLLM 绕开通用通信库、自己写一个 all-reduce kernel 的动机:小 message 上真正贵的不是搬数据,是多轮同步的固定成本。自写的那条路径**一次 kernel 直接读写对端显存** ,把同步轮次压到最少。

它只接管小 message,默认上限是 8 MB。准入条件一共**五条** ,逐条是:

| 条件 | 说明 |
|---|---|
| 未被禁用,且 world_size 不超过 8 | 超出范围直接退回通用库 |
| 数据类型在白名单里 | 只放行 fp32、fp16、bf16 |
| 字节数是 16 的倍数 | kernel 的对齐要求 |
| 张量是弱连续的 | 允许有 stride,但内存必须连成一片 |
| 尺寸小于上限 | **只有在 world_size 等于 2、或者卡间全连接时才检查这一条** ,否则直接不接管 |

最后一条的分支值得看清:**两卡时无条件放行,不要求 NVLink 全连接** ;只有 4 卡及以上才要求全连接。源码注释给了理由 —— 4 张以上不具备 NVLink 的卡,自写 all-reduce 相对通用库几乎没有提升。

数据类型那一条是容易漏掉的一条:**FP8 的 all-reduce 走不了这条自写 kernel** ,量化部署时这条优化是失效的。

还有一层容易被忽略:**8 MB 是默认值,不是最终值** 。构造时还要和一张「设备架构 × 卡数」的阈值表取最小,所以某些架构与卡数的组合下,实际阈值比 8 MB 更低。

### 1.15 prefill 反过来,大到要还给通用库

同样的公式换到 prefill(序列长度 4096),通信量涨了 4096 倍,一次 all-reduce 的 message 是 2 GiB。这时带宽项才真正主导:

$$
T^{\text{prefill}}_{\text{all-reduce}} \approx \frac{2 \times 32 \times 4096 \times 8192 \times 2}{600\,\text{GB/s}} \approx 7\ \text{ms}
$$

160 次就是约 1.1 s。这个数要和同一批的计算量并排看才有意义:$32 \times 4096 = 131072$ 个 token 走一遍 70B 模型约 18.4 PFLOPs,8 张卡按每卡 400 TFLOPS 的有效算力算约 5.7 s。所以**通信占比约 16%** ,显著但不致命。

两件事顺势就清楚了:

- 2 GiB 远超 8 MB 的上限,所以 prefill 的 all-reduce **会退回通用通信库** 。这不是降级 —— 带宽项主导时,算法优化比降低固定开销更要紧,通用库在这个尺寸上本来就更强。
- 实际部署里分块预填充会把这个大批次拆开,单次 all-reduce 的尺寸随之下降,上面这个 16% 是不切块时的上界。

所以 TP 的通信代价不是一个数,是**两个方向相反的机制** :decode 端受固定开销支配,靠自写 kernel 压;prefill 端受带宽支配,靠切块压。

### 1.16 一个只有行切才有的坑:偏置只能加一次

行切还有一个列切完全没有的麻烦:**偏置不能每卡都加。**

原因和 1.9 是同一个根子。行切之后要 all-reduce 求和,如果每张卡都在自己的部分和上加一遍偏置,求和之后偏置就变成了 $N$ 倍:

$$
\sum_i (X_i W_i^\top + b) = Y + N b \ne Y + b
$$

实现上的处理很直接:**只有 0 号卡把偏置融进矩阵乘,其余卡传空** ,注释写明了这就是为了保证 TP 大于 1 时偏置不会被加超过一次。

反方向还有一道保护:如果配置成「不做 all-reduce」却又要加偏置,构造时直接报错,错误信息写的是「不归约结果时给结果加偏置会导致错误的结果」。这两处合起来是同一条不变量的两个方向 —— **偏置必须恰好被加一次,而且必须加在求和之后的那一份数据上。**

### 1.17 TP 顺带把 KV cache 也切了,但这件事有天花板

TP 按注意力头切权重,KV cache 就跟着一起切了 —— 每张卡只持有自己那几个 KV 头的键值,**不需要任何复制** 。所以 TP 是一种难得的「三重加成」并行:同时加速计算、减少每卡 KV cache、减少每卡权重读取。

单 token 的 KV 有多大、TP=8 时每卡分摊多少,02 章 1.3.3 已经按同一个模型算过一遍,这里不重复。本节只回答它没回答的那个问题:**这条线性下降能走多远。**

答案是 **走到 TP 等于 KV 头数为止** 。再往上,就撞上 1.7 说过的那个分支 —— KV 头不够分了,于是被钳到每卡 1 个并开始复制。以一条 20480 token 的请求为例(量级参考,不是本仓库实测):

| TP | 每卡 KV 头 | 每卡每请求 KV | 相对 TP=1 |
|---|---|---|---|
| 1 | 8 | 6.7 GB | — |
| 2 | 4 | 3.35 GB | 2 倍并发 |
| 4 | 2 | 1.68 GB | 4 倍并发 |
| 8 | 1 | 0.84 GB | 8 倍并发 |
| **16** | **1(两卡共一份)** | **0.84 GB** | **仍是 8 倍,不再下降** |

最后一行就是天花板:TP 从 8 翻到 16,复制份数变成 2,**每卡 KV 一个字节都没少,显存白花** 。所以 **分组查询注意力的 KV 头数就是 TP 的上限** ——Llama-3-70B 是 8。

还有一个容易重复计算的地方:上面这笔账用的是 8 个 KV 头而不是 64 个查询头。**把 KV 压掉 8 倍是分组查询注意力的功劳,在 TP 之前就已经发生了** ,不能再算一遍记到 TP 头上。

### 1.18 TP 用满了整机,模型还是放不下

TP 的天花板不只在 KV 那一侧。它的规模受限于单机的卡数与卡间互联 —— 跨机做 TP,那 160 次 all-reduce 就要走网络,1.13 里那个「固定开销主导」的结论会彻底翻盘。

于是有了第二个痛点:**TP 已经吃满一台机器,模型还是装不下。** 671B 这个量级的模型就是这样。

流水线并行给的答案和 TP 正交:**TP 把每一层的权重切成 N 份分到不同卡,PP 把不同的层分到不同卡。**

### 1.19 PP 怎么切:两个除法是叠加的

把 80 层模型按 PP=2 分成两段,每段再配 TP=4:

| 段 | 层 | 这一段的权重 | 再被 TP=4 切开 |
|---|---|---|---|
| 第 0 段 | 0 到 39 | 约 68 GB | 每卡约 17 GB |
| 第 1 段 | 40 到 79 | 约 68 GB | 每卡约 17 GB |

关键在于**两个除法是叠加的** :

$$
\text{单卡权重} = \frac{\text{总权重}}{\text{PP} \times \text{TP}}
$$

段与段之间传的是激活值(隐状态),用点对点的发送与接收,不是集合通信。这一点和 TP 完全不同:**TP 的通信是「把一层的结果拼完整」,PP 的通信是「把一层的结果交给下一段」** 。

### 1.20 一次前向在段之间走几趟,每趟多大

PP=3 时,一个请求的前向被拆成三步,前两步各在段之间发一次隐状态,最后一段算完还要过输出头再采样:

```text
Stage 0:  layer 0..26      -> send hidden_states
Stage 1:  layer 27..53     -> send hidden_states
Stage 2:  layer 54..79 + lm_head  -> logits -> sampling
```

所以 **PP=N 有 N-1 次段间通信** ,每次传的都是 `[批大小, 序列长度, hidden]` 这么大一块 —— 和 1.13 里 all-reduce 搬的是同一种东西、同一个尺寸。

| 阶段 | 单次 P2P | PP=3 合计 |
|---|---|---|
| decode(批 32、每条 1 token) | 512 KB | 1 MB,可忽略 |
| prefill(序列 4096) | 2 GB | 两跳串行,约 14 ms 计入首 token 时延 |

### 1.21 别拿 all-reduce 的带宽数去算点对点

上面那个 14 ms 是按 **单向约 300 GB/s** 算的,不是 1.13 里用的 600 GB/s。这是一处很容易记反的地方:

**600 GB/s 是双向聚合带宽,只有双向都跑满时才适用** ——all-reduce 是这样,点对点的发送与接收不是,它只用一个方向。拿 600 去算 P2P,结果会乐观一倍。

还有一条也容易想错:**配了 TP 时,段间通信的总字节数是 TP 倍,但墙钟时间不随 TP 增加。** 因为 PP 的切分与 TP 正交 —— 隐状态在 all-reduce 之后各个 TP rank 持有的是相同的完整副本,每个 rank 各自发一份给下一段的对应 rank,**这 TP 条链路是并行的** 。

### 1.22 单请求的流水线,三分之二的时间在空转

PP 有一个 TP 完全没有的代价。把 PP=3 的单请求前向画成时间线:

```text
time ->
Stage 0:  [forward]  idle      idle
Stage 1:  idle       [forward] idle
Stage 2:  idle       idle      [forward]
```

每一步只有一段在干活,其余都闲着。空转比例是:

$$
\text{bubble} = \frac{\text{PP} - 1}{\text{PP}}
$$

PP=2 就浪费一半,PP=3 浪费三分之二,PP=4 浪费四分之三。**PP 分得越细,空转越严重** ——这条曲线的方向和「分得细才装得下」正好相反,是 PP 的核心张力。

### 1.23 让多个 step 同时在飞

上面那个 67% 是**单个请求**的图景。真实服务里请求源源不断,所以只要让不同的段去算**不同的 step** ,空转就没了:

```text
time ->
Stage 0:  [step1][step2][step3][step4][step5]
Stage 1:         [step1][step2][step3][step4]
Stage 2:                [step1][step2][step3]
```

引擎为此换了一个不阻塞的 step 实现,用一个队列托住那些已经提交、还没回来的批次 —— 这套机制 01 章 3.6 已经讲过,这里只补它没说的那部分:**队列到底该多长,以及气泡真的被消掉了多少。**

稳态下的吞吐因此变成:

$$
\text{吞吐} \approx \frac{1}{\max_i T_{\text{stage},i}} \quad \text{而不是} \quad \frac{1}{\text{PP} \times T_{\text{stage}}}
$$

也就是说**最慢的那一段决定吞吐** ,而不是所有段的耗时相加。

### 1.24 队列长度不总是等于 PP

01 章说的「队列容量等于流水线级数」是默认档,但不是全部。队列长度这个属性有三条分支:

| 条件 | 队列长度 |
|---|---|
| 异步调度关闭 | PP |
| 异步调度开启,且用 V2 运行器 | **PP + 1** ,多出来那一个专门用于异步重叠 |
| 异步调度开启,用 V1 运行器,且 PP = 1 | **2** |
| 异步调度开启,用 V1 运行器,且 PP > 1 | PP,因为 V1 运行器并不完整支持「异步调度加 PP」 |

两件事顺势就清楚了:**PP = 1 的场景也可能建出这个队列** (引擎建它的门槛是队列长度大于 1,不是 PP 大于 1);而 V1 运行器那一档是一条明说的能力缺口,源码注释直接写了它不完整支持异步调度配 PP。

### 1.25 在飞的 step 数和气泡数不是同一个数

这两个数差 1,很容易混:

| 数 | 值 | 含义 |
|---|---|---|
| 同时在飞的 step 数 | PP | 等于队列长度,每一段各算一个不同的 step |
| 气泡数 | **PP - 1** | 把流水线填满所需的预热步数 |

所以队列并没有消灭气泡,它只是**把气泡从稳态赶到了两头** ——启动时 PP-1 个,收尾时 PP-1 个,中间一路满载。批次足够多时这点开销摊薄到可以忽略;批次很少时它仍然是实打实的浪费。

### 1.26 推理里 PP 很少用,四个理由

| 理由 | 说明 |
|---|---|
| TP 通常已经够用 | 70B 的 141 GB 在 TP=8 下每卡约 18 GB,80 GB 的卡装完还剩很多给 KV cache |
| 气泡终归存在 | 队列只把气泡赶到两头,批次少时占比仍然高 |
| 延迟更差 | PP 是串行流水,一步要等所有段跑完;TP 是并行的,单步更快 |
| 只有超大模型才需要 | 要到 TP 用满整机仍装不下的量级,才轮得到 PP |

判据很干脆:**只有当「TP 乘以单卡显存」小于模型权重时才启用 PP** ,否则默认 PP=1。

### 1.27 开了 PP 会关掉 MoE 的序列并行,但约束不在配置里

这是本章第一处需要更正讲稿的地方,而且它是那种「结论对、理由半对」的类型。

**结论成立** :开了 PP,MoE 的序列并行确实不生效。

**但约束不在那个配置属性上。** 配置层判断要不要开 MoE 序列并行时,看的是四件事 —— 通信后端在不在白名单里、专家并行有没有开、TP 是否大于 1、DP 是否大于 1。**没有任何一条提到 PP。**

真正的约束写在**每个模型自己的实现里** ,而且是各写一遍 —— 至少八个模型文件里都有同一行「配置层说可以,并且 PP 等于 1」。这是一个「同一个概念有两层判断」的典型:配置层给出全局资格,模型层再叠一道自己的门槛。只查配置层会得出相反的结论。

理由也比讲稿给的更具体。源码注释挂着一条待办,说的是:**要等 PP 的边界逻辑能安全地跨段收发序列并行的隐状态之后,才能让两者共存。** 所以这不是「两种切法在原理上冲突」,而是**一处已经被记下来、等着做的实现缺口** 。

### 1.28 MoE 把显存和算力的比例拧断了

第三个痛点来自模型结构本身。混合专家模型(MoE)把每层的 FFN 换成了若干个独立的专家 FFN,每个 token 只激活其中几个。

以 Mixtral-8x7B 为例(hidden 4096、中间维 14336、32 层、8 个专家、每 token 选 2 个),单层的账是这样(量级参考):

| | 权重 |
|---|---|
| 换成 MoE 之前的一个 FFN | 约 352 MB |
| 8 个专家的 MoE 层 | 约 2.8 GB |
| 32 层合计 | **约 90 GB** |

**参数量按专家数放大,计算量只按激活数放大** ——显存涨了 8 倍,计算量只涨 2 倍。这个比例被拧断之后,原来那套「切权重」的办法就不够用了:单卡装不下全部专家,而专家之间本来就是彼此独立的整块,没必要再去切单个专家的矩阵。

### 1.29 EP 怎么切,以及一次前向的四步

切法直白:**8 个专家、EP=2,就是每卡 4 个专家** ,整个专家不再拆。

但这带来一个 TP 完全没有的问题:token 在哪张卡上,和它要用的专家在哪张卡上,**是两件互不相干的事** 。于是一次 MoE 前向变成四步:

```text
Step 1  Gate        each card scores all experts locally     路由权重各卡一份完整副本,不切
Step 2  Dispatch    all-to-all #1                            把 token 发到持有它所选专家的卡
Step 3  Compute     each expert runs its own FFN             各卡独立,不通信
Step 4  Combine     all-to-all #2                            把结果发回 token 原来的卡
```

第一步不通信:路由权重是各卡相同的完整副本,每张卡拿自己手上的 token 独立算一遍打分、选出各自的前 k 个专家。最后一步之后,原卡按路由权重把 k 个专家的输出加权合并。

有一个前提必须说清,否则整件事讲不通:**EP 下每张卡持有的是不同的 token 分片,不是同一份复制。** 如果每张卡都握着全部 token,就根本不需要把 token 发来发去了。

### 1.30 通信量:decode 可以忽略,prefill 很显著

两次 all-to-all 搬的都是被选中的那些「token 与专家的配对」的隐状态,上界是:

$$
\text{tokens} \times \text{top}_k \times \text{hidden} \times \text{字节宽度}
$$

| 阶段 | 单次 all-to-all | 两次合计 |
|---|---|---|
| decode(32 个 token、top-2、hidden 8192、bf16) | 1 MB | 2 MB,可忽略 |
| prefill(32 条请求各 4096,共 131072 个 token) | 约 4.3 GB | **约 8.6 GB** |

这个对比和 TP 那边是同一个形状 —— decode 端小到不用管,prefill 端大到必须管。原因也一样:通信量只跟这一步算多少 token 有关。

### 1.31 EP 越大,跨卡比例越接近 100%

手算例子里常常会出现「有些 token 的专家恰好都在本卡,不用发」的好情况。**这是挑出来的,不是常态。**

真实的路由分布接近均匀随机:EP=N 时,一个「token 与专家」的配对落在本地的概率大约是 $1/N$。所以 **EP 越大,跨卡比例越接近 100%** ,上一节那个上界基本就是实际值。换句话说,**EP 扩得越大,all-to-all 越省不掉** 。

### 1.32 路由是动态的,所以负载天生不均衡

TP 的切分是静态的:每张卡算多少,开机就定死了。**EP 不是** ——哪个专家收到多少 token,由路由当场决定,而路由看的是输入。

这里有个很容易被平均数骗过去的地方。假设 4 个 token、top-2、EP=2,每卡 4 个专家,而这 4 个 token 碰巧都选中了同样那两个热门专家,一个在 0 卡、一个在 1 卡。按卡统计,两张卡各收到 4 个 token,**总量完全均衡** 。

但实际算起来并不均衡:**专家 FFN 的耗时取决于单个专家收到多少 token,不是整卡收到多少。** 一张卡上一个专家扛了 4 个 token、另外三个专家颗粒无收,和四个专家各分 1 个,是完全不同的两回事。

### 1.33 all-to-all 是同步的,所以最慢的卡决定整轮

不均衡本身还只是浪费。真正把它放大的,是它**被夹在两个同步点之间** 。

all-to-all 是集合通信:所有 rank 必须同时参与,全都完成之后才能继续。于是一轮 MoE 变成这样:

```text
time ->
Card 0:  [dispatch wait]  [compute 6 pairs]  [combine wait]
Card 1:  [dispatch wait]  [compute 2 pairs]  [combine wait ....]
                                             Card 1 idles here, waiting for Card 0
```

两个同步点各放大一次:dispatch 时,发得少的卡要等发得多的卡;combine 时,算得快的卡要等算得慢的卡。**中间那段计算差异被原封不动地转成了空转。**

### 1.34 为什么要把缓冲区对齐到统一长度

看到「各卡发的 token 数不同却要对齐到同一长度」,很容易归咎于通信库不支持不等长。**这个归因是错的** ——底层的 all-to-all 原语本来就接受每个 rank 各自的切分长度。

真正逼出对齐的是另外两件事:

| 原因 | 说明 |
|---|---|
| CUDA Graph 捕获要求缓冲区形状固定 | 形状一变就得重新捕获,整张图的收益就没了 |
| DP 各副本的 token 数本来就不同 | 进 MoE 之前先要统一到同一长度,而且要向上取整到序列并行规模的倍数 |

第二条的做法是:把每个 DP 副本的 token 数按序列并行规模**向上取整再均分** ,于是每一份的长度都相同、且合起来不小于原数。多出来的槽位是无效 token,算了也不要。

所以这是一次**用带宽换形状确定性**的交换,不是能力不足。绕开这层对齐确实是有路子的,那属于另一套通信后端的选择。

### 1.35 不均衡对 prefill 和 decode 的伤害不一样

| 阶段 | 为什么 | 伤害 |
|---|---|---|
| prefill | 一步里 token 很多,路由更容易把大量 token 压到少数几个专家上 | **重** ,直接抬高首 token 时延 |
| decode | 一步里 token 很少,每个 token 独立选专家,偏斜是随机的、绝对值也小 | 轻,但一批之内各专家拿到的 token 数仍然不同 |

这条和 1.13 与 1.30 的分野是同一条线:**prefill 那一步的 token 多,所有跟 token 数成正比的代价都在那里集中爆发。**

### 1.36 vLLM 不丢 token,只把它补齐

训练框架里对付专家负载不均衡有个经典手法:给每个专家设一个**容量因子** ,超出的 token 直接丢掉不算。这在训练里勉强可接受(丢一点样本换吞吐),在推理里不行 —— 用户的 token 不能算着算着就没了。

vLLM 的 MoE 执行路径里**根本没有这个机制** :全仓唯一出现「容量因子」这个名字的地方,是某个视觉模型自带的实现,和这条路径无关。

它换了一种办法:把每个专家收到的 token 序列**补齐到分块大小的整数倍** ,让分块矩阵乘能直接跑。于是代价的性质变了 —— 从「精度损失」变成了「**padding 带来的无效计算** 」:某个专家只拿到 3 个 token,也要按一个完整的块去算。

这是本章第三次见到同一个交换。1.34 是用带宽换形状确定性,这里是用算力换「一个 token 都不丢」。**分块的机器不喜欢参差不齐,而抹平参差总要付钱。**

### 1.37 同一个 kernel 顺手做了本地筛选

上面那个补齐 kernel 在 EP 场景下还兼了第二份差事,而这件事设计得相当巧。

它的做法是:**先把所有专家都当成有效的**、给全部 token 排好序补齐,**在返回之前**才把不属于本 rank 的专家 id 标成 `-1`,对应的块在矩阵乘里直接跳过。docstring 把这个顺序写得很明白,还特意提醒传进来的专家总数必须是**全局**的专家数而不是本卡的。

为什么值得单拎出来:本地与远端的筛选本来是一件独立的事,完全可以另起一个 kernel。把它塞进补齐 kernel 的返回前,等于**用一个已经要跑的排序顺带完成了分卡** ,省掉一轮对全部 token 的遍历。

### 1.38 EPLB:把热门专家搬到轻载的卡上

补齐只是让不均衡不致命,没有让它消失。**专家负载均衡** (EPLB)才是直接冲着 1.32 那个痛点去的:观测到某些专家持续热门时,**把它的权重从重载的卡迁到轻载的卡** 。

它有一条硬前置:**必须先开专家并行** ,否则配置阶段直接报错,错误信息就写着专家并行必须为真才能用它。这其实是显然的 —— 不开 EP 时专家本来就按 TP 切碎摊在每张卡上(见 1.54),没有「某个专家在哪张卡」这回事,也就无从迁移。

代价是它要求模型支持权重迁移,所以不是所有 MoE 模型都能用。

### 1.39 另外两条缓解:变长后端与序列分片

| 手法 | 做什么 | 代价 |
|---|---|---|
| 变长路由的通信后端 | 不等所有 rank 都补齐到最大值,用异步通信让每个 rank 只发自己实际的数据量 | 要 NVSwitch 或 RDMA 这类硬件支持 |
| 配合序列并行 | MoE 在序列分片上做 dispatch,每个 rank 只处理 1/N 的 token,补齐开销也降到 1/N | 需要序列并行本身能开(见 1.57) |

前者是把 1.34 那层对齐直接绕开,后者是让被对齐的那个量本身变小。**两条路都不是消除补齐,而是缩小它作用的范围。**

### 1.40 网络和 SM 在轮流空转

到这里 MoE 的四步已经讲完,但还有一个结构性的浪费没动:**dispatch、专家计算、combine 在时间上首尾相接** 。

```text
time ->
             T1            T2            T3
comm    [ dispatch ] ............ [ combine  ]
compute ............ [ expert  ] ............
```

T1 和 T3 网络满载而 SM 全闲,T2 反过来。**两种硬件资源轮流空转**,总耗时是三段之和。

### 1.41 切成两个微批,让通信与计算落进同一个时间槽

双批重叠(DBO)的想法很直接:把一批切成两个**微批** ,让微批 1 的通信和微批 0 的计算落在同一个时间槽里。通信走通信流,计算走计算流,两条流在 GPU 上真正并发。

```text
time ->
             T1          T2          T3          T4
comm    [ disp0  ] [ disp1  ] [ comb0  ] [ comb1  ]
compute ........... [ comp0  ] [ comp1  ] ...........
```

T1 是启动(没有可重叠的计算),T4 是收尾,**中间两个槽里通信与计算真正重叠** 。顺序执行两个微批要 6 个槽,这里 4 个槽,省掉约三分之一;稳态下总耗时逼近「通信总量与计算总量取大」而不是两者相加。

微批数在开了这个开关之后**固定为 2** 。顺带一提,它并不是唯一的微批入口:还有一个独立的微批大小参数,设成大于 1 同样会启用微批,而那时的微批数等于这个参数本身。

### 1.42 CPU 上轮流跑,GPU 上才是同时跑

这里有一处极容易误解的地方:两个微批各由一个 CPU 线程驱动,而**同一时刻只有一个线程在跑** ,靠事件交替唤醒。那重叠是从哪来的?

关键在于 **CPU 只负责「下发 kernel」,下发完立刻让出,不等 GPU 做完** 。

```text
CPU:  thread0 issues disp0, yields -> thread1 issues disp1, yields -> ...
GPU:  comm stream    [ disp0 ][ disp1 ]
      compute stream        [ comp0 ]
```

一句话:**CPU 的串行让出只决定「下发顺序」,GPU 的两条流才决定「执行重叠」。重叠发生在 GPU,不在 CPU。**

### 1.43 有依赖的地方用 Event 卡住,没依赖的才放开

两条流一旦并发,正确性就得自己保证 —— 微批 0 的计算必须等它自己的 dispatch 数据到齐。这靠四个成对的方法:通信流上打完成标记、计算流上打完成标记、通信流等计算、计算流等通信。

**有数据依赖的地方用事件卡住,没有依赖的地方才放开重叠。** 这就是它既快又正确的全部道理。

实际用的是两个组合动作:从计算切到通信时,先给计算流打标记、让出 CPU、把本微批切到通信流、再让通信流等本微批的计算完成;反过来同理。**让出与切流被绑成了一个原子操作** ,因为这两件事分开做就会留下窗口。

### 1.44 「我发完就走,你替我收」

重叠真正被制造出来的那一下,是一对动作:**注册接收回调,然后立刻让出。** 不阻塞等 dispatch 收完,而是把「收数据」这件事登记成一个钩子,马上把 CPU 让给另一个微批去下发计算。

这里有个很容易看漏的细节:**钩子挂在下一个微批的上下文上,不是自己身上。** 也就是说收数据这件事,是由**另一个微批的线程在它自己合适的时机**替你完成的。

「我发完就走,你替我收」—— 这正是两个微批的交接点,也是那段「等通信」的空窗被让给对方计算的确切位置。

### 1.45 token 太少就不切:两个阈值

切微批不是白来的:切开后每个微批的 kernel 更小,GPU 可能打不满,而且额外多出一倍的 kernel 启动与事件同步开销。token 数少的时候,重叠省下的时间还不够补这些开销。

所以有两个阈值,decode 与 prefill 各一个,低于阈值就不切:

| 开关 | 默认 | 含义 |
|---|---|---|
| 是否启用双批重叠 | 关 | 总开关 |
| decode 侧阈值 | 32 | 这一步的 token 数低于它就不切 |
| prefill 侧阈值 | 512 | 同上,prefill 的门槛高得多 |

两个阈值还各有一条校验:**它们都必须至少等于微批数** ,否则连一个 token 都分不到,配置阶段直接报错。

### 1.46 共享专家不经过路由,所以能藏起来

有一类 MoE 用的是「共享专家加路由专家」的结构:**所有 token 都要过共享专家** ,同时再按路由选若干个路由专家,两份输出相加。

这个结构给出了另一个重叠机会,而且理由和 DBO 完全不同:**共享专家不依赖路由,也不依赖 dispatch** 。它一拿到输入就能算,不必等任何通信。

```text
no overlap:
  [shared] -> [dispatch] -> [routed compute] -> [combine] -> [add]

with overlap:
  stream 1 (routed):  [dispatch] -> [routed compute] -> [combine] -> [add]
  stream 2 (shared):  [shared compute] ......................^
                                                             等 shared 完成
```

效果很干净:**共享专家的计算时间被藏进路由专家的 dispatch 与计算里** 。只要共享专家的计算量不超过那段时间,它就几乎是免费的。

### 1.47 不是开关,是一个四值枚举

重叠方式不是「开」和「关」两态。代码里是一个枚举,**四个取值** :

| 取值 | 含义 |
|---|---|
| 没有共享专家 | 这个模型压根没有这个结构 |
| 不重叠 | 老老实实在路由那一坨之前跑一遍 |
| 由内核内部重叠 | 交给 MoE 内核在它的 dispatch 与 combine 之间安排 |
| 多流重叠 | 在辅助流上与门控、路由、专家并行 |

第一个取值和后面三个不是一类东西 —— 它说的是「结构上没有共享专家」,不是一档重叠方式。把它算进来才是四值,只数重叠方式则是三种。**这个区分值得留意:代码里判断走哪一档时,这四个是同一条链上的返回值。**

### 1.48 走辅助流要同时满足五个条件

三级判定的前两级很直白:**先问要不要禁用,再问内核能不能自己重叠** ,都不成立才轮到多流。

第三级要同时满足五条才走辅助流:

| 条件 | 为什么 |
|---|---|
| 平台是 CUDA 或类 CUDA | 非该类平台拿不到辅助流 |
| 辅助流存在 | 有一个环境变量能把它强制关掉 |
| **这一步的 token 数不超过阈值** | token 多的时候主流本来就把 GPU 打满了,再拆一条流没有收益 |
| 这次重叠确实划算 | 在 ROCm 上只有纯数据并行的部署才受益,是一条按经验加的平台判断 |
| 多流是安全的 | 路由专家与共享专家的输入若是同一块内存的别名,多流就不安全 |

**第三条的方向是反直觉的**:辅助流只在 token 少的时候用。这和 1.45 那个阈值恰好相反 —— 那边是 token 太少不值得切,这边是 token 太多不值得拆。两者不矛盾:DBO 切的是同一条流上的批,靠的是通信与计算错开;这里拆的是第二条流,靠的是主流没把 GPU 占满。

禁用那一级也有明确的理由:专家负载均衡配上不在白名单里的通信后端**会有正确性问题** (白名单只有两个后端),以及某种双边内核下本来就没什么可赚的;此外,做了序列分片的层直接禁用。

### 1.49 跨流的正确性靠成对的事件,而不是流生命周期标记

这里是本章第二处更正,而且是「**机制已经被换掉**」那一类。

一个常见的说法是:跨流用张量的流生命周期标记(防止输入在辅助流还在用时被回收)加上「辅助流等主流」来保证正确。**基准上这两个调用都不存在** ——整个 MoE 目录里一次都没有出现过前者。

实际用的是**两对 CUDA 事件** ,每个微批各一对:

```text
main stream:  record input_ready[i]
aux stream:   wait input_ready[i] -> run shared expert -> record output_ready[i]
main stream:  wait output_ready[i]
```

换成事件之后精度更高:「辅助流等主流」等的是整条主流到此为止的全部工作,而等一个事件**只等那一个点** 。

顺带记一笔:输出槽是两份、按当前微批 id 索引 —— 因为共享专家可能从 MoE 内核的收尾阶段被调用,两个微批各要有一份中间结果。**而事件同样是每个微批一对** ,理由一样。

### 1.50 MoE 的三种实现,数学上完全等价

前面讲的 dispatch 与 combine 只是三条路之一。MoE 层的通信实际有三种实现:

| | 方式一 | 方式二 | 方式三 |
|---|---|---|---|
| 名字 | TP all-reduce | EP 融合加 all-reduce | EP all-to-all |
| 开关 | 默认,不开 EP | 开 EP,数据并行为 1 | 开 EP,数据并行大于 1 |
| 专家权重 | 按 TP 切碎 | 整个专家放一张卡 | 整个专家放一张卡 |
| 通信 | 1 次 all-reduce | 1 次 all-reduce | **2 次 all-to-all** |
| 无效开销 | 无 | all-reduce 覆盖完整张量;每个 token 在每卡各存一份 | 对齐补齐加两次同步 |
| 负载不均衡 | **无** | 有 | 有 |

方式二能成立,靠的正是 1.37 那个标记:不属于本卡的专家块被跳过,那些位置留 0,而 0 值在求和里不影响结果。所以**三者的最终输出是同一个加权和,数学上完全等价** ,区别全在「无效开销长什么样」。

方式一「无负载不均衡」这一格值得多看一眼:每张卡都把**全部** token 与专家的配对在自己那 1/TP 的权重分片上算一遍,工作量逐卡完全相同 —— 代价是它根本没利用稀疏性。

### 1.51 最容易记错的一行:方式一和方式二的每卡权重一样多

直觉上「开了 EP 就能省显存」,所以方式二应该比方式一省。**不是的。**

把 256 个专家各切 1/TP,和拿 256/TP 个完整专家,**字节数完全相同** 。区别只在粒度:切碎的专家 vs 完整的专家。

那 EP 省的是什么?两件事:

- **让每个专家的矩阵乘保持完整** ,不被切碎到打不满 SM;
- **为跨节点扩展打开空间** ——方式三里专家并行规模乘上了数据并行,设备总数多了一个量级,那时每卡权重才是真的更少。

换句话说,**EP 省的不是「同样卡数下的显存」,而是把规模扩出去的可能性。**

### 1.52 为什么 decode 偏向 all-reduce、prefill 偏向 all-to-all

这两个方向都能从 1.13 和 1.30 推出来。

**decode 上方式一与方式二更优。** 激活很小,all-reduce 落在固定开销主导的区间(1.13:单次 5 到 15 µs,而不是带宽推出的 1.7 µs)。而 all-to-all 要付两次同步加对齐补齐,还要暴露在负载不均衡下 —— **两次 all-to-all 的固定开销比一次 all-reduce 更高** ,小 message 场景 all-reduce 赢。

**prefill 上方式三可能更优。** token 数很大,带宽项主导。方式一与方式二的 all-reduce 要搬完整的张量,而 all-to-all 搬的是「token 与专家配对」里真正跨卡的那部分,**专家越多、激活比例越稀疏,它越省** 。再加上方式三让每卡只承载 1/DP 的 token,激活显存也跟着降,长 prompt 场景更划算。

### 1.53 谁决定走哪一种

这不是一个用户直接选的档位,是从几个开关推出来的:

| 条件 | 落到哪一种 |
|---|---|
| 不开专家并行 | 方式一 |
| 开了专家并行,但数据并行、前缀上下文并行、序列并行都没开 | 方式二 |
| 开了专家并行,且三者之一成立 | 方式三 |

判据写成一行就是:**开了 EP,并且「数据并行大于 1、或前缀上下文并行大于 1、或序列并行开着」。** 注意后两项 —— 走 all-to-all 的触发条件不止数据并行一个,这是容易只记住一半的地方。

### 1.54 TP 和 EP 对 MoE 是互斥的

到这里可以回答 1.4 埋下的那个问题了。MoE 的 FFN 有两种切法,而它们**互斥,不能叠加** :

| 切法 | 每卡持有 |
|---|---|
| 纯 TP | 全部专家各自的 1/TP 权重(每个专家都被切开) |
| EP | 专家总数除以「TP 乘数据并行乘前缀上下文并行」个**完整**专家 |

有一个很自然但错误的想象:「TP 加 EP 等于先按专家分卡、每个专家再按 TP 切成小块」。**代码不这么做** ——开 EP 的分支里 MoE 内部的 TP 被直接置为 1(1.4 已经讲过这一行)。

所以命令行里那个 TP 数字,**对 MoE 层不是「每个专家切几份」,而是被压平算进了专家并行规模** ——TP 度在 MoE 层被翻译成了 EP 度。TP 仍然真实作用于注意力(按头切)和稠密层,只是不作用于专家权重。

### 1.55 为什么不把专家再按 TP 切碎

这个设计选择有具体理由,而且和 1.5 那笔账正好相反。

MoE 的**单个专家矩阵本来就比稠密 FFN 小一个量级** 。再按 TP 切下去,每块矩阵乘会小到打不满 SM;而且切了就要拼,**每个专家都要一次 all-reduce,通信次数按专家数放大** 。

整份分卡加一次 all-to-all 把 token 送过去,反而更划算。**这是同一条权衡在不同尺度下给出相反答案的例子** ——1.9 那里切碎是对的,因为那些矩阵足够大;这里切碎是错的,因为专家矩阵本来就小。

### 1.56 序列维还没被切过

回头看前面三种并行切过的维度:TP 切权重的输出维与输入维,PP 切层,EP 切专家。**序列维一次都没被切过。**

这留下了两个痛点。其一,归一化这类逐 token 的算子,每张卡都在完整序列上算一遍 —— 完全重复。其二,序列越长激活越大,而 1.5 那笔账只算了权重,没算激活。超长上下文场景里,后者才是真正顶不住的那一项。

序列并行(SP)和上下文并行(CP)就是冲这一维来的。它们有一个共同特点:**不额外占 GPU** ,而是复用 TP 那组 rank(1.3 已经点过)。

### 1.57 SP 的开关不在并行度参数里

这是它和前面几种并行最不一样的地方:**SP 没有自己的并行度参数** 。它不在那一族 `--*-parallel-size` 里,因为它复用 TP 的 rank,规模就等于 TP。

真正的开关在**编译配置**里,而且是自动判定的:先按模型与配置置真,随后逐条检查不兼容项再置回假。它的阈值字段默认为空,表示交给一个函数自动推算。

自动开关是因为 SP 有两个隐性代价:

| 代价 | 说明 |
|---|---|
| 补齐出来的无效计算 | token 数必须是 TP 的整数倍 —— 沿序列切 N 份要求能整除,所以运行时会把实际 token 数补齐 |
| CUDA Graph 可选尺寸变少 | 捕获时不能被 TP 整除的批大小会从候选尺寸里被剔掉,更容易落到更大的那一档或退回 eager |

**这也是它必须有 token 阈值把关、而不是无条件开启的原因。** 又一次是同一个形状:1.36 用算力换不丢 token,1.34 用带宽换形状确定性,这里是用补齐与图的灵活性换激活显存。

### 1.58 一层里 TP 区与 SP 区交替

SP 的核心做法只有一句:**把 TP 的 all-reduce 换成 reduce-scatter 加 all-gather** 。

求和之后顺手沿序列切成 N 份,于是紧跟着的归一化就在 1/N 的序列上做;下一个需要完整序列的算子之前再 all-gather 回来。一层 Transformer 因此被切成交替的两种区域:

```text
in:  residual sharded [B, seq/N, hidden]
  |
  +-- SP region:   RMSNorm on the shard, then all-gather      归一化只在 1/N 序列上做
  |
  +-- TP region:   QKV column -> attention -> output row       和 1.7 到 1.11 完全一样
  |                then reduce-scatter                          求和顺手切片
  |
  +-- SP region:   residual + RMSNorm on the shard, all-gather
  |
  +-- TP region:   gate_up column -> SiLU -> down row
  |                then reduce-scatter
  v
out: residual sharded [B, seq/N, hidden]
```

每层的通信变成 2 次 all-gather 加 2 次 reduce-scatter。**这和原来 2 次 all-reduce 的通信量相同** ——因为环形 all-reduce 本来就是 reduce-scatter 加 all-gather 两轮(1.13 的系数 2 正是从这里来的)。SP 只是把这两轮拆开,在中间插进了归一化。

所以 SP 的收益不在通信:**通信量一个字节没省,省的是归一化那一段的激活** ,从完整序列降到 1/N。注意力与 FFN 那两段仍然在完整序列上算,它们本来就需要。

### 1.59 先看没有 SP 时 MoE 模型长什么样

上一节那套是稠密模型的 SP。MoE 模型的 SP 更简洁,但要看出简洁在哪,得先摆出它没开 SP 时的样子。

大 MoE 模型的典型配置是 **TP 只切注意力,EP 切专家** ,一层的通信是这样:

| 位置 | 通信 |
|---|---|
| 归一化 | 无,每卡都在完整序列上算一遍 |
| 注意力(QKV 列切、输出行切) | **1 次 all-reduce** |
| 门控 | 无,各卡独立算 |
| dispatch | 1 次 all-to-all |
| 专家计算 | 无 |
| combine | 1 次 all-to-all |
| **合计** | **3 次集合通信** |

有两处值得留意。**专家那一段没有 all-reduce** ——EP 下每个专家在单卡上算完整,输出就是完整结果而不是部分和(1.50 讲过)。**而归一化仍然在完整序列上算** ,每卡各存一份完整激活,这正是 SP 要省掉的东西。

### 1.60 MoE 的 SP 比稠密模型更简洁:全程在分片上跑

开了 SP 之后,MoE 那一整段**从头到尾都在序列分片上跑,一次 all-gather 都不用** :

```text
in:  residual sharded [seq/N, hidden]
  |
  +-- SP region:  RMSNorm on the shard, then all-gather           拼回完整序列,注意力需要
  |
  +-- TP region:  QKV column -> attention -> output row            输出不做 all-reduce
  |               then reduce-scatter                              求和与切分一步完成
  |
  +-- SP region:  residual add + RMSNorm on the shard
  |
  +-- MoE:        gate -> dispatch -> experts -> combine           全程 [seq/N, hidden]
  |                                                                不做 all-gather
  v
out: hidden sharded [seq/N, hidden]
```

和稠密模型那套一比,差别一目了然:

| | 稠密模型的 SP | MoE 的 SP |
|---|---|---|
| all-gather | 2 次(注意力前、FFN 前) | **1 次** (只在注意力前) |
| reduce-scatter | 2 次(注意力后、FFN 后) | **1 次** (只在注意力后) |
| FFN/MoE 前后 | 都需要 | **都不需要** |

**SP 没有给 MoE 引入任何额外通信** ——那两次 all-to-all 是 EP 本身的开销,不开 SP 时也一样要做。

### 1.61 为什么门控可以在分片上做

上面那个「不需要 all-gather」全靠一件事:**门控是逐 token 的操作。**

每个 token 独立算自己的打分、独立选自己的专家,和序列里的其他 token 没有任何关系。所以沿序列维切开不影响正确性 —— 这和 1.9 里「激活函数是逐元素的所以能各卡独立做」是**同一个判据在不同维度上的应用** 。

判据一旦这么写出来就很好用:**一个算子能不能在分片上做,只看它跨不跨那一维。** 归一化跨的是 hidden 维不是序列维,所以能在序列分片上做;门控跨的是专家维也不是序列维,所以也能;注意力跨的恰恰是序列维,所以它必须先 all-gather。

### 1.62 all-reduce 去哪了:被推迟到下一层的归一化里

注意力的输出投影在这条路径上**始终不做 all-reduce** ,输出保持部分和的形态。源码注释就写在那一行上方:输出投影按不归约配置,归约要放到归一化之前做。

| SP 状态 | 那次归约由谁做 |
|---|---|
| 关 | 一个把 all-reduce 与归一化融合在一起的算子 |
| 开 | 显式的 reduce-scatter —— **求和与切分一步完成** |

MoE 与稠密 FFN 的输出同样保持部分和,把归约**推迟到下一层入口的归一化** 。

这是一个很值得记住的手法:**不要在算完的地方立刻归约,而是把归约推到下一个必须用完整数据的算子跟前** ,于是归约就能和那个算子融合成一个 kernel。1.68 讲的三种融合全建立在这一步上。

### 1.63 MoE 的 SP 真正省的是重复的那份 token

这里有一个容易被「省激活」四个字盖住的收益,而它比省激活值钱得多。

没开 SP 时,**同一个 TP 组里每个 rank 手上都是完整的、彼此重复的那一份 token** 。dispatch 会把同一批 token 重复发 N 遍。开了 SP 之后每个 rank 只持有 1/N,这份重复被消掉,**all-to-all 的数据量直接降到 1/N** 。

所以 MoE 的 SP 比稠密模型的 SP 更划算:稠密那边省的是归一化的激活,MoE 这边**额外省掉了 all-to-all 的 N 分之 N-1** 。

### 1.64 SP 既不省计算,也不省通信总量

把账摊开算,SP 的收益面其实很窄。

**计算几乎不变。** 归一化的计算量降到 1/N,但注意力与 FFN 那两段在 all-gather 之后仍然是完整序列 —— 而归一化本来就占总计算不到百分之一。

**通信总量也不变。** 这一点 1.58 已经说过:环形 all-reduce 本就是 reduce-scatter 加 all-gather 两轮,单看每一轮只搬 all-reduce 的一半,两轮加起来才等于原来那一次。

但有一件事确实变了:**kernel 数量翻倍** ,每层从 2 次集合通信变成 4 次。在 decode 阶段(消息只有几百 KB、固定开销主导,见 1.13)这是**净亏** 。

这正是 1.57 那个 token 阈值要挡住的场景。

### 1.65 推理里 SP 省的显存远少于训练

序列并行是训练里提出来的,而**它在训练里的收益和推理里不是一个量级** ,这个差别必须说清。

训练要为反向传播保留每一层的激活,所以 80 层会累加起来,SP 省下的是 80 层各自的那 N 分之 N-1。**推理没有反向,激活是流水式复用的** ——算完第 i 层就可以覆盖,同时活着的只有当前层的中间量加上跨层的残差,根本不存在 80 层累加(这一点 02 章 1.3.3 讲显存探测时已经建立过)。

以 prefill(批 32、序列 4096、hidden 8192、bf16)为例,一份完整张量是 2 GiB:

| | 纯 TP 每卡 | TP=8 加 SP 每卡 |
|---|---|---|
| 跨层传递的残差 | 2 GiB | **256 MiB** |
| 分片区内的归一化输出 | 2 GiB | **256 MiB** |
| TP 区内的 QKV、注意力、FFN 中间量 | 不变 | **不变** (all-gather 之后仍是完整序列) |

**省的是分片区那几个张量,不是全部。** 所以不要指望 N 倍级别的整体下降 —— SP 在推理里更主要的价值是下一节讲的那个。

### 1.66 prefill 有效,decode 净亏

| 阶段 | 激活规模 | SP 的效果 |
|---|---|---|
| prefill(序列 4096) | 大,每卡每层约 2 GiB | **有效** ,省下的显存归到 KV cache 池,可以增大批或支持更长序列 |
| decode(序列 1) | 极小,每卡每层十几 KB | **净亏** ,多出来的通信 kernel 开销大于收益 |

又一次是同一条分野线。1.13、1.30、1.35 都是这个形状:**prefill 那一步的 token 多,所有正比于 token 数的东西都在那里值钱;decode 那一步 token 少,固定开销说了算。**

### 1.67 拆开 all-reduce 之后,中间就能插东西了

SP 在推理里最值钱的地方不是省显存,是**它把一个原子操作拆成了两个** 。

all-reduce 是一步到位的原子通信,中间插不进任何计算。拆成 reduce-scatter 加 all-gather 之后,**中间那个分片区就成了一个可以放东西的空档** ——归一化被放进去了,而且既然归一化已经在里面,量化也可以跟着进去。

这套优化全部由编译期的一个改写 pass 完成:**识别出「all-reduce 接归一化」的图模式,替换成「reduce-scatter 接归一化接 all-gather」** ,对模型代码完全透明。

### 1.68 三种融合,六个类

改写 pass 里一共有六个模式类,是「首层 / 中间层」乘以「三种精度」:

| 融合链 | 省下什么 |
|---|---|
| reduce-scatter 加归一化加 all-gather | 归一化的计算量与它的输入输出张量都降到 1/N |
| 同上,中间层版本再融合残差相加 | 残差相加与归一化合成一个 kernel,省一次 kernel 启动和一次分片张量的读写往返 |
| reduce-scatter 加归一化加量化加 all-gather | **all-gather 那条腿搬的是量化后的数据** |

第三种是三者里收益最直接的:既然归一化之后紧接着就要给下一个矩阵乘,而那个矩阵乘本来就要把输入量化,**不如把量化提到通信之前做,让 all-gather 只搬量化后的字节** 。

### 1.69 为什么 all-gather 可以降精度而 reduce-scatter 不行

这一条是整套融合能成立的关键,而且理由很干净:

- **reduce-scatter 要做跨卡求和** 。低精度的舍入误差会在求和过程里累积放大,所以它必须保持高精度。
- **all-gather 只是把各卡的不同 token 段拼接在一起,没有任何算术运算** 。拼接不会引入新的误差。

再加上那句关键的:拼接后紧接着就是下一个矩阵乘的输入,**而那个矩阵乘本来就要把输入量化** 。所以这里的低精度**不是新引入的损失,只是把量化步骤提前到了通信之前** 。

这和 1.9 那条「非线性函数不满足分配律」是同一类推理:**看这个操作是不是算术的,再决定能不能在它上面动手脚。**

### 1.70 降精度省下来的只在一条腿上

省多少要算清楚,否则容易高估。取一份完整张量 64 MiB、8 卡:

| 模式 | reduce-scatter 腿 | all-gather 腿 | 每卡收发合计 |
|---|---|---|---|
| 纯 TP 的 all-reduce | — | — | 112 MiB |
| SP,all-gather 走 bf16 | 56 MiB | 56 MiB | 112 MiB,与纯 TP 相同 |
| SP,all-gather 走 FP8 | 56 MiB | 28 MiB | **84 MiB** ,省 25% |
| SP,all-gather 走 FP4 | 56 MiB | 14 MiB | **70 MiB** ,省 37.5% |

**reduce-scatter 那 56 MiB 是省不掉的下限。** 所以 FP8 把 all-gather 的字节数砍一半、FP4 砍四分之三,折算到整层通信是 25% 和 37.5% —— **不是「降到十六分之一」那种量级** 。量化后的比例因子张量也要一起 all-gather,但它按块存而不是按元素存,小一到两个量级,可以忽略。

### 1.71 长 prompt 的首 token 时延

到这里序列维被切开了,但只切在注意力之外 —— **注意力本身仍然要在完整序列上算** 。128K 上下文的 prefill 因此还是顶不住:

- 一次前向要对 12.8 万个 token 做完整的 Transformer 计算;
- **注意力的计算量随序列长度平方增长** ,128K 相比 8K 是 256 倍的浮点运算。分块实现不会把那张巨大的打分矩阵落地,所以显存不平方增长,**但计算量照样平方增长** ;
- 首 token 时延可能到几十秒。

前缀上下文并行(PCP)冲的就是这个:**把序列分到多组 GPU 上并行算 prefill 的注意力。**

### 1.72 PCP 怎么切:各算各的那段,但注意力要先把 K/V 拼回来

PCP 是 1.3 那个乘积式里的第三项,**它是真正占 GPU 的** 。字段注释把它的定位写得很准:它扩展进程规模,**但不增加 KV cache 的分片数** 。

一次前向分成两半:

```text
non-attention (FFN, norm):  each rank computes its own segment    段内无上下文依赖,不通信
attention:
  step 1  all-gather K/V across the PCP group                     Q 只有本段的,K/V 要完整序列
  step 2  local attention with a causal mask
  step 3  each rank stores only its own segment of KV cache       KV cache 仍按段分散存放
```

**非注意力模块完全不需要跨 rank 通信** ——它们逐 token,段内算完就行。注意力则必须先把 K/V 拼回完整序列,因为本段的查询要注意到它之前的所有 token。所以 PCP 的核心通信就是这一次 K/V 的 all-gather,通信量正比于「序列长度乘 hidden 除以 PCP」——每卡发自己那 1/PCP 段。

这里可以顺手对照 1.17 那个天花板:PCP 之所以对超长上下文有意义,正是因为**它切的是序列而不是头** ,不受 KV 头数的限制。

### 1.73 PCP 与 DCP 分管两个阶段

上下文并行有两个变体,分别管 prefill 和 decode,而且**可以同时用** :

| | 切什么 | 管哪个阶段 | 注意力怎么合 |
|---|---|---|---|
| PCP | 序列按段切 | prefill | 先 all-gather K/V,再本地算 |
| DCP | KV cache 按 token 交错切 | decode | 各算各段,再合并各段的结果与归一化因子 |

两者的分工很干净:prefill 时 PCP 让每个 rank 算一段序列、KV cache 按段落盘;decode 时 DCP 让每个 rank 持有交错的 KV,各自对自己那段做注意力,再把结果合起来。

### 1.74 PCP 的限制写在三层里,而且一层都不在配置里

这是本章第三处更正,而且**和 1.27 是完全同一个形状** ——约束的归属被写高了一层。

一个常见的说法是:PCP 与 DP 不兼容的检查在并行配置里。**基准上那里没有这条检查。** 它在**平台层** ,而且是**两处各写一遍**:CUDA 一处、ROCm 一处,连错误信息都各自带着平台名。

把三处更正并排看,模式就出来了:

| 约束 | 讲稿放在 | 实际在 | 写了几遍 |
|---|---|---|---|
| PP 关掉 MoE 的序列并行(1.27) | 并行配置的属性 | **模型实现** | 至少八处 |
| PCP 与 DP 不兼容 | 并行配置 | **平台层** | 两处 |
| MoE 序列并行的总开关(1.60) | — | 配置层给资格,**模型层再叠 PP 那道门槛** | — |

所以 **vLLM 的并行约束是分层的:配置层给全局资格,平台层与模型层再各自叠门槛。** 只查配置层会得出相反的结论 —— 这条教训在本章已经吃到第三次了。

限制本身也比通常说的多。除了与 DP 互斥、以及它会把 DCP 的取值限死在几个特定值上,还有一整层能力缺口写在 PCP 的执行期管理器里:**那一个文件里就有九处「尚未支持」** ,涵盖流水线并行、编码器-解码器模型、多模态输入、LoRA、推测解码等等。

还有一条范围上的事实值得记住:**PCP 目前只有 MLA 那条注意力路径接了** 。引用它的注意力代码只有 MLA 与稀疏 MLA 两个实现、MLA 的索引器,加上公共的后端基类与选择器;**分组查询注意力那条标准路径里没有 PCP 分支。** 所以它现在是一个为某一类模型准备的能力,不是通用开关。

### 1.75 PCP 的实测:加速比达不到理想的两倍

有一组公开的首 token 时延数据可以看出 PCP 的收益量级。**它来自昇腾硬件上的外部文档,不是本仓库的代码或测试能验证的** ——硬件、算子实现、互联带宽都与 NVIDIA 的卡不同,引它只为看趋势,不要当 GPU 上的预期值:

| 输入长度 | 无 PCP | 开 PCP | 加速比 |
|---|---|---|---|
| 32K | 5.1 s | 3.0 s | 1.7 倍 |
| 64K | 13.1 s | 8.9 s | 1.5 倍 |
| 120K | 33.9 s | 22.7 s | 1.5 倍 |

两件事值得注意:**加速比没达到 PCP=2 的理想 2 倍,而且随长度变长还略有下降。** 原因就在 1.72 那条通信量上 —— K/V 的 all-gather 正比于序列长度,**序列越长,这部分越吃掉并行收益** 。

这是一个通用形状:凡是「切开之后要拼回来」的并行,被切的那一维越大,拼回来的代价也越大,加速比就越够不着理想值。

### 1.76 TP 切不动 KV cache 的那一档

1.17 讲过 TP 对 KV cache 的天花板:切到 TP 等于 KV 头数就到头了,再往上 KV 头被复制。**DCP 冲的就是天花板之上那一段。**

复制有多浪费,取决于模型:

| 模型 | KV 头数 | TP=8 时 |
|---|---|---|
| 分组查询注意力(4 个 KV 头) | 4 | 每个 KV 头复制 2 份,**冗余 2 倍** |
| MLA(压成单一低秩潜向量) | 实际只有 1 | TP 无从按头切,**8 张卡持有完全相同的一份,冗余 8 倍** |

MLA 那一行是重点:它把 K/V 压成一个潜向量,**有效 KV 头数就是 1** ,所以 TP 一开就撞天花板。而这种冗余直接限制并发数 —— KV cache 占满显存,批大小上不去,吞吐就受限。

### 1.77 DCP:把冗余副本换成 token 分片

DCP 的想法一句话就够:**那些本来要重复复制的副本,换成不同 token 位置的分片。**

```text
without DCP (8 cards, 4 KV heads, 200K tokens):
  card 0: head 0, ALL tokens        card 1: head 0, ALL tokens     完全相同,冗余
  card 2: head 1, ALL tokens        card 3: head 1, ALL tokens     完全相同
  ...                                                              每卡 200K x 1 head

with DCP=2:
  card 0: head 0, tokens 0..99K     card 1: head 0, tokens 100K..  不同分片,不再冗余
  card 2: head 1, tokens 0..99K     card 3: head 1, tokens 100K..
  ...                                                              每卡 100K x 1 head
```

**冗余被消除,每卡 KV cache 直接减半。** 注意持有的头没变,变的只是每张卡负责哪些 token 位置。

切法是**交错的,不是前半段后半段** ——第 1 个 token 给 0 号 rank、第 2 个给 1 号、第 3 个又回到 0 号。这样安排的好处在 decode 上很实际:**新生成的 token 自然而然轮流落到不同 rank** ,不需要任何再平衡。

### 1.78 DCP 的注意力:各算各段,再用对数和指数合回来

KV 被切开之后,注意力就没法一次算完了。每个 rank 只看到一段 KV,算出来的是**局部归一化**的结果,得想办法合成全局正确的答案。

```text
step 1  each rank gets the full Q                          decode 时 Q 只有一个 token,量极小
step 2  local attention -> partial_out + lse per rank       lse 记录本段 exp 求和的量级
step 3  all-gather the LSE across the DCP group             只传标量,不传 output
step 4  correct each partial locally with the global LSE    纯本地计算,不通信
step 5  reduce-scatter the output along the head dim        求和之后按头切回各 rank
```

最后一步的输出形状是「每卡拿到部分头」,**正好接上后面输出投影的行切输入** ——两件事天然衔接,不需要额外的重排。

### 1.79 为什么只传对数和指数就够

这是 DCP 里最漂亮的一步,而且理由是纯数学的。

softmax 的分母是所有位置的指数之和。每个 rank 只看到一段,于是它算出的是**局部归一化的结果**,外加一个**局部分母的对数** 。全局分母只需要把各 rank 的这个标量汇总一下就能算出来,然后各 rank 把自己的结果乘上一个修正系数,加起来就是全局正确的答案。

**关键在于修正系数是标量。** 重量级的那个输出张量根本不需要广播 —— 它只在最后一步的 reduce-scatter 里走一遍。所以第 3 步的通信量只有「DCP 数乘批大小乘头数」个标量,**比输出张量小了一个头维的倍数** ,头维 128 时就是小两个数量级。

这正是**分块 softmax 那套数学搬到跨卡场景**的结果 —— 同一个把注意力分块算、再用对数和指数合并的技巧,05 章讲注意力后端时已经在单卡内部见过一次。

### 1.80 分组查询注意力与 MLA 的 DCP 不是一条路

两者的 DCP 上限与约束完全不同,而且**MLA 那条路把前者的整套校验都跳过了** 。

| | 分组查询注意力 | MLA |
|---|---|---|
| 冗余倍数 | TP 除以 KV 头数 | TP 倍,全部冗余 |
| DCP 最大值 | **TP 整除 KV 头数** | **可以一直开到等于 TP** |
| 额外约束 | TP 必须严格大于 KV 头数;每个 KV 头对应的查询头数要能被 DCP 整除 | 只要求 TP 能被 DCP 整除 |
| 做法 | 先按头切,剩余的冗余再按 token 切 | 潜向量直接按 token 切,算注意力时再上投影 |

分组查询注意力那三条约束为什么长这样,其实都是从「DCP 只能吃掉冗余」推出来的:

- **能切的份数上限就是冗余度** 。TP 恰好等于 KV 头数时一份重复都没有,DCP 无从下手 —— 所以代码直接要求 TP 严格大于 KV 头数。
- **同一个 KV 头对应的那组查询头要能再均分下去** ,分不均就构造不出 kernel 需要的头布局。

MLA 走另一条路:**潜向量只有一份、不存在头冗余,直接按 token 维切** 。所以那套校验整体被一个「不是 MLA」的短路条件跳过了。各 rank 只存自己那段潜向量,算注意力时各自上投影重建自己需要的 K/V —— 因为有效 KV 头数是 1,可以一直切到 DCP 等于 TP。

### 1.81 DCP 的代价也是固定开销,所以它只管 decode

DCP 越大,KV cache 冗余越少、并发越多、吞吐越高。代价是每层注意力多两次集合通信。

但这两次都不贵:**对数和指数是标量,几乎不占带宽** ;reduce-scatter 搬的输出在 decode 时也只是每请求一个 token 的小张量。**所以 DCP 的通信代价主要是固定开销** ——多两个 kernel、两次 rank 同步,和 1.13 里那个 5 到 15 微秒的量级同级,不是带宽。

**这个权衡在 prefill 阶段就不成立了**:prefill 的查询有几千到几十万个 token,reduce-scatter 搬的不再是小张量,带宽项压上来了。

这正是为什么切 prefill 序列要另设 PCP 这个独立维度,**而 DCP 的名字里写着 decode** 。两个名字不是随手起的,它们标记的是「这个权衡在哪个阶段成立」。

### 1.82 四种切法各自的位置

到这里六种并行里的四种都讲完了,可以并排看清它们各自占的位置:

| | TP | SP | PCP | DCP |
|---|---|---|---|---|
| 切什么 | 权重(按 hidden 或头) | 层间激活(按序列) | prefill 的序列 | KV cache(按 token 位置交错) |
| 扩展进程规模? | 是 | **否**,复用 TP 的 rank | 是 | **否**,PCP=1 时复用 TP 的 rank |
| 适用阶段 | prefill 与 decode 都用 | prefill(token 多时才开) | **仅 prefill** | **仅 decode** |

最后一行是这张表的重点:**同样是切序列,PCP 和 DCP 分管两个阶段,而分界线就是 1.81 那个「带宽项还是固定开销说了算」。**

这四种加上 PP 与 DP 对 KV cache 各自的影响,在 4.6 有一张完整的表,这里不重复。

### 1.83 另一条路:用 all-to-all 替掉 reduce-scatter

上一节收口了 vLLM 真正实现的四种切法。收口之前还要补一笔:**这四种里的序列并行,还有一条 vLLM 没有走的路** ——它把通信量又压下去一大截,值得知道存在,也值得知道为什么这里没走。

1.58 那套 SP 在注意力之后用 reduce-scatter(求和加切分)。**另一条路是用 all-to-all 替代它** ——把「头维到序列维」的重排提前到输出投影之前做,于是根本不需要求和。

> 以下方案源自 DeepSpeed 的 Ulysses 序列并行。**它那一侧的实现不在本仓库,无法核验** ;能在本仓库核验的只有「vLLM 这边是什么样」——vLLM 走的是 reduce-scatter 那条路,**没有 all-to-all 版本的序列并行** 。

思路的差别在于输出投影的权重怎么放:

| | 标准做法 | 换成 all-to-all |
|---|---|---|
| 注意力之后 | 输出投影按 TP 切,得到部分和 | **先 all-to-all 做头维到序列维的重排** |
| 输出投影的权重 | 每卡 1/TP,所以必须求和 | **每卡一份完整的**,各算各的 |
| 需要求和吗 | 需要,用 reduce-scatter | **不需要** |

### 1.84 为什么 all-to-all 的通信量小四倍

理由干净得出乎意料:**两者搬的不是同一个东西。**

- reduce-scatter 搬的是**输出投影之后**的张量,宽度是 hidden;
- all-to-all 搬的是**输出投影之前**的注意力输出,宽度是「每卡的头数乘头维」。

而注意力输出的宽度**远小于 hidden** ——本例里是 1024 对 4096,天然小四倍。再叠加 int8 量化又砍一半,总共约八倍。

| 方案 | 通信模式 | 每卡发送 | 相对基线 |
|---|---|---|---|
| 标准 reduce-scatter | 集合归约 | 基线 | 1 倍 |
| bf16 的 all-to-all | 点对点 | 小四倍 | **0.25 倍** |
| int8 的 all-to-all | 点对点加一次极小的归约 | 再小一半 | **0.125 倍** |

还有一件容易误判的事:**输出投影的计算量两种方案完全相同** 。标准做法是每卡算「全部 token 乘 1/TP 的宽度」,换成 all-to-all 之后是每卡算「1/TP 的 token 乘完整宽度」——**浮点运算数一模一样** ,只是把切分从权重维挪到了 token 维。

### 1.85 vLLM 缺的是哪两块

这条路 vLLM 目前没走。缺的东西比想象中少:

| 缺的 | 状态 |
|---|---|
| 「数据加缩放因子一起传下去」的那种封装 | 本仓库里 grep 不到 |
| 注意力输出之后的量化与 all-to-all 的融合 kernel | 没有 |
| **输出投影不切 TP** | **已经有现成开关** ——线性层基类与列切层都接受一个禁用张量并行的参数 |

所以这是一个**零件齐了一半**的优化方向,不是从零开始 —— 那个禁用开关已经在,只是目前没有注意力路径去用它。

### 1.86 单个副本已经打满,还要更多吞吐

最后一种并行的痛点最简单:**前面五种都是为了「装得下」或者「算得快」,而当一个实例已经装得下、也跑满了,还要更多吞吐怎么办?**

数据并行(DP)的答案是加副本。每个副本是一个完全独立的引擎实例,处理各自的请求,**副本之间几乎不通信** 。

但它在 MoE 场景里扮演的角色远不止「加副本」这么简单,下面两节讲的就是这件事。

### 1.87 超大 MoE 为什么必须配 DP 才开得动 EP

先把 DeepSeek V3 的专家权重算清楚(hidden 7168、专家中间维 2048、每层 256 个路由专家、61 层里 58 层是 MoE):

| | 量 |
|---|---|
| 单个专家(单层) | 3 个矩阵,约 4400 万参数,FP8 约 44 MB |
| 全模型的路由专家 | 58 层乘 256 个乘 44 MB,**约 654 GB** |

**「256 个专家」是每层 256 个,不是全模型 256 个** ——这是最容易算错一个数量级的地方。654 GB 也就是 671B 总参数的绝大部分,注意力、共享专家、词嵌入加起来只占十几 B。

654 GB 意味着:

| 配置 | 每卡 MoE 权重 | 结果 |
|---|---|---|
| TP=8,专家并行规模 8 | 82 GB | **超过单卡显存,必然溢出** |
| TP=8 加 DP=4,专家并行规模 32 | **20 GB** | 装得下,还剩很多给 KV cache |

这就是超大 MoE 必须开 EP、而且往往要配 DP 的原因:**光靠 TP 把专家并行规模做大不够** ,因为 TP 同时受注意力头数与 all-reduce 延迟的约束,很难开到 32。**DP 是把那个规模顶上去的唯一实际手段。**

### 1.88 开了 EP 不等于就走 all-to-all

这是一条极容易记混的线,而 1.53 已经埋下了伏笔。**开了专家并行,专家确实整份分卡了,但通信未必走 dispatch 与 combine。**

| 配置 | 专家怎么放 | MoE 的通信 |
|---|---|---|
| 不开 EP | 每个专家按 TP 切碎 | all-reduce |
| 开 EP,但数据并行、前缀上下文并行、序列并行都是 1 | **整份分卡** | 仍然是 all-gather 加 reduce-scatter 那条路 |
| 开 EP,且三者之一大于 1 | 整份分卡 | **dispatch 与 combine 的 all-to-all** |

中间那一行是关键:**纯 TP 加 EP 的组合,专家已经整份分卡了,但走的不是 all-to-all** 。专用的 all-to-all kernel 有自己的额外条件。把「开了 EP」和「走 all-to-all」划等号,就会在纯 TP 加 EP 的部署上得出完全错误的通信模型。

### 1.89 哪部分权重会因 DP 而冗余

「显存只够放一份完整模型就不能开 DP」——这句话**只对非专家部分成立** 。要分清三类:

| | 开 DP 之后 |
|---|---|
| **专家权重** | **不冗余** 。专家并行规模等于 TP 乘 DP,专家在全部 GPU 上切一遍,每个专家仍然只有一份 —— 所以 DP 从 1 加到 4,每卡的 MoE 权重反而变成四分之一 |
| 注意力与稠密部分 | **按 DP 冗余** 。每个副本是独立的引擎实例,词嵌入、注意力、共享专家、归一化各存一份 |
| KV cache | **完全独立** ,各副本自己管自己的块池,前缀缓存也不跨副本共享 |

第一行反直觉但很重要:**对超大 MoE 来说,专家权重占绝大多数,所以 DP 加 EP 恰恰是把每卡显存压下来的手段** ,而不是加显存的手段。这也解释了 1.87 那张表 —— DP 从 1 到 4,每卡从 82 GB 掉到 20 GB。

### 1.90 低并发选 TP 加 EP,高并发选 DP 加 EP

同样是 8 张卡、同样开专家并行,两种摆法的结果差别很大,而核心区别在 **KV cache 容量**和**通信模式**这两项。

| | TP=8、DP=1 | TP=1、DP=8 |
|---|---|---|
| 注意力通信 | 每层一次 all-reduce | **无** ,每卡持完整注意力权重 |
| MoE 通信 | all-reduce(不走 all-to-all,见 1.88) | all-to-all |
| KV cache | 每卡持 KV 头数除以 TP;MLA 下**有效头数是 1,八卡全冗余** | **每卡独立,不冗余** |
| 批大小上限 | 低(KV cache 被冗余吃掉) | **高** |
| 单请求延迟 | **低** (all-reduce 走 NVLink,延迟极小) | 偏高(每卡要读完整的注意力权重) |
| 适合 | 低并发交互式,延迟敏感 | 高并发批处理,吞吐优先 |

把它写成一条判据:**TP 摊薄的是单请求的延迟,DP 放大的是能同时跑多少请求。** 低并发时批本来就小,KV cache 的冗余不是瓶颈,延迟说了算;高并发时批大小才是瓶颈,而 KV cache 的冗余直接压住它。

最后把整章的调参逻辑收成一条:

$$
\text{MoE 的 decode 吞吐} \approx \text{DP} \times \frac{\text{每副本批大小} \times \text{每步 token 数}}{\text{每 token 时延}}
$$

**DP 在分子上线性扩展,而每副本的批大小受 KV cache 容量限制。** 所以实际的最优策略是:**在显存允许的范围内把 DP 顶到最大,每个副本内部用 TP 加 EP 保证模型装得下、KV cache 够大。**

这条策略的方向可以参考,但**具体倍数不要当基准** ——它取决于模型、序列长度分布与互联拓扑,而且本节引用的对比结论来自外部材料,不是本仓库能验证的。

## Part 2|图解

Part 1 是沿着六条痛点线一种一种走下来的。这一部分只做 Part 1 做不到的那件事:**把它们放在同一张图里,看清各自占哪一段。** 单种并行的机制不在这里重复。

### 2.1 六种并行在一层 Transformer 里各占哪一段

```text
layer input  [B, seq, hidden]
  |
  |  <-- SP region: norm on [B, seq/N, hidden], then all-gather      沿序列切,复用 TP 的 rank
  |
  +-- QKV projection        column parallel                          TP 沿输出维切,不拼
  |
  +-- attention             local per card                           PCP 在此 all-gather K/V
  |                                                                  DCP 在此 all-gather LSE
  |
  +-- output projection     row parallel                             TP 的第一次归约点
  |     |
  |     +-- all-reduce, or reduce-scatter when SP is on
  |
  +-- FFN or MoE
  |     |
  |     +-- dense:  gate_up column -> act -> down row -> all-reduce   TP 的第二次归约点
  |     |
  |     +-- MoE:    gate -> dispatch -> experts -> combine            EP 的两次 all-to-all
  |
layer output [B, seq, hidden]

PP cuts here, between layers, and sends hidden states point to point.
DP wraps the whole thing: each replica runs its own copy of all of the above.
```

三件事从这张图上一眼可见,而分开看时容易漏:

- **TP 在一层里有两个归约点** ,注意力后一个、FFN 后一个 —— 1.12 那个「一层两次」就是指这两处。SP 做的事就是把这两处的 all-reduce 各拆成两半。
- **CP 的两个变体挂在同一个位置** (注意力内部),但挂的东西不同:PCP 拼 K/V,DCP 拼对数和指数。
- **PP 的切口不在层内,DP 的切口在整张图之外。** 这两种和其余四种根本不在同一个层次上 —— 这也是 1.3 那个乘积式里它们位置各异的原因。

### 2.2 同一个 MoE 层,三种实现的数据流

1.50 给了三种实现的对照表,1.88 给了「开了 EP 未必走 all-to-all」的判据。**这两件事放在一起最容易记混** ,所以在这里用同一组 token 走一遍。设 8 个专家、每 token 选 2 个、2 张卡:

```text
routing:  A -> e0, e3 (both on card 0)     B -> e1, e5 (card 0 + card 1)
          C -> e4, e7 (both on card 1)     D -> e2, e6 (card 0 + card 1)

way 3  all-to-all dispatch       EP on, DP > 1
  dispatch  card 0 -> card 1: B (for e5), D (for e6)
            card 1 -> card 0: B (for e1), D (for e2)
  compute   each card runs only the token-expert pairs routed to it      精准,零浪费
  combine   send results back,原卡按路由权重加权合并
  cost      2 all-to-all, 对齐补齐, 两次同步, 暴露负载不均衡

way 2  fused compute + all-reduce   EP on, DP = 1
  compute   card 0 runs ALL 4 tokens against its own e0..e3
            card 1 runs ALL 4 tokens against its own e4..e7
            非本卡的 token-expert 对被标记跳过, 那些位置留 0
  all-reduce  0 值不影响求和, 结果与 way 3 逐位相同
  cost      1 all-reduce, 有白算, 但每卡工作量完全相同, 无负载不均衡
```

两者输出**逐位相同** 。两种方式的代价结构 1.50 已经列过(通信次数、无效开销、负载不均衡三项),这里只补它没回答的那个问题:**代价明明更大,方式二凭什么在单机上更划算?**

答案在一个容易被忽略的前提上:**decode 是访存瓶颈,算力本来就有富余。** 方式二白算的那部分,花的是闲着的算力;方式三省下的计算,换来的却是两次同步加对齐补齐,而且把负载不均衡直接暴露在关键路径上。所以单机 NVLink 下方式二赢,跨节点时 all-reduce 的延迟劣势才让方式三翻盘 —— 这就是 1.88 那条判据的由来。

### 2.3 一个请求在 DP 加 TP 加 EP 下从头走到尾

```text
request arrives
  |
  +-- load balancer in the API process picks a replica                DP 的分发在这里
  |
  +-- replica k: its own EngineCore, scheduler, KV cache              各副本互不相干
        |
        +-- for each layer:
        |     attention   TP group of this replica, one all-reduce    TP 组只在副本内
        |     MoE         experts sharded across ALL replicas         EP 组跨全部副本
        |                 dispatch / combine span TP x DP cards
        |
        +-- sampling, output
```

这张图回答的是 1.4 埋下的那个问题:**同一批 GPU 在两个层里的身份不同。** 注意力看到的是「本副本的 TP 组」,MoE 看到的是「横跨全部副本的专家池」。副本之间在注意力上互不相干,在 MoE 上却是同一个池子的不同分片 —— 这正是专家并行规模等于 TP 乘 DP 的由来。

## Part 3|机制之外:源码里额外读到的

前两部分讲清了六种并行**应该怎么工作**,Part 4 讲**怎么用它们**。这一部分夹在中间,只放一类东西:照着源码读下来,**机制层面看不见、但真实存在的细节**。

前面讲过的机制,这里一概不重复。每条只答一件事:它是什么,以及不这么做会出什么事。

> 每条对应源码的哪个文件、哪个符号,见本项目的代码索引页,正文不写。

### 3.1 进程组是按维度分别建的

六种并行不是共用一个通信域。启动时每个 worker 会按配置**为每个维度各建一个进程组** ,之后各层按需要取用:注意力取张量并行组,段间传递取流水线并行组,MoE 取专家并行组,副本协调取数据并行组。

这解释了 1.3 那个乘积式的物理含义:**`world_size` 决定要建多大的通信域,而每个维度各自在这个域里切出自己的子组。** SP 与 DCP 不额外占卡,正是因为它们直接复用张量并行那个已经建好的组。

### 3.2 推理实际只用到三个通信原语里的一个

通信原语一共提供了四个封装:all-reduce、all-gather、reduce-scatter,外加一个 gather。**但纯 TP 的推理路径只用到 all-reduce 这一个。**

| 原语 | 谁在用 |
|---|---|
| all-reduce | 行切层的输出求和 —— 唯一一直在用的 |
| all-gather | 列切层默认不拼接,所以**用不到** |
| reduce-scatter | 只有开了序列并行才出现 |

这是一个很干净的旁证:**1.7 那个「切完不拼」的设计,直接让一个通信原语在主路径上失了业。** 而开启序列并行之后,后两个才被那个改写 pass 引进来。

### 3.3 序列并行这个 pass 自己不提速,它是给后面的融合铺路

这是本章读源码读到的最重要的一条,而且它**改变了对整个序列并行的定位** 。

那个改写 pass 的类文档开门见山写着:**这个 pass 本身不直接带来性能提升,它是在为后续的融合铺路** ——具体点名了两种,矩阵乘与 reduce-scatter 的融合、all-gather 与矩阵乘的融合。

对照 1.64 的账就完全对得上:通信总量不变、计算几乎不变、kernel 数还翻倍。**单看这个 pass 本身,它是亏的。** 它的价值全在「拆开之后,原本嵌不进去的东西现在能嵌进去了」——1.68 的三种融合是第一批收益,而源码注释指出的那两种更彻底的融合还在后面。

所以对序列并行的准确描述不是「一种省显存的并行」,而是:**它把一个原子的集合通信拆成两段可优化的通信,自己不赚钱,赚钱的是后面接上来的东西。**

### 3.4 它只在整图模式下能用

这个 pass 有一条硬限制,而且理由很具体:**只支持整图编译,分段编译不支持。**

原因是它**把残差张量沿 TP 切开了** 。分段编译下,各段的边界处形状要对得上,而残差的形状在替换之后变了,**边界处就会形状不匹配** 。

这条和 06 章 1.20 那个「哪些算子能录进图」是同一类约束的两面:那边问的是「形状固不固定得下来」,这边是「形状被改了之后,分段的边界还对不对得上」。

### 3.5 从图末尾往前扫描,中间会经过一个语义错误的状态

这是整个 pass 里最精巧、也最容易看漏的一处。

替换是**从图的最后一层开始往前做**的。每替换一层,就在那一层插入一个对残差的切片。为什么必须倒着来:

```text
replace layer 79 first:  its residual output shrinks to [B, seq/N, hidden]
  layer 78 is not replaced yet, so its residual is still [B, seq, hidden]
  the slice inserted at layer 79 is therefore correct

then replace layer 78:   its residual output shrinks too
  now the slice inserted earlier is out of bounds for rank > 0
```

也就是说,**替换过程中图会经过一个语义上错误的中间状态** ——那些切片对非零号 rank 来说下标越界了。

它之所以安全,靠的是两件事,而源码注释把它们都写明了:**这个中间状态的图从来不会被执行** ;而且紧跟着会跑一个消除 no-op 的 pass,**按符号形状相等(输入形状等于输出形状)把这些切片清掉** ,然后才编译。

这是一个很值得记住的设计形态:**允许中间状态不自洽,靠「它不会被执行」加「下一道 pass 会清理」来保证正确性。** 换成正着扫描就得额外维护「这一层的残差已经缩过没有」,复杂得多。

### 3.6 六个模式类,以及量化档省的到底是哪一段

六个模式是「首层与中间层」乘以「三种精度」:

| | 首层 | 中间层 |
|---|---|---|
| 区别 | 归一化的输入**没有**残差相加(第一层的残差就是词嵌入) | 归一化的输入**有**残差相加,而且两者被融合成一个算子 |
| bf16 | 匹配 all-reduce 接归一化 | 匹配 all-reduce 接「残差加归一化」 |
| FP8 / NVFP4 | 上面再接一个量化 | 同左 |

把量化档省下的通信量按一份完整张量归一化算(8 卡):

| 量化档 | reduce-scatter 腿 | all-gather 腿 | 合计 | 相对纯 all-reduce |
|---|---|---|---|---|
| 无(bf16) | 0.875 | 0.875 | 1.75 | 1.00 倍 |
| FP8 | 0.875 | 0.4375 | 1.3125 | **0.75 倍** |
| NVFP4 | 0.875 | 0.219 | 1.094 | **0.625 倍** |

**最多把整层通信压到 62.5%** ,1.70 那条结论在这里换个口径又对上一次:**reduce-scatter 那一半是省不掉的地板。**

### 3.7 什么时候开序列并行,是按设备能力查表算出来的

阈值不是一个常数,是算出来的:

$$
\text{最小 token 数} = \frac{\text{每卡最小字节数} \times \text{TP} \times \text{MiB}}{\text{hidden} \times \text{元素字节数}}
$$

而公式里那个「每卡最小字节数」按平台分档:某类加速器写死一组固定值,CUDA 按设备能力查两张表(hidden 的下限与每卡字节数的下限),**查不到就直接返回空,表示这台设备上不开** 。hidden 不达标同样返回空。

有一个细节值得记一笔:**Blackwell 的各个变体被折叠成同一个策略桶** ,不按具体型号分别配。这是一种务实的取舍 —— 同代硬件的取舍点差不多,分太细反而难维护。

### 3.8 数据并行的协调靠一个布尔量,不是请求数

最后一条是需要更正的地方,而且错在两个维度上。

一个常见的说法是:各副本通过 all-reduce **同步「全局未完成请求数」,每 32 步一次** 。基准上两处都不是:

| | 常见说法 | 基准实际 |
|---|---|---|
| 同步什么 | 未完成请求**数** | **一个布尔量** ——「还有没有未完成的」。注释明写这是一次或运算,在整数上用取最大实现 |
| 多久一次 | 硬编码 32 步 | **一个配置项,默认 16 步** 。字段注释还提醒:这个值必须在各副本之间一致 |

「同步的是有没有而不是有多少」这个区分不是抠字眼 —— 副本之间**根本不需要知道别人有多少请求** ,它们只需要知道「是不是所有人都空了」,好一起进入等待。用布尔量做或运算,一个 32 位整数就够,而且语义上不会诱使人去做「按负载再平衡」这类它并不支持的事。

基准上还有一个合并版本:**把「还有没有未完成」和「有没有待暂停」两个布尔量塞进一个双元素张量,一次求和的 all-reduce 同时同步两件事** ——又一次「能合成一次通信就不做两次」。

还有一条硬约束是常见说法里完全没有的:**数据并行的引擎进程断言模型必须是 MoE** ,断言信息直白写着它只应该用于 MoE 模型。这一条直接印证了 1.87 —— 在 vLLM 这条路径上,**数据并行本来就是为超大 MoE 准备的**,不是一个通用的加副本手段。

### 3.9 三种执行器,以及它们和并行维度的关系

worker 怎么起,由三种执行器分工,而**选哪一种只看「卡在不在一个进程、机器在不在一起」** ,和用了哪几种并行无关:

| 执行器 | 用在哪 |
|---|---|
| 单进程执行器 | 单 GPU,worker 就在引擎进程里 |
| 多进程执行器 | 单机多卡 |
| Ray 执行器 | 多节点 |

单进程执行器还有一个子类,用在**外部启动器**那种模式下(1.3 提过的那一档)—— 所有 rank 由外面统一拉起,vLLM 自己不负责起进程。这也解释了 1.3 那条例外为什么只在这种模式下成立:**只有外部把全部进程拉齐了,数据并行才会被乘进单个引擎的进程规模。**

流水线并行对执行器没有额外要求,它只是让引擎把 step 函数从普通版本换成**带批次队列的版本** ——两者在同一个字段上二选一,建了队列就换,没建就不换。1.23 说的那套机制在代码里就是这一行三元表达式。

### 3.10 MoE 的并行配置是一个对象,不是几个散落的开关

本章反复出现的那几个量 —— TP、PCP、DP、EP、SP 的规模与序号、专家并行开没开、用哪个 all-to-all 后端、要不要专家负载均衡 —— **在代码里是同一个配置对象上的字段** ,而不是分散在各处的独立开关。

那几条判据也都是这个对象上的属性,**层层依赖** :

```text
is_sequence_parallel     = sp_size > 1
use_all2all_kernels      = use_ep AND (dp > 1 OR pcp > 1 OR is_sequence_parallel)
use_deepep_ht_kernels    = use_all2all_kernels AND backend == "deepep_high_throughput"
```

这个结构解释了 1.88 那条最容易记混的判据为什么长成那样:**「开了 EP」只是第一层,「走不走 all-to-all」是第二层,「走哪个 all-to-all 后端」是第三层。** 三层各有各的条件,不是一个开关管到底。

有一处需要留意:**这几个属性名在同一个文件里各有第二处** ,挂在另一个类上。更新基准时两处都要核 —— 这已经是本章第三次遇到「同名的东西有两份」了(1.27 的模型层门槛、1.74 的平台层校验)。

## Part 4|选型与决策

前三部分讲的是这六种并行怎么造的。这一部分讲怎么用:哪个指标被什么卡住、参数往哪边拧、出了问题先怀疑什么。

**本部分的耗时与显存数字都是量级参考,不是本仓库实测。** 凡是引自外部材料的,单独标注。

### 4.1 三个指标分别被什么卡住

| 指标 | 瓶颈性质 | 被哪种并行影响 |
|---|---|---|
| 首 token 时延 | prefill,算力瓶颈,序列长 | TP 与 EP 的计算加速,对上它们的通信开销 |
| 每 token 时延 | decode,访存瓶颈,每步一个 token | TP 摊薄权重读取,对上 all-reduce 的固定开销 |
| 吞吐 | GPU 利用率乘副本数 | DP 线性扩展,乘上单副本的效率 |

三行的瓶颈性质各不相同,所以**同一个参数在三个指标上的方向可以是相反的** 。下面两节把 prefill 与 decode 各算一遍。

### 4.2 prefill:TP 的边际收益递减,而且是结构性的

prefill 是算力瓶颈。TP 开大,计算按 $1/N$ 降 —— 但通信**不降反升** 。

关键在 1.13 那个环形 all-reduce 的系数 $\frac{2(N-1)}{N}$:**它随 N 上升、趋近 2,不是下降。** 每张卡的出口带宽是固定的,所以单次 all-reduce 的时间随 TP **略微变慢** 。

以 70B、批 32、序列 4096、bf16、每卡有效算力 400 TFLOPS 为例(量级参考):

| TP | 计算 | 通信(160 次) | 端到端 | 通信占比 |
|---|---|---|---|---|
| 2 | 23 s | 0.58 s | 23.6 s | 2.5% |
| 4 | 11.5 s | 0.86 s | 12.4 s | 7.5% |
| 8 | 5.7 s | 1.0 s | 6.7 s | **18%** |

TP 从 2 到 8,卡数翻了四倍,端到端只快了 **3.5 倍而不是 4 倍** 。

这里有一个很容易犯的错:**别拿 23 除以 5.7 得出 4 倍** ——那是纯计算时间的比值,恰好等于理想值,因为它**把通信整项漏掉了** 。折损正是通信贡献的那部分。

而且序列越长,那个待搬的张量越大,折损越明显。**这正是长 prompt 场景要引入 PCP 的原因 —— 换一个维度切序列,而不是继续加 TP。**

### 4.3 decode:TP 更划算,但「通信可忽略」是个误解

decode 是访存瓶颈,瓶颈在读权重。TP 开大,每卡只读 $1/N$ 的权重,访存时间近乎线性下降。以 70B、bf16(权重 140 GB)、显存带宽约 3 TB/s 为例:

| TP | 每步访存下限 | 通信(160 次,取 1.6 ms) | 通信占比 |
|---|---|---|---|
| 2 | 24 ms | 1.6 ms | 6.7% |
| 4 | 12 ms | 1.6 ms | 13% |
| 8 | 6 ms | 1.6 ms | **27%** |

端到端从 TP=2 到 TP=8 是 **3.4 倍,不是纯访存比的 4 倍** 。

**「decode 的通信可以忽略」是个误解。** 字节数确实小到带宽不成问题(1.13 算过,一次 512 KB),**可是 160 次集合通信的固定开销是一个与批大小、序列长度都无关的常数** ——访存时间被 TP 压得越小,这份常数的相对占比就越难看。

这里和 1.13 那个「占 3% 到 8%」的口径要对齐一下,两者并不矛盾:**分母不同。** 1.13 除的是一步 20 到 50 ms 的笼统前向时间,这一节除的是被 TP 压缩之后的访存下限。**TP 越大,同一份固定开销对着越小的分母,占比自然越难看** ——这恰恰是本节要说的那件事。

这正是 1.14 那件事的动机:**vLLM 为 8 MB 以下的 message 自己写 all-reduce,要优化的是延迟,不是带宽。** 两节合起来看,1.14 的存在理由到这里才完整。

### 4.4 EP 的通信量不能和 TP 的直接比

有一个隐藏的因子容易漏:**dispatch 时每个 token 的隐状态会被复制 $\text{top}_k$ 份分别发出去** 。所以 MoE 单层的通信量相对 TP 的 all-reduce,大约是:

$$
\frac{\text{top}_k}{2(M-1)/M} \quad \text{倍}
$$

| 模型 | 倍数 |
|---|---|
| Mixtral(每 token 选 2、EP=8) | 约 1.1 倍,与 TP 相当 |
| DeepSeek V3(每 token 选 8、EP=32) | **约 4 倍** |

**激活数越大,EP 的通信越重。** 但两件事把账拉回来:EP 只发生在 MoE 层(V3 是 61 层里的 58 层),而且它换来的是专家权重整份分卡 —— 也就是 1.87 那笔从 82 GB 降到 20 GB 的账。

### 4.5 P 和 D 可以用不同的并行策略

PD 分离时两侧是独立的副本组,各自加载权重、各自配置并行度,**KV cache 按请求的块传输,两边的配置不需要一致** 。这就给了一个机会:按各自的瓶颈分别配。

先把权重拆成两块,因为它们**被切的方式完全不同**(以 671B 的 MoE 为例,九比一的拆分是量级估计):

| | 量 | 怎么切 |
|---|---|---|
| 路由专家 | 约 600B | 被 EP 切,规模等于 TP 乘 DP 乘 PCP |
| 注意力、稠密层、共享专家、词嵌入 | 约 70B | 被 TP 切,**在 DP 组之间复制** |

于是在 16 张卡上:

| 配置 | 专家部分 | 非专家部分 | 每卡合计 |
|---|---|---|---|
| TP=8、DP=2 | 37.5B | 8.8B | 约 93 GB |
| TP=4、DP=4 | 37.5B | 17.5B | 约 110 GB |

**两种配置的专家并行规模都是 16,所以专家那一块每卡占用完全相同。** 差别全在非专家那一块 —— TP 越小,它被切得越少,每卡装的越多。

由此得出 P 与 D 该怎么配:

| | 主导代价 | 倾向 | 理由 |
|---|---|---|---|
| P 侧 | 算力瓶颈,all-reduce 的带宽项随序列长度线性增长 | **TP 偏小、DP 偏大** | 4.2 算过 TP=8 时通信占比已到 18%;缩小 TP 能压住这一项,而专家并行规模不变,MoE 的算力分散度不受影响 |
| D 侧 | 访存瓶颈,通信是固定开销而非带宽 | **TP 偏大** | 每卡权重随 TP 增大而降 —— 上表里 TP=8 比 TP=4 每卡少 17 GB,按 3 TB/s 算是每步少约 5.7 ms |

这张表是全章最实用的一处:**同一个模型、同样的总卡数,P 和 D 的最优 TP 方向相反,而理由就是 4.2 与 4.3 那两条瓶颈性质。**

### 4.6 六种并行对 KV cache 的影响各不相同

KV cache 是显存的另一大头,而它的容量**直接决定最大并发数,进而决定吞吐** 。六种并行对它的影响差别很大:

| 并行 | 每卡 KV cache | 总容量 | 说明 |
|---|---|---|---|
| TP=N | 总量除以「N 与 KV 头数的较小者」 | 不变 | 线性提升并发,**但到 KV 头数就到顶**(1.17) |
| PP=N | 总量除以 N | 不变 | 同样线性,**而且没有 KV 头数那道天花板** |
| DP=N | 每副本不变 | **乘以 N** | 总容量涨,但**不共享**,前缀缓存也不跨副本 |
| DCP=N | 在 TP 之后再除以 N | 不变 | 专治 TP 撞到天花板之后的那些冗余副本 |
| EP=M | **不变** | 不变 | 不切 KV,但腾出的权重显存会被算成可用显存分给 KV cache |
| SP | 无直接影响 | 不变 | 间接:省下分片区的激活,可以换更大的批 |

三件事值得单独记:

- **PP 与 TP 省的是不同的维度** ,可以叠乘;而 TP 有 KV 头数的天花板,PP 没有。
- **EP 那一行的「不变」容易误读。** 它确实不切 KV,但把每卡 MoE 权重从「总量除以 TP」压到「总量除以 TP 乘 DP」,**省下的几十 GB 会被显存探测算成可用显存分给 KV cache** ——所以并发确实会涨,只是这条收益走的是「权重让位」而不是「KV 分片」。
- **DP 的总容量涨但不共享** ,所以负载均衡必须做粘性路由(同一请求始终回到同一副本),否则前缀缓存就白建了。

### 4.7 选型:先定总卡数怎么分,专家并行是被决定的

把整章收成一棵决策树:

```text
dense model?
  yes -> only TP / PP / DP
    fits on one card        -> TP=1, add DP for throughput
    fits within one node    -> TP=8; latency first, or TP=2..4 + DP for throughput
    does not fit            -> TP=8 + PP=2

  no (MoE) -> decide how TP and DP split the total cards; EP follows from them
    few experts, all fit per card   -> do not enable EP, experts go through TP
    many experts                    -> enable EP, then pick the TP / DP ratio:
        TPOT or memory first        -> larger TP        每卡权重最小
        TTFT first                  -> smaller TP       all-reduce 的带宽项更小
        throughput first            -> smaller TP, larger DP

long prompt bound on TTFT   -> consider PCP    仅 MLA 路径, 与 DP 互斥
long decode bound on KV     -> consider DCP    GQA 有 TP 除以 KV 头数的上限
single replica saturated    -> add DP
```

MoE 那一支有一句必须记住:**专家并行规模等于 TP 乘 DP 乘 PCP,它不是一个独立旋钮。**

所以「把 EP 开大」的真实含义只有两种:**把卡从 TP 挪给 DP,或者干脆加总卡数。** 想清楚这一点,才不会写出「TP=8 加 EP=2」这种把专家并行当独立并行度的配置。

一个具体的例子:16 张卡上,TP=8 配 DP=2 与 TP=4 配 DP=4,**专家并行规模都是 16** ,区别只在 4.5 那张表里的非专家权重与 TP 组的大小。

### 4.8 关键参数

| 参数 | 默认 | 作用 |
|---|---|---|
| 张量并行度 | 1 | 切权重;受注意力头数与 all-reduce 延迟双重约束 |
| 流水线并行度 | 1 | 按层分段;只在 TP 用满整机仍装不下时才用 |
| 数据并行度 | 1 | 加副本;在 vLLM 这条路径上**断言模型必须是 MoE**(3.8) |
| 专家并行开关 | 关 | **不是并行度,是开关** ;规模由 TP 乘 DP 乘 PCP 决定 |
| 前缀上下文并行度 | 1 | 切 prefill 序列;仅 MLA 路径,与 DP 互斥 |
| 解码上下文并行度 | 1 | 切 KV cache;复用 TP 的 rank,分组查询注意力有上限 |
| 双批重叠开关 | 关 | 通信与计算重叠;两个 token 阈值各自把关 |
| 执行后端 | 多进程 | 多进程或 Ray |

序列并行**不在这张表里** ,它没有独立的并行度参数,开关在编译配置里且自动判定(1.57)。这本身就是一条容易找错地方的事。

### 4.9 常见误区

每条都是容易想当然、但源码给出相反答案的地方。

| 误区 | 真相 |
|---|---|
| TP 越大吞吐越高 | 不。计算按 $1/N$ 降,但 all-reduce 的每卡收发量按 $\frac{2(N-1)}{N}$ **微升** ,通信占比随 TP 恶化(4.2:TP=8 时已到 18%) |
| decode 的通信可以忽略 | 字节数可以,**次数不行** 。160 次集合通信的固定开销与批大小、序列长度无关,TP 越大占比越难看(4.3:TP=8 时约 27%) |
| 专家并行是一个可以单独调大的并行度 | 不是。**规模等于 TP 乘 DP 乘 PCP** ,「开大 EP」只能靠把卡从 TP 挪给 DP、或者加总卡数 |
| 开了专家并行就一定走 all-to-all | 不。数据并行为 1 且没开序列并行与前缀上下文并行时,走的是融合计算加一次 all-reduce(1.88) |
| 开了专家并行能省同样卡数下的显存 | 不。把每个专家切 $1/\text{TP}$ 与拿 $\text{TP}$ 分之一个完整专家,**字节数完全相同** 。EP 省的是 GEMM 的完整性与跨节点扩展的空间(1.51) |
| TP 能一直把 KV cache 切下去 | 不。切到等于 KV 头数就到顶,再往上 KV 头被**复制** ,显存白花。MLA 的有效 KV 头数是 1,等于完全切不动(1.17) |
| DCP 想开多大开多大 | 分组查询注意力有硬上限,还要求 TP 严格大于 KV 头数、且每 KV 头对应的查询头数能被 DCP 整除。**只有 MLA 能开到等于 TP**(1.80) |
| DCP 的通信量很大 | decode 阶段不大 —— 跨卡只传对数和指数这个标量。**真正的代价是多两次集合通信的固定开销** 。prefill 阶段才不成立,那里该用 PCP(1.81) |
| PCP 是通用能力 | 目前**只有 MLA 那条注意力路径接了** ,标准的分组查询注意力后端里没有 PCP 分支;而且它与 DP 互斥,还有一整层尚未支持的能力缺口(1.74) |
| 序列并行省通信 | **一个字节没省** 。它把一次 all-reduce 拆成两轮,总量相同、kernel 数翻倍。省的是归一化那一段的激活;而它真正的价值是**为后续融合铺路**,源码注释明写它自己不直接提速(3.3) |
| 量化能把序列并行的通信压到几分之一 | 最多压到 62.5%。**reduce-scatter 那一半必须保持高精度**(跨卡求和会累积舍入误差),省下的只有 all-gather 那条腿(1.70、3.6) |
| 显存只够放一份完整模型就不能开 DP | **只对非专家部分成立** 。对超大 MoE 来说专家权重占绝大多数,而它在 EP 下不冗余 —— DP 加 EP 恰恰是把每卡显存压下来的手段(1.89) |
| 别拿 600 GB/s 算点对点 | 那是双向聚合带宽,`send/recv` 只走单向,用它算 PP 的段间传输会乐观一倍(1.21) |
| 开 PP 会关掉 MoE 的序列并行,约束在并行配置里 | 结论对,**位置错** 。配置层那个属性只有四条,一条都没提 PP;真正的约束写在每个模型自己的实现里,至少八处各写一遍(1.27) |
| 数据并行靠同步「全局未完成请求数」来协调 | 同步的是**一个布尔量**(还有没有),用或运算聚合;周期是**配置项默认 16 步** ,不是硬编码的 32(3.8) |
