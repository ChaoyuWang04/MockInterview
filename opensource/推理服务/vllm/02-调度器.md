## Part 1|原理

### 1.1 朴素批处理的痛点

最朴素的 LLM 服务批处理是 **static batching(静态批处理)** :把多个请求拼成一个 batch,等 batch 内 **所有请求都生成完** 才接收下一批。

假设 batch 大小为 4,4 个请求分别生成 10 / 100 / 1000 / 100 个 token:

```text
朴素批处理时间线(batch=4):
t=0      请求1(p10)    请求2(p100)   请求3(p1000)  请求4(p100)   ← prefill
t=10     [1✓]           2 decode      3 decode      4 decode     ← 请求1 完成
t=100    [1✓ 等待]      [2✓]          3 decode      4 decode     ← 请求2 完成
t=100    [1✓ 等待]      [2✓ 等待]     3 decode      [4✓]         ← 请求4 完成
t=1000   [1✓ 等待]      [2✓ 等待]     3 decode  ←── 请求3 拖累整个 batch
t=1000   batch 完成,接收新 batch
```

问题:

1. **GPU 空转** :请求 1、2、4 完成后,对应的 batch slot 空置,GPU 算力浪费。
2. **延迟尖峰** :新到的请求必须等整个 batch 完成,最坏情况等 1000 个 token 的时间。
3. **显存浪费** :已完成的请求仍占着 KV cache 空间,直到整个 batch 结束。

> 🖼️ 占位:静态批处理与连续批处理的 slot 占用对比。回答「同样四条请求,两种调度下每个 slot 在各时刻是在算还是空着」。

### 1.2 连续批处理:iteration-level scheduling(迭代级调度)

**连续批处理** 的核心思想: **在每个 decode step(每生成一个 token)都重新决策** ——哪些请求继续、哪些请求结束、哪些新请求加进来。

```text
连续批处理时间线(每 step 重新组 batch):
t=0      prefill: [1,2,3,4]
t=10     decode:  [2,3,4,5]     ← 请求1 完成,请求5 加入
t=100    decode:  [3,4,5,6]     ← 请求2 完成,请求6 加入
t=100    decode:  [3,5,6,7]     ← 请求4 完成,请求7 加入
t=200    decode:  [3,5,6,7]     ← 等请求3 慢慢生成,但其他 slot 一直满载
```

收益:

1. **GPU 满载** :每 step 都尽量填满 batch,吞吐接近理论上限。
2. **低延迟** :新请求只要 batch 有空 slot 就立即加入,无需等待。
3. **显存高效** :完成的请求立即释放 KV cache,腾空间给新请求。

**实现关键** :必须有 PagedAttention。只有 KV cache 按 block 灵活分配与释放,才能支持请求的动态进出。 **连续批处理是建立在 PagedAttention 之上的。**

### 1.3 Chunked Prefill:解决 prefill 阻塞 decode

朴素的连续批处理仍有一个问题: **prefill 和 decode 不能同 batch** 。原因:

- prefill 是 **compute-bound(计算密集)** :处理几千个 prompt token,单 step 耗时 50 到 500 ms。
- decode 是 **memory-bound(访存密集)** :每 step 只处理 1 个 token,但需要扫描所有 KV cache,单 step 耗时 5 到 50 ms。

如果 prefill 和 decode 严格串行(即一个 step 里只做其中一件事):

```text
朴素串行(prefill 阻塞 decode):
step N:    prefill(请求A, prompt=4000 tokens) —— 500ms
step N+1:  decode(所有 running 请求) —— 20ms   ←── decode 等 prefill 完才能跑
step N+2:  decode —— 20ms
...
step N+30: prefill(请求B, prompt=3000) —— 400ms  ←── 又阻塞
step N+31: decode —— 20ms
```

问题:decode 的 TPOT(time per output token)出现周期性尖峰,从 20 ms 飙到 500 ms,用户体验差。本节所有耗时都是量级参考,不是本仓库实测。

#### 1.3.1 Chunked prefill 的做法

把长 prompt 切成小块(chunk),每 step 只处理一个 chunk(如 512 token):

```text
Chunked prefill(prefill 分块,与 decode 同 batch):
step N:    [chunk1 of 请求A (512 tokens)] + [decode 所有 running]  —— 50ms
step N+1:  [chunk2 of 请求A (512 tokens)] + [decode 所有 running]  —— 50ms
...
step N+8:  [chunk8 of 请求A (剩余 384 tokens)] + [decode]          —— 50ms
                                             ←── 请求A 进入 decode
```

收益:

1. **TPOT 平滑** :每个 step 的耗时基本恒定(chunk 计算量加 decode 计算量),无尖峰。
2. **prefill 与 decode 共享 step** :同一次 model forward 同时处理 prefill chunk 和 decode token,GPU 利用率最大化。
3. **TTFT 略增但可接受** :长 prompt 的首 token 延迟从 500 ms 变成 chunk 数乘以 50 ms 约等于 400 ms(差不多),但所有其他请求的 TPOT 不再尖峰。

#### 1.3.2 数学:最优 chunk size

设:

- $T_{\text{prefill}}(n)$:处理 $n$ 个 prefill token 的耗时(约 $O(n)$,因为 prefill 是 compute-bound)
- $T_{\text{decode}}(b)$:batch size $b$ 时 decode 一个 token 的耗时(约 $O(b)$,访存带宽限制)
- $N$:prompt 总长度
- $c$:chunk size

朴素的串行:$T^{\text{naive}}_{\text{total}} = T_{\text{prefill}}(N) + k \cdot T_{\text{decode}}(b)$($k$ 为该 prompt 占用期间 decode 的总步数)

Chunked:把 prefill 切成 $\lceil N/c \rceil$ 块,每步 $T_{\text{step}} \approx T_{\text{prefill}}(c) + T_{\text{decode}}(b)$,总时间 $\lceil N/c \rceil \cdot T_{\text{step}}$。

最优 $c$ 在 **prefill 和 decode 计算量均衡** 时取得:

$$
c^{*} \approx \frac{T_{\text{decode}}(b)}{\alpha}
$$

其中 $\alpha$ 是 prefill 的「每 token 计算时间」。实践中 vLLM 的 `max_num_batched_tokens` 默认 2048,意味着 chunk 加上所有 decode token 之和不超过 2048。

#### 1.3.3 Chunked Prefill 的完整作用总结

Chunked prefill 不只是「平滑 TPOT」,它同时解决了 **5 个独立问题** ,每个都有具体的数学或工程依据。

**作用 1:TPOT 平滑(消除 decode 延迟尖峰)**

- 问题:朴素做法下 prefill 一次算完(50 到 500 ms),期间所有 decode 请求等待,TPOT 出现周期性尖峰。
- 解决:切 chunk 后每 step 耗时恒定(chunk 计算加 decode 计算),无尖峰。

```text
朴素:    TPOT = [20ms, 20ms, 500ms!!!, 20ms, 20ms, 400ms!!!, 20ms]
Chunked: TPOT = [50ms, 50ms, 50ms, 50ms, 50ms, 50ms, 50ms]
```

**作用 2:防止 KV Cache OOM(逐 chunk 分配而非一次性分配)**

问题:朴素做法下,一个 100K token 的长 prompt 需要一次性分配 100K token 的 KV cache block。如果当前空闲 block 不够(即使只差一点点),整个请求无法调度,只能等——其他请求释放 KV 后才能开始。

```text
朴素(无 chunked prefill):
  请求 R: prompt = 100K token
  需要 KV cache: 100K × 320KB/token = 32GB
  当前空闲: 20GB
  → 不够! R 无法调度,在 waiting 队列等待
  → 必须等其他请求完成释放足够 KV,R 才能开始
  → 如果不断有新短请求插入,R 可能永远等不到(饥饿)
```

> 全文的「每 token KV」口径:以 Llama-3-70B(80 层、8 个 KV head、head_dim=128、FP16)为例,一个 token 的 KV 总量为 `2(K+V) × 8(kv_head) × 128(head_dim) × 2(FP16) × 80(层)` 等于 320KB。这是 **整个模型所有卡合计** 的量。TP=8 时每张卡只存 1 个 kv_head,单卡分摊 320KB 除以 8 等于 40KB/token。后文凡是「32GB / 2.5GB」这类总量都按 320KB 口径,凡是「单卡 block 数」都按 40KB 口径,不要混用。

解决:chunked prefill 每 step 只分配 chunk_size 个 token 的 KV cache(如 1024 token 约 320MB),不需要一次性满足全部。

```text
Chunked:
  请求 R: prompt = 100K token, chunk_size = 1024
  Step 1: 分配 1024 token 的 KV (320MB) → 够! 开始 prefill
  Step 2: 再分配 1024 token 的 KV → 够! 继续
  ...
  Step 98: 最后一块,完成 prefill
  → 每 step 只需 320MB 空闲,而非 32GB
  → R 几乎立刻可以开始(只要空闲 ≥ 320MB)
```

数学:朴素需要 $\text{free\_blocks} \ge \lceil N/B \rceil$($N$ 为 prompt 长度),chunked 只需 $\text{free\_blocks} \ge \lceil c/B \rceil$($c$ 为 chunk size)。当 $N = 100000$、$c = 1024$、$B = 16$ 时,朴素需要 6250 个 block,chunked 只需 64 个,降低约 100 倍。

**作用 3:限制激活内存(防止 prefill 本身的 OOM)**

问题:prefill 100K token 时,模型前向的中间激活(attention scores、FFN 中间层等)与 token 数成正比。100K token 的激活可能占几 GB——即使 KV cache 够,激活也可能 OOM。

这里要先说清一个容易搞错的点: **推理时的激活是「逐层复用」的** ,算完第 $i$ 层就把第 $i$ 层的中间 buffer 还给显存池给第 $i+1$ 层用(不像训练要留着做 backward)。所以峰值激活取的是 **单层** 的量级,不是「单层乘以层数」。

```text
朴素 prefill 100K token (Llama-3-70B, TP=8, FP16):
  FFN 中间层(单层,单卡):
    [100K, 28672/8=3584] × 2 bytes ≈ 717MB
  再加 qkv / o_proj / residual 等若干个同数量级 buffer
  → 单卡峰值激活几 GB,叠上权重 17.5GB 后逼近甚至超出 80GB 的余量
  (attention scores [100K, 100K] 不会被 materialize —— FlashAttention 分块算,
   但它的 workspace 同样正比于 token 数)
```

解决:chunked prefill 每 step 只算 chunk_size 个 token,激活内存与 chunk_size 成正比,与 prompt 总长无关。

```text
Chunked prefill (chunk = 2048, 即默认 token budget):
  FFN 中间层(单层,单卡): [2048, 3584] × 2 bytes ≈ 14MB
  → 激活内存恒定在几十 MB 量级,不随 prompt 长度增长
```

**作用 4:使连续批处理真正「连续」**

问题:朴素做法下,一个长 prefill 占用整个 step(几百 ms),期间无法加入新请求——与连续批处理的「每 step 动态增减」目标矛盾。

```text
朴素:
  step N: prefill(R, 100K token) ———— 500ms ————
          (期间无法加新请求,无法 decode)
  step N+1: 终于可以 decode + 加新请求
```

解决:chunked prefill 让每 step 的 token 数有上限(不超过 `max_num_batched_tokens`),调度器每 step 都能做决策——加新请求、移除完成请求、给 decode 分配 token。

```text
Chunked:
  step N:   [R_chunk1(2046)] + [A_decode(1), B_decode(1)]        ← 混合!
  step N+1: [R_chunk2(2045)] + [A_decode(1), B_decode(1), C_new(1)]  ← C 加入
  step N+2: [R_chunk3(2045)] + [A_decode(1), B_done, C_decode(1)]    ← B 完成
  → 每 step 都在动态增减,真正「连续」
```

**作用 5:公平性(防止长 prompt 饿死短请求)**

- 问题:朴素做法下,先到的长 prompt 独占 GPU 几百 ms,后到的短请求(即使只需 10 ms prefill)必须等待。
- 解决:chunked prefill 让长 prompt 分多个 step 处理,每个 step 只占一部分 budget,剩余 budget 给 decode 和新请求。

```text
朴素:
  t=0:   R(长 prompt) 开始 prefill
  t=500: R prefill 完,才能处理 S(短 prompt)
  → S 等了 500ms

Chunked:
  t=0:   R_chunk1(1948) + S_prefill(100)   ← S 立刻开始!
  t=50:  R_chunk2(2047) + S_decode(1)
  → S 几乎不用等
```

**总结表**

| 作用 | 朴素的问题 | Chunked 的解决 | 数学依据 |
|---|---|---|---|
| TPOT 平滑 | prefill 阻塞 decode 500ms | 每 step 混合 prefill 加 decode | $T_{\text{step}} \approx T_p(c) + T_d(b)$,恒定 |
| KV cache OOM | 需一次性分配 N token 的 KV | 每 step 只分配 c token 的 KV | 需求从 $\lceil N/B \rceil$ 降到 $\lceil c/B \rceil$ |
| 激活 OOM | 100K token 的单层激活几 GB | 每 step 只算 c token 的激活 | 激活正比于 $c$,与 $N$ 无关 |
| 连续批处理 | 长 prefill 占满 step,无法增减请求 | 每 step 有 budget 上限,可动态增减 | $c \le$ `max_num_batched_tokens` |
| 公平性 | 长 prompt 饿死短请求 | 每 step 只占部分 budget | budget 共享池机制 |

一句话:chunked prefill 不只是「让 decode 不等 prefill」,它同时把 **KV cache 分配粒度、激活内存、调度粒度、公平性** 都从「整个 prompt」降到「单个 chunk」——5 个维度的 OOM、延迟、公平问题一起解决。

> 🖼️ 占位:chunked prefill 的五个作用。回答「把粒度从整个 prompt 降到单个 chunk 之后,分别在时间轴、KV block、激活 buffer、调度决策点、等待队列这五处各带来什么变化」。

### 1.4 统一的 token 追踪模型

V1 调度器最优雅的设计是 **取消了 prefill/decode phase 的概念** 。每个请求只有两个计数器:

- `num_computed_tokens`:已经过模型前向、KV cache 已就绪的 token 数。
- `num_tokens_with_spec`:该请求当前一共有多少个 token 需要被算过,等于「prompt 加已生成的 output」再加上「推测解码给出的草稿 token」。

调度器的目标: **为每个请求分配 token,让 `num_computed_tokens` 追上 `num_tokens_with_spec`** 。

| 场景 | `num_computed_tokens` | `num_tokens_with_spec` | 含义 |
|---|---|---|---|
| 新请求刚到 | 0 | $N$(prompt 长度) | 全 prefill |
| prefill 中途 | 512 | $N$ | 还有 $N-512$ 待算 |
| prefill 完成 | $N$ | $N$ | 进入 decode |
| decode 一个 token | $N$ | $N+1$ | 还有 1 待算 |
| 推测解码(4 个 spec) | $N+k$ | $N+k+4$ | 一次算 4 个 |

每 step 调度器决定 **本次为每个请求算多少新 token** :基本量就是两个计数器的差,再受 token budget、单请求长 prefill 阈值、模型最大长度等一并压小。开了异步调度时,差值里还要加上「已经调度出去、但输出还没回来的占位 token 数」,避免同一批 token 被重复调度。

这个统一模型让 chunked prefill、continuous batching、speculative decoding 三者在调度层面 **完全正交** ——推测解码只是让 `num_tokens_with_spec` 一次多加几个,调度器完全不感知。

> 🖼️ 占位:两个计数器的追赶过程。回答「一条请求从进门到结束,这两个计数器各自怎么走、每 step 的差值怎么变成本次要算的 token 数」。

### 1.5 Token Budget:每 step 的计算量上限

#### 1.5.1 什么是 token budget

每 step 调度器有一个 **token budget** (由 `--max-num-batched-tokens` 控制,默认 2048)。它定义了 **单次 model forward 最多处理多少个 token** ——包括所有 prefill chunk token 和所有 decode token 的总和。

```text
一个 step 的 batch:
  请求 A (decode):    1 token      ┐
  请求 B (decode):    1 token      │ 总和 ≤ token_budget (2048)
  请求 C (prefill):   1024 token   │
  请求 D (prefill):   500 token    ┘
  总计: 1526 token ≤ 2048 ✓
```

调度器实际用的字段是 `Scheduler.max_num_scheduled_tokens`,它这样取值:

```python
self.max_num_scheduled_tokens = (
    self.scheduler_config.max_num_scheduled_tokens
    if self.scheduler_config.max_num_scheduled_tokens is not None
    else self.scheduler_config.max_num_batched_tokens
)
```

即:`max_num_scheduled_tokens` 没显式设时就等于 `max_num_batched_tokens`。此外 `schedule()` 里还有第二条预算线 `input_budget`,它 **始终取** `max_num_batched_tokens`,用于约束 model runner 输入张量的上限;两者在只设了 `max_num_batched_tokens` 的默认情况下同值。

#### 1.5.2 为什么需要 token budget:3 个约束的交集

token budget 不是随意设的——它同时满足 3 个物理约束。下面的数字统一以 Llama-3-70B、8 张 H100、TP=8、FP16 为例, **全部是量级参考,不是本仓库实测** 。

**约束 1:GPU 单 step 计算时间上限(控制 TPOT)**

一次 forward 的耗时与 token 数近似成正比(prefill 是 compute-bound)。如果不限制 token 数,一个 step 可能算 100K token,耗时好几秒——期间所有 decode 请求的 TPOT 一起被拖住。

```text
参照量: 70B 在 8×H100 上的 prefill 吞吐约 1.5 万 token/s
       → 每 token prefill ≈ 65µs(含 TP 通信与 kernel 开销的端到端值)

token_budget = 2048:
  一个「被 prefill 占满」的 step ≈ 2048 × 65µs ≈ 133ms
  → 这是单 step 耗时的上界;纯 decode 的 step 要快得多(见下)

无 budget 限制:
  100K token → 100000 × 65µs ≈ 6.5s
  → 这一个 step 里所有 decode 请求都卡住 6.5 秒
```

要注意「133ms」是 **上界而非典型值** :只有当这一步的 2048 个 token 几乎全是 prefill chunk 时才会到这个量级。纯 decode 的 step 里 token 数等于 batch 内请求数(比如 64 个请求就是 64 个 token),是 memory-bound,耗时通常只有 10 到 30 ms。

**约束 2:激活内存上限(防止 OOM)**

model forward 的中间激活(FFN 中间层、attention workspace)与 token 数成正比。token budget 限定了激活内存的上限。

如 1.3.3 所说,推理时激活是 **逐层复用** 的,峰值取单层的量级,且在 TP 下按卡切分:

```text
70B, FP16, TP=8, 单层 FFN 中间层(单卡):
  每 token: 28672 / 8 = 3584 维 × 2 bytes = 7KB

token_budget = 2048:
  单层激活 ≈ 2048 × 7KB = 14MB
  叠上 qkv / o_proj / residual / attention workspace 等同数量级 buffer,
  峰值大致在几十 MB → 完全可控

无 budget (100K token):
  单层激活 ≈ 100000 × 7KB = 700MB
  加上其余 buffer 后是几 GB 量级 → 挤压 KV cache 甚至 OOM
```

绝对值看起来不大,但它是 **线性增长且不可预测** 的那一项——启动期的 profile run 是按 `max_num_batched_tokens` 探测峰值显存的(见 1.6.5),budget 一旦放大,留给 KV cache 的空间就要相应收缩。

**约束 3:KV cache 单 step 分配上限(配合 chunked prefill)**

每 step 新处理的 token 需要写入 KV cache。token budget 限定了单 step 的 KV cache 增长量,防止一步吃掉太多 block。

```text
每 token KV: 320KB(全模型合计) / 40KB(单卡, TP=8)
token_budget = 2048:
  单 step KV 增长 ≤ 2048 × 40KB = 82MB/卡  ← 可控

无 budget:
  单 step 可能增长 100K × 40KB = 4GB/卡   ← 一步吃掉大块 KV cache
```

#### 1.5.3 token budget 与 chunked prefill 的关系

**token budget 就是 chunked prefill 的 chunk size 上限。** 调度器在分配 budget 时:

```text
请求 C: prompt = 100K token, 需要预填充
  剩余 budget = 2048 - 2(decode) = 2046
  → 本 step 给 C 分配 min(100K, 2046) = 2046 token
  → C 的 chunk size = 2046(不是整个 100K)
  → 下 step 继续分,直到 100K 算完(约 49 步)
```

注意 vLLM **没有** 「每个 chunk 固定多少 token」的配置。单 chunk 的实际大小是三者取最小:

```text
min(还差多少没算,          # num_tokens_with_spec - num_computed_tokens
    本 step 剩余预算,       # token_budget
    输入张量剩余额度)       # input_budget - draft_slots
```

再被 `long_prefill_token_threshold` 截断(默认 0 表示不截断)。所以 chunk 大小 **每一步都在变** ——同 batch 里 decode 请求多的那一步,prefill chunk 就小。

如果关掉 chunked prefill(`enable_chunked_prefill=False`),调度器看到该请求需要的 token 数超过它这一轮能给的额度时,会直接 `break` 不切 chunk,等 budget 够时一次性算——这就是 1.3.3 说的「退化」。

#### 1.5.4 token budget 的分配规则:RUNNING 优先

token budget 是一个 **单调递减的共享池** ——RUNNING 队列先消费,剩余的给 WAITING 队列:

```text
token_budget = max_num_scheduled_tokens   // 初始值 = 2048(默认)

阶段 1: 先给 RUNNING 队列
  for req in running:
      num_new_tokens = 还差多少没算(见 1.4)
      num_new_tokens = min(num_new_tokens, token_budget, 输入张量剩余额度)
      分配 KV blocks
      token_budget -= num_new_tokens        // 扣减

阶段 2: 再给 WAITING 队列(如果 budget 还有剩)
  while (waiting 或 skipped_waiting) 非空 and token_budget > 0:
      看队首请求(peek,不出队)
      计算它的 num_new_tokens
      分配 KV blocks
      成功才出队,token_budget -= num_new_tokens
```

为什么 RUNNING 优先:

- RUNNING 请求的 KV cache 已经在 GPU 上,每 step 都需要继续 decode,否则用户感知到的 TPOT 会飙升。
- WAITING 请求是「新增的」,可以等几个 step,用户对 TTFT 的容忍度比对 TPOT 高。

例外:Priority 策略下,高优先级的 WAITING 请求可能比低优先级的 RUNNING 请求先调度(详见 1.7)。

#### 1.5.5 token budget 调参的 trade-off

沿用 1.5.2 的 65µs/token 口径,「满载 step 耗时」列指的是被 prefill 占满时的上界:

| budget 值 | 满载 step 耗时 | 吞吐 | TPOT | TTFT | 适用场景 |
|---|---|---|---|---|---|
| 小(512) | 约 33ms | 低 | **低(好)** | 低 | 低延迟优先(实时 chat) |
| **默认(2048)** | 约 133ms | 中 | 中 | 中 | 通用平衡 |
| 大(8192+) | 约 530ms | **高** | 高(差) | 高 | 吞吐优先(离线批量) |

**核心 trade-off** :budget 大则每 step 算更多 token、吞吐高,但单 step 耗时长、decode 请求等得久、TPOT 高。反之亦然。

在线服务里常见的做法是把 budget 设到「单 step 满载耗时约等于可接受的 TPOT 上限」:想保 TPOT 低于 50ms,就把 budget 压到 512 到 1024;离线批量不在乎 TPOT,调到 8192 甚至 16384 换吞吐。这是经验做法,不是仓库里的配置建议。

> 🖼️ 占位:token budget 的三条约束与调参曲线。回答「同一个 budget 值同时被计算时间、激活内存、KV 增量三个上限约束,调大调小分别先撞到哪一条」。

### 1.6 并发上限:`max_num_seqs` 与三道闸门

`max_num_seqs`(默认 128)是 RUNNING 队列的硬上限——同一时刻最多有这么多请求在跑。但实际并发数可能更低,因为有 **3 道闸门** 同时限制。

#### 1.6.1 三道闸门

```text
新请求想进入 RUNNING → 必须同时通过 3 道闸门:

闸门 1: max_num_seqs(默认 128)
  ┌────────────────────────────────────────┐
  │ len(running) + 暂停的流式会话数 < 上限? │
  │   num_running = len(self.running) +     │
  │     self.num_waiting_for_streaming_input│
  │   if num_running >= max_num_running_reqs│
  │       break   # 停止从 WAITING 拉新请求 │
  │ (max_num_running_reqs 就是 max_num_seqs)│
  └────────────────────────────────────────┘
                    │ 通过?
                    ▼
闸门 2: KV cache 容量
  ┌────────────────────────────────────────┐
  │ allocate_slots() 返回非 None ?          │
  │   new_blocks = kv_cache_manager          │
  │     .allocate_slots(request, ...)        │
  │   if new_blocks is None: break           │
  │ 即使 running < max_num_seqs,             │
  │ KV cache 不够也进不来 —— 而且是 break,   │
  │ 本 step 后面的 waiting 请求一并不再尝试  │
  └────────────────────────────────────────┘
                    │ 通过?
                    ▼
闸门 3: token budget(max_num_batched_tokens)
  ┌────────────────────────────────────────┐
  │ token_budget > 0 ?                      │
  │   while (self.waiting or                 │
  │          self.skipped_waiting) and       │
  │         token_budget > 0:                │
  │ budget 被 running 请求消耗完后,          │
  │ waiting 里的请求等下个 step               │
  └────────────────────────────────────────┘
                    │ 通过?
                    ▼
             请求进入 RUNNING
```

**实际并发等于三道闸门能同时通过的请求数中的最小者。**

注意闸门 2 的行为是 `break` 而 **不是** 「跳过该请求继续试下一个」——WAITING 队列是有序的,队首都放不下,后面的更放不下。

> 🖼️ 占位:三道闸门。回答「一个新请求从 WAITING 进 RUNNING 要连过哪三关,每关卡住时是 break 还是 continue,分别等到什么条件才放行」。

#### 1.6.2 三道闸门的具体场景

以默认 `max_num_seqs=128`、`max_num_batched_tokens=2048` 为例(KV 容量列是按显存估的量级示意):

| 场景 | 闸门1 (max_seqs) | 闸门2 (KV cache) | 闸门3 (budget) | 实际并发 | 瓶颈 |
|---|---|---|---|---|---|
| 短序列 + 大 GPU | 128 | 够 600 个 | 2048 够 | **128** | 闸门1 |
| 长序列(8K token/请求) | 128 | 只够 160 个 | 2048 够 | **128** | 闸门1 |
| 超长序列(64K token/请求) | 128 | 只够 20 个 | 2048 够 | **20** | 闸门2 |
| 新请求持续涌入 | 128 | 够 | 2048 被 prefill 吃完 | 爬升慢 | 闸门3 |

第 4 行值得解释: **闸门 3 不封顶并发数,而是限制并发数的爬升速度。** 默认 budget 只有 2048,一个 2000-token 的新 prompt 就能吃掉一整个 step 的预算,所以「从 0 涨到 128 并发」需要几十个 step;短 prompt 场景下几个 step 就满了。

#### 1.6.3 超过 `max_num_seqs` 时的行为

```text
用户瞬间提交 1000 个请求 (max_num_seqs=128, budget=2048)

t=0    1000 个请求全部进入 WAITING 队列
       WAITING: [R1, R2, ..., R1000]  (1000 个)
       RUNNING: []  (空)

t=1    schedule() 从 WAITING 拉请求:
         闸门1: len(running)=0 < 128 ✓
         闸门2: KV cache 够 ✓
         闸门3: budget 2048 > 0 ✓
         → 假设每个 prompt 200 token, 本 step 只拉得下 10 个
           (10 × 200 = 2000 ≤ 2048, 第 11 个把 budget 撑破 → break)
       RUNNING: [R1..R10]
       WAITING: [R11..R1000]

t=2..k 每 step 继续拉, 但已 running 的请求要先吃 decode 预算
       → 并发数逐步爬升, 大约十几个 step 后到 128

t=k    闸门1: len(running)=128 >= 128 → break!
       → WAITING 不动, R129..R1000 继续等
       → RUNNING 里的 128 个持续 decode

t=某步 R5 生成 EOS → 从 RUNNING 移除, 释放 KV
       RUNNING: 127 个 → 有空位!
       → 下个 step schedule() 从 WAITING 拉 R129
       → R129 开始 prefill

...    持续到所有请求完成
       WAITING 队列没有大小上限, 1000/10000 个都能排
       但排队越久 TTFT 越高
```

关键:

- WAITING 队列 **无大小上限** ——多少请求都能排。
- 新请求要等 RUNNING 里出现空位(有请求完成,或被抢占踢出)才能进—— **不是时间片轮转,是「等空位」** 。
- 排队期间 TTFT 持续增长(用户等待首 token 的时间越来越长)。
- 并发数不是一步跳到 128 的,受 budget 限制逐 step 爬升。

#### 1.6.4 KV cache 不够时的额外行为:抢占

即使 `running < max_num_seqs`,KV cache 也可能不够。但要说清楚 **抢占是谁触发的** :

**抢占只发生在 RUNNING 循环里** ,触发方是 **一个已经在 running 的请求** ——它这一步要写新 token(decode 写第 N+1 个位置、prefill chunk 续算、或 spec/lookahead 要预留槽位),`allocate_slots` 却拿不到 block。此时调度器牺牲 **别的** running 请求来给它腾地方。

**WAITING 队列拿不到 block 时不会抢占** ,只是 `break` 掉本轮的 WAITING 调度,新请求下个 step 再试:

```python
new_blocks = self.kv_cache_manager.allocate_slots(...)
if new_blocks is None:
    # The request cannot be scheduled.
    if request.has_encoder_inputs:
        self.encoder_cache_manager.free(request)
    break        # ← 不抢占
```

所以正确的场景是这样的:

```text
running: [A(len=5000), B(len=3000), C(len=2000)]
KV cache 已用 100%, block pool 空

本 step 调度 RUNNING:
  A 要 decode 第 5001 个 token, 恰好跨到新 block
  allocate_slots(A, 1) → None (一个 block 都没有)
  → 抢占队尾的 C (FCFS): 释放 C 的全部 KV, C.num_computed_tokens=0,
    C 回到 waiting 队首
  → 重试 allocate_slots(A, 1) → 成功
  → running: [A, B]; A/B 正常 decode, C 下轮重新 prefill

(若 A 是队尾, 循环会一路抢到把 A 自己也抢占,
 此时直接 break, A 本轮不调度)
```

而「新请求 D 到达但 KV 不够」的结局只是:D 留在 waiting,下个 step 再试;等某个 running 请求完成或被抢占释放了 KV,D 才进得来。

牺牲品的选法随策略而变:FCFS 取 running 队尾(最晚入座的),Priority 取优先级最低、同级里到达最晚的那个。

> 🖼️ 占位:抢占的触发与恢复。回答「谁触发抢占、牺牲谁、被抢者的状态和计数器怎么变、它下一轮从哪里重新开始」。

#### 1.6.5 KV cache 容量怎么算:`gpu_memory_utilization` 的作用

闸门 2(KV cache 容量)不是用户直接配置的——它由 `gpu_memory_utilization`(默认 0.92)间接决定。vLLM 在启动时通过一次 **profile run(内存探测)** 自动计算可用 KV cache 空间,然后换算成 block 数量。

**计算链路(从参数到 num_blocks)**

```text
用户配置: --gpu-memory-utilization 0.92(默认)
   │
   ▼
① requested_memory = GPU 总显存 × gpu_memory_utilization
   │  request_memory():
   │    requested_memory = math.ceil(
   │        init_snapshot.total_memory * cache_config.gpu_memory_utilization)
   │  例: 80GB GPU × 0.92 = 73.6GB
   │  (free_memory < requested_memory 时直接抛 ValueError)
   │
   ▼
② profile run: 跑一次 dummy forward, 探测非 KV cache 的显存占用
   │  with memory_profiling(...) as profile_result:
   │      self.model_runner.profile_run()   ← 用假数据跑一次完整 forward
   │  测量: 权重显存 + 峰值激活显存; CUDA Graph 显存单独估算
   │  例: 权重 17.5GB + 激活 2GB + CUDA Graph 1GB = 20.5GB
   │
   ▼
③ available_kv_cache_memory = requested_memory - 非KV显存
   │  self.available_kv_cache_memory_bytes = (
   │      self.requested_memory
   │      - profile_result.non_kv_cache_memory
   │      - cudagraph_memory_estimate_applied)
   │  例: 73.6GB - 20.5GB = 53.1GB
   │
   ▼
④ 每 block 的字节数 = 2 (K+V) × num_layers × num_kv_heads
   │                    × block_size × head_dim × dtype_size
   │  ★ 必须乘 num_layers —— 每一层都有自己的一份 K/V
   │  例 (Llama-3-70B, 80 层, TP=8, FP16):
   │    2 × 80 × (8/8=1 kv_head) × 16 (block_size) × 128 (head_dim) × 2
   │    = 655,360 bytes = 640KB/block (单卡)
   │
   ▼
⑤ num_gpu_blocks = available_kv_cache_memory / 每 block 字节数
   │  由 get_kv_cache_configs() 换算
   │  例: 53.1GB / 640KB ≈ 8.7 万 blocks (单卡, 简化估算)
   │
   ▼
⑥ engine 侧记录可用显存并生成 KV cache 配置
   │  available_gpu_memory = self.model_executor.determine_available_memory()
   │  self.available_gpu_memory_for_kv_cache = available_gpu_memory[0]
   │  kv_cache_configs = get_kv_cache_configs(
   │      vllm_config, kv_cache_specs, available_gpu_memory)
   │
   ▼
⑦ BlockPool(num_gpu_blocks) 初始化
   │  scheduler 的闸门 2 就是这个 block 池
   │  每个请求分配 block, 完成释放, 满了就触发抢占
```

**具体数字示例** (Llama-3-70B、8 张 H100 80GB、TP=8、FP16;以下全是量级示意,不是本仓库实测)

```text
GPU 总显存:          80 GB/卡
gpu_memory_utilization: 0.92 (默认)
requested_memory:    80 × 0.92 = 73.6 GB

Profile run 测量:
  模型权重 (70B / 8卡, FP16):  70B × 2B / 8 = 17.5 GB/卡
  峰值激活 (max_num_batched_tokens=2048): 约 0.5 GB
  CUDA Graph (若干 bucket):      约 1 GB
  其他 (PyTorch runtime 等):     约 0.5 GB
  ─────────────────────────────────
  非 KV cache 显存合计:          约 19.5 GB

available_kv_cache_memory = 73.6 - 19.5 = 54.1 GB

每 block 大小 (80 层, TP=8 → 单卡 1 个 kv_head, block_size=16):
  2 × 80 × 1 × 16 × 128 × 2 = 655,360 bytes = 640 KB

num_gpu_blocks = 54.1 GB / 640 KB ≈ 88,600 blocks

每 token KV (单卡) = 640KB / 16 = 40 KB/token
  → 54.1GB / 40KB ≈ 142 万 token 的 KV cache
  → 假设平均请求 2000 token: 理论可容纳约 700 个请求
  → 实际受 max_num_seqs=128 限制, 通常先撞闸门 1
  → 但若平均请求涨到 11000 token, 128 × 11000 = 141 万,
    就正好把 KV cache 吃满 → 闸门 2 成为瓶颈, 开始出现抢占
```

最后那一行是这套换算真正有用的地方:它给出了 **「从闸门 1 瓶颈切换到闸门 2 瓶颈」的临界序列长度** 。用「KV 容量(token 数)除以 `max_num_seqs`」就能估出来——本例约 11K token。线上平均序列长度接近这个数时,就该考虑降 `max_num_seqs` 或升 `gpu_memory_utilization`。

顺带纠正一个容易想当然的点:vLLM 确实有一个 `watermark`(保留一小部分 block 不分配),但它 **默认是 0,也就是关闭的** 。所以默认配置下 block 数不会因为 watermark 而打折。

**`gpu_memory_utilization` 调参的影响**

```text
                    util=0.85    util=0.92 (默认)  util=0.95
                    ─────────    ───────────────   ─────────
requested_memory     68 GB         73.6 GB          76 GB
非 KV 显存           19.5 GB (固定) 19.5 GB          19.5 GB
KV cache 可用        48.5 GB       54.1 GB          56.5 GB
num_blocks           约 79,400     约 88,600        约 92,500
可容纳 token         约 127 万     约 142 万        约 148 万
临界序列长度         约 9.9K       约 11.1K         约 11.6K
抢占频率             高 (KV 少,易撞满)  中          低
OOM 风险             低            低               中 (激活峰值可能超)
```

注意「抢占频率」与「OOM 风险」是 **反向的两条曲线** :util 调低是把显存从 KV cache 挪给激活余量,KV 变小则更容易撞满、抢占 **变多** ;util 调高则 KV 变大、抢占变少,但激活突然涨大(比如临时调高了 `max_num_batched_tokens`)时会 OOM。

- 调高 util:KV cache 更大,支持更多并发、更长序列、更少抢占,但留给激活的余量少,如果 batch 或 budget 突然变大可能 OOM。
- 调低 util:KV cache 更小,并发少、序列短、抢占更频繁,但更安全,不会 OOM。

**关键** :`gpu_memory_utilization` 不是「KV cache 占多少显存」,而是「vLLM 总共最多用多少 GPU 显存」。KV cache 拿到的是 **减掉权重和激活后的剩余部分** 。

> 🖼️ 占位:从 `gpu_memory_utilization` 到 block 池的换算链路。回答「一张 80GB 卡上,总显存怎么一层层减成 KV cache,再除成多少个 block」;把权重、激活、CUDA Graph、KV 四段画成一根显存条。

### 1.7 抢占:当显存耗尽时

抢占的唯一触发点是: **某个已在 RUNNING 队列里的请求,这一步要写新 token,但 `allocate_slots()` 拿不到 block** 。具体成因有三类:

- **decode 跨 block** :running 请求序列越写越长,第 N+1 个 token 恰好要开一个新 block,而 block pool 已空。
- **prefill chunk 续算** :running 里的 prefill chunk 要接着算下一块,需要新 block。
- **spec decode / lookahead 预留** :`num_lookahead_tokens` 要求提前预留槽位,把需求量放大了。

此时调度器必须 **抢占别的请求** ,把它们的 KV cache 释放出来给触发者。

需要明确排除两种 **不会** 导致抢占的情况:

- **WAITING 里的新请求拿不到 block** :只 `break` 掉本轮 WAITING 调度,请求留在队列里下个 step 再试。
- **请求数超过 `max_num_seqs`** :只 `break`,排队等空位。

换句话说,抢占永远是 **「已经在跑的请求之间互相挤」** ,不是「新请求把老请求挤下去」。

#### 1.7.1 抢占只有 recompute 一种模式(没有 swap)

被抢占的请求,理论上有两种去处:

- **swap(换出)** :把它的 KV cache 拷到 CPU 内存里存着,下次被调度时再拷回 GPU。
- **recompute(重算)** :直接丢弃 KV cache,下次被调度时当作新请求重新 prefill。

vLLM 调度器 **只实现了 recompute** —— `vllm/v1/` 目录下不存在任何 swap 路径(没有 `swap_in` / `swap_out` / `PreemptionMode` 之类的符号),`_preempt_request` 唯一的动作就是释放 block 并把请求退回 waiting 队列。三条理由:

1. **swap 的搬运本身就不划算** :KV 要经 PCIe 往返一次。以 640KB/block 的量级算,换出几百个 block 就是几百 MB 的双向拷贝,耗时与直接重算 prefill 同量级,还要额外维护 CPU 侧显存池和拷贝流。
2. **prefix caching 把重算摊薄了** :被抢占的请求重新 prefill 时,已缓存的公共前缀 block 可以直接命中复用,实际只需重算被释放掉的那部分尾巴,而不是整条 prompt。
3. **调度逻辑不用分叉** :没有 swap 就没有「这个请求的 KV 在 CPU 还是 GPU」的第二种状态,请求状态机与主循环都因此少一整类分支。

这里有个实现细节值得记一笔:被抢占的请求状态并不是直接变回 `WAITING`,而是先置成一个专门的 `PREEMPTED` 状态,再 **插到 waiting 队列的最前面** 。用独立状态而不是复用 WAITING,是为了让后续逻辑能认出「这是重来的,不是新来的」。

#### 1.7.2 选择谁被抢占

| 策略 | 选择标准 | 直觉 |
|---|---|---|
| **FCFS(默认)** | `self.running.pop()`——弹出列表 **末尾** (最新加入的) | 先到先服务:早到的请求被保护 |
| **Priority** | `max(running, key=(priority, arrival_time))` | 优先级数值最大(即最低优先级)的先被抢占 |

**FCFS 的微妙设计** :`running` 是一个 `list`,新请求通过 `self.running.append(req)` 加入。`pop()` 弹出最后一个,也就是最新加入的。这保护了「老」请求。

#### 1.7.3 recompute 的代价

被抢占的请求 `num_computed_tokens` 被重置为 0,所有已生成的 token 仍在输出序列里,但 KV cache 没了。下次调度时整个请求从头 prefill(如果开了 prefix caching 则公共前缀 block 可复用)。同时它的草稿 token 会被清空、抢占次数计数加一。

代价:浪费了之前 prefill 加上所有 decode 的计算量。所以 **抢占是最后的手段** ,正常情况下应该通过 `--gpu-memory-utilization` 调到合适值,让调度器很少需要抢占。

> 🖼️ 占位:抢占前后的状态与计数器。回答「被抢者的 block、状态、num_computed_tokens、草稿 token 各发生什么,它回到队列的哪个位置,下轮从哪里重新开始」。

### 1.8 调度策略:FCFS vs Priority

| 维度 | FCFS(先到先服务) | Priority(优先级) |
|---|---|---|
| 底层结构 | `collections.deque` | `heapq`(最小堆) |
| 排序键 | 插入顺序 | `(priority, arrival_time, request_id)` |
| 典型场景 | 通用、公平 | SLA 分级(免费与付费用户) |
| 配置 | `--scheduling-policy fcfs`(默认) | `--scheduling-policy priority` |
| API | 请求按到达顺序排队 | 请求需指定 `priority` 字段 |

Priority 排序由 `Request.__lt__` 定义:

```python
def __lt__(self, other: "Request") -> bool:
    if self.priority != other.priority:
        return self.priority < other.priority       # priority 小的优先(数值小=高优先)
    if self.arrival_time != other.arrival_time:
        return self.arrival_time < other.arrival_time  # 同优先级, 早到的优先
    if self.request_id != other.request_id:
        return self.request_id < other.request_id      # 再用 id 稳定排序
    return id(self) < id(other)                        # 兜底: 对象地址
```

Priority 用 **数值小等于高优先级** (与 Unix `nice` 一致)。

这里和 1.7.2 的抢占选法正好互补:入队时用 `__lt__` 取最小(优先级最高的先服务),抢占时用 `max` 取最大(优先级最低的先牺牲),两处用的是同一个排序键。
