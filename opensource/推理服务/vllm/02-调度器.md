## Part 1|原理

### 1.1 朴素批处理的痛点

最朴素的 LLM 服务批处理是 **static batching(静态批处理)** :把多个请求拼成一个 batch,等 batch 内 **所有请求都生成完** 才接收下一批。

假设 batch 大小为 4,4 个请求分别生成 10 / 100 / 1000 / 100 个 token:

```text
朴素批处理时间线(batch=4):
t=0      请求1(p10)    请求2(p100)   请求3(p1000)  请求4(p100)   ← prefill
t=10     [1✓]           2 decode      3 decode      4 decode     ← 请求1 完成
t=100    [1✓ 等待]      [2✓]          3 decode      4 decode     ← 请求2 完成
t=100    [1✓ 等待]      [2✓ 等待]     3 decode      [4✓]         ← 请求4 完成
t=1000   [1✓ 等待]      [2✓ 等待]     3 decode  ←── 请求3 拖累整个 batch
t=1000   batch 完成,接收新 batch
```

问题:

1. **GPU 空转** :请求 1、2、4 完成后,对应的 batch slot 空置,GPU 算力浪费。
2. **延迟尖峰** :新到的请求必须等整个 batch 完成,最坏情况等 1000 个 token 的时间。
3. **显存浪费** :已完成的请求仍占着 KV cache 空间,直到整个 batch 结束。

> 🖼️ 占位:静态批处理与连续批处理的 slot 占用对比。回答「同样四条请求,两种调度下每个 slot 在各时刻是在算还是空着」。

### 1.2 连续批处理:iteration-level scheduling(迭代级调度)

**连续批处理** 的核心思想: **在每个 decode step(每生成一个 token)都重新决策** ——哪些请求继续、哪些请求结束、哪些新请求加进来。

```text
连续批处理时间线(每 step 重新组 batch):
t=0      prefill: [1,2,3,4]
t=10     decode:  [2,3,4,5]     ← 请求1 完成,请求5 加入
t=100    decode:  [3,4,5,6]     ← 请求2 完成,请求6 加入
t=100    decode:  [3,5,6,7]     ← 请求4 完成,请求7 加入
t=200    decode:  [3,5,6,7]     ← 等请求3 慢慢生成,但其他 slot 一直满载
```

收益:

1. **GPU 满载** :每 step 都尽量填满 batch,吞吐接近理论上限。
2. **低延迟** :新请求只要 batch 有空 slot 就立即加入,无需等待。
3. **显存高效** :完成的请求立即释放 KV cache,腾空间给新请求。

**实现关键** :必须有 PagedAttention。只有 KV cache 按 block 灵活分配与释放,才能支持请求的动态进出。 **连续批处理是建立在 PagedAttention 之上的。**

### 1.3 Chunked Prefill:解决 prefill 阻塞 decode

朴素的连续批处理仍有一个问题: **prefill 和 decode 不能同 batch** 。原因:

- prefill 是 **compute-bound(计算密集)** :处理几千个 prompt token,单 step 耗时 50 到 500 ms。
- decode 是 **memory-bound(访存密集)** :每 step 只处理 1 个 token,但需要扫描所有 KV cache,单 step 耗时 5 到 50 ms。

如果 prefill 和 decode 严格串行(即一个 step 里只做其中一件事):

```text
朴素串行(prefill 阻塞 decode):
step N:    prefill(请求A, prompt=4000 tokens) —— 500ms
step N+1:  decode(所有 running 请求) —— 20ms   ←── decode 等 prefill 完才能跑
step N+2:  decode —— 20ms
...
step N+30: prefill(请求B, prompt=3000) —— 400ms  ←── 又阻塞
step N+31: decode —— 20ms
```

问题:decode 的 TPOT(time per output token)出现周期性尖峰,从 20 ms 飙到 500 ms,用户体验差。本节所有耗时都是量级参考,不是本仓库实测。

#### 1.3.1 Chunked prefill 的做法

把长 prompt 切成小块(chunk),每 step 只处理一个 chunk(如 512 token):

```text
Chunked prefill(prefill 分块,与 decode 同 batch):
step N:    [chunk1 of 请求A (512 tokens)] + [decode 所有 running]  —— 50ms
step N+1:  [chunk2 of 请求A (512 tokens)] + [decode 所有 running]  —— 50ms
...
step N+8:  [chunk8 of 请求A (剩余 384 tokens)] + [decode]          —— 50ms
                                             ←── 请求A 进入 decode
```

收益:

1. **TPOT 平滑** :每个 step 的耗时基本恒定(chunk 计算量加 decode 计算量),无尖峰。
2. **prefill 与 decode 共享 step** :同一次 model forward 同时处理 prefill chunk 和 decode token,GPU 利用率最大化。
3. **TTFT 略增但可接受** :长 prompt 的首 token 延迟从 500 ms 变成 chunk 数乘以 50 ms 约等于 400 ms(差不多),但所有其他请求的 TPOT 不再尖峰。

#### 1.3.2 数学:最优 chunk size

设:

- $T_{\text{prefill}}(n)$:处理 $n$ 个 prefill token 的耗时(约 $O(n)$,因为 prefill 是 compute-bound)
- $T_{\text{decode}}(b)$:batch size $b$ 时 decode 一个 token 的耗时(约 $O(b)$,访存带宽限制)
- $N$:prompt 总长度
- $c$:chunk size

朴素的串行:$T^{\text{naive}}_{\text{total}} = T_{\text{prefill}}(N) + k \cdot T_{\text{decode}}(b)$($k$ 为该 prompt 占用期间 decode 的总步数)

Chunked:把 prefill 切成 $\lceil N/c \rceil$ 块,每步 $T_{\text{step}} \approx T_{\text{prefill}}(c) + T_{\text{decode}}(b)$,总时间 $\lceil N/c \rceil \cdot T_{\text{step}}$。

最优 $c$ 在 **prefill 和 decode 计算量均衡** 时取得:

$$
c^{*} \approx \frac{T_{\text{decode}}(b)}{\alpha}
$$

其中 $\alpha$ 是 prefill 的「每 token 计算时间」。实践中 vLLM 的 `max_num_batched_tokens` 默认 2048,意味着 chunk 加上所有 decode token 之和不超过 2048。

#### 1.3.3 Chunked Prefill 的完整作用总结

Chunked prefill 不只是「平滑 TPOT」,它同时解决了 **5 个独立问题** ,每个都有具体的数学或工程依据。

**作用 1:TPOT 平滑(消除 decode 延迟尖峰)**

- 问题:朴素做法下 prefill 一次算完(50 到 500 ms),期间所有 decode 请求等待,TPOT 出现周期性尖峰。
- 解决:切 chunk 后每 step 耗时恒定(chunk 计算加 decode 计算),无尖峰。

```text
朴素:    TPOT = [20ms, 20ms, 500ms!!!, 20ms, 20ms, 400ms!!!, 20ms]
Chunked: TPOT = [50ms, 50ms, 50ms, 50ms, 50ms, 50ms, 50ms]
```

**作用 2:防止 KV Cache OOM(逐 chunk 分配而非一次性分配)**

问题:朴素做法下,一个 100K token 的长 prompt 需要一次性分配 100K token 的 KV cache block。如果当前空闲 block 不够(即使只差一点点),整个请求无法调度,只能等——其他请求释放 KV 后才能开始。

```text
朴素(无 chunked prefill):
  请求 R: prompt = 100K token
  需要 KV cache: 100K × 320KB/token = 32GB
  当前空闲: 20GB
  → 不够! R 无法调度,在 waiting 队列等待
  → 必须等其他请求完成释放足够 KV,R 才能开始
  → 如果不断有新短请求插入,R 可能永远等不到(饥饿)
```

> 全文的「每 token KV」口径:以 Llama-3-70B(80 层、8 个 KV head、head_dim=128、FP16)为例,一个 token 的 KV 总量为 `2(K+V) × 8(kv_head) × 128(head_dim) × 2(FP16) × 80(层)` 等于 320KB。这是 **整个模型所有卡合计** 的量。TP=8 时每张卡只存 1 个 kv_head,单卡分摊 320KB 除以 8 等于 40KB/token。后文凡是「32GB / 2.5GB」这类总量都按 320KB 口径,凡是「单卡 block 数」都按 40KB 口径,不要混用。

解决:chunked prefill 每 step 只分配 chunk_size 个 token 的 KV cache(如 1024 token 约 320MB),不需要一次性满足全部。

```text
Chunked:
  请求 R: prompt = 100K token, chunk_size = 1024
  Step 1: 分配 1024 token 的 KV (320MB) → 够! 开始 prefill
  Step 2: 再分配 1024 token 的 KV → 够! 继续
  ...
  Step 98: 最后一块,完成 prefill
  → 每 step 只需 320MB 空闲,而非 32GB
  → R 几乎立刻可以开始(只要空闲 ≥ 320MB)
```

数学:朴素需要 $\text{free\_blocks} \ge \lceil N/B \rceil$($N$ 为 prompt 长度),chunked 只需 $\text{free\_blocks} \ge \lceil c/B \rceil$($c$ 为 chunk size)。当 $N = 100000$、$c = 1024$、$B = 16$ 时,朴素需要 6250 个 block,chunked 只需 64 个,降低约 100 倍。

**作用 3:限制激活内存(防止 prefill 本身的 OOM)**

问题:prefill 100K token 时,模型前向的中间激活(attention scores、FFN 中间层等)与 token 数成正比。100K token 的激活可能占几 GB——即使 KV cache 够,激活也可能 OOM。

这里要先说清一个容易搞错的点: **推理时的激活是「逐层复用」的** ,算完第 $i$ 层就把第 $i$ 层的中间 buffer 还给显存池给第 $i+1$ 层用(不像训练要留着做 backward)。所以峰值激活取的是 **单层** 的量级,不是「单层乘以层数」。

```text
朴素 prefill 100K token (Llama-3-70B, TP=8, FP16):
  FFN 中间层(单层,单卡):
    [100K, 28672/8=3584] × 2 bytes ≈ 717MB
  再加 qkv / o_proj / residual 等若干个同数量级 buffer
  → 单卡峰值激活几 GB,叠上权重 17.5GB 后逼近甚至超出 80GB 的余量
  (attention scores [100K, 100K] 不会被 materialize —— FlashAttention 分块算,
   但它的 workspace 同样正比于 token 数)
```

解决:chunked prefill 每 step 只算 chunk_size 个 token,激活内存与 chunk_size 成正比,与 prompt 总长无关。

```text
Chunked prefill (chunk = 2048, 即默认 token budget):
  FFN 中间层(单层,单卡): [2048, 3584] × 2 bytes ≈ 14MB
  → 激活内存恒定在几十 MB 量级,不随 prompt 长度增长
```

**作用 4:使连续批处理真正「连续」**

问题:朴素做法下,一个长 prefill 占用整个 step(几百 ms),期间无法加入新请求——与连续批处理的「每 step 动态增减」目标矛盾。

```text
朴素:
  step N: prefill(R, 100K token) ———— 500ms ————
          (期间无法加新请求,无法 decode)
  step N+1: 终于可以 decode + 加新请求
```

解决:chunked prefill 让每 step 的 token 数有上限(不超过 `max_num_batched_tokens`),调度器每 step 都能做决策——加新请求、移除完成请求、给 decode 分配 token。

```text
Chunked:
  step N:   [R_chunk1(2046)] + [A_decode(1), B_decode(1)]        ← 混合!
  step N+1: [R_chunk2(2045)] + [A_decode(1), B_decode(1), C_new(1)]  ← C 加入
  step N+2: [R_chunk3(2045)] + [A_decode(1), B_done, C_decode(1)]    ← B 完成
  → 每 step 都在动态增减,真正「连续」
```

**作用 5:公平性(防止长 prompt 饿死短请求)**

- 问题:朴素做法下,先到的长 prompt 独占 GPU 几百 ms,后到的短请求(即使只需 10 ms prefill)必须等待。
- 解决:chunked prefill 让长 prompt 分多个 step 处理,每个 step 只占一部分 budget,剩余 budget 给 decode 和新请求。

```text
朴素:
  t=0:   R(长 prompt) 开始 prefill
  t=500: R prefill 完,才能处理 S(短 prompt)
  → S 等了 500ms

Chunked:
  t=0:   R_chunk1(1948) + S_prefill(100)   ← S 立刻开始!
  t=50:  R_chunk2(2047) + S_decode(1)
  → S 几乎不用等
```

**总结表**

| 作用 | 朴素的问题 | Chunked 的解决 | 数学依据 |
|---|---|---|---|
| TPOT 平滑 | prefill 阻塞 decode 500ms | 每 step 混合 prefill 加 decode | $T_{\text{step}} \approx T_p(c) + T_d(b)$,恒定 |
| KV cache OOM | 需一次性分配 N token 的 KV | 每 step 只分配 c token 的 KV | 需求从 $\lceil N/B \rceil$ 降到 $\lceil c/B \rceil$ |
| 激活 OOM | 100K token 的单层激活几 GB | 每 step 只算 c token 的激活 | 激活正比于 $c$,与 $N$ 无关 |
| 连续批处理 | 长 prefill 占满 step,无法增减请求 | 每 step 有 budget 上限,可动态增减 | $c \le$ `max_num_batched_tokens` |
| 公平性 | 长 prompt 饿死短请求 | 每 step 只占部分 budget | budget 共享池机制 |

一句话:chunked prefill 不只是「让 decode 不等 prefill」,它同时把 **KV cache 分配粒度、激活内存、调度粒度、公平性** 都从「整个 prompt」降到「单个 chunk」——5 个维度的 OOM、延迟、公平问题一起解决。

> 🖼️ 占位:chunked prefill 的五个作用。回答「把粒度从整个 prompt 降到单个 chunk 之后,分别在时间轴、KV block、激活 buffer、调度决策点、等待队列这五处各带来什么变化」。

### 1.4 统一的 token 追踪模型

V1 调度器最优雅的设计是 **取消了 prefill/decode phase 的概念** 。每个请求只有两个计数器:

- `num_computed_tokens`:已经过模型前向、KV cache 已就绪的 token 数。
- `num_tokens_with_spec`:该请求当前一共有多少个 token 需要被算过,等于「prompt 加已生成的 output」再加上「推测解码给出的草稿 token」。

调度器的目标: **为每个请求分配 token,让 `num_computed_tokens` 追上 `num_tokens_with_spec`** 。

| 场景 | `num_computed_tokens` | `num_tokens_with_spec` | 含义 |
|---|---|---|---|
| 新请求刚到 | 0 | $N$(prompt 长度) | 全 prefill |
| prefill 中途 | 512 | $N$ | 还有 $N-512$ 待算 |
| prefill 完成 | $N$ | $N$ | 进入 decode |
| decode 一个 token | $N$ | $N+1$ | 还有 1 待算 |
| 推测解码(4 个 spec) | $N+k$ | $N+k+4$ | 一次算 4 个 |

每 step 调度器决定 **本次为每个请求算多少新 token** :基本量就是两个计数器的差,再受 token budget、单请求长 prefill 阈值、模型最大长度等一并压小。开了异步调度时,差值里还要加上「已经调度出去、但输出还没回来的占位 token 数」,避免同一批 token 被重复调度。

这个统一模型让 chunked prefill、continuous batching、speculative decoding 三者在调度层面 **完全正交** ——推测解码只是让 `num_tokens_with_spec` 一次多加几个,调度器完全不感知。

> 🖼️ 占位:两个计数器的追赶过程。回答「一条请求从进门到结束,这两个计数器各自怎么走、每 step 的差值怎么变成本次要算的 token 数」。

### 1.5 Token Budget:每 step 的计算量上限

#### 1.5.1 什么是 token budget

每 step 调度器有一个 **token budget** (由 `--max-num-batched-tokens` 控制,默认 2048)。它定义了 **单次 model forward 最多处理多少个 token** ——包括所有 prefill chunk token 和所有 decode token 的总和。

```text
一个 step 的 batch:
  请求 A (decode):    1 token      ┐
  请求 B (decode):    1 token      │ 总和 ≤ token_budget (2048)
  请求 C (prefill):   1024 token   │
  请求 D (prefill):   500 token    ┘
  总计: 1526 token ≤ 2048 ✓
```

调度器实际用的字段是 `Scheduler.max_num_scheduled_tokens`,它这样取值:

```python
self.max_num_scheduled_tokens = (
    self.scheduler_config.max_num_scheduled_tokens
    if self.scheduler_config.max_num_scheduled_tokens is not None
    else self.scheduler_config.max_num_batched_tokens
)
```

即:`max_num_scheduled_tokens` 没显式设时就等于 `max_num_batched_tokens`。此外 `schedule()` 里还有第二条预算线 `input_budget`,它 **始终取** `max_num_batched_tokens`,用于约束 model runner 输入张量的上限;两者在只设了 `max_num_batched_tokens` 的默认情况下同值。

#### 1.5.2 为什么需要 token budget:3 个约束的交集

token budget 不是随意设的——它同时满足 3 个物理约束。下面的数字统一以 Llama-3-70B、8 张 H100、TP=8、FP16 为例, **全部是量级参考,不是本仓库实测** 。

**约束 1:GPU 单 step 计算时间上限(控制 TPOT)**

一次 forward 的耗时与 token 数近似成正比(prefill 是 compute-bound)。如果不限制 token 数,一个 step 可能算 100K token,耗时好几秒——期间所有 decode 请求的 TPOT 一起被拖住。

```text
参照量: 70B 在 8×H100 上的 prefill 吞吐约 1.5 万 token/s
       → 每 token prefill ≈ 65µs(含 TP 通信与 kernel 开销的端到端值)

token_budget = 2048:
  一个「被 prefill 占满」的 step ≈ 2048 × 65µs ≈ 133ms
  → 这是单 step 耗时的上界;纯 decode 的 step 要快得多(见下)

无 budget 限制:
  100K token → 100000 × 65µs ≈ 6.5s
  → 这一个 step 里所有 decode 请求都卡住 6.5 秒
```

要注意「133ms」是 **上界而非典型值** :只有当这一步的 2048 个 token 几乎全是 prefill chunk 时才会到这个量级。纯 decode 的 step 里 token 数等于 batch 内请求数(比如 64 个请求就是 64 个 token),是 memory-bound,耗时通常只有 10 到 30 ms。

**约束 2:激活内存上限(防止 OOM)**

model forward 的中间激活(FFN 中间层、attention workspace)与 token 数成正比。token budget 限定了激活内存的上限。

如 1.3.3 所说,推理时激活是 **逐层复用** 的,峰值取单层的量级,且在 TP 下按卡切分:

```text
70B, FP16, TP=8, 单层 FFN 中间层(单卡):
  每 token: 28672 / 8 = 3584 维 × 2 bytes = 7KB

token_budget = 2048:
  单层激活 ≈ 2048 × 7KB = 14MB
  叠上 qkv / o_proj / residual / attention workspace 等同数量级 buffer,
  峰值大致在几十 MB → 完全可控

无 budget (100K token):
  单层激活 ≈ 100000 × 7KB = 700MB
  加上其余 buffer 后是几 GB 量级 → 挤压 KV cache 甚至 OOM
```

绝对值看起来不大,但它是 **线性增长且不可预测** 的那一项——启动期的 profile run 是按 `max_num_batched_tokens` 探测峰值显存的(见 1.6.5),budget 一旦放大,留给 KV cache 的空间就要相应收缩。

**约束 3:KV cache 单 step 分配上限(配合 chunked prefill)**

每 step 新处理的 token 需要写入 KV cache。token budget 限定了单 step 的 KV cache 增长量,防止一步吃掉太多 block。

```text
每 token KV: 320KB(全模型合计) / 40KB(单卡, TP=8)
token_budget = 2048:
  单 step KV 增长 ≤ 2048 × 40KB = 82MB/卡  ← 可控

无 budget:
  单 step 可能增长 100K × 40KB = 4GB/卡   ← 一步吃掉大块 KV cache
```

#### 1.5.3 token budget 与 chunked prefill 的关系

**token budget 就是 chunked prefill 的 chunk size 上限。** 调度器在分配 budget 时:

```text
请求 C: prompt = 100K token, 需要预填充
  剩余 budget = 2048 - 2(decode) = 2046
  → 本 step 给 C 分配 min(100K, 2046) = 2046 token
  → C 的 chunk size = 2046(不是整个 100K)
  → 下 step 继续分,直到 100K 算完(约 49 步)
```

注意 vLLM **没有** 「每个 chunk 固定多少 token」的配置。单 chunk 的实际大小是三者取最小:

```text
min(还差多少没算,          # num_tokens_with_spec - num_computed_tokens
    本 step 剩余预算,       # token_budget
    输入张量剩余额度)       # input_budget - draft_slots
```

再被 `long_prefill_token_threshold` 截断(默认 0 表示不截断)。所以 chunk 大小 **每一步都在变** ——同 batch 里 decode 请求多的那一步,prefill chunk 就小。

如果关掉 chunked prefill(`enable_chunked_prefill=False`),调度器看到该请求需要的 token 数超过它这一轮能给的额度时,会直接 `break` 不切 chunk,等 budget 够时一次性算——这就是 1.3.3 说的「退化」。

#### 1.5.4 token budget 的分配规则:RUNNING 优先

token budget 是一个 **单调递减的共享池** ——RUNNING 队列先消费,剩余的给 WAITING 队列:

```text
token_budget = max_num_scheduled_tokens   // 初始值 = 2048(默认)

阶段 1: 先给 RUNNING 队列
  for req in running:
      num_new_tokens = 还差多少没算(见 1.4)
      num_new_tokens = min(num_new_tokens, token_budget, 输入张量剩余额度)
      分配 KV blocks
      token_budget -= num_new_tokens        // 扣减

阶段 2: 再给 WAITING 队列(如果 budget 还有剩)
  while (waiting 或 skipped_waiting) 非空 and token_budget > 0:
      看队首请求(peek,不出队)
      计算它的 num_new_tokens
      分配 KV blocks
      成功才出队,token_budget -= num_new_tokens
```

为什么 RUNNING 优先:

- RUNNING 请求的 KV cache 已经在 GPU 上,每 step 都需要继续 decode,否则用户感知到的 TPOT 会飙升。
- WAITING 请求是「新增的」,可以等几个 step,用户对 TTFT 的容忍度比对 TPOT 高。

例外:Priority 策略下,高优先级的 WAITING 请求可能比低优先级的 RUNNING 请求先调度(详见 1.7)。

#### 1.5.5 token budget 调参的 trade-off

沿用 1.5.2 的 65µs/token 口径,「满载 step 耗时」列指的是被 prefill 占满时的上界:

| budget 值 | 满载 step 耗时 | 吞吐 | TPOT | TTFT | 适用场景 |
|---|---|---|---|---|---|
| 小(512) | 约 33ms | 低 | **低(好)** | 低 | 低延迟优先(实时 chat) |
| **默认(2048)** | 约 133ms | 中 | 中 | 中 | 通用平衡 |
| 大(8192+) | 约 530ms | **高** | 高(差) | 高 | 吞吐优先(离线批量) |

**核心 trade-off** :budget 大则每 step 算更多 token、吞吐高,但单 step 耗时长、decode 请求等得久、TPOT 高。反之亦然。

在线服务里常见的做法是把 budget 设到「单 step 满载耗时约等于可接受的 TPOT 上限」:想保 TPOT 低于 50ms,就把 budget 压到 512 到 1024;离线批量不在乎 TPOT,调到 8192 甚至 16384 换吞吐。这是经验做法,不是仓库里的配置建议。

> 🖼️ 占位:token budget 的三条约束与调参曲线。回答「同一个 budget 值同时被计算时间、激活内存、KV 增量三个上限约束,调大调小分别先撞到哪一条」。

### 1.6 并发上限:`max_num_seqs` 与三道闸门

`max_num_seqs`(默认 128)是 RUNNING 队列的硬上限——同一时刻最多有这么多请求在跑。但实际并发数可能更低,因为有 **3 道闸门** 同时限制。

#### 1.6.1 三道闸门

```text
新请求想进入 RUNNING → 必须同时通过 3 道闸门:

闸门 1: max_num_seqs(默认 128)
  ┌────────────────────────────────────────┐
  │ len(running) + 暂停的流式会话数 < 上限? │
  │   num_running = len(self.running) +     │
  │     self.num_waiting_for_streaming_input│
  │   if num_running >= max_num_running_reqs│
  │       break   # 停止从 WAITING 拉新请求 │
  │ (max_num_running_reqs 就是 max_num_seqs)│
  └────────────────────────────────────────┘
                    │ 通过?
                    ▼
闸门 2: KV cache 容量
  ┌────────────────────────────────────────┐
  │ allocate_slots() 返回非 None ?          │
  │   new_blocks = kv_cache_manager          │
  │     .allocate_slots(request, ...)        │
  │   if new_blocks is None: break           │
  │ 即使 running < max_num_seqs,             │
  │ KV cache 不够也进不来 —— 而且是 break,   │
  │ 本 step 后面的 waiting 请求一并不再尝试  │
  └────────────────────────────────────────┘
                    │ 通过?
                    ▼
闸门 3: token budget(max_num_batched_tokens)
  ┌────────────────────────────────────────┐
  │ token_budget > 0 ?                      │
  │   while (self.waiting or                 │
  │          self.skipped_waiting) and       │
  │         token_budget > 0:                │
  │ budget 被 running 请求消耗完后,          │
  │ waiting 里的请求等下个 step               │
  └────────────────────────────────────────┘
                    │ 通过?
                    ▼
             请求进入 RUNNING
```

**实际并发等于三道闸门能同时通过的请求数中的最小者。**

注意闸门 2 的行为是 `break` 而 **不是** 「跳过该请求继续试下一个」——WAITING 队列是有序的,队首都放不下,后面的更放不下。

> 🖼️ 占位:三道闸门。回答「一个新请求从 WAITING 进 RUNNING 要连过哪三关,每关卡住时是 break 还是 continue,分别等到什么条件才放行」。

#### 1.6.2 三道闸门的具体场景

以默认 `max_num_seqs=128`、`max_num_batched_tokens=2048` 为例(KV 容量列是按显存估的量级示意):

| 场景 | 闸门1 (max_seqs) | 闸门2 (KV cache) | 闸门3 (budget) | 实际并发 | 瓶颈 |
|---|---|---|---|---|---|
| 短序列 + 大 GPU | 128 | 够 600 个 | 2048 够 | **128** | 闸门1 |
| 长序列(8K token/请求) | 128 | 只够 160 个 | 2048 够 | **128** | 闸门1 |
| 超长序列(64K token/请求) | 128 | 只够 20 个 | 2048 够 | **20** | 闸门2 |
| 新请求持续涌入 | 128 | 够 | 2048 被 prefill 吃完 | 爬升慢 | 闸门3 |

第 4 行值得解释: **闸门 3 不封顶并发数,而是限制并发数的爬升速度。** 默认 budget 只有 2048,一个 2000-token 的新 prompt 就能吃掉一整个 step 的预算,所以「从 0 涨到 128 并发」需要几十个 step;短 prompt 场景下几个 step 就满了。

#### 1.6.3 超过 `max_num_seqs` 时的行为

```text
用户瞬间提交 1000 个请求 (max_num_seqs=128, budget=2048)

t=0    1000 个请求全部进入 WAITING 队列
       WAITING: [R1, R2, ..., R1000]  (1000 个)
       RUNNING: []  (空)

t=1    schedule() 从 WAITING 拉请求:
         闸门1: len(running)=0 < 128 ✓
         闸门2: KV cache 够 ✓
         闸门3: budget 2048 > 0 ✓
         → 假设每个 prompt 200 token, 本 step 只拉得下 10 个
           (10 × 200 = 2000 ≤ 2048, 第 11 个把 budget 撑破 → break)
       RUNNING: [R1..R10]
       WAITING: [R11..R1000]

t=2..k 每 step 继续拉, 但已 running 的请求要先吃 decode 预算
       → 并发数逐步爬升, 大约十几个 step 后到 128

t=k    闸门1: len(running)=128 >= 128 → break!
       → WAITING 不动, R129..R1000 继续等
       → RUNNING 里的 128 个持续 decode

t=某步 R5 生成 EOS → 从 RUNNING 移除, 释放 KV
       RUNNING: 127 个 → 有空位!
       → 下个 step schedule() 从 WAITING 拉 R129
       → R129 开始 prefill

...    持续到所有请求完成
       WAITING 队列没有大小上限, 1000/10000 个都能排
       但排队越久 TTFT 越高
```

关键:

- WAITING 队列 **无大小上限** ——多少请求都能排。
- 新请求要等 RUNNING 里出现空位(有请求完成,或被抢占踢出)才能进—— **不是时间片轮转,是「等空位」** 。
- 排队期间 TTFT 持续增长(用户等待首 token 的时间越来越长)。
- 并发数不是一步跳到 128 的,受 budget 限制逐 step 爬升。

#### 1.6.4 KV cache 不够时的额外行为:抢占

即使 `running < max_num_seqs`,KV cache 也可能不够。但要说清楚 **抢占是谁触发的** :

**抢占只发生在 RUNNING 循环里** ,触发方是 **一个已经在 running 的请求** ——它这一步要写新 token(decode 写第 N+1 个位置、prefill chunk 续算、或 spec/lookahead 要预留槽位),`allocate_slots` 却拿不到 block。此时调度器牺牲 **别的** running 请求来给它腾地方。

**WAITING 队列拿不到 block 时不会抢占** ,只是 `break` 掉本轮的 WAITING 调度,新请求下个 step 再试:

```python
new_blocks = self.kv_cache_manager.allocate_slots(...)
if new_blocks is None:
    # The request cannot be scheduled.
    if request.has_encoder_inputs:
        self.encoder_cache_manager.free(request)
    break        # ← 不抢占
```

所以正确的场景是这样的:

```text
running: [A(len=5000), B(len=3000), C(len=2000)]
KV cache 已用 100%, block pool 空

本 step 调度 RUNNING:
  A 要 decode 第 5001 个 token, 恰好跨到新 block
  allocate_slots(A, 1) → None (一个 block 都没有)
  → 抢占队尾的 C (FCFS): 释放 C 的全部 KV, C.num_computed_tokens=0,
    C 回到 waiting 队首
  → 重试 allocate_slots(A, 1) → 成功
  → running: [A, B]; A/B 正常 decode, C 下轮重新 prefill

(若 A 是队尾, 循环会一路抢到把 A 自己也抢占,
 此时直接 break, A 本轮不调度)
```

而「新请求 D 到达但 KV 不够」的结局只是:D 留在 waiting,下个 step 再试;等某个 running 请求完成或被抢占释放了 KV,D 才进得来。

牺牲品的选法随策略而变:FCFS 取 running 队尾(最晚入座的),Priority 取优先级最低、同级里到达最晚的那个。

> 🖼️ 占位:抢占的触发与恢复。回答「谁触发抢占、牺牲谁、被抢者的状态和计数器怎么变、它下一轮从哪里重新开始」。

#### 1.6.5 KV cache 容量怎么算:`gpu_memory_utilization` 的作用

闸门 2(KV cache 容量)不是用户直接配置的——它由 `gpu_memory_utilization`(默认 0.92)间接决定。vLLM 在启动时通过一次 **profile run(内存探测)** 自动计算可用 KV cache 空间,然后换算成 block 数量。

**计算链路(从参数到 num_blocks)**

```text
用户配置: --gpu-memory-utilization 0.92(默认)
   │
   ▼
① requested_memory = GPU 总显存 × gpu_memory_utilization
   │  request_memory():
   │    requested_memory = math.ceil(
   │        init_snapshot.total_memory * cache_config.gpu_memory_utilization)
   │  例: 80GB GPU × 0.92 = 73.6GB
   │  (free_memory < requested_memory 时直接抛 ValueError)
   │
   ▼
② profile run: 跑一次 dummy forward, 探测非 KV cache 的显存占用
   │  with memory_profiling(...) as profile_result:
   │      self.model_runner.profile_run()   ← 用假数据跑一次完整 forward
   │  测量: 权重显存 + 峰值激活显存; CUDA Graph 显存单独估算
   │  例: 权重 17.5GB + 激活 2GB + CUDA Graph 1GB = 20.5GB
   │
   ▼
③ available_kv_cache_memory = requested_memory - 非KV显存
   │  self.available_kv_cache_memory_bytes = (
   │      self.requested_memory
   │      - profile_result.non_kv_cache_memory
   │      - cudagraph_memory_estimate_applied)
   │  例: 73.6GB - 20.5GB = 53.1GB
   │
   ▼
④ 每 block 的字节数 = 2 (K+V) × num_layers × num_kv_heads
   │                    × block_size × head_dim × dtype_size
   │  ★ 必须乘 num_layers —— 每一层都有自己的一份 K/V
   │  例 (Llama-3-70B, 80 层, TP=8, FP16):
   │    2 × 80 × (8/8=1 kv_head) × 16 (block_size) × 128 (head_dim) × 2
   │    = 655,360 bytes = 640KB/block (单卡)
   │
   ▼
⑤ num_gpu_blocks = available_kv_cache_memory / 每 block 字节数
   │  由 get_kv_cache_configs() 换算
   │  例: 53.1GB / 640KB ≈ 8.7 万 blocks (单卡, 简化估算)
   │
   ▼
⑥ engine 侧记录可用显存并生成 KV cache 配置
   │  available_gpu_memory = self.model_executor.determine_available_memory()
   │  self.available_gpu_memory_for_kv_cache = available_gpu_memory[0]
   │  kv_cache_configs = get_kv_cache_configs(
   │      vllm_config, kv_cache_specs, available_gpu_memory)
   │
   ▼
⑦ BlockPool(num_gpu_blocks) 初始化
   │  scheduler 的闸门 2 就是这个 block 池
   │  每个请求分配 block, 完成释放, 满了就触发抢占
```

**具体数字示例** (Llama-3-70B、8 张 H100 80GB、TP=8、FP16;以下全是量级示意,不是本仓库实测)

```text
GPU 总显存:          80 GB/卡
gpu_memory_utilization: 0.92 (默认)
requested_memory:    80 × 0.92 = 73.6 GB

Profile run 测量:
  模型权重 (70B / 8卡, FP16):  70B × 2B / 8 = 17.5 GB/卡
  峰值激活 (max_num_batched_tokens=2048): 约 0.5 GB
  CUDA Graph (若干 bucket):      约 1 GB
  其他 (PyTorch runtime 等):     约 0.5 GB
  ─────────────────────────────────
  非 KV cache 显存合计:          约 19.5 GB

available_kv_cache_memory = 73.6 - 19.5 = 54.1 GB

每 block 大小 (80 层, TP=8 → 单卡 1 个 kv_head, block_size=16):
  2 × 80 × 1 × 16 × 128 × 2 = 655,360 bytes = 640 KB

num_gpu_blocks = 54.1 GB / 640 KB ≈ 88,600 blocks

每 token KV (单卡) = 640KB / 16 = 40 KB/token
  → 54.1GB / 40KB ≈ 142 万 token 的 KV cache
  → 假设平均请求 2000 token: 理论可容纳约 700 个请求
  → 实际受 max_num_seqs=128 限制, 通常先撞闸门 1
  → 但若平均请求涨到 11000 token, 128 × 11000 = 141 万,
    就正好把 KV cache 吃满 → 闸门 2 成为瓶颈, 开始出现抢占
```

最后那一行是这套换算真正有用的地方:它给出了 **「从闸门 1 瓶颈切换到闸门 2 瓶颈」的临界序列长度** 。用「KV 容量(token 数)除以 `max_num_seqs`」就能估出来——本例约 11K token。线上平均序列长度接近这个数时,就该考虑降 `max_num_seqs` 或升 `gpu_memory_utilization`。

顺带纠正一个容易想当然的点:vLLM 确实有一个 `watermark`(保留一小部分 block 不分配),但它 **默认是 0,也就是关闭的** 。所以默认配置下 block 数不会因为 watermark 而打折。

**`gpu_memory_utilization` 调参的影响**

```text
                    util=0.85    util=0.92 (默认)  util=0.95
                    ─────────    ───────────────   ─────────
requested_memory     68 GB         73.6 GB          76 GB
非 KV 显存           19.5 GB (固定) 19.5 GB          19.5 GB
KV cache 可用        48.5 GB       54.1 GB          56.5 GB
num_blocks           约 79,400     约 88,600        约 92,500
可容纳 token         约 127 万     约 142 万        约 148 万
临界序列长度         约 9.9K       约 11.1K         约 11.6K
抢占频率             高 (KV 少,易撞满)  中          低
OOM 风险             低            低               中 (激活峰值可能超)
```

注意「抢占频率」与「OOM 风险」是 **反向的两条曲线** :util 调低是把显存从 KV cache 挪给激活余量,KV 变小则更容易撞满、抢占 **变多** ;util 调高则 KV 变大、抢占变少,但激活突然涨大(比如临时调高了 `max_num_batched_tokens`)时会 OOM。

- 调高 util:KV cache 更大,支持更多并发、更长序列、更少抢占,但留给激活的余量少,如果 batch 或 budget 突然变大可能 OOM。
- 调低 util:KV cache 更小,并发少、序列短、抢占更频繁,但更安全,不会 OOM。

**关键** :`gpu_memory_utilization` 不是「KV cache 占多少显存」,而是「vLLM 总共最多用多少 GPU 显存」。KV cache 拿到的是 **减掉权重和激活后的剩余部分** 。

> 🖼️ 占位:从 `gpu_memory_utilization` 到 block 池的换算链路。回答「一张 80GB 卡上,总显存怎么一层层减成 KV cache,再除成多少个 block」;把权重、激活、CUDA Graph、KV 四段画成一根显存条。

### 1.7 抢占:当显存耗尽时

抢占的唯一触发点是: **某个已在 RUNNING 队列里的请求,这一步要写新 token,但 `allocate_slots()` 拿不到 block** 。具体成因有三类:

- **decode 跨 block** :running 请求序列越写越长,第 N+1 个 token 恰好要开一个新 block,而 block pool 已空。
- **prefill chunk 续算** :running 里的 prefill chunk 要接着算下一块,需要新 block。
- **spec decode / lookahead 预留** :`num_lookahead_tokens` 要求提前预留槽位,把需求量放大了。

此时调度器必须 **抢占别的请求** ,把它们的 KV cache 释放出来给触发者。

需要明确排除两种 **不会** 导致抢占的情况:

- **WAITING 里的新请求拿不到 block** :只 `break` 掉本轮 WAITING 调度,请求留在队列里下个 step 再试。
- **请求数超过 `max_num_seqs`** :只 `break`,排队等空位。

换句话说,抢占永远是 **「已经在跑的请求之间互相挤」** ,不是「新请求把老请求挤下去」。

#### 1.7.1 抢占只有 recompute 一种模式(没有 swap)

被抢占的请求,理论上有两种去处:

- **swap(换出)** :把它的 KV cache 拷到 CPU 内存里存着,下次被调度时再拷回 GPU。
- **recompute(重算)** :直接丢弃 KV cache,下次被调度时当作新请求重新 prefill。

vLLM 调度器 **只实现了 recompute** —— `vllm/v1/` 目录下不存在任何 swap 路径(没有 `swap_in` / `swap_out` / `PreemptionMode` 之类的符号),`_preempt_request` 唯一的动作就是释放 block 并把请求退回 waiting 队列。三条理由:

1. **swap 的搬运本身就不划算** :KV 要经 PCIe 往返一次。以 640KB/block 的量级算,换出几百个 block 就是几百 MB 的双向拷贝,耗时与直接重算 prefill 同量级,还要额外维护 CPU 侧显存池和拷贝流。
2. **prefix caching 把重算摊薄了** :被抢占的请求重新 prefill 时,已缓存的公共前缀 block 可以直接命中复用,实际只需重算被释放掉的那部分尾巴,而不是整条 prompt。
3. **调度逻辑不用分叉** :没有 swap 就没有「这个请求的 KV 在 CPU 还是 GPU」的第二种状态,请求状态机与主循环都因此少一整类分支。

这里有个实现细节值得记一笔:被抢占的请求状态并不是直接变回 `WAITING`,而是先置成一个专门的 `PREEMPTED` 状态,再 **插到 waiting 队列的最前面** 。用独立状态而不是复用 WAITING,是为了让后续逻辑能认出「这是重来的,不是新来的」。

#### 1.7.2 选择谁被抢占

| 策略 | 选择标准 | 直觉 |
|---|---|---|
| **FCFS(默认)** | `self.running.pop()`——弹出列表 **末尾** (最新加入的) | 先到先服务:早到的请求被保护 |
| **Priority** | `max(running, key=(priority, arrival_time))` | 优先级数值最大(即最低优先级)的先被抢占 |

**FCFS 的微妙设计** :`running` 是一个 `list`,新请求通过 `self.running.append(req)` 加入。`pop()` 弹出最后一个,也就是最新加入的。这保护了「老」请求。

#### 1.7.3 recompute 的代价

被抢占的请求 `num_computed_tokens` 被重置为 0,所有已生成的 token 仍在输出序列里,但 KV cache 没了。下次调度时整个请求从头 prefill(如果开了 prefix caching 则公共前缀 block 可复用)。同时它的草稿 token 会被清空、抢占次数计数加一。

代价:浪费了之前 prefill 加上所有 decode 的计算量。所以 **抢占是最后的手段** ,正常情况下应该通过 `--gpu-memory-utilization` 调到合适值,让调度器很少需要抢占。

> 🖼️ 占位:抢占前后的状态与计数器。回答「被抢者的 block、状态、num_computed_tokens、草稿 token 各发生什么,它回到队列的哪个位置,下轮从哪里重新开始」。

### 1.8 调度策略:FCFS vs Priority

| 维度 | FCFS(先到先服务) | Priority(优先级) |
|---|---|---|
| 底层结构 | `collections.deque` | `heapq`(最小堆) |
| 排序键 | 插入顺序 | `(priority, arrival_time, request_id)` |
| 典型场景 | 通用、公平 | SLA 分级(免费与付费用户) |
| 配置 | `--scheduling-policy fcfs`(默认) | `--scheduling-policy priority` |
| API | 请求按到达顺序排队 | 请求需指定 `priority` 字段 |

Priority 排序由 `Request.__lt__` 定义:

```python
def __lt__(self, other: "Request") -> bool:
    if self.priority != other.priority:
        return self.priority < other.priority       # priority 小的优先(数值小=高优先)
    if self.arrival_time != other.arrival_time:
        return self.arrival_time < other.arrival_time  # 同优先级, 早到的优先
    if self.request_id != other.request_id:
        return self.request_id < other.request_id      # 再用 id 稳定排序
    return id(self) < id(other)                        # 兜底: 对象地址
```

Priority 用 **数值小等于高优先级** (与 Unix `nice` 一致)。

这里和 1.7.2 的抢占选法正好互补:入队时用 `__lt__` 取最小(优先级最高的先服务),抢占时用 `max` 取最大(优先级最低的先牺牲),两处用的是同一个排序键。

> 🖼️ 占位:两种策略的队列行为对比。回答「同一批请求在 deque 与最小堆里的出队顺序,以及 Priority 下高优先级新请求如何插到前面」。

```text
  (某个 running 请求    │              │

  ┌────────────┐ ┌────────────┐ ┌────────────┐
```

`WAITING → RUNNING` 这条边要求「分配 KV 成功」;分配失败 **不会** 让它变成 `PREEMPTED` ——它原地留在 WAITING。只有已经在 RUNNING 的请求才会被抢占,而且触发者是 **另一个** (也可能是它自己)要不到 block 的 running 请求。

完整状态枚举里,除了图上这几个,还有三个 **阻塞态** :等结构化输出文法就绪、等远端 KV 传完、等流式请求的下一段输入。终态则不止图上两类,除了正常停止与长度封顶,还有被中止、被忽略、出错、检测到重复共六种。判定「是否已完成」用的是一个巧妙写法: **枚举顺序上排在 `PREEMPTED` 之后的一律算完成** ,所以新增终态只要往枚举末尾加就行,不用改判定逻辑。

### 2.2 单 step 决策流程

```text
EngineCore.step()
  │
  ▼
scheduler.schedule(throttle_prefills)
  │
  ├─ ① 初始化预算
  │     token_budget = max_num_scheduled_tokens (默认 2048)
  │     input_budget = max_num_batched_tokens   (默认 2048)
  │     如果整体暂停: token_budget = 0
  │
  ├─ ② 调度 RUNNING 队列 (按 running 列表顺序, 游标 req_index)
  │     while req_index < len(running) and token_budget > 0:
  │       req = self.running[req_index]
  │       num_new_tokens = req.num_tokens_with_spec
  │                      + req.num_output_placeholders
  │                      - req.num_computed_tokens
  │       num_new_tokens = min(num_new_tokens, token_budget,
  │                            input_budget - draft_slots, max_model_len 余量)
  │       if num_new_tokens == 0: req_index += 1; continue   # 跳过, 不停
  │       while True:
  │         new_blocks = kv_cache_manager.allocate_slots(req, num_new_tokens)
  │         if new_blocks is not None: break
  │         ★ 触发抢占 (牺牲别的 running 请求给 req 腾地方)
  │         preempted_req = running.pop()                # FCFS: 队尾
  │                       / max(running, key=(priority, arrival_time))  # Priority
  │         self._preempt_request(preempted_req)         # num_computed_tokens=0
  │         if preempted_req == req: break               # 连自己都抢了
  │       if new_blocks is None: break     # req 本轮无法调度, 整个循环终止
  │       token_budget -= num_new_tokens
  │       input_budget -= num_new_tokens + draft_slots
  │       req_index += 1
  │
  ├─ ③ 调度 WAITING 队列 (前提: 本轮无任何抢占 + 未暂停)
  │     while (waiting or skipped_waiting) and token_budget > 0:
  │       if len(running) + 暂停的流式会话数 >= max_num_seqs:
  │         break
  │       queue = _select_waiting_queue_for_scheduling()
  │       req = queue.peek_request()              # ★ 只看不出队
  │       ┌ 依赖类阻塞 (KV 还在传 / LoRA 满 / stale output 未排空 / mm 未就绪)
  │       │   → queue.pop_request(); step_skipped_waiting.prepend(req); continue
  │       └ 预算类不足 → break
  │       查前缀缓存: _get_local_prefix_cache_hit(req)
  │                   (+ connector.get_num_new_matched_tokens 查远端)
  │       num_new_tokens = req.num_tokens - num_computed_tokens
  │       if 禁用 chunked_prefill and num_new_tokens > 剩余预算:
  │         break                                 # prefill 不能切断
  │       num_new_tokens = min(num_new_tokens, 剩余预算)
  │       new_blocks = kv_cache_manager.allocate_slots(req, num_new_tokens)
  │       if new_blocks is None: break            # WAITING 不抢占, 直接停
  │       req = queue.pop_request()               # ★ 分配成功才真正出队
  │       token_budget -= num_new_tokens
  │       req.status = RUNNING
  │       self.running.append(req)
  │
  ├─ ④ 构建 SchedulerOutput
  │
  ├─ ⑤ _update_after_schedule()
  │     for req_id, num in num_scheduled_tokens.items():
  │       self.requests[req_id].num_computed_tokens += num
  │       重算 is_prefill_chunk
  │
  └─ ⑥ 返回 SchedulerOutput (主要字段)
        ├─ scheduled_new_reqs: list[NewRequestData]   # 首次调度的请求
        ├─ scheduled_cached_reqs: CachedRequestData   # 已缓存请求的增量
        ├─ num_scheduled_tokens: dict[req_id, int]
        ├─ total_num_scheduled_tokens: int
        ├─ scheduled_spec_decode_tokens / scheduled_encoder_inputs
        ├─ num_common_prefix_blocks: list[int]        # cascade attention 用
        ├─ finished_req_ids / preempted_req_ids
        └─ kv_connector_metadata                      # PD 分离时非 None
```

注意 ③ 里两种失败的分野: **依赖类阻塞用 `continue`** (请求挪进 `skipped_waiting`,让后面的请求有机会被调度), **预算或显存类不足用 `break`** (队首都放不下,后面的更放不下)。这是 `skipped_waiting` 双队列存在的理由。

②里的 `num_new_tokens == 0` 那条 `continue` 也值得单独看一眼:源码注释明确写了这是 **故意不严格遵守 FCFS** ——排在前面的请求这一轮算不动(比如 PP 下 prompt 已全部排过但还没算完、编码器预算耗尽),就先让后面的请求上,而不是整条队列一起卡住。

### 2.3 Chunked Prefill 时序图

以一个 prompt=4096 的请求 A 为例(`max_num_batched_tokens=2048` 即默认值;chunk 大小由每步剩余 budget 决定):

```text
Step 1:
  running: [B(decode), C(decode)]
  waiting: [A(prompt=4096)]
  调度: B(1) + C(1) + A_chunk1(2046) = 2048 tokens
  A.num_computed_tokens: 0 → 2046

Step 2:
  running: [B, C, A(prefill chunk 进行中)]
  调度: B(1) + C(1) + A_chunk2(2046) = 2048 tokens
  A.num_computed_tokens: 2046 → 4092

Step 3:
  running: [B, C, A(prefill chunk 进行中)]
  调度: B(1) + C(1) + A_chunk3(4) = 6 tokens   ← 最后一块只剩 4 个 token
  A.num_computed_tokens: 4092 → 4096  ← prefill 完成, is_prefill_chunk 变 False

Step 4:
  running: [B, C, A]   ← A 进入 decode
  调度: B(1) + C(1) + A(1) = 3 tokens
```

注意 Step 3 只有 6 个 token—— **chunk 大小不是固定的** ,最后一块是「剩多少算多少」。这也说明 prefill 期间每 step 的实际计算量波动很大(2048 到 6),所谓「TPOT 平滑」是相对于「一次算 4096」而言的上界被压住了,不是每步严格等长。

**关键观察** :每 step 的 token 总数都受 `max_num_batched_tokens` 限制,prefill 和 decode 混合在一起。

### 2.4 抢占回放

抢占的触发者是 **队列里已经在跑的请求** ,不是外面新来的请求。下面这个回放展示 FCFS 下的完整过程:

```text
Step N:
  running: [A, B, C, D]  (按加入 running 的先后排列, 4 个都在 decode)
  KV cache block pool 已空 (所有 block 都被这 4 个请求占着)
  waiting: [E(prompt=2000)]  ← E 只是在排队, 它进不来但也不会引发抢占

Step N+1: 调度 RUNNING 队列
  req_index=0 → A: 要 decode 第 5001 个 token, 恰好跨到新 block
    allocate_slots(A, 1) → None (一个 free block 都没有)

  抢占循环:
    preempted_req = running.pop() → D (列表末尾 = 最晚加入的)
    _preempt_request(D):
      - 释放 D 的所有 KV blocks → 归还 BlockPool
      - D.num_computed_tokens = 0
      - D.status = PREEMPTED
      - waiting.prepend_request(D)   # 放到队首, 下轮优先恢复
    preempted_reqs.append(D)

    重试 allocate_slots(A, 1) → 成功 (D 让出的 block 够了)
    → 跳出抢占循环

  继续 req_index=1,2 → B、C 正常 decode
  running: [A, B, C]

  ★ 因为本轮 preempted_reqs 非空, ③ 整段 WAITING 调度被跳过
    —— 刚抢占完说明显存吃紧, 再放新请求进来只会引发连锁抢占。
    所以 D 和 E 这一步都不会被调度。

Step N+2: 无抢占发生 → 进入 WAITING 调度
  waiting 队首是 D (prepend 进去的) → D 优先重新 prefill
  E 排在 D 后面, 等 D 之后才轮到
```

**极端情况** :如果触发者本身就是队尾(比如 running 只有一个请求,或者要不到 block 的恰好是最后一个),抢占循环会一路抢到把 **触发者自己** 也抢占掉。此时内层 `break` 跳出抢占循环、外层 `break` 终止整个 RUNNING 循环,这一步等于什么都没调度成——但显存被清出来了,下一步就能恢复。

**Priority 策略的差异** :牺牲品不是队尾,而是优先级数值最大(最低优先)的那个,可能位于 `running` 列表中间。所以代码要先定位下标、再移除,并在受害者下标小于当前游标时把游标回退一格,否则会静默漏掉紧随其后的那个请求。

跳过 WAITING 的条件其实还多一个:除了「本轮无抢占」,还要求调度器 **未处于暂停状态** 。

> 🖼️ 占位:抢占回放时序。回答「触发者、牺牲品、block 池、两个队列在三个 step 里各自怎么变」;把「本轮跳过 WAITING」标成一条显式的抑制边。

### 2.5 PD 混合调度(Co-located Prefill-Decode)

PD 混合(co-located,同进程混合)指 prefill 和 decode 在 **同一个 EngineCore 加 scheduler** 中执行——这是 vLLM V1 的 **默认模式** 。

#### 2.5.1 架构总览

```text
┌──────────────────────────────────────────────────────┐
```

核心特征:

- **一个 scheduler 管 prefill 和 decode** ,不区分 phase
- **token_budget 共享池** :prefill 和 decode 从同一个预算里扣
- **一次 forward 混合算** :变长注意力核用累计 query 长度数组分段处理(见 2.7)

#### 2.5.2 V1 的统一调度算法

V1 调度器 **没有显式的 prefill/decode phase 划分** ,只用已算 token 数判断请求当前在哪个阶段:

```python
request.is_prefill_chunk = request.num_computed_tokens < (
    request.num_tokens + request.num_output_placeholders
)
# True:  还在 prefill (未算完 prompt)
# False: 已进入 decode (每次 1 token)
```

这行在每个 step 的调度收尾处重算一次,所以「进入 decode」这件事没有显式的状态迁移,只是一个每步重新求值的布尔量。

#### 2.5.3 一个请求在混合调度下的完整生命周期

```text
请求 D (prompt=3000 token) 到达; token_budget=2048 (默认)

Step 1: D 在 waiting 队列
  schedule():
    ① RUNNING 队列: [A(decode,1), B(decode,1), C(decode,1)]
       budget 消耗 3, 剩余 2045
    ② WAITING 队列: peek 到 D
       D.num_computed_tokens = 0 (新请求)
       num_new_tokens = min(3000, 2045) = 2045   ← 被 budget 切断
       allocate_slots 成功 → D 出队, 加入 running
       D.num_computed_tokens: 0 → 2045  (is_prefill_chunk=True)
  batch: [A_dec(1), B_dec(1), C_dec(1), D_prefill_chunk1(2045)]
  GPU forward 一次算 2048 个 token

Step 2: D 在 running, 续算 prefill 的最后一块
  schedule():
    ① RUNNING: [A(1), B(1), C(1), D_prefill_chunk2(955)]
       num_new_tokens = 3000 - 2045 = 955 (小于剩余 budget, 不再切)
       D.num_computed_tokens: 2045 → 3000
       _update_after_schedule 重算:
         D.is_prefill_chunk: 3000 < 3000? No → D 进入 decode!
  batch: [A_dec(1), B_dec(1), C_dec(1), D_prefill_chunk2(955)] = 958 tokens

Step 3: D 已是 decode 请求
  schedule():
    ① RUNNING: [A(1), B(1), C(1), D(1)]   ← 全是 decode!
    ② WAITING: 空
  batch: [A_dec(1), B_dec(1), C_dec(1), D_dec(1)] = 4 tokens
  ← 纯 decode batch, 可以走 full CUDA Graph (最快的那条路径)

Step 4~N: D 持续 decode, 每 step 1 token
  ...
  直到 D 生成 EOS → D 从 running 移除, 释放 KV block
```

关键观察:

- Step 1 到 2:D 是 prefill chunk,与 A/B/C 的 decode 同 batch 混合算
- Step 3 起:D 变成 decode,batch 全是 decode(可走 full CUDA Graph;含 prefill 的混合 batch 走分段 graph)
- **没有任何 step 会「只做 prefill 不做 decode」或反之** ——两者始终混合
- chunk 的实际大小是 2045 与 955 这样「看剩多少给多少」的值,不存在固定的 chunk_size 配置

#### 2.5.4 DP 场景下的 prefill 节流

数据并行(DP)场景下,多个 replica 各自调度。为避免某 replica 突然涌入大量 prefill 拖垮整体延迟,V1 在 `schedule()` 的入参上引入了节流开关:

```python
defer_prefills = (
    throttle_prefills and not self.prefill_capacity_bound
) and any(not r.is_prefill_chunk for r in self.running)
```

- 节流开启:DP 协调器要求本 replica 本 step 延迟新 prefill。
- 延迟生效时: **已 running 的 prefill chunk 继续算** (必须完成),但 **不拉新 prefill** ——让 decode 请求优先。
- 注意第二个条件:只有当 running 里 **确实存在 decode 请求** 时才延迟。全是 prefill chunk 的时候延迟没有意义,不如接着排。
- 效果:在 DP 多 replica 间平衡 prefill 负载,避免单 replica 成 prefill 瓶颈。

#### 2.5.5 chunked prefill 关闭时的退化

若关掉 chunked prefill:

- WAITING 队列的新 prefill **不能被 budget 切断** ——需要的 token 数超过它这一轮能拿的额度时直接 `break`,整段 WAITING 调度终止(不是「跳过这个请求继续看下一个」)。
- 这会导致长 prompt 请求被持续推迟(直到某个 step 的 budget 一次性够用),TTFT 飙升;而且因为是 `break`,排在它后面的短请求同样被连带推迟。

所以 V1 **默认开启 chunked prefill** ——这是混合调度的前提。配置校验阶段会 **强制关掉** 它的是 **encoder-decoder 模型** (同时把长 prefill 阈值也清零),源码注释写得很直白:这类模型不支持 chunked prefill。

### 2.6 PD 分离调度(Disaggregated Prefill-Decode)

PD 分离(disaggregated)指 prefill 和 decode 在 **不同节点** 执行,KV cache 通过网络传输。调度器需要协调 KV transfer 的异步性。

#### 2.6.1 架构总览

```text
              ┌──────────────┐
              │ Load Balancer│  根据 prompt 长度 / 节点负载决定路由
              └──────────────┘
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
┌───────────────────┐   ┌───────────────────┐
│   P 节点集群       │   │   D 节点集群       │
│  (Prefill 专用)    │   │  (Decode 专用)     │
│                   │   │                   │
│ ┌───────────────┐ │   │ ┌───────────────┐ │
│ │ EngineCore_P  │ │   │ │ EngineCore_D  │ │
│ │ Scheduler_P   │ │   │ │ Scheduler_D   │ │
│ │               │ │   │ │               │ │
│ │ waiting:      │ │   │ │ waiting:      │ │
│ │  [新请求]      │ │   │ │  [等 KV 的请求]│ │
│ │ running:      │ │   │ │ running:      │ │
│ │  [prefill 中]  │ │   │ │  [decode 中]   │ │
│ └───────────────┘ │   │ └───────────────┘ │
│                   │   │                   │
│  只做 prefill      │   │   只做 decode      │
│  完成后发 KV ──────┼──►│  收到 KV 后        │
│                   │KV │  开始 decode       │
│                   │传输│                   │
│ GPU: 高算力配置    │   │  GPU: 高带宽       │
│ batch: 小(8~32)   │   │  batch: 大(256)   │
└───────────────────┘   └───────────────────┘
             │                     │
             ▼                     │
       ┌───────────┐               │
       │ Mooncake  │◄──────────────┘
       │  Store    │  (P 上传, D 下载)
       │  (可选)    │
       └───────────┘
```

与 PD 混合的根本区别:

- **PD 混合** :1 个 EngineCore,1 个 scheduler,prefill 和 decode 混在一个 batch
- **PD 分离** :2 组 EngineCore,各自独立 scheduler,P 只 prefill、D 只 decode,KV 跨节点传

这一节的节点配置建议(P 用高算力、小 batch;D 用高带宽、大 batch)是部署经验,不是仓库里的配置。

#### 2.6.2 P 节点调度流程

P 节点只做 prefill,调度逻辑 **与混合调度相同** ,但请求完成后不进入 decode:

```text
P 节点 Scheduler:

请求 R 到达 P 节点
  │
  ▼ 加入 waiting 队列
  │
  ▼ schedule() 选到 R
  │   chunked prefill (与混合调度相同)
  │   R.num_computed_tokens: 0 → 2045 → ... → N
  │   每轮 schedule() 都会把 connector 的 metadata 挂到
  │   SchedulerOutput.kv_connector_metadata 上
  │
  ▼ R prefill 完成 (num_computed_tokens == num_tokens)
  │
  ▼ worker 侧 connector 按 metadata 做实际的 KV send
  │   (KVConnectorModelRunnerMixin, 在 model forward 前后执行)
  │   ① 读取 R 的 KV block (所有层的 K/V)
  │   ② 通过 RDMA/NCCL 发往 D 节点, 或上传到 Mooncake Store
  │
  ▼ scheduler 侧 _free_request(R) → _connector_finished(R)
  │   返回 (delay_free_blocks, kv_xfer_params)
  │   ★ delay_free_blocks=True 时 block 不能立即回收 --
  │     KV 还在 send 中, 提前复用会让对端读到脏数据
  │
  ▼ 传输确认后, block 才真正归还 BlockPool
    _drain_deferred_frees() 负责排空延迟释放队列
    → P 节点的 KV cache 这时才能给下一个 prefill 请求用
```

这里最容易搞错的是分工: **scheduler 侧的 connector 只做「记账与决策」** (生成 metadata、回答「要不要延迟释放」), **真正搬 KV 的是 worker 侧的 connector 实例** 。同一个 connector 类会在两端各实例化一份,角色由一个二值枚举区分:一个跑在调度器进程里,一个跑在 worker 进程里。

延迟释放的实现比「等一下再放」更讲究:待释放的 block 连同一个 **step 序号栅栏** 一起入队,只有栅栏步已经处理完才真正归还,而且归还时按 **逆序** 释放,让尾部 block 先被淘汰。

**P 节点的特点** :

- scheduler 不使用等待远端 KV 的那个阻塞态——它是纯 producer
- KV cache 周转快:prefill 完 → 发走 → 确认后释放,再给下个请求
- batch 小(经验值 8 到 32,非代码默认值):prefill 是 compute-bound,小 batch 已能压满算力,并发上限需要显式调小

#### 2.6.3 D 节点调度流程

D 节点只做 decode,但需要 **等待 P 节点的 KV 传过来** 。调度器多了一个专门的阻塞态来处理这个异步等待。

**D 节点请求状态机**

```text
              请求 R 从 P 节点转来
                     │
                     ▼
              ┌─────────────┐
              │   WAITING   │  R 在 D 的 waiting 队列, 等 KV transfer
              └─────────────┘
                     │
         schedule() 每步检查:
           connector.get_num_new_matched_tokens(R)
                     │
         ┌───────────┴───────────┐
         │                       │
   KV 还没准备好             KV 已就绪
         │                       │
         ▼                       ▼
   保持 WAITING           allocate_slots()
   跳过本请求                    │
                          connector.update_state_after_alloc()
                          触发异步 KV 接收
                                 │
                                 ▼
                  ┌──────────────────────────┐
                  │ WAITING_FOR_REMOTE_KVS   │ KV 正在传输中
                  └──────────────────────────┘ (RDMA/NCCL 后台收)
                                 │
                  每 step 检查已完成传输的请求集合:
                                 │
                  ┌──────────────┴──────────────┐
                  │                             │
              还在传输                       传输完成
                  │                             │
                  ▼                             ▼
              保持等待              _update_waiting_for_remote_kv(R)
                                      │ cache_blocks(R) 注册到本地 prefix cache
                                      ▼
                             ┌──────────────────────┐
                             │ WAITING              │ (回到可调度状态)
                             │ 曾被抢占过则回 PREEMPTED│
                             └──────────────────────┘
                                      │ 下一 step schedule() 选到
                                      ▼
                                ┌───────────┐
                                │  RUNNING  │  开始 decode!
                                └───────────┘
                                      │ 每 step decode 1 token
                                      ▼
                                ┌───────────┐
                                │ FINISHED  │  EOS / max_tokens
                                └───────────┘
```

「回到哪个状态」这一步有个细节: **曾被抢占过的请求回到 `PREEMPTED`,没被抢占过的回到 `WAITING`** ——这样后续逻辑还能分清它是新客还是回锅客。

**D 节点 schedule() 的额外逻辑**

```text
schedule() 在 D 节点:

① 调度 RUNNING 队列 (与混合调度相同)
   for req in running:
     num_new_tokens = 1  (D 节点只做 decode, 没有 prefill chunk)

② 调度 WAITING 队列 (多了 connector 逻辑)
   while (waiting or skipped_waiting) and token_budget > 0:
     req = queue.peek_request()                # 只看不出队
     (a) 先尝试 promote 阻塞态请求
         _try_promote_blocked_waiting_request(req)
           if req.status == WAITING_FOR_REMOTE_KVS:
             if req_id in 已完成传输集合:
               _update_waiting_for_remote_kv(req)   # 注册 cache
               req.status = PREEMPTED if 曾被抢占 else WAITING
             else:
               pop + step_skipped_waiting.prepend + continue  # 还在传

     (b) 查本地 prefix cache
         _get_local_prefix_cache_hit(req)
           └ 挂了 connector 时走 kv_cache_manager
               .get_computed_blocks_for_connector(req)
             否则走 get_computed_blocks(req)

     (c) 查远程 KV
         partial_tail = num_new_local_computed_tokens % block_size
         block_aligned_local = num_new_local_computed_tokens - partial_tail
         ext_tokens, load_kv_async = connector.get_num_new_matched_tokens(
             req, block_aligned_local    # 只报块对齐的本地命中量
         )
         if ext_tokens is None:
           pop + step_skipped_waiting.prepend + continue  # connector 给不出结论

     (d) 分配本地 KV block
         new_blocks = kv_cache_manager.allocate_slots(req, ...)
         if new_blocks is None: break              # 不抢占, 直接停

     (e) 通知 connector 分配结果
         connector.update_state_after_alloc(
             req, kv_cache_manager.get_blocks(req_id), ext_tokens)

     (f) 关键分支
         req = queue.pop_request()                 # 到这里才真正出队
         if load_kv_async:
           req.status = WAITING_FOR_REMOTE_KVS     # 进等待状态
           step_skipped_waiting.prepend_request(req)  # 下轮再检查
           req.num_computed_tokens = num_computed_tokens
           # 先按远程量置好, 传输完成前不会被读取
           self._inflight_prefills.add(req)
           continue
         else:
           running.append(req)   # KV 已就绪, 直接 decode
```

(c) 里传给 connector 的是 **块对齐后** 的本地命中量,不是原始命中量。原因是 KV 以 block 为单位传输,半块无法作为传输边界;不足一块的尾巴留给本地重算。源码里还有一个额外分支:当这个尾巴存在、且远端能给出的量超过它时,会把这半块也纳入重新计算,避免本地半块与远端整块在边界上打架。

#### 2.6.4 KV transfer 完成的回调机制

每 step 结束后,`update_from_output()` 检查 worker 端 connector 报告的传输完成情况:

```python
def update_from_output(self, scheduler_output, model_output):
    kv_connector_output = model_runner_output.kv_connector_output
    if kv_connector_output:
        self._update_from_kv_xfer_finished(kv_connector_output)
```

它把已完成的 request_id 加入「已完成传输」集合。下一 step 的 `_try_promote_blocked_waiting_request` 检查此集合:

```python
def _try_promote_blocked_waiting_request(self, request) -> bool:
    if request.status == RequestStatus.WAITING_FOR_REMOTE_KVS:
        if request.request_id not in self.finished_recving_kv_req_ids:
            return False                      # 还没传完, 继续等
        self._update_waiting_for_remote_kv(request)   # 注册到 cache
        request.status = (RequestStatus.PREEMPTED
                          if request.num_preemptions
                          else RequestStatus.WAITING)  # 准备 decode
        return True
    ...
```

这个方法其实是 **三个阻塞态的统一出口** ,不只处理远端 KV:等结构化输出文法编译完成、等流式请求的下一段输入,也都走同一个入口各自判断能否放行;遇到未知状态直接断言失败。所以 2.2 里 WAITING 循环第一步的「先尝试 promote 阻塞态请求」,在混合调度下同样会执行,只是那时通常只有文法那一支会命中。

传输链路上还有一条错误路径:worker 报回来的除了「哪些传完了」,还有「哪些 block 失效了」;调度器据此把受影响请求的已算 token 数改回正确值,这样即便传输中途出错也不会拿脏 KV 去 decode。

#### 2.6.5 PD 分离的端到端时序

以下时间轴全部是量级示意,不是本仓库实测:

```text
时间轴 ────────────────────────────────────────────────────►

                    P 节点                    D 节点
                   (Prefill)                 (Decode)

t=0      请求 R 到达 LB
         LB: prompt 长(2000), 分给 P_0

t=10ms   P_0 收到 R
         scheduler: R → waiting → running
         schedule: R prefill chunk1 (2045 tokens, budget=2048)

t=50ms   chunk1 完成 -- 2000 < 2045, 其实一步就算完了
         (若 prompt = 5000, 则需 chunk1(2045)+chunk2(2045)+chunk3(910) 三步)

t=95ms   prefill 全部完成 (2000 token)
         worker 侧 connector 按 metadata 发 KV:
           读取所有层 K/V
           RDMA 发往 D_3              D_3 收到通知
         scheduler 侧 _connector_finished   R → waiting 队列
           → delay_free_blocks=True       检查 connector: KV 在传
         P_0 暂不释放 R 的 block         R 保持 WAITING

t=100ms                                 RDMA 传输中 (约 5ms)
                                        (KV 几百 MB, RDMA 100GB/s)

t=105ms                                 KV 传输完成!
                                        worker 报 finished_recving
         传输确认 → P_0 排空延迟释放,    _update_waiting_for_remote_kv(R):
         R 的 block 这时才归还 BlockPool    cache_blocks(R)
         (_drain_deferred_frees)           R.status = WAITING

                                          R: WAITING → RUNNING

t=120ms                                 R decode 3rd token
 ...                                     ...

t=10s                                   R 生成 EOS → FINISHED
```

关键延迟:

- P 节点 prefill:约 95ms(2000 token,chunked)
- KV transfer:约 5 到 10ms(RDMA)
- D 节点 decode 开始:t=110ms(TTFT)
- 后续每 token:约 5 到 50ms(TPOT)

**架构对比**

```text
│  └──────────────┘  │             │ 完成后     │传输│           │
│         │          │             │ 发送 KV ──┼──►│ 收到 KV   │
```

上图中的 batch 数量、GPU 型号分工,以及下面对比表里的 TTFT/TPOT/吞吐档位,都是 **部署经验值而非代码里的默认值** ——源码中没有任何地方为 P/D 角色预设不同的并发上限,这些差异全靠启动参数人为拉开。表中「1.5 到 2 倍」这类倍数取决于模型、prompt 长度分布与网络,不应当作固定结论。

**逐维度对比**

| 维度 | PD 混合(默认) | PD 分离 |

| scheduler | 1 个,统一调度 prefill 与 decode | P/D 各有独立 scheduler |

| GPU 配置 | 统一配置 | P 高算力,D 高带宽(可不同型号) |

| KV transfer 开销 | 无 | 有(约 5 到 10ms RDMA,占 TTFT 一部分) |
| CUDA Graph | 混合 step 走分段 graph,纯 decode step 走完整 graph | D 节点几乎总是纯 decode,稳定走完整 graph |
| 部署复杂度 | 低(单进程) | 高(需负载均衡、connector 与 KV transfer 配置) |
| 资源利用率 | 中(prefill 与 decode 互相挤占) | 高(P/D 各自满载) |
| 适用场景 | 通用、中低 QPS、短到中等 prompt | 高 QPS、长 prompt、SLA 严格、大规模部署 |
| 故障隔离 | 差(一崩全崩) | 好(P/D 独立,D 崩不影响 P) |

**决策框架** (部署经验,不是代码里的判据)

```text
  ✓ 不需要 SLA 分级
  ✓ 快速部署, 不想维护多组件

  ✓ prompt 长度 > 2000 token (长 prefill)
  ✓ 有 RDMA 网络 (NVLink/InfiniBand)
  ✓ SLA 严格 (TTFT < 200ms, TPOT < 30ms)
  ✓ GPU 资源充足 (> 16 卡)
  ✓ 需要 P/D 不同 GPU 配置 (P 用 H100, D 用 A100)

```

### 2.7 混合 batch 在 kernel 层如何处理

前面 2.5 讲的是 **调度层** 如何产生混合 batch(prefill 加 decode token 共享 token budget)。本节讲 **执行层与 kernel 层** 如何把混合 batch 一次算完——这是 V1 能做 chunked prefill 的物理基础。

#### 2.7.1 混合场景确实存在,而且是常态

在线服务场景下,几乎 **每个 step** 的 batch 都同时包含 prefill 和 decode token。原因:

- 总有「已在 decode 的请求」(用户在等 token 流式输出)。
- 同时又有「新请求到达」(需要 prefill)。
- 如果两者不能同 batch,要么 decode 等(TPOT 飙升),要么新请求等(TTFT 飙升)。

具体例子(`max_num_batched_tokens=2048`,即默认值):

```text
当前 step 的 batch 内有 4 个请求:
  请求 A: 已生成 100 token, 本 step 继续 decode → query_len=1
  请求 B: 已生成 50 token,  本 step 继续 decode → query_len=1
  请求 C: 新请求, prompt=500 token, 第一次 prefill → query_len=500
  请求 D: 新请求, prompt=2000 token, 第一次 prefill → query_len=1024 (被 budget 切开)

batch 总 token 数: 1 + 1 + 500 + 1024 = 1526 ≤ 2048 ✓
→ 这一个 forward pass 同时算 2 个 decode 加 2 个 prefill chunk

执行层会把请求重排成 "decode 类在前、prefill 按 token 数升序在后"
(见 2.7.4), 本例排序后正好是 A, B, C, D。
```

#### 2.7.2 算子级全景:哪些算子需要区分 P/D,哪些不需要

这是理解混合 batch 的关键: **一个 Transformer 层里有十几个算子,其中绝大多数根本不关心 token 是 prefill 还是 decode** ——它们只看到一个扁平的 `[总 token 数, ...]` 张量,按 batch 维统一算。 **只有 attention 算子需要区分。**

以一个 Transformer 层为例,batch 有 4 个请求(A/B decode 各 1 token,C prefill 500 token,D prefill 1024 token,总计 1526 token),每个算子的输入输出形状和是否区分 P/D:

```text
        ┌──────────────────────────────────┐
        │ input_ids: [1526]                │  1526 个 token id 拼成一条
        │ (A的1个 + B的1个 + C的500个 + D的1024个)│
        └──────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│ 算子 1: Token Embedding                                         │
│   输入: input_ids [1526]                                        │
│   输出: hidden_states [1526, hidden_dim=8192]                   │
│   区分 P/D? ✗ 不区分。每个 token id 查表得到 embedding           │
└────────────────────────────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│ 算子 2: RMSNorm (or LayerNorm)                                  │
│   输入: hidden_states [1526, 8192] → 输出: normed [1526, 8192]  │
│   区分 P/D? ✗ 不区分。逐 token 做 (x / rms(x)) * weight          │
└────────────────────────────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│ 算子 3: QKV Projection (ColumnParallelLinear)                   │
│   输入: normed [1526, 8192]                                     │
│   输出: q,k,v 各 [1526, num_heads=64, head_dim=128]             │
│   区分 P/D? ✗ 不区分。就是矩阵乘 X @ W^T, 1526 个 token 一起算    │
│   (TP 下 W 按列切, 各卡算 [1526, 64/TP, 128], 然后 all-reduce)  │
└────────────────────────────────────────────────────────────────┘
                        │
         ┌──────────────┴──────────────┐
         ▼                             ▼
┌─────────────────────┐   ┌────────────────────────────────────┐
│ 算子 4a: 写 KV cache │   │ 算子 4b: Attention (★唯一区分 P/D)  │
│  把本 step 新算的     │   │  输入: q [1526, 64, 128]           │
│  K,V 写入 block      │   │        k,v_cache [num_blocks, ...] │
│  slot_mapping 告诉   │   │        cu_seqlens_q [5]            │
│  每个 token 写到     │   │        block_table [4, max_blocks] │
│  哪个 block 的哪个位置│   │  输出: attn_out [1526, 64, 128]    │
│ 区分 P/D? ✗ 不区分   │   │ 区分 P/D? ✓✓✓ 区分!                │
│  每个 token 各写各的 │   │  kernel 用 cu_seqlens_q 分段:      │
│  slot               │   │   A[0:1]:      query_len=1 → decode │
└─────────────────────┘   │   B[1:2]:      query_len=1 → decode │
                          │   C[2:502]:    query_len=500 → prefill│

                          │  一次 kernel 调用, 内部按段走不同路径 │

                                        │

┌────────────────────────────────────────────────────────────────┐
│ 算子 5: Output Projection (RowParallelLinear)                   │
│   输入: attn_out [1526, 64, 128] → reshape [1526, 8192]         │
│   区分 P/D? ✗ 不区分。矩阵乘加 all-reduce                        │
└────────────────────────────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│ 算子 6: Residual Add                                            │
│   [1526, 8192] + [1526, 8192] → [1526, 8192]                    │
│   区分 P/D? ✗ 不区分。逐元素加                                   │
└────────────────────────────────────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────────────┐
│ 算子 7~10: FFN (RMSNorm → Up_proj → Activation → Down_proj →    │
│             Residual)                                           │
│   每个算子的输入输出形状都是 [1526, ...]                          │
│   区分 P/D? ✗ 全不区分。都是逐 token 或矩阵乘操作                 │
│   (Up_proj: [1526, 8192] → [1526, 28672])                       │
│   (Down_proj: [1526, 28672] → [1526, 8192])                     │

│   但采样时只需每请求最后 1 个 token 的 logits:                    │
│     A: logits[0], B: logits[1], C: logits[501], D: logits[1525] │
│   (prefill 请求只采样最后一个 token, 前面的 token 不需要 logits)  │
└────────────────────────────────────────────────────────────────┘
```

**结论** :一层 Transformer 有约 10 个算子,只有 attention(算子 4b)需要区分 prefill/decode,其余全部统一处理 `[1526, ...]`。

这就是为什么混合 batch 几乎没有额外开销——绝大多数算子根本不知道 batch 里有 P 和 D 的混合,它们只看到一个扁平的 token 维度。唯一的「特殊处理」是 attention kernel 内部根据累计 query 长度数组分段走不同路径,而这个分段是 kernel 自己做的,对 Python 层透明。

#### 2.7.3 核心机制:FlashAttention 变长接口

FlashAttention 提供的变长版本天然支持 batch 内不同请求的 query 长度不同—— **一次 kernel 调用处理整个混合 batch** 。attention backend 里的调用大致是这样:

```python
flash_attn_varlen_func(
    q=query[:num_actual_tokens],   # [总 token 数, num_heads, head_size]
    k=key_cache,                   # [num_blocks, num_kv_heads, block_size, head_size]
    v=value_cache,
    out=output[:num_actual_tokens],
    cu_seqlens_q=cu_seqlens_q,     # ★ 累积 query 长度: 区分每个请求的 query 段
    max_seqlen_q=max_seqlen_q,
    seqused_k=seqused_k,           # 每个请求的 KV 长度
    max_seqlen_k=max_seqlen_k,
    softmax_scale=self.scale,
    causal=causal,
    block_table=block_table,       # PagedAttention 的 block table
    # 省略: alibi_slopes / window_size / softcap / scheduler_metadata /
    #       fa_version / q_descale / k_descale / v_descale / num_splits ...
)
```

被省略的参数都与「混合 batch 怎么分段」无关:它们分别控制位置偏置、滑动窗口、logits 截断、kernel 调度元数据、FA 版本选择,以及 FP8 KV cache 的反量化缩放因子。 **分段信息只来自累计 query 长度数组与每请求的 KV 长度这两个参数。**

#### 2.7.4 累计 query 长度:混合 batch 的「分段索引」

`cu_seqlens_q`(cumulative query sequence lengths,累积查询序列长度)是一个 `[请求数 + 1]` 的数组,告诉 kernel 每个请求的 query 在大张量里的起止位置。

以上面的 4 个请求为例:

```text
请求 A (decode):        query_len = 1    → 1 个 token 的 query
请求 B (decode):        query_len = 1    → 1 个 token 的 query
请求 C (prefill chunk): query_len = 500  → 500 个 token 的 query
请求 D (prefill chunk): query_len = 1024 → 1024 个 token 的 query

总 token 数: 1 + 1 + 500 + 1024 = 1526
query tensor shape: [1526, num_heads, head_size]

cu_seqlens_q = [0, 1, 2, 502, 1526]
                ↑  ↑  ↑   ↑     ↑
               起点 A终 B终 C终   D终
```

一次调用处理全部 4 段:

| 段 | query 范围 | query_len | kernel 内部路径 |
|---|---|---|---|
| A | `[0, 1)` | 1 | **decode 路径** (split-KV:单 query 扫所有 KV block,分块累加) |
| B | `[1, 2)` | 1 | decode 路径 |
| C | `[2, 502)` | 500 | **prefill 路径** (标准 FlashAttention:多 query token 的 causal attention) |
| D | `[502, 1526)` | 1024 | prefill 路径 |

**token 在扁平张量里的排列顺序**

上面的例子中 A/B(decode)在前、C/D(prefill)在后—— **这不是巧合** :执行层会在建 batch 之前把请求按「decode 类在前、prefill 在后」重排一遍:

```python
def sort_batch_req_ids(num_tokens_per_req, draft_tokens, decode_query_len):
    # Order verification/decode -> short_extend -> prefill;
    # split_decodes_and_prefills relies on decode-like requests leading.
    key = lambda r: (
        not draft_tokens.get(r),                          # 有 draft token 的最前
        (num := num_tokens_per_req[r]) != decode_query_len,  # 再是纯 decode
        num,                                               # 剩下按 token 数升序
    )
    return sorted(num_tokens_per_req, key=key)
```

排序键的三层含义:

1. **spec decode 的 verification 请求排最前** (它们有 draft token)。
2. 然后是 query_len 恰好等于 `decode_query_len` 的 **纯 decode** 请求。
3. 其余(prefill chunk、短 extend)按 token 数 **升序** 排在后面。

累计 query 长度数组是在这个排好序的数组上做前缀和的:

```python
query_start_loc_np[0] = 0
np.cumsum(num_scheduled_tokens_np, out=query_start_loc_np[1 : num_reqs + 1])
```

沿用上面 4 个请求的例子:

```text
调度器给出的 num_scheduled_tokens (顺序 = schedule() 的遍历顺序):
  running 顺序可能是 [A(1), D(1024), B(1)], waiting 拉了 C(500)
  → {A:1, D:1024, B:1, C:500}

sort_batch_req_ids 重排后:
  [A(1), B(1), C(500), D(1024)]
   └ decode 类在前 ┘ └ prefill 按 token 数升序 ┘

flat tensor 排列:
  [A的1个 | B的1个 | C的500个 | D的1024个]
   位置 0   位置 1   位置 2-501  位置 502-1525

cu_seqlens_q = [0, 1, 2, 502, 1526]

kernel 分段:
  [0,1):      A → query_len=1    → decode 路径
  [1,2):      B → query_len=1    → decode 路径
  [2,502):    C → query_len=500  → prefill 路径
  [502,1526): D → query_len=1024 → prefill 路径
```

**为什么要排序** :注释里写明了—— `split_decodes_and_prefills` 依赖「decode 类请求排在前面」。有了这个不变量,attention backend 只需要 **一个分界下标** 就能把 batch 切成「decode 段加 prefill 段」两半,从而对两半分别选择最优 kernel(有些 backend 对纯 decode 段有专门的实现),而不必逐请求判断;完整 CUDA Graph 也靠它判断「这一批是不是 uniform decode」(见 2.7.7)。

旧版的 model runner 也有等价机制,只是 **按需触发** :只有 attention backend 设了重排阈值时才调用那个重排函数。

**kernel 本身在意顺序吗** :不在意。变长 kernel 用累计长度数组就能知道每段的起止位置,对每段独立判断 query_len——等于 1 走 decode 路径,大于 1 走 prefill 路径;每段各有各的 KV cache block table,怎么交错都能算对。 **排序是为了上层的便利,不是为了 kernel 的正确性。**

#### 2.7.5 kernel 内部:一次调用跑两种优化路径

变长 kernel 是 CUDA C++ 实现(FlashAttention 库的一部分),根据累计 query 长度自动对每段做不同处理:

| 段类型 | query_len | 计算特征 | 内部优化 |
|---|---|---|---|
| **decode 段** | 等于 1 | memory-bound(访存瓶颈) | split-KV 路径:单 query token 扫所有 KV block,分块并行累加 |
| **prefill 段** | 大于 1 | compute-bound(算力瓶颈) | 标准 FA 路径:多 query tile,分块 matmul 加 online softmax |

#### 2.7.6 scheduler 与 kernel 的解耦

回顾 2.5 的调度算法,scheduler **完全不感知** 「这是 prefill 还是 decode」:

```text
scheduler 视角:
  for req in batch:
    num_new_tokens = req.num_tokens_with_spec - req.num_computed_tokens
    # num_new_tokens = 1 → 实际是 decode
    # num_new_tokens > 1 → 实际是 prefill chunk
    # scheduler 只看 token 数, 不区分类型
```

区分 prefill/decode 的责任在 **执行层** :

- model runner 的输入准备阶段收集所有 token,构造累计 query 长度数组。
- attention metadata 的构建把 prefill/decode 的边界编码到 metadata 里。
- FlashAttention kernel 根据 metadata 自动分段处理。

这种解耦让 scheduler 逻辑极简(统一 token 追踪),同时让 kernel 能做针对性优化。

#### 2.7.7 混合 batch 与 CUDA Graph:完整图还是分段图

混合 batch 并不会让 CUDA Graph 失效,它只是 **换一种 graph** 。V1 的默认 graph 模式是「完整图与分段图并存」,语义是:

- **完整图(FULL)** :整个 forward(含 attention)捕成一张图。只对 **uniform decode** 批次可用——batch 里每个请求的 query_len 都等于 `decode_query_len`(无 spec 时是 1,有 spec 时是 `1 + 推测 token 数`)。
- **分段图(PIECEWISE)** :把 forward 按 attention 算子切成若干段, **每段单独捕图** ,attention 本身留在图外 eager 执行。对任意 batch 组成都适用,包括含 prefill 的混合 batch。

派发逻辑是一个三级降级:

```python
if CUDAGraphMode.FULL in allowed_modes:
    batch_desc_to_check = batch_desc
    if batch_desc_to_check in self.cudagraph_keys[CUDAGraphMode.FULL]:
        return CUDAGraphMode.FULL, batch_desc_to_check        # 命中整图

if CUDAGraphMode.PIECEWISE in allowed_modes:
    # 放宽的 key: 不看请求数, 也不要求 uniform
    batch_desc_to_check = replace(batch_desc, num_reqs=None, uniform=False)
    if batch_desc_to_check in self.cudagraph_keys[CUDAGraphMode.PIECEWISE]:
        return CUDAGraphMode.PIECEWISE, batch_desc_to_check   # 退到分段图

return CUDAGraphMode.NONE, BatchDescriptor(num_tokens)        # 最后才是 eager
```

注意分段图这一档用的是 **放宽后的 key** :把请求数置空、uniform 置假,所以同一个 token 总数下不管 batch 怎么组成都能命中同一张图。这正是分段图「对任意 batch 组成都适用」的实现方式。

「是不是 uniform decode」这个判断来自执行层的 `has_prefill` 标志,由「是否还有请求处于 prefill 中」这个布尔数组取或算出:

```python
is_prefilling_np = num_computed_prefill_tokens_np < prefill_len_np
batch_state = BatchReqState(..., has_prefill=bool(is_prefilling_np.any()))
```

注意它是执行层 `BatchReqState` 的字段, **不在 `SchedulerOutput` 上** ——又一处调度层与执行层的分工。

所以三档路径是:

| batch 组成 | 走哪条路 | 说明 |
|---|---|---|
| 纯 decode(uniform) | 完整图 | 整图 replay,launch 开销最低 |
| 含 prefill 的混合 batch | 分段图 | 非 attention 部分仍是图,attention eager |
| 形状没有对应 bucket | eager | 兜底路径 |

**为什么 attention 不能进整图** :CUDA Graph 要求捕获时的形状与 replay 时完全一致。prefill 的 query_len 每步都在变(2045、955、6……),attention 的累计长度数组与每请求 KV 长度的长度和内容都随之变,无法固定。非 attention 的算子只依赖「总 token 数」这一个维度,把总数 pad 到 bucket 就能固定形状,所以能进分段图。

因此关于 chunked prefill 与 TPOT 的正确说法是: **含 prefill 的 step 相比纯 decode step 慢,主要是因为多算了 chunk 的那几千个 token(计算量),以及退到分段图后 attention 段的 launch 开销——不是「完全退回 eager」。**
