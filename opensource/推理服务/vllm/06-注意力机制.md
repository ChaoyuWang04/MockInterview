# vLLM 06|注意力机制:各家都在改什么

05 章讲的是「kernel 怎么被挑中、怎么被调用」。这一章回答另一个问题:这些 kernel 背后的注意力机制本身,到底差在哪 —— 以及 2026 年各家基模为什么纷纷不用标准注意力了。

机制部分在源码上逐条核对过;各家模型的架构判断来自本仓库模型实现目录下它们自己提交的代码,外部资料只用来补背景并已注明。正文不写路径与行号,见代码索引页。

## Part 1|原理

### 1.1 一张图看完所有机制

![七种注意力机制的对比:每种压的是什么、每层每 token 的 KV cache 有多大](/opensource/vllm/06a-attention-family.svg)

图里用的是一组便于心算的小数字:**8 个 Q 头、每头 128 维、FP16**。真实模型的头数大得多,但比例关系不变。

**读图的关键是分清「省的是哪一维」。** 一个 token 的 KV cache 大小,是三个因子的乘积:

$$
\text{KV bytes} = \underbrace{2}_{K \text{ 和 } V} \times \underbrace{N_{kv}}_{\text{KV 头数}} \times \underbrace{D}_{\text{每头维度}} \times \underbrace{b}_{\text{每元素字节}}
$$

再乘以层数,就是这个模型每个 token 的总开销。七种机制分别在动不同的因子:

| 动哪一维 | 机制 | 做法 |
|---|---|---|
| KV 头数 $N_{kv}$ | MQA / GQA | 让多个 Q 头共用一组 K/V |
| 每头维度 $D$ | MLA | 不存 K/V,存一个低秩隐向量,用时再解压 |
| 参与计算的 token 数 | DSA / MSA | 存的一个不少,但每个 query 只对挑中的一部分算 |
| **整个公式不成立** | 线性注意力 | 根本不按 token 存,维护一个固定大小的状态 |
| 有效序列长度 | 滑动窗口 | 只保留最近一段窗口 |

最后两行要特别注意:**它们不是在这个公式里省,而是让这个公式失效**。线性注意力的状态大小与序列长度无关,所以「每 token 多少字节」这个问法本身就不适用 —— 这正是它最大的卖点,也是它最难评估的地方。

### 1.2 痛点:decode 被 KV 读带宽卡死

所有这些机制都在解同一个问题,值得先把这个问题算清楚。

decode 每步只有 1 个 query token,但要把该请求**全部历史 KV 读一遍**。设历史长度 $L$、头数 $N$、每头维度 $D$、每元素 $b$ 字节:

- **计算量**:$QK^\top$ 是 $N \cdot L \cdot D$ 次乘加,约 $2NLD$ 次浮点运算;乘 $V$ 同样 $2NLD$。合计 $4NLD$。
- **访存量**:K 和 V 各 $N \cdot L \cdot D$ 个元素,合计 $2NLDb$ 字节。

两者相除得到**算术强度**:

$$
\frac{4NLD}{2NLDb} = \frac{2}{b}
$$

BF16 下就是 **1 次浮点运算 / 字节**。而一张 H800 的拐点(算力除以带宽)约为 $989\ \text{TFLOPS} / 3.35\ \text{TB/s} \approx 295$(标称参数,量级参考)。

**也就是说 MHA 的 decode 注意力,算力利用率天然只有 $1/295 \approx 0.34\%$。** 这个比值和 $N$、$L$、$D$ **全部无关** —— 换更小的模型、更短的上下文都救不了它,它只由数据类型决定。

结论因此非常窄:**想让 decode 变快,只有两条路** —— 减少要读的 KV 字节数,或者提高每次 KV 读取被复用的次数。1.1 那张表里的所有机制,都是这两条路的不同走法。

### 1.3 MQA 与 GQA:压 KV 头数

**MQA** 把 KV 头数压到 1:所有 Q 头共用同一组 K/V。计算流程只有两处变化 —— K/V 的投影矩阵输出维度从 $N \cdot D$ 变成 $1 \cdot D$,打分时所有头用同一个 $k$。位置编码、mask、softmax、加权、输出投影**完全不变**。

以 LLaMA-2 7B 的形状(32 头、128 维、32 层、BF16)算:

| 方案 | 每 token 每层 | 32 层合计 | 相对 MHA |
|---|---|---|---|
| MHA | 16 KB | 512 KB | 1 倍 |
| MQA | 512 B | 16 KB | 1/32 |

32 倍压缩。代价是所有 Q 头被迫共享同一组 K/V,表达能力下降明显 —— MQA 在实践中通常要重新训练或蒸馏,质量损失可观察。这就是它被 GQA 取代的原因。

**GQA** 是折中:Q 头分成 $G$ 组,每组 $N/G$ 个 Q 头共享一组 K/V。$G = N$ 时退化为 MHA,$G = 1$ 时退化为 MQA。

**GQA 是 MHA 和 MQA 的超集,这也是为什么 vLLM 里没有独立的「MQA 后端」** —— 所有标准 attention kernel 都按 GQA 写,MHA 和 MQA 只是「每 KV 头服务几个 Q 头」等于 1 和等于 N 的两个特例。

以 LLaMA-3-70B 的形状(64 头、8 组、128 维、80 层、BF16):

| 方案 | 每 token 每层 | 80 层合计 | 相对 MHA |
|---|---|---|---|
| 若用 MHA | 32 KB | 2.5 MB | 1 倍 |
| **实际 GQA** | **4 KB** | **320 KB** | **1/8** |
| 若用 MQA | 512 B | 40 KB | 1/64 |

用 1/8 的缓存换来接近 MHA 的质量,这是过去两年主流模型的默认选择。

### 1.4 分组不只省显存,还提高了算术强度

GQA 在 kernel 里的实现方式,直接兑现了 1.2 说的第二条路。

decode 时每个请求只有 1 个 query token。如果一个 CUDA block 只处理一个「token 加一个头」的组合,那么矩阵乘的那一维长度只有 1,Tensor Core 完全浪费。vLLM 的统一 Triton kernel 的做法是**把同一 KV 组的多个 Q 头打包进那一维**:grid 的第二维直接取 KV 头数而不是 Q 头数,kernel 内部再把行号拆回「第几个 token」加「组内第几个 Q 头」。

好处是**一次 K/V 分块加载被组内所有 Q 头复用**,算术强度从 1.2 算出的 $2/b$ 提升到:

$$
\frac{2 \cdot n_{q/kv}}{b}
$$

其中 $n_{q/kv}$ 是每个 KV 头服务的 Q 头数。LLaMA-3-70B 那组形状($n_{q/kv} = 8$)就是 8 倍提升,BF16 下从 1 涨到 8 次浮点运算每字节。

**离拐点 295 还很远,所以 decode 依然是访存瓶颈** —— 但每读一个字节干的活多了 8 倍。这是 GQA 常被忽略的第二重收益:它不只让缓存变小,还让读缓存这件事更划算。

### 1.5 KV cache 的形状由谁决定

这里要澄清一个容易搞反的归属。

**KV cache 的形状不由后端的某个函数给出,而由层自己发布的缓存规格决定。** 标准 attention 层发布的规格里,KV 头数是显式的一维 —— MHA、MQA、GQA 的差异就落在这一维上。

规格里每单元的字节数是 `K 的每头维度 + V 的每头维度` 再乘以每元素字节。两者默认相等,所以看起来像乘以 2 —— 但**它不是某个后端写死的「乘 2」,而是两个字段相加的结果**。05 章 1.6 讲的 DiffKV 变体,正是这两个字段不相等的场景。对比 MLA 的规格,V 的那一维被置零,这一维直接退化。

后端在这里的角色**只有一个**:声明它能接受哪些块大小(FlashAttention 声明「16 的倍数」),建缓存前由一个统一的协商步骤定夺。所以「块大小必须是 16 的倍数」不是某个形状函数里的报错,是后端发布的约束 —— 这也是 05 章 4.5 那条「默认自动协商」的由来。逻辑形状到实际张量步长的映射由布局枚举决定,后端另有一个方法声明自己能吃哪几种布局;这套 03 章 1.11 已经讲过。

### 1.6 MLA 与稀疏:另外两条省法

**MLA** 动的是表示维度:缓存里存的不是 K/V,而是一个低秩隐向量,K/V 在算之前解压出来 —— 或者干脆把解压矩阵吸收进 Q 和输出投影,根本不解压(decode 走这条)。关键性质是**它的缓存大小与头数无关**:DeepSeek 那类 128 头的模型,若用 MHA 每 token 每层要 64 KB,MLA 只要约 1.1 KB。

**DeepSeek 稀疏注意力(DSA)** 动的是参与计算的 token 数:它仍然是 MLA,存的一个不少,只是每个 query 只对一个轻量索引器选出的 top-k 个 token 做注意力,其余位置直接不算。选中的 token 可以远在固定窗口之外 —— 这是它和滑动窗口的根本区别:**窗口是位置决定的,top-k 是内容决定的。**

**MiniMax 稀疏注意力(MSA)** 是同一思路的另一种走法:它建在标准 GQA 之上而不是 MLA 之上,索引分支按**块**打分并独立选出 top-k 块,主分支只在选中的块上算 softmax。代价是保留未压缩的真实 K/V、显存更高,换来的是长上下文检索精度。

两者的共同点是:**存储侧不省,计算侧省。** 所以它们缓解的是 1.2 里的「读带宽」,但不缓解显存容量 —— 这一点在容量吃紧的部署里要分清。

### 1.7 线性注意力:让那个公式失效

前面几种都还在「每个 token 存一份东西」的框架里。线性注意力跳出了这个框架。

它不做 Q/K/V 打分,而是维护一个**固定大小的状态矩阵**,每来一个 token 就按某种规则更新它。状态大小与序列长度无关,所以:

| 维度 | 标准注意力 | 线性注意力 |
|---|---|---|
| 缓存什么 | 历史 K/V 张量,随序列增长 | 固定大小的状态,不增长 |
| 预填充复杂度 | 序列长度的平方 | 线性 |
| 每 token 解码开销 | 随已生成长度增长 | 常数 |
| 能不能精确回看某个 token | 能 | 不能,只有状态里的摘要 |

最后一行是它的全部代价。状态是有损压缩,**精确检索能力会掉** —— 这正是各家没有全盘换掉标准注意力的原因。

vLLM 把这一类也登记成「注意力后端」,但它们的缓存规格是并列的另一种,也不参与后端优先级竞争(05 章 1.12)。目前基准上能看到的这一类包括 Mamba 两代、**门控 DeltaNet(GDN)**、线性注意力、短因果卷积,以及各家自带的变体。

**门控 DeltaNet** 是当前最主流的那个:它在线性注意力上加了两件东西 —— 一个纠错式的「增量规则」更新,和一个控制记忆衰减的门。**Kimi 的 KDA** 是它的细化版,把逐头一个衰减标量改成**逐通道**一个,以更细的粒度控制这块有限的状态。

### 1.8 各家现在怎么选

判断依据不是新闻稿,是**这几家自己提交进 vLLM 的实现** —— 基准的模型实现目录下有七个相关的模型族,按其中的符号分布可以直接读出各自的主力机制(具体目录见代码索引页):

| 模型族(基准目录) | 线性 / 稀疏那一侧 | 全注意力那一侧 | 形态 |
|---|---|---|---|
| Qwen 第四代实验版 | 门控 DeltaNet | MLA | 混合 |
| GLM-5 next | KDA | MLA | 混合 |
| Kimi K3 | KDA(全目录出现近两百次) | MLA | 混合 |
| MiniMax M3 | 块稀疏(MSA) | MLA 与标准 attention | 稀疏 |
| DeepSeek V3.2 | DSA | MLA | 稀疏 |
| DeepSeek V4 / V4.1 | 压缩稀疏与重压缩两路 | —— | 混合压缩 |

**一个很清楚的结论:「线性层配全注意力层、按比例交错」已经是三家的共同选择。** Qwen 实验版、GLM-5-next、Kimi K3 都是线性模块配 MLA;MiniMax 是唯一一家把宝压在块稀疏上的;DeepSeek 则在自己那条线上又往前走了一步。

外部资料(2026-09-14 检索)可以补上比例和动机,与上面的源码观察互相印证:

- **Qwen3-Next / Qwen3.5**:门控 DeltaNet 配门控注意力,**3:1 交错** —— 每四层里一层全注意力。Qwen3.5 把这套架构推到了 397B,回答了「线性能不能 scale」这个问题。
- **Kimi Linear**(arXiv:2510.26692):KDA 配 MLA,同样 **3:1**,而且 **MLA 层不加位置编码**,位置信息全交给 KDA 那一侧。这正好解释了 05 章 3.9 提到的那个「纯 latent 维度」的 head size 档位。
- **MiniMax**:M2 一代公开说明过为什么**放弃**混合与滑窗 —— 大量消融后发现长上下文的检索与多跳推理都有损失,而且低精度状态存储、前缀缓存、投机解码三件基建当时还不成熟。到 M3 才以块稀疏的形式回到高效注意力这条路。
- **DeepSeek V4**(arXiv:2606.19348):**不再用 MLA**,改成压缩稀疏与重压缩两种注意力交错。
- **GLM-5**:MLA 配 DSA,和 DeepSeek V3.2 同一套。

把这些放在一起看,2026 年的图景是:**没有一家还在用纯标准注意力,但也没有两家选了完全一样的路。** 分歧点在于「用有损的固定状态换成本」还是「保住精确 K/V 只在计算上省」—— 前者是 Qwen、Kimi、GLM 的混合路线,后者是 MiniMax 与 DeepSeek 的稀疏路线。

这对读 vLLM 源码的人意味着一件很实际的事:**05 章那套后端抽象之所以要容得下「不是 attention 的 attention 后端」和「模型钦定的后端」两类例外,正是因为上面这张表。** 抽象层的复杂度不是设计过度,是被这几年的架构分化逼出来的。
