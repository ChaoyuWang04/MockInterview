# vLLM 08|推测解码

decode 一步只能吐出一个 token,而这一步里 GPU 大半时间在等内存。推测解码拿这段闲置的算力换延迟:让一个小模型先猜 k 个 token,大模型一次前向把这 k 个位置一起验。这一章讲它凭什么快、什么时候反而更慢,以及代码里那两套同时存在的实现该怎么分辨。

拒绝采样的判定规则与分布等价性在 07 章 6.1 起已经讲过,本章不重复,只在用到时回指。

后六分之一换一个提法:推测解码在省下 GPU 时间的同时,**把 CPU 那一侧的开销加重了**,7.1 起讲这条自己带出来的痛点怎么被摘掉。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与方法,见代码索引页;正文不写路径与行号。

## Part 1|原理:GPU 在等内存,于是先猜再验

### 1.1 一次前向只出一个 token,而 GPU 在等内存

自回归生成是**严格串行**的:生成一个 token,把它接到序列末尾,再做一次完整的前向,才能产出下一个。要 N 个 token 就要 N 次前向,没有捷径。

真正刺眼的不是串行本身,而是**每一次前向都在浪费**。06 章算过这笔账:decode 阶段是访存瓶颈,一步里 GPU 绝大部分时间在等 HBM 把权重搬过来,算力利用率常常连 1% 都不到。**读了一整遍模型权重,只为了算一个 token。**

推测解码问的就是:同样读这一遍,能不能多算几个?

| 痛点 | 推测解码的应对 | 本章位置 |
|---|---|---|
| 每出一个 token 都要完整读一遍权重,算力几乎闲置 | 一次前向多验几个位置,把这遍读取摊给 k+1 个 token | 1.5 |
| 草稿猜得不准,验证时大批作废,前面白跑 | 把「猜得准不准」收敛成一个可算的量:接受率 | 2.2 |
| 草稿本身也要花时间,可能比省下的还多 | 一条精确判据算清楚什么时候该开 | 2.5 |
| 验证方式稍有不慎,输出分布就不再是目标模型的 | 拒绝采样,等价性 07 章已经证过 | 2.1 |
| **推测解码自己带来的:每步的 CPU 工作变重,反过来成了新瓶颈** | 让草稿 token 全程不落 CPU,调度靠占位符乐观推进 | 7.1 起 |

前四条是「**这笔生意划不划算**」这件事内部的张力,占本章前三分之二。**最后一条是推测解码自己制造出来的** ——它把每一步的 CPU 工作从「一次数据搬回加簿记」变成了「两次搬回,外加一条绕整个引擎一圈的草稿回路」。**GPU 那边省下的时间,有一部分被 CPU 这边吃了回去** ——这就是 7.1 起要解决的事,另起一条线。

下一节不在这两条痛点线上,它是**读码前提**:同一套能力在代码里有两份实现,不先分清楚,后面每一句「代码里是这样」都会找错地方。

### 1.2 读这一章之前:推测解码在代码里有两套

06 章 1.4 讲过模型运行器有两套独立实现。**推测解码是这条分叉影响最深的地方** ——不只是运行器,连草稿组件的称呼、目录、基类、每个具体 proposer 的类名,乃至拒绝采样器本身,都各有一份。两个同名的 `RejectionSampler` 类同时存在于代码库里,一个是 `nn.Module`,一个不是。

| | 第一代 | 第二代 |
|---|---|---|
| 草稿组件叫什么 | **Proposer**(提议者) | **Speculator**(推测者) |
| 基类 | `SpecDecodeBaseProposer` | `BaseSpeculator` → `DraftModelSpeculator` → `AutoRegressiveSpeculator` ,三级 |
| EAGLE 与 MTP | 同一个 `EagleProposer` 类兼管 | 拆成 `EagleSpeculator` 与 `MTPSpeculator` 两个类 |
| 拒绝采样器 | `RejectionSampler` ,是 `nn.Module` | `RejectionSampler` ,普通类 |

**认类名不要认目录**:两套各自住在一个叫 `spec_decode` 的目录里,光看目录名分不出来,类名才是可靠的路标(两个目录的完整位置见代码索引页)。唯一一对连类名都撞车的是拒绝采样器,只能靠「是不是 `nn.Module` 」区分。

第一代那个「一个类兼管 EAGLE 与 MTP」的分派走的是一个叫 `use_eagle` 的方法,而它实际返回的是五种方法名的集合。**源码自己也觉得这个名字不对** ——注释写着这个方法「通常是『用目标模型 hidden states 做推测解码』的代称」,底下还挂着一条 TODO 说要把命名理清楚。读到这里不要费劲去想 MTP 为什么算 EAGLE,它就是个历史包袱。

**默认走哪一套,是这一节最容易记反的地方。**

判定逻辑是**一条否决链,不是一份准入名单**:先看有没有开水印(开了就强制第二代,而且日志明说它覆盖了用户设的关闭开关),再看环境变量有没有显式指定,然后依次检查 ROCm 架构黑名单、有没有 Triton、本次配置是否命中第二代尚不支持的特性——**统统没命中,就用第二代**。也就是说,**什么都不设时默认是第二代**,不是「满足某些条件才切过去」。

与之对称还有另一份清单:**第一代做不到、因而不允许退回去的特性** ——预填充上下文并行、`dspark` 推测采样、自适应草稿验证、混合滑窗与全注意力的 DFlash 草稿、DFlash2 草稿、扩散模型、batch 分片采样,共七项。这份清单的用途是:**用户点名要第一代、却又用了这里面的特性时,配置校验阶段直接抛错**。它是一道拦截,不是一个自动切换的开关——两者方向正好相反,读反了会以为「不碰这些特性就是在跑第一代」,于是整章的代码定位全盘找错地方。

### 1.3 核心思路:先猜 k 个,再一次验完

推测解码由两篇 2023 年的论文各自独立提出(Leviathan 等,arXiv:2211.17192;Chen 等,arXiv:2302.01318)。做法拆成三段。

以 k=3 为例,序列已经生成到「我家有只」:

```text
阶段 1 | 草稿模型串行猜 3 个,花 3 次 draft forward
    draft("我家有只") -> 猫
    draft("我家有只猫") -> 在
    draft("我家有只猫在") -> 沙

阶段 2 | 目标模型一次 forward 验完
    把 3 个草稿直接拼到序列末尾:"我家有只[猫,在,沙]"
    一次前向同时算出 4 个位置的 logits

阶段 3 | 逐位置判定
    logits[0] 验「猫」 -> 接受
    logits[1] 验「在」 -> 接受
    logits[2] 验「沙」 -> 拒绝,改从修正分布采一个替补;位置 3 随之作废
    logits[3] 是 bonus,只有前三个全接受才用得上

本步产出 [猫, 在, 替补]:3 个 token,只花了 1 次目标模型前向
```

三段里,阶段 1 仍然是串行的——草稿模型自己也得一个一个猜。**真正并行的是阶段 2**:k 个草稿 token 一次性拼进序列,目标模型一次前向就把 k+1 个位置的判断全部算出来。每个位置的 logits 就是目标模型对「这个位置该是什么」的意见,拿它去对草稿的提议。

第 k+1 个位置的 logits 是顺带算出来的:它对应「三个草稿全对之后,下一个该是什么」。**全接受时它白送一个 token,这就是加速比上限为 k+1 的来源**(07 章 6.7 讲过它的三种产出叫法)。

### 1.4 并行验证到底并行了什么

「一次前向算 k+1 个位置」听起来像是模型要改结构,其实什么都不用改。把一层里各个算子的形状列出来就清楚了——设 batch 有 B 条请求、隐层宽度 h:

| 算子 | 朴素 decode | 推测 decode |
|---|---|---|
| `input_ids` / `positions` | `[B]` | `[B*(k+1)]` |
| block table(KV 索引) | `[B, 块数]` | **`[B, 块数]` ,不变** |
| embedding 查表 | `[B, h]` | `[B*(k+1), h]` |
| QKV 投影(每层) | `[B, h]` → `[B, 3H]` | `[B*(k+1), h]` → `[B*(k+1), 3H]` |
| attention | `[heads, B, seq_len]` | `[heads, B*(k+1), seq_len]` |
| MLP(每层) | `[B, h]` ↔ `[B, ffn]` | `[B*(k+1), h]` ↔ `[B*(k+1), ffn]` |
| LM head → logits | `[B, 词表]` | `[B*(k+1), 词表]` |

**只有 token 维从 `B` 变成 `B*(k+1)` ,权重矩阵一份没变,块表一行没变。** B=32、k=3 时 token 数从 32 变成 128,logits 从 `[32, 词表]` 变成 `[128, 词表]` ——仅此而已。

这和 02 章 7.1 是同一件事的两种外观。那边是 prefill chunk 与 decode token 混在一个 batch 里,这边是一条请求的草稿被摊平成多行;对执行层来说,**都只是「token 维变长了,其余不动」** ,变长注意力核照样按累计长度分段处理。这正是推测解码能塞进现有执行栈、几乎不动别处代码的原因。

表里的 `B*(k+1)` 是个简化写法,有两处要说准:**每条请求的草稿数是各自独立的**,代码里是一个逐请求的数组,不是统一的 k;**白送的那个位置数也是个变量**,不是写死的 1。真正的 logits 行数是「各请求草稿数之和,加上请求数乘以白送位置数」。

这里还藏着一道防线值得一提。取 logits 时,一条请求的若干行是从它 query 区间的**末尾往回数**取的。源码为此立了一条断言,注释说明了理由:**这条请求分到的 query 行数要是比它需要的 logits 行数还少,就会静默取到前一条请求的隐状态** ——不报错,不崩溃,只是算出一批张冠李戴的结果。断言防的是这种无声的串行数据。

一次 forward 里这四个位置各自在验什么:

### 1.5 为什么几乎是白送的

形状变了,计算量当然也变了。但耗时几乎没变——**因为 decode 的瓶颈不在计算量上**。

一步 decode 要读两样东西:模型权重(固定,与序列长无关),以及已经生成的所有 token 的 KV。以 70B FP16、80 层、8 个 KV head、head_size 128、序列长 2048、batch 为 1 为例:权重约 140 GB,KV 约 0.67 GB,合计约 141 GB。按 HBM 带宽 3 TB/s 算,**光是把这 141 GB 读一遍就要约 47 毫秒** ——这是单步耗时的下限,与算多少个 token 无关。而这一步的实际计算量只有几 GFLOPs,对着上千 TFLOPs 的峰值算力,利用率不到百分之一。

推测解码做的事就是:**同样读这 141 GB,算 k+1 个 token 而不是 1 个。**

| 一个 step 里 | 朴素 decode | 推测 decode(k=3) |
|---|---|---|
| 读权重 | 一遍 | 一遍,同一份 |
| 读已有 token 的 KV | 一遍 | 一遍,**一个字节都不多** |
| 写新 token 的 KV | 1 个 | k+1 个(写带宽远小于读,占比不到 5%) |
| 矩阵乘计算量 | 1 个 token | k+1 个 token(占比不到 1%) |
| 产出 token | 1 个 | 平均若干个(2.3) |
| 算力利用率 | 不到 1% | 约 4% |

第二行是整段论证的支点:**草稿 token 追加的是新的 K/V,已有 token 那一大坨 KV 的读取量一字不变。** 增量全部落在写入和计算这两个小项上,而它们本来就不是瓶颈——GPU 原本就在空转等数据。

这也解释了另一件反直觉的事:**目标模型的单步耗时与 k 几乎无关**(k 取 2 到 8 这个区间内)。唯一随 k 增长的是注意力的 Q×Kᵀ,但注意力的计算量远小于 MLP,它自身也是访存瓶颈(05 章讲过)而 KV 已经读过了,何况它只占一次前向总计算量的一两成。表里的百分比和下面的耗时都是量级参考,不是本仓库实测。

把一个完整例子的访存算到底更直观。生成 3 个 token:

- 朴素:三次目标模型前向,`3 × (140 + 0.67) ≈ 422 GB`
- 推测:一次目标模型前向加三次草稿前向,`141 + M_draft` GB

`M_draft` 是三次草稿前向的访存量。**草稿模型多大,直接决定这笔生意划不划算**:EAGLE 那类单层草稿头权重只有几百 MB,三次也就几个 GB,对着 422 GB 可以忽略;换成一个独立的 7B 模型(FP16 约 14 GB),三次就是 42 GB,占比已经不能忽略了。

**`M_draft` 与目标模型访存的比值,就是 2.4 那个 β 的物理含义。** 后面所有关于「值不值得」的讨论,量的都是这一件事。

### 1.6 「摊薄」有适用区间

上一节的论证有个前提,容易被顺手忽略过去:**那 141 GB 里,权重占 140,KV 只占 0.67——小了两个数量级。**

所以「读一遍权重多算几个 token」这个说法,严格来讲只在**小 batch、短上下文**的场景下成立。单条 2048 token 的序列,KV 根本不是访存的大头。

KV 要成为大头,得靠**长上下文乘以大 batch**。同一个模型,batch 开到 64、序列长到 32K,KV 就是 `320 KB/token × 32768 × 64 ≈ 671 GB` ——远远超过 140 GB 的权重。这时候被摊薄的主角换人了:**不再是权重被摊薄,而是 KV 被摊薄。**

结论方向不变(一次前向多产出几个 token,访存被摊薄),但**被摊薄的是什么、以及能省多少,随场景换主角**。顺带还有一个推论:推测解码对 batch=1 和小 batch 收益最大;batch 越大,朴素 decode 自身的算力利用率就已经不低了(batch=64 时可能到三成),可摊薄的空间随之收窄。

## Part 2|接受率、加速比与值不值的判据

### 2.1 验证必须比概率,不是比字面

阶段 3 的「验证」两个字,是整套机制唯一有数学风险的地方。

最朴素的验证是**比 token 字面**:草稿猜的和目标模型自己会选的一样就接受。贪心解码时这没问题。**随机采样时这么做是错的** ——会让最终输出的分布向草稿模型偏移,用户以为自己在从目标模型采样,拿到的却是被污染的分布。

正确的做法是**比概率**:接受概率取 `min(1, p/q)` ,拒绝之后从修正分布 `max(0, p−q)` 里采一个替补。这一套连同它的正确性证明、为什么不能直接从 `p` 重采、以及用猫狗鸟三个词做的端到端验算,**07 章 6.1 到 6.4 与 7.3 已经完整讲过,这里不重复**。

本章只需要接过它的一个结论:**推测解码是无损加速,不是近似加速** ——最终输出分布与「直接用目标模型采样」完全一致。所以下面所有关于加速比的讨论都只是在算时间,**不存在「用质量换速度」这个维度**。

### 2.2 接受率:两个分布的重叠度

草稿被接受的概率有多大,决定了这套机制能省多少。把它写成一个量:

$$
\alpha = \mathbb{E}_{q}\left[\min\left(1, \frac{p}{q}\right)\right]
$$

这个期望是**在草稿分布下取的** ——草稿按 `q` 提议,每个提议以 `min(1, p/q)` 的概率通过。展开来看,它正好等于**两个分布的重叠度**:草稿与目标在每个 token 上取较小的那个概率,加起来就是 α。

两个端点值得记住:草稿与目标完全一致时 α 为 1(每个提议都通过);两者毫无重叠时 α 为 0(一个都留不下)。

α 不是一个可以调的参数,**它是草稿模型质量的度量** 。选哪种草稿方案、草稿模型训得好不好,最终都体现在这一个数上。后面几节把 α 当已知量来推公式,实际部署时它要么实测、要么按经验估。

### 2.3 每 step 的期望产出

有了 α,就能算一步平均吐几个 token。做一个简化假设:**每个草稿 token 独立地以 α 被接受**(实际相邻位置是相关的,这是个近似)。

一步的产出只有两种结局:

- **前 i 个接受、第 i+1 个被拒**(i < k):产出 i+1 个(i 个接受的加一个替补),概率 `αⁱ(1−α)` 。
- **k 个全部接受**:产出 k+1 个(k 个接受的加一个白送的),概率 `αᵏ` 。

把两种结局加权求和:

$$
E[\text{tokens per step}] = \sum_{i=0}^{k-1}\alpha^{i}(1-\alpha)(i+1) + \alpha^{k}(k+1) = \frac{1-\alpha^{k+1}}{1-\alpha}
$$

两个端点对得上:α→1 时是 k+1(草稿全中,白送那个也拿到),α=0 时是 1(一个草稿都留不下,退化成朴素 decode)。

注意**无论接受几个,每一步都至少产出 1 个 token**:要么是被拒位置的替补,要么是全接受时白送的那个。这条保底是推测解码「最差也不会倒退到不产出」的原因。

### 2.4 加速比:两个自由量

一步的耗时是草稿加目标:`T_step = T_draft + T_target` 。而 1.5 已经说明 `T_target` 与 k 几乎无关,所以朴素和推测两边的每 token 耗时分别是:

$$
\text{TPOT}_{\text{naive}} = T_{\text{target}}, \qquad
\text{TPOT}_{\text{spec}} = \frac{(T_{\text{draft}} + T_{\text{target}})(1-\alpha)}{1-\alpha^{k+1}}
$$

记 `β = T_draft / T_target` ——**草稿开销占目标模型的比例**,也就是 1.5 末尾那笔账。相除化简得到一个很干净的式子:

$$
\text{speedup} = \frac{1-\alpha^{k+1}}{(1+\beta)(1-\alpha)} = \frac{E[\text{tokens}]}{1+\beta}
$$

**整套机制只有两个自由量**,各自对应一个 trade-off:

- **β(草稿开销)** 是纯额外成本。草稿模型越大、k 越大,β 越大,收益被吃掉得越多。β=0 时(n-gram、suffix 这类根本不跑模型的草稿方案)加速比取到最大。
- **α 与 k 一起决定期望产出。** α 高则 E 趋近 k+1;α 低则 E 趋近 1,此时草稿白跑,加速比可以小于 1——**比不开还慢。**

### 2.5 值不值得用:一条精确判据

把期望产出按等比数列展开,判据就浮出来了:

$$
E[\text{tokens}] = \frac{1-\alpha^{k+1}}{1-\alpha} = 1 + \alpha + \alpha^{2} + \cdots + \alpha^{k}
$$

加速比大于 1 就是 `E > 1 + β` ,两边减去那个恒定的 1:

$$
\alpha + \alpha^{2} + \cdots + \alpha^{k} > \beta
$$

**这是全章最有用的一个式子。** 左边是「k 个草稿 token 的期望净收益」——注意它和 2.2 的 α 定义一脉相承:第 i 个草稿要被采纳,得它自己和它前面每一个都通过,概率是 α 的 i 次方,把 k 个位置的采纳概率加起来就是左边。右边是「为此付出的草稿开销」。

**左边白捡到的 token 数,要多过右边的开销** ——判据就这一句话。

### 2.6 那条必要条件不能当门槛用

由 α < 1 可知左边小于 `kα` ,于是能推出一个必要条件 `α > β/k` 。这个式子形式简单,很容易被当成门槛拿去用。**它只必要不充分,当门槛会判错。**

举个反例:β = 0.5、k = 4、α = 0.3。`β/k = 0.125` ,α 是它的两倍多,看起来很安全。但代进真判据:`0.3 + 0.09 + 0.027 + 0.008 = 0.425` ,小于 β 的 0.5——**实际比朴素解码还慢**(加速比 0.95)。

原因是等比数列衰减得比线性快得多:α = 0.3 时,第四个草稿的贡献只有 0.008,`kα` 那个上界把它当成 0.3 来估,高估了三十多倍。**k 越大、α 越小,这个上界越离谱。**

下表把几种典型配置代进公式(E 按等比数列求和,加速比等于 `E/(1+β)` ):

| 场景 | β | α | k | E | 加速比 | 值得吗 |
|---|---|---|---|---|---|---|
| n-gram(草稿免费) | 0 | 0.5 | 3 | 1.875 | 1.88 | 值得 |
| n-gram(草稿免费) | 0 | 0.3 | 3 | 1.417 | 1.42 | 值得 |
| n-gram(草稿免费) | 0 | 0.1 | 3 | 1.111 | 1.11 | 勉强 |
| 小草稿模型 | 0.2 | 0.7 | 4 | 2.773 | 2.31 | 值得 |
| 小草稿模型 | 0.2 | 0.3 | 4 | 1.425 | 1.19 | 勉强 |
| 小草稿模型 | 0.5 | 0.3 | 4 | 1.425 | **0.95** | **反而更慢** |
| EAGLE(草稿快且准) | 0.15 | 0.8 | 4 | 3.362 | 2.92 | 很值得 |

**第 5、6 两行最值得盯住**:α 相同,E 就相同(都是 1.425),差别全在 β。**同样的接受率,草稿贵一倍就能把结果从「勉强能用」翻到「负收益」。** 这也是为什么草稿方案的选择比 k 调到几更要紧——β 在分母上,而 k 只是让左边那个等比数列多加一项越来越小的尾巴。

第一行与最后一行则是另一个方向的对照:n-gram 靠 β=0 取胜,EAGLE 靠 α=0.8 取胜,**两条路都能到位,但走法完全不同。**

### 2.7 三种验证方法,只有默认那种有等价性保证

2.1 说的无损保证,对应的是配置里的默认选项。基准上验证方法一共有三种:

| 取值 | 怎么验 | 分布等价 |
|---|---|---|
| **`standard`(默认)** | 逐个位置比概率,就是 2.1 那一套 | **保证** |
| `synthetic` | 按预先设定的接受率盲接受,**完全不看** `p` 与 `q` | 不保证 |
| `block` | 把整条草稿链**联合**验证,而不是一个一个判 | 另一套证明 |

`synthetic` 是压测用的仿真模式:接受率由用户直接给定(或者给一个目标平均接受长度,内部换算成逐位置的接受率),于是可以把 α 当旋钮拧,专门用来量「接受率变化对吞吐的影响」。**它的输出分布是错的,不能用于生产** ——选它就等于跳出了 2.1 那套数学。

`block` 换的是另一条技术路线:不逐位置独立判定,而是对整块草稿做联合验证,能在同样的 α 下接受更长的前缀。它的出处源码直接写在注释里(Sun 等,2024,arXiv:2403.10444),有自己的一套正确性论证。这里只需要知道它存在、且不走 2.1 的那套推导。

还有一个相邻的配置决定**草稿怎么采样**,默认是贪心。贪心不破坏等价性:**它相当于把草稿分布 `q` 取成 one-hot** ,此时 `min(1, p/q)` 退化成 `p(x)` ,仍是一个合法的拒绝采样器(实现里就是直接把草稿概率当成 1 代进去)。代价在接受率上——贪心草稿的 α 通常低于按 `q` 随机采的版本。改成随机采样会保留完整的草稿 logits 参与比值检验,换来更高的 α,**代价是多一份显存**。

## Part 3|草稿从哪来:各家 proposer

### 3.1 草稿从哪来:两条路线

前面十三节把「验」讲完了,还剩「猜」。α 是草稿模型质量的度量(2.2),而草稿怎么来,就决定了 α 和 β 各是多少 —— 也就决定了 2.5 那条判据两边的值。

基准上的方案按**要不要跑一个模型**分成两类:

- **模型驱动**:EAGLE / EAGLE3、MTP、Medusa、DFlash、DSpark,以及直接拿一个小模型当草稿。有权重、有 GPU 前向,**`β > 0`** 。
- **无模型**:n-gram、Suffix Decoding。纯在 CPU 上做字符串或树查找,**`β ≈ 0`** 。

这条分界正是 2.6 那张表里两组场景的来源:无模型那一类 β 为 0,判据左边只要大于 0 就成立,所以哪怕 α 只有 0.1 也还有得赚;模型驱动那一类要先还掉 β,α 不够高就是负收益。

下面逐个讲各自怎么猜。**它们的能力、KV cache 占用与横向对比不在这里** ,那是另一个问题,后面单列。

### 3.2 EAGLE:拿目标模型的隐状态当草稿的输入

EAGLE 用一个独立的小模型当草稿,但它和「随便找个小模型来猜」有一个本质区别:**它的输入是目标模型的隐状态,不是 token。**

这件事让它的两个阶段长得不一样:

- **第一步**:输入是目标模型这一轮算出的最后一层隐状态。此时草稿模型拿到的信息量远超一个 token id —— 它看到的是目标模型「想说什么」的完整内部表示,所以第一个草稿猜得特别准。
- **之后每一步**:上一步已经采出了一个草稿 token,这时只有 token id 可用,于是走 embedding 查表转成向量再往下猜。

**所以草稿模型需要 embedding 层,不是因为它要重新分词,而是因为从第二步起它只剩 token id 可用了。** 这个区别容易记反,记反了就会以为草稿模型自带一套词表。

代码里这两阶段是「一次前向 + 一个循环」:先用隐状态跑一次拿到第一个草稿,再循环 k−1 次,每次把上一步的草稿 token 喂回去。循环体的第一句是把 token id 转成 int32,旁边的注释解释了原因:**草稿模型被编译过,而 `argmax` 默认返回 int64,类型对不上会出事。**

EAGLE3 只在输入这一侧作了改动:它不满足于最后一层,还要目标模型的**若干中间层**,在草稿侧先拼接再投影回原本的宽度。代码里这一支带着一句断言,把它和 EAGLE 严格分开。

accept rate 能到八成以上是这类方案被广泛使用的原因(讲稿的经验值,不是本仓库实测)。代价也很直白:**得为每个目标模型单独训练一个配对的草稿模型**,而且 `β > 0` 。

### 3.3 EAGLE 与 MTP 的分野只在权重从哪来

MTP(Multi-Token Prediction)和 EAGLE 常被当成两种方法,**但在代码里它们几乎是同一个东西。**

判断「要不要走这条路」的谓词叫 `use_eagle` ,它返回的是五个方法名的集合 —— `mtp` 就在里面。于是第一代实现里,MTP 和 EAGLE 共用同一个 proposer 类;第二代虽然拆成了两个类,但两个类的结构相同,都只重写了「装载草稿模型」这一个方法,而且装载函数还是同一个。

真正的差别只有一处:**草稿权重从哪来。**

| | EAGLE | MTP |
|---|---|---|
| 草稿权重 | 单独训练、单独发布的小模型 | **目标模型 checkpoint 里自带的那一层** |
| 怎么配 | 用户显式指定草稿模型 | 自动指向目标模型同一份 checkpoint,改写架构名即可 |
| 隐状态输入 | 最后一层(EAGLE3 用多层) | 最后一层 |
| embedding 与 lm_head | 与目标共享 | 与目标共享 |

MTP 那一层是在目标模型训练时**联合优化**出来的,所以它天然贴合目标模型的分布 —— 这是它 accept rate 好看的原因,也是它不需要额外训练步骤的原因。配置上的「自动指向同一份 checkpoint」也顺理成章:权重本来就在那里,只是需要按另一个架构名把它装出来。

顺带一提,`use_eagle` 这个名字连源码自己都觉得不合适 —— 方法上方的注释说它其实是「使用目标模型隐状态的那一族方法」的代称,底下还挂着一条待重构的记号。读到这里不必费劲去想 MTP 为什么算 EAGLE。

### 3.4 MTP 已经不是 DeepSeek 一家的东西

MTP 这个设计出自 DeepSeek,很多材料也就停在「DeepSeek 系模型才有 MTP」。**基准上早已不是这样了。**

那个按目标模型改写架构名的地方,实际是一张**分发表**:基准上有 22 个 MTP 架构名、27 个对应的模型类型,覆盖 DeepSeek(V3 / V3.2 / V4 各一个)、GLM、Qwen、Kimi、MiMo、Ernie、Nemotron、混元、Pangu、LongCat、Gemma、MiniMax、Bailing 等一长串厂商。

**换句话说,「目标模型 checkpoint 里自带一层用来多预测一个 token」已经成了一个跨厂商的通行约定**,而 vLLM 这一侧要做的只是认出它是哪一家的、按对应的架构名装出来。这解释了为什么这张表这么长而且还在变长 —— 每来一个自带 MTP 的新模型,这里就多一支。

对使用者的实际含义是:**拿到一个新模型想开推测解码时,先看它的 checkpoint 里有没有 MTP 层** 。有的话这是最省事的一条路 —— 不用训练、不用额外权重、不用多配一个模型。

### 3.5 权重共享是有条件的

草稿模型要用 embedding 和 lm_head,而这两样在大词表模型上都不小。基准的做法是**尽量和目标模型共用同一份**,但这件事比「直接指过去」讲究。

判断要不要共享的逻辑是:**草稿自己没有那一份,就共享;草稿自己有一份,那就比一比 —— 逐字节相同才共享,不同就各留各的。** 所以「共享省显存」这句话要带个前提:草稿模型自带了一份不一样的权重时,显存是省不掉的,也不该省。

这里有个很有意思的细节:**判等这一步自己也在省显存。** 注释说明了原因 —— GPU 上比较两个张量是否相等,会分配一个和输入等大的布尔掩码。于是代码先看一眼显存余量,余量不足权重大小两倍时,**把两份权重都搬到 CPU 上去比**。一个「为了省显存,先检查省不省得起」的自指判断。

还有两条语义值得记住:

- **草稿模型看到的 embedding 不带 LoRA。** 目标模型挂了 LoRA 适配器时,共享过去的是**底下那层原始 embedding**,注释直接写明了这一点。也就是说草稿是按基座模型的语义在猜,而目标是按 LoRA 之后的语义在验 —— 这会体现在 accept rate 上。
- **流水线并行下 embedding 可能不在本 stage。** 这时草稿若确实需要它,会抛一条说清楚的错误,而不是拿个空的继续跑。

装载草稿模型时还有三处配置覆写:MoE 后端、KV cache 精度、注意力后端,都可以让草稿用与目标不同的设置。每一处都带着理由,其中注意力后端那条最见功夫:**只在用户显式指定时才覆写,好让草稿默认保持与目标一致的 KV 布局。**

### 3.6 n-gram:不跑模型,在已经写过的字里找重复

n-gram 把 β 压到了 0:**它根本不跑模型,纯在 CPU 上做子串匹配。**

思路一句话:在已经生成的全部 token(prompt 加 output)里,找一段**和当前末尾相同**的子串;找到了,就把那段子串**当时后面跟的 k 个 token** 拿来当草稿。

依据是语言有重复模式。代码场景最典型 —— 函数签名后面跟 `print` 或 `return` ,`for i in range` 后面跟缩进,同一个变量名反复出现。这些模式在同一份文件里会重复很多次,前面出现过什么,后面大概率还是什么。

它还有两道提前返回值得记:**上下文比最短匹配长度还短就直接不猜**;以及草稿数量会被 `max_model_len` 减去当前长度截一刀,**不许把序列顶过模型的最大长度**。后面 Suffix Decoding 那边有同一道约束。

代价也很清楚:accept rate 只有三到五成(讲稿的经验值),而且**对全新内容完全无效** —— 没写过的东西,查不到。所以它是那种「白捡就赚,捡不到也不亏」的方案,判据左边只要大于 0 就成立。

基准上还有一个 GPU 版,把匹配搬到 Triton kernel 里做,给大 batch 用 —— batch 一大,CPU 端的匹配自己会变成瓶颈。它还是异步调度白名单里的一项,而**普通的 CPU 版 n-gram 不在这份白名单里**。

### 3.7 n-gram 的算法:把后缀匹配翻成前缀匹配

「找一段和当前末尾相同的子串」直接做是 O(N²) —— 每个位置都要往回比一遍。基准用了一个很漂亮的转换。

**把 token 序列整个反转。** 于是「找和**末尾**相同的子串」变成了「找和**开头**相同的子串」,而后者正是 KMP 算法里 LPS 数组(最长公共前后缀)回答的问题,一遍扫描 O(N) 就能算完。

两个参数各管一头:

- **最短匹配长度**:太短的匹配是噪声。只匹配上一两个 token 就拿后面的内容当草稿,基本必错。
- **最长匹配长度**:它限制的是 LPS 数组的大小。源码注释说得很直接 —— 匹配长度反正被这个上限截住了,那就只给前这么多个前缀留位置,**省内存**。

整个匹配跑在 numba 的即时编译里,批内多条请求还开了多线程并行。**这是全章唯一一个瓶颈在 CPU 而不在 GPU 的组件**,所以它的优化方向和别处完全不同:别处在躲同步、躲分支,这里在躲 Python。

### 3.8 Medusa:一次前向,多个头各出一个 token

Medusa 不另外跑草稿模型,而是**在目标模型上多装几个解码头**。目标模型前向一次,各个头分别从同一份隐状态上预测一个位置,一次就把 k 个草稿都出齐。

和 EAGLE / MTP 对比,差别在猜的方式:**EAGLE 是自回归地猜 k 个(要 k 次草稿前向),Medusa 是并行地猜 k 个(零次额外前向)。** 代价是各个头彼此看不见,猜出来的 k 个 token 之间没有依赖关系。

它也因此**不产生独立的 KV cache** —— 它只在目标模型已有的隐状态上做预测,没有自己的序列要缓存。

有两处实现层的事实会直接影响能不能用上它:

- **它只有第一代实现。** 第二代的草稿组件分派里根本没有 Medusa 这一支,走到底会抛「尚不支持」。
- **它出的是 argmax,不产出草稿概率。** 也就是说它只能走 07 章 6.5 讲的贪心那一侧的判定,没有按概率打折的那条路。

### 3.9 Suffix Decoding:后缀树,而且草稿长度是变的

Suffix Decoding 和 n-gram 同属无模型一类,但它把「查重复」这件事做得更彻底:**为每个请求建一棵后缀树**,索引已经见过的全部 token。每次要猜时,拿当前序列末尾的一段当 pattern 在树里找最长匹配路径,沿着这条路径往下取 token 当草稿。

它和 n-gram 最重要的区别是 **草稿长度不是固定的 k,而是按匹配深度变的**:匹配得深就多给几个,匹配得浅就少给。上限由三个量共同卡住 —— 配置的草稿数(同样要减去模型最大长度的余量,和 n-gram 那道是同一道)、一个倍率上限,以及一个概率下限。

**这是全章第一个「每条请求草稿数不同」的方案** ,正好用上 1.4 说过的那件事:草稿数在代码里本来就是一个逐请求的数组,不是统一的 k。

另一个特点是**后缀树跨请求复用**:缓存多少条请求由配置决定,于是相同 prompt 的后续请求能直接吃到之前那条请求的历史输出。对 RAG 和文档问答这类场景效果特别好 —— 文档内容大量重复,后缀树能精准匹配很长的序列。

代价有三条:每个新 prompt 都要建树;非文档场景收益寥寥;而且它**依赖一个外部库**,代码里是在函数体内惰性 import 的。

### 3.10 DFlash:用 mask filling 把 k 次串行压成一次

EAGLE 那条路线的开销全在「串行」两个字上:k 个草稿要 k 次草稿前向,`β` 正比于 k。DFlash 的问题是:**能不能一次前向就把 k 个都猜出来?**

障碍是自回归的本性 —— 第二个 token 依赖第一个。DFlash 的绕法是 **mask filling**,思路来自 BERT:一次前向里发射 1 个 anchor 加 k 个 mask 位,**每个 mask 位独立预测自己那个位置该是什么**,谁也不看谁。anchor 那一位则用目标模型的隐状态预测白送的那个 token。

于是 `β` 从正比于 k 变成了一次前向的固定开销。

代价是联合分布变了:自回归给出的是 `P(t₁)·P(t₂|t₁)·P(t₃|t₂)`,mask filling 给出的只是 `P(t₁)·P(t₂)·P(t₃)` 这样的近似独立形式。**猜得更快,但猜得更差。**

实现上有一处很能说明问题:在第一代里,DFlash 和 EAGLE **共用同一份代码** —— 那个自回归循环前面有一句判断,「并行 drafting」命中时采完一次就直接返回,**压根不进循环**。所以两者的关系不是两套算法,而是「进不进那个循环」。第二代才把它拆成独立的草稿组件类,而且它**直接继承草稿模型基类,不经过自回归那一层** —— 继承关系本身说明了它不是自回归的。

### 3.11 不等效,为什么还能用

上一节的结论听起来很糟:DFlash 的草稿分布和 EAGLE **数学上不等效**,它丢掉了 token 之间的依赖。

| | EAGLE(自回归) | DFlash(并行) |
|---|---|---|
| 草稿联合分布 | $P(t_1)\cdot P(t_2 \mid t_1)\cdot P(t_3 \mid t_2)$ | 近似 $P(t_1)\cdot P(t_2)\cdot P(t_3)$ |
| 位置之间 | 每个都看着前一个 | 各自独立预测 |
| 草稿前向次数 | k 次,串行 | 1 次,并行 |
| `β` | 正比于 k | 与 k 无关 |
| accept rate | 高 | 较低 |

但它确实在用,有两条理由。

**第一,草稿模型就是照着 mask filling 训出来的。** 它在训练时看到的就是随机 mask,学的就是「看不见相邻位置时怎么合理地猜」。所以它并非一个被迫在陌生模式下工作的自回归模型,而是为这个模式优化过的模型。

**第二条更根本:拒绝采样根本不要求草稿是对的。** 07 章 6.1 证过,无论草稿质量如何,最终输出分布精确等于目标模型的分布。**草稿差只影响 accept rate,不影响正确性。** 于是「草稿准不准」从一个正确性问题,降级成了一个纯粹的性能问题 —— 而性能问题是可以拿判据去算的。

算的就是 2.5 那条判据:DFlash 把 β 压小了,却也把 α 压小了。谁赢取决于两边各降了多少。**k 不大(两到四)而草稿模型对 mask filling 训得又好时,α 的损失可能抵不过 β 的节省** ,这时候 DFlash 划算;反之 EAGLE 划算。2.6 那张表就是拿来算这件事的。

### 3.12 DSpark:在并行和自回归之间找折中

DFlash 放弃了全部 token 间依赖,EAGLE 保留了全部。DSpark 问:**能不能只花并行的钱,买回一部分依赖?**

它的做法是把两件事拆开看。一次草稿里其实有两个阶段:**主干前向**(算出各个位置的 logits)和**采样**(从 logits 里挑 token)。DFlash 两个阶段都是并行的。DSpark 保留并行的主干前向 —— 这是省时间的大头 —— 但把采样改成**从左到右逐个做**,每采一个,就用它去调整下一个位置的 logits。

这样主干仍然只跑一次,而采样阶段有了依赖。源码把这个偏置叫马尔可夫偏置:每个位置只参考**前一个**已采出的 token,而不是全部前文 —— 所以它是「半自回归」而不是自回归。

它和 DFlash 还有一处布局差异,理解起来有点绕但很关键:**DFlash 每请求发 1+k 个 query 位,那个 anchor 是用来出白送 token 的,不参与草稿预测;DSpark 每请求只发 k 个,它的 anchor 本身就是第一个草稿预测。** 两种布局互斥到什么程度呢 —— DFlash 那一侧直接把 DSpark 那条路径禁掉了,配置里打开会当场报错,错误信息就写着「DFlash 用的是固定的 1+N 布局,anchor 是 bonus token」。

反过来也有一个例外:某种格式的 checkpoint 装 DSpark 权重时,**反而要用 DFlash 的 1+k 布局**,此时 anchor 又变回白送 token。所以「发几个 query 位」这件事既看方法也看 checkpoint 格式。

最后一个细节容易误解:**「逐个采样」不意味着每步都要回 CPU 下发一次。** 文档字符串写明,整个草稿步 —— 并行主干前向**加上**那段序列马尔可夫采样 —— 全部被录进完整 CUDA Graph。串行的是数据依赖,不是 kernel 下发。

### 3.13 选哪个草稿方案,决定了整个引擎跑哪一代运行器

1.2 讲过运行器默认走第二代。这一节把那句话补完整:**默认是第二代,但推测解码能把它否决掉。**

第二代的草稿组件只实现了六种方法:EAGLE、EAGLE3、MTP、DFlash、DSpark,以及一个抽取隐状态的工具方法。**其余全部落在「第二代尚不支持」那份清单里** —— n-gram 和它的 GPU 版各占一条,Medusa、Suffix Decoding、独立草稿模型则由一条兜底规则统一否决掉。命中之后整个引擎自动退回第一代运行器。

还有一条更细的:EAGLE 想开并行 drafting 也会被否决,注释解释了为什么 DFlash 和 DSpark 不受影响 —— 它们在第二代上本来就是原生并行的,走的是自己的草稿组件。

这条因果值得单独记住,因为它把两件看起来无关的事拴在了一起:

**你挑的是草稿方案,连带换掉的是整个执行层。** 用 n-gram 或 Medusa,就等于把 06 章讲的那套「状态常驻 GPU、每步只传增量」换回了「CPU 侧维护镜像、逐步整体搬运」。这不只是名字不同,性能特征、CUDA Graph 的档位、乃至能不能开异步调度都跟着变。

它还解释了一个很容易形成的错觉。不少材料会说「推测解码跑在第一代运行器上」,这在经验上常常是对的 —— 因为 n-gram、Medusa、Suffix、独立草稿模型这几种最常见的配置**确实都在第一代上跑**。但原因不是第一代是默认,而是**这些方案把第二代否决掉了**。把结论记成「第一代是主路径」,下次配 EAGLE 或 MTP 时就会找错地方。

## Part 4|草稿的 KV cache 与横向对比

### 4.1 谁有自己的 KV cache

草稿模型要是个 transformer,它自己也要缓存 K/V —— 它每一步都得读全部历史位置。于是「有没有独立的 draft KV cache」把前面那些方案又切了一刀:

| 方案 | 草稿怎么产生 | 有独立的 draft KV cache |
|---|---|---|
| EAGLE / MTP | k 次自回归前向 | 有 |
| DFlash / DSpark | 1 次并行前向 | 有 |
| 独立草稿模型 | k 次自回归前向 | 有 |
| Medusa | 复用目标的隐状态加 k 个头 | **没有** |
| n-gram / Suffix | CPU 上查重复 | **没有**,压根不跑模型 |

这一刀的后果比看上去大:**有独立 KV cache 的那几种,显存要多占一份,PD 分离时还要多传一份**(4.5)。没有的那两类则彻底不碰显存 —— Medusa 是因为它只在目标模型已经算好的隐状态上做预测,没有自己的序列。

下面三节讲这份 KV cache 是怎么安排的。**它的安排方式比「多一份」这句话讲究得多,而且解释了推测解码为什么能塞进现有的块管理而不用改块管理。**

### 4.2 草稿与目标共用一份块映射,写的却是不同的层

最自然的猜想是:草稿模型是另一个模型,那就给它另开一套块表和块池。**基准不是这么做的。**

它的做法可以概括成一句话:**草稿层和目标层写进不同的 KV cache 张量(它们本来就是不同的层),但用同一份块映射。**

实现上有三处关键动作:

- **分层是按注册时机分的。** 装载草稿模型**之前**先把当前所有注意力层快照一遍,装完之后再取一次全集,两者相减,差集就是草稿新注册进来的那些层。**这个技巧不依赖任何命名约定** —— 不用去猜哪个层名带 `draft` 前缀,谁是后来的谁就是草稿的。
- **草稿可以用自己的注意力后端,但只在草稿层上生效。** 初始化后端时把「活跃层名」限定成草稿那批,于是两个模型各用各的 kernel 而互不干扰。草稿的注意力配置默认就是目标的那一份,只有注意力模式和目标不同的方案(比如可以非 causal 的 DFlash)才重写它 —— 这个「默认继承、例外重写」的意图写在属性的文档字符串里。
- **块表对象是直接复用的,不是拷贝。** 目标模型的块表传进来,草稿原样存下来用。

03 章讲过块表的两步定位,这里不重复。要接的是那个结论:**块映射本身与「哪一层」无关**,它只回答「这条请求的第 n 个 token 落在哪个物理块的哪个槽」。既然草稿和目标处理的是同一条序列的同一批位置,这份映射就该共用 —— 不共用反而要多维护一份、还得保证两份不打架。

### 4.3 于是 draft prefill 是零成本的

上一节那个安排有一个很漂亮的直接后果。

草稿模型的第一步(拿目标隐状态跑那次前向)需要注意力元数据和槽位映射。按理说这要重新构造一遍 —— 而 05 章讲过,构造注意力元数据本身是笔不小的 CPU 开销。

**但它不用构造,直接拿目标模型这一步已经算好的用。** 源码注释把理由写得很干脆:两者的 batch 形状与 KV cache 布局完全相同。形状相同是因为草稿和目标在处理同一批请求的同一批位置,布局相同是因为它们共用那份块映射。

不过这份便宜是有代价的,注释在另一处点明了:**草稿的图捕获因此被绑在了目标模型的构造器与缓冲区上** —— 既然运行时要复用目标的元数据,捕图时也必须用同一套构造器造出假的元数据,否则捕的图和跑的形状对不上。**省掉一次构造,换来一处耦合。**

### 4.4 一次草稿里,KV cache 经历了什么

把一次草稿从头走到尾,看这份 KV cache 什么时候被写:

1. **草稿的第一步(prefill)** ——用目标的隐状态和目标那份注意力元数据跑一次草稿前向,写进草稿 KV cache,产出第一个草稿 token。开了完整图就重放整图,否则走普通路径。
2. **早退** ——只要一个草稿 token 的话,到这里就返回了,后面整段不执行。
3. **后续 k−1 步** ——每次拿上一步的草稿 token 再跑一次前向,**追加写**草稿 KV cache。这一段有融合与非融合两种实现。
4. **返回** k 个草稿 token,交给目标模型验证。

之后目标模型一次前向验完,**被接受的那些 token 的 K/V 已经在目标的 KV cache 里了** —— 因为验证那次前向本来就把它们算了一遍并写了进去。

那被拒绝的位置呢?它们的草稿 K/V 还留在草稿 cache 里。**不擦除,靠下一次草稿时的回退覆盖掉** ——Part 5 讲这件事的完整形状。

### 4.5 PD 分离下会怎样

推测解码和 PD 分离(02 章 6.5)撞在一起会发生什么,是个很自然的问题。这一节要**先把代码说了什么和从代码推出什么分开**,因为这里两者的把握程度确实不同。

**代码里能直接验证的三条:**

- 草稿层和目标层共用同一个块表对象,所以 KV connector 按块传输时,**同一个块范围内的草稿层 K/V 和目标层 K/V 是一起走的**。
- **没有任何针对「P 节点只跑草稿第一步、D 节点跑剩下 k−1 步」的代码路径。** 草稿函数一被调用就一口气跑完全部步骤,中间只有那个「只要一个 token」的早退。
- **没有通用的「推测解码与 KV 传输互斥」断言。** 限制是各个 connector 自己加的,不是全局的。

**由这几条推出来的行为**(标明是推论):

- 草稿模型是 transformer,解码时要读所有历史位置的 K/V。P 节点做完 prefill 后,**草稿层的 K/V 如果没跟着目标 K/V 一起传到 D,D 的第一次草稿前向就会在未初始化的 K/V 上做注意力** ——草稿质量崩掉,接受率暴跌。所以**传草稿 KV 是正确性要求,不是优化项**。
- 而因为共用块映射,这个要求**顺带就被满足了**:传块就等于同时传了两份层的 K/V。
- P 节点也必须加载草稿权重(它要跑草稿的第一步),这是 PD 分离加推测解码相比纯 PD 分离的额外显存成本。
- n-gram 和 Suffix 无模型无 KV cache,PD 分离下没有任何额外传输成本。

推论到此为止。**但推理给得出方向,给不出代价的量级** ——代码里还有一条推不出来的:某个 connector 在同步块大小时留了注释说明,**开推测解码后主模型与草稿模型可能用不同的注意力后端、物理块大小不同,于是它要取两者的公共(最小)块大小**,好让 KV cache 的注册与传输对两个模型都成立。也就是说额外成本不止「多传一份」,还可能是**整个传输粒度被迫变细**。

还有一处更隐蔽的交互:某个存储后端的文档字符串提到,**推测解码会就地迁移推测状态块**,于是按位置读块可能读到已释放或仍活着的推测块,在一个合法的前缀哈希下写进错误的字节 —— 所以那一类状态只走精确交接路径,不走普通的按位置保存。

### 4.6 各方案横向对比

前面逐个讲完了,横着摆一次。**接受率那一列是社区经验区间,不是本仓库能验证的数字,只作数量级参考;** 各方案的代码位置见代码索引页。

| 方案 | 独立模型 | 独立 KV cache | `T_draft` | 接受率(经验) | 训练需求 | 推荐场景 |
|---|---|---|---|---|---|---|
| EAGLE / EAGLE3 | 有(一两层) | 有 | 中,k 次前向 | 80%+ | 要训草稿头 | 通用 |
| MTP | 有(目标内置) | 有 | 中,k 次前向 | 70~85% | 模型原生自带 | 自带 MTP 层的模型 |
| DFlash | 有 | 有 | **低,1 次并行前向** | 中 | 要训 mask filling 模型 | 延迟极度敏感 |
| DSpark | 有(结构同 DFlash) | 有 | **低,1 次并行加采样** | 中~高 | 要训,还多一个马尔可夫头 | 想要 DFlash 的速度加一点依赖 |
| Medusa | 有(多个头) | 无 | **低,0 次额外前向** | 60~75% | 要训头 | 已有 Medusa 权重 |
| n-gram | 无 | 无 | **零** | 30~50% | 无 | 代码补全、重复模式 |
| Suffix | 无(后缀树) | 无 | **零** | 50~90% | 无(在线建树) | RAG、文档问答 |
| 独立草稿模型 | 有(完整小模型) | 有 | **高**,k 次小模型前向 | 看模型配对 | 无,用现成小模型 | 有同族小模型 |

这张表最该横着读的是 `T_draft` 和接受率这两列 —— 它们正是 2.5 那条判据的两边。**Suffix 那一行的区间跨度最大(50%~90%)**,因为它极度依赖场景:文档重复度高时后缀树能匹配很长,换成开放对话就基本失效。

表里列的是用户视角的主要方案。代码里还有几个由草稿配置二次分派出来的变体、一个非推测用途的隐状态抽取方法,以及一个让用户自带类的插件口子,它们大多不对应新的方法名。

### 4.7 同族四种方案的前向次数与写入时机

EAGLE、MTP、DFlash、DSpark 是同一族 —— 前面那个谓词对它们全返回真,所以它们共用大量基础设施,**差异集中在「怎么把隐状态变成 k 个 token」这一件事上**。把这件事的几个维度摆开:

| | EAGLE / MTP | DFlash | DSpark |
|---|---|---|---|
| 草稿主干前向次数 | **k 次** | **1 次** | **1 次** |
| 额外的轻量步骤 | 无 | 无 | k 次马尔可夫采样,**不含前向** |
| 每请求 query token 数 | 第一步约 k+1,后续 1 | 固定 1+k | 固定 k |
| 上下文 K/V 从哪来 | 草稿自己前向算出来 | **目标隐状态直接投影** | 同 DFlash |
| 注意力元数据 | **每步重建** | 构造一次新的 | 同 DFlash |
| causal | 恒为是 | **可以非 causal** | 同 DFlash |

有两行值得单独说。

**「上下文 K/V 从哪来」是 DFlash 真正省钱的地方。** 上一批说它「一次前向预测全部 k 个」还不够准 —— 它把草稿做成了 cross-attention 结构:K/V 由目标的隐状态**直接投影**得到并写进 cache,**根本不经过草稿模型的完整前向**;前向只对那 1+k 个 query 位置做。省的不只是 k−1 次循环,还有 context 那一整半。

**DSpark 的 k 次采样循环里没有 transformer 前向。** 主干仍然只跑一次,循环里只有 embedding 查表、一个偏置投影和一次采样。**它拿回了部分 token 间依赖,却几乎没有付出前向代价** ——这是它相对 DFlash 的全部卖点。

最后那一行「可以非 causal」也不是小事:DFlash 的 mask 位彼此看不见(3.10),这在注意力层面就是非 causal 的掩码模式,由草稿配置决定,开启时会逐层断言确实关掉了 causal。**这也是它需要重写那个注意力配置属性的原因**(4.2)。

### 4.8 KV cache 管理:四者的共性与差异

共性就是 4.2 那一条,四者完全一样:**同一份块映射,不同的层**,回退语义也一致。

差异有两处。

**写入时机。** EAGLE / MTP 每个草稿步写一个 token 的 K/V,k 步共 k 个槽位。DFlash / DSpark 则分成两段:上下文 K/V 在前向**之前**预写,query K/V 在前向内写。

而这两段用的是**两套独立的槽位映射缓冲**,理由写在注释里,和 06 章那条纪律完全同源:**query 缓冲的地址必须稳定才能被 CUDA Graph 捕获,而上下文的长度每步都在变、不能进图**,所以上下文那次预写只能在图外急切执行。一个「能不能进图」的约束,把一份槽位映射劈成了两份。

**能用几个 KV cache 组。** DFlash / DSpark 支持多个草稿 KV cache 组,并按层映射到各自的组;EAGLE / MTP 则有一道校验,要求全部草稿层落在同一组。

这条差异正好解释了 1.2 里那份清单中一个看起来很怪的条目 —— 「混合滑窗与全注意力的 DFlash 草稿」为什么第一代运行器做不到:**混合两种注意力就需要多个 KV cache 组,而多组是第二代才有的能力。**

### 4.9 什么能重叠,什么不能

「草稿前向能不能和目标前向并行起来」是个很自然的期待。**答案是不能,四者都不能** —— 它们在同一条默认流上首尾相接:目标前向、采样、拒绝判定、草稿,一个接一个。这是数据依赖决定的,草稿要用目标这一步的隐状态。

能重叠的只有三处,而且只有最后一处四者有明显差别:

- **CPU 段与 GPU 段** ——靠异步调度,见 4.10。
- **数据搬回与计算** ——采样结果和草稿 token 各走独立的拷贝流。基准上与推测解码相关的这类拷贝流一共有四条,各管一样东西。
- **CUDA Graph 把多次 kernel 下发合成一次重放** ——严格说这不算「重叠」,是消除下发间隙。但对草稿这种「很多个小 kernel」的场景收益极大。

第三点上四者差得很明显:

| | 图覆盖到哪 | 后果 |
|---|---|---|
| EAGLE / MTP | k 步循环里每步各自判档,**而且每步都要重建注意力元数据** | 下发与元数据构建的开销乘以 k |
| DFlash | 整个 query 前向一次重放 | 每步 query token 数恒定,形状天然固定 |
| DSpark | 覆盖主干前向**加上**那 k 次采样循环 | k 次采样也进图,不产生 k 次下发 |

DFlash 这一侧还有两个细节值得记:**它明确不支持分段图** ——注释直接写了这句话;于是它的档位是个二选一,**要么完整图要么完全不录**,没有中间档。而 06 章讲过主模型侧有三个具体档加两个复合档 —— **草稿侧比主模型侧少了整整一层回退空间。**

完整图还有个前提:草稿的注意力后端必须支持到「统一批次」这一级,否则退回急切执行并打一条警告。

### 4.10 异步调度支持谁

异步调度(06 章讲过它怎么把 CPU 段和 GPU 段叠起来)在推测解码下不是全员可用的,有一份白名单。

同族这四种**全部在白名单里**,但名单的写法藏着一个细节:白名单判的是「属不属于 EAGLE 那一族的类型别名」,而**那个别名的定义里已经把 DFlash 包进去了**;DSpark 则因为不在这个别名里,只能在条件里**单独列一次名字**。所以看起来像四个并列的条件,其实是「一族加一个特例」。

名单之外还有一条对四者都生效的硬约束:**关掉「补齐草稿批次」这个开关,就不能用异步调度** ——显式一起开会报错,自动模式下则悄悄把异步关掉。原因和 06 章 8.6 讲的「全接受假设」是同一件事:异步调度的整个设计依赖「草稿复用目标的 batch 形状、CPU 不需要知道这一步拒了几个」,而那个开关一关,批次形状就随拒绝数变化了。

## Part 5|图解

### 5.1 一次推测步里,块发生了什么

Part 4 讲清了草稿 KV 怎么安排,但「被拒绝的那些 K/V 到底留下了什么」还是文字。用一条请求走一遍(块大小 16,k=4):

| 阶段 | 这条请求的块表 | 已算 token 数 | 块里实际写了什么 |
|---|---|---|---|
| 步骤开始 | `[B0, B1, B2]` | 48 | B0 到 B2 写满,48 个 token 的 K/V |
| 调度这一步 | `[B0, B1, B2, B3]` | 48 | **乐观预留了 k+1 个槽**,B3 还是空的 |
| 目标模型验证前向 | 同上 | 48 | 上一个 token 加 4 个草稿的 K/V 写进 B3 |
| 判定:接受 2 个、第 3 个被拒 | 同上 | **修正为 51** | B3 里后两个位置的 K/V **成了垃圾数据** |
| 下一步 | 同上 | 51 | 新 token 从 B3 的第 3 个槽开始写,**直接盖掉垃圾** |

关键在第四行和第五行之间:**已算 token 数从 48 跳到 51(接受 2 个加 1 个替补),而 B3 里其实写了 5 个位置的 K/V。** 多出来的那两个位置没人去清理。

### 5.2 被拒绝的 K/V 不擦除,只是「逻辑上不存在」

上一节那两个垃圾位置,是这一章最容易担心的地方:它们会不会被读到?

不会,而且机制比「擦掉它们」简单得多。**注意力读到哪里为止,是由已算 token 数决定的,不是由块里写了什么决定的。** 已算数被回退到 51,那么第 52 个位置之后的内容对注意力来说就不存在 —— 哪怕物理上那里躺着上一轮的草稿 K/V。下一步写新 token 时从第 52 个位置开始,自然就盖掉了。

**所以「作废」这个动作的全部内容,就是把计数器减回去。** 调度侧用「草稿数减去接受数」算出拒绝数,从已算数里减掉;异步调度下还要额外走一条批次变化的修正路径,因为那时候 CPU 侧的账和 GPU 侧的实际情况隔了一步。

草稿那一侧(有独立 KV cache 的那几种)用的是同一份块映射,只是写进草稿自己的层,**回退语义完全一致** ——同一个计数器管着两边。

第二个要点是显存账:**块是提前按 k+1 预留的。** 调度时按「这一步最多产出 k+1 个 token」去申请空间,哪怕最后只接受了 1 个。02 章 4.1 讲过这件事的另一面 —— 推测解码的槽位预留会把需求量放大,进而更容易触发抢占;这里补的是它的来源:**预留必须按最坏情况算,因为申请空间发生在验证之前,那时候还不知道会接受几个。**

这就是推测解码额外占显存的原因之一,也是 2.5 那条判据没有体现的一项成本 —— 它只算了时间,没算显存。

## Part 6|机制之外:选链与 proposer 实现

前五部分讲清了推测解码**应该怎么工作**,Part 8 讲**怎么用它**。这一部分夹在中间,只放一类东西:照着源码读下来,**机制层面看不见、但真实存在的细节**。前面讲过的机制,这里一概不重复。

### 6.1 选哪个草稿组件是一条长链,顺序本身携带信息

3.13 说过「选哪个方案决定了跑哪一代运行器」。这一节讲下一层:**运行器定了之后,具体建哪个类,是一条十一分支的判断链**,而这条链的**顺序**不是随便排的。

顺序大致是:用户自带类 → n-gram → 独立草稿模型 → n-gram 的 GPU 版 → 两个特定模型族的 MTP → DFlash → Suffix → **EAGLE** → Medusa → 隐状态抽取 → 兜底抛错。

关键在 EAGLE 那一支的位置。3.3 讲过那个谓词有多宽 —— 它对 EAGLE、EAGLE3、MTP、DFlash、DSpark 全部返回真。**但它排在倒数第三。**

于是链条的行为是:**更具体的分支先把自己那一份截走,剩下的才落到宽谓词上。** 那两个特定模型族的 MTP 和 DFlash 都排在它前面,所以它们各自走各自的类;只有普通的 EAGLE、EAGLE3 和标准 MTP 才真正落到那个共用的类里 —— **这正是 3.3 说的「MTP 与 EAGLE 共用一个类」的实现机制。**

**排在宽谓词前面的分支,等于是在给它打补丁。** 读这类链条时,光看某一支的条件不够,还得看它前面有谁。

### 6.2 光看方法名,猜不出实际跑的是哪个类

上一节那条链还有个更实际的后果:**同一个方法名会分派到不同的实现类。**

`mtp` 这一个取值就有四种落点,分派时还要再读一遍草稿侧的配置做**二次判定**:

| 触发条件 | 实际落到哪 |
|---|---|
| 草稿模型类型是某个特定模型族的 MTP | 那个模型族的专用类 |
| 草稿架构属于另一个特定系列 | 另一个专用类(只有第一代有) |
| 草稿有多个 MTP 层**而且** k 大于 1 | 多模块 MTP 类(只有第二代有) |
| 以上都不满足 | 标准的 MTP 类 |

`dflash` 同理:草稿架构名里含第二代 DFlash 标记时走 DFlash2 的类,否则走普通 DFlash 类。

**这件事的危险在于它是静默的。** 配了「多个 MTP 层加 k 大于 1」,你以为在跑标准 MTP,实际跑的是多模块那个类;两者的行为并不完全一样。**排查 MTP 行为异常时,第一步该确认的不是参数,而是自己实际落在哪个类上。**

两条路径的这层分派**还不对称**:多模块 MTP 只有第二代有,那个特定系列的 MTP 和用户自带类只有第一代有。所以换运行器不只是换实现,可能连能走的分支都变了。

### 6.3 那条链里有一个不可达的分支

这一节讲一个容易读出错误结论的地方,因为我自己差点读错。

第一代的分派链里**没有 DSpark 的专属分支**,而那个宽谓词把 DSpark 也算在内。照着链读下来,很自然会得出:第一代下配 DSpark 会静默落进 EAGLE 的类,而不是报错。

**这个推理在局部无懈可击,但结论不成立 —— 那条路径走不到。**

配置初始化时的结构是「先决定用哪代运行器,再跑对应那一代的校验」。而 DSpark:

- 不设环境变量时,它在第二代的允许名单里、不触发任何否决,于是**默认就走第二代**,用的是 DSpark 自己的类。
- 显式指定要第一代时,它在「第一代做不到」那份清单里(1.2),校验阶段**直接抛错**。

**两条路都到不了那个分支。**

教训很具体:**读分派链时,光看链本身不够,还要看谁能走到链的前面。** 一条分支在代码里存在,不等于它在运行时可达 —— 上游的校验可能早就把它拦掉了。

### 6.4 MTP 层是轮流复用的

3.4 讲过 MTP 的权重在目标模型的 checkpoint 里。这一节补一个实现细节,它解释了一条看起来很怪的配置约束。

一个模型的 checkpoint 里可能有不止一个 MTP 层。而草稿要猜 k 个 token,k 和层数不一定相等。代码的处理方式是**取余数**:第几步就用第「步号对层数取余」那一层。

于是:**只有一层时,就是同一层反复前向 k 次;有多层时,多个草稿步轮流复用这些层。**

这直接解释了那条约束:k 设得比 MTP 层数大时,**必须能被层数整除**,否则报错 —— 因为要整轮地复用,不能剩半轮。

顺带也给 8.3 的调参留了个伏笔:发现某个位置之后接受率崩了、想把 k 降下来时,**MTP 下还得顾及新的 k 能不能整除**,不能随便取一个数。

### 6.5 有一个插件口子,文档里少见

方法名里有一个取值是 `custom_class` ——**它让用户把自己写的草稿组件塞进来。**

此时草稿配置里的「模型」字段不再是模型路径,而是**一个类的完整导入路径**。代码用 `importlib` 把它导进来,传配置对象实例化,然后**直接返回** ——文档字符串特意写明了「不加任何包装」。

约束只有两条:路径里必须含点号(否则报「无效的自定义提议器模块路径」),以及返回的对象必须有一个可调用的 `propose` 方法。**它不继承任何基类**,因此前面讲的那套骨架、KV cache 安排、图捕获它一样也享受不到,全部要自己管。

这个口子在第二代里没有 —— 又一处 6.2 说的不对称。

### 6.6 Gemma4 的草稿不推进位置

4.7 那张表里「每请求 query token 数」那一列,还有一个本章没展开的变体。

基类上有一个属性决定「草稿的每一步之间要不要推进位置和序列长度」:

- **EAGLE 与标准 MTP 是真** ——每一步都产生新的 K/V,位置自然要往前走。
- **某个模型族的 MTP 是假** ——它的草稿是 **Q-only** 的:复用目标模型的 KV,位置保持不变。

这个标志的影响比看上去大。位置不前进,意味着**后续步的 KV 上下文完全没变**,于是只有第一步需要真正重算注意力,后面几步可以跳过。代码里的条件写得很直白:要么位置在推进,要么是第一步,才跑注意力。

还有一处连带效果:这个标志为假时,**融合多步解码被无条件打开** ——既然每步的上下文都一样,合并成更少的 kernel 启动就没有障碍了。

### 6.7 基类留了四个空钩子

草稿组件的基类上有四个生命周期钩子:预填充前、预填充后、多步解码前、多步解码后。**四个在基类里全是空实现。**

它们的用途是给子类一个插状态管理的地方 —— 比如需要在草稿前后维护自己那份缓冲或索引的方案。基类不假设任何子类需要做什么,只把位置留出来。

这类「空钩子」值得记一笔的原因是:**它是判断一个抽象层成不成熟的信号。** 基类如果只定义了必须实现的抽象方法,子类想插点什么就只能重写整个流程;留了钩子,子类就能只管自己那一小段。

### 6.8 草稿复用目标元数据的那一步,是原地改的

4.3 讲过草稿的第一步直接复用目标的注意力元数据。这里补它的实现方式,因为它解释了 4.10 那条约束。

复用不是把目标的元数据拷一份改,而是**原地修改** ——把已算 token 数、query 起始位置、序列长度全都减去这一轮被拒绝的 token 数,然后返回一个「被拒数量」的 GPU 张量。

**注意这个返回值是留在 GPU 上的。** 这正是 4.10 说的「异步调度依赖 CPU 不需要知道拒绝数」的实现:拒绝数从头到尾没有回过 CPU,元数据的修正在 GPU 上就地完成。

**那条约束的来源到这里就完整了** ——关掉「补齐草稿批次」这个开关,就等于要求批次形状随拒绝数变化,而拒绝数只有 GPU 知道;CPU 要想据此调整形状,就必须把它同步回来,异步调度也就无从谈起。

## Part 7|机制之外:一个推测步的搬回与异步

### 7.1 一个推测步里有两次数据搬回,用途完全不同

**从这一节起是 1.1 那张表的最后一行。** 前面所有内容都在回答「推测解码能省多少 GPU 时间」,接下来要问的是它**花掉了多少 CPU 时间** ——因为这笔开销不是原本就有的,是推测解码自己带出来的。

普通 decode 一步里只有一次 GPU 到 CPU 的搬运:把采样出的 token 拿回来,判断是不是结束符、发给用户。**推测解码有两次,而且两次的用途毫无关系** ——这是读这段代码最容易混淆的地方。

| | 第一次:草稿 token | 第二次:采样结果 |
|---|---|---|
| 搬的是什么 | `[请求数, k]` 的**未验证候选** | 只有**已被接受**的那些 token |
| 给谁用 | **下一步调度的输入** ——调度器要靠它算出下一步该排多少个 token | **本步的输出** ——加进序列、判结束符、发给用户 |
| 什么时候真的等 | 在独立的拷贝流上发起,只记一个事件,**取值时才同步** | 同步模式下**当场就等** |

第二次那个「当场就等」,就是整条流水线的硬同步点 —— GPU 从这里开始空转,一直等到 CPU 把簿记、调度、输入准备全部做完。06 章 1.1 那条痛点在推测解码下的具体形态就是它。

顺带把一个词定下来:**簿记**指的是 GPU 算完之后 CPU 上那段**纯记账、不做任何计算**的工作 —— 把结果拉回来、更新 token 账本、更新请求状态、组装输出回传。它全程串行,而且必须等 GPU 完成。

**「一次搬运」和「两次搬运」的区别不只是多一次拷贝**:第一次那条路会绕整整一圈(GPU 生成 → 拷到 CPU → 穿过引擎进程 → 写回调度器 → 下一步再传回 GPU),而且这一圈**串行在关键路径上**。这就是为什么推测解码的 CPU 开销比普通 decode 重得多。

### 7.2 为什么草稿排在数据搬回之前

顺着上一节看代码会发现一个反直觉的顺序:**先采样、再算草稿、最后才把结果搬回 CPU。**

直觉上应该反过来 —— 先把结果搬回来看看这一步是不是出了结束符,确认还要继续生成,再去算下一轮的草稿。**基准不这么做,而且注释直接说明了理由。**

**第一条理由:草稿的输入全是 GPU 上的张量。** 采样出的 token、目标模型的隐状态、注意力元数据,没有一样需要 CPU 参与。注释写得很直白 —— 这类草稿方案可以直接拿 GPU 上的采样结果当输入,**不需要等簿记做完**。如果为了看结束符而先搬回 CPU,就等于在草稿前面硬插一个同步点,每一步都多一次 GPU 空档。

**第二条理由:那个时刻根本还不知道有没有结束符。** 停止判定发生在数据搬回之后的 CPU 侧,草稿要想知道,就必须先同步 —— 和第一条直接冲突。

**代价是明确的:这一步恰好出结束符的请求,它的草稿白算了。** 下一轮那条请求已经结束,回写草稿时直接跳过。

**这是一笔很划算的交易:用偶尔浪费一次小模型的 k 步前向,换掉每一步的一个 CPU 同步点。** decode 阶段每一步都省,而浪费只在请求结束的那一步发生一次。

反过来也印证了这个判断:那些**必须要 CPU 侧 token 列表**的草稿方案(n-gram、Suffix、Medusa),代码里就老老实实排在簿记之后 —— **「先搬回再算草稿」这条路只属于它们。**

### 7.3 第一次搬回不做会怎样:静默失效

上一节说第一次搬运会绕一整圈,那它是必要的吗?

**同步模式下它是「架构必要」,不是「算法必要」** ——异步调度的存在本身就是反证:那边就把它省掉了。必要性只来自一个事实:**调度器跑在 CPU 上**。调度下一步时要算「这条请求该排多少个 token」,而这个数等于 1 加上草稿数;更要紧的是,草稿的**具体值**要写进调度输出、由 worker 据此拼出下一步的输入序列。CPU 手里没有这些值,就拼不出来。

**不做会怎样?不是崩溃,是静默失效。**

请求的草稿字段一直是空的,于是下一步只验证 1 个 token,**推测解码悄悄退化成了普通 decode** ——接受率指标全为 0,而服务照常返回完全正确的结果,不报任何错。**这类问题最难发现:输出是对的,只是加速没了。**

(真正会崩的是另一种情况:GPU 那边仍按 k 个草稿走、CPU 这边只记 1 个,两边的计数错位,KV 槽位与序列长度对不上。)

**异步调度是怎么省掉它的:调度器其实只需要知道草稿的数量,不需要知道值。** 于是用一串占位值顶上,真实的草稿由 GPU 直接写进下一步的输入 —— 这一整圈就消失了。这和 06 章 8.1 讲的「采样结果不回 CPU」是同一个手法,只是对象换成了草稿 token。

但有三类情况仍然必须搬:**结构化输出**(文法状态机要按草稿逐个推进)、**两种 penalty** 和**禁词** ——它们的判断逻辑都在 CPU 上,必须看见真实的 token id。

### 7.4 结束符来晚了,这一步的草稿就白算

7.2 说「出结束符时草稿白算」,这件事值得单独拆一下,因为它有四个容易搞错的地方。

**一、不是在前向内部剪枝。** 没有任何 kernel 会检查某一行是不是结束符然后跳过计算。请求是在**下一步的调度阶段**消失的 —— 调度器发现它已完成,压根不把它组进下一批。

**二、省下的是它在批次里占的 k+1 个槽位,不是整个前向。** 同批次的其他请求照跑,这一轮的前向只是**窄了一点**。只有批次里最后一个请求结束时,前向才真的不发生。

**三、结束符可能落在这一步 k+1 个接受 token 的中间。** 这时它之后的那些 token 已经算出来、已经写进 KV cache,但不会返给用户 —— 属于沉没成本。

**四、异步调度下这笔代价更大。** 同步模式的时序是「出结果 → 判停 → 再调度下一步」,结束符一确认,下一步就不会带上它。**异步把这个顺序反过来了** ——先调度下一步,再处理上一步的输出。于是那条请求的下一步照跑了一次完整的验证加一轮草稿,等处理到它的输出时才发现请求早已结束,**整帧丢弃**。源码注释把这个场景写得很直白:请求可能在模型正在执行它的时候就已经结束了,流水线并行或异步调度下都会这样。

第四条的开销要看批次情况:**批次里还有别的请求时,只是宽度多了 k+1 个 token;批次里只剩它一个时,才是实打实多了一次完整的目标前向加一轮草稿。** 所以这个代价**在低并发下才明显**。

### 7.5 一个 step 到底跑了几次前向

4.7 那张表写的是「草稿主干前向 k 次」。**这个说法对,但不够准 —— 那 k 次里第一次和后面 k−1 次的形状完全不同。**

| 哪一次 | token 数 | 形状特征 |
|---|---|---|
| 目标模型验证 | `B*(k+1)` | 预填充式,每请求 query 长度 k+1 |
| 草稿第 1 次 | `B*(k+1)` 减去本轮被拒数 | **与目标同形**(所以能复用它的元数据,4.3) |
| 草稿第 2 到 k 次 | 每次 `B` | 纯 decode 形状,每请求 1 个 |

**所以一个 step 是「1 次目标宽前向 + 1 次草稿宽前向 + (k−1) 次草稿窄前向」,共 k+1 次模型调用。**

有两处容易看错:

**草稿的第一次前向不是「每请求 1 个 token」,它和目标一样宽。** 原因是它必须把本轮**所有新接受的 token** 都喂给草稿模型,否则草稿的 KV cache 会落后于目标。代码里有个很能说明问题的细节:**即使配置成一个草稿都不猜,这次前向仍然要跑,只是返回一个空张量** ——跑它不是为了出草稿,是为了把 KV 补齐。

**MTP 的「一层」并不便宜。** 那一层是一个完整的 decoder layer(自注意力加 MoE 都在里面),外面还包着两个归一化、一个投影和一个输出头。β 的主项确实是层数比(一层对目标模型的全部层),**但别忘了草稿侧一共跑了 k 次前向、其中还有一次是宽的** ——按「只算 B 个 token、只跑一次」去估会严重低估。

### 7.6 异步调度下的乐观,多乐观了一份草稿

02 章 8.2 讲过「调度完立刻推进已算数,不等 GPU 算完」的乐观推进;06 章讲过异步调度怎么把 CPU 段和 GPU 段叠起来。**推测解码在这条路上只加了一件事,但它改变了乐观的幅度。**

普通 decode 下,乐观假设是「这一步会产出 1 个 token」。**推测解码下变成了「bonus 加全部 k 个草稿都会被接受」** ——占位数一次加 `1 + k`,而不是加 1。

这个放大是有后果的:占位撑起来的那一段是**还没被真实结果确认的**,所以 KV 只能缓存到「已算数减去占位数」为止。**乐观得越多,事后要还的账也越多** ——还账分三处做,见 7.9。

代码里还有两处细节值得记:占位的回退**只在非陈旧帧上做**,注释说明了原因 —— 抢占时占位已经被清零,陈旧交付再减一次就下溢了(02 章 8.3④ 讲的过期标记,在这里是同一条线)。

另一处更有意思:**扩散模型没有自回归的 bonus token**,注释专门标了一句,它的占位只有草稿那部分。**1.4 说过「白送的位置数是个变量而不是写死的 1」,这就是它为什么必须是变量。**

### 7.7 陈旧的草稿不只是让调度拿错值

接近草稿模型能处理的最大长度时,代码会干脆**不做这一轮草稿**,并且把草稿 token **清零**。

「清零」这个动作看起来是防御性的冗余 —— 反正下一步会重新写。注释给了两条理由,第二条比第一条严重得多:

- **调度器会拿上一步的旧草稿去排下一步** ——这是显而易见的那条。
- **对某些混合架构的模型,陈旧的草稿会污染 Mamba 的递归状态**,还会连带影响接近最大长度那些序列的 logprob。

第二条的性质完全不同:**前者是排错了 token 数,后者是把一个有状态模块的内部状态弄脏了。** 递归状态不像 KV cache 那样按位置寻址、写新的就能盖掉旧的 —— 它是一路演化下来的,污染了就回不去。

这也是 4.1 那条分界的一个延伸:**有没有独立 KV cache 只是表象,真正的问题是草稿组件带不带状态、那个状态能不能被覆盖。**

### 7.8 同一条请求,在两个批次里坐不同的位子

异步调度把采样结果留在 GPU 上(7.3),下一步直接 scatter 进输入。听起来很干净,但这里藏着一个容易忽略的前提。

**GPU 上那份「上一步的采样结果」是按上一步的批次顺序排的,而下一步的批次顺序很可能已经变了** ——有请求结束被移出,有新请求加进来。第 3 行那个 token,在这一步可能属于第 5 行那条请求。

所以代码额外维护了一张映射表:**上一步哪个请求排在第几行**。下一步 scatter 时靠它把每个值放到正确的位置;被判定要丢弃的请求干脆不进这张表。

这张表的存在感在延迟修正那段代码里最明显 —— 同一条请求要用**两个不同的下标**:用「上一步的行号」去读 GPU 上那份按旧顺序排的接受数,用「这一步的行号」去写按新顺序排的 CPU 账本。

**这是 GPU 常驻状态与动态批处理相遇时的必然代价。** 06 章 10.7 讲过槽位编号与批次顺序两套编号,这里是同一个问题跨了一步:**不只是同一时刻的两套编号,还有相邻两步之间的对位。** 状态留在 GPU 上省掉了搬运,但省不掉「它是按哪一刻的顺序排的」这个账。

### 7.9 乐观一次,要修正三处

7.6 说异步调度下的乐观幅度从 1 变成了 1+k。乐观完总要还账 —— **而这笔账要在三个地方分别还,时机和目的都不同。**

| 在哪修 | 什么时候 | 修什么、为什么 |
|---|---|---|
| **GPU 上** | 及时,就在准备输入时 | 用 GPU 上记着的每请求接受数,就地修正已算 token 数与位置 —— **不修的话这一步 forward 的位置就是错的** |
| **worker 的 CPU 侧** | 延迟,攒着一起修 | 按「乐观值减真实值」回填 CPU 账本;还要连带修另外两份计数 |
| **调度器** | 输出回来时 | 按拒绝数扣已算数,同时扣占位数 |

为什么非得分三处?**因为这三处的账本服务于三件不同的事,而它们需要正确值的时刻不同。**

GPU 那份必须**立刻**正确 —— 下一次前向马上就要用它算位置。CPU 那份可以**等一等** ——它服务的是后续的输入准备,攒到要用时再统一回填,能少几次同步。调度器那份则要等输出真的回来,因为只有那时才知道实际接受了几个。

第二处那个「延迟」值得多看一眼:它把待修正项先攒进一个列表,到需要的时候才一次性回填。**这正是全章反复出现的那条纪律** ——能不立刻同步就不立刻同步,哪怕代价是多维护一份待办清单。

代码里还有两处讲稿没提的连带修正:CPU 账本那一份之外,还要修「不含草稿的 token 数」,而这个量在 CPU 和 GPU 上各有一份,得一起改。**一次乐观,牵动的账本远不止一个。**

### 7.10 收口:三条并行的通道

把 Part 6 和 Part 7 收在一张图上。

![同步调度与异步调度下推测解码一个 step 的三条通道对比:两图的 GPU 计算块宽度完全相同,同步模式下计算块之间被 CPU 工作隔出空隙、同样的时间里只跑完两步,异步模式下计算块首尾相接、同样的时间里跑完四步。](/opensource/vllm/08a-bubble-vs-pipelined.svg)

图上两半的四色计算块**逐块等宽** ——代表的是同样的 kernel、同样的计算量。差别只有一处:**同步那半的块之间被 CPU 工作隔开了,异步那半首尾相接。** 于是同样长的一段时间,上面跑完两步,下面跑完四步。

橙色那一小块是**推测解码独有的**:草稿回路(7.1)。普通 decode 的同步模式里没有它,异步之后它整条消失。

异步调度打开之后,一个 step 里其实有**三条各自往前走的通道**:

| 通道 | 在跑什么 | 靠什么保证正确 |
|---|---|---|
| **默认流(计算)** | 前向 → 采样 → 判定 → 草稿 → scatter → 下一步前向,首尾相接 | **同一条流上的 kernel 本来就是顺序执行的** ——先后顺序天然成立,不需要任何显式同步 |
| **CPU(调度与簿记)** | 与计算流完全并行 | 靠乐观占位符往前推,**不依赖 GPU 的结果**(7.6),事后三处修正(7.9) |
| **拷贝流(输出)** | 把结果搬回 CPU 给用户 | 只在结果**真要给用户时**才等那个事件,不在关键路径上 |

第一条那句「流内顺序天然成立」是整套设计的支点:**正因为计算链全在一条流上,它才不需要任何同步点;而一旦某个环节要读 CPU 的值,这条链就会被切断** ——7.2 说的「草稿排在搬回之前」、7.3 说的「草稿值全程不落 CPU」,守的都是这一条。

同步与异步的差别,最后可以压成一句:

| | 同步 | 异步 |
|---|---|---|
| GPU 空闲 | 每步都等 CPU 消化完结果 | 下一步的调度与准备和这一步的 GPU 执行重叠 |
| 采样结果 | 搬回 CPU、解析,都在关键路径上 | 留在 GPU,搬回走独立拷贝流、旁路线程解析 |
| 草稿 token | 绕 GPU → CPU → 引擎 → 调度器 → GPU 一整圈 | **整条回路消失**,GPU 上直接 scatter 进下一步 |
| 谁知道拒绝了几个 | CPU | **GPU 为主**,CPU 延迟修正 |
| 代价 | 无 | 方案受白名单限制;乐观推进带来三处修正与陈旧帧处理 |

**这张表的最后一行是这套设计的真实价格:性能是靠「先假设、后修正」换来的,而修正的复杂度全落在了状态一致性上。** 这也是为什么异步调度有一份方案白名单(4.10)—— 不是所有草稿方案都扛得住这套乐观。

## Part 8|对比与决策

前面七部分讲的是这套机制怎么造的。这一部分讲怎么用:选哪种草稿方案、参数往哪边拧、接受率不对时先查什么。

### 8.1 怎么选

2.5 给了判据,4.6 给了各方案的 β 与接受率。把两者合成一条决策路径:

1. **目标模型的 checkpoint 里自带 MTP 层吗?** 有就用 MTP —— 零额外权重、不用训练,k 受层数约束(6.4)。这是最省事的一条路,而且 3.4 说过自带 MTP 的模型已经很多了。
2. **有训练好的 DFlash 或 DSpark checkpoint 吗?** 有就用它们 —— β 明显更低(一次前向对 k 次)。**把它们排在 EAGLE 前面是因为 β,但前提比 EAGLE 更难满足** ——得正好有配对的 checkpoint。
3. **有训练好的 EAGLE / EAGLE3 头吗?** 有就用,接受率最高。
4. **模型自带 Medusa 头吗?** 有就用,但注意它只有第一代实现(3.13)。
5. **输入输出高度重复吗?**(代码补全、检索增强、长文摘要)是的话用 n-gram 或 Suffix —— **零模型成本,判据左边大于 0 就赚。**
6. **以上都没有** ——不要开推测解码。没有草稿来源时硬上一个不配对的小模型,β 高而 α 低,大概率落进 2.6 那张表的负收益行。

### 8.2 关键参数

命令行有两种写法:主入口收一个 JSON,另外三个最常用的字段有独立的简写标志。**两种可以混用,但同一个字段两边都给会直接报错** ——错误信息会点名是哪个标志和哪个键冲突。除那三项之外的字段只能走 JSON。

| 字段 | 默认 | 作用 |
|---|---|---|
| `num_speculative_tokens` | **草稿模型配置里有就取那个,否则必填** | k 值,一次猜几个 |
| `model` | 无 | 草稿模型路径;MTP 可省略(复用目标权重);`custom_class` 时是类的导入路径(6.5) |
| `method` | 无 | 方案名;不给时按草稿模型架构推断 |
| `draft_tensor_parallel_size` | 无 | 草稿模型的张量并行度 |
| `disable_padded_drafter_batch` | 关 | 关掉「草稿复用目标批次形状」这项优化,**开了它就不能用异步调度**(4.10) |
| `prompt_lookup_max` / `_min` | 无 | n-gram 匹配的最长 / 最短长度(3.7) |
| `parallel_drafting` | 关 | 并行 drafting 开关;方法是 DFlash 或 DSpark 时会被**强制打开** |
| `num_speculative_tokens_per_batch_size` | 无 | 按 batch 大小动态调 k 的分段表 |
| `suffix_decoding_max_tree_depth` | **24** | 后缀树最大深度(3.9) |
| `suffix_decoding_max_spec_factor` | **1.0** | 后缀一次最多投多少,相对匹配长度 |
| `rejection_sample_method` | `standard` | 验证方法三选一,见 2.7 |
| `draft_sample_method` | `greedy` | 草稿采样方式,见 2.7 |

第一行那个默认值容易记错:**不是无条件必填** ——草稿模型自己的配置里带了这个数就用那个,没带才要求用户给。

### 8.3 接受率不对时,先看哪个数

监控侧有一个反直觉的地方:**导出的全是计数器,接受率本身要自己算。** 草稿总数、接受总数、逐位置的接受数和草稿数,都是单调递增的计数;比率得用两个计数器相除得到。源码的文档字符串里直接给了现成的查询式,包括接受率、平均接受长度,以及**逐位置的接受率向量**。

不接监控系统也能看 —— 日志侧有一个组件会周期性打印同样这几个量。

排查按这个顺序(经验做法,不是源码里的判据):

1. **先看逐位置接受率向量。** 它回答的是「第几个草稿 token 开始崩」。如果在第 j 位急剧衰减,**把 k 降到 j 附近** ——后面那些草稿是纯浪费,既花了草稿前向的时间,又按 k+1 多预留了块(5.2)。
2. **平均接受长度是收益的直接代理。** 它约等于每次目标前向产出的 token 数,也就是 2.3 那个期望产出。**小于 1.5 时基本没收益** ——对照 2.6 那张表,这个量级已经接近负收益区。
3. **接受率整体偏低,通常不是 k 的问题,而是草稿与目标的分布不匹配。** 权重没配对、分词器不一致、温度设得不同,都会压低 α。这时候调 k 没用,该换草稿来源。

第一条在 MTP 下有个额外约束:**新的 k 还得能被 MTP 层数整除**(6.4),不能随便取。

### 8.4 常见误区

| 误区 | 真相 |
|---|---|
| 推测解码总是更快 | 不。判据是 `α + α² + ... + α^k > β`(2.5);接受率太低时草稿白跑,而目标前向从算 1 个 token 变成算 k+1 个,净结果比朴素解码还慢 |
| k 越大越好 | 不。自回归草稿的开销随 k 线性增长,而尾部草稿的采纳概率是 α 的 k 次方、迅速衰减 —— **收益收敛而成本线性,所以存在最优 k**。何况块还要按 k+1 预留(5.2) |
| 推测解码会损失质量 | 不。默认配置下拒绝采样保证分布完全一致(2.1)。但这是**默认值的性质,不是推测解码的性质** ——另两种验证方法都不给这个保证(2.7) |
| n-gram 太简单,没什么用 | 不。代码补全、多轮对话这类重复度高的场景,它的接受率能到五成,而且**零额外模型成本**(4.6) |
| 草稿模型越大越准,所以越好 | 不。大草稿把 β 推高,而 β 在判据的右边。2.6 表里第 5、6 行就是反例:α 相同,草稿贵一倍就从「勉强能用」翻到负收益 |
| 开了推测解码,采样参数会失效 | 不。只有 `min_p` 与 `logit_bias` 失效,白名单、禁词、三种 penalty、温度、`top_k` / `top_p` 都照常生效(07 章 5.6) |
| 用推测解码就是在跑第一代运行器 | 不。默认是第二代;是 n-gram / Medusa / Suffix / 独立草稿模型这几种**方案**把第二代否决掉了(3.13),不是第一代是默认 |
| 配 DSpark 却用第一代,会静默走 EAGLE 的类 | 不。那条路径不可达,配置校验阶段就抛错了(6.3) |
| 看到 `method="mtp"` 就知道跑的是标准 MTP 类 | 不。还有一层读草稿配置的二次分派,可能静默落到三个专用类之一(6.2) |
| 草稿和目标各有一套块表 | 不。**同一份块映射,只是写进不同的层**(4.2) |
| 被拒绝的草稿 K/V 要擦掉 | 不。不擦,靠回退计数器让它「逻辑上不存在」,下一步自然覆盖(5.2) |
| 接受率可以直接从监控读出来 | 不。导出的是计数器,比率要自己相除算(8.3) |
