# vLLM 06|Worker 与 ModelRunner

调度器每 step 交出一份决策清单,GPU 要的却是形状固定、地址固定、不含任何 CPU 分支的张量。这一章讲执行层怎么跨过这道落差,以及为什么这件事的瓶颈在 CPU 而不在 GPU。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与方法,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 decode 的一步里,CPU 比 GPU 还忙

先看一个反直觉的数字。Llama-3-70B、batch=32、纯 decode,一次前向:

```text
GPU 侧:  ~2000 个 kernel 依次执行        ≈ 15 ms
CPU 侧:  ~2000 次 kernel launch × 7 µs   ≈ 14 ms
                                    ─────────────
         GPU 有将近一半时间在等 CPU 派活
```

这组数字是量级估算,不是本仓库实测,它对 CPU 主频、driver 版本和算子融合程度都很敏感。但量级本身说明了问题:**decode 阶段每个 kernel 都很小、跑得很快,反倒是「把 kernel 交给 GPU」这个动作本身成了关键路径。**

为什么是 2000 个。一层 Transformer 的注意力加 MLP 大约十几个 kernel(QKV 投影、RoPE、点积、softmax、AV、输出投影、残差加、RMSNorm、SwiGLU 拆两半再相乘、下投影……),80 层乘起来就是两千量级。prefill 时每个 kernel 要处理几千个 token,GPU 那一侧的耗时远大于下发耗时,这个比例不成问题;**decode 时每个请求只算 1 个 token,kernel 本身只要几微秒到几十微秒,下发的固定开销就压不住了。**

单次下发的 CPU 侧要走完整链路:打包 kernel 参数、调用 driver 接口(有系统调用开销)、把参数写进命令缓冲区并入队到 stream,GPU 才真正开始执行。5 到 10 微秒听起来微不足道,乘以两千就是毫秒级。

执行层这一章要回答的,就是这条痛点派生出的三个问题,外加它们共同欠下的一笔账:

| 痛点 | 执行层的应对 | 本章位置 |
|---|---|---|
| 下发两千次太慢 | 录成一张图,一次重放 | 1.7 起 |
| 每 step 重建请求状态太慢 | 缓冲区常驻 GPU,只改增量 | 1.5、1.6 |
| CPU 到 GPU 的搬运会插入同步点 | 锁页内存加异步拷贝,全程不等 | 1.38 起 |
| **前三样都要求「启动时就把一切定死」** | 空转几次把动态行为触发完,再量出显存预算 | 1.24 起 |

最后一行是前三行的代价:图要求形状与地址固定、缓冲区要求按上限预分配、流水线要求不能中途申请显存——**它们把复杂度全都推给了启动阶段**。所以这一章有一大段在讲启动,那不是跑题。

### 1.2 执行层站在哪一段

引擎的一次 step,从调度决策走到模型代码,中间隔着四层:

```text
引擎主循环 EngineCore.step()
  │  调度器交出本 step 的决策清单 SchedulerOutput
  ▼
执行器 ModelExecutor          ── 决定这份清单发给哪些进程
  ▼
工作进程 Worker               ── 每张 GPU 一个进程,持有 KV cache
  ▼
模型运行器 ModelRunner        ── 把清单翻译成 GPU 张量,调前向,采样
  ▼
模型代码(llama.py / qwen3.py …)
```

上面两层做的是**分发**,01 章讲过进程拓扑;下面两层做的是**翻译**,是这一章的内容。

这条链路上有一个容易被忽略的事实:**调度器交出来的清单是纯 CPU 数据** ——请求 id 是字符串,块号是 Python 整数列表,每 step 的请求集合还不一样。而模型前向要的是连续的 GPU 张量。这中间没有任何框架能代劳,只能逐字段手工翻译,而且每 step 都要翻一遍。1.5 之后的几节讲的都是怎么让这次翻译尽量不花钱。

### 1.3 五个角色,各持有什么

执行层内部不是一个大类包办,而是五个角色分工。理解它们的**持有关系**比理解调用顺序更有用,因为持有关系决定了什么东西能跨 step 复用:

| 角色 | 代码名 | 持有什么 | 生命周期 |
|---|---|---|---|
| 工作进程 | `Worker` | 模型运行器、KV cache 张量、分布式通信组 | 进程级 |
| 模型运行器 | `GPUModelRunner` | 模型实例、输入缓冲区、块表、注意力元数据构造器、采样器、图管理器 | 进程级 |
| 输入缓冲区 | `InputBuffers` | 预分配的固定 GPU 张量容器 | 进程级,**地址不变** |
| 本步输入 | `InputBatch` | 缓冲区张量切到本 batch 尺寸后的视图 | **单 step** |
| 块表 | `BlockTables` | 所有请求的块映射,加一套稀疏更新机制 | 进程级 |

分工的关键在最后两行的对比:**只有一个角色是每 step 新建的,而它新建的只是视图,不是数据。** 这是整个执行层性能设计的地基,1.5 展开。

张数与进程数的对应关系随并行方式而变:张量并行下 N 张 GPU 就是 N 个工作进程,彼此用 NCCL 通信;流水线并行下每个 stage 一组;数据并行下每个副本一组,各自持有一份独立的模型权重。

### 1.4 两套模型运行器,以及默认走哪一套

代码里的模型运行器有**两套独立实现**,外加一个只跑多模态编码器的变体:

| 实现 | 请求状态放在哪 | 输入准备靠什么 |
|---|---|---|
| **V2**(本章主角) | 常驻 GPU | 一批 Triton kernel,CPU 只负责下发 |
| V1 | CPU 侧维护 numpy 镜像 | 逐 step 整体搬到 GPU |
| 多模态编码器变体 | 同 V2 | 同 V2,但只跑编码器、不做自回归解码 |

两套的差别正是 1.1 那条痛点的两种答案:V1 每 step 在 CPU 上把状态算好再整体传过去,V2 把状态留在 GPU 上、每 step 只传增量并用 kernel 就地改。本章之后凡是不特别说明的,都指 V2。

**选哪一套不是用户直接决定的,而是一串否决。** 这里有一个很容易记反的点:**默认是 V2**,判定逻辑是一条「谁能把它否掉」的链,而不是一份「谁被允许用」的名单:

| 顺序 | 判定 | 命中的后果 |
|---|---|---|
| 1 | 开了水印 | **强制 V2**,而且日志明说它覆盖了用户设的关闭开关 |
| 2 | 环境变量显式指定 | 照办 |
| 3 | ROCm 平台且模型架构在黑名单里 | 退回 V1(黑名单目前三个架构) |
| 4 | 环境里没有 Triton | 退回 V1 |
| 5 | 本次配置命中了 V2 尚不支持的特性 | 退回 V1 |
| — | 以上都没命中 | **用 V2** |

第 1 条值得单独记:**它是唯一一条能压过用户显式设置的条件。** 其余四条都是「否掉」,只有水印是「顶上去」。

反方向还有一份对称的清单:**V1 做不到、因而不允许退回去的特性**——预填充上下文并行、`dspark` 投机采样、自适应草稿验证、混合滑窗与全注意力的 DFlash 草稿、DFlash2 草稿、扩散模型、batch 分片采样。命中这些而又要求用 V1 时,配置校验阶段直接抛错,不是悄悄降级。

> 两份清单方向相反,合起来才是完整语义:一份决定「默认用哪套」,另一份决定「不许用哪套」。

### 1.5 缓冲区一次性分配,视图每步重切

如果每 step 都按当前 batch 的实际大小新建一批 GPU 张量,会踩两个坑:显存分配本身有开销,而且**地址每步都在变,CUDA Graph 就无从谈起**(1.8 会看到图记的是地址)。

vLLM 的做法是把这两件事拆开:

```text
进程启动时  ── 输入缓冲区:按上限一次性分配,之后地址永不改变
              input_ids   [max_num_tokens]
              positions   [max_num_tokens]
              is_padding  [max_num_tokens]
              query_start_loc [max_num_reqs + 1]
              seq_lens        [max_num_reqs]
              dcp_local_seq_lens [max_num_reqs]

每个 step   ── 本步输入:把上面这些张量切到本 batch 的实际尺寸
              input_ids[:1526]  ← 只是视图,底下还是同一块显存
              加上本步才有的记账字段(请求 id、索引映射、各种计数)
```

六个字段按两种上限分配:和 token 数同长的按单步最大 token 数,和请求数同长的按最大请求数,查询起止位置因为要多一个哨兵而加一。

**每 step 只做原地写入,不重新分配。** 「本步输入」是个每 step 新建的数据类,但它新建的只是一组切片引用和一些 CPU 侧计数,底下的显存自始至终是同一块。这一条同时满足了两个需求:上层代码拿到的是尺寸正好的张量,底层地址却是固定的。

### 1.6 块表不重传,只补增量

块表(每个请求的逻辑块到物理块的映射,03 章 1.10 讲过它的结构)是执行层要传给 GPU 的最大一块数据。一个请求几千 token 就有几百个块号,几十个请求就是上万个整数。**每 step 整体重传是纯浪费——decode 时绝大多数请求的块表一个数都没变,顶多在末尾多一个块。**

块表这一层因此做了两级优化:

- **暂存写入**:CPU 侧把本步的改动攒成一份增量,再用一个 Triton kernel 一次性 apply 到 GPU 上的常驻块表。改了几个就传几个,不动的部分连碰都不碰。
- **收集重排**:前向真正要用的块表必须按本步的调度顺序排列,而常驻块表是按请求槽位排的。这一步同样由 Triton kernel 完成,顺手把 padding 出来的行清零。

两步都在 GPU 上做,CPU 只负责给出「哪些行要改」和「按什么顺序取」。这就是 1.4 说的「输入准备靠一批 Triton kernel」的具体形态。

### 1.7 CUDA Graph 要解决的是下发,不是计算

回到 1.1 的两千次下发。CUDA Graph 的想法很直接:**既然每 step 下发的 kernel 序列几乎一模一样,那就把它录一次,以后重放。**

录下来的是一张图:节点是 kernel,边是它们的依赖关系。重放时把整张图交给 driver 一次,CPU 侧的两千次参数打包与入队全部省掉,只剩一次图执行调用——开销从毫秒级掉到几十微秒。

要说清楚它省的是什么:**GPU 侧的计算一点没变,两千个 kernel 该怎么跑还是怎么跑。** 省掉的纯粹是 CPU 侧把它们交出去的那部分工作。所以收益完全取决于「GPU 计算时间 / CPU 下发时间」这个比值:

| 场景 | 比值 | 图的收益 |
|---|---|---|
| decode,batch 小 | 接近 1 | **最大**,batch 越小越明显 |
| decode,batch 大 | 比值变大 | 摊薄 |
| prefill | 远大于 1 | 几乎没有 |

这解释了 CUDA Graph 在 vLLM 里的定位:**它是为 decode 准备的。** prefill 一步就算几千个 token,GPU 那边本来就忙得很,下发开销藏在计算里看不见;何况 prefill 的 token 数随请求剧烈变化,要覆盖就得开很多个桶,每个桶都占显存(1.12)。

vLLM V1 把它当默认必开的特性。关掉它要用 `--enforce-eager`,而这个开关做的事比名字说的多:它同时把图模式置空、把捕获尺寸上限归零、把桶列表清空,并且连 `torch.compile` 一起关掉。

### 1.8 录下来的东西不许变:五条硬约束

「录一段固定的 kernel 序列,之后原样重放」这个定义本身就框死了能被录的代码:

| 约束 | 为什么 | 违反的后果 |
|---|---|---|
| 输入形状必须固定 | 图里每个 kernel 的线程网格、块大小、共享内存量在录制时就硬编码了 | 结果不对,或者直接报错 |
| 输入地址必须固定 | 图记的是设备指针,不是内容 | 换个张量就读到错误的内存 |
| kernel 序列必须固定 | 图只录 CUDA 侧的操作。Python 层的 `if` 在录制时走了哪个分支,以后每次重放都是那个分支 | 数据相关的分支行为错乱 |
| 不能有非 CUDA 侧操作 | 图只记 stream 上的操作 | 把张量取回 CPU、主机侧内存分配都不能在图里 |
| 不能触发显存分配 | 分配是主机侧行为 | 录制失败,或者重放时行为未定义 |

第三条是最根本的:**图里没有控制流。** 这也是为什么 attention 在混合 batch 下必须留在图外(02 章 2.7.7 讲过这个结论)——它的分段信息随每步的请求组成变化,不是一个能被固定下来的形状。

### 1.9 vLLM 怎么逐条满足这五条

五条约束对应五个设计,前面几节铺的东西在这里收口:

| 约束 | vLLM 的做法 |
|---|---|
| 形状固定 | 把实际 token 数向上对齐到预设的桶,多出来的位置填 dummy(1.12) |
| 地址固定 | 就是 1.5 的输入缓冲区:录制时绑定这组固定张量,之后每步准备输入时**就地写进同一批地址**(3.9 会看到,重放前并没有一次额外的搬运) |
| 序列固定 | 按 decode / 混合两种形态分别录不同的图,不在图内做形态判断 |
| 无非 CUDA 操作 | 所有需要 CPU 参与的判断都提到图外,在准备输入时做完 |
| 无显存分配 | 所有 workspace 提前分配好——包括注意力后端的中间缓冲区,在预热阶段就固定下来 |

最后一条和 05 章接得上:注意力后端的元数据构造器会在预热时完成惰性初始化、Triton kernel 会在预热时完成自动调优。**这两件事都是动态行为,绝不能被录进图里**,所以录制之前必须先跑一遍不录制的预热前向,让它们先发生完。

### 1.10 三个具体档,两个复合档

档位枚举有**五个**成员,不是三个:

| 成员 | 含义 |
|---|---|
| `NONE` | 不用图,纯 eager |
| `PIECEWISE` | 只录两次 attention 之间的非 attention 段,attention 留在图外 eager 执行 |
| `FULL` | 整个前向连 attention 一起录 |
| `FULL_DECODE_ONLY` | 复合档:decode 走 `FULL`,混合 batch 走 `NONE` |
| `FULL_AND_PIECEWISE` | 复合档:decode 走 `FULL`,混合 batch 走 `PIECEWISE` |

**只有前三个是运行时真正派发的档**,枚举自己的说明里写明了这一点。后两个是**配置档**,它们各自携带一对取值,运行时按本步 batch 的形态拆开取用:是纯 decode 就取前一个,是混合 batch 就取后一个。

02 章 2.7.7 说的「默认是完整图与分段图并存」,指的就是 `FULL_AND_PIECEWISE` 这一档。三种运行时路径的适用场景和取舍那里已经讲过,这里不重复;要补的只有一句:**「并存」不是运行时在两张图之间选,而是配置期就声明了两种形态各用哪一档。**

> 提个醒免得混:02 章里的「V1」指的是 **vLLM 引擎本身的代号**(整套引擎都在 `v1` 这个命名空间下),而本章 1.4 起说的「V1 运行器 / V2 运行器」是**这套引擎内部两套并存的模型运行器实现**。两个 V1 不是一回事,所以后文凡是指运行器的地方都会带上「运行器」三个字。

### 1.11 档位不是设什么就是什么

配置期有一串自动调整,把用户给的档位改成实际可行的那一档:

| 触发条件 | 调整结果 |
|---|---|
| pooling 模型 | 降到 `PIECEWISE`(不支持整图) |
| encoder-decoder 模型 | 降到 `FULL_DECODE_ONLY` |
| KV connector 声明自己需要分段 | 降到 `PIECEWISE`(它有逐层异步操作,录不进图) |
| 序列并行、或开了注意力与量化融合 | 反而**升**到 `FULL`(这两种情况下分段图不可用) |
| DeepEP 高吞吐后端加数据并行 | 直接降到 `NONE` |
| 注意力后端的图支持度不够 | 按支持度当场下调,降不到可用档就抛错 |

最后一条把这一章和 05 章接上了。05 章讲过**一个后端能不能被整图捕获,是它的构造器上的一个类变量**——那是能力声明;这里是那条声明的下游后果:**声明不够就整批降档,而且是在启动时降,不是运行时才发现。** 降档的日志会写清楚是哪个后端、支持度是什么、改成了哪一档。

注意这里有升有降。直觉上「自动调整」总是往保守方向走,但序列并行那两条是反的:分段图要求能在 attention 处切开前向,而那两种配置恰好不允许切,于是只能整个录成一张。

### 1.12 分桶:按 token 数,不是按请求数

形状必须固定,而每步的 token 数每步都不同。vLLM 的办法是**预设一组捕获尺寸,每个尺寸录一张图,运行时把实际数字向上对齐到最近的那个**,多出来的位置填 dummy token:

```text
桶列表:  [1, 2, 4, 8, 16, 24, 32, 40, 48, ..., 120, 128]

实际 3   → 对齐到桶 4,   填 1 个 dummy
实际 10  → 对齐到桶 16,  填 6 个
实际 20  → 对齐到桶 24,  填 4 个
实际 130 → 超过最大桶 → 没有图可用 → 退回 eager
```

**桶的键是 token 总数,不是请求个数。** 这个口径必须说清,因为两者在最常见的场景下恰好相等:纯 decode 且没开投机采样时,每个请求各出 1 个 token,token 数就等于请求数——于是口头上常被混称作「batch size 桶」。但只要有分块预填充,或者投机采样让一个请求带上好几个草稿 token,token 数就远大于请求数,**这时只有 token 数这个口径是对的**。

02 章 2.7.7 说过「同一个 token 总数下,不管 batch 里有几个请求都命中同一张图」——那句话的出处就在这里。

填 dummy 会浪费一点算力,但换来的是重放时零下发开销。只要 token 数不是特别小,这笔交易都划算。

### 1.13 区间映射:不在桶上的 token 数也能用图

上一节的例子里,实际 token 数 3 用了 size-4 的图。这件事需要解释一下,因为它不是运行时现算出来的。

一个容易产生的误解是:只有 `[1, 2, 4, 8, ...]` 这些数字才有图,其他数字都得退回 eager。实际上**建表时就把区间铺平了**:从「上一个桶加一」到「当前桶」之间的每一个整数,都被登记成指向当前桶的那张图。所以查表是 O(1) 的直接命中,没有「找最近的桶」这一步。

```text
建表:
  桶 4  → 键 3、4       都指向 size-4 的图
  桶 8  → 键 5、6、7、8  都指向 size-8 的图
  桶 16 → 键 9 … 16     都指向 size-16 的图

查表:
  token 数 = 3 → 直接命中 size-4 的图
```

还有一个细节:**同一个键下挂的是一个列表,不是单张图。** 原因有两类——同一个 token 数下可能同时存在整图和分段图两个版本;动态投机采样还会产出好几张 token 数相同但草稿长度不同的图。源码注释点明了后一种情况,并说明分组是为了让它们共享同一段候选区间。

### 1.14 派发只查一次表

有了区间映射,运行时的派发就很简单了:

```text
dispatch(本步的请求数、token 数、是否等长、LoRA 数、最大查询长度)
  │
  ├─ 用 (token 数, 有效 LoRA 数) 查候选表
  │     没这个键,或者图还没录完 → 退回 eager
  │
  ├─ 命中:拿到一个有序的候选列表
  │     按顺序逐个问「你能吃下这一批吗」
  │     第一个说能的就用它
  │
  └─ 一个都不行 → 退回 eager
```

三个特点:

- 只有**一次**查表。整图和分段图的候选挂在同一个键下,建表时按「先整图后分段」的顺序追加,所以列表天然是优先级有序的。
- **「放宽」发生在建表时,不是运行时。** 分段图的描述符建出来时,请求数那一栏本来就是空的——源码注释说得很直白:分段图重放时对请求数没有限制、不需要请求 padding,所以留空。
- 兼容性判断因此变成了几条「空就放行」:描述符的请求数为空就不比请求数,等长要求为空就不比等长,其余几项做大于等于的比较。

所以 **「先试整图、不行退分段图、再不行 eager」这个降级效果,是候选列表的顺序造出来的,不是运行时一轮轮试出来的** 。

> 02 章 2.7.7 讲过同一件事,但描述的是**两轮查表加一次运行时放宽**——那是另一套派发器,归 V1 运行器用(1.4 的两套实现)。两套目标一致、手法不同:V1 在运行时放宽描述符再查第二遍,V2 把放宽和优先级都提前到建表期。**默认走的是 V2 这套。**

### 1.15 录图的顺序:先大后小,把显存池一次撑到位

所有图共享**同一个显存池**,进程级单例。这个池是独立的分配器,录制期间图内部的所有临时分配——中间激活、各种 workspace、注意力后端的中间缓冲区——全部从它这里切,不走 PyTorch 默认的缓存分配器。

多张图能共用一块物理显存,靠的是一个前提:**vLLM 在单 stream 上顺序重放,任意时刻只有一张图在跑。** 所以 size-4 那张图的中间激活区域,等它放完就可以被 size-8 那张接着用。同一块显存,不同时间装不同图的中间结果。

于是池的最终大小约等于**所有图里峰值最大的那一张的峰值**,而不是所有图峰值之和。

这一条直接决定了录制顺序必须是**两层先大后小**:

```text
第一层  档位之间:先录分段图,再录整图
        ── 分段图的中间激活更大,先把池撑到峰值

第二层  档位内部:按 token 数从大到小(128 → 120 → … → 1)
        ── 同理,最大的桶先录

效果:   第一张图(分段图的最大桶)就把池撑满
        之后每一张都直接落进已分配的 buffer,池不再扩张
```

反过来从小到大录会怎样:池要经历上百次逐步扩张,碎片多、效率低。源码注释把这个意图写得很清楚,说的就是分段图激活更大、所以整图的激活能装进已经分配好的 buffer 里。

### 1.16 只有整图在这一步真的建图

录制那段循环里有一处很容易读错的地方:**循环体遍历了两种档位,但两种分段图都不在这里创建图对象。**

分段图分两类,走的分支不同,但结果一样:

| 分段图类型 | 在录制循环里做什么 | 谁真正录 |
|---|---|---|
| 不可打断 | 调一次前向,标记为分段模式 | 编译层的图包装器 |
| 可打断 | 多做一次「换一份干净的注意力状态」的准备,再调一次前向,然后直接跳过建图 | 同上 |

真正创建图对象、走进图捕获上下文、把结果登记进图表的,**只有整图这一条路**。分段图的录制下沉到了编译层——前向被 `torch.compile` 按 attention 切成若干段,每段由编译层的包装器各自捕获,而且用的是同一个全局显存池。

可打断那一类为什么要多做一次准备:预热那一遍可能已经改动过注意力元数据,直接拿去录会把预热留下的状态一起录进去,所以要重新生成一份干净的。这与 1.9 说的「预热必须先跑、但预热本身不能被录进去」是同一件事的两面。

还有一件录制循环里做了、但机制层面看不出来的事:**录制前后都要和显存下沉的拷贝流做一次同步。** 不同步的话,重放可能覆盖掉还在传输中的固定缓冲区——注释把这个后果写明了。

### 1.17 代价:显存不贵,启动时间贵

图的代价一共六项,其中显存那三项**只有一项随桶数增长**:

| 代价 | 随桶数增长 | 量级 | 怎么缓解 |
|---|---|---|---|
| 图元数据(kernel 拓扑、参数布局、stream 同步信息) | **是**,每张图一份 | 小,每张几 MB | 桶数适中即可 |
| 显存池里的中间激活 | 否,所有桶共享一个池 | 大,约等于最大那张图的峰值 | 用显存占比参数留出空间 |
| 固定缓冲区 | 否,按 token 上限与并发上限分配一次,所有桶共用 | 中 | 无——它本来就只有一份 |
| **启动变慢** | **是** | 每桶一到三秒,20 个桶就是几十秒 | 砍桶列表 |
| 对形状敏感 | — | 实际 token 数超过最大桶就退回 eager | 让最大桶对齐单步 token 预算 |
| 不好调试 | — | 崩在图里面,没有 Python 调用栈 | 用 `--enforce-eager` 关掉再复现 |

算一笔显存账:20 个桶的额外成本是 20 乘以几 MB,几十到一两百 MB 量级。对照 70B 模型的权重,这点占用几乎可以忽略。**真正的代价是启动时间。** 这两个数字都是量级参考。

所以调桶数的取舍不是「显存换性能」,而是「**启动时间**换性能」。想少等一点就砍桶列表,代价是更多的实际 token 数落不进桶、退回 eager。

最后一行值得单独记:**图会把出错现场吃掉。** 遇到看不懂的崩溃,第一步就是关掉图再跑一遍,拿到真正的栈。

### 1.18 这笔显存账是怎么量出来的:实测两张,再外推

上一节那些数字不是拍脑袋估的,也不是逐张图累加出来的——真要累加就得把上百张图全录一遍,而「知道要花多少显存」这件事本身发生在**决定 KV cache 能开多大之前**,那时候还不该把图录完。

vLLM 的办法是抽样加外推,靠图管理器上一对**只在测量时才启用**的字段:

| 字段 | 不为空时做什么 |
|---|---|
| 捕获条数上限 | 只录最大的那几张整图,其余跳过。因为待录列表已按 token 数降序,取前几个就是取最大的几个 |
| 显存样本列表 | 每录一张整图,前后各做一次同步加显存查询,把两次的差值记进列表 |

差值就是「这张图实际吃了多少显存」的真实增量。拿到几个样本之后,按这个单价外推出全部桶的总成本。

抽样条数是写死的常量:**只实测最大的两张。** 取最大的两张有道理——它们是上界,小图不会比它们更贵。

所以文档里那些显存数字,如果要落到具体部署上,用的是这条路径的输出,不是手算。

### 1.19 分段图为什么要借道编译器

分段图的定义很朴素:在每个注意力算子处把前向切开,非注意力的段录成图,注意力留在外面 eager 跑。

**这件事本身并不需要编译器。** 理论上完全可以手写:把前向拆成「前半段 → 注意力 → 后半段 → ……」,每段各自调 PyTorch 原生的图捕获接口。TensorRT-LLM 走的就是手写路线,连 PyTorch 都不依赖。(这一条是讲稿的定位参考,TensorRT-LLM 不在本仓库,无法用源码校验。)

vLLM 选择依赖 `torch.compile`,理由是**模型太多**:

- 每个模型的前向写法都不一样,手写切分要逐模型适配一遍。
- Dynamo 能把任意 PyTorch 模型抓成一张计算图,切分逻辑**写一次通吃所有模型**。
- Inductor 在切分之外还顺带做算子融合与 kernel 生成。

代价也很明确,后面 1.23 的对比会看到:整图那一档不依赖编译器,分段图依赖。编译器出问题,分段图就跟着出问题。

切分具体在哪一层做,有两条路:

| 路径 | 切分发生在 |
|---|---|
| **计算图层切分**(默认) | Dynamo 抓图之后,vLLM 自己遍历节点切 |
| 编译器内部切分 | 把注意力算子注册成 Inductor 的分区规则,让它在代码生成阶段切 |

两条路的**切点概念完全相同**,都是注意力类算子;区别只在「vLLM 自己切,还是让编译器在更底层切」。下面按默认那条讲。

### 1.20 切点:十六个注意力类算子

切点写死在一份类级清单里,当前是**十六条**:

| 分组 | 成员 |
|---|---|
| 标准与 MLA | 统一注意力、统一 MLA 注意力 |
| 状态空间类 | Mamba2、Mamba1、短卷积 |
| Qwen4Exp 的 AMD 后端 | 短卷积变体、QSA 变体 |
| 线性注意力类 | 线性注意力、Qwen 门控 DeltaNet(另有融合 norm 版与 XPU 版)、OLMo 混合门控 DeltaNet |
| 稀疏索引器 | DSA 的 Lightning Indexer(另有 ROCm/AITER 版) |
| 模型专用 | DeepSeek V4 注意力、腾讯 hpc-ops 的 RoPE-norm |

**这份清单和 05 章讲的后端家族是一一对应的。** 判据只有一条:凡是自成一档、形状不只取决于 token 总数的算子,就必须成为切点——否则录进图里会因为变长而失效。

反过来也说明了为什么非注意力算子可以录:QKV 投影、RMSNorm、RoPE、SwiGLU、MLP、残差、输出投影、all-reduce,这些算子的形状**只取决于 token 总数**。一旦按桶 padding 到固定 token 数,形状就定死了。注意力不行——它的形状取决于每个请求的序列长度、块表、累计长度,这些每步都在变,而且 kernel 内部还可能有数据相关的分支。

用户没有显式指定切点时,分段图模式就默认取这份清单。

> 这里有个容易想反的地方:**整图那一档并不是「不切图」。** 源码注释写明,即便用整图,fx 层面仍然保持分段结构,只是把整图捕获放到 fx 图**外面**去做。这么安排是为了减少「运行时 batch size 没被捕获」时的 CPU 开销。所以 1.16 说的「只有整图在这一步真的建图」,说的是建 `CUDAGraph` 对象这一步,不是说 fx 图没被切。

### 1.21 切图与包装:只有非注意力段被包起来

切分是一次线性遍历:逐个看计算图的节点,判断它的 target 在不在切点清单里。命中就单独切成一段,**连续的注意力算子合并到同一段**,不重复切。

以一层为例,切完是这样:

```text
原始前向计算图
  │  在每个注意力算子处切开
  ▼
段 0 : [RMSNorm → QKV 投影 → RoPE]            ← 非注意力,可录
段 1 : [统一注意力]                            ← 注意力,eager
段 2 : [输出投影 → 残差 → RMSNorm → gate/up
        → SwiGLU → down → 残差]               ← 非注意力,可录
段 3 : [下一层的注意力]                        ← eager
段 4 : [下一层的非注意力段]                    ← 可录
...
```

注意段 2:**它跨过了层边界**——本层注意力之后的部分和下一层注意力之前的部分是连着的,中间没有切点,所以合成一段。这解释了段数的量级:不是每层两段,而是**大约每层一段**。

切完之后每段各自交给编译后端,用 Inductor 按不同的形状区间各编一份。**编译完只有非注意力段会被套上图包装器**,注意力段原样留着 eager 跑。区分靠的是切分结果上的一个布尔标记,包装那一步只给没被标记的段套。

### 1.22 每段图什么时候录、什么时候放

包装器的逻辑是**懒录**——不在启动时统一录,而是跑到了才录:

```text
包装器被调用
  │
  ├─ 运行模式是 NONE,或者和自己的模式对不上
  │     → 直接跑原函数,既不录也不放
  │
  ├─ 第一次见到这个批次描述符
  │     → 现场录一张小图,存进自己的表
  │
  └─ 之后同一个描述符
        → 直接重放
```

第一条分支的理由不止是「跳过」:注释写明,它是为了让**嵌套多个不同运行模式的包装器时能正确派发**——每层包装器只认自己那一档,不是自己的就原样往下传。

这里有个很实际的工程细节。一次前向要录几十上百段,而 PyTorch 每次图捕获都会触发一轮垃圾回收与清空分配器缓存;段段都来一遍会**极慢**,而且逐段清空缓存还会把共享的显存池反复打散。vLLM 的做法是**只让第一段做这两件事,其余段全部禁掉**——用打补丁的方式把垃圾回收和清空缓存临时替换成空函数。

### 1.23 运行时怎么把两种段缝起来

一次前向执行时,切分后的模块按顺序依次被调用,前向上下文里带着本步的运行模式和批次描述符:

```text
前向(描述符 = BD)
  段 0  包装过 → 重放 图[BD]          零下发
  段 1  没包装 → eager 跑注意力        正常下发,处理变长
  段 2  包装过 → 重放 图[BD]          零下发
  段 3  没包装 → eager
  ...
```

**重放段和 eager 段交替执行,缝成一次完整的前向。** 非注意力算子占了 kernel 数量的绝大头,它们全部吃到了零下发的收益;只有注意力这一小段保留 eager 的灵活性。这就是「分段」这个名字的由来。

和整图那一档比,真正的差别只有两条(其余取舍 1.10 已经讲过):**整图对注意力后端有硬要求**——后端必须声明自己能被整图捕获,而分段图对后端没有任何要求,因为注意力压根不在图里;**整图不依赖编译器,分段图依赖**。

### 1.24 假跑:启动时必须先空转几次

图这条线到这里讲完了,但它欠着一笔账:1.9 说过**动态行为绝不能被录进图**,1.17 又说**图的显存要提前算进预算**。这两件事都只能在启动阶段还清——这就是 1.1 那张表最后一行说的代价。

模型加载完、开始收请求之前,vLLM 要先用假数据把整条前向路径真跑几次——随机 token id、假的缓存指针,调用一次完整的前向,结果直接丢掉。

跳过会出三类问题:首个请求超时、KV cache 容量估错、图捕获失败。

它被三种场景调用:

| 场景 | 为什么要跑 |
|---|---|
| **显存探测** | 算出峰值占用,决定 KV cache 能开多大(1.25) |
| **图捕获前的 pass** | 让注意力后端完成惰性初始化、让 Triton 完成自动调优(1.9 说过,这些动态行为不能被录进图) |
| 睡眠唤醒后 | 缓冲区重建之后再跑一次热身 |

有一类预热**不走这条路**:JIT 编译与 kernel 自动调优的预热,走的是另一个入口——它手工搭出真实的调度输出结构,再经 worker 的正常执行入口跑。理由很实在:**这样覆盖到的 kernel 路径才和线上一致。** 假跑走的是内部快捷通道,有些线上会走到的分支它碰不到。

换个角度看,这一整套空转要办成**四件正事**,接下来四节各讲一件:

| | 正事 | 在哪节 |
|---|---|---|
| 一 | 量出峰值显存,定下 KV cache 能开多大 | 1.25–1.29 |
| 二 | 把 Triton 的首次编译提前 | 1.30 |
| 三 | 在干净环境里做完自动调优 | 1.31 |
| 四 | 把一切「第一次才发生」的惰性初始化触发掉 | 1.32 |

第一件最重,占了五节——因为它不只是「跑一次」,还牵出探测跑什么形状、为什么跳过注意力、三个参数怎么分工、账本怎么记。

### 1.25 显存探测:唯一算不出来、只能实测的那一项

KV cache 能开多大,是一道减法:拿到允许用的显存,减掉不是 KV cache 的部分,剩下的除以每块的大小。

难点只在一项:**峰值激活占用没法静态算出来。** 它取决于批大小、序列长度、注意力后端、并行度、量化方式;而且注意力后端的 workspace、all-reduce 缓冲、SwiGLU 中间量、logits 缓冲这些东西都是运行时才分配的。只有真跑一次前向、对前后的显存快照做差,才有真数。

真实流程分三段:

```text
段 1  用户显式指定了 KV cache 大小
        → 跳过整个探测,但仍要跑一次前向
          (还得靠它把模型按 token 预算编译出来)
        → 日志明说:这条路不尊重显存占比参数

段 2  正常路径
        → 在显存记账上下文里跑一次假跑
        → 权重占用不测量,由加载器记下的确切字节数直接传进去

段 3  图的显存单独估
        → 平台是 CUDA 系,且图模式不是 NONE,才估
        → 估出来之后还要看一个环境变量,才决定扣不扣
```

这里有四个容易记错的点,都是讲稿点出来的,逐条核过:

1. **测量不是靠 PyTorch 的峰值接口手动相减**,而是 vLLM 自己的记账上下文。权重那一项更不是测出来的——加载时就已经记下确切字节数,直接当参数传进去。
2. **假跑不在这一层直接调**,中间隔着一层探测函数,由它转调。
3. **最终公式只有三项减法**,不是「总显存乘占比,再减权重、减激活、减 workspace」那种四项拆法——权重、激活、workspace 已经被记账上下文合并成了一项。
4. **图的显存是单独一条路径估的,而且要两道门**:平台与图模式是第一道,环境变量是第二道。这条路径调用的正是 1.18 那对测量字段的开启者。环境变量**默认是开的**,也就是默认会扣。

没有假跑会怎样:只能用一个静态估计甚至猜。估保守了 KV cache 太少、吞吐上不去;估激进了就在生产里 OOM。唯一合法的例外是段 1——用户自己把数字定死了,探测也就没意义,但代价是显存占比参数被完全忽略,OOM 风险自负。

### 1.26 探测跑的是什么形状的批

这是最容易想错的地方。直觉会以为探测跑的是「最大批次乘最长序列」,**不是**。

实际形状是:

```text
token 总数  = 单步 token 预算           ← 固定
请求数      = min(token 预算, 并发上限)
每个请求长度 = token 总数 / 请求数,余数均摊

例(token 预算 8192,并发上限 256):
  请求数      = min(8192, 256) = 256
  每请求 token = 8192 / 256    = 32
  → 探测的是「256 个请求、每个 32 token、共 8192 token」
```

均摊时会保证没有哪个假请求超过模型的最大长度。

这个形状**线上几乎不会出现**——线上更可能是 1 个请求 8192 token。但对显存来说无所谓:几乎所有激活的尺寸只取决于 **token 总数**(都是 `[token 数, 隐藏维]` 这种形状),而 logits 与采样相关的缓冲取决于**请求数**。探测把这两个维度同时推到上限,就够了。

> 讲稿摘录这段代码时略掉了三处:开头还有一整段**多模态编码器缓存的探测**(支持多模态且是首个流水线 rank 时先跑);采样那一支其实是**二选一**,挂了 pooling 就走 pooling 的假跑;收尾还会重置一次编码器缓存。

### 1.27 探测时注意力是被跳过的

假跑有一个开关可以跳过注意力,而它被一条硬约束锁死:**只有显存探测这一次允许打开**,别的场景打开就直接抛错。

理由是鸡生蛋:**探测的目的就是算出能开多少 KV cache 块,而此时 KV cache 还没分配。** 注意力 kernel 拿不到有效的缓存指针和块表,根本跑不了。所以这一次把注意力的准备整段跳掉,块表、槽位映射、注意力元数据全是空。

这带来一个真实的低估风险:**注意力后端自己的 workspace 在探测阶段没被计入。** vLLM 靠两件事兜住:

- 这些 workspace 大多在后端初始化时就按 token 预算预分配好了,属于常驻占用,探测开始前就已经发生,会被算进常驻那一项。
- 剩下的临时量由显存占比参数默认留出的余量吸收。

顺带一条:**跳过注意力和整图是互斥的**,源码里有断言挡着——整图必须把注意力一起录进去,元数据不能是空的。

### 1.28 三个参数各管一件事

这一节是整章最实用的部分。三个参数经常被混为一谈,其实各管各的:

| 参数 | 管什么 | 调大的后果 |
|---|---|---|
| 单步 token 预算 | **探测的唯一输入**,决定一次前向里激活的最大宽度 | 探测峰值变大 → 留给 KV cache 的显存变少 |
| 并发上限 | 探测批里的请求数上限,进而决定 logits 缓冲、采样张量、块表行数 | 对词表很大的模型(十几万词)这一项不小 |
| 模型最大长度 | **完全不参与探测**。它只影响块表的列数,以及一个请求最多能占多少块 | 属于 KV cache 侧的账,不是激活侧的账 |

一句话记法:**激活峰值由 token 预算定,logits 峰值由并发上限定,KV cache 的需求由最大长度乘并发定,而 KV cache 的供给是前两者吃完之后剩下的那部分。**

这解释了两个常见困惑:

- 「我把模型最大长度从 8K 调到 128K,为什么启动没变慢也没 OOM?」——**探测根本不看它。** 变的只是每个请求最多能吃多少块,那是运行时由调度器挡着的事(02 章 1.6 的三道闸门)。
- 「我把 token 预算从 8192 调到 65536,启动就 OOM 了。」——**非常正常**,那正是探测的唯一输入。

### 1.29 显存账本:两个量,一道三项减法

记账上下文在假跑前后各拍一次快照,吐出两个量:

| 量 | 怎么算 | 含义 |
|---|---|---|
| 常驻消耗 | 进程启动前的空闲显存减去探测跑完后的空闲显存 | 这张卡少掉的全部显存:CUDA 上下文、通信缓冲、模型权重、后端预分配的 workspace,以及探测后没被回收的常驻量 |
| 瞬时峰值余量 | 探测后的 PyTorch 峰值减去探测后的已分配量 | 纯粹的瞬时激活余量 |

两个细节值得记:

- 常驻消耗用的是**设备级的显存查询**,不是 PyTorch 的分配器统计。所以连 PyTorch 管不到的非 torch 分配(通信库、cuBLAS 句柄)也算得进去。
- 瞬时峰值余量为什么要减掉已分配量:**常驻那部分已经在常驻消耗里算过一次了**,直接用峰值会重复计数。源码注释专门写了这一句。

两者相加就是「不是 KV cache 的部分」,于是最终公式只有三项:

```text
可用 KV cache 显存 = 卡的总显存 × 显存占比
                   - 非 KV cache 部分(常驻 + 瞬时峰值余量)
                   - 图的显存估计(可能为 0)
```

有一条性质容易踩:**总显存是按卡的总容量算的,不是按当前空闲算的。** 所以同卡上还有别的进程时,把占比设成 0.9 的含义是「vLLM 最多用到整卡的 90%」,别人占掉的量会直接挤压 vLLM 实际拿到的 KV cache(02 章 1.6.5 的换算链路同一口径)。

源码里有一条断言就是防这个:探测期间如果别的进程**释放**了显存,快照的前后关系会不成立,这时直接报错,而不是给出一个错的数。

> 但这条断言不是无条件的。ROCm 上有一条回退路径:命中时**整条断言被跳过**,改用 PyTorch 保留量当下界重算常驻消耗——注释说明这是 AMD 的 CI 撞到的情况。所以「一定会报错」这个说法在 ROCm 上不成立。

### 1.30 Triton kernel 的第一次调用为什么特别慢

假跑的第二件正事是**把编译提前**。

vLLM 里大量算子是 Triton 写的(融合 MoE、部分注意力、RMSNorm 等)。Triton kernel 不是预先编好的二进制,而是**首次调用时才编译**:它的源码是 Python 里一个被装饰的函数,写的是并行计算的逻辑,不是机器码。第一次调用要走完「按形状与 dtype 特化 → 生成中间表示 → 编成机器码 → 加载到设备」这一整条链,每一步都有不可忽略的固定成本。

编译产物会按「源码哈希加 dtype 加形状签名」做缓存,第二次同 key 直接命中。所以慢的只有第一次——**但「第一次」如果发生在第一个真实请求上,那个用户就要替所有人等**。

一个大模型有几十个不同的 Triton kernel,融合 MoE 尤其密集:每个专家的矩阵乘都可能触发一次新特化。加起来是分钟级的量级。

> 这一段的机制属于 Triton 自身,不在本仓库,上面的描述是讲稿的定位参考,没有在源码上逐条校验。vLLM 侧能证实的是:它确实重度依赖 Triton,而且确实把这些编译挪进了启动阶段。

### 1.31 自动调优必须在目标卡上、在干净环境里做

第三件正事是**自动调优**,它和 JIT 编译常被混为一谈,其实是两件事:

| | JIT 编译 | 自动调优 |
|---|---|---|
| 做什么 | 把源码变成可执行的机器码 | 在多个**已编译**的候选实现里选最快的 |
| 产物 | 一份机器码 | 一条「这个形状用那个配置」的查表记录 |
| 谁需要 | 所有 Triton kernel | 主要是注意力与矩阵乘 kernel |

自动调优的做法是跑微基准:同一个注意力 kernel 内部通常有多个候选实现,它们在分块大小、KV 切分份数、流水线深度、寄存器分配上不同;首次遇到某个形状就把候选逐个跑一遍,选最快的那个存起来。

**它必须预热,而且理由比 JIT 那条更微妙:**

- 自动调优是**在线测量**,只能在目标卡上真跑才有准数——不同型号的 SM 数、带宽、缓存行为都不一样,离线预知不了。
- 更要紧的是**测量环境**。调优选出的配置一旦定下就长期沿用;如果它发生在用户流量之下,测量结果会被并发请求干扰,**选出一个次优配置,然后一直用下去**。

所以预热的价值不只是「把耗时提前」,还有「**在干净环境里量,才量得准**」。后一条是长期收益,前一条只是一次性的。

### 1.32 惰性初始化:第一次才发生的那些事

第四件正事最琐碎,但漏了同样会出问题。PyTorch 与 CUDA 运行时里有一批东西是**用到才建**的:

- 卷积与矩阵乘的句柄,第一次调用才初始化,占几十 MB;
- 矩阵乘的 workspace,第一次才分配;
- 集合通信的通信子,第一次规约才真正建立连接;
- 上下文本身也会在首次触发某些算子时再涨一截。

放到首个请求才做,后果是**双重的**:既消耗那一次的时间,又**增加显存**——而这部分显存如果发生在探测之后,探测得到的数字就偏小,后面可能 OOM。

这条和 1.9 说的「注意力后端的惰性初始化必须在录图之前完成」是同一件事的不同侧面:**凡是「第一次才发生」的东西,都必须被赶到启动阶段去发生。**

### 1.33 启动期的 OOM 只可能发生在两个台阶

按启动时序,显存压力有五个台阶:

```text
台阶 1  上下文与分布式初始化      几百 MB,几乎不会 OOM
   ↓
台阶 2  加载模型权重              OOM 说明卡根本装不下,不是估错
   ↓
台阶 3  探测的假跑            ★  最常见的启动 OOM 点
   ↓
台阶 4  一次性分配 KV cache       通常不 OOM,数字是算出来的
   ↓
台阶 5  图捕获                ★  第二常见
```

**台阶 3** 是整个启动过程里激活最高的一刻——显存里有权重,加上一次满宽的激活,而 KV cache 还没分配。探测的目的就是制造这个峰值,所以它 OOM 几乎总是因为 token 预算设得太大,或者权重本身已经吃掉了绝大部分显存。

这里有个**极容易记反的点**:台阶 3 的 OOM 和显存占比参数**没有关系**。探测是真的在申请显存,而占比参数只进 1.29 那道最终减法——**它管不住探测本身的峰值。** 解法是降 token 预算(首选)、降并发上限(词表大的模型有效)、或提高并行度。

**台阶 4** 报的通常不是 OOM,而是**主动检查**:要么算出来的可用显存为负或太小,直接抛「没有可用显存给缓存块」;要么是放不下一个最大长度请求所需的块数。两者都是检查不是崩溃——**vLLM 宁可启动失败,也不让你带着一个必然会 OOM 的配置跑起来。** 这个区分很重要。

**台阶 5** 之所以容易 OOM:KV cache 这时已经占满了,而捕获还要额外申请显存池(1.17)。图的显存估算会被预留出来,但它受两道门控——平台必须是 CUDA 系、图模式不能是 NONE——任一不满足就不预留,KV cache 就多吃了那部分,捕获时撞墙。解法是降占比、砍桶数,或退到分段图甚至关掉图。

### 1.34 分块预填充能缓解哪一类 OOM,以及一个常见的误解

先纠正一个流传很广的说法:**「必须开分块预填充,探测才会按 token 预算跑,否则它按模型最大长度跑。」——机制不是这样的。**

探测**永远**按 token 预算跑(1.26),源码里没有任何一条分支让它去读模型最大长度。

真正的差别在**配置校验**那一层。启动时有一条检查:**token 预算小于模型最大长度、而又没开分块预填充,直接抛错**,理由是那样等于把实际可用的序列长度砍到 token 预算,更长的请求会被拒绝。

于是链条是这样的:

```text
不开分块预填充
  → 配置校验强制要求 token 预算 ≥ 模型最大长度
    → 探测批至少和模型最大长度一样宽
      → 看起来「像是按最长序列跑」
```

结论上确实相当于按最长序列跑,但那是**配置约束逼出来的下界,不是探测自己去读了最大长度**。这个区分有实际意义:如果你手动把 token 预算设得比最大长度还大,探测跑的是前者,跟分块预填充开不开无关。

(顺带,同一条校验里还有第二个条件:**token 预算不能小于并发上限**——否则探测批里会有假请求分不到一个 token。)

分块预填充默认是开的,只有编码器-解码器模型会被强制关掉(02 章 4.3 记过这一条)。

按台阶逐个看它能不能帮上:

| 台阶 | 能不能缓解 |
|---|---|
| 台阶 2 权重 | 无关 |
| 台阶 3 探测假跑 | **间接缓解,而且是关键的那一下**。它本身不降低任何显存峰值,它做的是把激活峰值从「最大长度」量级**解耦**到「token 预算」量级,从而让「降 token 预算」这个首选解法变得合法 |
| 台阶 4 分配 KV cache | **完全帮不上** |
| 台阶 5 图捕获 | 顺带受益——桶的上界由 token 预算决定,它降下来桶就更小 |

台阶 4 那一行最容易想错,值得展开:一个很长的 prompt,不管一次算完还是切成十几段,**所有 token 的 K/V 最终都要落进 KV cache,总量一分不少。** 分块预填充削的是激活,不是 KV cache。所以「KV cache 空间不足」这类启动失败,只能靠降最大长度、降并发、量化 KV cache 或者加卡来解。

反过来说,分块预填充其实就是下一节保障 2 的实现机制:「运行时激活峰值不可能超过探测峰值」这个结论之所以成立,靠的正是它把超长 prompt 切进了每步预算之内。

### 1.35 起来之后为什么基本不再 OOM:四条硬约束

启动成功之后不再 OOM,靠的是四条约束,它们共同构成一个**显存总量在启动时就被冻结**的设计:

| 保障 | 内容 | 机制在哪 |
|---|---|---|
| 1 | KV cache 一次性预分配,运行时既不增长也不释放。启动时申请一整块大缓冲,之后所有层、所有请求都在这块上切视图;运行时「分配块」只是从空闲表取一个编号,**不触发任何显存分配** | 03 章 |
| 2 | 调度器把每步的激活宽度卡在探测过的上限之内——每步的 token 预算与请求数上限,正是探测时用的那两个数 | 02 章 1.5、1.6 |
| 3 | 显存不够时调度器的反应是**不调度**,不是硬上然后 OOM。块不够就让请求留在等待队列,或者抢占正在跑的请求腾出来。表现为吞吐下降或排队变长,**不是崩溃** | 02 章 1.7、03 章 |
| 4 | 所有 GPU 输入缓冲启动时按最大尺寸预分配,运行时只往里拷(1.5、1.6);图的显存池同理,捕获完就固定,重放不申请任何新显存(1.17) | 本章 |

保障 1 是 PagedAttention 最重要的工程价值之一,可以一句话概括:**显存需求从「随请求动态涨」变成「启动即定死」。**

### 1.36 剩下那些「不基本」的情况

上一节说的是「基本不会」,这个词是必要的。诚实地列一下仍然可能运行时 OOM 的场景——它们**全都在那四条约束之外**:

- **同卡上有别的进程。** 总量是按整卡算的(1.29),vLLM 并不知道别人后来又占了多少。这是运行时 OOM 的头号原因。
- **手动指定了 KV cache 字节数。** 走的是跳过探测那条路(1.25 段 1),日志里那句「如果 OOM 了,去对比一下初始空闲显存的差异」就是在提醒风险由用户承担。
- **图的显存没被预留。** 如果捕获侥幸成功但余量被吃干,后续任何一点额外分配都可能压垮。
- **显存碎片。** 长时间运行后分配器的碎片可能让「总量够但连续块不够」,报错里会带「已保留但未分配」的字样。这属于 PyTorch 分配器的行为,通常靠可扩展段的配置项缓解。
- **探测没覆盖到的路径在运行时才走到。** 多模态编码器的实际输入比探测用的假输入更大(跳过多模态探测时尤其危险)、运行时新加载适配器、跳过注意力导致的 workspace 低估(1.27)、以及睡眠唤醒之后的重建。
- **量化与 MoE 的专家相关缓冲**在特定路由分布下才膨胀。

一句话收口:**vLLM 的设计目标是「启动时把显存吃到目标水位并冻结,运行时零动态分配」,所以启动成功基本等于运行安全;剩下的 OOM 几乎都来自「有人从外部动了这张卡」或「探测没覆盖到那条路径」。**

### 1.37 完整的启动顺序

把前面这些串成一条线:

```text
① 加载模型权重              加载器顺手记下权重的确切字节数
        ↓
② 显存探测                  在记账上下文里跑一次假跑(跳过注意力)
                            图的显存单独估
                            → 得出可用 KV cache 显存 → 换算成块数
        ↓
③ 分配 KV cache             真正申请那块大缓冲
        ↓
④ kernel 预热               手搭调度输出,走 worker 的正常入口:
                            一个 prefill step(触发 Triton 编译)
                            三或五个 decode step(另一条 kernel 路径)
                            再加一次混合批的预热(又一条路径)
        ↓
⑤ 图捕获                    分段图在前、整图在后;每张图先跑
                            一次不录制的预热,再录
        ↓
⑥ 引擎就绪,开始收请求
```

顺序不能换:**② 必须在 ③ 之前**(不先探测就不知道能开多大),**③ 必须在 ⑤ 之前**(没有 KV cache 张量,注意力拿不到指针,录图会崩),**④ 必须在 ⑤ 之前**(编译与调优是动态行为,不能被录进图)。

第 ④ 步里那个 prefill 的长度值得单独看一眼:它取的是「decode 的固定查询长度**加一**」。注释给了理由——**要让这一批的每请求查询长度超过 decode 的那个值,否则会被误分类成 decode**,预热就覆盖不到 prefill 那条 kernel 路径了。这正好呼应 02 章 2.7.4 的排序键:那里判定「纯 decode」用的就是「查询长度等于该值」。

整套流程通常花十秒到两分钟,取决于模型大小与桶数。**这是必需成本,不是可省环节。**

### 1.38 搬运的敌人是同步点

回到 1.2 留下的那个问题:调度器交出来的是 CPU 数据,模型要的是 GPU 张量,这次翻译每步都要做一遍。

朴素的写法是每步现造张量:把 Python 列表转成 numpy,再转成设备张量。问题出在最后一步——**它内部会同步当前 stream**。语义上它必须保证「返回时数据已经在 GPU 上」,于是 CPU 必须停下来,等 GPU 把之前排队的活儿跑完。

后果是 CPU 和 GPU 完全串行:

```text
朴素:  CPU 造张量 → 等 GPU ────→ 下发 → 等 GPU ────→ 下发 → …
                    ↑ GPU 这段时间在忙,但 CPU 什么也做不了
                                          ↑ CPU 在忙,GPU 空转

目标:  CPU 永远不等 GPU,把下一步的拷贝和下发尽早塞进 stream
```

这就是 1.1 那条痛点的另一面:光把 kernel 下发做快还不够,**只要搬运里留着一个同步点,流水线就断在那里。** 后面几节讲的都是怎么把同步点一个个拆掉。

### 1.39 锁页内存与异步拷贝

第一道纪律是 1.5 已经说过的**预分配**,这里补一条它的推论:**热路径上绝不调用任何会新建张量的接口。** 新建会走分配器,而分配器有锁、可能同步 stream,是同步点的主要来源。

第二道是搬运本身,靠两个关键词:

**锁页内存。** 普通的 CPU 内存是可换页的,DMA 引擎不能直接访问;锁页之后,DMA 引擎能**不经 CPU 介入**地把数据搬到 GPU。这是异步拷贝的前提。

这一步不一定有拷贝开销——源码注释写明:**内存如果已经是锁页的,这一步是空操作。** 而常驻缓冲的 CPU 侧建的时候就指定了锁页,所以走常驻那条路时这一步零成本;只有传进来的是临时的 numpy 数组时,才真的多一次主机内拷贝。

> 这正是「为什么要预先备好缓冲、而不是每步现造数组」的一半理由。另一半在 1.41。

**异步拷贝。** 发起之后**立即返回**,不等数据搬完;拷贝被排进 stream,CPU 继续往下跑——算位置、构造元数据、下发下一个 kernel。

### 1.40 能不搬就不搬

上一节讲的是「搬得快」。但还有一招更彻底:**根本不搬。**

位置索引就是个例子。直觉上它应该在 CPU 上算好再传过去,实际上**它是在 GPU 上算出来的**——已算 token 数和请求内偏移这两样东西本来就已经在 GPU 上,一次逐元素加就得到位置索引,全程没有任何主机到设备的传输。

这条思路和 1.6 的块表增量更新是一脉的,只是更进一步:**增量更新省的是传输量,GPU 上现算省的是传输本身。**(全部手法的汇总见 1.50。)

块表那张表值得补个量:按并发 256、每请求最多 2048 块算,整表是 2 MB。每步真正变化的只有少数请求末尾新增的那几个块——**整表重传是把 2 MB 换成几十个整数的事**。承载暂存写的那三个元数据缓冲各自是一个池,池内轮转的份数等于最大并发批数(不是三份,容易数错)——为什么非轮转不可,1.46 会给出反例。

### 1.41 双缓冲:让两步同时在飞

前面几节让 CPU 在**一步之内**不等 GPU。还能更进一步:**让 CPU 在 GPU 还没算完上一步时,就去准备下一步。**

默认的主循环是串行的:调度、执行、拿结果、再调度。开启异步调度之后变成:

```text
串行:
  step N:   [调度 N]→[GPU 前向 N]→[拿结果 N]→  step N+1: …
              ↑ CPU 等 GPU                      ↑ GPU 空转等 CPU

异步:
  step N:   [调度 N]→[GPU 前向 N 在跑 ──────────]
  step N+1:        [调度 N+1]→[GPU 前向 N+1 排队 ─→]
                     ↑ CPU 不等 step N 的结果,立刻调度 N+1
  step N+2:                    [队列满了,取 step N 的结果]→[调度 N+2]
```

实现靠一个**定长队列**加非阻塞的 future。每一轮做三件事:调度并非阻塞地下发、把 future 入队、**队列没满就直接返回**(让主循环立刻再来一轮);只有**队列满了**才弹出最老的那个、阻塞等它完成。

队列长度在单卡开异步调度时是 **2**,也就是最多两步同时在飞。

稳态下队列**始终是满的**:CPU 调度一步只要几毫秒,GPU 前向要十几到几十毫秒,CPU 比 GPU 快得多,启动后队列很快填满,之后每轮变成「入一个、弹一个」。那个「弹一个并等它」看起来像浪费,其实不是——**等的同时,队列里还有一个更新的 step 正在 GPU 上跑**,GPU 始终有活干。

队列的另一个作用是**限流**。没有它的话,CPU 可能一口气调度上百个 step,每个都预占 KV cache 块,显存会爆。长度为 2 意味着最多两步同时占资源,超过就必须等最老的完成、释放块之后才能继续。

> 这也是上一节说的「缓冲池要轮转」的理由:**同时有两步在飞,它们各自的暂存缓冲不能是同一份**,否则第二步会覆盖掉第一步还没搬完的数据。轮转份数等于最大并发批数,正是为了一一对应。

> 实现上有个容易漏的细节:入队的不是一个 future 而是一组。采样那个 future 返回空时,要去取执行那个 future 的结果,**才能把原始异常抛出来**——否则错误会以「意外」的形式丢失。

### 1.42 乐观调度:不等上一步的结果就排下一步

上一节有个绕不过去的问题:**调度 step N+1 时,step N 的结果还没回来。** 而直觉上调度器应该先看 step N 采样出了什么、哪些请求碰到结束符了,才能决定 step N+1 算什么。

异步调度不等。它的办法是**预支**:每次调度结束,立刻给每个正在 decode 的请求预支下一个 token 的位置,假装「这个请求已经产出了下一个 token」。预支量是「每步采样数加上这一步给它调度的草稿数」;草稿 token 的真实值还没算出来,就先塞一串占位值。

于是下一次算「这个请求还要算几个新 token」时,预支量被加了进去——**请求看起来还有空间继续算,调度器就能把它排进下一步,不需要知道上一步实际采到的是结束符还是普通 token。**

代价很清楚:**如果 step N 跑完发现是结束符,step N+1 已经为它多算了一个 token。** 因为下一步的调度与下发都发生在上一步的结果处理之前。

这个多算的 token 既不会发给客户端,也不会污染 KV cache——处理输出时会先查请求还在不在表里、是不是已结束,**已结束的连采样结果都不读**。而且结果处理排在再下一步的调度之前,所以**最多只多算一次**。

代价的量级:批大小 32、每步约有一两个请求结束,大约是 3% 到 6% 的额外 decode 算力;换来的是 CPU 与 GPU 完全重叠。这些数字是讲稿的量级估算,不是本仓库实测。

> 「预支加事后修正」这套语义、两个计数器的分工、以及被拒绝的草稿 token 怎么回滚,02 章 3.2 已经完整展开过,这里不重复。本节只补执行层这一侧:**预支具体预支了什么,以及它为什么是队列能跑起来的前提。**

### 1.43 抢占撞上在途帧

还有一个边界情况:请求在预支还没兑现时就**被抢占**了(不是正常结束)。这时在途的那一帧就变成了**过期帧**——它返回时带回的 token 对应的是抢占前的状态。

处理得比「直接丢弃」细:抢占时把预支清零,同时记下「有多少在途 token 属于抢占前」;之后每步按调度量**等量放水**,慢慢把这个计数减回去。

过期帧默认的行为是**照常投递给客户端**,只是不回改计数器——预支在抢占时已经清零,过期的投递再去减就会下溢;草稿的拒绝回滚同样跳过,因为那个拒绝数产生于抢占回滚之前,再套一遍等于把账算重。两处注释都把理由写明了。

只有两种情况会走**整帧丢弃**:重置前缀缓存触发的同步抢占(同一步里立刻恢复,投递会导致 token 乱序),以及 KV 传输还挂着交接的请求(抢占释放块后 KV 已失效)。

> 「在途输出被标记为过期但照常交付」这个决策本身,以及丢掉它反而会扰乱草稿接受率统计的理由,02 章 3.3 已经讲过。这里补的是**抢占侧怎么记账**——那是 02 章没展开的一半。

### 1.44 采样出的 token 不回 CPU

上一节的乐观调度解决了「不等结果就排下一步」。但还有一个更朴素的问题:**step N 采样出来的 token,step N+1 要拿它当输入。**

朴素路径是绕一圈:GPU 采样 → 拷回 CPU → 组装成下一步的输入 → 再传回 GPU。一次往返,而且中间那次拷回是同步的,整条流水线又断了。

vLLM 的做法是**根本不绕这圈**:采样完立刻在 GPU 上把 token 写进一块常驻的「上一步采样结果」里,同时更新已算 token 数、token 序列、总长度;下一步准备输入时,由另一个 kernel 直接从那块地方搬进输入缓冲。

两头都是 Triton kernel,**全程在 GPU 上完成,CPU 不参与**。这是 1.40 那条「能不搬就不搬」用在了最热的那条路径上。

### 1.45 那 token 什么时候才到 CPU

不回 CPU 是对 forward 而言的。但 token 终究要到 CPU——engine core 得看它是不是结束符,客户端得收到它。

所以 token 其实有**两条路,各走各的**:

| 路径 | 给谁用 | 怎么走 |
|---|---|---|
| GPU 到 GPU | 下一步的前向 | 留在常驻缓冲里,下一步 kernel 直接搬。**零延迟** |
| GPU 到 CPU | 检测结束符、发给客户端 | 在**单独的拷贝流**上异步发起,只有 engine core 主动取结果时才同步等待 |

第二条路的实现是一个输出对象,在采样后立刻构造:它在拷贝流上排队,先等主流的前向完成,再异步把采样结果拷向 CPU,最后**记一个完成事件**。engine core 真正要结果时才去等那个事件,然后把数据取到 CPU、顺手裁掉未被接受的草稿 token。

串起来是这样:

```text
T1  前向 N 在主流上跑完
      → 构造输出对象,在拷贝流上发起 D2H(异步,不阻塞)
      → 把 future 入队
T2  worker 立刻准备 step N+1(用常驻的上一步采样结果)
      engine core 调度并下发 step N+1
      (step N 的 D2H 还在拷贝流上跑,与 step N+1 的准备重叠)
T3  队列满了 → engine core 取结果
      → 等那个完成事件 ← 到这里才真的等 D2H
      → token 落到 CPU → 调度器看到结束符,移除请求
T4  调度 step N+2 → 已结束的请求不再排
```

**关键点:拷贝在 T1 发起,直到 T3 才被等待。** 这段时间里,拷贝流上的 D2H 和主流上 step N+1 的前向**并行执行**——这就是「解耦」的具体含义。

两个细节值得记:

- 采样后的那次 GPU 侧回写是**故意排在构造输出对象之后**的。注释说明了理由:先把完成事件记下,异步拷贝就不必等回写跑完。
- 那个完成事件用的是**阻塞式**的。注释给的理由不是「要等」,而是**避免忙等把 CUDA driver 的锁占住**——忙等会拖累所有别的线程。

(pooling 模型走的是并列的另一个输出类,结构相同。)

### 1.46 只有一份暂存缓冲会出什么事

1.41 说过缓冲池必须轮转,当时只给了结论。这里补上反例,因为它是理解整套异步设计的关键。

假设只有一份锁页缓冲,而队列允许两步同时在飞:

![一份锁页缓冲与轮转两份的对比:横轴是时间、每行是一块物理内存,单缓冲时 step N+1 的写落进了 step N 的 DMA 读区间、同一块内存上读写重叠,GPU 收到一半新一半旧的数据;轮转两份后新的写落在另一行,冲突带消失](/opensource/vllm/06a-buffer-hazard.svg)

图里横轴是时间,**每一行是一块物理内存**。上半只有一块:step N 的 DMA 还在读它,step N+1 的写就落了进来——那块红色虚线区就是**同一块内存上,读区间与写时刻的重叠**。GPU 最终收到 `[10,20,60]`,一半新一半旧,前向 N 拿着错误的输入算出错误结果。

这叫**写后读竞争**:下一步对缓冲的**写**,发生在上一步的 H2D 对它的**读**完成之前。因为拷贝是异步的,CPU 根本不知道 DMA 读完了没有——想知道就得同步,而那又回到了 1.38 说的同步点,等于把异步的收益全吐回去。

**所以解法不能是「等一下」,只能是「换一块」。**

### 1.47 轮转几份,由几步同时在飞决定

缓冲池预分配若干份,每次取用就轮转到下一份——就是上图下半那个样子:**新的写落到另一行去,读和写不再共用同一块内存,冲突带自然消失。**

再往后一步看,轮转能一直成立:

```text
step N:    轮到 B0,写 B0,H2D 读 B0
step N+1:  轮到 B1,写 B1 —— 不动 B0,安全
step N+2:  轮到 B0,此时 step N 的 H2D 必定已完成
           (因为依赖它的前向 N 早已入队并执行)
```

份数必须**不少于同时在飞的步数**,源码注释把这条要求写死了。默认是 2,与 1.41 说的队列长度对上;而且有个下界保护——就算你把它调低,实际份数也不会小于 2。

真正做到自适应的是这一步:**V2 运行器在初始化时,把池子的默认份数设成 engine 允许的最大并发批数。** engine 里有多少步同时在飞,就开多少份缓冲,保证任何一个在飞步的缓冲都不会被后续步覆盖。

**V1 运行器不走这条路,池子一直是默认的两份。** 这是两套实现分工差别的又一处体现(1.4)。

### 1.48 异步调度对注意力计算的影响是零

到这里可以回答一个自然的疑问:这套乐观调度、双缓冲、GPU 内传递,对注意力 kernel 有什么影响?

**没有影响。** 注意力后端的代码里没有任何一处分支去问「现在是不是异步调度」。它收到的元数据——序列长度、块表、累计长度、槽位映射——在两种模式下结构完全相同。kernel 照常算,不关心输入是从 CPU 搬来的还是 GPU 内拷来的。

这印证了 05 章那条分工:**后端只认元数据,不认上层的执行模式。** 上层怎么折腾流水线,都不该漏进 kernel 里。

差异全部落在准备数据这一层,而且只有一处是显著的:

| 维度 | 同步调度 | 异步调度 |
|---|---|---|
| **输入 token 的来源** | CPU 侧组装后传过去 | **上一步的 GPU 采样结果,GPU 内拷贝** |
| 位置与序列长度 | 已算数加偏移 | 同一个公式 |
| 块表构造 | 暂存写加收集重排 | 相同 |

### 1.49 全接受假设:两套运行器的不同答卷

有一个地方异步调度确实带来了额外复杂度——**投机解码**。

调度器预支的时候(1.42)假设了「上一步的草稿 token 全都被接受」。但实际可能只接受了一部分,甚至请求已经结束。于是准备数据时用的序列长度是个**乐观值**,真实值要等前向跑完才知道。

两套运行器的处理方式截然不同,对比起来很能说明它们的设计分野:

**V1 运行器**在 CPU 侧维护一份乐观长度,用它做两件事:算注意力 workspace 的上界(取上界总是安全的),以及构造一份**丢弃掩码**——乐观长度小于实际 token 数,就说明这个请求的草稿没被全接受或者已经结束,它这一行的输出要丢掉。

关键在于**丢弃发生在前向之后**:

> **注意力 kernel 对所有请求照常计算,包括那些注定要被丢弃的,不做任何 mask。** 掩码只在后面的拒绝采样与隐藏状态抽取处生效。

为什么不在 kernel 里直接跳过?因为那要加条件分支,而**条件分支会破坏图捕获与算子融合**。代价是多算了一些会被丢弃的注意力输出。

这和 1.42 的「多算一个 token」是**同一个取舍**,而且可以提炼成一条贯穿全章的原则:

**宁可多算一点,也不要在热路径上加分支。** 分支破坏的是图捕获、算子融合、形状固定这些结构性收益,它们的价值远大于省下的那点算力。

**V2 运行器没有这套东西。** 它的序列长度与位置由 kernel 直接从 GPU 上的已算数算出,被拒绝的草稿由另一个 kernel 在 GPU 上回滚——**不需要在 CPU 上预先标记要丢哪些行**。这正是 1.4 说的「状态常驻 GPU」对「CPU 侧维护镜像」的差别,落到了最具体的一处。

(不开投机解码时,两者的差异只剩输入 token 的来源那一条——普通 decode 每步每请求只算一个 token,不存在草稿被拒绝的复杂性,乐观长度就等于实际长度。)

### 1.50 一个 step 的时间轴

把整个 Part 1 收口。一个 step 实际长这样:

```text
CPU:  [更新状态] [准备输入:numpy 算术 + 异步拷贝下发] [下发 kernel]
                          │
                          │ H2D(DMA,异步)
                          ▼
GPU:  [上个 step 的前向尾部] → [H2D 完成] → [本 step 的前向] → [下个 step 的 H2D]
                                                    ▲
                                                    └ CPU 早已在下发本 step 的 kernel
```

**CPU 永远在下发,不等 GPU;GPU 一直有事干,拷贝与计算交替。** 这条时间轴是 1.1 那个痛点的最终答案,而它由前面这些机制共同支撑:

| 机制 | 拆掉的是哪个同步点 |
|---|---|
| 缓冲预分配(1.5) | 分配本身 |
| 锁页加异步拷贝(1.39) | 等待拷贝完成 |
| 稀疏增量与 GPU 内现算(1.6、1.40、1.44) | 传输量,乃至传输本身 |
| 缓冲池轮转(1.47) | 「等 DMA 读完才能复用缓冲」 |
| 双缓冲队列(1.41) | 「等上一步结果才能调度下一步」 |
| 乐观调度(1.42) | 「等上一步结果才知道排什么」 |
| CUDA Graph(1.7 起) | 下发本身 |

最后一行值得重申:前六行解决的是**等待**,只有最后一行解决的是**下发**。两类问题都拆掉,CPU 才真正不再是 decode 的瓶颈。

顺带一提,请求顺序的重排(1.6)同样是纯 GPU 操作——kernel 在流上排队,CPU 不参与,所以它也不打断这条流水线。

## Part 2|图解

Part 1 是按痛点线走的:每一节回答「不这么做会出什么事」,机制被拆散在各处。这一部分只补一件 Part 1 做不到的事——**把它们在一次调用里的先后顺序摆出来**。

执行栈的上半段(engine 主循环怎么用队列把两步叠起来)、图的录制与重放流程、三条时间轴的重叠关系,1.41 至 1.50 已经讲透,这里不重复。

### 2.1 一个 step 在执行层内部的六步

```text
GPUModelRunner.execute_model(调度决策)
  │
  ├─ ① 同步请求状态            —— 增、删、改,全部作用在常驻 GPU 的状态表上
  │     · 结束的请求出表、释放槽位
  │     · 新请求入表,写 prompt token 与采样参数
  │     · 已有请求追加本步新分的块(只暂存)
  │     · 一次批量提交,把攒下的块表增量写进 GPU     ← 1.6
  │     · 若这一步没有 token 要算,到此为止:只跑 KV 传输的收尾就返回
  │
  ├─ ② 定 batch 描述符          —— 请求数、token 数,并跨数据并行 rank 对齐
  │     决定 padding 到哪个桶、走哪一档图                ← 1.12、1.14
  │
  ├─ ③ 准备输入与注意力元数据   —— 主体是一批 Triton kernel
  │     · 索引映射与起止位置:锁页加异步拷贝              ← 1.39
  │     · 输入 token:异步调度下是 GPU 内拷贝,否则从 CPU 来  ← 1.44
  │     · 位置与序列长度:直接在 GPU 上算,没有搬运        ← 1.40
  │     · 块表:按本步顺序重排,padding 行清零            ← 1.6
  │
  ├─ ④ 跑前向                   —— 走哪条路由 ② 的描述符决定
  │     整图 → 一次重放;分段图 → 图段与 eager 注意力交替;否则 eager  ← 1.10、1.23
  │     中间结果存进一个状态对象,留给下一步
  │
  ├─ ⑤ 采样                     —— 注意:这一步是**另一次调用**(3.2)
  │     采出的 token 留在 GPU 上给下一步用,同时在拷贝流上异步送往 CPU  ← 1.44、1.45
  │
  └─ ⑥ 构造输出
```

这张骨架图最该记住的是**① 和 ⑤ 的位置**:状态同步排在最前(所以块表增量必须在这一步之前攒好),而采样根本不在这次调用里——它是独立的第二次调用,理由见 3.2。

### 2.2 块表其实是两个张量

1.6 说过块表「按调度顺序重排」,但没点明重排的源和目标是**两个不同的张量**:

```text
常驻源表      [最大请求数 × 最大块数]   按请求槽位排,跨 step 复用
                    │
                    │  收集重排 kernel:按本步的批次顺序取行,
                    │  padding 行清零
                    ▼
本步目标表    [最大请求数 × 最大块数]   按本步批次顺序排,喂给 kernel

槽位映射      [KV 组数 × 最大 token 数]  另一个 kernel 单独算出
```

为什么不能只有一张:**源表必须按请求槽位排**,否则跨 step 的增量写就找不到自己那一行;而**前向要的是按本步批次顺序排**,因为注意力 kernel 按批次下标取块表。两种顺序无法共存,只能每步现生成一份。

padding 行必须清零,也是图带来的约束——形状固定意味着表里总有几行是空的(1.9),里面如果留着上一步的残值,kernel 会读到无效块号。

## Part 3|机制之外:源码里额外读到的

前两部分讲清了执行层**应该怎么工作**。这一部分只放照着源码读下来、**机制层面看不见但真实存在**的细节。前面讲过的一概不重复。

### 3.1 构造分三段,`__init__` 不碰 GPU

工作进程的构造被拆成三段,而且**第一段完全不碰 GPU**:

| 阶段 | 做什么 |
|---|---|
| 构造函数 | 纯 CPU 侧准备:精度开关、容错哨兵、睡眠模式的缓冲占位、profiler 配置,以及**记下该用哪套运行器** |
| 初始化设备 | 选定设备、建好分布式进程组,**然后才创建模型运行器** |
| 初始化 KV cache | 拿到配置之后,才建 KV cache、注意力元数据构造器、块表 |

顺序是被依赖关系逼出来的:运行器构造时要读设备属性,所以必须在选定设备之后;而 KV cache 的大小要等显存探测算出来(1.25),所以必须在更后面。

**运行器这边同样如此**:它的构造函数只做配置与派生量,真正的重头戏都在第三段。这解释了一个读代码时的困惑——在构造函数里找不到 KV cache 和块表,它们那时还不存在。

### 3.2 前向与采样是两次调用,不是一次

工作进程对外暴露的不是一个「跑一步」的方法,而是**两个并列的入口**:一个只跑前向不采样,一个只采样。

这个拆分不是洁癖,它是 engine 侧那条「等结构化输出的位掩码时推迟采样」(1.41)能成立的**前提**:前向可以先发出去跑,位掩码算好之后再单独调采样。合成一个方法就没法把这两件事分开安排。

两次调用之间靠一个状态对象交接:前向把本步的输入批次、注意力元数据、隐藏状态等**十个字段**存进去,采样那次取出来用,**取完立刻清空**。清空这一下是有意的——它同时起到了「上一次前向失败了吗」的标记作用:采样进来发现状态是空的,直接返回空,而不是拿着上一步的陈旧数据算。

流水线并行下还有一层:**不是最后一个 rank 的进程根本不采样**,它产出的是中间张量而非最终隐藏状态;它只是接收末端 rank 广播回来的 token,更新本地状态。

### 3.3 没有 token 要算的 step,仍然要走一趟

状态同步之后有一条早退分支:如果这一步调度器一个 token 都没排,就**不跑模型**,只跑 KV 传输的收尾然后返回。

值得注意的是它的位置——**早退发生在状态同步之后,不是之前**。也就是说哪怕不算任何 token,请求的增删、块的追加、块表的批量提交**照样要做**。道理很直接:这些是记账,记账不能因为「这一步没活干」就跳过,否则下一步的状态就是错的。

### 3.4 这一步没有「把块表拷上去」

读 `execute_model` 时容易找一个不存在的东西:**从 CPU 把块表拷到 GPU 的那一行**。

它不存在。追加块的方法只做暂存——把「第几行、从第几列开始、写哪些块号」记下来,不碰 GPU。真正落盘是状态同步末尾那一次批量提交,**一个 Triton kernel 处理整批增量**(1.6)。

这一路上还有两件讲稿没提、但读代码会撞见的事:

- **块号在这里要做一次展开。** 管理侧的块和 kernel 侧的块可能不是一个粒度,一个管理块对应多个 kernel 块时,要在暂存前把块号展开(这与 03 章讲的块表第二维要乘一个倍数是同一件事)。
- **有一条行容量检查。** 写入超出该行能放的块数时直接抛错,而不是越界写坏隔壁请求的块表。

### 3.5 KV cache 的形状不在运行器里手写

初始化 KV cache 那一步看起来该有一大段形状计算,实际上没有:**形状由每一层自己发布的缓存规格决定**,运行器只负责按算出来的字节数切视图;每一维的跨距也由一个专门的函数按布局枚举算出。

这是一处清晰的职责边界:**运行器不知道也不需要知道某一层的注意力是哪种形态**——标准注意力、MLA、还是状态空间模型,各自发布自己的规格,运行器一视同仁地分配。03 章讲过布局怎么决议,那是这条链路的另一端。

### 3.6 整条准备路径上没有一次同步

最后回到 1.38 那个痛点,给一个正面的回答。

把准备输入这一段从头读到尾,会发现 **CPU 只产生 numpy 的索引与长度数组**——批次下标到请求槽位的映射、每个请求的起止位置、每个请求排了多少 token。这些都是几十到几百个整数的小数组。

而 **token 的内容和位置全部在 GPU 上算出来**:输入 token 来自上一步留在 GPU 的采样结果,位置由已算数加偏移现算,序列长度同理。

于是整条路径上:

- 没有一处把 Python 列表直接变成设备张量(那会同步);
- 没有一次把数据从 GPU 取回 CPU(那更会同步);
- 所有拷贝都是锁页加异步,所有计算都是排进流的 kernel。

**CPU 从头到尾只在下发,一次都没有停下来等过 GPU。** 这就是 1.1 那条痛点的最终答案。

### 3.7 两套编号,以及那张映射表

前面一直在用两个下标却没解释过它们的区别,这里补上——它是整个执行层能「不在 CPU 上重排任何状态」的关键。

同一个请求有**两个身份**:

| 编号 | 含义 | 什么时候变 |
|---|---|---|
| 状态表下标 | 它在常驻状态表里占第几个槽位 | 入表时定下,**整条请求的生命周期内不变** |
| 批次下标 | 它在本步这一批里排第几个 | **每步都可能变**——有请求结束、有新请求加入 |

两套编号必须并存:常驻状态(已算 token 数、token 序列、块表)只能按**槽位**存,否则每步都要搬家;而 kernel 要按**批次顺序**取数据,因为张量是按批次紧凑排列的。

朴素的解法是每步在 CPU 上把状态按新顺序重排一遍——那是一大堆内存搬运,而且全在关键路径上。

vLLM 的解法是**加一层映射**:每步只算一张「批次下标 → 状态表下标」的小表,连同一份 CPU 镜像一起传上去。之后所有 Triton kernel 都靠它**间接寻址**:

```text
kernel 要第 3 个请求的东西
  → 查映射表,得知它在状态表的第 17 槽
  → 直接去第 17 槽取
```

于是**状态一次都不用搬**。算位置与序列长度的 kernel、回写采样结果的 kernel、重排块表的 kernel,全都这么干。CPU 那一侧只需要产出这张几百个整数的映射表——正是 3.6 说的「只产生索引数组」。

代价也很实在:代码里多了一层间接寻址,读起来不如直接操作 CPU 列表直观。**这是这套设计最主要的可读性成本。**

### 3.8 凡是记地址的东西,睡一觉就会失效

块表那一层除了数据张量,还存着几个**裸指针张量**——里面装的是别的张量的设备地址,给 kernel 一次性拿到所有组的表用。

这类东西有个特殊的脆弱点:**显存睡眠唤醒之后必须重建。** 睡眠会把底层张量释放掉,唤醒时重新分配,地址就变了;而指针张量里记的还是旧地址,再用就指向了别人的内存。

所以块表那一层专门有个方法负责重建这些指针张量,睡眠唤醒之后要调一次。

这条可以推广成一句提醒:**执行层里所有「记住了地址」的东西,在睡眠唤醒后都是可疑的。** 图也是同一类——它录的正是地址(1.8),所以唤醒后同样要重新预热(1.24)。

### 3.9 重放之前并没有一次搬运

教科书讲 CUDA Graph 通常是这个套路:准备一组静态缓冲,每次重放前把真实数据拷进去,然后重放。

**vLLM 不是这样的,而且差别值得说清。**

图管理器身上根本**没有静态缓冲这类成员**。静态缓冲不由它持有——那就是 1.5 的输入缓冲区,一次性分配、地址天然固定;录制时录进图的正是这些地址。

于是重放路径极短:**一次 offloader 同步,然后直接重放。** 没有任何拷贝。

道理想通了其实很自然:**数据早在准备输入那一步就已经就地写进这些地址了**(1.39、1.40)。既然写的就是图录的那块内存,哪还需要再搬一次?padding 那些位置也不用清——靠槽位映射里填无效值来处理(1.6)。

> 这一点纠正了一个容易形成的印象。讲稿在前面讲录制流程时给过一段「重放前先把数据拷进静态缓冲」的教学伪码,按基准那一步不存在;它自己在讲源码时也纠正了。**本章 1.9 原先照搬了那个说法,已经改掉。**

顺带一提,分段图也不在这条路径上重放——默认配置下那个方法就是普通调一次模型,真正的重放发生在编译层的包装器内部(1.22)。

### 3.10 预热必须走正门

1.24 说过 kernel 预热不走假跑那条内部快捷通道,而是手搭调度输出、经 worker 的正常入口跑。当时给的理由是「覆盖到的 kernel 路径才和线上一致」。

源码的注释还给了**第二个、而且是硬性的**理由:**必须走 worker 的入口,否则流水线并行的协调会出错。** 假跑那条路绕过了 rank 之间的收发协调,多卡流水线下直接就跑错了。

所以这不只是「覆盖得更全」的优化,是正确性要求。

预热本身也有几处克制的设计:

- **并发数是反推出来的。** 先按最坏情况算一个请求要几个块,再据此推能同时跑几个请求——而不是直接拿并发上限去凑。算的时候还要预留出第 0 块(它是空块)。
- **块不够就跳过,并打一条警告。** 预热宁可少覆盖一种形态,也不会因为凑不出批次而让启动失败。混合批那一支还有一道形态性早退:pooling 模型、并发上限太小、token 太少的情况下直接不跑,因为凑不出「一个 decode 加一个 prefill」这个组合。

这和 1.35 保障 3 的「显存不够就不调度,而不是硬上然后崩」是同一种克制:**宁可少做一点,不要把启动搭进去。**

## Part 4|对比与决策

前三部分讲的是这台机器怎么造的。这一部分讲怎么用它:和别家比取舍在哪、参数往哪边拧、出了问题先怀疑什么。

### 4.1 和 SGLang 的执行层比,取舍在哪

下表 vLLM 那一列是本章全程对着源码核过的;SGLang 那一列**不在本仓库、无法用源码校验**,是讲稿按其公开设计思路给的方向性描述,只用来标出 vLLM 在每个维度上做了什么选择,不宜当作 SGLang 当前实现的准确结论。

| 维度 | vLLM | SGLang(方向性) |
|---|---|---|
| 进程组织 | 每 GPU 一个工作进程 | 类似 |
| 请求状态放哪 | V2 运行器**常驻 GPU**,CPU 只传索引 | CPU 侧维护为主 |
| CUDA Graph | 三档运行时模式,按批次描述符派发 | 有图,档位划分较粗 |
| 块表更新 | 暂存增量加一个 kernel 批量落盘 | 整表或按行拷贝 |
| 预热 | 伪造真实调度输出,覆盖 prefill / decode / 混合三种形态 | 有预热 |

**这套设计的取向很明确:把每步的 CPU 工作压到只剩「算索引 + 下发 kernel」,其余全部推到 GPU 上用 kernel 做。**

代价也已经在前面出现过两次:**多了一层间接寻址**(3.7),以及**两套运行器并存**带来的实现分叉(1.4、1.49)。前者是可读性成本,后者是维护成本。

### 4.2 关键参数

| 参数 | 默认 | 作用 | 往哪边拧 |
|---|---|---|---|
| `--enforce-eager` | 关 | 关掉 CUDA Graph,顺带关掉编译 | 调试时开;线上不要开 |
| `-O.cudagraph_mode` | 按平台与配置自动定 | 选三档运行时模式或两个复合档 | 一般不动,让它自动降级(1.11) |
| `-O.cudagraph_capture_sizes` | 自动生成 | 桶列表,键是 **token 数**不是请求数 | 嫌启动慢就砍;砍太狠会有更多批次退回 eager |
| `--max-num-seqs` | 128 | 并发上限,同时是输入缓冲区的请求维上界 | 见 1.28:它定的是 logits 峰值 |
| `VLLM_USE_V2_MODEL_RUNNER` | 不设 | 强制选某一套运行器 | 不设时**默认走 V2**,只有 ROCm 黑名单、缺 Triton、命中不支持特性才退回 V1(1.4) |

最后一行要特别说明:**不设这个变量时走的是 V2,不是「按白名单挑」。** 判定是一串否决而不是一份准入名单,方向很容易记反。

### 4.3 出问题先看什么

| 现象 | 先查 |
|---|---|
| 启动就 OOM | 看它崩在哪个台阶(1.33)。探测那一步崩,降 token 预算;图捕获那一步崩,砍桶数或降显存占比 |
| 启动很慢 | 桶数乘以每桶录制耗时(1.17),砍桶列表 |
| 首个请求特别慢 | 预热没跑到那条路径(1.30、1.31) |
| 结果不对,但换成 eager 就对了 | 这是 bug,不是精度差异——见 4.4 第二条 |
| 崩在图里,没有调用栈 | 用 `--enforce-eager` 关掉图再复现,拿到真正的栈 |
| 想知道图到底用上没有 | 打开可观测性配置里的图指标,它会汇报各档的命中情况 |

性能分析用专门的 profiler 环境变量导出 trace,再用外部工具分析 kernel。

### 4.4 常见误区

| 误区 | 真相 |
|---|---|
| CUDA Graph 总是更快 | 不。prefill 阶段形状变化剧烈,要么开一堆桶、要么频繁退回 eager,白付启动时间与显存 |
| **batch 越小,图的收益越小** | **反了。** batch 越小,GPU kernel 越快、下发占比越高,图的收益**越大**(1.7 那张比值表) |
| eager 模式更精确 | 不。两种模式算出的结果应当相同;有差异就是 bug,不是可接受的精度差 |
| 桶列表越细越好 | 不。每个桶都要录一次(启动慢),而且各占一份图元数据 |
| 预热可以省略 | 不。编译与自动调优会在首个请求上一起爆发(1.30、1.31),而且探测不跑就没法定 KV cache 大小(1.25) |
| 图管理器持有一组静态缓冲 | 不。静态缓冲就是那批常驻的输入缓冲区,重放前**没有**额外的搬运(3.9) |

第二条最值得记住,因为它和直觉正好相反:**图省的是下发,不是计算**,而 batch 越小,下发在总耗时里占的比重越大。
