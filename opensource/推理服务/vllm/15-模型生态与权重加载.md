# vLLM 15|模型生态与权重加载

磁盘上是一堆按训练时的模块结构存下来的 `.safetensors` 文件,GPU 上要的是能直接喂给 kernel 的张量。这一章讲清中间那段路:引擎怎么从一个架构名找到实现类,怎么把 checkpoint 里的名字和形状翻译成自己要的样子,以及那十几种加载格式背后到底是几个加载器。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 加载不是「把文件读进显存」这么简单

如果 checkpoint 里存的东西和引擎要的东西长得一样,这一章就不存在了。实际上两边在五个维度上都对不上,每一条都逼出了一个设计:

| 痛点 | 具体表现 | 本章在哪里解决 |
|---|---|---|
| **名字对不上** | checkpoint 按训练时的模块结构存,引擎为了少几次 kernel 启动把几个权重融合成一个 | 1.6、1.11–1.13 |
| **形状对不上** | 权重要按张量并行切开,每张卡只拿一段 | 1.9,切法本身见 09 章 |
| **读法不对就 OOM** | 一次性读进内存再整体赋值,内存峰值是权重的两倍 | 1.7 |
| **存进去不等于能算** | kernel 要求的排布和 checkpoint 里的排布是两回事 | 1.10 |
| **找实现类的代价** | 用户只给一个架构名字符串,而为了找这一个类去导入全部模型文件,既慢又会污染 CUDA | 1.14–1.21 |

前四条是同一件事的不同侧面:**checkpoint 是按「训练时怎么存」组织的,引擎要的是「kernel 怎么读最快」**。第五条是另一条线——在碰权重之前,引擎得先知道自己要建的是个什么模型。

### 1.2 先说清要加载的是什么

一个 HuggingFace 模型目录里,和加载有关的只有几样东西:

| 文件 | 作用 |
|---|---|
| `config.json` | 模型结构描述。`architectures` 字段就是 1.14 起要查的那个架构名 |
| `model-0000N-of-0000M.safetensors` | 权重本体,切成多个文件只是为了单文件不要太大 |
| `model.safetensors.index.json` | 「哪个张量在哪个文件里」的索引,让加载器可以只读需要的那几个文件 |
| `generation_config.json` | 生成默认参数,加载权重时用不到 |
| `original/` | 模型作者放的原始格式,默认忽略 |

几个词先钉死,后面每一节都在用:

- **张量**:一个多维数组加一个 dtype。
- **state_dict**:PyTorch 的约定,「参数全名字符串 → 张量」的字典。全名用点分隔模块层级,和属性访问路径一一对应。
- **safetensors**:文件头是一段 JSON,记录每个张量的名字、dtype、形状,以及它在文件里的字节区间;文件头之后是裸的二进制数据,紧密排列,没有任何编码。
- **`.bin` / `.pt`**:PyTorch 老格式,本质是 pickle。反序列化时会执行 pickle 流里的指令,所以既慢又有安全风险——可以构造恶意 checkpoint 执行任意代码。

### 1.3 「分片」这个词在本章有两个意思

这一条单独列出来,因为它是本章最容易读岔的地方:

- **文件分片**:把 30GB 权重切成 4 个文件,纯粹为了单文件不要太大,和并行没有任何关系。
- **张量并行分片**:把一个大权重按行或列切成若干份,每张卡各持有一份。

后文凡是指文件的地方都会写明「文件」,其余的「分片」一律指张量并行那一种。

### 1.4 safetensors 快在能被内存映射,不在压缩

它不压缩。它的优势来自两件事凑在一起:**每个张量的字节区间在文件头里写明了,而且数据是裸排列的**。于是读一个张量只需要知道它的起止偏移,直接从映射区间里取那一段。

内存映射是操作系统提供的能力:把文件的一段直接映射进进程的虚拟地址空间,**并不实际读盘**;只有当程序真的去访问某个地址时,才触发缺页中断,由内核把对应的页从磁盘搬进物理内存。

这一条的推论很反直觉,但它是后面理解几种读取策略的基础:**打开一个 100GB 的 safetensors 文件几乎是零成本的**,真正的 IO 发生在逐个张量拷贝的时候。所以「加载慢」这件事该归因到哪一步,不能靠「打开文件花了多久」来判断。

### 1.5 贯穿全章的例子

后面每一节都回到这个例子:一个两层的 TinyLlama,Llama 架构,隐藏维 2048、32 个查询头、头维 64、4 个 KV 头、中间维 5632、词表 32000、bf16,用张量并行度 2 起服务。

checkpoint 里第 0 层长这样:

| checkpoint 张量名 | 形状 | 字节数 |
|---|---|---|
| `model.embed_tokens.weight` | `[32000, 2048]` | 131.1 MB |
| `model.layers.0.input_layernorm.weight` | `[2048]` | 4.1 KB |
| `model.layers.0.self_attn.q_proj.weight` | `[2048, 2048]` | 8.4 MB |
| `model.layers.0.self_attn.k_proj.weight` | `[256, 2048]` | 1.0 MB |
| `model.layers.0.self_attn.v_proj.weight` | `[256, 2048]` | 1.0 MB |
| `model.layers.0.self_attn.o_proj.weight` | `[2048, 2048]` | 8.4 MB |
| `model.layers.0.post_attention_layernorm.weight` | `[2048]` | 4.1 KB |
| `model.layers.0.mlp.gate_proj.weight` | `[5632, 2048]` | 23.1 MB |
| `model.layers.0.mlp.up_proj.weight` | `[5632, 2048]` | 23.1 MB |
| `model.layers.0.mlp.down_proj.weight` | `[2048, 5632]` | 23.1 MB |

`k_proj` 只有 256 行,是因为分组查询注意力只有 4 个 KV 头,乘以头维 64 得 256。

而 rank 0 上真实存在的张量是这样——**名字和数量都变了**:

| vLLM 参数名 | 形状 | 怎么来的 |
|---|---|---|
| `model.embed_tokens.weight` | `[16000, 2048]` | 词表按行切一半 |
| `model.layers.0.input_layernorm.weight` | `[2048]` | 归一化层不切 |
| `model.layers.0.self_attn.qkv_proj.weight` | `[1280, 2048]` | 三个张量融合后再切半,`(2048+256+256)/2` |
| `model.layers.0.self_attn.o_proj.weight` | `[2048, 1024]` | 按输入维切半 |
| `model.layers.0.mlp.gate_up_proj.weight` | `[5632, 2048]` | 两个张量融合后再切半,`(5632+5632)/2` |
| `model.layers.0.mlp.down_proj.weight` | `[2048, 2816]` | 按输入维切半 |

### 1.6 上下两张表之间发生了三件事

**改名、融合、切分**。这三件事就是权重加载的全部难点,后面所有机制都在处理它们中的某一件:

| 动作 | 例子 | 难在哪 |
|---|---|---|
| 改名 | `q_proj` → `qkv_proj` | 纯字符串映射,不难,但必须有地方声明 |
| 融合 | 三个张量拼进一个 | 一个参数要被**多次部分写入**,每次都得知道自己该写哪一段 |
| 切分 | 按并行度取其中一段 | 每张卡要的那段不一样,而 checkpoint 里只有完整的那一份 |

切分的规则——哪些权重按列切、哪些按行切、分组查询注意力下为什么按头切——属于张量并行本身,见 09 章讲切分的那几节。**本章只管一件事:一块数据到手之后,怎么找到它该写进去的位置。**

### 1.7 代价一:一次性读完,内存峰值是两倍权重

朴素做法是先把所有文件读进一个 state_dict,再整体赋值给模型。这个顺序有个硬伤:**赋值发生之前,内存里同时存在两份完整权重**——一份是刚读进来的 state_dict,一份是模型自己(它在建的时候已经分配过一遍)。

以一个 70B 的 bf16 模型(约 141 GB)为例,峰值就是 282 GB,很多机器直接就崩了。

vLLM 的做法是把权重做成一个**生成器**,逐个张量流过:加载器返回的是一个「名字加张量」的生成器,模型一边迭代一边把数据拷进已经在 GPU 上的目标参数,用完立刻释放。峰值内存因此降到**单个最大张量**的量级——本章的例子里就是那个 131 MB 的词嵌入。

这个「流式」的选择是后面很多设计的前提:**权重只能被顺序地、一个一个地看到,不能随机访问**。1.13 的标签怎么传、1.11 的递归怎么下发,都受它约束。

### 1.8 代价二:先在 CPU 建好再搬过去,白搬一趟

朴素做法建模型时,参数在 CPU 上分配并写入随机初始值,最后再整体拷到 GPU。这里有两份浪费:随机初始化真的会去算随机数,而那些值马上就要被 checkpoint 覆盖;整体拷贝又是一次完整的主机到设备传输。

vLLM 的做法是用设备上下文把模型构造过程包住,让所有参数**直接在 GPU 上分配**。配合各层构造函数里普遍使用「只分配不写值」的空张量,建模型这一步就退化成了几乎纯粹的显存分配。

同一个上下文还顺带钉住了默认 dtype,所以建出来的空壳在 dtype 和设备两件事上都已经是最终形态,不需要事后转换。

### 1.9 代价三:名字和形状都对不上,而标准接口要求严格一致

PyTorch 的标准赋值接口要求 state_dict 的键和模型参数名严格一一对应,形状也要完全相同。这在推理引擎里两条都不成立:checkpoint 里有 `q_proj` / `k_proj` / `v_proj` 三个张量,引擎里只有一个 `qkv_proj`;checkpoint 里 `q_proj` 是完整的 `[2048, 2048]`,而 rank 0 上的目标只是某个融合张量里的一段。

严格模式下这会直接抛异常。而**关掉严格模式更糟**——所有对不上的权重被静默跳过,模型带着一堆随机值加载成功,不报任何错。

所以 vLLM 放弃了这个接口,改成**每个模型自己实现一个接收权重迭代器的方法**,每个参数各自带一个回调函数,由它决定「这块数据该写到我的哪个位置」。1.11 到 1.13 讲的就是这套协议怎么运转。

### 1.10 代价四:加载完不等于能算

权重不是「存进去就完事」。以 FP8 量化为例,checkpoint 里存的是量化后的权重加一组缩放因子,而高性能矩阵乘 kernel 往往要求权重按特定的交错顺序排布、缩放因子被整理成特定形状。这些重排只能在**所有相关权重都到位之后**做——融合张量的三段没凑齐,就没法按整块重排。

于是加载流程末尾有一道统一的后处理:遍历所有模块,让每个量化方法有机会把权重改造成 kernel 需要的格式。05 章讲注意力吸收矩阵时提到的「两个解压矩阵在权重加载后就被拆出来、转置成矩阵乘友好的布局」,就是这道后处理的一个实例。

这里还有一条并列的路径值得记一笔:**在线量化有自己的收尾**。如果模型走的是加载时即量化的路子,会先走一遍逐层收尾,再进统一后处理。两者不是替代关系。

整个加载流程最后返回的是**切换到推理模式之后的模型**,这一步同样在加载器里完成,不留给调用方。

**四个代价对应四个设计:**

| 朴素做法的代价 | vLLM 的对策 |
|---|---|
| 内存峰值两倍权重 | 权重做成生成器,逐张量拷贝后立即释放 |
| 多一次完整的主机到设备拷贝 | 用设备上下文把模型构造包住,直接在 GPU 建空壳 |
| 名字和形状都对不上 | 放弃标准赋值接口,改用权重迭代器加逐参数回调 |
| 加载完 kernel 用不了 | 统一的加载后处理,把权重重排成 kernel 要的格式 |

### 1.11 三个名字空间

把上面三件事串起来看,权重加载本质是一个**三级映射**问题:

```text
[Level 1] checkpoint namespace  (HuggingFace naming, what is on disk)
    model.layers.0.self_attn.q_proj.weight    [2048, 2048]
    model.layers.0.self_attn.k_proj.weight    [ 256, 2048]
    model.layers.0.self_attn.v_proj.weight    [ 256, 2048]
        |
        |  rename + tag with a shard id
        v
[Level 2] vLLM logical namespace  (fused name + one shard id)
    model.layers.0.self_attn.qkv_proj.weight  shard_id = "q"
    model.layers.0.self_attn.qkv_proj.weight  shard_id = "k"
    model.layers.0.self_attn.qkv_proj.weight  shard_id = "v"
        |
        |  recurse down to the owning module, then call its weight loader
        v
[Level 3] physical tensor  (the actual memory on rank 0)
    qkv_proj.weight [1280, 2048]
        rows [   0, 1024)  <- q shard for this rank
        rows [1024, 1152)  <- k shard for this rank
        rows [1152, 1280)  <- v shard for this rank
```

第一级到第二级是**纯字符串操作加一个标记**:改名,然后告诉下游「这块数据是融合张量的第几段」。第二级到第三级才是真正的写入:递归找到拥有这个参数的模块,交给它自己的加载逻辑,由它按标记算出该写进哪个行区间。

映射器除了改名,还负责**跳过**:映射函数返回空就表示这个权重不要了,直接不往下传。checkpoint 里那些引擎用不上的张量就是这样被丢掉的。

### 1.12 为什么要融合

不融合的话,注意力的输入投影是三次矩阵乘,意味着三次 kernel 启动、三次把同一个输入从显存读进片上。融合之后输入只读一次,kernel 启动从三次降到一次。

这个优化在 decode 阶段最值钱:此时每个请求只有一个 token,矩阵乘退化成矩阵向量乘,计算量小到可以忽略,端到端时间几乎全是「读权重加启动开销」。按单次 kernel 启动 3 到 5 微秒的典型量级算,一个 32 层模型省下大约 256 微秒;而一次 decode 步总共可能只有 10 到 20 毫秒,**也就是省了 1% 到 2.5%**。

这个量级值得如实写出来:它是实打实的收益,但**不是数量级的改变**。融合真正的代价反而更醒目——checkpoint 的名字空间和引擎的名字空间从此不再一一对应,必须显式建立映射,也就有了这一整章。

同理,门控分支和上投影分支融合成一个权重。融合之后各段怎么切、为什么分组查询注意力下要按头切,见 09 章讲列切与行切的那几节。

### 1.13 一个「我是第几块」的标签,挂在张量上

融合之后,一个参数要被三次部分写入。写入函数必须知道「这次给我的是 q 还是 k 还是 v」,才能算出该写到行区间的哪一段。这个标签就是分片标识。

它的类型有两种:融合的 QKV 用字符串,因为分组查询注意力下 q 和 k/v 的大小不同,需要特殊计算;而普通的融合列切层用整数下标,因为各段大小由一个宽度列表直接给出。

真正有意思的是**它是怎么传下去的**——不走函数参数,而是**直接挂在张量对象上**当作一个属性。

理由是 1.7 那条流式约束的直接后果:数据要穿过递归下发的好几层才能到达目标参数,如果走参数,每一层递归都得加一个形参,而中间那些层根本不关心它。挂在张量上等于搭了个便车,**中间层一个字都不用改**。

这是本章第一次出现「因为只能顺序看到权重,所以得想办法让信息跟着数据走」这个模式,后面还会再遇到。

### 1.14 注册表要解决的问题

换一条线。在碰任何权重之前,引擎得先知道自己要建的是什么模型:用户给的是 `config.json` 里的一个字符串,比如 `LlamaForCausalLM`,引擎要找到对应的 Python 类。

这件事本身不难,难在一条约束:**不能为了找这一个类,把两百多个模型文件全部导入一遍。**

先把三个词铺平,后面的设计全绕着它们转:

- **导入**:Python 加载一个 `.py` 文件的过程。导入一个模型文件不是「读一个文件」,而是把它从头到尾**执行**一遍——定义类、执行模块级语句,并连带导入它依赖的所有模块。代价来自「执行」,不是「读盘」。
- **CUDA 上下文**:一个进程第一次调用任何 CUDA 接口时,驱动会在这个进程里建立一份 GPU 侧状态。一旦建立,它就和这个进程绑死了。
- **进程分叉**:复制当前进程产生子进程的方式。它复制的是内存快照,但驱动那一侧的 GPU 状态复制不过去。这就是「父进程碰过 CUDA,分叉出的子进程再用 CUDA 就直接报错」的根因——子进程手里拿着一份指向已失效资源的副本。

### 1.15 表里只存字符串

注册表的做法是:表的值不是类对象,而是 **「模块名加类名」两个字符串** 。类比是图书馆的索引卡——卡片上只写书在哪个书架,不会把书本身粘在卡片上。

不用装饰器注册,正是因为装饰器只有在模块被导入时才执行,而要让全部架构都注册上,就必须在启动时导入全部模型文件。那样有两个具体后果:

| 手段 | 解决的痛点 | 不这么做会发生什么 |
|---|---|---|
| 表里只存字符串 | 几百个架构挤在一张表里,一次启动只用一个 | 导入全部模型文件才能填满表,启动多花秒级时间,其中绝大多数白导 |
| 元信息探测放进子进程 | 元信息必须导入才拿得到,但主进程不能碰 CUDA | 主进程导入时若初始化了 CUDA,之后分叉出的工作进程一用 CUDA 就报错 |
| 元信息落磁盘缓存 | 起子进程加导入深度学习框架本身要一到三秒 | 每次启动都白付这一到三秒,短生命周期的服务尤其难受 |

三者是串起来的:**因为要惰性,元信息就没现成的;因为要探测元信息又不能污染主进程,就得起子进程;因为子进程贵,就得缓存。**

> 这里的「惰性」说的是注册表推迟导入,和 06 章讲的 kernel 与后端的惰性初始化不是一回事。

### 1.16 但有些决策必须在建模型之前就知道

矛盾在这里:引擎在真正实例化模型之前,需要知道一堆关于这个模型类的性质——它是文本生成还是池化模型?支不支持流水线并行?是不是注意力与状态空间混合的?支不支持多模态?这些信息决定了调度器、KV cache 管理器、输入处理器该怎么配。

基准上这份元信息有 **22 个字段**,覆盖生成还是池化、注意力类型、默认池化方式、多模态的几种变体、流水线并行、内部状态、混合架构、语音转写、视频剪枝方法等等。

问题是这些性质**只能通过检查类的继承关系和类属性得到**,而要得到类对象就必须先执行定义它的那个 `.py` 文件。惰性和「需要元信息」就这样卡死了。

### 1.17 为什么「知道类的性质」非导入不可

很容易觉得:判断一个模型支不支持流水线并行,看看名字或者读个配置表不就行了?

实际不行,因为这些性质是**用类型系统表达的,不是用数据表达的**。判断支不支持流水线并行,查的是这个类有没有实现对应的协议(有没有某几个特定成员);判断是不是混合架构,查的是类有没有被标注;判断支不支持多模态,查的是有没有多模态相关的方法。

这些判断的输入都是 **Python 类对象**。这就是死结的来源,而子进程是解开它的唯一低成本办法:**让那次导入发生在一个用完就扔的进程里。**

### 1.18 在子进程里导入并探测

具体做法是:父进程把「导入并探测」这件事打包成一个函数,序列化后交给一个新起的子进程执行,子进程算出那 22 个字段、写进临时文件,然后退出;父进程再把结果读回来。

序列化用的不是标准库那套,因为要传的是一个匿名函数,标准库不支持。落盘也不是写临时文件而是**先建一个临时目录再在里面写**,注释给出的理由是直接用临时文件会遇到权限问题。

关键收益在最后一步:**子进程退出时,它污染的 CUDA 上下文一起消失,父进程仍然是干净的。**

### 1.19 子进程还是太慢:按文件字节做缓存

起一个 Python 子进程加导入深度学习框架,代价在一到三秒的量级。每次启动都付这个成本不可接受,所以又加了一层磁盘缓存。

缓存的 key 是**模型源文件的内容哈希**,不是版本号。这个选择的动机是开发场景:你改了某个模型文件、给模型加上流水线并行支持,如果缓存 key 是引擎版本号,改完代码重启还会读到旧的「不支持」,表现成「我明明实现了,但命令行说不支持」——这种问题极难查。用字节哈希,改一个字符缓存立刻失效。

代价是每次启动都要读一遍模型文件算哈希,但那只是几十 KB 的顺序读,比导入便宜两个数量级。

哈希的算法本身有个容易忽略的细节:如果模块入口是包的初始化文件(包形式的模型),哈希会**覆盖整个包目录下所有 `.py` 文件**。注释写明了理由——包的入口文件往往只是重新导出,真正的实现在子模块里,只哈希入口文件就漏了。

写缓存走的是原子写,所以多个实例同时启动不会把缓存文件写坏。

### 1.20 这一到三秒到底付几次

结论是首次启动付一次,之后命中缓存。但 **「一次」的单位不是「一个模型」** ,容易估错,所以把粒度拆开:

缓存文件名由**模块名和类名**拼出来,点号换成横杠。所以首次跑 TinyLlama 付了这一到三秒之后,再跑任何别的 Llama 微调版、任何架构名相同的模型,**全部是缓存命中**——它们共用同一个模型文件,哈希一样。付费单位是「每个架构一次」,不是「每个模型一次」。反过来,第一次跑一个多模态模型会再付一次,因为那是另一个文件。

同一次启动内还有第二层内存缓存:探测函数上挂了一个容量 128 的缓存装饰器,所以一次启动里多处问同一个架构,只真正探测一次。

失效条件只有一个:那个 `.py` 文件的字节变了。因此升级引擎版本、或自己改了模型文件,升级后的第一次启动会重新付一次。这正是上面说的「宁可多付一次,也不能用陈旧元信息」的取舍。

**这一到三秒在总启动时间里通常不是主要成本。** 它只覆盖元信息探测这一段,权重读取、加载后处理的量化重排,以及图捕获都在它之外,量级往往是几十秒到几分钟。看到「首次启动慢」先别归因到这里。

容器和短生命周期场景要多留意一句:仓库和发行包里都**不预置**这个缓存目录,所以每个新建的容器、新的持续集成作业第一次跑某个架构都会重新付一次。把缓存目录挂成持久卷或者在构建镜像时预热一遍就能消掉它——**这条是推论,源码里没有写这种用法**;能这么做的依据是缓存 key 只由文件字节决定,不含机器或路径以外的信息,因此跨机器可复用。

一个对照:如果用类对象的形式注册树外模型,元信息在注册那一刻就地算出来,既不起子进程也不用磁盘缓存。代价是主进程已经导入了你的模型模块,重新暴露在 CUDA 污染风险下——这就是那个注册接口的文档建议改用字符串形式的原因。

### 1.21 注册表实测长什么样

基准上,这张表由 10 张分类表合并而成:

| 分类表 | 条目数 | 含义 |
|---|---|---|
| 文本生成 | 125 | 纯文本生成 |
| 多模态 | 120 | 图文、视频、语音 |
| 推测解码 | 61 | 草稿模型与多 token 预测头 |
| 向量化 | 33(运行时 39) | 向量化与池化模型 |
| 明确走后备实现的架构 | 13 | — |
| 后期交互检索 | 11 | — |
| 序列分类 | 10 | 分类与重排序 |
| 后备实现的入口类 | 10 | — |
| token 级分类 | 6 | 命名实体识别等 |
| 奖励模型 | 3 | — |

字面键相加 392,**去重后是 383 个唯一架构名**,指向 262 个不同的模块。跨表重复的架构名有 15 个,大多是同一个架构既能做生成又能做向量化。

向量化那一行的两个数字要解释一下:它除了 33 个字面写出的键,还带一段推导式,把文本生成表里所有实现类为 Llama 的条目(6 条)也并进来,注释写的理由是「多个模型共用同一个架构」。所以它运行时是 39 条。这 6 个键本来就在文本生成表里,**所以去重后的 383 不受影响**。

表的值是那对「模块名加类名」的字符串,不是类对象——这就是 1.15 说的惰性注册在数据结构上的样子。

### 1.22 从架构名到类:六步,顺序本身就是策略

有了表还不够。用户给的架构名可能不在表里、可能带任务后缀、也可能根本没有原生实现,所以解析是一条有先后的尝试链,**顺序本身携带策略**:

| 步 | 条件 | 做什么 |
|---|---|---|
| ① | 用户强制指定走 Transformers | 直接解析成通用壳子,成功即返回 |
| ② | 用户强制指定地球观测那一族 | 直接解析成固定的那个架构名 |
| ③ | 所有架构名都不在表里,且模式为自动、不做任务转换 | 试一次 Transformers 后备 |
| ④ | **主路径** | 逐个架构名归一化后查表,真正导入 |
| ⑤ | 还是没有,且模式为自动 | 再试一次 Transformers 后备 |
| ⑥ | 全败 | 抛出分类错误 |

①和②是互斥的两支(前者不成立才看后者)。③和⑤都是 Transformers 后备,区别在**它们站在解析任务类型的哪一侧**:③在任务转换类型已定之后,⑤在执行器类型定下来之前。两次都试,是因为中间那次主路径可能会顺带把这些属性解析出来,状态变了就值得再问一次。

一个容易忽略的细节:④ 成功时返回的是**原始架构名,不是归一化之后的**。归一化只服务于查表,对上层而言这个模型仍然叫它在 `config.json` 里的名字。

### 1.23 归一化:把任务后缀换回基础后缀

这一步处理一类很实际的情况:用户想把一个生成模型当向量化模型用,命令行给了对应的任务参数,于是引擎内部把架构名当作带任务后缀的变体去查表——而表里只有基础版本。

做法是先看架构名能不能匹配上某个已知的任务后缀;匹配上了,就**遍历所有已知后缀逐个替换、逐个查表**,哪个换出来的名字在表里就用哪个。不是「一律换回生成模型的后缀」那种单向映射——已知后缀有好几种,谁能命中事先并不知道。

找到基础实现类之后,再由加载器那一侧按任务转换类型包一层适配器:不转换就原样放行,要向量化就换掉输出头改成池化,要分类就换成序列分类的头。第四种情况会直接触发穷尽性断言——**新增一种任务类型而忘了在这里加分支,是编译期就能发现的错误,不是运行时静默走空**。

### 1.24 Transformers 后备:没有原生实现也能跑

如果引擎没有某个架构的原生实现,它会尝试用一个通用壳子去包装 Transformers 库里的实现。判定依据是模型配置里的远程代码入口,以及那个类自己声明的后端兼容性检查。

命中时会打一条警告,说这个架构没有原生实现、正在回退、部分特性可能不支持、性能可能不是最优。

这里有个讲稿容易漏掉的条件:**警告只在模式为自动时才打**。用户显式指定要走 Transformers 时不打——那是他自己要的,不是回退。

这条路能跑通,但通常拿不到全部优化:融合 kernel、部分并行策略、部分量化后端都用不上。

### 1.25 三种「不支持」,加一个兜底

同样是「不支持」,原因可以完全不同,所以错误也分了类:

| 情况 | 报错在说什么 |
|---|---|
| 架构名在表里,但探测失败 | 实现是存在的,导入或检查时出错了——**去日志里看真正的异常** |
| 架构名在「曾经支持过」的名单里 | 某个版本删掉了。报错会给出最后支持它的版本号 |
| 架构名在「已挪到插件」的名单里 | 实现搬去了独立仓库,报错直接给出插件地址 |
| 都不是 | 兜底:这个架构确实没听说过,报错附上全部支持的架构名 |

基准上前两张名单分别有 50 条和 4 条。

这个设计值得学:**把「删除」变成有信息量的错误**。用户看到「支持到某个版本为止」就知道该降版本还是该换模型,而不是对着一句「不支持」干瞪眼。第四条兜底才是最常见的那一类,前三条是把「其实有线索」的情况从里面摘出来。

### 1.26 加载协议的第一层:模型级

回到权重这条线。1.9 说过引擎放弃了标准赋值接口,那它用什么替代?答案是**两层回调**。

第一层在模型类上:每个模型实现一个方法,接收「名字加张量」的可迭代对象,返回一个集合,记录「我实际成功加载了哪些参数名」。

这个返回值不是装饰性的。

### 1.27 完整性校验:没被填过的参数要报出来

加载器拿那个集合去做完整性校验:把模型的全部参数名减去已加载的集合,**差集非空就直接抛异常,并列出是哪些参数**。

这正是 1.9 里第三个代价的解药。关掉严格模式会静默跳过对不上的权重,而这里会明确报出哪些参数没被 checkpoint 填过——**同样是「不一一对应」,一个装作没事,一个指着名字告诉你**。

默认开启的条件是两条:非量化模型,**且**模型返回了非空的集合。第二个条件是必要的:如果某个子模块的方法返回空,上层就不知道那棵子树加载了什么,校验会全面误报。

### 1.28 校验的两个逃生舱

**第一个是量化白名单。** 强制开启校验对量化模型也基本安全,因为校验里有一段白名单:凡是所在模块的量化方法带「用假设备占位」或「加载后要后处理」标记的,它底下的参数名会被**直接塞进已加载集合**视为加载完毕。这样在线量化的缩放因子、KV cache 的缩放因子这类「checkpoint 里本来就没有、后处理才产生」的参数不会被算成缺失。

默认对量化模型关掉,是因为白名单只覆盖得住「挂在带量化方法的模块下」这一类,覆盖不全的量化格式仍可能误报。

**第二个是给多 token 预测草稿模型的。** 有一个专门的小模块提供一对开关函数,这类模型自己的加载方法在做完整性断言前会先问一句这个开关;而权重同步的两条传输通道会用它把检查关掉——**增量同步天然不会一次给齐全部权重**,拿全量校验去卡它必然误报。多 token 预测本身见 08 章 1.17。

### 1.29 第二层:参数级的回调

每个参数对象上可以挂一个回调函数。加载器按名字定位到参数之后不直接拷贝,而是取出这个回调、把数据递给它。取不到就用一个朴素的默认实现:断言形状相同,然后拷贝。

注意这条路径**只传两个参数,没有分片标识**。而 1.13 说过融合层恰恰需要它,所以融合层不走这条路——它们各自定义了**模块级**的加载方法,由 1.35 的第二条分支把整个子流交给它们;这两个方法从张量属性上取回分片标识,再补成第三个实参传给回调。

**这就是 1.13 那个「挂在张量上搭便车」的兑现处**:中间所有递归层的签名都没变,而信息准确地到达了需要它的那一层。

### 1.30 回调家族

真正干活的是各个并行层自己的实现:

| 回调 | 干什么 |
|---|---|
| 默认实现 | 形状必须相等,直接拷贝。归一化层这类不切分的参数用它 |
| 行并行 | 沿第 0 维取本 rank 那一段 |
| 按轴切分的工厂 | 返回一个按指定轴切分的回调 |
| 组合装饰器 | 先用某个回调装入,再对结果套一个变换,例如加载缩放因子后取倒数 |
| 列并行层的实现 | 按输出维切 |
| 融合列切层的实现 | 融合加切分加量化偏移修正 |
| 融合 QKV 层的实现 | 同上,但三段大小不等,用字符串标识 |

这个「把函数挂在数据上」的设计,解决的问题是:**加载器不需要知道任何并行策略或量化格式的知识**。它只负责「按名字找到参数、把数据递过去」;怎么切、怎么对齐、量化后偏移怎么换算,全封装在参数所属的那个层里。新增一种并行方式或量化格式,不用改加载器一行代码。

切法本身(列切、行切、按头切)见 09 章 1.7 与 1.8。

### 1.31 一次完整的调用链

用 1.5 的例子走一遍:rank 0 加载 `k_proj`。

```text
checkpoint yields: ("model.layers.0.self_attn.k_proj.weight", tensor[256, 2048])
    |
    |  WeightsMapper.apply()   maps ".k_proj" -> (".qkv_proj", "k")
    v
("model.layers.0.self_attn.qkv_proj.weight", tensor[256,2048] with .shard_id="k")
    |
    |  AutoWeightsLoader._load_module recurses:
    |      model -> layers -> 0 -> self_attn -> qkv_proj
    |  qkv_proj defines its own load_weights, so the whole substream goes to it
    v
QKVParallelLinear.load_weights
    |  shard_id = getattr(loaded_weight, "shard_id", None)   -> "k"
    |  param    = self.weight                                -> shape [1280, 2048]
    v
QKVParallelLinear.weight_loader(param, loaded_weight, loaded_shard_id="k")
    |  offset = num_heads   * head_dim / tp = 2048 / 2 = 1024
    |  size   = num_kv_head * head_dim / tp =  256 / 2 =  128
    |  take this rank's half of loaded_weight: [0:128] on rank 0
    v
param.data.narrow(0, 1024, 128).copy_(slice)
```

偏移 1024 是 q 段在融合张量里占掉的宽度,长度 128 是 k 段在本 rank 上的宽度——两个数都能在 1.5 的目标形状表里对上。

### 1.32 改名的六种规则

映射器是一个有六个字段的数据类,每个字段都是「匹配 → 替换」的映射表,**按固定顺序依次施加**:

| 顺序 | 字段 | 匹配方式 | 典型用途 |
|---|---|---|---|
| 1 | 结构化重命名 | 规则对象 | 复杂的层级重排 |
| 2 | 正则 | 搜索后替换 | 带编号的批量改写 |
| 3 | 子串 | 包含则替换一次 | 最常用,例如把注意力模块改名 |
| 4 | 融合 | 包含则替换,**并且返回分片标识** | QKV 与门控上投影的融合 |
| 5 | 前缀 | 以此开头 | 去掉或加上顶层前缀 |
| 6 | 后缀 | 以此结尾 | 改结尾,例如把某个参数名换成标准写法 |

**值为空表示丢弃这个权重**,每一种匹配方式都支持。这是处理「checkpoint 里有但推理不需要」的标准手段。

两个映射器可以合并,量化场景用得上:模型自带的映射器需要和量化配置提供的 KV cache 缩放因子映射器合在一起用。

### 1.33 有一处需要「没融合过的名字」

这是个容易忽略的细节。LoRA 和量化配置看的都是**未融合**的名字——适配器里挂的是原始投影的名字,量化配置的忽略名单也是按 checkpoint 命名写的。

所以映射器另有一个只保留「改名」语义的变体,它做两件删减:丢掉融合规则,让分量名活下来不被改写成融合名;以及把所有映射到空的规则一并删掉。

第二条的理由写在文档字符串里,很讲究:**对「只给模块命名、不真的加载权重」的消费者来说,「这个权重别加载」是没有意义的指令**;如果照搬,会静默地缩小量化配置的忽略名单,或者让适配器的名字解析失败。量化侧的忽略名单见 11 章讲哪些层默认不量化的那一节。

### 1.34 一次遍历,递归下发

递归加载器的职责是把一个**扁平的**「名字加张量」流,分发到模型的**树状**模块结构里。

核心技巧是按第一段前缀分组:把名字在第一个点处切成两段,按第一段分组,同属一个子模块的权重打包成一个子流,递归传给那个子模块;子模块再切一层,如此直到叶子参数。

这里有个隐含的强前提:**分组只合并相邻的相同键**,所以权重流必须是「按前缀聚集」的顺序。safetensors 的文件分片天然满足(同一层的权重都在同一个文件里、且按名字排序)。如果喂进一个乱序的迭代器,同一个模块会被访问多次——**功能上仍然正确,不会漏权重**,只是每次都要重新取一遍子模块清单,多了重复开销。

这是本章第二次出现流式约束的后果:1.7 说权重只能顺序看到,这里说**顺序还得是对的**。

### 1.35 分发的五条优先级

| 优先级 | 命中什么 | 做什么 |
|---|---|---|
| ① | 这一层不在本 rank 上的占位模块 | 整段丢弃 |
| ② | 模块自定义了加载方法,且不是根模块 | 把整个子流交给它 |
| ③ | 前缀命中子模块 | 递归 |
| ④ | 前缀命中子参数 | 先查能不能跳过,否则调参数级回调 |
| ⑤ | 都不命中 | 依次查能不能跳过、在不在容忍前缀与后缀里,否则抛错 |

②是**逃生舱**:像混合专家层、多模态视觉塔这类需要特殊处理的子模块,可以自己接管整棵子树。1.29 说的融合层走的也是这一条。

「且不是根模块」这个限定是必要的:这个方法通常就是在模块自己的加载方法里被调用的,不排除根模块会无限递归。

⑤的报错信息包含了**该模块下所有可用参数名**,排障时非常有用——不是「找不到」,而是「找不到,这里有的是这些」。

### 1.36 权重绑定:同一块存储不能写两遍

输出头和词嵌入在绑定时是**同一个参数对象**,两个不同的名字指向同一块存储。如果两个名字都照常加载,同一块存储会被写两遍。

识别的办法是遍历所有词嵌入模块,用对象标识去重:第一个被遍历到的名字记为正名,其余名字记进一张别名表,值是它所指向的正名。

有了这张表,加载时有两处配合:

- **进递归之前先把别名对应的权重过滤掉**,并记下来。这样同一块存储不会被写两遍——写两遍不只是浪费,如果 checkpoint 里两个张量内容不一致,还会静默产生错误结果。
- **加载结束后核对**:被跳过的别名,它指向的正名是否真的被加载了。如果 checkpoint 里只有输出头而没有词嵌入,那么跳过输出头会导致这块存储根本没被写入,**必须报错而不是静默出错**。

第二条是整个机制的关键。去重本身容易想到,「去重之后要验证留下的那个真的被填了」才是难的部分。

这和 08 章 1.18 讲的草稿模型与目标模型共享权重不是一回事:那里是两个模型之间共用,这里是同一个模型内部两个名字指向同一块存储。

### 1.37 两个默认丢弃项

递归加载器内置了两个默认丢弃:

- **旋转位置编码的缓存**。一个映射器把频率表与预先算好的正余弦缓存统统映射成空。部分量化工具的产物里会带这些,而引擎自己算频率表,不需要它们。注意丢弃是**通过映射机制而不是一份名字黑名单**做的——和 1.32 是同一套机制,没有第二条并行的路。
- **偏置后缀**默认加入容忍后缀,注释说明理由是某类量化模型常带全零偏置。

### 1.38 十五个格式名落到七个类

命令行的加载格式有 15 个合法取值,映射表把它们指到 **7 个加载器类**。数量对不上是因为其中 8 个格式名都落到同一个默认加载器——**它们的区别只在「匹配哪些文件」和「用哪个权重迭代器」,不需要独立的类**。

| 格式名 | 加载器 | 区别在哪 |
|---|---|---|
| 自动(默认) | 默认 | 先探测有没有合并格式的文件,有则按那一套,否则按标准布局 |
| 标准 HF | 默认 | 匹配 safetensors 与两种老格式 |
| safetensors | 默认 | 强制 safetensors,不回退 |
| pt | 默认 | 老格式,走 pickle |
| 缓存为 numpy | 默认 | 首次加载转成 numpy 落盘,后续直读。只支持老格式 |
| mistral | 默认 | 合并格式,索引文件名也不同 |
| 快速 safetensors | 默认 | 依赖外部库,支持绕过 CPU 直接盘到显存 |
| 即时张量 | 默认 | 分布式加载加流水线预取加直接 IO |
| 随机值 | 假加载器 | 不读盘,填随机值。性能测试与持续集成用 |
| tensorizer | 对应类 | 对象存储友好 |

### 1.39 自己注册一个加载器

映射表之外还有一个注册入口,提供插件点:装饰一个自定义类,就能用一个新的格式名把它挂进映射表。注册时会检查是不是基类的子类;覆盖已有格式名会打警告但允许。

### 1.40 每个加载器的额外配置各不相同

有一个通用的额外配置字段,类型是字典,但**每个加载器都严格校验自己的白名单并对未知键报错**,不是随便传的:

| 加载器 | 允许的键 |
|---|---|
| 默认 | 是否多线程、线程数、是否强制开启完整性校验 |
| 预分片 | 文件名模式 |
| 流式读 | 是否分布式、并发度、内存上限 |
| 假加载器 | 无,传任何东西都报错 |
| tensorizer | 整个配置对象,不是普通字典 |

默认加载器还有一条互斥校验:多线程开关和读取策略不能同时用非默认值,因为多线程迭代器根本不看策略参数。这里没有静默忽略而是直接报错——**「静默丢弃用户的配置」是最难排查的一类 bug,宁可报错**。

### 1.41 加载时间拆成四段

「加载慢」是个笼统的说法。拆成四段才能对症下药:

$$
T_{\text{load}} = T_{\text{meta}} + T_{\text{read}} + T_{\text{H2D}} + T_{\text{post}}
$$

以一个 70B bf16 模型(约 141 GB)在单机 8 卡、并行度 8 下为例,**以下全是量级参考,不是本仓库实测**:

| 分量 | 含义 | 典型量级 |
|---|---|---|
| 元信息 | 解析配置、查表、建空壳模型 | 1 到 5 秒(首次可能再加子进程探测的那一到三秒) |
| 读盘 | 磁盘或网络到主机内存 | **主要瓶颈**,见 1.42 |
| 主机到设备 | 内存到显存的拷贝 | 每卡约 17.6 GB,按实测 20 GB/s 算约 0.9 秒 |
| 后处理 | 量化重排等 | bf16 模型近似为零;需要重排的量化格式可能几秒到几十秒 |

1.20 说的「首次启动慢先别归因到元信息探测」,在这张表里有了位置:它只是第一行的一部分。

### 1.42 读盘那一段:每个 rank 都要读一遍全部

推导读盘时间要先注意一个关键点:**并行度为 8 时,8 个工作进程各自都要读一遍全部 141 GB**。

原因在 1.4:safetensors 的读取粒度是**张量**,不是张量的一部分。每个 rank 需要的是每个张量的一段,但它拿不到「张量的一段」这个粒度,只能整个读进来再切。所以聚合读取量是 8 乘以 141,约 1128 GB。

$$
T_{\text{read}} = \frac{N_{\text{rank}} \times S_{\text{ckpt}}}{B_{\text{storage}}}
$$

| 存储介质 | 有效带宽 | 读盘时间(1128 GB) |
|---|---|---|
| 本地 NVMe,顺序读 | 6 GB/s | 188 秒 |
| 本地 NVMe,第二次启动命中页缓存 | 约 50 GB/s 以上 | 23 秒 |
| 100 GbE 网络文件系统,顺序 | 10 GB/s | 113 秒 |
| 同上,退化成随机小块读 | 0.5 到 2 GB/s | **560 到 2256 秒** |

最后一行是后面那套读取策略存在的全部理由。

### 1.43 为什么网络文件系统上会退化成随机小块读

内存映射模式下,取一个张量触发的是**缺页驱动的按需读**。对本地 NVMe,内核的预读机制会把顺序访问识别出来,批量取整片;但网络文件系统客户端的预读效果差很多,而且有三件事叠在一起:

- 引擎逐个张量读取的顺序,**不一定和张量在文件里的物理排布顺序一致**——后者由保存时决定;
- 并行度 8 时有 8 个进程并发访问同一批文件;
- 每次访问只要那一个张量的字节区间。

在服务端看来,这就是**大量并发的、不连续的小请求**,吞吐远低于顺序读。

### 1.44 四种读取策略

策略的合法取值有四个,加上「没设置」这个默认状态,一共五种行为:

| 取值 | 机制 | 主机内存开销 | 适用 |
|---|---|---|---|
| 未设置(默认) | 内存映射加**自动判定要不要预取** | 低 | 交给引擎决定 |
| 惰性 | 纯内存映射,明确禁止自动预取 | 低 | 本地 NVMe,或想要最低内存占用 |
| 急切 | 整个文件读进内存再解析 | 等于单文件大小 | 网络文件系统且内存充裕 |
| 预取 | 后台线程按 16 MB 块顺序读一遍全部文件 | 等于全部 checkpoint 大小,但在页缓存里,可被内核回收 | 网络文件系统首选 |
| 重建子类 | 读入后重建某量化库的张量子类 | 中 | 该量化格式专用 |

### 1.45 预取:不改主路径,只把数据焐热

预取的巧妙之处在于它**不改变主加载路径**,只是「在旁边偷偷把数据预热到页缓存」。主线程的内存映射读取遇到已在页缓存的页时,缺页中断变成不需要碰盘的那一种,速度接近内存拷贝。而它把随机小读变成了后台的**顺序大块读**,块大小 16 MB。

预取实现本身还做了 rank 分工:8 个 rank 各预取八分之一的文件(按 rank 做切片、步长为总数)。因为**页缓存是整机共享的**,rank 0 预热的文件 rank 3 也能受益,所以总的预取工作量还是 141 GB 而不是 1128 GB。

这是本章最漂亮的一处优化:1.42 那个「每个 rank 都要读一遍」的放大系数,在**预热这一侧被完全消掉了**——因为预热的产物是共享的,而读取的产物不是。

### 1.46 默认档的自动判定

不设策略时,迭代器自己决定要不要预取,判据两条:文件系统是不是网络类型(认三种),以及 checkpoint 总大小是否不超过可用内存的 **90%**。

四个分支各有各的行为:

| 网络文件系统 | 装得下 | 行为 |
|---|---|---|
| 是 | 是 | **自动开预取** |
| 是 | 否 | 打警告说明跳过自动预取,并报出两个数 |
| 否 | 是 | 打提示说明本地文件系统不自动预取,想强制开就加参数 |
| 否 | 否 | 同样不预取 |

两个细节:判定文件系统类型时**只检查第一个文件**,注释说明了理由——所有分片在同一目录,因此同一文件系统;它用**最长挂载点前缀匹配**,和内核决定路径归属的规则一致。取可用内存时,在某个平台上会额外读容器的资源限制取较小值,因为容器里读到的系统可用内存报的是宿主机的值。

### 1.47 多线程加载是另一条路

多线程开关走的是另一个迭代器,机制完全不同:若干线程各自把整个文件读进内存(**不是内存映射**),主线程按完成顺序消费。

实现里有个值得看的地方:提交任务用的是**生成器表达式而不是列表**。注释写明了理由——写成列表推导的话,所有提交会立刻全部发生,线程池排队时会有大量文件同时驻留内存。用生成器让提交也是惰性的,内存里最多约「线程数」个文件。

即便如此,峰值主机内存仍是「线程数乘以单文件大小」,比惰性模式高得多。默认线程数是 8。

### 1.48 怎么选

**以下是经验建议,不是仓库里的配置:**

| 场景 | 建议 | 理由 |
|---|---|---|
| 本地 NVMe,首次启动 | 默认 | 内存映射加内核预读已接近顺序读峰值 |
| 本地 NVMe,反复重启调试 | 默认 | 第二次起命中页缓存,读盘时间降一个数量级 |
| 网络文件系统,内存充裕 | 默认即可(会自动预取),或显式指定预取 | 随机小读变后台顺序大读 |
| 网络文件系统,内存紧张 | 急切 | 预取会被自动禁用,而急切逐文件读,峰值只是单文件 |
| 对象存储 | 流式读 | 专门做了并发范围请求 |
| 反复加载同一个并行配置的模型 | 先存成预分片,之后按预分片加载 | 每个 rank 只读自己那一份 |
| 混合专家加模型专家并行 | 确认专家过滤生效 | 见 1.49 |

### 1.49 混合专家的痛点:专家权重占八成半

混合专家模型的权重绝大部分是专家层。模块文档字符串直接给了数字:**专家通常占总权重字节的 85% 到 90%**。

专家并行模式下,每个 rank 只负责一部分专家。但朴素实现会把全部专家的权重都读一遍,然后在参数级回调里把不属于自己的丢掉——**读了成倍的无用数据**。这正好撞上 1.42 那个放大系数:本来每个 rank 就要读一遍全部,现在这「一遍全部」里还有八成半是它用不上的。

专家并行本身见 09 章 1.4。

### 1.50 在读盘之前就跳过

解法的关键是 1.4 提到的 safetensors 特性:**文件头里就有全部张量名**,可以先看名字再决定要不要取数据。所以过滤发生在取张量**之前**——名字不对就根本不读这块数据。

这是整章里「读法决定成本」这条线最干净的一次兑现:同样一个文件,先读头再挑着取,和整个读进来再挑,差的是八成半的 IO。

### 1.51 过滤的三条边界

**① 只匹配带数字编号的专家名。** 有些 checkpoint 把所有专家打包成一个三维张量,名字里没有编号。这种情况没法在文件级过滤(必须读整个张量再切),所以注释写明是**刻意放行**的。

**② 只跳过重张量,缩放因子一律保留。** 判定是名字以两种权重后缀之一结尾——注意是两个后缀,打包量化格式的那个后缀也在内。注释给了理由:**某些后端需要全部专家的激活缩放因子来算一个全局最大值**。缩放因子张量只有几 KB,全读也不心疼。这是个正确性约束,不是性能取舍。

**③ 专家负载均衡开启时整个过滤器禁用。** 注释说得很清楚:负载均衡会把热门专家在多个 rank 上冗余放置,这时某个 rank 可能需要按默认切分本不属于它的专家的权重,所以不能过滤。负载均衡本身见 09 章 1.38。

### 1.52 谁负责哪些专家

三个条件同时满足才启用:模型是混合专家、开了专家并行、开了这个过滤开关。

归属计算支持两种放置策略,注释明确说它**镜像了**融合专家层里的那份实现——两处逻辑必须一致,否则会读错专家:

- **连续放置**:按总数除以并行度分段,余数摊到前几个 rank。
- **轮询放置**:按并行度做步长,rank 0 拿第 0、第 8、第 16 个,依此类推。

还有个坑:这里的 rank 不是简单的张量并行 rank,而是**数据并行、前缀上下文并行、张量并行三维展平**之后的编号,注释里给了公式。三维中任何一维配错,算出来的专家区间就是错的,而症状是「模型能加载、输出是乱的」——不会报错。

### 1.53 过滤省下多少:一个真实的混合专家模型

用一个 6710 亿参数的混合专家模型估算:bf16 权重约 1.3 TB,专家占约 88%,专家并行度 8。**以下是按讲稿口径复算的估算,不是本仓库实测**:

| | 无过滤 | 有过滤 |
|---|---|---|
| 每 rank 读取量 | 1.3 TB | 非专家 0.156 TB 加专家 1.144/8 即 0.143 TB,合计约 **0.30 TB** |
| 8 rank 聚合读取量 | 10.4 TB | **2.4 TB** |
| 本地 NVMe 6 GB/s 下的读盘时间 | 约 1733 秒(29 分钟) | 约 400 秒(6.7 分钟) |

日志里能确认它有没有生效:启用时会打一条带并行度、rank 号和「加载几分之几专家」的信息。这条日志值得记住——**过滤没生效时症状只是「慢」,不会报错**。

### 1.54 装不下的时候:把一部分权重放在主机内存

前面所有优化都假设权重最终放得进显存。放不进怎么办?比如一张 24 GB 的卡想跑 26 GB 的权重,差一点点;或者混合专家模型的专家权重巨大,但每次前向只用到少数专家。

> 本节说的是**权重** offload,和 03 章讲的 KV cache offload 是两套独立的东西,配置、实现、时机都不同。

引擎提供两种后端,由配置选择、由一个工厂函数实例化。默认档是自动:预取那一侧的分组大小大于零就选预取,否则看零拷贝那一侧的额度大于零就选零拷贝,两个子配置都是默认值时返回一个**空实现**——零开销。

### 1.55 后端一:让 GPU 直接读主机内存

统一虚拟寻址是 CUDA 的能力:把一块**锁页内存**(被固定在物理内存、不会被换出的页)映射到 GPU 的虚拟地址空间,GPU 的 kernel 可以**直接用指针访问**这块内存,硬件在背后走 PCIe 搬数据,程序里看不到任何显式的拷贝调用。

实现上有三点值得注意:

- **逐参数决策,到额度就停。** 遍历模型参数,累计已挪出的字节数,超过配置的上限就停。所以「最多挪 10 GiB 到主机」这个参数决定的是总量,**具体哪些参数被挪由遍历顺序决定**。
- **可以按名字段选择性挪。** 配置里可以给一个「名字段集合」,只有匹配的参数才挪。匹配语义是**完整的段**:参数名里的某一段必须整个相等才算命中,写一个前缀片段是不行的。注释专门举了例子说明这样才能区分权重本身和它的缩放因子。
- **不可用时降级。** 统一虚拟寻址不可用、或者用环境变量显式关掉时,退化成把参数放在主机内存、每次前向显式搬一趟。

### 1.56 零拷贝的代价是一百倍

这一条必须写清楚,否则很容易把「零拷贝」理解成「免费」。

零拷贝省掉的是**显式的拷贝调用**,不是**数据搬运本身**。每次前向都要通过 PCIe 读那部分权重:PCIe 4.0 十六通道实测约 20 GB/s,而高端卡的显存带宽是 2 TB/s 量级——**慢一百倍**。所以配置的文档里明确警告需要快速的主机与设备互联。

代入一下:挪 10 GB 意味着每个 decode 步多花约 0.5 秒,而正常一个 decode 步是 10 到 20 毫秒。**对 decode 这是灾难性的。**

所以这条路只在「跑得动比跑得快重要」的场景有意义——本地实验、单请求调试。它不是一个吞吐方案。

### 1.57 后端二:在算这一层的时候搬下一层

预取的思路完全不同,它利用的是**计算和传输可以并行**这一点:在算第 N 层的时候,用一条独立的拷贝流把第 N+1 层的权重从主机搬到显存上一块固定的缓冲区。如果传输时间小于计算时间,延迟被完全隐藏。

配置有四个参数:

| 参数 | 默认 | 含义 |
|---|---|---|
| 分组大小 | 0(关闭) | 每 N 层一组 |
| 每组挪几层 | 1 | 每组挪**最后**几层 |
| 提前几层开始预取 | 1 | 越大隐藏得越好,但占更多显存 |
| 参数名字段 | 空集 | 同零拷贝的段匹配语义;空集表示该层所有参数 |

### 1.58 为什么是「每组的最后几层」

这个设计一眼看去很怪:为什么不是「挪前 N 层」?

因为要让被挪走的层**均匀散布**在模型中。每个被挪走的层前面都有若干个常驻层,**那些常驻层的计算时间就是可用的预取窗口**。如果连续挪一大段,预取就来不及了——前一层刚算完,下一层的权重还在路上。

这是本章少见的一处「配置项的形状本身在编码一个约束」:分组不是为了整齐,是为了保证每次预取都有足够的计算时间可以躲在后面。

### 1.59 预取的三个关键设计

**① 静态缓冲池。** 按「名字、形状、跨距、数据类型」分组,每组预分配若干个缓冲区,第 N 层用第 `N mod 容量` 个槽位,循环复用。预分配避免了每次前向都去申请显存——那会引入同步,还会造成碎片。分配时用的是保留内存布局的那种空张量构造,而不是普通的连续张量。

分组的键里**带参数名**,注释说明了理由:防止同一层内不同的参数共用缓冲区;而不同层之间的同名参数**正是靠槽位机制**共享的。

**② 双流加事件同步。** 计算流记录一个事件,拷贝流等这个事件,然后在拷贝流上发起异步拷贝,完成后记录另一个事件;消费端等这第二个事件。这是标准的 CUDA 异步编程模式。

但它和图捕获有微妙的交互,代码里专门区分了「正在捕获」和「普通执行」两条路径,还带一个兜底:事件不可用时退回到「等整条拷贝流排空」这种更粗的同步。

**③ 骗编译器。** 见下一节。

### 1.60 用一对假的数据依赖钉住同步语义

这是本章最精巧的一处实现。

预取需要在计算图里插入「等一下」的同步点。问题是:这个等待算子**实际上什么张量都没改**,它只是等一个事件。编译器看到一个没有副作用、和周围计算又没有数据依赖的算子,完全可以**把它重排到别的位置,或者直接删掉**——那预取的同步语义就没了。

解法是在注册这个自定义算子时声明「我会修改某个输入张量」。这句声明是假的,但它**强行制造了一条数据依赖链**,编译器就不敢动它了。

基准上这样的算子有**一对**:一个管等待、声明修改输入张量,一个管启动、声明修改输出张量。模块的文档字符串开门见山就写了这个手法的目的。

还有一处呼应:offload 配置的哈希函数在文档字符串里说明了为什么所有 offload 字段都要进编译缓存的哈希——因为预取后端会改写模块的前向、并往计算图里插自定义算子,**改任何 offload 设置都会改变计算图**。这两处是同一个事实的两面。

### 1.61 两种 offload 怎么选

| 维度 | 零拷贝 | 预取 |
|---|---|---|
| 数据流 | GPU kernel 直接读主机内存,按需、细粒度 | 显式异步拷贝到显存缓冲,批量、层粒度 |
| 延迟隐藏 | **无**,同步阻塞在 kernel 内 | **有**,与前面几层的计算重叠 |
| 额外显存 | 0 | 槽位数乘以单层被挪走的参数大小 |
| 实现规模 | 约 150 行 | 约 770 行,外加一个 76 行的算子模块 |
| 适合 | 应急「跑起来」,差一点点显存 | 生产环境有意识地用主机内存换显存,尤其是混合专家 |

**判断很简单:零拷贝是纯粹的减速换显存,预取是用显存和复杂度换回延迟。** 前者的额外显存是零但代价是一百倍带宽差;后者多占几块缓冲区,但只要预取窗口够,代价接近零。

### 1.62 假加载器:不读盘,但不能随便填

有一种加载格式不读盘,直接给参数填随机值。它看着像个玩具,但它是**性能基准测试和持续集成的基础设施**。

关键在于「随机值」这三个字不能打折,文档字符串说清了两条约束:

- **必须随机。** 某些硬件和 kernel 对特殊值有快路径(零值跳过、非规格化数的特殊处理),全零权重测出来的性能不真实。
- **必须是小值。** 默认区间是正负千分之一。权重随机意味着注意力打分也随机;如果权重是正负一的量级,几十层累积下来激活值会指数爆炸成无穷大,归一化之后出现非数,然后整个前向变成非数传播——**虽然不影响耗时统计,但会让「输出是否合理」这类检查全部失效**,也可能触发某些 kernel 的异常路径。

还有一条分布式一致性的考虑:用**逐参数的固定种子**,保证同一个参数在不同 rank 上生成相同的值。文档字符串还多说了一句实现原理:种子固定时,生成的随机值**只依赖参数的元素个数和数据类型**——这正是跨 rank 一致的来源。这样并行模式下各 rank 的「权重」是自洽的,不会因为随机值不一致导致规约之后的结果毫无意义。

### 1.63 填假权重的四个分支

| 情况 | 处理 | 理由 |
|---|---|---|
| 参数在**假设备**上 | 直接返回 | 留给在线量化流程去物化,见 1.64 |
| 非浮点类型 | 某个平台上清零,其他平台不动 | 注释说明该平台上整型参数保持未初始化会导致跨进程值不确定 |
| 某类加速器 | 在主机上生成再拷过去 | 注释给了两条理由:原地均匀采样在该平台上要求过多显存;而且另一个便捷函数不支持传随机数发生器 |
| 低于 16 位的数据类型 | 先转成半精度生成再转回 | 均匀采样不支持这类类型 |

第一条不是平台差异,它是下一节那条线的入口。

### 1.64 假设备与在线量化

**在线量化**指的是:checkpoint 里是高精度权重,引擎在加载过程中即时量化成低精度。这类量化方法有个特殊需求——它们不希望目标参数一开始就占着显存,因为最终存的是量化后那个更小的张量。所以它们把参数建在**假设备**上。

假设备是 PyTorch 的一种「没有实际存储」的设备:这类张量只有形状、数据类型、跨距这些元信息,**不占任何字节**。它的用途就是「先把模型结构搭出来,稍后再决定怎么分配真实内存」。

于是假加载器要分两种情况:普通层直接填随机值;在线量化层要先把假张量换成真实的显存张量、填随机值、恢复原始的参数回调,然后**主动走一遍真实的量化流程**,最后重置记账状态。这样假模式下测出来的性能才和真实的低精度部署一致——量化后的权重更小、用的 kernel 也不同。

正常加载路径上也有对应的处理,就是 1.10 提过的那条并列路径:判定方式是查任意模块的量化方法有没有声明「我用假设备」。

### 1.65 权重热重载:为什么必须分层

强化学习训练场景:训练框架用推理引擎做采样生成,每训练若干步就要把新权重推给引擎。如果每次都销毁实例重建,代价是几十秒到几分钟——还要重新做显存探测、重建 KV cache、重新捕获图,完全不可接受。

所以需要**原地换权重**。对高精度模型这不难,拷贝一下就完事。难的是量化模型:

- 显存里存的是**量化后的形态**(低精度权重加缩放因子,而且可能已经被重排成 kernel 专用的交错布局);
- 训练框架给的是**高精度权重**;
- 要把「高精度 → 量化 → 重排」这条链重新走一遍,但**不能把整个模型先恢复成高精度**——那需要两到三倍显存,直接就崩了。

解法是**按层流水线**:对每一层,先把它的量化张量记下来、参数换成假张量(零显存);等训练框架把这一层的高精度权重喂进来;物化这一层的高精度张量(只占一层的量)、量化、重排;释放临时张量,进入下一层。

**峰值额外显存因此只是「最大的那一层」,而不是整个模型。** 这是整章「分层」这个手法的第三次出现——1.7 的流式、1.57 的预取、这里的重载,都是把「整个模型」的量降到「一层」或「一个张量」的量。

### 1.66 按层流水线怎么记账

核心数据结构记录每一层的进度,基准上有七个字段:恢复用的元信息与目标设备、已加载的元素数与该层的总元素数、已收到但还没处理的权重缓冲、原来的量化张量,以及一组非持久缓冲区的名字。

最后那个字段的注释值得看:它把非持久缓冲区的名字和量化张量一起捕获,**为的是在重载过程中那个记录持久性的内部集合被改动之后,持久性信息仍然活着**。这类「把易失的元信息先抄一份」的防御,和 02 章讲的路由专家块号提前拍快照是同一个模式。

已加载元素数和总元素数的作用是判断**这一层的权重是否收齐**。因为一层里有好几个参数,而权重是一个个流进来的,必须等全部到位才能做量化和重排。计数方式是累加元素个数,达到总数就触发处理。

这是 1.7 那条流式约束在本节的又一次体现:**流式意味着你永远不知道「下一个来的是不是最后一个」,只能靠计数**。

### 1.67 包装而不是改写

实现手法是**包装每个参数原有的回调**:原回调照常执行,外面套一层记账逻辑。这样模型代码完全不用改——模型文件不知道自己正在被热重载。

同一套机制在两个地方复用:

- **记录元信息的那一步挂在建空壳模型里**,新旧两条模型构造分支各调用一处。也就是说**每次正常启动都会记一遍元信息**,为将来可能的热重载做准备。开销只是遍历一遍模块记形状和跨距,很小。
- **假加载器借用同一套物化逻辑**处理在线量化层,就是 1.64 那条路。

量化侧对这个场景的观察见 11 章讲后处理幂等性的那一段——那里从「同一个缩放因子槽会不会被写第二遍」的角度看到了同一件事。

### 2.2 safetensors 的物理布局

1.4 说的「文件头里有字节区间」具体长这样:

```text
model-00001-of-00002.safetensors
+---------+--------------------------------+---------------------------------+
| 8 bytes | JSON header (N bytes)          | raw tensor data, tightly packed |
+---------+--------------------------------+---------------------------------+
|    N    | {"model.embed_tokens.weight":  | [embed 131.1MB][q 8.4MB][k 1MB] |

|         |        [0, 131072000]},        |                 131072000       |
|         |  "...q_proj.weight": {...},    |                                 |
|         |  ...}                          |                                 |
+---------+--------------------------------+---------------------------------+
```

开头 8 字节是小端的头部长度,之后是 JSON 头,再之后是裸数据区。三件事都从这个布局直接推出来:

- **只读头就能拿到全部张量名**——这是 1.50 那个「读盘之前就跳过」成立的前提;
- **按偏移取任意一个张量**——这是内存映射按需读的前提;
- **数据区没有编码也没有压缩**——所以映射进来的字节可以直接当张量用,不需要解码这一步。

### 2.3 过滤在文件头上走一遍

用一个专家并行度 8、rank 3、连续放置的混合专家模型走读(该 rank 负责专家 96 到 127):

| 张量名 | 判定 | 结果 |
|---|---|---|
| `...self_attn.q_proj.weight` | 不是专家权重 | 读 |
| `...mlp.gate.weight` | 路由门控,不是专家权重 | 读 |
| `...mlp.shared_experts....weight` | 共享专家,名字里没有数字编号 | 读 |
| `...mlp.experts.0.gate_proj.weight` | 编号 0,不在 96 到 127 里 | **跳** |
| `...mlp.experts.0.gate_proj.weight_scale` | 不以权重后缀结尾 | 读 |
| `...mlp.experts.96.gate_proj.weight` | 编号 96,在区间里 | 读 |
| `...mlp.experts.128.gate_proj.weight` | 编号 128,不在区间里 | **跳** |
| `...mlp.experts.gate_proj.weight`(三维融合) | 没有数字编号 | 读全部 |

判定顺序就是 1.51 那三条边界的顺序:先解析编号,没编号一律放行;再看后缀,不是重张量一律放行;最后才比对区间。**三条里有两条是「放行」,只有最后一条会跳过**——这个顺序保证了任何拿不准的情况都倾向于多读而不是漏读。

### 2.4 两种 offload 的时间轴

```text
[zero-copy]  cpu_offload_gb = 10
  forward, layer L:
    GPU ====> [kernel running, reads weights straight from host memory] ==>
               ^                                            ^
               |  every access goes over PCIe (~20 GB/s)    |
               |  vs HBM ~2000 GB/s  ->  100x slower        |
               +------- the kernel stalls right here -------+
  result: no overlap at all, pure slowdown in exchange for HBM

[prefetch]  group_size = 8, num_in_group = 2, prefetch_step = 1
  compute stream:  [L4][L5][L6][L7]  ...        [L12]
                     |   |   ^   ^
                     |   |   |   +-- wait_prefetch(7)
                     |   |   +------ wait_prefetch(6)
                     |   +---------- record fork event
                     v   v
  copy stream:     [fetch L6 ][fetch L7 ]
                     ^
                     +-- runs while L4 and L5 compute; PCIe and SMs in parallel
  result: if T_copy(L6) < T_compute(L4) + T_compute(L5), fully hidden
  cost: the static buffer pool, slot_capacity copies; layer N uses slot N mod cap
```

## Part 3|机制之外:源码里额外读到的

前两部分讲清了加载**应该怎么工作**,Part 4 讲**怎么用它**。这一部分只放照着源码读下来、机制层面看不见但真实存在的细节。**前面讲过的机制,这里一概不重复。**

> 每条对应源码的哪个文件与符号,见代码索引页,正文不写。

### 3.1 一个进程里可以加载多个模型

模块的公共入口只有三个函数:拿加载器、拿模型、注册自定义加载器。前两个的签名里藏着一件事。

拿模型那个函数允许**单独传模型配置和加载配置**,而不是只用全局配置里的那一份。这是为了支持一个进程里加载多个模型:推测解码要同时加载目标模型和草稿模型(两个不同的模型配置),多模态模型的视觉塔有时也是独立的 checkpoint(不同的加载配置)。还有一个前缀参数,是给子模型加名字前缀用的。

所以 08 章讲的草稿模型、13 章讲的视觉塔,走的都是这个入口的第二条路——**加载器本身不知道自己正在加载的是主模型还是配件**。

另有一处小设计:加载格式这个字段挂了一个校验器强制转小写,所以命令行上写大写也能正常工作。

### 3.2 骨架写死在基类,子类只填一步

加载器的抽象基类只强制子类实现两个方法:下载模型和加载权重。而 1.8 到 1.10 那整条骨架——设备上下文、建空壳、调加载权重、在线量化收尾、统一后处理、切到推理模式——**全部写死在基类的模板方法里**。

这解释了 1.38 那张表为什么七个类就够:七个加载器的差异只在「权重从哪来、怎么读」这一步,前后的流程完全一致,没有任何一个加载器需要重写骨架。

四个细节:

- **加载配置里的设备可以覆盖全局设备配置。** 用途是把权重先加载到主机内存,再由别的机制搬上去;或者在没有 GPU 的环境里验证加载逻辑。
- **默认数据类型的上下文让空张量默认用半精度而不是单精度**,省一半分配。1.8 说的「顺带钉住 dtype」,省的就是这个。
- **有一个由环境变量控制的模型结构打印。** 排查「某个层的类型选错了」这类问题时很有用——这类问题的症状通常是形状对不上,而不是报错。
- **中间有一段峰值显存日志**,注释说明了目的:在线量化时加载过程中会短暂同时存在高精度临时张量和量化后张量,**峰值显存是个需要被测试覆盖的指标**。

### 3.3 建空壳时的三个机制

**① 用签名判断新旧接口。** 新式模型类的构造签名收两个关键字参数,旧式收一串分散的配置对象。判断方式是**检查构造函数的签名里有没有那两个参数名**,旧式走后面的兼容分支、逐个参数试着填,并打一条弃用警告。这个兼容分支主要服务**树外的自定义模型**——用户自己维护的模型类可能还是老签名。

**② 有一个隐式的上下文传递。** 各层的构造函数需要访问全局配置,但不想在每一层的签名里都传一遍。所以用一个上下文变量存「当前正在构造的模型的配置」,层内部自己去取。这和 1.13 那个「把分片标识挂在张量上」是同一个动机的两种解法:**都是为了不让中间层被迫转发它们不关心的东西**,一个挂在数据上,一个挂在上下文里。

**③ 量化配置要按引用拿到模型的融合映射表。** 这里有一个循环依赖:量化配置需要知道模型哪些模块是融合的,才能正确匹配它的忽略名单里那些按 checkpoint 命名写的名字;而那张融合映射表是模型类的类属性。

解决办法是把映射表**按引用**传给量化配置,文档字符串特意说明了为什么:某些模型会在实例化时根据配置动态修改这张表(不同版本的层结构不同),按引用传才能让后续的修改对量化配置生效。

文档字符串还有第三段说明这是**过渡期的临时函数**:等某个混入类被加到所有模型上之后,这个函数就可以删掉。
