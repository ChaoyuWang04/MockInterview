# vLLM 05|注意力后端

attention 是推理里最重的那个算子,而它没有一份能通吃所有硬件和所有模型的实现。这一章讲 vLLM 怎么把这堆差异关进一层抽象里,让模型代码一行都不用改。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 为什么不能只写一个 attention kernel

写 kernel 的人当然想只写一份。问题是「最优的 attention 实现」这件事至少被七个维度同时拉扯,每个维度换一档,最优解就换一个:

| 维度 | 取值 | 为什么会换 kernel |
|---|---|---|
| 硬件 | NVIDIA / AMD / Intel XPU / CPU | 指令集和内存层级完全不同,没有共用余地 |
| GPU 架构 | Ampere / Hopper / Blackwell / RDNA / CDNA | Tensor Core 的形状与异步搬运能力逐代变 |
| 模型架构 | MHA / GQA / MQA / MLA / 状态空间模型 | KV 的形状和数量级不同,有的根本不存 KV |
| 精度 | FP16 / BF16 / FP8 / INT4 | 量化后要多一步反量化,访存量也变了 |
| 场景 | prefill / decode / 两者混合 | 计算访存比差两个数量级 |
| 特性 | 滑动窗口 / 稀疏注意力 / attention sink | 改的是算法本身,不只是实现 |

七个维度的组合数就是为什么 vLLM 里躺着几十个 attention 实现。**痛点不在于实现多,而在于谁来挑。** 如果让模型代码自己挑,那么每加一个模型就要在里面写一遍「Hopper 上用这个、量化了用那个」,每加一个 kernel 又要回头改所有模型 —— 模型数和 kernel 数相乘。

vLLM 的回答是在中间切一刀:模型代码只管调用 `self.attn(q, k, v)`,**底下用哪个 kernel 它一概不知**。同一份 `llama.py` 在 FlashAttention、FlashInfer、Triton 上跑的是同一行代码。

代价是这一刀切下去之后,「谁来挑」这件事本身变成了一个需要认真设计的子系统 —— 本章余下的篇幅基本都在讲这个子系统,以及它没做到完美的那几处。

### 1.2 这一刀切在哪里:三件套的分工

抽象层不是一个类,是三个各管一段的角色。最容易读错的地方是它们的**生命周期完全不同**:

```text
  model code
     |   self.attn(q, k, v)               <- 模型代码只有这一行
     v
  Attention layer                         <- 注意力层, 持有 impl 实例
     |   q/k/v + metadata of this step
     v
  AttentionImpl                           <- 实现, 实例级, 真正调 kernel
     ^
     |   chosen at construction time      <- 构造时由 selector 定下来
     |
  AttentionBackend                        <- 后端, 类级, 从不实例化
     |
     +-- get_name()                       报名字
     +-- get_impl_cls()                   给出实现类
     +-- get_builder_cls()                给出构造器类
     +-- supports_*()                     能力声明, 供候选过滤
```

三件套各自回答一个问题:

- **后端**(`AttentionBackend`)是一个**类级别**的抽象,从头到尾不实例化。它上面**只有三个抽象方法**:报名字、给出实现类、给出构造器类。除此之外全是能力声明 —— 支持哪些 dtype、哪些 head size、能不能滑动窗口、能不能 attention sink。选择阶段只跟它打交道。
- **实现**(`AttentionImpl`)是**实例级别**的,每层一个,持有权重形状、缩放系数这些状态,真正把张量递给 kernel。
- **构造器**(`AttentionMetadataBuilder`)负责每个 step 把调度器给的东西翻译成 kernel 要的输入。

有两处分工容易想反,值得记一笔:

**metadata 的类型不是通过工厂方法拿的**,而是由构造器的泛型参数绑定的。也就是说「这个 backend 用哪种 metadata」这件事写在构造器的类型签名里,不是一个可以运行期返回的值。

**CUDA Graph 支持度挂在构造器上,不在后端上。** 一个 backend 能不能被整图捕获,取决于它的 metadata 每步形状稳不稳,而 metadata 是构造器造的 —— 责任归属是对的,但从 backend 那一侧找会找不到。

### 1.3 为什么标准路径只要一个 kernel 入口

prefill 一次算几千个 token、decode 每步只算一个,这两件事的计算访存比差着两个数量级,直觉上该有两个 kernel。vLLM 的标准路径只有一个。

**原因 02 章 2.7 已经讲透了**:decode 就是「query 段长度为 1 的 prefill」,只要 kernel 接受一个累计 query 长度数组来描述每条请求的段边界,段长 1 和段长 N 在 kernel 眼里没有本质区别;KV 侧的不连续用块表表达,也不需要另一套接口。那一节还给了混合 batch 怎么分段、decode 段走 split-KV、prefill 段走标准分块的完整走读,这里不重复。

本章要补的只有一句:**这个选择没有让复杂度消失,只是把它挪走了。** 挪到了两个地方 —— 构造器(要算出正确的段边界、每请求 KV 长度和块表)和 kernel 内部的 tile 划分(段长差异极大时负载不均,要靠 split-KV 或提前调度来补)。1.4 讲 FlashAttention 时会看到这两处代价的具体长相。

### 1.4 能力声明不是写死的常量

把「我支持 FP8 KV cache」写成一个返回 `True` 的方法,看起来是最自然的写法。FlashAttention 没这么写。

它的 FP8 判断分两段:先查一张静态的 dtype 白名单,**只有确认这个 dtype 确实是量化类型时,才去问底层的 FA 扩展模块**「你这一版编进来了吗」。attention sink 的判断是同一个形状:先确认变长接口本身可用,再问底层支不支持 sink。

为什么要绕这一圈:**FA 是一个预编译的 C++ 扩展,同一份 vLLM 装在不同机器上,编进来的 FA 版本可能不同。** 能力不是源码属性,是安装产物的属性。写成常量就会在「代码说支持、二进制里没有」的机器上直接崩在 kernel 调用处,而不是在选择阶段被干净地筛掉。

这条对读者的实际意义是:看到源码里写着支持某个特性,**不等于你这台机器上支持**。

### 1.5 FlashAttention:默认后端,一个入口四条分支

FlashAttention 出自 Stanford 的 Hazy Research(Tri Dao、Daniel Y. Fu、Stefano Ermon、Atri Rudra、Christopher Ré,2022,arXiv:2205.14135),核心是 **IO 感知的分块计算**:把 Q 乘 K 转置的大矩阵拆成能装进片上 SRAM 的小块来算,避免在显存里实例化完整的分数矩阵,显存复杂度从序列长度的平方降到线性。它是 GPU attention 的事实标准,在非 Blackwell 的 NVIDIA 卡上是优先级最高的候选。

「标准路径只有一个 kernel 入口」这句话要限定在 **dense 路径**上。实际有四组调用点,共用同一个变长函数:

| 分支 | 做什么 | 传参上的区别 |
|---|---|---|
| 主路径 | prefill、decode、两者混合,全走这条 | 直接给 KV cache 加块表,从分页缓存里读 |
| decode 上下文并行 | 把本 rank 段、跨 rank 上下文段、query 段分开算 | 给的是连续张量,两段各自返回对数和指数项再合并 |
| 编码器注意力 | 编码器或纯编码器模型 | **完全不碰 KV cache**,在更早的地方就分流了 |
| 级联注意力 | 共享前缀拆成前缀段和后缀段分别算再合并 | 分两次调用,同样靠合并函数拼回去 |

KV 的写入是**独立的一步**,不在这四条分支里 —— 由一个专门的缓存更新函数负责,里面调 reshape 加写入的 kernel。

dense 之外还有三样东西住在同一个接口文件里:稀疏注意力的两个专用函数,以及 CUDA Graph 用的那个按规格预编译变长函数的入口。FA 后端自己还挂了两个 mask 生成器 —— 多模态双向前缀用一个,滑动窗口用另一个 —— 它们作为参数注入同一个变长调用,而且是**二选一不是并存**。

所以更准确的说法是:**dense 路径一个入口,稀疏和图捕获各有自己的入口,mask 变化靠参数注入而不是换 kernel。**

### 1.6 DiffKV:它不是 FlashAttention 的 FP8 版本

这是最容易望文生义的一个变体。

标准 FlashAttention **自己就支持 FP8 KV cache**(见 1.4 那条两段式判断),K 和 V 同构的量化场景根本不需要换后端。

DiffKV 存在的理由是 **K 和 V 形态不一致**:两者的 head size 不同,或者 dtype 不同。标准 FA 假定 K/V 对称,把它们打包进同一个内容维度;一旦不对称,这个假定就塌了。典型场景是把 K 和 V 压到不同精度或不同维度的模型。

FA 和 Triton 各有一个 DiffKV 变体,共用同一套思路。**判断要不要用它,看的是 K 和 V 像不像,不是看精度高不高。**

### 1.7 FlashInfer:和 FlashAttention 正好相反的取舍

FlashInfer 是推理专用的注意力引擎(Zihao Ye 等主导,华盛顿大学牵头,CMU、NVIDIA 与 SGLang 团队参与,2025,arXiv:2501.01005)。它和 FA 在同一张优先级表里竞争,但设计取向几乎处处相反:

| 维度 | FlashAttention | FlashInfer |
|---|---|---|
| 设计目标 | 通用,训练推理都要照顾 | 只做推理 |
| 分页 KV | 靠块表参数支持 | 原生设计,分页是一等公民 |
| decode 优化 | split-KV 是可选路径 | 原生 split-KV 加批量分页注意力 |
| MLA | 不原生支持,要换专用实现 | 有专门实现 |
| Hopper 优化 | 取决于编进来的 FA 版本 | 深度优化(异步内存搬运、warp 专业化) |
| prefill 与 decode 混合 | **单个变长调用** | **分开的 wrapper 对象** |

最后一行是两者最实在的分歧。FlashInfer 一口气导入五个 wrapper:分页前缀填充、不规则前缀填充、分页解码各一个,再加上多级级联和带 sink 的两个。**「统一成一个调用」和「每种场景一个对象」是两条路**,前者让上层不用分类,后者让每个对象能针对自己的场景做到最优。

FlashInfer 的 decode 优势来自它的定位:decode 是访存瓶颈,它专门优化了从分页 KV cache 读取的访问模式,在 Hopper 上用异步内存搬运加速跨 SM 的数据流动。

### 1.8 Triton:慢一点,但你能改

| 维度 | FlashAttention / FlashInfer | Triton |
|---|---|---|
| 实现语言 | CUDA C++,预编译的扩展模块 | Python 内嵌的 GPU 语言,首次调用时即时编译 |
| 改一行要做什么 | 改 C++ 源码,重新编译整个扩展 | 改 Python,直接跑 |
| 跨硬件 | FlashInfer 仅 NVIDIA;FA 在 AMD 上走的是另一个库的移植版,**不是同一份代码** | 同一份源码在 NVIDIA 与 AMD 上都能编 |
| 自定义门槛 | 高 | 低 |

性能上 Triton 比前两者略慢,但差距在缩小。它的定位是三件事:前两者不可用时的兜底、需要自定义 attention 逻辑时的载体、以及 AMD 卡上的可选项。在 CUDA 的优先级表里它稳定排第三。

三个 Triton kernel 的出处各不相同,文件头都写了归属:统一 kernel(混合 batch 走这个)由 IBM Zurich 团队贡献;prefill kernel 从 SGLang 移植,vLLM 侧加了滑动窗口支持;decode kernel 也从 SGLang 移植,而 SGLang 又源自 LightLLM 的 DeepSeek-V2 分组查询注意力解码 kernel,vLLM 侧加了块大小大于 1 的支持。

**算子目录下还有几个 Triton kernel 不属于这个后端**,按名字很容易归错。真正的使用者分别是:解码 kernel 归 Triton 版 MLA,DiffKV 版归 DiffKV 后端,合并状态那个归一个按平台分发的调度函数(CUDA 上走原生实现,兜底才用 Triton 版),量化解码与写入那两个归 TurboQuant。还有一个 FP8 分组查询注意力打分的 kernel,**本仓库里根本没有任何地方 import 它**。

### 1.9 MLA:为什么必须另起一套接口

MLA(多头隐注意力)是 DeepSeek V2/V3 的核心创新 —— 把 KV cache 从「头数乘以每头维度」压到一个低秩隐空间,大幅减少显存占用。

它需要专用后端,不是因为算得更快,而是因为**计算形状根本不是标准的那一套**。标准 attention 是 Q 点乘 K 转置、softmax、再乘 V;MLA 要么先从隐向量解压出 K 和 V,要么干脆把解压矩阵吸收进 Q 和输出投影里根本不解压(decode 走这条)。吸收之后 kernel 看到的是一个 head 维度极大的多查询注意力,而不是常规的分组查询注意力。

所以 MLA 的实现类不继承标准实现,而是继承一个 MLA 专用基类,暴露的也不是单一的 `forward`,而是 prefill 和 decode 两个方法。

两处细节值得记:

**这两个基类是兄弟,不是两条独立分支。** 标准实现和 MLA 实现都继承自同一个更上层的实现基类 —— 这正是「MLA 也走同一套后端体系」的实现依据。抽象层没有为 MLA 破例。

**两个方法的抽象性不一样。** 只有 decode 那个是抽象方法,prefill 那个在基类里直接抛未实现。含义很实际:**一个只做 decode 的 MLA 后端是合法的**,而只做 prefill 的不是。

MLA 的 prefill 阶段要么解压隐向量、要么分块跑,和 decode 的 kernel 需求完全不同,所以它**单独有一套子体系** —— 自己的抽象基类、自己的注册表、自己的 selector,配套一个独立的配置项。这是全章唯一一处 selector 分叉。

### 1.10 MLA 后端有十几个,按硬件分三档

以注册表里登记的为准:

| 后端 | 底层库 | 什么时候轮到它 |
|---|---|---|
| FlashInfer MLA | FlashInfer | Blackwell 上第一优先级 |
| TokenSpeed MLA | TokenSpeed(第三方) | Blackwell 上第二,但只接 R1 维度加 FP8 KV |
| CUTLASS MLA | CUTLASS | Blackwell 上第三 |
| FlashAttention MLA | FlashAttention | Hopper 及更早上第一优先级 |
| FlashMLA | DeepSeek 官方 FlashMLA | Hopper 上第二 |
| Triton MLA | Triton | 通用兜底;**SM120 上是第一优先级** |
| 三个稀疏变体 | FlashMLA / FlashInfer / FlashAttention 各一个 | 稀疏注意力场景,排在各档末尾 |
| AMD 三件 | AITER | AMD 卡,含一个稀疏版 |
| CPU / XPU 四件 | 原生、Intel AMX、XPU 稀疏 | 非 GPU 推理 |

TokenSpeed 那一行的限制写在源码注释里:只接 R1 的维度加 FP8 KV,其余组合被能力校验直接拒绝。注释还补了一句为什么它排在 FlashInfer 之后 —— **不是因为它差,是因为它在 batch 小于等于 2 时会倒退**,要到 batch 约 8 以上才反超。

另有三个公共工具(索引转换、稀疏滑窗、压缩)不作为后端注册,只是被这些实现共用。

### 1.11 优先级不是一张静态表

「按硬件查一张固定的表」是个很自然的想法,但它是错的。

MLA 的选择确实按算力等级分三档(Blackwell、SM120、其余),但**每一档内部的顺序是当场算出来的**:

```text
Blackwell, sparse MLA:
  quantized KV           -> FlashInfer first      量化 KV 走 FlashInfer
  BF16 KV, heads <= 16   -> FlashInfer first      注释: FlashMLA 要 padding
  BF16 KV, heads >  16   -> FlashMLA   first

other tiers, sparse MLA:
  head_size == 512       -> SM90 sparse first     插到最前
  otherwise              -> SM90 sparse last      追加到末尾
```

非 MLA 那一侧也有一处动态:Blackwell 上默认把 FlashInfer 排在 FlashAttention 之前,**但非因果注意力时反过来** —— 源码注释写明那条 cutlass 路径有已知问题。

这件事的实际后果是:**换一个量化配置或换一个 head 数,选出来的 kernel 可能就变了。** 排查性能问题时,「同样的卡同样的模型」不足以推出「同样的后端」。

顺带纠正讲稿里一处自相矛盾:FlashAttention MLA 并不是「所有非 Blackwell 上的第一优先级」—— SM120 那一档只有 Triton MLA 和一个 FlashInfer 稀疏变体,FlashAttention MLA 根本不在候选里。

### 1.12 名字叫 backend,其实不是 attention

Mamba、Gated DeltaNet、线性注意力、短因果卷积这几类层也被登记成「注意力后端」,但它们**不做 Q/K/V 打分**,而是维护一个固定大小的循环状态。

| 维度 | 标准 attention | 状态空间与线性注意力 |
|---|---|---|
| 怎么算 | Q 点乘 K 转置,softmax,再乘 V | 状态递推 |
| 缓存什么 | 历史 K/V 张量 | 固定大小的状态,**不随序列增长** |
| 复杂度 | 序列长度的平方 | 线性 |
| 长序列 | 需要分块预填充 | 天然支持 |

它们的共同标记是一个返回真的判定方法(基类默认返回假,这五个各自覆盖)。对应的缓存规格也不是注意力规格,而是一个并列的状态规格 —— 两者都直接继承同一个缓存规格基类,是兄弟关系。这套规格体系 03 章 1.14 已经讲过,这里不重复。

**它们被放进这套体系,是因为 vLLM 的缓存管理和 metadata 构造都是围绕「每层有一个 backend」组织的**,复用同一套调度接口比另起炉灶便宜。

讲稿说这些后端「不出现在优先级表的候选列表里」,结论对,但真实原因更硬:**它们根本不在同一个枚举里**。主枚举之外另有一个状态空间专用的枚举,这五个住在那边 —— 连参与竞争的资格都没有。用哪个完全取决于 checkpoint 是什么架构,模型定义直接实例化对应的层,不经过 selector。所以「Mamba2 比 Mamba1 新所以 vLLM 优先用 Mamba2」这个说法不成立。

混合架构(Transformer 加 Mamba,或 Transformer 加 Gated DeltaNet)里两类层同时存在于一个模型,这正是「按缓存组的种类分别指定后端」那个配置项存在的理由之一。

### 1.13 绕过优先级表的第二条入口

选后端有两条路,讲稿只讲了第一条。

第一条是本章到目前为止讲的:selector 拿硬件、模型、精度去优先级表里筛,能力校验过滤掉不合格的候选,选中第一个。

第二条是**模型层直接钦定**。DeepSeek V4 的稀疏 MLA 有三个后端(FlashMLA、FlashInfer、ROCm 各一条硬件线),MiniMax-M3 的稀疏注意力有三个 —— 六个都**登记在同一张注册表里**,但源码注释写明它们由模型层选择,不参与优先级表的竞争。它们的实现类不住在注意力目录下,而住在各自的模型目录下。

这条入口的存在说明抽象层的边界在哪:**它保证「模型代码不感知 kernel」,但不保证「模型不能指定 kernel」。** 一个模型如果自带只有它用得上的 kernel,硬塞进通用优先级表没有意义 —— 别的模型永远选不中它,它自己也不需要跟别人比。

### 1.14 注册表是一张路径表,不是 import 表

注册表里的每一项,值是一个**类路径字符串**,不是类对象本身。真正的导入发生在取类的时候。

这个设计是为了避免循环依赖和启动期无谓的导入,但它有一个可观察的副作用:**一个指向不存在模块的登记项可以一直挂着不报错。** 基准上就有这么一项 —— 给没有 attention 层的模型(纯 embedding 或 pooling 模型)准备的那个占位后端,它指向的模块在整个仓库里搜不到,类名也搜不到。只要没有人选中它,谁也不会发现。

记住这一点的用处是:**看到注册表里有某个名字,不等于那个后端真的存在。** 要确认它可用,得去它指向的路径下看有没有那个类。

### 1.15 全景:这些后端之间是什么关系

```text
                          AttentionBackend
                       (class-level, never built)
                                 |
        +------------------------+------------------------+
        |                        |                        |
   AttentionImpl           MLAAttentionImpl          no attn impl
        |                        |                        |
    +---+---+----+           +---+----+            +---+---+---+----+
    |   |   |    |           |        |            |   |   |   |    |
   FA  FI  Tri  Flex      dense    sparse       Mamba GDN Lin SConv
    |                        |        |
    |                     FI-MLA   FlashMLA-Sparse
    |                    CUTLASS   FI-MLA-Sparse
    |                     FA-MLA   FA-MLA-Sparse
    |                   FlashMLA
    |                 Triton-MLA
    |                 TokenSpeed
    |
    +-- K/V heterogeneous  FA-DiffKV / Triton-DiffKV
    +-- quantized KV       TurboQuant
    +-- hardware-specific  ROCm / CPU / Intel AMX / XPU
    +-- model-pinned       DeepSeek-V4 x3 / MiniMax-M3 x3
```

三根主枝从左到右分别是:**标准 attention**(实现继承 `AttentionImpl`)、**MLA 家族**(实现继承 `MLAAttentionImpl`)、**状态空间类**(没有 attention 实现,走另一个枚举)。

四条关系值得单独记:

- **标准那四个在同一张优先级表里竞争**,区别只在底层库、优化深度和 mask 表达能力,处理的都是多头、分组查询、多查询这三种标准结构。
- **MLA 家族自成一支**,接口都不一样,但共享最上层的实现基类。稀疏 MLA 是 MLA 的子集,由一个判定方法标出,稀疏与否会作为条件传进 selector。
- **状态空间类不参与竞争**,不同的枚举、不同的缓存规格,由模型架构直接决定。
- **互斥性**:一个缓存组只用一个后端。混合架构的不同层属于不同的组,各自选各自的;同一层只用一个。

回到 1.1 的痛点:模型数乘以 kernel 数的组合爆炸,被这套抽象压成了「每个模型声明自己是哪一类,每个 kernel 声明自己能干什么,中间一个 selector 撮合」。代价是这套撮合逻辑自身长出了三件东西 —— 运行期才能确定的能力声明、当场计算的优先级、以及两条绕过撮合的旁路。这三样都不是设计失误,是「七个维度同时变化」这件事必然要付的账。

## Part 2|图解

### 2.1 一个后端是怎么被选中的

代码里**没有一棵 if/else 决策树**。实际形状是「候选列表 → 逐个校验 → 取优先级最小者」,硬件条件被编码进两个地方:优先级函数给出的候选顺序,和每个后端自己的准入校验。

```text
  层构造时: Attention / MLAAttention 调 get_attn_backend()
      |
      +-- 1. 收集所有影响选择的条件, 装进一个不可变元组
      |      head_size, dtype, kv_cache_dtype, block_size, use_mla,
      |      use_sparse, has_sink, has_sliding_window, attn_type,
      |      use_non_causal, use_batch_invariant, use_kv_connector,
      |      use_pcp, use_dcp, use_adaptive_verification ...
      |
      +-- 2. 解析"用哪个后端"这个偏好值
      |      全局配置给一个, 配了按组指定就按 KV 组种类覆盖
      v
  带缓存的内层函数                              键 = 上面那个元组 + 偏好值 + head 数
      v
  平台层 get_attn_backend_cls()                 NVIDIA / AMD / XPU 各一份
      |
      +-- [A] 偏好值非 None, 也就是用户显式指定了
      |       |
      |       +-- 只校验这一个
      |             +-- 导不进来  -> raise             模块缺失或编译产物没有
      |             +-- 校验不过  -> raise             能力对不上
      |             +-- 通过      -> 用它, 打一条日志
      |       * 没有任何 fallback 分支
      |
      +-- [B] 偏好值为 None, 自动选
              |
              +-- 候选顺序 = 优先级函数(硬件, dtype, head 数 ...)
              +-- 对每个候选跑准入校验
              |     不通过的连同序号记进一张失败原因表
              +-- 全部不通过 -> raise
              +-- 取序号最小的那个
                    若 --block-size 排除掉了更靠前的候选, 额外打一条 warning
      v
  到这一步才按全限定名真正 import 那个模块
```

三点和直觉不同:

**显式指定不是「优先尝试」,是「要么用它、要么报错」。** 想让 vLLM 在不兼容时自动退回,唯一的办法是**不指定**。这一条最常被误解,因为大多数框架的「指定后端」都是软的。

**显式分支有两条失败路径,它们的含义不同。** 一条是模块根本导不进来(抛出的是导入类异常,被包成配置错误再抛);另一条是能力校验不通过(错误信息里带着具体的不满足原因列表)。**1.14 那个指向不存在模块的悬空登记项,就是在第一条路径上炸** —— 注册表不校验路径,真正的校验推迟到了这里。

**缓存的键是一个不可变元组,这解释了第 1 步为什么要那么费劲。** 内层函数带记忆化,键就是那个元组加两个参数。把十几个散落在各处配置里的布尔量先收拢成一个可哈希的整体,是为了让「同样的场景」折叠成同一个缓存项 —— 一个模型几十上百层,每层都问一次,不折叠就要重算几十上百遍。

### 2.2 一个 step 的调用栈

```text
  ModelRunner.execute_model()
      |
      +-- 1. 组装跨后端共享的那份 metadata
      |      query 段边界 / 每请求 KV 长度 / 块表 / 槽位映射 / 计数若干
      |
      +-- 2. 每个 KV cache 组调一次 builder.build()
      |      产出该后端专属的 metadata
      v
  model.forward()
      |  metadata 通过 forward context 传递, 不是逐层参数透传
      v
  Attention layer.forward(q, k, v)
      v
  AttentionImpl.forward(layer, q, k, v, output, kv_cache, metadata)
      |  不区分 prefill / decode: 混合 batch 一次算完
      |
      +-- metadata 为空    -> 输出填 0 返回          启动期探测那一次
      +-- encoder 类       -> 走不碰 KV cache 的分支
      +-- 写 KV cache      -> 按槽位映射把本 step 的 k/v 落进去
      +-- DCP 开启         -> 走上下文并行分支
      +-- 命中级联条件     -> 走级联分支
      +-- 其余一律         -> 同一个变长调用
      v
  kernel
```

两个地方值得停一下。

**「每个 KV cache 组调一次」是混合架构能跑的原因。** 1.12 说过混合架构的不同层属于不同的组、各自选各自的后端 —— 到了执行层,这句话的兑现方式就是这一行:共享 metadata 组装一次,然后按组各翻译一份。

**metadata 走的是 forward context,不是函数参数。** 模型代码的 `self.attn(q, k, v)` 只有三个参数,本 step 的 metadata 从一个上下文对象里取。这是 1.1 那句「模型代码不感知 kernel」能成立的技术前提 —— 参数表里但凡出现 metadata,模型代码就得知道它是什么类型。

### 2.3 metadata 分三层

```text
  标记类                    空的, 只用来给泛型做上界
     ^
     |  各后端可继承可不继承
     |
  共享层                    跨后端、跨层共享, ModelRunner 每 step 组装一次
     |    query 段边界 / 每请求 KV 长度 / 块表 / 槽位映射
     |    请求数 / 实际 token 数 / 最长 query / 最长序列
     |    以及几个派生方法: 算每条请求的 query 长度、
     |    算每个 token 属于哪条请求、裁掉 padding 行
     |
     v  builder.build() 翻译
  专属层                    每个后端一个 dataclass, 内容差别很大
        FlashAttention 那份: 基本字段 + 级联三件 + DCP 若干 +
                             提前调度产物 + 两种非标准 mask 的参数
        MLA 那份:           内嵌 prefill 与 decode 两个子结构,
                             因为 MLA 真的要分两条路走
```

**只有中间那层是所有后端共用的。** 上面那层是空的(见 3.1),下面那层各写各的。所以「attention metadata」这个词在不同上下文里指的不是同一个东西 —— 读代码时要先看清说的是哪一层。

## Part 3|机制之外:源码里额外读到的

Part 1 讲了这套抽象**应该**怎么工作,Part 2 把两条路径画了出来。这一部分只放一类东西:照着源码读下来,**机制层面看不见、但真实存在的细节**。前面讲过的一概不重复。

### 3.1 那个基类是空的,而且不强制继承

`AttentionMetadata` 这个名字看起来像所有 metadata 的共同基类。它的类体只有一个 `pass`。

它的唯一作用是给泛型参数做上界 —— 有了它,`AttentionMetadataBuilder[M]` 才能写出类型约束。它不定义任何字段,**也不强制各后端继承**。事实上 FlashAttention 的 metadata 就是一个裸 dataclass,一个字都没继承;MLA 的那份倒是继承了。

**所以不能靠「是不是这个类的实例」来判断一个对象是不是 attention metadata。** 真正统一的约束在泛型签名上,不在继承关系上。

### 3.2 有没有 KV 累积和,标记了这条分支读不读分页缓存

共享 metadata 里给的是每条请求的真实 KV 长度,不是累积和 —— 因为 FlashAttention 的变长接口在**有块表**时,靠块表就能找到每条请求的 KV,不需要累积和。

但这不等于 KV 累积和在代码里不存在。它出现在**四个地方**,全都是不走分页缓存的分支:上下文并行那两处(传的是连续张量),编码器那两处(压根不碰 KV cache)。

**这两件事其实是同一件事的两面:有块表就不需要 KV 累积和,没块表就必须给。** 想知道一条 attention 分支读不读分页缓存,看它传不传这个参数就行。

### 3.3 能不能进图,不是 metadata 说了算

metadata 里**没有**「这一步走不走 CUDA Graph」这样的字段。可行性是 builder 的一个类变量,而且源码在它上面留了一行注释:不要直接读这个变量,去调那个方法。

做成方法而不是常量,是因为**同一个 builder 在不同配置下的支持度可能不同** —— 比如投机解码开启时才允许某一档。做成常量就表达不了这种依赖。

至于这一步实际走不走图,由 ModelRunner 侧决定,不是塞进 metadata 让实现自己判断。02 章 2.7.7 讲过那个三级降级的派发过程,这里只补一句归属:**判据在 builder,决策在 ModelRunner,实现全程不参与。**

### 3.4 builder 拿到的不是调度输出

很容易以为 builder 直接读调度器产出的那个对象。它没有 —— `build` 的签名里只有共享 metadata 和一个公共前缀长度,连调度对象的影子都没有。

调度输出到共享 metadata 的转换发生在 ModelRunner 里,builder 只做「共享 metadata → 后端专属 metadata」这一步翻译。

**这条边界和 02 章反复讲的那条是同一条**:调度层不认识 kernel,kernel 层不认识调度。中间的翻译工作被明确切成两段,各自只依赖上一段的产物。

### 3.5 图捕获那个方法有默认实现

看到「捕获 CUDA Graph 时用的构造方法」,直觉是每个后端都得自己实现一遍。不用 —— 基类的默认实现就是把公共前缀长度置零再转调普通构造。

**只有约束特殊的后端才需要覆盖**,MLA 是典型。这条的实际价值是:新写一个后端时,这个方法不用管。

### 3.6 那段警告不要随手改的注释

实现类的前向方法上方压着一段很醒目的注释,大意是:这个方法在分段图模式下是**eager 执行**的,连取视图、切片这种不产生 GPU 算子的操作都算显著的 CPU 开销,改动前必须先做基准测试。

这段注释解释了一件前面看起来有点奇怪的事:**为什么所有能预先算好的东西都被挪进了 builder。** 提前调度的产物、滑动窗口的参数张量,本来在前向里算也不是不行,但前向每层每步都要跑一遍,而 builder 每步只跑一次。在一个 eager 执行、CPU 开销被放大的方法里,这个差别是数量级的。

**「把计算挪出热路径」在这里的具体含义不是省 GPU 时间,是省 Python 时间。**

### 3.7 那几个「融合支持」声明是给编译器看的

实现基类上挂着几个名字带「融合」的方法,默认全部返回假,由各后端按支持情况覆盖。它们不在任何调用链上 —— 没有代码会在前向里读它们。

读它们的是 torch.compile 的融合 pass:实现声明支持,编译器就可以把归一化、位置编码、写 KV cache 折进 attention kernel 的那一次调用里,省掉中间张量的一次往返。(「省一次往返」是讲稿给的解释,不是源码注释里的原话。)

这是抽象层里少见的一类接口:**它的调用方不是运行时,是编译期。**

### 3.8 注释也会过期

自动选择那一段的上方有一句注释,说的是「没有指定后端,**或者指定的后端无效**,所以我们去找一个有效的」。

后半句在当前实现里**到不了**。指定的后端无效时,上面那个分支已经抛异常了,根本不会往下走(见 2.1)。这句注释是早期实现的残留 —— 那时候显式指定大概真的是「优先尝试」。

放这一条不是为了挑错,是因为它正好是本章反复出现的那个提醒的又一例:**源码里写着的东西,不一定是现在在跑的东西。** 1.4 的能力声明如此(源码说支持不等于这台机器支持),1.14 的注册表如此(登记了不等于模块存在),这里的注释也如此。核对一个断言,最终还是得看执行路径。

### 3.9 MLA 的代码不在后端文件里

1.9 说过 MLA 另起了一套接口。但它真正的特别之处在**代码摆在哪**:

标准 attention 是「层文件很薄,每个后端文件自成一套」。MLA 反过来 —— **公共逻辑全在层文件里**(一个三千多行的大文件,装下了层、后端基类、metadata 与它的两个子结构、构造器、两级实现基类),`mla/` 目录下每个后端文件**只覆盖 decode 那一次 kernel 调用和少量能力声明**。

两个后果:

**MLA 的「公共部分」比标准 attention 厚得多。** 分块预填充的工作区规划、权重吸收、对数和指数项的合并、稀疏索引转换,全在公共层。十几个 MLA 后端之间的真实差异,其实只有 decode kernel 那一次调用。

**后端可以反过来改写 KV cache 的形状。** MLA 的后端基类上挂着一个改写缓存规格的方法,把每单元的字节数按后端需求重算 —— 基准上是一张两档表,FP8 的 latent 布局算 656 字节,NVFP4 的算 352。这是**整套抽象里少数几处「后端反向影响 KV cache 形状」的入口**;别的地方都是缓存规格先定、后端适应。

顺带记一个容易看漏的数字:MLA 后端基类写死的 head size 白名单是**三个值**,不是两个。除了「latent 维度加上 rope 维度」的两种组合,还有一个**纯 latent 维度、不带 rope 段**的取值 —— 它对应的是**不加位置编码的 MLA 层**,也就是把位置信息整个交给别的层去管的那类混合架构(06 章会讲到,这正是 Kimi 那条线在用的配置)。

## Part 4|对比与决策

前三部分讲这套抽象怎么造的。这一部分讲怎么用它:各后端什么时候轮到、怎么强制指定、出问题先查什么。

### 4.1 各后端什么时候轮到它

「优先级」一列是优先级函数里的实际排位,可以从代码确证;「推荐场景」是经验判断。

| 后端 | 硬件 | 模型 | 自动选择时的优先级 | 推荐场景 |
|---|---|---|---|---|
| FlashAttention | NVIDIA Ampere 到 Blackwell | 标准 | Hopper 及更早第 1;Blackwell 第 2 | 默认通用 |
| FlashInfer | NVIDIA | 标准 | Blackwell 第 1;其余第 2 | Blackwell,大 batch decode |
| Triton | NVIDIA / AMD | 标准 | 第 3 | 兜底;要改 kernel 时 |
| Flex Attention | NVIDIA | 任意 mask | 第 4 | 标准 kernel 表达不了的 mask |
| TurboQuant | NVIDIA | 标准 | 第 5 | 量化 KV cache |
| FlashAttention MLA | NVIDIA 非 Blackwell | MLA 系 | 非 Blackwell、非 SM120 第 1 | DeepSeek 通用 |
| FlashInfer MLA | NVIDIA Blackwell | MLA 系 | Blackwell 第 1 | Blackwell 上的 DeepSeek |
| CUTLASS MLA | NVIDIA Blackwell | MLA 系 | Blackwell 第 3 | Blackwell 备选 |
| FlashMLA | NVIDIA Hopper | MLA 系 | 非 Blackwell 第 2 | Hopper 上的 DeepSeek |
| Triton MLA | 任意 NVIDIA | MLA 系 | 通用兜底;**SM120 第 1** | 没有专用 kernel 时 |

| HPC Attention | NVIDIA Hopper | 仅 Hy3 | **不在自动表里** | 必须显式指定 |

有三处值得回头对照 Part 1:稀疏 MLA 的档内顺序是**当场算的**(1.11);HPC 和状态空间类**根本不在候选表里**,但原因不同 —— 前者在枚举里只是没被排进任何一档,后者连枚举都不是同一个(1.12)。

### 4.2 和 SGLang、TensorRT-LLM 比

下表只有 vLLM 那一列能从本仓库代码确证,另两列是**讲稿的定位参考,不在本仓库内、无法校验**,做选型决策前应以对方仓库为准。

| 维度 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 抽象层 | 后端(能力声明)加实现(kernel)加构造器(每 step 输入)三件套 | 类似的三层划分 | 较薄,kernel 与 runtime 耦合更紧 |
| 后端选择 | 候选优先级表加准入校验,自动选 | 显式配置为主 | 构建期决定 |
| Triton | 有,含自研统一 kernel | 有 | 无 |
| MLA | 十几个注册变体,含稀疏与模型钦定 | 多变体 | 完整支持 |
| AMD | 有,ROCm 与 AITER 多个后端 | 部分 | 无 |
| 自定义门槛 | 中:继承三件套,Python 侧即可完成 | 中 | 高,要改 C++ 并重新构建 |

vLLM 这一列最值得关注的结构性差异是 **metadata 与 kernel 分离**:构造器每 step 跑一次,把调度器的输出翻译成 kernel 参数;实现只管调 kernel。这让「同一个 kernel 支持分块预填充、级联、上下文并行、投机解码」成为可能 —— **变化都被吸收进了构造器**。

### 4.3 怎么强制指定一个后端

配置项有三个层级,按作用范围从大到小:

| 配置项 | 作用范围 | 什么时候用 |
|---|---|---|
| 全局后端 | 整个模型 | 想让所有层都用同一个 |
| 按缓存组种类指定 | 一类 KV cache 组 | 混合架构才需要,例如全注意力层和滑窗层分开指定 |
| MLA prefill 后端 | MLA 的 prefill 阶段 | 只有 MLA 模型有这一项(见 3.8) |

命令行上,全局后端有两种等价写法:一个专用参数,或者把整份注意力配置作为 JSON 传进去。后两个层级只能走 JSON 那条路。想回到自动选择,显式传 `auto`。

四条约束:

- **专用参数和 JSON 里的同名字段互斥**,同时给会直接报错。
- 后端名字大小写不敏感,但**必须是枚举里存在的名字**;写错时报错信息会列出全部合法值 —— 这是注册表的元类专门做的。
- **显式指定不兼容的后端会报错,不会静默退回**(2.1 的 [A] 分支)。想要「能用就用、不能用就退」,只能不指定。
- **环境变量 `VLLM_ATTENTION_BACKEND` 已经不存在了**,基准上全仓库搜不到任何读取点。网上相当多的 vLLM 调优文章还在教用它,照做不会报错,只会**默默不生效**。

最后这条是本章最实用的一条。

### 4.4 排查:为什么没选到我要的后端

**先看日志确认实际选中的是谁。** 两条日志对应两条分支:显式指定走的那条只打「正在使用某后端」;自动选择那条还会**列出所有通过校验的候选**,信息量大得多。

**再看被淘汰的原因。** 每个被刷掉的候选连同原因字符串都会记下来,但打的是 debug 级别 —— **日志级别不调到 DEBUG 就看不到**。原因字符串来自各后端的准入校验方法,形如「head size 不支持」「block size 不支持」,能直接指出是哪一维不匹配。

这一节剩下的内容(仓库自带的 kernel 基准脚本、三种 profiler 各适合看什么)是工具用法,不是本仓库的机制,按经验参考对待。只补一句和 3.6 的呼应:**如果怀疑的是 CPU 侧开销而不是 kernel 本身**,要看的是时间线和 kernel 启动间隙那一类工具,不是单 kernel 的占用率分析 —— 3.6 那段注释警告的正是这类问题。

### 4.5 常见误区

| 误区 | 真相 |
|---|---|
| FlashInfer 总是更快 | 不一定。优先级本身就分架构:Blackwell 上 FlashInfer 第一,Hopper 及更早 FlashAttention 第一 |
| MLA 必须 Hopper 或 Blackwell | 不。Triton MLA 在任何 NVIDIA 卡上都能跑,SM120 上它还是第一优先级。有架构门槛的是那几个专用 kernel |
| Triton 后端是临时方案 | 不。它在优先级表里稳定排第三,是 AMD 与 SM120 的主力路径之一,MLA 的索引转换等公共 kernel 也是 Triton 写的 |
| block size 必须和后端匹配,所以要手动调 | 反了。默认是**自动协商**:后端声明自己能接受哪些块大小,建 KV cache 前统一定夺。只有你显式给了才变成硬约束,此时**可能反而排除掉更优的后端**,代码会专门为此打一条 warning |
| 指定的后端不兼容会自动退回默认 | 不会,直接报错 |
| 名字带「短卷积」的那个后端是滑动窗口注意力 | 不是。它属于状态空间家族。滑动窗口由标准后端通过一个参数支持,不是独立后端 |
| Mamba、Gated DeltaNet 也在优先级表里竞争 | 不在。它们在另一个枚举里,由模型架构直接决定(1.12) |

最后一行的延伸问题 —— 这些线性注意力到底是什么、各家为什么纷纷改用它 —— 是下一章的主题。
