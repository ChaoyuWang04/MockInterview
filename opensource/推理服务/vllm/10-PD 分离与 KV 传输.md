# vLLM 10|PD 分离与 KV 传输

把 prefill 和 decode 拆到不同节点上跑,这笔账值不值得,02 章已经算过。这一章讲拆开之后多出来的那件事:那份 KV cache 怎么从 P 走到 D —— 谁传、什么时候传、这笔时间算在谁头上,以及这笔买卖什么时候划不来。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

PD 分离在本仓库里由三章分工,互不重复:**调度侧**的状态机、阻塞态与延迟释放在 02 章 6.5 与 8.5;**两个实例之间的前缀复用怎么拼**在 04 章 3.1 至 3.4;本章讲**传输层本身**,以及部署时那几笔容易算错的账。

## Part 1|原理:拆开之后多出来的一件事

### 1.1 拆开之后,多出来一件必须做的事

prefill 和 decode 对硬件的要求正相反,混在一个 batch 里会互相拖累 —— 这一层 02 章 1.3 已经讲透,那里给的是同一张卡内部的调和办法(把长 prompt 切块,让两者共享一个 step);PD 分离是另一条路,干脆把两者放到不同的卡上。

两者的差异 02 章 1.3 列过了(算力瓶颈对访存瓶颈、单步 50 到 500 毫秒对 5 到 50 毫秒),这里只补讲稿多给的两个维度:**最优 batch 大小是相反的**(prefill 几到几十就压满算力,decode 要几十到几百才填满带宽),于是混部只能取一个折中值,**两头的 GPU 利用率都差着一个数量级**。这些区间是量级参考,不是本仓库实测。

但拆开不是免费的,而代价恰好是混部时根本不存在的一件事。

**混部时 KV cache 从来不需要搬。** prefill 把 KV 写进 block 池,decode 直接从同一个 block 池读,两者共用一份显存,中间一个字节都不动。拆开之后这个前提消失了:P 算出来的 KV 在 P 的显存里,D 要用它,就必须**整份搬过去**。

搬的量不小。以一张 70B 模型、TP=8 的卡为例,单 rank 每块(16 个 token)跨全部 80 层约 640 KB(口径同 03 章 3.4);一条 2000 token 的 prompt 占 125 块,单 rank 约 78 MB,八个 rank 合计约 620 MB。**每一条请求都要搬这么一次**,而且必须在 D 开始 decode 之前搬完。

于是这一章要回答三串问题,前四部分就按这三串排:

- **那份 KV 怎么搬过去**(1.3 至 3.2):它长在什么形状的内存里、谁负责搬、请求怎么分给 P 和 D、P 算完怎么告诉 D、推还是拉、一个 block 在显存里是几段、什么时候能和计算重叠,以及最后有多少延迟真的暴露在外。
- **搬的这笔时间算在谁头上**(3.3 至 3.6):首字 token 从哪一侧产出,决定了这笔时间落进 TTFT 还是 TPOT;而看均值会把它整个藏起来。
- **这笔买卖什么时候划不来,瓶颈会出在哪**(3.7 至 3.10):为什么撑不住的总是 P、TTFT 为什么不是缓慢上升而是突然暴涨、收益与代价各自是什么形状。

还有一条暗线贯穿全章、到 4.5 收口:**这个「只负责搬数据」的模块,会反过来向引擎提要求** —— 大张量怎么申请、维度怎么排、能不能开混合内存分配,都可能由它说了算。4.1 至 4.6 拆的就是这一层。

### 1.2 好处清单可以压成一句,但有一条 02 章没算到

02 章 6.10 那张表已经把混部与分离逐维对过 —— TPOT 稳定性、TTFT、GPU 利用率、batch 大小、弹性扩缩、跨实例前缀共享、硬件异构、运维复杂度、适用场景、传输开销。讲稿列的七个好处逐条落在那张表里,不重复。

只补那张表没给的一点,而这一点恰好是最容易算错的:**PD 分离在 P 侧省下的不是显存总量,是 block 的占用时长。**

混部时一条请求的 block 从 prefill 开始占,一直占到最后一个 token 生成完,可能是几百上千个 step。P 侧不一样:请求在 P 上只活到 prefill 结束加一次传输确认,几十到几百毫秒就把 block 还回池子。同样大小的 block 池,**周转率高一个数量级,能撑住的 prefill 吞吐就高一个数量级**。换到 02 章 3.1 那三道闸门的说法:在 P 上,闸门 2(KV 容量)几乎不再是瓶颈,并发上限回到闸门 1 和闸门 3 手里。

一处要更正:讲稿把「D 节点崩溃可以回落到 P 节点临时 decode」列成第七个好处。**基准上没有这个机制** —— 全树找不到任何从 D 失败回落到 P 继续 decode 的路径。故障隔离本身是成立的(P 和 D 是两组独立进程,一边崩不影响另一边已经在跑的请求),但「回落」是部署层要自己做的事,不是 vLLM 提供的能力。

### 1.3 那份 KV 长在一块不能动的大张量里

这一节回答一个问题:为什么所有传输实现都长成「注册一块内存、让对端远程读写」,而不是「把 KV 序列化出来发走」。

答案在 KV cache 的申请方式里。它不是按请求动态申请的,而是启动时一次性拿到的一整块显存,进程活着就不释放;block 只是这块显存上的逻辑分区,所谓「释放一个 block」是把引用计数减到零、把它还给空闲队列,底层字节始终属于那块大张量。这一层 03 章 3.4 与 3.5 已经展开,本章只借用结论。

结论的第一个后果是:**传输层拿到的是一段地址确定、生命周期等于进程的显存,于是可以直接注册给网卡,让对端单边读写,不需要序列化、也不需要中间缓冲。** 这是后面几个传输实现全都走「注册内存区加远程读写」的原因,也是它们能做到微秒级延迟的前提。

第二个后果反过来:**传输层的要求倒过来约束了这块张量怎么申请。** 基准上这一次申请有个平台分叉,注释把两边的理由都写明了:

| 平台 | 怎么申请 | 理由 |
|---|---|---|
| ROCm | 向上补齐到 4096 字节的页边界 | 要把整块 backing 注册成**一个**内存区,不补齐就凑不出单一区域 |
| 其他平台 | 严格按逻辑大小申请,不多要一个字节 | NIXL 与 CPU offload 都依赖「这块存储的字节数等于逻辑 KV 大小」这个等式 |

后一条是**不变量而不是优化**:一旦这块张量比逻辑 KV 大出一截,「存储字节数」与「块数乘块跨距」就不再相等,而代码里靠这个等式判断能否走整块快路径的地方会直接判错。04 章 2.5 讲写时复制时碰到过同一个等式 —— 布局允许时整块拷贝、否则退回逐层拷贝,判据就是它。**同一个不变量被两个模块的两拨代码各自依赖着,而它只由分配器那一行保证。**

### 1.4 谁来传:一个抽象层,两端各一份

引擎不认识网卡,也不认识任何一种存储服务。它只认识一个基类,所有具体实现都从它派生 —— NIXL、Mooncake(点对点与共享存储两种)、LMCache(进程内与多进程两种)、MoRIIO、HF3FS、FlexKV、CPU offload、一个把多个实现串起来的组合实现,以及几个示例实现。它们一共注册了多少个名字、怎么注册进来的,4.1 单独讲。

这个基类的方法分成两组,分界就是**它在哪个进程里跑**:

| 跑在哪 | 负责什么 | 典型动作 |
|---|---|---|
| 调度器进程 | 记账与决策 | 远端还能补多少 token、分到的块拿去接收哪一段、请求结束时块能不能立刻还 |
| worker 进程 | 真的搬字节 | 发起异步接收、在前向前后等传输、把完成情况报回去 |

同一个 connector 类在两端各实例化一份,用一个二值枚举区分自己是哪一份。02 章 6.6 点过这个分工,这里要补的是**最容易混的一处**。

**代码里的「角色」和配置里的「角色」是两回事。**

| | 取值 | 含义 |
|---|---|---|
| 代码里的枚举 | 调度器 / worker | 这个实例跑在哪个进程里 |
| 启动参数 `kv_role` | `kv_producer` / `kv_consumer` / `kv_both` | 这个实例在 PD 拓扑里扮演 P 还是 D |

讲稿的架构图把前者的取值写成了 producer 与 consumer,它自己在下一节又纠正了一遍 —— 两个概念确实容易串,而且串起来之后会得出「一个进程只能是 P 或 D」这种错结论:实际上每个实例的两份 connector **角色必然不同**(一份在调度器、一份在 worker),而它是 P 还是 D 由配置那一栏单独决定。

`kv_both` 这个第三个取值对应双向传输 —— P 也可能反过来从已经持有部分 KV 的 D 那边拉,04 章 3.3 讲过这条反向分支。但**它正在被弃用**:用 NIXL 时把角色配成 `kv_both` 会收到一条明确的弃用告警,让你改成 P 侧写 `kv_producer` 、D 侧写 `kv_consumer` ;而且开了前缀上下文并行时,消费侧用这个值会直接抛不支持。**新部署不要用它。**

### 1.5 请求怎么分给 P 和 D:路由不在 vLLM 里

一条请求要先到 P、prefill 完再到 D,谁做这个决定?**不是 vLLM。** 基准上引擎里没有任何路由策略:每个实例通过启动参数被配成 P 或 D,把一条请求拆成两半发出去的是一个外部网关(04 章 3.1 讲过,它发的是两份普通 HTTP 请求)。

vLLM 不做路由,但它会把**路由需要的事实吐出来**。P 侧请求结束时,connector 把对端坐标(引擎标识、主机、端口)打包进请求的传输参数交还给网关,网关再塞进发给 D 的那份请求里。NIXL 还会在这组参数里多写一个字段,声明自己这一侧是「等对端来读」还是「自己主动写」,好让外部网关分辨两种生产者。这个字段讲稿没提,但它正是「不做路由、只提供事实」这个分工最好的例证。

按「谁选的 D」分,部署上有三种模式。讲稿列了三种,基准上落地了两种:

| 模式 | 谁选 D | 基准上的实现 |
|---|---|---|
| 网关指定 | 外部网关在发 P 的同时就选好 D,坐标随传输参数带过去 | NIXL、Mooncake 点对点 |
| 中转站 | 不选。P 把 KV 上传到共享存储,D 自己去取 | Mooncake 共享存储 |
| P 选 D | P 算完后向 D 集群询价,D 主动认领 | **没有内置实现**,要在外部网关里自己做 |

第三种没有内置,和 02 章 9.1 那条取舍是同一件事:PD 分离靠 connector 抽象内建,**不引入外部编排组件**。一旦让 P 去询价,就得有一条 P 与 D 之间的控制面,那已经超出「传 KV」的职责范围了。

### 1.6 P 和 D 之间没有一句 RPC

P prefill 完之后,怎么通知 D 可以开始 decode?**不通知。** 两边之间没有任何请求级的远程调用,衔接完全靠「KV 传完了」这件事隐式触发:worker 侧 connector 把完成的请求 id 随模型输出捎回自己的调度器,调度器记进一个已完成集合;**下一个** step 里,调度器在处理等待队列的第一步去查这个集合,在里面才放行。

这套机制 02 章 6.8 已经展开(三个阻塞态的统一出口、传输失败时的块失效路径),本章只补一个它没给的量化结论:

**因为是轮询而不是被推醒,「KV 收完」到「开始 decode」之间恒定有最多一个 step 的延迟。** 这一个 step 在纯 decode 的 D 节点上是 10 到 30 毫秒量级(口径同 02 章 2.3),摊进 TTFT 通常可以忽略;但它是个**下界不为零**的固定成本,想把 TTFT 压到极限时绕不过去。

至于一条请求在 P 和 D 上完整走一遍是什么样,02 章 6.6、6.7 与 6.9 已经从调度器视角走读过 —— P 侧流程、D 侧状态机、端到端时序三份都在那里。

## Part 2|方向、分段与分层:传输侧看到的 KV

### 2.1 推还是拉:方向不是一个开关,是两套实现

KV 可以由 P 主动写到 D 的显存里(推),也可以由 D 主动从 P 的显存里读(拉)。两者不是同一份代码的一个参数,**在 NIXL 里是两套并行的实现**:共用一半基础逻辑,再各自派生出一对调度器侧与 worker 侧的类,注册成两个名字。还有第三个注册名是拉那一套的向后兼容别名 —— 也就是说,**不写明方向时拿到的是拉**。

1.4 讲的那两组方法,到这里正好用上:**方向的差异体现在「哪一侧的钩子里有东西」**。推的一方在 P 侧的保存钩子里真的发数据;拉的一方 P 侧几乎不做事,活都在 D 侧的载入钩子里。

三个具体实现落在不同位置:

| 实现 | 方向 | 谁发起 |
|---|---|---|
| NIXL 拉(默认) | 拉 | D 在请求被调度时远程读 P 的显存 |
| NIXL 推 | 推 | P 在 prefill 结束时远程写 D 的显存 |
| Mooncake 点对点 | **混合** | D 先把自己的坐标发过去,P 再推数据 |
| Mooncake 共享存储 | 两段拼起来 | P 推到存储,D 从存储拉 —— 存储当了中转缓冲 |

最后一行值得停一下:**「中转」并不是第三种方向,而是把推和拉各用一次。** 这样一来 P 不需要知道任何 D 的存在,同一份 KV 还能服务多个 D。

方向的选择会传导到一个很实际的地方 —— **P 什么时候能把显存还回去**:

| | 推 | 拉 | 中转 |
|---|---|---|---|
| P 释放块的时机 | 确认写完 | 等 D 读完 | 上传完即可 |
| 谁需要知道对端 | P 需要知道 D | D 需要知道 P | 两边都只需要知道存储 |
| 一份 KV 服务多个 D | 难,每个 D 各传一份 | 难 | 易 |
| 传输失败 | P 侧重试 | D 侧重试 | D 侧重试,数据还在 |

拉那一档还有个额外后果:P 的块要一直留到 D 读完,所以 1.2 说的「P 侧 block 周转快」在拉模式下打了个折扣 —— 这正是 04 章 3.3 那套租约加心跳续期存在的原因。

### 2.2 传输侧看到的不是「八十层」,而是「几段连续区间」

每一层各有一份独立的 KV cache,是一个四维视图:块数、KV head 数、每块装几个状态、单个状态的字节数。最后一维以**字节**计而不是元素个数,所以换 KV 的数据类型只改这个数、不改维数。这一层 03 章 2.4 与 3.1 已经展开。

顺带消一个歧义,因为两个数字都会遇到:**加上层这一维,整体的逻辑形状是五维**,`LBNHC` 这类 layout 名正是这五维的排布顺序(五个字母对应五维);**摘掉层那一维,每层的视图就是上面那个四维。** 两个说法都对,说的是两级,源码里也同时提供了这两种视角。

传输侧关心的是另一个问题:**一个 block 的数据在显存里是几段连续区间。** 这个数直接决定传输效率 —— 一次远程读写的开销与「段数」强相关,段越多越短,描述符处理和网卡小包开销就越大。八十层的模型,如果每层各占一段,传 N 个 block 就是 80N 段;如果一个 block 能整段传,就只有 N 段。**差了八十倍。**

段怎么划分不是配的,是**注册时逐层现算出来的**,基准上有五条分支:

| 情形 | 一个 block 占几段 | 什么时候落到这一档 |
|---|---|---|
| 状态空间层 | 每层若干段 | 这一层是 Mamba 一类的状态缓存,单独一支 |
| 压缩页 | 一段,页首尾相接 | 一个 kernel 行里装得下多个传输页 |
| 整块一段 | **一段,与层数无关** | 整块存储按块连续,且要么层内不稠密、要么各层已打包进同一块存储 |
| 每层一段 | 一层一段 | 整块存储按块连续,层内也稠密 |
| 一层再切 | 一层切成多段 | 整块存储不按块连续,例如 head 维不连续 |

第三档是效率最高的形状,**段数与层数彻底脱钩**。但它目前被限制在多头潜在注意力那一类上,源码里的待办说明了原因:打包存储下的张量并行切分还没处理,而这类注意力的 KV 在各个 rank 上是复制的,不涉及切分。第五档最不利,段数成倍上涨;基准上还给它加了一道保护 —— 一层的字节数除不尽段大小就直接报错,而不是算出一个错的划分。

于是有一条不太直观的因果:**注意力后端选了什么物理排布,会一路传导到 PD 分离的传输吞吐上。** K 和 V 有没有打包进同一维、head 维是否连续,决定的不只是 kernel 好不好写。

### 2.3 注册和划段是两回事

同一次注册里有两个粒度,容易混成一个:

- **注册按底层存储走**,并且**按存储地址去重** —— 多层共享一块存储时,这块存储只注册一次
- **传输区间按层(或层内的连续 head 段)走** —— 也就是 2.2 那五档

分开的理由很直接:注册是告诉网卡「这片显存可以被远程访问」,它的单位是分配;划段是告诉传输引擎「一次搬哪一截」,它的单位是逻辑布局。两者恰好相等只是常见情况,不是定义。

### 2.4 混合模型让段数再翻几倍

模型里混进状态空间层之后,段数的算法要分两条路。

**全注意力是快路径**:所有 group 的层数相同、不同 group 的层共享同一份张量、不同 group 的块永远落在不同区域 —— 有这三条,一次向量化广播就能把所有 block 的描述符编号展平算完。

**含状态空间层就得逐层累加**:每个这样的层占的区间数是「卷积子投影数加一个时序区」,按具体变体是四个或两个。注释特意点明它必须与实际发出的描述符数量对得上 —— 这里算错不会立刻炸,只会让远端读到错位的内存。

还有一处不显眼的坑:**物理页大小在混合模型里可能不一致**。kernel 对块大小有要求时,状态空间层和注意力层的块数会不同,代码用一个「每个逻辑块折几个物理块」的比值来换算。这个比值一旦在两端不一致,握手阶段会直接拒绝配对。

### 2.5 分层传是能力上限,不是默认行为

「算完第 i 层就把第 i 层的 KV 发走,和第 i+1 层的计算重叠」—— 这个想法成立,而且抽象层为它留了两个钩子(逐层保存、逐层等待)。但**留了钩子不等于有人用**。基准上把三个实现逐个看过来:

| 实现 | 逐层保存钩子 | 实际行为 |
|---|---|---|
| LMCache | **有实质逻辑** | 但函数开头就检查开关,没开就直接返回 —— 逐层是可配置项,不是默认 |
| Mooncake 点对点 | 空实现 | KV 在请求结束后由后台协程整体搬走,**完全没有逐层重叠**,只有请求粒度的异步 |
| NIXL | 空实现 | 保存钩子空着;等待钩子也只在启用主机中转缓冲时才做事,而那仍是整体搬运 |

所以那张「逐层流水线」的图描述的是**能力上限**,不是默认路径。默认(拉)语义下真正发生的重叠是另一回事:**重叠在 D 侧** —— D 载入这条请求的 KV 时,GPU 正在给别的请求做 decode。它不是 P 的逐层 prefill 与传输重叠。

这一条也解释了 04 章为什么会记下「这条链路上没有逐层流水线」:那里看的是 NIXL,结论对;换成开了开关的 LMCache,结论就变了。**「有没有逐层」是按实现问的问题,不是按架构问的。**

### 2.6 整块传和分层传是两个正交方向,会互相削弱

2.2 说整块一段效率最高,2.5 说逐层发能和计算重叠 —— 这两件好事**不能同时拿满**。

原因是它们切的方向垂直:「一个 block 整段传」的前提是这个 block 在存储里是连续的一整截,而「算完第 i 层」产生的数据是**跨所有 block 的同一层**。要凑出「一个 block 一整段」的连续性,就得等这批 block 的全部层都写完 —— 也就是等整个 prefill 结束。

| | 每层一段 | 一个 block 整段 |
|---|---|---|
| 传输单位 | 每层一次,共 L 次 | 每块一次,一次含所有层 |
| 算完第 i 层能不能单独发 | 能 | 不能,要等这些块的所有层写完 |
| 能和什么重叠 | 第 i 层的传输与第 i+1 层起的计算 | 这一批的传输与下一批的计算 |

结论不是「整块传就不能重叠」,而是 **重叠的粒度变粗了**。而这个结论在 vLLM 上还有一层缓冲:**分块预填充默认开着**(02 章 1.3),长 prompt 本来就被切成一批批算,所以一批的块写满就能整体发出去,与下一批的计算重叠 —— 重叠还在,只是从「层」上移到了「块批次」。

对 Mooncake 与 NIXL 这类本来就不逐层的实现,整块传是**纯收益**:它们原本就是请求或批次粒度的整体搬运,没有可损失的逐层重叠。

## Part 3|延迟账:TTFT、TPOT 与瓶颈为什么在 P

### 3.1 异步的两端:P 发完就走,D 等齐才动

**P 侧发起传输后不等待**,立刻把 GPU 让给下一个 prefill,搬运在后台线程与网卡队列上跑。代价是块不能立刻归还:调度器要等 worker 报告「发完了」才真正释放,所以 **P 上一个块的占用时间是 prefill 时间加传输时间**。延迟释放那套栅栏机制 02 章 6.6 与 8.5 ⑥ 已经展开。

**D 侧必须等这条请求所有层的 KV 都到位才能开始 decode** —— decode 的第一步就要用全部层做注意力,少一层算不出来。所以等待远端 KV 是一个**请求级**状态,没有「半个请求可以调度」的中间态。

但「等」不等于「空等」:D 是多请求批处理的,这条请求在等 KV 的时候,GPU 照常在给别的请求做 decode。**空转的是这条请求,不是这张卡。**

### 3.2 暴露在 prefill 之外的那段延迟

真正值得算的不是总传输时间,而是**PD 分离比单机多付出的那部分** —— 被计算盖住的那些不算成本。

设模型 $L$ 层,每层 KV 大小 $S_{\text{layer}}$ 字节,带宽 $B$ 字节每秒,prefill 总耗时 $T_{\text{prefill}}$。记每层的计算耗时 $c = T_{\text{prefill}}/L$、每层的传输耗时 $t = S_{\text{layer}}/B$。逐层发送时,总墙钟时间取两种堵法的较大者:

$$
T_{\text{total}} = \max\bigl(T_{\text{prefill}} + t,\; c + L t\bigr)
$$

两个分支的含义完全不同:

- **计算挡住传输**($c \ge t$):传输永远不排队,每层算完就发走,最后一层算完时只剩它自己那一段还在路上。暴露延迟就是 $t$,**与层数无关**。
- **带宽挡住计算**($t > c$):传输排成一队,从第一层算完起就一直在发。暴露延迟是 $c + Lt - T_{\text{prefill}}$。

于是:

$$
T_{\text{exposed}} = T_{\text{total}} - T_{\text{prefill}} = \max\Bigl(t,\; \frac{T_{\text{prefill}}}{L} + \frac{L\,S_{\text{layer}}}{B} - T_{\text{prefill}}\Bigr)
$$

常见的写法会把第二个分支里的 $c$ 写成 $t$,那样会多算一层的量;在带宽是瓶颈时误差就是 $t - c$。

代入一组量级参考:八十层的 70B 模型,带宽 50 GB/s。**每层 KV 的大小取决于 prompt 有多长** —— 按 03 章 3.4 的口径,八个 rank 合计每层每块约 64 KB,所以「每层 50 MB」对应的是一条约 12.8K token 的 prompt。这时单层传输 1 ms、总传输 80 ms;只要 prefill 本身耗时不短于 80 ms,就落在计算挡住传输那一档,**暴露延迟压到约 1 ms**。

但这是**理论上限**,前提是真的逐层发。按 2.5 的审计,默认路径不逐层,暴露延迟接近完整的 80 ms 减去与后续请求计算重叠掉的那部分。**这一节的公式是用来判断「值不值得去开逐层」的,不是用来预测默认配置的表现的。**

### 3.3 首字 token 在哪一侧产出

理论上没有歧义:prefill 的最后一次前向就会产出最后一个位置的 logits,采样一下就是第一个输出 token。**所以首字是在 P 侧算出来的。**

但这个事实和用户看到什么之间隔着一层:**「把哪个 token 发给终端用户」vLLM 核心不管。** P 和 D 是两个独立实例,各自把结果返回给调用方,拼接与去重是外部网关的职责。所以「首字从哪出」不是一个 vLLM 配置项,而是部署方案的选择。

仓库内部唯一为这件事提供的支持,是请求结束时那组可以回传给网关的传输参数:请求里带上一个特定的键,P 侧就把自己采出的第一个 token 塞进返回参数,网关再把它拼进发往 D 的请求里,这样 D 不必重算首字。**它只在一个实现上有,而且是 opt-in 的** —— 另外两个主流实现里没有对应机制,用它们时首字怎么处理完全由网关自己决定。

### 3.4 「首字从 D 出」只有两条路

先排除一个直觉上的第三条:**KV cache 里没有首字 token。** KV 存的是 prompt 各位置的键值,首字来自最后一个位置的 logits,而 logits 不在 KV 里。所以让 D 吐出首字,只能:

1. **P 把 token 本身随元数据传过去** —— 就是 3.3 那个回传键。D 拿到 token id 直接吐给用户,不需要额外前向。
2. **D 重算最后一个位置** —— 只加载 prompt 前 N−1 个 token 的 KV,自己跑一次单 token 前向拿到 logits。调度器里对应的就是「整个 prompt 全部命中时把已算 token 数减一」那段逻辑(02 章 8.5 ④ 已展开,那里是从本地全命中的角度讲的,约束完全相同)。

第一条省算力,第二条少耦合。**两条都不是「拿 P 的隐状态再前向一次」** —— D 手里没有 P 的隐状态,传的只有 KV。

选哪条会被一个部署上的偏好推动:让首字也从 D 出,用户就只从一个连接收数据,不用合并两个流,token 顺序天然有保证。代价写在下一节。

### 3.5 KV 传输时间算在 TTFT 还是 TPOT

这个问题有一个干净的答案,前提是先看清 TPOT 是怎么来的。

**TPOT 不是测出来的,是派生的。** 基准的压测脚本里,它等于端到端时延减去 TTFT、再除以「输出 token 数减一」:

$$
\text{TPOT} = \frac{\text{Latency}_{\text{e2e}} - \text{TTFT}}{N - 1}
$$

这意味着 **TTFT 和 TPOT 把一条请求的全部时延完整瓜分了,中间没有真空区。** KV 传输时间必须落在其中一边,不存在「两边都不算」。落在哪一边,由 3.3 那个部署选择决定:

| 首字从哪出 | KV 传输时间的归属 | TTFT | TPOT |
|---|---|---|---|
| D 侧 | **完整计入 TTFT** | 排队 + prefill + KV 传输 + D 的第一步 | 干净,就是 decode 的单步耗时 |
| P 侧 | **摊销进 TPOT** | 排队 + prefill,不含传输 | 单步耗时 + 传输时间除以 N−1 |

摊销那一档有个容易忽略的后果:**传输时间被 N−1 除**,所以输出越长,它在 TPOT 上的体现越小。一条输出两千 token 的请求,80 ms 的传输摊下来是每个 token 0.04 ms,基本看不见;而一条只输出十几个 token 的请求,同样的 80 ms 会让 TPOT 看起来翻几倍。**同一套部署,在长输出和短输出两种负载下量出来的 TPOT 不可直接比较** —— 这不是抖动,是指标定义带来的。

所以看到「PD 分离之后 TPOT 变差了」这种结论时,先问一句首字是从哪一侧返回的。

### 3.6 均值会骗人:还要看逐 token 的间隔

摊销那一档还有一个更要紧的后果:**摊销会掩盖问题。**

一条输出 200 token 的请求,20 毫秒的 KV 传输摊下来是每 token 0.1 毫秒,在 TPOT 均值里几乎看不出来。但**这 20 毫秒并没有消失,它全压在第一个间隔上** —— 用户从首字等到第二个字的那一下,实打实地凸起 20 毫秒,后面才平稳。均值把这个尖峰用 N−1 个平稳值稀释掉了。

所以还要看另一个指标:**逐 token 间隔**,也就是相邻两个输出 token 之间的实际时间。它不做平均,尖峰原样保留,在 P99 上一眼可见。

这不是我们的发明 —— **基准的压测脚本本来就同时记录这两组数**:一组是每条请求的 TPOT,一组是把所有请求的逐 token 间隔拼起来的长列表。两组并存,正是因为它们回答的是不同的问题。

顺带一个细节能把 3.5 那个 N−1 分母的极端情形说透:脚本里其实有**两个** TPOT 列表 —— 一个只收输出长度大于一的请求,另一个把输出长度等于一的请求按 0 记进去用于算有效吞吐。**因为 N 等于 1 时根本没有「相邻两个 token」,TPOT 这个量压根不存在。** 分母能取到零,说明这个指标在短输出上本来就是脆的。

落到实践:**评估 PD 分离时不要只看 TPOT 均值。** 输出越短,摊销的分母越小,传输对 TPOT 的污染越明显;要判断用户是不是真的感觉到了卡顿,看逐 token 间隔的 P99 和 P999。

### 3.7 为什么瓶颈总是 P,而不是因为它算得多

生产上一个反复出现的现象:并发一上来,P 先撑不住,TTFT 暴涨,而 D 那边很闲。

先排除一个听起来很顺的错误解释:**不是因为 prefill 的总计算量比 decode 大。** 拿一条 prompt 长 $N$ 、隐层维度 $d$ 的请求算两边的总量:

| | prefill(一次算完 N 个) | decode(走 N 步,每步 1 个) |
|---|---|---|
| 线性层 | $O(Nd^2)$ | $N \times O(d^2) = O(Nd^2)$ |
| 注意力 | $O(N^2 d)$ | $\sum_{i=1}^{N} O(id) = O(N^2 d)$ |

**两边同阶。** 生成 N 个 token 的全程,和预填充 N 个 token,总浮点运算量是一个量级的 —— 所以「prefill 计算量远超 decode 全程」这个说法站不住。

真正的差别是**算术强度**,也就是每读一字节权重能摊到多少次浮点运算:

| | prefill | decode |
|---|---|---|
| 单次前向的运算量 | $O(Nd^2)$ | $O(d^2)$ |
| 单次前向要读的权重 | 全部权重,读一遍 | 全部权重,同样读一遍 |
| 算术强度 | 高:权重读一次服务 N 个 token | 极低:权重读一次只服务 1 个 token |
| 因此受限于 | 峰值算力 | 显存带宽 |

结论就藏在最后一行里:

- **P 的单卡吞吐被峰值算力硬性封顶。** 一条两千 token 的 prompt 就能把计算单元喂满,再加 batch 也提不上去,单卡 token 每秒是个常数级上限。
- **D 的单卡吞吐可以靠 batch 放大。** 单条请求的算术强度极低,把 B 条请求的各一个 token 拼成一个 batch,权重仍然只读一遍,有效吞吐近似线性上涨,直到带宽饱和。

**同样的浮点运算总量,D 能用少得多的 GPU 时间做完。** 这就是 02 章 1.3 那对「算力瓶颈对访存瓶颈」在部署尺度上的后果,也是 P 和 D 的卡数比例通常不是一比一的根本原因。

### 3.8 TTFT 不是缓慢上升的,是到某一点突然暴涨

把 P 集群看成一个排队系统:请求按某个速率到达,若干张卡当服务台。把多个服务台合成一个等效窗口来近似,逗留时间是

$$
T \approx \frac{1}{c\mu - \lambda}
$$

其中 $\lambda$ 是到达速率、 $c\mu$ 是集群总服务能力。严格的多服务台等待时间要用更复杂的公式,但结论一致,而且**这个近似恰好在接近饱和时最准** —— 两者都由分母那一项主导,而饱和区正是我们关心的地方。

代进去看:集群能力 10 QPS 时,到达 8 QPS 逗留 0.5 秒,到达 9.5 QPS 逗留 2 秒,到达逼近 10 QPS 则趋于无穷。

**利用率从八成涨到九成五,等待时间涨了四倍。** 这是个非线性关系,而且拐点很陡。两条实践结论直接由它得到:

- **P 集群不能按「刚好够用」配容量。** 留两成余量和留半成余量,在排队时间上差的不是两成,是几倍。
- **TTFT 暴涨不是因为 prefill 本身变慢了**,单条请求的前向耗时一点没变;暴涨的是排队等 P 资源的时间。所以看到 TTFT 抖动先查队列长度,而不是去优化 kernel。

### 3.9 分离不让任何一步变快,收益全在别处

一个容易搞错的前提先摆清:**PD 分离不会让单条请求的 prefill 更快,也不会让单步 decode 更快。** 同样的模型、同样的卡、同样的 batch,一次前向的耗时是一样的。收益全部来自三个地方,而且三笔账的形状各不相同。

**第一笔:TTFT 的收益来自排队,不是来自算得更快。**

TTFT 等于排队时间加 prefill 时间。后者两种部署基本相同,差别全在前者:混部时新来的 prefill 要和在跑的 decode 抢 step,还要等显存(decode 请求的块长期不释放),有效服务率被算力和显存双重压低;分离之后 P 上的块以百毫秒计周转(1.2),服务率就是纯 prefill 的服务率。

代进 3.8 的排队公式,**这笔收益是非线性的**:同样把服务率提高两成,在低负载区几乎看不出差别,在九成利用率附近能把排队时间砍掉一半以上。所以「PD 分离能把 TTFT 降低百分之多少」这个问题**没有唯一答案,它取决于你压在哪个负载点上。**

**第二笔:TPOT 的收益是方差,不是均值。**

单步 decode 的耗时由 batch 大小和显存带宽决定,分离并不会让它变小 —— 事实上 D 侧 batch 开大之后,单步耗时通常还会略增(虽然吞吐涨了)。真实收益在两处:**尾延迟**(混部时一条两千 token 的 prefill 插进来就是一次上百毫秒的 step 尖峰,分离后 decode 侧的 step 时间方差大幅收窄),以及**可用的 batch 上限**(不用给 prefill 预留显存和算力余量,D 的 batch 能开到真正的带宽饱和点)。

所以「TPOT 降低百分之几」这种说法要小心:**如果指的是均值,分离带来的变化很小,甚至可能变差**(多了 3.5 那个摊销项);真正稳定改善的是逐 token 间隔的 P99。

**第三笔:吞吐的收益可以估算。** 设混部时为了压住 TPOT 尖峰,不得不把 batch 限制在最优值的 $\alpha$ 倍( $\alpha < 1$ ),且每个 step 有 $\beta$ 比例的时间被 prefill 占用,则

$$
\frac{\text{Throughput}_{\text{PD}}}{\text{Throughput}_{\text{colocated}}} \approx \frac{1}{\alpha\,(1-\beta)} \times \frac{1}{1 + \text{overhead}_{\text{KV}}}
$$

这个式子(讲稿给的模型,不是代码里的公式)一眼能解释两个方向的现象:**长输出、高并发**时 $\alpha$ 小、 $\beta$ 大、一次传输服务几百个 token,分子大分母小,收益明显;**短输出、低并发**时 $\alpha$ 接近 1(本来就没必要限 batch)、 $\beta$ 小、一次传输只服务几个 token,分母的开销项占主导,**可能反而更慢**。

### 3.10 代价是确定的,不是概率的

收益要看负载点,代价却是四条摆在那里的确定项。

**一、多一次全量 KV 的搬运。** 以一个 64 层、8 个 KV head、head_dim 128、fp16 的 32B 模型为例,单 token 的 KV 是 `64 × 8 × 128 × 2 × 2` 字节等于 256 KB(全模型所有卡合计,口径同 02 章 1.6 —— 那里的 80 层模型按同一个公式是 320 KB)。一条两千 token 的 prompt 就是约 500 MB:50 GB/s 的 RDMA 下 10 毫秒,200 Gbps 网卡下 20 毫秒。**这笔时间按 3.5 的规则落在 TTFT 或逐 token 间隔上,不会凭空消失。**

**二、P 侧块的占用期变长。** 延迟释放让块一直占到传输完成(3.1),等价于 P 的有效块容量打了折。

**三、运维面变大。** 多一个网关、两套集群的配比、两端 connector 的握手兼容性 —— 其中最后一项很具体:物理块比值对不上就直接拒绝配对(2.4)。

**四、故障面变大,而且多出一条混部里根本不存在的路径。** KV 传输可能失败,于是调度器要能拿到「哪些块失效了」,据此把受影响请求的已算 token 数改回正确值、退回去重算。这条兜底路径 02 章 6.8 提过;**它在混部里完全不需要存在**,因为那里 KV 从来不过网。

## Part 4|注册、配置与声明

### 4.1 注册表里存的是 loader,不是类

1.4 说过引擎只认识一个基类。补一个实现上的讲究:**注册表存的不是类对象,而是一个惰性加载的闭包** —— 注册时只记下「模块路径加类名」,真要用时才去 import。

这一步不是洁癖,它解决一个很实际的问题:这些实现各自依赖不同的外部库(RDMA 库、分布式存储客户端、各家的 SDK)。如果注册即 import,**装了 vLLM 但没装 NIXL 的机器会在启动时直接失败**,哪怕它根本不打算用 PD 分离。惰性加载之后,配置里没点名的实现永远不会被 import。

基准上一共注册了 **16 个**名字(其中一个是别名,所以不同的类是 15 个,见 2.1),覆盖三类用途:PD 分离的传输(NIXL 三个名字、Mooncake 两种形态、MoRIIO)、本地或远端的 KV 卸载(CPU 卸载两个、分布式文件系统、FlexKV、LMCache 两种)、以及组合与工具(把多个实现串起来的组合实现、压测用的伪命中实现、两个示例模板)。

还有一条**不用改 vLLM 源码的自研入口**:配置里可以直接填模块路径,解析时先看有没有填 —— 填了就 import 那个模块、按名字取类,取不到就明确报「在这个路径里找不到这个类」;没填才回退到内置注册表。**写自己的 connector 走这条路,示例模板只是抄骨架用的参考。**

### 4.2 配置对象里有四个没人读的字段

这一层还留着一些**只剩下定义、没有任何读取方**的东西,而它们看起来完全像是能用的。

传输配置对象里有传输 rank、IP、端口、缓冲区大小四个字段,全部有默认值、全部出现在参数文档里,但在整个 `vllm` 包下**除了定义那一行之外没有任何地方读它们** —— 是上一代实现的遗留。真正在用的是另外几个:实现的注册名、实例唯一标识、角色、以及一个留给各实现自己解释的私有配置字典。

这件事有个具体的坑:**这几个名字在别处被别的东西用着。** 有的实现自己算了一个同名的 rank(从环境变量推出来的,和配置里那个无关),另一个实现有自己的本地端口字段。**同名不同物**,照着名字去 grep 很容易得出「它有人用」的结论。

同一层还有两个类似的痕迹:教程里常见的两个 connector 名字在注册表里**确实不存在**,但它们的名字还**残留在两个不同模块的注释里**。照名字搜会搜到,照名字配会启动失败。这是本仓库反复遇到的那条老经验的又一种形态 —— 前面几章遇到的是「注释描述的行为过期了」,这里是「注释点名的类已经没了」。

### 4.3 传输层还能反过来规定 KV 的物理排布

1.3 讲过传输层的要求约束了 KV 大张量**怎么申请**。还有更强的一档:它能规定这块张量**怎么排布**。

挂上 Mooncake 点对点传输时,它会要求整个引擎把 KV cache 的布局固定成一种特定的维度顺序,日志里写明了理由:**为了异构张量并行下的安全传输。** 这里的异构指 P 和 D 的并行度可以不同 —— 比如 P 用 8 路、D 用 4 路,一端的一个块要拆成另一端的几块。张量并行怎么切 KV head、切到 head 数不够时怎么复制,09 章 2.1 与 2.3 已经讲清;这里只用它的结论:**只有按这个 stride 顺序排,那次拆分才落在干净的边界上。**

**NIXL 也强制同一种布局**,但它给的理由不一样 —— 日志里写的是「为了更好的传输性能」。同一个要求、两家各说各的动机,而落到引擎上是同一件事:**布局被传输层定死了**。

例外也说得通:多头潜在注意力那一类**两家都不强制**,返回「没有要求」,因为它的 KV 在各个 rank 上是复制的,压根不涉及切分。

把 1.3 和这一节放在一起看,是同一条主线的两级:

| 传输层的要求 | 反过来约束了什么 |
|---|---|
| 要能注册成单一内存区 / 要能按 `storage.nbytes()` 判定 | KV 大张量**怎么申请**(补不补齐页边界) |
| 要能在异构并行度之间安全拆块 | KV 大张量的维度**怎么排** |

**一个「只负责搬数据」的模块,反向决定了显存里那块最大的张量长什么样。** 这是 PD 分离在架构上最不直观的一处代价:它不是加了一层,而是把自己的约束推回到了最底下。

### 4.4 一个壳,两份实现,运行时二选一

这些实现里,LMCache 的接入方式是独一份的:**vLLM 仓库里既有一个壳类,也内置了一份适配器快照**,壳类的构造函数里有个开关决定运行时用哪一份。默认走**外部包里的最新版**,把开关打开才用**仓库内置的这份快照**,两条路各自打一行不同的日志。

这么设计是因为 LMCache 是独立的开源项目,发版节奏和 vLLM 不同:默认跟外部包,它可以独立迭代;内置快照则把适配层的版本锁死,不受外部包更新影响。

**但有个前提别搞错:即便走内置快照,存储引擎本体仍然在外部包里。** 内置的那份只是适配层,文件顶部照样 import 外部包的缓存引擎、GPU 连接器与查询客户端。**锁的是适配器的版本,不是依赖本身** —— 机器上没装那个包,两条路都跑不起来。

适配层里还有一条硬约束:**多头潜在注意力与逐层模式互斥**,两个同时开会直接抛错,错误信息写着「还不支持」。所以 2.5 说的「逐层是可配置项」要再加一个前提 —— **模型不能是 MLA 那一类**。

### 4.5 connector 要向引擎声明五件事

1.3 和 4.3 分别给了传输层反向约束引擎的两个实例。到这里可以把这条主线收口了:**基类上有一组「声明」,connector 用它们告诉引擎自己需要什么、能做什么**,引擎据此调整行为。

| 声明 | 回答什么 | 默认 |
|---|---|---|
| 本地混合命中能否不齐 | 各 KV group 的命中长度允许不一致吗 | 否 |
| 是否要求可靠交付 | KV 必须送达吗 | **不是「否」,而是「这个实例是不是生产者」** |
| 需要什么 KV 布局 | 强制引擎用哪种维度顺序 | 不要求 |
| 是否需要分段图 | 逐层钩子要求 CUDA Graph 走分段模式 | 否 |
| 是否支持混合内存分配 | 能处理多个 KV cache group 吗 | 看有没有继承那个能力接口 |

第二行值得单独看:**它的默认值是一个表达式,不是常量。** 只有生产者在请求完成时才需要把 KV 交出去,所以默认值直接取「本实例是不是生产者」。为真时,一个请求若在交付尚未完成时被抢占,会走重算而不是让它「完成」—— 否则就会把已经释放掉的块交出去。而纯缓存类的实现会把它覆写成假,理由很干脆:**丢一次保存只是未来一次缓存未命中,不是正确性问题。**

最后一行的后果最具体。基准上实现了混合内存分配能力的共 **8 个**,而 **LMCache 不在其中** —— 用 LMCache 就意味着**只能有一个 KV cache group,状态空间层与注意力层混合的模型跑不了**。这和 2.4 讲的是同一件事的两端:那边是混合模型让传输段数翻几倍的代价,这边是干脆不支持。

**「传输层只是搬数据」这个印象到这里可以彻底放下了。** 它决定张量怎么申请(1.3)、怎么排布(4.3),现在还决定引擎能不能开混合内存分配、CUDA Graph 走哪种模式、以及一个请求被抢占时该重算还是该放行。

### 4.6 同一个实现,三种角色下开关不同

同一个 connector 类,配成不同角色时行为差别很大。以 LMCache 为例:

| 角色 | 存 | 取 |
|---|---|---|
| 生产者(P) | 保存时把 KV 推给 D | 取决于查询客户端支不支持「生产者复用」,不支持就直接返回零 |
| 消费者(D) | **直接早退,什么都不存** | 正常查询加取回 |
| 兼任 | 存 | 取 |

中间那行是个值得记住的设计判断:**decode 产生的 KV 不回存。** 技术上它和 prefill 产生的 KV 没有区别,存起来完全可行;但它对后续请求的前缀复用几乎没有价值(每条请求的输出都不一样),**存进去只会挤掉真正有用的前缀**。所以这不是「还没实现」,是刻意不做。

## Part 5|图解

02 章 6.5 已经从调度器视角画过三张图 —— PD 分离的架构总览、D 侧的完整状态机、端到端时序。**那三张这里不重复。** 本部分只画调度器视角看不见的两件事:一次传输在物理上经过哪几道,以及三种方向在时间轴上差在哪。

### 5.1 一次传输要经过的两个阶段

传输不是「把一块显存发过去」这么一步。它分成**启动期做一次**和**每条请求做一次**两个阶段,前者的产物是后者的前提:

| 阶段 | 做什么 | 产物 | 本章出处 |
|---|---|---|---|
| 启动期 · 一次 | 分配 KV 大张量 | 一整块生命周期等于进程的显存 | 1.3 |
| 启动期 · 一次 | 把它注册给网卡,按底层存储去重 | 一组可被远程读写的内存区 | 2.3 |
| 启动期 · 一次 | 逐层决定一个 block 占几段 | 传输区间清单(五档之一) | 2.2 |
| 每请求 · 一次 | 调度器侧问「远端能补多少」 | 命中量,以及要不要异步接收 | 1.6 |
| 每请求 · 一次 | 分配本地块,告知对端用哪些块接收 | 本地到远端的块号映射 | 1.6 |
| 每请求 · 一次 | worker 侧按区间清单发起读写 | 字节真的动了 | 3.1 |
| 每请求 · 一次 | 完成后回报,下一个 step 放行 | 请求进入可调度状态 | 1.6 |

**最容易被跳过的是前三行。** 它们在启动时就把「这块显存能不能被远程访问、一次能连续搬多长」定死了,而这三件事恰好决定了后面每一条请求的传输效率。**调度器完全看不见它们** —— 调度器只看得见倒数四行。

### 5.2 三种方向下,P 的块各占多久

2.1 给过三种方向的对照表。表说得清「谁发起」,说不清的是**时间上的差别** —— 而这个差别直接决定 P 能撑住多少并发:

![三种 KV 传输方向下 P 侧块占用时长的对比:每组上面一条是 P、下面一条是 D,P 那条横条的长度就是它的块被占住的时长——推要等 D 备好块并报回坐标才能开始写,拉要一直占到 D 把数据读完、而且 D 越忙这段空等越长,中转上传完就能撒手,是三者里最短、也是唯一与 D 的忙闲无关的一种。](/opensource/vllm/10a-transfer-direction.svg)

图的下半把三条 P 摞起来直接比,右端就是各自能把块还回池子的那一刻:

- **推**:P 不能算完就发 —— 它得先等 D 备好块、把坐标报过来(2.1 说的「P 需要知道 D」),写完才还。
- **拉**:P 必须把块**留到 D 来读完为止**,中间那段它什么也没做,纯粹在等,**而且这段有多长取决于 D 多忙**。这就是 04 章 3.3 那套租约加心跳续期存在的原因 —— 没有它,P 不知道该等多久。
- **中转**:P 把数据交给存储就撒手,占用时长最短,而且**它是唯一一种 P 的占用时长与 D 的忙闲无关的方案**。

回到 1.2 的那笔账:PD 分离在 P 侧省下的是 block 的占用时长。**拉模式把这笔收益吃掉了一部分**,吃掉多少取决于 D 有多忙。所以「PD 分离能撑多少 prefill 并发」这个问题,**答案和传输方向有关**,不只和卡数有关。

## Part 6|机制之外:源码里额外读到的

前五部分讲清了这套机制**应该怎么工作**。这一部分只放一类东西:照着源码读下来,**机制层面看不见、但真实存在的细节**。前面讲过的一概不重复;每条只答一件事:它是什么,以及不这么做会出什么事。

> 每条对应源码的哪个文件与符号,见代码索引页,正文不写。

### 6.1 声明了支持,不等于真支持

4.5 那张表里最后一行是靠「有没有继承某个能力接口」判定的 —— 而这个判定有一处特例。

**把多个实现串起来的那个组合实现,自己继承了这个接口,所以判定结果是「支持」。但它实际支不支持,取决于它包着的每一个子实现。** 工厂里因此专门有一个判定函数为它开了特例:是组合实现时不看它自己,而是逐个去问子实现。**声明在类型上,真相在配置里。**

同一处还有一个反直觉的小设计:「需要什么布局」那条声明是个类方法,有默认实现(返回「不要求」),但**在基类自己身上调用会直接抛类型错误**,错误信息写着不该在抽象基类上调它。看起来多余,实际上挡的是一类具体的错误:这是类方法,拿着基类去问「你要什么布局」在语法上完全合法,但语义上问错了对象 —— 基类不是一个可用的 connector。**把这种问法变成立即失败,比返回一个看似合理的「不要求」要安全。**

### 6.2 分配之后的回调可能被调两次

调度器分配完块会回调 connector 一次。这个回调有个容易踩的地方:**开了异步加载时,同一条请求会被回调两次** —— 先为待加载的那部分 KV 分配一次,传输完成之后再为剩下的部分分配一次。

docstring 还专门提醒了判断依据:**要不要加载,看的是 token 数,不能看块列表是不是空的。** 原因举的就是组合实现:**没被选中的那个子实现照样会收到请求的真实块列表**,块列表非空但该加载的 token 数是零。照块列表判断,它会以为轮到自己了。

### 6.3 抢占要赶在覆写之前通知

worker 侧有一个钩子,在绑定本步元数据**之前**调用,用途是处理被抢占的请求和被淘汰的块。

关键在那个「之前」。做异步保存的实现手里可能还攥着某些块 —— 保存还没完成,块却因为抢占被释放、接着被别的请求拿去写。**等到覆写发生再通知就晚了,存出去的会是别人的数据。** 所以这个钩子必须排在本步的一切之前,给这类实现一个「先把手里的活收掉」的机会。

这和 4.5 那条「是否要求可靠交付」是一对:后者决定被抢占时该重算还是该放行,前者给出动手的时机。**一个管判断,一个管时机,少任何一个都会漏。**

### 6.4 worker 侧有两套集成代码,都在用

仓库里同时存在**两套** worker 侧的 connector 集成,对应两代 model runner,**而且都在用**:

| | 形态 | 谁在用 |
|---|---|---|
| 旧 | 一个上下文管理器混入,把整个 connector 生命周期包在一次模型执行里 | 上一代 model runner |
| 新 | 一个显式对象,同一套钩子拆成三个方法 | 新一代 model runner |

两者调用的钩子序列几乎一致,差别在**组织方式**和**新增的两件事**。

**这不是孤例。** 06 章 2.4 查出 CUDA Graph 的派发器同样是两代并存 —— **同一个 model runner 分代,在执行层和传输层各留下了一份痕迹**。读这类代码时,「这个功能有几套实现」是个必须先问的问题,否则很容易拿旧那套的行为去解释新那套的现象。

新路径相对旧路径的三点差异:

1. **注册时机前移到构造函数。** 把 KV 张量交给 connector、设置主机缓冲的拷贝操作,都在对象创建时一次做完,不再散落在 model runner 各处。
2. **前向之前多了一步抢占通知。** 先把抢占信息交给 connector,再绑定本步元数据 —— 这正是 6.3 那个「必须赶在覆写之前」的时机要求在新路径上的落地。
3. **前向上下文缺失时自己造一个。** 代码里还留着一条待办,直白承认「connector 拿前向上下文当参数」这件事本身是个历史包袱。

### 6.5 用一个什么都不做的实现,替代「有没有」的判断

新路径里还有一处手法值得单独看:**基类本身就是一个空实现** —— 四个方法分别是什么都不做、返回空、返回一个空的模型输出、什么都不做。模块级别造好一个单例,取 connector 时没配就把它返回。

于是**热路径上不需要判断「有没有 connector」**:无论配没配,调用方都拿到一个对象,照常调它的方法。这和 06 章那条「宁可多算一点,也不要在热路径上加分支」是同一种取舍,只是这里省掉的不是计算,而是**每一步都要做的存在性判断**。

同一个对象上还有一个开关,能把整套逐层钩子**整体摘掉**:它直接把全局的 connector 句柄置空,于是注意力层里的逐层加载与保存钩子根本不会被触发。model runner 在显存探测、空跑这类阶段会用它临时关掉传输 —— **那些阶段跑的是假数据,传出去毫无意义,还会污染对端。**

### 6.6 两个声明的聚合方向是相反的

把多个 connector 串起来的那个组合实现,要把子实现的声明聚合成自己的。**两个声明的聚合方向正好相反**:

| 声明 | 怎么聚合 | 含义 |
|---|---|---|
| 本地混合命中能不能不齐 | **全体同意**才算支持 | 有一个子实现不支持,整体就不支持 |
| 是否要求可靠交付 | **任一要求**就算要求 | 有一个子实现要求,整体就得遵守 |

这不是随手写的,而是由两者的**语义**决定的:前者是**能力**声明,能力由短板决定,全员具备才敢开;后者是**约束**声明,约束由长板决定,任何一方的要求都必须满足。

**把这两种声明混为一谈,聚合方向就会写反 —— 而写反之后系统照样能跑**,只是在某些配置下悄悄丢数据或悄悄降级。这类错误没有崩溃现场,只有事后对不上的账。

同一处还有一条账本,记录每个请求「除第一个之外还有几个异步保存没完成」。注释解释了为什么加载不需要同样的账:**多个 connector 可以并行异步保存,但只允许其中一个负责异步加载。** 保存是各存各的,加载却必须有唯一的数据来源。

### 6.7 故意不进哈希的那三项

NIXL 握手时会比对一个**兼容性哈希**,把 vLLM 版本、connector 版本、模型结构、注意力后端、KV 数据类型、混合内存分配开关、推测解码配置,以及传输方向,全部揉进一个摘要。任一项不一致,**握手阶段就报错** —— 这是 fail-fast,总好过传出一堆错乱的数据。

传输方向为什么要进哈希,注释写得很直白:**推和拉用的是不兼容的传输协议,一个推的 connector 和一个拉的 connector 绝不能握手成功。**

但更值得记的是**哪几项故意没进哈希**:张量并行度、块大小、KV 布局。注释给了理由 —— 这三项在握手时**另有一段运行时校验**,不进哈希是**为了支持异构部署**。也就是说 P 用八路并行、D 用四路,两端块大小不同,都是允许的;而版本或模型结构对不上,一步都走不下去。

**这份哈希把「必须一致」和「可以不同」明确分成了两类:前者进哈希、一票否决,后者进运行时校验、按情况适配。** 设计任何跨实例握手时,这个分界本身比具体有哪几项更值得借鉴。

## Part 7|对比与决策

前六部分讲的是这套机制怎么造的。这一部分讲怎么用它:和别的方案比取舍在哪、什么时候该用、参数往哪边拧、出了问题先怀疑什么。

### 7.1 和别的 PD 分离方案比,vLLM 的取舍在哪

下表 vLLM 那一列全程对着源码核过;另外三列**不在本仓库、无法用源码校验**,是讲稿的定位参考,看个大概就行。

| 维度 | vLLM | DistServe | Splitwise | Mooncake |
|---|---|---|---|---|
| 架构 | connector 抽象加十六个内置注册名,另有仓库外扩展入口 | 专门设计 | 专门设计 | 以 KV 存储为中心 |
| 传输后端 | NIXL 为主,另有 Mooncake 与多级缓存库 | RDMA | NVLink | RDMA |
| 跨实例前缀共享 | 支持,靠内容哈希或 chunk 哈希 | 无 | 无 | 支持 |
| 谁做路由 | **外部网关,引擎不内置** | 专门的负载均衡 | GPU 池 | 专门的负载均衡 |
| 首字从哪出 | **取决于用哪个 connector** | P 出 | P 出 | P 出 |
| 适用场景 | 通用 | 大规模 | 单机大模型 | 跨集群 |

**三个决定性选择**,它们解释了前面所有设计:

1. **不内置路由。** 引擎里没有任何路由策略,拆请求、选 P 选 D 全在外部网关;引擎只负责把路由需要的坐标吐出来(1.5)。换来的是引擎不必知道集群拓扑,代价是部署方要自己写那一层。
2. **后端做成注册表加惰性加载,而不是绑定一种协议。** 十六个内置名字加一条不用改源码的自研入口,而且没配到的实现永远不会被 import —— 少装一个可选依赖不影响启动(4.1)。
3. **让传输层把约束推回引擎,而不是让引擎去适配传输层。** 于是 KV 大张量怎么申请、怎么排布、能不能开混合内存分配,都可能被 connector 决定(1.3、4.3、4.5)。**这一条是代价最大、也最容易被低估的一个选择。**

### 7.2 什么时候该用 PD 分离

判据只有一句:**高并发**和**长 prompt**同时成立才划算。三种不该用的情形,都能用 3.9 那个吞吐比公式解释:

| 情形 | 为什么不划算 |
|---|---|
| 卡数很少 | P 和 D 各自都凑不出一个能跑满的集群,拆开只是把利用率摊薄 |
| 负载以 decode 为主 | prefill 侧本来就闲,拆出来的 P 节点大半时间空载 |
| prompt 很短 | 一次传输只服务几个 token,公式里的开销项占主导,**可能反而更慢** |

反过来,**负载越是「长 prompt 加高并发」,收益越大**:混部时为压住尖峰而被迫限制的 batch 能放开,一次传输又能摊到几百个输出 token 上。

还有一个容易被忽略的维度:**传输方向也影响这笔账**(5.2)。拉模式下 P 的块要留到 D 读完,收益被吃掉一部分;要把 P 的并发压到最高,中转模式才是占用时长最短的那个。

### 7.3 关键参数

所有配置都收敛到一个 JSON 参数里,**没有独立的命令行开关**。

| 字段 | 默认 | 作用 |
|---|---|---|
| connector 注册名 | 无 | 用哪个实现;设了它就必须同时设角色,否则直接报错 |
| 角色 | 无 | 生产者 / 消费者 / 兼任;取值非法也报错。**兼任那档已被 NIXL 标为弃用**(1.4) |
| 实例唯一标识 | 自动生成 | 握手用 |
| 私有配置字典 | 空 | **真正的调参入口**,各实现自己解释 |
| 自研模块路径 | 无 | 仓库外 connector 的入口(4.1) |

私有配置里最常用的几个键:组合实现的子实现列表;多级缓存库的内置快照开关、逐层开关、D 侧跳过尾部若干 token;共享存储的查询开关与异步查询开关。**它们分属不同实现,填错了不会报错,只是不生效。**

**一条要单独警告的**:配置对象里还留着传输 rank、IP、端口、缓冲区大小四个字段,**照着旧教程填它们不会报错,但也不会有任何效果** —— 它们没有任何读取方(4.2)。当前各实现的地址与配对信息走的是别的通道:NIXL 走请求的传输参数加握手元数据,Mooncake 走它自己的引导服务,共享存储走环境变量指向的配置文件,多级缓存库走它自己的传输规格与环境变量。

### 7.4 常见误区

每条都是容易想当然、但源码里给出相反答案的地方。

| 误区 | 真相 |
|---|---|
| PD 分离总是更好 | 不。低并发或短 prompt 下,传输与协调的开销大于收益(7.2) |
| PD 分离会改变输出 | 不会。P 算出的 KV 交给 D 继续 decode,数学上等价于单节点 |
| P 侧传输完成后会释放显存 | 错。释放的是块的引用计数,那块大张量进程活着就常驻(1.3) |
| prefill 的总计算量远大于 decode 全程 | 错。两边同阶,P 成为瓶颈是因为算术强度低、被峰值算力封顶(3.7) |
| TPOT 里不含 KV 传输 | 错。首字从 P 出时传输被摊销进 TPOT,并在逐 token 间隔的 P99 上原样暴露(3.5、3.6) |
| 等远端 KV 的请求会直接转成运行态 | 错。先回到可调度状态,再正常被调度一次(02 章 6.7) |
| KV 传输都是逐层重叠的 | 错。两家主流实现的逐层钩子都是空的,只有多级缓存库要显式开开关,而且 MLA 模型下这个组合直接报错(2.5、4.4) |
| 主流实现强制的是 HND 布局 | 错。两家都强制 LBHNC,而且 MLA 模型下都不强制(4.3、6.7) |
| 不带方向的那个 NIXL 名字会按角色自动选推还是拉 | 错。它就是拉的向后兼容别名;要推必须显式写推的那个名字(2.1) |
| 那个旧的 connector 基类名已经不存在了 | 存在,但只是别名,整个文件十行,**不是父类**(4.2) |
| 教程里那两个 connector 名字还能用 | 不能。注册表里没有,只是名字还残留在注释里(4.2) |
| 用多级缓存库也能跑状态空间层与注意力混合的模型 | 不能。它没实现混合内存分配能力,调度器里会断言只有一个 KV cache group(4.5) |
| 填 rank 与 IP 端口就能指定对端 | 不会报错,但没有任何效果 —— 这四个字段没有读取方(4.2、7.3) |
| 组合多个 connector 时,只要有一个支持某能力就行 | 反了。**能力声明取全体同意,约束声明才取任一要求**(6.6) |
