# vLLM 11|量化

一次推理里有三样东西在吃资源:权重、激活、KV cache。它们按 BF16 计价时分别卡住显存、算力和上下文长度,而量化就是把其中某几样换成「低精度数据张量加若干个 scale」。这一章讲清 vLLM 里有哪些地方能量化、每一处是怎么量的、以及配错了会发生什么——最后这件事比想象中要紧,因为大多数配错的组合**不会报错**。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 三笔账,卡在三个不同的地方

不量化会出什么事?最直接的回答是「显存不够」,但这个回答太粗——三样东西吃的是同一块显存,卡住的却不是同一件事:

| 吃什么 | 量级 | 真正卡住的是什么 |
|---|---|---|
| **权重** | 与参数量成正比。70B 按 BF16 是 140GB | **装不装得下。** 一张卡装不下就必须切分,切了就要通信 |
| **激活** | 与这一步算多少 token 成正比 | **算力用了几成。** tensor core 有 8bit 通路,喂 BF16 等于只用一半 |
| **KV cache** | 与「上下文长度乘并发」成正比。70B 按 02 章 1.3.3 的口径是每 token 320KB | **能跑多长、多少并发。** 长上下文下它比权重还大 |

三个痛点方向不同,所以省法也不同,而且**省了一样不等于省了另一样**:

- **只量化权重** 的方案(W8A16)把权重换成 8bit,激活仍是 BF16。GEMM 的两个输入精度不一致,算之前还得把权重反量化回 BF16 才能乘——**省了显存,一点算力没省**,甚至多了一次反量化。
- **权重和激活一起量化** (W8A8)之后两个输入都是 8bit,才真正走得上 8bit tensor core:**省显存、省访存带宽、算力翻倍**。
- **再把 KV cache 压到 8bit** (W8A8C8)动的是第三笔账。长上下文或大 batch 时这一步收益最大,因为那时 KV cache 本来就是最大的那一块。

这条线索贯穿全章:**每一个量化方案,都可以先问它动了三笔账里的哪几笔。** 后面讲到的所有家族——权重-only 的 AWQ/GPTQ、4bit 的 NVFP4/MXFP4、KV cache 的十几种变体——差别首先在这里,其次才在数值格式和粒度上。

### 1.2 W、A、C:三笔账各自在哪里下手

vLLM 把这三笔账做成了三个正交的维度,名字就叫 W、A、C:

| 维度 | 量化的是什么张量 | 归谁管 |
|---|---|---|
| **W** (Weight) | `qkv_proj`、`o_proj`、`gate_up_proj`、`down_proj`,以及 MoE 各专家的权重矩阵 | 命令行的 `--quantization`,或 checkpoint 自带的 `quantization_config` |
| **A** (Activation) | 每个 Linear 的输入,也就是上一层的输出或 LayerNorm 的输出 | 同上,但具体开关在方案内部——`activation_scheme` 或 `input_activations` |
| **C** (KV Cache) | 写进分页 KV cache 的 key 与 value,以及可选的 query 和 softmax 输出 | 命令行的 `--kv-cache-dtype` |

「彼此独立、可任意组合」不是一句修辞:**W 和 A 由一个参数管,C 由另一个参数管,两个参数互不干涉。** 一个 BF16 模型可以只开 C8;一个 FP8 模型也可以让 KV 保持 BF16。所以读到「这个模型是 FP8 的」时,要追问一句:FP8 指的是 W、A 还是 C。

### 1.3 A8 不是 C8:同一个「8」,两套东西

这是全章最容易读错的一处,而且错了会一路错下去。**W8A8 里的 A8 指 Linear 层输入的量化,C8 指 KV cache 存储的量化。** 两者除了都是 8bit,几乎没有共同点:

| | A8(激活量化) | C8(KV cache 量化) |
|---|---|---|
| 用哪个 scale | `input_scale`(静态时来自 checkpoint) | `k_scale` 与 `v_scale` |
| 什么时候量 | 进 GEMM 之前 | 写进 cache 之前 |
| 走哪条代码 | FP8 走 `QuantFP8`,INT8 走 `scaled_int8_quant` | 走写 cache 的那个算子 |
| 量完之后 | 立刻被消费,不留存 | **要在显存里躺很久**,直到请求结束 |

最后一行是两者性质上的分野:**激活量化的误差只影响这一次乘法,KV cache 量化的误差要被后面每一步注意力反复读到。** 这也是为什么 KV cache 那一侧发展出了十几种数值格式(见 1.15),而激活那一侧只有寥寥几种——误差在时间上被放大的那一侧,值得用更复杂的格式去换精度。

### 1.4 三大类之外,还有几处能下手的地方

W、A、C 覆盖了绝大部分,但代码里还有几个位置也在量化。讲稿把它们排成一张平铺的清单,而源码里的结构比那整齐得多——它们其实分三类:

**两处仍然是 W,只是形状或默认值不同。** MoE 各专家的权重是三维张量(专家数乘输出维乘输入维),scale 也因此多一维,由融合 MoE 的量化方法族处理。`lm_head` 与 embedding **默认不量化**,被放在忽略名单里;AWQ 与 GPTQ 提供了显式打开的开关,compressed-tensors 有专门的 embedding 量化方法。

**三处在 attention 内部,而且是同一套。** query 在开了 C8 且后端支持时也会被量化成 FP8;softmax 的输出(FP8 attention 第二个 GEMM 的输入)有自己的 scale;attention 的输出可以**直接以量化形态交出去**,让下游的 `o_proj` 省掉一次量化。这三个容易被读成三个孤立的角落,实际上 **query、key、value、softmax 输出这四个 scale 是由同一个方法一次性创建的**,它们是一条链:进 attention 的量化、cache 里的量化、attention 内部第二个 GEMM 的量化。只有输出那个 scale 在 attention 层本身。

输出这一处还有个值得记的实现细节:**那个 scale 是 kernel 写出来的,不是传进去的。** 自定义算子的声明里把它和输出张量一起列为「会被修改的参数」——也就是说,scale 由算 attention 的那一步现场产出。这正是「输出直接量化好」这句话的实现方式:不是事后再量一遍,而是让算完的那个 kernel 顺手把 scale 也算出来。

**一处根本不是量化。** 权重的 Hadamard 旋转是量化**前**的等价变换,用来把离群值摊平到各个维度上,好让后续量化的动态范围小一些。它不改变数学结果,只改变数值分布。把它和量化本身混为一谈,会以为它也带精度损失。

### 1.5 量化在算什么:两个公式

量化就是把一段浮点数映射到一个小整数区间,再记住映射系数。分对称与非对称两种。

**对称量化** 假设分布以零为中心,零点固定在 0:

$$
s = \frac{\max |x|}{Q_{max}}, \qquad \hat{x} = \mathrm{clamp}\left(\mathrm{round}\left(\frac{x}{s}\right),\ Q_{min},\ Q_{max}\right), \qquad x \approx s \cdot \hat{x}
$$

**非对称量化** 不做这个假设,多带一个零点偏移:

$$
s = \frac{\max(x) - \min(x)}{Q_{max} - Q_{min}}, \qquad z = Q_{min} - \frac{\min(x)}{s}, \qquad \hat{x} = \mathrm{clamp}\left(\mathrm{round}\left(\frac{x}{s}\right) + z,\ Q_{min},\ Q_{max}\right)
$$

代价差别很直接:对称量化只需要存一个 scale,GEMM 里也只是乘个系数;非对称多一个零点,而零点在矩阵乘法里**不能简单地乘过去**——它会展开出一个额外的修正项,需要在权重那一侧预先算好一份补偿量。代码里这两样东西叫 `azp` 与 `azp_adj`(activation zero point 及其权重侧修正项)。所以非对称量化精度更好,但要多一份参数和一段额外计算。

### 1.6 $Q_{max}$ 从哪来,以及 ROCm 上那个 224

上面两个公式里的 $Q_{min}$ 与 $Q_{max}$ 由目标数值类型决定:

| 目标类型 | $Q_{min}$ | $Q_{max}$ | 备注 |
|---|---|---|---|
| INT8 | −128 | 127 | 整数类型的极值 |
| FP8 E4M3 | −448 | 448 | NVIDIA 平台的主流 8bit 浮点 |
| FP8 E4M3FNUZ | −224 | 224 | ROCm 专用 |
| FP8 E5M2 | −57344 | 57344 | 动态范围大、精度差,vLLM 只在 KV cache 上用 |

E5M2 那一行解释了它为什么只出现在 KV cache:指数位多一位、尾数少一位,能表示的范围宽得多但每一档之间更疏。KV cache 里偶尔出现的大值比普遍的小误差更致命,所以宽范围在那里划得来;GEMM 的输入不吃这一套。

第三行那个 224 值得单独看一眼,因为它是**硬编码的,而且和硬件手册对不上**。ROCm 用的 FNUZ 变体按规格最大值是 240,vLLM 却取 224。源码注释写明了理由:**按 240 走,ROCm 上做动态量化的模型会掉精度。** 于是这里牺牲了一点表示范围换数值稳定。判断平台并返回这对极值的那个函数只有九行,是本章少数几个行号在讲稿与基准之间完全没漂移的地方——顺带说明这段代码很久没动过。

### 1.7 8bit 为什么真能省:累加器永远是 FP32

把权重和激活都量化成 8bit 之后,矩阵乘法怎么算?对称量化下设 $A = s_a \hat{A}$、$B = s_b \hat{B}$,那么

$$
D = AB = s_a s_b (\hat{A}\hat{B})
$$

两个 scale 都是标量(或按行按列的向量),可以**提到乘法外面**。于是实际的执行是三步:8bit tensor core 算 $\hat{A}\hat{B}$、在 **FP32 累加器**里累加、在 epilogue 里乘上 $s_a s_b$ 再转回 BF16。

这条等式是理解整章 dtype 链路的锚点,而其中最容易想错的是中间那一步:**累加永远是 FP32,不是 FP16,也不是 8bit。** 8bit 只是乘法的输入格式;几千个乘积相加时,累加器必须有足够的动态范围,否则一路累下来早就溢出或被舍入吃掉了。后面讲每个方案的「计算流程与 dtype 转换」时,变的是输入格式和 scale 的形状,**不变的是这个 FP32 累加器**。

这也顺手解释了 1.1 里那句「只量化权重的方案一点算力没省」:它的两个输入精度不一致,凑不出上面这个可以把 scale 提到外面的形式,只能先把权重还原成 BF16 再走 BF16 的乘法。

### 1.8 一个 scale 管多大一片:粒度

上面的公式里,$\max|x|$ 是在多大一片数据上取的?这就是**粒度**,它是精度与开销之间的主旋钮:一个 scale 管的范围越小,越不容易被离群值拖累,但要存的 scale 越多、kernel 也越复杂。

vLLM 用一个二元组统一描述粒度,两个分量分别是「一个 scale 覆盖多少行、多少列」,`-1` 表示整个维度:

| 记号 | 一个 scale 管多大 | 通行叫法 |
|---|---|---|
| `(-1, -1)` | 整个张量 | per-tensor |
| `(1, -1)` | 每行,也就是每个 token | per-token,也叫 per-row |
| `(-1, 1)` | 每列,也就是每个输出通道 | per-channel,也叫 per-column |
| `(1, 16)` | 每行里 16 个元素一组 | NVFP4 的组 |
| `(1, 32)` | 每行里 32 个元素一组 | MX 系列的块 |
| `(1, 128)` | 每行里 128 个元素一组 | per-token-group,DeepSeek 的激活 |
| `(128, 128)` | 一个 128 乘 128 的二维块 | block-wise,DeepSeek 的权重 |

前三行是三个预置常量,后四行按需构造。这张表往下读会发现一件事:**新数值格式(NVFP4、MX 系)几乎都把粒度做得很细。** 位宽越低,能容忍的动态范围越窄,只能靠缩小每个 scale 的管辖范围来补——这是 4bit 方案的共同形状,Part 4 会逐个展开。

### 1.9 量化类型不是一串字符串,是一组预置常量

知道了 dtype 和粒度,还差一件事才能唯一确定「这是哪种量化」:scale 本身是静态的(来自 checkpoint)还是动态的(每次 forward 现算)。三者合起来,代码里叫一个 scale 的**完整描述**;再加上被量化的数据 dtype、可能存在的二级 scale、以及是否对称,就是一个**量化类型的唯一标识**。

这一层抽象的价值不在类本身,而在于:**代码里预先定义了一整批这样的常量。** `kFp8StaticTensorSym`、`kFp8DynamicTokenSym`、`kFp8Static128BlockSym`、`kFp8StaticChannelSym`、`kNvfp4Static`、`kMxfp8Dynamic`、`kMxfp4Static`,以及 MXFP6 的 E3M2 与 E2M3 两种布局各自的静态与动态版本……它们是模块级的具名常量,不是运行时拼出来的。

为什么这件事重要:**后面好几处「支持哪些量化」的判断,实现上就是一张以这种常量为键的字典。** 1.13 会看到在线量化的能力边界字面上就是两个这样的字典——所谓「只支持这几种」不是一条人为写下的限制,而是**字典里只有那几个键**。读到能力清单时,去找那张字典比去读文档可靠。

### 1.10 三层抽象:谁解析、谁建参数、谁真算

一个量化层从 checkpoint 到算出结果,要过三层:

```text
checkpoint 的 quantization_config
  |
  v
+--------------------------+
| QuantizationConfig       |   解析 checkpoint,决定这个模型用哪种方案
+--------------------------+   每种方案一个子类,逐层可以不同
  |
  v
+--------------------------+
| *LinearMethod            |   建权重与 scale 参数、加载后做后处理
+--------------------------+   不负责算
  |
  v
+--------------------------+
| kernel                   |   真正做那次矩阵乘
+--------------------------+   按格式分包:FP8/INT8、混精度、NVFP4、MXFP4/6/8
```

这个分层里有一件影响阅读的事:**GEMM kernel 不在量化方案的目录下,而是自己一个独立的包**,按数值格式而不是按量化方案分子包。也就是说 AWQ 和 GPTQ 这两个不同的方案,可能共用同一个混精度 kernel;而同一个 FP8 方案在不同硬件上会落到不同的 kernel 实现。**方案和 kernel 是多对多的**,这正是要把它们分开放的原因。

分包一共七个:FP8 与 INT8 的 scaled 矩阵乘、WNA16 的混精度(Marlin 与 Machete 那一族)、NVFP4、MXFP4、MXFP6、MXFP8,再加一个 CUTE DSL 的。其中 MXFP6 在讲稿里完全没有出现,但它不是空壳——上一节提到的两种 6bit 布局各有预置常量支撑。

### 1.11 kernel 是启动期两段筛出来的,不是算的时候挑的

上一节的第三层是怎么选定的?**在建权重的时候就选定了,不是每次 forward 现挑。** kernel 抽象基类的生命周期在注释里写得很清楚,四步:选 kernel、构造实例、加载后处理权重、推理时执行。选择发生在推理开始之前,所以热路径上没有任何分支——这和 06 章反复出现的那条原则一致:**宁可启动时多做一点,也不要在热路径上加判断。**

选择本身是**两段式**的,两个方法分工严格:

| 方法 | 只看什么 | 举例 |
|---|---|---|
| 硬件能力检查 | GPU 架构、compute capability、可用指令 | 「这个 kernel 需要 compute capability 至少 9.0」 |
| 配置能力检查 | 量化方案、粒度、静态还是动态 | 「这个 kernel 只支持静态量化」 |

两段的顺序是固定的:**先筛硬件,再筛配置。** 这一半解释了一个常被问到的现象——同一个量化格式的 checkpoint,换一张卡就走了另一条 kernel,模型和配置一个字没改。两个方法都返回「行不行」加「不行的原因」,调用方把原因记下来,所以某个 kernel 为什么没被选上是可查的。

这里有一处容易被讲反的地方。配置能力检查吃进去的是**每个 kernel 自己的一份配置对象**,不是上一节那个统一的量化类型标识——后者只是配置对象的**一个字段**。这个区别不是吹毛求疵,因为**这场统一还没做完**:FP8 那条路的配置对象里确实就是「权重的量化标识」加「激活的量化标识」两个字段,干净;而同一个文件里 INT8 那条路的配置对象**至今是三个裸布尔**(输入是不是静态方案、是不是按通道、输入是否对称),上面还挂着一条源码里自己写的待改注释,内容就是「改成像 FP8 那样用量化标识」。

所以准确的说法是:**统一描述是迁移中的目标,不是既成事实。** 读 FP8 那一支时可以按「一个标识说明一切」去理解,读 INT8 那一支时得准备好看到散装的布尔字段。

### 1.12 量化从哪来:三种来源,而且能叠

同样是「这个模型是 FP8 的」,量化这件事发生的时机可以完全不同:

| 来源 | 怎么触发 | 权重在磁盘上是什么 | 谁做的量化 |
|---|---|---|---|
| **离线 PTQ** | checkpoint 自带 `quantization_config` | 已经是 INT4/INT8/FP8 | 外部工具(llm-compressor、AutoAWQ、ModelOpt、Quark) |
| **在线量化** | `--quantization` 作用在 BF16 checkpoint 上 | BF16 或 FP16 | vLLM 自己,在加载后处理那一步 |
| **运行时动态量化** | 隐含在方案里(激活方案设成动态、KV 用按 token 按头的粒度) | 不涉及 | GPU kernel 每次 forward 现算 |

绝大多数线上场景是第一种。第二种的价值是**不需要预量化的 checkpoint**:手上只有 BF16 权重、又不想跑一遍离线量化流程时,加载时顺手量化。第三种严格来说不是一种「来源」,而是某些参数的量化时机本来就只能在运行时——激活和 KV 直到算出来才存在,不可能预先量好。

三者可以叠加,而且有两种不同的叠法。讲稿讲的那种是后两类相叠:离线的 FP8 权重,加上动态的 per-token 激活,加上动态的按 token 按头的 KV。**更值得知道的是第一类和第二类也能叠**——预量化的 checkpoint 之上还可以再挂在线量化,专门去补那个方案**没有覆盖的层**。源码注释把边界划得很清楚:checkpoint 自带的方案仍然是主方案,叠加在它的配置加载完之后才发生。于是「这个 checkpoint 是 W4A16 的,但它的 MoE 部分没量化」这种情况有救。

### 1.13 在线量化能做什么、不能做什么

在线量化的能力边界,字面上就是两张字典:一张给 Linear 层,一张给 MoE。键是 1.9 那种量化类型常量,值是对应的量化方法类。

| 格式与粒度 | Linear | MoE |
|---|---|---|
| FP8 per-tensor | 支持 | 支持 |
| FP8 128 块 | 支持 | 支持 |
| FP8 per-channel 权重加 per-token 激活 | 支持 | 支持 |
| MXFP8 | 支持 | 支持 |
| MXFP4 | 支持 | 支持 |
| INT8 per-channel | **不支持** | 支持 |
| NVFP4 | **不支持** | 支持 |

两张表共七个键,前五个两边都有(但各自对应独立的 Linear 版与 MoE 版方法类,不是同一个类复用),后两个只对 MoE 开放。

**清单之外还有一条边界更要紧:在线量化做不了 W4A16。** AWQ 与 GPTQ 那一族需要校准数据来决定每组的 scale 与零点,而加载时手上没有校准集,只有权重本身。所以 4bit 权重-only 这条路**必须离线**,没有在线版本。

最后是一处工程上的坑。配了一个不在上面表里的组合会怎样?**不报错,静默地不量化。** 分派函数查不到对应的键时,回落到「未量化」的那个方法类——Linear 一条路,MoE 一条路,都是正常返回,不是抛异常。这一段里**没有任何日志**,所以「静默」这个词在这里是准确的(而 07 章有一处看似相同的场景,基准上其实明确打了一条警告——同一个形容词必须逐处核,不能凭印象)。

想知道有没有中招,有一个可观测的入口:**匹配成功的层会被记一笔账**,记下它的量化来源、量化类型、以及命中的是哪条匹配规则。**没被量化的层就是这本账里缺的那些。** 排查「我明明开了量化,怎么显存没降」时,先去看这本账缺了谁。

这张表还有三件事值得说在前面:

**表不是封闭的。** 有一个注册装饰器允许外部注册自定义量化方案,注册时会把名字加进合法取值、也加进当前平台的支持清单;而且**自定义注册的合并排在内置项之后**,所以它能覆盖内置方案。看到一个不在表里的 `--quantization` 值,先怀疑有自定义注册。

**有一项的实现不在量化包里。** DeepSeek-V4 那个配置类是从模型族目录导入的,量化包只是登记了名字。这和 05 章那三个 DSV4 注意力后端是同一个形状:**名字注册在中央,实现放在模型族自己的目录里。** 按包名去找会找不到。

**所有配置类都是函数内延迟导入的。** 那张映射字典是函数的局部变量,所有配置类在函数体里才 import,注释写明了理由:避免过早触发编译。这解释了为什么这张字典不能在模块层面被读到。

### 1.15 KV cache 的十八种 dtype

`--kv-cache-dtype` 的合法取值另有一张类型字面量,共 **18 种**,是全项目里单个参数取值最多的一处:

| 取值 | 存储 dtype | 形态 |
|---|---|---|
| `auto` | 跟模型 dtype | 不量化,但见下面那条例外 |
| `float16`、`bfloat16` | 同名 | 不量化,显式指定,可以与模型 dtype 不同 |
| `fp8`、`fp8_e4m3` | uint8 | per-tensor 的 E4M3,主流 C8 |
| `fp8_e5m2` | uint8 | per-tensor 的 E5M2。Ampere 上唯一可用的 fp8 KV,FlashAttention 不支持 |
| `fp8_inc` | 真正的 fp8 dtype | Intel Gaudi |
| `fp8_ds_mla` | uint8 | DeepSeek MLA 专用的 fp8 布局 |
| `nvfp4_ds_mla` | uint8 | 同上,NVFP4 版本 |
| `int8_per_token_head` | int8 | 每个 (token, head) 动态算一个 scale |
| `int4_per_token_head` | uint8 | 同上,4bit |
| `fp8_per_token_head` | uint8 | 同上,FP8 |
| `nvfp4` | uint8 | FP4 数据加 FP8 块 scale 打包 |
| `nvfp4_4over6` | uint8 | NVFP4 布局,但每 16 个值在两个候选 scale 里挑重建误差更小的那个 |
| `turboquant_k8v4` | uint8 | key 用 FP8、value 用 4bit |
| `turboquant_4bit_nc` | uint8 | key 与 value 都 4bit,加范数修正。约 3.8 倍压缩 |
| `turboquant_k3v4_nc` | uint8 | key 3bit、value 4bit,加范数修正。约 3.5 倍 |
| `turboquant_3bit_nc` | uint8 | key 与 value 都 3bit,加范数修正。约 4.9 倍 |

压缩倍数是量级参考,不是本仓库实测。

**多数低精度格式都用 uint8 存。** 这不是含糊,而是刻意的:4bit、3bit 这些位宽没有对应的张量 dtype,只能打包进字节数组,由 kernel 自己按布局解包。所以「存储 dtype 是 uint8」在这张表里等价于「有一套自定义的打包布局」,而 `fp8_inc` 那一行用真 fp8 dtype 是少数例外。

有两行的细节容易踩:

**`auto` 不总是「不量化」。** checkpoint 里声明了 KV 量化算法时,`auto` 会被解析成 fp8。更进一步,**少数模型默认就是 fp8**,要退回 BF16 必须显式写出来。而这里有个反向的坑:字段说明紧接着写了**对于不默认 fp8 的模型,显式写 `bfloat16` 是非法选项**——它不是一个「总是安全的保守选择」,在普通模型上写它会直接被拒。

**平台支持不一样。** 同一个字段的说明里带着一张平台矩阵:CUDA 11.8 及以上支持 `fp8`(等于 `fp8_e4m3`)与 `fp8_e5m2`,ROCm 只支持 `fp8`,Intel Gaudi 走 `fp8_inc`。挑格式之前先看平台。

`nvfp4_4over6` 那一行值得单独欣赏一下它的做法:同样是 NVFP4 的布局,但每 16 个值不是直接用最大值定 scale,而是在「最大值除以 6」和「最大值除以 4」两个候选里,选**平方重建误差更小**的那一个。多一次试算,换一点精度——这是 4bit 方案里很典型的思路。基准上只有一个后端声明支持它。

### 1.16 简写、双身份,以及 checkpoint 优先

`--quantization` 的取值里有一批是**在线量化的简写**,它们不对应独立的配置类,只是「在线量化框架加一组固定配置」的语法糖。脱糖规则是一张字典,**共七个键**:FP8 的三种粒度、MXFP8、MXFP4、MoE 的 INT8 per-channel、MoE 的 NVFP4。后两个的配置里**只有 MoE 一项、没有 Linear 项**,源码注释直接写着「Linear 保持不量化」——这就是 1.13 那张表里两行「不支持」的来源。NVFP4 那一项还带一条硬件限定,只在 Blackwell 加特定后端上可用。

这里有一处结构上很有意思的冲突:**七个简写里有两个名字同时也是 checkpoint 方案的名字**——MXFP8 和 MXFP4。同一个字符串,既可能是「用在线量化按这个格式量」,也可能是「这个 checkpoint 就是这个格式」。代码怎么分辨?

**注册简写用的是「不覆盖已有键」的写法,所以 checkpoint 路径优先。** 某些厂商的 checkpoint 会把量化方法标成 `mxfp8`,这种情况下走的是 ModelOpt 那份配置类,而不是在线量化。

但「那么 `--quantization mxfp8` 就走在线量化了」这个推论**不成立**,这是本章最容易想错的一处。这两个名字被单独列进了一个**延后名单**,注释写明:它们也是 checkpoint 方案名,**它们的在线配置只在 checkpoint 没有量化元数据时才被解析**。落到代码上就是:只给了 `--quantization mxfp8`、没给量化配置参数时,解析函数**直接返回空**,把决定权交回 checkpoint 元数据。要真正走在线量化,必须**两个参数一起给**。

所以这两个名字的准确语义是:「如果 checkpoint 自己说了它是什么,听 checkpoint 的;否则再看有没有给在线配置」。分流确实发生在那个解析函数里,但方向是**默认让位**,不是默认在线。

顺带把两个 CLI 参数的关系收口:**`--quantization` 管 W 和 A,`--kv-cache-dtype` 管 C,两者正交。** 一个 BF16 模型可以只开 C8;一个 FP8 模型也可以让 KV 保持 BF16。1.2 说过这件事,这里是它在参数层面的对应。

### 1.17 量化前的基准:各张量原本是什么形状

后面每一个方案做的事,都是把下表中的某几行换成「低精度数据张量加若干个 scale」。所以先把量化**前**的形状钉住,当作全章的对照底。形状里的维度名对应源码里的哪个变量,一并列出——这几个名字在读任何一个量化方法的建参数代码时都会遇到:

| 张量 | 量化前形状 | dtype |
|---|---|---|
| Linear 权重 | 输出维乘输入维 | bf16 |
| Linear 输入激活 | token 总数乘输入维 | bf16 |
| Linear 输出 | token 总数乘输出维 | bf16 |
| attention 的 query | token 总数、query 头数、每头维度 | bf16 |
| attention 的 key 与 value | token 总数、KV 头数、每头维度 | bf16 |
| KV cache | block 数、KV 头数、每 block 的 token 数、两倍每头维度 | bf16 |

| 维度 | 源码变量 | Llama-3-8B 取值 |
|---|---|---|
| 隐藏维 | `hidden_size` | 4096 |
| query 头数与 KV 头数 | `num_attention_heads`、`num_key_value_heads` | 32 与 8 |
| 每头维度 | `head_dim` | 128 |
| Linear 输入维(张量并行切分后) | `input_size_per_partition` | `qkv_proj` 是 4096 |
| Linear 输出维(张量并行切分后) | `output_size_per_partition` | `qkv_proj` 是 6144 |
| 融合层里有几个独立 Linear | `output_partition_sizes` 的长度 | `qkv_proj` 是 3 |
| 权重分组大小 | `group_size` | 128 |
| 权重二维块尺寸 | `weight_block_size` | 非块量化时不存在 |
| 本 rank 上的专家数 | `local_num_experts` | 仅 MoE 模型 |
| FFN 中间维(切分后) | `intermediate_size_per_partition` | 14336 |
| 每 block 容纳的 token 数 | `block_size` | 默认 16 |

两条换算后面反复用到:

**`qkv_proj` 的输出维是三段之和**,query 一段加 key、value 各一段。Llama-3-8B 上是 32 乘 128 加上两倍的 8 乘 128,即 4096 加 2048 等于 6144。

**没有「batch 乘 seq」这两维。** 表里的「token 总数」是整个 batch 展平后的一维长度,等于各请求本次要算的 token 数之和——调度器把整个 batch 拼成一维再进模型,机制见 02 章 2.7。prefill 时它是几千,纯 decode 时它约等于并发数。

最后那张表里,「融合层里有几个独立 Linear」这一行是后面理解 scale 形状的钥匙。`qkv_proj` 逻辑上是三个 Linear 融合成一个、`gate_up_proj` 是两个,而 **per-channel 的 scale 要按这几段分别算**——一个融合层的 scale 张量因此不是一整条,而是按段拼起来的。这个细节在 1.8 的粒度表里看不出来,要到具体方案的建参数代码里才显形。

KV cache 那一行的「布局随后端变」不在本章展开:五维形状与布局枚举在 03 章已经讲过,`block_size` 的取值权衡也在那里。
