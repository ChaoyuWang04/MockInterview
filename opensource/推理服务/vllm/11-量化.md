# vLLM 11|量化

一次推理里有三样东西在吃资源:权重、激活、KV cache。它们按 BF16 计价时分别卡住显存、算力和上下文长度,而量化就是把其中某几样换成「低精度数据张量加若干个 scale」。这一章讲清 vLLM 里有哪些地方能量化、每一处是怎么量的、以及配错了会发生什么——最后这件事比想象中要紧,因为大多数配错的组合**不会报错**。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理

### 1.1 三笔账,卡在三个不同的地方

不量化会出什么事?最直接的回答是「显存不够」,但这个回答太粗——三样东西吃的是同一块显存,卡住的却不是同一件事:

| 吃什么 | 量级 | 真正卡住的是什么 |
|---|---|---|
| **权重** | 与参数量成正比。70B 按 BF16 是 140GB | **装不装得下。** 一张卡装不下就必须切分,切了就要通信 |
| **激活** | 与这一步算多少 token 成正比 | **算力用了几成。** tensor core 有 8bit 通路,喂 BF16 等于只用一半 |
| **KV cache** | 与「上下文长度乘并发」成正比。70B 按 02 章 1.3.3 的口径是每 token 320KB | **能跑多长、多少并发。** 长上下文下它比权重还大 |

三个痛点方向不同,所以省法也不同,而且**省了一样不等于省了另一样**:

- **只量化权重** 的方案(W8A16)把权重换成 8bit,激活仍是 BF16。GEMM 的两个输入精度不一致,算之前还得把权重反量化回 BF16 才能乘——**省了显存,一点算力没省**,甚至多了一次反量化。
- **权重和激活一起量化** (W8A8)之后两个输入都是 8bit,才真正走得上 8bit tensor core:**省显存、省访存带宽、算力翻倍**。
- **再把 KV cache 压到 8bit** (W8A8C8)动的是第三笔账。长上下文或大 batch 时这一步收益最大,因为那时 KV cache 本来就是最大的那一块。

这条线索贯穿全章:**每一个量化方案,都可以先问它动了三笔账里的哪几笔。** 后面讲到的所有家族——权重-only 的 AWQ/GPTQ、4bit 的 NVFP4/MXFP4、KV cache 的十几种变体——差别首先在这里,其次才在数值格式和粒度上。

### 1.2 W、A、C:三笔账各自在哪里下手

vLLM 把这三笔账做成了三个正交的维度,名字就叫 W、A、C:

| 维度 | 量化的是什么张量 | 归谁管 |
|---|---|---|
| **W** (Weight) | `qkv_proj`、`o_proj`、`gate_up_proj`、`down_proj`,以及 MoE 各专家的权重矩阵 | 命令行的 `--quantization`,或 checkpoint 自带的 `quantization_config` |
| **A** (Activation) | 每个 Linear 的输入,也就是上一层的输出或 LayerNorm 的输出 | 同上,但具体开关在方案内部——`activation_scheme` 或 `input_activations` |
| **C** (KV Cache) | 写进分页 KV cache 的 key 与 value,以及可选的 query 和 softmax 输出 | 命令行的 `--kv-cache-dtype` |

「彼此独立、可任意组合」不是一句修辞:**W 和 A 由一个参数管,C 由另一个参数管,两个参数互不干涉。** 一个 BF16 模型可以只开 C8;一个 FP8 模型也可以让 KV 保持 BF16。所以读到「这个模型是 FP8 的」时,要追问一句:FP8 指的是 W、A 还是 C。

### 1.3 A8 不是 C8:同一个「8」,两套东西

这是全章最容易读错的一处,而且错了会一路错下去。**W8A8 里的 A8 指 Linear 层输入的量化,C8 指 KV cache 存储的量化。** 两者除了都是 8bit,几乎没有共同点:

| | A8(激活量化) | C8(KV cache 量化) |
|---|---|---|
| 用哪个 scale | `input_scale`(静态时来自 checkpoint) | `k_scale` 与 `v_scale` |
| 什么时候量 | 进 GEMM 之前 | 写进 cache 之前 |
| 走哪条代码 | FP8 走 `QuantFP8`,INT8 走 `scaled_int8_quant` | 走写 cache 的那个算子 |
| 量完之后 | 立刻被消费,不留存 | **要在显存里躺很久**,直到请求结束 |

最后一行是两者性质上的分野:**激活量化的误差只影响这一次乘法,KV cache 量化的误差要被后面每一步注意力反复读到。** 这也是为什么 KV cache 那一侧发展出了十几种数值格式(见 1.15),而激活那一侧只有寥寥几种——误差在时间上被放大的那一侧,值得用更复杂的格式去换精度。

### 1.4 三大类之外,还有几处能下手的地方

W、A、C 覆盖了绝大部分,但代码里还有几个位置也在量化。讲稿把它们排成一张平铺的清单,而源码里的结构比那整齐得多——它们其实分三类:

**两处仍然是 W,只是形状或默认值不同。** MoE 各专家的权重是三维张量(专家数乘输出维乘输入维),scale 也因此多一维,由融合 MoE 的量化方法族处理。`lm_head` 与 embedding **默认不量化**,被放在忽略名单里;AWQ 与 GPTQ 提供了显式打开的开关,compressed-tensors 有专门的 embedding 量化方法。

**三处在 attention 内部,而且是同一套。** query 在开了 C8 且后端支持时也会被量化成 FP8;softmax 的输出(FP8 attention 第二个 GEMM 的输入)有自己的 scale;attention 的输出可以**直接以量化形态交出去**,让下游的 `o_proj` 省掉一次量化。这三个容易被读成三个孤立的角落,实际上 **query、key、value、softmax 输出这四个 scale 是由同一个方法一次性创建的**,它们是一条链:进 attention 的量化、cache 里的量化、attention 内部第二个 GEMM 的量化。只有输出那个 scale 在 attention 层本身。

输出这一处还有个值得记的实现细节:**那个 scale 是 kernel 写出来的,不是传进去的。** 自定义算子的声明里把它和输出张量一起列为「会被修改的参数」——也就是说,scale 由算 attention 的那一步现场产出。这正是「输出直接量化好」这句话的实现方式:不是事后再量一遍,而是让算完的那个 kernel 顺手把 scale 也算出来。

**一处根本不是量化。** 权重的 Hadamard 旋转是量化**前**的等价变换,用来把离群值摊平到各个维度上,好让后续量化的动态范围小一些。它不改变数学结果,只改变数值分布。把它和量化本身混为一谈,会以为它也带精度损失。

### 1.5 量化在算什么:两个公式

量化就是把一段浮点数映射到一个小整数区间,再记住映射系数。分对称与非对称两种。

**对称量化** 假设分布以零为中心,零点固定在 0:

$$
s = \frac{\max |x|}{Q_{max}}, \qquad \hat{x} = \mathrm{clamp}\left(\mathrm{round}\left(\frac{x}{s}\right),\ Q_{min},\ Q_{max}\right), \qquad x \approx s \cdot \hat{x}
$$

**非对称量化** 不做这个假设,多带一个零点偏移:

$$
s = \frac{\max(x) - \min(x)}{Q_{max} - Q_{min}}, \qquad z = Q_{min} - \frac{\min(x)}{s}, \qquad \hat{x} = \mathrm{clamp}\left(\mathrm{round}\left(\frac{x}{s}\right) + z,\ Q_{min},\ Q_{max}\right)
$$

代价差别很直接:对称量化只需要存一个 scale,GEMM 里也只是乘个系数;非对称多一个零点,而零点在矩阵乘法里**不能简单地乘过去**——它会展开出一个额外的修正项,需要在权重那一侧预先算好一份补偿量。代码里这两样东西叫 `azp` 与 `azp_adj`(activation zero point 及其权重侧修正项)。所以非对称量化精度更好,但要多一份参数和一段额外计算。

### 1.6 $Q_{max}$ 从哪来,以及 ROCm 上那个 224

上面两个公式里的 $Q_{min}$ 与 $Q_{max}$ 由目标数值类型决定:

| 目标类型 | $Q_{min}$ | $Q_{max}$ | 备注 |
|---|---|---|---|
| INT8 | −128 | 127 | 整数类型的极值 |
| FP8 E4M3 | −448 | 448 | NVIDIA 平台的主流 8bit 浮点 |
| FP8 E4M3FNUZ | −224 | 224 | ROCm 专用 |
| FP8 E5M2 | −57344 | 57344 | 动态范围大、精度差,vLLM 只在 KV cache 上用 |

E5M2 那一行解释了它为什么只出现在 KV cache:指数位多一位、尾数少一位,能表示的范围宽得多但每一档之间更疏。KV cache 里偶尔出现的大值比普遍的小误差更致命,所以宽范围在那里划得来;GEMM 的输入不吃这一套。

第三行那个 224 值得单独看一眼,因为它是**硬编码的,而且和硬件手册对不上**。ROCm 用的 FNUZ 变体按规格最大值是 240,vLLM 却取 224。源码注释写明了理由:**按 240 走,ROCm 上做动态量化的模型会掉精度。** 于是这里牺牲了一点表示范围换数值稳定。判断平台并返回这对极值的那个函数只有九行,是本章少数几个行号在讲稿与基准之间完全没漂移的地方——顺带说明这段代码很久没动过。

### 1.7 8bit 为什么真能省:累加器永远是 FP32

把权重和激活都量化成 8bit 之后,矩阵乘法怎么算?对称量化下设 $A = s_a \hat{A}$、$B = s_b \hat{B}$,那么

$$
D = AB = s_a s_b (\hat{A}\hat{B})
$$

两个 scale 都是标量(或按行按列的向量),可以**提到乘法外面**。于是实际的执行是三步:8bit tensor core 算 $\hat{A}\hat{B}$、在 **FP32 累加器**里累加、在 epilogue 里乘上 $s_a s_b$ 再转回 BF16。

这条等式是理解整章 dtype 链路的锚点,而其中最容易想错的是中间那一步:**累加永远是 FP32,不是 FP16,也不是 8bit。** 8bit 只是乘法的输入格式;几千个乘积相加时,累加器必须有足够的动态范围,否则一路累下来早就溢出或被舍入吃掉了。后面讲每个方案的「计算流程与 dtype 转换」时,变的是输入格式和 scale 的形状,**不变的是这个 FP32 累加器**。

这也顺手解释了 1.1 里那句「只量化权重的方案一点算力没省」:它的两个输入精度不一致,凑不出上面这个可以把 scale 提到外面的形式,只能先把权重还原成 BF16 再走 BF16 的乘法。

### 1.8 一个 scale 管多大一片:粒度

上面的公式里,$\max|x|$ 是在多大一片数据上取的?这就是**粒度**,它是精度与开销之间的主旋钮:一个 scale 管的范围越小,越不容易被离群值拖累,但要存的 scale 越多、kernel 也越复杂。

vLLM 用一个二元组统一描述粒度,两个分量分别是「一个 scale 覆盖多少行、多少列」,`-1` 表示整个维度:

| 记号 | 一个 scale 管多大 | 通行叫法 |
|---|---|---|
| `(-1, -1)` | 整个张量 | per-tensor |
| `(1, -1)` | 每行,也就是每个 token | per-token,也叫 per-row |
| `(-1, 1)` | 每列,也就是每个输出通道 | per-channel,也叫 per-column |
| `(1, 16)` | 每行里 16 个元素一组 | NVFP4 的组 |
| `(1, 32)` | 每行里 32 个元素一组 | MX 系列的块 |
| `(1, 128)` | 每行里 128 个元素一组 | per-token-group,DeepSeek 的激活 |
| `(128, 128)` | 一个 128 乘 128 的二维块 | block-wise,DeepSeek 的权重 |

前三行是三个预置常量,后四行按需构造。这张表往下读会发现一件事:**新数值格式(NVFP4、MX 系)几乎都把粒度做得很细。** 位宽越低,能容忍的动态范围越窄,只能靠缩小每个 scale 的管辖范围来补——这是 4bit 方案的共同形状,Part 4 会逐个展开。

### 1.9 量化类型不是一串字符串,是一组预置常量

知道了 dtype 和粒度,还差一件事才能唯一确定「这是哪种量化」:scale 本身是静态的(来自 checkpoint)还是动态的(每次 forward 现算)。三者合起来,代码里叫一个 scale 的**完整描述**;再加上被量化的数据 dtype、可能存在的二级 scale、以及是否对称,就是一个**量化类型的唯一标识**。

这一层抽象的价值不在类本身,而在于:**代码里预先定义了一整批这样的常量。** `kFp8StaticTensorSym`、`kFp8DynamicTokenSym`、`kFp8Static128BlockSym`、`kFp8StaticChannelSym`、`kNvfp4Static`、`kMxfp8Dynamic`、`kMxfp4Static`,以及 MXFP6 的 E3M2 与 E2M3 两种布局各自的静态与动态版本……它们是模块级的具名常量,不是运行时拼出来的。

为什么这件事重要:**后面好几处「支持哪些量化」的判断,实现上就是一张以这种常量为键的字典。** 1.13 会看到在线量化的能力边界字面上就是两个这样的字典——所谓「只支持这几种」不是一条人为写下的限制,而是**字典里只有那几个键**。读到能力清单时,去找那张字典比去读文档可靠。

### 1.10 三层抽象:谁解析、谁建参数、谁真算

一个量化层从 checkpoint 到算出结果,要过三层:

```text
checkpoint 的 quantization_config
  |
  v
+--------------------------+
| QuantizationConfig       |   解析 checkpoint,决定这个模型用哪种方案
+--------------------------+   每种方案一个子类,逐层可以不同
  |
  v
+--------------------------+
| *LinearMethod            |   建权重与 scale 参数、加载后做后处理
+--------------------------+   不负责算
  |
  v
+--------------------------+
| kernel                   |   真正做那次矩阵乘
+--------------------------+   按格式分包:FP8/INT8、混精度、NVFP4、MXFP4/6/8
```

这个分层里有一件影响阅读的事:**GEMM kernel 不在量化方案的目录下,而是自己一个独立的包**,按数值格式而不是按量化方案分子包。也就是说 AWQ 和 GPTQ 这两个不同的方案,可能共用同一个混精度 kernel;而同一个 FP8 方案在不同硬件上会落到不同的 kernel 实现。**方案和 kernel 是多对多的**,这正是要把它们分开放的原因。

分包一共七个:FP8 与 INT8 的 scaled 矩阵乘、WNA16 的混精度(Marlin 与 Machete 那一族)、NVFP4、MXFP4、MXFP6、MXFP8,再加一个 CUTE DSL 的。其中 MXFP6 在讲稿里完全没有出现,但它不是空壳——上一节提到的两种 6bit 布局各有预置常量支撑。

### 1.11 kernel 是启动期两段筛出来的,不是算的时候挑的

上一节的第三层是怎么选定的?**在建权重的时候就选定了,不是每次 forward 现挑。** kernel 抽象基类的生命周期在注释里写得很清楚,四步:选 kernel、构造实例、加载后处理权重、推理时执行。选择发生在推理开始之前,所以热路径上没有任何分支——这和 06 章反复出现的那条原则一致:**宁可启动时多做一点,也不要在热路径上加判断。**

选择本身是**两段式**的,两个方法分工严格:

| 方法 | 只看什么 | 举例 |
|---|---|---|
| 硬件能力检查 | GPU 架构、compute capability、可用指令 | 「这个 kernel 需要 compute capability 至少 9.0」 |
| 配置能力检查 | 量化方案、粒度、静态还是动态 | 「这个 kernel 只支持静态量化」 |

两段的顺序是固定的:**先筛硬件,再筛配置。** 这一半解释了一个常被问到的现象——同一个量化格式的 checkpoint,换一张卡就走了另一条 kernel,模型和配置一个字没改。两个方法都返回「行不行」加「不行的原因」,调用方把原因记下来,所以某个 kernel 为什么没被选上是可查的。

这里有一处容易被讲反的地方。配置能力检查吃进去的是**每个 kernel 自己的一份配置对象**,不是上一节那个统一的量化类型标识——后者只是配置对象的**一个字段**。这个区别不是吹毛求疵,因为**这场统一还没做完**:FP8 那条路的配置对象里确实就是「权重的量化标识」加「激活的量化标识」两个字段,干净;而同一个文件里 INT8 那条路的配置对象**至今是三个裸布尔**(输入是不是静态方案、是不是按通道、输入是否对称),上面还挂着一条源码里自己写的待改注释,内容就是「改成像 FP8 那样用量化标识」。

所以准确的说法是:**统一描述是迁移中的目标,不是既成事实。** 读 FP8 那一支时可以按「一个标识说明一切」去理解,读 INT8 那一支时得准备好看到散装的布尔字段。

### 1.12 量化从哪来:三种来源,而且能叠

同样是「这个模型是 FP8 的」,量化这件事发生的时机可以完全不同:

| 来源 | 怎么触发 | 权重在磁盘上是什么 | 谁做的量化 |
|---|---|---|---|
| **离线 PTQ** | checkpoint 自带 `quantization_config` | 已经是 INT4/INT8/FP8 | 外部工具(llm-compressor、AutoAWQ、ModelOpt、Quark) |
| **在线量化** | `--quantization` 作用在 BF16 checkpoint 上 | BF16 或 FP16 | vLLM 自己,在加载后处理那一步 |
| **运行时动态量化** | 隐含在方案里(激活方案设成动态、KV 用按 token 按头的粒度) | 不涉及 | GPU kernel 每次 forward 现算 |

绝大多数线上场景是第一种。第二种的价值是**不需要预量化的 checkpoint**:手上只有 BF16 权重、又不想跑一遍离线量化流程时,加载时顺手量化。第三种严格来说不是一种「来源」,而是某些参数的量化时机本来就只能在运行时——激活和 KV 直到算出来才存在,不可能预先量好。

三者可以叠加,而且有两种不同的叠法。讲稿讲的那种是后两类相叠:离线的 FP8 权重,加上动态的 per-token 激活,加上动态的按 token 按头的 KV。**更值得知道的是第一类和第二类也能叠**——预量化的 checkpoint 之上还可以再挂在线量化,专门去补那个方案**没有覆盖的层**。源码注释把边界划得很清楚:checkpoint 自带的方案仍然是主方案,叠加在它的配置加载完之后才发生。于是「这个 checkpoint 是 W4A16 的,但它的 MoE 部分没量化」这种情况有救。

### 1.13 在线量化能做什么、不能做什么

在线量化的能力边界,字面上就是两张字典:一张给 Linear 层,一张给 MoE。键是 1.9 那种量化类型常量,值是对应的量化方法类。

| 格式与粒度 | Linear | MoE |
|---|---|---|
| FP8 per-tensor | 支持 | 支持 |
| FP8 128 块 | 支持 | 支持 |
| FP8 per-channel 权重加 per-token 激活 | 支持 | 支持 |
| MXFP8 | 支持 | 支持 |
| MXFP4 | 支持 | 支持 |
| INT8 per-channel | **不支持** | 支持 |
| NVFP4 | **不支持** | 支持 |

两张表共七个键,前五个两边都有(但各自对应独立的 Linear 版与 MoE 版方法类,不是同一个类复用),后两个只对 MoE 开放。

**清单之外还有一条边界更要紧:在线量化做不了 W4A16。** AWQ 与 GPTQ 那一族需要校准数据来决定每组的 scale 与零点,而加载时手上没有校准集,只有权重本身。所以 4bit 权重-only 这条路**必须离线**,没有在线版本。

最后是一处工程上的坑。配了一个不在上面表里的组合会怎样?**不报错,静默地不量化。** 分派函数查不到对应的键时,回落到「未量化」的那个方法类——Linear 一条路,MoE 一条路,都是正常返回,不是抛异常。这一段里**没有任何日志**,所以「静默」这个词在这里是准确的(而 07 章有一处看似相同的场景,基准上其实明确打了一条警告——同一个形容词必须逐处核,不能凭印象)。

想知道有没有中招,有一个可观测的入口:**匹配成功的层会被记一笔账**,记下它的量化来源、量化类型、以及命中的是哪条匹配规则。**没被量化的层就是这本账里缺的那些。** 排查「我明明开了量化,怎么显存没降」时,先去看这本账缺了谁。

| `int4_per_token_head` | uint8 | 同上,4bit |

| `nvfp4` | uint8 | FP4 数据加 FP8 块 scale 打包 |

**多数低精度格式都用 uint8 存。** 这不是含糊,而是刻意的:4bit、3bit 这些位宽没有对应的张量 dtype,只能打包进字节数组,由 kernel 自己按布局解包。所以「存储 dtype 是 uint8」在这张表里等价于「有一套自定义的打包布局」,而 `fp8_inc` 那一行用真 fp8 dtype 是少数例外。

有两行的细节容易踩:

**`auto` 不总是「不量化」。** checkpoint 里声明了 KV 量化算法时,`auto` 会被解析成 fp8。更进一步,**少数模型默认就是 fp8**,要退回 BF16 必须显式写出来。而这里有个反向的坑:字段说明紧接着写了**对于不默认 fp8 的模型,显式写 `bfloat16` 是非法选项**——它不是一个「总是安全的保守选择」,在普通模型上写它会直接被拒。

**平台支持不一样。** 同一个字段的说明里带着一张平台矩阵:CUDA 11.8 及以上支持 `fp8`(等于 `fp8_e4m3`)与 `fp8_e5m2`,ROCm 只支持 `fp8`,Intel Gaudi 走 `fp8_inc`。挑格式之前先看平台。

`nvfp4_4over6` 那一行值得单独欣赏一下它的做法:同样是 NVFP4 的布局,但每 16 个值不是直接用最大值定 scale,而是在「最大值除以 6」和「最大值除以 4」两个候选里,选**平方重建误差更小**的那一个。多一次试算,换一点精度——这是 4bit 方案里很典型的思路。基准上只有一个后端声明支持它。

### 1.16 简写、双身份,以及 checkpoint 优先

`--quantization` 的取值里有一批是**在线量化的简写**,它们不对应独立的配置类,只是「在线量化框架加一组固定配置」的语法糖。脱糖规则是一张字典,**共七个键**:FP8 的三种粒度、MXFP8、MXFP4、MoE 的 INT8 per-channel、MoE 的 NVFP4。后两个的配置里**只有 MoE 一项、没有 Linear 项**,源码注释直接写着「Linear 保持不量化」——这就是 1.13 那张表里两行「不支持」的来源。NVFP4 那一项还带一条硬件限定,只在 Blackwell 加特定后端上可用。

这里有一处结构上很有意思的冲突:**七个简写里有两个名字同时也是 checkpoint 方案的名字**——MXFP8 和 MXFP4。同一个字符串,既可能是「用在线量化按这个格式量」,也可能是「这个 checkpoint 就是这个格式」。代码怎么分辨?

**注册简写用的是「不覆盖已有键」的写法,所以 checkpoint 路径优先。** 某些厂商的 checkpoint 会把量化方法标成 `mxfp8`,这种情况下走的是 ModelOpt 那份配置类,而不是在线量化。

但「那么 `--quantization mxfp8` 就走在线量化了」这个推论**不成立**,这是本章最容易想错的一处。这两个名字被单独列进了一个**延后名单**,注释写明:它们也是 checkpoint 方案名,**它们的在线配置只在 checkpoint 没有量化元数据时才被解析**。落到代码上就是:只给了 `--quantization mxfp8`、没给量化配置参数时,解析函数**直接返回空**,把决定权交回 checkpoint 元数据。要真正走在线量化,必须**两个参数一起给**。

所以这两个名字的准确语义是:「如果 checkpoint 自己说了它是什么,听 checkpoint 的;否则再看有没有给在线配置」。分流确实发生在那个解析函数里,但方向是**默认让位**,不是默认在线。

顺带把两个 CLI 参数的关系收口:**`--quantization` 管 W 和 A,`--kv-cache-dtype` 管 C,两者正交。** 一个 BF16 模型可以只开 C8;一个 FP8 模型也可以让 KV 保持 BF16。1.2 说过这件事,这里是它在参数层面的对应。

### 1.17 量化前的基准:各张量原本是什么形状

后面每一个方案做的事,都是把下表中的某几行换成「低精度数据张量加若干个 scale」。所以先把量化**前**的形状钉住,当作全章的对照底。形状里的维度名对应源码里的哪个变量,一并列出——这几个名字在读任何一个量化方法的建参数代码时都会遇到:

| 张量 | 量化前形状 | dtype |
|---|---|---|
| Linear 权重 | 输出维乘输入维 | bf16 |
| Linear 输入激活 | token 总数乘输入维 | bf16 |
| Linear 输出 | token 总数乘输出维 | bf16 |
| attention 的 query | token 总数、query 头数、每头维度 | bf16 |
| attention 的 key 与 value | token 总数、KV 头数、每头维度 | bf16 |
| KV cache | block 数、KV 头数、每 block 的 token 数、两倍每头维度 | bf16 |

| 维度 | 源码变量 | Llama-3-8B 取值 |
|---|---|---|
| 隐藏维 | `hidden_size` | 4096 |
| query 头数与 KV 头数 | `num_attention_heads`、`num_key_value_heads` | 32 与 8 |
| 每头维度 | `head_dim` | 128 |
| Linear 输入维(张量并行切分后) | `input_size_per_partition` | `qkv_proj` 是 4096 |
| Linear 输出维(张量并行切分后) | `output_size_per_partition` | `qkv_proj` 是 6144 |
| 融合层里有几个独立 Linear | `output_partition_sizes` 的长度 | `qkv_proj` 是 3 |
| 权重分组大小 | `group_size` | 128 |
| 权重二维块尺寸 | `weight_block_size` | 非块量化时不存在 |
| 本 rank 上的专家数 | `local_num_experts` | 仅 MoE 模型 |
| FFN 中间维(切分后) | `intermediate_size_per_partition` | 14336 |
| 每 block 容纳的 token 数 | `block_size` | 默认 16 |

两条换算后面反复用到:

**`qkv_proj` 的输出维是三段之和**,query 一段加 key、value 各一段。Llama-3-8B 上是 32 乘 128 加上两倍的 8 乘 128,即 4096 加 2048 等于 6144。

**没有「batch 乘 seq」这两维。** 表里的「token 总数」是整个 batch 展平后的一维长度,等于各请求本次要算的 token 数之和——调度器把整个 batch 拼成一维再进模型,机制见 02 章 2.7。prefill 时它是几千,纯 decode 时它约等于并发数。

最后那张表里,「融合层里有几个独立 Linear」这一行是后面理解 scale 形状的钥匙。`qkv_proj` 逻辑上是三个 Linear 融合成一个、`gate_up_proj` 是两个,而 **per-channel 的 scale 要按这几段分别算**——一个融合层的 scale 张量因此不是一整条,而是按段拼起来的。这个细节在 1.8 的粒度表里看不出来,要到具体方案的建参数代码里才显形。

KV cache 那一行的「布局随后端变」不在本章展开:五维形状与布局枚举在 03 章已经讲过,`block_size` 的取值权衡也在那里。

### 1.18 收益落在哪个阶段:把三笔账再切一刀

1.1 按「吃什么」把资源分成三笔账。还有一刀切法同样重要:**按阶段**。一次推理的两个阶段瓶颈完全不同,而三笔账的收益分别落在不同的阶段上:

| 阶段 | 计算特征 | 瓶颈 | 量化的收益从哪来 |
|---|---|---|---|
| **Prefill** | 大 GEMM,一次算的 token 数可达上万 | **算力** | 8bit tensor core 吞吐约是 BF16 的两倍 |
| **Decode** | GEMV 或很瘦的 GEMM,token 数约等于并发数 | **访存带宽** | 权重字节数减半,读权重的时间就减半 |
| **Attention** | 读 KV cache | **带宽加容量** | KV 减半,能开更大 batch、更长上下文 |

把这张表和三笔账叠起来,得到三条判断——它们决定了一个方案值不值得用:

**权重量化的收益主要在 decode,而且不需要激活配合。** decode 时每一步只算很少的 token,GEMM 退化成读一遍权重再做一次很瘦的乘法,时间几乎全花在把权重从显存搬进来上。权重字节数减半,这段时间就减半——**即使激活仍然是 BF16**。这正是只量化权重的方案(W8A16、AWQ、GPTQ)在小 batch 下依然有效的原因,尽管 1.1 说过它「一点算力没省」。省算力和省带宽是两件事,decode 阶段要的是后者。

**激活量化的收益主要在 prefill 和大 batch。** token 数大时才真正吃算力,这时候两个输入都是 8bit 才有意义。反过来看更要紧:**token 数很小时,A8 甚至可能让它变慢。** 因为量化激活本身是一个额外的 kernel——读一遍 BF16、求最大值、写一遍 FP8;这点开销在大 batch 里可以忽略,在 decode 的一步里未必。

**KV cache 量化的收益随上下文长度线性增长。** 它不挑阶段,只挑长度:上下文越长、并发越高,KV cache 在显存里占的比重越大,C8 省下来的就越多。

代价也有四类,其中最后一类容易被忽略:

- **精度损失**:8bit 只有 256 个可表示值,粒度越粗损失越大。
- **额外 kernel 开销**:上面说的那次动态求最大值。vLLM 用编译把量化算子融合进上游来缓解。
- **校准成本**:静态激活量化与 INT8 需要离线跑一遍校准集才能定出激活的 scale。
- **硬件门槛**:**FP8 tensor core 要 SM89 及以上**(Ada、Hopper、Blackwell),而 **INT8 tensor core 从 SM75(Turing)就有**。这一条正好解释了 1.11 那个「先筛硬件、再筛配置」为什么必须存在:同一份 FP8 checkpoint 在两代卡上根本不是同一件事。

### 1.19 同样一个字节,两种花法

8bit 有两种花法,差别不在能表示多少个值——**两者都是 256 个**——而在这 256 个值怎么分布:

| | INT8 | FP8 E4M3 | FP8 E5M2 |
|---|---|---|---|
| 比特分配 | 1 符号加 7 数值 | 1 符号加 4 指数加 3 尾数 | 1 符号加 5 指数加 2 尾数 |
| 分布 | **均匀**,等间距 | **非均匀**,接近 0 处密集 | 更极端的指数分布 |
| 动态范围 | 固定 1 比 127,靠 scale 平移 | ±448,内部就有约 $2^{17}$ 的动态范围 | ±57344 |
| 相对精度 | 大值处高、小值处低 | **全域恒定**,约 $2^{-4}$ | 约 $2^{-3}$ |
| 离群值鲁棒性 | **差**:一个离群值抬高 scale,其余值全被压进几个格子 | **好**:离群值只占用指数位,小值仍有 3 位尾数 | 范围更宽但精度更差 |
| 硬件 | Turing 及以上,整数累加 | Ada、Hopper 及以上,FP32 累加 | 同 E4M3 |

「均匀 vs 指数分布」这一行是题眼,其余各行都是它的推论。INT8 把 256 个刻度等距铺在 $[-s\cdot127, s\cdot127]$ 上,所以绝对精度处处相同、相对精度随数值变小而变差;FP8 把刻度按指数密集地堆在 0 附近,所以**相对**精度处处相同。

E5M2 的位置在 1.15 已经交代过:它只用在 KV cache 上,线性层不用——两位尾数对乘法来说太糙了。

### 1.20 离群通道:为什么 FP8 不用校准,INT8 要

上一节那张表里「离群值鲁棒性」一行,是整章「为什么 FP8 比 INT8 好用」的全部根因,因为 **LLM 的激活里普遍存在离群通道**:某几个隐藏维的幅值比其他维大几十倍。

对 INT8 来说这是灾难。per-tensor 量化激活时,scale 由全张量的最大值决定,于是被那几个离群通道拉大;剩下几千个普通通道的值除以这个被撑大的 scale 之后,全都落进 int8 的低几位里——**可表示值还是 256 个,但实际用上的只有最低那几档**,精度直接崩掉。SmoothQuant、AWQ 这类方法要做的「把离群值从激活迁移到权重」,解决的就是这件事:用一个对角缩放把激活压平、把压下去的那部分乘进权重里,数学上等价,但两边的分布都变得好量化了。

FP8 E4M3 天生不怕这个。离群值大,只是把它自己的**指数位**抬高,普通小值该有几位尾数还是几位——相对精度不受影响。于是结论很直接:**FP8 的动态 per-token 量化就够用,不需要校准数据。**

这一条落到 vLLM 的默认值上就是:

- **FP8 的 W8A8 默认动态量化激活**,开箱即用,不需要任何校准集。
- **INT8 的 W8A8 要么静态 per-tensor**(那就得离线跑校准算出激活 scale),**要么动态 per-token**;而且 INT8 额外支持非对称——因为它是均匀网格,加一个零点能多榨出一点有效位宽,这对指数分布的 FP8 没什么意义。

### 1.21 为什么 per-channel 权重配 per-token 激活是「免费」的

1.7 给了反量化的等式,但那是没有下标的版本。真正决定开销的是**下标**。设 $i$ 走 token、$j$ 走输出通道、$k$ 走输入通道,per-token 的激活和 per-channel 的权重分别是:

$$
X_{ik} \approx s^X_i \cdot \hat{X}_{ik}, \qquad W_{jk} \approx s^W_j \cdot \hat{W}_{jk}
$$

那么 GEMM 要算的是:

$$
D_{ij} = \sum_k X_{ik} W_{jk} = \sum_k \left(s^X_i \hat{X}_{ik}\right)\left(s^W_j \hat{W}_{jk}\right) = s^X_i s^W_j \cdot \sum_k \hat{X}_{ik}\hat{W}_{jk}
$$

关键在最后一步:**$s^X_i s^W_j$ 不含 $k$,所以可以整体提到求和号外面。** 这一提,整条流程就被劈成两段互不干扰的部分:

- **主循环**,规模是「token 数乘输出维乘输入维」:纯粹的低精度 tensor core 乘累加,**指令流里一条乘 scale 的指令都没有**,因此能跑满硬件的 8bit 峰值算力。
- **epilogue**,规模是「token 数乘输出维」:累加器写回显存之前,顺手乘上那两个 scale(再加 bias)。

第二段的运算量只有第一段的 $1/\text{in\_features}$,典型值是四千分之一;而且它和「累加器转成输出 dtype」本来就要做的那次读写**融合在一起**,不额外增加任何显存访问。

所以「免费」的确切含义不是没有开销,而是**开销落在一个比主循环小三个数量级的阶段上,并且被访存完全掩盖**。这个说法在代码里能直接看到:Python 侧调用矩阵乘时,只是把两个 scale 张量原样传进去、顺带指定输出 dtype 就直接是 BF16,**中间不落一次 FP32**;按行还是按列广播由 kernel 自己决定。

### 1.22 什么组合不免费:一条判据

反过来看哪些组合提不出去,这条规律才立得住。

**激活如果按输入通道量化**,$s^X$ 的下标里就有了 $k$,提不出求和号,只能在主循环里逐 $k$ 乘。这正是 1.8 那张粒度表里 per-channel 不能作用于激活的原因——不是算不出来,而是那样做等于**放弃 tensor core 的连续累加**。上一节说的 SmoothQuant 之所以要把缩放**离线折进权重**,也是为了绕开这一点:折完之后运行时又回到了 per-token。

**权重如果按输入通道分组**(group 或 block),$s^W$ 的下标里出现 k 方向的块号,同理必须进主循环。

于是可以把这一组规律压成一句话:

> **scale 的下标只要落在 GEMM 的输出坐标上,反量化就能后置到 epilogue;一旦下标里出现被求和的那个维度,反量化就必须进主循环。**

四种常见组合按这条判据排下来是:

| 权重粒度 | 激活粒度 | 反量化在哪 | 主循环被干扰吗 |
|---|---|---|---|
| per-tensor | per-tensor | epilogue,标量乘 | 否。最简单 |
| per-channel | per-token | epilogue,行列广播乘 | 否。上一节那个「免费」组合 |
| per-channel | per-token 加非对称 | epilogue,多一项零点修正 | 否。修正项的下标同样只有输出坐标 |
| block | group | **主循环内**,逐 k 块反量化 | **是** |

非对称那一行值得多看一眼:它多出来的修正项是「权重沿输入维求和」得到的一个长度等于输出维的向量,静态量化时还会把激活零点直接乘进去预先折好。**下标仍然只有输出坐标,所以照样能留在 epilogue**——非对称的代价是多一个参数和一次预处理,不是打断主循环。代码里对称与非对称走的甚至是两个不同的算子,按有没有那个修正项分派。

### 1.23 block 量化为什么非要专门的 kernel

最后一行是唯一被打断的那个,值得单独算一遍。把 $k$ 按 128 切成若干 k 块,权重再按输出方向切块,两侧的 scale 就都带上了块号:

$$
D_{ij} = \sum_{kb} \underbrace{s^X_{i,kb}\, s^W_{jb,kb}}_{\text{随 } kb \text{ 变化}} \cdot \sum_{k \in kb} \hat{X}_{ik}\hat{W}_{jk}
$$

现在提不出去了:每个 k 块有自己的一对 scale,必须「先把这一段的低精度点积算完、乘上这一段的 scale、再累加到 FP32 累加器」。反量化从 epilogue 挪进了 k 方向的主循环。代价出在四个地方:

| | per-channel 配 per-token | block 配 group |
|---|---|---|
| 反量化位置 | epilogue,执行 1 次 | 主循环内,执行「输入维除以块宽」次 |
| 每次迭代的额外指令 | 无 | 两次 scale 读取加一次逐元素乘 |
| 累加链 | tensor core 内部一路累到底 | **每段都要出累加器、乘完再加回去** |
| tile 尺寸自由度 | 任意 | k 方向的 tile 必须和 scale 的块宽对齐 |

**第三行才是真正的性能杀手。** tensor core 最快的形态是「连续发射多条乘累加指令、累加器留在寄存器里不动」;一旦每 128 个 $k$ 就要把累加器取出来做一次逐元素乘,这条流水线就被打断了。这也解释了为什么 block 量化基本只在 Hopper 及以上才划算——那一代有异步搬运和 warpgroup 级异步乘累加,能把 scale 的读取和逐元素乘塞进等待间隙;更早的架构上这段代价藏不住,直接表现为吞吐下降。(这一段是硬件机制参考,不在本仓库源码的核对范围内。)

**换来的是精度。** per-token 只能给整行一个 scale,行里只要有几个离群通道,其余通道就被压到只剩几个有效格子;block 与 group 把范围缩到 128 个元素,离群值的影响被关在自己那一格里。这正是 DeepSeek 那一系敢用 FP8 同时做训练和推理的前提。

最后一个容易搞混的点:**激活侧配的是「每行 128 个一组」,不是二维的 128 乘 128。** 因为 token 数运行时才知道、而且每步都变,没法按 token 分块;何况逐 token 独立算 scale 本来就是好事(不同 token 的幅值差异很大)。所以「权重二维分块加激活一维分组」是这条路径固定的搭配。

这里有个实现上的暗礁:**激活那一维的组宽取自权重块尺寸的第一个分量**,也就是输出方向那个,而不是输入方向那个。DeepSeek 系两个值都是 128,所以看不出区别;一旦两者不等,这个取法就会显形。

### 1.24 于是 block 路径有自己一整套 kernel 候选

1.11 讲的是「怎么从候选里筛」,这里补上的是「候选是谁」。vLLM 为 block 路径准备了**一组完全独立的 kernel 候选**,和非 block 的那组分开维护;分水岭就是上一节那个结构差异——**判的是激活那把 key 的粒度是不是「分组」**。正因为激活被配成了每行 128 一组(而不是 per-token),这个判定才成立。

block 那一组的候选按优先级排下来是:DeepSeek 开源的 Hopper 专用实现最快,排第一;CUTLASS 的块缩放版本次之;最后是 Triton 写的兜底实现,任何平台可用但慢。

两组候选还有一处不对称值得记:**非 block 那一组可以在运行时被追加**——有一个注册入口允许把新 kernel 挂进某个平台的候选表;block 那一组没有对应的入口。所以第三方想插一个自己的 FP8 kernel 进来,只能插进非 block 那条路。

### 1.25 同一个粒度,作用在权重和激活上形状不同

前面几节讲的是粒度怎么影响计算,这一节讲它怎么落到**参数张量的形状**上。一条通用规律管住全部:**同一个粒度作用在权重和激活上,得到的 scale 形状不同,因为「行」的语义不同——权重的行是输出通道,激活的行是 token。**

| 粒度 | 作用于权重 | 作用于激活 | 权重侧 scale 个数 |
|---|---|---|---|
| per-tensor | 一个标量 | 一个标量 | 1 |
| per-channel | 每个输出通道一个 | **不适用**,见下 | 输出维 |
| per-token | 等价于 per-output-channel | 每个 token 一个 | 同上 |
| 每行 $g$ 个一组 | 输出维乘「输入维除以 $g$」 | token 数乘「输入维除以 $g$」 | 两者之积 |
| 二维块 | 「输出维除以块高」乘「输入维除以块宽」 | 只做一维分组 | 两维之积 |

「per-channel 不适用于激活」那一格不是省略,而是 1.22 那条判据的直接后果:激活的「通道」是输入维,scale 的下标会带上被求和的那一维,反量化就提不出求和号了。**这张表和那条判据是同一件事的两种写法**,一个讲形状,一个讲能不能提出去。

### 1.26 三条容易踩的形状细节

上面那张表是理想情况。实际读代码时有三处会对不上:

**① per-tensor 的 scale 在 checkpoint 里不是标量。** 融合层在磁盘上本来就是若干个独立的 Linear,各有各的 scale,所以参数按「有几个分片就开几个」来建。加载完之后才**取最大值重量化**成一个真正的标量——两个分片里幅度小的那个被迫用了更大的 scale,这是融合的代价。

这一条和 NVFP4 的二级 scale 恰好形成对照:那里也是按分片存,但处理方式是**校验所有分片必须相同,不同就直接失败**。同一个「分片各存一份」的形状,一个容忍不一致并取最大值,一个完全不容忍——因为前者是可以牺牲一点精度的量化 scale,后者是决定整个数值范围的全局系数。

**② 激活的动态 scale 是 forward 期的临时产物,不是参数。** 它的形状里那个尾随的 1 是被显式加出来的:先沿最后一维求绝对值最大,再把被消掉的那一维补回去。所以是「token 数乘 1」而不是「token 数」——后面每张表里激活 scale 都带这个尾巴,原因就在这。

**③ block 的 scale 个数用的是向上取整,不是整除。** 写法是「加上块宽减一再整除」。理由很实际:**张量并行切分后维度不保证能被 128 整除**。比如输入维 4096、张量并行切成 3 份,每张卡是 1366,除以 128 得 10 余 86——那个只有 86 个元素的零头块同样需要自己的 scale,用整除就把它连同它管的那 86 个元素一起丢掉了。kernel 侧对零头块按实际元素数计算、不足的部分补零。

这三条里第三条最值得记,因为它是**并行切分和量化粒度撞在一起**才出现的问题:单卡上永远遇不到,一开张量并行就可能踩。

### 1.27 七种方案的参数清单

把前面几节合起来,各方案在 layer 上真实存在的参数是这样的。所有形状都按 1.17 的维度名写:

| 方案 | 权重数据 | 权重 scale | 激活 scale(运行期) | 特有参数 |
|---|---|---|---|---|
| **FP8 per-tensor** | 输出维乘输入维,加载后转置成列主序 | 标量(磁盘上按分片存) | 标量(静态)或 token 数乘 1(动态) | 静态时有 `input_scale` |
| **FP8 block** | 同上,**不转置** | 二维块数,名字带 `_inv` 是 DeepSeek 的约定 | token 数乘「输入维除以块宽」 | **没有** `input_scale`,这条路强制动态 |
| **INT8 per-channel** | 同上,在 kernel 里转置 | 输出维乘 1 | token 数乘 1 | 非对称时有零点与权重侧修正项 |
| **AWQ** | 输入维乘「输出维除以 8」,沿输出维打包 | 「输入维除以组宽」乘输出维,**不打包** | 无,激活保持 BF16 | 零点张量,按打包形状存 |
| **GPTQ** | 「输入维除以 8」乘输出维,沿输入维打包 | 同上 | 同上 | 零点张量;开了激活重排序时还有一个通道到组的映射 |
| **NVFP4** | 输出维乘「输入维除以 2」,两个 4bit 挤一个字节 | **两级**:一级是「输入维除以 16」的 fp8 块 scale,二级是一个全局标量 | token 数乘「输入维除以 16」,而且是重排过的内存布局 | 激活也有自己的全局 scale |
| **MXFP8 / MXFP4** | 同上(MXFP8 不打包) | 「输入维除以 32」,dtype 是 E8M0 | 同形 | **没有二级 scale** |

几处值得单独拎出来:

**AWQ 和 GPTQ 的打包方向正好相反**,但只在磁盘上如此。AWQ 在加载后处理里会把打包顺序**转成 GPTQ 那一种**,所以运行时只有一种布局。读代码时如果按磁盘形状去对 kernel 的输入,会对不上。

**转置发生在哪不一样。** FP8 per-tensor 在加载后就转好了(因为 CUTLASS 那条路要列主序),INT8 是在 kernel 里转,而 FP8 block 那条路根本不转。

**NVFP4 与 MX 系最大的结构差异是有没有第二级 scale。** NVFP4 用一个全局 FP32 标量再乘一层,MX 系直接用 E8M0——一个纯指数、没有尾数的 8bit 格式,本身就是 2 的幂,不需要再套一级。这个差异顺带决定了 scale 的开销:NVFP4 是每 16 个值配一个字节,MX 系是每 32 个值配一个字节,**后者的 scale 开销正好是前者的一半**。

### 1.28 MoE 多出来的那一维:融合的前提与代价

MoE 把每个专家的两个 Linear 堆成三维张量,于是所有 scale 都多一维专家数。但真正要讲清的不是多这一维,而是**为什么门控和上投影这两个矩阵能被融合成一个**——因为这件事直接决定了 scale 的形状。

先消一个歧义:**MoE 里有两个不同的「gate」。** 一个是**路由门控**,一个把隐藏维映射到专家数的小 Linear,产出每个 token 选哪几个专家,位置在专家计算**之前**,通常不量化;另一个是 **SwiGLU 的门控分支**,和上投影并列,位置在**每个专家内部**。被融合的是后者,和路由那个毫无关系。源码里连注释都写明了:门控分支加载进融合权重的第一个逻辑位、上投影加载进第二个。

融合的前提只有一条:**两个矩阵吃的是同一个输入张量。** 门控分支和上投影都吃派发之后的那份激活,同一份数据;而矩阵乘对输出维是可以分块的,把两个权重沿输出维拼起来做一次乘法,再切开,结果和分别做两次**逐比特相同**。收益有三重:一次 kernel 启动代替两次(MoE 里尤其值钱,因为每个专家分到的 token 很少,启动开销占比高)、输入只从显存读一次而不是两次、乘法的输出维翻倍使得分块更充分。

反过来,下投影**融不进去**,因为它的输入是前两者的输出经过非线性之后的结果,存在数据依赖,不是同输入的并列关系。源码把这件事直接写进了命名——下投影的加载注释说它进的是「唯一的那个逻辑权重位」。同一条判据也解释了注意力里的输出投影为什么不能和 qkv 融合。而这根本不是 MoE 特有的技巧:稠密模型里 `gate_up_proj` 和 `qkv_proj` 用的是同一套融合层,分片数分别是 2 和 3——这也正好回答了 1.26 第一条里「per-tensor 的 scale 为什么在磁盘上按分片存」:**拼接之前它们本来就是各自独立的层。**

融合对量化的影响有四条:

- **per-tensor 的权重 scale 是「专家数乘 2」而不是「专家数乘 1」**,因为磁盘上门控和上投影各有一个。加载后必须取最大值重量化成每个专家一个,否则一次矩阵乘里没法用两个不同的 scale。**这是融合的代价:牺牲一点精度。**
- **block 与 group 量化不需要这一步**,因为它们的 scale 本来就是沿输出维分块的,拼接之后天然还是合法的分块 scale。这是 block 量化在 MoE 上精度更好的一个具体原因。
- **激活量化作用在派发之后的那份数据上**,而派发会把每个 token 复制到它选中的每个专家的分段里。所以 per-token 的 scale 行数是「token 数乘选中专家数」——**MoE 的激活量化开销比稠密层高出选中专家数那么多倍**,而且同一个 token 的那几份 scale 数值相同却各算了一遍。
- **路由那个小 Linear 一般不量化。** 它的输出维只有专家数,省不了什么,但选谁当专家这件事对精度极其敏感。

### 1.29 KV cache:scale 藏在末维的填充里

KV cache 这一侧的形状有个和前面完全不同的做法。写进 cache 之前,key 和 value 的形状是「token 数、KV 头数、每头维度」;写进去之后按 block 组织,**具体布局由后端决定**——不是某个中心函数单方面算出来的,后端有一个改写缓存规格的钩子,会在建 cache 之前先把规格调整成自己要的样子。不支持某种量化模式的后端,根本不实现这个钩子,这就是「后端支持面窄」的机制。

最值得看的是「每个 token 每个头各算一个 scale」那一档。它**不新增任何参数张量**,而是把 scale **内联进 cache 末维的填充里**:每个头的数据后面紧跟它自己的一个 FP32 scale,key 和 value 各一份,四段依次排在末维上。这也解释了它为什么不需要 checkpoint 提供 scale——scale 是运行时算出来、就地写在数据旁边的。

代价可以精确算出来。末维的字节数是「key 与 value 的数据字节数之和,加上两个 FP32 scale」,也就是固定多出 **8 个字节**。关键在于**这 8 个字节不随 cache 的 dtype 缩放**:

| 模式 | 每个 (token, 头) 的字节数 | 相对 BF16 的压缩比 |
|---|---|---|
| BF16 | 512 | 1× |
| FP8 per-tensor | 256 | **精确 2×** |
| INT8 每 token 每头 | 128 加 128 加 8 = 264 | 1.94× |
| INT4 每 token 每头 | 64 加 64 加 8 = 136 | 3.76× |

FP8 那一行拿到的是**精确的** 2 倍,因为它的 scale 是整个张量共用的一个参数,一个字节都不内联。而每 token 每头那两档都要付那 8 个字节:INT8 上它占 3.0%,INT4 上占 5.9%——**位宽越低,这笔固定开销的相对占比越大**,这就是 INT4 拿不到理想的 4 倍、只有 3.76 倍的全部原因。

### 1.30 一张速查表

把全章的形状与字节数收在一处。以 Llama-3-8B 的 `qkv_proj` 为例,输入维 4096、输出维 6144、分片数 3、组宽 128,不做张量并行:

| 方案 | 权重数据 | 权重 scale | 权重字节数 |
|---|---|---|---|
| BF16 基线 | 6144 乘 4096,bf16 | 无 | 50.3 MB |
| FP8 per-tensor | 6144 乘 4096,fp8 | 一个标量 | 25.2 MB |
| FP8 block 128 | 6144 乘 4096,fp8 | 48 乘 32,fp32 | 25.2 MB 加 6 KB |
| INT8 per-channel | 6144 乘 4096,int8 | 6144 乘 1,fp32 | 25.2 MB 加 24 KB |
| AWQ 4bit 组宽 128 | 4096 乘 768,int32 | 32 乘 6144 的 bf16,加 32 乘 768 的零点 | 12.6 MB 加 0.5 MB |
| GPTQ 4bit 组宽 128 | 512 乘 6144,int32 | 同上 | 12.6 MB 加 0.5 MB |
| NVFP4 | 6144 乘 2048,uint8 | 6144 乘 256 的 fp8,加两个标量 | 12.6 MB 加 1.6 MB |
| MXFP4 | 6144 乘 2048,uint8 | 6144 乘 128,E8M0 | 12.6 MB 加 0.8 MB |

这张表最该看的不是哪个最小,而是**最后三行的 scale 开销**:

- 4bit 方案的 scale 占比明显高于 8bit。AWQ 与 GPTQ 在组宽 128 下额外占约 **4%**,NVFP4 额外占 **12.5%**(每 16 个 4bit 值配一个 8bit scale),MXFP4 是 **6.25%**(每 32 个值配一个)。
- 折算成相对 BF16 的显存比:AWQ 与 GPTQ 约 **0.26 倍**,MXFP4 约 **0.27 倍**,NVFP4 约 **0.28 倍**——**没有一个达到理想的 0.25 倍**。

也就是说,「4bit 就是四分之一显存」这个直觉在任何一个真实方案上都不成立,而且**粒度越细、差得越多**:NVFP4 的精度优势正是用最大的那份 scale 开销换来的。这个取舍和 1.23 里「block 量化拿精度换 kernel 复杂度」是同一个形状,只是代价换到了显存上。

### 1.31 「静态」不是「per-tensor」,判据只有一条

激活的 scale 有静态和动态两种:静态的来自 checkpoint(离线跑校准集算出来),动态的在运行时从当前这一批数据实时算。区别通常被简化成「静态就是 per-tensor」,但这个理解会在读代码时立刻碰壁,因为代码里存在一大批「静态的非 per-tensor」量化类型。

准确的说法是:**「静态」的意思是「scale 与运行时数据无关」,判据只有一条——scale 张量的形状里不能出现 token 维。**

为什么这一条就够?因为 token 数每一步都在变,每个 token 的内容也无法预知,**离线根本写不出一个按 token 索引的 scale**。反过来,只要分组只沿隐藏维切,离线就能算得出来。于是下面这些都是合法的静态粒度:

| 静态粒度 | 含义 |
|---|---|
| per-tensor | 整个激活一个 scale |
| per-channel(按输入通道) | 每个输入通道一个,**正是 SmoothQuant 想要的形态** |
| 沿隐藏维分组 | NVFP4 与 MX 系的 scale 就是这一类 |

代码里有一处细节恰好反向印证了这条判据:动态量化那个算子的构造函数里有一条断言,**只对动态路径限制粒度**(只许 per-token 或 per-tensor),**静态路径反而完全放开**。限制加在动态那一侧而不是静态那一侧,说明约束的来源不是「静态很弱」,而是「动态路径的 kernel 只实现了两种」。

顺带消掉一个看着矛盾的名字:有一个叫「静态 per-token」的量化类型。它不矛盾,因为 per-token 的字面定义是「每行一个 scale」,而**行的语义随张量而变**(1.25 那条规律):作用在权重上时行就是输出通道,和 token 毫无关系,当然可以静态;只有作用在激活上时行才是 token,那时才必须动态。

### 1.32 框架支持的,比实际用上的多

上一节列的三种静态粒度都真实存在于代码里,但**真正被 Linear 路径用上的只有一种**。这个区别不搞清,读参数表时会一直对不上:

- **FP8**:静态激活量化那一支**直接写死成 per-tensor**,没有分支;对应的参数也就是按分片存的那个标量。
- **INT8**:compressed-tensors 的分派函数干脆就叫「静态张量级 W8A8」——静态即 per-tensor,名字里就写着。
- **唯一在用「静态加非 per-tensor」激活 scale 的是 NVFP4 与 MXFP4 那条路**,它们的组 scale 沿隐藏维切,正好符合上一节的判据。
- 至于**静态 per-channel 激活**,理论可行,而且正是 SmoothQuant 的核心思想,但**没有 kernel 直接吃它**。原因在 1.22 已经给过:激活按输入通道缩放会让 scale 的下标含上被求和的那一维,反量化就提不出求和号了。SmoothQuant 的解法是把这个缩放**离线折进权重**,运行时又回到 per-token。

这条「能力清单不等于在用清单」的提醒,和 1.13 那个「在线量化支持哪些就看字典里有哪几个键」是同一类:**判断某个组合能不能用,要去找实际的分派代码,不是去看有没有对应的类型常量。**

### 1.33 硬件能力反过来决定量化粒度

非 block 路径上,激活用哪种粒度是三选一决定的,而且第三条分支很说明问题:

| 条件 | 激活量化类型 |
|---|---|
| 配了静态 | per-tensor 静态 |
| 动态,且 CUTLASS 可用 | **per-token 动态**,更准 |
| 动态,但 CUTLASS 不可用 | **退化成 per-tensor 动态**,精度更差 |

第三条为什么存在:**per-token 动态量化需要 kernel 的 epilogue 支持按行广播 scale**。有 CUTLASS 就有这个能力;没有的时候(比如老卡只能走 PyTorch 自带的那个缩放矩阵乘),就只能退回整张激活一个 scale。

这是一个**硬件能力反过来决定量化粒度**的例子,也是 1.11 那个「先筛硬件、再筛配置」从另一侧看到的同一件事:那边是「配置定了,挑一个跑得动的 kernel」,这边是「kernel 的能力定了,反过来把配置改浅一档」。**同一个 checkpoint、同一份配置,换张卡精度就不一样**,而且不会有任何报错。

### 1.34 融合模块的零点怎么合并成一组

非对称量化的修正项在 1.22 已经交代过:它只依赖权重,可以在加载时预计算。这里补一处真正棘手的工程问题——**融合模块的零点该怎么合并**。

问题的形状和 1.26 第一条一样:`qkv_proj` 这类融合层在磁盘上是几个独立的 Linear,**各有各的一组「scale 加零点」**;而矩阵乘只能给整个激活矩阵一组。怎么把几组合成一组?

权重那边的解法是**取最大值**(见下一节)。零点这边用的是另一个更精确的办法:**先把每个分片的「scale 加零点」还原成它实际覆盖的那段实数区间,取所有区间的并集,再从并集反解出一组新的 scale 和零点。**

为什么这个办法更好:取最大值只管住了范围的上界,而区间并集**同时管住上下两端**。非对称量化的整个意义就在于上下界不对称,用一个只看上界的合并方式会把这个好处抵消掉。

还有一处容易忽略的类型细节:**checkpoint 里零点是按权重的数据类型存的**(也就是 int8),但运行时要当 int32 用——因为它要参与的是累加器那一侧的减法,而累加器是 int32。

### 1.35 权重量化:vLLM 只做三件事

从这里开始进入「具体怎么做」。先把分工说清:**权重量化是离线完成的**(在线量化那条路除外),vLLM 自己不做量化的数学,它只负责三件事:

1. **按 checkpoint 声明的格式建参数**——建出正确形状、正确 dtype 的空张量等着被填。
2. **加载**——把 checkpoint 里的值搬进去,融合层还要把几个分片搬到同一个张量的不同段上。
3. **后处理成 kernel 要的样子**——重量化、展开、转置、补齐,让 kernel 拿到它期望的布局。

1.27 那张参数清单是第一件事的产物,接下来两节讲的是第三件事——**后处理里发生的事情,是量化方案与 kernel 之间真正的接缝**,也是最容易读错的地方。

### 1.36 重量化:只在必要时做,而且有损

融合层的 per-tensor 权重 scale 在磁盘上是按分片存的,矩阵乘却只接受一个。做法是**取所有分片里最大的那个 scale**,然后逐分片先反量化回高精度、再用这个最大 scale 重新量化一遍。

**这一步是有损的**:原本用小 scale 表示的那个分片,现在被迫用一个更大的 scale,它的有效精度就下降了。这就是 1.26 第一条说的「融合的代价」在代码里的样子。

但有一个前提讲起来容易被略过:**这一步不是每次都做。** 代码里有一道守卫,判断的是**最后一个 scale 槽是否还停在初始化时的哨兵值**上。逻辑是这样的:参数按分片数开了 N 个槽,如果 checkpoint 本来就是融合好的、磁盘上只有一个 scale,那就只有第一个槽被填上,后面的槽还是哨兵值——**这种情况下整段重量化直接跳过**,因为它本来就已经是单个 scale 量化出来的了。注释里甚至点了一个具体的模型名当例子。

所以准确的说法是:**只有 checkpoint 里各分片各带一个 scale 时才重量化,那一次才有损;checkpoint 本来就融合好的,一点损失都没有。**

**per-channel 不需要这一步,这才是它比 per-tensor 更受欢迎的确切理由。** 把一个 per-tensor 的 scale 展开成 per-channel 只是把同一个值复制到每个输出通道上,**完全无损**;而多个分片各自的 per-channel scale 拼起来本来就是合法的 per-channel scale,连合并都不用。**展开是无损的,取最大值是有损的**——两条路的精度差距就出在这里。INT8 那条路因此根本没有重量化这一步。

顺带一提 1.27 提过的对齐问题:CUTLASS 的 FP8 kernel 要求某一维 16 对齐,不满足时会在后处理里补齐,同时记下真实的输出宽度,好在运行时把补出来的部分切掉。

### 1.37 激活量化:每个 Linear 入口各算一次

激活这一侧和权重完全不同:**它没有离线这一说,量化发生在每一次前向、每一个 Linear 层的入口**,是应用权重那一步的第一件事。

FP8 那一侧统一走同一个算子,按「静态还是动态」加「什么粒度」分派到不同实现;INT8 那一侧走另一个算子,语义由参数决定——给了 scale 就是静态 per-tensor,没给就是动态 per-token,再加一个开关决定要不要同时返回零点。

实现里有三个工程细节值得记:

- **scale 有一个兜底下界。** 全零输入会让最大值是 0、scale 也是 0,后面一除就炸。所以代码给 scale 压了一个极小的下界。
- **用取倒数再相乘,而不是直接除。** 注释说明了理由:即使在 per-token 这种 scale 不是标量的情况下,先求倒数再逐元素乘也比逐元素除快。
- **可以把 token 方向补齐到指定长度**,给某些对形状有对齐要求的 kernel 用。

还有一条分支专门为某个 Hopper 专用 kernel 准备:**把 scale 约束成 2 的整数次幂**(先取对数、向上取整、再变回 2 的幂)。这样反量化就退化成指数相加,kernel 更快。**这是「让数值格式迁就 kernel」的一个干净例子**,和 1.23 里 block 量化拿精度换 kernel 复杂度是同一族取舍——只不过这次让步的是 scale 的表示精度。

### 1.38 把这次量化省掉:融进上游算子

上一节那个「每个 Linear 入口各算一次」正是 1.18 说的那笔额外开销:读一遍 BF16、求最大值、写一遍 FP8。小 batch 下它占的比重不低。

省掉它的办法是**让上游直接吐出量化好的激活**。kernel 会声明一个「我能直接消费的预量化激活类型」;上游算子(比如归一化)如果能按那个类型输出 FP8 加 scale,Linear 这一步检测到之后就**整个跳过量化**,直接拿来用。

但这条路有一个限制值得注意:**CUTLASS 的 FP8 kernel 只在静态 per-tensor 时允许它**,因为动态 scale 要看完整批数据才知道,上游没法提前写对。于是形成一个略显别扭的局面——**最需要省掉这次 kernel 的小 batch 动态路径,恰恰是用不上这条优化的那一条。**

### 1.39 KV cache 的 scale 从哪来

KV cache 这条链路和前面两条最独立,和 `--quantization` 完全解耦。它的 scale 有两个来源,优先级从高到低:

**第一,checkpoint。** 注意力层上会注册四个 scale 参数(query、key、value、以及 softmax 输出各一个),**初值设成 −1.0 当作「尚未加载」的哨兵**——这样加载点只管写,不用另外记一个「有没有加载过」的标志。

**第二,默认 1.0。** checkpoint 里没有(两个 scale 都还停在哨兵值)就退化成 1.0,并打一条告警。scale 等于 1 意味着什么?**等于把 BF16 的值直接硬转成 FP8**。E4M3 的 ±448 通常能覆盖 KV 的取值范围,所以不至于崩,但显然不是最优。

这条告警有个漏洞值得指出:**它的条件里排除了 E5M2**,也就是说用 `fp8_e5m2` 且没有 scale 时**不会有任何提示**。而 E5M2 恰恰是 1.19 那张表里精度最差的一档——**最该提醒的那一档反而是静默的。**

加载后处理还强制要求 **KV 的 scale 必须是标量**,不是就直接抛错。唯一的例外是 1.29 讲过的「每 token 每头」那一系列——那类 scale 由 kernel 在写 cache 时现算,checkpoint 给了也忽略。所以这条链路上**要么全局一个标量,要么根本不从 checkpoint 拿**,没有中间档。

最后,处理完的 scale 会**以四种形态并存**:给 CUDA kernel 的设备张量、给某些需要主机标量的后端的 Python 浮点数、给某些融合 kernel 的 CPU 张量,以及加载期那个临时参数(处理完就删掉)。**同一个标量要准备四份**,是「不同后端各要各的形态」最直白的一处体现。

### 1.40 没有「运行时算 KV scale」这条路

上一节的两个来源之外,还有一个很多人会假设存在、但**基准上确实不存在**的第三条:运行时统计 KV 的动态范围、自动算出 scale。

代码里留着三个看起来正是干这个的经验常量。但它们**在全仓库里除了定义处没有任何读取方**——没有方法读它、没有命令行开关、`csrc` 里也没有。更彻底的是:它们只出现在类型声明块里,**真正的环境变量表里根本没有对应条目**,所以它们连环境变量都算不上。顺带一提,它们是那整个声明块里**仅有的三个不带统一前缀的名字**,一眼就能看出是别的年代留下来的残骸。

这个发现有实际后果:**FP8 KV cache 的精度完全取决于 checkpoint 里有没有带 scale。** 拿一个没有 KV scale 的模型开 C8,拿到的就是上一节说的「硬转」,而且如果用的是 E5M2,连告警都不会有。

### 1.41 量化发生在写进 cache 那一刻

写入路径很短:注意力层拿到 BF16 的 key 和 value 之后,交给一个统一的更新入口,最终落到后端的写 cache 算子,把两个 scale 一起传下去。

CUDA 那一侧的数值语义是**除以 scale**——和 1.5 的公式一致。这里有一个细节决定了整条路径的安全性:**转换用的是饱和模式,超出范围的值被 clamp 到 ±448,不产生无穷大或非数。**

这一条和上一节串起来看就明白了 C8 为什么敢用默认 scale 1.0:**即使 scale 完全没校准、某些值超出了 E4M3 的表示范围,结果也只是被削到边界,而不是污染出一个 NaN 把整条序列毁掉。** 不量化的时候则直接做一次类型转换,不走这条路。

### 1.42 读出来不反量化:原生 FP8 的注意力

这是 C8 最漂亮的一处:**FlashAttention 直接吃 FP8 的 key 和 value,不需要先反量化成 BF16。**

具体做法是:cache 张量按 uint8 分配(1.15 说过),进 kernel 之前先按位重解释成真正的 FP8 类型——这样绕开了某些 torch 版本对 FP8 类型的算子限制;然后把三个 scale 的倒数一起传进去。kernel 内部在 FP8 tensor core 上直接算注意力分数,**用两个 scale 的乘积把分数还原到真实尺度**再做 softmax,之后乘上 value 那一侧的 scale。

**整条路上没有任何中间的反量化张量。**

这和 1.21 讲的「反量化后置到 epilogue」是**同一个思路在注意力上的复现**:既然 scale 是常数因子,就没必要先把数据还原回高精度再算,而是让低精度的数算完、把常数因子留到必须用真实尺度的那一步(这里是 softmax 之前)再乘进去。**全章反复出现的那条暗线——能提出去的常数因子就别在主循环里乘——在这里第三次出现了。**

配套地,**query 也可以被量化成 FP8**,条件是后端支持、KV 用的是 FP8 或 NVFP4、且不是每 token 每头那一档。这里的注释解释了一个实现选择:量化 query 用的是普通的 torch 算子而不是自定义算子,**理由是让编译器能把它融进上游、降低 decode 期的开销**——正是 1.38 那条思路的又一次应用。

query 的 scale 如果 checkpoint 没给,会**退化成 key 的 scale** 并告警。到这里,本章已经出现了第三种降级:默认 scale 取 1.0、没有 CUTLASS 就退回 per-tensor 动态、query 的 scale 借用 key 的。**三处的共性是:缺了就用一个「大概不会错得太离谱」的替代值继续跑,而不是拒绝启动。** 这个取向让 vLLM 很好用,代价是**精度问题不会以报错的形式暴露**,只能靠看日志和看账本(1.13)。

### 1.43 谁支持 C8,以及怎么按层跳过

C8 的支持面比 W 和 A 都窄,因为它要求 attention kernel 本身能处理量化过的 cache。FlashAttention 的白名单只有五项:不量化的三种,加上 `fp8` 与 `fp8_e4m3`——**不含 E5M2**。E5M2 主要留给 Ampere 上的其他后端,而且有专门的校验禁止它和 FP8 的 checkpoint 混用。

还有一个开关值得单独记:**可以按层把某些层排除在 C8 之外**,支持按层号指定,也支持按「滑动窗口层」这个类型批量指定。典型用法就是后者——**滑窗层本来就只保留很短的一段 KV,省不了多少显存,那就让它保持 BF16 换精度。**

这是全章唯一一处**非全局的量化决策**:W 和 A 的方案一旦选定就作用于所有被覆盖的层,只有 C 这一侧提供了按层退出的口子。

### 1.44 一层里到底发生了什么:五条铁律

把 1.35 到 1.43 串起来,一个标准的解码层在 FP8 的 W8A8 加 C8 配置下,可以收成五条判定规则。它们各自的出处都在前面,合起来是一张「哪里量化、哪里不量化」的速查:

**① 层与层之间的通路永远是 BF16。** 量化只发生在矩阵乘和注意力的**内部**,进去之前量化、出来之前已经转回高精度。唯一的例外是 1.38 那条上游融合打开时,上游可以直接把 FP8 交给下游。

**② 累加永远是 FP32。** 1.7 那条等式的中间那一步,在整章任何一个方案里都没有变过。

**③ 归一化、旋转位置编码、softmax、激活函数都不量化。** 这些算子访存少、数值敏感,量化既没什么收益又要掉精度。

**④ A8 的 scale 和 C8 的 scale 完全独立。** 这是 1.3 那条易混点的最终形态:一个用在进矩阵乘之前,一个用在写 cache 之前,走的是不同的 kernel,取值也毫无关系。

**⑤ 每个 Linear 各自量化一次激活。** 注意力的四个投影、前馈的三个投影,每一个都要在自己的入口重新量化一遍输入。**这正是 1.38 那条上游融合优化在小 batch 下值钱的原因**——省的不是一次,是每层好几次。
