# vLLM 11|量化

一次推理里有三样东西在吃资源:权重、激活、KV cache。它们按 BF16 计价时分别卡住显存、算力和上下文长度,而量化就是把其中某几样换成「低精度数据张量加若干个 scale」。这一章讲清 vLLM 里有哪些地方能量化、每一处是怎么量的、以及配错了会发生什么——最后这件事比想象中要紧,因为大多数配错的组合**不会报错**。

vLLM 的量化模块是全项目覆盖面最广的一块:二十多种方案、九张 kernel 候选表、十八种 KV cache 格式。所以本章比别的章分得细一些,九个部分各答一个问题,**从任意一部分切进去都能读**。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:量什么、怎么算

### 1.1 三笔账,卡在三个不同的地方

不量化会出什么事?最直接的回答是「显存不够」,但这个回答太粗——三样东西吃的是同一块显存,卡住的却不是同一件事:

| 吃什么 | 量级 | 真正卡住的是什么 |
|---|---|---|
| **权重** | 与参数量成正比。70B 按 BF16 是 140GB | **装不装得下。** 一张卡装不下就必须切分,切了就要通信 |
| **激活** | 与这一步算多少 token 成正比 | **算力用了几成。** tensor core 有 8bit 通路,喂 BF16 等于只用一半 |
| **KV cache** | 与「上下文长度乘并发」成正比。70B 按 02 章 1.3.3 的口径是每 token 320KB | **能跑多长、多少并发。** 长上下文下它比权重还大 |

三个痛点方向不同,所以省法也不同,而且**省了一样不等于省了另一样**:

- **只量化权重** 的方案(W8A16)把权重换成 8bit,激活仍是 BF16。GEMM 的两个输入精度不一致,算之前还得把权重反量化回 BF16 才能乘——**省了显存,一点算力没省**,甚至多了一次反量化。
- **权重和激活一起量化** (W8A8)之后两个输入都是 8bit,才真正走得上 8bit tensor core:**省显存、省访存带宽、算力翻倍**。
- **再把 KV cache 压到 8bit** (W8A8C8)动的是第三笔账。长上下文或大 batch 时这一步收益最大,因为那时 KV cache 本来就是最大的那一块。

这条线索贯穿全章:**每一个量化方案,都可以先问它动了三笔账里的哪几笔。** 后面讲到的所有家族——权重-only 的 AWQ/GPTQ、4bit 的 NVFP4/MXFP4、KV cache 的十几种变体——差别首先在这里,其次才在数值格式和粒度上。

顺着这条线,全章要回答的是五个递进的问题,九个部分分别落在上面:

| 问题 | 在哪部分 |
|---|---|
| 量什么、怎么算 | 本部分(三笔账、公式、粒度、量化类型的统一描述) |
| vLLM 用什么结构组织这件事 | Part 2(三层抽象、kernel 怎么选、方案总表与 KV 格式全表) |
| 划不划算 | Part 3(把三笔账变成可算的收益,以及粒度的代价从哪来) |
| 三笔账各自怎么做 | Part 4(W、A、C 三条链路各自的实现与五条铁律) |
| checkpoint 里那些张量从哪来 | Part 5(离线算法。**vLLM 不做这一步**,但不懂它就读不懂参数表) |
| 十几种方案各自长什么样 | Part 6(逐个落到 vLLM 侧:AWQ、GPTQ、新数值格式、KV 全谱、MoE) |

### 1.2 W、A、C:三笔账各自在哪里下手

vLLM 把这三笔账做成了三个正交的维度,名字就叫 W、A、C:

| 维度 | 量化的是什么张量 | 归谁管 |
|---|---|---|
| **W** (Weight) | `qkv_proj`、`o_proj`、`gate_up_proj`、`down_proj`,以及 MoE 各专家的权重矩阵 | 命令行的 `--quantization`,或 checkpoint 自带的 `quantization_config` |
| **A** (Activation) | 每个 Linear 的输入,也就是上一层的输出或 LayerNorm 的输出 | 同上,但具体开关在方案内部——`activation_scheme` 或 `input_activations` |
| **C** (KV Cache) | 写进分页 KV cache 的 key 与 value,以及可选的 query 和 softmax 输出 | 命令行的 `--kv-cache-dtype` |

「彼此独立、可任意组合」不是一句修辞:**W 和 A 由一个参数管,C 由另一个参数管,两个参数互不干涉。** 一个 BF16 模型可以只开 C8;一个 FP8 模型也可以让 KV 保持 BF16。所以读到「这个模型是 FP8 的」时,要追问一句:FP8 指的是 W、A 还是 C。

### 1.3 A8 不是 C8:同一个「8」,两套东西

这是全章最容易读错的一处,而且错了会一路错下去。**W8A8 里的 A8 指 Linear 层输入的量化,C8 指 KV cache 存储的量化。** 两者除了都是 8bit,几乎没有共同点:

| | A8(激活量化) | C8(KV cache 量化) |
|---|---|---|
| 用哪个 scale | `input_scale`(静态时来自 checkpoint) | `k_scale` 与 `v_scale` |
| 什么时候量 | 进 GEMM 之前 | 写进 cache 之前 |
| 走哪条代码 | FP8 走 `QuantFP8`,INT8 走 `scaled_int8_quant` | 走写 cache 的那个算子 |
| 量完之后 | 立刻被消费,不留存 | **要在显存里躺很久**,直到请求结束 |

最后一行是两者性质上的分野:**激活量化的误差只影响这一次乘法,KV cache 量化的误差要被后面每一步注意力反复读到。** 这也是为什么 KV cache 那一侧发展出了十几种数值格式(见 2.6),而激活那一侧只有寥寥几种——误差在时间上被放大的那一侧,值得用更复杂的格式去换精度。

### 1.4 三大类之外,还有几处能下手的地方

W、A、C 覆盖了绝大部分,但代码里还有几个位置也在量化。讲稿把它们排成一张平铺的清单,而源码里的结构比那整齐得多——它们其实分三类:

**两处仍然是 W,只是形状或默认值不同。** MoE 各专家的权重是三维张量(专家数乘输出维乘输入维),scale 也因此多一维,由融合 MoE 的量化方法族处理。`lm_head` 与 embedding **默认不量化**,被放在忽略名单里;AWQ 与 GPTQ 提供了显式打开的开关,compressed-tensors 有专门的 embedding 量化方法。

**三处在 attention 内部,而且是同一套。** query 在开了 C8 且后端支持时也会被量化成 FP8;softmax 的输出(FP8 attention 第二个 GEMM 的输入)有自己的 scale;attention 的输出可以**直接以量化形态交出去**,让下游的 `o_proj` 省掉一次量化。这三个容易被读成三个孤立的角落,实际上 **query、key、value、softmax 输出这四个 scale 是由同一个方法一次性创建的**,它们是一条链:进 attention 的量化、cache 里的量化、attention 内部第二个 GEMM 的量化。只有输出那个 scale 在 attention 层本身。

输出这一处还有个值得记的实现细节:**那个 scale 是 kernel 写出来的,不是传进去的。** 自定义算子的声明里把它和输出张量一起列为「会被修改的参数」——也就是说,scale 由算 attention 的那一步现场产出。这正是「输出直接量化好」这句话的实现方式:不是事后再量一遍,而是让算完的那个 kernel 顺手把 scale 也算出来。

**一处根本不是量化。** 权重的 Hadamard 旋转是量化**前**的等价变换,用来把离群值摊平到各个维度上,好让后续量化的动态范围小一些。它不改变数学结果,只改变数值分布。把它和量化本身混为一谈,会以为它也带精度损失。

### 1.5 量化在算什么:两个公式

量化就是把一段浮点数映射到一个小整数区间,再记住映射系数。分对称与非对称两种。

**对称量化** 假设分布以零为中心,零点固定在 0:

$$
s = \frac{\max |x|}{Q_{max}}, \qquad \hat{x} = \mathrm{clamp}\left(\mathrm{round}\left(\frac{x}{s}\right),\ Q_{min},\ Q_{max}\right), \qquad x \approx s \cdot \hat{x}
$$

**非对称量化** 不做这个假设,多带一个零点偏移:

$$
s = \frac{\max(x) - \min(x)}{Q_{max} - Q_{min}}, \qquad z = Q_{min} - \frac{\min(x)}{s}, \qquad \hat{x} = \mathrm{clamp}\left(\mathrm{round}\left(\frac{x}{s}\right) + z,\ Q_{min},\ Q_{max}\right)
$$

代价差别很直接:对称量化只需要存一个 scale,GEMM 里也只是乘个系数;非对称多一个零点,而零点在矩阵乘法里**不能简单地乘过去**——它会展开出一个额外的修正项,需要在权重那一侧预先算好一份补偿量。代码里这两样东西叫 `azp` 与 `azp_adj`(activation zero point 及其权重侧修正项)。所以非对称量化精度更好,但要多一份参数和一段额外计算。

### 1.6 $Q_{max}$ 从哪来,以及 ROCm 上那个 224

上面两个公式里的 $Q_{min}$ 与 $Q_{max}$ 由目标数值类型决定:

| 目标类型 | $Q_{min}$ | $Q_{max}$ | 备注 |
|---|---|---|---|
| INT8 | −128 | 127 | 整数类型的极值 |
| FP8 E4M3 | −448 | 448 | NVIDIA 平台的主流 8bit 浮点 |
| FP8 E4M3FNUZ | −224 | 224 | ROCm 专用 |
| FP8 E5M2 | −57344 | 57344 | 动态范围大、精度差,vLLM 只在 KV cache 上用 |

E5M2 那一行解释了它为什么只出现在 KV cache:指数位多一位、尾数少一位,能表示的范围宽得多但每一档之间更疏。KV cache 里偶尔出现的大值比普遍的小误差更致命,所以宽范围在那里划得来;GEMM 的输入不吃这一套。

第三行那个 224 值得单独看一眼,因为它是**硬编码的,而且和硬件手册对不上**。ROCm 用的 FNUZ 变体按规格最大值是 240,vLLM 却取 224。源码注释写明了理由:**按 240 走,ROCm 上做动态量化的模型会掉精度。** 于是这里牺牲了一点表示范围换数值稳定。判断平台并返回这对极值的那个函数只有九行,是本章少数几个行号在讲稿与基准之间完全没漂移的地方——顺带说明这段代码很久没动过。

### 1.7 8bit 为什么真能省:累加器永远是 FP32

把权重和激活都量化成 8bit 之后,矩阵乘法怎么算?对称量化下设 $A = s_a \hat{A}$、$B = s_b \hat{B}$,那么

$$
D = AB = s_a s_b (\hat{A}\hat{B})
$$

两个 scale 都是标量(或按行按列的向量),可以**提到乘法外面**。于是实际的执行是三步:8bit tensor core 算 $\hat{A}\hat{B}$、在 **FP32 累加器**里累加、在 epilogue 里乘上 $s_a s_b$ 再转回 BF16。

这条等式是理解整章 dtype 链路的锚点,而其中最容易想错的是中间那一步:**累加永远是 FP32,不是 FP16,也不是 8bit。** 8bit 只是乘法的输入格式;几千个乘积相加时,累加器必须有足够的动态范围,否则一路累下来早就溢出或被舍入吃掉了。后面讲每个方案的「计算流程与 dtype 转换」时,变的是输入格式和 scale 的形状,**不变的是这个 FP32 累加器**。

这也顺手解释了 1.1 里那句「只量化权重的方案一点算力没省」:它的两个输入精度不一致,凑不出上面这个可以把 scale 提到外面的形式,只能先把权重还原成 BF16 再走 BF16 的乘法。

### 1.8 一个 scale 管多大一片:粒度

上面的公式里,$\max|x|$ 是在多大一片数据上取的?这就是**粒度**,它是精度与开销之间的主旋钮:一个 scale 管的范围越小,越不容易被离群值拖累,但要存的 scale 越多、kernel 也越复杂。

vLLM 用一个二元组统一描述粒度,两个分量分别是「一个 scale 覆盖多少行、多少列」,`-1` 表示整个维度:

| 记号 | 一个 scale 管多大 | 通行叫法 |
|---|---|---|
| `(-1, -1)` | 整个张量 | per-tensor |
| `(1, -1)` | 每行,也就是每个 token | per-token,也叫 per-row |
| `(-1, 1)` | 每列,也就是每个输出通道 | per-channel,也叫 per-column |
| `(1, 16)` | 每行里 16 个元素一组 | NVFP4 的组 |
| `(1, 32)` | 每行里 32 个元素一组 | MX 系列的块 |
| `(1, 128)` | 每行里 128 个元素一组 | per-token-group,DeepSeek 的激活 |
| `(128, 128)` | 一个 128 乘 128 的二维块 | block-wise,DeepSeek 的权重 |

前三行是三个预置常量,后四行按需构造。这张表往下读会发现一件事:**新数值格式(NVFP4、MX 系)几乎都把粒度做得很细。** 位宽越低,能容忍的动态范围越窄,只能靠缩小每个 scale 的管辖范围来补——这是 4bit 方案的共同形状,Part 4 会逐个展开。

### 1.9 量化类型不是一串字符串,是一组预置常量

知道了 dtype 和粒度,还差一件事才能唯一确定「这是哪种量化」:scale 本身是静态的(来自 checkpoint)还是动态的(每次 forward 现算)。三者合起来,代码里叫一个 scale 的**完整描述**;再加上被量化的数据 dtype、可能存在的二级 scale、以及是否对称,就是一个**量化类型的唯一标识**。

这一层抽象的价值不在类本身,而在于:**代码里预先定义了一整批这样的常量。** `kFp8StaticTensorSym`、`kFp8DynamicTokenSym`、`kFp8Static128BlockSym`、`kFp8StaticChannelSym`、`kNvfp4Static`、`kMxfp8Dynamic`、`kMxfp4Static`,以及 MXFP6 的 E3M2 与 E2M3 两种布局各自的静态与动态版本……它们是模块级的具名常量,不是运行时拼出来的。

为什么这件事重要:**后面好几处「支持哪些量化」的判断,实现上就是一张以这种常量为键的字典。** 2.4 会看到在线量化的能力边界字面上就是两个这样的字典——所谓「只支持这几种」不是一条人为写下的限制,而是**字典里只有那几个键**。读到能力清单时,去找那张字典比去读文档可靠。


## Part 2|vLLM 怎么组织这件事

### 2.1 三层抽象:谁解析、谁建参数、谁真算

一个量化层从 checkpoint 到算出结果,要过三层:

```text
checkpoint 的 quantization_config
  |
  v
+--------------------------+
| QuantizationConfig       |   解析 checkpoint,决定这个模型用哪种方案
+--------------------------+   每种方案一个子类,逐层可以不同
  |
  v
+--------------------------+
| *LinearMethod            |   建权重与 scale 参数、加载后做后处理
+--------------------------+   不负责算
  |
  v
+--------------------------+
| kernel                   |   真正做那次矩阵乘
+--------------------------+   按格式分包:FP8/INT8、混精度、NVFP4、MXFP4/6/8
```

这个分层里有一件影响阅读的事:**GEMM kernel 不在量化方案的目录下,而是自己一个独立的包**,按数值格式而不是按量化方案分子包。也就是说 AWQ 和 GPTQ 这两个不同的方案,可能共用同一个混精度 kernel;而同一个 FP8 方案在不同硬件上会落到不同的 kernel 实现。**方案和 kernel 是多对多的**,这正是要把它们分开放的原因。

分包一共七个:FP8 与 INT8 的 scaled 矩阵乘、WNA16 的混精度(Marlin 与 Machete 那一族)、NVFP4、MXFP4、MXFP6、MXFP8,再加一个 CUTE DSL 的。其中 MXFP6 在讲稿里完全没有出现,但它不是空壳——上一节提到的两种 6bit 布局各有预置常量支撑。

### 2.2 kernel 是启动期两段筛出来的,不是算的时候挑的

上一节的第三层是怎么选定的?**在建权重的时候就选定了,不是每次 forward 现挑。** kernel 抽象基类的生命周期在注释里写得很清楚,四步:选 kernel、构造实例、加载后处理权重、推理时执行。选择发生在推理开始之前,所以热路径上没有任何分支——这和 06 章反复出现的那条原则一致:**宁可启动时多做一点,也不要在热路径上加判断。**

选择本身是**两段式**的,两个方法分工严格:

| 方法 | 只看什么 | 举例 |
|---|---|---|
| 硬件能力检查 | GPU 架构、compute capability、可用指令 | 「这个 kernel 需要 compute capability 至少 9.0」 |
| 配置能力检查 | 量化方案、粒度、静态还是动态 | 「这个 kernel 只支持静态量化」 |

两段的顺序是固定的:**先筛硬件,再筛配置。** 这一半解释了一个常被问到的现象——同一个量化格式的 checkpoint,换一张卡就走了另一条 kernel,模型和配置一个字没改。两个方法都返回「行不行」加「不行的原因」,调用方把原因记下来,所以某个 kernel 为什么没被选上是可查的。

这里有一处容易被讲反的地方。配置能力检查吃进去的是**每个 kernel 自己的一份配置对象**,不是上一节那个统一的量化类型标识——后者只是配置对象的**一个字段**。这个区别不是吹毛求疵,因为**这场统一还没做完**:FP8 那条路的配置对象里确实就是「权重的量化标识」加「激活的量化标识」两个字段,干净;而同一个文件里 INT8 那条路的配置对象**至今是三个裸布尔**(输入是不是静态方案、是不是按通道、输入是否对称),上面还挂着一条源码里自己写的待改注释,内容就是「改成像 FP8 那样用量化标识」。

所以准确的说法是:**统一描述是迁移中的目标,不是既成事实。** 读 FP8 那一支时可以按「一个标识说明一切」去理解,读 INT8 那一支时得准备好看到散装的布尔字段。

### 2.3 量化从哪来:三种来源,而且能叠

同样是「这个模型是 FP8 的」,量化这件事发生的时机可以完全不同:

| 来源 | 怎么触发 | 权重在磁盘上是什么 | 谁做的量化 |
|---|---|---|---|
| **离线 PTQ** | checkpoint 自带 `quantization_config` | 已经是 INT4/INT8/FP8 | 外部工具(llm-compressor、AutoAWQ、ModelOpt、Quark) |
| **在线量化** | `--quantization` 作用在 BF16 checkpoint 上 | BF16 或 FP16 | vLLM 自己,在加载后处理那一步 |
| **运行时动态量化** | 隐含在方案里(激活方案设成动态、KV 用按 token 按头的粒度) | 不涉及 | GPU kernel 每次 forward 现算 |

绝大多数线上场景是第一种。第二种的价值是**不需要预量化的 checkpoint**:手上只有 BF16 权重、又不想跑一遍离线量化流程时,加载时顺手量化。第三种严格来说不是一种「来源」,而是某些参数的量化时机本来就只能在运行时——激活和 KV 直到算出来才存在,不可能预先量好。

三者可以叠加,而且有两种不同的叠法。讲稿讲的那种是后两类相叠:离线的 FP8 权重,加上动态的 per-token 激活,加上动态的按 token 按头的 KV。**更值得知道的是第一类和第二类也能叠**——预量化的 checkpoint 之上还可以再挂在线量化,专门去补那个方案**没有覆盖的层**。源码注释把边界划得很清楚:checkpoint 自带的方案仍然是主方案,叠加在它的配置加载完之后才发生。于是「这个 checkpoint 是 W4A16 的,但它的 MoE 部分没量化」这种情况有救。

### 2.4 在线量化能做什么、不能做什么

在线量化的能力边界,字面上就是两张字典:一张给 Linear 层,一张给 MoE。键是 1.9 那种量化类型常量,值是对应的量化方法类。

| 格式与粒度 | Linear | MoE |
|---|---|---|
| FP8 per-tensor | 支持 | 支持 |
| FP8 128 块 | 支持 | 支持 |
| FP8 per-channel 权重加 per-token 激活 | 支持 | 支持 |
| MXFP8 | 支持 | 支持 |
| MXFP4 | 支持 | 支持 |
| INT8 per-channel | **不支持** | 支持 |
| NVFP4 | **不支持** | 支持 |

两张表共七个键,前五个两边都有(但各自对应独立的 Linear 版与 MoE 版方法类,不是同一个类复用),后两个只对 MoE 开放。

**清单之外还有一条边界更要紧:在线量化做不了 W4A16。** AWQ 与 GPTQ 那一族需要校准数据来决定每组的 scale 与零点,而加载时手上没有校准集,只有权重本身。所以 4bit 权重-only 这条路**必须离线**,没有在线版本。

最后是一处工程上的坑。配了一个不在上面表里的组合会怎样?**不报错,静默地不量化。** 分派函数查不到对应的键时,回落到「未量化」的那个方法类——Linear 一条路,MoE 一条路,都是正常返回,不是抛异常。这一段里**没有任何日志**,所以「静默」这个词在这里是准确的(而 07 章有一处看似相同的场景,基准上其实明确打了一条警告——同一个形容词必须逐处核,不能凭印象)。

想知道有没有中招,有一个可观测的入口:**匹配成功的层会被记一笔账**,记下它的量化来源、量化类型、以及命中的是哪条匹配规则。**没被量化的层就是这本账里缺的那些。** 排查「我明明开了量化,怎么显存没降」时,先去看这本账缺了谁。

### 2.6 KV cache 的十八种 dtype

`--kv-cache-dtype` 的合法取值另有一张类型字面量,共 **18 种**,是全项目里单个参数取值最多的一处:

| 取值 | 存储 dtype | 形态 |
|---|---|---|
| `auto` | 跟模型 dtype | 不量化,但见下面那条例外 |
| `float16`、`bfloat16` | 同名 | 不量化,显式指定,可以与模型 dtype 不同 |
| `fp8`、`fp8_e4m3` | uint8 | per-tensor 的 E4M3,主流 C8 |
| `fp8_e5m2` | uint8 | per-tensor 的 E5M2。Ampere 上唯一可用的 fp8 KV,FlashAttention 不支持 |
| `fp8_inc` | 真正的 fp8 dtype | Intel Gaudi |
| `fp8_ds_mla` | uint8 | DeepSeek MLA 专用的 fp8 布局 |
| `nvfp4_ds_mla` | uint8 | 同上,NVFP4 版本 |
| `int8_per_token_head` | int8 | 每个 (token, head) 动态算一个 scale |
| `int4_per_token_head` | uint8 | 同上,4bit |
| `fp8_per_token_head` | uint8 | 同上,FP8 |
| `nvfp4` | uint8 | FP4 数据加 FP8 块 scale 打包 |
| `nvfp4_4over6` | uint8 | NVFP4 布局,但每 16 个值在两个候选 scale 里挑重建误差更小的那个 |

| `turboquant_k3v4_nc` | uint8 | key 3bit、value 4bit,加范数修正。约 3.5 倍 |
| `turboquant_3bit_nc` | uint8 | key 与 value 都 3bit,加范数修正。约 4.9 倍 |

压缩倍数是量级参考,不是本仓库实测。

**多数低精度格式都用 uint8 存。** 这不是含糊,而是刻意的:4bit、3bit 这些位宽没有对应的张量 dtype,只能打包进字节数组,由 kernel 自己按布局解包。所以「存储 dtype 是 uint8」在这张表里等价于「有一套自定义的打包布局」,而 `fp8_inc` 那一行用真 fp8 dtype 是少数例外。

有两行的细节容易踩:

**`auto` 不总是「不量化」。** checkpoint 里声明了 KV 量化算法时,`auto` 会被解析成 fp8。更进一步,**少数模型默认就是 fp8**,要退回 BF16 必须显式写出来。而这里有个反向的坑:字段说明紧接着写了**对于不默认 fp8 的模型,显式写 `bfloat16` 是非法选项**——它不是一个「总是安全的保守选择」,在普通模型上写它会直接被拒。

**平台支持不一样。** 同一个字段的说明里带着一张平台矩阵:CUDA 11.8 及以上支持 `fp8`(等于 `fp8_e4m3`)与 `fp8_e5m2`,ROCm 只支持 `fp8`,Intel Gaudi 走 `fp8_inc`。挑格式之前先看平台。

`nvfp4_4over6` 那一行值得单独欣赏一下它的做法:同样是 NVFP4 的布局,但每 16 个值不是直接用最大值定 scale,而是在「最大值除以 6」和「最大值除以 4」两个候选里,选**平方重建误差更小**的那一个。多一次试算,换一点精度——这是 4bit 方案里很典型的思路。基准上只有一个后端声明支持它。

### 2.7 简写、双身份,以及 checkpoint 优先

`--quantization` 的取值里有一批是**在线量化的简写**,它们不对应独立的配置类,只是「在线量化框架加一组固定配置」的语法糖。脱糖规则是一张字典,**共七个键**:FP8 的三种粒度、MXFP8、MXFP4、MoE 的 INT8 per-channel、MoE 的 NVFP4。后两个的配置里**只有 MoE 一项、没有 Linear 项**,源码注释直接写着「Linear 保持不量化」——这就是 2.4 那张表里两行「不支持」的来源。NVFP4 那一项还带一条硬件限定,只在 Blackwell 加特定后端上可用。

这里有一处结构上很有意思的冲突:**七个简写里有两个名字同时也是 checkpoint 方案的名字**——MXFP8 和 MXFP4。同一个字符串,既可能是「用在线量化按这个格式量」,也可能是「这个 checkpoint 就是这个格式」。代码怎么分辨?

**注册简写用的是「不覆盖已有键」的写法,所以 checkpoint 路径优先。** 某些厂商的 checkpoint 会把量化方法标成 `mxfp8`,这种情况下走的是 ModelOpt 那份配置类,而不是在线量化。

但「那么 `--quantization mxfp8` 就走在线量化了」这个推论**不成立**,这是本章最容易想错的一处。这两个名字被单独列进了一个**延后名单**,注释写明:它们也是 checkpoint 方案名,**它们的在线配置只在 checkpoint 没有量化元数据时才被解析**。落到代码上就是:只给了 `--quantization mxfp8`、没给量化配置参数时,解析函数**直接返回空**,把决定权交回 checkpoint 元数据。要真正走在线量化,必须**两个参数一起给**。

所以这两个名字的准确语义是:「如果 checkpoint 自己说了它是什么,听 checkpoint 的;否则再看有没有给在线配置」。分流确实发生在那个解析函数里,但方向是**默认让位**,不是默认在线。

顺带把两个 CLI 参数的关系收口:**`--quantization` 管 W 和 A,`--kv-cache-dtype` 管 C,两者正交。** 一个 BF16 模型可以只开 C8;一个 FP8 模型也可以让 KV 保持 BF16。1.2 说过这件事,这里是它在参数层面的对应。

### 2.8 量化前的基准:各张量原本是什么形状

后面每一个方案做的事,都是把下表中的某几行换成「低精度数据张量加若干个 scale」。所以先把量化**前**的形状钉住,当作全章的对照底。形状里的维度名对应源码里的哪个变量,一并列出——这几个名字在读任何一个量化方法的建参数代码时都会遇到:

| 张量 | 量化前形状 | dtype |
|---|---|---|
| Linear 权重 | 输出维乘输入维 | bf16 |
| Linear 输入激活 | token 总数乘输入维 | bf16 |
| Linear 输出 | token 总数乘输出维 | bf16 |
| attention 的 query | token 总数、query 头数、每头维度 | bf16 |
| attention 的 key 与 value | token 总数、KV 头数、每头维度 | bf16 |
| KV cache | block 数、KV 头数、每 block 的 token 数、两倍每头维度 | bf16 |

| 维度 | 源码变量 | Llama-3-8B 取值 |
|---|---|---|
| 隐藏维 | `hidden_size` | 4096 |
| query 头数与 KV 头数 | `num_attention_heads`、`num_key_value_heads` | 32 与 8 |
| 每头维度 | `head_dim` | 128 |
| Linear 输入维(张量并行切分后) | `input_size_per_partition` | `qkv_proj` 是 4096 |
| Linear 输出维(张量并行切分后) | `output_size_per_partition` | `qkv_proj` 是 6144 |
| 融合层里有几个独立 Linear | `output_partition_sizes` 的长度 | `qkv_proj` 是 3 |
| 权重分组大小 | `group_size` | 128 |
| 权重二维块尺寸 | `weight_block_size` | 非块量化时不存在 |
| 本 rank 上的专家数 | `local_num_experts` | 仅 MoE 模型 |
| FFN 中间维(切分后) | `intermediate_size_per_partition` | 14336 |
| 每 block 容纳的 token 数 | `block_size` | 默认 16 |

两条换算后面反复用到:

**`qkv_proj` 的输出维是三段之和**,query 一段加 key、value 各一段。Llama-3-8B 上是 32 乘 128 加上两倍的 8 乘 128,即 4096 加 2048 等于 6144。

**没有「batch 乘 seq」这两维。** 表里的「token 总数」是整个 batch 展平后的一维长度,等于各请求本次要算的 token 数之和——调度器把整个 batch 拼成一维再进模型,机制见 02 章 2.7。prefill 时它是几千,纯 decode 时它约等于并发数。

最后那张表里,「融合层里有几个独立 Linear」这一行是后面理解 scale 形状的钥匙。`qkv_proj` 逻辑上是三个 Linear 融合成一个、`gate_up_proj` 是两个,而 **per-channel 的 scale 要按这几段分别算**——一个融合层的 scale 张量因此不是一整条,而是按段拼起来的。这个细节在 1.8 的粒度表里看不出来,要到具体方案的建参数代码里才显形。

KV cache 那一行的「布局随后端变」不在本章展开:五维形状与布局枚举在 03 章 1.9 已经讲过(那里还消歧了「整体五维含层维、每层四维」),`block_size` 的取值权衡也在那里。


## Part 3|收益账与粒度的数学

### 3.1 收益落在哪个阶段:把三笔账再切一刀

1.1 按「吃什么」把资源分成三笔账。还有一刀切法同样重要:**按阶段**。一次推理的两个阶段瓶颈完全不同,而三笔账的收益分别落在不同的阶段上:

| 阶段 | 计算特征 | 瓶颈 | 量化的收益从哪来 |
|---|---|---|---|
| **Prefill** | 大 GEMM,一次算的 token 数可达上万 | **算力** | 8bit tensor core 吞吐约是 BF16 的两倍 |
| **Decode** | GEMV 或很瘦的 GEMM,token 数约等于并发数 | **访存带宽** | 权重字节数减半,读权重的时间就减半 |
| **Attention** | 读 KV cache | **带宽加容量** | KV 减半,能开更大 batch、更长上下文 |

把这张表和三笔账叠起来,得到三条判断——它们决定了一个方案值不值得用:

**权重量化的收益主要在 decode,而且不需要激活配合。** decode 时每一步只算很少的 token,GEMM 退化成读一遍权重再做一次很瘦的乘法,时间几乎全花在把权重从显存搬进来上。权重字节数减半,这段时间就减半——**即使激活仍然是 BF16**。这正是只量化权重的方案(W8A16、AWQ、GPTQ)在小 batch 下依然有效的原因,尽管 1.1 说过它「一点算力没省」。省算力和省带宽是两件事,decode 阶段要的是后者。

**激活量化的收益主要在 prefill 和大 batch。** token 数大时才真正吃算力,这时候两个输入都是 8bit 才有意义。反过来看更要紧:**token 数很小时,A8 甚至可能让它变慢。** 因为量化激活本身是一个额外的 kernel——读一遍 BF16、求最大值、写一遍 FP8;这点开销在大 batch 里可以忽略,在 decode 的一步里未必。

**KV cache 量化的收益随上下文长度线性增长。** 它不挑阶段,只挑长度:上下文越长、并发越高,KV cache 在显存里占的比重越大,C8 省下来的就越多。

代价也有四类,其中最后一类容易被忽略:

- **精度损失**:8bit 只有 256 个可表示值,粒度越粗损失越大。
- **额外 kernel 开销**:上面说的那次动态求最大值。vLLM 用编译把量化算子融合进上游来缓解。
- **校准成本**:静态激活量化与 INT8 需要离线跑一遍校准集才能定出激活的 scale。
- **硬件门槛**:**FP8 tensor core 要 SM89 及以上**(Ada、Hopper、Blackwell),而 **INT8 tensor core 从 SM75(Turing)就有**。这一条正好解释了 2.2 那个「先筛硬件、再筛配置」为什么必须存在:同一份 FP8 checkpoint 在两代卡上根本不是同一件事。

### 3.2 同样一个字节,两种花法

8bit 有两种花法,差别不在能表示多少个值——**两者都是 256 个**——而在这 256 个值怎么分布:

| | INT8 | FP8 E4M3 | FP8 E5M2 |
|---|---|---|---|
| 比特分配 | 1 符号加 7 数值 | 1 符号加 4 指数加 3 尾数 | 1 符号加 5 指数加 2 尾数 |
| 分布 | **均匀**,等间距 | **非均匀**,接近 0 处密集 | 更极端的指数分布 |
| 动态范围 | 固定 1 比 127,靠 scale 平移 | ±448,内部就有约 $2^{17}$ 的动态范围 | ±57344 |
| 相对精度 | 大值处高、小值处低 | **全域恒定**,约 $2^{-4}$ | 约 $2^{-3}$ |
| 离群值鲁棒性 | **差**:一个离群值抬高 scale,其余值全被压进几个格子 | **好**:离群值只占用指数位,小值仍有 3 位尾数 | 范围更宽但精度更差 |
| 硬件 | Turing 及以上,整数累加 | Ada、Hopper 及以上,FP32 累加 | 同 E4M3 |

「均匀 vs 指数分布」这一行是题眼,其余各行都是它的推论。INT8 把 256 个刻度等距铺在 $[-s\cdot127, s\cdot127]$ 上,所以绝对精度处处相同、相对精度随数值变小而变差;FP8 把刻度按指数密集地堆在 0 附近,所以**相对**精度处处相同。

E5M2 的位置在 2.6 已经交代过:它只用在 KV cache 上,线性层不用——两位尾数对乘法来说太糙了。

### 3.3 离群通道:为什么 FP8 不用校准,INT8 要

上一节那张表里「离群值鲁棒性」一行,是整章「为什么 FP8 比 INT8 好用」的全部根因,因为 **LLM 的激活里普遍存在离群通道**:某几个隐藏维的幅值比其他维大几十倍。

对 INT8 来说这是灾难。per-tensor 量化激活时,scale 由全张量的最大值决定,于是被那几个离群通道拉大;剩下几千个普通通道的值除以这个被撑大的 scale 之后,全都落进 int8 的低几位里——**可表示值还是 256 个,但实际用上的只有最低那几档**,精度直接崩掉。SmoothQuant、AWQ 这类方法要做的「把离群值从激活迁移到权重」,解决的就是这件事:用一个对角缩放把激活压平、把压下去的那部分乘进权重里,数学上等价,但两边的分布都变得好量化了。

FP8 E4M3 天生不怕这个。离群值大,只是把它自己的**指数位**抬高,普通小值该有几位尾数还是几位——相对精度不受影响。于是结论很直接:**FP8 的动态 per-token 量化就够用,不需要校准数据。**

这一条落到 vLLM 的默认值上就是:

- **FP8 的 W8A8 默认动态量化激活**,开箱即用,不需要任何校准集。
- **INT8 的 W8A8 要么静态 per-tensor**(那就得离线跑校准算出激活 scale),**要么动态 per-token**;而且 INT8 额外支持非对称——因为它是均匀网格,加一个零点能多榨出一点有效位宽,这对指数分布的 FP8 没什么意义。

### 3.4 为什么 per-channel 权重配 per-token 激活是「免费」的

1.7 给了反量化的等式,但那是没有下标的版本。真正决定开销的是**下标**。设 $i$ 走 token、$j$ 走输出通道、$k$ 走输入通道,per-token 的激活和 per-channel 的权重分别是:

$$
X_{ik} \approx s^X_i \cdot \hat{X}_{ik}, \qquad W_{jk} \approx s^W_j \cdot \hat{W}_{jk}
$$

那么 GEMM 要算的是:

$$
D_{ij} = \sum_k X_{ik} W_{jk} = \sum_k \left(s^X_i \hat{X}_{ik}\right)\left(s^W_j \hat{W}_{jk}\right) = s^X_i s^W_j \cdot \sum_k \hat{X}_{ik}\hat{W}_{jk}
$$

关键在最后一步:**$s^X_i s^W_j$ 不含 $k$,所以可以整体提到求和号外面。** 这一提,整条流程就被劈成两段互不干扰的部分:

- **主循环**,规模是「token 数乘输出维乘输入维」:纯粹的低精度 tensor core 乘累加,**指令流里一条乘 scale 的指令都没有**,因此能跑满硬件的 8bit 峰值算力。
- **epilogue**,规模是「token 数乘输出维」:累加器写回显存之前,顺手乘上那两个 scale(再加 bias)。

第二段的运算量只有第一段的 $1/\text{in\_features}$,典型值是四千分之一;而且它和「累加器转成输出 dtype」本来就要做的那次读写**融合在一起**,不额外增加任何显存访问。

所以「免费」的确切含义不是没有开销,而是**开销落在一个比主循环小三个数量级的阶段上,并且被访存完全掩盖**。这个说法在代码里能直接看到:Python 侧调用矩阵乘时,只是把两个 scale 张量原样传进去、顺带指定输出 dtype 就直接是 BF16,**中间不落一次 FP32**;按行还是按列广播由 kernel 自己决定。

### 3.5 什么组合不免费:一条判据

反过来看哪些组合提不出去,这条规律才立得住。

**激活如果按输入通道量化**,$s^X$ 的下标里就有了 $k$,提不出求和号,只能在主循环里逐 $k$ 乘。这正是 1.8 那张粒度表里 per-channel 不能作用于激活的原因——不是算不出来,而是那样做等于**放弃 tensor core 的连续累加**。上一节说的 SmoothQuant 之所以要把缩放**离线折进权重**,也是为了绕开这一点:折完之后运行时又回到了 per-token。

**权重如果按输入通道分组**(group 或 block),$s^W$ 的下标里出现 k 方向的块号,同理必须进主循环。

于是可以把这一组规律压成一句话:

> **scale 的下标只要落在 GEMM 的输出坐标上,反量化就能后置到 epilogue;一旦下标里出现被求和的那个维度,反量化就必须进主循环。**

四种常见组合按这条判据排下来是:

| 权重粒度 | 激活粒度 | 反量化在哪 | 主循环被干扰吗 |
|---|---|---|---|
| per-tensor | per-tensor | epilogue,标量乘 | 否。最简单 |
| per-channel | per-token | epilogue,行列广播乘 | 否。上一节那个「免费」组合 |
| per-channel | per-token 加非对称 | epilogue,多一项零点修正 | 否。修正项的下标同样只有输出坐标 |
| block | group | **主循环内**,逐 k 块反量化 | **是** |

非对称那一行值得多看一眼:它多出来的修正项是「权重沿输入维求和」得到的一个长度等于输出维的向量,静态量化时还会把激活零点直接乘进去预先折好。**下标仍然只有输出坐标,所以照样能留在 epilogue**——非对称的代价是多一个参数和一次预处理,不是打断主循环。代码里对称与非对称走的甚至是两个不同的算子,按有没有那个修正项分派。

### 3.6 block 量化为什么非要专门的 kernel

最后一行是唯一被打断的那个,值得单独算一遍。把 $k$ 按 128 切成若干 k 块,权重再按输出方向切块,两侧的 scale 就都带上了块号:

$$
D_{ij} = \sum_{kb} \underbrace{s^X_{i,kb}\, s^W_{jb,kb}}_{\text{随 } kb \text{ 变化}} \cdot \sum_{k \in kb} \hat{X}_{ik}\hat{W}_{jk}
$$

现在提不出去了:每个 k 块有自己的一对 scale,必须「先把这一段的低精度点积算完、乘上这一段的 scale、再累加到 FP32 累加器」。反量化从 epilogue 挪进了 k 方向的主循环。代价出在四个地方:

| | per-channel 配 per-token | block 配 group |
|---|---|---|
| 反量化位置 | epilogue,执行 1 次 | 主循环内,执行「输入维除以块宽」次 |
| 每次迭代的额外指令 | 无 | 两次 scale 读取加一次逐元素乘 |
| 累加链 | tensor core 内部一路累到底 | **每段都要出累加器、乘完再加回去** |
| tile 尺寸自由度 | 任意 | k 方向的 tile 必须和 scale 的块宽对齐 |

**第三行才是真正的性能杀手。** tensor core 最快的形态是「连续发射多条乘累加指令、累加器留在寄存器里不动」;一旦每 128 个 $k$ 就要把累加器取出来做一次逐元素乘,这条流水线就被打断了。这也解释了为什么 block 量化基本只在 Hopper 及以上才划算——那一代有异步搬运和 warpgroup 级异步乘累加,能把 scale 的读取和逐元素乘塞进等待间隙;更早的架构上这段代价藏不住,直接表现为吞吐下降。(这一段是硬件机制参考,不在本仓库源码的核对范围内。)

**换来的是精度。** per-token 只能给整行一个 scale,行里只要有几个离群通道,其余通道就被压到只剩几个有效格子;block 与 group 把范围缩到 128 个元素,离群值的影响被关在自己那一格里。这正是 DeepSeek 那一系敢用 FP8 同时做训练和推理的前提。

最后一个容易搞混的点:**激活侧配的是「每行 128 个一组」,不是二维的 128 乘 128。** 因为 token 数运行时才知道、而且每步都变,没法按 token 分块;何况逐 token 独立算 scale 本来就是好事(不同 token 的幅值差异很大)。所以「权重二维分块加激活一维分组」是这条路径固定的搭配。

这里有个实现上的暗礁:**激活那一维的组宽取自权重块尺寸的第一个分量**,也就是输出方向那个,而不是输入方向那个。DeepSeek 系两个值都是 128,所以看不出区别;一旦两者不等,这个取法就会显形。

### 3.7 于是 block 路径有自己一整套 kernel 候选

2.2 讲的是「怎么从候选里筛」,这里补上的是「候选是谁」。vLLM 为 block 路径准备了**一组完全独立的 kernel 候选**,和非 block 的那组分开维护;分水岭就是上一节那个结构差异——**判的是激活那把 key 的粒度是不是「分组」**。正因为激活被配成了每行 128 一组(而不是 per-token),这个判定才成立。

block 那一组的候选按优先级排下来是:DeepSeek 开源的 Hopper 专用实现最快,排第一;CUTLASS 的块缩放版本次之;最后是 Triton 写的兜底实现,任何平台可用但慢。

两组候选还有一处不对称值得记:**非 block 那一组可以在运行时被追加**——有一个注册入口允许把新 kernel 挂进某个平台的候选表;block 那一组没有对应的入口。所以第三方想插一个自己的 FP8 kernel 进来,只能插进非 block 那条路。

### 3.8 同一个粒度,作用在权重和激活上形状不同

前面几节讲的是粒度怎么影响计算,这一节讲它怎么落到**参数张量的形状**上。一条通用规律管住全部:**同一个粒度作用在权重和激活上,得到的 scale 形状不同,因为「行」的语义不同——权重的行是输出通道,激活的行是 token。**

| 粒度 | 作用于权重 | 作用于激活 | 权重侧 scale 个数 |
|---|---|---|---|
| per-tensor | 一个标量 | 一个标量 | 1 |
| per-channel | 每个输出通道一个 | **不适用**,见下 | 输出维 |
| per-token | 等价于 per-output-channel | 每个 token 一个 | 同上 |
| 每行 $g$ 个一组 | 输出维乘「输入维除以 $g$」 | token 数乘「输入维除以 $g$」 | 两者之积 |
| 二维块 | 「输出维除以块高」乘「输入维除以块宽」 | 只做一维分组 | 两维之积 |

「per-channel 不适用于激活」那一格不是省略,而是 3.5 那条判据的直接后果:激活的「通道」是输入维,scale 的下标会带上被求和的那一维,反量化就提不出求和号了。**这张表和那条判据是同一件事的两种写法**,一个讲形状,一个讲能不能提出去。

### 3.9 三条容易踩的形状细节

上面那张表是理想情况。实际读代码时有三处会对不上:

**① per-tensor 的 scale 在 checkpoint 里不是标量。** 融合层在磁盘上本来就是若干个独立的 Linear,各有各的 scale,所以参数按「有几个分片就开几个」来建。加载完之后才**取最大值重量化**成一个真正的标量——两个分片里幅度小的那个被迫用了更大的 scale,这是融合的代价。

这一条和 NVFP4 的二级 scale 恰好形成对照:那里也是按分片存,但处理方式是**校验所有分片必须相同,不同就直接失败**。同一个「分片各存一份」的形状,一个容忍不一致并取最大值,一个完全不容忍——因为前者是可以牺牲一点精度的量化 scale,后者是决定整个数值范围的全局系数。

**② 激活的动态 scale 是 forward 期的临时产物,不是参数。** 它的形状里那个尾随的 1 是被显式加出来的:先沿最后一维求绝对值最大,再把被消掉的那一维补回去。所以是「token 数乘 1」而不是「token 数」——后面每张表里激活 scale 都带这个尾巴,原因就在这。

**③ block 的 scale 个数用的是向上取整,不是整除。** 写法是「加上块宽减一再整除」。理由很实际:**张量并行切分后维度不保证能被 128 整除**。比如输入维 4096、张量并行切成 3 份,每张卡是 1366,除以 128 得 10 余 86——那个只有 86 个元素的零头块同样需要自己的 scale,用整除就把它连同它管的那 86 个元素一起丢掉了。kernel 侧对零头块按实际元素数计算、不足的部分补零。

这三条里第三条最值得记,因为它是**并行切分和量化粒度撞在一起**才出现的问题:单卡上永远遇不到,一开张量并行就可能踩。

### 3.10 七种方案的参数清单

把前面几节合起来,各方案在 layer 上真实存在的参数是这样的。所有形状都按 2.8 的维度名写:

| 方案 | 权重数据 | 权重 scale | 激活 scale(运行期) | 特有参数 |
|---|---|---|---|---|
| **FP8 per-tensor** | 输出维乘输入维,加载后转置成列主序 | 标量(磁盘上按分片存) | 标量(静态)或 token 数乘 1(动态) | 静态时有 `input_scale` |
| **FP8 block** | 同上,**不转置** | 二维块数,名字带 `_inv` 是 DeepSeek 的约定 | token 数乘「输入维除以块宽」 | **没有** `input_scale`,这条路强制动态 |
| **INT8 per-channel** | 同上,在 kernel 里转置 | 输出维乘 1 | token 数乘 1 | 非对称时有零点与权重侧修正项 |
| **AWQ** | 输入维乘「输出维除以 8」,沿输出维打包 | 「输入维除以组宽」乘输出维,**不打包** | 无,激活保持 BF16 | 零点张量,按打包形状存 |
| **GPTQ** | 「输入维除以 8」乘输出维,沿输入维打包 | 同上 | 同上 | 零点张量。激活重排序那一路还会带一个通道到组的映射,但**当前基准上已经不再使用**,见 6.4 |
| **NVFP4** | 输出维乘「输入维除以 2」,两个 4bit 挤一个字节 | **两级**:一级是「输入维除以 16」的 fp8 块 scale,二级是一个全局标量 | token 数乘「输入维除以 16」,而且是重排过的内存布局 | 激活也有自己的全局 scale |
| **MXFP8 / MXFP4** | 同上(MXFP8 不打包) | 「输入维除以 32」,dtype 是 E8M0 | 同形 | **没有二级 scale** |

几处值得单独拎出来:

**AWQ 和 GPTQ 的打包方向正好相反**,但只在磁盘上如此。AWQ 在加载后处理里会把打包顺序**转成 GPTQ 那一种**,所以运行时只有一种布局。读代码时如果按磁盘形状去对 kernel 的输入,会对不上。

**转置发生在哪不一样。** FP8 per-tensor 在加载后就转好了(因为 CUTLASS 那条路要列主序),INT8 是在 kernel 里转,而 FP8 block 那条路根本不转。

**NVFP4 与 MX 系最大的结构差异是有没有第二级 scale。** NVFP4 用一个全局 FP32 标量再乘一层,MX 系直接用 E8M0——一个纯指数、没有尾数的 8bit 格式,本身就是 2 的幂,不需要再套一级。这个差异顺带决定了 scale 的开销:NVFP4 是每 16 个值配一个字节,MX 系是每 32 个值配一个字节,**后者的 scale 开销正好是前者的一半**。

### 3.11 MoE 多出来的那一维:融合的前提与代价

MoE 把每个专家的两个 Linear 堆成三维张量,于是所有 scale 都多一维专家数。但真正要讲清的不是多这一维,而是**为什么门控和上投影这两个矩阵能被融合成一个**——因为这件事直接决定了 scale 的形状。

先消一个歧义:**MoE 里有两个不同的「gate」。** 一个是**路由门控**,一个把隐藏维映射到专家数的小 Linear,产出每个 token 选哪几个专家,位置在专家计算**之前**,通常不量化;另一个是 **SwiGLU 的门控分支**,和上投影并列,位置在**每个专家内部**。被融合的是后者,和路由那个毫无关系。源码里连注释都写明了:门控分支加载进融合权重的第一个逻辑位、上投影加载进第二个。

融合的前提只有一条:**两个矩阵吃的是同一个输入张量。** 门控分支和上投影都吃派发之后的那份激活,同一份数据;而矩阵乘对输出维是可以分块的,把两个权重沿输出维拼起来做一次乘法,再切开,结果和分别做两次**逐比特相同**。收益有三重:一次 kernel 启动代替两次(MoE 里尤其值钱,因为每个专家分到的 token 很少,启动开销占比高)、输入只从显存读一次而不是两次、乘法的输出维翻倍使得分块更充分。

反过来,下投影**融不进去**,因为它的输入是前两者的输出经过非线性之后的结果,存在数据依赖,不是同输入的并列关系。源码把这件事直接写进了命名——下投影的加载注释说它进的是「唯一的那个逻辑权重位」。同一条判据也解释了注意力里的输出投影为什么不能和 qkv 融合。而这根本不是 MoE 特有的技巧:稠密模型里 `gate_up_proj` 和 `qkv_proj` 用的是同一套融合层,分片数分别是 2 和 3——这也正好回答了 3.9 第一条里「per-tensor 的 scale 为什么在磁盘上按分片存」:**拼接之前它们本来就是各自独立的层。**

融合对量化的影响有四条:

- **per-tensor 的权重 scale 是「专家数乘 2」而不是「专家数乘 1」**,因为磁盘上门控和上投影各有一个。加载后必须取最大值重量化成每个专家一个,否则一次矩阵乘里没法用两个不同的 scale。**这是融合的代价:牺牲一点精度。**
- **block 与 group 量化不需要这一步**,因为它们的 scale 本来就是沿输出维分块的,拼接之后天然还是合法的分块 scale。这是 block 量化在 MoE 上精度更好的一个具体原因。
- **激活量化作用在派发之后的那份数据上**,而派发会把每个 token 复制到它选中的每个专家的分段里。所以 per-token 的 scale 行数是「token 数乘选中专家数」——**MoE 的激活量化开销比稠密层高出选中专家数那么多倍**,而且同一个 token 的那几份 scale 数值相同却各算了一遍。
- **路由那个小 Linear 一般不量化。** 它的输出维只有专家数,省不了什么,但选谁当专家这件事对精度极其敏感。

### 3.12 KV cache:scale 藏在末维的填充里

KV cache 这一侧的形状有个和前面完全不同的做法。写进 cache 之前,key 和 value 的形状是「token 数、KV 头数、每头维度」;写进去之后按 block 组织,**具体布局由后端决定**——不是某个中心函数单方面算出来的,后端有一个改写缓存规格的钩子,会在建 cache 之前先把规格调整成自己要的样子。不支持某种量化模式的后端,根本不实现这个钩子,这就是「后端支持面窄」的机制。

最值得看的是「每个 token 每个头各算一个 scale」那一档。它**不新增任何参数张量**,而是把 scale **内联进 cache 末维的填充里**:每个头的数据后面紧跟它自己的一个 FP32 scale,key 和 value 各一份,四段依次排在末维上。这也解释了它为什么不需要 checkpoint 提供 scale——scale 是运行时算出来、就地写在数据旁边的。

代价可以精确算出来。末维的字节数是「key 与 value 的数据字节数之和,加上两个 FP32 scale」,也就是固定多出 **8 个字节**。关键在于**这 8 个字节不随 cache 的 dtype 缩放**:

| 模式 | 每个 (token, 头) 的字节数 | 相对 BF16 的压缩比 |
|---|---|---|
| BF16 | 512 | 1× |
| FP8 per-tensor | 256 | **精确 2×** |
| INT8 每 token 每头 | 128 加 128 加 8 = 264 | 1.94× |
| INT4 每 token 每头 | 64 加 64 加 8 = 136 | 3.76× |

FP8 那一行拿到的是**精确的** 2 倍,因为它的 scale 是整个张量共用的一个参数,一个字节都不内联。而每 token 每头那两档都要付那 8 个字节:INT8 上它占 3.0%,INT4 上占 5.9%——**位宽越低,这笔固定开销的相对占比越大**,这就是 INT4 拿不到理想的 4 倍、只有 3.76 倍的全部原因。

![KV cache 末维上一个 (token, 头) 的字节布局对比,四条共用一把字节尺:BF16 是 512 字节、FP8 per-tensor 是 256 字节、INT8 每 token 每头是 264 字节、INT4 每 token 每头是 136 字节。浅色是数据段,深色是内联的 FP32 scale,后两条各有 K 与 V 两块 4 字节 scale,而这两块深色在两条上宽度完全相同。数据段随位宽缩短、scale 不缩,于是 FP8 恰好落在 256 字节的理想线上拿到精确 2 倍,而 INT8 与 INT4 各被同样 8 个字节顶过自己的理想线,占比从 3.0% 升到 5.9%——这就是 INT4 只有 3.76 倍而不是 4 倍的全部原因。](/opensource/vllm/11b-inline-scale-overhead.svg)

图上**两处越线的长度一模一样**,这就是「不随位宽缩放」的意思:数据段的长度是被位宽除过的,那两块深色不是。

### 3.13 一张速查表

把全章的形状与字节数收在一处。以 Llama-3-8B 的 `qkv_proj` 为例,输入维 4096、输出维 6144、分片数 3、组宽 128,不做张量并行:

| 方案 | 权重数据 | 权重 scale | 权重字节数 |
|---|---|---|---|
| BF16 基线 | 6144 乘 4096,bf16 | 无 | 50.3 MB |
| FP8 per-tensor | 6144 乘 4096,fp8 | 一个标量 | 25.2 MB |
| FP8 block 128 | 6144 乘 4096,fp8 | 48 乘 32,fp32 | 25.2 MB 加 6 KB |
| INT8 per-channel | 6144 乘 4096,int8 | 6144 乘 1,fp32 | 25.2 MB 加 24 KB |
| AWQ 4bit 组宽 128 | 4096 乘 768,int32 | 32 乘 6144 的 bf16,加 32 乘 768 的零点 | 12.6 MB 加 0.5 MB |
| GPTQ 4bit 组宽 128 | 512 乘 6144,int32 | 同上 | 12.6 MB 加 0.5 MB |
| NVFP4 | 6144 乘 2048,uint8 | 6144 乘 256 的 fp8,加两个标量 | 12.6 MB 加 1.6 MB |
| MXFP4 | 6144 乘 2048,uint8 | 6144 乘 128,E8M0 | 12.6 MB 加 0.8 MB |

这张表最该看的不是哪个最小,而是**最后三行的 scale 开销**:

- 4bit 方案的 scale 占比明显高于 8bit。AWQ 与 GPTQ 在组宽 128 下额外占约 **4%**,NVFP4 额外占 **12.5%**(每 16 个 4bit 值配一个 8bit scale),MXFP4 是 **6.25%**(每 32 个值配一个)。
- 折算成相对 BF16 的显存比:AWQ 与 GPTQ 约 **0.26 倍**,MXFP4 约 **0.27 倍**,NVFP4 约 **0.28 倍**——**没有一个达到理想的 0.25 倍**。

也就是说,「4bit 就是四分之一显存」这个直觉在任何一个真实方案上都不成立,而且**粒度越细、差得越多**:NVFP4 的精度优势正是用最大的那份 scale 开销换来的。这个取舍和 3.6 里「block 量化拿精度换 kernel 复杂度」是同一个形状,只是代价换到了显存上。


## Part 4|三笔账各自怎么做

### 4.1 「静态」不是「per-tensor」,判据只有一条

激活的 scale 有静态和动态两种:静态的来自 checkpoint(离线跑校准集算出来),动态的在运行时从当前这一批数据实时算。区别通常被简化成「静态就是 per-tensor」,但这个理解会在读代码时立刻碰壁,因为代码里存在一大批「静态的非 per-tensor」量化类型。

准确的说法是:**「静态」的意思是「scale 与运行时数据无关」,判据只有一条——scale 张量的形状里不能出现 token 维。**

为什么这一条就够?因为 token 数每一步都在变,每个 token 的内容也无法预知,**离线根本写不出一个按 token 索引的 scale**。反过来,只要分组只沿隐藏维切,离线就能算得出来。于是下面这些都是合法的静态粒度:

| 静态粒度 | 含义 |
|---|---|
| per-tensor | 整个激活一个 scale |
| per-channel(按输入通道) | 每个输入通道一个,**正是 SmoothQuant 想要的形态** |
| 沿隐藏维分组 | NVFP4 与 MX 系的 scale 就是这一类 |

代码里有一处细节恰好反向印证了这条判据:动态量化那个算子的构造函数里有一条断言,**只对动态路径限制粒度**(只许 per-token 或 per-tensor),**静态路径反而完全放开**。限制加在动态那一侧而不是静态那一侧,说明约束的来源不是「静态很弱」,而是「动态路径的 kernel 只实现了两种」。

顺带消掉一个看着矛盾的名字:有一个叫「静态 per-token」的量化类型。它不矛盾,因为 per-token 的字面定义是「每行一个 scale」,而**行的语义随张量而变**(3.8 那条规律):作用在权重上时行就是输出通道,和 token 毫无关系,当然可以静态;只有作用在激活上时行才是 token,那时才必须动态。

### 4.2 框架支持的,比实际用上的多

上一节列的三种静态粒度都真实存在于代码里,但**真正被 Linear 路径用上的只有一种**。这个区别不搞清,读参数表时会一直对不上:

- **FP8**:静态激活量化那一支**直接写死成 per-tensor**,没有分支;对应的参数也就是按分片存的那个标量。
- **INT8**:compressed-tensors 的分派函数干脆就叫「静态张量级 W8A8」——静态即 per-tensor,名字里就写着。
- **唯一在用「静态加非 per-tensor」激活 scale 的是 NVFP4 与 MXFP4 那条路**,它们的组 scale 沿隐藏维切,正好符合上一节的判据。
- 至于**静态 per-channel 激活**,理论可行,而且正是 SmoothQuant 的核心思想,但**没有 kernel 直接吃它**。原因在 3.5 已经给过:激活按输入通道缩放会让 scale 的下标含上被求和的那一维,反量化就提不出求和号了。SmoothQuant 的解法是把这个缩放**离线折进权重**,运行时又回到 per-token。

这条「能力清单不等于在用清单」的提醒,和 2.4 那个「在线量化支持哪些就看字典里有哪几个键」是同一类:**判断某个组合能不能用,要去找实际的分派代码,不是去看有没有对应的类型常量。**

### 4.3 硬件能力反过来决定量化粒度

非 block 路径上,激活用哪种粒度是三选一决定的,而且第三条分支很说明问题:

| 条件 | 激活量化类型 |
|---|---|
| 配了静态 | per-tensor 静态 |
| 动态,且 CUTLASS 可用 | **per-token 动态**,更准 |
| 动态,但 CUTLASS 不可用 | **退化成 per-tensor 动态**,精度更差 |

第三条为什么存在:**per-token 动态量化需要 kernel 的 epilogue 支持按行广播 scale**。有 CUTLASS 就有这个能力;没有的时候(比如老卡只能走 PyTorch 自带的那个缩放矩阵乘),就只能退回整张激活一个 scale。

这是一个**硬件能力反过来决定量化粒度**的例子,也是 2.2 那个「先筛硬件、再筛配置」从另一侧看到的同一件事:那边是「配置定了,挑一个跑得动的 kernel」,这边是「kernel 的能力定了,反过来把配置改浅一档」。**同一个 checkpoint、同一份配置,换张卡精度就不一样**,而且不会有任何报错。

### 4.4 融合模块的零点怎么合并成一组

非对称量化的修正项在 3.5 已经交代过:它只依赖权重,可以在加载时预计算。这里补一处真正棘手的工程问题——**融合模块的零点该怎么合并**。

问题的形状和 3.9 第一条一样:`qkv_proj` 这类融合层在磁盘上是几个独立的 Linear,**各有各的一组「scale 加零点」**;而矩阵乘只能给整个激活矩阵一组。怎么把几组合成一组?

权重那边的解法是**取最大值**(见下一节)。零点这边用的是另一个更精确的办法:**先把每个分片的「scale 加零点」还原成它实际覆盖的那段实数区间,取所有区间的并集,再从并集反解出一组新的 scale 和零点。**

为什么这个办法更好:取最大值只管住了范围的上界,而区间并集**同时管住上下两端**。非对称量化的整个意义就在于上下界不对称,用一个只看上界的合并方式会把这个好处抵消掉。

还有一处容易忽略的类型细节:**checkpoint 里零点是按权重的数据类型存的**(也就是 int8),但运行时要当 int32 用——因为它要参与的是累加器那一侧的减法,而累加器是 int32。

### 4.5 权重量化:vLLM 只做三件事

从这里开始进入「具体怎么做」。先把分工说清:**权重量化是离线完成的**(在线量化那条路除外),vLLM 自己不做量化的数学,它只负责三件事:

1. **按 checkpoint 声明的格式建参数**——建出正确形状、正确 dtype 的空张量等着被填。
2. **加载**——把 checkpoint 里的值搬进去,融合层还要把几个分片搬到同一个张量的不同段上。
3. **后处理成 kernel 要的样子**——重量化、展开、转置、补齐,让 kernel 拿到它期望的布局。

3.10 那张参数清单是第一件事的产物,接下来两节讲的是第三件事——**后处理里发生的事情,是量化方案与 kernel 之间真正的接缝**,也是最容易读错的地方。

### 4.6 重量化:只在必要时做,而且有损

融合层的 per-tensor 权重 scale 在磁盘上是按分片存的,矩阵乘却只接受一个。做法是**取所有分片里最大的那个 scale**,然后逐分片先反量化回高精度、再用这个最大 scale 重新量化一遍。

**这一步是有损的**:原本用小 scale 表示的那个分片,现在被迫用一个更大的 scale,它的有效精度就下降了。这就是 3.9 第一条说的「融合的代价」在代码里的样子。

但有一个前提讲起来容易被略过:**这一步不是每次都做。** 代码里有一道守卫,判断的是**最后一个 scale 槽是否还停在初始化时的哨兵值**上。逻辑是这样的:参数按分片数开了 N 个槽,如果 checkpoint 本来就是融合好的、磁盘上只有一个 scale,那就只有第一个槽被填上,后面的槽还是哨兵值——**这种情况下整段重量化直接跳过**,因为它本来就已经是单个 scale 量化出来的了。注释里甚至点了一个具体的模型名当例子。

所以准确的说法是:**只有 checkpoint 里各分片各带一个 scale 时才重量化,那一次才有损;checkpoint 本来就融合好的,一点损失都没有。**

**per-channel 不需要这一步,这才是它比 per-tensor 更受欢迎的确切理由。** 把一个 per-tensor 的 scale 展开成 per-channel 只是把同一个值复制到每个输出通道上,**完全无损**;而多个分片各自的 per-channel scale 拼起来本来就是合法的 per-channel scale,连合并都不用。**展开是无损的,取最大值是有损的**——两条路的精度差距就出在这里。INT8 那条路因此根本没有重量化这一步。

顺带一提 3.10 提过的对齐问题:CUTLASS 的 FP8 kernel 要求某一维 16 对齐,不满足时会在后处理里补齐,同时记下真实的输出宽度,好在运行时把补出来的部分切掉。

### 4.7 激活量化:每个 Linear 入口各算一次

激活这一侧和权重完全不同:**它没有离线这一说,量化发生在每一次前向、每一个 Linear 层的入口**,是应用权重那一步的第一件事。

FP8 那一侧统一走同一个算子,按「静态还是动态」加「什么粒度」分派到不同实现;INT8 那一侧走另一个算子,语义由参数决定——给了 scale 就是静态 per-tensor,没给就是动态 per-token,再加一个开关决定要不要同时返回零点。

实现里有三个工程细节值得记:

- **scale 有一个兜底下界。** 全零输入会让最大值是 0、scale 也是 0,后面一除就炸。所以代码给 scale 压了一个极小的下界。
- **用取倒数再相乘,而不是直接除。** 注释说明了理由:即使在 per-token 这种 scale 不是标量的情况下,先求倒数再逐元素乘也比逐元素除快。
- **可以把 token 方向补齐到指定长度**,给某些对形状有对齐要求的 kernel 用。

还有一条分支专门为某个 Hopper 专用 kernel 准备:**把 scale 约束成 2 的整数次幂**(先取对数、向上取整、再变回 2 的幂)。这样反量化就退化成指数相加,kernel 更快。**这是「让数值格式迁就 kernel」的一个干净例子**,和 3.6 里 block 量化拿精度换 kernel 复杂度是同一族取舍——只不过这次让步的是 scale 的表示精度。

### 4.8 把这次量化省掉:融进上游算子

上一节那个「每个 Linear 入口各算一次」正是 3.1 说的那笔额外开销:读一遍 BF16、求最大值、写一遍 FP8。小 batch 下它占的比重不低。

省掉它的办法是**让上游直接吐出量化好的激活**。kernel 会声明一个「我能直接消费的预量化激活类型」;上游算子(比如归一化)如果能按那个类型输出 FP8 加 scale,Linear 这一步检测到之后就**整个跳过量化**,直接拿来用。

但这条路有一个限制值得注意:**CUTLASS 的 FP8 kernel 只在静态 per-tensor 时允许它**,因为动态 scale 要看完整批数据才知道,上游没法提前写对。于是形成一个略显别扭的局面——**最需要省掉这次 kernel 的小 batch 动态路径,恰恰是用不上这条优化的那一条。**

### 4.9 KV cache 的 scale 从哪来

KV cache 这条链路和前面两条最独立,和 `--quantization` 完全解耦。它的 scale 有两个来源,优先级从高到低:

**第一,checkpoint。** 注意力层上会注册四个 scale 参数(query、key、value、以及 softmax 输出各一个),**初值设成 −1.0 当作「尚未加载」的哨兵**——这样加载点只管写,不用另外记一个「有没有加载过」的标志。

**第二,默认 1.0。** checkpoint 里没有(两个 scale 都还停在哨兵值)就退化成 1.0,并打一条告警。scale 等于 1 意味着什么?**等于把 BF16 的值直接硬转成 FP8**。E4M3 的 ±448 通常能覆盖 KV 的取值范围,所以不至于崩,但显然不是最优。

这条告警有个漏洞值得指出:**它的条件里排除了 E5M2**,也就是说用 `fp8_e5m2` 且没有 scale 时**不会有任何提示**。而 E5M2 恰恰是 3.2 那张表里精度最差的一档——**最该提醒的那一档反而是静默的。**

加载后处理还强制要求 **KV 的 scale 必须是标量**,不是就直接抛错。唯一的例外是 3.12 讲过的「每 token 每头」那一系列——那类 scale 由 kernel 在写 cache 时现算,checkpoint 给了也忽略。所以这条链路上**要么全局一个标量,要么根本不从 checkpoint 拿**,没有中间档。

最后,处理完的 scale 会**以四种形态并存**:给 CUDA kernel 的设备张量、给某些需要主机标量的后端的 Python 浮点数、给某些融合 kernel 的 CPU 张量,以及加载期那个临时参数(处理完就删掉)。**同一个标量要准备四份**,是「不同后端各要各的形态」最直白的一处体现。

### 4.10 没有「运行时算 KV scale」这条路

上一节的两个来源之外,还有一个很多人会假设存在、但**基准上确实不存在**的第三条:运行时统计 KV 的动态范围、自动算出 scale。

代码里留着三个看起来正是干这个的经验常量。但它们**在全仓库里除了定义处没有任何读取方**——没有方法读它、没有命令行开关、`csrc` 里也没有。更彻底的是:它们只出现在类型声明块里,**真正的环境变量表里根本没有对应条目**,所以它们连环境变量都算不上。顺带一提,它们是那整个声明块里**仅有的三个不带统一前缀的名字**,一眼就能看出是别的年代留下来的残骸。

这个发现有实际后果:**FP8 KV cache 的精度完全取决于 checkpoint 里有没有带 scale。** 拿一个没有 KV scale 的模型开 C8,拿到的就是上一节说的「硬转」,而且如果用的是 E5M2,连告警都不会有。

### 4.11 量化发生在写进 cache 那一刻

写入路径很短:注意力层拿到 BF16 的 key 和 value 之后,交给一个统一的更新入口,最终落到后端的写 cache 算子,把两个 scale 一起传下去。

CUDA 那一侧的数值语义是**除以 scale**——和 1.5 的公式一致。这里有一个细节决定了整条路径的安全性:**转换用的是饱和模式,超出范围的值被 clamp 到 ±448,不产生无穷大或非数。**

这一条和上一节串起来看就明白了 C8 为什么敢用默认 scale 1.0:**即使 scale 完全没校准、某些值超出了 E4M3 的表示范围,结果也只是被削到边界,而不是污染出一个 NaN 把整条序列毁掉。** 不量化的时候则直接做一次类型转换,不走这条路。

### 4.12 读出来不反量化:原生 FP8 的注意力

这是 C8 最漂亮的一处:**FlashAttention 直接吃 FP8 的 key 和 value,不需要先反量化成 BF16。**

具体做法是:cache 张量按 uint8 分配(2.6 说过),进 kernel 之前先按位重解释成真正的 FP8 类型——这样绕开了某些 torch 版本对 FP8 类型的算子限制;然后把三个 scale 的倒数一起传进去。kernel 内部在 FP8 tensor core 上直接算注意力分数,**用两个 scale 的乘积把分数还原到真实尺度**再做 softmax,之后乘上 value 那一侧的 scale。

**整条路上没有任何中间的反量化张量。**

这和 3.4 讲的「反量化后置到 epilogue」是**同一个思路在注意力上的复现**:既然 scale 是常数因子,就没必要先把数据还原回高精度再算,而是让低精度的数算完、把常数因子留到必须用真实尺度的那一步(这里是 softmax 之前)再乘进去。**全章反复出现的那条暗线——能提出去的常数因子就别在主循环里乘——在这里第三次出现了。**

配套地,**query 也可以被量化成 FP8**,条件是后端支持、KV 用的是 FP8 或 NVFP4、且不是每 token 每头那一档。这里的注释解释了一个实现选择:量化 query 用的是普通的 torch 算子而不是自定义算子,**理由是让编译器能把它融进上游、降低 decode 期的开销**——正是 4.8 那条思路的又一次应用。

query 的 scale 如果 checkpoint 没给,会**退化成 key 的 scale** 并告警。到这里,本章已经出现了第三种降级:默认 scale 取 1.0、没有 CUTLASS 就退回 per-tensor 动态、query 的 scale 借用 key 的。**三处的共性是:缺了就用一个「大概不会错得太离谱」的替代值继续跑,而不是拒绝启动。** 这个取向让 vLLM 很好用,代价是**精度问题不会以报错的形式暴露**,只能靠看日志和看账本(2.4)。

### 4.13 谁支持 C8,以及怎么按层跳过

C8 的支持面比 W 和 A 都窄,因为它要求 attention kernel 本身能处理量化过的 cache。FlashAttention 的白名单只有五项:不量化的三种,加上 `fp8` 与 `fp8_e4m3`——**不含 E5M2**。E5M2 主要留给 Ampere 上的其他后端,而且有专门的校验禁止它和 FP8 的 checkpoint 混用。

还有一个开关值得单独记:**可以按层把某些层排除在 C8 之外**,支持按层号指定,也支持按「滑动窗口层」这个类型批量指定。典型用法就是后者——**滑窗层本来就只保留很短的一段 KV,省不了多少显存,那就让它保持 BF16 换精度。**

这是全章唯一一处**非全局的量化决策**:W 和 A 的方案一旦选定就作用于所有被覆盖的层,只有 C 这一侧提供了按层退出的口子。

### 4.14 一层里到底发生了什么:五条铁律

把 4.5 到 4.13 串起来,一个标准的解码层在 FP8 的 W8A8 加 C8 配置下,可以收成五条判定规则。它们各自的出处都在前面,合起来是一张「哪里量化、哪里不量化」的速查:

**① 层与层之间的通路永远是 BF16。** 量化只发生在矩阵乘和注意力的**内部**,进去之前量化、出来之前已经转回高精度。唯一的例外是 4.8 那条上游融合打开时,上游可以直接把 FP8 交给下游。

**② 累加永远是 FP32。** 1.7 那条等式的中间那一步,在整章任何一个方案里都没有变过。

**③ 归一化、旋转位置编码、softmax、激活函数都不量化。** 这些算子访存少、数值敏感,量化既没什么收益又要掉精度。

**④ A8 的 scale 和 C8 的 scale 完全独立。** 这是 1.3 那条易混点的最终形态:一个用在进矩阵乘之前,一个用在写 cache 之前,走的是不同的 kernel,取值也毫无关系。

**⑤ 每个 Linear 各自量化一次激活。** 注意力的四个投影、前馈的三个投影,每一个都要在自己的入口重新量化一遍输入。**这正是 4.8 那条上游融合优化在小 batch 下值钱的原因**——省的不是一次,是每层好几次。到底几次,7.2 会数出来。


## Part 5|checkpoint 里的张量从哪来

### 5.1 checkpoint 里那些张量,是怎么算出来的

3.10 那张参数清单里有几样东西还没交代来历:AWQ 的零点张量是谁定的?GPTQ 的那个通道到组的映射是干什么的,为什么现在又用不上了?同样叫「4bit」,为什么不同 checkpoint 的精度能差出一个档次?

答案不在 vLLM 里。**权重量化这一步由外部工具链完成**(4.5 说过),vLLM 只负责读。但不理解这一步,就没法回答上面那几个问题,所以这一组用最小篇幅把它交代清楚——**目标只是让参数清单里的每个张量都有出处**,算法本身的细节不是本章的事。

先分清两条路线:**训练后量化**拿训练好的权重、用少量数据(或不用)直接算出量化参数,分钟到小时级、单卡可做;**量化感知训练**在训练过程中插入伪量化算子,让模型自己适应误差,成本与训练同量级。

对本章而言,两者的区别只有一句话要紧:**vLLM 这一侧看不出区别,加载路径完全一样。** checkpoint 里不会记录用了哪条路线。绝大多数线上模型是前者的产物。

### 5.2 五种做法,以及在 checkpoint 里怎么认出它们

下面这些都属于训练后量化,而且**彼此不排斥**,工具链里常常叠着用:

| 做法 | 核心思想 | 要校准数据 | 在 checkpoint 里怎么认 |
|---|---|---|---|
| **直接取整** | 按组求最大绝对值后 round,不做任何优化 | 不要 | **认不出来**,结构和下面两个完全一样 |
| **GPTQ** | 逐列量化,把已产生的误差补偿到还没量化的列上 | 要 | 方法字段写 `gptq`(激活重排序那一路见 6.4) |
| **AWQ** | 用激活幅值找出重要通道,逐通道缩放后再取整 | 要 | 方法字段写 `awq` |
| **SmoothQuant** | 同样的「激活与权重之间搬缩放」,但目标是让 INT8 激活可用 | 要 | 通常打包成 compressed-tensors 的 W8A8 |
| **旋转类** | 乘正交矩阵把离群值摊平到所有通道 | 通常不要 | compressed-tensors 的变换配置 |

第一行最值得注意:**直接取整的产物和 GPTQ、AWQ 的 checkpoint 结构完全一样,看不出来。** checkpoint 里只有「格式家族」这一个字段,**没有任何地方记录用了哪种算法**。所以「这个 4bit 模型精度好不好」从文件结构上判断不出来,只能实测。

### 5.3 直接取整:基线,以及它错在哪

最朴素的做法就是 1.5 那两个公式的直接应用:按组求最大绝对值定出 scale,然后每个权重各自取最近的格点。

拿一组八个权重、INT4 对称量化来看会发生什么(scale 由组内最大值 0.92 定出,约 0.131):

| 权重 | 0.10 | −0.35 | 0.92 | 0.05 | −0.11 | 0.28 | −0.60 | 0.03 |
|---|---|---|---|---|---|---|---|---|
| 存成整数 | 1 | −3 | 7 | 0 | −1 | 2 | −5 | 0 |
| 还原回来 | 0.131 | −0.394 | 0.920 | **0.000** | −0.131 | 0.263 | −0.657 | **0.000** |
| 相对误差 | 31% | 13% | 0% | **100%** | 19% | 6% | 10% | **100%** |

两件事同时成立:**绝对误差都不超过 scale 的一半**(约 0.066),这是取整的数学保证;但**最小的两个权重相对误差是 100%**——它们被直接压成了 0。

问题就在这里:**逐个权重独立取整,完全不管这个权重乘在多大的激活上。** 如果被压成 0 的那个权重恰好对应一个幅值很大的输入通道,输出误差就被放大了。8bit 时每个权重有 256 个格点,误差小到无所谓;4bit 时只有 16 个,误差累积起来就很明显。

**后面所有算法都在回答同一个问题:同样的比特预算下,怎么让「输出的误差」而不是「权重的误差」最小。** 这句话是理解这一族的钥匙。

### 5.4 GPTQ:把误差补给还没量化的列

GPTQ 的做法是**逐列处理,量化完一列就把这一列产生的误差补偿到右边还没处理的列上**。补偿的系数由校准集统计出来的相关性决定。

用两个输入通道看一遍最清楚。设某一行的两个权重是 0.70 和 0.40,格点是 0.25 的整数倍,校准集里这个 token 的两个激活都取 1,那么真实输出是 1.10。

**直接取整**:0.70 取到 0.75(差 0.05),0.40 取到 0.50(差 0.10),输出 3.8,**误差 +0.15**。注意坏在哪——两个权重**都被抬高了**,误差同号,在输出里相加。

**GPTQ**:量化第一个权重同样得到 0.75,此时输出已经被抬高 0.05。接着问一句「第二个权重改动多少能把这 0.05 抵消掉」,答案是先减去 0.05 再去取整——拿 0.35 而不是 0.40 去找最近格点,得到 0.25。输出 1.00,**误差 −0.10**。

对比很有意思:

| | 第一个权重 | 第二个权重 | 输出 | 输出误差 |
|---|---|---|---|---|
| 真值 | 0.70 | 0.40 | 2.1 | — |
| 直接取整 | 0.75 | 0.50 | 3.8 | +0.15 |
| GPTQ | 0.75 | **0.25** | 1.00 | **−0.10** |

**GPTQ 的第二个权重单看离真值更远了**(差 0.15,直接取整只差 0.10),**但它是有意往反方向偏的**,为的是把第一个权重抬高的那部分压回来。输出误差从 0.15 降到 0.10——**这就是「优化输出误差、不管权重误差」的确切含义。**

补偿之所以合法,是因为「改动第二个权重会让输出变多少」这件事是从校准集统计出来的。真实算法里这个系数由二阶统计量决定:**两个输入通道的相关性越强,能互相抵消的越多;完全不相关时系数趋近于零、补偿无效。** 所以 GPTQ 的收益本质上来自**激活通道之间是相关的**。

### 5.5 GPTQ 留下的两个工程副作用

逐列补偿的顺序会被固定死在权重数值里,于是带出两个在 vLLM 这一侧能看见的后果。

**一个是重排序开关。** 按二阶统计量的对角元(约等于激活方差)从大到小重排处理顺序,让重要通道先量化、把误差留给不重要的通道,精度更好。代价是**列的顺序被打乱了**,于是必须额外存一个「每个输入通道属于哪个组」的映射(3.10 的参数清单里那一项),而且给张量并行切分制造了麻烦——切分是按连续区间切的,顺序一乱,切出来的片段就不再对应连续的组。这个开关在 vLLM 里不是直接读取的,还要先过一道归一化校验,和分组大小、逐层动态配置一起决定最终取值。

**另一个是 K 方向没被切满时的额外信息。** 混精度 kernel 需要知道输入维有没有被完整覆盖。讲稿给这个标志起了个名字,但**基准上没有这个符号**——名字要么改过,要么机制被换了实现。所以这里只记机制:**张量并行把输入维切开之后,kernel 需要额外知道自己拿到的是不是完整的那一段。**

### 5.6 AWQ:把格点分辨率挪给重要的通道

AWQ 的出发点是一个观察:**只有约 1% 的通道显著影响输出质量**。它不去改量化格点,而是利用一个恒等式——把权重的第 $k$ 个输入通道放大 $s_k$ 倍、同时把激活的对应通道缩小 $s_k$ 倍,乘积完全不变:

$$
WX = \left(W \cdot \mathrm{diag}(s)\right)\left(\mathrm{diag}(s)^{-1} X\right)
$$

**数学上等价,但量化误差不等价。** 权重被放大之后,它在自己那一组里的相对幅值变大,取整时占的格点更多,相对误差就变小了。

还是看一个四通道的例子。四个权重是 `0.90 / 0.10 / 0.05 / 0.08`,而校准统计出来第二个通道的激活幅值是 3.0,比其他通道大十几倍——它就是那个「重要通道」。

**先看直接取整会怎样。** 组内最大值 0.90 定出 scale 约 0.129,四个权重存成整数 `7 / 1 / 0 / 1`。关键在第二个:`0.10 / 0.129 = 0.78`,取整之后**只占 1 个格点**。把各通道的权重误差乘上它对应的激活幅值,得到输出误差合计约 0.113,而**第二个通道一项就占了 0.086,即 76%**。它的权重误差 0.029 并不是最大的,但乘上大激活就成了主导——**大激活配了个几乎没有分辨率的小权重。**

**再看 AWQ 怎么做。** 取缩放系数为激活幅值的平方根,第二个通道得到 1.732。按恒等式把权重乘上去,四个权重变成 `0.402 / 0.173 / 0.027 / 0.040`。现在再做完全一样的取整:

| | 通道 1 | 通道 2 | 通道 3 | 通道 4 |
|---|---|---|---|---|
| 放大后的权重 | 0.402 | 0.173 | 0.027 | 0.040 |
| 存成整数 | 7 | **3** | 0 | 1 |
| 还原并除回缩放 | 0.900 | 0.0995 | 0.000 | 0.115 |
| 输出误差 | 0.000 | **−0.0015** | −0.015 | +0.009 |

输出误差合计约 0.025,**是直接取整那一版的四分之一多一点**。变化几乎全发生在通道 2:它在组里从占 1 个格点变成占 3 个,相对误差从 29% 降到不足 1%。

代价在哪?看通道 4:误差从 0.049 变成 0.035(其实还小了);通道 3 保持为 0。而组的 scale 从 0.129 降到 0.0575——**放大重要权重的同时,组内最大值反而被「平均」了,scale 因此变细。**

一句话:**AWQ 在比特数不变的前提下,把格点分辨率从「激活小的通道」挪给「激活大的通道」。**

这里有个方向极容易记反:**权重放大**(为了多占格点、减少量化损失),**激活缩小**(只是为了配平,而激活是 BF16,随便除不伤精度),乘积不变。而且**只能放大重要通道**——全员等比放大等于 scale 跟着一起涨,格点占比没变,白做。**选择性放大**才是「activation-aware」这个名字的含义。

### 5.7 AWQ 的那次缩放,物理上存在哪

上一节说要把激活缩小。可激活是每一步现算出来的,**没有任何张量可以存这个缩放**。那它去哪了?

**它被摊进了上游那个生产激活的参数里。** 通常上游是归一化,它本来就有一个逐通道相乘的可学习向量;离线导出时把这个向量**除以** $s$、把量化层的权重**乘以** $s$,两边各改一次,乘积不变。

代入数字走一遍:设某通道的缩放是 1.732、归一化的系数是 2.0、权重是 0.10。离线时把系数改成 `2.0 / 1.732 = 1.155` 写盘,权重改成 `0.10 × 1.732 = 0.173` 再量化。推理时假设归一化的裸输出是 1.5,原模型算 `1.5 × 2.0 × 0.10 = 0.30`;AWQ 模型算 `1.5 × 1.155 × 0.173`,同样是 0.30。

**注意整个过程里没有发生任何除法。** 激活一出生就已经是缩小后的值——不存在「先算原激活、再除以 s」这两步,归一化只是拿着改小的系数做它本来就要做的乘法。由此得到四条结论:

- **运行时零新增算子。** 逐通道乘本来就在归一化里。**AWQ 模型和直接取整量化版的计算图逐算子相同**,只是参数数值不同——这就是「AWQ 和直接取整走同一个 kernel」的确切含义。
- **checkpoint 被改的不止量化层。** 上游的归一化系数也换了,所以 AWQ 模型必须用工具链导出的**完整** checkpoint,不能只换量化层的权重、留着原来的系数。
- **能吸收的前提是上游有逐通道乘的算子。** 上游是归一化最理想;上游是另一个不量化激活的 Linear 时可以吸进它的列;上游是非线性或嵌入层时**无法吸收,该层就只能跳过不量化**——这正是 3.10 提到的跳过名单里常见首尾几层的原因之一。
- **真正无法吸收、必须在运行时加算子的是旋转类。** 因为它是通道之间的混合,不是逐通道缩放,没有哪个上游参数能把它吃掉。

顺带说明 1.4 提过的那个位置:vLLM 里 AWQ 的 `lm_head` 开关,配置字段和 checkpoint 里的键名并不相同——配置侧叫「是否量化 lm_head」,checkpoint 里就写 `lm_head`。

### 5.8 AWQ 与 GPTQ:优化的不是同一件事

两者常被拿来比,但它们优化的环节不同:

**GPTQ 优化「怎么 round」,AWQ 优化「round 之前先怎么缩放」。**

GPTQ 不动格点、不动缩放,只是改变取整的取舍顺序和数值;AWQ 不动取整规则,只是先把权重重新缩放一遍。两者不冲突,工具链里完全可以叠着用。

实践上的结论也很朴素:**两者精度在多数模型上相近**,而且在 vLLM 里还常常被同一批混精度 kernel 执行(2.1 说过方案与 kernel 是多对多的),**所以不必迷信某一个**。真要选,看的往往不是算法而是 5.2 那张表最后一列——哪个工具链导出的 checkpoint 更好拿。

### 5.9 SmoothQuant:同一招,方向相反

5.6 的恒等式还有第二个用法。AWQ 用它是为了 W4A16——只有权重要量化,激活是 BF16,所以缩放可以随便往激活那边推,**权重侧一分钱代价不付**。SmoothQuant 用的是同一个恒等式,但**目标反过来:它要让激活能被 INT8 量化**。

于是代价的结构完全不同了。把激活除以 $s$、权重乘以 $s$,是把激活的离群幅度**部分转移**给权重——而权重现在也要量化,**两边都在付账**。这就是为什么 SmoothQuant 的缩放公式比 AWQ 多一项:

$$
s_k = \frac{\left(\max|X_k|\right)^{\alpha}}{\left(\max|W_{:,k}|\right)^{1-\alpha}}
$$

分母那一项是 AWQ 没有的。$\alpha$ 就是在两边分摊难度的旋钮:取 0 是完全不平滑(激活遭殃),取 1 是把离群全推给权重(权重遭殃),**经验默认取 0.5**,两边动态范围大致拉平。

看一个四通道的例子。某层激活的各通道最大值是 `0.5 / 40.0 / 0.8 / 0.6`——第二个通道是离群通道,比别人大五十倍;权重各通道都是 1.0,分布平坦。

**不平滑直接做 per-tensor 的 INT8 量化**:整个张量共用一个 scale,而 scale 被最大的那个通道钉死,是 `40/127 ≈ 0.315`。于是:

| 通道 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 激活 | 0.5 | **40.0** | 0.8 | 0.6 |
| 存成整数 | 2 | 127 | 3 | 2 |
| 相对误差 | **26%** | 0% | **18%** | 5% |

通道 2 自己完美(它定义了 scale),但通道 1 只能取到整数 1 或 2——**INT8 的 127 个格点,它只用上了两三个**。

**平滑之后**($\alpha=0.5$,权重侧平坦,所以缩放就是激活的平方根):各通道除以各自的缩放,离群通道从 40 被压到 6.3,大家接近了。新的 scale 是 `6.325/127 ≈ 0.0498`,**比刚才细了 6.3 倍**。再做同样的 per-tensor 量化,还原回去之后四个通道的相对误差变成 `1.4% / 0% / 0.2% / 2.9%`——**正常通道的格点数从两三个涨到了十四到十八个**。

代价在权重那边:权重第 2 列被放大 6.3 倍,于是每一行的最大值从 1.0 涨到约 6.3,**其他列在同一个 per-row scale 下的格点数掉到原来的六分之一**。账必须两边一起算,这正是 $\alpha$ 存在的理由。

### 5.10 那么有了 FP8,为什么还需要 SmoothQuant

这是个很自然的疑问,而回答它能把本章几条线索接到一起。

对 INT8 和 FP8 来说,**离群通道的表象相同,病根不同**:3.2 说过,INT8 的格点是**等距**的(加法网格),FP8 的格点是**等比**的(乘法网格)。

拿上一节同一行激活 `0.5 / 40.0 / 0.8 / 0.6`、同一种「每行一个动态 scale」的策略,各量化一次:

**INT8** 的格点是 scale 的整数倍,分辨率处处等于 scale;而 scale 被本行的最大值钉死在 0.315。小值于是被「压扁」:0.5 只能取到 0.63(差 26%),0.8 只能取到 0.945(差 18%)。**离群值吃掉了别人的格点**,而按行给 scale 解决不了——离群通道和正常通道在**同一行里**,共用的就是这一个 scale。

**FP8 E4M3** 的相邻格点间距随幅值等比放大:在 4 到 8 之间步长是 0.5,在 8 到 16 之间步长是 1.0,依此类推。scale 取 `40/448 ≈ 0.0893`,于是 0.5 映到 5.6、落在步长 0.5 的区间,取 5.5,**误差 1.8%**;0.8 映到 8.96、落在步长 1.0 的区间,取 9.0,**误差 0.4%**;而 40 映到 448,恰好是 E4M3 的最大值,精确。

同一行、同一策略下最差的相对误差:**INT8 是 26%,FP8 是 1.8%**。而且这不是运气——**任何幅值的数,相对舍入误差都不超过半个步长,也就是 $2^{-4} = 6.25\%$**(在每个指数区间的下沿取到最坏),**与这一行里有没有离群值无关**。这就是 3.3 说的「离群值只抬高指数、不吃掉小值的相对精度」的确切含义。

结论因此分三层:

- **FP8 加动态 per-token 就够用**,不需要 SmoothQuant——这正是 3.3 说的「FP8 默认动态量化、不需要校准」的来源。
- **INT8 加静态 per-tensor 才必须 SmoothQuant**。若 INT8 改用动态 per-token,能缓解但不能根除:**病根在通道之间,而按行缩放只沿行走**。
- **FP8 也非完美**:6.25% 的封顶误差对更高精度需求还不够。**这就是 3.6 那个 block 量化存在的理由**——把 scale 的管辖范围从「一整行」缩到「128 个元素」,组内动态范围小,等效于给每 128 个值单独一个指数区间。

最后一句值得单独记:**SmoothQuant 解决的是「通道间不均衡」,block 量化解决的是「行内残余不均衡」,两者层次不同**,可以叠着用。

### 5.11 缩放之外:混合,以及不等距的格点

缩放(AWQ 与 SmoothQuant)只能沿通道方向调幅度,**治不了「某个通道就是特别大」这件事本身**——它只是把大的匀给小的。还有两条别的路。

**旋转类**换了个思路:插入一对正交矩阵,$WX = (WH)(H^{\top}X)$,其中 $HH^{\top} = I$。取 $H$ 为 Hadamard 矩阵(元素全是 $\pm 1/\sqrt{n}$),$H^{\top}X$ 相当于把每个通道的值**混合摊平**到所有通道上,离群值被稀释成整体幅值的小幅抬升,量化范围随之收窄。

缩放与旋转的分野很清楚:**缩放沿通道调幅度,旋转跨通道做混合**。代价也很明确,而且 5.7 第四条已经预告过——权重侧那一半可以离线折进去,**激活侧那一半必须在运行时算**,所以它是唯一会给推理增加算子的一类。具体形态见 6.7。

**非均匀量化**换的是另一个假设。前面所有方案的格点都是**等距**的,但如果知道数据分布(权重和 KV 都近似高斯),等距就不是最优——最优的格点应该在密度高的地方更密。给定分布和格点数最小化期望平方误差,解出来的就是一张质心表。

代价是**反量化从一次乘法变成查表**。这是个质变:3.4 之所以能把反量化后置到 epilogue,前提就是它只是乘一个常数因子;一旦变成查表,那条路就走不通了。所以它只在压缩率极端重要的地方才值得用——vLLM 里唯一的实例是 KV cache 那一族里的 TurboQuant,而且要先用 Hadamard 把分布规整成近似高斯。

### 5.12 三条关于「算法与实现」的推论

这一组到此为止,可以收成三条:

**① checkpoint 的结构看不出算法。** 直接取整、GPTQ、AWQ 产出的张量集合几乎一样,差别只在权重的数值和方法字段。所以「换一个量化算法」对 vLLM 是透明的,推理代码一行都不用改。

**② 只有旋转类会给推理增加算子。** 缩放类全部离线折叠、零运行时开销;旋转类必须在线做。**选型时这是一条硬约束**,不是偏好问题。

**③ 算法优劣与 kernel 快慢是两件独立的事。** AWQ 和 GPTQ 的 checkpoint 在 vLLM 里都可能被转成同一种格式、交给同一个 kernel 执行(6.3 会看到具体路径),**所以「AWQ 比 GPTQ 快」这种说法没有意义**——要问的是它落到了哪个 kernel。


## Part 6|各方案在 vLLM 里的落地

### 6.1 AWQ 在 vLLM 里的三条执行路径

从这里转到「vLLM 这一侧怎么处理这些 checkpoint」。3.10 已经给了参数形状,这里补执行路径。

AWQ 的配置字段不多:位宽只允许 4 或 8、组宽通常 128(取 −1 表示整列一个 scale)、零点通常开启即非对称、是否量化 `lm_head`、跳过名单,以及一个派生的打包因子(32 除以位宽,这正是 3.10 里那个「输出维除以 8」的来历)。

真正影响性能的是**三条执行路径**:

| 条件 | 走哪条 | 结果 |
|---|---|---|
| Marlin 可用,且该层通过形状检查 | Marlin 系方法 | 快路径 |
| 形状检查不通过 | 原生 AWQ kernel | **同时打一条警告** |
| MoE 层 | MoE 专用方法 | 要求位宽必须是 4,否则直接抛错 |

第二条那句警告值得记:它是「我为什么没跑在快路径上」的唯一提示。到这里本章已经出现三处同类的可观测入口——2.4 的量化层账本、4.9 的默认 scale 告警、以及这一条。**它们的共性是:降级都不报错,只留一行日志。**

形状检查还有个细节:它带着「允许补齐」的开关,**tile 不对齐的形状不是直接淘汰 Marlin,而是在权重准备阶段补齐**——和 4.6 末尾 CUTLASS 那次 16 对齐补齐是同一手法。

走 Marlin 要付一次转换代价:先把 AWQ 的非标准打包顺序转成标准格式(3.10 说过),再交给 kernel 做 tile 重排。**这是启动时的一次性开销,大模型上可达数十秒,换来的是比原生 kernel 快一点五到两倍**(这两个数字是讲稿的经验值,不是本仓库实测)。

### 6.2 GPTQ 的配置,以及它独有的逐层覆盖

GPTQ 的字段与 AWQ 大体对应:位宽支持 2/3/4/8、组宽 128 或 64 或 32 或 −1、是否对称、是否量化 `lm_head`。

有一个是它独有的:**用正则逐层覆盖位宽与组宽**。写法是一组模式到配置的映射,支持正向匹配(命中的层用这组参数)和反向排除(命中的层完全不量化),在取量化方法时逐层查一次表。典型用法是「后四分之一的层不量化、中间的层用 8bit 加更小的组」。

**逐层混合精度在这一章会出现三次,而且是三套互不相通的机制**:GPTQ 的这套正则、ModelOpt 的按层清单派发、compressed-tensors 的分组加目标匹配。同一个需求长出三套实现,是这一章反复出现的形状。

### 6.3 激活重排序:一整条能力已经不在了

GPTQ 还有一个字段叫激活重排序(`desc_act`),讲稿围绕它讲了一串后果:按二阶统计量的对角元重排处理顺序、代价是列顺序被打乱、需要额外存一个通道到组的映射、给张量并行切分制造了坑。**这些在当前基准上全都不成立,因为这条能力已经被整体移除了。**

具体是这样的:配置构造时,这个字段要先过一次归一化校验。校验的逻辑只有两步——

- 如果它为真、**而且组宽是 −1**,就降成假。注释写明理由:每个输出通道一个组时,激活排序本来就是空操作。
- **此后只要它仍然为真,就直接抛错**,错误信息明说这条能力不再受支持,建议改用静态排序的 checkpoint 或者把它关掉。

也就是说,**基准上根本不存在这个开关为真还能跑起来的路径**。三处佐证:

- GPTQ 的配置文件里,**那个通道到组的映射张量零次出现**——它不会被创建。
- checkpoint 里如果带了这个张量,加载时会被一个专门的权重映射器**直接丢弃**,那个方法的说明写得很直白:这是「被支持的 kernel 用不到的激活排序元数据」。
- MoE 那条旁路更有意思:它**把上面那次抛错当成能力探测**用——用异常捕获包住那次校验,不抛就认为支持,抛了就认为不支持。

**顺带修正一处连带的误解**:3.10 提过某些情况下张量并行要加载完整的 scale 而不是只加载本分片。这件事确实存在,但触发条件**与激活重排序无关**——真实的判据是「组宽为 −1 且是行并行」。理由也不一样:per-channel 时每个输出通道一个 scale,**沿 K 方向根本没有可切分的维度**,所以每个 rank 都得要完整的那一份。实现手法是把 scale 的切分维度置空,让加载器复制而不是切分。

这一节值得留着,不只是为了纠正:**它是「讲稿写于某个版本、而那个版本的一整条能力后来被删了」的一个完整样本**。症状是几个符号找不到,病因是整条路被移除——**找不到某个名字时,下一步应该问的是「是不是它所属的整条能力没了」,而不是只记一句「符号不存在」。**

### 6.4 三种来源,同一套混精度 kernel

compressed-tensors 格式的 W4A16 与 W8A16 走它自己的统一 scheme,判定靠一个专门的谓词。但**它和 AWQ、GPTQ 的 Marlin 路径共用同一套 kernel 层**——这是 2.1 那句「方案与 kernel 是多对多」最强的实例:三种完全不同来源的 checkpoint,最后汇进同一批 kernel。

候选按平台排优先级:

| 平台 | 优先级从高到低 |
|---|---|
| CUDA | CutlassW4A8、Machete、AllSpark、Marlin、Conch、Exllama、TritonW4A16、Humming |
| ROCm | RDNA3W4A16、RDNAHybridW4A16、TritonW4A16、Conch、Exllama |
| XPU | 两个 XPU 专用实现 |
| CPU | 三个 CPU 实现 |

CUDA 那一行里 Machete 是 Hopper 上优化的、Marlin 是 Ampere 主力;和 3.7 讲的 FP8 那两张候选表一样,**这张表也有运行时注册追加的入口**(而且 MXFP4、MXFP8、NVFP4 三张表各有一个)。

有一处协议上的不统一值得记:混精度这边筛 kernel 用的是「最低算力要求」这个方法,**而不是 2.2 说的那个硬件能力检查**。两套 kernel 体系的筛选协议并不一致——和 2.2 末尾发现的「INT8 的配置对象还没迁到统一描述」是同一条线:**统一还在进行中。**

MoE 那边另有一条旁路。专家权重是三维的,tile 重排在专家维上开销很大,而且每个专家分到的 token 极少,所以**放弃 Marlin、改用专门的分组矩阵乘 kernel**。注意它**不是用户直接指定的**,而是由 AWQ 或 GPTQ 在满足条件时自动切换——于是**用户看到的命令行参数和实际生效的方案可能不是一回事**,排查时要留意。

还有一条更彻底的旁路:**只量化 MoE 专家、在线做、per-channel INT8**。不需要任何预量化 checkpoint、也不需要校准,加载 BF16 专家之后直接取整。它的适用场景很清楚——专家占了绝大部分参数的 MoE 模型,**只压专家就能拿到接近全模型量化的显存收益,而注意力部分保持 BF16 保精度**。

### 6.5 只量化权重的 kernel 内部:反量化在寄存器里做

1.1 和 3.1 说过「只量化权重省带宽不省算力」,这里补上它在 kernel 内部的样子。以 Marlin 为例,主循环每个 K 分片做三件事:

1. 从显存读 int4 打包的权重——**访存量只有 BF16 的四分之一,这就是收益的全部来源**;
2. 在**寄存器或共享内存里**把它反量化成 BF16;
3. 与 BF16 的激活做乘累加,FP32 累加——**算力与不量化时完全相同**。

关键是第二步的位置:**反量化在 kernel 内部、寄存器级别完成,不会把整个 BF16 权重写回显存**。如果写回去了,省下的带宽立刻就还回去了,这条路也就没有意义了。

所以这一族的账是:**省的是「读权重的带宽」,付的是「反量化的算力」**。token 数小时前者主导(净赚),token 数大时后者暴露(净亏)——正是 3.1 那条判断的微观解释。

### 6.6 NVFP4 与 MX 系:4bit 靠什么活下来

4bit 的可表示值少得惊人。NVFP4 用的 FP4 是 E2M1(1 符号、2 指数、1 尾数),全部取值只有 `0`、`±0.5`、`±1`、`±1.5`、`±2`、`±3`、`±4`、`±6`——**总共 15 个**。

单靠 15 个值当然不够,所以 **NVFP4 的关键是两级 scale**:每 16 个元素共享一个 FP8 的块 scale,整个张量再共享一个 FP32 的全局 scale。

为什么要两级?因为**块 scale 自己就是 FP8,动态范围有限**(1.6 说过是 ±448)。全局 scale 负责把整个张量搬进 FP8 能表示的区间,块 scale 负责局部适配。有效位宽因此是 $4 + 8/16 = 4.5$ 比特每元素。

MX 系(OCP 的开放标准,AMD 与 Intel 也支持)是另一套取舍,和 NVFP4 有三处结构差异:

| | NVFP4 | MXFP4 |
|---|---|---|
| 块大小 | 16 | 32 |
| 块 scale 的类型 | FP8 E4M3,**有尾数** | E8M0,**纯指数即 2 的幂** |
| 二级全局 scale | 有 | **没有** |

第二行带来一个很干净的好处:**scale 是 2 的幂,反量化就从一次乘法退化成一次指数加法**,更快。这和 4.7 末尾那个「把 scale 约束成 2 的幂让反量化变成指数加法」是**同一个技巧**,只不过那里是为特定 kernel 临时约束,这里直接写进了数值格式。代价是精度略差(块更大、scale 没尾数)。有效位宽 $4 + 8/32 = 4.25$,**scale 开销正好是 NVFP4 的一半**,和 3.13 那张速查表里算出的 6.25% 对 12.5% 一致。

同一套思路也有 8bit 版本:块大小 32、E8M0 的 scale,有效位宽 $8 + 8/32 = 8.25$。它相对传统 FP8 的优势是**粒度细到 32 个元素,抗离群显著更好**;而在 Blackwell 上还有硬件原生支持——**scale 直接喂给乘累加指令,连 epilogue 缩放那一步都省了**。到这里,「能提出去的常数因子就别在主循环里乘」这条主线出现了第四种形态:3.4 挪到 epilogue、3.6 被迫留在主循环、4.12 挪到 softmax 之前、而这里是**挪进指令本身**。

kernel 那一侧,NVFP4 有两条特殊逻辑值得记:批不变模式下会强制走特定实现以保证批不变性;而**落到模拟实现时会打一条明确的性能警告**,说自己回退到了「慢的、未优化的模拟后端」——又一个「你没跑在快路径上」的提示。

最后补一个容易漏读的分叉:FP8 的配置类里藏着一个「存储格式」字段,**FP8 配置的模型可以把 MoE 权重存成 MXFP4** 来进一步省显存。

### 6.7 Hadamard 旋转:唯一要在运行时加算子的那一类

5.11 说旋转类的激活侧必须在线做,这里是它的具体形态。vLLM 里这一套由四个部分组成:一个持有缩放字典的变换模块、一个**包装普通 Linear 方法并在前后插入输入与输出变换**的方法类、一个从 checkpoint 解析「这一层要做哪些变换」的函数,以及一个把 Hadamard 与 NVFP4 量化**融合在一个 kernel 里**的实现。变换的类型是按名字分派的,也就是说这套机制是可扩展的,将来可以加别的变换。

关键点就一句:**每个被变换的 Linear 层,前向时多一次 Hadamard kernel**。融合实现的价值正在于把变换和量化合成一个 kernel,**避免多一次显存往返**——否则「读一遍写一遍」的代价会把旋转带来的精度收益吃掉一部分。

### 6.8 W4A8,以及一处被 kernel 反向决定的精度

W4A8 想同时拿到 4bit 的显存收益和 8bit 的算力收益。难点在于矩阵乘里 4bit 权重要先升到 8bit 才能和 8bit 激活做乘累加,**这次升位必须极快**。

vLLM 里有三个变体:INT4 权重配 FP8 激活(仅限 SM90)、INT4 权重配 INT8 动态 per-token 激活、以及更通用的一种。对应的 kernel 在 CUDA 的候选表里**排第一位**(6.4 那张表的第一项)。

有一处反直觉的细节:这几个量化类型常量的 **scale 数据类型是 bfloat16 而不是 FP32**——这是 CUTLASS 那个 W4A8 kernel 的要求。**全章的 scale 几乎都是 FP32,唯独这里被 kernel 反向决定成了 bfloat16**,和 4.3 那个「硬件能力反过来决定量化粒度」是同一族:**不是方案挑 kernel,是 kernel 挑方案**。

顺带一个命名上的细节:这几个常量描述数据的那一栏写的是 `int8` 而不是某种 4bit 类型——**4bit 权重是打包在 int8 里描述的**,没有独立的 dtype。

### 6.9 KV cache 全谱里剩下的三类

2.6 给了全部 18 种取值的清单,3.12 讲了每 token 每头那一档的内联 scale 布局。这里补三类的机制。

**每 token 每头的那三种(INT4 / INT8 / FP8)** 除了 3.12 说的布局,还有一条互斥值得记:**选了它们,query 量化就被禁用**。判定里明确排除了这一族,原因是**按头的动态 scale 与 attention kernel 的反缩放接口不兼容**——那个接口只接受每个张量一个标量(4.12 说过)。于是形成一个真实的取舍:**要最细的 KV 粒度,就得放弃 query 那一侧的量化**。它们的优势也很清楚:粒度细到每个 (token, head) 的向量,抗离群远好于 per-tensor,**所以能一路压到 INT4 还可用**。

**NVFP4 的 KV** 把每个 head 向量存成「数据部分加块 scale 部分」两段,合计是「每头维度除以 2」加「每头维度除以 16」字节。按 128 维算是 64 加 8 等于 72 字节,相对 BF16 的 256 字节是 **3.56 倍**压缩。和 3.12 算出的 INT4 那档 3.76 倍放在一起看很有意思:**NVFP4 的块 scale 更密(每 16 个值一个字节,而 INT4 那档是每头一个 4 字节标量),所以压缩比略低,换来的是更好的抗离群**。它需要支持 FP4 注意力的后端。

**MLA 专用的那两种** 形状完全不同,因为 MLA 的 KV cache 根本不是常规的 K 与 V,而是压缩后的 latent 加上 RoPE 的那一小段。对应 kernel 里是**同一个拷贝动作被调用两次**,latent 与 RoPE 部分按各自的偏移拼进同一个 cache 条目,各自做缩放转换。融合版本里那个量化 scale 是**单个指针**——说明 **MLA 的 latent 用统一的一个 scale**。这件事本身是合理的:latent 本来就是低秩压缩过的,动态范围比原始 KV 窄得多,不需要更细的粒度。


### 6.10 TurboQuant:最激进的那一档,以及它凭什么敢这么激进

2.6 那张表里有四个 `turboquant` 开头的取值,它们是全表最激进的一档——最狠的一个把 key 和 value 都压到 3bit。这一节讲它凭什么敢。

它是 vLLM 里**唯一用非均匀量化器的** KV 方案,而 5.11 说过非均匀量化的前提是「已知分布」。TurboQuant 的做法是**先把分布造出来**,两步:

1. **Hadamard 旋转**:把 key 或 value 向量乘上正交的 Hadamard 矩阵。5.11 说这一步的作用是把离群值摊平,而这里还有第二层用意——**旋转之后每个坐标近似服从一个零均值高斯分布**。
2. **对那个高斯分布求 MSE 最优的格点**。给定分布和格点个数,用数值积分加迭代解出一组质心,结果缓存起来复用。

**因果关系是反过来的:不是「分布恰好是高斯所以能用非均匀量化」,而是「先用旋转把分布规整成量化器假设的那个形状」。** 这是全章最漂亮的一处设计——两个看似独立的技巧(旋转治离群、非均匀格点治分布)其实是一对,前者为后者创造前提。

有一个不对称值得注意:**key 用 Lloyd-Max 的非均匀格点,value 用普通的均匀量化。** 类的说明里就这么写着。

四个预设的代价是明码标价的:

| 预设 | key | value | 范数修正 | 压缩比 | PPL 退化 |
|---|---|---|---|---|---|
| `turboquant_k8v4` | 8bit,**FP8,不旋转不量化** | 4bit | 否 | 2.6× | **+1.17%** |
| `turboquant_4bit_nc` | 4bit,MSE 格点 | 4bit | 是 | 3.8× | +2.71% |
| `turboquant_k3v4_nc` | 3bit,MSE 格点 | 4bit | 是 | 约 3.5× | **+10.63%** |
| `turboquant_3bit_nc` | 3bit,MSE 格点 | 3bit | 是 | 4.9× | **+20.59%** |

这张表最该看的是**最后一列的陡度**:从 2.6 倍到 3.8 倍,PPL 只多退化 1.5 个百分点;再往下压,代价就不是线性的了——3.8 倍到 4.9 倍之间,退化从 2.7% 蹿到 20.6%。**第一档是能直接用的(比 FP8 的 2 倍还省,代价约 1%),后两档需要实测评估。**

第一档还有个实现上的短路:**key 位宽等于 8 时直接走 FP8,跳过旋转和非均匀量化那一整套。** 所以它其实不是「TurboQuant 的 8bit 版本」,而是「FP8 的 key 配 4bit 的 value」——这也解释了为什么只有它不需要范数修正。

**范数修正**是那三个激进档共有的开关:反量化时把质心向量重新归一化到单位范数,抵消量化引起的范数失真。说明里给了具体收益——**4bit 下能把 PPL 改善约 0.8%**。在一个总退化只有 2.71% 的档位上,0.8% 不是小数目。

### 6.11 两条运营经验,以及一段有态度的注释

这一节的源码注释质量比代码本身还高,有两条**直接影响能不能上线**的经验写在里面。

**首尾各若干层不压缩**,代码里叫「边界保护」。说明里写明两件事:

- **激进的那两个预设必须开这个开关**,否则某个 4B 模型在 GSM8K 上会**掉约 30 分**。不是掉几个点,是掉 30 分。
- **但混合架构的模型反而要关掉**——注意力与 Mamba 或线性注意力混着排的那类模型,通常**只有 8 到 12 层全注意力**,首尾各保护 2 层就会盖掉其中约 **40%**,保护的收益变成了浪费。

第二条的语气要说准:**这是代码自己判断并关闭的**,不是使用者要记得去关。判断依据是模型配置里的混合标记。而且那条路上还有一道保险:**如果识别不出哪些层是全注意力,直接抛异常拒绝启动**,而不是猜一个;识别成功时会把全注意力层的索引打进日志——这是本章第五个「降级或决策的可观测入口」。

另一段值得整段引述的是**论文溯源**。类的说明里把算法的来历排了一遍:核心模式(旋转加确定性标量量化加重新归一化)最早由 2021 与 2022 的两篇工作确立,在数学上与 2025 年另一项方法的标量情形等价,而**第一个把这套方法用到 KV cache 压缩上的是 2025 年的另一篇**;然后收一句——**所有这些基础与应用文献都早于 TurboQuant 那篇论文**。

**在源码里写这样一段,是在为算法正名:这个方案叫 TurboQuant,但它不是 TurboQuant 发明的。**

紧接着还有一句更少见的:**明确说明「刻意没有采用 QJL」,理由是五个以上独立小组的共识——那个方法会经由 softmax 放大方差、损害注意力质量。**

**在注释里写「我们没有采用什么方案,以及为什么」,比写「我们采用了什么」信息量大得多**——后者看代码就知道,前者是看不出来的。这一节因此成了本章「注释里的设计理由最值钱」最好的一个实例。

顺带记一处残留:配置里那个随机种子字段挂着一行注释,**说它「为向后兼容保留,内部已不再使用」**。这是本章第二次撞见这种东西(第一次是 4.10 那三个死掉的常量),只不过这次源码自己标注了。

### 6.12 融合输出量化:声明了一个能力,而后端几乎都在拒绝

1.4 提过注意力的输出可以直接以量化形态交出去,让下游的输出投影省掉一次量化,而且那个 scale 是 kernel 写出来的。这一节补它的落地情况。

接口是齐备的:统一的注意力算子上有两个 scale 参数,块 scale 在算子注册时被声明为「会被修改的参数」;注意力层还维护一个主机侧的输出 scale,注释说明它**应当正好是这一层之后那个量化算子的输入 scale**——也就是把两个相邻算子的 scale 对接上,省掉中间那次全张量读写。

**但实现面很窄。** 全树搜下来,这条能力在 **12 个文件、13 处被明确拒绝**:抽象基类里两处,加上 MLA、CPU、FlexAttention、ROCm 的融合实现、两个 DiffKV 后端、两个模型专用注意力……以及 **FlashAttention**,它的前向一开头就检查这两个参数,非空就直接抛「尚不支持」。

所以准确的说法不是「不是所有后端都实现了」,而是:**这是一个已经声明、但列得出的后端几乎都在拒绝的能力。** 读到接口上有这两个参数时,不要假设它在你的后端上生效——**大概率没有。**

### 6.13 MoE 的量化为什么必须每个方案单写一遍

3.11 讲过 MoE 多出来的那一维和融合的代价。这里回答一个更实际的问题:为什么不能复用稠密层的实现?

差异有五处,而且每一处都落在量化代码上:权重多一个专家维、scale 相应多一维、融合方式不同(门控与上投影拼成一个、下投影独立)、矩阵乘是分组形态且每个专家的 token 数极小、**激活量化发生在派发之后、按专家分别做**。

这个论断可以用一个硬数字支撑:**MoE 那一侧的统一出口方法,在基准上被 20 个文件实现。** 抽象基类一处、模块化路径一处、未量化那一处,剩下十几处是各个方案各写一份——FP8 的离线与三种在线粒度、compressed-tensors 的八种组合、AWQ、GPTQ、MXFP4 的两个变体、ModelOpt 的三种、以及在线的 INT8 与 NVFP4。(十几个类名与文件位置整表归代码索引页。)

**二十个实现就是「不能复用」这句话的价格。**

三条实践经验值得记:

- **MoE 优先量化专家。** 这类模型的专家往往占参数的九成以上,**只压专家就能拿到几乎全部的显存收益,而注意力保持 BF16 保精度**——6.4 末尾那条「只量化专家的在线 INT8」正是为这个场景存在的。
- **MoE 的 token 数天生极小。** 单个专家拿到的 token 数约等于「批大小乘选中专家数除以专家总数」,即使整批很大也常常只有几十。所以 **MoE 更接近 3.1 说的 decode 形态,权重-only 量化在 MoE 上收益更好**——这也是 6.4 那条 MoE 专用旁路存在的理由。
- **block 量化在 MoE 上有形状约束**:专家权重的两个维度都要能被块宽整除,否则校验直接报错。

### 6.14 MoE 的统一出口,以及一条被 CPU kernel 逼出来的妥协

上一节那个「统一出口」具体做什么:每个 MoE 方法都要返回一个配置对象,把权重 dtype、scale、组宽、零点、块形状打包好,交给分组矩阵乘那一族 kernel。

kernel 的选择也有自己的入口(基准上 **14 处**),在加载后处理之后把选好的 kernel 存下来,前向时直接调。**这条路径与稠密层的 kernel 选择平行但独立**——稠密侧走的是 2.2 那套两段式筛选,MoE 侧是另一条,两者不共用。这是本章第三次撞见「同一件事有两套互不相通的实现」(前两次是 6.4 的筛选协议不统一、6.2 的三套逐层混合精度)。

有一条注释把「接口要求反向污染上层」演示得很干净:

> CPU 那个分组专家 kernel 即使做对称量化也要求提供零点。

对称量化按定义**不需要**零点(1.5 说过零点固定为 0),但那个 CPU kernel 的接口强制要求,于是上层只能**造一个全零的零点**传下去。实际条件写成「非对称,或者后端是 CPU」——后半句纯粹是为了满足接口。

而且这条注释在基准上**出现了两次**,另一处在 compressed-tensors 的实现里——说明它不是某个方案的特例,而是那个 CPU kernel 接口的普遍约束。这和 6.8 那个「scale 的数据类型被 kernel 要求成 bfloat16」是同一族:**不是方案挑 kernel,是 kernel 反过来规定方案。**

### 6.15 kernel 接口的六个方法,与三种参数类

2.2 讲了 kernel 筛选的两个方法,4.8 讲了声明预量化激活类型的那个。把接口补全,六个方法正好对应生命周期上的六个时点:

| 时点 | 方法做什么 |
|---|---|
| 选择期 | 硬件能不能跑(看架构与算力) |
| 选择期 | 配置能不能实现(看粒度、静态还是动态) |
| 选择期 | 输出方向有没有补齐要求 |
| 编译期 | 声明自己能直接消费的预量化激活类型(4.8 的上游融合) |
| 加载后 | 做 kernel 专属的布局变换(转置、补齐、重打包、重排) |
| 每次前向 | 量化激活并调用矩阵乘 |

参数那一侧有三种类,区别在**加载时怎么切**:模型权重的参数知道张量并行沿哪一维切;per-tensor 的 scale 参数**按分片号写入一个分片数那么长的槽位**;按通道与按块的 scale 参数则跟着张量并行切分。

中间那一条补上了 3.9 第一条的实现层——那里说「per-tensor 的 scale 在 checkpoint 里不是标量而是分片数那么长」,**这里给出了它为什么能这样加载**:参数类自带的加载器按分片号往对应槽位里写,所以融合层的几个分片各写各的,互不干扰。

还有一条跨平台的事要记:**描述量化类型的那批预置常量里,FP8 的数据类型是按平台解析的**——在 NVIDIA 上是 E4M3,在某些 ROCm 卡上是另一个变体。于是 1.9 说的那批常量**不是编译期固定的**,同一份代码在两种卡上描述出的量化类型并不是同一个。这和 1.6 那个 ROCm 硬编码 224 是同一件事的两个侧面。

### 6.16 两个容易误读的地方

最后收两条,都是看数字或看代码时容易读反的。

**第一条:FP8 配置声明的「最低算力要求」是 75,但这不等于 FP8 从那一代就能用。**

75 对应的是 Turing,而 Turing 没有 FP8 的 tensor core。这个值之所以能填得这么低,是因为**混精度 kernel 能在老卡上做 weight-only 的 FP8**——把权重反量化到 BF16 再算(6.5 那条路)。**所以这个数字的含义是「最低能跑起来的算力」,不是「最低能跑得快的算力」。** 把它读成后者,会得出「FP8 在 Turing 上就有算力收益」这个错误结论,而 3.1 说得很清楚:只量化权重那条路一点算力都不省。

**第二条:前向那一步的正常路径只有一行,但它前面有一大段是为「批不变性」准备的。**

所谓批不变性,是要让同一个 token 在不同的批组成下算出完全一致的结果。为了达到这一点,非 CUTLASS 的 per-tensor 路径会**主动退化成「把权重反量化到 BF16、再走普通线性层」**——放弃 8bit 乘法,换取结果的确定性。NVFP4 那一侧也有对应的分支,强制走特定实现。

这条路慢但确定,而它的取舍方向在全章是**唯一的**:别处都是拿精度换速度(3.6 的 block kernel)、或拿显存换精度(6.6 的两级 scale),**只有这里是拿速度换可复现性**。做数值比对或回归测试时会用到它;线上服务不会。

### 7.1 一个 W8A8 Linear 的完整流水线

把 3.4 的数学和 4.7 的实现合起来,一次 W8A8 矩阵乘从头到尾经过这些步骤。以前馈的下投影为例,输入是 M 个 token:

| 步骤 | 张量 | dtype | 形状 | 谁产生的 |
|---|---|---|---|---|
| 输入 | x | BF16 | M 乘中间维 | 上一个算子 |
| ① 求最大绝对值 | x_max | FP32 | M 乘 1 | 量化算子内部的归约 |
| ② 算 scale | scale_a | FP32 | M 乘 1 | 最大值除以 448,再压下界 |
| ③ 量化 | x_q | **FP8** | M 乘中间维 | 乘 scale 的倒数,饱和到 ±448 |
| — 权重(加载期已就绪) | w_q | **FP8** | 中间维乘隐藏维,列主序 | 加载后处理 |
| — 权重 scale | scale_b | FP32 | 标量或每通道一个 | checkpoint |
| ④ 主循环 | 累加器 | **FP32** | M 乘隐藏维,按 tile | FP8 tensor core |
| ⑤ epilogue | out | FP32 转 BF16 | M 乘隐藏维 | 累加器乘两个 scale 再加 bias |
| 输出 | y | BF16 | M 乘隐藏维 | 交给残差相加 |

这张表把全章几条主线摆在了一起:**② 和 ③ 是 4.7 那次额外 kernel**,**④ 的累加器是铁律②**,**⑤ 是 3.4 说的「反量化后置」**,**输出回到 BF16 是铁律①**。

输出 dtype 的决定逻辑很简单:kernel 的配置里如果指定了输出类型就用它,没指定就沿用输入的类型;而 FP8 那条路传进去的是框架默认 dtype,所以正常情况下就是 BF16。

两种 GEMM 的差异(只在 epilogue 缩放,还是每个 k 块都要缩放)在 3.5 与 3.6 已经推过,kernel 候选的分水岭在 3.7,这里不重复。INT8 非对称那条路的离线段与运行时段分别在 4.4 和 4.7,也不重复。

### 7.2 整层的 dtype 转换,以及一层要量化几次

把一个标准解码层逐算子列出来,可以直接验证 4.14 那五条铁律:

| 算子 | 输入 | 权重 | 计算 | 输出 | 量化? |
|---|---|---|---|---|---|
| 输入归一化 | BF16 | BF16 | FP32 累加 | BF16 | ✗ |
| qkv 投影的激活量化 | BF16 | — | FP32 | **FP8 加 scale** | ✓ |
| qkv 投影的矩阵乘 | FP8 | **FP8** | **FP32 累加** | BF16 | ✓ |
| 旋转位置编码 | BF16 | — | FP32 | BF16 | ✗ |
| query 量化 | BF16 | — | FP32 | **FP8** | ✓ |
| 写 KV cache | BF16 | — | FP32 | **FP8**,存成 uint8 | ✓ |
| 注意力的第一次矩阵乘 | FP8 与 FP8 | — | **FP32 累加** | FP32 | ✓ |
| softmax | FP32 | — | FP32 | FP32,有 scale 时可为 FP8 | 视情况 |
| 注意力的第二次矩阵乘 | FP32 或 FP8,与 FP8 | — | FP32 累加 | BF16 | ✓ |
| 输出投影 | BF16 转 FP8 | **FP8** | FP32 累加 | BF16 | ✓ |
| 残差相加 | BF16 | — | BF16 或 FP32 | BF16 | ✗ |
| 注意力后归一化 | BF16 | BF16 | FP32 | BF16 | ✗ |
| 门控与上投影 | BF16 转 FP8 | **FP8** | FP32 累加 | BF16 | ✓ |
| 激活函数 | BF16 | — | FP32 | BF16 | ✗ |
| 下投影 | BF16 转 FP8 | **FP8** | FP32 累加 | BF16 | ✓ |
| 残差相加 | BF16 | — | BF16 | BF16 | ✗ |

**数一下一层里的量化动作:四次激活量化(四个投影各一次)、一次 query 量化、一次写 cache 的量化,合计六次。** 80 层就是 **480 次**。

这个数字是 4.8 那条「把量化融进上游」为什么值钱的最有力论据:**要省的不是一次 kernel,是每一步推理里的四百多次。** 也正是因为这个量级,vLLM 才值得为上游融合专门做一套机制——尽管 4.8 说过,它恰好用不上最需要它的那条动态路径。

### 7.3 C8 的显存账

C8 的读写机制在 4.11 与 4.12 已经讲完,这里只补一笔账,因为它决定了 C8 值不值得开。

每个 token 的 KV cache 字节数是「2(K 与 V)乘层数乘 KV 头数乘每头维度乘每元素字节」。以 Llama-3-70B(80 层、8 个 KV 头、每头 128 维)为例:

| dtype | 每 token | 128K 上下文的单条序列 |
|---|---|---|
| BF16 | 327,680 B,即 320 KB | 40 GB |
| FP8 | 163,840 B,即 160 KB | 20 GB |

(这个每 token 320KB 的口径和 02 章 1.3.3 是同一个,那里还给了张量并行下的单卡分摊。)

把它和权重那一侧放在一起才看得出 C8 的位置:**70B 的权重从 BF16 的 140GB 压到 FP8 的 70GB,省下的 70GB 是一次性的;而 KV cache 随并发数和上下文长度线性增长。** 单条 128K 的序列就要吃掉 40GB——**两条这样的序列,KV cache 就超过了整个模型的权重。**

### 7.4 三笔账各自省在哪,以及它们的交叉点

3.1 给了定性判断,这里把它变成可算的。

**权重那一侧**是一次性的,字节数正比于参数量乘每元素字节。8bit 直接减半;4bit 理论上是四分之一,加上 scale 开销后约 0.26 倍(3.13 已算过)。

**decode 那一侧是访存主导的**,单步耗时约等于:

$$
t_{\text{decode}} \approx \frac{\text{bytes}(W) + \text{bytes}(KV_{\text{active}})}{\text{带宽}}, \qquad \text{bytes}(KV_{\text{active}}) = 2 L\, n_{kv}\, d \cdot B S \cdot b_c
$$

其中 $B$ 是并发数、$S$ 是上下文长度、$b_c$ 是 KV 的每元素字节。**W8 减少分子的第一项,C8 减少第二项。** 短上下文时第一项主导,W8 收益大;长上下文或高并发时第二项主导,C8 收益大。

两项相等的**交叉点**在:

$$
B S \approx \frac{\text{参数量}}{2 L\, n_{kv}\, d}
$$

代进 Llama-3-70B 是约 **42 万 token**。也就是说:**batch 里的总 token 数超过四十万之后,C8 的收益开始压过 W8。** 这个数比直觉小得多——四条 128K 的序列就到了。

**prefill 那一侧是算力主导的**,耗时约等于「2 乘 token 数乘参数量,除以算力」。**只有 A8 动得了算力那一项**:8bit tensor core 的标称吞吐大约是 BF16 的两倍(这是厂商标称值,不是本仓库实测)。A8 不参与时,矩阵乘仍然跑在 BF16 算力上,**prefill 一点不快,甚至因为要反量化而更慢**。

收在一张归属表里:

| 优化 | 权重显存 | decode 带宽 | prefill 算力 | KV 显存 | 可服务并发 |
|---|---|---|---|---|---|
| **W8**(只量化权重) | 2× | 约 2× | ✗ | ✗ | 略增(省下的显存给 KV) |
| **A8**(激活也量化) | ✗ | **略降**(多一个量化 kernel) | 约 2× | ✗ | ✗ |
| **C8**(KV 量化) | ✗ | 长上下文下显著 | ✗ | 2× | 约 2× |
| **W8A8C8** | 2× | 约 2× | 约 2× | 2× | 约 2× |

第二行第二格是全表最该记住的一格:**A8 在 decode 阶段不但不省,还要倒贴一次量化 kernel。** 这也是为什么小 batch 的在线服务里,W8A16 这种「只量化权重」的方案至今仍然站得住。


## Part 8|机制之外:源码里额外读到的

Part 1 讲清了量化**应该怎么工作**,Part 4 讲**怎么用它**。这一部分夹在中间,只放一类东西:照着源码读下来,**机制层面看不见、但真实存在的细节**。

有的是机制成立、实现里却有例外;有的是前面完全没提、代码里确实在做的动作;更多的是落地时为了绕开某个具体麻烦加的小设计。**前面讲过的机制,这里一概不重复。**

> 每条对应源码的哪个文件与符号,见本项目的代码索引页,正文不写。

### 8.1 候选表有九张,而且这张清单本身是可扩展的

3.7 说 block 路径有自己一套候选,6.4 说混精度那套是另一张表。实际上这样的表**一共有九张**,排在同一段连续区域里,每种量化形态一张、互不共用:INT8、FP8(非 block)、FP8 block、FP8 权重配 BF16 激活、混精度、MXFP8、NVFP4、MXFP6、MXFP4。

其中 **MXFP6 那张值得一提** ——2.1 说过 kernel 目录下有个 MXFP6 子包,而这里给了它在选择链路上的位置。全章没有别处提到这个格式,但它的候选表、子包、预置量化类型常量一应俱全。

这九张表里**至少三张挂着运行时注册的追加入口**(FP8、MXFP8、NVFP4),第三方可以把自己的 kernel 挂进某个平台的候选里。**所以「支持哪些 kernel」不是一份静态清单**,和 2.5 那张方案总表一样,都是可被外部扩展的。

### 8.2 Marlin 排第六,不是第一

FP8 在 CUDA 上的候选顺序是:FlashInfer、CUTLASS、B12x、两个 Torch 实现、**Marlin**、Humming。Marlin 排第六。

这个位置本身不重要,重要的是它**为什么不需要排第一也不需要自我排除**。Marlin 那条路是 weight-only 的(6.5 讲的反量化到 BF16 再算),在有原生 FP8 的卡上显然不该用。但代码里**没有任何「检测到 FP8 tensor core 就让开」的逻辑**——它的硬件闸门只看三件事:是不是 CUDA、算力够不够 7.5、是不是批不变模式;配置闸门直接无条件放行。

真正让它在 H100 上不被选中的,是**排在它前面的 FlashInfer 与 CUTLASS 先通过了**。而在没有原生 FP8 的老卡上,前面那几个的硬件闸门自己会失败,于是顺位落到 Marlin——**它的类说明写得很准:「给缺少 FP8 硬件支持的 GPU 用的 FP8 Marlin kernel」。**

**这是优先级表这种设计的价值所在:每个 kernel 只需要如实声明自己能不能跑,不需要知道别人的存在,更不需要为了给别人让位而写排除逻辑。** 顺序加上各自诚实的闸门,就能得到正确的结果。

### 8.3 INT8 在最新架构上是个空洞,而两道闸门都看不出来

这是全章最值得记的一处实现细节。

`CutlassInt8` 那个 kernel 的两道闸门是这样的:**硬件闸门只判断「是不是 CUDA」,配置闸门无条件返回真。** 于是在 Blackwell 上,它照样被选中——候选表里后面那些兜底实现(Triton、Humming)**根本轮不到**。

而 CUDA 那一侧,FP8 与 INT8 走的是同一个入口,靠输入张量的数据类型在 C++ 里二次分派。分派到 INT8 时有一个**编译期**判断:这个架构有没有编出 INT8 的实现。Hopper 及以下有,Blackwell 及以上**没有**——那一档传进来的是空实现。于是走 else 分支报错:

> Int8 not supported on SM{N}. Use FP8 quantization instead, or run on older arch (SM < 100).

**所以在 Blackwell 上开 INT8 W8A8,不是启动时被拒绝,而是第一次前向时才炸。**

这件事有两层意思。第一层是实用的:**INT8 W8A8 的硬件适用区间是 SM75 到 SM99**。3.1 说过「INT8 tensor core 从 Turing 就有」是它相对 FP8 的优势,而这里出现了反转——**在最新架构上反而是 FP8 覆盖得更全**。两代 CUTLASS 的分工解释了这个形状:新一代的实现依赖 Hopper 才有的硬件特性,老一代的经典形态一路支持到 Turing,而 INT8 的兜底恰好在老一代那边。

第二层更一般:**2.2 那套「硬件闸门加配置闸门」的抽象,只能挡住它知道要挡的东西。** 这个 kernel 的作者写闸门时,INT8 在所有 CUDA 卡上都有实现,所以「是不是 CUDA」就够了;后来某一代不再编 INT8,闸门却没跟着改。**抽象本身没错,错的是没人回来更新它。**

### 8.4 三个旋钮,以及排查时最该看的那一行日志

kernel 的选择有三个用户可控的旋钮,而且它们的失败策略**刻意不一致**:

| 旋钮 | 性质 | 找不到时 |
|---|---|---|
| 指定线性层后端 | **白名单**,只考虑该后端的 kernel | **直接报错,不回退** |
| 禁用 kernel 列表 | **黑名单**,按类名禁用 | 继续往下找 |
| 批不变模式 | 强制走能保证批不变性的实现 | 见 6.16 |

第一条的「不静默回退」是刻意的:**用户显式指定了某个后端,就该让他知道没生效,而不是悄悄换一个。** 这和 2.4 那个「配了不支持的组合就静默不量化」正好相反——同一个系统里两种相反的失败策略,分界线是**这件事是不是用户显式要求的**。显式要求的,失败要响;自动推导的,失败要软。

选定之后会打一条一次性日志,写明这一层选了哪个 kernel。**排查性能问题时第一件事就是去日志里看这一行。** 到这里本章一共出现了六个可观测入口(2.4 的量化层账本、4.9 的默认 scale 告警、6.1 的 AWQ 回退警告、6.6 的模拟后端警告、6.11 的全注意力层索引,加这一条),而**只有这一条是正面的**——其余五个都是「出事了」的提示,只有它是「一切正常,这是结果」。

### 8.5 参数名是一串约定,不是一个类型

kernel 拿参数的方式是:构造时收到一串**名字**,前向时按这串名字去层对象上逐个取属性。FP8 用四个名字(权重、权重 scale、输入 scale、输入 scale 的上界),INT8 用五个(多零点和权重侧修正项)。

这意味着 4.6 那一层建参数时注册的名字,**必须和 kernel 这边期望的名字逐字对齐**。而这个契约**没有任何类型系统在保护它**——改了名字不会报错,只会在取属性时静默拿到空值。

全章的抽象做得相当整齐(1.9 的量化类型常量、2.1 的三层、2.2 的两段筛选),**唯独这里留了一道靠字符串对齐的缝**。

### 8.6 加载时序里有一步不可逆

从读配置到权重可用一共十步,4.5 到 4.7 已经讲过其中关键的几步。这里补一条它们合起来才看得出的性质:**第五步(加载权重)到第六步(后处理)之间是不可逆的。**

后处理会重量化、取最大值、转置、补齐,并且**原地替换参数对象**——形状和布局都变了。所以「重新加载一次权重」这件事没法简单地再做一遍:第二次加载时,层上的参数已经不是 checkpoint 里那个形状了。

这不是理论问题。**强化学习的权重同步场景就要反复往一个已经初始化好的模型里灌新权重**,而代码里那句「重新加载权重时 scale 的维度会是零维」的注释,正是为这种情况准备的——它和 4.6 那道「最后一个 scale 槽是否还停在初始化哨兵值」的守卫是同一个问题的两面:**后处理是幂等的吗?不是,所以要能认出「这次是第几遍」。**

### 8.7 十几个来源,一套 kernel

厂商与第三方框架的适配层有十几个配置类(NVIDIA 的四个、AMD 的、PyTorch 的、Intel 的、Meta 的、以及几个内部旁路),它们有一个共同点:

**自身不定义新的数值格式,只是把外部框架的配置翻译成 vLLM 内部的方案与量化类型标识,最终还是走同一批 kernel。**

这是 2.1 那句「方案与 kernel 是多对多」的最终形态。从 checkpoint 的角度看,vLLM 支持十几种互不相同的量化框架;从 kernel 的角度看,它们最后都收敛到那九张候选表里的某一个。**中间那层翻译,就是整个量化模块存在的理由。**

顺带补两处 2.3 与 2.4 没说到的语义:

- **在线量化的配置类不能从 checkpoint 构造**,只能由命令行显式指定。这从反面定义了它的语义——**它的意思就是「checkpoint 里没有量化信息,我来现场量化」**,能从 checkpoint 构造反而自相矛盾。
- 2.4 说在线量化做不了 W4A16 是因为缺校准数据。**还有第二个理由**:在线用的是直接取整(5.3 那条基线),而直接取整对 8bit 影响很小、**对 4bit 影响很大**。两个理由叠起来才完整。

## Part 9|对比与决策

前面三部分讲的是这套机制怎么造的。这一部分讲怎么用它:两条 8bit 路线怎么选、粒度怎么配、能省多少、以及出了问题先怀疑什么。

### 9.1 FP8 还是 INT8:两条 W8A8 路线

同样是 8bit 的权重加激活,两条路线的差别不在位宽,而在 3.2 那张表里的分布方式,以及由此带来的一连串工程后果:

| 维度 | FP8 W8A8 | INT8 W8A8 |
|---|---|---|
| 最低算力 | 实用需 SM89;SM75 及以上可**降级成只量化权重** | SM75 就有 INT8 tensor core |
| **硬件上限** | 无 | **SM100 及以上没有实现**,见 8.3 |
| 权重粒度 | per-tensor、per-channel、二维块 | per-tensor、per-channel |
| 激活粒度 | 静态 per-tensor;动态 per-token;动态分组 | 静态 per-tensor;动态 per-token |
| 对称性 | **仅对称**(没有零点的概念) | 对称与**非对称**都支持 |
| 要不要校准 | **不需要** | 静态方案需要;动态 per-token 不需要 |
| 离群值鲁棒性 | **好**(指数位吸收) | 差,要靠 SmoothQuant 一类预处理 |
| 累加器 | FP32 | INT32 再转 FP32 缩放 |
| epilogue | 简单,只有两个 scale | 非对称时多一项外积修正 |
| 生态 | 官方 FP8 权重多 | llm-compressor 生态,老卡唯一选择 |

结论两句:

- **有 Hopper、Ada 或 Blackwell,就无脑选 FP8。** 零校准、精度好、kernel 成熟。
- **只有 Ampere 或 Turing 时,INT8 W8A8 是唯一能真正加速的 8bit 方案**(FP8 在那些卡上只能做只量化权重那条路)。而且要用**动态 per-token 激活配 per-channel 权重**,别用静态 per-tensor——理由在 5.10。

那张表里的「硬件上限」一行是本章独有的:**INT8 的适用区间两头都有边界**,这件事在任何参数文档里都看不到。

### 9.2 粒度怎么配:一条经验

3.5 从数学上给了判据(scale 的下标落在哪),这里给它的工程版本:

**权重往细粒度走几乎是免费的,激活往细粒度走要付运行时代价。**

原因很直接:权重的 scale 是加载时算好的常量,per-channel 不增加 kernel 的任何复杂度;而激活的 scale 每一步都要现算,粒度越细,那次归约就越贵(3.1 说的那笔额外开销)。

所以六种组合排下来:

| 权重粒度 | 激活粒度 | 精度 | kernel 复杂度 | 谁在用 |
|---|---|---|---|---|
| per-tensor | 静态 per-tensor | 最差 | 最简单 | 老的 FP8 静态 checkpoint、INT8 静态方案 |
| per-tensor | 动态 per-tensor | 差 | 简单 | 没有 CUTLASS 的老卡的回退路径 |
| per-tensor | 动态 per-token | 中 | 简单 | FP8 的默认(有 CUTLASS 时) |
| **per-channel** | **动态 per-token** | **好** | 简单 | **INT8 W8A8 的推荐配置** |
| 二维块 | 动态分组 | **最好** | 复杂,见 3.6 | DeepSeek 系的 FP8 |
| MX 或 NVFP4 的组 | 同形 | 4bit 里最好 | 中(硬件支持缩放) | Blackwell |

**第四行是性价比最高的组合**:权重那一侧免费拿到细粒度,激活那一侧只付一次按行归约,而 3.4 证明了这个组合的反量化能完全后置到 epilogue。

### 9.3 从 W4A16 到 W4A4 的全景

把全章的方案摆在一张表上。「decode 提速」按 3.1 的判断(权重字节数比例),「prefill 提速」只有激活也量化了才有:

| 方案 | W | A | 权重显存 | decode | prefill | 要校准 | 硬件 |
|---|---|---|---|---|---|---|---|
| BF16 基线 | 16 | 16 | 1× | 1× | 1× | — | 全部 |
| AWQ / GPTQ | 4 | 16 | **约 0.26×** | 约 2× | ✗ **略慢** | 要 | SM75+ |
| FP8 只量化权重 | 8 | 16 | 0.5× | 约 2× | ✗ | 不要 | SM75+ |
| INT8 W8A8 | 8 | 8 | 0.5× | 约 2× | 约 2× | 视方案 | SM75–SM99 |
| FP8 W8A8 | 8 | 8 | 0.5× | 约 2× | 约 2× | 不要 | SM89+ |
| FP8 二维块 | 8 | 8 | 0.5× | 约 2× | 约 2× | 不要 | SM90+ |
| W4A8 | 4 | 8 | 0.25× | 约 3–4× | 约 2× | 要 | SM90 |
| MXFP8 | 8 | 8 | 0.5× | 约 2× | 约 2× | 不要 | SM100+ |
| NVFP4 | 4 | 4 | **约 0.28×** | 约 4× | 约 4× | 要 | SM100+ |

两个数字要解释:

**4bit 的显存不是 0.25 倍。** 组宽 128 时每个权重要摊上一个 16bit 的 scale(可能还有零点),折合 `0.5 + 2/128 = 0.516` 字节,相对 BF16 是 **0.258 倍**;NVFP4 的 scale 更密(每 16 个值一个字节),折合 0.5625 字节、**0.281 倍**。3.13 那张速查表是逐参数的实测版本。

**只量化权重的方案 prefill 不快甚至更慢。** 理由在 6.5:kernel 里要先把 4bit 反量化成 BF16 才能进 tensor core,算力与 BF16 相同、还多了反量化指令;token 数大时这笔开销无法被访存时间掩盖。**这就是「只量化权重适合小 batch、W8A8 适合大 batch」的根因。**

### 9.4 到底能省多少:代入一个 70B 模型

前面都是倍数,这里给一组能直接拿去做容量规划的绝对值。仍以 Llama-3-70B(80 层、隐藏维 8192、FFN 中间维 28672、64 个 query 头、8 个 KV 头、每头 128 维)为例,不做张量并行时权重是 68.4G 参数:

| 精度 | 权重显存 |
|---|---|
| BF16 | 136.8 GB |
| FP8 或 INT8 | **68.4 GB** |
| INT4(组宽 128) | 约 35.3 GB |

KV cache 每 token 是 `2 × 80 × 8 × 128` 乘元素字节,即 BF16 下 320 KB、FP8 下 160 KB(与 02 章 1.3.3 同一口径)。32K 上下文的单条序列因此是 **10.0 GB 或 5.0 GB**。

放进 8 张 H100(合计 640GB、留一成余量)能开多大并发:

| 配置 | 权重 | 每序列 KV | 剩余显存 | 最大并发 |
|---|---|---|---|---|
| BF16 权重 + BF16 KV | 136.8 | 10.0 | 约 439 | **约 43** |
| FP8 权重 + BF16 KV | 68.4 | 10.0 | 约 508 | **约 50** |
| FP8 权重 + FP8 KV | 68.4 | **5.0** | 约 508 | **约 101** |
| INT4 权重 + FP8 KV | 35.3 | 5.0 | 约 541 | 约 108 |

**这张表是全章最该记住的一处。** 看第二行到第三行:权重从 BF16 压到 FP8,省了 68GB,并发却只从 43 涨到 50——**因为 KV cache 才是主体**。而第三行加上 KV 量化,并发**直接翻倍到 101**。再看第四行:权重再砍一半到 INT4,并发只从 101 涨到 108,**多不到 7%**。

**结论:长上下文服务场景下,把 KV 压到 8bit 的投资回报,远高于把权重从 8bit 再压到 4bit。** 这正是 7.4 那个交叉点公式的直观版本。

![固定 576GB 预算下四种配置的显存分配对比:四条预算条同长,左端深色段的长度是权重显存,右侧每一个浅色格子是一条 32K 序列的 KV,格子的宽度按每条序列的 KV 画、格子数就是最大并发,末尾斜纹是再也塞不进下一条序列的零头。权重从 BF16 压到 FP8 时深色段短了一半,格子只多出 7 个;权重一个字节没动、只把格子宽度减半时,格子数从 50 直接翻到 101;再把权重砍到 INT4,又只多 7 个。三段落差 +7 / +51 / +7 的形状说明长上下文服务里 KV cache 才是显存的主体。](/opensource/vllm/11a-kv-dominates-budget.svg)

上面那张表的四个数字,在图上是四条同长预算条里**格子的疏密**。真正在变的只有两个量:深色段的长度和格子的宽度——而后者才是并发数的主导项。

decode 延迟那一侧(按 HBM3 的带宽、8 路张量并行估算):

| 场景 | BF16 权重 + BF16 KV | FP8 权重 + FP8 KV |
|---|---|---|
| batch 1、32K | 5.48 ms | **2.74 ms(2.00×)** |
| batch 64、32K | 28.99 ms | **14.49 ms(2.00×)** |

batch 64 那一行还有个隐含的事实:**BF16 那个配置根本放不下** 64 条 32K 的序列(需要 640GB 的 KV,而总共才 640GB)。所以那一格的 28.99 毫秒是算出来的,不是能跑出来的。

### 9.5 KV cache:十八种取值怎么挑

2.6 给了全部取值的清单,4.9 到 4.13 讲了机制,7.3 与 9.4 算了账。这里把它们收成一张选型表。**压缩比一列用的是本章算出来的实际值,不是标称值**——内联 scale 那三档要付 8 个字节的固定开销(见 6.9):

| 取值 | 位宽 | scale 粒度 | scale 从哪来 | 实际压缩比 | query 能否量化 | 什么时候用 |
|---|---|---|---|---|---|---|
| `auto` / `float16` / `bfloat16` | 16 | — | — | 1× | ✓ | 不量化。但 `auto` 有两处例外,见 2.6 |
| **`fp8` / `fp8_e4m3`** | 8 | per-tensor | checkpoint,缺了退化成 1.0 | **精确 2×** | ✓ | **默认首选**(SM89 及以上) |
| `fp8_e5m2` | 8 | per-tensor | 可以不要 | 2× | ✗ | Ampere 上唯一可用的 fp8 KV。**FlashAttention 不支持,且缺 scale 时连告警都没有** |
| `fp8_inc` | 8 | per-tensor | INC 框架 | 2× | — | Intel Gaudi,真 fp8 dtype 存储 |
| `int8_per_token_head` | 8 | 每 (token, head) | **kernel 现算** | 1.94× | ✗ | **checkpoint 没带 scale 时的好选择** |
| `fp8_per_token_head` | 8 | 同上 | kernel 现算 | 1.94× | ✗ | 同上,格点分布更抗离群 |
| `int4_per_token_head` | 4 | 同上 | kernel 现算 | **3.76×** | ✗ | 极致省显存。那 8 字节固定开销在这一档占 5.9% |
| `nvfp4` / `nvfp4_4over6` | 4 | 每 16 元素加全局 | 运行时或 checkpoint | 3.56× | ✓ | Blackwell,需要支持 FP4 注意力的后端 |
| `fp8_ds_mla` / `nvfp4_ds_mla` | 8 / 4 | latent 统一一个 | checkpoint | 2× 或更高 | — | DeepSeek 的 MLA 模型专用布局 |
| `turboquant_k8v4` | K8 / V4 | 向量级质心 | **不需要** | 2.6× | ✗ | KV 是绝对瓶颈时的第一档,代价 **+1.17% PPL** |
| `turboquant_4bit_nc` | 4 / 4 | 同上 | 不需要 | 3.8× | ✗ | 更激进,**+2.71% PPL** |
| `turboquant_k3v4_nc` | 3 / 4 | 同上 | 不需要 | 约 3.5× | ✗ | **+10.63% PPL**,需实测评估 |
| `turboquant_3bit_nc` | 3 / 3 | 同上 | 不需要 | 4.9× | ✗ | **+20.59% PPL**,慎用 |

三条贯穿这张表的规律:

- **「query 能否量化」这一列基本等于「scale 是不是一个标量」。** 注意力 kernel 的反缩放接口只接受每个张量一个标量(4.12),所以凡是按 (token, head) 现算 scale 的,query 那一侧就得放弃——**要最细的 KV 粒度,就得付这个代价**(6.9)。
- **不需要 checkpoint 提供 scale 的那几档,压缩比反而更高。** 内联 scale 与向量级质心都是运行时自给自足的,代价是布局变宽或多一次旋转,换来的是不依赖 checkpoint。
- **压缩比越往下越高,但 PPL 的代价不是线性的。** 从 2.6 倍到 3.8 倍只多退化 1.5 个百分点,再往下就从 2.7% 蹿到 20.6%(6.10)。

### 9.6 怎么选:一棵决策树

```text
① 手上是什么卡?
  Blackwell (SM100+)
    追求极致吞吐  -> NVFP4 或 MXFP8,配 fp8 的 KV
    追求稳妥      -> FP8 W8A8 + C8
    注意          -> INT8 W8A8 在这一代没有实现,见 8.3
  Hopper (SM90) / Ada (SM89)
    DeepSeek 系   -> FP8 二维块,kernel 会自动选 DeepGEMM
    显存极紧张    -> W4A8,或 AWQ 配 C8
    默认          -> FP8 W8A8 + C8      <- 首选
  Ampere (SM80/86)
    大 batch      -> INT8 W8A8(动态 per-token 加 per-channel 权重)
                     注意:FP8 checkpoint 会被自动降级成只量化权重,别指望提速
    小 batch      -> AWQ 或 GPTQ,走 Marlin 或 Machete
    KV 是瓶颈     -> 加 fp8_e5m2(这一代唯一可用的 fp8 KV)
  Turing (SM75)
    AWQ / GPTQ,或 INT8 W8A8;FP8 只能做只量化权重那条路

② 有没有校准数据和时间?
  没有 -> FP8(权重离线量化加激活动态,零校准)
  有   -> INT8 静态、AWQ、GPTQ、NVFP4 都可以考虑

③ KV cache 要不要量化?
  上下文超过 8K,或并发超过 16      -> 强烈建议开,收益见 9.4
  checkpoint 里带 scale            -> 直接用 fp8,精度最好
  没有 scale,两个选择:
    (a) 仍用 fp8  -> 退化成 scale 为 1 的硬转,会有告警(E5M2 除外,见 4.9)
    (b) 每 token 每头那一族 -> scale 由 kernel 现算,精度更好
                              代价:query 量化被禁用,后端支持面窄
  KV 是绝对瓶颈且能接受 1~3% 的困惑度退化 -> TurboQuant 的前两档
  DeepSeek 的 MLA 模型             -> 用它专属的那种布局

④ MoE 模型有额外选项吗?
  只想压专家、零校准 -> 专家在线 INT8
  AWQ / GPTQ 的 MoE  -> 通常会自动切到专用旁路,见 6.4

⑤ 离群值特别严重?
  -> 旋转类方案,但注意运行时会多一次变换 kernel,见 6.7
```

### 9.7 常见误区

这一节每条都是容易想当然、而源码里给出相反答案的地方:

| 误区 | 真相 |
|---|---|
| 量化一定更快 | decode 靠减少权重字节数变快,prefill 靠 8bit tensor core 变快。**只量化权重在大 batch 的 prefill 下会更慢**;激活量化在极小 batch 下也可能更慢 |
| FP8 在所有卡上都快 | Ampere 及以下没有 FP8 tensor core,checkpoint 会被**自动降级成只量化权重**,prefill 一点不快。见 4.3 与 8.2 |
| FP8 的累加用 FP16 | **累加器是 FP32**,scale 在 epilogue 里乘。见 1.7 |
| W8A8 就是把 KV 也量化了 | 完全无关。一个是进 GEMM 前、一个是写 cache 前,**两套 scale、两套 kernel**。见 1.3 |
| FP8 不需要任何 scale | 权重 scale 是必须的(离线算好存在 checkpoint 里),**只是激活 scale 可以动态算**,所以不需要校准数据 |
| 开了 fp8 的 KV 就一定要有 scale | 没有会退化成 1 并打告警,仍然能跑。**但用 E5M2 时连告警都没有**。见 4.9 |
| **可以让 vLLM 在运行时帮我标定 KV scale** | **本仓库没有这个能力。** 两条独立证据:相关符号在代码里已不存在(全仓只剩一句注释说明没有这条路径),以及那三个看似为此准备的经验常量是死代码(见 4.10) |
| INT8 的 per-tensor 激活够用 | 激活里有离群通道,per-tensor 会让普通值只剩两三个格点。**必须用动态 per-token,或先做 SmoothQuant**。见 5.10 |
| AWQ 比 GPTQ 准 | 两者精度相近,取决于模型和校准集;而且在 vLLM 里**可能被同一批 kernel 执行**。见 5.8 |
| INT4 的显存是四分之一 | 组宽 128 下约 **0.26 倍**,NVFP4 约 **0.28 倍**。见 9.3 |
| 二维块量化一定更好 | 精度更好,但每个 K 块都要缩放,**需要 Hopper 及以上才藏得住开销**。见 3.6 |
| kernel 是运行时挑的 | **在建权重时就选定了**,之后的后处理按选中的 kernel 做布局。见 2.2 |
| E5M2 可以用于线性层 | 尾数只有两位,vLLM **只在 KV cache 上支持它**,而且 FlashAttention 还不支持。见 3.2 与 4.13 |
| INT8 在新卡上更保险 | 反了。**SM100 及以上没有 INT8 的实现**,而且两道闸门都不拦、直到前向才报错。见 8.3 |
| 指定了后端就一定生效 | 会生效或**直接报错**,不会静默换一个——这一条和上面那些「静默降级」相反,见 8.4 |
