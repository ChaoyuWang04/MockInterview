# 分块索引与查找

这一页回答一件事:token 序列按固定长度切块做成键,查找只告诉引擎「前缀命中到哪」,不负责把 KV 搬进显存。说法都在源码基准 `0cf5efc7`(tag `v0.5.5`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

同一段系统提示下次再来,本该少做一遍 prefill。可键一旦对不上,该命中的全 miss,坏的就是 **TTFT**:引擎把整段 prompt 再算一遍。

两种切法都会把这个指标弄坏。一种是两边块长度不一致:左边按 256 切、右边按 128 切,同一串 token 变成两套键,热层里明明有数据,查找却从第一块就断。一种是哈希漂了:进程内用语言自带哈希、独立服务用另一套摘要,或者两边空哈希起点不同,滚动链从第二块起全部对不上。尾段不够一块时,独立服务直接丢掉,不当成能命中的键——短 prompt 如果整段都不够一块,命中永远是零。

真问题不是「要不要哈希」,而是:**键必须按同一套切块和同一套滚动规则生成;查找只回答前缀走到哪一块,走到哪才去搬。**

## 二、解法

先把序列切成等长的块。每一块的键不只吃这一段 token,还吃前一块的哈希,从一块空起点滚下来。这样公共前缀共享同一串键,从分叉那一块开始各走各的。独立服务默认丢掉凑不齐的尾段;进程内那条还可以选择把不满的最后一块也存进去,但推荐路径上尾段不能命中。

查找是单独一条请求。引擎把 token 交给缓存服务,服务侧按同一套切块算出块键,向存储提交预取,再按请求号轮询。返回值是命中了几块,不是一块数据。没有登记过的模型布局、切完一块都没有,查找会提前结束并记成零命中,不会假装去搬。

![token 按固定块长切开后用滚动哈希做键；查找只返回命中了几块；取回是另一条请求，查找不会直接把 KV 搬进显存；不够一块的尾段丢掉](/opensource/LMCache/03a-chunk-lookup.svg)

为什么这么拆实际不吃亏:调度器只要知道「从第几块开始自己算」,就能决定还要不要全量 prefill。哈希和预取放在缓存进程里,推理线程不必为每一次可能的命中付滚动计算。查找和取回拆开,没命中就停,不会对着空气搬砖。

进程内路径有另一套切法:按特殊分隔符切段,给非前缀复用用。推荐的独立服务默认仍是等长切块;分隔符那条不在这一页展开。

## 三、代价

**两边块长度必须一致。** 改服务侧的块长而不改引擎侧,或者反过来,键空间整片平移,旧热层里的块全部作废。没有运行时协商能把两套键对上。

**滚动链从第一块断就全断。** 空起点、摘要算法、盐值任一不一致,后面的块即使 token 相同也对不上。语言自带哈希再叠进程盐漂,跨进程几乎必 miss。

**查找不是取回。** 多一趟请求、多一次轮询。短 prompt 上这趟往返可能比省下的计算还显眼;命中前缀够长时才划得来。

**不够一块的尾段在推荐路径上不进索引。** 默认 256 个 token 一块,255 个 token 的请求查找结果是 0。把块调小能捡回短前缀,但请求次数和元数据一起涨。

**查找会占住读锁。** 命中了却决定不取回,要另发松手;不松,热层里的块暂时赶不走。

## 四、和同类大厂框架不一样的地方

同类是「引擎外面的 KV 层怎么给一段 token 找键」。这一页拿 Mooncake、FlexKV 来衬切块与查找,不拿推理引擎本体来比。vLLM、SGLang 是宿主,HiCache 是引擎内前缀缓存,不进对等列。

| 维度 | Mooncake | FlexKV | LMCache |
|---|---|---|---|
| 键首先钉住什么 | 池里的对象,给预填充到译码搬家用 | 引擎显存不够时,把容量伸到主机、盘和远端 | 同一串 token 的等长前缀块,下次少做 prefill |
| 查找回答什么 | 对象在不在池里、从哪搬 | 公开材料按分层命中讲容量,不把「命中到哪一块」当独立请求 | 前缀命中了几块;取回另发 |
| 切块怎么对齐 | 跟传输块走 | 跟引擎块走 | 服务和引擎必须同一块长;推荐路径丢掉不满的尾段 |
| 哈希漂了会怎样 | 对象对不上,搬家失败 | 公开材料不把跨进程哈希当招牌 | 滚动链从断点起全 miss,TTFT 回到全量 prefill |

重心在 LMCache 这一列。Mooncake 与 FlexKV 只核各自公开说过的定位,实现细节等它们自己的解读,核不动就不写。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。块长和哈希算法是服务进程和引擎连接器各写一份,只改一边,查找会从第一块就 miss。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--chunk-size` · 每块多少 token | 独立服务启动 | `256` | 调大:索引变稀,短前缀更难命中;调小:请求变多,元数据涨 | 探活口 `/status` 的 `chunk_size`;引擎也可发「问块大小」 |
| `--hash-algorithm` · 滚动哈希用哪一种 | 独立服务启动 | `blake3` | 改成 `builtin` 或 `sha256_cbor` 必须引擎侧同一套,否则全 miss;`builtin` 还要固定进程哈希盐 | `/status` 的哈希名 |
| 进程内 `chunk_size` · 引擎嵌缓存时的块长 | 引擎配置 | `256` | 只影响进程内路径,和独立服务不是同一份配置 | 引擎日志 |
| 进程内 `pre_caching_hash_algorithm` · 引擎嵌缓存时的哈希 | 引擎配置 | `builtin` | 默认不是独立服务的 `blake3`;混用两条路径必漂 | 启动日志 `Using hash algorithm` |
| 进程内 `save_unfull_chunk` · 不满一块要不要存 | 引擎配置 | `False`;部分模式会被强制打开 | 打开:尾段也能进进程内缓存;独立服务查找仍丢掉尾段 | 配置本身 |
| `--max-cpu-workers` · 查找线程池 | 独立服务启动 | 跟 `--max-workers`,默认 `1` | 调高:查找并行升,CPU 升;搬砖走另一组 GPU 线程,不要拿这一项去加速取回 | 线程名 |
| `enable_scheduler_bypass_lookup` · 调度器绕过外部查找口 | 引擎配置 | 关 | 打开后走进程内直查,不再问独立服务那条查找 | 连接器选型 |
| `enable_async_loading` · 异步查找 | 引擎配置 | 关 | 打开后查找可返回「还在进行」;外部查找客户端不允许再开这一项 | 启动报错 |
| `hit_miss_ratio` · 人为限制命中比例 | 引擎配置 | 空,不限制 | 只用于压测,生产打开会故意丢掉命中 | 包装后的查找客户端 |
| `enable_chunk_statistics` · 记每块命中统计 | 引擎配置 | 关 | 打开后多包一层统计客户端,热路径多一次记账 | 统计日志 |

**怎么看。** 先对 `/status` 里的块长和哈希名,和引擎侧是否同一套。查找事件里有请求号、块键、序列长度;预取结束事件里有命中块数、请求 token 数、热层命中 token、冷层命中 token。返回 0 且原因是没有 GPU 布局或切完没有完整块,不要先去加大热层。探活 200 只说明进程活着,不说明键对得上。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机长上下文、系统提示反复出现 | 服务 `--chunk-size 256 --hash-algorithm blake3`;引擎块长和哈希与服务一致 | 用对齐的滚动键换少做 prefill;代价是短于 256 的请求查找为 0 |
| 大量短前缀、系统提示只有 32–64 个 token | 两边同时改成更小的块长,例如 `64` | 用更密的索引换短前缀也能命中;代价是查找次数和元数据涨 |
| 同机多引擎副本共享热层 | 服务只起一份,各引擎块长、哈希、模型名一致,不要混用进程内 `builtin` | 用同一套键换跨副本命中;代价是有一台漂了,看起来像热层空了 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 探活 200,命中永远是 0 | `/status` 的块长、哈希名是否和引擎一致 | 只改一边等于换了一套键;重启两边 |
| 长 prompt 也不命中 | 是不是进程内 `builtin` 对独立服务 `blake3` | 统一算法;语言自带哈希还要固定进程盐 |
| 只有尾差几个 token 就不命中 | 是不是不够一块被丢掉 | 这是推荐路径的设计,不是热层坏了 |
| 查找返回了块数,显存里没有 KV | 有没有再发取回 | 查找不搬砖 |
| 命中过的块突然写不进 | 有没有在不取回之后松查找锁 | 补松手,不要先加大热层 |
| 打开异步加载直接失败 | 是不是还配了外部查找客户端 | 两者不能同时开 |

## 六、常见误区

- **以为查找成功就是 KV 已经在卡上。** 因为调度器拿到了一个正数。那个数是命中了几块。搬砖是另一条请求;只查不取,显存还是空的。
- **以为改一块长会自动同步到引擎。** 因为服务探活口会报当前块长。引擎不读这个口做切块,两边是两份启动配置,改了都要重启。
- **以为独立服务默认哈希和进程内一样。** 进程内默认语言自带哈希,独立服务默认另一套摘要。混用两条路径,键对不上是必然,不是偶发。
- **以为短请求命中为 0 是热层太小。** 默认一块 256 个 token,不够一块的序列在推荐路径上根本没有键。先对块长,再谈容量。
- **以为盐值只影响隔离、不影响命中。** 盐进了键。租户之间故意隔离没问题;同一租户两边盐不一致,照样全 miss。
- **以为查找线程池也能加速搬砖。** 查找走 CPU 池,取回走另一组绑 GPU 的线程。把查找线程拉很高,搬砖带宽不会跟着涨。
