# 引擎插拔与 GPU 搬运

这一页回答一件事:适配层怎么认引擎的 KV 布局、把块从显存搬进搬出,而不改引擎内核。说法都在源码基准 `0cf5efc7`(tag `v0.5.5`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

引擎把 KV 排成自己的分页布局,是为了注意力一步就能算。缓存层要复用这些块,就必须按**同一套排布**把数据从显存拷走、再拷回来。布局一换、头数一变、K 和 V 从拼在一起改成分开,搬错的不是报错,是**静默算错**:命中看起来很高,生成却胡言。

把适配代码写进引擎仓更糟。引擎每周发版,连接器钩子跟着改;缓存层跟不上,线上只能钉死旧引擎,TTFT 优化永远晚一拍。真问题不是「会不会拷」,而是:**认布局的人必须跟引擎发版解耦,认错必须在登记时拒绝,不能拖到 decode。**

## 二、解法

引擎只提供钩子:登记这块显存、加载前把命中块灌回去、算完再把新块存走。本仓自己实现这些钩子。调度、前向、采样仍在引擎里;本仓不改注意力内核。

推荐路径上,钩子在引擎进程里,查找和热层在独立缓存服务里。适配层先把引擎的 KV 张量登记下来,按形状和引擎给的布局提示认出格式,再交给显存搬运器按页块拷。查找只传块键,不传整层权重。遗留路径把进程内缓存引擎嵌在同一进程,搬运器还是这一套,只是热层跟引擎共命运。

![引擎进程里调度与前向不改内核,本仓适配层实现登记加载保存钩子,布局识别根据张量形状与引擎提示决定格式,显存搬运器按页块拷进拷出,查找虚线指向独立缓存服务,遗留进程内引擎用虚线框标出且不接热层](/opensource/LMCache/02a-engine-plug-gpu-copy.svg)

为什么实际不吃亏:引擎发版只动钩子签名时,改的是本仓适配层,不必等引擎合入。布局识别发生在登记那一次;之后每步搬砖只带块号。对不上的布局在登记时抛错,而不是 decode 里静默错位。

官方集成文档把 TensorRT-LLM 仍标成即将到来;仓里已有适配文件,但用户文档不当成可抄的生产入口,这一页只记这一句。

编码器缓存、隐状态、多模态占位、按层搬运、延迟卸载都挂在同一套钩子上,体量薄,不当成另一条主路径。

## 三、代价

**登记必须发生在第一次前向之前。** 没登记就加载,适配层会警告并走降级路径,等于这一轮白问缓存。

**布局提示晚给或给错,搬运器按旧默认猜。** 缺提示时,CPU 注意力默认一种头排布,其余默认另一种。引擎若已换成别的排布,猜错就是静默错位。

**连接器类名和模块路径必须成对。** 只写引擎仓里那个旧封装名、不写本仓模块路径,装到的是引擎仓里那份,跟不上本仓发版。推荐独立服务时,还要写本仓多进程连接器,并指向请求口,不是探活口。

**按层搬运和第三版搬运器都不是默认。** 打开按层,在不支持的加速器上启动直接失败,不会悄悄落到别的实现。非前缀复用还要求搬运器在场,缺了断言失败。

**默认搬运假定能看见引擎那块显存。** 独立服务靠登记时的显存共享;共享失败时,不是「慢一点」,是后续取回对不上页。

## 四、和同类大厂框架不一样的地方

同类仍是「引擎外面的 KV 层」。这一页拿 Mooncake、FlexKV 衬托「适配代码住哪、认不认布局」。宿主引擎本身不进对等列。

| 维度 | Mooncake | FlexKV | LMCache |
|---|---|---|---|
| 适配代码住哪 | 公开材料强调传输与存储和引擎解耦,连接器作为引擎侧插件出现 | 公开材料按引擎下的容量层来讲,挂在引擎下面伸主机内存和盘 | 适配层在本仓;引擎用动态模块路径加载,不必等引擎合入 |
| 认不认引擎 KV 布局 | 公开定位在集群搬运和分布式池,不把「登记时识别分页形状」当招牌 | 公开定位在显存不够时扩容,布局细节本页未核 | 登记时按形状和引擎提示识别;对不上拒绝,不瞎拷 |
| 谁负责从显存搬块 | 传输引擎面向预填充到译码的交接 | 公开材料不把显存搬运器当独立产品面 | 本仓显存搬运器按引擎类型和加速器分发,内核仍归引擎 |
| 跟引擎发版的关系 | 解耦存储,引擎重启不影响池里对象 | 显存那一层仍归引擎 | 钩子实现跟引擎仓解耦;文档仍把某家引擎标成即将到来 |
| 当前这条请求的预填充到译码 | 公开定位就是拆开后的 KV 交接 | 公开材料不把这件事当招牌 | 本页只负责认布局和搬块,不把本层画成那条交接 |

重心在 LMCache 这一列。Mooncake、FlexKV 的内部钩子本页没有核源码,只写各自公开材料里站得住的那一句。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。改的是引擎进程里的连接器类名、模块路径和配置文件,以及本仓配置里跟搬运有关的开关;热层大小的必填项在 01,介质与水位见 04 章。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `LMCACHE_CONFIG_FILE` · 本仓配置文件 | 环境变量 | 不设则读环境项并告警 | 文件里的块大小、按层、第三版搬运器都会进适配层 | 日志 `Loading LMCache config file …` |
| `--kv-transfer-config` 里的 `kv_connector` · 连接器类名 | 引擎启动 | 无,要自己选 | 进程内封装名走遗留;动态名加模块路径才加载本仓最新钩子;多进程名走独立服务 | 启动日志里的连接器类 |
| `kv_connector_module_path` · 本仓模块路径 | 同上 JSON | 无;动态加载时必填 | 指到本仓适配文件,引擎仓那份封装不再挡发版 | 指错则 import 失败 |
| `kv_role` · 这端是否生产 KV | 同上 JSON | 文档示例常用 `kv_both` | 只消费则不存;只生产则不取 | 配置本身 |
| `lmcache.mp.host` / `lmcache.mp.port` · 独立服务请求口 | 连接器 extra | `tcp://localhost` / `5555` | 必须对上缓存服务请求口,不是探活口 | 连不上报 `ConnectionError` |
| `lmcache.mp.server_urls` · 多台服务地址 | 连接器 extra | 空,退回上面那对 | 多地址时禁止自动拉起服务 | 启动抛错或日志里的 URL 列表 |
| `lmcache.mp.eager_prefetch` · 进等待队列就查找 | 连接器 extra | 关 | 打开:查找提前,排队长时可能省 TTFT;可恢复请求仍不提前 | 日志 |
| `lmcache.mp.mq_timeout` · 登记等同步请求超时 | 连接器 extra | `300` 秒 | 调小:登记慢会超时;调大:故障发现变慢 | 超时异常 |
| `lmcache.mp.heartbeat_interval` · 心跳间隔 | 连接器 extra | `10` 秒 | 调小:更快发现服务死;心跳更密 | 心跳线程 |
| `lmcache.mp.autostart` · 由引擎拉起缓存服务 | 连接器 extra | 关 | 打开只允许一台服务;多地址直接拒绝 | 启动抛错 |
| `use_gpu_connector_v3` · 第三版搬运器 | 配置文件 / 环境 | 关 | 打开:走新实现,注释仍标不稳定;只在部分加速器上有 | 启动 `ValueError` 或不走 V2 日志 |
| `use_layerwise` · 按层搬 | 配置文件 / 环境 | 关 | 打开:与计算重叠;某类加速器上直接拒绝 | 启动报错 |
| `enable_blending` · 非前缀复用 | 配置文件 / 环境 | 关 | 打开要求搬运器在场,且部分加速器没有实现 | 断言失败或 `ValueError` |

**怎么看。** 引擎日志里先确认连的是哪一个连接器类。登记成功会打「正在登记 KV」。布局识别成功会打引擎 KV 格式那一行,后面跟形状说明;这一行没有、却已经在取回,就是没走到识别。独立服务路径上,请求口连不上先核 extra 里的端口是不是服务的请求口。命中高但输出错,先怀疑布局提示和引擎实际排布不一致,不要先加热层。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 推荐:vLLM 连独立缓存服务 | 服务按上一页起;引擎 `--kv-transfer-config` 用多进程连接器类名加本仓模块路径,extra 里 `lmcache.mp.host` / `lmcache.mp.port` 对请求口 | 用本仓发版节奏换「等引擎合入」;代价是必须先登记显存,端口连错命中为零 |
| 单机试进程内路径 | 引擎用进程内连接器类名,`LMCACHE_CONFIG_FILE` 指向本仓 yaml,不配多进程地址 | 少一个进程换「引擎崩了块一起没」 |
| SGLang 同机复用 | 引擎走 SGLang 适配初始化,配置文件不要写独立服务主机端口;块大小与服务侧一致 | 用本仓搬运器认 SGLang 的分池布局;代价是按层和某类加速器组合会启动失败 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 引擎起不来,import 连接器失败 | 模块路径是不是本仓那个文件 | 动态加载必须带路径;只写类名会找引擎仓 |
| 登记前就开始加载,日志警告请更新连接器 | 引擎版本是否还走前向里补登记 | 换成会先登记的路径,否则这一轮等于没缓存 |
| 命中很高,生成乱 | 登记日志里的格式行是否和当前注意力后端一致 | 补布局提示;不要靠缺提示时的旧默认 |
| 打开按层或第三版搬运器直接退出 | 当前加速器是否在支持集合里 | 关掉或换卡,不会静默落到别的实现 |
| 独立服务健康,引擎仍连不上 | extra 端口是不是请求口 | 不要填探活口 |
| 多地址还开了自动拉起 | 是否多于一台服务 | 多机请自己起服务,自动拉起只许一台 |
| TensorRT-LLM 按用户文档找不到入口 | 集成页是否仍写即将到来 | 仓里有文件,文档不当成可抄生产入口 |

## 六、常见误区

- **以为写进引擎仓的封装和本仓动态加载是同一个东西。** 因为类名都带连接器。引擎仓那份要等合入才更新;动态路径加载的是本仓当天的钩子。混用会在发版后静默落到旧实现。
- **以为缺布局提示时搬运器会自己「看懂」新排布。** 缺提示走的是旧默认:CPU 注意力一种,其余另一种。引擎已经换排布时,默认就是错的。
- **以为命中率高就证明拷对了。** 块键对上、字节拷错位,查找仍报命中,decode 才错。要以登记时的格式行为准,不要只看命中计数。
- **以为按层搬运是加速开关,打开就更快。** 它换的是和计算重叠的实现,默认关;不支持的加速器上是启动失败,不是稍慢。
- **以为 TensorRT-LLM 用户文档即将到来等于仓里没有代码。** 设计文档和适配文件已经在;集成页仍标即将到来,生产入口不要按那一页抄。
- **以为编码器缓存、隐状态和 KV 走同一条默认搬运。** 它们挂在同一套钩子附近,但是另一份配置和适配,体量薄,打开方式和 KV 默认路径不是同一个开关。
