# LMCache 框架总览

源码基准:官方仓库 <https://github.com/LMCache/LMCache>,分支 `dev`,commit `0cf5efc7e0e96f153d63ce1479e085a86845d668`,最近的发布 tag `v0.5.5`,核对日期 2026-09-21。全篇的「当前」「默认」都指这组基准。文档里的加速数字标为「官方数字」;论文数字标为「论文自报」。

## 一、LMCache 是什么

**LMCache** 是推理引擎旁边的一层 KV 缓存。引擎仍然负责切词、调度、前向和采样;LMCache 负责把算过的 KV 从 GPU 里拿出来,存住,下次同一段文本再来时送回去,让 prefill 少做一遍。它针对的负载很具体:长上下文、多轮对话、RAG 这类「同一段文本会反复出现,但不一定每次都在 GPU 里」的请求。官方数字是多轮和 RAG 上 TTFT 降 3–10 倍;论文自报与 vLLM 合用吞吐最高 15 倍。

它不是又一个推理引擎。PagedAttention、radix 树、调度器怎么进批,都在引擎自己的解读里。LMCache 只回答四件事:怎么插进引擎、块怎么编号和查找、热数据放在哪一层、跨进程或跨机器时怎么搬。

今天推荐的用法是 **独立进程**:`lmcache server` 在节点上跑一份缓存服务,引擎通过 ZMQ 或 gRPC 存取。引擎崩了,L1 里的块还在;同机多个引擎副本可以共用一份 CPU 侧缓存。仓库里仍有一套进程内库(`LMCacheEngine`),官方文档已经标成遗留路径,本解读只在需要对照时提起。

一句话定位:**LMCache 把 GPU 上的临时 KV 收成可分层、可共享、可观测的缓存服务,默认和引擎分进程,避免共命运。**

顶层入口(仓库根 `pyproject.toml` 的 scripts):

- `lmcache server`:推荐。独立缓存服务,带 HTTP 前端。
- `python3 -m lmcache.v1.multiprocess.server`:同一套服务,无 HTTP,文档标为遗留入口。
- `lmcache coordinator`:多机时的成员服务,不管 KV 数据。
- `lmcache_controller`:进程内控制面入口,对应遗留路径。

代码组织上,解读主体在 `lmcache/`(约 8 MB)。`lmcache/v1/distributed/` 与 `v1/storage_backend/` 是两套分层存储(前者跟多进程走,后者跟进程内走);`v1/multiprocess/` 是独立服务; `integration/` 与 `gpu_connector/` 是引擎插拔和显存搬运。`csrc/` 是算子,`operator/` 是 Kubernetes 部署件,本解读不立章。

## 二、6 个招牌:先建立全局图景

```text
        客户端请求 ── 推理引擎(vLLM / SGLang / …)
                           |
                    [2] 适配层 + GPU 搬运
                    认这一家引擎的 KV 布局,把块搬出搬进
                           |
                           v
              [1] 独立进程 lmcache server   ← 推荐;进程内库是遗留
                    查找、存储、观测都在这边
                           |
              [3] 分块索引(默认 256 token 一块)
                           |
              [4] L1:CPU 内存(也可 DAX / GDS 板)
                           |
              [5] L2 适配器:盘 / Redis / Mooncake / S3 / NIXL / …
                           |
            ┌──────────────┼──────────────┐
            v              v              v
     [6] P2P 读邻居 L1   PD 时与引擎     CacheBlend
         协调器只管谁活着  侧传输组合     非前缀段落也能命中
```

一句话记忆:

- **独立进程**:缓存和引擎不共命运,同机多副本共用 L1。
- **适配层**:引擎继续当引擎,LMCache 只认 KV 的形状和槽位。
- **分块索引**:命中粒度是块,不是整段 prompt。
- **L1**:CPU 侧热层,GPU 不必为了「下次可能再用」把 KV 留在显存里。
- **L2 插件**:热层放不下就往后扔,换存储后端不换查找。
- **P2P / Blend / 传输**:多机读邻居、非前缀复用、和 PD 传输组合——都是主线上的配件,不是另一套系统。

## 三、11 章,各自解决什么

下表是本解读的章表。**这里只回答「它存在是为了解决什么」**;展开讲解在各章,代码在哪见代码索引页。

| 主题 | 不这么做会怎样 | 做法一句话 | 详见 |
|---|---|---|---|
| 整体架构与两种部署 | 缓存和引擎一个进程:引擎一崩 KV 没了,GIL 抢推理,同机多副本各握一份 L1 | 推荐独立进程管 KV,引擎只发存取请求;进程内库留下对照 | 01 章 |
| 引擎插拔与 GPU 搬运 | 布局一换搬错就静默算错;适配写进引擎仓就跟不上发版 | 连接器认这一家的 KV 布局,把块从显存搬进搬出 | 02 章 |
| 分块索引与查找 | chunk 对不齐或哈希漂了,该命中的全 miss,TTFT 回到全量 prefill | 按块给 token 序列做键,查找只回答命中到哪 | 03 章 |
| L1 内存与分配 | L1 不够或碎片:GPU–CPU 拷贝堵住推理,或有容量却放不进 | 热块放在一块 CPU(或 DAX/GDS)区域,带水位驱逐 | 04 章 |
| 分层存储与 L2 适配器 | 只有 GPU 前缀缓存时,换请求、换进程、换机器都得重算 | L1 放不下的块异步落到可插拔 L2 | 05 章 |
| P2P 共享与协调器 | 每台机器各算各的长前缀,集群命中率上不去 | miss 时单向读邻居 L1;协调器只管谁活着 | 06 章 |
| PD 分离与 KV 传输 | prefill 和 decode 抢卡;跨机传 KV 失败只能重算 prompt | 当前请求的 P→D 走引擎侧传输,LMCache 做跨请求复用 | 07 章 |
| CacheBlend 非前缀复用 | RAG 可复用段落不在前缀上,前缀缓存全 miss | 不在前缀上的重复块也能命中,边界上补算一小段 | 08 章 |
| SERDE 与 CacheGen | 远端或盘上按满精度走,带宽把 TTFT 吃掉 | 进 L2 之前可量化、压缩、加密,按适配器开关 | 09 章 |
| 缓存编排 | 热文档被 LRU 赶走;没法预热或按租户清 | 查找之外还能钉住、搬走、清空(MP 上部分接口仍未齐) | 10 章 |
| 观测、CLI 与前端 | 命中率掉了分不清是 L1 满了、L2 慢了还是查找错了 | 命中、水位、请求跨度走同一条事件总线;CLI 是入口 | 11 章 |

配置系统不单独成章,入口和观测点集中在本页第六节。

## 四、一条请求怎么串起来

推荐路径上,引擎和缓存是两个进程。引擎侧的连接器在 prompt 到来时先问缓存:这些 token 块有没有。命中的块从 L1(必要时先从 L2 或邻居拉回来)搬回 GPU,引擎跳过这一段 prefill;没命中的照常算,算完再异步交给缓存。查找、搬砖、写回都在独立进程里做,推理线程不跟哈希和落盘抢锁。

同一节点上可以有多个引擎连同一份 `lmcache server`,L1 是共享的。多节点时,本机 L1 miss 可以去问邻居(P2P),协调器只告诉你谁还活着,自己不存 KV。

如果还开了 PD 分离,当前这条请求的 prefill→decode 传输仍由引擎侧的传输连接器做;LMCache 站在旁边,让「上一轮已经算过的前缀」不必再算一遍。两件事不要并成一件。

进程内路径把上面这些塞回引擎进程,官方已不推荐,细节留在 01 章对照。

## 六、怎么调它、怎么看它

各章「调参与观测」只写自己的参数,入口和观测点在这里说一次。

**三种入口,一个原则:改了要重启的都是启动参数。**

| 入口 | 长什么样 | 什么时候用 |
|---|---|---|
| 独立服务启动参数 | `lmcache server --l1-size-gb 20 --eviction-policy LRU`,传输、L2 适配器、P2P、Blend 引擎类型都在这里 | 生产推荐路径;改了要重启服务 |
| 引擎侧连接器配置 | 在引擎启动时声明连哪一种 LMCache 连接器、扮演什么角色 | 只改引擎、不改缓存服务时用;改了要重启引擎 |
| 进程内 YAML / 环境变量 | `chunk_size`、`local_cpu` 这类键,环境变量带 `LMCACHE_` 前缀 | 遗留的库模式;改了要重启引擎 |

多机还要单独起 `lmcache coordinator`。P2P 文档写明:只广告自己、不配协调器地址,服务拒绝启动。

**观测点先记这两处。**

| 看什么 | 在哪 | 备注 |
|---|---|---|
| 服务是否活着 | HTTP `/healthcheck`(文档给 Kubernetes 探活用) | 和指标口在同一套 HTTP 前端上 |
| 命中与水位 | HTTP `/metrics`,默认端口文档写 8080,指标名前缀 `lmcache_mp_` | `lmcache server` 下不要去找单独的 Prometheus 端口,文档写它此时无效 |
| 内部状态 | HTTP `/status`、`POST /cache/clear` | 清的是 L1 |
| 进程内指标 | 遗留路径走另一套日志与统计 | 11 章分开写,不要混 |

排障先看服务是否在、引擎连的是不是这一份服务,再看命中指标。不要用启动命令当「当前生效配置」的唯一来源。

## 七、阅读顺序

主干是 01 → 02 → 03 → 04 → 05,读完就抓住「独立进程 + 查找 + 热层 + 可插拔冷层」。06、07 只在多机或 PD 时读。08、09 是变换:非前缀命中和进 L2 之前的压缩加密。10、11 是生产和排障。

**怎么读**:先读过知识库里 KV cache、PD 分离那些专篇,再来。本解读不重讲前缀缓存是什么,只写 LMCache 把块放到引擎外面之后发生了什么。引擎侧连接器在 vLLM / SGLang 解读里各有落点,那些页写引擎怎么调连接器;本解读写连接器对面的缓存服务。各章第四节的对照对象是 Mooncake 与 FlexKV,不是宿主引擎,也不是 HiCache。

和引擎内前缀缓存的差别只在这里帮你分界,不以对比开章:

| 维度 | 引擎内前缀缓存 | LMCache |
|---|---|---|
| 活在哪 | 引擎进程的 GPU(或引擎自己的主机缓存) | 默认独立进程的 CPU 热层,后面可接 L2 |
| 引擎一崩 | 前缀一起没 | 独立进程里的块还在 |
| 同机多副本 | 各算各的,除非引擎自己做共享 | 多引擎连同一份服务,L1 可共用 |
| 非前缀 | 通常不命中 | CacheBlend 可命中段落 |
| PD | 引擎自己的传输连接器 | 与传输连接器组合,本层做跨请求复用 |

## 八、术语表

| 术语 | 一句话 |
|---|---|
| MP 模式 | 多进程:LMCache 跑独立服务,引擎当客户端。文档推荐路径 |
| 进程内 / 库模式 | LMCache 嵌在引擎进程里。文档标遗留 |
| L1 | 热层,通常是 CPU 内存,也可以是 DAX 或 GDS 板 |
| L2 | 热层后面的可插拔存储,盘、Redis、对象存储、Mooncake 等都走适配器 |
| chunk | 默认 256 个 token 一块,查找和搬运的单位 |
| CacheBlend | 让不在前缀上的重复块也能复用,边界上补算 |
| CacheGen | 一种有损压缩 KV 的变换,走 SERDE 接口 |
| SERDE | 进 L2 前后的序列化/反序列化插件,可量化、压缩、加密 |
| P2P | 本机 L1 miss 时单向 RDMA 读邻居 L1 |
| Coordinator | 多机成员服务,不存 KV |
| LMCache 驱动传输 | 独立进程用 CUDA IPC 一类路径自己搬块,文档默认 |
| 引擎驱动传输 | 引擎侧 PREPARE/COMMIT,独立进程配合 |
| 连接器 | 引擎里那层适配,不是缓存服务本身 |
