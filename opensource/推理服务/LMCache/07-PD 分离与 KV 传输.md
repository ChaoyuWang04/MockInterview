# PD 分离与 KV 传输

这一页回答一件事:预填充和译码拆开之后,当前这条请求的 KV 由谁搬、跨请求复用又由谁管。说法都在源码基准 `0cf5efc7`(tag `v0.5.5`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

同一张卡既要扛长 prompt 的预填充,又要扛一长串 decode,坏的是 **吞吐和间隔**:预填充一来,正在吐字的请求开始抖。把两类活拆到两台引擎,卡能各自扩,但又多出一件事——当前这条请求的 prompt KV 必须从预填充机交到译码机。交失败,译码侧只能把整段 prompt 再算一遍,TTFT 回到没拆之前。

拆开之后还有第二件事。下一轮、下一条请求还带着同一段系统提示,显存里的前缀已经被挤掉了,若每台引擎只认自己那次交接,集群仍会把同一段算许多遍。真问题不是「要不要 PD」,而是:**当前请求的交接,和跨请求的复用,不能走同一条管道。**

## 二、解法

当前请求的预填充到译码,走引擎侧传输:NIXL(底下是 UCX 或 RDMA)。译码实例把这块 KV 拉过去,不必重算 prompt。路由器开 PD 模式,先把请求打到预填充,再打到译码,并把两边的握手串起来。

LMCache 不接这条交接。它在旁边做跨请求复用:每台引擎把自己的 KV 卸到同机那份独立缓存服务。预填充路径上的来源顺序是:本机 GPU 前缀缓存,再问本机缓存服务,再自己算。官方最小部署是五个进程:预填充引擎、它的缓存服务、译码引擎、它的缓存服务、路由器。预填充和译码各跟自己那份服务,**不得共用一个**。

两边用引擎的组合连接器拼在一起:一份负责当前请求的 NIXL 交接,一份是本仓的多进程连接器,只跟本机缓存服务说话。缺引擎侧那次「真实块」修复时,组合连接器下的卸载会静默不触发——服务在,命中却永远是零。

![五进程组合:路由器在上;左是预填充引擎和它的缓存服务,右是译码引擎和它的缓存服务。黄实线从预填充引擎指向译码引擎,表示当前请求的 NIXL 交接;绿虚线各自向下指向本机缓存服务,表示跨请求卸载。没有从缓存服务指向译码引擎的黄线](/opensource/LMCache/07a-pd-five-processes.svg)

跨预填充池和译码池还要互相命中,再叠点对点,见 06 章。

同机进出独立进程,还有两条搬砖模式,跟 P→D 不是一件事。默认由缓存服务自己搬:引擎先登记显存,再发存、取。另一条是引擎先准备、自己拷、再提交,给服务看不见那块 GPU 的场景。两条可以同时装,由引擎实际发哪一种请求决定。非前缀复用拒绝只开引擎驱动那一种。

![左列默认由缓存服务从已登记显存拷块;右列引擎先准备再提交。两边都停在本机热层,不画到另一台引擎](/opensource/LMCache/07b-two-transfer-modes.svg)

进程内路径里还有一套「PD 存储后端」,发送端不落盘、直接往对端写。官方推荐的多进程 PD 不走它,本章不对等展开。

## 三、代价

**最小是五进程、两份热层。** 少起一份缓存服务、让两台引擎共用,官方明确禁止。热层仍要报容量和驱逐,见 01 章。

**当前请求的交接失败,默认可能被当成「再算一遍 prompt」。** 官方示例把失败策略设成直接失败,让问题冒出来,而不是静默重算。

**组合连接器要配齐。** 只插本仓连接器,没有引擎侧 NIXL,当前请求过不了机。只插 NIXL、不插本仓,跨请求复用没有。缺那次真实块修复,卸载不报错也不干活。

**单机把五进程叠在 localhost 上,NIXL 走回环,时延不能当 RDMA 成绩。** 官方写明那是功能验证。同机还要拆开每一类端口:两份缓存请求口、两份探活口、两份引擎口、两份侧信道口。

**冷交接在高并发下会把引擎侧 NIXL 路径打满。** 官方建议把译码侧 GPU KV 留够工作集,让多数交接变短、由缓存托住;否则降低并发。

## 四、和同类大厂框架不一样的地方

同类仍是引擎外面的 KV 层。NIXL 是传输库,不进对等列。对照对象是 Mooncake 和 FlexKV。

| 维度 | Mooncake | FlexKV | LMCache |
|---|---|---|---|
| 首先解决哪件事 | 拆开预填充和译码之后,当前 KV 怎么在集群里交接、怎么进池 | 显存不够时把容量伸到主机内存、盘和远端 | 下次同一段文本再来,少做一遍预填充 |
| 谁搬当前这条请求的预填充到译码 | 传输引擎就是为这件事做的 | | 交接走引擎侧 NIXL,本层不接这条管道 |
| 和引擎的进程关系 | 存储与引擎解耦 | 挂在引擎下面 | 推荐每台引擎旁一份独立服务,预填充与译码不共用 |
| 跨请求的块在哪 | 集群里的分布式池 | 本机主机内存往下伸 | 本机独立进程的热层;跨池再叠点对点见 06 章 |

FlexKV 公开材料不把 PD 交接当招牌,那一格留空。另两列只核公开定位,内部实现等各自的解读。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。引擎侧改的是 KV 传输配置和侧信道环境变量,缓存侧改的是两份独立服务;热层容量和驱逐见 01 章,跨池点对点见 06 章。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--kv-transfer-config` · 引擎组合哪几个连接器 | 引擎启动 | 无,PD 时必填 | 顶层 `MultiConnector`;内嵌 `NixlConnector`(生产者或消费者)加 `LMCacheMPConnector`(`kv_both`) | 引擎启动日志;配错则交接或卸载缺一边 |
| `kv_load_failure_policy` · 当前请求交接失败怎么办 | 嵌在 NIXL 连接器里 | 引擎侧自己的默认;官方示例 `fail` | `fail`:失败冒出来,而不是静默重算 prompt | 译码侧报错,而不是 TTFT 突然回到全量 prefill |
| `VLLM_NIXL_SIDE_CHANNEL_HOST` · 对端来握手的地址 | 引擎环境变量 | 无,示例要填可达地址 | 填错则对端连不上侧信道 | 对端握手失败 |
| `VLLM_NIXL_SIDE_CHANNEL_PORT` · 侧信道端口 | 引擎环境变量 | `5600` | 同机两实例必须错开 | 端口冲突或握手失败 |
| `UCX_NET_DEVICES` / `NCCL_CUMEM_ENABLE` · NIXL 底下网卡与显存 | 引擎环境变量 | 官方示例 `all` / `1` | 网卡不对则 RDMA 走不成 | NIXL 传输日志 |
| `--port` / `--http-port` · 每份缓存服务的请求口与探活口 | 缓存启动 | 请求口 `5555`、探活口 `8080`(01 章) | PD 示例用 `6555`/`8090` 与 `6556`/`8091`,两份必须错开 | 日志绑定地址;`curl` 探活口 |
| `--instance-id` · 这份服务的稳定身份 | 缓存启动 | 随机 UUID | 示例钉成 `prefiller` / `decoder` | `/status`、协调器成员 |
| `--supported-transfer-mode` · 同机存取谁搬砖 | 缓存启动 | `lmcache_driven` | `engine_driven`:改走准备/提交;`auto`:两条都装 | 日志 `Supported transfer mode:` |
| `--shm-name` · 引擎驱动时的共享内存名 | 缓存启动 | 空字符串,强制序列化 | 非空且池大于 0 才走共享内存槽;容量不够回退序列化 | 日志 `Using shm` / `Using pickle` |
| `LMCACHE_MP_TRANSFER_MODE` · 引擎 worker 选哪条搬砖 | 引擎环境变量 | `auto`(按设备历史逻辑) | 钉成 `lmcache_driven` 或 `engine_driven` | 登记失败或走错请求类型 |
| `enable_pd` / `pd_role` · 进程内 PD 存储后端 | 进程内配置 | 关 | 遗留路径,发送端直接往对端写;推荐多进程 PD 不要开 | 不走 `lmcache server` 那条 |

**怎么看。** 路由器回包的 `id` 会盖上预填充和译码地址。译码引擎日志里的 KV Transfer 指标看 NIXL 成功次数。本机卸载看预填充侧探活口 `/status` 的 `storage_manager.l1_manager.total_object_count`(prompt 至少要够一块)。命中率看引擎日志里的 **External prefix cache hit rate**,不要看缓存服务 `/status`;工作集还塞得进 GPU 前缀缓存时,这一行会一直是 0。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表与官方 PD 页。热层两项必填仍见 01 章。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 分机在线 PD,长 prompt 与 decode 抢卡 | 预填充机:`lmcache server --port 6555 --http-port 8090 --l1-size-gb 100 --eviction-policy LRU --chunk-size 256 --instance-id prefiller`;引擎 `kv_role=kv_producer`,NIXL 侧信道广告预填充 IP、端口 `5600`,多进程连接器连本机 `6555`。译码机另一份服务 `6556`/`8091`/`decoder`,引擎 `kv_consumer`,侧信道端口 `5558`。路由器 `--vllm-pd-disaggregation` | 用两池卡换预填充与译码解耦;代价是五进程、两份热层、RDMA 网,交接失败要能看见 |
| 单机功能验证 | 同一套五进程走 `localhost`,预填充、译码各绑一张卡;四类端口全部错开 | 用能跑通换可观测的路径;代价是 NIXL 走回环,时延不是 RDMA 成绩 |
| 预填充池和译码池还要互相命中 | 五进程之上,两份服务再加广告地址和协调器,见 06 章 | 用邻居命中换跨池重算;代价是启动门禁更严,不是把当前请求改走缓存服务 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 译码侧 TTFT 回到全量 prefill | 失败策略是不是静默重算;NIXL 成功次数 | 改成失败即暴露;核侧信道地址和端口 |
| 服务在,完全不卸载 | 引擎是否带了那次组合连接器真实块修复;本仓连接器有没有插上 | 缺修复会静默不触发,不是热层太小 |
| 两台引擎都连同一份缓存 | 官方要求各跟自己那份 | 拆成两个 `--port` / `--instance-id` |
| 单机端口冲突 | 两份请求口、探活口、引擎口、侧信道口 | 四类都要错开 |
| 打开非前缀复用起不来 | 传输模式是不是只开了引擎驱动 | 改成缓存服务自己搬,或两条都装 |
| `/status` 对象数不涨 | prompt 是否够一块;是否看错探活口 | 块大小两边一致;命中率看引擎那行日志 |
| 把进程内 PD 后端当推荐路径 | 是不是还在引擎进程里开 `enable_pd` | 改五进程组合;那套后端不对等展开 |

## 六、常见误区

- **以为 LMCache 在预填充引擎和译码引擎之间传当前请求的 KV。** 因为仓库里有传输模块,也有进程内 PD 后端。官方 PD 页写的是:当前请求走引擎侧 NIXL,本仓连接器只卸到同机服务。图上从缓存服务画到译码引擎的那条黄线,是错的。
- **以为两台引擎可以共用一份缓存服务。** 同机多副本共享热层是 01 章的非 PD 场景。PD 页写明预填充和译码各跟自己那份,端口和身份都要分开。
- **以为组合连接器插上就一定会卸载。** 缺引擎侧真实块修复时,卸载静默不触发。服务探活 200、对象数不涨,先查引擎版本,不要先把热层加到 100 吉字节。
- **以为单机五进程的时延能代表线上 RDMA。** 回环走 TCP。那套只用来确认路由器盖戳、NIXL 计数、对象数会涨。
- **以为交接失败引擎会大声报错。** 若不把失败策略设成直接失败,译码侧可能自己重算 prompt,看起来像「PD 没生效」,其实是失败被吃掉。
- **以为点对点打开后,当前请求也可以改走邻居热层。** 点对点是跨请求、跨池复用,见 06 章。当前请求的 P→D 仍是引擎侧 NIXL。
