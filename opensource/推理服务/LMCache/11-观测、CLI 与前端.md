# 观测、CLI 与前端

这一页回答一件事:命中率掉了以后,从哪条总线看出是热层满了、冷层慢了还是查找错了,以及命令行和网页分别看哪一口。说法都在源码基准 `0cf5efc7`(tag `v0.5.5`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

缓存服务自己活着、引擎也在问,不等于你能解释 **TTFT** 为什么回去了。热层水位、冷层预取、查找 miss、搬砖超时,各自打各自的日志时,排障会变成三份互不对齐的时间线。

更糟的是把探活口当成存取口、把独立指标口当成推荐入口上的刮取地址:健康检查 200,指标却永远是空的。真问题不是「要不要监控」,而是:**查找、热层、冷层、传输要进同一条事件总线,命令行只从探活口读已经汇好的结果,不要再开一条和引擎抢锁的统计路径。**

## 二、解法

热路径上的模块把事件丢进一条队列,后台线程再分给订阅者。默认装指标和日志两路;跟踪默认不装。队列满了就丢新事件,最多每秒警告一次,不堵推理。关掉整条总线时,发布直接空操作,排空线程也不起。

指标订阅把计数写进进程内的注册表。推荐入口把独立的指标 HTTP 关掉,改由探活口上的同一条指标路由吐出去——端口就是第 01 章那个探活口,不是另一套默认 9090。没配导出地址时走拉取;配了导出地址,指标改成推,这条拉取路由不再是主路径。跟踪没有本地回退:只开跟踪、不给导出地址,跟踪初始化直接跳过。

命令行是探活口的客户端。探活打健康检查路径;看内部状态打状态路径;清空、配额走第 10、05 章已经写过的 HTTP。它不订阅事件总线。

网页控制台是另一套:要先配运行时插件、再起一份发现服务,插件子进程去心跳,控制台再反代各节点的探活口。默认启动命令不装这套。进程内那份统计库是遗留路径,不对等展开。

![查找热层冷层传输把事件丢进总线,后台排空分给默认的指标和日志订阅;跟踪虚线仅在打开且有导出地址时才走;命令行只打探活口,不连总线;网页控制台灰盒无箭头](/opensource/LMCache/11a-event-bus-cli.svg)

为什么不吃亏:推理线程只做一次入队,哈希和格式化在排空线程上。同一条事件可以同时喂指标和日志,不必在热路径上打两遍。

## 三、代价

**推荐入口上,独立指标端口没有用。** 刮 9090 会空;要刮探活口上的指标路径。

**计数器是懒的。** 没有走过存取,对应时间序列还不出现。刚拉起就去对空页面,会误判「观测没开」。

**生命周期直方图默认只抽 1%。** 计数仍全量。把直方图当全量分布,分位数会漂。

**队列满了就丢。** 默认最多攒 10000 条。排空跟不上时,不是变慢,是少事件。

**跟踪默认关,且没有本地刮取。** 只打开关、不给导出地址,等于没开。

**网页控制台不是默认装上的。** 没配插件位置、没起发现服务,浏览器里不会自己出现一块看板。

## 四、和同类大厂框架不一样的地方

同类仍是引擎外面的 KV 层。这一页只拿 Mooncake 和 FlexKV 来衬「命中率掉了从哪看」。传输库不进对等列。

| 维度 | Mooncake | FlexKV | LMCache |
|---|---|---|---|
| 首先解决哪件事 | 预填充和译码拆开之后,KV 怎么在集群里搬、怎么进池 | 显存不够时把容量伸到主机、盘和远端 | 查找、热层、冷层、传输进同一条事件总线,再分给指标和日志 |
| 默认能刮到什么 | 公开材料把池和传输当招牌 | 公开材料把容量延伸当招牌 | 推荐入口:探活口上的指标路径;独立指标端口被关掉 |
| 跟踪 | 本页不写实现 | 本页不写实现 | 默认关;没有导出地址就跳过初始化 |
| 人怎么看 | 本页不写实现 | 本页不写实现 | 命令行打探活口;网页控制台要另起插件和发现服务 |

观测怎么看只在最后一列展开。另两列的内部看板核不动就不写。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。观测总线、指标和跟踪都在缓存服务进程上;探活口地址见第 01 章,清空见第 10 章,配额见第 05 章。命令行是运行时客户端,不必重启服务。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--disable-observability` · 关掉整条事件总线 | 启动 | 关(总线开着) | 加上后发布空操作、排空线程不起;开了协调器事件上报会启动失败 | 启动报错;指标不再涨 |
| `--disable-metrics` / `--disable-logging` · 关掉指标或日志订阅 | 启动 | 关(两路都装) | 加上后对应订阅不注册 | 指标口空,或少一类日志 |
| `--enable-tracing` · 打开跟踪订阅 | 启动 | 关 | 还要 `--otlp-endpoint`,否则跟踪初始化跳过 | 导出端有没有 span |
| `--otlp-endpoint` · 指标和跟踪的导出地址 | 启动 | 空,走拉取 | 有值:指标改推,探活口那条拉取不再是主路径 | 采集器;本地 `/metrics` 不再当主刮取 |
| `--prometheus-port` · 独立指标口 | 启动 | `9090` | 推荐入口 `lmcache server` 关掉独立服务器,这一项无效 | 不要刮这里;改刮 `--http-port` |
| `--event-bus-queue-size` · 总线队列上限 | 启动 | `10000` | 调小:更容易丢;调大:排空落后时占更多内存 | 日志 `EventBus queue full`;`lmcache_mp.event_bus.queue_depth` |
| `--metrics-sample-rate` · 生命周期直方图抽样 | 启动 | `0.01` | 只影响直方图,计数仍全量 | 分位数是否抖 |
| `--enable-extra-logging` · 周期性吞吐日志 | 启动 | 关 | 默认每 10 秒打一趟 GPU 侧吞吐和热层占用 | INFO 日志 |
| `--enable-gc-monitor` · 给垃圾回收计时 | 启动 | 关 | 不走事件总线;暂停超过 `--gc-monitor-min-pause-ms`(默认 1)才打 | INFO 日志 |
| `--runtime-plugin-locations` · 运行时插件(网页心跳用) | 启动 | 空列表 | 空则不拉插件子进程,控制台发现不到这台 | 进程列表;发现服务 |
| `lmcache ping kvcache --url` · 探活 | 运行时 CLI | `http://localhost:8080` | 打 `GET /healthcheck`;引擎未初始化是 503 | 退出码;耗时 |
| `lmcache describe kvcache --url` · 看状态 | 运行时 CLI | 同上 | 打 `GET /status` | 终端里的热层/模块摘要 |
| `GET /metrics` · 刮指标 | 探活口 HTTP | 推荐入口挂在 `--http-port` | 没流量时很多序列还不在 | 用 curl 打探活口 `/metrics`,过滤 `lmcache_mp_` |

**怎么看。** 先确认连的是探活口不是请求口。`GET /` 只证明 HTTP 活着,不碰引擎;`GET /healthcheck` 还要引擎已经起来。内部形状看 `/status`。命中、水位、搬砖看 `lmcache_mp.` 前缀的指标,不要用引擎那行「外部前缀命中率」代替(第 08 章非前缀命中本来就不进那一行)。总线自己的深度和落后秒数是 `lmcache_mp.event_bus.queue_depth` / `drain_lag_seconds`。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。热层两项必填仍见第 01 章。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机在线,只要能刮命中和水位 | `lmcache server --l1-size-gb 16 --eviction-policy LRU --http-port 8080`;刮这个探活口的 `/metrics` | 用探活口一条指标路径换少一个端口;代价是没流量时序列还没出现,9090 是空的 |
| 还要跟踪 | 同上,加 `--enable-tracing --otlp-endpoint http://127.0.0.1:4317` | 用推模式换 span;代价是本地拉取不再是主路径 |
| 只要本机缓存、少打点 | `--disable-observability`(不要同时开协调器事件上报) | 用少一条排空线程换看不见命中分解;代价是上报事件的启动门禁会拒绝 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 9090 上 `/metrics` 空 | 是不是 `lmcache server` | 改刮探活口;推荐入口关掉了独立指标服务器 |
| 探活口指标也几乎没有 | 有没有走过存、取 | 先打几条请求;序列是懒的 |
| `ping kvcache` 404 | 是不是打了 `/health` | 缓存服务是 `/healthcheck` |
| 健康 200,状态里引擎却像没起来 | 打的是不是 `GET /` | `/` 不碰引擎;要看健康检查或 `/status` |
| 打开跟踪,采集器没有 span | 有没有导出地址 | 没地址则初始化跳过 |
| 开了事件上报却起不来 | 是不是同时关了观测 | 上报骑在总线上,不能关 |
| 浏览器没有看板 | 插件位置和发现服务 | 默认启动不装;不是探活口自带页面 |

## 六、常见误区

- **以为推荐入口还会在 9090 吐指标。** 因为参数表里写着这个默认端口。推荐入口把独立服务器关掉,调用方必须自己在探活口挂指标路由。
- **以为健康检查 200 等于缓存在干活。** 因为探活口和指标口在同一进程。健康检查只问引擎对象在不在,不问命中、不问总线。
- **以为命令行连的是事件总线。** 因为它能打出热层摘要。`describe` 读的是 `/status`,`ping` 读的是 `/healthcheck`,都不订阅事件。
- **以为打开跟踪开关就会在本地看到 span。** 因为指标有拉取回退。跟踪没有本地回退,没有导出地址就是跳过。
- **以为网页控制台随 `lmcache server` 一起出现。** 因为文档目录里有看板页。要插件位置、发现服务、额外依赖,默认列表是空的。
- **以为关掉观测只少几条日志。** 因为听起来像啰嗦开关。发布变空操作,协调器事件上报会启动失败。
- **以为进程内那份统计库就是这条总线。** 因为它也叫观测、也有 Prometheus。那是遗留引擎进程里的计数;推荐路径走 `mp_observability`。
