# 缓存编排

这一页回答一件事:热层会自己赶人之后,还能不能钉住、搬走、按意图清空;推荐多进程路径上,管理面实际齐了哪些。说法都在源码基准 `0cf5efc7`(tag `v0.5.5`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

查找只回答「这些块在不在」。热层满了按最近使用赶,系统提示、租户文档、刚预热的前缀,都会和一次性长 prompt 抢同一份名单。赶完再 miss,TTFT 回到全量 prefill。

编排想补三件事:钉住别被赶、搬到另一台或另一层、按实例或按租户清干净。少这三件,运维只能等水位环自己动手,或者把整份热层一把掀掉。

真问题不是「有没有管理接口」,而是:**推荐的独立缓存服务上,这些编排到底落地了没有。** 文档里写着钉住、搬走、压缩,不等于请求口已经能做。

## 二、解法

推荐路径上,管理模块是组合器必装的一块。它管的是探活、问块大小、清空、调试应答、把引擎侧块分配报到事件总线,以及按沉默时间收掉已经登记却不再说话的 worker。探活带实例号时,会刷新传输模块上的存活时刻;收尸线程默认按超时的四分之一扫一圈,超时写成零就不启动这条线程。

清空有两条入口,落到同一个处理函数。一条走探活口的 HTTP;一条走请求口的请求类型。默认只清没锁的对象;强制才会把还占着读写锁的一起掀掉,飞行中的存取可能坏。探活口今天只认热层这一档。按键删除、从冷层预取回热层,是探活口上另一组路由,不是钉住,也不是按租户名一键清。

钉住、搬走、压缩在多进程文档里标成尚未落地。它们活在遗留的进程内控制器:独立起一个管理进程,引擎进程里再开 worker 线程挂号;用户打钉住、搬走、压缩、按位置清空,集群执行器再发到各 rank。官方文档把这套标成进程内、不推荐。进程里附带的网页控制台不单列,不是推荐部署的热路径。

![推荐多进程管理模块实际有探活、清空、收尸;文档里的钉住、搬走、压缩用灰虚线标未齐,实线不从推荐服务连过去;黄盒是遗留进程内控制器才有那些命令](/opensource/LMCache/10a-mp-management-gap.svg)

为什么不把「整份掀掉」当编排:它能救急,但不能保住热文档,也不能按租户切一块。按盐值分名单是热层驱逐策略,不是管理面上的钉住。

## 三、代价

**推荐路径没有钉住。** 热文档和一次性前缀走同一条 LRU。想保住,只能把热层开大、换驱逐策略,或走遗留控制器。

**清空默认留下锁着的对象。** 看起来清过了,占用还在;强制清又可能弄坏正在存取的会话。

**收尸按沉默时间切登记,不按业务租户切缓存。** 超时短于心跳的三倍,活着的 worker 会被当成死掉;超时写成零,死掉的登记会一直占着。从未探活过的 worker 另有更长的宽限,默认一小时。

**探活口清空和请求口清空不是两套语义,但是两套地址。** 连错口,命令到不了管理模块。CLI 走的是探活口那条 HTTP。

**打开遗留控制器不等于多进程服务多了钉住。** 两套代码、两套存储。进程内控制器默认关,要显式打开,还要实例名和上下行地址。

## 四、和同类大厂框架不一样的地方

同类是引擎外面的 KV 层。这一页只拿 Mooncake 和 FlexKV 来衬「管理面齐了没有」。宿主引擎内的前缀缓存不进对等列。

| 维度 | Mooncake | FlexKV | LMCache |
|---|---|---|---|
| 编排首先补哪件事 | 预填充和译码拆开之后,KV 怎么进分布式池、怎么在集群里搬 | 显存不够时容量怎么伸到主机、盘和远端 | 查找之外还想钉住、搬走、清空;推荐路径上后三件未齐 |
| 管理面落在哪 | 池和传输就是产品,不另开一套「钉住热文档」当招牌 | 公开材料把容量延伸当招牌,不把钉住/搬走当独立管理面 | 推荐独立服务:探活、清空、收尸;钉住搬走压缩在遗留进程内控制器 |
| 清空粒度 | 对象在池里,随传输与分层走 | 随下层介质走 | 推荐路径默认整份热层、只清没锁的;按键删除是另一条 HTTP |
| 和引擎进程的关系 | 存储与引擎解耦 | 挂在引擎下面伸容量 | 推荐管理模块在独立进程;进程内控制器跟引擎进程同生共死 |

重心在 LMCache 这一列。另两列只核公开定位,内部管理 API 核不动就不写。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。清空、按键删除、预取是探活口上的运行时接口,不必重启;收尸超时和遗留控制器开关改了要重拉对应进程。热层容量与驱逐见第 04 章,冷层预取策略见第 05 章。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--worker-reap-timeout-seconds` · 已探活 worker 沉默多久收尸 | 启动 | `120`;`0` 关掉收尸;非零必须 ≥ `30` | 调短:死掉的登记更快释放,活 worker 心跳慢会被误杀;关掉:死登记一直占着 | `/status` 里 `worker_liveness`;线程名 `lmcache-mp-worker-reaper` |
| `--worker-registration-grace-seconds` · 登记了但从未探活的宽限 | 启动 | `3600`,且必须 ≥ 收尸超时 | 模型预热超过这个值,登记会被收掉 | 同上 `registration_grace_seconds` |
| 引擎侧 `lmcache.mp.heartbeat_interval` · 适配器探活间隔 | 引擎连接器 extra | `10` 秒 | 服务收尸应 ≥ 三倍间隔,否则启动告警、运行时误杀 | 适配器启动日志 |
| `POST /cache/clear` · 探活口清热层 | 运行时 HTTP | 体可空,默认热层、不强制 | `force=true`:连锁一起清,飞行中存取可能坏;其它档位 400 | 200 返回 `cleared.tier=l1`;占用是否下降 |
| 请求口 `CLEAR` · 同一清空 | 运行时请求类型 | `force` 默认否 | 与 HTTP 同一处理函数 | 连接器/SDK 调用返回 |
| `DELETE /cache/objects` · 按键删 | 运行时 HTTP | 默认冷层;可指定热层或两层 | `force` 只对热层锁生效 | 响应;对象列表 |
| `POST /cache/prefetches` · 按 token 从冷层预热到热层 | 运行时 HTTP | 源冷层、目标热层 | 不是钉住;热层满了仍可能被 LRU 赶走 | `GET /cache/prefetches/{id}` |
| `enable_controller` · 打开遗留进程内控制器 | 进程内 YAML | `false` | `true` 必须同时给实例名、上下行 URL、worker 端口 | 引擎进程多一条 worker 线程 |
| `lmcache_controller --port` · 遗留管理 HTTP | 另起进程 | 主机 `0.0.0.0`、端口 `9000` | 钉住/搬走/压缩/按位置清空走这里,不进推荐请求口 | 日志 `Starting LMCache controller at …` |
| `health_check_interval` · 遗留控制器巡检 | 控制器配置 | `-1` 关 | 小于 1 且不是 -1 则拒绝启动 | 控制器日志 |

不带探活口的模块入口没有 `POST /cache/clear`。CLI `lmcache kvcache clear` 打的是探活口,默认体只清热层。SDK(`lmcache/sdk/`,约 77 KB)是连推荐请求口和探活口的客户端封装,不单列成章,也不提供钉住。

**怎么看。** 先确认走的是独立缓存服务。`/status` 里有 `worker_liveness`(是否启用收尸、超时、宽限、跟踪的实例数)。清空后看热层占用,不要只看 HTTP 200。引擎探活失败、登记被收,下一步取回会 miss,TTFT 跳回全量 prefill。不要在推荐服务的探活口上打 `/pin`、`/move`、`/compress`——那些路径在遗留控制器的 9000 端口。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机在线,只要能清热层、自动收死 worker | `lmcache server --l1-size-gb 20 --eviction-policy LRU`(收尸两项用默认);清的时候 `POST` 探活口 `/cache/clear` | 用整份热层清空和 120 秒收尸换运维接口;代价是没有钉住,热文档仍可能被 LRU 赶走 |
| 模型预热很长,怕登记被收 | `--worker-reap-timeout-seconds 0`,或把宽限加到超过预热 | 用关掉收尸换预热不被误杀;代价是死掉的 worker 登记一直占着 |
| 必须按 token 钉住或跨实例搬走 | 进程内 YAML `enable_controller: true` 并另起 `lmcache_controller`;不要指望推荐多进程服务 | 用遗留控制器换钉住/搬走;代价是跟引擎进程绑死,官方标不推荐 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 打了清空,占用几乎没掉 | 是不是锁还在;有没有 `force` | 等会话结束再清,或接受强制清的风险 |
| 清空 404 | 是不是连了请求口,或走了不带 HTTP 的模块入口 | 改探活口;推荐入口才有这条路由 |
| 清空 400 | `tier` 是不是热层以外 | 今天只认热层 |
| worker 还在,命中突然全没 | `/status` 的 `worker_liveness`;心跳是不是慢于收尸的三分之一 | 加大收尸超时,或加快引擎探活 |
| 推荐服务上 `/pin` 404 | 是不是把遗留控制器的路径打到了探活口 | 多进程文档仍标未齐;要钉住只能走遗留路径 |
| 打开控制器引擎起不来 | 实例名、上下行 URL、worker 端口是否都有 | 缺一项启动失败,不是运行时再降级 |

## 六、常见误区

- **以为多进程文档目录里的管理页已经能钉住、搬走、压缩。** 因为页还在,命令名也在。那一页正文写的是尚未落地,并把读者指到遗留章节。
- **以为探活口清空和请求口清空是两套实现。** 因为地址不一样。HTTP 找到管理模块再调同一清空;CLI 只包了 HTTP 那条。
- **以为清空等于按租户清。** 因为冷层可以按盐值赶。整份热层清空不看盐值;按盐值隔离是第 04、05 章的驱逐,不是本章的钉住。
- **以为预取就是钉住。** 因为都能把块放进热层。预取不改变驱逐名单,热层满了照样赶。
- **以为收尸超时默认关掉。** 因为模块构造参数写的是零。推荐入口把配置默认 120 秒传进去,零才是关掉。
- **以为遗留控制器网页就是推荐运维面。** 因为进程内目录下有前端静态文件。推荐路径没有把那套网页接到独立缓存服务上。
- **以为 SDK 能补齐钉住。** 因为它是官方客户端。它只封装推荐请求口和探活口,没有钉住、搬走、压缩。
