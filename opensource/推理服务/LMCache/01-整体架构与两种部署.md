# 整体架构与两种部署

这一页回答一件事:KV 缓存在不在引擎那个进程里,以及推荐路径上一条请求怎么问独立服务。说法都在源码基准 `0cf5efc7`(tag `v0.5.5`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

推理引擎把 KV 放在自己的进程里,是为了下一步 decode 够得着。可一旦这段文本还会在**下一轮、下一个副本、下一次引擎重启**里出现,把它继续拴在引擎进程上,坏的是 **TTFT**。

三种常见做法都会在规模上把这个指标弄坏。一种是只靠引擎自己的前缀缓存:引擎一崩,热数据一起没;同机再起一个副本,它看不到上一份。一种是把缓存库嵌进引擎进程:查找、哈希、往主机内存拷块,都跟推理线程抢锁,长 prompt 一来,decode 的间隔开始抖。再一种是每台机器各握一份磁盘缓存、彼此不说话:同一段系统提示在集群里被算许多遍,卡在忙,命中率却上不去。

真问题不是「要不要缓存」,而是:**缓存必须能活过引擎进程,又不能把推理线程拖进哈希和落盘。**

## 二、解法

把缓存做成独立进程。引擎只留一个连接器,负责问「这些块有没有」和「搬进搬出」;查找、热层、观测都在另一边。

推荐入口是一条启动命令,它在同一个操作系统进程里起两样东西:对外的探活与指标口,以及真正给引擎用的请求服务。请求服务默认走本机套接字,端口和探活口不是同一个。引擎连的是请求口;把探活口当成存取口,连接器会一直问错人。

请求服务本身是一个组合器。它先建共享上下文(热层、分块大小、哈希算法),再按配置装配模块:查找、管理、传输必有;点对点控制器会进列表,但没配广告地址时不拉编排线程;非前缀复用是另一种引擎类型,要另开,而且不能跟「引擎自己搬」那条传输同时作为唯一选择。模块装好之后,按请求类型分发。默认传输由缓存服务自己搬;另一种是引擎侧先准备再提交。两种可以同时装,由引擎实际发哪一种请求决定走哪条。

![两种部署对照:上半是推荐路径,推理引擎进程只留连接器,独立缓存服务进程里是请求服务、探活口、组合器和主机热层,协调器可选且不存 KV;下半是遗留路径,进程内缓存引擎和分层存储都嵌在同一个推理引擎进程里](/opensource/LMCache/01a-two-deployments.svg)

为什么这么拆实际不吃亏:引擎每步要传的是块的键和少量元数据,不是整层权重。哈希和水位驱逐放到独立进程后,推理线程不必为下一次可能的命中付 GIL。同机多个引擎副本连同一份服务,热层天然共享,不必在引擎里再做一份跨进程缓存。

仓库里仍有一套进程内路径:适配层在引擎进程里拉起缓存引擎,按实例名做成单例,存储走另一套分层代码。官方文档把它标成遗留。它方便单机试,但回答不了「引擎崩了块还在不在」。

推荐路径上,一条请求的顺序是固定的。先登记这块显存,再查找,命中才取回,未命中由引擎自己算,新块再存回去,会话结束时松手。查找和取回不是同一条请求。

![推荐路径上一条请求的五步:引擎侧依次是登记显存、查找、取回或自算、存新块、结束会话;缓存服务里传输模块处理登记与搬砖,查找模块按块键预取,管理模块负责清空和回收,块住在主机热层。未命中停在引擎自己算,不会从查找模块指向一块不存在的数据](/opensource/LMCache/01b-request-path.svg)

## 三、代价

**起服务必须先报热层多大、用哪种驱逐。** 这两项没有默认值,少一个启动器直接拒绝。热层按吉字节预留,开小了命中率上不去,开大了和引擎抢主机内存。

**多一个进程、多一趟本机往返。** 登记、查找、搬砖各是一次请求。单条短 prompt 上,这趟往返可能比命中省下的计算还显眼;长上下文、多轮、同一前缀反复出现时才划得来。

**探活口和请求口是两套。** 推荐入口把它们放进同一进程,但端口不同。只起不带探活口的那个模块入口,指标和健康检查都没有。

**默认传输假定缓存服务能看见引擎那块显存。** 换「引擎自己搬」要另开传输模式;非前缀复用还拒绝只开引擎驱动那一种。配错了不是降级,是启动失败。

**点对点不是打开就有。** 只广告自己、不配协调器地址,推荐入口会拒绝启动。协调器不管 KV,只回答谁还活着。

## 四、和同类大厂框架不一样的地方

同类是「引擎外面的 KV 层」,不是又一个推理引擎。vLLM、SGLang 是宿主,连接器怎么插是下一章的事。对照对象是 Mooncake(月之暗面 Kimi 线上用)和 FlexKV(腾讯云)。HiCache 是 SGLang 引擎内的三层前缀缓存,不进对等列。

| 维度 | Mooncake | FlexKV | LMCache |
|---|---|---|---|
| 首先解决哪件事 | 预填充和译码拆开之后,KV 怎么在集群里搬、怎么进分布式池 | 引擎显存不够时,怎么把容量伸到主机内存、盘和远端 | 同一段文本下次再来时,怎么少做一遍预填充 |
| 和引擎的进程关系 | 存储与引擎解耦,引擎重启不影响池里的对象 | 挂在引擎下面,显存那一层仍归引擎 | 推荐独立进程;进程内库是遗留 |
| 默认热数据在哪 | 集群里的分布式池,主机内存和盘分层 | 本机主机内存,下面接盘和远端 | 本机独立进程的主机热层,后面再接可插拔冷层 |
| 当前这条请求的预填充到译码 | 传输引擎就是为这件事做的 | 公开材料不把这件事当招牌 | 交接仍走引擎侧传输,本层做跨请求复用 |
| 远端怎么接别人 | 自己就是那口池 | 远端可挂 Mooncake 的存储 | 冷层适配器之一就是 Mooncake |

重心在 LMCache 这一列。另两列只核公开说过的定位,内部实现等各自的解读,核不动就不写。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。独立缓存服务改的是服务进程,引擎侧连接器改的是引擎进程,两边都要重启才会看见。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--l1-size-gb` · 热层容量,吉字节 | 启动 | 无,必填 | 调大:命中率升,主机内存被占;调小:热块被赶走,TTFT 回到全量 prefill | 探活口 `/status` 里的存储状态 |
| `--eviction-policy` · 热层满了怎么赶 | 启动 | 无,必填;`LRU` / `IsolatedLRU` / `noop` | `LRU`:按最近使用赶;`IsolatedLRU`:按盐值分名单,要配配额;`noop`:不赶,满了就写不进 | 启动参数本身 |
| `--transport` · 引擎连哪一种请求口 | 启动 | `zmq` | `grpc`:换协议,调度线程数走 `--grpc-server-workers`(默认 32) | 日志 `LMCache zmq cache server is running on …` |
| `--host` / `--port` · 请求口绑定 | 启动 | `localhost` / `5555` | 改了引擎连接器要跟着改,否则一直连不上 | 上面那行日志的地址 |
| `--http-host` / `--http-port` · 探活口绑定 | 启动 | `0.0.0.0` / `8080` | 只影响探活和指标,不影响存取 | `curl` 探活口 |
| `--chunk-size` · 每块多少 token | 启动 | `256` | 调大:索引变稀,短前缀更难命中;调小:请求变多,元数据涨 | `/status` 的 `chunk_size`;引擎也可发「问块大小」 |
| `--engine-type` · 要不要非前缀复用 | 启动 | `default` | `blend`:装非前缀模块;只开引擎驱动传输时启动失败 | 日志;启动报错 |
| `--supported-transfer-mode` · 谁负责搬砖 | 启动 | `lmcache_driven` | `engine_driven`:改走准备/提交;`auto`:两条都装 | 日志 `Supported transfer mode:` |
| `--max-workers` · 查找与搬砖的线程基数 | 启动 | `1` | 调高:查找和搬砖并行度升,CPU 占用升;可分别用 `--max-gpu-workers` / `--max-cpu-workers` 覆盖 | 线程名 |
| `--p2p-advertise-url` · 打开点对点 | 启动 | 关 | 打开后必须同时给协调器地址,且热层必须是一整块可登记内存 | 缺协调器时启动抛错 |
| `--coordinator-url` · 协调器地址 | 启动 | 空,不注册 | 有地址才会心跳;不管 KV | 协调器 `/instances` |
| `--instance-id` · 这台服务的稳定身份 | 启动 | 随机 UUID | 多机时要钉死,否则重启会被当成新成员 | 指标里的实例号 |

不带探活口的模块入口:`python3 -m lmcache.v1.multiprocess.server`,参数与上表请求口那一组相同,没有 `--http-port`。

**怎么看。** 先看两个进程还在不在:引擎一个,`lmcache server` 一个。再看探活口:`/healthcheck` 给探针,`/metrics` 看 `lmcache_mp_` 前缀(就在 `--http-port` 上,不要去找单独的 Prometheus 端口),`/status` 看块大小、哈希名、活跃会话。`POST /cache/clear` 清的是热层。请求口连不上时,先核 `--port` 是不是引擎连接器里写的那个,不要先去改探活口。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机在线,长上下文或多轮 | `lmcache server --l1-size-gb 20 --eviction-policy LRU`;引擎连本机请求口 | 用一份独立热层换「引擎崩了块还在」;代价是多一个进程,短请求上多一趟本机往返 |
| 同机多个引擎副本 | 服务只起一份,各引擎连同一个请求口 | 用共享热层换重复 prefill;代价是这份热层要按所有副本的并集来估 |
| 多机要互相读热层 | 先起 `lmcache coordinator`,每台服务加 `--p2p-advertise-url` 和 `--coordinator-url`;热层不要用 GDS 板或 Device-DAX | 用邻居的命中换本机重算;代价是必须有 RDMA 网,启动条件更严 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 服务起不来,报缺少热层大小或驱逐策略 | 启动命令有没有两项必填 | 补上,没有默认值 |
| 引擎报连不上缓存 | 引擎连的端口是不是请求口 `5555` | 不要连 `8080`;核 `--host` 是不是本机 |
| 探活 200,但完全不命中 | `/status` 的 `chunk_size` 是否和引擎侧一致 | 两边必须同一块大小 |
| 打开点对点直接退出 | 有没有协调器地址;热层是不是一整块内存 | 缺一就拒绝,不是运行时再降级 |
| `blend` 起不来 | 传输模式是不是只开了引擎驱动 | 改成缓存服务自己搬,或两条都装 |
| 指标口 404 | 是不是走了不带 HTTP 的模块入口 | 换 `lmcache server`;不要去找另一个 Prometheus 端口 |
| 引擎一重启命中全没 | 是不是走了进程内路径 | 改独立服务;进程内单例活在引擎进程里 |

## 六、常见误区

- **以为探活口就是引擎该连的口。** 因为推荐入口两个口在同一进程里。引擎连的是请求口,默认本机 5555;8080 只服务健康检查和指标。连错口,缓存服务看起来很健康,命中永远是零。
- **以为热层大小有默认。** 文档示例里常见 20 吉字节,那是示例不是默认。少写这一项,启动器拒绝,不会悄悄给一个值。
- **以为配了点对点广告就够了。** 代码在推荐入口里先检查协调器地址,没有就抛错。协调器还不存 KV,只回答成员名单。
- **以为进程内路径和独立服务共用同一份热层。** 两套存储代码。把引擎从进程内改成连独立服务,旧进程里的块不会出现在新服务里。
- **以为不带 HTTP 的模块入口和推荐入口是同一个东西。** 前者没有探活口,K8s 探针会一直失败,指标也没有。
- **以为非前缀复用只是加个开关。** 它是另一种引擎类型,并且拒绝「只开引擎驱动传输」。当成普通开关打开,得到的是启动失败,不是效果差一点。
- **以为独立进程就不碰 GPU 侧线程。** 默认传输下,搬砖线程池的基数是 `--max-workers`,默认 1。这不是「完全不占引擎的卡」,只是不跟推理抢同一个 Python 线程。
