# vLLM 15|多模态

图片、视频怎么在 token 序列里占住位置,预处理与编码各在哪里缓存、缓存多久,编码器又怎么和 decoder 分同一步的活。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

图文对话走的是无状态接口:第 5 轮提问时,客户端照样把第 1 轮那张图原样再发一遍。一张图要进语言模型得过两道工序:先在 CPU 上解码、缩放、切 patch,再过视觉编码器变成一串嵌入,每个嵌入在序列里占一个 token。以 Qwen2.5-VL 为例,每 28×28 个像素换 1 个 token:一张 1024×1024 的照片缩到 1036×1036,是 1369 个;默认的像素上限允许单张图到 16384 个;一段视频默认抽 32 帧,每帧 448×448 时是 4096 个。

照「来一张算一张」去做,坏的是三处:

- **带图请求的 TTFT。** 同一张图每轮都重新预处理、重新编码。预处理是纯 CPU 活,官方设计文档专门点名 Qwen2-VL 的处理器很慢;处理完的像素张量还要从 API 进程搬到 EngineCore 再搬上卡,1036×1036 那张按 32 位浮点约 26 MB。
- **同一步里所有请求的 TPOT。** 编码器在这一步前向之前、同一张卡上跑。它跑多久,这一步里在 decode 的请求就一起等多久,一步里编的图越多越长。
- **分块 prefill 切在图中间。** 视觉编码器是双向注意力,半张图编不出「一半的结果」;可 prefill 分块只按 token 数切,很容易切在一张 1369 个 token 的图中间。

## 二、解法:媒体在序列里占位,编码跟着占位区排

最天然的直觉:把每张图换成序列里一段长度刚好等于它嵌入个数的占位 token,之后 KV 块、调度、分块 prefill 都只看 token 位置,编码器的输出最后按位置盖回去。vLLM 就是这么做的,并在这条线上加了两级缓存和一道单独的闸:

![一条带 2 张图的请求走过三个进程:API 进程按内容算哈希、查只存键和大小的键表,命中只发哈希,再把图 A 展开成 256 个、图 B 展开成 1369 个占位 token;EngineCore 用同容量同顺序的值表补回张量,调度器同时守着 token 总额和编码预算两道闸;worker 上的编码器把不在缓存里的图整项编完,结果按哈希存进编码缓存,再切出本步要用的几行盖到占位位置上。下半是这条请求每步分到 1024 个 token 时的情形:第 1 步窗口只到图 B 的第 608 个占位 token,编码器却把 A、B 两项整项编完;第 2 步图 B 剩下的 761 行从编码缓存取,编码器不跑;编码预算或缓存装不下 B 时,第 1 步只排到 B 之前的 416 个 token](/opensource/vllm-lite/15a-placeholder-and-encoder-steps.svg)

**占位怎么展开。** 切词在前、多模态处理在后,处理器看不到原文。所以每个模型声明一组提示词改写规则:在切好的 token 里找到代表一张图的那个标记,换成 N 个占位 token,N 由处理器输出的网格尺寸算出;token 上找不到才退回文本上找。每个媒体项落成一条位置记录:从第几个 token 起、占多长、其中哪几位真正接嵌入。占位区里可以夹着起止标记这类普通 token,所以后面的编码缓存按嵌入个数记账,不按占位长度。

**第一级缓存:预处理结果,键和值分住两个进程。** 每个媒体项按内容算一个哈希,混进模型名和会改变处理结果的参数;调用方也可以给每项带一个稳定编号来代替内容哈希。API 进程只存键和大小,EngineCore 存处理好的张量,两边容量相同、插入与触碰的顺序相同,淘汰顺序也就相同,API 侧那份只是影子。命中时 API 进程既不跑处理器也不发像素,只发哈希,EngineCore 拿哈希补回张量。两边偶尔会漂,EngineCore 补不回时这条请求以可重试的错误结束,API 侧删掉这几个键,客户端重发一次就会带上数据。多开 API 进程、或多个数据并行副本共用一组 API 进程时,一对一的影子不成立,退化成每个 API 进程各存一份完整张量、每次照发。多卡时还能把张量放进共享内存,worker 直接读。

**第二级缓存:编码结果,放在 worker 显存里。** 调度器给一条请求定好这一步的 token 区间后,看哪些媒体项的占位区落进这个区间:编码缓存里已有的跳过;没有的整项交给编码器,哪怕本步只碰到它的一小段。编码在这一步前向之前做完,结果按哈希存进编码缓存,再按本步区间切出要用的几行,替换占位位置上的词嵌入。前缀缓存命中覆盖了整张图时,这张图不在窗口里,编码器不跑;前缀键里怎么混进图的内容见 04 章。

**编码预算和 token 总额是两道并列的闸。** 02 章的 token 总额管这一步算多少个 token;编码预算管这一步最多新编多少个嵌入,默认等于 token 总额,模型单个媒体项可能展开的最大个数更大时取后者。编码缓存的容量也按同样的规则定。编码不从 token 总额里扣。一张图编不下(预算用完,或缓存腾不出地方),这条请求本步只排到这张图之前的文本。前缀命中停在一张图中间时,这张图照样要整项编一遍;这时再编不下,这条请求本步一个 token 都不排,等下一步。

**编码结果留多久。** 一条请求的某个占位区全部算进 KV 之后,它放掉对这一项的引用;开了推测解码还要再多等草稿器往后看的那几位。没人引用的条目不立刻删,排进可回收队列,别的请求带同一张图来还能直接命中;只有新条目要地方时,才从最早变成可回收的删起,删掉的哈希随下一份调度结果发给 worker,显存这时才还回去。

为什么实际不吃亏:图变成了一段 token 位置,KV 块管理、前缀缓存、分块 prefill 都不用为它另开一条路,多模态的调度集中在调度器的一个函数里。同一张图第 2 次出现时,预处理与编码都能直接命中;前缀也还在的话,连这段 prefill 都省了。

## 三、代价

- **编码器还是和 decoder 挤在同一步。** 编码预算只给一步里编多少封了顶,不把编码挪出这一步;而且它不从 token 总额里扣,一步的工作量上限是 token 总额加一整份编码预算。图多的负载下,编图的那几步所有流的 TPOT 一起跳。真要拆开,得把编码器放到单独的实例上(12 章)。
- **满尺寸的媒体一步只能编一项。** 单项最大展开数超过 token 总额时,预算就等于这一项;一张满尺寸的图占满预算,同一步里别的图只能等下一步,带图请求的 TTFT 按图排队。
- **编码显存靠启动时估。** 编码缓存没有专门的显存池,就是一张按哈希存张量的表。启动时按预算把最大尺寸的假媒体编一遍、结果留在显存里,再跑语言模型的假前向,用这个峰值给 KV 让地方,估完清掉。有开关能跳过这一步来加快启动,代价是编码器的峰值得自己算,算少了第一批大图进来就 OOM。
- **预处理缓存按进程背。** 默认 4 GiB,占的是主存;影子模式下张量只在 EngineCore 一份,多开 API 进程后变成每个 API 进程各一份,而且每次都照发像素。
- **视频剪枝只省语言模型那一半。** 剪枝率在预处理时就按比例砍掉视频的占位个数(首帧全留),prefill 与 KV 跟着省;编码器仍把所有帧编完才挑留哪些,编码时间一点不少。留下哪些是编码之后才知道的,位置编码要在 worker 上重算。只有少数几个模型族实现了剪枝,别的模型设了剪枝率既不报错也不生效。
- **影子漂移会让一条请求失败一次。** 设计上当作可自愈的情况,但自愈靠客户端重试,不重试的调用方会看到一次服务端错误。

## 四、和 SGLang、TensorRT-LLM 比:编码器的活算不算进调度的账

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都让媒体在序列里占一段位置、编码结果按位置盖回去,分歧在谁来限制编码器一步干多少活,以及编码结果按什么记:

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 一步最多编多少 | 调度器里单独一份编码预算,与 token 总额并列;编不下就把这条请求截到图之前 | 没有这道闸,prefill 批里有几张图就编几张 | 接了按项调度的模型有单独的编码批大小与 token 上限,编码开销不进语言模型的 token 预算,一张图或一段视频整项占一个编码批位;其余模型在前向里顺带编,不设限 |
| 编码结果按什么记 | worker 显存里按内容哈希存,容量按嵌入个数计,默认等于 token 总额 | 按特征哈希存,默认 100 MB;同一个哈希也是前缀树里占位 token 的值 | 可选缓存,默认 128 MiB,按字节计,要模型报名才建 |
| 编码器录 CUDA graph | 默认关;打开后按几档 token 预算各录一张,运行时把一批图装进能装下的最小一档,装不下的走 eager | 默认关,一个环境变量打开 | 默认不设,标为原型,要模型自己实现录制与回放 |

vLLM 的取舍是把编码器当成调度器要记账的一种资源,和 token、KV 块并排;代价是记账只管「编多少」,不管「在哪编」,编码仍在这一步里同步做。SGLang 让编码结果和前缀树共用一个键,省掉一层记账,换来的是一步里编多少张图没有上限。预处理这一级也不同:vLLM 默认开 4 GiB 并在两个进程间做影子,SGLang 默认不开(只有 Kimi-K3 默认给 256 MiB),开了也只活在对外那个进程里。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。请求里能带的有三样:每个媒体项的稳定编号(聊天接口内容块里的 `uuid`,离线接口的 `multi_modal_uuids`),以及按请求覆盖处理器与媒体加载参数的 `mm_processor_kwargs`、`media_io_kwargs`;后两样会混进预处理缓存的键,改了就不再命中之前的缓存。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--max-num-batched-tokens` · 一步 token 总额,也是编码预算与编码缓存容量的底数 | 启动 | 见 02 章 | 调高:一步能多编几张图,编码缓存多留几项,满额的那一步更长;编码预算和编码缓存容量没有自己的参数,只能靠它和单项上限带 | 启动日志 `Encoder cache will be initialized with a budget of N tokens` |
| `--limit-mm-per-prompt` · 每条请求每种模态最多几项 | 启动,JSON | 每种模态 999 | 超了请求直接报错;某模态设 0:这个模态的编码器模块不加载,省显存,也不再参与算单项上限;可带宽高、帧数,启动时估显存用的假媒体按它造 | 报错 `At most N image(s) may be provided in one prompt` |
| `--mm-processor-cache-gb` · 预处理缓存大小 | 启动 | 4(GiB) | 调大:多轮、重复图命中更多,持有张量的进程多占主存;设 0:两级都关,只有前缀缓存也关时请求里的编号才被忽略 | 稳态日志 `MM cache hit rate`;`/metrics` 的 `vllm:mm_cache_hits` 除以 `vllm:mm_cache_queries` |
| `--mm-processor-cache-type` · 张量放 EngineCore 还是共享内存 | 启动 | `lru` | `shm`:API 进程把张量写进共享内存环形缓冲,多卡时各 worker 直接读,淘汰按先进先出;多开 API 进程时两种都退化成每个 API 进程一份 | — |

| `--mm-encoder-attn-backend` · 编码器用哪个注意力后端 | 启动 | 不设,按平台选(06 章) | 点名覆盖 | — |

**怎么看。** 一是启动日志:`Encoder cache will be initialized with a budget of N tokens, and profiled with K image items of the maximum feature size` 给出编码预算和启动估显存时用了几项最大尺寸的假媒体。二是稳态日志的 `MM cache hit rate` 与 `/metrics` 的 `vllm:mm_cache_hits`、`vllm:mm_cache_queries`,它们按媒体项计数,统计的是 API 侧的预处理缓存;编码缓存的命中没有任何指标。三是 `--enable-logging-iteration-details` 下每步的 `encoder inputs` 与 `encoder output embeddings`,能对出哪几步在编图、编了多少,和 TPOT 尖刺的时刻对照。四是告警 `Multi-modal cache miss for request`,出现一次就是一次影子漂移。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡 H100 跑 Qwen2.5-VL-7B,多轮图文客服,每轮带 1–4 张图、不收视频 | `vllm serve Qwen/Qwen2.5-VL-7B-Instruct --limit-mm-per-prompt '{"image": 4, "video": 0}' --mm-processor-kwargs '{"max_pixels": 1003520}'` | 单张图封顶 1280 个 token,一步 8192 的编码预算能编 6 张满尺寸图;视频不再参与算单项上限;代价是大于约 1 百万像素的图被缩小,细节丢 |
| 单机 4 卡 TP 4 的大视觉模型,视频理解为主 | `vllm serve <模型> -tp 4 --mm-processor-cache-type shm --mm-encoder-tp-mode data --media-io-kwargs '{"video": {"num_frames": 16}}'` | 预处理张量经共享内存直达各卡,编码按卡分数据;每张卡多放一份整编码器权重,KV 少一块;抽帧减半,快速动作可能漏掉 |
| H100 上批量给图打标,每张图只出现一次 | `vllm serve <模型> --mm-processor-cache-gb 0 --max-num-batched-tokens 16384` | 省下 4 GiB 主存和查表开销;一步能多编一倍的图,满额那一步更长;重复图再也命中不了预处理缓存 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 带图请求 TTFT 高,GPU 不满 | API 进程 CPU;`MM cache hit rate` | 多轮场景命中率低就调大 `--mm-processor-cache-gb`;API 进程 CPU 满就多开 API 进程,同时调低 `VLLM_MEDIA_LOADING_THREAD_COUNT`;模型支持就留着 `--mm-device-do-normalize` |
| 图多时所有流的 TPOT 一阵一阵地跳 | `--enable-logging-iteration-details` 下跳的那几步 `encoder output embeddings` 是多少 | 压像素上限或抽帧数;调小 `--max-num-batched-tokens` 连带压编码预算;还不够就拆出编码器实例(12 章) |
| 请求报 `exceeds the pre-allocated encoder cache size` | 这一项展开成多少个嵌入,请求有没有用处理器参数把像素上限调高 | 调大 `--max-num-batched-tokens`,或在请求里压像素、抽帧;报错里让调 `--limit-mm-per-prompt` 不对症 |
| 启动报 `Chunked MM input disabled but max_tokens_per_mm_item` | 是不是被强制成了不许切开 | 把 `--max-num-batched-tokens` 调到单项上限以上 |
| 偶发一次 500,日志有 `Multi-modal cache miss for request` | 影子漂移 | 客户端重试即可;频繁出现就用 `--mm-processor-cache-type shm` 或加大缓存 |
| 大图一来就 OOM | 是否开了 `--skip-mm-profiling`;请求级处理器参数是否把像素上限调得比启动时高 | 去掉跳过估算;请求里别放大像素上限;或调低 `--gpu-memory-utilization` 给编码器留余量 |
| 设了 `--video-pruning-rate`,视频请求的 prompt token 数没变 | 模型是否实现了剪枝 | 换支持的模型,或改用 `--media-io-kwargs` 减帧 |
| 图换了,回答还像旧图 | 请求是否带了 `uuid`,是不是拿 URL 当编号 | 编号要随内容变;不能保证就去掉编号,让它按内容算哈希 |

## 六、常见误区

- **以为报错里说的 `--limit-mm-per-prompt` 能把编码缓存调大。** 单项超出编码缓存时,错误信息确实这么建议。可编码缓存的容量等于 token 总额与单项上限取大,数量上限只管每条请求几项;真要装下更大的单项,得调 `--max-num-batched-tokens`,或者把这一项压小。
- **以为图片的 token 从 token 总额里扣。** 按 02 章的直觉,一步算多少全由总额定,于是以为编码也在里面。实际上编码预算和总额是两道并列的闸,一步可以同时满额 prefill 8192 个 token、再编 8192 个嵌入;想压编图那几步的时长,调小总额才会连带压住编码。
- **以为 `uuid` 只是给日志看的标签。** 官方示例直接拿图片 URL 当编号。编号一给,就顶替图片内容参与哈希,预处理缓存、编码缓存、前缀缓存认的都是它;同一个 URL 背后的图换了,三级缓存照样拿旧图的结果,不报任何错。
- **以为分块 prefill 会把一张大图分几次编码。** 分块只切 decoder 那一侧;编码器在这张图第一次被碰到的那一步整项编完,激活峰值由这一步里所有被碰到的整张图决定。想压编码器峰值,要压单项大小或编码预算,调小分块没用。
- **以为 `MM cache hit rate` 是编码缓存的命中率。** 名字里只说了多模态缓存。它统计的是 API 侧预处理缓存的命中,编码缓存命中与否没有指标;两者还可能一高一低,比如预处理命中了,编码结果早被挤掉,编码器照样要跑。
- **以为编码结果算完用完就释放。** 看到显存里编码缓存一直不降,容易怀疑泄漏。引用清零的条目只是变成可回收,留在显存里等下一张同样的图;只有新条目要地方时才按最早可回收的先删,这是有意的。
- **以为多开 API 进程只是多吃几个 CPU 核。** 多开之后影子缓存关掉,每个 API 进程各背一份 4 GiB 的完整预处理缓存、每次照发像素,每个进程还各带 8 个媒体线程;CPU 本来就紧的机器上,多开反而可能更慢。
- **以为设了视频剪枝率编码就变快。** 剪枝省的是语言模型那一侧的 prefill 与 KV,编码器照样把每一帧都编完;模型没实现剪枝时,这个参数连语言模型那一侧也不省,而且不报错。
