# vLLM 16|LoRA

一份底座权重要同时伺候许多个微调版本,每个版本只多一对瘦矩阵,怎么做到同一批里各算各的、又不为每个版本多占一份显存。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

多租户服务里,每个业务方拿同一个底座训出自己的适配器(LoRA 本身是什么见知识库「LoRA」一篇)。最省事的两条路都会坏:

**每个版本起一份副本,坏的是并发。** 以 Qwen3-8B 为例,BF16 权重约 16.4 GB,每 token 的 KV 约 144 KB。H100 80 GB 按默认显存占比,一份权重之外约 57 GB 能给 KV,装得下约 39 万个 token;同一张卡上为 4 个版本各起一份,权重吃掉 65.6 GB,每份只剩约 2 GB 的 KV,约 1.4 万个 token,一条长上下文就满了。流量还不均:冷门版本的副本闲着,热门版本的副本排着队,显存却一样多。

**把适配器合进权重,坏的是批。** 合并后一个权重张量只能是一个版本,同一批里挂着两个不同适配器的请求就没法一起算;要么按适配器拆批、每拆一次重写一遍权重,要么还是回到副本。

所以只能让底座一份、整批一起过,再给每个 token 补上它自己那份低秩增量。可这样一来又有两件事会坏:同一批里混的适配器越多,每层要多做的小矩阵乘越碎,吞吐往下掉;GPU 上同时能摆的适配器种类有上限,顶满之后,点名别的适配器的请求这一步进不来,某个适配器就一直排不上。

## 二、解法:适配器按槽位堆成大张量,token 只带槽号

最天然的直觉:每个能挂的线性层旁边另开一条小路,底座照常把整批一次算完,小路按 token 各补各的增量。难处只剩一个:同一批 token 要乘的 A、B 各不相同。vLLM 把 GPU 上的适配器按槽位堆成一块大张量,token 不认适配器、只认槽号,kernel 按槽号分段取用:

![vLLM 一步前向怎么同时算 3 个适配器:4 条请求共 10 个 token,先给每个 token 标上它那条请求的槽号,不挂适配器的标成无;再按槽号稳定排序,同槽的连成一段,不挂的那段跳过;每段先读 A 大张量里自己那一格把 4096 维缩到秩 16,再读 B 大张量里同一格扩回 4096 并加到底座输出上;秩只有 8 的适配器也按秩上限 16 占一整格、多出来的是补的零;右边是 CPU 缓存,本步新点名的适配器从这里拷进槽 2,挤掉最久没用的那个,被挤掉的仍留在 CPU 缓存里](/opensource/vllm-lite/16a-slot-segmented-lora.svg)

**槽位是启动时开好的几格。** 每个能挂的层按「槽数 × 秩上限」开一对全零的大张量,默认只有 1 格。装一个适配器就是把它的 A、B 拷进某一格,秩不到上限的部分留零。不挂适配器的 token 记成一个负数,池子里不给它留格。

**GPU 格子后面还有一级 CPU 缓存。** 适配器先从磁盘读进锁页内存,满了按最久未用整个丢掉;GPU 格子不够时同样挤掉最久没用的一格,被挤的还留在 CPU 缓存里。换入发生在 worker 准备这一步输入时:本步点名的适配器不在 GPU 就从 CPU 拷进一格,CPU 里也没有就当场读盘。

**调度器保证格子够用。** 一步里不同适配器的种类数不能超过槽数。运行队列里的请求已经占满了种类,等待队列里点名别的适配器的请求这一步就被跳过,下一步最先再试它,期间算进被暂时挡住的那一类等待(02 章)。

**一次前向怎么算完。** 带适配器的线性层里,底座的矩阵乘照常走,然后两个 Triton kernel 各发一次:先按段把输入乘 A、缩到秩那么宽,再按段乘 B、扩回来加到输出上。kernel 的第三维固定开「槽数 + 1」格,一格对应一段,读到不挂的那段或空位就当场退出;整批都不挂时连 kernel 都不下发。缩放系数在装载时已经乘进 B,运行时不再乘。这套分段做法出自 Punica(arXiv 2310.18547)。

**哪些层能挂。** 所有线性层(注意力的 QKV 与输出投影、MLP 的各段)、词嵌入与输出头,以及 MoE 的专家层;池化模型的分类头整层替换。MoE 的 A、B 多一维专家,按「槽 × 专家」堆;token 路由到专家后,按「适配器、专家」两个键对齐分块,在专家计算的流程里做同样的一缩一扩。专家并行本身见 11 章,这一层只收全收集加规约分散那一种通信方式。多模态模型默认只在语言模型那一截挂,视觉塔与连接层要另开一个实验开关,只有少数模型支持(多模态本身见 15 章)。

**不重启也能换。** 打开一个环境变量后,可以在运行时按名字加路径装一个适配器,或者用同一个名字覆盖成新版本;还可以挂解析器插件:请求点了一个没见过的名字,就按名字去本地目录或 Hugging Face 仓库里找,找到先装上,再服务这条请求。

为什么实际不吃亏:底座仍是一份、整批一次;秩 16 时,这条小路每层的乘加次数只有底座的约 0.63%,一步只多两次按段下发,次数不随请求数涨。GPU 上摆几个适配器,显存就按几格算,不为历史上出现过的每个版本买单。

## 三、代价

**显存按格买断,按秩上限补齐。** Qwen3-8B 所有能挂的层都挂上时,每格每 1 个秩约 6.08 MB:秩上限 16 时每格约 97 MB,秩上限 64、8 格约 3.1 GB,相当于约 2.1 万个 token 的 KV。这块在测 KV 预算之前就分好,算在模型占用里,KV 池跟着变小。秩 8 的适配器装进上限 64 的格子,显存和乘法次数都按 64 算。

**批的组成一变,就多一段 CPU 活和一次同步。** 每个 token 的槽号表在 CPU 上逐个 token 展开,拷到 GPU 排序、分段,中间要读回「有没有 token 挂适配器」和段数,是一次 GPU 到 CPU 的同步,源码里留着待消掉的注释。这几处都包在放行块里,07 章那个抓同步的检查不会报它们。

**kernel 按整批行数开格子。** 每一段都按整批 token 数开线程块,只有落在自己那段的真干活。源码注释自认:只有少数 token 挂适配器时这样开很浪费。

**换入挡在前向前面。** CPU 缓存默认和槽数一样大。轮换的适配器多于槽数时,每次换入都当场读盘,这一步所有请求一起等。

**冷门适配器可以一直等。** 热门适配器只要还有一条在跑,它的新请求就照收;冷门的要等到某一种在跑的请求全部结束才有格子。调度器里没有为它腾位置的机制。

**CUDA graph 的份数翻倍。** 捕图时有适配器和没适配器各录一份;打开按实际种类数分档录图,份数按 2 的幂再多出几档,启动更久(通用机制见 08 章)。

## 四、和 SGLang、TensorRT-LLM 比:适配器的显存按格买断还是按页记账

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都是底座一份、请求点名适配器,分歧在显存怎么给、装不下时怎么办、适配器在主机上留多少。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| GPU 上给适配器留多少显存 | 格数 × 秩上限,每格按上限补齐,启动即占 | 同样按「每批种类上限 × 秩上限」买断 | 按页记账,一个适配器占几页随它实际的秩走;池子默认取装完模型后空闲显存的 2% |
| 一步最多几种 | 格数,默认 1;不挂适配器的 token 不占格 | 默认 8,不挂的请求自己也占一格 | 不限种类,新名字要加页,页预算是上限 |
| 装不下时 | 跳过,留在等待队列 | 同样跳过;另有默认关的排空器,让热门的跑完腾格 | 跳过,留在队列 |
| 主机内存里留多少 | 默认等于格数,被挤掉的再点名要读盘 | 默认不限 | 默认 1 GB |
| 缩放系数 | 装载时乘进 B | 每格存一个系数,kernel 里乘 | 装载时乘进 B |

vLLM 的取舍是格子少而规整:每格一样大,kernel 按槽号直接寻址,代价是秩不齐时补零白占,主机侧默认也不留余量。SGLang 默认格子多、不设主机上限,换来少读盘;TensorRT-LLM 按实际秩分页,显存不为补零买单,但要多一层页管理。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。请求级只有一项:OpenAI 接口的 `model` 字段填适配器名,离线接口传 `LoRARequest`,一条请求只能挂 1 个。运行时能改的是适配器集合本身:打开 `VLLM_ALLOW_RUNTIME_LORA_UPDATING` 后,`/v1/load_lora_adapter` 按 `lora_name`、`lora_path` 装,带 `load_inplace` 同名覆盖,`/v1/unload_lora_adapter` 按名字卸;槽数、秩上限、目标层都改不了,超了只能重启。接口的 HTTP 层细节见 19 章。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--enable-lora` · 打开 LoRA | 启动 | 关 | 开:能挂的层换成带槽位的包装,显存按下面三项买断;不开时请求点适配器名报模型不存在 | 启动日志 `Using PunicaWrapperGPU.` |
| `--max-loras` · GPU 槽数,也是一步最多几种适配器 | 启动 | 1 | 调高:同一步能混的种类多,被挡的请求少;每格显存线性加,kernel 第三维跟着变宽 | `vllm:lora_requests_info` 的 `running_lora_adapters` 种类数贴着 `max_lora` 标签 |
| `--max-lora-rank` · 秩上限,每格按它补齐 | 启动 | 16;只能取 1、8、16、32、64、128、256、320、512 | 调高:能装更大秩的适配器;每格显存与每步乘法次数都按它算 | 装载失败报 `LoRA rank … is greater than max_lora_rank` |
| `--max-cpu-loras` · CPU 缓存上限 | 启动 | 不设时等于 `--max-loras`,设了不能比它小 | 调高:被挤出 GPU 的适配器留在锁页内存,再点名不读盘;每份按真实秩占主机内存 | 轮换时 step 周期性变慢 |
| `--lora-dtype` · 适配器精度 | 启动 | `auto`,跟底座 | 只能是 `float16` 或 `bfloat16`,kernel 只收这两种 | — |
| `--lora-target-modules` · 只在这些层后缀上挂 | 启动 | 不设:所有能挂的层 | 收窄:显存与每层两次小乘法都省;适配器里其他层的权重被静默丢掉 | 一层都没挂上时 debug 日志提示检查这个参数 |
| `--fully-sharded-loras` · TP 下把 A、B 两边都切 | 启动 | 关(默认只切一半) | 开:每卡显存与算量随 TP 变小,每层多一次秩那么宽的通信;长序列、大秩、大 TP 时可能更快;和专家并行下的 MoE LoRA 互斥 | — |
| `--specialize-active-lora` · 按实际种类数分档 | 启动 | 关 | 开:kernel 第三维按实际种类向上取到 2 的幂,少开空格子;图的份数更多,启动更久、多占显存 | 捕图耗时 |
| `--lora-modules` · 启动时装的适配器 | 启动 | 无 | `name=path`,或带 `base_model_name` 的 JSON;装不上启动即失败 | `/v1/models` 里带 `parent` 的条目 |
| `--default-mm-loras` · 按模态自动挂 | 启动 | 无 | 在线只在多模态模型的聊天接口生效;一条请求命中多个模态就一个都不挂 | — |
| `--enable-tower-connector-lora` · 视觉塔与连接层也挂 | 启动 | 关 | 开:实验性,只有实现了对应计数函数的模型生效;编码缓存按适配器名分开存 | 启动告警 `LoRA for the tower and connector of multimodal models is experimental` |
| `--enable-mixed-moe-lora-format` · MoE 的两种磁盘格式混着服务 | 启动 | 关 | 开:统一用按专家拆开的包装,按请求里的格式标记转换 | — |
| `--enable-moe-shared-loras` · MoE 适配器的外侧矩阵各专家共用 | 启动 | 关 | 开:按共用布局装载,省显存;适配器得是这种布局训的 | — |
| `--compilation-config` 里的 `cudagraph_specialize_lora` · 有无适配器各录一份图 | JSON | 开 | 在 V2 下关掉照样录两份,见误区 | — |
| `VLLM_ALLOW_RUNTIME_LORA_UPDATING` · 放行运行时装卸与解析器 | 环境变量 | 关 | 开:挂上装卸端点,请求点到没见过的名字时走解析器;启动告警只该在本地开发用;与多个 API 进程互斥 | 启动告警 `LoRA dynamic loading & unloading is enabled` |
| `VLLM_LORA_RESOLVER_CACHE_DIR` · 本地目录解析器 | 环境变量 | 无 | 设了就注册;按 `目录/适配器名` 找,要求 `adapter_config.json` 的底座名和服务的模型名逐字相同 | 日志 `Resolved and loaded LoRA adapter` |
| `VLLM_LORA_RESOLVER_HF_REPO_LIST` · Hugging Face 仓库解析器 | 环境变量 | 无 | 还得在 `VLLM_PLUGINS` 里写上 `lora_hf_hub_resolver` 才注册,否则只告警 | 同上 |
| `VLLM_LORA_ENABLE_DUAL_STREAM` · 底座与 LoRA 分两条流重叠 | 环境变量 | 0 | 设 1:两条流并行,SM90 以上顺带开 PDL;只在 CUDA 上;和全切分同开时自动关掉 | — |
| `VLLM_LORA_DISABLE_PDL` · 关 PDL | 环境变量 | 0 | 设 1:SM100 上 PDL 让 Triton 编译失败时用 | — |

**怎么看。** 一是日志:启动时 `Using PunicaWrapperGPU.` 说明 LoRA 开了;MoE 模型打 `Using TRITON Unquantized MoE LoRA backend` 或 `TrtLlmBf16LoRAExperts`,说明专家层走哪条 LoRA kernel;热加载成功打 `Loaded new LoRA adapter: name …`;每 10 秒那行稳态日志里的 `Deferred` 含被 LoRA 格数挡住的请求(02 章)。二是指标:`vllm:lora_requests_info` 的值是时间戳,信息在标签里,`running_lora_adapters` 与 `waiting_lora_adapters` 列出适配器名,`max_lora` 是格数;数据并行下它会告警可能不准。三是接口:`/v1/models` 列出底座和全部已登记的适配器。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡 H100,Qwen3-8B,12 个秩 16 的业务适配器,流量偏斜 | `vllm serve Qwen/Qwen3-8B --enable-lora --max-loras 4 --max-lora-rank 16 --max-cpu-loras 32 --lora-modules a=/adapters/a b=/adapters/b …` | 4 格约 389 MB 显存(约 2600 个 token 的 KV)换一步能混 4 种;32 份 CPU 缓存约 3.1 GB 锁页内存换轮换时不读盘 |
| 训练侧不停推新版本(RL、在线迭代),同名覆盖 | `VLLM_ALLOW_RUNTIME_LORA_UPDATING=1 vllm serve <模型> --enable-lora --max-loras 2 --max-lora-rank 64`,更新时 POST `/v1/load_lora_adapter` 带 `load_inplace` | 秩 64 两格换能装大秩;只能 1 个 API 进程;覆盖后前缀缓存不会自动失效,见误区 |
| 长尾适配器很多,按名字自动拉取 | `VLLM_ALLOW_RUNTIME_LORA_UPDATING=1 VLLM_LORA_RESOLVER_CACHE_DIR=/adapters vllm serve <模型> --enable-lora --max-loras 8 --max-cpu-loras 64 --specialize-active-lora` | 每个名字第一次被点时这条请求等读盘;分档录图换种类少时的 kernel 开销,启动更久 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 某个适配器的请求迟迟不出首 token,GPU 却不忙 | `Deferred` 是否不为 0;`running_lora_adapters` 的种类数是否贴着 `max_lora` | 调大 `--max-loras`;热门适配器长期占格时冷门的会一直等,只能加格或按适配器分流 |
| 混了适配器之后吞吐比纯底座掉得多 | 秩上限是否远大于实际最大秩;是否所有层都挂了 | 把 `--max-lora-rank` 降到实际最大;`--lora-target-modules` 收窄;试 `--specialize-active-lora` |
| 适配器轮换时每隔一阵整批卡一下 | 在用的适配器数是否多于 CPU 缓存(默认等于格数) | 调大 `--max-cpu-loras` |
| 开 LoRA 后启动日志里的 KV 容量少了一大截 | 格数 × 秩上限 × 层数 | 减 `--max-loras` 或 `--max-lora-rank`,或收窄目标层 |
| 调 `/v1/load_lora_adapter` 返回 404 | 是否设了 `VLLM_ALLOW_RUNTIME_LORA_UPDATING` | 设上重启;端点只在它打开时注册 |
| 启动报 `VLLM_ALLOW_RUNTIME_LORA_UPDATING cannot be used with api_server_count > 1` | API 进程数,数据并行默认按副本数多开 | 显式设 `--api-server-count 1` |
| 目录里明明有适配器,请求报 `The model … does not exist` | `adapter_config.json` 里 `peft_type` 是否是 `LORA`,`base_model_name_or_path` 是否和服务的模型名逐字相同 | 改配置,或起服务时用同一个模型名 |
| 同名覆盖后输出还像旧版本 | 前缀缓存是否命中了旧 KV | 覆盖后调一次 `/reset_prefix_cache`(要 `VLLM_SERVER_DEV_MODE=1`) |
| MoE 模型开 LoRA 启动报专家 kernel 不支持 LoRA | 专家后端与量化方案 | 未量化会自动走 Triton 或 FlashInfer 的 TRT-LLM 路径;量化的看 13 章能否换到支持 LoRA 的 kernel |
| 多模态模型挂了适配器,看图的能力没变 | 启动日志有没有 `supports adding LoRA to the tower modules` | 开 `--enable-tower-connector-lora`;没有这行说明模型不支持 |

## 六、常见误区

- **以为 `--lora-modules` 里列的适配器都常驻内存。** 名字列在启动参数里,看起来就像「都装好了」。实际 CPU 缓存默认和格数一样大,默认格数又是 1:列了 10 个,内存里只留最后装的那 1 个,其余每次被点名都要重新读盘。适配器一多,先把 `--max-cpu-loras` 设到常用的个数。
- **以为 `--max-loras` 是能服务的适配器总数。** 名字像总量,于是有人设成 64 想「服务 64 个」,显存按 64 格买断;也有人留默认 1,以为只能挂 1 个。它是一步里最多混几种、也是 GPU 格数。能服务多少个由登记和 CPU 缓存决定,格数只决定同一步能混几种。
- **以为卸载接口会释放显存和内存。** 官方文档写的是「卸载」,返回也是成功。实际 `/v1/unload_lora_adapter` 只把名字从 API 进程的登记表里删掉,不通知引擎;适配器还占着 GPU 格和 CPU 缓存,直到被最久未用挤掉。想腾地方,只能靠别的适配器把它挤出去,或者重启。
- **以为同名覆盖后新请求一定用新权重算。** `load_inplace` 确实重读了权重,但前缀缓存的键里混的是适配器名,不是版本;名字没变,新请求照样命中旧权重算出来的 KV 块(04 章)。RL 里每轮覆盖一次的,覆盖后要清一次前缀缓存。
- **以为 `--max-lora-rank` 设大一点只是保险。** 文档里它只是个上限,看着没有代价。每一格都按它开、kernel 也按它乘:秩 8 的适配器在上限 256 的池子里,显存和乘法都是 32 倍。设成实际用到的最大秩。
- **以为关掉 `cudagraph_specialize_lora` 能省一半捕图时间。** 它的说明写着关掉后只录带 LoRA 的那份图。那是旧的 V1 ModelRunner 的行为;默认的 V2 不管开关,都是有适配器、没适配器各录一份,关了什么都不省。
- **以为多模态模型挂上适配器,整个模型都生效。** 适配器训的时候常常连视觉塔一起训了。vLLM 默认只在语言模型那一截挂,视觉塔里的层直接跳过,每层打一行告警;要开实验开关,而且只有少数模型支持。开了之后编码缓存按适配器名分开,同一张图换个适配器就要重新编码。
- **以为解析器找不到适配器是目录配错了。** 目录对、文件也在,照样 404。文件系统解析器还要求 `adapter_config.json` 的 `base_model_name_or_path` 和服务的模型名逐字相同:训练时写的是本地路径、服务时用的是 Hugging Face 名字,就对不上,而且不打任何日志。
