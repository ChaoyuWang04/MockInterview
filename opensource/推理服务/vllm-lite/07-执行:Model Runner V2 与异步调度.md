# vLLM 07|执行:Model Runner V2 与异步调度

GPU 算完一步到下一步开始之间,CPU 要收结果、排下一步、备好输入;怎么把这段时间从 GPU 的时间轴上拿掉,而 CPU 又不必先知道上一步采出了什么。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

decode 的一步里,CPU 有三件事要在 GPU 开始下一步之前做完:把上一步采出的 token 拷回来,交给调度器判停和记账;调度器排出下一步谁上、各算几个 token、补哪几块;ModelRunner 把这份决定翻成前向要的张量,也就是每条请求的输入 token、位置、块表、注意力的起止下标和采样参数。三件事串在 GPU 的两步之间,这段时间 GPU 空转。

坏的是**小批 decode 的 GPU 利用率**。批越小、模型越小,一步前向越短;CPU 这三件事的耗时却不跟着缩,空档在一步里的占比就越大。表现是 TPOT 降不下去、GPU 利用率上不去,换一张更快的卡也没用,多出来的算力全在等 CPU。

把两边错开是天然的想法,但马上撞上两个难点。一是依赖:第 N+1 步的输入正是第 N 步刚采出的 token,CPU 排第 N+1 步时它还在 GPU 上没出来。二是缓冲打架:CPU 为下一步改写一块缓冲时,GPU 可能还在从这块缓冲读上一步的数据。V1 的 ModelRunner 最初没按错开来设计:它直接把一张常驻的「持久批」当成前向和采样的输入,请求进出时要整表挪行,还得另存一份请求状态作备份,防止行被覆盖;为了不让 CPU 改到 GPU 正在读的内存,又在准备输入的关键段外面套了一道栅栏。官方设计文档的原话是,这套账在异步调度下更难维护。

## 二、解法:调度器只数占位,token 在 GPU 上交接

最天然的直觉:排下一步时不等这一步的结果,反正这一步的 token 已经在 GPU 上,下一步前向直接从显存里拿。vLLM 分两层做:EngineCore 这一层把调度与执行错开一步;Model Runner V2 这一层把执行做成「CPU 只往 GPU 流里排活,从不停下来等 GPU」。

![上下两条时间轴对照:上半是异步调度关掉时,CPU 依次调度、准备输入,GPU 算一步,CPU 再收结果,GPU 每两步之间空出一段红色的空等,同样长的时间只跑了 4 步;下半是默认的异步调度,CPU 排好第 2 步、备好输入后才去收第 1 步的结果,GPU 7 步背靠背没有空档;图中标出排第 2 步时请求 r 只记 1 个占位、第 1 步采样把 token 写进 r 在持久状态表里的行并由第 2 步前向直接读出、第 1 步结果经副流拷回后调度器才用真值换掉占位并判结束,底部说明结束和被抢占的请求那一步迟到的输出怎么处理](/opensource/vllm-lite/07a-async-step-timeline.svg)

**错开一步。** EngineCore 的主循环带一个批队列,开异步调度时深度为 2(流水线并行时是段数加 1,见 10 章)。每转一圈先排一步新的发下去,worker 把活排进 GPU 流就返回;队列满了,才阻塞等最早那一步的结果、拿它更新调度器。于是 GPU 算第 N 步时,第 N+1 步已经排好、输入已经备好,在 GPU 流里排着队。

**占位只是一个计数。** 调度器排第 N+1 步要做的决定,是这条请求算几个 token、要不要新块,只看 token 的个数,不看值。所以它给每条排上 decode 的请求记「多了 1 个占位」(开推测解码时再加上草稿数,09 章),已算长度照常往前推。第 N 步的结果回来时,调度器把真 token 追加进请求、占位数减掉同样多,这一刻才判结束符与停止条件。值从来不经 CPU 转手:第 N 步采样完,GPU 把每条请求最后一个 token 写进它在状态表里的那一行;第 N+1 步前向开头,一个 kernel 按本步的请求顺序把这些行读出来,填进输入。

**迟到的输出。** 第 N+1 步发出时,第 N 步里有的请求其实已经采到了结束符。它在第 N+1 步照样多算 1 个 token,结果回来时调度器发现请求已结束,整行跳过。被抢占的请求更细一点:块已收回、已算长度清零,但在路上那一步的 token 是在旧 KV 上算对的,回来照样记进请求,只是不再动那些清零过的计数;这份输出回来之前,请求不准重新进门,免得重算时把同一个位置再采一遍。PD 分离里负责交出 KV 的那一端不能让被抢占的请求带着已收回的块去交付,这份输出改为直接丢弃(12 章)。

**Model Runner V2:状态常驻,每步按序收集。** V2 给每条请求分一个固定行号,从进来用到结束或被抢占;抢占当作结束处理,回来时按新请求重新登记,不再需要 V1 那份备份。行上挂着这条请求的全部状态:已算长度、最后一个采样 token、块表、采样参数、完整的 token 历史。前向的输入不再是这张表本身,而是每步按本步顺序从表里收集出来的一份新张量;顺序由注意力后端的要求定,decode 在前、短追加居中、prefill 在后。收集在 GPU 上并行做,请求进出只是占一行、放一行,不用挪别人。

CPU 对状态表的改动先记成一串增量,每步打包成一段连续缓冲拷上去,再用一个 kernel 写进 GPU 上的表;块表和已算长度都这样改。token 历史表按「最大并发数 × 最大上下文」开,太大,放在 GPU 能直接寻址的锁页主存里,prefill 时由 kernel 直接去读(UVA)。CPU 递给 GPU 的那些小缓冲按在路上的批数轮换,CPU 写的永远是 GPU 已经读完的那一份,栅栏就不需要了。采样结果在一条副流上拷回 CPU,拷完记一个事件,收结果的一方只等这个事件,不等整条流。

**V1 什么时候还在用。** 默认用 V2;配置里有 V2 还没做的特性时自动退回 V1,只打一行告警,常见的是几种推测解码方法、双批重叠(11 章)、弹性专家并行和原生 torch.compile 模式,完整清单在第五节。反过来,流水线并行配异步调度、预填充上下文并行、HiSparse、水印只有 V2 做了。worker 起来时按这个判断实例化其中一个,之后每步都是同样两次调用:先前向,后采样。拆成两次,是为了让调度器趁前向在跑时去算结构化输出的掩码,采样时再交进来(14 章)。

为什么这样实际不吃亏:CPU 的活一件没少,只是挪进了 GPU 正忙的时间里;只要收结果、调度、准备输入加起来比一步前向短,GPU 就一直是满的。错开的全部代价是「晚一步知道 token 的值」,而调度决定本来就只需要个数。长度上限这类事先就知道的停止条件,调度器能算出来,会直接不排那多余的一步。

## 三、代价

**碰到结束符的请求多算一步。** 靠结束符或停止 token 停下的请求,每条一生白算 1 个 token,白占这 1 个位置的 KV;停止字符串还要更晚,它在 API 进程才判(01 章)。

**块要按在路上的批来留。** 排第 N+1 步时第 N 步还没结清,滑动窗口层按「在路上的批数 × 每步 token 上限」多留块(03 章)。流水线并行时在路上的批更多,这一项跟着涨。

**被抢占的请求回来得晚一点。** 它要等在路上那一步的输出回来才能重新进门,最多等批队列深度那么多步。

**结构化输出只错开前向,不错开采样。** 下一步的掩码取决于上一步的 token,所以只要有带文法约束的请求在 decode,那一步的采样就要等上一步的结果回到 CPU、文法往前推一格、掩码算好才发出去;前向照样提前排在 GPU 上。

**有几种情况直接关掉。** 草稿在 CPU 上生成的推测解码方法、池化模型(源码注释说异步反而拖慢它)、不支持异步的执行器后端、V1 配流水线并行、ROCm 上 DeepEP 高吞吐模式配双批重叠(注释说会让结果出错),默认都自动关,只打一行日志;显式要求打开却撞上池化以外的这几种,启动直接报错。

**V1 下错开得不彻底。** V1 在 CPU 那份 token 表里先填一个占位值,真值等采样前需要时才补:请求带了惩罚、坏词,或挂了要看已生成 token 的 logits 处理器,每步采样前都要等上一步的 token 拷回 CPU。V2 把惩罚要的 token 计数放在 GPU 上随采样一起更新,没有这一等。

**两套 ModelRunner 并存。** V2 的设计文档自己写着还没做全、测得不够充分;哪一套在跑取决于配置组合,同一份启动参数多加一个特性,就可能静默换成 V1,性能特征跟着变。另外 token 历史表占锁页主存:最大并发 1024、上下文 131072 时是 512 MiB,随这两个数线性涨。

## 四、和 SGLang、TensorRT-LLM 比:上一步的 token 怎么交给下一步

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都把 CPU 收尾藏进 GPU 的下一步里,也都绕开了「CPU 得先知道 token」这件事,分歧在 token 存在哪、流水线并行时还错不错开。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| CPU 收尾与下一步前向错不错开 | 默认错开;不兼容的配置自动关 | 默认错开 | 默认错开 |
| 下一步的输入 token 从哪来 | 每条请求在状态表里有固定一行,采样写进去,下一步由 GPU 按本步顺序读出 | 按请求池槽位编号的一块显存缓冲,前向写,下一步读 | 上一步采样结果的设备张量直接交给下一步前向 |
| 流水线并行时 | Model Runner V2 照样错开,在路上的批数是段数加 1;V1 下自动关 | 关掉错开 | 换一条专门的流水线循环,它本身就跨循环处理上一批 |

vLLM 的取舍是把「错开一步」和「流水线填满」做成同一个批队列,只是深度不同,所以流水线并行不必在错开和不错开之间二选一。代价是这条路只在 V2 上走得通,V1 与 V2 要一直并存到 V2 补齐。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。没有哪一项能按请求覆盖。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--async-scheduling` / `--no-async-scheduling` · 调度与执行错开一步 | 启动 | 不设:自动开;池化模型、`ngram`/`suffix`/`medusa`/`mlp_speculator`/`custom_class` 推测解码、`disable_padded_drafter_batch`、执行器后端不支持、V1 配 PP、ROCm 上 `deepep_high_throughput` 配 DBO 时自动关 | 关:GPU 每两步之间空等,小批 decode 的吞吐降、TPOT 升;显式开而撞上池化以外的任一项:启动报错 | 以 `Async scheduling` 开头、含 `disabled` 的告警(池化模型只打 debug 日志);debug 日志 `Batch queue is enabled with size 2` |
| `VLLM_USE_V2_MODEL_RUNNER` · 用哪一套 ModelRunner | 环境变量 | 不设:能用 V2 就用 V2,撞上 V2 不支持的特性退回 V1 并告警 | 设 1:强制 V2,不支持的特性启动报错,DBO 也会改走 V2(未设时 DBO 一律退回 V1);设 0:强制 V1,PCP、PP 配异步、DSpark、自适应验证等 V1 不支持的启动报错;开 HiSparse 时设 0 报错,开水印时 0 被忽略 | 日志 `Using V2 Model Runner`;告警 `Model Runner V2 does not yet support ...; using the V1 model runner instead` |
| `VLLM_GPU_SYNC_CHECK` · 抓执行路径上的 CPU-GPU 同步 | 环境变量 | 不设(不查) | `warn`:预热完成后,worker 每步的前向与采样里一出现同步就告警,没锁页的非阻塞拷贝也算;`error`:直接抛错;只在 CUDA 与 ROCm 上生效;排查用,不要长开 | 告警 `GPU<->CPU sync detected` 及其调用栈 |
| `VLLM_USE_RAY_V2_EXECUTOR_BACKEND` · Ray 后端用哪一版执行器 | 环境变量 | 1 | 设 0:退回旧的 Ray 执行器,它不支持异步调度,异步被自动关 | 告警 ``Async scheduling will be disabled because it is not supported with the `ray` distributed executor backend`` |
| `--max-num-seqs` · 状态表的行数 | 启动 | 见 02 章 | 调高:状态表和 token 历史表按行数线性变大;token 历史表在锁页主存 | 主机内存占用 |
| `--max-model-len` · 状态表每行 token 历史的长度 | 启动 | 模型配置里的上下文长度 | 调高:token 历史表的锁页主存按比例涨,1024 行 × 131072 × 4 字节 = 512 MiB | 主机内存占用 |

| `--profiler-config` · 打开 profiler | 启动 | 不开 | 设 `profiler=torch` 并给 `torch_profiler_dir` 后,可用 `/start_profile`、`/stop_profile` 抓一段 trace,看 GPU 步与步之间有没有空档;只用于本地排障 | trace 里 GPU 时间轴的空白 |

**怎么看。** 一是启动日志:有 `Using V2 Model Runner` 说明是 V2;看到 `Model Runner V2 does not yet support` 就是退回了 V1,后半句写着是哪个特性;看到以 `Async scheduling` 开头、含 `disabled` 的告警,就是错开被关了,句中写着原因。异步开着且多卡时,每个 worker 进程里多一个名叫 `WorkerAsyncOutputCopy` 的线程,专门等拷回、打包结果,用 `py-spy dump` 能看到。二是 trace:打开 torch profiler 抓几步,异步正常时 GPU 的前向一个接一个,中间没有空白;空白一段一段出现,先回去查日志里是不是被关了。三是同步检查:`VLLM_GPU_SYNC_CHECK=warn` 下的每条告警都指向一个把错开打断的调用点。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡小模型在线聊天,小批 decode 为主 | `vllm serve Qwen/Qwen3-8B`,启动后确认有 `Using V2 Model Runner`、没有 `Async scheduling` 关闭告警 | 默认就是 V2 加异步;不换任何东西,只确认没被某个特性悄悄关掉 |
| 单机 8 卡、两段流水线,想要流水线和错开同时生效 | `vllm serve <模型> -tp 4 -pp 2`,不设 `VLLM_USE_V2_MODEL_RUNNER` | 在路上 3 批,流水线填满、CPU 收尾也藏住;代价是滑动窗口层多留 3 批的块,结构化输出的采样照样要等上一步 |
| 排障:怀疑某个特性在执行路径上同步,或要对照错开前后 | `VLLM_GPU_SYNC_CHECK=warn vllm serve <模型>`;对照组加 `--no-async-scheduling` | 用告警刷屏和吞吐换定位;查完去掉 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 小批 decode 时 GPU 利用率低、TPOT 降不下去 | 启动日志有没有异步被关的告警、有没有退回 V1 的告警 | 去掉引起关闭的那一项:CPU 草稿换成 GPU 上的方法、执行器换 `mp`;确认跑的是 V2 |
| 加了一个特性之后吞吐掉了一截 | 有没有 `using the V1 model runner instead` | 换成 V2 支持的做法,或接受 V1;对照组用 `VLLM_USE_V2_MODEL_RUNNER=0` 复现 |
| 启动报 `Model Runner V2 does not yet support:` | 是否设了 `VLLM_USE_V2_MODEL_RUNNER=1` | 去掉这个环境变量,让它自动退回 |
| 启动报 `Model Runner V1 does not support: pipeline parallelism with async scheduling` | 是否设了 `VLLM_USE_V2_MODEL_RUNNER=0`(或撞上了退回 V1 的特性)又显式写了 `--async-scheduling` | 去掉 `=0` 让 V2 接手;非要 V1 就去掉显式开关,异步会自动关 |
| 启动报 `Currently, async scheduling is only supported with EAGLE/MTP/...` | 是否显式写了 `--async-scheduling` 又用了 `ngram` 这类 CPU 草稿方法 | 去掉显式开关让它自动关,或换 `ngram_gpu`、EAGLE 一族 |
| 结构化输出请求一多,TPOT 明显变长 | 带文法约束的请求占比 | 采样要等上一步结果,是设计如此;掩码的开销见 14 章 |
| `VLLM_GPU_SYNC_CHECK=warn` 下告警刷屏 | 调用栈落在哪个特性里 | 那个特性每步都在打断错开;关掉它或报给上游 |

## 六、常见误区

- **以为异步调度是实验开关、默认关。** 官方专家并行部署文档把它列在「实验性」里,还建议「试试加上」这个开关,别家的对比材料也照这么写。基准代码里它不设就自动开,只在第五节那几种不兼容的情况下自动关;真要关得显式写 `--no-async-scheduling`。
- **以为 Model Runner V2 是要手动打开的实验品。** V2 目录的说明文件标题写着「实验性」,设计文档也说还没做全。但选择逻辑是不设环境变量就优先用 V2,只有撞上它不支持的特性才退回 V1;想用 V1 得明确设 `VLLM_USE_V2_MODEL_RUNNER=0`。
- **以为占位 token 是先猜一个值,错了再改。** 「占位」这个词让人以为 CPU 在预测下一个 token。调度器那边占位只是一个个数,值由 GPU 在下一步前向开头从状态行里自己读,CPU 自始至终不猜;采样本身和不错开时一样。
- **以为设 `VLLM_USE_V2_MODEL_RUNNER=1` 只是更稳地用上新版。** 不设时撞上不支持的特性会自动退回,设了 1 反而变成启动报错;双批重叠在不设时一律退回 V1,设了 1 才会去走 V2 那条还在开发的路。这个变量改的是「失败方式」,不只是版本。
- **以为 V1 和 V2 只差性能,来回切换没有副作用。** 官方文档写明 V1 的自定义 logits 处理器是另一套接口,按 V2 接口写的处理器切到 V1 要重写;PCP、DSpark、水印这些只在 V2 上有。排障时临时切到 V1 对照,先确认配置里没有只属于 V2 的东西。
- **以为流水线并行就得关掉错开。** 用过 SGLang 的人会这么想,它在流水线并行时确实关掉重叠。vLLM 在 V2 下两者共用一个批队列,在路上的批数是段数加 1;只有被迫退回 V1 时异步才自动关,所以流水线部署更要确认跑的是 V2。
- **把结束后多出来的那一步当成 bug。** 开 profiler 或数算力时发现请求结束后还被算了一步。那是错开的固定代价:结束符要等结果回到 CPU 才判得出,那时下一步已经发出;长度上限这种事先可知的停止条件不会多算,结束符和停止 token 一定多算 1 步。
