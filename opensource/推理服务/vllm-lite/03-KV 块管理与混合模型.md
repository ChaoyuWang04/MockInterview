# vLLM 03|KV 块管理与混合模型

一张卡能同时装下多少条请求,取决于两件事:启动时从显存里切出多大一个块池,以及每条请求的每一类注意力层要从池里拿走多少块。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

分页本身解决的是碎片,知识库里讲过。vLLM 真正要答的是两道算术题,答错了坏的都是**最大并发**。

第一道:KV 到底能拿多少显存。权重、激活峰值、CUDA graph 的缓冲、NCCL 这类不归 PyTorch 管的占用,都得先扣掉,剩下的才是 KV 的。扣少了,服务跑到第一个大批次或者抓图时 OOM;扣多了,显存闲着,并发白白少一截。这个数又没法事先写死,它随模型、并行方式、每步 token 上限、卡上有没有别的进程而变。

第二道:一条请求要几块。越来越多的模型把不同的层混在一起:一部分层看全部历史,一部分层只看最近 1024 个 token 的滑动窗口,还有一部分是 Mamba 这类线性注意力层,每层只存一份跟长度无关的定长状态。如果按「每层都存全长」记账,一个 10 层全注意力加 20 层滑窗、每层每 token 4 KiB 的模型,在 131072 的上下文下每条请求要预留 15 GiB;其中 20 层只会读最后 1024 个 token,预留的大半从头到尾没人碰。同样的显存,并发只剩分组记账时的 42%。

## 二、解法:先量出预算,再用一个池按注意力类型分组记账

最天然的直觉:启动时实测一次,把剩下的显存切成等大的块;每条请求一张块表,写着它的第几段 token 落在几号块。混合模型再多一步:同类型的层合成一组,每组一张表、一套记账规则,但所有组从同一个池里领块。

![上半是一个块池,24 个等大的块一字排开,0 号是红色的空块,其余按颜色标出属于这条请求的全注意力组、滑窗组、Mamba 组,灰色是空闲或别人在用的块;下半是同一条请求的三张块表,每格 16 个 token、共 7 格:全注意力组 7 格全是真块,滑窗组前 5 格换成 0 号只剩最后 2 块,Mamba 组也只剩最后 2 块;底部写明这条请求实际占 11 块,若都按全注意力记要 21 块](/opensource/vllm-lite/03a-block-pool-groups.svg)

**预算是量出来的。** 每张卡的 worker 先用假输入按每步 token 上限跑一次前向,量出权重、激活峰值和非 PyTorch 占用,再估一遍 CUDA graph 要多少。KV 预算 = 整卡显存 × 占比 − 这几项。也可以直接给一个字节数,跳过测量。多卡时各卡量出的块数取最小值,所有卡按同一个块数建池,调度器只管一份账。

**块的大小是定的,字节数是算的。** 一块缺省装 16 个 token;选中的注意力后端不收 16 时换成它能收的最小一档,MLA 常用的后端里就有只收 32、64 或 128 的。一块占多少字节 = 组内层数 × 块大小 × 每层每 token 的 KV 字节,池里的块数 = 预算 ÷ 这个数。

**分组让所有组的一块一样大。** 同类型的层先归到一起,再按层数最少的那一类切成等层数的组,凑不齐的补空层。例如 10 层全注意力加 20 层滑窗,切成 3 组、每组 10 层。每组的一块都是「10 层 × 16 个 token」,字节数相同,所以任何一块都能发给任何一组。物理上各组共用同一片显存:同一个块号在一个时刻只属于一个组,组里第 i 层就用这一块里的第 i 份。

**每组按自己的规则要块、还块。**

- 全注意力组:每个 token 都占位置,块一直留到请求结束。
- 滑窗组:算到哪,就把整块落在窗口外的那些从块表里换成 0 号空块,原来的块当场还池。准入时一条请求最多按「窗口加上正在路上的 token」预留,不按全长。
- Mamba 组:状态大小和长度无关。不开前缀缓存时整条请求只有 1 块;开着时滚动保留最近 2 块,前一步的状态拷进这一步的新块,再往前的还池,另加少量检查点块。Mamba 的一份状态常比 16 个 token 的注意力 KV 大得多,于是注意力的块大小被抬高到能装下一份状态,状态再补齐到同样的字节数。

还池的块排进一条空闲队列,里面的内容不清,前缀缓存命中时可以原样拿回去,那是 04 章的事。块不够时谁被踢回去重算,是 02 章调度器的事。

为什么实际不吃亏:记账全是 CPU 上的整数运算,每步只动新增和滑出窗口的那几块。一个池意味着不用事先决定「滑窗层给多少、全注意力层给多少」,长请求多时全注意力组多拿,短请求多时池子自然分给更多条请求。

## 三、代价

**测量只准在启动那一刻。** 预算是拿「启动时的空闲显存」和「一次假前向的峰值」推的。剖析期间同卡别的进程释放了显存,启动直接断言失败;启动后别的进程又占了显存,vLLM 不知道,OOM 在服务中途才出现。CUDA graph 的那份也只是估计值。另外占比算的是整卡总量,和卡上已经被占了多少无关:启动时空闲显存小于「总量 × 占比」就拒绝启动。

**块越大,尾巴越大。** 每条请求的每一组,最后一块平均空一半。块大小 16 时可以忽略;MLA 后端的 32 到 128,以及 Mamba 混合模型被抬到能装下一份状态的大块(官方设计文档说可能超过 400 个 token),尾块浪费和前缀命中的粒度都跟着变粗。

**凑齐层数要补空层。** 层数比例不整齐的模型,官方设计文档举的是 52 层滑窗加 10 层全注意力:按 10 层一组切,52 层滑窗交错分进 6 个组、每组 8 或 9 层,凑不满 10 层的空位合计 8 层,滑窗那部分最多白占 15.38%。Mamba 状态补齐到注意力块的字节数,也是纯填充。两处浪费启动时各打一行日志报百分比。

**滑窗的预留是保守的。** 准入和启动日志里的并发都按「窗口减 1,加上所有在路上的批次各一份每步 token 上限」给滑窗组预留。H100 在线服务默认每步 8192 个 token、开异步调度时两批在路上,窗口 1024 的组每条请求就按 1089 块预留;而稳态 decode 时它实际只占约 65 块。token 上限调得越大,滑窗模型能准入的请求越少。

**分组记账有前提。** 所在平台没声明支持时它不开(CUDA、ROCm、XPU、CPU 都声明了);挂了不支持它的 KV connector(12 章)时自动关掉,只打一行警告。关掉之后滑窗层退回按全长预留,Mamba 混合模型直接起不来。

## 四、和 SGLang、TensorRT-LLM 不一样的地方:要不要事先定比例

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。

三家都要回答同样三件事:KV 拿多少显存、滑窗层和全注意力层的 KV 各放多少、线性注意力的状态放在哪。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 定 KV 的总预算 | 整卡总量 × 占比,再减去实测的权重、激活峰值与 CUDA graph;也可直接给字节数 | 占比管的是「权重加 KV」,余下留给激活与 CUDA graph | 建 KV 管理器那一刻空闲显存的 90% |
| 一块几个 token | 16;后端或 Mamba 对齐会改 | 1;部分后端改成整页 | 32 |
| 滑窗层与全注意力层 | 同一个池,各组按需领块,比例随负载变 | 两个池,滑窗池的 token 数默认是全注意力池的 0.8 倍,部分模型改成 0.1,启动定死 | 每种窗口大小一个池,默认平分显存,环境变量可改比例,启动定死 |
| 线性注意力的状态 | 同一个池,状态补齐到一块注意力的字节数 | 单独的状态池,默认按状态与全注意力 KV 0.9 比 1 的显存比例切 | 另有专门的混合模型管理器,本页不对照 |

vLLM 的取舍是只要一个池、不设比例:负载怎么变都不会出现「一个池满了、另一个池闲着」,代价是所有组的一块必须一样大,于是要补空层、补状态、抬块大小。SGLang 和 TensorRT-LLM 让每类层有自己的池和自己的块形状,不用补齐,但比例要在启动时猜对,猜错的那部分显存就一直闲着。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。池的大小启动后不再变,运行时唯一能动它的是 18 章 sleep 模式的整体让出。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--gpu-memory-utilization` · 本实例最多用整卡总显存的多少(别名 `--device-memory-utilization`) | 启动 | 0.92 | 调高 0.01:KV 多出整卡总量的 1%,并发按比例涨;卡上留给别人的余地变小。启动时空闲显存小于「总量 × 占比」直接报错 | 日志 `Available KV cache memory: … GiB` |
| `--kv-cache-memory-bytes` · 直接指定每卡 KV 字节数 | 启动 | 不设 | 设了就不做显存剖析(假前向仍跑一次),占比被忽略;给大了分配或运行时 OOM,给小了并发封顶。命令行写成 `--kv-cache-memory` 也能认 | 日志 `reserved … GiB memory for KV Cache as specified by kv_cache_memory_bytes` |

| `--mamba-block-size` · Mamba 组一块几个 token | 启动 | 不设:开前缀缓存时等于块大小,不开时等于最大长度 | 只在开前缀缓存时能设,须是 8 的倍数 | 日志 `kv cache group sizes […]` |
| `--mamba-cache-dtype`、`--mamba-ssm-cache-dtype` · Mamba 状态的精度 | 启动 | `auto`;部分模型(如 NemotronH)SSM 状态默认 `float32` | 降精度:一份状态变小,注意力块被抬高的幅度和补齐浪费都变小;精度风险自担 | 日志 `Padding mamba page size by …%` |
| `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS` · 剖析时扣不扣 CUDA graph | 环境变量 | 1 | 设 0:KV 多拿 CUDA graph 那一份,抓图或跑起来后可能 OOM | 日志 `CUDA graph memory profiling is enabled` 及它建议的占比 |

**怎么看。** 一是启动日志的三行:`Available KV cache memory: X GiB` 是剖析后的预算;`GPU KV cache size: N tokens, Maximum concurrency for L tokens per request: Kx` 是换算结果;启动收尾还有一条以 `Free memory on device` 开头的 info,把权重、激活峰值、CUDA graph 各占多少列了出来,并给出两个可以直接抄的 `--kv-cache-memory` 字节数。混合模型再看 `kv cache group sizes` 与 `kv lcm block sizes` 两行,以及补空层、补状态的警告。二是稳态:每 10 秒那行的 `KV cache usage` 和 `/metrics` 的 `vllm:kv_cache_usage_perc`,算法是「1 − 空闲块 ÷ (总块数 − 1)」,减掉的那 1 块是 0 号空块。三是 `/metrics` 的 `vllm:cache_config_info`,标签里带着最终的块数、块大小和最大并发。

**手算一遍。** 一块的字节数 = 组内层数 × 块大小 × 2 × KV 头数 × 头维 × 精度字节;块数 = 预算 ÷ 一块的字节数;最大并发 = 块数 ÷ 一条最长请求在各组要的块数之和。例:32 层、每层 8 个 KV 头、头维 128、BF16,一块是 32 × 16 × 2 × 8 × 128 × 2 = 2 MiB;预算 40 GiB 就是 20480 块、327680 个 token;最大长度 32768 时每条请求 2048 块,日志会写 10.00x。换成第一段那个 10 层全注意力加 20 层滑窗的模型,同样 40 GiB、最大长度 131072:分组时一块 640 KiB、共 65536 块,每条请求 8192 + 2 × 1089 = 10370 块,并发 6.32x;关掉分组记账,一块 1920 KiB、共 21845 块,每条请求 8192 块,并发 2.67x。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡、模型原生支持 128K,业务最长 32K | `vllm serve <模型> --max-model-len 32768` | 用上下文上限换 4 倍的按最长请求算的并发;超过 32768 的请求被拒 |
| 一张 80 GB 卡上跑两个小模型实例 | 两个进程各起 `vllm serve <模型> --gpu-memory-utilization 0.45`,端口错开 | 各占整卡 45%,互不感知;第二个启动时空闲显存要不少于总量的 45%,两者同时启动时剖析可能互相干扰,建议串行拉起 |
| 固定机型批量部署,要缩短重启时间 | 第一次正常起,抄日志里「fit into requested memory」那个值,之后加 `--kv-cache-memory-bytes <该值>`;或设 `VLLM_ENABLE_STARTUP_PLAN=1` | 用跳过剖析换启动时间;换卡型、改并行方式或卡上多了别的进程,就得去掉重新测 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报 `Free memory on device … is less than desired GPU memory utilization` | 卡上有没有别的进程、上次的实例有没有退干净 | 清掉残留进程;或把占比降到「空闲 ÷ 总量」以下 |
| 启动报 `To serve at least one request with the model's max seq len` | 报错里给出的估计最大长度 | 调低 `--max-model-len` 或写 `auto`;或提占比、降 KV 精度、加 TP |
| 启动报 `No available memory for the cache blocks` | 权重加激活是否已经超过「总量 × 占比」 | 提占比、量化权重或加 TP |
| 启动时报 `Error in memory profiling` 断言 | 同一容器或同一张卡上是否有进程在剖析期间释放了显存 | 让 vLLM 独占这张卡,或串行启动 |
| 跑到第一个大批次或抓 CUDA graph 时 OOM | `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS` 是否被设成 0;卡上是否有后来者 | 恢复为 1;占比降 0.02–0.05;或用 `--kv-cache-memory-bytes` 给个保守值 |
| 滑窗或 Mamba 混合模型的 `Maximum concurrency` 比手算低一大截 | 日志有没有 `Hybrid KV cache manager is disabled` 或 `Turning off hybrid kv cache manager` | 去掉关闭参数;挂 connector 时换一个支持分组记账的(12 章) |
| 滑窗模型开着分组记账,并发仍偏低 | 每步 token 上限与异步调度的在路批数 | 调低 `--max-num-batched-tokens`(02 章),滑窗组的预留跟着降 |
| 日志出现 `Add … padding layers, may waste at most …%` 或 `Padding mamba page size by …%` | 百分比有多大 | 这是结构性浪费,不是错误;Mamba 那处可试降状态精度 |
| 稳态 `KV cache usage` 长期贴着 100%,`Waiting` 在涨 | 启动日志的最大并发与实际在跑的请求数 | 按上面几条扩容;抢占怎么发生见 02 章 |

## 六、常见误区

- **以为占比是「KV 占多少」或「空闲显存的多少」。** TensorRT-LLM 的同名概念是空闲显存的 90%,SGLang 的是权重加 KV,从那边过来的人会照着换算。vLLM 的占比是本实例能用的整卡总量份额,权重、激活、CUDA graph 全在里面,KV 拿剩下的。所以同卡两个实例各写 0.45 才对;把 0.9 调到 0.95,KV 多出的是整卡的 5%,不是 KV 的 5%。
- **以为日志里的 token 数就是池能装的 token 总数。** 纯全注意力模型上它确实约等于块数 × 块大小,大家就把它当成容量。混合模型上它是「最大并发 × 最大长度」,而最大并发是按每条请求都跑满、滑窗组按窗口加在路 token 保守预留算出来的。请求普遍很短时,实际同时在跑的 token 可以远多于这个数。
- **以为 `KV cache usage` 低就是前缀缓存里没东西,高就是该扩容了。** 这个比例只数被在跑请求引用的块;已经还池、内容还在、随时能被前缀命中拿回的块算空闲(04 章)。usage 50% 时池里另一半可能全是热前缀。要判断容量,看 `Waiting` 和抢占计数,不只看 usage。
- **以为滑窗模型的 KV 天然就省。** 模型卡片上写着窗口 1024,人们就默认 KV 只存 1024。省不省取决于分组记账开没开:挂一个不支持它的 KV connector 做 PD 分离,它在启动时自动关掉,只留一行警告,滑窗层全部退回按全长预留。上线 PD 后并发掉了一半,第一件事是翻这行警告。
- **以为 `--block-size` 写多少就是多少。** 这个参数看起来是直接生效的旗标。钉了值之后注意力后端确实不再改它,反过来它成了挑后端的条件,不收这一档的后端被跳过(06 章);可 Mamba 混合模型要把块抬到能装下一份状态,几种 KV 精度共用一个池时也要对齐页大小,这两处都会连用户值一起覆盖,只打一行 info。排查前缀命中粒度或尾块浪费时,以 `kv cache group sizes` 那行为准。
- **以为 `docs/design/` 里那两篇讲的就是现在。** 分页注意力那篇开头自己写着是历史文档,不再描述现有代码;混合 KV 管理那篇写于更早的提交,说「混合协调者只支持全注意力加一种别的类型」。当前协调者按规格把任意多个组合并查找,没有全注意力层的模型也能走。查行为以代码为准。
- **以为 `--kv-cache-memory-bytes` 是一个可以到处复用的精确值。** 它是日志建议出来的,看上去像测量结果。实际它只对「同卡型、同配置、启动时同样多的空闲显存」成立:换一台卡、旁边多一个进程,或改了每步 token 上限导致激活峰值变大,照抄就会 OOM。
