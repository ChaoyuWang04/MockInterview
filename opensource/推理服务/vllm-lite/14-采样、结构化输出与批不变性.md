# vLLM 14|采样、结构化输出与批不变性

模型每步交出一行词表宽的分数,这一步到底吐哪个 token:加工分数的各站按什么顺序走,格式约束怎么在抽样之前压进去,同一条请求换一批邻居为什么会换一个答案。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

decode 的每一步,前向给每条请求交出一行分数,Qwen3 这类模型一行有 151936 列。从这一行到一个 token,中间要过十来道加工:白名单、偏置、惩罚、禁词、温度、min-p、top-k 与 top-p,最后抽一个。算得不慢,麻烦在三处,坏的都是「吐出来的是哪个 token」,而且都不报错。

**加工的先后就是语义。** 偏置是往分数上加,重复惩罚是按比例缩,先加后缩和先缩后加得到的是两个分布。「至少生成多少个 token」要把结束符压成负无穷,可格式约束写到 JSON 收尾处只剩结束符可走,两站一叠,整行全是负无穷。顺序排错、参数调反,表现是输出绕着同一句话打转或者满嘴胡话,日志里一行告警都没有。

**让模型自由生成,格式迟早出错。** 要它吐 JSON,十次里九次对,第十次少一个括号,下游解析直接崩。事后校验只能重试;要保证每次都合法,只能在每一步抽样之前把「此刻文法上不许出现的 token」全部禁掉。这张禁表取决于前面已经吐了什么,每条带约束的请求每步都要重算一次;格式说明本身还得先编译成覆盖整张词表的自动机,编译是纯 CPU 活,放进主循环里做,所有请求会跟着一起停。

**同一条请求换一批邻居,答案就变。** 温度设成 0 也一样。矩阵乘、注意力、归一化、all-reduce 的 kernel 会看这一步批里有多少行来挑切法:行少时把 K 维或 KV 切成几段并行算完再合,行多时不切。浮点加法不满足结合律,切法一变,同一行分数在最后几位就不同;某一步第一名和第二名本来只差这么一点,一翻,后面整段发散。聊天服务里这是偶尔答案不一样,RL 里是推理侧的 logprob 和训练侧对不上,排障时是 bug 无法复现。

## 二、解法:顺序写死,掩码最先,随机数只认这条请求自己

最天然的直觉:把所有加工排成固定的一列,每站按行处理、整批一次做完;格式约束做成最前面的一站;要复现,就让进管线的分数和管线里的随机数都只由这条请求自己决定。Model Runner V2 的采样器就是这么排的:

![一步里 logits 变成 token 的定序管线:上面虚线框是 EngineCore 进程的 CPU,带格式约束的请求到达时把编译丢进线程池,编完才进批,之后每步在前向发出后逐行填位掩码,token 回来时状态机前进一格;下面虚线框是 GPU worker,分数依次经过紫色的文法掩码,以及灰色的复制成 FP32、白名单与偏置、惩罚、禁词、自定义处理器、思考预算强制、温度、min-p、top-k 与 top-p,最后由绿色的加噪取最大抽出新 token,噪声由种子、位置和 token 编号哈希得到;灰色各站批里没人用就不启动,默认的 logprob 取在掩码之后、任何加工之前;黄色标出批不变开关改的是前向里的矩阵乘、注意力、RMSNorm 与 all-reduce,抽样这一站在给了种子时本来就批不变](/opensource/vllm-lite/14a-sampling-pipeline.svg)

**顺序怎么定的。** 硬约束最先:文法掩码和白名单一上来就把不许的位置写成负无穷,后面哪一站都抬不回来。加性的在乘性的前面,源码注释直说偏置是加、惩罚是缩,两者不可交换,列表顺序就是管线顺序。调用方自带的处理器排在内置各站之后、温度之前,看到的是没缩放过的分数,接口说明要求它不许把被文法掐掉的位置抬回来。思考预算用完时强制只留思考结束标记,这一站排在所有改分之后,谁也覆盖不了它。最后才是温度、min-p、top-k 与 top-p,裁完抽一个。两站打架的那一处留了口子:最少 token 数压掉结束符之后,若这一行已经全是负无穷,就把停止 token 放回来,让文法能收尾。

**不用就不走。** 每一站先在 CPU 上看本步的请求里有没有人用到它,没人用就不启动 kernel;判断靠 CPU 上常驻的一份参数副本,不和 GPU 同步。整批都是贪心、或者都是温度 1 且没有任何加工时,连复制成 FP32 这一步都省掉,分数直接进抽样。

**抽样:加噪取最大。** 给每个 token 的分数加一份 Gumbel 噪声再取最大,数学上等价于按 softmax 分布抽一个,可是不用先算 softmax、不用排序和前缀和,一遍扫完词表即可。关键在噪声怎么来:V2 不用随机数发生器,而是拿这条请求的种子、这一行所在的位置和 token 编号哈希出来。于是带种子和不带种子的请求在同一个 kernel 里一次抽完;同一位置不管什么时候重抽,噪声都一样,推测解码的草稿与验证靠这一点对齐(09 章)。温度为 0 的行在同一个 kernel 里直接取最大。另有一条快路:批里没有贪心、没有显式种子、又有人用了 top-k 或 top-p 时,裁剪和抽样交给 FlashInfer 的一个融合 kernel,它不排序,用的是自己的随机数。V1 的做法是随机数发生器:不带种子的请求共用一个全局发生器,带种子的每条一个,源码注释承认要逐条处理、会慢。

**结构化输出:编译在后台,掩码在调度器,施加在 GPU。** 请求先在 API 进程过一遍校验,不合法的格式在这里就被拒,xgrammar、guidance、outlines、LM Format Enforcer 四个库挑哪一个也在这里定。进了 EngineCore,编译丢进一个线程池,请求挂在「等文法」状态、不进批(02 章),编完才第一次被排上。之后每一步,调度器把前向发出去,趁 GPU 在算,在 CPU 上给每条带约束的请求填一行位掩码:词表里每 32 个 token 压成一个 32 位整数,一位表示许不许。带约束的请求超过 128 条且没开推测解码时,切成 16 条一组丢进另一个线程池并行填。掩码随「开始采样」那次调用发给每个 worker,GPU 上一个 kernel 把不许的位置就地写成负无穷,然后才进采样器。采出的 token 回到调度器,状态机前进一格,下一步据此再填。开推测解码时每条请求一步要填 1 加 K 行,文法先把无效草稿截掉(09 章);异步调度下,这一步的采样要等上一步的 token 回来(07 章)。

**推理模型开格式约束。** 思考段本来就不该是 JSON。启动时配了推理解析器,调度器在思考结束标记出现之前给这条请求填全放行的掩码,出现之后才开始收紧;也可以设成从第一个 token 就收紧。思考段怎么切出来、工具调用怎么解析,归 19 章。

**批不变:把跟着批变的归约顺序钉死。** 一个环境变量打开之后,worker 起来时在 PyTorch 的算子分发层换掉批量矩阵乘、softmax、log-softmax 与按维求均值,A100 这一代连普通矩阵乘也换,Hopper 起则把 cuBLAS 的工作区压到切不了 K;vLLM 自己的线性层一律改走一个常驻型的 Triton 矩阵乘,K 方向的分块只按形状定,不随行数变;RMSNorm 换成逐行归约的 kernel;注意力把 KV 切段数钉成 1;MoE 用固定的分块配置、不切 K;张量并行时关掉自写的和 FlashInfer 的 all-reduce,NCCL 的 all-reduce 钉成树形算法、单通道;再关掉 TF32、低精度累加和 cascade 注意力。原则只有一条:同一行的算术顺序只看它自己,不看同批还有几行。抽样那一站在给了种子时本来就批不变,噪声不看邻居;源码对「随机采样却不给种子」打一行告警:这时种子是请求进门时现抽的,整批还可能落到 FlashInfer 那条快路上。哪些注意力后端声明支持批不变归 06 章,它和编译融合、CUDA graph 的关系见 08 章。

为什么实际不吃亏:十来站里常用的只有温度和 top-p 两三站,其余没人用就连 kernel 都不启动;文法掩码的 CPU 活藏在前向后面;批不变默认不开,只在要复现的场合付代价。

## 三、代价

**要加工就整批复制一份分数。** 只要这一步有一条请求需要任何一站,整批分数就先复制成 FP32 再逐站改:256 行、词表 151936 时一份 148 MiB,每步一次。账按「有没有人用」记,不按「谁用」记。

**惩罚的计数表开服就占着。** 为了在 GPU 上随采样一起更新,V2 给每个请求槽位开一行词表宽的 32 位计数,开服一次分配,不管有没有请求用惩罚:最大并发 1024、词表 151936 时是 594 MiB,源码的待办注释自己写着它能占到 GB 级。

**掩码是 EngineCore 的 CPU 活,跟着带约束的请求数涨。** 每行 4748 个 32 位整数,约 19 KB,每步经共享内存发给每个 worker;128 条以内逐条串行填,和调度抢同一个进程的 CPU(01 章)。前向比填掩码还短时,它就从藏在前向后面变成挡在采样前面。

**第一次见到的格式要付一次编译。** 编译在后台,不卡别人,可这条请求的 TTFT 里含着整个编译时间;xgrammar 的编译结果按格式内容缓存,上限 512 MB,同一份 schema 第二次来直接命中。编译失败的请求在下一次调度时以错误结束。

**一个引擎只有一个文法库。** 自动挑库是 API 进程按请求做的,可 EngineCore 只按第一条带约束的请求建一个库的实例,之后所有请求都交给它编译。

**批不变慢,而且是全进程的。** 换下来的都是最快的那条路:厂商库的切 K、注意力的切段并行、自写 all-reduce、量化的几种快 kernel(13 章);两个注意力后端下前缀缓存被关掉,Mamba 类层的后端不支持就直接起不来。它由环境变量控制,整台服务的所有请求一起付。官方文档标着 beta,没给慢多少的数字,承诺的范围只是「批的大小和批内请求的顺序」。

## 四、和 SGLang、TensorRT-LLM 比:掩码谁来算、随机数跟着谁走

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都在抽样前压文法掩码,也都有一个让结果可复现的开关;分歧在掩码由哪个进程算、随机数由谁决定,以及可复现这件事换掉了多少算子。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 抽样的随机数从哪来 | V2 用种子、位置、token 编号哈希出噪声,带不带种子一个 kernel;批里没有贪心与种子时交给 FlashInfer 的融合采样 | 不带种子时从全局发生器取噪声;种子只在确定性模式下生效,没给就填 42 | 带种子的请求每个槽位一份随机数状态;不带的共用一个种子固定为 42 的全局发生器 |
| 格式说明在哪编译 | EngineCore 的线程池,请求挂起等 | 调度器的线程池,另有一条文法队列 | 执行器循环里,请求第一次上批时当场编 |
| 每步的掩码谁来填 | EngineCore 趁前向在跑时填一份,发给所有 worker | 每个 rank 在采样前自己填一份 | 执行器循环里填 |
| 默认文法库 | 自动挑:xgrammar 优先,编不了按请求退到 guidance 或 outlines | xgrammar | 不装,要约束得点名 |
| 可复现换掉什么 | 矩阵乘、归一化、注意力切段、MoE 配置、通信,NCCL 单通道 | 分发层整体换算子,注意力与通信一起定住,NCCL 通道默认 8 | 只关注意力的多块切分、改走确定性 all-reduce、关 KV 块复用,矩阵乘不换 |

vLLM 的取舍是把掩码集中在 EngineCore 算一份,worker 只管施加,代价是这份 CPU 活和调度挤在同一个进程里。可复现这边,V2 的抽样不开任何模式也只看种子与位置,开关只需要管前向;代价是开关一开,整台服务一起变慢。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。采样参数和格式约束本身在请求里,每条各自一套、不用重启,表里「在哪调」写「请求」的就是这一类;OpenAI 兼容接口里非标准的字段放 `extra_body`。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `temperature` / `top_p` / `top_k` / `min_p` · 分布多尖、候选留多少 | 请求 | 不写时先取模型自带的生成配置,没有才是 1.0 / 1.0 / 全词表 / 0 | 温度低于 1e-5 当贪心,并把 top-p、top-k、min-p 复位;大于 0 小于 0.01 的被抬到 0.01 并告警;上限 2.0;`top_k` 取 0 或 -1 都是不裁 | 启动日志 `Default vLLM sampling parameters have been overridden by` |
| `repetition_penalty` / `frequency_penalty` / `presence_penalty` · 说过的词扣多少 | 请求 | 1.0 / 0 / 0,重复惩罚也可能来自生成配置 | 重复惩罚须大于 0,正分除、负分乘,prompt 里出现过的也算;另两个在 -2 到 2 之间,只看已输出的 | 输出里的复读 |

| `VLLM_USE_FLASHINFER_SAMPLER` · 允许 FlashInfer 融合采样 | 环境变量 | 不设:CUDA 上卡型与工具链支持就用 | 0:V2 一律走 Gumbel;显式设 1 而用不了时启动报错 | 日志 `Using FlashInfer for top-p & top-k sampling.` |
| `VLLM_XGRAMMAR_CACHE_MB` · xgrammar 编译缓存上限 | 环境变量 | 512 | 调大:schema 种类多时命中更多,占 EngineCore 的主存 | 同一 schema 第二次请求的 TTFT |
| `VLLM_REGEX_COMPILATION_TIMEOUT_S` · 正则转文法的超时 | 环境变量 | 5 秒 | 超时的正则直接报错;设 0 或负数不限时 | 报错 `Regex compilation timed out after` |
| `VLLM_V1_USE_OUTLINES_CACHE` · outlines 的编译结果落盘 | 环境变量 | 0:进程内只缓存 128 份 | 1:存进 SQLite,跨重启复用,没有上限 | 启动告警 `Enabling outlines cache` |

**怎么看。** 一是启动日志:`Default vLLM sampling parameters have been overridden by` 后面列出模型自带的生成配置改了哪几个默认值,这一行最常被略过;`Using FlashInfer for top-p & top-k sampling.` 说明快路可用。二是稳态日志与 `/metrics`:等文法编译的请求计在 `Deferred` 和 `vllm:num_requests_waiting_by_reason{reason="deferred"}` 里,和等 LoRA 槽位、等远端 KV 的混在一起(02 章);开推测解码时被文法判无效的草稿不计入草稿数(09 章)。三是错误日志:`Failed to compile grammar for request` 是编译失败,`Unexpected: grammar rejected tokens` 是状态机不认采出来的 token,请求随即以错误结束。四是响应:`finish_reason` 为 `length` 说明是被长度截断的,不是格式出错。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡 H100 跑 Qwen3-8B 带思考,在线服务以 JSON 与工具调用为主 | `vllm serve Qwen/Qwen3-8B --reasoning-parser qwen3 --structured-outputs-config '{"backend":"xgrammar","disable_any_whitespace":true}'` | 用固定一个库、JSON 不带随意空白换可预期的行为:xgrammar 编不了的 schema 直接 400,不会被别的库悄悄接走;思考段不受约束,格式在思考结束后收紧 |
| RL rollout,要求同一请求在任何批里吐同一串 token | `VLLM_BATCH_INVARIANT=1 vllm serve <模型> --generation-config vllm`,每条请求显式给 `seed` | 用吞吐和前缀缓存(视注意力后端)换逐位可复现;`--generation-config vllm` 让默认值不随模型目录变;不给种子的随机采样仍不保证 |
| 按模型卡的推荐参数跑聊天,只想压一压复读 | `vllm serve <模型> --override-generation-config '{"repetition_penalty":1.05}'` | 在模型自带的生成配置上合并一项;惩罚那一站对整批启动,计数表的显存开服就占着 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| JSON 偶尔不完整,末尾被截断 | `finish_reason` 是不是 `length` | 格式约束不管长度上限;调大 `max_tokens`,或在 schema 里限定数组与字符串长度 |
| 带格式的请求 400:`The provided JSON schema contains features not supported by xgrammar` | 后端是不是钉成了 `xgrammar` | 改回 `auto` 或换 `guidance`;或去掉 `multipleOf`、`uniqueItems` 这类关键字 |
| 带格式的第一条请求 TTFT 高,之后同一格式正常 | 稳态日志 `Deferred` | 编译在后台,首次必付;客户端固定 schema 字符串,调大 `VLLM_XGRAMMAR_CACHE_MB` |
| 带格式的请求以 500 结束,日志 `Failed to compile grammar for request` | 这个 schema 在引擎当前那个库上能不能编 | `auto` 下多半是库被第一条带约束的请求定成了别的;钉成能编它的库 |
| 思考模型带格式时推理段被掐掉或是空的 | 是否设了 `--reasoning-parser`;是否开了 `enable_in_reasoning` | 设上解析器,关掉后者 |
| 日志 `Unexpected: grammar rejected tokens`,请求报错结束 | 自定义处理器有没有改写被掩掉的位置 | 修处理器,不要抬回负无穷的位置 |
| 输出复读、绕圈子 | 启动日志里生成配置覆盖了哪些默认值;请求里的惩罚 | 调 `repetition_penalty`,或给 `repetition_detection` 让它自己停 |
| 同一 prompt 温度 0,单发与并发结果不同 | 批的组成不同,预期如此 | 要复现就开 `VLLM_BATCH_INVARIANT=1` |
| 开了批不变,随机采样仍不一致 | 有没有给 `seed`;告警 `Random sampling without an explicit seed may not be batch invariant` | 每条给种子,或温度 0 |
| 开了批不变启动报 `VLLM batch_invariant mode is not supported for` | 模型里有没有 Mamba 类层 | 换模型,或关批不变 |
| 开了批不变后多轮对话变慢 | 告警 `Disabling prefix caching for FLASHINFER/TRITON_MLA with batch invariance` | 换一个支持批不变又保得住前缀缓存的注意力后端(06 章) |
| 带约束的请求一多,TPOT 变长 | EngineCore 进程的 CPU;带约束的请求数 | 掩码是 CPU 活,异步调度下采样还要等上一步(07 章);按格式负载分实例 |

## 六、常见误区

- **以为自动挑库是每条请求各挑各的。** 官方文档说自动挡会「按请求的细节挑合适的后端」,校验代码也确实逐条挑、编不了就换库。可 EngineCore 只按第一条带约束的请求建一个库的实例,之后所有请求都交给它编译;第一条走了 xgrammar,后面那条本该换到 guidance 的 schema 照样交给 xgrammar。混着跑各种 schema 的服务,干脆钉死一个库。
- **以为请求里能关 JSON 的空白。** 请求参数里摆着 `disable_any_whitespace`、`disable_additional_properties`、`whitespace_pattern`,文档还给了旧字段到新字段的对照,看着就是按请求生效的开关。基准上没有一个后端读它们,只认启动时 `--structured-outputs-config` 里的同名项;而且要先把后端钉成 `xgrammar` 或 `guidance`,留在 `auto` 就启动报错。
- **以为不写温度就是 1.0。** OpenAI 的约定是 1.0,测试脚本也常省掉这个字段。`--generation-config` 默认是 `auto`,不写的温度、`top_p`、`top_k`、`min_p`、重复惩罚都先取模型目录里生成配置的值,启动时只打一行告警。同一个模型换一份权重目录,默认行为就可能变;要固定就设 `vllm` 或显式写全。
- **以为默认返回的 logprob 是模型原始分布。** 模式名叫 `raw_logprobs`,文档也说是「施加任何处理器之前」的值。文法掩码却是在进采样器之前就地写进分数的,所以带格式约束的请求,被掩掉的 token 在「原始」logprob 里就是负无穷。拿它做 RL 的重要性比或算困惑度,要记得约束已经在里面了。
- **以为温度 0 就能复现。** 贪心没有随机数,直觉上结果唯一。批的组成一变,前向的分数在最后几位就变,第一名第二名一翻,整段输出跟着变;这不是 bug,要逐位一致得开 `VLLM_BATCH_INVARIANT=1`,随机采样还得每条给 `seed`。
- **以为批不变要 Hopper 起步。** 环境变量旁边的注释写「需要算力 9.0 以上」,于是 A100 上直接放弃。官方文档写的是 8.0 以上,代码里 SM80 还专门走一套 Triton 矩阵乘替换;真正拦人的是注意力后端和 Mamba 类层的支持声明,不是卡代。
- **以为 `logit_bias` 能绕过格式约束。** 偏置和掩码都像是往分数上动手脚,容易以为谁后执行谁说了算。掩码排在最前,负无穷加任何有限的偏置还是负无穷;白名单也是和文法取交集,不会扩大允许集。
- **照着设计文档写自定义处理器。** `docs/design/logits_processors.md` 讲的是带 `update_state` 与批更新结构的那套接口,读起来更完整。那是 V1 的;默认跑的 V2 只收 `vllm.v1.worker.gpu.sample.logits_processor.LogitsProcessor` 的子类,加载时类型不对直接报错,要看的是 `docs/features/custom_logitsprocs.md`。
