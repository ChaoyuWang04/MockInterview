# vLLM 01|整体架构与请求流程

一条请求从进来到吐字,要经过哪几个进程、每一站做什么,为什么这样拆 GPU 才不用等 CPU。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

推理服务里的 CPU 活分两种。一种每步只做一次:决定这一步算哪些请求、各算几个 token、KV 放哪几块。另一种跟着请求数涨:每条新请求要套模板、切词;每出一步,每条在跑的请求都要把新 token 译回文字、查一遍有没有碰到停止串、往它的连接上写一块响应。在 H100 上起在线服务,默认一步最多同时跑 1024 条请求,后一种活在每一步里就要做 1024 份。

两种活挤在同一个 Python 进程里,坏的是**两个 token 之间的间隔**。解释器同一时刻只让一个线程干活,GPU 算完这一步,下一步要等调度这一件事做完才能开始;可调度排在 1024 份反切词和写响应的后面。并发越高,GPU 空等的时间越长。赶上一条超长 prompt 进来,光切词就把整个进程占住,所有在跑的请求一起卡一下。

## 二、解法:按「跟着谁涨」拆进程

最天然的直觉:跟着请求数涨的活放一个进程,每步一次的调度放另一个进程,真正碰 GPU 的前向再放到每张卡自己的进程里,三者之间只传小消息。vLLM 就是这么拆的:

![vLLM 的三类进程与一条流式请求走过的 9 站:API 进程里依次是收请求套模板、切词,EngineCore 进程里是输入线程、主循环调度、输出线程,GPU worker 进程每卡一个做前向与采样且只有一个 rank 交回结果;结果回到 API 进程做增量反切词与判停止串,判到就沿红色虚线反向叫停引擎,最后写 SSE 给客户端;单卡时 worker 就在 EngineCore 进程里](/opensource/vllm-lite/01a-process-topology.svg)

**API 进程**包揽所有跟着请求数涨的活:收 HTTP、套模板、切词、反切词、判停止串、写流式响应。切词不在事件循环上做,挪进一个线程池,默认只有 1 个线程,所以一条长 prompt 切词时,HTTP 收发和流式输出照常进行。结果回来后,输出协程每处理 128 条请求就让一次事件循环,不让一大批结果把 HTTP 堵住。

**EngineCore 进程**只干每步一次的活。它有 3 个线程:输入线程收包解包,输出线程打包发回,主循环夹在中间只碰两条进程内队列,从不碰套接字。这样收发和打包都能和 GPU 计算重叠。没有请求时主循环阻塞在输入队列上,不空转。

**GPU worker 进程**每张卡一个。主循环把这一步的调度结果写进一块共享内存,所有卡同时读到同一份;算完只有一个指定的 rank 把新 token 编号交回,其余卡不回。单卡时没有这个进程,worker 直接跑在 EngineCore 进程里,这一跳变成函数调用。

为什么这么拆实际不吃亏:进程之间传的东西很小。去程是新请求的 token 编号和采样参数,回程是这一步每条请求新出的那几个 token 编号。消息用紧凑的二进制格式打包,超过 256 字节的张量单独成帧、不拷贝。跨进程的开销和 GPU 算一步的时间差着数量级,还被输入输出两个线程藏在前向后面。数据并行时每个副本各有一个 EngineCore,API 进程默认也按副本数多开,每个 API 进程都连着全部 EngineCore,按各副本的排队长度和 KV 占用挑一个发。

## 三、代价

**停止串判得晚。** 碰到结束符和长度上限由 EngineCore 当场判;停止字符串却只能在 API 进程判,因为文字是在那里译出来的。判到之后要反向发一条中止消息回去,送达之前引擎照常往下算。开着异步调度时,API 进程拿到第 N 步结果的那一刻,第 N+1 步已经排好,这条请求照样在里面。多出来的 token 到了 API 进程直接丢掉,算力白花。

**反切词没有单独的进程。** 它和 HTTP 收发、写响应共用 API 进程的同一个事件循环。并发高、流式块又碎时,先满的是这个进程的 CPU,而 GPU 还没跑满。解法是多开 API 进程或换 Rust 前端,都要多占 CPU 核和内存。

**进程多,CPU 核要给够。** 官方的最低要求是每个进程一个物理核:单副本时是 2 加卡数,数据并行时再加上多开的 API 进程和一个协调进程;开了超线程要按 2 个逻辑核算 1 个。EngineCore 的主循环对 CPU 被抢特别敏感,容器里只给几个逻辑核的部署最容易在这里掉吞吐。

**在线服务没法捏回单进程。** 异步引擎客户端只支持多进程模式,想在一个进程里打断点,只能改用离线接口并关掉多进程。另外,当库用时子进程默认靠 fork 拉起;调用方在此之前已经初始化过 CUDA(或身在 Ray 里、在 WSL 上),就被强制改成 spawn,这时入口必须写在主模块保护里,否则子进程会把入口脚本再跑一遍。

## 四、和 SGLang、TensorRT-LLM 不一样的地方

三家都把切词和 GPU 前向拆到不同进程,分歧在剩下那几件 CPU 活各归谁:

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 切词 | API 进程,挪进线程池 | 主进程的事件循环上同步切,攒批执行器要手动打开 | 对外进程预处理完再交出去 |
| 反切词 | API 进程的输出协程 | 单独一个反切词进程 | 默认回对外进程,可另起后处理进程,默认零个 |
| 判停止字符串 | API 进程判,再反向叫停引擎 | 调度器自带一份分词器就地判,不需要反向叫停 | 执行器循环里按 token 序列判 |
| 调度与前向 | 调度在 EngineCore;多卡时每卡另起 worker 进程,单卡同进程 | 每个 rank 一个调度子进程,调度和前向在同一进程 | 执行器进程里同一条循环 |
| 进程之间怎么打包 | 紧凑二进制,大张量单独成帧 | 默认 Python 自带打包,紧凑格式要手动打开 | Python 自带打包加校验 |
| 调度进程空闲时 | 阻塞等消息 | 忙轮询,要打开开关才睡 | — |

vLLM 的取舍是让 EngineCore 只剩调度这一件事,其余 CPU 活全堆在 API 进程,API 进程不够就横向多开。SGLang 为反切词单开一站,并把停止串挪进调度器,换来不用反向叫停,代价是调度器也得装一份分词器。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。请求里只有流式间隔一项能覆盖,而且只能往大调。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--api-server-count` · 起几个 API 进程 | 启动 | 不设:单副本 1 个;内部负载均衡的数据并行下等于副本数 | 调高:切词、反切词、写响应的 CPU 分到多个进程,每个都连全部 EngineCore;每个进程各一份分词器;用 Rust 前端时忽略这个参数 | `ps` 里 `VLLM::APIServer_0`、`_1`… |
| `--renderer-num-workers` · 切词、套模板的线程数 | 启动 | 1 | 调高:同时到达的请求不再排一个线程的队,TTFT 的排队部分降;池化模型开着多模态预处理缓存时不能大于 1 | TTFT 高而 GPU 闲 |
| `--stream-interval` · 每攒几个 token 推一次 | 启动;请求里同名字段只能往大调 | 1 | 调高:反切词与写响应的次数按比例降,客户端收到的块变大变稀;第一个 token 和结束时总会推;GPU 不受影响 | SSE 每块带的 token 数 |
| `--distributed-executor-backend` · worker 怎么拉起 | 启动 | 单卡 `uni`(进程内);单机多卡 `mp`;在 Ray 放置组里是 `ray` | 单卡设 `mp`:worker 另起进程,多一次进程边界 | `ps` 里有没有 `VLLM::Worker…` |
| `--headless` · 只起引擎、不起 API 进程 | 启动 | 关 | 开:这台机器没有 HTTP 端口,API 进程在别的节点;多机数据并行的从节点用 | 启动日志里没有 HTTP 监听 |
| `--skip-tokenizer-init` · 不加载分词器 | 启动 | 关 | 开:请求必须直接给 token 编号,响应没有文本;RL 自己切词时用 | 响应里只有 token 编号 |
| `--disable-log-stats` · 不汇总每步统计 | 启动 | 关 | 开:每 10 秒那行稳态日志和引擎侧的 Prometheus 指标一起没了 | 日志里没有 `Avg prompt throughput` |
| `VLLM_ENABLE_V1_MULTIPROCESSING` · 离线接口把 EngineCore 放不放子进程 | 环境变量 | 1 | 设 0:离线 `LLM` 与 EngineCore 同进程,能打断点,失去 CPU 与 GPU 的重叠;在线服务不支持 | `ps` 里没有 `VLLM::EngineCore` |
| `VLLM_WORKER_MULTIPROC_METHOD` · 子进程怎么拉起 | 环境变量 | `fork`;用 `vllm` 命令起时改为 `spawn` | `spawn`:当库用时入口要有主模块保护;CUDA 已初始化、在 Ray actor 里或在 WSL 上时强制改 `spawn` | 日志 `Overriding VLLM_WORKER_MULTIPROC_METHOD to 'spawn'` |
| `VLLM_V1_OUTPUT_PROC_CHUNK_SIZE` · 输出协程每处理几条请求让一次事件循环 | 环境变量 | 128 | 调低:高并发下 HTTP 收发插得更勤,一步结果处理完得更晚;调高反之 | — |
| `VLLM_MSGPACK_ZERO_COPY_THRESHOLD` · 多大的张量单独成帧 | 环境变量 | 256 字节 | 调低:更多张量走单独帧、不拷贝,帧数变多 | — |
| `VLLM_ENGINE_READY_TIMEOUT_S` · 等 EngineCore 就绪的上限 | 环境变量 | 600 秒 | 大模型加载加编译超过 10 分钟时调高 | 报错 `Timed out waiting for engine core processes to` |
| `VLLM_HTTP_TIMEOUT_KEEP_ALIVE` · HTTP 空闲连接保持几秒 | 环境变量 | 5 | 调高:客户端连接池复用率高,空闲连接占句柄 | — |
| `VLLM_PROCESS_NAME_PREFIX` · 进程名前缀 | 环境变量 | `VLLM` | 一台机器跑多套服务时区分进程 | `ps` 里的前缀 |
| `VLLM_USE_RUST_FRONTEND` · API 层换成 Rust 进程 | 环境变量 | 0 | 设 1:API 进程固定 1 个,见 19 章 | `ps` 里有没有 Rust 前端进程 |

**怎么看。** 一是进程:`ps` 里应看到 `VLLM::EngineCore`(数据并行时是 `EngineCore_DP0`、`_DP1`…),多卡时每卡一个 `VLLM::Worker_TP0` 这样的 worker,单 API 进程时它就是 `vllm serve` 进程本身,开数据并行还有一个 `VLLM::DPCoordinator`。进程名靠 `setproctitle` 设,它是默认依赖。二是日志:EngineCore 出致命错误时打 `EngineCore encountered a fatal error.`,API 侧随后每条请求报 `EngineCore encountered an issue. See stack trace (above) for the root cause.`,根因要往上翻第一条异常;启动失败是 `Engine core initialization failed. See root cause above.`。三是接口:`/health` 只看引擎有没有报死,不真生成;`/metrics` 里 `vllm:num_requests_running` 与 `vllm:num_requests_waiting` 看负载。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡在线服务,并发 50–500 | `vllm serve Qwen/Qwen3-8B` | 默认就是 API 进程加 EngineCore 两个进程,worker 在 EngineCore 里;留至少 3 个物理核 |
| 单机 8 卡、高并发短请求流式,API 进程 CPU 先满 | `vllm serve <模型> -tp 8 --api-server-count 4 --renderer-num-workers 4 --stream-interval 4` | 用 4 个 API 进程和更稀的流式块换 CPU 余量;多 3 份分词器内存、多 3 个核,客户端每块 4 个 token |
| 离线脚本里打断点查问题 | `VLLM_ENABLE_V1_MULTIPROCESSING=0 python debug.py`,脚本里用 `LLM(...)` | 用单进程换可调试性;没有 CPU 与 GPU 的重叠,吞吐不代表线上 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| `/health` 返回 200,请求却全卡住 | `/health` 只看报死标志,引擎卡死它不知道 | 探针改成一条 1 token 的生成请求;看 EngineCore 日志最后一行在做什么 |
| 所有请求报 `EngineCore encountered an issue` | 往上翻 EngineCore 的第一条异常 | 根因多在 worker(显存不够、NCCL 出错);EngineCore 死了只能重启 |
| 启动十分钟后报 `Timed out waiting for engine core processes` | 加载权重与编译花了多久 | 调高 `VLLM_ENGINE_READY_TIMEOUT_S` |
| 容器里吞吐远低于同卡裸机 | 物理核数是否够 2 加卡数,再加多开的 API 进程 | 加核;或减 `--api-server-count` |
| API 进程 CPU 100%,GPU 没满 | 并发、流式块大小 | 调大 `--api-server-count` 与 `--stream-interval`;再不够换 Rust 前端 |
| 当库用时脚本被执行两遍 | 日志有没有 `Overriding VLLM_WORKER_MULTIPROC_METHOD to 'spawn'` | 入口加主模块保护;或把 CUDA 初始化挪到创建引擎之后,让它留在 `fork` |
| 设了停止串,生成量比预期多 | 停止串要到 API 进程才判 | 能用 `stop_token_ids` 就不用 `stop` 字符串,前者在引擎里当场判 |

## 六、常见误区

- **以为单卡也有一个 worker 进程。** 官方的进程说明和 CPU 公式都写「每卡一个 worker」,于是排障时去找 worker 进程的日志。单卡时后端默认是进程内的那一种,worker 就是 EngineCore 进程里的一个对象,`ps` 里根本没有 `VLLM::Worker`;worker 的报错都在 EngineCore 的日志里。
- **以为 `/health` 返回 200 就说明能出 token。** 用过 SGLang 的人会这么想,它的健康检查真发一条生成。vLLM 的 `/health` 只查「引擎有没有报死」这一个标志:EngineCore 卡在某个集合通信里不动,它照样 200。要真探活就发一条最小的生成请求。
- **以为停止串和结束符一样在引擎里判。** 结束符、停止 token 编号、长度上限都在 EngineCore 当场判;`stop` 字符串要等文字在 API 进程译出来才判,判到再反向叫停,中间多算的 token 白算。停止条件能写成 token 编号的,就别写成字符串。
- **以为多开 API 进程就能提吞吐。** 它只解决 API 进程 CPU 先满的问题。GPU 已经是瓶颈时多开没用,反而每个进程多占一个核、多一份分词器,还会和 EngineCore 抢 CPU。先看 API 进程的 CPU 再决定。
- **以为 CPU 核数给多少都行。** 按「GPU 服务主要吃 GPU」的直觉,容器常常只给 4 个逻辑核跑 4 张卡。官方最低要求是每个进程一个物理核,超线程要翻倍,4 卡至少 6 个物理核也就是 12 个逻辑核;EngineCore 主循环被抢一下,整批请求的这一步就晚一下。
- **以为调大流式间隔能减轻 GPU。** GPU 每步照算,它减的是反切词和写响应的次数,只在 API 进程 CPU 是瓶颈时有用;而且第一个 token 总是立刻推,不影响 TTFT。
- **以为在线服务也能关掉多进程来调试。** 那个环境变量只对离线 `LLM` 生效,异步引擎客户端明确不支持单进程;要调在线路径,得对 EngineCore 进程挂远程调试器。
