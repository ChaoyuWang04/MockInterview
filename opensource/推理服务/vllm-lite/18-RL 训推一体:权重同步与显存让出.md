# vLLM 18|RL 训推一体:权重同步与显存让出

训练和推理轮流用同一批卡、每隔若干步就要换一次权重时,推理服务怎么不重启就把显存交出去、再把新权重换进来,而且换完不拿旧 KV 冒充新结果。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

RL 的一步分两段:推理引擎生成 rollout,训练引擎拿这批样本算梯度、更新参数;下一步开始前,推理引擎必须换上刚训出来的权重。两段怎么摆卡,决定哪个指标先坏。

**训推共卡,坏的是显存峰值和切换时间。** 推理服务一起来就按显存占比把权重和 KV 池一次买断,默认占整卡的 0.92(03 章),训练那一段根本放不下。最笨的办法是每步杀掉服务再拉起:重读 checkpoint、重新编译、重抓 CUDA graph(08、17 章),每一步都付一遍冷启动,这段时间 rollout 吞吐是 0。

**训推分卡,坏的是每步搬多少字节。** 以 Qwen3-8B 为例,BF16 权重 16.4 GB、399 个张量,每步都要从训练卡送到推理卡。推理侧开 TP 时每张卡只需要自己那一片,最直接的广播却给每张卡都送一整份;MoE 开专家并行时更浪费,每张卡只放一小部分专家。

**两种摆法都会坏的是正确性,而且不报错。** 前缀缓存里的 KV 是旧权重算的,换了权重不清,命中越多偏得越多(04 章);KV 下放的下层也可能把旧 KV 拉回来(05 章)。一条请求要是跨过了换权重那一刻,前半截 token 出自旧策略、后半截出自新策略,拿去算重要性比就不再是 on-policy。

## 二、解法:进程与地址都不动,只还物理页

最天然的直觉:推理进程不退出,训练要卡时把显存交出去,训练完拿回来,再把新权重原地写进去。难处在「拿回来」:显存还了再借,地址一般就变了,而 CUDA graph 里烤死的恰恰是权重和 KV 的地址。

**可让出的分配器按标签记账。** 打开 sleep 模式后,worker 加载模型期间的每一次显存分配都改走 vLLM 自带的一个可插拔分配器,记上「权重」标签;分 KV 池时同样走它,记上「KV」标签。这个分配器直接调 CUDA 的虚拟内存接口:先保留一段虚拟地址,再把物理页映射上去。让出时只解除映射、把物理页还给驱动,虚拟地址留着;拿回时在同一段地址上映射新的物理页。地址没变,CUDA graph 与编译产物照旧可用,不用重抓也不用重编。

**两个级别只差权重备不备份。** 1 级把带权重标签的每一块先拷进主机锁页内存再还物理页,KV 直接丢;唤醒时拷回来,原样可用。2 级权重与 KV 都直接丢,只把模型里的小缓冲(旋转位置编码表这类)另存到主机;唤醒后权重那段显存内容未初始化,必须紧接着推一次新权重。另有 0 级只暂停调度、不动显存,以及一个只丢 KV、留着权重的接口。RL 每步都换权重,旧权重没有留的必要,2 级是更合适的那一档;训练时冻住、不参与推送的参数,可以按名字模式让 2 级也替它们在主机留一份。

![训推共卡时一个 RL step 的 8 个阶段里显存的去留:生成时推理进程持有旧权重与在用的 KV 块;一次睡眠调用先暂停、放掉在飞请求并清空缓存索引,再把权重与 KV 的物理页还给驱动,只留虚拟地址;训练进程随后占卡做前向、反向与优化器更新;接着只唤醒权重,这段显存内容未初始化,训练进程经 IPC 句柄把新权重逐层写回原地址,然后才唤醒 KV,得到一个空池并自动恢复调度;CUDA graph 私有池与 NCCL 通信缓冲不在可让出分配器里,全程占着,但因为地址没变,图不用重抓;下方两行对比 1 级,它在让出时把旧权重备份到与权重一样大的主机锁页内存,唤醒时拷回,紧接着又被新权重覆盖](/opensource/vllm-lite/18a-colocated-rl-step-memory.svg)

**唤醒可以按标签分两次。** 图里先只醒权重、推完新权重再醒 KV:推权重那一刻卡上同时有训练侧的新权重和推理侧的权重缓冲,KV 晚一点拿回来,峰值就少一整个 KV 池。调度要等所有标签都醒了才自动恢复。

**权重送进来有 4 条内置通道,训练侧各有一个对称的类。** 推理侧启动时只选一个后端名,打包方式、缓冲大小这些要两边一致的参数由训练侧在初始化握手时送过去,两边不会对不上。

- **同机共卡:CUDA IPC 句柄。** 训练进程把每个张量的进程间句柄发过来,推理 worker 直接读训练进程的显存,不经网络;句柄按 GPU 的硬件 UUID 分好,每个 worker 只认自己卡上那份。
- **分卡:NCCL 广播。** 训练侧 0 号 rank 与全部推理 worker 另建一个 NCCL 组,逐个张量广播,或者把许多小张量拼进固定大小的缓冲、轮换着播。每个 worker 收到的都是完整张量,再由本卡的加载函数切出自己那片。
- **稀疏更新:稀疏 NCCL。** 只广播改过的元素下标和值,推理侧按 checkpoint 坐标原地打补丁,不走逐层重载。
- **超大 MoE 分卡:分片直传。** 推理 worker 经 NIXL 从训练侧按需拉,每个 worker 只拉自己要的那一片;哪一片落到哪块显存,是初始化时拿不占存储的假张量把加载函数空跑一遍记下来的,之后每轮照着回放。worker 必须跑在 Ray 上。

此外,集体 RPC 能让每个 worker 从磁盘重读一遍权重;训练框架把引擎内嵌进自己进程时,集体 RPC 就是函数调用,可以直接把张量迭代器交给重载。

**一次更新是一个会话。** 初始化只做一次(比如建 NCCL 组);之后每轮先开会话,再送 1 到多批,最后收尾。开会话与收尾之间是逐层重载:一层的权重到齐,就当场做量化这类后处理,再拷回这一层原来的存储,显存布局不变。收尾时还会把已装的 LoRA 适配器全部清掉(16 章)。

**完整一轮是暂停、传权重、清缓存、恢复,顺序由调用方串。** vLLM 把清缓存并进暂停:暂停默认就把前缀缓存、多模态预处理缓存、编码器缓存连同 KV connector 那边一起清掉,更新会话本身既不暂停也不清。暂停时在飞请求有三种处理:当场放掉(默认)、等它们自然跑完、原地冻住;冻住的请求在清缓存时被抢占回等待队列,恢复后连已生成的部分一起按新权重重做 prefill。共卡时在暂停与恢复之间插进睡眠与分标签唤醒,而睡眠调用自己就先做一次暂停加清缓存。

为什么实际不吃亏:进程、NCCL 通信组、编译产物、CUDA graph 都原封不动,换一次权重只剩搬字节和逐层后处理两笔账;2 级睡眠一个字节都不往主机拷,醒来只是重新映射。

## 三、代价

**在飞请求默认被放掉。** 暂停和睡眠都默认当场中止在跑的请求,它们以中止结束返回客户端,已经算的 token 白算。选等完,就要等最长的那条;选冻住,请求不丢,但已生成的部分整段重做 prefill,而且 vLLM 不记录一条回答里哪段 token 出自哪版权重,版本号全局只有一个。

**1 级要一份和权重一样大的主机锁页内存。** Qwen3-8B 单副本就是 16.4 GB 锁页内存,睡、醒各一次整份拷贝。RL 每步都换权重时,醒来拷回的旧权重马上被新权重覆盖,这次拷贝纯属白花。

**2 级醒来的权重不能用。** 只醒权重不推新权重就开始生成,吐的是乱码;训练侧不发的冻结参数若没事先按名字保留,就一直是未初始化的内容。保留用的是可分页的主机内存,而且只管主模型。

**让不干净。** 不在可让出分配器里的东西一直占着:CUDA graph 私有池、NCCL 通信器的缓冲(另有一个实验开关能把它们也挂起)、传权重用的中转缓冲。NCCL 拼包默认每侧 2 个 1 GiB 缓冲,整个传输期间常驻;分片直传的接收缓冲不计入显存占比,占比设满了,服务照样起得来,第一次同步才 OOM。

**分卡时每张卡都收全量。** NCCL 通道下,一个 TP=8 的推理副本 8 张卡各收一整份,再各自扔掉 7/8;只有分片直传是按片拉。

**顺序全靠调用方。** 更新会话不检查是否已暂停;没暂停就推,正在生成的请求会一边生成一边被换权重,前缀缓存里的旧 KV 也原样留着。

**平台与进程限制。** sleep 模式只在 CUDA、ROCm、XPU 上能开;一个进程里只能有一个引擎用这个分配器;池内分配期间强制关掉 PyTorch 的可扩展段。

## 四、和 SGLang、TensorRT-LLM 比:分级睡眠,把清缓存并进暂停

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都把显存按类型打标签、都能不重启换权重,分歧在让出的粒度、在飞请求归谁处理、清缓存放在哪一步。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 显存按什么粒度让出 | 自带分配器,只分权重、KV 两个标签;按级别决定权重备不备份,唤醒可按标签分次 | 第三方让出库,KV、权重、CUDA graph 缓冲三类,按类点名让出与拿回 | 虚拟内存按 13 类执行器内存打标签,每类单独配恢复方式(不留、清零、主机内存、锁页内存),KV 默认不留 |
| 让出时权重默认怎样 | 1 级备份到锁页内存,2 级丢弃 | 默认不备份,要备份得启动时打开 | 按类默认备份到锁页或普通主机内存 |
| 让出前在飞请求怎么办 | 睡眠与暂停默认当场放掉,可选等完或冻住 | 释放接口要求已经空闲,否则断言失败;暂停另有打回、退回等待队列、原地停三种 | 睡眠与换权重默认先排空在飞请求再动手 |
| 权重通道 | NCCL 广播、CUDA IPC、稀疏 NCCL、分片直传 4 个内置引擎,训练侧各有对称的类 | 读盘、NCCL 广播、CUDA IPC 张量、checkpoint-engine 4 条 | 在 Ray 编排下,由 worker 扩展收 CUDA IPC 句柄 |
| 换完谁清前缀缓存 | 暂停那一步默认清,更新会话本身不清 | 更新接口默认清 | 换权重收尾时自动清 |
| 权重版本号 | 全局一个字符串,只能查当前 | 全局一个,另在每条响应里按 token 分段记版本 | 没有 |

vLLM 的取舍是把让出做成两档、把换权重拆成开会话、送批、收尾三步,并把清缓存交给暂停:接口少、组合固定,传输后端可以插拔,训练侧类与推理侧类成对出现。SGLang 按类点名更自由,CUDA graph 那块也能让,代价是释放前必须自己把服务清空;TensorRT-LLM 每类单独配恢复方式,并默认排空请求再动手,换来不丢请求,代价是等最长的那条。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。运行时能做的全在开发接口里(要 `VLLM_SERVER_DEV_MODE=1`,见总览第六节):暂停与恢复、睡眠与按标签唤醒、只放 KV、权重会话的初始化与三步、版本号、集体 RPC;不走 HTTP 时,`AsyncLLM` 上有对应的方法;离线 `LLM` 没有暂停与恢复,要暂停就用 0 级睡眠。清前缀缓存的接口见 04 章。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--enable-sleep-mode` · 打开 sleep 模式 | 启动 | 关 | 开:加载模型与分 KV 池都走可让出分配器,并自动打开下一项;只支持 CUDA、ROCm、XPU,别的平台启动报 `Sleep mode is not supported on current platform.` | 启动日志 `Enabling cumem allocator because sleep mode requires it.` |
| `--enable-cumem-allocator` · 只开可让出分配器 | 启动 | 关;上一项开时自动开 | 在 CUDA 上单开它,睡眠也能真还显存 | 睡眠日志里放掉的量 |
| `--sleep-preserve-parameter-names` · 2 级睡眠时替这些参数留主机副本 | 启动 | 空 | 按 glob 匹配运行时参数名(`model.named_parameters()`,不是 checkpoint 名);有一条匹配不上报 `No parameter matches sleep retention`;副本放在可分页内存;训练侧必须不发这些参数;1 级不受影响 | 主机内存占用 |
| `--enable-nccl-comm-suspend` · 睡眠时把 NCCL 通信器的显存也挂起 | 启动 | 关 | 开:实验性,多还一截通信缓冲,唤醒时恢复 | `Sleep mode freed` 那行 |
| `--weight-transfer-config` · 选权重传输后端 | 启动 | 不设:没有传输引擎,调会话接口报 `Weight transfer not configured` | `{"backend": "nccl"}`(给了配置不写后端时就是它)、`ipc`、`sparse_nccl`、`sharded_rdt`;其余参数由训练侧握手送来 | `/server_info` 里的配置 |
| `--distributed-executor-backend` · worker 怎么拉起 | 启动 | 见 01 章 | `ray`:分片直传必需,否则启动报错;`external_launcher`:训练框架用 torchrun 把引擎内嵌进每个训练 rank,自动关掉多进程 | 日志 `Using external launcher for distributed inference.` |
| `--load-format` · 首次怎么加载权重 | 启动 | `auto` | `dummy`:随机权重起服务,等训练侧第一次推权重;加载器本身见 17 章 | — |
| `--gpu-memory-utilization` · 推理进程占整卡的比例 | 启动 | 0.92 | 共卡时调低给训练侧留;KV 池按它算(03 章);NCCL 拼包缓冲与分片直传缓冲不在其内 | 启动日志的 KV 容量 |
| `VLLM_SERVER_DEV_MODE` · 挂开发接口 | 环境变量 | 0 | 设 1 才有本页全部 HTTP 接口;启动告警 `SECURITY WARNING: Development endpoints are enabled!` | 接口是否 404 |
| `VLLM_ALLOW_INSECURE_SERIALIZATION` · 允许反序列化 pickle | 环境变量 | 0 | IPC 句柄走 HTTP 时要 pickle 再 base64,服务端与训练侧都得设 1,否则报 `Refusing to deserialize` | — |
| `VLLM_ROCM_SLEEP_MEM_CHUNK_SIZE` · ROCm 上按多大块映射 | 环境变量 | 256(MB) | 调大睡醒更快,太大会 OOM;官方建议取 2 的幂 | — |

训练侧的参数写在训练进程里构造的初始化信息上,推理侧不用配:

| 训练侧字段 · 一句话中文说明 | 属于哪条通道 | 默认 | 调了之后 |
|---|---|---|---|
| `rank` · 本训练进程的编号,0 号是发送方 | 全部 | 必填 | 多 rank 训练时每个 rank 都要建引擎、都调 `send_weights()`,只有 0 号碰网络 |
| `world_size` · 训练侧加全部推理 worker 的组大小 | NCCL、稀疏 NCCL | 必填 | 推理 worker 数用 `/get_world_size` 查,默认含数据并行副本 |
| `packed` · 拼包传输 | NCCL、IPC | NCCL 开;IPC 关 | 开:NCCL 调用次数降到按缓冲算;IPC 下变成按块分批、显存有上界 |
| `packed_buffer_size_bytes` · 每个拼包缓冲多大 | NCCL、IPC | 1 GiB | 调小:两侧常驻显存少,调用次数多 |
| `packed_num_buffers` · 轮换几个缓冲 | NCCL | 2 | 调大:拼包、广播、拆包重叠得更多,每侧多占一个缓冲 |
| `num_consumers` · 全部推理 worker 数(TP × DP) | 分片直传 | 必填 | — |
| `num_rdt_buffers` · 两侧环形缓冲深度 | 分片直传 | 2 | 调大:流水更深,显存更多 |
| `buffer_presize_gb` · 每个缓冲预先开多大 | 分片直传 | 0.0 | 设成能装下最大的单个切片,避免同步中途扩缓冲 |
| `gather_lookahead` · 训练侧可以超前收集几层 | 分片直传 | 1 | 调大:收集慢于拉取时藏得住;训练侧同时驻留的层数是它加 1 |
| `stall_timeout_s` · 多久没进展就判失败 | 分片直传 | 300 秒 | 只是推理 worker 中途死掉的兜底,不是时延目标 |

运行时接口(都要开发接口放行;`AsyncLLM` 上暂停与恢复叫 `pause_generation`、`resume_generation`,睡眠、唤醒与权重会话的方法和路由同名):

| 接口 · 一句话中文说明 | 参数与默认 | 行为 |
|---|---|---|
| `POST /pause` · 暂停调度 | `mode` 默认 `abort`,可选 `wait`、`keep`;`clear_cache` 默认 true | 新请求照收但不调度;`abort` 当场中止在飞请求;`wait` 等跑完;`keep` 冻住,清缓存时抢占回等待队列;返回 `{"status": "paused"}` |
| `POST /resume` · 恢复调度 | 无 | 冻住与暂停期间收下的请求开始调度 |
| `GET /is_paused` · 是否暂停 | 无 | 返回 `{"is_paused": ...}` |
| `POST /abort_requests` · 只中止不暂停 | 体里 `request_ids`,空则全部 | 返回中止了几条 |
| `POST /sleep` · 睡眠 | `level` 默认 1,可选 0、2;`mode` 默认 `abort` | 先按 `mode` 暂停(1、2 级同时清缓存),再按级别还显存;返回空体 200 |
| `POST /wake_up` · 唤醒 | `tags` 可重复:`weights`、`kv_cache`、`scheduling`;不给就全醒 | 只醒一部分时调度保持暂停;0 级睡眠用 `scheduling` 恢复 |
| `GET /is_sleeping` · 是否在睡 | 无 | 任一标签没醒或调度仍暂停都是 true |
| `POST /release_kv_cache_memory` · 只还 KV | 无 | 要求已完成暂停且所有显存都在;用 `/wake_up?tags=kv_cache` 拿回 |
| `POST /init_weight_transfer_engine` · 建传输通道 | 体里 `init_info`,由训练侧生成 | 只调一次;NCCL 在这里建组 |
| `POST /start_weight_update` · 开会话 | 无 | 开逐层重载;会话已开时再调报错 |
| `POST /start_draft_weight_update` · 开草稿模型的会话 | 无 | 稀疏 NCCL 与分片直传不支持 |
| `POST /update_weights` · 送一批 | 体里 `update_info`;IPC 可给按 worker 编号排的列表 | 可调多次 |
| `POST /finish_weight_update` · 收尾 | 体里可带 `weight_version` | 完成逐层后处理、清 LoRA 状态;带了版本号就记下 |
| `POST /update_weight_version` · 只改版本号 | 体里 `new_version` | 不动权重 |
| `GET /weight_info` · 当前版本 | 无 | 返回 `{"weight_version": ...}`,起始值 `default` |
| `GET /get_world_size` · 推理 worker 数 | `include_dp` 默认 true | 算 NCCL 组大小用 |
| `POST /collective_rpc` · 在每个 worker 上调一个方法 | 体里 `method`、`args`、`kwargs`、`timeout`;参数只能是字符串 | 比如 `reload_weights` 从磁盘重读 |

训练侧用 `WeightTransferTrainerFactory.trainer_init(...)` 建引擎,每轮调一次 `send_weights()`,它替你调开会话、送批、收尾三个接口;控制面用 `HTTPVLLMWeightSyncClient`(默认超时 300 秒)或 `RayVLLMWeightSyncClient`。暂停、恢复、睡眠不在其中,要调用方自己调。

**怎么看。** 一是日志:睡眠时 worker 打 `CuMemAllocator: sleep freed X GiB memory in total, of which Y GiB is backed up in CPU and the rest Z GiB is discarded directly.` 与 `Sleep mode freed X GiB memory, Y GiB memory is still in use.`,后者的「still in use」就是没让出去的那部分;引擎打 `It took N seconds to fall asleep.` 与 `It took N seconds to wake up tags [...]`,这是睡、醒耗时的唯一读数;暂停时调度器打 `setting pause state to PAUSED_NEW`(冻住时是 `PAUSED_ALL`),恢复是 `UNPAUSED`;逐层重载时权重没按层排好,会打 `Allocating X MB of device memory to buffers to load [...] layers.`。二是指标:`vllm:engine_sleep_state` 按 `sleep_state` 标签分 `awake`、`weights_offloaded`(1 级)、`discard_all`(2 级)三条。三是接口:`/is_sleeping`、`/is_paused`、`/weight_info`。`/health` 在睡眠和暂停期间照样 200。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机共卡,FSDP 训练与推理同一批卡 | `VLLM_SERVER_DEV_MODE=1 VLLM_ALLOW_INSECURE_SERIALIZATION=1 vllm serve <模型> --enable-sleep-mode --gpu-memory-utilization 0.5 --load-format dummy --weight-transfer-config '{"backend": "ipc"}'`;每步 `/sleep?level=2` → 训练 → `/wake_up?tags=weights` → 训练侧 `send_weights()` → `/wake_up?tags=kv_cache` | 用一半显存的 KV 池换共卡;2 级不占主机锁页内存,在飞请求在睡眠时被放掉 |
| 训推分卡,生成与训练重叠的异步 RL | `VLLM_SERVER_DEV_MODE=1 vllm serve <模型> -tp 2 --weight-transfer-config '{"backend": "nccl"}'`;每轮 `/pause?mode=keep` → `send_weights()`(训练侧 `packed` 默认开)→ `/resume` | 每侧常驻 2 GiB 拼包缓冲换少发 NCCL 调用;冻住的请求不丢,但已生成部分重做 prefill,一条回答混两版策略且没有记录 |
| 大 MoE,专家并行,训推分卡跨 InfiniBand | `VLLM_SERVER_DEV_MODE=1 vllm serve <模型> --distributed-executor-backend ray --data-parallel-size 8 --data-parallel-backend ray --enable-expert-parallel --gpu-memory-utilization 0.85 --weight-transfer-config '{"backend": "sharded_rdt"}'`,训练侧 `buffer_presize_gb` 设到最大切片 | 每个 worker 只拉自己那片专家,换 Ray、NIXL 两个依赖和初始化时的空跑;显存占比留出接收缓冲;不能开 EPLB |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| `/sleep` 返回 200,`nvidia-smi` 纹丝不动 | 启动时有没有 `--enable-sleep-mode`;`Sleep mode freed` 那行是不是接近 0 | 加上重启;没开时睡眠照样暂停并放掉请求,只是不还显存 |
| 调这些接口全 404 | `VLLM_SERVER_DEV_MODE` | 设 1 重启 |
| 唤醒返回 200,请求进来却一直不出 token | `/is_sleeping` 是否仍是 true;是否只醒了 `weights` | 把剩下的标签也醒了;调度要全醒才恢复 |
| 换完权重输出是乱码 | 2 级睡眠后是否漏推权重;冻结参数是否不在推送范围 | 先推权重再醒 KV;冻结参数用 `--sleep-preserve-parameter-names` 保留 |
| 换完权重输出还像旧版本 | 是否没暂停就推;暂停时 `clear_cache` 是否被设成 false;KV 下放有没有磁盘层 | 先暂停再推;下层要单独清,见 05 章 |
| 唤醒时 OOM | 训练侧是否已把自己的显存挪走;是否一次醒了全部标签 | 先醒 `weights`、推完再醒 `kv_cache`;调低 `--gpu-memory-utilization` |
| 服务起来一切正常,第一次同步 OOM | 拼包缓冲与分片直传缓冲不在显存占比里 | 调小 `packed_buffer_size_bytes`,或调低 `--gpu-memory-utilization` |
| NCCL 同步卡死,或者推完是垃圾 | 训练侧迭代出来的张量顺序、dtype 是否与它声明的元数据一致;`world_size` 是否等于训练侧加 `/get_world_size` | 自定义权重源先测这一条;组大小按含数据并行的 worker 数算 |
| 报 `IPC handle not found for GPU UUID` | 训练进程与推理 worker 是否真在同一张卡 | 用 `--device-ids` 把服务钉到训练 rank 的卡上 |
| 报 `Refusing to deserialize` | 两端是否都设了 `VLLM_ALLOW_INSECURE_SERIALIZATION=1` | 两端都设 |
| 客户端一批请求以 abort 结束 | 暂停与睡眠的 `mode` 默认 `abort` | 要保留就传 `keep` 或 `wait` |
| 外部负载均衡的多实例,只有一个换了权重 | 暂停与更新是否对每个实例都发了 | 内部数据并行一次调用会扇出到全部副本;外部多实例要逐个发 |
| 分片直传启动报错 | `--distributed-executor-backend` 是否是 `ray`;是否开了 EPLB | 换成 `ray`;关掉 EPLB |

## 六、常见误区

- **以为没开 sleep 模式,调睡眠接口会报错。** 接口返回 200,日志也打了一行「freed」,看起来成功了。实际分配器里一块带标签的显存都没有,还掉的只是缓存分配器里零碎的空闲块;可暂停、放掉在飞请求、清缓存这些副作用一样不少。要看 `Sleep mode freed` 后面的数字,不看返回码。
- **以为睡眠只动显存、不动请求。** 名字叫 sleep,直觉是「挂起,醒来接着跑」。`/sleep` 的 `mode` 默认是 `abort`,在飞请求当场中止;想让它们醒来接着跑要显式传 `keep`,而且它们会按新权重重做 prefill。
- **以为推完权重就换干净了。** 用过 SGLang 的人会这么想,它的更新接口默认清前缀树。vLLM 的开会话、送批、收尾三个接口都不清缓存、也不暂停,清缓存藏在暂停里。跳过暂停直接推,正在生成的请求中途被换权重,前缀缓存里的旧 KV 也照样命中,全程不报错。
- **以为 `keep` 模式下 `clear_cache` 不起作用。** `/pause` 路由的注释就是这么写的,还标了弃用。代码里照样清:冻住的请求被抢占回等待队列,KV 作废,恢复后整段按新权重重算 prefill。异步 RL 文档说「恢复后生成的 token 全部按新权重算」,靠的正是这一步;真按注释把它当摆设关掉,冻住的请求就带着旧 KV 接着生成。
- **以为 1 级睡眠更稳,RL 也该用它。** 官方共卡加 FSDP 的示例用的就是 1 级,文档也说 1 级醒来原样可用。可 RL 每步都要推新权重:1 级让出时占一份与权重等大的锁页内存,醒来先把旧权重拷回,紧接着被新权重覆盖,两次整份拷贝都白做。每步都换权重就用 2 级,冻结参数用保留名单兜住。
- **以为睡下去显存就全还了。** 官方文档写「最多释放 90% 以上」。CUDA graph 私有池、NCCL 通信器缓冲、传输中转缓冲都不在可让出分配器里,一直占着;睡眠日志第二行的「still in use」才是训练侧真正拿不到的那部分,共卡时要按它留余量。
- **以为唤醒接口返回了就能接着服务。** 分标签唤醒只醒一部分时,调度保持暂停,新请求照收却不调度,`/health` 还是 200,客户端看到的是一直在等。`/is_sleeping` 要全部标签都醒才变 false。
- **以为 NCCL 通道会按推理侧的 TP 切好再发。** 训练侧不知道推理侧怎么切,它广播的是完整张量;每个推理 worker 都收一整份,再用自己的加载函数切。TP 越大浪费越多,大 MoE 要按片收得换分片直传。
- **以为权重版本号能看出一条回答用了哪版权重。** 收尾时带的版本号只是引擎里一个全局字符串,`/weight_info` 返回的是最近一次记下的值,响应里没有这个字段。冻住又恢复的请求混了两版策略,要自己在训练侧记:暂停前后各查一次版本、记下每条请求当时生成到第几个 token。
- **以为 IPC 走 HTTP 只要开发接口放行就够了。** IPC 句柄是 pickle 过的 Python 对象,服务端默认拒绝反序列化;服务端与训练侧两边都要设 `VLLM_ALLOW_INSECURE_SERIALIZATION=1`,这等于允许任何能访问这个端口的人让服务执行任意代码,所以端口只能对训练侧开放。
