# vLLM 框架总览(精简版)

源码基准:官方仓库 <https://github.com/vllm-project/vllm>,分支 `main`,commit `94f4170df37fe29d68bd2f7e5a496501b78d55ae`,最近的发布 tag `v0.30.0`,核对日期 2026-09-23。全篇的「当前」「默认」都指这组基准。本站另有一份按讲稿转录的长版 vLLM 解读,基准是 2026-09-13 的 `08426d51ef`,两边说法不一致时以本解读为准。

## 一、vLLM 是什么

**vLLM** 是 UC Berkeley Sky Computing Lab 开源、如今由社区维护的大语言模型推理与服务框架。它最早的出发点是一个显存问题:KV cache 随生成长度增长,长度事先不知道,按最大长度给每条请求预留连续显存,大半都浪费在碎片和空位上。vLLM 用操作系统分页的办法管 KV cache(PagedAttention),把显存利用率提上去,并发数跟着上去,吞吐也就上去了。今天的 vLLM 早已不止于此:同一套块管理之上长出了连续批处理、分块 prefill、前缀缓存、异步调度、编译与 CUDA graph、推测解码、PD 分离、KV 分层存储、大规模 MoE 部署,以及支持 386 个架构名的模型注册表。

一句话定位:**vLLM 把「KV 分页 + 不分阶段的 token 级调度 + 块哈希前缀缓存 + CPU/GPU 异步重叠 + 编译与 CUDA graph」做成一套推理服务栈,再用一层统一的 KV connector 接口把 PD 分离、KV 分层存储和外部缓存系统挂进来。** 它也是多个 RL 训练框架的 rollout 后端。

顶层入口(仓库根 `vllm/`):

- `vllm.LLM(...)`:离线批量推理,入口在 `entrypoints/llm.py`。
- `vllm serve <model>`:启动 OpenAI 兼容 HTTP server,同时提供 Anthropic Messages 接口与 gRPC,入口在 `entrypoints/cli/serve.py`;设环境变量后 HTTP 前端可换成实验性的 Rust 进程(仓库根 `rust/`)。
- `AsyncLLM`:在线服务用的异步引擎客户端,`vllm/engine/` 下的旧名只是它的别名。

代码组织上,引擎只有一套实现,在 `vllm/v1/`。按 Python 源码体量算,`vllm/` 共 37 MB,其中模型实现与模型层(`model_executor/` 加 `models/`)占 49%,引擎骨架 `v1/` 占 18%,`v1/` 里最大的两块是注意力后端与 worker。另有 3 块体量不小但本解读只讲到接口的东西:`csrc/`(C++ 与 CUDA 算子,5.5 MB)、`rust/`(实验性 Rust 前端,4.3 MB)、`platforms/` 与各硬件插件(ROCm、XPU、CPU、TPU 等移植)。

## 二、6 个招牌:先建立全局图景

```text
客户端并发请求(OpenAI / Anthropic / gRPC)
  |
  v
API 进程 ── 套模板、切词;增量反切词、流式返回
  |  ZMQ
  v
EngineCore 进程 ── 每步调度一次,结果广播给各卡 worker
  |    +-- [1] PagedAttention ── KV 切成定长块,块表映射,用完就还
  |    +-- [2] token 级调度 ── 不分 prefill 与 decode,每条请求只追一个数
  |    +-- [3] 前缀缓存 ── 块内容链式哈希,命中整块复用
  |    +-- [6] KV connector ── PD 分离、KV 下放、外部缓存走同一个接口
  |  共享内存
  v
GPU worker 进程(每卡一个)
       +-- [4] 异步调度 + Model Runner V2 ── GPU 跑第 N 步时 CPU 备第 N+1 步
       +-- [5] torch.compile + CUDA graph ── decode 整图,其余分段图
       +-- 注意力后端、推测解码、并行与 MoE、量化、多模态、LoRA、采样
```

一句话记忆:

- **PagedAttention**:KV cache 切成定长块,每条请求一张块表,显存按需分配、用完即还;混合模型的滑窗层、全注意力层、线性注意力层各有一套块账,共用一个池。
- **token 级调度**:调度器里没有「prefill 阶段」和「decode 阶段」,每条请求只有「已经算到第几个 token」这一个数,每步按 token 预算给大家追数,分块 prefill、前缀命中、推测解码都是这一个数的不同追法。
- **前缀缓存**:每块 KV 按「前一块的哈希 + 本块 token」做链式哈希,命中整块直接复用;默认开。
- **异步调度 + Model Runner V2**:CPU 准备下一步与 GPU 跑这一步重叠;新一代 ModelRunner 从设计上就假定执行循环里没有 CPU 同步点,当前默认启用。
- **编译与 CUDA graph**:默认优化级别下,模型先经 torch.compile 做融合,decode 批录整图,混合批走分段图。
- **KV connector**:PD 分离传 KV、把 KV 下放到 CPU 或存储、接 LMCache 与 Mooncake 这类外部缓存,全部走同一个接口,注册表里内置 17 个实现。

## 四、一条请求怎么串起来

一条请求进来后依次落在三类进程手里:**API 进程**里的 AsyncLLM 套聊天模板、切词,把请求经 ZMQ 发给引擎;**EngineCore 进程**的主循环每转一圈做一次调度(这里用上 token 级调度、块分配、前缀缓存、KV connector),把这一步的调度结果经共享内存广播给所有 worker;**GPU worker 进程**(每张卡一个)里的 ModelRunner 跑前向与采样(这里用上注意力后端、编译与 CUDA graph、并行、量化、推测解码、结构化输出的掩码)。新 token 回到 EngineCore,再经 ZMQ 回到 API 进程,由 OutputProcessor 增量反切词后流式吐给客户端。数据并行时每个副本各有一个 EngineCore,另有一个协调进程汇总各副本的排队长度与 KV 占用,供 API 进程做负载均衡;MoE 模型的副本还要靠它一起进入或退出运行状态(10 章)。

异步调度的意思是:EngineCore 在 GPU 跑第 N 步时就把第 N+1 步调度好,第 N 步采出的 token 留在 GPU 上直接喂给下一步。

## 六、怎么调它、怎么看它

各章「调参与观测」只写自己的参数,入口和观测点在这里说一次。

**四种入口,一个原则:改了要重启的都是启动参数。**

| 入口 | 长什么样 | 什么时候用 |
|---|---|---|
| 启动参数 | `vllm serve <model> --gpu-memory-utilization 0.92 …`,也可以把同样的键写进 YAML 用 `--config` 传 | 池的大小、并行方式、后端选择、各种开关;改了要重启 |
| 环境变量 | `VLLM_` 前缀,启动前 export | 实验开关与内部阈值(选 ModelRunner 版本、批不变模式、Rust 前端、开发接口);改了要重启 |
| 请求参数 | OpenAI 接口的标准字段,非标准的放 `extra_body`;离线接口是 `SamplingParams` | 采样、停止条件、结构化输出约束、种子、LoRA 名;每条请求各自一套 |
| 运行时接口 | 开发接口要先设 `VLLM_SERVER_DEV_MODE=1`:`/sleep` 与 `/wake_up`、`/pause` 与 `/resume`、`/update_weights`、`/reset_prefix_cache`、`/collective_rpc`、`/server_info`;LoRA 热加载的 `/v1/load_lora_adapter` 另要 `VLLM_ALLOW_RUNTIME_LORA_UPDATING` | 不重启能做的事只有这些 |

**观测点就两行日志加一个接口。**

| 看什么 | 在哪 | 怎么读 |
|---|---|---|
| 容量 | 启动时一行 `GPU KV cache size: N tokens, Maximum concurrency for L tokens per request: Kx` | K 小于期望并发就是 KV 不够,先调显存占比或上下文长度 |
| 稳态 | 每 10 秒一行:`Avg prompt throughput`、`Avg generation throughput`、`Running`、`Waiting`、`KV cache usage`、`Prefix cache hit rate`,出过抢占时多一个 `Preemptions` | `Waiting` 持续涨而 `KV cache usage` 接近满,是容量瓶颈;`Preemptions` 在涨说明在反复重算 |
| 指标 | `/metrics`(Prometheus,默认挂上),`vllm:` 前缀,如 `kv_cache_usage_perc`、`num_requests_waiting`、`time_to_first_token_seconds`、`prefix_cache_hits` | 线上看趋势用这个,不看日志 |

## 七、阅读顺序

主干是 01 → 02 → 03 → 04,读完就抓住了 vLLM 的块管理与调度主线。05 是块管理往显存外的延伸,06 到 09 是单卡执行栈,10 到 12 是多卡与分离,13 到 17 按需查阅,18 只在做 RL 训推一体时读,19 在接工具调用、推理模型或排查 API 层瓶颈时读。

**怎么读**:每章都是短页,页头一句话定位,然后核心问题、解法、代价、和同类大厂框架不一样的地方、调参与观测、常见误区。PagedAttention、前缀缓存、连续批处理、CUDA graph、并行策略、量化这些通用机制在知识库里各有一篇,这里直接用术语,只讲 vLLM 怎么做、怎么调;哪一句想展开,在对话里问。第四段的对照对象主要是 SGLang,两个项目的力气花在不同地方:

| 维度 | vLLM | SGLang |
|---|---|---|
| 前缀缓存 | 按块做链式哈希,命中粒度是整块 | radix 树,边可拆分,命中到 token;调度器可按命中长度排序 |
| CPU 与 GPU 的关系 | 异步调度加 Model Runner V2,采样结果留 GPU | 调度器提前一批准备元数据,用占位 token 让 GPU 不等 CPU |
| 显存之外的 KV | 走 KV connector 接口,下放与外部缓存都是插件 | GPU、host、分布式存储三层内建 |
| 服务层 | Python API 进程可多开,Rust 前端实验中 | HTTP 前端与路由网关可换成 Rust |

## 八、术语表

| 术语 | 一句话 |
|---|---|
| V1 | 当前唯一的引擎实现,代码在 `vllm/v1/`;旧引擎已删除 |
| EngineCore | 跑调度与执行主循环的那个进程,和 API 进程隔着 ZMQ |
| 块 / 块表 | KV cache 的定长分配单位,缺省 16 个 token 一块,后端与模型结构可以改它;块表记每条请求用了哪些块 |
| KV cache 组 | 混合模型里同一种注意力类型的层共用一套块账,叫一组 |
| token 预算 | 每一步最多算多少个 token,调度器在它之内分配 |
| 抢占 | 块不够时把一条运行中的请求踢回等待队列,放掉它的块,之后重算 |
| MRV2 | Model Runner V2,重新设计的 ModelRunner,当前默认 |
| 异步调度 | 调度第 N+1 步与执行第 N 步重叠 |
| 分段图 | 在注意力等不能入图的算子处切开,其余部分分段录 CUDA graph |
| KV connector | 把 KV 搬出或搬进本实例的统一接口,PD 分离与下放都走它 |
| EC connector | 多模态编码结果的搬运接口,编码器分离时用 |
| HiSparse | 稀疏注意力模型只在 GPU 留热 KV 的机制,实验中 |
| DBO | 双批重叠,MoE 层把一批拆两个微批让通信与计算错开 |
| EPLB | 专家并行负载均衡,按统计重排专家位置 |
| sleep 模式 | 不停服务就让出权重与 KV 显存,RL 训推一体用 |
