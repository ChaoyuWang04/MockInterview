# vLLM 02|调度器

每一步该算哪些请求、每条算几个 token、显存不够时让谁出去,怎么做到一条长 prompt 进来不卡住所有正在吐字的流。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

decode 的 TPOT 就是一步的时长,一步的时长又由这一步要算的 token 总数决定。96 条请求在 decode,凑成一步只有 96 个 token;这时进来一条 32768 token 的 prompt,要是整条一次算完,这一步的 token 数从 96 涨到 32864,96 条流在同一刻一起停住,TPOT 上出现一根和 prompt 长度成正比的尖刺。反过来按阶段轮流也不行:整批一起开始、一起结束,新请求要等最长的那条写完才能进门,TTFT 被最长的那条拖住。

第二处坏在显存。decode 每走 16 个 token(缺省块大小)就要一块新的 KV 块,而输出多长事先不知道。收进来的请求越多,越可能在半路一起要块而池里没有。这时必须有人让出来;让法不对,就是反复踢人、反复重算,吞吐和尾延迟一起坏。

## 二、解法:只追一个数,每步按总额补差

最天然的直觉:不分阶段,每一步都重新决定。vLLM 的调度器里没有「prefill 状态」和「decode 状态」,每条请求只记一个数:已经算到第几个 token。它的目标是 prompt 加上已生成的 token,开推测解码时再加上草稿。每一步有一个 token 总额,调度器拿它去给大家补差:

![vLLM 一步调度的两件事:上半是一步 8192 token 的预算怎么分,运行队列按进队顺序先分,96 条 decode 各拿 1 个 token,不设单条上限时一条长 prompt 的续算块吃掉剩下的 8096 个,等待队列里的新请求一个都进不来,设了每条 2048 的上限后同样 8192 个 token 分给了 4 条 prompt;下半是某条 decode 补块失败时,运行队列队尾也就是最后进来的那条被踢出,它的块全部还回块池,已算 token 清零后放回等待队列队首](/opensource/vllm-lite/02a-token-budget-and-preemption.svg)

**先补运行队列,再收等待队列。** 运行队列(running)按进队顺序走,decode 的差是 1,prefill 没算完的差是剩下的 prompt,每条拿「差」和「剩余总额」里小的那个。总额还有剩,才从等待队列(waiting)队首往里收:先查前缀缓存,命中的部分直接记成已算(04 章),剩下的差同样按剩余总额截断。分块 prefill 不是另一套机制,就是「差比剩余总额大时只给一截」的自然结果。

**长 prompt 可以再加一道单条上限。** 默认不设,于是一条长 prompt 每步都把 decode 用剩的总额吃光,直到算完,后面的新请求一个也进不来(图上 A 行)。设了上限,每条请求一步最多拿这么多,同一步里能同时推进好几条 prompt(B 行)。只有它一条请求时上限自动失效,没有谁会被它饿着。

**进门先看整条 prompt 放不放得下。** 收新请求时默认要求池里的空块装得下它整条 prompt,而不只是第一块,免得收进来算到一半就没块。另有一个条数上限,运行队列满了就不再收。

**块不够就踢队尾。** 给运行队列里某条补块失败时,把运行队列最后一条踢出去:块全部还回池,已算的数清零,放回等待队列最前面,之后从头 prefill。还不够就接着踢新的队尾,直到踢到正在补块的这条自己。这一步只要踢过人,就不再收新请求。开了优先级模式时,改踢优先级最低、同级里最晚到的那条。

为什么这么做实际不吃亏:decode 一条一步只占 1 个 token,1024 条 decode 也只用掉 8192 总额里的 1024 个,其余留给 prefill;prefill 吃算力、decode 吃带宽,拼进同一次前向,权重只读一遍。总额又给每一步的时长封了顶,尖刺最高就到「满额的一步」为止。前缀命中、草稿 token、被踢后重来,都只是「这个数怎么追」的不同情形,调度器不用为它们各开一条路。默认开着异步调度,排下一步时这一步的 token 还没采出来,调度器先记占位再往下排(07 章)。

## 三、代价

**踢人按先后,不按代价。** 队尾就是最后进来的那条,调度器不看它已经算了多少;刚把 20000 个 prompt token 算完的请求照样会被踢,清零后整条重来,只有前缀缓存还没驱逐的那部分能捡回来(04 章)。让出的办法只有重算一种,没有把 KV 换到 CPU 再换回来的模式;KV 下放到 CPU 是另一回事,见 05 章。

**准入不给输出留位置。** 整条 prompt 放得下就收,输出会长多长不估。推理模型这类一条输出上万 token 的负载,会在半路集体要块,抢占集中出在这时。可以设一个「收人时多留多少空块」的比例,默认是 0。

**一个总额管两头。** 总额调大,长 prompt 切得少,TTFT 短,但混进大块的那一步更长,TPOT 尖刺更高;调小反过来。单条上限只管「一条别吃独食」,不改一步的总量,压不住尖刺。

**挤的时候门是关的。** 踢过人的那一步不收新请求,显存吃紧时等待队列只进不出,TTFT 跟着涨。等待队列本身默认没有上限,来多少收多少;要在满载时直接拒绝,得在 API 进程另设上限。

## 四、和 SGLang、TensorRT-LLM 不一样的地方:准入宽,踢人简单

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都要回答同一组问题:一步里放什么、总额数什么、显存给谁、不够了踢谁。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 一步里 prefill 与 decode 同不同批 | 没有阶段之分,天然同批 | 默认一步只做一种,prefill 优先;同批要手动开 | 默认同批 |
| 一步的总额数什么 | 一个总额,decode 的 token 也算在内 | 只数 prefill 的新 token,decode 另有条数上限 | 一个总额,在跑的 decode 先占 |
| 长 prompt 切块 | 默认开 | 默认开,块大小按显存定 | 默认关,整条放不进就等 |
| 收新请求时显存看多远 | 整条 prompt 放得下就收,输出不预留 | 把输出还会长多少按一个自适应比例估进去 | 默认按整条请求算完来预留 |
| 块不够时踢谁 | 运行队列里最后进来的;优先级模式下踢优先级最低的 | 已生成最少、prompt 最长的 | 默认策略保证进批的都能算完,不踢;换成尽量塞满的策略才会暂停在跑的请求 |

vLLM 的取舍是准入放得最宽、踢人规则最简单:收得多、切得碎,换来 TTFT 和混批的吞吐,代价是显存吃紧时靠重算兜底。SGLang 用估输出长度把抢占挡在门外,TensorRT-LLM 默认干脆按最坏情况预留;所以那两家常见的是显存看着没满却不收人,vLLM 常见的是收进来之后再踢。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。请求级只有优先级一项,而且只在优先级策略下生效。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--max-num-batched-tokens` · 一步最多算多少 token | 启动 | 按卡和入口定:70 GB 以上且非 A100 的卡,在线 8192、离线 16384;160 GB 以上两者都是 16384;其余卡在线 2048、离线 8192;`--performance-mode throughput` 下翻倍 | 调高:长 prompt 切得少,TTFT 降、prefill 吞吐升,混进大块的那步变长,TPOT 尖刺升;调低反之;不能小于 `--max-num-seqs` | 启动日志 `Chunked prefill is enabled with max_num_batched_tokens=`;`vllm:iteration_tokens_total` 贴着它说明每步满额 |
| `--max-num-seqs` · 运行队列最多几条 | 启动 | 70 GB 以上的卡 1024,其余 256;不超过上一行;`throughput` 模式下翻倍 | 调高:decode 并发升,KV 更吃紧、更容易抢占;它同时定了 ModelRunner 每请求缓冲和 CUDA graph 的捕获上限(08 章) | 稳态日志 `Running` 贴着它 |
| `--max-num-active-seqs` · 只压准入条数,不缩缓冲 | 启动 | 不设,等于上一行 | 调低:decode 批变小、TPOT 降,缓冲与 CUDA graph 不变;不能大于 `--max-num-seqs` | 同上 |
| `--long-prefill-token-threshold` · 单条请求一步最多算多少 | 启动 | 0,不限 | 设 1024–4096:长 prompt 不再独吞总额,多条 prompt 一起推进,短 prompt 的 TTFT 降,长 prompt 自己的 TTFT 升;只有一条请求时不生效;不能大于上下文长度 | 长短 prompt 混到时短请求的 `vllm:time_to_first_token_seconds` |
| `--enable-chunked-prefill` · 分块 prefill | 启动 | 生成模型开;编码器-解码器模型强制关 | `--no-enable-chunked-prefill`:放不进剩余总额的 prompt 整条等;总额没手设时自动抬到上下文长度,手设得比上下文短则启动报错;生成模型关掉会告警可能出错 | 启动日志 |
| `--scheduler-reserve-full-isl` · 收人前确认整条 prompt 放得下 | 启动 | 开 | `--no-scheduler-reserve-full-isl`:只看这一块放不放得下,收得更多,长 prompt 算到半路没块就开始踢人 | 稳态日志 `Preemptions` |
| `--watermark` · 收人时多留的空块比例 | 启动 | 0 | 设 0.05:新请求和被踢回来的请求要多留 5% 的块才进门,抢占少,并发略低;只在这一步已有别人在跑时生效;取值 0 到 1,不含 1 | `KV cache usage` 不再顶到 100% |
| `--scheduling-policy` · 排队与踢人的规则 | 启动 | `fcfs` | `priority`:等待队列按请求的 `priority` 小者先、同级先到先;踢人改踢 `priority` 最大、同级最晚到的;不会为新来的高优先级请求主动踢人 | `vllm:request_queue_time_seconds` 按优先级分组看 |
| `priority` 字段或请求头 `X-Vllm-Priority` · 单条请求的优先级 | 请求 | 0 | 数值越小越先;请求头优先于字段;`fcfs` 下被忽略,不报错 | — |
| `--max-num-scheduled-tokens` · 调度器自己发出的 token 上限 | 启动 | 等于 `--max-num-batched-tokens` | 推测解码要往批里补 token 时调低,给草稿留位置(09 章) | — |
| `--max-num-queued-reqs` · 在跑加排队的请求总数上限 | 启动;在 API 进程执行 | 不限 | 满了新请求直接回 503,方便负载均衡换实例重试;多个 API 进程共享一个计数;按「副本数 × `--max-num-seqs` + 想要的排队深度」设 | 日志 `Request queue full - rejecting request` |
| `--max-num-queued-tokens` · 还在 prefill 的 prompt token 总量上限 | 启动;在 API 进程执行 | 不限 | 按「目标 TTFT × prefill 吞吐」设,超了回 503;计数偏保守:分块进度和前缀命中都不扣,会比实际早拒 | 日志 `Max queued tokens reached - rejecting request` |
| `--performance-mode` · 性能档位 | 启动 | `balanced` | `throughput`:没手设的一步总额和条数上限都翻倍,另外改 CUDA graph 的尺寸(08 章) | 启动日志 `Performance mode set to` |
| `--prefill-schedule-interval` · 数据并行下每几步才收一次 prefill | 启动 | 1 | 见 10 章 | — |
| `--scheduler-cls` · 换调度器类 | 启动 | 不设:开异步调度用异步子类,否则用基础类 | 接口不公开,换了不保证兼容;继承基础类而不是异步子类会丢掉异步调度 | 日志 `Using custom scheduler class` |

**怎么看。** 一是稳态日志:每 10 秒一行里的 `Running`、`Waiting`、`KV cache usage`;`Waiting` 里有一部分是被暂时挡住的(LoRA 槽位满、等远端 KV、等文法编译),这部分单独显示为 `Deferred`;出过抢占时多一个 `Preemptions: N`,N 是这 10 秒内的次数,不是累计。调度器踢人时不另打日志。二是 `/metrics`:`vllm:num_preemptions` 是累计抢占次数,`vllm:request_num_preemptions` 是每条请求被踢几次的分布,`vllm:num_requests_waiting_by_reason` 把排队分成 `capacity` 和 `deferred` 两种,`vllm:iteration_tokens_total` 是每步实际算了多少 token,`vllm:inter_token_latency_seconds` 看 TPOT 尖刺。

**典型配置。** 只列这一章管的参数,模型、并行度、显存占比照常另给。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| H100 在线聊天,流式体验优先,偶尔来 32k 长文 | `vllm serve <模型> --max-num-batched-tokens 4096 --long-prefill-token-threshold 1024` | 每步封顶 4096,满额那一步的 token 数减半;一步能同时推进 4 条 prompt,短请求不被长文挡;长文自己的 TTFT 和整体 prefill 吞吐变差 |
| 离线批量或评测,只看总吞吐 | 在线用 `vllm serve <模型> --performance-mode throughput`;离线脚本里 `LLM(...)` 在 70 GB 以上的卡默认总额已是 16384 | 一步更满,TPOT 和尖刺都变大;条数上限翻倍后 KV 更吃紧,留意 `Preemptions` |
| 推理模型长输出,显存偏紧,`Preemptions` 常年非零 | `vllm serve <模型> --max-num-active-seqs 256 --watermark 0.05` | 用并发换少踢人;CUDA graph 与缓冲尺寸不变,吞吐峰值略降、尾延迟稳 |
| 多租户分级,付费请求先进门 | `vllm serve <模型> --scheduling-policy priority --max-num-queued-reqs 4096`,请求带 `priority`(小者先) | 高优先级先进门、显存不够时后被踢;不会为新来的高优先级请求主动踢人;队列满回 503 让网关换实例 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 长 prompt 一来,所有流的 TPOT 一起跳一下 | `vllm:iteration_tokens_total` 是否贴着总额;尖刺时刻与长请求到达是否对得上 | 调小 `--max-num-batched-tokens`;单条上限压不住这个 |
| 一条长 prompt 在算时,别的新请求 TTFT 一起变长 | `--long-prefill-token-threshold` 是不是 0 | 设成总额的 1/4 到 1/2 |
| `Preemptions` 持续非零 | `KV cache usage` 是否贴 100%,`Running` 是否贴条数上限 | 调低 `--max-num-active-seqs` 或 `--max-num-seqs`,加 `--watermark`;容量本身不够看 03 章 |
| `Waiting` 涨,`KV cache usage` 不高 | `Running` 是否贴条数上限;`Deferred` 占多少 | 贴上限就调高 `--max-num-seqs`;`Deferred` 多查 LoRA 槽位(16 章)、远端 KV(12 章)、文法编译(14 章) |
| 客户端收到 503 | 日志是 `Request queue full` 还是 `Max queued tokens reached` | 放宽对应上限或扩副本 |
| 带 `priority` 的请求没有插队 | `--scheduling-policy` 是否还是 `fcfs`;数值方向是否弄反 | 改成 `priority`;数值小的先 |
| 启动报 `max_num_batched_tokens (…) is smaller than max_model_len` | 关了分块 prefill 又手设了较小的总额 | 开回分块,或把总额调到不小于上下文长度 |

## 六、常见误区

- **以为请求里带了 `priority` 就生效。** 接口文档写着「非 0 的优先级在没开优先级调度时会报错」,于是没报错就以为在排队里用上了。基准上全树没有这个检查,`fcfs` 下这个字段被默默忽略;要用得先起服务时换成 `priority` 策略。
- **以为高优先级的新请求能把在跑的低优先级请求踢下来。** 用过 SGLang 的人会这么想,它开优先级后默认允许插队抢占。vLLM 只有在运行队列里某条补块失败时才踢人,等待队列里的请求再高也不会触发抢占;优先级只决定谁先进门、踢谁。
- **排障时去日志里搜抢占的 WARNING。** 官方调优文档的抢占一节贴了一条带 `PreemptionMode.RECOMPUTE` 的 WARNING 样例,大家照着搜。那是旧引擎的日志,当前调度器踢人时一行都不打;要看 10 秒统计行里的 `Preemptions` 或 `vllm:num_preemptions`。
- **以为抢占可以改成换出到 CPU。** 同一节文档说默认是重算「而不是换出」,读起来像有两种可选。基准上只有重算一种,没有这个开关;把 KV 放到 CPU 的是 KV connector 的下放,和抢占无关(05 章)。
- **以为总额只管 prefill。** 从 SGLang 过来的人会把 `--max-num-batched-tokens` 对上它的 `--max-prefill-tokens`。vLLM 这个总额把 decode 的 token 也算在内,而且不能小于条数上限;把它调到很小,decode 和 prefill 一起被挤。
- **指望单条上限压住 TPOT 尖刺。** 名字里有「长 prefill」,看着就是治长 prompt 的。它限的是一条请求一步拿多少,几条 prompt 同时来时一步照样被填到满额;尖刺的高度只由总额决定。
- **调小 `--max-num-seqs` 只为压 decode 批。** 大家以为它只是准入上限。它同时决定 ModelRunner 每请求缓冲和 CUDA graph 的捕获上限,调小会连带改掉图的覆盖范围;只想让 decode 批小一点,用 `--max-num-active-seqs`。
- **看到 `Waiting` 高就判定显存不够。** `Waiting` 是两类加起来的:真在等容量的,和被 LoRA 槽位、远端 KV、文法编译暂时挡住的。先看 `Deferred` 或 `vllm:num_requests_waiting_by_reason`,后一类加显存没用。
- **以为收人时已经给输出留好了位置。** 默认开着「整条放得下才收」,容易被读成「整条请求」。它只算 prompt,输出一个 token 都不预留;长输出负载的抢占就来自这里,要留余量得设 `--watermark`。
