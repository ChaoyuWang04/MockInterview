# vLLM 04|前缀缓存

系统提示词、多轮历史、few-shot 示例这些每条请求都背着的开头,怎么只算一次,让后来的请求直接拿走现成的 KV。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

多轮对话和 agent 循环里,每一轮发给模型的 prompt 都是「系统提示词 + 之前所有轮的问答 + 这一轮的新输入」。不复用的话,第 N 轮的 prefill 要把前 N−1 轮原样再算一遍,而这一轮真正新增的往往只有一句话。TTFT 跟着轮数往上涨,和这一轮问了什么无关。

共享系统提示词的在线服务更直白:100 条请求共用一段 2000 token 的系统提示词,各算各的就是 200000 个 token 的 prefill,其中 198000 个在重复前面已经做过的事。few-shot 评测把同一组示例放在每道题前面,也是这个形状。

坏的是两样:**TTFT**,因为每条请求都要先把那段公共开头算完才轮到自己;**prefill 吞吐**,GPU 算力花在重复的 token 上,同一时间能接的新请求变少。每条请求还各存一份内容相同的 KV,显存被同一段开头占了很多份,并发也跟着掉。

## 二、解法:给每块 KV 一个只看内容的指纹

最天然的直觉:算过的 KV 按内容记下来,新请求来了先查,查到的直接挂进自己的块表,只算剩下的(块池与块表见 03 章)。难处在于一个 token 的 KV 不只取决于它自己,还取决于它前面的所有 token,所以「这一块是什么」必须把从开头到这一块的全部内容算进去。每次都把整段前缀重新哈希太贵,vLLM 用的是链式哈希:**第 i 块的键 = H(第 i−1 块的键, 本块的 token, 额外键)**。一个键就指纹了从开头到这一块末尾的全部内容,而每块只需要算一次。

![三条请求共用一段 48 token 的系统提示词,块大小 16:请求 A 先到,5 个满块的键从种子开始一环扣一环算出来,全部登记进哈希表;请求 B 的前 3 块键与 A 相同,直接复用 A 的物理块,第 4 块内容不同、键变了,查找就停在这里,末尾 6 个 token 不满一块、没有键;请求 C 与 A 的前 64 token 完全相同,但最后一个 token 必须真算一次,命中上限 63 向下取整到块边界成 48,于是表里明明有的第 4 块也要整块重算](/opensource/vllm-lite/04a-prefix-hash-chain.svg)

**键里除了 token 还有什么。** 同样的 token 不一定是同样的 KV,凡是会让 KV 不同的东西都得混进键里:请求挂了 LoRA 适配器,每一块都混进适配器名;多模态请求里图片展开成的占位 token 长得一模一样,所以凡是覆盖到图片的块都混进图片的内容哈希,以及图片在这一块里从第几个 token 开始;直接喂嵌入向量的请求,混进这一块嵌入本身的哈希;缓存盐只混进第一块,靠链传到后面每一块。登记进表时键尾再拼上 KV cache 组号,混合模型里同一段 token 在不同组各登记一份。

**链头的种子。** 第一块没有前一块,要一个种子顶上。默认的密码学哈希用一个写死的种子,于是不同进程、不同机器对同样的内容算出同样的键,KV 下放和外部缓存可以拿它当跨实例的地址(05、12 章)。换成非密码学的快速哈希时,种子改为每个进程随机:它扛不住蓄意构造的碰撞,种子一旦可预测,攻击者就能离线凑出和别人撞键的块。

**怎么查。** 请求一进 EngineCore,输入线程就把 prompt 所有满块的键算好,和 GPU 前向重叠;decode 每写满一块再补一个键,所以生成出来的内容也会被缓存。调度器给等待中的请求分块之前先查表:从第一块往后逐块查,第一次查不到就停,因为链式哈希保证后面的块不可能再对上。命中的块引用计数加 1,已经算过的长度记进请求,调度器按剩下的 token 排预算(02 章)。

查找有两条硬规矩。一是**最后一个 token 必须真算**,因为这一步要拿它出 logits,所以命中上限是 prompt 长度减 1。二是**命中只落在块边界**,不满一块的尾巴不登记也不查。两条叠在一起,prompt 恰好是整块时,表里明明有的最后一块也要整块重算。

**混合模型各组的命中怎么对齐。** 不同注意力类型对「能从哪里接着算」的要求不同。全注意力组要从开头连续命中,前 k 块能用,前 k−1 块一定也能用,所以从左往右扫;滑动窗口组只要命中点之前一个窗口那么多块还在,从右往左找第一段够长的连续命中;Mamba 组只要命中点那一块存着状态,也从右往左找。协调器先给一个候选长度,让各组轮流表态,谁接受不了就缩到自己能接受的位置,然后所有组重新表态,直到没人再缩。长度只减不增,一定收敛。全注意力排在最前,它一次扫描就给出最紧的上界,后面几组少做功。

**块怎么变成可让出的缓存。** 请求结束,块的引用降到 0 就进空闲队列,但键不抹。没有键的块插到队首,最先被重新分配;带键的块排到队尾,而且同一条请求的块倒着放回,覆盖前缀最长、最不可能被别人用上的尾块排在前面,先让出去。要新块时从队首取,取到带键的块,这时才把它的键从表里删掉。命中一个还躺在空闲队列里的块,就把它从队列中间摘出来,空闲队列是双向链表,摘一块是常数时间。

为什么实际不吃亏:查表是每块一次字典查找,哈希在输入线程里和 GPU 计算重叠;缓存不另占显存,它就是空闲 KV 里还没被重新分出去的那部分;而一次命中省下的是整段 prefill。

## 三、代价

**命中按整块算。** 分叉落在块中间,这一块整块重算;prompt 全部在表里时仍要重算 1–16 个 token。混合 Mamba 模型更粗:注意力块会被抬到至少和一份 Mamba 状态一样大,Mamba 状态也只在块边界存,命中粒度跟着变粗,要细到块内得额外设一个更细的匹配单位,而且只在特定组合下生效。

**哈希是 CPU 活。** 默认算法把「前一块的键、本块 token、额外键」序列化后算密码学哈希,每块一次,一条 32000 token 的 prompt 就是 2000 次。快速哈希能省 CPU,代价是碰撞只在理论上罕见、跨进程默认对不上键。

**表不去重。** 两条请求各自算出内容相同的块,就在同一个键下各挂一份物理块,各占一份显存。这是有意的:已经分出去的块号不能变,块表只追加不改写。

**LRU 是平的。** 系统提示词的块和某个会话最后一轮的块排在同一条队列里,只按何时被放回排序,没有「人人都要用的开头最后丢」这种结构上的偏好。缓存又只活在空闲显存里,并发一高,空闲块被在跑的请求吃光,缓存先被挤空,命中率恰好在负载最重时往下掉。

**清空要等全空。** 清缓存要求除了一个占位块以外所有块都空闲,否则直接失败返回。可以选择先把所有在跑的请求抢占回等待队列再清,代价是它们全部重算。RL 训推一体里每次换完权重都得清一次,否则旧权重算出来的 KV 会被新权重当真用上,而且不报错。

**有的请求不读缓存。** 要 prompt logprobs 的请求默认跳过查表,因为命中的那段没有 logits 可取。按均值或 CLS 池化的 embedding 模型、编码器-解码器模型、无注意力模型默认不开前缀缓存。

## 四、和 SGLang、TensorRT-LLM 比:怎么认出前缀,先丢哪块

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。

三家都默认开着前缀缓存,分歧在「凭什么认出算过的那段」和「显存不够时先丢谁」:

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 认出哪一段算过 | 每块一个链式哈希,逐块查字典 | 前缀树,从根逐 token 往下走 | 基数搜索树,按块往下走 |
| 最小命中单位 | 16 token 一块;混合模型可另设更细的匹配单位 | 默认 1 个 token | 默认 32 token 一块 |
| 分叉落在块中间 | 这一块重算 | 默认粒度下不存在半块 | 部分复用默认开,别人正在用的块先拷一份再切 |
| 显存不够丢谁 | 一条空闲队列按 LRU 让出,不分辈分;同一请求的块倒序放回 | 只从叶子挑,默认按最近使用打分,人人共用的主干最后才轮到 | 只踢叶子;按 0–100 的优先级分档,同档内按 LRU |
| 多租户隔离 | 缓存盐混进第一块的键,顺链带到后面 | 缓存盐当键的命名空间,不同盐从根就分开 | 缓存盐混进块键,文档要求键必须用密码学哈希 |
| 另一个进程能不能认出同一段前缀 | 默认能:键只取决于内容和固定种子 | 不能:树是进程内的有状态结构 | — |

vLLM 的取舍是让键成为内容的纯函数:同一套键直接拿去当 KV 下放、外部缓存与 PD 分离传输的地址,不用另建一层映射。代价是键里没有辈分,驱逐只能看时间,看不到「谁是谁的前缀」;SGLang 把辈分存进树里,换来按结构驱逐,却也把缓存锁在了一个进程里。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。请求里能改的只有缓存盐;离线接口的采样参数里还能指定这条请求跳不跳过读缓存。运行时只有一个清空缓存的开发接口。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--enable-prefix-caching` / `--no-enable-prefix-caching` · 开关 | 启动 | 按模型定:生成式的纯解码器与混合模型开;编码器-解码器、无注意力模型、双向注意力或均值与 CLS 池化的 embedding 模型关;RISC-V CPU 强制关 | 关:每条请求从头 prefill;没挂 KV connector 时连块哈希都不算 | 稳态日志里没有 `Prefix cache hit rate` 这一项 |
| `--prefix-caching-hash-algo` · 块哈希用什么算法 | 启动 | `sha256`(pickle 序列化) | `sha256_cbor`:规范 CBOR 序列化,跨 Python 与 vLLM 版本可复现;`xxhash`、`xxhash_cbor`:更快、非密码学、要另装 `xxhash` 包,种子每进程随机 | 启动日志 `Using a random per-process NONE_HASH seed` |
| `PYTHONHASHSEED` · 链头种子 | 环境变量 | 不设:密码学算法用固定种子 `vllm-none-hash`,快速算法每进程随机 | 所有实例设同一个值:快速算法下也能跨实例对上键;设了会同时覆盖两种算法的默认种子 | 多实例外部缓存的命中 |
| `--prefix-match-unit` · 命中最细能落在几个 token 上 | 启动 | 不设:单个 KV 组时等于块大小;多组时取可缓存组块大小的最大公约数 | 调小(必须整除每个可缓存组的块大小):混合模型可在大块内部命中;只改匹配粒度,不改状态存多密 | 设错启动报 `Invalid prefix_match_unit`,并列出各组块大小 |
| `--mamba-cache-mode` · Mamba 状态怎么进缓存 | 启动 | 开了前缀缓存的 Mamba 与混合模型自动设 `align` | `align`:只在块边界存状态;`all`:每块都存,已弃用(启动告警),模型不支持时退回 `align`,还会让 ModelRunner 退回 V1 | 启动日志 `Mamba cache mode is set to 'align'` |
| `--enable-mamba-shared-prefix-checkpoint` · 在共享前缀的分叉点多存一份 Mamba 状态 | 启动 | 关 | 开:同系统提示词、不同后缀的请求能从块内的分叉点接着算;要同时满足 `align`、Mamba 组开了 EAGLE 或 MTP、匹配单位小于 Mamba 块、不是多模块 MTP | 这类请求的命中长度 |
| `--prefix-cache-retention-interval` · 滑窗与 Mamba 组隔多少 token 留一个检查点 | 启动 | 0:只留回放边界与共享前缀分叉点 | 正值(调度块大小的倍数):额外按间隔留检查点,可命中的位置变多,缓存占的块也变多;模型没有滑窗或 Mamba 组时设非 0 启动报错 | — |
| `--block-size` · 一块几个 token | 启动 | 16;后端和混合模型会改 | 调大:命中粒度变粗;其余影响见 03 章 | 启动日志 `Setting attention block size to` |
| `cache_salt` · 缓存盐 | 请求字段(Chat、Completion、Responses、Anthropic 与池化接口) | 空 | 设了:只和同盐请求共享;非空,至多 128 个字符,不能含 `@`、`/`、`\`、NUL | 同一 prompt 换盐后 `cached_tokens` 归零 |
| `--enable-prompt-tokens-details` · 响应里带命中数 | 启动 | 关 | 开:`usage.prompt_tokens_details.cached_tokens` 给出本条请求命中多少 token,本地与外部合计 | 响应的 `usage` |
| `--kv-cache-metrics` / `--kv-cache-metrics-sample` · 块驻留指标 | 启动 | 关;采样率 0.01 | 开:导出块从分配到驱逐的寿命、驱逐前空闲多久、两次复用的间隔;统计日志不能关 | `/metrics` 里 `vllm:kv_block_idle_before_evict_seconds` 等三个直方图 |
| `--kv-events-config` · 对外发块登记与删除事件 | 启动,JSON | 关 | `enable_kv_cache_events` 设 true:经 ZMQ 发块存入、移除、全清三种事件,引擎外的缓存感知路由靠它 | 订阅端点,默认 `tcp://*:5557` |
| `VLLM_SERVER_DEV_MODE` · 挂开发接口 | 环境变量 | 0 | 设 1:挂出 `/reset_prefix_cache` | 接口是否 404 |

**怎么看。** 一是稳态日志:每 10 秒那行的 `Prefix cache hit rate` 是最近 1000 条请求的命中 token 数除以它们的 prompt token 数。分母是整个 prompt,所以它到不了 100%;被抢占后重新进场的请求单独记账,不算进去;挂了 KV connector 时多一项 `External prefix cache hit rate`,那是外部缓存的命中。二是 Prometheus:`vllm:prefix_cache_queries` 与 `vllm:prefix_cache_hits` 两个计数器都按 token 计,取速率相除就是线上命中率,外部缓存对应 `vllm:external_prefix_cache_queries` 与 `vllm:external_prefix_cache_hits`;直方图 `vllm:request_prefill_kv_computed_tokens` 是每条请求 prefill 真正算了多少 token,不含命中部分。三是请求级:开了上表那个开关后看 `cached_tokens`。四是清缓存:`POST /reset_prefix_cache` 返回 `{"success": true}` 或 `false`,失败时日志是 `Failed to reset prefix cache because some blocks (N) are not freed yet`,成功时是 `Successfully reset prefix cache`;加 `?reset_running_requests=true` 先抢占再清,加 `?reset_external=true` 连 KV connector 那边一起清;离线用 `LLM.reset_prefix_cache()`。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡在线对话或 agent,共享一段长系统提示词 | `vllm serve Qwen/Qwen3-8B --enable-prompt-tokens-details`;系统提示词里别放时间戳这类每次都变的内容 | 前缀缓存默认已开;多一个响应字段,换来每条请求的命中数可见 |
| 多租户服务,租户之间不能靠时延互相探测 | `vllm serve <模型>`,网关给每个租户生成一个 64 个十六进制字符(256 位)的随机串,填进该租户所有请求的 `cache_salt` | 租户内共享、租户间隔离;代价是公共的那段系统提示词每个租户各算一份、各占一份 |
| RL 训推一体,每隔几步换一次权重 | `VLLM_SERVER_DEV_MODE=1 vllm serve <模型>`,每次换权重前调 `POST /pause`(默认中止在跑请求并清前缀缓存),换完再 `POST /resume`;只想单独清缓存时用 `POST /reset_prefix_cache?reset_running_requests=true` | 用在跑请求的一次重算,换旧 KV 不被新权重误用;完整流程与下放层的坑见 18 章 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 大家共用一段系统提示词,命中率却远低于这段的占比 | 请求是否带了不同的 `cache_salt` 或不同的 LoRA;系统提示词里有没有每次都变的内容 | 把变动的内容挪到 prompt 末尾;同一信任组用同一个盐 |
| 低并发命中正常,并发一高命中率就掉 | 稳态日志的 `KV cache usage` 是不是贴着 100% | 降并发上限或调高显存占比;或把 KV 下放到 CPU(05 章) |
| 多轮对话第 2 轮起不命中 | 两轮 prompt 的 token 序列从哪里开始不同:聊天模板有没有改写历史 | 让模板原样保留历史;或由客户端直接发 token |
| 混合模型的命中长度总是某个大数的倍数 | 启动日志 `Setting attention block size to N tokens` | 按启动报错给的块大小设 `--prefix-match-unit`,再确认 Mamba 相关条件都满足 |
| 开了 EAGLE 或 MTP 推测解码后命中变少 | 命中长度是否比预期正好少一块 | 预期如此:最后一个命中块要重算来给草稿头出隐状态(09 章) |
| `/reset_prefix_cache` 返回 `{"success": false}` | 日志里还有几块没放 | 等请求跑完重试,或加 `reset_running_requests=true` |
| 多实例共享外部缓存,互相命中为 0 | 各实例的 `--prefix-caching-hash-algo` 是否一致;有没有 `random per-process NONE_HASH seed` 这行日志 | 统一算法;用快速哈希时所有实例设同一个 `PYTHONHASHSEED` |

## 六、常见误区

- **以为同一个 prompt 发第二遍,TTFT 应该接近 0。** 直觉是「全都缓存过了」。实际最后一个 token 永远要真算,命中又只落在块边界:prompt 恰好是 16 的整数倍时,最后一整块 16 个 token 全部重算。日志里的命中率也因为分母是整个 prompt 而到不了 100%。
- **以为前缀缓存有自己的容量,调大就能提命中率。** 找不到那个参数,于是去翻各种缓存大小。实际它没有独立容量,就是空闲 KV 里还没被重新分出去的块;能影响它的只有显存占比、并发和 KV 下放。命中率随并发下降,多半是在跑的请求把空闲块吃光了,不是哪个缓存设小了。
- **以为上一轮的回答下一轮一定能命中。** decode 写满的块确实登记了键,可下一轮的 prompt 是聊天模板重新渲染、重新切词出来的 token。模板若在历史里改写了上一轮回答(比如删掉思考段),或者文本反切再正切得到了不同的 token,从那里起后面每一块的键都不同,一块都查不到。
- **以为缓存盐是给租户贴的标签,填租户名就行。** 看到「按盐隔离」就当成命名空间用。实际盐是请求里任何人都能填的字段,可猜的盐等于没有盐:攻击者只要猜中就回到同一个缓存里,又能靠时延探测别人的 prompt。字段说明要求它随机、不可预测,举的例子是 256 位。
- **以为换成快速哈希只是更快。** 它还改了两件事:非密码学哈希扛不住蓄意构造的碰撞,多租户下有串 KV 的风险;种子变成每进程随机,多实例之间、同一服务的数据并行副本之间默认对不上键,外部缓存与按事件路由的网关一起失效,除非所有实例设同一个 `PYTHONHASHSEED`。
- **以为 `/reset_prefix_cache` 返回 200 就是清掉了。** 正常返回时 HTTP 状态码都是 200,成败写在响应体里。只要还有请求占着块,它就返回 `{"success": false}`,缓存原封不动。RL 里换完权重不检查这个返回值,就会拿旧权重的 KV 接着生成。
- **以为命中率低一定是缓存被挤掉了。** 先看分母:要 prompt logprobs 的请求默认不查表,不计入命中率;被抢占的请求单独记账也不计入。真正常见的原因是请求之间本来就不共享前缀:系统提示词里嵌了当前时间、请求 ID,开头第一块的键就已经各不相同了。
