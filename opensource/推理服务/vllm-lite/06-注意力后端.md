# vLLM 06|注意力后端

同一个注意力层要跑在 4 代 NVIDIA 卡、AMD 卡和 CPU 上,要服务普通注意力、MLA、稀疏 MLA,还要吃下 BF16 到 FP4 的 KV 精度;怎么在启动时替每一层挑出一份能跑的 kernel,而模型代码一行都不用改。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

注意力 kernel 是按「卡代 × 注意力结构 × 精度」一格一格写出来的,没有哪一份能填满整张表。第 3 代 FlashAttention 只在 Hopper 上有;A100 用的第 2 代既不收 FP8 的 KV,也不收 attention sink;MLA 的 decode 要对一份 576 维的共享潜向量做注意力,而 FlashAttention 在第 4 代之前头维上限是 256;FlashMLA 只编了 Hopper 和 Blackwell 两代。再叠上块大小、滑窗、上下文并行、PD 分离时 KV 的内存排列,一份 kernel 能不能跑,要十几个条件同时成立。

坏的是两样。一是**启动失败**:换了一张卡或一种 KV 精度,原来那份 kernel 不收了,又找不到替补。二是**吞吐悄悄掉**:替补找到了,却是兜底的通用实现,服务照常起来,只有一行日志变了。prefill 与 decode 的形状又不一样:prefill 一条请求带着上千个 query,瓶颈在算力;decode 每条只有 1 个 query,瓶颈在读 KV 的带宽。对 MLA 来说,这两个阶段最省的算法根本不是同一种。

## 二、解法:每个后端自报能跑什么,选择器按卡排队挨个问

最天然的直觉:谁最清楚一份 kernel 能跑什么,就让谁来回答。vLLM 把每份 kernel 包成一个后端,一个后端由四件东西组成:

- **能力声明**:收哪些卡代、头维、模型精度、KV 精度、块大小,支不支持 sink、滑窗、稀疏、非因果、上下文并行、PD 分离的 KV 传输、批不变。它们汇成一个准入校验:给一组条件,返回「不收的原因」列表,空列表就是能跑。
- **元数据构建器**:每一步把调度结果翻译成这份 kernel 要的参数(块表、每条请求的 query 从哪开始、decode 与 prefill 的分界)。每个 KV cache 组一个,组内所有层共用。它还声明自己能进哪种 CUDA graph(08 章),以及 query 多短才算 decode。
- **实现**:真正调 kernel、把新的 K、V 写进缓存的那一段。
- **KV 布局声明**:它的 kernel 能读哪几种内存排列,比如一块之内先按头排还是先按 token 排。

![同一套选择器在 6 种「模型 × 卡 × KV 精度」下的结果:上半是普通注意力的候选表,H100 上 FlashAttention 直接胜出;A100 开 FP8 KV 时 FlashAttention 因不收 FP8 KV 被刷掉,轮到 FlashInfer;A100 上带 attention sink 的模型连刷掉 FlashAttention 与 FlashInfer,落到 Triton。下半是 MLA 的候选表,H100 BF16 KV 选 FlashAttention MLA,换成 FP8 KV 后它被刷掉、FlashMLA 胜出且块大小改成 64,B200 上 FlashInfer MLA 排第 1 且块大小改成 32。底部黄条说明用户点名时不看候选表,只校验被点名的那一个,不过就启动报错](/opensource/vllm-lite/06a-backend-selection.svg)

**选择只在启动时做,按层的签名缓存。** 模型里每个注意力层构造时,把自己的签名交给选择器:头维、模型精度、KV 精度、是不是 MLA、是不是稀疏、有没有 sink、有没有滑窗,外加整个服务的几项条件(用户钉没钉块大小、开没开上下文并行与 PD 分离)。用户点名了后端,就只校验被点名的那一个。没点名,平台按卡代、是否 MLA、KV 精度和头数现排一张候选表,逐个调准入校验,第一个通过的胜出。签名相同的层只选一次;混合模型里滑窗层与全注意力层签名不同,可以落到不同的后端,也可以按层的类型分别点名。

**选完之后,三件事跟着它定。** 块大小由后端声明它收哪几档来改(03 章)。KV 的内存排列由 EngineCore 收齐所有后端的布局声明取交集,整个模型只用一种,交集为空就启动失败。decode 与 prefill 的分界用构建器自己的阈值,ModelRunner 负责把短请求排在批的前面(07 章)。

**枚举里的 44 个名字不是 44 个候选。** CUDA 的候选表只用到其中 18 个,AMD、CPU、Intel GPU 的表另用 10 个。剩下 16 个里,7 个由模型代码按名直接接上(DeepSeek V4 与 V4.1 的稀疏 MLA、MiniMax M3 的稀疏注意力),4 个只能点名才用,2 个是别名,3 个是占位或视觉编码器专用。Mamba、线性注意力、短卷积这类状态层住在另一个枚举里,不参与竞争,由层的类型直接决定;它们的状态怎么记账见 03 章。

**MLA 为什么有两条计算路径。** MLA 的 KV cache 每个 token 只存 512 维的潜向量加 64 维的位置部分(DeepSeek V3 的维度,下同)。注意力有两种算法。**展开**:用上投影把历史潜向量还原成 128 个头各自的 K、V,再做普通多头注意力,QK 维 192、V 维 128;代价是还原要按历史长度乘一遍大矩阵。**吸收**:把 K 的上投影提前乘进 query,直接拿潜向量当 K 和 V,128 个头共享同一份,QK 维 576、V 维 512,形状就是 MQA;每次点积长了 3 倍,但 KV 只读 1 份。prefill 的 query 多、和历史差不多长,还原的开销摊得开,展开省算力;decode 每条只有 1 个 query,吸收省带宽。

vLLM 在 MLA 层里把一批按 token 切成两段:排在前面、query 足够短的请求走吸收,其余走展开。吸收段用候选表选出来的主后端;展开段另有一张 prefill 候选表单独选,Hopper 及更早只有 FlashAttention 一个候选,Blackwell 有 4 个,先后还随模型的头维变。「多短算 decode」由主后端定:FlashAttention MLA 把 query 不超过 512 的请求都算作 decode,FlashMLA 是 128 且要求这些请求一样长,于是短的 prefill 块也走吸收。展开段要把整段历史还原成多头 K、V,为了不撑爆显存,历史按一块上限 65536 个 token 的工作区分块还原、分块算,再按各块的 log-sum-exp 合并。

**稀疏 MLA 这一族。** DeepSeek V3.2 这类模型多一个索引器,给每个 query 从全部历史里挑 top-k 个 token(k 由模型配置给定,元数据里的缺省值是 2048),稀疏后端只对这 k 个做吸收式注意力。索引器自己的 K 也存在 KV cache 里,也有一个后端,只是不在枚举里。候选表里稀疏后端排在各卡代 MLA 表的末尾;准入校验要求「稀疏与否」和层一致,稠密层走不到它们,稀疏层也走不到稠密的,一张表实际分成互不干扰的两段。Blackwell 上稀疏那一段的先后还当场排:FP8 KV 或每卡头数不超过 16 时 FlashInfer 的稀疏版在前,否则 FlashMLA 的稀疏版在前。prefill 里最长的序列不超过 k 时,挑出来的就是全部历史,这一段改走稠密的展开路径;开了 HiSparse 冷热分离(05 章)的层一律走吸收。

**prefill 与 decode 分不分开,看后端。** 普通注意力一个后端管两个阶段,区别在内部:FlashAttention 与 Triton 用一个变长 kernel 吃下 prefill 和 decode 混在一起的整批;FlashInfer 把批切成 decode 段与 prefill 段,各走一套 kernel。MLA 一定分开,而且两段是两个后端。

为什么实际不吃亏:选择只在启动时按签名各做一次,运行时就是直接调用;模型代码只认注意力层,换卡换精度不用动模型;加一份新 kernel 等于写一个后端类、在枚举里登记一行、在某张候选表里插一个位置;不收的原因是一条条字符串,选不中时能全部列出来。

## 三、代价

**候选表回答的是「能不能跑」,不是「快不快」。** 先后顺序写死在平台代码里,每个卡代一套,依据是开发者当时的基准测试;校验通过就用,启动时不实测。代码注释里就写着 Blackwell 上排第 2 的 TokenSpeed MLA 在 batch 超过 8 左右时比第 1 位快、batch 不超过 2 时反而慢,它仍然排第 2。

**一个条件变了,后端就换人,只留一行 info 日志。** 同一个 MLA 模型在 H100 上把 KV 从 BF16 换成 FP8,decode 就从 FlashAttention MLA 换成 FlashMLA,块大小从 16 变成 64;A100 上的普通注意力从 FlashAttention 换成 FlashInfer,能进哪种 CUDA graph 也跟着变(08 章)。换人不报错,被刷掉的原因只在 debug 级日志里。

**点名没有退路。** NVIDIA 与 AMD 上点名的后端校验不过就启动失败,不会退回自动(AMD 上个别量化层例外);一个全局点名作用于每一层,混合模型里只要有一类层不收它,整个服务起不来,只能改成按层的类型分别点名。反过来,CPU 上点名错了不报错,打一行 info 后照用 CPU 后端。

**钉块大小会挤掉更好的后端。** 不钉时块大小不参与校验,选完再改成后端收的档;钉了,它就成了准入条件,排在前面、只因块大小被刷掉的后端让给后面的,只打一行 warning。

**MLA 两段各有各的账。** prefill 后端单独选、单独校验,decode 那段能跑不代表服务起得来。展开段的工作区在启动剖析时按最坏情况占一次显存,KV 能分到的就少这一块:DeepSeek V3 在 TP 8 下每卡 16 个头,还原后的历史是 65536 × 16 × 256 个 BF16 数,每卡 512 MiB。

## 四、和 SGLang、TensorRT-LLM 比:「这个组合能不能跑」由谁回答

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都要替每一层挑一份 kernel,分歧在谁来判断一个组合能不能跑,以及 MLA 的两条路径由谁来切。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 没指定时怎么落到一份 kernel | 平台按卡代、结构、精度排候选表,逐个问后端自带的准入校验,取第一个通过的 | 一棵按卡代、结构、推测解码分叉的决策树直接返回一个名字,没有候选列表 | 默认用自家 kernel,工厂只认 3 个名字 |
| 指定的跑不了时 | 启动报错并列出原因,不回退 | 部分组合被改写成别的名字或别的页大小,只打日志;其余在构造后端时抛错 | 不认识的名字打警告,退回自家 kernel |
| MLA 的展开与吸收谁来切 | MLA 层把同一批按 token 切两段,前段吸收、后段展开;展开段另选一个 prefill 后端 | 模型代码按整批的模式挑一条,每个后端配一个挑选函数 | MLA 模块把同一批切成 context 段与 generation 段,两段用同一个后端名建出来 |
| prefill 与 decode 能否用两个后端 | 普通注意力不能;MLA 的展开段天然是另一个 | 能,两个字段不同就套一层分发器,官方标为实验 | 不能 |
| 稀疏注意力放在哪 | 稀疏 MLA 各变体与稠密的同在一张候选表,靠准入条件分开;少数由模型代码按名接上 | 每个模型家族一个稀疏后端名,内部再按卡与精度挑 prefill、decode 两个子实现 | 稀疏算法另起一层挑 token,同一个后端名下换成稀疏子类 |

vLLM 把「能不能跑」交给每个后端自己回答,选择器只负责排队,所以能在启动时列出每个候选被刷掉的原因,代价是顺序只按卡代写死。SGLang 的判断散在决策树和一串改写里,TensorRT-LLM 干脆只留 3 个名字。MLA 上 vLLM 是三家里唯一让展开段单独选后端的,prefill 能用上另一家的 kernel,也多了一处会选不中的地方。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。`-ac.xxx` 是 `--attention-config` 的点号写法,也可以整份写成 JSON 传给 `-ac`。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--attention-backend` · 全局点名一个后端 | 启动 | 不设,等同 `auto` | 大小写不敏感;只校验它,不过就报错;和 `-ac.backend` 互斥,两个都给直接报错 | 日志 `Using … backend.`(点名)或 `Using … attention backend out of potential backends`(自动) |
| `-ac '{"backend_per_kind": {...}}'` · 按 KV cache 组的种类分别点名 | 启动 | 空 | 键取 `full_attention`、`sliding_window`、`mla_attention`、`sliding_window_mla`、`encoder_only_attention`、`cross_attention`;没列的种类回落到全局点名或自动;列了的不收就报错 | 同上,每类层各一行 |
| `-ac.mla_prefill_backend` · MLA 展开段用谁 | 启动 | 不设:Hopper 及更早只试 `FLASH_ATTN`;Blackwell 依次 `FLASH_ATTN`、`TRTLLM_RAGGED`、`FLASHINFER`、`TOKENSPEED_MLA`(头维为 192/64/256 的模型把 `TRTLLM_RAGGED` 提到第 1);ROCm 先 `ROCM_AITER_FA` 再 `FLASH_ATTN` | 点名的不收就报错 | 日志 `Using … MLA prefill backend.` |
| `-ac.flash_attn_version` · FlashAttention 用第几代 | 启动 | 不设:Hopper 用 3,Blackwell 用 4,其余 2 | 只对 `FLASH_ATTN` 生效;在 Blackwell 上设 3 会被改成 4(装不上则 2);设 2 会让 Hopper 失去 FP8 KV 与 sink 支持 | 日志 `Cannot use FA version 3 on Blackwell platform` |
| `-ac.use_trtllm_attention` · FlashInfer 内部用不用 TensorRT-LLM 的 kernel | 启动 | 不设,按卡与头数自动 | 设 `false`:`FLASHINFER` 同时失去 sink 支持,带 sink 的模型会被刷到后面的候选 | DEBUG 日志里 `attention sinks not supported` |
| `-ac.disable_flashinfer_q_quantization` · FP8 KV 时不把 Q 量化成 FP8 | 启动 | `false` | 设 `true`:Q 以模型精度进 kernel,只在 KV 是 FP8 时有区别 | — |
| `-ac.sparse_mla_force_mqa` · 稀疏 MLA 的 prefill 也走吸收 | 启动 | `false` | 设 `true`:短 prefill 不再改走稠密展开,全部按 top-k 走吸收 | — |
| `--block-size` · 钉住块大小 | 启动 | 不钉:16,再按后端改(03 章) | 钉了之后参与准入校验,更靠前的后端可能被挤掉 | 日志 `--block-size N precluded higher-priority backend(s)` |
| `--kv-cache-dtype` · KV 精度 | 启动 | `auto` | 换精度常常就换后端,见上图与 13 章 | 选中那行日志变没变 |
| `VLLM_KV_CACHE_LAYOUT` · 强制 KV 的内存排列 | 环境变量 | 不设,取所有后端声明的交集里得票最多的 | 必须落在交集里,否则启动失败;旧名 `NHD`、`HND` 等价于 `LBNHC`、`LBHNC` | 启动报错 |
| `VLLM_ROCM_USE_AITER` · ROCm 上打开 AITER 系后端 | 环境变量 | `0` | 设 `1`:MLA 首选 `ROCM_AITER_MLA`;普通注意力里 AITER 的后端排在 `ROCM_ATTN` 之后 | 选中那行日志 |
| `VLLM_LOGGING_LEVEL` · 日志级别 | 环境变量 | `INFO` | 设 `DEBUG`:看到每个候选被刷掉的原因 | `Some attention backends are not valid for cuda with AttentionSelectorConfig(...)` |
| `--fail-on-environ-validation` · 未知的 `VLLM_` 环境变量直接报错 | 启动 | 关 | 开:拼错或已删掉的变量起不来,不再只打 warning | 日志 `Unknown vLLM environment variable detected` |

**卡型 × 注意力结构 → 默认后端。** BF16 KV、没有特殊结构时的首选;实际以启动日志为准。

| 卡 | 普通注意力 | MLA 吸收段(decode) | MLA 展开段(prefill) | 稀疏 MLA |
|---|---|---|---|---|
| A100、L40S(SM8x) | `FLASH_ATTN`(第 2 代);FP8 KV 落到 `FLASHINFER`;带 sink 落到 `TRITON_ATTN` | `TRITON_MLA` | `FLASH_ATTN` | 没有候选,启动报错 |
| H100、H200(SM90) | `FLASH_ATTN`(第 3 代);多模态前缀模型先试 `TRITON_FLASH_ATTN` | `FLASH_ATTN_MLA`;FP8 KV 落到 `FLASHMLA`(块 64) | `FLASH_ATTN` | `FLASH_ATTN_MLA_SPARSE`;头维 512 时 `FLASHINFER_MLA_SPARSE_SM90` 提到第 1;FP8 KV 落到 `FLASHMLA_SPARSE` |
| B200、GB200、B300(SM10x) | `FLASHINFER`;非因果时 `FLASH_ATTN` 在前;多模态前缀模型先试 `TRITON_FLASHINFER` | `FLASHINFER_MLA`(块 32) | `FLASH_ATTN`,不行依次往后 | FP8 KV 或每卡头数不超过 16:`FLASHINFER_MLA_SPARSE`;否则 `FLASHMLA_SPARSE` |
| RTX 5090、RTX PRO 6000(SM120) | `FLASH_ATTN` | `TRITON_MLA` | `FLASH_ATTN` | `FLASHINFER_MLA_SPARSE_SM120` |
| AMD Instinct(ROCm) | `ROCM_ATTN`;挂 KV connector 时跳过它 | `TRITON_MLA`;`VLLM_ROCM_USE_AITER=1` 时 `ROCM_AITER_MLA` | `ROCM_AITER_FA`,再 `FLASH_ATTN` | `ROCM_AITER_MLA_SPARSE` |
| CPU | `CPU_ATTN` | x86 有 AMX 时 `AMX_MLA`,否则 `CPU_MLA` | CPU 上的 SDPA | 不支持,直接报错 |

**怎么看。** 一是启动日志:自动选择打 `Using FLASH_ATTN attention backend out of potential backends: ['FLASH_ATTN', 'FLASHINFER', …]`,方括号里是通过校验的全部候选,第一个就是选中的;点名时只有 `Using … backend.`;MLA 模型另有 `Using FLASH_ATTN MLA prefill backend.`;后端改了块大小有 `Setting kv cache block size to 64 for FLASHMLA backend.`。二是 `VLLM_LOGGING_LEVEL=DEBUG` 后的那行 `Some attention backends are not valid for …`,每个被刷掉的候选后面跟着原因,常见的是 `kv_cache_dtype not supported`、`compute capability not supported`、`block_size not supported`、`attention sinks not supported`、`sparse not supported`。三是全部候选都不收时的报错 `No valid attention backend found for cuda with AttentionSelectorConfig(...). Reasons: {...}`,原因字典和 DEBUG 那行一样。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡 H100,Qwen3 这类 GQA 模型,在线服务 | `vllm serve Qwen/Qwen3-14B` | 什么都不设:第 3 代 FlashAttention,块 16;它声明任何批都能进整图,但默认模式下只有 decode 批走整图、混合批走分段图(08 章);升级 vLLM 后留意选中那行日志有没有变 |
| A100 上开 FP8 KV 换并发,并锁住后端 | `vllm serve <模型> --kv-cache-dtype fp8 --attention-backend FLASHINFER` | 本来就会落到 FlashInfer,写明是为了换版本或换卡时不静默换人;代价是挪到不收它的卡上直接起不来;FlashInfer 在 A100 上只有纯单 token 的 decode 批能进整图,推测解码的验证批走分段图(08 章) |
| 8 卡 H100 跑 DeepSeek V3,KV 用 FP8 | `vllm serve deepseek-ai/DeepSeek-V3 -tp 8 --kv-cache-dtype fp8` | decode 落到 FlashMLA、块改成 64,prefill 仍是 FlashAttention;用 KV 容量翻倍换块变粗(前缀命中粒度见 04 章);要回到 FlashAttention MLA 只能改回 BF16 KV |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报 `No valid attention backend found` | 报错里每个候选的原因 | 多半是 KV 精度、头维或 sink;换 KV 精度或去掉 `--block-size`;稀疏 MLA 在 A100 上本来就没有候选 |
| 启动报 `Selected backend … is not valid for this configuration` | 原因列表 | 去掉 `--attention-backend` 回到自动;混合模型改用 `backend_per_kind` 只点一类层 |
| 换卡、升级或改了 KV 精度后吞吐骤降 | 选中那行日志的后端名变没变 | 设 `VLLM_LOGGING_LEVEL=DEBUG` 看前面的候选为什么被刷;确认是装缺了还是条件变了 |
| 日志 `--block-size N precluded higher-priority backend(s)` | 是否钉了块大小 | 去掉 `--block-size`,让后端自己定档 |
| MLA 模型报 `No valid MLA prefill backend found` 或 `Selected MLA prefill backend … is not valid` | `-ac.mla_prefill_backend` 与卡代 | 去掉点名;Hopper 上只有 `FLASH_ATTN` 一个候选,它不行就要换卡或换精度 |
| 设了 `VLLM_ATTENTION_BACKEND` 没效果 | 日志 `Unknown vLLM environment variable detected: VLLM_ATTENTION_BACKEND` | 改用 `--attention-backend`;加 `--fail-on-environ-validation` 让这类错误起不来 |
| 带 sink 的模型在 H100 上落到 `TRITON_ATTN` | 是否设了 `-ac.use_trtllm_attention=false`,FlashAttention 是否第 3 代 | 去掉该设置;确认 `-ac.flash_attn_version` 没被设成 2 |
| AMD 上 DeepSeek 很慢 | 选中的是不是 `TRITON_MLA` | 设 `VLLM_ROCM_USE_AITER=1` |
| `VLLM_KV_CACHE_LAYOUT` 设了之后启动失败 | 各后端声明的布局 | 去掉它;布局由各后端的交集决定 |

## 六、常见误区

- **以为 `VLLM_ATTENTION_BACKEND` 还能选后端。** 网上大量调优文章和旧版文档都这么教,照做也不报错。这个基准全仓库没有一处读取它,启动只打一行 `Unknown vLLM environment variable detected`,后端照旧自动选。要点名只有 `--attention-backend` 或 `-ac.backend`。
- **以为点名的后端不行会自动退回。** 自动选择是「不行就试下一个」,人们以为点名也一样。NVIDIA 与 AMD 上点名只校验这一个,不过直接启动失败;这其实是好事,能挡住「以为在跑 A、实际在跑 B」。反过来 CPU 上点名错了不报错,只打 `Cannot use … backend on CPU.` 后照用 CPU 后端。
- **以为 44 个名字都是能挑的 kernel。** 枚举长得像一张菜单,报错时还会把 44 个名字全列出来。实际 CUDA 候选表只用 18 个;`FLASHMLA_SPARSE_DSV4` 这类由模型代码按名接上;`TORCH_SDPA` 的路径是空串,只给视觉编码器用;`NO_ATTENTION` 指向的模块在仓库里根本不存在,点它会在 import 时失败。Mamba 与线性注意力在另一个枚举里,`--attention-backend` 管不到它们,用哪个由层的类型直接决定。
- **以为 `--attention-backend FLASHMLA` 管住了 MLA 的全部。** 它只管吸收那段,也就是 decode 与短 prefill;展开那段由 `-ac.mla_prefill_backend` 另选。prefill 报错时去改主后端没用,Hopper 上展开段只有 FlashAttention 一个候选。
- **以为 decode 就是 query 长度等于 1。** 调度器里确实只有「每条追几个 token」,人们就以为后端按 1 划界。批里谁走吸收由主后端的阈值定:`FLASH_ATTN_MLA` 是 512,`FLASHMLA` 是 128 且要求等长;推测解码时阈值至少抬到 1 加草稿长度。看 profile 时 decode kernel 吃了不少 prefill token,原因在这里。
- **以为官方设计文档里的优先级脚注适用于所有卡。** 文档写的是稀疏 MLA 开 FP8 KV 时「总是」优先 `FLASHINFER_MLA_SPARSE`。代码里这条只在 SM10x 分支成立;Hopper 上稀疏那段按 `FLASH_ATTN_MLA_SPARSE`、`FLASHMLA_SPARSE` 排,只看头维是不是 512,不看 KV 精度。文档与代码冲突时以代码为准。
- **以为换后端只换了一个 kernel。** 后端还决定块大小、能进哪种 CUDA graph、KV 的内存排列、decode 的分界。KV 从 BF16 换成 FP8 之后,H100 上的 MLA 块从 16 变成 64、前缀命中粒度变粗,A100 上推测解码的验证批进不了整图,根子都是后端换了人,而不是 FP8 本身。
- **以为钉 `--block-size` 只影响 KV 的粒度。** 这个参数看起来和 kernel 无关。钉了之后它进入准入校验:H100 上 DeepSeek 开 FP8 KV 时本该落到只收 64 的 `FLASHMLA`,钉 16 就把它挤掉,一路落到 `TRITON_MLA`;日志里只有一行 `precluded higher-priority backend(s)` 的 warning。
