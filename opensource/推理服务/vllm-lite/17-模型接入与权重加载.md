# vLLM 17|模型接入与权重加载

一个模型名进来,vLLM 怎么从 386 个架构名里找到它的实现、找不到时退到哪里,又怎么把 checkpoint 里的张量切到每张卡上;冷启动的时间花在哪几段,哪种起法能拿掉哪几段。

说法都在源码基准 `94f4170df3`(tag `v0.30.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

这一章坏两个指标。

**新模型接不进来。** 模型仓库的配置文件里写着一个架构名字符串,vLLM 只认这个字符串来决定用哪份实现。注册表里现在有 386 个架构名,指向 263 个模型模块。启动时要是把它们全导入一遍,每个进程都得为用不上的模块付导入时间;更麻烦的是,有些模型文件一导入就碰 CUDA,父进程先初始化了 CUDA,之后再 fork 出 worker 就会出错(01 章)。反过来,配置里的名字一个都对不上,服务就起不来。

**冷启动慢。** 从拉起进程到接住第一条请求,中间要下载、读文件、切片、搬进显存、逐层整理,之后还有剖析显存与编译录图(03、08 章)。单机 8 卡、TP 8 时,默认每个 worker 进程都把整份 checkpoint 的张量逐个过一遍内存,再从每个张量里截下自己那 1/8。文件放在网络文件系统上,这种由缺页触发的读会碎成大量零散请求。扩缩容、故障重拉、RL 里反复重启时,这笔账每次都从头付。

## 二、解法:名字用到才导入,权重由每个参数自取一片

最天然的直觉是两张表:名字查类,格式查读法。vLLM 就是这么做的,只是两张表各多了一层讲究。

**架构名只存成字符串。** 注册表是一张「架构名 → 模块名加类名」的表,真要建模型时才导入命中的那一个模块。可引擎在建模型之前就得知道一些事:是不是多模态、支不支持流水线并行、有没有 Mamba 层,这些决定进程怎么拉起、KV 怎么分组。答案要导入类才看得到,vLLM 就另起一个用完即弃的子进程去导入、读出类上的能力标志,主进程一次也不碰 CUDA;结果按模型文件内容的哈希落盘缓存,文件不变,下次启动连子进程都省了。

**模型类用能力接口声明自己支持什么。** 这是接入一个新模型的主要功课。最低要求只有三件:构造时只收整份配置和一个层名前缀,能把 token 编号变成嵌入,前向收 token 编号和位置。其余能力各是一个接口,类继承了才算数。流水线并行要求非首段能收上一段的中间结果、能造一份空的中间结果供剖析用,没继承时开流水线并行在配置阶段就报错;LoRA 要求声明哪些投影被融合成一块、嵌入层叫什么,没继承时开 LoRA 直接报错;多模态(15 章)、推测解码要的隐藏状态(09 章)、量化用的名字映射(13 章)各有自己的接口;混合模型、无注意力这类标志决定 KV 怎么记账(03 章)。

**找不到原生实现时退到 Transformers 后端。** 配置里的架构名一个都不在表里、实现选择是自动时,vLLM 去 Transformers 库里找同名类;库里没有,再看模型仓库有没有自带代码,这一步要显式信任远程代码。找到的类还要自报能换注意力实现,才会被包进一个通用外壳:外壳按模型声明的张量并行计划把线性层换成 vLLM 的切分线性层,把注意力换成分页注意力,把词表嵌入换成按卡切词表的版本,其余照原样跑。注册表里另有 14 个架构名直接指向这个外壳。换上去的都是 vLLM 自己的层,所以量化、LoRA、流水线并行也接得上。

**加载器按格式分派,干的是同一件事。** 15 个格式名落到 7 个加载器类,插件还能注册新的格式名。每个加载器都走三步:在目标卡上按模型精度建出空参数,把权重灌进去,逐层整理。默认加载器的「灌」是一条流水线:文件逐个打开,张量逐个吐出;模型先把磁盘上的名字改成自己的名字,分开存的 q、k、v 投影被标上「我是融合块里的第几段」;再按名字前缀一层层往下递,递到参数时由参数自带的装载函数按本卡的 TP 序号截出一片,拷进显存。流水线并行里不归本段的层只是占位,递到就跳过。量化模型在这一步不做换算,加载器只把字节原样拷进每层量化方法声明的参数,换算与重排都在逐层整理那一步(13 章)。

**冷启动的几段,各有起法能拿掉。**

![一张 5 行 7 列的表,讲单机 8 卡 TP 8 下从模型名到能接请求的 7 段:下载、读配置找类、建空模型、读 checkpoint、截本卡一片拷进显存、每层整理、剖析编译录图,其中第 2 到第 7 段在 8 个 worker 进程里各自并行,最慢的卡决定就绪时间。默认起法里下载由一个进程做、其余等文件锁,之后每张卡都把整份 checkpoint 过一遍再各截 1/8;网络盘自动预取只把读 checkpoint 那一段变成每卡顺序预热 1/8 的文件进页缓存;预分片不再下载、每卡只读自己那份文件且不用再截;权重缓存守护进程只在元设备上建形状,不读盘、经 CUDA IPC 映射守护进程整理好的那份,只剩编译录图;进程快照恢复时下载、找类、建模型、编译录图都随进程恢复,但读 checkpoint、拷卡、逐层整理要重走一遍](/opensource/vllm-lite/17a-cold-start-stages.svg)

图外还有三条路:混合专家模型开专家并行时,可以在读文件之前按名字里的专家编号跳过不归本卡的专家(专家怎么分到卡上见 11 章);权重可以用 Run:ai 流式加载器直接从对象存储读;也可以用 Tensorizer 把整个模型序列化成一个文件再反序列化回来。bitsandbytes 与 GGUF 的读法已随插件搬出仓库(13 章),树内只留下插件注册新格式名的口子。

为什么这样实际不吃亏:查表只付命中那一个模块的导入;能力标志的子进程只在模型文件改过之后跑一次;张量一个一个地吐,默认走内存映射,主机内存里不会同时摊开整份 checkpoint;所有加载器共用建空模型与逐层整理两步,接一种新格式只要实现下载与灌权重两个方法。

## 三、代价

**退到 Transformers 后端能跑,不保证快。** 模型没声明张量并行计划时,外壳只能在认得出的融合模式上切分,认不出的线性层每张卡一整份;没声明流水线并行计划时,按子模块的声明顺序硬切,结构不规整就报错;用 MLA 的模型要是融合器没匹配上,直接关掉 MLA,退成把 V 头维补齐的普通注意力。这些都只在启动时打一行警告。

**默认没有去重。** 每张卡都把整份 checkpoint 过一遍,再丢掉 7/8。自动预取只在认出 NFS 或 Lustre、且整份 checkpoint 不超过可用内存 90% 时才打开;别的网络文件系统认不出来,照旧按缺页零散地读。

**省读盘的起法都拿灵活性换。** 预分片文件按存档时的 TP 度切死,换 TP 度就要重存;官方存档脚本要从本地目录起一个完整引擎,开着 LoRA 不能存。权重缓存守护进程在每张卡上常驻一份整理好的权重,零拷贝模式下引擎直接用那块显存,所以不能再开 sleep 模式;只放行声明能直接吃整理后权重的量化方法,别的硬报错;守护进程不在或指纹对不上时,默认打一行警告退回读盘,重启时间悄悄回到默认起法。

**进程快照换的是权限与可移植性。** 只支持 x86 Linux、单卡、一个不带认证的明文 HTTP 端口,不支持推测解码;要装 CRIU 与它的 CUDA 插件、要 root、要在内核里关掉 CRIU 存不下的异步 IO 接口;模型必须是远端仓库加 40 位的固定修订号。恢复时主机、卡、驱动、内核、Python、PyTorch、vLLM 版本、引擎参数都要和存档时一致,对不上直接失败,不退回普通启动。权重与 KV 在存档前已经让出,恢复时仍要从文件重读一遍。

**校验只在不量化时严格。** 不量化的模型加载完会核对每个参数都被 checkpoint 填过,缺了就报错;量化模型默认不核对,缺的参数就停在建空时的值。

## 四、和 SGLang、TensorRT-LLM 比:模型文件什么时候导入,重启时省掉哪几段

对照对象是 SGLang(基准 826d5170ae)与 TensorRT-LLM(基准 59f5c47f2e)。三家都直接吃 HuggingFace 格式的 checkpoint,分歧在注册表什么时候付导入的钱、没有原生实现时退不退、以及重启时靠什么跳过读盘。

| 必须有人做的事 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 架构名落到模型类 | 表里只存模块名和类名,用到才导入;能力标志在一次性子进程里探,按文件内容哈希落盘缓存 | 启动时把模型目录下的文件逐个导入;缺依赖的文件打一行警告跳过,那个架构就成了不支持 | 一张静态索引记着架构名在哪个模块,用到才导入 |
| 没有原生实现 | 自动退到 Transformers 后端,打一行警告 | 同样自动退到 Transformers 实现 | 报未知架构 |
| 同机多卡读同一份文件 | 默认各读各的;认出 NFS、Lustre 且装得进内存时,自动按卡分摊预热页缓存 | 分摊预热要手动打开 | 兼容的加载默认按卡条带预读 |
| 重启时不再读盘 | 每卡一个权重缓存守护进程,经 CUDA IPC 映射整理好的权重;守护进程不在或指纹不合,默认退回读盘 | 同样有守护进程;指纹不合直接报错退出 | 节点共享显存池;连不上直接失败,没有退路 |
| 把初始化好的整个进程存档 | 实验性的进程快照,只限单卡 | 全树没有 | 全树没有 |

vLLM 的取舍是「先起来再说」:注册表懒加载、没有原生实现就退 Transformers、守护进程不可用就退回读盘,宁可慢也不失败,代价是降级只留一行警告。TensorRT-LLM 站在另一头,未知架构和共享显存连不上都直接失败;SGLang 在注册表上走急切导入,在守护进程上和 TensorRT-LLM 一样选择报错。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。进程快照是单独的 `vllm snapshot create`、`inspect`、`restore` 三个子命令;权重缓存守护进程用 `python -m vllm.model_executor.model_loader.weight_cache.daemon` 加上与引擎一致的模型和并行参数单独起,每个 TP rank 一个,不支持流水线并行。

**怎么看。** 冷启动的时间按四行日志拆:`Time spent downloading weights for …` 是下载;`Loading weights took N seconds` 只算默认加载器从拿到文件列表到灌完最后一个张量,不含建模型与逐层整理;`Model loading took X GiB memory and Y seconds` 是整段加载,含建模型、逐层整理、LoRA 包装与草稿模型;`init engine (profile, create kv cache, warmup model) took … (compilation: …)` 是之后的剖析、分 KV、编译录图(03、08 章)。后两行相减大,问题在编译;`Loading weights took` 占了大头,问题在读盘,再看 `Filesystem type for checkpoints` 那一行认出的是什么文件系统、有没有 `Prefetching checkpoint files into page cache started`。实现落到了谁:原生实现不打额外日志,Transformers 后端打 `Using Transformers modeling backend.`,缺计划时再打 `does not define a tensor parallel plan` 或 `does not define a pipeline parallel plan`。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡、模型在网络盘、同一配置反复重启 | 先跑 `examples/features/sharded_state/save_sharded_state_offline.py --model <本地模型目录> --tensor-parallel-size 8 --output <预分片目录>`,之后 `vllm serve <预分片目录> -tp 8 --load-format sharded_state` | 每张卡只读自己那 1/8 文件;多占一份存储,换 TP 度要重存,逐层整理照常跑 |
| 同一台机上频繁重拉引擎(弹性扩缩、故障恢复) | 先常驻 `python -m vllm.model_executor.model_loader.weight_cache.daemon --model <模型> --tensor-parallel-size 4`,引擎 `vllm serve <模型> -tp 4 --load-format ipc_cache --model-loader-extra-config '{"fallback": false}'` | 重启跳过下载、读盘、整理;每张卡常驻一份权重,不能开 sleep 模式;关掉退回后守护进程没起来就直接失败,不会悄悄慢回去 |
| 新架构还没有原生实现,仓库自带模型代码 | `vllm serve <仓库> --trust-remote-code`,想确认走的是外壳就加 `VLLM_LOG_MODEL_INSPECTION=1` | 用吞吐换能跑;模型没声明张量并行计划时,TP 下认不出的线性层每张卡一整份 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 报 `Model architectures [...] are not supported for now` | 配置里的 `architectures`;该装的插件装没装、`VLLM_PLUGINS` 有没有把它滤掉 | 装插件或升级;想走 Transformers 后端,看仓库有没有 `auto_map` 并加 `--trust-remote-code` |
| 报 `was supported in vLLM until v…` | 这个架构已从树里删掉 | 用报错里给的旧版本,或换同系列的新架构 |
| 报 `is not supported in-tree anymore. Please install the plugin` | 架构已搬到树外插件 | 按报错里的地址装插件 |
| 报 `failed to be inspected` | 往上翻 `Error in inspecting model architecture` 与子进程的错误输出 | 多是模型文件缺依赖;装上后重启,缓存按文件哈希自动失效 |
| 报 `Failed to load the model config` 并提示信任远程代码 | 仓库是不是自带配置代码 | 确认仓库可信后加 `--trust-remote-code` |
| 报 `Pipeline parallelism is not supported for this model` | 模型类有没有实现流水线并行接口 | 改用 TP;或 `--model-impl transformers` 走外壳,外壳实现了这个接口 |
| 报 `does not support LoRA yet` | 模型类有没有实现 LoRA 接口 | 换有 LoRA 接口的实现(16 章) |
| 吞吐明显低于同尺寸模型 | 有没有 `falling back to Transformers implementation`、`does not define a tensor parallel plan` | 结构确实一致时,用 `--hf-overrides` 把 `architectures` 指到有原生实现的同族架构名 |
| 报 `Following weights were not initialized from checkpoint` | checkpoint 的张量名与模型对不上 | 核对 `architectures` 与仓库文件;确认缺的本来就可以缺,才用 `enable_weights_track: false` 关掉校验 |
| 报 `Cannot find any model weights` | `--load-format` 的文件模式与仓库里的文件对不对得上 | 换 `--load-format`,或检查 `--ignore-patterns` |
| 网络盘上 `Loading safetensors checkpoint shards` 走得很慢 | `Filesystem type for checkpoints` 认出的是什么 | 不是 NFS、Lustre 就显式 `--safetensors-load-strategy prefetch` 或 `eager`;内存不够时改预分片 |
| 用了 `ipc_cache`,重启还是慢 | 有没有 `Weight cache unusable (…); falling back to disk loading` | 查守护进程在不在、参数与引擎一致不一致;要失败得响亮就设 `fallback: false` |
| 报 `does not support loading from pre-processed weights` | 这个量化方法没声明能直接吃整理后的权重 | 这条不会退回读盘;换放行的量化格式,或不用 `ipc_cache` |
| 启动 10 分钟后超时 | `Model loading took` 与 `init engine … took` 哪个大 | 加载大就按本页提速;等待上限见 01 章 |

## 六、常见误区

- **以为注册表里没有的架构就跑不了。** 官方讲 HuggingFace 集成的设计文档就这么写:架构名在注册表里找不到,说明 vLLM 不支持。代码里自动挡会先去 Transformers 库、再去仓库自带代码里找,找到兼容的类就包进外壳跑起来。起不来之前先看它是不是其实起来了,只是跑在外壳上。
- **以为 Transformers 后端和原生实现一样快。** 支持模型列表那页写的是性能「应当与原生实现相同」。代码在退回时打的警告却是「性能可能不是最优」:没有张量并行计划的层每张卡一整份,MLA 匹配不上时整个关掉。文档与代码冲突时以代码为准,上线前压测一次。
- **以为 TP 8 时每张卡只读 1/8 的文件。** 「切分」这个词让人以为读也是切着读的。默认加载器的迭代器把全部张量逐个吐给每个进程,截片发生在拷进显存之前的最后一步;只有预分片让每张卡真的只打开自己那份文件。
- **以为网络盘上会自动预取。** 自动预取只认 `/proc/mounts` 里的 `nfs`、`nfs4`、`lustre`,CephFS、各种 FUSE 挂载都不算;总大小超过可用内存 90% 也不开。多机时预热的分摊按全局 rank 算,每台机器只预热了自己那几个 rank 分到的文件,其余照旧按缺页读。看 `Filesystem type for checkpoints` 那一行,别猜。
- **以为多线程读和专家过滤可以叠着开。** 两个开关都在说「加速加载」。多线程读走的是另一个迭代器,根本不接专家过滤;开了 EPLB,过滤也会自动关掉,因为冗余专家槽要看到全部专家。想靠过滤省读盘,就留在默认的单线程映射读法上。
- **以为写了 `--load-format ipc_cache` 就一定是从守护进程映射的。** 默认 `fallback` 是 true,守护进程没起、套接字路径不对、指纹对不上,都只打一行 `Weight cache unusable` 就退回读盘,服务照常起来,只是慢。要确认走没走,看启动时间和这行警告;要让它失败得响亮,关掉 `fallback`。
- **以为进程快照恢复时不用读权重。** 名字叫快照,人们以为显存也原样存了。建档前引擎先按 sleep 第 2 级让出权重和 KV,恢复时再从模型文件重读、重建 KV、跑一条金丝雀请求核对首个 token 和它的对数概率,对上了才放出 HTTP 端口。它省的是导入、建模型、编译录图这些初始化,读盘一分没省。
- **以为插件装上就生效,装坏了会报错。** 插件是按入口点自动发现的,但 `VLLM_PLUGINS` 一旦设了,不在名单里的就不加载;加载时抛异常只打一行 `Failed to load plugin`,启动继续,最后报出来的是「架构不支持」。插件还会在每个进程里各执行一次,包括探能力的那个子进程,写的时候要能重复调用。
- **以为 checkpoint 缺了权重一定会报错。** 不量化的模型确实会报 `Following weights were not initialized from checkpoint`。量化模型默认跳过这道校验,缺的参数就停在建空时的值,服务照常起来、答案是错的;怀疑时用 `enable_weights_track: true` 显式打开。
- **以为 `Loading weights took` 就是加载花的全部时间。** 它只量从拿到文件列表到灌完最后一个张量,不含下载、建模型、逐层整理;在线量化或需要重排的量化格式,整理那段可能比读还长。看整段要用 `Model loading took`。
