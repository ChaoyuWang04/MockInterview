# 模型家族集成层:接一个新模型要做什么

一个模型能独立生成,距离接入多阶段服务还差哪些接口——这一章用 Qwen3-Omni 说明模型实现与框架的交界。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

把一个离线模型塞进服务,最容易漏掉的不是前向,而是前向两端的约定:请求里的模态和采样设置怎样变成模型输入,生成结果怎样恢复成下一段认识的载荷,中止之后谁释放按请求保存的状态。

Qwen3-Omni 的 Thinker 接收的不是纯文本 token。图像和音频经过 Encoder 后,要连同位置、提示词和请求设置交给生成段。若每个家族都把这些差异写进公共 Scheduler,框架就会不断增加按模型名字判断的分支;新增模型和维护公共调度会相互牵制。

## 二、解法

**公共框架管理请求的生命期,模型包负责把本家的输入、计算和输出接到接口上。** 接入工作可以按注册、配置、工厂、请求适配、载荷约定来检查,但这是一组职责,不是必须长成固定文件的模板。

启动时先用 checkpoint 的架构信息找到管线配置类。配置声明阶段与工厂,工厂返回合适的 Scheduler,再把模型专用的请求构造器和结果适配器交给它。Qwen3-Omni 的 Thinker 就在这里接到 OmniScheduler:请求构造器读取阶段载荷,产生自回归请求数据;结果适配器保留原请求身份,把生成结果写回阶段载荷。Scheduler 不需要知道图像输入的每个字段怎样组织。

![Qwen3-Omni 的模型配置通过工厂装配 Scheduler,请求与结果分别经过模型适配器跨越框架边界,阶段状态在跨进程前转换为普通字典。](/opensource/sglang-omni/13a-model-contract-boundary.svg)

**管线识别与计算模型识别是两次接线。** 管线注册表发现模型包导出的配置类,决定整条服务怎样装配;复用 SGLang 执行模型时,还要让 SGLang 的模型注册表找到具体计算类。只完成前者,可能配置解析成功,到加载模型时才失败。

模型被拆成组件后,权重也要按组件装配。Qwen3-Omni 的图像和音频 Encoder 使用公共加载器按权重名前缀选取对应参数,去掉前缀后装入各自模块。这避免每个组件都实例化完整生成模型,但前缀与模块结构仍由模型实现负责匹配。

统一的是这些装配边界,不是强制所有模型使用相同计算循环。LLaDA2-Uni 也通过阶段工厂接入,生成段装配的是 DLLM Scheduler;不能把模型家族层概括成只有自回归一条执行路径。

## 三、代价

**接口越薄,模型包越要把边界说清楚。** Qwen3-Omni 在模型内用带类型的状态视图,跨阶段时转回普通字典。这有利于序列化,但不能靠类型声明自动保证某段需要的字段一定到齐;请求构造、边上的投影与结果适配仍须一起核对。

**复用不等于零适配。** 公共权重加载器可以选择分片、匹配前缀、装入模块,无法替模型判断哪个前缀才是语义正确的组件。接入新的 checkpoint 变体时,加载成功和模型输出正确是两项验证。

**每条按请求保存的状态都带来清理责任。** TTS 接入契约特别要求覆盖预处理中止、生成段接管前中止、预处理在中止后才完成这几个时序,并让清理可重复调用。单条成功生成不能证明这套服务接入已完成。调度与流式机制的实现分别见 05–07 章,这里关注模型接入者必须交出的接口。

## 四、与 vLLM-Omni 的模型扩展边界

两边都在模型专属输入与公共运行时之间放适配层,也都允许复用上游执行实现。本项目围绕模型包的管线配置与 Stage 工厂装配;vLLM-Omni 的模型执行注册表将上游 vLLM 模型与 Omni 模型合并,阶段输入处理器负责相邻阶段的数据转换。

vLLM-Omni 还把模型专属的附加请求字段、输出字段和提示词构造集中到扩展层,图像与视频扩散模型则有独立的管线注册入口。这个划分不能等同于本项目的 DLLM 接入:文本扩散的调度适配和图像、视频扩散管线是不同的执行对象。比较接入成本时,应拿同一个模型及其输出形态对照,不能只数注册表或文件个数。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

这里先列使用者选择已有集成的入口;下面另列模型作者需要对齐的代码声明,它们不是可随意从命令行开启的功能。

| 参数 | 在哪调与默认 | 改变什么 | 怎么看 |
|---|---|---|---|
| `--model-path` | 服务 CLI;默认未提供,没有配置文件提供路径时必须填写 | 选择 checkpoint,自动路径会按其架构查找管线 | 无法识别架构与架构未注册是不同错误 |
| `--config` | 服务 CLI;默认未提供 | 使用指定配置文件装配已有管线类 | 文件必须声明 `config_cls`;名称错误会在注册表查找时失败 |
| `config_cls` | 配置文件;必须填写,无通用默认 | 从已登记配置类及其变体中选择类;不会凭名字注册新实现 | 核对解析后的类名与阶段表 |
| `--text-only` | 服务 CLI;默认 `False` | Qwen3-Omni 选择文本管线,不拉起语音输出分支 | 默认导出语音配置类,文本变体为 `Qwen3OmniPipelineConfig` |

| 集成声明 | 由谁填写 | 核对点 |
|---|---|---|
| `architecture`、`architecture_aliases`、`EntryClass` | 模型包配置模块 | 架构及别名指向管线类;重复架构会报错,发现到的配置模块缺少 `EntryClass` 也会报错 |
| `factory_path` 与工厂返回对象 | 阶段配置与模型工厂 | 工厂必须能被导入,返回匹配公共运行时契约的 Scheduler |
| `request_builder`、`result_adapter` | 模型的 Scheduler 装配代码 | 输入转换保留请求身份;输出转换返回后续阶段认识的载荷 |
| `CAPABILITIES` | 模型包,可选 | 必须是 `ModelCapabilities` 实例;它声明架构可能支持的能力,不替具体 checkpoint 和部署策略授权 |

若模型包提供能力声明,启动日志会出现 `Model capabilities: …`;没有声明时查询返回 `None`,不是一张全部为假的能力表。Qwen3-Omni 在本基准的包入口没有这份声明,不能靠缺少这行日志判定它不支持流式音频。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| Qwen3-Omni,1 张 H100 80GB,先验证多模态输入到文本输出的集成 | `sgl-omni serve --text-only --port 8008 --model-path Qwen/Qwen3-Omni-30B-A3B-Instruct` | 先验证 Encoder 与 Thinker 边界;语音输出留到下一套配置核对,容量仍需结合显存配置确认 |
| Qwen3-Omni,2 张 H100 80GB,验证文本与音频输出的完整接线 | `sgl-omni serve --port 8008 --model-path Qwen/Qwen3-Omni-30B-A3B-Instruct` | 使用默认语音管线,覆盖 Talker 与 Vocoder,需要更多资源与输出校验 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 配置类能找到,模型加载却说架构未知 | 管线注册与 SGLang 模型注册是否都完成 | 对齐实际计算类与工厂使用的架构名称 |
| 家族在目录里,自动发现却找不到 | `Ignore import error` 或 `Skipping … no submodule` 日志 | 修复依赖与导入错误,不要先修改 checkpoint 架构名 |
| 前向有结果,下一段缺字段 | `result_adapter` 与载荷投影是否保留所需状态 | 对照下游 builder 的读取字段,补齐契约测试 |
| 某个变体拒绝参考音频 | 具体管线/ checkpoint 的策略,不是只看 `CAPABILITIES` | 核对该变体允许的请求形式,输入适配细节见 11 章 |
| 中止后显存或共享状态持续增长 | 三条中止竞态中的清理是否均覆盖 | 核对清理函数幂等性,补取消路径的验证 |

## 六、常见误区

**「复制样例的文件名,框架就会自动装配全部实现。」** 自动发现只解决配置类入口;工厂引用、请求适配器、计算类注册、权重映射仍有各自的连接点。目录外形相同不能证明这些连接正确。

**「能力声明为真,任意 checkpoint 都应该接受这种输入。」** 架构能力容易被误读为服务承诺。代码明确把 checkpoint 与部署策略留给管线配置,例如参考音频能力存在,具体音色变体仍可以拒绝上传参考音频。

**「为保险起见,请求构造器先把张量转到 CPU。」** TTS 接入契约专门提醒这会引入同步,生成段还要搬回设备。只有明确的 CPU 消费者或最终序列化边界才应要求 CPU 数据,不能把复制当成通用兼容层。
