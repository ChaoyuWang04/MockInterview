## 02｜Stage 与 Coordinator

**主旨成立。** Stage 通过统一消息契约接 Scheduler，模型特有的路由、投影、fan-in 合并等逻辑由配置注入；中间阶段直接交接，Coordinator 管请求两端及状态。底稿对动态目标范围校验、同进程投影与流式队列确有代码核查。

必须修正三处：

1. **0.1 秒 timeout 不是固定的阶段交接延迟。** 第五节从 outbox.get(timeout=0.1) 推导出空载固定空档，错误。它在线程中阻塞等消息，有消息就返回；timeout 只约束无消息时等待多久。保留“最多连取 64 条后让出事件循环”即可。证据：pipeline/stage/runtime.py:1103–1165；Scheduler 的 outbox 是 queue.Queue。
2. **图 02b 把 merge 放错了位置。** 发送端执行 project_payload；接收端收到各上游输入后，通过 InputHandler 执行 fan-in merge。图里“上游阶段调用投影函数或合并函数”应改为“发送端投影，接收端汇合”。证据：runtime.py:573–601、1331–1359；pipeline/stage/input.py:42–98。
3. **没有下一跳不是动态路由可以随意选择的终止方式。** 图 02a 写“算不出来就是终端”，第五节说路由函数把阶段判成终端；实际动态 route_fn 必须返回非空且属于声明集合的下游，空结果报错。终端主要由模型配置标记。改成“按声明路由；声明的 Terminal Stage 将结果交回 Coordinator”。证据：pipeline/stage_workers.py:669–712。

附带顺修：第五节“固定事件顺序”中，代码先记录 stage_complete 再发送正常下游 payload，不应拿文章中的相反顺序作必然排障规则。对 vLLM-Omni 的差异限定为控制侧编排，避免让读者误以为 async-chunk 的张量也必须经过中央 Orchestrator；其 ModelRunner/Connector 直接传数据的路径第 06 章已介绍。

图处理：02a、02b 都有明确用途，保留；改上述节点职责与终端解释，统一 Coordinator、Stage、Scheduler、Mailbox 等组件名为英文。

## 03｜声明式拓扑与配置

**基本通过，改动最少。** 配置类拥有拓扑，用户源覆写部署和执行设置；同层具体度与跨层优先级、同排名冲突报错都有源码支撑。它与第 09 章资源部署、第 10 章启动执行的边界合理。

需要顺修：

- 开头“纯文本引擎谁在哪跑根本不需要配置”不成立，TP/PP/DP 同样需要配置。改为“常规文本服务的职责结构较稳定；Omni 还需要声明模型特有的阶段图”。六段/七段例子注明是 Qwen 配置，避免把单个请求不要音频与更换整套文本配置混为一谈。
- Coordinator 在途上限并非必然派生出一个整数。第一个引擎段未声明完整、有效的准入值时为 None。正文和 03a 的派生列表加“可选”即可，不必展开实现细节。证据：pipeline/mp_runner.py:51–80。
- 引擎参数“自由透传”指配置扩展入口，不保证所有上游功能受支持。加一句回指第 05 章已有的适配限制即可。证据：scheduling/sglang_backend/server_args_builder.py:101–129。

图处理：03a 的来源/校验/派生流程和 03b 的配置所有权比较都可以保留，不要求重画。03a 的“晚写盖早写”宜改“高优先级覆盖低优先级”，与同排名冲突规则一致；这是低成本清晰度调整，不是推翻该图。

## 04｜Control Plane 与 Data Plane

**核心机制成立，但例外被说成了绝对边界。** locality 路由、同进程引用、直接 CUDA IPC、池化 CUDA IPC、SHM 与未接线的跨节点路径均有代码基础。

必须修正：

1. **入口不是 Control Plane 唯一携带实际数据的地方。** Terminal Stage 的 CompleteMessage 带最终 result，StreamMessage 带终端流式 chunk；小块 inline 也已在本章前文写出。应说“中间阶段的大张量通常通过数据面传递，入口、终端返回和小块 inline 是例外”。证据：pipeline/stage/runtime.py:1268–1309、1645–1678、1752–1805。
2. **改变位置不是影响传输路径的唯一办法。** 本章自己的表格已有 disable_direct_cuda_ipc_payload；实际选择还看 payload 的 tensor device。同卡 GPU 阶段传纯 CPU payload 也不能照图一概归为 CUDA IPC。删“唯一”，图题改“位置与数据条件决定候选路径”。证据：comm/router.py:192–227、262–286；runtime.py:1396–1432。
3. **SHM 不必然意味着 GPU→CPU→GPU 两次拷贝。** 两张 GPU 互访失败的回退可以如此解释；若一端本来就是 CPU，只有实际经过 GPU 边界时才发生对应拷贝。图 04a 当前把两种场景写在同一行，却给了统一的两次 GPU 拷贝，应加条件。

图处理：保留 04a 的路径图，以上条件补齐即可；“从上到下越来越贵”改为“不同路径的典型开销”，不做跨负载绝对排序。04b 比较图保留，但“接收后统一回 ACK”限定为 relay 路径，别覆盖同进程与 direct CUDA IPC。

次要表格调整：池子的槽数是分配粒度下的容量，单次传输可占多槽，不等于固定的并发传输份数。这属于顺手改一句，不需要新增段落。

## 05｜阶段特化调度

**选题与主线准确，主要问题集中在图上的分类。** 组合 SGLang、轻量 Scheduler、partial start、异步 decode 与不可用的 overlap 路径都有明确代码依据。

必须修正：

1. **Encoder batching 与并发无关的说法重复了第一章的问题。** 请求数上限和成本预算共同约束 batch，队列中有多少请求也影响实际 batch。图 05a 与正文一起改，不能写“不是条数”。证据：models/qwen3_omni/stages.py:854–928；scheduling/simple_scheduler.py:106–143。
2. **图 05b 的“这些方法本地没有，一行都没写”不准确。** get_next_batch_to_run、get_new_batch_prefill、process_batch_result 都有本地封装/覆写，再调用上游。保留“复用上游核心策略”，图上区分“本地适配后调用”与“缺失方法动态委托”，不要硬分为只写入口出口。证据：scheduling/omni_scheduler.py:735 起、1369–1427；底稿自身也登记过这批覆写方法。
3. **图 05c 的“没有扩散段”错误。** 存在 DllmScheduler，并由 LLaDA2-Uni 阶段工厂接入，持有 KV 相关对象。本章前文也介绍过它。可以比较 vLLM-Omni 的多模态 Diffusion 调度与本项目的 Diffusion LLM 路径，但必须明确二者范围不同，不能画成整个项目没有扩散。证据：scheduling/dllm_scheduler.py:1–65、195–218；models/llada2_uni/stages.py:85–130。
4. **“工厂决定，所以换不了 Scheduler 类”推理不成立。** 用户配置不能直接改 factory_path，但模型作者可改工厂，已有 Qwen preprocessing 工厂按 max_concurrency 在 SimpleScheduler 与 ThreadedSimpleScheduler 间选择。应限定为“没有通用的用户侧 Scheduler 类选择开关，具体能否切换取决于工厂”。证据：models/qwen3_omni/stages.py:802–835。

另有两句需简化纠正：KV 池并非统一按运行中请求数乘上下文长度确定，保留“AR 需要 KV，轻量的一次性阶段不需要”即可；prefill 计时不能一概包含独立 Encoder 的时间，应按阶段分别观测。

图处理：05a 保留并改 batching 文字；05b 保留结构、修方法归属；05c 修改最后一行和类切换说明。若希望减少图数，05c 可改短表，但这是可选编辑决定，不是验收要求。

## 06｜ModelRunner 与反馈式自回归

**核心闭环讲对了。** 固定 buffer、整批 clone、feedback 在本进程内回到下一步，能解释真实机制；也正确识别了文档描述的公共 FeedbackAR 类尚未落地。

必须修正：

1. **“整条回路没有一个 token id”错误。** Qwen Talker 仍会采样 token/code id，post_decode 更新 next_token_ids，并保留 sampled token 的轨迹。应改为“仅反馈 token id 不足以表达下一步输入，还需 feedback embedding 与文本输入”。证据：models/qwen3_omni/talker_model_runner.py:87–130；components/talker.py:1293。
2. **图 06a 的“每一步都发一次”和正文“最后一行永远扣住”都过度概括。** 配置支持前若干帧直接发送，之后 coalesce；未启用 coalesce 时也逐帧发。图中码本出边标成“按发送策略逐帧或攒帧发送”；扣住最新行只解释 coalescing 的相应分支。证据：talker_model_runner.py:132–184。
3. **把 codec_coalesce_frames 改成 5，不保证首音频更早，也不必然错过 CUDA graph。** 默认前 10 帧本就直发，Vocoder 独立按自己的解码门槛攒块，传输块大小不等于解码窗口大小。删除该配置的必然收益/退化描述，改为“调整发送粒度，结合 Vocoder 首窗与 graph 命中实测”。证据：models/qwen3_omni/config.py:232–233；components/code2wav_scheduler.py:48–115、387–397、428–468。
4. **“引擎参数拼错仍启动成功”没有成立保证。** Omni schema 允许 extra 不等于上游 ServerArgs 接受任意键；实际直接构造 ServerArgs(**kwargs)。改成“配置解析可能通过，随后仍需上游参数与启动校验”。证据：config/schema.py:152–210；server_args_builder.py:91–102。

图处理：06a 保留，明确以 Qwen Talker 为例，并修发送粒度；06b 保留，但模型专属子类不能概括成所有 23 家族“一族一个”，与本章自己统计的 14 家族带运行器不一致。两图使用 Thinker、Talker、ModelRunner、Vocoder、feedback queue 等英文角色名，职责说明用中文。

“回路不走主机”“clone 保留前一步数据”“按批判断是否能异步执行”等核心解释不需要进一步变成代码手册。性能方向若无实测，写可能影响，不写保证提升或明显下降。
