# ModelRunner 与反馈式自回归

Scheduler 把一批请求交到手上之后,这一步的前向怎么拼出来、模型专属的那点东西塞在哪一层——这一章回答这个。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

纯文本模型的一步解码,接口窄得一句话说得完:这一步采出一个 token id,下一步把这个 id 喂回去。上游引擎整条快路都是按这个接口修的——id 全程留在显存上跨步传递,一步的形状是固定的,所以 CUDA graph 能把它冻住反复重放。

Qwen Talker 这样的音频码生成器还多一条反馈路径。它一步产两样东西:一帧码本,和一份代表这一帧的嵌入。下一步真正吃进去的是后者,而且还要和上游 Thinker 那边流过来的一行文本嵌入相加。仍然会采样并保留 token id；不同之处是下一步额外需要反馈 embedding 与文本条件,仅沿用 token-id 回填路径不够。这里以 Qwen Talker 为例。

把这件事交给每个模型各写一套,坏掉的是两个地方。

**解码步频。** 回路一旦经过主机——逐条请求取一次值、逐行拷一次——每一步就多一次显存与主机之间的同步。音频是按帧对齐的,步频掉下去,用户听到的是持续的卡顿,不是首包那一下慢。

**正确性,而且是安静地坏。** 那几块缓冲区必须是固定地址的,否则重放不了;固定地址的另一面是下一步会原地盖掉它。取晚了一拍,或者取的时候只拿了个视图没拷贝,读到的就是下一步的数据。这种错不抛异常,只让声音听着怪。

这两个坑对每个出码本的模型都一样。基准上 23 个模型家族里,自己带一套 ModelRunner 的有 14 个,其中 13 个都覆写了解码之后的那个钩子,干的是同一件事。同一套缓冲区读写写 13 遍,就有 13 次踩同一个坑的机会。

## 二、解法

分三层,越往上越模型专属。

**最下面是所有自回归段共用的那个 ModelRunner。** 它拥有一步的全部通用力气:把调度批变成前向批、跑前向、采样、按请求把输出拆出来、记住这条请求走到第几步了。模型能插手的地方是一排钩子,按「前向之前 / 前向本身 / 前向之后」排开,prefill 与 decode 各一套。插不插随模型,不插就走标准路径。

**中间是 Thinker 那一层。** 它只干一件事:在 prefill 的输入里,把图像、视频、音频的嵌入按 token 位置贴进去。单独成一层,是因为这件事自带一堆共通的坑——分块 prefill 要记住这一模态消费到哪一行了,位置数对不上要当场报错而不是悄悄截断——不该每个 omni 模型自己再算一遍。

**最上面是反馈式那一套。** 出码本的模型把三个动作填进上面那排钩子:前向之前,把上一步的那份嵌入写进模型上一块按行号索引的固定缓冲区;前向本身交还给标准路径;前向之后,从另外两块固定缓冲区里,把这一帧的码和这一步的嵌入各整批克隆一份出来。

这么一排,**回路整个留在显存上,而且只克隆,不搬家**。整批克隆一次而不是每行克隆一次,是因为下一步的图内写会原地盖掉那两块缓冲,必须是一块新分配的内存才活得过下一步。

![横轴是时间,画的是相邻两个解码步,每一步分成写缓冲、跑前向、取产物三格:第 N-1 步取产物时从模型的两块固定缓冲区各整批克隆一份,码本那份沿一条紫线向下离开这个进程去 Vocoder 段,嵌入那份沿一条黄线横着进两步之间那个只在本进程里的feedback queue;第 N 步的写缓冲同时接两条线,黄线是队首的反馈嵌入,灰线从上方那条text queue下来、装的是上游 Thinker 沿流边一块一块送过来的文本嵌入,两者相加后写进模型上一块按行号索引的固定缓冲区并置上这一行的标记位,前向读一次就把标记位清掉;虚线框圈出的是这一段自己的进程,上游 Thinker 和 Vocoder 段都在框外](/opensource/sglang-omni/06a-one-step-feedback-loop.svg)

**出去的和回来的走两条路。** 码按直发或攒帧策略变成带目标名的流式消息进发件箱,由阶段壳按边的位置关系搬给 Vocoder 段(04 章);那份嵌入根本不出这个进程,直接进这条请求自己的队列等下一步。

**一步的收尾可以劈成两半。** 发射那一半把前向和采样排上 GPU、把这一步的产物公布出去、记一个事件就返回;回收那一半等事件、读缓冲、把输出拆成每条请求的结果。Scheduler 于是能先发下一步再回收上一步,把回收那半段的主机工作藏进下一次前向里。

三个容易看漏的地方。

**这一步能不能跑,是 ModelRunner 说了算。** 反馈行是自己上一步产的,文本行要等上游流过来;两样缺一样,这条请求这一步就不能进批,整批一起往后推。空转是这类段的常态,不是故障。

**写没写进去是按行记的,漏了不报错。** 缓冲区旁边有一个按行的标记位,前向里读一次就清掉;没被写过的那行会安静地退回按 token id 取嵌入的老路。所以 ModelRunner 手里的请求顺序必须和前向批的行顺序严格对齐,这个约定没有任何东西替你检查。

**「共用的反馈式 ModelRunner」在基准上还只是一排钩子。** 仓库里的开发者参考把它写成一个角色,还给了一份三函数的策略接口;基准的代码里没有这个类,那三段函数体仍然各自待在各模型的目录下。真正已经收口的是另外两件:基础 ModelRunner 定死了钩子的位置与时机,接一个新模型时挂 ModelRunner 的那个接缝也统一成了引擎工厂上的一个方法(05 章)。而模型目录约定里那个单独放三段函数的文件,基准上只有一个家族真的这么做了,那个文件自己的注释还写着共用 ModelRunner 是「将来的」。

## 三、代价

**固定缓冲区把并发上限焊在启动期。** 缓冲区是在模型构造那一刻按这一段的运行中上限一次性开出来的;解码图捕获的最大批不单独写时也等于这个数,所以默认情况下三者是联动的。代价不在「要一起调」,而在「只能在启动时调」——跑起来之后这一段同时能扛几条请求,已经是一块固定大小的显存了。谁单独写过图捕获上限,再抬运行中上限就会被启动期的校验拦下来。

**自定义前向要付出图外执行。** Thinker 注入深层视觉嵌入那条路绕开了标准前向,这一次 prefill 就只能 eager 跑,而且引擎自己把这种情况单独计了一类数。

**图捕获要往后挪。** 捕获必须等到这一段自己的解码状态全建好——反馈缓冲区分配了、采样器装上了、按帧的小工具编译完了——否则冻住的是一条还不完整的解码路,后面的请求要么落不进想要的形状,要么直接把缓冲区写越界。代价是这一段的启动更慢,而且慢在拉起流程的后半段。

**ModelRunner 兼了生产者,攒批的边界就归它管。** 码是 ModelRunner 自己往发件箱里放的,不经 Scheduler 的输出构造。好处是这一帧当场就能出去;代价是攒几帧再发、什么时候冲刷、最后一行怎么办,全要它自己拿捏。Qwen Talker 只在合并帧的 pending 分支中扣住最新行,留给收尾处理可能的 EOS；早期直发与关闭合并的分支并不这样扣行。

**劈成两半的那条路是有条件的,条件还不写在配置里。** 任何按输出历史打分的采样项都会让整批退回一步一等;Thinker 那边更严,会出音频的请求、要 logprob 的请求一律走同步。开了也可能整场都没走上,而这件事没有日志。

## 四、ModelRunner 这一层和 vllm-omni 不一样的 3 处

vLLM 社区的那套 omni 框架在同一个位置也有一层自回归 ModelRunner。下面三条都在它的基准 4d877780d3(tag v0.29.0rc1)上核过;点到为止,不评优劣。

1. **模型专属的那段代码挂在哪。** 这边由有需要的模型派生 ModelRunner 子类,填的是基类上声明好的钩子,钩子有哪些、什么时候调,看基类就知道。那边的 ModelRunner 类按执行形态固定下来——自回归一个、生成一个,平台再各自派生一层——模型专属的那段挂在模型对象上,由 ModelRunner 按名字一个个试探出来:准备 ModelRunner 输入、自己采样、采完再算一次、刷元数据、设置本批请求号,都是这个形状。

2. **采样之后那次「再算一次拿到码本」怎么表达。** 这边是解码之后的钩子,从模型的固定缓冲区里把码和反馈各克隆一份,码走流式边,反馈进本地队列。那边是一个采样之后的可选钩子,把这一步刚采出的 token 连同隐藏态一起喂回模型换出码,结果并进这一步的多模态输出里,跟着正常的输出路径回去;它还明确要求一次只能采一个 token,多于一个直接报错。

3. **ModelRunner 管不管把结果送出去。** 这边的 ModelRunner 只把带目标名的消息放进发件箱,真正怎么搬是阶段壳的事(04 章)。那边 ModelRunner 这一层自己持有 Connector,把一条带下一段编号与键的任务排进队列,交给后台线程发出去。两边都把「ModelRunner 不得自己挑下一段」写成了规矩,区别在这条规矩之后还剩多少活留在 ModelRunner 手里。

![这一层都必须做的 5 件事按行排开,各自的做法去盖这些行:一步的通用骨架归谁,这一行两边是同一个答案,都在 ModelRunner 这一层;模型专属的那段代码挂在哪,本项目挂在按需派生的 ModelRunner 子类上、钩子由基类声明,对面的 ModelRunner 类按执行形态固定、模型专属那段挂在模型对象上由 ModelRunner 按名字试探;采样之后那次再算一次拿到码本,本项目是解码之后的钩子从两块固定缓冲区各整批克隆一份,对面是采样之后的可选钩子把刚采出的那个 token 连同隐藏态喂回模型换出码;这一步的产物怎么交出去,本项目的 ModelRunner 只放一条带目标名的消息进发件箱、怎么搬归阶段壳,对面的 ModelRunner 自己持有 Connector 并把任务排给后台线程,而两边都写明 ModelRunner 不得自己挑下一段;这一步的收尾怎么不挡住下一步,本项目在一条流上把一步劈成发射与回收两半并按批判能不能走,对面走一条单独的拷贝流加每步一个后台线程攒输出对象](/opensource/sglang-omni/06b-where-the-model-specific-seam-falls.svg)

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**先说清楚这一层的可调面长什么样。** ModelRunner 没有自己的配置块——它是阶段工厂造出来的,所以调它就是调这一段的工厂参数和引擎参数(点号路径见 03 章)。两者的错法不同:Omni 的 engine schema 允许扩展项,但随后要构造上游 上游 ServerArgs 参数对象,拼错名字仍可能被参数或启动校验拒绝;工厂参数写了工厂不收的名字,启动时直接报错,报错里会写明是哪一段的哪个参数、哪个工厂不收。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--<段名>.factory.enable_async_decode` | 命令行点号覆写,或 YAML 阶段块里的 `factory` | 随工厂;Qwen 语音管线的 `thinker` 写成开,`talker_ar` 的工厂根本不收这个参数 | 开着才走「先发下一步、再回收上一步」的那条事件循环;关掉就一步一等 | 配置子命令的「解释」动作,看这一项最后是哪一层写的 |
| `--<段名>.factory.async_decode_min_batch_size` | 同上 | `2` | 批里行数少于它就不走前瞻,直接同步 | 同上 |
| `--<段名>.factory.codec_coalesce_frames` | 同上 | 工厂默认 `0`(不攒);Qwen 语音管线的 `talker_ar` 写成 `10` | 攒够这么多帧才往 Vocoder 发一条消息 | Vocoder 段收到的块有几行(07 章) |
| `--<段名>.factory.codec_coalesce_early_frames` | 同上 | 工厂默认 `0`;Qwen 语音管线写成 `10` | 开头这么多帧一帧一条直接发,不进攒批 | 同上 |
| `--<段名>.factory.codec_coalesce_first_frames` | 同上 | `0` | 只在上一项为 `0` 时起作用:第一次冲刷换一个更小的门槛 | 同上 |
| `--<段名>.factory.feedback_enabled` | 同上 | Qwen 语音管线的 `talker_ar` 写成开 | 关掉之后这一段的三个反馈钩子全部空转,不再往 Vocoder 发码 | Vocoder 段一条消息都收不到 |
| `--<段名>.engine.max_running_requests` | 命令行点号覆写 | 随工厂;Qwen 的 `talker_ar` 写成 `32` | 一个数定三样:准入上限、解码图捕获的最大批(没单独写时)、模型侧反馈缓冲区的行数 | 对不上时启动期的批策略校验直接失败,报错把数字一起打出来 |
| `--<段名>.engine.cuda_graph_max_bs` | 同上 | 不设时等于运行中上限 | 只调图这一侧;比运行中上限小就起不来 | 同上 |
| `--<段名>.engine.disable_cuda_graph` | 同上 | Qwen 的 `talker_ar` 把它写成关(即捕获图),平台不支持时才改回去 | 不捕获图之后解码全 eager,固定缓冲区的地址约束随之松掉,性能影响需要在目标负载上测量 | 管理接口返回的模型信息里的图那一块 |
| `--<段名>.engine.sampling_backend` | 同上 | Qwen 的 `talker_ar` 默认写成 `pytorch`,用户写了就盖掉 | 换回融合那套采样 kernel | 同上 |

**观测点,从起服务到跑起来。**

起服务时,Qwen 语音管线的两个自回归段各打两行,加载前一行、加载后一行,带卡号、张量并行位次、上下文长度、静态显存比例、这个进程的显存占用。这是判断某一段有没有把显存吃超的第一现场;别的家族有没有这两行,要看它自己的阶段工厂。

prefill 图那一档有一条断言:后端是用户点名的,就必须真的捕获出来,捕不出来直接启动失败,报错里写明它是被资格检查挡掉的;是模型自己选的,捕不出来只打一条警告然后降级。捕获成功那一行会写明后端名和捕获了哪几档长度。

跑起来之后看管理接口返回的模型信息,里面有一块图使用计数:重放了多少次、标准 eager 多少次、自定义前向的 eager 多少次,以及重放分别落在哪几档。**自定义前向那一格非零,说明注入走的是绕开标准前向的那条路。**

反馈式的段空转时,Scheduler 每 10 秒打一行,写明到目前为止推迟了多少个解码步、当前批有几行(05 章)。

**有一个数它自己算了却没打出来。** ModelRunner 统计了回收上一步时事件是不是已经完成、还是得停下来等,但基准上没有任何地方读这两个计数。想知道前瞻有没有真的重叠上,只能从外面量。

**典型配置**,三套,都能直接抄走。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 默认形态,这一层一个参数都不加 | `sgl-omni serve --model-path <模型>` 就是它 | Thinker 走一步前瞻、Talker 按 10 帧攒码;吞吐与首包都按模型自己调好的那组走 |
| 观察不同传输块粒度 | `sgl-omni serve --model-path <模型> --talker_ar.factory.codec_coalesce_frames 5` | 改变稳态消息粒度；默认前 10 帧仍直发,Vocoder 仍按自身阈值解码,不保证首包更早或必然错过 CUDA graph(07 章) |
| 怀疑一步前瞻带来了差异 | `sgl-omni serve --model-path <模型> --thinker.factory.enable_async_decode false` | Thinker 整场一步一等,便于比较同步路径；吞吐影响要实测 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后。**

| 症状 | 先查 | 然后 |
|---|---|---|
| 音频持续断续,文本正常 | Scheduler 那行推迟计数,看这一段是不是每步都在等 | 等的是文本行就往上游查 Thinker 的出字速度(05 章),等的是反馈行才回到这一层 |
| 把并发调大之后起不来 | 启动期批策略校验的报错,它把几个数一起打出来 | 十有八九是图捕获上限被单独写死过,没跟着运行中上限一起抬;两者都不单独写时本来是联动的 |
| 吞吐比预期低,前瞻像是没生效 | 这一段的工厂参数里前瞻是不是开着,以及批里的行数够不够那个下限 | 都够还是没提升,就看请求上有没有带按输出历史打分的采样项,或者是不是要出音频——这两类一律退回同步 |
| 图使用计数里 eager 那几格居高不下 | 分清是标准 eager 还是自定义前向的 eager | 自定义前向那格高,说明这批请求走的是注入深层视觉嵌入的路,本来就不进图;标准那格高才去查捕获的档位对不对 |
| 声音偶发退化成循环念同一段 | 这一段最终生效的采样后端 | 被覆写成融合那套的话,在图里捕获的随机状态跟启动有关,换回这一段自己的默认再复现 |

## 六、常见误区

**「文档里那个共用的反馈式 ModelRunner 是存在的,接新模型直接继承它。」** 开发者参考确实写了这个角色,还给了三函数的策略接口,连架构设计图上都画着它。基准上没有这个类。真正在那儿的是基础 ModelRunner 上那排钩子,加上「三段函数体单独放一个文件」的目录约定——而这个约定只有一个家族照做了,那个文件的注释自己写着共用 ModelRunner 是「将来的」。接新模型时照着最近的那个同类家族抄,比照着文档抄稳。

**「一步前瞻是个纯吞吐开关,开了只赚不赔。」** 它是按批判的,不是按段判的。基础 ModelRunner 会把带重复惩罚、频率惩罚、出现惩罚、最少新增 token、自定义 logits 处理器的批全部踢回同步,因为前瞻会让这些项读到一拍之前的输出历史;Thinker 那一层在这之上又加了两条,会出音频的请求和要 logprob 的请求一律同步。于是在语音管线里,恰恰是你最关心的那种请求走不上这条路。更麻烦的是,走没走上没有日志。

**「Talker 段的采样后端跟别的段一样。」** 不一样,这一段自己把默认写成了另一种,理由写在注释里:上游的采样器没有把种子传给那套融合 kernel,在图里捕获的随机状态因此和启动有关,少数提示词会把自回归带进退化循环。它只是默认,用户在这一段写了就被盖掉。排查「偶尔循环念同一段」时,先确认这一段最终用的是哪一种。

**「ModelRunner 那个目录里都是框架代码。」** 那个目录里有一个以某个模型命名的 ModelRunner,干的是那个家族的 Thinker 注入;而另外两个家族的 ThinkerModelRunner,是从同一个目录里的共用那层继承下去的。同一个目录里三种身份都有。还有一个同名陷阱:这个目录里另有一个类也叫 ModelRunner,但它继承的是上游引擎里那个设备侧的模型执行器,和本项目这一层的基类完全是两件东西,按名字搜会同时搜到。

**「攒帧只是省几条消息。」** 它改变数据到达 Vocoder 的节奏,可能连带改变解码窗口。但传输块不等于解码窗口：Qwen 默认前 10 帧逐帧直发,Vocoder 默认攒够 10 帧才解码。只把后续合并粒度从 10 改为 5,不能推出首包必然更早,也不能推出窗口必然错过 CUDA graph。扣住最新行只发生在合并帧的 pending 分支,不是“发出帧永远比产出少一”。

**「有现成的体检会在启动时检查缓冲区够不够。」** 基准里确实有一张表,按模型类名列出每个模型的反馈缓冲区字段该怎么读,一共 7 个模型类,看着就像个体检工具;但读这张表的那个函数,在发布出来的代码里没有任何调用方。启动时真正跑的是另一套更窄的批策略校验,它只有在这个家族的引擎工厂主动把模型侧的缓冲区行数传进来时才检查那一项,而基准上只有 3 个家族这么传了。剩下的家族不是没被检查,而是根本不需要——它们的缓冲区就是按运行中上限开的,自动跟着走。真正该盯的恰恰是那 3 个:它们的缓冲区尺寸另算一套,所以才要单独报上来核。
