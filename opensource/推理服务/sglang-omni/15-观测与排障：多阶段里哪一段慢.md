# 观测与排障：多阶段里哪一段慢

端到端延迟变长之后,先找请求卡在哪个阶段,再判断那段是在排队、搬数据还是跑 kernel,需要两种粒度的证据。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

语音生成经过预处理、Encoder、Thinker、Talker 和 Vocoder,其中还有流式重叠。只知道首音频晚了,不能确定是Thinker启动慢、Talker排队,还是Vocoder迟迟没有收到足够输入。只看整张卡的利用率,也无法把某个空闲窗口归到具体请求。

反过来,一上来就录全部 kernel,又容易淹没在不同请求、不同进程和重复decode的轨迹里。真正需要的是先找到请求经过的那一段,再放大看那段内部发生了什么。

## 二、解法

**先记录里程碑,再按需录底层执行。** 请求级事件记录器在准入、收到输入、进入Scheduler队列、开始首批执行、首次发出和终端完成等位置写事件。每条都带请求编号、Stage、进程与时间。离线视图将不同进程的事件按请求归并,把同一请求重新串起来。

归并后有三种看法:请求时间线回答「先后发生了什么」;阶段区间把同一Stage的开闭事件配对,回答「这段跨度有多大」;跨阶段交接按源、目标以及流式块编号配对,回答「交接在哪条边拖长」。同一个开事件可以对应多种区间,因此从首批开始到首次产出、到首次发出都能分别看。

torch profiler 再提供CPU与设备活动轨迹,用来检查选中的进程和时间窗口。两种记录可以共用采集会话编号,但仍是不同产物:事件报告重建请求路径,torch trace展示执行活动。共享会话编号方便人工关联,并不会自动把每条JSONL事件变成一段GPU kernel。

![多个进程各写事件文件,离线按请求编号归并并按阶段与交接配对;同一采集会话的torch轨迹另行提供进程和rank的底层活动,关联线不表示自动合并或测量时长。](/opensource/sglang-omni/15a-events-to-trace.svg)

采集控制由内置服务广播到Stage,TP主rank再把开始和停止转给其他rank。每个进程只有一份事件记录器,共处一进程的Stage写同一文件,靠事件里的Stage字段区分归属。Coordinator也记录自己的请求事件;torch trace则由各Stage所在进程启动。

## 三、代价

**事件跨度不是GPU纯计算时间。** 从输入到阶段完成包含排队、调度、计算及输出处理;跨阶段的两端事件也只是各自插桩位置,不能直接当作链路带宽测试。首批执行前后的时间尤其要看边界:主机函数返回与异步GPU完成不是天然同一时刻。

**不同统计区间可以重叠。** 一个请求的生成阶段可能彼此并行,同一阶段又有互相包含的区间。把阶段表里的总耗时全部相加,得不到客户端端到端延迟。事件中的终端响应也表示Coordinator收到了一个阶段的完成消息,并非客户端已收齐全部响应。

**采集本身有成本和缺口。** 事件写入有锁、序列化与文件I/O,写失败会吞掉异常并记丢弃次数,避免拖垮服务;这也意味着文件不一定完整。torch记录形状、内存或调用栈会进一步增加开销与体积,停止后的压缩还在后台运行。排障时应把「控制请求已返回」「所有进程已开始记录」「所有文件已导出」分开确认。

## 四、vLLM-Omni 同时提供哪几类观测

两边都能用torch profiler查看CPU与设备轨迹。vLLM-Omni的包装器按Stage和rank管理产物,还可导出算子表和内存快照;本章这条SGLang-Omni路径则突出请求事件归并,先从阶段与交接区间定位问题。

vLLM-Omni还有面向Prometheus的运行中请求数、端到端延迟、音频首包和连续性指标,以及按Replica边记录的传输统计。它的扩散管线计时器会在函数前后同步设备,再统计这段执行时长。这与本章事件记录器在调用点取主机时间的测量边界不同,即使都叫「某阶段耗时」也不能直接混比。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

环境变量属于启动配置;下面的采集请求字段在服务运行中生效,不用重启。产物命名与示例步骤以 NVIDIA 的标准 torch 路径为准。通过内置launcher启动才会挂这些HTTP路由,只调用`create_app`嵌入服务时需要另行挂载。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `SGLANG_TORCH_PROFILER_DIR` | 启动环境 | 未设 | 提供trace及事件目录的默认根路径;也可在采集请求中显式给路径 | 开始请求返回路径和各进程启动日志 |
| `run_id` | 开始/停止请求JSON | 开始时自动生成;停止时省略代表停止当前会话 | 固定值便于关联,停止时指定可避免停错会话 | JSONL的`run_id`与日志中active run |
| `event_dir` | 开始请求JSON | 有上述环境变量时为`<根>/<run_id>/events`;否则须显式提供以录事件 | 决定JSONL落盘位置;每轮独立目录避免混入旧事件 | `events_<首个Stage>_<pid>.jsonl` |
| `trace_path_template` | `/start_profile`请求JSON | 有默认根时为`<根>/<run_id>/trace` | 决定trace前缀,支持`{run_id}`和`{stage}`,再附加PID与rank | `*_pid<PID>_rank<RANK>.trace.json.gz` |
| `enable_torch` | `/start_profile`请求JSON | true | false只录事件,降低采集负担;也可直接用`/start_request_profile` | 返回开关及各进程产物 |
| `SGLANG_TORCH_PROFILER_RECORD_SHAPES` / `PROFILE_MEMORY` / `WITH_STACK` / `WITH_FLOPS` | 启动环境,后三项同样带完整`SGLANG_TORCH_PROFILER_`前缀 | 均关闭,值为`1`才启用 | 增加形状、内存、栈或FLOPs信息,也增加体积与开销 | torch trace与导出日志 |
| `SGLANG_OMNI_COMM_TRACE` | 启动环境 | 关闭 | 打开通信调试日志,用于继续细分交接路径 | `COMM_TRACE`日志,不是事件报告里的另一个表 |

HTTP采集默认广播所有注册Stage,TP控制继续扇出到其他rank;请求schema没有选择Stage的字段。内部控制客户端虽支持目标列表,不能把它当成当前HTTP字段。`config`虽被开始接口接收,这条广播实现没有把它装入消息,不能用它代替上述环境变量。

**两套采集起点。** 都面向已能稳定服务的模型部署,不改变卡型与模型配置;例如默认双卡Qwen3-Omni可先测单条语音请求,再在相同采集范围里复现并发。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 尚不知道慢在哪一段,只需请求路径 | `curl -sS http://127.0.0.1:8091/start_request_profile -H 'Content-Type: application/json' -d '{"run_id":"events-a","event_dir":"/tmp/omni-profile/events-a"}'` | 只录事件,保留阶段与交接跨度,不记录kernel内部细节 |
| 已定位某个时间窗口,复现CPU/GPU交互 | `curl -sS http://127.0.0.1:8091/start_profile -H 'Content-Type: application/json' -d '{"run_id":"trace-b","event_dir":"/tmp/omni-profile/trace-b/events","trace_path_template":"/tmp/omni-profile/trace-b/{stage}"}'` | 同时录事件与torch trace,增加采集开销;先保持昂贵附加项关闭 |

组合与推荐值是按语义推的起点,不是实测最优。

**按顺序完成一次采集。** 发开始命令后,先确认各进程的记录器启动日志,再送入可复现请求并等其完成;随后显式停止本轮,等待导出日志和文件落盘,最后生成报告。第二轮必须先停止第一轮再开始。

| 操作 | 可执行命令或字段 | 核对结果 |
|---|---|---|
| 停止第一套 | `curl -sS http://127.0.0.1:8091/stop_request_profile -H 'Content-Type: application/json' -d '{"run_id":"events-a"}'` | 进程文件关闭;HTTP返回本身不是逐Stage完成确认 |
| 输出事件表 | `python -m sglang_omni.profiler /tmp/omni-profile/events-a --format table` | `count`、`avg_ms`、`p95_ms`,先查有没有足够成对事件 |
| 停止第二套 | `curl -sS http://127.0.0.1:8091/stop_profile -H 'Content-Type: application/json' -d '{"run_id":"trace-b"}'` | 等`Trace exported`和gzip产物,再用Perfetto打开 |
| 保存完整关联事件 | `python -m sglang_omni.profiler /tmp/omni-profile/trace-b/events --format json --out /tmp/omni-profile/trace-b/report.json` | `timelines`保留事件和`t_rel_ms`,另有`stage_breakdown`、`hop_breakdown` |
| 启动前核实GPU环境 | `sgl-omni check-gpu --json --strict` | GPU逻辑到物理映射、版本、后端可导入性和警告;不加载模型,不证明模型可运行 |

最先读的事件通常是`request_admission`、`scheduler_queue_enter`、`scheduler_prefill_start`、`scheduler_first_emit`和`terminal_response`。流边再看`stage_stream_chunk_sent`与`stage_stream_chunk_received`,按`request_id`、`from_stage`、`to_stage`、`chunk_id`对应;Vocoder的细分事件见07章。

| 症状 | 先查 | 然后 |
|---|---|---|
| 开始接口成功,文件却不全 | 该进程是否收到广播,是否出现记录器写入警告 | 补齐完整采集窗口再比较,不能把缺失事件当成零耗时 |
| hop表没出现预期的边 | 两端是否都有事件,源/目标/块编号是否能配对 | 检查插桩顺序与捕获范围,再看通信日志 |
| 阶段总耗时比端到端还大 | 区间是否嵌套、Stage是否重叠、请求数是否相同 | 先回单请求时间线,不要相加统计行 |
| 换了采集编号,事件与trace对应不上 | 上一轮torch是否仍活动 | 显式停止旧会话后重新采集,并用新目录 |
| torch文件路径返回了,压缩文件暂时不存在 | 导出和后台gzip日志 | 等待真实文件完成;压缩失败时检查未压缩JSON |

## 六、常见误区

**文件名只有Thinker,就认为没有Talker事件。** 同进程部署下,第一个加入记录器的Stage决定文件名,后来加入的成员共用文件。要按每行的`stage`筛选,不能按文件名筛掉整份数据。

**同一采集编号就已经隔离了不同轮次。** 离线视图实际按请求编号归并,不自动按采集编号过滤。复用同一目录并重用请求编号会混在一起;每轮单独目录能避免这类看似连续的假时间线。

**时间线从零开始,零点必然就是准入。** 实现取该请求最早被记录的事件作零点。采集中途才开启、准入事件丢失或混入旧文件时,零点就不再代表请求进入服务,末点也不保证客户端完成。

**看到两端纳秒时间戳,就能直接跨机器相减。** 普通事件取墙钟,视图按该值排序和配对,没有自动时钟校准。模型路径还记录单调时钟与主机启动标识,但普通报表不会自动切换到这套字段;先确认时钟与插桩边界再解读跨度。

**停止请求事件只会关JSONL。** 两个停止HTTP入口广播的是同一种停止消息,Stage会同时处理符合会话编号的torch与事件记录器。不要把它们当成可以独立停止的两套长期采集会话。
