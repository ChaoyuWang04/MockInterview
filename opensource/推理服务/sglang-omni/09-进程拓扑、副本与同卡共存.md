# 进程拓扑、副本与同卡共存

一张卡还有计算余量,却塞不下更多服务副本时,应该复制什么、共享什么、让谁一起退出——这一章把这些部署边界分开。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

小型语音模型的吞吐可能先受主机调度、逐步生成和首音频延迟约束,没有把 GPU 喂满。继续往同一个 Scheduler 加请求,又可能先把首包和尾延迟推过业务要求。此时增加独立的执行进程,才有机会用另一条主机执行路径填上空闲。

但多开进程会多占显存:权重、KV cache、CUDA graph 和请求状态通常都要再备一份。**有计算余量,不等于有副本容量。** 而把两个 Stage 放到同一张卡,也没有回答它们是否同进程、请求由哪个 Replica 接手。这里的 Replica 指一份完整的逻辑进程副本。

## 二、解法

SGLang-Omni 把部署拆成 5 个可组合的决定,每一步只解决一个问题。

**先定同进程归组。** 显式归为同组的非 TP Stage 共享操作系统进程、Python 堆与事件循环,组内 GPU Stage 共用 CUDA context。这个组可以包含预处理和模型计算,并不要求一段一个进程;同组的 GPU Stage 必须落在同一张卡。

**再复制整个组。** 组内成员一起复制,而不是把一个有本地状态依赖的 Stage 单独拆走。Coordinator 在请求进入时为每个被复制的组各选一次 Replica,把绑定传给组内全部 Stage;同一条请求后续的流式块和中止操作沿用这份绑定。默认按组独立轮询。

**然后决定落在哪张卡。** 多个 Replica 可以各用一张卡,也可以重复选择同一张卡。位置相同并不会合并进程,每份 Replica 仍有自己的调度和请求状态。TP 的每个 rank 如何启动留到 10 章,这里的同卡共享以非 TP 进程为对象。

最后才是两种不同的共享: **CUDA MPS**让同卡多个 CUDA context 的 kernel 在资源允许时重叠;**CUDA IPC 权重共享**则让同一逻辑进程的同卡 Replica 引用同一份不可变权重。前者处理执行机会,后者处理重复存储,两者可以分别开启。

![同卡的两个进程副本各自包含预处理与引擎阶段,保留私有缓存和状态,只有引擎的可共享权重由主副本持有并供从副本引用;MPS 协调它们的 GPU 执行机会,示意不表示显存比例。](/opensource/sglang-omni/09a-process-replica-sharing.svg)

权重共享组中,编号最小的 Replica 先加载并导出句柄,其余成员挂接这份存储。运行时先等主副本就绪再启动从副本,退出时反过来。**共享的是存储,也共享了存储持有者的生存期**:主副本死亡后,从副本不能继续使用那些指针,监控会使它退出,整条管线失败。

## 三、代价

同卡 Replica 会争 CPU、显存带宽和 GPU 执行资源。只有单副本在真实延迟要求下仍留下可利用的空闲,这笔交换才有意义;计算已经饱和时,增加进程可能只增加竞争。权重共享也不会合并 KV cache、CUDA graph 或采样状态,模型策略标记为私有的张量仍逐副本保留。

放置检查按每个 Stage 声明的预算累加,负责提前拒绝明显装不下的布局,不是运行时显存隔离。共享权重不会替用户自动重写这份预算,也不能用「省下了权重」证明新增的 KV 与 graph 一定装得下。

另一个成本是故障收尾。MPS 守护进程按物理 GPU 管理,可能同时服务多个作业;退出一个作业不能顺手杀掉整张卡上的服务。运行时通过所有权租约记录各作业,验证客户端挂接,退出时清理自己的客户端。遇到无法证明归属的残留状态,它保留现场并报错,不自动猜测该杀哪个进程。

## 四、vLLM-Omni 在哪一层组织副本

对照 vLLM-Omni 的固定基准,两边都把放置与请求计算分开,也都维护请求到 Replica 的稳定关系。区别在副本边界:这边先把 Stage 组成逻辑进程再整体复制;vLLM-Omni 的 StageRuntime 为逻辑 Stage 建立 StagePool,由池管理各 Replica 的选择与亲和关系。

vLLM-Omni 的分布式路径还有 MembershipController,把远端 Replica 的加入和消失反映到池里;本章这条 SGLang-Omni 路径则在启动时展开配置中的进程副本。两边都有同卡部署:例如 vLLM-Omni 的 AuK 部署把 Encoder 与扩散阶段放在同卡,分别声明显存比例。**同卡布局本身不能证明用了 MPS 或共享了权重**;要判断这些能力,必须继续看对应的运行时机制。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

先用 `sgl-omni config resolve --config <配置文件> --show config` 核实归组与放置,再看实际启动日志。配置层写法见 03 章;这里只保留决定布局的入口。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `stages.<阶段>.process` | YAML 的 Stage | 字段默认 `None`,实际由模型声明,必需阶段不能缺名 | 归为同组后一起复制、同进程运行 | 解析配置中的成员关系 |
| `processes.<进程>.num_replicas` / `replica_devices` | YAML 顶层进程表 | `1` / `None` | 前者增加完整组的容量;后者覆写各副本 GPU,同卡填重复编号;GPU 组多副本必须填设备 | `Replicated process` 日志与展开后的实例名 |
| `gpu_memory_fraction` / `total_reserve_bytes` | 各 Stage | 均为 `None`,模型可声明 | 以比例或字节声明总占用,二者互斥;预算过大可能在启动前被拒 | 放置错误指出 GPU、缺预算的逻辑 Stage 或超额总量 |
| `placement.max_total_gpu_memory_fraction_per_gpu` | YAML 管线级 | `1.0` | 调低会更早拒绝同卡比例预算超额 | 启动时预算校验 |
| `mps` | YAML 或 `--mps` | `off` | `auto` 对本管线同物理卡至少 2 个合格非 TP 进程启用;`on` 一个也可,平台不支持则报错 | `MPS summary` 的 GPU UUID、daemon 和客户端名单 |
| `weight_share` | YAML 或 `--weight-share` | `off` | `on` 为同逻辑进程、同卡的副本分配主从角色,减少重复权重;没有可共享组则拒绝 | `Weight sharing on GPU`、`leader exported`、`follower attached` |
| `stages.<引擎阶段>.engine.max_total_tokens` | YAML 的 engine | 不在此层统一指定 | 原生权重共享要求显式正整数,防止从副本释放临时权重后把空闲误算为可用 KV | 预检报错与引擎 KV 容量日志 |

共享组要求恰好有一个 SGLang 引擎 Stage,且模型通过共享策略检查;不是任意两个模型都能共用权重。TP 组不参与这里的共享。不要同时设置原生 `weight_share` 和外部 `SGLANG_OMNI_WEIGHT_SHARE` 角色环境变量。

**两种部署起点。** 命令中的文件来自上游基准仓库,需在安装好服务及对应模型依赖的环境中执行。第一套使用原生进程副本;第二套是官方外部多服务脚本,复制整套服务,不能把它的 `N` 当作管线进程表中的副本数。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| Qwen3-Omni,3 张显存足够的 NVIDIA GPU,语音生成并发压住下游 | `sgl-omni serve --config examples/configs/qwen3_omni_speech_replica2.yaml --port 8091` | Thinker 留 GPU 0,Talker 与 Vocoder 各 2 份落 GPU 1、2;增加卡与下游权重副本,换语音侧容量;官方文件未指定卡型 |
| MOSS-TTS Local,官方 H100 80GB 配方,同卡并发语音 | `CONFIG=examples/mps_dp/configs/moss_local_h100_dp2.yaml N=2 WEIGHT_SHARE=1 CORE_BLOCKS="0-7 8-15" bash examples/mps_dp/launch.sh up` | MPS 与引擎权重共享配合,以各服务的私有 KV、codec 和 CPU 核换同卡容量;CPU 核块须按机器 NUMA 与物理核布局替换 |

组合与推荐值是按语义推的起点,不是实测最优。

**性能要做成受控对照。** 先把单副本并发加到吞吐平台,记录首音频、尾延迟、请求失败、Scheduler 队列及 GPU 轨迹;再固定总 GPU 与 CPU 资源,让每个 Replica 都有足够请求,比较完整服务吞吐。不能只凭瞬时 GPU 利用率低就判定 MPS 有收益,也不能把权重共享节省的显存直接换算成加速倍数。

| 症状 | 先查 | 然后 |
|---|---|---|
| 加副本后尚未加载模型就报错 | 每个副本设备是否填全、同卡 Stage 是否都声明总占用 | 按展开后的副本数重新算预算;只填 KV 字节不等于声明完整占用 |
| MPS 守护进程存在但吞吐没变 | `MPS summary` 和客户端挂接验证,再查单副本是否已饱和 | 检查请求供给和 CPU 核竞争,用相同延迟约束做对照 |
| 从副本一直等权重 | 主副本是否导出、模型及 GPU 身份是否匹配 | 先处理主副本错误;不要删除仍有活进程使用的句柄目录 |
| 重启遇到 MPS 残留状态 | 错误中的所有者租约、daemon 与客户端身份 | 按诊断确认存活作业再处理残留,不要执行全卡杀进程 |
| 显存下降但吞吐持平 | 比较时副本数是否没变 | 这符合共享存储的用途;只有新增容量被负载用起来才可能提升吞吐 |

## 六、常见误区

**看到同卡的两个阶段,就按同进程排查。** 部署图常只画 GPU 外框,容易藏掉进程边界。应同时核对 `process` 和设备声明;MOSS-TTS Local 的默认预处理与引擎同组,Vocoder 则独立,即使它们用的是同一张卡。

**为了关掉一个预算报错,把通用共置校验关掉。** 这看起来像是绕开保守限制,但由 `replica_devices` 引入的同卡进程共享仍强制要求完整占用预算;源码接受比例或总预留字节,旧文档只提比例。只设 `engine.kv_cache_bytes` 不能替代权重、激活和 graph 的预算。

**主副本已经不接请求,就先把它退出。** 普通独立副本可以这样想,共享权重时却会使从副本失去存储持有者。必须让从副本先退出,并以整条管线处理共享组故障;这不是单纯的负载均衡摘除。

**两个 Stage 各有 2 份副本,编号相同就一定配对。** 官方 Qwen 示例在默认轮询下确实成对推进,容易让人以为设备放置决定了请求配对。实际上它们是两个独立进程组,各自选一次 Replica;自定义绑定策略未必保持配对,同一组内部才共享同一次选择。
