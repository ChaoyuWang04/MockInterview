# 整体架构与一次请求的生命周期

一次 omni 生成被切成形态完全不同的几段之后,请求还怎么走、谁管调度、边界划在哪——这一章回答这个。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一个纯文本模型的一次生成,从头到尾是同一个模型在跑。Scheduler 只需要回答一个问题:这一步让哪些请求进批。

omni 模型不是。一次「听一段话、看一张图、想一想、再用声音答」的生成里至少有四种计算形态,它们对调度的要求互相冲突:

预处理是 CPU 上的解帧与重采样,一次一条,没有 KV cache 可言;Encoder 是一次性的大前向,计算量受单请求模态数量影响,也支持把多个请求攒成一批;thinker 是典型的自回归循环,吃显存、要前缀缓存、要连续批处理;Vocoder 是流式的小块解码,每攒够一小段码就要吐一次音频,吐晚了用户就听见卡顿。

这些负载需要不同的调度策略。自回归段要管理 KV cache 和连续批处理,Encoder 要组织一次性前向,Vocoder 要及时解码音频块。若下游只能等待上游整段完成,首音频就会被推迟。

它们的忙碌时段也不同:Encoder 主要处理输入,Thinker 和 Talker 持续生成,Vocoder 消费陆续到来的音频码。拆开调度后,既能让不同请求形成流水线,也能让同一请求的流式阶段重叠;实际延迟和利用率还取决于模型、放置与负载。

## 二、解法

把一次生成显式建模成一条有向图:每个节点是一个**Stage**,阶段自己声明跑在哪张卡、结果发给谁;阶段里挂一个和它负载匹配的 Scheduler。请求在图上流动,而不是在一个循环里打转。

从服务到计算可以分层理解:HTTP 或 WebSocket 收到它,客户端层把协议翻译成内部请求对象,**Coordinator**投给入口段,阶段收到后交给自己的 Scheduler,Scheduler 决定什么时候算,ModelRunner 准备前向批并跑前向。最终结果从终端阶段交回 Coordinator,流式块可提前返回。

这里的关键设计是**Coordinator 不负责模型专属计算**。沿这条请求主线,它主要负责四件事:把请求投给入口段、跟踪状态、收终端段的结果、出事时广播中止。它维护阶段控制端点与请求状态,但不替中间阶段决定每一跳;模型的接线由配置声明,阶段按约定执行。

三个容易看漏的地方:

**终端段是按请求算的,不是固定的。** 同一条管线,要音频输出的请求有两个终端——一个吐文本,一个吐波形,Coordinator 汇总最终结果,流式块可先返回;只要文本的请求只有一个终端,声音那半条图根本不会被走到。

**流边和结果边是两条平行的边。** thinker 一边把隐藏态一块一块地流给 talker,一边把文本结果按正常路由发给解码段。满足下游的攒块和 partial-start 条件后就能开工,不必等上游整份交付;共置配置等形态可能选择等待完整输入。

![同一请求的流式重叠示意:满足攒块与 partial-start 条件后,Talker 和 Vocoder 可以在上游完成前开始;首音频在首次解码完成后产生,条长不表示测量结果。](/opensource/sglang-omni/01a-streaming-overlap.svg)

**Qwen 默认语音配置每个阶段一个操作系统进程。** 共 7 个阶段进程,另有服务主进程;同进程配置、TP 和副本会改变这个数。默认一波启动,权重共享等场景才分波组织,就绪后服务才可用。

## 三、代价

**启动要等待多个阶段就绪。** GPU 阶段要加载相应模型与运行资源,CPU 上的 preprocessing 和 decode 则承担输入处理与文本输出;任何一个没起来,整条管线不可用。服务就绪需要整个配置中的必需阶段准备好。

**张量要跨进程。** 隐藏态、嵌入、音频码都得在进程之间搬。这是多阶段拆分直接买来的成本,也是为什么必须有一套单独的传输选择机制——那是 04 章的事。

**一个阶段失败会中止整条请求。** 任何一个终端段报错,Coordinator 立刻把整条请求判失败,并向所有段广播中止。非流式返回会等待终端结果聚合;流式返回可能已经发出部分文本或音频,之后才失败,已发送的内容无法撤回。代价是尾部的一次抖动会连累前面已经算完的部分,那些算力就白花了。

**排队的上限不是一个独立的旋钮。** Coordinator 只有在首个引擎段声明了有效的运行中上限与排队上限时,才按两者之和乘副本数设置在途上限。缺少声明时不启用这一层的上限,阶段内部仍可有自己的限制。

## 四、和单模型文本引擎不一样的 5 处

这里用 SGLang 的常规单副本文本服务作分层对比,不展开 PD 分离、TP、PP 与 DP 的全部形态。它正是本项目自回归阶段复用的引擎,对比目的是看清多阶段编排增加了什么。

两边都是多进程,但进程边切的位置不同,后面几条差异大半是从这一条派生出来的。

![常规 SGLang 文本服务与 Qwen3-Omni 默认语音配置的进程职责对比:两者都有服务主进程,Omni 将不同计算阶段进一步拆为七个阶段进程,其中包含 CPU 与 GPU 阶段。](/opensource/sglang-omni/01b-where-the-process-edge-falls.svg)

1. **Scheduler 的数量与种类。** 对照形态中的自回归工作由同类 Scheduler 负责;这边一条语音请求会依次落到好几个 Scheduler 手里,自回归的那个和 Vocoder 的那个,连批的概念都不一样。
2. **跨进程边上传的东西不是一个量级。** sglang 的进程间边传请求对象与 token,小到可以直接走消息通道;这边传的是隐藏态、嵌入和音频码,大到必须把协调消息和张量分成两条路走。
3. **结果有几个出口。** sglang 一条请求一个结果流;这边文本和音频是两条流、两个终端段,Coordinator 汇总最终结果,流式块可先返回,而且终端段的集合是按请求算的。
4. **拓扑是谁定的。** 对照形态围绕 Tokenizer、Scheduler 与 Detokenizer 组织;这边每个模型自己声明有哪些段、怎么连,用户只能覆写这些段上的设置,不能增删段。
5. **中止的波及面。** sglang 中止一条请求就是它自己的事;这边一个终端段失败会广播到所有段,包括那些已经把自己那份算完、正等着下游的段。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

配置分成管线、Stage、factory 与 engine 几层,还能用点号路径逐阶段覆写。拓扑由模型配置类声明,用户主要调整放置、资源和执行参数。引擎扩展参数可以传给 SGLang,但不代表所有上游功能都受支持;完整规则见 03 章。

**起服务的整体开关。** 下面以 Qwen3-Omni 为例,区分管线形态、部署与外围接口。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--text-only` | 命令行 | 关 | 未提供 --config 时选择 Qwen 的六阶段文本管线,没有 Talker 和语音输出 | 启动日志里的阶段清单 |
| `--colocate` | 命令行 | 关 | 校验 --config 选择的是 Qwen 共置配置;放置由该配置决定 | 启动日志里的放置摘要 |
| `--enable-realtime` | 命令行 | 关 | 挂上实时 WebSocket 端点 | 路由表里有没有那条路径 |
| `mps` | 管线级设置,命令行上按同一条路径语言写成 `--mps` | `off` | `auto` 只在同卡确实有 2 个及以上单卡非张量并行进程时开;`on` 一个进程就够,且平台不支持时直接报错 | 启动时的 MPS 状态行 |
| `--mem-fraction-static` | 命令行 | 不设时由 SGLang 自己定 | 给**每个**引擎段都设上静态显存比例 | 各段的显存占用日志 |
| `--<段名>.engine.mem_fraction_static` | 命令行点号覆写 | 无 | 只改这一段,盖掉上面那个全局值 | 同上 |
| `max_running_requests` / `max_queued_requests` | 引擎段的设置 | 随模型 | 首个引擎段显式声明有效值时,两者之和乘副本数形成 Coordinator 上限 | 拒绝时日志里会把这个上限打出来 |
| `--tts-batch-max-items` | 命令行 | 有默认值 | 批量语音接口一次最多收几条 | 超限时的接口报错 |
| `--allowed-local-media-path` | 命令行 | 不设 | 不设时禁用 file:// URL;裸本地路径默认仍允许,设置后按允许目录校验 | 请求被拒时的报错 |
| `--allowed-media-domain` | 命令行,可重复 | 不设 | 不设时任何公网地址都允许;设了就只允许这些域名 | 同上 |

**观测点:先看事件流,再看日志。** 请求级事件记录器按里程碑往 JSONL 里写,一条请求的完整时间线就是它的那几行:Coordinator 的准入与终端响应、每一段的收到输入与派发、每一跳的发出、Scheduler 侧的入队与 prefill 起止、首次吐出、Vocoder 的首个音频与解码结束。段与跳的耗时都从这里减出来。torch 剖析器和它共享同一个运行号,定位到段之后再用它往下钻。

在线健康看 Coordinator 的健康接口,它按状态分类统计当前在途的请求数。

**Qwen3-Omni 的三种启动形态。** 前两行的 `<模型>` 指该模型权重;第三行使用上游仓库的 H200 示例,其他硬件需调整显存预算。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 只要文本,单卡验证 | `sgl-omni serve --model-path <模型> --text-only` | 省去 Talker 与 Vocoder,减少语音侧的计算与显存需求 |
| 双卡语音,默认形态 | `sgl-omni serve --model-path <模型>` | 7 个阶段进程分两张卡,Talker 单独放置;资源隔离较直接,实际性能需按负载测量 |
| 单卡语音,挤一挤 | `sgl-omni serve --config examples/configs/qwen3_omni_colocated_h200.yaml --colocate --mps on` | GPU 阶段同卡但仍多进程,MPS 允许 kernel 重叠;节省卡数,也引入资源竞争 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后。**

| 症状 | 先查 | 然后 |
|---|---|---|
| 服务起不来,卡在某一波 | 启动日志里哪几段报到了、哪几段没有 | 没报到那段的子进程日志,通常是权重加载或显存不够 |
| 文本正常,音频一直不来 | 事件流里有没有 Vocoder 的首个音频事件 | 没有就往上看 talker 有没有收到流式块,再往上看那条请求是不是根本没被判成要音频输出 |
| 首包延迟忽好忽坏 | 事件流里每一跳的耗时,看抖的是哪一段 | 再结合队列与 kernel 轨迹区分排队、计算和传输 |
| 请求直接被拒 | 拒绝日志里打出来的在途上限 | 确认拒绝来自哪一层,再检查对应引擎段的准入配置 |
| 段数和文档对不上 | 启动日志里的阶段清单 | 以清单为准,官方 RFC 那张图是旧的 |

## 六、常见误区

**「Coordinator 总会从 SGLang 默认值算出在途上限。」** 不会。这里读取首个引擎段的准入默认声明与显式覆写;缺少必要值就不启用 Coordinator 上限,不能用引擎内部的运行时默认值代替。

**「终端段固定是两个,文本一个音频一个。」** 这话对着语音请求说没错,但终端集合是按请求算的——同一个服务上,一条不要音频的请求只有一个终端,声音那半条图完全不走。排障时按「两个终端都该有结果」去等,会等一个永远不来的东西。

**「七个进程意味着七段并行。」** 进程多不等于同时在算。Encoder 要等预处理,Thinker 要等输入嵌入;允许 partial start 的流式路径中,Thinker、Talker 与 Vocoder 又可以处理同一请求的不同进度。不同请求也可以形成流水线。

**「同卡共置就是同进程。」** Qwen 单卡语音配置仍是多个阶段进程,并不会自动变成 Python 对象引用直传。同进程是另一种配置:可省去序列化,但 Stage IO 共用事件循环,同步操作可能阻塞其他 Stage 的 IO;Scheduler 则在各自线程中运行。

**「官方 RFC 里的管线图就是当前实现。」** RFC 把语音管线画成 8 段,基准上是 7 段——那个聚合段只存在于纯文本管线里,语音路径上 thinker 和 talker 各自 fan-in,没有聚合这一步。同一份 RFC 里的阶段配置字段名也是旧的。文档用来理解设计意图,段数、字段名、默认值一律以启动日志和代码为准。

**「命令行帮助就是全部调参入口。」** 还有逐阶段的点号覆写。能被配置层接受,也不等于所有上游能力都能在该模型中使用;用 `config resolve` 看生效配置,实际支持范围以模型工厂和引擎适配为准。

**「中止是软的,已经算完的段不受影响。」** 中止是广播,所有段都会收到并清掉这条请求的状态,包括已经把自己那份算完、结果还在下游手里的段。这也是为什么尾部一次偶发失败,在监控上看起来像是前面几段一起出了问题。
