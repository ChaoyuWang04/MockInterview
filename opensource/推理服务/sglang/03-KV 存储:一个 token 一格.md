# SGLang 03|KV 存储:一个 token 一格

KV cache 为什么必须存在、朴素存法的三种浪费、分页的思想,vLLM 解读的「PagedAttention 与 KV Cache 管理」一章已经讲透。这一页只说 SGLang 遇到的问题、它的解法、以及它和 vLLM 不一样的地方。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

分页把碎片解决了,但共享的单位是块。vLLM 一块 16 个 token,两条请求的内容在第 20 个 token 处分叉,能共享的只有前 16 个;第 16 到 19 这 4 个 token 明明一模一样,后来那条请求也得重算一遍、写进自己的新块。

多轮对话、agent 循环、RL rollout 的分叉点落在任意一个 token 上。SGLang 的调度、驱逐、缓存复用全建在一棵前缀树上,树要在任意 token 位置劈开,底下的存储就必须能在任意 token 位置切开。块粒度做不到。

## 二、解法:两级,页的大小是 1

![SGLang 的两级 KV 存储:上半是第一级的清单,一张按并发上限乘最大上下文买断的整数矩阵,第 0 行专门垫给 CUDA graph 的假批次,请求 A 和请求 B 的前 12 格写着同一批格子号、第 12 格起才分开,每一行右边都拖着一条虚线的尾巴表示一直买断到最大上下文;下半是第二级的仓库,25 个格子一字排开,属于两条请求共用的、只属于 A 的、只属于 B 的和没人用的各是一种颜色,顺序是散的,一条箭头从清单第 0 列引到仓库的 3 号格说明两张清单写着同一个格子号就只存一份,仓库后面还叠着两层虚影表示每层各有一间](/opensource/sglang/03a-two-level-pools.svg)

把显存想成一个仓库,每个格子放一个 token 在某一层的 K 和 V;每层各有一间这样的仓库,同一个格子号在每层都指着自己那一份。请求那边另有一张清单,一条请求占一行,行的第 i 格写着「这条请求的第 i 个 token 在几号格」。GPU 拿着这一行去仓库取货。整章就是这两张表,加上一个负责发格子、收格子的分配器。

这就是 PagedAttention 那套间接寻址,只是页的大小定成 1 个 token。于是:

- 外部碎片没了,格子可以在仓库的任何位置。
- 内部碎片是 0,没有「最后一块没填满」这回事。vLLM 每条请求最多浪费 15 个 token,SGLang 是 0。
- 分叉不再对齐到块。两条请求前 1000 个 token 相同就共享 1000 个格子,第 1001 个各分各的,一个 token 都不用重算。树的节点值就是一段格子号,在任意位置劈开只改树,不动 KV。

分配器也因此简单得多:一整排空闲格子号躺在一个数组里,发货就切走前 n 个,收货直接拼回去,不需要算页号也不需要对齐。页大小一旦大于 1,这条路就换成另一个分配器,拿一个 GPU 核函数按「填满上一页的剩余、整页、尾页」三段去凑。

## 三、代价

两处,一处轻一处重。

**轻的那处:取货的次数变多。** 一格一个 token,取一次只拿一格。但一格在一层里装的是「本卡的 KV 头数乘头维乘精度」那么多字节,常见模型落在 256 字节到 2 KB 之间,而 GPU 访存的最小单位是 128 字节,所以每一趟都是满的——次数多了,却没有空跑,普通模型上测不出差别。真正不接受一格一格取的是那些一次要一整页的注意力后端,SGLang 在它们上面把页改回去,细粒度的好处也跟着没了。

**重的那处:第一级那张清单按最坏情况买断。** 它是一张稠密的整数矩阵,行数是并发上限,列数是最大上下文,启动时一次分配好,之后既不增也不缩。4096 并发、131072 上下文就是 2 GB,跑的全是短请求也是 2 GB。vLLM 那张表每 16 个 token 才记一个号,同样条件是 134 MB。这就是细粒度要付的固定价钱,和实际请求有多长完全无关。

## 四、和 vLLM 不一样的六处

![两边都必须做的两件事各占一行,每一行里 vLLM 和 SGLang 各一条带子:第一件事是把逻辑上的第 i 个 token 翻译成显存位置,同样 64 个 token 的跨度上 vLLM 只画出 4 个方框、每框写着 16 个 token 记 1 个号,SGLang 画出 64 个细方框,方框数量本身就是这张表宽 16 倍的原因;第二件事是定一个分配与共享的最小单位,两条请求在第 20 个 token 处分叉,vLLM 那两条带子的绿色只能停在 16,请求 B 的第 16 到 19 这 4 格是红的、要重算一遍写进自己的新块,SGLang 那两条带子的绿色正好停在 20,红色那 4 格根本不存在](/opensource/sglang/03b-vllm-diff-granularity.svg)

1. **分配的最小单位。** vLLM 一直是 16 个 token 一块。SGLang 默认 1 个 token 一格,但有五组后端各自声明自己只认哪几档页——FlashMLA 和 HPC-Ops 只认 64,TensorRT-LLM 和 CuteDSL 的几个 MLA 后端认 32 或 64,TensorRT-LLM 的 MHA 后端认 16、32、64、128,Intel 那条认 64 和 128。选中这些后端而页不在它认的那几档里,启动时就被改掉(多数改成 64),只打一行警告。用 DeepSeek 的时候要知道自己实际上在按页跑,前缀命中只能到页的边界——树的匹配长度本身就是先向下取整到页的。

2. **第一级那张表有多宽。** 两边都是启动时按「并发上限乘最大长度」买断的稠密整数矩阵,区别只在每格管几个 token,于是同样的配置下 SGLang 那张宽 16 倍。这不是「vLLM 会按需增长而 SGLang 不会」,两边都不会。

3. **谁记得哪些内容有人存过。** vLLM 按块算哈希,查一次表就知道;SGLang 把所有请求的 token 序列合成一棵前缀树,见 04 章。树能在任意 token 处劈开,这正是把页压到 1 的理由;代价是匹配和排序是 CPU 的活,等待队列超过 128 条时调度器自己就退回先来先服务。

4. **显存比例那个参数的意思不一样。** vLLM 的是「整张卡我用多少」,探测一次之后,权重和激活之外全给 KV。SGLang 的是「权重加 KV 一共占多少」,余下的留给激活和 CUDA graph 的缓冲;不指定时它按卡的容量倒推,80 GB 的卡上大致留 10 GB。同一个数字换更大的模型,SGLang 给 KV 的反而更少。运维看就绪前那行日志里剩多少显存,官方建议 5 到 8 GB。

5. **并发上限卡在哪。** SGLang 的并发上限默认不由显存直接定:拿总槽数除以最大上下文再乘 512,夹进 2048 到 4096,最后还要不超过总槽数的一半。上下文短的时候显存能放的请求远不止 4096,并发却停在那儿,得手动调高;上下文长的时候反过来,显存先见底。混了状态空间层的模型再多一道:每条请求要占 3 份状态(开了额外缓冲是 4 或 5,关掉前缀缓存是 1),并发上限被状态池除以这个数卡住,调 KV 的参数一点用没有。

6. **显存见底了怎么办。** 两边都是踢掉在跑的请求让它重算。vLLM 多一道默认关着的准入水位,把抢占腾出来的空间留给在跑的请求。SGLang 没有水位,它在每一步 decode 之前先问一句「下一步放得下吗」,放不下就先把树上没人用的节点驱逐掉,还不行才开始踢;踢的顺序是已经生成得最少的先走,生成得一样少的里面 prompt 最长的先走——丢掉的工作最少、腾出的空间最多,而且至少留一条在跑。每踢一个还顺手多驱逐 20 步的量,免得下一步又踢。两边默认都不备份被踢的 KV,SGLang 只在 PD 分离的 decode 节点上备到内存,因为那个节点自己算不了 prefill。

显存放不下往内存和硬盘放,两边都有,vLLM 默认关,SGLang 的分级缓存是它的招牌功能之一,见 05 章。

## 五、调参与观测

**参数在哪调。** 启动参数(`--mem-fraction-static` 这种命令行旗标,也可以写进 YAML 用 `--config` 传)决定池的大小和形状,改了要重启。环境变量(`SGLANG_` 前缀)是少数内部阈值,改了也要重启。运行时只有三个入口:`/flush_cache` 清空整棵树(有请求在队列里或在跑时拒绝,返回失败);`/release_memory_occupation` 与 `/resume_memory_occupation` 让 KV 池整体让出显存再拿回来;`/set_internal_state` 只能改流水线微批和推测解码的几个阈值,改不了这一页的任何参数。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--mem-fraction-static` · 权重加 KV 占显存的比例 | 启动 | 按卡容量倒推,80 GB 卡上约 0.875 | 调高:槽变多,并发和吞吐上去,余量变薄,激活或 CUDA graph 可能 OOM。调低:反过来 | 就绪前日志 `available_gpu_mem`,5–8 GB 合适;每次动 0.01 |
| `--max-total-tokens` · KV 池最多放多少 token | 启动 | 探测值 | 只能调低,高于探测值会被忽略并打 warning。调低:并发上限跟着降,用来复现某个并发下的行为 | 就绪前日志 `max_total_num_tokens` |
| `--max-running-requests` · 最多同时跑多少请求 | 启动 | `min(clamp(槽数 ÷ 上下文 × 512, 2048, 4096), 槽数 ÷ 2)` | 调高:短上下文下并发才上得去,第一级那张表按比例变大。调低:并发封顶,抢占变少但排队变长 | 就绪前日志 `max_running_requests`;Decode batch 行的 `#running-req` 贴着它就是卡在这里 |
| `--schedule-conservativeness` · 准入估计输出长度的松紧 | 启动 | 1.0 | 调高(1.3):准入更悲观,抢占变少,`token usage` 降一点。调低(0.3):进批更激进,`token usage` 上去,抢占可能变多 | 警告行 `KV cache pool is full. Retract requests.`;`token usage` 与 `#queue-req` |
| `--chunked-prefill-size` · 长 prompt 一次算多少 | 启动 | 按卡容量:2048 / 4096 / 8192 / 16384 | 调低(4096 或 2048):长 prompt 的 prefill 激活变小,不再 OOM,但长 prompt 的 TTFT 变长 | prefill 阶段 OOM 时先动它,不动比例 |
| `--page-size` · 分配的最小单位是几个 token | 启动 | 1(MUSA 平台、ROCm 开向量化布局时 64) | 别手调,后端会按自己的要求改。变大:命中退到页边界,每条请求平均浪费半页 | 启动日志里 page_size 被改的警告 |
| `--kv-cache-dtype` · KV 用什么精度存 | 启动 | `auto`(跟模型精度) | FP8:槽数翻倍。FP4 那几档还要额外存一份缩放,不到 4 倍。后端不支持融合反量化时每步多一次转换,TPOT 变长 | 就绪前日志 `max_total_num_tokens` 涨了多少 |
| `--swa-full-tokens-ratio` · 窗口层和全注意力层的槽数比 | 启动 | 0.8;DeepSeek-V4 一类模型改成 0.1 | 窗口模型两个子池的比例;窗口层槽不够时调高 | Decode batch 行的 `swa token usage` |
| `--max-mamba-cache-size` · 状态池能放多少份状态 | 启动 | 由 `--mamba-full-memory-ratio`(0.9)推 | 混合模型的状态池;并发被它卡住时调高 | 启动 warning `capped ... by the mamba state cache`;Decode batch 行的 `mamba usage` |
| `--enable-memory-saver` · 让 KV 池能整体让出显存 | 启动 | 关 | 开了 KV 池才能整体让出显存;RL 训推一体必开 | `/release_memory_occupation` 是否成功 |
| `--cuda-graph-max-bs-decode` · decode 用 CUDA graph 的最大批 | 启动 | 按卡容量与 TP 数,8 到 512 | 调高:大批 decode 更快,但 CUDA graph 吃余量,要同时调低比例 | 就绪前 `available_gpu_mem` 是否掉到 5 GB 以下 |
| `SGLANG_RETRACT_DECODE_STEPS` · 抢占后多留几步的量 | 环境变量 | 20 | 调高:抢占更少,但一次踢得更狠 | 警告行出现的频率 |

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表;组合与推荐值是按语义推的起点,**不是实测最优**。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 通用对话,H100 / H200 八卡大模型,上下文 32k 以上 | 只给 `--model-path` 和 `--tp-size 8`,起完看就绪前那行,`available_gpu_mem` 高于 8 GB 就把 `--mem-fraction-static` 每次加 0.01 再起 | 全默认,把调参交给日志;换来的是不会一上来就 OOM,代价是第一次起服务要试两三轮 |
| 短上下文高并发,例如 RAG 问答或分类,上下文 4k 以内 | 在上一套基础上显式加 `--max-running-requests 8192`,并把 `--chunked-prefill-size` 留在默认 | 突破默认 4096 的封顶,吞吐上去;代价是第一级那张表跟着变大,抢占也会变频繁,要盯 `Retract requests` 那行 |
| RL 训推一体,推理和训练共用一张卡 | 加 `--enable-memory-saver`,把 `--mem-fraction-static` 显式压到 0.7–0.8 | 让出显存的能力和训练侧的余量,换掉一部分 KV 容量与峰值吞吐;发请求前后各调一次让出与恢复接口,让出前必须等到完全空闲 |

**怎么看。** 三行日志够用。就绪前那一行看容量:`max_total_num_tokens`、`max_running_requests`、`context_len`、`available_gpu_mem`。`Prefill batch` 行的 `#new-token` 和 `#cached-token` 看命中。`Decode batch` 行的 `#running-req`、`token usage`、`gen throughput`、`#queue-req` 看稳态;混合模型上这一行还多出 `swa token usage` 或 `mamba usage`,而 `token usage` 本身**不含**状态池。`token usage` 高于 0.9 是健康,`#queue-req` 在 100–2000 之间说明客户端压得够。请求级看响应 `meta_info` 里的 `cached_tokens`。`/server_info` 能读回当前生效的全部参数和显存账(`/server_info` 是它的旧壳,每调一次打一行弃用警告)。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动就报显存不够 | 错误信息里算好的最小可行比例 | 照抄那个值 |
| prefill 阶段 OOM | `--chunked-prefill-size` | 降到 4096 或 2048,不先动比例 |
| decode 阶段 OOM | `--max-running-requests` | 调低;或比例降到 0.8、0.7 |
| `Retract requests` 频繁 | `--schedule-conservativeness` | 调到 1.3;仍频繁再减并发 |
| `token usage` 低于 0.9 且 `#queue-req` 大 | 准入太保守,常见于 max_new_tokens 给得大但回答早停 | 保守度调到 0.3 |
| `#running-req` 贴着 4096 不动 | 卡在并发上限的默认夹取 | 显式指定 `--max-running-requests` |
| 混合模型并发上不去,`token usage` 却很低 | 启动 warning 里有没有 `capped ... by the mamba state cache` | 调状态池或它的比例,不调 KV 比例 |
| DeepSeek 的 `cached_tokens` 总是 64 的倍数 | 启动日志里 page_size 被后端改了的那行警告 | 换后端,或接受页边界命中 |
| 回答质量突然不对,指标全正常 | 权重更新那次有没有把 `flush_cache` 关掉 | 保持默认开着 |

## 六、常见误区

- **看到 OOM 就降 `mem_fraction_static`。** 先分清在哪一步 OOM。prefill 时是长 prompt 的激活,动 `chunked_prefill_size`;decode 时是并发,动 `max_running_requests`。比例是最后才动的,它一降整机容量都跟着降。
- **看到 Retract 警告就减并发。** 官方文档明说每分钟一次左右是正常的。频繁出现先把保守度调到 1.3。减并发是把抢占换成排队,TTFT 照样差。
- **`token usage` 只有 0.6 就去加显存。** 队列里有人等、使用率却低,是准入太保守,不是显存少。典型场景是客户端给了很大的 max_new_tokens 但回答很早就停。保守度调到 0.3。
- **并发到 4096 上不去就去调显存。** 短上下文下卡的是那道「除以上下文再乘 512、夹进 2048 到 4096」的估算,显存空着一半也没用。显式指定 `max_running_requests`。
- **调 `max_total_tokens` 想涨容量。** 它只能往下压,给大了会被忽略并打一行 warning。
- **DeepSeek 的命中数总是 64 的倍数,以为缓存坏了。** 是后端把页钉成了 64,树在匹配时先把长度向下取整到页,命中只能到页边界。
- **调大 `cuda-graph-max-bs-decode` 之后开始 OOM。** CUDA graph 的缓冲吃的是比例之外那块余量,调它要同时把比例降下来。
- **开 FP8 KV 期望翻倍,结果变慢了。** 后端不支持融合反量化时每步多一次转换。先确认后端。
- **RL 训推一体:释放显存失败。** 释放接口断言服务完全空闲,有请求在飞就直接拒。先停发请求,等 `#running-req` 归零。
- **以为释放显存和更新权重要自己记得清树。** 两件事都自带清:释放接口在让出 KV 之前自己会清一次;四个权重更新接口的清缓存开关默认都是开的。真正的坑是反过来——有人为了省时间把它关掉,于是旧权重算的 KV 配上新权重,前缀命中越高答案错得越多,而且没有任何报错。
- **混合模型看着 KV 使用率很低,并发却上不去。** 卡在状态池,而日志里的 `token usage` 根本不统计状态池。那行 `capped ... by the mamba state cache` 是个 warning,很容易被当成普通信息略过。
