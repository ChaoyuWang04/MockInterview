# SGLang 14|多模态

引擎只认 token 而图片不是 token、模型的三段结构与谁是 tower、朴素做法的四堵墙、占位符机制、三级缓存、编码器和 decoder 抢同一个 step、M-RoPE 与视频剪枝,vLLM 解读的「多模态」一章已经讲透。这一页只说 SGLang 把一张图变成 embedding 的那条路、它省在哪、以及和 vLLM 不一样的地方。EPD 把编码器拆成单独服务器在 11 章,图片按内容哈希做占位 token 参与前缀树在 04 章,ViT 的 CUDA graph 开关在 07 章,多模态先从 KV 预算里扣一块在 03 章,本页只回指。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

一张 1024×1024 的图在 Qwen2.5-VL 上约 1300–1400 个 token,默认上限 16384 个;这些 token 在 KV 池里和文本一样占格子。图变成 token 要走 3 段,每段坏一个指标:

- **预处理在 CPU 上,而且在 tokenizer 进程里。** 解码 JPEG、缩放、归一化、切 patch,HF 处理器单线程 50–300 毫秒一张;tokenizer 进程是所有请求的入口,图片流量到 10–50 张每秒时它先打满,连纯文本请求的 TTFT 一起涨。
- **ViT 小批下发开销大。** 32 层每层 10–15 个 kernel,一张图 300–500 次下发;批只有 1 张时下发时间和算的时间一个量级,20–100 毫秒里有一半在等 CPU 发指令。
- **编码器和 decoder 争卡。** ViT 在 prefill 的前向里跑,同一张卡同一条流;它跑的那 20–100 毫秒,所有在 decode 的请求一起等。图多的负载下 TPOT 的 P99 先坏;多图、视频再多一层,ViT 的激活在 prefill 阶段把余量吃光,直接 OOM。

## 二、解法:先变成 embedding,再当文本走

最天然的直觉是「图片先过 ViT 变成 embedding,塞进文本 embedding 的对应位置,后面的 prefill 和 decode 不用知道有图」。SGLang 就是这么做的,一条请求的路径:

- tokenizer 进程收到请求,4 个 IO 线程并行下载和解码媒体(JPEG 默认由 nvJPEG 在 GPU 上解,失败退回 PIL);HF 处理器在 1–2 个隔离线程里跑,每个线程一份处理器的深拷贝;产出特征张量,以及把每张图展开成一段占位 token 的 input_ids。
- 特征经共享内存送到调度器。调度器给每个特征算一个哈希(CPU 上取 sha256 的前 8 字节,已在 GPU 上时用 Triton 核),占位 token 写成 1000000 加哈希对 2 的 30 次方取模,于是前缀树看到的是「这张图的内容」而不是「有一张图」(04 章)。
- prefill 那一步,模型运行器先拿哈希查 GPU 上的 embedding 缓存:命中直接取,不跑 ViT;没命中的把这一批所有请求的所有图去重后合成 1 次 ViT 调用,结果按图切开塞进缓存(默认 100 MiB,LRU)。然后把 embedding 散到占位位置上,语言模型照常前向。
- 开了分块预填充时,第一个碰到这张图的块整图编码、整份进缓存,后面每块只按位置切一段;编码完特征挪回 CPU,缓存被挤掉时还能重算。

为什么不吃亏:ViT 只有语言模型 1–5% 的参数,一张图 20–100 毫秒,和同样 1300 个 token 的 prefill 一个量级;真正省的是重复:多轮对话里同一张图第 2 轮起既不跑 ViT(embedding 缓存命中)也不跑 prefill(前缀树命中),两个缓存用的是同一个哈希。

## 三、代价

- **tokenizer 进程会碰服务卡。** 快速图像处理器默认在 `base_gpu_id` 那张卡上做缩放和归一化,正是调度器在跑 decode 的卡;所以这条路径的处理线程被钉在 1 个,多开反而更慢。
- **显存先扣一块。** embedding 缓存 100 MiB,用 GPU 传输特征时再加 1024 MiB 的池,在 KV 池定大小之前就从预算里扣掉(03 章)。
- **哈希是 CPU 的活。** 一张 1300 token 的图特征 10–25 MB,sha256 要 15–50 毫秒,在调度器进程里算;`SGLANG_MM_BUFFER_SIZE_MB` 能借 GPU 算,默认 0。
- **分块预填充管不住 ViT。** 整图在第一个块就编码完,激活峰值由这个块里所有请求的所有图决定,分块只切语言模型那一半。
- **特征来回搬。** tokenizer 到调度器 1 次,调度器上 GPU 1 次,编码完再回 CPU 1 次。
- **占位 token 烧 KV。** 一张满分辨率的图 16384 个格子,`--mm-process-config` 的 max_pixels 是唯一的刹车。
- **看不见。** 主服务器的 `/metrics` 里没有一个多模态指标,`sglang:encoder_*` 那组只在 EPD 的 encoder 服务器上有。
- **功能表打折。** 6 个架构自动关分块预填充;多模态模型的 prefill 默认不进 piecewise CUDA graph,白名单 3 个 piecewise、9 个 breakable(07 章);Gemma3、Llama4、Step3-VL、Inkling 默认关多模态。

## 四、和 vLLM 不一样的八处

1. **预处理在哪个进程、开多少线程。** vLLM 在 API 进程,媒体线程池 8,处理器缓存 4 GiB 每进程默认开。SGLang 在 tokenizer 进程,IO 线程 4(Qwen-VL、Kimi、PaddleOCR 是 16),处理线程 1–2 自动定,预处理缓存默认关(只有 Kimi-K3 默认 256 MiB),快速图像处理器默认在服务 GPU 上跑。
2. **缓存层数与键。** vLLM 三级:处理器缓存、按 embedding 个数计的编码器缓存、混了媒体身份的块哈希。SGLang 两级半:预处理缓存的键是媒体字节的 sha256 加处理器指纹加参数,embedding 缓存的键是特征张量的哈希、按字节 LRU,前缀树的占位 token 用的是后一个哈希,所以「有没有做过」和「算过没有」是同一个问题。
3. **有没有编码器预算。** vLLM 每步一道闸,算力预算或缓存容量不够就给这条请求 0 个 token 等下一步。SGLang 没有这道闸,prefill 批里有多少图就编多少,全树没有 encoder budget 这个概念,能限的只有每请求的数量和像素。
4. **分块怎么切图。** vLLM 默认切开占位区,每块只编本块那部分,可以禁止切开。SGLang 第一个碰到图的块整图编码,后面按位置切 embedding;6 个架构直接自动关分块。
5. **每模态上限的语义。** vLLM 默认 999,设 0 卸载那个模态的编码器。SGLang 默认不限,设了只拒请求,不卸载;不加载 encoder 权重要走 EPD 的 `--language-only`(11 章)。
6. **编码器 DP 的形态。** 两边都要模型声明。SGLang 是一个开关,把 ViT 复制到 TP 里每个 rank,图片按像素量均衡分片、算完 all-gather,15 个模型文件接了;TP=1 时只打警告。
7. **视频剪枝。** vLLM 是请求级剪枝率,模型要实现位置重算,视频路径的图自动关。SGLang 的 EVS 是模型配置里的 `video_pruning_rate`,首帧全保留、后续帧按与前帧的相似度丢 token,只有 1 个模型继承了它,README 明说和 Qwen2.5-VL 这类靠位置编码的模型不兼容。
8. **直传与自带哈希。** vLLM 直传 embedding 要显式开启、只对可信调用方。SGLang 原始媒体、处理器输出、预计算 embedding 3 种格式默认都收,全树没有开关;调用方还能自带 `mm_hashes` 和 `content_hash`,让外部路由器的决策和前缀树的键对齐。

## 五、调参与观测

**参数在哪调。** 启动参数一组 `--mm-*` 加 `--enable-multimodal`、`--limit-mm-data-per-request`、`--image-processor-backend`,改了要重启;环境变量 `SGLANG_VLM_CACHE_SIZE_MB`、`SGLANG_VIT_ENABLE_CUDA_GRAPH`、`SGLANG_IMAGE_MAX_PIXELS`、`SGLANG_MM_BUFFER_SIZE_MB`,以及没有前缀的 `REQUEST_TIMEOUT`;模型配置里的 `video_pruning_rate` 用 `--json-model-override-args` 改;请求侧 OpenAI 接口收 `image_url`、`video_url`、`audio_url`、`input_audio`,原生接口收 `image_data`、`video_data`、`audio_data`(文件路径、URL、base64、PIL 对象,一个请求给列表,批请求给列表的列表),外加 `mm_hashes`。运行时接口只有 `/flush_cache`,它顺手清空预处理缓存;没有任何多模态参数能在线改。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--enable-multimodal` · 开多模态 | 启动 | 多模态架构自动开;Gemma3、Llama4、Step3-VL、Inkling 默认关 | 关着时图片字段被忽略,当纯文本模型跑;没有 `--disable-multimodal` | 启动日志 `Multimodal is disabled for … set --enable-multimodal` |
| `--mm-attention-backend` · ViT 用哪个注意力 | 启动 | 按卡:Hopper fa3、Blackwell fa4、其他 CUDA triton_attn | 9 个取值;fa3 在 Blackwell 上直接报错;sdpa 最慢但哪都能跑 | 启动日志 `Multimodal attention backend not set. Use fa3` |
| `--mm-processor-worker-num` · HF 处理器的线程数 | 启动 | 0 = 自动:GPU 路径 1,CPU 路径 2 | CPU 路径 2 个线程吞吐涨 20–40%(官方 Qwen2.5-VL 4.46 → 6.08 req/s);GPU 路径开 2 个反而减半(9.30 → 4.02) | 日志 `Multimodal processor concurrency enabled with N isolated worker threads` |
| `--mm-io-worker-num` · 下载与解码的线程数 | 启动 | 0 = 模型默认 4;Qwen-VL、Kimi、PaddleOCR 16 | 远端 URL 多时调高,TTFT 里的加载段缩短;每个 tokenizer worker 各一份 | 日志 `Multimodal data loading enabled with N worker threads`(超过 4 才打) |
| `--image-processor-backend` · 缩放归一化在哪做 | 启动 | auto(GPU 快速处理器) | pil:全在 CPU,不抢服务卡,预处理时延涨 2–5 倍;auto:在 `base_gpu_id` 那张卡上跑 | tokenizer 进程在 `nvidia-smi` 上是否占显存 |
| `--mm-process-config` · 给 HF 处理器的限制 | 启动 | 无 | image.max_pixels 降到 1048576:每图最多约 1300 个 token 而不是 16384,TTFT 与 KV 占用都降,小字识别变差;video.fps、max_frames 同理 | 响应 `prompt_tokens` 里每图的贡献 |
| `--limit-mm-data-per-request` · 每请求每模态的数量上限 | 启动 | 无限制 | 超过直接拒;不卸载编码器 | 错误 `Image count N exceeds limit` |
| `--mm-preprocess-cache-size-mb` · 预处理结果的 CPU 缓存 | 启动 | 模型定:Kimi-K3 256,其他 0 | 同一张图反复来(系统提示里的图、多轮)时跳过解码与缩放;预算按 tokenizer worker 数均分,最多 8192 条 | 日志 `Multimodal preprocess cache enabled for … MiB total` |
| `--trust-mm-content-hashes` · 信调用方的 content_hash | 启动 | 关 | 开:预处理缓存命中时连媒体字节都不读;调用方哈希给错就答错图 | — |
| `--mm-feature-transport` · 特征怎么送到调度器 | 启动 | cpu(单机) | cuda_ipc:特征留在 GPU 池里少 1 次拷贝,池 `SGLANG_MM_FEATURE_CACHE_MB` 1024 MiB 从 KV 预算里扣,满了退回 cpu | 日志 `CUDA IPC multimodal feature pools reserve N MiB` |
| `--mm-enable-dp-encoder` · ViT 按数据并行 | 启动 | 关 | TP 内每个 rank 复制一份 ViT,图片按像素量分片;多图或高分辨率下 TTFT 降;TP=1 无效;权重复制多占显存 | 日志 `--mm-enable-dp-encoder is enabled across TP=N` |
| `--enable-broadcast-mm-inputs-process` · 只在 rank 0 组装多模态输入 | 启动 | 关 | 大 TP 下省掉每个 rank 各自重建一遍的 CPU 时间 | — |
| `SGLANG_VLM_CACHE_SIZE_MB` · GPU 上的 embedding 缓存 | 环境变量 | 100;Qwen3-VL 在大 Hopper 卡上和 RL on-policy 时自动 0 | 调高:重复图不再跑 ViT;从 KV 预算里扣;0 关掉 | 日志 `Reserving X GB of the KV budget for post-sizing multimodal allocations` |
| `SGLANG_VIT_ENABLE_CUDA_GRAPH` · ViT 走 CUDA graph | 环境变量 | 0 | 1:小批 ViT 时延降 20–50%;按序列长度每种尺寸一张图,分辨率杂时显存涨;只对 Qwen2.5-VL、Qwen3-VL、InternVL、Kimi-K3 生效(07 章) | 首次出现某个尺寸时的捕获停顿 |
| `SGLANG_IMAGE_MAX_PIXELS` · Qwen-VL 系的缩放上限 | 环境变量 | 16384 × 28 × 28 | 调低等价于 image.max_pixels,但只对 Qwen-VL 系处理器生效 | 同 `--mm-process-config` |
| `SGLANG_MM_BUFFER_SIZE_MB` · 算哈希时借的 GPU 缓冲 | 环境变量 | 0 | 调 256–1024:特征哈希从 CPU sha256 换成 GPU 核,单图省 15–50 毫秒;放不下的张量退回 CPU | 日志 `Preallocated NMB GPU buffer` |
| `REQUEST_TIMEOUT` · 拉远端媒体的秒数 | 环境变量 | 图 3、音频 5、视频 10 | 内网慢时调高;`--media-url-max-file-size-mb` 64 与 `--allowed-media-domains` 一起限;最多 5 次重定向 | 错误 `Error while loading data` |
| `video_pruning_rate` · EVS 视频剪枝率 | 模型配置 | 0 | 0.7 保留 30% 的视频 token,官方例子 TTFT 11.96 → 8.79 秒;0.9 时 VideoMME 从 0.665 掉到 0.644;只有继承了 EVS 的模型认 | 日志 `[EVS] … enabled` |

**怎么看。** 没有专门的指标,靠三处:启动日志(后端那行、`Reserving` 那行、处理器并发那行、`Automatically turn off --chunked-prefill-size` 那行);运行时两条警告,`Discarding cached multimodal embedding due to a token-count mismatch` 和 `Number of tokens in multimodal embedding does not match those in the input text`;剖析时 `/start_profile` 出来的 trace 里 `sglang.vlm.mm_embedding` 是 ViT 加散布,`sglang.vlm.language_model_prefill` 是语言模型,两段的比值就是「编码器占了 prefill 多少」。响应 `meta_info` 里的 `cached_tokens` 把占位 token 也算在内,图命中前缀树时它会一次跳 1300 以上。

| 症状 | 先查 | 然后 |
|---|---|---|
| 图多时 TTFT 高、GPU 利用率低 | tokenizer 进程的 CPU 是否打满;处理线程是不是 1 | `--image-processor-backend pil` 后线程调 2;加 `--tokenizer-worker-num`;远端 URL 多就加 IO 线程 |
| 图多时 decode 的 TPOT 尾巴变差 | ViT 是否在服务卡上和 decode 同批;图像处理器是否也在服务卡上 | 开 ViT 图;`--mm-enable-dp-encoder`;根治走 EPD(11 章) |
| 同一张图反复发还是慢 | `SGLANG_VLM_CACHE_SIZE_MB` 是否被模型覆盖成 0;`SGLANG_MM_SKIP_COMPUTE_HASH` 是否开着 | 显式设 100–1000;关掉 skip hash |
| 多图请求 prefill 阶段 OOM | 每图多少 token;这个架构的分块是否被自动关 | `--mm-process-config` 降 max_pixels 和 max_frames;分块对 6 个架构无效,只能限图 |
| 警告 `token-count mismatch` | 处理参数改过没有;是不是两张图哈希撞了 | 偶发忽略;频繁就开 `SGLANG_MM_PRECOMPUTE_HASH` 看哈希是否在传输前后不一致 |
| 警告 `does not match those in the input text` | `--chunked-prefill-size` 是否小于单图 token 数 | 调高分块或关掉 |
| KV 比预期少 100 MiB 到 1 GiB | `Reserving … multimodal` 那行 | 正常;不想要就 `SGLANG_VLM_CACHE_SIZE_MB=0` 且不用 cuda_ipc |
| 远端图片报 `Error while loading data` | 域名白名单、64 MiB 上限、3 秒超时 | 调 `REQUEST_TIMEOUT`;白名单加域名;换 base64 直传 |
| Gemma3、Llama4 发图没反应 | 这 4 个架构默认关多模态 | 加 `--enable-multimodal` |
| 请求 `exceeds limit` | `--limit-mm-data-per-request` | 调高,或客户端拆请求 |

## 六、常见误区

- **「预处理在 CPU 上,和 GPU 无关」。** 因为 HF 处理器是 CPU 库。实际默认的快速图像处理器在 tokenizer 进程里用 `base_gpu_id` 那张卡做缩放归一化,和调度器抢同一张卡;自动线程数在这条路上被钉成 1 就是因为这个。要真的不碰卡,`--image-processor-backend pil`。
- **「`--mm-processor-worker-num` 越大越快」。** 因为它叫 worker。官方在 GB300 上测过,GPU 路径开 2 个线程吞吐从 9.30 掉到 4.02 req/s;只有 pil 路径的第 2 个线程是真并行。
- **「embedding 缓存是显存大头,先调它」。** 因为它是唯一一个带 SIZE_MB 的多模态变量。默认 100 MiB;真正吃显存的是占位 token 占的 KV 格子(一张满分辨率的图 16384 个)和 ViT 的激活,先动 max_pixels。
- **「开了分块预填充,一张图会拆成多块编码」。** 因为语言模型是这样。整图在第一个碰到它的块里编完,分块只切 embedding;所以分块救不了 ViT 的 OOM,而且分块比单图 token 数还小时会出 `does not match` 警告让你把它调大。
- **「`--limit-mm-data-per-request` 设 0 能省掉 encoder 权重」。** 从 vLLM 带来的习惯。这里设了只拒请求,权重照加载;不加载 encoder 要 EPD 的 `--language-only`。
- **「embedding 缓存命中就等于 prefill 也省了」。** 因为两处都叫缓存。命中只跳过 ViT,1300 个占位 token 照样过语言模型;只有前缀树也命中(要求图前面的文本也一样)才两头都省。反过来前缀树命中了 ViT 一定不跑,因为占位区整个在前缀里。
- **「Qwen3-VL 也有 100 MiB 的 embedding 缓存」。** 因为默认值写着 100。Qwen3-VL 在大 Hopper 卡上被模型覆盖成 0(理由是流式流量每张图只用一次),重复图的流量要自己显式设回去。
- **「`cached_tokens` 只数文本」。** 因为图不是 token。占位 token 是树里的普通 token,一张图命中就是 1300 以上的 `cached_tokens`;看到这个数突然跳高不是 bug。
- **「ViT CUDA graph 设了就对所有模型生效」。** 因为是全局环境变量。只有 4 个模型系接了运行器,其他模型读了变量什么都不做,也不打日志。
- **「多模态有 `/metrics` 指标」。** 因为 EPD 文档里有 `sglang:encoder_*`。那组只在 encoder 服务器上,单机主服务器一个多模态指标都没有,只能看日志和 profile。
- **「`REQUEST_TIMEOUT` 是 SGLang 的变量」。** 它没有 `SGLANG_` 前缀,在 `/get_server_info` 里也看不到;图片默认 3 秒,对象存储慢一点就报加载失败,第一反应往往去查网络而不是这个变量。
