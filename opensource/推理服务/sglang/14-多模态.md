# SGLang 14|多模态

引擎只认 token 而图片不是 token、模型的三段结构与谁是 tower、朴素做法的四堵墙、占位符机制、三级缓存、编码器和 decoder 抢同一个 step、M-RoPE 与视频剪枝,vLLM 解读的「多模态」一章已经讲透。这一页只说 SGLang 怎么把一张图压成一个数、让两级缓存共用它,以及为此付了什么。ViT 的图捕获在 07 章,占位 token 参与前缀树在 04 章,把编码器拆成单独的服务器在 11 章,多模态从 KV 预算里预扣一块的账在 03 章,本页各留一句。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

一张 1024×1024 的图在 Qwen2.5-VL 上占 1300–1400 个 token,默认的缩放上限允许单张图最多占到 16384 个;这些 token 在 KV 池里和文本一样占格子。图要变成 token 得走 3 段,每段坏一个指标:

- **预处理在主进程里,而且它会碰服务卡。** 解码 JPEG、缩放、归一化、切 patch,这些活儿默认由快速图像处理器在服务的那张卡上做,而调用它的线程在主进程里——所有请求的入口。图片流量到 10–50 张每秒时这个进程先打满,连纯文本请求的 TTFT 一起涨。
- **ViT 小批下发开销大。** 32 层每层 10–15 个 kernel,一张图 300–500 次下发;批里只有 1 张时,下发时间和真正算的时间是一个量级,20–100 毫秒里有一半在等 CPU 发指令。
- **编码器和 decoder 争同一步。** ViT 在 prefill 的前向里跑,同一张卡同一条流;它跑的那 20–100 毫秒,所有在 decode 的请求一起等。图多的负载下 TPOT 的 P99 先坏;多图、视频再多一层,ViT 的激活在 prefill 阶段把余量吃光,直接 OOM。

## 二、解法:把这张图压成一个数

最天然的直觉是「图片先过 ViT 变成 embedding,塞进文本 embedding 的对应位置,后面的 prefill 和 decode 不用知道有过图」。SGLang 就是这么做的。这条路上真正值得看的是它多做的一件事:**给每张图的特征算一个数,再让这个数同时当两把钥匙**——编码器的输出存在哪一格,以及这张图在前缀树里长什么样。于是「这张图算过没有」和「这段前缀见过没有」变成同一个问题,而不是两个各查各的问题。

![一张图从主进程走到语言模型的那条路,以及中间那个数怎么被两处共用:上半是主进程,横排三步——4 个 IO 线程下载与解码、隔离线程里缩放归一化切 patch、把每张图展开成一段占位 token;特征张量随后送到调度器进程,先被压成一个哈希;下半是调度器进程,从这个哈希出去两条箭头,左边一条把占位 token 改写成这个数交给前缀树按内容匹配,右边一条拿它查 GPU 上的编码器输出缓存,命中就不跑 ViT、没命中的图全批去重后合成一次 ViT 再把结果按图切开写回缓存;最后 embedding 散回占位位置,语言模型只看见一串普通 token](/opensource/sglang/14a-one-image-one-number.svg)

一条请求的路径:

- 主进程收到请求,4 个 IO 线程并行下载和解码媒体(JPEG 默认由 nvJPEG 在 GPU 上解,失败退回 CPU);处理器在 1–2 个隔离线程里跑,每个线程持一份处理器的深拷贝;产出特征张量,以及把每张图展开成一段占位 token。
- 特征送到调度器。调度器给每个特征算一个哈希(CPU 上取 sha256 的前 8 字节,张量已经在 GPU 上时用 GPU 核算),占位 token 全部改写成 1000000 加这个哈希对 2 的 30 次方取模,于是前缀树看到的是「这张图的内容」而不是「这里有一张图」(04 章)。
- prefill 那一步,模型运行器拿同一个哈希查 GPU 上的编码器输出缓存:命中直接取,ViT 不跑;没命中的,把这一批所有请求的所有图按哈希去重后合成 1 次 ViT 调用,结果按图切开写回缓存。然后把 embedding 散到占位位置上,语言模型照常前向。
- 开了分块预填充时,第一个碰到这张图的块整图编码、整份进缓存,后面每块只按位置切一段;编码完特征挪回 CPU,缓存里那份被挤掉时还能重算。

为什么实际不吃亏:ViT 只有语言模型 1–5% 的参数,一张图 20–100 毫秒,和同样 1300 个 token 的 prefill 是一个量级;真正省下来的是重复。多轮对话里同一张图从第 2 轮起既不跑 ViT 也不跑 prefill,而这两处能一起省,正是因为它们查的是同一个数。

## 三、代价

- **预处理会碰服务卡。** 默认的快速图像处理器在主进程里用服务的那张卡做缩放和归一化,正是调度器在跑 decode 的那张卡;所以这条路径上处理线程被自动钉在 1 个,多开反而更慢。
- **显存先扣一块。** 编码器输出缓存默认 100 MiB,选了 GPU 传输特征时再加 1 GiB 的池;这两块在 KV 池定大小之前就从预算里扣掉(03 章)。
- **哈希是 CPU 的活。** 一张 1300 token 的图特征 10–25 MB,取 sha256 要 15–50 毫秒,而且在调度器进程里算;有个开关能预分配一块显存把它挪到 GPU 上,默认不开。
- **分块预填充管不住 ViT。** 整图在第一个块就编完,激活峰值由这个块里所有请求的所有图决定,分块只切语言模型那一半。
- **特征来回搬 3 次。** 主进程到调度器 1 次,调度器再上 GPU 1 次,编码完回 CPU 1 次。
- **占位 token 烧 KV。** 一张满分辨率的图 16384 个格子,唯一的刹车是给处理器压一个像素上限。
- **看不见。** 主服务器的指标接口里一个多模态项都没有,那一组编码器指标只在拆出去的编码器服务器上有(11 章)。
- **功能表打折。** 6 个架构一开多模态就自动关掉分块预填充;多模态模型的 prefill 默认不进分段图,两张回补白名单一张 3 个架构、一张 9 个(07 章);另有 4 个架构默认根本不开多模态,发图也当没看见。

## 四、和 vLLM 不一样的八处

![vLLM 和 SGLang 在多模态这条路上都躲不掉的六件事,每一行是一件事,左右两块是各自的答法:第一行是预处理的结果记不记,第二行是编码器的输出按什么键记,第三行是前缀缓存怎么认出这是哪张图,第四行是一步里最多编多少,第五行是分块预填充碰到一张图怎么切,第六行是怎么才能干脆不加载编码器;右侧第二、三行外面套着一道括号,标出这两行在 SGLang 这边用的是同一个键,而 vLLM 那两行用的是两个不同的键;第四行右侧是白底虚线,表示 SGLang 根本没有这一层](/opensource/sglang/14b-vllm-diff-six-rows.svg)

1. **预处理在哪个进程、开多少线程。** vLLM 在对外那个进程做,媒体加载线程池 8,预处理工作进程死死压在 2 以内,处理器缓存 4 GiB 默认开着,而且是对外进程与引擎进程一对互为镜像的缓存。SGLang 在主进程做,IO 线程默认 4(Qwen-VL、Kimi、PaddleOCR 这几系是 16),处理线程 1–2 自动定;预处理缓存默认关,只有 Kimi-K3 默认给 256 MiB,而且这份缓存只活在主进程里,不跨进程镜像,多开几个主进程时预算还要按进程数均分。
2. **两级缓存的键是不是同一个。** vLLM 三级三个键:预处理器缓存用媒体内容哈希,编码器缓存用内容标识(挂了适配器还要带前缀),前缀缓存把媒体身份加起始偏移混进块哈希。SGLang 是两级,而且后一级和前缀树共用一个键——编码器输出按特征张量的哈希存、按字节做最近最少使用淘汰,前缀树里的占位 token 就是这个哈希。
3. **有没有编码器预算。** vLLM 每步一道闸,算力预算或缓存容量不够就给这条请求 0 个 token,等下一步。SGLang 没有这道闸,prefill 批里有多少图就编多少,全树没有这个概念;能限的只有每请求的媒体数量和每张图的像素。
4. **分块怎么切图。** vLLM 默认切开占位区,每块只编本块那一部分,也可以要求不许切开。SGLang 是第一个碰到图的块整图编码,后面按位置切 embedding;另有 6 个架构直接自动关掉分块。
5. **怎么才能不加载编码器。** vLLM 把某个模态的数量上限设成 0,该模态的编码器模块就不加载,而预计算的 embedding 仍然能当输入喂进来。SGLang 的数量上限只拒请求、权重照加载;要真的不建塔得用一个独立模式,它压根不建视觉塔、连那部分权重文件都不读,省下的显存全归 KV,多模态请求一律拒——代价是只认 3 个架构,而且和 PD 分离互斥。
6. **编码器并行的形态。** 两边都要模型自己声明支持,也都是把塔复制到每个 rank 上、按数据分片。SGLang 这边是一个开关,图片按像素量均衡分到各 rank、算完 all-gather,15 个模型文件接了它;并行度不由你定,直接等于张量并行度,所以单卡时打开只会换来一句警告。
7. **视频剪枝。** vLLM 是请求级的剪枝率,模型要实现位置重算,视频路径的塔自动退出图捕获。SGLang 的剪枝率写在模型配置里,首帧全保留、后续帧按与前帧的相似度丢 token;只有 Nemotron 这一个模型家族接了它,而且它自己的说明里明写着和 Qwen2.5-VL 这类靠位置编码的模型不兼容。
8. **直传与自带哈希。** vLLM 直传 embedding 要显式开启,注释里写明只对可信调用方。SGLang 的原始媒体、处理器输出、预计算 embedding 这 3 种格式默认都收,没有开关;调用方还能自己把哈希带进来,让外部路由器的决策和前缀树的键对齐——信不信这个哈希倒是有个开关。

## 五、调参与观测

**参数在哪调。** 启动参数一组 `--mm-*`,加上 `--enable-multimodal`、`--language-model-only`、`--limit-mm-data-per-request`、`--image-processor-backend`,改了要重启;环境变量 `SGLANG_VLM_CACHE_SIZE_MB`、`SGLANG_VIT_ENABLE_CUDA_GRAPH`、`SGLANG_IMAGE_MAX_PIXELS`、`SGLANG_MM_BUFFER_SIZE_MB`,以及没有前缀的 `REQUEST_TIMEOUT`;模型配置里的 `video_pruning_rate` 用 `--json-model-override-args` 改;请求侧 OpenAI 接口收 `image_url`、`video_url`、`audio_url`、`input_audio`,原生接口收 `image_data`、`video_data`、`audio_data`(实例、文件路径、URL、base64 都行,一个请求给列表,批请求给列表的列表),外加 `mm_hashes` 与 `content_hash`。运行时接口只有 `/flush_cache`,它顺手清空预处理缓存;没有任何多模态参数能在线改。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--enable-multimodal` · 开多模态 | 启动 | 多模态架构自动开;Gemma3、Llama4、Step3-VL、Inkling 这 4 个默认关 | 关着时图片字段被忽略,当纯文本模型跑;没有反向的关闭开关 | 启动日志 `Multimodal is disabled for … set --enable-multimodal` |
| `--language-model-only` · 完全不加载编码器 | 启动 | 关 | 开:视觉塔不建、权重不读,省下的显存归 KV;多模态请求直接 400,`/model_info` 报 `has_image_understanding: false`;只支持 MuseGlimmer、Cosmos3、Cosmos3-Edge 三个架构,且不能和 PD 分离、EPD 三件套、编码器 DP 同开 | `/model_info` 那一项;起服务时架构不在白名单会直接报错退出 |

| `SGLANG_MM_BUFFER_SIZE_MB` · 算哈希时借的 GPU 缓冲 | 环境变量 | 0 | 调 256–1024:特征哈希从 CPU 的 sha256 换成 GPU 核,单图省 15–50 毫秒;放不下的张量退回 CPU | 日志 `Preallocated NMB GPU buffer` |
| `REQUEST_TIMEOUT` · 拉远端媒体的秒数 | 环境变量 | 图 3、音频 5、视频 10 | 内网慢时调高;最多跟 5 次重定向 | 错误 `Error while loading data` |
| `video_pruning_rate` · 视频剪枝率 | 模型配置 | 0 = 关 | 0.7 保留 30% 的视频 token,官方例子 TTFT 11.96 → 8.79 秒;0.9 时 Video-MME 从 0.665 掉到 0.644;只有接了剪枝的模型认 | 日志里的剪枝启用行 |

**怎么看。** 没有专门的指标,只能靠三处。一是启动日志:注意力后端那行、`Reserving … multimodal` 那行、处理器并发那行、`Automatically turn off --chunked-prefill-size as it is not supported for …` 那行。二是运行时两条警告,`Discarding cached multimodal embedding due to a token-count mismatch` 是缓存里那份的 token 数和这次要的对不上(丢弃重算),`Number of tokens in multimodal embedding does not match those in the input text` 是 embedding 比占位区长,它会从尾部截断,分块开着时还补一句让你调大分块。三是剖析:`/start_profile` 出来的 trace 里 `sglang.vlm.mm_embedding` 是 ViT 加散布、`sglang.vlm.language_model_prefill` 是语言模型,两段的比值就是「编码器占了这次 prefill 多少」。请求级看 `meta_info` 里的 `cached_tokens`,它把占位 token 也算在内,图命中前缀树时会一次跳 1300 以上。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| 图基本不重复:批量文档识别、OCR 流水线 | `--image-processor-backend pil`,再 `SGLANG_VLM_CACHE_SIZE_MB=0` | 用「预处理彻底离开服务卡」换掉预处理和 decode 抢卡,而且换路之后自动线程数本来就会从 1 变成 2,不用手设;图不重复时编码器输出缓存只是白占 100 MiB,关掉还给 KV。代价是单张图的预处理时延涨 2–5 倍 |
| 多轮对话,同一张图反复发 | `--mm-preprocess-cache-size-mb 512`,再 `SGLANG_VLM_CACHE_SIZE_MB=1000` 与 `SGLANG_MM_BUFFER_SIZE_MB=512` | 用 512 MiB 主机内存和 1 GB 显存换掉重复图的解码、缩放与 ViT,顺带把哈希挪到 GPU 上算。代价是 KV 预算少 1 GB,而且这套在 Qwen3-VL 的大 Hopper 卡上必须显式设,否则模型侧会把缓存改成 0 |
| 高分辨率多图,TTFT 卡在 ViT 上 | `--mm-enable-dp-encoder`,再 `SGLANG_VIT_ENABLE_CUDA_GRAPH=1` 与 `--mm-process-config '{"image": {"max_pixels": 1048576}}'` | 用每个 rank 各存一份塔权重换 ViT 的并行度,用录图换掉小批的下发开销,用像素上限直接砍每图 token 数。代价是显存多占一份塔、分辨率杂时图的份数多,以及小字识别变差;再不够就把编码器整个拆出去(11 章) |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 图多时 TTFT 高、GPU 利用率低 | 主进程的 CPU 是否打满;处理线程是不是被钉成了 1 | 换 `--image-processor-backend pil`,自动线程数会跟着变成 2;加 `--tokenizer-worker-num`;远端 URL 多就加 IO 线程 |
| 图多时 decode 的 TPOT 尾巴变差 | ViT 是否在服务卡上和 decode 同批;图像处理器是不是也在这张卡上 | 开 ViT 的图;`--mm-enable-dp-encoder`;根治走 EPD(11 章) |
| 同一张图反复发还是慢 | `SGLANG_VLM_CACHE_SIZE_MB` 是否被模型覆盖成 0;`SGLANG_MM_SKIP_COMPUTE_HASH` 是否开着 | 显式设回 100–1000;关掉跳过哈希那个开关 |
| 多图请求 prefill 阶段 OOM | 每图多少 token;这个架构的分块是不是被自动关了 | `--mm-process-config` 降 `image.max_pixels` 和 `video.max_frames`;分块对那 6 个架构无效,只能限图 |
| 警告 `token-count mismatch` | 处理参数改过没有;是不是两张图的哈希撞了 | 偶发可忽略;频繁就开 `SGLANG_MM_PRECOMPUTE_HASH`,看哈希在传输前后是否一致 |
| 警告 `does not match those in the input text` | `--chunked-prefill-size` 是不是小于单图的 token 数 | 调高分块或关掉分块 |
| KV 比预期少 100 MiB 到 1 GiB | 启动日志 `Reserving … multimodal` 那行 | 正常;不想要就 `SGLANG_VLM_CACHE_SIZE_MB=0` 且不选 `cuda_ipc` |
| 远端图片报 `Error while loading data` | 域名白名单、64 MiB 上限、3 秒超时、5 次重定向 | 调 `REQUEST_TIMEOUT`;白名单加域名;换 base64 直传 |
| Gemma3、Llama4 发图没反应 | 这 4 个架构默认关多模态 | 加 `--enable-multimodal` |
| 请求报 `exceeds limit` | `--limit-mm-data-per-request` | 调高,或让客户端拆请求 |
| 起服务就报 `--language-model-only does not support …` | 这个模式只认 3 个架构 | 换模型,或不用这个模式;想省编码器显存的其他模型只能走 EPD(11 章) |

## 六、常见误区

- **「预处理在 CPU 上,和 GPU 无关」。** 因为 HF 处理器是个 CPU 库。实际默认的快速图像处理器在主进程里用服务的那张卡做缩放归一化,和调度器抢同一张卡;自动线程数在这条路上被钉成 1 就是因为这个。要真的不碰卡,`--image-processor-backend pil`。
- **「`--mm-processor-worker-num` 越大越快」。** 因为它叫 worker。官方在 GB300 上测过,GPU 路径开 2 个线程吞吐从 9.30 掉到 4.02 req/s;只有 `pil` 路径的第 2 个线程是真并行,而且这时自动值本来就是 2,不用手设。
- **「编码器输出缓存是显存大头,先调它」。** 因为它是唯一一个带 SIZE_MB 的多模态变量。默认才 100 MiB;真正吃显存的是占位 token 占的 KV 格子(一张满分辨率的图 16384 个)和 ViT 的激活,先动像素上限。
- **「开了分块预填充,一张图会拆成多块编码」。** 因为语言模型是这样。整图在第一个碰到它的块里编完,分块只切 embedding;所以分块救不了 ViT 的 OOM,而且分块比单图 token 数还小时会出 `does not match` 警告叫你把它调大。
- **「`--limit-mm-data-per-request` 设 0 能省掉编码器权重」。** 从 vLLM 带来的习惯,那边设 0 确实会让编码器模块不加载。这里设了只拒请求,权重照加载;真要不加载得用 `--language-model-only`,而它只认 3 个架构。
- **「`--language-model-only` 是 EPD 的一部分」。** 因为它和 `--language-only` 只差一个词。`--language-only` 是 EPD 三件套里语言端那一件,编码器还在,只是在别的机器上(11 章);`--language-model-only` 是独立模式,根本没有编码器,而且和 PD 分离、EPD 三件套、编码器 DP 全都互斥,同开直接报错。
- **「缓存命中就等于 prefill 也省了」。** 因为两处都叫缓存。命中编码器输出缓存只跳过 ViT,1300 个占位 token 照样要过语言模型;只有前缀树也命中(要求图前面的文本也一样)才两头都省。反过来前缀树命中了 ViT 就一定不跑,因为占位区整个落在前缀里。
- **「Qwen3-VL 也有 100 MiB 的编码器输出缓存」。** 因为默认值写着 100。Qwen3-VL 在大 Hopper 卡上会被模型侧覆盖成 0(理由写在注释里:流式流量每张图只用一次),同一批覆盖还把预处理缓存也设成 0。重复图的流量要自己显式设回去。
- **「`cached_tokens` 只数文本」。** 因为图不是 token。占位 token 在树里就是普通 token,一张图命中就是 1300 以上的 `cached_tokens`;看到这个数突然跳高不是 bug。
- **「ViT 的 CUDA graph 设了就对所有模型生效」。** 因为是个全局环境变量。只有 4 系模型接了运行器,其他模型读了这个变量什么都不做,也不打日志(07 章)。
- **「多模态有 `/metrics` 指标」。** 因为 EPD 文档里有 `sglang:encoder_*` 那一组。那组只在编码器服务器上,单机主服务器一个多模态指标都没有,只能看日志和 profile。
- **「`REQUEST_TIMEOUT` 是 SGLang 的变量」。** 它没有 `SGLANG_` 前缀,在 `/server_info` 里也看不到;图片默认才 3 秒,对象存储慢一点就报加载失败,第一反应往往是去查网络而不是这个变量。
