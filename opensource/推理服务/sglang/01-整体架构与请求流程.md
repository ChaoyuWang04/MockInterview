# SGLang 01|整体架构与请求流程

为什么推理服务要拆进程、一个 step 里 CPU 和 GPU 都不该等对方、ZMQ 为什么合适,vLLM 解读的「整体架构与请求流程」一章已经讲透。这一页只说 SGLang 把一条请求拆到哪几个进程、每一站在哪、以及它和 vLLM 行为上不一样的地方。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

切词、调度、前向、反切词、HTTP 全挤在一个 Python 进程里,坏的是**每个 token 的时间**。Python 一次只让一个线程真正在跑,GPU 算完一步要等 CPU 发下一步,可这段空档里 CPU 还得给新请求切词、给老请求把 token 变回文字、给 HTTP 写响应。并发上到 100 条,一步 10–50 毫秒的 decode 里光 CPU 的活儿就能占掉一半,吞吐掉下来、字与字之间的间隔开始抖;再来一条 100k token 的长 prompt,光切词就 100–500 毫秒,这段时间所有在跑的请求一起停。

## 二、解法:三个工位三个进程

最天然的直觉:切词、算、反切词是三道工序,各占一个进程,中间用管子连起来,谁也不等谁。SGLang 就是这么做的——三个进程,以及一条流式请求走过的 7 站:

![SGLang 的三个进程与一条流式请求走过的 7 站:主进程里依次是 HTTP 路由、协议转换、TokenizerManager 与输出回写四站,Scheduler 子进程里调度与 GPU 前向采样在同一个进程且自己拿一份分词器判停止串,Detokenizer 子进程做增量反切词再把文字送回主进程写 SSE,三个进程之间走 ZMQ 的 Unix 域套接字,开数据并行时旁边多一个 DataParallelController](/opensource/sglang/01a-process-topology.svg)

管子是单向的,走本机文件系统上的套接字,不过网络。消息默认用 Python 自带的那套打包方式;有个开关能换成更紧凑的二进制格式,但换了之后多模态输入这类字段还是得用老办法包一层再塞进去,所以默认没开。

为什么这么拆实际不吃亏:每步要传的东西很小——这一批请求各自新出的那个 token 编号,加几张等长的列表,打包 10–100 微秒,过一趟管子 20–50 微秒;而 GPU 那边一步就是 10–50 毫秒,差了两三个数量级,拆进程的开销淹没在里面。反切词值得单独占一个进程,是因为每出一个 token 就要给**所有**在跑的请求各做一次,并发 1000 时这是一个整核的活:放主进程会挤掉 HTTP,放调度器会推迟下一步。

反切词这件事本身还有个麻烦:一个汉字通常要两三个 token 才凑得齐,光看新来的这一个 token 根本译不出字来。所以它的做法是每次把「上次停下的位置往前挪几个 token,再加上新 token」整段译一遍,然后减掉「上次停下的位置往前挪几个 token」单独译出来的那一段,差额才是这一步真正新增的文字。要是译出来结尾是个乱码方块,说明最后那个 token 只凑了半个字,就先把能确定的部分发出去,剩下的下一步带着更多 token 再试。

## 三、代价

**分词器要装 3 份。** 主进程一份用来切词,反切词进程一份用来还原,调度器还得有一份——因为停止串是它自己判的。每份 100–500 MB 内存,启动时各加载一次。

**请求要过 3 个进程、打包拆包 4 次**,单条请求因此多 0.1–0.5 毫秒。

**切词仍然堵事件循环。** 它是在主进程的事件循环上同步做的,没有线程池。一条超长 prompt 切 100–500 毫秒,这段时间同一个进程里所有 HTTP 处理和流式发送一起停。有个开关能把它挪到单独的执行器里攒批,但那也还是一个线程,只是不再堵住事件循环本身。

**空载也烧 CPU。** 调度器和数据并行的分发进程都是单线程忙轮询,不主动睡觉,所以没有请求的时候 CPU 也是满的,除非显式让它去等在管子上。

**反切词进程记不住太多请求。** 它最多同时跟踪 65536 条,超了最老的那条被挤掉,而那条请求下一次出 token 时就直接报错。并发真能上到这个量级的部署要当心。

## 四、和 vLLM 不一样的十处

![同一条流水线上的 5 件事在 vLLM 和 SGLang 各由哪个进程包办:每一行是一件必须有人做的事,上下贯穿两边,一个方框纵向盖住几行就表示这个进程包办了这几件事;vLLM 的 API 进程一口气盖住收 HTTP 切词、把 token 变回文字、判停止串三行,SGLang 则是主进程只盖第一行、反切词单独一个进程、调度器一口气盖住判停止串与调度与 GPU 前向三行](/opensource/sglang/01b-vllm-diff-process-map.svg)

上图里左边带红杠的三行,就是下面的前 3 处。

1. **反切词在哪做。** vLLM 在对外那个进程里顺手做了;SGLang 单独给它一个进程。多一个进程、多一趟消息,换来主进程只管收请求和切词。
2. **停止串在哪判。** vLLM 只能在对外进程判——文字是在那里还原的——判到了再反向发一条消息回去叫停;SGLang 让调度器自己留一份分词器,每步把输出的尾巴译出来自己判,判到直接结束,不需要反向通路。代价是流式输出时,尾巴上那几个字如果看着像停止串的开头,就得先扣着不发,等下一步确认不是才补上。
3. **调度和 GPU 隔不隔一层。** vLLM 的调度进程和执行进程是分开的,中间隔一层共享内存调用;SGLang 把两件事合进同一个进程,一个 rank 一个。省下那一跳,代价是收请求的那个 rank 每一步都得把这批广播给其他 rank。
4. **线程模型。** vLLM 的调度进程有收、主、发 3 个线程;SGLang 的调度器每轮开头把管子一次拉空,拉完就干活,从头到尾单线程。
5. **进程之间怎么打包。** vLLM 用紧凑的二进制格式;SGLang 默认用 Python 自带的那套,二进制格式是要手动打开的可选项。
6. **流式怎么吐字。** vLLM 每条请求只留一个待取的块,新内容就地并进去;SGLang 每条请求挂一张列表,唤醒时整张端走。两个默认值容易踩:一是每块带的是从开头到现在的全文而不是这一步新增的几个字,长回答的流式开销因此是平方级的,要增量得自己打开;二是唤醒不是每出一个 token 就做,而是攒够 16 条请求批量做一次。
7. **多开几个对外进程。** 两边都支持,参数名不同(见第五节)。SGLang 多开之后每个进程各带一套分词器和请求状态,鉴权中间件也就不装了,要鉴权得在前面另加一层。
8. **离线用法。** SGLang 的离线引擎起的是同一套子进程,只是不起 HTTP 服务器,改用自己的循环同步驱动。没有 vLLM 那种把一切塞回单进程、方便打断点的调试模式,调度器永远是子进程。
9. **对外说几种话。** 原生接口和 OpenAI 接口两边都有,SGLang 还多一套 Anthropic 接口:把请求翻译成 OpenAI 的样子走同一条内部流程,再把返回的流重新包成 Anthropic 的事件序列,而且始终开着,不用任何开关。把思考段切出来、把工具调用从文本里认出来,这两件事都在主进程做,在文字还原回来之后、写给客户端之前;各有一大堆按模型分的格式,工具调用 40 种、思考段 32 种,也可以让它启动时读一遍聊天模板自己猜是哪种。
10. **HTTP 这一层可以整个换成 Rust。** 打开之后,收请求、切词、反切词都不在 Python 里做了,由一个嵌在调度器进程里的 Rust 扩展接管,调度器直接从进程内的缓冲区拿请求,连管子都省了。它只服务原生接口和 OpenAI 的几条路由,没有 Anthropic。值得换的场景很具体:GPU 还没跑满而主进程 CPU 先满——高并发的短请求、每个 token 都要推给客户端、块特别碎;GPU 已经是瓶颈时换了没用。别把它和那个跨实例的路由网关搞混,后者是独立进程、在多台机器之间选路,见 18 章。另外还有一层前端语言,是个 Python 写法,把多轮生成和分支编译成对后端的多次调用,和进程模型无关。

## 五、调参与观测

**参数在哪调。** 这一章的参数全是启动参数和环境变量,改了要重启;运行时只有 `/abort_request`、`/pause_generation` 与 `/continue_generation` 三个入口,`/set_internal_state` 改不了流式间隔和切词相关的任何项。请求级只有 `sampling_params.stream_interval` 一项能覆盖启动值。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--tokenizer-worker-num` · 起几个 HTTP 加切词进程 | 启动 | 1 | 调高:HTTP 和切词的 CPU 分到多核,高 QPS 下 TTFT 降;每个进程各一份分词器,多一跳路由;`--api-key` 失效 | `ps` 里 `sglang::tokenizer_worker:` 进程数 |
| `--detokenizer-worker-num` · 起几个反切词进程 | 启动 | 1 | 调高:并发 1000 以上时反切词不再是单核瓶颈,TPOT 抖动降;请求按 HTTP 工作进程哈希钉死到某个反切词 | `ps` 里 `detokenizer_` 进程数 |
| `--enable-dynamic-batch-tokenizer` · 把单条文本的切词攒批放到单线程执行器 | 启动 | 关 | 开:并发到达的短 prompt 攒 32 条或 2 毫秒一起切,事件循环不被单次切词卡住;单请求多 2 毫秒 | 日志 `Using async dynamic batch tokenizer` |
| `--enable-tokenizer-batch-encode` · 批请求一次切完 | 启动 | 关 | 开:一个请求带多条文本时一次调分词器;带图或 `input_ids` 时不能开 | — |
| `--tokenizer-backend` · 用哪个分词器库 | 启动 | `huggingface` | `fastokens`:切词更快;3 份分词器一起换 | `/get_server_info` |
| `--skip-tokenizer-init` · 不加载分词器,只收 `input_ids` | 启动 | 关 | 开:调度器直接把 token id 发回主进程,反切词进程空转;RL 自己切词时用 | 响应里没有 `text` 只有 `output_ids` |

| `--incremental-streaming-output` · 每块只带增量文字 | 启动 | 关 | 开:块里 `text` 是增量不是累计;长回答的流式 CPU 从平方降到线性 | 块里 `text` 是否越来越长 |

| `--max-queued-requests` · 等待队列上限 | 启动 | 不限 | 设了:队列满时新请求立刻被拒;PD 分离下忽略 | 错误 `The request queue is full.` |

| `--tool-call-parser` / `--reasoning-parser` · 用哪套格式切工具调用与思考段 | 启动 | 不切;`auto` 按模板猜 | 设错:工具调用原样当正文吐出;`auto` 猜不到就等于没设 | `/get_server_info` 里两项的实际值 |
| `--sleep-on-idle` · 空载时等在套接字上 | 启动 | 关 | 开:空载 CPU 从 100% 降到接近 0;来第一条请求多 20–50 微秒 | `top` 看调度器进程 |

| `SGLANG_HEALTH_CHECK_TIMEOUT` · `/health` 最多等几秒 | 环境变量 | 20 | 调低:探针更快判死,但模型加载完前的抖动更容易误判 | 日志 `Health check failed.` |
| `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION` · `/health` 要不要真生成一个 token | 环境变量 | 1 | 设 0:`/health` 变静态 200,`/health_generate` 仍真生成 | — |
| `SGLANG_DETOKENIZER_MAX_STATES` · 反切词进程最多记多少请求 | 环境变量 | 65536 | 调高:并发超 65536 时不再踢最老的状态 | 错误 `Decode status not found for request` |
| `SGLANG_RUST_SERVER` · 用 Rust 前端 | 环境变量 | 0 | 设 1:不起 Python 的 HTTP、切词、反切词;没有 `/v1/messages`;`--tokenizer-worker-num` 无意义 | `ps` 里没有 `sglang::detokenizer` |
| `SGLANG_TIMEOUT_KEEP_ALIVE` · HTTP 长连接空闲几秒断 | 环境变量 | 5 | 调高:客户端连接池复用率高;空闲连接占句柄 | — |

**怎么看。** 这一章看 3 处。一是进程:`ps` 里应有主进程、`sglang::scheduler…` 每 rank 一个、`sglang::detokenizer` 一个,开 DP 多一个 `sglang::data_parallel_controller`;任一子进程死了主进程会收到 SIGQUIT 跟着退。二是启动那行 `Engine startup timings (s): load_weight=… kv_cache_allocation=… scheduler_e2e=… cuda_graph={…} tokenizer_e2e=…`,`tokenizer_e2e` 减 `scheduler_e2e` 就是主进程自己花的时间;之后 `The server is fired up and ready to roll!` 才是预热完成。三是 3 个接口:`/ready` 只看主进程状态,不碰调度器;`/health` 真发一条 1 token 的生成,调度器忙时直接丢掉这条(有输出在流就算活),20 秒内收不到反切词进程任何消息才 503;`/v1/loads` 读共享内存里各调度器每 5 轮写一次的快照(不变时 1 秒一次),不往调度器发消息,`/get_load` 是它的旧壳,每调一次打一行弃用警告。请求级看 `meta_info` 里的 `e2e_latency`、`prompt_tokens`、`completion_tokens`,日志看 `Received output for rid=… but the state was deleted`(健康检查或中止后的正常尾巴)与 `Abort queued request.`。

| 症状 | 先查 | 然后 |
|---|---|---|
| `/health` 503,GPU 利用率正常 | 日志 `Health check failed. Server couldn't get a response from detokenizer` | 看反切词进程在不在;看有没有 `Decode status not found` |
| TTFT 高,`gen throughput` 正常,主进程 CPU 100% | 主进程在切词或写 SSE | 加 `--tokenizer-worker-num`;短请求多就开动态攒批切词;再不够换 Rust 前端 |
| 流式块忽大忽小 | 请求里 `stream_interval`;尾巴是否疑似停止串前缀 | 停止串越长扣得越久;去掉不必要的 `stop` |
| 报 `Decode status not found for request` | 并发是否超 65536 | 调 `SGLANG_DETOKENIZER_MAX_STATES` |
| DP 某个副本一直热 | `--load-balance-method` 是不是轮询 | 换 `total_requests`;`total_tokens` 要 DP attention |
| `--api-key` 不生效 | `--tokenizer-worker-num` 是否大于 1 | 只在单工作进程模式生效;多进程时在前面加网关 |
| 客户端断了请求还在跑 | 非流式每 4 秒查一次,流式结束后 2 秒才发中止 | 调 `SGLANG_REQUEST_STATE_WAIT_TIMEOUT`;或客户端自己调 `/abort_request` |
| 工具调用当正文吐出来 | `/get_server_info` 里 `tool_call_parser` 是不是空 | 显式指定名字,`auto` 猜不到就等于没设 |
| 空载 CPU 100% | 调度器和 DP 控制器忙轮询 | `--sleep-on-idle`;DP 控制器没有对应开关 |
| 请求被拒 `The request queue is full.` | `--max-queued-requests` | 调高或在前面限流 |
| 用 msgpack 启动就 TypeError | 某个字段不是 msgspec 类型 | 改回 pickle,或给字段包 PickleWrapper |

## 六、常见误区

- **以为切词在子进程或线程池里。** 因为反切词是子进程,想当然切词也是。切词就在主进程的事件循环线程里同步做,一条 100k token 的 prompt 切 100–500 毫秒,这段时间同一进程里所有 HTTP 处理和流式发送一起停。动态攒批只是挪到一个单线程执行器,`--tokenizer-worker-num` 才是真的多核。
- **以为 `/health` 是静态探针。** 它真发一条 1 token 的生成,最多等 20 秒。忙的时候调度器把这条直接丢掉、有任何输出就算通过,所以不会给 GPU 加活;但模型还在加载时它是 503,探针的初始延迟要留够。
- **以为调大 `stream_interval` 能减轻 GPU。** GPU 每步照旧,它减的是消息数和反切词、HTTP 的 CPU。GPU 是瓶颈时调它没用。
- **以为 SGLang 进程间用 msgpack。** 默认 pickle,msgpack 是环境变量打开的可选项,而且打开后多模态输入这类字段还是包一层 pickle。
- **以为 DP 控制器按负载分。** 默认轮询,只跳过挂了的副本。选 `total_requests` 也只是每 20 毫秒读一次快照,中间靠「发一条加一」猜;快照本身每 5 轮才写一次。
- **以为工具调用和思考段是在调度器或反切词进程切的。** 都在主进程,文字回来之后、写 SSE 之前,按每段增量切。反切词进程只认得 gpt-oss 的一个停止 token 不去掉,别的一概不知道。
- **以为加了 `--tokenizer-worker-num` 就完事。** 每个工作进程各一份分词器、各自一套请求状态,`--api-key` 中间件不装,`/pause_generation` 要经路由广播到每个工作进程。
- **以为客户端断开请求立刻停。** 非流式是每 4 秒查一次连接,流式是响应结束后 2 秒才补一条中止;这之间 GPU 照算。
- **以为 Rust 前端就是 sgl-model-gateway。** 网关是独立进程,在多个实例之间路由;Rust 前端是嵌在 rank 0 调度器进程里的扩展,替换单实例的 HTTP、切词、反切词三站,两者可以叠着用。
- **以为 `/get_load` 会去问调度器。** 读的是共享内存里的快照,最多滞后 5 轮或 1 秒;它已弃用,每调一次打一行警告,新代码用 `/v1/loads`。
- **以为停止串是在反切词那边判的。** 调度器进程自己有一份分词器,每步 decode 输出尾巴判停止串;反切词进程只负责把匹配到的那一段从文字里裁掉。
