# SGLang 16|模型加载与权重缓存

磁盘上的 checkpoint 和 kernel 要的张量为什么对不上、改名融合切分这三件事怎么处理、注册表为什么要惰性、加载慢该归因到哪一段,vLLM 解读的「模型生态与权重加载」一章已经讲透,那套三级映射 SGLang 是照搬的。这一页只讲 SGLang 自己那条线:同一份权重此刻可能已经在别处热着,别再冷读一遍盘。RL 训练里的权重同步与显存让出在 17 章,量化方法本身在 12 章。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

坏掉的指标是**启动时间**,官方文档给这件事的量级是分钟级。权重文件本身就是 10–1000 GB,而从文件到「显存里一份能算的张量」中间是一条五段的流水线:读盘、进主机内存、按并行度切片、做量化后处理、落进显存。五段里最贵的是第一段,而它偏偏最容易被重复付。

有 3 种部署会把这笔钱翻倍:

- **一台机器 8 个 rank 读同一份文件。** 每个 rank 各自 mmap 同一批分片,网络文件系统上总流量就是 8 份 checkpoint。
- **同一张卡上跑 2 个引擎进程**(比如训练侧和推理侧各起一个)。权重在显存里放 2 份,大模型直接 OOM。
- **换一次权重要重启。** 重启不只是重读一遍盘,还要重新探测显存、重建 KV 池、重抓图,分钟级的事情整个重来。

## 二、解法:按距离借一份热的

最天然的直觉是「谁先读到就分给别人」。SGLang 把「别人」按距离由近到远排成 3 层,离得越近能省掉的流水线段数越多:

![同一份权重进到显存里,五条来路各自真正付出了多少:横向是从盘到显存的五段流水线(读盘、进主机内存、按并行度切片、量化后处理、落进显存),纵向是五条来路。绿格表示这一段由本引擎进程自己从头做,黄格表示只做其中一部分或由邻居分摊,灰格表示本进程这一段完全不做。冷读盘五格全绿;开预取时读盘那一格变黄,因为同机每个 rank 只预热其中一份;第二次读预分片时切片与量化后处理两格转灰;走守护进程时前四格全灰,引擎只做最后一格的指针映射;跨机直传时读盘与主机内存两格根本不存在,切片与量化由种子实例做过](/opensource/sglang/16a-five-roads-to-vram.svg)

- **同一台机器的多个 rank** 共用操作系统的页缓存。开了预取之后,每个 rank 只负责预热全部分片里的一份,后台线程顺序读;读盘总量从 N 份降到 1 份,后面的按需读全在内存里命中。分摊按**节点内的**序号算而不是全局序号,因为页缓存只在一台机器内共享。预取不等读完就让加载开始,预热线程在前面跑,加载在后面追。
- **同一张卡的多个进程** 共用一个常驻的权重守护进程。守护进程把五段流水线整条走完,再把每个张量导出成一个可以跨进程映射的显存句柄;引擎则在一个假设备上把模型建成空壳,逐个参数把存储替换成守护进程那一份,零拷贝。守护进程独立启动时活得比引擎久,引擎重启就只剩一次句柄交换。
- **另一台机器上的新实例** 走 R-Fork:不读盘,从一个正在跑的实例经 GPU 网络 rank 对 rank 直传,每一对 rank 各建一个只有两个成员的通信组。

另外两条路省的不是读盘,是省重复劳动:**第一次正常加载并量化之后把结果按当前并行配置落盘**,第二次配置对得上就直接读,连重新量化都跳过;以及**把读文件塞进抓图的那段时间**,抓完再把真权重提交进去。

实际不吃亏的原因很直接:页缓存是操作系统白送的;跨进程映射不多占一个字节显存;GPU 之间的网络比任何磁盘都快。

## 三、代价

这一整章的代价能收进一句话:**借来的东西一律不许改**,而且借的链条越短,禁令越硬。

**守护进程这条路只放行 2 种权重形态**:不量化,和分块 FP8。其他量化方法的收尾会改张量形状、或者在 Python 那一侧盖上一层元数据,跨进程映射过来会得到看着正常、算出来是错的数,所以它在碰守护进程之前就先硬报错,不管守护进程在不在。开了缓存之后,4 条在线换权重的通道全部拒绝,把权重备份到主机内存也被禁。

**指纹对不上不是退回读盘,是直接报错退出。** 指纹里除了模型路径、架构、各维并行度、量化配置和数据类型,还算进了 torch 版本和卡的算力——因为版本不同的两个进程可能走了不同的后处理分支,产出的权重能干净地映射过来却服务错数。只有一种情况允许退回读盘:守护进程的套接字文件根本不存在,而且引擎是以客户端身份起的;连接被拒、协议出错一律报错。

**守护进程一死,引擎手里的指针就悬空**,而且这些地址可能已经被录进 CUDA graph 了,没有任何原地补救的办法。引擎每 5 秒查一次守护进程还在不在,发现不在就打一行致命日志然后 SIGKILL 自己。另外,显存分配器要是开了可扩展段,分出来的内存根本导不出句柄,这种组合在碰设备之前就被拒掉。

**落盘的预分片要求并行配置和量化配置逐项一致**,目录还得放在所有 rank 都看得见的文件系统上。**R-Fork 要求种子实例和新实例的并行策略完全一样**,而且它只在启动那一刻拉一次,之后两边各走各的。

**注册表不惰性。** 每个调度器进程启动时把模型目录下 238 个文件逐个导入,这笔钱每次启动都付,和你要跑哪个模型无关。

## 四、和 vLLM 不一样的八处

![两边都要回答同一个问题:一个架构名字符串怎么变成一个 Python 类,而八处差异里只有这一处是形状上的分歧——「执行 .py 文件」这一步落在「用户给出架构名」这道竖线的哪一侧。上半的 vLLM 把它推到竖线右边:启动时一个文件都不导入,表里只存模块名加类名两个字符串,查表之后只导入命中的那一个;要类的性质时另起一个用完就扔的子进程导入一次,结果落磁盘缓存。下半的 SGLang 把它提到竖线左边:启动就把模型目录下 238 个文件逐个执行一遍,画成 238 个小格,其中 215 格是绿的、交出了入口类,23 格是灰的、白导一趟,合起来登记出 276 个架构名,于是竖线右边只剩一次几乎不花钱的查表。两边的参数名都在第五节](/opensource/sglang/16b-vllm-diff-import-side.svg)

1. **注册表是急切的。** vLLM 表里存的是字符串,元信息交给一个用完就扔的子进程去探,再按文件字节哈希落磁盘缓存,三样东西串起来就为了启动时不导入全部模型文件。SGLang 走了相反的路:模型目录下 238 个文件逐个导入,其中 215 个声明了入口类,登记出 276 个架构名;表里存的是类对象本身,没有子进程也没有磁盘缓存,只有一个进程内的函数级缓存。某个模型文件缺依赖时只打一行警告跳过,那个架构就成了「不支持」。外部模型包可以整包覆盖同名架构。
2. **落到哪个加载器,不是只看那个格式参数。** vLLM 是 15 个格式名落到 7 个类。SGLang 的枚举有 22 个值,命令行只开放 18 个,落到 15 个类另加 1 个从外部模块导入的私有插槽;有 3 个枚举值全树没有任何分支,命令行传不进去,从 Python 接口传进去会一路走到默认加载器才报错。更要紧的是**量化方法的优先级在格式参数之上**:有两类量化配置会把加载器整个换掉,格式参数写什么都不管用。量化检测本身在 12 章。
3. **网络盘上的预取要手动开。** vLLM 会自己判断文件系统类型和内存装不装得下,够就自动预取。SGLang 没有这个判定,必须显式开;开了之后它还会顺手把多线程读关掉,因为预取线程和读线程抢的是同一份 I/O——除非你在加载器的额外配置里显式写回来,那等于把带宽抢回去。
4. **预分片有两种,来路完全不同。** 一种是离线脚本产出的,每个 rank 读自己那份。另一种是第一次正常加载并量化之后自动落盘,目录名由并行配置和量化配置拼出来,里面放一个就绪标记文件;第二次配置对得上就直接读。模型目录只读时要另外指一个可写的根,否则第一次就落不下去。
5. **从正在跑的实例直接拿权重是内建能力,有 3 个后端。** 两个是自家的,一个走集合通信库,一个走传输引擎;第三个接外部的协调服务,不用配种子地址,没有可用的源就自己读盘并把自己登记成源。这条路参数不全时不报错,只打一行警告悄悄退回默认格式——**静默降级是这一章最容易忽略的行为**。
6. **同一张卡上的多个进程共用一份权重,但门槛立了三道。** 量化形态白名单、守护进程存活看门狗、以及把所有在线改权重的口子全部焊死。三道都不是可选项,少一道这条路就会在某个场景下静默服务错数。守护进程可以由引擎自己拉起,但那样它就是引擎的子进程,引擎退它也退,重启一点不快;要秒级重启必须独立启动它。
7. **热重载只有一条路,不分层。** 换个路径原地重读,只走默认加载器,失败了自动回滚重读原权重,默认顺手清前缀树,可以选择重抓图。vLLM 的分层热重载是为量化模型省显存,这边没有分层。除了权重缓存那道门,还有第二道和它无关的:某个融合矩阵乘优化会把权重的一份拆分结果缓存下来,原地写入对那份缓存不可见,所以它一开,全部在线换权重一律被拒。
8. **实现来源不是「原生或 Transformers」两选一,一共四档。** 自动、强制原生、强制包装 Transformers 库的实现(打一行警告说部分特性不支持、性能可能不是最优),再加上整条换到国产 NPU 的那套实现——由一个专门的入口类接管,它自己再去另一个包里查架构名。vLLM 解读里这一段只有原生与 Transformers 后备两条路。

## 五、调参与观测

**参数在哪调。** 启动参数决定走哪个加载器、怎么读盘、要不要接守护进程(`--load-format`、`--model-loader-extra-config` 传 JSON、`--weight-loader-*` 四个、`--weight-cache-*` 三个、`--remote-instance-weight-loader-*` 五个),改了要重启。环境变量(`SGLANG_` 前缀)管文件顺序、跳过哪些模型文件、预取块大小、守护进程的套接字与就绪文件路径,同样要重启。运行时只有两个入口:`/update_weights_from_disk` 原地换权重;`/model_info` 读回 `model_path`、`served_model_name`、`load_format`、`weight_version`、`architectures`。`/get_model_info` 与 `/get_server_info` 是打弃用警告的旧壳,`/get_weight_version` 与 `/weight_version` 已经直接返回 404。独立守护进程用 `python -m sglang.srt.weight_cache.daemon` 加同一套服务参数启动,单机起 `pp_size × tp_size` 个,多机必须给 `--dist-init-addr`。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--load-format` · 用哪个加载器 | 启动 | `auto`:先找 safetensors 再退 .bin;.gguf、Mistral 原生格式、对象存储与远程 URL 会自动改掉 | `dummy`:不读盘填随机数,只测性能。`sharded_state`、`presharded`:每 rank 只读自己那份。`fastsafetensors`:绕开主机内存直读显存 | `Load weight end` 行的 `elapsed`;`/model_info` 的 `load_format` |
| `--model-loader-extra-config` · 给加载器的 JSON | 启动 | `{}` | 默认加载器只认 `enable_multithread_load`(默认 true)与 `num_threads`(默认 8),写别的键直接报错;本地 NVMe 提到 16 读盘变快,网络盘反而互相抢 | `Loading safetensors checkpoint shards` 进度条 |

| `--weight-cache-timeout` · 等守护进程就绪最多几秒 | 启动 | 1800 | 大模型读盘慢时调高;等的是就绪文件出现,每 2 秒查一次 | `did not become ready within` |

| `SGLANG_EXTERNAL_MODEL_PACKAGE` · 外部模型包 | 环境变量 | 空 | 整包导入并覆盖同名架构 | `/model_info` 的 `architectures` 解析结果 |
| `SGLANG_USE_MODELSCOPE` · 从 ModelScope 下载 | 环境变量 | 0 | 设 1:本地路径不存在时走 ModelScope 而不是 HF | 下载日志的来源 |
| `/update_weights_from_disk` · 原地换权重 | 运行时 | `flush_cache` 为 true | 不重启;只走默认加载器;失败自动回滚 | 日志 `Update engine weights online from disk begin`;`/model_info` 的 `weight_version` |

**怎么看。** 这一章看 4 处。一是**夹住整段加载的两行日志**:`Load weight begin. avail mem=` 与 `Load weight end. elapsed=… type=… avail mem=… mem usage=…`。`elapsed` 是建模型、读盘、切片、量化后处理的总和,不是读盘时间;`mem usage` 才是权重实际占的显存。二是**启动分段计时那一行**:`Engine startup timings (s): load_weight=… kv_cache_allocation=… scheduler_e2e=… cuda_graph={…} tokenizer_e2e=…`,同一组数字也出在指标 `sglang:startup_time_seconds` 的 `phase` 标签上,按阶段各一个;注意在线换权重走的是另一个指标 `sglang:weight_load_duration_seconds`,它带 `source` 标签(`disk`、`distributed`、`tensor`、`ipc`),只记最近一次,记的是重载不是启动。三是**走了哪条路**:`Using model weights format ['*.safetensors']` 说明选中了哪类文件,`Loading from presharded checkpoint at` 说明吃到了落盘的预分片,`Detected Mistral native format` 说明格式被自动改过,`Loading safetensors checkpoint shards` 进度条看读盘速度。四是**守护进程两侧各自的日志**:守护进程侧 `Model loaded from disk in Xs` 与 `Exported N tensors as IPC handles. Ready to serve`,配不上时打 `Config mismatch: {字段: (守护进程侧, 引擎侧)}`;引擎侧 `Fetched N tensors from daemon`、`Zero-copy: mapped N tensors`、`Loaded model via IPC`。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| 本地 NVMe、单机多卡、启动一次跑很久 | `--model-loader-extra-config '{"num_threads": 16}'` | 用更多读线程换本地盘带宽;代价是主机内存峰值按线程数乘单文件大小涨。反复重启同一配置就再加 `--load-format presharded`,第二次省掉重新量化 |
| 网络文件系统、8 个 rank 读同一份 | `--weight-loader-prefetch-checkpoints --weight-loader-prefetch-num-threads 8 --weight-loader-drop-cache-after-load` | 用页缓存分摊把读盘总量从 8 份压到 1 份;代价是多线程读被自动关掉,本地盘上这套是纯负收益,而且丢页缓存意味着下次重启不再命中 |
| RL 或弹性扩缩容,同一张卡反复重启引擎 | 先独立起 `python -m sglang.srt.weight_cache.daemon`,引擎加 `--weight-cache-mode client` | 用「权重常驻在别人的显存里」换秒级重启;代价是量化只放行不量化与分块 FP8,所有在线换权重接口全拒,守护进程一死引擎立刻自杀 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 本地 NVMe 上启动慢,进度条走得慢 | `num_threads` 是不是默认 8 | 提到 16;反复重启同一配置改走 `presharded` |
| 网络盘上多 rank 一起启动很慢 | 预取开没开 | 开预取;主机内存不够再加 drop cache |
| 开了 `daemon` 模式重启没变快 | 守护进程是不是引擎自己拉的 | 改独立启动加 `client` |
| 引擎报 `Daemon config mismatch!` 直接退出 | 守护进程侧 `Config mismatch` 列出的差异字段:dtype、量化、各维并行度、revision、torch 版本、算力 | 对齐参数或重启守护进程;**这一条不会退回读盘** |
| 报 `not verified for CUDA IPC zero-copy` | 量化方法不在白名单 | 关掉权重缓存;这道门在连守护进程之前就查 |
| 守护进程启动就报导不出句柄 | 显存分配器是不是开了可扩展段 | 关掉该选项再起守护进程 |
| 引擎突然被杀,日志 `died while this engine holds its weights` | 守护进程先死了 | 先起守护进程再起引擎;检查它是不是被 OOM killer 收走 |
| `/update_weights_from_disk` 报 `not supported while the weight cache is active` | 权重缓存模式 | 关掉缓存后重启 |
| `/update_weights_from_disk` 报「HPC-Ops bf16xfp32」相关拒绝 | 那个融合矩阵乘优化开没开 | 关掉它,否则所有在线换权重都走不通 |
| 日志 `Fallback load_format to 'auto'` | R-Fork 的 ip、port、端口组是不是缺项 | 补齐;它不会报错只会静默降级 |
| 吞吐明显低于同尺寸模型 | 有没有 `falling back to Transformers` 警告 | 换原生架构名,或用外部模型包接进来 |
| 某个架构提示不支持,但代码里有这个文件 | 就绪前有没有 `Ignore import error when loading` 警告 | 那个模型文件缺依赖被跳过了,装上依赖 |
| 换权重后答案明显变差 | 请求里 `flush_cache` 是不是设成了 false | 保持默认 true |
| 主机内存被页缓存吃光 | 是不是长时间没丢缓存 | 开 drop cache |
| 预分片第一次没落盘 | `model_path` 是不是只读 | 在额外配置里给一个可写的 `presharded_path` |

## 六、常见误区

- **以为那个格式参数决定了加载器。** 名字就叫这个,自然会这么想。实际上量化配置的优先级在它之上:两类量化会把加载器整个换掉,日志里那行 `Using ModelOptModelLoader` 最常被略过,然后奇怪为什么 `--model-loader-extra-config` 不生效。
- **以为指纹对不上会退回读盘。** 引擎侧那行警告的措辞是 `Weight cache not available or config mismatch, falling back to disk load`,**源码自己的措辞就带误导**。真实行为是:只有套接字文件不存在才退回读盘,指纹不合是抛异常、进程退出。设计上是故意的——同一张卡上已经躺着另一份配置的权重,再读一份进来就是 OOM。
- **以为 `--weight-cache-mode daemon` 能让重启变快。** 名字里有守护进程,人们以为它常驻。引擎拉起的守护进程是引擎的子进程,引擎退它也退,而且第一次启动还多一次读盘加一次握手,比不开还慢。要秒级重启必须独立起守护进程,引擎用 `client`。
- **以为守护进程能让两个引擎各放一份权重。** 恰恰相反,它是让两个引擎共用同一份。代价就是谁都不能改:四条在线换权重通道全拒,CPU 备份被禁,量化只放行不量化和分块 FP8。
- **以为多线程越多读盘越快。** 本地盘上成立。网络盘上线程互相抢带宽,而且预取一开,系统就默认把多线程关掉了;你再显式写 `enable_multithread_load` 等于把它抢回来,结果更慢。
- **以为 R-Fork 是权重同步。** 它只在启动那一刻从种子实例拉一次,之后两边各走各的。种子后来换了权重,新实例不会跟着变。它还要求两边并行策略完全一致。
- **以为注册表和 vLLM 一样惰性。** 这份代码确实是从 vLLM 改来的,所以人们以为机制也一样。实际上启动时 238 个文件全导入,而且是每个调度器进程各导一遍;某个模型文件缺依赖只打一行警告跳过,那个架构就「不支持」。排查时先看就绪前的 `Ignore import error when loading`。
- **以为 `Load weight end` 里的 `elapsed` 是读盘时间。** 它包含建模型、切片和量化后处理,在线量化的模型里后处理可能占大头。`overlap` 模式下这行根本不打印。
- **以为启动加载有指标可看。** 有,但不是你想的那个。`sglang:weight_load_duration_seconds` 只记在线换权重,启动那次在 `sglang:startup_time_seconds` 的 `load_weight` 标签下。拿前者做启动看板会一直看到空值。
- **以为 `npcache` 能加速 safetensors。** 它只支持 .bin,safetensors 走它直接断言失败。
- **以为 `presharded` 要先跑离线脚本。** 那是 `sharded_state`。`presharded` 第一次自己落盘,但 `model_path` 只读(比如挂进来的 HF 缓存)时必须在额外配置里给一个可写的 `presharded_path`,否则第一次就静默落不下去,每次都是全量加载。
- **以为删了 checkpoint 还能热重载。** `--delete-ckpt-after-loading` 在就绪后把目录删了,之后 `/update_weights_from_disk` 读同一路径必然失败。
- **以为 `--model-impl` 只有原生和 Transformers 两档。** 一共四档,除了自动、原生、Transformers,还有一档整条换到国产 NPU 的实现上。
