# SGLang 12|量化

权重、激活、KV 三笔账各卡在哪、量化在算什么、粒度怎么配、kernel 怎么在启动期筛出来、在线量化能做什么不能做什么、KV 的 scale 从哪来,vLLM 解读的「量化」一章已经讲透(「原理:量什么、怎么算」「vLLM 怎么组织这件事」「三笔账各自怎么做」几部分)。SGLang 的量化底座是从 vLLM 移植的,注册表、FP8 方法类、KV scale 的加载逻辑文件头都写着来自 vLLM,所以这一页只写 SGLang 自己不一样的四块:kernel 后端交给用户、在线量化与重量化、KV 量化、checkpoint 检测与兼容表。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

权重卡显存(放不放得下),激活卡算力(矩阵乘快不快),KV 卡上下文与并发。量化把其中某一样换成低精度加 scale,三样各有一个入口,互不知道对方:`--quantization` 管权重和激活,`--fp8-gemm-backend` 与 `--fp4-gemm-backend` 管矩阵乘的 kernel,`--kv-cache-dtype` 管 KV。选错 kernel 比不量化还慢:权重的显存省下来了,矩阵乘却走了通用 Triton;KV 压成 FP8 槽数翻倍,注意力后端不做融合反量化,每步多一次转换,TPOT 反而变长。源码自己也这么说:不在「已优化」名单里的方法,启动时打一行「可能比不量化还慢」。

## 二、解法

**kernel 后端交给用户。** 块量化 FP8(DeepSeek 那种 128×128 一块一个 scale)的矩阵乘有 9 个候选名:auto、deep_gemm、flashinfer_trtllm、flashinfer_cutlass、flashinfer_deepgemm、flashinfer_cutedsl、cutlass、triton、aiter;NVFP4 有 6 个:auto、flashinfer_cudnn、flashinfer_cutedsl、flashinfer_cutlass、flashinfer_trtllm、marlin。显式指定就是它,硬件或依赖不满足直接抛错,不降级:Hopper 上指定 flashinfer_trtllm 报「需要 SM100/SM103」,没装 DeepGEMM 指定 deep_gemm 报「包不存在或被环境变量关了」,Hopper 上指定 FP4 的 flashinfer 系列报「需要 SM100+,请用 marlin」。只有 auto 才走优先级链。FP8 的链是 DeepGEMM(SM90 以上、装了包、环境变量没关)→ Blackwell 上的 FlashInfer(SM100 走 trtllm,SM120 走 cutlass)→ SM120 的 CUTLASS → AMD 的 AITER → 昇腾 → Intel XPU → Triton,SM120 上 auto 在启动时就被改写成 cutlass。FP4 的 auto 是 SM100 用 flashinfer_cutedsl,SM80 到 SM90 用 marlin(权重 4 bit、激活 16 bit 的退路,省显存不省算力),其余含 SM120 用 flashinfer_cutlass。选定之后 kernel 内还有一层形状级回退:DeepGEMM 要求输出维是 64 的倍数、输入维是 128 的倍数、块正好 128×128、输出 bf16,不满足的层当场走 Triton;FlashInfer trtllm 要求输入维至少 256;flashinfer_deepgemm 只接批小于 32 的调用,其余交回 DeepGEMM 或 Triton。这层回退每层每次调用判断,没有日志。

**在线量化与重量化。** `--quantization fp8` 对一个 BF16 checkpoint:加载时逐层量化,dense 层默认整个矩阵一个 scale,有 CUTLASS、Marlin 或 AITER 的 per-token 路径时改成每个输出通道一个;MoE 专家逐个一个 scale。这条路不是块量化,所以 `--fp8-gemm-backend` 管不到它。跨格式的重量化只有 1 个方法:`quark_mxfp4` 把 NVFP4 或 FP8 的 checkpoint 在加载时转成 MXFP4(FP8 先反量化到 BF16 再量化),给 AMD gfx95 用;`--quantization` 与 checkpoint 声明的方法不一致时,只有它被放行,并打一行「重量化可能掉精度,请重新评测」。`nvfp4_online` 只在 SM100 上可用,只把 routed experts(路由到的专家)转成 NVFP4,源可以是 BF16、FP16 或 FP8,激活每 token 一个 FP32 scale 运行时算;dense 层和 shared experts 保持 checkpoint 精度。`--moe-runner-backend` 没指定时自动定为 flashinfer_trtllm,指定了但不在 flashinfer_trtllm、flashinfer_trtllm_routed、flashinfer_cutedsl 三者之内直接报错。

**KV 量化。** `--kv-cache-dtype` 有 8 个正式取值:auto、bf16 与 bfloat16、fp8_e5m2、fp8_e4m3、mxfp8、nvfp4、fp4_mx_block16;第 9 个 fp4_e2m1 是废弃名,选了直接报错让你改 fp4_mx_block16。auto 不等于不量化:checkpoint 的量化配置里声明了 KV 是 FP8,auto 就变成 fp8_e4m3。FP8 的 scale 只支持整层一个标量,来源两个:checkpoint 里的 k_scale 与 v_scale,或 `--quantization-param-path` 指的 JSON(按 TP 秩和层号两级);都没有就是 1.0,打一行警告。FP4 的两种配方都是每 16 个值一个 scale(标准 MXFP4 是 32 个,所以名字里特意不叫 mxfp4),写入时现算,不需要 checkpoint 提供;nvfp4 在此之上每层还有一个全局 FP32 scale,取自 checkpoint 的 k_scale,没有也是 1.0。nvfp4 要 SM100 或 SM120,mxfp8 要 Blackwell,两种 FP4 都要 PyTorch 2.8 与 CUDA 12.8。哪个注意力后端吃哪种精度,06 章的兼容矩阵已经列过;FP8 KV 在池里怎么存、槽数翻倍与「后端不融合反量化时 TPOT 反而变长」,03 章讲过。

**checkpoint 自动检测与兼容表。** 不带 `--quantization` 时,从 config.json 的 quantization_config(缺 quant_method 或写 modelopt 的按 ModelOpt 解析)、独立的 hf_quant_config.json、compression_config、昇腾 ModelSlim 配置里认出方法;每个方法类还能改写检测结果,ModelOpt 据此分出 FP8、FP4 与混合精度。带了 `--quantization` 且与 checkpoint 不一致,查一张 8 行的兼容表:modelopt_fp8、modelopt_fp4、modelopt_mixed、petit_nvfp4 接受 checkpoint 写 modelopt;modelopt_fp4 与 nvfp4_online 接受 fp8;w8a8_int8、w8a8_fp8、auto-round-int8 接受 compressed-tensors。表里没有就报错;草稿模型例外,改用它自己检测到的方法。最后三道闸:方法不在注册表里报「Unknown quantization method」(命令行 31 个名字,CUDA 上注册表只有 28 个键,gptq 就在差集里,NVIDIA 与 AMD 上只剩 gptq_marlin);ROCm 上不在 13 个的白名单里报错;不在 22 个的「已优化」名单里打「可能比不量化还慢」警告,SM100 上的 mxfp4 与 mxfp8 免警。

## 三、代价

- 3 个入口互不知道对方,一个组合行不行要到 3 个时刻才知道:启动时的参数断言、加载时的方法类构造、第一次前向的 kernel 分发。
- 选定的后端不打日志。auto 落到了哪个 kernel、哪几层因为形状退到了 Triton,启动日志和 `/server_info` 都看不出来,后者回显的还是 auto;只有 DeepGEMM 的 JIT 预热有日志。
- 在线量化没有校准:整个矩阵一个 scale,离群通道吃亏。文档自己写离线优先,量化完要跑基准。
- FP4 KV 每 16 个值付 1 字节 scale,容量是 BF16 的 3.56 倍不是 4 倍;小模型在难数据集上掉点明显,文档给的例子是 120B 模型在 aime25 从 0.75 掉到 0.35。
- 跨格式重量化有损且慢:FP8 到 MXFP4 要先反量化到 BF16 再量化,一层一层做,日志要求重新评测。

## 四、和 vLLM 不一样的六处

1. **kernel 由谁定。** vLLM 每个方案一张候选表,启动时先筛硬件再筛配置,选中打一条一次性日志;用户能指定线性层后端(白名单,找不到报错)、能禁用某个 kernel(黑名单)。SGLang 是 2 个命令行参数各自一条优先级链,auto 走链、显式指定不满足就报错,同样「显式的失败要响」,但没有黑名单,也没有选中日志。
2. **形状回退发生在哪。** vLLM 在启动期按形状筛完;SGLang 的块 FP8 kernel 每次调用判断形状,不合适当场走 Triton。
3. **重量化的含义。** vLLM 的重量化是融合层多个分片 scale 取最大值那一步,只在需要时做。SGLang 那一步也有,另外多了跨格式的 `quark_mxfp4`。
4. **在线量化的范围。** vLLM 用两张字典(Linear 一张、MoE 一张)定义能在线做什么,配错静默不量化。SGLang 没有这种字典,`--quantization` 的 31 个名字里哪些支持在线、哪些只认离线 checkpoint,源码留了 TODO 说清单该只留支持在线的;`nvfp4_online` 是 vLLM 没有的在线 NVFP4。
5. **KV scale 的入口。** vLLM 的 per-tensor scale 只从 checkpoint 拿。SGLang 多一个 `--quantization-param-path` 的 JSON 入口,而且只在 fp8_e4m3 下读它。
6. **KV dtype 的取值。** vLLM 18 种;SGLang 8 种,没有 int8、TurboQuant、DeepSeek MLA 专用布局,多了 mxfp8 与两种 FP4 配方。

## 五、调参与观测

**参数在哪调。** 这一页的参数全是启动参数,改了要重启;3 个相关的环境变量也要重启。运行时没有能换量化方法或 kernel 后端的接口,`/set_internal_state` 改不了这里的任何一项。`/server_info` 回显的是你传的值:GEMM 后端写 auto 就回 auto,不告诉你落到了哪个 kernel。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--quantization` · 权重与激活用什么方法 | 启动 | 空,从 checkpoint 检测 | 未量化 checkpoint 给 fp8:权重减半、矩阵乘走 FP8;给了与 checkpoint 不一致的名字:报错,或 quark_mxfp4 重量化 | 日志 `Using CLI-specified quantization`、`Requantizing from`、`not fully optimized yet` |
| `--fp8-gemm-backend` · 块 FP8 矩阵乘用哪套 kernel | 启动 | auto;SM120 上自动改 cutlass | 显式指定不满足直接报错;flashinfer_deepgemm 只对批小于 32 的 decode 有效,其余回 DeepGEMM | 没有选中日志;报错信息里写着要求的硬件 |
| `--fp4-gemm-backend` · NVFP4 矩阵乘用哪套 kernel | 启动 | auto:SM100 cutedsl,SM80–90 marlin,其余 cutlass | Hopper 只能 marlin,省显存不省算力;Blackwell 之外指定 flashinfer 系列报错 | 报错 `require SM100+` |
| `--moe-runner-backend` · MoE 专家矩阵乘用哪套 | 启动 | auto;nvfp4_online 下自动 flashinfer_trtllm | 与 `--quantization` 有配对断言:flashinfer_trtllm 只收 7 种加不量化,cutedsl 只收 NVFP4 系 | 启动断言信息 `supports only` |
| `--kv-cache-dtype` · KV 存什么精度 | 启动 | auto;checkpoint 声明 FP8 KV 时变 fp8_e4m3 | fp8 槽数约 2 倍,fp4 约 3.56 倍;后端不融合反量化时 TPOT 变长(03 章);fa3 配 e5m2 被换成 triton(06 章) | 就绪前 `max_total_num_tokens`;警告 `KV Cache might lead to an accuracy drop` |
| `--quantization-param-path` · FP8 KV 的 scale JSON | 启动 | 空,scale 为 1.0 | 只在 fp8_e4m3 下读;不给且 checkpoint 无 scale 时等于硬转 | `Loaded KV cache scaling factors from`;警告 `Defaulting to scaling factors of 1.0` |
| `SGLANG_ENABLE_JIT_DEEPGEMM` · 允许 DeepGEMM | 环境变量 | 开,另要 SM90 以上且装了包 | 关掉后 auto 链跳过 DeepGEMM,Hopper 落到 Triton | DeepGEMM 预热日志有无 |
| `SGLANG_USE_AITER` · AMD 上启用 AITER | 环境变量 | 关 | 关着时指定 aiter 报错,auto 落到 Triton | 报错 `requires AMD GPUs with SGLANG_USE_AITER=1` |
| `SGLANG_FP4_IGNORED_LAYERS` · 在线 NVFP4 跳过哪些专家 | 环境变量 | 空 | 列出的专家保持源精度 | — |

**怎么看。** 启动日志里找三类行。量化方法三行:`Using CLI-specified quantization (X) which is compatible with HF config quant_method (Y)` 说明你传的名字和 checkpoint 对上了;`Requantizing from quant_method='X' to the requested online quantization='Y'` 后面跟着重新评测的要求;`X quantization is not fully optimized yet. The speed can be slower than non-quantized models` 是名单外方法的警告。KV 两行:`Loaded KV cache scaling factors from` 或 `Using FP8 KV cache but no scaling factors provided. Defaulting to scaling factors of 1.0`;FP4 一开就有 `NVFP4 KV Cache might lead to an accuracy drop`。kernel 后端没有正面日志,只有报错;DeepGEMM 的 JIT 预热日志出现,说明 auto 落到了它。

| 症状 | 先查 | 然后 |
|---|---|---|
| 开了 fp8 显存降了,吞吐没涨甚至降 | Hopper 上 DeepGEMM 装没装,auto 是否落到了 Triton | 装 DeepGEMM;或显式指定,让它报错告诉你缺什么 |
| 启动报 `requested via --fp8-gemm-backend` | 显卡代与后端的硬件要求 | 换 auto,或换这张卡支持的名字 |
| 启动报 `Unknown FP8 GEMM backend` | 指定了 flashinfer_cutedsl 但模型不是 MXFP8 dense | 换 flashinfer_cutlass 或 auto |
| 启动报 `Unknown quantization method: gptq` | NVIDIA 与 AMD 上 gptq 已移除 | 换 gptq_marlin |
| 启动报 quant_method 与 quantization 不匹配 | checkpoint 已量化 | 去掉 `--quantization`;要跨格式只有 quark_mxfp4 |
| 启动打 `not fully optimized` | 方法不在已优化名单 | 接受,或换 fp8、gptq_marlin、awq_marlin 这类有专用 kernel 的 |
| 开 FP8 KV 之后 TPOT 变长 | 06 章矩阵,后端是否融合反量化 | 换 fa3、trtllm 系或 flashmla |
| 开 FP8 KV 后答案质量下降 | 日志 `Defaulting to scaling factors of 1.0`;是不是 e5m2 | 给 JSON 或换带 k_scale 的 checkpoint;e5m2 换 e4m3 |
| FP4 KV 启动报 `float4_e2m1fn_x2` | PyTorch 与 CUDA 版本 | 升到 2.8 与 12.8 |
| nvfp4_online 启动报 moe runner 错 | `--moe-runner-backend` 是否在 3 个之内 | 去掉,让它自动选 flashinfer_trtllm |
| AMD 上 Gemma 4 批量 decode 答案错 | 是否 aiter 加 fp8_e4m3 | KV 改回 auto |

## 六、常见误区

- **以为 `--fp8-gemm-backend` 管所有 FP8。** 人们看名字。它只管块量化 FP8、MXFP8 dense 与 NVFP4;在线 `--quantization fp8` 走整矩阵一个 scale 的路径,MoE 走 `--moe-runner-backend`,都与它无关。
- **以为 auto 在 Hopper 上会选 flashinfer_deepgemm。** 文档里它是 Hopper 专用、decode 小批更快,人们以为 Hopper 默认就是它。auto 链里根本没有它,只能显式指定;没装 DeepGEMM 的 Hopper 上 auto 落到 Triton。
- **以为显式指定后端、启动没报错,就每层都在用它。** 形状不合的层每次调用悄悄走 Triton,没有日志。DeepGEMM 要 64 与 128 的倍数,FlashInfer trtllm 要输入维至少 256,小模型的某些投影层就是不满足。
- **以为 flashinfer_cutedsl 是块 FP8 的合法后端。** 它在 9 个选项里,但块 FP8 的显式分发没有它这一分支,会报 Unknown FP8 GEMM backend;它只对 MXFP8 dense 有效。
- **以为 `--quantization fp8` 会做 DeepSeek 那种块量化。** 在线 fp8 没有块,整个矩阵或每个通道一个 scale,离群通道会吃亏;想要块量化只能离线出 checkpoint。
- **以为 `--kv-cache-dtype auto` 就是 BF16。** checkpoint 声明了 FP8 KV,auto 就是 fp8_e4m3,ModelOpt 的 FP8 checkpoint 常带这条声明。
- **以为 `--quantization-param-path` 给了就生效。** 只在 fp8_e4m3 下读;用 fp8_e5m2 时它被无视,而且没有任何提示。
- **以为 FP4 KV 省 4 倍。** 每 16 个值多 1 字节 scale,实际 3.56 倍;启动时那行「可能掉精度」不是摆设,小模型在难题上掉一半。
- **以为已量化的 checkpoint 也要带 `--quantization`。** 不需要,会检测;带错了直接报不匹配,只有那 8 行兼容表放行。文档专门强调 DeepSeek V3 与 R1 已经是 FP8,别再加。
- **以为「not fully optimized」只是提示。** 名单外的方法(awq 而非 awq_marlin、bitsandbytes、gguf、blockwise_int8、SM100 之外的 mxfp4)真的可能比 BF16 慢,这行 warning 最常被略过。
- **以为 nvfp4_online 会量化整个模型。** 只动 routed experts,dense 层与 shared experts 保持原精度,显存省得没想象中多;还只有 SM100 能用。
- **以为跨格式重量化是免费的。** FP8 到 MXFP4 先反量化再量化,两次舍入;日志明确要求重新评测。
