# SGLang 12|量化

权重、激活、KV 三笔账各卡在哪、量化在算什么、粒度怎么配、kernel 怎么在启动期筛出来、在线量化能做什么、KV 的 scale 从哪来,vLLM 解读的「量化」一章已经讲透。SGLang 的量化底座是从 vLLM 移植的,注册表、FP8 的方法类、KV 的 scale 加载逻辑文件头都注明来自那边,所以这一页不重复原理,只写 SGLang 自己不一样的四块。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

量化开了,显存确实降了,吞吐却没涨,甚至变慢。这一章要防的就是这件事。

省显存几乎一定成功,因为它只取决于权重变成了几个字节;省时间却取决于另外两样:矩阵乘最终落到哪个 kernel,以及注意力后端会不会顺手把 KV 反量化掉。这两样都不在你写的那个开关里——三笔账各有一个独立入口,彼此不知道对方存在。配错了没有异常,只是慢:权重砍掉一半,矩阵乘却走了通用的 Triton 实现;KV 压成 8 bit、槽数翻倍,后端不做融合反量化,每步多一次转换,TPOT 反而变长。

源码自己承认这件事:有一份「已优化」的方法名单,不在名单里的方法启动时会打一行「可能比不量化还慢」。

## 二、解法

底座照搬,所以「怎么量、粒度怎么配、scale 怎么加载」和参照项目一样。SGLang 自己加的是四块。

**把 kernel 后端提到命令行,自动挡走链,手动挡不降级。** 块量化 FP8 的矩阵乘有 9 个候选、NVFP4 有 6 个,各由一个启动开关选(名字都在第五节)。自动挡是一条写死的优先级链:先看 DeepGEMM 能不能用,再看 Blackwell 上的 FlashInfer,再看 SM120 的 CUTLASS,再看 AMD 的 AITER,然后昇腾、Intel,最后兜底的 Triton。手动挡是另一套逻辑:硬件或依赖不满足直接抛错,绝不悄悄降级——Hopper 上点名要 Blackwell 那一支,报的是「需要 SM100」;没装 DeepGEMM 还点名它,报的是「包不存在,或者被环境变量关了」。取舍很干脆:自动挡保证起得来,手动挡保证你以为在用的就是在用的。

但只保证了一半。后端选定之后,kernel 里还有一层按形状的回退,每层每次调用现判:DeepGEMM 要求输出维是 64 的倍数、输入维是 128 的倍数、块正好 128 乘 128、输出是 BF16;FlashInfer 的那一支要求输入维至少 256、输出是 BF16。不满足的层当场改走 Triton,没有任何日志。所以「启动没报错」不等于「每一层都在用它」。

**加载时量化,以及一条跨格式的重量化。** 给一个 BF16 的 checkpoint 指定 FP8,它在加载时逐层量化:dense 层默认整个矩阵一个 scale,只有 CUTLASS 或 Marlin 可用、或者 AMD 那边开了每 token 激活时,才改成每个输出通道一个——因为那几个 kernel 只认按通道的 scale;MoE 专家逐个一个 scale。这条路不是块量化,所以上一段那个 FP8 矩阵乘开关管不到它。真正跨格式的重量化只有一条:把 NVFP4 或 FP8 的 checkpoint 在加载时转成 MXFP4(FP8 要先反量化回 BF16 再量化),给 AMD 新一代卡用;命令行指定的方法与 checkpoint 声明的不一致时,只有这一条被放行,并打一行「重量化可能掉精度,请重新评测」。另外还有一种只在 Blackwell 上可用的在线 NVFP4,只把路由到的专家转过去,dense 层与共享专家保持 checkpoint 原来的精度。

**自己的一套 KV 精度配方。** 除两种 FP8 外,还有 MX 风格的 FP8、NVFP4,以及一种块 16 的 FP4。两种 FP4 配方都是每 16 个值一个 scale(标准的 MX 块是 32 个,所以名字里特意避开 MXFP4),写入时现算,不需要 checkpoint 提供;NVFP4 在此之上每层还有一个全局 FP32 系数,取自 checkpoint 里 key 的那个 scale,没有就是 1.0。FP8 那一侧相反:只支持整层一个标量,来源是 checkpoint 或一份外部 JSON,两处都没有就是 1.0 加一行警告,那等于硬转。还有一件容易漏的:自动挡不等于不量化——checkpoint 的量化配置里声明了 KV 是 FP8,自动挡就解析成 FP8 E4M3。哪个注意力后端吃哪种精度,06 章的兼容矩阵已经列过;FP8 的 KV 在池里怎么存、槽数翻倍之后为什么反而可能变慢,03 章讲过。

**检测在前,四道闸在后。** 不指定方法时,先看昇腾那套配置在不在(在就用它),否则依次看模型配置里的量化段、压缩配置、放在仓库根上的那份独立量化配置文件;认出来之后,每个方法类还有一次改写检测结果的机会。指定了又和 checkpoint 对不上,查一张 8 行的兼容表,表里没有就报错(草稿模型例外,改用自己检测到的那个)。之后三道闸:方法不在本平台的注册表里,报「未知的量化方法」——NVIDIA 与 AMD 上的经典 GPTQ 就卡在这里,它只注册在昇腾、CPU 与 Intel GPU 上,别的平台只剩 Marlin 版;ROCm 上还要过一张 13 项的白名单;最后是第一节那张 22 项的「已优化」名单,不在里面只警告不拦。

## 三、代价

- 3 个入口互不知道对方,一个组合行不行要到 3 个时刻才知道:启动时的参数断言、加载时的方法类构造、第一次前向的 kernel 分发。
- **选中了什么它不说。** 自动挡落到了哪个 kernel、哪几层因为形状退回了 Triton,启动日志里都没有,那两个文件里根本没有日志调用;服务信息接口回显的是解析后的启动参数,你写自动挡它就还是自动挡。只有两个特定模型族会在解析期把它改写成具体名字并各打一行日志,以及 DeepGEMM 的即时编译预热会留下痕迹。
- 加载时量化没有校准:整个矩阵一个 scale,离群通道吃亏。文档自己写离线优先,量化完要跑基准。
- FP4 的 KV 每 16 个值要付 1 字节 scale,容量是 BF16 的 3.56 倍而不是 4 倍;小模型在难数据集上掉点明显,文档给的例子是 120B 的模型在一个数学竞赛集上从 0.75 掉到 0.35。
- 跨格式重量化有损且慢:FP8 到 MXFP4 先反量化回 BF16 再量化,两次舍入,日志明确要求重新评测。

## 四、和 vLLM 不一样的六处

两边的参数名都在第五节。

1. **kernel 由谁定,以及选完说不说。** vLLM 每个方案一张候选表,启动时先筛硬件再筛配置,选中打一条一次性日志;用户能给线性层后端一张白名单,也能把某个 kernel 拉黑。SGLang 是两个命令行开关各带一条优先级链,自动挡走链、手动挡不满足就报错,同样坚持「显式的失败要响」,但没有黑名单,也不打选中日志。
2. **形状回退发生在哪。** vLLM 在启动期就按形状筛完;SGLang 的块 FP8 kernel 每次调用现判形状,不合适当场走 Triton。
3. **重量化指什么。** vLLM 说的重量化是融合层里多个分片的 scale 取最大值那一步,只在需要时做。SGLang 那一步也有,另外多出一条真正跨格式的路。
4. **在线量化的边界写在哪。** vLLM 用两张字典写死了在线能做哪几种,配了表外的组合不报错、静默地不量化。SGLang 没有这种字典,哪些方法支持在线、哪些只认离线 checkpoint 没有一处写明,源码自己留了一条待办说这张清单本该只留支持在线的;而它多出一种 vLLM 没有的在线 NVFP4。
5. **KV 的 scale 从哪来。** vLLM 的整层标量只从 checkpoint 拿。SGLang 多一个外部 JSON 入口,按张量并行秩与层号两级组织,而且只在一种 FP8 精度下才去读它。
6. **KV 精度的取值谱。** vLLM 18 种;SGLang 9 种,其中 1 个是选了直接报错的废弃名。它没有 INT8、没有那一族靠范数修正的 3 bit 与 4 bit 配方、没有 MLA 专用布局,多了 MX 风格的 FP8 与两种 FP4 配方。

## 五、调参与观测

**参数在哪调。** 这一页的参数全是启动参数,改了要重启;3 个相关的环境变量也一样。运行时没有任何能换量化方法或 kernel 后端的接口,`/set_internal_state` 只认 5 个与本章无关的字段。`/server_info` 回显的是解析后的启动参数:GEMM 后端写 `auto`,回显还是 `auto`;只有 LongCat 的非 ue8m0 FP8 checkpoint 与 HYV4 的 MXFP8 这两处会在解析期被改写成具体名字,并各打一行日志。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--quantization` · 权重与激活用什么方法 | 启动 | 空,从 checkpoint 检测 | 未量化 checkpoint 给 `fp8`:权重减半、矩阵乘走 FP8;给了与 checkpoint 不一致的名字:报错,只有 `quark_mxfp4` 被放行去重量化 | 日志 `Using CLI-specified quantization`、`Requantizing from`、`not fully optimized yet` |
| `--fp8-gemm-backend` · 块 FP8 与 MXFP8 dense 的矩阵乘用哪套 kernel | 启动 | `auto`;SM120 上内部按 `cutlass` 走(回显仍是 `auto`) | 显式指定而硬件或依赖不满足:直接报错不降级;`flashinfer_deepgemm` 只接批量小于 32 的调用,其余回 DeepGEMM 或 Triton | 没有选中日志;报错信息里写着这个后端要求的硬件 |
| `--fp4-gemm-backend` · NVFP4 矩阵乘用哪套 kernel | 启动 | `auto`:SM100 走 `flashinfer_cutedsl`,SM80–SM90 走 `marlin`,其余走 `flashinfer_cutlass` | Hopper 上只有 `marlin` 能用,权重 4 bit、激活 16 bit,省显存不省算力;Blackwell 之外指定 flashinfer 系列报错 | 报错 `require SM100+. Use --fp4-gemm-backend marlin` |
| `--moe-runner-backend` · MoE 专家矩阵乘用哪套 | 启动 | `auto`;`nvfp4_online` 下自动定为 `flashinfer_trtllm` | 与 `--quantization` 有配对断言:`flashinfer_trtllm` 只收 7 种方法加不量化,`flashinfer_cutedsl` 只收 NVFP4 系 3 种 | 启动断言信息 `supports only` |
| `--kv-cache-dtype` · KV 存什么精度 | 启动 | `auto`;checkpoint 声明 FP8 KV 时解析成 `fp8_e4m3` | FP8 槽数约 2 倍,两种 FP4 约 3.56 倍;后端不融合反量化时 TPOT 变长(06 章);`mxfp8` 要 Blackwell,`nvfp4` 要 SM100 或 SM120,两种 FP4 都要 PyTorch 2.8 与 CUDA 12.8 | 就绪前那行 `max_total_num_tokens`;警告 `KV Cache might lead to an accuracy drop` |
| `--quantization-param-path` · FP8 KV 的 scale JSON | 启动 | 空,scale 取 1.0 | 只在 `fp8_e4m3` 下读,文件按 TP 秩与层号两级组织;模型没有加载 scale 的入口时直接报错 | `Loaded KV cache scaling factors from`;警告 `Defaulting to scaling factors of 1.0` |
| `SGLANG_ENABLE_JIT_DEEPGEMM` · 允许用 DeepGEMM | 环境变量 | 开;另要 CUDA SM90 以上且包能导入 | 关掉后 `auto` 链跳过 DeepGEMM,Hopper 上一路落到 Triton | DeepGEMM 的即时编译预热日志有没有出现 |
| `SGLANG_USE_AITER` · AMD 上启用 AITER | 环境变量 | 关 | 关着时显式指定 `aiter` 报错,`auto` 落到 Triton | 报错 `requires AMD GPUs with SGLANG_USE_AITER=1` |
| `SGLANG_FP4_IGNORED_LAYERS` · 在线 NVFP4 跳过哪些层 | 环境变量 | 空 | 列出的层保持源精度 | — |

**怎么看。** 启动日志里找三类行。量化方法三行:`Using CLI-specified quantization (X) which is compatible with HF config quant_method (Y)` 说明你传的名字和 checkpoint 对上了;`Requantizing from quant_method='X' to the requested online quantization='Y'` 后面跟着重新评测的要求;`X quantization is not fully optimized yet. The speed can be slower than non-quantized models` 是名单外方法的警告。KV 两行:`Loaded KV cache scaling factors from` 或 `Using FP8 KV cache but no scaling factors provided. Defaulting to scaling factors of 1.0`;两种 FP4 一开就有 `KV Cache might lead to an accuracy drop`。GEMM 后端没有正面日志,只有报错,唯一的旁证是 DeepGEMM 的预热日志出现说明 `auto` 落到了它。另外注意力后端可能被 KV 精度改写:`fa3` 配 `fp8_e5m2` 会被换成 `triton`,日志写 `FlashAttention3 only supports fp8_e4m3 if using FP8`。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| checkpoint 已经是量化好的(DeepSeek 的 FP8 这类),Hopper 单机 | 什么都不加,只把 DeepGEMM 装上 | 检测自己会认出方法,多加 `--quantization` 反而容易报不匹配;装 DeepGEMM 是为了让 `auto` 别落到 Triton |
| 手上只有 BF16 权重、显存吃紧、要立刻起服务 | `--quantization fp8` | 用加载时逐层量化换权重减半;代价是整矩阵一个 scale、没有校准,精度不如离线出的 checkpoint,而且这条路不是块量化,`--fp8-gemm-backend` 对它无效 |
| 长上下文或高并发,显存卡在 KV 上 | `--kv-cache-dtype fp8_e4m3`,配一个带 `k_scale` 的 checkpoint 或 `--quantization-param-path`,注意力后端按 06 章挑融合反量化的那几个 | 用 KV 槽数翻倍换一点精度;后端挑错会让 TPOT 变长,scale 缺省成 1.0 会掉点。Blackwell 上再想压可以换 `fp4_mx_block16`,但先在自己的数据集上测一遍 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 开了 FP8 显存降了,吞吐没涨甚至降 | Hopper 上 DeepGEMM 装没装,`auto` 是否落到了 Triton | 装 DeepGEMM;或显式指定,让它报错告诉你缺什么 |
| 启动报 `requested via --fp8-gemm-backend` | 显卡代次与这个后端的硬件要求 | 换回 `auto`,或换这张卡支持的名字 |
| 启动报 `Unknown FP8 GEMM backend` | 是不是指定了 `flashinfer_cutedsl` 而模型不是 MXFP8 dense | 换 `flashinfer_cutlass` 或 `auto` |
| 启动报 `Unknown quantization method: gptq` | NVIDIA 与 AMD 上 `gptq` 已移除 | 换 `gptq_marlin` |
| 启动报 quant_method 与 quantization 不匹配 | checkpoint 是不是已经量化过 | 去掉 `--quantization`;要跨格式只有 `quark_mxfp4` |
| 启动打 `not fully optimized` | 方法在不在那 22 项名单里 | 接受,或换 `fp8`、`gptq_marlin`、`awq_marlin` 这类有专用 kernel 的 |
| 显式指定了后端,启动也没报错,但速度还是没上去 | 层的形状是否满足这个 kernel 的整除要求 | 没有日志可查,只能对着模型维度算;换 `auto` 或换后端再比一次 |
| 开 FP8 KV 之后 TPOT 变长 | 06 章矩阵,当前后端是否融合反量化 | 换一个融合的后端 |
| 开 FP8 KV 后答案质量下降 | 日志有没有 `Defaulting to scaling factors of 1.0`;是不是 `fp8_e5m2` | 给 JSON 或换带 `k_scale` 的 checkpoint;`fp8_e5m2` 换 `fp8_e4m3` |
| 指定了 `fa3` 却发现跑的是 `triton` | 是不是配了 `fp8_e5m2` | 换 `fp8_e4m3`,或接受被改写 |
| FP4 KV 启动报 `float4_e2m1fn_x2` | PyTorch 与 CUDA 版本 | 升到 2.8 与 12.8 |
| `--kv-cache-dtype fp4_e2m1` 直接被拒 | 这是已废弃的名字 | 改用 `fp4_mx_block16` |
| `nvfp4_online` 启动报 MoE runner 错 | `--moe-runner-backend` 是不是那 3 个之一 | 去掉,让它自动定为 `flashinfer_trtllm` |
| AMD 上 Gemma 4 批量 decode 答案错 | 是不是 `aiter` 后端加 `fp8_e4m3` | KV 改回 `auto` |

## 六、常见误区

- **以为 `--fp8-gemm-backend` 管所有 FP8。** 人们看名字。它只管块量化 FP8、MXFP8 dense 与(通过另一个参数)NVFP4 那一侧;`--quantization fp8` 走的是整矩阵或每通道一个 scale 的路径,MoE 走 `--moe-runner-backend`,都与它无关。
- **以为 `auto` 在 Hopper 上会选 `flashinfer_deepgemm`。** 文档里它写着 Hopper 专用、小批 decode 更快,于是人们以为 Hopper 默认就是它。`auto` 链里根本没有它,只能显式指定;没装 DeepGEMM 的 Hopper 上 `auto` 落到 Triton。
- **以为显式指定了后端、启动又没报错,就每层都在用它。** 形状不合的层每次调用悄悄走 Triton,没有日志。DeepGEMM 要 64 与 128 的倍数,FlashInfer 那一支要输入维至少 256,小模型的某些投影层就是不满足。
- **以为 `flashinfer_cutedsl` 是块 FP8 的合法后端。** 它确实在那 9 个选项里,但块 FP8 的显式分发根本没有它这一分支,会报 `Unknown FP8 GEMM backend`;它只对 MXFP8 dense 有效。
- **以为 `/server_info` 会告诉你实际用了哪个 kernel。** 它回显的是解析后的启动参数,写 `auto` 就还是 `auto`。SM120 上内部改走 `cutlass` 这种重写发生在模块内部,不写回参数;只有 LongCat 与 HYV4 那两处模型级覆盖才真的改了参数值。
- **以为 `--quantization fp8` 会做 DeepSeek 那种块量化。** 加载时的 FP8 没有块,整个矩阵或每个输出通道一个 scale,离群通道会吃亏;想要块量化只能用离线出好的 checkpoint。
- **以为 `--kv-cache-dtype auto` 就是 BF16。** checkpoint 的量化配置里声明了 KV 是 FP8,`auto` 就是 `fp8_e4m3`,ModelOpt 的 FP8 checkpoint 常带这条声明。
- **以为 `--quantization-param-path` 给了就生效。** 只在 `fp8_e4m3` 下读;用 `fp8_e5m2` 时它被完全无视,而且没有任何提示。
- **以为 FP4 的 KV 省 4 倍。** 每 16 个值多 1 字节 scale,实际 3.56 倍;启动那行「可能掉精度」不是摆设,小模型在难题上能掉一半。
- **以为已量化的 checkpoint 也要带 `--quantization`。** 不需要,会检测;带错了直接报不匹配,只有那 8 行兼容表放行。文档专门强调 DeepSeek V3 与 R1 已经是 FP8,别再加。
- **以为「not fully optimized」只是提示。** 名单外的方法(`awq` 而非 `awq_marlin`、`bitsandbytes`、`gguf`、`blockwise_int8`、SM100 之外的 `mxfp4`)真的可能比 BF16 慢,这行警告最常被略过。
- **以为 `nvfp4_online` 会量化整个模型。** 只动路由到的专家,dense 层与共享专家保持源精度,显存省得没想象中多;而且只有 SM100 能用。
- **以为跨格式重量化是免费的。** FP8 到 MXFP4 先反量化再量化,两次舍入;日志明确要求重新评测。
