# SGLang 02|调度器:缓存感知与零开销重叠

连续批处理为什么按步调度、chunked prefill 怎么把长 prompt 切开、每步的 token 预算怎么分、显存耗尽之后抢占谁,vLLM 解读的「调度器」一章已经讲透。这一页只说 SGLang 遇到的问题、它的解法、代价、以及和 vLLM 不一样的地方。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

每一步 GPU 只算 5–30 毫秒,算完调度器要在 CPU 上做一轮事:把采样结果拷回来、判断谁结束了、释放显存、把树更新、挑下一批、把输入拷上去。这一轮是 Python,小模型上要 2–10 毫秒。GPU 在这段时间里空转,decode 越快的模型空转比例越高,7B 模型在一张卡上能空掉 20–30% 的时间,吞吐和 TPOT 一起坏。

第二个问题是进批的顺序。等待队列里谁先进批决定了树能不能一次长好、后面的请求能不能命中;进多少又要猜每个请求还会生成多长,猜多了显存空着,猜少了跑到一半被踢出去重算。

## 二、解法:CPU 和 GPU 各干各的

最天然的直觉是把 CPU 的事和 GPU 的事错开:GPU 算第 N 步的时候,CPU 处理第 N−1 步的结果、准备第 N+1 步。难点在第 N 步的输入是第 N−1 步采样出来的 token,CPU 准备第 N 步时还不知道它是什么。

SGLang 的办法是不让 CPU 知道。每个请求在显存里有一个固定的格子,前向结束时采样出的 token 直接写进自己的格子;下一步前向开始时,从格子里把 token 取出来当输入。写和读都在 GPU 的计算流上排队,顺序天然对,CPU 全程不碰 token 的值,只碰格子号。于是主循环变成:挑批、把前向和采样扔给 GPU、把上一步的结果拿来处理、记下这一步等下一轮处理。

为什么实际不吃亏:CPU 处理结果的那段时间原本就和 GPU 前向串行,现在并行了,每步省的就是那 2–10 毫秒。剩下的一点开销是每步多一次「上一步结果」的同步,和采样要等上一步处理完才能发射(因为约束解码的下一个掩码依赖上一步的 token)。

进批的顺序和数量走另一条线。顺序由排队策略定,默认先来先服务,按命中长度排要手动开,队列超过 128 条自动退回(04 章)。数量由准入预算定:可用显存加可驱逐的树节点,减去在跑的请求还要长的部分。「还要长多少」是估的:用户给的 `max_new_tokens` 乘一个比例,比例从 0.7 起步,每一步没抢占就往下减一点,600 步减到 0.1,一旦抢占就按被踢请求的实际长度重新估一个更高的值,服务空闲时归位到 0.7。这个比例就是 `--schedule-conservativeness` 拧的量。

一步只做一件事:有能进的新请求就先算 prefill,没有才算 decode。长 prompt 按块切,每块的大小按显卡定在 2048–8192 之间;要让 prefill 和 decode 同批得手动开混合模式。

## 三、代价

- **结束的请求多跑一步。** CPU 判断某个请求结束时,GPU 已经在算下一步了,这个请求在下一批里还占一行,多生成的那个 token 和格子在收尾时释放。每个请求一生浪费 1 步 decode 的算力和 1 个 KV 格子。
- **抢占也晚一步。** 显存不够的判断在 CPU 上做,做完那一步前向已经发出去了。SGLang 的应对是抢占后多留 20 步的量(03 章)。
- **有些功能关掉重叠。** 流水线并行、扩散语言模型、Mamba 混合模型的无缓冲树策略、CPU 上的推测解码、稀疏头 embedding、苹果 mps 设备,这几种情况自动关,日志里一行 warning。约束解码配推测解码时,每个 decode 步前要先同步上一步的状态,那一步不重叠。两个连续的 prefill 批之间可以用环境变量关掉重叠,换第一批的 TTFT。
- **一步只做一件事的另一面。** prefill 优先意味着来一个长 prompt,在跑的 decode 都要等它这一块算完,TPOT 有一根和块大小成正比的毛刺。混合模式能抹平,但不支持返回 logprob 的请求和 beam search。
- **估计会错。** 比例是全局一个数,同时服务短回答和长回答的负载时,它对谁都不准;错的方向由保守度决定。

## 四、和 vLLM 不一样的七处

1. **重叠默认开。** vLLM 的异步调度是实验性开关,默认关。SGLang 默认开,自动关的情况在上一节。
2. **一步只做一件事。** vLLM 没有阶段概念,prefill 块和 decode 天然同批。SGLang 默认一步要么 prefill 要么 decode,prefill 优先;同批要开 `--enable-mixed-chunk`。
3. **预算只管 prefill。** vLLM 的 `max_num_batched_tokens` 是每步所有 token 的总额,decode 也算在内。SGLang 的两个预算(`--max-prefill-tokens` 每批、`--chunked-prefill-size` 每块)只数 prefill 的 token,decode 不占预算,能进多少 decode 由显存和 `--max-running-requests` 定。
4. **准入靠估。** vLLM 只看当前这一步的块够不够。SGLang 把每个在跑请求「还会长多少」算进去,比例自适应,所以 `token usage` 不到 0.9 时可能是估得太保守而不是显存不够。
5. **抢占谁。** vLLM 踢最后进来的。SGLang 踢已生成最少、prompt 最长的,再多留 20 步的量(03 章);开优先级后可以改成先踢低优先级。
6. **排队策略。** vLLM 先来先服务或优先级。SGLang 8 种,默认先来先服务,按命中长度排要手动开、队列超过 128 条自动退回(04 章);优先级要单独开关,而且只能配先来先服务或按输出长度排。
7. **优先级有阈值和插队踢人。** vLLM 的优先级只影响顺序。SGLang 开优先级后默认允许抢占:新请求比在跑的高出 10 以上才能踢它;等待队列满了先踢队里优先级最低的而不是拒绝新来的;显存不够时的抢占也可以按优先级。

## 五、调参与观测

**参数在哪调。** 这一页的参数几乎全是启动参数,改了要重启;比例的起点、衰减、抢占预留、两个超时是环境变量,也要重启。请求参数只有一个 `priority`。运行时没有能改调度的接口,`/set_internal_state` 改不了这里的任何一项。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--disable-overlap-schedule` · 关掉 CPU 与 GPU 重叠 | 启动 | 关(重叠开着) | 关掉:每步多 2–10 毫秒,吞吐和 TPOT 变差;只在排障或某个功能不兼容时关 | 启动日志有没有「Overlap schedule is disabled」;`Decode batch` 行 `gen throughput` |
| `--chunked-prefill-size` · 长 prompt 一块算多少 | 启动 | 按显卡 2048–8192;DP attention 下再除以 dp 数 | 调小:prefill 激活小、decode 毛刺短、长 prompt 的 TTFT 变长;设 -1 关掉分块,长 prompt 整条进 | 就绪前日志 `chunked_prefill_size` |
| `--max-prefill-tokens` · 一批 prefill 最多多少新 token | 启动 | 16384,不小于模型上下文 | 调小:一批进的请求少,同源请求可能分到两批,批内查重失效;调大:一批更满,激活更大 | `Prefill batch` 行 `#new-seq` 与 `#new-token` |
| `--enable-mixed-chunk` · prefill 块和 decode 同批 | 启动 | 关 | 开:长 prompt 进来时 decode 不停,TPOT 毛刺消失,每步 prefill 预算减去 decode 的 token;要 logprob 或 beam 的请求不混 | 日志里 forward mode 是否出现 mixed |
| `--schedule-policy` · 等待队列按什么排 | 启动 | fcfs | 8 种;有共享前缀的负载换 lpm(04 章);priority 不是这个参数的值,要用下一行 | `#cached-token` |

| `--prefill-max-requests` · 一批 prefill 最多几条 | 启动 | 不限 | 限条数不限 token;大量短 prompt 时压住一批的启动开销 | `#new-seq` |

| `--priority-scheduling-preemption-threshold` · 高出多少才能踢人 | 启动 | 10 | 调高:插队更难,在跑的更稳;调低:高优先级 TTFT 更好,重算更多 | `Retract requests` 行的频率 |
| `--disable-priority-preemption` · 优先级只排队不踢人 | 启动 | 关(能踢) | 关掉抢占后优先级只影响进批顺序 | 同上 |
| `--retraction-policy` · 显存不够先踢谁 | 启动 | length | priority:先踢低优先级,同级再按长度 | 被踢请求的优先级分布 |
| `--enable-prefill-delayer` · DP attention 下等各卡一起 prefill | 启动 | 关 | 开:某张卡有 prefill 而别的卡没有时最多等 30 步,等到大家都有再一起算;要重叠开着 | `/metrics` 里 delayer 的直方图 |

| `--prefill-delayer-token-usage-low-watermark` · 使用率低于多少不等 | 启动 | 不设 | 显存用得少时直接放行,不等 | 同上 |

| `SGLANG_REQ_RUNNING_TIMEOUT` · 运行超过多少秒作废 | 环境变量 | 关 | 秒数;在跑的请求再跑 1 步后收 503 | `Request running timeout reached` |
| `SGLANG_DISABLE_CONSECUTIVE_PREFILL_OVERLAP` · 两个连续 prefill 批不重叠 | 环境变量 | 关 | 开:第一批的 TTFT 更好,吞吐略降 | 连续长 prompt 的 TTFT |
| `SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_BUSY` · 每步查显存账 | 环境变量 | 0 | 1:静默记录,漏了才打印;2:每步打印;查到不平直接断言 | `[Mem Check (BUSY)]` 行 |

**怎么看。** `Prefill batch` 行多了 `#new-seq` 和 `#pending-token`,前者是这批进了几条,后者是分块中还没算完的 token 数;`Decode batch` 行看 `#running-req` 和 `#queue-req`。抢占的 warning 行里 `#new_token_ratio: 0.5 -> 0.9` 这一对数是比例前后值,右边贴着 1.0 说明估计已经封顶,再抢占就只能减并发。`/metrics` 开了之后有被踢请求数、prefill delayer 的等待直方图、每步是否走 CUDA graph。就绪前那一行的 `chunked_prefill_size` 和 `max_prefill_tokens` 是实际生效值,DP attention 下前者已经被除过。

|---|---|---|
| 小模型吞吐远低于预期,GPU 利用率 60–70% | 启动日志有没有「Overlap schedule is disabled」 | 找出关掉它的功能;流水线并行换张量并行 |
| 长 prompt 一来 TPOT 就一根刺 | `chunked_prefill_size` 与是否开混合 | 调小块或开 `--enable-mixed-chunk` |
| 长 prompt 的 TTFT 太长 | 块太小,或 DP attention 把它除过 | 调大块;DP 下显式指定 |
| 抢占频繁且 `#new_token_ratio` 贴着 1.0 | 估计已经封顶 | 减 `--max-running-requests`,不再动保守度 |
| `token usage` 低且队列长 | 保守度;`SGLANG_CLIP_MAX_NEW_TOKENS_ESTIMATION` 是否被客户端的大 `max_new_tokens` 撑满 | 保守度 0.3(03 章);或让客户端给真实的 `max_new_tokens` |
| 带 `priority` 的请求被拒 | `--enable-priority-scheduling` 没开而 `--abort-on-priority-when-disabled` 开了 | 开优先级或去掉字段 |
| 高优先级请求还是排队 | 差值不到 10,或 `--disable-priority-preemption` | 调阈值;或接受只排队 |
| 请求收到 503 | 两个超时环境变量 | 看是排队超时还是运行超时 |
| DP attention 下有的卡空转 | 各卡 prefill 不同步 | 开 `--enable-prefill-delayer` |
| 服务空闲时报 memory leak | 空闲自检发现账不平 | 开 busy 检查定位是哪步漏的;报 issue |
| 一步卡住 300 秒后进程消失 | watchdog | 先用 `--soft-watchdog-timeout` 拿现场 |

## 六、常见误区

- **看到重叠调度就以为 CPU 在预测 token。** 人们以为要重叠就得猜下一个 token。实际上 CPU 什么都不猜,它只知道每个请求的格子号,token 由 GPU 自己写自己读,CPU 在同一时刻处理的是上一步的结果。
- **以为 SGLang 和 vLLM 一样每步都是混合批。** 因为 vLLM 默认混批,大家默认引擎都这样。SGLang 默认一步只做一件事,而且 prefill 优先;decode 被长 prompt 打断的毛刺就来自这里,开 `--enable-mixed-chunk` 才混。
- **把 `--max-prefill-tokens` 当成 vLLM 的 `max_num_batched_tokens`。** 名字像。SGLang 这个只数 prefill 的新 token,decode 不占预算,所以调它对并发和 decode 一点影响都没有。
- **以为 `--schedule-policy priority` 能开优先级。** 参数里没有这个值。优先级是单独的 `--enable-priority-scheduling`,而且开了之后策略只能是 fcfs 或 lof。
- **以为默认按命中长度排队。** 文档和早期版本给人的印象是 lpm 是默认。这个基准上默认是 fcfs,想要缓存感知排队要显式指定。
- **以为保守度直接是「预留多少」。** 它是比例起点的乘数,起点 0.7 乘它,下限和衰减都跟着起点走;而且 DP attention 下启动时已经悄悄乘了 0.3,再手动调低就叠上去了。
- **调 `--num-continuous-decode-steps` 想减少调度开销。** 参数还在,这个基准上调度器没有任何一处读它,调了等于没调。
- **以为被抢占的请求和 vLLM 一样回队首。** 回的是等待队列,带着「被踢过」的标记,下一轮按策略重排,不保证先进。
- **以为等待超时会把请求静默丢掉。** 不会,客户端收到 503 和明确的消息;运行中的请求还会多跑 1 步再释放,日志里看到它「结束后还在跑」是正常的。
- **以为空闲时的 memory leak 报错是误报,重启了事。** 空闲自检是账本级的:可用加可驱逐加锁定加会话持有等于总量,不平就是某条路径漏释放。默认它直接抛错,重启只是把账清零,下次还会漏。
- **DP attention 下手动把块调回 8192。** 启动时块已经按 dp 数除过,就绪前日志里的数才是每张卡实际的块。手动指定的值同样会被除。
- **以为关掉重叠能让答案更稳定。** 重叠不改变 token 的值,只改变 CPU 处理它的时机。确定性要看 13 章,和这个开关无关。
