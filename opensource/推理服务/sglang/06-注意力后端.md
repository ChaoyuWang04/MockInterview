# SGLang 06|注意力后端

attention 为什么没有一份能通吃所有硬件和模型的 kernel、后端和每步元数据怎么分工、MLA 为什么要另起接口,vLLM 解读的「注意力后端」一章已经讲透(「一个 kernel 通吃不了所有硬件和模型」与「选择与注册」两部分)。这一页只说 SGLang 遇到的问题、它的解法、代价、以及和 vLLM 不一样的地方。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

注册表里 23 个后端,命令行 26 个名字(2 个是废弃别名)。分四个维度:硬件(NVIDIA 的 Ampere、Hopper、Blackwell 又分 SM100 与 SM120,AMD,昇腾,Intel 的 XPU 与 CPU,摩尔线程,苹果 mps)、模型结构(普通多头注意力 MHA,DeepSeek 把 KV 压成一个向量的 MLA,DeepSeek V3.2 那种先挑 top-k 再算的稀疏注意力 DSA,Qwen 3.5 那种线性层与全注意力层交错的混合模型)、KV 精度(bf16、FP8、FP4)、阶段(prefill 与 decode 的 kernel 不同,有的后端只会 decode)。

选错的后果不一样:选了这张卡不支持的,启动时直接报错;选了要按页取 KV 的,页大小被改成 64,前缀命中退到页边界(03 章);Hopper 上手动指定 flashinfer,decode 会比默认慢,因为这个基准上它有已知回退;开了 FP8 KV 但后端不做融合反量化,槽数翻倍、TPOT 反而变长(12 章)。

## 二、解法:一个名字一个类,启动时定死

最天然的直觉是:每个后端一个类,类里同时有 prefill 和 decode 两套 kernel,启动时按「什么卡、模型是不是 MLA、开没开推测解码、页多大」挑一个名字,之后不再换。SGLang 就是这么做的。注册表是名字到工厂函数的字典,工厂函数当场断言硬件和模型结构(fa3 要求 SM80 到 SM90,trtllm_mla 只给 MLA 模型,hpc_ops 不支持推测解码),不满足就抛错。

默认怎么选是一棵决策树,不是优先级表。MHA 模型:Hopper 且 CUDA 12.3 以上选 fa3,除非推测解码 topk 大于 1 或页大于 1;Blackwell SM100 选 trtllm_mha,KV 头不对称的模型改 fa4;AMD 选 aiter;苹果 mps 选 torch_native;其余有 flashinfer 且模型没有 attention sink 就 flashinfer,否则 triton。MLA 模型:Hopper 选 fa3,SM100 选 flashinfer,AMD 上 KV 头数是 16 或 128 选 aiter 否则 triton,其余 triton。个别模型有自己的钦定(Step3p 在 Blackwell 上 fa4、Hopper 上 fa3;HRM-Text 强制 triton;扩散语言模型强制 flashinfer)。开确定性推理时走另一棵树:Blackwell 上非 DeepSeek 选 flashinfer、DeepSeek 选 triton,Hopper 选 fa3;手动指定的不在 6 个确定性后端里直接报错(13 章)。

选完之后还有一串修正:页大小按后端要求改写(flashmla 改 64,trtllm_mla、tokenspeed_mla、cutedsl_mla 不是 32 或 64 就改 64,trtllm_mha 不是 16、32、64、128 就改 64,hpc_ops 改 64,fa4 配非 MLA 模型在 SM100 上改 128),每次改写打一行警告;fa3 配 fp8_e5m2 静默换成 triton;cutedsl_mla 只会 decode,prefill 侧自动填 trtllm_mla;Intel 平台没有对应指令集就退回 torch_native 或 triton。

三个参数的关系:`--attention-backend` 是底,`--prefill-attention-backend` 和 `--decode-attention-backend` 各自覆盖一个阶段,没指定的阶段继承底;两个都指定且相同就直接当底;不同就套一层分发器,按这一步的模式转发:decode 和空转给 decode 后端,推测解码的 verify 按 `--speculative-attention-mode` 定(默认 prefill 侧),其余给 prefill 后端。混合模型、稀疏模型再在外面包一层:GDN、Mamba2、KDA、短卷积、MiniMax 稀疏各有自己的包装类,把选出来的全注意力后端当成员,线性层走自己的 kernel。

基类的接口就两件事。一是 `forward` 按模式转到 `forward_decode` 或 `forward_extend`,每层调一次;二是每次前向开头调一次 `init_forward_metadata`,把这批请求在槽位表里的行整理成 kernel 要的形状:FA3 把每行按页步长抽样再除以页大小得到页表,Triton 把每行拼成一条扁平的槽号列表加前缀和,并按序列长度和 SM 数当场算每条请求切几份。CUDA graph(把一步的 kernel 序列录下来重放)下这套元数据不能每步新分配:启动时 `init_cuda_graph_state` 按最大批和最大上下文一次买断(FA3 的页表是最大批乘最大页数,Triton 的中间结果缓冲是最大 token 数乘头数乘最大份数乘 V 维、fp32),每步重放前 `init_forward_metadata_out_graph` 在图外刷新这些缓冲,`init_forward_metadata_in_graph` 录进图里;batch 为 1 的推测解码还会把图外那段本身也录成一张小图,省掉每步 20–100 个小算子的 CPU 下发。

为什么实际不吃亏:选择只在启动时做一次,运行时零开销;元数据整理的形状和后端无关,换后端不改调度器;修正都有日志,不会不知道自己在跑什么。

## 三、代价

- **没有能力矩阵,约束散在 12 个修正函数和 3 个处理器里。** 一个组合行不行,要么启动报错,要么被静默改写后打一行警告,有的直到构造后端那一刻才知道(fa3 的 SM 断言、trtllm_mla 的 MLA 断言、hpc_ops 的推测解码断言)。
- **页大小被改写就丢了 token 级命中。** DeepSeek 在 flashmla 或 trtllm_mla 上命中只到 64 的倍数(03 章)。
- **确定性模式限定 6 个后端,其中 flashinfer 和 intel_xpu 还要关掉前缀缓存。**
- **后端私有缓冲吃显存。** Triton 的中间结果缓冲是最大 token 数乘头数乘最大份数乘 V 维、fp32,MLA 模型在 AMD 上份数会算到 256、缓冲到 4 GB,所以钉在 256;FlashInfer 工作区默认 384 MB,Qwen2、Qwen3 系 512 MB,确定性模式 2 GB。
- **有的后端关功能。** torch_native 和 flex_attention 关 CUDA graph,flex_attention 不支持推测解码;aiter 在上下文超过 8192 时把显存比例乘 0.85。
- **prefill 与 decode 用两个后端是实验功能。** 启动打一行 warning,提示可能覆盖默认后端。

## 四、和 vLLM 不一样的七处

1. **怎么选。** vLLM 是候选优先级表加逐个校验,不行就试下一个,淘汰原因打 debug 日志。SGLang 是一棵决策树返回一个名字,没有候选循环,没有能力校验方法;显式指定就是它,不行要么报错要么被改写。
2. **prefill 和 decode 可以是两个后端。** vLLM 一个后端两个阶段都管。SGLang 三个参数,不同就套分发器按模式转发,推测解码的 verify 归哪边另有开关。
3. **元数据谁整理。** vLLM 的构造器是独立对象,每步把调度输出翻译成 kernel 参数。SGLang 由后端自己在每次前向开头整理,CUDA graph 下拆成图外刷新和图内录制两段,基类给了默认实现。
4. **页大小谁说了算。** vLLM 一直 16。SGLang 默认 1,后端要求就改成 32、64 或 128,只打一行警告(03 章)。
5. **混合模型怎么接。** vLLM 的状态空间类不参与选择。SGLang 在选出的全注意力后端外面包一层,线性层的 kernel 由 `--linear-attn-backend` 一族单独定,Blackwell 上全注意力后端还限定在 3 个里。
6. **稀疏注意力是一等后端。** vLLM 的稀疏 MLA 变体在优先级档里当场排序。SGLang 的 dsa 是一个后端名,内部再按显卡和 KV 精度选 prefill 与 decode 两个子后端,bf16 时 prefill 用 flashmla_sparse、decode 在 Blackwell 用 trtllm 在 Hopper 用 fa3,FP8 时 Blackwell 用 trtllm、Hopper 用 flashmla_kv,AMD 用 triton;nsa 是废弃别名。
7. **草稿模型另有一套。** 推测解码的草稿模型只允许 7 个后端,不在名单里退回 flashinfer(AMD 和 XPU 退 triton)并打警告;目标模型不受影响。

## 五、调参与观测

**参数在哪调。** 这一页的参数全是启动参数,改了要重启;后端内部的阈值是环境变量,也要重启。运行时没有能换后端的接口,`/set_internal_state` 改不了这里的任何一项。`/get_server_info` 读回的 `attention_backend`、`prefill_attention_backend`、`decode_attention_backend`、`page_size` 是修正之后的实际生效值。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--attention-backend` · 用哪套 kernel | 启动 | 按显卡与模型结构决策树 | 显式指定不做候选回退:卡不支持直接报错;要求页大小的后端会改写 `page_size` | 日志 `Attention backend not specified. Use X backend by default`;`/get_server_info` |

## 六、常见误区

- **以为像 vLLM 一样有候选链,指定的后端不行会自动换下一个。** 人们从 vLLM 的日志里习惯了「被淘汰的候选」。SGLang 显式指定就是它:不匹配要么启动报错,要么被静默改成另一个并打一行警告,没有「下一个候选」。
- **以为 `--attention-backend` 决定了所有注意力层的 kernel。** 名字像。线性层另有 `--linear-attn-backend` 一族,DSA 另有两个子后端参数,多模态编码器另有 `--mm-attention-backend`;混合和稀疏模型是在选出的后端外面包一层,包装层自己不算注意力。
- **以为文档说的「Blackwell 默认 trtllm_mha」总成立。** 文档只写了主线。topk 大于 1、页大于 1、KV 头不对称(走 fa4)、SM120(走 flashinfer)都不走它。
- **以为 Hopper 上 flashinfer 比 fa3 快。** 早期版本确实默认 flashinfer。这个基准上 Hopper MHA 默认 fa3,注释写明是 flashinfer 0.6.1 在 Hopper 上的回归,修好之前不换。
- **以为 `--decode-attention-backend` 只影响 decode。** 推测解码的 verify 和草稿默认走 prefill 侧,要 `--speculative-attention-mode decode` 才走 decode 侧;CUDA graph 也只默认捕 decode 侧。
- **调 `--triton-attention-reduce-in-fp32` 想修 fp16 溢出。** 参数还在,帮助文本也还在。这个基准上没有任何 kernel 读它。
- **以为 `num_kv_splits` 是实际切几份。** 它是上限。实际按序列长和 SM 数当场算,确定性模式下按 256 的 tile 固定,AMD 默认 16 不是 8。
- **以为 nsa 是另一个后端。** 它是 dsa 的废弃别名,选了会打 DeprecationWarning;compressed 同理是 dsv4 的别名。文档矩阵里的 Cutlass MLA 这个基准上代码里没有。
- **以为 Ampere 不能用 fa3。** MHA 模型可以,工厂函数放行 SM80;MLA 模型不行。
- **以为确定性模式只改采样。** 它换默认后端、限定 6 个后端、DeepSeek 只剩 4 个、flashinfer 和 intel_xpu 上还关前缀缓存,还把 FlashInfer 工作区抬到 2 GB。
- **以为 DSA 模型要手动指定 dsa。** 按模型结构自动。但子后端由 `--kv-cache-dtype` 决定,改精度等于换 kernel,日志里那一行 `Set DSA backends` 最常被略过。
