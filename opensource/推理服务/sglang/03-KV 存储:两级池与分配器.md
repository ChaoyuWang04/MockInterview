# SGLang 03|KV 存储:一个 token 一个槽

vLLM 用 PagedAttention 解决了 KV cache 的碎片问题,SGLang 面对的是分页之后剩下的那个问题:**块粒度表达不了 RadixAttention 需要的共享形状**。多轮对话、agent 循环、RL rollout 的分叉点落在任意 token 上,而块粒度下命中止于块边界、分叉处要复制一块、树没法在块中间劈开。SGLang 的答案是把分配单位从 block 降到 token,地址表做成「每请求一行、每个位置一格」的稠密表,树的节点值直接就是槽号切片。这一章讲这个决定带来的一切:两级池长什么样、一个槽在显存里是什么、为什么页后来又回来了、能放多少、见底之后怎么办。

KV cache 为什么必须存在、缓存的只有 K 和 V、朴素管理的三种浪费、分页的思想,vLLM 解读的「PagedAttention 与 KV Cache 管理」一章已经讲透,本章只用它的结论和它的算例(Llama-3-70B、TP=8、FP16)。全章内容都在源码上逐条核对过;每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:分页之后还剩一个问题,块粒度表达不了共享的形状

### 1.1 一个 token 的 KV 值多少字节

缓存里存的是每个 token 经过每层 attention 的 K 和 V 投影向量,只增不改,内容完全由前缀 token 序列决定。Llama-3-70B、80 层、GQA 8 个 KV head、head_dim 128、FP16:每 token 整模型 320 KB;TP=8 时 KV head 被切开,**单卡每 token 40 KB**。本章后面所有的账都用这个数。

### 1.2 分页解决了碎片,没解决共享的形状

分页把「逻辑连续」和「物理连续」拆开之后,三种浪费里前两种没了,第三种「公共前缀存了很多份」也有了答案:多个 block table 指向同一块。但这个答案有一个前提,**共享的单位是块**。看真实负载的分叉形状:

| 负载 | 前缀是什么 | 分叉点在哪 |
|---|---|---|
| 多轮对话 | 系统提示词加整段历史 | 每轮末尾,位置随机 |
| agent 循环 | 工具说明加所有历史步骤 | 每次工具返回之后,位置随机 |
| RL rollout | 同一 prompt | prompt 末尾,64 条同时分叉 |
| RAG、few-shot | 文档或示例 | 用户问题之前 |

分叉点落在块内部时,块粒度下有三件事:

1. **命中止于块边界**。两个请求在第 N 个 token 分叉,只有完整的块算命中,分叉点所在的块整个作废。块大小 16、N=20 时命中 16 个,N=100 时命中 96 个;块大小 64 时 N=20 命中 0 个。
2. **分叉处要复制一块**。新请求要往分叉点之后写,但那一块被别人引用着,必须先拷一份再写,否则改坏别人的 KV。多轮对话每一轮都要拷一次。
3. **前缀树没法在块中间劈**。RadixAttention 的树把没有分叉的一段压成一个节点,新序列走到节点中间分叉时要把节点从那个位置劈成两半。节点的值如果是块号列表,劈开的位置必须落在块边界上,否则两半共用一块。

第 3 条是决定性的。SGLang 的调度、驱逐、缓存感知排序全建在树上(04 章),树要在任意 token 位置劈开,底下的存储就必须能在任意 token 位置切开。

### 1.3 SGLang 的答案:一个 token 一个槽,地址表是一张稠密表

把分配单位降到 token:显存里的 KV 池按「槽」编号,一个槽存一个 token 在所有层的 K 和 V;每个在飞的请求有一行地址表,行长等于最大上下文长度,第 i 格记第 i 个 token 的槽号。任意一格可以指向任意槽,任意位置可以切开。

| | 块粒度(vLLM) | token 粒度(SGLang) |
|---|---|---|
| 分配与共享的单位 | 一块 16 个 token | 一个 token |
| 命中粒度 | 块边界,N=20 命中 16 | 单个 token,N=20 命中 19(最后一个留给前向算) |
| 分叉处 | 复制分叉所在的那一块 | 不复制,新 token 分新槽 |
| 树在块中间劈 | 做不到,单 group 有断言钉死 | 节点值就是槽号切片,任意位置切 |
| 内部碎片 | 每请求最多 15 个 token | 0 |
| 地址表 | 每请求 ⌈L/16⌉ 个块号,约 134 MB | 每请求 max_ctx 个槽号,可达 2 GB |
| kernel 读 KV | 查块号加块内偏移,块内连续读 | 逐 token 查槽号,按槽号 gather |

前五行是收益,后两行是代价。这一章剩下的内容就是把这张表的每一行落到源码上。

## Part 2|两级池:请求到位置,位置到 KV

### 2.1 第一级:每个请求一行,每格一个槽号

第一级叫请求到 token 池(ReqToTokenPool)。它是一个 GPU 上的二维 32 位整数张量,行数是最大并发请求数加 1,列数是最大上下文长度。请求进来时从空闲行列表尾部弹一行,请求结束时把行还回去;每一行还配一个代数计数,每次被重新分出去就加一,异步路径上拿着旧行号的人先比代数,不一致就知道这行已经易主。

第 0 行是保留的。CUDA graph 要求批大小固定,不够的位置用假请求补齐,假请求的行号默认是 0,它们的读写全落在第 0 行,真实请求永远不用它。这样补齐的批不需要任何特判,源码注释把它叫 padding row。

一行里的格子彼此没有关系:第 999 格可以指向第 137 号槽,第 1000 格可以指向第 90000 号槽。前缀命中到第 1000 个 token 时,这一行的前 1000 格照抄缓存树里的槽号,第 1001 格开始才分新槽。

### 2.2 第二级:每层一对张量,槽号跨层通用

第二级叫 token 到 KV 池(TokenToKVPool)。它按层分,每一层各有一个 K 张量和一个 V 张量,第一维就是槽号,后两维是 KV 头数和头维度。按 1.1 的模型,单卡每层的 K 张量是 [槽数 + 1 页, 1, 128] 的 FP16,一个槽在一层占 256 B 的 K 加 256 B 的 V,80 层合计 40 KB。**槽号在所有层通用**:一个 token 在第 0 层用第 137 号槽,在第 79 层也用第 137 号槽,所以第一级只需要记一个数。

槽总数是启动时算出来的(Part 3),再加一页。多出来的那一页从第 0 号槽开始,和第一级的第 0 行一样是给假请求写垃圾用的,注释叫它 padded page。

### 2.3 树的节点值就是槽号切片:劈开不复制,命中到 token,碎片为 0

两级拆开之后,前缀树(04 章)的节点值可以直接是「这一段 token 对应的槽号张量」,键是 token 序列,两者等长对应。新序列走到某个节点,公共长度短于节点键的全长,就把节点从公共长度处劈成两段:前半段接在原位,后半段成为它的孩子,两半各拿原值张量的对应切片。**KV 一个字节都不动,动的只是树。** 命中的槽号照抄进新请求的行,新 token 分新槽,任何时候不会往别人的槽里写,所以分叉处没有复制。

命中粒度跟着变成 token:两条序列前 N 个 token 相同,就命中 N 减 1 个(最后一个 token 留给这次前向,要拿它算 logits)。内部碎片跟着变成 0:请求占的槽数就是它的 token 数,没有「最后一块没填满」这回事。

请求结束时,分配层不决定槽的去留,把请求交给树,树决定哪一段留下当前缀缓存、哪一段直接回收。分配层只负责把请求的行还给第一级。

### 2.4 代价:一张按最大值买断的表,和一次 gather

第一级每格 4 字节,行数乘列数,按最大值一次分配,不随实际长度伸缩。用 Part 3 会算出来的默认行数 4096:上下文 8192 时这张表是 134 MB,上下文 131072 时是 2 GB。**跑短请求也是 2 GB,因为列数按最大上下文买断;跑长上下文也是 2 GB,因为行数按最大并发买断。** 块表同样条件下记的是块号,131072 除以 16 再乘 4096 个格,约 134 MB,差 15 倍。对 51.5 GB 的 KV 预算,2 GB 是 4%,这是 token 粒度的显存价格。

第二笔代价在 kernel。块粒度下 kernel 查一次块号就能连续读 16 个 token;token 粒度下 kernel 拿到的是一行槽号,要按槽号 gather。各注意力后端每步开始时从第一级把本批请求的行取出来,整理成自己要的格式,有的要页表,有的要扁平索引,这一步在 06 章。这也是为什么页后来又回来了,Part 3 讲。

## Part 3|一个槽在显存里长什么样,以及能放多少

### 3.1 每层一对张量:NHD 默认,HND 给按页读的 kernel

第二级每层的 K 张量有三种物理排布可选。默认 NHD,形状 [槽, 头, 维],一个槽就是一行,同一个 token 的所有 head 连续。写入是按槽号散射:前向算完一层的 K 和 V,按本批的槽号一次 index_put 写进去,NHD 下一个 token 的全部 head 落在一段连续内存里,和 vLLM 默认 LBNHC 的理由一样。HND 形状 [页, 头, 页内位置, 维],把页和头折成一个索引,让按头分页读的 kernel 直接消费。AMD 上还有一种向量化的五维排布,只有 AITER 后端认。排布在池构造时定死,kernel 看到什么形状取决于它。

FP8 精度的 KV 按无符号 8 位整数存,取出来再看成 FP8,原因只是 PyTorch 的按索引写入不支持 FP8 张量。

### 3.2 页为什么又回来了:后端钉页,命中粒度跟着退

page_size 不填默认 1,一个槽就是一页,分配器是一个空闲槽号张量,分配切走前面 n 个,回收拼到后面。这是 SGLang 的本来形态。

页大于 1 从来不是用户选的,是 kernel 要的。FlashMLA 和 HPC-Ops 只认 64;TensorRT-LLM 的 MLA、tokenspeed、CuteDSL 三个 MLA 后端只认 32 或 64;TensorRT-LLM 的 MHA 认 16 到 128。选了这些后端,启动时配置层把 page_size 改过去,打一行警告。这时分配器换成分页分配器,空闲列表里放页号,分出去的槽号总是页对齐的整段;prefill 和 decode 各一个 Triton kernel 整批分配,prefill 把每个请求要新分的 token 分成「填上一页剩下的空位、整页取、尾页取」三段,decode 只在跨页边界时取新页。调 kernel 之前按「每个请求一张新页」高估需求,先问缓存树要空间,不够就驱逐,因为 kernel 跑起来没有回头路。

**页一回来,1.3 那张表右边一列就往左边退**:命中粒度退到页边界,64 的页最坏丢 63 个 token;内部碎片回来,每请求平均浪费半页,4096 并发下是 131072 个槽,按 1.1 的 40 KB 是 5 GB,按 DeepSeek 的 70 KB 是 9 GB;整页回收,一页里只要还有一个 token 在用整页不能还。用 DeepSeek 这类 MLA 模型跑主流后端,实际上都在按页分。命中率比预期低,先看启动日志里 page_size 有没有被改。

### 3.3 池家族:模型结构决定槽里装什么

今天的模型把 MHA、MLA、滑动窗口、Mamba、稀疏索引几种层混在一起,槽里装的东西各不相同。第二级因此是一个家族,启动时按模型结构挑一种,分配、写入、回收接口全家一样,第一级和调度器不知道底下是哪种池。

| 池 | 一个槽在一层存什么 | 每 token 字节(FP16) | 什么模型用 |
|---|---|---|---|
| MHA 池 | 一份 K 和一份 V,头数乘头维 | 2 × 头数 × 头维 × 2 | Llama、Qwen |
| MLA 池 | 一个向量,潜向量维加 RoPE 维;V 是它的前一段视图 | (潜向量维 + RoPE 维) × 2,DeepSeek-V3 是 576 × 2 = 1152 B 每层 | DeepSeek V2 / V3 |
| DSA 池 | MLA 池再加一份索引器缓存 | 上一行加索引器 | DeepSeek V3.2 |
| 滑动窗口混合池 | 两个子池,全注意力层一个,窗口层一个,各自计数 | 只数全注意力层 | Gemma |
| 线性混合池 | 全注意力层一个 KV 池,加按请求分槽的状态池 | KV 只数全注意力层,状态另算 | Qwen3-Next、Nemotron |
| MiniMax 稀疏池 | 主池加索引器池 | — | MiniMax |
| FP4 / MXFP8 池 | 数据加缩放因子 | 数据加缩放 | 开低精度 KV 时 |

写入位置捆成一个结构体,除了主位置还带窗口子池位置和全注意力子池位置,后端发一次写入调用,底下是哪种池它不管。窗口层的槽在 token 滑出窗口时就回收,不等请求结束,监控里窗口子池使用率在请求中途下降是设计不是泄漏。Mamba 层每个请求一份固定状态,混合模型每个请求取一行的同时再从状态池取一个槽,状态池的槽数独立配置。

### 3.4 显存里能放多少槽:启动时量一次

槽总数不是用户配的,由显存占比间接决定,启动时算一次。用 vLLM 那一章同一台机器(8 张 H100 80 GB,Llama-3-70B,TP=8):

| 步 | 做什么 | 本例 |
|---|---|---|
| ① | 模型装载完量一次剩余显存 | 80 − 17.5 = 62.5 GB |
| ② | 减运行期余量:装载前总显存 × (1 − mem_fraction_static),比例取 0.86(举例,默认值按显卡启发式给) | 80 × 0.14 = 11.2 GB |
| ③ | 多模态模型再减一块给编码器 | 0 |
| ④ | 剩下全给 KV | 51.3 GB |
| ⑤ | 除以每 token 字节,向下页对齐 | 51.3 GB ÷ 40 KB ≈ 130 万个槽 |
| ⑥ | 最大并发:槽数 ÷ 上下文 × 512,夹在 2048 到 4096 | 上下文 8192:81000 → 4096 |
| ⑦ | 第一级按 ⑥ 的行数分配 | 4096 × 8192 × 4 B = 134 MB |

三点要说清。**mem_fraction_static 不是「KV 占多少」,是「权重加 KV 一共占多少」**,② 减掉的是总显存乘以 1 减比例,同一个比例换更大的模型给 KV 的就更少;余量留给激活和 CUDA graph,它们才是运行中真正会向 CUDA 要显存的人,④ 之后 KV 层不再向 CUDA 要任何东西。② 算出来小于等于 0 启动直接报错,错误信息里算好最小可行的比例。运维上判断比例合不合适看就绪前日志的剩余显存,5–8 GB 合适,高于 8 GB 往上加,每次 0.01。

⑤ 之后还有三道上限,只能往下压:用户给的 max_total_tokens 给高了打警告用探测值;流水线并行各段层数不同取最小;Mamba 状态池另外分账。没有任何参数能把槽数调到探测值以上,想要更多槽只有调高比例、开 FP8 KV、换 MLA 模型三条路。

⑥ 这一步决定的行数就是 2.4 那张表的大小,也是并发的一道闸。**多数短上下文部署的并发卡在这里,不在显存**:本例 130 万个槽、上下文 8192,槽数的一半是 65 万,行数却封在 4096。要跑到 4096 以上必须显式指定,代价是第一级按比例撑大。上下文 131072 时反过来,估计行数夹到 2048,但 130 万个槽平均每请求只有 635 个,并发到不了 2048 就被槽数封死。Mamba 混合模型再多一道:开前缀缓存时每个请求占三份状态槽(树上留一份、在算一份、乒乓一份),并发上限是状态槽数除以 3,日志会明说「capped by the mamba state cache」。

$$\text{并发} = \min\left(\frac{\text{槽数}}{2},\ \text{第一级行数},\ \frac{\text{状态池槽数}}{3}\right)$$

## Part 4|显存见底之后:先驱逐,再抢占,踢丢工作最少的

### 4.1 见底的一步

decode 每步给每个在飞请求分一个新槽,槽是线性减少的,总有一步分不出来。每步 decode 之前,调度器问分配器下一步要的槽数够不够:分配器先让缓存树把没人引用的前缀驱逐掉,再比空闲槽数;还不够就抢占,把在飞请求从批里踢出去直到空间够。**踢谁:已经生成的 token 最少的先被踢**,同样少的话 prompt 更长的先被踢,也就是踢丢掉的工作最少的那个。开了优先级调度先按优先级,再按这个。批里至少留一个请求。

被踢的请求释放全部 KV,不插进缓存树(注释说要立刻腾空间),重新排队从头 prefill;它的 prompt 前缀多半还在树上,重算的只是分叉之后的部分。**默认不备份**,只有 decode 分离节点例外:它没有 prefill 能力,踢了没人能算回来,所以把 KV 备份到 host 再释放,恢复时拷回来,备份放不下就只能中止请求。5000 个 token 乘 40 KB 是 200 MB,PCIe 4 代按 20 GB/s 算 10 毫秒,比重算便宜一个量级,代价是 host 内存。

抢占够了空间之后还多驱逐一点:按剩余请求数乘一个步数,默认 20,给接下来 20 步 decode 预留。没有这一条,踢完刚好够这一步,下一步又短缺又踢,系统在抢占里打转。vLLM 用 watermark 解决同一个问题,思路不同:watermark 是 running 相对 waiting 的优先级,SGLang 是踢完多留几步。

抢占循环收敛在同一个判断上,所以 decode 侧的短缺一定走抢占,不会走到分配失败抛错。**分配失败抛错只发生在 prefill 侧,而且是故意的**:prefill 取行失败说明准入闸门(02 章)算错了,错误信息让人调小最大并发;取槽失败先把缓存树打印出来再让人调小 batch。两种都不静默回退,静默回退会把闸门的 bug 藏到永远查不出来。

### 4.2 抢占频繁是准入太松,不是显存太少

日志里「KV cache pool is full. Retract requests」每分钟一次以内是正常的。频繁出现,先把调度保守度调大到 1.3 左右,让准入闸门估计输出长度时更悲观;反过来 token 使用率总在 0.9 以下、队列却有请求在等,调小到 0.3 左右。先调这个,再考虑减并发,减并发是把抢占换成排队。

## Part 5|图解

### 5.1 两级池与两个请求的共享

```text
  第一级 ReqToTokenPool(行 = 请求,列 = 位置,格 = 槽号;int32,GPU 上)
  行 0 [ 0    0    0    0   ... ]              <- padding row,假请求落这里
  行 1 [ 137  138  139  901  902  903 ... ]    <- 请求 A:前 3 格是命中的前缀槽
  行 2 [ 137  138  140  141  ... ]             <- 请求 B:与 A 共享前 2 格,第 3 格分叉,不复制

  第二级 TokenToKVPool(每层一对张量,第一维 = 槽号;槽 0 所在页是 padded page)
  层 0   K [槽 0 | 槽 1 | ... | 槽 137 | 槽 138 | ... ]   V 同形状
  ...
  层 79  K [ ...                                      ]   V ...

  槽 137 在 80 层各占 256 B 的 K 和 256 B 的 V,合计 40 KB(Llama-3-70B,TP=8,FP16)
```

### 5.2 树的节点值就是槽号切片

```text
  树节点:键 = token 序列,值 = 槽号张量,等长对应
  节点 X:键 [t0 t1 t2 t3 t4 t5]   值 [137 138 139 901 902 903]

  新序列 [t0 t1 t2 u3 ...] 走到 X,公共长度 3,在节点中间分叉:
  劈开 → X 前半:键 [t0 t1 t2]  值 [137 138 139]
         X 后半:键 [t3 t4 t5]  值 [901 902 903]   (成为前半的孩子)
         新分支: 键 [u3 ...]    值 [新槽 ...]      (新 token 分新槽)
  KV 一个字节不动;块粒度下这一步要复制第 3 个 token 所在的那一块
```

### 5.3 见底的一步

```text
  每步 decode 前:需要 n 个槽
       │
       ├─ 缓存树驱逐无人引用的前缀 ──> 空闲 ≥ n ? ──是──> 分配,继续
       │                                  │否
       ▼                                  ▼
  抢占:按「输出最少、prompt 最长」排序,从尾部踢,直到够
       ├─ 单机:释放全部 KV,不进树,重排队
       └─ decode 分离:备份到 host 再释放;备份失败中止
       │
       └─ 再多驱逐 (剩余请求数 × 20) 个槽,防下一步又抢占

  prefill 侧不走这里:取行失败 / 取槽失败 = 准入算错,直接抛错
```

## Part 6|机制之外:源码里额外读到的

### 6.1 五处静默读错的防线

KV 存储层最坏的事故不是 OOM,是读到了不属于这个请求的 KV:注意力照常算,采样照常出字,指标全正常。源码里有五处专门的防线,每一处对应一种读错。行还回去又分给别人,防线是 2.1 的代数计数。三层缓存逐层加载和 PD 逐层传输时第 3 层到了第 20 层还在路上,防线是取某一层张量的接口上挂一个按层计数器,读第 i 层先等第 i 层到齐,注释明说这个接口只给注意力后端用。CUDA graph 补齐的假请求写 KV,防线是 2.1 和 2.2 的垫片行与垫片页。推测解码的草稿被拒,防线是每个请求记两个长度,已分配的和已提交的,验证通过才提交,结束时多分未提交的尾巴整页回收,树只收提交过的那段。RL 换了权重旧 KV 没换,防线是权重更新接口的清缓存开关,开着就把整棵树清空,失败直接断言。

### 6.2 RL 训推一体:整池释放只能在空闲时

训练框架把推理引擎和训练进程放在同一批卡上,训练那一段要把推理侧的显存让出来。释放接口按 KV 缓存、权重、CUDA graph 三类标签分别处理;释放 KV 时先清空缓存树,PD 分离节点还要先清传输队列和预分配队列,再让显存保存器暂停这一块。接口断言服务完全空闲才能调,有请求在飞直接失败。恢复按相反顺序。这条路要开 enable_memory_saver。

### 6.3 PD 分离的两条额外要求

prefill 节点算完要把 KV 传给 decode 节点,传输按槽号段发,槽号越连续段数越少。所以 PD 模式下回收的槽号不直接归还,先攒进暂存区,不够用时合并排序再用;单机不排,因为没人按段传输。开了 NVLink 传输时 KV 张量从一个自定义显存池里分,让传输引擎能直接注册这块内存。

### 6.4 三个小动作

回收可以分组:先开一个组,期间所有回收只记下来,组结束时一次拼接一次回收,调度器处理一批请求的结束时把 10–50 次小回收压成一次。有一种可选模式让 KV 池先只保留一段虚拟地址上界,等 CUDA graph 捕获完、知道激活实际占多少之后再补物理页,槽数这时向上对齐到页边界。可选的统一池把整个预算当一块字节缓冲,子池从两端往中间长,哪种层用得多哪个多占,代价是虚拟槽号加一张映射表,默认不开。

## Part 7|对比与决策

### 7.1 token 粒度换来了什么,付了什么

| 维度 | 块粒度(vLLM) | token 粒度(SGLang) |
|---|---|---|
| 命中粒度 | 块边界;混合模型可让 prompt 尾部一个边界命中 | 单个 token,减 1 |
| 分叉 | 复制分叉所在的块 | 不复制 |
| 树在任意位置劈 | 不能 | 能,节点值就是槽号切片 |
| 内部碎片 | 每请求最多 b − 1 | 0;后端钉页后回到 b − 1 |
| 地址表 | 块数级,约 134 MB | 并发 × 上下文,可达 2 GB |
| kernel 读 | 查块号,块内连续读 | 逐 token gather;要页的 kernel 用 HND |
| 显存预算 | 按比例给 vLLM 全部,探测激活后剩下给 KV | 权重加 KV 占比例,余量按公式扣 |
| 见底 | 抢占重算;watermark 管准入 | 抢占重算,多留 20 步;decode 分离节点备份到 host |
| 抢占顺序 | 见 vLLM 调度器章 | 输出最少的先踢 |

两边都是「逻辑连续、物理离散」,差别全在粒度。vLLM 把粒度定在块,换来小表和天然对齐;SGLang 把粒度定在 token,换来树需要的任意位置切开,代价是表大和每次读多一跳。哪边划算取决于负载:分叉点随机、前缀长、多轮的负载偏向 token 粒度;单轮短请求、不开前缀缓存的负载,那 2 GB 是纯开销,应该把最大并发压到实际需要的数。

### 7.2 这张卡能撑多少并发:token 粒度下少了 b − 1

设 KV 可用显存 M、单卡每 token 字节 p、请求平均长度 T,块粒度下每请求占 T + b − 1 个槽,token 粒度下就是 T:

$$N_{\text{token}} = \min\left(\left\lfloor \frac{M}{T \times p} \right\rfloor,\ \text{第一级行数}\right)$$

本例 M 51.3 GB、p 40 KB、T 1024:显存允许约 1300 个请求,和块粒度算出来的 1300 几乎一样,分页的收益 token 粒度全部继承,多出来的只是那 b − 1。真正不同的是第二项:**行数默认封在 4096,而且短上下文下它比显存先到顶**。这个数字的意义和 vLLM 那一章一样,是「KV cache 不再是瓶颈」,实际并发还被准入闸门和计算吞吐卡住。

### 7.3 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| mem_fraction_static | 按显卡启发式 | 权重加 KV 占显存的比例 | 就绪前日志剩余显存高于 8 GB 往上加,每次 0.01;5–8 GB 合适 |
| max_total_tokens | 探测值 | 槽总数上限 | 只能往下压;复现某个并发上限时用 |
| max_running_requests | 按槽数推,2048 到 4096 | 最大并发,也是第一级的行数 | 短上下文并发想超 4096 时显式指定;抢占频繁时调小 |
| page_size | 1 | 分配粒度 | 不要手调,后端会改 |
| kv_cache_dtype | auto | KV 精度 | FP8 槽数翻倍,先确认后端支持反量化融合 |
| swa_full_tokens_ratio | 由模型定 | 窗口层槽数与全注意力层之比 | 窗口模型槽不够时调 |
| max_mamba_cache_size | 按比例 | 状态池槽数 | 混合模型并发被状态池卡时调 |
| schedule_conservativeness | 1.0 | 准入估计输出长度的松紧 | 抢占多调到 1.3,利用率低调到 0.3 |
| enable_memory_saver | 关 | KV 池可整体释放再恢复 | RL 训推一体必开 |

### 7.4 常见误区

| 误区 | 真相 |
|---|---|
| 「SGLang 没有分页」 | 逻辑上还是槽号表加间接寻址,只是页恰好等于一个 token;MLA 后端下页会被钉到 32 或 64 |
| 「mem_fraction_static 是 KV 占比」 | 是权重加 KV 的占比,换大模型同一个比例给 KV 的更少 |
| 「max_total_tokens 能把容量调高」 | 只能调低 |
| 「并发上不去是显存不够」 | 多数短上下文部署卡在 4096 的默认行数;Mamba 混合模型卡在状态池 |
| 「抢占会备份 KV」 | 默认不备份,只有 decode 分离节点例外 |
| 「窗口子池使用率中途下降是泄漏」 | 是设计,窗口层的槽在 token 滑出窗口时回收 |
| 「跑短请求地址表就小」 | 按最大并发和最大上下文买断,短请求也是 2 GB |
| 「token 粒度命中 N 个就是 N 个」 | 最后一个 token 留给前向算 logits,命中 N 减 1;按页分时再退到页边界 |
