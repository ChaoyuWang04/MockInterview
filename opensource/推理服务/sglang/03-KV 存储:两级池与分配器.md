# SGLang 03|KV 存储:六种事故,六道防线

维护一个推理引擎的 KV 存储层,日常不是在设计数据结构,是在处理事故:服务跑到一半 OOM 崩了;100 个请求每步各长一个 token,槽用光了整机在抢占里打转;一步 decode 明明只要几毫秒,CPU 却在给几千个请求算地址;显存空着一半,并发却卡死在 4096;最糟的是不崩不卡,答案悄悄错了。这一章按这六种事故讲 SGLang 的 KV 存储层:每一道设计都是为了某一种事故不再发生,你绕过它,那种事故就回来。

KV cache 为什么必须存在、朴素存法的三种浪费、分页的思想、页多大合适,vLLM 解读的「PagedAttention 与 KV Cache 管理」一章已经讲透,本章不重讲;前缀怎么复用见 04 章,显存放不下往外放见 05 章。全章内容都在源码上逐条核对过;每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|六种事故

### 1.1 KV 存储层只管三件事,但每件都能出人命

kernel 算第 n 个 token 的注意力时,要把这个请求前面所有 token 的 K 和 V 一个不落地读出来。KV 存储层只管三件事:**记住每个 token 的 K 和 V 在显存哪里;请求来了给它腾地方,走了收回来;腾不出来时决定牺牲谁**。三件事任何一件出错,后果不是报错,是下面这张表。

### 1.2 事故表

| 事故 | 谁干的 | 症状 | 动哪个指标 | 防线在哪 |
|---|---|---|---|---|
| 崩 | 运行中有人向 CUDA 要显存;激活没地方放 | 跑到一半 OOM,整个服务没了 | 稳定性 | Part 2:启动时把账算死,运行中 KV 层一个字节不再要 |
| 卡 | 100–1000 个请求每步各长 1 个 token,槽用光 | 抢占风暴,请求反复被踢回队列,TPOT 抖到秒级 | 尾延迟、TTFT | Part 3:每步先问,先驱逐再踢,踢丢工作最少的,踢完多留 20 步 |
| 慢 | 每步给 1000–5000 个请求算槽号落在 Python 上 | 一步 decode 被 CPU 拖住,GPU 空转 | TPOT、吞吐 | Part 4:地址表就是 GPU 张量,整批分配一个 kernel |
| 装不下 | 并发卡在 4096,显存空着一半 | 并发上不去,调 mem_fraction 没反应 | 并发上限、显存效率 | Part 5:三道闸取最小,多数部署卡在行数不在显存 |
| 算错 | 槽号易主、KV 只传了一半、假请求写脏、草稿被拒、权重换了 KV 没换 | 不崩不卡,答案错,而且不报错 | 可复现、正确性 | Part 6:五种静默读错,五道防线 |
| 接不上 | 新模型结构、MLA 后端、PD 分离 | 命中率突然掉一半;并发被状态池卡;传输慢 | TTFT、并发上限 | Part 7:池家族同一接口;后端钉页;PD 排序与备份 |

「算错」最容易被忽视,因为它没有任何日志,只有用户说「今天回答质量不对」。这一类防线平时看起来像多余的检查,拆掉一个,某一天就会出一次查不出原因的事故。

### 1.3 这些事故在不同负载下各自先来哪一种

| 负载 | 先撞哪种事故 | 为什么 |
|---|---|---|
| 高并发短请求 | 装不下 | 4096 的默认行数比槽数先到顶 |
| 长上下文 | 崩、卡 | 一个请求 10000–100000 个槽,预算算错就 OOM,算对了也频繁抢占 |
| MLA 模型 | 接不上 | 主流后端把页钉到 64,token 级命中失效 |
| Mamba 混合模型 | 装不下 | 并发被状态池卡住,调 KV 参数没用 |
| PD 分离 | 卡、接不上 | decode 端没有 prefill 能力,抢占不能重算;槽号不连续传输慢 |
| 推测解码 | 算错 | 被拒的草稿 KV 如果当成有效,下一步就错 |
| RL 训推一体 | 算错、崩 | 换权重后旧 KV 一个不能留;训练要显存时 KV 池要整体让出去 |

### 1.4 两个公式

槽总数在启动时算死,之后不变:

$$\text{槽数} = \left\lfloor \frac{\text{装载后剩余显存} - \text{装载前总显存} \times (1 - f) - \text{多模态保留}}{\text{每 token 字节数}} \right\rfloor_{\text{页对齐}}$$

f 是 mem_fraction_static。并发上限是三道闸取最小,第三项只在 Mamba 混合模型上存在:

$$\text{并发} = \min\left(\frac{\text{槽数}}{2},\ \text{地址表行数},\ \frac{\text{状态池槽数}}{3}\right)$$

## Part 2|不崩:启动时把账算死,运行中一个字节都不再要

### 2.1 事故:运行中 cudaMalloc,迟早在最忙的时候 OOM

最早的做法是请求来了就向 CUDA 要一块显存。这种系统能跑通所有测试,然后在线上最忙的那个小时 OOM,因为激活、CUDA graph、通信缓冲和 KV 在同一块显存里抢,谁最后要谁死。KV 存储层的第一条纪律因此是:**所有 KV 显存在启动时一次买断,之后运行中 KV 层不向 CUDA 要任何东西**。分配和回收全是在一个固定张量上算下标。这也是为什么本章后面所有东西都叫「槽」而不叫「内存」:槽是编号,不是地址。

### 2.2 预算公式里减的是「总显存乘以一减比例」,所以这个比例含权重

模型权重装载完后量一次剩余显存,减两样东西,剩下全给 KV:运行期余量,等于装载前的显存总量乘以 1 减 mem_fraction_static;多模态模型再扣一块给图像编码器。**mem_fraction_static 不是「KV 占多少」,是「权重加 KV 一共占多少」**,同一个比例换一个更大的模型,给 KV 的就更少。余量留给激活和 CUDA graph,它们才是运行中真正会向 CUDA 要显存的人。

算出来小于等于 0,启动直接报错,而且错误信息里算好了最小可行的 mem_fraction_static。宁可启动失败,不要跑起来再崩。

### 2.3 一个 token 值多少字节,决定了这块预算换成多少槽

预算除以每 token 字节数就是槽总数,向下取整到页对齐。每 token 字节数按池算:MHA 池是本卡分到的 KV 头数乘以 K 头维加 V 头维乘以层数乘以精度字节;MLA 池是潜向量维加 RoPE 维乘以层数乘以精度字节,DSA 再加索引器那份;混合模型只数全注意力层,窗口层和状态层另算;FP4 加缩放因子。

算例:8 个 KV 头、头维 128、32 层、BF16,每 token 128 KB,50 GB 预算放约 40 万个 token。MLA 模型潜向量 512 加 RoPE 64、61 层、BF16,每 token 约 70 KB,同样 50 GB 放约 73 万个。这就是 DeepSeek 一类模型显存效率高的来源。

### 2.4 三道上限只能往下压,没有任何参数能把槽数调高

用户给的 max_total_tokens 只能往下压,给高了打警告用探测值;流水线并行时各段层数不同,取最小;开了 Mamba 时状态池另外分账。想要更多槽只有三条路:调高 mem_fraction_static、开低精度 KV、换 MLA 模型。运维上判断比例合不合适看就绪前日志的剩余显存:5–8 GB 合适,高于 8 GB 往上加,每次 0.01,加到 OOM 退一步。

### 2.5 事故的另一半:激活的账算错了,也是崩

余量留少了,CUDA graph 捕获或者长 prompt 的激活会在运行中 OOM,这时崩的不是 KV 层,但锅在这个比例上。所以有一种可选模式把顺序反过来:KV 池先只保留一段虚拟地址上界,等 CUDA graph 捕获完、知道激活实际占多少之后,再把物理页补上去,槽数这时向上对齐到页边界。默认不开,因为它假设捕获期的激活峰值就是运行期的峰值。

## Part 3|不卡:见底时谁走,怎么走,走完留多少

### 3.1 事故:每步都在踢人,被踢的重排队再被踢

decode 每步给每个在飞请求分一个新槽。100–1000 个请求同时在跑,槽是线性减少的,总有一步分不出来。朴素做法是分不出来就报错,请求失败;稍好一点是踢几个请求出去,但踢错了人、踢少了,下一步又踢,整机在抢占里打转,尾延迟从几十毫秒抖到几秒。这就是抢占风暴。

### 3.2 每步 decode 前先问一次,短缺走抢占不走报错

每步 decode 之前,调度器问分配器:下一步要的槽数够不够。分配器先让缓存树把没人用的前缀驱逐掉,再比较空闲槽数。抢占循环收敛在同一个判断上,所以分配器这边的短缺一定走抢占,不会走到分配失败抛错。**分配失败抛错只发生在 prefill 侧,而且是故意的**:prefill 取行失败说明准入闸门(02 章)算错了,这种错必须暴露,静默回退会把闸门的 bug 藏到永远查不出来。取行失败的错误信息让人调小最大并发,取槽失败的错误信息先打印缓存树再让人调小 batch,两者都不回退。

### 3.3 踢谁:输出最少的先走,因为它丢掉的工作最少

抢占按一个顺序把在飞请求从批里踢出去,直到空间够。默认顺序是**已经生成的 token 最少的先被踢**,同样少的话 prompt 更长的先被踢。被踢的请求释放全部 KV、不插缓存树、重新排队从头 prefill,所以踢一个输出了 2000 个 token 的请求等于扔掉 2000 步 decode,踢一个刚开始的请求几乎不亏。开了优先级调度时先按优先级,再按这个。批里至少留一个请求。

### 3.4 踢完多留 20 步,否则下一步又踢

抢占够了空间之后还会多驱逐一点:按剩余请求数乘一个步数,默认 20,给接下来 20 步 decode 预留。没有这一条,踢完刚好够这一步,下一步又短缺,又踢,这就是风暴的成因。

### 3.5 默认不备份被踢请求的 KV,只有 decode 分离节点例外

单机抢占不备份,被踢的请求重新 prefill,成本已经被前缀缓存摊掉一部分:它的 prompt 前缀多半还在树上。decode 分离节点没有 prefill 能力,踢了就没人能算回来,所以它把 KV 备份到 host 再释放,恢复时拷回来;备份放不下就只能中止请求。

### 3.6 抢占频繁是准入太松,不是显存太少

日志里「KV cache pool is full. Retract requests」每分钟一次以内是正常的。频繁出现,先把调度保守度调大到 1.3 左右,让准入闸门估计输出长度时更悲观;反过来 token 使用率总在 0.9 以下、队列却有请求在等,调小到 0.3 左右。先调这个,再考虑减并发。减并发是把风暴换成排队,不是解决。

## Part 4|不慢:地址表就是 GPU 上的张量,一步分配是一个 kernel

### 4.1 事故:decode 一步 20 毫秒,CPU 给 1000 个请求算地址就用掉 10 毫秒

kernel 要读每个 token 的 KV 地址。如果地址表在 host 上,每步要把 1000–5000 个请求的地址搬到 GPU;如果分配在 Python 里逐请求循环,1000 个请求就是 1000 次小操作。这两件事任何一件都能吃掉 decode 一步的一半时间,GPU 在等 CPU。SGLang 的零开销调度(02 章)要求 CPU 在这一步几乎不做事,所以 KV 存储层的地址表和分配器都得在 GPU 上。

### 4.2 第一张表:每个请求一行,每格一个槽号,kernel 直接读

每个在飞的请求分一行,行长是最大上下文长度,每格一个 32 位整数,记这个位置的 token 的 KV 在哪个槽。整张表是一个 GPU 二维张量,行数是最大并发加 1。注意力后端每步从这张表里把本批请求的行取出来整理成自己要的格式(有的要页表,有的要扁平索引),这一步在 06 章;kernel 拿到的就是槽号,不经过 host。

请求来了从空闲行列表尾部弹一行,走了还回去,弹几个就是几个操作。一行里的格子彼此没有关系,第 999 格可以指向第 137 号槽,第 1000 格指向第 90000 号槽。这意味着任意一个 token 的 KV 可以单独指向任意一个槽,不需要对齐到任何块边界,这是下一章 radix 树能命中到单个 token 的前提。

### 4.3 第二张表:槽号跨层通用,所以第一张表只记一个数

第二张表按层分,每层各有一个 K 张量和一个 V 张量,第一维就是槽号。槽号在所有层通用:一个 token 在第 0 层用第 137 号槽,在第 31 层也用第 137 号槽,所以第一张表只需要记一个数。三种物理排布可选,默认 NHD 一个槽一行,写入按行散射;HND 把页和头折成一个索引让按头分页的 kernel 直接消费;AMD 上还有一种五维排布只有 AITER 后端认。排布构造时定死。

### 4.4 页大小 1 时分配就是一次切片

page_size 不填默认 1,一个槽就是一页,分配器是一个空闲槽号张量,分配切走前面 n 个,回收拼到后面,没有页内碎片。这是 SGLang 的默认形态,大多数 MHA 模型都在这条路上。

### 4.5 按页分时,整批一次分完,而且故意高估

后端要求按页分时(Part 7),分配换成分页分配器,prefill 和 decode 各一个 Triton kernel 一次处理整批请求。prefill 的 kernel 把每个请求要新分的 token 分成三段:先填满上一页剩下的空位,再整页整页取新页,最后不满一页的再取一页;每个 token 只要知道自己落在哪一段就能算出槽号。decode 的 kernel 只在序列长度跨过页边界时取新页,否则槽号是上一个加 1。

调 kernel 之前有一步保守估计:假设每个请求都会用到一张新页,先按这个上限问缓存树要空间,不够就先驱逐。kernel 跑起来没有回头路,所以宁可多算。**代价是命中率**:多驱逐的那部分前缀是被当保险付掉的。

### 4.6 回收攒着一起做

按页回收是把槽号除以页大小得页号,去重后整页放回,一页里只要还有一个 token 在用整页都不能回收。回收还可以分组:先开一个组,期间所有回收只记下来,组结束时一次拼接一次回收。调度器处理一批请求的结束时就是这么做的,把 10–50 次小回收压成一次。

### 4.7 这套东西的账:并发乘上下文的一张表

地址表每格 4 字节,行数乘列数,按最大值一次分配。最大并发 4096、上下文 131072 时是 2 GB,**跑短请求也是 2 GB,跑长上下文也是 2 GB**。块表方案同样条件下约 134 MB。这 2 GB 换来的是 kernel 直接读和任意 token 指任意槽;不开前缀缓存的部署应该把最大并发压到实际需要的数,因为那时它只剩纯开销。

## Part 5|装得下:并发到底卡在哪

### 5.1 事故:显存空着一半,并发卡死在 4096

上线后监控显示 KV 使用率 50%,队列里却有请求在等,调 mem_fraction_static 没反应。这不是显存的问题,是并发被另一道闸卡住了。并发上限是三道闸取最小,每道各有各的参数,调错一道另两道不动。

### 5.2 第一道:地址表行数,默认封在 2048 到 4096

不指定最大并发时,按槽总数除以上下文长度再乘 512 估,夹在 2048 到 4096 之间;指定了就按数据并行副本数平分。按 2.3 的 MHA 算例,40 万个槽、上下文 8192,估计值 25000,夹到 4096。这时槽数一半是 20 万,并发上限就是 4096,卡在行数,和显存无关。要跑到 4096 以上必须显式指定,代价是地址表按比例撑大。

### 5.3 第二道:槽总数的一半

无论行数怎么定,都不超过槽总数的一半。上下文 131072 时估计行数 1562,夹到 2048,但 40 万个槽平均每请求只有 195 个,并发根本到不了 2048 就被槽数封死。**短上下文看行数,长上下文看槽数。**

### 5.4 第三道:Mamba 混合模型的状态池,除以 3

Mamba 层没有逐 token 的 KV,每个请求一份固定状态。混合模型每个请求取一行的同时再从状态池取一个槽,状态池的槽数是独立配置的。开前缀缓存时每个请求要占三份状态槽,树上留一份、在算一份、乒乓一份,所以并发上限是状态槽数除以 3。日志会明说「capped by the mamba state cache」。调 mem_fraction_static 和 max_total_tokens 对这道闸都没用。

### 5.5 页大于 1 时每个请求平均浪费半页

页 64、4096 并发,尾页平均浪费 4096 乘 32 等于 131072 个槽,按 MLA 每 token 70 KB 是约 9 GB,按 MHA 128 KB 是约 16 GB。页大小 1 没有这笔账,这是 SGLang 默认页 1 的理由之一;页被后端钉大时这笔账自动回来。

### 5.6 装不下时的三个真开关

FP8 KV 把槽数翻倍,前提是注意力后端支持融合反量化,否则每步多一次转换。滑动窗口模型的窗口层槽数和全注意力层槽数按一个比例分,窗口层的槽在 token 滑出窗口时就回收,不等请求结束,监控里窗口子池使用率在请求中途下降是设计不是泄漏。可选的统一池把整个预算当一块字节缓冲,子池从两端往中间长,哪种层用得多哪个多占,代价是虚拟槽号加一张映射表,默认不开,混合模型的比例调不准时才值得试。

## Part 6|不错:五种静默读错,五道防线

### 6.1 事故:不崩不卡,答案错,没有日志

KV 存储层最坏的事故不是 OOM,是读到了不属于这个请求的 KV。注意力照常算,采样照常出字,只是某几层用的是别人的、或者上一版权重的、或者还没传完的 K 和 V。用户看到的是「回答质量今天不对」,排查时所有指标正常。下面五种情况每一种都发生过,每一种都有一道专门的防线。

### 6.2 槽号易主:每行一个代数计数

请求 A 结束,它的行还回去,马上分给请求 B。异步路径上还拿着 A 的元数据的人,如果按旧行号去读,读到的是 B 的槽号。防线是每一行配一个代数计数,每次重新分出去就加一;拿着旧元数据的人先比代数,不一致就知道这行已经易主。

### 6.3 KV 只传了一半:读第 i 层前等第 i 层

三层缓存逐层加载(05 章)和 PD 分离逐层传输时,第 3 层的 KV 可能已经到了,第 20 层还在路上。注意力如果按层顺序读,读到第 20 层就是垃圾。防线是取某一层 K 或 V 张量的接口上挂一个按层的计数器,读第 i 层先等第 i 层到齐。注释明说这个接口只给注意力后端用,别拿去做统计,否则统计代码会在这里阻塞。

### 6.4 假请求写脏:第 0 行和第 0 页是垫片

CUDA graph 要求批大小固定,不够的位置用假请求补齐。假请求也会照常写 KV,如果它的槽号指向真实请求的槽,真实请求的 KV 就被覆盖。防线是第一张表第 0 行和第二张表第 0 号槽所在的页都留给假请求,它们的读写全落在这里,真实请求永远不用第 0 行和第 0 页。这样补齐的批不需要任何特判。

### 6.5 草稿被拒:每个请求两个长度

推测解码先给草稿 token 分槽写 KV,验证之后可能拒绝其中一部分。被拒的草稿 KV 已经在槽里了,如果把它们当成有效历史,下一步的注意力就带着错的 token。防线是每个请求身上记两个长度,已分配的和已提交的,验证通过才提交;请求结束时,已分配但未提交的尾巴按「多分了」整页回收,缓存树只收提交过的那段。

### 6.6 权重换了 KV 没换:更新后清树,释放前先清树

RL 训练每隔几步给推理引擎换一次权重。旧权重算出来的 KV 配新权重,前缀命中越高答案错得越多,而且完全没有报错。防线有两道:权重更新接口带一个清缓存开关,开着就把整棵树清空,失败直接断言;训练要显存时的整池释放接口,先清空缓存树再暂停 KV 那块显存,并且断言服务完全空闲才能调,有请求在飞就拒绝。恢复按相反顺序。这条路要开 enable_memory_saver。

### 6.7 抢占不插树

被踢的请求释放 KV 时不把它们插进缓存树,源码注释的理由只有一句:要立刻腾空间。抢占走和正常结束一样的释放路径,只有这一个开关不同;被踢的请求重新 prefill 时,它的前缀多半还能在树上命中别人留下的那份。

## Part 7|接得上:池家族、后端的隐形规则、PD 的额外要求

### 7.1 事故:换个模型,命中率掉一半;换个模型,并发上不去

今天的模型把 MHA、MLA、滑动窗口、Mamba、稀疏索引几种层混在一起,KV 的形状各不相同。如果调度器和注意力后端要按模型结构各写一遍分配逻辑,每来一种新结构就要改三处。SGLang 的做法是让第二张表长成一个家族,启动时按模型结构挑一种,分配、写入、回收接口全家一样,调度器不知道底下是哪种池。

| 池 | 每个槽存什么 | 什么模型用 |
|---|---|---|
| MHA 池 | 每层一份 K 和一份 V | Llama、Qwen 这类标准结构 |
| MLA 池 | 每层一个向量,长度是潜向量维加 RoPE 维;V 是它的前一段视图 | DeepSeek V2 / V3 |
| DSA 池 | MLA 池再加一份索引器缓存 | DeepSeek V3.2 这类稀疏注意力 |
| 滑动窗口混合池 | 两个子池:全注意力层一个,窗口层一个,各自计数 | Gemma 这类窗口与全注意力交替 |
| 线性混合池 | 全注意力层一个 KV 池,加按请求分槽的状态池 | Qwen3-Next、Nemotron 这类 Mamba 混合 |
| MiniMax 稀疏池 | 主池加索引器池 | MiniMax 稀疏注意力 |
| FP4 / MXFP8 池 | 数据张量加缩放因子张量 | 开低精度 KV 时套在上面几种之外 |

写入位置捆成一个结构体,里面除了主位置还带窗口子池位置和全注意力子池位置,后端发一次写入调用,底下是哪种池它不管。FP8 的 KV 按无符号 8 位整数存,取出来再看成 FP8,原因只是 PyTorch 按索引写入不支持 FP8 张量。

### 7.2 后端的隐形规则:MLA 后端把页钉到 32 或 64,token 级命中就没了

页大于 1 从来不是用户选的。FlashMLA 和 HPC-Ops 只认 64,TensorRT-LLM 的 MLA、tokenspeed、CuteDSL 三个 MLA 后端只认 32 或 64,TensorRT-LLM 的 MHA 认 16 到 128。选了这些后端,启动时配置层把 page_size 改过去,打一行警告。**用 DeepSeek 跑主流后端,实际上都在按页分,下一章的树只能命中到页边界**,64 的页最坏丢 63 个 token 的命中,加上 5.5 那笔尾页碎片。命中率掉一半先看启动日志里 page_size 有没有被改。

### 7.3 PD 分离的两条额外要求:槽号要连续,decode 端要备份

prefill 节点算完要把 KV 传给 decode 节点,传输按槽号段发,槽号越连续段数越少。所以 PD 模式下回收的槽号不直接归还,先攒进暂存区,不够用时合并排序再用;单机部署不排,因为没人按段传输。开了 NVLink 传输时 KV 张量从一个自定义显存池里分,让传输引擎能直接注册这块内存。decode 端抢占时备份到 host 而不是丢掉重算,3.5 讲过。

### 7.4 其余子系统一表

| 子系统 | 它向存储层要什么 | 存储层给的东西 |
|---|---|---|
| 缓存树(04 章) | 请求结束时决定哪段留下 | 分配层不做去留判断,只回收树说不要的那段 |
| 准入与调度(02 章) | 每步知道还剩多少槽 | 空闲槽数加可驱逐槽数,分配前先驱逐 |
| 三层缓存(05 章) | 逐层加载时读第 i 层要等第 i 层 | 按层计数器,6.3 |
| 推测解码(08 章) | 草稿先占槽、验证后才算数 | 两个长度,6.5 |
| CUDA graph(07 章) | 补齐的假请求要能读写 | 垫片行与垫片页,6.4 |
| 多模态(14 章) | 编码器要显存 | 预算先扣保留量,2.2 |

## Part 8|图解

### 8.1 显存见底的一步

```text
  每步 decode 前:需要 n 个槽
       │
       ├─ 缓存树驱逐无人引用的前缀 ──> 空闲 ≥ n ? ──是──> 分配,继续
       │                                  │否
       ▼                                  ▼
  抢占循环:按「输出最少、prompt 最长」排序,从尾部踢
       ├─ 单机:释放全部 KV,不进树,重排队(下次 prefill 从头算)
       └─ decode 分离:备份到 host 再释放;备份失败则中止请求
       │
       └─ 空间够了之后再多驱逐 (剩余请求数 × 20) 个槽,防下一步又抢占

  prefill 侧不走这里:取行失败 / 取槽失败 = 准入算错,直接抛错
```

### 8.2 五种静默读错与五道防线

```text
  读错的来源                     没有防线时 kernel 读到的        防线
  ─────────────────────────────  ────────────────────────────  ─────────────────────────
  行还回去又分给别人              别人的槽号                     每行代数计数,先比再读
  逐层加载 / 逐层传输未完成       还没到的层是垃圾               取层张量前等该层计数器
  CUDA graph 补齐的假请求写 KV    被覆盖的真实请求的槽           第 0 行、第 0 页当垫片
  推测解码的草稿被拒              被拒的草稿当成历史             已分配 / 已提交两个长度
  RL 换了权重                     旧权重算的 KV                  更新后清树;释放前清树且要求空闲
```

### 8.3 并发上限的三道闸

```text
  槽总数 ── ÷ 2 ──────────────────────────┐
                                          │
  地址表行数(默认 槽数/上下文×512,       ├── 取最小 ── 并发上限
    夹在 2048–4096;可显式指定)──────────┤
                                          │
  状态池槽数 ── ÷ 3(仅 Mamba 混合模型)───┘

  MHA、40 万槽、上下文 8192:  20 万 / 4096 / 无        -> 4096,卡在行数
  MHA、40 万槽、上下文 131072:20 万 / 2048 / 无        -> 实际由槽数封:40 万 ÷ 平均长度
  Mamba 混合、状态槽 3000:    ... / ... / 1000          -> 1000,卡在状态池
```

### 8.4 两张表与一个请求的三条长度线

```text
  ReqToTokenPool(行 = 请求,列 = 位置,格 = 槽号)
  行 0 [ 0    0    0    0   ... ]            <- 垫片
  行 1 [ 137  138  139  901  902  903 ... ]  <- 请求 A:前 3 格是命中的前缀槽
  行 2 [ 137  138  140  141  ... ]           <- 请求 B:与 A 共享前 2 格,第 3 格分叉,不复制

  TokenToKVPool(每层一对张量,第一维 = 槽号,槽 0 所在页是垫片)

  一个请求的行上三条长度线:
  位置: 0 ...... p-1 | p ...... s-1 | s ... s+k-1 |
        前缀命中(照抄)| 本次算的新 token | 草稿(推测解码)|
                      ^               ^             ^
                 prefix_len       committed     allocated
```

## Part 9|机制之外:源码里额外读到的

### 9.1 取行失败与取槽失败的错误信息不同

取行失败的信息让人调小最大并发,因为行数是准入闸门的账;取槽失败先把缓存树打印出来再让人调小 batch,因为那是驱逐没腾出来。两者都不静默回退。

### 9.2 分配前的估计故意偏大

按页分配时估计需求按「每请求一张新页」算再去驱逐,批里大多数请求其实用不到新页。开前缀缓存又跑高并发时这笔保险会压低命中率。

### 9.3 排布是构造时定死的

NHD、HND、AMD 五维三种排布在池构造时定,kernel 看到什么形状取决于它,运行中不换。

### 9.4 写入位置结构体会被按层截短

分段 CUDA graph 和数据并行补齐会把写入位置按层截短,结构体在构造时把窗口子池位置和全注意力子池位置也切到同样长度,三者永远等长。

### 9.5 回收的槽号只在 PD 下排序

token 级分配器的暂存区和合并排序只在 PD 分离的 prefill 或 decode 节点上启用,单机回收就是拼接。

### 9.6 统一池的槽号是虚拟的

统一池给上层的槽号要经过一张虚拟到物理的映射表,回收时还要压缩;这是它默认不开的原因,不是功能不全。

### 9.7 窗口层的槽在 prefill 和 decode 开头各回收一次

滑动窗口混合池的分配走读里,prefill 和 decode 开头都有一步「先回收滑出窗口的槽」,所以窗口子池的容量可以按窗口大小而不是上下文长度配。

### 9.8 释放 KV 池时 PD 队列也要清

RL 的整池释放接口在 PD 分离节点上会先把传输队列和预分配队列里的请求清掉,再暂停 KV 显存;否则队列里的请求恢复后指向的槽已经不存在。

## Part 10|对比与收益账

### 10.1 和 vLLM 的 KV 管理比

| 维度 | vLLM | SGLang |
|---|---|---|
| 地址表 | 块表,记块号,块内位置靠算,约 100 MB | 两级表,记槽号,细到 token,可达 GB 级 |
| 默认粒度 | 块大小 16 | 页大小 1,后端要求时改成 32 或 64 |
| 前缀命中粒度 | 整块 | 单个 token,按页分时退化到页 |
| 显存预算 | 按比例给 vLLM 全部,探测激活后剩下给 KV | 权重加 KV 占比例,余量按公式扣 |
| 见底 | 释放重算 | 释放重算,多留 20 步;decode 分离节点备份到 host |
| 抢占顺序 | 见 vLLM 调度器章 | 输出最少的先踢 |
| 静默读错的防线 | 见 vLLM 03 章 | 代数计数、按层等待、垫片行页、两个长度、换权重清树 |
| 混合模型 | KV 分组,每组自己的块表 | 家族里挑一种池,窗口和状态各自计数 |

两边都是「逻辑连续、物理离散」,差别在粒度:vLLM 把粒度定在块,换来小表和天然对齐;SGLang 把粒度定在 token,换来 radix 树需要的任意位置指向,代价是表大和每次读多一跳。

### 10.2 地址表的账:2 GB 对 134 MB

最大并发 4096、上下文 131072、每格 4 字节是 2 GB;块表同样条件是 131072 除以 16 再乘 4096 个格,约 134 MB,差 15 倍。换来的是分叉处不复制和命中不对齐块边界。不开前缀缓存的部署这 2 GB 是纯开销。

### 10.3 抢占的账:重算对备份

单机重算 5000 个 token 的 prefill 是 50–500 毫秒,还要重新排队;decode 分离节点的备份是显存到 host 的拷贝,5000 个 token 乘 128 KB 是 640 MB,PCIe 4 代按 20 GB/s 算约 32 毫秒,恢复再拷一次。备份便宜一个量级,但要占 host 内存,而且 decode 节点没有别的选择。

### 10.4 页大小的账:钉页的两笔钱

页 64 时命中最坏损失 63 个 token,平均 32 个;尾页碎片 4096 并发平均 9–16 GB。两笔都随页大小线性涨,page_size 不要手调,后端要多少给多少,想避开只能换后端。

## Part 11|参数、开关与排障

### 11.1 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| mem_fraction_static | 按显卡启发式 | 权重加 KV 占显存的比例 | 就绪前日志剩余显存高于 8 GB 往上加,每次 0.01;5–8 GB 合适 |
| max_total_tokens | 探测值 | KV 槽总数上限 | 只能往下压;复现某个并发上限时用 |
| max_running_requests | 按槽数推,2048 到 4096 | 最大并发,也是地址表行数 | 短上下文并发想超 4096 时显式指定;抢占频繁时调小 |
| page_size | 1 | 分配粒度 | 不要手调,后端会改 |
| kv_cache_dtype | auto | KV 精度 | FP8 槽数翻倍,先确认后端支持反量化融合 |
| swa_full_tokens_ratio | 由模型定 | 窗口层槽数与全注意力层之比 | 窗口模型槽不够时调 |
| max_mamba_cache_size | 按比例 | 状态池槽数 | 混合模型并发被状态池卡时调 |
| schedule_conservativeness | 1.0 | 准入估计输出长度的松紧 | 抢占多调到 1.3,利用率低调到 0.3 |
| enable_memory_saver | 关 | KV 池可整体释放再恢复 | RL 训推一体必开 |

### 11.2 排障:症状先查什么

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报显存不够 | 错误信息里的最小可行 mem_fraction_static | 照抄 |
| 运行中 OOM | 是激活不是 KV;就绪前日志剩余显存是否低于 5 GB | 调低 mem_fraction_static |
| 「Retract requests」频繁 | schedule_conservativeness | 调到 1.3;仍频繁再减并发 |
| token usage 低于 0.9 且队列有请求 | 准入太保守 | 保守度调到 0.3 |
| 并发上不去 | 卡在三道闸哪一道:日志「capped by the mamba state cache」;短上下文是否 4096 | 显式指定并发或调状态池 |
| MLA 模型命中率低 | 启动日志 page_size 是否被后端改成 64 | 换后端或接受 |
| 回答质量突然不对,指标正常 | RL 换权重后是否开了清缓存;推测解码是否开;PD 或 HiCache 逐层传输 | 对照 Part 6 逐条 |

### 11.3 常见误区

- 页大小 1 不等于没有分页,逻辑上还是槽号表加间接寻址。
- mem_fraction_static 是权重加 KV 的占比,换大模型同一个比例给 KV 的更少。
- max_total_tokens 只能调低。
- 并发受三道闸取最小,多数短上下文部署卡在行数不在显存。
- 抢占默认不备份,只有 decode 分离节点例外。
- 窗口层的槽在请求中途被回收是设计。
- 地址表 2 GB 跑短请求也是 2 GB。
- 静默读错没有日志,Part 6 的五道防线一道都不能拆。
