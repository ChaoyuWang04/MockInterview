# SGLang 03|KV 存储:一个 token 一格

KV cache 为什么必须存在、朴素存法的三种浪费、分页的思想,vLLM 解读的「PagedAttention 与 KV Cache 管理」一章已经讲透。这一页只说 SGLang 遇到的问题、它的解法、以及它和 vLLM 不一样的地方。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

分页把碎片解决了,但共享的单位是块。vLLM 一块 16 个 token,两个请求的内容在第 20 个 token 处分叉,只有前 16 个算共享,分叉所在的那一块要复制一份再写。

多轮对话、agent 循环、RL rollout 的分叉点落在任意一个 token 上。SGLang 的调度、驱逐、缓存复用全建在一棵前缀树上,树要在任意 token 位置劈开,底下的存储就必须能在任意 token 位置切开。块粒度做不到。

## 二、解法:一个 token 放一格

把显存想成一个仓库,每个格子放一个 token 在所有层的 K 和 V。每个请求一张清单,第 i 行写着「第 i 个 token 在几号格」。GPU 拿着清单去仓库取货。

这就是 PagedAttention 那套间接寻址,只是页的大小是 1 个 token。于是:

- 外部碎片没了,格子可以在仓库任何位置。
- 内部碎片是 0,没有「最后一块没填满」这回事。vLLM 每请求最多浪费 15 个 token,SGLang 是 0。
- 两个请求前 1000 个 token 相同就共享 1000 个格子,第 1001 个分叉,新请求分新格,不复制任何东西。树的节点值就是一段格子号,在任意位置劈开只改树,不动 KV。

## 三、代价

一格一个 token,格子多,GPU 搬的次数多。一个 token 的 KV 有 256 字节到 2 KB,GPU 一次搬 128 字节,所以每趟都是满的,次数多了但没有空跑,普通模型上测不出差别。只有 FlashMLA 这类「一次搬一整排」的程序不接受一格一格取,SGLang 在这些程序上把格子改回 64 个一排,细粒度的好处也跟着没了。

清单按「最大并发乘最大上下文」买断。4096 并发、131072 上下文是 2 GB,vLLM 同样条件 134 MB。跑短请求也是 2 GB。

## 四、和 vLLM 不一样的六处

1. **清单的大小。** vLLM 每 16 个 token 记一个号,SGLang 每个 token 记一个号,而且每行按最大上下文买断,不随实际长度缩。
2. **谁记得「哪些内容有人存过」。** vLLM 用指纹:每 16 个 token 算一个哈希,查一下就知道。SGLang 用一棵树:所有请求的 token 序列合成一棵前缀树,新请求从根往下走,走到哪分叉就从哪开始算。树的好处是分叉可以在任意 token,调度器能看到谁和谁共享多少。树的坏处是只在这一个进程里,PD 分离和多副本要另建;匹配是 CPU 的活,等待队列超过 128 条时 SGLang 自己就退回先来先服务。
3. **显存比例参数的意思不一样。** vLLM 的 0.92 是「整张卡我用多少」,探测一次后权重和激活之外全给 KV。SGLang 的 mem_fraction_static 是「权重加 KV 一共占多少」,余下的留给激活。同一个数字换更大的模型,SGLang 给 KV 的更少。运维看启动前日志里剩多少显存,5 到 8 GB 合适。
4. **并发卡在哪。** SGLang 的并发上限默认是清单的行数,自动算出来夹在 2048 到 4096 之间。上下文短的时候显存能放的请求远不止这个数,并发却停在 4096,要手动调高。上下文长的时候反过来,显存先见底。Mamba 混合模型再多一道:每个请求占 3 份状态,并发上限是状态池除以 3,调 KV 的参数没用。
5. **显存用光了怎么办。** 两边都是踢掉在跑的请求让它重算。vLLM 多一个 watermark,默认关着。SGLang 踢「已经生成得最少」的那个,它丢掉的工作最少;踢完再多空出 20 步的量,免得下一步又踢。两边默认都不备份被踢的 KV,SGLang 只在 PD 分离的 decode 节点上备份到内存,因为那个节点自己算不了 prefill。
6. **页什么时候回来。** vLLM 一直是 16 个一格。SGLang 默认 1 个一格,换到 FlashMLA、TensorRT-LLM 的 MLA 这类程序时被改成 32 或 64 个一格,只打一行警告。用 DeepSeek 的时候要知道自己实际上在按页跑,命中只能到页的边界。

显存放不下往内存和硬盘放,两边都有,vLLM 默认关,SGLang 的 HiCache 是它的招牌功能之一,见 05 章。

## 五、调参与观测

**参数在哪调。** 启动参数(`--mem-fraction-static` 这种命令行旗标,也可以写进 YAML 用 `--config` 传)决定池的大小和形状,改了要重启。环境变量(`SGLANG_` 前缀)是少数内部阈值,改了也要重启。运行时只有三个入口:`/flush_cache` 清空整棵树(有请求在飞时拒绝);`/release_memory_occupation` 与 `/resume_memory_occupation` 让 KV 池整体让出显存再拿回来;`/set_internal_state` 只能改流水线微批和推测解码的几个阈值,改不了这一页的任何参数。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--mem-fraction-static` · 权重加 KV 占显存的比例 | 启动 | 按显卡启发式 | 调高:槽变多,并发和吞吐上去,余量变薄,激活或 CUDA graph 可能 OOM。调低:反过来 | 就绪前日志 `available_gpu_mem`,5–8 GB 合适;每次动 0.01 |
| `--max-total-tokens` · KV 池最多放多少 token | 启动 | 探测值 | 只能调低。调低:并发上限跟着降,用来复现某个并发下的行为 | 就绪前日志 `max_total_num_tokens` |
| `--max-running-requests` · 最多同时跑多少请求 | 启动 | 按槽数推,夹在 2048–4096 | 调高:短上下文下并发才上得去,清单(第一级)按比例变大。调低:并发封顶,抢占变少但排队变长 | 就绪前日志 `max_running_requests`;Decode batch 行的 `#running-req` 贴着它就是卡在这里 |
| `--schedule-conservativeness` · 准入估计输出长度的松紧 | 启动 | 1.0 | 调高(1.3):准入更悲观,抢占变少,`token usage` 降一点。调低(0.3):进批更激进,`token usage` 上去,抢占可能变多 | 警告行 `KV cache pool is full. Retract requests`;`token usage` 与 `#queue-req` |
| `--chunked-prefill-size` · 长 prompt 一次算多少 | 启动 | 按显卡 | 调低(4096 或 2048):长 prompt 的 prefill 激活变小,不再 OOM,但长 prompt 的 TTFT 变长 | prefill 阶段 OOM 时先动它,不动比例 |
| `--page-size` · 分配的最小单位是几个 token | 启动 | 1 | 别手调,后端会改。变大:命中退到页边界,每请求平均浪费半页 | 启动日志里 page_size 被改的警告 |
| `--kv-cache-dtype` · KV 用什么精度存 | 启动 | auto | FP8:槽数翻倍;后端不支持融合反量化时每步多一次转换,TPOT 变长 | 就绪前日志 `max_total_num_tokens` 翻倍与否 |
| `--swa-full-tokens-ratio` · 窗口层和全注意力层的槽数比 | 启动 | 由模型定 | 窗口模型两个子池的比例;窗口层槽不够时调 | Decode batch 行的 `swa token usage` |
| `--max-mamba-cache-size` · Mamba 状态池的大小 | 启动 | 按比例 | 混合模型的状态池;并发被它卡住时调高 | 启动日志 `capped by the mamba state cache` |
| `--enable-memory-saver` · 让 KV 池能整体让出显存 | 启动 | 关 | 开了 KV 池才能整体让出显存;RL 训推一体必开 | `/release_memory_occupation` 是否成功 |
| `--cuda-graph-max-bs-decode` · decode 用 CUDA graph 的最大批 | 启动 | 按模型 | 调高:大批 decode 更快,但 CUDA graph 吃余量,要同时调低比例 | 就绪前 `available_gpu_mem` 是否掉到 5 GB 以下 |
| `SGLANG_RETRACT_DECODE_STEPS` · 抢占后多留几步的量 | 环境变量 | 20 | 抢占后多预留几步;调高抢占更少但一次踢得更狠 | 警告行出现的频率 |

**怎么看。** 三行日志够用:就绪前那一行看容量(`max_total_num_tokens`、`max_running_requests`、`available_gpu_mem`);`Prefill batch` 行的 `#new-token` 和 `#cached-token` 看命中;`Decode batch` 行的 `#running-req`、`token usage`、`gen throughput`、`#queue-req` 看稳态。`token usage` 高于 0.9 是健康;`#queue-req` 在 100–2000 之间说明客户端压得够。响应的 `meta_info` 里有 `cached_tokens`。`/get_server_info` 能读回当前生效的全部参数。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报显存不够 | 错误信息里的最小可行比例 | 照抄 |
| prefill 阶段 OOM | `--chunked-prefill-size` | 降到 4096 或 2048,不先动比例 |
| decode 阶段 OOM | `--max-running-requests` | 调低;或比例降到 0.8 |
| `Retract requests` 频繁 | `--schedule-conservativeness` | 调到 1.3;仍频繁再减并发 |
| `token usage` 低于 0.9 且 `#queue-req` 大 | 准入太保守,常见于 max_new_tokens 大但早停 | 保守度调到 0.3 |
| `#running-req` 贴着 4096 不动 | 卡在清单行数 | 显式指定 `--max-running-requests` |
| 混合模型并发上不去 | 日志 `capped by the mamba state cache` | 调状态池,不调比例 |
| DeepSeek 的 `cached_tokens` 总是 64 的倍数 | page_size 被后端改了 | 换后端或接受 |
| 回答质量突然不对,指标正常 | RL 换权重后有没有清树;`/release_memory_occupation` 前树清了没 | 权重更新带 flush_cache |

## 六、常见误区

- **看到 OOM 就降 mem_fraction_static。** 先分清在哪一步 OOM。prefill 时是长 prompt 的激活,动 chunked_prefill_size;decode 时是并发,动 max_running_requests。比例是最后才动的,它一降整机容量都跟着降。
- **看到 Retract 警告就减并发。** 每分钟一次是正常的。频繁出现先把保守度调到 1.3。减并发是把抢占换成排队,TTFT 照样差。
- **token usage 只有 0.6 就加显存。** 队列里有人等、使用率却低,是准入太保守,不是显存少。典型场景是客户端给了很大的 max_new_tokens 但回答很早就停。保守度调到 0.3。
- **并发到 4096 上不去就去调显存。** 短上下文下卡的是清单的行数,显存空着一半也没用。显式指定 max_running_requests。
- **调 max_total_tokens 想涨容量。** 它只能往下压。
- **DeepSeek 的命中数总是 64 的倍数,以为缓存坏了。** 是 FlashMLA 把页钉成 64,命中只能到页边界。
- **调大 cuda-graph-max-bs 之后开始 OOM。** CUDA graph 的缓冲吃的是余量,调它要同时把比例降下来。
- **开 FP8 KV 期望翻倍,结果变慢了。** 后端不支持融合反量化时每步多一次转换。先确认后端。
- **RL 训推一体:训练时释放显存失败。** 释放接口要求服务完全空闲,有请求在飞就直接拒。先停发请求,等 `#running-req` 归零。
- **RL 换了权重没清树。** 旧权重算的 KV 配新权重,前缀命中越高答案错得越多,而且没有任何报错。权重更新接口带 flush_cache。
- **混合模型看着 KV 使用率很低,并发却上不去。** 卡在状态池。日志里那一行「capped by the mamba state cache」很容易被当成普通信息略过。
