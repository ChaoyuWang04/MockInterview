# SGLang 03|KV 存储:两级池与分配器

注意力 kernel 算一个请求时,要拿到它每一个历史 token 的 K 和 V 在显存里的地址。这一章讲 SGLang 用哪两张表记这些地址、谁来分配和回收、显存能装多少 token,以及装不下时先踢谁。

KV cache 为什么必须存在、朴素存法浪费在哪、分页的思想是什么,这些原理 vLLM 解读的「PagedAttention 与 KV Cache 管理」一章已经讲透,本章不重讲,只在 Part 1 给一张回指表。全章内容都在源码上逐条核对过;每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:一句痛点,其余回指

### 1.1 痛点只有一句

一张卡上同时跑几百个请求,每个请求几千个 token,每个 token 在每一层各有一份 K 和一份 V。kernel 算第 n 个 token 的注意力时,要把这个请求前面所有 token 的 K 和 V 一个不落地读出来。**谁记得每个 token 的 K 和 V 放在显存哪里,以及谁在请求来了给它腾地方、走了把地方收回来** ,这就是 KV 存储层的全部工作。

SGLang 在这件事上比通用做法多一个要求:它的前缀缓存(下一章)要命中到单个 token,不是整块整块地命中。所以地址表必须细到 token,分配也要能按 token 分。这一条决定了它和块表方案的所有差别。

## Part 2|两级表:请求到槽,槽到 KV

### 2.1 第一张表:每个请求一行,一行记它所有 token 的槽号

SGLang 不用块表。它给每个在飞的请求分一行,这一行的长度是模型的最大上下文长度,每一格放一个整数,记这个位置的 token 的 KV 存在哪个槽。这张表叫请求到 token 池(ReqToTokenPool),整张表是一个二维整数张量,行数是最大并发请求数加一,列数是最大上下文长度。

请求进来时从空闲行里取一行,请求结束时把行还回去。取行的动作从空闲列表尾部弹,弹几个就是几个操作,不用扫整个列表。每一行还配一个代数计数,每次被重新分出去就加一,用来在异步路径上识别一个槽号是不是已经易主。

第 0 行是保留的。CUDA graph 补齐的假请求默认落在第 0 行,它们的读写都打在这里,不会污染真实请求。

这张表的代价是实打实的:每格四字节,行数乘列数。最大并发四千、上下文十三万时,这张表就是二十亿字节。它按最大值一次分配,不随实际长度伸缩。这是用显存换「按 token 寻址」的第一笔账。

### 2.2 第二张表:每个槽一份 KV,按层各一份

第二张表叫 token 到 KV 池(TokenToKVPool)。它按层分,每一层各有一个 K 张量和一个 V 张量,张量的第一维就是槽号,后两维是 KV 头数和头维度。槽号在所有层通用:一个 token 在第 0 层用第 137 号槽,在第 31 层也用第 137 号槽。所以第一张表只需要记一个数。

槽的总数是启动时算出来的(Part 6),再加一页。多出来的那一页从第 0 号槽开始,和第一张表的第 0 行一样是给假请求写垃圾用的。

三种物理排布可选。默认是 NHD,一个槽就是一行,写入是按行散射;HND 把页和头折成一个索引,让按头分页的 kernel 直接消费;AMD 上还有一种向量化的五维排布,只有 AITER 后端认。排布是构造时定死的,kernel 看到什么形状取决于它。

FP8 精度的 KV 在存储上是按无符号八位整数存的,取出来时再看成 FP8。这是因为 PyTorch 的按索引写入不支持 FP8 张量,不是精度上的考虑。

### 2.3 为什么是两级而不是块表

块表记的是「第几块」,块内位置靠算。这里的表记的是「第几个槽」,槽就是最小单位。两级表的好处只有一个,但正是 SGLang 要的:**任意一个 token 的 KV 可以单独指向任意一个槽** 。前缀命中到第 1000 个 token 时,这一行的前 1000 格照抄缓存树里的槽号,第 1001 格开始才分新槽;命中的那一段不需要对齐到任何块边界。

代价也直接:表大(2.1 那笔账),以及 kernel 读 KV 时要多一次间接寻址。后一条各注意力后端自己消化,它们在每步开始时从这张表里把本批请求的槽号取出来整理成自己要的格式(有的要页表,有的要扁平索引),这一步在 06 章。

## Part 3|分配器:按 token 分,还是按页分

### 3.1 默认按 token 分

分配器管的是第二张表的槽号。page_size 这个参数不填时默认解析成 1,也就是一个槽就是一页。这时用的是最简单的分配器:一个空闲槽号张量,分配就切走前面 n 个,回收就拼到后面。没有页的概念,也就没有页内碎片。

只有 PD 分离时多一步:回收的槽号先放进暂存区,等到不够用了再和空闲区合并并排序。排序是为了让传输侧拿到尽量连续的槽号,和 PD 无关的部署不排。

### 3.2 什么时候必须按页分

页大于 1 不是用户的偏好,是后端的要求。FlashMLA 和 HPC-Ops 只认 64;TensorRT-LLM 的 MLA、tokenspeed、CuteDSL 三个 MLA 后端只认 32 或 64;TensorRT-LLM 的 MHA 认 16 到 128。选了这些后端,启动时配置层会把 page_size 改过去并打一行警告。用 MLA 模型跑主流后端,实际上都在按页分。

按页分时换成分页分配器,空闲列表里放的是页号,分出去的槽号总是页对齐的整段。

### 3.3 一批请求怎么一次分完

分页分配器给 prefill 和 decode 各写了一个 Triton kernel,一次处理整批请求,不在 Python 里逐个请求循环。

prefill 那个 kernel 把每个请求要新分的 token 分成三段:先填满它上一页剩下的空位;再整页整页地取新页;最后一段不满一页的再取一页。三段的边界由前缀长度和目标长度算出,每个 token 只要知道自己落在哪一段,就能算出自己的槽号。decode 那个 kernel 更简单:序列长度跨过页边界才取新页,否则槽号就是上一个槽号加一。

调用 kernel 之前有一步保守估计:假设每个请求都会用到一张新页,先按这个上限去问缓存树要空间,不够就先驱逐。这一步宁可多算,因为 kernel 跑起来之后没有回头路。

### 3.4 回收:按页整页回收,并且攒着一起回收

按页分配的回收是把槽号除以页大小得到页号,去重后整页放回。这意味着一页里只要还有一个 token 在用,整页都不能回收,这是分页的固有代价,页越大越明显。

回收还可以分组:先开一个组,期间所有回收的槽号只是记下来,组结束时一次拼接、一次回收。调度器在处理一批请求的结束时就是这么做的,把几十次小回收压成一次。

## Part 4|一步里的分配走读

### 4.1 prefill:先拿行,再拿槽,再写表

一个新请求进入 prefill 批时,已经从缓存树拿到了它命中的前缀槽号(04 章的事)。分配按这个顺序走:

1. 给请求取一行。取不到直接抛错,而不是回退,因为准入闸门(02 章)本来就应该保证行够用,取不到说明闸门算错了。
2. 给这次要算的新 token 取槽。先按需要的数量问缓存树能不能驱逐出足够空间,再让分配器分。按 token 分就是切走 n 个;按页分就跑 3.3 的 kernel。
3. 把这一行写好:前缀那段照抄命中的槽号,新 token 那段填刚分的槽号。
4. 分到的新槽号作为写入位置交给前向。每一层的注意力算完 K 和 V,按这些位置写进第二张表。

写入位置不是裸张量,是一个小结构体,里面除了主位置还带滑动窗口子池的位置和全注意力子池的位置。这样后端只要发一次写入调用,不用关心底下是哪种池。

### 4.2 decode:一个请求一个槽

decode 每步给每个请求分一个槽。上一个槽号从第一张表里查(位置是序列长度减一),新槽号按页规则算出来,写到序列长度那一格,序列长度加一。每个请求身上记两个长度:已分配的和已提交的。推测解码时这两个数会分开,草稿 token 先分配、验证通过才提交,验证失败的那段在请求结束时按「多分了」处理。

### 4.3 结束:哪些槽留下由缓存树决定

请求结束时,分配层自己不决定槽的去留。它把请求交给缓存树,树决定哪一段留下当前缀缓存、哪一段直接回收(04 章)。分配层只负责两件事:多分配却没提交的那段尾巴整页回收,以及把请求的那一行还给第一张表。

抢占走的是同一条路,区别是不把 KV 插进缓存树,因为抢占就是为了立刻腾空间。

## Part 5|池的家族:模型结构决定用哪种池

### 5.1 同一个模型里可能有三种「历史」

MHA 和 GQA 的层存 K 和 V;MLA 的层只存一个压缩向量;滑动窗口的层只需要保留最近一个窗口;Mamba 和线性注意力的层根本不存逐 token 的东西,只存一份固定大小的状态。今天的模型常把这几种层混在一起。第二张表因此长成了一个家族,启动时按模型结构挑一种。

| 池 | 每个槽存什么 | 什么模型用 |
|---|---|---|
| MHA 池 | 每层一份 K 和一份 V,形状是头数乘头维 | Llama、Qwen 这类标准结构 |
| MLA 池 | 每层一个向量,长度是潜向量维加 RoPE 维;V 就是这个向量的前一段视图 | DeepSeek V2 / V3 |
| DSA 池 | MLA 池再加一份索引器缓存 | DeepSeek V3.2 这类稀疏注意力 |
| 滑动窗口混合池 | 两个子池:全注意力层一个,窗口层一个,各自独立计数 | Gemma 这类窗口与全注意力交替 |
| 线性混合池 | 全注意力层一个 KV 池,加一个按请求分槽的状态池(卷积状态加时间状态) | Qwen3-Next、Nemotron 这类 Mamba 混合 |
| MiniMax 稀疏池 | 主池加索引器池,索引器分只存 K 的层与存 K 和 V 的层 | MiniMax 稀疏注意力 |
| FP4 / MXFP8 池 | 数据张量加缩放因子张量 | 开了低精度 KV 时套在上面几种之外 |

### 5.2 窗口层的 KV 单独计数

滑动窗口混合池把全注意力层和窗口层分成两个子池,各有各的槽总数。两边的比例由一个参数决定,窗口层的槽数是全注意力层的多少分之一。窗口层的槽在 token 滑出窗口后就能提前回收,不用等请求结束,分配走读里 prefill 和 decode 开头都有一步「先回收滑出窗口的槽」。

### 5.3 状态型的层按请求分槽,而且会卡并发

Mamba 层没有逐 token 的 KV,只有每个请求一份状态。所以混合模型的第一张表也换了一种:每个请求取一行的同时,再从状态池取一个槽。状态池的槽数是独立配置的,启动时按显存比例切出来。这带来一个不显眼的后果:**并发上限可能被状态池卡住** ,而不是被 KV 池卡住。状态池每个请求要占的槽数在开前缀缓存时是三份(树上留一份、在算一份、乒乓一份),所以最大并发是状态槽数除以三。日志里会明说是被这个卡住的。

### 5.4 可选的统一池:一块字节缓冲里装所有子池

以上各种混合池都是「几个独立张量拼起来」,各自的容量启动时就切死。还有一种可选的统一池,把整个 KV 预算当成一块无类型的字节缓冲,两个子池从两端往中间长,中间可以夹几个浮动的子池。哪种层用得多,哪个子池就多占。代价是上层看到的槽号都是虚拟的,分配器要维护虚拟到物理的映射表,回收时还要压缩。这条路默认不开。

## Part 6|显存账:能放多少 token

### 6.1 预算怎么算

模型权重装载完成后量一次剩余显存,减去两样东西,剩下的全给 KV:

- 运行期余量:模型装载前的显存总量乘以(1 减去 mem_fraction_static)。这就是这个参数的真正含义:它不是「KV 占多少」,而是「权重加 KV 一共占多少」,余量留给激活和 CUDA graph。
- 多模态保留量:多模态模型再扣一块。

剩下如果小于等于零,启动直接报错,并算出最小可行的 mem_fraction_static 打在错误信息里。

### 6.2 一个 token 值多少字节

预算除以每 token 的字节数就是槽总数,再向下取整到页对齐。每 token 字节数按模型结构算:

- MHA 池:本卡分到的 KV 头数,乘以 K 头维加 V 头维,乘以层数,乘以精度字节数。
- MLA 池:潜向量维加 RoPE 维,乘以层数,乘以精度字节数;DSA 再加索引器缓存那份。
- 混合模型只数全注意力层,窗口层和状态层另算。
- FP4 再加上缩放因子张量。

算例:8 个 KV 头、头维 128、32 层、BF16,每 token 是 8 乘 256 乘 32 乘 2 等于 131072 字节,也就是 128 KB。50 GB 预算能放约四十万个 token。

### 6.3 三道外部约束

算出来的槽数还要过三道:用户给的上限只能往下压,给高了打警告用探测值;流水线并行时各段层数不同,取所有段的最小值;开了 Mamba 时状态池另外分账。

### 6.4 最大并发数从槽数推

最大并发数默认按槽总数除以上下文长度再乘 512 估,夹在 2048 到 4096 之间;用户指定时按数据并行副本数平分。无论哪种,都不超过槽总数的一半。混合模型再受 5.3 那条状态池限制。

这个数决定了 2.1 那张表的行数,也就决定了那二十亿字节。

### 6.5 一条运维经验

官方文档给的判断方法很朴素:服务就绪前的日志里有一行剩余显存,落在 5 到 8 GB 之间是合适的;高了就把 mem_fraction_static 往上调,低了就往下调。另一个办法是每次加 0.01,加到 OOM 为止再退一步。

## Part 7|显存见底:先驱逐,再抢占

### 7.1 每一步 decode 之前先问一次

每步 decode 之前,调度器问分配器:下一步要的槽数够不够。分配器先让缓存树把没人用的前缀驱逐掉,再比较空闲槽数。抢占循环收敛在同一个判断上,所以分配器这边的短缺会走抢占,不会走到分配失败抛错。

### 7.2 抢占谁:输出最少的先走

抢占按一个顺序把在飞请求从批里踢出去,直到空间够。默认顺序是**已经生成的 token 最少的先被踢** ,同样少的话 prompt 更长的先被踢,也就是踢丢掉的工作最少的那个。开了优先级调度时先按优先级,再按这个。批里至少留一个请求。

被踢的请求释放全部 KV,不插进缓存树,重新排队等下一次 prefill 从头算。这是默认行为。只有 decode 分离节点例外:它把 KV 备份到 host 再释放,恢复时拷回来不重算,备份放不下就只能中止请求。

踢完之后还会多驱逐一点:按剩余请求数乘一个步数,给接下来几步 decode 预留,避免下一步又抢占。

### 7.3 抢占太频繁怎么办

调度保守度这个参数控制准入闸门估计输出长度时的松紧。日志里频繁出现「KV cache pool is full. Retract requests」就把它调大;反过来 token 使用率总在九成以下、队列却有请求在等,就把它调小。偶尔抢占一次是正常的。

## Part 8|图解

### 8.1 两张表与一个请求的一行

```text
  ReqToTokenPool  (行 = 请求槽,列 = 上下文位置,格 = KV 槽号)

        位置:  0     1     2     3     4     5   ...  max_ctx-1
  行 0   [ 0     0     0     0     0     0   ...    0 ]   <- 保留给假请求
  行 1   [ 137   138   139   901   902   903 ...      ]   <- 请求 A:前 3 个是命中的前缀槽
  行 2   [ 137   138   140   141   ...              ]   <- 请求 B:和 A 共享前两个槽
  ...

  TokenToKVPool  (每层一对张量,第一维 = KV 槽号)

  层 0   K: [槽 0 | 槽 1 | ... | 槽 137 | 槽 138 | ... ]   V: 同形状
  层 1   K: [ ...                                      ]   V: ...
  ...
  层 L-1

  槽 0 所在的那一页是垫片,假请求的写入落在这里。
```

请求 A 和 B 在位置 0 和 1 指向同样的槽,这就是前缀共享在两级表上的样子:表里存的是槽号,槽号可以重复出现在多行里。谁能共享、什么时候回收,04 章讲。

### 8.2 一个请求的 KV 一生

```text
  到达 -> 缓存树匹配前缀 -> 取一行 -> 为新 token 取槽 -> 写行
       -> prefill 前向:每层写 K/V 到新槽
       -> 每步 decode:取一个槽,写行末尾,前向写 K/V
       -> 结束:缓存树决定留哪段;多分的尾巴回收;还行
  途中显存见底 -> 先驱逐无人用的前缀 -> 不够就抢占:输出最少的先释放并重排队
```

## Part 9|机制之外:源码里额外读到的

### 9.1 行和页的第 0 号都是垫片

第一张表的第 0 行和第二张表第 0 号槽所在的页,都留给 CUDA graph 补齐的假请求。这样补齐的批不需要任何特判,假请求照常读写,只是读写的是垃圾区。

### 9.2 分配之前的估计故意偏大

按页分配时,估计需求按「每个请求一张新页」算,再去驱逐。批里大多数请求其实用不到新页,多驱逐的部分是被当成保险付掉的。

### 9.3 槽号易主靠代数计数识别

第一张表每一行有一个代数,重新分配就加一。异步路径上拿着旧槽号的元数据,可以用代数判断这个槽是不是已经给了别的请求。

### 9.4 写入位置捆成一个结构体

后端写 KV 时拿到的不是一个位置张量,而是主位置、窗口子池位置、全注意力子池位置三个一组。后端按池的类型用其中一个或几个,发一次写入调用就够。分段 CUDA graph 和数据并行补齐会把位置按层截短,结构体在构造时把另外两个位置也切到同样长度。

### 9.5 读 KV 之前可能要等一层

取某一层的 K 或 V 张量的接口上挂了一个按层的计数器。开了逐层加载(05 章的分层缓存,以及 PD 分离的逐层传输)时,读第 i 层要先等第 i 层的数据到齐。注释明说这个接口只给注意力后端用,不要拿去做统计。

### 9.6 先占虚拟地址,捕获完再补物理页

有一种可选模式,KV 池先只保留一段虚拟地址上界,等 CUDA graph 捕获完、知道激活实际占多少之后,再把物理页补上去。这时槽总数会向上对齐到页边界,而不是向下。

### 9.7 PD 分离用专门的显存池

开了 NVLink 传输的 PD 分离时,KV 张量从一个自定义的显存池里分,而不是 PyTorch 的默认分配器,这样传输引擎可以直接注册这块内存。

### 9.8 两种分配失败,两种态度

取行失败直接抛错,错误信息让人调小最大并发,因为这是准入算错了;取槽失败也抛错,但先把缓存树打印出来,错误信息让人调小 batch。两者都不静默回退。

## Part 10|对比与决策

### 10.1 和 vLLM 的 KV 管理比

| 维度 | vLLM | SGLang |
|---|---|---|
| 地址表 | 块表,记块号,块内位置靠算 | 两级表,记槽号,细到 token |
| 默认粒度 | 块大小 16 | 页大小 1,后端要求时改成 32 或 64 |
| 表的大小 | 块数级 | 最大并发乘最大上下文,四字节一格,可达 GB 级 |
| 前缀命中粒度 | 整块 | 单个 token(要看后端是否按页) |
| 显存预算 | 按比例给 vLLM 全部,探测激活后剩下给 KV | 权重加 KV 占比例,余量按公式扣 |
| 抢占 | 释放重算 | 释放重算;decode 分离节点备份到 host |
| 抢占顺序 | 见 vLLM 调度器章 | 输出最少的先踢 |
| 混合模型 | KV 分组,每组自己的块表 | 家族里挑一种池,窗口和状态各自计数 |

两边都是「逻辑连续、物理离散」,差别全在粒度:vLLM 把粒度定在块,换来小表和天然对齐;SGLang 把粒度定在 token,换来 radix 树需要的任意位置指向,代价是表大和每次读都多一跳。

### 10.2 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| mem_fraction_static | 按显卡启发式 | 权重加 KV 占显存的比例 | 就绪前日志里剩余显存高于 8 GB 就往上加,每次 0.01 |
| max_total_tokens | 探测值 | KV 槽总数上限 | 只能往下压;想复现某个并发上限时用 |
| max_running_requests | 按槽数推,2048 到 4096 | 最大并发 | 抢占频繁时调小;它决定第一张表的大小 |
| page_size | 1 | 分配粒度 | 不要手调,后端会改 |
| kv_cache_dtype | auto | KV 精度 | FP8 能把槽数翻倍,先确认后端支持反量化融合 |
| swa_full_tokens_ratio | 由模型定 | 窗口层槽数与全注意力层槽数之比 | 窗口模型槽不够时调 |
| max_mamba_cache_size | 按比例 | 状态池槽数 | 混合模型并发被状态池卡住时调 |
| schedule_conservativeness | 1.0 | 准入估计输出长度的松紧 | 抢占多调大,利用率低调小 |
| enable_memory_saver | 关 | KV 池可整体释放再恢复 | RL 训练中换权重时用 |

### 10.3 排障先看什么

- 日志里 token usage 在 0.9 以上是健康;低于 0.9 且队列有请求,是准入太保守。
- 「KV cache pool is full. Retract requests」每分钟一次以内可以不管,频繁出现先调保守度,再考虑减并发。
- 混合模型并发上不去,先看日志有没有「capped by the mamba state cache」。
- 启动就报显存不够,错误信息里给了最小可行的 mem_fraction_static,照抄即可。

### 10.4 常见误区

- 页大小 1 不等于「没有分页」。逻辑上还是槽号表加间接寻址,只是页恰好等于一个 token。
- max_total_tokens 不能把容量调高,只能调低。
- 最大并发不只受 KV 槽数限制,还受第一张表的行数和状态池的槽数限制,三者取最小。
- 抢占默认不备份 KV,被踢的请求重算全部前缀,只有 decode 分离节点例外。
- 混合模型里窗口层的槽会在请求还在跑的时候被回收,这是设计,不是泄漏。
