# SGLang 03|KV 存储:每种模型结构与部署形态下,KV 放在哪、能放多少

注意力 kernel 算一个请求时,要拿到它每一个历史 token 的 K 和 V 在显存里的地址。这一章讲 SGLang 用哪两张表记这些地址、谁来分配和回收、显存能装多少 token、装不下时先踢谁,以及这些决定在长上下文、高并发、MLA 模型、Mamba 混合模型、PD 分离、RL 训推一体这些负载下各自撞上哪道墙。

KV cache 为什么必须存在、朴素存法的三种浪费、分页的思想、页多大合适,vLLM 解读的「PagedAttention 与 KV Cache 管理」一章已经讲透,本章不重讲;前缀怎么复用见 04 章,显存放不下往外放见 05 章。全章内容都在源码上逐条核对过;每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:地址细到 token 是为了下一章,其余全是显存账

### 1.1 痛点只有一句

一张卡上同时跑 100–1000 个请求,每个请求 2000–8000 个 token,每个 token 在每一层各有一份 K 和一份 V。kernel 算第 n 个 token 的注意力时,要把这个请求前面所有 token 的 K 和 V 一个不落地读出来。**谁记得每个 token 的 K 和 V 放在显存哪里,谁在请求来了给它腾地方、走了把地方收回来,谁在腾不出来时决定牺牲哪个请求** ,这就是 KV 存储层的全部工作。

SGLang 比通用做法多一个要求:它的前缀缓存要命中到单个 token,不是整块整块地命中。所以地址表必须细到 token,分配也要能按 token 分。这一条决定了它和块表方案的所有差别,也决定了它要为此多付的那笔显存。

### 1.2 它动的指标

| 指标 | KV 存储层怎么动它 | 代价落在哪 |
|---|---|---|
| 并发上限 | 槽总数、地址表行数、状态池槽数三道闸取最小,哪道先到顶并发就停在哪 | 三道闸各有各的参数,调错一道另两道不动 |
| 显存效率 | 每 GB 显存装多少 token:池的类型定每 token 字节数,页大小定尾页浪费 | 页大于 1 时每请求平均浪费半页 |
| 吞吐 | 一步能进批的 token 数被空闲槽数封顶 | 分配前按每请求一页高估,会多驱逐前缀 |
| TTFT | 地址粒度决定前缀命中粒度;被抢占的请求要重算整段 prompt | 后端钉页后命中退化到页对齐 |
| 稳定性 | 见底时先驱逐再抢占,不走分配失败;取行失败直接抛错 | 抢占风暴时每步都在踢人 |
| 可复现 | RL 换权重后 KV 池整体释放再恢复,旧 KV 一个不留 | 释放只能在服务完全空闲时做 |

### 1.3 八种负载,八种放法

| 负载 | KV 在这种负载下的形状 | 撞哪道墙 | 最在乎 |
|---|---|---|---|
| 长上下文 | 一个请求就占几万个槽;地址表每行按最大上下文买断 | 槽总数;地址表本身可达 GB 级 | 显存效率 |
| 高并发短请求 | 1000–5000 个请求各占 100–1000 个槽 | 地址表行数;并发默认封在 4096 | 并发上限 |
| MLA 模型 | 每 token 只存一个压缩向量,字节数是 MHA 的几分之一 | 主流 MLA 后端要求按 32 或 64 的页分,token 级命中失效 | TTFT、显存效率 |
| 窗口与 Mamba 混合模型 | 三种层三种历史:全量 KV、一个窗口、一份固定状态 | 状态池另算账,并发可能被它先卡住 | 并发上限 |
| 多模态 | 图像编码器要显存,预算先扣一块 | 槽总数比纯文本模型少 | 显存效率 |
| PD 分离 | KV 要从 P 端传到 D 端,槽号越连续传输越省 | 回收的槽号要攒着排序;D 端抢占要备份到 host | 稳定性 |
| 推测解码 | 草稿 token 先占槽,验证通过才算数 | 每个请求身上两个长度:已分配与已提交 | 吞吐 |
| RL 训推一体 | 训练时 KV 池要整体让出显存,推理时再拿回来 | 释放、恢复、清缓存三步都有前提 | 可复现 |

共同点是「槽是唯一的分配单位,谁拿到槽号谁就能写」;不同点是每种负载把压力压在不同的表上:长上下文压第二张表,高并发压第一张表,混合模型压状态池,PD 与 RL 压的不是容量而是槽号的连续性与整池的可释放性。

### 1.4 由此对存储层的三个要求

1. **任意一个 token 的 KV 能单独指向任意一个槽**,分叉与命中不对齐到任何块边界。这是下一章的前提。
2. **池随模型结构换,分配接口不换**。MHA、MLA、窗口、Mamba、稀疏索引、低精度,启动时挑一种池,调度器和后端看到的分配、写入、回收接口一样。
3. **见底时丢最少的工作,而且不静默**。先驱逐没人用的前缀,再踢在飞请求;踢谁按丢掉的工作量排;真分不出来就报错并说清调哪个参数。

### 1.5 两个公式:能放多少 token,能开多少并发

槽总数由启动时的显存账定:

$$\text{槽数} = \left\lfloor \frac{\text{装载后剩余显存} - \text{装载前总显存} \times (1 - f) - \text{多模态保留}}{\text{每 token 字节数}} \right\rfloor_{\text{页对齐}}$$

f 就是 mem_fraction_static。并发上限是三道闸取最小:

$$\text{并发} = \min\left(\frac{\text{槽数}}{2},\ \text{地址表行数},\ \frac{\text{状态池槽数}}{3}\right)$$

第三项只在 Mamba 混合模型上存在。Part 5 逐项展开这两个公式里的每一个数从哪来。

## Part 2|两级表:任意 token 指任意槽,代价是一张按最大值买断的表

### 2.1 第一张表每格记一个槽号,所以任何位置都能指向任何槽

SGLang 不用块表。它给每个在飞的请求分一行,这一行的长度是模型的最大上下文长度,每一格放一个整数,记这个位置的 token 的 KV 存在哪个槽。这张表叫请求到 token 池(ReqToTokenPool),整张表是一个二维 32 位整数张量,行数是最大并发请求数加 1,列数是最大上下文长度。

请求进来时从空闲行里取一行,请求结束时把行还回去。取行的动作从空闲列表尾部弹,弹几个就是几个操作,不用扫整个列表。每一行还配一个代数计数,每次被重新分出去就加一,用来在异步路径上识别一个槽号是不是已经易主。

一行里的格子彼此没有关系:第 999 格可以指向第 137 号槽,第 1000 格可以指向第 90000 号槽。前缀命中到第 1000 个 token 时,这一行的前 1000 格照抄缓存树里的槽号,第 1001 格开始才分新槽,命中的那一段不需要对齐到任何块边界。这就是 1.4 的第 1 条。

### 2.2 第二张表槽号跨层通用,所以第一张表只记一个数

第二张表叫 token 到 KV 池(TokenToKVPool)。它按层分,每一层各有一个 K 张量和一个 V 张量,张量的第一维就是槽号,后两维是 KV 头数和头维度。槽号在所有层通用:一个 token 在第 0 层用第 137 号槽,在第 31 层也用第 137 号槽。所以第一张表只需要记一个数,不需要记「每层各在哪」。

槽的总数是启动时算出来的(Part 5),再加一页。多出来的那一页从第 0 号槽开始,和第一张表的第 0 行一样是给假请求写垃圾用的。

三种物理排布可选。默认是 NHD,一个槽就是一行,写入是按行散射;HND 把页和头折成一个索引,让按头分页的 kernel 直接消费;AMD 上还有一种向量化的五维排布,只有 AITER 后端认。排布是构造时定死的,kernel 看到什么形状取决于它。

### 2.3 这张表的大小由并发决定,不由实际长度决定

第一张表的代价是实打实的:每格 4 字节,行数乘列数,按最大值一次分配,不随实际长度伸缩。最大并发 4096、上下文 131072 时,这张表就是 2 GB。**跑短请求也是 2 GB,因为列数按最大上下文买断;跑长上下文也是 2 GB,因为行数按最大并发买断。**

行数从哪来:不指定时,按槽总数除以上下文长度再乘 512 估一个数,夹在 2048 到 4096 之间;指定了就按数据并行副本数平分。无论哪种,都不超过槽总数的一半。想把这张表压小,唯一有效的手段是把最大并发调低,上下文长度是模型定的。

### 2.4 块表做不到的只有一件事,而那件事正是下一章要的

块表记的是「第几块」,块内位置靠算,表的大小是块数级,几十 MB。两级表记的是「第几个槽」,槽就是最小单位,表的大小是并发乘上下文,GB 级。两级表的好处只有一个:**任意 token 单独指向任意槽**。代价有两笔:表大,以及 kernel 读 KV 时要多一次间接寻址。后一条各注意力后端自己消化,它们在每步开始时从这张表里把本批请求的槽号取出来整理成自己要的格式,有的要页表,有的要扁平索引,这一步在 06 章。

SGLang 认为这笔账值得付,理由全在下一章:多轮对话和 agent 循环的分叉点在随机位置,块表方案在分叉处要复制一块,两级表不用。如果一个部署根本不开前缀缓存,这张表就是纯开销,这时应该把最大并发压到实际需要的数。

## Part 3|分配:默认按 token,但 MLA 后端会把你钉到页

### 3.1 页大小 1 时分配器就是一次切片

分配器管的是第二张表的槽号。page_size 这个参数不填时默认解析成 1,一个槽就是一页。这时用的是最简单的分配器:一个空闲槽号张量,分配就切走前面 n 个,回收就拼到后面。没有页的概念,也就没有页内碎片。

只有 PD 分离时多一步:回收的槽号先放进暂存区,等到不够用了再和空闲区合并并排序。排序是为了让传输侧拿到尽量连续的槽号,和 PD 无关的部署不排。

### 3.2 页大于 1 不是偏好,是后端的要求,而且命中粒度跟着变

页大于 1 不是用户选的,是后端要的。FlashMLA 和 HPC-Ops 只认 64;TensorRT-LLM 的 MLA、tokenspeed、CuteDSL 三个 MLA 后端只认 32 或 64;TensorRT-LLM 的 MHA 认 16 到 128。选了这些后端,启动时配置层会把 page_size 改过去并打一行警告。**用 DeepSeek 这类 MLA 模型跑主流后端,实际上都在按页分,而下一章的树在按页分时只能命中到页边界**:64 个 token 的页,最坏丢 63 个 token 的命中。1.2 表里 TTFT 那格的代价就是这一条。

按页分时换成分页分配器,空闲列表里放的是页号,分出去的槽号总是页对齐的整段。

### 3.3 整批一次分完,而且故意高估

分页分配器给 prefill 和 decode 各写了一个 Triton kernel,一次处理整批请求,不在 Python 里逐个请求循环。prefill 那个 kernel 把每个请求要新分的 token 分成三段:先填满它上一页剩下的空位;再整页整页地取新页;最后一段不满一页的再取一页。三段的边界由前缀长度和目标长度算出,每个 token 只要知道自己落在哪一段,就能算出自己的槽号。decode 那个 kernel 更简单:序列长度跨过页边界才取新页,否则槽号就是上一个槽号加 1。

调用 kernel 之前有一步保守估计:假设每个请求都会用到一张新页,先按这个上限去问缓存树要空间,不够就先驱逐。这一步宁可多算,因为 kernel 跑起来之后没有回头路。**代价是命中率**:批里大多数请求其实用不到新页,多驱逐的那部分前缀是被当成保险付掉的。

### 3.4 整页回收:一页里剩一个 token 在用,整页都不能还

按页分配的回收是把槽号除以页大小得到页号,去重后整页放回。一页里只要还有一个 token 在用,整页都不能回收,页越大越明显。

回收还可以分组:先开一个组,期间所有回收的槽号只是记下来,组结束时一次拼接、一次回收。调度器在处理一批请求的结束时就是这么做的,把几十次小回收压成一次。

### 3.5 一步里的顺序:取行失败就是准入算错了

一个新请求进入 prefill 批时,已经从缓存树拿到了它命中的前缀槽号。分配按这个顺序走:

1. 给请求取一行。取不到直接抛错,而不是回退,错误信息让人调小最大并发,因为准入闸门(02 章)本来就应该保证行够用,取不到说明闸门算错了。
2. 给这次要算的新 token 取槽。先按需要的数量问缓存树能不能驱逐出足够空间,再让分配器分;仍然不够就把缓存树打印出来再抛错,错误信息让人调小 batch。两种失败都不静默回退。
3. 把这一行写好:前缀那段照抄命中的槽号,新 token 那段填刚分的槽号。
4. 分到的新槽号作为写入位置交给前向。每一层的注意力算完 K 和 V,按这些位置写进第二张表。写入位置不是裸张量,是一个小结构体,里面除了主位置还带滑动窗口子池的位置和全注意力子池的位置,后端发一次写入调用就够。

decode 每步给每个请求分一个槽:上一个槽号从第一张表里查,新槽号按页规则算出来,写到序列长度那一格,序列长度加 1。每个请求身上记两个长度,已分配的和已提交的。推测解码时这两个数会分开:草稿 token 先分配、验证通过才提交,验证失败的那段在请求结束时按「多分了」处理。

请求结束时,分配层自己不决定槽的去留。它把请求交给缓存树,树决定哪一段留下当前缀缓存、哪一段直接回收。分配层只负责两件事:多分配却没提交的那段尾巴整页回收,以及把请求的那一行还给第一张表。抢占走的是同一条路,区别是不把 KV 插进缓存树,源码注释说得直白:抢占就是为了立刻腾空间。

## Part 4|池家族:模型结构决定用哪种池,并发上限可能被状态池卡住

### 4.1 同一个模型里可能有三种历史

MHA 和 GQA 的层存 K 和 V;MLA 的层只存一个压缩向量;滑动窗口的层只需要保留最近一个窗口;Mamba 和线性注意力的层根本不存逐 token 的东西,只存一份固定大小的状态。今天的模型常把这几种层混在一起。第二张表因此长成了一个家族,启动时按模型结构挑一种。

| 池 | 每个槽存什么 | 什么模型用 |
|---|---|---|
| MHA 池 | 每层一份 K 和一份 V,形状是头数乘头维 | Llama、Qwen 这类标准结构 |
| MLA 池 | 每层一个向量,长度是潜向量维加 RoPE 维;V 就是这个向量的前一段视图 | DeepSeek V2 / V3 |
| DSA 池 | MLA 池再加一份索引器缓存 | DeepSeek V3.2 这类稀疏注意力 |
| 滑动窗口混合池 | 两个子池:全注意力层一个,窗口层一个,各自独立计数 | Gemma 这类窗口与全注意力交替 |
| 线性混合池 | 全注意力层一个 KV 池,加一个按请求分槽的状态池,存卷积状态加时间状态 | Qwen3-Next、Nemotron 这类 Mamba 混合 |
| MiniMax 稀疏池 | 主池加索引器池,索引器分只存 K 的层与存 K 和 V 的层 | MiniMax 稀疏注意力 |
| FP4 / MXFP8 池 | 数据张量加缩放因子张量 | 开了低精度 KV 时套在上面几种之外 |

分配、写入、回收的接口在整个家族里一样,调度器不知道底下是哪种池。这是 1.4 的第 2 条。

### 4.2 窗口层的槽在请求还在跑时就被回收,这是设计不是泄漏

滑动窗口混合池把全注意力层和窗口层分成两个子池,各有各的槽总数。两边的比例由一个参数决定,窗口层的槽数是全注意力层的多少分之一。窗口层的槽在 token 滑出窗口后就能提前回收,不用等请求结束,分配走读里 prefill 和 decode 开头都有一步「先回收滑出窗口的槽」。看日志会发现窗口子池的使用率在请求中途下降,那不是泄漏,是窗口在滑。

### 4.3 Mamba 混合模型的并发上限是状态槽数除以 3

Mamba 层没有逐 token 的 KV,只有每个请求一份状态。所以混合模型的第一张表也换了一种:每个请求取一行的同时,再从状态池取一个槽。状态池的槽数是独立配置的,启动时按显存比例切出来。

后果不显眼但很硬:**并发上限可能被状态池卡住,而不是被 KV 池卡住**。开前缀缓存时每个请求要占三份状态槽,树上留一份、在算一份、乒乓一份,所以最大并发是状态槽数除以 3。日志里会明说是被这个卡住的。调 mem_fraction_static 和 max_total_tokens 对这道闸都没用,要调的是状态池自己的参数。

### 4.4 低精度 KV 只是换了池,不换分配器

FP8 精度的 KV 在存储上按无符号 8 位整数存,取出来时再看成 FP8。原因是 PyTorch 的按索引写入不支持 FP8 张量,不是精度上的考虑。FP4 和 MXFP8 各多一份缩放因子张量,每 token 字节数按数据加缩放算。这些池的槽号语义和 MHA 池一样,分配器和地址表都不知道精度变了。开 FP8 KV 能把槽数翻倍,但要先确认注意力后端支持融合反量化,否则每步多一次转换。

### 4.5 统一池默认不开:容量按层型浮动,代价是虚拟槽号

以上各种混合池都是「几个独立张量拼起来」,各自的容量启动时就切死:窗口层与全注意力层的比例、状态池的大小,定了就不动。还有一种可选的统一池,把整个 KV 预算当成一块无类型的字节缓冲,两个子池从两端往中间长,中间可以夹几个浮动的子池,哪种层用得多哪个子池就多占。代价是上层看到的槽号都是虚拟的,分配器要维护虚拟到物理的映射表,回收时还要压缩。这条路默认不开,混合模型的比例调不准时才值得试。

## Part 5|显存账与见底:mem_fraction_static 不是 KV 占比,抢占踢的是丢工作最少的

### 5.1 预算公式里减掉的是「总显存乘以一减比例」,所以比例含权重

模型权重装载完成后量一次剩余显存,减去两样东西,剩下的全给 KV:

- 运行期余量:模型装载前的显存总量乘以 1 减 mem_fraction_static。**这个参数不是「KV 占多少」,而是「权重加 KV 一共占多少」**,余量留给激活和 CUDA graph。同一个比例换一个更大的模型,给 KV 的就更少。
- 多模态保留量:多模态模型再扣一块给图像编码器。

剩下如果小于等于 0,启动直接报错,并算出最小可行的 mem_fraction_static 打在错误信息里,照抄即可。

### 5.2 一个 token 值多少字节,按模型结构算

预算除以每 token 的字节数就是槽总数,再向下取整到页对齐。每 token 字节数按池算:

- MHA 池:本卡分到的 KV 头数,乘以 K 头维加 V 头维,乘以层数,乘以精度字节数。
- MLA 池:潜向量维加 RoPE 维,乘以层数,乘以精度字节数;DSA 再加索引器缓存那份。
- 混合模型只数全注意力层,窗口层和状态层另算。
- FP4 再加上缩放因子张量。

算例:8 个 KV 头、头维 128、32 层、BF16,每 token 是 8 乘 256 乘 32 乘 2 等于 131072 字节,也就是 128 KB,50 GB 预算能放约 40 万个 token。换成 MLA:潜向量 512 加 RoPE 64、61 层、BF16,每 token 是 576 乘 61 乘 2 约 70 KB,同样 50 GB 能放约 73 万个 token。这就是 1.3 表里 MLA 模型显存效率高的来源,也是它被钉到页 64 时碎片账更值得算的原因(8.4)。

### 5.3 三道上限只能往下压

算出来的槽数还要过三道:用户给的 max_total_tokens 只能往下压,给高了打警告用探测值;流水线并行时各段层数不同,取所有段的最小值;开了 Mamba 时状态池另外分账。**没有任何参数能把槽数调到探测值以上**,想要更多槽只有三条路:调高 mem_fraction_static、开低精度 KV、换 MLA 模型。

### 5.4 每步 decode 前先问一次,短缺走抢占不走报错

每步 decode 之前,调度器问分配器:下一步要的槽数够不够。分配器先让缓存树把没人用的前缀驱逐掉,再比较空闲槽数。抢占循环收敛在同一个判断上,所以分配器这边的短缺会走抢占,不会走到分配失败抛错。分配失败抛错只发生在 prefill 侧,那是准入的错(3.5)。

### 5.5 抢占顺序:输出最少的先走,默认不备份

抢占按一个顺序把在飞请求从批里踢出去,直到空间够。默认顺序是**已经生成的 token 最少的先被踢**,同样少的话 prompt 更长的先被踢,也就是踢丢掉的工作最少的那个。开了优先级调度时先按优先级,再按这个。批里至少留一个请求。

被踢的请求释放全部 KV,不插进缓存树,重新排队等下一次 prefill 从头算。**默认不备份**。只有 decode 分离节点例外:它把 KV 备份到 host 再释放,恢复时拷回来不重算,备份放不下就只能中止请求。

踢完之后还会多驱逐一点:按剩余请求数乘一个步数,给接下来几步 decode 预留,避免下一步又抢占。

### 5.6 抢占太频繁是准入太松,不是显存太少

调度保守度这个参数控制准入闸门估计输出长度时的松紧。日志里频繁出现「KV cache pool is full. Retract requests」就把它调大到 1.3 左右;反过来 token 使用率总在 0.9 以下、队列却有请求在等,就把它调小到 0.3 左右。每分钟一次以内的抢占是正常的。先调这个,再考虑减并发。

### 5.7 和其他子系统的交互

RL 训推一体和 PD 分离对存储层提的要求最特别,其余一表带过。

**RL 训推一体:整池释放,只能在空闲时。** 训练框架把推理引擎和训练进程放在同一批卡上,训练那一段要把推理侧的显存让出来。释放接口按三类标签分别处理:KV 缓存、权重、CUDA graph。释放 KV 缓存时先清空缓存树,再让显存保存器暂停这一块;PD 分离的节点还要先把传输队列和预分配队列里的请求清掉。这个接口断言服务完全空闲才能调,有请求在飞就直接失败。恢复按相反顺序来。权重更新完成后有一个开关决定是否清缓存,开着就把整棵树清空,旧权重算出的 KV 一个不留,这是 1.2 表里可复现那一格。开 enable_memory_saver 才有这条路。

**PD 分离:槽号要连续,抢占要备份。** prefill 节点算完要把 KV 传给 decode 节点,传输按槽号段发,槽号越连续段数越少。所以 PD 模式下回收的槽号不直接归还,先攒进暂存区,不够用时合并排序再用(3.1)。开了 NVLink 传输时 KV 张量从一个自定义的显存池里分,而不是 PyTorch 的默认分配器,让传输引擎能直接注册这块内存。decode 节点抢占时不能像单机那样丢掉重算,因为它没有 prefill 的能力,所以备份到 host(5.5)。

| 子系统 | 它向存储层要什么 | 存储层给的东西 |
|---|---|---|
| 缓存树(04 章) | 请求结束时决定哪段留下 | 分配层不做去留判断,只回收树说不要的那段 |
| 准入与调度(02 章) | 每步知道还剩多少槽 | 空闲槽数加可驱逐槽数,分配前先驱逐 |
| 三层缓存(05 章) | 逐层加载时读第 i 层要等第 i 层到齐 | 取层张量的接口上挂按层计数器 |
| 推测解码(08 章) | 草稿先占槽、验证后才算数 | 每请求两个长度:已分配与已提交 |
| CUDA graph(07 章) | 补齐的假请求要能读写 | 第 0 行与第 0 页当垫片,不特判 |
| 多模态(14 章) | 编码器要显存 | 预算先扣保留量 |

## Part 6|图解

### 6.1 两张表与一个请求的一行

```text
  ReqToTokenPool  (行 = 请求槽,列 = 上下文位置,格 = KV 槽号)

        位置:  0     1     2     3     4     5   ...  max_ctx-1
  行 0   [ 0     0     0     0     0     0   ...    0 ]   <- 保留给假请求
  行 1   [ 137   138   139   901   902   903 ...      ]   <- 请求 A:前 3 个是命中的前缀槽
  行 2   [ 137   138   140   141   ...              ]   <- 请求 B:和 A 共享前两个槽
  ...

  TokenToKVPool  (每层一对张量,第一维 = KV 槽号)

  层 0   K: [槽 0 | 槽 1 | ... | 槽 137 | 槽 138 | ... ]   V: 同形状
  层 1   K: [ ...                                      ]   V: ...
  ...
  层 L-1

  槽 0 所在的那一页是垫片,假请求的写入落在这里。
```

请求 A 和 B 在位置 0 和 1 指向同样的槽,这就是前缀共享在两级表上的样子:表里存的是槽号,槽号可以重复出现在多行里,而且 B 在位置 2 就分叉了,分叉处不需要复制任何东西。谁能共享、什么时候回收,04 章讲。

### 6.2 一个请求身上的三条长度线

```text
  位置:     0 ........ p-1 | p ........ s-1 | s .. s+k-1 |
            前缀命中(照抄)  | 本次要算的新 token | 草稿 token   |
                             ^                ^            ^
                        prefix_len        seq_len     kv_allocated_len
                                           = kv_committed_len

  prefill:  取行 -> 为 [p, s) 取槽 -> 写行 -> 前向按槽写 K/V
  decode:   每步为 s 取 1 个槽,seq_len += 1
  spec:     草稿先占 [s, s+k),验证通过 committed 追上 allocated,失败的尾巴结束时整页回收
  结束:     树决定 [0, s) 里哪段留下;[committed, allocated) 回收;还行
  抢占:     全部释放,不进树;decode 分离节点先备份到 host
```

### 6.3 并发上限的三道闸

```text
  槽总数 ── ÷ 2 ──────────────────────────┐
                                          │
  地址表行数(max_running_requests,        ├── 取最小 ── 并发上限
    默认按 槽数/上下文×512 估,夹在        │
    2048–4096) ───────────────────────────┤
                                          │
  状态池槽数 ── ÷ 3(仅 Mamba 混合模型)───┘

  例:MHA 模型 40 万槽、上下文 8192:
     槽数/2 = 20 万;估计行数 = 400000/8192×512 = 25000 -> 夹到 4096;无状态池
     并发上限 = 4096,卡在地址表行数,和显存无关
```

### 6.4 显存见底的一步

```text
  每步 decode 前:需要 n 个槽
       │
       ├─ 缓存树驱逐无人引用的前缀 ──> 空闲 ≥ n ? ──是──> 分配,继续
       │                                  │否
       ▼                                  ▼
  抢占循环:按「输出最少、prompt 最长」排序,从尾部踢
       ├─ 单机:释放全部 KV,不进树,重排队(下次 prefill 从头算)
       └─ decode 分离:备份到 host 再释放;备份失败则中止请求
       │
       └─ 空间够了之后再多驱逐 (剩余请求数 × 预留步数) 个槽,防下一步又抢占
```

## Part 7|机制之外:源码里额外读到的

### 7.1 行和页的第 0 号都是垫片

第一张表的第 0 行和第二张表第 0 号槽所在的页,都留给 CUDA graph 补齐的假请求。补齐的批不需要任何特判,假请求照常读写,只是读写的是垃圾区。

### 7.2 分配之前的估计故意偏大

按页分配时,估计需求按「每个请求一张新页」算,再去驱逐。批里大多数请求其实用不到新页,多驱逐的部分是被当成保险付掉的。开了前缀缓存又跑高并发时,这笔保险会压低命中率。

### 7.3 槽号易主靠代数计数识别

第一张表每一行有一个代数,重新分配就加一。异步路径上拿着旧槽号的元数据,可以用代数判断这个槽是不是已经给了别的请求。

### 7.4 写入位置捆成一个结构体

后端写 KV 时拿到的不是一个位置张量,而是主位置、窗口子池位置、全注意力子池位置三个一组。后端按池的类型用其中一个或几个,发一次写入调用就够。分段 CUDA graph 和数据并行补齐会把位置按层截短,结构体在构造时把另外两个位置也切到同样长度。

### 7.5 读 KV 之前可能要等一层

取某一层的 K 或 V 张量的接口上挂了一个按层的计数器。开了逐层加载时,读第 i 层要先等第 i 层的数据到齐。注释明说这个接口只给注意力后端用,不要拿去做统计。

### 7.6 先占虚拟地址,捕获完再补物理页

有一种可选模式,KV 池先只保留一段虚拟地址上界,等 CUDA graph 捕获完、知道激活实际占多少之后,再把物理页补上去。这时槽总数会向上对齐到页边界,而不是向下。

### 7.7 FP8 存成 uint8 是 PyTorch 的限制

FP8 的 KV 张量按无符号 8 位整数分配,写入时按整数写,读出时再看成 FP8。原因只有一个:按索引写入不支持 FP8 张量。和精度、和 kernel 都无关。

### 7.8 回收的槽号只在 PD 模式下排序

token 级分配器的暂存区和合并排序只在 PD 分离的 prefill 或 decode 节点上启用。单机部署回收就是拼接,顺序无所谓,因为没有人按段传输它。

### 7.9 两种分配失败,两种态度

取行失败直接抛错,错误信息让人调小最大并发,因为这是准入算错了;取槽失败也抛错,但先把缓存树打印出来,错误信息让人调小 batch。两者都不静默回退。

### 7.10 释放 KV 池要先清树

RL 的释放接口在暂停 KV 那块显存之前先把缓存树清空。否则恢复之后树里还留着指向旧显存内容的槽号,而那些槽的内容已经不可信。

## Part 8|对比与收益账

### 8.1 和 vLLM 的 KV 管理比

| 维度 | vLLM | SGLang |
|---|---|---|
| 地址表 | 块表,记块号,块内位置靠算 | 两级表,记槽号,细到 token |
| 默认粒度 | 块大小 16 | 页大小 1,后端要求时改成 32 或 64 |
| 表的大小 | 块数级,几十 MB | 最大并发乘最大上下文,4 字节一格,可达 GB 级 |
| 前缀命中粒度 | 整块 | 单个 token,按页分时退化到页 |
| 显存预算 | 按比例给 vLLM 全部,探测激活后剩下给 KV | 权重加 KV 占比例,余量按公式扣 |
| 抢占 | 释放重算 | 释放重算;decode 分离节点备份到 host |
| 抢占顺序 | 见 vLLM 调度器章 | 输出最少的先踢 |
| 混合模型 | KV 分组,每组自己的块表 | 家族里挑一种池,窗口和状态各自计数 |

两边都是「逻辑连续、物理离散」,差别全在粒度:vLLM 把粒度定在块,换来小表和天然对齐;SGLang 把粒度定在 token,换来 radix 树需要的任意位置指向,代价是表大和每次读都多一跳。

### 8.2 地址表的账:2 GB 换来的是什么

最大并发 4096、上下文 131072、每格 4 字节,地址表 2 GB。同一张卡上块表方案记的是块号:131072 除以 16 是 8192 块每请求,4096 个请求是 3355 万格,4 字节一格约 134 MB。差 15 倍。这 2 GB 换来的是任意 token 指任意槽,也就是下一章分叉处不复制、命中不对齐块边界。不开前缀缓存的部署,这 2 GB 是纯开销;开了前缀缓存的多轮负载,它省下的是每轮分叉处一整块的复制和最多 15 个 token 的命中损失。

### 8.3 并发上限的账:多数时候卡在地址表,不在显存

按 5.2 的 MHA 算例,50 GB 预算 40 万个槽。上下文 8192 时估计行数是 40 万除以 8192 再乘 512 等于 25000,夹到 4096;槽数一半是 20 万;所以并发上限是 4096,卡在地址表行数。要跑到 4096 以上,必须显式指定最大并发,而这会把地址表按比例撑大。反过来上下文 131072 时估计行数是 1562,夹到 2048,这时 40 万个槽平均每请求只有 195 个,并发根本到不了 2048 就被槽数封死,真正的并发上限是「40 万除以平均请求长度」。**短上下文看行数,长上下文看槽数。**

### 8.4 页大小的账:页 64 时每个请求平均浪费半页

页大于 1 时,每个请求最后一页平均有一半空着。页 64、4096 并发,尾页浪费平均是 4096 乘 32 等于 131072 个槽。按 MLA 每 token 70 KB 算是约 9 GB,按 MHA 128 KB 算是约 16 GB。这是钉页的显存代价。命中的代价另算:分叉点落在页内时,最多损失 63 个 token 的命中,平均 32 个。两笔账都随页大小线性涨,所以 page_size 不要手调,后端要多少给多少。

### 8.5 抢占的账:重算对备份

单机抢占的代价是重算整段 prompt。5000 个 token 的 prefill 在一张卡上是 50–500 毫秒,而且要重新排队。decode 分离节点的备份走的是显存到 host 的拷贝:5000 个 token 乘 128 KB 是 640 MB,PCIe 4 代按 20 GB/s 算约 32 毫秒,恢复时再拷一次。备份比重算便宜一个量级,但它要占 host 内存,而且 decode 节点没有别的选择。单机不备份是因为重算的成本已经被前缀缓存摊掉一部分:被踢的请求重新 prefill 时,它的 prompt 前缀多半还在树上。

## Part 9|参数、开关与误区

### 9.1 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| mem_fraction_static | 按显卡启发式 | 权重加 KV 占显存的比例 | 就绪前日志里剩余显存高于 8 GB 就往上加,每次 0.01;落在 5–8 GB 合适 |
| max_total_tokens | 探测值 | KV 槽总数上限 | 只能往下压;想复现某个并发上限时用 |
| max_running_requests | 按槽数推,2048 到 4096 | 最大并发,也是地址表行数 | 短上下文想超过 4096 时显式指定;抢占频繁时调小 |
| page_size | 1 | 分配粒度 | 不要手调,后端会改 |
| kv_cache_dtype | auto | KV 精度 | FP8 能把槽数翻倍,先确认后端支持反量化融合 |
| swa_full_tokens_ratio | 由模型定 | 窗口层槽数与全注意力层槽数之比 | 窗口模型槽不够时调 |
| max_mamba_cache_size | 按比例 | 状态池槽数 | 混合模型并发被状态池卡住时调 |
| schedule_conservativeness | 1.0 | 准入估计输出长度的松紧 | 抢占多调到 1.3,利用率低调到 0.3 |
| enable_memory_saver | 关 | KV 池可整体释放再恢复 | RL 训推一体时必开 |

### 9.2 排障先看什么

- 日志里 token usage 在 0.9 以上是健康;低于 0.9 且队列有请求,是准入太保守。
- 「KV cache pool is full. Retract requests」每分钟一次以内可以不管,频繁出现先调保守度,再考虑减并发。
- 并发上不去:先看是三道闸的哪一道。混合模型看日志有没有「capped by the mamba state cache」;短上下文看是不是卡在 4096 的默认行数。
- 启动就报显存不够,错误信息里给了最小可行的 mem_fraction_static,照抄即可。
- MLA 模型命中率比预期低,先看启动日志里 page_size 有没有被后端改成 64。

### 9.3 常见误区

- 页大小 1 不等于「没有分页」。逻辑上还是槽号表加间接寻址,只是页恰好等于一个 token。
- mem_fraction_static 不是 KV 占比,是权重加 KV 的占比。换大模型同一个比例给 KV 的更少。
- max_total_tokens 不能把容量调高,只能调低。
- 最大并发不只受 KV 槽数限制,还受地址表行数和状态池槽数限制,三者取最小;多数短上下文部署卡在行数。
- 抢占默认不备份 KV,被踢的请求重算全部前缀,只有 decode 分离节点例外。
- 混合模型里窗口层的槽会在请求还在跑的时候被回收,这是设计,不是泄漏。
- 地址表的 2 GB 跑短请求也是 2 GB,它按最大并发和最大上下文买断。
