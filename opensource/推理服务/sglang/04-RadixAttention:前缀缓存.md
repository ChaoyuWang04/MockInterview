# SGLang 04|RadixAttention:前缀缓存

同一段系统提示词、同一轮对话历史,每来一条请求都从头算一遍 prefill,算出来的 K 和 V 和上次一模一样。这一章讲 SGLang 怎么把所有请求的 token 序列合成一棵 radix 树,让后来的请求直接接在前人算过的地方;以及树怎么保护在途的 KV、显存满了先丢谁、调度器怎么反过来利用这棵树提高命中率。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。上一章讲的两级表是这棵树的底座:树里存的值就是那张表里的槽号。

## Part 1|原理:同一段前缀,每条请求都在重算

### 1.1 痛点

一个聊天应用,系统提示词两千个 token,用户每说一句话,客户端把整段历史加新的一句一起发来。第二轮请求的前两千多个 token 和第一轮完全相同,引擎却把它们当成新 prompt 重新 prefill 一遍。few-shot 提示、RAG 拼进去的文档、agent 循环里每一步都带的工具说明,全是这个形状。

重算的代价是算力和延迟:prefill 是计算密集的,两千个 token 的 prefill 在一张卡上是几十到几百毫秒,而这几十毫秒算出来的 K 和 V,上一轮已经算过并且还躺在显存里,只是没人记得它在哪。

### 1.2 复用的前提:前缀必须逐字相同

因果注意力保证了一件事:第 i 个 token 的 K 和 V 只依赖它前面的 token,不依赖后面的。所以两条请求只要前 n 个 token 完全相同,这 n 个 token 在每一层的 K 和 V 就完全相同,可以直接拿来用。差一个 token 都不行,差的那个 token 之后的一切都要重算。

这把问题定义清楚了:**复用的单位是「公共前缀」,能复用多少取决于两条序列从头开始能对上多长** 。

### 1.3 要解决的三件事

- **怎么找**:一条新请求来了,几百个在途和历史请求里,谁和它的公共前缀最长,那段前缀的 KV 在显存哪里。
- **怎么留**:请求算完了,它的 KV 不能立刻回收,得留着给后来人;但正在被别人用的那段,又不能被回收掉。
- **怎么丢**:显存有限,留下的 KV 迟早要丢,先丢谁。

按整段 prompt 做哈希表,第一件事就做不了:两条请求只是前面一样、后面不一样,整段哈希对不上。按定长块做哈希链(vLLM 的做法)能找到,但命中只能停在块边界,分叉处那半块白算,而且每条请求来了要先算一串哈希。SGLang 的回答是把「前缀」这个概念直接做成数据结构:所有请求的 token 序列合并成一棵前缀树,找公共前缀就是从根往下走。

## Part 2|一棵树:radix 树怎么存前缀

### 2.1 为什么是 radix 树

普通的前缀树一个节点一个 token,两千个 token 的系统提示词就是两千个节点串成一条链,走一遍两千步。radix 树把没有分叉的一段压成一个节点,节点的键是一段 token 序列,只有出现分叉的地方才拆开。上面那条系统提示词在树里就是一个节点,走一步。

节点的键是一段 token,值是这段 token 对应的 KV 槽号,一一对应、等长。槽号就是上一章第二张表的下标,树本身不碰 KV 数据,只管「哪些 token 的 KV 在哪些槽」。

每个节点的子节点放在一个字典里,字典的键是子节点键的第一个 token(按页分配时是第一页的 token 元组)。所以从一个节点往下走不需要遍历所有孩子,拿新请求的下一个 token 查一次字典就知道该进哪个孩子。

### 2.2 匹配:从根往下走,走到对不上为止

新请求的 token 序列从根开始:用第一个 token 查字典找到孩子,把孩子的键和序列对齐比较,得到公共长度。

- 公共长度等于孩子键的全长:整个孩子命中,把它的值收进结果,序列去掉这一段,继续往下查。
- 公共长度短于孩子键:分叉发生在这个节点内部。这时把孩子从公共长度处劈成两段,前半段成为新节点接在原来的位置,后半段成为它的孩子。命中到前半段为止。
- 字典里没有下一个 token:命中到此为止。

劈开节点只改拓扑,不动 KV:两半各拿走原节点值张量的对应切片。这一步发生在读路径上,也就是说匹配本身会改树的形状,让下一次匹配停在更精确的边界。

匹配的结果是命中的槽号拼成的张量,加上停下的那个节点。停下的节点很重要,后面加锁和插入都从它开始。

比较两段 token 是否相同是 Python 层最容易变慢的地方。实现用指数搜索:先比 1 个、再比 2 个、4 个、8 个,每次是一次 C 层的切片比较,找到第一个不同的窗口再二分,长前缀不需要逐 token 的 Python 循环。

按页分配时,匹配长度向下取整到整页:半页的命中不算命中,因为半页的槽号不是页对齐的,分配器给不出后半页的位置。

### 2.3 插入:走到头,把尾巴挂上去

插入和匹配走同样的路,区别是走到对不上的地方后,把剩下的 token 和槽号做成一个新叶子挂在停下的节点下面。路径上经过的每个节点都刷新访问时间、命中计数加一、优先级取路径上的最大值。

插入返回命中了多长。调用方据此知道这条请求的 KV 里前多长是别人已经有的(那段槽号可以直接释放,树里用的是别人那份),后面多长是新贡献给树的。

### 2.4 命名空间:同样的 token 不一定能共享

两条请求 token 序列相同,KV 却不一定相同:换了 LoRA 适配器,或者调用方明确要求隔离。树用两个附加键处理这件事。一个是 extra_key,LoRA 的 id 会拼进去,调用方也可以自己给;另一个是 cache_salt,调用方给的隔离盐。附加键不同的序列在树里根本不会相遇:子节点字典的键带着附加键,同样的 token 在不同命名空间下落进不同的孩子。

### 2.5 草稿模型的键是二元组

推测解码开 EAGLE 时,草稿模型第 i 个位置的 KV 不只依赖前 i 个 token,还依赖第 i 加一个 token(它的输入是目标模型的隐状态加下一个 token)。所以草稿的前缀缓存不能按单 token 建键。树在 EAGLE 模式下把键看成二元组序列,第 i 个键是(第 i 个 token,第 i 加一个 token),n 个 token 只有 n 减一个键,最后一个 token 的 KV 不进树。实现上只是翻一个标志位,不真的构造二元组列表。

## Part 3|在途保护与一个请求的 KV 一生

### 3.1 引用计数:正在被用的路径不能丢

请求命中之后,它的 prefill 和 decode 会一直读那段前缀的 KV。这期间如果树把那段驱逐了,请求读到的就是别人的数据。树用引用计数保护:请求进批时,从它停下的节点一路走到根,每个节点的计数加一;请求结束时再走一遍减一。计数大于零的节点不参与驱逐。

树同时记两本账:可驱逐的 token 总数和受保护的 token 总数。节点从零变一时它的长度从前一本挪到后一本,从一变零时挪回来。调度器看第一本账判断还能腾出多少。

### 3.2 谁加锁、什么时候加

准入闸门(02 章)在决定一条请求能不能进批时先临时锁一下,算完预算就解开;真正进批时再锁,并把解锁需要的凭据存在请求上。这样锁的粒度就是「从进批到结束」,不多不少。根节点的计数初始就是一,永远不会被驱逐。

### 3.3 结束:整段插入,再在 prompt 边界补一刀

请求结束时,把它的 prompt 加输出整段作为键、这一行的槽号作为值插进树。插入会返回命中了多长,那段是别人已有的,这条请求自己那份槽号释放掉;命中之外的才是它留给树的。

然后再做一件小事:用 prompt 那一段单独再插一次。整段插入产生的是一个叶子,prompt 和输出在同一个节点里,驱逐时要丢一起丢。补插 prompt 会把这个叶子从 prompt 边界劈开,输出段成为独立的叶子,可以先于 prompt 被驱逐,因为下一轮对话会带着同样的 prompt 回来,但很少带着同样的输出。补插的这次不加命中计数,否则每条请求都会给自己的 prompt 白加一次。

最后解锁。

### 3.4 中途:分块 prefill 每块结束就先插一段

长 prompt 分几块算(02 章),每块算完就把已经算过的部分插进树,而不是等整个请求结束。原因很实际:同一个长文档可能同时有几条请求在排队,第一条算完第一块,第二条就能命中第一块。

插完之后请求会重新匹配一次,拿到新的停留节点,解开旧锁、加上新锁。按页分配时会多一个细节:最后一个不满页的部分不进树,但槽号还在请求手里,请求记一个「受保护长度」,让后面的释放知道哪段是树的、哪段是自己的。

### 3.5 一生

| 时刻 | 树做什么 | 槽号在谁手里 |
|---|---|---|
| 到达,准入 | 匹配,得到命中槽号与停留节点;临时锁算预算,进批后正式锁 | 命中段属于树,新段还没分 |
| prefill 每块结束 | 已算部分插入,重新匹配,换锁 | 已算部分转归树,请求持锁 |
| decode 每步 | 不碰树 | 新槽在请求手里 |
| 结束 | 整段插入,prompt 边界补插,释放重复段,解锁 | 全部转归树 |
| 被抢占 | 释放,不插入 | 全部回收 |
| 显存不够 | 从可驱逐的叶子开始丢 | 丢掉的槽回到分配器 |

## Part 4|驱逐:只看叶子,从枝尖往根走

### 4.1 候选只有可驱逐的叶子

能被丢的节点要同时满足三件事:它的 KV 还在显存(没被丢过),没有请求锁着它,并且没有一个还持有 KV 的孩子。第三条是关键:如果一个节点的孩子还在,丢掉这个节点等于把孩子的前缀丢了,孩子就没法用了。所以驱逐永远从叶子开始。树维护一个可驱逐叶子的集合,插入、删除、加锁、解锁都会更新它。

### 4.2 驱逐怎么走

需要腾出 n 个 token 时,把所有可驱逐叶子按策略打分放进一个堆,分数最低的先弹。弹出一个叶子,释放它的槽号,把它从父节点的字典里删掉,累计释放数。如果它的父节点因此没有孩子了、也没有锁,父节点就成了新的叶子,打分入堆。这样驱逐沿着一根枝从尖往根走,直到够数或者没有候选。

策略只负责打分,不决定丢多少,也不能把某个节点钉死在显存里:如果其他都丢完了还不够,策略再保护的节点也会被丢。

### 4.3 八种打分

| 策略 | 先丢谁 | 适合 |
|---|---|---|
| lru(默认) | 最久没被访问的 | 通用,前缀的复用概率随时间衰减 |
| lfu | 命中次数最少的,同样少的按最久 | 一小撮 prompt 被反复用,想让它们扛过一波一次性流量 |
| slru | 命中次数没到门槛的先丢,门槛之上的按最久 | 像 lfu,但给「证明过自己」的前缀一条硬底线 |
| priority | 插入它的请求优先级最低的先丢 | 开了优先级调度,想让缓存保留和准入用同一套排序 |
| tlru | 多轮对话里超出下一轮 TTFT 预算的尾巴先丢 | agent 和多轮负载,尾延迟比命中率重要 |
| fifo、mru、filo | 按创建时间或反向 | 只在注册表里,命令行不提供,做实验用 |

命中次数只在别的请求命中它时加,分块 prefill 的中间插入不加,评为已驱逐的节点不加。优先级是插入它的请求带的,多个请求经过同一节点取最高。

### 4.4 什么时候触发

上一章说过:分配槽之前先按需求量问树能不能腾出来,不够就驱逐;抢占之后再多驱逐几步 decode 的量。树自己不主动清理,所有驱逐都是分配器问出来的。

## Part 5|调度器与树的耦合:先进批的决定后进批的命中

### 5.1 顺序本身就是命中率

等待队列里有三条请求,前两条共享一段两千 token 的前缀,第三条不共享。如果先算第三条,前两条各自 prefill 时对方还没进树,两千 token 算两遍;如果先算前两条中的任何一条,另一条就命中。**谁先进批,决定了别人能不能命中** 。所以 SGLang 的调度策略默认是缓存感知的,而不是先来先服务。

### 5.2 最长前缀优先

默认策略 LPM 在每轮准入前对等待队列里每条请求做一次匹配,按命中长度降序排队。命中最长的请求要算的新 token 最少,先进批还能把它的输出留给后面。

这个匹配每轮都做,队列长了就贵。所以队列超过 128 条时自动退回先来先服务,不做匹配。这是一个默默发生的降级,日志不会提示。

### 5.3 批内查重:同一批里也不要重算

等待队列里两条新请求共享前缀,但树里还没有(谁都没算过)。LPM 看它们的命中长度都是零,可能把两条一起放进同一批,于是两条各算一遍。批内查重处理这件事:命中长度不超过 32 的请求,再到一棵只记 token 不记 KV 的模拟树里查一遍等待队列内部的前缀;如果和排在前面的某条请求共享超过 32 个 token,就临时把它排到队尾,让前面那条先算,自己下一轮再来命中。

### 5.4 深度优先加权

第二种缓存感知策略按树的形状排队:先统计每个子树里有多少条等待请求停在那里,然后深度优先遍历,子树里请求多的孩子先走。效果是同一子树的请求连续进批,共享的前缀在显存里被连续使用,不容易在中间被驱逐。

### 5.5 响应比

第三种是最高响应比优先:等待时间除以要算的新 token 数,等得久且要算得少的先进。它用处理过的 token 数当时钟,不用墙钟时间,吞吐波动时排序仍然稳定。这条策略防的是 LPM 的饿死问题:命中短的请求在 LPM 下可能一直排在后面。

### 5.6 不感知缓存的三种

先来先服务、输出上限最长优先、随机。关掉前缀缓存时,缓存感知策略会自动换成先来先服务。

## Part 6|默认那棵树:统一树与可换的树核

### 6.1 两个实现,默认是统一树

仓库里有两棵树。一棵是最早的 RadixCache,前面几个 Part 讲的算法就照它讲,现在只剩调度器做批内查重时用它建模拟树。默认构造的是 UnifiedRadixCache,算法相同,但把「节点的值」从一个槽号张量扩成了按组件分的一组。

### 6.2 组件:一棵树管三种历史

混合模型的一段 token 有三种历史(03 章):全注意力层的 KV、滑动窗口层的 KV、Mamba 层的状态。统一树给每个节点按组件存数据:全注意力组件存槽号,窗口组件存窗口内的槽号,Mamba 组件存状态槽。一棵树、一次匹配,三种历史一起命中或一起不命中;驱逐按组件分别记短缺,哪种不够丢哪种,一种组件的驱逐可能顺带释放另一种,共用池时这种连带就够用了。

每个组件维护一条自己的 LRU 双向链,驱逐沿链走,候选仍按 Part 4 那套策略打分。链表上加一个分界,session 引用过的节点在前、没引用的在后,驱逐从尾往前走就天然先丢没引用的。

### 6.3 树核可换

统一树把「树的算法」和「缓存的策略」分开:匹配、插入、劈开、驱逐叶子这些操作归树核,host 备份、存储预取、session 引用这些归缓存。树核通过一个注册表选,默认是 Python 实现,环境变量可以切到 Rust 实现,支持全注意力、窗口、Mamba 三种组件的任意组合。另有一个实验性的 C++ 版走的是另一条路,不经过统一树。

### 6.4 session 感知

长会话下,一个会话的 KV 在显存紧张时被别的会话挤掉,下一轮就要重算。开了 session 感知后,请求带上会话号,结束时它留下的叶子按会话号登记引用;驱逐时先丢没有任何会话引用的。引用是软保护,不是钉死:没引用的丢完还不够,有引用的照丢。会话结束调用关闭接口去掉引用,KV 不立刻释放,只是回到普通的驱逐顺序。

### 6.5 树之上还挂了什么

节点上有一串按页的哈希值,那是给 host 内存和分布式存储做键用的(05 章);树的插入和删除会发出事件,发布给外部的路由网关维护近似的树(18 章)。这两件事都不改变本章讲的树本身。

## Part 7|图解

### 7.1 三条请求进树

```text
  请求 A = [sys(2000) | q1(20)]        请求 B = [sys(2000) | q2(30)]        请求 C = [sys | q1 | ans1(100) | q3(25)]

  A 结束后:                B 结束后(在 sys 之后分叉):        C 结束后(顺着 A 的路往下长):

  root                     root                                root
   └─ [sys q1]              └─ [sys]                            └─ [sys]
      (2020 个槽)              ├─ [q1]                              ├─ [q1]
                               └─ [q2]                              │   └─ [ans1 q3]      <- C 命中 sys+q1,新算 125
                                                                    └─ [q2]

  B 到达时匹配 [sys q1] 命中 2000 个,不到整段,节点被劈成 [sys] 和 [q1];B 只算 q2 的 30 个。
  C 到达时走 root -> [sys] -> [q1],全命中,2020 个 token 一个不算。
```

### 7.2 锁与驱逐在一次 decode 步里的位置

```text
  准入:匹配 -> 临时锁 -> 算预算 -> 正式锁(到根的路径计数 +1)
                                     |
  分配:需要 n 个槽 -> 可驱逐总数够吗 -> 不够:按策略弹叶子,释放,父节点补位
                                     |
  前向:读命中段 + 写新段(锁保证命中段还在)
                                     |
  结束:整段插入 -> prompt 边界补插 -> 释放重复段 -> 解锁(计数 -1,可能回到可驱逐集合)
```

## Part 8|机制之外:源码里额外读到的

### 8.1 匹配会改树

劈开节点发生在匹配里,不只在插入里。一次只读的查询可能让树多一个节点。这是刻意的:让边界落在精确的位置,后面的匹配和插入都省事。

### 8.2 命中计数防自引用

分块 prefill 每块结束都插一次,如果每次都给路径上的节点加命中计数,一条长请求会把自己的前缀刷成「热门」。所以中间插入不加计数,结束时补插 prompt 那一刀也不加。

### 8.3 补插用更高的优先级

prompt 边界那次补插带的优先级比整段插入高一,并且路径取最大值,所以 prompt 段的优先级永远不低于输出段。在 priority 策略下这意味着输出段先走。

### 8.4 根是特殊的

根节点的键是空序列,引用计数初始为一,优先级是最小整数。前两条保证它永不被驱逐,第三条保证任何真实优先级都能覆盖它。

### 8.5 半页归请求

按页分配时,请求最后不满一页的那段不进树,但槽号在请求的行里。请求记一个受保护长度,表示这一行前多少是树的、后面是自己的;释放时只释放自己的那段。没有这个长度,要么漏释放,要么把树的槽号释放掉。

### 8.6 多卡上的树必须一致

张量并行的每个 rank 各有一棵树,插入和驱逐的结果必须一样,否则各 rank 的槽号对不上。统一树的插入、驱逐接口上有一致性检查,比对各 rank 的参数和结果。

### 8.7 强制未命中

有一个调试环境变量能让所有匹配返回零命中,用来测量「没有前缀缓存」的基线,不用重启改配置。

### 8.8 关掉前缀缓存之后

关掉后不是没有树,而是换成一个只做分块的缓存:它只负责在分块 prefill 之间保住已算的部分,请求结束就全释放,没有跨请求的复用。缓存感知策略这时自动退回先来先服务。

### 8.9 批内查重那棵树的值是假的

批内查重用的模拟树不接内存池,插入时的值是一个同长度的布尔张量,只是为了让匹配能返回长度。它每轮准入前清空重建。

## Part 9|对比与决策

### 9.1 和 vLLM 的块哈希比

| 维度 | vLLM 块哈希 | SGLang radix 树 |
|---|---|---|
| 数据结构 | 每块一个哈希,链式,块表指向块 | 前缀树,节点键是 token 段,值是槽号 |
| 命中粒度 | 整块 | 单个 token(按页分配时整页) |
| 分叉处 | 半块要复制或丢弃 | 劈开节点,不复制 KV |
| 找前缀的成本 | 算一串哈希,查哈希表 | 从根往下走,每步一次字典查找加一次段比较 |
| 跨进程复现 | 哈希可复现,天然支持跨实例 | 树只在进程内;跨实例靠网关维护近似树 |
| 与调度器的关系 | 调度器不看缓存 | 默认按命中长度排队,还做批内查重 |
| 驱逐 | 按块 LRU | 按叶子,八种策略 |

两边都在做「记住算过的前缀」,分歧是把复杂度放在哪:vLLM 放在哈希和块对齐上,换来简单的表和可复现的键;SGLang 放在树的维护上,换来 token 级命中和调度器可以利用的结构。

### 9.2 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| disable_radix_cache | 关 | 关掉跨请求复用,只留分块缓存 | 负载没有任何共享前缀时开,省匹配开销 |
| schedule_policy | lpm | 排队策略:lpm / dfs-weight / hrrn / fcfs / lof / random / routing-key | 命中短的请求饿死时换 hrrn;树深且请求聚集时试 dfs-weight |
| radix_eviction_policy | lru | 驱逐打分 | 热点 prompt 被冲掉时换 lfu 或 slru;多轮 agent 尾延迟敏感换 tlru |
| radix_eviction_policy_config | 空 | 策略参数,JSON | slru 的保护门槛、tlru 的预算,键写错启动就报错 |
| enable_session_radix_cache | 关 | 按会话登记引用,先丢无引用的 | 长会话多、显存紧张时开,客户端要传会话号并在结束时关闭 |
| page_size | 1 | 命中向下取整到整页 | 不是这章的参数,但它决定命中粒度 |
| 树核后端(环境变量) | python | 切到 rust | 匹配成 CPU 瓶颈时试 |
| 批内查重阈值(环境变量) | 32 / 32 | 命中多短才查、批内共享多长才降级 | 设成负一关掉 |

### 9.3 什么时候该关

请求之间没有共享前缀的负载,比如离线跑随机采样的评测集,树只会增加每轮的匹配和插入开销,关掉更快。树的构造参数里留了一个「结束时不插入」的开关,但基准上没有任何调用方设置它,实际不可用。

### 9.4 怎么看命中率

每条请求的响应元信息里有 cached_tokens 一项,是命中的 token 数,开了分层缓存还会细分命中落在哪一层。想知道「没有缓存会怎样」,用强制未命中的调试开关跑一遍对比。

### 9.5 常见误区

- 不同 LoRA 的请求不共享前缀,哪怕 prompt 完全一样。
- 命中永远到不了最后一个 token 之后:新请求至少要算一个 token 才能出第一个输出;EAGLE 模式下更是最后一个 token 本身就不进树。
- 页大于 1 时半页不算命中,长 prompt 的尾巴总要重算一小段。
- LPM 在队列超过 128 时会悄悄退回先来先服务,高并发下命中率下降不一定是缓存的问题。
- 关掉缓存不等于没有树,分块 prefill 仍然靠树保住中间结果。
- Rust 树核不是默认,默认是 Python 实现。
