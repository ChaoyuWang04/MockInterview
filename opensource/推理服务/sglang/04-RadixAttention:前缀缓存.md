# SGLang 04|RadixAttention:前缀缓存

03 章把 KV 放进了两级表,但有件事它没管:系统提示词、few-shot、上一轮对话,每来一条请求都从头 prefill 一遍,算出来的 K 和 V 和上一条一模一样。这一章讲 SGLang 用一棵 radix 树把算过的前缀留下来给后来人,以及这件事在什么情况下会让你以为命中了其实没有、命中率和并发怎么抢同一块显存、显存满了先丢谁。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:同一段前缀不该算第二遍

### 1.1 真实负载里,请求共享的开头有多长

| 场景 | 公共前缀 | 典型长度 |
|---|---|---|
| 系统提示词 | 「You are a helpful assistant…」加工具说明 | 200–3000 token |
| few-shot | 几个示例对话 | 500–5000 token |
| RAG | 检索到的文档片段 | 1000–10000 token |
| 多轮对话 | 整段历史 | 2000–50000 token |
| agent 循环 | 工具说明加全部历史步骤 | 2000–50000 token,每步都在长 |

朴素做法下,每条新请求把整个前缀 prefill 一遍,哪怕这段的 K 和 V 上一条请求刚算完、此刻还躺在显存里。

### 1.2 省下的是 prefill,动的是三个指标

prefill 是算力密集的,5000 个 token 在一张卡上是 50–500 毫秒。前缀缓存让新请求只算它独有的那一段,直接动三个数:

- **TTFT 下降**:5000 token 的文档前缀全命中后,只剩最后一个 token 要算,首字延迟从 200 多毫秒掉到 20 毫秒上下(11.1 有算例)。
- **吞吐上升**:省下的算力直接服务更多请求。这一项通常比 TTFT 更值钱,因为 prefill 和 decode 在同一张卡上抢时间。官方博客给的数字是相对不做前缀复用的引擎最高 5 倍吞吐(官方数字,多轮和 few-shot 负载)。
- **显存不涨**:复用靠的是两级表里多行指向同一个槽,不复制数据。

代价在后面三个 Part 里逐条出现:树本身要一张按最大值买断的地址表;每轮调度要把等待队列匹配一遍,这是 CPU 的活;树里留下的 KV 和在飞请求抢同一块显存,而且抢不过。

### 1.3 复用的前提:整条前缀逐字相同

因果注意力保证第 i 个 token 的 K 和 V 只依赖它前面的 token。所以两条序列只要前 n 个 token 完全相同,这 n 个位置在每一层的 K 和 V 就完全相同。反过来,**前缀里任何一处不同,从分叉点起后面所有位置的 KV 都是错的,而且不报错**:第一层看起来还对,第二层起 attention 已经读到了不同的 K。这个证明 vLLM 04 章「只看本段 token 行不行」一节逐层写过,这里不重复。

它给缓存定了一条铁律:能复用的只有「从第一个 token 开始连续相同」的那一段,一个 token 都不能跳。

### 1.4 于是要解决三件事

- **找**:上百条在途和历史请求里,谁和新请求的公共前缀最长,那段 KV 在哪些槽。
- **留**:请求算完了 KV 要留给后来人;正在被人用的那段不能被回收。
- **丢**:显存有限,先丢谁。

vLLM 用块哈希链解决「找」,命中只能停在块边界。SGLang 把「前缀」这个概念直接做成数据结构:所有请求的 token 序列合并成一棵前缀树,找公共前缀就是从根往下走,命中可以停在任何一个 token。

## Part 2|树凭什么敢复用

### 2.1 一个公式:命中长度

$$\text{hit} = \min\Big(\Big\lfloor \frac{\mathrm{LCP}(\text{seq}, \text{tree})}{\text{page}} \Big\rfloor \times \text{page},\ \ |\text{seq}| - 1\Big)$$

三项各有来历。LCP 是新序列与树里任何一条路径的最长公共前缀,树的结构保证它就是「从根往下能走多远」。除以页再乘回去,是因为按页分配时半页的槽号不是页对齐的,分配器给不出后半页的位置,所以半页不算命中。减一是硬性封顶,下面 2.4 讲。

只要记住这个公式,后面 Part 3 那五种「以为命中了其实没有」都是它的某一项在起作用。

### 2.2 前缀关系就是树的形状

普通前缀树一个节点一个 token,2000 个 token 的系统提示词是 2000 个节点。radix 树把没有分叉的一段压成一个节点,键是一段 token,值是这段 token 的槽号,等长对应;只在分叉处才拆开。系统提示词在树里就是一个节点,走一步。

子节点放在字典里,字典键是子节点键的第一个 token。从一个节点往下不需要遍历孩子,拿新序列的下一个 token 查一次字典就知道进哪个孩子。所以匹配的成本是「分叉数」量级,不是 token 数量级。

比较两段 token 是否相同用指数搜索:先比 1 个、2 个、4 个,每次一次 C 层切片比较,找到第一个不同的窗口再二分。长前缀不需要逐 token 的 Python 循环。

### 2.3 劈开只发生在公共前缀的末尾,而且只改拓扑

新序列走到某个节点,公共长度短于节点键的全长,说明分叉在节点内部。这时把节点从公共长度处劈成两段:前半段接在原位,后半段成为它的孩子,两半各拿原值张量的对应切片。**KV 一个字节都不动**,动的只是树。

要注意的是劈开发生在匹配路径上,也就是一次只读的查询会改树的形状。这在单进程里无害,在张量并行下意味着每个 rank 必须做一模一样的匹配,否则各 rank 的树分叉、槽号对不上。统一树在插入和驱逐接口上做了跨 rank 的一致性校验。

### 2.4 为什么全命中也要算一个 token

一条请求和树里某条路径完全相同时,公式里的减一起作用:匹配长度最多是输入长度减一,最后一个 token 永远留给这次前向去算。源码注释给的理由是要能算 logprob:输出第一个 token 的分数必须由本次前向产生,不能从缓存里拿。所以「全命中」的请求 TTFT 不是零,是一个 token 的 extend 加一次采样。

EAGLE 推测解码下再少一个:草稿模型第 i 个位置的 KV 依赖第 i 加一个 token,树把键看成二元组,n 个 token 只有 n 减一个键,最后一个 token 本身就不进树。

### 2.5 同样的 token,不同的命名空间永远不相遇

换了 LoRA 适配器,或者调用方明确要求隔离,同样的 token 序列 KV 也不同。树用两个附加键处理:LoRA 的 id 会拼进 extra_key,调用方还可以给 cache_salt。附加键进了子节点字典的键,不同命名空间的序列在树里落进不同的孩子,连比较都不会发生。**多 LoRA 服务里命中率低,先查是不是每个适配器各自一棵子树** 。

## Part 3|你以为缓存了,其实没有

### 3.1 后端把页钉成 64 时,树的 token 级命中就没了

page_size 默认是 1,这时公式里的向下取整不起作用,命中真的到 token。但 FlashMLA、HPC-Ops 这类后端只认 64 的页,TensorRT-LLM 和 CuteDSL 的 MLA 后端只认 32 或 64,启动时配置层会把 page_size 改过去(03 章)。用 DeepSeek 跑这些后端,命中粒度就是 64:两条请求共享 2050 个 token,命中 2048 个,尾巴 2 个加上后面的整段都要重算。**radix 树「命中到 token」的招牌,在最需要它的 MLA 模型上不成立** ,那里它和块哈希只差一个数据结构。

### 3.2 被抢占的请求不留任何东西

显存见底时调度器踢掉在飞请求(03 章)。被踢的请求释放全部 KV,**不插进树**,因为抢占就是为了立刻腾空间。它重新排队后从头 prefill,之前算过的东西一点不剩。抢占顺序默认踢输出最少的,也就是刚开始的请求先走,损失的工作最少,但这些请求的前缀往往就是当下最热的那批。

### 3.3 请求结束前,它的输出对别人不可见

树只在两个时刻收东西:分块 prefill 每块结束,和请求结束。decode 期间产生的 token 一个都不进树。所以多轮对话的第二轮要想命中第一轮的回答,第一轮必须已经结束;两条同时在跑的请求,谁也命中不了谁的输出。分块 prefill 那个时刻是有意设计的:同一份长文档同时排队几条请求,第一条算完第一块,第二条就能命中第一块。

### 3.4 输出段是最先被丢的

请求结束时整段(prompt 加输出)插入树,产生一个叶子。紧接着树用 prompt 单独再插一次,把这个叶子从 prompt 边界劈开,输出段成为独立的叶子。理由写在注释里:LRU 驱逐可以丢掉输出的 KV 而不连带丢掉可复用的 prompt KV。这在系统提示词场景是对的,但在多轮对话里,**上一轮的回答恰恰是下一轮前缀的一部分,而它现在是树上最先被丢的那批** 。多轮 agent 负载在显存紧张时命中率先崩,第一处看这里。

### 3.5 队列一超过 128,缓存感知排序就没了

默认调度策略按命中长度排队,每轮对等待队列里每条请求匹配一次。队列超过 128 条时,这个匹配被判定为太贵,策略自动退回先来先服务,日志不提示。高并发下命中率突然下降、TTFT 分布变宽,不一定是缓存出了问题,可能只是排队的请求数过了这条线。

## Part 4|命中率不是免费的

### 4.1 地址表按最大值一次买断

token 级命中要求每个 token 能单独指向任意槽,所以地址表是「每请求一行、每行最大上下文长度」的整数表,每格四字节,启动时按最大并发买断(03 章)。最大并发 4096、上下文 131072 时是 2 GB 显存。这 2 GB 不随实际长度伸缩,是 token 级命中的固定成本。

### 4.2 每轮调度都要把等待队列匹配一遍

命中长度排序需要每条等待请求的命中长度,而命中长度只能靠匹配得到。所以每轮调度先对整个等待队列逐条走树,这是 CPU 上的串行工作,零开销调度(02 章)藏不掉它。指数搜索让单次匹配便宜,但请求数一多总量还是压过了收益,128 那条线就是这么来的。

### 4.3 命中率与并发抢同一块显存,准入永远赢

准入闸门算「还能放多少 token」时,把树里可驱逐的 KV 也算作可用:预算等于空闲槽加可驱逐槽。也就是说树里的 KV 从来不会挡住新请求;新请求要地方,树先让。结论有两层:

- 前缀缓存不会降低并发上限,它只用空闲显存。
- 并发拉满时,树被驱逐得只剩正在被锁的路径,命中率趋近于「同时在飞的请求之间的共享」,历史请求留下的东西基本没了。

所以高并发下命中率低是设计使然:显存要么给在飞请求当 KV,要么给树当缓存,准入选前者。想要命中率,要么留显存余量,要么把缓存往外扩(05 章的三层缓存)。官方调参文档说 token usage 在 90% 以上是健康的,那 90% 里包含树占的部分。

### 4.4 有时候让请求多等一轮反而更快

两条新请求共享一段前缀,但树里还没有。按命中长度排序它们都是零,可能被放进同一批,各算一遍。批内查重处理这件事:命中不超过 32 个 token 的请求,再到一棵只记 token 不记 KV 的模拟树里查等待队列内部的前缀;和排在前面的某条共享超过 32 个 token,就临时排到队尾,让前面那条先算,自己下一轮命中。**调度器主动让一条请求多等一轮,换整体少算一遍 prefill** 。

## Part 5|留:引用计数护住在途的路径

### 5.1 锁从停留节点走到根

请求命中之后会一直读那段前缀的 KV。树用引用计数保护:进批时从停留节点走到根,每个节点计数加一;结束时走一遍减一。计数大于零的节点不参与驱逐。树同时记两本账,可驱逐的 token 总数和受保护的 token 总数,节点计数在零和一之间变化时长度在两本账之间挪。准入闸门看的就是第一本账。根节点计数初始为一,永不驱逐。

### 5.2 一个请求和树打交道的五个时刻

| 时刻 | 树做什么 | 谁持有槽 |
|---|---|---|
| 准入 | 匹配得到命中槽号与停留节点;算预算时临时锁,进批后正式锁并存下解锁凭据 | 命中段归树,新段未分 |
| 分块 prefill 每块结束 | 已算部分插入;重新匹配拿新的停留节点;解旧锁加新锁 | 已算部分转归树 |
| decode 每步 | 不碰树 | 新槽在请求手里 |
| 结束 | 整段插入;prompt 边界补插;释放和树重复的槽;解锁 | 全部转归树 |
| 被抢占 | 释放,不插入 | 全部回收 |

分块 prefill 的中间插入不给路径上的节点加命中计数,否则一条长请求会把自己的前缀刷成热门。按页分配时最后不满一页的部分不进树,请求记一个受保护长度,释放时只释放自己的那段。

## Part 6|丢:只丢叶子,从枝尖往根走

### 6.1 三个条件,一个堆

能被丢的节点要同时满足:KV 还在显存、没有请求锁着、没有还持有 KV 的孩子。第三条是关键,丢掉一个有孩子的节点等于把孩子的前缀丢了。所以驱逐永远从叶子开始。需要腾 n 个 token 时,把可驱逐叶子按策略打分放进堆,弹分数最低的,释放槽,删叶;父节点因此没有孩子且没锁,就成了新叶子入堆。驱逐沿一根枝从尖往根走,直到够数。

策略只打分,不决定丢多少,也不能把节点钉死:其他都丢完还不够,策略再保护的节点也会被丢。

### 6.2 八种打分,各动哪个指标

| 策略 | 先丢谁 | 动的是什么 |
|---|---|---|
| lru(默认) | 最久没访问的 | 通用命中率,前缀复用随时间衰减 |
| lfu | 命中次数最少的 | 热点 prompt 的命中率,扛一次性流量 |
| slru | 命中没过门槛的先丢 | 同上,但给「证明过的」前缀一条硬底线 |
| priority | 插入它的请求优先级最低的 | 让缓存保留和准入用同一套排序 |
| tlru | 超出下一轮 TTFT 预算的对话尾巴 | 多轮负载的尾延迟,不是平均命中率 |
| fifo、mru、filo | 按创建时间或反向 | 只在注册表里,命令行不提供 |

命中次数只在别的请求命中时加。tlru 是唯一直接以延迟指标为目标的策略,它承认一个事实:多轮对话里保住整段历史不一定值,保住「下一轮 prefill 能在预算内完成」的那部分才值。

### 6.3 驱逐永远是分配问出来的

树不主动清理。分配槽之前先按需求量问树能不能腾出来,抢占之后再多问几步 decode 的量(03 章)。

## Part 7|谁先进批,决定谁能命中

| 策略 | 排序依据 | 动的指标 | 坑 |
|---|---|---|---|
| lpm(默认) | 命中长度降序 | 命中率、TTFT | 队列超过 128 退回 fcfs;命中短的请求可能饿死 |
| dfs-weight | 按树深度优先、子树里等待请求多的先走 | 同一子树的请求连续进批,前缀不易在中途被驱逐 | 同样受匹配成本约束 |
| hrrn | 等待量除以要算的新 token 数 | 防饿死,尾延迟 | 用处理过的 token 数当时钟,不看墙钟 |
| fcfs、lof、random | 不看缓存 | 无 | 关掉缓存时自动退回 fcfs |

排队顺序决定命中率的原因很直接:两条共享前缀的请求,先进批的那条算完,后进的才能命中;先算了不相干的第三条,前两条各算一遍。

## Part 8|默认那棵树:统一树与可换的树核

### 8.1 两个实现,默认是统一树

仓库里有两棵树。最早的 RadixCache 是前面几个 Part 照着讲的算法,现在只剩调度器做批内查重时用它建模拟树。默认构造的是 UnifiedRadixCache,算法相同,但节点的值从一个槽号张量扩成按组件分的一组。

### 8.2 一棵树管三种历史

混合模型的一段 token 有全注意力层的 KV、滑动窗口层的 KV、Mamba 层的状态三种历史(03 章)。统一树的节点按组件存数据,一次匹配三种一起命中;驱逐按组件分别记短缺,哪种不够丢哪种。每个组件维护一条自己的 LRU 链,驱逐沿链走,候选仍按 Part 6 的策略打分;链上加一个分界,session 引用过的节点在前,驱逐从尾往前天然先丢没引用的。

### 8.3 树核可换,默认 Python

统一树把「树的算法」和「缓存的策略」分开:匹配、插入、劈开、驱逐叶子归树核,host 备份、存储预取、session 引用归缓存。树核通过注册表选,默认 Python,环境变量可切到 Rust 实现,支持全注意力、窗口、Mamba 的任意组合。另有实验性的 C++ 版不经过统一树。

### 8.4 session 感知:先丢没人认领的

长会话下一个会话的 KV 被别的会话挤掉,下一轮就要重算。开了 session 感知后请求带会话号,结束时它留下的叶子按会话号登记引用,驱逐先丢没有引用的。引用是软保护:没引用的丢完还不够,有引用的照丢。关闭会话只去掉引用,KV 回到普通顺序。

### 8.5 树之上还挂了什么

节点上有一串按页的哈希,那是 host 内存和分布式存储的键(05 章);树的插入和删除会发出事件,发布给路由网关维护近似的树(18 章)。都不改变本章讲的树。

## Part 9|图解

### 9.1 三条请求进树

```text
  请求 A = [sys(2000) | q1(20)]        请求 B = [sys(2000) | q2(30)]        请求 C = [sys | q1 | ans1(100) | q3(25)]

  A 结束后:                B 结束后(在 sys 之后分叉):        C 结束后(顺着 A 的路往下长):

  root                     root                                root
   └─ [sys q1]              └─ [sys]                            └─ [sys]
      (2020 个槽)              ├─ [q1]                              ├─ [q1]
                               └─ [q2]                              │   └─ [ans1 q3]      <- C 命中 sys+q1,新算 125
                                                                    └─ [q2]

  B 到达时匹配 [sys q1] 命中 2000 个,不到整段,节点被劈成 [sys] 和 [q1];B 只算 q2 的 30 个。
  C 到达时走 root -> [sys] -> [q1],2019 个命中,最后 1 个留给本次前向。
```

### 9.2 显存紧张时谁在让谁

```text
  准入要 n 个槽 ──> 空闲槽够吗 ──否──> 树里可驱逐的够吗 ──是──> 从叶子丢到够 ──> 放行
                      │是                     │否
                      └──> 放行                └──> 踢在飞请求(不插树)──> 再问一遍

  树永远排在新请求后面;只有被锁的路径(在飞请求正在读)不让。
```

## Part 10|机制之外:源码里额外读到的

### 10.1 补插用更高的优先级

prompt 边界那次补插带的优先级比整段插入高一,路径取最大值,所以 prompt 段的优先级永远不低于输出段。在 priority 策略下这意味着输出段先走。

### 10.2 根是特殊的

根节点键是空序列,引用计数初始为一,优先级是最小整数。前两条保证它永不被驱逐,第三条保证任何真实优先级都能覆盖它。

### 10.3 强制未命中

一个调试环境变量能让所有匹配返回零命中,用来测「没有前缀缓存」的基线,不用重启改配置。

### 10.4 关掉前缀缓存之后不是没有树

关掉后换成一个只做分块的缓存:它只负责在分块 prefill 之间保住已算的部分,请求结束就全释放。缓存感知策略这时自动退回先来先服务。

### 10.5 批内查重那棵树的值是假的

模拟树不接内存池,插入的值是同长度的布尔张量,只为让匹配能返回长度。每轮准入前清空重建。

### 10.6 「结束时不插入」的开关没人用

树的构造参数里有一个「结束时不插入」的开关,基准上没有任何调用方设置它。

## Part 11|收益账、对比与决策

### 11.1 命中率怎么传到 TTFT

设 prompt 长 L,命中比例 h,prefill 吞吐 R(token 每秒),首 token 的一次 decode 耗时 d,则

$$\text{TTFT} \approx \frac{L(1-h) + 1}{R} + d$$

加一是 2.4 那个永远要算的 token。算例:L 等于 5000,R 取 20000 token 每秒(假设值),d 取 20 毫秒。h 为 0 时 TTFT 约 270 毫秒;h 为 0.9 时约 45 毫秒;h 为 1 时约 20 毫秒,几乎全是 d。曲线的意思是:命中率从 0 到 0.9 把 TTFT 砍掉 80%,从 0.9 到 1 的最后一段只剩下 d,所以**追求最后几个点的命中率不值,守住前 90% 才值** ,而前 90% 靠的是 Part 4 那些别让它掉下来的事。

### 11.2 和 vLLM 的块哈希比

| 维度 | vLLM 块哈希 | SGLang radix 树 |
|---|---|---|
| 找前缀 | 逐块算哈希、查表,哈希把前一块卷进来保证前缀相同 | 从根往下走,树的形状保证前缀相同 |
| 命中粒度 | 整块(默认 16) | 单 token;后端要求整页时退化到 32 或 64 |
| 分叉处 | 半块要复制或丢弃 | 劈开节点,不动 KV |
| 地址表 | 块数级 | 并发乘上下文,GB 级 |
| 跨进程 | 哈希可复现 | 树只在进程内,跨实例靠网关近似树 |
| 与调度器 | 调度器不看缓存 | 默认按命中长度排队,还做批内查重 |
| 驱逐单位 | 块 | 叶子节点 |

两边的分歧是把复杂度放在哪:vLLM 放在哈希和块对齐上,换来小表和可复现的键;SGLang 放在树上,换来 token 级命中和调度器能利用的结构。当页被后端钉成 64 时,两边的命中粒度已经没有差别。

### 11.3 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| disable_radix_cache | 关 | 关掉跨请求复用 | 负载没有共享前缀时开,省匹配开销 |
| schedule_policy | lpm | 排队策略 | 命中短的请求饿死换 hrrn;树深且请求聚集试 dfs-weight |
| radix_eviction_policy | lru | 驱逐打分 | 热点被冲掉换 lfu 或 slru;多轮尾延迟敏感换 tlru |
| radix_eviction_policy_config | 空 | 策略参数,JSON | 键写错启动就报错 |
| enable_session_radix_cache | 关 | 按会话登记引用 | 长会话多、显存紧张时开,客户端要传会话号并关闭 |
| page_size | 1 | 命中向下取整到整页 | 别手调,后端会改;改了就是 3.1 的情况 |
| mem_fraction_static | 按显卡 | 显存余量 | 想要命中率就给树留余量,见 4.3 |
| 树核后端(环境变量) | python | 切 rust | 匹配成 CPU 瓶颈时试 |
| 批内查重阈值(环境变量) | 32 / 32 | 命中多短才查、批内共享多长才降级 | 设负一关掉 |

### 11.4 什么时候关,怎么看命中率

请求之间没有共享前缀的负载(随机采样的离线评测)关掉更快。命中数在每条请求的响应元信息里,开了分层缓存还会细分命中落在哪一层;要看「没有缓存会怎样」用强制未命中的开关跑一遍对比。

### 11.5 常见误区

- 全命中的请求 TTFT 不是零,永远还要算一个 token。
- MLA 模型配主流后端时命中粒度是 64,不是 token。
- 不同 LoRA 的请求不共享前缀,哪怕 prompt 完全一样。
- 高并发下命中率低是准入优先的结果,不是缓存坏了;想要命中率就留显存余量。
- 队列超过 128 时缓存感知排序自动关闭,日志不提示。
- 上一轮的回答比系统提示词先被驱逐,多轮负载显存紧张时先查这个。
- 被抢占的请求什么都不留,重算全部。
- 默认树核是 Python,Rust 不是默认。
