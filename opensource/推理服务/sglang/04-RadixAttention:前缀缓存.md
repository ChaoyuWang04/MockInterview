# SGLang 04|RadixAttention:前缀缓存

前缀为什么能复用、链式哈希凭什么保证不误命中、命中边界落进块内部时为什么要复制,vLLM 解读的「Prefix Caching」一章已经讲透;基数树本身是什么、为什么淘汰必须从叶子开始,知识库的 RadixAttention 一篇讲过。这一页只说 SGLang 拿这棵树多做了哪几件事、代价落在哪、以及和 vLLM 不一样的地方。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

一段 5000 token 的 prefill 在一张卡上是 50–500 毫秒,多轮对话每一轮都付一次。这笔账 vLLM 那章已经算过,省掉它的办法两边也一样:算过的那段 KV 留着,下一条请求直接引用。

SGLang 真正多问的是另外两件事,它们只在多轮对话、agent 循环、RL rollout 这三类负载上显出来:

- **分叉点落在任意一个 token 上。** 上一轮回答有多长是模型定的,不会正好停在 16 的倍数上;agent 每一步往上下文里塞的工具输出也不会。
- **前缀之间有辈分。** 一个系统提示词底下挂着 100 条会话,一条会话底下挂着 10 轮,一轮 prompt 底下挂着 64 条采样。显存不够时最该留的是最上面那一层,最该丢的是最下面那一层。

一张按块算出来的哈希表答不了第二件事:系统提示词的那几块,和某条会话最后一轮回答的那一块,在表里是平级的两条记录——谁是谁的祖先根本没被记下来。**这一章的全部内容,是把这层辈分显式地存下来之后能多做哪几件事,以及为此付了什么。**

## 二、解法:让结构本身携带信息

把所有请求的 token 序列合成一棵树,没有分叉的一段压成一个节点,节点的值是这段 token 各自的格子号(03 章)。树是什么、为什么先丢叶子,知识库那篇讲过;下面只说 SGLang 让这棵树额外管了什么。

![一棵前缀树上同时在发生的四件事:根往右是所有请求共用的系统提示词与工具说明,它底下挂着两条会话分支和一条一次性请求;会话 A 的第二轮正在跑,它从叶子一路到根的每个节点都被锁住不可丢;会话 B 已经结束,结束时代码在它的 prompt 和回答之间又劈了一刀,回答那半边成了独立的叶子;显存不够时可丢的只有两片叶子,主干要等它底下全空才轮得到,而被丢掉的顺序里回答永远排在 prompt 前面](/opensource/sglang/04a-tree-who-goes-first.svg)

**匹配、劈开、锁。** 新请求从根往下走,走到哪分叉就从哪开始算。走到某个节点中间才分叉,就把这个节点从那里劈成两半——劈的只是树的拓扑和那串格子号,KV 一个字节都不动。全命中的请求也要留最后 1 个 token 给这次前向,因为要拿它算 logits。进批的请求给自己这条路径上的每个节点各加一次锁,一路加到根,锁着的节点不会被丢;结束时解锁,路径留在树上变成可丢的缓存。

**结束的时候还要再劈一刀。** 一条从头到尾没被缓存过的请求,如果把整条路径(prompt 加回答)当成一个叶子插进去,显存紧张时就只能整段丢——连同下一轮还要用的那截 prompt 一起。所以插完之后代码会拿 prompt 那一截再插一遍,专门在 prompt 与回答的交界处把这个叶子劈开,并且给 prompt 那半边更高的保留优先级。**回答先被丢、prompt 留着,是设计出来的,不是碰巧。**

**驱逐只从叶子挑。** 显存不够时把当前所有可丢的叶子按一个分数排一遍,最低的先走;丢掉一个,它的父节点可能刚好变成叶子,再入选下一轮。打分函数有 8 种实现,命令行上放出来 5 种,各自换的东西不同:按命中次数排让热点 prompt 不被一次性流量冲掉,按尾延迟排让多轮负载的长尾优先于总命中率,按请求优先级排让缓存的去留跟准入一致。

**调度可以读这棵树。** 等待队列的排序有三种策略会去看树:按命中长度排、按子树权重深度优先排、按「等了多久比还要算多少」排。前两种让同源的请求连着进批,一次 prefill 就把树长好,后面的全命中;第三种是防止命中短的请求被一直插队。**默认不是它们中的任何一个,而是到达顺序。**

**同一批里的同源请求另有一道。** 只有在上面那三种策略生效时,调度器才会另建一棵不接显存池的模拟树,把本轮等待队列里彼此共享很长前缀的那几条先压后一轮,让其中一条先把树长出来、其余的下一轮全命中。默认的到达顺序下这道完全不跑,同一个 prompt 的 64 条采样会一起进批、一起从头算。

**树还能往下延伸。** 显存里的节点被丢之前先备份到内存和硬盘,见 05 章。

## 三、代价

- **这棵树只活在一个进程里。** 哈希是纯函数,两个进程对同一段 token 能算出同一个指纹;树不行,它是一份有状态的结构。所以 PD 分离的 decode 端默认不建树,多个副本之间也共享不了,要跨实例的缓存感知只能在外面另起一个网关、照近似的规则再建一棵(18 章)。
- **匹配和排序是 CPU 的活。** 按命中长度或按等待比排队,每一轮都要把整个等待队列逐条走一遍树。队列一长这笔开销就压过收益,所以调度器到了某个长度会自己退回到达顺序——而且日志里不说。
- **地址表按最坏情况买断 2 GB**(03 章)。树能在任意 token 劈开的前提,就是这张表一格一个 token,这笔固定成本先付掉。
- **后端钉页之后命中退到页边界。** 匹配前先把长度向下取整到页,所以页被改成 64 的后端上,命中数永远是 64 的倍数(03 章)。
- **并发拉满时树被驱逐空。** 缓存只用在跑的请求剩下的那点显存,并发越高留给树的越少,命中率跟着归零——这个时候换驱逐策略没有任何用。
- **上一轮的回答活不到下一轮。** 这是第二节那一刀的另一面:回答那段是叶子,先丢。推理模型上甚至有个开关直接不缓存思考段和回答,结束时只把 prompt 前缀留在树上。

## 四、和 vLLM 不一样的六处

![vLLM 和 SGLang 的前缀缓存都必须做的三件事各占一行:第一行是认出哪一段算过,vLLM 查一次哈希表拿回一个答案也就是算过没有,SGLang 走一趟树拿回三个答案分别是命中多长、停在哪个节点、这个节点底下还挂着谁,答案数量一比三就是后面两行差别的来源;第二行是显存不够时挑谁丢,vLLM 把所有缓存块排进同一条队列,主干块和会话尾巴块在队列里平级、位置只看谁久没被碰,SGLang 只从叶子挑,主干在树的上游要等底下全空才轮得到;第三行是等待队列里谁先进批,vLLM 两种排队策略都不看缓存,SGLang 在不看缓存的四种之外另有三种会读树,其中两种在队列长时自动退回到达顺序](/opensource/sglang/04b-vllm-diff-three-jobs.svg)

1. **指纹对树。** vLLM 每 16 个 token 算一个链式哈希,查一次表拿回一个答案:这一段算过没有。SGLang 走一趟树,拿回来的是三样东西——命中多长、命中停在哪个节点、这个节点底下还挂着谁。后面五处全是从多出来的那两样里长出来的。
2. **丢谁。** vLLM 把带哈希的块排进一条 LRU 队列,队首先丢;系统提示词的块和某条会话最后一轮回答的块在这条队列里是平级的,谁久没被碰谁先走。SGLang 只从叶子挑,主干要等它底下全空了才轮得到,人人都要走的那段开头因此天然最后丢。
3. **谁先进批。** vLLM 的两种排队策略——到达顺序与按优先级——都不看缓存。SGLang 默认也是到达顺序,但另有三种会去读树。**开了之后不一定一直生效**:按命中长度和按等待比这两种,在等待队列超过某个长度时会自己退回到达顺序;按子树权重那种不退。
4. **同一批里的同源请求。** vLLM 刻意不去重,一个哈希可以对应多个物理块。SGLang 用模拟树在批内查重,把重复的压后一轮。但这道挂在上一条的三种策略里,而且只有按命中长度和按等待比这两种真的会用上查重的结果——按子树权重那种照样算了一遍,却把结果丢掉了。默认的到达顺序下它根本不跑。
5. **清空整棵树这件事。** vLLM 那边是一个调试端点,只要还有块被占着就返回失败,要调用方自己重试。SGLang 这边多两样:手动那个端点可以带一个等待时长,在这段时间里盯着,等到服务完全空闲再清;而且四个权重更新接口各自带一个清缓存开关,**默认都是开的**。RL 训推一体下这是必需品——旧权重算出来的 KV 配上新权重,命中越高答案错得越离谱,而且没有任何报错。
6. **树的形态。** SGLang 默认用的不是上面讲的那棵经典树,而是一棵统一树:同一棵树上按层型分成全注意力、滑动窗口、Mamba、C128 四类组件,每类各有自己的驱逐链,丢掉一个内部节点会级联丢掉它下面的另外几类。树核还能整个换成 Rust 实现,代价是那个实现不认驱逐策略的参数、不认按会话保护、也不认 C128 这类组件。

## 五、调参与观测

**参数在哪调。** 树的开关、排队策略、驱逐策略都是启动参数,改了要重启;批内查重的两个阈值和树核后端是环境变量;按会话保护要客户端配合,每条请求带同一个会话号、结束时调关闭接口(错误与取消路径也要调)。运行时只有两件事:`/flush_cache` 清空整棵树,以及四个权重更新接口自带的清缓存开关。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--disable-radix-cache` · 关掉前缀树 | 启动 | 关(树开着) | 开:换成按块切的 chunk 缓存,没有共享前缀的负载省下每轮的匹配与插入;有共享前缀的负载 TTFT 直接变差 | `Prefill batch` 行的 `#cached-token` 归零 |
| `--schedule-policy` · 等待队列按什么排 | 启动 | `fcfs`,到达顺序 | `lpm` 按命中长度排,同源连着进,批内查重也只在它和 `hrrn` 下生效;`dfs-weight` 按子树权重深度优先,不用查重结果但也不会退回;`hrrn` 防命中短的请求饿死。候选值里的 `priority` 没有实现,填了启动就报未知策略 | `#cached-token`,以及队列里长尾请求的等待时间 |
| `--radix-eviction-policy` · 显存不够时先丢谁 | 启动 | `lru` | `lfu`、`slru`:热点 prompt 不被一次性流量冲掉;`tlru`:多轮与 agent 的尾 TTFT 优先于总命中率,要默认的统一树;`priority`:没开优先级调度时每个节点都是 0,等价于 `lru` | 换策略前后的 `#cached-token` 与 TTFT 分布 |
| `--radix-eviction-policy-config` · 驱逐策略的参数 | 启动,JSON | 空 | `slru` 收 `protected_threshold`(默认 2);`tlru` 收 `threshold` 与 `next_prompt_estimate`,前者必须大于后者。键写错启动就报 TypeError,不会被忽略;`lru`、`lfu`、`priority` 不收任何键 | 启动是否成功 |
| `--enable-session-radix-cache` · 按会话保护缓存 | 启动 | 关 | 带同一个会话号的 KV 比无主的 KV 后被丢;是软保护不是钉住,腾不出空间照样丢。Rust 树核不支持,同时开启动报错 | 多轮负载显存紧张时的 TTFT |
| `--strip-thinking-cache` · 推理模型的思考段与回答不入树 | 启动 | 关 | 开:结束时只留 prompt 前缀,思考段与回答被当成多分配的空间直接释放;缓存内容因此变了,所以是显式开关 | 同一会话下一轮的 `cached_tokens` |
| `--disaggregation-decode-enable-radix-cache` · PD 分离的 decode 端开树 | 启动 | 关 | 开:D 端先匹配再锁,P 端跳过 D 已经有的那一截、只传剩下的。与 HiSparse、推测解码、假传输后端不兼容 | decode 端的 `#cached-token` |
| `--page-size` · 分配的最小单位是几个 token | 启动 | 见 03 章 | 别手调;被后端钉成 64 之后匹配先向下取整,命中只能落在页边界 | `cached_tokens` 是不是总是 64 的倍数 |
| `--mem-fraction-static` · 权重加 KV 占显存的比例 | 启动 | 见 03 章 | 树只用在跑的请求剩下的显存;想要命中率就得留余量 | `token usage` 贴着 1 时树已经被驱逐空 |
| `IN_BATCH_PREFIX_CACHING_CHECK_THRESHOLD` · 命中多短才做批内查重 | 环境变量 | 32 | 命中已经超过它的请求不查重(长前缀本来就会命中);设 -1 关掉整道 | RL 同 prompt 多条时的 `#new-token` |
| `IN_BATCH_PREFIX_CACHING_DEPRIORITIZE_THRESHOLD` · 批内共享多长才压后一轮 | 环境变量 | 32 | 调低:更容易把同源请求拆到不同轮,总命中率高一点,首条的等待久一点 | 同上 |
| `SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND` · 树核用 Python 还是 Rust | 环境变量 | `python` | `rust`:匹配成了 CPU 瓶颈时试;不认驱逐策略参数、不认按会话保护、不认 C128 组件,撞上就启动报错 | 调度一轮的耗时 |
| `SGLANG_RADIX_FORCE_MISS` · 强制所有匹配返回零命中 | 环境变量 | 关 | 调试用,拿来对照「完全没有缓存会怎样」 | 对照前后的 TTFT |

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表;组合与推荐值是按语义推的起点,**不是实测最优**。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 多轮对话或 agent,共享一段长系统提示词 | 在 03 章那套通用起法上加 `--schedule-policy lpm`;命中率仍不稳就把 `--mem-fraction-static` 再压 0.02,给树留余量 | 用「每轮一次全队列匹配」换命中率;队列一长它自动退回到达顺序,所以高并发压测的数字会比小并发时难看 |
| RL rollout,同一个 prompt 采 64 条 | `--schedule-policy lpm`,批内查重那两个阈值保持默认;权重更新接口的清缓存开关保持开着 | 用第一条多等一轮,换其余 63 条全命中;代价是首条的 TTFT 被拉长,以及每次换权重都要重新把树长一遍 |
| 离线评测或随机 prompt 压测 | 加 `--disable-radix-cache`,`--schedule-policy` 留默认 | 省掉每轮的匹配与插入,换掉全部命中收益;前缀几乎不重复时这笔是净赚 |

**怎么看。** `Prefill batch` 行的 `#new-token` 对 `#cached-token` 就是这一批的命中比,同一行的 `#queue-req` 是当前等待队列长度——它越过退化阈值时,按命中长度排就已经不生效了,而日志不会提示。请求级看响应 `meta_info` 里的 `cached_tokens`,开了三层缓存时 `cached_tokens_details` 还会细分命中落在哪一层。多轮负载要看 TTFT 的分布而不是平均值:上一轮回答被丢的那一次会拉出一根长尾。

| 症状 | 先查 | 然后 |
|---|---|---|
| 命中率突然掉一半 | 启动日志里 page_size 有没有被后端改掉;`#queue-req` 是不是长到让排队策略退化了 | 换后端,或接受页边界命中;限流,或换成不会退化的 `dfs-weight` |
| 多轮负载的 TTFT 有长尾 | `token usage` 是不是贴着 1,树已经被驱逐空 | 留余量、开 HiCache,或换 `tlru`、开按会话保护 |
| 同一个 prompt 的 64 条 rollout 全部重算 | `--schedule-policy` 是不是默认的 `fcfs` | 批内查重只在 `lpm` 与 `hrrn` 下生效,先把策略换掉再谈阈值 |
| 多 LoRA 服务命中率低 | 适配器标识拼在键的最前面 | 每个适配器各一棵子树,同样的 token 一个都不共享;按适配器分实例 |
| PD 分离下 P 端每次全量传 | decode 端的树默认是关的 | 开 `--disaggregation-decode-enable-radix-cache`;与 HiSparse、推测解码不能同开 |
| 换驱逐策略后启动就报错 | JSON 的键名;是不是在 Rust 树核上传了策略参数 | 对照文档的键;Rust 树核只认策略名,不认参数 |
| 填了 `--schedule-policy priority` 启动报未知策略 | 这个候选值没有对应实现 | 要按优先级调度就开 `--enable-priority-scheduling`,策略留 `fcfs` |
| `/flush_cache` 一直返回失败 | 有请求在跑或在排队时它直接拒 | 带上 `timeout`,让它等到完全空闲再清 |

## 六、常见误区

- **缓存感知排队是默认开的。** RadixAttention 的博客把「缓存感知调度」当招牌讲,人就以为装上就有。实际上默认是到达顺序,要按命中长度排得显式指定 `lpm`,官方调参文档也只是写「有共享前缀可以试试 `lpm`」。
- **批内查重是一道独立的兜底。** 不是。它长在按缓存排队的那条路径上,默认的 `fcfs` 下整道不执行;更隐蔽的是 `dfs-weight` ——它会把查重算完,然后把结果丢掉。真正用上查重结果的只有 `lpm` 和 `hrrn`。
- **开了 `lpm` 就一直在生效。** 等待队列一长它就退回先来先服务,日志不提示。压测时命中率随并发往下掉,先看 `#queue-req`,不要先去换驱逐策略。
- **命中率低就换驱逐策略。** 多数时候是在跑的请求把显存占满、树被驱逐空了,这时候换什么策略都一样。先看 `token usage`,留余量或者开三层缓存。
- **RL 换了权重得自己记得清树。** 反了。四个权重更新接口的清缓存开关**默认就是开的**,真正的坑是有人为了省时间把它关掉——旧权重算的 KV 配新权重,命中越高答案错得越多,而且没有任何报错。
- **`/flush_cache` 调了就一定清干净。** 不带等待时长时,只要队列里有人等或者有请求在跑,它直接返回失败;带上等待时长才会盯着,等到完全空闲再动手。
- **上一轮的回答和系统提示词一样安全。** 代码专门在 prompt 与回答的交界处把叶子劈开,并给 prompt 那半边更高的保留优先级——回答先丢是写在实现里的意图。多轮负载显存紧张时的长尾 TTFT 就来自这里。
- **全命中的请求 TTFT 应该接近 0。** 永远还要算最后 1 个 token,因为要拿它出 logits。
- **prompt 完全一样就一定共享。** 不同适配器、不同缓存盐的请求,标识拼在键的最前面,从根开始就是两棵互不相干的子树,一个 token 都不共享。多模态输入按内容哈希占位,同一张图才共享。
- **PD 分离下前缀缓存自动生效。** decode 端默认是关的,不开就是 P 端每次全量传。
- **开了按会话保护就万事大吉。** 客户端要在每条请求上带同一个会话号,会话结束要调关闭接口,错误和取消路径也要调,否则引用一直挂着。而且它是软保护:腾不出空间时,被引用的 KV 照样丢。
- **Rust 树核是默认。** 默认是 Python。切过去之后驱逐策略参数、按会话保护、C128 组件这三样都不认,撞上直接启动失败,不是静默降级。
- **离线评测也该开树。** 随机采样的评测集没有共享前缀,树只多出每轮的匹配与插入,关掉更快。
- **命中率要自己估。** 不用,响应里就有;想知道完全没有缓存会怎样,用强制未命中的那个环境变量跑一遍对照。
- **`--help` 里列出来的排队策略都能用。** 因为命令行的候选值就是它给的。`priority` 在候选值里,但两个策略枚举合起来没有它,填了直接以未知策略启动失败——要按优先级调度得开另一个开关(第五节),而且开了之后排队策略只能配到达顺序或按输出长度排。
