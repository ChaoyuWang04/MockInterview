# SGLang 04|RadixAttention:前缀缓存

03 章把 KV 放进了两级表,但有件事它没管:系统提示词、few-shot、上一轮对话,每来一条请求都从头 prefill 一遍,算出来的 K 和 V 和上一条一模一样。这一章讲 SGLang 用一棵 radix 树把算过的前缀留下来给后来人:树凭什么敢复用、什么情况下你以为命中了其实没有、命中率和并发怎么抢同一块显存、显存满了先丢谁,以及拆成 PD 分离和三层缓存之后这套复用还成不成立。

全章内容都在源码上逐条核对过。每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:同一段前缀不该算第二遍

### 1.1 真实负载里,请求共享的开头有多长

| 场景 | 公共前缀 | 典型长度 |
|---|---|---|
| 系统提示词 | 「You are a helpful assistant…」加工具说明 | 200–3000 token |
| few-shot | 几个示例对话 | 500–5000 token |
| RAG | 检索到的文档片段 | 1000–10000 token |
| 多轮对话 | 整段历史 | 2000–50000 token |
| agent 循环 | 工具说明加全部历史步骤 | 2000–50000 token,每步都在长 |

朴素做法下,每条新请求把整个前缀 prefill 一遍,哪怕这段的 K 和 V 上一条请求刚算完、此刻还躺在显存里。

### 1.2 省下的是 prefill,动的是三个指标

prefill 是算力密集的,5000 个 token 在一张卡上是 50–500 毫秒。前缀缓存让新请求只算它独有的那一段,直接动三个数:

- **TTFT 下降**:5000 token 的文档前缀全命中后,只剩最后一个 token 要算,首字延迟从 200 多毫秒掉到 20 毫秒上下(6.3 有算例)。
- **吞吐上升**:省下的算力直接服务更多请求。这一项通常比 TTFT 更值钱,因为 prefill 和 decode 在同一张卡上抢时间。官方博客给的数字是相对不做前缀复用的引擎最高 5 倍吞吐(官方数字,多轮和 few-shot 负载)。
- **显存不涨**:复用靠的是两级表里多行指向同一个槽,不复制数据。

代价在后面逐条出现:树本身要一张按最大值买断的地址表;每轮调度要把等待队列匹配一遍,这是 CPU 的活;树里留下的 KV 和在飞请求抢同一块显存,而且抢不过;拆成 PD 分离之后树也要拆成两棵。

### 1.3 复用的前提:整条前缀逐字相同

因果注意力保证第 i 个 token 的 K 和 V 只依赖它前面的 token。所以两条序列只要前 n 个 token 完全相同,这 n 个位置在每一层的 K 和 V 就完全相同。反过来,**前缀里任何一处不同,从分叉点起后面所有位置的 KV 都是错的,而且不报错**:第一层看起来还对,第二层起 attention 已经读到了不同的 K。这个证明 vLLM 04 章「只看本段 token 行不行」一节逐层写过,这里不重复。

它给缓存定了一条铁律:能复用的只有「从第一个 token 开始连续相同」的那一段,一个 token 都不能跳。

### 1.4 于是要解决三件事

- **找**:上百条在途和历史请求里,谁和新请求的公共前缀最长,那段 KV 在哪些槽。
- **留**:请求算完了 KV 要留给后来人;正在被人用的那段不能被回收。
- **丢**:显存有限,先丢谁。

vLLM 用块哈希链解决「找」,命中只能停在块边界。SGLang 把「前缀」这个概念直接做成数据结构:所有请求的 token 序列合并成一棵前缀树,找公共前缀就是从根往下走,命中可以停在任何一个 token。

### 1.5 一个公式:命中长度

$$\text{hit} = \min\Big(\Big\lfloor \frac{\mathrm{LCP}(\text{seq}, \text{tree})}{\text{page}} \Big\rfloor \times \text{page},\ \ |\text{seq}| - 1\Big)$$

三项各有来历。LCP 是新序列与树里任何一条路径的最长公共前缀,树的结构保证它就是「从根往下能走多远」。除以页再乘回去,是因为按页分配时半页的槽号不是页对齐的,分配器给不出后半页的位置,所以半页不算命中。减一是硬性封顶,1.8 讲。

只要记住这个公式,后面 2.5 那五种「以为命中了其实没有」都是它的某一项在起作用。

### 1.6 前缀关系就是树的形状

普通前缀树一个节点一个 token,2000 个 token 的系统提示词是 2000 个节点。radix 树把没有分叉的一段压成一个节点,键是一段 token,值是这段 token 的槽号,等长对应;只在分叉处才拆开。系统提示词在树里就是一个节点,走一步。

子节点放在字典里,字典键是子节点键的第一个 token(按页分配时是第一页的 token 元组)。从一个节点往下不需要遍历孩子,拿新序列的下一个 token 查一次字典就知道进哪个孩子。所以匹配的成本是「分叉数」量级,不是 token 数量级。

比较两段 token 是否相同用指数搜索:先比 1 个、2 个、4 个,每次一次 C 层切片比较,找到第一个不同的窗口再二分。长前缀不需要逐 token 的 Python 循环。

### 1.7 劈开只发生在公共前缀的末尾,而且只改拓扑

新序列走到某个节点,公共长度短于节点键的全长,说明分叉在节点内部。这时把节点从公共长度处劈成两段:前半段接在原位,后半段成为它的孩子,两半各拿原值张量的对应切片。**KV 一个字节都不动**,动的只是树。

劈开发生在匹配路径上,也就是一次只读的查询会改树的形状。单进程里无害;张量并行下每个 rank 必须做一模一样的匹配,否则各 rank 的树分叉、槽号对不上,统一树在插入和驱逐接口上做了跨 rank 的一致性校验。

### 1.8 为什么全命中也要算一个 token

一条请求和树里某条路径完全相同时,公式里的减一起作用:匹配长度最多是输入长度减一,最后一个 token 永远留给这次前向去算。源码注释给的理由是要能算 logprob:输出第一个 token 的分数必须由本次前向产生,不能从缓存里拿。所以「全命中」的请求 TTFT 不是零,是一个 token 的 extend 加一次采样。

EAGLE 推测解码下再少一个:草稿模型第 i 个位置的 KV 依赖第 i 加一个 token,树把键看成二元组,n 个 token 只有 n 减一个键,最后一个 token 本身就不进树。

### 1.9 同样的 token,不同的命名空间永远不相遇

换了 LoRA 适配器,或者调用方明确要求隔离,同样的 token 序列 KV 也不同。树用两个附加键处理:LoRA 的 id 会拼进 extra_key,调用方还可以给 cache_salt。附加键进了子节点字典的键,不同命名空间的序列在树里落进不同的孩子,连比较都不会发生。**多 LoRA 服务里命中率低,先查是不是每个适配器各自一棵子树** 。

多模态走的是另一条路:图片在 token 序列里占的位置被替换成由图片内容哈希算出的占位 token,所以同一张图两次请求能命中,不同的图天然分叉,不需要附加键。

## Part 2|命中、保护与回收

### 2.1 命中之后:锁从停留节点走到根

请求命中之后会一直读那段前缀的 KV。树用引用计数保护:进批时从停留节点走到根,每个节点计数加一;结束时走一遍减一。计数大于零的节点不参与驱逐。树同时记两本账,可驱逐的 token 总数和受保护的 token 总数,节点计数在零和一之间变化时长度在两本账之间挪。准入闸门看的是第一本账。根节点计数初始为一,永不驱逐。

### 2.2 一个请求和树打交道的五个时刻

| 时刻 | 树做什么 | 谁持有槽 |
|---|---|---|
| 准入 | 匹配得到命中槽号与停留节点;算预算时临时锁,进批后正式锁并存下解锁凭据 | 命中段归树,新段未分 |
| 分块 prefill 每块结束 | 已算部分插入;重新匹配拿新的停留节点;解旧锁加新锁 | 已算部分转归树 |
| decode 每步 | 不碰树 | 新槽在请求手里 |
| 结束 | 整段插入;prompt 边界补插;释放和树重复的槽;解锁 | 全部转归树 |
| 被抢占 | 释放,不插入 | 全部回收 |

### 2.3 分块 prefill 每块结束就先插一段

长 prompt 分几块算(02 章),每块算完就把已算的部分插进树,不等整个请求结束。原因很实际:同一份长文档同时有几条请求在排队,第一条算完第一块,第二条就能命中第一块。插完之后请求重新匹配一次,拿到新的停留节点,解开旧锁、加上新锁。中间插入不给路径上的节点加命中计数,否则一条长请求会把自己的前缀刷成热门。

### 2.4 结束:整段插入,再在 prompt 边界补一刀

请求结束时,把 prompt 加输出整段作为键、这一行的槽号作为值插进树。插入返回命中了多长,那段是别人已有的,这条请求自己那份槽号释放掉;命中之外的才是它留给树的。

然后再做一件事:用 prompt 那一段单独再插一次。整段插入产生的是一个叶子,prompt 和输出在同一个节点里,驱逐时要丢一起丢。补插 prompt 会把这个叶子从 prompt 边界劈开,输出段成为独立的叶子,可以先于 prompt 被驱逐。注释写的理由是:LRU 驱逐可以丢掉输出的 KV 而不连带丢掉可复用的 prompt KV。补插的这次不加命中计数,优先级比整段高一。

### 2.5 你以为缓存了,其实没有

| 情况 | 发生了什么 | 公式里的哪一项 |
|---|---|---|
| 后端把页钉成 64 | FlashMLA、HPC-Ops 只认 64 的页,TensorRT-LLM 和 CuteDSL 的 MLA 后端只认 32 或 64,启动时配置层把 page_size 改过去(03 章)。两条请求共享 2050 个 token,命中 2048 个,尾巴 2 个加后面整段重算 | 向下取整到页 |
| 全命中 | 最后一个 token 永远留给本次前向 | 减一 |
| 被抢占 | 释放全部 KV,不插树,重新排队后从头 prefill;抢占顺序默认踢输出最少的,也就是刚开始的请求先走(03 章) | LCP 归零 |
| 请求还没结束 | decode 期间产生的 token 一个都不进树。多轮对话第二轮要命中第一轮的回答,第一轮必须已经结束;两条同时在跑的请求谁也命中不了谁的输出 | 树里还没有 |
| 上一轮的回答 | 2.4 让输出段成为独立叶子。系统提示词场景这是对的;多轮对话里上一轮的回答恰恰是下一轮前缀的一部分,而它是树上最先被丢的那批 | 被驱逐 |

**radix 树「命中到 token」的招牌,在最需要它的 MLA 模型上不成立** ,那里它和块哈希只差一个数据结构。多轮 agent 负载在显存紧张时命中率先崩,先查最后一行。

### 2.6 回收:只丢叶子,从枝尖往根走

能被丢的节点要同时满足:KV 还在显存、没有请求锁着、没有还持有 KV 的孩子。第三条是关键,丢掉一个有孩子的节点等于把孩子的前缀丢了。所以驱逐永远从叶子开始。需要腾 n 个 token 时,把可驱逐叶子按策略打分放进堆,弹分数最低的,释放槽,删叶;父节点因此没有孩子且没锁,就成了新叶子入堆。驱逐沿一根枝从尖往根走,直到够数。

策略只打分,不决定丢多少,也不能把节点钉死:其他都丢完还不够,策略再保护的节点也会被丢。树不主动清理,所有驱逐都是分配器在分配前问出来的(03 章)。

### 2.7 八种打分,各动哪个指标

| 策略 | 先丢谁 | 动的是什么 |
|---|---|---|
| lru(默认) | 最久没访问的 | 通用命中率,前缀复用随时间衰减 |
| lfu | 命中次数最少的 | 热点 prompt 的命中率,扛一次性流量 |
| slru | 命中没过门槛的先丢 | 同上,但给「证明过的」前缀一条硬底线 |
| priority | 插入它的请求优先级最低的 | 让缓存保留和准入用同一套排序 |
| tlru | 超出下一轮 TTFT 预算的对话尾巴 | 多轮负载的尾延迟,不是平均命中率 |
| fifo、mru、filo | 按创建时间或反向 | 只在注册表里,命令行不提供 |

命中次数只在别的请求命中时加。tlru 是唯一直接以延迟指标为目标的策略,它承认一个事实:多轮对话里保住整段历史不一定值,保住「下一轮 prefill 能在预算内完成」的那部分才值。

### 2.8 命中率与并发抢同一块显存,准入永远赢

准入闸门算「还能放多少 token」时,把树里可驱逐的 KV 也算作可用:预算等于空闲槽加可驱逐槽。也就是说树里的 KV 从来不会挡住新请求;新请求要地方,树先让。结论有两层:

- 前缀缓存不会降低并发上限,它只用空闲显存。
- 并发拉满时,树被驱逐得只剩正在被锁的路径,命中率趋近于「同时在飞的请求之间的共享」,历史请求留下的东西基本没了。

所以高并发下命中率低是设计使然:显存要么给在飞请求当 KV,要么给树当缓存,准入选前者。想要命中率,要么留显存余量,要么把缓存往外扩(Part 3)。官方调参文档说 token usage 在 90% 以上是健康的,那 90% 里包含树占的部分。

另外两笔固定成本:token 级命中要求每个 token 能单独指向任意槽,所以地址表是「每请求一行、每行最大上下文长度」的整数表,按最大并发一次买断,4096 并发、131072 上下文就是 2 GB(03 章);命中长度排序需要每轮对整个等待队列逐条走树,这是 CPU 上的串行工作,零开销调度(02 章)藏不掉它。

### 2.9 谁先进批,决定谁能命中

两条共享前缀的请求,先进批的那条算完,后进的才能命中;先算了不相干的第三条,前两条各算一遍。所以默认调度策略是缓存感知的:

| 策略 | 排序依据 | 动的指标 | 坑 |
|---|---|---|---|
| lpm(默认) | 每轮对等待队列逐条匹配,按命中长度降序 | 命中率、TTFT | **队列超过 128 条自动退回 fcfs,日志不提示**;命中短的请求可能饿死 |
| dfs-weight | 按树深度优先、子树里等待请求多的先走 | 同一子树的请求连续进批,前缀不易在中途被驱逐 | 同样受匹配成本约束 |
| hrrn | 等待量除以要算的新 token 数 | 防饿死,尾延迟 | 用处理过的 token 数当时钟,不看墙钟 |
| fcfs、lof、random | 不看缓存 | 无 | 关掉缓存时自动退回 fcfs |

还有一步批内查重:两条新请求共享前缀但树里还没有,按命中长度排序它们都是零,可能被放进同一批各算一遍。命中不超过 32 个 token 的请求,再到一棵只记 token 不记 KV 的模拟树里查等待队列内部的前缀;和排在前面的某条共享超过 32 个 token,就临时排到队尾,让前面那条先算,自己下一轮命中。**调度器主动让一条请求多等一轮,换整体少算一遍 prefill** 。

## Part 3|PD 分离与三层缓存下,前缀复用还成立吗

### 3.1 拆成两个实例之后,树也变成两棵

PD 分离(11 章)把 prefill 和 decode 放到不同节点。前缀缓存的地基是「KV 还躺在显存里」,现在 KV 在 P 算出来、传到 D 去用,两个节点各有自己的显存,也就各有自己的一棵树。P 的树和 D 的树互不知道对方有什么。

P 侧的树照常工作:分块 prefill 每块结束插入,请求发送完毕后释放并解锁。它服务的是 P 节点上后续请求的 prefill,和单机没有区别。

### 3.2 D 侧的前缀缓存默认是关的;开了才会「先匹配再收」

D 节点收 KV 之前可以先查自己的树:这条请求的前缀如果上一条对话已经传过来并留在 D 的显存里,就不用再传。实现上 D 收到请求先做一次匹配并加锁,匹配结果分两个长度:显存里已经有的,和显存加 host 加存储一共有的。后一个数通过 PD 协议告诉 P,**P 只从这个位置往后发 KV** ,前面的一个字节都不传;中间「host 有、显存还没有」的那段由三层缓存的拉回补上。

这个开关默认是关的。开了之后省的不是算力而是传输带宽和 D 侧的写入,代价是 D 侧要维护树、要为匹配加锁、要和 P 协商长度。启动参数的说明里写明它和 HiSparse、推测解码不兼容。

协商发生在 PD 的握手阶段:D 在 bootstrap 时就把「我已经有多长」交给 P,P 在握手完成后取出这个数,把发送起点设在这里,要传的页数按剩余 token 算。也就是说 P 在开始 prefill 之前就知道要少传多少,这不是传输中途的优化,是握手协议的一部分。

窗口模型上还有一刀:D 侧的命中会被截到滑动窗口起点之前,让最后一个窗口落在新传的那段里,代价是最后约一个窗口长度的全注意力 KV 不复用。

### 3.3 D 侧的抢占不重算,备份到 host;RL 场景例外

单机抢占是释放重算(03 章)。D 节点没有 prefill 能力,被踢的请求重算意味着回到 P 重新走一遍。所以 D 侧的抢占把 KV 备份到 host 再释放,恢复时拷回来;备份走的是统一树的接口,和三层缓存的 host 池是同一套。备份放不下时请求只能中止。

有一种情况备份反而不能用:RL 训练里权重会在服务运行中更新,被抢占时备份下来的 KV 是旧权重算的,恢复后接着用会让同一条序列的前后两段来自两套权重。所以有一条「真抢占」路径,被踢的请求不从备份恢复,而是等权重更新完成后回到原来的 P 节点按新权重重算前缀,再走一遍握手。源码注释明说这是为 RL 场景准备的。

### 3.4 三层缓存:一次匹配返回三段长度

显存放不下的前缀往 host 内存和分布式存储放(05 章)。树是这三层的共同索引:节点上除了显存槽号还记 host 槽号和按页的哈希,匹配结果因此带三段长度,显存命中、host 命中、存储命中。准入闸门按「显存命中加 host 命中」算这条请求要算多少新 token;进批前先发起从 host 拉回,拉回要么把承诺的 host 段全部拉回,要么一个都不拉,不允许拉一半。拉回落地后请求重新拿到停留节点,受保护长度随之更新。

对本章的意义是:**命中率的分母从「显存能放多少」变成「三层一共能放多少」** ,2.8 那条零和在显存层仍然成立,但被驱逐的 KV 不再是消失,而是降到下一层。代价是拉回的带宽和延迟,那是 05 章的账。

### 3.5 写透还是写回,决定驱逐时发生什么

三层缓存有两种写策略,默认写透。这直接改变了 2.6 那个「驱逐一个叶子」的含义:

| 叶子的状态 | 写透 | 写回 |
|---|---|---|
| host 已有副本 | 降级:显存槽释放,节点留在树上指向 host | 同左 |
| host 没有副本 | 直接删除,树上不再有它 | 先把 KV 备份到 host,备份完成再降级 |

写透在 KV 写进显存的同时就往 host 抄一份,所以驱逐时几乎总能降级;代价是每次写都占 PCIe 带宽。写回只在要丢的时候才抄,平时不占带宽,代价是驱逐变成一次异步的备份加降级,腾出空间要等备份完成。多轮对话为主的负载,写透让 2.5 最后一行「上一轮回答先被丢」从「丢了重算」变成「丢了拉回」。

### 3.6 存储层的预取:赶不上就当没命中

存储层(L3)不在拉回的同步路径上。本地匹配之后,没命中的部分去存储层查元数据,连续命中超过一个阈值(默认 256 个 token)才发起预取,把数据先搬到 host。预取什么时候停有三种策略:尽力而为,GPU 能开始 prefill 就停;等全部完成;超时,超时时间按「基础 2 秒加每 1024 个 token 0.1 秒」线性算,封顶 30 秒。停下时已经到 host 的那部分照常算命中,没到的按未命中重算。

超时的判定在流水线并行的第 0 段做,张量并行各 rank 取最大值,也就是任何一个 rank 认为超时就整体停。这是因为各 rank 的墙钟不一致,不能各自判。

### 3.7 其他子系统怎么碰到这棵树

| 子系统 | 交互 | 详见 |
|---|---|---|
| 多副本 / DP attention | 每个调度进程一棵树;DP 控制器有轮询、跟随 bootstrap、按请求数、按 token 数四种分发,没有一种看缓存,轮询会把相关请求打散 | 18 章的网关就是为这件事存在的 |
| 多模态 | 图片占位 token 由内容哈希生成,同图命中、异图分叉 | 14 章 |
| 推测解码 | EAGLE 下树的键是二元组,最后一个 token 不进树;D 侧开前缀缓存与推测解码不兼容 | 08 章 |
| 混合模型 | 统一树按组件存全注意力、窗口、Mamba 三种历史,一次匹配三种一起命中,驱逐按组件分别记短缺 | 03 章、5.10 |
| 窗口层的环形布局 | 某些布局把窗口层 KV 放在按请求的环里,不进树;匹配时硬性截掉尾部一个窗口,让这段重算把环填上 | 03 章 |
| 自定义位置嵌入 | 请求带位置覆盖时匹配直接给空序列,零命中 | 无 |

## Part 4|图解

### 4.1 三条请求进树

```text
  请求 A = [sys(2000) | q1(20)]        请求 B = [sys(2000) | q2(30)]        请求 C = [sys | q1 | ans1(100) | q3(25)]

  A 结束后:                B 结束后(在 sys 之后分叉):        C 结束后(顺着 A 的路往下长):

  root                     root                                root
   └─ [sys q1]              └─ [sys]                            └─ [sys]
      (2020 个槽)              ├─ [q1]                              ├─ [q1]
                               └─ [q2]                              │   └─ [ans1 q3]      <- C 命中 sys+q1,新算 125
                                                                    └─ [q2]

  B 到达时匹配 [sys q1] 命中 2000 个,不到整段,节点被劈成 [sys] 和 [q1];B 只算 q2 的 30 个。
  C 到达时走 root -> [sys] -> [q1],2019 个命中,最后 1 个留给本次前向。
  A 结束时其实插了两次:整段 [sys q1] 加补插 [sys],所以 B 到达前 [sys] 与 [q1] 就已经是两个节点。
```

### 4.2 一次准入里,锁与驱逐在什么位置

```text
  准入:匹配 -> 临时锁 -> 算预算(空闲 + 可驱逐 - 已承诺) -> 正式锁(到根的路径计数 +1)
                                     |
  分配:需要 n 个槽 -> 空闲够吗 --否--> 按策略弹可驱逐叶子,释放,父节点补位 --仍不够--> 踢在飞请求(不插树)
                                     |
  前向:读命中段 + 写新段(锁保证命中段还在)
                                     |
  每块结束:插入已算段 -> 重新匹配 -> 换锁
                                     |
  结束:整段插入 -> prompt 边界补插 -> 释放重复段 -> 解锁(计数 -1,路径回到可驱逐集合)
```

### 4.3 PD 分离下,D 侧先匹配再收

```text
  P 节点                                      D 节点
  ──────                                      ──────
                                              收到请求 -> 在 D 的树上匹配并加锁
                                                 显存命中 = l1,三层合计 = total
                                              把 total 告诉 P  ─────────────┐
  收到 total ────────────────────────────────────────────────────────────────┘
  prefill 全部 token(P 自己的树照常插入)
  只发送位置 [total, 末尾) 的 KV ──RDMA──>     [0, l1) 用显存里的
                                              [l1, total) 由 host / 存储拉回
                                              [total, 末尾) 收到后写入
                                              开始 decode;结束时插进 D 的树
  开关关闭时(默认):total = 0,P 发送全部 KV。
```

### 4.4 三层缓存下一次匹配返回什么

```text
  新请求 token:  [──────────── 4000 个 ────────────][ 新 token ]
  匹配结果:      [ 显存 2000 ][ host 1500 ][ 存储 400 ]  ...
                     ^ 直接用      ^ 进批前拉回   ^ 预取,赶不上就当没命中
  准入按 3500 算命中,要算的新 token = 总长 - 3500(减 1);
  拉回要么 1500 个全到,要么一个不到,不允许 800。
```

### 4.5 驱逐一个叶子,在三层缓存下是两种动作

```text
  写透(默认):                          写回:
  写 KV 到显存 ──同时──> 抄到 host        写 KV 到显存(host 没有)
        ...                                     ...
  驱逐叶子:释放显存槽                    驱逐叶子:先备份到 host(异步)
            节点留下,指向 host                     备份完成 -> 释放显存槽,节点指向 host
  下次命中:host 命中,拉回                下次命中:host 命中,拉回
  代价:每次写占 PCIe                      代价:腾空间要等备份
```

## Part 5|机制之外:源码里额外读到的

### 5.1 匹配会改树

劈开节点发生在匹配里,不只在插入里。一次只读的查询可能让树多一个节点。这是刻意的:让边界落在精确的位置,后面的匹配和插入都省事。代价是多卡上各 rank 的树必须一致,统一树的插入、驱逐接口上带一致性校验,比对各 rank 的参数和结果。

### 5.2 命中计数防自引用

分块 prefill 每块结束都插一次,如果每次都给路径上的节点加命中计数,一条长请求会把自己的前缀刷成「热门」。所以中间插入不加计数,结束时补插 prompt 那一刀也不加。lfu 和 slru 依赖这个计数,没有这条它们会系统性偏向长请求。

### 5.3 补插用更高的优先级

prompt 边界那次补插带的优先级比整段插入高一,路径取最大值,所以 prompt 段的优先级永远不低于输出段。在 priority 策略下这意味着输出段先走。

### 5.4 根是特殊的

根节点的键是空序列,引用计数初始为一,优先级是最小整数。前两条保证它永不被驱逐,第三条保证任何真实优先级都能覆盖它。

### 5.5 半页归请求

按页分配时,请求最后不满一页的那段不进树,但槽号在请求的行里。请求记一个受保护长度,表示这一行前多少是树的、后面是自己的;释放时只释放自己的那段。没有这个长度,要么漏释放,要么把树的槽号释放掉。分块 prefill 每插一次这个长度就更新一次。

### 5.6 强制未命中

有一个调试环境变量能让所有匹配返回零命中,用来测量「没有前缀缓存」的基线,不用重启改配置。

### 5.7 关掉前缀缓存之后不是没有树

关掉后换成一个只做分块的缓存:它只负责在分块 prefill 之间保住已算的部分,请求结束就全释放,没有跨请求的复用。缓存感知策略这时自动退回先来先服务。

### 5.8 批内查重那棵树的值是假的

批内查重用的模拟树不接内存池,插入时的值是一个同长度的布尔张量,只是为了让匹配能返回长度。它每轮准入前清空重建。

### 5.9 「结束时不插入」的开关没人用

树的构造参数里有一个「结束时不插入」的开关,基准上没有任何调用方设置它,实际不可用。

### 5.10 默认那棵树是统一树

仓库里有两棵树。最早的 RadixCache 是前面几个 Part 照着讲的算法,现在只剩批内查重时用它建模拟树。默认构造的是 UnifiedRadixCache,算法相同,但节点的值从一个槽号张量扩成按组件分的一组:全注意力层的 KV、滑动窗口层的 KV、Mamba 层的状态各是一个组件,一次匹配三种一起命中。每个组件维护一条自己的 LRU 链,驱逐沿链走,候选仍按 2.7 的策略打分;链上加一个分界,session 引用过的节点在前、没引用的在后。

### 5.11 树核可换,默认 Python

统一树把「树的算法」和「缓存的策略」分开:匹配、插入、劈开、驱逐叶子归树核,host 备份、存储预取、session 引用归缓存。树核通过注册表选,默认 Python,环境变量可切到 Rust 实现,支持全注意力、窗口、Mamba 的任意组合。另有实验性的 C++ 版不经过统一树。

### 5.12 session 感知:先丢没人认领的

长会话下一个会话的 KV 被别的会话挤掉,下一轮就要重算。开了 session 感知后请求带会话号,结束时它留下的叶子按会话号登记引用,驱逐先丢没有引用的。引用是软保护:没引用的丢完还不够,有引用的照丢。关闭会话只去掉引用,KV 回到普通顺序。

### 5.13 树之上还挂了什么

节点上有一串按页的哈希,是 host 内存和分布式存储的键(05 章);树的插入和删除会发出事件,发布给路由网关维护近似的树(18 章)。都不改变本章讲的树。

### 5.14 哈希是惰性算的

节点插入时不算页哈希,注释写「Hash will be computed lazily during event emission」:只有发 KV 事件或要往 host、存储写的时候才算,劈开节点时已算的哈希按页切分给两半。没开三层缓存也没开事件发布的部署,树上从来没有哈希。

### 5.15 legacy 树的节点也带 host 字段

最早那棵 RadixCache 的节点上就有 host 槽号、host 引用计数和「写透待确认」标记,不是统一树才有。三层缓存最初就是在它上面长出来的,统一树把这些字段按组件拆开而已。

### 5.16 预取的超时不是各 rank 自己判

存储预取要不要停,流水线第 0 段算超时,张量并行各 rank 对结果取最大,再沿流水线广播。注释解释:各 rank 墙钟不同,各自判会分叉,而分叉的后果是各 rank 对同一请求算出不同的命中长度。

## Part 6|对比与收益账

### 6.1 和 vLLM 的块哈希比

| 维度 | vLLM 块哈希 | SGLang radix 树 |
|---|---|---|
| 找前缀 | 逐块算哈希、查表,哈希把前一块卷进来保证前缀相同 | 从根往下走,树的形状保证前缀相同 |
| 命中粒度 | 整块(默认 16) | 单 token;后端要求整页时退化到 32 或 64 |
| 分叉处 | 半块要复制或丢弃 | 劈开节点,不动 KV |
| 地址表 | 块数级 | 并发乘上下文,GB 级 |
| 跨进程 | 哈希可复现 | 树只在进程内,跨实例靠网关近似树 |
| 与调度器 | 调度器不看缓存 | 默认按命中长度排队,还做批内查重 |
| 驱逐单位 | 块 | 叶子节点 |
| PD 分离 | D 侧按块哈希查本地再问远端 | D 侧默认不查,开了才先匹配再收 |

两边的分歧是把复杂度放在哪:vLLM 放在哈希和块对齐上,换来小表和可复现的键;SGLang 放在树上,换来 token 级命中和调度器能利用的结构。当页被后端钉成 64 时,两边的命中粒度已经没有差别。

### 6.2 页对齐到底损失多少

页大小为 p 时,两条请求实际共享 L 个 token,命中的是 L 向下取整到 p 的倍数。损失的期望是 (p 减 1) 除以 2 个 token,再加上永远要算的那一个:

| 页大小 | 每次命中平均少算的 token | 2050 token 共享前缀的实际命中 |
|---|---|---|
| 1 | 0,加 1 个封顶 | 2049 |
| 16 | 7.5,加 1 | 2048 |
| 64 | 31.5,加 1 | 2048 |

绝对数很小。真正的损失不在这里,而在 2.5 第一行说的:页越大,「分叉处那半页」越经常出现,系统提示词和用户输入的边界几乎不会恰好落在 64 的倍数上。

### 6.3 命中率怎么传到 TTFT

设 prompt 长 L,命中比例 h,prefill 吞吐 R(token 每秒),首 token 的一次 decode 耗时 d,则

$$\text{TTFT} \approx \frac{L(1-h) + 1}{R} + d$$

加一是 1.8 那个永远要算的 token。算例:L 等于 5000,R 取 20000 token 每秒(假设值),d 取 20 毫秒。

| h | 要算的 token | TTFT |
|---|---|---|
| 0 | 5001 | 约 270 毫秒 |
| 0.5 | 2501 | 约 145 毫秒 |
| 0.9 | 501 | 约 45 毫秒 |
| 1 | 1 | 约 20 毫秒 |

命中率从 0 到 0.9 把 TTFT 砍掉 80%,从 0.9 到 1 的最后一段只剩下 d。所以**追求最后几个点的命中率不值,守住前 90% 才值** ,而前 90% 靠的是 2.5 和 2.8 那些别让它掉下来的事。

### 6.4 容量怎么传到命中率

树能留多少取决于显存里除去在飞请求之后还剩多少。设槽总数 N,在飞请求 n 条、平均长度 s,树的容量大约是 N 减 n 乘 s。lru 下一段前缀能否命中,取决于它两次被用之间树里流过了多少新 token,流过的少于容量就还在。一个可代入的估算:

| 场景 | 槽总数 | 在飞 | 树的容量 | 结果 |
|---|---|---|---|---|
| 8B 模型,H100,轻载 | 400000 | 50 条乘 4000 | 200000 | 系统提示词与最近几十轮对话都在 |
| 同上,满载 | 400000 | 100 条乘 4000 | 0 | 树里只剩被锁的路径,命中率靠批内共享 |
| 同上,开三层缓存 | 显存 400000,host 若干百万 | 100 条乘 4000 | 显存 0,host 全部 | 命中靠 host 拉回,TTFT 多一段拉回时间 |

数字是估算,不是实测。它说明的是 2.8 的结论:并发一满,显存层的树就空了,想要命中率只能往外扩。

### 6.5 三层缓存把容量往外扩,但拉回不是免费的

host 命中的那段要拉回显存才能用,拉回走 PCIe,带宽比显存低一个量级以上;存储命中的那段还要先预取到 host。所以三层缓存下 TTFT 的公式多一项拉回时间,它和「重算这段」的时间之间有个交叉点,短前缀重算更快、长前缀拉回更快。这笔账 05 章算。

### 6.6 为什么这里不需要写时复制

vLLM 的命中停在块边界,命中边界落进块内部时那一块要复制一份再往后写,否则会改坏别人的块(vLLM 04 章「命中边界落进块内部时,那一块为什么必须复制」)。SGLang 没有这一步:树的值是槽号,命中的槽号照抄进请求的行,新 token 分新槽,任何时候都不会往别人的槽里写。分叉处只劈树、不动 KV,也就没有复制。

代价换到了别处:page_size 大于 1 时半页不算命中(1.5),等于把「复制半块」换成了「放弃半页」。两边都在处理同一个问题,分叉点不落在对齐边界上,vLLM 选择复制保住命中,SGLang 选择放弃保住不写共享槽。

| disaggregation_decode_enable_radix_cache | 关 | PD 分离下 D 侧先匹配再收 | 多轮对话走 PD 分离时开;与 HiSparse、推测解码不兼容 |
| page_size | 1 | 命中向下取整到整页 | 别手调,后端会改;改了就是 2.5 第一行 |
| mem_fraction_static | 按显卡 | 显存余量 | 想要命中率就给树留余量,见 2.8 |
| 树核后端(环境变量) | python | 切 rust | 匹配成 CPU 瓶颈时试 |
| 批内查重阈值(环境变量) | 32 / 32 | 命中多短才查、批内共享多长才降级 | 设负一关掉 |

### 7.2 什么时候关

请求之间没有共享前缀的负载,比如离线跑随机采样的评测集,树只会增加每轮的匹配和插入开销,关掉更快。PD 分离的 D 侧默认就是关的,多轮对话负载才值得开。

### 7.3 怎么看命中率

每条请求的响应元信息里有 cached_tokens,是命中的 token 数,开了三层缓存还会细分命中落在哪一层。想知道「没有缓存会怎样」,用强制未命中的调试开关跑一遍对比。

### 7.4 常见误区

- 全命中的请求 TTFT 不是零,永远还要算一个 token。
- MLA 模型配主流后端时命中粒度是 64,不是 token。
- 不同 LoRA 的请求不共享前缀,哪怕 prompt 完全一样。
- 高并发下命中率低是准入优先的结果,不是缓存坏了;想要命中率就留显存余量或开三层缓存。
- 队列超过 128 时缓存感知排序自动关闭,日志不提示。
- 上一轮的回答比系统提示词先被驱逐,多轮负载显存紧张时先查这个。
- 被抢占的请求什么都不留,重算全部;只有 PD 分离的 D 侧例外。
- PD 分离下 D 侧的前缀缓存默认是关的,不开就是 P 每次全量传。
- 默认树核是 Python,Rust 不是默认。
