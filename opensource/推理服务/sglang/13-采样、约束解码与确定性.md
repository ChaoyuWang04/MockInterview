# SGLang 13|采样、约束解码与确定性

挑一个 token 的管线为什么要定序、约束为什么必须事前禁止而不是事后校验、批不变性为什么难,vLLM 解读的「采样机制」「结构化输出」「确定性推理与批不变性」三章已经讲透。这一页只说 SGLang 在这最后一层上的取舍:它的默认值全是照着「别让流水线停下来」调的,而这三件事各自要为这个取向补一个窟窿。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

前向交出来的是一张每行 15 万列上下的分数表,这一章管的是从这张表到一个 token 的最后一段路。它坐在每一步的最末端,这里每多一次 GPU 等 CPU,02 章费力搭起来的重叠就断一次。三种负载各有一种坏法,而且三种都不报错。

**混合负载下,一条请求能把整批拖慢。** 惩罚和偏置都不是「谁用谁付钱」:只要批里有一条请求用了,就为**整批所有行**建一张「批大小乘词表」的 float32 表,每一步读一遍。批 256、词表 15 万时,一张就是 150 MB 量级,而且每种惩罚各一张。

**带格式约束的负载,坏的是 TTFT 和调度器那一颗 CPU。** 把一段格式说明编译成对整个词表的自动机不便宜:10 毫秒起步,复杂的格式到秒级,源码给它留的耗时桶一路排到 240 秒。放进调度循环里编译,一个大格式会让所有在跑的请求跟着停。编完之后每一步还有一笔固定开销:给每个带约束的请求算出「现在允许哪些 token」,这是调度器进程里的 CPU 活,一行一个请求,并发越高越顶不住。真正常踩到这一层的其实不是手写 schema 的人,而是用工具调用的人——指定了必须调工具,服务会自己给这条请求编一份格式。

**要复现时,坏的是答案本身。** 同一条请求这次和 3 条拼在一起、下次和 300 条拼在一起,矩阵乘的加法顺序不同,分数在小数点后第 7 位不同,某一步的第一名和第二名一翻,后面整段发散。温度 0 也一样。对聊天服务这是偶尔答案不同,对 RL 训练这是推理侧算出的 logprob 和训练框架对不上。

## 二、解法:顺序写死,编译挪出循环,要复现就把前两件事的快退回去

**采样:一条写死的管线,外加三处「宁可多算也不同步」。** 顺序不给调用方选:先惩罚,再压格式掩码,再加偏置,再跑调用方自带的处理器,然后除温度、归一化、裁掉候选集、抽一个。两处相邻关系决定语义——惩罚在温度之前,所以惩罚的力度不随温度缩放;偏置在掩码之后,而负无穷加上任何有限的数还是负无穷,所以偏置救不回被格式掐掉的 token。为了不在这一步停下来,它做了三件看着绕的事:整批都是贪心时直接取最大,归一化和裁剪整段跳过;惩罚要用的那几张表在上一步处理结果时就累加好了;不带种子时,抽样默认走「加一层噪声再取最大」的技巧而不是标准的多项式抽样,因为后者要在 CPU 侧记一笔随机数偏移、还要校验一次分布合法性,两样都卡在解码的关键路径上。多卡之间也不对答案,每步省一次 all-reduce,赌的是这几个算子本身确定。

**约束解码:编译在环外,环里只剩填表和压掩码。** 编译丢进线程池,带约束的请求先进一条**独立的文法队列**,编译完了才进等待队列;同一串约束第二次来直接用缓存,编译失败的结果也缓存,同样的坏格式下次立刻被拒。环里每一步走四站,下图是这两个尺度的分工:

![一条带约束的请求的两个时间尺度:左边虚线框里是只发生一次的编译,请求到达后先进独立的文法队列,线程池在后台把格式说明编译成对整个词表的自动机,编译期间调度器每轮要花掉最多 5 毫秒去轮询这条队列,编完进缓存再转入等待队列;右边实线的闭环是每一步都要走一遍的四站,黄色的两站在调度器进程的 CPU 上——按行填一张位掩码(每 32 个 token 压成一位),以及把新出的 token 回喂给状态机让它前进一格,绿色的一站在 GPU 上——把位掩码拷过去之后由一个 kernel 就地把不允许的位置写成负无穷,然后采样出一个 token。环上标着每步只出一个 token,「一次跳过一段固定字符」的三个接口方法在代码里但调度器没有调用点](/opensource/sglang/13a-grammar-two-clocks.svg)

带思考段的模型另有一层壳:识别出这条请求会先思考,就把收紧推迟到思考结束序列出现之后。还有一条少见的态度——格式说明里那些文法库编不进去的条款,它宁可当场把整条请求拒掉,也不静默地当作没写。

**确定性:把前面那些「快」一条条收回来。** 一个开关,连着四件事:在框架的分发层整体替换 7 个算子,让加法顺序只看形状不看批里有几行;把通信定住(树形归约、通道数钉死、关掉自写和对称内存的那两条快路,见 09 章);注意力按后端分两招,一类把切段数钉成 1,一类改成按固定长度切段——段数跟着序列长度走,但段的边界不跟着邻居走(后端本身是 06 章的主场);抽样改成由种子和位置算出来的噪声,和这条请求在批里排第几无关。设了 RL 的对齐目标,这个开关自动打开。

## 三、代价

- **惩罚与偏置是整批的账**,不是单条的账,而且是「批大小乘词表」这个量级。要控成本只能在入口把用惩罚的请求分流。
- **掩码是调度器进程的 CPU 活,而且是逐行填的。** 三个文法库里只有一个自带原生的并行填,另外两个就是一个 Python 循环。每步还现分配一块锁页内存装位掩码——留了复用缓冲的接口,但没有一处调用它。
- **编译期间,慢的不止那一条请求。** 文法队列非空时,调度器每一轮都要在轮询上花掉最多 5 毫秒;轮满 10000 次判编译超时,那条请求被判失败。
- **文法缓存没有上限,也没有淘汰。** 键是那串约束字符串本身,进去就一直在,只有清缓存接口能清,而且要服务完全空闲。
- **多卡默认不对答案,分叉就是挂死。** 某一步各卡采出不同的 token,后面形状对不上,整组停住,没有超时也没有日志。
- **确定性连带改掉一串**:融合的采样 kernel 换成 PyTorch 原生的、通信融合关掉、两个注意力后端下的前缀缓存关掉。还有一件更硬的:那种按最大概率比例裁候选的过滤在这条路上是**撞断言**,不是被忽略——源码注释说带种子时它给的结果是错的。批不变的算子比厂商库慢,文档没给比例。
- **这一层几乎没有监控。** 编译耗时、缓存命中、超时计数这一组指标在代码里定义得整整齐齐,但没有任何一处调用它们;真正在报的只有文法队列长度一个。

## 四、和 vLLM 不一样的八处

![同一张分数表,两边的加工顺序:上下两条管线各按自己的真实顺序排格子,五件双方都必须做的事(惩罚、除温度、归一化、裁候选集、抽一个)用同一种填色,虚线把两边的同名格连起来,连线的斜度就是错位。vLLM 那条是划掉不该选的、惩罚、除温度、在分数空间裁候选集、归一化、抽一个,logprob 的快照取在整条管线开始之前;SGLang 那条是惩罚、格式掩码、偏置、调用方自带的处理器、除温度、归一化、在概率空间裁候选集并重新归一化、抽一个,logprob 默认取归一化之后那一份。两条管线上「划掉不该选的」那一格错开了 3 格,一条长虚线把它们连起来。图上不写参数名,两边的参数名都在第五节;vLLM 的掩码与偏置走的是另一套按注册顺序应用的处理器链,这张图不摆它们的位置](/opensource/sglang/13b-vllm-diff-pipeline.svg)

1. **裁候选集在哪个空间。** vLLM 在分数空间裁——把淘汰的位置写成负无穷,再归一化一次,被淘汰的项天然不进分母。SGLang 反过来:先归一化,再在概率空间把淘汰的项置零并重新归一化。所以两边的「先后关系」在这一格上是镜像的。
2. **「划掉不该选的」这一格在哪、谁提供。** vLLM 有一对请求参数(白名单与禁词)排在整条管线最前面。SGLang 根本没有这对请求参数,等价物是一个内置的处理器,要服务显式开一个开关才能用,而且排在掩码和偏置**之后**——它能把负无穷覆盖回去,而覆盖回去之后状态机不认这个 token,整条请求以「不被接受」结束。
3. **logprob 默认是哪一份分数算的。** vLLM 在任何加工开始之前就拍一张快照,默认返回的是原始分数。SGLang 默认返回的是除温度、归一化之后那一份;要加工前的那份,只有一个服务级环境变量,而且全服务只能选一种。对 RL 这一条最要命:两边同一个字段的含义不一样。
4. **掩码谁来填、怎么搬。** vLLM 在并发上限够高时把填掩码切开丢线程池并行填,GPU 上那块掩码缓冲开服时就分配好、每步只覆盖前几行、走专用拷贝流。SGLang 是调度器进程里一个循环逐行填,每步现分配一块锁页内存再非阻塞拷过去,只有第三个文法库因为自带原生并行填才跳出这个循环。
5. **带约束的请求在哪等、等多久。** vLLM 把它放进跳过队列,每步用 100 微秒的超时去取一次编译结果,不参与常规的等待队列扫描。SGLang 给它一条独立的文法队列,每轮最多轮询 5 毫秒、轮满 10000 次判失败;多卡下还要对一次账——就绪取各卡的交集、失败取并集,再沿流水线逐级传给后面的 rank。
6. **非法的格式在哪被挡下。** vLLM 在对外那个进程里就试编译一次,非法 schema 是同步的 4xx,一点 GPU 都不花。SGLang 的编译在调度器的线程池里,失败的请求走的是「生成失败」那条路,客户端拿到的是一条正常响应里的错误。作为交换,它多了一层 vLLM 没有的静态检查:编译之前先走一遍 schema,把当前文法库无法编码的条款挑出来直接报错——默认那个库上是 11 个关键字,加上「字符串格式只认 14 种,其余一律拒」和「格式、正则、长度限制这三类不许同时出现两类」,另一个库的名单更长。
7. **后端的数量与回退。** vLLM 默认是自动挡,带一条会回退的选择链,一共四个库。SGLang 默认就是那一个库,不回退:显式指定的用不了就报错,只有分词器不被支持这一种情况会整体退化成「不支持约束」并打一行警告。它另外留了一个注册表,允许外部塞进自己的文法后端与采样后端。
8. **批不变怎么做到。** vLLM 是替换算子,再在几处热点代码里插开关判断,注意力一律把切段数钉成 1。SGLang 在分发层一次性替换 7 个算子、不在业务代码里插判断,注意力那边两招并用——一类钉成 1,一类改成按固定长度切段。代价的分布也不同:SGLang 这边有两个后端在确定性下要关掉前缀缓存,而其中一个正是 Blackwell 上不指定后端时的默认值。

## 五、调参与观测

**参数在哪调。** 采样和约束的参数几乎都在请求里:原生接口放在 `sampling_params`,OpenAI 兼容接口放在标准字段或 `extra_body`,每条请求各自一套,不用重启。服务级的是文法后端、采样后端、确定性开关、思考解析器,都是启动参数,改了要重启;`/set_internal_state` 只认 5 个与本章无关的字段,运行时改不了这里的任何一项。剩下的是一组环境变量,全在进程启动时读一次。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `temperature` / `top_k` / `top_p` / `min_p` · 分布多尖、候选留多少 | 请求 | 1.0 / 全词表 / 1.0 / 0;OpenAI 路由先读模型自带的生成配置 | 温度低于 1e-6 当成贪心(温度改回 1、候选只留 1 个);整批都贪心才走快路,混进一条随机的整批掉回完整管线;确定性下带 `min_p` 的请求撞断言 | 混合批的 TPOT |
| `frequency_penalty` / `presence_penalty` / `repetition_penalty` · 说过的词扣多少分 | 请求 | 0 / 0 / 1.0,取值范围 [-2, 2] / [-2, 2] / (0, 2] | 力度不随温度变;批里有一条用了,这一种惩罚就为整批建一张批大小乘词表的表 | 重复率;开惩罚前后的 `gen throughput` |

| `--attention-backend` · 注意力用哪套 kernel | 启动 | 按显卡 | 确定性下只认 `ascend` / `fa3` / `fa4` / `flashinfer` / `intel_xpu` / `triton` 这 6 个(文档只写了 3 个);不指定时 Blackwell 上非 DeepSeek 选 `flashinfer`、DeepSeek 选 `triton`,Hopper 及更早选 `fa3`;`flashinfer` 与 `intel_xpu` 下前缀缓存被关,吸收式 MLA 模型在这两个后端上直接报错 | 日志 `radix cache is not compatible` |
| `--rl-on-policy-target` · logprob 对齐哪个训练框架 | 启动 | 空,唯一取值 `fsdp` | 设了自动开确定性、把多模态缓存设成 0、logprob 改走 `log_softmax`(注释说两条路在 1e-6 上就对不齐) | 训练侧 logprob 是否对齐 |
| `SYNC_TOKEN_IDS_ACROSS_TP` · 每步各卡对一次答案 | 环境变量 | 关 | 对答案的方式是取各卡里最小的那个 token id;带文法时本来就会对。**名字没有 `SGLANG_` 前缀**,带前缀的那个同名变量在代码里没有读者 | 挂死是否消失 |
| `SGLANG_RETURN_ORIGINAL_LOGPROB` · logprob 取温度前的值 | 环境变量 | 关 | 整个服务只能选一种 | logprob 的量级 |
| `SGLANG_OPT_USE_GUMBEL_SAMPLE` · 不带种子时用加噪取最大代替多项式抽样 | 环境变量 | 开 | 关掉退回标准多项式抽样,decode 关键路径上多一次 CPU 侧记账和一次分布校验 | decode 的 TPOT |
| `SGLANG_FLASHINFER_PREFILL_SPLIT_TILE_SIZE` / `SGLANG_FLASHINFER_DECODE_SPLIT_TILE_SIZE` / `SGLANG_TRITON_DECODE_SPLIT_TILE_SIZE` · 确定性下注意力按多长一段切 | 环境变量 | 4096 / 2048 / 256 | 只在确定性模式下读;`flashinfer` 那条还会把工作区拉到 2 GB 并在图里禁掉 KV 切分 | 显存占用 |
| `SGLANG_DETERMINISTIC_NCCL_NCHANNELS` · 确定性下 NCCL 通道数 | 环境变量 | 8 | 上下限钉成同一个值,免得归约树跟着消息大小变 | — |
| `SGLANG_BATCH_INVARIANT_OPS_ENABLE_MM_DEEPGEMM` / `SGLANG_BATCH_INVARIANT_OPS_ENABLE_MM_FALLBACK_VARIANT` · BF16 矩阵乘走哪条 | 环境变量 | 开 / 关 | 前者让它走 DeepGEMM 的确定性算法,关掉退回常驻 Triton kernel;**后者一旦打开,形状不合时会退回非批不变的实现,确定性就不再成立** | — |

**怎么看。** 这一层没有专门的日志行,看的是三处。一是请求失败信息:`Tokens not accepted` 是有人在掩码之后改了分数,`Failed to compile … grammar` 是编译失败(带库自己的报错),`Grammar preprocessing timed out` 是轮满了,`is not supported by xgrammar: keyword(s) … would be ignored` 是静态检查拦下的 schema 关键字。二是指标:文法队列的长度有一个 `sglang:num_grammar_queue_reqs`,日志里的 `#queue-req` 只数等待队列、数不到它;编译耗时、缓存命中、超时那一组指标全都没有调用点,面板上永远是空的。三是确定性模式启动时打的每一行警告,它们逐条告诉你这次连带关掉了什么。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| 工具调用与 JSON 输出为主的在线服务 | `--constrained-json-disable-any-whitespace`;思考模型再加 `--reasoning-parser` | 用「JSON 里不许有随意空白」换更小的自动机和更短的编译;代价是模型不能在 JSON 里换行缩进。不设思考解析器的话,格式从第一个 token 就生效,思考段被掐死 |
| RL rollout,要和训练框架对齐 | `--rl-on-policy-target fsdp --attention-backend fa3`,每条 rollout 自己给 `sampling_seed` | 用批不变算子和钉死的通信换逐位可复现;显式给后端是为了保住前缀缓存,不给的话 Blackwell 上会落到关前缀缓存的那一个。种子不给就全是 42,n 条 rollout 会一模一样 |
| 高并发短请求,只用温度和 top-p | 什么都不加 | 默认就是这一档:整批贪心走快路、不建任何大表。别在这一档混进带惩罚或偏置的请求,那是整批的账 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 请求以 `Tokens not accepted` 失败 | 自定义处理器是不是在掩码之后改了分数 | 去掉它,改用格式本身表达;推测解码里的回滚见 08 章 |
| 带格式的第一条请求很慢,第二条正常 | 编译在文法队列里,`#queue-req` 看不出来 | 看 `sglang:num_grammar_queue_reqs`;轮询上限乘间隔至少是 50 秒,编译比这还久的 schema 才需要调它 |
| 某段时间每一轮都慢一点,和请求数对不上 | 文法队列非空时调度器每轮花掉最多 5 毫秒 | 别让大量新 schema 同时首次到达;客户端固定 schema 字符串 |
| 同一个 schema 每次都重新编译 | 缓存键是整串字符串 | 固定字段顺序与空白;Pydantic 每次生成的顺序可能不同 |
| 服务跑久了内存缓慢上涨,schema 种类很多 | 文法缓存没有上限也没有淘汰 | 空闲时调 `/flush_cache`,它会连着清 |
| 思考模型带格式一个字都出不来 | 有没有设思考解析器;请求是不是走了会标记思考模式的那条路由 | 设上;原生路由默认不标记思考模式 |
| 开惩罚后整批变慢 | 一条请求用惩罚,整批建大表 | 把用惩罚的请求分到别的实例 |
| 多卡挂死,没有任何日志 | 各卡采样分叉 | 开不带前缀的那个同步环境变量确认;带文法时本来就会同步 |
| 开了确定性还是不一致 | 注意力后端是不是那 6 个;有没有开那个「形状不合就退回非批不变实现」的变量 | 换后端;把那个变量关掉(带 `min_p` 的请求不会悄悄错,它直接撞断言) |
| 开了确定性后多轮对话变慢 | 日志 `radix cache is not compatible` | 换 `fa3`、`fa4` 或 `triton` |
| 确定性下 n 条采样全一样 | 没给种子 | 每条给不同的 `sampling_seed` |
| 两条路由行为不一致,同一个 prompt 结果不同 | 不写温度时,只有 OpenAI 路由读模型自带的生成配置 | 显式写全温度与 `top_p`,或改 `--sampling-defaults openai` |

## 六、常见误区

- **想用 `logit_bias` 给格式开后门。** 人们以为偏置和掩码都是「往分数上加东西」,顺序无所谓。掩码在偏置之前,负无穷加任何有限数还是负无穷。真能覆盖负无穷的是那条自定义处理器,可它覆盖完状态机不认这个 token,请求直接以 `Tokens not accepted` 结束——所以那也不是后门,是把请求写死的办法。
- **以为 schema 里写的每一条都被强制执行。** 「输出保证符合给定约束」这句话太容易照单全收。实际上有一批条款文法库编不进去。SGLang 的选择是宁可拒绝也不静默放过:默认库上 11 个关键字直接报错,字符串格式只认 14 种、其余一律拒,格式与正则与长度限制这三类也不许同时出现两类。所以从别处搬来、在别处跑得好好的 schema,在这里可能直接被拒,这不是 bug 是设计。
- **以为带格式的请求在等待队列里排着。** 排障第一反应是看日志里的队列长度,而它数的是等待队列。带格式的请求在一条独立的文法队列里,看不见;更要命的是这条队列非空时,调度器每一轮还要在轮询它上面花掉最多 5 毫秒——慢的不止那一条请求。
- **以为同一个 schema 一定命中缓存。** 缓存键是那串约束字符串本身,字段顺序变了、多一个空格,都是新键,再付一次编译。反过来这个缓存也没有上限、没有淘汰,schema 种类多的服务只能靠空闲时清缓存。
- **以为这一层有监控可看。** 代码里编译耗时、缓存命中、超时计数一应俱全,很容易顺手在面板上配一行。它们没有任何调用点,数字永远是 0;唯一真在报的是文法队列长度。
- **以为跳跃前填在生效。** 三个接口方法都在基类上摆着,名字也在术语里。调度器没有调用点,另一个库那条路连跳转表都写死成空。每一步仍然只出一个 token。
- **以为不写温度就是 1.0。** 走 OpenAI 兼容路由时,默认值先从模型自带的生成配置里取,原生路由不取。同一个模型、同一句话,两条路由拿到的默认温度可能不是一个值。
- **以为 `min_new_tokens` 是个无害的小开关。** 它把所有停止 token 压成负无穷,模型本该停的时候被迫从剩下的里面挑一个,分布本来就偏向停止时会出怪话;而且它也是一张批大小乘词表的表。
- **以为温度 0 就是确定的。** batch 组成一变分数就变,前缀命中与否也参与。要真确定得开那个开关。
- **以为确定性只是慢一点。** 它还换掉融合的采样 kernel、关掉通信融合,并且在两个注意力后端下关掉前缀缓存——其中一个正是 Blackwell 上不指定后端时的默认值,多轮对话会明显变慢,日志里只有一行警告。另外带 `min_p` 的请求在这条路上是直接撞断言,不是被忽略。
- **以为确定性模式下不给种子就是随机。** 不给统一是 42,温度 0.8 跑 100 次是同一个回答,`n` 条也一样。RL 里每条 rollout 要自己给不同的种子。
- **以为那个同步开关的名字带 `SGLANG_` 前缀。** 环境变量清单里确实有一个带前缀的同名项,但采样器读的是不带前缀的那个,带前缀的那个没有任何读者。设错了等于没设。
- **以为在 vLLM 上调好的采样参数搬过来效果一样。** 两边的加工顺序不同:裁候选集一个在分数空间一个在概率空间,格式掩码与偏置的位置也不同,而且 logprob 默认返回的不是同一份分数。带约束再加惩罚的组合要重新试。
