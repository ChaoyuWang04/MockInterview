# SGLang 13|采样、约束解码与确定性:三条线共用一张分数表

模型前向交出来的是一张每行 10 多万列的分数表,从这张表到吐出一个 token,中间要过一条加工管线。这一章讲三件互不依赖的事:管线里每一步改什么、为什么是这个顺序、错了动哪个指标;怎么在采样之前就把语法上不可能的 token 掐掉,以及这件事在高并发下的代价落在哪;为什么同样的输入换个 batch 会出不同的字,SGLang 把它按住之后又连带关掉了什么。三条线各自独立,只想读其中一条可以直接跳。

采样、拒绝采样、约束掩码与批不变性的数学原理,vLLM 解读的「采样机制」「结构化输出」「确定性推理与批不变性」三章已经讲透,本章只写 SGLang 自己的实现决策。全章内容都在源码上逐条核对过;每节对应源码的哪个文件与符号,见代码索引页;正文不写路径与行号。

## Part 1|原理:三条线,三个痛点,一张分数表

### 1.1 三个痛点

- **顺序即结果**。惩罚、温度、裁剪、掩码这几步,每一步都在改同一张分数表,先做哪个后做哪个,结果不一样。惩罚放在温度之后,惩罚的力度会随温度缩放;偏置放在掩码之前,偏置能把被禁的 token 救回来。管线的顺序不是实现细节,是语义。
- **自由生成再解析,随时会吐出非法 JSON**。要模型输出严格合法的结构,靠事后校验是赌运气,唯一可靠的办法是在每一步采样之前就把语法上不可能的 token 全部禁掉。代价是每步多一次掩码填充,以及每个新约束一次编译。
- **同样的 prompt、同样的种子,换个并发就换个答案**。GPU kernel 按 batch 大小改变归约的拆分方式,浮点加法不满足结合律,分数上 1e-7 量级的差异就能翻转一个 argmax。RL 训练要拿推理引擎的 logprob 和训练框架对齐,这条不按住就没法做 on-policy。

### 1.2 它动的指标

| 指标 | 三条线怎么动它 | 代价落在哪 |
|---|---|---|
| TPOT | 采样坐在每步的最末端,这里每多一次 GPU 到 CPU 的同步,整条流水线就停一次 | 全批贪心走 argmax 快路;惩罚张量提前算好;各 rank 默认不同步 |
| 吞吐 | 掩码填充和惩罚记账是 CPU 的活,并发上去后压在调度循环里 | 没人用惩罚就不建张量;掩码只给带文法的行填 |
| TTFT、尾延迟 | 带约束的请求先排文法队列,编译不完成不进等待队列 | 编译慢的 schema 拖长它自己的 TTFT;等待有上限,超过判失败 |
| 稳定性 | 各 rank 采样结果分叉会挂起整个 TP 组;掩码与文法状态不一致会抛错 | 有文法时自动同步;不接受的 token 直接报错不静默 |
| 可复现 | 批不变算子加带种子的 Gumbel-max,同一请求在任何 batch 里得同样的字 | 采样后端强制 PyTorch,注意力限 6 个后端,FlashInfer 下关前缀缓存 |

### 1.3 七种负载,各碰哪条线

| 负载 | 碰到什么 | 分叉点 | 最在乎 |
|---|---|---|---|
| 高并发混合批 | 贪心和随机、带惩罚和不带、带文法和不带,在一个批里 | 全批贪心走快路,否则全走管线 | TPOT |
| agent 工具调用 | JSON schema 或结构化标签约束,同一个 schema 反复用 | 编译缓存命中与否 | TTFT、稳定性 |
| 思考模型 | 思考段要自由,答案段要合法 | 思考结束序列出现的那一步 | 稳定性 |
| RL rollout | 同一 prompt 采 n 条,每条要能重跑出同样的 logprob | 种子;确定性模式自动开 | 可复现 |
| 推测解码 | 草稿 token 被拒后文法状态要回滚;带种子的裁剪路径有的不支持 | 验证失败的那一步 | 可复现、稳定性 |
| TP 多卡 | 每个 rank 各自采样,靠 kernel 确定性保持一致 | 有文法时改为同步 | 稳定性 |
| 流式多轮 | 停止串、停止正则、EOS 每步判一次 | 尾部窗口 | TPOT |

### 1.4 由此对三条线的要求

1. **管线顺序写死,并且每一步就地改分数表**,不改形状,不回 CPU。
2. **约束的编译不在每步的开销里**,编译好的文法按约束内容跨请求缓存,失败也缓存。
3. **确定性是一个开关带出一串改动**:换算子、限后端、改采样后端、改通信算法、关前缀缓存,用户只按一个开关,其余自动。

## Part 2|采样管线:顺序即语义,偏置救不回被掩的 token

### 2.1 分数表只取每个请求的最后一行

前向结束时每个请求只需要最后一个位置的分数。logits 处理器先从隐状态里把每个请求的最后一行挑出来,再过一次词表投影,得到的就是那张每行词表大小的分数表。prefill 时如果要返回输入 token 的 logprob,才会对更多位置做投影。这一步省掉的是整段 prompt 乘以词表大小的矩阵乘。

### 2.2 顺序固定,两处相邻关系换不得

分数表进入采样器后按这个顺序加工,每一步都是就地修改:

1. 自定义 logit 处理器(按请求传进来的),然后把非有限值清成安全值。
2. 惩罚:频率惩罚和存在惩罚是加法,重复惩罚是乘法,最小输出长度惩罚把 EOS 压成负无穷。
3. 文法掩码:不允许的 token 置负无穷。
4. logit 偏置:调用方指定的按 token 加分。
5. 除以温度。
6. softmax。
7. top-k、top-p、min-p 裁剪。
8. 抽一个。

两处顺序决定语义:**惩罚在温度之前,所以惩罚力度不随温度变;偏置在掩码之后,所以偏置救不回被掩掉的 token**,负无穷加任何数还是负无穷。想用偏置绕过 schema 的人会发现偏置像没生效,那不是 bug。

### 2.3 贪心是一个特例,不是一条分支

温度小于 1e-6 的请求在参数归一化时被改写成温度 1、top-k 等于 1,之后管线里没有「贪心」这个概念,只有「候选集只剩一个」。整批请求都是 top-k 等于 1 时走一条快路:直接对分数表取 argmax,不做 softmax 也不裁剪。混合批里贪心请求照常走完整管线,top-k 等于 1 的裁剪自然只剩最大的那个。这是 1.3 表里高并发混合批那一行:一个随机请求混进来,整批就从快路掉回管线。

### 2.4 两个采样后端,确定性模式只认一个

裁剪和抽样有两套实现,按配置选,装了 flashinfer 就默认它。flashinfer 后端把 top-k 和 top-p 融合成一个 kernel,不排序;min-p 走单独的路径,先做 top-k 和 top-p 的重归一化再按 min-p 抽。PyTorch 后端就是教科书做法:排序、累积和、把 top-k 之外和累积超过 top-p 的位置置零、再按 min-p 阈值置零、最后 multinomial。flashinfer 后端不支持带种子的抽样,确定性模式会把后端强制改成 PyTorch 并打一行警告。

### 2.5 惩罚的记账在 CPU 端提前做好

惩罚要知道每个请求到现在为止输出过哪些 token。每步采样之后,新 token 喂给惩罚器累积;下一步前向之前,惩罚器把累积结果变成两张与分数表同形状的张量,一张加法的、一张乘法的,前向后直接加上和乘上。零开销调度(02 章)下这两张张量在上一步就准备好了,采样时不需要等 CPU。没有任何请求用惩罚时,整个惩罚器不构造张量。

### 2.6 返回的 logprob 默认是温度之后的

默认返回的是温度之后、裁剪之前的 logprob。有环境变量可以改成返回温度之前的原始 logprob,默认关。确定性模式下 logprob 必须走 log_softmax 这个 kernel,而不是先 softmax 再取对数,注释说两者差在 1e-6 量级,足以破坏 prefill 与 decode 的 logprob 逐位对齐。

### 2.7 判停每步在尾部做一次,非法正则直接中止

采样出来的 token 交回调度器,调度器判这条请求是否结束:

- token 级:命中 EOS、调用方给的停止 token、tokenizer 附加的停止 token。忽略 EOS 的请求跳过这一条。
- 字符串级:调用方给的停止字符串,只在输出尾部一个窗口里找,窗口长度是最长停止串的长度。
- 正则级:调用方给的停止正则,每步在尾部跑一次搜索;正则本身非法的话请求直接中止,不是忽略。
- 长度级:到达最大输出长度。

停止串默认会从输出里裁掉,有开关可以保留。停止正则写成贪婪匹配会让每步的搜索变慢,这是流式负载里 TPOT 的一个隐蔽来源。

## Part 3|约束解码:编译排专门的队,每步只吐一个 token

### 3.1 四种约束,三个后端,后端是服务级的

请求可以带 JSON schema、正则、EBNF 文法或结构化标签四种约束之一。后端三个:xgrammar 默认,支持全部四种;outlines 支持 JSON 和正则;llguidance 支持前三种。后端是服务级的,一个服务只有一个,不支持的组合返回一个无效文法对象,请求中止。

### 3.2 编译是异步的,请求先排专门的队,失败也缓存

文法编译要把约束展开成对整个词表的自动机,10 毫秒到几秒。请求到达时先按(类型,约束字符串)查缓存;没命中就交给线程池编译,请求进一个文法队列等着,不进普通等待队列。每轮调度先看队列里谁编译完了,把它们挪进等待队列;编译失败的请求中止,并把失败结果也缓存起来,**同样的坏约束下次直接拒,不再编译**。等待轮数有上限,超过判失败而不是继续等。张量并行的各 rank 各自编译,准备好的集合取交集、失败的取并集,保证各 rank 对同一请求做同样的决定。

这是 1.3 表里 agent 那一行的兑现:同一个工具 schema 第一次来付编译,之后全走缓存;schema 拼错了只付一次。

### 3.3 每步一张位掩码,没填的行天然放行

采样前,批里每个带文法的请求各填一行掩码:让 matcher 按当前状态标出哪些 token 允许,打包成位图。整批的掩码一次搬到 GPU,一个 kernel 把不允许的位置置负无穷。批级掩码新分配时是「全部允许」的状态,只有带文法且未结束的请求才往里填,所以一个批里有的行受约束、有的行不受,一个 kernel 就能处理。掩码用完立刻从批信息里删掉,注释说否则会被延迟采样的闭包一直持有。

### 3.4 采样后推进状态,不接受就抛错

采样出的 token 送回调度器后,喂给该请求的 matcher 推进状态。matcher 不接受这个 token 时直接抛错,这是不该发生的:掩码已经保证它可选。真出现了,先查是不是有自定义处理器或偏置在掩码之后改了分数。推测解码下,被拒绝的草稿 token 要从 matcher 里回滚。matcher 走到终止状态后,后面的步不再填掩码。

### 3.5 思考模型:先放开,再收紧

带思考段的模型在思考时要自由生成,思考结束后才该受约束。一个包装器套在真正的文法对象外面:匹配到思考结束序列之前,填掩码时不施加约束;匹配到之后才把每个 token 转给内层文法。可以给思考段设最大长度,到了就只允许结束序列。

### 3.6 跳跃前填的接口还在,调度器没有调用点

文法对象的接口上有三个方法:能不能跳、跳过去的字符串和下一个状态、跳完之后重新分词并同步状态;outlines 后端还带一份压缩状态机的实现。但基准上调度器没有任何地方调用它们,也没有对应的启动参数。**约束解码目前每步只出一个 token**,schema 里那些固定的键名和引号也是一个一个 token 采出来的。

## Part 4|确定性:温度 0 不够,开了之后不带种子的请求永远同一个答案

### 4.1 温度为 0 也不能保证两次跑出同样的字

原因在 batch:同一个请求这次和 3 个请求拼在一起、下次和 300 个拼在一起,矩阵乘和归约的拆分方式不同,加法顺序不同,分数在 1e-7 那一位不同,某一步的 argmax 就翻了。前缀缓存也参与:命中了前缀的请求和没命中的请求,注意力的分块边界不一样。

### 4.2 换掉会随 batch 变的算子

开确定性模式后,运行时在启动时用 PyTorch 的算子注册机制,把矩阵乘、带偏置的矩阵乘、批矩阵乘、log_softmax、按维求均值、RMS 归一化这几个 aten 算子换成自己的实现:持久化的 Triton kernel,归约顺序只看张量形状,不看 batch 里有几行。这套实现来自 Thinking Machines 的批不变算子库。批矩阵乘还额外把 torch 的函数入口本身换掉,防止绕过注册。

### 4.3 注意力限 6 个后端,FlashInfer 下前缀缓存被自动关掉

注意力后端只能是 6 个之一:fa3、fa4、flashinfer、triton、ascend、intel_xpu。不指定时按显卡代选:Blackwell 上非 DeepSeek 模型选 flashinfer,DeepSeek 模型选 triton;Hopper 及更早选 fa3。指定了不在清单里的直接报错。共同点是 KV 分块大小可以钉死,不随序列长度自适应。

再往下一层:**只有 fa3、fa4、triton、ascend 四个后端在确定性下支持前缀缓存**。选了 flashinfer 或 intel_xpu,启动时自动把前缀缓存关掉并打一行警告。DeepSeek 这类吸收式 MLA 模型更严,后端不在这四个里直接报错。所以 Blackwell 上跑确定性模式不显式指定后端,会得到一个没有前缀缓存的服务,多轮负载的 TTFT 会明显变差,而日志里只有一行警告。

### 4.4 种子:默认 42,不带种子的 n 条采样是同一个答案

确定性模式下,采样不用 multinomial,而是 Gumbel-max:用种子、当前位置、词表下标三者做哈希得到均匀随机数,变成 Gumbel 噪声加到 logprob 上取 argmax。同一个请求在同一位置的随机数只由种子和位置决定,和它在 batch 里排第几无关。噪声全程 float64,注释明说用 float32 会数值不稳。

种子张量只在确定性模式下构造,请求不带种子时填 42。**所以确定性模式下,同一个 prompt、温度 0.8、不带种子,跑 100 次是同一个回答;一次请求里要 n 条,展开成 n 条请求时采样参数原样复制,n 条也是同一个回答。** 想从同一个 prompt 采多条不同但可复现的回答,必须给每条请求不同的种子。这条是给 RL 准备的:同一批 rollout 要能重跑出同样的 logprob。不开确定性模式时种子张量是空的,走普通 multinomial,那时才是「每次不一样」。

### 4.5 代价:慢,以及一串被连带关掉的东西

批不变 kernel 比厂商库慢,文档没有给出比例。开关带出的改动:采样后端强制 PyTorch;flashinfer 与 aiter 的 all-reduce 融合关掉;张量并行时 NCCL 改用树算法,自定义 all-reduce 与对称内存 all-reduce 关掉;flashinfer 与 intel_xpu 后端下前缀缓存关掉;PyTorch 后端的 min-p 裁剪遇到种子直接断言失败,所以确定性下 min-p 不可用。多模态模型还会把 VLM 的特征缓存关掉。这些没有一条需要用户手动做,也没有一条会在启动参数里显式出现。

## Part 5|三条线怎么打架:与 TP、推测解码、RL、零开销调度的交互

### 5.1 TP:各 rank 各自采样,默认不同步,有文法才同步

张量并行的每个 rank 都有一份完整的分数表,各自采样。默认不做 all-reduce 来统一结果,省一次通信,正确性依赖最后一次 all-reduce、词表投影、采样 kernel 都是确定性的。注释承认这在少数情况下不成立,rank 之间会分叉导致挂起;用了文法约束时分叉概率更高,所以有文法时自动同步。同步的方式是对 token id 取所有 rank 的最小值,**不是投票**:哪个 rank 采出了更小的 id,所有 rank 就用它。也可以用环境变量强制总是同步,默认关。确定性模式再往下走一层,把 NCCL 算法钉成树、关掉自定义 all-reduce,让通信本身也不随 token 数变。

### 5.2 推测解码:文法要回滚,带种子的裁剪路径有的不支持

草稿 token 被验证拒绝后,该请求的 matcher 要回滚相应步数,否则掩码状态和实际输出错位,下一步就会「不接受」。带种子的采样在 PyTorch 后端的排序路径上要先把裁剪后的概率取对数再做 Gumbel-max,注释说这里没有重归一化,min-p 分支因此直接拒绝种子。推测解码自己的采样在 08 章。

### 5.3 RL:设了 on-policy 目标,确定性就自动开

rl_on_policy_target 这个参数目前只有一个取值 fsdp。设了它,确定性推理自动打开,VLM 特征缓存关成 0,logprob 走 log_softmax 直接从温度后的 logits 算,让推理侧的 logprob 和训练框架逐位对齐。另有一条给 RL 用的路径:请求可以要求返回「这一步裁剪之后还剩哪些 token、各自权重多少、选中的那个权重多少」。实现上在裁剪的同时抓一份过滤后的概率,和主路径共享同一套阈值语义,注释把这条写成正确性不变量:融合采样 kernel 和单独的重归一化原语必须在截断、并列、联合支持集三件事上语义一致。

### 5.4 零开销调度:惩罚张量提前、掩码及时删、文法队列按轮询等

零开销调度让下一批的元数据在上一批前向时就准备好。惩罚器的两张张量在上一步就累积完(2.5);掩码用完立刻删,否则延迟采样的闭包会一直持有它(3.3);文法队列的等待按轮询计数,每轮最多等一个轮询间隔,注释算过实际等待时间是上限乘以轮询间隔与一步前向耗时中较大的那个。三处都是同一个动机:采样这一端不能让 GPU 等 CPU。

### 5.5 自定义处理器拿得到整个请求

调用方可以按请求指定一个处理器类和参数,处理器在管线第一步拿到整张分数表和每个请求的参数。内置的有两个:禁词处理器,把一组 token 置负无穷;思考预算处理器,数思考段已经出了多少 token,到预算就强制输出思考结束符。处理器拿得到请求对象本身,所以能看到完整的输入和输出历史。它排在惩罚和掩码之前,改出来的分数会被后面每一步继续加工。

| 子系统 | 它和三条线的关系 |
|---|---|
| 束搜索 | 不是采样器的分支;宽度 k 的请求跑成一个领队加 k 减 1 行裸行,裸行在采样前从分数表切掉,由束搜索按联合分数选 |
| 调度器(02 章) | 文法队列在调度器里,每轮先挪编译完的进等待队列;判停也在调度器 |
| 前缀缓存(04 章) | 确定性模式下 flashinfer 与 intel_xpu 后端关掉它 |
| 多模态(14 章) | on-policy 目标下 VLM 特征缓存关成 0 |
| Ascend NPU | 自己的采样 kernel,top-k 只接受 1 到 1024,超出整批退回通用实现;确定性模式不改它的采样后端 |

## Part 6|图解

### 6.1 从分数表到判停

```text
  前向 ──> 最后一行做词表投影 ──> [每请求一行分数]
                                        |
      自定义处理器 -> NaN 清洗 -> 惩罚(加法 / 乘法 / 压 EOS)
                                        |
                              文法掩码(不允许的置 -inf)
                                        |
                                   logit 偏置          <- 救不回上一步被掩的
                                        |
                          / 温度 -> softmax -> top-k / top-p / min-p
                                        |
               全批贪心:argmax     否则:multinomial 或 带种子 Gumbel-max
                                        |
                        有文法或强制同步:各 rank 取 MIN
                                        |
                              token 回到调度器
                                        |
        文法 matcher 推进 -> 惩罚器累积 -> 判停(token / 字符串 / 正则 / 长度)
```

### 6.2 一条带约束的请求的一生

```text
  请求到达(json_schema)
       │
       ├─ 查编译缓存 (类型, 约束串) ──命中──> 进等待队列
       │                                        ▲
       └─ 未命中 ──> 线程池编译 ──> 进文法队列 ──┤ 每轮调度轮询:编译完了就挪
                        │                       │ 等待计数 ≥ 上限 -> 判失败中止
                        └─ 编译失败 ──> 缓存失败结果,请求中止;同样的约束下次直接拒
       │
  每步:matcher 填一行位掩码 ──> 整批搬 GPU ──> kernel 置 -inf ──> 采样
       │
  token 回来 ──> matcher.accept ──不接受──> 抛错「Tokens not accepted」
       │                        └─ 推测解码被拒的草稿:rollback
       └─ 终止状态 ──> 后续步不再填掩码
```

### 6.3 一个开关带出的一串改动

```text
  --enable-deterministic-inference (或设了 rl_on_policy_target)
       │
       ├─ 算子:mm / addmm / bmm / log_softmax / mean / rms_norm 换成批不变 Triton kernel
       ├─ 采样后端:flashinfer -> pytorch(Ascend 除外)
       ├─ 种子张量:构造;不带种子的请求填 42
       ├─ 注意力后端:限 fa3 / fa4 / flashinfer / triton / ascend / intel_xpu
       │      └─ flashinfer / intel_xpu:disable_radix_cache = True
       ├─ 通信:关 allreduce 融合;TP>1 时 NCCL_ALGO=allreduce:tree,关自定义 all-reduce 与对称内存
       ├─ logprob:走 log_softmax kernel
       └─ on-policy 目标下:VLM 特征缓存 = 0
```

## Part 7|机制之外:源码里额外读到的

### 7.1 非有限值先清掉

进管线的第一件事是把分数表里的 NaN 和无穷清成安全值,否则 softmax 之后整行都是 NaN,multinomial 直接报错。

### 7.2 top-k 的哨兵,以及 NPU 的范围

「不裁剪」用一个 2 的 30 次方的常量表示,而不是负 1 或空值,这样 kernel 不需要特判,比较一律成立。NPU 后端的 kernel 只接受 1 到 1024 的 top-k,超出范围整批退回通用实现。

### 7.3 文法队列的等待有上限,而且不小

编译迟迟不完成的请求每轮等待计数加一,超过上限判失败中止。上限默认 10000 轮,轮询间隔默认 5 毫秒;每轮实际等的是间隔与一步前向耗时中较大的那个,所以上限至少 50 秒,decode 一步 20 毫秒时是 200 秒。真正会撞上它的是那些编译要几分钟的 schema。

### 7.4 各 rank 取最小值是为了省一次通信,不是为了公平

同步只在有文法或显式打开时做,而且做的是 all-reduce 取 MIN。理由是它比广播便宜,而且在各 rank 本来就一致的情况下结果不变。

### 7.5 Gumbel 噪声必须是 float64

带种子的抽样把哈希出来的均匀随机数变成 Gumbel 噪声再加到 logprob 上。注释明说这一步用 float32 会数值不稳,所以整条路径都是 float64,即使分数表本身是 bf16。

### 7.6 掩码用完就删

批级位掩码在采样之后立刻从批信息里置空。注释说否则延迟采样的闭包会一直持有它,1000–5000 个请求的掩码在 GPU 上堆着不放。

### 7.7 返回原始 logprob 是一个环境变量

默认返回温度之后的 logprob;要温度之前的,设环境变量。这不是请求级参数,整个服务只能选一种。

### 7.8 on-policy 目标连带关掉 VLM 缓存

设了 rl_on_policy_target,多模态模型的特征缓存被设成 0 MB。缓存的特征是上一次前向算出来的,和本次逐位对齐没有保证。

### 7.9 束搜索的裸行在采样前切掉

宽度为 k 的束搜索请求跑成一个领队请求加 k 减 1 行没有请求对象的裸行,裸行在分配前拼到批尾,在采样前从分数表里切掉,由束搜索自己按联合分数选。整组共享 KV 的槽由组统一释放。日志里的请求数不包含裸行。

### 7.10 采样支持集的正确性不变量

返回裁剪后支持集那条路径,在裁剪的同时抓一份过滤后的概率。注释把它写成不变量:融合的联合采样 kernel 和单独的重归一化原语必须在截断、并列、联合支持集三件事上语义一致,否则返回的权重和实际采样的分布对不上。

## Part 8|对比与收益账

### 8.1 和 vLLM 比

| 维度 | vLLM | SGLang |
|---|---|---|
| 管线顺序 | 白名单 → 偏移 → 禁词 → 惩罚 → 温度 → 裁剪 | 自定义处理器 → 惩罚 → 文法掩码 → 偏置 → 温度 → 裁剪 |
| 惩罚的记账 | 两套,一套回 CPU 一套不回 | 累积在 CPU 端,变成两张张量在前向前加乘 |
| 采样 kernel | 自写 top-k/top-p 融合 kernel,不排序 | flashinfer 融合 kernel 或 PyTorch 排序法,二选一 |
| 带种子抽样 | 先批量填再逐行覆盖 | 只在确定性模式下构造种子张量;种子加位置哈希的 Gumbel-max,默认种子 42 |
| TP 上的 token 一致 | 见 vLLM 采样机制章 | 默认不同步,有文法时取 MIN |
| 文法编译 | 线程池异步,请求进阻塞等待态 | 线程池异步,请求进独立的文法队列,各 rank 取交集,失败也缓存 |
| 跳跃前填 | 无 | 接口在,调度器未接线 |
| 批不变 | 换 kernel,注意力 split 钉 1 | 用算子注册机制换 aten 算子,注意力限 6 个后端,部分后端下关前缀缓存 |

### 8.2 管线的账:一步里省掉的同步

采样在每步末端,每一次 GPU 到 CPU 的同步都直接加在 TPOT 上。SGLang 在这一段省掉的同步有三处:全批贪心时不做 softmax 和裁剪,一次 argmax;惩罚的两张张量在上一步就准备好,前向后只做一次加和一次乘;各 rank 不做 all-reduce 统一 token。代价是三条对应的限制:批里混进一个随机请求就掉回管线;惩罚器在 CPU 上逐 token 累积;rank 分叉时挂起而不是报错。

### 8.3 文法的账:编译摊销,等待有上限

编译一次 10 毫秒到几秒,按(类型,约束串)缓存,同一个 schema 的第 2 到第 n 个请求一分钱不付;失败也缓存,坏 schema 只付一次。每步的固定开销是填一行位掩码加一次搬运,只有带文法的行付。等待上限是 10000 轮乘以 max(5 毫秒, 一步前向),至少 50 秒,超过判失败。所以 agent 负载里 TTFT 的分布是双峰的:缓存命中的请求和普通请求一样,第一次见到的 schema 多付一次编译。

### 8.4 确定性的账:关掉了什么

批不变 kernel 慢于厂商库,文档没给比例。可以数清楚的是关掉的东西:flashinfer 采样 kernel、all-reduce 融合、自定义 all-reduce、对称内存 all-reduce、min-p 裁剪、flashinfer 与 intel_xpu 后端下的前缀缓存、on-policy 目标下的 VLM 缓存。前缀缓存那一条在多轮负载上最贵:Blackwell 上不指定后端就会撞上它。

### 8.5 TP 同步的账:一次 all-reduce 对一次挂起

默认不同步省的是每步一次 all-reduce,一个 int32 向量,批 256 是 1 KB,通信本身不到 10 微秒,省的主要是一次 kernel 发射和一次流同步。付的是分叉后整个 TP 组挂起,没有超时,只能靠外部探活。有文法时分叉概率高到不值得省,所以自动同步;没文法时依赖 kernel 确定性,多数时候成立。

## Part 9|参数、开关与误区

### 9.1 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| temperature / top_k / top_p / min_p | 1.0 / 全词表 / 1.0 / 0 | 分布尖锐度与候选集 | 温度低于 1e-6 即贪心;确定性下 min_p 不可用 |
| frequency_penalty / presence_penalty / repetition_penalty | 0 / 0 / 1.0 | 加法、加法、乘法惩罚 | 重复严重先试 repetition 1.05 到 1.2 |
| min_new_tokens | 0 | 到达前压住 EOS | 防止秒答 |
| stop / stop_token_ids / stop_regex / no_stop_trim / ignore_eos | 空 | 判停 | 正则每步在尾部跑,别写贪婪匹配 |
| json_schema / regex / ebnf / structural_tag | 空 | 四选一的约束 | 提示词里同时说明格式,约束只保证合法不保证合理 |
| grammar_backend | xgrammar | 服务级文法后端 | 只在 xgrammar 不支持时换 |
| sampling_backend | 有 flashinfer 就 flashinfer | flashinfer 或 pytorch | 确定性模式自动改 pytorch |
| sampling_seed | 不填;确定性下填 42 | 带种子的可复现抽样 | 同 prompt 多回答时每条不同种子 |
| logit_bias | 空 | 按 token 加分 | 在掩码之后,救不回被掩的 token |
| custom_logit_processor | 空 | 按请求的处理器类与参数 | 思考预算用内置的 |
| enable_deterministic_inference | 关 | 换批不变算子、限注意力后端、强制 pytorch 采样、改通信 | RL 或复现问题时开,接受吞吐下降;Blackwell 上显式指定 fa4 或 triton 才能保住前缀缓存 |
| rl_on_policy_target | 空 | logprob 计算与训练框架对齐,并自动开确定性 | 只在做 on-policy RL 时设 |
| SGLANG_SYNC_TOKEN_IDS_ACROSS_TP | 关 | 每步各 rank 同步 token | 多卡挂起时开着排查 |
| SGLANG_GRAMMAR_MAX_POLL_ITERATIONS / POLL_INTERVAL | 10000 / 0.005 秒 | 文法队列等待上限 | 编译要几分钟的 schema 才需要调 |

### 9.2 排障先看什么

- 结构化输出报「Tokens not accepted」:掩码和 matcher 状态不一致,先查是否有自定义处理器或偏置在掩码之后改了分数,再查推测解码的回滚。
- 多卡挂起且请求带文法:先开强制同步 token 的环境变量确认是 rank 分叉。
- 开了确定性还是不一致:先查注意力后端是不是 6 个之一,再查采样后端,再查有没有请求带 min_p。
- 开了确定性后多轮 TTFT 变差:看启动日志有没有「radix cache is not compatible」,是的话换 fa3、fa4 或 triton。
- 确定性下 n 条采样全一样:没给种子,每条给不同的 sampling_seed。
- 约束请求迟迟不开始:看文法队列,编译慢的 schema 会在那里等,最长等 50 秒以上才判失败。

### 9.3 常见误区

- 温度为 0 不等于确定性,batch 组成才是主要变量;前缀命中与否也是。
- logit 偏置改不了被文法掩掉的 token。
- 跳跃前填在基准上不生效,约束解码每步一个 token。
- 各 rank 默认不同步采样结果,依赖 kernel 确定性;这是性能取舍,不是 bug。
- 确定性模式下不带种子不等于「随机」,而是所有请求共用种子 42。
- 确定性只按一个开关,但它连带关掉的东西不止一样,启动日志里的警告要逐行看。
- 束搜索的成员行不是请求,日志里的请求数不包含它们。
