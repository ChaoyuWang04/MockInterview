# SGLang 13|采样、约束解码与确定性

模型前向交出来的是一张每行 10 多万列的分数表,从这张表到吐出一个 token,中间要过一条加工管线。这一章讲三件互不依赖的事:管线里每一步改什么、为什么是这个顺序;怎么在采样之前就把语法上不可能的 token 掐掉;以及为什么同样的输入换个 batch 会出不同的字,SGLang 怎么把它按住。

三条痛点线各自独立,只想读其中一条可以直接跳。采样、拒绝采样、约束掩码与批不变性的数学原理,vLLM 解读的「采样机制」「结构化输出」「确定性推理与批不变性」三章已经讲透,本章只回指,主体写 SGLang 自己的实现决策。全章内容都在源码上逐条核对过;每节对应源码的哪个文件与符号,见代码索引页。

## Part 1|原理:三条痛点,三处回指

### 1.1 三条痛点

- **顺序即结果**。惩罚、温度、裁剪、掩码这几步,每一步都在改同一张分数表,先做哪个后做哪个,结果不一样。惩罚放在温度之后,惩罚的力度会随温度缩放;裁剪放在温度之前,温度就改不了候选集。管线的顺序不是实现细节,是语义。
- **自由生成再解析,随时会吐出非法 JSON**。要模型输出严格合法的结构,靠事后校验是赌运气,唯一可靠的办法是在每一步采样之前就把语法上不可能的 token 全部禁掉。
- **同样的 prompt、同样的种子,换个并发就换个答案**。GPU kernel 按 batch 大小改变归约的拆分方式,浮点加法不满足结合律,分数上 1e-7 量级的差异就能翻转一个 argmax。

## Part 2|采样管线:SGLang 的顺序

### 2.1 分数从哪来

前向结束时每个请求只需要最后一个位置的分数。logits 处理器先从隐状态里把每个请求的最后一行挑出来,再过一次词表投影,得到的就是那张每行词表大小的分数表。prefill 时如果要返回输入 token 的 logprob,才会对更多位置做投影。

### 2.2 固定顺序

分数表进入采样器后按这个顺序加工,每一步都是就地修改:

1. 自定义 logit 处理器(按请求传进来的),然后把非有限值清成安全值。
2. 惩罚:频率惩罚和存在惩罚是加法,重复惩罚是乘法,最小输出长度惩罚把 EOS 压成负无穷。
3. 文法掩码:不允许的 token 置负无穷。
4. logit 偏置:调用方指定的按 token 加分。
5. 除以温度。
6. softmax。
7. top-k、top-p、min-p 裁剪。
8. 抽一个。

有两处顺序值得记:惩罚在温度之前,所以惩罚力度不随温度变;偏置在掩码之后,所以偏置救不回被掩掉的 token,负无穷加任何数还是负无穷。

### 2.3 贪心是一个特例,不是一条分支

温度小于 1e-6 的请求在参数归一化时被改写成温度 1、top-k 等于 1,之后管线里没有「贪心」这个概念,只有「候选集只剩一个」。整批请求都是 top-k 等于 1 时走一条快路:直接对分数表取 argmax,不做 softmax 也不裁剪。混合批里贪心请求照常走完整管线,top-k 等于 1 的裁剪自然只剩最大的那个。

top-k 不填时不是「不裁」,而是一个很大的哨兵值,代表整个词表。

### 2.4 两个采样后端

裁剪和抽样有两套实现,按配置选。flashinfer 后端把 top-k 和 top-p 融合成一个 kernel,不排序;min-p 走单独的路径,先做 top-k 和 top-p 的重归一化再按 min-p 抽。PyTorch 后端就是教科书做法:排序、累积和、把 top-k 之外和累积超过 top-p 的位置置零、再按 min-p 阈值置零、最后 multinomial。flashinfer 后端不支持带种子的抽样,确定性模式会把后端强制改成 PyTorch。

### 2.5 惩罚的记账在 CPU 端提前做好

惩罚要知道每个请求到现在为止输出过哪些 token。每步采样之后,新 token 喂给惩罚器累积;下一步前向之前,惩罚器把累积结果变成两张与分数表同形状的张量,一张加法的、一张乘法的,前向后直接加上和乘上。零开销调度(02 章)下这两张张量在上一步就准备好了,采样时不需要等 CPU。没有任何请求用惩罚时,整个惩罚器不构造张量。

### 2.6 带种子的抽样

请求可以带一个采样种子,不带时用固定默认值。带种子的抽样不用 multinomial,而是 Gumbel-max:用种子、当前位置、词表下标三者做哈希得到均匀随机数,变成 Gumbel 噪声加到 logprob 上取 argmax。这样同一个请求在同一位置的随机数只由种子和位置决定,和它在 batch 里排第几无关。噪声全程 float64,注释明说这一步用 float32 会数值不稳。

### 2.7 各 rank 各自采样,默认不同步

张量并行的每个 rank 都有一份完整的分数表,各自采样。默认不做 all-reduce 来统一结果,省一次通信,正确性依赖最后一次 all-reduce、词表投影、采样 kernel 都是确定性的。注释承认这在少数情况下不成立,rank 之间会分叉导致挂起;用了文法约束时分叉概率更高,所以有文法时自动同步,取各 rank 结果的最小值。也可以用环境变量强制总是同步。

### 2.8 返回 logprob 时取哪个分数

默认返回的是温度之后、裁剪之前的 logprob。有环境变量可以改成返回温度之前的原始 logprob。确定性模式下 logprob 必须走 log_softmax 这个 kernel,而不是先 softmax 再取对数,注释说两者差在 1e-6 量级,足以破坏 prefill 与 decode 的 logprob 逐位对齐。

## Part 3|判停与逐请求的定制

### 3.1 四类停止条件

采样出来的 token 交回调度器,调度器判这条请求是否结束:

- token 级:命中 EOS、调用方给的停止 token、tokenizer 附加的停止 token。忽略 EOS 的请求跳过这一条。
- 字符串级:调用方给的停止字符串,只在输出尾部一个窗口里找,窗口长度是最长停止串的长度。
- 正则级:调用方给的停止正则,每步在尾部跑一次搜索;正则本身非法的话请求直接中止。
- 长度级:到达最大输出长度。

停止串默认会从输出里裁掉,有开关可以保留。

### 3.2 自定义 logit 处理器

调用方可以按请求指定一个处理器类和参数,处理器在管线第一步拿到整张分数表和每个请求的参数。内置的有两个:禁词处理器,把一组 token 置负无穷;思考预算处理器,数思考段已经出了多少 token,到预算就强制输出思考结束符。处理器拿得到请求对象本身,所以能看到完整的输入和输出历史。

## Part 4|约束解码:编译、掩码、推进

### 4.1 四种约束,三个后端

请求可以带 JSON schema、正则、EBNF 文法或结构化标签四种约束之一。后端三个:xgrammar 默认,支持全部四种;outlines 支持 JSON 和正则;llguidance 支持前三种。后端是服务级的,一个服务只有一个。

### 4.2 编译是异步的,请求先排一个专门的队

文法编译要把约束展开成对整个词表的自动机,10 毫秒到几秒。请求到达时先按(类型,约束字符串)查缓存;没命中就交给线程池编译,请求进一个文法队列等着,不进普通等待队列。每轮调度先看队列里谁编译完了,把它们挪进等待队列;编译失败的请求中止,并把失败结果也缓存起来,同样的坏约束下次直接拒。等待轮数有上限,超过判失败。张量并行的各 rank 各自编译,准备好的集合取交集、失败的取并集,保证各 rank 对同一请求做同样的决定。

### 4.3 每步一张位掩码

采样前,批里每个带文法的请求各填一行掩码:让 matcher 按当前状态标出哪些 token 允许,打包成位图。整批的掩码一次搬到 GPU,一个 kernel 把不允许的位置置负无穷。已经结束或文法已终止的请求那一行留空,不受约束。掩码用完立刻从批信息里删掉,注释说否则会被延迟采样的闭包一直持有。

### 4.4 采样后推进状态

采样出的 token 送回调度器后,喂给该请求的 matcher 推进状态。matcher 不接受这个 token 时直接抛错,这是不该发生的:掩码已经保证它可选。推测解码下,被拒绝的草稿 token 要从 matcher 里回滚。matcher 走到终止状态后,后面的步不再填掩码。

### 4.5 思考模型:先放开,再收紧

带思考段的模型在思考时要自由生成,思考结束后才该受约束。一个包装器套在真正的文法对象外面:匹配到思考结束序列之前,填掩码时不施加约束;匹配到之后才把每个 token 转给内层文法。可以给思考段设最大长度,到了就只允许结束序列。

### 4.6 跳跃前填的接口还在,调度器没有调用点

文法对象的接口上有三个方法:能不能跳、跳过去的字符串和下一个状态、跳完之后重新分词并同步状态;outlines 后端还带一份压缩状态机的实现。但基准上调度器没有任何地方调用它们,也没有对应的启动参数。约束解码目前每步只出一个 token。

## Part 5|确定性推理

### 5.1 痛点

温度为零也不能保证两次跑出同样的字。原因在 batch:同一个请求这次和三个请求拼在一起、下次和三百个拼在一起,矩阵乘和归约的拆分方式不同,加法顺序不同,分数在 1e-7 那一位不同,某一步的 argmax 就翻了。

### 5.2 换掉会随 batch 变的算子

开确定性模式后,运行时在启动时用 PyTorch 的算子注册机制,把矩阵乘、带偏置的矩阵乘、批矩阵乘、log_softmax、按维求均值、RMS 归一化这几个 aten 算子换成自己的实现:持久化的 Triton kernel,归约顺序只看张量形状,不看 batch 里有几行。这套实现来自 Thinking Machines 的批不变算子库。批矩阵乘还额外把 torch 的函数入口本身换掉,防止绕过注册。

注意力只有三个后端支持确定性:FlashInfer、FlashAttention 3、Triton。它们的共同点是 KV 分块大小可以钉死,不随序列长度自适应。

### 5.3 非贪心也确定

采样这一步的随机性用 2.6 的带种子 Gumbel-max 解决,随机数只由种子和位置决定。想从同一个 prompt 采多条不同但可复现的回答,给每条请求不同的种子。这条是给 RL 训练准备的:同一批 rollout 要能重跑出同样的 logprob。

### 5.4 代价

批不变 kernel 比厂商库慢;确定性模式下采样后端强制 PyTorch,通信融合被关掉,flashinfer 的采样 kernel 不能用。还有一个「on-policy 目标」参数,让 logprob 的计算路径和指定的训练框架对齐,用 log_softmax 的 kernel 直接从温度后的 logits 算,绕过 softmax 再取对数那条路。

## Part 6|图解

### 6.1 从分数表到判停

```text
  前向 ──> 最后一行做词表投影 ──> [每请求一行分数]
                                        |
      自定义处理器 -> NaN 清洗 -> 惩罚(加法 / 乘法 / 压 EOS)
                                        |
                              文法掩码(不允许的置 -inf)
                                        |
                                   logit 偏置
                                        |
                          / 温度 -> softmax -> top-k / top-p / min-p
                                        |
               全批贪心:argmax     否则:multinomial 或 带种子 Gumbel-max
                                        |
                              token 回到调度器
                                        |
        文法 matcher 推进 -> 惩罚器累积 -> 判停(token / 字符串 / 正则 / 长度)
```

## Part 7|机制之外:源码里额外读到的

### 7.1 非有限值先清掉

进管线的第一件事是把分数表里的 NaN 和无穷清成安全值,否则 softmax 之后整行都是 NaN,multinomial 直接报错。

### 7.2 top-k 的哨兵

「不裁剪」用一个 2 的 30 次方的常量表示,而不是负一或空值,这样 kernel 不需要特判,比较一律成立。NPU 后端的 kernel 只接受 1 到 1024 的 top-k,超出范围整批退回通用实现。

### 7.3 掩码行留白的语义

批级掩码新分配时是「全部允许」的状态,只有带文法且未结束的请求才往里填。所以一个批里有的行受约束、有的行不受,一个 kernel 就能处理。

### 7.4 束搜索是「一个领队加几行裸行」

束搜索不是采样器的分支,而是调度器侧的结构:宽度为 k 的请求跑成一个领队请求加 k 减一行没有请求对象的裸行,裸行在分配前拼到批尾,在采样前从分数表里切掉,由束搜索自己按联合分数选。整组共享 KV 的槽由组统一释放。

### 7.5 采样支持集也能返回

有一条给 RL 用的路径:请求可以要求返回「这一步裁剪之后还剩哪些 token、各自权重多少、选中的那个权重多少」。实现上在裁剪的同时抓一份过滤后的概率,和主路径共享同一套阈值语义,注释把这条写成正确性不变量。

### 7.6 文法队列的等待有上限

编译迟迟不完成的请求每轮等待计数加一,超过上限判失败中止,而不是无限等。上限和轮询间隔各是一个环境变量;注释算过实际等待时间是上限乘以轮询间隔与一步前向耗时中较大的那个。

## Part 8|对比与决策

### 8.1 和 vLLM 比

| 维度 | vLLM | SGLang |
|---|---|---|
| 管线顺序 | 白名单 → 偏移 → 禁词 → 惩罚 → 温度 → 裁剪 | 自定义处理器 → 惩罚 → 文法掩码 → 偏置 → 温度 → 裁剪 |
| 惩罚的记账 | 两套,一套回 CPU 一套不回 | 累积在 CPU 端,变成两张张量在前向前加乘 |
| 采样 kernel | 自写 top-k/top-p 融合 kernel,不排序 | flashinfer 融合 kernel 或 PyTorch 排序法,二选一 |
| 带种子抽样 | 先批量填再逐行覆盖 | 种子加位置哈希的 Gumbel-max,默认种子固定 |
| TP 上的 token 一致 | 见 vLLM 07 章 | 默认不同步,有文法时同步 |
| 文法编译 | 线程池异步,请求进阻塞等待态 | 线程池异步,请求进独立的文法队列,各 rank 取交集 |
| 跳跃前填 | 无 | 接口在,调度器未接线 |
| 批不变 | 换 kernel,注意力 split 钉 1 | 用算子注册机制换 aten 算子,注意力限三个后端 |

### 8.2 关键参数

| 参数 | 默认 | 作用 | 怎么调 |
|---|---|---|---|
| temperature / top_k / top_p / min_p | 1.0 / 全词表 / 1.0 / 0 | 分布尖锐度与候选集 | 温度低于 1e-6 即贪心 |
| frequency_penalty / presence_penalty / repetition_penalty | 0 / 0 / 1.0 | 加法、加法、乘法惩罚 | 重复严重先试 repetition 1.05 到 1.2 |
| min_new_tokens | 0 | 到达前压住 EOS | 防止秒答 |
| stop / stop_token_ids / stop_regex / no_stop_trim / ignore_eos | 空 | 判停 | 正则每步在尾部跑,别写贪婪匹配 |
| json_schema / regex / ebnf / structural_tag | 空 | 四选一的约束 | 提示词里同时说明格式,约束只保证合法不保证合理 |
| grammar_backend | xgrammar | 服务级文法后端 | 只在 xgrammar 不支持时换 |
| sampling_backend | 按平台 | flashinfer 或 pytorch | 确定性模式自动改 pytorch |
| sampling_seed | 不填即固定默认值 | 带种子的可复现抽样 | 同 prompt 多回答时每条不同种子 |
| logit_bias | 空 | 按 token 加分 | 在掩码之后,救不回被掩的 token |
| custom_logit_processor | 空 | 按请求的处理器类与参数 | 思考预算用内置的 |
| enable_deterministic_inference | 关 | 换批不变算子、钉注意力分块、强制 pytorch 采样 | RL 或复现问题时开,接受吞吐下降 |
| rl_on_policy_target | 空 | logprob 计算与训练框架对齐 | 只在做 on-policy RL 时设 |

### 8.3 排障先看什么

- 结构化输出报「Tokens not accepted」:掩码和 matcher 状态不一致,先查是否有自定义处理器或偏置在掩码之后改了分数,再查推测解码的回滚。
- 多卡挂起且请求带文法:先开强制同步 token 的环境变量确认是 rank 分叉。
- 开了确定性还是不一致:先查注意力后端是不是三个之一,再查采样后端。
- 约束请求迟迟不开始:看文法队列,编译慢的 schema 会在那里等。

### 8.4 常见误区

- 温度为零不等于确定性,batch 组成才是主要变量。
- logit 偏置改不了被文法掩掉的 token。
- 跳跃前填在基准上不生效,约束解码每步一个 token。
- 各 rank 默认不同步采样结果,依赖 kernel 确定性;这是性能取舍,不是 bug。
- 束搜索的成员行不是请求,日志里的请求数不包含它们。
