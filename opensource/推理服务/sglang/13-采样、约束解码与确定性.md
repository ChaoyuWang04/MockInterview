# SGLang 13|采样、约束解码与确定性

采样的数学、约束掩码的原理、批不变性为什么难,vLLM 解读的「采样机制」「结构化输出」「确定性推理与批不变性」三章已经讲透。这一页只说 SGLang 在这三件事上各自遇到的问题、它的解法、以及它和 vLLM 不一样的地方。三件事互不依赖。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、采样管线

**问题。** 前向交出一张每行 10 多万列的分数表,要从每一行里挑一个 token。挑之前要做惩罚、掩码、偏置、温度、裁剪几步,每一步都在改同一张表,顺序换了语义就变,而且不报错。这一步又在每步的最末端,这里多一次 GPU 等 CPU,整条流水线就停一次。

**解法。** 顺序写死在代码里,不给调用方选:自定义处理器、惩罚、文法掩码、偏置、温度、softmax、裁剪、抽一个。两处顺序决定语义:惩罚在温度之前,所以惩罚力度不随温度变;偏置在掩码之后,所以偏置救不回被掩掉的 token。为了不停流水线:整批都是贪心时一次 argmax,不做 softmax 也不裁剪;惩罚要用的两张张量在上一步就算好;多卡时各 rank 各自采样,默认不互相对答案,省一次通信。

## 二、约束解码

**问题。** 让模型自由生成再解析 JSON,解析失败是常事。另一个问题是文法要先编译成对整个词表的自动机,10 毫秒到几秒,放在调度循环里编译,一个大 schema 会让所有请求等它。

**解法。** 每步采样之前,用文法算出当前位置允许哪些 token,其余置负无穷,模型只能从合法的里面挑。编译交给线程池,带约束的请求先进一个专门的队列,编译完了才进等待队列;同一个 schema 第二次来直接用缓存,编译失败的也缓存,同样的坏 schema 下次直接拒。带思考段的模型思考时不加约束,思考结束后再收紧。每步只出一个 token,「跳过固定字符」的接口在代码里但调度器没接。

## 三、确定性

**问题。** 同一个请求这次和 3 个请求拼在一起、下次和 300 个拼在一起,GPU 里矩阵乘的加法顺序不同,分数在小数点后第 7 位不同,某一步选中的 token 就翻了。温度 0 也一样。对聊天服务这是偶尔答案不同,对 RL 训练这是推理侧的 logprob 和训练框架对不上。

**解法。** 一个开关。开了之后:矩阵乘、log_softmax、归一化这些算子换成「加法顺序只看形状、不看批里有几行」的版本;注意力只能用 6 个后端;抽样改用种子加位置算出来的噪声,和批里排第几无关;logprob 走一条和训练框架逐位对齐的路径。设了 RL 的 on-policy 目标,这个开关自动打开。

**要知道的三件事。** 这个开关连带关掉一串东西:flashinfer 的采样、通信融合、min-p 裁剪,以及在 flashinfer 后端下的前缀缓存,Blackwell 卡上不指定后端默认就是 flashinfer,多轮对话会明显变慢。不带种子的请求默认种子 42,所以温度 0.8 跑 100 次是同一个回答,要多条不同的回答每条给不同的种子。批不变的算子比厂商库慢,文档没给比例。

## 四、和 vLLM 不一样的四处

1. **管线里掩码的位置。** vLLM 把白名单和禁词放最前面,SGLang 把文法掩码放在惩罚之后、偏置之前。
2. **多卡要不要对答案。** vLLM 见它的采样章;SGLang 默认不对,靠 kernel 确定性,只在请求带文法时对一次,对的方式是取各卡里最小的那个 token id。
3. **带约束的请求排哪。** vLLM 进阻塞等待态,SGLang 进一个独立的文法队列,各卡编译结果取交集。
4. **确定性怎么换算子。** vLLM 换 kernel 并把注意力的 split 钉成 1;SGLang 用 PyTorch 的算子注册机制整体替换 aten 算子,注意力限 6 个后端,部分后端下关掉前缀缓存。

## 五、调参与观测

**参数在哪调。** 采样和约束的参数几乎都在请求里:原生接口放在 `sampling_params`,OpenAI 兼容接口放在标准字段或 `extra_body`,每条请求各自一套,不用重启。服务级的只有文法后端、采样后端、确定性开关、reasoning parser,是启动参数。三个内部阈值是环境变量。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `temperature` / `top_k` / `top_p` / `min_p` | 请求 | 1.0 / 全词表 / 1.0 / 0 | 温度低于 1e-6 就是贪心;整批贪心走快路,混进一条随机请求整批掉回完整管线;确定性下 min_p 不可用 | 混合批的 TPOT |
| `frequency_penalty` / `presence_penalty` / `repetition_penalty` | 请求 | 0 / 0 / 1.0 | 力度不随温度变;批里有一条用了惩罚整批就多两张 batch 乘词表的张量 | 重复率;开惩罚前后的 TPOT |
| `min_new_tokens` | 请求 | 0 | 到达前压住 EOS;分布本来就偏向停止时会出怪话 | 输出尾部 |
| `stop` / `stop_token_ids` / `stop_regex` / `no_stop_trim` / `ignore_eos` | 请求 | 空 | 停止正则每步在尾部跑,贪婪匹配拖慢每一步 | 流式输出的 TPOT |
| `json_schema` / `regex` / `ebnf` / `structural_tag` | 请求,四选一 | 空 | 第一次见的约束付一次编译(10 毫秒到几秒),之后走缓存;编译失败的也缓存 | 第一条请求的 TTFT 对第二条 |
| `logit_bias` | 请求 | 空 | 在掩码之后,救不回被 schema 掩掉的 token | 「Tokens not accepted」 |
| `custom_logit_processor` | 请求 | 空 | 要服务开 `--enable-custom-logit-processor`;思考预算用内置的 | 思考段长度 |
| `sampling_seed` | 请求 | 不填 | 只在确定性模式下起作用;不填统一是 42 | 同 prompt 多次的输出是否一样 |
| `n` | 请求 | 1 | 展开成 n 条请求;确定性下不给不同种子 n 条一样 | n 条输出是否一样 |
| `--grammar-backend` | 启动 | xgrammar | outlines 不支持 EBNF 和结构化标签;只在 xgrammar 不支持时换 | 请求被拒的信息 |
| `--reasoning-parser` | 启动 | 空 | 设了服务才知道思考结束序列,schema 才会放过思考段 | 思考模型带 schema 的输出 |
| `--sampling-backend` | 启动 | 有 flashinfer 就 flashinfer | 确定性模式自动改 pytorch | 启动日志的警告 |
| `--enable-deterministic-inference` | 启动 | 关 | 换算子、限注意力后端、强制 pytorch 采样、改通信;flashinfer 后端下关前缀缓存 | 启动日志的每一行警告 |
| `--attention-backend` | 启动 | 按显卡 | 确定性下 Blackwell 默认 flashinfer,前缀缓存被关;显式给 fa4 或 triton 保住 | 日志 `radix cache is not compatible` |
| `--rl-on-policy-target` | 启动 | 空 | 设 fsdp 自动开确定性并关 VLM 缓存 | 训练侧 logprob 是否对齐 |
| `SGLANG_SYNC_TOKEN_IDS_ACROSS_TP` | 环境变量 | 关 | 每步各卡同步 token;排查多卡挂死时开 | 挂死是否消失 |
| `SGLANG_GRAMMAR_MAX_POLL_ITERATIONS` / `POLL_INTERVAL` | 环境变量 | 10000 / 0.005 秒 | 文法队列等待上限,至少 50 秒;编译要几分钟的 schema 才动 | 约束请求判失败的时间 |
| `SGLANG_RETURN_ORIGINAL_LOGPROB` | 环境变量 | 关 | 返回温度之前的 logprob;整个服务只能选一种 | logprob 的量级 |

**怎么看。** 采样这一层没有专门的日志行,看的是结果:重复率、解析失败率、同 prompt 多次输出是否一致、`Decode batch` 行的 `gen throughput` 在开惩罚或文法前后的变化。约束请求排队在 `#queue-req` 里看不出来,它们在专门的文法队列里;编译慢的 schema 表现为那一条请求的 TTFT 长。确定性模式启动时打的每一行警告都要读,它们告诉你连带关掉了什么。

| 症状 | 先查 | 然后 |
|---|---|---|
| 「Tokens not accepted」 | 自定义处理器或 logit_bias 是否在掩码之后改了分数 | 推测解码的回滚 |
| 带 schema 的第一条请求很慢 | 编译在排队,之后走缓存 | schema 大到几分钟才需要调等待上限 |
| 同样的坏 schema 立刻被拒 | 失败结果缓存了 | 改 schema 内容才会重新编译 |
| 思考模型带 schema 一个字都出不来 | 没设 `--reasoning-parser`,schema 掐住了思考段 | 设上 |
| 多卡挂死没有日志 | rank 采样分叉 | 开同步环境变量确认;有文法时会自动同步 |
| 开了确定性还是不一致 | 注意力后端是否 6 个之一;是否有请求带 min_p | 换后端;去掉 min_p |
| 开了确定性后多轮 TTFT 变差 | 日志 `radix cache is not compatible` | 换 fa3、fa4 或 triton |
| 确定性下 n 条采样全一样 | 没给种子 | 每条给不同 `sampling_seed` |
| 开惩罚后整批变慢 | 一条请求用惩罚,整批建两张大张量 | 把用惩罚的请求分到别的实例 |

## 六、常见误区

- **用 logit_bias 给 schema 开后门。** 掩码在偏置之前,负无穷加任何数还是负无穷。要放开某个 token,改 schema。
- **schema 改了一个空格,以为会重新编译。** 会。缓存的键是约束字符串本身,任何改动都是新键,又付一次编译。反过来,同一个 schema 用 Pydantic 每次生成时字段顺序变了,也是新键。
- **第一条带 schema 的请求慢,以为服务卡住了。** 是编译在排队,它不在普通等待队列里,`#queue-req` 看不出来。第二条起走缓存。
- **思考模型不需要告诉服务。** 不设 reasoning parser,schema 从第一个 token 就生效,思考段被掐死,模型要么一个字出不来要么直接输出答案。
- **min_new_tokens 是无害的。** 它把 EOS 压成负无穷,模型本来该停的时候被迫从剩下的 token 里挑一个,分布本来就偏向停止时会出怪话。
- **温度 0 就是确定的。** batch 组成一变分数就变,前缀命中与否也参与。要确定性得开那个开关。
- **确定性只是慢一点。** 它还连带关掉 flashinfer 采样、通信融合、min_p,以及 flashinfer 后端下的前缀缓存。Blackwell 上不指定后端,默认就是 flashinfer,多轮对话会明显变慢,日志里只有一行警告。
- **确定性模式下不给种子就是随机。** 不给统一是 42,温度 0.8 跑 100 次同一个回答,n 条也一样。RL 里每条 rollout 要自己给不同种子。
- **多卡偶尔挂死是网络问题。** 各卡各自采样,某一步采出不同 token 后面形状对不上,整组挂死,没有超时。带文法时会自动同步;排查时开同步环境变量。
- **stop_regex 和 stop 一样便宜。** 正则每步在输出尾部跑一次,贪婪匹配把每一步都拖慢。
- **在 vLLM 上调好的采样参数搬过来效果一样。** 顺序不同:SGLang 的文法掩码在惩罚之后、偏置之前,白名单和禁词没有单独的位置。带约束加惩罚的组合要重新试。
