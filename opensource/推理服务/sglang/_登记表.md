## 二、一句话核心

sglang 和 vLLM 解决同一个问题(高吞吐低延迟地服务 LLM),但把力气花在三处 vLLM 没有的地方:**前缀缓存用 radix 树而不是块哈希,并让调度器按缓存命中排序;CPU 调度与 GPU 计算提前一批重叠(零开销调度);缓存往外分三层(HiCache),往上跨实例(网关的缓存感知路由)**。此外它是大规模 MoE 部署(PD 分离 + DeepEP + 双批重叠 + 专家负载均衡 + DP attention)的标杆实现。6 万 KB 源码里,推理运行时 3 万 KB,其中模型实现与算子层各占五分之一,KV 管理一成。

## 六、候选章推导过程中的判断

- 零开销调度没有独立成章,因为它的痛点(CPU 决策挡住 GPU)和调度器是同一条线;`event_loop_overlap` 与 `event_loop_normal` 并列在 `Scheduler` 里,`FutureMap` 是它的数据结构。放进 02 章作为下半部分
- HiCache 独立成章而不是像 vLLM 那样并入 KV 章,依据是体量(1100 KB,比 `radix_cache.py` 加 `unified_radix_cache.py` 还大)和主张背书(三篇设计文档)
- MoE 从并行章拆出,依据是 2025-05-05 博客把 PD + DeepEP + TBO + EPLB + DPA 当成一套系统讲,这套系统有自己的痛点(通信不规则、负载不均),和 TP / PP 的痛点(装不下)不同
- 采样、结构化输出、确定性合章,依据是三者体量合计 350 KB,各自撑不起一章,而痛点又能串成一条(从分数到 token 的最后一段路上,谁能改分数、谁能禁 token、谁保证同分数同结果)
- Model Gateway 成章,依据是它是 v0.4 三大特性之一,且 4 MB Rust 代码没有任何 vLLM 章能对应
- 01 章把 API 层收成一个 Part,与 vLLM 的四主题决议一致
- 低把握的 15、16 两章在成稿阶段先做「探路小批」再定 Part 结构
- **2026-09-18 用户复盘总览后定的写法(待成稿检验后再进守则)**:sglang 是独立项目,不以「与 vLLM 对比」开章或当主体;但共有原理不重讲,vLLM 是推理引擎的基石解读,原理回指它(回指只写章名与小节标题措辞,不写编号)。候选章按此分三类:**A 独立成文**(01、02、04、05、10、18,机制是 sglang 自己的,完整痛点线)、**B 原理同实现异**(03、06、07、08、09、11、12、14、15、16、17,原理段压成一个 Part 回指,主体写实现决策,「机制之外」与「对比与决策」加重,篇幅约为 vLLM 对应章的三分之一到一半)、**C 合并章**(13,写法同 B)。对比表集中在总览「阅读顺序」一节和各章尾段,不进正文主体
