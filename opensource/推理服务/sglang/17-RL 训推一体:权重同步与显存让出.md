# SGLang 17|RL 训推一体:权重同步与显存让出

训练和推理挤在同一批卡上这一层,参照项目 vLLM 的解读里没有对应的一章。这一页只说服务怎么把显存交出去再拿回来、怎么把训练刚算完的权重换进来、以及它和同类常见做法不一样的地方;权重第一次是怎么装进来的见 16 章,KV 池本身见 3 章,前缀树见 4 章,预录前向图见 7 章,训推之间的数值对不齐见 13 章。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

RL 一步分两段:推理引擎跑 rollout 生成样本,训练引擎拿这些样本算梯度、更新权重。两段共用同一批卡时,三个指标会坏。

- **显存峰值。** 推理引擎一起来就把权重、KV 池、预录前向的那块缓冲全买断了,训练那一段要么放不下,要么只能杀掉服务再起。
- **每步的空转时间。** 每训练一步都要给推理端换一次权重。杀掉重起等于重读一遍 checkpoint 再重抓一遍预录前向,大模型上 30–300 秒,这段时间 rollout 吞吐是 0;一轮训练跑上千步,时间全耗在这里。
- **正确性悄悄坏掉。** 前缀树里存的 KV 是旧权重算出来的,换了权重不清树,前缀命中率越高答错得越多,而且不报任何错;一条请求如果跨了换权重那一刻,前半截 token 是旧策略生成的、后半截是新策略的,拿去算梯度就不再是 on-policy。

## 二、解法:让服务睡觉,而不是杀掉它

最天然的直觉:训练要用卡的时候让推理进程把显存交出去,训练完再拿回来,进程本身一直活着。

SGLang 把自己占的显存分成三类各贴一个标签——KV 池、模型权重、预录前向的图缓冲。释放接口按标签把物理显存还给驱动,恢复接口按相反顺序拿回来。底下是一个第三方的显存让出库:它只把物理页还掉,虚拟地址留着不动,所以预录前向图里烤死的那些地址拿回显存后依然有效,不用重抓图。三类里只有前两类默认真的贴了标签;图缓冲那一类要另外打开一个开关才贴,不开的话释放它等于什么都没做。

![RL 一步里显存的让出与拿回:横轴是时间,三条带子分别是 KV 池、模型权重、预录前向的图缓冲,带子实心表示这块显存还在这个进程手里、空心表示已经还给驱动;让出的顺序是 KV 池、权重、图缓冲,拿回时严格反序,而进程本身自始至终没有退出;KV 那一类让出时顺带把前缀树清了,权重那一类让出前先把模型里算过一次的常量表另存到不带标签的显存里;图缓冲那条带子默认是灰的,表示不额外开开关它根本不会被让出;训练占卡那一段结束后要先拿回显存,再推一次新权重,服务才能继续接请求](/opensource/sglang/17a-one-rl-step-timeline.svg)

权重换进来有 4 条路,对应 4 种部署形态:

- **读盘。** 训练端把 checkpoint 存下来,推理端重读一遍。最简单,也是新副本扩容唯一能走的路;多副本时每个副本各读一份全量。
- **集合通信广播。** 训练端和推理端各占一批卡,双方另建一个进程组,训练端的 0 号 rank 把参数张量一个个广播给推理端的每个 rank。
- **显存句柄。** 训练进程和推理进程在同一台机器上,训练端把张量的进程间句柄传过来,搬的是指针不是数据;每个 rank 只解开属于自己的那一份,解别人的会把生产方的引用计数弄坏。
- **参数服务器握手。** 多机各读 checkpoint 的一部分,再按 GPU 的硬件 UUID 认领、互相分发。这条路由 checkpoint-engine 这个独立项目实现,SGLang 这边只提供它要求的那几个回调:我的卡叫什么、用哪个函数装权重、装完还要做什么。

![4 条权重通道各自把什么搬过了哪条线:每行一条通道,左边是训练端、右边是推理引擎,中间那条绿色的横条就是这一步真正过线的权重字节;读盘那条叠了三层,表示同一份权重被每个副本各读了一遍,广播那条是厚厚的一条表示全量过一次网,显存句柄那条细到只剩一根线因为传的是指针、字节一个都没动,参数服务器那条被切成四段表示每台机只搬自己读到的那一片再横向补齐,底下还有一根紫色细线是按卡的硬件 UUID 做的握手;最右边一列标出每条通道会不会顺带把草稿模型也换掉,广播那条是唯一不换的](/opensource/sglang/17b-four-weight-channels.svg)

4 条路的收尾是同一套:参数原地覆写,不重新分配显存;默认清空整棵前缀树;记下新的版本号,并给每条还在生成的请求记一笔「你是在这里换的权重」。

为什么实际不吃亏:权重是原地写进已经分配好的张量,显存布局不变,所以拿回显存后不需要重抓前向图;清树只是把树和分配器重置,不搬数据;让出权重之前引擎会把模型里那些算过一次就不再变的常量表(旋转位置编码表这类)另存一份到不带标签的显存里,拿回来再写回去,所以这部分不用重算。

## 三、代价

**让出显存要求服务完全空闲。** 接口不等、不排空,有请求在飞直接断言失败,得由调用方自己先暂停。而且空闲的定义比「没有在跑的请求」严得多:等待队列、PD 分离的几个队列、分层缓存在途的写回与预取、语法约束的排队,任何一样非空都不算空闲。

**让出权重之后什么都没留下。** 让出库只还物理页不存内容,拿回来的是一片未初始化的显存,必须紧接着推一次权重才能用。把权重备份到内存是启动时另开的选项,代价是内存里常驻一份完整权重。

**每次换权重默认清整棵树。** 上一轮 rollout 攒下的前缀命中全部作废,下一批请求要从头算 prefill。

**图缓冲那一类不是白给的。** 打开它之后,自定义 all-reduce 在图捕获期间不能再用注册过的共享缓冲区,只能走未注册的那条慢路;而分段捕获的那个图后端和显存让出直接不兼容,一起开启动就抛异常。

**广播通道一个张量一次集合通信。** 大模型的参数张量按千计,一次更新就是 500–2000 次广播;把一批张量拼成一条再广播,是要显式选的加载格式。

**只有主模型是 4 条路都换的。** 草稿模型跟不跟着换按通道而定,广播这条路全树就没有草稿侧的实现。

## 四、和同类常见做法不一样的地方

把推理引擎接进 RL,有一个很自然的做法:引擎提供一个「RL 模式」,把暂停、让显存、换权重、恢复打包成一次调用,训练框架喊一声,引擎自己走完一步。SGLang 明确不这么做,它的 RL 文档把这条写成一句口号:做库,不做框架。落到行为上有 5 处不一样。

1. **一步 RL 是调用方自己按顺序串起来的。** 暂停、让出、拿回、推权重、继续是几个互不相干的接口,谁先谁后由调用方决定,引擎不检查你有没有按顺序来——唯一的检查是释放接口会断言空闲。好处是能拆:只让出 KV 不让出权重、只改版本号不动权重、让出之后干脆不拿回而是让训练端接管这张卡,都是合法组合。代价是漏掉一步没人提醒你。
2. **换权重是一次调用一次做完,不是一个会话。** 4 条通道各有各的接口,一次调用从传输到收尾全做完,清树和记版本号打包在里面而且默认打开。最容易忘的那一步被做成了默认值,而不是留给调用方收尾。
3. **显存是按种类贴标签,不是按深度分档。** 常见做法是给睡眠定几个档位,档位越深交出去的东西越多。这里没有档位,三类显存各一个标签,要哪几类就报哪几类的名字,组合自由;但也因此没有一个「深睡」的按钮替你把该让的都让掉。
4. **让出权重默认不留副本。** 直觉上「让出再拿回」应该原样还给你,这里不是:RL 的下一步本来就要推一份新权重进来,存旧的那份纯属浪费内存。要留副本得启动时显式开。
5. **版本号能落到 token 上。** 版本号通常只有一个,表示引擎现在装的是哪一版。这里除了那个全局版本号,每条响应还会给出这条回答的输出 token 分成几段、每段各是哪个版本生成的,超过一段就说明这条样本不是纯 on-policy。「换权重会把一条在飞的请求切成两半」这件事被做成了可观测的字段,而不是留给调用方自己去猜。

此外训练端那一侧 SGLang 只给了一个无状态的函数:每个训练 rank 各自序列化自己那片分片,汇到推理端 0 号 rank 再转置成按张量组织的形状。引擎的生命周期始终握在调用方手里,这个函数自己不持有任何状态。

## 五、调参与观测

**参数在哪调。** 这一章几乎全是运行时接口。启动时只有 4 组旗标:`--enable-memory-saver` 决定能不能真的还显存;`--enable-weights-cpu-backup` 与 `--enable-draft-weights-cpu-backup` 决定让出权重时备不备份;`--weight-version` 是起始版本号;`--load-format dummy` 加 `--checkpoint-engine-wait-weights-before-ready` 让服务先用随机权重起来、等第一次 IPC 更新才就绪。`--weight-cache-mode` 必须是 `off`,否则所有让出与更新接口都拒绝。环境变量两个:`SGLANG_MEMORY_SAVER_CUDA_GRAPH` 决定 CUDA graph 那一类要不要贴标签,`SGLANG_WAIT_WEIGHTS_READY_TIMEOUT` 是等首次权重的秒数。运行时接口按 RL 一步的顺序:`/pause_generation` → `/release_memory_occupation` → 训练 → `/resume_memory_occupation` → 4 个 `/update_weights_from_*` 之一 → `/continue_generation`;`/init_weights_update_group` 只在用 NCCL 通道前调一次,`/update_weight_version` 只改版本号,`/weights_checker` 算校验和。多 DP 副本时 NCCL、张量、IPC 三条通道要求 `dp_size` 为 1 或开了 DP attention;磁盘通道和让出、拿回接口会扇出到每个副本,磁盘通道要求全部成功才算成功。

| 参数或接口 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--enable-memory-saver` · 让 KV 与权重两类显存能整体让出 | 启动 | 关 | 开:释放接口真的把物理显存还给驱动;库没装的话启动直接抛 ImportError。不开:退化成空适配器,只清树,显存一字节不动 | 释放前后 `nvidia-smi`;关着时日志里不会有任何提示 |
| `SGLANG_MEMORY_SAVER_CUDA_GRAPH` · 让 CUDA graph 的图缓冲也贴标签 | 环境变量 | 0 | 设 1:`cuda_graph` 标签才真的有东西可让;自定义 all-reduce 在捕获期改用未注册缓冲区,`--cuda-graph-backend-decode breakable` 会直接抛 NotImplementedError | 只放 `cuda_graph` 标签时 `nvidia-smi` 降不降 |
| `--enable-weights-cpu-backup` · 让出权重时先拷到内存 | 启动 | 关 | 开:拿回权重后不用立刻重推;内存多占一份完整权重,让出与拿回各多一次拷贝 | 拿回后不推权重直接 `/weights_checker`,校验和是否与训练端一致 |

| `/pause_generation` 的 `mode` · 在飞请求怎么处理 | 运行时 | `abort` | `abort` 全部打回客户端,在 HTTP 那一层循环打到锁松开为止;`retract` 退回等待队列、恢复后按新权重重算;`in_place` 原地停、KV 留着,之后清树会失败 | `Decode batch` 行 `#running-req` 归零 |

| `/resume_memory_occupation` 的 `tags` · 拿回哪几类 | 运行时 | 空 = 三类全拿回 | 顺序固定图缓冲 → 权重 → KV;拿回权重后不推权重就是一片垃圾 | 拿回后先跑一条固定 prompt 比对 |

| `/init_weights_update_group` + `/update_weights_from_distributed` · NCCL 组广播 | 运行时 | `backend=nccl`、`group_name=weight_update_group`、`flush_cache` 开 | 训练端 0 号 rank 广播,每个张量一次异步广播再统一等;`load_format=flattened_bucket` 把一批拼成一条只播一次 | 日志 `init custom process group:`;指标 `{source="distributed"}`;失败信息含 `partially updated` |

| 请求字段 `flush_cache` · 更新后清不清树 | 每次请求 | 开 | 关:旧 KV 配新权重;只该在连续多次推张量的中间那几次关,最后一次必须开 | 响应质量;`cached_tokens` 是否归零 |
| 请求字段 `torch_empty_cache` · 清树时顺带把分配器缓存还给驱动 | 每次请求 | 4 个更新接口关;`/continue_generation` 开 | 开:更新中临时张量多时省出余量;多一次同步 | 日志 `[continue_generation] torch.cuda.empty_cache() called: reserved … MB -> … MB` |
| `/update_weight_version` · 只改版本号 | 运行时 | `abort_all_requests` 开 | 默认先打掉在飞请求再改号;不动权重 | 日志 `Weight version changed. old_version= new_version= num_recorded=` |
| `/weights_checker` · 每个 rank 算权重校验和 | 运行时 | `action=checksum` | 含草稿模型(名字加 `draft.` 前缀);TP 各 rank 分别报,DP 各副本分别报 | 响应里每 rank 一条校验和记录 |

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| 训推同机同卡,单机 8 卡以内,自己写训练循环 | `--enable-memory-saver`,每步 `/pause_generation` → `/release_memory_occupation` → 训练 → `/resume_memory_occupation` → `/update_weights_from_tensor` → `/continue_generation` | 用「让出 KV 与权重 + 传句柄」换到几乎零拷贝的换权重;代价是训练与推理必须同机,而且这 6 步得调用方自己按顺序串,漏一步没人提醒 |
| 训推各占一批卡,跨机,权重走网 | `--enable-memory-saver` 不开(卡不共用),开服后调一次 `/init_weights_update_group`,每步走 `/update_weights_from_distributed` 并带 `load_format=flattened_bucket` | 用一条常驻的 NCCL 组换掉读盘;代价是训练端要自己保证张量名、dtype、shape 与推理端逐一对得上,错一个整批作废,而且草稿模型不跟着换 |
| 多机大模型,要秒级换权重、也要秒级扩副本 | `--load-format dummy --checkpoint-engine-wait-weights-before-ready --weight-version v0`,权重走 `/update_weights_from_ipc` | 用「各机只读 checkpoint 的一部分再横向补齐」换启动与换权重的时间;代价是多一个独立组件要部署、要装额外依赖,并且 GPU UUID 一旦对不上直接失败 |

**怎么看。** 版本号看三处:`/model_info` 的 `weight_version` 是当前生效的;每条响应 `meta_info.weight_version` 在这条请求结束时是这条最后一个 token 用的那个版本,中途的流式块给的是服务当前的全局值;`meta_info.weight_versions` 只在请求结束的那一帧出现,给出每段输出 token 各用哪个版本,左闭右开、只数输出 token,一段以上就说明这条不是纯 on-policy。`/get_weight_version` 与 `/weight_version` 两条老路由已经弃用,直接返回 404 并在错误信息里让你去 `/model_info`。日志看 5 行:`Start update_weights. Load format=`、`Update weights end.`、`Cache flushed successfully!`(有请求在飞时是 `Cache not flushed because there are pending requests`)、`Weight version changed.`、`init custom process group:`。指标只有一个 `sglang:weight_load_duration_seconds`,带 `source` 标签,是 gauge 不是直方图,每次更新结束时写一次最近那次的秒数——更新期间引擎是暂停的,周期性统计那条路根本不会跑,所以只能这么埋。

| 症状 | 先查 | 然后 |
|---|---|---|
| 释放接口断言 `should be called only when server is idle` | `#running-req`、`#queue-req`、PD 三个队列、HiCache 在途读写、语法队列 | 先 `/pause_generation`,等 `#running-req` 归零再放 |
| 放了显存 `nvidia-smi` 没降 | 有没有 `--enable-memory-saver`;没有的话日志里什么都不会留 | 加旗标重启;只放 `cuda_graph` 标签的话还要 `SGLANG_MEMORY_SAVER_CUDA_GRAPH=1` |
| 开了 `--enable-memory-saver` 就起不来 | 启动日志里的 ImportError 或 `Breakable CUDA graph is not compatible with memory saver mode` | 装 `torch-memory-saver`;把 `--cuda-graph-backend-decode` 换回 `full` |
| 拿回显存后答案是乱码 | 让出过 `weights` 且没开 CPU 备份 | 拿回后立刻推一次权重;或开 `--enable-weights-cpu-backup` |
| 换权重后质量变差、指标全正常 | 请求里 `flush_cache` 是不是被关了;用的是不是 `in_place` 暂停 | 别关 `flush_cache`;换 `retract` 暂停 |
| 更新接口卡住不返回 | 没 pause,更新在等在飞请求跑完才拿到写锁 | 先 `/pause_generation`;或带 `abort_all_requests=true`(IPC 通道没有这个字段,只能先 pause) |
| 返回 `partially updated … discard the whole weights` | NCCL 组里张量名、dtype、shape 与训练端对不上 | 整批重发,不要只补发失败的那些 |
| 返回 `[weight_cache] … weight cache is active` | `--weight-cache-mode` 不是 `off` | 改回 `off` 重启;守护进程共享的那份权重不能原地改 |
| 返回 `HPC-Ops bf16xfp32 GEMM` 相关的拒绝 | 该算子缓存了 fp32 权重拆分,原地写它看不见 | 关掉这个优化再更新 |
| 多 DP 副本更新直接断言 | `dp_size must be 1 or dp attention must be enabled` | 开 DP attention;或每个副本各起一个服务分别推 |
| 草稿模型没跟着换 | 走的是 NCCL 通道 | 草稿模型改用磁盘、IPC 或张量通道推 |
| 响应 `weight_versions` 有两段 | 这条请求跨了一次换权重 | 正常;要纯 on-policy 就用 `retract` 而不是 `in_place` |
| 服务起来了一直不就绪 | 在等 checkpoint-engine 的第一次 IPC 更新 | 看 `Weights are ready after` 有没有出现;调 `SGLANG_WAIT_WEIGHTS_READY_TIMEOUT` |

## 六、常见误区

- **以为释放接口会自己等请求跑完。** 排障时第一反应是「它总会排空吧」,于是直接调,然后收到一个断言异常;调度器的请求处理没有兜异常的地方。空闲不只是 `#running-req` 为 0:等待队列、PD 的 bootstrap 与 prealloc 与 transfer 队列、HiCache 在途的写回与预取与备份、语法队列,任何一样非空都不算。
- **以为让出权重再拿回来,权重还在。** 因为 KV 那边拿回来就能接着用,想当然权重也一样。KV 能用是因为反正要重算;让出库只留地址不留内容,拿回来的权重是未初始化的显存。引擎自己只另存了常量表,参数默认不存,要存得启动时开备份旗标。
- **以为开了 `--enable-memory-saver`,三类显存就都会让出。** 最出人意料的默认值在这里:CUDA graph 那一类还要 `SGLANG_MEMORY_SAVER_CUDA_GRAPH=1` 才会被贴标签,不设的话放 `cuda_graph` 标签是一次空操作,而且不报错、不打日志。
- **以为不开 memory saver,释放接口也能省一点。** 它退化成一个什么都不做的适配器,只清树,一个字节都不还。代码里那条「不会省显存」的警告全树没有调用点,所以唯一的证据是 `nvidia-smi`。
- **以为 `flush_cache` 是可选的优化,关掉更快。** 4 个更新接口默认都开,关掉的唯一正当理由是连续推多批张量时中间那几次省一下,最后一次必须开。关掉不会报错,只会答错。
- **以为 `abort_all_requests` 默认会打掉请求。** 磁盘、NCCL、张量三条通道默认都是关,IPC 通道压根没有这个字段;只有 `/update_weight_version` 默认是开。不 pause 又不带这个字段,更新接口就在那等在飞请求全部跑完才拿到写锁。
- **以为 `in_place` 暂停加更新等于 `retract`。** `in_place` 把 KV 留着,更新后清树因为运行批非空而失败,断言直接炸;就算过了,也是旧 KV 配新权重。PD 分离的 prefill 节点上 `retract` 也会留着正在分块的那一条,源码注释自己写了这一条会带着旧权重的前缀 KV 继续。
- **以为 NCCL 通道一次广播一批。** 默认是一个张量起一次异步广播、最后统一等,`load_format=flattened_bucket` 才是拼成一条只播一次。
- **以为草稿模型自动跟着换。** 磁盘和 IPC 两条路先换主模型再遍历草稿;张量那条路是先草稿后主模型、`disable_draft_model` 可以跳过;NCCL 这条路全树只有主模型那一份实现。
- **以为 `/get_weight_version` 能查版本。** 它和 `/weight_version` 都是已弃用的壳,直接返回 404,错误信息让你去 `/model_info`。响应里的 `weight_version` 也不是全局的,是这条请求最后一个 token 用的那个。
- **以为 `--checkpoint-engine-wait-weights-before-ready` 等的是「任何一种权重更新」。** 旗标的帮助文本是这么写的,但全树只有 `/update_weights_from_ipc` 成功后会把就绪标志置真,磁盘或张量通道推进去不解除等待。而且等超时之后只打一行 error 就继续预热,服务照样起来,只是里面装的还是随机权重。
