# SGLang 08|推测解码

推测解码为什么几乎白送、接受率怎么决定加速比、草稿从哪来、被拒的 KV 怎么办,vLLM 解读的「推测解码」一章已经讲透;拒绝采样的数学在 vLLM 解读的「采样机制」一章。这一页只说 SGLang 遇到的问题、它的解法、代价、以及和 vLLM 不一样的地方。每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

decode 每步只出 1 个 token,却要把整份权重从显存搬一遍,GPU 大部分时间在等内存。推测解码让一个便宜的草稿先猜几个,主模型一次前向验完,搬一次权重出多个 token。

麻烦不在这个思路,在它给调度器留下的那个数。**每一步都会冒出一个「这次接受了几个」,而这个数是 GPU 算出来的**:接受几个决定序列长度、决定下一步喂什么、决定要不要再分配 KV。CPU 想知道它就得等一次拷贝,一等,02 章辛苦建起来的 CPU 与 GPU 重叠就断在这里——而推测解码恰恰是重叠最值钱的场景,因为草稿模型本身是一串很小的 kernel,连猜几步就是几组下发,CPU 稍微慢一点 GPU 就空着。

哪种负载会坏:接受率低的负载(高温采样、开放式写作、草稿和主模型不配对),草稿全白算,主模型每步从算 1 个 token 变成算好几个,TPOT 比不开还长。批大了也坏:每步要验的 token 数是并发乘验证宽度,并发 64、验证宽度 4 到 8 就是每步 256–512 个 token,decode 从等内存变成等算力,草稿每浪费 1 步就是整批一起浪费。

## 二、解法:接受了几个,CPU 不问

最天然的直觉:既然那个数是 GPU 算出来的,就让它一直待在 GPU 上,CPU 只管形状不管数值。SGLang 的重叠版 worker 一个 decode 步在 GPU 上接着跑三段——草稿、验证、草稿追赶,中间只在验证结束那一刻往显存里写一次东西,**全程不回 CPU**。

![一个推测 decode 步里 GPU、CPU、KV 三条线各自在干什么:GPU 那条从左到右是草稿连猜 5 步(整段捕成一张 CUDA graph)、主模型一次定宽验证、草稿补上被接受的那几个 token 的 KV,三段接着跑中间不回 CPU,验证结束那一刻写公告板并打事件;CPU 那条在同一段时间里只做按最坏情况预留、准备下一批的形状、按格子号取下一步的输入三件事,公告板那一刻标着一个红色的「被去掉的那次等待」——同步做法必须在那里停下来把接受数拷回来;KV 那两行里分配长度按 2 倍草稿宽度撑开到 8 格、提交长度在验证之后才跟上到 2 格,中间的落差是没被接受的加上双缓冲](/opensource/sglang/08a-one-spec-step.svg)

写公告板那一下就是 02 章的那块板子:下一步的输入 token、草稿要用的隐状态和每步留下的候选概率,都按请求号存在 GPU 缓冲区里,下一步的草稿直接从格子里取,CPU 全程只碰格子号。调度器真要用序列长度时,走一条私有的拷贝流,等公告板的事件到了再拷,不打扰计算流。

CPU 不知道接受了几个,那 KV 怎么分?**按最坏情况分**:每个请求每步先占满草稿宽度的格子,验证之后只把接受的那几个算作已提交,03 章那两个长度(撑开的那个和坐实的那个)就是为这件事准备的;再多留 1 倍当双缓冲,吸收提交比分配晚一步的滞后。

约束解码本来必须每步同步一次文法状态,否则不知道下一步允许哪些 token。草稿在 GPU 上跑的那几种算法把这一步挪进了验证里,用一道屏障在主模型前向期间推进文法,重叠不断;只有语料树那一种因为草稿是在 CPU 上查表,没有 GPU 阶段可以藏,配文法时每个 decode 步照旧同步。

**为什么实际不吃亏。** 草稿连猜的那几步整段捕成一张 CUDA graph,验证是固定宽度的 extend、有自己的图,追赶那一步也有;三个阶段各一套注意力后端和图。8 种内建算法全跑在这同一个骨架上,关掉重叠只是让调度器同步地跑同一个 worker,老的那套非重叠 worker 已经从代码里删掉了。

**8 种内建算法,按草稿从哪来分成 5 类。** 一是拿主模型隐状态当输入的小草稿头,三种:两代 EAGLE,加上一种只读主模型 KV、自己不开池的冻结变体(Gemma4 的助手草稿会被自动提升成它);模型自带 MTP 层时草稿权重就在主模型里,不用另给路径。二是独立的小模型,不和主模型共享词嵌入和输出头。三是不跑模型,从已生成 token 的语料树里查,还能在启动或运行时挂外部语料。四是块草稿,一次前向出整块,两种;其中一种再配一个置信度头,决定这一块里每条请求各验多长。五是让主模型自己当草稿,靠一个训练好的 LoRA 切过去。不满意就用一个装饰器注册自己的名字和 worker 工厂,内建名和那个别名不能占;注册时要声明支持重叠,不声明也能跑,只是必须关掉重叠,并且会打一行弃用警告。

**自适应步数**只有两代 EAGLE 加上每步只留一个分支时才有:每个批大小区间各记一条接受长度的指数平均,起步 10 个批不动,之后每 5 个批调一次——往上走的条件是接受长度超过当前这一级的步数减 0.5,往下掉的条件是低于下一级步数减 0.5(下一级是 0 步时改用 0.5);批大小 1 那一档往下掉还额外多要 0.25 的迟滞,其余三档上下对称。内置阶梯按并发分 4 档:1 起可选 1、3、5、7 步,8 起 0、1、3 步,32 起 0、1 步,64 起只有 0 步,0 步就是不猜。每一档启动时都把三个阶段的图捕好,切档是换引用,不重录。

## 三、代价

- **KV 按最坏情况占。** 每请求每步预留 2 倍草稿宽度的格子,每步留多个分支且页大于 1 时还要按分支数乘。所以只要开了推测,并发上限被默认改成 48,日志一行 warning,要更高得自己算好再显式指定。
- **草稿有自己的 KV 池。** 每个主模型 token 配一个草稿槽,5 层的块草稿在 bf16 下每 token 10240 字节,和主模型池同量级;把草稿 KV 改成 FP8 省出来的是空闲显存,不抬静态显存比例它不会变成容量。
- **图占显存。** 草稿、验证、追赶各一套图;开自适应后每一档再各一套。小批量下的捕图列表比不开推测更密。
- **接受率决定一切。** 每步固定验一个定宽的窗口,平均接受长度低于 2 时算力白烧。
- **有的功能关掉或降级。** 语料树、LoRA 自草稿、冻结 MTP 关掉混合分块;独立小模型、语料树、LoRA 自草稿、非 NPU 的块草稿不配 DP attention,带置信度头的那种要把输出头也按 DP 切开;三种不能配流水线并行,真要配得开一个实验环境变量;PD 分离的 decode 端开树和角色切换都拒绝推测;Flex attention 拒绝推测;有的后端只收单分支;LoRA 有白名单(15 章);返回采样掩码的请求被拒。
- **多卡每步广播。** TP 各卡的 softmax 有浮点差异,验证结果由 rank 0 广播给其余 rank,每步多一次集合通信。

## 四、和 vLLM 不一样的七处

![两边都必须做的五件事各占一行,左右两格填各自的做法:猜出一组候选那一行,左边是 4 个方框连成的一条链、右边是 1 个起点分出 3 个分支的一棵树;判候选收不收那一行,左边有主模型分布和草稿分布两个输入、右边草稿分布那一格是空的白底虚线框,只剩主模型概率;给草稿留格子那一行,左边 5 格、右边 8 格;谁知道「这一步收了几个」那一行,每列上半是 CPU 侧下半是 GPU 侧,左边有一支红箭头穿过那条界、右边那支箭头停在界上被打了叉;决定这一步猜几个那一行,左边是按并发查的三级静态表、右边是一部带上下箭头的四级阶梯](/opensource/sglang/08b-vllm-diff-five-rows.svg)

1. **默认怎么验。** vLLM 默认标准拒绝采样,拿主模型概率和草稿概率的比值判;而它的草稿默认是贪心取最大的那个,于是草稿分布退化成一个点,比值退化成主模型概率本身。SGLang 干脆直接写成这个退化形式:草稿概率当 0,一个草稿 token 被接受的概率就是主模型给它的概率,同一层的兄弟节点概率累加着比,被拒的兄弟把主模型概率记下来,最后那个白送的 token 从剩下的那部分概率里采。两边的默认路径因此长得很像,SGLang 省掉了一整份草稿概率张量。**但别据此断言「两边输出分布完全等价」**:标准拒绝采样在拒绝时是从扣掉草稿那份概率之后的残量里采,而这条路径的草稿概率是 0、扣不掉任何东西,两者在拒绝分支上未必重合——这一步没有在基准上验到底,底稿记了待查。全批贪心时再退一层,直接比 argmax。真正的标准拒绝采样在 SGLang 里是要显式打开的另一条路:打开之后草稿改成按自己的分布随机采(温度跟着主模型缩放)、接受率更高,代价是那份草稿概率张量要存下来,而且只有两代 EAGLE、每步单分支、两个接受阈值都是 1.0、不配确定性推理、草稿和主模型词表一致时才允许。ROCm 上第一代 EAGLE 会自动打开它——那边没有采样验证 kernel,不开就退成 argmax,温度和 top-p 被静默忽略。
2. **树还是链。** vLLM 验的是一条链,草稿被摊平成连续的几行。SGLang 每步留多个分支时草稿是一棵树,验证用一张树掩码一次算完;树在页大于 1 时只有三个后端能跑,Hopper 上默认后端也会因此换掉。
3. **三个旋钮不是一个。** vLLM 一个 k。SGLang 是步数、每步分支数、验证宽度三个,要么全不设走一张按模型架构查的默认表(Llama 与 Grok 是 5、4、8,其余一律 3、1、4),要么三个全设;每步单分支时验证宽度会被强制改成步数加 1。
4. **重叠默认开,而且没有白名单。** vLLM 那边异步调度在推测解码下只对一份算法白名单开放,而且一旦关掉「草稿复用目标批次形状」那项优化就用不了——显式一起开会报错,自动模式则悄悄把异步关掉。SGLang 这边推测解码默认就是重叠的,8 种内建算法一视同仁,只有 CPU 设备自动关;要同步路径得显式关重叠,而且跑的仍是同一个 worker。
5. **接受阈值可以运行时改。** vLLM 没有这两个旋钮。SGLang 的两个接受阈值是少数几个能在运行时改的字段;改了输出分布就不再等于主模型,而且每改成功一次顺手把累计接受长度清零。
6. **自适应是运行时阶梯,不是静态表。** vLLM 提供的是一张按批大小写死的分段表。SGLang 按实际观测到的接受长度在候选步数里上下走,大批时可以一路降到 0 步、也就是暂时不猜。
7. **算法清单不同。** vLLM 有 Medusa 和后缀解码,SGLang 这个基准上一个都没有;SGLang 的语料树是跨请求共享的、还能挂外部语料,另有 LoRA 自草稿和冻结 MTP 两种 vLLM 没有的。两边都有的是两代 EAGLE、MTP、独立小模型、以及那两种块草稿。两边的参数名都在第五节。

## 五、调参与观测

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表;组合与推荐值是按语义推的起点,**不是实测最优**。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 自带 MTP 层的大模型(DeepSeek、GLM、Bailing 这一串),H200 八卡通用对话 | 只加 `--speculative-algorithm NEXTN`,三个旋钮全不设让它走默认表的 3、1、4,然后显式给一个 `--max-running-requests`(先用 48 起,按就绪前的 `max_total_num_tokens` 除以「2 × 4」估上限再往上抬) | 零额外权重、零训练换 decode 提速;代价是并发被默认压到 48,不显式抬就白白空着显存 |
| 低并发、延迟敏感,手上有训练好的 EAGLE3 头 | `--speculative-algorithm EAGLE3` 加 `--speculative-draft-model-path`,三个旋钮全设成 `--speculative-num-steps 5`、`--speculative-eagle-topk 1`、`--speculative-num-draft-tokens 6`,再开 `--speculative-adaptive` | 小批时多猜几步吃满接受率,并发涨上来时它自己降档甚至停猜;代价是每个候选步数各捕一套图,显存更紧,且自适应要求 topk 1,放弃了树验证 |
| 代码补全、RAG 问答这类输入输出高度重复的负载 | 只加 `--speculative-algorithm NGRAM`,不给任何草稿权重;并发仍要显式抬 | 零模型成本、零训练;代价是每步固定验 12 个 token,语料树在 CPU 上占容量 10000000 个节点,配文法时每个 decode 步都要同步,而且不能配 DP attention |

**怎么看。** 开了推测,`Decode batch` 行多出 `accept len` 和 `accept rate`:前者是每条请求每次验证平均收下几个 token(含最后那个白送的),直接对应加速比;后者是草稿 token 被接受的比例,分母是「请求验证次数 × (验证宽度 − 1)」。`DSPARK` 再多 `cap len` 与 `block accept len`。`/server_info` 里的 `avg_spec_accept_length` 是从启动以来的累计值,开自适应时那里还能读到当前的 `speculative_num_steps`。每条响应的 `meta_info` 有 `spec_accept_length`、`spec_accept_rate`、`spec_verify_ct`、`spec_num_correct_drafts`、`spec_num_proposed_drafts`。`/metrics` 有 `sglang:spec_accept_length`、`sglang:spec_accept_rate`、`sglang:spec_num_steps` 等 gauge。想扫参数组合,官方带了 `bench_speculative` 脚本。

| 症状 | 先查 | 然后 |
|---|---|---|
| 开了推测反而变慢 | `accept len` 是否低于 2 | 换草稿或算法;高并发开 `--speculative-adaptive` 或降步数 |
| `#running-req` 卡在 48 | 启动 warning 里的 reset to 48 | 显式指定 `--max-running-requests`,同时按 2 倍草稿宽度重算 KV 预留 |
| 启动 OOM | 三个旋钮和 `--cuda-graph-max-bs-decode` | 照文档的配方:`--mem-fraction-static 0.5` → `--cuda-graph-max-bs-decode 2` → 3/1/4 → `--max-running-requests 4`,稳了再逐项抬,比例最后抬 |
| 报 topk > 1 with page_size > 1 | 注意力后端 | 换 `flashinfer`、`fa3`、`triton`,或把 `--page-size` 设回 1 |
| ROCm 上温度像没生效 | 是否退成了 argmax 验证 | 确认启动日志有「Rejection sampling is enabled」;`EAGLE3` 不会自动开 |
| `accept rate` 高、`accept len` 上不去 | 步数太小 | 加步数,或开自适应 |
| 自适应没动 | 启动 warning 里的退回原因 | 改成 `EAGLE`/`EAGLE3` 加 topk 1;去掉 DP attention、TBO、PDMux、多层 EAGLE |
| 「LoRA with EAGLE ... does not support」 | 15 章的 4 条禁用组合 | 关掉对应那一项 |
| 带文法的请求一来吞吐掉 | 是不是 `NGRAM` | 换 EAGLE 家族,文法在验证里推进 |
| TP 多卡挂死 | rank 分叉 | 13 章的同步开关;`SGLANG_SPEC_TP_SYNC` 缩范围定位 |
| 改了阈值答案变怪 | 两个阈值是不是还是 1.0 | 改回 1.0;想提速去调步数 |

## 六、常见误区

- **以为重叠版是个要开的选项。** 老文档和已删的环境变量 `SGLANG_ENABLE_SPEC_V2` 留下的印象。这个基准上推测解码只有重叠版 worker,那个环境变量还设着会打一行「has been removed」;想要同步路径是 `--disable-overlap-schedule`,跑的仍是同一个 worker。
- **以为 SGLang 和 vLLM 一样默认是标准拒绝采样。** 两边都叫「验证」。SGLang 默认不看草稿分布,接受概率就是主模型给的那个概率。**但也别顺手推出「所以 SGLang 默认是有损的」** ——vLLM 的草稿默认也是贪心的,比值同样退化成主模型概率,两条路径的接受判据是一回事;不同之处只在拒绝之后那个白送 token 从哪份概率里采,这一步没验到底(底稿)。显式打开拒绝采样换来的是更高的接受率,不是正确性。
- **把 `--speculative-eagle-topk` 当采样的 `top_k`。** 名字里都有 topk。它是草稿树每层的分支数,和请求的 `top_k` 无关;`UNO` 的 K 也是这个意思。
- **只设三个旋钮里的一个。** 以为另外两个会按默认表补上。不会:三个要么全不设,要么全设;每步单分支时验证宽度会被悄悄改成步数加 1,日志里只有一行 warning。
- **照文档设 topk 1 才敢开重叠。** 文档的 V2 一节写着重叠只支持 topk 1、大于 1 会报错。这个基准上启动并没有这条检查,Llama 的默认表就是 topk 4 且重叠开着,分配器里也有页大于 1 的树分支;文档那段是旧的。
- **看 `accept rate` 0.6 就觉得差。** 它是逐草稿 token 的比例,尾部的 token 本来就接不住。看 `accept len`,3 以上就值。
- **把 `avg_spec_accept_length` 当最近值。** 它从启动累计,而且 `/set_internal_state` 每成功一次就清零——哪怕这次改的是别的字段。前后对不上不是 bug。
- **以为 `NGRAM` 免费。** 不跑模型不等于不花钱:每步固定验 12 个 token,语料树在 CPU 上、容量 10000000 个节点,配文法时每步同步,而且不配 DP attention。
- **给 MTP 模型手动传草稿路径。** 以为草稿总要单独指定。DeepSeek、GLM、Bailing 这一串自动指向主模型,手动传会打「does not require」,而且传错了会真的去加载那份权重。
- **调低接受阈值当免费加速。** 阈值低于 1.0 之后接受的 token 不再服从主模型分布,是有损的;它之所以能在运行时改,正因为它是给实验用的。
- **以为自适应也会调分支数和验证宽度。** 它只调步数,验证宽度跟着等于步数加 1,分支数必须是 1;并发 64 以上内置阶梯只有 0 步,看到它把推测关了是设计如此。而且不是「低了才降」——批 1 那一档往下掉多要 0.25 的迟滞,其余几档上下对称。
- **推测解码下按接受长度估 KV 用量。** 分配是按最坏情况、每步 2 倍草稿宽度预留的,默认并发 48 就是这么来的;显存空着一半也进不了更多请求,要显式抬并发。
