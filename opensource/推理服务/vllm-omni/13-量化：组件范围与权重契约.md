# 量化：组件范围与权重契约

这一页说明低精度怎样落到目标组件,以及为什么量化方法必须与 checkpoint、硬件和权重搬运方式相容。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

扩散 pipeline 中,DiT、text encoder 和 VAE 的权重布局、计算量与精度敏感性不同。只看到模型总显存很大,就把全局精度降下去,可能压缩了错误组件,也可能让关键层的误差在 denoise 中累积。另一种失败更直接:checkpoint 已经存成低比特权重和配套 scale,加载器却按另一种格式解释它。

**量化首先是范围和存储契约问题,之后才是 kernel 选择。** 本项目要回答的是哪些组件实际接入量化、权重何时转换、scale 从哪里来。通用量化原理见知识库;这里不把一种位宽当作所有模型通用的性能承诺。

## 二、解法

**先选组件,再给层选择计算方法。** 量化工厂沿用 vLLM 的注册体系,补上扩散专用方法与组件路由。组件路由按层前缀找最具体的匹配项,允许某个子范围明确保持原精度;没有命中时才走默认配置。它不会把任意 PyTorch 模块改造成量化层,模型必须把配置传给支持量化的 Linear 或其他实现。

![组件路由优先匹配更长前缀,明确禁用的子树保持原精度,其他已接入的层才进入量化方法,未命中的组件使用默认配置](/opensource/vllm-omni/13a-component-quant-routing.svg)

**全局配置并不自动排除 encoder。** MiniMax H3 分别解析 DiT 与 text encoder 的配置,其量化感知 encoder 可以接到同一份全局配置。保护措施也有具体原因:缺少对应 scale 的视觉或音频 encoder 不应误用某些预量化格式;精度敏感的 norm 和 modulation 层另有配置过滤。不能把这些保护概括成所有 encoder 永远不量化。

**加载时区分转换与读取。** 在线量化从普通权重出发,在加载过程中生成量化权重和 scale;推理时激活如何处理,仍由具体方法决定。预量化 checkpoint 已经提供存储格式,工厂会把磁盘 metadata 与当前方法对齐:方法不匹配就报错,同一方法若声明已序列化,则切换到对应离线路径。加载器还补做未完成的逐层处理,避免残留的占位权重进入执行。

**组件名字也属于契约。** Wan 的级联 DiT 把两个 Transformer 当作兄弟组件精确选择,再分别核对各自 checkpoint。若一个组件被明确禁用量化,磁盘却声明它已量化,会拒绝加载;保持原精度需要真正的原精度权重,不能靠路由把打包权重变回来。

## 三、代价

**驻留显存和启动峰值不是同一个指标。** 在线量化需要读入普通权重并完成转换,还要生成 scale 与运行时布局。启用 CPU Offload 时,加载器可以先在加速器上量化再移回主机;运行阶段更省显存,不代表启动时也按同样比例下降。

**位宽相同,执行路径仍可能不同。** Weight-only 保持高精度激活,而权重和激活都量化还要付出激活转换成本。设备能保存某种 dtype,不等于装有对应 GEMM 实现。更低位宽还可能需要额外校正张量、重排或回退层,不能从文件大小推断生成速度。

**兼容性看最终张量布局。** 分布式逐层 Offload 的 AllGather 路径会检查每个受影响组件的在线方法;当前放行 per-tensor FP8、INT8、MXFP8 等已适配布局,其余在线方法拒绝进入该路径。HSDP 对部分 FP8 权重还有专门的连续存储适配。这里不存在「量化与所有 Offload 互斥」的一条总规则,但也不能由一个成功组合推及所有格式。

**质量要单独验收。** 保存下来的权重更小、kernel 能运行、图像仍符合要求,是三件事。应固定输入、seed、分辨率和采样设置,分别看输出、生成时间与峰值显存;像素误差也不能代替语义和视觉检查。

## 四、和 sglang-omni 的量化接入对照

sglang-omni 的这条接入路径把量化配置解析、量化层与加载后处理交给 SGLang;本地适配负责 Qwen3-Omni 的阶段前缀归一化,以及自定义权重加载中的 FP8 scale 转换。

vLLM-Omni 同样复用底层推理引擎,但本章的扩散路径额外提供组件配置路由、扩散专用方法和加载器与 Offload 的布局检查。两边都要对齐 checkpoint 名称与运行时层名;区别是本项目在扩散加载侧承担了更多适配职责,不是宣称注册的方法越多就越快。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--quantization` / `quantization_config` | CLI 方法名;Python / 部署配置可传结构化配置 | 扩散配置为 `None`;有 checkpoint metadata 时可自动检测 | 选择全局方法,范围取决于模型已接入的组件 | `Building quantization config`、`Auto-detected quantization` |
| `--diffusion-quantization-config` | CLI JSON | `None` | 精确给出方法属性或组件映射 | `Per-component quantization` 及实际层名 |
| 组件前缀与 `default` | 结构化 `quantization_config` | 未指定的默认配置为 `None` | 最长前缀优先;JSON `null` 明确禁用该匹配范围,不继续落入默认方法 | 核模型传入的 runtime prefix;Wan 的兄弟组件使用精确名字 |
| `ignored_layers` | 方法配置内部 | 本章 FP8/INT8/BitsAndBytes 配置通常为 `[]`;磁盘可另有策略 | 保留敏感层精度,增加这部分权重与计算成本 | 固定 seed 比较输出,核重映射后的层名是否命中 |
| `activation_scheme` | 方法配置内部 | FP8 指南为 `dynamic`;本地 INT8 实现也是 `dynamic` | FP8 可按有校准 scale 的路径选择 `static`;INT8 当前拒绝其他值 | 配置校验、scale 是否由 checkpoint 提供 |
| `is_checkpoint_int8_serialized` | INT8 checkpoint metadata / 方法配置 | 构造默认 `false` | 选择读入已量化权重的路径;不能用标志代替离线转换 | 自动切换离线路径日志、缺少权重或 scale 报错 |
| `quant_type`、`compress_statistics` | BitsAndBytes 方法配置 | `nf4`、`true` | 选择四位权重格式与 scale 压缩,激活保留 BF16/FP16 | 权重驻留、生成时间和输出差异 |
| `VLLM_OMNI_USE_QUACK_FP8` | 环境变量 | 按 CUDA capability 主版本 10 自动尝试,还需可选依赖 | 控制融合 bias 的 FP8 GEMM 替换;不能用强制开关补出硬件指令 | patch 成功日志或 `Quack FP8 GEMM failed` 回退警告 |

**硬件门槛按方法核。** 本地 BitsAndBytes 路径只接受 CUDA,声明最低 SM75;INT8 分 CUDA 与 NPU。原生 MXFP8 接 NPU 和 XPU,但 XPU 不接受这条原生离线格式;MXFP4 还有限定 gfx950 的 ROCm 在线实现。不要从总览的一格“支持”推出所有 checkpoint 格式都可用。SVDQuant 的当前实现更严格,只接受已序列化 NVFP4 checkpoint,设备检查限定 SM103。

**Blackwell 也要分清型号。** 可选 quack 自动路径面向 capability 10.x 的数据中心 GPU;RTX 50 系列等 capability 12.x 不自动走它。后者有自己的原生 FP8 路径,强制 quack 可能反复失败回退,不等于开启了更快的 kernel。

以下先隔离量化本身,资源假定为单张有足够加载余量的 CUDA GPU。H100 80 GB 与 A100 80 GB 是验证起点,并非最低显存声明;需要具备对应 vLLM kernel 或可选 BitsAndBytes 依赖。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| H100 80 GB,Qwen-Image 图像生成,先验证在线 FP8 | `vllm serve Qwen/Qwen-Image --omni --quantization fp8` | 无需另做 checkpoint,用加载期转换和低精度误差换取权重压缩;与同设置 BF16 对照 |
| 同样硬件与模型,FP8 输出出现退化,先保留图像 MLP | `vllm serve Qwen/Qwen-Image --omni --diffusion-quantization-config '{"method":"fp8","ignored_layers":["img_mlp"]}'` | 保留敏感计算,牺牲部分压缩与潜在加速;是否改善由输出对照决定 |
| A100 80 GB,Z-Image-Turbo,只考察四位权重节省 | `vllm serve Tongyi-MAI/Z-Image-Turbo --omni --quantization bitsandbytes` | 使用在线 weight-only 路径,激活仍为原计算精度;不承诺比 BF16 更快 |

组合与推荐值是按语义推的起点,不是实测最优。

随仓 `compare_diffusion_trajectory_similarity` 工具可对参考与候选分别运行,保存图像或帧。报告中的 `output_metrics` 给像素误差与相似度,`avg_generation_time_s` 给生成时间,`max_peak_memory_mb` 是 worker 提供时才有的峰值。缺失显存报告不能当作零占用;三组指标应分别判断。

| 症状 | 先查 | 然后 |
|---|---|---|
| 一加载就报量化方法不一致 | checkpoint 的 `quant_method` 与当前配置 | 使用匹配方法或自动检测;不要只改磁盘标签 |
| 明明只想量化 DiT,encoder 也变了 | 是否传了全局配置,模型是否有量化感知 encoder | 改组件映射并核 runtime prefix |
| 运行显存降了,启动仍 OOM | 在线转换的加载设备与临时权重 | 分开测启动峰值和运行峰值,再检查 Offload 加载日志 |
| DLO+AllGather 拒绝量化 | 报错列出的具体在线方法与受影响组件 | 核是否可用 rank-local 搬运,或换已放行方法;不要关闭全部 Offload 作为固定结论 |
| 图像退化但程序无错 | 敏感层、输入与 seed 是否固定 | 保留敏感层重新比较,再决定量化范围 |
| 权重更小但时延变差 | 实际 kernel、回退警告、激活转换与搬运时间 | 做热身后的同负载对照,分别记录质量、速度和显存 |

## 六、常见误区

**把 online 理解成每次请求都重新量化全部权重。** 这个词容易与动态激活量化混在一起;本项目在线权重量化主要发生在加载期,请求期间的激活处理由方法另行决定。

**用 null 关闭组件量化,就能加载原精度结果。** 路由只选择处理方法。Wan 会拒绝“组件禁用但磁盘已量化”的冲突,因为打包权重缺少的精度无法由配置恢复。

**以为更具体的组件规则没匹配也会报错。** 通用路由采用前缀匹配和默认回退,运行时权重名又可能被 mapper 改写。拼错前缀可能只是落回默认配置;要检查实际命名和生效范围。

**照旧说明认定 encoder 一律不量化、Offload 一律不兼容。** 两者都已有模型或方法特定的接线。正确排查对象是组件、checkpoint 和搬运路径的组合,否则会把能用的省显存方案一起排除。
