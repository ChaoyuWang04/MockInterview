# 观测、剖析与基准

这一页解释同一次请求为什么需要客户端计时、阶段统计和 GPU trace 三种观察方式,以及怎样把它们接到可复现的 benchmark 上。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

语音服务“慢”可能是第一段声音来得迟,也可能是开头很快、后面不断断流;图片服务“慢”可能是排队,也可能是 denoising、VAE 或响应编码。如果只盯 GPU kernel,客户端等待的时间会消失;如果只盯请求总时长,又不知道该改哪个阶段。

多阶段流式执行让问题更复杂:上游还在生成,下游已经消费早先的 chunk。阶段耗时与传输耗时可能重叠,不能把它们相加后称作用户等待时间。benchmark 的平均吞吐也不能替代尾延迟。

**观测的核心是先确定谁在什么时刻计时,再用相同请求和负载把不同层的证据关联起来。**

## 二、解法

**先在客户端判断交付是否满足需要。** Speech benchmark 在发起 HTTP 请求前开始计时,收到第一个非空 PCM chunk 时记录 TTFP,收完响应时记录总延迟。它根据音频字节数、采样率与声道数还原内容时长,再计算 RTF。文本 TTFT、音频 TTFP 与完整媒体生成延迟回答的是不同问题;TTS 没有文本输出,就不应硬造一个文本 TTFT。

**再用服务端统计缩小范围。** Orchestrator 汇集阶段输出中的生成时间、模态产出与相邻阶段传输记录,按请求建立阶段快照。最终输出阶段完成时记录引擎请求的 E2E,同时向 Prometheus 写入完成原因与延迟。这个结束点早于可能继续发生的 HTTP 编码、视频落盘或客户端下载,更不是播放器播完的时刻。

![示意时间轴区分客户端完整响应、引擎完成、重叠的阶段与传输、有限GPU捕获窗口;条带长度不代表实测结果](/opensource/vllm-omni/17a-measurement-boundaries.svg)

传输也拆成发送、接收解码与在途观察,并带上阶段与 replica 身份。它们帮助判断时间落在 connector 的哪一侧,而不是自动给出网卡带宽。汇总保留各自边界,比强行拼成无重叠的端到端分解更可靠。

**最后才进入剖析。** Diffusion pipeline profiler 包装模型方法,在方法前后同步设备,记录 CPU 时钟经过的时间;重复 denoising step 可以累加成 diffusion 区间。完整 forward 与内部 VAE、denoising 方法可能嵌套,这些记录也不能全数相加。Torch profiler 则在 worker 内捕获 CPU/GPU 活动,停止后导出 trace 与算子表,用于进一步查看执行空隙、同步和热点。

benchmark 将这些观察接回同一工作负载:Omni CLI 扩展上游压测参数,选择适配目标端点的客户端,需要阶段指标时向请求附带返回要求,最后分别汇总成功响应中的客户端延迟和服务端快照。它是测量入口,并不保证任意两次运行天然可比。

## 三、代价

**精细观察会扰动被观察的执行。** 方法计时中的设备同步会改变异步重叠;Torch trace、shape、stack 与 memory 记录也有采集和导出成本。因此持续运行的统计适合发现趋势,短时剖析适合解释原因,正式吞吐测量应明确是否包含这些成本。

**聚合会丢失请求之间的关系。** Prometheus Histogram 适合看分布,但单看阶段分位数无法还原某次慢请求的关键路径。跨阶段 token 总量还可能混有中间表示,不能直接当作用户可读文本吞吐。完成计数必须按原因过滤,其中取消不能当作业务成功。

**指标名字不等于测量契约。** 服务端音频 RTF 使用阶段生成时间,Speech benchmark 使用客户端总延迟;数值不同不一定意味着实现冲突。按 chunk 到达时间估计的播放缺口也只是连续性模型,不包含真实播放器的缓冲策略和播放确认。复现实验要一起保存模型 revision、硬件、部署配置、请求形状、并发、预热与测量窗口。

## 四、与 SGLang-Omni 的对照

固定基准下,SGLang-Omni 的 Stage runtime 在接收上游 payload 和完成输入聚合时写入请求事件。它的 RequestEventRecorder 按进程保存 JSONL,带有请求、stage、运行标识和时间戳;启动剖析的控制消息还能同时开启 worker Torch trace 和请求事件记录。这条路径适合沿同一请求重建“输入何时到达、何时就绪”的过程。

vLLM-Omni 本章的主路径则由 Orchestrator 汇集阶段输出快照,持续暴露 Prometheus 分布,并把快照返回给 benchmark 做阶段汇总。两者都能进一步采集 GPU trace,但一个请求事件、一个累计阶段快照,不能只因为都有“阶段时间”就直接对比数值。

SGLang-Omni 还在通信层提供独立的通信事件日志,也体现了同一个边界:控制流与数据搬运证据需要到真实埋点处解释。这里比较的是这些已经接入运行路径的观测方式,不据此推断谁的延迟更低。

## 五、调参与观测

这里同时有服务启动开关、请求字段、benchmark 命令参数和运行时捕获控制,生效范围不同,不能统一当作启动配置。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
| --- | --- | --- | --- | --- |
| `--log-stats` | Omni 服务启动 | 关闭 | 启用阶段/请求统计与对应指标写入 | `/metrics` 返回成功不等于已有样本;核 `vllm_omni:` 数据与阶段标签 |
| `--enable-diffusion-pipeline-profiler` | 服务启动 | 关闭 | 包装 pipeline 方法并同步计时 | 看 `stage_durations`,嵌套 forward 与子方法不相加 |
| `--enable-ar-profiler` | 服务启动 | 关闭 | 将 AR 阶段时间加入阶段时长输出 | 区分 AR 生成区间与客户端 TTFT |
| `profiler_config` | 引擎/服务启动 | Diffusion 配置为 `None` | 配置 `torch` 捕获及输出目录,或 `cuda` 捕获范围 | Torch 的细项继承所安装 vLLM 配置;不以文档旧版链接推定当前默认 |
| `/start_profile`、`/stop_profile` 的 `stages` | 运行时 POST | 未指定时覆盖所有阶段 | 在已配置 profiler 的服务中选择捕获阶段并起停 | 停止后检查对应 stage/rank 产物,不是仅检查请求返回成功 |
| `return_stage_metrics` | 支持该字段的请求 body | Image/Video 为 `None`,不主动返回详细快照 | 请求携带服务端阶段指标 | 不会因此开启 GPU trace;显式 `false` 不会被 bench 的通用自动注入改成 `true` |
| `--print-stage` | benchmark 命令 | `False` | 请求并打印阶段统计 | Image 后端、部分 Chat 指标也会自动请求快照,不只由此开关触发 |
| `--omni-request-timeout-s` | benchmark 命令 | CLI 为 `None`,运行时采用 900 秒 | 超时计为失败;非正数恢复 6 小时上限 | 同时报告超时数,不能只比较剩余成功样本的延迟 |

以下 benchmark 在源码仓根目录执行,服务已按对应模型部署在本机默认端口;Qwen-Image 先取得模型到 `/models/Qwen-Image`,确认其 `tokenizer` 子目录存在,再将命令中的本地路径替换为实际位置;硬件是语义起点,不是显存或性能保证。启动时统一显式开启 `--log-stats`,保留同一模型与 stage 配置。

| 场景 | 怎么起/怎么测 | 拿什么换什么 |
| --- | --- | --- |
| Qwen3-TTS-12Hz-0.6B-CustomVoice / 单张 A100 40GB,查首包 | `vllm bench serve --omni --model Qwen/Qwen3-TTS-12Hz-0.6B-CustomVoice --backend openai-audio-speech --endpoint /v1/audio/speech --dataset-name seed-tts-text --dataset-path benchmarks/build_dataset/seed_tts_smoke --seed-tts-locale en --num-prompts 20 --num-warmups 2 --max-concurrency 1 --extra-body '{"voice":"Vivian","language":"English","task_type":"CustomVoice"}' --percentile-metrics e2el,audio_ttfp,audio_rtf,audio_underrun` | 先固定文本集、音色和单并发,再增加负载;用 TTFP、连续性和失败数约束吞吐。核对 PCM 采样率与声道,避免内容时长算错 |
| Qwen-Image / 单张 A100 80GB,定位生成区间 | `vllm bench serve --omni --model Qwen/Qwen-Image --tokenizer /models/Qwen-Image/tokenizer --endpoint /v1/images/generations --dataset-name random --random-input-len 64 --random-output-len 1 --num-prompts 10 --num-warmups 2 --max-concurrency 1 --percentile-metrics e2el --print-stage --extra-body '{"size":"1024x1024","num_inference_steps":20,"seed":42,"return_stage_metrics":true}'` | 第一轮不启用 trace;第二轮加方法计时定位 VAE/denoising,再用短 Torch 窗口解释热点。以采集扰动换定位能力,两轮不混成同一性能结果 |
| Qwen3-Omni-30B-A3B-Instruct / 2 张 H100 80GB,查阶段拥塞 | 使用第 05 章默认两卡布局,执行 `vllm bench serve --omni --model Qwen/Qwen3-Omni-30B-A3B-Instruct --endpoint /v1/chat/completions --backend openai-chat-omni --dataset-name random --random-input-len 64 --random-output-len 100 --num-prompts 20 --num-warmups 2 --max-concurrency 1 --print-stage --percentile-metrics ttft,tpot,itl,e2el --extra-body '{"modalities":["text"]}'` | 固定文本输出后逐级增加并发,核 stage/replica 与传输边;GPU 不繁忙时回看第 05 章 Orchestrator 诊断,不要直接扩副本 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先看什么 | 如何解释与处理 |
| --- | --- | --- |
| 客户端慢,引擎 E2E 较短 | 编码/落盘路径、网络交付及客户端读取 | 引擎完成不是响应收完,先补齐两端边界 |
| 显示接收速率很高,总传输仍慢 | `rx_decode_time_ms`、`in_flight_time_ms`、发送时间 | `rx_mbps` 用解码时间作分母,不能当实测链路带宽 |
| 总体平均很好,部分请求很慢 | 成功样本分位数、失败/超时数、逐请求记录 | `e2e_avg_time_per_request_ms` 是窗口时长除请求数,不是逐请求延迟均值 |
| 完成计数上涨但用户取消很多 | `finished_reason="abort"` 与失败原因 | `requests_success_total` 名字下也有 abort,需要过滤 |
| 配好了 profiler 却没有 trace | 路由是否装配、worker 是否起停、目录与 rank | 配置、捕获、导出是三个步骤;轻量方法计时不产生 Torch trace |

## 六、常见误区

- **“各 stage 加传输,就是 E2E。”** 流式阶段可重叠,方法计时可嵌套;先画实际测量边界再分析关键路径。
- **“收到第一包就是开始顺畅播放。”** 首包只说明一个时刻,后续到达节奏与播放器缓冲还决定连续性。
- **“同名 RTF 可以直接对比。”** 必须同时核分子区间、音频时长来源和样本集合。
- **“trace 里优化了一个 kernel,服务就更快。”** 还要在关闭诊断扰动、固定工作负载且输出正确的 benchmark 中验证客户端指标。
