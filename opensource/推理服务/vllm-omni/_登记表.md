## 二、一句话核心

vLLM-Omni 是 vLLM 社区的 **any-to-any 多模态服务运行时**。它和 vLLM 的关系不是竞争而是扩展:文本自回归那一段的调度、分页 KV、连续批处理直接复用 vLLM,vLLM-Omni 自己拥有的是**阶段抽象、跨阶段编排、段间传输,以及一整套与自回归平行的非自回归(扩散)执行栈**。

它的设计靶子是:一次 omni 请求要穿过计算形态、批处理方式、注意力形状、并行策略、显存行为、量化路径全都不同的若干段,而输出可以是文本、图像、视频、音频或机器人动作。回答是把**阶段**定义成「有自己的模型组件、执行策略、资源归属与性能目标的逻辑执行单元」,让批处理、注意力、并行、量化全部 stage-local,再用 `PipelineConfig` / `DeployConfig` 把**模型结构**与**部署放置**彻底分开——同一个逻辑模型可以 AR-only、DiT-only 或 AR → DiT 三种部署,不改模型代码。

论文标题就是这句话:*vLLM-Omni: Fully Disaggregated Serving for Any-to-Any Multimodal Models*(arXiv 2602.02204)。

24 MB 运行时代码里,模型实现占 14.7 MB(61%),扩散框架侧约 2.4 MB,服务面 1.5 MB,引擎与阶段运行时 1.2 MB,段间传输 0.6 MB。

- 检测确实接在活路径上:`vllm_omni/entrypoints/omni_base.py:137` 的 `class OmniBase(PDDisaggregationMixin)` 让所有入口继承它,`vllm_omni/engine/omni_engine_base.py:590` 在启动时调 `PDDisaggregationMixin.detect_pd_separation_from_stage_configs(self.stage_configs)`。也就是说**每次启动都会跑一次 PD 检测**,这和 sglang-omni 那种「只有自己模块和单测引用」的死代码不是一回事
- 但**没有任何一份随仓部署配置打开它**:`git grep kv_transfer_config 4d877780d3 -- 'vllm_omni/deploy/*.yaml'` 在 96 份 yaml 上**零命中**。文档自己也写着「Deploy-based configuration: Not yet migrated; the supported `stages:` deploy schema cannot currently expand Qwen3-Omni into the four-stage PD topology」
- 文档还列了另外三条未完成:Thinker→Talker 的 embedding merge「不在活的 stage processor 里接线」、Orchestrator 要求 `remote_request_id` 而钉住的 Mooncake 连接器不返回这个元数据、PD 的端到端测试在迁移期间被临时关掉
- **结论**:写成一整章会让读者以为这是一种可用部署形态。正文口径 = 「检测与路由的骨架在活路径上,但基准上没有一份可跑的 PD 部署」,落点见第五节

## 五、候选章推导过程中的判断

**04 与 05 分章,不合并。** 两者都在 `engine/` 下且都关于「跨进程」,但按 06 的「痛点是不是同一条」判据是两条:04 的痛点是「一条请求散在多个进程,状态没人管」,05 的痛点是「逻辑阶段要展开成副本并起进程」。作者自己也把它们写成两份独立的模块契约文档(`module/engine_orchestration.md` 与 `module/stage_runtime.md`),各有不同的 owner 与不变量命名空间(`ORCH-INV-*` 与 `STAGE-INV-*`),属于判据二「主张背书」。

**07 不按 AR / generation 拆两章。** `LLM_GENERATION` 这一类有自己的调度器与 runner(`core/sched/omni_generation_scheduler.py` 32 KB、`worker/gpu_generation_model_runner.py` 47 KB),但合计只有 79 KB,按 06 的体量判据撑不起一章;而它和 AR 段的痛点是同一条——「vLLM 的调度语义只覆盖文本自回归」。按合并规则并进 07,在那一章里讲清三种执行类型的分工。

**08 把三件事合成一章。** 前缀缓存(`core/prefix_cache/` 128 KB)、模型自带 KV 的申报协议(`model_local_kv.py` 与 `worker/base.py` 的显存账)、扩散侧 KV(`diffusion/diffusion_kv/` 108 KB)各自都撑不起一章,但痛点是同一条「KV 谁管、算不算进预算、AR 与 DiT 要不要两套」。**0.28.0 的 News 把「a unified AR/DiT paged KV cache runtime」当成一件招牌讲**,属于判据二的主张背书,合章成立。

**10 与 11 分章,不合并。** 都属于「扩散怎么跑得快」,但 10 解的是「一张卡装不下 / 一步太慢」(切分),11 解的是「kernel 选错 / 步间冗余」(单卡算得更省)。两条痛点,分章。

**12 把 offloader 与 host weight runtime 合成一章。** 前者 232 KB、后者 175 KB,各自都够边界,但痛点是同一条「权重太大,显存与主机内存都不够」:offload 解的是「装不下就往外放」,host weight runtime 解的是「同机别加载多遍」。而且 `feature/host_weight_runtime.md` 明说它是「shared infrastructure」,扩散与自回归都可以依赖,放在扩散章里反而框窄了。

**13 量化留章而不是并进各章第五段。** 230 KB 在这个项目里算小,但量化在 omni 场景下有一个独有问题——**同一条流水线里不同段该不该一起量化**(文档反复强调 VAE 与文本编码器不跟着 DiT 走),这是单模型引擎没有的。留章。

**14 是最大的框架侧章(约 1700 KB),不再细拆。** `entrypoints/` 1460 加 `protocol/` 100、`clients/` 85、`outputs/` 84。体量上够拆成「接口面」与「输出契约」两章,但两者的痛点是同一条「omni 的请求与响应装不进文本接口」,且作者把它们写在同一份 `module/entrypoints.md` 的 ownership 边界里(`primary_code_paths` 同时列了 `entrypoints/**`、`clients/**`、`protocol/**`)。合章,输出契约做成一个 Part。

**15 只有一套全双工框架,不是三套。这是 2026-09-20 探路小批纠正的一处误判。** 拆解阶段我只读了 `docs/design/` 下的 `fullduplex.md` 与 `fullduplex-personaplex.md`,又 `git grep` 到 `experimental/fullduplex/` 有活引用,于是判成「三套实现关系不明、全表把握最低」。**读了 `vllm_omni/experimental/fullduplex/README.md` 就一句话的事**:该 README 明写「The native full-duplex runtimes graduated out of this package」,原生全双工运行时已经毕业到稳定树。核对结论:

- **统一框架一套**:`engine/duplex/`(507 KB、27 文件)加双工引擎、双工编排器、`entrypoints/duplex/`(60 KB)与客户端。`design/fullduplex.md` 是它的 owner 文档
- `experimental/fullduplex/`(157 KB)剩下三样东西:JoyVL 这一个模型的集成、一个该 README 自己标注「应用应改用新客户端」的遗留探针客户端(benchmark 与 e2e driver 仍在引用,所以 grep 显示它不是死代码)、视频帧拼接工具
- **PersonaPlex 是模型不是框架**:它注册在流水线注册表里,有自己的部署配置、输入处理器与客户端;`fullduplex-personaplex.md` 是这个模型的设计记录。全仓只有 MiniCPM-o 4.5 与 Qwen3-Omni 两个模型声明了双工插件,PersonaPlex 没有声明

把握因此从中提到高。**教训:判一个包的定位之前先读那个包自己的 README,不要只读 `docs/design/` 下的设计文档**——设计文档讲的是契约,包 README 讲的是当前谁在用谁。

**`experimental/` 364 KB 不独立成章,按三块分流。** 按 06「每章定下来后写一句『在哪些场景下哪个指标会坏』,写不出来的说明它不是一章」——「实验区」写不出统一的一句。分流:`fullduplex/`(157 KB)与 `ar_diffusion/`(158 KB,有 `feature/realtime_ar_diffusion.md` 背书,是 AR 与去噪交替的会话)进 15 章;`world_models/`(49 KB)进 16 章。

**动作输出不独立成章。** README 把机器人策略与动作输出列为招牌之一,按判据四(参照项目没有对应物)本该独立成章——sglang-omni 完全没有这一块。但核对代码后发现 **π0、π0.5、GR00T、InternVLA-A1、DreamZero 全部落在 `diffusion/models/` 下**,因为动作策略本身就是扩散/流匹配模型;框架侧没有第四套执行栈,只有 `entrypoints/openpi/` 一个服务面。所以它是「扩散栈的一种输出模态」,机制进 09–12,服务面进 14,不另起一章。**这个判断本身值得在 01 章或 14 章点一句**,因为「动作也是扩散」是读者最容易想错的地方。

**PD 分离不成章,落两处。** 依据是第三节末尾的核对结论:检测在活路径上但没有可跑的部署形态。落点——**路由那半**并进 04 章,当作「编排器要在跨段路由之外再认一种段间关系」的实例;**连接器契约那半**并进 06 章,因为 KV 页本来就是连接器要搬的一种数据。两处都要写明它当前是什么状态,不要写成一种可用部署。

**配置系统单独成章(02),这点和 sglang / sglang-omni 不同。** 那两个项目的配置集中在总览第六节。这里成章的理由是判据二:作者把「模型结构 / PipelineConfig / 阶段运行时策略 / DeployConfig」四层分离当成**架构结论**写进 `design/architecture_overview.md`,并给了一张五层解析图,还专门写了 `module/vllm_omni_config.md`;而且 `deploy/` 下 96 份 yaml 带平台分节覆写,是这个项目读者真正要上手改的东西。

**章序**:01–06 是框架骨架,07–08 是 AR 侧,09–13 是扩散侧,14–15 是两头的面,16–17 是接入与外围。按 06 的短页读法,只读 01、02、03、06、09 就能建立主线。

**新增 03「阶段图的边」,这是盲拆对比逼出来的一章(第七节 ①)。** 拆解阶段我把 `stage_input_processors/`(454 KB、35 项)划给了模型集成层,当成「每个模型自带的一个处理器」。读完论文才发现**它是整个系统编程模型的一半**:论文把模型定义成阶段图,节点是阶段、**边是用户写的变换函数**,并且把用户要实现的函数分成三类——每步调的前向、每次迭代调的输入预处理、交接时只调一次的段间变换。代码里对应 `StagePipelineConfig` 的两个自定义处理函数字段加上那 35 个处理器。按 06 的判据:体量 454 KB 够(判据一),**论文把它当核心抽象是最强的主张背书**(判据二),痛点「上游产物怎么变成下游输入」和 02 的「拓扑怎么声明」、04 的「谁管请求状态」都不是一条(判据三)。独立成章,插在 02 之后,其后各章顺移。

**2026-09-20 探路小批:这一章成立,而且主旨要收窄。** 加章时我只有论文的口径和目录名,没读实现,风险是这 35 个处理器其实各写各的、写出来变成流水账。拿三个形态完全不同的模型对了一遍——Qwen3-Omni(三段自回归)、MiniCPM-o 4.5(全双工)、MiniMax-H3(单扩散段):

**公开函数的签名聚成三种形态,跨这三个模型逐字一致:**

| 形态 | 固定位置参数 | 谁在用 |
|---|---|---|
| 流式分块的段间变换 | `(transfer_manager, multimodal_output, request, is_finished=False)` | Qwen3-Omni 两条边、MiniCPM-o 一条边 |
| 整份交接的段间变换 | `(transfer_manager, pooling_output, request)` | 同上三条边 |
| 下游的输入预处理 | `(source_outputs, prompt=None, requires_multimodal_data=False, streaming_context=None)` | Qwen3-Omni、MiniCPM-o 各两个,MiniMax-H3 的 `encoder2diffusion` |

上述是样例观察;2026-09-22 补核确认存在按签名传递的可选上下文,不可概括为所有处理函数的参数数量固定。唯一的例外 `minimax_h3.prepare_encoder_prompt` 是入口段的输入准备、不是段间变换,形态不同是合理的。

**框架侧的调用证实了这是有意设计,也证实了它还没做完**:编排器调下游预处理函数时,先按固定的三个位置参数调,再**用反射探测函数签名**决定要不要多传一个采样参数,而那几行上面就压着一条 TODO——「replace signature probe with explicit kwarg contract」。项目自己承认契约是隐式的。

所以主旨从「边是一等公民的抽象」(论文的说法,代码里没有基类支撑)收窄成**「段与段之间那道缝里,框架保证什么、模型必须自己做什么」**:框架提供不同交接与输入准备路径,模型实现数据适配,具体契约要沿调用点确认。把握从中提到高。

### 漏了(两条,都来自论文)

**① 边是一等公民,我的章表把它当成了一个配置字段。** 论文 3.2 的核心抽象是 **stage graph**:节点是阶段,**边是用户自定义的 stage-transfer 函数**。论文明确区分三类用户要写的函数,并且说清了各自的调用频率:

| 函数 | 干什么 | 调用频率 |
|---|---|---|
| `forward` | 这一段的一次批前向 | 每步 |
| `preprocess` | 把上游产物拼进本段这一步的输入 | **每次迭代都调**(Talker 每个解码步都要拼 Thinker 的隐藏态) |
| stage-transfer | 段与段交接时变换并路由中间数据 | **只调一次**(`Thinker2Talker`、`Talker2Vocoder`) |

这正好落在代码的 `custom_process_input_func` / `custom_process_next_stage_input_func` 两个字段(`docs/configuration/stage_configs.md` 的 `StagePipelineConfig` 表)和 `model_executor/stage_input_processors/`(454 KB、35 项)上。**我原来把这 454 KB 划给了 15 章「模型集成层」,当成接模型的附属品**——但论文把它当成整个系统的编程模型。这是实打实漏了一章。

**② 连接器还管段内传输,并且 PD / EPD 是它的设计目标之一。** 论文 3.4 明说统一连接器同时处理 intra-stage 传输:prefill 与 decode 之间的 KV、encoder 与 prefill 之间的多模态缓存,并且「remains compatible with existing EPD disaggregation」。我在第三节把 PD 判成「检测在活路径但没有可跑的部署形态」,那个判断按代码仍然成立;**但我漏掉了「连接器接口本来就是为这类段内搬运设计的」这层意思**——论文说它的连接器是从 vLLM 的 PD KV 传输机制**泛化**来的,泛化对象包括嵌入、隐藏态、音视频张量。这条要写进连接器那一章,不能只当 PD 的落点。

### 视角不同(两条)

### 撞出来的两处事实修正
