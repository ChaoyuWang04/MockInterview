# KV与前缀缓存：复用边界与显存预算

这一页说明 omni 请求中的哪些状态可以复用,以及分页 KV、阶段输出和模型自带缓存分别由谁管理。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

前缀命中后,Thinker 可以跳过已经算过的 prefill。但 Talker 仍需要那段前缀对应的 hidden states:如果只保留 Attention 的 KV,本轮 forward 又只返回新 token 的输出,交给下游的条件就少了前半段。

另一个容易漏掉的是显存。除了引擎管理的分页 KV,codec decoder 可能自己保留 Transformers cache,CUDA graph 也可能持有缓存副本。这些状态的生命周期与并发倍率不同,只看分页池大小不能解释真实峰值。

**能否复用和由谁占用内存必须同时讲清。** 否则,前者表现为命中后下游输入不完整,后者表现为启动正常、并发上来却 OOM。

## 二、解法

对于适用的 AR stage,vLLM-Omni 在 vLLM 的 KV block 映射旁边维护一份**阶段输出镜像**。它缓存的是 hidden states 和符合逐 token 形状的多模态输出,不是再复制一份 Attention KV。命中时按同一组 slot 找回前缀输出,和本次新算的尾部拼接,让下游仍拿到完整条件。

![AR的GPU KV映射对应CPU阶段输出镜像,前缀输出与新尾部合并交给下游;Diffusion分页复用vLLM分配组件但拥有独立请求池,模型自带KV另行报告且不自动扣除预算](/opensource/vllm-omni/08a-cache-ownership.svg)

镜像存储 PrefixBlockPool 放在 CPU,支持时使用 pinned memory。它沿用 KV pool 的 slot 编号,底层 KV block 被复用后,对应输出行也会被新数据覆盖。OmniPrefixCacheManager 跟踪命中与输出合并,OmniPrefixCacheController 负责将本步输出搬到主机暂存区并写入镜像。这个设计补的是跨段输出完整性,不替代 vLLM 原有的多模态 encoder cache。

**复用有适用边界。** 当前输出镜像要求单个 full-attention KV group 和可对应的 block 布局。接收外来 KV 的阶段不能将其直接当作本地镜像命中;speculative decoding 等改变 token 位置记账的组合也被拒绝。不是有 KV 的地方都能打开这套镜像。

**Diffusion 复用的是分页基础组件。** 显式选择分页路径时,DiffusionKVCacheManager 包装 vLLM 的 KVCacheManager,为同一公开请求的 CFG 执行序列一起预留空间,不足时整体回滚。Worker 分配实际 KV Tensor,安装 Scheduler 给出的 block 信息。这里使用自己的池和请求状态,当前关闭跨请求前缀缓存;默认仍是原有的稠密 KV 路径。因此,“共用 vLLM 分页组件”不等于“AR 和所有 DiT 共用一个缓存池”。

**模型自带 KV 走申报协议。** 缓存的真正持有者声明每行几何尺寸、物理容量、生命周期和并发倍率,加载后由 runner 汇总报告。申报只描述占用,不负责分配,也不自动从分页预算再扣一遍。已经常驻的部分与请求到来后才增长的部分,必须结合实际显存测量区分。

## 三、代价

**节省 prefill 计算,增加主机内存与搬运。** 输出镜像按整个 KV pool 的 slot 容量为每个输出字段分配空间,并非只为当前命中的 token 分配。更大的 GPU KV pool 因而也可能带来更大的 CPU 镜像;暂存区另占主机内存,延迟写入的输出还会暂占设备空间。

**命中是一份一致性承诺。** KV 已命中而所需 hidden rows 不存在时,框架报错,不能悄悄当成普通 miss。新请求、取消与 block 复用之间需要维持镜像一致性,这也解释了为什么该能力有配置限制,随仓 Qwen3 部署仍保持关闭。

**分页预算不是整台卡的全部占用。** GPU Worker 用设备级 profiling 估算权重、激活峰值和其他占用,再计算可留给 KV 的空间。模型自带的逐请求 cache 可能在 profiling 后才出现;提高并发会增加这部分压力。相反,已在加载期常驻的 graph cache 不能再按申报总量重复扣除。

Qwen3-TTS 的流式 codec decoder 就同时申报保留在请求间分块中的 cache 和临时工作副本,二者都随最大并发数估算;graph 持有的副本另算固定项。不能把“请求级”或“进程级”几个字直接当作内存乘数。

## 四、与 sglang-omni 比较缓存的归属

对照核于 sglang-omni 基准 89e60d0bf2。两边都依赖底层 AR 引擎处理 KV,但本章的阶段输出镜像不能直接对应到对侧的所有缓存。

sglang-omni 的 AR cache factory 按配置选择 SGLang 的 RadixCache 系列或不做前缀匹配的 ChunkCache。其 Qwen3 image/audio encoder 另外建立 CPU StageOutputCache,按条目数和字节预算做 LRU 淘汰。

vLLM-Omni 此处的 PrefixBlockPool 则按 vLLM KV slot 存逐 token 的阶段输出,随 slot 复用覆盖,没有独立的条目级 LRU。前者例子缓存 encoder 结果,后者补齐因 AR 前缀命中而省略的输出行,两者的 key、粒度和失效条件不同。比较是否省算力之前,先确认缓存的究竟是哪一层结果。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

先按 stage 判断是否适用,再做复用收益对照。下面的 Qwen3 默认均指随仓部署,不是从底层 vLLM 的默认值推导。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `enable_prefix_caching` | 部署 YAML 顶层或每段 | Qwen3-Omni 三段均 `false`;Qwen3-TTS 两段也为 `false` | 适用 AR stage 开启后可复用前缀,增加输出镜像及复制开销 | 重复前缀耗时、输出完整性、镜像初始化日志 |
| `max_num_seqs` | 每段部署配置 | 本页 Qwen3-Omni/Qwen3-TTS 随仓各段为 64 | 降低可限制并发压力,也降低按并发申报的 model-local KV 峰值 | 排队、吞吐、`Model-local KV` 明细和运行峰值 |
| `gpu_memory_utilization` | 每段部署配置 | Qwen3-Omni 为 0.9/0.6/0.1;Qwen3-TTS 为 0.3/0.3 | 自动估算路径下,提高通常给分页 KV 更多空间,压缩其他用途余量 | `Available KV cache memory` 与实际峰值 |
| `max_num_batched_tokens` | 每段部署配置 | Qwen3-Omni 为 32768/32768/65536 | 更大的步级容量会放大输出缓存暂存区;不要将它当成请求数 | CPU pinned memory、每步 token 数与 prefill 耗时 |
| `kv_cache_memory_bytes` | 每段引擎配置 | 不指定时走自动预算;Diffusion 配置默认 `None` | 显式非零值直接指定 KV 字节预算,仍执行 warmup;不能继续依赖利用率比例自动留余量 | 启动预算日志、共置阶段合计显存 |
| `diffusion_kv_mode` | Diffusion 部署配置 | `dense_legacy` | `paged_scheduler` 选择 Scheduler 管理的分页路径,不自动开启跨请求复用 | 模型是否提供 KV layer/row 适配与初始化结果 |
| `diffusion_kv_max_rows_per_request` | Diffusion 部署配置 | `None` | 分页路径必须由模型适配给出正值,用于请求行容量;不应随意猜测 | 配置校验与 block table 初始化 |

输出镜像的常驻主机空间,每个字段约为“block 数 × block 大小 × 每 token 特征宽度 × 元素字节数”。这不包含 staging 与其他临时副本。`staging_depth` 等内部缓存设置不是部署 YAML 调参入口,不要为了缩减主机占用添加不存在的开关。

**观测分成两本账。** `prefix_cache: initialized mirror` 给出实际镜像形状与字段;`Model-local KV (outside the paged manager)` 给出申报峰值及各项 row 来源。前者帮助估算主机内存,后者是设备占用报告,都不能取代满并发测量。`OmniPrefixCacheUnmatchError` 指向命中/配置契约不成立,不应按普通低命中率处理。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| Qwen3-Omni,2×H100随仓放置,先建立基线 | 复制 `qwen3_omni_moe.yaml` 为 `qwen3-cache.yaml`,保留三段 `enable_prefix_caching: false`;运行 `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --deploy-config qwen3-cache.yaml` | 不增加阶段输出镜像,重复前缀仍需计算 |
| 同模型有重复前缀,评估 Thinker 复用 | 同一部署副本只把 stage 0 的 `enable_prefix_caching` 改为 `true`,其余两段保留 `false`,保持不使用外来 KV 和 speculative decoding | 用主机镜像与复制换取少做 prefill;先比较重复请求及输出,再验证目标并发下的 preemption 场景 |
| Qwen3-TTS 流式生成,先压低额外缓存峰值 | 复制 `qwen3_tts.yaml` 为 `tts-cache.yaml`,将两段 `max_num_seqs` 从 64 改为 16,保留前缀缓存关闭;运行 `vllm serve Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice --omni --deploy-config tts-cache.yaml` | 降低并发容量和按并发估算的本地 KV 占用,接受更多排队;固定 graph 项不会按相同比例下降 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 开缓存就初始化失败 | 是否单个 full-attention group,是否接收外来 KV 或使用 speculative decoding | 按异常说明关闭不适用 stage 的缓存,别只改 block 大小碰碰运气 |
| 首个真实请求后 CPU 内存陡增 | 新输出字段的镜像形状与暂存容量 | 分开核对常驻镜像和 staging,再评估收益是否值得 |
| 启动成功,满并发 OOM | model-local KV 中哪些项随并发增长 | 降并发或给动态状态留余量,再复测峰值 |
| 已命中却缺少上游 hidden states | 命中行与镜像是否一致,是否触发不支持的恢复路径 | 保留失败证据并关闭该阶段复用对照,不要把错误吞成 miss |
| 开启 Diffusion 分页后重复请求仍重算 | 当前 manager 是否启用跨请求缓存 | 将分页容量管理与前缀复用分开评价 |

## 六、常见误区

**看到 KV 命中,就认为下游已经拥有完整条件。** AR 引擎复用的是 Attention 状态,它不会因此重新产出被跳过位置的 hidden states。阶段输出镜像存在的原因,正是补上这部分。

**申报日志有总数,就以为引擎已自动预留同样多的额外显存。** 当前协议只汇总报告。把所有申报项重新扣掉会重复计算已经常驻的部分,完全不看报告又可能漏掉后续随请求增长的部分。

**调小 `max_model_len` 能同比缩小全部模型自带 cache。** 这很像分页 KV 的预算直觉,但 codec 的滑动窗口、模型内部循环和固定容量各有边界。应先看申报中的容量来源与 row 来源。

**图里都画成 block,所以 AR、DiT 和模型内部 cache 是同一个池。** 分页是组织方式,不是所有权证明。Diffusion 分页路径复用 vLLM 组件,模型内部 Transformers cache 仍由模型持有,AR 输出镜像则占主机内存;必须分别定位和核算。
