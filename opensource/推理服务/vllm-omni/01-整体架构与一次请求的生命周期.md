# 整体架构与一次请求的生命周期

这一页沿 Qwen3-Omni 的语音请求,说明不同阶段怎样接力、怎样提前开始下游计算,以及谁负责请求的开始与结束。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一次「听一段话、想一想、再用声音答」需要不同组件接力:Thinker 理解输入并生成文本,Talker 生成音频码,Code2Wav 将码还原成波形。最直观的实现是顺序调用,每一段结束后再把完整结果交给下一段。

这种整份交接的方式容易遇到三个问题。

**不同阶段难以按自己的节奏调度。** 如果把整个模型包在一个生成调用里,框架就难以分别控制每段的批处理和并发。即使各段已经用上独立引擎,整份交接仍会让下游等待上游完成;阶段内部有批处理能力,不等于阶段之间已经重叠执行。

**资源放置不够灵活。** 把所有组件固定在同一进程、同一张卡上,就难以单独给较重的阶段增加设备或副本。Thinker、Talker 与 Code2Wav 的负载不同,通常不适合只用一份整体预算来考虑。

**首个音频包等得太久。** Code2Wav 可以在拿到第一批音频码后开始工作。若一定等 Talker 生成整句音频码才交付,就把本可重叠的计算串行化了。

要解决的核心是:**让计算形态不同的阶段各自调度,同时让下游尽早拿到可用输入。** 前两段逐步 Decode,Code2Wav 则按收到的音频码还原波形,三者不需要共享同一种执行循环。

## 二、解法

把模型组织成明确的执行阶段,每段配置自己的执行方式、并发和设备放置,阶段之间通过模型提供的转换函数与传输组件交接数据。

拆开会增加搬运和协调开销,换来独立放置、调度以及重叠执行的空间。这个交换是否划算取决于模型、载荷与部署;共享内存可以服务单机交接,但不能据此把张量搬运视为没有成本。

先分清**服务启动**和**请求执行**。启动时,引擎通过 StageRuntime 准备阶段副本,加载模型并等待就绪。请求到来后,入口整理输入,引擎交给 Orchestrator,后者提交阶段请求、跟踪跨段状态并收集终端输出。StageRuntime 提供的是运行请求所需的副本,不是每条请求都要再穿过的一层计算。

**模型组件、阶段与 GPU 不是一一对应。** Qwen3-Omni 注册为 Thinker、Talker、Code2Wav 三段,后两段可以共置一张 GPU;共置不等于合并进程。另一些模型将文本编码、去噪和媒体解码封装在一个 Diffusion stage 内。模型若提供不同的注册结构,部署配置可以选择它们,但不能任意把三个 stage 变成一个 stage。

**控制面先准备请求,数据面再持续供给分块。** 开启流式分块后,Orchestrator 预先提交下游请求并绑定副本,OmniConnector 随着上游计算交付数据。下游有了可用分块就能开始,不必等完整结果。对于这种接收分块的边,Orchestrator 跳过重复的完成时转发,仍负责请求跟踪、取消和结束。

## 三、代价

**启动和生命周期管理更复杂。** 多个阶段要加载权重、准备设备资源并等待就绪。能并行初始化的部分与必须顺序初始化的部分共同决定启动耗时;例如共用设备的阶段可能需要顺序准备,不能只取最慢单阶段的耗时。

**一条请求的状态散在多处。** 取消、超时和错误需要传到关联阶段。某个副本死亡时,框架摘除它并让绑定其上的请求失败;该阶段仍有可用副本时,后续请求才能继续服务。

**编排自身有开销。** 默认是轮询:Orchestrator 循环检查各阶段副本的输出。事件驱动路径可以显式启用,但不是默认行为。阶段和副本数量增多时,需要关注编排进程的 CPU 开销。

**传输成本随后端变化。** 共享内存路径涉及主机内存与设备之间的数据搬运;部分平台后端支持设备内存直接传输,例如 NPU 上的 Yuanrong Transfer Engine。载荷大小、序列化和分块次数都会影响开销。

**调参面变成多份。** 每段有自己的参数,部署还可能按硬件平台覆写。共置时需要合起来考虑显存与计算竞争,不能把每段的配置孤立看待。

**收益要对应负载。** 纯文本单阶段服务未必需要多阶段编排;但单阶段 Diffusion 仍能使用本项目的扩散执行栈与服务接口。因此不能把“只有一段”直接等同于“使用它没有收益”。

## 四、和 sglang-omni 不一样的 4 处

两边都用多阶段服务组织 omni 模型。这里比较下一跳决策、数据转换、流式交接和服务能力这四件事;参照项目基准为 89e60d0bf2,具体调用点记在底稿。

**下一跳决策。** vLLM-Omni 的普通完成时转发主路径按相邻阶段号推进。sglang-omni 的 Stage Runtime 根据阶段路由选择下一跳。后者的 Coordinator 仍掌握入口、终端与副本信息,只是下一跳选择不集中在它里面。

**段间数据转换。** vLLM-Omni 在阶段配置中接入整份交接、分块交接和下游输入准备的处理函数;sglang-omni 把接收数据的整理放在下游阶段的输入侧。两边都需要模型适配,区别在框架从哪里调用它,本项目的具体契约见第 03 章。

**流式交接。** vLLM-Omni 提前提交下游,收到分块后开始计算,并避免在上游完成时再次提交同一交接。sglang-omni 将流式数据与完成结果分成不同路径处理。不能把这个差异理解为某一边开启流式后就没有控制面了。

**服务能力。** vLLM-Omni 从阶段推导支持的任务,再结合端点策略限制公开接口。sglang-omni 使用模型能力声明参与服务接口选择。内部能执行一种任务,和服务是否开放对应接口,在两边都需要区分。

![两个运行时按下一跳决策、段间转换、流式交接和服务能力逐项对照,比较的是处理职责与调用位置,不把框架规则与模型声明视为互斥分类](/opensource/vllm-omni/01b-vs-sglang-omni.svg)

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。部署文件可能按硬件平台覆写,读的时候要把顶层与对应平台的设置一起看。

**先看放置和交接,再看性能参数。** 流水线结构由模型注册,部署 YAML 的 `pipeline` 可以选择已提供的结构变体;设备、并发与传输方式则属于部署配置。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--omni` | 命令行 | 关 | 打开 omni 服务路径;`vllm-omni serve` 同样需要它 | 启动日志是否进入 omni 引擎与 Orchestrator |
| `--deploy-config` | 命令行 | 按模型选随仓配置 | 选择阶段放置与运行参数 | 启动时的配置与阶段日志 |
| `--stage-init-timeout` | 命令行 | 300 秒 | 增大可容忍更慢的阶段初始化 | 超时报错中的阶段号 |
| `--omni-lb-policy` | 命令行 | `random` | 改变同一阶段的副本选择策略 | 请求分布与副本负载 |
| `--omni-heartbeat-timeout` | 命令行 | 30 秒 | 调整对副本失联的容忍时间 | 副本摘除日志 |
| `async_chunk` | 部署配置顶层 | 按模型;本例为 `true` | 允许上下游重叠执行;关闭则走整份交接 | 首个音频包时间与阶段活动 |
| `devices` | 部署配置每段 | 按模型 | 决定阶段放在哪些设备,同设备表示共置 | 阶段启动日志 |
| `gpu_memory_utilization` | 部署配置每段 | 按模型 | 改变阶段的显存预算;共置时要合计并留余量 | 显存占用、初始化是否成功 |
| `max_num_seqs` | 部署配置每段 | 按模型 | 改变阶段并发容量 | 阶段指标、吞吐与等待时间 |
| `enforce_eager` | 部署配置每段 | 通常为 `false`,可能有平台覆写 | 关闭图捕获,影响启动及执行性能 | 启动日志与实际时延 |
| `input_connectors` | 部署配置每段 | 单机通常自动配置共享内存 | 选择上游数据来源与传输通道 | 连接器初始化与传输日志 |
| `VLLM_OMNI_EVENT_DRIVEN_ORCH` | 环境变量 | 关 | 启用事件驱动编排路径 | CPU 占用与请求时延 |
| `--enable-orch-monitor` | 命令行 | 关 | 收集编排循环及副本窗口统计 | 退出清理时写出的 JSON |
| `VLLM_OMNI_ORCH_MONITOR_PATH` | 环境变量 | 启用监控后自动命名 | 改变上述监控文件路径,本身不启用监控 | JSON 的 `windows` 与 `replicas` |
| `VLLM_OMNI_ABORT_TIMEOUT` | 环境变量 | 2 秒 | 调整中止请求的等待上限 | 取消过程与各阶段日志 |
| `VLLM_OMNI_INPUT_WAIT_TIMEOUT_S` | 环境变量 | 600 秒;0 关闭 | 调整阶段等待上游输入的上限 | 输入等待超时报错 |

**观测点三处**:启动日志确认结构与放置;阶段指标帮助区分等待与计算;Orchestrator Monitor 记录循环活动、副本输出队列积压和在途请求数。监控 JSON 不是实时的逐请求轨迹,输出队列长度也不等于调度等待队列长度。

**三个配置方向**:

| 场景 | 从哪里开始 | 拿什么换什么 |
|---|---|---|
| Qwen3-Omni 三段语音,双卡 CUDA 部署 | `qwen3_omni_moe.yaml` 标注验证环境为 2×H100;stage 0 独占一张卡,stage 1、2 共置另一张,`async_chunk: true` | 以分块协调换取更早的音频输出;其他设备需重新确认容量 |
| 只需要理解与文本输出 | 选用模型提供的 Thinker-only 结构及兼容 checkpoint | 不启动语音链,降低资源需求,不再输出语音 |
| 对照排查流式结果问题 | 在支持两种交接路径的模型上比较 `async_chunk: false` 与 `true` | 接受整份交接的等待,便于对照上游结果与转换过程 |

这些是理解配置取舍的起点,不是实测最优参数或适用于所有模型的部署配方。

| 症状 | 先查 | 然后 |
|---|---|---|
| 服务卡在初始化 | 哪个阶段未就绪 | 检查权重、设备和显存,再判断是否需要增大超时 |
| 首个音频包很慢 | 是否启用分块,各段何时开始工作 | 再检查 Talker 到 Code2Wav 的分块与等待 |
| 单独运行够显存,共置却失败 | 同设备各段的预算与额外占用 | 留出余量或调整放置 |
| 副本报错后阶段不可用 | 是否还剩健康副本 | 区分单请求错误、副本死亡与整个阶段无可用实例 |
| 改配置但行为没变 | 对应平台是否有覆写 | 查看启动时真正生效的配置 |
| 监控文件没有出现 | 是否开启 `--enable-orch-monitor` | 核对输出路径及是否执行正常退出清理 |

## 六、常见误区

**看到上游来源是列表,就以为支持任意 DAG 调度。** 配置能描述来源,不等于运行时实现了任意分支与汇合。当前普通完成时转发的主路径按相邻阶段推进;设计新拓扑前要确认实际路由支持,不能仅凭字段形状判断。

**换成本包命令,就以为不用加 omni 开关。** `vllm-omni serve MODEL --omni` 与官方常见的 `vllm serve MODEL --omni` 都需要开关。模型注册插件负责让 worker 识别模型架构,不要把这件事和 CLI 分流混成一个机制。

**第一个终端有结果,就认为整条请求结束。** 同时请求文本和音频时,Thinker 与 Code2Wav 都是终端,Talker 则不是。要等本次请求所需的终端完成,不能在文本先返回时截断仍在生成的音频。

**看到完成时转发被跳过,就认为下游不再由 Orchestrator 管理。** 流式路径已提前提交并绑定下游,数据由 OmniConnector 持续供给。读代码时应同时看预提交与完成处理,只看后者会漏掉控制面的前半段。

**模型能生成某种输出,对应 API 就一定开放。** 引擎推导的任务能力还要经过端点策略约束。例如 Qwen3-Omni 的对话交接需要聊天模板,不能据文本生成能力就认定所有文本接口都可用。

**默认编排是事件驱动,于是忽略编排进程的 CPU。** 当前默认轮询;事件驱动需要显式开启。检查多阶段服务瓶颈时,除了 GPU 执行,也要看输出处理与编排是否积压。
