# 模型集成层：接一个新模型要做什么

这一篇看模型怎样把自己的计算交给公共运行时：注册负责找到实现，执行、数据、权重与能力契约决定它能否被正确调用。

说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题：能找到模型类，不等于能完成请求

Qwen3-Omni 的 Thinker 能单独生成文字，但整条语音链还需要 Talker 接到正确的条件，再由 Code2Wav 把 codec 变成 waveform。把模型类放进 Registry，只解决“去哪里实例化”。公共运行时还需要知道：哪段逐 token 执行，哪段一次生成；模型输出里哪些是用户结果，哪些是下游条件；checkpoint 的哪些权重属于当前段。

这里最容易漏掉的是**两个局部正确之间的接口**。Thinker 文字正确，并不能证明 Talker 拿到了对应的 hidden states；Code2Wav 单独解码正确，也不能证明它拿到的 codec 排列、请求长度和结束信号一致。接入工作的完成单位因此是可执行的契约闭环，而不是一个能 import 的类。

这一章只看模型如何兑现这些契约。Pipeline 的配置合并在第 02 章，段间 payload 的转换机制在第 03 章；这里不再展开模型的 Attention、MoE 或扩散方程。

## 二、解法：让每个阶段只承担自己声明的执行与数据责任

### 找到实现，也找到它适用的拓扑

vLLM-Omni 的模型 Registry 把 architecture 映射到可延迟加载的模型类；Pipeline Registry 则把模型类型映射到阶段拓扑，也允许根据 checkpoint 配置选择变体。Qwen3-Omni 就用后者区分完整语音链与 Thinker-only：关闭音频输出的 checkpoint 不需要启动另外两段。

进入一个阶段后，同一个 Qwen3-Omni wrapper 只实例化该段对应的子模型。Thinker、Talker 接受 AR 运行路径，Code2Wav 接受 generation 运行路径；wrapper 的前向也只执行当前段。**模型不会在自己的前向里启动下游模型**，跨段调度仍由公共运行时负责。这样同一组 checkpoint 可以服务不同拓扑，而模型实现不必嵌入进程安排。

![Qwen3-Omni 的各阶段分别兑现执行、payload 和权重契约，QwenImage 则通过自动生成的单阶段拓扑进入扩散运行时。](/opensource/vllm-omni/16a-model-contracts.svg)

### 输入与输出要在实际调用点接上

Qwen3-Omni 的多模态输入 Processor 绑定在模型类上，负责入口图片、音频等数据的处理；阶段之间的 Processor 是另一套职责。Thinker 输出文字相关 hidden states，同时提供 Talker 所需的中间表示和特殊 token embedding；Talker 输出 codec；Code2Wav 最终返回 waveform 与 sample rate。不能把“入口支持音频”当成“下游自动理解所有输出”。

这些转换函数不是留在模型目录里的说明。Pipeline 声明选用哪种转换路径，Connector 的传输适配器加载相应函数，并把当前请求、模型输出和结束状态传给它。Qwen3-Omni 的异步转换会等待足够的条件或 codec 再产生 payload，缺少必要条件时可以暂不发送。因此接入验收必须经过真实调用链，同时覆盖普通输出、首个 chunk 与结束时的尾部输出。

### 权重归属与运行接口一起确定

Qwen3-Omni wrapper 按 Thinker、Talker、Code2Wav 的 checkpoint 前缀分组，只把对应权重交给当前已实例化的子模型，再汇总已装载的参数名。名称映射也要反映实际模块嵌套。能创建空模型并通过一次前向，并不能证明 checkpoint 的参数落到了正确位置。

QwenImage 给出另一种接入形态：其扩散 Pipeline 类在扩散 Registry 中注册，框架可以自动生成单阶段拓扑，不需要为它再手写一份多阶段 Pipeline 或段间 Processor。QwenImage 声明 DiT 的权重来源交给公共 Loader，encoder、VAE、scheduler 和 tokenizer 则在构造时按各自子目录加载。这是该模型的装载分工，不应推广成所有模型都必须采用的唯一 Loader 模板。

### 能力需要逐项兑现

QwenImage 还声明组件位置、请求 batch 与 step execution 支持，并提供分步执行的方法。运行时会检查请求 batch 能力；step execution 也有独立的接口和能力判断。注册成功并不会自动得到这些能力，更不会自动保证 Parallel、Cache、Offload 的任意组合成立。

外围适配同样属于契约的一部分：自定义 Transformers 配置和 tokenizer 解决 checkpoint 的读取与文本解释；Plugin 让子进程也能获得注册；模型 extras 集中表达额外请求字段和模型专属输入构造，避免公共入口持续增加按模型名分支。World Model 的实验性适配又多了一层 session state 契约，当前接口仍可能变化，不能把这层存在解释为所有模型都获得了持久会话能力。

## 三、代价：复用运行时，换来跨边界的一致性责任

这种分工减少了每个模型重复实现调度、通信和服务接口的需要，却把正确性要求放在多个边界上。修改 Talker 的条件格式，就要同时核对 Thinker 输出和转换函数；改变模块嵌套，也要检查权重映射、量化匹配与组件发现。局部重构可能不改变模型数学，却仍然破坏整条请求。

注册还要跨进程生效。主进程里手动 import 成功，不代表执行模型的 worker 已有相同映射。vLLM-Omni 通过上游通用 Plugin 入口注册自己的模型实现；Omni 自己也有 Plugin 加载入口。重复加载、依赖缺失和名称覆盖因此都属于接入边界，而不是服务启动以后的偶发细节。

测试成本也随声明的能力增加。最小请求验证普通前向，batch 验证输出归属，流式请求验证首尾和结束，分步执行还要与完整请求路径核对结果。把所有能力声明一次性复制过来，会扩大必须证明的范围。更稳妥的接入顺序是先闭合最小可运行路径，再逐项开放已验证的能力。

## 四、对照 SGLang-Omni：同样拆开发现与执行，入口组织不同

在固定对照基准中，SGLang-Omni 会扫描模型包的配置模块，通过统一入口类收集 architecture 及 alias，形成 Pipeline Config Registry；Qwen3-Omni 的语音配置由各阶段 factory 描述组件构造。底层 SGLang 模型的注册则发生在 Model Runner，包含 Thinker、Talker 等实现。

vLLM-Omni 的主线是显式模型映射、独立的 Pipeline 映射与 vLLM Plugin 注册，Qwen3-Omni wrapper 再按阶段选择子模型。两边都需要把“发现一个模型”与“以正确接口执行一个阶段”接起来。差别在注册和阶段构造的位置，不能从目录更集中或类更少推出接入工作更少；两边都必须验证数据、装载与执行契约。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

模型接入首先改声明和实现，部署参数只能选择已存在的路径，不能补出缺失的能力。下表区分启动时读取的模型声明和用户部署选项；声明字段不是可任意改写的服务调优旋钮。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--deploy-config` / `pipeline` | 启动 CLI / deploy YAML | 不指定时按模型发现拓扑；Qwen3 完整链带内置 deploy | 显式选择已有拓扑，如 Thinker-only | 启动的 stage 数、输出 modality 是否符合目的 |
| `execution_type` | 模型 `StagePipelineConfig` 声明 | `LLM_AR`；Qwen3 Code2Wav 显式 `LLM_GENERATION` | 确定阶段执行路径；扩散显式 `DIFFUSION` | runner/scheduler 类型与前向输入输出是否相符 |
| `custom_process_next_stage_input_func`、`async_chunk_process_next_stage_input_func` | 模型 Pipeline 声明 | 均为 `None`，Qwen3 显式提供 | 为传输路径绑定模型自己的转换函数 | 缺 tensor、空 payload、尾部未发出的日志 |
| `async_chunk` | deploy YAML | `DeployConfig` 为 `true`；Qwen3 内置配置显式开启 | 选择异步 chunk 转换；关闭后要有相应完整 payload 路径 | 首音与结束是否完整，不只看文字结果 |
| `supports_request_batch`、`supports_step_execution` | 扩散 Pipeline 类声明 | 请求 batch 检查的缺省为不支持；step 需声明且满足协议，QwenImage 均开启 | 允许框架调用相应能力接口 | batch 输出按请求分离、step 路径能否通过能力检查 |

下面是接入回归的语义起点，复用已有模型与已存在的启动方式，不代表新模型能直接套用这些配置。

| 模型与硬件场景 | 启动配方 | 优先验证的契约 |
|---|---|---|
| Qwen3-Omni Instruct，2 × H100，复核完整文字与语音链 | `CUDA_VISIBLE_DEVICES=0,1 vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --port 8091` | 内置布局把 Thinker 放卡 0、Talker 与 Code2Wav 放卡 1；用 Chat 请求验证文字、首音和尾音 |
| 同一 Instruct，2 × H100-80G，只验证 Thinker 接入 | 上述命令加 `--deploy-config vllm_omni/deploy/qwen3_omni_moe_thinking.yaml` | 已有配置用 TP=2，只启动 Thinker；无音频输出是所选拓扑的结果 |
| QwenImage，单张 H100 80GB，先验证普通图像请求 | `vllm serve Qwen/Qwen-Image --omni` | 验证自动单 stage、组件装载和图像返回；80GB 是参照文档所列约 60GiB 基础峰值留余量的起点，并非该卡实测 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 主进程能识别，worker 报 architecture 不支持 | Plugin 是否在该进程加载、映射是否指向 Omni 类 | 再查延迟 import 的依赖错误，别只重复添加 Registry 项 |
| 文字正常，语音迟迟不来 | 当前是否 Thinker-only、输入是否经过 Chat template | 完整链再查 Thinker 条件缺失、Talker codec 与尾部 payload |
| 参数已下载，输出却异常或提示未装载 | checkpoint 前缀、实际模块路径、已装载参数集合 | 分别核对当前 stage 和组件来源，不能用下载完成代替装载验收 |
| 单请求通过，batch 或 step 报不支持 | 能力声明与对应方法是否真的存在 | 用相同模型输入分别回归普通路径和扩展路径 |
| 特殊 tokenizer 或请求字段不生效 | 自定义配置/tokenizer 注册、模型 extras 的类名映射 | 再查消费这些声明的入口，避免把问题移成公共服务层的模型名分支 |

## 六、常见误区

**“两个 Registry 加完，再给每个模型复制 Pipeline 和 Processor 就齐了。”** 多阶段示例很容易让人形成这个印象，但单阶段扩散已有自动拓扑，简单路径也未必需要段间转换。先确定真实阶段边界，再决定哪些声明和转换必须新增。

**“同一个 wrapper 意味着每个阶段加载整套模型。”** 类名相同会造成这种错觉，Qwen3-Omni 实际按当前 stage 构造子模型并分派权重。类复用与运行时权重归属是两件事。

**“模型有前向方法，就可以声明支持所有调度与优化能力。”** 普通前向只覆盖一种调用形态。请求 batch、分步执行、流式输出及组件发现各有额外契约；注册成功不是这些能力的替代证明。

**“辅助目录只是杂项，不影响接入是否完成。”** tokenizer 解释错特殊 token、子进程漏注册、extras 未被入口读取，都可能在数学实现正确时让请求失败。它们不属于模型算子，却仍在模型可服务的闭环上。
