# vLLM-Omni 总览

源码基准:官方仓库 <https://github.com/vllm-project/vllm-omni>,分支 `main`,commit `4d877780d38cbf93e273aef73e99a100d38e2768`,最近的发布 tag `v0.29.0rc1`,核对日期 2026-09-20。全篇的「当前」「默认」都指这组基准;标了「官方文档说法」的来自仓库内的设计文档,没有实测。

## 一、vLLM-Omni 是什么

**vLLM-Omni** 是 vLLM 社区维护的多模态服务运行时。它和 vLLM 不是竞争关系而是扩展:vLLM 当初是为文本自回归生成设计的,一个模型、一种执行循环、输出是一串 token;vLLM-Omni 要服务的模型,一次生成会穿过计算形态完全不同的几段——先用编码器把图像和音频变成条件,再用自回归模型想出内容,再用另一个模型把内容变成音频码本,最后用声码器还原成波形;或者干脆没有自回归这回事,几十步去噪直接出一段视频。

这些段的差异不只是大小不同。自回归段逐 token 生成,依赖 KV Cache 和连续批处理;扩散段反复去噪,需要适合去噪步的调度与注意力实现;编码器负责把输入变成条件;声码器按块还原音频,影响首包延迟。它们对调度、并行和显存的需求不同,**一套执行策略盖不住**。部分扩散模型也有 KV 状态,但不能直接套用文本生成的前缀复用假设。

vLLM-Omni 的回答是把**阶段**作为部署与执行的组织单元:模型实现声明有哪些阶段、如何交接,部署配置决定设备放置、副本数量和运行参数。模型可以提供不同的已注册结构,例如完整语音流水线与 Thinker-only 变体,由配置解析选择;这不意味着任意模型都能自由拆成自回归、扩散或二者组合。

一句话定位:**vLLM-Omni 为多模态模型提供统一服务,用阶段化执行组织不同计算形态,用段间转换与传输连接它们,并在 vLLM 执行能力之外提供完整的扩散执行栈。** 它既能服务多阶段语音模型,也能服务单阶段的图像、视频和动作生成模型。

顶层入口(包根 `vllm_omni/`):

- `Omni(...)` / `AsyncOmni(...)`:离线与异步推理的 Python API,入口在 `entrypoints/omni.py` 与 `entrypoints/async_omni.py`。
- **`vllm serve <模型> --omni`**:启动 OpenAI 兼容 HTTP server,入口 `entrypoints/openai/api_server.py`。本包也提供 **`vllm-omni serve <模型> --omni`**;使用本包命令时同样需要 `--omni`。此外,模型注册插件让 vLLM worker 识别 omni 模型架构,这是独立于命令分流的接入机制。
- `DuplexOmni`:全双工实时服务,以会话持续处理输入和输出,入口 `entrypoints/duplex_omni.py`。serve 选择这条路径需要模型提供双工插件,且实际会话模式为 `duplex`;仅声明插件不会自动开启。
- `entrypoints/openpi/`:机器人动作策略的服务面,和上面三条并列。

代码组织上,运行时集中在 `vllm_omni/`:模型实现在 `model_executor/models/` 与 `diffusion/models/`,框架主线在配置、引擎、阶段运行时、段间传输和扩散运行时。平台适配不单独成章,但涉及硬件能力的结论需要核对 `platforms/` 的实际实现;ComfyUI 插件作为独立产品不展开。

## 二、7 个招牌:先建立全局图景

```text
客户端:HTTP / WebSocket / Python API
                    │
                    ▼
       AsyncOmniEngine:装配引擎、提交请求、收集输出
          │                               │
          ▼                               ▼
 Orchestrator:推进请求             StageRuntime:管理副本
 路由、取消、输出与完成             进程启动、就绪与关停
          │                               │
          └───────────┬───────────────────┘
                      ▼
 [1] PipelineConfig 定义结构;DeployConfig 选择结构变体与设备放置
                      │
                      ▼
 [3] 执行体系:AR / generation 执行路径 + Diffusion 执行栈
                      │
       上游阶段 ── [2] 模型提供的数据转换 ── 下游阶段
           └──── [5] OmniConnector 搬运中间数据 ────┘
                [4] 流式分块让上下游执行重叠
                      │
                      ▼
           文本 · 音频 · 图像 · 视频 · 动作

 [6] KV 管理与前缀缓存:按模型与执行路径提供状态管理和复用
 [7] 实时全双工:常驻会话,持续接收输入并产生输出
```

一句话记忆:

- **[1] 结构与部署分离**:模型声明阶段结构,用户配置放置与运行参数,也可选择模型已提供的结构变体。
- **[2] 段间数据转换**:模型提供处理函数,把隐藏态、音频码等上游结果变成下游输入;整份交接与流式分块有不同调用路径。
- **[3] 多种执行形态**:AR 与 generation 路径扩展 vLLM,Diffusion 有自己的执行栈;扩散既可整请求执行,也可按步调度。
- **[4] 阶段执行重叠**:上游边算边交付,下游收到可用分块就能开始,减少等待整份结果的时间。
- **[5] OmniConnector**:统一承载阶段间的张量、KV 与传输元数据,覆盖单机与跨节点传输。
- **[6] KV 管理与前缀缓存**:多模态输入可参与前缀匹配,模型自带 KV 提供显存申报与诊断,部分扩散路径复用分页 KV 基础设施;实际启用取决于模型与配置。
- **[7] 实时全双工**:引擎维持常驻会话,持续处理输入与输出,线上协议与模型执行解耦。

## 四、一条请求怎么串起来

以 Qwen3-Omni 的语音问答为例。Thinker 理解输入并生成文本和给下一段的条件;Talker 生成音频码;Code2Wav 将码还原成波形。随仓 CUDA 配置把 stage 0 放在一张 GPU,stage 1、2 共置在另一张 GPU,并默认开启流式分块。

1. **入口**收到带音频的请求,整理成引擎能处理的输入。
2. **引擎与 Orchestrator**提交 Thinker 请求,建立跨阶段关联。流式模式下,Orchestrator 还提前向下游提交占位请求并绑定副本,让下游准备好接收分块。副本的启动和就绪由 StageRuntime 负责。
3. **Thinker**把多模态输入编码成条件,执行 Prefill 与 Decode,产生文本并为 Talker 提供条件。项目支持前缀缓存,但这份默认部署配置将其关闭。
4. **Talker**接收经过转换的上游数据,逐步生成音频码。OmniConnector 把分块交给下游,不必等整句生成完。具体输入准备与数据转换在第 03 章展开。
5. **Code2Wav**在收到足够的音频码后生成波形。该配置的常规分块为 25 帧,首块基准为 4 帧,用于提早输出音频。
6. **输出**来自 stage 0 的文本与 stage 2 的音频;stage 1 不是用户可见的终端。实际返回哪些模态取决于请求,Orchestrator 跟踪所需终端的完成情况,入口将结果封装为响应。

这里降低首包等待的关键是**执行重叠**:下游在上游结束之前就能开始计算。代价是分块、数据转换和取消都要跨阶段协调;块长也会影响等待与搬运开销。

图像或视频模型则可以将文本编码、去噪和媒体解码封装在一个 Diffusion stage 内。模型内部组件不等于框架注册的 stage,不能仅靠改设备配置任意拆开。仓库中的动作生成模型也使用扩散/流匹配相关执行路径,不需要额外创造第四套框架执行栈。

## 六、怎么调它、怎么看它

**配置有两个来源,职责严格分开。**

| 来源 | 谁拥有 | 能改什么 | 在哪 |
|---|---|---|---|
| `PipelineConfig` | 模型实现,注册进 `OMNI_PIPELINES` | 有哪几段、`execution_type`(`LLM_AR` / `LLM_GENERATION` / `DIFFUSION`)、谁的输出喂给谁、哪段是终端输出、哪段拥有分词器 | `model_executor/models/<家族>/pipeline.py` |
| deploy YAML | 用户 | 每段的 `devices`、`gpu_memory_utilization`、`max_num_seqs`、`max_num_batched_tokens`、`enforce_eager`、`tensor_parallel_size`、`enable_prefix_caching`、采样默认值、段间用哪个连接器 | `vllm_omni/deploy/*.yaml`,`--deploy-config` 指定;不给就按流水线里的 `default_deploy_config_name` 自动加载 |

**部署配置不能任意增删阶段**,但 `pipeline` 可以选择模型已注册的结构变体。选定结构后,再覆写放置和运行参数。

两个容易忽略的点:

- **按平台分节覆写**。部署配置里可以写 `platforms:` 段,按 `cuda` / `musa` / `npu` / `rocm` / `xpu` 分别覆写某几段的参数。Qwen3-Omni 的随仓配置就用它给 ROCm 把第 2 段改成逐算子执行,给 NPU 换成分段图并改了张量并行度。看一份部署配置时不要只看顶层的 `stages:`。
- **段间连接器在段上声明**。每段用 `input_connectors` 写明从哪一段收、用哪个连接器;连接器本身在顶层 `connectors:` 里定义。单机不写就自动用共享内存。

**七种连接器怎么选**(官方文档说法):

| 场景 | 用哪个 | 备注 |
|---|---|---|
| 单节点 | `SharedMemoryConnector` | 不指定时自动选它 |
| 多节点,TCP | `MooncakeStoreConnector` | 要 Mooncake Master 和元数据服务 |
| 多节点,RDMA | `MooncakeTransferEngineConnector` | 带托管内存池,官方文档标为最快 |
| 多节点,RDMA | `MoriTransferEngineConnector` | 走 Mori IOEngine |
| 多节点 | `NixlConnector` | UCX 上的 NIXL READ,唯一覆盖 Intel XPU 的后端 |
| 多节点 | `YuanrongConnector` | 使用 Yuanrong Datasystem 与 etcd |
| 多节点,NPU | `YuanrongTransferEngineConnector` | 使用 Transfer Engine 与 NPU 内存池,不同于 Datasystem 路径 |

传输路径随后端与载荷变化:共享内存等路径涉及主机内存,NPU 上的 Yuanrong Transfer Engine 则支持设备内存直接传输。不能把一种连接器的拷贝路径套到所有后端。

**观测**:指标走 Prometheus,按阶段打点;请求级剖析器和框架剖析器各管一层;硬件覆盖 CUDA、ROCm、MUSA、NPU、XPU,但各平台支持的特性不同,部署配置里的平台分节就是在补这些差异。

## 七、阅读顺序

**只想建立主线**:01(整体架构)→ 02(配置)→ 03(段与段之间那道缝)→ 06(段间传输)→ 09(扩散执行栈)。这五章讲完「一次请求怎么穿过若干段」「段与段怎么交接」和「扩散段和自回归段到底差在哪」。

**要上手部署**:01 → 02 → 06 →(按模型类型)07、08 或 09 → 14(接口面)。想调性能再加 10–13。

**要接一个新模型**:01 → 02 → **03** → 16,再按模型形态读 07 或 09。03 章是这条线的重点——模型如何接入框架的数据交接路径在这里展开。

**和 sglang-omni 对着读**:两个项目在同一个领域解同一类问题,但切法不同。sglang-omni 把自回归那段整个外包给 sglang,自己专注多阶段编排,覆盖面集中在语音与 omni 对话;vLLM-Omni 同样把自回归外包给 vLLM,但**额外自建了一整套扩散执行栈**,于是覆盖面伸到图像、视频和机器人动作。这个差别决定了两边的章表形状:sglang-omni 的重心在调度与流水线拓扑,vLLM-Omni 的重心有一半落在扩散怎么跑得快。各章第四段的对比就沿这条线展开。

## 八、术语表

| 词 | 一句话 |
|---|---|
| 阶段 | 有自己的模型组件、执行策略、资源归属与性能目标的逻辑执行单元;不一定是一个进程 |
| 阶段图 | 这个系统对模型的表示:节点是阶段,边是把上游产物变成下游输入的函数 |
| 段间变换函数 | 把上游产物转换成下游数据的模型处理函数,整份交接与流式分块的调用方式不同 |
| 输入预处理函数 | 按对应模型的执行路径整理下游输入的函数 |
| 流水线配置 | 模型自己的 Python 定义,定义有哪几段、谁喂给谁;部署可选择已注册变体,不能任意改写其内部结构 |
| 部署配置 | 用户写的 YAML,选择已提供的结构变体,并配置阶段放置、显存、批处理与连接器 |
| 执行类型 | 阶段的三种形态:LLM_AR、LLM_GENERATION 和 DIFFUSION;Generation 可以返回波形等载荷,不必采样 token |
| 编排器 | 拥有跨段请求状态、路由、取消与输出顺序的那个组件 |
| 阶段运行时 | 把逻辑阶段展开成副本并管进程生命周期的那个组件 |
| 连接器 | 段间搬张量与 KV 的统一契约,7 种实现;只传输,不决定下一段 |
| 阶段执行重叠 | 上一段边算边把部分结果吐给下一段,下一段不等整段算完就开工 |
| 扩散主干 | 去噪网络本身,对应文本模型里的 Transformer 主干 |
| 整请求批 / 步批 | 扩散的两种批处理模式:一次前向做完整条请求,或每个调度周期推进一步去噪 |
| 跳步缓存 | 利用相邻去噪步的相似性跳过部分计算的一类加速手段 |
| 换出 | 把权重从显存挪到主机内存,用时再搬回来;分整模型、按层、按层且跨卡三档 |
| 主机侧权重运行时 | 让同机多个 worker 复用同一份已经加载并转换好的权重表示 |
| 首包时间 | 从收到请求到吐出第一个流式媒体包(通常是音频)的时间 |
| 实时因子 | 生成一秒音频所花的墙钟时间;小于 1 表示快于实时 |
| 全双工 | 边听边说,不需要按住说话;要有轮次判定 |

分页 KV、连续批处理、前缀缓存、张量并行、混合专家、量化这些通用机制在知识库 `04-Infra/01-原理/` 下各有一篇,本解读只写这个项目怎么用它们。
