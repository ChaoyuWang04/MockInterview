# 段间转换：框架与模型的分工

这一页说明上游产物怎样变成下游可计算的输入,以及框架与模型适配各自负责什么。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

Thinker 能生成文本,不代表把文本交给 Talker 就能恢复原模型的语音生成过程。Qwen3-Omni 的 Talker 还需要 Thinker 的 embedding 与 hidden states;Code2Wav 则需要按 codebook 排列的音频码。这些都不是一次普通文本请求能完整表达的输入。

问题也不只是传多少字节。下游 scheduler 要知道该为输入预留多少位置,模型要知道哪些张量是条件、哪些是新生成的内容,分块解码还要知道哪些音频码属于左侧上下文。**传到了错误形状或错误边界的数据,会让下游等待、错配位置,或者生成错误音频。**

因此,段间转换解决的是“上游已经算完了什么,下游接下来究竟能算什么”,而不是简单改一下字段名。

## 二、解法

把**下游请求准备**与**模型载荷准备**分开。请求准备让框架能提交和调度下游工作;载荷准备则把上游张量整理成下游模型理解的内容。两者可以走不同路径,最终在下游会合。

在 Qwen3-Omni 的整份交接中,Orchestrator 调用 Talker 的输入处理函数,按文本结构计算所需位置数,生成占位 token。真正的 embedding 与 hidden states 由上游 worker 一侧打包,经 OmniConnector 送达。占位 token 用来安排计算,并不替代语音条件张量。

![整份交接中请求占位与条件张量分路进入下游,分块交接中模型处理器积累并切分载荷,框架提前建立下游请求并传递结束标记](/opensource/vllm-omni/03a-stage-handoff.svg)

图中紫色部分属于模型适配:Thinker 到 Talker 要对齐文本位置与条件张量;Talker 到 Code2Wav 要过滤停止码、调整 codebook 排列。分块时,处理器还能先积累数据而暂不交付,等形成可用块再输出,结束时处理剩余内容。

绿色部分属于框架:根据模式选择处理函数,在调用点提供请求、原始输入或流式上下文,把准备好的输入提交给下游,并组织载荷交付。分块处理器没有产出张量时,框架仍会在段落或请求结束时传递相应标记。预提交与请求结束的完整机制见第 04 章,传输实现见第 06 章。

这组分工不要求每个模型拥有完全一样的转换函数。MiniMax Music 3 的整份交接就以 acoustic window 数量安排占位长度,下游再做窗口处理。框架复用调用位置和交接流程,模型决定载荷含义与工作量表达。

## 三、代价

**同一条边要维护一致的数据语义。** 整份和分块路径接收数据的时机不同,但最终都要满足下游模型的输入要求。修正停止码过滤、边界对齐或 speaker 信息时,只修其中一条路径会留下另一条路径的错误。

**分块需要保留转换状态。** Qwen3-Omni 的首块 Thinker 条件可能要先积累;音频码也要攒成块,并携带解码所需的左侧上下文。这增加了每条请求的缓存与重复处理。更小的块可能更早送出,却会增加调用次数,不能直接等同于整条链更快。

**框架不能代替模型检查语义。** 一个张量即使能序列化、传输并还原,也可能错了顺序或长度。Qwen3 的整份处理器会对缺失条件、空音频码等情况记录警告并停止交付;此时下游等待可能只是上游适配失败的表现。

## 四、和 sglang-omni 的输入整理对照

两边都把通用交接与模型语义分开,差别是适配挂在哪里。以下对照核于 sglang-omni 基准 89e60d0bf2。

vLLM-Omni 将输入准备和上游载荷生产分别注册到阶段结构中,运行时选择整份或分块的生产处理器。Qwen3 的整份路径尤其清楚地分开了 scheduler 占位与条件张量。

sglang-omni 的 Stage Runtime 在收到完整载荷后调用 InputHandler:DirectInput 直接交付,AggregatedInput 等待指定来源齐备后调用合并函数。Qwen3 的模型合并函数再把 encoder 结果组织为 Thinker 输入,并清除已消费的中间数据,避免重复携带张量。其流式分块另有接收入口。

这里能学到的是**通用接收规则与模型整理规则需要各有位置**。不能把 sglang-omni 的 InputHandler 等同于本项目的所有转换处理器,也不能从某个 Qwen3 占位函数推导出所有模型只传 token。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

本章可调的是交接模式和音频码分块。模型处理函数由 pipeline 注册,属于模型接入契约,不是部署时任意替换的性能开关;配置选择的整体规则见第 02 章。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `async_chunk` | 部署 YAML 顶层 | `DeployConfig` 为 `true`;Qwen3 随仓配置也是 `true` | 允许边生产边交付;关闭后对照整份路径,通常增加下游启动等待 | 首个音频包时间、上下游活动是否重叠 |
| `initial_codec_chunk_frames` | Qwen3 connector 的 `extra` | 随仓配置 4;处理器未配置时为 0,不启用特殊首块 | 较小首块减少攒码等待,增加短块处理占比 | 第一块到达时间与首包音频 |
| `codec_chunk_frames` | 同上 | 25 | 较小块减少攒码等待,但增加分块次数与上下文重复比例 | 包间隔、吞吐及音频连续性 |
| `codec_left_context_frames` | 同上 | 25 | 更多左侧上下文增加重复载荷与解码工作;质量影响要实测 | 块边界音频、载荷大小与解码时间 |

分块参数应保持有效取值:常规块长要大于 0,特殊首块为 0 表示沿用常规块长。这里的帧是 codec frame,不是文本 token,也不是最终波形 sample。

**处理函数契约要从调用点读。** `custom_process_input_func` 接收上游结果、原始 prompt 和多模态要求,并按声明取得 `streaming_context`、`next_stage_hf_config` 或关键字限定的 `target_model_config`。分块生产函数取得 transfer manager、当前载荷、请求和结束信息,支持时还会收到 `new_token_ids`。整份生产入口也会在处理器接受时补充 `is_finished`。这些是不同调用契约,不能统一成一个固定三参数函数。

**观测先找载荷,再找等待。** Qwen3 的 `missing thinker tensors`、`empty thinker conditioning`、`missing codes.audio` 指向载荷缺失或对齐问题;`no valid codec rows after filtering` 指向过滤后没有可用音频码。Orchestrator 的 `process_engine_inputs FAILED` 指向请求准备失败。正常分块处理中返回 `None` 可以表示继续积累,不能仅凭一次空返回判故障。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| Qwen3-Omni 语音,随仓验证的 2×H100 放置 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --deploy-config qwen3-handoff.yaml`,本地文件 `qwen3-handoff.yaml` 从 `qwen3_omni_moe.yaml` 复制,保留 `async_chunk: true` 与 4/25/25 的首块、常规块、左侧上下文 | 用较短首块尽早开始解码,后续块减少频繁交接 |
| 同一模型定位整份与分块的结果差异 | 使用同一启动命令和部署副本,仅改 `async_chunk: false` | 接受完整上游生成的等待,方便对照完整条件与音频码;分块大小此时不控制整份交接 |
| 首包并非重点,先比较统一块长 | 在分块部署副本中设 `initial_codec_chunk_frames: 0`,保留其他两项 25 | 取消短首块特例,增加首块攒码等待,便于观察常规分块行为 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 上游已结束,Talker 一直等输入 | 上游是否记录缺失或空 conditioning 警告 | 对照 token 数与条件张量行数,再查传输是否送达 |
| 文本正常但音频在块边界异常 | 停止码过滤、codebook 排列与左侧上下文 | 用同一输入比较整份路径,定位转换还是后续解码 |
| 调小常规块长,首包时间几乎不变 | 是否仍启用独立的首块长度 | 区分首块攒码等待与上游生成耗时 |
| 新处理器报参数不匹配 | 它挂的是输入准备、整份生产还是分块生产调用点 | 按该入口支持的上下文修正签名,不要只改函数名 |

## 六、常见误区

**看到函数叫 token-only,就删掉另一条张量通道。** 名字容易让人以为 token 已包含全部信息;Qwen3 这里生成的是 scheduler 占位,真正语音条件仍由 connector 交付。只看请求能提交成功,无法证明输入完整。

**照着样例写三个参数,以为这是全项目统一签名。** 整份生产样例确实常见三个参数,但输入准备会按声明获得额外模型或流式上下文,分块生产还有结束信号。接入前要核对实际调用方,不能从相似的函数名判断契约。

**每次调用都必须吐出一块,否则就是丢数据。** 分块处理器需要攒够可用输入,首块还可能有特殊准备;空返回可以是正常等待。真正要核的是结束时是否把尾块和结束标记正确送出。

**首块、后续块都调小,吞吐一定更好。** 小块减少的是局部攒码等待;调用次数和重复左侧上下文却会增加。首包、稳定包间隔与总吞吐要分开观察,不能只根据一个参数方向判断整条链的收益。
