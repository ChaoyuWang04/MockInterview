# AR运行时：调度与多模态执行

这一页解释阶段请求怎样在输入就绪后进入计算,以及 AR 的逐步采样与 Generation 的载荷生成如何共用 vLLM 执行框架。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

下游已经收到了请求,不代表它已经拿到可计算的内容。Talker 可能还在等 Thinker 的 hidden states,Code2Wav 可能只收到部分音频码。此时照普通请求直接排进 GPU 批次,会把尚未到齐的输入当成有效工作;等输入到达后再错误地重置进度,又可能重复计算或丢掉已经生成的内容。

另一方面,Thinker 和 Talker 要反复采样,Code2Wav 却是把可用音频码还原成波形。后者没有理由等待“下一个文本 token”才能报告结果。要解决的是:**让载荷就绪、调度预算与请求进度保持一致,同时允许不同的生成方式。**

## 二、解法

**先判断能不能算,再判断这一轮算多少。** 阶段内的调度器先处理输入到达通知、分块状态和超时。需要完整载荷的请求,尚未收到数据时暂时退出可调度队列;得到就绪通知后重新参与排队。分块输入有自己的等待与恢复路径,不把“已经创建请求”当成“已经有下一块”。

这里的输入协调器 OmniSchedulingCoordinator 只管理就绪状态和调度可见的元数据,不亲自搬张量。真正的载荷由第 06 章的传输路径进入 worker。普通整份交接与流式交接的等待机制不同,但都要在选批之前把请求进度整理好。

**AR 保留上游选批,Generation 改变工作单位。** OmniARScheduler 在处理 omni 输入后调用 vLLM 的调度方法,沿用其预算、排队与请求推进语义。OmniGenerationScheduler 则优先安排当前可用输入的生成工作,同样受 token 预算和并发上限约束;没有下一块时不靠占位输入反复运行。Generation 在处理完输入且上游已结束后完成,不以采样到文本结束标记作为唯一条件。

![阶段调度先让缺输入请求等待,再为已就绪请求分配计算预算;AR沿用vLLM选批并采样,Generation处理可用输入并生成多模态载荷,结果和输入就绪通知回到调度器推进下一轮](/opensource/vllm-omni/07a-omni-execution.svg)

**调度计划携带元数据,模型运行器准备真实输入。** 调度输出保留 vLLM 的基础字段,再附上 omni 请求信息和接收登记。共享模型运行器 OmniGPUModelRunner 按当前批次准备 token、embedding 和每请求的模型数据;AR 与 Generation 的专用 runner 随后执行各自的前向和结果整理。模型侧转换细节留在第 03 章,这里关心的是它们必须对应当前被调度的请求与计算范围。

结果同样分清身份。AR 可以返回采样 token 及多模态产物;Generation 通过多模态输出通道返回波形等数据,即使没有采样 token 也可以产生有效输出。调度器据此更新请求状态,载荷到达的元数据则留到下一轮选批前消费,避免在同一轮反复重置进度。

## 三、代价

**等待不一定释放容量。** 某些模型在两块输入之间保留内部状态。Generation 调度器会把这种模型暂时等待下一块的请求也计入准入容量,否则新请求可能占掉旧请求仍在使用的模型槽位。GPU 暂时没计算,不等于能够无限接新请求。

**复用上游也要对齐协议。** 当前 omni worker 使用带 omni hooks 的 v1 model runner,调度器也同步采用匹配的输出形式。上游存在另一套 runner,并不代表可以直接切换;请求恢复时缺少所需字段就会破坏运行状态。

**每段仍有独立预算。** 一个阶段能容纳的请求数,与它一轮能处理的 token 数是两个限制。提高并发上限不会让一段未到达的音频码出现,也不会自动增加每轮计算预算。多段共卡时还要考虑相互竞争,而不是只看某个阶段的队列长度。

**结果整理也是执行开销。** 多模态输出要按请求拆分并送回正确接收方,部分路径涉及设备到主机拷贝。异步执行还需要保存当轮请求映射和张量快照,不能借用下一轮已经变化的批状态。本章没有测量这些成本的占比。

## 四、和 sglang-omni 的阶段调度对照

参照项目基准为 89e60d0bf2。两边都复用成熟的 AR 调度语义,但挂接位置不同。

vLLM-Omni 的 AR 调度器继承 vLLM Scheduler,在上游选批前后加 omni 输入和输出处理。sglang-omni 的 OmniScheduler 通过本地包装调用上游 SGLang 的批选择方法,未实现的方法再动态绑定到上游类;它自己持有并适配运行批状态。

对于 Qwen3-Omni 的波形生成,本项目选择 Generation scheduler 与专用 runner,保留引擎的执行、结果更新接口。对侧则使用独立的 Code2WavScheduler,在流式 Vocoder 框架下累计可解码窗口,达到条件才执行。区别不是谁“更支持多模态”,而是**非 AR 工作继续接入统一引擎协议,还是交给阶段专用循环**。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。下面用 Qwen3-Omni 的 Thinker、Talker、Code2Wav 分别对应 stage 0、1、2。参数放在每段部署配置,或用 `--stage-overrides` 指定阶段;平台覆写仍按第 02 章的规则生效。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `max_num_seqs` | 每段部署或逐段 CLI | Qwen3 随仓各段 64;部署 schema 本身不指定 | 增大允许更多并发请求,增加资源压力;保留状态的等待请求也可能占额度 | 请求排队、阶段吞吐与模型容量 |
| `max_num_batched_tokens` | 每段部署或逐段 CLI | Qwen3 前两段 32768,Code2Wav 65536 | 改变每轮 token 预算,影响批次大小与等待 | 阶段调度、执行时长及排队 |
| `async_scheduling` | AR 阶段部署或逐段 CLI | AR 构造默认 `true`;Qwen3 Code2Wav 显式 `false` | AR 可切换同步调度作为对照,可能减少重叠机会 | 生效 scheduler 配置与阶段时延 |
| `async_chunk` | 部署顶层,或 `--async-chunk` / `--no-async-chunk` | Qwen3 随仓 `true` | 决定跨段能否随分块推进;不同于上一行的段内调度 | 下游输入等待与首个音频包时间 |
| `enforce_eager` | 每段部署或逐段 CLI | Qwen3 CUDA 配方为 `false`;平台可覆盖 | 打开可避开图捕获路径进行对照,执行性能可能变化 | 图捕获报错、实际推理时延 |
| `VLLM_OMNI_INPUT_WAIT_TIMEOUT_S` | 进程环境变量 | 600 秒;0 关闭,负数及非有限值拒绝 | 控制整份输入或分块停滞多久后失败;不是总生成时限 | `waiting ... for connector input` 或 `waiting for a chunk` 错误日志 |

**先分清没有工作和工作未完成。** 输入等待超时会把请求标为 `FINISHED_ERROR`,日志带请求身份和等待类别。Generation 的 `sampled_token_ids` 为空不代表没有结果,还要看 `multimodal_outputs` 与完成状态。诊断进度问题时,也要区分收到一块、处理完当前输入与整条输入流结束。

若日志出现 `forces v1 model runner for omni hooks`,它说明运行时主动对齐了兼容路径,不能直接当成性能故障。若启用 profiler,AR 与 Generation 的执行路径提供 `gpu_model_runner: preprocess`、`Forward` 等范围,可进一步区分输入整理与模型前向。

以下以随仓配方注明的 2×H100 环境为资源前提,没有在本章执行 GPU 测试。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 先建立三段语音执行基线 | 沿用第 05 章的 Qwen3-Omni 启动方式,不添加 stage overrides | 使用随仓预算及执行模式,先观察哪段等待、哪段计算 |
| 降低并发观察请求推进 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --stage-overrides '{"0":{"max_num_seqs":8},"1":{"max_num_seqs":4},"2":{"max_num_seqs":4}}'` | 缩小在途容量,接受吞吐上限变化,便于对照请求状态 |
| 排查 AR 异步调度相关问题 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --stage-overrides '{"0":{"async_scheduling":false},"1":{"async_scheduling":false}}'` | 关闭前两段异步调度作对照,仍保留默认段间分块,不把两个机制一起改掉 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 下游有请求,却没有 GPU 计算 | 是否等待首份载荷或下一块 | 先核上游及交付状态,再查并发和 token 预算 |
| Code2Wav 没有 token,客户端却收到音频 | 多模态输出和完成状态 | 用波形产出与音频时延观测,不要按文本 token 数判断运行失败 |
| GPU 空闲,新请求仍不能准入 | 模型是否保留跨块状态,等待请求是否占容量 | 查上游是否停滞,再决定降并发或增加资源 |
| 调同步后仍看到分块音频 | 改的是 `async_scheduling` 还是 `async_chunk` | 按段内执行和段间交接分别设计对照 |
| 请求长时间挂住后报错 | 输入等待日志中的请求及阶段 | 判断丢载荷还是上游确实较慢,再考虑延长超时 |
| 图捕获失败 | 平台配方和实际 stage 的 `enforce_eager` | 用该阶段 eager 模式验证执行,避免先修改整个模型配置 |

## 六、常见误区

**Generation 还调用采样接口,所以也是逐 token 生成。** 这个名字来自引擎的共同执行协议。Generation runner 在该接口里整理每请求的多模态结果,返回的采样 token 可以为空;是否完成由输入处理进度及流结束状态决定。

**看到请求在等待队列,就只增加批预算。** 缺载荷的请求也可能暂存在等待体系里,但每轮选批前会被输入门控排除。预算只能影响已经具备计算条件的工作,不能修复上游未送达的数据。

**把输入等待超时设成负数表示不限时。** 这是其他系统常见习惯,这里却会在启动时报错。需要关闭时使用 0,但它会同时关闭整份载荷与分块等待的保护,让丢失输入的请求可能一直保留。

**基类来自 vLLM,上游所有 runner 都能直接启用。** omni 的调度输出和 worker hooks 有配套要求。当前强制采用 v1 runner 正是为了保留这种协议一致性;看到兼容警告后强行绕过,可能把恢复请求变成缺字段错误。
