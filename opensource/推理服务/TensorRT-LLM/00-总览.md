# TensorRT-LLM 框架总览

源码基准:官方仓库 <https://github.com/NVIDIA/TensorRT-LLM>,分支 `main`,commit `59f5c47f2e0033e158e8e64015c1c068eaf92bf6`,最近的发布 tag `v1.2.1`(不是当前 HEAD 的祖先,仍记在发布线上),树内版本 `1.3.0rc28`,核对日期 2026-09-22。全篇的「当前」「默认」都指这组基准;性能数字来自官方博客,标为「官方数字」。

## 一、TensorRT-LLM 是什么

**TensorRT-LLM** 是 NVIDIA 开源的大语言模型推理与服务栈,跑在 NVIDIA GPU 上。它要解决的矛盾和所有推理引擎相同:显存与算力有限、请求长短不一,却要把百亿到万亿参数的模型以低延迟、高吞吐送出去。

和名字容易让人误会的两点先说清。第一,它**不是**同目录下的 TensorRT SDK(`projects/推理服务/TensorRT`)。第二,本基准上**已经没有 TensorRT 引擎这条后端**:`trtllm-build` 不存在,HuggingFace 权重直接进 PyTorch 运行时,`LLM(backend="tensorrt")` 会报错。今天唯一的执行后端是 PyTorch;`AutoDeploy` 是建在这套运行时上的第二条前端,文档标 Beta。

它的出发点是:用一套 Python LLM API 把「加载模型、IFB（连续批处理）、分页 KV、多卡并行」收成一次 `generate()` 或一个 OpenAI 兼容服务,内核仍是逐步生成,但调度、缓存和 kernel 选择都为 NVIDIA GPU 特化。官方文档把运行时拆成四块:**Scheduler**(这一步谁该算)、**KVCacheManager**(KV 块怎么分、怎么复用)、**ModelEngine**(GPU 上跑前向)、**Sampler**(logits 变成 token)。这四块装在每 rank 一个 `PyExecutor` 的后台循环里。

一句话定位:**TensorRT-LLM 把「PyTorch 上的 IFB（连续批处理） + 分页 KV 与跨请求复用 + 可换注意力后端 + Wide-EP + PD 分离 + 推测解码」做成一套 LLM 推理服务栈;旧的 TensorRT 引擎编译链已经删掉。** 官方数字包括 Blackwell 上 DeepSeek-R1 的吞吐纪录,以及 Llama 4 Maverick 突破每用户 1000 TPS。

顶层入口:

- `from tensorrt_llm import LLM`:离线或嵌入式推理,`LLM(model=...).generate(...)`,入口在 `llmapi/llm.py`。
- `trtllm-serve <hf_model>`:OpenAI 兼容 HTTP,入口 `commands/serve.py` → `serve/openai_server.py`。
- `trtllm-bench` / `trtllm-eval`:压测与评测,不是服务主路径。
- `trtllm-llmapi-launch`:多进程拉起 LLM API 的辅助脚本。

代码组织上,解读主体在 `tensorrt_llm/`(约 41 MB)。真正跑请求的是 `_torch/pyexecutor/`(约 3.2 MB)加上注意力、MoE、服务层。旁边有三块体量不小但本解读不立章的东西:`_torch/cute_dsl_kernels/` 与 `cpp/tensorrt_llm/kernels/`(算子层,只讲到「用哪个后端」)、`_torch/visual_gen/`(VisualGen,扩散图像/视频,官方写明独立 pipeline)、`triton_backend/`(Triton 插件,卫星)。`_torch/auto_deploy/`(约 4.2 MB)是第二条前端,单独一章,不按 Linear/Attention 再镜像一遍。

## 二、6 个招牌:先建立全局图景

```text
        客户端 ── HTTP:trtllm-serve / Python:LLM.generate
                        |
                        v
              [1] LLM API + 每 rank 一个 PyExecutor
              切词在 API 侧;循环里调度 → 准备 KV → 前向 → 采样
                        |
          ┌─────────────┼─────────────┐
          v             v             v
   [2] IFB（连续批处理）    [3] 分页 KV      [4] 注意力后端
   context 与 decode   块池 + 前缀复用   默认 TRTLLM
   同批;overlap 默认开  外部走 Connector  稀疏是算法+kernel
          |             |
          └──────┬──────┘
                 v
        [5] Wide-EP / 大规模 MoE     [6] PD 分离
        专家与槽位分开,热专家可复制   prefill / decode 分池
        EPLB 改路由表                 NIXL 搬块,和计算重叠
```

一句话记忆:

- **PyExecutor**:每 rank 一个后台循环,把调度、KV、前向、采样串成一步;API 进程通过 Worker 或 Proxy 跟它说话。
- **IFB（连续批处理） + overlap**:新请求的 prefill 可以跟别人的 decode 同批;CPU 收尾默认藏到下一步 GPU 计算后面。
- **分页 KV 复用**:KV 按块池管,填满的块进搜索树,后来的请求可以少算前缀;块也可以经 Connector 接到外部。
- **注意力后端**:默认用 TRT-LLM 自己的 kernel 路径,可换成 FlashInfer;长上下文再叠加稀疏算法。
- **Wide-EP**:细粒度 MoE 不靠「一个专家钉死一张卡」,而是槽位 + 复制 + 负载均衡。
- **PD 分离**:prefill 和 decode 分到不同 GPU 池,KV 用 NIXL 搬走,避免同卡互相拖延迟。

| AutoDeploy 绑定 | 新 HF 模型要等手写模型类才能吃上这套运行时 | `torch.export` 做图变换,接到同一套 PyExecutor(Beta) | 16 章 |

## 四、一条请求怎么串起来

一条文本请求进来后,先落到 **LLM API**(Python `generate` 或 `trtllm-serve` 的 HTTP 入口):套聊天模板、切词、配采样参数,然后交给 **GenerationExecutor**。单卡默认可以是同进程 Worker;多 rank 通常是 Proxy 把请求送到每个 rank 的 Worker。

每个 rank 上,**PyExecutor** 在后台循环里重复四件事:从队列取新请求 → Scheduler 决定这一批谁算 → KVCacheManager 准备块 → ModelEngine 前向 → Sampler 出 token。IFB（连续批处理）的意思是:还在 prefill 的请求可以和已经在 decode 的请求出现在同一批。Overlap 的意思是:GPU 已经在跑第 n+1 步时,CPU 才去处理第 n 步的停词和回包——默认开着,代价是流水线里多一截 decode。

多卡时,`Mapping` 描述这张卡在 TP / PP / DP / EP / CP 里扮演哪一段。如果开了 PD 分离,这条请求的 prefill 和 decode 不在同一池 GPU 上,KV 块经 NIXL 搬走后再继续生成。

VisualGen 不走这套循环,它有自己的 `DiffusionExecutor`,本解读不展开。

## 六、怎么调它、怎么看它

各章「调参与观测」只写自己的参数,入口和观测点在这里说一次。

**四种入口,一个原则:改了要重启的都是启动参数。**

| 入口 | 长什么样 | 什么时候用 |
|---|---|---|
| 启动参数 / YAML | `trtllm-serve <hf_model> --config config.yaml`,或构造 `LLM(...)` 时传入 `TorchLlmArgs` 同名字段 | 并行度、KV 比例、后端选择、overlap 开关;改了要重启 |
| 环境变量 | 如 `TLLM_LOG_LEVEL`、`TLLM_LOG_LEVEL_BY_MODULE`、`TLLM_RANK_CRASH_HARD_KILL_GRACE`;遥测关闭用 `TRTLLM_NO_USAGE_STATS` | 日志、多 rank 崩溃处理、遥测;改了要重启 |
| 请求参数 | `SamplingParams`(温度、top-k、停词、约束)、LoRA 名、PD 相关的 `DisaggregatedParams` | 每条请求各自一套 |
| 运行时接口 | OpenAI 的 chat/completions 等 HTTP 路径;LLM API 的 `generate` | 不重启能做的事主要在请求侧 |

**观测点先看日志模块标签,再看服务指标。**

| 看什么 | 在哪 | 健康值 |
|---|---|---|
| 子系统 | 日志里 8 字符模块标签,如 `[runtime ]`、`[_torch  ]`、`[serve   ]` | 用 `TLLM_LOG_LEVEL_BY_MODULE` 按模块加详细度 |
| 容量 | KV 配置里的 `free_gpu_memory_fraction`(默认 0.9)与 `max_tokens` 谁先碰到 | 启动后仍要留出运行余量,具体 GB 看卡 |
| 出事 | 多 rank 时一个 rank 崩了,默认约 10 秒后拆掉整场作业 | 单 rank 不受这条影响 |
| HTTP | `trtllm-serve` 的 OpenAI 兼容端口(文档示例 8000) | 探活先打 chat/completions 而不是随便一个健康口 |

默认会采集匿名遥测(GPU 型号、并行度、特性开关,不含 prompt)。关闭方式见 README:环境变量、`~/.config/trtllm/do_not_track`,或 CLI `--no-telemetry`。

## 七、阅读顺序

主干是 01 → 02 → 03 → 04 → 05,读完就抓住了「API 进程 + PyExecutor 循环 + KV + 注意力 + 图捕获」。06 到 09 是加速与多卡(推测、并行、MoE、PD),10 到 14 按需查阅,15 在要对外服务时读,16 只在需要把现成 PyTorch 模型接进来、又不想手写模型类时读。

**怎么读**:PagedAttention、KV cache、PD 分离、量化这些通用机制只在知识库展开一遍。本解读每章只写这个项目怎么用、怎么调。和 vLLM、SGLang 的差别集中在下表,不在各章开头抢参照。

| 维度 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 执行后端 | PyTorch | PyTorch | 本基准只有 PyTorch;旧 TensorRT 引擎已删除 |
| 前缀 KV | 块哈希,命中整块 | radix 树,命中到 token | 块池 + 搜索树复用,粒度是块 |
| CPU 与 GPU | 异步调度 | 零开销调度,占位 token | overlap 默认开,多一截 decode 换吞吐 |
| 大规模 MoE | EP / DP 各自支持 | PD + DeepEP + 双批重叠 + EPLB + DPA | Wide-EP:槽位与专家分开,EPLB,面向 NVL72 |
| 服务层 | Python 进程 | HTTP 前端与网关可换 Rust | `trtllm-serve`;大规模编排常和 Dynamo 组合 |

## 八、术语表

| 术语 | 一句话 |
|---|---|
| PyExecutor | 每 rank 一个后台循环,串起调度、KV、前向、采样 |
| IFB（连续批处理） | context 与 generation 可以同批 |
| Overlap Scheduler | CPU 处理第 n 步时 GPU 已在跑第 n+1 步,默认开 |
| Wide-EP | 专家与槽位解耦的大规模专家并行 |
| EPLB | 专家并行负载均衡,改 Expert→Slot 路由表 |
| Helix | PD decode 侧把同一批卡时分给注意力 CP 与 FFN TP |
| NIXL | PD 时默认的 KV 传输后端之一,走 RDMA / NVLink |
| AutoDeploy | 用 `torch.export` 把现成 PyTorch 模型接到本运行时的 Beta 前端 |
| VisualGen | 扩散图像/视频栈,不走 PyExecutor,本解读不立章 |
| TorchSampler | 本基准唯一采样器,旧的 TRTLLM Sampler 已删除 |
| Mapping | 一张卡在 TP/PP/DP/EP/CP 里的角色表 |
