# TensorRT-LLM 04|注意力后端与稀疏注意力

注意力 kernel 对不上头数、精度或 MLA 形状就会算错或极慢;长上下文还把每步 decode 的算力花在不该看的 KV 上。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

注意力没有一份能通吃所有卡代、头数、精度和 MLA 的 kernel。坏的是**这一步前向的对错和时延**:形状对不上就断言失败,对上了但选了参考实现就慢一个数量级;超长 prompt 的 decode 若对全部历史 KV 做满注意力,算力和访存一起炸,每个 token 的间隔被注意力单独拖死。

稀疏解决的是第二件事,不是第一件。它不另造一套注意力,只决定**少算哪一部分 KV**。把「换 kernel」和「少算 KV」揉成一个开关,排障时分不清是后端选错还是算法名单错。

## 二、解法:名字换 kernel,算法再叠一层选 KV

最天然的直觉:模型代码自己按卡型挑 kernel,长上下文再手写一套稀疏注意力。实际不吃亏的做法是切开两段。注意力层构造时读一个启动字符串,工厂只认三个名字:自家默认、核库、参考实现。不认识的名字打一行警告,退回自家默认。有稀疏配置时,工厂在同一名字下换成稀疏子类,并不新开一条注意力栈。

![启动时一个字符串进工厂:默认走自家 kernel,可换成核库或参考实现,不认识的名字警告后退回默认;开了稀疏之后算法先选出 token 或页,稀疏子类 kernel 只按这份名单算,模型前向仍是同一行](/opensource/TensorRT-LLM/04a-backend-and-sparse.svg)

自家默认路径能吃融合 QKV、融合位置编码、分页 KV、MLA、注意力 sink;分块注意力也只允许走这条。核库路径给要对齐外部实现的人;参考实现只服务连续批处理和线性 KV,文档写明不给生产。RoPE 融不进算子时,注意力层自己关掉融合,改在层外做。

稀疏是「算法选、kernel 算」。公开算法五条:无训练的页级淘汰(prefill 仍稠密,只压缩留下的 KV,decode 再按页挑)、模型自带的 MLA 索引器、混合压缩历史、块级 GQA 选择、以及只在 softmax 里跳过合格 tile(不减 KV 存量)。算法产出 pattern,kernel 消费;没有算法的稀疏 kernel 能力不是用户 API。VisualGen 那套稀疏不在这一页。

为什么实际不吃亏:模型代码始终调同一行前向;换 kernel 是启动一次的名字解析;长上下文要省算力时只加算法配置,不重写注意力层。

## 三、代价

**未知名字会静默退回默认。** 拼错后端名不会起不来,只打警告。你以为在跑核库,日志里其实是自家路径。

**能力不在后端上就当场断言。** 分块注意力、注意力 sink、相对位置偏置、MLA 跳过修正,都绑在自家默认路径。核库装不上时工厂也退回默认。

**稀疏配置是原型。** 无训练页级淘汰要求关掉块复用和切块 prefill,也不走 PD 分离;块级那条没有稠密回退。跳过 softmax 不减小 KV,省的是 kernel 内部活,显存账不变。

**参考实现能跑不等于能上线。** 它为正确性对照而存在,吞吐不是这条路径的指标。

## 四、注意力 kernel 怎么换、长上下文要不要少算一部分 KV

这一页比的是注意力 kernel 怎么换、长上下文要不要少算一部分 KV。对等列是 vLLM 和 SGLang。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 没指定时怎么落到一份 kernel | 默认自家路径,工厂三个名字 | 按硬件与精度算一张优先级表,有多个候选 | 决策树只吐一个名字,没有候选列表 |
| 选不中怎么办 | 不认识的名字警告后退回默认;能力不够就构造断言 | 当前候选淘汰,试下一个 | 改写成另一个名字,或构造时抛错,没有回头 |
| 稀疏叠在哪 | 算法选 token 或页,kernel 消费 pattern,仍挂在原来的后端名字下 | 稀疏变体登记在同一张表,由模型层钦定,不参与优先级竞争 | 稀疏是一等后端名,内部再分子实现 |
| prefill 与 decode 能否两套 kernel | 一个后端管两阶段 | 一个后端管两阶段 | 三个字段,不同时套分发器 |
| 核库在对照里的位置 | 可选后端名字,不是对等框架 | 候选之一 | 候选之一 |

重心在本项目:换 kernel 是三个名字的工厂,不是优先级循环;少算 KV 是另加的算法层。核库只当可选实现,不进对等列。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `attn_backend` · 用哪套注意力 kernel | 启动(LLM 构造或 extra yaml) | `TRTLLM` | `FLASHINFER`:走核库; `VANILLA`:参考实现,不给生产;拼错:警告后退回 `TRTLLM` | 日志 `Falling back to TRTLLM attention backend`; RoPE 不融合时有 `Will disable rope_fusion` |
| `sparse_attention_config` · 稀疏算法 | 启动,原型 | 空,稠密 | 填算法后工厂换稀疏子类;无训练页级淘汰还要关块复用和切块 prefill | 日志 `Using sparse attention:` 后面跟算法名 |
| `enable_mla_skip_correction` · MLA 跳过修正 | 启动,原型 | 关 | 开:只允许 `attn_backend=TRTLLM`,否则校验失败 | 启动是否 `requires attn_backend='TRTLLM'` |
| `mla_skip_correction_threshold` · 跳过修正阈值 | 启动,原型 | `8.0`(大于 0、不超过 32) | 只在上一开关打开时生效;上限随 kernel 精度变 | 同上 |
| `kv_cache_config.enable_block_reuse` · 块复用 | 启动 | 开 | 无训练页级淘汰必须关,否则这条稀疏路径不支持 | 启动报错或文档约束 |
| `enable_chunked_prefill` · 切块 prefill | 启动 | 关 | 无训练页级淘汰必须保持关 | 同上 |

**怎么看。** 一是启动日志:`Falling back to TRTLLM attention backend` 说明名字没对上;`Using sparse attention:` 说明算法层挂上了;`rope_fusion is true but the attention backend does not support it` 说明位置编码被踢出算子。二是能力错误:分块注意力配了非默认后端会 `does not support chunked attention`;MLA 跳过修正配了非默认后端会在参数校验处失败。三是长上下文:稀疏开了但 decode 时延几乎没动,先看算法是不是只跳 softmax(KV 没减),再看 prefill 是否仍按稠密算。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡生产,普通 GQA | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --extra_llm_api_options attn-trtllm.yaml`(yaml 里 `attn_backend: TRTLLM`) | 用自家默认 kernel 换吞吐;分块注意力和 sink 都能走 |
| 要对齐核库实现或排查自家路径 | `python -c "from tensorrt_llm import LLM; LLM('Qwen/Qwen2.5-7B-Instruct', attn_backend='FLASHINFER')"` | 用核库换对照; RoPE 融合会关,部分特性断言失败 |
| 超长 decode、无训练稀疏 | `trtllm-serve Qwen/Qwen2.5-14B-Instruct --extra_llm_api_options rocket-sparse.yaml`(yaml 里算法 `rocket`、`prompt_budget: 2048`,并关掉块复用与切块 prefill) | 用留下的 prompt KV 预算换 decode 少算页; prefill 仍稠密,且不能 PD、不能复用块 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 以为换了核库,速度没变 | 有没有 `Falling back to TRTLLM` | 核库没装或名字拼错,先装再写对 |
| 启动 `does not support chunked attention` | 后端是不是默认那条 | 分块注意力只能留在自家路径 |
| 启动要求 `attn_backend='TRTLLM'` | MLA 跳过修正是否打开 | 关掉该开关,或改回默认后端 |
| 开了稀疏 decode 仍按全历史那么慢 | 日志算法名是不是 skip softmax;页级淘汰的 prefill 是否仍稠密 | 换会减 KV 的算法,或接受 prefill 不省 |
| 稀疏起不来,提到块复用或切块 prefill | 那两个开关 | 按算法关掉;要复用块就不要这条无训练稀疏 |
| 参考实现能出字但吞吐极差 | `attn_backend` 是否 `VANILLA` | 改回默认,参考路径不是生产 |

## 六、常见误区

- **以为换注意力后端就是换一套调度。** 调度和 KV 池还在执行器循环里。这里只换注意力层底下的 kernel 类。
- **以为稀疏是第四个后端名字。** 稀疏挂在已有名字下面。工厂先看后端字符串,再看有没有算法配置。
- **以为开了稀疏 prefill 也少算。** 无训练页级那条 prefill 仍稠密,省的是留下的 KV 和之后的 decode。跳过 softmax 连 KV 存量都不减。
- **以为不认识的后端名会起不来。** 它警告后退回默认。对错要看那行 fallback 日志,不能看启动成功。
- **以为核库和本项目是并列的两套服务。** 核库是可选 kernel,对照表的对等列仍是 vLLM 与 SGLang。
- **以为参考实现能顶生产。** 文档把它标成基线,特性少、没有生产优化。
