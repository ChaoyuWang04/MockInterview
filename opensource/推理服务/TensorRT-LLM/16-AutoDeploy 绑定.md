# TensorRT-LLM 16|AutoDeploy 绑定

新出的 Hugging Face 模型如果只能等手写模型类,上线窗口会被卡住,运行时优化也吃不上。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

主干前端要在仓库里给每种架构手写一份模型类,才能走分页 KV、IFB（连续批处理）和 overlap。新权重一来,坏的是**能不能当天把模型接到同一套执行器上**。等手写类的那几天,吞吐和时延都谈不上:服务起不来,并发为零。已经验证过的那一长串因果语言模型可以走这条第二条前端,但文档标 Beta,规划里的 LoRA 和加速草稿不要当成默认热路径。

## 二、解法:导出成图,变换完接到同一套执行器

最天然的直觉:别再抄一份模型类,把现成 PyTorch 前向导出成计算图,在图上自动切分、插缓存、融合,再交给已经在跑的那套执行器。本项目的 AutoDeploy 就是这条路,文档叫 Beta。

![现成 Hugging Face 模型先经工厂、导出、图变换和编译,实线接到适配引擎再进同一套执行器;虚线才进轻量调试运行时;规划中的 LoRA 与加速草稿只在旁注箱,没有热路径箭头](/opensource/TensorRT-LLM/16a-autodeploy-bind.svg)

默认走图模式:工厂先在元设备上搭架构,再导出成图模块,按站做模式匹配、切分、装权重、融合、把注意力换成带缓存的实现,最后编译。默认编译后端会抓 CUDA Graph;矩阵里用来验证模型的那组是另一套编译加注意力组合,不要把验证配方当成代码默认。

为什么实际不吃亏:变换发生在拉起作业的时候,请求进循环之后看到的仍是同一套调度、分页 KV 和 overlap。调试运行时是另一条入口,用朴素调度,方便把新图跑通,不应当成生产循环。

## 三、代价

**仍是 Beta。** 接口会改,文档写明可能不向后兼容。规划里的 LoRA、加速草稿和一部分新架构还没有当成热路径落地。

**导出和变换是启动税。** 大 MoE 要扫整张图,启动可以到分钟级;作业起来之后每步不再付这笔。只装架构、不装权重可以先看图对不对,但不能拿来服务。

**并行不能用主干那套张量并行开关。** 这一条前端只认世界大小,再在图上切;把主干的并行字段填进去会直接拒。

**验证清单不是宇宙。** 文档说兼容一类因果语言模型工厂,另外列了一长串用固定配方验证过的卡。清单外的模型可能导出失败、模式匹配对不上,或注意力后端选错就比手写类还慢。

**调试运行时没有生产调度。** 世界大小写成 0 只对调试运行时有意义。推测解码配某一种注意力再抓 CUDA Graph,这条前端会拒。

## 四、第二条前端怎么接到同一套执行器

这一页比的是第二条前端怎么用图变换接到同一套执行器、新模型还要不要手写模型类。对等列是 vLLM 和 SGLang。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 第二条前端是什么 | 导出成图再变换,文档标 Beta | 没有第二条导出前端接同一执行器 | 没有第二条导出前端接同一执行器 |
| 新模型要不要手写类 | 图模式可以跳过手写类;对不上图就仍要改变换或退回主干类 | 靠模型注册与编译器,不是导出后再接本仓库执行器 | 靠模型注册与编译器,不是导出后再接本仓库执行器 |
| 接到哪套循环 | 默认接到同一套执行器,IFB 与 overlap 仍在那边 | 只有一条执行路径 | 只有一条执行路径 |
| 调试怎么走 | 另有轻量运行时,朴素调度,不接生产循环 | 没有对等的第二条运行时 | 没有对等的第二条运行时 |
| 并行怎么声明 | 只认世界大小,图上自动切 | 走自己的并行配置 | 走自己的并行配置 |

重心在本项目:把「新权重当天接到执行器」做成图变换绑定,而不是再镜像一套 Linear 和注意力实现。vLLM 和 SGLang 都有编译加速,但没有这条「导出之后接到同一套执行器」的前端。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `runtime` · 接生产执行器还是调试运行时 | 启动 / YAML | `trtllm` | `demollm`:朴素调度,方便对图;生产吞吐和 IFB 都没有 | 日志是否走 AutoDeploy 实验配置;进程里有没有执行器工人 |
| `mode` · 全图变换还是只换 Hugging Face 注意力 | 启动 | `graph` | `transformers`:不导出整图,只替换注意力;切分和融合这一套没有 | 日志变换总时长;图可视化是否整张 |
| `compile_backend` · 变换完怎么编译 | 启动,快捷方式写进 `compile_model` | `torch-cudagraph` | `torch-simple`:不优化;`torch-compile`:只编译;`torch-opt`:编译再抓图 | 启动后第一步是否有抓图开销 |
| `attn_backend` · 插缓存注意力用哪套 kernel | 启动,快捷方式写进插缓存变换 | 图模式 YAML 里是 `trtllm` | `flashinfer` / `triton` / `torch`:换 kernel;验证清单常用 flashinfer,不是代码默认 | 一步时延;选错会比手写类慢 |
| `world_size` · 几张卡做自动切分 | 启动 | `1` | 调高:图上切分;填主干张量并行字段会拒;`0` 只对调试运行时表示不拉进程 | 启动是否报只认世界大小 |
| `skip_loading_weights` · 只装架构 | 启动 | 关 | 开:导出更快,不能服务 | 前向数值全错或直接失败 |
| `model_factory` · 用哪家工厂装模型 | 启动 | `AutoModelForCausalLM` | 换成图像文本工厂或 Eagle 专用工厂;对不上就装失败 | 启动报工厂不在注册表 |
| `--model` · 权重路径或 Hub 名 | 示例脚本 CLI | 无,必填 | 指向 Hugging Face 卡或本地目录 | 脚本要求必须提供模型 |
| `--args.yaml-extra` · 额外变换 YAML | 示例脚本 | 空列表 | 后写的文件覆盖默认图模式 YAML | `dry_run` 打印合并后的配置 |
| `--use-registry` · 从示例注册表带配方 | 示例脚本 | 关 | 开:按模型名塞注册表 YAML,显式文件仍可覆盖 | 日志里 yaml 列表变长 |

**怎么看。** 一是入口:生产路径用 AutoDeploy 自己的语言模型类,后端被写死成内部名;示例脚本在 `examples/auto_deploy` 下跑 `build_and_run_ad.py`。二是日志:`Total time for all transforms` 是启动税;实验配置会整份 YAML 打出来。三是不要看主干 `Using LLM with PyTorch backend` 那行来判断走了这条前端。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡把已验证的小模型当天接上执行器 | `python examples/auto_deploy/build_and_run_ad.py --model TinyLlama/TinyLlama-1.1B-Chat-v1.0` | 用启动时的导出和变换换掉手写模型类;默认编译会抓 CUDA Graph |
| 新架构先对图、不要生产调度 | `python examples/auto_deploy/build_and_run_ad.py --model TinyLlama/TinyLlama-1.1B-Chat-v1.0 --args.runtime demollm --args.compile-backend torch-simple` | 用朴素运行时和不优化编译换可打断点的前向;IFB 没有 |
| 清单里验证过的 7B,按验证配方跑 | `python examples/auto_deploy/build_and_run_ad.py --model Qwen/Qwen2.5-7B-Instruct --args.compile-backend torch-compile --args.attn-backend flashinfer` | 用验证清单那组编译和注意力换默认的 CUDA Graph 加 trtllm 注意力;仍是 Beta |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报只认世界大小 | 是否填了主干张量并行字段 | 改 `world_size`,不要填那些字段 |
| 导出失败或模式匹配对不上 | 模型是否在验证清单;是否图模式 | 先换清单内模型;或退回主干手写类 |
| 一步比手写类还慢 | 编译后端和注意力是不是验证配方 | 对清单模型改成验证那组;不要默认当最优 |
| 调试很顺、一换生产就行为变 | 运行时是不是 `demollm` | 改回 `trtllm` 才接到执行器 |
| 推测解码启动被拒 | 是否 flashinfer 还开着 CUDA Graph,或分段抓图仍开 | 按报错改编译后端;不要当热路径 |
| 只看到架构对、数值全错 | 是否跳过了装权重 | 关掉 `skip_loading_weights` |

## 六、常见误区

- **以为这是默认 LLM 入口。** 默认入口仍是主干 PyTorch 后端加手写模型类。AutoDeploy 要走自己的类和示例脚本,后端名被写死。
- **以为验证清单等于默认热路径。** 清单用编译加 flashinfer 验证;代码默认编译是抓 CUDA Graph,图模式注意力 YAML 默认是另一套 kernel。
- **以为调试运行时也有 IFB。** 那条入口是朴素调度,专门用来对图。
- **以为 LoRA 和加速草稿已经能跟这条前端一起开。** 文档规划里还在列;代码里推测有条件接受,但和部分注意力、分段抓图互斥,不要画进热路径。
- **以为可以沿用主干的张量并行开关。** 这一条前端会拒,只认世界大小。
- **以为任意 Hugging Face 因果语言模型导出了就能上线。** 工厂声称覆盖一类模型,真正核过的是清单;对不上图仍要改变换或退回手写类。
