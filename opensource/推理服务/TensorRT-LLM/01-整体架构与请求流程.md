# TensorRT-LLM 01|整体架构与请求流程

请求的切词、调度和前向如果挤在同一个 Python 进程里,每个 token 的时间会被 CPU 活吃掉一半。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

HTTP、切词和 GPU 前向如果挤在同一个解释器里,坏的是**每个 token 的间隔**。Python 一把锁,同一时刻只让一个线程跑解释器;GPU 算完一步要等 CPU 发下一步,可这段空档里 CPU 还得给新请求切词、给老请求把 token 变回文字、给套接字写响应。并发到 100 条时,一步 10–50 毫秒的 decode 里,光 CPU 的活儿就能占掉一半,吞吐掉下来、字与字之间开始抖。再来一条超长 prompt,切词本身就要 100–500 毫秒,这段时间所有在跑的请求一起停。

旧的引擎编译链已经删掉了,今天唯一的执行后端是 PyTorch。PyTorch 这条路上 Python 侧更重,进程拆不开,问题只会更明显。

## 二、解法:对外进程切词,执行器进程算

最天然的直觉:切词和写响应是 CPU 活,调度和前向是 GPU 活,各占一个进程,中间用管子连起来,谁也不等谁。本项目默认就是这么做的。

![一条请求默认走两个进程:对外进程里做 HTTP 与切词,同一进程里的代理用本机消息队列把 token 编号送给执行器进程;执行器进程里调度、准备缓存、前向、采样在同一条循环里;token 编号默认送回对外进程再还原成文字,后处理进程默认不起](/opensource/TensorRT-LLM/01a-process-topology.svg)

Linux 上即便只有一张卡,默认也拆成对外进程加执行器进程。注释写明是为了流式性能;捏回单进程要显式打开环境变量,或者这条请求要回整表 logits。多卡时对外进程拉起一组 MPI 工人,每个 rank 一个执行器循环。编排器默认走 MPI;改成 Ray 或 RPC 是原型路径,不是这一页的主干。

管子是本机 ZeroMQ 队列,默认一对一,消息用 Python 自带的打包再加一层校验。每步要传的是这一批新出的 token 编号和若干等长列表,相对 GPU 一步 10–50 毫秒,拆进程的开销淹没在里面。

执行器进程里的循环默认还把 CPU 收尾藏到下一步 GPU 计算后面:当前这一步已经在 GPU 上跑时,CPU 才去处理上一步的停词和回包。那是下一章的调度故事;这一页只要记住——拆进程是为了让切词和 HTTP 不要踩在这条循环上。

![执行器循环默认把上一步的 CPU 收尾藏进当前一步的 GPU 前向后面:时间条上 GPU 连续满载,CPU 的停词与回包落在下一步的空档里](/opensource/TensorRT-LLM/01b-overlap-timeline.svg)

为什么这么拆实际不吃亏:切词发生在对外进程把请求交出去之前,执行器进程拿到的已经是 token 编号。反切词默认也在对外进程做,执行器不用为了「译出一个汉字」卡住下一步。后处理进程是可选的第三工位,默认零个;高并发流式要把还原文字从对外进程挪走时再加。

## 三、代价

**默认就要多一个进程。** 启动慢一截,入口必须写在主模块保护里,否则子进程会把入口脚本再跑一遍。单进程调试更方便,但注释写明流式会变差。

**请求至少过一次进程边界。** 单条请求因此多一截打包和排队;要回整表 logits 时这条路径更重,所以回 logits 会走单进程工人。

**切词仍然在对外进程上。** 它不是执行器的活。一条超长 prompt 切 100–500 毫秒,这段时间同一个对外进程里的 HTTP 和流式发送一起停。后处理进程默认不起,反切词也还在这个进程里。

**分词器至少装一份在对外进程。** 另起后处理进程时,还原文字的那份要再装一遍。跳过初始化则两边都不装,请求必须自带 token 编号,响应里也没有文本。

## 四、切词、调度、前向分别落在几个进程里

这一页比的是一条请求进引擎之后,切词、调度、前向分别落在几个进程里。对等列是 vLLM 和 SGLang。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 切词在哪 | 对外进程预处理完再交出去 | 对外进程 | 主进程事件循环上同步切,没有线程池 |
| 调度和前向隔不隔一层 | 执行器进程里同一条循环,调度和前向不拆进程 | 调度在引擎进程;单卡时工人也在这个进程里,多卡才另拉 GPU 工人 | 每个 rank 一个调度子进程,调度和前向合在一起 |
| 反切词在哪 | 默认回对外进程;可另起后处理进程,默认零个 | 对外进程 | 单独一个反切词进程 |
| 停止串在哪判 | 执行器循环里判,不需要为了停词再问对外进程 | 文字在对外进程还原,停止串也在那边判,判到再反向叫停 | 调度器自己留一份分词器,就地判 |
| 默认单卡还拆不拆 | Linux 默认仍拆代理加执行器;环境变量或回 logits 才捏回单进程 | 默认多进程;单卡工人在引擎进程内 | 调度器永远是子进程,没有单进程调试模式 |
| 进程之间怎么打包 | 本机消息队列,默认 Python 自带打包加校验 | 紧凑二进制;多模态张量另走共享内存 | 默认 Python 自带打包,紧凑格式要手动开 |

重心在本项目:默认就把切词留在对外进程,把调度和前向关进执行器循环,反切词先不单独占一个进程。vLLM 把停止串放在对外进程,SGLang 为反切词单开一站;本项目把「要不要第三工位」做成后处理进程的开关,默认关掉。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `TLLM_WORKER_USE_SINGLE_PROCESS` · 单卡是否捏回单进程工人 | 环境变量 | `0`,拆进程 | 设 `1`:对外和执行器同一进程,方便打断点,流式变差 | 日志 `Using single process worker for TP1` |
| `--num_postprocess_workers` · 另起几个还原文字的进程 | 启动 | `0` | 调高:流式反切词不再堵对外进程;每份再装一套分词器 | `ps` 里后处理进程数;日志 `initiate postprocess workers` |
| `skip_tokenizer_init` · 不加载分词器 | 启动 | 关 | 开:请求必须自带 token 编号,响应没有文本 | 响应里只有编号没有 `text` |
| `tokenizer_mode` · 用快分词器还是慢分词器 | 启动 | `auto` | `slow`:不用快实现,切词更慢但兼容某些定制词表 | 启动是否报分词器加载失败 |
| `orchestrator_type` · 多卡工人怎么拉 | 启动 | 空,走 MPI | `ray` 或 `rpc`:原型编排,不是默认主干 | 日志 `Orchestrator is creating` 后面跟哪种执行器 |
| `backend` · 执行后端 | 启动 | `pytorch` | 填已删除的旧引擎名会直接报错 | 日志 `Using LLM with PyTorch backend` |
| `num_serve_frontends` · 几个 HTTP 前端挂到同一组执行器 | 启动 | `1` | 调高:多个前端进程连已经拉起的工人,自己不再孵化 MPI | 环境变量 `TLLM_EXECUTOR_ATTACH_INFO` 是否被消费 |

**怎么看。** 一是进程:默认应看到对外进程(命令行起服务或 Python 入口)加至少一个执行器工人;后处理进程默认没有。二是启动日志:`Using LLM with PyTorch backend` 说明走的是现在这条后端;`Using single process worker for TP1` 说明被捏回单进程,流式会差。三是请求级看返回里有没有文本、有没有 token 编号;跳过分词器初始化时只有编号。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡在线服务 | `trtllm-serve TinyLlama/TinyLlama-1.1B-Chat-v1.0` | 默认拆进程,切词不踩执行器循环 |
| 单卡调试或要回整表 logits | `TLLM_WORKER_USE_SINGLE_PROCESS=1 python -c "from tensorrt_llm import LLM; LLM('TinyLlama/TinyLlama-1.1B-Chat-v1.0')"` | 用单进程换掉 IPC,方便打断点;流式变差 |
| 高并发流式、对外进程 CPU 先满 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --num_postprocess_workers 2` | 用两份后处理进程换对外进程的反切词 CPU;多占一套分词器内存 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报旧引擎后端 | 日志是否 `Unknown backend` 或 `ValueError` | 不要填旧引擎名,默认就是 PyTorch |
| 流式很卡,GPU 利用率不低 | 日志有没有单进程工人那行 | 去掉单进程环境变量;需要回 logits 就接受这条代价 |
| 对外进程 CPU 100%,GPU 还没满 | 后处理进程数是不是 0 | 加后处理进程,把还原文字挪走 |
| 响应没有文本只有编号 | 是否跳过了分词器初始化 | 关掉该开关,或自己在外面还原 |
| 多卡起不来,提示 GPU 不够 | 本机可见卡数和并行度 | 先减并行,或确认没有挂到已有工人上却又去孵化 MPI |
| 入口脚本被跑了两遍 | 有没有主模块保护 | 拆进程的入口必须写在主模块保护里 |

## 六、常见误区

- **以为默认还是单进程多线程。** 那是旧印象。Linux 单卡默认已经拆成对外进程加执行器进程;单进程要环境变量或回 logits 才会走。
- **以为切词在执行器进程里。** 切词在对外进程预处理完才交出去。执行器循环拿到的是 token 编号。超长 prompt 卡住的是对外进程,不是 GPU 循环。
- **以为后处理进程默认开着。** 默认零个。没加进程时,反切词仍在对外进程,和切词抢同一把锁。
- **以为旧引擎编译链还能选。** 填旧后端名会报错。今天没有编译引擎这一步,权重直接进 PyTorch 运行时。
- **以为拆进程是为了多卡。** 多卡确实要多个 rank;单卡拆进程是为了流式,和张数无关。
- **以为执行器循环把调度和前向拆到了两个进程。** 它们在同一个执行器进程里。和对外进程隔开的是切词与 HTTP,不是调度和前向。
