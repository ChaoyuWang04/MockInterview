# TensorRT-LLM 02|调度器:IFB（连续批处理）与 overlap

静态批要等整批都生成完才收新人。IFB（连续批处理）让新请求的 prefill 和别人的 decode 挤进同一步,再把 CPU 收尾藏进下一步 GPU。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

在线服务里请求长短差一个数量级:有人只再要一个 token,有人刚把 100–500 个 prompt token 送进来。如果等整批都写完才换人,短请求占着坑空转,新请求的首 token 被拖到最长那条写完。如果每步只做一件事,一条超长 prompt 的 prefill 会把正在流式的 decode 顶出 10–50 毫秒以外的毛刺。

就算批组对了,每步 GPU 只算 10–50 毫秒,CPU 还要判停词、回包、挑下一批。这两段串行,小模型上 CPU 能吃掉一步的一半,吞吐和字间隔一起抖。

## 二、解法:同一步混批,CPU 收尾藏到下一步

最天然的直觉:每步重新组批,结束的立刻让位,新来的立刻占坑。本项目把这件事做成 IFB（连续批处理）:一步里同时有 context 请求和 generation 请求。容量调度先看这条还能不能保证算完、显存够不够;微批调度再按「一步最多几条、最多几个 token」往里塞。注释写明 decode 先占预算,剩下的才给新 prompt;切块开着时,塞不下的 prompt 切一块进来,而不是整条等。

![一步里已经在 decode 的请求先占预算,新 prompt 吃剩余;送进前向时 context 段排在 generation 段前面;切块关着则整条 prompt 塞不进就等,切块开着则切一块和 decode 同批](/opensource/TensorRT-LLM/02a-ifb-mixed-batch.svg)

张量还有一条硬约束:context 序列必须排在 generation 序列前面,不能按进批的时间顺序乱排。

重叠是另一条时间轴。默认走重叠循环:先把当前这一步的前向丢上 GPU,再去处理上一步的停词和回包。流水线并行换成另一条循环,不是这一页的默认单卡路径。关掉重叠才回到「前向完再收尾」的串行循环。

为什么实际不吃亏:decode 每步只占一两个 token,把新 prompt 的一块塞进同一矩阵,权重还是读一次。CPU 那 10–50 毫秒里有一段本来就和 GPU 串着,藏到下一步前向背后就淹没了。多出来的代价是结束的请求还会在 GPU 上多跑一截 decode。

## 三、代价

**切块默认关。** 关着时,剩余预算装不下整条 prompt,这条就进不了这一批。长 prompt 的首 token 被正在跑的 decode 挤着;反过来,一条刚好能整条塞进预算的超长 prompt 会把这一步撑满,decode 的字间隔出现一根和 prompt 长度成正比的刺。

**默认保证不踢人。** 容量策略默认是「一旦进批就保证能算完」,显存按最坏预留,看起来空着也可能不再收新人。改成尽量塞满才会在跑到一半把人暂停、重算,TTFT 好看、重算变多。

**重叠默认多一截 decode。** 停词是在上一步的 CPU 收尾里判的,GPU 已经在算下一步。每个请求一生多占一步算力和一格缓存。流水线并行、以及若干还不能和重叠共事的路径,会强制关掉重叠。

**预算是算力 token,不是缓存命中。** 前缀能复用的那一段不计入这一步要算的个数;看起来预算还很宽,实际新算的并不多。

## 四、一步里 prefill 和 decode 怎么进同一批

这一页比的是一步循环里新请求的 prefill 怎么跟别人的 decode 进同一批,以及 CPU 收尾藏不藏进下一步 GPU。对等列是 vLLM 和 SGLang。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 一步里能不能混 | 默认就能混:context 和 generation 同一步 | 默认混,长 prompt 切块和 decode 同批 | 默认一步只做一件事,prefill 优先;要混得手动开 |
| 谁先占预算 | 注释写明 generation 先占,剩下给新 prompt | 总额里 prefill 块和 decode 一起数 | 两个预算只数 prefill 新 token,decode 另有并发上限 |
| 切块默认 | 关;不开则整条 prompt 塞不进就等 | 切块是连续批处理的默认配套 | 切块开着,但是否混批另有开关 |
| CPU 收尾藏不藏 | 默认藏进下一步 GPU;关掉才串行 | 异步调度是实验开关,默认关 | 重叠默认开 |
| 进批保不保证算完 | 默认保证不踢人,显存按最坏留 | 当前这一步的块够不够就进 | 把「还会生成多长」估进准入,比例会自适应 |
| 张量顺序 | context 必须排在 generation 前面 | 按当前步要算的 token 摞行 | 一步一种阶段,没有这条前后约束 |

重心在本项目:默认就把新 prompt 和别人的 decode 放进同一步,但切块要手动开,否则长 prompt 仍可能整条进不来。重叠默认开,和 SGLang 同类、和 vLLM 默认关相反。保证不踢人换的是显存利用率,不是混批本身。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `disable_overlap_scheduler` · 关掉 CPU 与 GPU 重叠 | 启动 YAML | 重叠开着 | 加上后关掉:每步多一截 CPU,吞吐和字间隔变差;流水线并行或尚未支持重叠的路径会强制关 | 是否走重叠循环;结束请求是否还多跑一步 |
| `enable_chunked_prefill` · 长 prompt 切块进批 | 启动 | 关 | 开:prompt 切一块和 decode 同批,首 token 稳、整条超长不再一次撑满一步 | 一步里同时有 context 和 generation;长 prompt 是否跨多步 |
| `max_num_tokens` · 一步最多算多少 token | 启动 | `8192` | 调小:一步更短、首 token 稳、长 prompt 更依赖切块;调大:矩阵更大、首 token 和字间隔一起变差 | 迭代日志里这一步的 token 数是否贴顶 |
| `max_batch_size` · 一步最多几条请求 | 启动 | `2048` | 调小:并发硬顶下降;不能大于一步 token 上限 | 同时在跑的条数是否贴顶而 token 还空 |
| `capacity_scheduler_policy` · 显存不够时保不保证算完 | 启动 YAML | 保证不踢人 | 改成尽量塞满:暂停、重算变多,看起来更满 | 是否出现暂停列表;缓存占用是否长期偏低 |
| `context_chunking_policy` · 多条要切的 prompt 怎么分块 | 启动 YAML | 空 | 先来先服务、均分进度、或强制切;只在切块开着时有意义 | 多条长 prompt 的首 token 是否轮流往前走 |
| `waiting_queue_policy` · 还没进批的队列怎么排 | 启动 YAML | 先来先服务 | 改成按优先级:大数先服务,并列再按到达 | 带优先级的请求是否插队 |
| `use_python_scheduler` · 不用 C++ 调度器 | 启动 YAML | 关,走绑定 | 开:纯 Python 调度,方便改逻辑,热路径变慢 | 是否仍走绑定容量调度 |
| `print_iter_log` · 打每步日志 | 启动 YAML | 关 | 开:每步打印批大小与耗时 | 标准输出的迭代行 |
| `batch_wait_timeout_ms` · 凑批最多等多少毫秒 | 启动 YAML | `0`,不等 | 大于 0:本地攒到条数或超时再开步,利用率换首 token | 空闲时一步是否被故意拖长 |

**怎么看。** 一是一步里是否同时出现 context 和 generation:切块关着时,长 prompt 经常整条缺席。二是迭代日志(要打开打印):看这一步 token 数有没有贴着上限、条数有没有贴着并发顶。三是关掉重叠之后,GPU 利用率掉、字间隔变稳但变慢,用来确认问题是不是 CPU 收尾而不是混批本身。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。重叠开关不在命令行长选项里,要写进附加配置文件。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡在线聊天,短回答为主、偶发长 prompt | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --enable_chunked_prefill --max_num_tokens 8192` | 用切块换掉「整条 prompt 进不来」;重叠保持默认开 |
| 排障、对齐 token、或功能还不支持重叠 | `trtllm-serve TinyLlama/TinyLlama-1.1B-Chat-v1.0 --extra_llm_api_options overlap-off.yaml`,文件里写关闭重叠 | 用串行循环换可复现的一步一收尾;吞吐变差 |
| 超长上下文、首 token 有上限 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --enable_chunked_prefill --max_num_tokens 4096 --max_batch_size 64` | 用更小的一步预算换首 token;并发顶一起压住 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 长 prompt 一直排队,decode 很满 | 切块开了没有 | 打开切块,让一块和 decode 同批 |
| 长 prompt 一来字间隔一根刺 | 切块关着且整条塞进了一步预算 | 打开切块,或把一步 token 上限调小 |
| 小模型 GPU 利用率 50–70% | 重叠是不是被关掉 | 去掉关闭重叠;流水线并行先换回单段 |
| 缓存占用长期偏低、队列却很长 | 是不是保证不踢人把最坏长度都留下了 | 先减并发顶,不要一上来改成尽量塞满 |
| 一步 token 很少、条数却贴顶 | 并发顶比 token 预算先撞上 | 加大并发顶,或接受短 decode 为主 |
| 关掉重叠之后答案变了 | 多出来的那一步 decode 被拿去当最终 token | 收尾时丢掉多生成的那一个,不要当确定性开关 |

## 六、常见误区

- **以为 IFB（连续批处理）等于切块默认开。** 混批是默认能力,切块是另一个开关,默认关。关掉时超长 prompt 仍可能整条进不来,或整条撑满一步。
- **以为送进前向的顺序就是进批的优先级。** 预算上 decode 先占坑,张量上 context 必须排在前面。两件事不要当成同一条规则。
- **以为重叠会改下一个 token。** 它只改 CPU 处理停词的时机。多跑的那一步是收尾浪费,不是另一种采样。
- **以为保证不踢人就是永不排队。** 它保证的是已经进批的人能算完,不是保证队列里的人立刻进批。看起来空着不再收人,常常是预留太狠。
- **以为一步 token 上限只管 prompt。** decode 也占个数。短回答高并发时,先撞上的经常是条数顶而不是 token 顶。
- **以为流水线并行还走同一条重叠循环。** 多段流水线换了另一条循环;不要拿单卡重叠的开关去解释那段空档。
