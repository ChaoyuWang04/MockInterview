# TensorRT-LLM 10|量化

满精度权重先把卡撑满;精度选错时矩阵乘落到慢路径,间隔比不量化还长。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

权重按满精度装时,坏的是**能不能把模型拉起来**。70B 级按 BF16 就要一百多 GB,一张卡先被权重吃光,KV 池还没划,并发为零。

权重砍掉一半并不自动变快。配方表里有整张量 FP8、块缩放 FP8、按行 FP8、NVFP4,还有只压权重的 4 bit 配方。卡代次对不上、checkpoint 声明和启动覆盖拧着,前向仍走宽精度乘法,还要多一次反量化。这时坏的是**每个 token 的间隔**:显存省了,吞吐比不量化还差。

KV 是另一笔账。长上下文、高并发时池比权重大。权重已经压过、KV 仍按满精度写,槽数上不去;反过来只压 KV、注意力每步先还原,间隔同样拉长。

## 二、解法:预量化权重直接进运行时,KV 可单独降精度

最天然的直觉:量化在仓库外做完,服务只读已经压好的权重。本项目默认就是这条路。PyTorch 后端直接吃 Model Optimizer 出的预量化 checkpoint,不再走已删除的引擎编译链。checkpoint 里的量化段写明权重用哪套配方、KV 要不要一起压;启动时读到这份文件就把运行时配方对齐,不必再手填一份。

KV 可以单独改。checkpoint 没声明 KV 量化时,仍可在启动时把池改成 FP8;文档写明即便仓库默认没开,也能手动打开。NVFP4 的 KV 不行:要离线再出一份,而且当前只允许权重已经是 FP8 时再开。启动覆盖会盖掉 checkpoint 里的 KV 精度,两边不一致打警告,不静默混用。

![预量化 checkpoint 进运行时:仓库里的量化段决定权重配方;虚线是启动时单独改 KV 精度,FP8 可对未声明的 checkpoint 覆盖,NVFP4 的 KV 必须先离线出好](/opensource/TensorRT-LLM/10a-prequant-runtime-kv.svg)

为什么实际不吃亏:校准和分组在离线做,热路径只加载低精度张量和系数。权重与 KV 两套字段分开,满精度装不下时先换预量化权重;池先满时再动 KV,不必把三笔账绑死成同一种精度。

## 三、代价

**服务不做在线量化。** 手里只有满精度权重,这里不会在加载时现压。要另走 Model Optimizer 的离线脚本,再把导出目录当模型路径。

**配方绑卡代次。** Hopper 上有整张量、块缩放、按行的 FP8,没有 NVFP4 权重;Blackwell 消费级卡没有块缩放 FP8,也没有 NVFP4 的 KV。矩阵写着支持、卡不对,启动或第一次前向才会爆。

**覆盖 KV 会改全局配方。** 显式写成 FP8 或 NVFP4 时,运行时那份 KV 算法跟着改;混合精度 checkpoint 还要把每一层的 KV 算法改成同一个,否则池按覆盖后的元素宽度分配、注意力仍按 checkpoint 读写,会越界。

**NVFP4 的 KV 不能只改一个开关。** 文档要求离线时权重走 FP8、KV 走 NVFP4;只在启动里写 NVFP4、权重仍是满精度,当前不支持。

## 四、预量化怎么跑、KV 单独降精度、选错会不会更慢

这一页比的是预量化权重怎么直接跑、KV 要不要单独降精度、精度选错会不会比不量化还慢。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 权重从哪来 | 默认读已经量化好的仓库,对齐配方后进 PyTorch 运行时 | 命令行指定方法,也可读仓库自带配置;部分方法允许加载时现压 | 不指定就检测仓库;指定了和仓库对不上大多直接报,只有一条跨格式重量化 |
| KV 能不能单独改 | 可以。自动表示沿用仓库;显式 FP8 可盖未声明的仓库;NVFP4 要离线出好 | 另一路精度开关,和权重方法互不干涉 | 另一路精度开关;自动时若仓库声明了 FP8 的 KV 就解析成 FP8 |
| 选错会怎样 | 卡代次或配方对不上,走不到对应矩阵乘,间隔比满精度还长;覆盖和仓库拧着打警告或断言 | 多数配错不报错,只是慢;启动期按硬件和配置筛 kernel | 有一份已优化名单,不在名单里启动警告可能比不量化还慢 |
| 在线现压 | 本页这条主干没有 | 有白名单,表外组合静默不量化 | 加载时 FP8 现压;另有只转专家的在线 NVFP4 |
| 离线工具 | 官方指向 Model Optimizer,导出后再当模型路径 | 仓库外量化,引擎负责加载 | 仓库外量化,引擎负责加载 |

重心在本项目:量化发生在进服务之前;运行时负责读配方、让 KV 精度可以单独覆盖,不在热路径上现做校准。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `quant_config.quant_algo` · 权重与激活用哪套算法 | YAML 的 `quant_config`,或由仓库写入 | 空,等仓库填 | 空且仓库有量化段:对齐仓库;手填且与仓库冲突:启动报冲突 | 日志 `Found hf_quant_config.json, pre-quantized checkpoint is used`、`Setting quant_algo=` |
| `kv_cache_config.dtype` / `--kv_cache_dtype` · KV 池存什么精度 | 启动或 YAML | `auto`,沿用仓库的 KV 算法,不改写 | `fp8`:覆盖为 FP8,未声明的仓库也能开;`nvfp4`:覆盖为 NVFP4,要离线配方;`fp8_ds_mla` 只走 YAML,命令行选项没有这一项 | 日志 `Overriding checkpoint kv_cache_quant_algo`;`auto` 时无覆盖行 |
| `quant_config.kv_cache_quant_algo` · 运行时 KV 算法 | 由上面精度同步,一般不要手填 | 空 | 精度写成 `fp8` 或 `fp8_ds_mla` 时同步成 FP8;写成 `nvfp4` 时同步成 NVFP4;`auto` 不碰 | 与仓库冲突且未走覆盖:报 `conflicting with` |
| `quant_config.group_size` · 分组量化一组多少个数 | YAML,常被仓库覆盖 | `128` | 只对按组的 4 bit 配方有意义;与仓库分组对不上会按仓库改写 | 日志 `Setting group_size=` |
| Model Optimizer 离线脚本 · 仓库外出预量化权重 | 仓库外,不是本服务启动参数 | 无 | `--quant fp8` 出 FP8 权重;再加 `--kv_cache_quant nvfp4` 出 NVFP4 的 KV,且必须同时 `--quant fp8` | 导出目录出现 `hf_quant_config.json` |

**怎么看。** 一是启动有没有 `Found hf_quant_config.json`:有就是预量化路径,没有就仍是满精度权重。二是 `Setting quant_algo=` 是否和仓库一致;手填冲突会直接失败。三是 KV:`auto` 不应出现覆盖警告;显式 `fp8` 或 `nvfp4` 在仓库已有另一套 KV 算法时会打 `Overriding checkpoint`。四是无法识别的 KV 方案会警告后关掉 KV 量化,池仍按满精度划,槽数不会翻倍。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| Hopper 或 Blackwell,仓库已是 Model Optimizer 的 FP8 | `trtllm-serve nvidia/Llama-3.1-8B-Instruct-FP8 --config fp8-prequant-serve.yaml`(文件可只写注释或空对象,不要再填一套 `quant_algo`) | 用预量化权重换满精度装不下;配方以仓库为准,手填反而容易冲突 |
| 权重已能装下,长上下文把 KV 池先吃满 | `trtllm-serve Qwen/Qwen2.5-14B-Instruct --kv_cache_dtype fp8 --config fp8-kv-only.yaml`(文件写 `kv_cache_config: {dtype: fp8}`) | 用 KV 槽数约翻倍换一点精度;注意力不融合反量化时间隔会变长 |
| Blackwell 数据中心卡,已离线出 FP8 权重加 NVFP4 的 KV | `trtllm-serve /path/to/fp8-nvfp4-kv --kv_cache_dtype nvfp4 --config nvfp4-kv-hopper-off.yaml`(文件写 `kv_cache_config: {dtype: nvfp4}`) | 用更窄的 KV 换更长上下文;Hopper 与消费级 Blackwell 矩阵写不支持,不要套 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 满精度 OOM,权重都没装完 | 模型路径是不是预量化仓库、有没有 `hf_quant_config.json` | 换成 Model Optimizer 出的 FP8 或 NVFP4 仓库,不要指望服务现压 |
| 开了量化显存降了,每个 token 更慢 | 卡代次是否落在该配方的硬件表上 | Hopper 用整张量或块缩放 FP8;NVFP4 权重只给 Blackwell |
| 启动报 `quant_algo` 冲突 | YAML 是否又写了一套算法 | 删掉手填,让仓库写入 |
| 启动报只有 FP8 或 NVFP4 允许作预量化仓库的 KV | 是否给满精度仓库指定了别的 KV 算法 | KV 只留 FP8 覆盖,或走离线 NVFP4 |
| 写了 NVFP4 的 KV 起不来 | 离线是否同时 `--quant fp8`;卡是不是 sm100 或 sm103 | 按文档重出 checkpoint;消费级 sm120 不要开这条 KV |
| 覆盖 KV 之后非法访问或答案漂 | 是不是混合精度仓库、各层 KV 算法是否被一起改写 | 看覆盖警告;不要只改全局、留下按层旧宽度 |
| `auto` 时期望 KV 已是 FP8,槽数却没翻 | 仓库有没有声明 KV 算法 | 没有声明就显式 `--kv_cache_dtype fp8` |
| 命令行找不到 `fp8_ds_mla` | 这一项不在命令行选项里 | 写进 YAML 的 `kv_cache_config.dtype` |

## 六、常见误区

- **以为启动填一种精度就会在加载时现压。** 人们从别的引擎带着「给个方法名就在线量化」过来。这里默认只跑已经量化好的仓库;满精度路径不会在加载时逐层压。
- **以为文档说 Hopper 上用 FP8,字段默认就是 FP8。** 那是硬件表上的能力,不是默认值。权重算法默认空,KV 精度默认自动,沿用仓库。
- **以为 KV 精度会跟权重走。** 两套字段。FP8 权重仓库仍可能把 KV 留在满精度;`auto` 不会自作主张改 KV。
- **以为 NVFP4 的 KV 和 FP8 的 KV 一样,改一个启动项就行。** FP8 可以对未声明的仓库覆盖;NVFP4 要离线出,且权重必须已经是 FP8。
- **以为配方表有 4 bit 就能在 Ampere 上跑 FP8 权重。** Ampere 硬件表只给了 FP8 的 KV 和 W4A16 系,没有 FP8 权重那几列。
- **以为旧的引擎编译链还要先编再量化。** 填旧后端名会报错。今天权重直接进 PyTorch 运行时。
