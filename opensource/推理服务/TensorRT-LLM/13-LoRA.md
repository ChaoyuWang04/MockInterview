# TensorRT-LLM 13|LoRA

多租户各带一套微调，若每套都复制一份底模，KV 池被切碎；若全往显存里叠，种类一多就 OOM。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过，「当前」与「默认」都指这组基准。

## 一、核心问题

一份底模要同时伺候多套适配器（挂在线性层上的一对瘦矩阵，每个业务方一套）。请求只带适配器名，底模不能复制。种类一杂，两处先坏：

**调度按显存页拦新种类。** 同一种已经在本批里，再来一条不占新页；新名字要加页。页预算顶满后，这条请求本批进不去，留在队列。此时 KV 和算力可能都空着，坏的是排队时间与首 token。热门长请求一直占着设备缓存，冷门名字可以一直等。

**页划太大就和 KV 抢显存。** 设备缓存可按空闲显存比例划，也可按「同时几套 × 秩上限 × 模块数」买断。开满又叠量化、图、KV 池，启动或换手时直接 OOM。主机侧还有一份缓存给预取，默认约 1 GB；只加设备页、不管主机，换手时仍要读盘，全体间隔抖一下。

## 二、解法:底模一份，适配器按页进设备缓存，请求点名

最天然的直觉：底模只装一份，适配器按名字挂上；同一批里不同请求可以点不同名字。本项目就是这条路。

![请求带适配器名后，调度器先看设备页够不够：够就装进设备缓存再进槽位前向，不够则虚线跳过、请求留在队列；底模常驻一份，适配器占有上限的设备页，主机侧另有缓存给预取](/opensource/TensorRT-LLM/13a-multi-adapter-slots.svg)

启动先开一份适配器配置：目录可空，但目标模块和秩上限要能罩住以后要热装的那批，否则只能重启。磁盘认两种格式：HuggingFace 的 PEFT，以及 NeMo（NeMo 只覆盖注意力里那一组融合 QKV）。量化底模可以叠适配器；适配器精度和底模可以不是同一套，原生低精度小乘只在部分卡代次上走，走不了就升到计算精度。

进批之前，调度器用设备页当预算：本批没见过的名字才加页，加超了就把这条跳过。进了批，设备缓存里有就直接用；没有则从路径读进主机再拷上卡。decode 走图时另有一套槽位管理：槽数默认等于同时在卡上的套数上限（没填时按 8），槽满按最久没用换人；不用适配器的请求不占真槽，用一个哨兵下标。图要固定地址，所以槽表改了只改指针，不重新抓图。prefill 和混批仍走逐请求那张表。可断的 prefill 图和适配器配置互斥，启动直接拒。

为什么实际不吃亏：瘦矩阵比整份底模小两个数量级，设备页只为「这一批同时活着的种类」买单，不是为历史上出现过的每套买单。主机缓存把换手的读盘挡在前向前面；页不够是排队而不是把所有租户的权重叠进同一块显存。

## 三、代价

**设备页和 KV 抢同一块卡。** 按套数买断时，启动就按秩上限乘模块数占满，实际只装两套也按上限掏。比例划法吃的是装完底模之后的空闲显存，KV 池跟着变小。

**本批种类不能超过槽上限。** 超过是断言，不是再排队。槽给图用；eager 那条不受槽数约束，但仍受设备页约束。

**换手要搬。** 设备上没有的名字先读盘或从主机拷。默认同步叠在底模计算上；打开重叠才走第二条流，访存紧时才划算。

**目标模块空且目录也空，会按默认映射把能挂的模块全开。** 注释写明显存会很难看。QKV 三件套缺一角会用零张量补上，不报错。

**图和适配器要谈判。** 专用管理器只服务纯 decode 图；有 context 行就退回 eager。打开「有适配器和没适配器各抓一套图」时，和注意力数据并行互斥。

## 四、多适配器怎么共服一个底模、切换时排队还是显存叠加

这一页比的是多适配器怎么共服一个底模、切换时排队还是显存叠加。对等列是 vLLM 和 SGLang。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 底模几份 | 一份，请求点名适配器 | 一份，请求点名 | 一份，请求点名 |
| 卡上同时几套 | 设备页预算；没填套数时还可按空闲显存比例划 | 槽位数买断 | 一批种类上限，默认含底模那一格 |
| 装不下怎么办 | 本批跳过，请求留队列 | 槽满踢最久没用；内存侧默认等于槽数 | 槽满等或踢；可开排空器对付热门霸位 |
| 不用适配器占不占格 | 不占真槽，哨兵下标 | 池外负数哨兵 | 底模占一格 |
| 主机侧 | 默认可划约 1 GB 给预取 | 内存容量默认等于格数 | 默认不限，设了才卸 |
| 和图 | decode 用专用槽位管理器；可断 prefill 图直接拒 | 捕图要造假适配器，否则捕到早退 | kernel 总发射，空格早退 |
| 格式 | HuggingFace 与 NeMo（NeMo 只融合 QKV） | 以 HuggingFace PEFT 为主 | HuggingFace PEFT |

重心在本项目：用设备页卡住「同时活着的种类」，用排队换掉显存叠加；图不重讲，只留专用槽位管理器和可断图那条拒绝。

## 五、调参与观测

启动侧的适配器池、页预算和图开关改了要重新拉起整个作业；请求体里点名哪一套不用重启。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `lora_config` · 打开多适配器路径 | YAML | 空,不开 | 配了才走设备缓存和槽位;只开 `enable_lora` 且同时给了本项时,前者被忽略 | 日志 `Initialized CUDA Graph LoRA manager` |
| `lora_config.lora_dir` · 启动预装的目录 | YAML | 空列表 | 空:自定义词嵌入或输出头不会套上;和非空目标模块至少要有一头,否则按默认映射全开 | 警告 `lora_dir is empty`;`all LoRA modules will be expected` |
| `lora_config.lora_target_modules` · 哪些层留位 | YAML | 空,可从目录推断 | 空且目录也空:默认映射全开,显存暴涨;QKV 缺角补零 | 启动警告;答案是否该变却没变 |
| `lora_config.max_lora_rank` · 按多大秩预留 | YAML | `64` | 调高能热装更大秩,设备页线性涨;超过上限的装不进 | 装载失败或页预算打满后排队 |
| `lora_config.max_loras` · 设备上同时几套 | YAML | 空,不按套数买断 | 有值:设备模块层数按秩×模块×套数写死;空:图槽仍按 8 | 日志 `max N adapters`;排队变长还是 OOM |
| `lora_config.max_cpu_loras` · 主机侧同时几套 | YAML | 空 | 有值:主机模块层数按同样公式写死 | 换手是否还读盘 |
| `lora_config.lora_ckpt_source` · 权重格式 | YAML 与请求 | `hf` | `nemo`:只认融合 QKV | 装载 `KeyError` 或不支持的键 |
| `lora_config.overlap_lora_and_base` · 适配器算子与底模重叠 | YAML | 关 | 开:第二条流,访存紧时间隔可能降 | 压测 TPOT;第二条流是否在profiler里 |
| `lora_config.cuda_graph_specialize_lora` · 有无适配器各抓一套图 | YAML | 关 | 开:无适配器批少走适配器图;与注意力数据并行互斥 | 启动 `cannot be used when attention DP` |
| `peft_cache_config.device_cache_percent` · 空闲显存划多少给设备缓存 | YAML | `0.02` | 调高:同时种类多、排队少,KV 池变小;未设套数时才靠它 | 启动后 KV 槽数变少;OOM |
| `peft_cache_config.host_cache_size` · 主机缓存字节 | YAML | `1073741824`(1 GB) | 调高:预取更宽;预取目录字段当前不支持,填了启动拒 | 报错 `LoRA prefetch is not supported` |
| `lora_request` · 这条请求用哪一套 | 请求 `extra_body`;Python 的生成接口 | 空,走底模 | 要名字、整数编号、路径;路径未装过则现读 | 响应是否像该业务;错误是否缺路径 |

**怎么看。** 一是启动:有适配器配置时应看到图侧管理器那行,以及设备缓存用的流。二是排队:队列长、在跑的少、KV 占用也低,三者同时出现是卡在设备页,不是卡在 KV。三是请求:OpenAI 兼容口把适配器写在额外字段里,不要只改 `model` 名指望换人格。四是格式:NeMo 键对不上会在装载时报不支持的键。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 两三套适配器、流量都热 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --config lora-few-hot.yaml`(文件写 `lora_config: {lora_target_modules: [attn_q, attn_k, attn_v], max_lora_rank: 16, max_loras: 4, max_cpu_loras: 4}`) | 用按套数买断的设备页换掉换手读盘;KV 少一截 |
| 十几个租户、同时只要七八套在卡上 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --config lora-slots8-host.yaml`(文件写 `lora_config: {lora_target_modules: [attn_q, attn_k, attn_v], max_lora_rank: 32, max_loras: 8, max_cpu_loras: 16}`) | 用 8 个设备位加更宽的主机缓存换多租户;本批超过 8 种会断言 |
| 种类很多、显存紧、接受排队 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --config lora-percent-queue.yaml`(文件写 `lora_config: {lora_target_modules: [attn_q, attn_k, attn_v], max_lora_rank: 16}` 和 `peft_cache_config: {device_cache_percent: 0.05, host_cache_size: 2147483648}`) | 用 5% 空闲显存和 2 GB 主机换同时种类;页满就排队,不要再把套数开到 10–50 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 队列长、KV 占用低 | 本批是不是在换新名字、设备页是否打满 | 加 `max_loras` 或提高设备缓存比例;热门钉在主机侧 |
| 启动 OOM,底模明明装得下 | 目标模块是否被默认映射全开;套数×秩是否按上限买断 | 写死真正用到的模块;把秩上限降到真实最大值 |
| 换适配器全体间隔抖 | 设备上有没有这一套;主机缓存够不够 | 提高 `max_cpu_loras` 或主机字节;热的预装进 `lora_dir` |
| 答案完全像底模 | 请求有没有 `lora_request`;名字、编号、路径是否齐 | 补额外字段,不要只改模型名 |
| 启动报可断 prefill 图不支持 LoRA | 是否同时开了可断后端和适配器配置 | 关掉可断,或不要适配器 |
| 启动报图特化与注意力数据并行 | `cuda_graph_specialize_lora` 是否开着 | 关掉特化,或关掉注意力数据并行 |
| 装 NeMo 失败 | 是不是只含融合 QKV 以外的模块 | 换成 HuggingFace,或只挂那一组 |
| 一批直接崩在断言 | 独特名字是否多于槽上限 | 把 `max_loras` 加到本批种类以上,或打散请求 |
| 填了预取目录起不来 | `lora_prefetch_dir` 当前不支持 | 删掉该字段 |

## 六、常见误区

- **以为多租户就是多起几份服务。** 人们从「一套适配器一份权重」过来。这里底模只有一份;复制进程会把 KV 切碎,这正是要避免的。
- **以为套数空着就是不占显存。** 空着不按套数买断,但设备缓存仍按空闲显存比例划,默认 2%;图槽仍按 8。不写不等于零开销。
- **以为目标模块空着最省心。** 目录也空时会按默认映射全开,注释已经警告显存。热装什么都能进,每层却多两次小乘。
- **以为请求改模型名就会换人格。** OpenAI 兼容口要额外字段带名字、编号和路径。只改模型名仍走底模。
- **以为页不够会 OOM。** 调度器先跳过本批。看到的是排队而不是立刻爆显存;把比例或套数开到和 KV 抢光,那才会 OOM。
- **以为 decode 图和适配器不能共存。** 05 章讲图怎么抓;本章只是专用槽位管理器让指针可改、图不用重抓。互斥的是可断 prefill 图,以及「两套图」加注意力数据并行。
- **以为 NeMo 和 HuggingFace 能随便混模块。** NeMo 只认融合 QKV。别的键会在装载时报不支持。
