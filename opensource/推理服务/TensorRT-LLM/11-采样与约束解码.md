# TensorRT-LLM 11|采样与约束解码

前向交出来的是一张词表那么宽的分数表。采样要从里面挑出下一个 token；格式约束如果每步只许吐一个,吞吐会被打穿。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

在线 decode 每步 GPU 只算 10–50 毫秒。这一层如果在采样前还要在 CPU 上给整张词表填一张「现在允许哪些 token」的位图,坏的是**吞吐和字间隔**,GPU 并没有更忙。

**带 JSON、正则、文法的负载,坏的是每步只出一个 token。** 花括号、逗号、字段名在文法里常常是确定的,可本项目没有「一次跳过一段固定字符」的调用点:位图填完仍只采一个,再进下一步前向。长 schema 的输出长度几乎等于 GPU 步数,吞吐被打穿。

**同一条循环里还要给重叠收尾、给推测解码核草稿。** 填位图、喂状态机、拷掩码都是执行器进程上的 CPU 活,和停词回包抢同一段空档;草稿还要按个回滚状态机。重叠藏不住这段,推测解码的草稿长度也喂不饱。

不带约束、温度也不写时,默认就是贪心,这一层几乎看不见。问题只在「要格式」和「要随机」混进同一条热路径之后才爆。

## 二、解法:采样只留一套,约束和改分都挂在采之前

最天然的直觉:前向一结束立刻 argmax。本项目默认就是这条。温度、候选集、惩罚不写时,一律当贪心;只有显式打开随机旋钮,才走完整抽样。旧的另一套采样器已经删掉,入口再点它的名字会直接拒。

约束不是生成后再校验,而是采样前把不合法的位置写成负无穷。调用方自带的改分回调挂在前向末尾、约束之前;约束在执行器循环里填位图、拷到 GPU、压进 logits,然后才抽样。带约束的请求不能走图内采样那条快路,否则采到的是还没掩过的分数。

![前向交出分数表之后:绿是每步都走的前向与采样,黄是调用方改分,紫是带约束才走的 CPU 填位图。实线是默认贪心路;虚线箭头落到填位图,表示只有挂了文法的请求才进这一站,填完仍只采一个 token](/opensource/TensorRT-LLM/11a-sample-before-guide.svg)

为什么实际不吃亏:不带约束时,这一站根本不起文法解码器,采样器按策略把同批请求归组,贪心走快路。付代价的是那些真要格式的行。

## 三、代价

**文法后端默认是空的。** 空就不会建解码器,请求上的格式字段没有掩码可压;点名工具调用那条路会在 HTTP 上直接 400,普通 JSON 格式则可能静默长成自然语言。要约束必须在启动配置里点名两个文法库之一,改了要重启。

**填位图是执行器循环上的逐行 CPU。** 并发越高、词表越宽,这一步越顶重叠留给停词的空档。推测解码还要按草稿逐个推进、核错再回滚,采样侧把 CPU 抢穿,草稿再长也换不成吞吐。

**每步仍然只出一个新 token。** 确定片段不会被一次写进序列,长 JSON 的 GPU 步数下不来。

**带约束或改分的请求会把整批拉出图内采样。** 批里混进一条,快路作废。

## 四、采样怎么从 logits 出 token、文法约束挂在哪

这一页比的是采样怎么从 logits 出 token、文法约束挂在哪、会不会把 overlap 和推测解码的 CPU 抢穿。对等列是 vLLM 和 SGLang。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 采样器几套 | 只剩一套 PyTorch 采样器,旧引擎那套已删 | 默认一套,另有实验路径 | 一套,可换 kernel 后端 |
| 不写温度时 | 贪心 | 按接口与模型配置,常不是纯贪心 | 原生路由偏 1.0,兼容路由先读模型配置 |
| 约束挂在哪 | 前向末尾改分,然后执行器在采样前压位图 | 处理器链里,采样前掩码 | 惩罚之后、偏置之前压掩码 |
| 文法后端默认 | 空,不建解码器 | 自动选,带一条回退链 | 默认就是那一个库,不回退 |
| 填位图在哪 | 执行器循环里逐行填,和重叠收尾抢 CPU | 高并发可丢线程池,缓冲开服就备好 | 调度器进程逐行填,编译另进文法队列 |
| 约束一步几个 token | 没有跳跃前填,一步一个 | 可一次采多个再适配掩码 | 跳跃接口在,调度器没有调用点,也是一步一个 |

重心在本项目:默认贪心、默认不装文法。装上之后约束坐在采样前的 CPU 上,一步仍只出一个 token,重叠和推测解码在采样侧看到的就是这段被抢走的空档。

## 五、调参与观测

文法后端和是否读模型自带的生成配置是启动项,改了要重新拉起;温度、候选集、惩罚、单条约束挂在请求上,不用重启。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `guided_decoding_backend` · 用哪套文法库 | 启动 YAML | 空,不建解码器 | `xgrammar` 或 `llguidance`:启动建解码器,请求上的 JSON、正则、文法才真压掩码;填别的名字启动失败 | 日志 `Guided decoder initialized with backend` |
| `generation_config` · 不写温度时要不要读模型自带生成配置 | 启动 | `trtllm`,保持本项目默认贪心 | `auto`:请求没写的项可被模型 JSON 里显式字段补上,贪心不再保证 | 同 prompt 不写温度是否仍贪心 |
| `temperature` / `top_k` / `top_p` / `min_p` · 分布多尖、候选留多少 | 请求 | 全空则贪心 | 温度 0、候选 1、或最小概率 1 仍贪心;否则缺项补成温度 1、候选全开 | 同 prompt 多次是否变化 |
| `repetition_penalty` / `presence_penalty` / `frequency_penalty` · 说过的词怎么扣 | 请求 | 空,运行时按 1 / 0 / 0 | 在温度之前改分;出现次数惩罚要在推测配置里预先开工作区,否则带惩罚的请求直接被拒 | 重复率;请求是否被拒 |
| `guided_decoding` · 这一条必须符合的 JSON、正则或文法 | 请求 | 空 | 后端已点名才压掩码;与点名工具调用互斥 | 输出是否能被 schema 解析;HTTP 400 |
| `max_tokens` · 最多新生成多长 | 请求 | `32` | 调大才写得完长 JSON;不写不是「模型自己停」 | 输出在 32 处被截断 |
| `logprobs` · 每步回几个对数概率 | 请求 | 空,不回 | `0`:只回抽中那个 token 的对数概率,和已删那套采样器的约定不同 | 响应里对数概率条数 |
| `logits_processor` · 调用方改分 | 请求 | 空 | 前向末尾、约束之前原地改;能改到负无穷以外 | 是否采到不该出现的 token |
| `sampler_type` · 旧采样器开关 | 启动,已删除 | 无此参数 | `auto` 或本项目采样器名:警告后忽略;`TRTLLMSampler`:启动失败 | 警告或 `ValueError` |
| `enable_in_graph_sampling` · 采样是否进 CUDA graph | 启动 YAML | 关 | 开:不带约束的贪心 decode 可进图;批里有约束或改分则整批退回图外 | 带 JSON 的请求间隔是否仍贴着图外 |

**怎么看。** 一是启动日志有没有 `Guided decoder initialized with backend`:没有就还没装文法。二是点名工具调用却没装后端,HTTP 直接 400。三是输出在大约 32 个新 token 处齐刷刷结束,先看请求有没有把最大长度写上去。四是关掉重叠之后字间隔变稳但更慢,用来确认慢的是采样前这段 CPU,而不是前向本身。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡聊天,不需要 JSON,要默认贪心 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --config sample-unconstrained.yaml`(文件写 `generation_config: trtllm`) | 用本项目默认贪心换可复现短答;不要开 `auto`,否则模型 JSON 可能把温度补上 |
| 工具调用与 JSON 为主 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --config guided-xgrammar-json.yaml`(文件写 `guided_decoding_backend: xgrammar`) | 用启动时装上文法换格式合法;每步仍只出一个 token,吞吐换正确性 |
| 高并发短 JSON,CPU 已经贴着重叠空档 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --config guided-llguidance-cpu.yaml`(文件写 `guided_decoding_backend: llguidance`) | 换另一套文法库试填位图开销;不要和推测解码叠在同一实例上抢 CPU |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| JSON 请求仍在说人话 | 启动有没有文法后端那行日志 | YAML 写上 `xgrammar` 或 `llguidance` 后重启 |
| 点名工具调用 400 | 后端是不是空的 | 先装文法,再发带格式的请求 |
| 长 JSON 总在很短处截断 | `max_tokens` 是不是还停在 32 | 请求里把上限写到 schema 需要的长度 |
| 小模型 GPU 不满,带格式后字间隔抖 | 填位图是否和重叠收尾抢 CPU | 约束实例不要叠推测解码;或把格式请求分到另一实例 |
| 同 prompt 不写温度却不贪心 | `generation_config` 是不是 `auto` | 改回 `trtllm`,或请求里写死温度 0 |
| 启动要旧采样器 | 是否还传 `sampler_type` | 删掉该参数;对数概率按 `0` 回抽中项来迁 |

## 六、常见误区

- **以为不写温度就是 1.0。** 人们从别的引擎带着这个默认。本项目三个旋钮都空时是贪心;只有显式打开随机,缺项才补成温度 1。
- **以为请求里带了 JSON schema 就一定约束。** 后端默认空,解码器根本没建。点名工具调用会 400,普通格式字段可能被静默丢掉。
- **以为约束能一次吐出整段确定字符。** 位图按下一步填,采样仍一步一个,没有跳跃前填。
- **以为重叠能把填位图藏进 GPU。** 掩码必须压进当前这一步的分数表,才能再采样。它和停词回包抢的是同一段 CPU,不是可以挪到下一步 GPU 背后的那种收尾。
- **以为 `max_tokens` 会跟模型自己的结束符走。** 默认 32。长 JSON 先撞上限,不像「写完为止」。
- **以为 `logprobs=0` 表示不回对数概率。** 在仅剩的这套采样器上,0 表示只回抽中那个 token 的值。
