# TensorRT-LLM 15|服务层

只有 Python 入口时没法当网关;多实例 PD 没有人发号、选实例,同一条请求对不上。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

语言模型对象能跑通单机,但客户端要的是 **OpenAI 形状的 HTTP**。没有这一层,切词、写套接字、鉴权都得自己包,线上没法当网关。并发到 100 条时,对外进程已经在切词和流式发送上抢锁,再没有独立的服务入口,探针和真实流量挤在同一条 Python 调用里。

分池之后更糟:prefill 和 decode 各是一组实例。客户端只打一次聊天,编排必须先标成只做 context、再标成只做 generation,并且两侧带着**同一条全局请求号**。没有协调器,工人各自轮询,号对不上,KV 握手对不上,09 章那次搬块根本接不上。坏的是 TTFT:请求在两池之间丢,或者卡在等一块永远不会来的缓存。

## 二、解法:命令行开 HTTP,分池靠协调器对号

最天然的直觉:对外开一个兼容聊天和补全的 HTTP,后面仍用 01 章那套对外进程加执行器。本项目默认命令就是干这个:模型名当参数,本机 8000 起服务,切词在网关进程做完再交引擎。多开几个前端时,它们共享同一组工人、同一端口由内核分连接,自己不再孵化 MPI。

分池不走这条合池入口。另起编排服务:工人先向协调器要一个全局请求号,再分别打 prefill 实例和 decode 实例。协调器管的是**选哪台、记占用、请求结束释放**,不是搬 KV。轮询和按负载可以在工人本地选;会话粘连、按块哈希这类有状态路由必须问协调器,否则多工人会把同一会话拆到不同实例。

![合池时客户端打 OpenAI 网关再进 MPI 工人;分池时网关工人虚线问协调器选实例,再实线先后打 prefill 与 decode,两侧带同一请求号](/opensource/TensorRT-LLM/15a-http-pd-coordinator.svg)

工人数为 1 且没写外部协调器地址时,协调器嵌在同一进程,少一跳。工人数大于 1 时本进程先起协调器,再拉一队只转发的网关。已经有外部协调器时,本进程只当工人,不再自己起一份。

编排器字段空着时创建路径走 MPI 本机队列,不是 Ray。文档把 Ray 标成原型;填成 Ray 或 RPC 才换路。多前端只认默认那条经典 IPC,和原型编排器互斥。

为什么不吃亏:合池多的只是一层 HTTP,执行器循环没变。分池多的是选路和发号,搬块仍在 09 章。猜错实例最差是多一次 prefill,对不上号才会把整条请求写坏。

## 三、代价

**合池默认就要一个监听端口。** 起服务比直接调语言模型对象慢一截;健康检查默认不真生成,探针 200 只说明进程还在,不说明 GPU 能出 token。

**分池默认就要协调器。** 单工人嵌在同进程还好;多工人或多机必须有人独占选路状态。有状态路由每条请求多一次内部往返;预留超时默认 180 秒,超时才放实例,占位会拖容量。

**多前端共享端口但状态不共享。** 对话存档这类按进程记的接口会被关掉,否则第二次请求落到另一个前端就找不到上一条。

**编排器空不等于挂上 Ray。** 空值走 MPI。把原型编排器和多前端一起开,启动直接拒。

## 四、HTTP 网关怎么把请求送进引擎、多实例 PD 靠什么对上请求

这一页比的是 HTTP 网关怎么把请求送进引擎、多实例 PD 靠什么对上请求、编排器默认是不是 MPI。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 合池怎么对外 | 命令行起 OpenAI 兼容 HTTP,切词在网关进程 | 命令行起兼容 HTTP,切词在对外进程 | 主进程自带兼容 HTTP,另有 Anthropic |
| 分池谁对上请求 | 本仓协调器发全局号并选实例 | 引擎外网关发两次 HTTP | 跨实例网关同时发给两侧,带房间号 |
| 协调状态在哪 | 单工人可嵌同进程;多工人必须独占一份 | 网关进程 | 独立 Rust 网关,树按字符猜亲和 |
| 默认编排器 | 空则 MPI 本机队列,Ray 是原型 | 默认多进程工人 | 调度永远是子进程 |
| 多开对外入口 | 多个前端挂同一组工人,内核分连接 | 支持多对外进程 | 可多开切词进程,跨实例走网关 |
| 健康检查 | 默认只看进程;另有真生成一条的探针 | 有就绪与生成探针 | 就绪不碰调度器,健康可真生成 |

重心在本项目:合池用命令行当网关,分池用协调器对号,编排器空着仍是 MPI。vLLM 把分池编排放在引擎外;SGLang 跨实例靠独立网关猜前缀。本页不重讲 01 的进程拓扑,也不重讲 09 的 KV 搬块。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--host` · HTTP 绑哪张网卡 | 启动 | `localhost` | 改成 `0.0.0.0`:集群外可连 | 监听地址;连不上先看是不是只绑了本机 |
| `--port` · HTTP 端口 | 启动 | `8000` | 改端口避开冲突; `0` 让内核分配,要配合回写地址文件 | 日志里实际绑定的端口 |
| `--config` · YAML 里塞引擎与网关项 | 启动 | 无 | 合池:覆盖语言模型参数;分池子命令里这是配置文件,不给起不来 | 显式命令行盖过文件里的同名项 |
| `--num_serve_frontends` · 几个 HTTP 前端挂同一组工人 | 启动 | `1`,上限 64 | 调高:共享端口分连接,自己不孵化 MPI;与非空编排器互斥 | 进程数;环境变量 `TLLM_EXECUTOR_ATTACH_INFO` 是否被消费 |
| `orchestrator_type` · 多卡工人怎么拉 | 启动或 YAML | 空,走 MPI | `ray` 或 `rpc`:原型路径;多前端大于 1 时不能填 | 日志 `Orchestrator is creating` 后面跟哪种执行器 |
| `trtllm-serve disaggregated -c` · 分池编排入口 | 启动 | 配置文件无则解析失败 | 按 YAML 起网关加协调器 | 日志 `Reserving disaggregated server address` |
| `num_workers` · 分池网关工人数 | YAML | `1` | `1` 且无外部地址:协调器嵌同进程;`>1`:本进程起协调器再拉工人 | 进程角色环境变量 `TLLM_DISAGG_ROLE` |
| `disagg_coordinator_url` · 外部协调器地址 | YAML | 空 | 有值:本进程只当转发工人,不再起协调器 | 工人打内部选路接口是否 200 |
| `--schedule_style` · 先打哪一侧 | 启动,可盖 YAML | YAML 默认 `context_first`;命令行默认空表示不盖 | `generation_first`:先占 decode 再做 prefill | 请求体里分阶段参数 |
| `--server_start_timeout` · 等工人起来的秒数 | 启动 | `180` | 调低:启动失败更快;模型加载慢会误杀 | 启动是否超时退出 |
| `--request_timeout` · 编排打工人的秒数 | 启动 | `180` | 调低:卡住的分池请求更快失败 | 上游 HTTP 超时日志 |
| `TRTLLM_DISAGG_COORDINATOR_RESERVATION_TIMEOUT` · 选路预留多久释放 | 环境变量 | `180` | 调低:实例更快腾出;请求慢会被当成过期放掉 | 日志 `Releasing stale coordinator reservation` |

**怎么看。** 合池:进程里应有网关加 MPI 工人;`GET /health` 200 只说明生成器还认为自己活着,真要出 token 用 `GET /health_generate`。分池:`GET /health` 看协调器是否就绪;`GET /cluster_info` 看两侧实例清单。请求级看聊天路由是否 200;分池失败常见 503(选不到实例)或上游 502。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡合池当网关 | `trtllm-serve Qwen/Qwen2.5-1.5B-Instruct --config openai-gateway.yaml --host 0.0.0.0 --port 8000` | 用 HTTP 换 Python 入口;切词仍在网关进程 |
| 分池、单编排进程 | `trtllm-serve disaggregated -c pd-coordinator.yaml` | 用协调器对上请求号,换一次额外选路;KV 传输仍要按 09 章配 |
| 合池高 QPS、网关 CPU 先满 | `trtllm-serve Qwen/Qwen2.5-7B-Instruct --config openai-multi-frontend.yaml --num_serve_frontends 2` | 用两个前端分连接,换掉对话存档;编排器必须保持空着走 MPI |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 客户端连不上 8000 | 是不是绑在本机回环 | 把主机改成全网卡,或在本机访问 |
| 健康 200 但聊天一直挂 | 有没有打过真生成探针 | 看执行器是否已经在跑,不要把存活当就绪 |
| 分池启动立刻退出 | 配置文件在不在、端口能不能绑 | 分池子命令必须给 YAML;端口 0 和多工人不能混用 |
| 分池 503 选不到实例 | 协调器健康和集群清单 | 等工人注册;有状态路由确认虚线那一站通了 |
| 同一会话落到不同 decode | 路由是不是有状态、工人是不是大于 1 | 有状态必须问协调器,不要只靠工人本地轮询 |
| 多前端起不来 | 编排器字段是不是空 | 清掉 Ray 或 RPC,只走默认 MPI |
| 日志说预留过期 | 预留超时是不是 180 秒太短 | 加长环境变量,或先查请求是否已经在工人侧卡死 |

## 六、常见误区

- **以为语言模型对象已经是网关。** 对象能生成,但不能当 OpenAI HTTP。线上流量走命令行服务,不是再包一层同步调用。
- **以为编排器空着会走 Ray。** 字段默认空,创建路径是 MPI。Ray 要显式填,文档自己标原型。
- **以为分池网关会搬 KV。** 它只发号和选实例。块怎么传仍是 09 章的传输器。
- **以为多工人可以各自记路由。** 有状态路由必须一份状态;多工人不经协调器,同一会话会对不上。
- **以为健康 200 等于能出字。** 默认健康不跑生成。执行器已经致命错误时,健康会 503 并尝试关掉服务。
- **以为多前端只是多几个切词进程。** 它们挂的是同一组工人,并且会关掉按进程记的对话存档。
