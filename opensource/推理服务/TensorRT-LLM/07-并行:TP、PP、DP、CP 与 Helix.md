# TensorRT-LLM 07|并行:TP、PP、DP、CP 与 Helix

一张卡装不下权重，超长 decode 里注意力和 FFN 又抢同一批卡，用户侧每秒 token 数上不去。

说法都在源码基准 `59f5c47f`(tag `v1.2.1`)上核过，「当前」与「默认」都指这组基准。

## 一、核心问题

单卡装不下时，坏的是**能不能把模型拉起来**。权重按列切开，每层就要把激活拼回来；层再切成几段接力，气泡吃掉首 token；请求复制到多张卡上，权重复制、KV 各管各的，吞吐才跟副本走。超长 decode 是另一条骨折：注意力要扫整段上下文，FFN 要吃满计算，两段如果各占一排卡就浪费，挤在同一批卡上又互相拖，用户侧 TPS 上不去。

## 二、解法:权重切、层切、请求切、上下文切；Helix 只在 decode 时分

最天然的直觉：哪一维装不下就切哪一维。本项目把世界规模写成张量并行乘流水线并行乘上下文并行。张量并行切权重，同一批 token 各卡算一片再拼；流水线并行切层，激活点对点往下传；注意力数据并行不另乘世界规模，它把张量并行那一组卡改成各接各的请求、权重复制、KV 按请求切开，适合大 batch；上下文并行把长序列摊到组里。专家怎么切归 08 章，这一页不展开。

Helix 不是再占一排卡。它只给 PD 分离里的 generation 服务器：同一批卡先当注意力的上下文并行，各卡只碰自己那份 KV，偏结果合并后再把这批卡改当成 FFN 的张量并行。文档写明长输入通常要超过 64K、小 batch、要压用户侧 TPS 时才划算；现支持 MLA，并且落在 Blackwell 上的 DeepSeek-V3 与 Lite。默认上下文并行类型不是它，世界规模大于 1 也还不会走进这条时分。

![四张卡上张量并行切权重、流水线切层、数据并行切请求、上下文并行切序列；底部虚线框是 Helix，只在 PD 的 decode 侧把同一批卡先当注意力再当 FFN，默认没有实线指进去](/opensource/TensorRT-LLM/07a-parallel-cuts-helix.svg)

为什么实际不吃亏：小 batch 切权重，通信尺寸跟这一步 token 数走，不跟模型总参数走；大 batch 改切请求，注意力不再每卡做同一批；Helix 用时间换空间，decode 侧不用为注意力和 FFN 各备一排卡。

## 三、代价

**张量并行每层要通信。** 头数不够分时，GQA、MQA、MLA 的 KV 会在各卡上复制，显存并不按并行度线性降。

**流水线有气泡。** 级数上去，短请求小批更容易净亏；层数不均时最慢那一段决定一步。

**注意力数据并行复制权重。** 单卡本来就装不下时，这条路走不通；它吃的是「权重已装下、请求还要横向加吞吐」。

**Helix 有门。** 要 PD 的 decode 侧、上下文并行度至少 2、显式选这种类型；块宽还要和 KV 块宽一致。prefill 池、普通稠密短请求、非 MLA 或非 Blackwell 上的 DeepSeek 路线，都不该指望它把用户侧 TPS 拉起来。组内还要做一次偏注意力交换。

## 四、一张卡装不下时怎么切，Helix 只在哪一段时分

这一页比的是一张卡装不下时权重、层、请求、上下文怎么切，以及 Helix 只在哪一段把同一批卡时分复用。

| 维度 | TensorRT-LLM | vLLM | SGLang |
|---|---|---|---|
| 世界规模怎么乘 | 张量并行乘流水线乘上下文并行；注意力数据并行改写同一组卡的身份，不另乘 | 流水线、张量、prefill 上下文并行在乘积里；数据并行默认是另一套引擎 | 每个张量乘流水线 rank 一个调度进程；数据并行注意力另章 |
| 大 batch 注意力怎么切 | 打开注意力数据并行：权重复制，KV 按请求切开 | 数据并行副本各跑各的请求 | 数据并行注意力把副本间的请求切开，和专家并行叠 |
| 长上下文 decode 切 KV | Helix 把 KV 按上下文并行切开，再把同一批卡改去跑 FFN | 有 decode 侧上下文并行，复用张量并行那组 rank | DCP 按位置条带化 KV，也复用张量并行 rank |
| 注意力和 FFN 是否分卡 | Helix 不分卡，时分复用；不是空间上的注意力-FFN 分离 | 不靠时分把同一批卡改身份 | 不靠时分把同一批卡改身份 |
| Helix 给谁用 | 只给 PD 的 generation 服务器；长输入、小 batch、MLA 加 Blackwell 上的 DeepSeek | 无同名机制 | 无同名机制 |

重心在本项目：四种空间切法写进同一张映射；Helix 是 decode 侧的时分，不是默认热路径，也不替代专家并行。

## 五、调参与观测

这一页的参数全是启动配置，改了要重新拉起整个作业。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `tensor_parallel_size` / `--tp_size` · 张量并行度 | 启动或 YAML | `1` | 调高：每卡权重变少，每层要拼激活；头不够时 KV 复制 | 进程数是否等于张量乘流水线乘上下文；报错 `world_size must equal to tp_size * pp_size * cp_size` |
| `pipeline_parallel_size` / `--pp_size` · 流水线级数 | 启动或 YAML | `1` | 大于 1：层分段，激活点对点；短请求小批容易亏 | 同上乘积；各 rank 是否只扛一段层 |
| `context_parallel_size` / `--cp_size` · 上下文并行度 | 启动或 YAML | `1` | 大于 1：长序列摊开；不等于自动打开 Helix | 乘积对得上；Helix 还要类型字段 |
| `enable_attention_dp` · 注意力是否改成按请求切开 | YAML | `false` | `true`：权重复制、KV 按请求分区，适合大 batch；单卡装不下时反而更挤 | 各卡是否在跑不同请求 |
| `cp_config.cp_type` · 上下文并行类型 | YAML | `ULYSSES` | `HELIX`：decode 侧时分；还要并行度 ≥2 | 未设 Helix 时不会走进时分路径 |
| `cp_config.tokens_per_block` · Helix 用的块宽 | YAML | 空 | 必须与 KV 块宽一致，文档示例 `32` | 对不上直接断言失败 |
| `kv_cache_config.tokens_per_block` · KV 块宽 | YAML | `32` | Helix 开启且填了上下文块宽时必须相等 | 同上断言 |
| `pp_partition` · 每段各几层 | YAML | 空，均分 | 手写每 rank 层数；原型字段 | 层数总和是否等于模型层数 |

**怎么看。** 一是进程与卡数：世界规模必须等于三项乘积，对不上启动即失败。二是 Helix：并行度仍为 1，或类型不是 Helix，都不会时分。三是注意力数据并行：打开后同一组卡改接不同请求，不要再按「每卡一片权重、同一批 token」去读日志。

**典型配置。** 三套能直接抄走的起法，参数名和默认值都来自上表。

| 什么场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡，稠密 70B 级，权重单卡装不下 | `trtllm-serve Qwen/Qwen2.5-72B-Instruct --tp_size 8` | 用 8 路张量并行把权重大致摊开，换每层拼激活 |
| 8 卡已能装下，大 batch 要吞吐 | `trtllm-serve Qwen/Qwen2.5-32B-Instruct --config attn-dp-tp8.yaml`（文件写 `tensor_parallel_size: 8` 与 `enable_attention_dp: true`） | 用权重复制换各卡自己的 KV 与请求切片；装不下权重时不要用 |
| PD 的 decode 侧，DeepSeek MLA、输入长于 64K、小 batch 要用户侧 TPS | `trtllm-serve deepseek-ai/DeepSeek-V3-Lite --cp_size 2 --config helix-decode.yaml`（文件写 `context_parallel_size: 2`、`cp_config: {cp_type: HELIX, tokens_per_block: 32}`、`kv_cache_config: {tokens_per_block: 32}`） | 用同一批卡时分换掉「注意力与 FFN 各占一排」；只挂 generation 服务器，不要指望 prefill 池 |

组合与推荐值是按语义推的起点，不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报世界规模不等于三项乘积 | 卡数、三项并行度 | 改到乘积相等，不要只改张量并行 |
| 开了上下文并行但 decode 仍慢、也没有时分 | 类型是不是 Helix、是不是 PD 的 generation 侧 | 只在 decode 服务器写 Helix；prefill 不要套 |
| Helix 启动断言块宽 | 两处块宽是否都是 32 | 写成同一个数 |
| 大 batch 张量并行通信把一步拖死 | 是否仍关着注意力数据并行 | 权重已装下就改切请求 |
| 注意力数据并行更 OOM | 权重是不是本来就单卡装不下 | 先切权重或切层，不要复制 |
| 用户侧 TPS 上不去、输入已经很长 | 是不是还在同卡挤注意力和 FFN、batch 是不是已经很大 | 小 batch 长输入才考虑 Helix；大 batch 走数据并行 |

## 六、常见误区

- **以为 Helix 是空间上的注意力-FFN 分卡。** 名字像分离。它是同一批卡先算注意力再算 FFN，专门给 PD 的 decode 侧，不是再拉一排卡。
- **以为上下文并行度大于 1 就是 Helix。** 默认类型是另一种切法。时分要并行度至少 2 并且类型写成 Helix。
- **以为注意力数据并行会再乘一批卡。** 它改的是张量并行那一组卡的身份：权重复制、请求切开。世界规模公式里没有单独一项。
- **以为 Helix 能救 prefill 池。** 文档写明只配 generation 服务器。prefill 仍用普通切法。
- **以为头数不够时 KV 也按张量并行度缩小。** GQA、MQA、MLA 在头不够分时会复制 KV，显存账不能按并行度除。
- **把专家并行当成这一页的旋钮。** 专家与槽位归 08 章；三项乘积对得上也不等于专家已经切开。
