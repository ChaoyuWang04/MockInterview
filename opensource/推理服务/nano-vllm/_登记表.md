## 二、一句话核心

nano-vllm 里模型结构只占 216 行,近一半代码在做排队、座位和批次三件事。它不是一个模型,是一台把「很多人同时要生成」翻译成「GPU 每一步算一批」的调度机器。

## 三、餐厅比喻(全项目统一,不要另起比喻)

| 代码里的东西 | 餐厅里的角色 | 一句话 |
|---|---|---|
| LLMEngine | 经理 | 收单、每一轮问领班叫谁、把这一批交给厨房、只收结账单 |
| Scheduler | 领班 | 决定这一轮服务哪些客人:有等位的新客就先安排入座点菜,没有才给在座的上下一道菜 |
| BlockManager | 座位管理员 | 管桌位:分配、回收、登记哪几桌坐过同样的人以便拼桌 |
| Sequence | 一位客人 | 一条请求:等位、在座、结账三种状态 |
| ModelRunner | 厨房 | 把这一批客人的单拍平,一锅做出来;rank 0 还负责「出菜」(采样) |
| ModelRunner rank 1..N | 分店厨房 | TP 子进程,只跟着做同样的菜,不做决策 |
| SharedMemory + Event | 传菜窗口 + 叫号铃 | rank 0 把「做什么、给谁做」写进窗口,按铃叫醒分店 |
| Qwen3ForCausalLM + layers | 菜谱与灶台 | 模型结构与算子;Attention 是把 K/V 放进桌位的那口灶 |
| Context | 本轮工单 | 这一轮的变长拼批元数据、槽位映射、桌位表 |
| Config / SamplingParams | 店规 | 所有上限与默认值 |
| KV block | 桌位 | 256 个 token 一桌;显存里能摆多少桌在开店前算好 |
| prefix cache | 拼桌 | 开头几桌完全一样的客人共用桌位,不重做 |
| prefill | 新客入座上第一轮菜 | 一次把 prompt 全部算完,产出第一个 token |
| decode | 每轮给每桌上一道菜 | 每个 step 每位在座客人只算一个 token |
| chunked prefill | 大桌分批上菜 | prompt 超过一轮预算时分几轮做,且只允许队首客人这么做 |
| preempt | 请离席重新排队 | 桌位不够时把 running 队尾客人的桌位收回,他回到等位队列最前面,下次从头重算 |
| CUDA graph | 预排好的流水线 | 开店前为常见桌数录好一整套动作,decode 时直接回放 |
| warmup | 开店前试做最大一单 | 量出厨房最多要占多少显存,剩下的全摆桌子 |

## 六、术语表(总览是唯一定义点,这里是同步副本;各页新词在各自术语卡)

| 术语 | 一句话 | 类比 |
|---|---|---|
| prefill / decode | 先把 prompt 一次算完并产出第一个 token,之后每步只算一个 token | 新客入座上第一轮菜 / 每轮上一道菜 |
| KV cache | 每层 attention 算过的 key 与 value 存下来,后面的 token 直接读 | 每桌已经上过的菜 |
| block / block_table | 256 个 token 的 KV 为一块;每位客人持有自己用到的块编号列表 | 桌位 / 这位客人坐过哪几桌 |
| slot / slot_mapping | 块编号乘 256 加块内偏移,得到每个 token 在大张量里的绝对位置 | 桌号乘座位数加座位号 |
| prefix cache | 按块算链式哈希,开头几块内容完全相同就复用同一块 | 拼桌 |
| chunked prefill | prompt 超过一轮预算就分几轮做 | 大桌分批上菜 |
| preempt | 桌位不够时收回某位在座客人的桌位,让他重新排队 | 请离席 |
| batch / step | 一轮:领班叫一批客人,厨房做一次前向 | 一轮上菜 |
| CUDA graph | 把一次前向的所有 GPU 操作录下来,之后按批大小直接回放 | 预排好的流水线 |
| eager | 不用 CUDA graph,每次现跑 | 现做 |
| TP / all-reduce | 张量并行:同一层的矩阵切给多张卡,算完把结果加起来 | 分店各做一半,再对账 |
| NCCL | GPU 之间集合通信的库 | 分店之间的对讲机 |
| spawn / SharedMemory / Event | 子进程启动方式 / 进程间共享的一块内存 / 进程间的信号量 | 开分店 / 传菜窗口 / 叫号铃 |
| varlen / cu_seqlens | 把长短不一的多条序列首尾相接拼成一条,用累计长度数组记录边界 | 把几桌的单写在同一张纸上,用横线分隔 |
| context_lens | decode 时每位客人当前已有多少 token | 每桌已经上了几道菜 |
| ref_count | 一块被几位客人共用 | 一桌坐了几拨拼桌的人 |
| pinned memory | 钉住不换页的 CPU 内存,GPU 可以异步直读 | 传菜口的固定托盘 |
| xxhash | 一种快速非加密哈希 | 给每桌菜单盖章 |
| TTFT | 从请求进门到第一个 token 的时间 | 上第一道菜要等多久 |

## 七、统一示例(各页共用,数字不要另编;甲、乙的轨迹都来自纯 Python 干跑真实代码)

- **示例甲**(01、02 用):店规取 example.py 的实参(`enforce_eager=True`、`tensor_parallel_size=1`)加预算 512、16 张桌,`max_tokens=3`。三位客人 A、B、C 的 prompt 分别 300、600、1000 个 token。轨迹 7 步:第 1 步 A 一次做完拿到第一个 token;第 2、3 步 B 分 512 加 88 两轮,第 2 步采出的 token 被丢弃;第 4 到 5 步 C 分 512 加 488;之后 decode 到三人结账。01 只画 A、B 两位,共 5 步。
- **示例乙**(03、04 用):8 张桌,块 256。A 612 个 token、B 562 个,两人前 512 个相同;C 1024 个与谁都不同;三人 `max_tokens=8`。到店顺序 A 先,再 C、B。轨迹 16 步:第 1 步 A 得桌 0、1、2;第 2 步 C 得 3 到 6、B 命中桌 0、1 只算 50 个得桌 7;第 3 步 C 要新桌,B 被请离席、桌 7 转给 C;第 4 到 9 步 B 每轮查桌命中 0、1 但缺一张新桌;第 9 步 A、C 结账退桌;第 10 步 B 回座复活桌 0、1 只算 51 个;第 16 步 B 结账。
- **示例丙**(05、06 用):店规默认;模型形状用符号表示,L 层、H_kv 个 kv 头、d 维,不要编造具体模型的数字。

干跑方法:`uv run --with xxhash --with numpy python <脚本>`,脚本用 `importlib` 直接加载 `engine/sequence.py`、`scheduler.py`、`block_manager.py` 三个文件,桩掉包入口(`nanovllm/__init__.py` 会导入 torch)与 config(`types.SimpleNamespace`),厨房用递增假 token 代替。脚本不入仓库。

## 八、写法纪律

1. **双名制**:图上和正文里先叫角色名,后跟代码名;文件路径进行尾或表格,不进正文句子。
2. **术语卡**:本页新出现的 infra 词,先在术语卡里用一句话加类比定义,再使用。
3. **一图一问**:标题就是问题;一张图最多 12 个节点、一条主路径;超了拆成 a、b 两图,编号各自从 ① 重起。
4. **走读对编号**:图上的消息或步骤有编号,正文按编号讲,每步只出现角色名,代码名只在该步末尾附一次。
5. **时间尺度不混**:每页页首标明「启动期一次 / 每 step / 每 request / 跨 request」,不同尺度不同框。
6. **不编造**:图上每个节点、每条边在证据表里都有 file:line 与原样引用;找不到写「未找到」;推断标「推断」。
7. **同步与异步三分法**:同进程同步调用 / 单向广播(写共享内存并按铃,不等回)/ GPU 异步(`non_blocking` 拷贝;`.tolist()` 是同步点)。

## 九、已确认的事实(后续页面直接引用不必再证)

- 退桌不清理 `hash_to_block_id`,条目只在该块被 `_allocate_block` 重新分配时删除(`block_manager.py:47-48`)。
- `Sequence.is_prefill` 在 prefill 完成后不立刻翻 False,要等第一次被 decode 调度(`scheduler.py:68`)。
- 空出但带章的命中桌算命中,但仍占一张新桌:复活要 `free.remove`(`block_manager.py:85-88`),这是精确计数不是保守。
- 共享的桌永远是写满的整桌,之后不会再被写,所以整个项目不需要 copy-on-write(`block_manager.py:62`,`model_runner.py:181`)。
- 分块预填充中途那一轮照样采样,结果被 `postprocess` 的 `continue` 丢弃(`scheduler.py:86-87`);第二轮 `__getstate__` 仍重发整段 token_ids(`sequence.py:73`)。
- 各 rank 各自算 `num_kvcache_blocks`,经理只用 rank 0 的数,没有校验(`model_runner.py:113`,`llm_engine.py:34`);推断:各卡显存不同时高桌号越界。
- `graph_bs` 到 `max_bs` 为止按 16 步进,`max_num_seqs` 不是 16 的倍数且大于 8 时可能找不到桶而抛 `StopIteration`(`model_runner.py:202, 234`);推断,默认 512 安全。
- README 说的 torch compilation 是五个小算子上的 `@torch.compile` 装饰,不是整模型编译。
