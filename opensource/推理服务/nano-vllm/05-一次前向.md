# 05 一次前向:一批客人怎么拍平成张量?现做还是回放?分店怎么跟着做同一批?

> 时间尺度:每 step(经理每叫一批,厨房 `run` 一次)  |  源码基准见总览

这页只回答厨房里的事:领班交来一批客人之后,到返回一串 token 之前,厨房做了什么。读完你能说出:prefill 与 decode 各自把客人拍平成哪几个张量、每个张量的 dtype 与上 GPU 的方式;槽位映射和桌位表分别怎么算、桌位表在 prefill 里为什么有时是 None;现做(eager)与回放(CUDA graph)的三条选路条件、回放前静态缓冲怎么填、补齐位靠什么不出错;以及 TP 时分店厨房为什么能只凭一份瘦身名单做出同样的菜,却什么都不回传。

## 二、术语卡

| 术语 | 一句话 | 类比 |
|---|---|---|
| 拍平 | 把一批客人各自的 token 段首尾相接拼成一条,用 `cu_seqlens` 记边界 | 几桌的单写在同一张纸上,用横线分隔 |
| H2D 拷贝 | Host 到 Device,把 CPU 张量搬进显存;从 pinned 内存出发可以异步 | 托盘固定在传菜口,厨师放下就走 |
| 同步点 | 让 CPU 停下来等 GPU 做完的那一步;这页里只有 `.tolist()` | 菜真正端到手上的一刻 |
| 静态缓冲 | 启动期按最大批分好的固定地址张量,录制与回放都只认这些地址 | 流水线上固定位置的托盘 |
| 分桶 `graph_bs` | 只为 1、2、4、8、16、32……512 这些批大小录图,实际批向上取整 | 只备 4 人桌、8 人桌,3 个人坐 4 人桌 |
| 补齐位 | 桶比实际批大出来的那几行,算了但不用 | 4 人桌空着的那把椅子 |
| 哨兵 -1 | 槽位映射里 -1 表示「这行别写」,写 KV 的 kernel 看到就返回 | 空椅子前不摆盘 |
| 逐段取末位 | prefill 时每位客人只有最后一个位置的 logits 有用,lm_head 只算这几行 | 每桌只问最后一道菜的评价 |
| 指数竞赛采样 | 每个候选除以一个指数分布随机数再取最大,数学上等价于按概率抽样 | 每道菜抽一次签,签上数字最大的上 |
| 会合点 | TP 时各分店必须同时到场交换结果的集合通信:all_reduce、gather | 对账 |

## 三、走读:示例丙

店规全部默认(预算 16384、最多 512 人、一桌 256、默认录图、单卡)。三位客人:A 的 prompt 300 个 token;B 600 个,前 512 个与一位已结账客人完全相同,入座时拼桌命中 2 桌,所以 `num_cached_tokens=512`、这轮只算 88 个;C 1000 个。桌号只是示意(由座位管理员在 04 页决定):A [10, 11],B [2, 3, 12](2、3 是命中的旧桌),C [13, 14, 15, 16]。模型形状用符号:L 层、H_kv 个 kv 头、每头 d 维。厨房依赖 torch 与 GPU,本页所有数字是按源码手算的,并用纯 Python 复算过 `prepare_prefill` 与 `prepare_decode` 的槽位算式。

### step P:三人同批 prefill(图 a ① → ⑥,图 b ① ⑥ ⑦ ⑧ ⑨ ④ ⑤)

图 a ① 经理把 `[A, B, C]` 和 `is_prefill=True` 交给厨房;厨房不问队列、不问桌位怎么来的,只读每位客人身上带着的 `num_cached_tokens`、`num_scheduled_tokens`、`token_ids`、`block_table`。`ModelRunner.run`

图 a ② prefill 读法逐人取 `start = num_cached_tokens`、`end = start + num_scheduled_tokens` 这一段:A 取 [0, 300)、B 取 [512, 600)、C 取 [0, 1000);位置就是 `range(start, end)`。每人的 q 长度是这一段,k 长度是 `end`(含拼桌命中的部分)。槽位按桌铺:从 `start` 所在桌到 `end` 所在桌逐桌铺满,首桌加上 `start % 256` 的偏移,末桌截到 `end`:

$$\text{slot}(t) = \text{block\_table}\big[\lfloor t/256 \rfloor\big] \times 256 + (t \bmod 256)$$

A 铺 2560–2815、2816–2859(桌 10 满、桌 11 前 44 位);B 只铺桌 12 的 3072–3159(88 位);C 铺桌 13、14、15 各 256 位,桌 16 前 232 位(3328–4327)。若客人没有桌位表(只有 warmup 的假客人会这样),这一步直接 `continue`。`prepare_prefill`

图 a ③ 五个列表变五个张量:`input_ids`(1388 个,int64)、`positions`(int64)、`cu_seqlens_q = [0, 300, 388, 1388]`、`cu_seqlens_k = [0, 300, 900, 1900]`(都是 int32)、`slot_mapping`(1388 个,int32);`max_seqlen_q = max_seqlen_k = 1000` 是两个 Python 整数,不上 GPU。每个张量都是 `torch.tensor(..., pin_memory=True).cuda(non_blocking=True)`:先落在钉住的 CPU 内存,再异步搬进显存,CPU 不等。

图 a ④ 桌位表的条件:`cu_seqlens_k` 末项 1900 大于 `cu_seqlens_q` 末项 1388,说明批里有人带着已缓存的前缀,于是建桌位表——按最长的 4 桌补 -1:A `[10, 11, -1, -1]`、B `[2, 3, 12, -1]`、C `[13, 14, 15, 16]`,int32,同样 pinned 异步上 GPU。若三人都没有前缀命中,两个末项相等,桌位表保持 None。`prepare_block_tables`

图 a ⑤ 把 `is_prefill=True`、两个累计长度、两个最大长度、槽位映射、桌位表一起写进本轮工单;`context_lens` 留 None。工单是厨房进程内的一个全局变量,不是传参。`set_context`

图 a ⑥ 只有 `input_ids`、`positions` 作为返回值交给前向;灶台和 lm_head 在层内自己 `get_context()` 取工单。同时 rank 0 备好 `temperatures`(float32,`[T_A, T_B, T_C]`)。`run_model` / `prepare_sample`

图 b ① → ⑥ 选路:`is_prefill` 为真,三条件命中第一条,现做。`run_model`

图 b ⑦ 每层灶台先做两件事:`store_kvcache` 起 1388 个 Triton 程序,每个把自己那行的 K、V(各 H_kv×d 个数)写到 `slot × D` 的位置;然后因为工单里桌位表不是 None,K、V 改指向整张缓存,`flash_attn_varlen_func` 用 `cu_seqlens_q/k`、`max_seqlen_q/k`、`causal=True` 和 `block_table` 算注意力——A 的 300 个 query 读桌 10、11,B 的 88 个 query 读桌 2、3、12 共 600 个 K/V,C 读 4 桌。注意这个开关是批级的:只要一人命中,全批都从缓存里读,没命中的人也一样,因为他们的 K/V 刚刚已经写进去了。`Attention.forward`

图 b ⑧ KV cache 是一整块 `[2, L, 桌数, 256, H_kv, d]` 的张量,每层的灶台各持一对视图 `k_cache = kv_cache[0, l]`、`v_cache = kv_cache[1, l]`;`slot` 是把「桌数 × 256」拍平后的绝对行号,所以一个槽位对每一层都成立。`allocate_kv_cache`

图 b ⑨ 切菜刀:每层的 `o_proj` 与 `down_proj` 是 RowParallelLinear,单卡时就是普通矩阵乘;TP=2 时各分店算半份再 `all_reduce` 相加。加上开头 embedding 的一次 all_reduce,一次前向的会合点是 $1 + 2L$ 次 all_reduce 再加末尾 1 次 gather。`RowParallelLinear.forward`

图 b ④ 出 logits:hidden 是 `[1388, hidden]`,lm_head 看到工单里 `is_prefill=True`,取 `cu_seqlens_q[1:] - 1 = [299, 387, 1387]` 这三行再乘词表矩阵,得 `[3, V]`。TP 时每家分店只有 `V/TP` 列,`gather` 到 rank 0 后按最后一维拼回 `[3, V]`,rank≠0 的 logits 置 None。`ParallelLMHead.forward`

图 b ⑤ 采样只在 rank 0:logits 转 float 后逐行除以各自温度,softmax 得 $p$,然后

$$\hat{y} = \arg\max_i \frac{p_i}{E_i},\qquad E_i \sim \text{Exp}(1)$$

对 $E_i/p_i$ 而言这是一组速率为 $p_i$ 的指数分布取最小值,取到第 $k$ 个的概率恰是 $p_k$,所以它就是按概率抽样,只是没有任何 CPU 同步。`.tolist()` 把三个 token 搬回 CPU,这一步等 GPU 把前面全部做完;随后 `reset_context()` 清空工单。返回 `[tA1, tB1, tC1]`。`Sampler.forward` / `ModelRunner.run`

领班善后(01 页):三人各 `append_token`,长度变成 301、601、1001。

### step D:三人一起 decode,bs=3(图 a ① ⑦ ⑧ ④ ⑤ ⑥,图 b ① ② ③ ④ ⑤)

图 a ⑦ decode 读法每人只读一格:`input_ids` 取 `last_token`,位置取 `len(seq) - 1 = [300, 600, 1000]`,`context_lens` 取 `len(seq) = [301, 601, 1001]`,槽位只算新 token 那一格:

$$\text{slot} = \text{block\_table}[-1] \times 256 + \text{last\_block\_num\_tokens} - 1$$

A 末桌 11、末桌已有 45 个 → 2860;B 末桌 12、已有 89 个 → 3160;C 末桌 16、已有 233 个 → 4328。三个数正好接在 step P 各自区间后面。`prepare_decode`

图 a ⑧ 四个张量:`input_ids`、`positions` int64,`slot_mapping`、`context_lens` int32,同样 pinned 异步上 GPU。图 a ④ 桌位表每轮必建,仍是那张 3×4 的表。图 a ⑤ 工单只写 `is_prefill=False`、槽位映射、上下文长度、桌位表,累计长度留 None。图 a ⑥ 交前向。

图 b ① → ② 选路:不是 prefill、没开 `enforce_eager`、3 ≤ 512,三条件都假,走回放。先按 `graph_bs = [1, 2, 4, 8, 16, 32, …, 512]` 取第一个 ≥ 3 的桶,得 4,取 `graphs[4]`。然后填静态缓冲:`input_ids[:3]`、`positions[:3]` 直接盖;`slot_mapping` 先整体 `fill_(-1)` 再盖前 3 行;`context_lens` 先 `zero_()` 再盖前 3 行;`block_tables[:3, :4]` 盖左上角。第 4 行就是补齐位:它的 `input_ids`、`positions` 和桌位表是上次留下的旧值,但槽位是 -1、上下文长度是 0。`run_model:200-210`

图 b ③ `graph.replay()` 把录制时那一整套 GPU 动作原样重放。录制时工单指向的就是这些静态缓冲的切片,所以回放读的是静态缓冲,而不是 ⑤ 里刚写的工单张量——工单在回放路上只是中转站。图 b ⑧ 的虚线说的就是这件事:录好的灶台动作照样写槽位、读桌位,补齐位那一行写 kernel 看到 -1 直接返回,flash-attn 看到 `cache_seqlens=0` 什么都不读。回放完取 `outputs[:3]`,shape `[3, hidden]`。`capture_cudagraph:240-243` / `run_model:211-212`

图 b ④ lm_head 现做:工单里 `is_prefill=False`,不取末位,直接乘词表矩阵得 `[3, V]`。图 b ⑤ 与 step P 相同:温度、指数竞赛、`.tolist()`、清工单,返回 3 个 token。

### TP=2 旁白(图 a ⑨,图 b ⑩)

经理调 `call("run", seqs, is_prefill)` 时,rank 0 先把 `["run", seqs, is_prefill]` pickle 进传菜窗口、按铃,再执行自己那份;分店在 `loop` 里醒来,反序列化后调同名 `run`。客人在 pickle 时瘦身:prefill 带整段 `token_ids`,decode 只带 `last_token`——恰好是两种读法各自需要的全部字段,`prepare_decode` 从不索引 `token_ids`。分店的 `temperatures` 是 None,前向与总店逐层同步(all_reduce),末尾把半张 logits `gather` 给 rank 0 后自己拿到 None,于是不采样、`token_ids` 也是 None;`loop` 不接收返回值,`reset_context` 各清各的。

## 五、状态与失败分支

- **warmup 的假客人**没有桌位表:`prepare_prefill` 对它 `continue`,槽位映射为空;此时 `k_cache` 还是空张量,灶台跳过写缓存,只跑 flash-attn。这是 06 页的启动期,05 只需知道拍平代码为它留了这一道口子。
- **`bs > 512` 现做**:静态缓冲只到 `min(max_num_seqs, 512)` 行,再大的 decode 批录不了图。默认店规下 decode 批本来就 ≤ 512,这条不触发。
- **桶表有洞(按代码推断,未实测)**:`graph_bs` 在 16 以上按 16 步进到 `max_bs`。若把 `max_num_seqs` 调成 12、20 或 300 这样的值,桶表最大只有 8、16、288,而 decode 批可以到 12、20、300 且不超过 512,`next(...)` 找不到桶会抛 `StopIteration`。默认 512 与所有 16 的倍数都安全。
- **补齐位的旧值**:静态缓冲里 ≥ bs 的行不清零,桌位表右侧超过本轮宽度的列也不清;之所以无害,是槽位 -1 拦住写、上下文长度 0 拦住读、`outputs[:bs]` 切掉算出的垃圾。三道拦截缺一不可。
- **批级拼桌开关**:prefill 只要有一人 `num_cached_tokens > 0`,整批改从缓存读 K/V。正确性靠「先写后读」的顺序保证;代价是没命中的人也走带 `block_table` 的路径。
- **rank≠0 的返回值**:`run_model` 在 lm_head 末尾就已经是 None,`run` 不调采样器;经理只拿 rank 0 的结果。分店异常没有回程,只会在下一次 all_reduce 卡住(01 页已述)。
- **同步与异步**:H2D 全部走 pinned + `non_blocking`,CPU 不等;回放路里往静态缓冲的赋值是设备内拷贝,也不等;整个 `run` 只有 `.tolist()` 一个同步点。每步都新分配临时 pinned 张量,成本本页未测。
- **灶台的三条断言**:`slot_mapping.numel() == N`、K/V 末维连续、缓存第二维步长等于 `H_kv × d`;任何一条不满足在写缓存前就报错,不会写错位置。

## 六、持有什么,不持有什么

**厨房 rank 0 · ModelRunner**,主进程
- 持有:模型权重;`kv_cache` 大张量与每层灶台的视图;`graphs`、`graph_pool`、`graph_vars` 六个静态缓冲;TP 时的共享内存句柄;每轮临时的 `temperatures` 与 `token_ids`。
- 不持有:队列与桌位分配权(只按客人带来的 `block_table` 写槽位);客人对象本身;工单以外的任何跨轮状态。

**分店厨房 · ModelRunner rank 1..N**,各自子进程
- 持有:自己那份权重分片、`kv_cache`(kv 头数除以 TP)、图、静态缓冲。
- 不持有:温度、logits(gather 后为 None)、token_ids、返回值;收到的客人是瘦身副本,算完即弃。

**本轮工单 · Context**,每个厨房进程内一个全局变量
- 持有:`is_prefill`、`cu_seqlens_q/k`、`max_seqlen_q/k`、`slot_mapping`、`context_lens`、`block_tables`。
- 不持有:任何跨 step 的东西——`run` 末尾清空;回放路上它也不是 kernel 真正读的地址。

**灶台 · Attention + store_kvcache**,每层一口
- 持有:`k_cache`、`v_cache` 两个视图。
- 不持有:桌位编号(来自工单)、注意力核本身(来自 flash-attn)。

## 七、设计取舍

- **prefill 不走图**:prefill 的 token 总数每轮不同,`cu_seqlens` 长度也不同,而 CUDA graph 要求形状和地址固定。代价是 prefill 每轮付 Python 与 kernel 启动开销;好处是拍平代码不必为 prefill 准备第二套静态缓冲。
- **分桶回放与补齐浪费**:3 位客人坐 4 人桶,四分之一的行白算;最坏是 17 位客人坐 32 人桶。换来的是只录 36 张图而不是 512 张,以及 decode 每步只剩一次 `replay` 调用。decode 每行只算一个 token,白算的行便宜,省下的启动开销贵,所以划算。
- **工单用进程内全局变量而不是逐层传参**:录图时前向签名必须固定为 `model(input_ids, positions)`,灶台却需要五六个随批变化的张量;放进全局变量,`nn.Module` 的接口一行不改,录制时把静态缓冲切片放进去即可。代价是可读性——读 `Attention.forward` 时要记得它偷偷读了全局。
- **槽位 -1 哨兵**:让「哪些行不写」这个信息跟着数据走,kernel 里一句 `if slot == -1: return` 就够,不需要单独传 bs。代价是每轮多一次整块 `fill_(-1)`。
- **pinned + non_blocking 与唯一同步点**:七八个小张量分别异步上 GPU,CPU 不等;直到 `.tolist()` 才停。省下的是每个张量一次等待;代价是出错时栈信息离出错点远。
- **子进程不采样不回传**:logits 经 gather 天然只在 rank 0,再采一次是浪费,回传更没必要;代价是没有任何 ack。
- **lm_head 不进图**:图只录 `self.model`,输出 `[bs, hidden]` 的小缓冲;若把词表乘法录进去,静态缓冲要多一块 `[512, V]`。prefill 与 decode 也因此共用同一个 `compute_logits`。
- **指数竞赛采样**:不用 `torch.multinomial`,一次向量化算完,没有 CPU 同步,还能被 `@torch.compile` 整体编译;代价是不支持贪心(温度不能为 0)。

## 八、面试考点串联

- 「prefill 和 decode 的输入张量有什么区别」→ prefill 五个:变长拼接的 ids、positions、`cu_seqlens_q/k`、槽位区间;decode 四个:每人一格的 ids、positions、`context_lens`、末位槽;桌位表 prefill 条件带、decode 必带。
- 「slot_mapping 怎么来的」→ 桌号 × 256 + 桌内偏移;prefill 逐桌铺区间,decode 只算新 token 那一格;-1 表示别写。
- 「CUDA graph 为什么只用于 decode,怎么处理批大小变化」→ 形状固定才能录;按 `[1,2,4,8,16…512]` 分桶向上取整,静态缓冲填前 bs 行,补齐位靠 slot -1 与 context_len 0 拦截。
- 「为什么用全局 Context 而不是传参」→ 录图时前向签名必须固定;录制时工单指向静态缓冲切片,回放读的是缓冲不是新工单。
- 「TP 时一次前向有几次通信」→ embedding 1 次 all_reduce、每层 2 次(o_proj、down_proj)、末尾 1 次 gather;分店不采样不回传。
- 「采样器怎么按温度采样」→ 除温度、softmax、除 Exp(1) 噪声取 argmax,等价于按概率抽样;温度必须 > 0。
- 「一步里的同步点在哪」→ 只有 `.tolist()`;H2D 全是 pinned 异步。
