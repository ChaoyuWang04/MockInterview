# 02 调度决策:一次 schedule() 里,token 预算怎么分给 waiting 与 running?

> 时间尺度:每 step 一次。经理(LLMEngine)每调一次 `step()`,领班(Scheduler)就先做一次 `schedule()` 决定这一轮叫谁,厨房算完后再做一次 `postprocess()` 善后。  |  源码基准见总览

这页只回答一件事:领班每一轮怎么用一份 token 预算(默认 16384,示例里压到 512)在「等位的新客」和「在座的老客」之间做选择。读完你能说出:为什么新客永远优先、为什么只有队首能分批上菜、桌位不够时先请谁离席、厨房交回 token 之后领班按什么顺序记账。

图 b 四条泳道按角色分:经理交回 token,领班逐位记账,座位管理员(BlockManager)负责登记满桌与退桌,最底下一条是客人(Sequence)最终落在哪个状态。主路径是「结账」那条:② 先登记满桌、③ 再推进计数、⑤ 追加 token、⑥ 判结账、⑦ 退桌、⑧ 出队。④ 是唯一的岔路:分块 prefill 没做完,这一轮采出来的 token 直接丢掉,客人原地留在 waiting 队首。

## 二、术语卡

| 术语 | 一句话 | 类比 |
|---|---|---|
| token 预算 | `max_num_batched_tokens`,厨房一轮最多做多少 token;循环里用 `remaining = 预算 − num_batched_tokens` 表示还剩多少 | 今晚厨房最多出多少道菜 |
| num_cached_tokens | 这位客人已经算过并写进桌位的 token 数;prefill 做完时等于 prompt 长度,之后每步加 1 | 已经上桌的菜数 |
| num_scheduled_tokens | 这位客人本轮要算的 token 数;prefill 是一段,decode 恒为 1;善后时清零 | 这一轮给他上几道 |
| 队首 / 队尾 | 两个 `deque`:`waiting` 只看队首、做完弹出、被抢者插回队首;`running` 新人追加到队尾、抢占从队尾拿、整批排完插回队首 | 等位号牌 / 在座名单 |
| 自抢 | decode 时找不到别人可抢,只能把自己请离席,本轮不排自己 | 没人可让,自己起身 |
| TTFT | Time To First Token,从请求到第一个 token 的等待;prefill 优先就是在压它 | 新客等第一道菜的时间 |

## 三、走读:示例甲

店规默认,`max_num_batched_tokens` 压到 512;三位客人 A、B、C 的 prompt 分别 300、600、1000 个 token,`max_tokens=3`,单卡。桌位取 16 张(示例甲没有规定这个数,16 张足够三人坐下,保证这条轨迹里不出现抢占)。下表由真实的 `Scheduler` / `BlockManager` / `Sequence` 代码在本机干跑得到(干跑方法见证据表),每行记录 `schedule()` 返回时的数字。

| step | 本轮 batch | is_prefill | num_scheduled / num_cached(排入时) | waiting(排完后) | running(排完后) |
|---|---|---|---|---|---|
| 1 | [A] | True | A 300 / 0 | [B, C] | [A] |
| 2 | [B] | True | B 512 / 0 | [B, C](B 没做完,留队首) | [A] |
| 3 | [B] | True | B 88 / 512 | [C] | [A, B] |
| 4 | [C] | True | C 512 / 0 | [C](C 留队首) | [A, B] |
| 5 | [C] | True | C 488 / 512 | [] | [A, B, C] |
| 6 | [A, B, C] | False | A 1 / 300,B 1 / 600,C 1 / 1000 | [] | [A, B, C] |
| 7 | [A, B, C] | False | A 1 / 301,B 1 / 601,C 1 / 1001 | [] | [](三人 FINISHED) |

桌位表:A 得 [0, 1],B 得 [2, 3, 4],C 得 [5, 6, 7, 8];空桌 16 → 14 → 11 → 7,第 7 步结账后回到 16。前 5 步全是 prefill,而且每步只有一个人:这就是「prefill 优先」加「只有队首可分块」叠在一起的效果。

**第 1 步,按图 a 编号。** ① 看队首 A,remaining = 512 − 0 = 512。② A 首次入座,领班问座位管理员 can_allocate:A 要 2 桌,第 1 桌的哈希没在登记簿里,空桌 16 ≥ 2,返回 0 张命中;要做 300 − 0 = 300 个。③ 512 ≥ 300,不用分块。④ allocate 给 A 桌位 [0, 1];scheduled = min(300, 512) = 300;num_batched = 300。⑤ 0 + 300 == 300,做完:A 变 RUNNING,从 waiting 弹出、追加到 running 队尾。回到 ① 看 B:remaining = 212。② B 首次,要做 600。③ 212 < 600 而且批里已经有 A → 停。⑥ 返回 ([A], True)。注意 212 个预算白白剩下了。

**第 2 步。** ① B,remaining = 512。② B 还没有桌位,要做 600。③ 512 < 600,但批里没人,B 是第一位 → 允许分块。④ allocate 给 B [2, 3, 4];scheduled = min(600, 512) = 512;num_batched = 512。⑤ 0 + 512 ≠ 600,没做完:B 留在 waiting 队首,状态仍是 WAITING。回到 ①:remaining = 0 → 跳出。⑥ 返回 ([B], True)。转到图 b:② hash_blocks 把 B 刚填满的第 1、2 桌登记进 `hash_to_block_id`;③ num_cached = 512;④ 是 prefill 且 512 < 600 → `continue`:厨房这一轮照样采了一个 token,但被丢掉;B 原地留在 waiting 队首。

**第 3 步。** ① B,remaining = 512。② B 已有桌位,走「续做」:600 − 512 = 88。③ 够。④ 不再 allocate;scheduled = 88;num_batched = 88。⑤ 512 + 88 == 600 → B 变 RUNNING,running = [A, B]。回到 ① 看 C:remaining = 424。② C 首次,要做 1000。③ 424 < 1000 且批里有 B → 停。⑥ 返回 ([B], True)。图 b:② hash_blocks 算出 start = 512 ÷ 256 = 2、end = 600 ÷ 256 = 2,相等,第 3 桌是半桌,不登记;③ num_cached = 600;④ 做完了 → ⑤ 追加 B 的第 1 个生成 token,B 变 601 个;⑥ 生成数 1 < 3 → 留在 running。

**第 4、5 步**对 C 重演第 2、3 步:先做 512,再做 488,第 5 步结束时 waiting 空、running = [A, B, C]。图 b 里第 4 步登记 C 的第 1、2 桌,第 5 步登记第 3 桌(start = 2,end = 1000 ÷ 256 = 3),第 4 桌是半桌。

**第 6 步,第一次 decode。** ① waiting 空,prefill 循环直接跳出,批里没人 → 掉到 ⑦。⑦ 取 running 队首 A;⑧ A 现在 301 个 token,301 mod 256 = 45,不等于 1,不要新桌;⑨ scheduled = 1,is_prefill = False,may_append 什么也不做。再取 B(601 mod 256 = 89)、C(1001 mod 256 = 233),同样不要新桌。running 空了 → ⑩ `extendleft(reversed([A, B, C]))` 把三人按原顺序插回队首,running 还是 [A, B, C],返回 ([A, B, C], False)。图 b:② hash_blocks 对 A 算 start = 300 ÷ 256 = 1、end = 301 ÷ 256 = 1,不登记;③ num_cached = 301;④ 不是 prefill,直接 ⑤ 追加;⑥ 生成数 2 < 3 → 留在 running。

**第 7 步**再 decode 一轮:三人生成数都到 3 == max_tokens → ⑥ 判结账 → status = FINISHED → ⑦ deallocate 退桌(倒序减 ref_count,9 张桌全部回到空闲队列,但登记簿里的哈希不删)→ ⑧ `running.remove` 出队。经理的 `step()` 随后把三人的 `completion_token_ids` 收进 outputs。

## 四、关键函数、参数与默认行为

| 函数或参数 | 位置 | 做什么 | 默认或条件 |
|---|---|---|---|
| `schedule()` | `nanovllm/engine/scheduler.py:25-73` | 先跑 prefill 循环,排上任何人就返回 `(seqs, True)`;否则跑 decode 循环返回 `(seqs, False)` | 一轮只可能是纯 prefill 或纯 decode,不混批 |
| `remaining` / `num_batched_tokens` | `scheduler.py:27, 32, 47` | 预算余额与已用量;余额每看一位重算,已用量只在排入时增加 | 余额为 0 立刻跳出(`:33-34`) |
| `can_allocate(seq)` | `nanovllm/engine/block_manager.py:58-73` | 逐桌算链式哈希查拼桌,返回命中桌数;空桌不够返回 −1 | 只查前 `num_blocks − 1` 桌,最后一桌永远不算命中 |
| `allocate(seq, n)` | `block_manager.py:75-92` | 命中桌 ref_count + 1,其余从空闲队列取;写 `num_cached_tokens = n × 256` | 只在 `block_table` 为空时调用(`scheduler.py:44-45`) |
| 分块判定 | `scheduler.py:42-43` | `remaining < num_tokens and scheduled_seqs` 就 break | 只有批里还没人时,队首才可以只做一部分 |
| 状态迁移 | `scheduler.py:48-51` | `num_cached + num_scheduled == num_tokens` 才变 RUNNING 并换队 | 没做完的留在 waiting 队首,状态不变 |
| `can_append(seq)` | `block_manager.py:103-104` | `len(seq) % 256 == 1` 时需要 1 张空桌,否则需要 0 张 | 返回布尔:空桌数 ≥ 需要数 |
| `may_append(seq)` | `block_manager.py:106-108` | 同一条件成立就真的取一张新桌追加到 `block_table` | 在 `can_append` 通过之后调用(`scheduler.py:69`) |
| `preempt(seq)` | `scheduler.py:75-79` | 状态改回 WAITING、`is_prefill = True`、退掉全部桌位、插回 waiting 队首 | 受害者:`running.pop()` 取队尾(`:62`);running 空则自己(`:64`) |
| `extendleft(reversed(...))` | `scheduler.py:72` | 把本轮排上的 decode 客人按原顺序插回 running 队首 | 保证下一轮仍是老客在前、新客在后 |
| `postprocess()` | `scheduler.py:81-92` | 登记满桌 → 推进计数 → 分块没做完就 continue → 追加 token → 判结账 | 结账顺序:FINISHED → deallocate → `running.remove` |
| `hash_blocks(seq)` | `block_manager.py:110-120` | 对本轮跨过的整桌算链式哈希并登记;半桌跳过 | 用推进前的 `num_cached_tokens` 定起点 |
| `max_num_batched_tokens` / `max_num_seqs` | `nanovllm/config.py:9-10` | 每轮 token 上限 / 每轮人数上限 | 16384 / 512;示例甲把前者压到 512 |
| `max_tokens` / `ignore_eos` | `nanovllm/sampling_params.py:7-8` | 结账两个条件的参数 | 64 / False;eos 由 tokenizer 填入(`llm_engine.py:33`) |

两条核心公式,块级写出来方便对照:

$$
\text{remaining} = \text{max\_num\_batched\_tokens} - \text{num\_batched\_tokens},\qquad
\text{num\_scheduled\_tokens} = \min(\text{num\_tokens},\ \text{remaining})
$$

$$
\text{hash\_blocks 登记范围} = \left[\left\lfloor \tfrac{\text{num\_cached}}{256} \right\rfloor,\ \left\lfloor \tfrac{\text{num\_cached} + \text{num\_scheduled}}{256} \right\rfloor \right)
$$

## 五、状态与失败分支

- **prefill 循环的四个出口**:waiting 空或人数到 `max_num_seqs`(`:30`);预算余额为 0(`:33-34`);队首首次入座但空桌不够,`can_allocate` 返回 −1(`:37-38`);预算不够而批里已有人(`:42-43`)。四个出口之后都到同一个判定:批里有人就返回 prefill 批,没人才进 decode(`:54-58`)。图 a 把它压成 ⑤→⑥ 与 ①→⑦ 两条边。
- **队首被空桌卡住会拖住所有新客**:−1 是 break 不是跳过,队首之后的人这一轮谁也进不来;只要在座的人还在 decode,新客就一直等。这是 FIFO 的代价。
- **分块 prefill 的中间态**:客人已经持有桌位、`num_cached_tokens > 0`,但状态仍是 WAITING、人在 waiting 队首。这时如果它被别人抢了桌位?不会:抢占只从 running 里拿人(`:62`),waiting 里的半桌客人不会被抢。
- **抢队尾**:decode 循环里 `running` 只剩本轮还没轮到的人,已经排进批的在 `scheduled_seqs` 里,这一轮安全;`pop()` 拿到的是还没轮到的人里最晚入座的那位。被抢者退掉全部桌位、`is_prefill` 改回 True、插到 waiting 最前面,下一轮以「首次入座」身份重排,已生成的 token 留在 `token_ids` 里一起重算。干跑验证过:2 张桌、两位各 256 token 的客人同时入座后,第 2 步是后到者被抢、先到者拿走它的桌。
- **自抢会撞上 assert**:running 空时自抢并 break,如果这位客人是本轮唯一一位、而且批里还没人,`assert scheduled_seqs`(`:71`)直接抛异常。干跑验证过:1 张桌、一位 256 token 的客人,第 2 步 decode 就抛 AssertionError。也就是说,一条序列单独占满全部桌位再要新桌时,当前代码不是退避而是崩溃;有别人已经排进批时自抢才是安全的。
- **被抢后的重算可能不用从头来**:退桌只减 ref_count,桌里的 token 内容与哈希登记都还在;下一轮 `can_allocate` 若命中自己留下的整桌就直接拼桌。干跑验证过:3 张桌两位客人的自抢场景里,受害者下一轮只重算了 1 个 token。这一点会在 03、04 页展开。
- **分块没做完时的采样是白做的**:厨房照样跑采样器,领班在 `:86-87` 直接 continue,不追加。
- **eos 也进 token_ids**:`append_token` 在结账判定之前(`:88-89`),所以 `completion_token_ids` 的最后一个可能就是 eos;`ignore_eos=True` 时只看 `max_tokens`。
- **首次入座至少算 1 个 token**:`can_allocate` 不查最后一桌,所以哪怕 prompt 与别人完全相同,也至少重算最后一桌,厨房总有 logits 可采样。

## 六、持有什么,不持有什么

- **领班(Scheduler)** 持有 `waiting`、`running` 两个 deque、预算上限、`eos`、桌位大小;每轮的 `scheduled_seqs` 与 `num_batched_tokens` 是局部变量,函数返回就没了(`scheduler.py:10-17, 26-27`)。它不持有任何 token 内容,也不知道厨房怎么算。
- **座位管理员(BlockManager)** 持有桌位表、空闲队列、已用集合、哈希登记簿(`block_manager.py:29-33`);它只管编号和引用计数,不碰显存里的 K/V。
- **客人(Sequence)** 自己持有 `status`、`token_ids`、`block_table`、`num_cached_tokens`、`num_scheduled_tokens`、`is_prefill`(`sequence.py:20-31`)。领班改的是客人身上的字段,不是自己的账本;跨进程时客人瘦身成计数加桌位表加最后一个 token,`is_prefill` 为 True 才带全部 token(`sequence.py:72-74`)。
- **经理(LLMEngine)** 只持有调用顺序:`schedule → run → postprocess`(`llm_engine.py:49-55`);它把 `is_prefill` 原样转交厨房,厨房据此选 `prepare_prefill` 还是 `prepare_decode`(`model_runner.py:215`)。
- **厨房(ModelRunner)** 拿到的是 `num_cached_tokens` 到 `num_cached_tokens + num_scheduled_tokens` 这一段(`model_runner.py:139-142`);分块续做时 K 比 Q 长,厨房才会带上桌位表让灶台读旧 K/V(`:162-163`,`layers/attention.py:64-66`)。

## 七、设计取舍

- **prefill 优先,而不是 decode 优先。** 代码事实:只要排上一位新客就返回 prefill 批,在座的人整轮不动(`:54-55`)。好处是 TTFT 短、新客尽快进入 running 让后面的 decode 批更大;代价是每来一位新客,在座所有人的下一个 token 都要多等一轮,长 prompt 分块时甚至多等好几轮(示例甲里 A 在第 1 步拿到第一个 token,第 6 步才拿到第二个)。没有它:decode 优先会让新客在高负载下长期拿不到第一个 token。这是取舍不是定理,nano-vllm 选了简单的一边。
- **只允许队首分块。** 代码事实:`:42` 的条件与注释。这样任何时刻最多只有一位「半桌客人」,而且它一定在队首,续做逻辑只需看 `block_table` 是否为空(`:35, :40`),不用记「谁做到哪」。代价是预算浪费:示例甲第 1 步剩 212、第 3 步剩 424 都没用上,B 和 C 各多等了一轮。放开的话,多人同时持有半桌会占住桌位却不产出 token。
- **重算式抢占,而不是把 K/V 换出到 CPU。** 代码事实:`preempt` 只做退桌、改状态、插回队首(`:75-79`),`engine/` 里没有任何换出、换入或 CPU 缓冲区。好处是没有 PCIe 搬运、没有第二套桌位表,代码 5 行;代价是被抢者要把 prompt 加已生成的 token 全部重算,序列越长越贵。拼桌登记簿没删,所以整桌命中时可以少算。
- **抢队尾,不抢自己。** 代码事实:`running.pop()` 取队尾(`:62`),自己是最后手段(`:63-65`)。队尾是最晚入座的人,已投入的算力最少,牺牲它最便宜;而且它被插回 waiting 队首,下一轮以队首身份优先重排、还能分块。代价是它的 TTFT 等于重来一次;没有这条规则(比如抢队首)会让最老的请求反复被打断、永远做不完。

## 八、面试考点串联

- **「nano-vllm 一个 step 里 prefill 和 decode 会混在一批吗?」** 不会。`schedule()` 返回的 `is_prefill` 是整批一个布尔,厨房按它二选一准备输入;排上任何新客就是纯 prefill 批。
- **「token 预算怎么用?」** `remaining = 上限 − 已排`,每看一位重算;首次入座的需求是 `prompt 长度 − 命中桌 × 256`,续做的需求是 `总数 − 已缓存`;排入量取 `min(需求, remaining)`。
- **「chunked prefill 给谁?为什么?」** 只给批里还没人时的队首。保证任何时刻最多一位半桌客人,续做只看 `block_table` 空不空;代价是余额浪费。
- **「抢占抢谁?怎么恢复?」** 抢 running 队尾(本轮还没轮到的人里最新的一位),退掉全部桌位、插回 waiting 队首,下一轮当首次入座重算;整桌命中可少算。只剩自己时自抢,若批里还没人会撞 assert。
- **「postprocess 的顺序为什么重要?」** 先 `hash_blocks` 再推进计数,因为登记范围用的是推进前的 `num_cached_tokens`;先 `append_token` 再判结账,所以 eos 也在输出里;结账时先退桌再出队。
- **「decode 什么时候要新桌?」** 序列长度 mod 256 等于 1 的那一步,也就是下一个要算的 token 恰好是新一桌的第一个。
