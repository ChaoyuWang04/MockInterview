# 01 指挥循环:generate() 之后,两位客人从进门到结账经过哪些手?哪一跳跨进程?每一跳同步还是异步?

> 时间尺度:每 request,跨若干 step  |  源码基准见总览

这页只回答一件事:用户脚本调一次 `generate()`,里面到底转了几圈、每圈经过谁的手。读完你能说出:一条请求从入队到结账走的固定节拍(经理问领班叫谁、交厨房做、让领班善后),第一个 token 是在领班的 postprocess 里写回客人的,分块预填充没做完那一步的采样结果会被原地丢掉,以及 TP 时主进程到子进程只有一条单向广播、没有回程。

## 一、先看图

![指挥循环:两位客人从 generate() 到结账](/opensource/nano-vllm/01-command-loop.svg)

[打开交互版](/opensource/nano-vllm/01-command-loop.html)

怎么读:七条竖线是七个角色,从左到右按对话顺序排:用户脚本、经理、领班、座位管理员、厨房 rank 0、传菜窗口、分店厨房。横向四条色带是四个时间段:收单、step 1、step 2–3、step 4–5。每个 step 里"经理问领班 → 领班找座位管理员 → 领班回话 → 经理把这批交厨房 → 厨房回 token → 经理让领班善后"六拍反复出现,这就是指挥循环的一圈。粗箭头是同步函数调用,细的回箭头是返回值;只有 ⑦⑧ 两条虚线是 TP=2 时才有的分支,它们跨进程且没有回箭头,是全图唯一的异步动作。示例用底稿示例甲:A、B 两位客人的 prompt 各 300、600 个 token,`max_tokens=3`,一轮预算 512;单卡按 example.py 的 `enforce_eager=True`。

## 二、术语卡

| 术语 | 一句话 | 类比 |
|---|---|---|
| step | 经理循环一圈:领班叫一批、厨房算一次前向、领班善后 | 一轮上菜 |
| prefill / decode | 先把 prompt 一次算完并产出第一个 token;之后每步每人一个 token | 新客入座上第一轮菜 / 每轮上一道菜 |
| chunked prefill | prompt 超过一轮预算就分几轮做,只允许队首客人这么做 | 大桌分批上菜 |
| 同步调用 | 调用方停在原地等返回值 | 经理站在窗口等菜 |
| 单向广播 | 写完就走,不等对方回复;这里靠共享内存加 Event | 把单子贴到传菜窗口、按铃,不等回话 |
| pickle / `__getstate__` | Python 把对象变成字节串;`__getstate__` 决定带哪些字段 | 跨店传单只抄要点,不抄整本菜单 |
| gather / all-reduce | 多卡把各自那份汇到 0 号卡 / 各卡相加后人人一份 | 分店把半张单子交回总店 / 分店对账 |
| pinned memory + non_blocking | 钉住的 CPU 内存,GPU 可异步直读,不等拷贝完成 | 传菜口的固定托盘 |
| `.tolist()` | 把 GPU 张量搬回 CPU,会等前面所有 GPU 工作做完 | 菜真正端到手上的那一刻 |

## 骨架代码:generate 加 step 压成八行

右边注释写调的是谁、在哪个进程、等不等。

```python
def generate(prompts, sp):                                    # 经理;主进程;同步,全部结账才返回
    for p in prompts: scheduler.add(Sequence(tok.encode(p), sp))    # 经理→领班;同进程同步;入 waiting
    while not scheduler.is_finished():                       # 经理问领班;waiting、running 都空才停
        seqs, is_prefill = scheduler.schedule()              # 经理→领班→座位管理员;同进程同步
        token_ids = runner.call("run", seqs, is_prefill)     # 经理→厨房 rank 0;同进程同步;TP>1 时先 write_shm 单向广播给分店(跨进程,不等回)
        scheduler.postprocess(seqs, token_ids, is_prefill)   # 经理→领班;同进程同步;写回 token 或丢弃,判结账
        outputs += [(s.seq_id, s.completion_token_ids) for s in seqs if s.is_finished]   # 经理自己收账单
    return [{"text": tok.decode(ids), "token_ids": ids} for ids in 按 seq_id 排序]         # 回用户脚本;同步返回
```

## 三、走读:示例甲,A(300)与 B(600),max_tokens=3,预算 512

领班与座位管理员是纯 Python,下面每一步的数字来自在本机用 `SimpleNamespace` 伪造店规后干跑 `Scheduler` 得到的轨迹(本机没有 `xxhash`,哈希用 blake2b 打桩;A、B 没有公共前缀,不影响轨迹)。共 5 个 step:3 轮 prefill、2 轮 decode。

**收单**

① 用户脚本调 `generate(prompts, sp)` 进入经理;这一调同步阻塞,直到所有客人结账才返回。`LLMEngine.generate`
② 经理把每条 prompt 编成 token、包成一位客人,交给领班入队;此时 waiting=[A, B],running 为空。`add_request` → `Scheduler.add`

**step 1:A 入座,拿到第一个 token**

③ 经理问领班这一轮叫谁。`Scheduler.schedule`
④ 领班从 waiting 队首拿 A,问座位管理员能否安排:A 要 2 桌,分到 [0, 1]。轮到 B 时剩余预算只有 212 < 600,而这一批已经有人,分块只给队首,B 留在原地。`can_allocate` / `allocate`
⑤ 领班回话:这批是 [A],is_prefill=True,A 转 RUNNING。返回类型 `tuple[list[Sequence], bool]`
⑥ 经理把这批交厨房 rank 0,同进程同步调用。`ModelRunner.call("run", seqs, True)`
⑦ (TP=2 分支)厨房先把 `["run", seqs, True]` pickle 进 1 MiB 共享内存,给每个分店的 Event 按铃,然后不等任何回复,直接做自己那份。序列化时客人被瘦身成 6 元组:4 个计数、block_table、以及 prefill 时的整段 token_ids(A 这一步约 982 字节,本机 pickle 实测)。`write_shm` / `Sequence.__getstate__`
⑧ (TP=2 分支)分店在 `loop` 里 `event.wait()` 醒来,读长度、反序列化、清铃,再调同名方法 `run`。分店的 `temperatures=None`,logits 在 lm_head 里被 gather 到 rank 0 后置 None,`token_ids=None`,什么都不回传;它与总店唯一的会合点是每层 `all_reduce` 与最后的 `gather`。`read_shm` / `ParallelLMHead.forward`
⑨ 厨房把 300 个 token 拍平,H2D 拷贝走 pinned memory 异步进显存,跑一次前向,只取每位客人最后一个位置的 logits 采样;`.tolist()` 在这里等 GPU 做完,返回 `list[int]`,长度等于客人数:[tA1]。`ModelRunner.run`
⑩ 经理让领班善后:先给整块的桌位盖哈希章,再把 cached 推到 300;因为 300 == 300,不是分块中途,所以 `append_token(tA1)`。**A 的第一个 token 在这一步、在主进程领班手里写回客人对象。** A 有 1 个完成 token,没到 3,不结账;本 step 输出为空。`Scheduler.postprocess`

**step 2–3:B 大桌分批上菜**

⑪ 经理再问领班。waiting=[B],B 是这批第一个,允许分块:B 先拿 512。`schedule`
⑫ 座位管理员一次把 B 的 3 桌 [2, 3, 4] 全分了,但这一轮只算前 512 个 token。`allocate(B, 0)`
⑬ 领班回 [B],is_prefill=True,scheduled=512;B 仍在 waiting、仍是 WAITING(0+512 ≠ 600,不换队)。注意 running 里的 A 这一轮没被叫到:只要有人在 prefill,decode 就让路。
⑭ 经理交厨房;这 512 个 token 没有已缓存前缀,所以不带 block_tables。`call("run", [B], True)`
⑮ 厨房照常采样,返回 [tB?]。
⑯ 领班善后:cached 推到 512 后 512 < 600,命中 `continue`。**这个采出来的 tB? 既不 append 也不保存,原地丢弃**;但盖章照做,桌 2、3 已有哈希。`postprocess`
⑰ 经理再问领班:B 已有 block_table,剩 600−512=88 个;512+88 == 600,B 转 RUNNING,出 waiting、进 running;running=[A, B]。
⑱ 领班回 [B],is_prefill=True,scheduled=88。
⑲ 经理交厨房:这次 `cu_seqlens_k`(600)大于 `cu_seqlens_q`(88),厨房把 block_tables 一并写进本轮工单,灶台从桌位读回前 512 段 K/V。`prepare_prefill` → `set_context`
⑳ 厨房返回 [tB1]。
㉑ 领班善后:cached=600 == 600,`append_token(tB1)`,B 拿到第一个 token。

**step 4–5:每轮一道菜,直到结账**

㉒ waiting 空了,领班进入 decode 分支,把 running 里的人依次弹出。`schedule`
㉓ 每人问一次座位管理员:len(A)=301、len(B)=601,除以 256 余数都不是 1,不需要新桌;`num_scheduled_tokens=1`,`is_prefill=False`。`can_append` / `may_append`
㉔ 领班回 [A, B],is_prefill=False,再把两人按原序放回 running 队首。
㉕ 经理交厨房;TP 时这次瘦身只带 last_token,每位客人约 83 字节。`call("run", [A, B], False)`
㉖ 厨房每人只算一个位置,返回 [tA2, tB2];example.py 开了 `enforce_eager`,走现做路径而不是 CUDA graph 回放。
㉗ 领班善后:各 append 一个;step 5 与 step 4 完全同形,产出 tA3、tB3。
㉘ step 5 善后时 `num_completion_tokens == max_tokens == 3`,A、B 先后置 FINISHED,座位管理员回收桌位,领班把两人从 running 移走;经理这一步收到两张账单。`deallocate` / `running.remove`
㉙ `is_finished()` 看到 waiting、running 都空,循环结束;经理按 seq_id 排序、解码成文本,同步返回给用户脚本。`generate` 返回 `list[dict]`

## 四、关键函数、参数与默认行为

| 函数或参数 | 位置 | 做什么 | 默认或条件 |
|---|---|---|---|
| `generate(prompts, sampling_params, use_tqdm)` | `llm_engine.py:60-90` | 入队、循环 step、收账单、解码 | 单个 SamplingParams 复制给每条 prompt;实际返回 `list[dict]`(注解写的是 `list[str]`) |
| `add_request(prompt, sp)` | `llm_engine.py:43-47` | 字符串则 encode,构造 Sequence,领班入队 | 也接受 `list[int]` |
| `step()` | `llm_engine.py:49-55` | schedule → call("run") → postprocess → 收账单 | 返回 `(outputs, num_tokens)`;decode 时 num_tokens 取负,用符号区分两种吞吐 |
| `is_finished()` | `llm_engine.py:57-58`,`scheduler.py:19-20` | 终止条件 | `not waiting and not running` |
| `schedule()` | `scheduler.py:25-73` | 先 prefill 后 decode,二选一 | 只要有 prefill 就不 decode;分块只给批里第一位 |
| `postprocess(seqs, token_ids, is_prefill)` | `scheduler.py:81-92` | 盖哈希章、推 cached、写回或丢弃、判结账 | `is_prefill and cached < num_tokens` 时 continue |
| 结账条件 | `scheduler.py:89` | eos 或 max_tokens | `ignore_eos=False`,`max_tokens=64` |
| `call(method_name, *args)` | `model_runner.py:85-89` | TP>1 且 rank 0 先 write_shm,再本地 getattr 调用 | 返回本地方法的返回值 |
| `write_shm` / `read_shm` | `model_runner.py:68-83` | 4 字节长度 + pickle;Event set / wait / clear | 共享内存名 `nanovllm`,固定 1 MiB |
| `loop()` | `model_runner.py:61-66` | 子进程死循环等指令 | 收到 `"exit"` 才退出 |
| `run(seqs, is_prefill)` | `model_runner.py:214-220` | prepare → run_model → sampler → reset_context | rank≠0 返回 None |
| `Sequence.__getstate__` | `sequence.py:72-74` | 跨进程只带 4 个计数 + block_table + token_ids 或 last_token | prefill 带整段 token_ids,decode 只带 last_token |
| `ParallelLMHead.forward` | `layers/embed_head.py:56-66` | prefill 只取每段最后一个位置;TP 时 gather 到 rank 0 | rank≠0 的 logits 为 None |
| `max_num_batched_tokens` | `config.py:9` | 一轮预算 | 默认 16384;示例甲设 512 |

## 五、状态与失败分支

- 客人只有三种状态:WAITING → RUNNING → FINISHED。分块中途仍是 WAITING,只是 block_table 已非空、cached 在涨;preempt 会把 RUNNING 打回 WAITING 并清空桌位(本例桌位充足,没触发)。
- 循环终止只看两个队列是否都空,不看输出数;`generate` 没有超时、没有流式输出,一位客人没结账,所有人的结果都不返回。
- decode 分支末尾 `assert scheduled_seqs`:若 waiting 队首客人的桌数超过整店桌数,`can_allocate` 一直返回 -1,而 running 为空,这一行直接抛 AssertionError,不是排队等待。
- 分块预填充未完成的那一轮,厨房照样采样,领班用 `continue` 丢弃;丢的是一个 token,不是整轮前向。
- TP 分支的失败没有回程:子进程异常时 rank 0 收不到任何信号,只会在下一次 NCCL 集合通信里卡住。共享内存固定 1 MiB,prefill 广播整段 token_ids,批太大写不下时切片赋值会失败(本文未实测具体异常类型)。
- 退出路径:`atexit` → `engine.exit` → `call("exit")` 广播 → 子进程 `loop` 收到 exit 跳出 → 主进程 `p.join()`。

## 六、持有什么,不持有什么

**经理 · LLMEngine(主进程)**
- 持有:tokenizer;领班;rank 0 厨房对象;子进程句柄 `ps` 与每个子进程的 Event。
- 不持有:任何 GPU 张量;任何队列(在领班手里);任何 token 内容(在客人对象里);子进程的返回值(根本没有)。
- 一句话:它只握指挥棒,整套节拍就是 `step()` 那几行。

**厨房 rank 0 · ModelRunner(主进程)与分店厨房 · ModelRunner rank 1..N(子进程)**
- 持有:模型权重;`kv_cache` 大张量;CUDA graph 与 `graph_vars`;TP 时的共享内存句柄;rank 0 额外准备采样用的 temperatures。
- 不持有:waiting / running 队列;桌位分配权(只按 block_table 写槽位);客人对象的所有权。跨进程收到的是瘦身副本,算完即弃,任何字段改动都不会回到主进程。
- 一句话:厨房只认工单,不认客人。

## 七、设计取舍

- **prefill 优先、decode 让路**:step 2、3 里 A 明明在 running 却空等两轮。好处是 `run` 不必同时处理两种张量形状;坏处是在座客人的每 token 延迟被后来者拉长。没有它就要做混合批,`prepare_*` 要复杂一倍。
- **分块只给队首**:step 1 剩下 212 预算没用上。换来的是 `schedule` 里一个 `and scheduled_seqs` 就把规则说清。
- **子进程不回传**:logits 经 gather 天然只在 rank 0,回传没必要;代价是没有 ack,主进程无法感知分店挂了。
- **瘦身序列化**:decode 每位客人约 83 字节而不是整段 token_ids;代价是分块 prefill 的第二轮仍要重发整段(B 两次都约 1884 字节)。
- **多采一次就丢**:分块中途仍采样,`run` 不用带"这轮要不要采"的分支,浪费的是一次 softmax。
- **主循环同步单线程**:`generate` 没有并发、没有流式,简单到可以整页画完;换成服务化就得把 `step` 搬进事件循环。

## 八、面试考点串联

- 「nano-vllm 的一次 step 做什么」→ 三段:schedule(先 prefill 后 decode)、run(拍平、前向、采样)、postprocess(写回或丢弃、判结束)。
- 「第一个 token 在哪产生」→ prefill 那一轮的 sampler 产出,postprocess 里 `append_token` 写回;分块未完成的采样结果直接丢。
- 「TP 时主从怎么通信」→ 共享内存 + Event 单向广播方法名与参数;logits 靠 NCCL gather 汇到 rank 0,子进程不回传。
- 「跨进程为什么要 `__getstate__`」→ 只传计数、block_table 和必要的 token,decode 一位客人约 83 字节。
- 「同步点在哪」→ Python 侧 `.tolist()`;进程间 all_reduce / gather;H2D 拷贝 pinned + non_blocking 不等。
- 「为什么 decode 会被 prefill 饿着」→ 调度二选一,没有混合批;可延伸到 vLLM 的混批 chunked prefill 作对比。
