# 04 KV 块与前缀缓存:一个桌位从空闲到复活或重置经过谁的手,拼桌怎么判定?

> 时间尺度:跨 request,一张桌的一生横跨多位客人、多个 step  |  源码基准见总览

这页只回答一件事:一张桌位(KV block)的**编号**怎么在座位管理员的账本里流转,桌上的 **K/V 内容**怎么被灶台按槽位写进显存大张量、又被读回来;两条线只在客人手里的桌号单(block_table)交汇。读完你应该能脱口而出:编号走「空闲队列 → 分配 → 桌号单 → 出菜后整桌盖章登记 → 退桌回队尾但章不擦 → 被人查簿命中就共享或复活,被 popleft 到才重置」;拼桌判定是逐桌算链式哈希、查登记簿、再比对整桌 token,最后一桌永远不查;桌上的内容从不擦除,只被后来者按「桌号 × 256 + 桌内偏移」的槽位覆盖。

五列是桌位的五种处境:空闲与分配、入座、写满盖章、退桌仍带章、拼桌命中。左上 ① 空闲队列往下到 ② 分配或重置,再往右进 ③ 桌号单,这是每张桌第一次被用的路;③ 往右到 ④ 盖章、往上进 ⑤ 登记簿,只有整桌写满才走。⑤ 往右下到 ⑥ 拼桌判定,再往上到 ⑦ 共享或复活,顶上那条回头线把桌号交回新客人的 ③。③ 往下到 ⑧ 退桌,底部那条虚线回到 ①:退桌只把编号送回队尾,章还留在桌上;下一次 ①→② 才是重置。图上所有节点都在主进程,不碰 GPU。

### 图 b:桌上的内容(内容流)

上一行是编号线:① 桌号单进厨房,② 按「桌号 × 256 + 偏移」算出本轮每个 token 的槽位,③ 写进本轮工单。下一行是内容线:菜谱算出本轮的 K、V,④ 灶台的 Triton kernel 按工单里的槽位把它们搬进 ⑤ 显存大张量,⑥ flash-attn 再拿着工单里的 block_tables 从整张大张量里读回自己的桌。③ 到 ⑥ 顶上那条线说明读桌不靠槽位,靠桌号表。这一行都在厨房进程,每 step 重来一次。

## 二、术语卡

| 术语 | 一句话 | 类比 |
|---|---|---|
| Block / block_id | 一张桌的卡片:编号、ref_count、hash、整桌 token 的副本;编号就是它在大张量里的下标 | 桌号牌 |
| free_block_ids / used_block_ids | 空闲编号的双端队列(左出右进,先进先出)与在座编号的集合 | 空桌名单、在座名单 |
| hash_to_block_id | 登记簿:章 → 桌号;只增不删,唯一的删除点在重新分配时 | 拼桌登记簿 |
| 链式哈希(compute_hash) | 本桌的章 = xxh64(前一桌的章 ‖ 本桌 256 个 token);第一桌没有前一桌 | 章上压着前一桌的章 |
| 盖章(hash_blocks) | 出菜后给本轮刚写满的整桌算章并登记;半桌不盖 | 上完一整桌菜才盖章 |
| 拼桌判定(can_allocate) | 从第一桌起逐桌算章、查簿、比对整桌 token,断在第一个未命中处;最后一桌不查 | 领班问「前面几桌有人坐过一样的吗」 |
| 复活 / 共享 | 命中的桌若空出,从空闲队列中间取回、ref_count=1;若在座,ref_count+1 | 空桌上的菜还没撤,直接坐下 / 和别人挤一桌 |
| 重置(reset) | popleft 拿到的桌清掉 ref_count、hash、token 副本,并从登记簿删掉指向自己的章 | 撤桌换新台布 |
| slot / slot_mapping | token 在大张量里的绝对位置 = 桌号 × 256 + 桌内偏移;本轮每个 token 一个 | 桌号 × 座位数 + 座位号 |
| kv_cache / k_cache / v_cache | 开店前摆好的大张量 [2, L, 桌数, 256, H_kv, d];每层灶台拿其中一片视图 | 整个大厅 / 每口灶前的那排桌 |
| store_kvcache | Triton kernel,一个 token 一个程序,按槽位把本轮 K、V 搬进大张量;槽位为 −1 就跳过 | 传菜员按座位号放菜 |
| flash_attn_varlen_func / flash_attn_with_kvcache | 读桌的两条路:prefill 用前者,带 block_table 时改读整张 cache;decode 用后者,按 context_lens 读到哪一格 | 按桌号表找菜 |
| cu_seqlens_k > cu_seqlens_q | 本批有人带着缓存来(拼桌或分批续做),厨房据此才构造 block_tables | 有人拼桌,才需要桌号表 |

## 三、走读:示例乙里桌 0 与桌 7 的一生

店规:8 张桌,每桌 256 个 token,其余默认。客人:A 的 prompt 612 个 token,B 的 562 个,两人前 512 个完全相同;C 的 1024 个与谁都不同;三人 max_tokens=8。到店顺序:第 1 步只有 A;第 2 步之前 C、B 先后到店且 C 在前。这是 03 页干跑定稿的同一条轨迹;本页用同一脚本加上桌位探针重跑,厨房是假的,槽位按厨房的算式复算(见证据表)。下表只盯桌 0 和桌 7:ref 是 ref_count,「章」表示已盖章登记,「空#k」表示在空闲队列第 k 位。

| step | 事件 | 桌 0 | 桌 7 | 空闲队列 | 内容流:本轮写进哪些槽 |
|---|---|---|---|---|---|
| 1 | A 入座 | ①→② popleft 得 0、1、2;ref=1;出菜后 ④ 盖章 0、1,⑤ 登记 | 空#4 | [3,4,5,6,7] | A 写槽 0..611(桌 0、1、2);批里没人带缓存,不建 block_tables |
| 2 | C、B 入座 | ⑥ B 查簿命中 0、1,整桌 token 一致;⑦ 在座 → ref=2 | ①→② popleft 给 B,ref=1;只写 50 个,④ 不盖章 | [] | C 写槽 768..1791;B 写槽 1792..1841;cu_seqlens_k 1586 > cu_seqlens_q 1074,建 block_tables [[3,4,5,6],[0,1,7,−1]],整批改读整张 cache |
| 3 | C 要新桌,B 被请走 | ⑧ ref 2→1,不归零、不动 | ⑧ ref 1→0,回队尾;同一轮 C 的 may_append 再 popleft 到 7,② 重置(无章可删) | [7] → [] | A 写槽 612(桌 2 偏移 100);C 写槽 1792(桌 7 偏移 0),把 B 留下的第一格盖掉 |
| 4–9 | 每轮先看队首 B | ⑥ 每轮都命中 0、1,但缺 1 张新桌,返回 −1 | C 的 decode token 逐格写 1793..1798 | [] | A 写槽 613..618;C 写槽 1793..1798 |
| 9 | 出菜后 A、C 结账 | ⑧ 倒序 2、1、0,ref 归零,依次 append 队尾;章和 token 副本原样留下 | ⑧ C 倒序 7、6、5、4、3,7 最先入队 | [2,1,0,7,6,5,4,3] | 出菜在前、退桌在后,本轮写入照常 |
| 10 | B 回座 | ⑥ 仍命中 0、1;⑦ 空出带章 → free.remove 复活,ref=1;② popleft 得 2 | 空#0,排在队首,下一个被重置的就是它 | [7,6,5,4,3] | B 写槽 512..562(桌 2,51 个),盖掉 A 留下的内容;block_tables [[0,1,2]],从整张 cache 读回 A 写的 0..511 |
| 11–16 | B 上菜、结账 | 第 16 步 ⑧ 归零回队尾,章仍在 | 空#0 | [7,6,5,4,3,2,1,0] | B 写槽 563..568 |

四个值得停一下的地方:

1. **桌 0 为什么能复活。** 第 9 步 A 结账时 ⑧ 只做三件事:ref_count 减一、归零就 append 到空闲队列队尾、清客人的桌号单;`Block.hash`、`Block.token_ids` 和登记簿一个字都没动(`block_manager.py:53-56, 94-101`)。第 10 步 B 查簿命中后,⑦ 发现桌 0 不在 used_block_ids 里,走的是「从空闲队列里 remove 掉、ref_count=1」这条分支(`:85-88`)。显存里桌 0 的 K/V 也没人动过:第 9 步之后没有任何槽位落在 0..511,B 第 10 步直接从整张 cache 读回。
2. **桌 7 为什么被重置。** 桌 7 第 2 步只写了 50 个 token,不满一桌,④ 的登记范围 [512 ÷ 256, 562 ÷ 256) 是空的,没盖章;第 3 步 B 被请走,桌 7 归零回队尾;C 紧接着要新桌,② popleft 到的就是它,`reset` 把 ref_count 置 1、hash 置 −1、token 副本清空(`:20-23, 43-51`)。桌 7 从头到尾没进过登记簿,所以 ② 里「删登记」那一行没有触发;补充干跑里 D 到店 popleft 到带章的桌 6 时才触发(见证据表)。
3. **B 第 4 到 9 步为什么查到却坐不下。** ⑥ 命中 0、1 两桌,但它们都在座,新桌数从 3 减到 1;B 的第三桌必须是新桌,而空闲队列是空的,于是返回 −1(`:69-72`)。第 9 步的查询发生在 A、C 结账之前,所以也是 −1。
4. **第 2 步 C 明明没拼桌,为什么也改读整张 cache。** 厨房按整批判断:只要 cu_seqlens_k 的总和大于 cu_seqlens_q 的总和,就给全批构造 block_tables(`model_runner.py:162-163`);灶台看到 block_tables 不为 None,就把 k、v 换成整张 k_cache、v_cache,由 flash-attn 按 block_table 找桌(`attention.py:65-70`)。C 自己的 K/V 是同一层里前一行 store_kvcache 刚写进去的,读回来一样。

链式哈希与槽位的算式:

$$
h_i = \mathrm{xxh64}\big(\mathrm{le64}(h_{i-1}) \,\|\, \mathrm{int64}(t_{256i}, \dots, t_{256i+255})\big),\qquad i = 0 \text{ 时不拼入 } h_{-1}
$$

$$
\mathrm{slot}(p) = \text{block\_table}\!\left[\lfloor p / 256 \rfloor\right] \times 256 + (p \bmod 256),\qquad
\text{decode 只有一个 } p = \text{len}(seq) - 1
$$

干跑用真实的 xxh64 核对过:A 与 B 前两桌的链式章逐位相同(第一桌 `0xa6e9cbce06c61a00`),而同一桌 token 换一个前缀,章就完全不同。

## 五、状态与失败分支

- **查桌失败**:can_allocate 返回 −1,领班让队首原地等,本轮转 decode(`scheduler.py:36-38`);示例乙第 4 到 9 步的 B 就是这样。
- **同一 step 到店拼不上**:章在 postprocess 才盖(`scheduler.py:83`),同一轮叫号的两位客人互相看不到对方的桌;拼桌只在跨 step 时成立。
- **章相同、桌不同**:登记簿命中后还要比对整桌 token(`block_manager.py:66`),不一致按未命中处理,循环就此打住;前面的桌已逐桌核对过,所以整条前缀都对上了。
- **登记簿指向别桌**:两桌章相同时后登记者覆盖(`:120`);先登记的桌被 popleft 时发现登记簿不再指向自己,不删(`:47`),避免误删别桌的登记。
- **断言**:_allocate_block、_deallocate_block 要求 ref_count==0(`:46, 54`),allocate 要求桌号单为空(`:76`);ref_count 记错会直接崩,而不是悄悄串桌。
- **槽位 −1**:CUDA graph 回放前把 slot_mapping 整段填 −1 再覆盖前 bs 个(`model_runner.py:206-207`),kernel 对 −1 直接返回(`attention.py:23`),多余的批槽不会写到桌 0 上。
- **warmup 不写桌**:开店前试做时 kv_cache 还没分配,k_cache 是空张量,`numel()` 为 0 就跳过写桌(`attention.py:62`);客人也没有桌号单,槽位循环直接 continue(`model_runner.py:149-150`)。
- **显存不够摆一张桌**:`assert config.num_kvcache_blocks > 0`(`model_runner.py:114`),开店直接失败。

| 谁 | 持有 | 不持有 |

| 灶台 Attention | 本层的 k_cache、v_cache 视图 | 桌号的分配权;槽位从工单里取 |

## 七、设计取舍

- **链式哈希,而不是单块哈希。** 章 = xxh64(前一桌的章 ‖ 本桌 token),同一桌 token 换一个前缀就是另一个章(`block_manager.py:36-41`;干跑核对过)。原因是因果注意力下每个 token 的 K、V 取决于它前面的全部 token:只比本桌 256 个 token 相同,桌上的菜不一定相同。代价是命中只能从第一桌连续数下去,中间有一桌不同,后面全部作废。
- **整桌才参与拼桌,最后一桌永远不查。** 盖章范围按整桌下取整(`:111-113`),判定只查前 num_blocks−1 桌(`:62`)。代码没写原因,从行为推断有两层:一是首次入座至少算 1 个 token,厨房总有 logits 可采样(`scheduler.py:39`);二是最后一桌是客人接着写 decode token 的桌(`model_runner.py:181`),必须私有,共享桌永远不会再被写,因此整个项目不需要 copy-on-write。代价是 prompt 尾巴那不到一桌总要重算,示例乙里 B 两次入座各重算了 50 和 51 个。
- **退桌惰性失效,而不是立刻擦章。** _deallocate_block 只动两个集合(`:53-56`),登记删除推迟到该桌被 popleft 重新分配那一刻(`:47-48`)。好处是被请走或刚结账的客人留下的整桌能被下一位复活(示例乙第 10 步 B 省了 512 个 token);代价是登记簿里会积累指向空桌的旧条目,以及 free.remove 是对双端队列的线性查找(`:87`)。
- **先进先出回收,而不是 LRU 结构。** 空闲队列左出右进(`:44, 56`),没有时间戳;退桌时倒序还桌(`:95`),一位客人的尾桌最先入队、前缀桌最晚入队,于是最先被重置的是最早退还的尾桌,最可能被拼的前缀桌留得最久。复活的桌从队列中间取走、下次退桌再排到队尾,效果接近按「上次退桌时间」的 LRU,却只用了一个 deque。
- **ref_count 共享,而不是复制。** 拼桌命中在座的桌只把 ref_count 加一(`:83-84`),两位客人的桌号单里写着同一个编号,大张量里只有一份;退桌时减到零才真正还桌(`:97-99`)。示例乙第 3 步 B 被请走时桌 0、1 只是从 2 减到 1,A 照常读桌。代价是 ref_count 记错就串桌,所以两处断言守着它。

## 八、面试考点串联

- **「PagedAttention 的 block table 在这里长什么样?」** 客人手里的 block_table 是桌号列表,厨房用它算槽位写桌(`model_runner.py:151-161, 181`),右填 −1 成矩阵交给 flash-attn 读桌(`:123-127`,`attention.py:70, 73`);大张量按 [桌数, 256, H_kv, d] 摆,slot × D 就是物理偏移(`attention.py:28, 38`)。
- **「prefix caching 怎么判定命中?为什么要链式哈希?」** 见第七节第一条;再补一句:哈希只当索引,命中还要比对整桌 token(`block_manager.py:66`)。
- **「被抢占的请求回来时省了什么?」** 退桌不擦章、不擦内容,整桌命中就复活;只重算不满一桌的尾巴加已生成的 token(示例乙第 10 步 51 个)。与 03 页的请离席对照着讲。
- **「为什么不需要 copy-on-write?」** 只有整桌、且不是最后一桌才会共享;共享桌不再被写。这是「最后一桌不参与拼桌」换来的简化。
- **「KV cache 能摆多少桌是怎么算出来的?」** warmup 先做一次最大批量量出峰值,剩余显存除以每桌字节数 2 × L × 256 × H_kv × d × itemsize(`model_runner.py:106-113`);TP 时 H_kv 按分店数平分(`:110`)。
- **「CUDA graph 回放时批不满怎么办?」** slot_mapping 填 −1、kernel 跳过(`model_runner.py:206`,`attention.py:23`),context_lens 清零、block_tables 只覆盖前 bs 行(`:208-210`)。
