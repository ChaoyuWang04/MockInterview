# 06 启动期:开店前按什么顺序做了什么,每一步定下哪些常量?

> 时间尺度:启动期一次  |  源码基准见总览

这页只回答一件事:`LLM(path, ...)` 这一行背后,经理和厨房按什么顺序把店开起来,每一步产出什么常量、被谁消费、受哪条店规影响。读完你能说出:桌数不是配置出来的,是 rank 0 厨房试做一单量出峰值之后按剩余显存算出来再写回店规的,所以领班必须在厨房之后才能建;分店是先开的,各自完整跑一遍厨房初始化,最后停在传菜窗口前等指令;CUDA graph 在开门前就按批大小倒序录好了。

## 一、先看图

![启动期:从店规到开门](/opensource/nano-vllm/06-startup.svg)

[打开交互版](/opensource/nano-vllm/06-startup.html)

怎么读:三条泳道是三个角色,经理在主进程,厨房 rank 0 也在主进程,分店厨房各占一个子进程。主路径 ① 到 ⑦ 从左到右单调推进,粗线是必经之路。② 之后有一条虚线下到分店泳道:分店进程一启动就各自把 ③ 到 ⑥ 同样跑一遍,再在 ⑥ 之后与总店 barrier 会合、打开传菜窗口进入 loop。⑤ 到 ⑦ 那条虚线是 `enforce_eager=True` 时跳过录流水线的捷径。每个节点的副标题就是它产出的常量。

## 二、术语卡

| 术语 | 一句话 | 类比 |
|---|---|---|
| warmup / 试做 | 开门前用假客人跑一次最大规模的 prefill,让 CUDA 分配器记住前向的峰值占用 | 试做最大一单,看灶台最多要占多大地方 |
| 峰值显存 peak | `torch.cuda.memory_stats` 里 allocated_bytes.all.peak,历史最高分配量 | 最忙时厨房占的面积 |
| itemsize | 一个数占几字节,bf16 是 2 | 一份菜的分量 |
| CUDA graph 捕获 / 内存池 | 把一次前向的所有 GPU 操作录成图,之后按批大小回放;多张图共用同一块中间显存 | 为常见桌数预排好流水线,共用一套周转盘 |
| spawn | 子进程从头启动一个新的 Python 解释器并重新导入模块,不继承父进程的状态 | 新开一家分店,不是把总店复制一份 |
| barrier | 所有 rank 都到齐才继续 | 各店同时开张的会合点 |
| NCCL 进程组 | GPU 之间集合通信的成员名单,按地址与 rank 编号入组 | 各分店的对讲机频道 |
| safetensors / packed_modules_mapping | 权重文件格式;把 HF 权重里分开存的 q、k、v 与 gate、up 装进 nano-vllm 融合后的线性层的对应分片 | 把散装食材倒进预先分好格的盒子 |

## 三、走读:示例丙,店规默认,TP=2

店规默认:一轮最多 16384 个 token、最多 512 位客人、单条最长 4096、显存用 0.9、桌大小 256、录流水线。模型形状用符号:L 层、每个 rank H_kv 个 kv 头、每头 d 维。下面按图上编号走,行号都在 `nanovllm/engine/` 下,厨房的行号指 `model_runner.py`。

**① 建店规。** 经理只把 Config 认识的字段收进来,其余关键字丢掉,构造店规;`__post_init__` 做三条断言:模型目录存在、桌大小是 256 的倍数、TP 在 1 到 8 之间;再把 `max_model_len` 与模型自带的 `max_position_embeddings` 取小。然后把桌大小写进客人类的类属性,之后每位客人算自己要几桌都用它。产出:店规对象。`llm_engine.py:18-21`,`config.py:20-25`

**② 开分店。** TP=2 时只开一家分店:用 spawn 上下文造一个 Event,起一个子进程,目标函数就是 ModelRunner 本身,参数是店规、rank 1 和这个 Event。店规是以 pickle 副本进入子进程的,分店之后改的是自己那份。产出:子进程句柄列表 ps 与 Event 列表。`llm_engine.py:22-30`

**③ 建菜谱装权重。** rank 0 和分店各做一遍:先按固定地址 `tcp://localhost:2333` 加入 NCCL 进程组,选自己的卡,把默认 dtype 改成模型的 dtype、默认 device 改成 cuda,这样后面凡是 `torch.empty` 都直接落在卡上。建 Qwen3ForCausalLM,再装权重:遍历目录下所有 safetensors,凡是名字里带 q_proj、k_proj、v_proj 的装进融合层 qkv_proj 的对应分片,gate_proj、up_proj 装进 gate_up_proj,其余参数直接拷贝;分片怎么切由参数自带的 weight_loader 决定。最后建采样器。产出:在卡上的模型。`model_runner.py:26-33`,`utils/loader.py:12-28`,`models/qwen3.py:187-193`

**④ 试做最大一单。** 清空缓存、重置峰值统计,然后造假客人:每位长度 seq_len 等于预算与单条上限取小,默认是 4096;人数等于预算除以 seq_len 与人数上限取小,默认是 4。给每位客人把本轮要算的数填成整段,跑一次 prefill。此时还没有 KV 大张量,灶台看到 k_cache 是空的就跳过写入,客人也没有桌位所以槽位映射为空;这一单只为让分配器记下激活与 logits 的峰值。跑完再清一次缓存。产出:峰值显存读数。`model_runner.py:91-101`,`:149-150`,`layers/attention.py:62`

**⑤ 摆桌。** 读显存总量与空闲量,算出已用量;读峰值与当前分配量;每个 rank 的 kv 头数是模型 kv 头数除以 TP;一桌的字节数按公式算;桌数等于「总量乘 0.9 减去已用、减去峰值、加回当前」整除一桌字节数,断言大于零;然后一次性 `torch.empty` 出形状为 [2, L, 桌数, 256, H_kv, d] 的大张量,逐层把第 0 维的 K 视图和 V 视图挂到每个灶台上。产出:`config.num_kvcache_blocks` 与 kv_cache。注意写回的是各自手里的店规:rank 0 改的是经理那份,分店改的是自己的副本。`model_runner.py:103-121`

$$
\text{block\_bytes} = 2 \cdot L \cdot 256 \cdot H_{kv} \cdot d \cdot \text{itemsize},\qquad
\text{num\_kvcache\_blocks} = \left\lfloor \frac{\text{total}\cdot 0.9 - \text{used} - \text{peak} + \text{current}}{\text{block\_bytes}} \right\rfloor
$$

**⑥ 录流水线。** `enforce_eager` 为假才做。最大批 max_bs 取人数上限与 512 的小者,默认 512;每位客人最多几桌按单条上限除以桌大小向上取整,默认 16。先造好一套静态输入缓冲:input_ids、positions、slot_mapping、context_lens 各 512 长,block_tables 是 512 乘 16,outputs 是 512 乘 hidden。批大小列表是 1、2、4、8 再加 16 到 512 步长 16,共 36 档。按从大到小的顺序,每档先设本轮工单、跑一遍前向热身,再在 `torch.cuda.graph` 里跑一遍录下来;第一张图的内存池给后面所有图共用;录完同步一次、清掉工单。产出:graphs 字典、graph_pool、graph_vars。`model_runner.py:223-257`

录完把默认 device 与 dtype 改回去,之后 CPU 侧临时张量默认落在 CPU,再钉住内存异步拷贝进卡。TP=2 时还有一步会合:rank 0 建一块名为 nanovllm、1 MiB 的共享内存,然后 barrier;分店先 barrier 再按名字打开同一块内存,随即进入 loop,`__init__` 从此不返回,直到收到 exit。`model_runner.py:38-48`,`:61-66`

**⑦ 建领班,开门。** 回到经理:装 tokenizer,把 eos 写进店规,然后建领班;领班构造时把店规里的桌数交给座位管理员,座位管理员按这个数造桌位表和空闲队列。最后登记 atexit,保证退出时能通知分店。产出:领班与座位管理员。`llm_engine.py:32-35`,`scheduler.py:15`,`block_manager.py:28-33`

**退出路径。** 进程退出触发 atexit:经理广播 exit,分店的 loop 收到 exit 跳出;经理删掉厨房对象,再逐个 join 子进程。厨房自己的 exit 关闭共享内存、rank 0 负责 unlink,删掉 graphs 与内存池,同步一次,退出 NCCL 组。`llm_engine.py:35-41`,`model_runner.py:50-59`

| 函数或参数 | 位置 | 做什么 | 默认或条件 |
|---|---|---|---|
| `LLMEngine.__init__` | `llm_engine.py:17-35` | 店规、桌大小、分店、rank 0 厨房、tokenizer、eos、领班、atexit,顺序固定 | 领班在厨房之后 |

## 五、状态与失败分支

- **三条店规断言**在 ① 就挡住:模型目录不存在、桌大小不是 256 倍数、TP 超出 1 到 8。
- **桌数算出来不是正数**在 ⑤ 断言失败:别的进程占着显存,或者模型加试做峰值已经超过 0.9 的总量。
- **各 rank 各自算桌数,经理只用 rank 0 那个数。** 分店改的是店规副本,没有人把 rank 0 的桌数广播给分店。若某张卡空闲显存更少,它的大张量就更小,rank 0 分出的高桌号在那张卡上会越界。这是推断,未实测。
- **地址与名字写死**:NCCL 用 `tcp://localhost:2333`,共享内存名固定 nanovllm。同一台机器上第二个 TP 大于 1 的实例会撞端口或撞名。这是推断。
- **分店的 `__init__` 不返回**:它在 barrier 之后进入 loop,只有 exit 能让它出来;分店里出的异常不会回传给经理,01 页已述。
- **spawn 要求用户脚本有 main 保护**:子进程会重新导入主模块,example.py 用 `if __name__ == "__main__"` 包住入口。`example.py:32-33`
- **试做不写 KV**:此时 k_cache 为空,灶台跳过写入,所以峰值里只有激活与 logits,不含 KV;KV 的空间正是 ⑤ 里「减去峰值之后剩下的」。

## 六、持有什么,不持有什么

启动期结束时:

- **经理**持有 tokenizer、领班、rank 0 厨房、子进程句柄与 Event;店规里的 `eos` 与 `num_kvcache_blocks` 是启动期才填上的两项。它不持有任何 GPU 张量。
- **厨房 rank 0**持有模型、采样器、kv_cache 大张量、graphs、graph_pool、graph_vars,以及 TP 时的共享内存句柄。它不持有领班,也不知道桌数被谁消费。
- **分店厨房**各持有一份同样的东西,外加自己的 Event 与店规副本;不持有 tokenizer、领班、采样温度。
- **每个灶台**持有 kv_cache 里属于自己那一层的 K、V 视图;写入位置由每轮工单的槽位映射决定。

## 七、设计取舍

- **试做量峰值,而不是按公式估显存。** 公式要把每层激活、logits、临时缓冲全算准,模型一换就错;跑一次真前向让分配器自己报数,代价是启动多花一次最大规模 prefill 的时间。
- **开门前预录 36 档流水线。** 换来 decode 每步免去几百次 kernel 启动的 Python 开销;代价是启动期 36 次热身加 36 次捕获,以及一套 512 行的静态缓冲和共享内存池;`enforce_eager` 是关掉它的总闸。
- **桌数各算各的,不广播。** 少一次进程间通信,代码更短;代价是默认各卡显存一致,不一致时没有保护。
- **地址与名字写死。** 零配置就能起 TP;代价是同机单实例。
- **spawn 而不是 fork。** 子进程干净地重新导入,不继承父进程已经初始化的 CUDA 上下文;代价是启动慢一些,且要求 main 保护。

## 八、面试考点串联

- 「KV cache 的块数怎么定」→ 试做量峰值,剩余显存整除一块字节数;一块字节数是 2 乘层数乘 256 乘每 rank kv 头数乘头维乘 itemsize。
- 「为什么要 warmup」→ 不是为了预热性能,是为了让分配器记下峰值,好把剩下的显存全摆成桌子。
- 「CUDA graph 怎么捕获、怎么选」→ 36 档批大小倒序捕获、共享一个池;decode 时选第一个不小于当前批的档,多出来的位置用 -1 槽位跳过写入。
- 「TP 子进程怎么起、怎么退」→ spawn 起、各跑一遍初始化、barrier 后开共享内存进 loop;退出靠 atexit 广播 exit 再 join。
- 「启动顺序里最容易忽略的依赖」→ 领班必须在厨房之后建,因为桌数是厨房试做后才写回店规的。
