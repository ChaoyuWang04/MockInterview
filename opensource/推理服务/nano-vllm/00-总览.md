# nano-vllm 总览

一句话:**nano-vllm 是一个从零写的迷你 vLLM,1385 行 Python,把「很多人同时要生成」翻译成「GPU 每一步算一批」。** 模型结构只占 216 行,近一半代码在做排队、座位和批次三件事。它不是一个模型,是一台调度机器。

源码基准:官方仓库 <https://github.com/GeeeekExplorer/nano-vllm>,分支 `main`,commit `bb823b3e06983d71485a8e1f23715ebd87d98ef8`,提交日期 2026-04-26,核对日期 2026-09-09。本项目所有页面里的「当前」「默认」都指这组基准。官方自述是 a lightweight vLLM implementation built from scratch;README 列的特性是 prefix caching、tensor parallelism、torch compilation 与 CUDA graph,其中 torch compilation 在代码里是五个小算子上的 `@torch.compile` 装饰(激活、RMSNorm、旋转位置编码、采样),不是整模型编译。

## 一、先看一张总图

![nano-vllm 总图:两种进程,一条指挥链](/opensource/nano-vllm/00-overview.svg)

[打开交互版](/opensource/nano-vllm/00-overview.html):可以缩放、搜索、点一个组件高亮它的上下游;右上角三个「引导视图」分别只亮出指挥链、数据面和进程边界;每个组件右上角的「来源」标签指向对应的文件与行号。

怎么读这张图:

- **上面一行是指挥链。** 用户脚本把 prompts 交给经理;经理每一轮先问领班「这轮叫谁」,领班向座位管理员要桌位;然后经理把这一批交给厨房。
- **中间一行是数据面。** 厨房把这批客人的单拍平成张量,交给菜谱前向;灶台把算出的 K/V 按槽位写进显存里那张 KV cache 大张量,下一轮直接读。
- **左边一列是进程边界。** 只有开了张量并行(TP)才存在。rank 0 的厨房把「做什么、给谁做」写进传菜窗口并按铃,分店厨房醒来做同样的菜,只在算子内部通过 NCCL 对账。分店不做决策、不采样、不回传。
- 实线是调用与数据,虚线是控制消息,橙色虚框是进程边界。

## 二、它站在哪一层

| 层 | 里面有什么 | 行数 | 谁提供 |
|---|---|---|---|
| 用户脚本 | 构造 LLM 与 SamplingParams,调 generate | 33 | 你写,`example.py` |
| 调度与编排 | LLMEngine、Scheduler、BlockManager、Sequence、ModelRunner | 642 | nano-vllm `engine/` |
| 模型结构 | Qwen3 的 attention、MLP、decoder layer、lm_head | 216 | nano-vllm `models/` |
| 算子 | TP 切分的 linear、写 KV 的 Triton kernel 与 attention 封装、RMSNorm、RoPE、embedding、采样 | 429 | nano-vllm `layers/` |
| 配置与工具 | Config、SamplingParams、Context、权重加载 | 98 | nano-vllm |
| 注意力核与通信 | flash_attn_varlen_func、flash_attn_with_kvcache;NCCL all-reduce | 第三方 | flash-attn、torch.distributed |
| 计算底座 | tensor、CUDA graph、Triton、torch.compile | 第三方 | PyTorch、Triton |
| 硬件 | 1 到 8 张 GPU | | |

读出两件事。第一,nano-vllm 自己不写注意力核,注意力全交给 flash-attn;它写的是**围绕注意力的一切**:谁先算、算多少、K/V 放在哪、怎么复用。第二,vLLM 有 61 万行,nano-vllm 只留了这条主干,所以它是理解 vLLM 调度骨架的最短路径,但它没有 API server、没有异步引擎、没有把 KV 换出到 CPU、没有投机解码。

## 三、一个餐厅的比喻

全项目只用一个比喻:一家座位有限的餐厅。后面每一页的角色名都从这张表来。

| 代码里的东西 | 餐厅里的角色 | 一句话 |
|---|---|---|
| LLMEngine | 经理 | 收单、每一轮问领班叫谁、把这一批交给厨房、收结果 |
| Scheduler | 领班 | 决定这一轮服务哪些客人:先安排新客入座点菜,一位新客都没排上才给在座的上下一道菜 |
| BlockManager | 座位管理员 | 管桌位:分配、回收、登记哪几桌坐过同样的人以便拼桌 |
| Sequence | 一位客人 | 一条请求:等位、在座、结账三种状态 |
| ModelRunner | 厨房 | 把这一批客人的单拍平,一锅做出来;rank 0 还负责出菜,也就是采样 |
| ModelRunner rank 1..N | 分店厨房 | TP 子进程,只跟着做同样的菜,不做决策 |
| SharedMemory + Event | 传菜窗口 + 叫号铃 | rank 0 把「做什么、给谁做」写进窗口,按铃叫醒分店 |
| Qwen3ForCausalLM + layers | 菜谱与灶台 | 模型结构与算子;Attention 是把 K/V 放进桌位的那口灶 |
| Context | 本轮工单 | 这一轮的变长拼批元数据、槽位映射、桌位表 |
| Config / SamplingParams | 店规 | 所有上限与默认值 |
| KV block | 桌位 | 256 个 token 一桌;显存里能摆多少桌在开店前算好 |
| prefix cache | 拼桌 | 开头几桌完全一样的客人共用桌位,不重做 |
| prefill | 新客入座上第一轮菜 | 一次把 prompt 全部算完,产出第一个 token |
| decode | 每轮给每桌上一道菜 | 每个 step 每位在座客人只算一个 token |
| chunked prefill | 大桌分批上菜 | prompt 超过一轮预算时分几轮做,且只允许队首客人这么做 |
| preempt | 请离席重新排队 | 桌位不够时收回在座名单最后一位的桌位,没有别人就收自己的;他回到等位队列最前面,再次入座时能拼桌的部分不用重算 |
| CUDA graph | 预排好的流水线 | 开店前为常见桌数录好一整套动作,decode 时直接回放 |
| warmup | 开店前试做最大一单 | 量出厨房最多要占多少显存,剩下的全摆桌子 |

## 四、组件登记表

每个组件用「角色名 · 代码名」两个名字,后面各页都沿用。「持有什么、不持有什么」是理解系统最狠的一刀:谁拥有哪块可变状态,谁就是那块状态的真源。

| 角色 | 代码名 | 所在进程 | 持有什么 | 不持有什么 |
|---|---|---|---|---|
| 用户脚本 | `example.py` | 主进程 | prompts、SamplingParams | 任何内部状态 |
| 经理 | LLMEngine | 主进程 | tokenizer、领班、rank 0 厨房、子进程句柄与 Event | 任何 GPU 张量 |
| 领班 | Scheduler | 主进程 | waiting、running 两个队列,座位管理员 | 模型状态、token 内容 |
| 座位管理员 | BlockManager / Block | 主进程 | 桌位表、空闲队列、占用集合、哈希到桌位的索引 | 桌上的 K/V 内容,只管编号 |
| 客人 | Sequence / SequenceStatus | 主进程,跨进程时瘦身序列化 | 自己的 token、状态、block_table、各种计数 | 其他客人 |
| 厨房 | ModelRunner | rank 0 在主进程,其余各占一个子进程 | KV cache 大张量、CUDA graph 池与静态输入缓冲、模型权重 | 队列与调度决策 |
| 传菜窗口 | SharedMemory + Event | 主进程与子进程之间 | 1 MiB 共享内存,内容是 pickle 的「方法名 + 参数」 | 返回值,子进程不回传 |
| 本轮工单 | Context | 每个厨房进程内全局 | 本轮的累计长度、槽位映射、上下文长度、桌位表 | 跨轮状态 |
| 灶台 | Attention + store_kvcache | 厨房进程 | k_cache、v_cache 视图 | 桌位编号的分配权 |
| 菜谱 | Qwen3ForCausalLM + layers | 厨房进程 | 权重、TP 切分的算子 | 调度信息 |
| 店规 | Config / SamplingParams | 全局 | 上限与默认值 | 运行态 |

店规的全部默认值,出处 `nanovllm/config.py:8-18` 与 `sampling_params.py:5-8`:

| 参数 | 默认 | 含义 |
|---|---|---|
| max_num_batched_tokens | 16384 | 厨房一轮最多做多少个 token |
| max_num_seqs | 512 | 一轮最多同时服务多少位客人 |
| max_model_len | 4096 | 单条请求最长 token 数,还会与模型的 max_position_embeddings 取小 |
| gpu_memory_utilization | 0.9 | 显存总量的多少可以用 |
| tensor_parallel_size | 1 | 分店厨房数量,1 到 8 |
| enforce_eager | False | True 则不录 CUDA graph,全部现做 |
| kvcache_block_size | 256 | 一桌坐多少 token,必须是 256 的倍数 |
| num_kvcache_blocks | -1 | 开店前由 rank 0 算出写回,见 06 |
| eos | -1 | 开门前由 tokenizer 填入 |
| temperature | 1.0 | 必须大于 1e-10,不允许贪心 |
| max_tokens | 64 | 最多生成多少 token |
| ignore_eos | False | True 则遇到 eos 不停 |

**贯穿各页的三个示例。** 同一批客人在不同页反复出现,数字不另编:示例甲给 01 与 02,店规取 example.py 的实参加一轮预算 512、16 张桌,A、B、C 三位客人的 prompt 分别 300、600、1000 个 token,`max_tokens=3`,轨迹 7 步;示例乙给 03 与 04,8 张桌,A 612、B 562 且前 512 个 token 相同,C 1024,`max_tokens=8`,第 3 步 B 被请离席、第 10 步回座拼桌;示例丙给 05 与 06,店规默认,模型形状用 L、H_kv、d 符号。示例甲、乙的数字都来自用纯 Python 干跑真实的领班与座位管理员代码,不是手算。

## 五、阅读顺序

先结构后行为。本页建立位置感;01 看指挥链怎么转;02 与 03 拆领班;04 拆座位管理员;05 与 06 拆厨房;07 回答「没有它会怎样」。每页只回答一个问题,页首标明时间尺度,图在前、走读在后。

| 页 | 回答的问题 | 时间尺度 | 图型 |
|---|---|---|---|
| 01 指挥循环 | 两条 prompt 从进门到第一个 token 再到结束,经过哪些手,哪一跳跨进程 | 每 request | 时序图 + 骨架代码 |
| 02 调度决策 | 一次 schedule 里预算怎么分,prefill 为什么优先,分块与抢占在哪分叉 | 每 step | 流程图 |
| 03 请求状态机 | 一位客人有哪些状态,什么事件触发跳转,被请离席后回到哪 | 每 request,跨 step | 状态机 |
| 04 KV 块与前缀缓存 | 一个桌位从空闲到复活或回收经过谁的手,拼桌怎么判定 | 跨 request | 数据流 |
| 05 一次前向 | 一批客人怎么拍平成张量,现做与流水线怎么选,分店怎么跟着跑 | 每 step | 数据流 |
| 06 启动期 | 开店前做了什么,每步产出什么常量,受哪些店规影响 | 启动期一次 | 流程图 |
| 07 取舍与消融 | 没有领班、座位管理员、拼桌、流水线、分店各会怎样 | | 表格 |

## 六、术语表

只在这里定义一次,各页直接用。

| 术语 | 一句话 | 类比 |
|---|---|---|
| prefill / decode | 先把 prompt 一次算完并产出第一个 token,之后每步只算一个 token | 新客入座上第一轮菜 / 每轮上一道菜 |
| KV cache | 每层 attention 算过的 key 与 value 存下来,后面的 token 直接读 | 每桌已经上过的菜 |
| block / block_table | 256 个 token 的 KV 为一块;每位客人持有自己用到的块编号列表 | 桌位 / 这位客人坐过哪几桌 |
| slot / slot_mapping | 块编号乘 256 加块内偏移,得到每个 token 在大张量里的绝对位置 | 桌号乘座位数加座位号 |
| prefix cache | 按块算链式哈希,开头几块内容完全相同就复用同一块 | 拼桌 |
| chunked prefill | prompt 超过一轮预算就分几轮做 | 大桌分批上菜 |
| preempt | 桌位不够时收回在座名单最后一位的桌位,让他回到等位队首重新排队;桌上的章不擦,回来还能拼桌 | 请离席 |
| 自抢 | decode 时在座名单里没有别人可抢,只能把自己请离席;若批里还没人会撞断言 | 没人可让,自己起身 |
| TTFT | Time To First Token,从请求到第一个 token 的等待;prefill 优先压的就是它 | 新客等第一道菜的时间 |
| batch / step | 一轮:领班叫一批客人,厨房做一次前向 | 一轮上菜 |
| CUDA graph | 把一次前向的所有 GPU 操作录下来,之后按批大小直接回放 | 预排好的流水线 |
| eager | 不用 CUDA graph,每次现跑 | 现做 |
| TP / all-reduce | 张量并行:同一层的矩阵切给多张卡,算完把结果加起来 | 分店各做一半,再对账 |
| NCCL | GPU 之间集合通信的库 | 分店之间的对讲机 |
| spawn / SharedMemory / Event | 子进程启动方式 / 进程间共享的一块内存 / 进程间的信号量 | 开分店 / 传菜窗口 / 叫号铃 |
| varlen / cu_seqlens | 把长短不一的多条序列首尾相接拼成一条,用累计长度数组记录边界 | 把几桌的单写在同一张纸上,用横线分隔 |
| context_lens | decode 时每位客人当前已有多少 token | 每桌已经上了几道菜 |
| ref_count | 一块被几位客人共用 | 一桌坐了几拨拼桌的人 |
| pinned memory | 钉住不换页的 CPU 内存,GPU 可以异步直读 | 传菜口的固定托盘 |
| xxhash | 一种快速非加密哈希,用来给每块 token 内容做指纹 | 给每桌菜单盖章 |

## 七、状态所有权表

| 可变状态 | 拥有者 | 谁在哪里改它 | 谁读它 |
|---|---|---|---|
| waiting、running 两个队列 | 领班 | add、schedule、preempt、postprocess,`engine/scheduler.py:22-92` | 经理的 is_finished |
| 桌位表、空闲队列、占用集合、哈希索引 | 座位管理员 | allocate、deallocate、hash_blocks,`engine/block_manager.py:43-120` | 领班的 can_allocate、can_append |
| 客人的 status、is_prefill、block_table、各计数 | 客人自己保存,领班与座位管理员改 | `engine/scheduler.py:46-51, 67-69, 76-77, 84-90`;`engine/block_manager.py:89-101, 108` | 厨房拍平时读 |
| KV cache 大张量 | 厨房 | 灶台的 store_kvcache 按槽位写,`layers/attention.py:33-40, 63` | flash-attn 读 |
| CUDA graph 池与静态输入缓冲 | 厨房 | 启动期 capture_cudagraph 建,`engine/model_runner.py:223-257`;每轮 run_model 填,`:200-211` | graph.replay |
| 本轮工单 Context | 厨房进程内全局 | prepare_prefill 与 prepare_decode 设,run 末尾清,`engine/model_runner.py:169, 187, 219` | 灶台 |
| num_kvcache_blocks | 店规,启动期由 rank 0 写回 | allocate_kv_cache,`engine/model_runner.py:113` | 领班构造座位管理员时读,`engine/llm_engine.py:34` |
| 静态缓冲 graph_vars、采样温度、采出的 token | 厨房;后两项只在 rank 0 存在 | run_model 每轮填缓冲,`engine/model_runner.py:203-210`;`:216, 218` | graph.replay;经理收 token |
| 子进程收到的客人副本 | 无人持有,算完即弃 | `engine/model_runner.py:63-64`,`engine/sequence.py:76-83` | 分店厨房拍平时读 |

最后一行值得多看一眼:桌位总数是 rank 0 厨房开店试做之后才算出来写回店规的,而经理是先建厨房、再建领班,领班才能拿到这个数。这条启动顺序上的依赖,06 页会展开。

想找代码时看这张表;读懂系统不需要先看它。
