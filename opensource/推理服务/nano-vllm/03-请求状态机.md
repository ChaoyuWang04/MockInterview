# 03 请求状态机:一位客人从等位到结账经过哪些状态?

> 时间尺度:每 request,跨 step  |  源码基准见总览

这页只回答一件事:一位客人(Sequence)从建单到结账会经过哪些状态、什么事件让它跳转、哪个是终态、被请离席之后回到哪里又丢了什么。读完你应该能脱口而出:状态牌只有 WAITING、RUNNING、FINISHED 三种;WAITING 靠 block_table 空不空再分成「等位」和「大桌分批上菜中」;只有在座的客人会被请离席;请离席回到 waiting 队首,桌位和已缓存计数清零,但 token_ids 一个不丢;回来时拼桌照样能命中,因为收桌位时不擦哈希。

## 一、先看图

![客人的一生:一条请求从等位到结账经过哪些状态?](/opensource/nano-vllm/03-request-lifecycle.svg)

[打开交互版](/opensource/nano-vllm/03-request-lifecycle.html)

上面一条带是主路径,四个编号状态从左到右:①等位 → ②大桌分批上菜中 → ③在座 → ④结账;①到③之间从上方绕过去的那条粗线才是常见路径,一轮吃下整份 prompt 就不经过②。下面一条带只有一个节点「请离席」,画成可恢复的失败:它只从③进来,并且有一条真实的回头路回到①。③不画自环,节点副标题「每轮上一道菜」就是那个循环:每个 step 出一个 token,直到结账。代码里没有取消、超时、出错这类状态,④是唯一的终态。

## 二、术语卡

| 术语 | 一句话 | 类比 |
|---|---|---|
| status / SequenceStatus | 客人身上的状态牌,只有 WAITING、RUNNING、FINISHED 三种 | 等位牌、座位牌、已结账 |
| waiting / running | 领班手里的两张名单,都是双端队列;新客进 waiting 队尾,入座后进 running 队尾 | 等位名单、在座名单 |
| block_table | 客人手里的桌号单;空的表示还没分到桌位 | 坐过哪几桌 |
| num_cached_tokens | 已经算完 K/V、真正「上了桌」的 token 数 | 已上的菜数 |
| num_scheduled_tokens | 本轮要算的 token 数;领班每轮填、厨房用、出菜后清零 | 本轮点的菜数 |
| is_prefill | 客人下一轮是不是「上第一轮菜」;也决定跨进程时带全部 token_ids 还是只带最后一个 | 新客标记 |
| can_append / may_append | 上下一道菜前看看要不要新桌:长度除以 256 余 1 时要 | 这桌坐满了,再开一桌 |
| eos / max_tokens / ignore_eos | 两种结账条件:出了结束符,或生成数达到上限;ignore_eos 只关掉前者 | 客人说吃饱了 / 到打烊时间 |
| preempt | 桌位不够时把在座名单最后一位请走,桌位收回,他回到等位名单最前面 | 请离席 |

## 三、走读:示例乙,三位客人把 8 张桌挤满

店规:8 张桌,每桌 256 个 token,其余默认(一轮最多 16384 个 token、512 位客人)。客人:A 的 prompt 612 个 token,B 的 562 个,两人前 512 个完全相同;C 的 prompt 1024 个,与谁都不同。三人 max_tokens 都设为 8,方便看完整个过程。到店顺序:第 1 步只有 A;第 2 步之前 C、B 先后到店,C 排在 B 前面,这样 B 是最晚入座的,第 3 步被请走的就是他。厨房用假的:每轮给每位客人出一个不等于 eos 的 token。下表由纯 Python 干跑真实的领班与座位管理员得到(见证据表),c 是 num_cached_tokens,n 是 num_tokens,桌是 block_table。

| step | 分支 | 本轮叫号 | A | B | C | 空桌 | 图上发生了什么 |
|---|---|---|---|---|---|---|---|
| 1 | prefill | A:612 | ③ c=612 桌 0,1,2 | ① | ① | 5 | A 走 ①→③:拼桌查询命中 0 桌,分 3 桌;出菜后桌 0、1 盖章,第 1 个 token 到手,n=613 |
| 2 | prefill | C:1024,B:50 | ③ | ③ c=562 桌 0,1,7 | ③ c=1024 桌 3,4,5,6 | 0 | C 是队首先叫号,分 4 桌;B 拼桌命中 A 的桌 0、1,只算 50 个;在座名单变成 [A, C, B],桌位用光 |
| 3 | decode | A:1,C:1 | ③ c=613 | 请离席→① n=563 | ③ c=1025 桌 3,4,5,6,7 | 0 | C 的 n=1025,除 256 余 1 要新桌但没空桌:请走在座名单最后一位 B;B 桌位收回(桌 7 空出,桌 0、1 只减一次 ref_count)、c=0、is_prefill=True、回到等位队首;C 拿到桌 7 |
| 4–8 | decode | A:1,C:1 | ③ | ①(队首) | ③ | 0 | 每轮先看队首 B:拼桌查询回 -1(缺 1 张新桌),领班直接转 decode;B 干等 5 轮 |
| 9 | decode | A:1,C:1 | ④ n=620 | ① | ④ n=1032 | 8 | A、C 第 8 个生成 token 到手,达到 max_tokens:结账、桌位全部收回,但桌上的哈希和内容都还在 |
| 10 | prefill | B:51 | ④ | ③ c=563 桌 0,1,2 | ④ | 5 | B 重新入座:拼桌命中 2 桌,桌 0、1 虽已空出但没被人重置,直接复活;num_cached_tokens=512;只算 51 个 = 50 个自己的 prompt + 1 个第 2 步生成的 token |
| 11–15 | decode | B:1 | ④ | ③ | ④ | 5 | 正常上菜 |
| 16 | decode | B:1 | ④ | ④ n=570 | ④ | 8 | B 结账,两张名单都空,generate 循环结束 |

三个值得停一下的地方:

1. **第 2 步 B 为什么能拼桌**:桌位的章是在出菜后盖上去的;A 第 1 步就上完了菜,所以第 2 步 B 来时桌 0、1 已有章。若 A、B 同一轮到店、同一轮叫号,B 查桌时章还没盖,命中 0 桌。拼桌只在「跨 step」成立(`block_manager.py:110-120`,`scheduler.py:83`)。
2. **第 3 步为什么是 B 被请走**:领班从在座名单头部取到 C,发现要新桌又没空桌,先请走名单最后一位,那是最晚入座的 B;请走后再查一次 C,有空桌了就继续。如果 C 后面没有人,C 会请走自己(`scheduler.py:60-65`)。
3. **第 10 步 B 省了什么、丢了什么**:省下 512 个 token 的 K/V,不是靠自己的旧桌(桌 7 早被 C 重置),而是靠 A 留下的桌 0、1;丢掉的是 50 个自己的 prompt 和 1 个已生成 token 的 K/V,重新算一遍。token_ids 本身一个没丢,第 2 步生成的那个 token 还在,第 10 步的 51 个里包含它。

换一个到店顺序(B 先于 C 到店):在座名单是 [A, B, C],第 3 步 C 自己要新桌时名单已空,只能请走自己;第 4 到 9 步 C 一直查不到桌位,因为它要 5 张(4 张复活 + 1 张新),而空桌只有 4 张:拼桌查询里「空出但有章」的桌算命中,却不减少要申请的新桌数。第 10 步 A、B 结账后 C 回座,4 张旧桌全部复活,只重算 1 个 token。这是「请离席后重新排队,拼桌能省掉什么」的极端答案:整份 prompt 都能省,前提是没人动过那些桌(`block_manager.py:66-72`)。

再换店规把一轮预算压到 512 个 token(max_num_batched_tokens=512):C 的 1024 个要分两轮。第 1 步后 C 处在 ②:状态牌仍是 WAITING、桌 0 到 3 已分好、c=512、仍在等位队首;第 2 步吃完后半段才转 ③。这期间不会进入 decode 分支,因为只要队首有分批中的客人,prefill 分支一定叫得到人并提前返回。代价是在座客人饿着:同一干跑里第 3、4 步 A 分批时,C 坐在座位上两轮没上菜(`scheduler.py:41-55`)。

## 四、关键函数、参数与默认行为

| 函数或参数 | 位置 | 做什么 | 默认或条件 |
|---|---|---|---|
| SequenceStatus | `sequence.py:8-11` | 三个枚举值 WAITING、RUNNING、FINISHED | 没有第四个 |
| Sequence.__init__ | `sequence.py:18-31` | 建单:status=WAITING、is_prefill=True、num_cached_tokens=0、block_table=[] | max_tokens=64、ignore_eos=False、temperature=1.0 |
| Scheduler.add | `scheduler.py:22-23` | waiting.append,新客进队尾 | 经理 add_request 调用 |
| Scheduler.schedule 前半 | `scheduler.py:30-55` | 从等位队首起叫号:没桌位的先查拼桌再分桌;一轮吃完整份才换 RUNNING;叫到人就返回 | max_num_seqs=512、max_num_batched_tokens=16384;分批只许队首 |
| Scheduler.schedule 后半 | `scheduler.py:58-73` | 前半一个人都没叫到才进来:逐位查 can_append,不行就请走名单尾;每人 num_scheduled_tokens=1、is_prefill=False | assert 至少叫到一人 |
| Scheduler.preempt | `scheduler.py:75-79` | status=WAITING、is_prefill=True、deallocate、waiting.appendleft | 只被 decode 分支调用 |
| Scheduler.postprocess | `scheduler.py:81-92` | 盖章、num_cached_tokens += num_scheduled_tokens、清零;分批未完的到此为止;其余 append_token 再查结账 | eos 由 tokenizer 填入(`llm_engine.py:33`) |
| BlockManager.can_allocate | `block_manager.py:58-73` | 数拼桌命中(只看前 num_blocks-1 桌);空桌不够回 -1 | 空出但有章的桌算命中但不减新桌数 |
| BlockManager.allocate | `block_manager.py:75-92` | 命中的桌 ref_count+1(空桌则复活),其余从空闲队列取;num_cached_tokens=命中桌数×256 | 要求 block_table 为空 |
| BlockManager.deallocate | `block_manager.py:94-101` | 逆序 ref_count-1,归零的回空闲队列;num_cached_tokens=0、block_table 清空 | 不擦 hash 和 token_ids |
| BlockManager.can_append / may_append | `block_manager.py:103-108` | 长度除以 256 余 1 时需要并分配一张新桌 | 空桌数 ≥ 需要数 |
| Sequence.append_token | `sequence.py:67-70` | token_ids.append、last_token、num_tokens+1 | 只在 postprocess 调用 |
| Sequence.__getstate__ | `sequence.py:72-83` | is_prefill 为真带全部 token_ids,否则只带 last_token | 仅 TP>1 跨进程时用到 |

一位客人需要多少张桌,以及上下一道菜前是否要新桌:

$$\text{num\_blocks}=\left\lceil \frac{\text{num\_tokens}}{256} \right\rceil,\qquad \text{need\_new}=[\,\text{num\_tokens} \bmod 256 = 1\,]$$

## 五、状态与失败分支

五个状态各自的字段签名:

| 图上状态 | status | block_table | is_prefill | 在哪张名单 |
|---|---|---|---|---|
| ①等位 | WAITING | 空 | True | waiting(新客在队尾,被请走的在队首) |
| ②大桌分批上菜中 | WAITING | 非空,num_cached_tokens < num_tokens | True | waiting[0] |
| ③在座 | RUNNING | 非空 | 刚入座那一轮仍为 True,第一次 decode 叫号时变 False | running |
| 请离席(瞬时) | RUNNING 改回 WAITING | 清空 | 改回 True | 从 running 移到 waiting 队首 |
| ④结账 | FINISHED | 清空 | 保持 | 都不在 |

状态牌和新客标记的全部赋值点,以及两个计数在各条边上的变化:

| 字段 | 赋值点 | 值与时机 |
|---|---|---|
| status | `sequence.py:20` | WAITING,建单 |
| status | `scheduler.py:49` | RUNNING,整份 prompt 在本轮吃完 |
| status | `scheduler.py:76` | WAITING,请离席 |
| status | `scheduler.py:90` | FINISHED,结账 |
| is_prefill | `sequence.py:27` | True,建单 |
| is_prefill | `scheduler.py:68` | False,decode 叫号 |
| is_prefill | `scheduler.py:77` | True,请离席 |

| 边 | num_cached_tokens | num_scheduled_tokens |
|---|---|---|
| ①→②、①→③ 分桌时 | = 命中桌数 × 256 | = min(还没算的 token 数, 本轮剩余预算) |
| ② 下一段、②→③ | 不变;出菜后 += 本轮数 | = min(num_tokens − num_cached_tokens, 剩余预算) |
| ③ 每轮 decode | 出菜后 += 1 | = 1 |
| ③→请离席→① | = 0 | 不变,此时已是 0 |
| ③→④ | = 0,deallocate | 已在出菜后清零 |

结账条件只在 append_token 之后查:出了 eos 且 ignore_eos 为假,或生成数正好等于 max_tokens,两者任一成立。ignore_eos 只关掉前者,max_tokens 永远有效。分批上菜中途的轮次连 append_token 都不做,自然也不会结账(`scheduler.py:86-90`)。

谁会被请离席:preempt 只有两个调用点,都在 decode 分支里,取的都是 running 名单里的人,先是名单尾,名单空了才是正在查的这一位。分批上菜中的客人在 waiting 里,并且只要他在队首,prefill 分支必定叫到他并提前返回,decode 分支根本进不去,所以他永远不会被请走。反过来,刚入座还没上过第二道菜的客人(is_prefill 仍为 True)是可以被请走的,示例里的 B 就是(`scheduler.py:54-55,60-65`)。

代码里没有的分支:没有取消、没有超时、没有出错状态;拼桌查询回 -1 的客人只是留在等位队首再等一轮,并且挡住后面所有人。一个没兜住的角落:在座名单只剩一位客人,他要新桌又没空桌时会请走自己,随后断言失败;这要求单条序列超过全部桌位容量,默认配置下桌位远多于 max_model_len,一般碰不到(`scheduler.py:63-65,71`)。

## 六、持有什么,不持有什么

| 字段 | 谁写 | 谁读 |
|---|---|---|
| status | 客人建单;之后只有领班改(`scheduler.py:49,76,90`) | 经理按 is_finished 收结果(`llm_engine.py:54`) |
| is_prefill | 客人建单;领班改(`scheduler.py:68,77`) | 客人自己的 __getstate__(`sequence.py:73`) |
| block_table | 只有座位管理员增删(`block_manager.py:89,91,101,108`) | 领班判断有没有桌位;厨房算槽位(`model_runner.py:151-161,181`) |
| num_cached_tokens | 座位管理员分桌、收桌;领班出菜后累加(`block_manager.py:92,100`,`scheduler.py:84`) | 领班算还剩多少要算;厨房定 prefill 起点(`model_runner.py:139`) |
| num_scheduled_tokens | 领班每轮填、出菜后清零(`scheduler.py:46,67,85`);厨房试做时也填(`model_runner.py:99`) | 厨房定本轮长度(`model_runner.py:140`) |
| token_ids | 客人自己 append_token(`sequence.py:67-70`) | 座位管理员切块盖章;厨房取输入 |

客人持有自己的 token 历史、状态牌、桌号单和几个计数;不持有桌上的 K/V(在厨房的大张量里)、不持有名单(领班的)、不持有桌位的引用计数和哈希索引(座位管理员的)。请离席时被拿走的正是「别人持有、只登记在他名下」的那部分:桌号单和桌上的菜;他自己持有的 token 历史原样留下。

## 七、设计取舍

**为什么只有三个枚举值**。领班真正需要区分的只有「在哪张名单」:waiting、running、都不在。「分批上菜中」「刚入座还没 decode」「被请走过」都能从 block_table、is_prefill、num_tokens 与 num_prompt_tokens 之差推出来,不值得多一个枚举值。代价是读代码的人要同时看两三个字段才知道客人处在哪个细分状态,而且一位被请走的客人和新客在状态上无法区分,只能靠他在队首的位置。

**为什么回到队首而不是队尾**。被请走的客人已经花过算力,排到队首意味着一有空桌他就是第一个回座的,不会被后来的新客插队饿死;同时在座名单里的人都比等位名单里的人先到,先来先服务的次序没有被打乱。代价是队首堵车:他要不到桌位时,后面所有等位的人也进不来,只能等在座客人结账放桌。

**为什么重算而不是保存进度**。请离席只做三件事:改状态牌、收桌位、排队首;K/V 直接丢,不往 CPU 内存搬。省掉的是一整套换出换入的缓冲区和拷贝逻辑,换来的是最坏情况整条序列重算一遍。两个细节把代价压低:一是请走的是最晚入座的那位,他通常生成得最少,丢掉的最少;二是收桌位不擦哈希,回座时只要旧桌没被别人重置,拼桌查询就能把它们原样复活,示例里 C 回座只重算了 1 个 token。

## 八、面试考点串联

- 「nano-vllm 的请求有哪些状态?」三个枚举值,加两个靠字段推出的细分:WAITING 有没有 block_table、RUNNING 有没有 decode 过。
- 「preempt 怎么做的,丢了什么?」改回 WAITING、is_prefill 置 True、桌位逐张减引用、num_cached_tokens 归零、排到等位队首;token_ids 不丢,K/V 全丢,回来重算。
- 「谁会被抢?」只有 running 名单里的人,先抢最晚入座的;分批上菜中的客人在 waiting 里,decode 分支进不去,永远不会被抢。
- 「preempt 之后 prefix cache 还有用吗?」有,deallocate 不擦哈希,can_allocate 能命中空出但没重置的桌并把它复活;但这些桌仍按「新桌」计入空桌需求。
- 「eos 和 max_tokens 谁说了算?」每次 append_token 后一起查,任一成立就结账;ignore_eos 只屏蔽 eos。
- 「is_prefill 除了标记 prefill 还管什么?」跨进程序列化时决定带全部 token_ids 还是只带最后一个 token。
