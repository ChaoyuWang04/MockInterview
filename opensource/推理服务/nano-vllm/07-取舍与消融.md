# 07 取舍与消融:没有这一层会怎样?

> 时间尺度:无,这是全项目的取舍总表  |  源码基准见总览

前面六页各自讲了「它是怎么做的」,这一页换个问法:**把某一层拿掉,你得自己写什么、系统会坏在哪、留下它又付了什么代价、nano-vllm 用了几行把它写完。** 一个机制值不值得存在,用这三问就能定义清楚。行数按函数级的行号范围数,出处都在各页的证据表里。

## 一、消融表

| 机制 | 讲它的页 | 没有它,你要怎么写,或者会怎样 | 有了它,付出什么代价 | nano-vllm 用几行,在哪 |
|---|---|---|---|---|
| 领班的 step 循环与二选一批次 | 01、02 | 一次只服务一位客人,或者自己写批处理循环;GPU 大半时间在等 Python | 一轮只能纯 prefill 或纯 decode;有新客就让在座的等一轮 | schedule 49 行、postprocess 12 行,`scheduler.py:25-73, 81-92`;step 7 行,`llm_engine.py:49-55` |
| 桌位制:block_table 与槽位映射 | 04、05 | 每位客人按单条上限 4096 预留一段连续 K/V,大半空着,同时在座人数骤减;这正是 PagedAttention 论文要解决的问题 | 间接寻址;每轮算槽位;最后一桌平均空半桌;注意力核必须支持桌位表 | Block 与 BlockManager 95 行,`block_manager.py:26-120`;槽位算式约 25 行,`model_runner.py:123-127, 151-161, 181` |

把最后一列加起来不到 400 行,却撑起了全部调度语义;剩下的一千行是模型结构与算子。这就是总览那句话的来源:nano-vllm 不是一个模型,是一台调度机器。

表里有一条隐藏的连锁反应值得单独说:因为最后一桌永远不参与拼桌,共享的桌永远是写满的整桌,之后不会再被任何人写,所以整个项目不需要 copy-on-write。一条看似保守的判定规则,省掉了一整套写时复制的机制,04 页的证据表给出了证明链。

## 二、两段裸写法对比

下面左边是「没有这一层」时的写法,示意用,不来自任何仓库;右边是 nano-vllm 的真实结构。

**没有领班,逐条生成:**

```python
for prompt in prompts:                      # 一位客人一位客人来
    ids = tokenizer.encode(prompt)
    for _ in range(max_tokens):
        logits = model(ids)                 # 每次都重算整段,或者自己管 past_key_values
        ids.append(sample(logits[-1]))
```

**nano-vllm,一批一批算,K/V 落在桌位上(`llm_engine.py:49-55, 73-75`):**

```python
while not scheduler.is_finished():
    seqs, is_prefill = scheduler.schedule()             # 领班:谁上、算多少
    token_ids = runner.call("run", seqs, is_prefill)    # 厨房:一次前向服务整批
    scheduler.postprocess(seqs, token_ids, is_prefill)  # 领班:写回、结账、退桌
```

**没有桌位制,每人预留一段连续 K/V:**

```python
kv = torch.empty(num_seqs, max_model_len, ...)   # 4096 格,常常只用几百格
kv[i, t] = new_kv                                # 位置就是 token 序号
```

**nano-vllm,按需领桌,槽位是桌号乘 256 加桌内偏移(`block_manager.py:106-108`,`model_runner.py:181`):**

```python
if len(seq) % block_size == 1:                                   # 这桌坐满了
    seq.block_table.append(block_manager._allocate_block())      # 再开一桌
slot = seq.block_table[-1] * block_size + seq.last_block_num_tokens - 1
```

## 三、nano-vllm 里没有的东西

这些都是代码事实,也正是读 vLLM 时要在总图上标成外围、留到后面再拆的区域:

- **没有 API 服务与异步引擎**:入口只有 `generate`,同步单线程,一位客人没结账所有人的结果都不返回,`llm_engine.py:60-90`。
- **没有 KV 换出**:请离席只退桌重算,`engine/` 里没有任何 CPU 缓冲区,`scheduler.py:75-79`。
- **没有混合批**:一轮纯 prefill 或纯 decode,`scheduler.py:54-58`。
- **没有 LRU**:空闲队列先进先出,最早退的桌最先被重置,`block_manager.py:44, 56`。
- **采样只有温度**:没有 top-p、top-k,也不允许贪心,`sampling_params.py:5-11`,`layers/sampler.py`。
- **只有 Qwen3 一种结构**:`models/` 下只有 `qwen3.py`。
- **没有投机解码、结构化输出、LoRA、多模态**:`engine/` 与 `layers/` 里没有对应模块。

## 四、面试考点串联

- 「nano-vllm 和直接调 HF generate 的本质区别」→ 不是模型不同,是多了领班、桌位和批次:很多人同时要生成,被翻译成 GPU 每一步算一批。
- 「PagedAttention 解决什么」→ 连续预留的浪费与并发上限;代价是间接寻址与内部碎片,nano-vllm 用 95 行账本加 25 行槽位算式实现。
- 「chunked prefill 与 preempt 各解决什么」→ 前者让长 prompt 排得上,后者让超额接客不崩;两者的代价分别是余量浪费与重算。
- 「CUDA graph 为什么只用于 decode」→ 形状固定才能录;prefill 每轮不同;代价是启动期录 36 张图和分桶补齐。
- 「如果给 nano-vllm 加一个功能先动哪一层」→ 加采样策略动 sampler;加模型结构动 models 与 loader;加混合批要同时动 schedule 与 prepare_prefill;加 KV 换出要动 preempt 与 BlockManager。
