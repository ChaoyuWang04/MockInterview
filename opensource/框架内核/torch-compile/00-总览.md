# torch.compile 总览

源码基准:官方仓库 <https://github.com/pytorch/pytorch>,分支 `main`,commit `217579124a28a51d623935fa5e414a6e93d3488a`,最近的正式发布 tag `v2.14.0`(仓库自报版本 `2.15.0a0`),核对日期 2026-09-23。全篇的「当前」「默认」都指这组基准。torch.compile 不是独立仓库,源码是 pytorch 仓里的 `torch/_dynamo/`、`torch/_functorch/`、`torch/_inductor/` 等几个目录,与 FSDP 解读共用同一个基准。

## 一、torch.compile 是什么

**torch.compile** 是 PyTorch 2 的即时编译栈。它解决的问题只有一个:**eager 模式太碎**——每个算子单独 launch 一次 kernel,中间结果每一步都写回显存再读出来,小算子一多,GPU 大半时间在等 CPU、在搬数据。

它的办法是:**不改用户代码,在 Python 函数执行前把它截下来,把里面的张量操作抓成一张图,连反向也提前抓出来,再交给编译器融合成少量 kernel。** 编译一次,之后同样的输入直接跑编译产物。代价也集中在这里:首次调用要先编译,冷启动明显变慢;编译结果只在一组条件下成立,要靠 guard 判断这次调用能不能复用,不能就重编译。

它由三段接力完成,各管一件事:

- **Dynamo**(`torch._dynamo`):前端,负责抓图。它在字节码层面模拟执行 Python,把张量操作记成一张 FX 图,把「这张图在什么条件下成立」记成 guard;遇到抓不了的调用就把图断开。
- **AOTAutograd**(`torch._functorch`):中段,把前向和反向合成一张联合图,去掉原地修改和别名,再切回前向图和反向图。反向因此也能被编译。
- **Inductor**(`torch._inductor`):默认后端,负责生成代码。它把图分解成少量原语,降到循环级的中间表示,决定哪些算子融进同一个 kernel,在 GPU 上生成 Triton 代码;矩阵乘默认交给现成库,打开调优后才在模板和现成库之间实测挑选。

代码花在哪(解释本体,不含测试):`_inductor` 约 11.6 MB,`_dynamo` 约 5.6 MB(其中建模 Python 语义的 `variables/` 就有 2.5 MB),`_functorch` 约 1.6 MB,C++ 侧的帧拦截与 guard 在 `csrc/dynamo` 约 0.5 MB。**前端的体量主要花在「把 Python 模拟准」上,后端的体量主要花在调度、代码生成与矩阵乘模板上**,这两处就是这份解读的重心。

紧挨着它、但本解读不展开的两块:FSDP、张量并行等分布式实现各有自己的解读,这里只写编译器怎么处理图里的通信;导出(`torch.export`)与 AOTInductor 离线部署另立单元。算子融合、CUDA graph、访存受限与计算受限的分析在知识库各有一篇,这里只写 torch.compile 怎么做。

## 二、6 个招牌:先建立全局图景

```text
                 eager 太碎:每个算子一次 launch,中间结果来回过显存
                                    │
          [1] 帧拦截 + 字节码符号执行:不改代码,把张量操作抓成图
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
   [2] guard                    [3] graph break             [4] 动态形状
   图在什么条件下成立           抓不了的地方断开            形状变了不必每次
   不成立就重编译               前后两段各自成图            都重编译
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    ▼
          [5] AOTAutograd:反向也提前抓,自动决定存哪些激活、重算哪些
                                    │
                                    ▼
          [6] Inductor:分解 → 循环级 IR → 融合 → Triton 与矩阵乘模板
```

一句话记忆:

- **帧拦截与符号执行**:编译发生在函数第一次被调用时,不是装饰的那一刻。抓图时张量换成只带形状、类型和设备的假张量,不真算。
- **guard**:编译产物挂在函数的 code object 上,旁边记着一串检查条件。之后每次调用先在 C++ 里查一遍,全过才复用,否则重编译;同一个函数默认最多存 8 份,满了之后不再编新的,已有的照样命中,对不上的调用走 eager。
- **graph break**:抓图撞上不支持的调用时不会报错,而是把前半段先编成图,那一句交给 eager,后半段当成一个新函数继续抓。代价是图被切碎,融合机会跟着少。
- **动态形状**:默认先按具体形状编译;某一维在两次调用之间变了,重编译时就把这一维换成符号,之后同类变化不再触发重编译。
- **AOTAutograd**:反向在编译期就抓出来,和前向一起优化。前反向怎么切由一个最小割算法决定:哪些中间结果存下来,哪些在反向里重算。
- **Inductor**:默认后端。核心是调度器决定融合,GPU 上生成 Triton,矩阵乘默认直接调 cuBLAS 这类现成库;打开 max-autotune 后,才在现成库、Triton 模板以及可选的 CUTLASS 等候选之间实测挑选(12 章)。

## 三、16 章,各自解决什么

下表是本解读的章表。**这里只回答「它存在是为了解决什么」**;展开讲解在各章,代码在哪见代码索引页。

| 主题 | 不这么做会怎样 | 做法一句话 | 详见 |
|---|---|---|---|
| 一次编译的形状 | 小算子链每个都单独 launch,中间结果来回过显存,GPU 空等 | 首次调用抓图、提反向、生成代码,产物挂在函数上,之后只查 guard | 01 章 |
| 抓图:帧拦截与字节码符号执行 | 靠跟踪一次执行来抓图会漏掉 Python 控制流,抓错了结果静默出错 | 在帧执行前截下,逐条模拟字节码;张量换成只传形状的假张量 | 02 章 |
| Python 语义建模与副作用 | 改字典、闭包、模块属性这类副作用漏记,编译后结果和 eager 不一致 | 每种 Python 对象有一个追踪类,副作用记下来,图跑完再重放 | 03 章 |
| guard 与重编译 | 每次调用的检查开销压过收益;条件一变就重编译,撞上限后新条件下的调用静默走 eager | 抓图时记下成立条件,编成 C++ 里的检查树,只查真正用到的东西 | 04 章 |
| graph break 与续跑 | 一处不支持的调用把图打碎,融合机会没了,还多出来回切换 | 前半段成图,这一句交给 eager,后半段生成续跑函数接着抓 | 05 章 |
| 动态形状 | 变长输入每换一次长度就重编译一次;数据依赖的形状直接断图 | 维度用符号表示,按需特化;晃动过的维自动转成动态 | 06 章 |
| AOTAutograd:联合图与函数化 | 反向不进图只能加速一半;原地修改与别名不处理,编译器不敢融合 | 前反向合成一张联合图,去掉原地修改,张量子类展开成普通张量 | 07 章 |
| 前反向切分与重计算 | 前向存的激活太多显存爆,存得太少反向重算太多 | 用最小割在「存」与「重算」之间自动取舍 | 08 章 |
| Inductor 前端:分解与 lowering | 算子太多,不可能每个都写 kernel,覆盖不全就只能回退 | 先分解成少量原语,再降到循环级中间表示,途中跑模式替换 | 09 章 |
| 调度与融合 | 访存受限的算子链不融合,每一步都读写一次显存 | 调度器按读写依赖决定哪些节点融进同一个 kernel,并重排以压峰值显存 | 10 章 |
| Triton 代码生成与调优 | 融合了但块大小不合形状,kernel 照样跑不快 | 按融合结果生成 Triton,块大小靠启发式加运行时调优 | 11 章 |
| 矩阵乘模板与 max-autotune | 矩阵乘走不进最优实现;调优一开编译时间明显拉长 | 在现成库与多种模板之间实测挑选,并把后续逐元素运算融进模板 | 12 章 |
| CUDA Graph Trees | 小批量下 CPU launch 开销主导;多张图各占一份内存池,显存翻倍 | 编译产物录成 CUDA graph 回放,多张图共用一个内存池 | 13 章 |
| 算子扩展:自定义算子、用户 Triton kernel 与 FlexAttention | 自己写的 kernel 进不了图,整段断开;注意力变体只能手写 | 注册成编译器看得懂的算子或高阶算子;注意力变体用打分函数描述,由模板生成 | 14 章 |
| 分布式:通信重排与计算重叠 | 编译后的图里集合通信和计算串行,算力空等 | 通信进图后拆成发出与等待两个节点,默认做保守的相邻交换让它和计算重叠;分桶与按估时重排要显式打开 | 15 章 |
| 编译耗时:缓存与预编译 | 冷启动每次都要重新编译,多机作业每台都重复一遍 | 多级缓存按图的哈希复用,编译并行化,还能提前编好整段打包 | 16 章 |

## 四、一次调用怎么串起来

![两行流程图:上面一行是首次调用,依次经过帧拦截、字节码符号执行、AOTAutograd、Inductor,最后把编译产物和 guard 挂到函数的 code object 上并写进磁盘缓存,符号执行遇到不支持的调用会发生 graph break;下面一行是之后的调用,先做 guard 检查,命中就直接跑编译产物,没命中就回到上面一行重新编译,同一函数最多保留 8 份](/opensource/torch-compile/00a-first-call-and-later-calls.svg)

**首次调用**:函数的 Python 帧在执行前被截下。Dynamo 不让解释器直接跑,而是自己逐条模拟字节码:碰到张量操作就记进 FX 图,碰到 Python 对象就用追踪类记下它的状态和副作用,同时把用到的每个前提(输入的类型与形状、读过的全局变量、模块属性)记成 guard。图抓完交给后端:AOTAutograd 把前向和反向合成联合图、去掉原地修改,再切成前向图和反向图;Inductor 把两张图各自分解、降级、调度融合、生成代码。最后,编译产物连同 guard 挂到这个函数的 code object 上,AOTAutograd 与 Inductor 的产物同时进磁盘缓存,下次进程启动可以直接取;Dynamo 抓图本身不缓存,每次启动都要重抓(16 章)。

**之后的调用**:帧同样先被截下,但这次只查 guard。检查在 C++ 里做,全部通过就直接跑编译产物;如果开了 CUDA graph,整段 kernel 按录好的顺序一次回放。任何一条不通过就重新编译一份,同一个函数默认最多存 8 份(准确计法见 01 章)。

**graph break**:抓图途中撞上不支持的调用(比如打印、调用无法追踪的第三方库、依赖张量数值的分支),Dynamo 把已经抓到的前半段编成图,那一句交给 eager 执行,再把函数剩下的部分包成一个续跑函数,续跑函数被调用时同样会被截下来接着抓。结果仍然正确,但一个函数变成了几张小图,中间夹着 eager 执行。

**显存**:编译本身不改变模型需要什么数据,但会改变两件事。一是前反向切分决定前向存下哪些激活,默认的最小割会在显存和重算之间取舍,和手写的重计算叠在一起时要看清楚是谁在起作用;二是开了 CUDA graph 之后,输入输出缓冲会被池化常驻。展开见 08 与 13 章。

## 六、怎么调它、怎么看它

各章「调参与观测」只写自己的参数,入口在这里说一次。

**先让图完整,再谈调优。** graph break 和重编译不解决,换什么模式都白调:图是碎的,融合就是碎的。

| 旋钮 | 长什么样 | 什么时候改 |
|---|---|---|
| `mode` | `default`;`reduce-overhead` 打开 CUDA graph;`max-autotune` 打开矩阵乘调优、坐标下降调优与 CUDA graph;`max-autotune-no-cudagraphs` 同上但不开 CUDA graph | 小批量、CPU 开销主导时试 `reduce-overhead`;矩阵乘占大头且能接受更长编译时再上 `max-autotune` |
| `fullgraph` | 默认 `False`;设成 `True` 后一有 graph break 就报错 | 想确认整个函数成一张图时打开 |
| `dynamic` 与 `mark_dynamic` | 默认 `None`,先按静态编,形状晃了再转动态;`True` 一开始就尽量动态;`False` 永远特化 | 输入长度一直在变时,提前把那一维标成动态 |
| `recompile_limit` | 同一函数最多几份编译结果,默认 8 | 重编译撞上限、性能突然掉回 eager 时,先查为什么重编,不要先调大 |
| `backend` | 默认 `inductor`;可换成调试后端或自注册后端 | 排查是抓图的问题还是代码生成的问题时,换成只抓图不编译的后端 |
| `options` | 透传给 Inductor 的配置 | 按章查;常用的见 10–13 章 |

**观测的三处**:图是不是碎了,开 `TORCH_LOGS=graph_breaks` 看每一处断图的原因;为什么重编译,开 `TORCH_LOGS=recompiles`(想看 guard 全文用 `guards`);生成了什么代码,开 `TORCH_LOGS=output_code`。动态形状的特化过程用 `TORCH_LOGS=dynamic`。整个编译过程的结构化日志可以交给 tlparse 汇总成网页。

## 七、阅读顺序

主干是 01 → 02 → 04 → 05 → 07 → 10,读完就抓住了主线:怎么抓图、什么时候复用、为什么会断、反向怎么进来、融合怎么发生。

然后按你撞到的问题读:重编译多读 06;显存比 eager 还高读 08 与 13;模型里有自己写的 kernel 或注意力变体读 14;多卡训练里编译后没变快读 15;启动太慢读 16。03、09、11、12 是前后端的内部细节,想看清某一段为什么这样生成时再读。

**怎么读**:本解读**不讲算子融合、CUDA graph 这些概念本身,也不重讲 torch.compile 的整体原理**,知识库里各有一篇,这里只写 torch.compile 怎么把它们落地、和其他做法差在哪、怎么调。每一章都是短页:核心问题、解法、代价、和同类大厂框架不一样的地方、调参与观测、常见误区。哪一句想展开,在对话里问。

和推理引擎解读的分工:vLLM、sglang 都用 torch.compile 编译模型的一部分,那边只写「它们怎么调用编译、怎么切图、怎么配 CUDA graph」;编译器内部发生了什么在这里。和 FSDP 的分工同理:FSDP 那边写它怎么和编译共存,编译器怎么重排图里的通信在 15 章。

## 八、术语表

| 术语 | 一句话 |
|---|---|
| 帧 | Python 执行一个函数时的运行现场,Dynamo 在它执行前截下 |
| code object | 函数编译后的字节码对象,编译产物和 guard 挂在它上面 |
| FX 图 | PyTorch 用来表示一串张量操作的图结构,是各段之间传递的格式 |
| guard | 一份编译产物成立的前提条件,每次调用前检查 |
| 重编译 | guard 没通过时重新编一份,与旧的并存 |
| graph break | 抓图撞上不支持的调用时把图断开,中间那句交给 eager |
| 续跑函数 | graph break 之后,函数剩余部分被包成的新函数 |
| 假张量 | 只带形状、类型、设备的张量,抓图时代替真张量 |
| 符号形状 | 用符号代替具体数字的维度,让一份编译结果适配多种长度 |
| 联合图 | 前向和反向合在一起的一张图 |
| 函数化 | 把原地修改改写成无副作用的等价形式 |
| lowering | 把图里的算子降成 Inductor 的循环级中间表示 |
| 模板 | 预先写好的矩阵乘或注意力 kernel 骨架,由调优挑参数 |
| CUDA graph | 把一串 kernel launch 录下来整段回放,省掉 CPU 开销 |
