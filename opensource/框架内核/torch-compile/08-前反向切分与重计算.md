# 前反向切分与重计算

这一页回答一件事:联合图拆回前向图与反向图时,前向该把哪些张量交给反向、哪些留到反向里重算,这个取舍由谁、按什么标准来做。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

07 章录出的联合图是一张图,运行时却必须拆成两次调用:前向在这一步的开头跑,反向要等 loss 算完、用户调了反向才跑。前向留给反向的张量,也就是激活,从被算出来的那一刻一直占着显存,直到反向用完。知识库《显存管理与OOM》讲过,激活是随微批和序列长度一起涨的那一项;切在哪,决定了这一项有多大。

两头都会骨折。**照 eager 的习惯切**,每个算子各存各的求导所需,长序列、大微批下显存先爆。**只存输入,反向把整段前向重跑一遍**,显存最省,可矩阵乘、注意力也跟着重来,每一步都慢一截。

编译让这件事更敏感。Inductor 会把一串逐元素运算融成一个 kernel(10 章),中间值原本根本不落显存;切分一旦决定把其中某个中间值存下,就等于逼它多写出去一次、反向再读回来一次。反过来,在反向里重算一个逐元素运算,可以融进反向本来就要跑的那个 kernel,几乎不花什么。

还有第三方:用户可能早就在模型里手写了激活重计算,或者用策略逐个算子指定存还是算。编译器自己的取舍和用户的标注叠在一起时,必须说得清谁说了算。

所以这一章的问题是:**联合图从哪里切开,前向交给反向的张量集合怎么选,显存、读写与重算之间怎么换,用户的标注又怎么参与。**

## 二、解法

最天然的直觉是只存「贵的」、便宜的都重算。torch.compile 的默认切分器把这句话翻译成了一个图上的最小割问题。

![一张小联合图上的最小割:用户代码先做矩阵乘 h = x·W,再算 y = h·sigmoid(h);割线把前向和反向隔开,被切断的是输入 x 与矩阵乘结果 h 两条边,这两个张量存下交给反向,参数 W 存它不计代价;sigmoid 的结果 σ 不跨割线,在反向里用 h 重算,紧挨着乘法的反向与 sigmoid 的反向;图旁注明存 σ 要多写一次、占显存到反向、再读一次,而重算 σ 只是在反向本来就读 h 的 kernel 里多做几次算术](/opensource/torch-compile/08a-min-cut-save-or-recompute.svg)

**把「存」变成一条边的容量。** 联合图里每个前向节点拆成入口和出口两个点,中间连一条边,容量是这个张量的字节数;节点之间的数据依赖连容量无穷的边。一个虚拟源点接到前向输入上,一个虚拟汇点接到反向需要的东西上。求源点到汇点的最小割:被割断的节点边,就是前向要存下的张量;割线另一侧、又被反向用到的前向节点,在反向图里重算。割的总容量就是存下的字节数,最小割就是存得最少的那个方案。

**权重不只是字节数。** 参数默认按零代价计,它本来就常驻显存,存它不多花什么。在前向里本来会被融合掉、不落显存的中间值,权重翻倍,因为存它意味着多写一次。离反向越远的张量权重越大,每远一步乘 1.1,最多按 100 步算,源码注释自己称这个系数是猜的:存得越早,占得越久。

**谁能重算,靠禁令决定。** 权重里没有计算量这一项:切分器的前提是「允许重算的算子,在反向里重算是免费的」。为了让这个前提成立,默认只放行一张白名单:逐元素运算、视图、类型转换、一部分求和求均值这类归约、索引。矩阵乘、卷积、注意力、随机算子都不在名单上,源点到它们连一条无穷边,只能存。名单之外还有几条禁令:输出比输入小 4 倍以上的,存结果更划算,不许重算;在反向里要被矩阵乘这种融不进去的算子用到的,重算完还得写出去,不再免费,不许重算;同一个值既被近处用、又隔着一个融不进去的算子被远处用,远处那一支不许重算,因为两处重算很难再融到一起;一条可融合的逐元素长链延伸超过 100 个节点,就在那里强制存一次,免得反向从头重算一长串。结果就是那句直觉:矩阵乘的结果存下,它后面的逐元素运算宁可在反向里重算。

**有几类东西永远存。** 集合通信的结果强制存,不重算:每张卡独立编译,若一张卡重算了通信而另一张没有,两边就会互相等死。带副作用的算子强制存;前向和反向都原地改同一个输入时,前向写进去的那个值也强制存,免得重算时写两遍。

**显存预算:在默认和全重算之间插值。** 默认切法以速度为目标,只省那些「免费」的。显存还不够时,可以给一个 0 到 1 的预算:0 表示只存输入,相当于整段做激活重计算;1 表示默认切法;中间按两者的激活量线性插值。求解分三步。先把几条启发式禁令放开再割一次,够低就用;再把白名单也放开,只留随机算子、计算密集算子这类黑名单再割一次,够低就用;还不够,就把仍被禁止重算的节点当成 0-1 背包:每个节点的重量是它的字节数,价值是估出来的重算时间,默认按 FLOPs 估,在预算内挑出重算代价最小的一组放开禁令,最后再割一次。背包默认用把显存量化成 10000 格的动态规划求解。预算可以全局设,也可以在编译区域里用一个上下文只给这张图设。

**用户的标注写进同一张图。** 在编译区域里调用激活重计算,Dynamo 把被包住的函数抓成一个高阶算子(03 章讲过它里面的副作用默认断图);AOTAutograd 展开它时,区域里的每个算子都被打上「优先重算」的标签。用了选择性激活重计算,策略函数会给每个算子返回四种之一:必须存、优先存、必须重算、优先重算。切分器照这些标签建图:两种重算都连一条到汇点的无穷边,强制在反向里重算,连矩阵乘也不例外;必须存等同于禁止重算;优先存不加任何约束,交给最小割决定。两个相邻的重计算区域首尾相接时,交界处的张量强制存下,否则后一段要从前一段的开头重算起。于是分工很清楚:标注过的区域用户说了算,其余部分最小割说了算。

**重算的随机算子要重放同一个随机数。** 用户区域里的 dropout 在反向里被重算,必须和前向抽到一样的掩码。Inductor 在切分之前就把随机算子改写成由显式种子驱动的版本,复制到反向的那份拿到的是同一个种子;其他后端由切分器把这类算子包成「先存随机状态再跑」与「用存下的状态再跑」一对,把随机状态从前向图传给反向图。

**另一条路:卸到主机内存。** 切完之后还有一步可选的改写:对被标记的保存张量,在前向里它最后一次被用到之后插一次拷到主机的操作,在反向里第一次用到它之前插一次拷回;可以放到独立的流上,并按设定的主机到显卡带宽估算传输时间,提前把拷回挪到前面,和计算重叠。视图、非连续张量、参数和模型输出不卸。这一步默认关,配置注释写明是测试用途;哪些张量要卸,也得用户自己在联合图上用一段自定义 pass 标记,仓库里没有自动挑选的逻辑。

**为什么实际不吃亏。** 切分只在编译时做一次。默认预算下,被重算的全是逐元素运算和视图,它们在反向里和本来就要跑的逐元素运算融在一起,多出来的是几条算术指令,少掉的是一次写和一次读;配置注释的说法是它应当总比 eager 省显存。AOTAutograd 自带另一个切分器,照 eager 的样子把前向里被反向用到的全部存下;Inductor 与调试用的 AOTAutograd 后端都换成了最小割切分器。

## 三、代价

**「重算免费」是个假设,由启发式兜着。** 最小割只数字节,重算的算量完全不进目标函数;它靠白名单和几条禁令保证放行的都是便宜算子。那几条禁令的阈值,源码注释自己写着是随手定的:输出小 4 倍、长链 100 个节点、每步 1.1 倍;其中一条注释说自己是三条里最可疑的。遇到模型结构和这些经验不合,切出来的方案可能存多了,也可能在反向里多算了。

**默认追求速度,不追求显存。** 默认预算下,矩阵乘和注意力的结果一律存下,只省逐元素那部分。大模型长序列训练里,光这些存下的结果就可能放不下,这时要么调小预算,要么在模型里手写重计算。

**预算越小,编译越慢。** 预算小于 1 时,最坏要多割 3 次,再解一次背包;把重算时间估法换成实测,还要在编译期逐个跑算子基准。

**一张图只能有一个预算。** 编译区域里的预算上下文必须一致,不一致直接报错;默认还要求它覆盖整张图的前向。想给模型的不同部分不同预算,只能用断图把它们分成不同的图,而断图本身又打碎了融合(05 章)。

**用户区域里的矩阵乘也会被重算。** 普通的激活重计算不告诉编译器哪些值贵,整个区域都被标成「优先重算」,切分器把它当强制执行,区域里的矩阵乘、注意力全在反向里再做一遍。想保住它们,要改用选择性激活重计算显式列出来。

**编译下的激活重计算和 eager 不完全一样。** eager 的反向是把 Python 函数再调一遍,编译后是把 ATen 算子复制进反向图;前向里的 Python 副作用因此默认断图(03 章)。带策略函数的区域里不能有原地算子,编译时会打一条警告提醒。

**多卡上切分决定可能不一致。** 每张卡各自编译,尺寸提示不同时,最小割可能在两张卡上给出不同的保存集合。有一个临时配置可以让各卡在切分前对齐决定,默认关。

**卸载是实验功能。** 同步的拷贝会让计算等传输;异步版要自己设带宽估计才能排好预取;挑选也全靠自己。

## 四、和同类大厂框架不一样的地方

对照对象是 JAX 的激活重计算(按 docs.jax.dev 当前文档核对)与 Megatron-LM 的激活重计算(基准 fb6a123a09)。两者都在大规模训练里用:前者由用户写策略决定存什么,后者由用户按模块勾选,正好衬出 torch.compile 默认交给编译器来挑。

| 各家都要回答的事 | torch.compile 的切分器 | JAX | Megatron-LM |
|---|---|---|---|
| 什么都不标时存什么 | 按字节求最小割:矩阵乘结果存,逐元素运算在反向里重算 | 自动求导在前向尽量算完并存下;放进即时编译后,由 XLA 自己决定哪些值重算 | 不开重计算就全部存下 |
| 用户怎么指定重算范围 | 包一段函数整段重算,或给策略逐个 ATen 算子指定存还是算;还能只给一个显存预算,让编译器自己挑 | 给子函数套上重计算变换,整段只存输入;或给它一个策略,按原语判断能不能存,比如只存没有 batch 维的矩阵乘结果,也能按用户给中间值起的名字选 | 按模块名选:完整模式以层为单位整段重算,要么把各层按固定层数均匀分组、每组只存入口,要么只重算每个流水段的前若干层;选择性模式只重算列出的子模块,默认只有 core attention |
| 卸到主机内存 | 默认关的实验功能,要自己在图上标 | 策略可以把指定名字的值或无 batch 维的矩阵乘结果卸到主机的固定内存 | 有 CPU 卸载,但和激活重计算不能同时开,配置校验直接报错 |

一句话:JAX 与 Megatron 都把「存什么」交给用户,前者给了一套按原语与名字写的策略语言,后者给了一张按模块名勾选的清单;torch.compile 把默认决定交给编译器按字节求最小割,用户的标注只在自己包住的区域里压过它。好处是用户什么都不标也能省下一部分显存,代价是想知道某个张量到底存没存,得去看切分后的图。

## 五、调参与观测

这一章的参数分四处:`torch._functorch.config` 里的全局配置,对之后发生的编译生效;模型代码里的标注(激活重计算的包法、区域预算上下文),改了代码要重新抓图;`torch._inductor.config.custom_partitioner_fn` 整个替换切分器;调试用的环境变量,要在导入 torch 之前设好。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `activation_memory_budget` | `torch._functorch.config` | `1.0` | 调小:存得更少、重算更多;`0` 只存输入 | `AOT_PARTITIONER_DEBUG=1` 时的 `Theoretical Activations Stored` |
| `torch.autograd.graph.region_activation_memory_budget(b)` | 编译区域里的上下文管理器,原型接口 | 不用则取全局值 | 只作用于这张图,覆盖全局值;在 eager 下调用直接报错 | 同一张图里值不一致时报 `conflicting budgets` |
| `activation_memory_budget_require_full_coverage` | `torch._functorch.config` | `True` | `False`:区域没包住整张图的前向也生效,预算作用于整张图 | 未覆盖时报错并列出没被包住的算子 |
| `activation_memory_budget_runtime_estimator` | 同上 | `"flops"` | `"profile"`:逐个算子实测,估得更准,编译更慢 | — |
| `activation_memory_budget_solver` | 同上 | `"dp"` | `"greedy"` 更快更粗;`"ilp"` 要装 scipy;`"dp_knapsack_sliding_hirschberg"` 省求解内存;`"dynamic_memory_budget_dp"` 实验性,自己找拐点 | — |
| `PARTITIONER_MEMORY_BUDGET_PARETO` | 环境变量 | 未设 | 设成 `1`:把 0 到 1 各预算下的「激活量–重算时间」曲线画成 SVG,需要 matplotlib | 目录由 `PARTITIONER_MEMORY_BUDGET_PARETO_DIR` 指定,默认当前目录 |
| `aggressive_recomputation` | `torch._functorch.config` | `False` | `True`:除了「归约不重算」以外的禁令全关,白名单换成黑名单;显存更省,反向更慢 | 调试日志里的 `# remat/fw/bw` |
| `ban_recompute_not_in_allowlist` | 同上 | `True` | `False`:只禁随机、矩阵乘这类计算密集算子与非内置算子,排序、池化这类也允许重算 | 同上 |
| `ban_recompute_reductions` | 同上 | `True` | `False`:允许重算输出比输入小 4 倍以上的归约 | 同上 |
| `recompute_views` | 同上 | `False` | `True`:视图永远不存,一律重算 | — |
| `treat_parameters_as_free_to_save` | 同上 | `True` | `False`:参数也按字节计入割的代价 | — |
| `enable_activation_offloading` | 同上 | `False` | `True`:对切分后被标了 `should_offload` 的保存张量插入卸载与拷回;标记要靠 `joint_custom_pass` | 前向图里出现 `cpu_offload_` 开头的节点 |
| `activation_offload_separate_stream`、`activation_reload_prefetch`、`activation_offload_cpu_gpu_bw` | 同上 | `False`、`False`、`50.0`(GB/s) | 独立流上异步传输;按带宽估计把拷回提前 | 反向图里拷回节点的位置 |
| `joint_custom_pass` | 同上 | `None` | 在切分前拿到联合图,可以改节点的标记 | — |
| `custom_partitioner_fn` | `torch._inductor.config` | `None` | 换掉最小割切分器,Inductor 的联合图 pass 照跑 | — |
| `backend="aot_eager_default_partitioner"` | `torch.compile` | — | 用照 eager 切的默认切分器、不做代码生成,和 `aot_eager` 对照看最小割省了多少 | 两者的前向图输出个数 |
| `AOT_PARTITIONER_DEBUG` | 环境变量 | 未设 | 设成 `1`:切分器打印存了多少、重算了哪些算子,并往 tlparse 写 `min_cut_information` | 配 `TORCH_LOGS=torch._functorch.partitioners` 才能看到 |

用户侧的激活重计算接口:`torch.utils.checkpoint.checkpoint(fn, *args, use_reentrant=False, context_fn=...)`;`context_fn` 用 `functools.partial(create_selective_checkpoint_contexts, policy_fn 或算子列表)` 构造。列表里的算子按 `CheckpointPolicy.MUST_SAVE` 处理,其余按 `PREFER_RECOMPUTE`。

**观测三处。** 看切分结果:`TORCH_LOGS=aot_graphs` 打出切分后的前向与反向图,前向图返回值里排在用户输出之后的那些张量就是交给反向的,反向图开头的逐元素算子就是重算的。看数字:`AOT_PARTITIONER_DEBUG=1` 加 `TORCH_LOGS=torch._functorch.partitioners`,每张图打出 `Theoretical Activations Stored`(按假张量估的保存总量)、按大小排好的每个保存张量、`# remat/fw/bw`(重算节点数、前向与反向节点数)、`Count of Ops Rematerialized`,以及被禁止重算的算子清单。看预算的取舍:`PARTITIONER_MEMORY_BUDGET_PARETO=1` 画出整条曲线,再决定预算设在哪。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 显存够用,只要速度 | 什么都不改,默认预算 `1.0`;先用 `AOT_PARTITIONER_DEBUG=1` 看一眼存了多少 | 只省逐元素那部分激活,不多花计算 |
| 显存紧张,不想改模型代码 | `torch._functorch.config.activation_memory_budget = 0.5`,再用 `PARTITIONER_MEMORY_BUDGET_PARETO=1` 看曲线微调 | 激活量落在默认与整段重算的正中间;用按 FLOPs 估出的最少重算换显存,编译时间变长 |
| Transformer 训练,已按层包了激活重计算 | 每层 `checkpoint(block, x, use_reentrant=False, context_fn=functools.partial(create_selective_checkpoint_contexts, [torch.ops.aten.mm.default, torch.ops.aten._scaled_dot_product_flash_attention.default]))` | 保住矩阵乘与注意力的结果,只重算逐元素与归一化;显存比整层重算多,反向少算一遍矩阵乘 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 编译后仍然 OOM,或显存比预期高 | `Theoretical Activations Stored` 与前向图的输出个数,大头是不是矩阵乘结果 | 调小 `activation_memory_budget`,或在模型里包激活重计算 |
| 编译后反向明显变慢 | `# remat/fw/bw` 与 `Count of Ops Rematerialized` 里有没有 `mm`、注意力 | 多半是整层激活重计算区域把矩阵乘也重算了:改用选择性策略把它们列成必须存,或调大预算 |
| 调了预算,保存量没变 | 后端是不是 Inductor 或 `aot_eager`;是否设了 `custom_partitioner_fn`;调试日志里被禁止重算的节点是不是空的 | 预算只在最小割切分器里生效;没有可放开的节点时,预算低于极限也只能停在全放开的结果 |
| 换了 `activation_memory_budget_solver` 或 `activation_memory_budget_runtime_estimator`,结果和换之前一模一样 | 是不是命中了 AOTAutograd 缓存:这两项取内置字符串时不进缓存键 | 对比实验时设 `TORCHINDUCTOR_AUTOGRAD_CACHE=0` 关掉这层缓存 |
| 报 `conflicting budgets within a single joint graph` | 同一张图里是否有两个不同值的区域预算 | 用 `torch._dynamo.graph_break()` 把它们分到不同的图 |
| 报 `must cover the entire forward of a graph` | 区域预算是否只包住了图的一部分 | 包住整个前向,或设 `activation_memory_budget_require_full_coverage = False` |
| 报 `Need networkx installed` | 环境里有没有 networkx | 装上;最小割靠它求解 |
| 报 `AOT Autograd failed to partition the joint forward-backward graph` | 报错里列出的冲突节点:某个值反向要用,却既不能存也不能重算 | 这是 PyTorch 的 bug;带上 tlparse 里的 `min_cut_failed_fx_graph` 等产物报 issue |
| 多卡编译后在反向卡住,单卡正常 | 各卡保存集合是否一致(对比各卡的 `aot_graphs`) | 试 `torch._functorch.config._sync_decision_cross_ranks = True`,开了 AOTAutograd 缓存时还要配 `_sync_cache_decision_cross_ranks` |
| 用了 `context_fn` 后看到提示原地算子的警告 | 区域里有没有 `relu_` 这类原地调用 | 改成非原地写法 |

## 六、常见误区

**「编译不改变激活,想省显存只能自己包重计算。」** 人们这么以为,是因为 eager 的经验里激活只由模型结构决定。实际上默认的最小割已经把可融合的逐元素中间值挪到反向重算,配置注释的说法是它应当总比 eager 省;再往下省,改一个预算就行,不必动模型代码。

**「最小割是在权衡显存和计算量。」** 「重计算」这个名字容易让人这么理解。实际上割的权重只有字节数,重算被假定免费,计算量只通过白名单和禁令间接体现;只有预算小于 1、走到背包那一步时,才第一次按 FLOPs 估重算时间。所以默认切法不会因为「这个逐元素运算很长」就选择存它,除非撞上长链那条禁令。

**「策略里的优先重算、优先存只是建议,编译器会再权衡。」** `CheckpointPolicy` 的文档说优先级的那两种可以被 torch.compile 这类子系统覆盖。当前的切分器里,`PREFER_RECOMPUTE` 和 `MUST_RECOMPUTE` 一视同仁,都是强制重算;`PREFER_SAVE` 则完全不加约束,最小割照样可能把它重算掉。要保证存下,只有 `MUST_SAVE`。

**「用 checkpoint 包住一层,编译器还会替我把矩阵乘存下。」** 因为默认切法确实会存矩阵乘,人们以为包了之后也一样。实际上普通的激活重计算在编译下把区域里每个算子都标成优先重算,也就是强制重算,矩阵乘一个不留。要让编译器只重算便宜的那部分,要么不包、改用预算,要么用选择性策略把矩阵乘列出来。

**「预算 0.5 就是激活减半。」** 配置注释的举例容易让人按「省掉多少比例」去理解。代码里的算法是在两端之间插值:0 对应整段重算时只存输入的量,1 对应默认切法的量;而且两端都是按假张量估的,源码注释承认实际占用通常比估计的少。先用曲线看清两端各是多少,再定预算。

**「打开卸载配置,激活就会自动卸到 CPU。」** 开关的名字像是一键功能。实际上它只处理被标了 `should_offload` 的节点,而 torch 源码里没有任何代码去设这个标记,测试里是靠 `joint_custom_pass` 手工标的。`CheckpointPolicy` 里虽然有 `MUST_CPU_OFFLOAD` 与 `PREFER_CPU_OFFLOAD`,当前没有代码消费它们:在 eager 下它们落进「不存」的分支、等同于重算,在编译下切分器也不认。

**「运行时把 `debug_partitioner` 设成 `True` 就能看到切分日志。」** 它看上去和别的配置项一样可以随时改。实际上切分器模块在导入时就把它读成了一个常量,之后再改不起作用;要在导入 torch 之前设 `AOT_PARTITIONER_DEBUG=1`,而且这些日志挂在 `torch._functorch.partitioners` 自己的日志器上,`TORCH_LOGS=aot` 看不到,要把模块名写进 `TORCH_LOGS`。
