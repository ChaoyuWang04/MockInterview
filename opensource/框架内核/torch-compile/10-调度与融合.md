# 调度与融合

这一页回答一件事:图降成一串循环级节点之后,Inductor 凭什么决定哪几个节点合进同一个 kernel、合完按什么顺序执行。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

09 章把图降成了一串循环级节点:能内联的逐元素运算已经并进了使用者,剩下的每个节点是一段循环,写一块必须落地的缓冲。如果一个节点就是一个 kernel,又回到了 eager 的老毛病。访存受限的算子链上,每一步都把结果写回显存,下一步再读回来;一条 add → relu → mul 的链,三个 kernel 一共读写 6 次整张量,真正必要的只有读输入、写结果这 2 次。为什么这一写一读很贵,知识库「算子融合」篇讲过,这里不重复。

难处在于不能见谁合谁。合并首先要**合法**:消费者读生产者结果时用的下标,必须和生产者写的下标一一对上,否则同一个 kernel 里一个线程要的值可能由另一个线程负责算,还没算出来;合完的节点也不能在依赖图里绕出环。其次要**划算**:两段循环的形状对不齐,硬塞进一个 kernel 只能照顾一方的分块,另一方的访存变得零散;一个 kernel 里装的东西太多,寄存器压力把占用率压下去,反而比分开跑慢;把原图里隔得很远的两段合在一起,中间缓冲活得更久,峰值显存上涨。最后还要**算得起**:候选对的数目随节点数平方增长,编译期不能把每一对都实测一遍。

所以这一章的问题是:**给定一串知道自己读写什么的循环节点,怎么在编译期内挑出一组合法又划算的合并,再排出一个峰值显存低的执行顺序。**

## 二、解法

最天然的直觉:把每个节点读写了哪些显存摆出来,两个节点碰到同一块显存、下标又对得上,就有东西可省;省得多的先合。Inductor 的调度器就是这么做的:读写清单从循环体里推,省了多少按字节数,合并用贪心。

![同一段计算融合前后的显存读写对比。左边是融合前:add、relu、mul、sum 四个 kernel 各自读写显存,add 读 x 写 y1,relu 读 y1 写 y2,mul 读 y2 写 y3,sum 再读一遍 x 写出按行求和的 s,中间结果 y1、y2 写回显存又被下一个 kernel 读回,整张量大小的读写一共 7 格。右边是融合后:一个 kernel 在同一趟循环里做完 add、relu、mul 并顺带求和,只读一次 x、写 y3 和 s,纵向合并让 y1、y2 留在寄存器里省掉 4 格,横向合并让两处对 x 的读共享一次、省掉 1 格,整张量大小的读写只剩 2 格](/opensource/torch-compile/10a-fusion-before-after.svg)

**读写清单从循环体里推出来。** 每个节点的循环体用一个只记录、不计算的处理器跑一遍:每一次读记成一条「读哪块缓冲、下标是循环变量的什么表达式、循环范围多大」,每一次写同样记下。下标写不成循环变量表达式的(外部库调用、用户自定义算子、按数值去查另一张表),退化成「依赖整块缓冲」,它永远对不上具体下标,只保证先后顺序。还有一种只管顺序的弱依赖:某块缓冲先被读、后被原地改写,改写的节点必须排在读的后面;读的那一方如果被消掉,这条依赖也跟着作废。

**候选只在碰到同一块缓冲的节点之间找。** 调度器按缓冲把节点分组,只在同一组里、前后相距 64 个以内的节点之间两两试,不做全图配对。这是把平方级的搜索压下来的第一道闸。

**合法性按两种关系分开判。** 两个节点有依赖时是纵向合并:消费者对生产者输出的每一次读,下标都要和生产者的写完全一致(或在合并、调换循环之后一致),这样值就在同一个线程里从生产者手上直接交给消费者,不经过显存;还要确认没有第三个节点夹在中间,既依赖生产者、又被消费者依赖,否则合并后成环。两个节点互不依赖时是横向合并:它们读同一份输入,合在一起这份输入只读一次。两种合并还都要过代码生成后端的形状检查:逐元素节点之间,元素总数和归约长度都得相等;逐元素节点可以并进一个归约,前提是它的元素数正好是归约的外层长度乘内层长度,或者等于归约输出的元素数;两边各自想要的分块方式对不上,也拒。

**打分看省下多少字节。** 每个合法候选得到一个分数,依次比五项:是不是和矩阵乘模板的合并、两边是不是同类(都是逐元素或都是归约)、两边共有的读写合计多少字节、读同一块缓冲不同位置的重叠程度、在原图里隔多远。模板那一项之外,两边字节数一旦相差 16 倍以上,就直接按字节比,同类与否不再起作用。几条硬门槛挡在打分之外:共有字节为 0 的不合;横向合并共有字节不到 10 的不合,在原图里相隔超过 64 个位置的也不合;一个融合节点最多装 64 个原始节点;估计合并后多占的显存超过省下字节的 32 倍,不合。

**贪心、多轮,合到合不动。** 每一轮把合法候选按分数从高到低排好,逐个重新检查一遍(前面刚做的合并可能让它成环或超限),通过就合。合出来的新节点带着两边读写清单的并集,下一轮照样参与。最多 10 轮,某一轮节点数不再减少就停。之后再补一轮:两个节点因为循环顺序不同而下标对不上时,试着调换其中一个的循环顺序,凑成可合。

**省下的写在生成 kernel 时兑现。** 一块缓冲如果所有使用者都在同一个融合节点里,又没有被原地改写,生成这个 kernel 时就不再写它,它也不再分配显存。纵向合并省下的那一写一读,就是在这一步真正消失的。

**最后重排顺序压峰值。** 融合定下来之后,调度器用三种拓扑排序各排一遍:每一步挑让当前峰值涨得最少的节点;优先执行前驱最早完成的节点,让缓冲尽快释放;按读写总量从小到大深度优先。连同原顺序一共四个方案,各自估一遍峰值显存,取最低的那个。

**为什么实际不吃亏。** 大多数被融合的是访存受限的逐元素与归约,它们的耗时大体正比于读写的字节数,按字节打分排出的先后和按时间排的差不多;拿不准的场景,另有开关让调度器把每个候选合并实际跑一遍再决定。

## 三、代价

**分数不是时间。** 默认不实测,只数字节。一次省了字节、却让分块对不齐或寄存器吃紧的合并,分数照样高。挡在前面的只有几条硬规则:分块检查、64 个节点的上限、峰值显存检查。打开实测后,每个候选都要把两个节点分开和合在一起各生成、编译、跑一次,只有合起来比分开跑的时间之和短才合,编译时间明显变长。

**下标必须精确对上。** 生产者按行写、消费者按转置后的顺序读,在纵向合并里就是依赖没对上,链在这里断开,中间结果照样落显存。调换循环顺序和反解下标能救回一部分,救不回的只能在日志里看到。经由张量取值的间接下标永远对不上;生产者以原子加这类需要全局同步的方式写入时,消费者也不能在同一个 kernel 里读它。

**贪心的结果依赖顺序。** 分数高的先合,它可能让后面一个本来更好的合并成环或超限。结果对原图的节点顺序敏感,同一个模型换一种写法,最后的 kernel 数可能不同。

**横向合并会拉长生命期。** 源码注释点名的场景是开了激活重计算的模型:不同检查点区域里的重算节点被横向合到一起,显存占用明显上升。64 个位置的距离限制就是为此加的,注释自己也承认它是一条粗略的启发式。

**外部调用是断点。** 外部库调用不能当生产者接逐元素尾巴,也不能当消费者被并进来,只有声明支持尾巴的用户 Triton kernel 例外。默认模式下矩阵乘走外部库,所以矩阵乘后面的逐元素链从矩阵乘之后才开始融;要把尾巴并进矩阵乘,得走模板那条路,见 12 章。

**峰值显存是估出来的。** 重排按每块缓冲的大小提示估峰值,动态形状下用的是提示值而不是实际值;重排发生在融合之后,只能在已定的融合结果上挪顺序,改不了融合本身拉长的生命期。

## 四、和同类大厂框架不一样的地方

对照对象是 XLA 的 GPU 后端与 TensorRT 的层融合,前者是 Google 在 JAX 与 TPU、GPU 上的编译器,后者是 NVIDIA 的推理优化器。三者都要把多个算子合进一个 kernel,差别在靠什么决定合不合。以下关于 XLA 与 TensorRT 的说法都只取自它们的官方文档。

| 必须回答的问题 | Inductor 调度器 | XLA 的 GPU 后端 | TensorRT |
|---|---|---|---|
| 合完是什么 | 一个融合节点,交给代码生成后端出 kernel | 一个融合计算,文档写明总是编成恰好一个 GPU kernel,内部的中间结果不落显存 | 若干层合成一个带内部选项的新层 |
| 靠什么决定能不能合 | 不认算子名:只看读写下标对不对得上、循环形状齐不齐,再按省下的字节打分贪心合并 | 文档没有公开融合决策的细节,不作比较 | 构建阶段识别融合目录里列出的固定模式;相邻的逐元素层可以合成一层,但合成的大小有上限 |
| 矩阵乘能不能带前后 | 默认模式下矩阵乘走外部库,不带尾巴;模板路径另议 | 含矩阵乘的融合交给 Triton 生成,文档示例里类型转换、矩阵乘、缩放、取负合成了一个融合 | 卷积后接 ReLU、GELU、Clip,或接逐元素的求和、取最小、取最大,各有专门的模式 |
| 用户怎么看结果 | 融合日志逐条打出两节点为什么没合;kernel 名里带着被合进去的算子名 | 打印优化后的 HLO,看生成了哪些融合 | 构建日志里,被合并的层名拼成新层的名字,如 ip1 + relu1 |

一句话:TensorRT 只合它认识的模式,可预测但覆盖窄;Inductor 用一套通用的读写账决定一切,新算子只要降得成循环就能参与融合,代价是分数只看字节、不看时间。

## 五、调参与观测

这一页的参数分三处:Inductor 的全局配置 `torch._inductor.config`,在 Python 里改,对之后发生的编译生效;同一批键也能通过 `torch.compile(..., options={...})` 只对这一次编译调用生效;少数键另有环境变量,在导入时读取,要在进程启动前设好。想整套换掉打分与合并的启发式,可以继承 `InductorChoices` 覆盖 `can_fuse`、`score_fusion` 等方法,再通过 `inductor_choices_class` 装上。

| 参数 | 在哪调 | 默认 | 往哪边调、会怎样 | 怎么看 |
|---|---|---|---|---|
| `max_fusion_size` | 全局配置或 `options` | 64 | 调小:一个 kernel 装的原始节点更少,寄存器压力下降,kernel 数变多 | `fusion` 日志 `exceeds max fusion` |
| `score_fusion_memory_threshold` | 同上 | 10(字节) | 调大:横向合并更挑剔,只共享一个标量的节点不再合;低于它时还会触发调换循环顺序再试 | `fusion` 日志 `score_fusion_memory_threshold` |
| `max_fusion_buffer_group_pairwise_attempts` | 同上 | 64 | 调大:同一缓冲的使用者里更远的候选也会被试,大图编译变慢;调小相反 | `compile_times()` 里 `Scheduler.fused_nodes` 的耗时 |
| `max_fusion_unique_io_buffers` | 同上 | `None`(不检查) | 设成整数:合并后读写的不同缓冲数超过它就不合,限制 kernel 参数与寄存器 | `fusion` 日志 `fusion_prevent_too_many_reads_and_writes` |
| `aggressive_fusion` | 同上 | `False` | `True`:没有共同读写的逐元素节点也按循环形状分组去试;归约仍要求有共同读写 | kernel 数变化 |
| `benchmark_fusion` | 同上,或 `TORCHINDUCTOR_BENCHMARK_FUSION=1` | `False` | `True`:每个候选实测,合起来不比分开快就不合;编译明显变长 | `fusion` 日志 `can fuse (benchmark)` 与 `cannot fuse (benchmark)` |
| `loop_ordering_after_fusion` | 同上,或 `TORCHINDUCTOR_LOOP_ORDERING_AFTER_FUSION` | 开源构建 `True` | 关掉:循环顺序不同的节点不再调换去凑合并,转置相关的链更容易断 | `TORCH_LOGS=loop_ordering` |
| `triton.tiling_prevents_pointwise_fusion` | 同上 | `True` | `False`:分块方式不一致的逐元素节点也合 | `fusion` 日志 `tiling mismatch` |
| `epilogue_fusion`、`prologue_fusion` | 同上;后者也可 `TORCHINDUCTOR_PROLOGUE_FUSION` | 都是 `True` | 把逐元素尾巴或前处理交给矩阵乘模板的总开关,细节见 12 章 | `fusion` 日志 `template epilogue not satisfied`、`prologue fusion turned off` |
| `reorder_for_peak_memory` | 同上 | `True`(lite 模式下 `False`) | 关掉:保留融合后的拓扑顺序,峰值显存可能上涨 | `torch._inductor.memory` 的 INFO 日志:`Baseline peak memory` 与每种排序的估值 |
| `combo_kernels` | 同上 | `False` | `True`:融合后再把互不依赖的 kernel 横向拼成一个,少一些 launch,代码生成见 11 章 | 生成代码里 kernel 数 |
| `use_dce` | 同上 | `True`(lite 模式下 `False`) | 关掉:没有使用者的节点不删,多出无用 kernel | `ir_pre_fusion` 里的节点数 |
| `debug_fusion` | 同上,或 `TORCHINDUCTOR_DEBUG_FUSION=1` | `False` | `True`:生成代码里每个 kernel 前加一行注释,列出被合进来的节点名 | `output_code` |

**观测四处。** 为什么没合:`TORCH_LOGS=fusion` 对每个被拒的候选打一行 `cannot fuse buf3 with buf5: 原因`,每一轮结束打 `completed fusion round (i/10): fused N nodes into M nodes`;`schedule` 给更粗的调度信息。合成了什么:`TORCH_LOGS=ir_pre_fusion,ir_post_fusion` 打印融合前后的节点清单,设 `TORCH_COMPILE_DEBUG=1` 时同样的内容落进调试目录的 `ir_pre_fusion.txt`、`ir_post_fusion.txt`。生成了几个 kernel:`TORCH_LOGS=output_code` 看生成代码,kernel 名形如 `triton_poi_fused_add_mul_relu_0`,`poi` 是逐元素、`red` 是归约,中间是被合进来的算子。跑得怎样:官方的 GPU 性能分析页给了按 kernel 类别拆 GPU 时间、把单个 kernel 抽出来单独测带宽的流程。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 训练或推理,先看融合到底做了什么 | `TORCH_LOGS=fusion,output_code` 加 `TORCHINDUCTOR_DEBUG_FUSION=1` 跑一步,其余默认 | 日志量大、第一步更慢,换来每个 kernel 装了哪些节点、每个没合的原因 |
| 长时间跑的推理或训练,吞吐优先、编译时间不敏感 | `torch.compile(model, options={"benchmark_fusion": True})` | 用明显更长的编译,换掉按字节估错、实际更慢的合并 |
| 融合后的某个大 kernel 比拆开跑还慢(寄存器吃紧) | `options={"max_fusion_size": 16, "max_fusion_unique_io_buffers": 16}` | 用更多的 kernel 与多一些的显存读写,换每个 kernel 的占用率 |
| 小批量推理,大量互不依赖的小 kernel,launch 开销主导 | `options={"combo_kernels": True}`(`mode` 与 `options` 不能同时传,要配 CUDA graph 就在 `options` 里另加 `"triton.cudagraphs": True`) | 用更长的编译和更大的 kernel,换更少的 launch |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先看哪里 | 再做什么 |
|---|---|---|
| 一条逐元素链编译后仍是好几个 kernel | `TORCH_LOGS=fusion` 里这两个节点的 `cannot fuse` 原因 | `memory deps did not match`:多半是转置或视图让下标对不上,确认循环重排开着;`node1 is extern`:链中间夹着外部调用,只能在 eager 层面改写 |
| 某个融合 kernel 比 eager 还慢 | `output_code` 里它装了几个节点,单独测这个 kernel 的带宽 | 调小 `max_fusion_size`,或开 `benchmark_fusion` 对照 |
| 编译后峰值显存比预期高 | `fusion` 日志有没有 `Fusion will increase peak memory`;`torch._inductor.memory` 日志里各排序的估值 | 确认 `reorder_for_peak_memory` 没被关;开了激活重计算的模型看是不是远距离横向合并 |
| 编译时间大头在调度器 | `compile_times()` 里 `Scheduler.fused_nodes` 与 `Scheduler.__init__` | 关掉 `benchmark_fusion`;调小 `max_fusion_buffer_group_pairwise_attempts` |
| 两个明明读同一个输入的归约没合到一起 | `fusion` 日志的原因是不是归约长度不一致 | 形状不同的归约默认不合;只有读同一输入、归约方向不同的一对有专门路径 `triton.mix_order_reduction`(开源构建默认开),其余情况接受分开跑 |

## 六、常见误区

**「融合越多越快。」** 知识库讲融合的收益是省访存,于是人们以为调度器合得越狠越好。实际上它按字节打分、默认不计时,合成的大 kernel 只能按其中一方分块,寄存器压力也跟着涨。64 个节点的上限和分块检查是护栏,不是保证;真遇到融合后变慢,解法是调小上限或开实测,而不是开 `aggressive_fusion`。

**「`aggressive_fusion` 就是把融合开大一档。」** 名字让人这么以为。实际上它只放开一件事:没有共同读写的逐元素节点,也按循环形状分组去试合并;归约依然要求有共同读写,其余门槛一条不少。它解决的是「本来就该放在一起的独立小算子」,对下标对不上的纵向链毫无帮助。

**「相邻的两个操作作用在同一个张量上,就一定能纵向合并。」** 人们看的是张量名,调度器看的是下标表达式。生产者按行写、消费者按列读,或者中间隔着一个改变步长的视图,就是 `memory deps did not match`,中间结果照样落显存。循环重排能救按维度换序的一类,救不了经由张量取值的间接下标。

**「横向合并只省不亏。」** 它确实省一次读,但把原图里隔得很远的两段绑到一起,前一段的输出要一直活到后一段跑完。开了激活重计算的模型最容易踩到:显存占用反而上涨。调度器的 64 个位置距离限制和峰值显存检查都是事后补的启发式,不能完全挡住。

**「kernel 名看不出融合了什么,要去开 `TORCHINDUCTOR_UNIQUE_KERNEL_NAMES`。」** 官方的 GPU 性能分析页写着这个选项默认关、为了提高缓存命中。基准上的代码里它默认已经是开的,kernel 名本来就带着类别和算子名。看到的名字若只有 `triton_`,先查是不是有人显式把它设成了 `0`。

**「峰值显存重排会顺手纠正融合带来的显存上涨。」** 重排跑在融合之后,只在已定的融合结果上挪执行顺序;融合把哪些缓冲的生命期拉长了,它改不了。它用的还是大小提示值,动态形状下估出来的峰值和实际可能差得不少。
