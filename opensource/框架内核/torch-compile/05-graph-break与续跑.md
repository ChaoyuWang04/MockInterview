# graph break 与续跑

这一页回答一件事:抓图撞上模拟不了的代码时,torch.compile 怎么把函数切开、让切口后面的部分照样被编译,以及切口在什么地方会失控。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

Dynamo 模拟不了所有 Python。打印、写文件、调一个用 C 写又没有等价实现的函数、按张量的值走分支,这些在抓图时要么没法不真执行,要么根本算不出结果(02、03 章)。模型代码里这种句子很常见,而且往往夹在两段纯张量运算中间。

碰到这一句,直接的做法只有两种,都会骨折。**报错**,要求用户把这句改掉或挪出去,于是「不改代码就能编译」这条承诺当场作废;**整个函数放弃**,回 eager 跑,于是一句打印让整个函数的算子全部失去融合,编译等于没开。

真正要的是中间路线:能抓的抓成图,抓不了的那一句交给 Python,之后的部分接着编译。可「之后接着编译」本身就难:Dynamo 只能在一个函数被调用、帧还没开始执行时截下它(02 章),它没法从一个函数的第 30 行开始抓。而且切开是有价钱的:切口两边的算子再也融不到一起,每次调用都要多回一趟 Python;切口如果落在循环里、嵌套函数里,碎的方式还会成倍放大。

所以这一章的问题是:**怎么把一个函数在任意一句处切开,让切口之后的部分重新变成一个能被截下、能被编译的函数,同时让切口的数量和代价可控。**

## 二、解法

最天然的直觉是单步调试:走到抓不了的那一句停下,把已经抓到的交出去编译,这一句让 Python 自己跑,跑完从下一句接着抓。torch.compile 就是这么做的。难点全在「接着抓」,它的答案是:既然只能从函数开头抓,那就现做一个「开头就是原函数第 30 行」的新函数,叫续跑函数。

![一处断图把函数切成三段:示例函数 f 的前两行和第三行里的求和进图 1,第三行的 print 由 Python 执行,后两行进续跑函数里的图 2;编译时生成两段字节码,f 的改写后字节码负责调图 1、写回副作用、还原仍会被读到的局部变量、原样执行 print、再调续跑函数,续跑函数是 f 字节码的整份拷贝加一段序言,序言把参数压回栈、重进仍在进行的 with 块、跳到断点下一条;之后每次调用的时间线依次是查 f 的 guard、图 1、还原与写回、print、截下续跑函数并查它的 guard、图 2,图 1 与图 2 之间张量要写回显存,算子无法融合](/opensource/torch-compile/05a-split-at-graph-break.svg)

**第一遍不当场切,从头再抓一遍。** 模拟到一条调用发现抓不了时,执行器手里的追踪对象可能已经被这条指令改了一半,状态是脏的。它不去回滚,而是在这条指令处记一笔「这里要断」,然后把整个函数从头重新模拟;第二遍走到这一处之前就停下,拿到的是干净的状态。重来的次数有上限(02 章)。依赖张量的条件跳转是例外:跳转指令动不了 Python 状态,可以当场切,不用重来。

**编前半段,切口处把现场存下来。** 已经抓到的算子编成图 1。切口处还活着的东西都要交出去:操作数栈上的值,以及之后还会被读到的局部变量(之后没人读的直接丢掉,不进图的输出)。副作用写回也在这里做一次(03 章),因为接下来那句 Python 可能正要看它们。正在进行的 with 块,比如关梯度、autocast,在图 1 结束时退出;生成的字节码在执行切口那一句之前把它重新进入、执行完再退出,续跑函数开头再进一次,所以那一句和后半段看到的全局状态都与 eager 下一致。

**切口那一句原样执行。** 生成的字节码在调完图 1、还原完变量之后,把原来那条指令照抄一遍,交给 Python 真正执行。于是这句的参数如果是张量运算(比如打印一个求和的结果),求和已经在图 1 里算完了,只有打印本身走 Python。

**续跑函数:整份拷贝,加一段序言。** 续跑函数的字节码是原函数字节码的完整拷贝,前面加一段序言:把传进来的参数一个个压回操作数栈,重新进入切口处仍在进行的 with 块,然后一条跳转指令跳到切口的下一条。切口之前的那段代码还在,只是永远走不到。续跑函数的名字里带着原函数名和切口的行号,作为全局变量装进用户函数所在的模块。

**它被当成普通函数调用,于是自然被截下。** 生成的字节码最后一步是「调用续跑函数,把栈上的值和活变量当参数传进去,返回它的结果」。这是一次普通的 Python 调用,帧钩子照常截下它,从它的开头抓图,抓出图 2;它有自己的 code object,也就有自己的 guard 与缓存条目。它里面再撞上抓不了的东西,就再切一次,链条可以任意长。

**依赖张量的分支,两条去路各接一个续跑函数。** 模拟到按张量的值跳转时,图 1 把条件张量也作为输出交出来;生成的字节码里保留原来的跳转指令,让 Python 对真张量求值选路,跳和不跳的两个目标各接一个续跑函数。

**续跑函数总是从原函数生成。** 续跑函数里又断图时,新的续跑函数不从续跑函数拷,而是回到最初那个函数,按「切口位置、栈上有几个值、活着哪些变量、在哪些 with 块里」查一张缓存表,没有才生成。几条路径汇到同一个切口,只会生成一个续跑函数,不会按分支数指数增长。

**嵌套函数里断图,默认冒泡到最外层。** 被内联的函数里撞上抓不了的东西,默认不在那一层切,而是整个冒泡到最外层那一帧里调用它的那一句:外层函数在这里切开,这次调用本身成了「交给 Python 执行的那一句」。被调用的函数于是作为一个新的顶层帧被截下,从头抓到同一处又冒泡一次……官方文档的说法是续跑只在顶层函数上做,嵌套深度为 N 时,同一处断图要被抓 N 次,总共模拟的帧数是 N 的平方量级。当前有一个默认关闭的开关,让续跑直接在内层发生:一次编掉前半段,然后按层依次调用每一层的续跑函数,最内层的结果交给外一层接着跑。

**有三种地方续不了,退路各不相同。** 切口落在循环体里(判断法是一条启发式:从当前位置往后到第一条返回指令之间,有没有跳回前面的跳转),续跑函数没法接回循环的下一圈,整个函数放弃,回 eager,并打上跳过标记(02 章)。切口落在 try 块里,或落在一个不能退出再重进的上下文管理器里,退回到之前最近一个「栈为空、不在 try 里」的位置编前半段,函数剩下的部分在同一帧里原样按 eager 跑,不再生成续跑函数。Python 3.12 起列表与字典推导式被内联进函数体,自带一个循环,里面断图本来会触发整帧放弃;这里特殊处理,把整段推导式包成一个单独的函数交给 Python 跑,推导式之后照常续跑。

**为什么实际不吃亏。** 切分只在编译时做一次;稳态下每处切口每次调用多出来的,是一次图的调用、几行还原变量的字节码、一次普通函数调用和一份 guard 检查。换来的是用户不改一行代码就能先跑起来,结果与 eager 一致,之后再按日志一处处消断图。

## 三、代价

**融合跨不过切口。** 切口前算出、切口后还要用的张量,必须作为图 1 的输出写回显存,图 2 再读进来。原本可以融成一个 kernel 的逐元素链被一刀切开,访存受限的模型最先感到。每张图各自走一遍后端,前向和反向都按切口分段。

**每处切口每次调用都付固定开销。** 回到 Python、从图输出里还原变量、做一次写回、调续跑函数、查续跑函数的 guard。函数算得重时看不见;小模型、高频调用、或者开了 CUDA graph 希望整段回放时(13 章),切口越多越明显。

**编译时间成倍。** 除条件跳转外,每处断图都让整个函数从头重新模拟一次(02 章);嵌套深度 N 的断图被抓 N 次。一个函数里断得多、嵌套又深,Dynamo 本身的耗时会压过后端。

**循环里的一句打印最贵。** 循环体里断图,整个函数回 eager,而且跳过标记是粘的,之后的调用都不再尝试编译这个函数。它调用到的函数还会被各自截下,但这个函数本身的循环、循环外的算子全部失去编译。一个训练步里在循环中打一行日志,就能让整段编译作废。

**try 块和陌生的上下文管理器让尾巴全部 eager。** 这时不是切成两段接着编,而是「编前半段、后面全扔给 Python」,直到函数返回。

**续跑函数也吃重编额度。** 它是独立的 code object,有自己的 8 条缓存额度(01 章),自己的 guard 条件;前半段传进来的参数形状一变,它也要重编。切口越多,要预热的编译结果越多。

**日志与栈会让人迷路。** 同一处断图在嵌套时出现多次;报错栈里夹着名字带原函数名和行号的续跑函数。官方在详细模式下专门加了一段提示:最近一次抓图的起点未必是你套编译的地方。

## 四、和同类大厂框架不一样的地方

01 章已经比过「依赖数值的分支:断图还是报错」。这里比一层更细的:抓不了的东西最后落在哪、数据依赖的控制流交给什么结构。对照 TensorFlow 的 tf.function 与 JAX 的即时编译。

| 双方都要回答的问题 | torch.compile 的断图与续跑 | JAX 的即时编译 | TensorFlow 的 tf.function 与 AutoGraph |
|---|---|---|---|
| 函数中间有一句编译器处理不了的 Python | 默认在这里切开:前半段成图,这一句回到 Python 执行,后半段由续跑函数重新抓成另一张图 | 用户显式写一个 host 回调,编进程序;每次调用都把输入从设备搬到主机、结果再搬回,官方提醒在 GPU、TPU 上这份搬运与同步的开销可能很大 | 可以把这段 Python 包成图里的一个算子,图仍是一张,这个算子运行时按 eager 执行;官方建议只用于原型与实验:要拿 GIL,函数体不随图序列化,必须和调用它的 Python 程序在同一进程 |
| 按张量的值走的 if | 默认切开,Python 对真张量求值选路,两条去路各接一个续跑函数;要留在图里得改写成条件高阶算子(14 章) | 用户手写条件原语;它是官方列出的 4 个结构化控制流原语之一,可以求导 | AutoGraph 把条件是张量的 if 自动改写成条件算子,两支都进图,运行时选 |
| 按张量的值走的循环 | 循环体里切不开,整个函数回 eager | 用户手写 while、定次循环或 scan 原语;while 只支持前向模式求导,定次循环要端点是静态的才支持反向 | AutoGraph 把条件是张量的 while、对张量迭代的 for 改写成循环算子,循环体在图里只出现一次 |
| 用户怎么找到要改的那一处 | 断图日志逐处给类型、原因与用户代码行;整图模式或「断图即报错」开关让第一处就报错 | 追踪时直接抛「追踪值被当成布尔值」的错误,说明里列出 if、while、and、or、max、min 这些隐式转布尔的写法 | 不用找:条件是张量的 if 与循环被自动改写 |

一句话:TensorFlow 与 JAX 把抓不了的东西做成图里的一个节点(回调或控制流算子),图始终是一张,代价是用户改写代码或付 host 往返;torch.compile 把它留在图外,用续跑函数把几张图和几段 Python 拼起来,用户不用改代码,代价是图碎,以及循环里断图时整个函数回退。两边的参数名都在第五节。

## 五、调参与观测

这一章的参数分三处:编译入口的具名参数(`fullgraph`、`backend`,见 01 章的参数表,改了要重新包一次);在代码里写的装饰器、上下文与函数调用,抓图时按所在区域生效;全局配置,在编译前改。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `torch._dynamo.error_on_graph_break(True)` | 装饰器或上下文,可嵌套,内层覆盖外层 | 未包时为 `False` | 这片区域里一有断图就报错;但不保证整个函数只有一张图,也不能在 `fullgraph=True` 下放行 | 异常消息就是断图原因 |
| `torch._dynamo.error_on_graph_break(False)` | 同上 | — | 在「断图即报错」的区域里给个别难消的片段放行 | `TORCH_LOGS=graph_breaks` |
| `torch._dynamo.config.nested_graph_breaks` | 全局配置 | `False` | `True`:内层函数里的断图在那一层续跑,同一处只抓一次;出问题时可用 `torch._dynamo.disable_nested_graph_breaks` 对局部关回去 | 日志里同一处断图的重复次数 |
| `torch.compiler.disable(fn, recursive=True)` | 装饰器 | `recursive=True` | 调用处断一次,函数本身和它调到的函数全部 eager;`recursive=False` 只放过这一层,里面调到的函数仍被截下编译 | 断图类型 `Skip calling torch.compiler.disable()d function` |
| `torch.compiler.is_compiling()` | 在代码里判断 | — | 抓图时为真;把写文件这类语句放进 `if not torch.compiler.is_compiling():`,抓图时直接跳过,不断图,编译后这句也不再执行 | — |
| `torch._dynamo.graph_break()` | 在代码里调用 | — | 人为切一刀,用来实验切口放在哪里更合算 | 断图类型 `Call to torch._dynamo.graph_break()` |
| `backend="eager"` | 编译入口 | `inductor` | 只抓图不生成代码;官方建议排查断图时用它,迭代快 | — |

**观测四处。** `TORCH_LOGS=graph_breaks` 每处断图打一段 `Graph break in user code at 文件:行`、`Graph Break Reason:` 与用户栈,原因里依次是断图类型、Explanation、Hint 和一个按类型编号的说明页链接(当前登记表里有 582 个编号);同一类型、同一位置第二次出现起只打一行 `user stack suppressed due to duplicate graph break`,设 `TORCHDYNAMO_VERBOSE=1` 则每次都打全,并附上最近 20 条模拟过的字节码。整个函数回退的那种断图,日志里写的是 `torch.compile will skip tracing the frame … and fall back to eager`。`torch._dynamo.explain(f)(*args)` 返回图数、断图数(按图数减一算)、每处原因与用户栈、每张图里的算子。`torch._dynamo.utils.counters["graph_break"]` 按原因计数,`counters["resumes"]` 按续跑函数名计数,能直接看出生成了几个续跑函数。tlparse 报告里每个续跑函数都有自己的一组编译记录,原字节码也会存进去。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 第一次接入,先摸清断在哪 | `model.compile(backend="eager")` 加 `TORCH_LOGS=graph_breaks`;或在单独的脚本里跑 `torch._dynamo.explain(model)(x)` | 不生成代码,换最快的排查迭代;只看断图,不看性能 |
| 库作者或性能关键模块,要求热路径无断图 | 外层保持 `fullgraph=False`,热路径函数加 `@torch._dynamo.error_on_graph_break(True)`,确实消不掉的日志片段用 `with torch._dynamo.error_on_graph_break(False):` 放行 | 用几处明确放行的断图换其余区域的强约束;比 `fullgraph=True` 灵活,但不保证一张图 |
| 预处理、日志、稀疏特征这类断得很多又不值得编译的函数 | 对它加 `@torch.compiler.disable`;嵌套很深又想在内层续跑的,试 `torch._dynamo.config.nested_graph_breaks = True` | 用函数入口处的一次断图换掉里面的许多处;嵌套续跑开关是默认关闭的实验路径,换来更少的重复抓图 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 编译了但没变快 | `TORCH_LOGS=graph_breaks` 或 `explain` 的断图数与位置 | 先消模型计算中间的断图,预处理与日志里的可以留着(官方的建议也是这样排) |
| 整个函数都是 eager 的速度 | 日志里有没有 `graph break in loop` 或 `fall back to eager` | 把那一句挪出循环;或把循环体抽成函数,只编译它;改完后 `torch._dynamo.reset()` 清掉跳过标记 |
| 断图之后的部分好像没被编译 | 日志里有没有 `Compiling up to the previous resumable state` | 断点在 try 块或不支持的上下文管理器里;把那一句挪出去 |
| 同一处断图在日志里出现好几次 | 这句是不是在被内联的深层函数里 | 默认每层冒泡一次,属正常;嫌编译慢就 `disable` 那个函数,或开 `nested_graph_breaks` |
| 断图原因是 `Data-dependent branching` | 条件张量是怎么算出来的,日志会把它的计算链一路打出来 | 能无分支就用 `torch.where`、`torch.clamp`;条件其实不依赖数据就改成 Python 数;必须分支用 `torch.cond`(14 章) |
| 报错栈里出现 `torch_dynamo_resume_in_f_at_行号` | 这是续跑函数,行号是切口所在行 | 正常现象;真正的出错位置看栈最后一行 |

## 六、常见误区

**「断图就是那一行不编译,其余照旧。」** 日志只指出一行,看起来代价也只有一行。实际上切口前后的算子再也融不到一起,活着的张量要落一次显存,每次调用多回一趟 Python;切口落在循环里时,整个函数都不编译,落在 try 块里时,切口之后的全部不编译。

**「在循环里打一行 print 调试,顶多多一处断图。」** 在循环外确实如此,于是大家在循环里也这么写。循环体里的断图续跑不了,这个函数整个放回 eager,而且被打上粘性的跳过标记,这个进程里不会再尝试编译它。调试时改用 `torch._dynamo.config.reorderable_logging_functions`(03 章),或把 print 挪到循环外。

**「日志里同一个断图出现三次,说明代码里有三处。」** 日志一处一段,自然这么数。嵌套三层的函数里的一处断图,默认会先在最外层冒泡一次、在中间层冒泡一次、在最内层真正处理一次,同一行被抓了三次。数断图要按位置去重,或者打开嵌套续跑。

**「`error_on_graph_break(True)` 就是可以局部开关的 `fullgraph=True`。」** 名字和效果都像。区别在保证上:`fullgraph=True` 保证整个函数只有一张图,而且一旦打开,内部不能再关;`error_on_graph_break(True)` 只保证这片区域里断图会报错,不保证一张图,优先级也低于 `fullgraph`。

**「`torch._dynamo.explain` 只是看一眼,不影响正在跑的程序。」** 它长得像只读的诊断接口。实际它在开始前和结束后各调一次 `torch._dynamo.reset()`,进程里已经编好的所有结果都被清掉,下一次调用要从头编译。在服务进程或训练中途调用它,相当于手动触发一次冷启动。

**「续跑函数是从断点开始的一小段新代码。」** 从报错栈里的名字看像是这样。实际它是原函数字节码的完整拷贝,只在前面加了序言跳到断点;它是独立的 code object,有自己的 guard 和自己的 8 条额度,切口之前那段代码也在里面,只是走不到。所以某个切口后面频繁重编,要去查的是续跑函数的重编原因,不是原函数的。
