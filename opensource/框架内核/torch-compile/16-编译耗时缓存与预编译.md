# 编译耗时:缓存与预编译

这一页回答一件事:一次冷启动的编译时间花在哪几段,每一段能不能从上一次的结果里拿回来,拿不回来的那段又怎么省。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

编译结果只活在进程里。缓存条目挂在 code object 上,进程一退就没了;一次冷启动从秒级到分钟级,大模型更久(01 章)。这笔账在三种场景下被反复付:

- 训练作业被抢占、重启、从 checkpoint 续跑,每一次都从零编;
- 推理服务扩容,新拉起的实例在编完之前接不了流量;
- 多机作业里,每台机器、每个 rank 把同一批图各编一遍。

最直接的补救是把结果存盘复用。可一旦复用,就有第二种骨折:缓存明明在,却没命中,也说不清为什么;或者一部分 rank 命中、另一部分没命中,快的那几个在集合通信上干等,一直等到超时。

所以这一章的问题是:**编译的哪几段能跨进程复用,凭什么判断能复用,没命中时怎么查;复用不了的那一段又怎么省。**

## 二、解法

最天然的直觉就是构建系统的做法:每一段的产物,按「这一段的输入」算一个哈希当键,存进磁盘;下次输入一样,直接拿产物,不用管什么时候该作废。分层缓存这件事本身见知识库 TorchCompile 篇第六节,这里只讲每一层的键里装了什么、命中时省掉什么。

![一次冷启动编译的五段和每段后面的缓存:上排依次是 Dynamo 抓图、AOTAutograd、Inductor 生成代码、Triton 编译、第一次调用时的块大小实测;抓图那一段没有缓存层,每次启动都重抓;Triton 编译和块大小实测各有一层缓存,只省自己那一段;FX 图缓存盖住 Inductor 与 Triton 编译两段;AOTAutograd 缓存再往前盖住 AOTAutograd 这一段;预编译把五段全部盖住,代价是不许断图、形状默认按示例特化、丢掉一部分 guard、版本与 GPU 型号必须一致](/opensource/torch-compile/16a-cache-layers-per-stage.svg)

**键宽到「键一样,产物就一定能用」。** Inductor 那一层叫 FX 图缓存,它的键不只有图:还有输入张量的形状、步长、类型和设备(设备带卡号),图里常量的实际取值,Inductor 的全部配置,默认浮点类型与确定性开关,再加两样环境指纹:整棵 torch Python 源码逐文件算出的哈希,以及 GPU 型号、CUDA 与 Triton 的版本。代码里任何一处改动都可能改变生成的 kernel,干脆全算进去,宁可多作废,不可错用。

**符号维不进键,进条件。** 动态形状下,输入长度是符号,键里只记符号的名字,不记当时的值。每个条目另带一段「这份代码对哪些尺寸成立」的条件表达式;一个键下可以存好几条,查到后拿当前尺寸逐条判,判过的那条才算命中。这是 04 章 guard 的思路搬到了磁盘上。

**AOTAutograd 那一层是更外面的一圈。** 它的键从 Dynamo 交来的图算起,加上求导开关、autocast 状态和 AOTAutograd 自己的配置,再把 FX 图缓存键的全部组成带上。存的东西很薄:前反向两张图在 FX 图缓存里的键,加上重建运行时包装用的元数据。命中时联合图、函数化、切分全部省掉,前反向产物回头去 FX 图缓存里取;那边取不到,这一层也按未命中算。所以它离不开 FX 图缓存,后者一关,这一层整个绕过。图里出现白名单之外的 Python 调用时同样绕过,因为键说不清那个函数会做什么。

**kernel 二进制跟着图走。** Triton 把 kernel 源码编成二进制时有自己的缓存目录,按卡号分开,键由 Triton 自己算。开源默认还把这些二进制打包进 FX 图缓存的条目,命中时先写回 Triton 的目录,所以只搬了 FX 条目、没带 Triton 目录的机器也不用重编。调优结果另存:逐元素与归约 kernel 挑中的块大小(11 章),存成 kernel 源码旁边的一个小文件,键是 kernel 源码的哈希加 torch 源码哈希,候选列表一变就作废;矩阵乘的实测耗时(12 章)按机器指纹存一张总表。

**抓图为什么不存。** Dynamo 的产物是改写后的字节码和一棵 guard 树(01、04 章),guard 里大量是按对象身份的检查:这个函数还是不是那个函数,这个模块还是不是那个模块。身份只在一个进程里有意义,换一个进程就无从比较。所以默认每次启动都重抓一遍,热启动省的只是后面几段;跨进程只留一样东西,即哪些维是动态的(06 章)。有一个默认关着的实验开关可以把这一段也存盘,代价是把按身份的 guard 全部丢掉。

**再往前一步:预编译。** 编译入口上有一个提前编译的方法:给出示例输入,当场把五段全部跑完,连同 guard 与改写后的字节码打成一个文件,另一个进程加载后直接用,抓图也省掉。为了能跨进程判断,它默认只留张量元信息、全局状态、形状条件这类 guard,全局变量和按身份的 guard 一律丢掉。另有一个不经过 Dynamo 的预编译接口:按示例输入非严格地追踪整段计算,吐出一段自带调用逻辑的 Python 源码和一份 kernel 缓存,权重不打进去,运行时再把模型传进来。

**整包搬家,或者远程共享。** 进程里产生或命中过的每一层条目都会记进一张清单,一个接口把它们序列化成一串字节,另一台机器用对应的接口导入,写回本地缓存目录,之后照常按键查。想让一群机器实时共享,AOTAutograd、FX 图、调优三层都能接 Redis,开源默认关。

**另一条路是少编。** 大模型多半是同一种层重复堆叠。区域编译只对重复的那一块调编译入口,每一层共用一份结果。嵌套编译区域在整模型编译时标出重复的层:第一次遇到时照常抓图,后面每次出现,把上一次记下的 guard 换成这一层的对象复核一遍,过了就直接复用那张子图,不再重抓;每个函数最多存 8 份,超了报错。并行是第三招:Triton 与 C++ kernel 交给子进程池去编。池子在第一次调到 Inductor 后端时就开始预热;还没准备好时不等,当场在主进程里串行编;闲 60 秒后工作进程退掉,下次有活再唤醒。

**为什么实际不吃亏。** 算键要把图、常量和配置序列化一遍再哈希,比起编译本身很便宜;键保守到命中就一定能用,不需要任何人管失效;没命中的代价就是照常编一遍,不会比不用缓存更差。

## 三、代价

**热启动不是零。** 抓图每次都付,这一段在 Python 里逐条模拟字节码(02 章);命中之后还要算键、读盘、把生成的模块加载进来、按符号维条件复核。模型越大、断图越多,这部分越显眼。

**键宽,所以脆。** 换 torch 版本、给 torch 打一行补丁、升级 Triton 或 CUDA、换一种 GPU,全部作废;Inductor 任何一项会影响输出的配置改了也作废;图里的常量取值进键,常量一变就是一个新键。

**卡号在键里。** 同一台机器上 8 个 rank,输入张量分别在 8 张卡上,键各不相同:各编一份,各存一份,重启后各自命中自己那份。共享一个缓存目录,并不能让 8 个 rank 只编一次。

**绕过和未命中是两回事。** 未命中至少会把结果存下来,下次能中;绕过是根本不进缓存:自定义图变换没实现唯一标识、图里有不支持缓存的高阶算子,以及只在 AOTAutograd 那一层绕过的两种:图里有白名单外的调用、打开了参数冻结。这些图每次启动都要全编,日志里只有一行 INFO。

**多卡命中不齐会互相等。** 命中的 rank 先跑到集合通信,等还在编的 rank。为此命中时会按省下的编译时间临时加长所有进程组的通信超时。编译过程本身要发集合通信时(08 章的跨 rank 同步切分决策),部分命中会让没命中的 rank 卡住,需要另开一个开关:各 rank 查完先对一下结果,有一个没中就全体重编。

**磁盘只增不减。** 这几层没有按大小或时间淘汰的逻辑,默认目录又在系统临时目录下:长期运行的机器越攒越大,容器重建或清理临时目录时又整体丢光。Redis 那头写入时也不设过期。

**预编译拿灵活换确定。** 不许断图;形状默认按示例特化,换形状就过不了 guard;丢掉全局变量与身份 guard,意味着加载后把某个全局函数换掉,它照跑旧图,不报错;加载时 Python、torch、CUDA、Triton 的版本和 GPU 型号任何一项对不上就直接报错;整个功能仍标着实验性。

## 四、和同类大厂框架不一样的地方

对照对象是 JAX 的持久化编译缓存,以及 TensorRT 的计时缓存与引擎序列化。前者是 Google 在大规模训练与推理里给 XLA 编译结果用的磁盘缓存,后者是 NVIDIA 推理部署时缩短构建时间的标准做法;三家都要回答「存什么、键里有什么、多机怎么共享、没命中怎么查」。表中关于 JAX 与 TensorRT 的每一格,都核自 docs.jax.dev 与 docs.nvidia.com 上的官方页面。

| 各家都要回答 | torch.compile | JAX 的持久化编译缓存 | TensorRT |
|---|---|---|---|
| 默认开不开 | 本地磁盘缓存默认开,落在系统临时目录下 | 可选,设了缓存目录才开 | 计时缓存要自己创建、挂到构建配置上;不挂时构建器建一个临时的,构建完就丢 |
| 存的是什么 | 按段分层:前反向切分结果、生成的代码与 kernel 二进制、调优结果;抓图不存 | 编译好的整个程序;默认连带打开 XLA 的调优缓存,kernel 缓存可选 | 每层各种实现的计时,默认也带 JIT 编出的代码;完整产物是序列化后的引擎 |
| 键里有什么 | 这一段输入的图、输入元信息(含卡号)、常量取值、整棵 torch 源码的哈希、GPU 型号与 CUDA 和 Triton 版本、编译配置 | 函数未优化的 HLO、jaxlib 版本、相关 XLA 编译选项、设备数与拓扑(GPU 上只含型号名)、压缩算法、一个可由用户改写的钩子返回的字符串 | 输入输出张量配置与层参数都相同的层直接复用计时;内容绑定目标设备、CUDA 与 TensorRT 版本,以及会改变实现的构建选项 |
| 哪些不存 | 被绕过的图,见第三段 | 编译不到 1 秒或产物小于下限的不写 | 只覆盖常用层:卷积、反卷积、池化、softmax、矩阵乘、逐元素、shuffle 与内存布局转换 |
| 多机怎么共享 | 各机本地目录;可接 Redis;或把整包导出再导入 | 冷启动时所有进程都编,只有全局 rank 0 写,所以缓存要放共享文件系统;还能在单机上模拟多机拓扑,预先把缓存填好 | 计时缓存可序列化给别的构建器;引擎默认只保证在同 OS、同 CPU 架构、同 GPU 型号、同 TensorRT 版本下可用 |
| 没命中怎么查 | 调试日志逐项列出键的每个组成及其哈希,两次运行一对就知道哪项变了 | 有一个解释未命中的开关,文档说目前只覆盖追踪缓存的未命中 | 文档未涉及,不作比较 |

一句话:JAX 缓存的是编完的整个程序,键从未优化的 HLO 算起,查缓存之前函数已经追踪并降成了 HLO;TensorRT 缓存的是逐层计时,完整产物是一个换机器、换版本就要重建的引擎文件。torch.compile 按段分层、默认全开,键里连 torch 自己的源码都算进去,换来的是命中就安全,代价是一动就全废,而最前面的抓图那一段谁也省不掉,只能靠预编译整段绕开。

## 五、调参与观测

这一页的参数分四处:三份 Python 全局配置(`torch.compiler.config`、`torch._inductor.config`、`torch._functorch.config`),改了对之后发生的编译生效;环境变量,在进程启动前设好;运行期接口(整包导出导入、预编译的存与取),在代码里调用;模型代码里的标注(嵌套编译区域),改了要重新抓图。编译线程数 `TORCHINDUCTOR_COMPILE_THREADS`、`torch.compiler.reset()` 只清进程内缓存这两件见 01 章;PGO 的开关见 06 章。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `TORCHINDUCTOR_CACHE_DIR` | 环境变量 | 系统临时目录下的 `torchinductor_<用户名>` | 指到持久盘:重启、换容器后缓存还在;底下分 `fxgraph/`、`aotautograd/`、`triton/<卡号>/`、`cache/`(矩阵乘调优)、`dynamo/`(PGO 与实验性抓图缓存) | 看这几个子目录有没有长出新文件 |
| `TRITON_CACHE_DIR` | 环境变量 | 未设,即缓存根目录下 `triton/<卡号>` | 单独指定 Triton 二进制的位置 | — |
| `torch._inductor.config.fx_graph_cache` | 全局配置,或 `TORCHINDUCTOR_FX_GRAPH_CACHE` | `True` | 关掉后每次都重跑 Inductor 与 Triton 编译,AOTAutograd 缓存也跟着绕过 | `TORCH_LOGS=inductor` 里的 `fx graph cache hit for key` 与 `miss for key` |
| `torch._functorch.config.enable_autograd_cache` | 全局配置,或 `TORCHINDUCTOR_AUTOGRAD_CACHE` | `True` | 关掉后每次都重建联合图与切分;08 章做切分对比实验时要关 | `TORCH_LOGS=aot` 里的 `AOTAutograd cache hit for key` |
| `torch._inductor.config.bundle_triton_into_fx_graph_cache` | 全局配置,或 `TORCHINDUCTOR_BUNDLE_TRITON_INTO_FX_GRAPH_CACHE` | 开源 `True` | 关掉后 FX 条目不带 kernel 二进制,命中后要靠 Triton 目录,那里没有就重编 | tlparse 里命中条目的 `triton_bundler_meta` |
| `torch._inductor.config.autotune_local_cache` | 全局配置 | `True` | 关掉后每次启动重新实测块大小与矩阵乘候选 | 11、12 章的实测日志是否每次都出现 |
| `torch.compiler.config.cache_key_tag` | 全局配置,或 `TORCH_COMPILE_CACHE_KEY_TAG` | 空串 | 拼进各层的键;换一个值等于整体作废,不用删目录 | — |
| `torch.compiler.config.force_disable_caches` | 全局配置,或 `TORCHINDUCTOR_FORCE_DISABLE_CACHES=1` | `False` | 所有缓存都不读不写,在缓存根目录下另开临时目录编;测真正的冷启动用它;打开时 `aot_compile` 直接报错 | `TORCH_LOGS=+inductor` 里 `FX cache status: use_cache=False` |
| `TORCHINDUCTOR_FX_GRAPH_REMOTE_CACHE`、`TORCHINDUCTOR_AUTOGRAD_REMOTE_CACHE`、`TORCHINDUCTOR_AUTOTUNE_REMOTE_CACHE` | 环境变量 | 未设,开源即关 | 设成 `1` 接 Redis;要装 `redis` 包;读先本地后远程 | 包没装时一条 `Unable to create cache` 警告;连不上时不报,静默当作没有 |
| `TORCHINDUCTOR_REDIS_HOST`、`TORCHINDUCTOR_REDIS_PORT`、`TORCHINDUCTOR_REDIS_URL` | 环境变量 | `localhost`、`6379`、未设 | 设了 URL 就只用 URL | Redis 里键的形状是 `pt2:fx-graph-v1::<键>:c1` 这一类 |
| `torch._inductor.config.unsafe_skip_cache_dynamic_shape_guards` | 全局配置 | `False` | 命中时不判符号维条件,加载快一点,可能用错条目 | — |
| `torch._functorch.config._sync_cache_decision_cross_ranks` | 全局配置 | `False` | 各 rank 查完 AOTAutograd 缓存后取一次最小值,有一个没中就全体按未命中重编 | 日志 `AOTAutograd cache cross rank miss: rank=... local_hit=False` |
| `TORCHINDUCTOR_WORKER_START` | 环境变量 | `subprocess` | `subprocess` 另起一个干净的 Python 进程托管进程池;`fork`、`spawn` 直接建多进程池,在守护进程里建不起来 | 日志 `Creating 'subprocess' pool with N workers` |
| `torch._inductor.config.quiesce_async_compile_pool` | 全局配置,或 `TORCHINDUCTOR_QUIESCE_ASYNC_COMPILE_POOL` | `True`,闲 60 秒退掉工作进程 | 关掉后工作进程常驻,占内存,中途重编不用等唤醒 | — |
| `TORCH_WARM_POOL` | 环境变量 | `1` | `0`:不在后端第一次被调用时预热进程池 | — |

| `torch.compiler.save_cache_artifacts()`、`torch.compiler.load_cache_artifacts(data)` | 运行期接口 | — | 导出本进程产生或命中过的各层条目;导入时写回本地缓存目录 | 两者都返回一份按类别列出的键清单 |
| `torch.compile(fn, fullgraph=True).aot_compile(((x,), {}))`,`save_compiled_function(path)`,`torch.compiler.load_compiled_function(f)` | 运行期接口,实验性 | — | 提前编好整段、存成一个文件、另一个进程加载;模块要在 `.forward` 上调,调用时把模块当第一个参数 | 版本不符报 `Compile package was created with a different ...` |
| `torch.compiler.precompile(fn, *example_inputs)`、`torch.compiler.precompile.load(code, cache)` | 运行期接口 | `backend="inductor"` | 不经 Dynamo,返回 Python 源码加 kernel 缓存;形状与控制流按示例特化 | 违反约定时抛 `PrecompileError` |
| `torch.compiler.nested_compile_region` | 装饰器,标在重复的层上 | `max_reuse_entries=8` | 整模型编译时该层只抓一次,后面照印;条件不同就再编一份,超过上限报错 | `TORCH_LOGS=+hierarchical_compile` 打出复用失败的 guard |

**观测四处。** 命中没有:`TORCH_LOGS=inductor,aot` 每次查缓存打一行 `hit`、`miss` 或 `Bypassing ... because`;计数在 `torch._dynamo.utils.counters["inductor"]` 的 `fxgraph_cache_hit`、`fxgraph_cache_miss`、`fxgraph_cache_bypass`,以及 `counters["aot_autograd"]` 的 `autograd_cache_hit` 等。为什么没中:`TORCH_LOGS=+inductor,+aot` 打出 `FX graph cache hash details for key` 与 `Autograd graph cache hash details for key`,下面每行是 `[分项哈希] 组成名: 取值`,把两次运行的这几行对一下,哈希不同的那一行就是原因。整体报告:tlparse 里每次编译有 `fx_graph_cache_hit`、`_miss`、`_bypass` 与 `aotautograd_cache_*` 工件,带键的全部组成和绕过原因,命中时还记着省下的编译时间(`time_saved_ns` 或 `time_saved_ms`)。热启动剩多少:`compile_times()` 里 Dynamo 那几项在热启动时照样有,后端那几项应该明显缩短;多卡作业里命中的 rank 会打 `Increasing NCCL timeout by N`。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机训练作业,经常被抢占重启 | 启动前 `TORCHINDUCTOR_CACHE_DIR=/持久盘/torchinductor`,其余保持默认 | 用一块持久盘换重启后的后端编译;抓图照付 |
| 多机训练或推理扩容,环境镜像一致 | 第一次跑完在每个 rank 上 `data, _ = torch.compiler.save_cache_artifacts()` 按 rank 存到共享存储;新进程在第一次调用前 `torch.compiler.load_cache_artifacts(data)` | 用一次导出与分发换每台机器的冷启动;键里有卡号与机器指纹,rank 与卡型要对得上 |
| 同上,但有一套长期在线的缓存服务 | 三个 `*_REMOTE_CACHE=1` 加 `TORCHINDUCTOR_REDIS_URL` | 不用管分发,换来对 Redis 的依赖;没有过期,要自己清 |
| 推理服务,输入形状固定,冷启动要求最短 | 构建时 `torch.compile(model, fullgraph=True).forward.aot_compile(((x,), {}))` 再 `save_compiled_function`;部署时 `torch.compiler.load_compiled_function` | 连抓图一起省掉,换来版本与 GPU 型号锁死、不许断图、guard 变少 |
| 由同一种 block 重复堆叠的大模型,冷启动太久 | 在 block 的 forward 上加 `@torch.compiler.nested_compile_region`,整模型照常 `model.compile()` | 用一个装饰器换掉逐层重复的抓图与编译;层与层条件不同时照样多编 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 每次重启都和第一次一样慢 | 缓存根目录是不是还在系统临时目录、容器重建后还在不在;`TORCH_LOGS=inductor` 是 `miss` 还是 `Bypassing` | 改到持久目录;是绕过就按原因处理 |
| 目录在,还是 `miss` | `+inductor,+aot` 两次运行的键组成逐行对 | 常见是 torch 或 Triton 版本、配置项、图里常量取值不同 |
| 日志是 `Bypassing FX Graph Cache because 'Unsupported post grad custom pass'` 一类 | 自定义图变换有没有继承 `CustomGraphPass` 并返回 `uuid()` | 补上唯一标识;AOTAutograd 层的 `Unsupported call_function target` 要么改写那处调用,要么登记进 `unsafe_marked_cacheable_functions` |
| 缓存全中,热启动仍然慢 | `compile_times()` 里 Dynamo 各项占多少 | 抓图不缓存;考虑预编译、嵌套编译区域,或先消断图(05 章) |
| 多机作业偶发集合通信超时,只在重启后 | 各 rank 的 `hit` 与 `miss` 是否一致 | 统一缓存来源;编译期有跨 rank 同步时打开 `_sync_cache_decision_cross_ranks` |
| 导入整包后只有 rank 0 快 | 导出是不是只在 rank 0 做了 | 每个 rank 各导出、各导入自己那份 |
| 设了远程缓存却看不到效果 | 有没有 `Unable to create cache` 警告;Redis 能不能连通 | 装 `redis` 包、查地址;连不上时不会报错 |
| 编译时 CPU 只有一个核在忙 | 有没有 `Creating ... pool` 日志;是否在守护进程里 | 守护进程里用 `subprocess` 启动方式;或确认 `TORCHINDUCTOR_COMPILE_THREADS` 没被设成 `1` |
| 预编译产物加载时报版本或 GPU 不符 | 报错里是哪一项 | 在与部署完全相同的镜像和卡型上重新预编译 |

## 六、常见误区

**「有了磁盘缓存,第二次启动就不编译了。」** 人们把缓存想成「整个编译结果」,于是以为热启动是零。实际上 Dynamo 每次都重抓,guard 每次都重建,缓存省的只是抓图之后那几段;图碎、Python 逻辑重的模型,热启动的主要耗时恰恰在抓图。

**「缓存按模型结构算,模型不变就能命中。」** 键里有整棵 torch 源码的哈希、GPU 型号和 CUDA、Triton 版本,还有图里常量的取值。升级一次 nightly、在 site-packages 里改一行调试输出、把作业从 A100 挪到 H100,缓存全部作废,日志里只显示 `miss`,不告诉你是哪一项。排查时第一反应去看模型代码是错的,应该先开 `+inductor` 对键的组成。

**「共享缓存目录,8 张卡只需要编一次。」** 这个直觉来自普通的文件缓存。键里带着输入张量的设备号,每个 rank 的键都不同,第一次各编各的,之后也只命中自己那份;整包导出同理,rank 0 的包对 rank 3 没用。

**「设了远程缓存的环境变量,就在用 Redis 了。」** 远程层只在构造时失败才打一条警告,连接失败会被静默标成不可用,之后每次查询都当作没有。症状是「设了跟没设一样快」,很少有人想到去看 Redis 的连通性。

**「删掉 fxgraph 目录就能测冷启动。」** 还有 AOTAutograd 目录,它会引用 FX 条目,取不到时才算未命中;Triton 目录里的二进制与调优结果也还在,测出来的是半冷启动。要测真冷启动,开 `force_disable_caches`,它会整个换到一个新的临时目录。反过来,生产上别忘了关它,它连预编译都拒绝。

**「预编译出来的文件和权重文件一样,可以发到任何机器。」** 它更像一个编好的二进制:Python、torch、CUDA、Triton 版本和 GPU 型号任何一项不同都拒绝加载;默认丢掉了全局变量与对象身份的 guard,加载后替换一个全局函数,它不会发现,照跑旧图。部署侧要把它当成和镜像绑定的构建产物来管理。
