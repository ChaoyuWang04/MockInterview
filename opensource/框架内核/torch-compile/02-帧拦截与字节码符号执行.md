# 帧拦截与字节码符号执行

这一页回答一件事:不改一行用户代码,torch.compile 怎么从一个 Python 函数里把张量运算抓成图,又怎么保证抓到的正是这次调用真正会走的那条路。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

编译器要一张图,手里却只有一个 Python 函数。最省事的抓法是跟踪一次执行:把函数真跑一遍,张量上发生的运算都录下来。PyTorch 自带的跟踪式导出就是这么做的,官方文档对它的警告也写得明白:只有程序不依赖数据时才对。

这种抓法在两处骨折。

**控制流被静默烙死。** 真跑一遍,解释器只会走一条路:这次 n 大于 0,录下来的图里就只有 if 那一支,Python 的循环按这次的次数摊平。下次 n 变成负数,图还是那张,结果算错,不报任何错。模型里这类分支到处都是:按层数循环、按配置开关走不同路径、按输入长度选实现。

**抓图本身要付真代价。** 真跑就要真算:一个大模型抓一次图,GPU 上完整跑一遍前向,显存与时间都照付;随机数被消耗、全局状态被改动,抓图这个动作本身就改变了程序后面的行为。

还有一个约束让事情更难:入口在用户手里的任意一个函数,它会调用别的函数,别的函数又会调用第三方库。编译器既不能要求用户改代码,也不能指望这些函数都有源码可读。

所以这一章的问题是:**怎么在函数真正执行之前拿到它,不真算就推出每一步张量的形状,并且只把这次调用确实会走、下次能验证还会走的那条路抓进图。**

## 二、解法

最天然的直觉是:既然跟踪一次执行会漏掉「本来可能走的另一条路」,那就不让 Python 解释器跑,自己当解释器,一条一条读字节码,每一步都清楚自己为什么这么走。torch.compile 的前端 Dynamo 就是这么做的。CPython 允许第三方替换帧的求值函数(PEP 523,知识库 TorchCompile 篇已经讲过它是什么),Dynamo 用它在帧执行前把帧截下来。

![逐条模拟字节码的过程:左列是示例函数 f 的字节码,一次一条;第二列是每条执行完之后的符号栈,局部变量先以惰性占位入栈,第一次被乘法用到时才包装成带假张量的追踪对象,同时在 FX 图里添加占位 x 与乘法节点,并记下 x 的类型、形状、设备等前提;比较 n 大于 0 时 n 按常量 3 处理,当场算出真,只记下 n 等于 3 这条前提,跳转指令因此不跳,图里没有分支;调用 g 时开一个内联解释器,g 里的 relu 记进同一张图;最后返回时栈顶成为图的输出,图交给后端并生成新字节码](/opensource/torch-compile/02a-bytecode-stack-and-graph.svg)

**截帧只在编译调用期间生效。** C 层把解释器的帧求值函数换成自己的钩子,钩子每次先看一个线程局部的回调:回调为空,帧按原样交回 CPython;回调为「只运行」,只查已有缓存,不编译;回调是 Dynamo 的转换函数,才真正介入。编译包装出来的函数在调用原函数前打开回调,返回后立刻关掉,所以只有这一次调用栈里新开的帧会被截下。查缓存、命中执行的流程见 01 章;未命中时,C 层把这一帧的字节码、局部变量、全局变量、内建函数表打包,回到 Python 交给 Dynamo。查 guard 期间回调被临时置空,检查代码自己不会再被截。

**先筛一遍,不是每一帧都值得抓。** 局部变量里找不到张量或模块、代码里也没引用 torch 的帧;生成器;已经开始执行的帧;Dynamo 跳过名单上的文件,一律放回 CPython 原样执行。被放掉的帧会在它的 code object 上打一个「跳过」标记,之后同一段代码再被调用,C 层看到标记直接放行,连 Python 都不回。

**逐条模拟,手里是自己的栈。** 被截下的帧交给一个符号执行器。它持有一套和 CPython 同构的状态:一个操作数栈、一张局部变量表,里面放的不是真值,而是追踪对象(每种 Python 对象怎么建模见 03 章)。每种字节码对应一个处理方法,按操作码查表分发;遇到没有处理方法的指令就断图。参数不在一开始就全部包装,先以惰性占位放进局部变量表,第一次真正被用到时才包装、才记前提;函数里从没读过的参数直接不进表,也就不会为它记任何前提。

**张量换成假张量,只推元信息不算数。** 碰到张量运算,执行器做两件事:往 FX 图里加一个节点;在假张量模式下把这个运算「跑」一遍,得到结果的形状、dtype、设备、步长。假张量本质是一个挂在 meta 设备上的张量,另外记着它假装所在的设备;运算走的是只分配输出、不碰数据的 meta 实现或分解规则。于是取形状做算术、按设备选分支这类 Python 代码,在模拟中都能得到答案(形状是符号时得到的是符号表达式,06 章)。同一个真张量无论被转换几次都得到同一个假张量,两个互为别名的真张量得到共享同一份假存储的两个假张量,别名关系一路带进图里。算不出来的只有依赖数据本身的东西:取出一个标量的值、输出形状取决于数据的算子(比如 nonzero),默认在这里断图。

**控制流就地决定,决定的依据记成前提。** 这是和跟踪一次执行最根本的区别。模拟到条件跳转时,执行器看栈顶那个值:它是已知的 Python 常量,就按这个值选一支继续,另一支不进图,同时这个常量是怎么来的(比如「第 2 个参数等于 3」)已经记成了前提;它是符号整数,按这次的实际值判断并记下相应的前提;它是张量,值在抓图时不可知,就在这里断图(05 章)。循环同理,每转一圈就往下模拟一圈,图里没有循环结构。图里只有一条路,但下次调用前 guard 会先确认这条路还成立(04 章),不成立就重编,不会静默跑错。

**调到别的函数就内联。** 碰到对普通 Python 函数的调用,执行器不去真调,而是为被调函数新建一个内联执行器:参数直接用调用方栈上的追踪对象,深度加一,和外层共用同一张 FX 图与同一套副作用记录。被调函数返回时,返回值作为一个追踪对象压回外层的栈。于是跨多层函数的张量运算最后落进同一张图,函数边界在图里消失。哪些函数能钻进去、哪些必须断开,由跳过规则决定(03 章);内联的函数里断图,默认会冒泡到最外层那一帧处理(05 章)。

**返回时交卷。** 模拟到最外层的返回指令,栈顶的值成为图的输出,整张图交给后端编译,同时生成一段替代原函数的新字节码;这三样(图、新字节码、guard)就是 01 章缓存条目里的东西。模拟完一个张量运算都没碰到,说明这一帧不值得编译,同样打上跳过标记放回 eager。

**抓图不许动真状态。** 整个抓图过程外面包着一层状态保护:grad 开关、推理模式、确定性算法开关、默认 dtype、CPU 与 CUDA 的随机数状态都在进入前存下、结束后恢复;结束时还会核对一遍全局状态,变了就直接报错,提示这是 Dynamo 的 bug。抓图对程序后面的行为没有任何可见影响。

**为什么实际不吃亏。** 模拟与假张量推导都只在编译那一次发生,之后每次调用走的是生成的字节码和编译好的图,和这套解释器再无关系。它换来的是跟踪一次执行给不了的两样东西:控制流的每一次取舍都有记录可查,抓图时 GPU 上一个 kernel 都不跑。

## 三、代价

**编译期慢,而且慢在 Python 里。** 用 Python 写的解释器去模拟 Python,每条字节码都要经过分发、建追踪对象、记前提;每个张量运算还要在假张量模式里走一遍 meta 实现。官方文档对假张量的评价很直接:它不做计算,但全在 Python 里、又常常要走分解,小张量下完全是开销主导,带上符号形状更慢。为此假张量加了一层按「算子加输入元信息」做键的调度缓存。断图时还要从头再模拟一遍(最多 100 次,05 章),大函数的抓图时间会成倍放大。

**和 CPython 版本死死绑在一起。** 模拟的对象是字节码,而字节码的指令集、帧布局每个 Python 小版本都在变。C 层与执行器里到处是按版本分叉的代码;遇到没有处理方法的新指令只能断图。当前基准明确拒绝在 Python 3.15 及以上运行编译,关闭 GIL 的构建要求 3.13.3 以上。升级 Python 前,先确认所用的 PyTorch 版本已经跟上。

**假张量不是永远不真算。** 一个内置算子如果既没有 meta 实现也没有分解规则,假张量会退一步:用全零的真张量在它假装的设备上把真实 kernel 跑一次,借此拿到输出的元信息。这一步真的占显存、真的花时间,只对 aten、prims 等一张白名单上的算子命名空间开放,且形状含符号时不做。多数自定义算子没有这条退路,没注册假实现就在这里断图。

**跳过标记是粘的。** 一段代码第一次被截下时如果被判为「不值得抓」(比如那次调用恰好没传张量,或者走的分支一个张量运算都没有),它的 code object 会被标成跳过,之后传进真张量也不会再编译,直到手动清掉 Dynamo 的全部状态。

**整帧放弃时只在日志里说。** 抓图中途遇到无法从断点续下去的情况,默认不报错,而是把整个函数放回 eager,只在断图日志里记一笔。函数没被编译、速度和 eager 一样,是最常见也最难发现的结果。

## 四、和同类大厂框架不一样的地方

01 章已经和 JAX 的即时编译比过抓图方式、依赖数值的分支、缓存键与形状变化。这里往下比一层:三家在抓图那一刻都要处理一段「不是张量运算」的 Python 代码,处理法决定了用户会踩到什么坑。对照对象再加上 TensorFlow 的 tf.function,它是 TensorFlow 把 Python 程序转成图的入口。

| | torch.compile | JAX 的即时编译 | TensorFlow 的 tf.function |
|---|---|---|---|
| 抓图时读的是什么 | 函数的字节码,不需要源码 | 不读程序,带着追踪对象把函数执行一遍 | 默认先由 AutoGraph 读源码、改写成图友好的代码再执行;调试器会停进改写后的源码 |
| 判断普通 Python 值的条件与循环 | 模拟到跳转时值已知,只走那一支,并记下这个值作为下次复用的前提;循环逐圈展开 | 追踪值只能通过形状、dtype 这类静态属性影响控制流,图里只知道走过的那一支 | 条件在抓图时照常执行,只有一支进图;Python 循环每转一圈往图里加一份运算 |
| 打印、往外部列表追加 | 抓图时不执行;打印处断图,每次调用都真打印;列表修改记下来,每次调用照样生效(03 章) | 只在抓图时发生,不进编译结果 | 只在第一次用某组输入调用时发生,之后重跑图,不再执行这段 Python |
| 张量的替身 | 假张量:形状、dtype、设备、步长,以及谁和谁共享存储 | 追踪对象,代表形状、dtype 这类基本属性 | 图里的符号张量,图要求输入有确定的数据类型与维度 |

一句话:JAX 与 tf.function 抓图时真的执行 Python,非张量代码只在抓图那一刻生效,文档提醒用户只写纯函数;torch.compile 从不执行它,每一处要么在模拟中算清并记成前提,要么断开交给 eager,于是用户不必改写,代价是前一段那些编译期开销。

## 五、调参与观测

这一章的参数分两处:Python 里改的全局配置,在之后发生的编译里生效;环境变量,由配置模块在导入 torch 时读一次,要在导入之前设好。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `torch._dynamo.config.capture_scalar_outputs` | 全局配置,或环境变量 `TORCHDYNAMO_CAPTURE_SCALAR_OUTPUTS=1` | `False` | `True`:`.item()` 这类取值不再断图,结果变成图里的无依据符号(06 章) | 断图日志里 `Data dependent operator` 消失 |
| `torch._dynamo.config.capture_dynamic_output_shape_ops` | 全局配置,或 `TORCHDYNAMO_CAPTURE_DYNAMIC_OUTPUT_SHAPE_OPS=1` | `False` | `True`:`nonzero`、`unique` 这类输出形状取决于数据的算子进图 | 断图日志里 `Dynamic shape operator` 消失 |
| `torch._dynamo.config.rewrite_assert_with_torch_assert` | 全局配置 | `True` | 对张量的 `assert` 改写成图里的异步断言,不断图;关掉后按数据依赖分支断图 | `TORCH_LOGS=graph_breaks` |
| `torch._dynamo.config.nested_graph_breaks` | 全局配置 | `False` | `True`:内联函数里断图时在那一层续抓,不冒泡到最外层(05 章) | 同上 |
| `torch._dynamo.config.allow_empty_graphs` | 全局配置 | `False` | `True`:一个张量运算都没抓到的帧也生成编译结果,不再打跳过标记 | `TORCH_LOGS=+dynamo` 里的 `skipping:` 行 |
| `torch._dynamo.config.suppress_errors` | 全局配置,或 `TORCHDYNAMO_SUPPRESS_ERRORS` | `False` | `True`:Dynamo 内部报错不再抛出,整帧退回 eager;会掩盖真问题,只在应急时开 | 日志里的警告 |
| `torch._dynamo.config.fake_tensor_cache_enabled` | 全局配置,或 `TORCH_FAKE_TENSOR_DISPATCH_CACHE` | `True`(环境变量默认 `"1"`) | 设成 `0` 关掉假张量调度缓存,编译变慢;只在怀疑缓存给错元信息时用 | `FakeTensorMode.cache_info()` 的命中与未命中数 |
| `TORCHDYNAMO_DEBUG_FUNCTION` | 环境变量 | 未设 | 设成一个函数名:只编译同名的函数,其余帧全部跳过;用来在大模型里二分 | `TORCH_LOGS=+dynamo` 里的跳过原因 |
| `TORCHDYNAMO_VERBOSE` | 环境变量 | 未设 | 设成 `1`:报错带上 Dynamo 内部的完整调用栈 | 报错信息 |

整图模式(`fullgraph=True`)会自动放开前两项:这时 `.item()` 与 `nonzero` 不断图也不报错,直接进图。

**观测四处。** 截没截、为什么跳过:`TORCH_LOGS=+dynamo` 打出每一帧的 `skipping: 函数名 (reason: ...)`,`torch._dynamo.utils.counters["frames"]` 里 `total` 与 `ok` 对比看有多少帧被截下、多少成功。模拟到了哪:`TORCH_LOGS=trace_source` 打出正在模拟的源码行,`trace_bytecode` 打出每条指令和当时的符号栈,`trace_call` 细到每个表达式。抓到了什么:`TORCH_LOGS=graph_code` 打出 FX 图的 Python 代码,`bytecode` 打出原字节码与改写后的字节码;官方文档推荐配合 depyf 把改写后的字节码反编译成可读的 Python。重来了几次:日志里的 `Restarting analysis due to` 每出现一次,就是整帧重新模拟一遍。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 第一次接入,想看清 Dynamo 在每一帧做了什么 | `TORCH_LOGS="+dynamo,graph_code,bytecode"`,配合 depyf | 用大量日志换完整的抓图过程,只在小输入上跑一两步 |
| 模型里有 `.item()` 或 `nonzero`,断图很多 | `torch._dynamo.config.capture_scalar_outputs = True` 与 `capture_dynamic_output_shape_ops = True` | 用无依据符号换图的完整;后端生成的 kernel 更通用,可能插入运行期断言(06 章) |
| 大模型里某个函数编译出错,想缩小范围 | `TORCHDYNAMO_DEBUG_FUNCTION=函数名`,加 `backend="eager"` | 只编一个函数、不生成代码,换来更短的复现时间 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 套了编译,某个函数的速度和 eager 一样 | `TORCH_LOGS=+dynamo` 里它的 `skipping:` 原因:没找到张量、在跳过名单、没抓到算子 | 首次调用就传真实输入;已被标成跳过的用 `torch._dynamo.reset()` 清掉后重跑 |
| 编译时间长,大头在 Dynamo 而不在 Inductor | `torch._dynamo.utils.compile_times()` 与 `Restarting analysis due to` 出现的次数 | 先消断图(05 章),除条件跳转外的断图都会让整帧重新模拟一遍 |
| 报 `Operator does not support running with fake tensors` | 是不是自定义算子没有注册假实现 | 给算子补假实现(14 章) |
| 报 `Missing bytecode handler` 或 `Python 3.15+ not yet supported` | 当前 Python 版本 | 换到 PyTorch 已支持的 Python 版本 |
| 报 `Global ... state changed while dynamo tracing` | 抓图过程中哪段代码改了全局状态 | 这是 Dynamo 的 bug;先用 `torch.compiler.disable` 把那段隔出去,再报 issue |
| 报 `Data-dependent branching` | 分支条件是不是张量 | 改成 `torch.where` 或 `torch.cond`(05 章) |

## 六、常见误区

**「Dynamo 是把函数跑一遍、边跑边录。」** 连官方深度解读都用「它是一个 tracer,执行函数并记录」来开头,听起来就是跟踪一次执行。实际上抓图期间函数体一行都没真执行:字节码由 Dynamo 自己模拟,张量是假张量,随机数与全局状态在结束时原样恢复。所以抓图阶段 GPU 上看不到 kernel,显存也不涨;例外只有那些没有 meta 实现、只能用全零真张量兜底的内置算子。

**「用 Python 值做分支,图会被烙死,换个值就算错。」** 这是从跟踪式导出带过来的经验,那边文档确实这么警告。这里不一样:分支取哪一支是按这个值当场决定的,值从哪来已经记成前提,下次值变了 guard 不过,重编一份。代价是重编,不是错结果。真正会断图的是分支条件依赖张量的数值。

**「第一次调用随便传点什么预热,之后真实输入会正常编译。」** 编译确实发生在调用时(01 章),于是人们以为第一次调用无关紧要。实际上第一次调用如果没传张量,或者走的路径上没有任何张量运算,这段代码会被打上跳过标记,之后传真张量也直接放行,一直是 eager,日志里只有一行 `skipping:`。

**「假张量从不真算。」** 名字给人的印象如此,大多数时候也确实如此。但没有 meta 实现的 PyTorch 内置算子会用全零真张量兜底跑一次真实 kernel,编译期在 GPU 上的那点显存和耗时往往就来自这里;自定义算子则没有兜底,缺假实现直接断图。

**「设 `TORCHDYNAMO_SUPPRESS_ERRORS=0` 就是不吞错。」** 这一带的其他开关都是按是否等于 `"1"` 判断,人们顺手这么写。这一个是按「有没有设、是不是空串」判断的,设成 `0` 反而把吞错打开了。要关它,就别设这个变量。

**「整图模式下 `.item()` 应该会报断图。」** 默认模式下它确实断图,于是人们以为整图模式会把它变成报错。实际上整图模式会自动放开标量取值与动态输出形状的捕获,`.item()` 直接进图变成无依据符号,报错可能推迟到后端或运行期,形状看不懂时去 06 章查。

**「内联进来的函数断了图,只影响那个函数。」** 函数边界在源码里很清楚,人们自然以为断图也按函数算。实际上被内联的函数在图里已经没有边界,默认的做法是把断图冒泡到最外层那一帧,外层函数在这次调用处整体切开,前后分成两张图(05 章)。
