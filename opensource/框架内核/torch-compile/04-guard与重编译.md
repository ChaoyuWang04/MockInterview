# guard 与重编译

这一页回答一件事:一份编译结果凭什么认定这次调用还能用,认不出来时又怎么说清楚是哪一条变了。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一张图只在抓它的那次调用的条件下成立。条件远不止输入张量的形状:抓图时读过的一切都算,包括张量的类型、dtype、设备、是否需要梯度、各维大小与步长,传进来的 Python 数的值,读过的全局变量,模块上的属性(比如是不是训练模式),以及 grad 开关、autocast、默认 dtype 这类全局状态。漏记一条,条件变了还跑旧图,结果静默出错。

guard 是什么、为什么形状一变就要重编,知识库 TorchCompile 篇已经讲过;这里只讲它怎么记、怎么查、坏在哪。坏法有三种:

- **记得太多,每次调用都付检查费。** 条件在每次调用前都要全部重查一遍。一个大模型整体编译,光模块属性就能攒出一大片条件;函数本身算得很快、调用又很密时,查条件的时间会占到可见的比例。
- **记得太细,无关的变化也触发重编。** 模块上一个每步加一的计数器、一个每步都变的学习率,都会被当成「条件变了」,每次调用都重编,很快撞上上限退回 eager(01 章)。
- **重编了却说不清为什么。** 一个模型攒下的条件成片,不告诉你是哪一条不成立,就没法下手。

所以这一章的问题是:**条件怎么记才不漏也不多,怎么组织才查得快,查不过时怎么只用一行话说清原因。**

## 二、解法

最天然的直觉是:抓图时读过什么,就记下「读到的是什么样」;下次调用把同样的东西再读一遍,逐条比。torch.compile 就是这么做的,讲究在记法和查法上。

![一份编译结果的 guard 检查树:根上先查全局状态;第一层按来源分成局部变量 x、局部变量 self、全局变量字典三支;x 下挂张量检查,self 下挂类型检查并经属性字典分到 training 与 linear 的 weight,全局变量字典下只取读过的 scale;每个节点先查自己的检查再进子节点,任何一条不过立即返回;形状关系等收尾检查最后跑;示例里 x 的张量检查不成立,重编日志只报这一条,写明第 0 维期望 3 实际 4](/opensource/torch-compile/04a-guard-tree.svg)

**只记读过的。** 函数的输入进来时先包成一个惰性的占位,抓图真正用到它时才落下条件;没碰过的参数、全局变量不进检查。每条条件都带着它的来源:一条从这一帧的局部变量或全局字典出发、逐级取属性或取下标的路径,「局部变量 self 的子模块 linear 的参数 weight」就是一个来源。来源怎么在追踪时产生见 03 章。

**用了什么,就记成哪一种检查。** 用到张量,记一条张量检查,把类型、dispatch key、dtype、设备、是否需要梯度、维数、各维大小与步长一次比完;用到 Python 数、字符串,按值记;用到函数、类、模块对象,按身份记;全局状态不挂在任何来源上,打包成根上的一条总检查。形状上的条件(哪一维是符号、维与维之间的关系)另见 06 章。

**按来源长成一棵树,整棵放在 C++ 里。** 所有条件按来源路径合并:根是这一帧,第一层分叉是各个局部变量和全局字典,再往下每一级是一次取值,具体检查挂在节点上。同一段前缀只取一次值,self 下面所有参数共用前面那几级取值。模块的属性不走模块自己的取属性方法,而是直接去它的属性字典、子模块表、参数表里按键取,省掉 Python 层的开销。整棵树在 Python 里搭好,检查在 C++ 里跑。牵涉好几个节点的条件(两个输入是不是同一个张量)挂在涉及的每个节点上,共用一份状态,最后一个节点到齐时才判定;形状之间的关系默认拼成一个 Python 函数,挂在根上最后跑。

**查的顺序与短路。** 根上先查全局状态;然后深度优先走各子树,每个节点先查挂在自己身上的检查,再依次进子节点;全过了才跑收尾检查。任何一条不成立立即返回「不过」。某个子节点失败过,它的失败次数加一,父节点把子节点按失败次数重新排序,下一次最容易失败的先查。一个函数挂着好几份编译结果时,不属于这次输入的那几份能在前几条检查里就被否掉。

**失败了怎么说原因。** 快速路径只回答过或不过,不记账。确定要重编时,再对已有的每一份编译结果各跑一遍带诊断的检查,找出各自第一条不成立的那一条,翻译成一行人话:哪个张量、哪一维、期望多少、实际多少。所有检查都过、只是换了一个后端函数对象时,原因会写成后端不匹配。按身份记下的对象被回收了,那份编译结果直接作废,原因写成「某某被释放」。

**为什么实际不吃亏。** 稳态下几乎每次都命中排在最前的那一份,每个节点只取一次值、比一次;字典没被改过(CPython 给每个字典一个版本号)时,它下面那些不可变的值连取都不取。编译完还会拿抓图那一帧把整棵树跑一次:不过说明 guard 自相矛盾,直接报错;过了顺便量一次检查耗时,写进日志。

## 三、代价

**每次调用都付,而且贵在取值。** 官方文档的判断是:每次调用的开销大头在「把要检查的对象取出来」,比较本身反而便宜。模型越深、模块越多,树越大;整模型编译的推理服务、小批量高频调用,最先感到它。图前面还有一段每次都跑的字节码,负责把参数和 buffer 取出来传进图,它和 guard 一起构成每次调用的固定开销。

**省检查费的办法都以正确性为代价。** 官方给的几种减法(不查模块属性、不查全局变量、预热后只查区分几份结果所需的最少条件)名字里都带着不安全:它们假定预热之后那些状态不再变,一旦变了就静默跑旧图,不会重编,也不会报错。只砍模块属性上的检查还不够,省下的开销有一部分会挪到图前那段取参数的字节码上,要和「参数装进图里」一起开。

**默认就有几处不查。** 为了省开销,当前默认有意放过了两类条件:模块上原本为空的钩子字典不检查,编译之后再给这个模块挂钩子,编译结果不会发现;参数与参数之间不查是否互为别名,同一个参数被当成两个输入传进来也不会发现。

**按值记的东西太细。** 全局变量、模块属性、默认参数里的 Python 整数一直按值记,每步都在变就意味着每步重编;作为参数传进来的整数只有第一次按值记,变过一次就换成符号(06 章)。

**原因一次只报一条。** 每份编译结果只报第一条不成立的检查,修掉这条,下一次可能冒出下一条。想一次看全要开详细模式,但那份清单里有些检查在实际运行时根本没被执行到,因为运行时在第一条失败处就停了。

## 四、和同类大厂框架不一样的地方

对照对象是 TensorFlow 的 tf.function,Google 在大规模训练与推理里长期在用。它也是「首次调用时追踪成图、按条件缓存、条件变了重新追踪」,差别在于判断能不能复用时看什么。

| 双方都要回答的问题 | torch.compile | TensorFlow 的 tf.function |
|---|---|---|
| 复用的判据从哪来 | 抓图时读过的一切:参数、全局变量、闭包、模块属性、全局状态,编成一棵检查树 | 只看调用参数:按每个参数的类型信息拼出一个函数签名,和已有追踪结果的签名比 |
| 全局变量或闭包变了 | 读过的都有条件,变了就重编 | 不重新追踪,继续用追踪时的值;官方建议把要变的量做成变量对象 |
| 传进来的 Python 数 | 第一次按值记,值变了转成符号 | 值本身就是类型的一部分,每个新值追踪一次 |
| 传进来的普通 Python 对象 | 按读过的属性逐条检查 | 先比身份,再比相等;同一个对象改了属性不会重新追踪 |
| 张量形状变了 | 默认第一次按具体形状,晃过一次就换成符号 | 按形状与 dtype 匹配;可以固定输入签名(不符就报错),或打开放宽重追踪的开关,自动找一个更宽的形状重追踪 |
| 谁对「没查到的东西变了」负责 | 默认由框架查;用户主动关掉部分检查后,由用户负责,变了就静默跑旧图 | 由用户负责:官方要求别依赖全局变量与闭包,要变的量走参数或变量对象 |

JAX 的即时编译在全局变量上和 tf.function 一样:官方示例里,全局变量改了,已编译的函数照样用第一次追踪时的值,直到参数的类型或形状变了、函数被重新追踪,才读到新值。

一句话:TensorFlow 与 JAX 不管全局变量,要求用户把函数写纯;torch.compile 接受任意 Python,于是凡是读过的都要查,换来的是每次调用的检查费,以及一套「关掉哪些检查」的不安全开关。两边的参数名都在第五节。

## 五、调参与观测

这一章的参数分三处:编译入口的 `options` 字典(改了要重新包一次);运行期可以随时切换的编译姿态;Dynamo 的全局配置(在编译前改)。上限、`set_stance` 的其余姿态、`isolate_recompiles` 见 01 章的参数表。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `options={"guard_filter_fn": f}` | `torch.compile` / `Module.compile` 的 `options` | 不设,所有检查都保留 | `f` 逐条决定每个 guard 留不留;丢得越多,每次调用越快,被丢掉的状态变了就静默跑旧图 | `TORCH_LOGS=guards` 看树变小了多少 |
| `torch._dynamo.config.install_free_tensors` | Python 里改全局配置 | `False` | `True`:参数与 buffer 装进图里当属性,不再作为图输入,图前取参数的字节码变短,张量检查也少一些 | profiler 里图前那段与 `TorchDynamo Cache Lookup` 的耗时 |
| `torch._dynamo.config.use_recursive_dict_tags_for_guards` | 同上 | `False` | `True`:嵌套模块整棵子树靠字典版本号一次判定,不再逐条走;官方建议在砍检查之前先试它 | 同上 |
| `torch._dynamo.config.max_saved_pointers_for_recursive_dict_tags_check` | 同上 | 256 | 上一行那条快路径最多记住多少个不同的对象;区域编译里一份编译结果被很多个相同的层复用时才需要调大 | — |
| `torch.compiler.set_stance(skip_guard_eval_unsafe=True)` | 运行期,可当上下文 | `False` | 只跑区分已有几份编译结果所需的检查(张量检查加上曾经失败过的分支);期间一旦需要重编,直接抛 `RuntimeError`,不会编 | 报错信息 `Recompilation triggered with skip_guard_eval_unsafe stance` |
| `torch._dynamo.config.allow_unspec_int_on_nn_module` | Python 里改全局配置 | `False` | `True`:模块上的整数属性不再按值记,改走动态形状,计数器类属性不再每步重编 | `TORCH_LOGS=recompiles` 里的原因消失 |
| `torch._dynamo.config.error_on_recompile` | 同上 | `False` | `True`:任何一次重编都抛 `RecompileError`,消息就是重编原因;适合放进测试 | 异常消息 |

`guard_filter_fn` 的现成取值都在 `torch.compiler` 里,名字都以 `_unsafe` 结尾:

| 过滤函数 | 留下什么 |
|---|---|
| `skip_guard_on_inbuilt_nn_modules_unsafe` | 丢掉 `torch.nn.Linear` 这类内建模块上的检查,其余保留 |
| `skip_guard_on_all_nn_modules_unsafe` | 丢掉所有模块上的检查;官方说这一项对降 guard 开销最有效 |
| `skip_guard_on_globals_unsafe` | 丢掉全局变量上的检查 |
| `keep_tensor_guards_unsafe` | 只留张量检查,默认连参数的张量检查也不留 |
| `keep_portable_guards_unsafe` | 只留全局状态、形状、非全局张量上的检查 |
| `skip_all_guards_unsafe` | 全部丢掉,调用时直接用第一份编译结果 |

**观测四处。** `TORCH_LOGS=guards` 打出每份编译结果的整棵树(以 `TREE_GUARD_MANAGER:` 开头,一行一个节点或检查),末尾是编译时量到的一次检查耗时 `Guard eval latency = … us`;`TORCH_LOGS=verbose_guards` 再给每条检查附上它在追踪时被加进来的调用栈,查「这条到底是谁读出来的」。`TORCH_LOGS=recompiles` 每次重编打一段 `Recompiling function … triggered by the following guard failure(s):`,下面每份旧结果一行,形如 `0/0: tensor 'x' size mismatch at index 0. expected 3, actual 4`;`recompiles_verbose` 列出每份旧结果所有不成立的检查。每次调用的检查耗时在 profiler 里是 `TorchDynamo Cache Lookup` 事件,拿它和整个函数的耗时比,决定值不值得砍。tlparse 报告里每份编译结果都有 guard 树与耗时,每次重编都有原因。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 推理服务,权重与模块属性上线后不再改,输入按几档分桶 | `torch._dynamo.config.install_free_tensors = True`,`model.compile(options={"guard_filter_fn": torch.compiler.skip_guard_on_all_nn_modules_unsafe})`;每档预热到不再重编,再在服务循环外包 `torch.compiler.set_stance(skip_guard_eval_unsafe=True)` | 用「模块被改了也不会发现」换最低的每次调用开销;漏预热的一档会直接报错而不是悄悄重编 |
| 训练,会切 train 与 eval、会改模块属性 | 保留默认检查;先试 `torch._dynamo.config.use_recursive_dict_tags_for_guards = True`;步数、学习率这类每步变的数改成张量 | 正确性不打折,只拿字典版本号的快路径省开销;计数器改张量要动代码 |
| CI 或排查重编 | `torch._dynamo.config.error_on_recompile = True`,或 `TORCH_LOGS=recompiles_verbose,guards` | 预热之后出现的任何重编都立即暴露;日志量大,只在排查时开 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 编译后单步反而比 eager 慢,尤其是小模型 | profiler 里 `TorchDynamo Cache Lookup` 占整步多少 | 占比可见时,先试字典版本号快路径,再考虑砍模块检查加 `install_free_tensors` |
| 每一步都重编 | `TORCH_LOGS=recompiles` 的原因是不是某个模块属性、全局变量或默认参数里的数的值 | 整数属性开 `allow_unspec_int_on_nn_module`,或改成张量;浮点数改成张量 |
| 重编原因是 `BACKEND_MATCH failure` | 是不是每次编译前都新建了一个后端函数对象(比如在循环里写 lambda) | 复用同一个后端对象 |
| 原因写着 `Cache line invalidated because … got deallocated` | 被按身份记下的对象(模块、函数)是不是被回收后重建了 | 让它常驻;反复重建的对象无法复用编译结果 |
| 修掉一个重编原因,又冒出另一个 | 默认日志只报每份结果的第一条 | 开 `recompiles_verbose` 一次看全 |
| 开了 `skip_guard_eval_unsafe` 后报 `Recompilation triggered` | 是不是有一档输入没预热到 | 补齐预热,或这一档不进这个上下文 |
| 编译后给模块挂了钩子却不生效 | 模块上的空钩子字典默认不检查 | 编译前挂好钩子,或挂完 `torch.compiler.reset()` 重新编 |

## 六、常见误区

**「guard 开销就是比张量形状。」** 张量检查最显眼,打印出来一眼就看到,所以大家以为贵在它。官方文档的判断是开销大头在取值:沿着 self 一级级取子模块、取属性。所以官方把「丢掉模块上的检查」列为降开销最有效的一项,而不是去动张量检查。

**「重编日志列出的就是全部原因。」** 日志一行一条,看起来像完整清单。实际上每份旧的编译结果只报它第一条不成立的检查;第一条修好了,第二条下次才出现。`recompiles_verbose` 能列全,但要记得运行时并没有真去跑那些排在后面的检查。

**「带 unsafe 的过滤函数最坏就是多重编几次。」** 直觉上少查几项顶多判错成「不过」。方向正好相反:被丢掉的检查永远不会失败,状态变了也判成「过」,跑的是旧图,结果静默出错。它们只适合预热后状态确实冻结的场景。

**「`skip_guard_eval_unsafe` 等于完全不查。」** 名字读起来像跳过全部检查。实际还跑一小组区分已有几份结果所需的检查(张量检查,加上以前失败过的分支);新输入如果需要重编会直接报错。危险的是另一种情况:新输入恰好通过了这一小组、却不满足被跳过的条件,那就静默用错。

**「编译后改模块,guard 一定能发现。」** 默认检查确实覆盖了读过的模块属性,所以大家以为改什么都会重编。但原本为空的钩子字典默认不查,编译后挂上的钩子在编译结果里不会执行;反过来,关掉模块检查的过滤函数之后,连 `training` 这类属性变了也不会发现。

**「把步数、学习率放在模块属性上,编译器会自动当变量处理。」** 张量形状有自动动态,人们以为数也一样。模块上的整数属性默认按值记,每步一变就每步重编,撞上限后新出现的值都走 eager(01 章;官方文档里就是这个例子)。改成张量,或打开 `allow_unspec_int_on_nn_module`。
