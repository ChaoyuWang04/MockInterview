# 一次编译的形状

这一页回答一件事:torch.compile 到底在什么时候编译、编译出来的东西存在哪、下一次调用怎么决定用不用它。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

编译器要的是一张固定的图,Python 程序给不了。同一个函数,这次输入是 512 长、下次是 1024 长;这次走 if 分支、下次走 else;训练到一半有人改了一个全局开关。图是按某一次调用的样子抓下来的,只在那一次的条件下成立。

于是两头都会骨折。**编一次就假定永远成立**,条件一变,跑的还是旧图,结果静默出错;**每次调用都重编**,一次编译从秒级到分钟级,特别大的模型可达小时级,编译时间把省下来的那点 kernel 时间吃得干干净净。

还有第三个约束让事情更难:不能要求用户改代码。模型是现成的 Python,编译器得接受它本来的样子。

所以这一章的问题是:**一份编译结果以什么为单位保存、在什么条件下复用、条件不成立时怎么办。**

## 二、解法

最天然的直觉就是函数缓存:把「这次调用成立的条件」当键,把编译结果当值存起来,下次先查键。torch.compile 就是这么做的,只是键和值都比普通缓存讲究。

![一个函数的编译缓存:调用 f 时帧先被截下,依次检查挂在 code object 上的缓存条目,每条是一棵 guard 检查树加一段改写后的字节码,最近命中的排最前;命中就执行改写后的字节码,它调用编译好的图,前向 kernel 首次调用时已编好,反向 kernel 默认等第一次反向才编;全部不过时,未满 8 条就重新抓图编出新条目插到最前,已满 8 条就不再编译,这次走 eager 而已有条目照用](/opensource/torch-compile/01a-cache-on-code-object.svg)

**缓存挂在哪。** 不挂在函数对象上,挂在函数的 code object 上,也就是 Python 编译出来的那份字节码。同一个函数不管被调多少次、被多少个包装引用,共用同一份缓存。

**一条缓存条目是什么。** 两样东西:一棵 guard 检查树,记着这份结果成立的全部前提(输入的类型、形状、步长、设备,读过的全局变量,模块上的属性);一段改写后的字节码,它替原函数执行:调用编译好的图、把抓图期间记下的副作用重放一遍、返回结果。编译产物并不是替换掉整个函数,而是一段「新版本的函数体」,里面嵌着对编译图的调用。

**每次调用怎么走。** 函数的帧在执行前被 C++ 写的钩子截下,按顺序逐条查缓存:某条的 guard 全过,就执行它那段字节码,并把它挪到最前,下次最先查;全不过,才回到 Python 调 Dynamo 抓图编译,编好的新条目插到最前。同一个函数默认最多存 8 条(准确的计法见第三节);满了之后不再编译,已有条目照常命中,对不上的输入直接按 eager 跑。

**编译发生在调用那一刻,而且分两次付账。** 给函数套上编译,什么都不会发生;第一次调用时才抓图、提反向、生成前向 kernel。反向图在这时已经切好,但默认要等第一次真正跑反向时才交给 Inductor 生成代码;只有反向要用到符号形状时,才在前向编译时一并编掉。所以训练的第一步会慢两次:前向慢一次,反向再慢一次。

**为什么实际不吃亏。** 稳态下训练与推理的输入条件几乎不变,几乎每次都命中排在最前的那一条;guard 检查在 C++ 里跑,不回到 Python。真正的代价集中在编译的那几次,只要重编译不失控,它就是一次性成本。

## 三、代价

**冷启动慢。** 官方给的范围是常见模型从秒级到分钟级,特别大的模型可达小时级。磁盘缓存能让同一台机器上的热启动快很多,冷启动躲不掉(16 章)。

**不止慢第一次。** 官方文档的说法是「前一两次调用」要付编译费。第二次常见的来源是形状:第一次按具体形状编,第二次长度一变,就重编一份把这一维换成符号(06 章)。再加上训练第一步的反向单独编一次,前几步的耗时和稳态差得很远,做性能测试时不跳过这几步,结论会整体偏慢。

**每次调用都要查 guard。** 条件记得越多,查得越久。一步计算很重时这点开销看不见;函数很小、调用很密时,它会占到可见的比例(04 章)。

**8 条额度怎么数。** 缓存按 code object 存,于是在循环里动态生成的多份同名函数、对同一个函数的多次编译调用,都挤在同一份缓存里。计数时只数「按身份钉住的对象和这次调用相同」的条目:同一个模块类的多个实例共用一份前向代码,编译结果若按身份钉住了模块实例,每个实例各有 8 条;不分对象的总条目数另有 256 条的上限。没有按身份钉住任何对象时,就是整个函数共 8 条,互相挤占。有一个选项能让每次编译调用各算各的额度。

**撞上限不报错,只是悄悄变慢。** 满 8 条之后,新条件下的调用静默回到 eager,只在日志里打一条警告。要求整个函数成一张图的模式下则相反,撞上限直接报错。

**包装的方式会改变模块的外观。** 把模块整体交给编译入口,拿到的是一个包着原模块的新模块,参数名前面多一层前缀,存下来的 checkpoint 和没编译的模型对不上;官方推荐直接在模块上调它自带的编译方法。DDP、FSDP 这类分布式包装也不适合整个包进去编译,官方建议编译里面那个模块。

## 四、和同类大厂框架不一样的地方

对照对象是 JAX 的即时编译(背后是 XLA),Google 在大规模训练与推理里用的就是这一套。两边都是「首次调用时编译、结果缓存、条件变了重编」,差别在抓图方式和缓存键。

| | torch.compile | JAX 的即时编译 |
|---|---|---|
| 怎么抓图 | 不执行函数,在字节码层面逐条模拟;张量换成只带元信息的假张量 | 把函数真跑一遍,参数换成只带形状和类型的追踪对象,记下每个操作 |
| 分支依赖张量的数值 | 断图:前半段成图,那一句 eager 执行,后半段接着抓,结果正确但图变碎 | 直接报错,要改写成结构化的控制流 |
| 缓存键 | 函数的 code object 加上一整套 guard:张量元信息、全局变量、模块属性都可能在里面 | 函数本身,加上输入的形状与类型,以及标成静态的参数的取值 |
| 形状变了 | 默认第一次特化,晃过一次就换成符号,之后同类变化不再重编 | 每遇到一个新的形状或类型就重新编译 |

一句话:JAX 让用户按编译器的规矩写代码,换来可预测;torch.compile 接受任意 Python,换来的是 guard 与断图这两套额外机制,以及它们带来的不确定。

## 五、调参与观测

这一章的参数分三处:编译入口的具名参数(改了要重新包一次);运行期可以随时切换的编译姿态;全局配置与环境变量。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `mode` | `torch.compile` / `Module.compile` | `default` | `reduce-overhead` 开 CUDA graph;`max-autotune` 再加矩阵乘调优,编译明显变长 | `torch._inductor.list_mode_options()` 看每种打开了什么 |
| `fullgraph` | 同上 | `False` | `True`:一处断图就报错;撞重编译上限也报错而不是回 eager | 报错信息直接指到断图的那一行 |
| `dynamic` | 同上 | `None` | `True` 一开始就尽量符号化;`False` 永远按具体形状编 | `TORCH_LOGS=dynamic` |
| `backend` | 同上 | `inductor` | `eager` 只抓图不编译,`aot_eager` 再加 AOTAutograd;用来二分是哪一段出的问题 | `torch._dynamo.list_backends()` |
| `recompile_limit` | 同上 | `None`,即用全局值 | 只对这一次编译调用生效的上限 | 日志 `torch._dynamo hit config.recompile_limit` |
| `isolate_recompiles` | 同上 | `False` | `True`:这次编译调用的新条目单独计额度,不和同一函数的其他编译调用互相挤 | — |
| `disable` | 同上 | `False` | `True`:编译入口变成空操作,用来对照 eager | — |
| `torch._dynamo.config.recompile_limit` | Python 里改全局配置 | 8 | 调大:更多条件各有一份编译结果,也更多次编译;先查为什么重编,再决定调不调 | 同上那条日志 |
| `torch._dynamo.config.accumulated_recompile_limit` | 同上 | 256 | 同一个 code object 上不分对象的条目总数上限;`recompile_limit` 只数按身份钉住同一批对象的条目 | 同上那条日志,`limit_type` 不同 |
| `torch._dynamo.config.fail_on_recompile_limit_hit` | 同上 | `False` | `True`:撞上限直接报错,不再静默回 eager | 抛 `FailOnRecompileLimitHit` |
| `torch.compiler.set_stance` | 运行期随时调用,也能当上下文或装饰器 | `default` | `force_eager` 忽略所有编译;`eager_on_recompile` 需要重编时改走 eager;`fail_on_recompile` 需要重编时报错;`eager_then_compile` 第一次 eager、之后再编 | 行为立刻变化,不用重新包 |
| `torch.compiler.reset()` | 运行期调用 | — | 清掉进程内的编译缓存;磁盘缓存不动 | 下一次调用重新编译 |
| `TORCH_COMPILE_DISABLE` | 环境变量 | 未设 | 设成 `1`:整个进程的编译都关掉 | — |
| `TORCHINDUCTOR_COMPILE_THREADS` | 环境变量 | CPU 核数与 32 取小 | 设成 `1`:不再用子进程并行编 kernel,调试时断点好打,编译变慢 | 日志 `compile_threads set to` |

**观测三处。** 编译了几次、为什么:`TORCH_LOGS=recompiles` 每次重编打一行原因,`guards` 打出每条缓存条目的全部条件。编译花在哪:`torch._dynamo.utils.compile_times()` 按阶段汇总 Dynamo 的耗时,`TORCH_COMPILE_DEBUG=1` 再带上 Inductor 各阶段与产物。整体报告:设 `TORCH_TRACE` 指向一个目录(只设 `TORCH_COMPILE_DEBUG=1` 时也会自动落一份),再用 tlparse 汇总成网页,每一次编译、每一处断图、每一次重编都在里面。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡或 DDP 训练,输入形状固定 | 先 `model.compile(fullgraph=True)` 跑几步确认没有断图,再去掉 `fullgraph`;用 DDP 时先编译再包 | 用前几步的编译时间换稳态吞吐;`fullgraph` 只在排查阶段开,换来断图立刻暴露 |
| 小批量推理,形状固定或已分桶 | `model.compile(mode="reduce-overhead")` | 用常驻的 CUDA graph 内存池换掉每步的 CPU launch 开销 |
| 变长输入,不想每个长度编一次 | 进编译前对长度那一维调 `torch._dynamo.mark_dynamic`,或用 `torch.compiler.set_stance("eager_then_compile")` 让第一次调用走 eager,从前两次调用推断哪些维是动态的 | 用符号形状的 kernel(可能略慢于特化版本)换掉按长度重编 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 前几步特别慢,之后正常 | 是不是第一步的前向和反向各编一次,第二步又因形状重编一次 | 正常现象;测性能时跳过前几步,或用磁盘缓存预热 |
| 跑着跑着突然变回 eager 的速度 | 日志里有没有 `hit config.recompile_limit` | 用 `TORCH_LOGS=recompiles` 找重编原因,先消原因,再考虑调上限 |
| 每一步都在编译 | `TORCH_LOGS=recompiles` 的原因是不是在变的张量形状或 Python 数值 | 形状标动态;把在变的 Python 数值改成张量或移出编译区域 |
| 编译后加载 checkpoint 报键名不匹配 | 键名是不是多了 `_orig_mod.` 前缀 | 改用 `model.compile()`,或存取时用原模块 |
| 想确认编译到底有没有生效 | `set_stance("force_eager")` 对照一次 | 两次耗时几乎一样,说明图碎或一直在重编,查 `graph_breaks` 与 `recompiles` |
| 调试时断点进不去生成的 kernel 编译 | 编译在子进程池里做 | 设 `TORCHINDUCTOR_COMPILE_THREADS=1` |

## 六、常见误区

**「套上编译的那一刻就编译了。」** 人们这么以为,是因为很多编译器都是先编后跑。这里套上只是装了个钩子,第一次调用才抓图编译;还没调用就测速,测的是 eager。

**「只有第一步慢。」** 因为编译听起来是一次性的事。实际上第一步的反向默认要等反向真正开始才编,第二步如果长度变了还会因为自动动态形状重编一次,官方文档自己写的就是「前一两次调用」。

**「超过 8 次重编,整个函数就回 eager。」** docstring 里的说法容易让人这么理解。实际是满了之后不再编新的,已经编好的 8 份照样命中,只有对不上它们的那些输入走 eager。所以症状是「部分输入慢」而不是全慢,更难察觉。

**「`torch.compile(model)` 和 `model.compile()` 是一回事。」** 前者返回一个包着原模块的新模块,原模块被注册成它的子模块,参数名全多出 `_orig_mod.` 前缀,checkpoint 键名对不上;注册了全局模块钩子时,钩子还会多触发一次。后者在原模块上改自己的调用入口,模块外观不变,是官方推荐的写法。

**「重编译上限是按函数对象算的。」** 实际缓存按 code object 存,额度按「钉住的对象是否相同」分开数。循环里用同一段代码生成的多个闭包、同一个函数被多次编译,只要没有按身份钉住不同的对象,就共用同一份 8 条额度,互相挤占;反过来,同一个模块类的多个实例各算各的,总数到 256 为止。想让某次编译单独计额度,要显式打开 `isolate_recompiles`。

**「把 DDP 或 FSDP 包好的模型整个拿去编译最省事。」** 官方文档明说编译不擅长处理这些分布式包装,建议编译里面那个模块,再交给包装。

**「清缓存就要从头编。」** `torch.compiler.reset()` 只清进程内的缓存,Inductor 的磁盘缓存还在;下一次调用要重新抓图,但后端产物常常能直接从磁盘取。反过来,想测真正的冷启动,光调它不够,还得让磁盘缓存失效。
