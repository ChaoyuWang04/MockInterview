# Triton 代码生成与调优

这一页回答一件事:调度器定下一个融合 kernel 装哪些节点之后,Inductor 怎么把它写成一段 Triton 代码、块开多大、由谁按什么顺序调用。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

哪些节点合进同一个 kernel,10 章已经定了。合完不等于快:同样一段融合后的循环,块切得不合形状,照样跑不快。

块太小,一个 program 只处理 128 个元素,访存不够宽,启动的块数又多;块太大,每个线程要握住的寄存器变多,溢出到本地内存,或者一个 SM 上只能驻留很少的块,延迟藏不住;形状不是 2 的幂时,最后一块有一截是掩码掉的空转。归约更麻烦:每行 768 个元素,一次读进块里就能算完;每行 50000 个,一次读不下,只能分段累加;只有 1 个输出、却要归约上亿个元素时,整件事落在一个块上,GPU 绝大部分 SM 闲着。

难处在于编译器事先不知道哪种切法最快。它取决于卡的型号、数据类型、内存布局,文档里没有公式;把所有可能都实测一遍,又会把首次运行拖到不可接受。

所以这一章的问题是:**给定一组已决定合并的循环节点,怎么把它们对齐到同一套下标上写成一个 kernel,选出合适的切块方式和块大小,而且挑选的代价只付一次。**

## 二、解法

最天然的直觉就是照着手写 Triton 的人去做:先定一个 program 负责哪一块下标,把每个节点的计算写成对这块下标的读、算、写;块大小凭经验列几组,真跑一下,留快的那组。Inductor 的代码生成就是这么做的,只是每一步都自动化了。

![一个融合 kernel 怎么切块的示意。左栏是逐元素 kernel:4096 乘 768 的连续张量摊平成一维,切成等长的块,每块交给一个 program 并行,候选有两组,块大小 1024 配 4 个 warp 共 3072 块,或块大小 512 配 8 个 warp 共 6144 块,第一次调用各跑一遍留快的。中栏是持久化归约:按行求和,每行 768 列,一个 program 负责 1 行,一次把整行读进块里,归约块取 768 向上的 2 的幂 1024,多出的 256 个位置被掩码,只有 1 组候选,不实测。右栏是循环归约:每行 50000 列,一个 program 负责 1 行,沿归约方向每次读 2048 个、累加进与块同形的累加器,循环 25 次,最后一次只有 848 个有效,默认 1 组候选,寄存器压住占用率时再加一组把归约块减半到 1024 实测比较。底部是挑选的时间线:编译期按形状与归约方向列出 1 到 6 组候选并在子进程里逐组预编译;第一次调用用真实输入逐组实测,原地改写的参数先备份,寄存器溢出超过 16 个的淘汰;留下最快的一组并写进调优缓存;之后的调用直接用这一组,输入形状变了也不重挑;可选的坐标下降从选中的那组出发,把每个块大小或 warp 数乘 2、除 2 试跑,快 0.1% 以上才换](/opensource/torch-compile/11a-tiling-and-autotune.svg)

**先把迭代空间对齐。** 每个节点带着自己的循环形状和下标函数(09 章),kernel 这一侧最多有 3 个逐元素轴和 2 个归约轴,默认只用一个逐元素轴 x 加一个归约轴 r。代码生成器把每个节点的循环维度按顺序填进 kernel 的轴:某一维比当前轴剩下的长度大,就拆成两段跨进下一个轴;拆不整除,或者填完还剩下不为 1 的长度,就判定这个节点放不进这套轴。10 章说的「分块方式对不上就不合」,问的就是这件事。

**再决定切成一维还是二维。** 默认所有逐元素维摊平成一个轴。只有当某次读或写的连续方向不在最后一维(典型是转置),只用一个轴总有一方的访存不合并,才考虑切成两个轴,让读和写各自沿自己的连续方向成块。候选切法按涉及的元素数打分,写的分数翻倍,两段长度合适再翻倍,取第一个所有节点都放得进的。默认还开着一项合并访存分析:对每次读写找出让地址连续的那个循环变量,按字节估分,再建议要不要多切一刀。归约默认不切成多维。

**节点在循环里怎么排。** 含归约的 kernel,每个节点要么放进归约循环体里(与归约同形,或者逐元素形状正好等于输出数乘归约长度),要么放在循环之后(形状只剩输出那一维,比如拿归约结果去做除法)。遇到要用前一个归约结果的节点,就先关上当前循环,在后面另开一个。所以循环归约写成的 softmax,生成代码里通常是一个循环求最大值和分母,再一个循环重读输入、写出结果。

**下标函数展开成语句。** 分两遍:第一遍跑一遍所有节点,收集用到的全部下标表达式,供化简和决定能否原地写;第二遍逐个节点执行循环体,每一次读、每一个算子、每一次写都翻译成一行 Triton 语句。同一个表达式由公共子表达式消除只生成一次;每次读都带上越界掩码;半精度浮点的归约先提升到单精度再累加。kernel 名里带着类别与被合进来的算子名,源码完全相同的两个 kernel 只定义一次。

**归约有三种写法,按长度挑。**

- **持久化归约**:整行一次读进块里,只归约一次,不写循环。归约块取归约长度向上的 2 的幂,768 就开 1024,多出的 256 个位置掩码。门槛是归约沿连续方向时长度不超过 1024,其他方向不超过 64 且长度的上下界相同
- **循环归约**:块沿归约方向走,每步读一段,累加进与块同形的累加器,循环结束再在块内归约一次。长度没有上限,代价是多一层循环和一份累加器
- **输出太少时拆开**:以沿连续方向的归约为例,输出个数不到 SM 数的 2 倍、归约长度又超过门槛(Blackwell 之前是 8192)时,降级阶段就把它拆成两级,先并行算出部分结果写到显存,再用第二个 kernel 归约一次。另有一种协作归约,多个线程块在一个 kernel 里跨块同步地合作,默认关

**块大小:启发式列候选,第一次调用实测。** 生成的 kernel 源码上方有一个装饰器,写着每一维的长度提示(提示值向上取 2 的幂)、归约方向,以及 kernel 的读写次数这类元信息;模块加载时,装饰器按这些信息生成候选配置。默认模式下,一维逐元素 kernel 给 2 组;二维逐元素 kernel 给 6 组,但只有一个输入一个输出的二维 kernel 只给一组正方形块;归约方向明确的归约通常只给 1 组,方向不明的给 6 组。每组候选在编译子进程里先编好,编不过资源检查的丢掉。第一次真正调用时,若还剩不止一组,就用这次的真实输入逐组计时:会被原地改写的参数先备份,免得试跑污染数据;寄存器溢出超过 16 个的直接判负。最快的一组留下,其余丢弃,结果写进调优缓存(见 16 章),之后的调用直接用它启动。

**两处补救。** 循环归约编完后,如果每个线程用的寄存器多到压低了占用率、而块数又多到一轮排不下,就再加一组把最大的归约块减半,一起实测。另有一个可选的坐标下降:从选中的那组出发,把每个块大小和 warp 数各试乘 2、除 2,快过 0.1% 才换,一轮轮做到没有改进为止;每试一组都要现编一个变体。

**多个互不依赖的 kernel 拼成一个。** 10 章决定了哪些互不依赖的 kernel 要横向拼接,拼接本身在这里生成:每个子 kernel 照常生成自己的循环体,再一起包进一个 kernel,开头按 program 编号分派,前一段编号交给第一个子 kernel,用满再交给下一个;子 kernel 大小相近、掩码浪费不到 20% 时改成轮流分派。一组对列表逐项做同样运算的节点也走这条路。

**最后是一段 Python 包装代码。** 整张图生成一个 Python 模块:开头逐个声明 kernel,把源码交给异步编译,等全部编完;然后是一个调用函数,按调度器排好的顺序分配输出缓冲、算出每个 kernel 的启动网格并启动、在中间调用外部 kernel(矩阵乘默认走外部库,模板路径见 12 章)、释放不再用的缓冲、返回结果。

**为什么实际不吃亏。** 被融合的大多是访存受限的逐元素与归约,块大小在一个较宽的区间里效果接近,少量候选就能落在好区间里;挑选只付一次,稳态下直接走缓存好的启动路径;调优结果还能落盘复用。

## 三、代价

**调优发生在运行时,而且是第一次调用那一刻。** 默认的 Python 包装下,编译结束时块大小还没定,第一次真正跑到这个 kernel 才实测。训练的第一步前向、第一次反向都会各付一次,和 01 章说的「编译分两次付账」叠在一起;多组候选的 kernel 越多,首步越慢。开坐标下降后,每个 kernel 还要额外现编、现测若干变体。

**实测会抬高显存。** 会被原地改写的参数要先克隆一份再试跑;推理图和反向图里,克隆会超出历史峰值留下的余量时改为拷到 CPU、每跑一次再拷回来,换成更慢的调优;训练的前向图不做这层节省,克隆直接占显存。

**按第一次的输入定终身。** 挑选只做一次,用的是第一次调用的真实输入。动态形状下,同一个 kernel 之后跑的所有长度都用这一组块大小;长度提示取的也是提示值(06 章),不是之后实际遇到的长度。

**默认候选很少,启发式就是全部决策。** 方向明确的归约、持久化归约、只有一进一出的二维逐元素 kernel,默认都只有 1 组候选,根本不实测。启发式选错了,默认模式下没有第二次机会。

**计时有噪声。** 两组耗时接近时,不同进程可能选出不同的组,归约块不同意味着累加顺序不同,数值会有末位差异。要求确定性的模式为此关掉了归约块大小的调整。

**块大小不合形状照样浪费。** 768 开到 1024,四分之一的通道空转;50000 按 2048 一段切,最后一段只用了 848 个。这是 2 的幂块和任意形状之间躲不开的损耗,形状本身不友好时,调优只能在几种浪费之间选一种。

## 四、和同类大厂框架不一样的地方

对照对象是 XLA 的 GPU 后端与 TensorRT。前者是 JAX 背后的编译器,把部分融合交给 Triton、其余自己直接生成 LLVM IR;后者是 NVIDIA 的推理优化器,构建引擎时对每层的多种现成实现逐个计时。三家都要回答「生成什么、块多大、什么时候挑」。表中关于 XLA 与 TensorRT 的每一格,都能在它们官方文档的原文里找到。

| 问题 | Inductor | XLA 的 GPU 后端 | TensorRT |
|---|---|---|---|
| kernel 从哪来 | 每个融合都现生成一段 Triton 源码 | 含矩阵乘或 softmax 的融合转成 Triton IR 交给 Triton;归约、转置等直接生成 LLVM IR | 不生成源码,从预先写好的多种实现里挑 |
| 什么时候实测挑选 | 默认在第一次调用时,用真实输入 | 编译期,为 Triton 融合调分块参数 | 构建引擎时,每层把可用实现逐个计时,选最快的 |
| 结果怎么复用 | 调优缓存,见 16 章 | 可指定一个目录,每个融合一份结果文件,默认关;失效要用户自己管 | 计时缓存记下每种层配置下各实现的耗时,遇到相同配置直接复用 |
| 变长输入 | 只按第一次调用的输入挑一次 | 文档没有写调优与变长输入的关系,不作比较 | 按优化配置里指定的那组形状调,最小到最大之间都能跑 |
| 挑选能否复现 | 计时接近的候选,不同进程可能选得不一样 | 文档没有涉及,不作比较 | 文档明说耗时接近时不同次构建可能选不同实现,建议锁频、加平均次数、复用计时缓存 |

一句话:TensorRT 和 XLA 都把挑选放在编译或构建那一步,部署时拿到的是定稿;Inductor 把它推迟到第一次调用,换来不用事先知道输入,代价是首次运行慢,并且结果绑定在那一次的输入上。

## 五、调参与观测

这一页的参数分三处:Inductor 全局配置 `torch._inductor.config`,在 Python 里改,对之后的编译生效,也可以用 `torch.compile(..., options={...})` 只作用于一次编译调用;`mode="max-autotune"` 与 `"max-autotune-no-cudagraphs"` 会顺带打开 `max_autotune` 和 `coordinate_descent_tuning`;带环境变量的键在导入时读取,要在进程启动前设好。候选配置是编进生成代码里的,改了配置要让它重新编译(缓存命中时照用旧结果,见 16 章)。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `max_autotune_pointwise` | 全局配置或 `options`;`TORCHINDUCTOR_MAX_AUTOTUNE_POINTWISE=1` | `False` | `True`:归约不再按方向只留 1 组,拿到完整的 6 组候选;一维逐元素仍是 2 组 | `+inductor` 日志里 `CachingAutotuner gets N configs` |
| `max_autotune` | 同上;`TORCHINDUCTOR_MAX_AUTOTUNE=1`;两种 max-autotune 模式 | `False` | 包含上一条,另开矩阵乘调优(12 章) | 同上 |
| `coordinate_descent_tuning` | 同上;`TORCHINDUCTOR_COORDINATE_DESCENT_TUNING=1`;两种 max-autotune 模式 | `False` | `True`:选中后再逐个维度乘 2、除 2 试跑,首次运行明显变长 | `+inductor` 日志 `COORDESC:` 每试一组一行,最后一行 `Improve from ... Nx` |
| `coordinate_descent_search_radius` | 同上;`TORCHINDUCTOR_COORDINATE_DESCENT_RADIUS` | `1` | 调大:每一维一次试更多档,变体更多 | 同上 |
| `coordinate_descent_check_all_directions` | 同上;`TORCHINDUCTOR_COORDINATE_DESCENT_CHECK_ALL_DIRECTIONS=1` | `False` | 逐维找不到改进时,再把多维一起改的组合全试一遍 | 日志 `found improvement ... by looking in all directions` |
| `triton.autotune_pointwise` | 全局配置或 `options` | `True` | `False`:逐元素 kernel 只留 1 组,不再实测 | 同第一行 |
| `triton.persistent_reductions` | 同上;`TORCHINDUCTOR_PERSISTENT_REDUCTIONS` | `True` | 关掉:所有归约都写成循环 | kernel 名 `triton_per_` 与 `triton_red_` 的比例 |
| `triton.multi_kernel` | 同上;`TORCHINDUCTOR_MULTI_KERNEL` | `0` | `1`:持久化与循环两版都生成,运行时实测挑;持久化门槛放宽到 16 倍 | 生成代码里的 `async_compile.multi_kernel(...)` 声明 |
| `split_reductions` | 同上;`TORCHINDUCTOR_SPLIT_REDUCTIONS` | `True` | 关掉:输出很少的长归约不再拆成两级,并行度下降 | 生成代码里同一归约是 1 个还是 2 个 kernel |
| `triton.cooperative_reductions` | 同上;`TORCHINDUCTOR_COOPERATIVE_REDUCTIONS=1` | `False` | 打开后输出很少的长归约改用跨块协作归约,两级拆分自动让位 | kernel 参数里有 `RSPLIT` |
| `dynamic_scale_rblock` | 同上;`TORCHINDUCTOR_DYNAMIC_SCALE_RBLOCK` | `True` | 关掉:循环归约不再按寄存器占用补一组减半的候选 | `+inductor` 日志 `Dynamically scale down` |
| `triton.spill_threshold` | 全局配置或 `options` | `16`(ROCm 上 `32`) | 调小:溢出寄存器的候选更早被淘汰 | INFO 日志 `Skipped M/N configs ... register spilling` |
| `triton.max_tiles` | 同上 | `None`(按分析路径取 2 或 3) | `1`:不再切成二维,转置类访存全部走一维 | `perf_hints` 日志 `possibly bad tiling` |
| `triton.coalesce_tiling_analysis` | 同上;`TORCHINDUCTOR_COALESCE_TILING_ANALYSIS` | `True` | 关掉:退回按步长为 1 的维度打分的老办法 | kernel 是否带 `y` 维 |
| `triton.tile_reductions` | 同上 | `False` | `True`:归约也允许切成多维 | `perf_hints` 日志 `Reduction over non-contiguous dims` 提示可以开它 |
| `triton.autotune_at_compile_time` | 同上;`TORCHINDUCTOR_AUTOTUNE_AT_COMPILE_TIME` | `None`:Python 包装在首次调用时调,AOTInductor 编译时调 | `True`:编译阶段用生成的随机输入调完 | 编译耗时与首次调用耗时此消彼长 |
| `combo_kernels` | 同上 | `False` | `True`:互不依赖的 kernel 拼成一个;一个最多装 `combo_kernel_max_num_nodes`(默认 `8`)个子 kernel | 生成代码里 kernel 数 |
| `benchmark_kernel` | 同上;`TORCHINDUCTOR_BENCHMARK_KERNEL=1` | `False` | 每个 kernel 文件末尾附带单独测速入口 | 直接运行 kernel 文件,打印耗时与带宽 |
| `deterministic` | 同上;`TORCHINDUCTOR_DETERMINISTIC=1` | `False` | 跳过影响数值的设备端实测,归约块与 warp 数不再调 | 两次运行结果逐位一致 |

**观测四处。** 生成了什么:`TORCH_LOGS=output_code` 打印整个包装模块,`kernel_code` 按 kernel 打印;每个 kernel 上方的装饰器里写着长度提示、归约方向和候选来源,`triton_poi_`、`triton_red_`、`triton_per_` 分别是逐元素、循环归约、持久化归约。挑了哪组:`TORCH_LOGS="+inductor"` 打开调试级日志,看得到 `Best config for triton_...: XBLOCK: ..., num_warps: ...` 与每组的寄存器数、溢出数;设 `TORCHINDUCTOR_DUMP_LAUNCH_PARAMS=1` 会把每次启动的块大小、warp 数与网格追加到运行脚本旁的 `.launch_params` 文件。切块可疑:`TORCH_LOGS=perf_hints` 会报 `possibly bad tiling` 和归约沿非连续维的提示。首次调用花在哪:tlparse 与 `compile_times()` 里的 `CachingAutotuner.benchmark_all_configs` 与 `CachingAutotuner.coordinate_descent_tuning` 两项;单个 kernel 慢,按官方的 GPU 性能分析页把它的文件单独拿出来跑,再加 `TORCHINDUCTOR_MAX_AUTOTUNE=1` 对照。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 长时间跑的训练,归约多(norm、loss),能接受首步更慢 | `options={"max_autotune_pointwise": True, "coordinate_descent_tuning": True}` | 用首步更长的实测时间,换归约 kernel 的块大小从 1 组启发式变成实测加局部搜索 |
| 推理服务,冷启动要短、要可复现 | 默认模式,再设 `TORCHINDUCTOR_DETERMINISTIC=1`,上线前用固定形状预热 | 放弃归约块的调整和部分实测,换每个进程选到同一组配置 |
| 输入很长、输出很少的归约慢(全局求和、小批量的损失) | 默认的两级拆分之外,试 `options={"triton.cooperative_reductions": True}` 对照 | 用跨块同步的开销,换掉第二个 kernel 与中间结果的一次读写 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 第一步比第二步慢很多,编译早已结束 | `compile_times()` 里 `benchmark_all_configs` 的耗时 | 正常现象;测性能时跳过前几步,或让调优缓存预热(16 章) |
| 某个归约 kernel 占了大头 | `output_code` 里它的装饰器:是不是只有 1 组候选、归约方向是什么 | 开 `max_autotune_pointwise` 或 `coordinate_descent_tuning` 对照;方向不对再看切块日志 |
| 首次调用时显存溢出,稳态下不会 | 那个 kernel 是否原地改写大缓冲(优化器更新一类) | 调优时要克隆这些缓冲;先用小一些的批跑通,或关掉它的调优(`triton.autotune_pointwise=False`) |
| 同一模型两次运行结果末位不同 | 两次 `Best config` 日志里同一归约的块大小是否不同 | 需要逐位一致就开 `deterministic` |
| 变长输入下某些长度特别慢 | 这个 kernel 是按哪个长度调的(第一次调用的输入) | 预热时先喂最常见的长度;或按长度分桶,各编一份 |
| 转置类 kernel 带宽很低 | `perf_hints` 有没有 `possibly bad tiling`,kernel 是否只有 x 维 | 确认 `triton.max_tiles` 没被设成 `1`、合并访存分析开着 |

## 六、常见误区

**「只有 max-autotune 才会实测。」** 名字让人以为默认模式全靠猜。实际上默认模式下,只要一个 kernel 有不止一组候选(一维逐元素的 2 组、二维逐元素的 6 组、方向不明的归约的 6 组),第一次调用都会逐组计时。max-autotune 多出来的是给归约补全候选、打开坐标下降,以及矩阵乘调优。

**「开了 max-autotune,逐元素 kernel 就会调得更细。」** 一维逐元素 kernel 在两种模式下拿到的都是同样的 2 组候选;max-autotune 只在它原本被压成 1 组时(关了 `autotune_pointwise`,或只有一进一出的二维 kernel)才把候选放开。逐元素 kernel 慢,真正起作用的是坐标下降,或者回头查切块。

**「编译完成,kernel 就已经调好了。」** 编译结束时装饰器里只有候选;块大小是在第一次调用时才定的。在编译后、第一次调用前做性能测量或录 CUDA graph(13 章),测到或录下的都不是稳态。

**「形状变了会重新调。」** 调优按 kernel 只做一次,用第一次调用的输入。动态形状下,换了长度只是换网格大小,块大小照旧;真正会让它重新挑的,是形状变化触发了重编译、生成了新的 kernel 源码。

**「持久化归约总比循环归约快。」** 它省掉了循环和累加器,但整行要握在寄存器里。长度一大,寄存器溢出、占用率下降,反而慢。门槛(连续方向 1024)就是为此设的;想让两种都生成、运行时实测,用 `multi_kernel`,而不是把门槛调大。

**「坐标下降能找到最优的块大小。」** 它是局部搜索:每次只动一个维度,只试乘 2 和除 2 两档,快过 0.1% 才接受,起点是启发式或实测选中的那组。多个维度要一起变才有改进的情况,它会停在原地;`coordinate_descent_check_all_directions` 能补一部分,代价是试的组数成倍增加。
