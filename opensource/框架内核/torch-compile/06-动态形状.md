# 动态形状

这一页回答一件事:输入的某一维每次都不一样时,torch.compile 怎么用一份编译结果吃下一整段长度,又在什么时候不得不退回按具体数字编。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

按具体形状编出来的图,张量检查会逐维比尺寸(04 章)。第一次是 512,第二次是 513,就不是同一份了。推理服务的 prefill 长度从 1 到 8192 都可能出现,训练的最后一个 batch 往往不满;每来一个新长度就重编一次,一次秒级到分钟级,撞到 8 份的上限后新长度全走 eager(01 章)。把维度写成符号、让一份结果适配多种长度这个思路,知识库 TorchCompile 篇已经讲过;这一章讲它在源码里怎么落地,以及落地时撞上的三块硬骨头。

**代码会拿尺寸做判断。** 「长度超过 1024 走分块实现」「batch 为 1 时跳过某步」这类写法到处都是。维度换成符号以后,这句 if 该走哪一支?随便挑一支,换个长度就可能算错。

**有些大小取决于数据本身。** 掩码里有多少个非零元素、从张量里取出来的一个标量,抓图时根本没有值可看,更谈不上按它分支。默认做法是在这里断图(02 章),检测、稀疏、MoE 路由这类模型因此被切成碎片。

**0 和 1 是特殊值。** 广播、连续性检查、视图变形里到处在问「这一维是不是 1」。把 1 也当成普通符号,这些问题一个都答不出来;把它单独对待,batch 为 1 的请求就会意外触发一次重编。

所以这一章的问题是:**哪些维用符号表示,对符号的判断怎么做才不出错,判断不了的时候怎么办。**

## 二、解法

最天然的直觉是:把「512」换成一个变量 s0,同时记住它这次的实际值;代码对 s0 做判断时,就拿实际值算出答案,并把这个答案记成一条条件,下次输入不满足这条条件再重编。torch.compile 就是这么做的,那个实际值叫提示值。

![一个维度的一生:第 1 次调用 x 形状为 8 乘 64,按具体形状编译并记下尺寸;第 2 次调用形状为 16 乘 64,张量检查不过,重编日志写明第 0 维期望 8 实际 16;尺寸记录合并成问号乘 64,只有晃过的那一维记成问号;重编时第 0 维换成符号 s0,提示值 16,范围从 2 到无穷;抓图时 x.size(0) 大于 1024 这句按提示值判为假并记下 s0 不超过 1024 这条条件,x.size(0) 不等于 0 这句由范围直接得真而不记条件;编完后张量检查跳过第 0 维,形状条件拼成 Python 函数挂在根上最后跑;之后来 512 直接命中,来 1 因不满足大于等于 2 而重编成常量 1,来 3000 因超过 1024 重编出另一份;左下对照取决于数据的大小,取标量得到的无依据符号 u0 没有提示值,对它做 if 判断时推不出真假,就在那里断图](/opensource/torch-compile/06a-life-of-a-dim.svg)

**一次编译一个符号形状环境。** 每次抓图都新建一个符号形状环境,挂在假张量模式上。它登记这次编译里所有的符号:每个符号的名字(输入尺寸的符号以 s 开头,编号由来源名的哈希得出,同一个输入在不同次编译里编号相同;取决于数据的按顺序叫 u0、u1)、提示值、取值范围,以及抓图过程中积累下来的全部条件和已知事实。表达式用 SymPy 表示,整套推理都在 Python 里,没有 C++ 版本。

**哪一维用符号:默认先写死,晃过才换。** 每段代码有一份尺寸记录,按「文件内容的哈希、首行号、函数名」找到这段代码,再按输入的来源名(比如局部变量 x)存它见过的尺寸。每一维只有三种状态:没见过、见过一个具体值、见过两个不同的值(记成问号)。第一次调用把 [8, 64] 记下,各维照常写死;第二次来了 [16, 64],张量检查不过,重编时两条记录合并成 [?, 64],只有第 0 维换成符号,第 1 维仍是 64。这份记录在进程内全局有效,清空 Dynamo 状态时一起清掉。作为参数传进来的 Python 整数走同一套:第一次按值记,值变过一次就换成符号。全局变量里的整数、模块上的整数属性、参数默认值始终按值钉死(03 章);模型参数的形状默认也不参与。浮点数值变过之后同样会被换成符号,但全局配置里打开了 Inductor 的 CUDA graph 时始终按值记。

**用户也可以提前说。** 自动的办法总要多编一次。想省掉它,可以在进编译之前给张量的某一维做标注。标注分强弱:强标注要求这一维最后必须是符号,抓图时被代码写死了就直接报错;弱标注只是建议,被写死也不报错。也可以按来源名给一张名单,名单跨断图仍然有效,还能反过来列一张「必须写死」的名单压住自动动态。编译入口上那个一刀切的开关会让所有维一上来就是符号,这时尺寸相同的维还会共用同一个符号,等于默认它们永远相等。编译入口另有一种声明式写法:逐个参数写清哪一维是变量、变量的上下限以及变量之间的算术关系,没写到的一律写死。这两个入口参数不能同时给。

**0 和 1 不给符号。** 给一个尺寸建符号时,实际值是 0 或 1 就直接返回常量,不建符号;其余值建出来的符号默认范围是 [2, ∞)。官方文档给的理由是:这样广播和连续性检查不用额外加条件。代价是 1 永远自成一份:一维被换成符号之后再来个 1,不满足「至少为 2」,重编时直接按常量 1 编。

**对符号的每一次比较都留下一条条件。** 抓图时代码对符号做判断,符号形状环境先试着不看提示值直接判定:用取值范围和已知事实能推出来的(比如 s0 至少为 2,所以「s0 不等于 0」必然为真),直接返回,不记条件。推不出来的,拿提示值代进去算出真假,把结果记成一条条件:这次 16 不大于 1024,就记「s0 不超过 1024」。若记下的是等式(比如「s0 等于 33」),s0 从此被替换成 33,由它算出来的所有表达式都跟着写死,这一维实际上又变回了静态。编译结束时,这些条件连同每个符号的取值范围,翻译成用输入来源表达的形状条件;张量检查里符号那一维跳过不比,形状条件拼成一个 Python 函数,挂在 guard 树的根上最后跑(04 章)。强标注的维若在这一步被发现只剩一个取值,就在这里报约束冲突。

**取决于数据的大小:无依据符号。** 取出一个标量、一个算子的输出长度取决于数据,在打开相应的捕获之后,结果是一个无依据的符号:它进得了图,能参与算术,能传给算子,但没有提示值。对它的判断只能靠取值范围和已知事实;推不出来,又没有值可代,就报数据依赖的错,Dynamo 在那一句断图,整图模式下直接报错。救法是在前面写一句运行期断言,比如「u0 大于 0」:它既让符号形状环境记住这条事实、收紧取值范围,也作为断言留在图里,运行时真去检查。PyTorch 自己的视图、切片、形状检查这类框架代码已经大面积改写成遇到无依据符号就走通用路径,而不是分支。输入的某一维也可以主动标成无依据:它不再被 0、1 特化,也不能按提示值挑分支,换来一张对所有长度都成立的图。

**跨运行记住哪些维是动态的。** 上面那份尺寸记录可以落盘:给作业一个标识,编译成功后就把记录写进编译缓存目录,下一次启动的第一次编译直接按问号处理,省掉那次注定作废的静态编译。记录按 rank 分开存;多卡 SPMD 作业可以在编译时让各 rank 用集合通信交换见过的尺寸,只要任一 rank 上晃过,大家都当动态。

**为什么实际不吃亏。** 多数模型只有 batch 和序列长度这 1–2 维在变。多付一次编译之后,一份符号化的结果覆盖 2 以上的所有长度,每次调用只多出几条整数比较;提示值还留在符号上,Inductor 做调优与启发式选择时仍然有一个真实的尺寸可用。

## 三、代价

**第一份静态编译多半是白编。** 自动动态要看到两个不同的值才动手,于是第一份按具体形状编的结果在第二次调用时就被取代;它还留在缓存里占一个名额。新的符号化结果排到最前,默认连原来那个形状也由它来服务,那份静态结果基本不会再被用到。

**符号化的 kernel 更保守。** 尺寸成了运行期参数,Inductor 没法把它当常量折叠、按它挑块大小。官方文档对一刀切的开关评价是容易出错、可能让性能回退、编译更慢。无依据符号更糟:调优时没有提示值,用一个固定的回退值 8192 代替。

**推理在 Python 里,也有编译期开销。** 每一次对符号的判断都要走一遍取值范围分析与 SymPy 化简;符号越多、表达式越复杂,抓图越慢。

**一处写死,全盘皆静。** 等式条件会把符号替换成常数。代码里一句「长度等于 33」、一次和固定长度张量的逐元素运算(两边尺寸必须相等),都会让这一维悄悄变回静态;没做标注时只是又一次按长度重编,做了强标注就是编译报错。

**0 和 1 躲不掉。** batch 为 1 的请求总会单独编一份;稀疏模型里大量尺寸实际就在 0、1、2 之间晃,官方文档专门把这称为 0/1 特化问题。不带上下限的强标注也不拦这件事,0 和 1 被特化时不报约束冲突。

**无依据符号有两笔账。** 一是图的语义可能和 eager 不完全一致:框架代码为了不分支而走通用路径,官方文档自己承认会偏离 eager 的语义。二是运行期断言要真的去读数据,断言的对象若是 GPU 上的张量,就要同步一次。

**断图会丢掉动态性。** 两段编译区域之间是 eager 代码,符号不会穿过它传下去;后一段看到的是普通的整数和张量,要从头再晃一次才会变成符号。

## 四、和同类大厂框架不一样的地方

01 章已经比过 JAX 即时编译「每个新形状重编」,04 章比过 tf.function 的放宽重追踪。这里比到更细一层:当用户明确要一份结果服务一整段形状时,符号维的范围从哪来、对它的比较怎么处理、取决于数据的大小怎么办。对照对象是 JAX 导出时的形状多态(让一次导出的结果适配一族形状),以及 NVIDIA 推理引擎 TensorRT 的动态形状。

| 双方都要回答的问题 | torch.compile | JAX 导出时的形状多态 | TensorRT 的动态形状 |
|---|---|---|---|
| 哪些维可变,谁说了算 | 默认靠观察:两次调用间晃过的维自动变符号;也可以提前标注或声明 | 用户在导出时的形状规格里写维度变量 | 用户构建网络时把运行期才知道的维写成 -1 |
| 符号维的取值范围 | 输入尺寸默认 [2, ∞),0 和 1 单独按常量编;可以声明上下限 | 所有维度变量默认至少为 1;可以另加大于等于、小于等于、等于三种约束 | 构建时至少要给一个优化配置文件,为每个输入写最小、最优、最大形状;配置文件可以有多个,范围可相交也可不相交 |
| 对符号维的比较,结论取决于具体值时 | 拿提示值算出一支,记成条件;下次不满足就重编 | 必须对所有取值都成立,判不出来就在导出时报不确定比较的错;官方建议改写成取最大最小值,或补约束 | 形状关系由用户显式告诉构建器:同名的维视为相等,更复杂的关系用断言层表达,运行时违反就报错 |
| 取决于数据的输出大小 | 无依据符号:默认断图,打开捕获后能进图,但不能拿来分支 | 即时编译下不支持:非零元素的个数这类输出要事先给定一个静态上限,多了截断,少了填充 | 支持:这一维报成 -1,由用户提供的输出分配器在大小确定后分配显存 |
| 一份结果管多大范围 | 条件内的所有形状共用一份已编好的 kernel;越界就重编 | 追踪与降级只做一次,但每个具体形状仍按需重新编译 | 引擎构建一次;自动调优按最优形状来,部分实现只在最小、最优、最大三者相等时才可用 |

一句话:JAX 与 TensorRT 都要求用户先把范围和关系说清楚,说不清的比较在构建时报错;torch.compile 默认替用户观察,判断不了的先按这次的值挑一支、记成条件赌下去,赌输了就重编。换来的是不改代码就能动态,代价是重编次数取决于代码里有多少对尺寸的判断。

## 五、调参与观测

这一章的参数分四处:编译入口的具名参数(改了要重新包一次);张量上的标注函数(进编译之前调用,对这个张量对象生效,不能在被编译的代码里调用);Dynamo、fx 与 Inductor 的全局配置(在编译前改);`torch.compiler.config` 的来源名单与作业标识(既可以在启动前用环境变量给,也可以在运行期用 `torch.compiler.config.patch` 改)。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `dynamic` | `torch.compile` / `Module.compile` | `None`,自动动态 | `True`:一上来全部输入维与参数整数都是符号,尺寸相同的维共用符号,官方不推荐;`False`:关掉自动动态,每个新尺寸各编一份 | `TORCH_LOGS=dynamic` |
| `dynamic_shapes` | 同上 | `None` | 传 `torch.fx.experimental.dynamic_spec` 里的 `ShapesSpec`:声明的维变成无依据符号,带上下限与关系,其余一律写死;与 `dynamic` 同时给直接报错 | 同上 |
| `torch._dynamo.mark_dynamic(t, dim, min=, max=)` | 进编译前对输入张量调用 | 未标 | 强标注:第一次编译就是符号;被代码写死时报 `ConstraintViolationError` | 报错信息指到写死它的代码 |
| `torch._dynamo.maybe_mark_dynamic(t, dim)` | 同上 | 未标 | 弱标注:被写死不报错 | `TORCH_LOGS=dynamic` |
| `torch._dynamo.mark_static(t, dim)` | 同上;也可用在模块类上 | 未标 | 这一维永远写死;用在模块类上时它的整数属性保持常量 | — |
| `torch._dynamo.decorators.mark_unbacked(t, dim, min=, max=, shape_id=)` | 同上 | 未标 | 这一维变成无依据符号:不做 0/1 特化,不能按提示值分支;同一 `shape_id` 的维在运行期检查彼此相等 | 断图或报错里的 `data-dependent` |
| `torch.compiler.config.dynamic_sources` | 环境变量 `TORCH_COMPILE_DYNAMIC_SOURCES` 或运行期修改 | 空 | 按来源名(如 `L['x']`、`L['x']:0`、正则)标成符号;压过 `dynamic=False` 与参数、模块属性的静态开关,对整数也有效 | tlparse 的 PGO 工件里能直接抄来源名 |

| `torch.compiler.config.dynamic_values` | 环境变量 `TORCH_COMPILE_DYNAMIC_VALUES` | 空 | 值等于名单里某个数(如 1111)的整数与维一律标成符号;用一个罕见的哨兵值预热,找回断图后丢掉的动态性 | — |
| `torch._dynamo.config.automatic_dynamic_shapes` | 全局配置,或环境变量 `TORCH_DYNAMO_AUTOMATIC_DYNAMIC_SHAPES` | `True` | `False`:不再自动把晃过的维换成符号 | — |
| `torch._dynamo.config.automatic_dynamic_shapes_mark_as` | 全局配置 | `"dynamic"` | `"unbacked"`:自动动态换出来的是无依据符号 | — |
| `torch._dynamo.config.force_parameter_static_shapes` | 同上 | `True` | `False`:模型参数的形状也参与自动动态 | — |
| `torch._dynamo.config.force_nn_module_property_static_shapes` | 同上 | `True` | `False`:模块上张量属性的形状也可以动态 | — |

| `torch._inductor.config.unbacked_symint_fallback` | Inductor 全局配置 | 8192 | 无依据符号在调优时代入的尺寸 | — |

`.item()` 与 `nonzero` 能不能进图,由 02 章参数表里那两个捕获开关决定;整图模式会自动打开它们。

**观测三处。** 符号是怎么来的、条件是谁加的:`TORCH_LOGS=dynamic` 每建一个符号打一行 `create_symbol s77 = 16 for L['x'].size()[0] [2, int_oo]`,每加一条条件打一行 `eval Eq(s77, 33) [guard added]` 并附上用户代码的位置;找到第一处特化最关键,因为之后依赖它的符号都会跟着写死。想看某个符号在哪建的、某条条件的完整调用栈,设 `TORCHDYNAMO_EXTENDED_DEBUG_CREATE_SYMBOL="s77"` 或 `TORCHDYNAMO_EXTENDED_DEBUG_GUARD_ADDED="Eq(s77, 33)"`。为什么变成了动态:`TORCH_LOGS=+dynamic` 里的 `marking L['x'] as dynamic (from automatic dynamic/PGO)`,重编原因里的 `size mismatch at index 0`。最后装了什么:`TORCH_LOGS=guards` 里张量检查的 `size=[None, 64]` 表示第 0 维是符号,形状条件单独成行。tlparse 报告里,`compilation_metrics` 有特化小节,PGO 工件用问号标出每个来源哪些维是动态的,来源名可以直接抄进名单。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 推理服务,batch 与序列长度都在变,prefill 长度至少为 2 | 进编译前 `torch._dynamo.mark_dynamic(ids, 1)`,batch 那维用 `torch._dynamo.maybe_mark_dynamic(ids, 0)`(batch 会出现 1) | 省掉首次静态编译,用符号化的 kernel 换掉按长度重编;batch 为 1 仍单独一份 |
| 大作业反复重启,模型里有断图 | `TORCH_COMPILE_JOB_ID=<作业名>`;多卡 SPMD 再加 `TORCH_COMPILER_COLLECTIVES=1` | 首次运行照常多编,之后的重启直接按动态编;各 rank 行为一致,但要求断图位置处处相同 |
| 检测、MoE 路由这类有 `.item()`、`nonzero` 的模型 | 打开 02 章那两个捕获开关;分支前补 `torch._check(n > 0)` 之类的断言 | 用运行期断言(可能要同步 GPU)换掉断图;语义可能偏离 eager,先在小输入上对一遍结果 |
| 自动动态把某维变成了符号,kernel 反而变慢 | `TORCH_COMPILE_STATIC_SOURCES="L['x']:1"` | 那一维回到按值重编,换回特化 kernel |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 每个新长度都重编 | `TORCH_LOGS=recompiles` 是不是 `size mismatch`;有没有设 `dynamic=False`;那个张量是不是参数、模块属性,或从断图前的 eager 代码传过来 | 前两种标注或改参数;后几种用来源名单 |
| 报 `ConstraintViolationError` 写着 `You marked ... as dynamic but your code specialized it` | `TORCH_LOGS=+dynamic` 里第一条 `Eq(s77, …) [guard added]` 指向哪行代码 | 改掉那句判断;确实只能写死就改用弱标注 |
| 长度跨过某个值又重编一次 | 形状条件里有没有 `<= 1024` 这类不等式,来自哪句 if | 这是按提示值挑分支的正常结果;分支数有限就接受,想要一份结果就把分支改成张量运算 |
| batch 为 1 总是单独编译 | 形状条件里的 `2 <= L['x'].size()[0]` | 接受,或把那一维标成无依据 |
| 报 `Could not guard on data-dependent expression` | 报错里 `Potential framework code culprit` 指向用户代码还是 `torch/` 下 | 用户代码加 `torch._check`;框架代码按官方说法是 bug,去报 |
| 设了 PGO,第二次运行仍然先静态编一次 | 有没有设 `TORCH_COMPILE_JOB_ID`;代码是否改过(记录按文件内容哈希与行号定位) | 设上标识;改过代码的第一次运行重新积累 |

## 六、常见误区

**「标了 `mark_dynamic`,这一维就再也不会重编。」** 名字听起来像一劳永逸。它只保证这一维一上来就是符号、被写死时报错;0 和 1 照样特化,不带上下限时对此也不报错;代码里对它的不等式判断照样记成条件,长度跨过阈值照样重编。

**「`dynamic=True` 最省事,一步到位。」** 因为它是入口参数,看起来最正式。官方文档明确不推荐:所有维和整数都变成符号,kernel 更保守、编译更慢;尺寸相同的维还会被当成同一个符号,之后来一个两维不等的输入就是一次重编。应该只标真正在变的那几维。

**「动态形状就是不管形状了。」** 人们以为符号化之后图对所有长度都成立。实际上每一句对尺寸的 if 都按第一次看到的值选了一支,选择记成了条件;最常见的是注意力实现按长度分块、按 batch 是否为 1 走捷径。图只在这些条件内成立,所以动态之后仍会有重编,只是次数由分支数决定,而不是由长度的个数决定。

**「打开标量捕获,`.item()` 之后的代码就都能进图。」** 捕获开关确实让取值不再断图。但拿到的是无依据符号,没有提示值;紧接着一句 `if n > 0` 仍然会断图,整图模式下直接报错。要在分支前用 `torch._check` 告诉它事实,或者把分支写成张量运算。

**「PGO 默认开着,第二次启动自然就快。」** 本地 PGO 的开关确实默认是开的。但开源版要显式给作业标识才会读写记录,不设就什么都不发生。反过来,给了标识却改了代码,记录按文件内容与行号定位,改动处也会失效。

**「Python 整数和张量的维一样,变了都会自动转符号。」** 作为参数传进来的整数是这样。全局变量、模块属性、参数默认值里的整数始终按值钉死,每变一次重编一次;浮点数在全局打开 `torch._inductor.config.triton.cudagraphs` 时也按值钉死。04 章说的每步重编,指的是后一类。

**「动态版本编出来以后,老形状还走原来那份特化结果。」** 直觉上更特化的应该优先。实际新编的条目插在最前,老形状也满足它的条件,于是全由符号化版本服务,旧的静态结果只是占着一个名额。想让老形状继续走特化版本,要打开 `automatic_dynamic_exclusion_guard`。
