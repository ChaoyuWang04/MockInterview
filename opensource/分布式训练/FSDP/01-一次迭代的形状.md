# 一次迭代的形状

这一页回答一件事:一张卡装不下的模型,怎么在一组卡上跑完一次完整的迭代。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

训练一个模型,一张卡上同时住着三样东西:参数、梯度、优化器状态。三样不等大——常用的那类自适应优化器给每个参数另外带两份状态,所以「参数有多大」这个直觉数字,要乘上好几倍才是真实占用。

纯数据并行不解决这件事。它让每张卡各拿一整份完全相同的副本,各算各的那一批数据,最后把梯度归约一次。卡越加越多,能吃的批次越来越大,**可单卡的占用一点没变**。于是模型一过某个大小,加多少张卡都没用:进程起来,第一次前向还没走完就 OOM,连第一步都到不了。

还有一件容易被忽略的事:那些完全相同的副本,**绝大部分时刻都闲着**。算到中间某一层的时候,第一层和最后一层的参数只是躺在显存里占位置。

![两组各 4 张卡的对照图:左边每张卡都放着一整份参数、一整份梯度、一整份优化器状态,四张卡的内容一模一样;右边每张卡的同样三样东西都只剩四分之一宽的实心块,后面跟着一个虚线空框表示它本来的大小,说明每张卡只留自己那一段](/opensource/FSDP/01a-what-sits-on-one-card.svg)

## 二、解法

既然各张卡存的是一模一样的东西,那就别各存一份——**一人存一段,谁要用谁去凑**。

先看默认的一维分片与一个非根通信组:参数沿第 0 维切给网格中的各张卡,每张卡常驻自己那一份;梯度和优化器状态跟着参数走,也各自只留一段。真要算某一块网络的时候,这一块涉及的参数在卡之间互相凑齐,拼出一份完整的,算完立刻扔掉。反向再凑一次,算出来的梯度是完整形状的,把它按同样的切法打散回各卡,每张卡只留自己那一段——正好和手里的分片参数对得上,优化器直接在这一段上更新,这一轮更新完,下一轮再从更新后的分片开始聚合。根组默认保留前向的完整参数,因而不需要反向再聚合。

**为什么实际不吃亏**:计算本来就是一块一块进行的,任何一个时刻真正用得上的参数只有一小部分。所以凑齐这件事可以按块拆开,而且可以提前发起——正在算这一块的时候,下一块的凑齐已经在另一条通道上跑着了。提前发起有机会把通信藏在计算底下;藏不住的部分仍会增加每步时间。

驱动这一切的东西很轻:分片不包装模块,通过模块上的 hooks 接管参数生命周期。前向之前的 hook负责凑齐,前向之后的 hook负责释放,反向对称。模型结构、参数的完整名、你写的那些前向代码都不用改,变的只有参数的身份——它从一个普通张量变成一个知道自己分布情况的张量:完整形状是多少、本卡持有哪一段、按哪一维切的,都写在它身上。

## 三、代价

**多了参数聚合**。纯数据并行主要同步梯度;这里的非根组通常需要前向、反向各一次 all-gather,再做一次 reduce-scatter。这描述的是单组路径,整步通信次数还取决于分组与保留策略。能不能藏住,取决于你把模型切成了多少块,以及 CPU 有没有跑在 GPU 前面足够远。

**分片不等于峰值也按比例缩小**。计算时仍要容纳完整参数和梯度,再加上激活、优化器状态与通信缓冲。上图只展示一个组的参数与梯度生命周期,不能直接当作整步显存峰值。

**参数不再是普通张量**。任何按普通张量对待参数的代码都要重看一遍:读形状没问题,那是完整形状;可要拿到本卡真正持有的那段数据,得显式去取。

**必须走模块调用**。凑齐挂在模块调用上,绕过它直接调某个方法,hook不会触发,参数还是分片的,报出来是一个莫名其妙的形状错。自定义的前向方法要显式登记一次。

**一轮出错就不能接着跑**。前向或反向中途抛异常之后,这一轮的内部状态处于未定义状态:在途的通信、各组的训练态、梯度累积的进度全乱了。要跑下一轮必须先在根模块上重置一次,那一轮的梯度一律作废。

## 四、和同类常见做法不一样的地方

对比对象取 Megatron-LM——同样要回答「一步训练怎么在一组卡上跑」,重点比较参数驻留与通信边界。下面每一条都在它主干 2026-09-20 的那份代码(基准 fb6a123a09)上核过,完整基准记在底稿。

**参数驻留方式不同**。Megatron 默认的数据并行保留完整参数与优化器状态,同步梯度;启用分布式优化器后,才沿数据并行维分片优化器相关状态,更新后再同步参数。这里则连参数也分片常驻,按组在计算前临时 all-gather,换取更低的参数驻留。

**通信边界不同**。Megatron 的梯度重叠默认关闭;开启后,可以按元素数阈值把缓冲区划成桶,桶内梯度就绪时发起归约。这里通常按模块调用划出通信组,边界与模型结构对应。两种方式都要在通信粒度与计算重叠之间取舍。

**模块接入方式不同**。Megatron 的 DDP 使用包装模块,FSDP2 原位改造模块并保留参数完整名。不过包装结构不等于导出的 checkpoint 必然多一层前缀:Megatron 的状态字典接口会转发给内部模型。

Megatron 另有全分片路线,其中一条使用 PyTorch FSDP2。因此这里比较的是它的 DDP 与分布式优化器路径,不是说 Megatron 只能保留完整参数。

## 五、调参与观测

这一页的旋钮分两类:包模块的时候一次定死的,和运行期可调用的。前者是分片入口的具名参数,后者是分片之后挂在模块上的方法——FSDP2 的显式控制更细;FSDP1 也有运行期控制,例如用于梯度累积的上下文管理器。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `mesh` | 分片入口 | 按当前默认进程组的大小现搭一张一维网格 | 决定切给哪些卡;给二维网格就变成组内切、组间复制 | 打印参数,网格与切法写在它身上 |
| `reshard_after_forward` | 分片入口 | `None`:非根模块按 `True` 走,根模块在首轮初始化时被改成 `False` | `True` 省显存、反向多一次 all-gather;`False` 相反 | 数反向阶段的 all-gather 次数 |
| `shard_placement_fn` | 分片入口 | `None`,一律按第 0 维切 | 可以改切哪一维,或让某些参数用另一张网格 | 打印参数的切法 |
| `mp_policy` | 分片入口 | 三个 dtype 字段全 `None`,沿用原精度 | 改计算与通信的精度 | 通信量与 loss 曲线 |
| `offload_policy` | 分片入口 | 不 offload | 把分片参数、梯度、优化器状态搬到主机内存 | 显存降、每步时间涨 |
| `ignored_params` | 分片入口 | 空 | 列进去的参数不切、不搬设备、反向不归约 | 确认这些参数仍是普通张量 |

运行期可调用的那一类,本章只用得上四个,其余留给后面几章:

| 方法 | 做什么 | 什么时候用 |
|---|---|---|
| `reshard()` / `unshard()` | 手动把当前模块管理的参数组退回分片,或提前 all-gather | 想在前向和反向之间动参数时 |
| `set_requires_gradient_sync()` | 控制梯度归约,默认也递归设置子模块 | 梯度累积的中间那几个微批 |
| `set_reshard_after_forward()` | 调整前向后重分片,默认也递归设置子模块 | 只想让某几层不重分片 |
| `reset_iter_state()` | 在根模块重置迭代状态,失败的累积序列作废 | 捕获到前向或反向的异常之后 |

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡,参数放得下但优化器状态放不下 | 每个 transformer 层上调一次分片入口,最后在根模块上再调一次,其余全默认 | 用参数 all-gather,换取参数、梯度和优化器状态的分片常驻 |
| 曾为提速关闭部分非根层的前向后重分片,现在显存不足 | 对这些层恢复 `reshard_after_forward=True` | 缩短完整参数驻留,代价是恢复反向 all-gather |
| 卡确实不够,宁可慢 | 在逐层分片的基础上打开 CPU offload,锁页保持默认的开 | 显存大幅下降,每步时间明显变长 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测三处**:通信有没有真被盖住,只有 profiler 里那几条流的时间线说了算,别的都是猜;显存对不对,结合参数、梯度、优化器状态、激活和通信缓冲检查峰值,再判断是否需要调整分组;切法对不对,直接打印参数,它自己就带着网格和切法。

| 症状 | 先查 | 然后 |
|---|---|---|
| 分片之后还是 OOM | 是不是只在根模块上调了一次分片入口 | 改成每层调一次,根模块最后再调 |
| 形状不匹配,而且只在某个自定义方法里出现 | 这个方法是不是绕过了模块调用 | 把它登记成前向方法 |
| 优化器更新完参数没变 | 优化器是不是拿分片后的参数建的 | 先分片,再建优化器 |
| 每步时间比预期慢很多,但通信量对得上 | profiler 里通信是排在计算后面还是底下 | 见 03 章 |
| 第二轮开始报各种内部状态断言 | 上一轮是不是抛过异常 | 在根模块上重置一次再继续 |

## 六、常见误区

**分片了仍可能 OOM**。先查是不是只在根模块上调用了一次,使完整模型参数同时驻留;再看激活与通信缓冲等占用。逐层划组如何降低参数驻留,见 02 章。

**以为参数的形状变小了**。没有。参数对外报的是完整形状——这是为了让你的模型代码不用改。本卡真正持有的只有一段,要显式去取才拿得到。统计参数量、手工切分、把参数塞进别的库,这几处最容易按「形状对得上就是数据在手」来写,然后在多卡上静默出错。

**把前向后的重分片一律关掉当提速手段**。根模块默认就是关的,因为它的参数在反向一开始就要用,退回去再凑一次纯属白跑。可非根模块也关掉的话,前向走完整个模型之后所有完整参数都还在手里,参数驻留会上升,可能导致 OOM;梯度和优化器状态仍可保持分片,总显存不能直接等同未分片训练。

**先建优化器,再分片**。顺序反了。优化器必须拿分片之后的参数来建,并且在分片参数上做更新;拿分片前的参数建出来的优化器,更新的是一批已经被换掉的对象。

**绕过模块调用**。直接调某个方法而不是调模块本身,hook不触发,参数还是分片的。多输出、多阶段的模型里最常见——主前向之外还有一个生成方法、一个打分方法,这些都要各自登记一次。

**异常之后接着跑下一批**。捕获住了前向的异常,以为跳过这一批就行。实际上在途的通信、各组的训练态、梯度累积的进度都停在半路,下一轮会在各种意想不到的地方断言失败。必须先在根模块上重置。
