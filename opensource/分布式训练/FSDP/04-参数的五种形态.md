# 参数的五种形态

这一页回答一件事:一份参数被反复凑齐又扔掉,扔掉之后反向还要原样找回来,这件事怎么做到不崩。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

省显存的全部收益,押在同一个动作上:临时凑出来的那份完整参数,用完立刻不占地方。这个动作不是偶尔发生——每个通信组前向做一次、反向做一次,一个 32 层的模型一轮就是 64 次以上。任何一次没扔干净,省下的显存就攒着不还,峰值一路顶到 OOM。

麻烦在于「扔掉」这个词在 PyTorch 里通常的含义:让张量对象的引用计数归零,存储跟着还给分配器。可这份完整参数不归你一个人管——前向刚算完,autograd 为了反向已经把它、或者它的某个视图,压进了自己的保存区。于是两条路都是死的:

- **按常规扔**。引用计数归不了零,存储还在,显存一点没降。你以为释放了,峰值曲线纹丝不动。
- **强行换掉对象**。下一次凑齐时另建一个张量,autograd 存的那个还指着老的那块内存。新对象不能恢复 autograd 已保存的引用关系;保留旧存储会失去省内存的收益,释放旧存储又不能靠另建对象恢复那些视图。

这不是边角情况。前向后重分片、激活重算、梯度累积、手动预取,全都建立在「这份东西可以安全地消失再回来」之上。这一条不成立,前面几章讲的省显存全是空话。

## 二、解法

换个层面动手:**别碰对象,碰它脚下那块存储**。张量对象和它背后的存储是两件事——把存储缩到 0 字节,内存就还给分配器了,而对象、形状、步长,以及 autograd 存着的那些视图与它的别名关系,全都原封不动。要用的时候再把存储撑回原来的大小,把通信的结果原地写进去。

代价换成了一条硬约束:完整参数这个对象**只在第一次凑齐时构造一次**,之后每一轮都是往同一个对象里原地写。

顺着这条约束往回推,一个参数就分成了五种形态:

- **原始参数**:你建模型时的那个普通张量,分片做完它就可以被回收
- **分片参数**:本卡常驻的那一段,类型换成了带分布信息的分布式张量。FSDP 拿它做两件事——对外报出完整形状与本卡持有哪一段,以及给优化器一个能直接更新的对象
- **凑齐的输入**:交给通信的一维数据,由分片参数变换而来
- **凑齐的输出**:通信写回来的一维数据,被反复伸缩的就是这块
- **完整参数**:把输出按原来的形状与步长摆出来的那一份,autograd 的叶子就是它

默认无 dtype 转换的路径中,分片参数与 all-gather input 共享数据,all-gather output 与完整参数共享数据;原始参数在分片后可以回收。五种形态并不等于五份常驻内存。**故意分成五种,是因为中间那两道被留成了可替换的变换**:输入 = 前置变换(分片参数),完整参数 = 后置变换(输出)。留这个口子是给量化这类扩展用的——前置变换可以把一个参数变成多份输出,压缩后的数据一份、还原用的 scale 一份,通信传输量化数据以及返回为输入的 scale 等信息,后置变换再把它们还原成完整参数。

**为什么实际不吃亏**:伸缩存储本身不搬数据,只是向分配器要一块或还一块;「构造一次、之后原地写」顺带把每一轮重建张量、重新注册的那点 host 开销也省了,而 host 开销恰恰是这套东西最紧张的资源。

## 三、代价

**所有写入都变成原地写**。既然对象不换,新数据只能写进同一块存储。往 autograd 可能保存过的张量里原地写,本该触发「保存的张量被改过」那道检查,所以这些写必须显式绕开版本计数。绕开是对的——这块存储此刻确实没别人在用——但正确性从此由 FSDP 自己的状态机保证,框架不再兜底。

**「参数还在不在」不能再看对象**。对象一直在,身份判断一直成立,变的是它脚下的字节数。任何按「拿得到这个张量就等于拿得到数据」写出来的检查,在这里一律失效。

**本地那一段有两个大小**。为了不在每次发起通信前临时补零,分片参数背后的一维数据是按「能被卡数整除」预先补齐好的,而挂在模块上的那一份只是它前面的一个窄视图。参数在切的那一维上不能整除卡数时,排在后面的卡甚至会拿到一个长度为 0 的段。

**不按第 0 维切就多一次真实拷贝**。通信凑回来的东西,各卡的段总是按第 0 维首尾相接的。切的是别的维时,这个拼法和参数原来的排布对不上,必须再拼一次才能还原——这一次是真的在搬数据,不是改改视图。

**扩展的自由度全落在你这边**。前置与后置变换是按名字去找的两个方法,一旦你定义了,补齐到多大、用什么精度、输出什么时候能释放,就全由你负责。框架只在形状对不上时抛一个断言,而这个断言只有带补位的那几张卡抛得出来——别的卡什么都不知道,继续等,最后整组一起超时。

## 四、和同类常见做法不一样的地方

对比放在 Megatron-LM 上:两边都要回答「这张卡持有哪一段」,但把答案写在了完全不同的地方。下面每条都在它主干那份代码上核过,基准 fb6a123a09,行号记在底稿。

**答案写在参数里,还是写在参数外**。这里写在参数自己身上:切的是哪一维、铺在哪张网格上、完整形状多大,都是这个参数的属性,打印出来就看得见。那边写在参数外面:参数被铺进一块连续的大缓冲区,「本卡负责哪一段」是一组偏移量——这个参数在整块缓冲区里的起止、在所属桶里的起止、在本卡那块区域里的起止,以及这一段对应参数自身的哪一截,四个区间凑齐才说得清一件事。

**那边的分卡边界不认参数边界**。缓冲区按卡数等分成几块连续区域,边界落在哪里和参数从哪开始到哪结束毫无关系,这是那份代码里写明的前提。于是一个参数可能被两张卡各分走一截。这里反过来,每个参数各自在自己的那一维上切,所以「本卡持有某个权重矩阵的前四分之一」这句话能直说——代价是每个参数都要单独补齐到能整除,零碎的补位比一整块缓冲区多。

**对象换不换**。那边只在建缓冲区时动一次手:把每个参数的数据换成缓冲区上的一个视图,此后这个视图再也不变,通信直接写进缓冲区本身。这里每一轮要在模块上换两回参数对象,凑齐时换成完整参数、释放时换回分片参数。换对象比换视图贵,买到的是分片参数始终是个完整独立的对象,优化器和checkpoint层可以直接吃。

**完整那一份住在哪,是两边最实的差别**。那边的参数缓冲区按完整大小一次分配、整个作业常驻,它切开的是「谁负责归约与更新哪一段」,参数本身每张卡都是全的;所以那边压根不需要让什么东西消失,也就不需要这一页讲的整套办法。这里常驻的只有切开那一份,完整那份的存储被反复清零——省下来的显存和这一页的全部复杂度,是同一件事的两面。

**高精度那一份在哪一侧也是反的**。那边的分布式优化器给自己负责的那一段另外克隆一份高精度主权重,更新完再拷回缓冲区对应的切片;这里高精度的那份就是常驻的分片参数,低精度的那份只在凑齐的输入到完整参数这一段存在,用完就没。

## 五、调参与观测

这一页的旋钮有一半不在分片入口上:它们是你给自己的张量类型加的几个方法,FSDP 在凑齐前后按名字去找。另一半是分片入口的具名参数,包模块的时候一次定死;只有最后那个是分片模块上的方法,两轮之间随时能改。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `shard_placement_fn` | 分片入口,包模块时定 | `None`,一律按第 0 维切 | 返回一个 `Shard` 就换切哪一维;返回 `ShardPlacementResult` 就让这个参数走另一张网格 | 打印参数,切法与网格写在它身上 |
| `reshard_after_forward` 给整数 | 分片入口,包模块时定 | `None`(非根按 `True`、根按 `False`) | 前向后退到一个更小的 world size,于是多出第三种常驻形态;整数必须是分片维大小的非平凡因子 | 前向结束后显存不回到最低那一格 |
| `fsdp_pre_all_gather` | 定义在分片参数内层张量的类型上 | 没有就走默认路径 | 接管「分片参数 → 凑齐的输入」,可以一进多出;签名是 5 个入参,旧的 1 个入参签名仍兼容 | 数一下凑齐输入的个数与 dtype |
| `fsdp_post_all_gather` | 同上 | 同上 | 接管「凑齐的输出 → 完整参数」;必须和上一个成对定义,只定义一个直接报错 | 同上 |
| `fsdp_should_release_all_gather_outputs_after_post_all_gather` | 同上 | 没定义时按不释放 | 返回 `True` 表示后置变换之后原始输出就没用了,可以立刻释放;和整数重分片互斥,组合起来报未实现 | 峰值少掉一份凑齐输出 |
| `mp_policy` 的 `param_dtype` | 分片入口,包模块时定 | `None`,沿用原精度 | 低精度那份从凑齐的输入开始、到完整参数为止;分片参数与优化器更新仍是原精度 | 打印完整参数与分片参数的 dtype,两者应当不同 |
| `offload_policy` | 分片入口,包模块时定 | 不 offload | 分片参数常驻主机内存,取凑齐输入前多一次异步拷回设备 | 设备侧参数只剩完整那一份 |
| `set_unshard_in_backward()` | 分片模块上的方法,两轮之间可改 | `True` | 关掉之后这一组反向不再凑齐,完整参数这一形态在反向里根本不出现;只有确认这一组的参数反向用不上才能关 | 反向的 all-gather 次数少一组 |

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 常规 dense 模型,不碰参数表示 | 三个可选参数全不给,每个参数各自按第 0 维切 | 使用默认的共享存储路径,无需自定义变换 |
| 想让 all-gather 走低精度 | 只给 `mp_policy` 填上 `param_dtype`,其余不动 | 例如 FP32 降到 BF16 时参数传输量减半,多出低精度的 all-gather input;分片参数仍是原精度,优化器不必另留主权重 |
| 自己实现量化后的 all-gather | 把分片参数的内层张量换成自定义类型,成对实现 `fsdp_pre_all_gather` 与 `fsdp_post_all_gather`,再用 `fsdp_should_release_all_gather_outputs_after_post_all_gather` 声明输出能不能提前释放 | 通信量按量化位宽下降;补齐、dtype、释放时机全由你负责,写错了只有带补位的那几张卡报,表现成整组通信超时 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测三处**:参数此刻是哪一形态,看挂在模块上的那个对象的类型——分片状态下它是带分布信息的分布式张量,凑齐之后是普通张量,不用翻任何内部字段;完整那份有没有真释放,看它背后 untyped storage 的字节数,释放干净就是 0;凑齐的输入是不是分片参数本身,把两者的 data pointer 对一下,开了混合精度或自定义变换就会对不上。profiler 里 `FSDP::all_gather_copy_out` 那一段就是把输出写进这些形态的地方。

| 症状 | 先查 | 然后 |
|---|---|---|
| 分片时报参数不连续 | 这个权重是不是某个转置或切片出来的视图 | 先做一次连续化再分片,当前不支持非连续参数 |
| 换了分片维之后报未实现 | 这一维的长度能不能被分片数整除 | 非 0 维当前只支持整除,换回第 0 维,或把这一维补齐 |
| 加载checkpoint之后下一次通信形状就不对 | 是不是绕过 `load_state_dict` 直接给模块赋了新参数 | 走 `load_state_dict`,让它后面那道重新补齐跑起来 |
| 反向数值对不上,前向看着正常 | 是不是在前向和反向之间改过参数 | 先 `reshard()` 退回分片,确认挂着的是分片参数再改 |
| 自定义张量类型报两道变换必须成对 | 是不是只实现了其中一个 | 两个一起实现,少一个直接在初始化阶段就报 |
| 部分 rank 卡住,最后整组通信超时 | 自定义前置变换返回的形状等不等于补齐后的分片大小 | 按补齐后的大小返回;形状不对只有带补位的那几张卡报得出来 |

## 六、常见误区

**以为「释放完整参数」是把那个张量扔掉**。会这么想是因为在别处释放显存确实就是让引用归零。这里不是:对象从头到尾是同一个,被清零的是它脚下的存储。所以用「这个张量还在不在」来判断释放没释放,永远得到「还在」;要看的是存储的字节数。

**以为凑齐的输入就是分片参数本身**。默认路径下确实是同一块数据,于是很容易写出「改了分片参数,凑出来的自然是新值」这种假设。一旦开了混合精度,输入是现铸的一份低精度拷贝;一旦有自定义前置变换,它可能是压缩后的另一种东西。写扩展时按「就是同一个」来用,拿到的是上一轮的值。

**以为本卡那一段就是「完整形状除以卡数」那么大**。实际上背后的一维数据被预先补齐到了能整除的大小,补的那几行是零;而参数在切的那一维上不能整除卡数时,排在后面的卡可能一个元素都分不到,拿到的是长度为 0 的张量。按 rank 手算偏移去拼别人那一段的代码,在这两处都会错位,而且只在特定的卡数与特定的层上才错。

**把前向后退到一个更小的范围当成纯粹的显存旋钮**。它确实省显存,但它同时换掉了挂在模块上的那一份:既不是分片参数,也不是完整参数,而是一个只在那个小范围内有意义的中间形态。官方在这个参数的文档里写明,要在前向与反向之间改参数,挂着的必须是分片参数——不是就先手动退回去。另外,这一档和「后置变换之后立刻释放输出」是互斥的,因为那份输出正是用来切出中间形态的。

**以为把完整参数存下来下一轮还能用**。对象是稳定的,存下来的引用也一直有效,所以这个想法看起来很合理。可它脚下的存储在前向结束那一刻就被清零了,再次凑齐是原地写回同一块地方:中间那段时间读到的是空存储,下一轮读到的是别人的新值——两种都不是你想留的东西。要留就在还没释放的时候自己拷一份出去。

**以为加载checkpoint只是把数值填进去**。按赋值语义加载会把本地张量整个换掉,预先补齐的那份和记下来的引用一并作废,下一次通信就按错误的大小发起。所以加载接口后面挂了一道专门的重新补齐;绕过它直接给模块赋一个新参数,这道补齐不会跑,而报错要等到下一次通信才出现。
