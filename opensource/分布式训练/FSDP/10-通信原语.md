# 通信原语:连缓冲区一起替换

这一页回答一件事:通信慢在缓冲分配或硬件适配时,怎样改掉底层路径,又不重写 FSDP 的调度。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

同样一次 all-gather,输入输出放在哪种显存里,可能决定通信库能否使用特定的传输路径。若接口只让人替换最后那次通信调用,前面已经用普通分配器准备好了缓冲区,新实现仍可能用不上需要的内存。

通信暂存区还会反复申请和释放。普通分配器有缓存,并不意味着每次都向设备申请新显存,但专用内存的分配、注册与复用仍可能成为额外开销。此时继续改模块分组或预取时机,没有直接触及这条瓶颈。

## 二、解法

FSDP 把**分配缓冲区和执行通信放进同一个可替换对象**。上层依旧决定何时聚合参数、何时归约梯度;下层对象决定怎么申请、从哪里申请、最终调用什么。两者以输入输出缓冲区衔接,不需要为了换分配器重写前后向 hooks。

内置路径有普通分配、进程组分配与 symmetric memory。最后一种是让通信参与者能够建立对应关系的对称内存,源码通过专用内存池复用它,减少反复分配与建立映射的开销。它还会在通信前建立参与者间的内存对应关系。

![FSDP 上层先请求通信缓冲区,可替换通信对象分别提供普通分配、进程组分配或对称内存池,填入数据后再执行 collective;内置路径最终仍调用标准集合通信入口](/opensource/FSDP/10a-communication-boundary.svg)

**换内存来源不等于换了 collective 的语义或算法**。内置路径最终仍调用标准 all-gather 或 reduce-scatter 入口,具体硬件优化由下层通信库结合内存、拓扑和策略决定。算法原理见知识库「集合通信」,本章只讲 FSDP 留出的接入边界。

## 三、代价

默认路径最直接,高级路径则多了兼容条件。进程组如果不能提供专用分配器,就回退到普通分配;对称内存需要初始化与内存映射,能否用上期望的硬件路径还要看通信库与机器拓扑。开启接口本身不是提速证据。

自定义对象还要兑现原来那套协议:缓冲区的大小、精度、设备,通信参与组,归约操作,以及完成时机都必须正确。特别是 all-gather 的输入可以是输出缓冲区中的一段,不能假定两块内存互不重叠;自己复用缓冲区,也不能覆盖仍在通信或使用中的数据。

这些替换针对当前模块的参数组,不会自动替整棵模型逐层安装。若一个模块因参数使用不同网格而拥有多个参数组,自定义通信入口会拒绝这种含混的替换。分组与时序仍分别由 02、03 章负责。

## 四、和同类常见做法不一样的地方

对照 Megatron-LM 基准 fb6a123a09 的参数与梯度缓冲路径。

| 比较维度 | FSDP2 | Megatron-LM |
|---|---|---|
| 专用内存接在哪里 | 在参数组的通信边界,替换暂存区分配与collective调用对象 | 在训练框架构建参数/梯度缓冲区时选择NCCL专用内存池 |
| 通信前的准备 | 通信对象负责所选内存路径所需的分配与准备,上层仍驱动生命周期 | 分配前进行communicator warmup,让后续通信使用已注册缓冲 |
| 能从接口判断什么 | 能明确替换边界,不能仅凭专用内存池推断网络算法或提速 | 同样需要结合通信库和环境确认实际路径,专用内存池不等于某一种网络算法 |

## 五、调参与观测

这些是分片模块上的方法,不是启动命令。建议在 `fully_shard` 完成后、首轮训练前,对需要改变的各个 FSDP 模块分别设置;变更实验配置时重新启动作业,避免在在途通信中切换对象。

| 参数或接口 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `set_custom_all_gather(comm)` | 每个 FSDP 模块 | `DefaultAllGather` | 自定义缓冲分配与 all-gather 实现;成本由对象决定 | 在自定义对象记录分配与调用,用 profiler 对齐完成时机 |
| `set_custom_reduce_scatter(comm)` | 每个 FSDP 模块 | `DefaultReduceScatter` | 自定义缓冲分配与 reduce-scatter 实现,须遵守传入 `op` | 与默认结果核对梯度,再测归约耗时 |
| `set_allocate_memory_from_process_group_for_comm(enable)` | 每个 FSDP 模块 | 未启用,使用普通分配 | `True` 尝试用 ProcessGroup 的 allocator;不支持就回退;`False` 恢复默认路径 | 先确认 backend 的 `supports_tensor_alloc(device)`,再比显存与通信时间 |
| `set_symm_mem_for_comm(backend)` | 每个 FSDP 模块 | 未启用;调用时 `backend="NCCL"`,当前仅支持它 | all-gather 使用对称内存;reduce-scatter 另有下述前置条件 | 分开检查 AG 与 RS,不凭方法名断定两者都已切换 |
| `set_force_sum_reduction_for_comms(enable)` | 每个 FSDP 模块 | `False` | `True` 要求通信使用 SUM,均值缩放由通信前后另做;这是切换对称内存 RS 的前置设置 | 核对梯度数值与缩放开销,详见 09 章 |
| `NCCL_CTA_POLICY` | NCCL 初始化前的环境变量 | 本章不指定 NCCL 外部默认值 | 对称内存 AG 的 Copy Engine 路径需要值 `2`,也可在 ProcessGroup options 中设置 zero-CTA policy | 核对运行环境与 profiler,不能只凭变量判断硬件路径生效 |

`AllGather`、`ReduceScatter` 都需要实现 `allocate(size, dtype=..., device=...)` 与 `__call__`。后者接受输入、输出、`group` 和 `async_op`;归约还接受 `op`。异步 all-gather 返回的 `Work` 会被 FSDP 等待,使用当前流的完成事件也参与依赖管理。自定义对象若另起流,必须把完成关系接回调用方,不能只把请求发出去就视为完成。

内置 allocator 开关与自定义对象不能混用;ProcessGroup 分配与对称内存也应作为不同实验路线。**对称内存 RS 的顺序有要求**:先设 `set_force_sum_reduction_for_comms(True)`,再调 `set_symm_mem_for_comm()`。源码在后一个方法执行时检查 SUM 设置;只开启对称内存而保留默认设置时,RS 仍用默认实现。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 普通 CUDA/NCCL 作业,还没有通信瓶颈证据 | 完成分片后不调用本章的替换方法 | 保留标准分配与 collectives,先取得数值和性能基线 |
| NCCL backend 支持专用分配,想单独评估内存来源 | 对各目标模块调用 `set_allocate_memory_from_process_group_for_comm(True)` | 保持标准 collective 调用,测试专用缓冲是否改善耗时;不支持时回退 |
| 支持 symmetric memory 的 CUDA/NCCL 环境,要测 AG 与 RS 对称内存 | 对各目标模块先调 `set_force_sum_reduction_for_comms(True)`,再调 `set_symm_mem_for_comm()`;若测 Copy Engine AG,初始化前另设 `NCCL_CTA_POLICY=2` | 增加初始化与缩放条件,换取尝试专用通信路径的机会,不保证更快 |

组合与推荐值是按语义推的起点,不是实测最优。

每次只改一条路线,固定模型分组、batch 与精度,比较 warmup 后的每步时间、通信区间与显存峰值。先核对 loss 和梯度,再判断节省的是分配时间还是通信时间;前者不能冒充网络带宽提高。

| 症状 | 先查 | 然后 |
|---|---|---|
| 开启 ProcessGroup 分配后性能不变 | backend 是否支持专用分配,瓶颈是否在缓冲处理 | 确认不是回退,再用 profiler 判断是否值得保留 |
| 对称内存 AG 生效,RS 没变化 | 是否在切换前启用了强制 SUM | 按正确顺序重新启动并设置,再分别测 AG/RS |
| 调 allocator 方法时报 custom comm 断言 | 是否已经安装了另一条分配路线或自定义对象 | 从默认模型初始化开始选择一条路线,不要叠加开关 |
| 自定义实现偶发错值或挂起 | rank 间组、dtype、调用顺序、输入输出别名及完成依赖 | 先恢复默认对象确认问题范围,再修自定义协议 |

## 六、常见误区

**把普通分配当成每次都向 GPU 申请新内存**。源码每次调用 `torch.empty`,看起来像不断申请;CUDA caching allocator 会复用已缓存的内存。只有观测到实际分配或注册成本,才能把收益归因于专用内存池。

**只在根模块设置,以为每层都会跟着变**。其他 FSDP 方法有递归选项,很容易把这种习惯带过来。本章的替换方法只处理当前状态的参数组,逐层分片的模型需要逐个设置目标模块。

**把通信完成理解成 Python 函数返回**。自定义实现返回很快,看似提高了效率,实际数据可能仍在另一条流上写入。FSDP 后续会消费这些缓冲区,缺少完成依赖会变成偶发数值错误;性能比较必须包含真正完成通信所需的等待。
