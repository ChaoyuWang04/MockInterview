# 拿什么换显存

这一页回答:前向算完的参数留多久、放在哪,才能让显存和每步时间都在可接受的范围内。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**同一组参数,前向用完不代表这轮不再用。** 反向还要用它:现在释放,到时就要重新 all-gather;现在留下,它就要陪着后面的层一起占显存。层数多、参数大时,这个等待区间会把本来能运行的作业推到 OOM;显存富余而通信慢时,释放得太积极又会拉长一步。

通用分片原理见知识库的 ZeRO 与 FSDP 篇。这里不改分组,也不调整预取,只看同一个组的参数在两次计算之间怎么存。

## 二、解法

最直接的选择是**算完就还,或留到反向再还**。FSDP2 默认对非根模块选前者,对根模块选后者:根模块通常很快就进入反向,保留完整参数能省下一次来回。

中间还有一档:前向后把参数切给一个更小的组。每张卡比原来多留一段,反向就只需在这个小组内 all-gather。它没有消灭通信,而是用更长、更大的参数驻留缩小下一次通信的范围。

![在原始分片规模为 8 的示例中,前向后模块可持有八分之一、四分之一或完整参数视图;前三种视图位于 GPU,CPU offload 加立即重分片则把八分之一分片留在 CPU,反向前再搬回 GPU 并聚合](/opensource/FSDP/06a-residency-tradeoff.svg)

如果连常驻分片也挤不下,再用 **CPU offload**。分片参数平时放在 CPU,all-gather 前搬回 GPU;反向归约后的分片梯度搬回 CPU,优化器也在那里更新。计算仍在 GPU 上完成,完整参数何时释放仍由前面的保留策略决定。

## 三、代价

**少存就多传,多存才可能少等。** 立即重分片需要反向再聚合;完整保留能跳过这次聚合;中间档要多存前向后的分片,并承担小组内聚合。能省多少时间取决于链路和通信是否已经被计算盖住,不是少一次通信就必然快一个固定比例。

CPU offload 还多出主机与设备之间的搬运,以及 CPU 上的优化器计算。锁页内存有助于复制效率和重叠,却会占用不能供其他进程使用的主机内存。

这些选择主要改变**参数等计算时的驻留**。激活、完整参数、梯度和通信缓冲仍可能形成峰值;因此看到常驻显存下降,还得量完整训练步的峰值,不能直接推算 batch size 能翻几倍。

## 四、和同类常见做法不一样的地方

对照 Megatron-LM 的 DDP 加分布式优化器路径:它把优化器管理的数据分片,更新后再 all-gather 参数供模型使用。这里的保留旋钮则直接放在模块的前向与反向之间,决定本组完整参数何时退回分片。

两边都能把优化器工作交给 CPU,但控制位置不同。Megatron 的混合设备优化器按参数元素量目标划分 CPU 与 GPU 两组,允许把部分优化器状态和更新放到 CPU;FSDP2 的 CPU offload 策略按所管理的模块参数生效,把这些分片参数、分片梯度及优化器状态一起放到 CPU。

这个对照仅限上述 Megatron 路径,不概括它另有的全分片实现。重点是 FSDP2 把“保留多久”和“分片放哪”分别交给模块级策略,可以对不同层做不同选择。

## 五、调参与观测

保留策略既能在分片时指定,也有运行期布尔 setter;offload 策略在构造分片模块时选定。先从 `torch.distributed.fsdp` 导入对应入口与策略类,再建优化器。

| 参数或方法 | 在哪调 | 默认 | 调了之后哪个指标变 | 怎么看 |
|---|---|---|---|---|
| `reshard_after_forward` | `fully_shard(...)` | `None`:非根 `True`,根 `False` | `True` 缩短完整参数驻留,反向重新 all-gather;`False` 保留完整参数,跳过该次通信 | profiler 的反向 all-gather 与显存时间线 |
| `reshard_after_forward=k` | 同一入口,构造时指定整数 | 不启用中间档 | 原分片规模为 `N` 时,选满足 `1<k<N` 且整除 `N` 的整数;前向后参数视图由约 `1/N` 增至 `1/k`,反向聚合范围缩到 `k` | 核对小组规模和反向通信,另量峰值 |
| `set_reshard_after_forward(value, recurse=...)` | 分片后模块的方法,在完整迭代之间调整 | `recurse=True`,值必须显式给 bool | 改保留策略;默认会连子模块一起改,不接受整数档 | 只改一组用 `recurse=False`,再核反向时间线 |
| `offload_policy` | `fully_shard(..., offload_policy=...)` | `OffloadPolicy()`,不 offload | 换为 `CPUOffloadPolicy()` 后常驻设备内存下降,增加 CPU/GPU 搬运与 CPU 更新 | 参数本地张量的 device、H2D/D2H、CPU 更新耗时 |
| `CPUOffloadPolicy(pin_memory=...)` | offload 策略构造参数 | `True` | 锁页利于复制与重叠,增加锁页主机内存;关掉可缓解该内存压力 | 主机内存余量与复制耗时一起看 |

整数档不等于“保留几层”,也不等于“保留比例”。例如原分片规模为 8,填 4 表示前向后按 4 个 rank 分片。实现也接受两个端点:整数 1 转为不重分片,整数 8 转为原规模重分片;实际使用中写布尔值更清楚。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 8 卡 transformer,显存富余但反向聚合等待明显 | 只对选中的层调用 `layer.set_reshard_after_forward(False, recurse=False)` | 让这些层的完整参数留到反向,省对应 all-gather |
| 2 节点各 4 卡,原始分片规模 8,每连续 4 个 rank 对应同一节点 | 对选中的层用 `fully_shard(layer, mesh=mesh, reshard_after_forward=4)` | 多保留前向后分片,让反向聚合缩至 4 卡;mesh 排列须与目标小组一致 |
| 常驻分片仍占满 GPU,主机内存充足,接受更慢更新 | 对各层用 `fully_shard(layer, offload_policy=CPUOffloadPolicy(), reshard_after_forward=True)`,根模块也按需要显式指定 | 主机内存和搬运时间换 GPU 容量,避免完整参数在前向后继续滞留 |

组合与推荐值是按语义推的起点,不是实测最优。

用同一模型、batch 和精度比较稳定迭代:在测量前调用 `torch.cuda.reset_peak_memory_stats()`,完成并同步后读 `torch.cuda.max_memory_allocated()`;同时量整步耗时。用 `torch.profiler` 看 all-gather 与 H2D/D2H,把通信或复制的实际等待和峰值对应起来。缓存分配器保留量与活跃张量占用不同,不要只凭 `nvidia-smi` 判断参数是否释放。

| 症状 | 先查 | 然后 |
|---|---|---|
| 切换保留策略后,前向末尾 OOM | 是否在根模块调用 setter,默认递归把所有层都改了 | 缩到少数目标层并设 `recurse=False`,量整步峰值 |
| 整数档直接报取值错误 | 是否整除原分片规模,是否把整数传给了只收 bool 的 setter | 在构造入口指定合法整数,或改用布尔档 |
| offload 后仍在计算某层时 OOM | 峰值是否来自该层完整参数或激活 | 不再只盯常驻分片,结合 02 章检查完整参数的聚合粒度 |
| GPU 显存降低,训练却慢得多 | H2D/D2H 等待与 CPU optimizer step 各占多少 | 确认锁页与主机内存,仅对确实需要的模块 offload |

## 六、常见误区

**在根模块上改一个值,以为只影响根。** 运行期 setter 默认递归,它很方便,也容易把原本逐层释放的整个模型都变成完整保留。局部试验先明确目标模块和递归范围。

**看到 offload 就以为 GPU 不再存参数。** 名字容易让人联想到把整个训练搬走;实际只是分片常驻位置和优化器更新在 CPU,前反向计算仍需要 GPU 上的完整参数。若同时关闭前向后重分片,完整参数照样会留到反向。

**拿 Python 的整数 1 当布尔开。** 日常代码常把 1 和 True 混用,这里却先区分 bool 与 int:整数表示组大小,1 的效果是保留完整参数,正好不是立即释放。

**改完前向后保留的参数,以为优化器那份也跟着改了。** 完整视图或中间档视图并非原始分片参数。确实需要在前反向之间修改时,先显式 `reshard()` 回到原始分片,再按正确的分片布局操作。
