## 02 通信组：主线正确，修通信计数与对比解释

自底向上认领剩余参数、模块边界决定通信粒度，均有源码依据，章节独立合理。02a 模块认领图可保留。

必须改：

1. 第二节及 02b 把每步 AG 次数写成组数，遗漏非根组反向的 AG。按图中一个嵌入根组、四个层各调用一次、默认前向后重分片、每组一次前反向且有梯度的示例，逐层方案应为 9 次 AG / 5 次 RS；两层一组若以顺序容器作为单次调用单元，应为 5 / 3；只包根为 1 / 1。若所谓两层合组是列表中两个模块分别调用，需按实际调用和分片驻留计算，不能直接套单次容器的次数。更适合入门的改法：去掉“整步次数”列，图只比较组数和单次完整参数量，正文另用一句说明反向还会聚合。
2. “只包根白做”“峰值回到不分片水平”会抹掉优化器状态和梯度分片的收益。改为“仍有完整模型参数的驻留峰值，无法获得逐层释放的收益”。不把最大单组参数量直接等同整步峰值。
3. Megatron 共享 embedding 单独分桶的原因写错：核心是首尾 pipeline stage 对共享权重采用一致的优化器分片布局，让 DP reduce-scatter 能先于 embedding all-reduce；不是简单因为“同一权重梯度生成两次”。也不能把不同 pipeline stage 上的参数副本与同一进程中一个 Parameter 被两个模块引用当作完全相同的情况。建议缩为一句真实区别。

依据：FSDP `_fsdp_state.py:203–207`、`_fsdp_init.py:_get_managed_modules/_init_param_group`、`_fully_shard.py:141–157`；Megatron `core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py:1833–1844`，标准分布式优化器另见 `core/optimizer/distrib_optimizer.py` 的共享参数分桶逻辑。

术语：02a 的注意力/前馈改成 Attention/MLP，嵌入/输出头用 Embedding/LM Head；02b 的通信列若保留，写 all-gather / reduce-scatter。一般性中文解释保持。

## 03 重叠与预取：基本合格，修图的观测口径

CPU 提前量、显式预取、默认共享 communicator、独立 RS 进程组等核心机制都写对。03a 的三种时序对比有明确意义，可保留。

必须改：

1. 03b 顶部写“CUDA 流上看到的样子”，却把默认共用 communicator 的 AG 与 RS 画成实际同时执行；中间又画成网络串行。应把顶部标成“期望的提交/依赖关系”而非默认实际执行时间，或分开画默认与独立 communicator 的真实执行示意。m4 的初次反向 AG 若不画，明确它发生在图示区间之前。不能让同一横坐标同时表示提交时刻与完成区间。
2. “没有 FSDP::forward_prefetch 标记就是没预取”不成立：默认隐式前向重叠通过常规 pre-forward 发起 AG，不要求出现显式预取标记。改为看下一组 AG 是否提前，以及计算等待是否缩短。
3. 典型配置“默认不花额外显存”与本章预取、延迟释放缓冲的解释相冲突。改为“不额外加深默认预取”，不要承诺默认重叠没有缓冲成本。

依据：`_fsdp_state.py:_pre_forward/_pre_backward`、`_fsdp_param_group.py:FSDPCommContext/_prefetch_unshard/wait_for_unshard`、`_fully_shard.py:758–774`。术语把图中的凑参数流/打散流改为 all-gather 流/reduce-scatter 流；保留中文释义。章节无需合并或扩写。

## 04 参数的五种形态：机制选得好，修两处核心事实

“保留对象与别名关系，通过 storage resize 释放/恢复数据”抓到了实现难点。两张图分别回答数据形态与 autograd 引用，均有保留价值。

必须改：

1. 正文写“前两者共用数据”，按其列表是原始参数与分片参数，这是错的。默认共享的是分片参数与 all-gather input，以及 all-gather output 与完整参数。04a 框的位置其实画对了，应让正文与图一致；不再推导“五种形态恒等于三块常驻显存”。原始参数正常可回收，输入是否复制还取决于 dtype 等。
2. 正文与 04a 图脚写量化扩展“通信只走压缩数据那份”，遗漏同样返回为 all-gather input 的 scale。实现会把前置变换返回的所有输入纳入聚合。改成“通信传输量化数据及所需 scale 等信息，再由后置变换还原”。
3. 04b 将丢弃旧对象、另建新对象必然解释为“读上一轮旧值、静默错误”过强：autograd 保留的是当前前向保存的对象；保留旧存储会失去省内存效果，释放后另建对象则不能恢复原别名。改为说明“新对象不能恢复 autograd 已保存的引用关系”，不编造唯一故障表现。

依据：`_fsdp_param.py:66–101` 两段设计注释、`_init_sharded_param` 的新建分片存储；`_fsdp_collectives.py:337–357` 遍历所有输入并计算总通信元素。

术语：两图的“凑齐输入/输出”改 all-gather input/output，autograd 与 scale 保留英文。低精度“通信减半”可简单限定为 FP32→BF16/FP16，不展开更多边界。

## 05 初始化：主线成立，收窄一致性承诺和错误诊断

meta → 分片 → 分配本地存储 → 初始化的顺序有据，05a 三条路线有比较意义；无须重画整章。

必须改：

1. “各卡拼起来必然和普通单卡同种子完全相同”超出证据。DTensor 的 RNG 按分片位置设置 offset 并推进全局状态，这说明它协调分布式随机操作；不能据此保证任意设备、随机算子、形状和自定义初始化都与普通单卡逐元素一致。当前 offset 有按 4 对齐等实现条件，CPU mesh 随机支持也有警告。入门只需写“在受支持的 DTensor 随机操作下协调各 rank 的初始化”，不展开算子细节。
2. “各 rank 的 loss 不同就先查种子”不能作为错误诊断：数据并行不同 rank 本来就可能吃不同样本，局部 loss 正常不同。应检查初始化后聚合参数或同一输入下的输出，再比较。
3. 从 checkpoint 起步无需随机初始化，但“切法必须和当前网格一致”会误解 DCP：其加载计划可以按目标分片重新读取。改为“构造正确的目标模型与网格，由兼容的加载路径恢复”。meta 能否直接装载取决于所用 API；该基准 DefaultLoadPlanner 的 `_init_state_dict` 确有分配 meta DTensor 的逻辑，不能反过来断言所有加载前都必须手动 to_empty。具体装载流程交 11 章。
4. 对比里“Megatron 从来不完整实例化”应限定 GPU TP 并行层路径，因为下文自己就介绍了 CPU master weight 路径。05a 第三列的 1/4 是示例 TP 分片，不是所有 Megatron 参数都会按该比例缩小；图注补范围即可。图脚“初始化显存峰值”宜改“图示参数的驻留量”，避免把局部参数量当作全作业峰值。

依据：`tensor/_random.py:is_rng_supported_mesh/_compute_rng_offsets`、`checkpoint/default_planner.py:324`、`checkpoint/planner_helpers.py:_init_state_dict`、`checkpoint/default_planner.py:create_default_local_load_plan`；Megatron `tensor_parallel/layers.py:_initialize_affine_weight_cpu/_gpu`。

术语：meta、DTensor、CPU offload、checkpoint 保留原词；图中用 meta 标识“仅形状无数据”，不要每次都绕成一长串中文。普通中文解释继续保留。
