# checkpoint:存下来还要读得回去

这一页回答一件事:训练状态怎样分片落盘,又怎样在换了分片布局后继续训练。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

模型靠分片才放得下,存档时却把参数和优化器状态重新凑到单卡,checkpoint 本身就可能触发 OOM。另一种直觉是每个 rank 随手保存自己的张量,恢复时按 rank 号原样读回;可卡数变了,原来那块数据不再等于新 rank 需要的那块。

**文件保存成功和训练能够恢复,是两件事**。需要保存的不只是数据,还有每块数据属于哪个参数、处在完整张量的什么位置。分片保存与完整导出的用途区别见知识库《FSDP》,本章追到这份布局信息如何驱动恢复。

## 二、解法

FSDP2 的分片参数本身就是 DTensor,因此生成分片状态字典时,不用先把参数聚合回来。PyTorch Distributed Checkpoint,简称 DCP,接过这些带布局的张量:保存时各 rank 写本地分片;恢复时先看当前模型要什么布局,再从存档中读取与本地目标范围重叠的部分。

![一个12元素张量按3路分片保存后改为2路恢复,中间保存区块被拆给两个目标rank,读取依据张量范围而非原rank号。](/opensource/FSDP/11a-checkpoint-reshard.svg)

**稳定的连接点是参数名和全局位置**。统一的状态字典接口还会把优化器内部的参数编号换成模型中的完整参数名,让参数与对应的优化器状态一起适配新布局。读盘填入目标状态字典后,再写回模型和优化器,才走完恢复链路。

## 三、代价

分片状态字典不用参数 all-gather,不代表保存过程零通信:默认 DCP 仍要协调各 rank 的计划,还要写元数据和数据。换布局后,目标分片可能横跨多个存储区块,恢复成本也受存储吞吐与读取碎片影响。

需要给普通单进程工具一份完整权重时,仍要显式聚合。把结果搬到 CPU 能减轻 GPU 驻留,却把容量要求转移到主机;让 rank 0 持有结果也不是让完整模型消失。完整导出和分片续训是两条不同路径,应按接收方实际需要选择。

## 四、和同类大厂框架不一样的地方

Megatron-LM 的分布式 checkpoint 也按张量的全局位置恢复,不是认原来的 rank 文件。它用自己的分片描述对象记录全局形状、本地形状和偏移,加载入口接收当前模型的分片状态来决定读哪些范围。

FSDP2 则直接把训练中的 DTensor 交给 PyTorch 的统一状态字典和 DCP 接口。区别落在**谁提供分片描述**:本项目沿用张量已有的布局,不必在 FSDP 内再造一套存档张量表示。这里仅比较 checkpoint 接口,不展开两个训练框架的其他并行后端。

## 五、调参与观测

这些选项在每次获取或写回状态字典时传入,不需要为了改保存形态重启训练。保存目录与读取目录由 DCP 调用指定,各参与 rank 应采用一致的调用顺序与状态键。

| 参数 | 在哪调 | 默认 | 调后影响与怎么看 |
|---|---|---|---|
| `full_state_dict` | `StateDictOptions`,传给 `get_state_dict` 等接口 | `False` | 开启后聚合完整张量;检查返回值是否仍有 DTensor,观察获取状态时显存峰值 |
| `cpu_offload` | 同上 | `False` | 将状态搬到 CPU;与全量模式一起开启时仅 rank 0 得到完整字典,其他 rank 为空;检查各 rank 返回键与主机内存 |
| `broadcast_from_rank0` | 写回时的 `StateDictOptions` | `False` | 加载 rank 0 的完整状态并逐张量广播后切成本地布局;要求同时开启全量模式,不是读取分片存档的常规开关 |
| `strict` | 写回时的 `StateDictOptions` | `True` | 控制模型写回时的键匹配;检查 `missing_keys` 和 `unexpected_keys`,不能用关闭检查代替恢复验证 |
| `checkpoint_id` | `dcp.save` / `dcp.load` | `None` | 文件系统场景填写 checkpoint 目录;未提供存储对象时据此推导读写器,两者都未提供会报错 |

先导入 `torch.distributed.checkpoint as dcp`,以及 `torch.distributed.checkpoint.state_dict` 中的 `get_state_dict`、`set_state_dict`、`get_model_state_dict`、`StateDictOptions`。以下用已完成分片、已分配目标张量的 `model` 和随后创建的 `optimizer`;恢复在第一次反向前完成。`path` 是所有参与 rank 可访问的同一 checkpoint 目录。

| 场景 | 调用顺序 | 拿什么换什么 |
|---|---|---|
| 常规 FSDP2 训练,分片存模型和优化器 | `m, o = get_state_dict(model, optimizer)` → `state = {"model": m, "optimizer": o}` → 所有参与 rank 调 `dcp.save(state, checkpoint_id=path)` | 保持分片落盘,避免完整模型集中驻留;需要分布式存储读取流程 |
| 同结构模型换卡数续训 | 在新布局上重新执行 `m, o = get_state_dict(model, optimizer)` → `state = {"model": m, "optimizer": o}` → `dcp.load(state, checkpoint_id=path)` → `set_state_dict(model, optimizer, model_state_dict=state["model"], optim_state_dict=state["optimizer"])` | DCP 按目标分片读所需范围;需要先构造并分配新布局,不是给加载器一个空字典 |
| 向需要普通完整张量的工具导出模型 | 所有参与 rank 调 `weights = get_model_state_dict(model, options=StateDictOptions(full_state_dict=True, cpu_offload=True))`,仅 rank 0 再执行 `torch.save(weights, export_path)` | 接口更便于单进程消费,代价是完整权重聚合与 rank 0 主机内存;这份导出不含优化器 |

组合与推荐值是按语义推的起点,不是实测最优。

模型与优化器只覆盖续训状态的一部分。训练步数、scheduler、随机数状态和数据进度需要训练程序一并保存恢复;上表聚焦 FSDP 的模型与优化器路径,不宣称重启后的采样序列自动完全相同。

| 症状 | 先查 | 然后 |
|---|---|---|
| 存档时突然 OOM | 是否打开全量模式,是否让每个 rank 都持有完整结果 | 常规续训改走分片保存;确需完整导出时核对 CPU 容量 |
| 只有 rank 0 在保存,其他 rank 等住 | 是否把整个分布式状态获取和 DCP 调用也放进了 rank 判断 | 所有参与 rank 一起走分布式步骤,只把最终普通文件写入限定到 rank 0 |
| 改卡数后加载失败 | 是否保存了可描述全局布局的分片状态,目标状态是否已按新布局构造 | 用目标模型与优化器获取状态字典,交 DCP 重切;不要按旧 rank 手工拼接 |
| 权重恢复了,训练却像重新起步 | 是否只保存模型,是否遗漏优化器写回或训练程序自己的进度 | 用成对获取/写回接口恢复优化器,另核 scheduler 与数据进度 |
| 关闭模型严格匹配后仍缺数据 | DCP 读入阶段是否已经缺键,键名或结构是否发生变化 | 先修复存档和目标状态的对应关系;模型写回选项不能跳过读盘计划检查 |

## 六、常见误区

**把“分片状态字典零通信”理解成“任何保存都零通信”**。状态字典生成只是第一步;DCP 默认协调保存计划,而完整导出本来就需要聚合。看见 checkpoint 阶段有通信,先区分它发生在哪一步。

**加载器拿到路径就能自己创建新模型**。容易把它想成普通反序列化,实际 DCP 需要目标张量的形状与布局来生成读计划。先按目标布局创建并分配张量,再加载;初始化本身的路线见 05 章。

**只要张量被原地写了,就省掉最后的写回**。这在简单权重上看起来能工作,但模型加载后的处理和优化器状态不会因此自动全部完成。上表明确保留 `set_state_dict`,并把恢复放在反向之前或优化器更新之后,不要在尚未更新的反向梯度中间恢复。

**把能改分片数理解成能随意改模型结构**。重切依据同一个完整参数的名字、形状和区块位置;它不替你决定改名的层对应谁,也不自动补回没存的优化器状态。布局变化和模型结构迁移要分开验证。
