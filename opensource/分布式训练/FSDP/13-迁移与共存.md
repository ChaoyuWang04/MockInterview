# 迁移与共存:换的是接入契约

这一页回答一件事:已有 FSDP1 训练代码迁到 FSDP2,哪些只是换入口,哪些必须重新核对行为。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

两套实现从同一个包导出,都叫 FSDP,也都能分片训练。最容易出错的迁移因此不是完全写不起来,而是换了入口后训练还能跑,但通信组边界、梯度累积或精度已经变了。最后看到显存涨了、loss 偏了,却以为只是新实现性能不同。

**迁移单位是训练行为,不是配置字典**。先确认实际调用的是哪一套,再把模型接入、优化器、累积循环与恢复链路分别对齐。FSDP1 的内部结构见 12 章,这里不重新拆它。

## 二、解法

FSDP1 通过 wrapper 接管原模型;FSDP2 在原模块上加入 hooks 与分片方法,参数按原来的名字变成 DTensor。模块仍是原来的对象,并不代表里面的参数对象也没变,优化器要等分片完成后再建立。

迁移时先保留原模型结构和打算一起通信的模块边界,把逐层包装改为逐层原位分片,最后处理根模块。接着核对分片范围、前向后参数是否保留、哪些微批同步梯度,而不是寻找一个能包办所有行为的旧策略名。

![FSDP1 在模型外添加 wrapper,FSDP2 在原模型上添加 hooks 并替换为 DTensor 参数;两边分别建立优化器,通过统一状态字典入口连接模型与优化器状态,图中没有两代嵌套](/opensource/FSDP/13a-migration-contract.svg)

两套 API 在这份基准里仍然共存。**共存是可以分别选择入口**,不是把同一模型先包装一次、再分片一次。迁移后的模型与旧模型应作为独立实例比较;统一的状态字典接口提供共享连接点,隐藏部分实现差异,具体落盘与恢复见 11 章。

## 三、代价

原来的性能调参不能直接继承。参数表示、内存管理和预取控制发生了变化,即使计算结果接近,原来合适的分组也未必还是最佳选择。先固定精度与 batch 核对正确性,再独立测显存和每步时间。

依赖参数身份、局部分片形状或 wrapper 层级的外围代码也要审查。参数名保留下来,有助于 checkpoint 和按参数分组的优化器配置,但手写的参数属性、裁剪工具与自定义方法调用仍可能依赖旧对象。原位改造减少了一层包装,没有替这些集成代码自动完成适配。

旧 checkpoint 也不能仅凭文件名一致就视为可直接迁移。需要核对模型与优化器状态的规范参数名、张量形状、保存形态以及恢复接口;成功加载后还应继续一次更新,确认恢复的不只是权重。

## 四、和同类常见做法不一样的地方

Megatron-LM 在基准 fb6a123a09 中有实际调用 PyTorch FSDP2 的适配类:它挑选子模块执行分片,再处理根模块,还在分片前保存参数的自定义属性,分片后恢复。这里的重点是框架自己的模型约定也需要跟着适配,不只是替换 PyTorch 的入口。

FSDP 提供模块、参数和通信的基础契约;训练框架负责把契约接到模型与训练循环中。因此判断一段训练代码用哪一代,要追到实际调用,不能从上层适配类名字里出现「wrapper」就认定它使用 FSDP1。本段只描述已核过的适配路径,不代表 Megatron 的默认后端选择。

## 五、调参与观测

先核对 `FullyShardedDataParallel` 与 `fully_shard` 的实际 import 和调用。下表中的构造与分片选项要在作业初始化时设定;同步和重分片方法则按训练循环调用。FSDP2 入口默认 `mesh=None`、`reshard_after_forward=None`、`mp_policy=MixedPrecisionPolicy()`。

| FSDP1 配置或接口 | 原默认与含义 | FSDP2 对应位置 | 迁移后看什么 |
|---|---|---|---|
| `use_orig_params` | `False`,向优化器暴露 flat 参数;`True` 暴露原参数视图 | 没有同名用户参数,直接逐参数 DTensor;不是简单设为 `True` | 分片后重新建立优化器,检查按参数名设置的超参数 |
| `auto_wrap_policy` | `None`,不会自动细分子模块 | 没有同名入口参数;按既定边界自底向上调用 `fully_shard`,根最后 | profiler 中参数聚合的粒度是否仍符合原意 |
| `sharding_strategy=FULL_SHARD` | 默认策略;非根前向后释放完整参数,根保留完整存储供反向使用 | `reshard_after_forward=None` 默认非根为 `True`,根为 `False`,驻留目标相近 | 两代对模块注册的参数视图不同,不能按驻留相近推成逐项等价 |
| `SHARD_GRAD_OP` | 非默认,前向后保留完整参数 | `reshard_after_forward=False` 对齐这项行为 | 参数常驻仍分片;梯度累积时反向后重分片另行控制 |
| `HYBRID_SHARD` / `_HYBRID_SHARD_ZERO2` | 非默认,组内分片、组间复制,区别在前向后是否重分片 | 二维 `mesh` 加前向后重分片选择 | 检查复制与分片轴的 rank,见 07 章 |
| `NO_SHARD` | 非默认,参数与状态复制 | 不能用 `reshard_after_forward=False` 代替;纯复制路径见 07 章 | 确认需要的究竟是复制训练,还是只省去反向聚合 |
| `limit_all_gathers` | `True`,CPU 限流控制聚合提前量 | 没有同名旋钮,使用新内存管理与预取控制 | 重新观察显存和 CPU/GPU 时间线,见 03、04 章 |
| `no_sync()` | 未进入时同步,退出上下文恢复原状态 | 累积中间微批 `set_requires_gradient_sync(False)`,最后微批前恢复 `True`;默认递归 | setter 不会在作用域退出时自动恢复;若要保留反向后的参数,另用 `set_reshard_after_backward(False)` |
| `mixed_precision` | `None`;策略包含 `buffer_dtype`,子模块输入转换默认 `False`,根输入转换默认 `True` | `mp_policy` 使用 `MixedPrecisionPolicy`,dtype 默认 `None`,`cast_forward_inputs=True`,没有 `buffer_dtype` 字段 | 显式核对 buffer 与各模块输入 dtype;新策略还可设 `output_dtype`,见 08 章 |
| `state_dict_type()` 与优化器状态转换 | 默认 `FULL_STATE_DICT`,使用实现专属接口 | 统一 `get_state_dict` / `set_state_dict`,`StateDictOptions(full_state_dict=False)` 为默认分片形态 | 模型与优化器一起恢复;统一取写状态不等于完成磁盘 I/O,见 11 章 |

梯度同步与参数重分片是两项独立控制。若旧的累积循环依赖 `SHARD_GRAD_OP` 在 `no_sync()` 内保留反向后的完整参数,只迁移同步开关不够;需要另外对齐 `set_reshard_after_backward` 的行为,并在最后微批恢复预期设置。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 2 张 CUDA GPU 上先核对普通全分片训练 | 保留原模块边界,逐层及根调用 `fully_shard`,保留 `reshard_after_forward=None`,沿用 FP32,最后建立优化器 | 按非根释放、根保留的驻留目标对齐;内部参数视图仍需单独核对 |
| 同一小模型核对 2 个微批的累积 | 第 1 个微批前 `set_requires_gradient_sync(False)`,第 2 个前设 `True`,之后才更新;两边使用一致的 loss 缩放 | 减少中间同步,但累积的梯度驻留可能更大;保留参数另行设定 |
| 小模型核对迁移后的恢复链路 | 两代分别使用统一状态字典入口;资源足够时可用 `StateDictOptions(full_state_dict=True)` 做按参数名的完整张量比较,恢复后再跑一次更新 | 完整比较更直接,代价是聚合与内存;大模型保存继续走 11 章的分片流程 |

组合与推荐值是按语义推的起点,不是实测最优。

最小验收按顺序做:相同初始权重、输入、随机条件和优化器超参数,分别跑一次更新,比较 loss、归约后的梯度与更新后参数;再比较包含 2 个微批的一次累积更新;最后保存、重建模型和优化器、恢复并继续更新。浮点归约顺序可能不同,应使用与 dtype 相符的误差判据,不要求逐位相等。数值通过后再比较显存峰值与每步时间,不要把性能变化混进正确性判定。

| 症状 | 先查 | 然后 |
|---|---|---|
| 能训练,但聚合变成一次很大的通信 | 是否只替换了根入口,丢掉旧包装边界 | 恢复逐层分片,再测显存与时间 |
| 累积后各 rank 更新不一致 | 最后微批前是否重新启用梯度同步 | 修正循环中的显式开关与 loss 缩放 |
| 参数名相同,优化器更新却不对 | 优化器是否仍引用分片前参数,参数组规则是否依赖旧类型 | 分片后重建并核对每组参数 |
| 恢复成功,下一步 loss 却明显偏离 | 优化器状态、训练步数与随机状态是否一起恢复 | 与未中断的小试对照,不要只检查权重能否加载 |

## 六、常见误区

**看到原位改造,以为旧参数引用仍有效**。模型对象不换,很容易继续使用提前缓存的参数列表。FSDP2 会安装分片后的参数,优化器和参数相关工具应在这之后绑定;参数的完整名字稳定,不能替代对象身份检查。

**把 `no_sync()` 换成一次关闭调用就结束**。上下文管理器退出会恢复状态,setter 不会。小试只跑中间微批可能发现不了,要把最后同步和优化器更新一起验证。

**把 `reshard_after_forward=False` 当成旧的 `NO_SHARD`**。名字都像「不切」,实际前者只控制前向后是否保留完整参数,不取消参数、梯度和优化器状态的分片体系。先明确要保留哪个时刻的什么状态,再选入口。

**以为同一个包只能代表一代实现**。这个基准同时导出两套 API,上层框架也可能有自己的外层包装。排障先定位实际分片入口和参数类型,不要凭模块路径或类名猜版本。
