# 重叠:通信流与预取

这一页回答一件事:每一块计算之前都要凑一次参数,这笔通信怎么才能不进到每步时间里。说法都在源码基准 `217579124a`(main,仓库自报 `2.15.0a0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一个通信组要算,得先把它的参数凑齐。这笔通信只有两种命运:藏在别的计算底下,或者加在每步时间上。而藏得住的前提很不起眼——**发起它的是 CPU**。凑齐挂在模块的前置hook上,hook跑在 Python 里;要让下一个组的凑齐盖在当前组的计算底下,CPU 必须在 GPU 还忙着算当前组的时候,就已经跑到下一个组的hook。

这个领先量不是常数。层一小,一层的计算在 GPU 上一瞬间就完;host 端一重——每层发出去的小算子很多、取数据和前向抢同一个 Python 线程、循环里插了一次同步或一次日志——CPU 自己就成了节拍器。两头一夹,领先塌下来,发起点从「当前组还在算的时候」滑到「当前组算完之后」:计算流上每一格之间都空出一段,那段就是完整暴露出来的一次 all-gather。通信量一点没变,吞吐却掉了一截。

还有两处是结构上盖不住的,和领先多少无关:前向的第一次凑齐前面没有计算可盖,反向最后一次打散梯度后面也没有。

## 二、解法

三件事:通信别和计算挤在一条流上,发起点尽量往前挪,反向另起一套。

**分流**。一条流就是 GPU 上的一列队伍,同一条队伍里的东西按顺序来。所以凑参数、打散梯度各走自己的流,计算流才可能和它们同时跑。习惯上说三条流,真正建出来的比这多两条:凑齐之前要先把本卡那一段按通信要求拷进一块连续缓冲,这一步也吃 GPU,它单独占一条;二维网格下那次跨组归约再占一条。算上计算流,一次迭代最多有 5 列队伍同时在动。凑齐、拷入、打散这三条建成高优先级,免得它们的拷贝被别的任务挤到后面。

**前向不需要任何配置**。每个组的前置hook发起自己的凑齐,等它完成,再算这个组。CPU 领先的时候,当前组还在 GPU 上算,下一个组的hook已经在 CPU 上跑过了——重叠就这么白来的。拷入那条流的用处是让下一个组的拷入和当前组的通信并起来;代价是当前这块通信输出缓冲不能马上还,要留到下一个组拷完由它顺手释放,整个前向的最后一块由根模块收尾。

**反向没有这份便宜**。反向的执行顺序由 autograd 决定,hook是被梯度触发的,不存在「CPU 提前跑到下一层」这回事。所以这里换了一套:前向时每个组算完都往一张共享的单子上记一笔,反向倒着读这张单子——进入某个组的反向,顺手把单子上前一个组的凑齐发出去。这是显式的,默认就开着,深度是 1 个组。打散梯度再走自己那条流,于是计算、下一组 all-gather 与上一组 reduce-scatter 可以提前提交;默认共享 communicator 的两类通信仍在网络上串行。

**领先不够时有手动档**。可以给某个模块一张名单:进它的前置hook、它自己的参数拷出来之后,就把名单上那几个组的凑齐一并发出去。发起点从「下一个模块的hook」提前到「当前模块的hook里」,不再看 CPU 领先多少。名单上只放一个,重叠深度和默认一样,只是发得更早;放两个及以上才是更深的重叠,代价是预留显存往上走。反向也有一张同样的名单,但它是**顶替**默认那套,不是叠加。

## 三、代价

**预取一个组,就多握一份完整参数**。默认深度 1 已经意味着峰值里多出一个组的量;名单越长,同时在手的完整参数越多。显存和重叠在这里直接对冲。

**隐式的前向预取还额外扣着一块缓冲**。为了让下一个组的拷入盖在当前组的通信底下,当前这次通信的输出不能立刻释放,要等下一个组拷完。所以前向流水执行期间,可能比「一个组的完整参数」再多一块。

**跨流分配会留下碎片**。缓冲在通信流上分配、在计算流上释放,缓存分配器按流记账,跨流用过的块不会马上回到通用池。有一个私有开关能把凑齐改回在当前流上发异步通信来避开这件事,但那样隐式重叠也没了:必须自己做显式预取,而且拷入与精度转换不再和计算并行。

**反向预取是按前向的次序猜的**。那张单子记的是前向里各组结束的先后;前向跑了两遍、走了不同分支、或者一部分模块被重算包起来,反向要的次序就和单子对不上。猜错不报错,只是把不该现在凑的组提前凑出来握着,而真正要算的那个组现凑现等。

**流上重叠不等于线上重叠**。凑参数和打散梯度默认共用一个进程组,也就是同一个通信器,而一个通信器一次只处理一个集合通信。时间线上两条流各有方块,网卡上它们仍然一个接一个。

**每轮开头有一道坎**。凑参数那条流要等上一轮的优化器更新落地才能开始,默认的等法是等整条计算流——于是优化器之后随手加的任何计算,都会把这一轮的第一次凑齐往后推。

## 四、和同类常见做法不一样的地方

对照 Megatron-LM 基准 fb6a123a09 的 DDP 与分布式优化器通信路径。两边都希望将参数聚合、梯度归约与计算重叠,但开启条件和调度方式不同。

| 比较维度 | FSDP2 | Megatron-LM |
|---|---|---|
| 重叠的接入方式 | 通信流与预取属于运行机制,首轮前向建流,可调整发起时机 | 梯度归约和参数聚合各有重叠开关,默认均关闭。参数聚合还要求先采用分布式优化器、自研FSDP或相应分片优化器路径 |
| 通信调度手段 | 使用4条通信相关CUDA流,在对应流中发起collective | 常规路径通过异步collective句柄及消费前等待管理依赖,不额外创建专用通信流;多实例分布式优化器路径另建通信流 |
| 预取链 | 默认反向按记录的前向次序逆序预取下一组;前向靠CPU领先,也可用显式名单加深 | 启用参数聚合重叠后,桶按逆序串成深度1的链;子模块前置hook等待当前桶并发起下一桶,主要通过桶大小调整粒度 |
| 梯度归约触发 | 一组反向完成后归约该组梯度 | 启用重叠时,桶内所有参数梯度就绪才归约;未启用时在反向结束后归约。参数注册与执行顺序不匹配可能拖慢桶就绪、削弱重叠,实现也有重复发起下一桶聚合的告警 |

不同CUDA流或异步句柄只提供调度条件,都不能单凭接口形式判断实际通信已经并行。

## 五、调参与观测

重叠本身没有开关,它是结构的一部分;这一节能动的全是时机——发起得多早、留几份缓冲、通信走哪个进程组。它们都是分片之后挂在模块上的方法,不用重新包模块;其中建进程组的那一个要在各卡上一致地调。

| 方法 | 做什么 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `set_modules_to_forward_prefetch()` | 进这个模块的前置hook,就把名单上那几个组的 all-gather 一并发出去 | 空名单,靠 CPU 领先隐式重叠 | 名单放 1 个:深度不变,只是发得更早;放 2 个及以上:重叠更深,预留显存涨 | profiler 上看 `FSDP::forward_prefetch for …` 落在哪一格 |
| `set_modules_to_backward_prefetch()` | 同上,用于反向;**它顶掉默认的反向预取** | 空名单,默认按前向逆序预取前一个组 | 同上 | 同上,名字是 `FSDP::backward_prefetch for …` |
| `set_post_optim_event()` | 给根模块一个事件,凑参数的流只等这个事件 | 没有事件,等整条计算流 | 优化器之后的无关计算不再推迟本轮第一次 all-gather;事件用完即弃,每轮都要给新的 | 一轮开头第一次 all-gather 的起点 |
| `set_reduce_scatter_max_input_buffers()` | 最多留几份梯度打散的输入缓冲 | `1` | 打散暴露时调到 `2`,免掉「等上一次打散腾缓冲」的停顿;再大是拿显存换更深的重叠 | `FSDP::post_backward_rs_wait` 这一格还在不在 |
| `set_separate_reduce_scatter_group()` | 给打散单开一个进程组 | 关,和 all-gather 共用分片进程组 | 两个集合通信在网络扛得住时可以真并发 | 打散与凑齐在时间线上是否还首尾相接 |
| `set_unshard_in_backward()` | 这一组反向要不要凑参数 | `True` | 明确用不到的组(比如 embedding)反向省掉一次 all-gather | 反向的 all-gather 次数 |
| `unshard(async_op=True)` | 手动提前发起某一组的 all-gather,拿一个句柄回来 | — | 自己排通信顺序时用;忘了等也不会错,前置hook会替你等 | 同上 |
| `_set_unshard_async_op()` | 私有开关:凑齐改成在当前流上发异步通信 | `False` | 分配回到默认流,跨流碎片没了;但隐式重叠也没了,必须自己显式预取 | 预留显存与时间线一起看 |

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 层够大、host 端干净,只要默认的重叠 | 每层调一次分片入口、根模块最后调一次,预取相关的一个都不碰 | 不额外加深默认预取;仍有默认预取与通信缓冲的显存成本 |
| 层小或 host 端重,前向每格之前都空一段 | 每一层把下一层设成自己的前向预取名单,反向保持默认 | 多握一个组的完整参数,换回被暴露的那次 all-gather |
| 反向里打散暴露(梯度大、归约慢) | 打散输入缓冲上限调到 2,还不够就给打散单开进程组 | 峰值多一份打散输入缓冲、多一个通信器,换掉回收等待 |
| 优化器之后还跟着一段无关计算 | 每轮在优化器之后记一个事件交给根模块 | 不花显存,只挪掉一次假依赖 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测三处**。第一,计算流上有没有空格、空格正对着的是不是一次通信:这一章的每个动作在 profiler 里都有自己的名字,`FSDP::all_gather`、`FSDP::all_gather_copy_out`、`FSDP::post_backward_reduce`、`FSDP::post_backward_rs_wait` 各自带着模块名。第二,预取到底发生没有、发给了谁,看 `FSDP::forward_prefetch for …` 与 `FSDP::backward_prefetch for …` 这两行,这些标记反映显式预取;默认隐式前向重叠要看下一组 all-gather 是否已经提前发出。第三,hook的先后顺序对不对,把 `torch.distributed.fsdp.fully_shard` 这个 logger 调到 debug,每个组的前后向hook会按实际顺序打出来。

| 症状 | 先查 | 然后 |
|---|---|---|
| 前向每格计算之前都空一小段 | host 端是不是太重:同步、日志、取数据在不在同一个线程 | 先把 host 端的同步拿掉;还不够再给每层设前向预取名单 |
| 加了前向预取名单,显存涨了但时间没变 | 名单指的是不是前向真正的下一个组 | 名单按前向执行顺序给,不是按模块定义顺序 |
| 反向的凑齐盖不住,前向却正常 | 是不是自己设过反向预取名单 | 先去掉名单回到默认,再按需要加回 |
| 两条通信流的方块首尾相接,像串行 | 打散是不是还和凑齐共用一个进程组 | 给打散单开进程组 |
| 每轮第一次 all-gather 总是很晚 | 优化器之后是不是还有别的计算 | 每轮给根模块一个优化器之后的事件 |
| 反向预取的目标明显不对 | 这一轮前向是不是跑了多次、或走了不同分支 | 这种迭代别指望默认预取,自己给名单 |
| 时间线上 `FSDP::post_backward_rs_wait` 占掉一大格 | 梯度打散是不是比反向计算慢 | 把打散输入缓冲上限往上调一档 |

## 六、常见误区

**「profiler 上几条流都有方块,重叠就成立了」**。流是 GPU 上的执行序列,通信器才是网线上的排队规则。默认凑参数和打散共用一个进程组,同一个通信器一次只处理一个集合通信:两条流上确实都有方块,可在网卡上它们仍然轮流。要让两者真并发,得给打散单开一个进程组,而且网络本身吃得下。

**「预取名单越长越好」**。名单每多一个组,就有一份完整参数被提前凑出来、一直握到用完。官方对「放 2 个及以上」的说法是更激进的重叠、更多的预留显存——先涨的是峰值,先出事的是分配器。默认深度 1 是按「刚好盖住一格」定的,不是保守。

**「反向也是靠 CPU 领先自然重叠的」**。不是。反向由 autograd 驱动,hook被梯度触发,没有 CPU 提前跑到下一层这回事。反向的重叠完全靠前向记下的那张次序单子倒着走。所以「前向跑两遍再反向」「按条件走不同分支」这类写法里,预取会指向一个不对的组,而且不报错。

**「自己指定反向预取只是在默认之上加强」**。它是顶替。一旦给了名单,默认那套按逆序预取的逻辑对这个模块就不再跑;名单漏了一个组,那个组就完全没有预取。这是最容易在「我想再快一点」的时候反把事情弄慢的一步。

**「每轮第一次凑齐慢是网络慢」**。常常是在等上一轮的优化器。凑参数那条流在每轮开头要等计算流,而优化器之后随手加的指标统计、滑动平均、日志同步全在计算流上。给根模块一个优化器之后的事件,这条假依赖就断了。

**「host 端的事不影响 GPU」**。这一章的核心问题就是它。凑齐是 CPU 上的hook发出去的,CPU 一慢,发起点就落到计算之后,GPU 只能干等。数据加载、日志、指标同步和前向抢的是同一个 Python 线程,它们慢的不只是自己。

**「打散在另一条流上,输入缓冲留几份无所谓」**。默认只留 1 份:下一个组的拷入必须等上一次打散把缓冲用完。打散一旦暴露,这个回收等待就直接停在计算流上,而且它在时间线里有自己的名字,不照着名字看很难想到是在等缓冲。
