# MoE 路由与 permute

这一页回答一件事:专家算得动之前,token 怎么按专家重排、打分怎么融进一次核,跨卡时分发与合并停在哪。说法都在源码基准 `f0b6e717`(tag `v2.19.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

MoE 层里真正贵的往往不是专家矩阵乘。token 还按序列排着,每个专家看到的是跳行;路由还拆成打分、取前几名、写掩码、算辅助损失好几跳。专家数一上去,搬运和核启动把卡吃满,计算反而看不见。

跨卡时更糟:专家不在本卡,还要先按路由图把 token 送到对的 rank,算完再合回来。分发容量估小了会丢 token 或直接卡住;估大了显存被空槽吃掉。eager 路径每步还要一次主机同步,录不进图。

所以这一章的问题不是「专家怎么乘」(那是 04 章的分组线性层),而是:**token 不 permute、路由不融合时,专家计算被搬运和启动淹没。**

## 二、解法

先打分,再重排,最后合回去。顺序不能反。

**打分融进一次核。** 直觉是 softmax、取前几名、写路由图各调一次。实际路径把打分函数、取前几名、可选的组内取前几名和专家偏置写进同一套前向;中间量用三十二位攒,只在写回时落到输入类型。辅助损失另有一条融合核,系数可以在主机折好,也可以丢给设备以便录图。路由图默认按专家轴写成布尔表;专家特别多时可以按位压成无符号八位。需要稠密下标时,调用方自备一块缓冲区,路由图就不再物化。

**同一专家的 token 挤成连续行。** 路由图画完,permute 按掩码或按下标把行重排,并留下行号图给反向和 unpermute。掩码路径还会顺带重排概率、按对齐补零。合回去时按行号图写回原序;有概率就加权相加,丢掉的行在图里标成负一。量化张量走这条自定义算子时不会被先拆成普通张量;编译区域里量化输入直接拒绝,量化要挪到编译外面。

![融合路由一次核产出路由图,本卡把同一专家的 token 排成连续块再交给分组乘,算完按行号图合回原序并按概率加权;跨卡分发与合并画成虚线,只在专家不在本卡时走](/opensource/TransformerEngine/07a-moe-permute-unpermute.svg)

**跨卡只多两步。** 进程里先借专家并行组的通信句柄做一次引导。之后每步是准备加分发、本卡专家算、再合并。分发吃十六位激活,权重必须是三十二位;需要块缩放时在分发里量化,不接受已经量化好的输入。合并要求调用方先乘好取前几名的权重。零拷贝要对称内存分配,且必须给出每卡接收容量;省掉容量就是 eager,每步按实际接收数分配,录不进图。

**为什么实际不吃亏。** 重排是一次按行搬运,换来的是专家侧连续块,分组乘才能吃满。路由融合少的是启动次数,不是算法。跨卡分发不替代本卡 permute:本卡专家仍然要连续块。

## 三、代价

**路由核不算六十四位。** 输入进核会提到三十二位再算;打分结果按实现约定落在三十二位。分数量化均衡只接 sigmoid 加专家偏置,不接组内取前几名。直方图边界必须有限且下界小于上界;录图前要先认定当前版本,回放时不再做 Python 校验。

**permute 吃 CUDA 张量。** 掩码路径输出行数必须大于零;下标路径零表示按 token 数乘取前几名推断。空输入走快路径,忽略输出行数。工作区按下标路径的最大展开 token 数涨,只涨不缩。

**专家并行引导只能一次。** 组大小至少为 2。零拷贝和溢出丢弃都要求给出每卡接收容量。通信库版本不够会在引导时报错。eager 禁止调用方自备接收缓冲;零拷贝下不传持久缓冲会从池里分配,同样录不进图。

**分组乘仍在 04 章。** 本页把行排齐;切分长度怎么交给一次分组乘,不在这里再写一遍。

## 四、和同类算子库不一样的地方

本页只比专家侧 token 怎么重排、打分怎么融。Apex 核在主干 8a6508aa;FlashAttention 只写本库快照里它不是 MoE 重排库。两者都不是专家路由或 permute 库,表里那两列不是漏写接口。

| | 本库 | Apex | FlashAttention |
|---|---|---|---|
| token 怎么按专家排 | 自己的 permute 与 unpermute,掩码或下标,留下行号图再合回 | 不是 MoE 重排库。公开入口是融合归一化和融合优化器,没有按专家挤行的算子 | 不是 MoE 重排库。只有注意力核,没有路由图,也没有按专家重排 |
| 打分怎么融 | 打分、取前几名、辅助损失各有融合核;中间量三十二位 | 没有路由融合入口 | 没有路由 |
| 跨卡专家 | 借进程组句柄做分发与合并;容量、eager、零拷贝是引导时定的 | 不做专家并行 | 不做专家并行 |
| 和矩阵乘的边界 | 排齐之后交给 04 章的分组线性层 | 融合稠密是普通矩阵乘加偏置,不是分组专家 | 不适用 |

Megatron 是宿主,自己调这些入口,不进对等列。FlashInfer 不进本列。

## 五、调参与观测

这一页的参数是路由融合、permute 图类型和专家并行引导,改了要重跑该层前向或重新引导进程组。专家矩阵乘怎么一次分组见 04 章。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `map_type` | permute / unpermute | `mask` | `index` 吃 `[token, 前几名]` 下标,掩码吃 `[token, 专家]` | 路由图形状对不对;合回去是否还原 |
| `num_out_tokens` | permute | 无,调用方算 | 掩码必须大于 0;下标 0 表示按 token×前几名推断 | 输出行数是否等于路由图求和 |
| `routing_map_format` | 融合取前几名 | 布尔表 | 无符号八位按位压专家轴;自备下标缓冲则不再物化路由图 | 路由图 dtype 与尾维 |
| `score_function` | 融合取前几名 / 辅助打分 | 调用方必填 | `softmax` / `sigmoid` / `sqrtsoftplus`;分数量化均衡只接 sigmoid | 概率是否按预期归一 |
| `use_pre_softmax` | 融合取前几名 | 调用方传 | 开则先 softmax 再取前几名 | 与宿主实现是否对齐 |
| `fused_moe_aux_loss` 的 `total_num_tokens` | 辅助损失 | 无,必填 | Python 整数走主机折系数;零维整型 CUDA 张量走路图安全路径 | 录图时系数是否仍随步变 |
| `ep_bootstrap` 的 `recv_capacity_per_rank` | 专家并行引导 | `None` 即 eager | 给出则按容量定接收缓冲,可录图;省掉每步主机同步 | 是否在录图;接收行是否顶满容量 |
| `zero_copy` | 专家并行引导 | `False` | 开则要求容量,且载荷走对称内存;实验性 | 分配是否来自对称内存池 |
| `drop_on_overflow` | 专家并行引导 | `False` | 超出容量丢 token 而不是卡住;同样要求容量 | 溢出时 token 数是否变少 |
| `dispatch_fwd_quant_recipe` | 分发缓冲 | 不设则十六位收 | 目前只接 MXFP8 块缩放,在分发里量化 | 接收侧是不是分组量化张量 |

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单卡 MoE,先确认重排真发生 | 融合取前几名出掩码,`moe_permute` 用 `map_type='mask'`,专家算完 `moe_unpermute` 带回概率 | 最少跨卡;换来的是还没测容量与通信 |
| 专家很多、路由图表太大 | 融合取前几名改 `routing_map_format='bitmap_u8'`,或自备稠密下标缓冲 | 路由图更瘦;调试时不如布尔表直观 |
| 要对齐专家块再进分组乘 | `moe_permute_and_pad_with_probs` 带上每专家计数和对齐长度,合回时把补零偏移传给 unpermute | 块对齐换显存;忘传偏移会合错位 |
| 多卡专家并行,要录图 | `ep_bootstrap` 给出 `recv_capacity_per_rank`,分发合并传持久接收缓冲,不要 eager | 可录图;容量估小会丢或卡住,估大会空占显存 |
| 多卡但步长不稳、先跑通 | 引导时省掉每卡接收容量走 eager,分发不要自备接收缓冲 | 按实际接收分配;每步主机同步,录不进图 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测三处**:路由有没有融,看打分到路由图是不是一次核,不要数 Python 里有几次取前几名;permute 有没有发生,看专家输入行是不是按专家成块,而不是仍按序列跳行;跨卡看引导之后接收行是否顶着容量,eager 还要看每步有没有一次主机同步。

| 症状 | 先查 | 然后 |
|---|---|---|
| 专家数上去,耗时线性涨,矩阵乘占比却低 | token 有没有 permute;路由是不是拆成多跳 | 先走融合取前几名再 permute;矩阵乘本身见 04 章 |
| permute 直接报错 | 输入是否 CUDA;掩码的输出行数是否大于 0 | 张量放到 CUDA;输出行用路由图求和 |
| 编译区域里 permute 失败 | 输入是不是量化张量 | 量化挪到编译外面 |
| 分发要三十二位权重却拿到十六位 | `topk_weights` 类型 | 先转成三十二位再分发 |
| 引导时报通信库太旧或组太小 | NCCL 是否达到 2.30.4;专家并行组是否至少 2 | 换库或把组做大 |
| 录图失败或每步卡在主机 | 是不是 eager;零拷贝有没有自备持久缓冲 | 给出接收容量;零拷贝传持久槽 |
| 合回后数值对不齐 | unpermute 有没有带概率;补零路径有没有传偏移 | 概率与偏移和 permute 成对出现 |

## 六、常见误区

**「专家层换成分组线性就够了,token 还按序列排也行。」** 分组乘吃的是连续块。不 permute,专家看到跳行,启动和搬运仍在。04 章管乘,本章管排。

**「路由就是一次取前几名,融合可有可无。」** 打分、写图、辅助损失拆开时,专家还没算,启动已经花完。融合换的是启动次数。

**「Apex 或 FlashAttention 也有 permute。」** 对等列里这两家都不是 MoE 重排库。不要去它们的融合归一化或注意力核里找按专家挤行。

**「分发会替我做本卡 permute。」** 跨卡只把 token 送到对的 rank。本卡专家仍要连续块,permute 还在。

**「eager 更省事,录图也能用。」** 省掉容量是按步分配,带一次主机同步,契约写明录不进图。要录图就给出容量并自备持久缓冲。

**「已经量化的激活可以直接丢进分发。」** 分发只吃十六位,需要块缩放时自己在里面量化。预先量化的张量这条路是封的。
