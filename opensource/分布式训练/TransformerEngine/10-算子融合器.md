# 算子融合器

这一页回答一件事:自定义层怎么排成一条可融合管线,以及为什么前向和反向会融成不同的核。说法都在源码基准 `f0b6e717`(tag `v2.19.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

模块级融合只覆盖官方那几块积木。自己写的层——归一化、线性、激活、残差加和、集合通信——如果还是一个模块一次 launch,小核把 GPU 喂不饱,中间激活还要落地。低精度训练更糟:每一步前后多一次转换,转换本身也是内存瓶颈。

把这些步硬写成另一块融合模块,能跑到核,但改架构就要改那块巨石。官方文档把那条路叫自上而下:手调到极限,难改。

所以这一章的问题不是「归一化加线性那块现成积木怎么配」(那是 05 章),而是:**自定义层有没有排进一条管线,让融合器按前向、反向各自拼核。**

## 二、解法

自下而上。用户交出一串可融合算子,放进顺序容器。容器第一次前向时,把相邻的可融合算子收成一组,交给融合器。融合器先拆成基础算子,再跑三遍登记过的融合函数:先做前后向成对的融合,再单独做前向融合,再单独做反向融合。autograd 挂在整条管线上,因为前向和反向允许融成不同的核。

官方上手那条前馈就是例子:层归一化、线性、SwiGLU、再一段线性。前向往往把线性、偏置、激活收成一次;反向则可能把激活和偏置、线性与加和收成另一套。同一串基础算子,两套拼法。

![同一条用户管线被画成三行:上行灰框是层归一化、线性、激活、线性四步基础算子;中行绿框是前向拼法,线性加偏置加激活收成一块;下行紫框是反向拼法,激活加偏置、线性加加和另收,和前向切分不同](/opensource/TransformerEngine/10a-fwd-bwd-fusion-split.svg)

顺序容器里插进普通框架模块,两边的可融合算子会被拆成两份融合器,通道也过不去。残差、专家分发这类分叉,靠额外输入输出或命名通道在同一份融合器里走;通道名最多一个生产者,可以扇出给多个消费者。

**为什么实际不吃亏。** 现成融合层仍然最快、最省事;这条 API 换的是:新架构不必再雕一块巨石,登记一条滑动窗口就能接到同一套核。量化开关仍是外面的上下文,融合器只是去读邻居的量化器,好让转换也融进核里。

## 三、代价

**普通模块会切断管线。** 身份模块、自己写的路由、任何非可融合模块,都会把两侧拆开。通道不能跨融合器;要跨,只能走公开的额外输入输出,等于放弃这一段融合。

**通道绑死在第一次构造。** 融合器建好就把覆盖到的基础算子锁住。单独调一次算子也会建一份临时融合器。事后再改通道名会报错,换路由就要新建算子。

**前向融合和反向融合必须各自能跟未融合算子对接**——成对那一趟除外。只登记前向、反向另走散装,中间量对不上就会 silently 错或直接对不上形状。成对融合放宽这条:两半不必各自可替换,但一对必须整体等价,例如前向少存一份、反向自己重算。

**配方一变,缓存作废。** 融合结果按配方类型、反向从哪一步开始、反向覆盖三项缓存。训练和推理、重算的无梯度前向,会各留一份计划,不是每次前向现场乱拼。

**编译路径很窄。** 融了就退回急切;多算子一组也不走自定义算子;带额外张量、非张量关键字、延迟缩放,都会拒绝。文档标明这条 API 仍是实验性的,接口会变。

**手插量化算子是专家手段。** 管线被拆开时,可以在归一化后面显式插一步量化,好让下一段线性吃量化张量。量化器配置容易次优,官方自己打了警告。

## 四、和同类算子库不一样的地方

本页只比自定义层能不能排成一条可融合管线。Apex 核在主干 8a6508aa,有融合核,没有把用户算子排成管线再按前向反向分头拼的这套入口。FlashAttention 是注意力核,不是融合器。

| | 本库 | Apex | FlashAttention |
|---|---|---|---|
| 用户怎么接到融合核 | 一串可融合算子进顺序容器,融合器按登记函数拼;前向和反向可以不同 | 公开入口是现成融合核,调用方选核,没有「排管线再拼」 | 你直接调注意力核,没有管线,也没有前后向两套拼法 |
| 自定义层 | 基础算子加登记函数就能接到同一套核;成对融合允许两半一起设计 | 新层通常意味着再写一条融合核,或退回框架算子 | 不适用:不是层容器 |
| 和现成融合模块 | 现成归一化加线性仍在 05 章;本页是第二条、自下而上的入口 | 融合归一化就是产品本身,没有第二条管线 API | 不适用 |
| 切断条件 | 普通框架模块拆开融合器;通道不能跨组 | 没有管线可切断 | 不适用 |

Megatron 是宿主,不进对等列。FlashInfer 不进本列。

## 五、调参与观测

这一页的参数是算子管线怎么排、通道怎么绑、融合函数怎么登记,改了要重建容器或重跑第一次前向;量化开关见 01 章,现成归一化加线性见 05 章,矩阵乘见 04 章。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `te.ops.Sequential` | 建模型 | 无,要自己把可融合算子放进去 | 相邻可融合算子收成一份融合器;中间夹普通模块则拆开 | 第一次前向后 `_module_groups` 是一份还是多份 |
| `FusibleOperation` 相对普通模块 | 建层 | 非可融合模块原样前向 | 可融合的才进融合器 | 身份模块两侧是否仍是两段核 |
| `set_extra_input_channel` / `set_extra_output_channel` | 建算子、第一次前向之前 | 未命名则走公开额外输入输出 | 同名通道在同一融合器内接线;改绑要新建算子 | 前向参数个数是否少了那几份 |
| `output_to_caller` | 绑输出通道时 | `True` | `False` 则通道张量不返回给调用方 | 返回值是不是只剩主输出 |
| `op_kwargs` | 顺序容器前向 | 不传 | 只允许打到基础算子,给分组线性预分配缓冲 | 关键字打到复合算子会报错 |
| `register_forward_fusion` | 进程里登记 | 库已登记线性加偏置加激活、线性加偏置加加和、线性加缩放加加和、用户缓冲前向线性 | 前向滑动窗口多一条拼法 | 前向核是一块还是散装 |
| `register_backward_fusion` | 进程里登记 | 库已登记激活加偏置反向、线性加加和反向、线性加缩放反向、加和加 RMSNorm 反向、用户缓冲反向线性 | 反向另一套拼法 | 反向核切分是否与前向不同 |
| `register_forward_backward_fusion` | 进程里登记 | 默认列表空,实验性分组 MLP 自己登记 | 成对融合先于单向融合;两半不必各自可替换 | 前向少存、反向重算是否成对出现 |
| `te.ops.Quantize` | 拆开的两段容器之间 | 不插则各段自己量化 | 鼓励下一段吃量化张量;配置可能次优 | 段与段之间是不是量化张量 |
| `te.ops.Linear` | 管线里的线性 | 内部是基础线性加偏置再加集合通信 | 行切分时通信紧跟矩阵乘,前向偏置加激活那条不走 | 行并行时融合是否被通信切开 |

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 把官方前馈排成管线 | 顺序容器里依次放层归一化、线性、SwiGLU、线性,前向仍套量化上下文,反向在外 | 接到与现成融合 MLP 相近的核;换来的是实验性 API,接口会变 |
| 残差要过同一份融合器 | 归一化后做额外输出,末尾做额外输入,通道名绑 residual,且不返回给调用方 | 残差不拆管线;通道必须先于第一次前向绑好 |
| 中间夹了普通模块 | 拆成两段顺序容器,公开额外张量把残差递过去;必要时第一段末尾加量化算子 | 融合各自一段;跨段通道走不通 |
| 新激活要融进线性 | 实现基础算子,再登记前向或成对融合函数,prepend 视与库内窗口谁先匹配 | 自定义层走到融合核;登记顺序错了会永远匹配不到 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测三处**:融没融看第一次前向之后前向算子列表是不是短于基础算子个数,不要看「都换成库里的线性」;前向反向是否不同切分,看两份列表对同一串基础下标的分组;管线有没有被切断,看顺序容器中间有没有普通模块、通道报错是不是找不到更早的生产者。

| 症状 | 先查 | 然后 |
|---|---|---|
| 自定义层还是一步一核 | 算子是不是可融合的,有没有夹普通模块,融合函数有没有登记到对应方向 | 换成可融合算子并连在一起;要新拼法就登记 |
| 残差一加融合消失 | 生产者和消费者是不是被普通模块拆开,通道是不是跨了融合器 | 同一容器内绑通道,或改走两段公开额外张量 |
| 改通道名立刻报错 | 是不是已经前向过、或单独调过一次算子 | 新建算子再绑,不要改已经锁住的那份 |
| 前向看起来融了,反向数值飘 | 只登记了前向融合,反向仍散装,中间量对不上 | 补反向融合,或改成成对融合让两半一起设计 |
| 编译一开就退回急切 | 是不是已经融了、多算子、带额外张量、或延迟缩放 | 接受急切,或拆成单算子且不用延迟缩放 |

## 六、常见误区

**「我已经用了融合归一化加线性,还要这条管线吗。」** 那是 05 章的现成积木。本页是第二条入口:用户自己排算子。两条都能吃到融合核,对象不同。

**把普通顺序容器和本库顺序容器当成同一个东西。** 框架那份不会把相邻算子收成融合器,也不会按前向反向分头拼。

**通道写在第一次前向之后。** 单独 `op(x)` 也会锁通道。文档写明:要进多算子融合器,先绑再前向。

**以为前向融了反向自动融。** 三遍函数列表是分开的。官方前馈图就是前向一块、反向另一套切分。

**在管线中间塞身份模块「占个位」。** 它会把融合器劈开,通道作废。占位请用库里的恒等可融合算子。

**把实验性三个字读成「能当生产默认」。** 公开子模块开头就写了会变。新架构先在这条 API 上试拼法,定稿仍可能搬回现成模块。
