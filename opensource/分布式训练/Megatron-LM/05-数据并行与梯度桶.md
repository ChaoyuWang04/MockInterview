# 数据并行与梯度桶

这一页回答一个问题:梯度还在反向计算时,已经算好的部分怎样先开始同步,又如何保证没有漏掉累积的贡献。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

数据并行副本算完各自的数据之后,还要同步梯度才能更新参数。如果等整份模型反向结束才通信,这一段等待就完整地加在每步末尾。模型更大、数据并行组更大时,同步可能成为明显的尾部开销。

但“一个参数算出梯度就立刻发出去”也不合适:小通信太多会增加启动开销,而同一参数还可能继续接收其他 microbatch 的贡献。需要同时回答两件事:哪些梯度合成一次通信,什么时候这批梯度才真正完整。

## 二、解法

**先把梯度放进连续缓冲,再按桶同步。** Megatron 的 DDP 包装器按参数和梯度的精度、通信范围等条件组织缓冲区,参数的主梯度通常是其中的一段视图。默认的普通布局按参数注册顺序的逆序分桶,让分组尽量贴近反向的就绪顺序;一个桶不需要等整份模型算完。

**累积期间先不报就绪,最后一个 microbatch 才放行。** 反向 hook 把梯度累加到主梯度里。前面的 microbatch 暂停自动同步,最后一个才登记就绪;桶组内各参数的就绪次数达到预期后,发起通信。这里按“次数”判断,因为同一参数可能在计算图中使用多次。常规自动触发路径的首个 batch 先记录这些次数并在收尾阶段通信,后续 batch 才使用这份记录自动触发。

![稳定训练阶段,较早就绪的桶 A 发起通信时,桶 B 的梯度仍在计算;最后一个桶的通信完成后才进入梯度收尾](/opensource/Megatron-LM/05a-grad-bucket-overlap.svg)

图画的是常规自动触发路径,并把一个桶组简化为一个桶。实现还可以把不同缓冲区的桶合成一个桶组,统一安排通信;流水线调度也能显式启动同步。

**同步的落点由优化器路径决定。** 普通 DDP 使用 all-reduce,各副本得到完整的归约梯度;启用分布式优化器的常规路径使用 reduce-scatter,每个 rank 保留对应分片的归约结果。优化器状态由谁持有,留到 06 章。通信发出后仍需在收尾处确认完成,并按模型配置补做共享 embedding、序列并行相关参数等梯度同步,才能交给参数更新。

## 三、代价

**桶越小,越早出发,但通信次数更多。** 大桶更容易摊薄启动开销,也可能等到反向接近结束才就绪。最佳尺寸取决于每桶梯度的生产速度与链路,不能只盯着集合通信的带宽数字。

**不是每个流水线位置都细分桶。** 当前参考路径对非首流水线 stage、后续 model chunk 等情况关闭细分桶。源码的取舍是:这些位置的数据并行通信通常不在同一条关键路径上,没必要复制首 stage 的分桶策略。

**连续缓冲与精度都有成本。** FP32 梯度累积和通信会增加对应缓冲占用与传输字节。混合精度、专家参数和分片布局也会影响实际桶数,所以“给一个桶大小”不等于“全模型恰好分成相同大小的桶”。Megatron-FSDP 的参数分片与缓冲生命周期另见 07 章。

## 四、和同类常见做法不一样的地方

**分桶与 overlap 是共同手段,差别在它接入哪条训练路径。** DeepSpeed 的 ZeRO 同样有连续梯度缓冲、分桶和通信重叠。Megatron 这里把它们放在 DDP 包装器里,由 microbatch 调度控制何时允许同步,再按普通优化器或分布式优化器选择集合通信。

PyTorch FSDP 的概括性对照是围绕模型分片组织参数与梯度通信。本章这条 Megatron DDP 路径即使不启用优化器分片,也能通过梯度桶隐藏一部分同步等待;不要把“通信重叠”和“状态分片”当成同一个开关。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**在哪调。** 以下使用参考训练入口的 CLI;直接使用 Core 时对应 DDP 配置对象。自定义训练循环还要正确调用 `no_sync`、`finish_grad_sync` 和清零接口,它们是运行时协议,不是额外的启动参数。

| 参数 | 默认 | 调整的作用 | 怎么看 |
|---|---|---|---|
| `--overlap-grad-reduce` | 关 | 允许梯度同步覆盖反向计算;关闭时在收尾处同步 | 稳定步通信时间线与每步耗时 |
| `--ddp-bucket-size` | 无显式值 | 按元素数给出分桶目标。参考入口默认取 `max(40000000, 1000000 × DP含CP组大小)`;不开 overlap 时取消细分 | 启动桶清单、实际元素数与 padded size |
| `--ddp-num-buckets` | 无 | 从本地模型参数量推导目标桶大小;与上一项互斥,不保证最终恰好得到这个桶数 | 不同 dtype/专家缓冲的桶清单 |
| `--use-distributed-optimizer` | 关 | 常规梯度通信从 all-reduce 改为 reduce-scatter;同时改变优化器状态布局 | 通信轨迹;状态成本见 06 章 |
| `--accumulate-allreduce-grads-in-fp32` | CLI 开关默认关 | 将梯度累积与归约设为 FP32,增加缓冲和通信字节。BF16 常规配置会按主梯度精度自动打开,应看最终配置 | DDP 配置与每桶梯度 dtype |
| `--check-for-large-grads` | 关 | 在桶通信前检查异常大的局部梯度,增加检查开销 | `found unexpected large grads in bucket` |

**配置起点**:以下是已有可运行稠密模型配方上的增量,假设使用支持该配方精度的 GPU、DP 大于 1、不开 Megatron-FSDP,先在 PP 为 1 的环境比较。模型、global batch 与 microbatch size 保持一致。

| 场景 | 增量设置 | 代价与前提 |
|---|---|---|
| 建立同步基线 | 不加 `--overlap-grad-reduce`,保留原优化器路径 | 通信主要留在反向之后,便于确认稳定步基线 |
| 观察默认重叠效果 | 加 `--overlap-grad-reduce`,桶大小留默认 | 等待可能缩短,也可能因通信与计算争用而收益有限 |
| 默认桶启动太晚 | 在上一组加 `--ddp-bucket-size 10000000` | 用更多较小通信换更早发起;1000 万是实验起点,不是实测最优值 |

组合与推荐值是按语义推的起点,不是实测最优。

**看哪里。** 启动日志中的 `Setting up DistributedDataParallel` 给出配置;`Number of buckets for gradient all-reduce / reduce-scatter` 和后续参数清单给出实际布局。稳定阶段比较每步耗时与通信轨迹。`all-grads-sync` 计时包住梯度同步收尾,在 overlap 路径中主要反映这里仍需等待的部分,不能直接当成整步所有梯度通信的总时长;首步的触发行为又与后续步不同。

| 症状 | 先查 | 然后 |
|---|---|---|
| 开了 overlap,首步仍像整段通信 | 是否还在记录首个 batch 的就绪次数 | 观察后续稳定步,再判断 overlap 是否生效 |
| 改桶大小却没出现预期的小桶 | overlap 是否开启,当前 PP rank 与 model chunk 是否允许细分 | 看实际桶清单;再查单个大参数、dtype 与专家缓冲划分 |
| 桶越小反而越慢 | 小通信次数与带宽利用率,是否还有足够反向计算可覆盖 | 比较更大桶,用总步耗时选取舍 |
| 报 `Communication call has not been issued` | 最后 microbatch 是否恢复同步,各参数 hook 次数是否匹配首批记录 | 检查自定义循环、未使用参数和变化的执行分支;不要只调超时 |
| 梯度同步后仍有额外通信 | 是否属于 embedding 或序列并行等附加同步 | 按对应进程组确认职责,不要把它们算作同一个 DP 桶 |

## 六、常见误区

**「no_sync 就是不算梯度。」** 名字容易让人以为它跳过反向。实际上这里仍把各 microbatch 的贡献累加到主梯度,只是暂时不登记自动通信的就绪状态。自定义循环把最后一次反向也留在这个上下文里,会破坏同步触发条件。

**「桶大小写的是字节。」** 通信工具常显示字节量,但这个参数使用元素数。同样的元素数改成 FP32 梯度,占用和传输量会变化;桶边界还要尊重参数与布局,不应把目标大小当成严格切片上限。

**「finish 里还有等待,说明 overlap 没起作用。」** 最后就绪的桶本来就可能没有足够计算来遮住通信,收尾等待不能凭空消失。应同时看前面哪些通信已经被覆盖,以及整步是否变短。

**「首步记录好了,以后任何动态分支都能照常跑。」** 就绪计数是按首个 batch 记录的。之后若参与反向的参数或使用次数变化,就不能再假设原有自动触发条件仍然成立;这与简单调大桶或延长超时是两类问题。
