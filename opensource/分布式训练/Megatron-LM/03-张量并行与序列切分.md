# 张量并行与序列切分

这一页回答一个问题:一层权重或一条序列在单卡上装不下时,沿哪个轴切开,又在哪些位置交换数据。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**模型变宽,权重和训练状态变大;序列变长,激活占用上升。** 两种压力不能只靠同一种切分解决。到底何时显存不足,还取决于层数、microbatch、精度、重算策略和卡的容量,不存在与硬件无关的宽度或序列长度阈值。

把矩阵乘分到更多卡上,又会遇到另一个问题:每卡计算变短,层内通信却仍要发生,逐渐藏不进计算。Megatron 的选择因此不只是「切几份」,还包括**哪些区域保留切分,在哪个边界交换数据**。

## 二、解法

**第一刀是张量并行。** Megatron 把按输出维切的线性层和按输入维切的线性层配成一对:前者各算一部分输出,后者各算一份部分和。标准稠密 Transformer 块中,attention 的 QKV 投影与输出投影是一对,MLP 的两层是另一对。这样前向只需在每对末尾做一次 all-reduce,不必在中间把完整张量拼回去。反向则可以先异步归约输入梯度,再计算权重梯度,争取把通信藏进矩阵乘。

**第二刀是序列并行。** 张量并行之外的 LayerNorm、dropout 等区域原本在各卡上重复保存激活,而这些操作逐 token 独立。Megatron 把这些区域沿序列切开,进入矩阵乘前 all-gather,出来时 reduce-scatter。按常见集合通信分解计算,它与原来的 all-reduce 有相当的通信字节量,但调用边界增加了;收益是少存重复激活,并不意味着通信耗时一定不变。

![标准稠密 Transformer 块的前向中,TP 在两段末尾做 all-reduce,SP 将其换成段首 all-gather 与段末 reduce-scatter,默认 P2P CP 另外在 attention 内交换 KV。](/opensource/Megatron-LM/03a-where-the-exchange-happens.svg)

**第三刀是上下文并行。** 它使用独立于张量并行的一组卡,把输入和激活沿序列分开。标准稠密块里的线性层、LayerNorm 继续处理本地 token,只有 attention 额外需要 CP 通信,让本地 query 看见其他分段的 key 与 value。默认路径按环形交换 KV,也支持先 all-gather、按头 all-to-all 及分层组合;图中画的是默认路径,原有 TP/SP 通信仍然存在。

因果 attention 中,越靠后的 token 要看见的前文越多。默认的等长序列分配把序列切成卡数 2 倍的段,每卡拿一头一尾,平衡 attention 工作量。下面用按段号递增的简化负载解释配对,条长不代表实际耗时。

![3 张卡各取 2 段时,连续分配得到示意负载 3、7、11,首尾配对得到 7、7、7;数字只是按段号计重的演示,不能换算成训练加速比。](/opensource/Megatron-LM/03b-zigzag-load-balance.svg)

这张图不适用于所有层。Mamba 的按头切分路径在卷积和状态扫描前用 all-to-all 把序列分片换成头分片,让每个本地头看到完整序列,算完再换回来。混合模型若在不同层使用不同序列布局,层边界还需额外转换。

**随机数也要跟着切分边界走。** 复制区域要维持副本一致,切分区域要使用彼此区分的随机流,不能要求所有卡的 dropout 掩码一律相同或一律不同。Megatron 分开维护默认流、TP 流和专家流;启用 SP 时,Transformer 块使用 TP 随机流。checkpoint 还要恢复这些状态,仅重新设一个 seed 不等于接着原来的随机序列训练。

输出层也延续这个思路:词表切开后,普通词表并行交叉熵归约每 token 的最大值、目标 logit 和指数和,无需先拼完整 logits。另有实验性的权重按需聚集路径,在 TP 分片之上继续减少常驻权重,使用前重建的是本卡的 TP 权重片,并非全模型权重。

## 三、代价

**层内通信反复发生,优先把 TP 留在高速互联域。** 跨机并非不支持,但是否划算取决于互联、矩阵大小和重叠效果。长序列场景可以用 CP 分担激活压力,避免只靠提高 TP 把每卡矩阵乘越切越小。

**异步下发不等于已经重叠。** 本地线性层的反向路径依赖通信先于相关计算下发;环境设置会影响这个顺序,实际收益仍要看 profiler。Transformer Engine 的分块重叠是另一个配置入口,不能把所有通信优化都归结成同一个开关。

**切分受张量形状约束。** 头数、query 分组和序列长度必须满足相应整除条件;Mamba 按头切的路径还受每卡头数限制。CP 降低本地序列相关激活,但通信缓冲区、参数和临时张量不因此全部等比例缩小。

## 四、和同类常见做法不一样的地方

PyTorch FSDP 的状态分片路线侧重参数、梯度和优化器状态的驻留;本章的 TP 则把一次线性计算本身分给多卡,SP 与 CP 继续处理激活的分布。两类手段解决的压力不同,可以组合,不能用「状态已经分片」推导出「长序列激活也已经分片」。

Megatron 把切分规则和通信边界直接纳入线性层及其求导路径。接入模型时要匹配这些层的输入输出契约,收益是能安排单次矩阵乘前后的通信。仓库里的实验性权重按需聚集又增加了一个选择:按单个权重重建 TP 分片,并预取后续权重。这里描述的是 Megatron 的组织方式,不是其他框架的能力上限。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

下面使用训练命令行入口。Core 库用户设置对应配置对象;实验性的 `--yaml-cfg` 使用嵌套结构并忽略普通 argparse 参数,不能把命令行参数名原样搬成一张平铺 YAML 表。

| 参数与入口 | 默认 | 调整影响 | 怎么看 |
|---|---|---|---|
| CLI `--tensor-model-parallel-size` | 1 | 增大后每卡权重片与部分激活更小,矩阵乘也更小;通信可能成为瓶颈 | 显存峰值、step time、每 GPU 吞吐 |
| CLI `--sequence-parallel` | 关 | 切开 TP 复制区域的序列激活;TP 为 1 时训练入口会警告并关闭它 | 启动警告、显存峰值 |
| CLI `--tp-comm-overlap` | 关 | Transformer Engine 的 TP 通信与 GEMM 重叠;要求先启用 SP | profiler 的通信与 GEMM 时间线 |
| CLI `--tp-comm-overlap-cfg` | 无 | 指定逐层重叠配置文件,进一步调整上述路径 | 与默认重叠配置对比 step time |
| CLI `--context-parallel-size` | 1 | 增大后每卡处理更短的序列,增加 CP 通信;标准组合总卡数为 TP×CP×PP×DP | 显存峰值、tokens/s |
| CLI `--cp-comm-type` | `p2p` | `p2p` 环形交换 KV;`allgather` 先聚齐 KV;`a2a` 换成头分片;`a2a+p2p` 分层组合。Core 字段默认 `None`,文档将聚集写作 `all_gather` | attention 区间耗时 |
| CLI `--hierarchical-context-parallel-sizes` | 无 | 分层 CP 度数,乘积必须等于 CP;`a2a+p2p` 要求提供 | 启动校验与跨域通信量 |
| CLI `--attention-cp-layout` / `--linear-cp-layout` | 均为 `zigzag` | 两类层的序列布局;不同布局可能增加边界 all-to-all。启用 CP 的 softmax attention 当前要求 `zigzag` | 层边界通信 |
| CLI `--linear-cp-mode` | `headwise` | 递归/线性 attention 的 CP 路径;`chunkwise` 要求线性层布局为 `contiguous` | 启动校验、层耗时 |
| CLI `--tensor-parallel-num-weight-shards` | 无,回落到 TP 度数 | 超过 TP 度数时启用额外权重分片与按需聚集;实验特性,要求 Transformer Engine ≥2.19 | 常驻显存与聚集开销 |
| 进程环境 `CUDA_DEVICE_MAX_CONNECTIONS` | 本章不替 CUDA 指定默认值 | 本地 TP 异步反向路径建议设为 1,保证所依赖的下发顺序;其他重叠路径应按各自要求配置 | 源码警告、profiler |

**典型配置**。下面是已有完整训练命令的增量,不是完整命令或实测最优值。假设使用具有 NVLink 的 NVIDIA GPU、Transformer Engine 稠密 GPT 路径,模型头数和张量形状满足切分条件;数据、精度、global batch 等沿用原作业。

| 场景 | 配置增量 | 交换条件 |
|---|---|---|
| 单机 8 卡,模型宽度带来显存压力,先试 TP=4、DP=2 | `--tensor-model-parallel-size 4 --sequence-parallel`;本地异步 TP 路径启动前设 `CUDA_DEVICE_MAX_CONNECTIONS=1` | 以层内通信换更小的权重和激活片;PP=1、CP=1 |
| 同样 8 卡,长序列激活仍吃紧,试 TP=4、CP=2、DP=1 | 上一组加 `--context-parallel-size 2 --cp-comm-type p2p`;序列长度为 4 的倍数 | 每卡 CP 序列份额减半,增加 attention KV 交换;保持 global batch 时 microbatch 数可能变化 |
| 上一组能运行但 TP 通信暴露明显 | 再加 `--tp-comm-overlap`,先使用默认重叠配置 | 以重叠所需缓冲和调度开销换时间;是否更快由 profiler 与端到端测量决定 |

组合与推荐值是按语义推的起点,不是实测最优。

**看哪里。** 固定模型、有效序列长度、global batch 和卡数后,step time 可以直接比较;同时看 tokens/s、日志中的 `throughput per GPU (TFLOP/s/GPU)` 与显存峰值。卡数或有效 token 数改变时,先统一工作量口径。profiler 可关注 `qkv`、`core_attention`、`linear_proj`、`linear_fc1`、`linear_fc2` 区间,判断通信是否真正被计算覆盖。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报整除错误 | attention 头数、query 分组还是序列长度 | 调整相应切分度;普通 CP 启动要求序列长度为 2×CP 的倍数 |
| SP 开了但显存变化不明显 | TP 是否为 1、主要占用是否来自参数或其他激活 | 查启动警告,固定负载比较实际峰值;理论显存报告仅作估计 |
| 提高 TP 后 step time 变长 | 每卡 GEMM 是否过小、通信是否跨慢链路 | 降低 TP 做对照;长序列可尝试 CP 分担 |
| 异步通信仍暴露在关键路径 | 使用的是本地反向路径还是 TE 重叠路径 | 按对应环境与 SP 前提排查,再检查时间线 |
| 混合模型层边界出现 all-to-all | attention 与线性层布局是否不同 | 确认算法要求后再决定是否统一布局 |

## 六、常见误区

**「SP 没写进理论显存报告,就是没开。」** 容易把公式分支当作运行状态。该报告只有在 SP 与选择性重算同时满足时才走对应估计函数;应结合启动配置和警告判断,不能只看公式名字。

**「固定 seed,更换并行度后 loss 就必须逐位相同。」** seed 只是随机流起点,切分域、随机数消费顺序和归约顺序都可能变化。排查复现先保持拓扑与配置一致,续训还要恢复 checkpoint 的随机数状态。

**「首尾配对图的 11 比 7 就是训练加速比。」** 图里的单位只是让负载不均衡显形。真实时间还包含 kernel、通信、其他层和同步,必须用同负载的运行结果判断。
