# 可观测、确定性与容错

这一页回答一个问题:训练变慢或出现异常数值时,怎样定位、重跑诊断,再决定是否恢复作业。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**异常数值和进程失效不是同一种故障。** loss 突然变大,可能来自输入、算法、非确定性计算或设备问题;rank 卡住或退出,则可能根本没有结果可供比较。只记录一个最终loss,很难判断发生在哪一步;直接重启又可能丢掉诊断线索。

Megatron 把这件事拆成三层:先观察阶段与rank差异,对可疑结果复用同一输入重跑,需要时再借助checkpoint和外部恢复机制重启。前一层提供证据,不会自动代替后一层。

## 二、解法

**观测先回答“在哪慢、哪里异常”。** timers记录阶段耗时,可比较不同rank的范围;OpenTelemetry把训练、评估、checkpoint和通信等已埋点边界连成trace,并记录训练指标。能耗监控读取GPU能量计数并聚合,张量观察接口则允许特定调用方订阅已经埋点的张量。后两者不是自动扫描整个模型的诊断器。

**结果重跑回答“相同输入能否复现”。** 状态机在optimizer更新前保存可回退状态,包括RNG及调用方注册的额外状态,并让数据迭代器能够回退。某个已接入检查点拒绝结果时,各rank协调后重跑同一次forward/backward,比较对应检查点的结果是否在容差内一致。

![fatal结果校验失败后先同GPU重跑;不可复现提示瞬态错误并退出,可复现则保存诊断checkpoint,换GPU重跑;不同GPU仍复现指向输入或应用,不同则提示原设备持久错误。](/opensource/Megatron-LM/17a-rerun-diagnosis.svg)

图限定**fatal校验失败路径**。同GPU无法复现时,状态机报告可能的瞬态错误并退出,可以从此前checkpoint恢复;同GPU能够复现时,才请求保存诊断checkpoint并退出,让下一次作业尝试在不同GPU上重跑。若又落到原GPU,会要求再调度。换GPU后仍复现,说明原结果可能是输入和应用本身产生的;换GPU后不再复现,才提示原设备可能有持久错误。这里是诊断线索,不是硬件故障的最终证明。

**进程恢复另有入口。** FT集成用外部监控器观察初始化、训练step与checkpoint阶段的超时,需要对应launcher与依赖。进程内restart包装器则负责清理状态和重新进入训练函数,并结合恢复状态继续工作。它们处理作业的失效与重启,不替代上面的数值比较。

## 三、代价

**观察会影响被观察的执行。** 实际timer启停会同步CUDA,可选barrier还会等待其他rank;扩大计时范围可能扰动原有重叠。trace导出、张量统计、重跑和checkpoint也都有成本。先用低粒度定位,再在小范围加细节,比全程打开所有记录更容易解释结果。

**重跑需要可回退状态和可比较的执行。** 保存随机种子不等于保存全部运行状态;自定义模块在forward中改变的状态也要纳入保存/恢复约定。确定性模式会限制部分融合和通信选择,但不能据此承诺任意硬件、拓扑、并行度和软件版本之间逐bit一致。

**监控不是存档。** 超时判断可以触发恢复动作,但能够回到哪里仍取决于已有checkpoint、数据进度与恢复实现。FT会跳过若干初始慢step再监控稳定step,否则编译和初始化时间容易被误判成卡死。故障注入只用于验证这些响应链,不应混进正常性能测量。

## 四、和同类常见做法不一样的地方

PyTorch FSDP的模型外部分片路线解决状态如何分布,而这里讨论的是训练循环如何提供证据并管理异常步骤。Megatron把结果验证放到forward/backward迭代控制中,让输入回退、RNG恢复、诊断checkpoint与后续重跑形成明确流程。

因此评估容错能力时,要分别检查数值异常有没有检查点、挂起有没有监控、恢复有没有可用状态。能重启一个进程,不等于已经确认了异常数值的原因。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数与入口 | 默认 | 调整影响 | 怎么看 |
|---|---|---|---|
| CLI `--timing-log-level` | 0 | 可选0/1/2,增大可启用更多已分级计时点 | 阶段耗时与计时引入的同步影响 |
| CLI `--timing-log-option` | `minmax` | 可选 `max`、`minmax`、`all`,改变rank耗时汇总展示 | 慢rank与全体范围,别只看均值 |
| CLI `--otel-enabled` | 关,环境配置可开启 | 启用可选OpenTelemetry集成,需nemo-lens/OTel及导出配置;缺依赖时no-op | exporter收到的span与metrics,不是仅看命令行成功 |
| CLI `--log-energy` | 关 | NVML能耗读取与跨rank聚合,依赖pynvml和硬件计数支持 | Joules与有效token数,缺数据不能当零功耗 |
| CLI `--rerun-mode` | `validate_results` | 已接入检查调用可触发结果诊断;`disabled`关闭重跑机制 | Result validation与各次rerun日志、退出码 |
| CLI `--deterministic-mode` | 关 | 校验算法选项/环境并启用PyTorch确定性算法;当前要求关闭交叉熵融合、TP通信重叠等冲突项 | 启动校验与固定条件下重复运行差异 |
| CLI `--enable-ft-package` | 关 | 启用nvidia-resiliency-ext FT集成,须用 `ft_launcher`;当前CLI标注内部使用 | setup/step/checkpointing各阶段监控 |
| CLI `--ft-num-warmup-iters` | 5 | 初始step不进入稳定step超时监控 | 编译/初始化与稳定step耗时差异 |
| CLI `--inprocess-restart` | 关 | 使用可选inprocess包装器;缺扩展时警告并返回原训练函数 | 是否实际初始化wrapper及恢复日志 |

**典型配置**。以下是已有兼容训练命令的增量,保持模型、数据、并行度和软件环境固定;不是完整训练命令,也不主动执行故障注入或重启。

| 场景与前提 | 配置起点 | 验证目标 |
|---|---|---|
| step耗时波动,先找rank/阶段差异 | `--timing-log-level 1 --timing-log-option minmax` | 定位最慢阶段,再短时扩大观测,同时比较无额外计时基线 |
| 已安装遥测依赖并配置可达OTLP接收端,需要跨阶段trace | 加 `--otel-enabled` | 确认实际收到span,再按需要扩充span组/导出rank范围 |
| 已接入结果校验,准备复现可疑数值 | 保持 `--rerun-mode validate_results`,在符合启动约束的配方上加 `--deterministic-mode` | 同输入重跑的可比性与状态回退;不要同时换拓扑或并行度 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 日志正常但遥测端没有数据 | 依赖、master开关、导出rank与exporter配置 | 验证接收端再扩大span范围;no-op不代表网络正常 |
| 同GPU重跑结果不一致 | RNG/数据是否回退、算法是否确定、额外状态是否注册 | 按瞬态错误线索调查,保留日志;不能先认定是坏GPU |
| rank等待或频繁超时重启 | 慢step是否集中在warmup/checkpoint,FT是否实际初始化 | 调整有证据的阶段超时,验证checkpoint恢复,不要仅放大所有timeout |

`capture_tensor_observations` 是调用方注册观察器的上下文接口,未注册时观察点不工作;重计算可通过暂停观察避免重复计数。`fault_injector` 的hang/crash等注入需要可选扩展,与rerun内部模拟“结果比较异常”的注入不是同一层。这里不提供会中断现有作业的注入配置。

## 六、常见误区

- **“同GPU复现异常,就是坏卡。”** 还需要换GPU比较;不同GPU也复现时,输入或应用原因仍在候选中。
- **“瞬态异常分支会保存新的诊断checkpoint。”** 图中的fatal路径在同GPU不可复现时直接退出;可复现才进入保存并换GPU的分支。
- **“默认结果验证覆盖所有张量。”** 它依赖实际接入的检查调用,首次迭代还会跳过该结果拒绝逻辑;不是全模型扫描。
- **“重跑一次就完成故障恢复。”** 诊断比较、作业restart和从checkpoint续训是不同动作。非fatal检查可以记录并继续,不能套用图中的退出路径。
- **“确定性模式保证换卡数后完全相同。”** 算法限制、相同输入和可回退状态是前提,跨布局的数值等价需要单独验证。
