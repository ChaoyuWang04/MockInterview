# 权重搬家:换并行度读回与直搬推理侧

这一页回答一个问题:权重已经按训练布局分散到各 rank,怎样换一套布局恢复,或者直接交给推理模型。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**rank 的局部张量不是权重的永久身份。** 同一个矩阵,训练时可能被切成 2 份,推理时切成 4 份;同一层也可能随 PP 布局换到另一个 rank。如果存下来的只是「第几张卡上的字节」,接收方就不知道这些字节属于全局矩阵的哪里。

这产生两种需求。训练重启要从 checkpoint 恢复模型与训练状态;RL 回路则要反复把最新训练权重交给推理侧。它们都需要理解逻辑分片,但前者经过存储,后者直接在活着的模型之间传输。

## 二、解法

**落盘链用逻辑坐标描述分片。** 每份张量带上全局名称、全局形状、本地形状、偏移与副本标识。保存时记录这些关系;恢复时先按新配置构建模型,由目标模型声明自己需要的分片,加载策略再从存档中读出对应区域。不是先把完整模型集中到某张 GPU,再统一切开。

![同一个逻辑矩阵原来沿列切为2份,存档保留名称、形状和偏移,新布局的4个rank分别请求各自区间;中间长条是逻辑坐标,不是一块完整GPU缓冲。](/opensource/Megatron-LM/13a-checkpoint-layout.svg)

**训练恢复还要回答“接着哪一步训练”。** 除模型权重外,还涉及 optimizer 主参数与动量、学习率调度、iteration、RNG 等状态。模型分片能够重组,不代表 optimizer 的旧扁平缓冲也能重组。分布式优化器默认使用依赖缓冲布局的存法,主要允许改变 DP;需要改变模型并行布局时,应在保存前选择按模型参数组织 optimizer 状态的格式。该路径有额外转换与聚集成本。

**在线 refit 则先规划,再搬对应切片。** 各 rank 交换源、目标参数元数据,每个 rank 独立生成相同的全局传输顺序,只保留自己参与的发送和接收。规划会处理 TP 切片、PP 层名与 EP 专家身份;已经支持的 GTP 布局也按逻辑区域求交。执行器通过传输服务搬运切片并写入目标模型,后续同布局 refit 可以复用计划。

![源rank持有矩阵两半,目标rank需要四个区间;元数据先汇总以生成一致计划,权重数据再按交集点对点发送,不经过checkpoint。](/opensource/Megatron-LM/13b-online-refit.svg)

这条链搬的是模型参数及持久 buffer,例如 router 的专家 bias,并不把训练 optimizer 一起交给推理侧。目标需要特定低精度格式时,还可在接收侧执行已接入的转换。MXFP8 路径需要先准备目标持久缓冲;随后原位更新,保持已经捕获的设备地址。

## 三、代价

**可迁移性需要元数据和转换成本。** checkpoint 要读写存储;可重排的 optimizer 格式还要把训练用的扁平缓冲还原成参数形状。不能在恢复命令里临时打开一个选项,就把已经保存的受限格式变成完整可重排格式。

在线 refit 避开了磁盘往返,仍要支付首次元数据交换、计划构建、网络传输和临时缓冲的成本。直接 GPU 传输、经过 CPU 暂存、RDMA 或分组传输的依赖与拓扑要求不同。按参数分批可压低部分执行暂存,但单个完整参数仍可能超过预算,也不是所有后端都按相同方式分批。

**换布局不等于原样重放训练。** 当前分布式 checkpoint 加载在 TP、PP 或 world size 改变时会忽略旧 RNG 状态。即使权重与 optimizer 成功恢复,也不能据此承诺逐步数值一致。模型结构、分片规则、格式和 optimizer 实现仍要兼容;新增层或改变模型家族另有迁移流程。

## 四、和同类常见做法不一样的地方

DeepSpeed和Megatron都能保存训练状态,但checkpoint格式与重排条件必须分别核实。Megatron还把在线refit作为另一条路径,因此“恢复训练”与“刷新推理权重”应分开选择入口。

| 对比维度 | DeepSpeed训练checkpoint入口 | Megatron权重搬运路径 |
|---|---|---|
| 保存对象 | 引擎保存模型和优化器等状态,调用方可附加自己的训练状态 | 模型与训练状态由参考层组织,分片描述保留全局权重身份 |
| 改变布局前先查什么 | 检查所用ZeRO/checkpoint格式及对应加载或转换路径 | 检查目标TP/PP/EP语义,以及optimizer存档是否保留可重排的参数语义 |
| 调用方的职责 | 参与rank协同存档,并管理引擎之外的状态与恢复时机 | 目标模型先声明所需分片;在线refit则先准备源/目标模型和通信组 |
| 本章讨论的传输边界 | 此处对照的是落盘保存与加载接口 | 除落盘恢复外,refit直接交换元数据并搬运模型权重切片 |

最后一行是在区分接口用途,不是断言DeepSpeed整个项目没有其他权重传输能力。任何一条路径成功,都不能证明另一条路径支持相同状态与布局。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

下表同时列出训练 CLI 与 refit API 的初始化选择。`swap_model_weights` 本身是作业运行期间重复调用的操作;所选布局、通信组与依赖应在启动时准备好。

| 参数与入口 | 默认 | 调整影响 | 怎么看 |
|---|---|---|---|
| CLI `--ckpt-format` | `torch_dist` | 可选 `torch`、`torch_dist`、`torch_dcp`、`fsdp_dtensor`;不是可任意互换的封装名 | 实际识别格式、目标训练实现与加载校验 |
| CLI `--dist-ckpt-optim-fully-reshardable` | 关 | 保存分布式optimizer时从 `dp_reshardable` 改用 `fully_reshardable`,为兼容的TP/PP/EP/DP重排保留模型参数语义 | 存档metadata、保存耗时、主机/设备内存峰值 |
| CLI `--no-load-optim` / `--no-load-rng` | 未指定,解析默认 `None` | 显式跳过对应训练状态;适合只取权重,不等同于完整续训 | optimizer初始化、iteration与scheduler恢复策略 |
| CLI `--exit-on-missing-checkpoint` | 关 | load路径不存在时退出,避免无意随机初始化 | 加载日志与选中的iteration |
| CLI `--refit-method` | `gloo` | 当前有 `nccl`、`nccl_m2n`、`gloo`、`nvshmem`、`nixl` 五项 | refit端到端时间、链路流量、暂存峰值 |
| API `swap_model_weights(..., refit_method=...)` | 必填,无默认 | 显式选上述后端或传入 `CopyService`;源/目标模型及通信组须已建立 | 首次规划与重复refit分开计时 |
| CLI `--refit-execution-batch-bytes` / API `execution_batch_bytes` | `None` | 软性每rank暂存预算;单参数不拆分。NIXL仍整模型提交,NCCL M2N用原生分组限制 | 峰值暂存和分批开销,不能当硬显存上限 |

传输服务对应 `NCCLCopyService`、`NCCLM2NCopyService`、`GlooCopyService`、`NVSHMEMCopyService`、`NixlCopyService`。Gloo 经过 CPU 暂存;其余各有 GPU 通信依赖。NCCL M2N 当前只接受非共置的连续源、目标 rank 区间,不接受重叠/空闲rank、多目标池或GTP计划;内置共置 RL 路径不能直接选它。不要把 README 里的 NCCL “default choice” 当成 CLI 默认值。

**典型配置**。下面是已有兼容训练/推理作业的增量或API调用,需保留原作业的模型、数据与分布式启动配置。

| 场景与前提 | 起点 | 验证重点 |
|---|---|---|
| 现有distributed optimizer训练,计划下次改变TP/PP;模型结构与optimizer保持兼容 | 在**下一次保存前**加入 `--ckpt-format torch_dist --dist-ckpt-optim-fully-reshardable`;恢复时使用目标并行度 | 新存档metadata确为模型空间格式,再验证目标布局加载;仅给旧存档的恢复命令加开关不够 |
| 只用兼容checkpoint权重做评估或重新开始训练状态 | 原加载命令加 `--no-load-optim --no-load-rng --exit-on-missing-checkpoint`;若要重置iteration/scheduler另按工作流选择 `--finetune` | 权重覆盖完整,并检查iteration、scheduler与数据进度;不要称作无缝续训 |
| 同一组NVIDIA GPU rank上已建训练与推理模型,布局受支持且NCCL可用 | `swap_model_weights(train_model, infer_model, refit_method="nccl")` | 先验证目标权重/输出,再分开测首次与缓存命中的耗时;MXFP8目标先调用 `prepare_swap_model_weights` |

组合与推荐值是按语义推的起点,不是实测最优。

工具边界也要区分。`tools/checkpoint/convert.py` 用loader/saver插件协议搬全量层权重,具体模型与格式能力取决于插件,不能当通用训练状态转换器。`weighted_merge.py` 则对同布局的 `torch_dist` 模型checkpoint做加权合并,浮点权重在CPU上用FP32累积,extra state按来源复制;它不负责调和不同分片布局,也不合并optimizer/RNG。合并产物还需在目标工作流单独加载验证。

| 症状 | 先查 | 然后 |
|---|---|---|
| 模型权重可加载,optimizer恢复失败 | 存档metadata的分片格式与目标布局是否兼容 | 若旧格式只支持DP重排,先用受支持布局恢复;下一次保存前再选可重排格式 |
| refit内存峰值超过所填预算 | 后端是否走通用分批执行,以及最大单参数大小 | 将软预算与不可拆单参数分开估算,结合实际后端调整暂存方案 |
| 换并行度恢复后结果不逐步一致 | RNG是否被忽略、训练状态是否完整恢复 | 固定拓扑和输入做复现检查,不要将权重加载成功等同数值逐步复现 |

## 六、常见误区

- **“checkpoint里有所有卡的数据,就能任意换并行度。”** 还需一致的逻辑名称、形状与受支持的分片元数据。`torch_dcp`训练入口当前限制到PyTorch FSDP2且不支持其TP/PP组合;`fsdp_dtensor`是Megatron-FSDP专用路径,另有expert、融合权重及缺键处理。
- **“只要finetune就一定不载optimizer。”** 一般加载会跳过,但当前GPT→hybrid兼容路径有继续加载optimizer的例外。明确只取权重时使用 `--no-load-optim`;该迁移的层映射细节另属模型迁移问题。
- **“refit是把整份训练状态广播给所有推理卡。”** 计划按目标切片分发模型参数与持久buffer;optimizer与训练RNG不是这条API的传输内容。元数据all-gather也不等于权重all-gather。
- **“一次成功搬完,之后可以随意增删rank。”** 缓存面向既有模型布局与通信组;当前模块没有负责运行中改变进程组成员的完整编排。
