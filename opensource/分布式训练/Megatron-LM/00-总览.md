# Megatron 框架总览

源码基准:官方仓库 <https://github.com/NVIDIA/Megatron-LM>,分支 `main`,commit `fb6a123a09f524a2abfca81a78b6478358ca77e0`,最近的发布 tag `core_v0.19.2`,核对日期 2026-09-20。全篇的「当前」「默认」都指这组基准;性能数字来自官方 README,标为「官方数字」。原理层面的并行策略、ZeRO、集合通信、显存管理在本站知识库各有一篇,这里不重讲,只写这个项目怎么实现、怎么调。

## 一、Megatron 是什么

这个仓库装的是**两层东西**,官方文档明写它们通常一起用:

**Megatron Core** 是一个**可组合的库**。它提供 transformer 构件、五个维度的并行、流水线调度与分布式优化器、混合精度、GPU 优化 kernel 与显存管理、dataloader 和一批模型架构。它不替你决定训练循环长什么样,只把「一层怎么切、一步怎么排、状态怎么存」这些难做对的事做成可以拼装的零件。

**Megatron-LM** 是一份**参考实现**。它在 Core 之上给了一个抽象层很薄的原生 PyTorch 训练循环、一套参数体系、预置的训练脚本和 checkpoint 编排。官方把它定位成「探索 Megatron Core 的直接入口」。

这个区分决定你该读哪一层:Core 提供可复用的训练能力,参考实现负责把它们编排起来。第三方可以自己写外层循环,同时按需复用参考层的辅助函数。例如 verl 主要接 Core,slime 还复用了 training 中的参数校验、模型构造与 checkpoint 函数。是否采用参考循环,与是否复用这些辅助函数,是两件事。

一句话定位:**Megatron 是把「五维并行 + 流水线调度 + 优化器状态分片 + 分布式 checkpoint」做成可组合零件的训练引擎,自己再配一份参考实现证明这些零件能拼成一个跑到六千卡的训练系统。** 官方数字:2B 到 462B 的模型,6144 张 H100 上 MFU 从 41% 升到 47% 至 48%。

顶层入口:

- `python pretrain_gpt.py --<一堆参数>`:参考实现的训练入口,同目录还有 `pretrain_hybrid.py`、`pretrain_mamba.py`、`pretrain_vlm.py`、`train_rl.py`,各对应一类模型。
- `uv pip install megatron-core` 后 `import megatron.core`:当零件柜用,自己写训练循环。第三方可以从这条路径接入。
- `--yaml-cfg <文件>`:实验性 YAML 配置入口,使用自己的嵌套结构与校验路径,不能把 CLI 参数逐项原样搬进去。

代码花在哪(KB,`tests/` 的 48 MB 按惯例剔除):`megatron/core/` 共 11.5 MB,其中 transformer 2388、inference 2212、models 1184、distributed 1152、ssm 684、optimizer 508、resharding 380、pipeline_parallel 368、tensor_parallel 348、datasets 328、dist_checkpointing 284;`megatron/training/` 共 1.5 MB,训练循环与参数体系各占 284 和 228。

两个数字和直觉不一样,值得先知道:`transformer/` 的 2388 里有 648 是 MoE、604 是实验性注意力变体;`distributed/` 的 1152 里有 936 是 Megatron-FSDP —— 也就是说,今天这个仓库里体量最大的几块,都不是当年那篇论文讲的东西。

## 二、六个招牌:先建立全局图景

![上层参考循环组织启动、训练步与条件存档,下层 Core 提供对应能力;反向中的梯度通信可以重叠,refit 是可选扩展](/opensource/Megatron-LM/00a-two-layers-one-iteration.svg)

- **五维并行与 rank 摆位**:TP、PP、CP、DP、EP 可以组合。进程组把逻辑并行维度落到实际 rank 上,摆位影响哪些通信走机内链路、哪些走机间链路。
- **流水线调度**:把一个 global batch 拆成 microbatch,在多个流水段之间穿插前向与反向;交错式调度让一个 rank 持有多个 model chunk,进一步调整执行次序。
- **数据并行与状态分片**:经典 DDP 管理梯度同步,可配合分布式优化器切分优化器状态;更新后同步模型参数。Megatron-FSDP 则提供另一条全分片路线,两者同仓维护。
- **MoE 完整支持**:router 与负载均衡、三种 token dispatcher、专家并行与通信优化相互配合,解决 token 分给谁、负载是否均衡、数据怎么搬运的问题。
- **低精度、融合与 CUDA Graph**:接入 Transformer Engine 等算子实现,通过 FP8/FP4、融合算子及 CUDA Graph 降低计算、内存访问和下发开销;各项能力按模型与配置选用。
- **权重保存与搬运**:分布式 checkpoint 用分片元数据支持兼容布局间的恢复;resharding/refit 可把训练侧权重直接搬到推理布局,主要用于 RL 训推循环,不必先落盘。

## 四、一次 iteration 怎么串起来

参考入口先解析并校验配置、初始化并行环境,再构造模型和优化器、恢复训练状态并准备数据迭代器。Core 提供建组、模型构件与分布式执行能力,参考层负责组织这些步骤。

一次训练步的主线是:**清梯度并读取 microbatch → 调度前向与反向 → 完成梯度同步和处理 → 更新参数与学习率**。开启通信 overlap 时,部分梯度通信已经在反向期间发起,并非全部排在反向之后。分片优化器、重算、offload、低精度与 CUDA Graph 都是这条主线上的可选机制。

循环在相应时机记录日志、运行评估、保存 checkpoint 并判断是否退出。checkpoint 能否换并行布局恢复,取决于格式与模型、状态的支持范围。RL 还可以在训练与推理之间调用 refit 搬运权重;它与落盘恢复共享“适配并行布局”的问题,但不是同一条执行链路。

## 六、怎么调它、怎么看它

**在哪调**

| 入口 | 长什么样 | 什么时候用 |
|---|---|---|
| 命令行参数 | `python pretrain_gpt.py --tensor-model-parallel-size 4 --pipeline-model-parallel-size 4 …`;一部分参数手写,一部分由配置类字段生成 | 配置参考训练入口;字段存在排除、映射与默认值处理 |
| YAML 配置 | `--yaml-cfg <文件>`,使用嵌套结构和独立校验,属于实验性入口 | 使用匹配的 YAML 示例;不是 CLI 的同名替代,该路径不合并普通 CLI 参数 |
| 配置对象 | `TransformerConfig` 等对象以及参考入口的配置容器 | 直接接 Core 或装配模型;与 CLI 有转换关系,并非字段逐项相同 |
| 环境变量 | 分布式启动的 `RANK`、`WORLD_SIZE`、`LOCAL_RANK`、`MASTER_PORT`;通信与算子层的 `CUDA_DEVICE_MAX_CONNECTIONS`、`PYTORCH_CUDA_ALLOC_CONF`、若干 `NCCL_` 与 `NVTE_` 开关;日志级别 `MEGATRON_LOGGING_LEVEL` | 通信行为、显存分配器、确定性算法开关;这些不由参数体系管,改了要重启 |

**看什么**

| 看什么 | 在哪 | 说明 |
|---|---|---|
| 每步耗时与吞吐 | 训练日志行的 `elapsed time per iteration (ms)`、`throughput per GPU (TFLOP/s/GPU)` | 固定模型、序列长度与 global batch 后比较;吞吐项需开启相应日志 |
| 训练是否正常 | 同一行的 `learning rate`、`global batch size`、各 loss 项、`loss scale`、`grad norm`、`num zeros`、`params norm` | 低精度训练看 `loss scale` 有没有反复回退 |
| 跳步与数值异常 | 同一行的 `number of skipped iterations`、`number of nan iterations` | 非零就要查 |
| 能耗 | 同一行的 `energy per GPU (J/iter/GPU)`、`power per GPU (W/GPU)` | 开了能耗监控才有 |
| MoE 专家分布 | 同一行追加的 MoE 指标段 | 用专家数参数时才出现 |
| 显存 | 理论显存报告函数按参数算出权重与优化器占用;运行时峰值由可观测指标给 | 先用理论值排配置,再看实测 |
| 指标外送 | 八个 OpenTelemetry 指标:`megatron.training.step_duration_ms`、`loss`、`throughput_tflops`、`tokens_per_sec`、`grad_norm`、`skipped_iters`、`learning_rate`、`memory_allocated_gb`,可转成 Prometheus 名字 | 要接监控后端时用 |

## 七、阅读顺序

本系列聚焦训练系统。01–14、16–17 构成 16 个主体章节,15 是按需阅读的实验性 attention 扩展专题。主干是 01 到 04:先看清两层怎么分工、进程组怎么建、单层和单条序列怎么切、流水线怎么排。这四章读完就抓住了骨架。05 到 07 是围绕「显存不够、通信太慢」长出来的三条线。08 是装配机制,读懂它才知道换架构要动哪里。09 与 10 是 MoE,今天的重头。11 与 12 是把显存和算力榨干的两套手段。13 只在换并行度或做 RL 训推一体时读。14 到 17 按需查阅。

**怎么读**:每章第四段写的是「和同类常见做法不一样的地方」,对照组全篇固定成两个 —— **PyTorch FSDP**(本站另有一篇解读)代表「模型定义原样保留、在外面包一层分片」那条路线,**DeepSpeed** 代表「把分片和显存优化做成引擎加一份配置」那条路线。不是每章都把两个都比一遍,比得上哪个就比哪个;某一维度在对方那里根本不存在,那本身就是一处差异。重点始终在 Megatron 自己这边,对照只用来把它的选择衬出来。

| 维度 | PyTorch FSDP / DeepSpeed | Megatron |
|---|---|---|
| 接入方式 | FSDP 提供模型分片接口;DeepSpeed 提供训练引擎,调用方组织循环 | Core 可直接组合使用;Megatron-LM 另提供完整参考循环 |
| 模型与并行 | FSDP 重点是数据并行分片;DeepSpeed 还包含其他并行能力 | TP/PP/CP/EP 等与模型构件、调度相互配合 |
| 状态分片 | 分别由 FSDP 策略或 ZeRO 等机制处理 | 经典 DDP 可配分布式优化器,另有 Megatron-FSDP |
| checkpoint | 能否改变布局取决于所用格式和恢复路径 | 分片元数据支持兼容布局恢复,具体范围见 13 章 |

需要注意的是,这条分界线在这个仓库里已经不那么干净了:一份叫 Megatron-FSDP 的实现就住在 `distributed/fsdp/`,两条路线同仓并存,07 章专讲。这里要分清两个同名的东西 —— 仓库自带的那份和 PyTorch 自带的那份不是一回事。

原理层面的并行策略推导、ZeRO 分级、集合通信和显存管理,本站知识库 `04-Infra` 各有一篇,这里不重复。
