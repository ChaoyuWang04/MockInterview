# 分布式优化器与优化器家族

这一页回答一个问题:数据并行的各卡已经算同一份模型,为什么还要各存一整套优化器状态,能否分工更新后只交换新权重。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**模型能装下,不代表训练状态也能装下。** 常规 BF16 Adam 训练除了模型权重,还维护 FP32 主参数以及一阶、二阶矩状态。数据并行副本增加时,这些状态若仍各存一份,每卡的显存压力不会随副本数下降。

但更新完以后,每个副本又必须看到一致的新权重。真正要解决的是:**谁负责更新哪一段,谁保留这段的历史状态,何时让其他副本看到更新结果**。

## 二、解法

Megatron 的普通分布式优化器给连续参数缓冲划定所有权。每个 DP rank 负责一段元素范围,范围可以横跨参数边界,也可以只包含一个大矩阵的一部分。优化器只为本地负责的部分维护主参数和状态,不要求每个 rank 都执行完整更新。

前面的 DDP 路径先用 reduce-scatter 把归约后的梯度交给各自的所有者;优化器取出本地有效片段,进行梯度处理和更新。以常规 BF16 Adam 为例,更新的是本地主参数的 FP32 副本,然后转换回 BF16 模型参数片。最后 all-gather 的是**更新后的模型参数**,主参数和 Adam 的历史状态继续留在原所有者处。

![两个 DP rank 分别持有一半 FP32 主参数和 Adam 状态,reduce-scatter 交付本地归约梯度,本地更新并转换后只 all-gather BF16 模型参数,恢复两份一致模型。](/opensource/Megatron-LM/06a-owned-state-and-update.svg)

图中为了突出所有权,把通信画成两个阶段;实际作业可以按桶重叠。未启用参数聚集重叠时,优化器更新后发起同步;启用后,聚集可以延迟到下一轮前向附近,但相关层使用参数前必须等它就绪。桶怎么就绪、如何重叠由 DDP 负责,本章只看更新前后的交接。

**换优化器家族,所有权粒度也可能变化。** Adam 的逐元素更新适合连续范围切分;Muon 的矩阵更新需要保留矩阵结构,对应的按层分布式路径把完整参数分给 DP rank,这里的「完整」仍是已有 TP 切分之后的参数。当前预计算布局让这类参数不跨 DP 分片边界,再接入 DDP 通信。被标记为 embedding/output、不是二维矩阵,或被显式排除的参数另交给默认 Adam,也可选择 Lion;判断依靠参数属性与形状,并非仅靠层名。组合由一个串联优化器统一推进。

## 三、代价

**省下的是状态副本,不是整卡显存按 DP 度数等分。** 普通分布式优化器仍保留前向所需的模型参数副本,梯度缓冲和通信临时空间也占显存。标准 BF16 权重、FP32 主梯度与 Adam 状态的文档模型给出每参数从 18 字节降到 6+12/d 字节,d 是状态分片组大小;这不是含激活、padding 和临时分配的峰值公式。

**更新成为「归约—本地更新—参数同步」的链条。** 状态少了,却增加了参数同步环节;卡数更多不一定让 step 更短。按完整参数分工还要平衡矩阵大小、更新计算量和 padding,不能沿用普通元素分片的均匀假设。

**低精度模型不等于低精度状态。** 普通路径保留 FP32 主参数;另有精度感知 Adam 可以改变主参数或状态的存储精度,但这需要后端支持和单独的数值验证。CPU 卸载、Megatron-FSDP 与 optimizer CUDA graph 是另外的机制,分别在显存、全分片与执行优化章节展开。

## 四、和同类常见做法不一样的地方

PyTorch FSDP 的全分片路线会在计算边界安排参数的聚集与重分片。本章普通分布式优化器的重点则是**更新职责分工**:前向仍使用本地模型副本,更新状态按 DP 所有权保存,更新结果再同步给副本。选择时先区分压力来自模型本身、优化器状态还是激活,不能只看到「分片」就认为驻留行为相同。

Megatron 还让优化器参与定义参数缓冲布局:逐元素更新和矩阵更新可以给出不同的所有权划分,DDP 再消费这些布局。因此切换家族不只是换一个更新公式,也可能改变分工、padding 和通信衔接。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

下表以训练 CLI 为入口;Core 用户使用 `OptimizerConfig` 及相应 DDP 配置。learning rate、weight decay 与调度仍需沿用模型已经验证的配方,不要把显存优化和更换训练算法混在一次对照里。

| 参数与入口 | 默认 | 调整影响 | 怎么看 |
|---|---|---|---|
| CLI `--optimizer` | `adam` | 可选 Adam、SGD、Muon、Lion、SOAP、Adaptive Muon;后几类依赖 emerging-optimizers。不同家族改变更新规则,不保证可互换 | 配置日志、loss 与更新耗时 |
| CLI `--use-distributed-optimizer` | 关 | Adam 进入连续元素范围分片;新兴优化器入口转换到 layer-wise 路径。原生 SGD 不能直接套用普通 DistributedOptimizer 的当前构造条件 | 每卡状态显存、参数同步时间 |
| CLI `--overlap-param-gather` | 关 | 让参数聚集与前向重叠;普通 Adam 路径要求分布式优化器及梯度通信重叠等前提 | profiler 与 step time,详见梯度桶章 |
| CLI `--clip-grad` | 1.0 | 按全局 L2 norm 裁剪;改阈值会改变训练,不是纯性能优化 | `grad norm`、loss |
| CLI `--loss-scale` | 无 | 显式值走静态 scaling;未指定时 FP16 使用动态 scaler,BF16 普通路径不自动启用 scaler | `loss scale`、跳步数量 |
| CLI `--use-precision-aware-optimizer` | 关 | Adam 专用的状态精度路径;普通 DDP 场景要求分布式优化器及兼容 TE FusedAdam | 初始化校验、显存与数值对照 |
| CLI `--main-params-dtype` / `--exp-avg-dtype` / `--exp-avg-sq-dtype` | 均为 `fp32` | 精度感知路径下可降低主参数或矩状态存储精度;选择受 CLI 与后端约束 | 显存峰值、loss、跳步数量 |
| CLI `--muon-momentum` | CLI 0.9;Core 0.95 | Muon 动量;两种入口默认不同,对齐实验时应显式给值 | 保存的配置与loss |
| CLI `--muon-tp-mode` | `duplicated` | `duplicated`/`distributed` 对完整矩阵做正交化;`blockwise` 分片各算,更新规则随 TP 改变;`auto` 自动选择部分路径 | 更新耗时、拓扑变化前后的数值对照 |
| CLI `--muon-scalar-optimizer` | `adam` | Muon 家族的非矩阵/排除参数可改交 `lion` | 参数分组配置、loss |

**典型配置**。以下是完整训练命令上的增量,假设使用支持 BF16 的 NVIDIA GPU、常规 DDP,每卡的模型和激活已能容纳;并非完整训练命令或实测推荐值。

| 场景 | 配置增量 | 拿什么换什么 |
|---|---|---|
| 4 个 DP 副本,Adam 状态占用吃紧 | `--bf16 --optimizer adam --use-distributed-optimizer` | 用更新后参数同步换更少的本地状态;保持原 learning rate 与 global batch 做对照 |
| 上一组能稳定训练,参数聚集开始拖慢前向 | 上一组加 `--overlap-grad-reduce --overlap-param-gather` | 增加调度和缓冲配合,尝试隐藏同步耗时;保持精度与算法不变 |
| 已有独立验证的 Muon 配方,需要分担状态 | `--bf16 --optimizer muon --use-distributed-optimizer --muon-momentum 0.9 --muon-tp-mode duplicated` | 使用矩阵级所有权和额外矩阵更新计算;须安装兼容 emerging-optimizers,当前不走 FP16 或 FSDP 组合 |

组合与推荐值是按语义推的起点,不是实测最优。

**看哪里。** 初始化会打印优化器配置。训练日志有 `loss scale`、`grad norm` 与 `number of skipped iterations`;计时器可区分 `optimizer-copy-to-main-grad`、`optimizer-inner-step`、`optimizer-copy-main-to-model-params`、`params-all-gather`。同步计时在重叠模式下不代表全部暴露时间,应结合 profiler 和固定工作量下的 step time。至少跑过实际更新后再比较状态显存,不要只截初始化时的占用。

| 症状 | 先查 | 然后 |
|---|---|---|
| 开分布式优化器后显存没按 DP 度数下降 | 主占用是否是激活、模型副本或缓冲;状态是否已初始化 | 分别看状态与峰值,不把 1/d 当整卡公式 |
| SGD 加分布式开关启动失败 | 构造断言是否提到支持的优化器与状态初始化 | 当前普通路径保留 SGD 非分布式配置,或使用已验证的 Adam 分片方案 |
| FP16 连续跳过更新 | loss scale、梯度 Inf/NaN与训练数值 | 排查溢出和配方;动态 scaler 会调整尺度,不能把跳步当成功更新 |
| Muon 换 TP 后结果变化明显 | 是否用了 `blockwise`,两入口的 momentum 是否一致 | 先固定模式与显式超参数,再做数值对照 |
| 每步 optimizer 时间降了,step time 没降 | 参数 all-gather 是否成为新的等待 | 查看同步与前向时间线,再决定是否启用重叠 |

## 六、常见误区

**「all-gather 完了,每卡又拿回了所有 Adam 状态,所以没省显存。」** 容易把用于更新的状态和用于下一次前向的参数混为一谈。普通路径只同步新模型参数,历史状态仍由原 rank 保管。

**「换成 Muon,照抄旧类注释就能判断通信。」** 按层优化器的类说明仍描述早期全梯度 all-reduce 路径,当前预计算布局还支持对齐分片并接入 DDP 的 reduce-scatter。判断作业要看实际启用的布局和分支,不能只读类名或旧说明。

**「BF16 作业的所有训练状态也是 BF16。」** 模型精度只说明其中一份权重的表示。普通混合精度更新依赖 FP32 主参数;降低状态精度是另外的选择,应把数值验证与显存收益一起记录。
