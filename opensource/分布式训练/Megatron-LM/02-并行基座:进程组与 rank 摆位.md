# 并行基座:进程组与 rank 摆位

这一页回答一个问题:五个并行维度叠在一起之后,哪几张卡编成一组、这一组是不是落在同一台机器里,到底是谁定的。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

假设连续 rank 0–7、8–15 分别位于两台 8 卡机,张量并行 2、流水线并行 4、数据并行 2。这一套并行度有两种合法的摆法,在满足模型与训练配置约束时都能运行,而它们把每一步都要走的那几类通信摆在完全不同的地方。

![连续 rank 同机的 16 卡示例中,更换轴序把跨机通信从流水线转移到数据并行](/opensource/Megatron-LM/02a-two-legal-rank-layouts.svg)

在图示部署下,默认摆法把同一层被切开的两张卡放在同机;数据并行的梯度通信也在机内;跨机的是流水线段之间的点对点收发。对调之后,整条流水线缩进机内,梯度归约反过来跨机。

差别不在配置项的多少,在于哪一类通信吃机内带宽、哪一类吃机间带宽。张量并行的通信量和每层激活是同一个量级,而且每一层都要走;流水线只在段边界传一次激活。把前者摆到较慢的机间链路上,可能增加通信等待;合法的配置也可能吞吐不佳。

而且摆位不是你一张卡一张卡指定的。你给的是每个维度的大小,谁挨着谁是从这几个数推出来的。

## 二、解法

不给五套建组代码,只给一个坐标系。

**一条顺序串把全局编号拆成五个坐标。** 五个维度名排成一串,靠左的步长小、靠右的步长大:最左那一维的相邻成员就是相邻的全局编号,最右那一维的相邻成员隔着「其余所有维度的乘积」那么远。这条串决定逻辑 rank 的分组,再由 rank 到机器的映射决定通信是否跨机。默认那条串把张量并行放在最左、流水线并行放在最右,中间依次是上下文并行、专家并行、数据并行。

**所有维度的组由同一个函数切出来。** 想要哪几维的组,就把这几维在串上的位置标真、其余标假:标真的那些维当组内序号,标假的那些维当组号,一次调用返回全局上的所有组。张量并行组、数据并行组、流水线组、上下文并行组、专家并行组,以及各种把两三维合起来的组,全都是同一个函数换一个掩码的结果。

![rank 6 按五维坐标分解,将不同维度标为组内变化轴,分别得到 TP、DP 和 PP 的成员列表](/opensource/Megatron-LM/02b-one-mask-per-dimension.svg)

**参考入口集中建组,组件再查询或接收组。** 启动时各 rank 按相同顺序创建全局各组,保存自己参与的组。除了各并行维度,还会建立合并维度的组、默认连接流水线首尾的 embedding 组,以及按配置启用的子组。后续组件通过查询接口或显式传入的进程组集合取得通信范围,不必各自重算 rank。

**稠密层和专家层各有一套发生器。** 一个发生器里不允许同时出现大于 1 的专家并行和上下文并行 —— 稠密侧保留上下文并行轴,专家侧保留专家并行轴,两边的数据并行度分别计算。启动时有一条断言把两套算出来的流水线组逐个比一遍,不相等就当场停:稠密计算与专家计算必须使用一致的流水线成员。

## 三、代价

**全局状态路径是一套进程级坐标系。** 这条路径的组存在模块级全局变量里,建之前先断言「还没建过」,要换一套就得先整套销毁。同一个进程里换一组并行度再跑,标准做法是重启进程。

**建组本身是启动时间的一部分。** 每张卡都要走一遍全局的每一个组,组数跟着维度组合涨;卡多的时候这一段不短,而且它排在装配模型之前,串行等着。

**顺序串只有一维,表达不了真实拓扑。** 它能说的只有「谁的步长小」,说不了哪 8 张卡共享一条高速互联、哪几台机在同一个机架下。为了通信效率,它要求调用方安排相邻编号尽量物理相邻 —— 源码把这一条写成了对调用方的要求,而不是框架能保证的事。参考训练入口用于切换轴序的旋钮是:把数据并行和流水线并行在串上对调,其余位置的先后写死在代码里。

**同一个维度的组不止一份。** 数据并行这一维就有 6 个变体:带不带上下文并行、带不带权重分片那一维、是不是分片优化器切出来的子域。取错了归约的范围就错,而且错法是静默的。

**取组有三套写法,同仓并存。** 最老的一套是直接读全局变量;新写的组件收一个进程组集合对象,构造时允许只填一部分,没填的字段读出来是空而不是抛异常;再有一套是按 N 维网格描述的接口,可描述一个 rank 区间里的多维划分,它按需建组,重复建同一个组直接报错。三套之间没有强制收敛,新代码该用哪套要看它接的是哪一边。

## 四、和同类常见做法不一样的地方

进程组的名称相同,不代表rank排列相同。这里最值得和DeepSpeed流水线拓扑对照的是维度如何落到rank,以及调用方怎样把逻辑网格映射到机器;PyTorch FSDP则提供模型分片这一侧的接口。

| 对比维度 | 对照路线 | Megatron |
|---|---|---|
| 并行关系的组织 | DeepSpeed流水线拓扑按命名轴描述进程坐标 | 参考入口先建立TP、PP、DP、CP、EP等需要的组,再构造模型 |
| 轴序的含义 | DeepSpeed流水线拓扑最右轴变化最快 | rank生成顺序中最左维度步长最小,同一串轴名不能直接照搬 |
| 传给执行组件的内容 | FSDP使用配置好的分片通信范围;其他并行关系由调用方组织 | Core组件可使用全局并行状态,也可显式接收所需进程组 |

两边的逻辑拓扑都要落到实际机器上。迁移配方时检查组成员与机内、机间边界,比只核对各维度的大小更有用。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**在哪调。** 下表使用参考入口的 CLI。`--yaml-cfg` 是实验性独立路径,采用嵌套结构与单独校验,不能当成 CLI 同名键的文件版。直接接 Core 时,建组接口接收并行度与 `order`;参考入口只在两种轴序之间选择。

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `--tensor-model-parallel-size` | 1 | 一层权重切给几张卡。调大省每卡显存,但每层都多几轮组内集合通信;一旦超过单机卡数,这一维必然跨机 | 启动日志 `> initialized tensor model parallel with size`;每 GPU 吞吐 |
| `--pipeline-model-parallel-size` | 1 | 模型按深度切成几段。调大省显存,气泡比例跟着 microbatch 数走 | 启动日志 `> initialized pipeline model parallel with size` |
| `--context-parallel-size` | 1 | 一条序列切给几张卡。长序列省激活显存,注意力计算增加跨 rank 通信 | 每步耗时与显存峰值 |
| `--expert-model-parallel-size` | 1 | 专家分给几张卡。只对 MoE 有意义,它和上下文并行分属两套发生器,不能在同一套里同时大于 1 | 专家侧那批组建完才会往下走 |
| `--expert-tensor-parallel-size` | 跟随张量并行度 | 专家层自己的张量并行度。它与 EP 等一起决定专家侧 DP,可能与稠密侧不同,流水线大于 1 且两侧数据并行度不等时,需要流水线在最后的轴序 | 启动时那条流水线组比对断言 |
| `--use-tp-pp-dp-mapping` | 关 | 把顺序串从 `tp-cp-ep-dp-pp` 换成 `tp-cp-ep-pp-dp`:流水线组变紧凑、数据并行组变松散 | 各组的成员编号;坐标串接口 `get_all_ranks` |
| `--distributed-timeout-minutes` | 10 | 所有进程组的集合操作超时。建组阶段对不齐就在这里报 | 调大只是让它晚一点失败,不解决对不齐 |

**配置起点**:以下是稠密模型已有配方上的并行增量,不是完整训练命令。假设每机 8 张高速互联 GPU、连续 rank 同机、上下文并行与额外权重分片轴为 1;模型仍须能装入给定切分。

| 场景 | 增量配置 | 代价与前提 |
|---|---|---|
| 单机 8 卡,一层需要跨卡切分 | `--tensor-model-parallel-size 8 --pipeline-model-parallel-size 1` | TP 留在机内,DP 为 1;扩大 global batch 可增大 microbatch size 或增加累积的 microbatch 数 |
| 4 台 8 卡机,模型需要分成 2 段 | `--tensor-model-parallel-size 8 --pipeline-model-parallel-size 2`,不加摆位开关 | DP 为 2,TP 同机,PP 跨机;需观察段间通信与 bubble |
| 两台 8 卡机,希望流水线在机内 | `--tensor-model-parallel-size 2 --pipeline-model-parallel-size 4 --use-tp-pp-dp-mapping` | DP 为 2,每条流水线连同 TP 占一台机器,DP 通信跨机;是否更快须测量 |

组合与推荐值是按语义推的起点,不是实测最优。

**看哪里。** 启动日志报告张量并行、权重分片轴与流水线的大小,不能单凭这些数字确认物理摆位。先核对各组成员与 rank 所在主机,再比较每步耗时、通信等待和每 GPU 吞吐。`get_all_ranks` 可查看本 rank 在各维度的坐标;通信挂住时,配合 `--flight-recorder-dump-path` 等诊断配置查看通信记录。

**症状表**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动就报总卡数除不开 | 报的是稠密那条还是专家那条 | 稠密的除数是张量 × 流水线 × 上下文 × 权重分片;专家的是专家张量 × 专家并行 × 流水线 × 专家权重分片 |
| 启动报两套发生器的流水线组对不上 | 专家侧的数据并行度是不是和稠密侧不相等 | 先关闭 `--use-tp-pp-dp-mapping` 恢复 PP-last;若仍失败,核对两侧完整划分。只对齐 expert TP 不保证 DP 相等,EP 等也参与计算 |
| 建组阶段卡住,最后集体超时 | 各 rank 拿到的并行度参数是不是完全一致 | 对齐参数;把 `--distributed-timeout-minutes` 调长只会让它晚一点失败 |
| 跑得动,但每 GPU 吞吐低于参考配置 | TP 成员是否跨机,机间通信是否占主要等待 | 在显存允许时比较更小 TP;若改轴序,同时核对 PP 与 DP 的通信去向 |
| 梯度范数或 loss 和预期对不上 | 代码取的是哪一个数据并行组变体 | 按用途取:梯度归约取不含权重分片轴的那个,切批量与算 microbatch 数取含的那个 |
| 超时时间和预期不符 | 参考实现传进去的默认是 10 分钟,`initialize_model_parallel` 这个函数自己的默认是 30 分钟 | 以命令行参数为准;函数默认只在绕过参考实现直接调库时生效 |

## 六、常见误区

**「数据并行组就是数据并行组。」** 会这么以为,是因为它在参数里只是一个数、在日志里只是一个维度大小 —— 一个数对应一个组是最自然的推断。实际上取它的那个接口有三个开关、6 种返回:带不带上下文并行、带不带权重分片那一维、是不是分片优化器切出来的子域。取错不报错,只会让归约的范围悄悄错掉 —— 出问题时几乎没人第一时间怀疑它。

**「顺序串随便改就能贴着我的机器摆。」** 会这么以为,是因为它看起来就是个可以自由写的字符串,库里那个建组函数确实收一个串。但参考实现只在两种串之间二选一,由一个布尔开关控制。直接调用 Core 可以传入其他顺序,但仍须满足整除与流水线一致性约束,并核对真实拓扑。

**「张量并行度只受层宽和显存限制。」** 会这么以为,是因为教程都从「一层放不下就切开」讲起。它同时决定这一维会不会出机器:张量并行度一旦超过单机卡数,这一维必然跨机,而它通常需要频繁的层内通信。单机卡数是重要的性能参考,不是合法性的上限;是否值得跨机要看显存压力和实际链路。

**「建进程组就是切一切,很快。」** 会这么以为,是因为它在日志里只占三行。实际上每张卡都要参与全局每一个组的创建,组数跟着维度组合涨,各类组在全局都有各自的成员列表,部分组还受配置控制。启动慢的时候它是候选项之一,不是可以直接排除的那一项。

**「专家并行和别的维度一样挂在同一个坐标系上。」** 会这么以为,是因为文档把五个维度并排列在一张表里。实际上专家层的摆位由另一套发生器算,和稠密侧强制对齐的只有流水线这一维,还是靠一条断言事后比出来的。改专家侧的张量并行度会连带改专家侧的数据并行度,从而影响能否使用非 PP-last 摆位。

**「拿到进程组集合对象就等于拿到了所有组。」** 会这么以为,是因为它是个数据类,看上去字段都在。它允许只填一部分,没填的字段读出来是空而不是抛异常 —— 于是错误推迟到第一次真正用那个组的时候才爆,而那时候的栈已经离建组很远了。
