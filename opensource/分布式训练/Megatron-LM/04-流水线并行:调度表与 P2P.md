# 流水线并行:调度表与 P2P

这一页回答一个问题:模型按层切到不同 GPU 后,每张卡怎样安排 microbatch 的前反向,减少接力中的空等。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

按层切模型解决了单卡放不下的问题,却引入了前后依赖:下一段要等上一段的激活,上一段做反向又要等下一段的梯度。一次 iteration 的开头要把流水线填起来,结尾要把它排空,这期间有 GPU 暂时没有计算可做,形成 bubble。microbatch 太少时,填充与排空占比尤其明显。

层数平分也不等于耗时平分。embedding、输出端和 MTP 的工作不同,某段算得慢,相邻段就可能等它。**调度顺序和层的落位要一起看**:前者决定什么时候有活可做,后者决定每份活有多重。

## 二、解法

Megatron 让不同 microbatch 的前反向交替进入流水线。以非交错 1F1B 为例:先做 warmup,只推前向;梯度开始回来后进入 steady,每轮做一个前向和一个较早 microbatch 的反向;最后用 cooldown 补完剩余反向。这样不用等整批前向结束才开始释放反向所需的激活。

![每个 PP rank 独立列出 warmup、steady 和 cooldown 的动作顺序,非交错与交错各有不同的 warmup 次数,横向位置不表示跨 rank 的同时执行。](/opensource/Megatron-LM/04a-one-step-three-phases.svg)

交错调度把一张卡负责的层再分成多个 **model chunk**,各 chunk 在完整模型中并不相邻。调度表记录接下来处理哪个 microbatch、哪个 chunk,把流水线接力拆得更细,提供减少 bubble 的机会。图上只编码动作次序:每次动作处理的层数和通信等待都可能不同,不能从格子宽度推算加速比。

层分配默认按规则切分;首尾可以单独指定层数,更不均匀的模型还可以手写布局。下面左图说明 chunk 在模型中的位置,右图是官方文档给出的布局实例。

![16层模型在PP4下可连续分段或每卡分成两个model chunk;另一侧展示61个decoder层加1个MTP层在PP16和VPP2下的官方自定义布局。](/opensource/Megatron-LM/04b-layer-placement.svg)

调度器还负责把计算与 P2P 收发接起来:前向发激活,反向发梯度,steady 中可以把发激活和收梯度放进同一次通信调用。固定形状的常规路径按配置准备接收张量;变长序列或独立 MTP 路径则先交换形状。交错调度支持把部分 P2P 通信与计算重叠,但收到数据之后才能开始对应计算的依赖仍然存在。

## 三、代价

**更细的接力增加通信边界。** model chunk 多了,每次计算变短,收发次数也增加;能否省下时间,取决于计算量、网络和重叠效果,不是 chunk 数越大越好。

**调度还决定激活驻留。** 非交错调度中,靠前的 rank 在 warmup 留下更多尚未完成反向的 microbatch。交错会改变这些驻留数量,但真实峰值还取决于 chunk 大小、层类型和 activation checkpointing,不能仅凭 warmup 次数断言显存一定上涨。

**自定义布局只校验合法性,不替你测均衡。** 它检查 embedding、loss、decoder 和 MTP 的数量与顺序等约束,官方仍标为实验特性。合法布局能运行,不代表每个 rank 一样快;改模型后还要重新检查。

## 四、和同类常见做法不一样的地方

DeepSpeed 把流水线调度表示成一串指令,由引擎映射到前向、反向和收发方法。Megatron 则在专门的调度函数中组织 warmup、steady、cooldown 循环,直接穿插通信、梯度同步与计算钩子。读 Megatron 时,沿调度循环追一次 microbatch 比只读单层实现更容易看清执行顺序。这是代码组织方式的差异,不意味着指令式调度不能合并通信。

PyTorch FSDP 适合用来理解训练状态如何分片;本章关注的是不同层之间的前反向接力。两者解决的问题不同,不能用状态分片的效果直接预测流水线的 bubble。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

以下使用参考训练脚本的命令行入口。直接调用 Megatron Core 时要构造配置对象;其默认值不一定等同参考脚本处理后的值。YAML 走自己的加载与校验路径,不能把下表的命令行名称原样当成 YAML 键。

| 参数 / 在哪调 | 默认 | 调整的作用与代价 | 怎么看 |
|---|---|---|---|
| CLI `--pipeline-model-parallel-size` | 1 | 增加 PP rank 数可分摊层,也增加接力深度 | iteration 耗时与每 GPU 吞吐 |
| CLI `--num-virtual-stages-per-pipeline-rank` | 无 | 指定每 rank 的 model chunk 数,大于1时启用交错;更细计算伴随更多收发 | profiler 中计算与P2P间隙 |
| CLI `--num-layers-per-virtual-pipeline-stage` | 无 | 按每 chunk 层数推导 chunk 数;不能与上一项或自定义布局同时给 | 启动整除校验 |
| CLI `--pipeline-model-parallel-layout` | 无 | 手写每个 chunk 的层布局,承担手工配平工作 | 启动布局表、各rank计算耗时 |
| CLI `--decoder-first-pipeline-num-layers` / `--decoder-last-pipeline-num-layers` | 无 | 单独调整首尾 decoder 层数,给额外计算腾位置 | 各rank计算耗时 |
| CLI `--microbatch-group-size-per-virtual-pipeline-stage` | PP大小 | 每个chunk连续处理的microbatch数;须在PP到总microbatch数之间,末组非空时也须至少有PP个 | warmup长度与显存峰值 |
| CLI `--no-overlap-p2p-communication` | 交错时不写即开启重叠;非交错时强制关闭 | 写上关闭P2P重叠;Core配置对象的重叠默认则是关闭 | P2P与计算是否重叠、iteration耗时 |
| CLI `--overlap-p2p-communication-warmup-flush` | 关 | 将重叠扩展到warmup与cooldown;要求P2P重叠开启且不用批量收发 | profiler中的首尾区间 |
| CLI `--timing-log-level` / `--timing-log-option` | `0` / `minmax` | 级别1增加整体前反向等计时,2增加计算与收发计时;`all`按rank报告 | 定位计算或通信较重的rank |

**配置起点**。下表是已有可运行训练命令的增量,还需原有模型、数据、精度、TP/DP和启动配置。三组均假设16层dense decoder、PP4、每次iteration有8个microbatch;卡型不限,但需先确认显存足够,没有做GPU性能实测。

| 场景 | 命令行增量 | 取舍 |
|---|---|---|
| 先建立非交错基线 | `--pipeline-model-parallel-size 4 --timing-log-level 2 --timing-log-option all` | 先定位层间不均与通信等待,暂不增加chunk |
| 在同一模型上尝试交错 | `--pipeline-model-parallel-size 4 --num-virtual-stages-per-pipeline-rank 2 --microbatch-group-size-per-virtual-pipeline-stage 4` | 每chunk有2层;与基线比较吞吐和显存,默认group已是允许下限 |
| profiler已确认首尾计算较重 | `--pipeline-model-parallel-size 4 --decoder-first-pipeline-num-layers 2 --decoder-last-pipeline-num-layers 2` | 非交错时decoder层数变成2/6/6/2;减轻首尾,但可能让中间段变成瓶颈 |

组合与推荐值是按语义推的起点,不是实测最优。

**看哪里。** 级别2的 `forward-compute`、`backward-compute` 和 `forward-send-backward-recv` 等计时可定位计算、通信或等待较重的 rank。收发计时可能含传输、等待和同步,还受异步重叠影响,**其总和不等于 bubble**。需要确认空闲发生在哪时,用 profiler 看计算与通信时间线;交错调度提供 `warmup`、`steady`、`cooldown` 和 `misc` 的 NVTX 区间。

| 症状 | 先查 | 然后 |
|---|---|---|
| group size 启动校验失败 | 是否小于PP、大于microbatch总数,或最后余组小于PP | 回到默认PP;再在合法区间内尝试 |
| 开交错后显存不足 | 各rank峰值、chunk大小和激活驻留 | 若group曾调大,可降回PP;默认已不能再降,再评估重算或microbatch大小 |
| 层数或布局启动校验失败 | chunk入口是否冲突、层数是否匹配 | 三种chunk入口只选一个,按报错修层分配 |
| 交错且关闭重叠时PP2报错 | 参考脚本要求此组合PP大于2 | 使用受支持的重叠配置,或改回非交错基线 |
| 某个rank收发计时很长 | profiler中它在等待哪段计算或传输 | 先区分层不均与网络瓶颈,再改布局或重叠配置 |

## 六、常见误区

**看到warmup更多,就断定显存更大。** warmup计的是调度动作,交错前后一次动作处理的层并不相同。比较时需要固定模型、microbatch和重算条件,实测各rank峰值,不能拿动作数代替字节数。

**把重叠默认值直接从Core配置复制到训练脚本。** 两条入口的默认行为不同:参考脚本通过反向开关控制重叠,并在非交错时关闭它。排查前先确认最终配置,否则很容易以为自己在比较同一条通信路径。

**以为层数相同就已经配平。** decoder层计数看不出embedding、MTP与输出计算的差别。只有定位到哪段计算更重之后,重新分层才有明确方向。
