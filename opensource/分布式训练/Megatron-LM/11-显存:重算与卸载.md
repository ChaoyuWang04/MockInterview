# 显存:重算与卸载

这一页回答一个问题:前向留下的 activation 和更新权重所需的状态挤满 GPU 时,怎样缩短它们占用显存的时间。说法都在源码基准 `fb6a123a09`(tag `core_v0.19.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

前向算完一层,不代表它的中间结果可以立即释放:反向还要用它们。序列更长、microbatch 更大或流水线中尚未反向的 microbatch 更多,都会加重这段等待期的显存压力。另一部分长期占用来自优化器的更新参数与状态,即使当前没有执行更新,它们也需要存放位置。

这里要改变的是**数据的存活方式**:需要时重新算,或者先放在 CPU,用前再搬回来。梯度与优化器状态由哪个 rank 持有见 05–07 章,本章只看持有之后如何少占 GPU。

## 二、解法

**重算保留入口,不保留全部过程。** Megatron 可以为整段 Transformer 层建立 activation checkpoint,也可以只选择层内子模块。前向保存边界输入与随机数状态,反向到达时恢复随机数状态,重新执行这段前向,再计算梯度。部分轻量构件还能在后续前向用完输出后丢弃输出的存储,在消费它的反向开始前重建。

![同一段前向到反向之间,保留方案让 activation 留在 GPU,重算方案只留下边界输入,卸载方案经 D2H 暂存 CPU 后经 H2D 恢复](/opensource/Megatron-LM/11a-activation-lifetime.svg)

**activation offload 保留数值,改变存放位置。** 细粒度路径按子模块划分保存张量的组,把符合条件的 activation 异步复制到CPU pinned memory(锁页内存),并在安全的流依赖下释放相应 GPU 存储。反向前安排 H2D 预取,计算流仍须等恢复完成。首次 iteration 记录分组和大小,之后按策略保留部分临近使用的组在 GPU,避免无益的往返。

**优化器 offload 是另一条生命周期。** CPU 上的优化器接收从 GPU 传来的梯度,更新它负责的参数副本及状态,再把新参数复制回 GPU。GPU 仍保留模型计算所需的权重;开启传输重叠后,不同参数的传输、CPU 更新与 GPU 更新可以穿插,但每次更新仍要先拿到自己的梯度。

## 三、代价

重算用额外计算换显存,边界输入和反向临时量仍要占空间。整段重算通常比只重算子模块覆盖更多中间结果,也会重复更多计算;最终应比较相同训练配置下的峰值显存与 iteration 时间。

offload 把压力转到 CPU 内存、传输带宽和调度上。异步复制只提供重叠机会,不能保证传输完全隐藏;反向追上 H2D,或者 CPU 更新赶不上 GPU,等待就会进入关键路径。pinned-memory pool会保留可复用缓冲,因此 GPU 显存下降并不等于整机内存占用下降。

选择也受构件与执行模式限制。Megatron 还提供另一条按层的 Transformer Engine CPU offload 路径,它与细粒度路径不是同一套开关,兼容约束不能混用。低精度与 CUDA graph 的计算优化放在 12 章。

## 四、和同类常见做法不一样的地方

DeepSpeed同样提供activation checkpoint与offload,因此本章不能只用“有卸载”说明差异。更有用的比较是保存边界由谁指定,以及需要把哪类状态搬到CPU。

| 对比维度 | DeepSpeed对应机制 | Megatron对应机制 |
|---|---|---|
| activation重算边界 | checkpoint接口包装调用方选择的函数区域 | Transformer整层分段或已接入的子模块边界,与层执行衔接 |
| activation的CPU暂存 | activation checkpoint路径可以将保存内容搬到CPU | 细粒度offload按子模块保存张量分组,接入microbatch预取与释放 |
| optimizer卸载 | ZeRO的optimizer offload与分片阶段配合 | CPU optimizer接收梯度、更新副本后回传,与activation卸载分别配置 |

两边都需要付出重复计算或主机传输成本。调优先确认峰值由哪类数据造成,再决定缩短GPU驻留时间的方式。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**在哪调。** 下表使用参考训练入口的 CLI;直接调用 Core 时对应配置字段由调用者填写。重算与 activation offload 属于 Transformer 配置,优化器 offload 属于 Optimizer 配置,同名“卸载”不代表同一对象。

| 参数 | 默认 | 调整的作用 | 怎么看 |
|---|---|---|---|
| `--recompute-granularity`、`--recompute-modules` | 粒度未启用;模块列表解析为 `core_attn` | `selective` 选择子模块;`full` 建立整层范围的 checkpoint | 峰值显存、反向中的重复前向 |
| `--recompute-method`、`--recompute-num-layers` | 均无 | `full` 下必需;`uniform` 的数量是每段层数,`block` 的数量是本地层列表中选择重算的层数 | 实际重算范围与 iteration 时间;`selective` 不填这组 |
| `--fine-grained-activation-offloading`、`--offload-modules` | 关;列表空 | 启用所选子模块的保存张量卸载;`attn_proj` 必须与 `core_attn` 一起选择 | warmup 后的 offload 汇总和 D2H/H2D 时间线 |
| `--activation-offload-fraction`、`--min-offloaded-tensor-size` | `1.0`、`1048576` 个元素 | 前者选择符合条件的分组比例,后者过滤小张量;不是显存字节配额 | 实际卸载字节数、峰值显存与传输等待 |
| `--optimizer-cpu-offload`、`--optimizer-offload-fraction` | 关;CLI 比例 `1.0`,Core 类默认 `0.0` | 把选中参数的更新及状态放 CPU;按整参数划分,比例不是精确字节上限 | CPU 内存、optimizer step 时间及参数回传 |
| `--overlap-cpu-optimizer-d2h-h2d` | 关 | 使用独立传输流并拆分 CPU 更新,增加重叠机会 | 梯度 D2H、CPU step、参数 H2D 的依赖与间隙 |

**配置起点**:以下为已有可运行的稠密 GPT、BF16、AdamW 配方上的独立增量,使用支持 BF16 的 GPU,不叠加 CUDA graph、FP8 或其他 offload。CPU offload 组还需充足主机内存与匹配的 CPU optimizer 依赖。

| 场景 | 增量设置 | 代价与前提 |
|---|---|---|
| activation 峰值不足以运行目标 microbatch | `--recompute-granularity full --recompute-method uniform --recompute-num-layers 1` | 每层建立重算单元;先测重复计算代价,再调整分段 |
| 希望保留 attention 计算,以传输换显存 | `--transformer-impl transformer_engine --fine-grained-activation-offloading --offload-modules core_attn attn_proj` | TE ≥ 2.10 时还需环境变量 `NVTE_CPU_OFFLOAD_V1=1`;检查主机传输是否成为瓶颈 |
| 优化器状态占用突出 | `--optimizer-cpu-offload --optimizer-offload-fraction 1.0 --use-precision-aware-optimizer --use-distributed-optimizer --overlap-cpu-optimizer-d2h-h2d` | 参考入口要求 precision-aware,普通 DDP 路径还要求 distributed optimizer,其配置要求 Adam,且 offload 构造要求 AdamW 模式;GPU 模型权重仍保留 |

组合与推荐值是按语义推的起点,不是实测最优。

**看哪里。** 固定模型、序列长度、microbatch 和并行布局,比较 warmup 后的显存峰值与 iteration 时间。细粒度 offload 的汇总提供实际卸载字节数,时间线中的 `activation offloading`、`activation reloading` 区间帮助判断传输是否赶上反向;CPU optimizer 则应一起看 CPU 更新耗时与两向复制。

| 症状 | 先查 | 然后 |
|---|---|---|
| 重算开启后仍然 OOM | 峰值发生在 activation、优化器初始化还是更新 | 针对对应对象调整,不要只扩大重算范围 |
| offload 比例减半,显存没有按比例变化 | 分组选择、小张量过滤和保留在 GPU 的组 | 看实际字节汇总,不要按比例直接估算收益 |
| GPU 内存下降但 iteration 变慢 | H2D 等待、CPU 更新和传输带宽 | 缩小卸载范围,与重算方案在相同负载下比较 |
| 开关组合在启动时报错 | 细粒度和按层 offload 是否混开,重算粒度是否配错 | 按当前入口的校验调整;不要把不同路径的约束套在一起 |

## 六、常见误区

**「checkpoint 会把训练状态存到磁盘。」** 同一个词很容易混淆:这里是 activation checkpoint,保存的是反向重建所需的边界信息,并不代替用于故障恢复的训练 checkpoint。

**「offload 默认比例相同,CLI 能跑,Core 也会卸载同样多。」** 参考 CLI 的 optimizer offload 比例是 1.0,Core 配置类却是 0.0。直接使用 Core 时只打开开关而不填比例,可能没有得到预期的 CPU 状态分担。

**「复制标了异步,后面就不用等。」** 异步表示提交后允许其他工作推进,不是消除依赖。CPU optimizer 在读取梯度前会同步对应 D2H 事件,activation 反向也要等 H2D 恢复;只看到复制与计算部分重叠,不能推导它们完全没有成本。
