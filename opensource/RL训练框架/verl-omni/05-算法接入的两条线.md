# 算法接入:策略梯度与直接偏好两条线

对着 verl 解读的《算法怎么插进来》读:那边讲两张表怎么让十几种变体都不碰训练主循环,这一页讲扩散这边为什么光有两张表不够——变体之间连一步有哪几个阶段都不一样,于是分岔切在了两层。说法都在源码基准 `b708218d5b`(tag `v0.2.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

以 verl 常见 PPO/GRPO 变体为参照,主要可替换两处:一批回答怎么折算成Advantage,有了Advantage怎么算损失。在共享的训练阶段内,可以把这两处抽成注册表;这不代表所有文本 RL 算法都有完全相同的流程。

扩散这边不够。这边的变体分成两族,而两族对「一步」的要求根本不同。

Policy Gradient 沿选中的去噪训练片段重算 log-prob,把同一提示词下各样本的 Reward 转成 Advantage;一条轨迹的各选中步共享这个 Advantage。Direct Preference 则以最终样本的隐变量为起点重新加噪,不需要保存整条反向采样轨迹。其中 DPO 比较 chosen/rejected 样本对;NFT 默认按每条样本的 Reward 构造训练权重,不必组成好坏对。DPO 还可以直接读取离线偏好数据,省去在线 Rollout 和 Reward。

如果把这些差异全塞进同一份顺序流,就要同时判断算法族、数据来源及可选的参考约束等条件。流程分工会越来越难读。

真问题是**分岔该切在哪一层**。切太细,每个阶段一个开关,循环烂掉;切太粗,每个算法一份循环,回到复制粘贴。

## 二、解法

切两刀,一粗一细。

**粗的那一刀切在训练循环本身。** 按算法族分出两个训练器子类,各写一份顺序流。走策略梯度的那份从取提示词一路写到同步权重,旧策略重算、Reference Model 与 Teacher 等阶段按配置出现;走直接偏好的那份短得多,而且它内部还按数据来源再分一次——在线那条要生成要打分,离线那条一上来就从数据里读现成的分数。两个子类共一个基类:数据装载、验证、存档续训、把 worker 组拉起来,都在基类上写一遍。入口文件拿配置里的族名查出类来,这是一处集中选择训练主循环的入口;损失、引擎和各个可选阶段仍有自己的分支。

数据来源那个字段不止决定一步的形状,它还**决定集群上起哪几组角色**:离线那条只建 Actor,生成与打分的整套 worker 组一个都不创建。这和参照项目那边「估计器名决定价值网络那组起不起」是同一类事,只是判据换了一个。

**细的那一刀切在两张表上。** 一张收「一批分数怎么变成Advantage」,在控制器上查;一张收「有了输入怎么算损失」,在 worker 里查。装饰器在模块导入时把名字登记进去,循环手里只有一个从配置读来的名字。

但这两张表不是参照项目那样正交的两条轴。Advantage那张今天只有一个函数,挂着两个名字;真正在换的是损失那张,十个条目。原因就在上一节:Direct Preference 不走控制器的 Advantage 阶段,这张表查不到它头上。

那它的算法细节收进哪里?**收进损失类自己身上。** 每个损失除了算损失,还带一个批准备钩子:轨迹和分数都拿到之后,由这个钩子把整批改写成这个算法要的形状。基类的默认实现原样返回,所以策略梯度那一族什么都不用做;在线成对那条在这里按分数给每个提示词挑出最好和最差的一条,把整批砍成一对一对;正向过程那条在这里自己算一遍组内归一、把归一后的值映射成一个 0 到 1 的权重、再抽出真正要训练的那几个时间步。**同一件事在两族里的落点不同**:一族在控制器上查表算,一族在损失类的钩子里算。

worker 那边还有一处值得说:最终损失是**从同一张表里取三次加起来**的。主损失一次,打开对 Reference Policy 的约束再取一次,打开蒸馏再取一次,各乘各的系数。所以那张表里有几个条目压根不是拿来当主损失的,它们只是加项。

每个损失还在类上声明自己要哪些键——模型前向得吐出哪几个、批里得带哪几个。派发之前统一校验一遍,缺了就报出缺哪些、现有哪些。这一小步很值钱:表天生会让「注册过」和「跑得通」变成两件事,而这个声明把第二件事的暴露时刻从训练中途提前到了第一个微批。

## 三、代价

四笔。

**第一笔:一个名字级联到四处,一复用就撞墙。** 模型配置里有一个算法名,通过配置模板同时喂给四个派发点:训练侧适配器表、生成侧适配器表、Advantage 表、损失表。完成相关实现与注册之后,这一默认级联可以减少重复配置。可大多数新变体是复用的——换个采样窗口、换个裁剪方式,Advantage和损失一字不动。这时级联把新名字推到那两张表上,但新名字不一定已注册:Advantage 表接受字符串扩展,缺注册才查不到;损失还额外受配置类的取值白名单约束。官方的解法是把这两处手工钉回旧名字,仓库里的滑窗配方就是这么写的:一个启动脚本里三个算法名,两个是旧的。**一个字段只能传名字,不能代替实现、注册与配置校验。**

**第二笔:表和白名单要手工同步,现在已经对不齐。** 损失表里注册了十个名字,配置白名单里只有九个;少的那一个是 Reference Policy 约束用的加项,由代码按名直取,本来也不该让人填。方向反过来同样出事:注册了而忘了加进白名单,解析配置时就被顶回来,而报错说的是「无效取值」,不是「没注册」——查错的方向一开始就被带偏。

**第三笔:两族各算各的组内归一。** 正向过程那条在损失类的钩子里重写了一遍减均值除标准差,和 Advantage 表里那个函数几乎一样,源码注释专门写了一句「这和策略梯度的Advantage不是一回事」。这是分层带来的真实重复:那个函数长在控制器上、按Advantage的接口写;钩子长在损失类上、产出的是一个权重。合并的代价比重复还大,所以没合。

**第四笔:同名参数在不同损失里的合适取值明显不同。** 比值裁剪幅度这一个字段,配置默认是万分之一,官方给策略梯度那条主线配方填的是十万分之一,给另一个带偏置项的损失建议的是2e-6。不是笔误,是不同损失对裁剪幅度的敏感性不同。**读一个损失的参数就得读那个损失**,别拿另一个的经验套。

## 四、和 verl 的算法接入不一样的五处

**第一,两张表不是两条轴。** 那边Advantage和损失分开填,可选组合是乘出来的,几个听上去像新算法的东西其实是同一个Advantage配不同的损失。这边Advantage那张表只有一个函数挂两个名字,乘不出什么;真正的两条轴是「训练器线 × 损失」。照那边的经验来排组合,会发现一半的格子在这边根本不存在。

**第二,主循环能不能一直不动,要看新算法属于哪一族。** 那边的承诺是循环一行不动;这边只对策略梯度那一族成立。直接偏好那一族要的是另一份顺序流——已经写好了,加新算法不用再写一遍,但这份顺序流是**复制出来的,不是分支出来的**:两份里的存档判断、剖析器状态机、指标收集是逐行同构的两套。少了一个共同的主循环,好处是各自的阶段序列一眼看得见,代价是改一处要改两处。

**第三,调用约定这边守住了一半。** 那边表里的函数签名不统一,控制器留着一小片按名字分叉的代码专门决定该塞哪几样东西,最常用的两个估计器干脆没走查表。这边损失那一侧做对了:要哪些键写成类属性,派发前统一校验,报错把缺的和现有的都列出来。可Advantage那一侧犯了同一个错——两个额外开关只在估计器名正好等于枚举里第一个取值时才传下去,另一个名字指向的是同一个函数,却只能拿到函数签名上的默认值。两个名字、一个函数、不同的行为,而指标上看不出差别。

**第四,角色由什么决定。** 那边是估计器名加两个约束开关,决定价值网络与 Reference Model 那两组起不起。这边多了一层更粗的:数据来源那个字段直接决定整套生成与打分的 worker 组建不建。离线那条跑起来时集群上只有 Actor,看着像配错了,其实是对的。

**第五,全模态那条线几乎没自己加东西。** 走策略梯度时它直接用参照项目的那两张表,本仓库一行算法代码都没加,启动脚本里填的就是那边的估计器名和损失名;只有走直接偏好时才另开了一张表,而那张表到今天只有一个条目。**这是「薄层」最干净的一次体现**:能复用的一概不重写,重写的都是那边表达不了的。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**先说入口。** 选一个算法要填的不是一个字段,是一组:族名与数据来源定大方向,算法名再级联到Advantage与损失两处——复用已有实现时这两处要手工钉回去。引擎那一侧的注册键不跟着级联,得单独填,见 04 章。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `algorithm.trainer_type` | 启动配置 | `policy_gradient` | 换成 `direct_preference` 走另一份顺序流,一步里不再有摊分算 Advantage 这一段 | 步内出现的计时段 |
| `algorithm.sample_source` | 启动配置 | `online` | `offline`:只建 Actor,生成与打分的 worker 组一个都不起 | 启动时建出来的 worker 组 |
| `actor_rollout_ref.model.algorithm` | 启动配置 | `flow_grpo` | 一个名字同时选两张适配器表加 Advantage 估计器加损失;复用已有实现时后两处要另行钉回 | 起不来时报错里列出的已注册键 |
| `algorithm.adv_estimator` | 启动配置 | 跟随上一行 | 只有策略梯度那条线读它;内置 `flow_grpo` 与 `dance_grpo` 指向同一函数;还可注册其他字符串名字 | 未知估计器的启动报错 |
| `actor_rollout_ref.actor.diffusion_loss.loss_mode` | 启动配置 | 跟随算法名 | 换主损失;白名单九个取值 | `actor/` 前缀下出现哪几个键 |
| `actor_rollout_ref.actor.diffusion_loss.clip_ratio` | 启动配置 | `0.0001` | 比值裁剪幅度;主线配方用 `1e-5`,`grpo_guard` 官方建议 `2e-6` | `actor/pg_clipfrac` |
| `actor_rollout_ref.actor.diffusion_loss.adv_clip_max` | 启动配置 | `5.0` | 策略梯度里是裁Advantage;`diffusion_nft` 里是把Advantage映射成权重的分母 | `actor/reward_prob_mean` |
| `actor_rollout_ref.actor.diffusion_loss.kl_mask_threshold` | 启动配置 | `1e-5` | 只有 `flow_dppo` 读:散度超过它且还在往外跑的样本,损失清零 | `actor/masked_fraction` |
| `actor_rollout_ref.actor.diffusion_loss.add_kl_coefficient` | 启动配置 | `true` | 只有 `flow_dppo` 读:散度要不要按噪声尺度归一 | `actor/kl_new_old_mean` |
| `actor_rollout_ref.actor.diffusion_loss.mix_beta` | 启动配置 | `0.5` | 只有 `diffusion_nft` 读;官方配方用 `0.1` | `actor/positive_loss`、`actor/negative_loss` |
| `actor_rollout_ref.actor.diffusion_loss.ref_kl_coef` | 启动配置 | `0.0` | 只有 `diffusion_nft` 读:预测空间上对 Reference Model 的约束 | `actor/ref_kl_loss` |
| `actor_rollout_ref.actor.diffusion_loss.adaptive_weight_min` | 启动配置 | `1e-5` | 只有 `diffusion_nft` 读:重建项分母的下限,必须为正 | `actor/total_loss` 有没有跳变 |
| `actor_rollout_ref.actor.diffusion_loss.dpo_beta` | 启动配置 | `2000.0` | 只有 `dpo` 读;官方在线配方用 `100.0` | `actor/dpo_loss`、`actor/implicit_acc` |
| `actor_rollout_ref.actor.use_kl_loss` · `kl_loss_coef` | 启动配置 | `false` · `0.001` | 打开后在主损失之外从同一张表再取一项加上去 | `actor/kl_loss`、`kl_coef` |
| `actor_rollout_ref.actor.use_distill_loss` · `distill_loss_mode` · `distill_loss_coef` | 启动配置 | `false` · `distill_kl` · `1.0` | 第三项,还是同一张表;取值只认两个蒸馏损失 | `actor/distill_kl_loss` |
| `algorithm.norm_adv_by_std_in_grpo` · `algorithm.global_std` | 启动配置 | 均为 `true` | **只在估计器名正好是 `flow_grpo` 时才传下去**;填 `dance_grpo` 拿到的是函数签名默认值 | Advantage的分布区间 |
| `algorithm.adv_mode` | 启动配置 | `continuous` | 只有 `diffusion_nft` 读,五个取值决定Advantage怎么映射成权重 | `actor/reward_prob_mean` |
| `algorithm.timestep_fraction` | 启动配置 | `1.0` | 只有 `diffusion_nft` 读:抽多大比例的时间步进这次更新 | 更新那一段的耗时 |
| `algorithm.paired_preference` | 启动配置 | `false` | 置真:Actor 小批翻倍,打乱被强制关掉,好让成对样本不被拆开 | 启动时那条关闭打乱的警告 |
| `algorithm.old_policy_update_interval` · `old_policy_decay_schedule` · `old_policy_decay` | 启动配置 | `1` · `copy` · `null` | 旧策略副本多久刷一次、用覆盖还是滑动平均 | 旧策略那组指标 |
| `actor_rollout_ref.rollout.n` | 启动配置 | `1` | 组相对必须大于 1;在线成对时每个提示词只留 2 条,其余全丢 | 更新那一步的批大小 |
| `actor_rollout_ref.rollout.calculate_log_probs` | 启动配置 | `false` | 直接偏好那条线应当留假;策略梯度的配方一律显式置真 | 交回来的批里有没有逐步概率 |
| `actor_rollout_ref.model.model_type` | 启动配置 | `diffusion_model` | 引擎注册键,不跟着算法名级联;两族各有自己的取值,见 04 章 | 起不来时报找不到注册项 |

**典型配置。** 基于完整官方配方的三个调整方向:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 在线策略梯度起步 | 选对应模型配方,算法名用 `flow_grpo`、组大小设 `16`、裁剪幅度按配方填 `1e-5`;Reference Policy 约束先关着 | 最标准的一条,旧策略重算和可选约束按配置执行;Reward 满足条件时可与 Rollout 重叠 |
| 复用现成损失的新变体(换采样窗口、换裁剪) | 算法名填新的,同时把 `algorithm.adv_estimator` 与 `actor_rollout_ref.actor.diffusion_loss.loss_mode` 钉回 `flow_grpo`,新增的旋钮挂在生成侧那一块 | 只写一对适配器,不碰两张表;代价是三个算法名从此要一起维护,漏钉一处就起不来 |
| 在线成对偏好 | 族名换 `direct_preference`、数据来源留 `online`、`algorithm.paired_preference=true`、`loss_mode=dpo`、`model_type=diffusion_dpo_model`、组大小 `16`、`calculate_log_probs=false` | 用「生成 16 条只留 2 条」换掉整条轨迹的存储与重算;每张卡的微批必须是不小于 2 的偶数 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测。** 这一章看三处。一是**哪几个计时段出现了**:摊分算 Advantage 那一段只在策略梯度那条线上有,批准备那一段只在在线直接偏好那条线上有,旧策略概率那一段跳过之后就消失——**判断你实际在跑哪条线,看计时段比读配置快**。二是**Actor 指标里出现了哪些键**:比值与裁剪比例那一组只有策略梯度那族会报,掩码比例那一组只有带散度掩码的损失会报,成对损失与隐式准确率那一对只有成对偏好会报,加项的两个键只在对应开关打开时才出现;键出现得不对,就是算法没选成你以为的那个。三是**启动那几行报错**:未注册的适配器键会把全部已注册的两元组列出来,未知估计器和无效损失取值会各自列出可用名字,而这三种报错指向的是三个不同的字段。

| 症状 | 先查 | 然后 |
|---|---|---|
| 起不来,报无效的损失取值 | 算法名是不是级联过去了 | 复用已有损失的变体必须把损失那一处手工钉回旧名字,白名单不认新名字 |
| 起不来,报未知的 Advantage 估计器 | 同上,另一处 | 新名字尚未注册;复用时显式选旧名字,扩展时注册新函数或别名 |
| 起不来,报找不到已注册的适配器 | 报错里列出的两元组 | 有的算法名只注册了生成侧那一半,训练侧没有对应项,这种名字当前配不通 |
| 集群上只有 Actor,没起生成和打分 | 数据来源那个字段 | 离线那条本来就不创建这两组 worker,这是预期不是故障 |
| 换了组内归一那个开关,曲线毫无变化 | 估计器名填的是两个取值里的哪一个 | 开关只在其中一个名字下才传进函数,另一个拿的是签名默认值 |
| 直接偏好跑起来后批一下子小了很多 | 组大小,以及是不是在线成对 | 在线成对每个提示词只保留最好和最差两条,组大小 16 时 14 条被丢弃 |
| 在线成对报建不出偏好对 | 组大小是不是还等于 1 | 一个提示词至少要两条才挑得出一对 |
| 成对样本被拆进不同微批 | 每卡微批是不是偶数,打乱是不是关着 | 成对开关会强制关打乱并打一行警告,但微批的奇偶要自己保证 |
| 换了主损失之后报缺某个键 | 报错里列出的缺失键与现有键 | 每个损失在类上声明了自己要什么;缺的那几个通常由生成侧适配器或引擎产出,换损失往往要连着换引擎注册键 |
| 指标里始终没有蒸馏或约束那一项 | 对应的两个开关 | 这两项是在主损失之外另取一次加上去的,开关不开就完全不出现 |

## 六、常见误区

- **以为算法名是一个纯粹的开关。** 它是四个派发点的默认共同输入,但各表独立维护,损失还有白名单。新算法需完成实现与注册,复用型变体则可能要分别指定已有 Advantage 与损失名字——官方自己的滑窗配方就得在启动命令里把另外两处钉回旧名字。**这一条是本章最贵的误会**,因为报错信息指向的是被钉回的那两个字段,而根因在算法名那一个字段上。
- **以为注册表里列得出的名字都能填。** 这边的问题和参照项目那边方向相反:那边是注册了却喂不到数据,这边是**注册了却不在白名单里**。损失表里有十个名字,能填的只有九个;多出来那个是代码按名直取的加项。反过来也一样,忘了同步白名单时报错说的是「无效取值」,查错方向一开始就错了。
- **以为直接偏好那条线就是「吃离线数据」。** 它有在线和离线两种形态,而且在线那种才是当前配方里更常见的:照样生成、照样打分,只是生成回来的不是轨迹而是成品,打完分再由损失类的钩子准备输入:DPO 挑出样本对,NFT 构造逐样本权重。看到一条直接偏好的配方起了整套生成与打分栈,不用怀疑配错了。
- **以为新一代训练器那条路只能跑策略梯度。** 它的基类名字里确实写着策略梯度,但类里有一整段是给直接偏好准备的,被挡住的只有「直接偏好加离线数据」那一种组合,报错还会明确告诉你回老入口。**类名比代码旧**,照名字下结论会漏掉一整条已经有配方的路径。
- **以为两条线都会去查 Advantage 表。** 只有策略梯度那条会。NFT 算出来的那个逐样本权重是在损失类的钩子里现算的,虽然它也读组内归一那两个开关、算法也长得像,但那是另一份代码。想改它的行为,去改损失那一侧,改 Advantage 表没用。
- **以为比值裁剪幅度是个跨损失通用的经验值。** 配置默认万分之一,主线配方十万分之一,带偏置项的那个损失官方建议`2e-6`。三个取值差异明显,共用一个字段名。**照另一个损失的经验填这个数,裁剪要么全程不起作用,要么一上来就把所有样本裁死。**
- **以为 Reference Model 那一段由约束开关决定。** 策略梯度那条是这样;DPO 则由损失本身要求 Reference Model 的预测,所以即使约束开关关着,那一段照样出现、照样占卡。NFT 的 FSDP 引擎还会在 Actor 内关闭适配器取得参考预测,再由 ref_kl_coef 决定参考项是否影响损失;这与独立 Reference Model 阶段不同。
- **以为全模态那条线也有一套自己的算法接入。** 它走策略梯度时用的是参照项目那两张表,本仓库一行都没加;只有直接偏好才另开了一张表,而那张表只有一个条目。在这边翻找全模态的策略梯度实现是白费力气,那份代码在参照项目那边。
