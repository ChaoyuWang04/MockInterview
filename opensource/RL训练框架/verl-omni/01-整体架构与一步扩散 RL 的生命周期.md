# 整体架构与一步扩散 RL 的生命周期

一批提示词怎样经过 Rollout、打分和 Actor 更新,以及这些阶段为什么要为扩散模型重新组织。说法都在源码基准 `b708218d5b`(tag `v0.2.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

把扩散模型接进文本后训练框架,首先要解决的是**训练需要的中间数据,普通生成接口不会交回来**。

普通图像生成只需要返回成品;扩散 Policy Gradient 还需要知道选中的去噪步经历了什么:中间状态、时间步、采样所用条件。Actor 要在这些状态上重新前向,计算更新策略所需的 log-prob。因此 Rollout 不只交图,还要交回训练需要的轨迹片段。生成可以走完整条链,训练和保存的却不必是全部生成步。

第二处是**样本分数怎样用于轨迹上的更新**。本章讨论的 FlowGRPO 路径为一张图提供一个样本级 Reward,再从同一提示词下多条样本的相对得分计算 Advantage。不同样本可以有不同 Advantage,同一条轨迹选中的训练步则共享它。这不是文本与扩散的根本区别:文本 GRPO 也可以让一个回答的有效 Token 共享同一 Advantage。

第三处是**生成与视觉打分的资源竞争**。Reward 可以来自规则、外部服务或视觉模型;复杂打分可能进入关键路径。因此框架既要组织训练数据,也要安排 Rollout、打分与 Actor 如何交接资源。

## 二、解法

下面沿默认入口下、在线 Policy Gradient 的共卡路径看一步;其他模式在第四节区分。

**控制器保留顺序流程,底层复用 verl。** 它取提示词、调用 Rollout、收分数、安排所需前向、计算 Advantage、更新 Actor 并同步权重。worker 的分发、资源池与权重传输沿用 verl;扩散特有的阶段和数据组织由本仓库实现。

一个提示词生成一组样本,Rollout 返回成品及选中的轨迹片段。共卡且启用显存释放时,Rollout 完成后进入 sleep,给后续训练腾出显存。满足流式打分条件时,已完成的样本可以提前评分,与剩余生成重叠;这能减少等待,但不保证消除全部打分耗时。

之后按配置执行旧策略 log-prob 重算、Reference Model 前向以及 Teacher 前向。**Teacher 提供蒸馏需要的模型预测,不是另一个给图片打分的 Reward Model**;它可以复用 Actor worker,也可以独立部署。完成这些准备后,控制器计算 Advantage,Actor 更新参数,新权重再同步给 Rollout。

## 三、代价

**第一笔是轨迹数据。** 相比只返回成品,保存和传输训练片段增加了数据开销。减少保存或训练的步数可以降低成本,但也改变训练覆盖的范围;生成步数、保存的轨迹窗口和参与更新的步数是相关但不同的选择。

**第二笔是资源交接。** 共卡节省常驻模型所需的 GPU,代价是 sleep、唤醒和权重交接;独立资源池能减少竞争,但需要额外资源。是否值得,要看具体负载。

**第三笔是路径组合。** 算法族、在线或离线数据、同步或异步执行是不同维度,也不是所有组合都支持。排查问题前,先确认当前路径实际包含哪些阶段。

## 四、和 verl 一步训练不一样的地方

**数据形态不同。** 文本 Rollout 主要返回 Token 序列及相关信息;扩散 Rollout 还要组织选中去噪步的状态与条件。两者都有数据开销,但需要保存的内容不同。

**Advantage 不应被当成两者的区别。** 本仓 FlowGRPO 的主线是样本间比较、样本内共享:同一提示词生成多条图像轨迹,结果分数经过中心化和缩放后用于选中的训练步。默认采用组内中心化与全批标准差缩放,也可按配置调整。下图展示这一关系,不表示每个去噪步单独获得一次评分。

![FlowGRPO 的样本与时间步图:同一提示词的三条示意样本分别获得结果 Reward,计算样本级 Advantage 后广播到各自选中的训练步;同一行数值相同,不同行可以不同,空白位置未参与本次更新。](/opensource/verl-omni/01b-reward-on-timeline.svg)

**训练路径的切分不同。** 本项目的扩散默认入口按 Policy Gradient 与 Direct Preference 区分算法族。Direct Preference 可以使用离线样本对,也可以在线生成、评分,再按算法构造成对比较或逐样本加权目标;只有离线路径省去在线 Rollout 与打分。V1 则提供队列与异步组织方式,需选择对应入口并启用开关。具体算法见 05 章,异步见 08 章。

**Rollout 后端的选择更集中。** 本基准的扩散服务围绕 vLLM-Omni 接入,训练配置必须明确选择后端;模型适配与批处理能力见 02、03 章。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `trainer.use_v1` | 启动配置 | `false` | 配合 V1 入口启用新训练器 | 启动日志中的入口与训练器 |
| `algorithm.trainer_type` | 启动配置 | `policy_gradient` | 选择算法族;Direct Preference 不等于离线 | 实际执行的阶段 |
| `algorithm.sample_source` | 启动配置 | `online` | 选择样本来源;离线 Direct Preference 不做在线 Rollout | 数据来源与阶段计时 |
| `actor_rollout_ref.rollout.name` | 启动配置 | 必填 | 指定 Rollout 后端 | 启动校验 |
| `actor_rollout_ref.rollout.n` | 启动配置 | `1` | FlowGRPO 需要同提示词多样本来形成相对优势 | `critic/rewards/zero_std_ratio` |
| `actor_rollout_ref.rollout.pipeline.num_inference_steps` | 启动配置 | `10` | 控制生成去噪步数,不等于保存或更新的步数 | `timing_s/gen` |
| `actor_rollout_ref.hybrid_engine` | 启动配置 | `true` | 控制共卡组织;分卡还需启用 `separate` 并配置独立资源与权重通路 | 资源布局与权重同步耗时 |
| `actor_rollout_ref.actor.use_kl_loss` | 启动配置 | `false` | 当前 Policy Gradient 路径增加 Reference Model 约束 | Reference 前向计时 |
| `reward.reward_model.enable_resource_pool` | 启动配置 | `false` | 旧单 Reward Model 路径使用独立资源池,满足条件时可流式打分 | Reward 与整步耗时 |
| `algorithm.rollout_correction.bypass_mode` | 启动配置 | `false` | 复用 Rollout log-prob,跳过旧策略重算;需配套返回 log-prob | 重算计时与训推偏差 |
| `trainer.save_freq` / `trainer.test_freq` | 启动配置 | 均为 `-1` | 设置存档和验证频率 | 对应阶段是否执行 |

**配置方向。** 以下用于理解取舍,实际启动从匹配模型的官方配方开始。

| 场景 | 调整方向 | 拿什么换什么 |
|---|---|---|
| 先理解一步流程 | 默认入口、共卡、在线 Policy Gradient;FlowGRPO 使用同提示词多样本 | 资源复用,接受阶段切换开销 |
| 视觉打分成为瓶颈 | 根据 Reward 路径配置独立资源池,核对能否启用流式打分 | 增加资源,减少生成与打分竞争;命名多奖励模型当前不支持流式 |
| Rollout 长尾使训练等待 | 选择 V1 分卡异步配方 | 增加资源与样本陈旧度管理,换取阶段重叠 |

**观测。** 阶段耗时看 `timing_s/*`,按图归一耗时看 `timing_per_image_ms/*`,整步与吞吐看 `perf/time_per_step`、`perf/throughput`。先看等待发生在哪里,再决定分卡或异步是否有帮助。

| 症状 | 先查 | 然后 |
|---|---|---|
| FlowGRPO Reward 曲线不动 | 同提示词样本数量与分数差异 | 组内无差异时相对 Advantage 缺少学习信号;再查其他损失与梯度 |
| 一步明显变慢 | Rollout、Reward、Actor 各阶段计时 | 确认瓶颈后再调整资源,不要预设一定是打分 |
| 代码与日志对不上 | 入口、算法族与样本来源 | 对照当前路径,不套用另一分支的阶段 |
| Rollout 结束后显存不降 | 是否共卡、是否启用 sleep | 独立部署或未释放缓存时不能期待同样的显存变化 |

## 六、常见误区

- **以为 V1 在这里也是默认路径。** 从 verl 读过来容易沿用这个判断;本项目扩散线需显式选择 V1 入口并启用开关。
- **以为 Direct Preference 天然没有 Rollout。** 在线配方同样要生成和评分;DPO 再构造样本对,NFT 使用逐样本权重,只有离线路径省略在线生成与打分。
- **以为图像的每个去噪步都要重新打分。** 本章 FlowGRPO 用样本级 Reward 形成 Advantage,再用于该样本的选中训练步;样本内共享不代表不同样本之间没有差异。
- **以为 Teacher 就是另一个 Reward Model。** 两者提供不同信号:前者给蒸馏预测,后者给任务分数,不要把两种前向混在一起。
- **把 Rollout 计时直接当成引擎吞吐。** 共卡路径的阶段计时还包含资源交接,与独立运行推理引擎的测量口径不同。
- **以为保存的步数就是生成步数。** 生成走过的时间步、保存的窗口和 Actor 选取的训练步必须区分,不能看到数量不同就认定配置出错。
