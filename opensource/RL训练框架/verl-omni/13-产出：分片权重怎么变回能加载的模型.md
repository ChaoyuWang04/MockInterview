# 产出：分片权重怎么变回能加载的模型

怎样把训练保存的分片恢复成完整 Actor 权重,再打包为推理侧能够识别的模型目录。说法都在源码基准 `b708218d5b`(tag `v0.2.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**能够恢复训练的 Checkpoint,不等于能够直接加载的推理模型。** 恢复训练可能需要模型、优化器、学习率调度器与随机状态;推理加载器需要完整模型权重、对应配置,以及生成流水线依赖的组件。两者面向的使用者不同。

FSDP 把参数分散在不同 rank 的文件里。仅把文件放到同一个目录,不会自动变成推理加载器认识的权重。扩散模型还有第二个问题:训练更新的通常是生成网络,完整生成仍需要底模里的文本编码器、VAE 和 Tokenizer 等资产。

## 二、解法

**先重建被训练的完整组件,再决定交付单个组件还是完整 Pipeline。** 产出工具读取 Actor 的配置与 rank 文件,检查训练配置是否与底模兼容,再按模型结构要求逐个恢复参数。每个训练参数都必须来自 Checkpoint,缺失时直接失败,不从底模拿旧权重补齐。

重建依据是 DTensor 的分片布局。分片参数按设备网格顺序沿记录的维度拼接,副本参数必须逐值相等;普通 Tensor 只有完整形状才被接受,多 rank 时还要验证副本一致。工具不会猜测一个普通 Tensor 是否恰好是某个维度的切片。

重建后的权重写成标准 safetensors。只交付生成网络时,输出包含组件配置与权重;交付完整 Pipeline 时,用新权重替换底模中的训练组件,保留其余组件与资产。MiniMax H3 的完整产出还要把训练侧名称和张量布局转为原生包格式,因此这一步也不总是简单改文件名。

![模型产出文件流:Actor 各 rank 的参数分片按布局重建后写入新的 safetensors,兼容底模提供配置与未训练组件,产出可选独立组件或完整 Pipeline;LoRA 输入在入口被拒绝,校验产物后仍需单独验证加载与生成。](/opensource/verl-omni/13a-checkpoint-to-artifact.svg)

**LoRA 不走这条完整权重出口。** 当前工具发现 LoRA 元信息或 adapter 参数就拒绝导出。这里的“合并”是恢复分布式权重,并不包含把 LoRA 增量融合进底模。

## 三、代价

**省下全模型常驻内存,仍要承担重建和校验成本。** rank 文件在 CPU 上映射读取,参数逐个重建,输出按预算攒成文件。但单个大 Tensor、重建副本和写后校验都需要额外内存,文件分片预算不是进程内存上限。

**完整 Pipeline 换来可携带性,也增加复制与磁盘空间。** 未训练组件从本地兼容底模复制,导出器不会替你下载缺失资产。Actor 配置、完整参数集合与底模结构必须相符,仅有同一个模型家族名称还不够。

**校验需要读回,但不替代模型运行。** 导出时会将重建结果与源分片核对,将写出的权重与预期值核对,并记录文件哈希与张量元信息。它保证的是本次转换与文件完整性;加载、固定输入前向和实际生成质量需要另外验证。

## 四、与上游 verl 的关系

本项目沿用 verl 的“配置、执行合并、清理”生命周期,但为扩散模型独立实现结构识别与打包。固定上游通过 Transformers 的模型配置与加载类组织产物;这里按已审查的扩散架构选择组件或 Pipeline,没有把扩散配置直接送进 Transformers 的自动配置入口。

范围也不能从上游顺推。上游有保存 LoRA adapter 的逻辑,并不代表 VeRL-Omni 这个出口已经支持 LoRA;当前入口只接受受支持的 FSDP 完整权重,不代理 Omni 或普通 Transformers 模型的产出。BAGEL 也在本出口之外,训练时可用不等于这里可导出。

## 五、调参与观测

这些参数用于独立离线 CLI,每次调用读取一次,不需要重启训练作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `merge` / `test` | `verl_omni.model_merger` 子命令 | 必选 | 前者重建并打包;后者只复查已有产物 | JSON 结果与失败异常 |
| `--backend` | 离线 CLI | 必填,仅 `fsdp` | 选择当前唯一后端;输入还必须符合 FSDP2 表示 | rank 元数据与布局检查 |
| `--local_dir` / `--base_model` | 离线 CLI | merge 必填 | 指向 Actor Checkpoint 与兼容底模 | 缺参数、缺文件或结构不匹配时报错 |
| `--target_dir` | 离线 CLI | `tmp` | 设置新产物目录;目标必须不存在且父目录已存在 | 成功返回 `output_dir` |
| `--output_format` | 离线 CLI | `pipeline` | 改为 `transformer` 只输出组件,减少复制 | 是否有完整流水线组件与 `model_index.json` |
| `--dtype` | 离线 CLI | `preserve` | 显式转换训练所得浮点权重,保留声明的 FP32 部分 | manifest 的 dtype 与张量记录;溢出直接失败 |
| `--max_shard_size` | 离线 CLI | `2147483648` 字节 | 控制输出文件攒批预算,单张量超限会独占文件 | 输出分片数与进程实际内存 |
| `--hf_model_config_path` | 离线 CLI | Actor 目录下的 `huggingface` | 指定训练时对应的配置目录 | 与底模配置的兼容性检查 |
| `--trust-checkpoint` | 离线 CLI | `false` | 显式允许读取可信的 pickle Checkpoint | 未设置时 merge 拒绝启动 |
| `--trust-remote-code` | 离线 CLI | `false` | 允许复制受支持本地底模中的 Python 资产 | 原生 H3 或部分 Boogu 包的资产检查 |
| `--test_hf_dir` | test 子命令 | 必填 | 复查产物文件、哈希、索引和张量元信息 | 成功时 `integrity=passed` |

**支持范围。** 当前架构表覆盖 Qwen-Image、Qwen-Image-Edit Plus、SD3、Flux、Wan、LTX-2、MiniMax H3 与 Boogu-Image;配置和标准资产布局仍须通过校验。输入支持一维 FSDP2 的 `Shard`、`Replicate`,以及满足完整形状和副本一致性要求的普通 Tensor;不支持 FSDP1 `ShardedTensor`、多维混合分片、TP、量化权重或任意自定义 Pipeline。

**典型配置方向。** 以下选择建立在官方导出流程的完整输入条件之上。

| 场景 | 怎么配 | 拿什么换什么 |
|---|---|---|
| 只把训练后的组件交给已有推理程序 | `--output_format transformer`,使用兼容组件底模 | 减少复制,由调用方组装其余依赖 |
| 希望产物目录携带整套生成资产 | 保留 `--output_format pipeline`,提供完整本地底模 | 增加磁盘复制,换取完整打包 |
| 先检查转换是否可靠 | 保留 `--dtype preserve`,导出后运行 `test` | 避免额外精度转换,仍须另做运行验证 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测。** 检查 `merge_manifest.json` 的源与底模指纹、输出清单和 `verification`。其中 `runtime=not_run` 是预期结果,不是漏报成功。该基准使用 Linux 的不覆盖式原子重命名发布目录;非支持平台会明确失败。已有目标不会被覆盖,失败只清理本次暂存目录与锁,没有自动断点续导。

| 症状 | 先查 | 然后 |
|---|---|---|
| 提示训练参数不完整 | 是否拿到完整 Actor 状态,或混入 adapter | 恢复匹配的完整 Checkpoint,不要用底模补缺键 |
| 提示 rank 文件不符 | FSDP 元数据声明与实际 rank 文件集合 | 找齐同一次保存的文件,不混用不同步数 |
| LoRA 配方训练完成却无法导出 | 本出口是否拒绝 LoRA 元信息 | 区分 adapter 保存、adapter 加载和权重融合,不强行套完整权重出口 |
| 调小分片预算仍内存紧张 | 单 Tensor 大小与重建、校验峰值 | 为离线导出留足 CPU 内存,不要把预算当 RSS 上限 |
| test 通过但生成结果不符合预期 | 模型加载方式与运行验证是否完成 | 单独做加载和固定输入比较,再评估生成质量 |

## 六、常见误区

- **看到 merge 就以为会融合 LoRA。** 同一个词常用于不同工具;本入口重建的是分布式完整权重,遇到 adapter 会报错。
- **拿“同系列底模”补齐缺失训练参数。** 这样可能得到能加载但不是训练结果的模型,所以工具要求完整键集合,宁可失败也不混入旧参数。
- **把输出文件数量当成训练 rank 数。** 输入按分布式保存,输出按文件大小预算重新组织,两者没有一一对应关系。
- **以为 test 会跑一次图像生成。** 它只检查已发布文件,不会自动用 GPU;即使文件哈希一致,也没有证明生产输入下的生成质量。
- **把官方微型模型测试当成自己权重的验收。** 官方有 CPU 加载与前向一致性测试,它们证明对应测试条件下的实现行为;真实 Checkpoint 的加载与运行仍应单独验证。
