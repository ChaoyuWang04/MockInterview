# 整体架构与一步训练的生命周期

这一页回答一件事:一次后训练里,生成、训练、数据怎么摊在几类进程上,以及一步循环依次经过谁的手。说法都在源码基准 `5bae5bb792`(tag `v0.3.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一次强化学习后训练要同时养活两件会抢卡的事:一边用推理服务源源本本地出样本,一边用训练框架对着这些样本更新策略。它们每一步还要换一次权重。样本从哪来——单轮答题、多轮改代码、外面已经写好的 agent——差别极大。

最常见的两种做法都会在规模上把指标弄坏。一种是为每种任务 fork 一套训练循环:补丁跟不上,崩在漏掉的那一处,坏的是**稳定性**。另一种是把算法逻辑也写成多进程程序,每张卡跑同一份脚本、按序号判断自己该干什么:换训练后端就要连循环一起改,想看中间那批奖励还得在所有进程里同时停下来,坏的是**可改性和可观测性**。

反过来把推理引擎当库函数塞进训练进程也不行:生成要吃独立的调度、缓存和 HTTP,训练要吃自己的并行和优化器,挤在一个进程里两边都施展不开。

所以真问题是:循环必须好写好查,生成和训练必须能各占各的进程,任务差别不能逼你去改循环。

## 二、解法

把循环留在提交作业的那个进程里,顺序写完。生成和训练做成两组远端角色,数据从生成侧切好再交给训练侧。

**循环是一段单机脚本。** 先向集群要卡,先起生成管理器(因为有的作业要用数据源的长度反推总步数),再起训练组,然后进入一步循环:生成一批、训练一批、把新权重推给生成侧。评测和存档按间隔插在循环里,不是另一套入口。

**生成侧是一个不占 GPU 的管理器,后面挂着若干推理服务。** 管理器持有数据源和生成函数:默认函数负责并发和回收,每条样本怎么跟服务器说话可以整段换成用户函数。管理器把样本转成训练用的张量字典,按数据并行切成每张训练卡一份,放进对象存储,循环那边拿到的是引用。

**训练侧是一组持有模型分片的进程。** 循环对这一组发一次协同训练,每个数据并行 rank 取自己那份引用。需要价值网络时,先让它算出价值再交给策略。训完之后才推权重——下一步生成必须用新权重。训练进程在让出显存打开时,会在训练前后自己醒过来、睡下去。

更狠的一档是生成期间把训练进程整个杀掉,下一步再按刚写下的检查点拉起来。这一档要求权重走盘上的全量文件,也不能和价值网络一起开,细节在放置与权重两章。

## 三、代价

三笔,都要认。

**第一笔是循环本身在提交作业的进程里。** 它要等生成结束、等训练结束,自己几乎不占 GPU,但会把引用和日志留在这个进程里。这个进程不是集群里那张最闲的卡,是你提交作业的那台——它挂了,整场都停。

**第二笔是生成和训练之间的腾挪。** 同卡时两边轮流占用显存,每步睡一次醒一次,这段时间两边都在干等。分卡时省了这趟舞,但卡要准备两份,权重还得从训练切法变成生成切法送过去。

**第三笔是「一步」变长了。** 生成、训练、推权重串在一起,任何一段慢下来都拖住整步。慢的那一段往往不在你盯着的那张训练卡上:生成在推理服务里,数据在管理器里,训练在另一组进程里。排查一次「这步怎么变慢了」,要同时看三类角色。

## 四、和同类常见做法不一样的地方

这一节拿实际项目做横向对照,用来把 slime 自己的选择衬出来,不是评哪家更好。对照对象只取大厂在大规模训练里真用的框架;这一页主对 verl——字节的后训练框架,本站已经有成稿。

| 比什么 | slime | verl |
|---|---|---|
| 循环写在哪 | 提交作业的进程里顺序写完,生成管理器和训练组才是远端角色 | 控制器做成远端角色再提交,循环落在集群里某台节点上 |
| 生成怎么接进来 | 推理服务起成 HTTP 服务,任务差别换生成函数,不换循环、不换引擎接口 | 推理引擎收成可换后端,循环通过副本调生成;默认路径上生成和打分各是一条主干 loop |
| 训练怎么接进来 | 只吃 Megatron,不在 slime 里再包一层引擎 | 六个训练后端收成同一组生命周期,换后端只动 worker 那一侧 |
| 数据怎么到训练侧 | 生成管理器按数据并行切好,每份放进对象存储,训练进程拿自己那份引用 | 控制器只拿元数据键,计算进程按键自取 |
| 一步里默认有谁 | 生成管理器加一组训练进程;价值网络默认不起 | 四类角色默认登记在同一个资源池,生成 loop 和打分 loop 都是主干 |

换句话说,slime 拿「循环短、生成可插、训练只吃切好的引用」换了两样东西:不为每种任务 fork 循环,也不在 slime 里再包一层训练引擎。这是一笔交易——生成函数写砸了,循环帮不上忙;切错了,训练侧看到的就是错的。和 verl 比,少的是那层分发协议和元数据队列。

## 五、调参与观测

**这一页的参数全是启动配置,改了要重新拉起整个作业。** 启动方式是跑仓库根的训练脚本,三类参数怎么拼见总览第六节。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--num-rollout` · 总步数 | 启动 | 空,用 epoch 反推 | 设了就忽略 epoch;必须和 epoch 至少设一个 | 循环上界 |
| `--num-epoch` · 按数据集长度反推总步数 | 启动 | 空 | 总步数 = epoch × 数据集大小 ÷ 每步题数;和上一项同时设时它被忽略 | 生成管理器启动时算出的每 epoch 步数 |
| `--rollout-batch-size` · 每步多少道题 | 启动 | 必填 | 大了生成更久、一步更长;和每题几条回答一起决定训练侧看到的样本数 | 生成日志里这一步的样本数 |
| `--n-samples-per-prompt` · 每题几条回答 | 启动 | 1 | 大了生成更久,组内对比更稳 | 同上 |
| `--start-rollout-id` · 从第几步接着训 | 启动 | 空则 0,续训时尝试从检查点读 | 循环从这一步开始,前面的生成不会重做 | 循环变量 |
| `--save-interval` · 每隔几步存档 | 启动 | 空 = 不按间隔存 | 设了必须同时给保存路径;最后一步仍会强行存 | 保存目录 |
| `--eval-interval` · 每隔几步评测 | 启动 | 空 = 不评测 | 设了必须配置评测集;第 0 步默认先评一次 | 评测日志 |
| `--skip-eval-before-train` · 开训前那次评测要不要跳 | 启动 | 关 | 开:省掉冷启动评测 | 第 0 步是否先出现评测日志 |
| `--num-critic-only-steps` · 前几步只训价值、不动策略 | 启动 | 0 | 大于零时前几步没有策略更新;默认优势估计不是 PPO,价值网络根本不会起 | 训练日志里策略更新是否缺席 |
| `--release-train` · 生成期间把训练进程杀掉再拉起来 | 启动 | 关 | 开:同卡时不再走训练侧 sleep,改成杀进程;要求全量盘同步、每次都存档,且不能和价值网络一起开 | 每步训练前是否重新创建 actor |
| `--debug-rollout-only` · 只跑生成 | 启动 | 关 | 开:不起训练组,生成结果不转成训练数据;不能和只跑训练同时开 | 循环里训练与推权重被跳过 |
| `--debug-train-only` · 只跑训练 | 启动 | 关 | 开:不起推理服务,可从落盘的生成结果回放 | 生成管理器里服务字典是空的 |
| `--save-debug-rollout-data` · 把每步生成落盘 | 启动 | 空 | 设了每步写一个文件,路径里可带步号 | 该路径下的文件 |
| `--load-debug-rollout-data` · 从落盘回放生成 | 启动 | 空 | 设了会顺带打开只跑训练,跳过推理服务 | 生成管理器不再调生成函数 |
| `--rollout-data-transport` · 引用走对象存储还是加速传输 | 启动 | `object-store` | `nixl`:大张量走加速通道,管理器要打开张量传输 | 管理器创建时的选项 |

**怎么看。** 这一章看三处。一是提交作业的进程:循环卡在生成、训练还是推权重,看它在等哪一次远端调用。二是生成管理器日志:导入了哪条生成函数、这一步样本数、耗时。三是训练组:每个 rank 是否都收到了自己那份引用;价值网络开启时,策略更新是否被前几步跳过。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| 单机先把循环跑通 | 总步数设小;先不要评测间隔;需要时打开生成落盘 | 用吞吐换一次能跑完的验证,便于确认生成、训练、推权重三站都通 |
| 只调生成或只调训练 | 打开只跑生成,或打开只跑训练并指定回放路径 | 用「另一侧完全不起」换排障时间;两边不能同时开 |
| 同卡、生成很长、训练进程占着显存不划算 | 打开生成期间杀掉训练进程,并配全量盘同步与保存路径 | 用每步重建训练进程的时间,换生成期间整份训练显存 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动后长时间卡住、一步都没有 | 生成管理器是否在等推理服务就绪 | 服务没起来时循环会堵在第一次生成 |
| 总步数不是你想的那个 | 总步数和 epoch 是否同时设了 | 同时设时 epoch 被忽略;只设 epoch 时步数由数据集长度除以每步题数算出 |
| 第 0 步先跑了一次评测 | 评测间隔是不是设了 | 不想要就打开跳过开训前评测 |
| 策略一直不更新 | 优势估计是不是 PPO、前几步只训价值是不是大于零 | 默认优势估计不会起价值网络;PPO 下前几步本来就不更新策略 |
| 打开杀掉训练进程直接报错 | 是否同时开了价值网络、是否没给保存路径、权重是不是全量盘 | 这三个条件缺一不可 |
| 只跑生成和只跑训练同时开 | 启动校验 | 两者不能同时设 |
| 训练侧拿到的样本数对不上 | 每步题数乘每题几条回答,以及生成函数是否把一次执行拆成多段 | 多段必须共用同一个编号,否则会按多条独立样本计 |

## 六、常见误区

**以为还有一个异步训练入口。** 仓库根只有这一份循环。完全异步换的是生成函数,后台工人跨步保持在飞的轨迹,循环骨架不动。去找另一份训练脚本,是第一反应最容易错的地方。

**以为循环跑在某张训练卡上。** 它跑在提交作业的进程里,自己几乎不占 GPU。训练卡上是持有分片的那组进程。在训练卡的日志里找「这一步循环走到哪了」,找错地方。

**以为生成管理器也占 GPU。** 它是远端角色,申请的是 CPU;GPU 在它后面挂着的推理服务上。同卡时那份 GPU 是训练和推理服务轮流用,不是管理器在用。

**以为默认会起价值网络。** 价值网络是否出现,跟的是优势估计是不是那一种需要它的算法,不是一个单独的总开关。按「有 actor 就有 critic」估算卡数,会多算一组。

**把生成落盘和回放落盘当成同一件事。** 回放路径会顺带打开只跑训练、跳过推理服务;另有一条回放路径故意不关推理服务,用来量长上下文的显存。看名字像、行为不是。

**以为评测间隔为空就是「评一次」。** 空是整场不评。设了间隔,第 0 步默认还要先评一次,除非显式跳过。
