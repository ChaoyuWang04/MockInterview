# 观测、复现、容错与调试

这一页回答一件事:静默的强化学习故障要靠三类角色各自的痕迹、健康检查和可回放的生成数据定位,而不是再加一层框架。说法都在源码基准 `5bae5bb792`(tag `v0.3.2`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

强化学习作业一挂就是整晚。推理服务卡死,心跳超时,同卡把显存让出去之后还去探活——探活打到睡着的引擎上,引擎被误杀,下一步生成接不回去。坏的是**可恢复性**:进程还在,样本链路已经断了。

另一头更常见:这一步墙钟变长,日志只给一个总时长。生成在管理器后面的 HTTP 服务里,训练在另一组进程里,提交作业的那个进程只是在等远端调用返回。只盯总时长,分不清慢在出样本、算奖励、训一步,还是推权重。坏的是**可观测性**。

再加一层「观测框架」解决不了这两件事。循环已经写在提交作业的进程里,生成和训练已经是两组远端角色。缺的是钉在这三类角色上的痕迹、睡醒时会停手的探活,以及一份能原样回放的生成落盘。

## 二、解法

**谁出问题就看谁,不要把三类角色揉成一张总表。** 提交作业的进程告诉你循环卡在生成、训练还是推权重;生成管理器告诉你这一步样本、耗时、以及探活有没有把引擎判死;训练组告诉你训练等待和训练本体各占多久。图上三列并排,就是这句断言。

**探活跟睡醒绑在一起。** 打开容错以后,生成管理器给每组引擎起一条监视线程。线程一上来先停着,只有生成或评测开始才恢复探活;引擎把显存让出去、或准备拉起死掉的引擎之前,必须先暂停。探活超时就把那一组杀掉、槽位留空,本轮生成走完后再拉起来补权重。路由器自己那套健康检查关掉,把探活让给这条监视器——起路由器那一章已经写过这一句。

**排障靠落盘,不靠再跑一遍随机生成。** 只跑生成时把样本连同时间线一起写下;回放那条路径会顺带关掉推理服务、只训训练侧。训练侧另有一份落盘,按样本编号能和生成落盘对上。要看长尾出在哪一条样本、奖励模型卡在哪一段,打开时间线查看器读落盘里的 span,不必再起一场作业。

![三类角色各看什么:提交作业的进程看循环卡在哪一站;生成管理器看样本、落盘和健康检查;训练组看等待与训练本体;同卡让出显存时健康检查必须先暂停](/opensource/slime/10a-observe-roles-health.svg)

## 三、代价

**第一笔是探活本身会误杀。** 大 MoE 第一次编译、瞬时打满队列,都可能让一次心跳超时。超时默认按秒计,第一次恢复后还有一段宽限;宽限给短了,引擎还没醒就被杀掉。杀完到下一轮补权重之前,那台服务是空槽,请求打过去会少一台。

**第二笔是落盘占盘、占写。** 每步一份生成文件,评测步还会多一份带评测前缀的。训练落盘只在流水线最后一段、张量并行 0 号上写,但要把上下文并行拼回去再按数据并行收齐。路径模板填错、生成落盘和训练落盘写成同一个文件,启动直接拒绝。

**第三笔是观测默认很瘦。** 奖励、损失、KL 进看板;推理服务高频指标不往看板上倒,要自己刮 HTTP。请求时延按步聚合成一小撮性能字段,不是每条请求一条。Prometheus 没在旁边跑,历史就没有。

## 四、和同类大厂框架不一样的地方

对照只取大厂在大规模训练里真用的框架;这一页主对 verl。重点在 slime 怎么排障,不评哪家更好。

| 比什么 | slime | verl |
|---|---|---|
| 生成侧挂了怎么办 | 打开容错后由生成管理器探活,超时杀引擎、本轮后再拉起补权重 | 本页未核到对等的「杀引擎再拉起」监视器;服务端点上的探活是等引擎就绪,不是这条生命周期 |
| 生成能不能原样回放 | 落盘是带时间线的样本文件,回放路径会关掉推理服务、固定训练输入 | 控制器可以把生成文本、分数落到目录里供人看,不是同一套可回放样本 |
| 一步慢在谁 | 提交作业进程看卡在哪次远端调用;生成侧按步聚合请求时延;训练侧把等待和训练本体拆开 | 有跨角色计时和可选的轨迹后端,主场在它自己的归因章 |
| 确定性 | 推理确定性加训练确定性,再配通信与随机算法环境变量,小模型上有对照脚本 | 本页未核 |

slime 拿「不另起观测框架」换回了三件事:探活跟睡醒同一条生命周期,落盘能回放,计时钉在三类角色上。这是一笔交易——训练 rank 挂了、整场被集群抢走,仍然要靠调度器和检查点,容错开关管不到那一层。

## 五、调参与观测

**这一页的参数全是启动配置,改了要重新拉起整个作业。** 排障开关和循环开关拼在同一条启动命令里,改完必须整场重来。

| 参数 · 一句话中文说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--use-fault-tolerance` · 打开生成侧容错 | 启动 | 关 | 开:每组引擎一条监视线程;只跑训练时不起 | 日志里监视器启动、暂停、恢复 |
| `--rollout-health-check-interval` · 两次探活间隔 | 启动 | 30 秒 | 大了发现得晚,小了更容易误杀 | 监视线程两次探活之间的等待 |
| `--rollout-health-check-timeout` · 一次探活等多久 | 启动 | 30 秒 | 大了少误杀,挂了发现更晚 | 探活失败那条错误日志 |
| `--rollout-health-check-first-wait` · 每次恢复后的宽限 | 启动 | 0 秒 | 大 MoE、编译重时加大,否则会在宽限里被暂停再等下一轮 | 恢复后的第一条宽限日志 |
| `--save-debug-rollout-data` · 生成落盘路径模板 | 启动 | 空 | 每步写一个文件,评测步文件名带评测前缀 | 该路径下的文件 |
| `--load-debug-rollout-data` · 回放生成落盘 | 启动 | 空 | 设了训练侧独自跑、推理服务整场不起 | 生成管理器不再调生成函数 |
| `--load-debug-rollout-data-subsample` · 回放时抽一段 | 启动 | 空 | 按比例从一头一尾各取一半,加快试训 | 抽完后的条数日志 |
| `--save-debug-train-data` · 训练侧落盘 | 启动 | 空 | 流水线最后一段、张量并行 0 号写一份含全部数据并行分片的文件 | 该路径;不能和生成落盘写成同一个字符串 |
| `--dump-details` · 一键填上两套落盘目录 | 启动 | 空 | 生成落到子目录,训练落到另一个子目录 | 两个子目录 |
| `--debug-rollout-only` · 只跑生成 | 启动 | 关 | 不起训练组,生成结果不转成训练数据;用来单独盯推理服务 | 循环里训练与推权重被跳过 |
| `--debug-train-only` · 只跑训练 | 启动 | 关 | 不起推理服务;常和回放一起用 | 服务字典是空的 |
| `--use-wandb` · 把训练指标打到看板 | 启动 | 关 | 开:奖励、损失、按步聚合的性能字段进看板;不上传推理服务的高频刮取 | 看板里的性能前缀 |
| `--use-tensorboard` · 同步打到 TensorBoard | 启动 | 关 | 与看板可同时开 | 日志目录 |
| `--sglang-enable-deterministic-inference` · 推理侧确定性 | 启动 | 关 | 需配合注意力后端与训练侧确定性,以及通信、随机算法环境变量 | 对照脚本的指标是否逐点重合 |

**怎么看。** 提交作业的进程:循环卡在等生成、等训练还是等推权重。生成管理器:监视器是暂停还是恢复、探活失败有没有杀引擎、落盘路径打没打出来。训练组:等待时长和训练本体时长是否拆开;性能字段里请求时延的均值、队列时间的中位数。落盘之后用时间线查看器打开生成文件,一行一条样本,预填充与解码分离时会多出两列虚拟轨道。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| 长作业、推理服务会偶发卡死 | 打开容错;大 MoE 把恢复后宽限加大 | 用偶发误杀换「挂了能杀掉再拉起」;训练 rank 挂了仍要靠检查点 |
| 训练侧数值不对、生成不要再随机 | 先落生成盘,再打开回放(会顺带只跑训练) | 用固定输入换可复现的训练对比;推理服务整场不起 |
| 只怀疑生成或只怀疑服务拓扑 | 打开只跑生成,需要时加上生成落盘 | 用「训练组完全不起」换排障卡时;两边不能同时开 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 同卡让出显存之后引擎被杀掉 | 探活是否在让出之前暂停 | 没暂停就是打到睡着的服务上,先确认容错开了且走的是管理器的暂停 |
| 大模型第一次生成就被探活杀掉 | 恢复后宽限是不是 0 | 加大宽限;宽限期间若再次暂停,下一轮恢复会重新等 |
| 回放了仍在起推理服务 | 用的是不是那条「故意不关服务」的回放 | 调试回放会关服务;另一条用来量长上下文显存,不关 |
| 一步很慢但训练卡很闲 | 提交作业进程卡在哪次调用,生成侧性能字段 | 闲着通常是在等生成或推权重,不是训练本体 |
| 看板没有请求时延 | 有没有打开看板、这一步有没有样本 | 性能字段按步聚合,没有样本就没有;高频刮取不进看板 |
| 两套落盘写成同一路径 | 启动校验 | 必须分开;一键目录会自动拆成两个子目录 |
| 容错开了训练进程还是没了 | 挂的是不是训练 rank | 开关只管生成引擎,不管训练组和提交作业的进程 |

## 六、常见误区

**以为打开容错,训练进程挂了也会被拉起来。** 人们会这么以为,是因为名字叫容错。实际上监视器只盯生成引擎,杀的是推理服务那一组。训练 rank、提交作业的进程、集群抢占,仍然走检查点和调度器。

**以为探活应该一直打。** 同卡让出显存时引擎不应答是正常的。监视器必须先暂停再让出;一上来也是停着的,第一次生成才恢复。按「服务活着就该一直探」去读日志,会把暂停当成故障。

**以为总时长拆不开。** 提交作业的进程、生成管理器、训练组三处日志各管一段。只在训练卡上找「这一步为什么慢」,找错角色。

**把两条回放当成同一件事。** 调试回放会关掉推理服务、只训训练侧;另一条回放故意把服务留着,用来量长上下文。看名字像,关服务这件事完全相反。

**以为官方说明页上的探活间隔就是代码默认。** 说明页写过更短的间隔和更长的首次等待;这组基准里间隔和超时都是 30 秒,首次宽限是 0。按说明页去调,会和启动默认对不上。
