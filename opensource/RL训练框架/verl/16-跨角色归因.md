# 跨角色归因:这一步慢在谁身上

一次 RL 训练变慢时,先找控制器在等哪一段,再进对应进程看计算与通信,才能把优化落到真正拖慢整步的地方。

说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**一步变慢,不等于 Actor 算得慢。** 长回答、工具调用、奖励服务、模型前向、参数交接都可能拖住控制器。只看 GPU 利用率,不知道它在为哪个角色工作;只看整步时间,又分不清是在计算还是等待。尤其在异步训练里,控制器取到的一批轨迹可能早已生成完毕,本次取样等待短,并不能说明生成便宜。

## 二、解法:先找阶段,再找进程

最自然的办法是每个角色放一个计时器,但角色不等于进程:Actor 和 Reference 可以共用一组 worker,生成却发生在独立的推理服务里。verl 因此把**阶段计时**和 **profiler**分开。前者告诉你控制器在一段调用上花了多久;后者记录进程内的操作时间线,回答这段时间里 CPU、GPU 和通信到底在做什么。

![控制器的阶段计时覆盖取样等待与模型调用,而训练 worker 和 Rollout 引擎各自记录进程内的 trace;共用 worker 的 Actor 与 Reference 属于同一条进程时间线,异步生成可以与训练重叠,不能把三行时长相加。](/opensource/verl/16a-attribution.svg)

沿这张图排查时,先选异常阶段,再打开对应进程的 trace。这里的 trace 指操作时间线,不是回答文本。另一套请求追踪记录 prompt、回答与工具调用;它能解释某条轨迹经历了什么,不能替代设备 profiler,而且必须先确认当前生成入口真正接通了它。

## 三、代价

**观察本身会改变负载。** 记录调用栈、张量形状和设备事件需要额外处理,trace 落盘也需要空间;把所有 rank、所有步都打开,可能先把排障作业变成存储压力测试。因此先用现成的阶段指标缩小范围,再采一个稳定阶段的进程窗口。

回放已保存的 Rollout 可以减少重复生成,让训练侧问题更容易复现,代价是输入已经不来自当前策略。它适合隔离生成对排障的影响,不能用来证明端到端训练吞吐或学习效果提高。

## 四、和 slime、ROLL 的侧重点不同

三者都把计时和更细的 profiler 分开,区别在于从哪一层进入。

| 框架 | 源码里的观测入口 | 排障时怎样读 |
|---|---|---|
| verl | 控制器汇总阶段时长,选定训练步后启动参与的 worker 与 Rollout 引擎 profiler | 先找等待阶段,再对齐不同进程的时间线;共置角色不能按文件数计数 |
| slime | 命名计时器累计耗时,训练 profiler 随训练推进采集窗口 | 计时器定位命名区间,再看训练侧记录;不能把区间时间直接当 kernel 时间 |
| ROLL | 状态搬运上下文包住加载、执行、卸载,并有局部 profiler | 对一次角色执行,可以继续分辨状态搬运和实际执行的代价 |

这些入口提供的是观察角度,没有同模型、同负载的测量,不能据此排性能名次。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

先读 `timing_s/`。`gen` 包住取样及前后钩子,同步模式还含 Rollout 睡眠;`old_log_prob`、`ref`、`values`、`adv`、`update_actor` 等按实际执行的阶段出现。`step` 包住训练、周期存档和步末交接,**周期评测在这个计时器之外**。所以它既不是所有日志项的和,也不是两次面板更新之间的完整墙钟时间。

`timing_per_token_ms/gen` 的分母是 response token;Reference、value、优势与更新的分母是 prompt 加 response token。基准没有为 `old_log_prob` 生成同名的每 token 指标。比较两次作业时先保持 token 口径一致,不要拿生成的每 token 时间和训练的每 token 时间直接做快慢排名。指标由 `Tracking` 按步发往总览所述日志后端;日志后端负责保存,不会把这些口径自动变成互斥阶段。

| 参数 | 在哪调、默认 | 调整后的影响 | 怎么看 |
|---|---|---|---|
| `global_profiler.tool` · `global_profiler.steps` | Hydra 启动覆盖;均为 `null` | 选 `torch` 等工具并指定步数后才有采集窗口;增加采集步会增加记录量 | 指定步的 profiler 启停日志和 trace 文件 |
| `actor_rollout_ref.actor.profiler.enable` | Hydra;`False` | 开启共置训练 worker 的记录,也涵盖其中的 Reference 工作 | 训练文件内部的 `actor_compute_log_prob`、`ref_compute_log_prob`、`actor_update` 区间 |
| `actor_rollout_ref.actor.profiler.all_ranks` · `ranks` | Hydra;`False` · `[]` | 已开启时,空列表回退 rank 0;扩大 rank 范围才能查跨 rank 长尾,文件量也增大 | 文件名中的 rank 与进程号 |
| `actor_rollout_ref.actor.profiler.tool_config.torch.contents` · `discrete` | Hydra;`[]` · `False` | 空列表或包含 `cuda` 时采 CUDA activity,CPU activity 始终开启;后者置真按阶段分文件 | 设备事件及阶段名;不分文件时在同一 trace 内找区间 |
| `global_profiler.profile_continuous_steps` | Hydra;`False` | 置真把相邻选中步连成窗口,便于观察步间空隙;需要非分段采集 | 窗口起止步与 trace 内边界 |
| `global_profiler.save_path` · `relocate_results` | Hydra;`outputs/profile` · `False` | 后者收拢支持迁移的输出,减少遗漏子目录;多机仍是各节点本地路径 | 训练 trace、Rollout 副本子目录;Nsight 默认还查 Ray 日志目录 |
| `skip.rollout_tq.enable` · `steps` · `action` · `dump_dir` | Hydra;`False` · `[]` · `cache` · `~/.verl/rollout_dump` | V1 按选中步保存/复用轨迹;`cache` 找同一步,`repeat` 找可用缓存;改变的是输入来源 | `RolloutTqSkip` 的保存、加载和注入日志 |
| `actor_rollout_ref.rollout.trace.backend` | Hydra;`null` | 请求追踪后端配置存在,但基准默认 V1 调用把逐样本 trace 置假,单改此项不能打开它 | 不应拿“没有请求 trace”判断设备 profiler 失效 |

Rollout 设备 profiler 默认继承 Actor 的启用与 rank 选择,推理引擎另写自己的 trace。Critic 独立运行时也要开启 `critic.profiler.enable`,默认同样为 `False`;不要因为训练文件里找不到 Critic 就认定采集丢失。

**典型配置**。下表是在一份已经能运行的训练命令后追加的覆盖项,不替代模型、数据和资源配置。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| CUDA 多卡共置训练,先看某个稳定步的 Actor/Reference | `global_profiler.tool=torch global_profiler.steps=[5] actor_rollout_ref.actor.profiler.enable=True actor_rollout_ref.actor.profiler.ranks=[0] actor_rollout_ref.actor.profiler.tool_config.torch.contents=[cuda]` | 限定一张卡、一个步的记录量;不能据此排除其他 rank 的长尾 |
| 同模型同数据,隔离生成后检查训练侧 | `skip.rollout_tq.enable=True skip.rollout_tq.steps=[1,2] skip.rollout_tq.action=cache skip.rollout_tq.dump_dir=/tmp/verl-debug-cache` | 首次缺缓存仍真实生成并保存,后续复用;保留相同数据顺序与配置,用真实策略取样换可重复输入 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| Actor trace 看起来在生成期间空闲 | 是否打开了训练 worker 的文件 | 找 Rollout 引擎自己的 trace,按时间戳对齐 |
| 开 profiler 后没有输出 | 工具、步数、角色启用是否同时满足,该 rank 是否被选中 | 查实际 worker 日志与所在节点的输出目录 |
| `gen` 变长但 decode 没变慢 | 取样等待、长回答、工具与奖励路径,以及同步模式的睡眠 | 沿 08–11 章定位等待来源,不要先改训练微批 |
| 总时长对不上阶段之和 | 是否把 `step` 又加了一遍,是否存在嵌套、异步重叠或评测 | 以计时上下文边界为准,需要时对齐进程 trace |
| 开缓存后仍在生成 | 是否选中了该步、缓存是否完整、是否用了 V1 的配置组 | 先跑出完整缓存,再确认出现注入日志 |

## 六、常见误区

**“配置里有请求 trace 后端,默认训练就一定支持。”** 旧 Agent Loop 确实按样本抽取并传入追踪开关,所以照文档配置很容易产生这个预期。但默认 V1 的 TransferQueue 适配入口把 `trace_this_sample` 固定为假;它继承了追踪初始化,不等于接通了采集。不要持续增加采样上限来修这个调用边界。

**“没有 Reference 文件,所以 Reference 没执行。”** 共置时它和 Actor 共用进程,profiler 也以共用 worker 为单位启动一次。先到同一文件中找阶段区间;单独打开 `ref.profiler.enable` 不能替代共置 worker 所读的 Actor 配置。文件名里的角色组合描述进程,不是单个函数。

**“回放后取样几乎不等了,就是生成优化成功。”** 缓存命中会把旧轨迹重新注入 TransferQueue,保留组内关系并重写当前步的标签,还可能循环补足缓存组。真实推理已被替代,这只能帮助检查下游。跳过管理器当前配置只有三种 Rollout 接线,不是任意关闭 Actor、Reward 或优势阶段的开关。

**“面板平均值正常,所有卡就都正常。”** 聚合会隐藏分布。verl 的普通指标列表按名字中的 max/min 或默认均值归约,显式 Metric 另按聚合类型处理;要定位慢 rank,应扩大 profiler 的 rank 选择并对照时间线,不能只盯一个归约后的数。
