# 训练引擎抽象与后端接入

这一页回答一件事:同一段训练循环如何通过统一接口调用不同训练后端,把并行实现差异留在适配层。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一次后训练里,Actor、可选 Critic 与 Reference 都需要模型计算能力:把一个微批喂进模型、算出 loss、反向、更一次、再把新权重交出去。Actor 全套都做,Critic 全套都做,Reference 只做前半截。

麻烦的不是这件粗活,是做它的那个框架。模型在 8B 上下的时候,分片数据并行够用,直接吃 HuggingFace 的模型实现,接一个新模型当天就能跑;涨到 200B 以上、再变成 MoE,就得换成张量并行加流水线并行加专家并行的那一套,模型定义要另写一份,权重要转一遍。换框架这件事在 RL 里躲不掉——同一个组这个月跑 8B,下个月跑 400B。

如果训练循环直接调框架的接口,换一次框架要动的地方远不止模型那一块:

- **一个微批切几份、谁跟谁是一组。** 分片数据并行下每张卡就是一个数据并行分身;流水线并行下,一个分身横跨好几张卡,而且只有最后那一级手上有输出。
- **谁把结果交回控制器。** 控制器要的是这一批样本的 logprob,可上面那个差别决定了哪些 rank 该说话、哪些该闭嘴;判错了不是崩,是收回来半批数据。
- **参数和优化器状态什么时候搬下卡。** 共卡时需要按配置安排这些状态的驻留与搬运,不同后端的实现并不相同。
- **权重按什么形状交给生成侧。** 切法不同,交出来的形状就不同。

所以坏掉的不是吞吐,是两样更难修的东西:**改动面积**——每接一个框架就多一套训练循环、多一套分发规则,各个角色各来一份;**结果对不对得上**——两套并行代码各写各的,同一份算法在两边跑出不同的 loss,而这种错不会崩,只会让曲线悄悄不一样。

## 二、解法

给训练框架定一个接口,谁都实现它。天然,问题只在这一刀切在哪。

**接口统一的是训练生命周期。** worker 负责角色、训练批次与 loss 的组织,VeRL 自己的 Engine adapter 把初始化、前向反向、优化器更新、装卸与存档接到具体后端上。建模型、包并行、组装优化器、剪梯度等对接代码仍在 VeRL 中,底层能力由 PyTorch、Megatron 等框架提供。换后端时主要改适配与配置,训练循环可以复用。

可以把它看成三层。**上层是训练循环与 worker**,决定哪个角色处理哪一批数据、用什么 loss。**中层是 VeRL 的 Engine adapter**,按基类契约实现计算、微批处理、参数导出和状态管理。**底层是训练框架**,提供模型实现、并行与优化能力。接口不只是一项微批计算,而是一整套可供 worker 调用的生命周期。

**关键的一招是:引擎除了会算,还要自报拓扑。** 建好模型之后,它按网格名在本地登记四件事:我这张卡在数据并行里排第几、这张网格上数据并行一共几份、通信组是哪个、我这个 rank 手上有没有输出。控制器不读配置,第一次用到这张网格时才来问一遍,拿到就缓存(这套问答机制是 02 章的主场,这里只说引擎这一侧要答什么)。**这就是为什么换后端不用动训练循环**:循环发出的是「把这批算一遍」,而摊开和收拢的规则是引擎按自己的并行方式报上来的——控制器按引擎报告的数据并行分组分发,再按出口标记收集,不必亲自解释 TP 与 PP 的内部布局。

取哪个类由一张注册表决定,钥匙分四段:模型类型、后端名、设备、硬件厂商。后两段在运行时探测,也各有一个环境变量可以覆盖;厂商没登记的退回该设备的默认实现。这把四段钥匙的用处很实在:同一个后端名在两种加速卡上可以落到两个不同的类——NPU 上的 Megatron-LM 是华为 MindSpeed 的实现,它在注册表里占的正是「Megatron-LM 在 NPU 上」这个位置,而不是第七个后端名。

模型类型现在只有两种:**语言模型**输出下一个 token 的 logits,**价值模型**把同一个躯干的输出接成一个标量。Critic 因此不是另一种 worker,是同一种 worker 换一个模型类型。

角色的组装靠嵌套。Actor、Rollout 副本、Reference 常常要挤在同一批卡上,所以有一个混合 worker 把它们装进一个进程:里面是两个训练 worker(一个带优化器的 Actor、一个只做前向的 Reference)、一个 Rollout 副本、一个权重传输引擎。Critic 也使用训练 worker,但默认会与 Actor 登记到同一资源池,合成为共置进程;监督微调那条路上用的也是它,只是不经过控制器。这一层是新写的,里面已经没有旧协议对象,数据一律是张量字典。

各后端的适配厚度不同。FSDP 路径直接使用 HuggingFace 模型,并补上序列并行和多模态所需处理;Megatron-LM 路径通过桥接完成模型与权重转换;MindSpeed 适配 NPU。TorchTitan、VeOmni、NeMo Automodel 更多复用各自框架的并行能力,但仍需要 VeRL 的生命周期与计算适配。VeOmni 还复用了 FSDP Engine 的部分实现。

参数怎么交给生成侧,这里只说接口那一句:引擎有两种交法,一种交拼好的整张量,一种交本地分片外加一份用设备网格和放置方式写成的分布声明,让拿的人自己算偏移。**两种都只是「按什么形状交出去」;权重怎么传、怎么只传变了的部分,是 05 章的事。**

## 三、代价

**接口是够用就好,不是完备。** 基类自己在注释里写着接口随时会变。更实际的问题是能力不齐:七个后端名里只有四个注册了价值模型,另外三个只能跑不需要 Critic 的算法;两个新后端明说不支持流水线并行,一个在构造配置时就拒绝,另一个收下字段、跑到前向那一步才报;还有一个只在监督微调那条路上接着,强化学习的配置组里根本没有它的位置。**「六个后端」是六个目录,不是六条都走得通的路。**

**每个后端都是一层壳,壳要跟着上游跑。** 抽象挡住的是 verl 这边的改动,挡不住上游的改动。分片数据并行那一路靠给 HuggingFace 打补丁支持序列并行和多模态,官方把「补丁容易被 transformers 的版本撞坏」写成这条路的固有痛点;TorchTitan 那一路要求 torch 与 TorchTitan 都用 nightly 构建,还得和推理引擎的二进制兼容对齐。抽象层越薄,这类牵连越直接。

**一致性靠测试维持,不靠类型。** 接口约束得了方法名和返回值,约束不了「两个后端算出来的 loss 应该相等」。官方给新后端定的验收办法,就是跑同一个监督微调脚本、比第一步的 loss 与梯度范数是否接近。这是一条真实的底线,但它是事后的。

**配置面积翻倍。** 真正共用的只有一小组:动态批、微批预算、去填充、数据类型、随机种子。并行度怎么写、offload 怎么开、重计算怎么配,每个后端一套自己的字段,互相不通用。换后端不用重写训练循环,要重写的是启动命令。

## 四、同一道题,三家答成了三个样子

拿智谱系的 slime 与阿里的 ROLL 作对照,按接入方式比较,不把目录数量当作能力数量(核对日期 2026-09-20)。

1. **接入面的选择不同。** verl 在统一注册接口下适配 FSDP、Megatron-LM 等训练框架,Rollout 接入 vLLM、SGLang 等服务。slime 的主线围绕 Megatron 与 SGLang 组织;ROLL 通过策略工厂选择 Megatron、DeepSpeed 等训练策略和生成策略。这里比较的是适配方式,不能由文件夹数量直接推导支持能力。
2. **差别在怎么隔离适配,不在谁完全不写模型代码。** verl 把建模、并行包装、优化器与存档的对接放入 Engine adapter;slime 将这些工作集中在 Megatron 后端中;ROLL 放在各自策略实现中。三家都要做对接,verl 的选择是让上层通过统一生命周期调用。
3. **外部扩展如何接进来。** verl 的注册机制与配置搜索路径允许接入仓库外的实现,FSDP-Turbo 就有对应接入示例。这个扩展口让实现与主仓分开演进,同时也把依赖版本和配置兼容性留给使用者。

## 五、调参与观测

**本页涉及的全是启动配置**,任何一项动了都要把整个作业重新拉起一遍。启动方式与配置组合规则见总览第六节。

**选后端是两个开关,不是一个。**

| 参数 · 一句话说明 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `model_engine` · 换整套配置组 | 启动 | `dp` | 换成 `megatron` / `veomni` / `torchtitan`,Actor、Reference、Critic 三处各挂上对应后端的子配置;留在 `dp` 就是 FSDP 家族那一套 | 打印出来的配置里 `actor` 下面挂的是 `fsdp_config` 还是 `megatron` |
| `actor_rollout_ref.actor.strategy` · 注册表钥匙的第二段 | 启动 | `fsdp` | FSDP 家族三档在同一个配置组里换:`fsdp2` 走 FSDP2,`fsdp_turbo` 走 Ascend 那一层(要先把它的路径加进 `PYTHONPATH`) | 起来的引擎类名 |
| `actor_rollout_ref.ref.strategy` · Reference 的后端 | 启动 | 插值跟随 Actor | 写死可以让 Reference 和 Actor 用不同后端 | 同上 |
| `critic.strategy` · Critic 的后端 | 启动 | `fsdp` | 只有 `fsdp` / `fsdp2` / `megatron` / `veomni` 注册了价值模型 | 起 Critic 时报不报「未知后端」 |
| `VERL_ENGINE_DEVICE` · 覆盖探测到的设备 | 环境变量 | 未设 | 设了就按它取类,不看真实设备 | 取不到类时的报错里回显这两段 |
| `VERL_ENGINE_VENDOR` · 覆盖探测到的厂商 | 环境变量 | 未设 | 同上;厂商没登记时退回该设备的默认实现,`cuda` 还会再退一次到 `nvidia` | 同上 |

**所有后端共用的那一组**(前缀 `actor_rollout_ref.`):

| 参数 · 一句话说明 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|
| `actor.use_dynamic_bsz` · 微批按 token 预算还是按条数攒 | `false` | 真:按每卡 token 预算攒微批,样本长短不齐时每步显存更平 | 每步微批数是否随批内长度变 |
| `actor.ppo_max_token_len_per_gpu` · 训练态每卡微批的 token 预算 | `16384` | 大了显存涨、微批数少、梯度累积轮次少 | `actor/perf/max_memory_allocated_gb` |
| `actor.ppo_micro_batch_size_per_gpu` · 非动态批时每卡一微批几条 | `null` | 动态批关着时必须设,两者都空会在构造配置时直接报错 | 启动即报 |
| `rollout.log_prob_max_token_len_per_gpu` · 前向态的 token 预算 | 跟随 `actor.ppo_max_token_len_per_gpu` | 前向不留激活,可以比训练态给得大 | 旧概率那一段的显存 |
| `rollout.log_prob_micro_batch_size_per_gpu` · 前向态每卡一微批几条 | `null` | 同上,动态批关着时必须设 | 启动即报 |
| `actor.ppo_mini_batch_size` · 一个训练批切成几段更新 | `256` | 决定一步里走几次优化器步;传给 worker 时还要乘以每题采样数 | `actor/grad_norm` 每步出现几次 |
| `actor.ppo_epochs` · 同一批样本重复走几遍 | `1` | 大于 1 时同一批数据多更新几轮,样本利用率高、离策更远 | 同上 |
| `model.use_remove_padding` · 去掉填充再打包 | `true` | 关掉会把填充位也算一遍;它同时决定引擎那一侧的同名开关 | 微批 token 数是否等于有效 token 数 |
| `model.use_fused_kernels` · 用融合的输出层算子 | `false` | 开:省掉词表大小的中间结果,详见 14 章 | `actor/perf/max_memory_allocated_gb` |
| `actor.<后端子节>.param_offload` · 不上场时把参数搬去 CPU | `false` | 真:省显存,换每步两次搬运;FSDP 前向态走自己的 CPU offload 策略 | 权重同步前后那几行显存日志 |
| `actor.<后端子节>.optimizer_offload` · 把优化器状态搬去 CPU | `false` | 同上,省的是优化器那一份 | 同上 |
| `actor.<后端子节>.seed` · 随机种子 | `42` | 各后端各有一份,别只改一处 | — |
| `actor.<后端子节>.full_determinism` · 逐位确定性 | `false` | 只在排查复现问题时开,会关掉一批非确定算子,详见 12 章 | 两次同配置的曲线是否逐位一致 |

**各后端自己的并行度。** 下面这些字段都挂在角色下面的后端子节里(Actor 是 `actor_rollout_ref.actor.<后端子节>`,Reference 与 Critic 各有同名的一份);FSDP 家族的子节叫 `fsdp_config`,其余三个和后端同名。

| 后端 | 主要字段 | 默认 | 备注 |
|---|---|---|---|
| FSDP / FSDP2 | `fsdp_size` · `ulysses_sequence_parallel_size` · `reshard_after_forward` · `offload_policy` · `model_dtype` | `-1` · `1` · `true` · `false` · `fp32` | 序列并行要求去填充打开;`offload_policy` 只对 FSDP2 有效 |
| FSDP-Turbo | `turbo_config.distributed` 下的分片组、专家并行、上下文并行三个大小 | `16` · `1` · `1` | 它自己的上下文并行和上面那个序列并行不能同时开,会直接报错 |
| Megatron-LM | `tensor_model_parallel_size` · `pipeline_model_parallel_size` · `virtual_pipeline_model_parallel_size` · `context_parallel_size` · `expert_model_parallel_size` · `sequence_parallel` · `use_distributed_optimizer` · `use_mbridge` | `1` · `1` · `null` · `1` · `1` · `true` · `true` · `true` | 重计算等透传字段走 `override_transformer_config`,默认只对注意力做选择性重计算 |
| VeOmni | `fsdp_size` · `ulysses_parallel_size` · `expert_parallel_size` · `moe_implementation` · `init_device` | `-1` · `1` · `1` · `fused` · `meta` | 引擎继承自 FSDP 那一个,字段名却是自己的一套 |
| TorchTitan | `data_parallel_shard_size` · `tensor_parallel_size` · `context_parallel_size` · `expert_parallel_size` · `attn_type` · `spmd_backend` · `activation_checkpoint` | `1` · `1` · `1` · `1` · `flex` · `spmd_types` · `selective` | 流水线并行字段收下但不支持,跑到前向那一步才报 |
| NeMo Automodel | `distributed_strategy` · `tp_size` · `ep_size` · `cp_size` | `fsdp2` · `1` · `1` · `1` | 只在监督微调的配置里出现;流水线并行在构造配置时就被拒 |

**观测点有三处。**

一是每步的 worker 级指标。更新那一段会上报 `actor/loss`、`actor/grad_norm`、`actor/lr`、`perf/mfu/actor`,外加三个内存读数 `actor/perf/max_memory_allocated_gb`、`actor/perf/max_memory_reserved_gb`、`actor/perf/cpu_memory_used_gb`;Critic 的同名指标把前缀换成 `critic/`。**MFU 是每卡值**:按这一批的 token 数与实测耗时估出总算力,再除以设备峰值和总卡数。**旧概率、参考概率、算价值这三段的同类指标在 worker 里算了但不上报**,控制器那一侧的对应行是注释掉的——看这三段的开销要去 16 章的剖析器。

二是启动日志。六个后端目录里只有分片数据并行那一个是无保护导入,其余五个都包在异常捕获里,缺依赖只打一行「某某 engine is not available」的警告,启动照样成功;真正的失败推迟到按名字取类的那一刻,报的是「未知后端」或一条写明设备与厂商的错误。

三是权重同步前后的显存日志。共卡路径上会依次打出一串显存读数,把它们排一下就知道这一刻显存被谁占着;这串读数的完整顺序与怎么读,是 06 章的主场,这里不重复。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡、8B 以内,先把链路跑通 | 全默认,只加 `actor_rollout_ref.actor.strategy=fsdp2` 与 `actor_rollout_ref.actor.use_dynamic_bsz=true` | 用最小的配置面换一次能跑完的验证;动态批省掉手算每卡微批 |
| 30B 级 MoE,卡刚好不够 | 上一套之上把 Actor 的参数与优化器 offload 都打开,Reference 的参数 offload 也打开 | 用每步两次搬运换显存;共卡时这笔搬运会和 Rollout 副本的睡醒叠在一起 |
| 200B 以上,必须上张量并行与流水线并行 | `model_engine=megatron`,按卡数分配张量、流水线、专家三个并行度,重计算走 `override_transformer_config` | 用一次性的模型接入成本与更长的启动时间换可扩展性;Critic 要跟着一起换后端 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动就报「未知后端」 | 启动日志里有没有那行「某某 engine is not available」 | 是依赖没装,不是名字写错;补依赖或换后端 |
| 改了后端名但行为没变 | 改的是不是后端子节里的那个同名字段 | 子节里的那个每次都被角色层的同名字段覆盖回去,要改外面那个 |
| 换成 Megatron-LM 后配置报缺字段 | `model_engine` 是不是还停在默认组 | 两个开关要一起换,只换钥匙不换配置组,后端会拿到别家的配置对象 |
| 起 Critic 时报「未知后端」,Actor 却正常 | 这个后端有没有注册价值模型 | 只有四个取值有;换后端,或换成不需要 Critic 的算法 |
| 构造配置就失败,说微批二选一 | 动态批开没开 | 动态批关着就必须给每卡微批;两个都空是随包默认 |
| Reference 的显存读数比 Actor 低很多,且不随 offload 开关变 | 它是不是 FSDP 前向态引擎 | 该路径强制采用参数 CPU offload,并把两个手动 offload 开关置假 |
| 梯度累积的通信比预期多 | 延迟同步那个开关的实际取值 | 随包配置把它关了,数据类里的默认值是开着的;以配置文件为准 |
| 一步慢,但不知道慢在哪个角色 | 先看阶段计时,再看 `perf/mfu/actor` | 本页的指标只覆盖更新那一段,跨角色归因见 16 章 |

## 六、常见误区

**以为换后端只要改一个开关。** FSDP 家族三档确实只改一个——它们共用同一套配置组,只是注册表里的钥匙不同。但换到 Megatron-LM、VeOmni、TorchTitan,还要同时换配置组,因为 Actor、Reference、Critic 三处挂的后端子配置是由配置组选的。只换钥匙不换组,后端会拿到另一家的配置对象,报出来的错和真正的原因隔着好几层。

**以为后端子节里的那个同名字段是选版本的地方。** 不是。角色层的那个字段在构造配置的最后一步会把自己的值写回子节,覆盖你在子节里写的任何东西。代码里的注释把原因写得很清楚:子节里的默认值是空的,不写回去就会一路退到 FSDP1。所以想用 FSDP2,要改的是角色层那个。

**以为六个后端都能跑完整的 PPO。** 注册表按「模型类型 + 后端名」两段开,七个后端名全都注册了语言模型,注册价值模型的只有四个。差别只在起 Critic 的那一刻暴露,而且报的是「未知后端」,不是「这个后端没有 Critic」——看着像名字拼错了。

**以为 MindSpeed 是第七个后端名。** 它没有自己的名字。它注册在 Megatron-LM 这个名字下,设备那一段填 NPU;在昇腾卡上写 Megatron-LM,拿到的就是它。反过来也成立:两个环境变量能改写探测到的设备与厂商,于是「我明明在这张卡上,为什么起的是另一个类」这个问题,答案可能在环境变量里而不在配置里。

**以为 Reference 的 offload 开关在各后端都一样。** FSDP 前向态的引擎在包并行的时候直接强制参数常驻 CPU,并把参数和优化器两个 offload 开关就地置假,连搬运函数都提前返回。所以在 Reference 上调这两个开关不会有任何效果,而且它的显存读数和 Actor 不是一回事,别拿来横向比。

**以为随包的默认配置能直接起来。** 起不来。动态批默认关着,而每卡微批默认是空的,两者必须二选一,否则在构造配置对象时就抛错——这是所有人踩的第一脚,不是配置写错了,是默认值故意留空。

**以为梯度累积默认会省掉中间那几次同步。** 数据类里那个开关的默认值是开的,随包的配置文件把它改成了关。也就是说默认每个微批都做一次梯度同步,不是一个 mini-batch 才做一次。查任何一个默认值都要以配置文件为准,不要以数据类的字段默认值为准——这两处不一致的地方不止这一个。

**以为后端导入失败会让作业启动不了。** 六个目录里只有分片数据并行那一个是无保护导入,其余五个都包在异常捕获里,缺依赖只是一行警告。作业会正常起来,一路走到按名字取类才失败。排查时先回头翻启动日志最前面那几行警告,比盯着报错点有用。
