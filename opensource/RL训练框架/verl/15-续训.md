# 续训

这一页回答一件事:作业中断后,怎样把模型、训练进度和已经取出的样本接回同一步。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

长时间 RL 训练遇到进程退出或机器故障,损失的不只是最后一段计算。只存权重,optimizer 的动量、学习率进度和随机状态就接不上;只恢复模型和步数,取数位置可能从头开始。异步训练还多一层:数据已经从 dataloader 取走,生成却还没完成,这些题目不在下一批数据里,也还没有进入当前权重。

所以 checkpoint 的目标是**保存同一步对应的训练状态与数据进度**,避免重启后悄悄漏题、重复取数或重置优化过程。本章讲作业重启;运行中的异步调度见 09 章,训练向 Rollout 热更新权重见 05 章。

## 二、解法

最自然的做法是让模型自己存档,但模型不知道题目读到哪里。verl 因此分两层:训练引擎保存 Actor 与可选 Critic 的状态;V1 控制器再保存 dataloader 游标、记录步数,异步模式额外保存 TransferQueue 中尚未消耗的数据。TransferQueue 是跨阶段保存样本及其状态的数据服务。

FSDP 按 rank 保存模型、optimizer 和附加状态,附加状态包含学习率调度器与随机状态。Megatron 把模型、optimizer 与随机状态分开组织;它的学习率调度器随 optimizer 保存,是否采用保存的调度器配置另有控制。两种后端都不是只导出一个可推理模型就结束。

![V1 续训把模型状态、数据游标和异步队列放在同一步目录下;恢复时完成的轨迹保留,未完成的 prompt 清理旧轨迹后重新生成,不恢复生成引擎的 KV cache。](/opensource/verl/15a-resume-boundary.svg)

图中最容易误读的是右下分支:**续训保住的是未完成的题目,不是生成到一半的执行现场。** 这让控制器能接回已经取出、尚未训练的工作,却不承诺重启后得到逐 token 相同的回答。

## 三、代价

完整状态比纯权重大,频繁保存会增加磁盘写入与训练停顿;另外导出 HuggingFace 权重还会增加一次完整权重收集与写盘。间隔拉长能降低这笔开销,却扩大故障后要重做的训练区间。异步模式还要保存队列数据,恢复未完成题目时会重新付出生成成本。

存档格式也限制恢复方式。FSDP 这条实现按当前 world size 和 rank 找文件,不能据此承诺换卡数直接续训。Megatron 的 optimizer 分片格式有不同的重新分片能力,但这不等于整个 RL 作业可以任意换并行布局。先在相同布局验证一次保存、重启、接着训练,再单独验证资源变更。

## 四、和同类框架的区别

| 框架 | 训练之外的状态放在哪里 | 对理解 verl 的帮助 |
|---|---|---|
| verl V1 | 控制器保存 dataloader;异步模式保存 TransferQueue,重启时区分完成与在途题目 | checkpoint 的边界延伸到了已取出、未训练的数据 |
| slime | 主循环分别保存训练模型与全局数据源;数据源保存取数偏移、epoch 和样本编号 | 同样把模型状态与取数状态分开维护,不能只搬模型目录 |
| ROLL | 已登记的训练集群保存各自状态,流水线另存运行状态和随机状态,再交存储管理器上传 | 模型保存、流水线保存与远端上传是不同的完成点 |

对比只看各自已核对的保存入口,不把数据源游标、流水线状态和在途生成恢复当成同一种能力。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

以下通过 Hydra 配置或命令行点分覆盖设置;保存目录应放在重启后仍可访问的存储上。Actor 的内容配置位于 `actor_rollout_ref.actor.checkpoint`,启用 Critic 时也要检查 `critic.checkpoint`。

| 参数与设置位置 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `trainer.save_freq` | `-1` | 设正数才保存;数值越小,保存耗时占比越高、故障重算区间越短 | `timing_s/save_checkpoint`;最后一步也受正数开关约束 |
| `trainer.default_local_dir` | `checkpoints/${trainer.project_name}/${trainer.experiment_name}` | 改变本地保存与自动恢复的根目录 | `Saving checkpoint to`、`Resuming from` 日志 |
| `trainer.resume_mode` | `auto` | `disable` 从头开始;`resume_path` 精确选择某一步 | `auto` 读取 `latest_checkpointed_iteration.txt`,找不到时从头训练 |
| `trainer.resume_from_path` | `null` | 配合 `resume_path` 指向 `global_step_N` 目录,不能只指向 Actor | 日志里的目录与恢复步数是否一致 |
| `actor_rollout_ref.actor.checkpoint.save_contents` / `load_contents` | `['model','optimizer','extra']` / 跟随保存项 | 少存减少体积,但失去相应恢复状态;`hf_model` 额外导出完整 HuggingFace 模型 | FSDP 的分片文件;Megatron 的 `ckpt_contents.json` |
| `actor_rollout_ref.actor.checkpoint.async_save` | `false` | Megatron 可提交异步写入,但当前 V1 未接通其 finalize 调用链,本章保持关闭 | 不以回调触发或 RPC 返回认定落盘完成 |
| `actor_rollout_ref.actor.optim.use_checkpoint_opt_param_scheduler` | `false`(Megatron) | 置真时加载保存的学习率调度器状态;适合沿用原学习率计划的续训 | `Loaded LR scheduler checkpoint` 日志 |
| `trainer.max_actor_ckpt_to_keep` / `max_critic_ckpt_to_keep` | 都为 `null` | 设正数限制对应角色存档数,降低磁盘占用;不代表清理整个步目录 | 管理器的删除日志及剩余目录 |
| `trainer.checkpoint_callback_class` | `null` | 可接上传或登记逻辑,增加存档后处理耗时;异常会中止训练 | driver 回调日志与异常栈 |

**先确认恢复了什么,再看训练有没有继续。** `Resuming from` 只证明选中了路径;接着检查模型、optimizer、随机状态的加载日志。若出现 `No dataloader state found`,程序会继续但从新的取数位置开始。异步模式再核对 `Loading TransferQueue state`、`Restored ... training prompt groups` 与 `Re-issued ... in-flight prompts`。这些日志对应不同状态,不能用步数非零代替完整检查。

FSDP 默认的 `huggingface/` 里主要是配置与 tokenizer,不代表已经有完整模型权重。Megatron 的 `ckpt_contents.json` 标明每种内容的相对路径,并在该角色写入完成后生成;它证明的是该角色的保存完成,不能单独替代 dataloader 和队列的核对。V1 的自动恢复只按 tracker 选目录,不会遍历并校验所有分片。远端备份应覆盖整个 `global_step_N` 目录以及恢复所需的 tracker;只设置 `trainer.default_hdfs_dir` 不足以保证 dataloader 与队列也被备份。

**典型配置**:在已有、已跑通的训练启动命令后追加这些覆盖项;模型、数据和 GPU 布局沿用原作业。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡、现有 FSDP 小模型作业,先验证中断续训 | `trainer.save_freq=1 trainer.max_actor_ckpt_to_keep=2 trainer.max_critic_ckpt_to_keep=2 trainer.resume_mode=auto` | 每步写盘换最短的恢复验证周期;重启后核对步数、游标与分片加载 |
| 多机 Megatron 作业,原模型与原布局继续训练 | `trainer.save_freq=20 trainer.resume_mode=auto actor_rollout_ref.actor.checkpoint.async_save=false actor_rollout_ref.actor.optim.use_checkpoint_opt_param_scheduler=true` | 降低保存频率换取更大的重算区间;若启用 Critic,同时设 `critic.optim.use_checkpoint_opt_param_scheduler=true` |
| 已有 V1 异步作业,指定一次完整存档恢复 | `trainer.resume_mode=resume_path trainer.resume_from_path=/mnt/verl/run/global_step_100` | 放弃自动选最新的便利,换取明确恢复点;该路径需替换为实际完整目录 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 训练结束却没有 checkpoint | `save_freq` 是否仍为负数 | 设为正数后再验证,末步不会绕过这个条件 |
| 明明有目录却从头训练 | tracker 是否存在且指向存在的目录 | 核实完整性后用明确路径恢复,不要只手写一个新步数 |
| 重启后题目又从头出现 | `data.pt` 是否随整个目录保留 | 补齐原存档,只有模型目录不构成相同进度续训 |
| 存档后上传的文件不全 | 回调是否收到 `async_save=True` | 当前 V1 保持同步保存,验证所有角色与数据文件后再上传 |
| 换卡数后找不到 FSDP 分片 | 文件名中的 world size / rank | 先按原布局恢复;模型格式转换另做验证,不能当原 optimizer 续训 |

## 六、常见误区

**看到“最新一步”就认为那一步完整可恢复。** tracker 像一个完成标记,但查找函数只读步数并检查目录存在,并不校验每个文件。复制存档时先复制了 tracker、漏了数据文件,仍可能选中这个目录。应把 tracker、角色状态与控制器状态作为一次备份整体核对。

**把异步训练与异步存盘当成同一个开关。** 两者名字相似,前者让生成与训练重叠,后者让文件写入离开同步调用。V1 异步训练仍可使用同步存盘;当前基准中 Megatron 的异步写入 finalize 调用只出现在旧训练器与分离实验路径,V1 没有接通,不要照搬异步存盘配置。

**恢复后回答不同,第一反应是随机状态没加载。** 随机状态确实要查,但在途 prompt 会先删除旧 trajectory 再重新生成,不是从原 KV cache 接着 decode。生成执行现场与外部工具状态不属于这里恢复的内容,不能要求整段 agent 交互逐项重放一致。

**只限制 Actor 的保留数,以为磁盘就有了总上限。** 配置名看上去像全局策略,实际管理器清理的是自己登记的角色目录;Critic、步目录中的数据和 TransferQueue 文件不因此一起被清理。排查磁盘增长要按目录看占用,不能只看 Actor 的 checkpoint 数量。
