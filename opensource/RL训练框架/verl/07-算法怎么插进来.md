# 算法怎么插进来

这一页回答一件事:十几种算法变体怎么做到不碰训练主循环就能换。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

RL 算法变体的产出速度远高于框架本身的迭代速度,而变体之间真正不同的地方其实很窄:一批回答怎么折算成每个 token 的优势,以及拿到优势之后损失怎么写。窄归窄,位置要命——这两件事分别嵌在一步训练的中段和末段,是整条流水线上最深的地方。

把它们直接写进训练循环,坏掉的不是吞吐,是另外两样。**改动面积**:加一个变体要在循环里插一段分支,循环越长,每次插改越容易碰到不该碰的东西。**正确性**:分支互相嵌套之后,新变体的判断会顺手改掉旧变体的行为,而 RL 的曲线本来就难以区分「算法不行」和「代码写错」——一条曲线跑坏了,你分不清该怪谁。

所以真正的要求是:算法要能一条一条地加,加的时候看不见训练循环;训练循环要能一直不动,哪怕下个月又来五个变体。

## 二、解法

两张表。一张收「一批回答怎么变成优势」,一张收「有了优势怎么算损失」。

每张表就是一个字典,配一个挂在函数上的装饰器:函数写在文件哪一行不重要,模块被导入时它自己把名字登记进去。训练循环手里只有一个从配置读来的名字,查表取函数、调用,完事。加一个变体等于写一个函数加一行装饰器,循环一行不动。

**为什么是两张而不是一张。** 因为这两件事根本不在同一个进程里。优势要在控制器上算,它得看到整批样本才做得了组内比较;损失要在 worker 里算,它得拿到这一次前向刚吐出来的 logprob。一张表跨不过这道边界,于是查表也分两次,一次在控制器,一次在 worker。

拆成两处不是更麻烦吗。反过来——**两张表各选各的,可选组合是乘出来的**。官方示例里那几个听上去像新算法的东西,填进去之后都是同一个优势估计配一个不同的损失,真正要两边一起换的变体反而是少数。

还有一件不显眼的事:**算法配置还会影响哪些角色需要启用**。默认按优势估计是否需要价值函数决定 Critic,也允许显式配置;奖励侧或损失侧只要启用 KL,就需要 Reference 概率。角色是否启用不等于是否新增独立进程,默认共卡关系见 06 章。角色判断被收进辅助模块,优势计算入口仍有按算法选择输入的分支。

![一个算法变体要填的口子落在一步训练的哪几处:上面一条泳道是控制器进程,里面有奖励侧 KL 与查优势估计表两个口子;下面一条泳道是 worker 进程,里面有查策略损失表、损失侧 KL、熵项系数、怎么聚合成标量四个口子;两张注册表各自贴着它所喂的那个口子;最下面一排是算法与相关配置决定的要求——是否启用 Critic 与 Reference,以及额外中间量、攒批方式这类两张表装不下、只能另开开关的要求。](/opensource/verl/07a-two-registries.svg)

还有第三类要填的东西,它进不了表:有些变体要求前面的阶段**多吐一个中间量**(比如更新策略时额外算一项逐 token 的统计量),或者要求**换一种攒批的方式**(同一道题得生成多条回答才做得了组内比较;有的还要把整组全对或整组全错的题扔掉重取)。这类要求落在别的阶段上,查表查不到,只能在配置里另开开关。

## 三、代价

三笔。

**第一笔:调用约定守不住。** 表里的函数签名并不统一,同一张表的不同条目要的输入不一样——有的要知道哪些样本属于同一道题,有的要一条基线,有的要上面那个额外统计量。控制器那边于是仍留着一小片按名字分叉的代码,专门决定这次该往函数里塞哪几样东西;更直白的是,两个最常用的估计器干脆被写成硬编码分支,压根没走查表那条路,只有其余的才落到表里。**表挡住了主循环,没挡住调用点。**

**第二笔:错要等到运行时才报。** 装饰器在导入时登记,配置里的名字到跑起来才查。名字拼错了,报错会把表里所有可用的名字列出来,这一条还算体面;难查的是名字对、函数也在表里,但当前这条路径上根本没人给它喂那份它要的输入——**默认的训练循环里就有这样一个估计器**,它依赖的准备逻辑只存在于已经标了弃用的旧循环里。表让「注册过」和「跑得通」变成了两件事。

**第三笔:参数语义压不住。** 表统一了控制流,统一不了参数含义。同一个裁剪参数,在标准损失里是比值偏离 1 的容许幅度,在另外两个损失里被当成散度的上下界,在还有一个损失里它虽然仍是比值的界、但下界被官方示例故意设成一个大数字,等于关掉。**读一个损失的参数就得读那个损失**,不能拿另一个的经验套。

## 四、换一个算法变体,三家各自要改什么

拿智谱系的 slime 与阿里的 ROLL 作对照,两家仓库本站都已克隆,下面的说法在它们树上核过(核对日期 2026-09-20)。同一件事,三家的落点差在四处。

1. **算法代码住在哪一层。** verl 的两张表都在训练循环那一层,与训练后端无关:六种训练引擎共用同一份优势估计与损失实现,worker 侧只是在引擎建好之后把损失函数挂上去。slime 的优势分支与损失分支写在 Megatron 后端目录下的那个损失文件里,和这个后端的上下文并行、词表切分代码长在一起。ROLL 的优势计算在一个后端无关的工具模块里,但策略损失直接写成各条流水线自己 worker 类的一个方法,四个 worker 类里躺着四份几乎一样的副本。
2. **扩展范式不一样。** verl 是「往表里加一条」:写个函数、加行装饰器,名字自动进表,查不到时报错还能把全部可用名字列出来。slime 是「给一个函数路径」:内置的那几个要改命令行候选值列表再往 if-elif 链上加一支(链尾抛未实现),但它同时在全仓库铺了 18 处同样的口子——优势、损失、采样过滤、奖励模型、权重更新后处理都能用命令行给一个 Python 函数的路径,运行时加载。这条路更自由,代价是没有任何一处能列出「当前可用的有哪些」,路径拼错、签名对不上都得等到跑起来。ROLL 两样都不走:改配置里那个字面量类型的取值列表,再在分支上加一支(它有注册表,用在 agent 工具上,没用在算法上)。
3. **优势和损失是不是两条轴。** 这是差得最远的一处。verl 两个名字分开填,所以 GSPO、CISPO、GMPO 在它这里都是同一个优势估计配一个不同的损失。slime 只有一条轴:那两个变体是优势估计开关的另外两个取值,选中之后它既改优势分支,也在损失函数内部换一条公式——一个开关同时管两头,「这个优势配那个损失」没有位置表达。ROLL 更靠里:只有一个裁剪损失写死在 worker 方法里,变化靠几个布尔开关加料(要不要双边裁剪、比值按 token 还是按整条序列算、要不要加 KL 项)。
4. **主循环里还剩几处算法判断。** verl 那几个训练器文件里,估计器名只出现 1 次,还是原样传下去的那一次——按名字分叉的判断被搬进了一个单独的小模块。ROLL 的 RLVR 流水线文件里,按估计器名判断的地方有 9 处,散落在建资源、取中间值、算指标几段;slime 的名字则漏进了生成侧与指标侧。这是「有没有表」最直接的体现。

这不是谁更先进。slime 一条轴,是因为它主打的算法面本来就窄,把两头绑在一起能省掉一整类「配错组合」的事故;ROLL 把损失写进流水线,换来的是每条流水线可以自己改而不牵连别人。verl 付的钱写在上一段:表越大,调用约定越守不住,能选的组合里也混着一些跑不通的。

## 五、调参与观测

**这一页的参数全是启动配置**,改了要重新拉起整个作业。参数分三处:优势那一侧挂在算法配置下,损失那一侧挂在 Actor 配置下,KL 与熵这两项两边各有一套、含义不同。

**优势那一侧(控制器进程读)**:

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `algorithm.adv_estimator` | `gae` | 换掉就换了整个优势估计;留默认值会连带起一组 Critic | `critic/advantages/mean` 的量级与分布 |
| `algorithm.gamma` · `algorithm.lam` | `1.0` · `1.0` | `lam` 只有 `gae` 用;`gamma` 除 `gae` 外还被 `reinforce_plus_plus` 自己从算法配置里取走,其余估计器两个都不读 | `critic/returns/mean` |
| `algorithm.norm_adv_by_std_in_grpo` | `true` | 置假则组内只减均值不除标准差;**只有 `grpo` 这条硬编码分支收得到** | `critic/advantages/max` 是否仍被压在小范围内 |
| `critic.enable` | `null` | 显式置真假就以它为准;留空才回落到「估计器是不是 `gae`」 | 启动日志里 `Disabled critic as algorithm.adv_estimator != gae` 那条警告 |
| `algorithm.use_kl_in_reward` | `false` | 置真则把 KL 罚进 token 级奖励,并强制起 Reference | `actor/reward_kl_penalty`、`actor/reward_kl_penalty_coeff` |
| `algorithm.kl_penalty` | `kl` | 换 KL 估计式;可选 `kl`/`k1`、`abs`、`mse`/`k2`、`low_var_kl`/`k3`,名字后加 `+` 走直通梯度 | `actor/reward_kl_penalty` 的方差 |
| `algorithm.kl_ctrl.type` | `fixed` | 换成 `adaptive` 后系数按当前 KL 与 `target_kl` 的比值逐步调 | `actor/reward_kl_penalty_coeff` 是否随步数漂移 |
| `algorithm.kl_ctrl.kl_coef` | `0.001` | 奖励侧 KL 的初始系数 | 同上 |
| `algorithm.kl_ctrl.target_kl` · `horizon` | `0.1` · `10000` | 只在自适应档生效 | 同上 |
| `algorithm.filter_groups.enable` | `false` | 置真则丢掉组内得分全同的题并重新取批,一步变长、有效样本变干净 | `.../filter_groups/evicted_samples` |
| `algorithm.filter_groups.metric` | `reward` | 按哪个字段判「全同」;填别的名字就去打分附带信息里取 | 取不到时第一批组攒齐即抛异常,信息里点出前几个题目号 |
| `algorithm.filter_groups.max_num_gen_batches` | `0` | **默认路径上它不生效**:置成正数会被内建缓冲忽略并打一条警告,让你改用在飞批次上限那个参数 | 启动日志里那条忽略警告 |
| `algorithm.use_pf_ppo` · `pf_ppo` | `false` · `{}` | 只在 `gae` 分支里按偏好重加权,别的估计器读不到 | `critic/advantages/mean` |
| `algorithm.gdpo_reward_keys` · `gdpo_reward_weights` | `null` · `null` | 只有 `gdpo` 用;不填或键对不上,第一次算优势时断言失败 | 断言信息直接点名这两个字段 |
| `actor_rollout_ref.rollout.n` | `1` | 组内比较类估计器必须大于 1,否则组内只有一条回答 | `critic/advantages/mean` 是否恒等于得分 |

**损失那一侧(worker 进程读)**:

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `actor_rollout_ref.actor.policy_loss.loss_mode` | `vanilla` | 换损失;当前表里有 `vanilla`、`gspo`、`cispo`、`geo_mean`、`sapo`、`gpg`、`dro`、`clip_cov`、`kl_cov`、`dppo_tv`、`dppo_kl`、`bypass_mode` | `actor/pg_loss`、`actor/pg_clipfrac` |
| `actor.clip_ratio` · `clip_ratio_low` · `clip_ratio_high` | `0.2` · `0.2` · `0.2` | 含义随损失而变(见第三节);放宽上界给正优势更大步子 | `actor/pg_clipfrac` 升高说明裁剪在起作用 |
| `actor.clip_ratio_c` | `3.0` | 负优势侧的兜底下界,必须大于 1 | `actor/pg_clipfrac_lower` |
| `actor.loss_agg_mode` | `token-mean` | 五个取值:`token-mean`、`token-sum`、`seq-mean-token-sum`、`seq-mean-token-mean`、`seq-mean-token-sum-norm`;换了等于换长回答的权重 | `actor/pg_loss` 随回答长度分布的漂移 |
| `actor.loss_scale_factor` | `null` | 只有 `seq-mean-token-sum-norm` 用;留空取回答上限长度,训练中会随之漂 | `actor/pg_loss` 的绝对量级 |
| `actor.entropy_coeff` | `0` | 非零才加熵项,并自动打开熵计算 | `actor/entropy_loss` |
| `actor.use_kl_loss` | `false` | 置真则把 KL 加进损失(不是加进奖励),并强制起 Reference | `kl_loss`、`kl_coef` |
| `actor.kl_loss_coef` · `kl_loss_type` | `0.001` · `low_var_kl` | 损失侧 KL 的系数与估计式,取值与奖励侧那一套同源 | `kl_loss` |
| `actor.policy_loss.clip_cov_ratio` · `clip_cov_lb` · `clip_cov_ub` | `0.0002` · `1.0` · `5.0` | 只有 `clip_cov` 读 | `actor/pg_clipfrac` |
| `actor.policy_loss.kl_cov_ratio` · `ppo_kl_coef` | `0.0002` · `0.1` | 只有 `kl_cov` 读 | `actor/ppo_kl` |
| `actor.policy_loss.dro_beta` | `null` | 只有 `dro` 读,留空或非正值直接抛错 | 第一次更新策略时就报 |
| `actor.tau_pos` · `actor.tau_neg` | `1.0` · `1.05` | 只有 `sapo` 读,**挂在 Actor 这一层而不是损失子树下** | `actor/pg_loss` |
| `actor.calculate_sum_pi_squared` | `false` | `optimal_token_baseline` 这一族要求置真,否则算优势时断言失败 | 断言信息直接点名这个字段 |
| `actor.ppo_epochs` · `ppo_mini_batch_size` | `1` · `256` | 一批样本反复更新几轮、每轮切多大;轮数大了比值越跑越远,裁剪比例随之上升 | `actor/pg_clipfrac`、`actor/ppo_kl` |

训推概率对不上那一套修正也接在损失这个口子上:它算出的逐 token 权重作为一个可选入参传给表里任一个损失,乘在逐 token 的损失上;`bypass_mode` 则是专门为它准备的一个表项。那条线怎么选、阈值怎么定,见 12 章。蒸馏是同一张损失表的另一个用法:把蒸馏损失取负当成优势喂进去,复用同一批损失实现。

**观测点分三处。** 优势侧看 `critic/` 前缀那几组:`score/`、`rewards/`、`advantages/`、`returns/` 各有均值、最大、最小;起了 Critic 还多 `critic/vf_loss`、`critic/vf_clipfrac`、`critic/vf_explained_var`。损失侧看 `actor/` 前缀:`pg_loss`、`pg_clipfrac`、`pg_clipfrac_lower`、`ppo_kl`,开了熵与 KL 再加 `actor/entropy_loss`、`kl_loss`、`kl_coef`。**第三处是启动日志**,两条最值钱:一条是上面那句关掉 Critic 的警告,另一条是两侧 KL 同时打开时的提示。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 可验证奖励的数学 / 代码任务,组内比较起步 | `algorithm.adv_estimator=grpo`、`algorithm.use_kl_in_reward=false`、`actor.use_kl_loss=true` 配 `kl_loss_coef=0.001`、`rollout.n=8`、损失留默认 | 不启用 Critic 可省去它的显存与计算,但组内比较要靠多条回答换,生成侧开销涨 |
| 同上,但长回答训着训着塌 | 在上一套基础上把 `actor.policy_loss.loss_mode` 换成 `gspo`,`actor.loss_agg_mode=seq-mean-token-mean`,`clip_ratio_c=10.0` | 先对每条序列的有效 token 平均,再在序列间平均,降低长度直接决定样本权重的影响;稳定性仍需实验验证 |
| 偏好式奖励模型、要价值函数 | `algorithm.adv_estimator=gae` 保持默认、`critic.enable=true`、`algorithm.use_kl_in_reward=true` 配 `kl_ctrl.type=adaptive`,损失留默认 | 多养一组 Critic 换更低方差的优势,一步时长与显存都涨 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动即报「不支持的损失模式」或「未知的优势估计」 | 报错信息里列出的可用名字 | 名字只在导入时登记,拼错到运行时才发现;照列表改 |
| 没配 Critic 却起了一组 Critic worker | 启动日志里有没有那条关闭警告 | 估计器默认是 `gae`,不改就要 Critic;要么改估计器,要么显式关 |
| 优势全等于原始得分、训练毫无进展 | 每题生成几条回答 | 组内只有一条时均值取 0、标准差取 1,组内比较退化成没有基线的策略梯度 |
| 改了组内标准差归一那个开关却没反应 | 估计器名是不是向量化那一支 | 这个开关只传给硬编码的那条分支,表里其余条目收不到,取函数自带的默认值 |
| KL 罚得过重、回答迅速变短 | 两个 KL 开关是不是都开着 | 启动日志里有提示但不拦,两处会各罚一次;留一处 |
| `actor/pg_clipfrac` 接近零、像没裁剪 | 这个损失怎么解释那两个裁剪参数 | 有的损失把下界当成 1 减去它,示例里故意填一个大数等于关掉下界 |
| 选的估计器报「缺某个字段」 | 这个字段由哪一步产出 | 它要的准备逻辑可能只存在于旧训练循环里,当前默认路径不产出 |

## 六、常见误区

**以为注册表里列得出的名字都能跑。** 登记是导入时的事,喂数据是训练循环的事,两件事没有人对账。基准上就有一个估计器需要每道题额外跑一遍贪心生成拿基线,而产出这条基线的代码只在已标弃用的旧训练循环和分离式训练器里,默认路径上选它必然缺字段。**把注册表当成支持列表看,是这一章最贵的误会。**

**以为组内标准差归一那个开关对所有组内比较类估计器都生效。** 它只在硬编码的那条分支上被显式传进去;走查表那条路的条目——包括同一族的向量化实现——拿到的是函数签名里的默认值。两边参数名一样、默认值也一样,所以置假之后两条路的行为不同,而日志上看不出差别。

**以为把 KL 写进奖励和写进损失是二选一。** 它们是两个互不排斥的开关,分属两个配置子树,同时打开就罚两次。启动时确实会打一行提示,但它是一条普通的提示、不带警告级别,混在一整屏启动日志里最容易被划过去。反过来也要记:**两个都关是默认状态**,这时候不启用 Reference 计算,也不会产出参考概率。

**以为裁剪参数在哪个损失里都是一个意思。** 标准损失里它是比值偏离 1 的容许幅度;两个散度型损失把它当成散度的上下界;还有一个损失虽然仍按比值裁,但它对被裁的比值切断了梯度,于是官方示例把下界填成一个远大于 1 的数,让下界彻底失效。照标准损失的经验去读这个数,会得出完全相反的结论。

**以为你设的损失聚合方式一定生效。** 表里的函数拿到这个参数之后可以不用:有一个损失在实现里把聚合方式写死成按序列平均再按 token 平均,忽略传进来的值。同理,官方示例里给那个损失加温度参数时用的是损失子树下的路径,而实现读的是 Actor 这一层——**示例里写着、实际没生效**,这种错不报任何东西,只是那两个数永远是默认值。

**以为多轮会话天然对应多条独立训练记录。** 普通 ToolAgentLoop 会把多轮交互合成一个 AgentLoopOutput,并不是每轮单独一条。只有自定义循环为同一会话返回多个输出时,这里的特殊处理才显出区别:GRPO 取会话最后一个输出计算优势,再广播给同会话的其余输出;其他估计器直接交给原有优势计算函数。换估计器时应先看循环的输出结构,不能只看任务是否多轮。

**以为配置注释里列出的取值都实现了。** KL 估计式那一项的注释里列着一个「完整」档,函数走到它直接抛未实现;而注释里没写的那个在名字后加加号的直通梯度写法,倒是真能用。**注释和实现是两拨人维护的**,查一个取值到底能不能填,以报错为准比以注释为准可靠。
