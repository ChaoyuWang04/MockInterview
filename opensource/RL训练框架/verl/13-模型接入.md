# 模型接入:两条路

这一页回答一件事:一份 Hugging Face 模型怎样成为 verl 能训练的模型,以及为什么加载成功还不算接入完成。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

换一个模型,最容易得到的好消息是 checkpoint 加载成功。真正的麻烦可能在后面:训练拿到的 token 布局与模型 forward 不匹配,图像位置处理错了,或者训练完成后 Rollout 接不住新权重。此时模型能生成文字,但一次在线更新还没有成立。

**接入要对齐的是模型行为,不只是模型名字。** Hugging Face 提供配置、tokenizer、processor 和权重;训练引擎还需要可训练的实现,并要求它接受本引擎准备的输入、返回本引擎消费的结果。额外打开去 padding、sequence parallel 或 fused kernel,这些边界也会跟着变。

本章的两条路指常用的 Transformers 与 Megatron 模型接入方式,不是把 verl 的所有训练后端限制为二选一。03 章负责后端接口,这里负责接口下面的模型从哪里来。

## 二、解法

**能保留原实现的,直接加载;需要另一套计算实现的,通过 Bridge 转换。** Bridge 是把 Hugging Face 模型资料接到 Megatron 模型构造与权重布局的适配层。两条路共享模型资料的入口,但模型对象不是同一个。

FSDP 与 FSDP2 直接加载 Transformers 的模型类。安装的 Transformers 已认识该模型时,通常无需把整份建模代码复制进 verl;外部实现可以通过模型仓库的自定义代码或预先导入的扩展包接入。verl 只在需要时补自己的行为:处理多模态输入、适配去 padding 与 Ulysses,或者替换输出计算以直接得到 logprob 和 entropy。

Megatron 路径则由 Bridge 读取 Hugging Face 模型资料,生成模型构造器,verl 再补上并行和执行要求、构造分布式模型并加载权重。**当前默认采用 NVIDIA Megatron-Bridge**,另保留旧 mbridge 的兼容分支。仓库内按模型登记的配置转换器与初始化器已标为弃用;默认训练引擎要求使用 Bridge,因此不能把旧表当成当前接新模型的第一站。

![Hugging Face 模型资料分别进入直接加载 Transformers 和经 Bridge 构造 Megatron 两条训练路径,随后各自满足 verl 的 forward 契约;Rollout 对架构和权重的支持仍是独立边界。](/opensource/verl/13a-model-entry.svg)

最天然的疑问是:直接加载已经够用,为什么还留转换路线。因为模型资料的通用性与训练实现的选择是两件事。保留原模型可以复用 Transformers 生态;经 Bridge 则可以使用 Megatron 的模型实现与并行能力,同时继续从 Hugging Face 格式起步。模型支持范围也随这两个实现及其依赖版本分别确定。

## 三、代价

**直接加载的代价是补丁兼容。** 模型可以被 Transformers 构造,不表示它的所有优化组合都符合 verl 的预期。补丁会依据模型类型及 Transformers 版本分支,有的还会替换类的 forward;升级模型库后,要重新检查真正执行的是哪段行为。

**转换的代价是语义映射。** 配置中的 attention 结构、位置编码与共享 embedding,必须和构造出来的 Megatron 模型一致;权重形状能装进去只是其中一项。新架构需要 Bridge 自身能表达它,再由 verl 的 forward 适配正确传递输入。不能靠在名称列表追加一行替代这些工作。

**两条路都要支付端到端验证成本。** 官方 FSDP 扩展指南要求先验证模型与补丁,再跑在线更新、比较同步后的 token logprob,并验证存档重载。权重传输机制见 05 章,训推差异的定位见 12 章;本章只确定这些边界必须一起通过。

## 四、和同类常见做法不一样的地方

slime 的 Megatron 模型入口可以直接使用自定义模型构造函数;默认构造路径从训练参数建立配置与 layer spec,再创建 Megatron 模型。相比之下,verl 当前默认的 Megatron 接入把 Hugging Face 到模型构造器的转换交给 Bridge,自己补训练所需的行为。

ROLL 也保留模型资料与训练实现之间的分支:Actor provider 按训练参数类型进入 Megatron Core Adapter 的自动模型加载,或进入 Hugging Face 模型加载。**因此,两条模型接入路线并非 verl 独有。** verl 这一章值得记住的是直接加载与窄补丁的分工,以及默认 Megatron 入口对 Bridge 的依赖,不是用目录或注册项数量比较谁支持的模型更多。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

下面的模型项位于 `actor_rollout_ref.model`。命令行可以用完整点分路径覆盖;Megatron 项位于 `actor_rollout_ref.actor.megatron`,适用于已选择该训练后端的作业。更换后端需要连同对应配置组一起选择,不能只改模型路径。

| 参数与位置 | 默认 | 调整影响 | 怎么看 |
|---|---|---|---|
| `actor_rollout_ref.actor.strategy` | 普通 Actor 配置为 `fsdp` | 选择训练实现,影响可用模型与并行方式 | 训练引擎初始化日志;完整后端选择见 03 章 |
| `actor_rollout_ref.actor.fsdp_config.ulysses_sequence_parallel_size` | `1` | 大于 1 启用 Ulysses,同时增加输入布局约束 | 初始化断言与 attention 补丁日志 |
| 模型组 `path` | `~/models/deepseek-llm-7b-chat` | 更换训练模型与权重来源;不是速度旋钮 | 加载日志、实际模型类及参数规模 |
| 模型组 `hf_config_path`、`tokenizer_path` | `null`,各自回退到 `path` | 允许配置或 tokenizer 独立存放;不匹配会改变输入语义或阻止构造 | 检查最终配置、tokenizer 与 processor,包括特殊 token |
| 模型组 `external_lib` | `null` | 在配置加载前导入外部模块,让自定义实现有机会登记 | 导入异常和随后解析出的模型类 |
| 模型组 `trust_remote_code` | `false` | 允许使用模型仓库自定义实现;仅用于已审阅且打算执行的代码 | 配置与模型加载异常是否指向自定义代码 |
| 模型组 `override_config` | `{}` | 覆盖 HF 配置;其中 attention 实现未指定时选 `flash_attention_2` | 最终 HF 配置与模型实际 attention 类型 |
| 模型组 `use_remove_padding` | `true` | FSDP 路径减少 padding 计算,也要求相应 forward 兼容 | attention 补丁日志与输入布局;Ulysses 大于 1 时不能关闭 |
| 模型组 `use_fused_kernels`、`fused_kernel_options.impl_backend` | `false`、`torch` | FSDP 开启后可直接计算 logprob 与 entropy,降低输出计算的中间存储需求;须核模型兼容 | `Using … backend for fused kernels` 或 `Skipping monkey patch` |
| Megatron 组 `use_mbridge`、`vanilla_mbridge` | `true`、`false` | 前者在当前 Engine 中必须为真;后者为假选 NVIDIA Megatron-Bridge,为真选兼容 mbridge | Bridge 的依赖异常、模型构造日志 |
| Megatron 组 `override_transformer_config` | 含 `attention_backend: flash` 与重计算子项,并非空表 | 覆盖 Bridge 模型构造器的配置;错误项可能在构造阶段失败 | 构造器校验、模型结构及随后 forward |

**观测要跨过加载阶段。** FSDP 的 `After init model from HF AutoModel` 表示初始化走到了相应位置,不证明 Rollout 重载成立;Megatron 的 `module:` 打印模型 chunk 数,也不是通过了完整接入的通知。先看异常来自配置解析、模型构造、补丁还是 forward,然后再查权重重载。

**典型配置**。以下只列模型接入覆盖项,追加到已跑通的数据、算法和 Rollout 启动配置上;模型路径替换为本地已备好的模型。GPU 数量与并行布局继续使用原作业配置。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 CUDA、小型文本模型,先验证 FSDP2 基础行为 | `actor_rollout_ref.actor.strategy=fsdp2`、`actor_rollout_ref.model.path=/models/Qwen2.5-0.5B-Instruct`、`actor_rollout_ref.model.use_remove_padding=false`、`actor_rollout_ref.model.use_fused_kernels=false`;Ulysses 保持 1 | 保留 padding 计算,减少首次定位时同时变化的优化行为 |
| 已跑通 FSDP2 的同一模型,验证去 padding | 保持相同模型与输入,改 `actor_rollout_ref.model.use_remove_padding=true`,继续保留 `actor_rollout_ref.model.use_fused_kernels=false` | 减少 padding 计算,增加 packed 输入兼容性的检查 |
| 已有 Megatron 配置、模型已由所装 Bridge 与 Rollout 支持 | 覆盖 `actor_rollout_ref.model.path` 为目标模型,保持 `actor_rollout_ref.actor.megatron.use_mbridge=true`、`actor_rollout_ref.actor.megatron.vanilla_mbridge=false` | 复用 HF 模型资料,承担 Bridge、Megatron 与模型版本匹配成本 |

组合与推荐值是按语义推的起点,不是实测最优。

新增模型按官方指南至少验证 2 次在线 optimizer step,第二次权重交接检查 Rollout 初始化处理完成后的再次加载;随后比较同步后的 token logprob 并存档重载。这是验证要求,不是本页已跑过这些模型的声明。

| 症状 | 先查 | 然后 |
|---|---|---|
| HF 配置能读,模型类解析失败 | Transformers 版本、自定义实现是否已导入 | 核 `external_lib` 与 `trust_remote_code`,再查 AutoModel 对该架构的选择 |
| 模型加载成功,去 padding 后 forward 失败 | 该模型命中的补丁与 attention 实现 | 用相同输入对照普通布局;Ulysses 大于 1 时先恢复到 1 再做此对照 |
| 关闭 fused 后仍看到补丁日志 | 日志说的是输出融合还是 attention/多模态处理 | 分别核对应开关,不要把所有补丁当成一项 |
| Megatron 报 Bridge 包缺失 | 当前选择的是哪一种 Bridge | 安装作业所需的匹配依赖,不要把 `use_mbridge` 置假绕过 |
| 开始能生成,更新后重载失败 | 训练导出的参数布局与 Rollout 加载器 | 按 05 章检查权重边界;补训练模型注册名不能修复加载器 |

## 六、常见误区

**在注册表找到类名就宣布支持。** 文件名很像权威清单,所以容易直接数名字。实际上当前 Megatron Engine 的模型构造交给 Bridge,旧表还把配置转换、初始化、forward 和权重转换分开登记;某处有名字不代表其余环节都齐。先沿实际调用入口查,再看所选功能。

**看到跳过 monkey patch 就认为全部使用原版 forward。** 那条日志来自 fused 输出分支,此前模型专用处理或 attention 补丁可能已经生效。关闭 fused 只适合隔离该项优化,不能据此声称整个模型未被修改。

**把独立配置路径当成所有加载分支的统一输入。** 看到可单独指定 `hf_config_path`,容易以为它自动决定 Bridge 的全部架构信息。当前 NVIDIA Bridge 是从模型 `local_path` 调用 `from_hf_pretrained`,而兼容 mbridge 使用已加载的 `hf_config`。使用独立配置或覆盖项时,应检查实际构造器读到的内容,不要只检查公共配置对象。

**新模型不认识就复制一份完整 Transformers 建模文件。** 这样能很快找到一个可改的地方,却把上游实现维护也接了过来。当前文档明确要求优先复用上游或外部实现,只有 verl 特有的行为才放窄补丁;改过的行为需要与上游实现做 forward 或 forward/backward 对照。
