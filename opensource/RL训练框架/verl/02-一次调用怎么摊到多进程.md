# 一次调用怎么摊到多进程

这一页回答一件事:控制器上那行看起来平平无奇的方法调用,底下是怎么变成一组 worker 的协同计算的,以及这批数据在这个过程里走的是哪条路。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准;每一条对应源码的哪个文件与符号,见代码索引页。

## 一、核心问题

控制器是一个进程。一步训练里每个阶段的输入都要从它手里发出去,输出都要收回它手里:1024 条样本各自的 token 编号、掩码、3 份 logprob、优势与回报,发出去一趟、收回来一趟,每个阶段各来一遍。

**模型并行让这件事更糟。** 一个张量并行组里,每个 rank 都会算出同一份输出。原样收回来,张量并行开到 8 就是同一份东西的 8 个副本挤进控制器,拼一次、再切开、再发下去。进程数翻倍,收回来的份数跟着翻倍,而控制器永远只有一个。

坏掉的指标因此很具体:**控制器进程的常驻内存**,以及**每个阶段前后那两趟全量搬运的墙钟时间**。批越大、序列越长、并行度越高,这两样涨得越快;先出事的通常是内存——控制器明明一张卡都没占,却被节点的内存上限杀掉。

还有一个更隐蔽的麻烦。每摊开一次,总得有人决定:这批切成几份、哪一份给谁、收回来的哪些留哪些丢。这套规则要是写在每个调用点上,换一次并行策略就得把控制流从头改一遍——而换并行策略恰恰是这类框架最常做的事。

## 二、解法

分成两件事看:一次调用怎么摊开,以及摊开之后数据走哪条路。

**摊法写在被调方法上,不写在调用点。** worker 类里每个想让控制器直接调的方法,头上挂一个声明,说清三件事:参数怎么切给各个进程、返回值怎么拼回来、控制器要不要等。worker 组建起来的那一刻,把这些带声明的方法逐个扫出来,在自己身上合成一个同名方法。控制器那边写出来就是一行普通调用,底下是切、发、等、拼四步。

声明能选的摊法是有限的几种,分两类。一类是原样复制给每个进程,用在初始化、存档、换权重这种每个进程都得亲自干一遍的活上;默认路径上绝大多数带声明的方法都是这一类。另一类是按数据并行的份数把批切开,用在纯计算上——而真正扛主力的,是这一类里的**延迟问路**。

**延迟问路是这一层最值钱的设计。** 控制器不从配置里推算这组 worker 的数据并行是几份。第一次在某张网格上调方法时,它先向每个进程各问一句:你算第几份数据、你要不要交回结果。答案缓存下来,以后按这张表切、按这张表收。张量并行组里只有被标成出口的那个 rank 交回真东西,其余交回一个空壳——同一份输出因此只被搬一次,而不是 8 次。换训练后端、改并行策略,控制器一行不用动,因为那些事它压根没问过配置。

**数据不跟着调用走。** 旧的载体是一个协议对象:一份张量字典、一份非张量数组、一份元信息捆在一起,自带切分、拼接、补齐、改名、取列。它还在,但新的 worker 层已经不收发它了,换成了干净的张量字典。

再往前一步是元数据引用。一批样本注册进 TransferQueue 之后,控制器手里只剩一串键和每条样本的标签。分发声明里埋了一层桥:调用发到 worker 那边,桥先看入参里有没有元数据对象,有就按键把真数据取下来,算完把新增的那几列写回去,返回一份更新后的元数据。在这次远端模型计算的分发与回收中,控制器主要传递引用;本地计算仍按需取回张量。

**但它故意没有走到极端。** 控制器仍然按列名把需要的几列拉回自己手里:算优势拉 7 列,把生成结果落盘时拉 5 列、包括题目和回答的 token 编号再在本地还原成文字;长度均衡更省,排序分区只看每条样本随身带的长度标签,连着做的补齐也只拉一条样本当模板。省掉的是「整批全列来回两趟」,不是「控制器再也看不见数据」——后者会把 RL 最需要的那点可观测性一起省掉,奖励塌没塌、优势是不是全零,就又得靠往 worker 里塞打印语句来看了。

**还有一档是不等。** 声明里可以说这次调用不阻塞:控制器拿回来的是一个待兑现的句柄,里面没有数据。句柄可以直接当成下一次调用的入参传下去,由目标 worker 在自己进程里兑现,数据于是从产出它的进程直连到消费它的进程。默认路径上拿到这种句柄的是Critic 的两次调用,算价值那一次拿到就等、等完连结果都不看——真正的输出早就由 worker 自己写进数据服务了。

## 三、代价

**第一笔:调用签名变成了协议。** 方法要能被摊开,参数就必须是可切的批数据或者可复制的小对象,返回值要么能拼、要么每个进程各给一份。想临时加一个只有某些 rank 才有的返回值,就得动摊法本身,而摊法是全局注册表里的东西,动它影响的是所有 worker 组。

**第二笔:「我调了一个函数」这个错觉会反噬。** 控制器上那一行底下是进程总数那么多次远端调用加一次等待:任何一个 worker 卡住,整行卡住;错误从远端抛回来,栈是断的,报错里看不见你自己的代码。调试时最花时间的不是修,是定位到底是哪个进程出的事。

**第三笔:批大小必须能被数据并行份数整除。** 协议对象上有一套自动补齐,但默认关着,而且默认路径的分发根本不走那条。改由训练器在长度均衡那一步先把批凑到整除,补进去的是合成样本:对齐长度、奖励清零、打上标记,下游算指标时再按标记滤掉。这条链路上任何一环漏了滤,指标就被这些假样本稀释。

**第四笔:多了一组必须活着的进程。** 样本不在控制器内存里了,它们在另一组进程的内存里。这组进程的容量、分片数、它和存档怎么对齐、它挂了怎么办,全都成了新的运维面;而且它是一个外部依赖包,不在本仓库里,出了事只能去它自己的仓库查。

**第五笔:三种载体在同一次训练里并存。** 老协议对象、张量字典、元数据引用,转换点散在桥、收集函数和训练器里。读代码时第一件事永远是先认清手上拿的是哪一种,认错了后面整段都读歪。

## 四、和 slime、ROLL 不一样的三处

拿智谱系的 slime 与阿里的 ROLL 作对照,两家的仓库本站都已克隆,下面每条都在它们树上核过(核对日期 2026-09-20)。

1. **有没有这一层。** slime 没有:它直接写 Ray 的远端调用,分发规则跟着长在调用点上,用到远端调用的有 9 个文件。ROLL 有,而且是**同一套设计**——它的工作者方法头上挂的也是分发模式声明,枚举里也有一对多、全体对全体这些名字。所以这一层不是 verl 独有的发明,是这条技术路线上的共识;真正的分歧在下面两条。
2. **摊法是问出来的,还是算出来的。** ROLL 的分发模式是一个固定枚举,六个值,名字里直接写着数据并行与模型并行——切几份从配置推。verl 是可注册的动态枚举,而且默认路径上的计算方法一律走延迟问路:第一次用到某张网格时向每个进程各问一句,答案缓存复用。**这一步是 verl 独走的**,代价是静态读代码看不出某次调用会切成几份。
3. **数据面反而是趋同的。** 同一个外部数据服务在 verl、slime、ROLL 三家都出现了(slime 3 个文件、ROLL 2 个文件引用它)。所以「控制器只拿元数据」也不是这里的发明。verl 的不同在于它把这一层和分发协议缝在了一起——桥埋在分发声明里,取数与写回随调用自动发生,而不是让调用方自己去取。好处是上层无感,坏处是出了问题要同时看分发与数据服务两侧。

## 五、调参与观测

**这一页的参数分两类:一类在启动配置里按点分路径覆盖,改了要重新拉起整个作业;另一类是环境变量,要在拉起作业之前设好,因为它们随运行时环境下发到各个 worker。** 运行时没有任何接口能改这一层的行为。

| 参数 | 在哪调 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|---|
| `transfer_queue.enable` | 启动配置 | `false` | 默认入口在启动时强制置真;你自己置真的唯一额外效果是给 worker 的运行时环境多塞一个同名环境变量 | 启动时打印的完整配置 |
| `transfer_queue.backend.storage_backend` | 启动配置 | `SimpleStorage` | 换 `MooncakeStore`(注释标了实验性)后走 KV 分层存储,大样本的搬运可以走 RDMA | 启动配置打印 |
| `transfer_queue.backend.SimpleStorage.total_storage_size` | 启动配置 | `100000` | 所有存储单元合计能放多少条样本;小于一个全局批就直接放不下 | — |
| `transfer_queue.backend.SimpleStorage.num_data_storage_units` | 启动配置 | `8` | 存储分片数;配置注释建议不少于节点数的 2 倍,分片少了负载不均也不耐故障 | — |
| `transfer_queue.metrics.enabled` · `.port` | 启动配置 | `false` · `0` | 置真后按 Prometheus 风格开一个 HTTP 端点暴露指标,否则只走日志;端口 0 表示自动挑空闲端口 | 该端点 |
| `transfer_queue.backend.MooncakeStore.protocol` | 启动配置 | `tcp` | 换 `rdma` 后传输走网卡直通,要配合网卡名一起设 | — |
| `transfer_queue.backend.MooncakeStore.global_segment_size` · `.local_buffer_size` | 启动配置 | `4294967296`(4 GB) · `1073741824`(1 GB) | 每个客户端挂载的全局内存段与本地缓冲区;小了大样本写不进去 | — |
| `transfer_queue.backend.MooncakeStore.auto_init` | 启动配置 | `false` | 置真会让它自己拉起元数据服务,**并且会终止已存在的同名进程** | 该进程还在不在 |
| `transfer_queue.backend.MooncakeStore.metadata_server` · `.master_server_address` · `.local_hostname` | 启动配置 | `localhost:50123` · `localhost:50124` · `localhost` | 三个都是单机默认值,多机必须改成真实地址,否则每个节点各连各的本机 | — |
| `transfer_queue.backend.MooncakeStore.device_name` | 启动配置 | `''` | 空表示让它自己挑网卡 | — |
| `VERL_LOGGING_LEVEL` | 环境变量 | 同一个变量两处默认不同:全局日志配置取 `INFO`,桥自己的模块 logger 取 `WARN` | 显式设成 `INFO` 才看得见桥每次取数与写回的条数和耗时 | 日志行 |
| `VERL_AUTO_PADDING` | 环境变量 | `FALSE` | 老协议对象的自动补齐总开关;默认路径的分发不读它,置真也不影响新链路 | — |
| `TRANSFER_QUEUE_ENABLE` | 环境变量,由入口按配置下发 | 不设 | 本仓库没有任何一处读它,含义完全由外部那个数据服务包解释 | worker 的运行时环境 |
| `trainer.ray_wait_register_center_timeout` | 启动配置 | `300` | worker 组等注册中心的秒数;默认入口不读它,只有旧入口和分离式训练器读 | — |

**观测点有三处,第二处最要紧。**

第一处是 worker 的名字。每个 worker 在集群里的名字是「组前缀 + 类名 + 放置组序号 + 冒号 + 本机序号」,列一遍活着的角色就能看出这组摊在哪几台机器上、每台几个;远端报错时,错误里带的也是这个名字。worker 组建好还会打一条日志,列出这次合成出来的角色名。

第二处是桥的两条日志。取数时打一条,带函数名、进程号、这次取了多少条、花了多久;写回时打一条,带函数名、进程号、耗时。**这是唯一能直接量出「这一步搬了多少、搬了多久」的地方**,而它是 `INFO` 级,被默认的日志级别挡在外面——排查搬运开销的第一步就是先把这个级别打开。

第三处是延迟问路的网格名。它们是代码里写死的字符串,默认路径上有三个:训练用的 `train`、策略用的 `actor`、参考模型用的 `ref`。日志里出现哪个名字,就说明这次问的是哪一组的切法。控制器侧每个阶段的耗时是另一套计时器,见 01 章,这里不重复。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 先把搬运量看清楚,再决定要不要调 | 把 `VERL_LOGGING_LEVEL` 设成 `INFO`,存储后端与分片数保持默认 | 用日志量换「每一步到底搬了多少条、多久」的可见度 |
| 多机大批,控制器内存吃紧 | 把 `transfer_queue.backend.SimpleStorage.num_data_storage_units` 提到节点数的 2 倍以上,`total_storage_size` 按一个全局批的 2–3 倍留余量 | 用更多存储进程的内存,换控制器这个单点的内存 |
| 样本本身很大(多模态、长序列),机器有 RDMA | `transfer_queue.backend.storage_backend` 换 `MooncakeStore`,`protocol` 设 `rdma` 并填网卡名,`auto_init` 保持假、自己起元数据服务 | 用一个标注实验性的依赖换搬运带宽,同时接受多一个要运维的服务 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 报错栈里完全看不到自己写的代码 | 错误信息里带的是哪个 worker 名字 | 那是远端抛回来的,去那个 worker 的日志看真正的栈 |
| 改了批大小就断言失败,说只支持等分 | 批大小能不能被数据并行份数整除 | 老协议对象的自动补齐默认关;新链路靠长度均衡那一步补齐,检查是不是绕过了它 |
| 启动就报「没装那个数据服务」 | 装的是不是只有最小依赖 | 它是核心依赖之一,版本下限 `0.1.10`,漏装时控制器一侧在导入阶段就会失败 |
| 打开了数据服务,控制器内存还是涨 | 哪几步在按列名往回拉数据 | 算优势、算指标、生成结果落盘这几步本来就要取回,先看取的列名对不对 |
| worker 组起来了,但某个方法在组上找不到 | 那个方法头上有没有挂分发声明 | 没挂声明的方法不会被合成到 worker 组上,只能在 worker 进程内部自己调 |
| 8 个进程,收回来只有 1 份 | 这组的出口标志 | 张量并行组里只有出口 rank 交回真数据,其余是空壳,这是设计不是丢数据 |
| worker 悄悄死了,作业却一直吊着 | 下一次调用什么时候超时 | 存活巡检那条路径默认没启用,只能靠调用本身报错,别等巡检来救 |

## 六、常见误区

**以为控制器上那一行是一次远程调用。** 它读起来确实像调一个对象的方法——这层抽象的全部目的就是让它读起来像。实际上它是进程总数那么多次远端调用,加上一次同步等待,再加上切与拼两段发生在控制器自己身上的运算。按「一次调用」去估它的开销,批一大就估偏一个数量级。

**以为设计文档里那个按数据并行切的分发模式还是主路径。** 官方设计文档整篇拿它当例子讲,谁读完都会去代码里找它。它在仓库里已经没有任何使用点了:默认路径上的计算方法一律走延迟问路那一种。8 种预定义摊法里,实际被用到的只有 4 种加这个工厂,剩下几种是历史遗留;更极端的是其中一种连分发函数都没注册,真用上会直接抛键错误。

**以为那个同名的环境变量是这条链路的总开关。** 名字写得像开关,而且入口确实会下发它。但本仓库没有任何一处读它——它是给外部那个数据服务包看的。真正的事实是:控制器一侧带着配置初始化这个服务,worker 一侧的桥在第一次撞见元数据对象时无参初始化,**两边看到的根本不是同一组设置**。想确认链路到底怎么起的,看启动时打印的那份完整配置,不要看环境变量。

**以为带 fused 字样的那个共卡类合成函数是新主路径。** 名字像升级版,旧的那个头上还明明白白写着「已弃用,改用 FusedWorker」。实际调用关系正好相反:默认训练器调的就是被标弃用的那个,而带 fused 的那个在整个仓库里零调用点。照着注释去读新路径,会读进一段没人走的代码。

**以为非阻塞就是「先发出去,过会儿再等」。** 控制器在非阻塞档下不等也不取,拿到的是一个空句柄;数据什么时候真正落地,不在控制器的时间线上,所以在控制器上打断点是看不见它的。而且默认路径上这一档只用在价值网络那两次调用上,拿到句柄立刻就等掉了,其中算价值那次连等回来的结果都直接丢弃——输出早就由 worker 自己写进数据服务了,源码里还留着一条注释说这条路上句柄与元数据引用尚未打通。这一档真正省下的是 worker 之间直连传数据的能力,不是异步本身。

**以为上了数据服务之后控制器就彻底不碰数据了。** 宣传语是「控制器只拿元数据」,容易读成「一列都不拉」。实际上算优势那一步要拉 7 列回来,生成结果落盘要拉 5 列并在本地把 token 编号还原成文字,算指标时还要再拉一批。省掉的是整批全列的来回搬运,不是全部搬运;排查控制器内存时,第一个要看的就是这几处各拉了哪些列。

**把 worker 存活巡检当成有人在替你盯着。** 代码里确实有一条后台线程,轮询每个 worker 还活着没有,死了就给主线程发中止信号——看见它很容易松一口气。但它在本仓库里没有任何调用点,默认不开。worker 悄悄死掉时,你等到的是下一次调用超时或报错,而不是这条巡检。
