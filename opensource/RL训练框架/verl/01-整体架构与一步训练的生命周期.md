# 整体架构与一步训练的生命周期

这一页回答一件事:默认同步训练的各个角色如何组织在进程与 GPU 上,以及一步训练依次经过谁的手。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一次后训练要协调 Actor、Rollout 与 Reward,并按算法需要启用 Reference 和 Critic。默认同步模式下,训练与生成共享 GPU、交替执行,每步结束再把新权重交给 Rollout。Reference 提供参考概率,不是 PPO 的 old policy。

如果算法流程与每个进程上的并行执行细节混在一起,修改生成、打分或更新顺序时,就得同时处理各进程的协调;观察中间数据也需要理解它们分布在哪里。另一方面,大模型的前向反向又往往需要多进程协同。

所以真问题是:算法控制流必须好写好查,神经网络计算流必须多进程,两者怎么在一台集群上共存。

## 二、解法

把两条流分开,各给各的进程模型。

**算法控制流留在一个进程里,顺序写**:取一批题目、让生成方产出回答、打分、准备概率与可选的 value、算优势、更新 Actor。这个进程是控制器,它自己不持有模型、几乎不吃显存,只发号施令,外加做几步轻量的张量运算。它看起来就是一段单机脚本。

**计算流留在多进程里**。每个训练 rank 对应一个 worker 进程,按所选并行方式持有模型参数,只会做"前向""反向""更新一次"这类粗活。控制器要办一件事,就朝一个代理对象发一次调用,代理把这次调用摊给它管的那一组 worker,再把结果收拢回来。**控制器看起来像在调一个函数,底下是一整组进程在协同**——摊开和收拢的规则怎么声明,是下一章的事。

最天然的疑问是:数据这么来回搬不贵吗。贵,所以后来补了一刀:一批样本注册进一个独立的 TransferQueue,跨阶段主要传键与标签,worker 按键自取。控制器仍会读取必要字段来计算优势、统计指标和查看样本,省掉的是不必要的整批往返。这两件事——调用怎么摊开、数据走哪条路——都在 02 章展开。

生成方也用同一套思路包了一层:推理引擎不是被当成库函数调进来,而是起成一组能睡下、能醒来、能换权重的副本。**共卡时需要安排显存交接**——取样结束后先让 Rollout 睡下,再进行训练计算;步末恢复接收权重所需的内存、推送新权重,最后恢复生成所需的缓存。睡眠释放哪些内存取决于后端与模型形态,不一定把权重全部丢弃。副本这一层怎么起、对外提供哪些动作,见 04 章。

## 三、代价

三笔,都要认。

**第一笔是通信。** 控制器和 worker 之间每一次往返都是真实的跨进程调用。改成键引用之后小了很多,但没有消失。这是这条路线换来灵活性付的钱,不要假装它不存在。

**第二笔是显存的来回腾挪。** 共卡意味着同一块显存这会儿归训练、那会儿归生成;每步睡一次醒一次,这段时间两边都在干等。这段开销是否显著,取决于模型大小、并行布局与后端实现。

**第三笔是"一步"变长了。** 九个阶段串在一起,任何一段慢下来都拖住整步;而且因为角色不同,慢的那一段往往不在你盯着的那张卡上。排查一次"这步怎么变慢了",要沿参与本步的各个角色检查。

## 四、和另一种做法的三处不同

这里对比的是控制流与计算流紧密耦合的组织方式,不把所有其他框架都归成同一种实现。要看 slime、ROLL 的具体区别,见 02 章。

1. **算法代码的边界。** 控制器写阶段顺序,worker 封装后端计算;换后端时尽量把变化留在 worker 与引擎层。
2. **中间状态的可见度。** 控制器可以按需取回概率、奖励与优势,不必为了每次观察都改 worker 里的计算代码。
3. **数据与调用的代价。** 这种分工需要跨进程协调,TransferQueue 可以减少不必要的数据往返,但不会消除全部传输和本地处理。

这个选择方便组合算法与后端,代价是多了一层分发、数据服务与调试边界。是否更快,仍要看具体负载。

## 五、调参与观测

**这一页的参数全是启动配置**,改了要重新拉起整个作业。启动方式是跑训练主模块并在命令行上追加点分路径的键值覆盖,组合规则见总览第六节。

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `trainer.use_v1` | `true` | 置假回到旧入口,本页描述的九阶段结构不成立 | 启动日志里会打一条弃用警告 |
| `trainer.v1.trainer_mode` | `sync` | 换成两档异步后,生成不再严格等训练,改变等待与重叠方式,同时需要管理样本陈旧度 | 启动日志里创建的训练器类名 |
| `actor_rollout_ref.hybrid_engine` | `true` | **默认档与共卡异步档根本不读它**;只有分卡异步档读,置假时那一档不在训练卡上起 Rollout 副本 | 分卡异步档的启动日志会打一条说明 |
| `trainer.nnodes` · `trainer.n_gpus_per_node` | `1` · `8` | 决定全局池 GPU 数;Rollout 副本数还取决于并行度 | worker 组创建日志 |
| `data.train_batch_size` | `1024` | 大了显存和一步时长都涨,小了梯度噪声大 | `timing_s/step` |
| `data.gen_batch_size` | `null`(普通同步路径回退到训练批大小) | 决定取数粒度;异步与动态补样路径可将它改为 1 | 提交批次数 |
| `trainer.v1.<模式>.parameter_sync_step` | 同步档 `1`,分卡异步档 `4` | 把一个训练批分成多次控制器子循环,步末仍同步一次;分卡异步需与 PPO mini-batch 大小匹配 | `timing_s/update_weights` 占比 |
| `trainer.critic_warmup` | `0` | 全局步数小于该值时不更新 Actor,用于 Critic 预热 | `timing_s/update_actor` 是否缺席 |
| `trainer.save_freq` · `trainer.test_freq` | `-1` · `-1` | 负数关闭周期存档与周期评测;训练前评测由下一项控制 | `timing_s/save_checkpoint`、`timing_s/testing` |
| `trainer.val_before_train` | `true` | 置假跳过开训前的那次评测,省一段冷启动 | 启动日志里的初始评测指标 |
| `trainer.total_epochs` | `30` | 与数据集大小一起决定总步数 | 进度条总数 |
| `trainer.resume_mode` | `auto` | 决定是否自动从最近一次存档接着训 | 启动日志里加载的存档路径 |
| `trainer.rollout_data_dir` | `null` | 设了会把每步的生成结果落盘,便于人工看回答 | 该目录下每步一个文件 |
| `trainer.logger` | `["console", "wandb"]` | 决定指标上报到哪 | 对应后端的面板 |
| `trainer.device` | `cuda` | 昇腾环境下入口会自动改写 | 启动日志 |

**先看阶段耗时,再看引擎指标。** `timing_s/step` 是步级总量,`gen`、`old_log_prob`、`adv`、`update_actor` 等是其中的阶段计时,不能把总量和子项当作互斥开销相加。`reward`、`ref`、`values`、`update_critic` 只在对应路径出现;均衡没有单独计时器。部分阶段还提供 `timing_per_token_ms/` 指标,用于按 token 规模比较。确定慢在哪一段后,再查看该角色的日志和引擎侧指标。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡,先把链路跑通 | 保持默认同步档与共卡;把训练批和生成批都调小;关掉周期存档与评测,不需要初始评测时另关 `trainer.val_before_train` | 用吞吐换一次能跑完的验证,便于快速发现配置错 |
| 多机、卡够,追吞吐 | 同步档共卡不变,按节点数放大训练批;打开存档频率;评测频率设成 20–50 步一次 | 用一步时长换梯度质量与可恢复性 |
| 卡利用率被长尾拖住 | 换共卡异步档,预热批次保持默认 | 用样本新鲜度换卡利用率,详见 08 章 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动后长时间卡住、没有任何步数 | worker 组创建日志走到哪一组 | 多半卡在模型加载或 Rollout 副本起服务,看副本侧日志 |
| 一步时长忽高忽低 | `timing_s/gen` 的波动 | 长尾样本所致,先看生成长度分布,再考虑换异步档 |
| `timing_s/update_weights` 占比高 | 采用的传输后端、权重规模与并行布局 | 沿权重导出、传输与唤醒定位开销,见 05 章 |
| 控制器被内存杀掉 | 控制器被调度到了哪个节点 | 官方明确建议不要把它放在集群头节点上 |
| 中间值全对但训不动 | `timing_s/update_actor` 是否一直缺席 | 价值网络预热步数没走完时策略本来就不更新 |

## 六、常见误区

**以为控制器就是提交作业的那个进程。** 它不是。入口把控制器本身也做成一个远端角色再提交出去,所以它落在集群里的某个节点上,不一定是你敲命令的那台。官方明确建议不要把它调度到集群头节点——它吃内存,而头节点通常资源最少。在头节点上查"控制器为什么被 OOM 杀掉",是第一反应最容易错的地方。

**以为 TransferQueue 那个开关归你管。** 配置里它默认是关的,而默认入口在启动时把它直接置真;只有你自己在配置里显式打开,那个同名的环境变量才会随运行时环境下发到各个 worker。照配置默认值判断这条链路开没开,会判反。

**以为一步只同步一次权重就等于一步只更新一次。** 一个训练批可以再切成若干次本地更新,每次都经过相同的阶段骨架,其中若干阶段按配置跳过,而权重同步仍然按步走。同步档下这个次数默认是 1,分卡异步档下默认是 4——**两档默认值不同**,照着同步档的经验读异步档的日志会对不上。

**把生成那一段计时当成推理引擎的吞吐。** 那段计时里还含着 Rollout 副本睡下去的时间(按后端策略让出显存),推送新权重则另算一段。引擎本身快不快,要去看引擎侧的指标,不是这个数。

**以为共卡是靠那个共卡开关控制的。** 名字写得像总开关,配置里也默认为真,但基准上**默认档与共卡异步档一行都不读它**,只有分卡异步档读——在那一档里它决定要不要在训练卡上再起一组 Rollout 副本。默认档下把它置假,什么也不会发生。

**以为四个角色各有各的资源池。** 默认同步模式使用一个全局 GPU 池:Actor、Rollout 及按需启用的 Reference、Critic 共享这批资源,占满 `trainer.nnodes` 乘 `trainer.n_gpus_per_node` 那些卡。在这一模式下还可分出独立池子供两个角色使用——开了独立资源池的奖励模型,以及蒸馏用的教师模型。按「四个角色四份卡」估算资源,方向就反了。

**以为 Reference 模型一定独占一组进程。** 默认共卡路径上,Actor 与 Reference 本就由同一组 worker 管理;启用 LoRA 后还可以复用 Actor 的底座来计算参考概率。共用进程与复用模型参数是两件事,都不能按角色名称直接推算 GPU 数。

**以为实验性目录里的东西是可选的。** Agent Loop 和 Reward Loop 的代码确实放在名为实验性的包里,但在默认路径上它们是主干:没有 Agent Loop 就没有生成,没有 Reward Loop 就没有分数。目录名在这里不代表成熟度。
