# 把推理引擎当成可换权重的服务

这一页只回答一个问题:训练侧要用推理引擎产出样本,这件事为什么不能写成一次函数调用。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

生成是一步训练里最长的一段,而且它有多长不由你定:同一批题目里,最慢的那条轨迹决定整段什么时候结束。

但真正让「调一次函数、拿回一批结果」这个写法站不住的,是另外两件事。

**第一件是中断。** 异步训练换权重时,可能需要暂停还在跑的生成请求。停止本次请求不等于丢弃已有轨迹:客户端可以保留已生成的 token 与 logprob,换权重后带着前缀继续,因此一条轨迹可能跨过多个权重版本。批进批出的接口没有中断点:发出去了就只能等它自己跑完,而它什么时候跑完取决于最慢那条。

**第二件是多轮。** agentic 任务里一条轨迹是「生成一段 → 调个工具 → 把工具结果接上去继续生成」,下一轮的输入取决于上一轮的输出,不同轨迹的轮数还不一样。把这种东西塞进一次批调用,只有两条路:每一轮都等整批对齐,让最慢的那条拖住所有人;或者在调用内部自己再实现一遍调度。这件事怎么被做成一层可中断、可插工具的会话,是 10 章的主场,这里只说它决定了生成的形状。

所以问题不是「生成慢」。问题是**生成这一段的形状根本不像一次函数调用**:它要能被打断、能按单条请求走、能在中途插进别的事。

## 二、解法

**把推理引擎起成服务,训练侧当客户端用。** 听起来是把事情搞复杂了,但上面那两个难题恰好就此消失:服务本来就按请求处理,中断是它自带的动作,多轮不过是多发几次请求。

这一层分三段。

**最里面是副本。** 一个副本就是「在每个节点上敲一条起服务命令」的那个东西:它按张量并行、数据并行、流水线并行三个度数相乘算出自己占几张卡,再除以每节点的卡数,得出它跨几个节点,每个节点上起一个服务进程。**副本数由资源与并行度推导**:默认融合路径用训练池卡数除以每副本卡数,独立生成池则用自己的资源规模。

副本有三种摆法:和训练引擎融在同一个进程里、和训练进程共用同一批卡但各自独立成进程、以及独占一组卡。第一种是默认;前两种共卡布局都需要协调睡眠与唤醒——训练要用卡的时候,生成这一侧必须先把显存腾出来。

**中间是服务。** 每个节点上一个服务进程,但只有 0 号节点那个真正持有引擎对象、对外露出地址;多节点副本里其余节点跑的是无头进程,只参与计算、不接请求。副本对外因此只有一个入口:即使内部拆成预填充与解码两组服务,登记出去的也只有预填充那一个地址,解码侧藏在它后面按轮转领活。

服务对外有两副面孔。一副是进程间的直接调用,输入是 token id、输出也是 token id,生成走的是这一副;另一副是 OpenAI 兼容的 HTTP 地址,给指标抓取和外部路由器用。

**最外面是路由。** 一个独立进程管着所有服务的池子,按两条规则派活:同一条轨迹的后续请求尽量回到上一次那台,前缀缓存才命中得上;没有历史的就挑在途请求最少的那台。取服务器和还服务器各是一次调用,而且只序列化路由器自己声明要的字段——默认那套只认请求编号,连提示词都不过去。打开逐位可复现之后这套规则整个换掉,改成按请求编号哈希整个池子:「谁在途最少」本身依赖请求到达的时刻,跑两次不会一样。

**本章关注副本的四个控制动作**:睡下、醒来、换权重、中断。

睡下是把权重和 KV 缓存一起从显存里放掉。醒来是反过来,但**分两口气**:先只醒权重,等新权重推完、训练侧把自己的参数卸回内存、并且所有 rank 都到齐,才醒 KV 缓存。这个顺序错了,就是两边同时占着显存的那个峰值。睡多深由副本自己判:通常释放权重与缓存;涉及草稿模型或只同步 LoRA 等路径时,要避免丢失不会被这次更新重写的权重。浅睡如何处理权重取决于后端:SGLang 的 adapter 路径保留 base weights,vLLM level-1 仍涉及权重内存的解除映射与恢复。

换权重这个动作本身只到接口为止:副本声明「我能接一串带名字的张量」,至于这串张量怎么从训练侧切好、走哪条线过来,是 05 章的事。副本这一侧只负责收尾的那一下——**换完必须硬清一遍缓存**,本地前缀缓存和外挂的共享 KV 存储一起作废,旧权重算出来的 KV 一块都不能留。

中断是三步:先关掉准入,再等已经进门的请求落地,最后让引擎中断在跑的请求;客户端可保留部分结果重试。关门时还要一并声明后来者怎么办——副本马上就回来,就让它们停在门口等;副本这次是要退出轮转,就直接判失败、让客户端改投别家。这道准入闸是 verl 自己加在引擎前面的一层,不是每个后端都有;没有的那个后端只能打一条日志,说「拒绝模式我做不到,请求会一直等下去」。

## 三、代价

**第一笔是两层中转。** 每个请求先找路由要一台服务器,再向那台服务器发一次调用,结束后还要把它还回去——三次跨进程往返,一条请求都躲不掉。

**第二笔是控制面收窄成一个点。** 睡醒、中断、清缓存全部只有 0 号服务响应,多节点副本里其余服务在这些动作上是哑的。好处是不必做跨节点的一致性,坏处是这个点一卡整个副本就不动了,而且从外面看不出来卡在哪个节点。

**第三笔是并行度和副本粒度绑死了。** 在 GPU 池大小固定时,想多要几个副本,需要把每副本并行度调小;把并行度调大,就自动变成更少更大的副本。副本数一变,路由池的宽度、粘性会话的分布、每张卡上留给生成的显存比例全跟着变,而这三样都不是你直接配的。

**第四笔是睡醒窗口里的请求要有个去处。** 停在门口的请求占着客户端的并发额度,判失败的请求要客户端自己重来。两种都不免费,而且这段逻辑在不同后端上行为并不一致。

## 四、和 slime、ROLL 的三处分歧

拿智谱系的 slime 与阿里的 ROLL 作对照,两家的仓库本站都已克隆,说法在它们树上核过(核对日期 2026-09-20)。

1. **服务化这一层不是 verl 独有的。** slime 的生成后端目录里同样有部署、引擎组、服务控制与 PD 分离这几件东西;ROLL 也把生成引擎做成了独立的策略。把推理引擎起成一组可控的服务,是这一代框架的共同选择,不是这里的发明。真正的差别在下面两条。
2. **多后端意味着同一控制动作要分别实现。** verl 在 vLLM、SGLang、TensorRT-LLM 等接入路径上提供统一的副本与路由接口,slime 的主线紧贴 SGLang,ROLL 通过生成策略对接服务。统一接口不意味着细节相同,例如拒绝新请求的准入控制在各后端上并不齐全。
3. **旧路是被删掉的,不是留着不推荐。** 这一条的对照面在 verl 自己仓库里:批进批出的同步生成入口如今只剩一个抛异常的方法,配置里把生成档位写成同步会在校验阶段直接被拒,报错明说这条路已经移除。不是「两种都支持、推荐用新的」,是旧的那条已经不通——这决定了读者不必在两套写法之间犹豫。

## 五、调参与观测

**这一章的参数全在启动时定死**,跑起来之后一个都改不了;写法是在训练命令后面追加点分路径的覆盖项。表里标了「要加号」的那几个在配置文件里没有对应行,只能用 Hydra 的追加写法塞进去。下表省略了统一的 `actor_rollout_ref.rollout.` 前缀。

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `name` | 无,必填 | 选后端:`vllm`、`sglang`、`trtllm`。配置注释里还列着 `hf`,但注册表里没有,填了会在取类时报「找不到这个后端」 | 服务 actor 名的前缀 |
| `mode` | `async` | 唯一可用值。写 `sync` 直接抛错退出,写别的值只打弃用警告 | 配置校验阶段的报错 |
| `tensor_model_parallel_size` | `2` | 与下面两个并行度相乘 = 一个副本占几张卡;乘积变大,副本变少变大,路由池变窄 | 服务管理器打印的地址清单长度 |
| `data_parallel_size` | `1` | 同上。大于 1 时 vLLM 那条路会按每节点卡数再切出本地数据并行度 | 同上 |
| `pipeline_model_parallel_size` | `1` | 三个后端都还没实现大于 1,写了直接报 not implemented | 配置校验阶段的报错 |
| `expert_parallel_size` | `1` | 非 TensorRT-LLM 后端上必须等于张量并行 × 数据并行,否则断言失败 | 配置校验阶段的报错 |
| `gpu_memory_utilization` | `0.5` | 大了 KV 缓存多、并发上得去,但共卡时留给训练的余量少 | 引擎启动日志里的 KV 缓存块数 |
| `standalone_gpu_memory_utilization` | `null` | 只对独占卡的副本生效,为空时退回上一行 | 同上 |
| `free_cache_engine` | `true` | 置假则睡下、醒来、放缓存三个动作全部空转;共卡下等于不腾显存 | 换权重前后的显存日志 |
| `enable_sleep_mode` | `true`,**要加号** | 置假则引擎不开睡眠能力,起服务时改用可扩展显存段 | 起服务前这个值会被单独打印一行 |
| `max_num_seqs` | 配置文件 `256`,数据类 `1024` | 引擎的并发上限;同时决定服务 actor 的并发额度取 `1000` 与「该值 + 16」的较大者 | 路由器状态里的在途请求数上限 |
| `max_num_batched_tokens` | `8192` | 一批最多多少 token,大了吞吐高、显存峰值高 | 引擎调度日志 |
| `max_model_len` | `null` | 空则取模型的最大位置数;设得比它大会直接报错 | 配置校验阶段的报错 |
| `n` | `1` | 一条题目采几个样本,GRPO 类算法要大于 1;生成时长近似按比例涨 | 一步取回的轨迹条数 |
| `full_determinism` | `false` | 打开后:路由改成按请求编号哈希整池、每轮不再换新请求编号、随机种子按副本序号加偏移 | 同配置跑两次的曲线是否逐位对齐 |
| `seed` | `42` | 实际种子是副本序号加这个值,所以同一作业里各副本天然不同 | 引擎启动参数 |
| `skip_tokenizer_init` | `true` | 只有 SGLang 与 TensorRT-LLM 照它走;vLLM 那条路把这一项写死成「不跳过」 | 起服务参数里的对应项 |
| `router_config_path` | `null` | 指向一个外部 YAML(里面写 `router_class` 全限定名)就换掉内置路由;与程序注入的路由类同时给时,后者胜出并打一条警告 | 启动日志里的路由器类名 |
| `engine_kwargs.vllm` / `.sglang` / `.trtllm` | `{}` | 原样透传给引擎的起服务参数;vLLM 那条路会先把值为空的键丢掉 | 0 号副本把拼好的起服务命令行整条打印出来 |
| `disaggregation.enabled` | `false` | 打开则副本内部拆成预填充与解码两组。只支持 vLLM 与 SGLang,且当前只允许一组预填充、单节点放得下、数据并行为 1 | 副本构造时的 not implemented 报错 |
| `disaggregation.transfer_backend` | `nixl` | KV 搬运通路;vLLM 那条路当前只认 `nixl` 与 `mooncake` | 同上 |
| `disable_log_stats` | `true` | 置假才吐引擎自己的统计 | 引擎周期性统计日志 |
| `prometheus.enable` · `prometheus.port` | `false` · `9090` | 打开后各副本的指标端点被写进 Ray 的抓取配置并热加载;要求 `disable_log_stats` 为假,否则启动即报错 | 抓取配置文件里那条 rollout 任务的目标清单 |

**观测点有六处,够用了**:

- **副本起没起来**:服务管理器在所有副本就位后打印一行地址清单,清单长度就是副本数。这是第一处该看的地方,因为副本数算错时它一眼就看得出来。
- **路由现在什么样**:路由器有一个状态查询,返回每台的在途请求数、总在途数、活跃台数和登记过的句柄清单;另有一个清空粘性会话的动作,返回被丢掉的条目数和当时各台的负载。
- **单条请求的回执**:每次生成返回的结构里带停止原因(正常完成还是被作废)、被抢占的次数、这次前缀缓存命中了多少 token,以及产出它的那版权重对应第几步。多轮场景下还额外带这条轨迹跨过的最小与最大步数——**两个数不相等,就说明这条轨迹中途换过权重**。
- **抢占次数会被聚合**:Agent Loop 把每条轨迹的抢占次数汇成最小、最大、平均三个指标,另外单报最慢那条的抢占次数。
- **中断做了多少**:服务端每次全量作废都打一条「已作废 N 条请求」,并列出请求编号。
- **闸门有没有卡住**:关门时若已进门的请求 60 秒还没落地,会打一条超时警告,然后硬着头皮往下走。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡先把 GRPO 跑通 | 共卡不动;`rollout.tensor_model_parallel_size=2`、`rollout.gpu_memory_utilization=0.6`、`rollout.n=5` | 4 个副本,粒度细、路由摊得开;显存偏向生成,训练侧靠参数卸载补回来 |
| 模型大到一张卡装不下一个副本 | `rollout.tensor_model_parallel_size` 提到 8 或 16,`rollout.gpu_memory_utilization` 降到 0.4–0.5,`rollout.enforce_eager=true` | 用副本数换单副本容量;关掉图捕获,省下睡下时放不掉的那部分显存 |
| 长尾严重,希望生成能被干净地打断 | 后端保持 `vllm`(准入闸只有它有),`rollout.max_num_seqs` 按显存上调,配合异步档 | 用单条时延换并发;准入闸让换权重不必等最慢那条跑完 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动后卡在起服务这一步不动 | 0 号副本打印的那条起服务命令行 | 多半是透传参数与引擎版本对不上,把透传项二分着去掉 |
| 路由报「池子里没有可用服务器」 | 是不是正好在换权重,或者副本刚被摘出轮转 | 只靠共卡副本供生成的那个客户端变体会每秒重试而不是报错;若是独占副本压根没起来,回头查上一行 |
| 换完权重第一步的指标塌了 | 换权重之后有没有清缓存这一步 | 外挂共享 KV 存储要 vLLM 0.22 以上才保证清干净,旧版本会留下旧权重算的 KV |
| 训练侧在换权重那一刻显存爆掉 | 醒来两口气的先后 | 必须等训练侧参数卸回内存、且全部 rank 到齐,才能醒 KV 缓存;只同步本卡不够 |
| 共卡下可用显存比估算少一整份模型 | 模型带不带投机解码草稿权重,这次是不是只同步低秩适配器 | 浅睡对权重的处理因后端而异,不能按「权重全释放」统一估算 |
| 多节点副本睡不下去 | 控制动作发到了哪个节点 | 只有 0 号服务响应,其余节点是无头进程,发过去也没人接 |

## 六、常见误区

**以为还能同步地调一次生成、拿回一批结果。** 那个方法确实还在:基类上有一个默认抛异常的版本,vLLM 那个适配器还专门重写了它——重写的唯一目的是把错误信息写清楚,说同构多进程那条生成路径已经退役。配置里把生成档位写成同步,更是在校验阶段就抛错。人们会这么以为,是因为仓库自己的 SGLang 后端文档还停在「初始化一个 rollout 对象、然后调生成」那个写法上,而那篇文档的更新日期比基准早了一年多。

**以为副本数是配出来的。** 没有这个参数。默认融合路径:副本数 = 训练池卡数 ÷(张量并行 × 数据并行 × 流水线并行);独立池用生成池卡数计算。资源池大小不变时,想要更多副本就要把每副本并行度调小,而并行度又被模型大小卡着——所以「加副本」是一个受限的推导结果,不是一个旋钮。跑起来发现副本数不对,先去算这个除法,不要去配置里找。

**以为配置里列出来的每一项都有人读、而且对所有后端一样。** 两件事各错一半。一是有死配置:分阶段唤醒和过采样早停这两项在基准上只出现在配置与文档里,代码里没有任何读取点,调它们既不生效也不报错。二是有后端差异:跳过分词器这一项写在公共配置段里,看着像全局开关,实际上 vLLM 那条路把它写死了,只有另外两个后端照配置走。判断一个开关到底管不管用,只能去代码里找读取点。

**以为睡下就是把显存全放掉。** 睡眠深度和权重保留方式随模型形态与后端变化。SGLang 的 LoRA adapter 路径可保留 base weights,vLLM 浅睡仍要恢复权重内存。估算显存时应看实际后端的驻留与恢复策略,不能把「浅睡」统一理解为只释放 KV cache。

**以为清前缀缓存是个优化选项。** 它是正确性要求。旧权重算出来的 KV 块如果留到下一步,等于拿上一版策略的中间结果去拼这一版的输出。所以每次换权重都硬清一遍,连外挂的共享 KV 存储也一起作废——长前缀去重带来的那点收益,在权重边界上一分不留。**这也是为什么 KV 卸载在 RL 里的收益比在纯服务场景里小**:步与步之间它被清空,能吃到的只有一步之内的重复。

**以为路由只是个负载均衡器。** 它管着两件跟正确性有关的事。一是多轮会话必须落回同一台,否则前缀缓存一次都命中不了,每一轮都重新算整段历史。二是服务器被摘出轮转时,指向它的粘性条目要能自动失效并重选,否则那条轨迹会一直往一台已经不接活的服务器上撞;训练与生成切换时,训练器还会主动把粘性缓存整个清掉,让新加进来的副本也能分到活。把它当成「随便挑一台」来理解,这两件事都会被漏掉。
