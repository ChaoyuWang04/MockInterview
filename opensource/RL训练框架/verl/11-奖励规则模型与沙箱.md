# 奖励:规则、模型与沙箱

这一页回答一件事:同一批回答的评分既可能是字符串判题,也可能要调用模型或执行代码,VeRL 怎样安排这些工作并把结果交回训练。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

生成结束不等于样本已经可以训练。数学题可以在 CPU 上核答案,偏好评分要做模型前向,代码题还要等测试用例执行。把它们都塞进控制器逐条算,短回答也会被慢评分拖住;让奖励模型和 Rollout 同时抢同一批 GPU,又会撞上显存边界。

问题在于**评分方法不同,等待的资源也不同**。训练器需要一个统一结果,却不能用同一种执行时机处理所有评分。

## 二、解法

VeRL 把奖励拆成两层:Reward Loop 安排在哪算、何时算;里面的 Reward Manager 负责把样本交给评分函数,再整理结果。这是 V1 默认训练路径的一部分,不需要另外启用一套奖励循环。

**先按资源决定时机。** 规则奖励和独立资源池里的奖励模型可以在轨迹完成后立即接单;奖励模型若与训练共卡,默认同步训练会等 Rollout 睡下,再集中唤醒奖励模型打分。这个边界决定奖励能否与其他轨迹的生成重叠,不是“用了异步函数就一定重叠”。会话如何结束见 10 章,这里从完整轨迹交给评分方开始。

**再按评分方法分流。** 自定义函数优先:它可以直接判题,也可以调用模型服务再解析答案。没有自定义函数时,未开启奖励模型就按数据来源选内置规则;开启模型则走内置判别式评分。生成式裁判要怎样写提示词、怎样把生成文本变成分数,由自定义函数负责,不会因为填了一个模型路径就自动获得这些逻辑。

![Reward Loop 先决定奖励能否随轨迹完成立即计算,再由 Reward Worker 将样本分流到规则函数、模型服务或代码沙箱;模型路由器与沙箱服务是不同的执行端,结果最终统一交回训练。](/opensource/verl/11a-reward-dispatch.svg)

默认 Reward Manager 从回答 token 解码出文本,把数据来源、标准答案和附加信息交给函数。同步函数放到执行器里跑,异步函数直接等待。函数既可返回标量,也可返回含主分数与诊断字段的字典。默认装配会把标量放在回答最后一个有效 token 上,其他位置填零;后面的 KL 处理与优势计算归 07 章。

模型评分并不在这个 CPU Worker 里加载一份神经网络。VeRL 复用 Rollout 副本启动奖励模型服务,前面放一个按在途请求数选服务的路由器。代码评分则走另一条出口:规则函数抽取代码、拆开测试用例,通过 Sandbox Fusion 的 HTTP 服务执行,汇总通过情况。沙箱服务需要事先可用,这条链路负责调用它。

## 三、代价

**并发只会搬走等待,不会消灭等待。** 增加 Reward Worker 能让更多评分同时进行,也会放大 CPU、模型服务或沙箱的压力。共卡模型省了独立资源池,却把评分留成一步里的串行阶段;独立模型能提前接单,但需要另付 GPU 资源。

**失败也可能被压成分数。** 默认代码评分会把执行错误计入未通过,而内置分流函数只取评分结果中的标量,不保留沙箱返回的逐例诊断。训练曲线上的低奖励因此可能来自代码错误、答案格式错误或服务失败。想区分这些原因,需要保留服务日志,或用自定义函数把诊断整理成额外字段。

**接口统一不等于每条组合都已接严。** 基准的独立判别式模型路径存在返回字段缺口:内置模型评分只给主分数,轨迹内调用方却还直接读取附加信息。第五节给出具体排查点;独立部署的设计能力不能当成这条内置组合已经跑通的证据。

## 四、和 slime、ROLL 的组织方式有什么不同

| 共同要做的事 | VeRL | slime | ROLL |
|---|---|---|---|
| 选择评分逻辑 | Reward Manager 接评分函数,默认规则按数据来源分流 | 生成流程调用奖励入口,优先样本或全局自定义函数,再选内置评分类型 | Reward Scheduler 先按数据领域分组,交给对应 Reward Cluster |
| 把结果接回训练数据 | 轨迹内评分与共卡批量评分汇入统一奖励张量 | 样本缺奖励时调用评分函数,把结果写回样本 | 收集各领域结果,再按原始样本顺序重排 |

这里的区别是接入边界:VeRL 将评分函数外面再包一层分布式调度和模型服务管理,方便同一训练器按资源部署安排时机。slime 的上述入口贴着生成样本走,ROLL 的上述调度器突出多领域分组。这个比较不代表任何一家只能使用表中的评分方法。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。下表使用当前 `reward` 配置树;在训练命令后追加对应键值。旧配置有迁移逻辑,混用两套写法会让旧项覆盖新项,新作业只用这一套。

| 参数与位置 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `reward.num_workers` | `8` | 增大可增加并发评分容量,也增加 CPU 与下游请求压力;不是模型副本数 | Ray 中 `reward_loop_worker_*` 数量、CPU 负载、下游在途请求 |
| `reward.reward_manager.name` | `naive` | `remote` 将同步评分放入额外 Ray 进程,适合线程不兼容或 CPU 密集函数;`rate_limited` 对自定义评分加限流 | Worker 创建日志、评分失败栈;不要把 `remote` 用于异步函数 |
| `reward.custom_reward_function.path` · `name` | `null` · `compute_score` | 设路径后优先调用自定义函数;奖励语义由函数决定 | 样本的主分数及 `reward_extra_info`,自定义函数日志 |
| `reward.reward_model.enable` · `model_path` | `false` · `null` | 开启后启动奖励模型服务,增加显存与模型推理开销 | 模型服务启动日志;内置判别式路径的响应字段 |
| `reward.reward_model.enable_resource_pool` | `false` | 开启后允许轨迹内评分与生成重叠,改用独立 GPU 资源 | 资源池与服务部署;独立内置 DisRM 的字段问题见下表 |
| `reward.reward_model.nnodes` · `n_gpus_per_node` | `0` · `8` | 独立池必须将节点数设为正数;共卡时这两项被训练资源规模覆盖 | 资源池校验错误、奖励模型副本数量 |
| `reward.reward_model.rollout.name` | 必填,无默认后端 | 内置 DisRM 对 vLLM 调 `classify`,对 SGLang 调 `v1/embeddings`;本基准 TensorRT-LLM 分支直接报错 | vLLM 读取 `data[-1].probs[-1]`,SGLang 读取 `data[-1].embedding[-1]` |
| `reward.reward_model.rollout.tensor_model_parallel_size` | `2` | 增大使每副本占用更多 GPU,固定资源下副本数可能减少 | 奖励模型服务数、显存、吞吐;副本还受数据与流水线并行影响 |
| `reward.reward_model.rollout.gpu_memory_utilization` | `0.5` | 增大增加推理内存预算,可能改善批处理容量,也更易与共卡角色冲突 | 奖励模型显存、服务启动或推理 OOM |
| `reward.sandbox_fusion.url` | `null` | 对内置代码数据源设置后改走 Sandbox Fusion;未设时走本地代码评分实现 | 请求是否进入指定服务、API 错误日志 |
| `reward.sandbox_fusion.max_concurrent` | `64` | 限制每个 Reward Manager 所建沙箱信号量的并发请求,增大可能压垮服务;不是全作业上限 | 沙箱并发、排队与 HTTP 错误;同时核 Worker 数 |
| `reward.sandbox_fusion.memory_limit_mb` | `1024` | 提高单例执行内存限制,减少内存不足但增加服务侧资源需求 | 传给沙箱的 `memory_limit_MB` 与执行结果 |

**先确认打分口径,再看平均奖励。** 内置规则按 `data_source` 选择,默认 Manager 读取 `reward_model.ground_truth`。例如 GSM8K 的默认规则会找规定的答案标记,答案数值正确但格式不符仍会失分。自定义函数返回字典时必须含 `score`,需要观测的诊断也放在该字典里;只返回标量时默认 Manager 将同一个值记成 `acc`,这个字段名不保证分数就是二值准确率。

共卡评分可看 `timing_s/reward`,轨迹内评分的等待包含在取样链路中,不能靠该阶段计时缺席判断没有算奖励。验证汇总和样本额外信息能帮助核分;默认代码分流已丢掉逐例诊断时,应直接检查沙箱日志。内置 Sandbox Fusion 路径会执行全部测试用例,但连续评分只按前 10 例计算通过率,不是“只执行 10 例”。

**典型配置**均是在已有可运行的训练、数据与模型配置上追加奖励项,不是完整训练命令;卡数只表示资源规模,显存能否容纳所选模型仍需核对。

| 场景 | 奖励项怎么设 | 拿什么换什么 |
|---|---|---|
| 已能运行的单机数学题作业,先核评分格式 | `reward.reward_model.enable=false`、`reward.reward_manager.name=naive`、`reward.num_workers=2`;使用已适配内置规则的数据来源 | 用较低评分并发换容易检查的 CPU 负载与样本结果 |
| 单机 8 卡中复用训练资源做 DisRM,模型需能在所选并行布局下运行 | `reward.reward_model.enable=true`、`reward.reward_model.model_path=<判别式奖励模型目录>`、`reward.reward_model.rollout.name=vllm`、`reward.reward_model.enable_resource_pool=false`、`reward.reward_model.rollout.tensor_model_parallel_size=2` | 用串行评分与显存交接换不额外分配奖励 GPU |
| 代码任务,已有可访问的 Sandbox Fusion 服务 | `reward.reward_model.enable=false`、`reward.num_workers=2`、`reward.sandbox_fusion.url=<服务的代码执行地址>`、`reward.sandbox_fusion.max_concurrent=8`、`reward.sandbox_fusion.memory_limit_mb=1024` | 用较低请求并发换可控服务压力;并发限制按 Worker 分别生效 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 自定义函数明明配置了,模型分数却没有参与 | 函数是否主动调用 `reward_router_address` | 自定义函数优先,模型启用不会自动把两路分数相加;在函数中明确组合 |
| 独立内置 DisRM 报 `KeyError: reward_extra_info` | `compute_score_disrm` 只返回 `reward_score`,而轨迹内调用直接读取额外字段 | 这是本基准的字段契约缺口;核修复或自定义包装,不要当作 GPU 不足反复扩容 |
| 沙箱返回错误,训练却只是奖励降低 | API 请求日志、用例格式、代码块是否能抽取 | 默认分流只保留标量;需要追踪失败类型时用自定义函数返回诊断字典 |
| 沙箱并发远超过配置值 | 实际 Reward Worker 数与每个 Worker 的信号量 | 按总服务容量下调 Worker 数或单 Worker 上限,在服务端统一限流 |
| CPU 打分在线程里报错 | 函数是否使用仅主线程可用的机制 | 对同步函数尝试 `reward.reward_manager.name=remote`,同时检查额外 Ray 进程资源 |
| 不知道奖励为何突然全为零 | `data_source`、标准答案格式、函数返回与沙箱服务状态 | 先固定样本逐条核分,不要先改训练算法或加大批次 |
| 奖励模型 HTTP 请求长期不结束 | 路由器及模型服务是否实际返回 | 内置请求使用 `ClientTimeout(total=None)`,重试次数不是端到端超时;在服务或自定义调用中设置可验证的截止时间 |

## 六、常见误区

**看见两套同名 Manager,以为只是目录移动。** 旧 `workers.reward_manager` 保留的是整批 `__call__` 接口,当前加载器取的是 Reward Loop 注册表里的 `run_single` 接口。连旧 `ray_trainer` 在这个基准上也初始化 Reward Loop,所以不能简单按“V1 用新、关闭 V1 就用旧”理解。复制旧 `compute_score_timeout` 或旧构造参数到当前 Manager,不会自动得到那段旧行为。

**以为打开奖励模型就会自动得到生成式裁判。** 这看起来符合“换模型路径就换评分器”的直觉,但内置分支按判别式模型组织请求。生成式裁判的提示词、采样请求与结果解析要写在自定义函数里,函数还要显式使用传入的路由地址。

**以为代码奖励的 0 分就是代码错了。** 默认包装把执行故障与不通过都压进一个标量,连缺代码块也可能直接得到 0。只盯平均分会把服务故障误判成模型退化;先看固定样本的服务日志和测试输入。

**以为配置了沙箱地址,自定义评分就自动受沙箱并发限制。** 默认加载器只在未提供自定义函数时给内置函数绑定沙箱地址和信号量。接管评分函数也接管了调用与限流责任,需要自行实现,不是保留同名配置就够了。
