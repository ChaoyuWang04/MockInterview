# verl 框架总览

源码基准:官方仓库 <https://github.com/verl-project/verl>,分支 `main`,commit `f3d9b56e789c39a06c4b87cc367bae02bac9102b`,最近的发布 tag `v0.8.0`,核对日期 2026-09-20。全篇的「当前」「默认」都指这组基准;带「官方数字」的性能数据来自官方文档,未实测。

## 一、verl 是什么

**verl** 是字节 Seed 团队发起、社区维护的大模型后训练框架,论文《HybridFlow: A Flexible and Efficient RLHF Framework》的开源实现。它要解决的事情和推理引擎完全不同:一次强化学习后训练里,要协调 **Actor**、**Rollout** 与 **Reward**,并按算法需要启用 **Reference** 和 **Critic**。它们可以共享或分开使用 GPU;训练产生的新权重还要交给 Rollout,才能用于后续生成。

它的出发点是把这件事看成**两级数据流**。算法那一层(先生成、再打分、再算优势、再更新)是控制流,神经网络那一层(前向、反向、优化器)是计算流。如果两层逻辑紧密耦合,修改算法时就容易牵动分布式执行细节;而大模型的计算又往往需要多进程协同。verl 的回答是**把两层拆开**:控制流留在**一个** Python 进程里,像写单机脚本一样顺序写;计算流留在多进程 worker 里,由一层分发协议把控制器的一次方法调用摊成多进程的一次协同计算。代价是数据要在控制器与 worker 之间来回,这也正是它后来把数据换成元数据引用的原因。

一句话定位:**verl 把「单控制器写算法、多控制器跑计算」做成了一套后训练框架,并把训练引擎、Rollout 服务和权重传输接起来,支持同步与异步调度,在资源利用和样本新鲜度之间做取舍。**

顶层入口(仓库根 `verl/`):

- `python -m verl.trainer.main_ppo`:本文默认 PPO 训练路径的入口,配置走 Hydra 组合,入口在 `trainer/main_ppo.py`。
- `verl.trainer.main_ppo_v0`:旧入口,已标记弃用并声明在 v0.9.0 移除。**默认不走这条**——默认开关打开时走上面那个入口;三个实验性训练器仍从旧模块里取几个公共函数,所以文件还在。
- `verl.trainer.sft_trainer`:监督微调训练器,本解读不展开。
- `python -m verl.model_merger`:训练结束后把分片权重合回 HF 格式的离线工具。

代码组织上,主体全部在 `verl/`(5373 KB、468 个文件),另有三块体量不小但本解读不涉及的东西:`tests/`(2437 KB)、`docker/` 与 `.github/`(CI 与镜像)、`recipe/`(**是未初始化的子模块,内容不在本仓库**)。从体量看,`verl/` 里工具与适配层占 28%,worker 层 20%,训练循环与算法 17%,实验性的异步与两个 loop 16%,模型接入 8%;**而全篇的核心、那套混合控制器编程模型只有 88 KB**,不到百分之二。


## 二、6 个招牌:先建立全局图景

```text
                单控制器进程:一步 RL 的训练循环顺序写在这里
                生成 → 打分 → 旧概率与参考概率 → 优势 → 更新
                                    │
              [1] 混合控制器:一次方法调用摊成多进程协同计算
                  数据不必回控制器,控制器手里可以只有元数据引用
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
   [6] 两个 loop              [2] 引擎抽象                [4] 放置与显存
   Agent Loop 产出轨迹     训练与生成各有多种后端    各个角色共卡还是分卡
   Reward Loop 组织打分    收成同一组生命周期方法          不上场的先把显存让出来
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    ▼
                  [3] 权重通路:训练侧的切法 → 生成侧的切法
                   逐张量分片契约 + 6 种传输引擎 + 只传变了的部分
                                    │
                                    ▼
                  [5] 同步与异步调度:何时取样、训练、同步权重
                   按资源部署与负载选择,同时约束样本陈旧度
```

一句话记忆:

- **混合控制器**:算法逻辑是一条顺序代码,底下每一步都是多进程协同;由一个装饰器声明「这次调用的数据怎么切给各进程、结果怎么收回来」。
- **引擎抽象**:训练与生成各有统一接口,降低训练循环对具体后端的依赖;实际支持范围由后端决定。
- **权重通路**:训练侧按训练的并行方式切,生成侧按推理的并行方式切,每一步都要重新对齐一次;这是训推交替带来的重要开销,也是最值得优化的一段。
- **放置与显存**:多个角色可以挤在同一批卡上,也可以各占一片;挤在一起就必须有人先让出显存。
- **同步与异步调度**:决定训练和生成何时等待、如何交错或并行,并管理样本陈旧度;收益取决于负载和资源配置。
- **两个 loop**:Agent Loop 把一次生成变成可中断、可调工具的会话;Reward Loop 组织规则与模型打分。二者在 V1 默认路径上承担生成与奖励计算,打分能否重叠还取决于部署方式。

## 四、一步训练怎么串起来

先看默认同步训练的主线。**控制器进程**(单个 Python 进程)从数据集取一批提示词,交给**Agent Loop**;Agent Loop 把提示词提交给**Rollout 副本**,副本背后是推理引擎,多轮任务下 Agent Loop 还会在中间插入工具调用,直到拿回完整轨迹。**Reward Loop** 按配置组织规则、模型或沙箱打分。规则奖励与独立部署的奖励模型可在轨迹处理期间打分;共卡奖励模型则要等 Rollout 让出显存后再运行。

训练侧准备 Actor 的 old logprob,需要 KL 约束时再计算 Reference logprob;需要 Critic 时还要计算 value。控制器据此计算优势,再安排 Critic 与 Actor 更新。Reference 是参考策略,不等于 PPO 更新所用的 old policy。更新完成,**权重通路**把新权重从训练侧的切分方式转成生成侧的切分方式送过去,下一步才敢用新权重生成。

三种 V1 模式主要改变这条主线的调度:同步模式等待本步完成后再开始下一步;共卡异步提前提交任务,通过中断与续接交错使用同一批 GPU(08 章);分卡异步让独立的 Rollout 池持续生成,训练侧从缓冲取样(09 章)。异步模式还要限制样本陈旧度;提交年龄的门禁与轨迹实际使用过的权重版本是两个相关但不同的量。

数据在这个过程里**不一定回控制器**:V1 默认把批数据放进 TransferQueue,跨阶段主要传元数据引用,worker 按引用自取;控制器仍会按需读取张量,用于优势计算与观测。

## 六、怎么调它、怎么看它

各章「调参与观测」只写自己的参数,入口在这里说一次。

**四种入口,一个原则:改了要重新拉起整个作业的都是启动配置。**

| 入口 | 长什么样 | 什么时候用 |
|---|---|---|
| Hydra 主配置 | `trainer/config/ppo_trainer.yaml` 按 defaults 组合出十几个子配置文件 | 定一套固定的实验配置 |
| 命令行覆盖 | 启动命令后面直接追加点分路径等号写法 | 单次实验调某几个值 |
| 配置数据类 | `base_config.py` 派生的一组数据类,字段默认冻结,只有登记过的才可改 | 读代码时查一个字段的真实默认值 |
| Ray 运行时环境变量 | `trainer/constants_ppo.py` 按设备能力拼出来,与入口接收的 Ray 运行环境配置合并 | 绕开特定硬件或通信库的坑 |

`trainer/config/` 下带下划线前缀的几个文件是**组合结果的快照**,不是给人改的;查随包组合默认值可以看快照,本次作业的最终值以启动时解析并打印的配置为准。

观测的三处:训练指标走统一的上报层到 wandb 或 mlflow 等后端;生成侧另有轨迹追踪能力,是否接入需看当前生成路径;跨角色的耗时归因走剖析器体系(见 16 章)。

## 七、阅读顺序

主干是 01 → 02 → 03 → 04 → 05,读完就抓住了 verl 的主线:控制流与计算流怎么分,两侧引擎怎么收编,权重怎么来回。06 与 07 是把这条主线用起来的两件事(卡怎么摆、算法怎么换);08 与 09 分别展开共卡调度与独立生成的异步调度,只在卡利用率成为瓶颈时读,且要按 08 → 09 的顺序;10 到 16 按需查阅。**16 章不重复各章第五节的参数**,它只回答「这一步慢在谁身上」。

**怎么读**:本站把 verl 当训练与 RL 领域的参照系,同领域其他框架的解读都会回指这里。强化学习的算法本身(PPO、GRPO 及其变体、KL 控制、奖励模型)在知识库里各有一篇,**本解读一概不讲算法是什么**,只讲 verl 怎么把它插进去、怎么排布卡、怎么调。每一章都是短页:核心问题、解法、代价、和同类常见做法不一样的地方、调参与观测、常见误区。哪一句想展开,在对话里问。

和推理引擎解读的分工也在这里说清:推理引擎那边关心的是一条请求怎么在显存和算力约束下被服务好;verl 关心的是**一步训练里各个角色怎么使用 GPU,以及它们之间怎么交换权重和数据**。生成阶段 verl 直接用推理引擎,不重写——所以 04 章只写「怎么把引擎当服务用」,引擎内部见 vLLM 与 SGLang 的解读。

## 八、术语表

| 术语 | 一句话 |
|---|---|
| 单控制器 | 算法控制流跑在一个进程里的做法,verl 用它写训练循环 |
| 多控制器 | 计算流由多进程各自执行同一段代码的做法,verl 用它跑前向反向 |
| 混合控制器 | 前两者的组合,verl 的核心编程模型 |
| worker 组 | 控制器与一组远端 worker 之间的代理,一次调用由它摊开 |
| 资源池 | 卡与 worker 进程的绑定关系,决定谁跟谁共卡 |
| 分发模式 | 装饰器上声明的一个枚举值,规定这次调用的数据怎么切、结果怎么收 |
| 协议对象 | 早期的数据载体,把一批样本的张量与非张量字段打包在一起 |
| 元数据批 | V1 跨阶段传递的键与标签,需要计算时再按键读取数据 |
| TransferQueue | 外部依赖包,提供上面那套元数据与数据面;本解读只写 verl 这一侧怎么用 |
| 共卡开关 | V1 分卡异步中决定训练卡上是否也启用 Rollout 副本;同步与共卡异步不读这一开关 |
| 分片导出契约 | 训练引擎向权重通路交付参数的约定,用设备网格加放置方式声明分布 |
| Agent Loop | 把一次生成变成可中断、可调工具的会话的组件,V1 的默认生成路径 |
| Reward Loop | V1 默认奖励计算组件,执行时机取决于奖励类型与资源部署 |
| 三档模式 | 同步、共卡异步、分卡异步,同一个训练器基类下的三个子类,区别在资源部署与调度方式 |
| 一步离策 | 允许训练用的样本来自上一步权重的异步做法 |
| 跳过管理器 | 能把流水线里任意一段跳过的调试开关 |
