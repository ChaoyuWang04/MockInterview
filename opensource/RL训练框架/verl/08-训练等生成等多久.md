# 训练等生成等多久

这一页只处理一步里最不讲道理的那段空等:训练侧停在那儿等最慢的一条轨迹写完,以及把这段等待换成「样本旧一点」之后,能换回什么、要付什么。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一批题目里,绝大多数轨迹早早就写完了,剩下几条还在往下吐 token。**整段生成什么时候结束,由最慢的那一条说了算。** 更难看的是它结束前的那一段:卡还整片占着,上面却只剩零星几条请求在解码,并行度塌下来,算力基本白烧。官方在复现 DAPO 32B 时量过这一段——生成占掉整步的大约 70%,而且加卡压不下去,因为长尾是某一条轨迹自己的长度,不是并行度不够。

训练侧在这段时间里一个字都干不了。它要的是完整的一批:组内比较要凑齐同一题的全部回答,批要按数据并行切匀,少一条都开不了算。

反过来把这条要求放宽,就有机会减少空等:不等这一批全齐,先拿手上够数的那些训。但放宽是有价钱的——拿来训的样本越旧,它描述的越不是当前这个策略,梯度方向就偏;放得太开,曲线直接不涨。

还有一种安排让生成持续推进,训练凑够较小的一批就取走。那是下一章的事。**这一章的问题是,在「训练还要等生成」这一段里,这条线画在哪。**

## 二、解法

这里对照三种调度方式,看它们怎样处理等待与重叠。前两种是 V1 的同步、共卡异步模式,第三种是独立入口的一步离策实验训练器。**它们不是同一个开关的三个档位,也不是按样本年龄依次增大的阶梯**。以下沿用第一、第二、第三种来区分,配置入口见第五节。

**第一种,一步之内什么都不放宽。** 取样一直等到这一批最后一条轨迹落地,然后让 Rollout 副本睡下、把卡交给训练,步末推完新权重再把它叫醒。每条样本都出自上一步刚推过去的那份权重,长尾全额付。

**第二种,同一批卡上让生成提前一批开跑。** 只多做两件事。开训前先额外灌一批题目进去,生成侧手上因此永远有比「这一步要用的那批」更多的活;取样不再等「这一批都完成」,而是等「够一批的题组完成了」——够了就停,把还没写完的那些**当场中断**。中断不等于作废:已经吐出来的 token 和概率原样留着,下一步换完权重、生成恢复,从断点接着往下写。

于是那条长尾不再让整片卡空转:等它的同时,引擎在同一批卡上替下一批干活;而它自己被切成两段,中间跨过了一次换权重。要留意的是,这一档里生成和训练**从来没有真的同时跑**——卡只有一份,靠的是中断与睡醒把两件事在时间上咬得更紧。

**第三种,把生成挪到另一片卡上,用流水线重叠相邻批次。** 它先收回上次发出的生成结果,把当前权重推给生成侧,再立即发出下一批生成,同时训练手上这一批。正常持续更新的稳态下,训练使用上一轮策略生成的样本,因此称为一步离策;首批预热和未更新 Actor 的阶段不套用这个稳态描述。两侧可以真并行,但仍有权重同步、等待上一批结束等边界,不是生成永远不停。

V1 另有提交年龄控制:已完成的题组超限时可丢弃补题;也可在仍有待发或在跑的题组达到阈值时暂停取样,等它们落定。后一种只避免按陈旧度主动淘汰,失败与分组过滤仍可丢弃。严格同步使用另一套取样逻辑,不走这道陈旧度控制。

![三种调度的稳态示意:同步在同一批卡上依次生成与训练;共卡异步提前提交题组,取够后中断并保留前缀,下一步续跑;独立的一步离策训练器让下一批生成与当前批训练在两组卡上重叠。时间段只表示顺序与重叠,不表示真实耗时或三者之间单调递增的陈旧程度。](/opensource/verl/08a-three-clocks.svg)

## 三、代价

**第一笔:长尾没有消失,只是换了地方计价。** 第二种里最慢那条仍然要写完,只是现在跨着步写;它跨的步数越多,这一批样本离当前策略越远。长尾没被消灭,它从「时间」这本账挪到了「新鲜度」那本账上。

**第二笔:一条轨迹的前半段和后半段不是同一个策略写的。** 这和「整条都出自旧权重」是两件不同的事,指标上也分开记。系统这一侧能做的只有把版本跨度记下来;怎么在损失里修正它,是 12 章的事。

**第三笔:V1 的两种异步模式把取题目的粒度压到了一条。** 为了让「淘汰几组就补几组」数得准,一进异步档,数据装载器的取数粒度被强制改成一条题目,用户自己填的值会被一条警告直接覆盖。默认那一批 1024 条题目于是就是 1024 次取数再拼起来,这笔活全落在控制器进程上。

**第四笔:第三种要多划一片卡,而这片卡该多大不好定。** 生成给少了,训练每步开头还得等;给多了,生成侧空转。官方给的判据是把那段等待的计时配上长度分布看:等待长而长度均匀,加卡有用;等待长而长度是长尾,加卡没用,该去动停止条件。

**第五笔:第三种那个循环是纯异步写的。** 一步里每两个阶段之间都插着一次主动让出控制权,为的是让后台那条生成协程有机会推进。代价是这条循环变脆:任何一个阶段在控制器上真正阻塞住,后台的生成就跟着停,而这件事从计时上看不出来。

## 四、同样是让生成跑在前面,三家拧的不是同一个旋钮

三处差异:一处在旋钮的个数上,一处在共卡这个场景里允不允许异步,一处在「让生成跑在前面」这件事被做进了哪一层。

**第一处,这里是两个数,ROLL 那里是一个。** ROLL 用一个浮点数同时决定两件事:调度器按它把在飞的题目数放大,取批时又拿当前步减去它的上取整,当作「最旧能取到哪一步」。所以在 ROLL 里想「多预取一点但别更旧」办不到,两者绑死。这里把它们拆成两个参数,一个管提前量、一个管版本上限,默认值一个是 1、一个是 8。

**第二处,共卡还能不能异步。** ROLL 的 agentic 那条线在共卡分支上直接断言那个比例必须为 0,断言信息把理由写死了:共卡只支持同步、在策;RLVR 那条线不拦,但发现生成和别的角色共用设备时会打一条性能警告。这里的第二种恰恰是专为共卡做的——同一批卡,靠中断与睡醒在时间上错开。

**第三处,重叠做在哪一层。** slime 只有一个训练循环,循环里「要这一批生成结果」那句始终是阻塞的;想让生成跑在前面,换的不是训练器而是**生成函数**——它有一个可替换的函数路径参数,默认那个实现按批收口,换成全异步那个实现之后,后台线程维持一个跨批不散的在飞轨迹池,训练循环本身一行不动。这里反过来:换的是训练器类,生成侧的接口一行不动。相应地,slime 没有以权重版本为单位的上限,只有一个「恢复时先挑旧的」的排序开关;被中断的样本退回缓冲区,还可以把先前那段生成的损失掩码清零,只拿在策那段 token 训。VeRL 的共卡异步保留被打断的前缀,不因续跑就自动掩掉旧段,并记录版本跨度;整组仍可能因陈旧、失败或过滤被淘汰。

![提前生成与样本年龄的控制关系:VeRL 的预热量和版本阈值各管一件事;slime 的在途池控制数量,不提供版本年龄硬界限;ROLL 的提前生成比例同时影响预算与年龄界限。连线表示控制依赖,不以条长比较批次、并发数量和权重版本。](/opensource/verl/08b-one-dial-or-two.svg)

这笔交易 verl 认得很清楚:多一个旋钮意味着多一种配错的方式,换来的是「提前量」和「陈旧度」可以分开调——共卡下提前量受显存约束、陈旧度受算法约束,两条约束本来就不来自同一个地方。

| 指标 | 读法 |
|---|---|
| `timing_s/gen` | V1 两种异步模式下它是「训练侧等一批可训样本等了多久」,不是引擎吞吐;第一种下它还含着副本睡下去的那段(01 章) |
| `training/off_policy/trajectory_spans/{mean,max,min}` | 一条轨迹是几个权重版本接力写出来的;第一种下恒为 1,第二种下大于 1 是常态 |

| `training/off_policy/trajectory_staleness_worst/{mean,max,min}` | 按最旧版本算的滞后,与上一条一起圈出这批样本的年龄区间 |
| `training/off_policy/evicted_samples` · `.../evicted_samples_staleness/{mean,max,min}` | 因超龄被丢掉几组、这些组多旧;只有超龄这一种理由会产出年龄数 |
| `training/rollout_failure/evicted_samples` · `training/filter_groups/evicted_samples` | 另外两种淘汰理由各丢了几组;三种理由取并集,一组只被丢一次 |
| `timing_s/generate_async`(第三种) | 后台那条生成协程从发出到收回的墙上时间,可能与训练阶段重叠,不是纯引擎计算耗时 |
| `timing_s/sync_rollout_weights` · `timing_s/update_weights`(第三种) | 一步开头推权重那一下,内外两层计时 |

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 先把链路跑通、确认算法接对了 | 保持默认的第一种 | 用吞吐换「样本一定出自最新权重」,出问题时能先排除掉离策这条因素 |
| 共卡,生成被长尾拖住 | `trainer.v1.trainer_mode=colocate_async`,预热批次与采样上限都保持默认 | 用样本新鲜度换卡利用率;轨迹开始跨版本,得同时盯跨度指标 |
| 共卡且长尾很重,愿意再放宽 | 同上,把 `trainer.v1.colocate_async.num_warmup_batches` 提到 `1.5` 到 `2` | 用更旧的样本换更小的空等;在飞请求变多,KV 缓存压力同步上升 |
| 卡够多,愿意专门划一片给生成 | 换第三种的入口模块与配置文件,按 `rollout.n_gpus_per_node` 与 `trainer.n_gpus_per_node` 切分,并显式 `actor_rollout_ref.hybrid_engine=false` | 用一片卡换真并行;正常更新的稳态下按一步离策流水线运行,不使用 V1 的采样阈值 |
| 希望保留耗时较长的在途题组 | V1 共卡或分卡异步,`trainer.v1.sampler.max_off_policy_strategy=wait` | 用等待避免陈旧度淘汰,不保证失败或无信号的题组也被保留 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 换到第二种后取样计时没下来 | 预热批次是几 | 它决定生成侧手上有多少「下一批」的活;是 1 时长尾期间能并行的额外请求就只有一批,把它提到 1.5 或 2 再看 |
| 提前生成的题组频繁被丢弃 | 超龄计数、预热量与版本阈值 | 上一步提交的题组本步提交年龄已是 2;阈值过小会抵消预热收益,先让提前量与年龄界限匹配 |
| 轨迹跨度指标持续走高 | 是不是同一批题目反复被中断 | 每步中断是这一档的常态;跨度一直涨说明长尾轨迹始终写不完,该去看停止条件与最大回答长度 |
| 第三种一启动就断言失败 | 共卡那个开关有没有显式置假 | 这一档在训练器构造时就断言它为假,而那份配置文件里并没有替你写死它 |
| 第三种里生成那个计时大得离谱 | 它和取样计时的比值 | 前者是后台请求的墙上时间,可能与训练重叠;未能隐藏的等待应结合取样计时看 |
| 取样一直不返回,日志只剩一行状态计数 | 那行里待发、在跑、已完成、失败四个数 | 已完成长期不涨是生成侧卡住;失败在涨要去看 Agent Loop 的报错 |

## 六、常见误区

**以为换到第二种就得顺手把版本阈值也调小。** 预热量决定提前安排多少活,年龄阈值决定愿意接受多旧的题组,两者需要一起看。上一步提交的题组到本步,提交年龄已是 2;阈值设成 1 会淘汰其中已经完成的旧组,再补新题,削弱提前生成的收益。但新补的题组可以在当前步完成,不能据此断言作业必然原地打转。

**以为第一种下那两个采样上限也在起作用。** 阈值和策略两个参数写在全局配置里,看上去与档位无关。实际上第一种用的是另一个取样实现,它的淘汰理由里根本没有「超龄」这一项,策略那个参数在它身上是彻底的空操作,类注释里写明了这一点。想在第一种下「稍微放宽一点」做不到——它的在策是结构性的,要放宽只能换档。

**以为小数预热批次会被地板成整批。** 配置注释和函数注释都写着「小数部分会向下取整到整数个取数块」,还举了 1.5 批变成一批加半批的例子,读起来像是分数会丢精度。但V1 两种异步模式一启动就把取数粒度强制改成一条题目,那个取整的分母于是是 1,小数批次可细化到整数道题,不会直接丢掉半批;最终题数仍需取整。

**以为第二种和第三种是同一件事的两种写法。** 不是。第二种在同一批卡上,靠中断和睡醒把两件事咬紧,生成和训练从不真的同时跑,省下来的是长尾那段空转;第三种在两片卡上,生成和训练真并行,省下来的是整段生成。把它们混成一件事,就会指望第二种也能把整段生成藏掉,然后对着没怎么变的一步时长发愁。

**照着文档里那个等待计时的名字去面板里找。** 第三种的说明文档反复提到一个「等上一批生成」的计时名,还把整步时间拆成了它加上几段;那个名字在基准代码里一处都搜不到,实际记下来的仍然是取样那一段的通用名。指标名要以代码为准。

**照抄文档里那一档的启动命令。** 它的说明文档和它自己的 README 写的启动模块名带着一个异步前缀,而仓库里的模块没有这个前缀;同目录下的示例脚本用的才是对的那个。

**以为第三种支持所有算法。** 它的 README 列了七个能用的优势估计,读起来像是一张受支持清单。代码里找不到任何对应的校验点:填一个不在表上的名字既不报错也不告警,只是没人替你保证它对。那一档随包的 13 个示例脚本全部用的是同一个估计器。

**把第三种方式的后台生成计时当成纯引擎耗时。** 它从协程发出请求到收回结果计时,期间可能与训练重叠,也受控制器调度影响。它不能直接当作引擎计算时间;训练还等了多久,要结合取样计时看。
