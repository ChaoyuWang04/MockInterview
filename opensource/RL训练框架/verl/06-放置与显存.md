# 放置与显存:共卡还是分卡

这一页回答一件事:Actor、Rollout 与按需启用的 Critic、Reference 如何共享 GPU,挤在一起之后那张卡的显存该归谁、谁在什么时刻让出。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

启用相应角色时,有四类显存需求,吃法各不相同:Actor 要装参数、梯度和优化器状态三份,其中优化器状态那份通常比参数本身还大;Critic 一模一样再来三份;Reference 只要一份参数;Rollout 副本要一份权重外加一池 KV 缓存。

**各占一片卡是最干净的摆法,代价直接写在账上。** 官方的最小资源表里,7B 模型跑 GRPO——一个连 Critic 都不需要的算法——的下限是 2 张 H800,而那已经是把省显存的手段全开之后的数;32B 的下限是 8 张 H20。再给每个角色单划一片,一台机器就排不下了。在串行的训练—生成安排下,各自独占 GPU 还会产生阶段性空闲;异步重叠则能缓解这一点。

**挤在一起,必须给阶段重叠留余量。** 参数和优化器 offload 默认关闭时,Actor 的这部分状态长期占用 GPU;Rollout 起服务时也要依据显存预算分配权重与 KV cache。训练激活、权重导出和传输缓冲还会临时占空间。因此既要过启动时的容量检查,也要核对训练与换权重阶段的峰值。

**第二个麻烦在换手那一刻。** 一步训练的末尾要把新权重推给生成侧:副本得先醒过来接,训练侧刚跑完更新、分配器手里还攥着一堆没归还的块,两边撞在同一瞬间。这段时间既不属于生成、也不属于更新,任何一段计算的耗时与显存指标都量不到它。

所以真问题是两件:谁跟谁挤,以及挤在一起之后谁在什么时刻让出多少。

## 二、解法

分开看。

**谁跟谁挤,由一张池子表决定。** 起作业时先声明若干个资源池,每个池写成「几台机器、每台几张卡」;再把每个角色登记到一个池名上。落在同一个池里的训练侧角色会被合成成一个类:每张卡起一个进程,进程里装着这些角色各自的对象;控制器手里拿到的是几个只露出各自方法的代理,底下是同一批进程。**默认路径上只声明一个池,凡是要建的训练侧角色登记的都是它**——Actor 和生成副本本来就是同一个角色对象,Critic 在用 GAE 时建,Reference 在用到 KL 时才建,但不论建几个,填的都是同一个池名。全员共卡不是某个开关的结果,是池子表本来就这么写的。

为什么要挤,官方文档给的两条理由都不是省卡:Actor 和生成侧挤在一起,是为了换权重能在进程内直通,不必绕一圈网络;Actor 和 Reference 挤在一起,是为了低秩适配那条路——那时候 Reference 就是 Actor 的底座,本来就是同一份参数,再占一片卡纯属浪费。

能搬出去的只有两个角色:奖励模型和蒸馏用的教师模型,它们各自有一组「几台机器、每台几张卡」的字段,填了就单开一个池。Actor、Critic、Reference 没有这种字段,**想让 Critic 占另外几张卡,当前的配置里没有这句话可说**。

**什么时候让,由训练引擎上下文与 Rollout 生命周期共同安排。** 训练引擎这一侧,每个角色上场时进一个上下文:进去按各自的开关把参数、梯度缓冲、优化器状态搬上卡,出来再搬回主机内存。生成这一侧由控制器通过生命周期钩子安排副本睡眠与权重更新,具体见 04 章。**这里最容易读反的一点是:上下文永远在,搬不搬由开关定,而那两个开关默认都是关的**——于是一进一出全是空转,共卡下真正每步在腾挪的只有生成副本。Reference 的 FSDP 前向路径另有 CPU offload 策略,该引擎在包并行的时候被强制成参数常驻主机内存,按层取用。

**换手那一刻是排好序的。** 步末换权重依次做四件事:先只唤醒副本的权重、推完新权重、训练侧把参数卸回内存(这一步同样看开关,关着就是空转)、全部 rank 到齐之后才唤醒 KV 缓存。四件事前后一共打五条显存读数,**推权重期间要特别关注训练参数、导出缓冲与 Rollout 权重的重叠**;具体驻留取决于训练后端和卸载配置。开关关着时训练参数仍常驻,但不代表峰值已在启动时定死,导出和传输的临时分配仍可能导致显存不足。源码注释把全体等待那一步的理由写得很直白:只同步自己这张卡不够,得等所有 rank 都卸完,否则先醒过来的那一侧会把别人的卡撑爆。

还有两处不显眼的让法。一是反向要用的中间结果:有个开关把每一层前向算出的激活搬去主机内存、反向前再搬回来,卡上一次只留两组,和梯度检查点配着用能把每卡微批开大一截;它只在分片数据并行那一路有读取点,别的后端要么另有一档自己的异步版本,要么根本不看这个开关——开了既不生效也不报错。二是启动那一下:训练引擎建好之后会主动把分配器缓存着的空闲显存还给设备,因为同卡上的推理引擎是按驱动报的空闲量去算 KV 缓存能开多大的,缓存不还回去,它看到的数就是错的。

## 三、代价

**第一笔:Ray 的卡账和显存账是两本账。** 每个 worker 进程只向 Ray 申请三分之一张卡,一张卡上因此可以合法地放三个进程——Ray 只管这个数字够不够,不看谁占了多少显存。资源检查也只在启动时比一次「集群一共多少卡、你一共要多少卡」;过了这一关,后面所有的显存不足都不在它的视野里。

**第二笔:池子放不下时是静默挂住。** 放置组按「一个池一台机器一组、组内所有卡必须在同一台机器上」去申请,申请不到就一直等,没有超时,也没有周期性日志。作业看起来在启动,实际上卡死在这里。

**第三笔:让出显存的代价是双向搬运。** 训练侧的办法是把张量拷回主机内存,不是把地址解绑。每个阶段进出各一趟,卡越多、模型越大,这笔带宽就越显眼;而且主机内存得装得下,启用了卸载的参数或优化器状态都需要主机内存承接。**这也是它默认关着的原因**:关着换来的是训练侧不用搬,代价是生成侧只能在剩下的空间里过日子。

**第四笔:卡的编号绑在节点上。** 放置组按节点地址排过序,为的是同一套机器重启之后每张卡的序号还和上次一样,本地写下的分片存档才对得上。换一批机器、或者节点数变了,这个前提就没了。

**第五笔:共卡把奖励模型挤到了采样之后。** 奖励模型不单开池时,它和训练挤在同一批卡上,只能等采样结束、卡腾出来才轮到它算分;想让打分和生成重叠着跑,就得给它单独划一片卡。

## 四、同样是共卡,三家把话说在了不同的地方

对照面还是智谱系的 slime 与阿里的 ROLL,这两个仓库本站已克隆,下面每一条关于放置与让出显存的说法都在它们树上核过(核对日期 2026-09-20)。

1. **共卡是怎么说出口的。** verl 说的是池名:声明几个池,每个角色登记到一个池上,同名就是共卡;默认只声明一个池,所有角色都在里面。slime 说的是一个布尔开关:全部卡排成一条,生成侧从某个偏移量开始,开了共卡偏移量就是 0、总卡数取训练与生成的较大者,关了就把两段首尾接起来;Critic没有自己的位置,永远跟着 Actor 那一段。ROLL 说的是卡号:每个角色直接写一串 GPU 序号,两个角色的序号有交集就算共卡,子集关系还会被单独识别成「部分共卡」再走一套额外校验,连总共要几台机器都是从最大的那个序号反推出来的。**三家的表达力刚好排成一条线**,verl 在中间:比一个布尔开关灵活,但说不出「Critic 放 4 到 7 号卡」这种话。

2. **训练参数的装卸由谁安排。** ROLL 把卸载与装载做成了控制器能直接调的集群方法,流水线在换权重前后一句句显式地调,还能点名只卸模型参数、只卸优化器状态,甚至只卸某几个数据并行分身。verl 把时机藏在引擎上下场的上下文里;控制器那一侧虽然也留了一个注明「手动控制装载与卸载」的方法,但默认训练器一次都没调过。好处是每个阶段不会忘记让出,坏处是想让某个阶段例外,只能往数据里塞一个标志带下去。

3. **让出的方式不是同一种。** verl 和 ROLL 都是把张量拷回主机内存,ROLL 还用上了锁页内存;slime 训练侧调用 Torch Memory Saver 的暂停与恢复接口,并配合通信组的拆除与重建。仅从调用方不能推出它完全不拷贝。slime 还多一档最狠的:把训练进程整个杀掉、下一次训练前再建回来,前提是权重同步走磁盘并且每步都存档。verl 树上没有任何杀 worker 的路径,进程一次建好就活到作业结束。

![三家按资源放置、Critic 独立放置、训练参数装卸时机与内存管理方式比较;VeRL 的训练 Engine 上下文按配置装卸,Rollout 的睡眠与权重更新仍由控制器显式安排。](/opensource/verl/06c-three-ways-to-say-it.svg)

## 五、调参与观测

**这一页的参数全是启动配置**,改了要重新拉起整个作业。

**池子怎么划。**

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `trainer.nnodes` · `trainer.n_gpus_per_node` | `1` · `8` | 全局池的形状,训练侧角色都在这个池里;它同时是吞吐指标的分母 | 启动时创建了几个池、各多大 |
| `actor_rollout_ref.hybrid_engine` | `true` | **只有分卡异步档读它**:置假则训练卡上不起生成副本,生成全部由独占池供给。同步档与共卡异步档根本不读这一项,置假没有任何效果 | 分卡异步档会打一条「hybrid replicas disabled」 |
| `actor_rollout_ref.rollout.nnodes` · `.n_gpus_per_node` | `0` · 跟随训练侧的每节点卡数 | 独占生成池的形状。分卡异步档要求两项都大于 0,其余档位不读 | 服务管理器打印的地址清单长度 |
| `reward.reward_model.enable_resource_pool` | `false` | 置真则奖励模型另开一个池,打分能和生成重叠;为假时它和训练挤在同一批卡上,只能等采样结束再算 | 启动时创建了几个池 |
| `reward.reward_model.nnodes` · `.n_gpus_per_node` | `0` · `8` | 上一项为真时两项必须都大于 0;为假时这两项会被就地改写成训练侧的值 | 启动即报 |
| `distillation.nnodes` · `.n_gpus_per_node` | `0` · `8` | 开了蒸馏时教师模型独占的池,两项都要大于 0 | 同上 |

**让出什么。** 参数与优化器状态那两个开关按后端各有一份,字段名在 03 章的后端配置表里;这里只列跨后端共有的、以及决定显存怎么分的那几个。

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `actor_rollout_ref.rollout.gpu_memory_utilization` | `0.5` | 生成侧起服务时一次圈走多少,圈完就不再变。共卡下它和训练侧常驻的那一摞是此消彼长的;同一个数在三个后端上填进三个定义不同的旋钮,见误区 | 引擎启动日志里的 KV 缓存块数 |
| `actor_rollout_ref.model.enable_activation_offload` | `false` | 真:前向算出的激活搬去主机内存、反向前再搬回,每卡微批能开更大,换一段搬运时间。只有分片数据并行那一路实现了它,分片层数少于 3 时打一条警告后直接放弃 | `actor/perf/max_memory_allocated_gb` 的峰值降下来 |
| `critic.model.enable_activation_offload` | `false` | 同上,Critic 那一份 | `critic/perf/max_memory_allocated_gb` 的峰值降下来 |
| `actor_rollout_ref.actor.veomni.enable_async_activation_offload` | `false` | VeOmni 后端唯一支持的激活搬运档,搬运和计算重叠;上面那个同步开关在这条路上没有读取点 | 打印出来的完整配置 |
| `actor_rollout_ref.model.enable_gradient_checkpointing` | `true` | 关掉会把激活全留在卡上;它和激活搬运是配着用的,两个同时开时会换成兼容的那一版重计算 | 同一组显存读数 |
| `VERL_LOGGING_LEVEL` | 相关模块取 `WARN` | 设成 `DEBUG` 才看得见换权重那五条显存读数 | 日志行 |

**观测点有四处。**

第一处是换手的五条读数,按顺序是 `Before resume weights`、`After resume weights`、`After update_weights`、`After offload model to cpu`、`After resume kv_cache`。**这是观察两边交接的一组直接读数**,而它是 `DEBUG` 级、并且只有 0 号 rank 打。每条同时给四个数:PyTorch 的已分配与已保留,外加驱动报的设备已用与总量。**共卡下要看的是后面那一对**——副本睡下释放的显存在 PyTorch 的计数器里根本不出现,源码里那个取数函数专门多取一次驱动的数,注释写明的理由就是这个。

第二处是建模时的一串:`After init model from HF AutoModel`、`Before FSDP`、`After FSDP`、`After offload model/optimizer/grad during init`。中间那两条不走 logger、直接打到标准输出,所以日志级别没开也看得见。最后那一条是引擎起服务前卡上的最后一个读数,**推理引擎就是在这之后去量空闲显存的**;想知道生成侧到底能拿到多少,看这一条比看配置里的比例准。

第三处是吞吐:`perf/throughput` 是每秒每卡多少 token,分母取池子表里声明的卡数。**奖励池和教师池的卡算在分母里**(它们并不训练),而独占生成池的卡不算——分卡异步档自己把这部分加了回去,别的档位没有这个池。跨配置比这个数之前先确认分母。

第四处是显存快照:剖析器能按窗口把分配器的历史落成文件,用 PyTorch 官方的可视化页面打开看是谁占着;剖析器本身归 16 章。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡,先把链路跑通 | 全默认的一个池、全员共卡;把 `actor_rollout_ref.rollout.gpu_memory_utilization` 压到 `0.4`–`0.5` | 用生成并发换训练侧不被挤爆,也便于先从读数上看清各角色各占多少 |
| 单机 8 卡,模型偏大 | 上一套之上打开 Actor 的参数与优化器 offload(字段见 03 章),再把 `actor_rollout_ref.model.enable_activation_offload` 与梯度检查点一起打开,并把生成侧的比例回调到 `0.6`–`0.7` | 用每步几趟主机内存搬运换显存;主机内存要留够三份状态的位置 |
| 卡够多,想让打分不再排在采样后面 | `reward.reward_model.enable_resource_pool=true`,并给 `reward.reward_model.nnodes` 与 `.n_gpus_per_node` 填上独立的机器数与卡数 | 多要一片卡,换奖励计算和生成重叠 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动后长时间没有任何日志,也不报错 | 集群里空闲的卡够不够填满一整个池 | 放置组申请不到会一直等,没有超时也没有周期日志;去 Ray 的状态里看有没有挂着的放置组 |
| 报「可用卡数小于需要的卡数」 | 几个池加起来要多少 | 独占生成池不在这次检查里——它是作业跑起来之后才建的,所以这一关过了也可能后面还是不够 |
| 推理引擎起不来,说显存不够 | 建模那一串的最后一条读数 | 参数搬运开关关着时训练侧一直在卡上,引擎是在它后面才去量空闲显存的;先降生成侧的比例,或者打开参数 offload |
| 换权重那一刻显存不足 | 第二条与第三条读数之间发生了什么 | 检查训练参数、导出/传输缓冲与 Rollout 权重的重叠;开关关着也可能在这里出现额外峰值 |
| 0 号卡的读数看着还有余量,别的卡却炸了 | 显存读数只有 0 号 rank 打 | 它不代表全组;换手那一步专门加了一次全体等待,就是为了这个 |
| 调了 Critic 的搬运开关,Actor 那边的显存纹丝不动 | 分别观察角色引擎与整卡占用 | 两个角色共用进程但配置独立;卸载 Critic 不会卸载 Actor,却可以降低整张卡的总占用 |
| 两次实验的吞吐没法横着比 | 分母各自算了哪些卡 | 分母是池子表里声明的卡数,奖励池与教师池算在内、独占生成池不算 |

## 六、常见误区

**以为共卡下训练侧每步都在让显存。** 引擎上下场的上下文一进一出确实各有一次搬运,看代码很容易以为每个阶段都在腾挪。但那两个开关默认都是关的,这时上下文里的判断直接返回,搬运一次都不发生;换权重路径里那一步「把参数卸回内存」同样带着开关,关着就是空转。**共卡省下来的是生成侧那一份,不是训练侧那一份**——训练侧从作业起来占到作业结束,生成侧只能在剩下的空间里起服务。

**以为把共卡那个开关置假就能分卡。** 它默认为真,名字也像个总开关。实际上默认的同步档和共卡异步档根本不读它;只有分卡异步档读一次,用来决定训练卡上要不要起生成副本;三个实验性训练器反过来断言它必须为假;旧入口那条路则断言它必须为真。同一个字段在四个地方有四种读法,照着它去推「我这次是共卡还是分卡」必错——看启动时到底创建了几个池。

**以为 Actor 和 Critic 是两组进程。** 控制器手里确实是两个 worker 组对象,各有各的方法名。但默认路径上它们登记的是同一个池,合成之后是同一批 Ray 进程,两个组对象只是同一批进程的两个视角。因此两个角色占用要相加,但卸载开关仍各自生效:卸载 Critic 能减少整卡占用,并不等于卸载了 Actor。

**以为 Ray 报告卡还没占满就说明还有显存。** 每个 worker 进程只申请三分之一张卡,这个分数是写死的,不是按显存算出来的。Ray 的账只保证「一张卡上不超过三个进程」,一个进程占 70 GB 还是 7 GB 它一概不知。共卡下判断还剩多少,只能看显存读数里驱动报的那一对数。

**以为 PyTorch 的显存计数器能看出共卡的账。** 看不出。副本睡下释放的那部分是在 PyTorch 的分配器底下做的,已分配和已保留这两个数一点不动。源码里那个取数函数专门多取一次驱动报的设备已用与总量,注释直接写明原因就是这个。拿训练侧上报的那几个内存指标去估共卡余量,会把生成侧那一整份当成不存在。

**以为生成侧那个显存比例在三个后端上是同一个意思。** 同一个配置项,填给 vLLM 的是「占设备总量的比例」,填给 SGLang 的是「静态显存占空闲显存的比例」,填给 TensorRT-LLM 的是「空闲显存的比例」——三个旋钮的基准各不相同。在一个后端上调顺手的值换个后端可能直接撑爆,而这不是文档没写清楚,是代码里就把同一个数分别映射到了三个名字不同的参数上。

**以为激活搬运那个开关对所有后端都管用。** 它挂在模型那一段配置上,看着是全局的。真正读它的只有分片数据并行那一路的引擎;VeOmni 另有一档自己的异步版本,其余后端一个读取点都没有。在它们身上把这个开关打开,既不生效也不报错——配置注释里写的「会被拒」并不存在,代码里找不到那个拒绝点。判断一个搬运开关管不管用,只能去对应后端的引擎里找读取点。

**以为奖励模型默认自己有卡。** 它的配置里明明白白给了机器数和每节点卡数两个字段,看着就像它自带一片。实际上那两个字段只在另开池的开关打开时才被读;开关默认是关的,这时它们会被就地改写成训练侧的值,奖励模型和训练挤在同一批卡上——而且只能等采样结束才轮到它算分。

**以为给 worker 塞环境变量有个配置入口。** worker 组确实接受一个自定义环境变量的参数,官方自己的示例脚本里也有一行往它上面写分配器配置。但没有任何训练器从配置里读这一项,那一行是空转的。要改分配器行为只能在拉起作业的那个环境里设;而且换权重那一段会先把可扩展显存段关掉、做完再打开,所以这一项的最终状态由代码定,不由你设的那个变量定。
