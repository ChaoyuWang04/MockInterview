# 多轮会话与工具调用

这一页回答一件事:一条轨迹要「说一段、调个工具、把结果接上再说一段」,而且每条走几个来回还不一定,这个循环该由谁写、写在哪一层。说法都在源码基准 `f3d9b56e78`(tag `v0.8.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

生成那一侧已经是一组按请求收活的服务了(04 章)。但服务只认一件事:给我一段输入,还你一段输出。agentic 任务要的不是这个,是一条来回——模型说一段,工具做一下,结果接回去再说一段,直到它自己不想说了为止。**说几个来回由模型当场决定**,同一批题目里有的一轮就收,有的来回十几次。

把这件事写成一次批量调用,轮数不齐就只剩两种摆法,而且都坏。

**一种是按轮对齐**:每一轮都等整批走完,再一起进下一轮。整批的时长于是变成「每一轮里最慢那条」加起来,而不是「每条自己那一串」里最长的那个。轮数越不齐,这两个数差得越远;早早收尾的那些轨迹,在后面每一轮里都在陪跑。

**另一种是在调用内部自己再实现一遍调度**:等于把一个带状态的循环塞进一个本来只该返回张量的函数里,而这个循环还要负责执行工具。工具是 CPU 上的等待——发个请求、跑个沙箱、查个库——它本来可以和别人的生成互相盖住,塞进同一次批调用里就盖不住了。

还有第三件更硬的:批量调用只有一个返回值,**最后一条不回来,前面的都不算数**。一条轨迹明明早就跑完了,却要跟着整批一起等,才能去打分、才能进训练队列。

## 二、解法

**一条轨迹一个协程,循环就写在协程里。**

每个协程是一个小状态机:准备好提示 → 发一轮生成 → 看看有没有工具调用 → 有就去执行、把结果接回上下文、回到生成 → 没有就终止。一个会话进程里同时跑着一批这样的协程,各自推进各自的状态,谁也不等谁;默认起八个这样的进程,轮流落在集群的各个节点上。谁先走完谁先交卷。

![三条轨迹各走各的轮数的示意图:上半部分每条轨迹都是模型生成与工具执行交替的一串色块,三条的段数与长度都不同,完成时刻也不同,各自单独写进数据队列;下半部分是同一组轨迹在按轮对齐时的样子,每一轮结束都有一道关卡,先做完的必须停下来陪跑,整批要到明显更晚的时刻才算完。](/opensource/verl/10a-turns-not-aligned.svg)

**一轮就是一次请求。** 循环用的就是 04 章那个按请求走的调用面,一轮调一次。一条轨迹从头到尾用同一个请求编号,路由会尽量把后续轮次派回原服务器,以复用前缀缓存;服务器或路由状态变化时不保证仍落在原处;而对引擎来说,每一轮是一次相互独立的请求。

**怎么让它停在工具调用那儿。** 每个模型族吐工具调用的写法不一样,所以解析这件事是一套按模型族分开的东西,当前随包带了九套。它除了负责把文本解析成函数名加参数,还声明「哪些 token 一出现就该停」——自己会吐结束符的模型族不用额外声明,不会的就得靠这个;循环把这些 token 塞进这一轮的采样参数,模型吐完一次工具调用就停住,不会自顾自往下编工具的返回结果。

**工具分两种契约。** 一种是有生命周期的类:建一个实例、执行、释放,可以带每条轨迹自己的状态,也可以顺手给一个分数;另一种就是一个普通 Python 函数,它对外的接口描述由框架从函数签名和文档串自动推出来,不用另写一份。两种都按名字装进会话进程,跨来源撞名直接报错。一轮里可以同时发出去好几个工具调用,但默认只执行第一个。

**接回上下文的那一下才是关键。** 最省事的写法是把最终那份消息列表重新套一遍模板拿 token,但这条路走不通:解析器会把工具调用从模型正文里挑出来、放进结构化字段,再套回去得到的 token 和模型当时真吐的那一串不是同一串,而仓库自己的文档写明,这种偏差在单轮上就足以让训练不收敛。所以这里只渲染新增的那几条消息,增量地并进已有的 token 流——基础实现直接拼接;需要处理边界的模型族会先撤掉重复的分界 token,或在接缝里补上边界 token。

并的同时要维护一条掩码:模型自己吐的 token 记 1,工具塞回来的、模板补进去的一律记 0。**这条掩码就是训练时算不算损失的依据**,也是这里把多轮推理轨迹用于训练时的一项关键约束。掩码旁边还并排躺着一条 logprob,三样东西必须在每个接缝上同步改。

![需要边界修正的模型族的一次合并示例,不是所有模型统一执行的步骤:合并前是提示、上一轮模型生成的 token,以及结尾那个将被撤掉的分界 token;合并后撤掉了那个分界 token,接上补的边界 token、工具消息渲染出来的 token 和下一轮的生成提示,下方的掩码行与 token 行一格对一格,只有模型自己生成的那一段记 1。](/opensource/verl/10b-merge-point.svg)

**交卷不是返回值。** 一条轨迹跑完就自己写进 TransferQueue,键是题目编号加会话号加序号;题目那一级另有一个状态标记,要等它底下所有会话都落定才写终态。训练侧看到的于是是一批陆续到齐的键,不是一个一起返回的批——怎么按键取数是 02 章的事。

**打分和生成重叠也在这儿接线。** 会话循环手里握着奖励 worker 的句柄,一条轨迹生成完成就直接发过去打分,分数跟着这条轨迹一起落库,而别人还在生成。但句柄不是永远有:只有打分确实能和生成并行——用规则奖励,或者奖励模型分到了自己的资源池——它才非空;奖励模型和训练挤同一批卡时它是空的,打分退回到取样之后由训练器统一做。具体评分与独立内置 DisRM 的结果字段边界见 11 章,这一层只负责递交数据并接回结果。

**整层都能换掉。** 一条样本走哪套循环,由数据集里的一列名字决定,名字去注册表里取类;注册表除了随包的两套(一问一答的、带工具的),还能从一份配置按名字追加自定义的。更彻底一点,管理整批轨迹的那个管理器本身也能按类的全限定名整个换成别人的 agent 框架,官方对自定义管理器只提两条要求:生成方法不许阻塞,产出放进 TransferQueue。

## 三、代价

**第一笔是拼 token 的账全记在这一层。** 每个接缝上有三种编辑——撤掉几个、补进几个、追加几个——而 token、掩码、logprob 三条并排的东西都要跟着同一份编辑改。任何一处错位,训练看到的分布就和生成时不是同一个,而这种错位不会崩、只会让曲线慢慢不对。

**第二笔是长度上限卡在轮与轮之间。** 每一轮重拼出来的提示有上限,超了从左边截掉一段并打一条警告(带图的提示则直接报错,因为占位符和特征必须一一对应);整条轨迹的响应部分也有上限,一旦攒够就立刻终止。于是一条长轨迹很可能停在「工具刚返回、模型还没来得及说话」那一刻,最后一轮是半截的。工具返回的文本本身还有一道更早的闸,默认只留很短一段。

**第三笔是工具跑在会话进程里。** 异步的直接等,函数工具里同步的那些被挪进线程池;一个慢工具占的不只是自己那条轨迹,还占着这个进程的调度余量。工具真正跑在哪台机器上、沙箱怎么隔离、失败怎么重试,这一层一概不管——它只负责把返回值包成一条消息。工具抛异常时也不会中断轨迹,而是把错误文本当成工具的回答塞回去让模型自己看。

**第四笔是一条轨迹可能跨权重版本。** 来回多的那些轨迹,中间赶上一次换权重,前半段就是上一版策略产出的。每条轨迹落库时带着起止两个步号,这两个数不相等就说明它跨过了权重边界;要不要这条轨迹由后面的过滤决定,那是异步档的事(08、09 章)。

## 四、多轮这一层,三家安在了不同的位置

拿智谱系的 slime 与阿里的 ROLL 作对照,两家的仓库本站都已克隆,说法在它们树上核过(核对日期 2026-09-21)。

1. **这一层在不在主路径上。** 这边,会话循环是生成的唯一入口:连一问一答都是一套注册在册的循环,只不过它只跑一轮就收。slime 的核心里没有这一层——随包的生成函数就是发一次 HTTP、收一次结果;要多轮,你替换的是一整个函数(在命令行上给一个 Python 路径,也可以按样本各给各的),循环写在你自己那份代码里。ROLL 则把多轮单列成了一条流水线,和它跑常规可验证奖励的那条并排放着,两条各有各的配置和 worker。
2. **工具在谁的概念里。** 这边有一套自己的工具契约,两种写法都按名字装进进程,工具的返回值被包成一条消息追加进对话。ROLL 也有工具注册表(编号映射到入口点,随包注册了三个),但工具最终被包成一个**环境**——调一次工具就是让环境走一步,工具基类还是从外部那个环境库里拿的。slime 核心里根本没有工具这个概念:工具接口、工具描述结构、工具注册,一样都搜不到;它的 agentic 路线是把现成的编码 agent 命令行原样丢进沙箱跑,自己只在模型 API 那一层做代理,工具属于那个 harness,不属于框架。
3. **谁负责把回答解析成动作。** 这边自带九套按模型族写的解析器,因为同一套循环要在三个推理后端上都成立,不能指望后端替它解析。slime 直接借它唯一那个推理引擎自带的解析器,连工具描述都转成那个引擎的结构再递过去。ROLL 自己写了解析器,但形态是「把回答解析成环境的一个动作」,不是「解析成一次函数调用」——这跟它把工具当环境是同一个选择的两面。

一句话:同样是多轮,这边把它做成了主路径上的一层,slime 把它留给用户自己写的那个函数,ROLL 把它翻译成了环境。

## 五、调参与观测

**这一页的参数全是启动配置**,改了要重新拉起整个作业。下表除注明的两行外,统一省略 `actor_rollout_ref.rollout.` 前缀;标了「要加号」的那一行在随包配置里没有对应条目,只能用 Hydra 的追加写法塞进去。

| 参数 | 默认 | 调了之后哪个指标往哪边变 | 怎么看 |
|---|---|---|---|
| `agent.num_workers` | `8` | 会话进程数。太少则单个进程的事件循环成瓶颈,太多则每个进程分到的协程少、工具等待盖不住生成 | 启动时创建的会话 worker 名字,一个进程一条 |
| `agent.default_agent_loop` | `single_turn_agent` | 数据集里没有那一列名字时,所有样本走哪套循环;改成 `tool_agent` 等于全局切到带工具的那套 | 名字取不到时的断言报错会把注册表里现有的名字全列出来 |
| `agent.agent_loop_config_path` | `null` | 指向一份 YAML(每项写名字加类的全限定名),把自定义循环按名字追加进注册表 | 同上,报错里会多出这些名字 |
| `agent.agent_loop_manager_class` | `null`,**要加号** | 换掉整个管理器,接管这一层;官方只要两条:生成方法不阻塞、产出放进 TransferQueue | 填错时在初始化管理器那一步直接抛导入错误 |
| `multi_turn.format` | `hermes` | 选按哪个模型族解析工具调用、用哪些停止 token;填注册表里没有的名字会报「未知的解析器」 | 起训时的报错 |
| `multi_turn.tool_config_path` | `null` | 一份 YAML,装有生命周期的类工具 | 每个类工具被装上时会把自己的接口描述整条打印出来 |
| `multi_turn.function_tool_path` | `null` | 一个 Python 文件,装用装饰器注册的函数工具;与上一行共存,名字撞了直接报错 | 列出装了哪几个的那条日志是信息级,默认级别看不见;一个装饰器都没找到时打的是警告,默认就看得见 |
| `multi_turn.max_assistant_turns` | `null`(不限) | 模型最多说几次,到了就终止并按当前状态收尾 | 每步的轮数指标 |
| `multi_turn.max_user_turns` | `null`(不限) | 工具结果最多接回去几次 | 同上 |
| `multi_turn.max_parallel_calls` | `1` | 一轮里最多执行几个工具调用;**超出的被直接丢掉,不报错** | 轮数指标与工具段耗时 |
| `multi_turn.max_tool_response_length` | `256` | 工具返回文本的字符上限,超了按下一行的方式截 | 轨迹里工具那一段的长度 |
| `multi_turn.tool_response_truncate_side` | `middle` | 从 `left`、`right` 还是中间截;截掉的位置会留一段省略标记 | 同上 |
| `multi_turn.enable` | `false` | **当前路径一行都不读它**;只有旧入口和另一条异步实现读 | 置真什么也不会发生 |
| `multi_turn.use_inference_chat_template` · `multi_turn.tokenization_sanity_check_mode` · `multi_turn.num_repeat_rollouts` | `false` · `strict` · `null` | 三项都是死配置:唯一读前两项的那个请求结构在基准上没有生产调用点,第三项全树没有读取点 | 调了既不生效也不报错 |
| `prompt_length` · `response_length` | 跟着数据集的两个长度,各 `512` | 前者是每轮重拼后提示的上限,超了从左边截并打警告,带图的提示直接报错;后者是整条轨迹响应部分的上限,攒够就终止 | 警告日志、轮数指标顶不顶着上限 |
| `trace.backend` · `trace.token2text` · `trace.max_samples_per_step_per_worker` | `null` · `false` · `null` | **当前路径上三项都不生效**:每条轨迹都按不追踪发起,限流那段逻辑也在被覆盖掉的方法里 | 追踪后端里一个 span 都没有 |
| `data.return_raw_chat` | `true` | 循环读的是原始消息列表;置假会直接取不到 | 起训时的取值报错 |

**观测点有五处**:

- **轮数分布**:每一步都有轮数的最小、最大、平均三个数,评测步另有一组同名的。看轮数不齐到什么程度,第一眼就看这三个数的差距。注意计数方式:一问一答报的是 2;带工具那套按「模型说的次数 + 工具接回的次数 + 1」算。
- **一条轨迹跨了几步权重**:每条轨迹落库时带着起止两个步号,两个数不等就说明它中途换过权重。
- **每条轨迹的三段耗时**:生成、工具、打分各有一个计时器,挂在轨迹自己身上。**但要当心**:把这些汇成最小、最大、平均并单报最慢那条的那段代码,只在旧管理器里跑;当前默认的那个管理器没有这一步,所以那几个以 `agent_loop/` 开头的汇总指标在默认路径上不出现。
- **工具装没装上**:类工具靠启动时打印出来的接口描述确认;函数工具靠那条警告确认没装空。
- **解析失败**:模型没按格式吐时控制台会打一条解码失败的错误日志,官方明说这不代表训练异常——但它连着出现就说明模型族和解析器选错了。

**典型配置**:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 先把一问一答的链路跑通 | 全默认:`rollout.agent.default_agent_loop=single_turn_agent`,不配任何工具路径 | 用功能换确定性,先确认服务、路由、落库这条链是通的,再谈工具 |
| 数学题里挂一个代码执行工具 | 数据集加一列把这些样本标成带工具的循环;`rollout.multi_turn.tool_config_path` 指到工具 YAML;`rollout.multi_turn.format` 对齐模型族;`rollout.multi_turn.max_assistant_turns=4` | 用轮数上限换一步时长的可预期性;上限压太小会把本来能解出来的轨迹砍在半路 |
| 工具返回很长(检索、日志、栈) | `rollout.multi_turn.max_tool_response_length` 提到 2000–4000;`rollout.multi_turn.tool_response_truncate_side=right`;同时把 `data.max_response_length` 一起放大 | 用上下文长度换信息完整;两个长度不一起调,轨迹会在工具结果刚贴进来时就撞上响应上限 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后**:

| 症状 | 先查 | 然后 |
|---|---|---|
| 起训就报「这套循环没注册」 | 数据集那一列里的名字,和报错里列出的注册表 | 名字拼错,或者自定义循环那份配置的路径没被解析到 |
| 所有样本都只走了一轮 | 数据集里有没有那一列名字,以及全局默认名是什么 | 多轮不是由那个同名开关打开的,它在当前路径上没人读 |
| 轮数最大值总顶着上限 | 两个轮数上限,和响应长度上限 | 先分清是被轮数砍的还是被长度砍的:被长度砍的那些,最后一轮是半截的 |
| 工具明明返回了内容,模型像没看见 | 工具返回的字符上限与截断侧 | 默认只留很短一段且从中间截,头尾保留、中间被截掉;关键内容在中间时仍会丢失 |
| 模型一次吐了好几个工具调用,只有第一个生效 | 一轮里的并行调用上限 | 默认是 1,多出来的被直接丢掉,既不报错也不告诉模型,于是它下一轮很容易重发同样的调用 |
| 打开了追踪后端却什么都看不到 | 当前跑的是哪个管理器 | 默认那条路上每条轨迹都按不追踪发起,追踪装饰器一个都不会触发 |
| 一整组轨迹迟迟不落库 | 这道题底下的会话是不是都结束了 | 题目级的状态标记等所有兄弟会话落定才写终态,有一条卡住就整组不动 |
| 奖励相关的字段全空,而生成正常 | 奖励是不是和训练挤同一批卡 | 那种情况下会话循环手里没有打分句柄,打分退回到取样之后由训练器统一做 |

## 六、常见误区

**以为要把那个多轮开关打开才算多轮。** 名字写得像总开关,配置里默认还是关的,但当前路径上一行都不读它——读它的只有旧入口和另一条异步实现。真正决定一条样本走哪套循环的,是数据集里的那一列名字,取不到才退到全局默认名。人们会这么以为,是因为仓库自己的多轮文档还停在「把多轮置真、后端选那一个」的写法上,而那篇文档里写的那个工具配置键,在当前的配置树里已经找不到对应行了。

**以为轮数就是工具调用次数。** 一问一答报的是 2,不是 1;带工具那套按「模型说的次数加上工具接回的次数再加一」算,所以一次工具调用的轨迹报的是 4。拿这个数去估工具调用量,会高估一倍还多。要看工具真跑了多少,得看工具那一段的耗时。

**以为可以把最终的消息列表重新套一遍模板拿 token。** 这是这一层存在的主要理由之一,不能。解析器会把工具调用从模型正文里挑出来放进结构化字段,再套回去得到的 token 和模型当时真吐的那串对不上;解码再编码这一步本身也会漂。仓库文档写得很直白:这种偏差在单轮上就足以让训练不收敛。所以这里宁可维护一条增量拼起来的 token 流,也不走那条看起来更干净的路。

**以为一轮里能并行调好几个工具。** 确实有这个参数,但默认是 1,而且超出的那些调用是被切片直接丢掉的——不报错,也不会以任何形式告诉模型「你后面那几个我没执行」。模型下一轮只看到第一个工具的结果,于是反复重发同样的调用,轮数指标先顶上限,你却在工具那边查不到任何异常。

**以为工具返回的文本会原样进上下文。** 默认只留 256 个字符,而且默认从中间截,留头留尾中间填一段省略标记。检索结果、代码执行输出、报错栈基本都会被砍。排查「模型为什么总说工具没给它信息」,第一件事是看这个值,不是去看工具本身。

**以为打开追踪后端就能看到每一轮的输入输出。** 追踪的装饰器铺得很全,每套解析器、每次生成、两套循环的入口、类工具的执行入口上都挂了;但当前默认的那条路上,每条轨迹都是按「这条不追踪」发起的,源码里还留着「待补追踪支持」的注记。同一条路上,把每条轨迹耗时汇成最小、最大、平均的那段代码也没人调。想看轮数只能靠轮数指标。

**以为多轮的请求结构就是那套带状态枚举、逐轮自检的模型。** 它确实存在,也确实长得像正主:有状态枚举、有消息对象、有分轮拼 token 之后和整段拼一次比对的自检模式。但在基准上它没有任何生产调用点,全树只有一个测试文件在引用它;连带着那两个看起来很关键的配置项——按推理端模板渲染、分轮拼 token 的一致性自检——也没人读。照它去理解当前的多轮实现,会理解成另一套系统。

**以为会话循环自己会算奖励。** 它确实握着奖励 worker 的句柄,也确实在轨迹生成完成后发过去打分。但句柄只在两种情况下非空:用规则奖励,或者奖励模型分到了自己的资源池。奖励模型和训练挤同一批卡时句柄是空的,这时打分退到取样之后、由训练器把副本睡下再统一做。按「打分总是和生成重叠」去估一步时长,在共卡奖励模型那一档会估少一整段。
