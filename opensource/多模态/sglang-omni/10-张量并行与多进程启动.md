# 张量并行与多进程启动

把一个 Stage 扩成多个 TP rank 后,谁负责让它们一起起来、收到同一份工作,又在启动失败时一起退场——这一章回答这些问题。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

TP 的集合通信要求参与者按相容的顺序进入计算。只把模型拆到多张卡还不够:如果只有接收请求的 rank 开始前向,其他 rank 没拿到工作,先进入集合调用的那个就会等住。此时 GPU 没有报显存不足,进程也还活着,请求却不往前走。

启动也有同样的完整性要求。某个 rank 已经加载完,不代表整个 Stage 能工作;某个 Stage 就绪,也不代表管线能接请求。多进程启动器必须把「已经创建进程」和「整条管线已经可用」分开。

## 二、解法

**先生成每个进程的启动记录,再以全体就绪作为服务边界。** 启动记录包含阶段身份、工厂、设备、rank、通信端点与内部队列。进程组是启动器管理生死的容器,不要把它和底层集合通信使用的进程组混为一谈。非 TP 阶段可以共享一个操作系统进程;TP 阶段则每个 rank 独占一个进程。

子进程根据记录构造 Scheduler 和 Stage,启动通信后才报告就绪。这一步做什么由阶段工厂决定:预处理阶段不必加载生成模型,模型阶段才准备对应的模型和运行资源。默认先拉起同一波里的全部进程,再等待它们就绪;只有启用权重共享产生依赖时,才先起导出权重的一侧及其他无依赖进程,后起引用权重的一侧。权重共享本身的放置与生命周期见 09 章。

运行时,**rank 0 承担这个 TP Stage 的外部控制接口**,Coordinator 注册的是它的端点;其他 rank 从内部队列接收控制消息。关闭、剖析与管理命令由 rank 0 扩散,中止走单独的队列。工作载荷是否也由这一层复制,取决于 Scheduler 是否声明需要:简单调度器需要这份复制,自回归的 OmniScheduler 则在自己的调度循环内广播工作。两条路的目的相同,都是让参与计算的 rank 拿到工作,避免只有一侧进入集合调用。

图里的消息复制是工作入口的配套机制,不代替模型前向中的集合通信。它也不意味着所有数据都经 Coordinator 搬运:阶段之间的载荷传输仍由 04 章的数据面负责。

## 三、代价

**启动时延受最慢的必需进程限制。** 同一波全部就绪前,启动器不会宣布服务可用;同卡的 GPU 工厂构造还会争用启动锁。因此「同波启动」不等于所有模型同时加载,也不能把增加进程数直接当作缩短冷启动的办法。

**工作扩散增加了一层进程间传递。** 需要复制工作载荷的 Scheduler 要经过内部队列,而自回归 Scheduler 有自己的广播路径。接入新 Scheduler 时,选择错这条路径会造成重复分发或缺席计算;这比少传一个普通业务字段更严重,因为错误可能表现为集合调用一直等待。

**失败的清理单位大于单个 rank。** 启动抛错或被取消后,启动器会终止已经拉起的子进程、关闭通道与 Coordinator、删除本次 IPC 目录。运行中检测到子进程死亡,也会把在途请求判失败。这里没有把缺失的 rank 静默剔除后继续执行的语义。

## 四、vLLM-Omni 把并行执行交给哪一层

两边都把「启动后端」和「向整条管线宣告就绪」分开,失败时也要回收已取得的资源。区别在于本章这层管理的对象:本项目显式构造 Stage 的逐 rank 启动记录,再通过内部控制队列补齐阶段语义。

vLLM-Omni 的本地自回归路径由 StageRuntime 启动 Stage EngineCore,使用选出的 executor;扩散路径有专门的副本启动入口。它的扩散分布式层还显式组织 TP、流水线、序列与 CFG 等并行组。这是扩散执行侧的边界,不能把那套组结构直接映射成本项目的 Stage 进程组,也不能据此推导某种语音管线谁更快。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 | 在哪调与默认 | 改变什么 | 怎么看 |
|---|---|---|---|
| `tp_size` | 阶段配置;默认 `1` | 增大时该阶段展开为更多 rank 进程,带来集合通信;模型工厂必须支持 | `Building scheduler for … (tp_rank=…/…)` 是否覆盖全部 rank |
| `gpu` | 阶段配置;通用默认 `None`,模型配置另有放置 | TP 时必须给数量匹配且不重复的 GPU 列表;不匹配会在启动前拒绝 | 配置校验错误、rank 的设备映射日志 |
| `SGLANG_OMNI_STARTUP_TIMEOUT` | 服务启动进程的环境变量;默认 `600` 秒 | 加大允许冷启动更久,也延后真正卡死的暴露;按每个启动波次计时 | `Process … did not become ready` 与后附错误栈 |
| `start(timeout=…)` | 直接调用 `MultiProcessPipelineRunner` 的 Python 接口;默认 `120.0` 秒 | 仅直接使用 runner 的调用方受这个默认值约束;服务入口会传入上一行的值 | 区分服务启动和嵌入调用,不要混用超时默认 |

`StageGroup … spawned … process(es)` 只证明已创建子进程。继续等 `Process … ready` 和最后的 `MultiProcessPipelineRunner started: … stage(s), … process(es)`。若出现 `died during startup`,优先读附带的 `Startup failure detail`,不要先扩大等待时间。运行期监视器每 `5` 秒检查子进程存活,这不是请求超时配置。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 1 张 H100 80GB,Qwen3-Omni 文本输出,先检查环境能否启动 | `sgl-omni serve --model-path Qwen/Qwen3-Omni-30B-A3B-Instruct --text-only --port 8008` | 用模型自带的单卡配置减少 rank 间变量;这是启动排查基线,显存是否够仍取决于运行配置 |
| 同样的模型与单卡,首次加载超过默认等待且日志仍有进展 | `SGLANG_OMNI_STARTUP_TIMEOUT=1200 sgl-omni serve --model-path Qwen/Qwen3-Omni-30B-A3B-Instruct --text-only --port 8008` | 延长加载预算,代价是故障等待也延长;不改变 TP 或计算速度 |

组合与推荐值是按语义推的起点,不是实测最优。

TP 配置应从支持该并行方式的模型工厂出发,同时修改阶段的 `tp_size` 与 `gpu` 列表。这里不提供给所有模型通用的双卡命令,因为启动器能展开 rank 并不等于任意工厂都实现了 TP 前向。

| 症状 | 先查 | 然后 |
|---|---|---|
| rank 0 已就绪,服务仍没起来 | 其余 rank 与其余阶段是否也有 ready 日志 | 定位未就绪进程的工厂构造与错误栈 |
| 首次前向卡住,各进程都还活着 | 自定义 Scheduler 是否正确声明 `requires_tp_work_fanout` | 核对它已有的广播机制,再检查各 rank 是否进入同一计算序列 |
| 同卡多个阶段冷启动很慢 | `Acquired GPU startup lock` 的取得顺序 | 区分正常串行构造与进程失败,再决定是否延长启动预算 |
| 启动中断后重启仍遇到资源占用 | 原进程是否退出、启动错误之后是否进入清理 | 先保留退出码与完整日志,不要只删除 socket 文件掩盖活进程 |

## 六、常见误区

**「环境变量没改,超时就应该是 120 秒。」** 直接读 runner 的函数签名很容易得到这个数,但服务入口显式传了 600 秒。排查等待时间之前,先确认是谁调用启动器。

**「能看到多个 rank 的日志,就说明各 rank 都收到了请求。」** 日志证明的是启动成功。自定义 Scheduler 若依赖外部复制却未声明,rank 0 可以独自把请求放进队列,随后等不到其他 rank 的集合调用。反过来,已有内部广播的 Scheduler 也不应不加区分地再复制一次。

**「权重引用方和导出方一起起更快。」** 直觉上并行加载能省时间,但引用方可能先抢到同卡启动锁,在锁内等尚未导出的权重,反而挡住导出方。分波在这个依赖场景下是避免互等的条件,不是全项目启动都必须遵守的串行顺序。
