# 声明式拓扑:一份配置决定谁在哪跑

一条管线有哪几段、谁连谁、每段落在哪张卡上,这组事实写在哪、谁能改——这一章回答这个。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

常规文本服务里,切词、调度、前向、反切词的职责结构比较稳定,但 TP、PP、DP 和设备放置同样需要配置。Omni 在这些部署设置之外,还要声明模型特有的 Stage 图。

omni 不是。以 Qwen3-Omni 为例,文本配置与语音配置分别声明六段与七段；这是整套配置的选择,并非单条请求不要音频就自动删掉一个 Stage;有两张卡还是一张卡决定了自回归那两段分开还是挤在一起;每段占多少显存又跟着卡型变。这里至少有四组事实在互相牵扯:**哪些段存在**、**段与段怎么连**(正常路由、要等齐哪几个上游、流式块另外走一条边)、**每段落在哪张卡、和谁共用一个进程、占多少显存**、**每段自己的构造参数与引擎参数**。

把它们写进框架:23 个模型家族就是 23 套分支,框架从此认识模型,接一个新模型的成本没有上界。写进启动脚本:每个模型、每种卡型、每种形态各一份脚本,而且脚本和代码会各说各的——线上跑的究竟是哪一版拓扑,只能靠读脚本猜。

坏掉的不是延迟也不是吞吐,是**两条工期**:接一个新模型要改几处框架代码,以及同一份权重换一种机型要重写多少东西。

## 二、解法

让模型自己声明,框架只读这张表。

一个模型一份配置类,里面是一张**阶段表**。每一行是一个阶段,一行里同时说清四件事:身份(叫什么、由哪个工厂造)、路由(正常结果发给谁、要不要等齐几个上游再开工、怎么合并、流式块另外发给谁)、位置(哪张卡、张量并行几路、和谁共用一个操作系统进程、占这张卡多少)、参数(这一段的构造参数;自回归那几段还多一块专给上游引擎的)。表之上再放几样管线级的东西:权重路径、同卡档位、权重共享、放置上限、长音频切片策略。

其余全是**派生**的,不单独维护:入口段就是表里第一行(模型可以另外指定),终端段就是打了终端标记的那些,放置图和进程分组是把整张表扫一遍算出来的,连可选的 Coordinator 在途上限也从首个引擎段的有效准入声明与副本数派生；声明不完整时为 None。**表是唯一的事实,别处都是它的函数。**

用户能做的只有一件事:**覆写这张表上已经存在的格子**。改某一段落哪张卡、改显存配额、改批大小、改引擎参数——可以;加一段、删一段、改路由、改谁等谁——不行。不是「不推荐」,是写了当场报错,而且报错会顺带说出这条路径为什么归模型管。

覆写有几个入口,但**只有一条路径语言**:一条点号路径从阶段名开头,一层一层指到那个格子。配置文件里它是按阶段名嵌套的映射,命令行上它是同一条路径省掉前缀之后的一个长选项。不管从哪进来,都先被归约成同一种东西——**一条写入**:哪条路径、什么值、来自哪个源。

于是「谁盖谁」不再散落在各个入口的代码里,而是每条写入自带的两个序号:**在第几层**(模型默认 < 配置文件 < 命令行),以及**在这一层里有多具体**(一把撒给所有引擎段 < 按角色选中一批段 < 逐条写明某一段)。两条写入排名相同、值又不同,不比先后也不比长短,直接报错让人挑一个——因为任何一种自动决出的胜负,都会变成用户必须先学会才能预测自己命令行行为的规则。

![一个值从写下到生效要过的三道关:左边竖排五个来源,最上面是模型的管线配置类,它是被覆写的底,下面四个依次是配置文件里的选择器条目、配置文件里逐段与顶层写的值、命令行的广播开关、命令行的点号覆写,竖直位置就是优先级,按来源层级与具体度比较,高优先级覆盖低优先级,同排名不同值报错;中间是一道门,每条写入先被编译成一条点号路径,字段名不在表上的当场挂并附上几个相近的候选,命中可见性规则的当场挂并说出这条路径为什么归模型管,过关的才算一条写入;右边是排队、整份重新校验、派生出入口段与终端段与放置图与进程分组与可选在途上限,最后冻进每个子进程的启动记录](/opensource/sglang-omni/03a-how-one-value-wins.svg)

想换拓扑怎么办:**换一个配置类**。同一个模型可以带好几个,纯文本一个、语音一个、单卡共置一个;配置文件第一行写的就是它选哪一个。

三个容易看漏的地方:

**这张表不是数据,是一段 Python。** 平台差异直接写在里面:某一段在某个厂商的卡上要多设一个环境变量关掉一条融合算子,就是表里的一个条件分支。所以配置文件里没有「平台」这个维度。

**能被覆写的格子不止是数字。** 流式块能不能在正式载荷到达之前先收、这条边要不要禁用直连显存传输,都是用户能盖的格子——它们看着像拓扑,但改了不会让图变形,所以是开放的。

**表上没有「边」这一列。** 路由写在每个阶段自己那一行的「发给谁」里,没有一张单独的边表;要看全图,只能把表从头扫到尾。

## 三、代价

**拓扑的表达力被整个换成了不可写。** 想把某一段拆成两段、插一段自己的后处理、让某条边改走另一个下游,配置层一律没有入口,只能进模型包里写一个新配置类。这是有意的取舍:框架用「用户不能动拓扑」换来了「框架不必认识模型」。

**两条自由尾巴上的错要到很晚才报。** 构造参数和引擎参数这两块都接受没声明过的键——前者按名字直接递给这一段的工厂,后者整包转给上游引擎。好处是接新模型不用改框架的字段表;代价是这两块上的拼写错误在解析时一路放行,要等到起子进程、工厂签名对不上时才挂。于是同一类错分成了两种命:声明过的字段名写错,命令行当场报错还给你几个相近的候选;自由尾巴上的键写错,服务起到一半某一段起不来。

**合并只发生一次,在拉起服务之前。** 几层来源合成一份,校验一次,派生一次,然后整份被冻进各个子进程的启动记录。没有运行时改配置这回事,改任何一个格子都要重新拉起整个作业。

**派生越多,一个格子的影响面越大。** 改某一段的进程归属,改的不只是它自己:它决定了哪两段同进程,进而决定了它们之间那条边是直接传对象引用还是跨进程搬张量。改自回归段的运行中上限,改的是整个服务的在途上限。表上看是一个数,实际动的是三件事。

**多进程共用一张卡时,显存配额从「可以不填」变成「必须填」。** 默认如此,模型可以在管线级把这条要求关掉,但由副本引起的共卡一律要求声明,而且是在任何一个子进程起来之前就挂,报错点名缺配额的那几段。这也是为什么单卡共置那套起法必须带一份配置文件:文件里除了选中共置那个配置类,主要内容就是逐段的显存配额。

## 四、和 vllm-omni 不一样的 4 处

先说一件两边一样的事,免得被看成差异:**两边都对用户冻结拓扑**。那边的阶段拓扑是一个冻结的数据类,类注释直接写着它不是用户配置;这边靠一套逐字段的可见性规则,把同一批字段挡在用户源之外。都是「只能覆写,不能增删」。不一样的是这条线画在哪里。

![两边都必须做的 5 件事按行排开,各自的配置块去盖这些行:SGLang-Omni 一侧,模型的管线配置类是一个高盒子,从上往下盖住有哪些段谁连谁、落哪张卡几个副本多少显存、每段的引擎与批参数、平台差异四行,用户侧只有一个矮盒子盖住中间两行,最上面那一行的用户侧是一个虚线空格写着写不了,第五行是一条横跨两个子列的黄条,写着逐字段的可见性规则;vLLM-Omni 一侧,模型的拓扑文件只盖住最上面一行,模型侧在中间三行是一个虚线空格,每模型一份的部署文件是一个高盒子盖住落哪张卡、引擎与批参数、平台差异三行,第五行是一条灰条,写着拓扑那一份是冻结数据类、部署那一份没有路由字段](/opensource/sglang-omni/03b-where-the-config-line-falls.svg)

1. **分界线画在文件上,还是画在字段上。** 那边把一件事拆成两份文件:拓扑写在模型的一个 Python 文件里(有哪些段、每段是什么执行形态、上游是谁),部署写在每个模型一份的 YAML 里(落哪张卡、几个副本、显存比例、引擎参数),仓库里这样的部署文件有 96 份;它的架构总览把这条链明写成模型结构、拓扑、每段的运行策略、部署四层。这边不分文件:路由和放置在同一张阶段表的同一行上,分界线是逐字段判的——同一行里,「发给谁」归模型,「落哪张卡」归用户。
2. **阶段按名字寻址,还是按序号。** 这边的阶段用名字寻址,而且显式拒绝位置下标:写下标会被告知这里按名字寻址,写一个不存在的名字会把这条管线真实的阶段名全列出来。那边的阶段带一个整数编号,上游依赖是一组编号,部署文件里的条目按编号对上,命令行上的逐段覆写把编号拼进选项名里。
3. **用户手里拿到的起点不一样。** 这边给的是工具:有一条命令把模型自己那份配置按用户写法导出来,改完再喂回去,导出与读回是等价的;仓库里的示例配置只有 36 份短文件,内容基本是逐段的显存配额、落哪张卡,外加几个引擎与构造参数。那边仓库里直接带着写好的部署文件,一个模型一份甚至几份,按卡型、按并发形态分开,拓扑那一侧还在自己的配置里挂着默认用哪一份。
4. **平台差异安顿在哪。** 那边的部署文件里有一个平台段,按平台名再给每个阶段覆盖一层——同一份文件里能同时写下五种平台各自的显存比例、并行度和图捕获模式。这边没有这个维度:平台差异在模型的配置类里用条件分支解决,配置文件只有一种。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**几层来源,一条路径语言。** 优先级先看层、再看具体度;排名相同而值不同的两条直接报错。

| 来源 | 层 | 具体度 | 长什么样 |
|---|---|---|---|
| 模型包里的管线配置类 | 模型默认 | 基线 | 它是被覆写的底,不是一条写入;文件第一行的 `config_cls` 选中它 |
| 配置文件的 `shared:` 选择器条目 | 配置文件 | 按角色 | `select:` 下按 `stages`、`engine`、`exclude` 挑段,同一条写进选中的几段 |
| 配置文件的 `stages:` 映射与顶层字段 | 配置文件 | 逐条写明 | 按阶段名嵌套,每个叶子拆成一条写入 |
| `--mem-fraction-static` | 命令行 | 广播 | 一把撒给所有引擎段的 `engine.mem_fraction_static` |
| `--<段名>.<字段>` 点号覆写 | 命令行 | 逐条写明 | `stages.` 前缀省掉,从阶段名开头,一次只写一个叶子 |

**调参面有多大。** 起服务命令自己声明的选项一共 13 个,其中 `--model-path` 与 `--config` 只是用来挑基线;点号路径能写到的是下面这些。字段数是基准上逐类数出来的,不含每个模型自己扩出来的那部分。

| 层 | 字段数 | 用户能写几个 | 里面是什么 |
|---|---:|---:|---|
| 管线级 | 14 | 11 | 权重路径、管线名、进程副本策略、管线级环境变量、同卡档位、权重共享、放置上限与共卡是否必须声明配额、端点目录、放置策略、长音频切片(只在模型允许切片时才有这条路径);写不了的 3 个是配置类名、阶段集合、入口段 |
| 阶段级 | 23 | 12 | 落哪张卡、张量并行度、进程归属、显存配额、字节预算与要不要强制、这一段的环境变量、要不要允许先收流式块、要不要禁用直连显存传输、通信缓冲块;写不了的 11 个全是拓扑 |
| 工厂级 | 21 + 自由尾巴 | 全部 | 序列长度上限、批大小与等待窗口、异步解码、prefill 合批的几项、请求构建并发;没声明过的键按名字直接递给工厂。模型可以给某一段派生一份自己的工厂参数类,把常用键变成有类型、能被枚举到的正式字段 |
| 引擎级 | 11 + 自由尾巴 | 全部 | 只挂在驱动上游引擎的那几段上;静态显存比例、运行中上限、token 上限、CUDA graph、torch compile、量化、KV 池字节数等,其余整个上游服务端参数集当自由尾巴透传 |
| 通信块 | 7 | 全部 | 槽大小、信用数、显存 IPC 的槽与池、Mooncake 的协议与网卡 |
| 环境变量 | 18 | — | 不走路径语言,直接读进程环境 |

自由尾巴不是理论上的出口:仓库自带的 36 份示例配置里,`attention_backend`、`sampling_backend`、`max_prefill_tokens`、`disable_overlap_schedule` 这些键一个都没在字段表里声明过,全靠尾巴透传给上游引擎;`optimize`、`initial_max_batch_size` 之类同样是按名字递给工厂的。

**14 条可见性规则,每条带不让用户写的理由。** 写中任何一条,路径在编译期就挂,报错把理由一起打出来。

| 挡住的路径 | 理由 |
|---|---|
| 管线级 `config_cls` | 它是从配置类名推出来的,手写没有效果 |
| 管线级 `stages` | 阶段按名字逐个配置,整份集合不能被用户源创建或整体替换 |
| 管线级 `entry_stage` | 入口属于拓扑,由模型的配置类声明 |
| 阶段级 `name` | 名字就是地址,所有用户源都靠它寻址 |
| 阶段级 `factory_path` | 工厂属于拓扑 |
| 阶段级 `next`、`terminal`、`route_fn` | 路由属于拓扑 |
| 阶段级 `stream_to`、`stream_done_to_fn` | 流边属于拓扑 |
| 阶段级 `wait_for`、`wait_for_fn`、`merge_fn` | 扇入属于拓扑 |
| 阶段级 `project_payload` | 载荷投影属于拓扑 |

**起服务时真正影响拓扑与放置的那些。** 改了都要重启。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--config` | 命令行 | 不设 | 文件里的 `config_cls` 决定用哪个配置类,也就决定了拓扑;它在场时 `--text-only` 整个不被读 | 启动日志里的阶段数与进程数那一行 |
| `--text-only` | 命令行 | 关 | 只在没给 `--config` 时生效,换成纯文本那个配置类 | 同上 |
| `--model-path` | 命令行 | 不设 | 没给 `--config` 时由它挑基线;两个都给时它作为命令行源盖掉文件里的同名字段 | `sgl-omni config explain model_path` |
| `--colocate` | 命令行 | 关 | **它自己不改放置**:要求同时给 `--config`、要求解析出来的配置类正好是共置那一个,并把合并后的配置整份打出来 | 终端上的 Merged Configuration 段 |
| `--mem-fraction-static` | 命令行,广播 | 不设时由上游引擎自己定 | 给每个引擎段都写上静态显存比例,逐段点号覆写盖得住它 | 同上 |
| `--<段名>.gpu` | 命令行点号 | 随模型 | 改这一段落哪张卡;该进程已声明副本落卡时这条会被拒,报错点名那个进程 | `sgl-omni config resolve --show diff` |
| `--<段名>.tp_size` | 命令行点号 | 1 | 这一段切几路张量并行;大于 1 时必须同时给同样长度且互不相同的卡号列表 | 校验期报错 |
| `--<段名>.process` | 命令行点号 | 随模型;非张量并行段必填 | 同名的段共用一个操作系统进程,改名就是把它们拆开或并起来;张量并行段独占进程,这里只是前缀 | 启动日志里的进程数 |
| `--<段名>.gpu_memory_fraction` | 命令行点号或文件 | 随模型 | 这一段每个 rank 在那张卡上的占用上限;共卡时通常是必填项 | 起子进程之前的容量校验报错 |
| `--<段名>.total_reserve_bytes` | 命令行点号或文件 | 不设 | 按字节写这一段每个副本的总预算,接受 `2GiB` 这种写法;和上一条互斥,只能留一个 | 同上 |
| `--<段名>.engine.<键>` | 命令行点号或文件 | 随模型 | 只改这一段的引擎参数;写在非引擎段上是路径错 | `sgl-omni config explain` |
| `--<段名>.factory.<键>` | 命令行点号或文件 | 随模型 | 只改这一段的构造参数;没声明过的键直接按名字递给工厂 | 工厂不认这个参数时,起这一段时报错点名段与参数 |
| `--<段名>.env.<名>` | 命令行点号或文件 | 空 | 只给这一段的 worker 进程加环境默认值,不覆盖已有的进程环境 | 启动日志里的环境默认值名单 |
| `processes.<进程名>.num_replicas` | 文件或命令行点号 | 1 | 把这个逻辑进程整体复制几份;它是顶层字段,点号路径从它自己开头而不是从阶段名开头。机制见第九章 | 启动日志里的进程数 |
| 任意路径写 `none` | 命令行或文件 | — | 专门的清空写法,先于类型转换生效;把模型默认清掉,让下游自己的默认重新接管 | `sgl-omni config explain` 里那条路径变成未设置 |

**观测点:先看最终生效的那份,再看启动命令。** 配置子命令有四个动作,它们和起服务跑的是同一套合并。

| 想知道什么 | 用哪条 | 说明 |
|---|---|---|
| 这个模型自带的拓扑长什么样 | `sgl-omni config view --model-path <模型>` | 按用户写法打出来,阶段列表变成按名字键控的映射 |
| 要一份能直接改的起点 | `sgl-omni config export --model-path <模型>` | 同样的东西写成一份文件,读回去等价 |
| 这组参数最后会起成什么样 | `sgl-omni config resolve --show config` | 和起服务用的是同一个解析器,连张量并行推出来的引擎覆写都一起算上 |
| 源到底改了什么 | `sgl-omni config resolve --show diff` | 只列被源改掉的字段;一条都没有时直接说没有 |
| 某一项为什么是现在这个值 | `sgl-omni config explain <路径>` | 列出所有贡献过的源,赢的那条标出来,被压下去的标成 superseded |
| 起服务时想看合并结果 | 带 `--colocate`,或把 `--log-level` 调到 `debug` | 终端上打出整份 Merged Configuration |
| 起完之后的形状 | 启动日志 | 阶段数与进程数、配置了哪些管线级环境变量名、Coordinator 在途上限各一行 |

**典型配置**,三套,都能直接抄走。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 默认双卡语音,只想动一段的引擎参数 | `sgl-omni serve --model-path <模型> --thinker.engine.mem_fraction_static 0.8` | 不写文件,一条命令说完;代价是这条命令本身成了唯一的记录 |
| 单卡共置,按卡型给每段配显存 | 写一份文件,`config_cls` 填共置那个类,`stages:` 下逐段写 `gpu_memory_fraction`,再 `sgl-omni serve --config <文件> --colocate` | 省一张卡,换一份必须跟着卡型维护的文件 |
| 一段起多个副本 | 同一份文件里给那几段写 `gpu_memory_fraction`,并在 `processes:` 下给同名进程写 `num_replicas` 与 `replica_devices` | 用更多卡换吞吐,换来副本粒度的排障复杂度 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后。**

| 症状 | 先查 | 然后 |
|---|---|---|
| 报「没有这个字段」,还列了几个相近的名字 | 报错里那行候选 | 候选是按当前配置类的字段表算的;名字对不上多半是文档旧了,以导出的那份为准 |
| 报「这条路径是内部的」,后面跟一句理由 | 那句理由 | 它是拓扑字段,只能换配置类;想改放置或配额,改同一行上别的格子 |
| 写了一个值但完全没生效 | `sgl-omni config explain` 那条路径 | 看是被更高一层盖了,还是根本没被任何源碰过 |
| 两条写入被判冲突,服务起不来 | 报错里并排列出的两个源与两个值 | 同排名不自动决胜;删掉一条,或把其中一条换成更具体的写法 |
| 文件里能写,命令行同样的值写不了 | 是不是想用一个选项写下一整块 | 命令行一次只写一个叶子,成块地写要用文件;自由尾巴上的键例外 |
| 服务起到一半,某一段报工厂不接受这个参数 | 报错里点名的段与参数名 | 自由尾巴上的键拼错了,或者这个键本该写在另一段上 |
| 起子进程之前就报显存对不上 | 报错里点名的那几段或那张卡 | 补上缺的配额,降低配额总和,或者把某一段挪到别的卡 |

引擎参数的自由透传只是配置扩展入口,仍需通过上游参数校验与本项目的适配限制；上游支持的功能不一定在这里可用,见 05 章。

## 六、常见误区

**「共置那个开关会把段挤到一张卡上。」** 人们这么以为,是因为它的帮助信息就是这么写的,而且带上它起出来确实只用一张卡。实际上它自己不改任何放置,它只做三件事:要求同时给配置文件、要求解析出来的配置类正好是共置那一个、把合并后的配置整份打出来。真正把段挪到同一张卡上的是那个配置类。只给那份文件、不加这个开关,起出来的放置一模一样。

**「给了配置文件,纯文本那个开关还管用。」** 不管用,而且不警告。挑基线是一个三路分支,文件优先;文件在场时纯文本开关整个不被读到。管线形态完全由文件里写的配置类名决定,不由命令行上还挂着什么决定。

**「开发者参考页的字段表就是全集。」** 基准上阶段配置有 23 个字段,参考页列了 19 个;管线级有 14 个,参考页列了 10 个真实存在的,外加一个早就不存在的阶段融合字段——同一个文档站的迁移页写着它已经被进程归属字段取代,写进配置文件会直接当未知字段挂掉。想知道当前有哪些字段,用导出命令,别读参考表。

**「参数名写错会立刻报错。」** 分两种命。声明过的字段名写错,路径在编译期就挂,报错还附上几个相近的候选;构造参数和引擎参数这两块的自由尾巴上写错,解析一路放行——前者要等起那一段、工厂签名对不上时才挂,后者一路转给上游引擎,由上游决定认不认。所以「命令行收下了」不等于「这个参数存在」。

**「广播开关和逐段写明会打架。」** 不会,这正是具体度这个序号存在的理由:一把撒出去的那条排名更低,逐段写明的天然盖住它,而且不算冲突。真正会打架的是同一条路径被同排名写了两次——比如同一个点号选项在命令行上出现两遍、值还不一样,这时不决胜负,直接要求挑一个。

**「解释命令打出来的就是赢家给的那个值。」** 标题行是最终生效值,不是赢家给的值。模型自己的校验可能在赋值之后再改写一遍;这时赢家那一行仍然显示源写下的值,后面括号里注明它最后变成了什么。排障时看标题行,复盘谁写的看下面那几行。
