# SGLang-Omni 总览

源码基准:官方仓库 <https://github.com/sgl-project/sglang-omni>,分支 `main`,commit `89e60d0bf216bacd0e072d79f969550469614662`,最近的发布 tag `v0.1.6`,核对日期 2026-09-22。全篇的「当前」「默认」都指这组基准;标了「官方数字」的来自官方文档,不是实测。

## 一、SGLang-Omni 是什么

**SGLang-Omni** 是 omni、语音与 TTS 模型的**多阶段服务运行时**,和 SGLang 同属 sgl-project。

它要解决的问题和纯文本引擎不是一回事。一个文本模型的一次生成是一条自回归循环:tokenization、prefill、decode、detokenization,从头到尾一个模型在跑。而一次「听一段话、看一张图、想一想、再说出来」的生成被切成计算形态完全不同的若干段——预处理是 CPU 上的解帧与重采样,Encoder 是一次性的大前向,Thinker 是典型的自回归循环,Talker 也是自回归但每一步要吃上一步的产物,Vocoder 则是流式的小块解码。把这些塞进同一个 Scheduler,批策略、显存预算、KV cache 全都对不上:Encoder 不需要自回归的 KV cache,Vocoder 则需要及时处理陆续到来的音频块。

SGLang-Omni 的回答是**把一次生成显式建模成一条阶段流水线**,每段配一个和它负载匹配的 Scheduler,段与段之间用统一的 Control Plane 与 Data Plane 连起来。至于自回归那一段——批选择、KV cache 管理、前缀缓存、prefill 与 decode 的排布——它复用 SGLang 的核心能力,并通过自己的 Scheduler 与 ModelRunner 做适配。

一句话定位:**SGLang-Omni 拥有流水线拓扑、阶段生命周期、阶段间传输、模型家族集成层和 OpenAI 兼容服务面,复用并适配 SGLang 的自回归调度与模型执行能力。**

顶层入口:

- `sgl-omni serve`:起 OpenAI 兼容的 HTTP 服务,也是最常用的入口。
- `sgl-omni config`:看、导出、解析、解释某个模型最终生效的管线配置。排障先看它,不看启动命令。
- `sgl-omni-router-py` 与 Rust 二进制:多副本部署时的前门。
- 还注册了一个 SGLang 的服务后端入口点,让 SGLang 侧能把 omni 管线当成一种后端拉起来。

代码组织上,Python 运行时在 `sglang_omni/`(约 5900 KB),Rust 与 Python 两套路由器在 `sglang_omni_router/`(约 1300 KB)。从体量看,`sglang_omni/` 里**模型家族独占 73%**(23 个家族,4300 KB),剩下的框架代码里服务面、调度、流水线三块各占 6% 左右,传输、配置、ModelRunner 各占 2%–3%。另有一块本解读不涉及的 `OmniTyper/`(约 245 KB),是 Apple Silicon 上的一个 Swift 语音输入应用,调用本项目的语音识别服务,属于独立产品。

## 二、五件招牌:先建立全局图景

```text
        客户端:多模态 chat / 语音生成 / 转写 / 实时 WebSocket
                              |
          多副本时先过 [5] Rust 路由器(能力匹配 + 健康感知)
                              |
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
  [1] 多阶段流水线                            [4] 同卡共存
  一次生成切成若干段,拓扑写在                 拓扑 / 副本 / 放置 / MPS /
  模型自己的配置类里,框架不认识模型            权重共享,五种机制各管一件事
        |                                           |
        └─────────────────────┬─────────────────────┘
                              ▼
                    [2] 阶段特化调度
      自回归段组合 SGLang 的 Scheduler,其他段按负载配专用 Scheduler
                              |
                              ▼
                  [3] Control Plane 与 Data Plane 分离
      Control Plane 负责提交 / 数据就绪 / 中止 / 关停等协调消息;
      张量走同进程引用、显存 IPC、共享内存或跨节点后端
```

一句话记忆:

- **多阶段流水线**:一次生成是一条有向图,不是一次前向。哪些段存在、怎么路由、谁是入口、谁是终端,全写在模型自己的配置类里,用户只能覆写不能增删。
- **阶段特化调度**:所有 Scheduler 共用一套 Mailbox 接口,所以阶段层不需要知道自己挂的是哪种。自回归段把批选择与 KV 管理交给 SGLang,Encoder、聚合、解码这些段用不带 KV cache 的轻量 Scheduler,Vocoder 用流式 Scheduler。
- **Control Plane 与 Data Plane 分离**:阶段间的大张量与协调消息通常分开传递,具体入口、终端返回与小块内联另有路径。同一条边在同进程时直接传 Python 对象引用,同机按位置关系走显存 IPC 或共享内存。**跨节点那一档在这个基准上接不上**——决定一条边算不算跨节点的那份远端段名单默认是空的,全树没有一处给它赋值(04 章)。
- **同卡共存**:小段独占一张卡是这类管线最常见的浪费。五种机制分工明确,组合起来把多个完整副本塞进一张卡。官方在 H100 80GB、HiggsTTS3-4B 的特定测试中报告双副本与三副本约 1.4–2.1 倍吞吐,也记录了失败和退化情况;这是官方旧基准的实验结果,不是本篇基准或任意模型的保证。
- **OpenAI 兼容服务面加 Rust 路由器**:一套接口覆盖多模态 chat、语音生成、转写、翻译与实时对话;多副本时由 Rust 前门按 worker 声明的模型、模态与媒体契约做匹配。

## 四、一条请求怎么串起来

![Qwen3-Omni 的语音管线被切成七段,分别落在 CPU 进程、GPU 0 和 GPU 1 上:预处理和 decode 跑在 CPU,两个 Encoder、Thinker 和 code2wav 跑在 GPU 0,talker_ar 单独占 GPU 1;Thinker 用实线把文本结果送到 decode,同时用流边把隐藏态喂给 talker_ar,talker_ar 再把音频码流给 code2wav,decode 与 code2wav 两个终端段各自把结果回给主进程里的 Coordinator](/opensource/sglang-omni/00a-seven-stages-two-cards.svg)

以 Qwen3-Omni 的语音管线为例。请求从 HTTP 或 WebSocket 进来,客户端层把它翻译成内部请求对象交给**Coordinator**;Coordinator 把它投给入口段,此后只做三件事:跟踪请求状态、收终端段的结果、广播中止。

接下来这条请求在**七个阶段**之间走,而且这七个阶段默认各自占一个操作系统进程:预处理 tokenization 并把图像、视频、音频解开;两个 Encoder 各自出嵌入;**Thinker** 是自回归主干,一边出文本 token,一边把隐藏态从流边吐出去;**talker_ar** 在另一张卡上接住隐藏态,自回归地生成音频码;**code2wav** 把码变成波形。`decode` 和 `code2wav` 都是终端段,Coordinator 汇总最终结果;流式文本与音频块可提前返回。

三个容易看漏的地方:

- **Talker 不等 Thinker 说完。** 隐藏态是沿流边一块一块过去的,满足攒块与启动条件后,音频可以在文本生成结束前开始输出。
- **Talker 的输入不止隐藏态。** 它同时 fan-in 预处理与两个 Encoder 的载荷,而且两个 Encoder 只在这条请求确实要音频输出时才把载荷投给它。
- **纯文本管线是另一套。** 六段,多一个聚合段把预处理与两个 Encoder 的结果并起来,没有 Talker 也没有 Vocoder。语音路径反而没有这个聚合段,因为 Thinker 和 Talker 各自 fan-in。

## 六、怎么调它、怎么看它

各章「调参与观测」只写自己的参数,入口和观测点在这里说一次。

**四种入口,一条路径语言。** 这个项目把「哪个阶段的哪个设置」统一成一条点号路径,YAML 与命令行只是它的两种拼写:YAML 里写在阶段映射下,命令行里省掉前缀、直接从阶段名开头。

| 入口 | 长什么样 | 什么时候用 |
|---|---|---|
| 模型自带的默认值 | 写在模型的管线配置类里 | 拓扑本身:哪些阶段存在、怎么路由、谁是入口。**用户改不了** |
| 配置文件 | 一份 YAML,阶段映射下按阶段名写 | 成套的部署设置;它只能覆写已有阶段的设置,不能增删阶段 |
| 命令行整体开关 | 起服务时的几个大开关:纯文本管线、共置、实时端点、显存比例、TTS 批上限、本地媒体与域名白名单、MPS 档位 | 一次性切形态 |
| 命令行点号覆写 | 和 YAML 同一条路径,从阶段名开头 | 单独调某个阶段的某一项 |

**调参面比命令行看起来的大得多。** 命令行自己声明的选项是 13 个(其中 2 个只用来挑基线),而点号路径能写到的是:管线级 11 个可写字段、每个阶段 12 个可写字段加 21 个工厂参数,引擎段还多 11 个声明键**外加传递 SGLang 参数的扩展入口**(实际支持范围仍受 Omni 与模型适配限制),另有 18 个自有环境变量。拓扑那一组字段(阶段名、工厂、路由、流边、fan-in、载荷投影)标成内部,用户源写不了。

四层来源的优先级从低到高是模型默认、配置文件、命令行开关与命令行点号覆写。**排障先看最终生效的配置,不看启动命令**:配置子命令有四个动作,看、导出、解析、解释,其中「解释」会告诉你某一项最后是被哪一层写成现在这个值的。

**同卡共存的档位单独说一句。** MPS 有三档:不碰、自动、强制。自动档只在同一张卡上确实有两个及以上单卡非张量并行进程时才开;强制档一个进程就够,并且在不支持 MPS 的平台上直接报错而不是降级警告——做同卡数据并行时要用强制档,同一张卡上的多个服务进程才会加入同一个守护进程。

**观测点分三层。**

| 看什么 | 在哪 | 说明 |
|---|---|---|
| 单条请求的时间线 | 请求级事件记录器写的 JSONL,每行一个里程碑:准入、预处理、Encoder、prefill、首 token 或首个音频码块、每一跳、终端响应 | 多阶段归因主要靠它 |
| 某一段的 kernel | torch 剖析器产出的 Chrome 轨迹,和事件记录器共享同一个运行号 | 事件记录器先定位到段,再用它往下钻 |
| 副本与集群 | 路由器侧的 Prometheus 指标、健康检查与诊断接口 | 多副本部署时看这里 |

管理接口默认不鉴权;一旦在服务端或 Python Router 上设了管理密钥,或者设了对应的环境变量,相应管理路由就要带 Bearer 令牌。Rust Router 的静态转发边界另见 14 章。

## 七、阅读顺序

主干是 01 → 02 → 03 → 04 → 05,读完就抓住了这个项目的主线:一次生成怎么被切成流水线、框架怎么做到不认识模型、张量怎么走、每段的 Scheduler 凭什么不一样。06 与 07 是执行与输出,08 到 10 按部署形态按需读,11 与 12 是输入输出两头的面,13 只在要接新模型时读,14 与 15 是外围。

**各章拿什么作对比。** 01 章比的是**下面那一层**——单模型文本引擎的做法,用 sglang 当实例,因为这套运行时自回归那一段组合的正是它;这一层的差异是理解整个架构的入口,放在第一章最合适。**其余各章比的是 `vllm-omni`**,vLLM 社区的那套 omni 框架——它和本项目解决同一类问题,是真正同层的东西。对比点到为止:只写两边在同一个问题上的取舍不同,不做优劣评判,也不替对方的实现写结论;重点始终在本项目自己怎么做。

本解读的每一章都是短页:核心问题、解法、代价、与参照项目的对比、调参与观测、常见误区。读过 sglang 解读的人读起来最省力,但不是前提。通用机制(前缀缓存、KV cache、连续批处理、CUDA graph、并行策略)在知识库里各有一篇,这里不重讲。

下面以常规、非 PD 分离的单副本文本服务为 SGLang 对照,省略 TP、PP、DP 等部署展开;表中不是 SGLang 全部能力的边界:

| 维度 | SGLang | SGLang-Omni |
|---|---|---|
| 一次生成是什么 | 一条自回归循环,从头到尾一个模型 | 一条有向图,若干段计算形态不同的阶段 |
| 拓扑从哪来 | 常规路径:Tokenizer、Scheduler、前向、Detokenizer | 模型自己的配置类声明,框架不认识模型 |
| Scheduler | 一种 Scheduler 管所有请求 | 每段配一种,自回归段组合 SGLang 的那一种 |
| 进程之间传什么 | tokenization 与调度之间传请求对象和 token | 阶段之间传隐藏态、嵌入、音频码这些张量,所以 Control Plane 与 Data Plane 必须分开 |
| 多卡的含义 | 一个模型切到多卡(TP、PP、EP) | 既有一个阶段切到多卡,也有多个阶段共用一张卡 |
| 输出 | 文本 token 流 | 文本与音频两条流,两个终端段由 Coordinator 合并 |

章表上的差异也由此而来:sglang 那边是一章 KV 存储加一章前缀缓存加一章三层缓存,这边一句话回指就够了;而阶段、拓扑、传输、同卡共存这四章围绕多阶段模型重新组织,是理解本项目的重点。

## 八、术语表

| 术语 | 一句话 |
|---|---|
| Stage | 流水线里的一个逻辑执行单元,自己声明跑在哪、结果去哪 |
| Coordinator | 主进程里的请求路由与终端收集者,不认识模型 |
| Mailbox | 阶段与 Scheduler 之间的两个队列,所有 Scheduler 共用这一套接口 |
| Control Plane | 走提交、数据就绪、中止、关停这几种小消息的那条路 |
| Data Plane | 走张量的那条路,按边的位置关系挑传输方式 |
| relay | Data Plane 的可插拔后端;注册了 5 个,基准上建得出来的只有显存 IPC、共享内存与跨节点那一种 |
| 同进程对象传递 | 同一个操作系统进程里的两个阶段直接传 Python 对象引用,不序列化 |
| Thinker | omni 模型里出文本与隐藏态的自回归主干 |
| Talker | 接住 Thinker 的隐藏态、自回归生成音频码的那一段 |
| Vocoder | 把音频码变成波形的那一段,按块流式解码 |
| Streaming Edge | 和正常结果路由平行的一条边,一块一块地传,带块号与结束位 |
| fan-in | 一个阶段等齐几个上游再开工,合并函数决定怎么并 |
| Terminal Stage | 没有下游的阶段,结果由 Coordinator 收走;一条管线可以有多个 |
| 进程拓扑 | 哪些阶段共用一个操作系统进程 |
| 进程副本 | 把一个逻辑进程整体复制几份,按请求粘住 |
| MPS | NVIDIA 的多进程服务,让同卡的多个进程的 kernel 能重叠 |
| 权重共享 | 同卡的多个副本里,最小编号的那个加载权重,其余通过显存 IPC 别名过去 |
| 反馈式自回归 | 下一步解码要用上一步在同一个 ModelRunner 里产出的反馈的那类模型 |
| 能力表 | 模型声明自己支持哪些模态与任务的地方,路由器按它做匹配 |
