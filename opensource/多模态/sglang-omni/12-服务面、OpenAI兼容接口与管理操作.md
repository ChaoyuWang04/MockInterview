# 服务面、OpenAI 兼容接口与管理操作

聊天、语音和权重管理共用一套服务时,哪些请求进入生成管线、哪些直接控制已有阶段,决定了排队、错误与成功该怎么解释。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

对调用方来说,聊天是消息列表,转录是音频上传,语音合成是文本与声音选项;对模型来说,它们都要变成能进入 Stage 的内部请求。把协议处理塞进每个 Scheduler,模型接入就会重复处理 HTTP、音频编码和错误格式。

另一种混淆更危险:同一个服务也能暂停生成和更新权重。它们看起来也是一次 HTTP 调用,却不能像普通请求那样沿生成图逐段流动。更新成功到底指所有模型、某个引擎,还是只是接口收到了命令,必须由服务层讲清楚。

## 二、解法

**协议适配和模型执行分开。** FastAPI 路由先解析与校验外部请求,聊天、TTS 和转录分别处理自己的协议语义,再交给统一 Client。Client 把生成请求交给 Coordinator,返回时将内部结果整理成文本、音频、用量或流式块,路由层最后组装外部响应。转录适配器还按模型架构处理提示词与时间戳能力,所以接口同名不代表每个模型支持的输出完全一致。

**准入在提交生成请求时发生。** Coordinator 有有效在途上限时,会在登记请求之前拒绝超额请求;通过后再进入 Stage 管线。这个上限来自首个引擎阶段的运行中容量与排队容量,结合其进程副本数计算。配置缺少有效值时,这一层可以不设上限,阶段内部仍有自己的调度约束。它不是一个自动把所有请求排成单队列的 HTTP 网关。

**管理命令复用已有 Stage 的控制入口。** Client 把命令交给 Coordinator,后者按目标阶段广播,Stage 再交给自己的 Scheduler 管理处理器。正在运行的 OmniScheduler 将跨线程到来的管理操作排进内部队列,由调度线程执行。管理命令没有对应的新生成 Stage,也不经过普通生成的在途准入。

![生成请求经过协议适配和生成准入进入阶段执行,管理命令通过同一个 Client 与 Coordinator 的独立控制分支抵达已有 Stage 的管理处理器,两条路径分别返回生成结果和逐阶段管理结果。](/opensource/sglang-omni/12a-serving-control-branches.svg)

管理调用的结果按 Stage 汇总。没有管理能力的 Stage 会报告跳过;更新类操作要求至少一个目标实际参与,且参与者全部成功,才给整体成功。因而部分阶段不支持可以与整体成功同时出现,全体跳过则不能算更新完成。调用方还要看逐阶段结果,不能把顶层成功读成「整条管线所有组件都换了权重」。

## 三、代价

**兼容接口保留了模型和传输差异。** 普通响应可以等到执行结束后再决定 HTTP 成功或失败;流式响应一旦发出响应头和内容,后续错误不能撤回已发数据。聊天流通过 SSE 输出,流式语音则先拿到第一个可用音频块再构造 PCM 响应,后半段仍可能失败。调用方必须区分完整结束与传输中断。

**批量语音不是一次原子准入。** 服务把批内每项建立为独立生成任务,各自进入正常语音路径,最后按原顺序汇总成功与错误。整批通过格式检查之后,仍可能只有部分项目生成成功;批大小限制只限制一次提交的项目数,不会给整批预留生成容量。

**管理汇总也不是跨阶段事务。** Coordinator 分别发送、等待和汇总,各 Scheduler 自己处理暂停、活动请求与更新。一个阶段失败时,已有成功结果不代表会回滚。全模型权重摘要还要逐张量搬到 CPU 计算哈希,会阻塞该引擎推理;它适合检查更新一致性,不适合当高频健康探针。

## 四、vLLM-Omni 如何接入兼容服务层

两边都在协议层与模型执行之间放适配层,聊天和语音处理最终都调用引擎侧生成接口。SGLang-Omni 在自己的 FastAPI 应用中注册路由,用统一 Client 接 Coordinator;vLLM-Omni 则先构建上游 vLLM 的应用,替换聊天、模型列表和健康等路由,再安装 Omni 的处理器。

vLLM-Omni 的聊天服务类继承上游聊天服务,语音类也复用上游服务基类;启动后还按模型的端点限制关闭不支持的路由。这边在注册的协议入口中做能力校验,例如翻译请求会检查当前管线是否具备音频翻译能力。对读者最有用的结论是:兼容服务的职责都在适配层,但复用上游应用还是独立组装应用,会改变路由和错误处理的落点。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

下面前半张表是启动配置;后半张表另外列出按次生效的请求和管理字段,它们不要求重启。接口覆盖与模型能力要分开验证。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--host` / `--port` | 启动命令 | `0.0.0.0` / `8000` | 改监听地址与端口,不改变模型放置 | 启动监听日志;端口占用时可能选新端口 |
| `--tts-batch-max-items` | 启动命令 | `32` | 调低可减少单次批量请求展开的任务数,不改变引擎批大小 | 批量语音超限返回的项目数错误 |
| `stages.<首引擎>.engine.max_running_requests` / `max_queued_requests` | YAML或逐阶段启动覆写 | 随模型声明,不保证两项都存在 | 有效时形成 Coordinator 在途上限;调大可能增加等待与内存压力 | `Rejecting request ... in-flight cap`及阶段队列 |
| `SGLANG_OMNI_ADMIN_KEY` | 服务进程环境变量 | 未设,不启用这层管理鉴权 | 设置后管理路由要求Bearer凭据,不等于所有生成接口都鉴权 | 缺凭据401,错误凭据403 |

| 请求字段或接口 | 在哪调 | 默认或限制 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `stream` | 聊天或单条语音请求体 | 默认false;语音流需`response_format="pcm"` | 提前接收输出,同时承担中途失败处理 | 聊天SSE的结束块与`[DONE]`;PCM连接是否完整结束 |
| `stages` / `timeout_s` | 管理请求体 | 目标省略为全部已注册Stage;超时按操作分别指定 | 缩小影响范围或调整等待;逻辑阶段名展开到副本 | `results`里的每个Stage及`success`、`skipped`、`unsupported` |
| `mode` | `/pause_generation`请求体 | `abort` | 默认中止已有请求;`retract`或`in_place`改变保留方式 | `num_paused_requests`与`engine_paused` |
| `abort_all_requests` / `keep_pause` / `flush_cache` | `/update_weights_from_disk`请求体 | false / false / true | 决定活动请求处理、更新后暂停状态及缓存清理 | 每阶段`flush_success`、`engine_paused`和更新错误 |
| `action` | `/weights_checker`请求体 | `checksum` | `snapshot`留摘要供`compare`比较;计算完整权重摘要会阻塞推理 | `matched`、`changed`、`per_gpu_checksum`及摘要耗时日志 |

管理等待时间:模型信息默认30秒,暂停和继续60秒,磁盘更新及权重检查120秒,分布式更新组相关操作300秒。HTTP 的 `/update_weights_from_tensor` 当前固定返回501,因为没有张量数据通道;Python 内部存在同名动作不代表HTTP已可用。`/generate` 是另外的非流式生成入口,不能据此承诺任意RL训练器即插即用。

**典型配置。** 以下沿用Qwen3-Omni默认双卡语音布局,要求2张显存足够的GPU;卡型与显存配额由部署配置决定。服务面的开关不会让原本装不下的模型变得可运行。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 本地验证聊天与语音协议,低并发 | `sgl-omni serve --model-path Qwen/Qwen3-Omni-30B-A3B-Instruct --host 127.0.0.1 --port 8091` | 只绑定本地地址,保持模型默认准入,先验证单请求与错误响应 |
| 验证批量语音及管理调用,小批并发 | `SGLANG_OMNI_ADMIN_KEY="<自设密钥>" sgl-omni serve --model-path Qwen/Qwen3-Omni-30B-A3B-Instruct --host 127.0.0.1 --port 8091 --tts-batch-max-items 8` | 限制单批展开规模并启用管理凭据,多次提交次数增加;8是语义起点而非吞吐最佳值 |

组合与推荐值是按语义推的起点,不是实测最优。

**先看哪层说失败。** `/health`依据Coordinator是否运行返回200或503,不证明一次真实生成或一次权重更新可成功。批量语音看`total`、`succeeded`、`failed`和逐项结果;管理看逐阶段结果。当前队满的HTTP映射并不统一:TTS会映射503,聊天非流式的通用异常分支可能返回500,所以排障还应保留错误正文与请求编号。

| 症状 | 先查 | 然后 |
|---|---|---|
| 批量语音HTTP返回成功,却缺音频 | `results`逐项状态与错误,不要只看HTTP码 | 将失败项对应到各自请求编号,分清校验拒绝与生成准入失败 |
| 健康正常,新请求仍被拒绝 | 在途上限日志及首引擎容量声明 | 调整请求供给,再根据延迟预算决定是否扩队列 |
| PCM已播放一段后断开 | 服务端该请求最后异常及中止日志 | 按不完整生成处理,不要把已收字节当作完整音频 |
| 更新返回失败,重试前不知道状态 | 每个Stage更新结果与模型信息 | 先确认实际权重版本;混合版本的模型信息查询可返回409 |
| 管理HTTP超时,误以为没有执行 | 目标Stage日志及当前模型状态 | 确认是否已产生副作用再决定重试;超时不提供自动回滚 |

## 六、常见误区

**用批量语音大小去控制GPU batch。** 名字都带batch,容易把HTTP项目数当作一次前向大小。每项生成有自己的请求编号和准入,真正怎么合批仍由Stage的Scheduler决定,整批也可能部分失败。

**看到更新的顶层成功,就认为预处理、Thinker和Vocoder全更新了。** 无能力的Stage可以被跳过,更新成功要求的是至少一个实际参与者成功且参与者无失败。应检查目标与逐阶段结果,必要时缩小目标范围再检查模型版本。

**暂停默认会把请求留在原地。** 这个直觉适用于暂停按钮,但这里默认模式会中止已有请求。若是为了在线换权重,还要核对活动请求处理和更新后的暂停状态,不能只按接口名推测行为。

**权重检查里的重置会恢复模型。** `reset_tensors`这个名字像修改权重,实际只重新保存当前权重摘要;它不回滚任何张量。`compare`必须先有摘要,且摘要相同只证明本次检查范围内的张量一致,不证明训练或生成质量。
