# Rust 路由器:多副本前门

多台服务的模型和媒体能力不完全相同,请求该发给谁,流式返回多久才算真正释放容量——这一章回答这个。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

给多台服务做轮询,只解决了「别总打同一台」。语音请求还可能指定输出格式、参考音色和流式返回;一台 Worker 能生成文字,不等于它能满足这组声音要求。把模型、格式和输出方式拆成互不相关的标签,甚至会拼出任何 Worker 都没声明过的组合。

流式请求还有另一种失真:响应头已经返回,音频却还要持续生成和传输。如果此时就把请求从在途数量里减掉,Router 会以为后端已经空闲,继续把新请求压上去。**正确选路既要保证能力组合匹配,也要让容量记账覆盖真正的流生命周期。**

## 二、解法

本章主体是独立运行的 **Rust Router**。它从启动配置读取已有 Worker 的地址及能力声明,做健康探测和请求转发,不负责启动模型或编排内部 Stage。

每条能力声明描述一个完整组合:服务类别、模型、输入与输出形态等。分类路径必须在同一条声明中满足请求,不能拿一行的模型和另一行的格式拼接。健康状态再筛掉尚未确认健康或已失效的 Worker,最后按轮询或最少在途负载选择目标。

但并非每条请求都要先读完整正文。若启动时能证明同一信任域内相关 Worker 的默认模型和能力声明等价,正文就不会改变候选组,可以边收边转。不能得到这份证明时,先在有上限的缓冲区收正文、分类,再选目标。**直通省掉的是为选路而解析正文,不是取消健康过滤或协议检查。**

![Rust Router 的聊天 HTTP 路径将能力与健康过滤后的请求交给 Worker,从准入到响应体结束始终持有额度;响应头和首个音频块都不会提前释放,出错或取消才走终止清理。](/opensource/sglang-omni/14a-lease-through-stream.svg)

转发时把准入额度和 Worker 在途记账交给响应体对象持有。它随着响应体读到末尾、报错或被丢弃而释放,因此客户端慢读造成的持续占用也能反映在负载里。转发按下游读取推进上游读取,用背压避免把完整长音频攒在 Router 中。

注册音色还多一条约束:带状态的音色操作与相应请求需要固定的归属 Worker,不能任意轮询到没有该音色记录的副本。这与普通无状态请求的负载选择分开。

## 三、代价

**静态能力清单需要与实际服务一致。** 健康探测确认的是端点是否成功响应,不会替部署者重新推导模型能做什么。声明多了会误投,声明少了会拒绝本来能处理的请求;能力不同还会失去免分类直通的机会。

**分类路径要先付出缓冲和解析成本。** 单条正文大小和全局缓冲字节数分别受限,准入也有全局与服务类别的额度。它们解决的是不同资源的拥塞,不能只提高连接数就认为容量扩大了。

**最少请求并不是预测最短完成时间。** 它观察在途负载,不了解下一段音频还要生成多久;批量语音还会按条目占用权重。它比不看负载的轮询多了一份即时信息,但不是按 GPU 算量精确排队。

**已经发出的流没有透明重放。** Rust HTTP 客户端明确关闭自动重试,一次转发失败会终止当前请求并可能触发立即健康探测。请求截止时间约束上传、分类和等待上游响应头;进入响应体转发后,这里没有再用同一个截止时间截断整段输出。客户端断开能释放 Router 的转发资源,不代表已经验证 Worker 内部每个计算阶段都同步停下。

## 四、与 vLLM-Omni 分清前门和阶段选路

vLLM-Omni 的 OpenAI API 入口负责构造应用、启动服务并接入引擎;引擎内部的 StagePool 选择的是某一个 Stage 的副本。这里的 Rust Router 则面对多个已经运行的完整 Worker 服务,按外部请求的能力要求选择目的地。

两边都有「选副本」,但选择对象不同。前门选好完整服务后,服务内部仍需自己的阶段调度与副本选择。不能把 StagePool 画成这个 Router 的一一对应模块,也不能从这几个入口文件推断整个 vLLM 生态没有独立 Router。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**先分清可执行入口。** Rust 二进制 `sgl-omni-router` 只接收 `--config` 和可选 `--check-config`,使用严格 TOML。`sgl-omni-router-py` 是另一套 Python 实现,有自己的参数与配置,不是 Rust 的启动包装器;它还可通过 `--launcher-config` 启动受管理的 Worker。下面的配置均针对 Rust,不混用 Python 开关。

| 配置字段 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `router.strategy` | TOML `[router]` | `round_robin` | `least_requests` 优先最小在途负载,并列时按轮转次序 | `/diagnostics` 的 Worker 在途情况 |
| `admission.global` | TOML `[admission]` | 必填 | 控制全局在途请求信封数量,满时快速拒绝 | `/metrics` 的准入使用与拒绝指标 |
| `admission.generation_http` / `speech_http` 等 | TOML `[admission]` | 未配置为无该类额度,须与启用路由一致 | 限制服务类别;批量语音按条目数消耗类别额度 | 类别准入与 Worker 加权负载 |
| `server.max_connections` | TOML `[server]` | 1024 | 限制接受的客户端连接,不等于生成请求额度 | 连接相关指标与拒绝 |
| `health.interval_ms` / `timeout_ms` | TOML `[health]` | 均为 5000 毫秒 | 调小加快探测也增加探测频率或超时敏感度 | `worker health changed` 日志、最近探测结果 |
| `health.success_threshold` / `failure_threshold` | TOML `[health]` | 2 / 3 | 连续成功/失败达到门槛才改状态 | `/diagnostics` 的连续探测计数 |
| `http.buffered_request_total_bytes` | TOML `[http]` | 256 MiB | 整体分类正文缓冲预算 | 缓冲预算与拒绝指标 |
| `http_generation.buffered_request_max_bytes` / `streamed_request_max_bytes` | TOML `[http_generation]` | 8 MiB / 512 MiB | 分别限制分类路径与直通路径正文大小;媒体配置有同名字段 | 正文过大错误及所走路径 |
| `http_generation.request_timeout_ms` | TOML `[http_generation]` | 1800000 毫秒 | 限制上传、分类和等响应头的时间;媒体配置亦有此项 | 请求/上游超时错误,不当作响应流总时限 |
| `router.voice_owner_worker_id` | TOML `[router]` | 不设 | 使用上传音色能力时指定唯一归属 Worker | 配置校验、音色请求派发目的地 |
| `workers.service_profiles` | TOML 每个 Worker 下的数组 | 必填 | 定义完整能力组合,决定匹配及能否直通 | `--check-config`、请求匹配错误 |

**从完整示例起步,不要只抄一段 Worker 地址。** 在本基准源码根目录中,`sglang_omni_router/rust/examples/omni.toml` 是完整双副本聊天配置,`tts.toml` 是完整双副本语音配置。文件已包含必需的服务、停机、日志、Router、准入、健康与 Worker 声明;运行前复制并修改地址、模型名及真实能力。示例里的 `omni-model` 和 `tts-model` 是占位模型名,不负责下载或启动模型。

语音示例尤其值得保留其分行方式:压缩格式与 WAV 放在非流式声明,PCM 另占一行支持非流式与流式。这避免把「支持 MP3」和「支持流式」错误组合成「支持流式 MP3」。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 已启动的同构聊天副本 | 从 `omni.toml` 完整复制为 `router-chat.toml`,改两处 Worker 地址、默认模型及能力中的模型名;运行 `sgl-omni-router --config router-chat.toml --check-config`,成功后去掉 `--check-config` 启动 | 保持能力行等价可走免正文分类路径,仍由 Worker 校验实际请求 |
| 已启动的同构 TTS 副本 | 从 `tts.toml` 完整复制为 `router-tts.toml`,修改实际地址和模型名,保留格式/流式两行;运行 `sgl-omni-router --config router-tts.toml` | 示例采用 `least_requests`,让长音频占用反映在选路中 |
| 同信任域内能力不同的 Worker | 在完整配置中按实际能力分别修改每台的 `service_profiles`,先做配置校验再启动 | 用正文缓冲与分类成本换取明确的能力匹配 |

组合与推荐值是按语义推的起点,不是实测最优。

`/live` 看进程存活,`/ready` 还要结合当前生命周期和各启用服务的可路由条件;`/v1/models` 来自配置汇总,不能当成实时能力探测报告。`/diagnostics` 和 `/metrics` 才能把健康、准入和转发终止放在一起看。

| 症状 | 先查 | 然后 |
|---|---|---|
| 刚启动全部请求不可用 | Worker 是否仍为 `unknown`,成功探测是否达到门槛 | 检查实际健康端点,不要先修改选择策略 |
| 模型明明在线却找不到匹配项 | 同一条能力行是否同时覆盖模型、模态、格式和流式要求 | 修正完整能力声明,不要跨行补标签拼能力 |
| 响应头已回,准入仍满 | 响应体是否还在传或客户端是否慢读 | 看响应体终止指标,这是持续持有额度的预期行为 |
| 增加连接数仍被拒绝 | 全局、类别额度和缓冲预算分别是否耗尽 | 调整真正拥塞的预算并核后端承载量 |
| 同名音色有时找不到 | 上传音色的归属 Worker 及健康状态 | 固定状态归属,不能靠轮询碰运气 |

## 六、常见误区

**「健康检查成功就证明清单里的能力都是真的。」** 探测循环看 HTTP 成功状态,不会跑一遍每种模型与格式组合。排查误投时,应核 Worker 的真实服务配置与能力行,而不是只看绿色健康状态。

**「流式请求收到第一个块,Router 就该减一次在途。」** 首块只是传输开始。实现把额度交给响应体持有到终止;提前归还会让长流在负载统计里消失,使最少请求策略失去依据。

**「请求超时字段会限制整个音频播放时长。」** 这个名字容易让人这样理解,但 Rust HTTP 转发在响应头前使用该截止时间,响应体对象不携带它。客户端播放超时与转发后的长流治理应另行安排。

**「同目录下的 Python 命令可以直接套 Rust 参数。」** 两套入口的配置模型不同,Python 还有受管理 Worker 启动和控制面功能。排查配置不生效时先确认正在运行哪个可执行程序,不要把 Python 的启动行为归到 Rust 数据面。
