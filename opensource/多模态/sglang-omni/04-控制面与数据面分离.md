# 控制面与数据面分离

一次生成被切成若干段之后,段与段之间要搬的不再是几个 token,而是隐藏态、嵌入和音频码——这一章回答这些张量走哪条路、由谁决定、代价落在哪。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

管线里跑着两种完全不同的东西。

一种是协调:这条请求交给你、那份东西可以读了、中止、关停。它们是小结构体,要的是立刻送到、顺序不乱。另一种是数据:隐藏态、嵌入、音频码、KV 页。它们要的恰恰相反——最好别序列化、别拷贝,能原地读就原地读。

把两种东西塞进同一条通道,坏掉的是两个指标。

**首个音频包的延迟。** 流边上每一小块都要走一遍完整的序列化:打包成字节、拷进内核、再拷出来。而流式边上的块小、次数多,一次算的量本来就压不住一次搬运的固定开销,于是传输反客为主成了这一跳的大头——这一跳又正好压在首包的关键路径上。

**吞吐。** 一条通道上,大块的张量会把小消息堵在后面。中止消息排在一块隐藏态后面,意味着「立刻停」要等那一块传完才生效;而在一条七段的管线上,这种队头阻塞每一跳都来一次。

还有一层更隐蔽的浪费:统一通道把位置关系全扔掉了。同一个进程里的两段本来可以直接递一个对象引用,同一张卡上的两段本来可以直接读对方那块显存,这些便宜一分都拿不到——明明什么都没搬的两段,也要走一遍打包和拷贝。

## 二、解法

分成两条路,让它们互相不认识。

**控制面主要走小消息**,用本机的域套接字:点对点用推拉,中止用发布订阅广播出去。正常 Stage 交接主要送句柄与事件；入口提交、终端返回和小块内联是直接携带内容的例外。

**数据面走张量**,由一个路由器按这条边两端的位置关系挑一种搬法。阶段代码只说「发给谁」,从不说「怎么发」。

挑法就是最天然的那个直觉:**近的走近路**。路由器把位置关系排成一组优先尝试近路的分支；这是机制顺序,不是硬件实测的成本排名——

- 两段在同一个进程里:根本不搬,直接把 Python 对象引用递过去,不序列化也不拷贝,连控制消息都省了。
- 同一张卡、不同进程:把显存句柄塞进控制消息,对面映射过来读原地那块显存。没有中间缓冲,也不用回确认——所有权交给 PyTorch 自己的跨进程显存机制。
- 同节点的两张卡,且两卡能互相访问:走一块常驻在发送端显存上的池子,发送端占几格写进去,接收端拷走后回一条确认,发送端凭确认放掉那几格。
- 一端根本不在 GPU 上,或者两张卡互访不了:落到主机的共享内存,一块内存一份数据,接收端读完就释放。
- 两端被标成不在同一个节点:交给跨节点后端,协议由它自己选。

流式块另有一个小口子:一块在主机上的流式块,只要小到 16 KiB 以内、而且附带的元数据里不含张量,就直接塞在控制消息里过去,连数据面都不碰。

![Stage 间的传输分支：同进程对象引用、同卡直接 CUDA IPC、池化 CUDA IPC、共享内存与预留的跨节点后端。选择还取决于 Tensor 设备、互访能力及直连开关；GPU→GPU 经共享内存回退才需要 D2H 与 H2D。图中正常中间交接不涵盖入口、终端与内联内容例外](/opensource/sglang-omni/04a-one-edge-five-rungs.svg)

三个容易看漏的地方。

**这条阶梯是推出来的,不是配出来的。** 没有任意点名传输后端的统一开关。阶段上的通信设置只能调缓冲区大小、同时在飞的份数和跨节点后端的连接选项,它自己的类注释就写明了它不负责选传输方式。位置是主要条件,还要看 Tensor 所在设备与路径开关。例如 关闭载荷直连的设置 能关闭正常载荷的同卡直连；流式块不受这个载荷开关影响。

**后端只搬字节,不认识载荷。** 打包发生在后端之上:先把载荷里的张量递归抽出来、原地留占位符,把不含张量的那份壳序列化成消息头,再把所有张量拼成一个连续的字节缓冲。后端只看见一个缓冲和一段元数据。所以换后端不牵动载荷格式,换载荷格式也不牵动后端——这就是「两条路各自可以独立替换」在代码里的样子。

**分离不是“控制面绝不携带内容”。** Coordinator 的入口 SubmitMessage 直接带原始输入；Terminal Stage 的 CompleteMessage 可带最终结果,发回 Coordinator 的 StreamMessage 也可带输出块。Stage 间还允许小 CPU 流式块内联。分离主要针对中间 Stage 的大张量交接,不能把入口说成唯一例外。

KV 页也归数据面管,有一套与模型无关的搬运契约:发送端先问接收端要位置,接收端按页预留、回一个目的地句柄,发送端才按页号把页拷过去;拷完接收端提交,这些页的归属就转给它自己的请求生命周期,中途出错则回滚。它只认显存句柄那一档,而且要求两端的张量并行度相同。基准上唯一会要求它的是一套没有接进任何管线的 Scheduler 角色,那部分见 05 章。

## 三、代价

**便宜的那几档各有各的附加条件,不满足就静悄悄降级。** 同进程那一档传的是同一个对象引用,接收端必须当只读用:谁顺手改了一个张量,改的就是上游还在用的那块显存。同卡直连那一档要求这个进程看到的显存卡号没有被重映射过,而且对面是个单卡的段。差一条,这条边就退到下一档,而配置一个字都没变。

**池化那一档要押住显存。** 发送端在自己那张卡上开一块常驻池,默认算下来是 1 GB,按 64 KiB 一格切开。这块池子是这一段自己的进程用 torch 申请的,而阶段的字节预算是靠按进程的 torch 分配器上限落地的——所以它是从这一段的预算里扣的,不是额外的。而且格子要押到接收端的确认回来为止:确认慢一点,后面的块就堵在分配器上等。

**位置关系变了,吞吐跟着变,而提示只有一行。** 把两段挪到互相访问不了的两张卡上,这条边会自动退回主机共享内存,在 GPU→GPU 的共享内存回退中会增加 D2H 与 H2D；CPU 端点不必经历这两趟;降级警告每个原因只打一次,之后一切正常。

**跨节点那一档在基准上走不到。** 决定一条边算不算跨节点的,是一份远端段名单;而启动器从头到尾没有往里写过东西,它的默认值是空集。这套代码里的跨节点后端是备着的,不是当前任何一条发布出来的管线在用的。

## 四、和 vllm-omni:一处趋同,三处不一样

vLLM 社区的那套 omni 框架在同一个位置也有一层「只负责搬数据」的东西。下面四条都在它的基准 4d877780d3(tag v0.29.0rc1)上核过;点到为止,不评优劣。

**先说趋同的那一处:「搬数据的这一层不挑下一段」两边都写成了硬规矩。** 那边的模块设计文档把它列成第一条不变量,明说这一层不得挑下一段、不得实现模型专属的执行策略;这边写在路由器的类注释和通信文档里,后端不路由请求、不做扇入、不挑下游、不解释载荷。这一处不必找差异——至于那一跳真正由谁决定,两边的取舍在 02 章。

三处不一样:

1. **谁来挑后端。** 那边按边点名:部署配置里一张「从哪一段到哪一段」映射到具名 Connector 的表,外加一个兜底 Connector;96 份部署配置里 53 份写了这个块,其中 52 份点的是共享内存那一个,另有 4 处点了传输引擎类的后端。这边没有可点名的地方,由路由器从位置关系推出来。
2. **同节点上最快的那一档在不在。** 那边的 Connector 清单里没有显存句柄这一档——全树搜不到任何显存跨进程句柄的用法,同机就走共享内存或几种传输引擎。这边把同进程的对象引用和同卡的显存句柄摆在共享内存前面,共享内存也接住 GPU 互访不可用时的回退数据。
3. **接收端怎么知道可以读了。** 那边是按键去取:取不到就返回空,由上层隔一会儿再来取一次,源码注释里把这种「还没好」明确留给轮询重试。这边是发送端主动发一条就绪消息把接收端叫醒,池化或共享内存等 relay 路径由接收端确认后释放缓冲；同进程直传与直接 CUDA IPC 不用这一套 relay ACK。

![两边都必须做的五件事按行排开,各自的实现去盖这些行:搬数据的这一层要不要挑下一段,这一行两边都是同一个答案,都明确不归这一层管;这条边用哪个后端那一行,本项目是运行时的一个路由器按两端的位置关系推出来、用户写不了,对面是部署配置按边点名外加一个兜底;把对象变成可搬的字节那一行,本项目在后端之上统一抽张量再拼成一个连续缓冲、后端只见字节,对面由 Connector 自己收下整个对象并自己序列化、能直接搬原始字节的后端可以声明跳过；把字节搬过去那一行两边又是同一件事,都是一组可插拔的后端；让接收端知道可以读了那一行,本项目由发送端发一条就绪消息把接收端叫醒,对面由接收端按键轮询直到取到](/opensource/sglang-omni/04b-who-owns-which-step.svg)

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**先说清楚这一层的可调面有多小。** 不能任意点名后端；可配缓冲区、连接选项以及关闭正常载荷直连的开关,而且是按段配的。基准上没有任何一个模型家族或示例配置写过这个块——所有段都跑在默认值上。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--<段名>.comm.cuda_ipc_pool_size_mb` | 命令行点号覆写,或 YAML 阶段块里的 `comm` | 不设,由下面两项相乘得出 | 直接定这一段显存池的总大小 | 启动日志里的池分配行,带总大小、格数与每格大小 |
| `--<段名>.comm.cuda_ipc_slot_size_kb` | 同上 | `64` | 分配粒度;一次传输可占连续多格,格数等于池大小除以格大小；一次传输可能占多格,实际并发传输数还取决于载荷大小 | 同上 |
| `--<段名>.comm.slot_size_mb` | 同上 | `512` | 只在不设池大小时参与相乘;另外定跨节点后端的每格大小 | 同上 |
| `--<段名>.comm.credits` | 同上 | `2` | 共享内存那一档同时在飞的块数上限;不设池大小时也参与相乘 | 发送端卡住时先看它 |
| `--<段名>.comm.mooncake_protocol` | 同上 | `rdma` | 跨节点后端用哪种协议 | 跨节点后端的初始化日志 |
| `--<段名>.comm.mooncake_hostname` | 同上 | 不设,取本机主机名 | 跨节点后端对外声明的地址 | 同上 |
| `--<段名>.comm.mooncake_device_name` | 同上 | 空 | 指定 RDMA 网卡 | 同上 |
| `--<段名>.disable_direct_cuda_ipc_payload` | 同上 | 关 | 关掉这一段发载荷时的同卡直连档,退到池化那一档;流式块不受它影响 | 跳事件里的传输名 |
| `SGLANG_OMNI_CUDA_IPC_WAIT_THREADS` | 环境变量,也可以写进阶段的环境块 | `8` | 等显存事件完成用的线程池大小 | 传输侧事件里同卡传输的等待耗时 |
| `SGLANG_OMNI_COMM_TRACE` | 环境变量 | 关 | 打开传输侧的结构化事件,22 种 | 日志里带 `COMM_TRACE` 前缀的 JSON 行 |

**观测点分三层,从粗到细。**

第一层是请求级事件流里的每一跳:每条跳记录都带着这一跳实际用的传输名,一共六种可能——同进程对象、同卡直连、内联、池化显存、共享内存、跨节点。**一条边悄悄换了档,只在这里露出来。**

第二层是传输侧的结构化事件,要单独打开。它给的是入队等待、写缓冲、发控制消息各自的耗时,以及一条边第一次选定传输和之后每次改变的记录——后者只在首次和变化时打,所以日志里出现第二条就说明这条边真的换过档。页式 KV 搬运那一套也在这一层,从预留、就绪到拷完各有一条。

第三层是两行普通日志:显存池分配那行会打出池子多大、切成几格;同卡互访不可用时有一条降级警告,写明了从哪张卡到哪张卡、因为什么退到共享内存,并且每个原因只打一次。

**典型配置**,三套,都能直接抄走。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 默认形态,先量一遍每条边走的是哪一档 | `SGLANG_OMNI_COMM_TRACE=1 sgl-omni serve --model-path <模型>` | 拿到每条边的选档与分段耗时,换日志量暴涨;量完就关 |
| 显存紧,把自回归段的池子压小 | `sgl-omni serve --model-path <模型> --thinker.comm.cuda_ipc_pool_size_mb 256` | 省显存,换同时在飞的份数变少,流式块更容易排队 |
| 怀疑同卡直连有问题,把某一段退回池化那一档 | `sgl-omni serve --model-path <模型> --talker_ar.disable_direct_cuda_ipc_payload true` | 多一次拷贝和一次确认,换掉直连那一档的所有前提条件 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后。**

| 症状 | 先查 | 然后 |
|---|---|---|
| 某一跳突然变慢,配置却一个字没动 | 这一跳事件里的传输名,和之前比 | 从同卡直连或池化显存变成共享内存,就是位置关系变了或两卡互访不可用;降级警告那行写明了原因 |
| 流式块越堆越慢,发送端像被卡住 | 传输侧事件里的入队等待耗时 | 等得久就是格子用光了在等对面确认:要么把池子调大,要么查接收端为什么读得慢 |
| 起服务时报套接字路径超长 | 控制面的套接字目录前缀加上最长的那个阶段名 | 控制面只用本机域套接字,路径有长度上限;换一个短的基准目录 |
| 同卡两段之间没走直连 | 这一段有没有关掉直连档,以及这个进程有没有被重映射过显存卡号 | 两者任一成立就只能走池化那一档,这是预期行为不是故障 |
| 页式 KV 搬运报只支持一种传输 | 两端落在哪张卡、张量并行度是不是一样 | 这条契约当前只认显存句柄那一档,并且要求两端并行度相同,别的位置关系一律拒绝 |

## 六、常见误区

**「后端是可以配的,清单里那四个填哪个用哪个。」** README 和设计 RFC 至今写着数据面有共享内存、NCCL、NIXL、Mooncake 四种可插拔后端,安装依赖里也实打实装了 NIXL 的轮子。实际上传输方式的枚举只有四个值——同进程对象、显存 IPC、共享内存、Mooncake——而后端表里注册着五个;路由器造后端的那一步只认其中三种,别的直接抛错。**NCCL 与 NIXL 两个后端在基准上没有任何选中路径**:没有枚举值指向它们,全树也没有任何调用方按那两个名字去造它们。它们是备着的,不是当前在跑的。

**「跨节点那条路配一配就能用。」** 决定一条边算不算跨节点的是一份远端段名单,而启动器从头到尾没有往里写过东西——它的默认值是空集,全树也找不到赋值点。所以跨节点后端虽然造得出来、连接选项也能配,当前却没有任何一条边会被判成跨节点。想验证这一档,得先有人把名单填上。

**「同一张卡上就一定走直连。」** 直连那一档的条件比「同卡」多三条:目标段得是个单卡段、在另一个进程里,而且这个进程看到的显存卡号没有被重映射过。另外有四个编码与聚合段在自己的配置里主动关掉了发载荷时的直连。条件差一条就静悄悄退到池化那一档,跳事件里的传输名是唯一的现场证据。

**「共享内存那一档的块大小归那个槽大小参数管。」** 不归。共享内存那一档每次按张量的实际字节数开一块,槽大小那个值在它里面算出来之后就再没用过;真正限住它的是在飞份数那个值,默认只允许两块同时在飞。槽大小影响的是不设池大小时显存池的总量,以及跨节点后端的每格大小——调错地方会让人误以为参数不生效。

**「显存池是传输层额外要的显存,和这一段的预算无关。」** 它就在这一段自己的进程里用 torch 申请,默认算下来 1 GB;而阶段的字节预算是靠按进程的 torch 分配器上限落地的,所以池子是从这一段的预算里扣的。更容易踩的是它**懒分配**:起服务时看不出来,要等这一段第一次往外发东西才申请——一个把预算卡得刚刚好的段,会在第一条请求走到它的出边时才 OOM。

**「控制面完全不碰载荷。」** 不是。入口提交、终端 CompleteMessage 与回 Coordinator 的 StreamMessage 都可能带内容,小 CPU 块也可内联。排查大控制消息时,先辨别它属于哪一种路径；正常 Stage 间的大张量交接才主要走句柄与独立数据传输。
