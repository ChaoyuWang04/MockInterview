# 阶段与 Coordinator:框架怎么做到不认识模型

23 个模型家族、从一段到七段的管线,共用同一套流水线代码,而这套代码里没有任何一个模型的名字——这一章讲它靠什么做到,又为此付了什么。说法都在源码基准 `89e60d0bf2`(tag `v0.1.6`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

把一次生成切成多段,这件事本身不难写。难的是写完第一个模型之后。

每个模型的切法都不一样。转写模型只有一段,它既是入口也是终端;Qwen 的语音管线七段、两个终端。有的模型要某一段等齐三个上游才能开工;有的要上游一边算一边把中间结果流给下游;有的要把同一份产物按下游是谁改写成不同形状再发出去。

这些差别一旦落进框架,框架就会长出一串按模型分岔的判断:这个模型的 Encoder 输出要这样并,那个模型的 Talker 要允许先收流式块。坏掉的不是压测里某个数字,是两件更难受的事。

**接入成本没有上界。** 第 N 个模型要改框架,改完得把前面那些模型重新验一遍,因为它们走的是同一段代码。模型越多,每加一个的代价越大。

**出错的位置和写错的位置对不上。** 模型作者写的是自己那几行,炸的是框架里一个和他无关的分支;排障的人要同时懂框架和那个模型才看得懂。

所以这一章的问题不是怎么跑得快,是**怎么让框架层一行都不认识模型**。

## 二、解法

把模型能影响框架的地方收成一份清单,清单之外不留第二条通道。

框架这一侧是死的:一个阶段就是一层 IO 壳。它做的永远是那几样——从控制面收消息、把数据面读回来的东西交给自己的执行体、等齐该等的上游、把结果发给下一跳或报给 Coordinator、把流式块按边转出去。壳里没有一处按「这是哪个模型」或者「这是哪种 Scheduler」分岔。

模型这一侧塞进来的东西全是**点号导入路径**。阶段这一级一共六种:造这一段执行体的工厂、决定下一跳是谁的路由函数、声明这次要等齐哪几个上游的解析函数、把等齐的几份并成一份的合并函数、流式结束时该通知谁的函数、按下游不同把载荷改写成不同形状的投影函数。管线那一级还有一个:这条请求的终端段是哪几个。框架拿到的只是字符串,在阶段自己起来的时候导进来,当成普通可调用对象挂在固定的位置上。

**最关键的一条是:这些函数只能收窄,不能新增。** 路由函数返回的目标必须落在阶段表声明过的下一跳集合里,扇入解析函数返回的上游必须落在声明过的等待清单里,终端解析函数返回的段必须落在静态终端集合里;越界一律当场抛错,并把允许的集合打出来。于是一条请求运行时能走的图,永远是声明好的那张图的子图。框架因此既不必理解返回值的含义,也不会被一个写错的钩子带到没接线的地方去。

Coordinator 那一侧更省。它只存三样东西:入口段的名字、终端段的名字集合、每个阶段的控制端点。中间那些跳它一概不知情,那是上游阶段自己算出目标自己发出去的(Coordinator 只碰两端这件事在 01 章说过)。

![一条边上谁拥有什么:上游阶段和下游阶段都画成同一层虚线壳,壳里绿色的六个方框是框架自己的固定部件——控制面收发、扇入等齐、Mailbox 桥接、传输选择、流式路由、终端上报,每个阶段都一模一样;紫色的七个方框是模型用点号路径插进来的钩子,分别挂在工厂、路由、等待解析、合并、流结束通知、载荷投影和管线级的终端解析这七个固定插槽上,每个紫框下面都标着它的返回值必须落在阶段表声明的哪个集合里;灰色的 Coordinator 画在最上方,只有两根箭头落地,一根投给入口段,一根收终端段的结果,中间每一跳的箭头都在两个阶段之间直接连,不经过 Coordinator](/opensource/sglang-omni/02a-who-owns-what-on-one-edge.svg)

阶段和它挂的执行体之间也是一份固定合同:收件箱三种消息(新请求、流式块、流结束),发件箱五种消息(结果、流式块、出错、KV 页搬运、已准入)。壳按消息种类做事,不问对面是什么。几样可选能力靠属性名试探——有没有自己的入队口、有没有管理操作入口、有没有要注册的 KV 池——试不到就当这一段没有。

## 三、代价

**错得晚。** 阶段表的形状在配置对象建起来的那一刻就查:段名唯一、下一跳与终端标记二选一、声明了等待清单就必须给合并函数、引用到的段名都得存在。但「这个字符串导不导得进来」不在这一关——那是各段自己起进程时才知道的。一个拼错的路径不会被启动校验挡下,它会让那一段在拉起波次里倒下,整条管线随之不可用。管线那一级的终端解析函数是唯一的例外,它在主进程里解析,写错了服务根本起不来。

**试探式的能力发现会把「没实现」读成「不支持」。** 壳找不到某个可选入口就当这一段没有,而且返回的是成功。管理类操作因此要额外拦一道:Coordinator 汇总时先把标成跳过的段剔掉,权重更新这一类如果剔完一个不剩,整体判失败而不是判成功——否则一次什么都没干的更新会报成功。

**同进程那条边把「不许就地改」的纪律推给了模型作者。** 两段在同一个操作系统进程里时,载荷是直接传 Python 对象引用过去的,不序列化也不拷贝,接收方拿到的就是上游手里那个对象。框架只在一种情况下替你验:这一跳有多个下游、并且这条边上挂了投影函数时,它会走一遍投影出来的对象图,确认里面没有任何可变容器和原件是同一个,确认不了就退回去走传输那条路。只有一个下游时,对象直接过去,不验。

**保序得框架自己扛。** 同一条边上的载荷、流式块、流结束信号是各自独立的消息,到达顺序不保证。壳的做法是按「哪条请求 + 哪个上游」把到达的消息串成一条车道,后来的那个必须等前面那个做完才往下走。顺序是对了,代价是每条边每条请求都挂着一串任务,清理要跟着请求状态一起做。

## 四、和 vllm-omni 不一样的 3 处

vLLM 社区的那套 omni 框架解决的是同一类问题。下面只说两边在同一个问题上的取舍不同,不评优劣,那边的实现以他们自己的解读为准。

1. **跨段路由划给谁。** 这边划给发送端:每个阶段自己调模型给的路由函数算出下一跳,结果必须落在阶段表声明的集合里,Coordinator 不碰任何一跳。那边划给 Orchestrator:它的主循环按段、按副本逐个取输出,再由它构造并提交下一段的请求,所以控制侧的下一段请求由它编排；async-chunk 的数据仍可由 ModelRunner 与 Connector 直接交接;设计文档把这条写成了不变量——入口与阶段客户端都不得自行把请求转给下游,阶段客户端也不选下一个逻辑段。
2. **下一段怎么算出来。** 这边的拓扑是一张有向图:一段可以有多个下游,也可以有多个上游要等齐,谁接谁写在阶段表里。那边的段带整数编号,转发时取当前编号加一,请求各自带一个末段编号决定走到哪为止。
3. **形态差异吸收在哪一层。** 这边吸收在构造期:壳只认 Mailbox,段与段的差别全在工厂路径指向的那个执行体里。那边吸收在编排循环里:循环按段的执行形态分岔(扩散一条路、语言模型一条路),Orchestrator 还会按一段在模型里的角色决定要不要把多模态特征带下去。

![一次跨段交接的职责分工：SGLang-Omni 由发送端 Stage 决定下一跳、投影并发送,接收端 InputHandler 负责 fan-in 合并,Coordinator 接入口和终端；vLLM-Omni 的控制侧 Orchestrator 组织下一段请求,async-chunk 数据通路可以直接交接](/opensource/sglang-omni/02b-who-sits-on-the-hop.svg)

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**先说清楚这一层绝大部分是写不了的。** 拓扑与钩子属于模型的配置类,配置文件和命令行都只能覆写已有阶段的设置,不能增删段、也不能改接线。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| 阶段表里的拓扑 11 项:段名、工厂路径、下一跳、终端标记、路由函数、流边、流结束目标函数、等待清单、等待解析函数、合并函数、载荷投影 | 只在模型的配置类里 | 随模型 | **用户源一律写不了**,写了报路径错,并把不让写的理由一起打出来 | `sgl-omni config view --model-path <模型>` 打出模型声明的那一份 |
| `terminal_stages_fn` | 管线级,配置文件顶层或命令行点号覆写 | 随模型;Qwen 语音管线指向一个按输出模态挑终端段的函数 | 换一个可导入的函数决定每条请求的终端集合;返回值必须是静态终端集合的子集,越界这条请求直接报错 | 路径导不进来时服务起不来;逐请求的结果看事件流里 Coordinator 的终端响应 |
| `--<段名>.can_accept_stream_before_payload` | 阶段级点号覆写 | `false` | 允许这一段在自己那份载荷到达前就先开流式队列收上游的块;关着时先到的块会让这条请求失败,报错里写明是这个原因 | 事件流里这一段有没有流式块收到事件 |
| `--<段名>.process` | 阶段级点号覆写 | 随模型 | 改哪些段共用一个操作系统进程;同进程的边改走对象引用直传,跨进程的边走传输(这一项的全貌在 09 章) | 这一跳发出事件里的传输字段 |

Coordinator 上还可能有一个在途请求数上限,由首个引擎段完整、有效的准入声明派生；缺少声明时为 None,不在这一层调,见 01 章。

**观测点:按职责读事件,不要把它当成跨进程的全局时钟。** 常规路径上先是 Coordinator 准入、Stage 收到输入、fan-in 齐备、派发给 Scheduler；结果返回后先记录 `stage_complete`,再发送下一跳并记录 `stage_hop_sent`。声明的 Terminal Stage 则把结果交回 Coordinator。流式块另有首次发出、每块发出、每块收到等事件,可与正常结果交错。一段尚未出现 fan-in 齐备事件,先查它在等谁；有完成却无下一跳事件,还要结合终端声明、错误和发送进度判断,不能推断成“动态路由返回空就正常结束”。

**两个写死在框架里的数,排障时会撞到。** Stage 在线程中用 `outbox.get(timeout=0.1)` 阻塞等待消息,消息到达就可返回；0.1 秒约束的是无消息时的等待,不是每一跳固定多等 100 ms。一轮最多连取 64 条便让出事件循环。

**典型配置**,三套,都能直接抄走。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 接新模型前先看清这条管线被声明成什么样 | `sgl-omni config view --model-path <模型>`,再用 `sgl-omni config resolve --model-path <模型> --show diff` 看自己的覆写到底改了哪几项 | 多两条命令,换掉「照着设计文档猜拓扑」这一整类错 |
| 排一个路由或扇入的问题,先把语音那半条图摘出去 | 先 `sgl-omni config resolve --model-path <模型> --text-only --show config` 确认这套形态下剩哪几段,再照同样的参数起服务 | 图更短、终端只剩一个,嫌疑面小一半;代价是语音路径上的问题这样看不见 |
| 自己接的模型里下游偶发「流式块先于载荷到达」 | `sgl-omni serve --model-path <模型> --<段名>.can_accept_stream_before_payload true` | 换掉那条失败;代价是这一段会在正式载荷到来前就建起请求状态,清理更依赖中止广播 |

组合与推荐值是按语义推的起点,不是实测最优。

**症状 → 先查 → 然后。**

| 症状 | 先查 | 然后 |
|---|---|---|
| 某一段收到了输入却迟迟不开工 | 事件流里这一段有没有「扇入齐了」 | 没有就是还差上游:看这一段声明等谁、这次的等待解析函数把范围收成了什么,再回上游看那一跳发出了没有 |
| 启动时报「返回了静态拓扑之外的目标」 | 报错里打出来的允许集合 | 路由函数返回了没在下一跳清单里的段名;要么把返回值收回集合内,要么去模型的配置类里把那个段加进下一跳 |
| 请求失败,报错说流式块先于载荷到达 | 那一段有没有打开先收流式块的开关 | 打开它,或者让上游别在载荷发出之前就开始流 |
| 权重更新报成功但模型没变 | 返回里逐段的明细,看哪些段被标成了跳过 | 只有真正执行了的段才算数;全被跳过时整体会判失败,报成功说明至少有一段执行了,去那几段核 |
| 同进程两段之间偶发脏数据 | 这条边是不是同进程,以及上面有没有投影函数 | 同进程边传的是对象引用,接收方不能就地改;要改就先隔离自己要修改的数据；多下游投影检查只覆盖可变容器,不是所有 Tensor 的深拷贝保证 |

## 六、常见误区

**「Coordinator 负责把请求从一段送到下一段。」** 它叫 Coordinator,健康接口在它上面,拒绝的日志也是它打的,看着就该管路由。实际上它只碰两端:把请求投给入口段,收终端段的结果。中间每一跳都是上游那一段自己算出目标、自己发出去的。去 Coordinator 里找路由表会一无所获,要看接线得去模型的阶段表。

**「路由函数是普通 Python 函数,想返回哪一段都行。」** 它确实是普通函数,所以人们默认它自由。实际上返回值必须非空且落在阶段表声明过的下一跳集合里,空结果或越界当场抛错。扇入的动态解析、终端集合的动态解析都是同一个规矩:**只能收窄,不能新增**。这也意味着一个接新模型的人想让某一段多一个下游时,改钩子是没用的,得改阶段表。

**「段间的流式队列有上限,所以不会堆爆。」** 构造这个队列时确实传了一个 4096 进去,看着像个水位线。但那个数存下来之后没有任何地方读它,每条请求的队列是无界的——背压在发送端那一侧,不在这里。指望这个数护住内存的人会失望。

**「Scheduler 没实现管理操作会报错。」** 不会。壳按属性名试探能力,试不到就返回成功,并标一句这一段不支持。所以看一次权重更新到底有没有发生,要看逐段明细而不是看总的成功字段;只有权重更新那一类在「一段都没真执行」时才会被翻成失败,别的动作不会。

**「同进程等于免费。」** 同进程边确实不序列化不拷贝,直接传对象引用。但它只在一个下游时无条件走这条路;多个下游时框架要先确认投影出来的对象和原件不共享任何可变容器,确认不了就退回去走传输。省的是拷贝,赔的是接收方从此不能就地改自己收到的东西。

**「拓扑字段全锁死了,所以终端集合也改不了。」** 阶段那一级的 11 个字段确实一个都写不了,报错还会告诉你为什么。但管线那一级决定「这条请求的终端段是哪几个」的那个解析函数不在锁定清单里,用户源能写。它在主进程里解析,拼错了服务直接起不来;导得进来但返回了静态集合之外的段,则是每条请求各自报错。
