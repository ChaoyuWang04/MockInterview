# 奖励:多奖励服务、异步打分与可复现

对着 verl 解读的《奖励:规则、模型与沙箱》读:那边讲打分怎么从一次函数调用变成一条和训练重叠的流水线,这一页讲打分对象换成图、视频和音轨之后,这条流水线要多长出哪几样东西——一次训练挂好几个 Reward Model、每个模型自己占卡自己睡醒、分数分两层相加,以及「同一份配置跑两次分数一样」为什么今天只覆盖了打分这一段。说法都在源码基准 `b708218d5b`(tag `v0.2.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

打分慢,而且它默认站在路中间。

文本 RL 那边的奖励常常是一次规则校验,几毫秒的事。这边不是:要么是另一个视觉模型把整张图重新编码一遍,要么是一个视觉语言模型看着图作答——把图上的字念出来,再拿念出来的那串字和目标比。后者是一次完整的多模态前向加一段自回归解码。视频更贵:仓库里那个念字的打分器对视频按帧间隔抽样,抽出几帧就发几次对话请求,而且一帧一帧串着发,最后取平均。

危险不在于它慢,在于**一步的顺序把它卡在了生成和更新之间**。生成侧其实早就有一批样本做完了,它们躺着等整批齐,等的是最慢那一条;等齐了才轮到打分,打分不结束,算 Advantage 和更新一步也动不了。

第二处问题是**一个数不够用**。图像上很少只有一路信号可用:念字准不准是一路,好不好看是一路,和提示词对不对得上又是一路,视频还要另算运动质量。这几路信号的量纲差一到两个数量级、谁波动大谁统治梯度——这件事本身知识库的《多模态RL》讲过,这里不重复。落到框架上的是另一个问题:这几个打分器在同一次训练里怎么共处。它们各自要模型、要卡、要生命周期;有的能被推理引擎服务起来,有的是个普通视觉模型直接加载就能用,有的压根不在这个作业里、在别的机器上当服务跑着。

第三处是**分数复现不了**。同一份配置跑两次,奖励曲线对不上。排障时这一条最要命:改了一行,曲线变了,你分不清是改动起了作用,还是它本来就会抖。

## 二、解法

三件事:让打分与剩余 Rollout 重叠、把「谁持有模型」和「谁定义分数」切开、把几个分数合成一个。

**缩短等待靠样本级流式。** 哪条轨迹先生成完,哪条就先被送去打分,藏在剩余生成的后面——这个形状 01 章交代过,这里只补两件它没说的。一是它**不是随便就开**:首先不能配置命名 Reward Model。此前提下,纯规则、纯函数或外部服务可以流式;旧单模型路径则要求 Reward Model 有独立资源池。多个打分函数或外部服务本身并不排斥流式。Reward Model 和训练挤在一起时它一定关着,因为打分要用的显存此刻正被训练占着。二是打开之后**耗时会换个地方出现**:打分的时间被算进生成那一段,关键路径上那一段的计时掉到接近零。

![同步与流式 Reward 的示意时间轴:两图使用相同的四条样本、单个打分槽位及单样本打分时长。上图等 Rollout 全部完成才依次评分;下图每条完成即评分,前三条被剩余 Rollout 覆盖,最后一条仍留在尾部。整批评分完成后才开始 Actor 更新。图下列出流式条件,明确命名 Reward Model 不适用。](/opensource/verl-omni/06a-reward-on-critical-path.svg)

**第二件事是把模型和分数切开。** 一个有名字的 Reward Model 在这里只管三样:占哪些卡、怎么被调用、什么时候醒什么时候睡。它**不决定分数是多少**——把模型的输出变成一个数,是另一件东西的事:一个普通的打分函数,配置里给出它在哪个文件、叫什么名字。于是同一个打分器可以有好几种活法:交给推理引擎服务起来,打分函数去打那个服务;或者在打分 worker 的进程里直接加载,打分函数拿到的是一个推理句柄;或者干脆不在这个作业里,打分函数把图压成 JPEG 发到外面的服务去,回来一个数。仓库里那个偏好打分器三种活法各写了一个入口,是这一刀最干净的例子。

这一刀换来的是:换后端不用改打分逻辑,加一个打分器不用改框架。

**第三件事是合成,而且是分两层的。** 每一项配一个权重,乘起来加在一起。第一层发生在打分 worker 里:同一个管理器手上的几项各自算完,按权重乘加成一个数。第二层发生在控制器上:走原生后端的模型各自成一组,其余各项合成一个共享组,**同一批样本在每个组里都要过一遍**,然后把各组交回来的数按样本相加。所以最终那个标量是「组内加权 + 组间直加」,执行分两层,但代数上等价于把各项拉平后的加权和;中间没有新增归一或别的非线性变换。

![一次训练里几个有名字的 Reward Model 怎么摆:左边一摞灰格子是生成完的一批样本,箭头从同一个点分成两路,表示整批同时送进每一个组而不是分给其中一个;中间上下两个虚线框是两个打分 worker 组,上面那个是共享组,里面并排放着一个走引擎后端的绿色项和一个一格卡都不占的黄色项,下面那个是原生模型独占的一组,里面是一个紫色项;右上角是父资源池的四个格子竖排,前两格绿色被引擎服务连续占掉、后两格紫色是原生模型的两个完整副本,黄色那一项一个格子也不占;右下角把一条样本的账写开:共享组给出一个加权和、原生组给出另一个加权和,两个数直接相加才是这条样本的奖励。](/opensource/verl-omni/06b-named-models-and-sum.svg)

拿到这个标量之后的事在 01 章:以 FlowGRPO 为例,先比较同提示词下各样本的 Reward,得到样本间不同的 Advantage;同一轨迹各选中训练步共享该 Advantage,不是归一后在时间步之间造出差别。

**可复现是单独一件事,而且只盖住了打分。** 官方为它列了一张范围表,当前支持范围是 Reward Model 推理,生成侧和扩散采样都标着将来。支持的那一行分四层做:批不变性让一条请求的输出不受同批里有谁影响;浮点确定性把一串确定性算子、确定性通信、固定随机种子的开关打开,而且必须赶在集群起来之前设好环境变量,晚了继承不到;路由在打分副本负载相同时按请求内容的校验和挑,同一条请求每次落到同一个副本;最后是逐请求采样种子,在支持的模型、硬件与算子范围内,用相同输入、采样参数和种子提高重复打分的一致性,不是跨环境的绝对保证。

## 三、代价

**第一笔:两个招牌今天只能二选一。** 挂了有名字的 Reward Model,流式就关了——判断流式条件的那个函数一看到它们就返回假,官方限制清单的最后一条也明写着这件事。因此命名 Reward Model 与流式目前不能同时使用;这不等于多个打分函数或外部服务不能流式。

**第二笔:契约是一条一条的。** 管理器接口的形状就是「一条样本进来,一个数出去」,打分 worker 靠并发把一批条目同时发出去。对外部服务和引擎服务这没问题,并发正好撑满对面;对一个就在本进程里的 GPU 打分器,这等于一条一条喂。所以仓库里三个自带模型的打分器各写了一套模块级的异步队列加消费者循环,把并发到达的请求重新攒成批再送进模型——**攒批这件事没有被框架接过去,是每个打分器自己重复了一遍**。

**第三笔:卡是手排的。** 原生模型的位置是父资源池里的格子下标,人手写在配置里;引擎模型按配置顺序从池头连续切走;两者不能重叠,重叠了在启动时报错。纯函数打分器更直白——视频那套配方里,两个打分器各自在参数里写死了用哪一块卡。批在组内按 worker 数补齐再均分,**没有动态负载均衡,也没有工作窃取**,流式那条路上选哪个 worker 干脆是随机挑的。

**第四笔:框架只做加法,不做校准。** 合成就是权重乘加,权重总和只被校验大于零,不做归一。知识库那一篇反复强调的「合成之前先按当前策略这一批估均值和标准差」,框架这一侧一个字都不做——要做就得写进自己的打分函数里。

**第五笔:开启 offload 时,原生模型的「睡」是整个丢掉。** 引擎那条的睡醒是引擎自己的那一套;原生那条的睡是把模型对象置空、调一次收尾、垃圾回收、清一次显存缓存,醒来时从头构造一遍。Reward Model 小的时候这无所谓,大了就是每步一次加载。而且睡之前要等在飞的推理排空,它会挡在那里。

**第六笔:同一件事在两条路上记账口径不同。** 流式那条路合批时只收每条样本都带的键,只在部分样本上出现的键被整批丢掉;有名字的模型那条路取并集,缺的填空。于是「某一项在少数样本上失败」这件事,在一条路上看得见,在另一条路上看不见。

## 四、和 verl 的奖励不一样的四处

**第一,「三类」不是同一个三类。** 那边章表把打分方式分成规则、模型、沙箱三类,痛点写成「打分慢就堵住整步;代码类任务还要起沙箱」。后半句在这边没有对应物:打分对象是图、视频和音轨,没有要执行的代码——沙箱那一块配置随着上游结构一起继承了下来,本仓库这一侧没有任何代码读它。取而代之的第二个痛点是量纲。分类的轴也跟着换了:那边按「拿什么判」分,这边按「模型在谁家」分——引擎服务的、打分 worker 进程里的、作业之外的。

**第二,重叠是不是主路径。** 那边序章把打分流水线和生成循环并称两个 loop,并且写明「在新一代训练器里都是主路径,不是可选项」;这边重叠是**有条件的**:不使用命名 Reward Model,并且没有框架托管的模型,或者旧单模型路径使用独立资源池。而且这两个条件里的第二个默认是关的,第一个又和「挂多个 Reward Model」互斥。**从那边读过来的人最容易在这里踩空**——以为重叠照旧是默认,结果打分整个待在关键路径上,而且没有任何提示。

**第三,卡的分法多了一层。** 那边把放置单列一章,回答的是四个角色共卡还是分卡;这边奖励这一路在拿到父池之后还要**在池内再切一次**:引擎模型按配置顺序从池头连续占,原生模型按写死的下标挑,不占卡的那些项什么也不拿。所以同一句「给奖励一张卡」,在这边要回答两个问题:父池从哪来,以及池里的哪几格归谁。

**第四,可复现挂在哪一章。** 那边把逐位确定性放在训推不一致那一章,治的是同一段文字两侧算出的概率对不上;这边的确定性开关挂在奖励这一路上,治的是同一张图两次打分不一样,而且范围表明写只覆盖 Reward Model 推理这一段,生成侧与扩散采样都标着将来。两边治的不是同一种不一致。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**参数在哪调。** 三处入口:奖励这一整块的配置组、命名模型各自的配置子块、以及写在某一项打分函数名下的额外键(它们被原样转发给那个函数当入参,外部服务的地址、超时、重试就走这条)。另有几个环境变量只管某一个打分器的采样。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `reward.num_workers` | 启动配置 | `8` | 共享组起这么多个打分 worker,按 Ray 节点轮转;原生模型那一组的个数由它自己的放置决定,不看这一项 | worker 的名字前缀与个数 |
| `reward.reward_manager.name` | 启动配置 | `VisualRewardManager` | 换 `MultiVisualRewardManager` 才挂得了多项;全模态那条线换回 verl 自带的 `naive`;音轨输出用 `AudioRewardManager` | 启动日志里建出来的管理器类名 |
| `reward.custom_reward_function.path` / `name` | 启动配置 | 空 / `compute_score` | 单项打分的入口。开了 Reward Model 就必须给,不给启动直接报错;走多奖励时这两项被拿去挂一个占位函数 | 启动报错点名这两项 |
| `reward.reward_functions` | 启动配置 | 空 | 多奖励的入口,每项写清文件、函数名、权重、必不必需;这四项之外的键原样转发给打分函数 | 启动日志里每项一行,带权重与是否必需 |
| `reward.reward_functions.<项>.weight` | 启动配置 | `1.0` | 乘在这一项的分上;总和只被校验大于零,**不做归一** | 指标里每一项自己的均值 |
| `reward.reward_functions.<项>.required` | 启动配置 | `false` | 真:这一项失败整步抛;假:记 0 分、记一次错误,其余项照常 | 指标里这一项的错误计数 |
| `reward.aggregation` | 启动配置 | `weighted_sum` | **没有任何代码读它**,加权求和写死在管理器里 | — |
| `reward.models` | 启动配置 | 空 | 挂命名 Reward Model。一挂上,流式打分就关了,而且管理器必须是多奖励那个,引用模型的项还必须自带打分函数 | 启动报错 |
| `reward.models.<名>.backend` | 启动配置 | **必填** | `engine` 交给推理引擎服务;`native` 在打分 worker 进程里直接加载;别的取值直接报错 | 启动报错 |
| `reward.models.<名>.offload` | 启动配置 | `true` | 打分前醒、打完睡。原生那条的「睡」是把模型对象整个丢掉,下一步重新构造 | 显存曲线与打分那一段的耗时 |
| `reward.models.<名>.placement.devices` | 启动配置(原生) | **必填** | 父池里的格子下标,不是显卡号也不是并行的 rank;一个下标起一个完整副本 | 启动报错列出撞上的下标 |
| `reward.models.<名>.replicas` | 启动配置(引擎) | `1` | 世界大小 = 它 × 张量并行 × 数据并行 × 流水并行;和下一行的乘积要是世界大小的整数倍 | 启动报错里的两个数 |
| `reward.models.<名>.n_gpus_per_node` / `nnodes` | 启动配置(引擎) | 空 / 空 | 这个模型要占父池多少格;两项必须一起给 | 同上 |
| `reward.reward_model.enable` | 启动配置 | `false` | 旧的单模型路径。和命名模型互斥,两个一起开直接报错;开了它就必须显式给打分函数 | 启动报错 |
| `reward.reward_model.enable_resource_pool` | 启动配置 | `false` | 真:奖励角色拿一个独立父池,流式打分才开得起来;假:用全局池,而且下一行两项被改写成训练器的值 | 总卡数;打分那一段的计时 |
| `reward.reward_model.n_gpus_per_node` / `nnodes` | 启动配置 | `8` / `0` | 独立父池的大小;开了独立池两项都必须大于零 | 启动报错 |
| `reward.reward_model.model_path` | 启动配置 | 空 | Reward Model 路径;命名模型各自的路径盖过它 | 打分请求里带的模型名 |
| `reward.reward_model.rollout.name` | 启动配置 | **必填,无默认** | 打分的引擎后端;命名的引擎模型没写时自动填 `vllm` | 启动报错 |
| `reward.reward_model.rollout.tensor_model_parallel_size` | 启动配置 | `2` | Reward Model 的张量并行,它直接乘进世界大小 | 起服务的进程数 |
| `reward.reward_model.rollout.gpu_memory_utilization` | 启动配置 | `0.5` | 打分引擎的显存预留;和训练共池时往低调,独占卡时往高调 | 显存曲线 |
| `reward.reward_model.rollout.free_cache_engine` | 启动配置 | `true` | 假:打分引擎不睡不醒,独占一张卡时该这么设 | 显存曲线 |
| `reward.reward_model.rollout.response_length` | 启动配置 | `2048` | 它就是打分请求的最长回答;为空或零才回落到 4096 | 打分回答被截断的样子 |
| `reward.reward_model.rollout.full_determinism` | 启动配置 | `false` | 打开走可复现那一套。**它要求旧单模型开关为真**,所以挂了命名模型就走不到它 | 启动时导出的那几个环境变量 |
| `reward.reward_model.rollout.seed` | 启动配置 | `42` | 浮点确定性与逐请求采样共用的种子;各副本用同一个,不按副本号偏移 | 同配置复跑两次比曲线 |

| `reward.reward_model.rollout.profiler` | 启动配置 | 跟全局剖析器 | 打分服务端自己的剖析器;训练器在真正打分的那一段前后开关它 | 剖析产物目录下的奖励子目录 |
| `reward.accelerator_workers.enabled` | 启动配置 | `false` | 把打分 worker 绑到训练卡的格子上,给自己写的、要用卡的打分函数用;和旧单模型开关同时开直接报错 | 启动报错 |
| `GENRM_OCR_TEMPERATURE` 等四个 | 环境变量 | 打分器自带 `0.7` / `0.8` / `4096` | 只管念字那个打分器的温度、核采样、最长回答与种子,不经过配置 | 打分回答的稳定程度 |

**怎么看。** 这一章看四处。一是**打分的时间记在哪一段**:流式打开时它被算进生成那一段,关键路径上那一段的计时接近零;没打开时它自己是独立的一段。判断流式到底开没开,比读配置快的办法是看这两段计时的比例。二是**每一项自己的曲线**:多奖励管理器按项名报出每项的分、每项自带的附加信息,以及合成后的那个数,指标层再给它们各加一层前缀求均值——**只看合成分会漏掉「一维塌了另一维猛涨」**,这一条知识库里写过,这里只说键在哪。三是**启动日志里每个子奖励一行**,带着权重、必不必需、是不是协程;项数对不上就在这里看。四是**打分服务端的剖析器**:它和生成侧的副本是同一套,训练器在真正打分的那个窗口前后开关它——流式时那个窗口是生成阶段,关键路径上时是打分阶段;外部 HTTP 服务不在这套里,它的耗时得去它自己那边量。

**典型配置。** 基于完整官方配方的四个调整方向,不是完整启动命令。

| 什么场景 | 在默认起法上加什么 | 拿什么换什么 |
|---|---|---|
| 先把奖励这一段跑通 | 什么都不加:管理器用默认的,打分函数指到仓库自带的压缩率打分器 | 不占卡不联网,流式天然是开的;代价是这个信号很弱,只够验证链路 |
| Reward Model 是瓶颈 | 开独立资源池并给它一两张卡,引擎后端填 `vllm`,把打分引擎设成不睡、显存预留调高 | 旧单模型路径可用独立卡换取重叠,但仍可能留下打分尾部;命名模型不适用 |
| 一次要挂好几路信号 | 管理器换成多奖励那个,每项写清文件、函数名、权重;要用卡的项在它自己的额外键里指定卡号 | 换来多路信号,代价是多个命名模型与流式今天二选一,而且量纲得自己在打分函数里校准 |
| Reward Model 大到不该和训练放一起 | 打分函数换成仓库自带的 HTTP 客户端,地址、超时、重试写在这一项名下;训练作业里不给奖励留卡 | 训练侧一张卡都不为打分留,而且并发天然撑满对面;代价是多一个要自己运维的服务,剖析器也看不到它 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 一步比预期慢一大截,生成那一段却不长 | 打分那一段的计时占比 | 先辨别是否使用命名模型或旧单模型共池;纯函数及外部服务不要求独立 GPU 池 |
| 打开流式后打分那一段的计时掉到接近零 | 生成那一段是不是同步变长了 | 这是预期:时间被记到生成那一段去了,不是打分变快了 |
| 挂了命名模型之后流式没了 | 有没有配命名模型 | 命名模型不参与流式,是明写的限制;要流式就退回旧的单模型路径 |
| 启动报某一项引用了不认识的模型 | 项名和模型名对不对得上 | 同名自动绑定,名字不同要显式写;而且引用了模型的项必须自带打分函数 |
| 启动报格子重叠 | 原生模型的下标 | 引擎的分配从池头连续占,原生的下标不能落进那一段,也不能和别的原生撞 |
| 打开确定性开关曲线还是对不上 | 旧单模型开关是不是真 | 确定性的环境变量只在它为真时导出,而它和命名模型互斥 |
| 换成多奖励管理器之后确定性失效 | 打分请求里有没有种子 | 多奖励那个管理器不注入采样参数,种子要由打分函数自己带 |
| 某一项的错误计数在指标里找不到 | 走的是流式还是关键路径 | 流式合批只收每条样本都带的键,只在部分样本上出现的计数被整批丢掉 |
| 打分 worker 起不来,说共置数不够 | 用的是不是绑在训练卡上的那种打分 worker | 父池的共置数要至少是 2 |
| 原生模型每步都在重新加载 | 那个卸载开关 | 原生那条的睡是整个丢掉对象,要常驻就把它关掉 |
| GPU 上的打分器慢得像一条一条来 | 这个打分器自己有没有攒批 | 管理器契约是一条一条调的,要批只能打分器在模块里自己再攒一次 |
| 打分请求打到了一个随机初始化的小模型 | 模型路径给了没有 | 念字那个打分器的默认模型名是测试用的小模型 |

## 六、常见误区

- **照着确定性那篇文档的示例去填打分的引擎后端。** 它的配置示例把那个字段写成了全模态那个引擎的名字,而另一篇讲多奖励的文档明写「全模态引擎不做奖励服务」,仓库里 33 个官方配方**无一例外**填的都是另一个名字。**两篇官方文档在这一点上对不上,以配方为准**;确定性那一段真正落地的开关在别处,不靠这个名字。

- **以为异步奖励默认就开着。** 71 个启动脚本里 33 个开了引擎 Reward Model,其中只有 6 个给它独立的卡;剩下 27 个的打分就在训练卡上、老老实实待在关键路径里。异步奖励是官方专门写了一页的功能,但示例里它是少数派,而且不开的时候一行提示都没有。
- **以为挂了好几个命名 Reward Model 还能流式。** 不能。官方限制清单最后一条明写命名模型不参与流式,代码里判断流式条件的那个函数一看到它们就返回假。**这是这一章最该先记住的一条:两个招牌今天只能二选一。**
- **以为打分那一段的计时掉下去就是打分变快了。** 开了流式之后打分的时间被算进生成那一段。拿前后两次的打分计时比「优化效果」,比的是记账位置,不是真实耗时。
- **以为权重会被归一。** 不会。总和只被校验大于零,之后原样乘加。而合成之前要按当前这一批把各分量校准到同一个量纲,是知识库那一篇反复强调的前提,框架这一侧一个字都不做——量纲差一到两个数量级时,权重写成多少都不代表你以为的那个意思。
- **以为配置里那个「合成方式」的字段起作用。** 它有默认值、有文档、十来个启动脚本显式写了它,可仓库里没有任何代码读它。加权求和是写死在管理器里的,那个字段改成别的值也不会报错。
- **以为原生 Reward Model 的卸载是搬到主存。** 引擎那条是引擎自己的睡醒;原生那条在 offload 开启时把模型对象置空、调一次收尾、垃圾回收、清显存缓存,下一步从头构造一遍。模型不大时无所谓,大了就是每步一次完整加载——而且睡之前还要等在飞的推理排空。
- **以为放置里写的是显卡号。** 写的是父资源池里的格子下标。一个下标起一个完整副本,不是分片模型里的一个 rank;下标不能落进引擎已经占掉的那一段,也不能和别的原生模型撞。
- **以为打分是按批送进去的。** 管理器的契约是一条样本一次调用,打分 worker 靠并发把一批同时发出去。这对外部服务和引擎服务正好,对一个就在本进程里的 GPU 打分器就是一条一条喂。仓库里三个自带模型的打分器各写了一套模块级的异步队列加消费者循环来补这一刀,上限还各不相同。
- **以为可复现开关一开就全链路可复现。** 范围表写得很清楚:当前支持范围是 Reward Model 推理,生成侧和扩散采样都标着将来。更要紧的是它的门槛——那几个环境变量只在旧的单模型路径上导出,而多奖励那条路根本走不到;就算走到了,多奖励那个管理器也不往打分请求里塞种子。另外它**不管采样参数**:温度、核采样仍然各配各的,打分器自己带的默认值优先。
- **以为子奖励失败会让你知道。** 默认是不必需:失败记 0 分、记一次错误、训练继续。更隐蔽的是流式那条路上合批取的是交集,只在部分样本上出现的错误计数会被整批丢掉——曲线上什么都看不出来,只是那一项的分被零拉低了。要它出事就停,得把那一项显式标成必需。
- **以为视频打分就是图像打分多几帧。** 念字那个打分器对视频按帧间隔抽样、一帧发一次请求、串着发,最后把各帧的分取平均。帧数一多,这一条样本的打分时间是线性涨的,而且这一路上没有任何攒批。
