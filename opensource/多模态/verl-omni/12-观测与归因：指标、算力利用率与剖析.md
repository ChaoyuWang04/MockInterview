# 观测与归因：指标、算力利用率与剖析

训练变慢时,怎样分清是在等生成、等打分,还是 Actor 计算本身不够高效。说法都在源码基准 `b708218d5b`(tag `v0.2.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**同样的一步变慢,可能需要完全不同的处理。** Rollout 长尾、Reward 服务等待、Actor 前向和反向、权重同步都会影响训练进度。只有总耗时,无法判断该加生成资源、调整 micro-batch,还是减少同步开销。

阶段名称也不能直接当成硬件活动。默认扩散流程的生成计时可以包含流式 Reward,共卡时还包含 Rollout 进入 sleep 的交接。看到生成阶段变慢,并不能立即归因于去噪计算。反过来,Actor 算得更快,也未必缩短被 Rollout 主导的一步。

## 二、解法

**先定位墙钟时间花在哪,再缩小到调用内的计算。** 训练器记录各阶段耗时、样本吞吐与学习指标;worker 则估算 Actor 训练和 log-prob 重算的 MFU。MFU 表示模型计算量相对于设备理论峰值的比例,这里的分子来自架构公式,不是硬件计数器直接测出的指令量。

扩散不能只按文本 Token 数估算。计数器读取 latent 与提示词序列长度,结合架构的线性层和 Attention 结构,再乘参与本次调用的时间步数及前向次数。Qwen-Image 的联合 Attention 与 Wan 的自注意力加交叉注意力分别建模;CFG 引起的额外前向也纳入估计。它统计的是训练调用的形状,不应直接拿完整生成步数代替。

![训练计时与 MFU 范围图:默认扩散一步包含生成、训练和权重交接,验证另计;Actor MFU 使用内部计算调用的耗时,以及数据并行组内的模型计算量估计、组规模和单设备峰值,不以整步耗时作分母。](/opensource/verl-omni/12a-timing-and-mfu-scope.svg)

图中采用的计算口径是:组内估计计算量,除以调用耗时、数据并行组规模和单设备峰值的乘积。序列长度先在数据并行组内汇总,分母也使用同一组规模。训练估算包含前向和反向;只有前向的调用再除以 3,沿用前向加反向约为前向 3 倍的估计约定。

**需要证实瓶颈时再看时间线。** PyTorch profiler、Nsight Systems 或 Ascend profiler 用于观察算子、通信和等待;RL-Insight 汇总长期指标与 Rollout 状态时间线。前者帮助解释一次调用,后者帮助观察整个作业的变化,都不能由一个 MFU 数字替代。

## 三、代价

**模型估计有适用边界。** 当前内置 Qwen-Image、SD3、Wan 与 MiniMax-H3 的估算器,未注册架构会警告并给出零值。已注册也不代表覆盖所有变体:SD3 额外 Attention 层会触发未完整建模的警告。零值与低值都应先检查计数器是否适用,再判断硬件是否空闲。

LoRA 仍按完整模型的前向加反向计算量统计,冻结权重实际省去的部分反向没有相应扣除,因此报告值可能高估实际执行计算量。设备峰值也必须采用一致的精度与稠密计算口径。跨模型、跨硬件或改变并行方式后,MFU 不宜直接排名。

**采集本身也要占资源。** 多角色、多 rank、连续多步的 trace 会增大文件与采集开销。验证样本的图像、视频和音频还需要转换、编码与上传;本仓媒体辅助函数服务于 W&B 样本展示,不是 profiler。比较性能时应保留同样的采集条件,并把样本质量检查和计算效率判断分开。

## 四、和上游 verl 的关系

| 共同任务 | 本仓采用什么 | 新增的职责 |
|---|---|---|
| 记录实验指标 | verl 的 Tracking 与 MFU 指标命名 | 扩散按样本、时间步组织指标,并包装多模态验证样本 |
| 估算模型计算量 | 保留计算量除以时间和设备峰值的思路 | 新增扩散架构公式、latent/提示词长度与时间步元数据 |
| 采集性能 trace | verl 的分布式 profiler 基础设施 | 在默认扩散循环中控制 Actor、Rollout、Reward 等角色的采集边界 |
| 在线监控 | verl 的 RL-Insight logger 与状态记录接口 | 入口启用客户端,补充 vLLM-Omni 的 sleep、唤醒等状态 |

同名指标只是便于统一观察,不是口径完全相同的证明。文本吞吐按 Token,本章扩散 helper 按批内样本数;视频样本也不因此变成每秒帧数。MFU 中汇总范围与归一化的组规模,也应与具体 worker 实现一起核对。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `global_profiler.tool` / `global_profiler.steps` | 扩散主配置 | 均为 `null` | 选择工具和采集步;仍须启用具体角色 | 对应步是否产生 trace 文件 |
| `actor_rollout_ref.actor.profiler.enable` / `ranks` | Actor profiler 配置 | `false` / `[]` | 启用并限制 Actor 采集范围 | Actor 输出目录与 rank |
| `actor_rollout_ref.rollout.profiler.enable` | Rollout profiler 配置 | `false` | 另行采集生成服务,不随 Actor 自动开启 | Rollout replica 的 trace |
| `reward.reward_model.rollout.profiler.enable` | Reward profiler 配置 | `false` | 为受管 Reward 服务开启采集 | Reward 专用输出目录 |
| `global_profiler.save_path` | 扩散主配置 | `outputs/profile` | 指定常规 profiler 输出目录;Ray 的 Nsight 文件另有位置 | 文件实际路径与时间戳 |
| `global_profiler.profile_continuous_steps` | 扩散主配置 | `false` | 连续选中步共用采集区间 | 相邻步骤之间是否保留时间线 |
| `VERL_OMNI_DEVICE_FLOPS_TFLOPS` | 作业环境变量 | 未设置,沿用 verl 设备峰值查询 | 覆盖单设备 BF16 稠密峰值,仅改变估计归一化 | MFU 与设备规格口径 |
| `trainer.logger` | 主配置 | `[console, wandb]` | 加入 `rl_insight` 启用对应监控客户端 | 标量是否到达监控端 |
| `RL_INSIGHT_SERVER_URL` | 作业及 Ray 环境变量 | 官方接入要求显式提供地址 | 指向所有节点可访问的监控服务 | worker 到服务的连接与数据时间戳 |
| `actor_rollout_ref.rollout.disable_log_stats` | Rollout 配置 | `true` | 监控引擎指标时设为 `false` | 每个 replica 的统计指标 |
| `transfer_queue.metrics.enabled` | V1 队列配置 | `false` | 暴露队列指标端点,与是否启用队列本身分开 | 队列指标是否注册并可访问 |

**先认清指标覆盖范围。** 下表描述默认扩散循环及其 helper,不是给所有入口承诺同一计时边界。

| 观测项 | 统计什么 | 不能据此断言什么 |
|---|---|---|
| `timing_s/*` | 各计时块墙钟耗时;流式 Reward 可落在 `gen` 内 | 把所有字段相加就得到无重叠总时间 |
| `perf/time_per_step` | `step` 计时;含权重同步及条件触发的 Checkpoint,不含后续验证 | 作业全程平均一步耗时 |
| `perf/throughput` | 批内样本数除以 step 耗时及调用方传入的 GPU 数 | 所有部署布局天然采用相同 GPU 成本口径 |
| `perf/mfu/actor` / `perf/mfu/actor_infer` | Actor 训练调用与旧策略 log-prob 重算的估计 MFU | 全作业 GPU 利用率或 Rollout 引擎利用率 |
| `critic/rewards/zero_std_ratio` | 同提示词样本 Reward 标准差为零的组占比 | 存在一个单独的 Critic Worker |

**配方方向。** 在对应官方完整训练脚本上选择观测范围,这些组合不代表已经采集成功。

| 场景 | 调整方向 | 拿什么换什么 |
|---|---|---|
| 默认扩散入口中 Actor 更新慢 | 选一个训练步、Actor 的一个 rank,启用 PyTorch profiler 与 CPU/CUDA 内容 | 缩小 trace,先看局部计算与等待 |
| 怀疑打分拖慢生成 | 同一步启用 Rollout 与 Reward 服务各自的 profiler;引擎侧使用离散采集 | 增加采集开销,核对实际重叠关系 |
| 长时间或多节点运行 | 接入 RL-Insight,打开引擎统计;V1 另开队列指标端点 | 增加外部监控依赖,连续观察各角色状态 |

组合与推荐值是按语义推的起点,不是实测最优。

**入口边界必须先核对。** 默认扩散入口具有按步启停的 profiler 生命周期;扩散 V1 虽能由入口把 TaskRunner 放到 Nsight 下,当前没有同样的按步协同启停,不能直接照搬默认入口的控制器采集窗口。Nsight 需要各节点已有工具与相应依赖,报告位置由 Ray 管理。开启配置后,仍需检查目标步是否实际运行、文件是否生成且可打开。

| 症状 | 先查 | 然后 |
|---|---|---|
| MFU 为零或异常偏低 | 未注册架构、变体警告、序列长度与设备峰值 | 再用 profiler 检查计算和通信,不要先改 batch |
| Actor MFU 上升,整步没变快 | Rollout、Reward、同步的阶段耗时 | 优化实际关键路径,不要只追一个局部比例 |
| 开了 profiler 却没有文件 | 入口、角色 enable/rank、目标步是否被恢复点跳过 | 检查工具依赖、实际输出目录和服务端日志 |
| RL-Insight 只有标量没有引擎或队列数据 | 引擎统计开关、队列指标开关和各节点可达性 | 分别验证端点;安装包不等于服务已经运行 |

## 六、常见误区

- **把 Actor MFU 当成整个集群忙碌程度。** 它的计时范围比一步训练窄,外部排队与权重交接可以很慢,同时 Actor 调用内部仍很高效。
- **看到 Reward 阶段很短就排除打分瓶颈。** 流式打分发生在生成窗口内,独立计时块可能只是收取已有分数。
- **看到 LoRA MFU 更高就认定执行了更多有效算力。** 估算没有按冻结权重扣除反向,应同时比较同条件下的调用耗时与样本吞吐。
- **以为只打开全局 profiler 就覆盖所有进程。** Actor、生成服务和 Reward 服务各有开关;V1 的生命周期边界也不同。
