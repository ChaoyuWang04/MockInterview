# 模型接入:两个适配器与两张注册表

对着 verl 解读的《模型接入:两条路》读:那边一个新模型要选的是两条接入路径里的哪一条,两条都落在训练侧;这一页讲当生成侧也得自己写一个适配器之后,「接一个模型」变成了什么。说法都在源码基准 `b708218d5b`(tag `v0.2.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一个扩散模型要在这里训起来,**同一个模型得在两套毫不相干的运行时里各跑一遍**。生成侧在多模态推理引擎的进程里跑完整条带噪采样循环,把算法需要的训练片段与成品交回来;训练侧在训练引擎的进程里,只把这条轨迹上选中的某一步重新前向一次,算当前策略下的 log-prob。两边是两个仓库、两套代码路径、两个进程,可两侧的 log-prob 必须具有一致的含义——策略梯度使用的是概率比 exp(当前 log-prob − 旧 log-prob),不是把两个 log-prob 直接相除。

麻烦在于「概率口径一致」不是自动成立的。它要靠一长串逐条对齐才成立:轨迹里每个张量叫什么名字、提示词编码出来是什么形状、用哪个采样调度器、注意力用哪套实现、中间状态存成什么精度、探索噪声按什么种子选在哪几步。这里面任何一条对不上,**程序都不会说「不一致」**。

它坏的方式很隐蔽。权重还一次都没更新,第一步的比值就已经不等于 1;裁剪全落在偏低的那一侧,另一侧一次都不触发。官方排障文档里记了三个现场,两个的根因都是某一侧把中间状态存成了低精度,另一个是两侧算旋转位置编码时用的序列长不是同一个——一侧按有效 token 数算、一侧按补齐后的宽度算,补齐位之后的 token 全拿到错的位置。更隐蔽的是探索噪声:同一个提示词的几条轨迹如果在不同的时间段注入噪声,组内的奖励差里就混进了一份和策略无关的成分,Advantage 估计跟着失真。官方记过一次对照,同一份配置只改这一处,一边 28 步就塌了,一边跑过 181 步还在涨(官方数字)。

第二处麻烦:这个仓库要接的不是「一个模型」,是**一个模型和一个算法的组合**。同一个架构配不同的 RL 算法,训练侧要重新前向的东西根本不一样:有的在反向采样的轨迹上逐步重算,有的直接在干净隐变量上加噪再预测一次,还有的一行数据就是一对样本、一步里压根没有生成这一段(01 章)。所以「这次训练该用哪个适配器」不能只看模型是谁。

第三处:有些模型标准扩散库根本载不进来——它们自带一套架构定义和权重格式,不走那条自动加载。

## 二、解法

三句话:通常按模型与算法的组合组织包,包里分别实现 Rollout 与训练适配器;两张注册表按「架构名加算法名」分发;两侧共用的东西收进包外的公共模块。

包的标准构成是三个文件。**生成侧适配器**继承推理引擎里那个模型的流水线类,把确定性采样换成带噪采样,按算法需要交回训练片段、最终隐变量与提示词编码,log-prob 则按配置返回,再声明自己吐的是图还是视频、带不带音轨。FlowGRPO 通常只保留选中的 SDE 窗口;DPO/NFT 主要用最终隐变量,不要求交回完整去噪链。**训练侧适配器**实现四个类方法:建调度器、设时间步、把微批拼成这个架构认识的前向入参、前向一次并采样上一步。第三个文件放两侧都要用的东西——噪声时间表、提示词模板这一类;它的存在本身就是那份契约的物理体现:凡是必须两侧一致的,就别让两边各写一份。

![接一个模型的结构图:最上面是两个上游依赖,推理引擎提供模型流水线、标准扩散库提供 transformer 与调度器配置,适配器只是缝合层;中间左右两大列分别是生成侧运行时和训练侧运行时,各自要写一个适配器文件;正中那一列把两侧必须逐条对齐的六项契约横排下来——架构名与算法名、采样调度器、提示词编码、轨迹字段名、数值精度、注意力实现——每一行都横跨两侧,表示这一项两边写的必须是同一个东西;最右一列是这一项对不上时会看到的症状,从启动报错到比值第一步就偏,全都不会有人告诉你「不一致」。](/opensource/verl-omni/02a-two-adapters-one-contract.svg)

两张注册表都是普通的字典,键都是那个二元组。架构名不是自己起的,它必须逐字等于模型目录里那份索引文件写的类名,启动时自动读出来;算法名来自配置里的一项。**同一个算法名还被配置模板引用成 Advantage 估计器的默认名**,所以改它会一次换掉三样东西:训练侧适配器、生成侧适配器、算哪种优势。

两张表查不到时的反应不一样,这一点很要紧。训练侧查不到直接抛错,顺手把已注册的键全打出来;**生成侧查不到却是静默的**——框架只是不去替换流水线,于是引擎用上游原版的那条,而原版不注噪声、不交回轨迹。所以生成侧那一半注册漏了,表现不是起不来,是跑起来之后训练侧拿不到该拿的东西。

同一个架构的第二个算法几乎不用重写。训练侧适配器直接继承第一个,只覆写变了的那一两个方法;最薄的那个只有一行类声明,没有方法体。图生图是同样的套路再加一层:继承一个图生图基类和那个文生图适配器,补两个钩子——一个从微批里把条件图的隐变量取出来,一个把它拼进前向入参、再在输出上切回原长度。「不许静默退化成文生图」这件事确实有人挡,但**挡它的不是这个基类**:两侧共用的那个前向入参构造函数先判断这个适配器属不属于图生图这一类,属于就要求它交出来的条件非空——交回空值和交回空字典分别报两种错,并把微批里有哪些键一并打出来。基类自己的注入方法反倒是放行的:条件为空就原样返回、退化成文生图,那条路留给直接调用它的人。

载不进标准扩散库的模型,**只换一步**。训练侧适配器上有个「这个模块怎么造出来」的钩子,默认返回空表示走标准加载;返回一个自己写的模块,引擎就直接拿它用。那个模块继承另一条基类,自己负责加载权重、声明分片边界、接 LoRA、存盘。注册键、调度器、轨迹字段、精度这些契约一条不变,所以它不是第二套接入方式,只是同一套接入方式换了个加载动作。

全模态那条线的键换了一套。自回归模型的适配器和算法无关——算法走 verl 已有的配置字段,于是训练侧的键变成「架构名加阶段」:同一个模型训思考那一段还是说话那一段,才是要分发的维度。生成侧那张表更松,键只有一个流水线名字,查不到返回空且明确不报错,它本来就是可选的。

![注册键分发图:左上两个方框是启动时拿到的两个字符串,架构名从模型目录的索引文件自动探测、算法名来自配置,两者合成一个二元组去查两张注册表;中间是九个扩散架构乘六种算法的网格,格子左半填绿表示生成侧注册了、右半填紫表示训练侧注册了、两半齐全才算一对适配器、空格表示这个组合根本没有注册,从图上能一眼看出一个架构横向铺满了五种算法而其余架构大多只占一格,另有一格只填了左半、一格只填了右半;下方两块黄色面板是偏离主路的两条岔路,一条是标准扩散库载不进来的模型改走自写模块的加载钩子,另一条是全模态线把键换成架构名加阶段、而且生成侧那张表是可选的。](/opensource/verl-omni/02b-registry-dispatch.svg)

## 三、代价

四笔。

**第一笔,算法进了键,组合就成了笛卡尔积。** 一个架构支持五种算法就是五个包。继承能把每个包压得很薄,但包数跟着算法涨,而且注册表只认精确的二元组:训练侧少一个组合就会启动报错,不会退回同架构的另一个算法;Rollout 侧缺项则回退上游流水线。当前这 17 个包摊开来是 9 个扩散架构配 6 种算法,再加 2 个全模态架构各一个阶段。

**第二笔,一致性靠约定,不靠类型。** 注册表只查键在不在,不查两侧到底对不对得上。字段名要逐字一致,精度要人肉保证;注意力后端倒是有一道启动校验,但那只是那串清单里的一条。**能自动拦的错都在启动时炸,拦不住的全都表现成数值慢慢跑偏。**

**第三笔,默认加载路径依赖两个上游的模型支持。** Diffusers 提供 Transformer 与调度器配置,vLLM-Omni 提供 Rollout 流水线。缺少支持时需要额外实现,但训练侧可以通过模型适配器的 自定义模块构建 钩子绕过 Diffusers 自动加载。走自写模块那条路等于把上游没有的架构自己抄一份进来——最大的那个包因此成了这一块里最大的一个,光那份本地重写的架构文件就 26 KB,而且引擎为此打的警告写得很直白:自定义加载出来的模块,引擎那一层的钩子(注意力处理器、梯度检查点包装、LoRA、精度提升)可能只部分生效,甚至静默失效。

**第四笔,初始化是无条件全量导入。** 包初始化逐个导入这 17 个包,每个生成侧适配器又在模块顶层导入推理引擎里对应的流水线类,一处保护都没有。结果是:只做训练的进程也会导入这些包及其 Rollout 适配器;上游少一个模型,整个框架起不来。

## 四、和 verl 模型接入不一样的四处

**第一,要跨的东西不同。** 那边一个新模型要选的是两条接入路径里的哪一条,两条都在训练侧,选完就只剩训练侧的事;这边要写的是两个适配器,分别活在两个进程、两套代码路径里。所以两边章表上那句看着一样的痛点——「接进来数值对不上」——说的不是同一件事:那边对不上的是同一段文字两侧算出的概率,这边先对不上的是数据格式本身,概率的事还排在后面。

**第二,算法在不在键里。** 那边把算法变体挡在训练循环外面,靠的是另外两张注册表(Advantage 估计和策略损失);它们和模型接入是两件独立的事,加一个算法不用动模型。这边算法名直接进了模型注册键,同一个架构配不同算法就是两个不同的适配器、两个不同的包。换来的是每个算法可以有自己的前向形状,代价就是上一节那笔笛卡尔积。

**第三,体量差了四倍。** 那边模型接入占全仓 8%;这边占 32%,是全仓最大的一块。多出来的基本上是生成侧那一半:这边每个模型都得额外有一个跑采样循环的生成侧适配器,而且它普遍比训练侧那个厚,最悬殊的一对差了 5 倍以上。更值得注意的是这一块内部的比例——真正公共的契约代码只占 13%,另外 87% 是 17 个包各自的适配器。**这层抽象没有把重复消掉,只是把重复框住了。**

**第四,全模态那条线反而更像 verl。** 它的适配器和算法无关,算法照旧走 verl 的配置字段,键退回「架构名加阶段」,生成侧那张表还是可选的。所以这条线上「接一个模型」的形状和那边更接近——它的在线 Policy Gradient 训练器本来就是直接继承 verl 的(01 章)。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `actor_rollout_ref.model.algorithm` | 启动配置 | `flow_grpo` | 注册键的后一半;它同时是 Advantage 估计器的默认名 | 启动报错里打出的已注册键清单 |
| `actor_rollout_ref.model.architecture` | 启动配置 | 空,从模型目录的索引文件自动探测 | 注册键的前一半;自写模块那条路没有索引文件,必须显式给 | 同上 |
| `actor_rollout_ref.model.external_lib` | 启动配置 | 空 | 查表前先导入这个库,仓库外的适配器靠它把自己注册进来 | 启动日志里的导入行 |
| `actor_rollout_ref.model.extra_tokenizers` | 启动配置 | 空 | 多个切词词表的模型要一个词表一条;键名由生成侧适配器定 | 生成侧读不到键时报错 |
| `actor_rollout_ref.model.attn_backend` | 启动配置 | `_flash_3_varlen_hub` | 训练侧的注意力实现 | 启动校验 |
| `actor_rollout_ref.rollout.rollout_attn_backend` | 启动配置 | `FLASH_ATTN_3_HUB` | 生成侧的注意力实现;和上面一项不成对直接起不来 | 启动报错 |
| `actor_rollout_ref.rollout.max_prompt_embed_length` | 启动配置 | 空,退回流水线的最大序列长 | 多编码器模型拼完之后的提示词编码长度;短了直接报错 | 启动报错点名这一项 |
| `actor_rollout_ref.rollout.max_num_seqs` | 启动配置 | `1024` | 生成侧适配器没声明支持整请求批处理时,这个值被压回 1(批处理本身见 03 章) | 日志里那行「压回 1」 |
| `actor_rollout_ref.rollout.step_execution` | 启动配置 | `false` | 打开后走逐步生命周期,同一个适配器的另一条执行路径,不另开注册项(两种批处理的取舍见 03 章) | 步内出现的计时段 |
| `actor_rollout_ref.model.lora_rank` | 启动配置 | `0` | 大于 0 走 LoRA,适配器的校验钩子在配置期就跑 | 启动报错里适配器给的说明 |
| `actor_rollout_ref.model.target_modules` | 启动配置 | `all-linear` | 有的架构的权重同步通路带不动这个默认值,适配器直接拒绝 | 启动报错列出它认的那几类 |
| `actor_rollout_ref.model.transformer_subfolder` | 启动配置 | `transformer` | 权重与配置在模型目录下的哪个子目录 | 加载报错 |
| `actor_rollout_ref.model.config_path` | 启动配置 | 空 | 另一条训练后端从这里读模型配置,不填就用权重目录 | 加载报错 |
| `actor_rollout_ref.model.model_stage` | 启动配置(全模态线) | `thinker` | 全模态注册键的后一半:这次训哪一段 | 启动报错里的已注册键 |
| `VERL_USE_EXTERNAL_MODULES` | 环境变量(全模态线) | 未设 | 设成本包名,让 verl 主动导入它,那些注册才会跑 | 报「没有注册」却确认写过适配器时先查它 |

**典型配置。** 三套能直接抄走的起法:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 标准扩散库能载的文生图模型 | 架构名交给自动探测,算法名用默认;新包里两个适配器各一个文件,调度器直接复用公共的那个带噪调度器 | 最省事,前提是两个上游都已经支持这个模型 |
| 同一个架构再加一个算法 | 架构名不动,只换算法名;训练侧适配器继承已有的那个、只覆写要变的方法,生成侧同理 | 用继承换掉重写,代价是包数跟着算法涨,而且新组合必须两侧都注册,漏了生成侧不会报错 |
| 标准扩散库载不进来的模型 | 训练侧适配器覆写造模块的钩子,返回一个继承另一条基类的自写模块;架构名必须在命令行上显式给 | 换来能训上游没适配的架构,代价是自己维护一份模型实现,而且引擎级钩子可能只部分生效 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测。** 这一章要看的东西集中在启动阶段和第一步。启动阶段有四处:注册表查不到时打出的已注册键清单、注意力后端不成对时的启动校验、LoRA 目标模块被适配器拒绝时给出的可用清单、以及并发被压回 1 的那行提示。第一步有两处,都在训练指标里:更新前的比值应接近 1,裁剪可以完全不发生;**如果比值系统性偏离 1、裁剪长期偏向同一侧,优先检查精度、调度器、位置编码与批形状是否一致**。走自写模块那条路的,还要在加载日志里找那行「引擎级钩子可能只部分生效」的警告——它说明这次加载绕过了引擎的一部分处理。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报「没有为这个组合注册模型」 | 报错里打出来的已注册键清单 | 架构名要逐字等于模型目录索引文件里的类名,算法名要等于配置里那个值;自写模块那条路没有索引文件,架构名必须显式给 |
| 起得来,但训练侧说轨迹字段缺了 | 生成侧那张表里有没有这个组合 | 生成侧查不到是静默的,引擎会用上游原版流水线,而原版不注噪声、不交回轨迹 |
| 第一步比值就低于 1,裁剪全落在低的那一侧 | 是不是某一侧把中间状态存成了低精度 | 轨迹里的隐变量要全程单精度,前向前才转成模型精度 |
| 只有打开逐步执行时比值才偏 | 两侧算旋转位置编码时用的序列长是不是同一个 | 一侧按有效 token 数算、一侧按补齐后的宽度算,补齐位之后的 token 全拿到错的位置 |
| 奖励方差越训越大,训练很快崩掉 | 探索噪声的窗口种子是按请求选还是按卡选 | 按请求选会让同一个提示词的几条轨迹在不同时间段注入噪声,方差里混进一份和策略无关的成分 |
| 并发调大了生成还是一条一条来 | 生成侧适配器有没有在自己类上声明支持整请求批处理 | 没声明就被压回 1;**继承来的那份声明不算数**,这是注册装饰器干的(压回 1 之后的吞吐影响见 03 章) |
| 打开 LoRA 就起不来,报目标模块不支持 | 目标模块那一项是不是还停在默认值 | 有的架构的权重同步通路只认几类投影,适配器在配置期直接拒绝默认值 |
| 起不来,报注意力后端不匹配 | 训练侧和生成侧那两项 | 它们是成对的,融合实现配融合实现、原生实现配原生实现 |
| 图生图模型报条件为空 | 生成侧有没有把条件图的隐变量交回来、键名对不对 | 分发器要求图生图适配器返回非空条件;条件隐变量的键名不能和算力统计保留的那个撞 |

## 六、常见误区

- **以为注册表是按模型分的。** 它按「架构加算法」分。同一个模型换个算法就是另一个适配器,训练侧表里没有这个组合就启动报错——好消息是它报错时把整张表打出来,照着看比翻代码快。真正会咬人的是反过来:改了算法名,Advantage 估计器的默认名跟着变了,而你以为只换了一个适配器。
- **以为两张表查不到的反应是一样的。** 训练侧查不到直接炸,生成侧查不到静默放行,引擎转而用上游原版的流水线。这是这一章里最值得记住的一条不对称:**漏注册生成侧不会让你起不来,只会让你训不动。**
- **以为架构名可以自己起一个好记的。** 它必须逐字等于模型目录里索引文件写的那个类名,一个字母都不能差。自写模块那条路没有这份索引,必须在命令行上显式给——给错了的表现和没注册完全一样。
- **以为把并发调大生成就批起来了。** 生成侧适配器要在自己的类上显式声明支持整请求批处理;注册装饰器发现这个类自己没写,就直接在它身上补一个「不支持」,**继承来的那份声明不算数**。这是注册那一刻发生的事,所以放在这一章;被盖掉之后吞吐掉成什么样、该盯哪一行日志,见 03 章。
- **以为两侧只要各自都能跑就算对上了。** 第一步、权重还没更新的时候,比值本来就应该接近 1。低于 1 而且裁剪长期偏向同一侧,应先排查训推一致性;低精度中间状态是官方记录的一种原因,不是唯一原因。这个错最贵的地方在于它长得像「算法不收敛」,于是人去调学习率和裁剪范围,越调越远。
- **以为注意力后端是两边各调各的。** 它是启动时校验的一对:训练侧选了融合实现,生成侧必须选对应的那一个,否则直接起不来。这一条是少数几个被自动拦住的,剩下的契约项没有这个待遇。
- **以为探索噪声怎么选无所谓,反正是随机的。** 按请求选和按卡选,曲线完全是两回事:前者把「噪声打在哪几步」变成了组内的一个额外变量,组相对算法会把它当成策略的差别学进去。
- **以为每个包都一定是一对适配器。** 有两个不是:一个只有训练侧,因为离线偏好那条线一步里根本没有生成;一个只有生成侧,注册了但当前没有任何配方走它。照着「一定有两个文件」去翻会扑空。
- **以为走自写模块那条路只是换了个加载方式。** 引擎会明确警告:注意力处理器、梯度检查点包装、LoRA、精度提升这些引擎级钩子可能只部分生效。换句话说,这条路换掉的不只是加载动作,还有一截你本来白拿的处理。
