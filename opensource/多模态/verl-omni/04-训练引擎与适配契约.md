# 训练引擎:两条后端与一套适配契约

对着 verl 解读的《训练引擎抽象与六个后端》读:那边讲一个引擎基类怎么把好几种训练框架收编成同一组生命周期方法,这一页讲同一套契约换成去噪轨迹之后多出了哪一层、为什么这边只剩两条后端、以及并行方式怎么组合上去。说法都在源码基准 `b708218d5b`(tag `v0.2.0`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

文本模型的一次更新,前向是一条序列过一遍网络;**扩散 Policy Gradient 的一次更新,前向是一张二维的表**——一批轨迹先切成微批,每个微批再遍历选中的训练时间步,梯度累积的步数是这两个数的乘积。一条视频轨迹本来就长,再乘上去噪步,单卡装不下是常态,只能靠并行方式组合着来:参数按卡分片、长序列再横着切开、数据并行的组数还得够大才摊得开。

麻烦在于,**能组合出哪几种并行方式,不是训练循环说了算,是训练后端说了算**。一个后端能把这个架构加载进来、能给你切序列、能给你切专家;换一个后端,这三样可能只剩一样。而多模态生成模型偏偏是最需要换后端的那一类:架构一年换好几茬,哪个库先支持它,训练就得先落到哪个库上。

于是如果训练循环直接写在某个后端的接口上,换一次并行组合就等于重写一遍循环——取一批、算 Advantage、更新、同步权重这条顺序流,会被分片、卸载、聚参数这些细节搅成一团。这一章要解决的就是这件事:**把「模型怎么算一步」和「参数怎么摆在卡上」切开**,切口就是那套两条后端都得实现的适配契约。

## 二、解法

契约分成八件事,覆盖训练生命周期,具体调用取决于算法与配置。按调用顺序是:启动时报出自己的并行布局;把模型建起来并摆上卡;给每个去噪步准备输入、收下输出;把一次前向反向按微批和去噪步两层展开;走一次优化器;存档与续训;把权重聚回整张交给生成侧;最后是 LoRA 那一套(按后端能力提供)。

最关键的一处不是方法多,而是**布局是问出来的,不是读配置猜出来的**。worker 起来的第一件事是问引擎:我是第几个数据并行组、我这个进程要不要负责把结果收上去;拿到答案才去登记分发协议。于是控制器发一次调用,数据摊成几份、由谁收回来,全看引擎当时怎么答。换后端换的是答案,不是这段代码。

第二处是**模型怎么算一步根本不归后端管**。每一步喂什么、收什么,两条后端调的是同一个模型适配器——接一个新模型只写一次,两边逐字复用。存档也是同一个分片存档管理器。所以八件事里真正分岔的只有三件:并行布局怎么建、模型怎么装进来、有没有 LoRA。

![训练引擎适配契约的结构图:左列是一次更新里契约要求的八件事,右边两列是两条训练后端各自怎么落,颜色按整行走——绿色那两行画成横跨两列的一个方框,表示两边用的是同一份代码(模型适配器与分片存档管理器);紫色三行是各写一遍但行为与输出格式已经对齐(双层前向反向、走一次优化器、把权重交给生成侧);黄色两行是各用各的机制、能力并不相同(报并行布局、建模型并摆上卡);红色那一行只有默认那条后端有,另一条在构造时直接拒绝;顶上的灰条是训练 worker 与控制器那条顺序流,它只调左列这几件事,并行布局也是启动时问引擎要来的,所以换后端时循环一行都不用动。](/opensource/verl-omni/04a-engine-contract.svg)

**两条后端各适合什么**,说到底就是那三件事的取舍。默认那条自己动手:用通用扩散库把模型加载进来,分片、混合精度、区块编译、梯度检查点一项一项自己配;长序列横着切也在这条上,不过真正切序列的活交给模型库去做。好处是全程在自己手里,LoRA、把输入留在主存逐步搬上卡、把梯度归约推到最后一次反向,这些优化都能往上加,但推迟梯度归约可能提高峰值显存。Diffusers 不能自动加载的架构,也可以让模型适配器通过 自定义模块构建 接管加载。另一条反过来:把建模型和并行化整包交给一个外部训练库,自己只当转接头。好处是白得那个库的并行能力,比如多出一维切专家;坏处是能力边界由对方定——切序列和 LoRA 今天都是直接拒绝。

## 三、代价

**第一笔:契约只覆盖「怎么算一步」,不覆盖「怎么把模型建起来」。** 后者只能各写一遍,而接第二条后端时,这「一遍」写得相当难看:它绕过对方训练器的构造函数手工造一个空壳,再把对方的建模、并行化、建优化器几步分别调一遍,然后从壳里把模型和优化器取走;为了让这几步肯跑,还得填一份根本用不上的训练参数——批大小、轮数、数据路径,全是摆设。这份耦合钉死在对方的内部方法上,对方一改结构就断。它说明增加后端有维护成本;至于为什么只实现两条,代码本身并不能证明作者的全部取舍。

**第二笔:两条后端的能力不对等,所以「换后端只是配置问题」这句话是有前提的。** 前提是你要的那几样两边都有。LoRA 只有默认那条有,背后是一个混入类加一份专门的收集与导出工具;切序列同理。更隐蔽的是按算法分的那道岔:默认那条按算法族注册了三个模型类型,另一条只注册了策略梯度那一个——走直接偏好、或者走那条噪声感知微调路线的配方,压根没有第二条后端可选。

**第三笔:两层展开把显存账变复杂了。** 默认那条给了两个优化开关,但都默认关着,而且砍的不是同一块——一个动输入,一个动梯度,谁是瓶颈得先量出来,不是两个一起打开就算数。两个也都不是白拿的:一个把每一格变成一趟同步的主存往返,另一个用更高的峰值去换更少的通信次数。

## 四、和 verl 的引擎抽象不一样的四处

**第一,后端选择更少,而且第二条随时可能没有。** 那边收编了六种训练框架;这边只有两条,并且第二条是可选依赖——包初始化时用异常包着导入,装不上就直接把那个名字置空,注册表里自然也不会有它。所以在那边换后端是选型题,在这边先是安装题:官方安装文档自己写着:那个库要的底层框架版本和生成侧那套推理依赖要的对不上,得跳过依赖解析硬装,而且在当前这套依赖上,完整的训练跑还没验证过。

**第二,抽象是那边的,这边加的是行不是层。** 引擎基类、注册表、把引擎包成角色的 worker 类,都来自那边;这边没有另起一套抽象,只是往同一张注册表里添了几行。注册键是「模型类型 + 后端名 + 设备」三元组,所以两边的后端名撞上也不打架——这边添的是新模型类型那几行。(接模型那两张表按架构名加算法名分发,和这张表不是一回事,见 02 章。)

**第三,契约里多了一层,而这一层没有共用的地方可放。** 一次前向反向要按微批和去噪步两层展开,是契约上没有预留的形状,结果就是两条后端各写了一遍几乎同构的双重循环。这段重复不是疏忽,是契约的粒度停在「一次前向反向」上,而扩散把这一次拆成了一张表。

**第四,权重交出去的方式更简单,也更粗。** 那边另有一层分片导出契约,用设备网格加放置方式声明参数怎么分布,归权重通路那一章管;这边两条后端都是在自己的导出函数里就地把分片张量聚回整张、统一加同一个前缀,然后流式交出去。省掉一层的代价是精度和聚合时机都写死在各自的实现里:一条固定转成一种半精度,另一条用配置里写的那个。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**先说入口。** 换后端不是改一个字段,是换一整套配置模式:配置组里那一项一换,Actor 与 Reference Model 两边的配置块一起跟着换,另一条后端的字段就不认了。两套配置块混着写,会在解析配置时被当成未知键顶回来。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `diffusion/model_engine` | 启动配置(配置组) | `dp_diffusion` | 换成 `veomni_diffusion`:Actor 与 Reference Model 整套配置模式切到另一条后端 | 解析出来的配置块名 |
| `actor_rollout_ref.actor.strategy` | 启动配置 | `fsdp` | `fsdp2` 走新一代分片接口;`veomni` 走另一条后端,要配合上一行一起改 | 启动日志里建出来的引擎类名 |
| `actor_rollout_ref.model.model_type` | 启动配置 | `diffusion_model` | 直接偏好与噪声感知微调那两条各改成自己的取值;**另一条后端只注册了默认这一个** | 起不来时报找不到注册项 |
| `actor_rollout_ref.actor.fsdp_config.fsdp_size` | 启动配置 | `-1`(全体) | 设成每节点卡数:分片组关在节点内,跨节点聚参数没了 | 多机下每步的通信占比 |
| `actor_rollout_ref.actor.fsdp_config.ulysses_sequence_parallel_size` | 启动配置 | `1` | 大于 1 把长序列横着切开;要求扩散库版本够新,否则启动直接报错 | 启动报错;数据并行组数随之变小 |
| `actor_rollout_ref.actor.fsdp_config.param_offload` | 启动配置 | `false` | 打开省显存,代价是每次前向反向多一趟主存往返 | 显存曲线与更新那一段的耗时 |
| `actor_rollout_ref.actor.fsdp_config.optimizer_offload` | 启动配置 | `false` | 打开后优化器状态与更新都挪到主存,更新那一段变慢 | 同上 |
| `actor_rollout_ref.actor.fsdp_config.offload_policy` | 启动配置 | `false` | 新一代分片接口专用;打开后由它接管参数摆放,上面两个开关被置回关 | 参数所在设备 |
| `actor_rollout_ref.actor.fsdp_config.reshard_after_forward` | 启动配置 | `true` | 设 `false`:前向后不再重新分片,省一次聚参数,吃显存 | 峰值显存 |
| `actor_rollout_ref.actor.fsdp_config.model_dtype` | 启动配置 | `fp32` | 训练时留空会被强制成单精度;多机配方一律写半精度 | 启动日志里的模型大小 |
| `actor_rollout_ref.actor.ppo_micro_batch_size_per_gpu` | 启动配置 | **必填,无默认** | 调小是激活显存爆掉时的第一手;调大摊薄集合通信,到一定尺寸后收益很快见底 | 前向反向那一段的耗时 |
| `actor_rollout_ref.actor.enable_timestep_staging` | 启动配置 | `false` | 打开后轨迹留在主存、逐步搬上卡;官方验证范围只有一个模型配两种算法、且序列没横着切 | 峰值显存与更新耗时要一起量 |
| `actor_rollout_ref.actor.use_no_sync_for_gradient_accumulation` | 启动配置 | `false` | 打开后梯度归约推到最后一次反向;通信次数降,峰值显存升 | 峰值显存 |
| `actor_rollout_ref.actor.optim.lr` | 启动配置 | `1e-6` | 两条后端的优化器配置类不同,学习率调度的可选项也不同 | 指标里的学习率 |
| `actor_rollout_ref.actor.grad_clip` | 启动配置 | `1.0` | 裁剪阈值;范数不是有限值时,这次更新整个跳过 | 指标里的梯度范数 |
| `actor_rollout_ref.model.enable_gradient_checkpointing` | 启动配置 | `true` | 关掉省一趟重算、吃显存;开着时算力利用率的口径要按多出的那趟修正 | 峰值显存 |
| `actor_rollout_ref.model.attn_backend` | 启动配置 | `_flash_3_varlen_hub` | 老卡换成上一代那个取值;装不上时启动直接失败,不会偷偷降级 | 启动报错 |
| `actor_rollout_ref.model.use_regional_compile` | 启动配置 | `false` | 打开后把重复的模块块先编译一遍;只在新一代分片接口且序列没横着切时可用 | 首步耗时 |
| `actor_rollout_ref.model.fsdp_layer_prefixes` | 启动配置 | `["transformer_blocks."]` | 低秩权重分层聚取按这个前缀走;对不上会报一个参数都没收到 | 同步权重时的报错 |
| `actor_rollout_ref.rollout.layered_summon` | 启动配置 | `false` | 参数卸到主存时应当打开,否则同步权重这一步容易爆显存 | 同步权重那一段是否爆显存 |
| `actor_rollout_ref.actor.veomni_config.ulysses_parallel_size` | 启动配置 | `1` | 另一条后端上设成非 1 直接抛不支持 | 启动报错 |
| `actor_rollout_ref.actor.veomni_config.expert_parallel_size` | 启动配置 | `1` | 另一条后端独有的一维并行 | 启动日志里的并行状态 |
| `actor_rollout_ref.actor.veomni_config.model_dtype` | 启动配置 | `bfloat16` | 它同时是权重交给生成侧时的导出精度 | 同步过去的张量精度 |

**多机怎么取值。** 没有单独的机制,只是这几个旋钮换一组值:分片组大小设成每节点卡数,把聚参数关在节点内;前向后不再重新分片,拿显存换速度,再靠两个卸载开关兜回来;注意力后端换成新的那个取值;拓扑两项按实际节点数与每节点卡数填;批大小按总卡数等比放大,每卡微批保持不变。生成与打分各占几张卡不在这一页。

**典型配置。** 基于完整官方配方的三个调整方向:

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机先跑通 | 选择对应模型配方,设置每卡微批;算力利用率不够再确认两个卸载开关都关着 | 作为起点;长序列需另测显存 |
| 长序列放不下 | 把序列横着切开(大于 1),每卡微批降到最小,梯度检查点开着;还不够再打开逐步搬运输入 | 拿通信和一趟重算换容量;数据并行组数变小,集合通信占比升 |
| 模型只有那个外部库支持 | 配置组换到另一条后端,配置块整套改成它那一份,切序列与 LoRA 都别想 | 拿能力换「装得进去」;白得一维切专家 |

组合与推荐值是按语义推的起点,不是实测最优。

**观测。** 这一章看三处。一是引擎有没有建出来:启动时那个引擎类名就是注册表查到的那一行,查不到直接失败,不会降级。二是梯度范数:它每步都报,不是有限值时只打一行警告,就把这次更新整个跳掉——**没有单独的跳过标志,但非有限的梯度范数仍会返回并进入指标,日志也会警告**。三是每卡算力利用率与前向反向那一段的耗时,用来判断卸载和微批调得对不对,口径在观测那一章。

| 症状 | 先查 | 然后 |
|---|---|---|
| 起不来,报找不到注册项 | 模型类型与后端名这一对组合 | 另一条后端只注册了策略梯度那一个模型类型,也不支持昇腾 |
| 起不来,报未知键 | 是不是两套配置块混着写了 | 配置组一换,另一条后端的字段就不认了 |
| 前向反向阶段爆显存 | 每卡微批 | 先调小它,再考虑卸载 |
| 更新或同步权重时爆显存 | 两个卸载开关,以及分层聚取 | 先开优化器卸载,参数卸载放最后;参数卸到主存时分层聚取必须开着 |
| 算力利用率低得离谱 | 两个卸载开关是不是都开着 | 都关掉收益最大;中等长度下把序列横着切是净亏,关掉还能把数据并行组数撑大 |
| 奖励曲线突然不动,损失正常 | 日志里的梯度范数警告 | 范数不是有限值时更新被跳过;结合梯度范数指标和警告确认 |
| 换到另一条后端后省不下显存 | 有没有把那两个开关也带过去 | 逐步搬运输入与推迟梯度归约在那条上不存在 |
| 同步权重时报一个参数都没收到 | 分层聚取的前缀 | 它要和模型的分片层命名对得上 |
| 多机比单机慢很多 | 分片组大小 | 不设就会跨节点分片,每步都在网络上聚参数 |

## 六、常见误区

- **以为默认就是新一代分片接口。** 官方安装文档确实写着默认用新一代;可配置里那个字段的默认值是上一代,新一代是各个配方脚本自己显式写上去的——71 个启动脚本里 31 个写了新一代、3 个写了上一代、2 个写了另一条后端,其余 35 个一个字没写,吃的就是那个上一代的默认值。**照文档那句话去读配置,会读出一个和实际不符的结论。**
- **以为换后端只是换一个字段。** 换的是一整套配置模式:Actor 和 Reference Model 的配置块一起换,另一条的字段会被当成未知键顶回来。更要紧的是能力边界——LoRA、把序列横着切、按算法分出来的那两个模型类型,在另一条上都不存在。
- **以为两条后端的差别是快慢。** 官方在 64 张卡上拿同一份配方对过一次:每卡吞吐 0.079 对 0.077 张每秒,每步 100 秒对 105 秒,基本打平(官方数字)。选哪条不是性能题,是「模型装不装得进去、要不要 LoRA」。
- **以为一次更新只过一遍模型。** Policy Gradient 按选中训练步展开,NFT 也遍历抽出的 `train_timesteps`;DPO 则按微批做单次训练计算。前两者的梯度累积步数是微批数乘选中训练步数。拿文本侧的经验去估每卡微批,第一次就会爆。
- **把参数卸载当成万能的省显存手段。** 官方的调优顺序写得很明确:先两个卸载开关都关着跑,爆了先开优化器卸载,参数卸载放到最后。反过来先开参数卸载,吞吐掉得最狠;而且一旦开了,同步权重那一步的分层聚取就必须跟着开,不然照样爆。
- **以为把序列横着切总是更省。** 在中等序列长度上,它的全交换通信比省下来的显存更贵,而且它还吃掉数据并行的组数、让每个分片变大。官方建议是先关掉试。
- **以为梯度范数只是个观测指标。** 它不是有限值时,这一步的梯度被清空、优化器根本没走。会打印警告,非有限范数也保留在指标中,只是没有额外的跳过计数,曲线看起来像是「学不动」。
- **以为 Reference Model 是另一套东西。** 它用的是同一个引擎类,只是配置上标成只前向:不建优化器,而且会被强制按只前向的方式摆放,手动搬家的调用对它直接返回、不生效。
