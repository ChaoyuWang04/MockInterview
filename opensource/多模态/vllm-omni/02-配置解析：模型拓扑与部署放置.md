# 配置解析：模型拓扑与部署放置

这一页说明模型结构、部署文件与启动参数怎样汇成每段可执行的配置,以及换卡、改预算时哪些东西可以变。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

Qwen3-Omni 的 Thinker、Talker、Code2Wav 承担不同计算,却必须对阶段身份、交接方式和终端输出有相同理解。把配置全写进模型代码,换卡就要改模型;全部开放给部署文件,又可能把语音链的中间段删掉,留下能启动却接不起来的组件。

真正的问题是:**换部署时,怎样只改变资源安排,保留模型已经实现的计算结构。** 即使没有改结构,同一个显存预算还可能同时出现在基础配置、平台分支和命令行里。若最终执行侧各读一份,排障就会变成猜哪个值生效。

## 二、解法

先把两种事实分开。模型拥有 PipelineConfig,负责声明有哪些 stage、各段执行类型、上下游和最终输出。部署拥有 DeployConfig,负责设备、并行度、预算和连接器设置。前者定义可以运行的结构,后者决定这次怎样运行它。

**配置解析先选结构,再给结构里的每一段补上部署。** 通常从 checkpoint 元数据识别注册的 pipeline;部署文件也能明确选择已经注册的结构变体。随后按阶段编号匹配部署条目,为每段生成带类型的运行配置,交给后面的运行时。把同一设备分给两个 stage 是共卡,不会因此把它们合成一个 stage。

![模型注册结构决定阶段集合,部署配置按阶段编号附着资源设置,显式启动覆写随后进入各段配置;同样的三段结构可以分别采用 CUDA 与 NPU 放置,不会因为设备数改变而增删阶段](/opensource/vllm-omni/02a-config-resolution.svg)

**平台分支解决“同一个模型,不同设备”的差异。** Qwen3-Omni 的默认配置在 CUDA 上让 Thinker 独占设备,Talker 与 Code2Wav 共卡;NPU 分支则让 Thinker 跨设备并行,并调整后两段的放置与图捕获设置。改变的是部署安排,阶段身份和顺序保持一致。

最后得到的是 OmniConfigResolution:所用配置路径、各段配置和选中的 pipeline 汇在同一个解析结果里。AR、Generation 与 Diffusion 的配置分别构造,把引擎字段分给各自的消费者,避免把某一种执行引擎的专用参数直接塞给所有阶段。

## 三、代价

**自由度有边界。** 部署文件可以选模型已经提供的结构,不能仅靠增删部署条目创造新的计算阶段。自定义拆分要先实现并注册相应 pipeline;框架提供的专门扩展也有自己的校验路径,不等同于任意修改拓扑。

**默认值不再只有一个来源。** 未提供部署文件时会加载模型指定的随仓配置;提供自己的文件后,解析器使用这份文件。只写一个预算值的短文件,并不天然继承原来的设备、连接器和采样设置,需要显式声明继承关系。

**优先级依字段职责而异。** 普通引擎参数可以在平台配置之后接受显式启动覆写;阶段是否分块还要服从整条链的兼容约束;模型要求的采样约束也不能被部署默认冲掉。记住“命令行最后赢”不足以解释所有结果。

**解析成功不是容量验证。** 配置层能识别部分不兼容组合,但实际显存是否够、共卡是否相互拖慢,仍要在目标模型与硬件上验证。这一章核的是配置机制,没有执行 GPU 性能实验。

## 四、和 sglang-omni 的配置解析对照

两边都把可运行的拓扑交给模型实现,允许用户调资源放置。对照基准为 89e60d0bf2,差异在于怎样表达并解释一次覆写。

| 要解决的事 | vLLM-Omni | sglang-omni |
|---|---|---|
| 区分结构与部署 | 模型的 PipelineConfig 与部署配置分开,部署按阶段编号匹配 | 模型配置类同时承载结构与部署默认,路径可见性规则限制用户能改的字段 |
| 决定哪个值生效 | 分别合并部署继承、平台分支及有对应消费者的启动字段;结构与模型约束另行保留 | 用户源先化为配置 patch,按来源层级与具体度排序,冲突检查后统一应用 |
| 追溯一次修改 | 需要连同选中的 pipeline、部署文件及平台分支检查 | 解析结果附带 provenance,记录基线、来源及校验后的值 |

本项目的选择适合把经过验证的部署配方随模型一起提供。使用者先选择配方,再局部调预算;理解某个值时,也必须知道它属于结构、部署还是模型约束。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

**先确认继承了什么,再改一段。** 自定义 YAML 用 `base_config` 指向基准文件;相对路径按当前覆写文件所在目录解析。`stages` 和 `platforms` 中的阶段条目按 `stage_id` 合并,不是用列表位置替换整段。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--deploy-config` | 命令行 | 不指定;加载 pipeline 指定的随仓文件,未指定随仓文件则用部署类默认 | 更换本次部署来源 | 核对实际文件及它的 `base_config` |
| `pipeline` | YAML 顶层 | `null`,自动识别 | 选择注册结构变体,可能改变阶段数量与输出能力 | 未注册名称会报错;查看启动阶段数 |
| `base_config` | YAML 顶层 | 不继承 | 保留基础配方并局部修改 | 同时检查基础文件与平台分支 |
| `devices` | YAML 每段或 `--stage-overrides` | schema 为 `null`;Qwen3 默认依次为 `"0"`、`"1"`、`"1"` | 改变设备放置与共卡竞争 | 阶段日志、设备占用 |
| `tensor_parallel_size` | YAML 每段或 `--stage-overrides` | 部署 schema 为 `null`;未覆写时并行默认 1 | 增加段内 TP,同时需要匹配设备安排 | 阶段并行配置和设备数 |
| `num_replicas` | YAML 每段或 `--stage-overrides` | 1 | 增加阶段实例,占用更多资源 | 副本及设备分配日志 |
| `gpu_memory_utilization` | YAML 每段或 `--stage-overrides` | schema 为 `null`;Qwen3 配方依次为 0.9、0.6、0.1 | 调整各段显存目标;降低可能减少缓存容量 | 显存占用、初始化和容量日志 |
| `max_num_seqs` | YAML 每段或 `--stage-overrides` | schema 为 `null`;Qwen3 配方各段为 64 | 限制阶段并发,减小通常降低容量需求 | 实际并发、排队与吞吐 |
| `async_chunk`、`--async-chunk`、`--no-async-chunk` | YAML 顶层及每段;命令行控制管线级 | 部署默认 `true`;单段强制关闭 | 改变阶段交接方式,需要上下游兼容 | 不兼容边的配置错误、首个输出时间 |
| `default_sampling_params` | YAML 每段 | `null`;实际配方逐段指定 | 设置默认采样行为,仍受模型约束 | 配方与模型 `sampling_constraints` 合并结果 |
| `platforms` | YAML 顶层 | `null` | 当前平台的阶段设置覆盖基础部署 | 例如 ROCm 的 Code2Wav `enforce_eager: true` |

**覆盖关系要分开看。** 以下说明的是生产使用的结构化解析路径,不是把所有配置排成一个通用优先级。

| 配置类别 | 实际处理 | 容易漏掉的边界 |
|---|---|---|
| 普通阶段引擎字段,如 `max_num_seqs` | 基础 YAML → 继承覆写 → 对应平台阶段设置 → 显式 CLI;公开入口将 `--stage-overrides` 展开到逐段覆写 | 全局参数只流向拥有该字段的执行类型;调单段优先用逐段入口 |
| 字典引擎字段 | 显式 CLI 通常递归合并现有字典 | `omni_kv_config` 是整体替换的特例;平台合并也不是任意层级一律递归 |
| `async_chunk` | CLI 先修改管线级值;某段设 `false` 可退出;单段管线关闭分块 | 相关边的生产者与消费者必须一致,不能靠全局开关强行打开不支持的链 |
| 默认采样 | 部署默认与模型 `sampling_constraints` 合并 | 模型标量约束胜出;必需 `stop_token_ids` 追加并去重 |
| 结构身份与阶段集合 | 由选中的注册 pipeline 生成 | 改部署列表的长度不是增删计算阶段 |

**观测从启动前错误开始。** 未注册的 `pipeline`、已移除的 `stage_args` 格式、分块边不一致都有明确报错。服务启动时 `Launching Orchestrator thread with … stages` 能确认最终阶段数,但不能证明每个引擎字段都符合预期。排查预算应进一步对照对应阶段的引擎配置与显存容量日志。

**典型配置。** 以下命令取自 Qwen3-Omni recipe,按默认配方的 2×H100 场景理解;其他卡型先核容量。这里的 2×H100 是随仓注释声明的验证环境,不是本次实测。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 完整语音链,从随仓配方开始 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --port 8091` | 沿用平台适配与默认并发;资源需求也随配方一起接受 |
| 共卡的 Talker 需要缩小显存预算 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --port 8091 --stage-overrides '{"1":{"gpu_memory_utilization":0.5}}'` | 只缩小 Talker 预算,给共卡留空间,可能减少它的缓存容量 |
| 先以较低并发验证部署 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --port 8091 --stage-overrides '{"0":{"max_num_seqs":8},"1":{"max_num_seqs":4},"2":{"max_num_seqs":4}}'` | 降低各段并发上限,接受吞吐上限变化以观察容量与交接 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 短 YAML 改了预算,原来的放置却丢了 | 是否显式写 `base_config` | 继承完整配方,再保留需要的局部覆写 |
| 基础 YAML 改了,当前机器仍用旧值 | 当前平台同一阶段的字段 | 调整对应平台分支,或使用明确的逐段 CLI |
| 全局增加 TP 后单卡阶段失败 | 每段 TP 与 `devices` 是否一起改变 | 只给需要跨卡的阶段设置 TP 与设备 |
| 删掉部署条目,语音阶段仍存在 | 当前选中的 `pipeline` | 选择已注册的所需结构,不要靠删部署条目删 stage |
| 分块开关导致配置报错 | 报错点名的上下游阶段 | 保持对应边模式一致,并确认模型已实现此交接方式 |
| 采样默认改了却不生效 | 模型的 `sampling_constraints` | 区分可调默认与模型必需条件,不要先怀疑 CLI 解析 |

## 六、常见误区

**自定义文件只写差异,就自动叠在官方配方上。** 随仓默认会自动加载,容易让人以为自己的文件只是补丁。实际显式文件接管部署来源;想保留官方其余设置,必须用 `base_config` 表达继承。

**部署列表里少一段,运行时就少一段。** 列表看起来像阶段清单,实际是按编号附着的部署设置。结构化配置遍历的是注册 pipeline 中的阶段;要只保留 Thinker,应选择模型已经提供的对应结构。

**一个全局 TP 参数就能让重阶段跨卡。** 全局引擎参数可能传播到多个有对应消费者的阶段,不是根据模型大小自动挑段。Thinker 要跨卡而 Talker 保持单卡时,用逐段覆写同时声明 TP 与设备。

**平台分支只是文档示例,不会参与解析。** 它会按当前运行平台匹配。Qwen3 的 ROCm 分支将 Code2Wav 切到 eager,原因是该路径的图捕获兼容性;只看 YAML 顶部的 `enforce_eager: false` 会漏掉实际设置。

**任何字典都只是更新自己写的键。** 普通 CLI 字典常用递归合并,让人容易把这个习惯推广到全部字段。`omni_kv_config` 明确整体替换,平台分支也有自己的合并规则;复制一个只剩局部键的配置前,先确认字段语义。
