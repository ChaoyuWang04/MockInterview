# Orchestrator：请求状态与输出顺序

这一页解释一条请求在多个阶段同时活动时,怎样保持身份、推进下游,并在正确的时刻结束。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

Qwen3-Omni 同时返回文本和音频时,Thinker 的文本可能已经结束,Talker 与 Code2Wav 还在工作。如果入口把第一个完成信号当作整条请求完成,用户就会收到被截断的音频;如果把每个阶段都当作独立请求,取消时又可能只停掉其中一段。

**阶段完成与请求完成必须分开。** 流式交接进一步让多个阶段同时持有同一请求:此时不能再用“当前走到第几段”这一个数字概括进度,还必须知道已经提交了哪些段、绑定了哪些副本、哪些终端已经完成。

## 二、解法

跨阶段协调者 Orchestrator 为请求保留一份状态,记录请求身份、各阶段采样设置、提交时间,以及本次需要等待的终端集合。入口层另外保留客户端身份与内部身份的对应关系,阶段池 StagePool 保存请求到副本的绑定。**统一的是关联关系,不是强求每层的请求编号字符串完全一样。**

普通整份交接在上游结束后准备下一段输入并提交;流式交接则预先提交那些通过 Connector 接收分块的下游,让 StagePool 选定并绑定副本。随后分块到达,下游便可工作;上游结束时,Orchestrator 对这条边跳过重复转发。转换规则归第 03 章,传输过程归第 06 章。

输出还要经过阶段侧的 MultimodalOutputProcessor:文本沿用 vLLM 的处理,没有文本解码器的多模态输出走专门路径。Orchestrator 收集处理后的结果,把终端输出送回入口,把中间阶段结果用于推进。这里保证的是请求关联与完成条件,并不把不同模态排成“整段文本发完才发整段音频”的固定播放顺序。

![同一请求先登记所需终端,文本与音频可以先后返回;Thinker 完成只更新终端集合,Code2Wav 完成后集合齐全才结束请求](/opensource/vllm-omni/04a-request-lifecycle.svg)

Qwen3-Omni 中,Thinker 是文本终端,Code2Wav 是音频终端,Talker 不是终端。入口按请求模态选出所需终端;只要其中还有未完成项,阶段的完成信号就不能升级为请求结束。取消也沿同一关联关系传播到各阶段,随后释放绑定和状态。全双工会话有自己的生命周期,不套用普通请求完成即清理的规则,详见第 15 章。

## 三、代价

**状态必须成套清理。** 客户端、Orchestrator、阶段池和输出处理器各有自己的职责;只删入口队列,不会自动停止 GPU 上的生成。客户端断开时,入口主动中止内部请求;阶段池按绑定找到副本,完成实际中止后才提交输出处理器的状态清理。

**错误影响范围需要分层判断。** 可识别的坏输入可以只让当前请求失败。副本死亡时,受影响请求失败,并停止它们在其他阶段的工作;副本摘除和后续派发的边界见第 05 章。整个阶段没有可用副本时,需要经过它的请求失败,健康检查也会反映不可用。编排循环自身的致命错误则可能结束引擎,不能把所有错误都概括为“服务不受影响”。

**协调也占 CPU。** 默认循环检查各阶段输出;事件驱动路径改变等待与唤醒方式,不改变下一跳和终端收敛规则。输出处理已经积压时,单纯给 GPU 增加容量未必能解决问题。

## 四、和 sglang-omni 的请求协调对照

sglang-omni 的 Stage Runtime 在阶段完成时选择下一跳,Coordinator 接收终端完成消息并汇合本次请求所需的结果。vLLM-Omni 将普通完成时的跨段推进集中在 Orchestrator,主路径按相邻阶段推进,StagePool 负责把提交落到具体副本。

两者都有按请求选择终端、等待所需终端完成的机制。区别主要是**下一跳决策放在哪里**:本项目读 Orchestrator 就能追到普通请求的推进与结束;对侧还要沿 Stage Runtime 的阶段路由继续读。流式分块不会让本项目失去这层控制职责。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。请求模态决定终端集合,属于每条请求的选择;这里列的是影响编排等待与诊断的服务配置。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--omni` | 启动命令 | 关 | 进入 omni 服务路径 | Orchestrator 启动日志 |
| `VLLM_OMNI_EVENT_DRIVEN_ORCH` | 环境变量 | `0` | 设为 `1` 改用事件唤醒,可能减少空轮询 CPU 开销 | 对比 CPU、首包时间和端到端时延 |
| `VLLM_OMNI_ABORT_TIMEOUT` | 环境变量 | 2 秒 | 增大客户端取消后的等待上限,也延长异常中止的等待 | 请求取消日志与阶段中止结果 |
| `--enable-orch-monitor` | 启动命令 | 关 | 收集循环及副本窗口统计,增加诊断开销 | 正常清理时输出的 JSON |
| `VLLM_OMNI_ORCH_MONITOR_PATH` | 环境变量 | 当前目录自动命名 | 指定监控文件位置,不单独启用监控 | 文件中的 `windows`、`replicas` |

**看清两层完成信号。** 内部 `engine_outputs.finished` 描述阶段输出,外层 `OutputMessage.finished` 表示所需终端已全部结束。对照请求日志时还要带上 `stage_id` 与 `replica_id`;客户端编号、Orchestrator 编号与 EngineCore 内部编号存在映射,不能只靠字符串相等串日志。

监控中的 `outputs_queue_size` 是副本输出队列积压,`inflight` 是副本在途/负载统计,都不能直接当成 GPU 调度等待队列。文件在清理时写出,不是实时逐请求时间线。

以下以随仓 Qwen3-Omni 配置标注的 2×H100 为资源起点,使用 `Qwen/Qwen3-Omni-30B-A3B-Instruct`;其他卡型先核对模型容量与部署配置。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 记录默认轮询基线 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --enable-orch-monitor` | 保留默认编排行为,增加窗口统计开销 |
| 对照编排 CPU 与时延 | `VLLM_OMNI_EVENT_DRIVEN_ORCH=1 vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --enable-orch-monitor` | 用事件唤醒替换空轮询,收益需与同一负载基线比较 |
| 取消排查时保留固定文件 | `VLLM_OMNI_ABORT_TIMEOUT=5 VLLM_OMNI_ORCH_MONITOR_PATH=/tmp/omni-orch.json vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --enable-orch-monitor` | 给中止更多等待时间,不因此保证故障阶段能够响应 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 文本完成却一直等不到请求结束 | 本次是否还要求音频,Code2Wav 是否完成 | 沿该请求的下游绑定检查输入等待与输出,不要手动把文本完成当总完成 |
| 流式下游像是没有启动 | 是否执行预提交,下游是否声明接收分块 | 查预提交失败日志;缺少入口 token 的错误不能靠放宽取消超时修复 |
| 客户端断开后仍有计算 | 入口取消是否传到各阶段,副本中止是否成功 | 查看中止超时及绑定,不要只检查 HTTP 连接已关闭 |
| 一个副本死亡后请求失败 | 失败请求绑定哪个副本,该阶段是否还有健康副本 | 区分受影响请求失败、阶段不可用与 Orchestrator 已退出 |
| 输出队列积压且 GPU 未满 | 输出处理与编排 CPU、监控窗口 | 对照事件驱动路径,再决定是否改变阶段容量 |

## 六、常见误区

**把“终端”读成“流水线最后一段”。** 顺序调用的习惯容易让人只盯最后的音频阶段。这里文本阶段本身也是终端,所需集合由请求模态选出;增加一个输出分支时,要同时核对完成条件。

**看到编号不同就判定串请求。** 入口为了隔离请求会生成内部编号,EngineCore 还可能有自己的编号。排查取消丢失时先核对映射与副本绑定;随意把编号统一替换,反而会破坏输出处理器保存的关联。

**把流式段结束当作会话结束。** 一段输入结束后还可能继续接收更新。输出处理和 Orchestrator 都区分段结束与真正终止;否则第一段结束就清状态,后续输入便找不到原请求。

**以为取消只需要丢弃结果。** 对调用者来说不再读取似乎就够了,但下游可能已经预提交。框架必须中止实际工作再清状态;AR 终端还可能返回已生成前缀,因此取消响应也不能简单当作空输出。
