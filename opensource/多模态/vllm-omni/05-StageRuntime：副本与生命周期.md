# StageRuntime：副本与生命周期

这一页解释配置中的逻辑阶段怎样变成可接收请求的副本,以及请求绑定和副本故障怎样被管理。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

把 Thinker 和 Talker 分配到 GPU 上,并不表示服务已经准备好。引擎还要启动进程、加载权重、测量内存、准备执行资源,入口才能安全地把请求交给它。共用 GPU 的阶段若同时测量显存,会互相干扰;只因进程已经创建就开始接请求,又可能把工作发给尚未就绪的副本。

副本增加后还有第二个问题:同一请求的后续输入不能每次随意挑一个实例。Decode 状态还留在原副本,新选中的实例没有它。**需要管理的是从准备、就绪到退出的一整段生命周期,而不只是创建几个进程。**

## 二、解法

生命周期管理者 StageRuntime 将每个逻辑阶段展开成副本初始化计划,为各副本解析设备和引擎配置,完成启动及就绪握手,再组装阶段池 StagePool。Orchestrator 通过池提交请求;谁该进入下一阶段由第 04 章负责,池解决的是“这次提交交给哪个具体副本”。

**默认先让初始化互不干扰。** 本地 LLM 副本按物理设备的重叠关系分组,同组依次初始化,不同组可以并行。设备集合不必完全相同:一个副本使用两张卡,另一个使用其中一张,也不能绕过这个约束。Qwen3-Omni 的 Talker 与 Code2Wav 共卡时,共用的是设备,不是同一个引擎进程。

显式启用同卡并发初始化时,框架先做设备预算准入,再通过引擎内部的阶段锁保护加载、显存测量和资源分配。这不是简单取消串行限制。本地 Diffusion 另有独立的串行初始化组,不能把 LLM 分组规则套到所有执行形态。

![StageRuntime 将逻辑阶段展开并启动副本,就绪后交给 StagePool;请求持续绑定原副本,完成释放绑定,副本丢失则摘除并让受影响请求失败](/opensource/vllm-omni/05a-replica-lifecycle.svg)

**选一次,沿绑定继续。** 本地 StagePool 在存活且可用的副本间轮询,后续提交优先复用已有绑定。分布式路径从成员信息中筛选健康且已接入客户端的副本,再用负载均衡器选择并记录亲和关系。请求正常结束释放绑定,副本本身留在池里服务其他请求。

分布式部署还需要区分两种登记。OmniMasterServer 分配副本身份和通信地址,StageRuntime 据此连接远端引擎;OmniCoordinator 收集状态、队列负载与心跳。MembershipController 将这些成员变化落到 StagePool。仅仅拿到地址,还不满足派发条件。

## 三、代价

**安全的初始化顺序会延长冷启动。** 同组副本需要等前一个完成,总时间不能按“所有阶段中最慢的那个”估算。可选并发路径增加准入与锁的复杂度,也要求确认它保护得到实际执行设备;当前会拒绝该路径无法覆盖的 Ray 或多节点执行器。

**多副本不是免费容量。** 新副本意味着额外的模型和执行资源。设备配置决定副本分别看见哪些卡,并不保证这些资源预算一定容得下;共卡阶段要一起核对显存。

**保留绑定也保留了故障边界。** 成员失联后,框架摘除客户端、使绑定失效,并清理受影响请求。剩余健康副本可以承接后续请求,但已有 Decode 状态不会因此自动搬过去。副本数量恢复和失败请求恢复是两件事。

**启动中途失败也要回收。** StageRuntime 收集已经初始化的客户端并关闭它们,启动资源同样有失败回滚路径。正常停机还涉及引擎管理器、成员订阅与线程,不能把“入口不再接请求”当成进程资源已经释放。

## 四、和 sglang-omni 的副本组织对照

vLLM-Omni 围绕逻辑阶段建立 StagePool,每段分别持有副本客户端与请求绑定。sglang-omni 的复制单位是显式 Process:一个 Process 内的成员阶段一起复制,请求在准入时选定该 Process 的副本,并将同一个选择投射到其成员阶段。

这使两边的扩容边界不同。本项目按阶段寻找容量,对侧则要先看哪些阶段被声明在同一个 Process 中。两边都把启动与就绪等待分开处理;不能因多个阶段用了同一 GPU,就认定它们共享进程或采用相同的副本复制方式。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。部署 YAML 的解析和平台覆写见第 02 章;此处只看它们怎样影响副本生命周期。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `devices` | 每阶段部署 YAML | 未指定时继承启动可见设备;随仓模型可显式设置 | 改变副本落卡及初始化重叠分组 | 设备拆分日志与实际进程设备 |
| `num_replicas` | 每阶段部署 YAML | 1 | 增加该阶段实例容量,也增加资源占用 | `replicas`、`devices split` 启动日志 |
| `--stage-init-timeout` | 命令行 | 300 秒 | 放宽使用此预算的阶段初始化等待,包括设备锁;不覆盖所有底层握手 | 报错阶段及启动握手日志 |
| `--init-timeout` | 命令行 | 600 秒 | 放宽整体初始化等待预算 | 引擎初始化超时日志 |
| `--omni-lb-policy` | 分布式 head 命令行 | `random` | 可选 `round-robin` 或 `least-queue-length`,改变新请求的分布 | 各副本负载与绑定;本地轮询不受此项改变 |
| `--omni-heartbeat-timeout` | 分布式 head 命令行 | 30 秒 | 增大可容忍更久的心跳间断,同时延后失联发现 | 成员状态变化、摘除与请求错误日志 |

**就绪看引擎,派发看成员与接入。** 本地日志中的 `EngineCore running` 带阶段号和副本号;分布式再对照 `attached remote replica` 及 Coordinator 中的 `UP` 状态。StagePool 只选择既报告可用、又有客户端可连接的候选。心跳负载由调度器未完成请求数刷新,不是每次请求派发都同步更新的瞬时值。

默认阶段心跳间隔为 5 秒,MembershipController 每 0.5 秒检查成员快照;Coordinator 也按周期检查超时。因此心跳超时阈值不是“故障发生后恰好这么多秒就完成摘除”的保证。

以下两套使用随仓 Qwen3-Omni 配置标注的 2×H100 作为资源前提。它们用于核对初始化行为,没有在本章进行 GPU 实测。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 先确认默认就绪顺序 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni` | 保留同设备默认串行保护,冷启动需要等待各组内副本 |
| 权重与设备已核对,但整体初始化超过默认预算 | `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --init-timeout 1200` | 给予入口等待整个引擎就绪的更多时间,也会更晚报告真正卡住的初始化 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 只看到部分阶段开始加载 | 阶段是否共用或部分重叠设备 | 按初始化组检查前一副本进度,不要直接判断线程卡死 |
| 远端已经注册却没有流量 | 客户端是否接入,成员状态是否可用 | 分开排查握手、连接地址与心跳 |
| 增加副本后启动越界或显存不足 | 设备拆分结果,每副本所需设备数 | 核对启动可见设备与合计资源预算 |
| 改负载策略却仍像轮询 | 当前是否走分布式 head 路径 | 本地池保持轮询,不要只凭同名启动参数推断生效 |
| 副本死亡后请求失败 | 哪些请求绑定该副本 | 检查摘除与清理,由调用方决定是否重试,不要期待状态自动迁移 |
| 启动失败但设备仍有占用 | 初始化失败回收与进程管理器日志 | 区分本次残留资源和同设备上的其他服务 |

## 六、常见误区

**把“卡相同”当成“进程相同”。** 设备放置图经常把共卡阶段画在一起,容易让人以为它们共享一个调度循环。Qwen3-Omni 的 Talker 与 Code2Wav 仍是分别启动的阶段引擎,需要各自握手和管理。

**把注册日志当成上线验收。** 注册已经分配了身份与地址,看起来像全部完成;实际上 head 还要接好客户端,Coordinator 还要收到可用状态。排查“有进程但没流量”时,这两个条件缺一不可。

**看到超时就只改单阶段参数。** 参数名容易让人误以为它统管所有启动等待,但当前本地 LLM 的底层就绪握手没有直接接收这份预算。先确认卡在设备锁、底层握手还是入口等待整体就绪,再修改对应限制;同设备组的串行等待还会增加整体耗时。

**认为同卡并发初始化只是一个加速开关。** 这个直觉来自不同 GPU 可以同时加载,但同卡显存测量会受其他进程影响。可选路径依靠专门的准入和阶段锁,要求设备由该部署专用;绕过保护不能等价为更快启动。
