# 扩散注意力后端与跳步缓存

这一页解释怎样减少一次扩散生成中的重复计算,以及为什么换 attention kernel 和复用跨步结果需要分别验收。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

视频序列变长后,每次 denoise 的 attention 会变重;同一请求还要反复调用 transformer。只优化一次 attention,仍会在后续步骤重新运行整个网络;只尝试跨步复用,真正执行的步骤又可能落到不合适的 kernel 上。

**本章解决的是一次生成要付出多少计算。** 第 09 章决定何时把控制权交回调度器,第 10 章决定怎样分摊到设备;这里进一步决定哪些计算用更合适的实现完成,哪些计算可以接受近似复用。

## 二、解法

最直接的办法是先让必须执行的步骤更便宜,再判断相邻步骤是否值得重算。vLLM-Omni 把这两件事分成独立接入点。

**attention 在构造时按角色选择实现。** 模型声明这一处是 self、cross 或更具体的角色,统一选择器先找精确角色设置,再找类别、全局设置和平台默认。平台负责检查设备、依赖与支持的形状。这样长序列与敏感的短序列不必使用完全相同的策略,模型也不需要自己复制一套设备选择逻辑。

**跨步缓存围绕 transformer 安装,在新生成开始时刷新。** Runner 加载 pipeline 后启用缓存后端,整请求执行前刷新本轮状态;部分 pipeline 接管请求边界的缓存切换。以输入变化驱动的实现为例,先用模型适配器提取判据,累积相邻步骤的变化;变化足够小时,把之前保存的 residual 加到当前 hidden states 上,否则真实执行并更新 residual。复用的是当前请求内部的近似计算,不是另一条相同 prompt 的最终结果。

![attention 后端作用于真实计算分支,跨步缓存可以绕过 transformer blocks 并复用上次 residual,两条路径都回到当前步骤的后处理与采样器更新](/opensource/vllm-omni/11a-attention-step-cache.svg)

**单步内部还可以少算不重要的 attention tile。** 当前稀疏实现保留 QK 计算,根据分数判断是否省去该 tile 的 Softmax 与 PV。它不复用上一 denoise 步的 residual,也不把整个 denoise 步删除。因此 kernel 替换、单步稀疏和跨步复用是不同的优化位置,不能用一个“缓存命中率”概括。

## 三、代价

**加速路径的误差会累积。** 稀疏 attention 舍弃小贡献,跨步复用则用旧 residual 或预测代替新计算。即使每项单独可接受,叠加后也要重新比较相同 prompt、seed、分辨率与步数下的输出,尤其是视频的时间一致性。

**缓存本身并非免费。** 保存 residual 要占显存,提取输入、计算变化与判断分支也有开销。输入变化驱动的实现还会把判据取回 CPU。步数很少或模型计算很轻时,这些成本与预热可能吃掉收益。

**有注册项不代表所有模型都可用。** attention 还受 mask、head size、硬件与并行路径约束;缓存则需要对应的模型适配器。DreamZero 的预测复用直接接入自己的 denoise 循环,不能把它推广成所有 pipeline 的通用跳步能力。

**执行粒度有兼容边界。** 当前第 09 章的逐步 Runner 明确拒绝扩散缓存后端。不能因为两者都围绕 denoise 步工作,就认为逐步调度与跨步缓存已经能一起使用。

## 四、和 sglang-omni 的模型局部选择对照

这里对照 sglang-omni 基准 89e60d0bf2 的 MOSS-Audio-Tokenizer。它在 codec attention 内检查设备与 dtype,自动选择可用实现,显式指定不兼容实现则报错;自动回退还保留原因。

vLLM-Omni 本章的区别在于把 Diffusion attention 的角色解析、平台兼容性与实现注册分开,再为扩散缓存提供统一启用和刷新入口。前者是具体 codec 的局部选择,后者是扩散栈的公共接入层。这个对照说明职责放在哪里,不把 codec 的 streaming KV 当成跨 denoise 的近似 residual 缓存,也不据此判断两个项目的整体性能。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。表中嵌套字段通过 `--diffusion-attention-config` 的 JSON 或点式参数设置;缓存字段通过 `--cache-config` 的 JSON 设置。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--diffusion-attention-backend` | 命令行 | 未指定,由平台选择 | 为所有未覆写角色指定后端,性能方向取决于设备与形状 | `Resolved diffusion attention backend` 日志中的角色、后端与来源 |
| `per_role` | attention JSON | 空 | 精确角色优先于类别,再到全局;每项替换完整 spec,不继承其稀疏设置 | 同一日志的 `role` 与 `via` |
| `default.skip_softmax.threshold` | attention JSON,仅 `TRTLLM_ATTN` | 未设置 | 增大通常跳过更多 tile,增加近似误差;0 不跳过 | 固定输入比较 attention 耗时与输出 |
| `default.skip_softmax.target_sparsity` | 同上 | 未设置 | 通过 checkpoint 校准曲线选工作点,和 `threshold` 互斥 | 缺校准时报错;目标不是每层实得稀疏比例 |
| `default.skip_softmax.disabled_until_timestep` | 同上 | 0,不启用门控 | 正值使归一化 timestep 高于该值时保持 dense;降低正值通常保留更多 dense 步 | pipeline 未发布 timestep 时的 `staying dense` 警告 |
| `--cache-backend` | 命令行 | `none` | 选 `cache_dit`、`tea_cache`、`mag_cache`、`sea_cache` 或 `step_cache`;各自模型范围不同 | 启用日志、适配器错误与实际耗时 |
| `rel_l1_thresh` | cache JSON,TeaCache | 未指定则模型默认,通常 0.2;MiniMax-H3 为 0.17 | 增大允许累计更多变化后再重算,更激进 | 固定输入质量对照与 transformer 耗时 |
| `max_warmup_steps` | cache JSON,Cache-DiT | 4 | 增大保留更多初始真实计算,减少可复用空间 | Cache-DiT summary |
| `residual_diff_threshold` | 同上 | 0.24 | 增大允许更激进复用,需复查质量 | summary 与输出对照 |
| `max_continuous_cached_steps` | 同上 | 3 | 限制连续复用长度;调大减少强制重算机会 | summary 中计算与缓存情况 |
| `--enable-cache-dit-summary` | 命令行 | 关 | 请求执行后输出 Cache-DiT 统计,不是所有后端的统一统计开关 | transformer 对应 summary |

`TRTLLM_ATTN` 在本基准要求数据中心 Blackwell、head size 128、可用的 FlashInfer trtllm-gen kernel,以及相容的 mask-free 或 packed-padding 路径。RTX 5090 不属于此处的数据中心 Blackwell 范围。单独选它仍是 dense attention;`skip_softmax` 才是稀疏控制。并行组合还要按第 10 章检查,不能只看设备名称。

**先确定生效,再测收益。** 后端解析日志证明选择了谁;缓存启用日志证明安装了适配;二者都不证明端到端已经变快。对同一组请求分别记录 denoise 耗时、总延迟、峰值显存和输出质量。Cache-DiT 可额外开启 summary;没有该 summary 不能直接断定其他缓存未运行。

以下图像配置以单张 A100 80 GB、`Qwen/Qwen-Image`、整请求执行和单请求负载为起点;显存仍取决于分辨率和输出数量。两套缓存配置分别与基线比较,不叠加。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 建立无跨步近似的图像基线 | `vllm serve Qwen/Qwen-Image --omni --cache-backend none` | 保留完整 denoise 计算,记录平台实际选择的 attention 后端 |
| 观察 block 缓存是否值得用 | `vllm serve Qwen/Qwen-Image --omni --cache-backend cache_dit --enable-cache-dit-summary` | 使用默认预热与连续复用限制,以近似误差和缓存占用换取少算 blocks |
| 对照输入变化驱动的复用 | `vllm serve Qwen/Qwen-Image --omni --cache-backend tea_cache --cache-config '{"rel_l1_thresh":0.1}'` | 比该模型默认阈值更保守,以较少复用换取质量验证空间 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 指定 attention 后端后启动失败 | GPU 型号、依赖、head size 与 mask 契约 | 先回平台默认建立基线,不要把注册表当兼容性清单 |
| 改全局稀疏配置,某个角色没变化 | 是否有 `per_role` 完整覆写 | 在该角色 spec 中明确保留或取消稀疏设置 |
| 开门控后始终 dense | `staying dense` 警告及 pipeline 是否发布 timestep | 修正集成或关闭门控做受控对照,不要先把稀疏阈值拉大 |
| 缓存启动时报模型不支持 | 后端的模型适配器和启用日志 | 改用该 pipeline 已实现的后端或关闭缓存 |
| 报 `Step mode does not support cache_backend yet` | 是否同时启用了 `--step-execution` | 在逐步调度和整请求缓存之间选择本次实验目标 |
| 缓存已开但收益很小 | 实际 denoise 步数、预热与计算占比 | 再看 summary 和端到端分段耗时,不要先同时打开所有近似选项 |

## 六、常见误区

**把 StepCache 当成逐步执行的缓存版本。** 名字里都有 step,很容易一起打开。`step_cache` 是 DreamZero denoise 循环根据历史预测的相似度复用预测;采样器仍推进 latent。`--step-execution` 则改变 Runner 与调度器之间的执行契约,当前禁止搭配缓存后端。

**把门控值 0 当成“所有高噪声步骤都保持 dense”。** 按普通比较式理解确实容易得出这个结论,但这里 0 是关闭门控的特殊值。设正值才读取归一化 timestep;这个值也不是已经执行的步数比例。

**看到 checkpoint 写了稀疏目标,就以为服务会自动照用。** 当前读取校准曲线和忽略层名单,不会直接采用 checkpoint 中的目标稀疏度与 timestep 门控值。应在启动配置明确设置,并检查 secondary transformer 的校准是否读到。

**拿更高的复用率直接证明更好的配置。** 重算越少看起来越快,但输入比较、状态保存和非 denoise 部分仍耗时,近似误差还会随生成过程传播。先保留单项对照,只有端到端收益与质量同时满足要求才保留组合。
