# 扩散执行栈：整请求与逐步调度

这一页解释 DiffusionEngine 何时把新请求加入计算,以及为什么整请求批处理与逐步调度是两种不同的服务方式。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

图像或视频生成通常包含输入编码、反复 denoise 和最后解码。如果调度器只调用一次完整 pipeline,它要等这次调用返回,才能重新安排这一执行通道里的工作。长请求运行期间,新到达的短请求可能只能排队;把同批请求合起来执行可以提高设备利用率,却没有改变这个调度边界。

**关键不是一次允许多少请求,而是计算在什么时候把控制权交还调度器。** 想在 denoise 之间接纳新请求或处理取消,就必须把 latent、采样进度和请求局部状态从完整调用中拆出来,不能只照搬文本 Decode 的 token 循环。

## 二、解法

DiffusionEngine 选择执行粒度,调度器选择本轮请求,Executor 把工作交给 Worker,DiffusionModelRunner 调用具体 pipeline。两条执行路径共用排队、请求身份和输出交付,但一次执行返回时所代表的进度不同。

**整请求路径交付完整结果。** RequestScheduler 从等待队列中取出相容请求,组成一轮,Runner 调用完整 pipeline,返回每条请求各自的结果。若模型支持融合批处理,这一轮可以一起计算;容量只有一个时,就是串行请求执行,不是第三种独立模式。当前这一轮开始后才到达的请求,不能插进已经运行的完整调用。

**逐步路径交付本轮进度。** StepScheduler 保留未完成请求,容量允许时再加入相容的新请求。Runner 为新请求准备输入和 latent,将活动状态组成 InputBatch,执行一次 denoise,再分别更新每条请求的 latent 与进度。完成的请求解码并退出,其他请求留下继续。模型必须实现这套状态接口,还必须支持多请求的批量计算,才有逐步 continuous batching。

![整请求路径要等完整调用返回才重新调度,逐步路径在 denoise 边界保留活动请求并加入相容新请求;完成者退出后后续请求继续推进](/opensource/vllm-omni/09a-diffusion-batching.svg)

**合批仍有条件。** 分辨率、CFG 设置、输出数量和 LoRA 等会影响批量张量契约,需要相容;逐步路径允许各请求处在不同 denoise 进度,总步数也可以不同。当前队列保守地按 FIFO 接纳,队首请求不相容时会停下,不会越过它寻找后面的相容项。

执行完成与向用户发包也分开。内部每条请求都有输出队列,整份结果和分块结果沿同一通道交付。逐步执行可以只在最终完成时输出;是否能提前发出有效图片、音频或视频块,仍取决于 pipeline。

## 三、代价

**逐步调度增加常驻状态与组织开销。** Runner 要保存各请求的 latent、条件输入和局部采样器状态,每轮组织批次并把更新写回。新请求进入时还需要做输入准备。因此逐步模式给了更多调度机会,并不承诺单请求生成更快。

**更大的容量不保证更大的实际批次。** FIFO 与相容条件共同限制合批;形状不一致的业务,提高容量可能只增加内存压力。整请求模式还可以主动等待短暂窗口来收集突发请求,代价是先到请求多等一段时间。

**取消的响应边界随粒度变化。** 引擎在执行前后处理取消队列,逐步路径通常能在 denoise 之间处理,整请求路径可能要等完整调用返回。这里没有让正在运行的 GPU kernel 任意中断的保证。

**支持范围要逐 pipeline 核对。** Qwen-Image 实现了整请求合批与逐步批量推进;Helios 虽有逐步接口,却明确限制同一轮只有一个活动请求。参数能打开引擎分支,不代表模型已经支持对应执行方式。并行、注意力、缓存、Offload 和量化的具体实现分别留给第 10–13 章。

## 四、和 sglang-omni 的整任务调度对照

这里仅比较 sglang-omni 的 SimpleScheduler 路径:它接收一个计算函数,也可以接收批量计算函数,收集请求后调用,再把各结果交回。这个调度器看到的是一次函数调用的完成,并不在这个通用调用接口里维护本章这套逐请求 denoise 状态。

vLLM-Omni 的整请求路径与这种任务边界接近;逐步路径则进一步要求模型交出准备、denoise、状态更新和解码接口,使调度器重新取得每轮安排工作的机会。这个对照只说明接口暴露的粒度,不把 SimpleScheduler 代表成 sglang-omni 的全部生成能力。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。默认值指 Diffusion 配置;不要直接套用文本引擎或其他阶段的同名默认值。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `--step-execution` | 命令行;Diffusion 配置 `step_execution` | 关 | 选择逐步执行,要求 pipeline 实现状态接口 | 不支持时的启动错误,以及逐步请求进度 |
| `--max-num-seqs` | 命令行;Diffusion 配置 `max_num_seqs` | 1 | 增加当前执行模式的活动请求容量,通常增加显存需求 | 实际批次、排队时间、吞吐与峰值显存 |
| `--request-batch-max-wait-ms` | 命令行;Diffusion 配置 `request_batch_max_wait_ms` | 0 毫秒 | 整请求新批次开始前等待合批;可能增大批次也增加首请求等待 | `[RequestBatch] admission wait done` 的 `waiting`、`max_batch`、`waited_ms` |
| `--diffusion-streaming-output` | 命令行;Diffusion 配置 `streaming_output` | 关 | 要求逐步路径,未开启逐步时会自动打开;仅模型支持时输出中间块 | 自动启用警告与实际输出的非终止块 |

**先看队列等待,再看计算。** 新请求被接纳时记录 `scheduler_queue_wait_ms`;引擎还维护等待请求指标。整请求的初始化日志给出容量与合批等待配置,逐步调度的 debug 日志记录加入队列时的步数。不要把合批窗口、排队等待和 denoise 计算耗时混成一个指标。

以下均以 `Qwen/Qwen-Image` 为例,资源前提参考随仓配方中的单张 A100 80 GB。批量配置还要按请求分辨率和输出数量核对剩余显存;以下组合未经本章 GPU 实测。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 相同形状的突发图像请求,考察整请求合批 | `vllm serve Qwen/Qwen-Image --omni --max-num-seqs 2 --request-batch-max-wait-ms 20` | 用最多 20 毫秒的合批等待上限换取更大的批次机会,实际可提前结束等待 |
| 验证逐步路径的单请求结果 | `vllm serve Qwen/Qwen-Image --omni --step-execution --max-num-seqs 1` | 先验证状态推进及输出一致性,不追求多请求吞吐 |
| 已核单请求结果,考察相容请求的持续进入 | `vllm serve Qwen/Qwen-Image --omni --step-execution --max-num-seqs 2` | 增加活动状态与显存占用,换取逐步合批机会;当前属于实验性路径 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 增大并发容量后启动报不支持合批 | pipeline 的 `supports_request_batch` | 回到容量 1,或选已实现整请求合批的 pipeline |
| 开逐步时报接口缺失 | 是否实现 `prepare_encode`、`denoise_step`、`step_scheduler`、`post_decode` | 不要靠继续增大容量绕过能力检查 |
| 已有空位却没有接纳后面的请求 | 队首与活动请求的相容条件 | 固定分辨率、CFG 和 LoRA 做对照,确认是否 FIFO 阻塞 |
| 改合批等待后逐步模式没变化 | 当前是否开启 `step_execution` | 该等待窗口只属于整请求调度 |
| 开流式仍只收到最终图像 | pipeline 是否有可用中间输出边界 | 区分“按步调度”与“按块交付”,检查模型能力 |
| 单请求逐步正常,多请求却报错 | pipeline 是否真正支持多状态输入 | 例如 Helios 应保持容量 1,不要把单请求支持扩大为 continuous batching |

## 六、常见误区

**把并发上限当成 continuous batching 开关。** 文本服务里常把两者一起调,容易顺手套过来。这里先由执行模式决定调度边界;没开逐步时,增大容量仍是完整 pipeline 的静态批次。

**为了凑满批次不断拉长等待。** 看到批次偏小,直觉是再多等一点。实际可能是队首形状或 LoRA 不相容;窗口延长只让先到的请求多等,不能把不相容输入变成同一批。

**以为同一批必须走到相同步数。** 单次 pipeline 循环通常共享一个进度,迁移代码时容易把它留在 pipeline 对象上。逐步路径保存每条请求自己的采样器与进度,共享状态会让并发结果互相干扰。

**把关闭消费者当成取消计算。** 不再读取输出看起来像请求已经离开系统,但内部输出队列移除与调度状态结束是两个动作。要停止工作必须走中止路径,不能只关闭结果迭代器。
