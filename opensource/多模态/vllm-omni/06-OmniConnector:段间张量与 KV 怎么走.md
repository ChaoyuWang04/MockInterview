# OmniConnector:段间张量与 KV 怎么走

这一页说明阶段产物怎样被找到、取走并回收,以及跨进程和跨节点各要解决什么。说法都在源码基准 `4d877780d3`(tag `v0.29.0rc1`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

把 Thinker 和 Talker 放进独立进程后,上游的张量地址对下游不再天然可用。即使两段共用一张 GPU,也不能把一个进程里的 Python 对象直接当成另一个进程的输入。

跨节点又多一层问题:下游得知道去哪台机器取哪份数据,发送端还得把数据保留到接收完成。回收过早会读不到,回收过晚会占满共享内存或传输内存池。音频分块持续产生时,这个问题会重复发生。

所以,真正需要统一的是**数据如何定位、何时可取、由谁释放资源**。模型载荷是否正确由第 03 章的转换处理器负责;OmniConnector 负责跨越进程或机器边界。

## 二、解法

连接器抽象 OmniConnectorBase 将交接分成写入、读取、按请求清理与整体关闭。调用方给出来源、目的阶段和数据 key,后端处理存储、序列化或设备传输的具体实现。

这里有三件不同的东西。**key 是这份数据的名字**,普通阶段载荷用请求身份、来源阶段和块序号配对收发。**metadata 是找到或解释这份数据所需的传输信息**,例如共享内存名称、数据长度或发送端地址。**payload 才是真正要用的载荷**,可以包含 hidden states、音频码或 KV。

不是每次交接都必须把写入返回的 metadata 原样转发。共享内存可直接按 key 查找;远端传输也能先得到发送端地址,再查询该 key 的完整信息。关键在于发送与接收使用同一套定位规则。

![共享内存交接按同一key写入和读取载荷,读取尚未就绪时继续等待,成功读取与请求清理分别回收已消费和未消费资源;跨节点需要可达的远端定位信息及对应后端](/opensource/vllm-omni/06a-connector-transfer.svg)

图中画的是共享内存路径。SharedMemoryConnector 将对象序列化为字节,写入本机 POSIX 共享内存;接收端复制字节、释放共享段,再还原对象。这能跨进程,不能跨机器。序列化器会将 Tensor 转到 CPU,因此共享内存也不意味着没有拷贝。

跨节点可以使用 Mooncake Transfer Engine 等后端,以发送端信息定位已注册的内存。设备路径要具体看后端与载荷:Mooncake Transfer Engine 支持主机或 GPU 内存池,NPU 上的 Yuanrong Transfer Engine 使用 NPU 内存池,并有直接读取设备缓冲区的路径。不能把一种主机中转方式当成全部实现。

KV 也能复用连接器,但它不是普通阶段载荷直接换个名字。OmniKVTransferManager 先组织 layer、block 和并行 rank 对应的数据,再选择张量、字节或对象载荷交给连接器。这里统一的是搬运接口,KV 布局与缓存策略另有专门逻辑,缓存管理见第 08 章。

## 三、代价

**统一接口不代表统一传输成本。** 共享内存要付出序列化、主机字节复制和对象重建的成本;内存池后端要预留、注册并管理缓冲区。设备直传可以省掉部分主机中转,但不能据此保证任意模型载荷都走这条路径。

**资源生命周期延伸到接收端。** 写入成功只说明后端接受了这份数据,不说明下游已完成计算。共享内存读取后释放共享段,未消费的数据靠请求清理或连接器关闭回收;Mooncake Transfer Engine 还为陈旧缓冲区提供超时回收。异常路径与正常路径都需要收尾。

**一个 key 不一定能被无限次读取。** 当前 Mooncake Transfer Engine 的单份发送缓冲区在成功传输后回收,不能把一次写入当成任意多个消费者的广播存储。多 rank KV 的组织由 manager 处理,不能只根据统一接口就推导出任意广播能力。

**小块与大块各有成本。** 小块增加定位、调用和回收次数;大块增加在途占用与等待。第 03 章的分块大小决定交付粒度,本章的内存池容量决定能容纳多少在途数据,它们不是同一个旋钮。

## 四、和 sglang-omni 的传输分层对照

参照项目基准为 89e60d0bf2。两边都把阶段逻辑与具体传输后端隔开,但接口的组织方式不同。

vLLM-Omni 根据阶段边的配置建立 Connector,调用方按 key 写入和读取对象,后端返回大小及可选 metadata。模型运行器与分块适配器在上层安排异步交付,基础接口自身是普通同步方法。

sglang-omni 的 CommRouter 先按位置关系选择传输:同进程可传本地对象,远端选择 Mooncake,本机 GPU 间由平台选择传输,CUDA peer access 不可用时可退回共享内存。Relay 则提供异步 Tensor 传输,返回带 metadata 和完成等待方法的操作对象。其共享内存发送操作会等待接收确认,超时则回收。

区别是**本项目把按 key 存取的后端契约放在中心,对侧更显式地分开位置选择与异步传输操作**。这不意味着本项目没有后台执行,也不意味着对侧所有路径都经过网络。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

后端配置在部署 YAML 顶层的 `connectors` 中定义,阶段通过 `input_connectors` 或 `output_connectors` 引用。下表将通用配置与 Mooncake Transfer Engine 的配置分开标明,避免把某个后端的选项套给共享内存。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `name` | `connectors` 中每个实例 | 未指定的阶段边自动配置 `SharedMemoryConnector` | 切换传输后端,改变部署依赖与数据路径 | `Created connector` 与自动配置日志 |
| `input_connectors` / `output_connectors` | 部署 YAML 每段 | 根据已知阶段边补共享内存连接器 | 明确哪条边使用哪个后端 | 收发两端阶段与实例是否对应 |
| `protocol` | Mooncake Transfer Engine 的 `extra` | `rdma` | 选 `tcp` 可比较不依赖 RDMA 数据路径的传输;性能要实测 | 启动协议与实际传输日志 |
| `host` / `zmq_port` | 同上 | 自动探测本机 IP / 50051 基准端口 | 改变发送端对外地址与端口起点;实际端口按阶段和 rank 派生 | 接收端是否能查询目标发送端 |
| `memory_pool_size` | 同上 | 构造函数缺省 1073741824 字节,即 1 GiB | 增大可容纳更多在途载荷,也增加常驻内存占用 | 分配失败、并发载荷大小与内存占用 |
| `memory_pool_device` | 同上 | `cpu` | 改成适用的设备池可使用设备传输路径,占用设备内存并要求环境支持 | 启动内存池位置、传输耗时与设备内存 |
| `buffer_ttl_seconds` | 同上 | 300 秒 | 增大延长陈旧发送缓冲区保留,降低过早过期风险但延迟回收;非正值禁用 TTL 检查 | `TTL expired` 日志与长期内存占用 |

**先确认定位,再看速率。** 分块发送成功日志有 `Sent` 和 key;失败有 `Chunk send failed`。整份路径的 `send_full_payload_outputs: enqueue` 只证明入队,接收路径的 `recv_chunk_result` 才说明取到了载荷。共享内存的 `put failed`、`shm get failed` 要结合 `/dev/shm` 容量和 key 检查。

`health()` 返回后端自身的状态和计数,不是端到端探针。SharedMemoryConnector 直接返回 `healthy` 加 `puts`、`gets`、`bytes_transferred`;Mooncake Transfer Engine 也不能仅凭该状态证明远端地址可达、目标 key 存在或下游已消费。应使用一次实际交接核对这些条件。

| 场景 | 配置方向 | 拿什么换什么 |
|---|---|---|
| Qwen3-Omni 单机双卡,先复现随仓交接 | 从 `qwen3_omni_moe.yaml` 复制本地 `qwen3-transfer.yaml`,保留 `SharedMemoryConnector`;启动 `vllm serve Qwen/Qwen3-Omni-30B-A3B-Instruct --omni --deploy-config qwen3-transfer.yaml` | 使用简单的本机交接,接受主机序列化与拷贝 |
| 已有跨节点阶段部署,先验证地址与存取闭环 | 两端对应边使用 `MooncakeTransferEngineConnector`,`protocol: tcp`、`memory_pool_device: cpu`、`memory_pool_size: 1073741824`,并核实 `host` 可达 | 以主机池和 TCP 建立传输对照;这组 connector 设置本身不会替你部署远端阶段 |
| 同一跨节点负载已有 RDMA 环境 | 保持上述主机池起点,改 `protocol: rdma`,两端核实 RDMA 设备与地址 | 增加环境要求,观察数据搬运耗时是否降低;随后再单独比较设备池 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 读取返回 `None` | key、发送进度、后端日志 | 区分尚未写好、根本没写入与读取失败,不要立即当空结果完成 |
| 单机正常,换远端就一直等 | 是否仍使用共享内存,发送端地址是否可达 | 切换适合跨节点的后端并核对两端实例配置 |
| 并发升高后发送失败 | 共享内存或传输池容量,未消费数据是否积压 | 核对消费与清理,再决定增加容量还是降低在途负载 |
| 取消后占用长期不回落 | 请求清理与后台在途发送是否结束 | 查未消费共享段、陈旧缓冲区与关闭路径 |
| health 显示正常但没有音频 | 是否有对应 key 的成功读取 | 取不到查传输;已取到再回到转换和模型执行 |

## 六、常见误区

**metadata 里写了远端地址,共享内存就能跨机器。** 两种后端都有 metadata 容易让人误会它们可以互换。SharedMemoryConnector 不理解远端地址,遇到非共享内存 metadata 会退回本机 key 查找,不会自动升级成网络传输。

**读取没有结果,说明上游生成了空内容。** 共享内存可能尚未创建,也可能刚创建还没设好大小;这些情况都可以返回 `None` 让上层继续尝试。先核对发送和 key,再讨论模型是否产生空载荷。

**put 成功就能立刻释放发送缓冲区。** 写入往往只是让数据可被接收端找到。接收尚未发生时自行回收,会把正常交接变成缺失数据;应由后端约定的消费、确认和清理路径管理生命周期。

**换成设备池后,所有序列化与主机拷贝都会消失。** 设备池只是具备设备传输的条件之一。KV manager 会依据后端能力选择载荷形式,普通对象也可能仍要序列化;检查实际载荷与 fast path,比只看配置值更可靠。
