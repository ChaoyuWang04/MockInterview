# 模型接入:生成的 modeling

这一页回答一件事:VeOmni 怎样把官方 HF 的模型代码改成训练版,同时让改了什么始终看得见、跟得上上游。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

训练框架拿到一份官方 HF 的 modeling,不能原样用:归一化、SwiGLU、旋转位置编码要换成融合算子,MoE 的专家要改成能交给融合算子和专家并行的堆叠布局,loss 要走不物化整张 logits 的融合路径,模型还得告诉框架哪些参数要额外切。常见做法是**运行时打补丁**:导入时把 HF 类上的某个方法、某张全局表里的某个函数替换掉。

补丁一多就出三种事。**顺序依赖**:两个补丁改同一个方法,谁后导入谁生效,换一下导入顺序行为就变。**看不见最终代码**:真正在跑的前向是原版加上散在好几个文件里的替换拼出来的,loss 对不上 HF 基线时,没人能指着一份代码说「就是这里不一样」。**升级 transformers 后静默失效**:上游给类改了名,补丁打在一个已经不存在的名字上,什么也没替换;上游改了方法签名,补丁照样替换,却按旧的参数约定在跑。这两种都不报错,只让数值慢慢偏。

还有一类问题补丁解决不了:**上游根本没有的结构**。Qwen3.5 发布的 checkpoint 带着多 token 预测头(MTP)的权重,而当前钉住的 transformers 5.16.1 里没有这个模块,加载时把这些权重当多余键忽略。继续训练只训主干,MTP 头原地不动,和主干越来越不配套;想把它接回来,要新增一个类、改构造函数、改两层前向、改 loss 的返回,这已经不是「替换一个方法」的量级。

权重也对不上。为了走融合算子,训练版的 MoE 把每层的专家堆成一个大张量;HF 上的 checkpoint 很多是每个专家单独存键,有的是转置过的布局。名字对不上时,加载器把多余的键记一行 info 日志跳过,把缺的参数当新参数初始化,训练照常开始,只是初始 loss 高得离谱。

## 二、解法

最天然的直觉是**把改完的代码写出来**:复制一份 HF 的 modeling 手改,所有改动一眼看得见。它的毛病在维护:上游一升级,手改的那份就漂走了。VeOmni 只手写「改哪里」,改完的整份文件交给生成器写出来:

- **补丁配置**(每个模型族、每种硬件一份 Python 文件)只声明改动:整类换掉、整函数换掉、只重写某个类的某个方法;另外可以加导入、在文件顶部或某个类之后插入辅助函数与类、删掉不再需要的导入名。
- **生成器**(patchgen,仓库里单独发布的一个包)把钉住版本的 HF 源码当文本读进来,不导入它,按语法树逐个处理顶层定义并**按原顺序**输出:没点名的类和函数连注释原样照抄;被点名的前面加一段标记注释,写明换成了什么、为什么换。文件头列出上游模块、transformers 版本和全部补丁,另外写一份与上游源码的差异文件,两份都进仓库。
- **模型注册表**按模型类型登记一个取类函数。建模型时读 config.json 里的模型类型,取出这个函数;函数按当前设备导入 GPU 版或 NPU 版的生成文件,再按 config 里的架构名挑出具体的类。

![Qwen3-MoE 的两份生成文件逐行对照:左边官方 HF 源码与 GPU、NPU 两份补丁配置一起交给生成器;中间按 HF 源码原顺序列出每个顶层定义,多数原样保留,归一化、MLP、路由、稀疏 MoE 块、主干和因果语言模型头只重写前向,专家类与旋转位置编码函数整段换掉,算子空位和并行计划方法是补上的,两份之间唯一的差别是 NPU 版的稀疏 MoE 块没有接路由回放;右边注册表按模型类型与设备二选一导入,再往类上挂三个钩子](/opensource/VeOmni/02a-generated-modeling-file.svg)

上图是 Qwen3-MoE 的实际处置。**大部分定义原样保留**:注意力类、解码层、预训练基类、旋转位置编码类一字不改,序列并行版的注意力函数另行登记进 HF 的注意力函数表(见 03 章),不需要动类。被改的是 6 个类的前向、1 个专家类和 1 个函数;「补上的」有两样:文件开头的 6 个算子空位,以及因果语言模型类上返回并行计划的方法。后者就是补丁配置补结构的方式:要重写的方法在上游类里不存在时,生成器把它直接加进类体。

生成的 modeling 里只留**算子空位**,不写死用哪个融合实现;建模型之前按配置与硬件绑定,见 03 章。

**漂移检查把「看得见」变成「对得上」。** CI 在改动生成器、模型目录或依赖锁的提交上,用钉住的 transformers 把每一份补丁配置重新生成一遍,规整格式后与仓库里的生成文件和差异文件逐字比对,差一个字节就失败。于是仓库里的生成文件永远等于「当前补丁配置作用在当前钉住的上游源码上」的结果;手改生成文件会被下一次重生成覆盖,检查也过不去。升级 transformers 时,重生成后读差异文件,就知道上游动了哪里、补丁落在哪里。

**GPU 与 NPU 各生成一份。** 19 个模型族有 GPU 版补丁配置,其中 12 个另有 NPU 版;NPU 版逐条引用 GPU 版里写好的实现,只替换与设备有关的部分,生成出来是另一个独立文件。没有 NPU 版的 7 个族,在昇腾上也导入 GPU 版文件。

**模型自带的钩子。** 框架尽量不按模型类型写分支,而是问模型类「你有没有某个能力」;构建主流程里只剩两处按类型的白名单,一处管上下文并行,一处管编码器负载均衡。当前框架会去模型上找的能力有:并行计划,即哪些参数沿哪一维额外切,切法见 05 章;位置编号函数、多模态元数据函数与额外的拼批规则,见 08 章;配置类上的构建前自检,当前只有 DeepSeek-V4 实现;以及与权重相关的三样,权重转换器、导出时的索引键改名、LoRA 目标映射。前几样多半在补丁配置里作为方法补进类,后三样由取类函数在取类时挂到类上。

**权重转换器只管「转成什么形状」。** Qwen3-MoE 的 HF checkpoint 每层每个专家存 gate、up、down 三个键,生成的模型每层只有两个堆叠参数:gate 与 up 拼起来的 [E, 2I, H],和 down 的 [E, H, I]。转换器随权重一个一个流进来就收,某层某个投影的 E 个专家收齐就堆起来,gate 与 up 都齐了就拼接后交出去;所有分片读完还有没收齐的,直接报错,说明 checkpoint 残缺。别的族做的是别的形变:Qwen3-VL-MoE 只需转置,形状分辨不出是哪种布局时报错而不猜;DeepSeek-V4 还要把低精度存储的权重反量化;Qwen4-Exp 只在第 0 维补零行。权重怎样按分片流式读进来、谁读谁收,见 04 章。

**多 token 预测是「补上上游没有的结构」的完整例子。** Qwen3.5 的补丁配置做了四件事:在解码层类之后插入一个 MTP 模块类,子模块名与 checkpoint 里的键一一对应;重写外层条件生成类的构造函数,在 loss 权重为正时把这个模块建在顶层,名字就叫 mtp;重写文本主干的前向,按需把嵌入、位置编码和掩码带出来;重写外层前向,算出 MTP 的 loss,和主 loss 一起放进一个字典返回。参数名与发布的 checkpoint 完全一致,所以加载、分布式 checkpoint、导出 HF 权重都不用为 MTP 写专门代码。MTP 本身是什么见知识库。

**为什么实际不吃亏**:生成文件在运行时就是一个普通的 Python 模块,没有任何额外开销;没绑定的算子空位退回 HF 原逻辑,路由那处重写的注释也写明了以与 HF 原版逐位一致为目标。审阅成本只落在差异文件上:Qwen3-MoE 的 GPU 版生成文件 858 行,相对上游的差异文件 546 行。

## 三、代价

**生成物很大,而且进仓库。** 31 份生成文件合计 2888 KB,占 veomni 目录下 Python 代码的 39%。每改一次补丁配置,都要重生成并提交生成文件与差异文件,提交的改动行数被放大。

**版本被钉死在一个 transformers 上。** 生成和漂移检查都必须在 5.16.1 下做,因为生成器读的是本机装的那份上游源码;生成文件照样从 transformers 导入基类、掩码与工具函数。用 pip 安装的用户要自己装这个版本,运行时没有一道核对版本的检查。

**生成器只拦得住一部分上游变化。** 上游删掉一个补丁里还在引用的名字,规整格式时会报未定义名;上游只改了方法签名、目标还在时,补丁照样套上去,按旧约定运行。整类或整函数替换的目标在上游源码里找不到时,生成器不报错,那条补丁不生效,文件头却照样把它列进补丁清单。声明语法里有一个「修改构造函数」的装饰器,生成器根本没有实现,补丁被静默丢掉;要改构造函数只能把整个构造函数当方法重写。

**GPU 与 NPU 两份靠手工对齐。** NPU 版补丁配置一条一条地引用 GPU 版的实现,漏引一条,NPU 文件就少一处改动;漂移检查只比「重生成的和仓库里的是否一致」,不比两份之间是否一致。当前 Qwen3-MoE 就是这样:GPU 版的稀疏 MoE 块接了路由回放,NPU 版没有,也就是图中唯一一行两边颜色不同。

**自包含不是全部行为。** 取类函数在取类时往生成的类上挂钩子;昇腾上建完模型还会把前向包一层,把变长注意力的边界张量挪到 CPU;注意力实现在导入时登记进 HF 的全局注意力函数表。这几处都不在生成文件里,只读生成文件看不到。

**没登记的模型类型直接报错。** 默认模式下取类只查注册表,查不到就抛错,不会退回 HF 原版类。要训一个没移植的模型,只能整个作业切到 HF 模式,而那个模式同时关掉 VeOmni 的注意力登记与算子配置,序列并行和融合算子一起没了。

**多 token 预测有硬限制。** 开着序列并行,构造时直接断言失败;不能跨续训开关,因为参数集合变了,严格读取分布式 checkpoint 会缺键;只有文本与 Qwen3.5 视觉语言的 SFT 训练器会构造它的标签,DPO 与 RL 不支持;MFU 统计不含这个头,开了之后报出来的 MFU 偏低。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09)。两边都要回答「模型代码从哪来、怎么换构件、HF 权重怎么进来」,答案相反。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 模型代码从哪来 | 官方 HF 源码经补丁配置生成训练版,一个模型族一份文件 | 框架自己的层,构造时按规格(ModuleSpec)装配,见 Megatron 解读 08 章;HF 模型只在 LLaVA 这类多模态路径里整个包一层原样调用 |
| 换一个构件 | 在补丁配置里声明换类或重写方法,重新生成 | 在规格里换子模块的类,新构件要满足原有的输入输出与进程组约定 |
| HF 权重怎么进来 | 训练启动时直接读 HF 的 safetensors,布局不同的由模型自带的转换器在装载时转 | 用离线转换工具,按加载与保存两类插件搬成 Megatron 格式,见 Megatron 解读 13 章 |
| 上游没有的结构 | 在补丁配置里补模块、补方法 | 框架自带多 token 预测块,按层数参数打开 |
| 上游升级时 | 换钉住的 transformers 重生成,读差异文件 | 模型代码不随 transformers 变;接一个新结构要在框架里实现对应构件 |

取舍很清楚。Megatron 的层是自己写的,张量并行与流水并行可以直接写进层里,代价是每个新结构都要框架亲手实现一遍,HF 权重还要先离线转一次。VeOmni 放弃张量与流水并行,换来「HF 上出了新模型,写一份补丁配置就能训、直接读 HF 权重」,代价是版本钉死、生成物要维护,以及上一节那几处生成器拦不住的变化。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。作业参数只有下表几项;另一组是改补丁配置时用的开发期命令,放在第二张表,不影响正在跑的作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `MODELING_BACKEND` · 模型代码走哪一套 | 启动时的环境变量 | `veomni` | 设为 `hf`:配置、处理器、模型类全走 HF 的自动类,不登记 VeOmni 注意力、不装算子配置,生成文件与钩子都不用 | 启动日志的环境变量段 `MODELING_BACKEND=hf (source=env)`;建模型时打 `Loading model from Huggingface modeling.` |
| `model.config_path` · 读哪份 config.json | YAML 或命令行 | 不设则等于 `model.model_path` | 里面的 `model_type` 是注册表的键,`architectures` 的第一项决定挑哪个类 | `[CONFIG] Loading … from Huggingface …` 那一行 |
| `model.model_path` · 权重目录 | YAML 或命令行 | 不设:随机初始化 | 转换器按这里 checkpoint 的键名决定转不转 | `Unexpected key in state dict: …` 与 `Find missing key(s) in state dict: …` |
| `model.safetensor_idx_path` · 分片索引 | YAML 或命令行 | `model.model_path` 下的 `model.safetensors.index.json` | 导出 HF 权重时按它分片,MoE 族先做索引键改名;找不到则导出成单个文件 | `Converted fqn_to_index_mapping for …`;警告 `fqn_to_index_mapping is None, …` |
| `model.model_config` · 覆盖 config 字段 | YAML 或命令行 | 空 | 按字段覆盖 config.json 里的值,MTP 的开关就写在这下面 | 落盘的 `veomni_cli.yaml` |
| `model.model_config.text_config.mtp_loss_weight` · MTP loss 权重(Qwen3.5 系) | YAML 或命令行 | 不设:不建 MTP 头 | 为正且 checkpoint 的 `mtp_num_hidden_layers` 为正时才建头;权重在模型里乘,日志里的 `mtp_loss` 是乘过的值 | `Qwen3.5 MTP enabled: N layer(s), loss weight W.`;每步的 `foundation_loss`、`mtp_loss` |

| 开发期命令 | 做什么 | 什么时候用 |
|---|---|---|
| `patchgen <补丁配置模块> --dry-run` | 只读上游源码、报补丁条数,不写文件 | 刚写好补丁配置,先看能不能加载 |
| `patchgen <补丁配置模块> --diff -v` | 生成并规整 `.py`,同时写 `.diff`,打印补丁清单 | 改完一份补丁配置 |
| `patchgen --all --diff`(即 `make patchgen`) | 重生成仓库里全部补丁配置 | 升级钉住的 transformers 之后 |
| `patchgen --check`(即 `make check-patchgen`) | 重生成到临时文件,与仓库里的 `.py`、`.diff` 逐字比对,不一致时退出码为 1 | 提交前;CI 跑的就是它 |
| `patchgen --check --fix` | 用重生成结果覆盖仓库里的文件 | 确认漂移只来自格式规整时 |
| `patchgen --list` | 列出按 `pyproject.toml` 里 `[tool.patchgen]` 找到的全部补丁配置 | 确认新配置被发现 |

**观测。** 本章看 3 处。一是类从哪来:`Built foundation model class: …` 打出完整模块路径,默认模式下应当落在 `…generated.patched_modeling_<族>_gpu` 或 `_npu` 里;落在 `transformers.models…` 说明作业跑在 HF 模式。二是空位绑了什么:`OpSlot dispatch bound: …` 列出这份生成文件里每个空位绑上的实现,细节见 03 章。三是权重对没对上:转换器生效时,日志里不应出现带专家编号的 `Unexpected key in state dict`,`Find missing key(s)` 里也不应出现专家参数。另外,生成文件头的 `Based on: transformers==5.16.1` 应当和本机装的版本一致。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 训一个已移植的族(如 Qwen3-MoE),权重来自 HF | `MODELING_BACKEND` 保持默认;`model.model_path` 指向本地 HF 目录,`model.config_path` 不设 | 什么也不换;启动后先核对 `Built foundation model class` 指向 `generated` 下的文件 |
| loss 对不上 HF 基线,要一条对照曲线 | 同一份数据与种子另起一个作业,设 `MODELING_BACKEND=hf` 与 `model.accelerator.ulysses_size: 1` | 用丢掉序列并行、融合算子与 VeOmni 注意力换一条纯 HF 的参照曲线;两条曲线开始分叉的地方,再去读生成文件的 `.diff` |
| Qwen3.5 继续训练,连同 MTP 头一起训 | `model.model_config.text_config.mtp_loss_weight: 0.3`,`model.accelerator.ulysses_size: 1`,`model.tokenizer_path` 用本地目录,数据走对话模板 | 用每个深度多一层解码层和一次共享输出头的投影,换回一个和主干同步更新的 MTP 头;官方文档在 16 卡昇腾、Qwen3.5-35B-A3B、序列长 1024、1 层 MTP 上测得每步慢 3.9%、峰值显存多 2.1% |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动报 `Unknown Modeling name: X. No Modeling registered for this source.` | config.json 的 `model_type` 与注册表的键是否一致(`qwen3_5` 与 `qwen3_5_text` 是两个键) | 用已登记的键;没移植的模型只能整个作业设 `MODELING_BACKEND=hf` |
| MoE 模型初始 loss 远高于 HF 基线 | 日志里是否有大量带专家编号的 `Unexpected key in state dict`,以及 `Find missing key(s)` 里有没有 `experts.gate_up_proj` | 查这个族的取类函数有没有挂转换器,以及 checkpoint 实际是逐专家、已融合还是转置的布局 |
| 加载末尾报 `incomplete checkpoint detected` | 哪一层哪个投影没收齐专家 | 查 checkpoint 分片是否残缺,或 config 里的专家数与 checkpoint 不符 |
| 同一份配置在 GPU 与昇腾上行为不同 | 两份生成文件头注释里的补丁清单是否一致 | 在 NPU 版补丁配置里补上漏引的那一条,重生成 |
| CI 的 `Check Patchgen Drift` 失败 | 本机 transformers 是否为 5.16.1;是否手改了 `generated/` 下的文件 | 在钉住版本下 `patchgen --all --diff` 重生成后提交;确认只是格式漂移时用 `patchgen --check --fix` |
| 打开 MTP 后构造时断言失败,提到 sequence parallel | `model.accelerator.ulysses_size`、`cp_size` 是否大于 1 | MTP 与序列并行二选一 |
| 打开 MTP 后报 `Qwen3.5 MTP loss requires mtp_labels` 一类错误 | tokenizer 路径是不是 Hub 名;数据是否走对话模板 | 用本地 tokenizer 目录;纯文本数据变换不产出 MTP 标签 |
| 从旧 checkpoint 续训时打开 MTP,读档报缺键 | 保存那个 checkpoint 时是否已开 MTP | 从 HF 权重的第 0 步就开,不要跨续训切换 |

## 六、常见误区

- **以为模型类型没登记会自动回落 HF 原版。** 会这么以为,是因为上游给维护者的约束说明写着「键对不上会回落到原版 HF 加载」,配置那一层也确实如此:没有自定义配置类就用 HF 的配置。实际上取类那一步只查注册表,查不到直接抛错;回落只有整个作业设 `MODELING_BACKEND=hf` 这一条路,而这条路同时关掉了序列并行与融合算子。
- **以为改 `generated/` 下的文件能最快修一个 bug。** 会这么以为,是因为它就是普通 Python 文件,改完立刻生效。实际上下一次重生成会把它覆盖,CI 的漂移检查在那之前就会失败;修改要回到补丁配置。
- **以为漂移检查通过就说明补丁都生效了。** 它只保证仓库里的文件等于重生成的结果。补丁目标在上游找不到、上游改了签名、用了没实现的 `modify_init`,重生成一样稳定,检查一样绿,文件头的补丁清单也照列不误。要确认生效,去 `.diff` 里找对应的改动段。
- **以为 GPU 版和 NPU 版生成文件只差算子。** 会这么以为,是因为 NPU 版的描述写的都是「换成 NPU 融合实现」。实际上 NPU 版是逐条引用 GPU 版实现拼出来的,漏引就少一处改动;Qwen3-MoE 当前在昇腾上就没有路由回放。排查跨硬件差异,先对比两份文件头的补丁清单。
- **以为读生成文件就看到了全部行为。** 「自包含」说的是没有藏起来的猴子补丁,不是全部行为都在文件里:取类时挂上的转换器与 LoRA 目标映射、昇腾上对前向的一层包装、导入时登记进 HF 注意力函数表的实现,都在文件之外。
- **以为日志里的 `mtp_loss` 是 MTP 头的原始交叉熵。** 权重是在模型里乘上去的,日志里是乘过权重的贡献,训练优化的也是这个和。想看原始值,把权重设成 1.0。
- **以为 MoE 权重没对上会报错。** 键对不上时,多余的键只打一行 info 日志,缺的参数被初始化后训练照常开始;只有转换器自己发现某层专家没收齐才报错。最常见的来源是给新模型抄了兄弟族的转换器,而两边的 checkpoint 布局其实不同——上游在迁移 Qwen3-Omni-MoE 时就因此加载进了空的专家权重,转换器重写后才修好。
