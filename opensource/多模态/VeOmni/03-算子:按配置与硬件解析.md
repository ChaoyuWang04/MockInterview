# 算子:按配置与硬件解析

这一页回答一件事:模型里每个能换实现的算子,由谁、在什么时候决定用哪一份,选错了什么时候知道。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

训练框架想跑得快,就得把 HF modeling 里逐个写开的小算子换成融合实现:RMSNorm、RoPE、SwiGLU 换成 Liger 的融合核,MoE 的逐专家循环换成分组矩阵乘,交叉熵换成不物化整张 logits 的融合 linear 加交叉熵。最省事的换法是按名字替换:看到模块里叫 RMSNorm 的类,就换成融合版。这条路有三个坑。

**名字相同,数学不同。** Qwen3 的 RMSNorm 是「权重 × 归一化结果」,权重初始化为 1;Qwen3.5 的是「(1 + 权重)× 归一化结果」,权重初始化为 0。两者输入输出形状一模一样,把标准融合核替换上去,不报错、loss 照降,只是每一层都少乘了那个 1——**静默算错**。DeepSeek-V4 的 RoPE 只旋转最后一段通道、cos 与 sin 交错排列,通用的融合 RoPE 套上去直接出 NaN。

**换硬件。** 融合核的默认值是按 NVIDIA GPU 挑的,Liger 与 Triton 都假设 CUDA。同一份配置拿到昇腾上,要么在第一次前向时才因为包不存在或算子跑不了而崩,这时加载权重、切分的时间已经花掉;要么被某层兜底逻辑悄悄换回慢路径,吞吐掉了一截,用户还以为自己用着融合核。

**新结构只有专用算子才跑得动。** DeepSeek-V4 的稀疏注意力先由索引器替每个 query 挑出要看的 KV,再只算这些位置;mHC 把残差流扩成多路再混合。HF 原版是一段稠密的参考实现,能算对,序列一长就吃不消。Qwen3.5 的门控 delta 规则更极端:参考实现不认打包后的样本边界,打包训练的第一步就报错。对这些结构,「原版也能跑」只在字面上成立。

## 二、解法

最天然的直觉:**每个可替换的算子留一个空位,空位自己写明「我是哪个算子、哪种数学口径」;实现登记在一张按「算子加口径」分桶的表里,每个实现写明自己要什么硬件;建模型之前,按配置里的名字去对应的桶里取,取不到或硬件不符就当场报错。**

![注册表按算子名加变体分桶的示意:左列是生成的 modeling 里的 8 个空位,各自自报算子与变体;中列是注册表里对应的桶和桶里挂着的实现,颜色表示硬件要求,绿色为 NVIDIA GPU、黄色要求 SM90 这一代、紫色为昇腾 NPU、灰色跨多种硬件;右列是配置给的名字与查表结果:同一个 Liger 名字在标准、Qwen3.5、无权重三个 RMSNorm 桶里各取到不同口径的那一份,GPT-OSS 的专家桶里没有默认的 Triton 实现所以建模型前报错,门控 delta 规则选了只支持 SM90 的 FlashQLA 而本机是 SM100 所以硬件校验报错,mHC 取默认的 eager 时不查表、走 HF 原逻辑](/opensource/VeOmni/03a-variant-buckets.svg)

**空位**(OpSlot)是生成的 modeling 文件里的一个模块级对象,空位是补丁配置写进生成文件的,生成机制见 02 章。前向里只有两行守卫:空位绑了非 eager 的实现就调它,否则往下走 HF 原代码,原代码一行不改。空位带两个名字:算子名,和**变体**——同名算子的数学口径,例如 RMSNorm 有标准、无权重、Qwen3.5 带偏移三种,RoPE 有全维与只转一部分维度两种。

**注册表按「算子加变体」分桶**(KernelRegistry)。用户在配置里只填一个实现名,变体由空位决定。同一个 Liger 名字,在标准桶里取到偏移为 0 的那一份,在 Qwen3.5 桶里取到偏移为 1、全程 FP32 计算的那一份,用户没有机会把标准核装到 Qwen3.5 上。桶里没有这个名字,查表直接报错,并列出这个桶里有哪些可选。

**每个实现带一张硬件要求**:哪类设备(NVIDIA GPU、昇腾 NPU、寒武纪 MLU,或不挑),以及算力代数的下限与上限。查表时当场检查,不满足就报错,错误里写明它要什么。FlashQLA 目前只发了 Hopper 版,它的下限和上限都是 SM90,在 Blackwell 上会被拦下。

**什么时候定,分三个时刻,越早越好。** 解析配置时:注意力的名字先改写;在昇腾或寒武纪上,仍等于默认值的字段换成本机能跑的实现;然后按一张允许表校验,昇腾上不支持的显式取值、GPU 上填了只有 NPU 能跑的取值,当场拒绝。建模型、分配任何权重之前:先把交叉熵装进 HF 的损失映射,把负载均衡损失绑到一个进程级的函数指针上;取类时导入生成的 modeling;然后扫一遍这个模块里的全部空位,逐个查表绑定;最后才构造模型。前向时:守卫只看一个布尔,不查表。

**为什么实际不吃亏**:绑定只在建模型前做一次,前向路径上多出来的只是一次布尔判断;每个实现登记的是一个懒加载的工厂,没选中的库不会被导入,所以没装 TileLang 的昇腾机器照样能导入整个框架。任何空位都可以填 eager,它就是 HF 原逻辑,是对数值的基线。

**NPU 默认改写只动默认值。** RMSNorm、RoPE、视觉 RoPE、交叉熵换成昇腾实现,MoE 专家换成昇腾分组矩阵乘,SwiGLU 与负载均衡损失退回 eager;用户显式写了非默认值的字段原样保留,交给校验去拒绝。Qwen3.5 门控 delta 那三项只在一个模型族里有空位,不在改写范围内,要手动选。

**注意力走另一条路。** 注意力不经过空位,而是注册进 HF 自己的注意力函数表。在 VeOmni 后端下,FlashAttention 2/3/4、FlexAttention、MagiAttention 这几个名字在解析配置时就被改写成带序列并行的包装名——不管序列并行开没开;包装在每次前向时看序列并行开没开,开了才在注意力前后各做一次 all-to-all。eager、SDPA 与原生稀疏注意力不改写,建模型时只打一条警告,说它们缺序列并行支持。序列并行本身见 06 章。

**第三方后端的扩展点。** 各个选择字段都是普通字符串而不是枚举,第三方包可以往某个桶里登记新名字,同名覆盖要显式声明;MoE 的绑定函数也允许外部包先截获自己的名字,认不出的再交给开源版处理。

**DeepSeek-V4 的三项新结构。** 稀疏注意力的索引器与注意力本体各有一个选择,默认 eager,可选 TileLang(SM90 起)。它们不是函数空位,而是只存一个字符串的**配置值空位**(OpsConfigSlot),由模型代码自己按字符串分支,因为要换的是整段计算路径而不是一个函数。mHC 的前混合、后混合、最终收束各是一个函数空位,三个桶都只挂 TileKernels 的一份。三者**选了 TileLang 就不回落**:遇到非 CUDA 张量、不支持的头数、精度或带缓存的解码,直接报错。FP8 量化训练不是选算子而是选一套伪量化配方,不占空位;它的伪量化核只有 SM90 起的 NVIDIA GPU 能跑,所以在解析配置时就检查,不留到训练跑了一段、第一次伪量化时才炸。索引器的 KL 训练目标依赖两个 TileLang 实现,这条跨字段的约束由模型配置在建模型前自己检查。

**编译与 CUDA graph 也在这一层开。** torch.compile 只编译每个 decoder 块的前向方法,不把模块包起来,这样 FSDP2 在块前后挂的参数聚合与重分片钩子留在编译区之外;编译与图重放的原理见知识库「TorchCompile」「CudaGraph」两篇。前提在解析配置和切分时就检查:只支持 CUDA 与 FSDP2,不能有额外并行(专家并行的 all-to-all 可能被捕获进编译块),多模态只放行稠密的 Qwen3-VL;数据必须打包成**固定长度**,即开着动态批、再填充到「微批 × 最大序列长度」,否则每一步的打包长度都不同,不断重编译,CUDA graph 也无法重放。要用 CUDA graph,还得关掉前向后的重分片。

## 三、代价

**两套机制并存,报错时刻各不相同。** 空位注册表是新的一套;旧的一套在模型族的设备补丁里直接替换 HF 模块上的类或函数,当前还剩 DeepSeek-V3、DeepSeek-V4 的 RoPE 与 Wan 三处;Wan 那一处挂在旧版 Wan 模型上,那个模型没有登记进注册表、只有测试在用,能训的扩散版 Wan 用自己内联的 RoPE,不受它影响(09 章);交叉熵与负载均衡损失另有进程级的入口。同一类配错,有的在解析配置时报,有的在取类时报,有的在绑定空位时报。都在构造模型之前,但错误信息长得不一样,查的地方也不一样。

**默认值不等于对每个模型都合法。** 默认值按 GPU 上最常见的模型挑。DeepSeek-V4 的设备补丁把 RoPE 的 Liger 与昇腾实现都显式禁掉,默认配置直接报错,必须改成 Triton 或 eager;GPT-OSS 的专家桶里只有 Quack 一份,默认的 Triton 查不到。报错是对的,代价是换模型时配置要跟着改。

**eager 不是万能退路。** 大多数空位填 eager 就是 HF 原逻辑;门控 delta 规则与因果卷积的 eager 在打包训练下直接报错,MoE 专家的 eager 是逐专家循环,只适合调试。

**NPU 改写与模型无关。** 改写只知道「这个字段有没有昇腾实现」,不知道这个模型的算子口径在那份实现上验证过没有。DeepSeek-V4 的昇腾样例配置把 RMSNorm、RoPE、SwiGLU 全部钉成 eager,理由就是通用昇腾核没有对它的两种 RMSNorm 验证过。

**空位是全进程共享的。** 空位、配置值空位与配置单例都只有一份,同一进程里两个模型共用一个生成模块时,后绑定的覆盖先绑定的,只打一条警告(见 01 章)。

**融合交叉熵有契约。** Liger 的融合版自己做输出层投影,要求前向把隐藏状态和输出层权重一起交给损失函数;没打过补丁的模型拿不到这两样就报错,不会退回 eager。

**编译的限制多。** 专家并行、Qwen3-VL 上的序列并行、非打包数据、扩散训练都不支持;填充到固定长度浪费掉的 token 算力,是换来不重编译的代价。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09),它自己写 Transformer 层,融合与低精度主要交给 Transformer Engine。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 选择的粒度 | 每个算子单独一个选择,按「算子加变体」查表 | 先选一整条实现路线(Transformer Engine、本地实现或推理优化),规格工厂据此给每层挑好类,见 Megatron 解读 08 章 |
| 同名不同数学怎么防 | 口径写在空位上,桶里没有同口径的实现就报错 | 层是自己写的,口径由选中的类决定,不存在拿融合核去顶替别人的类这回事 |
| 注意力后端谁定 | 配置直接点名,解析时改写成带序列并行的包装 | 默认交给 Transformer Engine 按环境自动挑,也可以显式指定 |
| 条件不满足时 | 建模型前报错;DeepSeek-V4 的三项选了 TileLang 就不回落 | 融合 softmax 每次前向检查精度与形状,不满足就静默改走 PyTorch softmax |
| CUDA graph 的范围 | 只有按 decoder 块编译时附带的图重放 | 可按层捕获,也可把整轮前向反向捕获成一张图(不含优化器),见 Megatron 解读 12 章 |

两条路的出发点不同。Megatron 选的是路线,一次选定就是一套自洽的构件,单个算子在运行时按条件退回也不会换掉数学口径。VeOmni 拿来的是别人写的 modeling,没有整条路线可换,只能一个空位一个空位地替换,而逐个替换的每一处都可能静默出错——所以它把口径写在空位上、把硬件写在实现上,宁可在建模型前报错,也不在运行时回落。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。算子选择都在 `model.ops_implementation.*` 下,每个模型一份;编译开关在 `model.accelerator.torch_compile.*`。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `attn_implementation` · 注意力 | YAML 或命令行 | `flash_attention_2`,解析后改写为 `veomni_flash_attention_2_with_sp` | 可选 `eager`、`sdpa`、`flash_attention_2/3/4`、`flex_attention`、`magi_attention`、`native-sparse`;只有 FlashAttention、FlexAttention、MagiAttention 三族带序列并行 | 日志 `Replacing attn_implementation from …`;缺序列并行时的警告 `… you are missing sequence parallelism support.` |
| `moe_implementation` · MoE 专家计算 | YAML 或命令行 | `fused_triton`(SM70 起);昇腾改写为 `fused_npu`,寒武纪改写为 `fused_mlu` 或 `fused_mlu_triton` | `fused_quack` 要 SM90 起;`eager` 是逐专家循环;旧别名 `fused` 按本机解析并告警 | `OpSlot dispatch bound: … moe_experts (triton)` |
| `cross_entropy_loss_implementation` · 交叉熵 | YAML 或命令行 | `liger_kernel`;昇腾改写为 `npu`,寒武纪改写为 `eager` | `chunk_loss` 是分块的 linear 加交叉熵,不挑硬件;`npu` 是它加一道昇腾检查;`eager` 先物化整张 logits | `✅ VeOmni ops config applied: CrossEntropy (…)` |
| `rms_norm_implementation` · RMSNorm | YAML 或命令行 | `liger_kernel`;昇腾改写为 `npu`,寒武纪改写为 `eager` | `triton` 只有 DeepSeek-V3 登记了(批不变版) | `OpSlot dispatch bound: rms_norm (…)` 或 `Apply ops patches to …` |
| `swiglu_mlp_implementation` · SwiGLU | YAML 或命令行 | `liger_kernel`;昇腾、寒武纪改写为 `eager` | 没有昇腾实现 | 同上 |
| `rotary_pos_emb_implementation` · RoPE | YAML 或命令行 | `liger_kernel`;昇腾改写为 `npu`,寒武纪改写为 `eager` | `triton` 只有 DeepSeek-V3、DeepSeek-V4 与旧版 Wan(只有测试在用)登记了;DeepSeek-V4 只能选 `triton` 或 `eager` | 同上 |
| `rotary_pos_emb_vision_implementation` · 视觉塔 RoPE | YAML 或命令行 | `eager`;昇腾改写为 `npu` | 只有 `npu` 一种非 eager 实现 | 同上 |
| `load_balancing_loss_implementation` · 负载均衡损失 | YAML 或命令行 | `triton`;昇腾、寒武纪改写为 `eager` | 选 `triton` 而没装 triton 包时解析即报错 | `✅ VeOmni ops config applied: … LoadBalancingLoss (…)` |
| `rms_norm_gated_implementation`、`causal_conv1d_implementation`、`chunk_gated_delta_rule_implementation` · Qwen3.5 门控 delta 三件套 | YAML 或命令行 | 都是 `fla`,不做硬件改写 | 昇腾选 `npu`,门控 delta 规则还可选 `npu_ascendc`;`flash_qla` 只限 SM90;`eager` 在打包训练下报错 | `OpSlot dispatch bound: …` |
| `dsa_indexer_implementation`、`dsa_attention_implementation` · 稀疏注意力的索引器与本体 | YAML 或命令行 | `eager` | DeepSeek-V4 可选 `tilelang`(SM90 起);`cudnn` 与 `flashmla_cudnn` 是 GLM-DSA 的 | `OpSlot dispatch bound: dsa_indexer_implementation (…)` |
| `mhc_implementation` · mHC | YAML 或命令行 | `eager` | `tilelang` 要 SM90 起、BF16 激活 | `OpSlot dispatch bound: mhc (…)` |
| `qat_implementation` · 量化训练配方 | YAML 或命令行 | `none` | `fp8_blockwise` 只在 SM90 起的 NVIDIA GPU 上放行,训练看到的舍入与 FP8 部署一致 | 解析期报错 `qat_implementation=… requires an SM90 or later NVIDIA CUDA GPU` |
| `model.accelerator.torch_compile.enable` 及 `backend`、`mode`、`fullgraph`、`dynamic` | YAML 或命令行 | 关;`inductor`、不设、开、关 | 开了只编 decoder 块;`mode: reduce-overhead` 或 `backend: cudagraphs` 才走 CUDA graph | `Compiled N decoder blocks with torch.compile.` |
| `train.pad_to_length` · 填充到固定长度 | YAML 或命令行 | 关 | 开了且开着动态批时,长度定为「微批 × 最大序列长度」;编译必须开它 | `set pad_to_length = micro_batch_size * max_seq_len = …` |
| `MODELING_BACKEND` | 环境变量 | `veomni` | 设为 `hf` 时不注册 VeOmni 注意力、不改写注意力名、不装损失映射 | `⚠️ Skip applying ops patch. Using huggingface transformers backend.` |

**观测。** 本章看 4 处。一是解析期的两类改写:`Replacing attn_implementation from …` 与每个字段一行的 `…: auto-resolved GPU default '…' -> '…' on Ascend NPU.`,在昇腾上跑之前先数一遍被改了哪些。二是 `✅ VeOmni ops config applied: …` 后面那张 `=========== OPS ============` 表,它只可靠地反映交叉熵与负载均衡损失。三是真正的绑定结果 `OpSlot dispatch bound: …`,每个空位一项,写着它最终拿到的实现名;旧机制的三个模型族另看 `Apply ops patches to …`。四是同一进程里第二个模型改绑时的警告 `OpSlot('…', '…') was already bound to '…'; rebinding to '…'.`

**典型配置。** 组合与推荐值是按语义推的起点,不是实测最优。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| H100 × 8 训 Qwen3 MoE 或稠密文本模型 | 算子全用默认;要试 SM90 专用的专家核就加 `moe_implementation: fused_quack` | 默认组合用 Triton 与 Liger 覆盖 SM70 起的卡;换 Quack 是拿 SM90 依赖换另一套分组矩阵乘,且只有 Triton 与昇腾两家带专家 LoRA 的融合版,挂专家 LoRA 时不要换 |
| H100 上训 DeepSeek-V4,要稀疏注意力真正稀疏地算 | `attn_implementation: eager`、`dsa_indexer_implementation: tilelang`、`dsa_attention_implementation: tilelang`、`mhc_implementation: tilelang`、`rotary_pos_emb_implementation: triton`;要对齐 FP8 部署再加 `qat_implementation: fp8_blockwise` | 拿 SM90 依赖与不回落换稀疏注意力的速度;量化训练多付一层伪量化的开销,换训练与部署看到同样的舍入 |
| 昇腾上训 DeepSeek-V4 | `attn_implementation: eager`、`moe_implementation: fused_npu`、`cross_entropy_loss_implementation: npu`、`load_balancing_loss_implementation: eager`、`rms_norm_implementation: eager`、`rotary_pos_emb_implementation: eager`、`swiglu_mlp_implementation: eager` | 把没对这个模型验证过的通用昇腾核挡在外面,拿 RMSNorm 与 RoPE 的速度换数值可信;专家与损失仍走昇腾实现 |
| 稠密文本模型想减掉 kernel 启动开销 | `model.accelerator.torch_compile.enable: true`、`mode: reduce-overhead`、`model.accelerator.fsdp_config.reshard_after_forward: false`、`train.dyn_bsz: true`、`train.pad_to_length: true` | 用前向后不重分片多占的参数显存,加上填充浪费的 token,换 decoder 块的融合与 CUDA graph 重放 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 昇腾上启动即报 `… is not supported on Ascend NPU.` | 哪个字段被显式写成了非默认值 | 改成报错里列出的值,或 `eager` |
| 建模型前报 `Unknown kernel 'triton' for op='moe_experts', variant='gpt_oss'` | 这个模型的空位变体下挂了哪些实现 | 按报错里的 `Available` 改,GPT-OSS 用 `fused_quack` |

## 六、常见误区

- **以为 OPS 表里 `_fused_moe_forward = None` 说明没用上融合 MoE。** 会这么以为,是因为那张表紧挨着「ops config applied」打出来,看上去就是全部算子的最终状态。实际上它在建模型的最开头打印,那时 MoE 的函数指针还没绑,空位绑定要到取类之后才发生。MoE 用了什么,以后面那行 `OpSlot dispatch bound: … moe_experts (…)` 为准。
- **以为在 YAML 里显式写上默认值,昇腾上就不会被改写。** 会这么以为,是因为「显式写的非默认值会被保留」这句话容易被读成「显式写的都保留」。实际上改写只比较值是否等于默认值,写没写看不出来:在昇腾上显式写 `load_balancing_loss_implementation: triton` 一样会被换成 `eager`。
- **以为昇腾上自动改写出来的实现都能放心用。** 改写只看这个字段有没有昇腾实现,不看这个模型的口径有没有验证过。DeepSeek-V4 的 RMSNorm 在昇腾上会被默默绑到通用核上,官方样例配置正是为此把它钉成 `eager`;RoPE 则因为设备补丁显式禁用了昇腾实现,会在建模型前报错。
- **以为选了 `sdpa` 开序列并行也能正确训练。** 会这么以为,是因为只有一行警告、训练照常开始。实际上 Qwen3 这类模型的序列并行 all-to-all 全在注意力包装里做,`sdpa` 不走包装,每张卡只在自己那一段序列里做注意力,没有报错。
- **以为 `eager` 永远是安全的退路。** 对大多数空位是,对 Qwen3.5 的门控 delta 规则与因果卷积不是:它们的 eager 不认打包后的样本边界,而动态批默认开着,打包训练第一步就报错。
- **以为 GPU 上什么都不配就能训任何模型。** 默认值不是对每个模型都合法:DeepSeek-V4 的 RoPE 默认值被显式禁用,GPT-OSS 的专家桶里没有默认的 Triton。它们都会在建模型前报错,而不是静默跑;遇到了按报错里给的可选值改即可。
- **以为 FP8 量化训练会像其他选项一样在绑定时才检查。** 它不是空位,没有查表这一步,所以专门在解析配置时检查 SM90;在 ROCm、昇腾或更老的卡上,作业在读配置时就会停下,不是跑到一半。
