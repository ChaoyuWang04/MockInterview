# 显存:重算与激活卸载

这一页回答一件事:长序列把激活推到比权重还大时,VeOmni 怎样让每一层的激活只在层与层的接缝处留一份,又不让搬运把每一步拖慢。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

FSDP2 把参数、梯度和优化器状态都分掉了(04 章),激活一点没分。前向每过一层,注意力和 MLP 里的中间结果都要留到反向,总量与每卡 token 数、隐藏维、层数同时成正比。多模态样本天生长,一段视频或一组高分辨率图拼进一条序列就很长。算一笔账:每卡 32K token、隐藏维 4096、BF16,光是一层的**输入**就是 256 MiB,36 层是 9 GiB,层内的中间结果还比输入宽得多;而一个 8B 模型切在 8 张卡上,每卡分到的 FP32 主权重只有 4 GB。先爆的是激活。

序列并行能把激活按卡数摊薄(06 章),但它要占卡、有头数约束。剩下两条路是少存和挪走,各有各的坑。

少存,就是反向时重算。问题在于重算的边界画在哪:画得太细,要改模型代码;画得太粗,反向时一口气重跑一大段,临时峰值又回来了。

挪走,就是把存下来的激活拷到主机内存。最直接的写法是每存一个张量就同步拷一次:计算流停下来等 PCIe,反向时再一个一个同步拷回,每一步都被拖慢。异步拷贝能躲开等待,可它的账跨越一次前向和一次反向——哪一层的哪个张量在主机上、何时能释放卡上那份、何时该预取回来——一步中途报错,账没清干净,下一步就会对上错的张量。

两件事叠在一起还有一个顺序问题:重算和卸载拦的是同一件事,都是「autograd 把张量存下来留给反向」。谁在外、谁在内,决定了搬走的是什么。顺序反了,要么把本该扔掉的中间结果也搬一遍,要么该搬的一样没搬。

## 二、解法

最天然的直觉:**激活只在层与层的接缝处留一份**。层内的中间结果不存,反向到这一层时拿层输入重算一遍;层输入本身也不必一直占着卡,前向算下一层时顺手把它拷到主机,反向快到这一层时再提前拷回来。

![一步里 4 层解码层的时间线:计算流上前向 L0 到 L3、反向 L3 到 L0,每个反向先重算本层;拷贝流上前向时依次把 L0、L1、L2 的输入搬到主机,L3 的输入不搬;反向时 L2 的回搬没有预取、计算流空等一段,之后每搬回一层就预取下一层;下方四条泳道画出每层输入先在卡上、再在主机上、反向前回到卡上的时段,最底一行说明层内中间激活在前向算完即丢、反向时重算出来用完即丢](/opensource/VeOmni/10a-recompute-async-offload.svg)

**重算按整层做,默认开。** 构建时,在分片之前(04 章),框架让模型自己打开重算:凡是继承了 transformers 那个带重算入口的层基类的模块——文本的解码层、视觉塔的块、音频编码层——前向只存本层输入,反向时整层重跑一遍。粒度由模型代码决定,和分片分组无关:给分片追加分组类名(04 章)不会改变哪些模块被重算。没有「隔 N 层重算一次」或「只重算注意力」的档位;框架留了一个挂选择性重算上下文的口子,当前没有任何调用方往里填东西,那个把算子名转成算子对象的工具函数也没有调用点。

**两种重算实现,当前只有一种能用。** 默认走 PyTorch 的非可重入实现,并打开提前停止:反向重跑到反向所需的张量都算出来就停,不跑完这一层剩下的部分。可重入实现是另一条路,打开后框架换上自己的一版检查点函数,注释说是为了去掉「可重入加重算」多出来的一次参数聚合,挂的是旧版 FSDP 的内部钩子。它要从被调用的对象上取出所属模块,而解码层交给它的是一个偏函数,取不到——树内一份配置样例的注释写明,这条路在 transformers v5 下对所有模型都是坏的。

**同步卸载:整次前向包一层,见一个存一个。** 它在训练器那一层给整次前向、整次反向各套一个「存张量时先过一道」的钩子,不分模块:任何被存下的张量,只要大于 1 KB、又不是转置过的权重,就同步拷到主机。可以给卡上留一个额度,额度内的先到先留,超出的才搬。与重算一起开时,前向一律全搬(反正存下的只剩各层输入),额度只用在反向重算出来的中间结果上,注释说这是为了避免来回颠簸。拷贝用可分页内存,注释给的理由是锁页内存会被缓存分配器攒着不还。

**异步卸载:按层挂,只搬层输入。** 同样在分片之前、而且在打开重算之前,框架找出要卸载的模块——默认就是模型声明的不可拆分模块(解码层,多模态模型还有视觉块),也可以按名字模式指定——把每个实例换成一个私有子类,在它的调用入口外面再套一层存张量的钩子。于是一层前向时钩子叠了两层:外层是卸载,内层是重算。重算把层输入存下来的那一刻发生在内层钩子挂上之前,经过的是外层,被卸载接走;层内的中间结果由内层的重算接管,不存。这正是源码注释写明参照 MindSpeed-MM 的那个顺序。钩子按内存地址认张量,只接走与本层输入同一块内存的那一个,其余一概放行。

**搬运怎样和计算错开**(见上图)。所有被卸载的层按调用顺序编号,共用一条拷贝流。每层一开始,把它的输入交给拷贝流去拷,计算流接着算这一层;进入下一层时,先在主机侧等上一层的拷贝完成,再把卡上那个张量的存储换成空的。这一步不是删掉一个副本,而是把原张量本身掏空,所以只接受独占整块存储的张量,和别的视图共用内存的一律不碰。最后一层的输入不搬,反向第一个就要用它。反向到某一层取回输入时,顺手让拷贝流把下一层的输入预取回来。

**主机缓冲从一个池里取。** 池按形状、步长和精度分桶复用;闲置缓冲的总量有上限,超出就按最久未用淘汰;锁页申请失败时退回可分页内存,打一行警告。上限只管闲置的,不管在途的:一步里正在主机上躺着的层输入可以超过它。

**每一步开头清账。** 编号计数器与在途张量表跨越一次前向与反向;正常情况下反向每取回一个张量就销一笔。一步中途报错,autograd 图可能还活着,残留的编号会让下一步的预取与等待对上错的张量。所以训练器在每一步取完数据、回调开始之前,把挂在模型上的账本全部重置;层调用中途抛异常也会当场重置。缓冲池不在重置之列,旧图回收后照样复用。视觉塔在一步里可能被调两次(图像一次、视频一次),计数器遇到重复编号时递增而不清零,这是相对 MindSpeed-MM 改掉的一处撞号。

**两种卸载只能选一个。** 同步是训练器那一层的钩子,异步是模块那一层的钩子,同时打开,解析配置时就报错。开着异步时,训练器那一层的前向与反向上下文都是空的。

**为什么实际不吃亏**:重算的代价是每层反向前多一次本层前向,而且提前停止会截掉用不上的尾巴,换来的是层内中间结果全部不存;异步卸载每层只搬一个张量,拷贝走独立的流,与下一层的计算重叠,只要一层的计算比这一次拷贝慢,拷贝就藏在计算后面。

## 三、代价

**重算是一刀切的。** 默认开,每层都做;激活本来放得下的短序列作业也付这份算力。要么全开,要么全关,没有按层数或子模块折中的档位。

**同步卸载每搬一个张量就停一次。** 拷贝和计算在同一条流上串行,可分页内存又让拷贝本身更慢;额度外的中间结果在反向重算出来后立刻被搬走、又立刻搬回。它不认模块,层外的张量只要被存下、大于 1 KB,一样要搬。它也不认同一个张量被存了几次,每存一次搬一份。

**异步卸载离开重算就不划算。** 不开重算时,钩子照样只接走层输入,层内的中间结果全留在卡上,省下的只是每层一份输入。

**拷贝慢于计算时,异步退化成等待。** 进入下一层前要在主机侧等上一层拷完,拷不完 CPU 就停在那里,下一层的计算发不出去。反向第一个要搬回的那层没有人替它预取,这段回搬总是露在外面。D2H 和 H2D 共用一条拷贝流,两个方向不能同时跑。

**主机内存是另一本账。** 在途的层输入全都在主机上:按上面那笔账,每个 rank 约 9 GiB,同机 8 个 rank 约 70 GiB,而且默认是锁页内存。调小缓存上限压不住这个峰值,只会让每一步重新申请锁页内存。

**认张量靠第一个位置参数。** 本层输入既不在第一个位置参数、也不在隐藏状态那个关键字里时,钩子找不到它,就退化成把这一层存下的所有合格张量都搬走。本层输入如果是别人的视图,会先复制一份独占的再搬,这份复制本身也占显存。

**自动发现要模型声明。** 模型没声明不可拆分模块,或者声明了却一个实例也匹配不上,构建时直接报错,不像分片分组那样静默退化(04 章)。

**扩散模型各有各的重算。** Wan、Qwen-Image、LTX 的 DiT 不走解码层基类,而是在自己的块循环里调检查点;LTX 在循环里写死了非可重入实现,可重入与提前停止两项对它不起作用。MiniMax-H3 的 DiT 干脆不看重算开关:块级重算由条件模型交给它的一个字段决定,在线编码与离线训练两条数据路径都把这个字段写成开。扩散训练本身见 09 章。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09)。

它的重算和卸载都做到了子模块一级,正好衬出 VeOmni 只在层边界上动手的选择。Megatron 这一侧的机制见 Megatron 解读 11 章。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 默认 | 重算默认开,每层都做 | 重算默认关,不设就保存全部激活 |
| 重算粒度 | 只有整层;选择性重算的挂口存在,没人用 | 可以整层(均匀分段,或只对每个流水级里指定数量的层),也可以只重算层内子模块,选了子模块档又不指定时默认只重算核心注意力 |
| 卸载什么 | 每层一份层输入,层内全靠重算 | 细粒度卸载按子模块卸它们的输入(归一化、QKV 线性、核心注意力、专家第一层等),与重算是两套独立配置 |
| 搬运怎么排 | D2H 与 H2D 共用一条拷贝流;规则写死:最后一层不搬,回搬时预取下一层 | D2H 与 H2D 各一条流;第一次迭代是热身,记下各组的分组与字节数,之后把最后几组标成不卸载,保证回搬不挡住计算流 |

差异来自模型从哪来。Megatron 自己写 Transformer 层,可以在层里任何一处插检查点、插卸载边界;VeOmni 拿的是 HF 的 modeling,不改写模型代码就能控制的边界只有「一层的调用入口」,所以重算和卸载都挂在那里,一个管层内、一个管层输入,靠钩子的内外顺序拼成一套。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。重算与异步卸载都在构建时、分片之前挂到模型上,同步卸载在训练器构建末尾决定;DPO 的参考模型两者都关(01 章)。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `model.accelerator.gradient_checkpointing.enable` · 按层重算 | YAML 或命令行 | `true` | 关:层内中间激活全部留卡上,每层反向少一次前向;激活显存随层数与 token 数线性涨 | 日志 `Enable gradient checkpointing.`;每步指标 `max_memory_allocated(GB)` |
| `model.accelerator.gradient_checkpointing.enable_reentrant` · 可重入实现 | YAML 或命令行 | `false` | 当前不要开:换上的检查点函数从偏函数上取不到模块,第一次前向就报错 | 报错栈停在框架自带的 `CheckpointFunction.forward` |
| `model.accelerator.gradient_checkpointing.early_stop` · 重算提前停止 | YAML 或命令行 | `true` | 关:反向重算跑完整层,多算一截;只对非可重入实现生效 | profiler 里每层反向前那段重算的长度 |
| `model.accelerator.gradient_checkpointing.debug` · 检查点调试 | YAML 或命令行 | `false` | 开:打开 PyTorch 的检查点调试模式,重算前后存下的张量对不上时给出更详细的报错 | 报错信息 |
| `model.accelerator.offload_config.enable_activation` · 同步激活卸载 | YAML 或命令行 | `false` | 开:整次前向与反向里被存下的张量同步搬到主机;与异步互斥 | 每步耗时;每步指标 `cpu_used_memory(GB)` |
| `model.accelerator.offload_config.activation_gpu_limit` · 同步卸载的卡上额度(GB) | YAML 或命令行 | `0.0` | 调大:更多激活留卡上,搬得少、每步快;开着重算时只作用于反向重算出来的中间结果 | `max_memory_allocated(GB)` 与每步耗时一起看 |
| `model.accelerator.offload_config.enable_async_activation` · 异步激活卸载 | YAML 或命令行 | `false` | 开:按层把层输入异步搬到主机;与同步同开,解析即报 `mutually exclusive` | 构建时每个被挂的模块一行 `Applying activation offload to module: …, offload idx: …, offload_layers_num: …` |
| `model.accelerator.offload_config.activation_offload_modules` · 卸载哪些模块 | YAML 或命令行 | `[]`:按 `_no_split_modules` 自动发现 | 名字按模块全路径逐段匹配,`*` 不跨点;`model.layers.{*}` 展开这个模块列表的全部子层并按顺序编号;一个都匹配不上直接报错 | 同上那行日志里的 `offload idx` 与 `offload_layers_num`,最后一个编号的那层不会被搬 |
| `model.accelerator.offload_config.activation_offload_host_cache_limit_gb` · 主机闲置缓冲上限(GB) | YAML 或命令行 | `4.0` | 调小:闲置缓冲更早还给系统,之后要重新申请锁页内存;`0` 关掉复用;不限制在途的量;负数或非有限值解析即报错 | `cpu_used_memory(GB)`;警告 `Pinned host allocation for async activation offload failed; falling back to pageable host memory.` |
| `train.profile.enable` / `start_step` / `end_step` / `profile_memory` · 抓 trace 与显存历史 | YAML 或命令行 | `false` / `1` / `2` / `true` | 开:在区间内抓 trace,并录下显存分配历史 | 日志 `Profiling memory visualization saved at ….pkl`,拿 PyTorch 的显存快照查看器打开 |

**观测。** 本章看 4 处。一是挂没挂上:开重算应当看到一行 `Enable gradient checkpointing.`,没有这一行说明模型没有开启重算的方法,开关被静默跳过;开异步卸载应当看到每个目标模块一行 `Applying activation offload to module: …`,数一数行数、看 `offload_layers_num` 是否等于层数(多模态模型还要加上视觉块)。二是峰值:开着 wandb 时每步上报 `max_memory_allocated(GB)`、`max_memory_reserved(GB)` 与 `num_alloc_retries`,都是全体 rank 取最大;每个 epoch 结束打一行 `VRAM usage after epoch N: cur …GB, max …GB.`。三是主机一侧:`cpu_used_memory(GB)` 与 `cpu_available_memory(GB)`,异步卸载的在途量都算在这里。四是时间线:打开 profiler 抓一两步,看拷贝流上的 D2H 是否被每层前向盖住、反向开头那段 H2D 有多长,再用显存快照确认峰值落在哪一层。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 文本或多模态 SFT,序列不长、激活放得下 | `model.accelerator.gradient_checkpointing.enable: false` | 用显存换掉每层反向前的那次重算,每步更快;序列一长先 OOM 在激活上 |
| 长视频或长文档,重算之后激活仍放不下,主机内存充裕(每个 rank 能腾出「层数 × 每层输入」那么多) | 重算保持默认,加 `model.accelerator.offload_config.enable_async_activation: true` | 每层一份层输入挪到主机,换来 D2H 与 H2D 的带宽占用和锁页内存;一层计算比一次拷贝快时开始拖慢每步 |
| 显存极紧的 DiT LoRA,连参数也要放主机 | `model.accelerator.fsdp_config.offload: true`,加 `model.accelerator.offload_config.enable_activation: true`、`activation_gpu_limit: 2.0`,重算保持开 | 参数、梯度、优化器状态和各层输入全部去主机,卡上只留 2 GB 给反向重算的中间结果;每步都要同步搬运,换来能在小卡上跑起来 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 开了重算,激活显存却和没开一样 | 日志里有没有 `Enable gradient checkpointing.`;模型的层是否继承了带重算入口的层基类 | 没有就是开关被跳过,换用有这个基类的生成 modeling;DiT 查它自己的块循环 |
| 打开可重入后第一次前向就报 `AttributeError` | 报错栈是否停在框架自带的 `CheckpointFunction.forward` | 关回 `enable_reentrant: false` |
| 开异步卸载后构建时报 `requires model._no_split_modules` 或 `did not match any` | 模型的不可拆分模块声明,或自己写的名字模式 | 用 `activation_offload_modules` 写出与模块全路径逐段对得上的模式 |
| 开异步卸载后显存几乎没降 | 重算是否开着;`offload_layers_num` 是否等于层数 | 打开重算;模式漏了的层补上 |
| 开异步卸载后每步明显变慢 | profiler 里 D2H 是否比每层前向还长;反向开头 H2D 的等待 | 每卡 token 太少时拷贝盖不住,改用序列并行(06 章)或关掉卸载 |
| 主机内存一路涨,或被容器杀掉 | `cpu_used_memory(GB)`;同机 rank 数 × 层数 × 每层输入 | 调小缓存上限只压闲置量;真正的峰值要靠减小每卡 token 数或改用序列并行 |
| 同步卸载开着,每步慢了一大截 | `activation_gpu_limit` 是否为 0 | 能腾出显存就调大额度,或者改用异步卸载 |
| 自己写的训练器开了异步卸载,偶发一步报错之后行为异常 | 它是否重写了一步训练,却没有在每步开头调 `_reset_async_activation_offload_if_enabled` | 照四个任务训练器的做法,在取完数据、回调开始之前补上这一调用 |

## 六、常见误区

- **以为 `max_memory_allocated(GB)` 是这一步的峰值。** 会这么以为,是因为它每步都上报一次。实际上树内没有任何地方重置峰值统计,它是从作业开始到现在的历史峰值,而且是全体 rank 的最大值;第一步的装载峰值(04 章)或某一步的长样本会一直挂在上面,之后调小激活也看不到它往下走。要比较开关前后,各起一个作业看前几步,或者用 profiler 的显存快照。
- **以为 `activation_offload_host_cache_limit_gb` 是主机内存的上限。** 会这么以为,是因为它的名字里有 limit、单位是 GB。实际上它只管闲置缓冲池能留多少,在途的层输入不受它约束;调到 0 也照样占那么多主机内存,只是每一步都要重新申请锁页内存,反而更慢。
- **以为异步卸载会把整层激活都搬走。** 会这么以为,是因为「激活卸载」听起来是全量的。实际上它只搬每层一份层输入,层内的中间结果靠重算扔掉;关掉重算只开卸载,省下的显存很少,这是最常见的误配。
- **以为可重入重算只是另一种风格,可以随便切。** 会这么以为,是因为参数说明只写了一句「使用可重入实现」。实际上框架在这条路上换了自己的检查点函数,它要从被调用对象上取所属模块,而当前的解码层交给它的是偏函数,开了就报错。
- **以为追加 `basic_modules` 能改重算粒度。** 会这么以为,是因为分片分组和重算都是「按层」。实际上 `basic_modules` 只决定 FSDP2 的分组(04 章);重算落在哪些模块上由模型代码里哪些类继承了带重算入口的层基类决定,异步卸载的自动发现也只看 `_no_split_modules`,不看这里追加的类名。
- **以为同步卸载的额度是「最多留这么多在卡上」的硬顶。** 会这么以为,是因为它的单位是 GB。实际上它按存下的先后计数,额度内的先到先留;开着重算时前向一律全搬,额度只在反向重算时起作用,前向的显存它管不着。
- **以为 DiT 也听重算开关的。** Wan、Qwen-Image 听,LTX 听但只认非可重入;MiniMax-H3 不听,它的块级重算始终打开,关掉开关也不会变快。
