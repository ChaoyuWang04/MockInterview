# 长序列:Ulysses 与上下文并行

这一页回答一件事:一条序列长到一张卡装不下它的激活时,VeOmni 怎么把它分给几张卡,又在哪一处让每张卡看到整条序列。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

FSDP2 分掉的是参数、梯度和优化器状态,**激活不分**:每张卡照样把自己那条样本从头算到尾。序列长度翻倍,每一层存下来留给反向的激活就翻倍。长视频、长文档、多图对话把一条样本拉得足够长时,先爆的不是权重,是这一条样本自己的激活;再多卡做数据并行也救不了,因为每张卡都得装下一整条。

把序列沿长度切给几张卡,是最直接的办法。归一化、MLP、各个线性投影都是逐 token 独立的,切开之后各算各的,一点不受影响。**只有注意力不行**:每个 query 要看到它之前的全部 key,而那些 key 分散在别的卡上。

难点于是落在注意力怎么补齐整条序列上,而这一步有硬约束。VeOmni 的做法是在注意力这一处把「按序列切」临时换成「按头切」,这要求头数能被切开:8 个 query 头配 3 张卡,根本分不开,开不了;GQA 的 KV 头更少,2 个 KV 头配 4 张卡,也得先想办法。DeepSeek-V4 更极端:它的 KV 只有一个头,按头切无从谈起,而它的压缩器与稀疏索引器要沿整条序列开窗,每张卡只拿一段根本算不了。

数据这一头也有坑。按卡数等分序列,长度除不尽时,切片按整除取整,除不尽的尾巴 **静默丢掉**,不报错;next-token 的标签跨段边界,一段最后一个 token 的标签在下一张卡上,切完再移标签就错位了。

## 二、解法

最天然的直觉:**注意力之外按序列切,注意力之内按头切**。进注意力前做一次 all-to-all,每张卡交出自己那段的大部分头、换回别人那几段的少数头,于是每张卡拿着整条序列的几个头,照常调用 FlashAttention;出来再一次 all-to-all 换回去。一层只多这两次交换,其余计算与参数都不动。all-to-all 与 Ulysses 本身的原理见知识库「并行策略」「集合通信」两篇。

![Ulysses 在一层注意力前后的两次换切法:以序列并行度 4、8 个 query 头、2 个 KV 头为例,query 在注意力之前每卡持有 1 段序列乘 8 个头共 8 格,all-to-all 之后每卡持有 4 段乘 2 个头共 8 格;KV 头数 2 小于并行度 4,先把每个 KV 头复制 2 份,再 all-to-all 成每卡 4 段乘 1 个头,卡 0 与卡 1 拿到 kv0、卡 2 与卡 3 拿到 kv1,正好配上各自的 query 头;注意力算完,输出再一次 all-to-all 回到按序列切的形状](/opensource/VeOmni/06a-ulysses-reshard.svg)

**网格:序列并行维排在分片维的内侧。** 设备网格的各维从外到内是组间复制、组内分片、Ulysses、上下文并行,所以一个序列并行组是编号相邻的几张卡,单机 8 卡、序列并行度不超过 8 时,交换都在机内。在这张网格上再拼出 4 种组:读数据的组只含复制与分片两维,不含序列并行,**同一个序列并行组里的卡读的是同一份数据**;序列并行组本身;汇总 loss 的组;参数分片的组。每个模型可以有自己的序列并行度,各自的组从当前拓扑现取(01 章)。

**分片维与序列并行维融合。** 同一个序列并行组里的卡本来就持有同一份参数副本,VeOmni 把分片维和序列并行维压成一维交给 FSDP2:16 张卡、序列并行度 4 时,数据并行度是 4,参数却按 16 份切。序列并行的卡一起分担参数、梯度和优化器状态;它们各自只算了一段序列的梯度,这些梯度在这一维上归约时被自然加在一起。

**数据侧:在 dataloader 里切好。** 打包好的一个微批(打包本身见 07 章)在 CPU 进程里依次处理。先对整条序列把标签左移一位,跨段边界的那个标签因此不会丢。再补齐到序列并行度的整数倍:补上的 token 位置编号为 0,打包的规矩里这就是一条新样本的开头,于是补齐的尾巴自成一段,真实 token 看不见它,它的标签填成忽略值,不进 loss;视觉 patch 按 4 倍补齐,因为视觉塔会把 patch 合并成 token,切点不能落在合并块中间。然后各字段切出本卡连续等长的一段,唯独位置编号先留整条,用它算出样本边界再切,所以每张卡拿到的都是整条序列的边界,交换回整条序列后直接能用。

**注意力包装:前后各一次交换。** 开序列并行时,注意力名被改写成带序列并行的包装(改写规则见 03 章)。包装在调用注意力内核前检查头数:query 头数必须被并行度整除;KV 头数不小于并行度时要被它整除,直接平分;小于并行度时要反过来,并行度被 KV 头数整除,先把每个 KV 头复制成若干份,使每张卡恰好分到自己那组 query 头共用的那一个。按头存放的辅助量,例如 attention sink,也只截出本卡那几个头。算完之后,输出再换回按序列切;FlexAttention 还要求掩码对所有头相同,因为交换后每张卡的本地头号都从 0 重新数。MagiAttention 走同一对交换,但只能配上下文并行度 1、微批里只有一条打包序列。

**线性注意力要在模型里自己写。** Qwen3.5 的门控 delta 层不走注意力包装,它在自己的前向里交换 Q、K、V 与两个门控量,再把因果卷积的权重按本卡的头截出对应通道;输出侧的门控信号在交换回来之后才用,省掉一次交换。

**异步版本:把通信藏进投影。** 同步写法是先把 Q、K、V 三个投影都算完再交换。异步版本把三个投影拆开:Q 投影一算完就发它的交换,紧接着算 K 投影,K 算完发 K 的交换再算 V;Q、K 换回来之后,在等 V 的时候做 Q、K 的归一化,RoPE 则放到交换之后、在整条序列上做。反向按同一思路流水:一个梯度在路上时算另一个投影的梯度;输出投影的前向是同步的,反向把输入梯度的交换与权重梯度的计算叠在一起。它自带整套前向反向,归一化选哪份实现跟算子配置走同一个选择。当前只有 Qwen3-VL(稠密与 MoE)的文本注意力接了这条路。

**扩散模型版本的三处不同。** 一是 Q、K 的归一化跨整个隐藏维而不是逐头,必须在交换之前、每张卡还持有全部头时做;二是没有 GQA 的复制;三是扩散模型的注意力是双向的,补齐的尾巴会被真实 token 看见,Wan 因此另建一张全局加性掩码把尾巴屏蔽掉。Wan 的异步开关当前固定为关,MiniMax-H3 则把头分成若干块,一块交换时算上一块。扩散训练器里只有序列并行组的 0 号卡读数据,再广播给组内其他卡(09 章)。

**loss 与输出怎么汇总。** 每张卡只有一段 token 的 loss。先在序列并行组内按各卡的有效 token 数加权,合成同一个值;整组都没有有效 token 时返回 0,不返回 0 除以 0 得到的 NaN。之后的全局平均按全作业的 token 数算,不按卡数(01 章)。需要逐样本的输出(logits、logprob)时,先在组内全收集,去掉补齐的尾巴,再按样本边界拆开;后训练里 logprob 的汇总见 14 章。

**多模态的图像 token。** 视觉塔的输入同样按 patch 切给组内各卡,出来的图像特征在组内全收集,按位置填回整条序列后再切回本段(08 章)。

**DeepSeek-V4 改走上下文并行:只切 query。** 每张卡保留连续的一段 query、全部头;KV 只有一个头,直接全收集成整条;压缩器按「窗口归它第一个 token 所在的卡」分工,越过段边界的窗口从相邻卡取一小段边角,各卡压好的行再全收集,按卡号拼起来就是全局顺序。KV 在每张卡上都是完整的一份,稀疏索引、滑动窗口下标全都保持全局坐标,不用重映射,这是整个设计最省心的地方。**为什么不用 Ulysses**:KV 单头没法按头分,本来就得全收集;压缩器与索引器要沿整条序列开窗,Ulysses 下每张卡都得先收齐整条序列的隐藏状态再各自重算一遍;上下文并行下两次 all-to-all 都消失,设计文档按生产 trace 估算,每步通信量从约 465 GB 降到约 7.4 GB(估算,未在这份实现上实测)。模型代码里 Ulysses 这条路仍然保留。

**为什么实际不吃亏**:一层只多两次 all-to-all,官方文档的估算里每条链路的通信量随并行度增大而下降;归一化、MLP、投影这些占大头的计算完全不变,注意力内核也不用改;序列并行的卡并进分片维,参数显存还多摊给了这几张卡。

## 三、代价

**头数决定了能开多大。** 并行度只能取 query 头数的约数,KV 头数还要能平分或被复制成整数份。KV 头数小于并行度时,复制出来的那几份多占了交换带宽与显存,反向还要把复制头的梯度加回原来的头。

**只有注意力包装那一处在交换。** 模型走 eager 或 SDPA 时,序列照样在 dataloader 里被切开,注意力却只在自己那段里算,开序列并行只有一行警告(03 章)。线性注意力、扩散模型、DeepSeek-V4 的交换都写在各自的模型代码里,新接一个结构就得再写一遍。

**异步版本覆盖面窄。** 只有 Qwen3-VL 读这个开关,其余模型打开它不报错也不生效;它要求 FlashAttention 系的注意力实现;Qwen3-VL 开编译时,序列并行与异步都得关。

**连续切分对因果注意力不均衡。** 后面的段要看的前文更多,但 Ulysses 下每张卡算的是整条序列的几个头,这个问题不存在;上下文并行下每张卡只算自己那段 query,靠后的卡活更重,当前没有做首尾配对。

**上下文并行只是第一版。** 只放行 DeepSeek-V4、只能在 GPU 上跑、不能和 Ulysses 同时开、没有 KV cache;验证过的并行度只有 2 和 4,8 从未跑过。每张卡那段不能比最大压缩率还短,这个检查在第一次前向才做,不在启动时。索引器每张卡都要对整个全局压缩数组打分,负载不均;边角交换从所有卡全收集,而实际只读两个邻居。有几类错误是**挂住而不是报错**:某张卡在反向里不再读某个收集结果,就不进那次集合通信的反向,其余卡等到 NCCL 看门狗超时。

**MagiAttention 与上下文并行互斥。** 选 MagiAttention 时上下文并行度必须是 1,建模型前与每次前向各查一次。

**同一个序列并行组吃一份数据。** 序列并行度 4,数据并行度就除以 4,全局批的配法跟着变(01 章)。多 token 预测与序列并行也不能同开(02 章)。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09)。它的长序列方案是张量并行附带的序列并行,加上独立的上下文并行,见 Megatron 解读 03 章。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 长序列的主力 | Ulysses:注意力前后各一次 all-to-all,在序列切与头切之间换 | 上下文并行:默认按环形点对点交换 KV,也可选先全收集、按头 all-to-all 或分层组合 |
| 对模型的要求 | 注意力走带序列并行的包装,或模型自己写交换;上下文并行只放行 DeepSeek-V4 | 用 Transformer Engine 注意力的模型,把上下文并行组传进注意力即可 |
| 序列怎么分给各卡 | 连续等分,每卡一段 | 默认切成上下文并行度 2 倍的段,每卡拿一头一尾,平衡因果注意力的负载 |
| 长度除不尽时 | dataloader 自动补齐,补齐部分自成一段、不进 loss | 启动时断言序列长度是上下文并行度 2 倍的整数倍 |
| 张量并行附带的序列并行 | 不支持张量并行,也就没有这一项 | 把张量并行之外逐 token 的区域沿序列切开;张量并行度为 1 时自动关掉 |
| 梯度在哪一组上归约 | 序列并行维并进 FSDP2 的分片维 | 梯度按数据并行与上下文并行合起来的那一组归约 |

两边在梯度这一行其实殊途同归:切序列的卡都当成数据并行的一部分来归约。分歧在注意力那一行。Megatron 的层是自己写的,可以把上下文并行做进注意力内核,对所有用它的模型一视同仁。VeOmni 拿来的是别人写的 HF modeling,它能插手的只有「调用哪个注意力函数」这一处,所以选了只需在调用前后各换一次形状、内核一行不改的 Ulysses;代价是头数约束,以及遇到 DeepSeek-V4 这种单头 KV 的结构时,只能为它单独写一条上下文并行。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。每个模型各一份,放在该模型的 `accelerator` 下。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `model.accelerator.ulysses_size` · Ulysses 序列并行度 | YAML 或命令行 | 1 | 每卡激活约降为 1/度数;必须整除总卡数,且满足上面的头数约束;数据并行度按它等比缩小 | 日志 `Initializing parallel state: … cp_size …, ulysses_size …` 与 `Device mesh: …` |
| `model.accelerator.cp_size` · 上下文并行度 | YAML 或命令行 | 1 | 大于 1 只放行 DeepSeek-V4、只在 GPU 上;与 `ulysses_size` 同时大于 1 直接报错 | 同上;非 DeepSeek-V4 在建模型时报错 |
| `model.accelerator.enable_async` · 异步 Ulysses | YAML 或命令行 | 关 | 只有 Qwen3-VL(稠密与 MoE)读它;打开后 QKV 投影与交换重叠;要求 FlashAttention 系实现 | 每步耗时;profiler 里 all-to-all 是否与投影 GEMM 重叠 |
| `data.max_seq_len` × `train.micro_batch_size` · 打包长度 | YAML 或命令行 | 2048 × 1 | 这是**整个序列并行组共用**的一条打包序列的长度,每卡拿 1/序列并行度 | 日志 `Use dynamic_batching -->` 里的 `batching_token_len` 与 `sp_size` |
| `model.ops_implementation.attn_implementation` · 注意力实现 | YAML 或命令行 | `flash_attention_2` | 只有 FlashAttention、FlexAttention、MagiAttention 三族带交换;MagiAttention 要求 `cp_size: 1`;DeepSeek-V4 的交换写在模型里,样例配置用 `eager` | 03 章 |

**观测。** 本章看 3 处。一是拓扑:`Initializing parallel state: …` 那一行的 `dp_size` 应当等于总卡数除以序列并行度,紧接着的 `Device mesh: …` 能看到 `ulysses` 或 `cp` 这一维是否真的建出来了。二是数据:`Use dynamic_batching -->` 那段同时打出 `dp_size` 与 `sp_size`,`batching_token_len` 是整组共用的长度,不是每卡的。三是头数:序列并行度与头数对不上时,错误出在第一次前向的注意力包装里,不在启动时。

**典型配置。** 组合与推荐值是按语义推的起点,不是实测最优。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡训 32 个 query 头、8 个 KV 头的文本模型,每条样本 64K | `model.accelerator.ulysses_size: 8`、`data.max_seq_len: 65536`、`train.micro_batch_size: 1` | 每卡只存 8K token 的激活,KV 恰好每卡 1 个头不用复制;整机只剩 1 份数据并行,吞吐靠多机补 |
| 两机 16 卡训 Qwen3-VL 稠密,长视频,想把交换藏起来 | `model.accelerator.ulysses_size: 4`、`model.accelerator.enable_async: true`,注意力保持 `flash_attention_2` | 交换留在机内、数据并行度 4;异步版本拿一整套手写前向反向换 QKV 投影与通信重叠,不能再开编译 |
| H100 上训 DeepSeek-V4 长序列 | `model.accelerator.cp_size: 4`,`ulysses_size` 保持 1;算子沿用 03 章的 H100 配置;打包长度除以 4 后不小于模型最大的压缩率 | 每卡保留全部头、只算 1/4 的 query,拿每卡一份完整 KV 与压缩行的显存换掉两次 all-to-all;只验证过 2 与 4 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动即报 `World size should be a multiple of pp_size: …, ulysses_size: …, cp_size: …` | 总卡数能否被序列并行度整除 | 换一个能整除的度数 |
| 第一次前向报 `num_query_heads (…) must be divisible by ulysses_size (…)` | 模型配置里的 query 头数 | 改成头数的约数 |
| 报 `ulysses_size (…) must be divisible by num_key_value_heads (…)` 或 `num_key_value_heads (…) must be divisible by ulysses_size (…)` | KV 头数与序列并行度谁大 | KV 头少时取 KV 头数的倍数,KV 头多时取它的约数 |
| 启动即报 `Context parallelism cannot be combined with Ulysses yet` | 两个度数是否都大于 1 | 二选一 |
| 建模型时报 `Context parallelism is not implemented for model type …` | 模型是不是 DeepSeek-V4 | 改用 `ulysses_size` |
| 昇腾上报 `Context parallelism is GPU-only in this release` | `cp_size` | 设为 1,改用 Ulysses |
| DeepSeek-V4 第一次前向报 `… needs shards at least one compression window wide …` | 打包长度除以 `cp_size` 是否小于最大压缩率 | 减小 `cp_size` 或加长打包长度 |
| DeepSeek-V4 报 `DeepSeek V4 requires explicit position_ids under sequence parallelism` | 数据是否经过 VeOmni 的 collator | 走 collator,或自己传全局位置编号 |
| 报 `Async Ulysses attention only supports flash attention implementations.` | `attn_implementation` | 换 FlashAttention 系,或关掉 `enable_async` |
| 打开 `enable_async` 后每步耗时纹丝不动 | 模型是不是 Qwen3-VL | 其他模型不读这个开关 |
| 所有卡同时卡住,10 分钟后 NCCL 看门狗报 `ALLREDUCE` 超时 | 是否开着上下文并行、是否改过 DeepSeek-V4 的压缩或索引路径 | 查哪张卡在反向里没读到某个收集结果 |

## 六、常见误区

- **以为 `cp_size` 是对所有模型通用的另一种序列并行。** 会这么以为,是因为网格和参数校验对任何模型都接受它。实际上它只放行 DeepSeek-V4,而且这个白名单是必需的:开上下文并行会让 dataloader 照样切序列,其他模型的交换却只认 Ulysses 那个开关,于是永远不收集,每张卡只在自己那 1/度数 里做注意力,loss 曲线看上去很正常。
- **以为序列并行度只要整除卡数就行。** 头数才是更紧的约束,而且它在第一次前向才报,不在启动时。最常见的是照着 8 卡机填 8,结果模型只有 12 个头;或者 KV 头有 6 个,配 4 既不能平分也没法复制。
- **以为同一个序列并行组里的卡各吃各的数据。** 它们读的是同一个打包微批,各取一段。数据并行度是总卡数除以序列并行度,全局批要按这个数配,否则报「不是整数倍」。
- **以为 `data.max_seq_len` 是每张卡的序列长度。** 它是整个序列并行组共用的那条打包序列的预算。想让每卡 8K、开 8 路序列并行,要填 65536;照每卡填 8192,每卡实际只有 1K,显存省了、吞吐也掉了。
- **以为开了 `enable_async` 就所有模型都异步了。** 只有 Qwen3-VL 的文本注意力读它,其余模型不报错、不告警、照走同步路径。判断有没有生效只能看 profiler。
- **以为补齐的 token 对注意力无害是理所当然的。** 在语言模型里无害,是因为补齐部分的位置编号为 0,被当成一条独立样本,而且因果注意力只往前看。新接一个双向注意力的扩散模型时照抄这套补齐,真实 token 会看见补齐的尾巴;Wan 专门为此建了一张全局掩码。
- **以为 FSDP2 的分片份数等于数据并行度。** 序列并行维并进了分片维,16 卡、序列并行度 4 时参数按 16 份切,而数据并行度是 4。按数据并行度去估每卡参数显存会高估 4 倍;专家并行度要整除的也是这个融合后的维度(05 章)。
