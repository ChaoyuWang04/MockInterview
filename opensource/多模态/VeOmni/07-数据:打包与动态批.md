# 数据:打包与动态批

这一页回答一件事:长短不一的样本怎样不补 padding、又让每个 rank 每步吃到差不多的 token 数,中断以后怎样从原来读到的地方接着读。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**补齐成矩形,算力花在假 token 上。** 一个微批里的样本要拼成一个张量,最省事的办法是补到这一批里最长那条。对话数据里一条几句话的问答和一条长长的多轮对话会被放进同一批,短的那条后面全是 padding,注意力和 MLP 照样对它们算一遍,显存也照样占着。

**去掉 padding 以后,按条数凑批会让 rank 之间不齐。** 每个数据并行 rank 读自己那一份数据,每步各取固定条数。条数一样,token 数却可以差好几倍:分到长样本的 rank 要算很久,分到短样本的 rank 早早算完,然后在梯度同步那一步干等。这一步的耗时由最慢的那个 rank 决定。对话 SFT 还有一层:两个 rank 物理 token 数一样,真正算 loss 的助手回复 token 却可以差很多,提示很长的那一侧白算了大半。

**续训时数据游标对不上。** 每个 rank 读的是**自己那一份**分片,读到哪了只有它自己知道;凑批用的缓冲区里还压着已经读进来、没用掉的样本。只存一份全局游标,续训时所有 rank 都从 rank 0 的位置接着读,这一片被重放,其余分片被跳过;缓冲区不存,里面压着的样本就凭空消失。两种错都不报错,只让 loss 曲线在续训点附近悄悄变形。

**对话变成训练样本这一步,标签错了也不报错。** SFT 只该在助手回复上算 loss;模板一旦把用户提问也标成了要学的内容,或者把对话从开头截掉了一段,训练照常收敛,只是学的东西不对。

## 二、解法

最天然的直觉是**按 token 数装箱,不按条数装**:样本去掉 padding 首尾相接,每个微批装到一个固定的 token 预算为止,于是各 rank 每个微批的长度都贴着同一个预算。装箱由每个 rank 在本地做,不跨 rank 商量;游标因此天然是 rank 私有的,就按 rank 各存一份。

![同一串变长样本分给两个数据并行 rank:左边按每个微批 2 条补齐成矩形,rank 0 要算 18 格、其中 6 格是 padding,rank 1 只算 8 格然后等 10 格;右边去掉 padding、按预算 12 从缓冲区里按顺序挑样本首尾相接,位置编号每条从 0 重新数,rank 0 挑了 2 条、rank 1 跳过放不下的一条后挑了 4 条,两边都正好 12 格,不用互相等](/opensource/VeOmni/07a-packing-vs-padding.svg)

**样本先经数据变换与对话模板。** 数据集读出一条原始记录,交给按数据类型登记的数据变换。纯文本整篇分词、末尾补一个结束符,再按最大序列长度切成若干段,每段各是一条样本,全部 token 都算 loss。对话数据交给**对话模板**:它逐条消息渲染成 token,再按每条消息的角色决定这段 token 要不要算 loss,不算的标成忽略。仓库登记了一组模板:有照固定格式手拼的(ChatML、Llama2 与一个朴素格式),也有直接调用分词器自带模板的;后者每加一条消息就把前缀重新渲染一遍,新多出来的那段 token 归这条消息,前面已渲染的部分一旦被改写就直接报错,因为那样就无法确定哪段 token 属于哪条消息。模板默认只在助手消息上算 loss,单条消息也可以自带一个标记改写它;超过最大序列长度时**保留尾部**,截掉的是对话开头。多模态模板归 08 章。

**五种数据集,各自按数据并行 rank 切分。** 映射式数据集整份读进来,由分布式采样器按 rank 分下标;流式数据集边读边打乱(打乱缓冲 10000 条),再按行号对数据并行度取模分给 rank,rank 内按同样的办法分给各个 worker,凑不满一整轮的尾巴丢掉;交错式在多个源之上按固定比例混合,流式的混合后再切、映射式的交给采样器切;Energon 数据集把 rank 号和 rank 总数交给 Megatron-Energon 自己的 worker 配置;加权多源数据集下一段再说。同一个序列并行组里的几张卡数据并行 rank 相同,读的是同一份数据。

**打包在 collator 里做。** 凑进同一个微批的几条样本沿序列维首尾相接成一行,批维只剩 1。每条样本的位置编号从 0 起,拼接后保留原样,于是「位置编号为 0 的地方」就是样本边界;collator 在 CPU 上从位置编号算出边界的累积长度,和最长段的长度一起塞进批里,交给变长注意力,模型里每一层都直接用,不再从 GPU 张量反推(变长注意力怎么用这组边界见知识库「FlashAttention」)。注意力掩码全是 1,边界只靠这组累积长度表达。还有一处容易漏:标签在 collator 里是不移位的,loss 计算时才错开一位,所以一条样本的最后一个 token 会去预测下一条样本的第一个 token;collator 把除第一条外每条样本的首个标签改成忽略,切断这条跨样本的预测。开了序列并行,collator 在这之后再按 rank 切序列并补到能整除,见 06 章。

**动态批:一个缓冲区,按顺序装箱。** 每个 rank 手里有一个样本缓冲区,读进来的样本先进缓冲区。缓冲区里至少有 200 条、token 总数也够一个预算时,才凑一个微批:从头往后扫,这条放得进剩下的预算就放,放不进就跳过留给下一次,凑满预算就停。预算是「微批大小 × 最大序列长度」。每一步凑几个微批是固定的,等于梯度累积步数(算法见 01 章);每个微批装几条样本不固定,短样本多的时候一个微批可以装很多条。上图右边就是这个过程:rank 1 跳过了放不进剩余预算的 H,接着用 F、G 填满。

**计数口径可以换成有效 token。** 默认数的是物理 token,也就是掩码里的 1。换成有效 token 以后,只数标签不是忽略的那些,也就是真正算 loss 的 token;为了防止一个微批塞进太多「提示很长、回答很短」的样本把显存撑爆,同时加一道物理 token 上限,默认是预算的 1.5 倍。有效 token 是在样本进缓冲区时数的,打包时再被改成忽略的边界标签不会回头扣掉。

**批大小预热是给预算爬坡。** 打开以后,前若干步每个微批的预算从 200 token 线性涨到完整预算;爬坡少吃的那部分 token,总步数的算法里已经按比例补回去了(见 01 章)。

**凑批可以放在两个地方跑。** 默认放在**主进程**:dataloader 的 worker 只负责读记录、跑数据变换,一次交一条上来;主进程里的动态批加载器(DynamicBatchSizeDataLoader)维护缓冲区、凑批,并在主进程里调 collator 打包。另一种放进**每个 worker**:每个 worker 把自己读到的样本放进自己的缓冲区,凑好、打包好,一次交出一整步的几个微批,缓冲区的状态随 StatefulDataLoader 按 worker 存取。映射式数据集进 worker 模式时,原来的采样器会被一层包装替代,按同样的规则在 rank 之间和 worker 之间分下标。

**多源加权混合。** 训练数据路径指向一份 YAML 时就进入多源模式,YAML 列出各个源、名字和权重。默认走交错式;另一种加权多源数据集每取一条先按权重随机选一个源,随机数按「种子、轮次、数据并行 rank、worker 号」派生,所以每个 rank 抽到的源序列各不相同,比例只在期望上成立。它的权重可以按条数算,也可以按 token 算:按 token 时,用各源到目前为止的平均长度去除权重,长样本多的源被抽得少一些,落到 token 上的比例才是你写的比例。某个源先读完时,可以整体停下、重开这个源直到所有源都读完一遍、或者永远重开。每条样本都被打上来源编号,按数据源拆 loss 本该用的就是它;但在默认的回调顺序下,这个编号在拆 loss 之前就被吞吐计量器从批里取走了,见 15 章。

**游标按 rank 各存一份。** 存 checkpoint 时,每个 rank 把自己的 dataloader 状态写进一个以 rank 号命名的文件,步数、随机状态和计量器写进另一个;续训时各 rank 只读自己的那两个,所有 rank 都读到了状态文件才恢复,有任何一个 rank 缺状态文件,全体都只恢复权重、数据从头读。游标之所以不能只存一份,是因为它的内容本来就按 rank 不同:流式数据按 rank 取模切分,多源采样按样本序号对数据并行度取模,Energon 的 worker 配置里带着 rank 号。游标和权重分开存,是为了能单独丢掉游标,把旧权重接到新数据上续训。

**后台预取是可选的一层。** 打开后,一个后台线程提前从 dataloader 取下一步的数据放进长度为 1 的队列,每取一次就把 dataloader 当时的状态一起存下;训练循环真正拿走哪一批,就把哪一批对应的状态当作当前游标,所以提前读出来的那一步不会被当成已经训练过。

**为什么实际不吃亏**:装箱全在 CPU 上做,各 rank 之间不需要任何通信,GPU 看到的只是一个长度贴着预算的张量;200 条的缓冲区让装箱有得挑,放不进的样本不必硬塞,也不会被丢掉,只是晚一点再用。

## 三、代价

**rank 之间只是接近,不是相等。** 每个 rank 只在自己的缓冲区里挑,除了单条就超长的样本,微批长度不会超过预算,但可能差一截;预算越小、样本越长,差得越多。开了有效 token 口径,物理长度最多可以到预算的 1.5 倍,显存峰值随之浮动。

**缓冲区会重排样本顺序,也拖慢起步。** 放不进的长样本被留在缓冲区里,短样本先被拿去填缝,训练看到的顺序和数据集的顺序不一样。第一个微批要等缓冲区攒够 200 条才出得来,数据变换慢的时候(长文档分词、多模态解码),启动后第一步明显迟到。

**主进程模式把打包压在训练循环上。** 默认的运行位置里,凑批和 collator 都在主进程里和训练循环同步交替执行,取下一步数据的这段时间 GPU 在等;开了序列并行、多模态元数据预计算以后这份活更重。要么换到 worker 里凑批,要么开后台预取,把它挪到另一个线程。

**两种运行位置的行为不一样,不只是快慢。** 批大小预热只在主进程模式里生效,worker 模式的凑批器根本不看这个配置。单条样本超过预算时,主进程模式照样把它单独作为一个微批放出去,worker 模式则打一行警告直接丢掉。数据读完时,主进程模式会从头再读一遍,直到凑够算出来的步数;worker 模式读完就结束这一轮。

**游标绑定了卡数和 worker 数。** 游标文件按全局 rank 号命名,记录着卡数却不校验。换成更多的卡续训,多出来的 rank 找不到自己的文件,全体退回只恢复权重,数据从头读;worker 模式下的映射式数据集会核对 rank 总数、种子、数据集大小与是否打乱,对不上直接报错,并且要求 worker 数与保存时一致。缓冲区里没用完的样本是整条存进游标的,缓冲区大、样本大时游标文件随之变大;代码里支持只存下标、续训时再按下标取回,但配置里没有打开它的入口。

**多源的「随时间变化的权重」写了也不生效。** YAML 允许写一种随训练进度变化的权重计划,解析时也会校验;交错式只认第一段计划里的固定权重,其余各段打一行提示后忽略,加权多源数据集遇到非固定的计划直接报错。

**打包依赖模型认得边界。** 边界只存在于位置编号和那组累积长度里,注意力掩码是全 1。走变长注意力的实现都没问题;门控 delta 规则这类算子的 eager 实现不认打包边界,见 03 章。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09)。

两边都要把变长数据变成等长的计算量,Megatron 把这件事尽量前移到离线与全局,VeOmni 留在训练时的每个 rank 本地做。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 样本从哪来 | 训练时在 dataloader 里在线分词、套对话模板,每条样本长度各异 | 预训练读离线分好词的索引数据集,按固定序列长度跨文档切样本,样本天生等长,不需要 padding;见 Megatron 解读 16 章 |
| SFT 怎么打包 | 缓冲区在训练时挑样本拼成一个微批,边界靠位置编号归零 | SFT 数据集把数据文件里同一行预先放在一起的几段对话拼成一条,每段补到并行度能整除,整条再补齐或截断到固定序列长度 |
| rank 之间怎么拉齐 | 每个 rank 只看自己的缓冲区,按 token 预算装箱,不通信;每步微批数固定 | 可选的打包调度器先在数据并行组里收集整个全局批每条样本的长度,按原顺序装到长度上限,再用 all-to-all 把样本送到该去的 rank;每步的微批数随之变化 |
| 续训游标 | 每个 rank 存自己的 dataloader 状态,连同缓冲区里没用完的样本 | 只存一个全局的已消费样本数,各 rank 的采样器从这个编号起按自己的 rank 取下标 |
| 批大小爬坡 | 每个微批的 token 预算从一个小值线性涨到完整预算 | 按样本数或 token 数设阈值,分段加大全局批;旧的线性爬坡已标为弃用 |

Megatron 的做法让「数据读到哪」退化成一个所有 rank 共用的整数,换卡数续训只要重算各 rank 的下标;代价是数据得离线预处理,SFT 的混拼也要在数据准备阶段做好。VeOmni 的数据是在线处理的多模态原始记录,长度只有读出来才知道,所以只能在训练时本地装箱,游标也就只能按 rank 存。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `train.dyn_bsz` · 按 token 预算凑批 | YAML 或命令行 | 开 | 关:每个微批固定 `train.micro_batch_size` 条,仍然打包、不补 padding;总步数改按样本数算 | 启动日志是 `Use dynamic_batching -->` 还是 `Use fixed_sample_batching -->` |

| `data.dyn_bsz_buffer_size` · 缓冲区至少攒几条才开始凑 | YAML 或命令行 | 200 | 调大:装箱更紧、起步更慢、CPU 内存更多、顺序被打乱得更厉害;调小相反 | 第一步出现的时间;每步 token 数的波动 |

| `data.dataloader.in_order` | YAML 或命令行 | 开 | 关:慢 worker 不再堵住后面的批,但续训顺序不再精确 | 启动警告 `data.dataloader.in_order=False can improve throughput …` |
| `data.dataloader.use_background_prefetcher` · 后台预取 | YAML 或命令行 | 关 | 开:取数据与打包挪到后台线程,和上一步的计算重叠 | 每步耗时 |

**观测。** 本章看 4 处。一是启动时的凑批配置:`Use dynamic_batching -->` 那一段打出预算、数据并行度、序列并行度、微批数与预热步数,`Main Collate Configuration` 表列出每个字段的拼接维与填充值,先对一遍再往下跑。二是样本被跳过或单独放出:主进程模式下只有 1 个 token 的样本会被打印 `WARNING: EMPTY STRING.` 后丢弃,worker 模式下超预算样本打 `Sample length … skipping.`。三是续训:成功时 rank 0 打 `Restored trainer state from … (global_step=…, start_epoch=…, start_step=…)`;某个 rank 缺游标文件打 `No dataloader cursor at …; the dataloader restarts from its beginning.`,任一 rank 缺状态文件则打 `Trainer state missing on at least one rank; resuming weights only.`。四是落盘结构:每个 step 目录下 `loader/rank_{R}.pt` 是游标,`extra_state/rank_{R}.pt` 是步数、随机状态与计量器,rank 0 最后写 `checkpoint_manifest.json` 表示全部 rank 的这两样都已落盘;目录的其余部分归 13 章。

**典型配置。**

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 大规模纯文本预训练,数据放不进内存 | `data.data_type: plaintext`、`data.datasets_type: iterable`、`train.micro_batch_size: 4`、`data.max_seq_len: 4096`,`data.train_size` 填真实 token 总量 | 每个微批 16384 token 的预算换 rank 间的齐整与更少的微批调度开销;流式读换掉了按长度自动算步数,步数全靠你报的 token 总量 |
| 提示很长、回答很短的对话 SFT | `model.chat_template: chatml`、`train.dyn_bsz_count_mode: effective`、`train.dyn_bsz_physical_overflow_ratio: 1.2`、`data.dataloader.use_background_prefetcher: true` | 用最多 1.2 倍预算的物理长度浮动换各 rank 算 loss 的 token 更齐;后台线程换掉主进程上的打包等待 |
| 多源混训,要能精确续训 | `data.train_path` 指向多源 YAML,YAML 里写 `level: token`、`stopping_strategy: all_exhausted`;`data.multisource_datasets_type: veomni_weighted_multisource`、`train.dyn_bsz_runtime: worker` | 按 token 计的混合比例与按 worker 存取的缓冲区,换来续训时卡数、worker 数都不能变,批大小预热也用不了 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动后很久才出第一步 | 数据变换有多慢;`data.dyn_bsz_buffer_size` 是否过大 | 加 `data.dataloader.num_workers`,或调小缓冲区 |
| GPU 利用率低、主进程 CPU 满 | 是否是默认的主进程凑批,且开了序列并行或多模态 | 换 `train.dyn_bsz_runtime: worker`,或开后台预取 |
| 偶发 OOM 总落在某几步 | 是否开了 `effective` 口径;有没有超长单条样本被主进程模式单独放出 | 调小物理上限倍数,或在数据变换里截断到最大序列长度 |
| 开 `train.pad_to_length` 后报 `pad_to_length must be >= packed sequence length.` | 是否有单条样本比预算还长 | 截断这类样本,或加大微批 × 最大序列长度 |
| 续训后 loss 曲线在续训点跳一下 | 日志是否出现 `resuming weights only` 或 `restarts from its beginning`;续训的卡数是否和保存时一样 | 用原卡数续训;确认每个 rank 的 `loader/` 与 `extra_state/` 文件都在 |
| worker 模式续训报 `Cannot restore _MapStyleSamplerWrapper with a different sampler setup` | 报错里列出的是 rank 总数、种子、数据集大小还是打乱开关 | 恢复成保存时的那一项;确实要换,就删掉 `loader/` 只接权重 |
| 对话数据启动即报 `KeyError: 'loss_mask'` | 用的是不是 `default` 或 `llama2` 模板 | 给每条消息加 `loss_mask`,或换成 `chatml` / `tokenizer` |
| 用 `tokenizer` 模板报 `structurally rewrote an earlier conversation prefix` | 分词器自带模板是否会在追加消息时改写前面的轮次 | 换成照固定格式拼的模板 |
| 多源训练中途数据从头再来(主进程模式),或这一轮提前结束(worker 模式) | 日志里某个源是否已读完;停止策略是不是默认的 `first_exhausted` | 改成 `all_exhausted` 或 `never_exhausted`,或打开 `data.dataset_repeat` |

## 六、常见误区

- **以为关掉 `train.dyn_bsz` 就回到了补 padding。** 会这么以为,是因为「动态批」和「去 padding」在很多框架里是一个开关。实际上打包在 collator 里,两种模式都走;关掉的只是按 token 预算凑批,每个微批改成固定条数,rank 之间照样会因为长短不齐而互相等。
- **以为开了序列并行,预算就是每张卡的 token 数。** 会这么以为,是因为预算的名字叫「微批大小 × 最大序列长度」,听上去是每卡的量。实际上它是整个序列并行组共用的一条序列的长度,切到每张卡上是它除以序列并行度;想让每卡吃满,要把最大序列长度按序列并行度放大。
- **以为两种运行位置只是快慢不同。** 会这么以为,是因为文档只说 worker 模式为了精确续训。实际上批大小预热只在主进程模式里生效,超预算的单条样本在主进程模式里被单独放出、在 worker 模式里被丢掉,数据读完时主进程模式会从头再读、worker 模式直接结束这一轮。从一种切到另一种,训练看到的数据就变了。
- **以为 `train.bsz_warmup_ratio` 是学习率预热。** 它是每个微批 token 预算的爬坡,从 `train.bsz_warmup_init_mbtoken` 线性涨上去;打开以后总步数也会跟着多算一截。在 worker 模式下它什么都不做,也不报错。
- **以为续训可以随手换卡数。** 游标按全局 rank 号一个文件一个文件地存,记录了卡数却不校验。卡数变多,新 rank 找不到文件,全体静默退回只恢复权重、数据从头读;卡数变少,读到的是按旧切分记下的位置。最常被略过的就是那行 `resuming weights only`。
- **以为 `effective` 口径下每个微批的显存和原来一样。** 预算数的是算 loss 的 token,物理长度要到 1.5 倍上限才被拦住;提示很长的数据上,打开它等于把每个微批的物理长度放大了一截。
- **以为对话超长时截掉的是结尾。** 模板保留的是最后那段 token,被截掉的是开头:系统提示和前几轮先没。系统提示很重要的数据,要在进训练之前自己控制长度。
- **以为不管用哪个模板,都只在助手回复上算 loss。** `chatml` 与 `tokenizer` 默认如此;`default` 与 `llama2` 完全按每条消息自带的标记决定,没有这个字段直接报错。助手消息算 loss 的范围也不只是回复正文:`chatml` 把角色头与结束标记一起算进去。
- **以为仓库里的合成数据集能在配置里选来冒烟测试。** 那组按模型造随机样本的数据集只给测试用(接入新模型的文档也让你往里加一个给测试),没有登记进数据集注册表,配置里选不到;想先不接真数据跑通流程,要自己准备一个小数据文件。
