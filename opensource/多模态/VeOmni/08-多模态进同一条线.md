# 多模态进同一条线

这一页回答一件事:图片、视频、音频这类每条样本数量不同、尺寸不同的输入,怎样在数据侧就被加工成模型能直接吃的形状,让视觉塔、音频塔和语言模型跑在同一条训练线上而不互相拖累。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

**形状由内容决定,内容读出来才知道。** 一张图变成多少个视觉 token,取决于它缩放后的高和宽;一段视频取决于抽了几帧、每帧多大。语言模型这边要为每张图留出同样多的占位 token,还要按每张图的时间、高、宽三个网格尺寸排出三维旋转位置(M-RoPE,原理见知识库「任意分辨率与高分辨率」);视觉塔自己用变长注意力,一批里所有图的 patch 首尾相接,它得知道每一帧从哪开始、最长的一帧多长。这些都是**元数据**:几个整数、几张小表,算起来不费事。

**麻烦在算它的地方。** HF 原版的 Qwen-VL 系模型把这些推导写在前向里。网格尺寸是 GPU 上的张量,要变成主机上的整数,CPU 就得停下来等 GPU 把排在前面的活全部做完;视觉塔每一层还要对帧边界求一次最大值,层数越多,等得越多。每等一次,CPU 就停止往 GPU 发射后面的算子,GPU 随即空转。这种等待不报错、不进日志,只让每步变慢、让 profiler 上出现一截一截的空隙。

**不设上限,一条样本就能撑爆序列。** 一张 4K 截图、一段一分钟的视频,按原分辨率切 patch,单条样本的视觉 token 就能超过整个训练长度。多模态样本又不像纯文本那样可以随手从开头截掉一段:占位 token 的个数必须和视觉塔吐出的特征个数一一对应。

**rank 之间也不齐,而且会挂住。** 数据并行下每个 rank 读自己的样本,这一步有的 rank 分到三张图加一段视频,有的一张图也没有。视觉塔的算量随之悬殊;更糟的是,没有图的 rank 根本不经过视觉塔,那些参数在反向里没有梯度,FSDP 在视觉塔那几层的集合通信上等不齐,整个作业挂住。Omni 模型还多一层:负责说话的 talker 在理解类 SFT 里用不到,照样建出来交给 FSDP,就会在各 rank 模态不对称的那一步上失步。

**已经训好的塔经不起主干的学习率。** 视觉塔、音频塔都是预训练过的,全量微调时和语言模型一起更新;用同一个学习率,大步长会把视觉特征打散(冻结与分层学习率的道理见知识库「多模态训练」)。

## 二、解法

最天然的直觉:**元数据由样本决定,那就趁样本还在 CPU 上把它算完。** 一条样本自己就能定下来的(占位个数、三维位置、模态掩码),在数据变换里逐条算;要等拼成一批、补齐之后才定下来的(视觉塔的帧边界),在 collator 里整批算。算好的整数和小张量随批一次非阻塞拷贝上 GPU,前向里只读现成的数。

![一条多模态样本在 CPU 与 GPU 之间的分工:左列 CPU 上依次是按数据源名取的预处理函数、读取与缩放、处理器、多模态对话模板、模型借出的位置编号函数、collator 打包补齐、模型借出的元数据函数,其中对话模板、位置编号函数和元数据函数三步产出元数据;它们的结果随批一次拷贝进右列 GPU 上的视觉塔、特征填回与语言模型。右列两个红色虚线框标出原版在前向里从 GPU 张量现推三维位置和视觉塔帧边界的位置,每推一次都要等 GPU,现在只在没走 collator 时兜底](/opensource/VeOmni/08a-mm-metadata-on-cpu.svg)

**① 按数据源名取预处理函数。** 各数据集的原始格式各不相同:ShareGPT4V 是 human 与 gpt 轮流说话,LLaVA-Video 是视频问答,有的图文对只有一段字幕。仓库为每个数据源登记一个预处理函数,把记录统一成「角色 + 若干(模态, 内容)」的列表,这里只留占位,不读像素。用哪个函数看数据源名:单源训练取配置里写的名字,多源训练取多源 YAML 里每个源的名字(07 章),两者都没有时取样本自带的来源字段。多模态这边登记了 29 个名字(扩散模型另有 4 个,归 09 章);名字对不上,第一条样本就报「没有登记这个预处理器」。

**② 读取与缩放,像素预算在这里定。** 图像等比缩放进像素上下限,高宽再对齐到视觉塔一个合并块的边长(Qwen-VL 是 28 像素),长宽比超过上限直接报错。视频先按目标帧率算帧数,夹在最少与最多帧数之间,再对齐到时间方向的合并因子,在全片上均匀取帧,不够就重复最后一帧。每帧的像素上限还可以随帧数收紧:给整段视频一个总像素预算,帧越多每帧越小,视觉 token 总数因此可以预期。路径或字节形式的视频容器只解码被选中的帧,同时抽出音轨、重采样到 16 kHz。抽出来的视频还带着每一帧在原片里的帧号,下一步要用。

**③ 处理器出像素块和网格,④ 模板按网格展开占位。** 处理器(分词器加图像、视频处理器)从模型 checkpoint 目录自动加载:加载出完整处理器,就说明这个模型看得见文本以外的东西;只有分词器,就当纯文本模型。数据流水线读的和导出时写出去的是同一个处理器对象。它把像素切成 patch,给出每张图、每段视频的「时间 × 高 × 宽」网格,网格乘积除以合并块面积就是这张图的视觉 token 数。VeOmni 已经抽过帧,调用视频处理器时关掉它自己的抽帧,否则帧号会被覆盖。多模态对话模板拿着这组个数,把每个图像占位展开成「视觉开始 + 那么多个图像 pad + 视觉结束」,只在助手回复上算 loss,角色头不算;Qwen3-VL 的模板还把视频按时间块拆开,每块前面写上这一块在原片里的秒数,秒数由帧号除以原片帧率得到。Omni 模型不走这套模板,而是调用处理器自带的对话模板,固定插一条 Qwen 的系统提示,再按 assistant 这个词元的位置划出要学的区间。文本部分的模板在 07 章。

**⑤ ⑦ 模型把两个函数借给数据侧。** 推导公式因模型而异:Qwen2.5-VL 的视觉塔用窗口注意力,还要一张窗口重排表;collator 不知道这些。所以推导挂在模型身上,以两个能跨进程传递的函数交出来,随补丁配置一起生成进 modeling(机制见 02 章):

- **位置编号函数**:包住 HF 的三维位置算法,配一份把图像、视频 token 号换成 VeOmni 占位值的假配置,在数据变换里逐条样本算出三维位置;HF 顺带返回、只有生成解码才用的位置偏移直接丢掉。同一步把图像、视频掩码也算好,前向不用再比对 token 去找占位。
- **元数据函数**:collator 打包之后(开序列并行时是补齐之后)调用一次,把整批的网格转成主机上的列表,按「每帧 h × w 个 patch」展开成视觉塔的帧边界与最长段。序列并行补上的那段像素(06 章)被记成一张额外的假图,变长注意力把它当成独立的一段,真实图像看不到它。

训练器只看模型有没有这两个函数,collator 本身不含任何模型专属逻辑。当前能接进视觉语言训练器的 9 个 Qwen 系模型族都借出了这两个函数;Omni 还多交一张表,说明音频特征、音频长度与音频掩码怎么拼、要不要按序列并行切。没走 collator 的输入(第三方流水线、手拼的推理输入),前向里保留着原版推导作兜底,照付等待的代价。仓库有一个回归测试,在 CUDA 的同步调试模式下跑这些模型的前向,出现隐式同步就失败,并逐位比对预计算与兜底两条路的输出。

**没有图的 rank 也跑一遍视觉塔。** 这一步没有图像或视频的 rank,按视觉塔自己的配置造一张全零假图跑一次视觉塔,输出取均值乘 0 加到文本 embedding 上,deepstack 那几路特征也照样穿过语言模型。梯度全是 0,但每个 rank 都经过了同一组视觉参数,集合通信对得齐。假图的元数据在前向里直接用整数拼出来,同样不用等。Omni 的音频塔照此处理。

**塔的学习率与冻结。** 视觉语言训练器把可训参数按名字分两组:名字里带 visual 的用单独的视觉学习率,**默认就是 1e-6**,其余用主干学习率;学习率调度对两组同比例缩放,曲线形状一致。要完全不动视觉塔,可以冻结它:Omni 冻结时保留视觉 merger 可训,其他模型连 merger 一起冻;Omni 还能单独冻音频塔,保留它的输出投影可训。开了 LoRA 时这两个冻结开关被忽略,可训范围由 LoRA 决定(11 章)。

**Omni 只训 thinker。** 补丁后的 Qwen3-Omni 在构造时就不建 talker 与声码器,相应的类从生成文件里剔掉,载权重时丢掉以它们开头的键,前向只转发给 thinker;训练器建完模型后再调一次关 talker 的方法,把可能残留的部分删掉。补丁配置里写明了理由:这些参数在 SFT 里没有任何损失用得到,建出来只会被 FSDP 包装却永不前向,在模态不对称的那一步上让各 rank 失步挂住。

**离线音视频是同一条线的另一个入口。** Qwen3-Omni 另有一个预处理函数,接收已在别的流水线里解码好的样本:每段视频是一组帧图片的字节加一段 WAV,作为一个音画对齐的整体交给处理器,由它交错排布视频与音频 token。它走的是同一套缩放、抽帧、模板与钩子,只是省掉了训练时的容器解码,训练机也不再需要 ffmpeg。

**为什么实际不吃亏**:这些推导在 CPU 上就是几次整数循环,挪过去以后 GPU 前向里少了等待点;拷贝随批一次完成,整数和列表根本不上 GPU。像素预算放在数据侧,一条样本在进动态批缓冲区之前长度就已确定,按 token 装箱(07 章)拿到的是真实长度。

## 三、代价

**编码器负载不均,当前没有解。** 仓库里有一个编码器数据均衡器:把数据并行组里每张图的 patch 数全收集起来,按「patch 数的平方」贪心地分给当前负载最小的 rank,用 all-to-all 把像素送过去,算完再把特征送回原 rank。配套开关只放行 Qwen3-VL MoE,开序列并行时被重置为关。但在这组基准上,**没有任何模型代码读这个开关**:它只被写进模型配置,视觉塔的前向与假图路径都不调用均衡器,均衡器只在单元测试里被用到;接入新模型的文档里那段调用示例,在当前生成的 modeling 里找不到对应代码。rank 之间的视觉塔负载仍由各自分到的样本决定。

**钩子只管视觉塔的帧边界。** Omni 音频塔的长度信息不在元数据函数里,仍由前向按特征长度推。开序列并行时,deepstack 特征按 rank 切片前要数出本 rank 之前有多少个图像 token,这里仍有两次等待;昇腾上视觉塔会把拷贝上去的帧边界再取回主机。

**活全压在 CPU 上。** 解码、缩放、重采样、切 patch 都在 dataloader 里,长视频的一次数据变换可能比一步训练还慢;默认的动态批还在主进程里凑批、调 collator(07 章),元数据函数也跟着在主进程跑。离线帧列表这条路会先把一段视频的全部帧解码并缩放,再从中抽帧,抽得越狠浪费越多。

**多模态模板不截断。** 文本模板超长时保留尾部(07 章);多模态模板启动时就声明不截断,Omni 那条路也不截断。一条样本多长,完全由像素预算、帧数上限和文本长度决定;超出动态批预算的样本在主进程凑批时单独成一个微批,在 worker 凑批时被丢掉。

**像素缩了两道。** 数据侧按自己的预算缩一次,处理器按自己的配置还会再对齐、再夹一次。只改一边,实际分辨率可能纹丝不动。

**分组只认名字里的一个子串。** 视觉学习率只认 visual:音频塔跟着主干走;名字里不带它的视觉模块也会被当成主干。冻结视觉塔时,Omni 与其他模型对 merger 的处理不一样。优化器选 Muon 时,这套分组被整个忽略,只打一行警告(12 章)。没开专家并行这类额外并行时,传进去的两组参数不再按「哪些模块不做权重衰减」细分,那份不衰减的名单跟着失效。

**导出的 Omni 权重只有 thinker。** talker 与声码器从没被建出来,训完导出的 checkpoint 里没有它们;补丁版的开 talker 方法会直接报错,让你去用上游原版实现做语音生成。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09)。

它的多模态在 LLaVA 模型与 MIMO 两处实现,语言模型之外的组合层见 Megatron 解读 14 章。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 图像占位在哪展开 | 数据侧:模板按处理器算出的个数一次写满占位 token,样本进 dataloader 缓冲区时长度已定 | 模型前向里:每张图在 token 序列里只占 1 个位置,前向按图块数乘每块 token 数展开,同时重排位置、标签与损失掩码,拆分时要把每条样本的图像数取回主机 |
| 视觉塔的变长边界 | collator 在 CPU 上算好,随批拷贝 | 动态分辨率时在前向里由图像尺寸现算,取最长段要把值取回主机 |
| 没有图的 rank | 整座视觉塔对一张全零假图跑一遍,输出乘 0 | 只让视觉投影层过一个全零向量,保证投影层留在计算图里 |
| 冻结 | 冻视觉塔、冻音频塔两个开关,Omni 保留 merger 与音频投影可训;视觉塔默认另用一个更小的学习率 | 语言模型、视觉模型、视觉投影、声音模型、声音投影各有一个冻结开关,冻语言模型时可以单独放开路由器 |
| 编码器与语言模型放在哪 | 同一批卡,每个 rank 给自己的样本跑编码器 | MIMO 允许编码器与语言模型各占一组互不重叠的卡 |

分歧的根源是模型由谁来写。Megatron 的多模态模型是自己写的,展开占位、对齐标签都放在自己的前向里做,把编码器挪到另一批卡上也只是它自己的事。VeOmni 拿来的是 HF 的 Qwen 系 modeling,前向里能动的地方有限,于是把能提前算的都挪到数据侧,让补丁后的前向只剩读现成的数;代价是这条线离开 Qwen 系就得为新模型重写一遍数据变换与钩子。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。`data.mm_configs` 是一个自由字典,里面的键原样传给预处理函数和读取缩放的各个函数。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `data.source_name` · 单源训练用哪个预处理函数 | YAML 或命令行 | 不设 | 必须等于 `preprocess.py` 里某个登记名;多源训练改由多源 YAML 的 `names` 决定,样本自带的 `source` / `source_name` 字段是后备 | 名字不对报 `Unknown preprocessor name: … No preprocessor registered for this source.` |
| `data.mm_configs.image_max_pixels` / `image_min_pixels` · 每张图的像素上下限 | YAML | 不设,不限 | 调小:每张图 token 少、序列短、细节少;样例配置取 602112(768 个 28 × 28 块) | 首个微批日志里 `image_grid_thw` 的值 |
| `data.mm_configs.scale_factor` · 高宽对齐到它的倍数 | YAML | 不设,不对齐 | 设成合并块边长(Qwen-VL 为 28),处理器就不用再取整 | 同上 |
| `data.mm_configs.max_ratio` · 长宽比上限 | YAML | 不设 | 超出直接报错,不是跳过 | `absolute aspect ratio must be smaller than …` |
| `data.mm_configs.fps` / `min_frames` / `max_frames` · 抽帧 | YAML | 2.0 / 不设 / 不设 | 帧数 = 时长 × 目标帧率,再夹进上下限;不够的重复最后一帧 | 首个微批日志里 `video_grid_thw` 的第一维 |
| `data.mm_configs.frame_factor` / `frame_factor_remainder` · 帧数对齐 | YAML | 不设 / 0 | 帧数对齐到「因子 × k + 余数」;Qwen 系时间合并因子为 2 | 报 `Cannot lay out … video tokens over … time chunks` 时先查它 |
| `data.mm_configs.video_max_pixels` / `video_min_pixels` · 每帧像素上下限 | YAML | 不设 | 同图像,按帧算 | 同上 |
| `data.mm_configs.video_total_pixels` · 整段视频的总像素预算 | YAML | 不设,关 | 每帧上限改为「总预算 ÷ 帧数 × 时间合并因子」与每帧上限取小,且不低于每帧下限的 1.05 倍;样例取「最大序列长度 × 784 × 0.9」 | 长视频与短视频的 `video_grid_thw` 高宽是否拉开 |
| `data.mm_configs.use_audio_in_video` · 是否抽视频音轨 | YAML | **开**(代码默认;使用文档写的是关) | 路径与字节视频会被抽音轨、重采样;Qwen-VL 那条路抽完不用 | 警告 `Failed to extract audio from video: …` 说明抽取失败、按无音频处理 |
| `data.mm_configs.sample_rate` · 音频采样率 | YAML | 16000 | 视频音轨与字节形式的音频重采样到它;路径形式的独立音频固定按 16000 读 | — |
| `data.mm_configs.max_image_nums` · 每条样本最多几张图 | YAML | 不设 | 读完全部图后只留前 N 张;除了 `doom` 这个预处理函数,对话里的占位不会跟着减 | `Image token number is missing for a image input.` |
| `model.tokenizer_path` · 处理器与分词器从哪加载 | YAML 或命令行 | 等于 `config_path`,后者默认等于 `model_path` | 指向一个只有分词器的目录,模型就被当成纯文本 | 本地路径里没有处理器时警告 `… no preprocessor loaded from …` |
| `model.processor_config` · 覆盖处理器配置 | YAML | 空 | 例如改 Qwen-VL 图像处理器的 `size` 上下限;与 `mm_configs` 的像素预算取更紧的那个 | 同 `image_grid_thw` |
| `model.chat_template` · 对话模板名 | YAML 或命令行 | 不设 | Qwen-VL 系填 `qwen2vl`、`qwen2_5vl`、`qwen3vl` 或 `qwen3_5vl`;Omni 不设,用处理器自带模板 | 启动日志 `Qwen2VLTemplate will not truncate sequence when longer than [max_seq_lens].` |
| `train.vit_lr` · 视觉参数的学习率 | YAML 或命令行 | 1e-6 | 名字含 `visual` 的可训参数用它,其余用 `model.optimizer.lr`;两组同形状调度;Muon 下被忽略 | wandb 或日志里的学习率;Muon 下警告 `… ignores the provided param_groups argument …` |
| `train.freeze_vit` · 冻结视觉塔 | YAML 或命令行 | 关 | Omni 保留 merger 可训,其他模型连 merger 一起冻;开 LoRA 时忽略 | 日志 `**** trainable parameters ****` 那一段 |
| `train.freeze_audio_tower` · 冻结音频塔 | YAML 或命令行 | 关 | 只对 Omni 生效,保留音频输出投影;开 LoRA 时忽略 | 同上 |
| `model.encoder_data_balance` / `encoder_data_balance_sorting_algo` · 编码器数据均衡 | YAML 或命令行 | 关 / `post_mbs_balancing_greedy_without_pad` | 只放行 `qwen3_vl_moe` 且不开序列并行;当前没有模型读它,打开不改变负载 | 警告 `Encoder data balance currently supported only for Qwen3-VL MoE, …` 或 `Warning: Qwen3VLEncoderDataBalance currently does not support sequence parallelism. …` |

**观测。** 本章看 4 处。一是首个微批:训练器把第一个微批逐键打进日志,`multimodal_metadata['vit_image_cu_seqlens']` 这类行出现,说明元数据函数生效了;`image_grid_thw`、`video_grid_thw` 的值就是缩放之后的网格,拿它乘一下就知道每张图多少 token。二是可训参数:`**** trainable parameters ****` 之间列出所有可训参数名,冻结有没有生效、merger 在不在,看这里。三是 collator 配置表:`Main Collate Configuration` 里 Omni 应当多出 `input_features`、`audio_feature_lengths`、`audio_mask` 三行,`pixel_values` 那行的补齐倍数是 4。四是隐式同步:改过补丁配置之后跑 `tests/models/test_model_forward_no_implicit_sync.py`,它在 CUDA 同步调试模式下跑前向,多出一次等待就会失败。

**典型配置。**

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| Qwen3-VL MoE 图文加视频 SFT,序列 4096 | `model.chat_template: qwen3vl`;`data.mm_configs` 写 `image_max_pixels: 602112`、`video_max_pixels: 602112`、`video_total_pixels: 2889523`、`max_frames: 16`、`fps: 2.0`、`use_audio_in_video: false`;`train.vit_lr` 保持默认 | 用长视频每帧分辨率下降换单条样本长度可预期;显式关掉音轨,省下每段视频一次音频解码与重采样 |
| Qwen3-Omni 从原始视频训,只想调理解能力 | `model.chat_template` 不设;`data.mm_configs` 写 `scale_factor: 28`、`frame_factor: 2`、`min_frames: 4`、`max_frames: 20`、`use_audio_in_video: true`;`train.freeze_audio_tower: true` | 冻住音频塔主体省下它的梯度与优化器状态,换来音频编码器不再适配新数据,输出投影仍在学;训练机要装 ffmpeg |
| Qwen3-Omni,帧与音频已离线抽好 | `data.source_name: qwen_omni_offline_av`;样本 `videos` 每项是含 `frames` 与 `audio` 的字典;`data.mm_configs.use_audio_in_video: true` | 用离线预处理和更大的存储换每一轮都不再解码容器;帧列表会被全部解码再抽帧,离线时就该按目标帧率抽好 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| 第一条样本就报 `Unknown preprocessor name: …` | `data.source_name` 或多源 YAML 的 `names` 是否等于某个登记名 | 改名,或在 `preprocess.py` 里登记一个 |
| 报 `Image token number is missing for a image input.`(视频同理) | 样本 `images` 的个数与对话里 `<image>` 的个数是否一致;是否设了 `max_image_nums` | 对齐数据,或去掉 `max_image_nums` |
| 报 `Cannot lay out … video tokens over … time chunks` | 帧数能否被视频处理器的时间合并因子整除 | 设 `frame_factor` 为该因子 |
| 启动后很久不出第一步,CPU 满 | 是否在读原始视频容器;Qwen-VL 上是否没关 `use_audio_in_video` | 关掉音轨;改用离线帧;加 `data.dataloader.num_workers` |
| 偶发 OOM,总落在含长视频的那几步 | 首个微批里 `video_grid_thw`;是否设了 `video_total_pixels` | 设总像素预算,调小 `max_frames` |
| 报 `ffmpeg is not available; …` | 视频是不是路径或字节形式 | 装 ffmpeg,或改成帧列表、帧字典 |
| Omni 报 `Offline-A/V dict with ndarray … requires an explicit …` | 离线字典里的 `audio` 是不是数组而没给 `audio_fps` | 补上 `audio_fps`,或改存 WAV 字节 |
| 视频训练里模型对声音毫无反应 | 日志里有没有 `Failed to extract audio from video` | 抽音轨失败时会静默当成无音频,检查容器里的音轨 |
| 开序列并行后前向报 `position_ids is None while sequence parallel is enabled` | 输入是否经过 VeOmni 的数据变换 | 走数据变换,或自己按全序列预算位置 |
| 开 `train.freeze_vit` 报 `Cannot find visual module for model_type=…` | 这个模型有没有视觉塔 | 纯文本模型不要开 |
| 开了 `model.encoder_data_balance`,各 rank 视觉塔耗时仍然悬殊 | 当前代码没有调用均衡器 | 靠数据侧控制每步图像数与像素预算 |

## 六、常见误区

- **以为打开 `model.encoder_data_balance` 就会把视觉塔的负载在 rank 间摊平。** 会这么以为,是因为开关、排序算法、均衡器类和单元测试一应俱全,接入新模型的文档里还有调用示例。实际上在这组基准上它只被写进模型配置,没有任何模型前向读它;打开不报错,只有非 Qwen3-VL MoE 或开了序列并行时打一行警告,负载纹丝不动。
- **以为不写 `use_audio_in_video` 就不会抽音轨。** 会这么以为,是因为使用文档的参数表写默认关。实际上代码默认开:路径或字节形式的视频都会被抽音轨、重采样到 16 kHz,Qwen-VL 那条路抽完直接扔掉,白白占着 dataloader 的 CPU。仓库里所有视觉语言样例配置都显式写了关,抄配置时别漏掉这一行。
- **以为 `data.mm_configs` 里写错的键会报错。** 会这么以为,是因为 VeOmni 的配置对未知字段一向直接报错。`mm_configs` 却是一个自由字典,键原样传进一串用 `**kwargs` 接参的函数,拼错的键被静默忽略:把 `image_max_pixels` 写成 `max_pixels`,像素照旧不限,序列照旧爆。
- **以为视觉塔默认和主干用同一个学习率。** 从 HF Trainer 过来的人习惯一个学习率管全部。实际上只要视觉塔可训,名字带 visual 的参数就用 `train.vit_lr`,默认 1e-6,比样例配置里的主干学习率 1e-5 小一个数量级;想让视觉塔学快一点要显式调它。反过来,音频塔不吃这个值,它跟着主干走。
- **以为 `train.freeze_vit` 在所有模型上冻的是同一块。** Omni 冻结视觉塔时保留 merger 可训,Qwen-VL 系连 merger 一起冻。两边训出来的差别不在日志里报,只能看 `**** trainable parameters ****` 那一段。
- **以为 `data.max_seq_len` 会截断多模态样本。** 它只截纯文本对话。多模态模板启动时就声明不截断,超长样本原样进动态批;控制长度的只有像素预算、`max_frames` 和 `video_total_pixels`。
- **以为训完的 Qwen3-Omni 能直接说话。** 训练用的 modeling 从构造起就没有 talker 与声码器,导出的 checkpoint 里只有 thinker;要做语音生成,得回到上游原版实现。
- **以为照着预处理器注册表那篇文档写 `data.datasets` 就能配数据源。** 那段示例里的字段在当前配置里不存在,启动即报 `Invalid configuration keys`。单源用 `data.source_name`,多源用多源 YAML 里的 `names`。
