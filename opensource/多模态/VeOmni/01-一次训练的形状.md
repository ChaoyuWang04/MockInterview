# 一次训练的形状

这一页回答一件事:一个训练作业里,哪些东西每个作业只有一份,哪些东西每个模型各有一份,两者怎么拼成一次训练。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

常见的训练器把一切塞进一个类:建进程组、建模型、切分、建优化器、建数据、跑循环、存 checkpoint,并且全进程只有**一套**并行拓扑——哪些卡组成数据并行组、哪些卡组成序列并行组,全局只有一个答案,谁要用谁去读。

作业里只有一个模型时这没问题。作业里一旦出现**第二个模型**就会出事:DPO 要一个冻结的参考模型陪着策略模型一起前向,蒸馏要一个老师,Omni 模型的不同部分可能想用不同的序列并行度。这时候,一切「去读全局拓扑」的代码都会拿第一个模型的答案去服务第二个模型:序列并行的 all-to-all 用错了组,collator 按错的并行度切序列,梯度裁剪按错的组去归约范数。形状恰好对不上的,当场报错;形状恰好对得上的,**静默算错**;通信组对不齐的,所有 rank 一起**挂住**,日志里什么也没有。

存取也会乱。数据读到哪了、随机数状态、步数计数器——这些**每个作业只有一份**;权重、优化器状态、学习率调度器——这些**每个模型一份**。两类状态混在一个对象里,多一个模型,要么游标存了两遍、续训时互相覆盖,要么参考模型的权重被当成训练状态跟着存。

还有一件单模型也躲不开的事:构建顺序本身就是约束。优化器必须拿切分之后的参数来建;collator 要知道序列并行度才能切;学习率调度器要知道总步数,而总步数要等数据集建好才算得出来。顺序排错,不会报错,只会得到一个看上去能跑的错误作业。

## 二、解法

最天然的直觉:**按寿命分家**。每个作业只有一份的东西归训练器,每个模型一份的东西归模型自己;再给每个模型发一张写着名字的**工牌**,工牌背后是这个模型自己的那套并行拓扑,谁干活先亮自己的工牌。

![一个 DPO 作业的两半与三张工牌:左边训练器只持有作业级的一份东西,包括进程组、数据管线、训练循环、回调和数据游标;右边两个模型运行时各持有自己的模型、分片、优化器或冻结副本,各亮一张工牌;中间的命名拓扑表里 base、policy、reference 三个名字因为拓扑参数完全相同,指向同一个拓扑对象,所以只建了一次进程组](/opensource/VeOmni/01a-two-halves-and-badges.svg)

**模型那一半叫模型运行时**(VeOmniModelRuntime)。构造它就等于把模型建好:先用自己的名字登记一套拓扑,然后在这套拓扑下依次建模型、冻结或挂 LoRA、切分并装载权重、建优化器;离开拓扑之后再准备分词器与处理器、checkpoint 管理器。它不是一个模块,而是一个**模型的把手**:对它取属性、对它调用,都转发给里面真正的模型,所以训练循环里写「把这批数据喂给模型」照样成立。

**作业那一半叫训练器**(BaseTrainer)。它先初始化进程组,用名字 base 登记作业默认的那套拓扑,再设随机种子——登记放在设种子之前,是因为有的 GPU 平台在确定性通信的环境变量打开之后建网格会出问题。然后它构造模型运行时,**再进入这个模型的拓扑**去建数据变换、数据集、collator 和 dataloader,因为 collator 要按这个模型的序列并行度切数据。最后建学习率调度器和回调。

**工牌是按名字查、每次现查的。** 模型运行时不保存拓扑对象本身,每次要用时拿名字去登记表里取,登记表是唯一真源。运行期的切换是**按操作**的:前向、算 loss、反向各自进入这个模型的拓扑,梯度裁剪也在自己的拓扑里做。DPO 的一步里,参考模型的前向亮 reference 的工牌,策略模型的前向与反向亮 policy 的工牌。

**为什么实际不吃亏**:拓扑参数完全相同的名字,登记时直接复用同一个拓扑对象,不会重复建进程组。上图的 DPO 作业登记了 3 个名字,实际只建了 1 套网格。单模型作业里,训练器和模型运行时登记的都是 base 这一个名字,切换工牌等于什么都没做。

**按任务的训练器是拼出来的,不是继承出来的。** 文本、视觉语言、扩散、DPO 这几个训练器各自持有一个训练器基类的实例,再把构建步骤一步一步显式调出来。DPO 就是这么把两个模型运行时装进一个作业的:策略模型照常构建;参考模型是另一个运行时子类,复制策略模型的配置,关掉 LoRA、混合精度、重计算、编译与激活卸载,只建模型、只做切分装载,不建优化器,也不参与存 checkpoint。

**训练的形状也在这一层定死。** 全局批必须是「微批 × 数据并行度」的整数倍,倍数就是梯度累积步数;数据并行度是总卡数除以序列并行、上下文并行这几维之后剩下的那部分。例如 16 张卡、序列并行度 2,数据并行度是 8;微批 1、全局批 32,就累积 4 步。总步数有两种算法:动态批打开时(默认),每步按 token 预算凑批,一步吃掉多少条样本事先不知道,所以要你声明**训练 token 总量**,总步数 = token 总量 ÷(全局批 × 最大序列长度)向上取整;动态批关闭时,按样本数除以每个 rank 每步取的条数来算。

## 三、代价

**把手不是模块。** 训练器上的模型是一个把手,不是真正的模块。任何做类型检查、或要把真模块交给分片接口与分布式 checkpoint 的代码,都要走模型运行时自己的方法;在调用处自己剥一层把手,是这套设计明确不许的写法。

**忘了亮工牌不报错。** 当前拓扑是一个上下文,不是参数。在模型运行时与训练循环之外新写的代码,如果直接去读「当前拓扑」,读到的是最近一次登记或进入的那一套;单模型作业里永远是对的,多模型作业里才会错,而且是静默的。拓扑还没登记时去读,拿到的是一个单进程的默认拓扑,只打一行警告。

**拼出来的训练器要逐个维护。** DPO 与扩散训练器重写了「前向加反向」这一步,不走基类那一版。只加在基类那一步里的逻辑,这两个训练器会整段跳过——加新的生命周期逻辑,要么把每个重写版都改到,要么显式拒绝不支持的训练器。

**同一套生成的 modeling 被两个模型共用。** 算子空位是模块级的全局对象,策略模型和参考模型实例共用同一组空位。临时拦截某个空位的代码,如果只绑定在一个模型上,会看到另一个模型的前向。

**登记是一次性的。** 同一个名字第二次登记,直接返回第一次的那个拓扑,不管第二次给的配置是什么。所有 rank 还必须按同样的顺序登记,因为建进程组本身是一次集合通信。

**动态批要你自己报 token 总量。** 它不从数据里数,默认值是一个固定数。报小了,训练在数据还没吃完时就结束;报大了,默认的动态批会在数据读完后从头再读,凑够算出来的步数为止,等于把一部分数据多训了几遍,也不报错。

**参考模型不能单独配。** DPO 的参考模型永远复制策略模型的配置,换一个不同结构或不同切法的参考模型当前不支持。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09),同为大规模训练框架,路线相反。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 拓扑从哪来 | 按名字登记多套,当前拓扑是一个可切换的上下文,深处的通信工具直接读当前那套 | 启动时各 rank 按相同顺序建好全局各组;新写的组件改收一个显式传入的进程组集合,见 Megatron 解读 02 章 |
| 一个 rank 上有多个模块 | 每个模型一个名字,运行到它时进入它的上下文 | 一个多模块进程组集合,按模块名各映射一份进程组集合,构造组件时传进去 |
| 用错组的时候 | 忘了进入上下文,就静默用了默认那套 | 集合对象允许只填一部分,没填的字段读出来是空,错误推迟到第一次真正用这个组时才爆 |
| 模型与作业的边界 | 模型运行时与训练器两个对象,一个作业可以装多个模型运行时 | 训练入口是一个函数,模型、数据集与前向各由调用方传入的构造函数提供;张量并行与流水并行写在模型层里 |

两条路各有取舍。显式传组的写法让每个组件的通信范围在构造时就写死,啰嗦但查得到;上下文切换的写法让序列并行、collator 这些深处的代码不用层层传参,换来的是「没进上下文」这类错误没有任何信号。VeOmni 选后者,因为它的模型来自 HF 的 modeling,不可能把进程组一层层塞进别人写的构造函数里。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。本章只列决定训练形状的几项;并行度各维怎么选在 04 到 06 章,动态批的细节在 07 章。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `train.micro_batch_size` · 每个 rank 每个微批几条样本(动态批下是 token 预算的倍数) | YAML 或命令行 | 1 | 调大:每个微批更长,显存升;动态批下每个微批的 token 预算 = 它 × `data.max_seq_len` | 日志 `Use dynamic_batching -->` 那几行里的 `batching_token_len` |
| `train.global_batch_size` · 全局批 | YAML 或命令行 | 不设:等于微批 × 数据并行度,不累积 | 必须是微批 × 数据并行度的整数倍,倍数就是累积步数;不是整数倍直接报错 | 日志 `Set gradient accumulation to N.` 或 `` `global_batch_size` is None, disable gradient accumulation.`` |
| `model.accelerator.dp_replicate_size` / `dp_shard_size` · 数据并行度拆成组间复制 × 组内分片 | YAML 或命令行 | 都是 -1:全部给组内分片,复制为 1 | 设其中一个,另一个自动推;两个都设则乘积必须等于数据并行度 | 日志 `Initializing parallel state: dp_size …, dp_replicate_size …, dp_shard_size …` |
| `data.train_size` · 动态批下的训练 token 总量 | YAML 或命令行 | 10000000 | 决定总步数;报小了训练提前结束;报大了,默认的主进程动态批会从头重读数据凑够步数(worker 模式与关掉动态批时则是本轮提前结束、学习率衰减不到底) | 日志 `Start training. … Train steps: N.` |
| `data.train_sample` · 关掉动态批且数据集无长度时的样本总量 | YAML 或命令行 | 10000 | 同上,换成按样本算 | 同上 |
| `train.num_train_epochs` · 轮数 | YAML 或命令行 | 1 | 总步数 = 每轮步数 × 轮数,学习率调度按这个总数排 | 同上 |
| `train.max_steps` · 每轮步数上限,调试用 | YAML 或命令行 | 不设 | 设了且小于算出的步数:每轮只跑这么多步 | 警告 `Set train_steps to N. It should be for debug purpose only.` |
| `train.seed` · 随机种子 | YAML 或命令行 | 42 | 在拓扑登记之后、模型构建之前设 | 落盘的 `veomni_cli.yaml` |
| `train.sync_each_train_step` · 每步开始前同步一次设备 | YAML 或命令行 | 开 | 关:允许数据搬运与主机到设备的拷贝和下一步重叠 | 每步耗时是否下降 |

**观测。** 本章看 4 处。一是启动时的整份配置:rank 0 把解析后的完整配置打进日志,并落一份 `veomni_cli.yaml` 到输出目录,复现以它为准。二是拓扑:每建一套新拓扑打一行 `Initializing parallel state: …`,名字复用已有拓扑时打 `Reusing cached parallel state for identical topology.`;DPO 作业里应该只看到一行初始化、其余都是复用。三是形状:`Set gradient accumulation to N.` 与 `Use dynamic_batching -->` 那一段里的 `num_micro_batch`,两者应当相等。四是步数:`Start training. Start step: … Train steps: … Start epoch: … Train epochs: …`,拿它和你心里的数对一遍再往下跑。

**典型配置。** 三套能直接抄走的起法,参数名和默认值都来自上表。组合与推荐值是按语义推的起点,不是实测最优。

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单机 8 卡 SFT,想要固定样本数的全局批 | `train.dyn_bsz: false`、`train.micro_batch_size: 1`、`train.global_batch_size: 64` | 用每步 8 次累积换一个大小固定、按样本计的全局批;映射式数据集的总步数按长度自动算,流式数据集要报 `data.train_sample` |
| 多机预训练,每机 8 卡、共 4 机 | 动态批保持默认,`model.accelerator.dp_replicate_size: 4`、`dp_shard_size: 8`,`data.train_size` 填真实 token 总量 | 分片只在机内做、跨机只做复制,用跨机的梯度 all-reduce 换掉跨机的参数聚合;步数靠你报的 token 总量 |
| 调通流程,先跑几步看形状 | 任意配置加 `train.max_steps: 20` | 用截断的训练换快速看到拓扑、累积步数与每步耗时 |

| 症状 | 先查 | 然后 |
|---|---|---|
| 启动即报全局批 `should be a multiple of …` | 微批 × 数据并行度是多少;数据并行度是否已扣掉序列并行那几维 | 把全局批改成它的整数倍 |
| 训练在数据远没吃完时就结束 | 日志里的 `Train steps`;是否开着动态批而 `data.train_size` 还是默认值 | 按真实 token 总量填 `data.train_size` |
| 跑完的步数远多于数据量该有的步数 | `Train steps` 与「真实 token 总量 ÷ 每步 token」对不对得上 | 同上,token 总量报大了,数据被从头重读;细节见 07 章 |
| 日志出现 `Parallel state has not been initialized. returning default Single-process state.` | 哪段代码在拓扑登记之前或训练器之外读了当前拓扑 | 改成在模型运行时的方法里做,或显式按名字取拓扑 |
| 新加的功能在文本训练里生效,在 DPO 或扩散训练里没反应 | 它是否只写在了基类的前向加反向那一步 | 把这两个训练器重写的那一步也改到 |
| 两个模型想用不同并行度,第二个却沿用了第一个的 | 两个运行时是否登记了同一个名字 | 换一个名字;同名第二次登记不会生效 |

## 六、常见误区

- **以为训练器上的模型就是 `nn.Module`。** 会这么以为,是因为取属性、调用、取参数都照常工作。实际上它是模型运行时这个把手,转发了模块的接口;做类型判断、交给分片接口或分布式 checkpoint 时会失败,真模块在它里面那一层,而且这种边界应当交给模型运行时自己的方法去处理。
- **以为 trainer-free 就是没有训练器。** 会这么以为,是因为 README 的设计原则写的是「不用固定结构的训练器类」。实际上任务脚本每个只有 8 行,整个流程都在训练器类里;这个词在当前代码里的意思是训练器由基类实例拼出来、构建步骤显式排开,想改哪一步就换哪一步。
- **以为 `global_batch_size` 是每张卡的批。** 它是全局的,而且除的是数据并行度不是总卡数。开了序列并行之后,同一个序列并行组里的几张卡只算一份数据并行度,照总卡数去配就会报「不是整数倍」。
- **以为动态批下步数是从数据里数出来的。** 不是。`data.train_size` 是你报给它的 token 总量,默认值 10000000 跟你的数据毫无关系。最常见的表现是换了数据集、忘了改这一项,训练安安静静跑完,只是跑的步数不对。
- **以为 DPO 的参考模型可以配成另一个模型。** 参考模型永远复制策略模型的配置,只改精度并关掉训练相关的开关;想拿一个不同的参考模型当前不支持。
- **以为给第二个模型登记一个新拓扑就能让它用不同的并行度。** 名字相同时第二次登记直接返回第一次的对象,新配置被忽略,只打一行调试级日志。要不同的拓扑,名字必须不同,而且所有 rank 要按同样的顺序登记。
- **以为在基类的前向加反向里加的逻辑对所有训练器都生效。** DPO 和扩散训练器重写了这一步,基类里新加的东西它们一行都不会执行;这是维护者自己写进约束清单里的坑。
