# checkpoint:续训与导出

这一页回答一件事:一个步目录里的每样东西由谁、在什么时候写,续训时怎么判断它完整、换了并行度还能不能读回,给推理用的权重又怎么导出来而不把某一张卡撑爆。说法都在源码基准 `019b1c0276`(tag `v0.1.12`)上核过,「当前」与「默认」都指这组基准。

## 一、核心问题

一次存盘要落下的东西,寿命和主人各不相同。权重和优化器状态属于模型,按分片散在每张卡上;学习率调度器和扩散条件模型的噪声生成器也跟着模型走;数据读到哪、随机数状态、步数计数器属于整个作业,而且每个 rank 的内容都不一样。全塞进同一个目录、同一套写法,就会出三类事。

**半截存档被当成完整存档。** 存盘写到一半进程被杀,或者一次异步保存还在后台往盘上流分片,目录已经在那里了。续训如果只看「最新的步目录」,就会读到一半是这一步、一半是上一步的权重,或者读到一个还没有游标的步,数据从头开始。同一个作业重启后又训到同一步、覆盖旧目录时也一样:覆盖到一半的那段时间里,旧的完成标记还立着。

**导出 HF 权重时单卡聚合 OOM。** 最直接的导出是把整模型聚到 rank 0,再写成 safetensors。Qwen3-235B 这一档的 MoE,bf16 权重约 470 GB,聚到一张 80 GB 的卡上放不下;退到 CPU 内存里聚,主机内存也可能放不下。

**并行度一换读不回。** 如果每个 rank 只是把自己手里那块字节存成一个文件,换了卡数或专家并行度,新 rank 要的那块和旧文件里的那块对不上。专家尤其麻烦:05 章讲过,专家先沿专家维切给专家并行组,再交给 FSDP,每张卡手里的专家张量已经丢掉了「我是全局第几个专家」的身份。

还有一件历史包袱:v0.1.12 及更早版本写的存档是另一种目录形状,新代码得还能接着训。

## 二、解法

最天然的直觉:**按主人分目录,各管各的完成标记。** 模型的状态写在模型子目录里,由这个模型的 checkpoint 管理器负责;作业的状态按 rank 写在步目录根下,由作业级的回调负责;给推理用的导出另开一棵树,续训永远不读它。

![一个步目录的写入者与顺序:模型子目录里先由每个 rank 写一份附加状态,再由全体 rank 经 DCP 写权重目录和优化器目录,各自的元数据文件由 rank 0 最后落;清缓存与 barrier 之后,导出到期的步由各 rank 写 safetensors 分片、rank 0 拼成整文件;然后每个 rank 写自己的数据游标和作业状态;最后 rank 0 写完成清单。作业根目录下的模型资产在训练开始时由 rank 0 写一次](/opensource/VeOmni/13a-step-dir-writers.svg)

**何时、存什么、怎么存分三层。** 01 章的两半在这里各有分工:时机由回调决定,按步、按轮;要存哪些对象由训练器和模型运行时说了算,训练器只是把「存」「读」「导出」转给它持有的模型;怎么存由每个模型的 checkpoint 管理器负责,它唯一的职责就是把顺序排对。所有路径都从一个目录规则模块算出来,写的一方和读的一方用同一个函数,不会一个拼了步号、另一个又拼一次。

**模型状态走 DCP,权重与优化器分两个目录。** DCP 存的不是「第几张卡的字节」,而是每一块在全局张量里的坐标,读的时候按当前切法重新取,机制见 FSDP 解读 11 章。VeOmni 在它上面做了两件事。第一,权重和优化器各写一个 DCP 目录:Adam 的优化器状态约是权重的 2 倍,离开这次训练就没用,分开存才能只拷权重、只转换权重。第二,专家参数在交给 DCP 之前,按每个参数挂的分片说明临时把专家维补回去,拼成一个在「专家内 FSDP × 专家并行」二维网格上的分布式张量,DCP 看到的就是全局 E 个专家的完整形状;读回来之后再把专家维丢掉,还原成运行时的样子。

**读的时候权重严格、优化器宽松。** 权重目录里缺任何一个模型参数就直接报错,列出缺的前 10 个名字,LoRA 除外(它的 DCP 只存可训练的那部分,底座从 HF 来,见 04 章与 11 章)。优化器允许缺项:从来没收到过梯度的参数(没被路由到的专家、冻结的底座)根本没有状态可存,读回时保持新建优化器的默认状态,和下一步自己生成的一样。

**小状态按 rank 各存一份。** 学习率调度器的状态加上模型运行时交出来的附加状态(09 章那个噪声生成器),每个 rank 写一个 pickle 到模型子目录下的附加状态目录,赶在两次 DCP 之前写,因为它小,先写完能让中途死掉的存盘少留一点残骸。作业级那份——步数、CPU 与设备两路随机状态、计量器、分数据源 loss 的累计——连同数据游标一起由作业回调按 rank 写,内容见 07 章。两个目录同名,但一个在模型子目录里、一个在步目录根下,装的东西不同。

**完整性是两半标记的合取。** DCP 每写完一个目录,由 rank 0 在里面落一个元数据文件,这是 DCP 自己的完成标记。作业回调等所有 rank 的游标都写完、归约确认没人失败之后,再由 rank 0 写一份完成清单,记格式版本、步号和卡数,先写临时文件再改名,读者不会看到半截清单。清单不列模块,也不等 DCP:异步保存时清单完全可能比分片先落盘。所以自动续训挑步时两样都要:清单在,并且模型子目录下每个 DCP 目录的元数据都在(优化器目录只在存在时才要求),挑其中步号最大的。重写同一步时,各方先删掉自己的那个标记再动数据:DCP 存取器删元数据,作业回调删清单,覆盖到一半的步两半都不成立。

**一次存盘的顺序与理由。** 管理器存盘前先清一次显存缓存,因为 DCP 在 NCCL 上聚合时要临时分配缓冲;维护者在 16 张 H100 上训 Qwen3.5-35B-A3B 视觉语言模型时,就撞到过 DCP 内部的 NCCL 显存分配失败。存完再清一次、全体 barrier,然后才轮到导出和游标。回调的排列是「先模型、后游标」(01 章):中间崩了,留下的是有权重、没游标的步,续训时只打一行警告、全体只恢复权重。

**异步与暂存是同一个问题的两种答案。** 目标盘慢到写一次就拖住训练循环时,可以异步:权重和优化器是两个独立的后台保存,各自一个 Gloo 进程组,两者互相重叠;同一类的上一次保存要等到下一次同类保存开始前、导出前、续训读盘前和训练结束时才收尾,任何一个 rank 的后台保存失败,收尾时全体一起报错。也可以暂存:同步写到节点本地盘,由每个节点的 0 号本地 rank 拷到目标目录,先清空目标、再拷数据、最后拷元数据,拷失败时上一份存档完好如初。两者不能同开,因为异步保存返回时暂存副本就被删了,后台写还在读它。

**导出另开一棵树,从活着的模型直接写。** 导出不读刚写的 DCP 文件,而是每个 rank 从自己手里的分片取一份状态(专家维同样补回),浮点 32 位的在副本上转成 bf16,按原始 HF 索引把每个参数分到对应的文件号;每个 rank 只写自己那块,最后由 rank 0 在盘上把各块按文件拼成完整的 safetensors,写出索引,再把 config 和分词器放进去。整个过程没有哪张卡要装下整个模型。导出前,管理器保证这一步的 DCP 已经存在:导出节奏和存盘节奏不重合时,它先补存一次 DCP,作业回调也按同样的节奏补写游标和清单,所以每个导出过的步都能续训。训练结束那次导出,补存完 DCP 之后先丢掉优化器和调度器,再开始导出。

**导出的退路在 rank 0 的主机内存里。** 昇腾 NPU 上,以及 PyTorch 低于 2.9 时,走旧路径:rank 0 把刚写的权重 DCP 整个读进主机内存,再按 5 GB 一个文件写出,其余 rank 在 barrier 等着。NPU 绕开分布式那条路,是因为 HSDP 下各复制 rank 各自在卡上做 fp32 到 bf16 的转换,昇腾 910B 上不逐位一致,拼文件时读到哪个 rank 就是哪个 rank 的数。

**离线合成与专家拆分。** 训练时没导出,可以事后用合并脚本把一个步目录转成 HF:它只打开权重目录,不碰优化器和游标;先从元数据排出分片计划,每次只读一个分片大小(默认 2 GB)的张量进内存,转 bf16、写文件、释放,再读下一片。里面是 LoRA 键时自动改写成 PEFT 的 adapter 文件。VeOmni 导出的 MoE 权重是专家堆叠的布局;要还原成 HF 常见的逐专家键,另有一个拆分脚本。反方向的合并脚本已经标为弃用,因为训练启动时装载器会边读边堆叠专家(02 章)。

**换并行度:DCP 那部分能读回,按 rank 的文件不行。** 权重和优化器按全局坐标存,专家也存成全局 E 的形状,读回时按当前网格重新取,换卡数、换专家并行度在机制上成立;树内测试覆盖的是同一套并行配置下存了再读、再离线合成 HF 并与 DCP 逐项比对,专家并行度取 1、4、8 各跑一遍,没有覆盖存与读用不同并行度。按 rank 存的两类文件则绑着卡数:作业侧缺一个 rank 的文件,全体放弃作业侧状态(07 章);模型侧那份附加状态缺了则不报错,见第三节。

**多模块与旧格式。** 目录规则里预留了多模块作业的写法:模型子目录、导出目录和模型资产按模块名再嵌一层,游标和清单不嵌,因为一个作业只有一个数据流。基准上没有哪个管理器子类设置模块名,单模型作业都落在不嵌的那一层。旧格式的续训集中在一个兼容文件里:v0.1.12 的步目录本身就是一个 DCP 目录,权重和优化器混在同一批文件里,调度器和作业游标混在同一个按 rank 的 pickle 里。读取时先找新布局,找不到才退回旧形状;自动挑步时,旧步只在完全没有新布局的模型子目录时才被接受。删掉这个兼容文件和引用它的几处导入,旧存档就改为直接失败。

## 三、代价

**两半标记只在自动挑步时检查。** 显式给一个步目录续训,不看清单也不看元数据是否齐全,直接去读。读到缺元数据的 DCP 目录会报错;读到有权重、缺游标的步,只打警告、数据从头。

**按 rank 的文件把卡数钉死。** 卡数变多时,编号超出旧卡数的 rank 找不到自己那份模型附加状态,调度器不恢复也不报错,而旧编号的 rank 照常恢复;同时作业侧因为有 rank 缺文件而全体放弃,步数从 0 数起。结果是权重和优化器接上了,各 rank 的学习率却不在同一步上。

**专家零通信布局的存档不能换切法。** 12 章的专家零通信让专家内 FSDP 那一刀和专家并行那一刀落在同一维;补回专家维时两刀的嵌套顺序和物理排布相反,拼出的全局张量沿专家维按块错位。同一套并行配置存了再读完全可逆,换了切法再读、或者从外部读这份存档(包括离线合成 HF),看到的专家顺序就是错开的。代码注释里写明了,修它要改网格的维序。

**旧存档永远不删。** 每次存盘新建一个步目录,基准上没有任何保留份数或清理逻辑。优化器状态约是权重的 2 倍,按步存的长作业会一直往盘上堆。

**导出不是免费的。** 每次导出是一次全体参与的集合保存,rank 0 还要在盘上把各块拼成整文件;导出节奏不和存盘节奏重合时,还要额外补一次 DCP。

**异步的收尾可能落在不该等的地方。** 后台保存比存盘间隔还慢时,下一次同类保存开始前会阻塞训练等它;暂存则要求每个节点的本地盘同时放得下这个节点上所有 rank 的权重和优化器。两者的 Gloo 超时默认是 30 分钟,多机时还要求 Gloo 网络本身能通,配错只在第一次存盘时暴露。

## 四、和同类大厂框架不一样的地方

对照对象是 Megatron-LM(基准 fb6a123a09)。

同为大规模训练框架,两边都用分布式存档续训,分歧在「谁来宣布一次存档完成」和「存档之外还要不要管」。

| 比较维度 | VeOmni | Megatron-LM |
|---|---|---|
| 哪一步是完整的 | 每个步目录自带两半标记:作业侧的完成清单加每个 DCP 目录的元数据;自动续训扫描目录,取两半都在的最大步 | 保存根目录下一个记录最新迭代号的文本文件,rank 0 在保存收尾时改写,异步保存时挂在收尾回调里;续训读这个号 |
| 留几份存档 | 不删旧的 | 可设保留间隔,新存档记好之后,删掉上一份不在间隔上的存档 |
| 换并行度后的随机状态 | 随机状态按 rank 存在作业侧文件里;有 rank 缺文件,全体放弃作业侧状态 | 张量并行度或流水并行度与存档不同时,打一行提示后忽略旧随机状态 |
| HF 权重 | 训练中按步、按轮或结束时直接导出 safetensors | 训练的存取模块不写 HF 权重,只可选地把分词器文件放进存档;格式转换走离线工具,见 Megatron 解读 13 章 |

Megatron 的单一迭代号文件简单可靠,前提是写它的那一刻整份存档已经落盘,所以异步时它要等后台保存收尾;VeOmni 让作业侧和模型侧各自宣布完成,游标和清单不用等后台分片,换来的是续训一方必须同时检查两样东西。导出也是同一取舍:VeOmni 的模型本来就是 HF 的 modeling,导出只是换个写法;Megatron 的模型层是自己的,离开训练框架必须转换。

## 五、调参与观测

这一页的参数全是启动配置,改了要重新拉起整个作业。

| 参数 | 在哪调 | 默认 | 调了之后 | 怎么看 |
|---|---|---|---|---|
| `train.checkpoint.output_dir` · 作业根目录 | YAML 或命令行 | `output` | 存档落在它下面的 `checkpoints/global_step_N/`,模型资产落在 `model_assets/` | 目录本身 |
| `train.checkpoint.save_steps` · 每隔多少步存一次 | YAML 或命令行 | 0:不按步存 | 调小:崩溃时丢的步少,写盘时间与磁盘占用多 | `Distributed checkpoint saved at … successfully!` |
| `train.checkpoint.save_epochs` · 每隔多少轮存一次 | YAML 或命令行 | 1 | 设 0 且 `save_steps` 也是 0:除训练结束的导出外不存 | 同一步已按步存过时打 `Skipping duplicate checkpoint save at epoch_end …` |
| `train.checkpoint.save_hf_weights` · 是否导出 HF 权重 | YAML 或命令行 | 开 | 开:训练结束一定导出一次,并补写那一步的 DCP 与游标;LoRA 作业导出 adapter | `Distributed HuggingFace safetensors save took …s` |
| `train.checkpoint.hf_save_steps` / `hf_save_epochs` · 中途导出的节奏 | YAML 或命令行 | 0 / 0 | 设了:按节奏额外导出;不在存盘节奏上的步会补一次 DCP | 步目录下出现 `hf_ckpt/` |
| `train.checkpoint.load_path` · 续训路径 | YAML 或命令行 | 不设 | 给步目录:直接读,不做完整性检查;给 `auto`:扫描 `output_dir/checkpoints/` 挑两半标记都在的最大步 | `found valid previously saved checkpointed steps: …` 或 `Failed to find latest checkpoint path, will start training from step 0...` |
| `train.checkpoint.save_async` · 异步保存 | YAML 或命令行 | 关 | 开:权重与优化器转后台写,训练继续;下一次同类保存、导出、训练结束前收尾 | `[RANK r] waiting for previous DCP save (ckpt) to end...` 出现在下一次存盘时 |
| `train.checkpoint.stage_dir` · 暂存目录 | YAML 或命令行 | 不设 | 设:先写本地盘再拷到目标,失败时旧存档完好;不能和异步同开,解析配置时就报错 | 报错 `stage_dir cannot be combined with save_async …` |
| `train.checkpoint.save_timeout_seconds` · 暂存与异步的 Gloo 超时 | YAML 或命令行 | 不设:Gloo 默认 30 分钟 | 必须是正整数;两者都没开时只打警告、不生效 | 警告 `save_timeout_seconds=… has no effect …` |
| `train.checkpoint.dcp_save_to_lowest_rank` · 复制分片交给最小 rank 写 | YAML 或命令行 | 关 | 开:复制的那份集中到最小编号的复制组写,写并行度下降;专家分片不受影响 | 各节点本地盘上的分片分布 |
| `train.checkpoint.manager` · 存取后端 | YAML 或命令行 | `dcp` | 只登记了 `dcp` 一种,且要求数据并行模式是 `fsdp2` 或 `ddp` | 启动报错 `Unsupported distributed backend …` |

**观测。** 本章看 4 处。一是存盘:每次存盘 rank 0 打 `Distributed checkpoint saved at …/model successfully!`,开异步时这行只说明交出去了,要到步目录里 `model/ckpt/.metadata` 与 `model/optimizer/.metadata` 都出现才算落盘;再看 `checkpoint_manifest.json` 里的 `global_step` 和 `world_size`。二是续训:开头依次是 `Load distributed checkpoint from … successfully!`(模型那一半)和 `Restored trainer state from …`(作业那一半,07 章),只出现前一行、后面跟着 `resuming weights only`,说明游标没接上;权重缺键时报 `DCP is missing N model key(s) required for a full-model resume: …`。三是旧格式:`Loaded pre-split checkpoint from …` 和 `Loaded job cursor from … (VeOmni 0.1.12 layout)` 说明走了兼容路径。四是导出:`Distributed HuggingFace safetensors save took …s` 表示走了分布式那条路;看到 `fqn_to_index_mapping is None, …` 说明没有索引,所有权重会写进一个文件(索引从哪来见 02 章)。离线合成的用法是 `python scripts/merge_dcp_to_hf.py --load-dir <步目录>`,可选 `--save-dir`、`--model-assets-dir`、`--shard-size`、`--mode`;专家拆分是 `scripts/moe_ckpt_merge/moe_split.py --merge_hf_path … --split_hf_path …`。

**典型配置。**

| 场景 | 怎么起 | 拿什么换什么 |
|---|---|---|
| 单轮长跑的预训练,要能中途续 | `train.checkpoint.save_steps: 500`、`train.checkpoint.load_path: auto`,`save_hf_weights` 保持默认 | 用每 500 步一次的写盘时间和不断增长的磁盘占用,换崩溃后最多丢 500 步;HF 只在结束时导出一次 |
| 输出目录在慢速共享存储上,写盘拖住训练 | `train.checkpoint.save_async: true`、`train.checkpoint.save_timeout_seconds: 3600` | 写盘和训练重叠;代价是清单可能先于分片落盘,后台写比存盘间隔慢时下一次存盘会阻塞 |
| 同样的慢速存储,但要求失败时旧存档不坏 | `train.checkpoint.stage_dir: /local_nvme`(节点本地盘) | 同步写本地再拷,拷失败旧存档完好;每节点本地盘要放得下全部 rank 的权重和优化器 |
| 多机 HSDP,各节点只写本地盘 | `train.checkpoint.dcp_save_to_lowest_rank: true` | 复制分片集中到最小编号的复制组,那台节点拿到完整一份;写入并行度下降,专家分片仍分散在各节点 |

组合与推荐值是按语义推的起点,不是实测最优。

| 症状 | 先查 | 然后 |
|---|---|---|
| `load_path: auto` 选了一个比预期更早的步 | 最新那个步目录里有没有 `checkpoint_manifest.json`,`model/ckpt/` 下有没有 `.metadata` | 缺哪一半就是那一步没存完;确认后显式指定路径,或删掉残缺的步 |
| 续训后 loss 接上了,学习率却像回到预热 | 续训卡数是否比保存时多;新增 rank 的 `model/extra_state/` 下有没有自己编号的文件 | 用原卡数续训;确实要扩卡,先接受调度器与步数重新开始 |
| 续训报 `DCP is missing N model key(s)` | 保存与续训时的模型结构是否一致,是否中途开关了 MTP 头(02 章) | 结构改了就不能严格续训;只想接权重,先离线合成 HF 再从 HF 起 |
| 训练结束导出时 rank 0 主机内存爆 | 是不是 NPU,或 PyTorch 低于 2.9 | 训练里关掉 `save_hf_weights`,事后用合并脚本分片合成 |
| 开异步后训练每隔 N 步卡一下 | 日志里 `waiting for previous DCP save` 与下一次存盘的间隔 | 拉大 `save_steps`,或改用暂存 |
| 多机暂存或异步在第一次存盘时挂住、超时 | Gloo 能否跨节点通信,网卡是否指定 | 设好 Gloo 的网卡环境变量,并把 `save_timeout_seconds` 设得比一次写盘更长 |
| 磁盘被存档塞满 | `checkpoints/` 下有多少个步目录 | 框架不清理,自己在作业外删旧步;每一步的 `optimizer/` 是大头 |

## 六、常见误区

- **以为学习率调度器存在 `model/lr_scheduler.pt`,由 rank 0 写一份。** 会这么以为,是因为官方的 checkpoint 布局文档、架构说明、约束清单和管理器的类注释都这么写,目录规则模块里也定义了这个路径。实际上这个路径没有任何调用点;调度器状态和条件模型的生成器一起,由每个 rank 写进 `model/extra_state/extra_state_rank_R.pt`,读的时候也各读各的。照文档去找这个文件、或者只拷 rank 0 那份,都会落空。
- **以为默认会按步存 checkpoint。** `save_steps` 默认是 0,默认只在每轮结束存一次,训练结束再导出一次。单轮的长作业不改这一项,中途崩了就没有任何存档可接。
- **以为给 `load_path` 指一个步目录会先检查它完整不完整。** 只有 `auto` 会检查两半标记。手工指到一个异步保存还没收尾就崩掉的步,要么在读 DCP 元数据时报错,要么只恢复权重、数据从头,取决于缺的是哪一半。
- **以为 `hf_ckpt/` 可以拿来续训,或者续训会参考它。** 续训只读 `model/`、`loader/`、`extra_state/`,导出树从不被读。想把训练结果交给别处接着训,给的应该是整个步目录,或者用 HF 权重当新作业的起点。
- **以为换卡数只影响数据游标。** 07 章讲的是作业侧游标;模型侧的附加状态也按 rank 存,扩卡后新 rank 的调度器静默不恢复。最常被略过的是续训日志里那行 `resuming weights only`——它出现时步数已经从 0 数起了。
- **以为导出 HF 会把整个模型聚到 rank 0 的显存里。** GPU 且 PyTorch 2.9 以上时,每个 rank 只写自己的分片,rank 0 在盘上拼文件;真正会整模型进内存的是 NPU 与旧 PyTorch 的退路,进的是 rank 0 的主机内存,不是显存。
- **以为两个 `extra_state/` 是一回事。** 步目录根下的 `extra_state/rank_R.pt` 是作业状态(步数、随机状态、计量器),`model/extra_state/extra_state_rank_R.pt` 是模型附加状态(调度器、生成器)。清理存档时想「只丢游标、换数据接着训」,要删的是 `loader/`,两个 `extra_state/` 都得留。
- **以为框架会只保留最近几份。** 当前没有任何保留或清理逻辑,每次存盘都是新目录,清理要在作业外自己做。
