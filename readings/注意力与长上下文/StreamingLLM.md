# StreamingLLM:训练窗口 4K 的模型,怎么跑完 400 万 token

<!-- release-date: 2023-09-29 -->

**本文依据**:`Efficient Streaming Language Models with Attention Sinks`,arXiv 2309.17453v4(2024-04-07,ICLR 2024 正式版),21 页。作者 Guangxuan Xiao 等,MIT Han Lab 主导,Meta AI、CMU、NVIDIA 合作。代码 `mit-han-lab/streaming-llm`。首发日取 arXiv v1 提交日 2023-09-29。文中所有数字都标了 PDF 页码;标「外部补充」的段落不来自本文。

## 一句话

Softmax 的分母必须凑够 1,模型于是把用不掉的注意力全倒进开头那几个 token —— 这批 token 语义上不重要,但**一旦把它们的 KV 淘汰掉,整个注意力分布就崩了**。StreamingLLM 只做一件事:滑动窗口之外,永远钉住开头 4 个 token 的 KV。代价是几乎为零的显存,收益是 400 万 token 的稳定流式生成。

**但它不扩上下文窗口。** 这句话是全文最需要记住的一句,第七节会用三组数字说明它意味着什么。

## 一、矛盾:流式部署卡在两件事上

把 LLM 放进多轮对话这类**不会结束**的场景,会同时撞上两堵墙(p1):

1. **KV cache 无限涨。** 每个历史 token 的 Key 与 Value 都要留着,显存与解码延迟一起往上走。
2. **模型外推不了。** 序列一旦超过预训练窗口(Llama-2 是 4K),质量就掉。

注意这两堵墙是**独立**的。把窗口从 4K 扩到 32K 能推后第二堵墙,但推不倒它 —— 超出 32K 照样掉;而且第一堵墙反而更高了。论文把自己明确归到「长度外推」这一类,并声明**不做**上下文扩展、也不改善模型对长文本的利用(p3)。这个自我定位是理解后面所有取舍的前提。

## 二、三种朴素解法,各卡在哪

论文用同一个模型、同一段文本把四种做法摆在一起量(Llama-2-13B,PG19 测试集第一本书 65K token,p1 图 1):

| 做法 | 复杂度 | 困惑度 | 卡在哪 |
|---|---|---|---|
| 稠密注意力 | $O(T^2)$ | 5641 | 超过预训练窗口就掉,且缓存无限涨 |
| 窗口注意力 | $O(TL)$ | 5158 | **一旦开头 token 被淘汰就塌** |
| 滑窗 + 每步重算 | $O(TL^2)$ | 5.43 | 质量好,但每生成一个 token 都要重建整窗 KV,慢到不能用 |
| StreamingLLM | $O(TL)$ | 5.40 | 见第七节 |

第二行是整篇论文的起点。窗口注意力看起来无懈可击 —— 只留最近 L 个 token 的 KV,显存恒定、速度恒定。但它塌得比直觉早得多:**不是逐渐变差,而是在「第一个 token 被挤出缓存」那一刻断崖**(p4 图 3)。5158 这个困惑度不是「差一点」,是模型已经不工作了。

第三行是唯一质量可接受的基线,也是后面比性能时的对照组。它慢的原因是窗内注意力仍是二次的,每步都要重算一遍。

## 三、attention sink:窗口注意力为什么会塌

### 现象

可视化 Llama-2-7B 全部层与头的平均注意力(256 条长度 16 的句子,p3 图 2),看到两件事:

- 最底下两层(layer 0、1)是「局部」模式,注意力给最近的 token;
- **从第三层往上,所有层、所有头都死死盯着第一个 token。**

### 为什么

论文把原因归到 Softmax 的形式上(p4 式 1):

$$
\text{SoftMax}(x)_i = \frac{e^{x_i}}{e^{x_1} + \sum_{j=2}^{N} e^{x_j}}, \quad x_1 \gg x_j
$$

Softmax 要求所有被注意的 token 权重之和为 1,**没有「谁都不看」这个选项**。当前 query 在历史里找不到真正匹配的东西时,这份注意力总得倒在某处。于是模型学会了找一个固定的垃圾桶 —— 论文给这个垃圾桶起的名字就是 **attention sink**。

淘汰掉这些 token 的 KV,等于从上面那个分母里删掉了最大的一项,**剩下所有 token 的注意力权重会被整体放大**,分布偏离训练时见过的样子。这才是窗口注意力断崖的机制,而不是「丢了重要信息」。

### 是位置,不是语义

这是论文最漂亮的一步。开头 token 重要,有两种可能:它的**语义**重要,还是模型学到了对**绝对位置**的偏好?

作者把前 4 个 token 换成换行符 `\n` 再跑一遍(p5 表 1):

| 缓存配置 | 困惑度 |
|---|---|
| 0 + 1024(纯窗口) | 5158.07 |
| 4 + 1020(原始开头 4 token) | 5.40 |
| 4 个 `\n` + 1020 | 5.60 |

换成毫无语义的换行符,困惑度只从 5.40 变到 5.60。**语义几乎不参与,起作用的是「它在开头」这个位置事实。**

至于为什么偏偏是开头:自回归的可见性是单向的,开头的 token 被后面**所有** token 看见,后面的 token 只被更后面的一小部分看见。所以开头那几个最容易被训练成 sink(p5)。

### 为什么要 4 个而不是 1 个

四个模型上做消融(p5 表 2,PG19 拼接 400K token):

| 模型 | 0 + y | 1 + y | 2 + y | 4 + y | 8 + y |
|---|---|---|---|---|---|
| Falcon-7B | 17.90 | 12.12 | 12.12 | 12.12 | 12.12 |
| MPT-7B | 460.29 | 14.99 | 15.00 | 14.99 | 14.98 |
| Pythia-12B | 21.62 | 11.95 | 12.09 | 12.09 | 12.02 |
| Llama-2-7B | 3359.95 | 11.88 | 10.51 | 9.59 | 9.54 |

**Llama-2 那一行和其余三行不一样。** 别的模型 1 个就够,Llama-2 要到 4 个才收敛(9.59),8 个再加只赚 0.05。论文的解释是:Llama-2 确实给每段前面加了 `<s>`,但那是在**切 chunk 之前**加的,切完之后落在第 0 位的往往是个随机 token —— 没有一个稳定的起始符,模型只好把这份差事摊给好几个开头 token(p5)。

所以「4 个」不是什么神秘常数,是**没有专职 sink 时的兜底冗余**。这条直接推出第五节。

## 四、StreamingLLM 做的两件事

### 第一件:缓存分两段

KV cache 拆成两块(p5 图 4):

- **attention sink** ——开头 4 个 token 的 KV,永不淘汰,只负责稳住注意力分布;
- **滚动窗口** ——最近 L 个 token 的 KV,负责真正的语言建模。

不微调,不改权重,任何用相对位置编码(RoPE、ALiBi)的自回归模型都能直接套上。

### 第二件:位置按**缓存内下标**算,不按原文下标

这一条最容易读错,也是能不能跑起来的分水岭(p5)。

假设缓存里现在装着原文的 token `[0, 1, 2, 3, 6, 7, 8]`,正在解码第 9 个:

```text
原文下标:  0  1  2  3  │  6  7  8  ← ✗ 不能这么给
缓存下标:  0  1  2  3  │  4  5  6  ← ✓ 实际这么给
           └─ sink ─┘   └─ 滚动窗口 ─┘
```

如果按原文下标给位置,相对距离会随着文本变长一路涨到模型没见过的范围 —— 那正是外推失败的老问题,等于什么都没解决。按缓存下标给,**相对距离永远被框在缓存大小之内**,模型看到的永远是它训练时见过的距离。

落到两种编码上(p5):

- **RoPE**:缓存里存的是**旋转变换之前**的 Key,每步解码时再按缓存内的位置施加旋转;
- **ALiBi**:把原本会「跳一下」的线性偏置改成连续的。

代价是 RoPE 那一路不能直接缓存最终的 Key,每步要重新旋转一次 —— 这笔开销是逐 token 的线性量,与重算整窗的二次开销不在一个量级。

## 五、预训练时留一个专职 sink

第三节末尾那个「为什么要 4 个」的答案,自然指向一个修法:**从一开始就给模型一个固定的垃圾桶。**

论文用 Pythia-160M 的代码与配方,在去重 Pile 上从零训了三个 1.6 亿参数的模型,训练 143000 步,除 batch size 降到 256 外配置完全一致(p7):

| 做法 | 0+1024 | 1+1023 | 2+1022 | 4+1020 |
|---|---|---|---|---|
| Vanilla(原样) | 27.87 | 18.49 | 18.05 | 18.05 |
| Zero Sink(SoftMax₁) | 29214 | 19.90 | 18.27 | 18.01 |
| Learnable Sink(可学占位符) | 1235 | **18.01** | 18.01 | 18.02 |

读这张表要看**第二列**:只给 1 个 sink 时谁已经到位了。

- Learnable Sink 18.01,和它自己给 4 个时一模一样 —— **一个就够。**
- Vanilla 18.49,要给到 2 个才追平。
- Zero Sink 19.90,**比 vanilla 还差**,要给到 4 个才行。

Zero Sink 就是 SoftMax₁,即在分母上多加一个常数 1、让权重不必凑满(p6 式 2),等价于在注意力里预置一个 Key 和 Value 全为零的 token。论文的措辞是它「在一定程度上缓解了问题」,但表里它在关键那一列是**倒数第一**。我的解读:**光给一个出口不够,这个出口还得能被训练**;全零的 Key 意味着它对任何 query 的打分都是常数,模型没法把它调成一个好用的垃圾桶。

sink token 的代价接近于零:预训练损失曲线与 vanilla 基本重合(p7 图 6),7 个 NLP benchmark 上的零样本成绩也没有退化(p7 表 4)。注意力图上能直接看到它在干活 —— 加了 sink token 之后,各层各头的注意力集中到这个 token 上,**其他开头 token 收到的注意力明显变少**(p7 图 7)。

论文因此建议:以后训 LLM,都在每条样本前面放一个 sink token。

## 六、它买到了什么

- **困惑度追平 oracle。** 20K token 上与「滑窗 + 每步重算」基本持平;稠密注意力超出预训练窗口即失效,窗口注意力超出缓存即崩(p4 图 3)。
- **400 万 token 稳定。** Llama-2-[7,13,70]B、Falcon-[7,40]B、Pythia-[2.8,6.9,12]B、MPT-[7,30]B 全部跑通,困惑度全程平稳(p7 图 5)。
- **22.2 倍加速。** 相对唯一可用的重算基线,单 token 解码延迟随缓存大小**线性**增长,而重算基线是**二次**的;显存占用与重算基线相当(p9 图 10)。
- **真实任务上不掉分。** 把 ARC 的问答对拼成一条流喂进 Llama-2-Chat,逐个位置判精确匹配(p8 表 5):

| Llama-2-Chat | 7B ArcE / ArcC | 13B | 70B |
|---|---|---|---|
| 单条独立跑(参照) | 71.25 / 53.16 | 78.16 / 63.31 | 91.29 / 78.50 |
| 稠密注意力 | 显存溢出 | 显存溢出 | 显存溢出 |
| 窗口注意力 | 3.58 / 1.39 | 0.25 / 0.34 | 0.12 / 0.32 |
| StreamingLLM | **71.34 / 55.03** | **80.89 / 65.61** | **91.37 / 80.20** |

窗口注意力那一行值得停一下:**准确率是个位数甚至归零**,不是「变差」而是彻底失效。而 StreamingLLM 和「每道题单独跑」持平,几处还略高。

## 七、它买不到什么

这一节比上一节重要。论文自己在附录里写得很清楚:StreamingLLM **不扩上下文窗口,也不增强长期记忆**,它只能在当前缓存里活动(p15)。三组数字把这句话的边界钉死:

**① 距离一超过缓存,准确率直接归零。** 在 StreamEval 上拉开提问与答案之间的距离(p16 表 7),缓存 4+2044 的配置在 20 行(460 token)距离上还有 85.80,距离一旦超过缓存容量就是 **0.00** ——不是缓慢下降,是断崖。

**② 长文档任务上反而不如朴素截断。** LongBench 上,官方截断基线保留开头 1750 与结尾 1750 个 token;StreamingLLM 用 4+3496 的配置**打不过它**(p17 表 8)。原因论文写明了:开头那段关键的 prompt 信息被丢了。把配置改成 1750+1750 就追平 —— 但那时候它已经不是「4 个 sink」了,而是老老实实留了 1750 个真 token。

> 这一条把第四节那个「4 个 sink 就够」的印象校正得很及时:**4 个 sink 只是占位符,不承载任何信息。** 凡是需要开头信息的任务,该留多少就得留多少。

**③ 缓存开大,困惑度不一定降。** 这是论文顺手抓到的一个更普遍的毛病(p9 表 6):

| Llama-2-7B | 4+508 | 4+1020 | 4+2044 | 4+4092 |
|---|---|---|---|---|
| 困惑度 | 9.73 | 9.32 | **9.08** | 9.59 |

缓存从 2044 涨到 4092,困惑度反而从 9.08 退到 9.59。论文给的结论是模型**没有用好它拿到的全部上下文** —— 这与 Lost in the Middle 那一支的发现同向。

所以它的适用面很窄也很清楚:**日常多轮对话、短文档问答这类只需要短期记忆的场景**;长文档问答与摘要**不适合**(p15)。

## 八、可迁移的三条

**① 「Softmax 必须凑满 1」是个会渗出来的约束。** 它不只造出 attention sink;论文提到量化离群点那边有过类似观察,SoftMax₁ 正是从那条线上提出来的(p4)。凡是遇到「某个位置的数值异常大且与语义无关」,先想想是不是某个归一化逼出来的。

**② 缓存的位置编号可以和原文脱钩。** 这是个很便宜、很少被想到的自由度:**位置编码消费的是「缓存内的相对距离」,不是「文本里的绝对位置」。** 一旦想通这一点,任何做 KV 淘汰的方案都要回头检查一遍自己的位置是怎么给的。

**③ 给模型一个显式的出口,比堵住它便宜。** sink token 的成本是一个 token,收益是把「4 个开头 token 全得留着」降到「留 1 个专职的」。但出口必须**可学** —— Zero Sink 那个全零出口反而更差。

## 九、它之后发生了什么

> 以下为**外部补充**,不来自本文。

论文自己在 Impact 一节列出它已被 NVIDIA TensorRT-LLM、Intel Extension for Transformers、HuggingFace Transformers、MLC LLM 等推理方案采用(p10)。

attention sink 这个概念本身后来长成了一条独立的研究线,本库「注意力与长上下文」方向下的 `Attention-Sink-Survey` 就是专门梳理它的综述;`Topological Trouble With Transformers` 从另一个角度讨论上下文历史的表示困难。工程侧,vLLM 的 KV cache 管理里有专门处理 sink 的那一类 full-attention manager,细节见开源解读的 vLLM 章节。

## 读完该留下的判断

- **被实验支持的**:attention sink 现象在 Llama-2、MPT、Falcon、Pythia 四族上都成立;换行符实验证明起作用的是位置不是语义;4M token 的稳定性与 22.2 倍加速有完整数据。
- **是作者的推断而非证明的**:「Softmax 必须归一」是 attention sink 的**成因** —— 这是一个很有说服力的解释,但论文给的是现象与相关证据,没有给因果实验。Zero Sink 的失败其实对这个解释构成了一点张力:如果单纯是归一化逼出来的,那么放开归一化就该解决,而实际没有。
- **没有公开的**:sink token 的验证只做到 1.6 亿参数(p7),**大模型上从零重训带 sink token 会怎样,论文没有做**。这是「建议以后都这么训」这条主张里最薄的一环。
