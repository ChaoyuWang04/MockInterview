# 检索优化

一句话:检索优化管的是**从"查询进来"到"候选交给生成器"之间的一整段**——把正确证据既捞得上来、又排得靠前、还得在延迟预算内。它的主线不是堆技术,而是先判断证据在哪一层丢了,再只改那一层。

## 一、先定位:证据是在哪一层丢的

查询侧是一条四级流水线:**查询改写 → 召回 → 重排 → 上下文组装**。

这条流水线有一个决定一切的性质:它是**单调收窄**的。后一级只能从前一级的输出里挑,**永远补不回前一级漏掉的东西**。这就是"reranker 救不回漏召文档"的全部原因——重排只是把已有候选换个顺序,召回阶段没进候选集的文档,再强的模型也变不出来。

诊断动作很朴素:准备一批真实 query,人工标出"能支持答案的那些文档块"(下称 gold),然后逐级看 gold 还在不在。

| 症状 | 说明丢在哪一层 | 该改什么 |
|---|---|---|
| 知识库里根本没有 gold | 数据 | 补数据。这时候调相似度、换模型都是白费 |
| gold 没进 top-K 候选 | 召回 | 查询改写、混合检索、切块粒度、过滤条件是否写错 |
| gold 进了候选但排在几十名开外 | 排序 | 融合权重、加 reranker |
| gold 排到第一但答案还是错 | 上下文 / 生成 | 去重、版本冲突、压缩删了限定词、模型没忠于证据 |
| 召回一大堆但整体相关性差 | 先别下结论 | **先看 gold 在不在候选里**:在 → 排序问题;不在 → 召回问题 |

最后一行是高频追问「召回很多但相关性差怎么排查」的正解。因为"多而不准"有两种病因完全相反,一种要改排序、一种要改召回,搞反了整轮优化都白做。第二步再查过滤条件——租户、语言、时间窗、权限写错会**在打分之前**就把 gold 剔掉,这类问题在相似度分数上完全看不出来。指标怎么定义、离线线上怎么对齐,见 RAG评测 篇;本篇只用到"gold 有没有进 top-K"这一个验收动作。

### Retriever 的输入输出不只是一句话

- **输入** = query + 过滤条件(租户、语言、时间窗、文档权限)+ 对话历史。权限必须在检索层就生效,不能指望取回来再过滤——那等于已经把不该看的内容读出来了
- **输出** = 一组候选,每条带**正文、分数、文档 ID、来源与元数据**。分数用于融合与阈值,来源用于生成时的引用溯源;只吐一堆裸文本的 retriever,后面所有环节都做不了事
- **和 Generator 的分工**:Retriever 决定证据的**上限**,Generator 决定这个上限能兑现多少。所以两边必须分开评测——检索命中率和答案忠实度掉的是两口井

## 二、Retriever 怎么工作:离线编码一次,在线只编码 query

稠密检索用的是**双塔(Bi-Encoder)**:文档一个编码器、query 一个编码器,各自压成一个向量,相似度就是这两个向量的点积或余弦。整条路径拆成两段——离线:全库文档过文档塔编码一遍,灌进向量索引;在线:query 过查询塔编码,拿这一个向量去索引里取 Top-K。

**文档塔为什么能离线缓存?** 因为文档向量的计算**只依赖文档本身,和 query 无关**。全库一百万个块,离线跑一遍编码器存下来就行,之后不管来多少 query 都不用重算。在线剩下的只有两件事:把这一句 query 编码成一个向量(一次几十 token 的前向),再去索引里找最近邻。

这条"与 query 无关"的性质,正是第六节 Cross-Encoder **不能**离线预计算的镜像——记住这一对照,双塔和交叉编码的所有差异都能从它推出来。

**索引和向量数据库不是一层概念**:HNSW、IVF、PQ 是**索引数据结构**,负责"别把一百万个向量都算一遍";向量数据库是**服务系统**,负责持久化、元数据过滤、增删改、多租户和高可用。面试里把两者混着说会被追问。索引结构本身见 Embedding 篇;FAISS 这类索引库与向量数据库的工程边界、以及增量更新与一致性,见 切块与索引 篇。

### 多级索引:每一层只负责一件事

| 层 | 干什么 | 用什么 | 设计原则 |
|---|---|---|---|
| 过滤层 | 把搜索空间砍到"合法且相关的子集" | 标量/倒排索引上的元数据条件 | 只做硬约束(权限、租户、时间窗),**宁可宽不可错** |
| 粗召层 | 从子集里捞出几百条候选 | BM25 + ANN 双路 | 高召回、低精度、便宜 |
| 精排层 | 把几十条排准 | Cross-Encoder 或 LLM | 高精度、高成本,只看很少的条数 |

原则一句话:**上层只负责别漏,下层只负责排准**。上层用错手段(比如在过滤层就上高精度模型)既慢又会提前丢 gold。

### 一次在线检索的延迟大概花在哪

口径:单卡 GPU、base 规模(约 100M 参数)编码器、候选正文约 512 token、百万到千万级向量库。这是**数量级**参考,不是 benchmark。

| 阶段 | 量级 | 随什么增长 |
|---|---|---|
| query 编码 | 几毫秒 | query 长度(很短,基本恒定) |
| ANN 检索 + 元数据过滤 | 几毫秒到几十毫秒 | 库规模、索引参数、过滤选择性 |
| Cross-Encoder 重排 50 条 | 几十到一两百毫秒 | **候选数 × 候选长度,线性** |
| 上下文组装(去重、截断) | 通常 10 ms 以内 | 上了压缩模型才会变贵 |

对照一下:重排 50 条 512-token 的候选,等于让编码器吃掉约 2.6 万 token,和一次两万多 token 的 prefill 同量级。所以**重排往往是查询侧最大的那笔开销**,而不是向量检索。

## 三、BM25:词法检索到底在算什么

BM25 是**带词频饱和与长度校正的词法打分函数**,靠倒排索引查得飞快。

$$
\operatorname{score}(D,Q)=\sum_{q\in Q}\operatorname{IDF}(q)\cdot\frac{f(q,D)\,(k_1+1)}{f(q,D)+k_1\left(1-b+b\,\dfrac{|D|}{\operatorname{avgdl}}\right)}
$$

读法:对 query 里每个词分别打一份分再相加。每份分 = **这个词有多稀有**(IDF)× **它在这篇文档里出现得有多密**(那个分式)。$f(q,D)$ 是词频,$|D|$ 是文档长度,$\operatorname{avgdl}$ 是全库平均长度。

### k1 和 b 开大开小分别会怎样

- **$k_1$ 控制词频多快饱和**。分子分母里 $f$ 同阶,所以 $f \to \infty$ 时整个分式趋近 $k_1+1$——**词频的贡献有天花板**。$k_1$ 越大,饱和越慢,词频的差异保留得越多;$k_1 \to 0$ 时退化成"出现过就满分"的布尔匹配。Lucene / Elasticsearch 默认 1.2
- **$b$ 控制长度归一化强度**,取值 0 到 1。$b=0$ 完全不看长度;$b=1$ 按 $|D|/\operatorname{avgdl}$ 全额归一化。**为什么需要它**:长文档"碰巧包含查询词"的概率天然更高,不校正就会系统性偏袒长文档。但 $b$ 太大会误伤本来就该长的文档(完整的 API 文档页、长政策条款)。Lucene 默认 0.75
- **RAG 里的一个实际结论**:切块之后每块长度已经比较接近,$\operatorname{avgdl}$ 周围方差很小,$b$ 的作用被大幅削弱,所以从默认值往下调常常没什么坏处。但这仍要在自己的标注集上验,没有通用最优值
- **调参的前提比参数本身重要**:必须固定分词、字段、停用词和切块策略再去搜 $k_1, b$,否则你以为在调 BM25,其实在调分词器

### 和 TF-IDF 的关系,以及两个变体

| 维度 | 朴素 TF-IDF | BM25 |
|---|---|---|
| 词频 | 线性或对数,**无上界** | 饱和函数,上界 $k_1+1$ |
| 长度 | 靠向量归一化(余弦)间接处理 | **显式且带可调旋钮 $b$** |
| IDF | $\log(N/n)$ 一类 | 概率型,常带 0.5 平滑 |

IDF 的口径差异是真会踩的坑:经典 Robertson IDF 在词出现在过半文档时会变成负数,Lucene 改写成 $\ln\!\left(1+\frac{N-n+0.5}{n+0.5}\right)$ 保证恒正。**所以跨引擎比 BM25 分数没有意义**,只能比排序。

- **BM25F**:多字段(标题/正文/标签)加权。关键在于它是**先把各字段的词频加权合成一个伪词频,再进饱和函数**,而不是各字段算完分再相加——后者会让同一个词在每个字段里各饱和一次,等于变相放大
- **BM25+**:给每个命中词的贡献加一个常数下界。解决的是长度归一化对超长文档惩罚过度,导致"命中了但分数低到近乎没命中"

**BM25 在 RAG 里的价值**:专有名词、型号编号、报错码、数字、刚出现的新词——这些稠密检索最容易翻车的地方,BM25 只要倒排里有就能精确命中,而且不需要训练、天然抗领域漂移。

## 四、稀疏 + 稠密:为什么要混,怎么混

| | 稀疏检索(BM25/SPLADE) | 稠密检索(双塔) |
|---|---|---|
| 怎么匹配 | 离散词项 + 倒排索引 | 向量空间里找近邻 |
| 擅长 | 精确词、编号、数字、稀有实体、**新词** | 同义改写、口语化提问、概念相似 |
| 翻车在哪 | 用户换了说法就一个词都对不上 | 领域偏移时误召回;否定词、数字、精确约束容易被压没 |
| 可解释性 | 好(能指出命中了哪个词) | 差(只有一个相似度) |

**为什么要混:两边失手的地方几乎不重叠。** 新词最典型——embedding 模型没见过这个词,tokenizer 把它切成碎片,向量会落到一个和真实含义无关的位置;而 BM25 只认倒排表里有没有这个词,完全不受影响。长尾 query 同理。反过来,用户用同义词提问时 BM25 一个词都命中不了,只能靠稠密路兜。

### 三条融合路线

**1. RRF(倒数排名融合)**——只用名次,不用分数:

$$
\operatorname{score}(d)=\sum_{i}\frac{1}{k + r_i(d)}
$$

$r_i(d)$ 是文档 $d$ 在第 $i$ 路结果里的排名,$k$ 是平滑常数(原论文取 60)。$k$ 的作用是压住头部:没有它的话第 1 名和第 2 名的权重差一倍,加了 60 之后差距被拉平,**低排名文档的影响也不会完全消失**。前提是各路排序质量大致可比;好处是**完全不需要校准**,两路分数尺度差多少都无所谓;代价是丢掉了"第一名强多少"的信息——一个断崖式命中和一个勉强命中在 RRF 眼里一模一样。

**2. 分数归一化后加权**:$\alpha \cdot \text{norm}(s_\text{dense}) + (1-\alpha)\cdot \text{norm}(s_\text{sparse})$。前提是两路分数被拉到同一尺度。坑在于 min-max 通常是**批内**归一化——同一个文档在不同 query 下的归一化分数不可比,所以基于它设的绝对阈值,一旦候选分布变了就失效。BM25 的原始分无上界、随语料统计漂移,更不能跨 query 直接比。

**3. 学习融合 / 排序**:把两路排名、原始分、query 类型、文档特征喂给一个小模型学权重。前提是有足够标注且线上分布不会漂太快,否则收益会被维护成本吃掉。

### 权重不该是一个全局常数

不同 query 类型的最优权重方向相反,一个常数必然委屈一边。可行做法是先做一次轻量 query 分类(含编号、型号、引号、报错码 → 偏稀疏;自然语言长问句 → 偏稠密),按类切权重。**验收必须按 query 切片分别看**——自然语言 query 通常占多数,总体指标会把实体类 query 的退化平均掉,看不见。

**Embedding 和业务领域不匹配时,检索侧能先做的止血**:提高稀疏路权重;用领域词典做查询归一化,把内部黑话映射成文档里的写法。根治要靠领域微调,那属于 Embedding 篇,训练目标与负例机制见 对比学习 篇。

**两类索引的成本形状不同**:BM25 的开销主要在建倒排索引和词典,查询是稀疏点积;稠密路的大头是**离线把全库编码一遍**,加上向量占的内存(768 维 float32 = 3 KB 一块,百万块约 3 GB)。稠密路在线不一定比 BM25 慢,取决于维度、索引类型和过滤方式。

## 五、查询改写:三种手段,三种代价

| 手段 | 干什么 | 什么时候有用 | 代价 |
|---|---|---|---|
| 规则归一化 | 统一缩写、产品名、时间、实体写法 | 永远该先做 | 几乎为零,但要维护词表 |
| 多视角改写 | 生成 n 条同义 query 并行检索再合并 | 用户措辞和文档措辞对不上 | 检索次数 ×n,候选集变大,重排跟着变贵 |
| HyDE | 先让 LLM 编一段"假设的答案文档",拿它的向量去检索 | 问句和文档形态差距大 | 多一次 LLM 生成(几百毫秒量级),**会放大错误前提** |
| 子问题分解 | 把多跳问题拆成几步依次检索 | 单次检索不可能命中的组合问题 | 轮次串行相加,**错一步全错** |

**HyDE 为什么有用**:query 是短问句,文档是长陈述,两者在向量空间里是**两种文本形态**,直接算相似度属于跨形态匹配。HyDE 先把 query 变成"文档形状",跨形态就变成了同形态。

**HyDE 什么时候放大错误**:模型不知道答案的 query——私域数据、公司内部信息、最新事件。它会编出一段看起来很合理的假文档,向量落进错误的语义区域,把真正的 gold 挤出候选。前提本身就错的 query 同样危险("X 的退款期是不是 30 天?"——模型会顺着这个假设写)。所以 **HyDE 必须并联而不是替换**:原 query 那一路保留,HyDE 作为额外通道,最后融合。

**怎么保证改写不改变原问题**:

1. **改写只能加,不能替**——原 query 始终作为一路参与召回,改写结果只是额外通道。这一条兜住了绝大多数事故
2. 约束改写模型只做"补上下文、加同义词",禁止引入原文没有的实体和限定条件;同时记录改写前后的对应关系,出问题时能一眼看出是不是改写把问题改坏了
3. 多轮对话额外要做指代消解("它"→上一轮的实体)和省略补全,否则第二轮 query 单独看根本没有检索价值

**多跳检索**就是分解的执行形态:检索 → 从结果里读出中间答案 → 用它拼下一个 query → 再检索。它的代价在第八节按 Agent 的口径细算。

## 六、重排:Cross-Encoder 贵在哪、值在哪

| | Bi-Encoder(双塔) | Late Interaction(ColBERT 类) | Cross-Encoder |
|---|---|---|---|
| 怎么算 | 各压成一个向量再点积 | 文档每个 token 一个向量,在线做 MaxSim | query 和文档拼成一条序列一起进模型 |
| 文档能否离线 | ✅ 一块一个向量 | ✅ 但存储涨到"每 token 一个向量" | ❌ 完全不能 |
| 在线成本 | 一次 query 前向 + ANN | 中等 | **候选数 × 一次前向,线性增长** |
| 用在哪 | 全库召回 | 中间层召回/重排 | 只在几十条候选上重排 |

所以**Reranker 不等于 Cross-Encoder**,late interaction 是另一个精度—成本折中点。

**Cross-Encoder 为什么更准**:query 和文档在**每一层 attention 里都能互相看见**。双塔是各自压成一个向量再见面,全部交互被压缩进最后那一次点积——这就是双塔容易漏掉否定("不支持 X"和"支持 X"向量很近)、漏掉数字、以及漏掉"整篇不相关但有一段正好回答问题"的原因。

**为什么不能预计算**:它的输入是 (query, doc) 这个**对**,文档的表示依赖于 query,而 query 在线才知道。和第二节双塔那条"文档向量与 query 无关"正好相反。

**能不能直接用 LLM 重排**:能(RankGPT 一类把候选列表塞进 prompt 让模型输出顺序),优点是零样本、能理解复杂指令;缺点是延迟高一个量级、有位置偏差(候选在列表里的顺序会影响结果)、成本按 token 计。更常见的用法是**离线拿它造训练数据**,再蒸馏到小 reranker。

**和推荐系统的精排不是一回事**:RAG 重排只判断"这条能不能支持回答这个问题",是纯文本相关性;推荐精排优化的是点击/转化,输入里有大量用户侧和场景特征,相关性只是其中一个信号。

### 训练数据怎么造

- **正例**:真能支持答案的块——不是"字面上和 query 像"的块
- **易负例**:随机抽的其他文档,让模型先学会基础的主题区分。不能全是难负例,否则模型的打分标定会偏
- **难负例**:必须从**线上召回器的 top-K 里取**。因为 reranker 上线后只会见到"召回器认为不错的那些",训练分布得和它一致。用随机负例训出来的模型,典型症状是离线指标漂亮、上线一点不涨
- **假负例**:top-K 里没被标为正、但其实相关的块。直接当负例会把模型教坏。缓解手段:只取排名区间内的负例(避开最靠前那几条)、用更强的模型或人工抽查过滤、给负例打软标签而不是硬 0
- **数据来源**:人工标注(准但贵)、点击日志(量大但有**曝光偏差**——用户只能点他看得见的,没曝光的文档永远拿不到点击)、公开集(起步用)、教师模型伪标签
- **目标函数**:pointwise(每条独立打分,简单但没学到相对关系)/ pairwise(学"A 比 B 好",最贴排序目标)/ listwise(直接优化整列表指标)。下游只取 top-3 时,pairwise 或 listwise 更对味
- **数据质量怎么评**:标注一致性、正例的"真支持率"抽查、负例里的假负例比例抽查;最实在的一条是**换一版数据训,看离线排序指标和端到端答案质量是不是同向变化**——只有离线涨、端到端不动,通常就是训练分布和线上对不上

难负例的**挖掘算法**(迭代式 ANN 挖掘、批内负例)属于 对比学习 篇。

### 候选数、延迟,和"重排后还是不好"

**候选数 N 怎么定**:N 越大,gold 在里面的概率越高(这是召回上界),但重排成本线性增长、噪声也变多。方法是画 Recall@N 曲线找拐点——曲线基本走平之后再加 N 就是纯烧钱。同理,过滤阈值只在模型、数据和分数校准都不变时才有意义(见第四节)。

**在线延迟怎么压**:两级重排(先用小模型砍到 1/5,再用大模型精排)、蒸馏小 reranker、截断候选长度(成本随 token 数走)、按 query 难度动态决定要不要重排。

**重排后仍不好,接着往哪查**:回到第一节的诊断表。gold 不在候选里 → 召回的锅;gold 在且排到了前面但答案错 → 上下文或生成;gold 在但就是排不上去 → 要么训练分布和线上候选不像,要么这类 query 的判据模型压根没学过(比如"要最新的那一条才算对"——这不是文本相关性问题,得靠元数据排序补)。

**Reranker 和 Embedding 联合训练**:利是目标一致,难负例挖掘可以共用一套数据工程,reranker 还能当 teacher 蒸馏给双塔;弊是**embedding 一变,全库向量要重新编码并重建索引**,而换 reranker 是零成本热切换——耦合训练会把这个不对称的代价绑在一起。工程上通常保持解耦,只共享数据管线。

## 七、候选到上下文:去重、冲突、压缩、动态粒度

- **去重**:多路召回加上重叠切块,很容易产出几乎一样的块。不去重的后果是宝贵的上下文预算被同一句话占了三遍。按文档 ID + 文本指纹去,或按相似度阈值合并
- **冲突**:同一问题的新旧两版文档给出不同答案,**检索分数解决不了这个**——分数只看相关,不看谁对。要靠元数据(时间、版本、来源可信度)显式排序,并把时间戳一起写进 prompt
- **位置**:证据被塞在长上下文正中间时更容易被忽略(即"lost in the middle"),所以最强的证据放最前或最后,别按检索顺序随便铺
- **压缩**:用小模型或规则删掉与 query 无关的句子,省 token 效果明显。风险是**删掉限定条件**——"本政策仅适用于 2024 年前签约用户"这种句子在压缩模型眼里像废话,删完之后答案会从"部分正确"变成"自信地答错"。验收时要单独看带限定条件的那批 query
- **动态粒度**:检索用小块(语义集中,向量更准),喂模型时把命中块的**前后邻居或所属父块**一并带上,补回被切断的上下文。本质是把"检索粒度"和"阅读粒度"解耦。切块策略本身见 切块与索引 篇
- **候选太多或太少**:太多 → 噪声上升,先压缩再截断,同时把 top-K 调小;太少甚至为空 → **不要用低分候选凑数**,因为一条不相关证据足以诱导模型顺着它编。宁可少给,或者直接走第八节的降级路径。至于让生成器按固定 schema 吐出引用字段,那属于解码侧,见 解码策略 篇

## 八、Agent 场景:多轮检索的延迟与正确率

Agent 把"一次检索"变成"一轮里检索若干次,而这样的轮次有好几个"。带来两个新问题:

1. **延迟从一次相加变成沿路径累积**。按第二节的量级,单次检索链路 150–300 ms、一次生成几百毫秒到数秒,5 轮工具调用的下界就已经是好几秒。所以 Agent 里检索优化的重点不是把单次做到极致,而是**减少轮次**和**让能并行的并行**
2. **多了一类失败模式**:上一轮检索到的错误证据被写进上下文,污染了下一轮自动生成的 query,错误一路滚下去

| 手段 | 怎么做 | 不能违反的约束 |
|---|---|---|
| 缓存 | 缓存 query → 候选 | key 必须带**租户 + 权限集合 + embedding 模型版本 + 索引数据版本**,缺一个就会串号或返回陈旧结果 |
| 并行 | 无依赖的检索同时发出 | 多跳的后一跳依赖前一跳的中间答案,不能并 |
| 限步 | 给检索次数设上限 | 触顶时要有明确行为(问澄清 / 给部分结果),不能静默截断 |
| 降级 | 检索为空或全低分时启用 | **不能退回"凭参数知识硬答"**,那正是幻觉的来源 |

**缓存命中率和知识新鲜度直接冲突**。可用的折中是按数据变更频率分层设 TTL(静态文档长 TTL,高频更新的短 TTL 或干脆不缓存),并在底层数据版本号变化时整体失效那一层。**多 Agent 共享检索结果时,权限必须是 cache key 的一部分,而不是取出来之后再过滤**——后者只要有一条代码路径忘了过滤就是越权,而且很难测出来。

**证据和参数知识冲突**:默认以检索证据为准,因为参数知识没有时间戳、不可溯源。但要分两种情况——证据之间互相冲突,按元数据定优先级;证据和模型常识冲突,来源可信就信证据,同时把冲突显式说出来。最不能接受的是模型悄悄用参数知识覆盖了证据,却还照样附上引用。**检索质量极差时的降级顺序**:反问澄清 → 给出有依据的部分结果并标明缺口 → 明确说"没找到依据"。三者都比编一个答案强。

**怎么量化 RAG 优化对端到端的影响**:一次只改一个环节、固定其他,然后看**任务成功率**而不是检索指标。"检索指标涨了但任务成功率不动"是很常见的现象,它说明瓶颈本来就不在检索。分层指标体系与实验设计见 RAG评测 篇。
