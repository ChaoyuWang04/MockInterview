# GraphRAG

一句话:GraphRAG 是**在离线阶段把实体和它们之间的关系抽成一张图、再按社区层级预先写好摘要**的一条 RAG 路线——它补的是普通向量 RAG 的一个结构性缺口:块与块之间的关系从来没进过索引。代价是建图要对全库跑一遍 LLM,所以它不是升级版,是一个贵的专用索引。

## 一、它补的是普通向量 RAG 的哪个洞

普通向量 RAG 的索引单元是**独立编码的块**:每块各自压成一个向量,块和块之间没有任何连接。检索就是"在这一堆互不相干的点里挑最像 query 的 K 个"。

这个形状决定了有两类问题它天生做不好。

**一是全局归纳**——"这批材料主要讲了哪几件事""这家公司这两年的争议集中在哪"。**这里的困难不是"漏召回",而是问题形状不匹配**:答案不存在于任何一个块里,它是几十上百篇文档共同支撑出来的。加大 K 也不解决:K 开到 200,你只是把 200 个块塞进上下文让模型现场归纳,既超预算,又是**抽样**——向量相似度会优先挑"措辞最像问题的块",而不是"最能代表全库分布的块"。

**二是多跳**——"A 公司现任 CTO 之前在哪家公司做过什么"。第一跳(A 公司 → CTO 是谁)和第二跳(那个人 → 他的履历)的证据常常在不同文档里,而第二跳那篇文档里可能压根没出现"A 公司"这四个字。**它和原始 query 在向量空间里不像**,一次检索捞不到。

GraphRAG 的思路一句话:**把"关系"和"跨文档的归纳结构"提前在离线算好,变成可检索的索引对象**。在线做不到的事挪到离线做——它所有的好处和所有的代价,都从这一句推出来。

## 二、图怎么建:四步,每一步都在花钱

链路是固定的四步。注意最后一列:**成本形状全都是"随语料线性增长的 LLM 调用"**,这和普通建库"每块过一次 embedding 小模型"差着两三个数量级。切块、元数据、建库链路这些通用机制见 切块与索引 篇,本节只讲图特有的部分。

| 步骤 | 干什么 | 典型失败 | 成本 |
|---|---|---|---|
| 实体关系抽取 | 对每个块跑抽取 prompt,吐出实体(名字、类型、描述)和关系(头、尾、描述、强度) | 漏抽、粒度不一致、关系措辞每次都不一样 | 块数 ×(1 + 追补轮数)次 LLM 调用 |
| 消歧与合并 | 把同一个真实对象的多种写法并成一个节点,合并它们的描述 | 该合的没合(图碎了)、不该合的合了(两个对象混成一个) | 规则和向量聚类便宜,LLM 复核按候选对数收费 |
| 落库 | 节点表、边表、原文块,以及各自的向量 | 边丢了证据出处,下游无法核查 | 存储,可忽略 |
| 社区检测 + 逐层摘要 | 把图切成层级化的社区,自底向上给每个社区写一段摘要 | 摘要脱离原文,变成无从追溯的断言 | 社区数量级的 LLM 调用,层数越多越贵 |

### 抽取:不稳是常态,只能靠约束压住

同一段文本连抽两次结果多半不完全一样,这是**生成式抽取的固有性质**,不是 bug。三条压制手段:**先固定实体类型表**(规定只抽人物、机构、事件、地点这几类,否则模型会自己发明类型);**结构化输出加低温度**;**多轮追补**(微软 GraphRAG 里叫 gleaning——第一遍抽完再追问一句"还有没有漏的",轮数可配)。追补能明显提升抽全率,但每一轮都是全库再过一遍,token 成本按轮数翻倍。

**每条实体和关系必须带证据出处(它出自哪个块)。** 这是真题要点里"不能只存模型生成的摘要"的原因:没有出处的边在下游就是一句不可验证的断言,错了也查不出来——第六节会看到它怎么被放大。

### 消歧与合并:两个方向的错,代价不一样

同一个人可能写成"张三""张总""Zhang San";不同的人也可能同名。可行的流水线是**归一化 → 别名表与字符串相似 → 实体描述的向量聚类 → 高价值类型交给更强的模型或人工复核**。

两类错误的危险程度不对称:**该合的没合**只是把图切碎,邻域扩展走不到该走的地方,症状是"漏",还算好查;**不该合的合了**会把两个对象的事迹拼进同一个节点,之后所有邻域扩展、社区摘要、多跳路径都在这个假节点上继续长,答案会**言之凿凿地错**。所以合并这一侧要保守,并且**记录合并前的实体身份以便回滚**。实体消歧作为一个可训练任务,它的输入输出与数据集设计见 SFT 篇。

### 存成什么:图数据库不是必需品

三种形态都能用:图数据库(方便写多跳遍历)、关系表里的节点表加边表(规模不大时够用)、列式文件加向量库(微软 GraphRAG 的参考实现走这一路,产物是实体、关系、社区、社区报告等几张表,不强制上图数据库)。

判据是**你的多跳查询有多复杂**:只扩一两跳,任何存储都做得了;要跑真正的路径搜索或图算法,才值得上图数据库。但有一条不能省——**实体描述和社区摘要都要各自建向量索引**。因为查询入口仍然是语义匹配:用户不会报实体 ID,你得先靠向量找到"从哪个实体出发"。索引结构本身见 Embedding 篇。

### 社区检测与逐层摘要:Global Search 的前提

**社区**就是图里彼此连得密、和外面连得稀的一撮节点,类比一下就是"一个圈子"。Leiden 是常用算法,它优化**模块度**(社区内部的边比随机情况多出多少);相比更老的 Louvain,它保证**社区内部是连通的**——Louvain 会产出内部断成两半的社区,那种社区摘要出来就是两件不相干的事凑一段。

它是**层级**的:顶层几个大社区对应粗粒度主题,往下逐层细分。摘要**自底向上**做:底层社区的摘要由它的实体、关系和证据生成,上层社区的摘要再由子社区的摘要压一层。

**为什么必须摘要,不能直接把子图丢给模型?** 因为一个社区背后的原文可能是几十万 token,塞不进任何上下文;而一张裸的节点边列表模型读起来也没有叙述性。摘要把"一坨子图"变成**一段可检索、可直接当证据用的自然语言**。这一步做完,"全库有哪些主题"才第一次变成一个能在有限预算内回答的问题。

## 三、怎么查:Local 与 Global 是两条不同的路径

| | Local Search | Global Search |
|---|---|---|
| 入口 | query 向量匹配**实体描述**,找到起点实体 | **不找实体**,直接取某一层的**全部**社区摘要 |
| 沿什么走 | 从起点实体扩邻域:相邻实体、连接它们的关系、关联的原文块、所属社区摘要 | 不走图,把摘要打乱切成批 |
| LLM 调用 | 1 次 | **map 阶段每批一次(可并行)+ reduce 一次** |
| 上下文里装什么 | 按 token 预算排过优先级的混合证据(实体 + 关系 + 原文) | 各批要点汇总、排序、截断后的结果 |
| 适合 | "X 是什么""X 和 Y 什么关系""X 有哪些下游" | "主要主题是什么""争议集中在哪""整体趋势如何" |
| 翻车在哪 | 起点实体找错就全错;扩不到没抽出来的关系 | 贵;细节被摘要抹平,问具体数字容易答不准 |

两条路径的差异必须讲透,只说名字接不住追问。

**Local 的本质是"以实体为锚的邻域取证"。** 它和普通 RAG 最大的不同不是换了个索引,而是**它能把措辞完全不像 query 的证据拉进来**——只要那段原文和命中实体之间有一条边。普通向量检索做不到,因为它只认相似度。

**Global 的本质是"读摘要而不是找证据"。** 它压根不做检索:不筛、不排序、不取 top-K,而是把某一层的社区摘要**全部**读一遍,map 阶段让模型从每批摘要里提取带评分的要点,reduce 阶段按分数排序、截断到预算内、再汇总成答案。**这就是它能答全局问题的原因**(覆盖是完整的,不是抽样的),**也是它贵的原因**(成本正比于那一层的摘要总量,而不是 K)。

**层级是唯一的成本旋钮**:选高层,摘要少、粗、便宜;选低层,摘要多、细、贵。微软的实现里还有一个介于两者之间的 DRIFT Search——先用社区摘要给 query 做扩展、生成若干追问,再落到局部检索。

**图检索不取代向量检索。** 实体名写错、query 偏语义、或者要的就是一段精确原文时,普通混合检索更稳。工程上常见的形态是先做一次轻量的 query 路由(点查 / 关系查 / 全局归纳),分别送到不同通道再融合;融合方式与查询改写见 检索优化 篇。

## 四、多跳:在图上走 vs 拆成多次向量检索

图上的落地方式很朴素:**锚定起点实体 → 沿边扩 k 跳 → 把路径上的边和它们的证据块一起喂给模型**。

强在三处:① 边是**离线建好**的,在线只是遍历,不需要多轮 LLM 推理;② 中间实体不用模型自己猜出来,顺着边就到了;③ **路径本身就是可展示的证据链**,能回答"你凭什么这么说"。

弱在三处:① **扇出是指数级的**,2 跳就必须设预算上限,一个被广泛提及的实体 1 跳就能带出几十个邻居(和代码调用图扩几跳是同一个问题,见 切块与索引 篇);② **图里没有的边永远走不到**,而向量检索至少还有语义兜底;③ 抽错的边会拼出一条**看起来严丝合缝的假路径**。

拆成多次向量检索(分解子问题 → 检索 → 读出中间答案 → 拼下一个 query)则正好相反:不用建图、不受抽取质量限制,但**轮次是串行的,错一步全错**,而且每一跳都要一次 LLM 读取。查询分解本身见 检索优化 篇。

判据:**多跳问法固定、实体类型有限、同一批关系被反复问 → 建图划算**,因为一次性投入被摊薄了;**问法开放、语料小、多跳 query 占比低 → 拆检索更省**。

## 五、代价账:两笔钱要分开算

**离线**这一笔是大头,而且是**一次性大额投入,随语料线性增长**:抽取是块数 ×(1 + 追补轮数)次 LLM 调用;摘要是社区数量级的调用,层数越多越贵;消歧介于两者之间。一个论文口径的参照:约 100 万 token 的播客语料,用 gpt-4-turbo、600 token 窗口建图跑了 **281 分钟**(单机加公开 API,论文自报;换模型和并发后差别很大)。对照普通向量 RAG 的离线只是过一遍 embedding 模型——**"每块一次 LLM 生成"和"每块一次小模型前向"差两三个数量级**。

**在线**分两种。Local 和普通 RAG 同量级,只多一次图遍历,毫秒级;**Global 高一个数量级以上**,因为要读一层的全部摘要、发多次 map 调用再 reduce。论文给过一个对照:根层社区摘要做一次全局问答约 **2.7 万** context token,而"直接对全部原文做 map-reduce 摘要"的基线要约 **101 万**,少 97% 以上。但口径要看清——**那个基线是全库摘要,不是 top-K 向量检索**;和后者的几千 token 相比,Global Search 依然贵得多。

控成本就三条:**社区摘要必须离线算好并缓存**(绝不能查询时现算)、**用 query 路由把 Global 只留给真正的全局问题**、**限制社区层级与 map 批数**。整机的成本配置与降级策略见 RAG系统设计 篇。

**另外,GraphRAG 的重量是可以调的。** 微软那套(全量抽取 + 层级社区 + 逐层摘要)是最重的一档;LightRAG 省掉逐层社区摘要,改成实体级与主题级的双层检索,主打更便宜、更容易增量更新;HippoRAG 则把多跳交给图上的个性化 PageRank 一次传播完成,不做多轮 LLM 推理。**先问清"我要的是全局归纳还是多跳",再决定要不要付社区摘要这笔钱**——这两件事的成本完全不同。

## 六、抽取错了怎么发现、怎么修

先分清三类错:**漏抽**(图碎、邻域扩不到)、**错抽**(假边)、**粒度不一致**(同一概念一会儿是实体、一会儿是属性)。

**不需要标注、可以天天跑的结构体检**:孤立节点比例、度分布(极高度节点常常是消歧合并过头)、社区数量与大小分布(社区特别多说明图太碎)、同名实体簇大小、**边的证据出处缺失率**(这一项应该恒为 0)。

**需要模型或人工的三种手段**,按性价比排:

1. **重复抽取比一致率**。同一批块抽两遍比差异——差异大说明 prompt 或类型表不稳,该先修抽取而不是修图。这个"多次投票的一致率"本身就可以当**置信度**用。
2. **回原文核验**。每条边都能指回它的证据块,把(边,证据块)交给一个更强的模型判"这段话支不支持这条关系",低分的抽出来人工看。
3. **人工闸只加在高价值类型上**。人名、机构、金额、日期、法条这几类错了后果最重,值得白名单和人工审核;给所有边都加人工审核不现实。

置信度怎么用比它本身更重要:**低置信的边可以留在图里当候选,但不参与社区摘要和多跳路径**。因为**错误在图上会被放大**——一条假边先影响社区划分(把不该在一起的节点拉进同一个社区),再被写进社区摘要变成一句**脱离原文的自然语言断言**,然后被 Global Search 当成事实读出去。等它变成摘要里的一句话,原始的错早就查不到了。这就是"必须保留出处、不能只存摘要"的完整理由。

修的时候优先做轻的:**边级黑名单 + 重跑受影响社区的摘要**;确实是抽取 prompt 或类型表的系统性问题,才值得全库重抽。

## 七、增量更新:哪些能局部改,哪些必须全量重跑

前提是建图时就存好**块 ↔ 实体/边的双向映射**,否则一份文档改了,你根本不知道该动图里哪几个节点(和"删一份敏感文档要能反查所有派生物"是同一个道理,见 切块与索引 篇)。

真正的难点是**局部改动可能改变社区结构**:新增一条跨社区的边,可能让两个社区并掉;而社区摘要是自底向上做的——**底层社区一变,它所有祖先层的摘要全部作废**。所以重算范围要分三档:

| 变的是 | 重算范围 |
|---|---|
| 实体描述、边的证据补充,不动拓扑 | 只重算该实体所属最底层社区的摘要 |
| 新增或删除边(尤其跨社区的边)、批量新增文档 | 在受影响节点的邻域上重跑社区检测,变动的社区**及其全部祖先层**重写摘要 |
| 换抽取模型、改实体类型表、语料大批量翻新 | **全量重跑**。抽取模型一换,实体粒度和关系措辞就和旧图不是一个体系,混着用等于图里有两套标准——和换 embedding 模型必须全量重编码是同一类问题,见 切块与索引 篇 |

第二档要不要继续往上扩,可以看**社区成员变动比例**是否越过阈值:没越过就只重写那几个社区,越过了就把这一层整个重算。

一致性上有一条硬规则:**图、社区划分、社区摘要、向量这四份派生物必须同版本**,查询时读同一个版本号,**绝不允许新摘要配旧社区划分**。落地方式和普通索引一样,是"主图 + 增量层 + 别名切换"。

频率上要接受一个事实:**社区检测和逐层摘要是批处理,天然做不到分钟级**。常见折中是**分速率更新**——实体和边实时写进增量层,让 Local Search 立刻能用;社区与摘要按小时或天重算,Global Search 允许滞后,并把这个滞后明确告诉使用方。

## 八、什么时候不该用 GraphRAG

这是选型题必须给的结论。四种场景直接劝退:

- **语料小**(几百篇以内):全库摘要或者干脆长上下文塞进去更便宜,建图的一次性投入摊不薄
- **问题都是点查**("这条条款怎么写的""这个错误码什么意思"):答案就在单个块里,图带不来任何东西
- **实体关系稀疏**(操作手册、FAQ、API 文档、代码):抽出来的边少而且都是弱关系,社区划分基本是噪声
- **预算紧或更新极频繁**:建图成本和"图/社区/摘要必须同步"的复杂度都吃不下

还要认一个公开评测的诚实结论:已有系统性评测报告 **GraphRAG 在很多真实任务上并不优于普通 RAG**(arXiv:2506.05690),对照评测的结论则是**两者各有所长、组合起来最好**(arXiv:2502.11371)。所以默认顺序应该是:**先把普通 RAG 的切块、混合检索、重排做扎实**,只有当"归纳类 / 多跳类"问题确实答不了,才引入图。

一个可操作的决策动作:拿一批真实 query 分成点查、关系查、全局归纳三类统计占比,**后两类合计不到一两成,基本不值得建图**。真要上线,按五项分别对比:答案质量、证据可追溯率、建图成本、更新时延、单次查询的 token 与延迟(指标定义与错误归因见 RAG评测 篇;整机链路与垂直领域治理见 RAG系统设计 篇)。

最后划清一条容易混的边界:**GraphRAG 用的是显式的实体关系图加文本摘要,检索走图遍历和文本匹配**;TransE、RotatE、GNN、GAT 那一路是把图**嵌进向量空间**做链接预测和节点表示,属于知识图谱表示学习,是另一套方法,本篇不展开。
