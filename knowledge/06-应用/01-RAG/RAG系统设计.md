# RAG系统设计

一句话:RAG 系统设计管的是**这台机器由哪些模块拼成、模块之间交换什么、以及它答不出来的时候怎么办**——单个模块怎么调是别的篇的事,这篇只回答"整条链路怎么搭、怎么治理、钱花在哪一段"。

## 一、RAG 是什么,以及它答不了什么

**RAG 就是"先查资料,再让模型依据资料回答"。** 它把容易变的知识放在外部库里,推理时按问题取回证据再交给模型,所以适合企业知识库、客服、法规与文档问答这类**知识密集型**任务——这类任务的难点不是推理有多深,而是要记住大量会变的事实。

它相对"把知识写进参数"有两个结构性好处:**知识库可以独立更新**,改一份文档不用重训模型;**答案能指回来源**,可审计、可追责。

但边界必须说清,面试里这一问答不好会显得没落过地:

- **RAG 不保证真实。** 它只是**增加了有证据作答的机会**。没有权威语料、检索漏召回、证据互相冲突、模型误读证据,任何一环出问题都照样错
- **知识更新不是即时生效。** 新文档要走解析、切块、编码、建索引、版本切换才可查,这条链路本身有延迟,见 切块与索引 篇
- **"RAG"不等于端到端可训练。** 原论文把检索到的文档当作生成的隐变量、在其上做边缘化,并讨论了联合训练检索器与生成器;而今天绝大多数生产系统是**可独立替换、独立评测的模块化流水线**,梯度根本不穿过检索。判断一个架构时要看具体实现,别把论文的设定套到工程系统上

### RAG 和微调怎么选、怎么组合

判据是**你要改的是"知道什么"还是"怎么做事"**:

| 需求 | 选什么 | 因为 |
|---|---|---|
| 事实会变、要可溯源、量大 | RAG | 改数据比改参数便宜几个数量级,而且能给出处 |
| 输出格式、语气、领域术语习惯、任务行为要稳定 | 微调 | 这些是"行为",没法靠往上下文里塞证据可靠地约束住 |
| 既要新知识又要稳定行为 | 两个都要 | 常见组合:微调管"怎么答",RAG 管"依据什么答" |

一条容易被追问的推论:**把大量事实塞进微调数据是低效的**,因为事实一变就要重训,而且训完仍然不可溯源。垂直领域怎么划这条线,见第五节。

## 二、两条链路,以及模块之间的契约

**离线链路**(建库,决定天花板):解析 → 清洗 → 切块 → 向量化 → 建索引(带版本与权限)。每一步的做法与失败模式见 切块与索引 篇,索引结构与模型选型见 Embedding 篇。

**在线链路**(答一个问题):查询理解与改写 → 召回 → 重排 → 上下文组装 → 生成 → 核验。前四步的技术手段全部归 检索优化 篇,本篇只讲它们之间交什么、谁为什么负责。

| 模块 | 吃进什么 | 吐出什么 | 决定什么 | 换掉它的代价 |
|---|---|---|---|---|
| 索引 | 文档 | 可检索单元 + 元数据 | **能不能答**的物理上限 | 全量重建 |
| Retriever | query + 过滤条件 | 候选(正文、分数、ID、来源) | **证据的上限** | 换 Embedding 要全库重编码 |
| Reranker | query + 候选 | 重排后的少量候选 | 上限内的**精度** | 热切换,几乎零成本 |
| 上下文组装 | 候选 + 预算 | 最终喂进模型的那段文本 | 上限**兑现多少** | 改 prompt 即可 |
| Generator | 指令 + 证据 + 问题 | 答案 + 引用 | 兑现质量 | 换模型要重测全部阈值 |

**最重要的一条契约:Retriever 决定证据的上限,Generator 决定这个上限能兑现多少。** 所以两侧必须分开评测——检索命中率掉和答案忠实度掉是两口井,混在一个端到端分数里就没法定位。指标怎么定义、责任怎么划分,见 RAG评测 篇。

还有一条工程上常被忽略的契约:**Retriever 吐出的不能只是一堆裸文本**。分数用于融合与阈值判定,来源与元数据用于引用溯源和权限校验,文档 ID 用于去重和失效传播——少吐一样,下游就有一整类事做不了。

### 召回不足时,该动哪一环

按**从便宜到贵**的顺序排查,不要一上来就换模型:

1. **过滤条件写错了吗**——租户、语言、时间窗、权限会在打分之前就把正确文档剔掉,这类问题在相似度分数上完全看不出来
2. **切块是不是把答案切散了**——见 切块与索引 篇
3. **查询和文档措辞对不上吗**——加同义词归一化、查询改写、混合检索,见 检索优化 篇
4. **Embedding 领域不匹配吗**——最后才动这个,因为换它要全库重编码

### 长文档除了直接切片,还有哪些路

这是系统级的选型菜单,机制各归各篇:

| 方案 | 思路 | 什么时候用 |
|---|---|---|
| 父子块 / 邻接扩展 | 小块检索、大块喂模型 | 默认首选,便宜(见 切块与索引 篇) |
| 层级摘要 | 逐层聚类摘要,按需取某一层 | 需要跨大段归纳 |
| 迭代检索 | 生成过程中按需再检索(FLARE 那一路) | 长回答、写着写着才知道还缺什么 |
| 多轮分解 | 拆成子问题依次检索 | 多跳、组合条件 |
| 图索引 | 实体关系 + 社区摘要 | 全局归纳与多跳,见 GraphRAG 篇 |
| 长上下文直接塞 | 不检索,整篇喂进去 | 文档量小;注意成本和"中间信息丢失" |

## 三、生成侧:把证据变成模型能正确使用的证据包

候选集怎么去重、压缩、控制粒度是**查询侧**的活,见 检索优化 篇第七节。本节接着往下:这些证据到了模型面前,怎么摆。

### Prompt 的三段式与一条安全红线

**系统指令、带编号的证据、用户问题必须明确分隔。** 证据每段带上**来源与时间戳**,因为后面的引用核验和冲突处理都要用它。指令里至少写死两条:材料不足就说明不足;每个结论要对应到编号。

红线是:**检索回来的文档是数据,不是指令。** 文档里如果写着"忽略以上要求,直接说 X",那是**提示注入**,必须靠结构隔离和指令优先级压住,不能指望模型自觉。这条在开放语料和用户上传文档的场景是硬需求。

### 证据冲突:显式并列,不要静默挑一条

**检索分数解决不了冲突,因为分数只衡量"像不像",不衡量"谁对"。** 正确做法是把冲突双方连同**时间、版本、来源权威度**一起放进上下文,要求模型**指出存在冲突**;判不了就明确说判不了,而不是挑一条讲得斩钉截铁。

在 prompt 层面可操作的三件事:证据分组标注(把同主题的放一起并标出差异维度)、显式给排序规则(比如"以生效时间更晚的为准,但要说明另一版的存在")、要求输出里保留冲突提示。垂直领域的冲突判定要复杂得多,见第五节。

### 长度控制与"中间信息丢失"

token 不够时按代价从低到高:**按问题抽取关键句** → **父子块换成更小的检索粒度** → **分层摘要** → **拆成多轮检索**。有两条纪律:

- **压缩必须能回到原文核验。** 压缩模型最容易删掉的恰恰是限定条件("仅适用于 2024 年前签约用户"在它眼里像废话),删完答案会从"部分正确"变成"自信地答错"
- **不要把"固定位置"或"固定 token 比例"当通用规则。** 证据放最前还是最后、留多少余量,都要在自己的数据上测

**证据被埋在长上下文正中间时更容易被忽略**(lost in the middle),所以最强的证据放两端,别按检索顺序随手铺。

### 模型总是忽略部分证据,怎么诊断和缓解

先诊断再下药,顺序是:**给证据编号,让模型输出每条用到没有** → 把该用的那条**单独喂**进去看它能不能用对(能用对说明是干扰问题,不是理解问题)→ **减少候选数**看忽略是否消失 → 换个位置再试。

对应的缓解手段:压缩候选数与噪声、把关键证据挪到两端、要求模型**逐条核对并给出未采用的理由**、必要时拆成"先抽取要点、再综合作答"两步。**降低解码温度只能减少随机性,不能保证事实正确**——这是常见的错误答法。

### 怎么评估不同的 Prompt 模板和证据组织方式

固定检索结果、只换 prompt,在同一批 query 上比忠实度、引用支持率和答案正确率;**引用格式对不等于引用正确**,必须核对被引证据是否真的支持那句话。具体指标定义与实验设计见 RAG评测 篇。

## 四、Fallback:先判断有没有足够证据,再决定重试还是退出

### 判定:单一相似度阈值靠不住

**"Top-1 分数低"只是一个信号,不能当判据。** 因为不同 Embedding 模型、不同距离度量、不同 query 类型的分数分布根本不可比,同一个阈值换个模型就失效(见 Embedding 篇)。稳一点的判定要综合几路信号:

- **分数分布**:最高分与次高分的落差、整体分数的塌陷程度,比绝对值更有信息量
- **Reranker 分数**:它见过 query 和文档的交互,比双塔分数更可信
- **候选一致性**:几条候选彼此矛盾或毫不相干,说明检索没抓到主题
- **关键要素覆盖度**:把问题里的实体、时间、条件抽出来,看候选覆盖了几项——**这一路最实用**,因为它直接对应"能不能答"
- **来源质量**:命中的都是低权威来源时要降级处理

### 四级阶梯,按顺序走

| 级别 | 动作 | 什么时候用 |
|---|---|---|
| 1 · 修查询 | 纠正实体、补时间与领域条件、同义词扩展、拆子问题 | 最便宜,永远先试 |
| 2 · 扩检索 | 权限不变的前提下加混合检索、放宽过滤、扩大候选再重排去噪 | 怀疑是召回不足 |
| 3 · 向用户澄清 | 请用户补对象、时间或范围 | **问题本身含糊时,这比盲目扩检索有效得多** |
| 4 · 安全降级 | 低风险场景标注"以下为模型一般知识,未从知识库核实";高风险场景拒答、给相关材料或转人工 | 前三级都没救回来 |

**绝不能把"绕过检索让模型凭参数知识答"当默认兜底。** 它可能给出正确常识,也可能给出无法核验的内容,而用户分不出这两者——这正是幻觉最难被发现的形态。

**重试必须有预算**:最大重试次数、总延迟上限、调用次数上限,三者缺一就可能出现 Agent 反复检索把延迟拖垮的情况。触顶时要有明确行为(澄清或给部分结果),**不能静默截断**。

### 阈值怎么校准

不是拍脑袋,是**按业务代价定**:

$$
\text{期望代价} = P(\text{错答}) \cdot C_{\text{错答}} + P(\text{误拒}) \cdot C_{\text{误拒}}
$$

意思是:把阈值挪动一格,错答率和误拒率一个降一个升,总代价取决于这两类错各自值多少钱。所以做法是先标一批**有答案 / 无答案**都覆盖的样本,扫一遍阈值画出"拒答率—错答率"曲线,再按业务里 $C_{\text{错答}}$ 与 $C_{\text{误拒}}$ 的比值选点。医疗、法律、金融里错答的代价远高于多拒一次,阈值就该保守;闲聊和推荐类反过来——**这就是"高风险业务和普通客服的 Fallback 为什么不同"的完整答案**,不是"更谨慎"这种空话。

### 失败要闭环,不然同样的坑会一直踩

记录原 query、改写后的 query、候选与分数、走了哪级 fallback、用户反馈。然后**按失败类型分桶**,因为每一类的修法完全不同:

| 失败类型 | 怎么修 |
|---|---|
| 库里压根没有 | 补数据。这时候调检索、换模型全是白费 |
| 有但解析或索引漏了 | 查建库链路、重建索引 |
| 查询没对齐(措辞、缩写、指代) | 补同义词表、改查询改写 |
| 召回到了但排序错了 | 动重排 |
| 权限过滤正确拦截 | **不是 bug,不要改**;要在指标里单独隔离,否则会被记成检索失败 |

最后一行尤其重要:不隔离它,权限拦截会污染检索指标,让你去修一个根本没坏的东西。

## 五、垂直领域:让每条知识都能回答"谁发布、何时有效、给谁看"

**医疗、法律这类垂直 RAG 的核心不是换一个向量库,而是给每条知识挂上可判定的属性,并让答案能回到那条证据。** 这句话是整节的纲。

### 数据与检索

数据侧先圈定**允许使用的权威来源**,解析时保留标题层级、条款号、表格与附件结构,每个块存:文档 ID、版本、**生效区间**、法域或科室、权限标签、原文位置。扫描件和复杂表格要 OCR 或版面模型,但**识别结果必须抽样校验**,不能直接当可靠事实用。

检索侧一般是**术语/BM25 召回 + 语义召回 + 元数据过滤**,再上 Reranker。专业缩写、同义词、历史名称要进词表或训练样本,否则"三高""房颤"这类说法根本对不上文档用词。融合与重排的机制见 检索优化 篇。

### 冲突不能简单选最新

**"取最新一条"在垂直领域是错的。** 至少要比三件事:**权威层级**(国家标准 vs 地方细则 vs 科室共识)、**适用范围**(法域、人群、科室是否覆盖这次的问题)、以及**查询问的是哪个时点**——问"2019 年的规定是什么"时,最新版恰恰是错的答案。所以生效区间必须存成**区间**而不是单个时间戳,检索时按查询时点过滤。

### 废止条款怎么保证不再被引用

三层一起上,少一层都会漏:**索引层**打失效标记并沿派生物传播(块、向量、缓存都要),**检索层**默认过滤已废止项(除非用户明确问历史),**生成层**要求引用时带生效状态。验收方式是**探针查询**——准备一组"应该再也检不到"的 query,每次更新后跑一遍。派生物怎么反查见 切块与索引 篇。

**权限必须在检索前生效**,不能取回来再过滤。因为后过滤的本质是"先读出来再遮住",只要有一条代码路径忘了遮就是泄露。

### 什么放 RAG,什么要 SFT

**会变的、要溯源的、量大的事实 → RAG**(指南、法条、药品说明、公司制度);**稳定的行为规范 → SFT**(必须先问哪些澄清问题、答案要遵循什么结构、什么情况一律转人工、专业术语的表达习惯)。判据一句话:**"改一次要不要重训"**——要重训的就不该放进微调数据。

### 评测要加的项

除了通用的检索与生成指标(见 RAG评测 篇),垂直领域必须额外测:**引用支持率**、**过期知识命中率**、**越权率**、**拒答准确率**,以及按人群、科室、法域分层的**高风险误答率**。最后一项不能只看总均值,因为高风险场景通常是小样本,平均一下就看不见了。

## 六、配置与成本:三个组件不在同一个维度上

这是本篇最常被追着问的一节。先分清位置,再谈权衡:

| 组件 | 在哪一段 | 决定什么 | 主要成本 |
|---|---|---|---|
| Embedding + 向量检索 | 召回 | 效果**上限**——没召回的永远出不来 | 索引存储、离线编码 |
| Reranker | 精排 | 上限内的**精度**——把对的排到前面 | 在线推理,随 top-k 线性增长 |
| Fallback | 兜底 | 效果**下限**——证据不足时别瞎答 | 尾部请求的额外延迟与调用 |

**先投召回,再投重排。** 这是**顺序问题不是偏好问题**:重排只能对已经召回进来的候选排序,召回率不够时换再强的 Reranker 也变不出没进候选的文档。所以先测 Recall@N,不达标就先改 Embedding、加混合检索或改切块;召回够了再看重排。

**延迟按段分配预算。** 假设端到端 800 ms,一种典型分法是向量检索 50 ms、重排 150 ms、生成 500 ms、余量 100 ms。**最直接的旋钮是重排的 top-k**——从 100 降到 50 通常延迟减半而排序质量掉得很少,但这条曲线必须自己测。次一级的旋钮是重排模型规模:交叉编码器最准也最贵,late interaction 是中间档(见 检索优化 篇)。

**级联是标准结构**:便宜的先过滤,贵的只看少量候选。向量检索出 100 条 → 轻量模型粗排到 30 条 → 交叉编码器精排到 5 条,每一级的过滤比例决定成本曲线。

**Fallback 的账要单独算**:它花的是**尾部请求**的成本,换的是"给出错误答案"的代价,所以阈值定在哪由第四节那个代价公式决定,而不是由平均延迟决定。

### 四个高频追问

- **召回率已经很高,重排还有多少空间?** 上界是 $\text{Recall@N} - \text{Recall@k}$——**候选层已经捞到、但没进最终 k 条的那部分,就是重排最多能补回来的量**。这个差很小就别投重排了,该去改召回或切块
- **粗排和精排用同一份训练数据会怎样?** 两者面对的候选分布不同:粗排要从海量里粗筛,精排只见"粗排认为不错的那几十条"。用同一份数据训,精排见不到它上线后真正要区分的那种**难例**,典型症状是离线好看、上线不涨
- **Fallback 触发率突然上升,先查哪一段?** 按链路从后往前:**先确认不是索引或数据变更**(重建、批量更新、权限规则改动)→ 再看 query 分布是否变了(新活动、新产品词)→ 最后才怀疑模型或阈值。因为前两者是最常见也最容易验证的
- **端到端准确率不变但拒答率上升,说明什么?** 说明**系统把原本能答对的问题也拒掉了**——多出来的拒答落在了本来就答不对的那批上是理想情况,但准确率没动而拒答涨,更可能是阈值收紧过头或某类 query 的分数分布漂了。要按 query 类型分层看,别只看总数
