# Embedding

一句话:Embedding 是**把离散对象压成一串数,并让「距离近」这件事对某个任务有意义**的表示——意义全部来自训练目标,不是向量自带的;向量索引则是在「必须准」和「必须快」之间做的一笔交易:只搜一部分数据,换延迟和内存。本篇负责表示本身与文档库场景的向量索引。

## 一、Embedding 到底是什么

**它不是降维,是被训练目标塑造出来的。** 最常见的误解是把 Embedding 当成「把稀疏高维压成稠密低维」,但压缩只是副作用:一个随机初始化、从没训过的 embedding 矩阵同样稠密同样低维,它的余弦相似度却毫无意义——因为从没有任何损失函数要求过「相似的东西要靠近」。

由此有一条贯穿全篇的判据:**向量距离的语义,只在训练目标定义的那个任务下成立**。用问答对训出来的检索模型,「近」的含义是「这段文字能回答这个问题」;用改写句对训出来的模型,「近」的含义是「这两句在说同一件事」。拿后者做问答检索,会把一堆措辞相近但答非所问的段落排到前面。这也是第五节「不要只看榜单」的根。

和 one-hot 的关系则是**数学等价、工程与表达力都不等价**。对一个 ID 类对象,查表和「one-hot 乘 embedding 矩阵」结果完全相同:

$$
\mathbf{e}_i = \mathbf{x}_i^{\top} W, \qquad \mathbf{x}_i \in \{0,1\}^{|V|},\ W \in \mathbb{R}^{|V| \times d}
$$

意思是:$\mathbf{x}_i$ 只有第 $i$ 位是 1,乘上 $W$ 之后**恰好是把 $W$ 的第 $i$ 行取出来**。既然结果一样,工程上为什么一律用查表?因为词表常是十万量级:显式构造 one-hot 要为一个词分配十万个数、做十万次乘法,其中 99999 次乘的是 0;查表把这件事变成一次内存寻址,反向传播也只更新被用到的那几行。更关键的差别在表达力:one-hot 里任意两个词彼此正交、余弦恒为 0,「猫」和「狗」跟「猫」和「螺丝刀」一样远;而 $W$ 的行被梯度一起推着走,共现或配对关系会把它们拉近。**one-hot 只是编号,Embedding 是编号加上了关系。**

## 二、三类表示的分野

| 表示 | 怎么学出来的 | 向量随语境变吗 | 适合什么 |
|---|---|---|---|
| Word2Vec / GloVe | 从语料的**词共现统计**学每个词型一个固定向量 | 不变 | 资源紧张的词级任务;「苹果」在水果和公司两种语境下是同一个向量 |
| BERT 的 token 表示 | 掩码语言建模,每个位置由**双向上下文共同决定** | 变 | 抽取、序列标注、分类;但 `[CLS]` 没有为余弦检索优化过 |
| SBERT / SimCSE 等句向量模型 | 在编码器上做 pooling,用**句对或对比目标**直接训句子相似度 | 一句一个向量 | 语义搜索:文档可离线编码、缓存、进 ANN 索引 |
| CLIP 类双塔跨模态模型 | 图像塔与文本塔双向对比,两模态压进同一空间 | 一图/一句一个向量 | 图文互搜、零样本迁移(机制见 对比学习 篇,视觉侧见 视觉编码器 篇) |

这张表也决定了 OOV、歧义词、领域漂移该怎么答,因为**这三件事在三类表示里根本不是同一个问题**:

- **OOV**:静态词向量遇到词表外的词只能给 UNK;现代模型走子词切分,生僻词被拆成若干子词拼出表示,严格意义的 OOV 基本消失,但**拆得太碎会让专名的表示变差**(切分机制见 Tokenizer 篇)。型号、药名、代码标识符尤其吃这个亏,这也是必须配一路 BM25 做精确匹配的原因之一。
- **歧义词**:静态词向量把所有义项挤成一个向量,天然解决不了;上下文表示和句向量由整句决定,歧义主要靠上下文消解。真正剩下的坑是**短 query**——「苹果 售后」这种三五个字上下文太少,得靠改写补齐(见 检索优化 篇)。
- **领域语义偏移**:通用模型没见过「这个批号是否合规」这类领域内的相关性定义,表现为召回的都是措辞像但业务上不相关的段落。只能靠领域数据微调或换领域模型,调参救不回来。

## 三、句向量怎么取出来:pooling 与归一化

### 为什么裸 BERT 的 `[CLS]` 直接做余弦检索会差

1. **训练目标压根没要求过这件事**。掩码语言建模优化的是「预测被遮住的词」,`[CLS]` 是留给下游分类头再训一层用的;没有任何一步要求「两个语义相近的句子,`[CLS]` 夹角要小」。第一节那条判据在这里直接兑现。
2. **表示空间各向异性**。BERT-flow 那篇的观察是:预训练语言模型的表示挤在一个狭窄锥形区域里,任意两句的余弦都偏高且彼此接近,**区分度被整体压掉**;词频还会影响词向量的分布密度,高频功能词把句子表示往一起带。
3. **尺度不可比**。没经过对比目标训练的向量范数分布很散,内积会被长向量主导。

所以补救方向是把「相似要靠近」写进目标:SBERT 用句对监督微调,SimCSE 用同一句过两次 dropout 造正对做对比训练,或者做后处理式白化。**关键不是换 pooling,是换目标**——只改 pooling 不训练,提升非常有限。

**mean pooling 还是 CLS pooling?** 判据只有一条,而且最容易答反:**跟着模型发布时用的那种走**。SBERT 系列大多用 mean pooling 训练,BGE、E5 这类不少用 `[CLS]`;换一种等于用了一个从没被训练过的读出方式,分数会明显掉。只有自己从头微调、两种都能训时才谈得上比较:mean pooling 每个 token 都有贡献、默认更稳,但**必须按 attention mask 加权平均**,否则 padding 把向量拉向零,而且文本越长越把关键句稀释成「这段的大致意思」;CLS pooling 读出便宜,但要求训练时确实把句子级信息汇聚到了那个位置。

L2 归一化则把向量投到单位球面上,于是**内积直接等于余弦相似度**。三个好处:模型没法靠「把向量拉长」抬高所有相似度(这条捷径与语义无关);相似度被钉在 $[-1,1]$,温度和阈值才有稳定含义;索引里存归一化后的向量,内积索引和余弦索引就是同一套。**但阈值仍不可跨模型搬**——「余弦大于 0.7 算命中」换个模型就失效,因为每个模型的余弦分布本身不同。归一化对训练动态的影响见 对比学习 篇。

## 四、维度、序列长度与成本

**维度高不保证更准**,因为**维度是容量上限,不是信息量**。信息由训练数据和训练目标决定,维度只决定「最多能装多少」;数据信号撑不满时,多出来的维度装的是噪声。而且高维下距离对比度会下降——随机点对之间的距离趋于接近,「最近邻」这个信号本身变弱,PQ 的每个子空间还要承担更多维度、量化误差更大。实践里 384/512 维的小模型在很多垂直库上打得过 1536 维的大模型,是常态不是反常。

成本这边则是确定要涨的(以 1000 万条 1024 维为例):

| 存法 | 每条向量 | 1000 万条合计 |
|---|---|---|
| fp32 原始向量 | 4096 B | ≈ 41 GB |
| fp16 原始向量 | 2048 B | ≈ 20 GB |
| 每维 1 字节的标量量化 | 1024 B | ≈ 10 GB |
| PQ,切 64 段每段 8 bit | 64 B | ≈ 640 MB |
| HNSW 图边(`M`=32,邻居 ID 4 字节) | 底层约 256 B,叠加在向量之上 | ≈ +2.6 GB |

暴力距离计算也与维度成正比,一次 1024 维内积是 512 维的两倍。这张表还藏着一个反直觉、第十二节要用的结论:**图边在 fp32 原向量面前只多 6%,在 64 字节的 PQ 码面前却是它的 4 倍**——一旦压了向量,内存瓶颈就从向量翻到图上。真需要一个模型同时支持长短向量,可以用 Matryoshka 式训练,让前 $k$ 维本身就是一个可用的短向量;**普通模型的向量不能随便截断**,那是硬丢掉几个维度。

**序列长度**这一头,编码成本随长度按注意力的平方涨,而超出最大长度的部分**直接被截断**、对向量零贡献——这就是长文档必须切块的直接原因。另一头是精度:一块塞得越长,向量越是「这一整块的平均意思」,定位越糊。切多长、怎么切、父子块怎么做,见 切块与索引 篇。

## 五、选型与评测:用自己的数据说话

**不要拿榜单名次当选型依据。** MTEB、BEIR 这类基准的价值是划出候选范围、检查零样本迁移能力,不是替你做决定:榜单的任务分布、语言、文本长度和相关性定义都不是你的,而且公开榜单存在训练数据与评测集重叠的风险,名次和你库上的表现常常对不上。

正确动作是先花半天建一个**目标数据集**:从真实日志取几百条 query,人工标出相关文档(标不动就先标「够用的那一条」),然后分两层看。检索层看 **Recall@K**(该捞的有没有捞回来)、**MRR**(第一条正确答案排第几)、**nDCG**(多档相关性下的排序质量),K 要按下游真正塞进上下文的条数取——评 Recall@100 但线上只用 Top-5 是自欺欺人;下游层看同一套检索结果喂给生成模型后的**回答质量**,检索指标涨了而回答没变好是常见现象,说明瓶颈在别处(指标体系见 RAG评测 篇)。

同时要量的工程指标:向量维度、最大输入长度、编码吞吐、显存与存储、ANN 召回率、端到端 P95 延迟。中文与垂直领域另外必查四件事:切词与子词切分对专名的破坏程度、缩写别名(「三高」「CPI」)能不能对上、实体型号的精确匹配、长文档的分块表现。

还有一条常被答错:**ANN 检索不能笼统写成 $O(1)$ 或「保证毫秒级」**。它仍要遍历图或扫描桶、随机访问候选向量,主要成本往往是**随机访存**而不是浮点运算;延迟取决于 `efSearch` / `nprobe`、向量在不在内存、以及并发压力。百万级以上的常规做法是文档塔离线编码入库、查询塔在线编码,ANN 粗召回后再用更强的交互式模型重排(重排见 检索优化 篇)。

## 六、DPR 与 Contriever:训练信号的区别

两者结构是同一套:**双编码器(双塔)**,query 和 passage 各自独立编码,用内积比相似度。这个结构的全部价值在于**文档向量可以离线算好、缓存、进索引**——像交叉编码器那样把 query 和文档拼起来一起过模型就没法预计算,百万级库根本查不动。差别在训练信号:

| | DPR | Contriever |
|---|---|---|
| 训练信号 | 开放域问答的**问题–正 passage 人工监督对** | **无标注文本**上的对比预训练 |
| 正对怎么来 | 标注给的 | 从同一篇文档里独立裁两段当正对(论文比过逆完形填空,发现随机裁剪更稳) |
| 负例怎么来 | batch 内其他问题的正例 + BM25 挖的难负例 | MoCo 式动量队列,负例来自之前若干批,数量与批大小解耦 |
| 强在哪 | 训练分布贴近目标问答任务时最直接 | 没有相关性标注时的起点,跨域迁移好 |
| 弱在哪 | 吃标注量,对正例定义与负例质量敏感 | 不保证在所有目标域赢过监督模型,也不保证赢过 BM25 |

选型判据一句话:**有几千条以上贴近线上分布的标注对,走 DPR 这条监督路;没有标注,先用 Contriever 这类无监督起点顶上,同时开始攒标注。** 两者不互斥,Contriever 训完照样可以用领域数据微调。

### DPR 的负样本与 batch 内负例的偏差

DPR 论文考察了三类负例:语料随机抽的段落、BM25 返回的高分但不含答案的段落、以及同一批里别的问题的正例(即 batch 内负例);**最优配置是 batch 内负例加一条 BM25 难负例**。这个组合便宜有效,但 batch 内负例带三重偏差:

1. **分布偏差**(最要命):候选全是「某个问题的标注正确答案」,天生是被人挑过的高质量段落;线上要面对的却是全库几百万条从没被标注过的普通段落。模型练的是「从一批好段落里挑一个」,考的是「从全库里排除掉海量平庸段落」。ANCE 那条路线正是针对这点——用定期刷新的 ANN 索引从**全库**挖负例,让训练分布贴近推理分布。
2. **假负例**:同一批里出现语义等价的问题时,它的正例对我其实也是正例,却被当负例推开,**批越大撞上的概率越高**——这一条和第 1 条方向相反,一个嫌批内候选太容易,一个嫌批越大越容易误伤。
3. **难度不可控、候选数被批大小绑死**:批内负例难不难全看这一批随机撞上了什么,不是挑出来的;想要更多负例只能加大 batch,而 batch 又受显存限制。Contriever 用动量队列、ANCE 用全库挖掘,都是为了把「负例数量」和「批大小」解绑。

### 没有相关性标注时怎么训、怎么评

训练侧走三条弱信号:文档天然结构(标题–正文、摘要–全文、同文档内两段)、行为日志(点击、加购)、以及用更强的模型造伪标签(让 LLM 依据段落生成问题,或用交叉编码器打分再蒸馏)。**伪标签必须抽样人工审查并报误标率**,否则是在把一个模型的偏见固化进检索器。评估侧:先用 BEIR 这类零样本基准确认没跑偏,再用少量人工标注的目标域集合定版本,同时用无标注也能算的代理信号(Top-1 与 Top-10 的分数差、召回结果重复率)做日常监控。

## 七、检索场景的对比训练怎么落地

Embedding 微调的损失基本是两族:一族是**候选间竞争**(InfoNCE 这类,让 query 在一批候选里认出正例),一族是**相对间隔**(Triplet 这类,只要求正例比负例近一个 margin)。顺手澄清一个常被问的关系:前一族本质就是**把这一批候选当类别做的一次 softmax 交叉熵**,所以「对比损失」和「交叉熵」不是互斥的两类。两族的数学形式、梯度怎么分配、温度的机制、难负例挖掘的方法论,见 对比学习 篇,那篇是主负责篇;这里只讲检索场景独有的落地问题。

先记一个最常见的实现事故:**相似度和距离方向相反,符号不能混写**。用距离时写 $[\,d(a,p)-d(a,n)+m\,]_+$,改用余弦相似度就必须整个翻过来写成 $[\,s(a,n)-s(a,p)+m\,]_+$。写反了 loss 照样会降,只是降的是错的那一头。

**正例按业务定义,不按文本相似度定义。** 问答检索的正例是「能回答这个问题的段落」,哪怕它和 query 一个字都不重;去重任务的正例是「表达同一件事的另一句」;推荐召回的正例是真实发生的正反馈。同一个库换个业务目标,正例集合就得重造——第一节那条判据的直接后果。

**难负例必须先核实它真的不相关。** 检索场景最典型的假负例是:BM25 或上一版模型挖出来的高分负例,其实同样能回答这个问题——把它推开等于在教模型「正确答案要排后面」。三条可操作的发现手段:用更强的交叉编码器或 LLM 复核难负例,分数高的挑出来人工看;先做近似去重(同一篇文档的重叠切块、转载的重复正文最容易命中);盯**一问多答**的情况,一个 query 有多个正确段落时,标准单正例形式会把其余正确答案当负例,正确做法是换多正例目标,或把已知相关的候选从分母里屏蔽掉。

**温度、归一化和难例比例要一起调,而且按检索验证集选,不按训练 loss 选。** 温度控制的是高相似度负例在这一批里拿到多大权重,调小越集中在最难的那几个上,所以它和难例比例是同一个旋钮的两半(机制见 对比学习 篇)。训练 loss 跨配置不可比:批大小一变候选数就变,温度一变 logits 尺度就变,loss 降了可能只是题变简单了。判据是在**独立的、贴近线上分布的**检索验证集上比 Recall@K 与 MRR。优先级也要记住:**温度替代不了数据质量**——假负例满地的数据集,调温度只能在「被噪声带偏」和「学不动」之间挑一个。

## 八、向量索引:一笔「少搜一点」的交易

倒排索引存的是「词项 → 文档列表」,擅长精确关键词、稀有实体、编号型号和可解释的词法匹配;向量索引按 Embedding 距离找语义近邻,擅长同义改写和概念相似,但会漏掉精确字符串约束。**两者互补而非替代**,实际召回常常两路都跑再融合——怎么融合、RRF 怎么算、查询改写和重排怎么接,见 检索优化 篇。

精确搜索(Flat)要和每一条向量都算距离,结果百分百正确,代价是访问量随规模线性增长。ANN 的全部思路就是**只访问最可能包含近邻的那一小部分数据**,用一点召回率换延迟和内存。所以任何 ANN 索引的第一句话都相同:**它会漏,漏多少必须在你自己的真实数据上测 Recall@K**——不同数据的簇结构、维度、分布差别很大,别人报的召回率不迁移。

| 索引 | 核心做法 | 优势 | 局限 |
|---|---|---|---|
| Flat | 与全部向量算精确距离 | 结果精确,是**评测其他索引召回率的基线** | 计算与访存随规模线性涨 |
| HNSW | 分层近邻图,从稀疏高层导航到底层 | 同召回下延迟通常最低;支持增量插入 | 图边吃内存;构建重;删除多为软删 |
| IVF | 聚类中心分桶,只扫最近的若干桶 | 内存友好、易分片、扫描量可控 | 要训聚类;桶不均衡伤召回与尾延迟 |
| PQ | 切子空间,每段只存码字编号 | 压缩几十倍,距离靠查表算得快 | 距离是近似值,压得越狠误差越大 |
| IVF-PQ | IVF 缩小候选范围 + PQ 压缩桶内向量 | 内存受限的大规模检索主力 | 聚类、探桶数、量化参数要一起调 |
| OPQ | PQ 之前先学一个正交旋转 | 各子空间能量更均衡,同压缩比下误差更小 | 多一步训练,旋转矩阵随数据重训 |

LSH 也能做近似搜索,但在具体数据和硬件上是否合适要实测,不能按名气选。

## 九、HNSW:带高速公路的近邻图

把它想成一张有高速公路的路网:底层是密集乡道、连着每个点的近邻,上层节点越来越少、跨度越来越大,像高速。每个节点的最高层数按几何分布随机决定,所以上层节点指数级变少。查询从最高层的固定入口出发,**贪心**走向离查询更近的邻居,走不动就下沉一层;逐层细化,最后在底层维护一个大小为 `efSearch` 的候选队列做束搜索,返回 Top-K。

| 参数 | 管什么 | 调大的收益 | 调大的代价 |
|---|---|---|---|
| `M` | 每个节点保留的邻居数上限 | 图更连通、召回上限更高,高维数据尤其需要 | **内存线性涨**(见第四节那张表)、构建更慢 |
| `efConstruction` | 建图时每个点找邻居的候选范围 | 邻居选得更准、图质量更好,同 `efSearch` 下召回更高 | 只拖慢建索引,**不影响查询延迟** |
| `efSearch` | 查询时的候选队列大小 | 召回单调上升 | 延迟与访存线性上升;必须 ≥ K |

调参顺序:`M` 和 `efConstruction` 建一次索引就定死了,先按内存预算定 `M`(常见 16–48),`efConstruction` 在可接受的建索引时间内往大取;**`efSearch` 是唯一的线上旋钮**,可以不重建索引就扫出一条召回–延迟曲线,按 P95 预算取点。

### 那个 $O(\log N)$ 要说清楚

**HNSW 的查询复杂度没有通用严格的 $O(\log N)$ 最坏保证。** 论文给的是在特定假设和它测过的数据集上的对数级标度,不是对任意数据分布成立的最坏情况上界。实际会明显偏离的场景:数据高度聚簇导致贪心在局部兜圈子、维度很高时图的近邻结构本身变差、大量删除后图连通性退化、以及 `efSearch` 固定时召回随数据增长而下滑。面试里把这句讲对,比背一个复杂度更能说明你真跑过。

## 十、IVF 与 PQ:先分桶,再压缩

### IVF:`nlist` 与 `nprobe`

先用 k-means 训 `nlist` 个粗聚类中心,每条向量写进最近的桶;查询时先算 query 到各中心的距离,只扫最近的 `nprobe` 个桶。`nprobe` 是线上旋钮,调大则召回涨、扫描量涨,角色和 `efSearch` 一样。`nlist` 是建索引时定的,它两头受气:

$$
C(\text{nlist}) \approx \text{nlist} + \text{nprobe} \times \frac{N}{\text{nlist}}
$$

意思是:一次查询的访问量等于**和所有聚类中心比一遍**(前项)加上**扫 `nprobe` 个桶里的向量**(后项)。前项随 `nlist` 涨、后项随 `nlist` 降,所以存在最优点;求极小得 $\text{nlist}=\sqrt{\text{nprobe}\cdot N}$,这正是「`nlist` 取 $\sqrt{N}$ 量级」这条经验的来源——把 `nprobe` 当成小常数吃掉,就剩下 $\sqrt{N}$。代入 $N=10^7$:按 $\sqrt{N}$ 取是约 3200,按含 `nprobe`=16 的完整式取是约 1.3 万,实践中在这两者之间选一个再实测。两种取法下一次查询访问的都是**几万条**(前者约 5 万、后者约 2.5 万),而不是一千万条,少两个数量级。这个式子假设桶均匀,只当起点。

**桶不均衡是 IVF 最典型的坑。** 真实语料从不均匀:重复模板、热门话题会把一大堆向量挤进同一个桶。后果有两层——召回上,`nprobe` 个桶已经扫了几十万条却还漏;延迟上,命中大桶的查询显著变慢,平均延迟看不出来,**P99 直接被拉高**。处理手段:重训聚类中心并检查桶大小分布(不是只看平均)、把超大桶再切一层、按桶大小做分片与负载均衡、给单次查询设扫描量上限。

### PQ:切子空间 + 查表算距离

把 $d$ 维向量切成 $m$ 段,每段各自训一本码本(常见 256 个码字,正好 8 bit),存储时每段只留最近码字的编号。查询时:

$$
\|q - x\|^2 \approx \sum_{s=1}^{m} \big\| q^{(s)} - c^{(s)}_{k_s(x)} \big\|^2
$$

意思是:查询也切成 $m$ 段,候选的第 $s$ 段已被替换成码本里第 $k_s$ 个码字,所以整体距离约等于逐段距离之和。关键在于**这些逐段距离在查询一开始就对全部码字算好、放进一张表**,之后每个候选只做 $m$ 次查表加法。以 1024 维、$m$=64、每本 256 个码字为例:一次性算 $64\times256=16384$ 个距离,之后每个候选从 1024 次乘加降到 64 次查表加法,存储从 4096 字节降到 64 字节——**省的不只是算力,更是内存带宽**,而 ANN 的瓶颈本来就在访存。压缩比由原始精度、段数和每段位宽共同决定,没有固定值。

1024 维这种高维下每段要压的维度更多、误差自然更大,五条缓解手段按性价比排:**先粗后精**(PQ 只做粗筛,对 Top 几百个候选读原始向量重算精确距离再排序——最有效,因为精排只碰很少候选,召回损失几乎全补回来);**降低压缩强度**(加段数或加位宽,内存换精度);**上 OPQ**(PQ 假设各子空间独立且能量相当,真实向量常不是,某几维方差极大而切分正好把它们劈开,OPQ 先学一个正交旋转把能量摊匀再切);**先降维再量化**(PCA 或 Matryoshka 式截断,前提是模型支持);**回源头改 Embedding 训练**,让向量本身更好压。是否有效不看量化误差本身,看 **Recall@K 和下游回答质量**——误差涨了但 Top-K 顺序没变,就没有损失。

## 十一、FAISS 与向量数据库:职责边界

FAISS 提供 Flat、IVF、PQ、HNSW 等索引组件和 CPU/GPU 实现,可以组合出「粗筛 + 压缩距离 + 精排」这类流程。它的加速来自四处,**注意其中三处都在减少访存**:索引结构减少实际访问的向量数(图导航或只扫若干桶);量化压缩减少存储、内存带宽和距离计算量;批量计算、SIMD 与 GPU kernel 提高实际吞吐;必要时用原始向量对短候选集重新精排,把召回损失补回来。

**但 FAISS 是算法与本地索引库,不是数据库。** 它不管持久化、不管分片副本与故障恢复、不管元数据过滤与权限、不管在线服务治理与监控。Milvus、Pinecone 这类向量数据库补的正是这一格,内核往往还是同一族算法。所以选型不该问「谁更快」:单机、库不大、要极致可控、能自己写服务层,就用 FAISS 这类库直接嵌进应用;需要多副本高可用、带元数据的硬过滤、多租户隔离、在线增删和运维界面,就上向量数据库;**性能必须按当前版本和自己的部署实测**,不能按产品名判断。

至于 FAISS 内部的 IVF 与 HNSW 怎么选:**内存吃紧、库很大、能接受调 `nprobe` 换召回 → IVF(通常配 PQ);延迟要求苛刻、库在百万级、内存给得起 → HNSW。** RAG 里两者组合的常见形态是用 HNSW 当 IVF 的粗量化器(快速找到最近的若干聚类中心),或者 IVF-PQ 粗筛后读原向量精排。

## 十二、规模、更新、迁移与验收

### 十亿级的瓶颈在内存

十亿条 768 维 fp32 原始向量就是约 3.1 TB,单机放不下;HNSW 还要在这之上叠图边。四类瓶颈按出现顺序:原始向量、图边、分片副本带来的成倍放大、以及构建时间(建图是插入 $N$ 次局部搜索,不是线性小常数)。可用手段:

- **分片**:按租户、时间、类目这类业务维度硬切,查询时先过滤再检索。这往往是第一手段,因为多数查询根本不需要扫全库。
- **压缩向量**:PQ 或标量量化。注意第四节那条——压完之后**图边反而成了主要开销**,所以「HNSW + PQ」常要同时调小 `M`。
- **落盘**:DiskANN 那条路线把图放 SSD、内存只留压缩向量做粗筛,论文自报在单机 64 GB 内存加一块 SSD 上索引十亿点,SIFT1B 上 5000+ QPS、平均延迟 3 ms 以内、1-recall@1 95%+(论文口径,自己的数据要重测);实在不够就**调小图参数、先粗筛再局部搜索**,用召回换内存。

### 高实时更新:索引结构承不承受得住

结论先行:**HNSW 支持增量插入但删除多为软删**,删除标记积累到一定比例会同时伤召回和延迟,必须定期重建;**IVF/PQ 的聚类中心和码本是训出来的**,新数据分布一漂,旧码本就不再匹配,也要重训。所以高实时场景的通行结构是**稳定的主索引 + 一个小的增量索引**:新数据先写增量层并参与联合查询,后台再批量合并或重建主索引,FreshDiskANN 那条线就是把这件事做进索引本身。版本号、删除标记、写入顺序与一致性检查这一整套链路,见 切块与索引 篇;Agent 记忆场景的漂移检测与双写重建见 记忆与上下文 篇。

### 换模型或换维度之后,索引怎么迁移

一条铁律:**不同模型产出的向量之间没有可比性,新旧向量绝不能混进同一个索引**——它们不在同一个空间里,距离算出来是纯噪声。所以「迁移」实际上是重建:

1. **全量重新编码**,这是主要成本,先按文档数 × 编码吞吐估 GPU 小时和窗口;
2. **重训索引里可学习的部分**——维度变了不只是换个向量,IVF 的聚类中心、PQ/OPQ 的码本、任何降维矩阵全部作废,要在新向量上重训;
3. **版本号钉在索引和每条记录上**并在查询侧强制校验,缺这一步,一次误配就是静默的全线质量下滑,而且不报错;
4. **影子索引 + 灰度**:新索引灌完先不接流量,用目标数据集跑 Recall@K 和下游回答质量,不退化再按比例切流,老索引留一段时间随时回滚,同时把**阈值和 Top-K 全部重新校准**(第三节说过余弦分布随模型而变,旧阈值直接搬必然错)。

### 验收不能只看 QPS

QPS 只说明「跑得快」,不说明「找得对」,而 ANN 恰恰是拿正确性换速度的。至少同时报五项:**Recall@K**(以 Flat 精确检索为基准)、**P95/P99 延迟**(平均值会把桶不均衡这类尾部问题藏起来)、**内存占用**、**构建与更新成本**、**下游指标**(RAG 回答准确率或推荐线上指标)。最后一项是最终判据:近似误差可不可接受只有下游说了算——Recall@10 从 0.98 掉到 0.95 而回答质量没动,这笔交易就是划算的。
