# 切块与索引

一句话:把原始文档变成"能被检索命中、命中后还能用"的索引单元——这是 RAG 里唯一在**离线**就把天花板定死的环节,检索侧再怎么调也捞不回一个切坏的块。

## 一、离线建库是一条数据链路,不是一段切分脚本

从原始文件到索引可查,固定要走六步。**这条链路的性质是:上游的错会被下游放大,而且几乎都表现成同一个症状——"召回率低"**,所以排查顺序必须从上游往下走。

| 环节 | 这一步在干什么 | 典型失败 | 在检索上表现成什么 |
|---|---|---|---|
| 解析 | PDF / HTML / Office → **带层级**的文本 | 双栏 PDF 按行读串了行;表格丢表头 | 块内容自相矛盾,数字对不上 |
| 清洗 | 去页眉页脚、导航栏、样板文字、近重复 | 顺手把正文里的条款也删了 | 该有的证据根本不在库里 |
| 切块 | 定"检索的最小单元" | 从句子中间截断 | 条件和结论分家,答案缺前提 |
| 元数据 | 挂来源、版本、权限、标题路径 | 只存了 text | 过滤不了,新旧版本混着召回 |
| 向量化 | 文本 → 向量 | 查询侧没加同样的指令前缀 | 分数整体偏移,排序失真但不报错 |
| 入库 | 向量 + 原文 + 索引三者关联 | 向量与原文的 ID 对不上 | 检到了却取不出原文 |

### 建库自体检:不用标注也能天天跑

出问题时不要一上来就换 embedding 模型,先看这几个数——它们不需要人工标注,能直接定位是哪一步坏了:

- **解析失败率 / 空块比例**:解析层的健康度
- **块长分布**:如果一大堆 20 字以下的碎块,说明切分退化了(常见于表格和目录页)
- **近重复率**:重复块会在 top-k 里占掉多个名额,等于把 k 变小了
- **孤儿块比例**:没有标题路径或来源的块,一旦被召回就无法给出处
- **索引条数 vs 块条数**:对不上就是入库丢了数据

## 二、解析与清洗:结构比文字更值钱

**解析阶段的目标不是"把字都抠出来",而是"拿到带层级的字"**。因为后面切块要按标题切、上下文头要拼章节路径、元数据过滤要用文档结构——层级一丢,后面全部退化成按长度硬切。

**PDF 分三类处理**:文本层完好的直接抽,但要按坐标聚成栏再读,否则双栏论文会左右交错;扫描件先 OCR;公式和复杂版面的学术文档可以用视觉模型直接转成标记语言(Nougat 那一路)。

**表格必须连表头进块**。一张 20 行的表如果被切成 5 块,后 4 块就是一堆没有列名的数字,召回了也没法用。三种可行做法:整表作为一个块;超长表按行切但**每块重复表头**;或者把每一行转写成一句自带列名的话("2023 年 Q2 营收为 …")。第三种最贵,但对"某年某项是多少"这类点查最准。

**图片与扫描页**保存 OCR 文字 + 页码 + 区域坐标 + 原图引用,不能只留一段脱离位置的文字。因为生成侧要给出处,人工要能翻回原页核对。

**清洗**去掉页眉页脚、导航、版权样板、目录页,再用 MinHash / SimHash 之类做近似去重(爬来的镜像页、同一份合同的多个版本)。注意别把正文里的免责声明、附则当样板删掉——**清洗的删除是不可逆的,宁可少删**。

## 三、切块:在"定位得准"和"证据够全"之间选

### 权衡本身

- **块小**:一个向量只代表一个主题,检索精度高;但容易把主语、条件、结论切散,单块信息不足以回答。
- **块大**:证据完整;但一个定长向量要代表多个主题,语义被平均掉,和任何具体查询都不够像(**语义稀释**),同时挤占生成侧预算——同样 top-5,块 200 token 是喂 1000 token,块 1000 token 就是喂 5000 token,差 5 倍。

### 五种策略

| 策略 | 怎么切 | 适合什么 / 代价 |
|---|---|---|
| 固定长度 | 数满 token 或字符就断 | 基线,便宜稳定;会在句子、表格、代码中间截断 |
| 滑窗 + overlap | 相邻块重复一段内容 | 缓解边界截断;块数与存储上升,top-k 里出现重复 |
| 递归切分 | 按分隔符优先级逐级降级:段落 → 句号 → 逗号,直到满足长度 | 通用默认;结构差的文本会退化成固定长度 |
| 结构化切 | 按标题层级、条款号、表格、函数边界切 | 规范文档、法条、代码最可靠;强依赖解析质量 |
| 语义切块 | 逐句编码,相邻句相似度掉到阈值以下就断 | 结构差的长文;编码贵、阈值敏感 |

语义切块要老实说一句:它直觉上最优,但 arXiv:2410.13070 的系统评测结论是**收益不稳定、不足以抵消计算开销**。所以它不是默认选项,是结构化切不动时的补救。

### chunk size 与 overlap 怎么定

先统一口径:说"512"必须说清是 token 还是字符、哪个 tokenizer 的 token。中文一个汉字折算多少 token 随 tokenizer 差别很大(中文字表的模型大致 1 字 1 token,多语言 BPE 上常常不止),**同一个数字换个模型就不等价,阈值必须按实际 tokenizer 实测**。

经验区间(是经验值,不是定律):通用问答、FAQ 类落在 **200–500 token**;需要长推理链或完整条款上下文的落在 **500–1000 token**,并配父子块。硬上限是 embedding 模型窗口——早期 BERT 系只有 512 token,新一代长上下文模型能到 8k 量级。但**窗口大不等于该切大块**:向量维度是固定的,塞进去的内容越多,单个向量能承载的区分度越低。

overlap 常见取块长的 **10%–20%**。它的代价可以直接算:

$$
N_{\text{chunk}} \approx \frac{L}{C\,(1 - o)}
$$

文档总长 $L$、块长 $C$、重叠比例 $o$ 时的块数大约是这么多。$o = 0.2$ 时块数变成 1.25 倍——**overlap 是拿存储和 top-k 名额换边界安全**,不能无脑开大。存储也能直接估:768 维 float32 向量是 3 KB,100 万块就是 3 GB 纯向量,还不算原文和索引本身的开销。

### 跨块取证:小块检索、大块喂模型

真正解决"块小丢上下文"的不是加 overlap,而是**让检索单元和喂给模型的单元解耦**:

| 做法 | 索引里放什么 | 命中后喂什么 |
|---|---|---|
| 父子块 | 子块(小、精确) | 子块所属的父块(整节 / 整条) |
| 上下文头 | 子块正文前拼上"文档标题 > 章节路径 > 表头" | 同上 |
| 邻接扩展 | 子块 | 命中块 ±1~2 个相邻块,按原文顺序拼回 |
| 层级摘要(RAPTOR) | 叶子块 + 逐层聚类摘要 | 命中的那一层 |
| 上下文化块 | 用 LLM 给每块生成一句"它在全文里是什么"再一起编码 | 原块 |

最后一种有公开数字:Anthropic 自报在其评测集上,按 **top-20 块的检索失败率**口径,contextual embeddings 把失败率从 5.7% 降到 3.7%(约 −35%),再叠上同样上下文化的 BM25 降到 2.9%(约 −49%)。口径是他们自己的数据集,不通用,但方向清楚:**给块补回它丢掉的上下文,收益比反复调块长大**。

代价也要说清:父子块要多存一层映射,而且多个子块命中同一父块时 top-k 去重变复杂;上下文化块要对每个块调一次 LLM,建库成本随块数线性增长。Late chunking(arXiv:2409.04701)是省钱的一路——先用长窗口模型编码整篇,再在 token 表示上按块池化,每个块的向量天然带全文上下文,不用额外调 LLM;arXiv:2504.19754 的对比结论是它更省但在相关性和完整性上有损失。更极端的一路是把段落拆成自洽的"命题"再索引(arXiv:2312.06648),同等预算下优于段落级,代价是要 LLM 抽命题、还要另外维护回原文的位置。

### 怎么比较两套分块方案

**必须控制变量,而且对齐的是 token 预算,不是 top-k。** 因为块长一变,同样 top-5 喂进模型的 token 也跟着变——不冻结这一项,你分不清是切得更好了还是单纯上下文给多了。正确姿势:固定 embedding 模型、reranker 和 prompt,按"喂给模型的总 token 预算"对齐两套方案的 k,再在同一份真实查询集上比。用哪些指标、失败怎么归因,见 RAG评测 篇。

## 四、元数据:建库时决定了检索时能过滤什么

**元数据是整条链路上唯一"过期不候"的东西**——建库没存的字段,检索时再想用只能重建索引。

| 字段 | 为什么值得存 |
|---|---|
| doc_id / chunk_id | 向量 ↔ 原文的稳定关联;删除与更新按它传播 |
| 来源、URL、页码 / 行号 | 生成侧要给出处,人工要能核查 |
| 标题路径(H1 > H2 > H3) | 拼上下文头;也能按章节过滤 |
| 版本号 / 生效时间 | 防新旧版本混召,也支持按时间衰减排序 |
| 权限标签(部门 / 密级) | 权限只能在检索层拦,不能靠生成侧"别说" |
| 文档类型、语言 | 按类型路由到不同的切块与检索策略 |
| 内容哈希 | 增量更新时判断"这块到底变没变" |

### 过滤和向量检索怎么配合

- **后过滤**:先做向量 top-k,再按元数据筛。实现简单,但过滤条件越苛刻,筛完剩得越少,极端情况 top-100 全被筛光返回空。
- **前过滤**:先用元数据缩小候选集,再在子集上搜近邻。语义上正确,但对图结构的 ANN 索引不友好——被滤掉的点往往是图里的连通桥梁,剔除后剩下的点可能互相走不到,召回会塌。

工程折中很固定:**高选择性、低基数的字段(租户 ID、密级)做前过滤,并按它物理分片**,一个租户一套索引,过滤退化成"选哪个索引",完全不影响 ANN 质量;低选择性字段(语言、类型)做后过滤,并把 k 放大到 3–5 倍再筛。索引侧怎么实现带条件的近邻搜索,见 Embedding 篇。

**权限必须走前过滤或分片这一路。** 因为后过滤的本质是"先检索出来再遮住",只要有一处忘了遮就是泄露;分片是物理隔离,漏不了。

## 五、向量化与入库

### 查询侧和文档侧必须对齐

三件事要和 embedding 模型的训练约定一致,错一个分数就没有意义:

1. **指令前缀**:不少模型要求查询和文档各加不同前缀,少加或加错会让分数系统性偏移。
2. **归一化**:按余弦相似度训练的模型,向量要做 L2 归一化;归一化后内积与余弦等价,索引就能用内积度量。
3. **距离函数**:余弦 / 内积 / 欧氏必须和训练目标一致。

这三条是最难查的一类 bug:**用错了不会报错,排序看上去也挺正常,只是效果一直差**。模型本身怎么选、维度怎么权衡,见 Embedding 篇。

### FAISS 和向量数据库的工程边界

| | FAISS 这类索引库 | 向量数据库 |
|---|---|---|
| 定位 | 一个**算法库**:给一堆向量,建索引、搜近邻 | 一个**服务**:存储 + 检索 + 治理 |
| 持久化 | 自己序列化到文件,自己管备份 | 内置 |
| 元数据过滤 | 基本没有,要自己另配 KV / 关系库并保证一致 | 内置字段与条件过滤 |
| 增删改 | 删除通常只能标记 + 重建,原地更新受限 | 有增量、合并、压缩机制 |
| 分片 / 副本 / 多租户 | 无,自己搭 | 内置 |

判据很实用:**规模在百万级以内、数据基本不变、只有一个进程用 → FAISS 足够,省掉一整套运维**;一旦要在线增删、按元数据过滤、多副本高可用、多个服务共享,你在 FAISS 外面补齐这些,等于重写了一个向量数据库。

规模上去后的四角取舍(召回 / 延迟 / 内存 / 更新),本篇只负责"更新"这一角,见下一节;另外三角是 ANN 索引结构与参数的问题,见 Embedding 篇。

## 六、代码知识检索:哪些能复用,哪些必须重做

面向文档的 RAG **不能直接复用**,三处根本不同。

**一、切块单位是语法结构,不是长度。** 用 AST / tree-sitter 解析,以函数、方法、类为最小单位。固定长度切会把函数从中间截断,得到的片段既不能编译也无法理解。cAST(arXiv:2506.15655)给了一个可操作的做法:把 AST 节点递归拆小,再把相邻兄弟节点在长度上限内合并——既不超窗口,又不跨语法边界;论文报告 RepoEval 检索 Recall@5 +4.3、SWE-bench 生成 Pass@1 +2.67。

**二、每块必须补上下文头。** 一段只有函数体的代码,脱离文件路径、所属类、完整签名和必要 import,看不出它属于谁、操作什么类型:

```python
# 索引里的一个代码块 = 上下文头(切块时补上,原文里没有)+ 函数体
# file: billing/invoice.py
# class: InvoiceService
# imports: from decimal import Decimal
def apply_discount(self, amount: Decimal, code: str) -> Decimal:
    """按优惠码打折;未知码原样返回。"""
    rule = self._rules.get(code)
    if rule is None:
        return amount
    return (amount * (1 - rule.rate)).quantize(Decimal("0.01"))
```

**三、相似性的定义变了。** 找代码时用户常常要的是**精确标识符**——某个函数名、错误码、配置键。而向量检索恰恰对精确匹配最弱:`get_user_by_id` 和 `get_user_by_name` 在向量空间里几乎重合,用户要的偏偏是其中一个;反过来"这里分页是怎么做的"这类意图查询又只有向量能处理。**所以代码检索必须混合词法检索(BM25 / 符号索引)与向量检索**,只上向量是这类系统最常见的失败原因。融合方式见 检索优化 篇。

代码还有文本没有的显式结构:调用图、import、定义-引用、继承层次都能静态分析出来。命中一个函数后沿这些边扩展,把调用者、被调用者、类型定义一起带上,通常比继续抠向量精度更有效。

四个具体边界:

- **函数超过 embedding 窗口怎么切**:按内部语法块切(if / for / try 块、连续语句段),每个子块都带同一个上下文头,再额外索引一个"签名 + docstring + 摘要"的代表块用于粗召回。绝不按行数硬切。
- **调用图扩几跳**:1 跳(直接调用者与被调用者)是安全默认,2 跳就必须设预算上限。因为扇出是指数级的——一个被广泛调用的工具函数,1 跳就可能带出几十个调用点。控制手段是给边分优先级(定义 > 直接调用 > 同文件)再按总 token 预算截断。
- **注释和实现不一致以哪个为准**:两者都索引,但**以实现为准**。注释是意图,能提高召回(用户常按意图搜);实现是事实,答案必须基于它。工程做法是把注释放进"用于检索的文本"、把实现放进"返回给模型的内容"。
- **重命名与文件移动**:块的身份要靠内容哈希 + 符号 ID,不能用路径当主键。否则一次目录调整会表现成"删掉一大批、新增一大批",索引全量翻新,历史链路也断了。

**能复用的部分**:向量库、重排、生成侧的上下文组装、评测框架。要重做的是解析、切块、索引和查询理解这四层。还有一条硬边界:**代码索引必须绑定 commit**——检索到旧实现比检索不到更危险,因为它看起来是对的。跨语言时每种语言要一套解析器,支持成本随语言数线性增长。

## 七、增量更新与一致性

### 第一步:先判断"变的是什么"

| 变的是 | 症状 | 该做什么 |
|---|---|---|
| 内容(新增 / 修改 / 删除) | 答案引用了过期事实 | 增量入库 + 删除传播,不动索引结构 |
| 查询分布(用户问法变了) | 召回主题不对,但文档其实还在库里 | 补查询样本,做同义词、查询改写或检索器微调 |
| 表示空间(换了 embedding 模型) | 分数不可比 | **全量重编码 + 整体切换,没有增量选项** |

第三种最容易踩:**新旧模型的向量根本不在同一个空间,分数没有可比性**,混在一个索引里搜出来的排序是没有意义的。

### 版本要贯穿整条链路

原文 → 解析结果 → 块 → 向量 → 索引,每一层都记版本,并且**下游记住上游的版本号**,这样才回答得了"这个块出自哪一版文档、用哪个模型编的、落在哪个索引里"。删除和失效必须作为**事件**沿这条链往下传,而不是只把原文删掉。

### 主索引 + 增量层 + 别名切换

1. **主索引**:稳定、大、后台批量重建,不接受频繁原地写。
2. **增量层**:一个小索引(数据量小时暴力扫描就够),新数据先进这里,分钟级可查。
3. **删除标记(tombstone)**:删除不去主索引里物理抠洞——图索引原地删代价高还破坏连通性——而是记一条"该 chunk_id 已失效",查询时过滤掉,下次重建才真正丢弃。

查询时两层都查、合并去重,防重复和防漏检各有一条硬规则:

- **防重复**:同一个 chunk_id 在两层都有时,以增量层为准。所以合并必须**按 chunk_id 去重,而不是按文本去重**——文本可能只改了一个数字,按文本比对会当成两条不同记录都留下。
- **防漏检**:切换靠**别名**。查询访问的是一个逻辑名,后台重建完新索引后把别名一次性指过去。绝不能"先删旧再建新",那个中间窗口是真空期。

### 上线前影子评测,上线后可回滚

新索引先影子运行:固定题集 + 近期真实查询同时打新旧两套,比 Recall@K、端到端正确率、延迟,还要专门比**空结果率**和**旧文档误命中率**——这两个专抓"切换后某类查询彻底捞不到"和"旧版本没清干净",平均指标看不出来。异常就把别名指回旧索引,变更与删除审计记录全程保留。

### 三个高频追问

- **换 embedding 模型怎么不停机**:双写。后台用新模型把全量数据重编码进一套新索引,线上仍走旧索引;新索引影子评测通过后切别名,旧索引保留一段回滚期再下线。关键是**别为了省事让两套向量共存于一个索引**。
- **怎么分清"知识过期 / 索引陈旧 / 查询漂移"**:三个动作依次做。① 去原文库查这条知识,原文本身就是旧的 → 知识过期,只能改数据,改 Prompt 没用。② 原文是新的但检索不到 → 拿这个块 ID 直接查索引,查不到就是索引陈旧(增量没落地或重建漏了)。③ 原文新、索引里也有、就是排不上去 → 查询侧问题,看新词新实体比例、召回文档的平均年代、人工相关性。**别只盯着向量距离的分布漂移**,模型置信度变化不等于数据变了。
- **删掉一份敏感文档怎么确认派生物都失效**:按 doc_id 反查所有派生对象逐类核销——块、向量、稀疏索引条目、查询结果缓存、embedding 缓存、离线快照与备份、日志里落的原文片段。做法是**建库时就维护 doc_id → 派生对象的正向清单**,而不是删的时候去猜有哪些。删完再用一组"应该检不到"的探针查询做验收。

### 更新频率怎么定

没有通用值。**越快生效,增量层和多版本查询越复杂;越依赖全量重建,窗口期越长。** 重建周期、增量层上限、回滚保留期这三个数由知识变化速度和业务 SLA 决定。一个可操作的触发判据:当增量层大到明显拉高查询延迟,或者 tombstone 占比越过阈值时,就该重建主索引。

Agent 场景下的事件级切块和向量记忆治理是另一套问题,见 记忆与上下文 篇。
