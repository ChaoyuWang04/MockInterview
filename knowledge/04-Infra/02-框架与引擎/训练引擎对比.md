# 训练引擎对比

一句话:这篇不找一个永远最快的训练引擎,而是回答 **FSDP2 与 Megatron-Core 到底是不是同一层东西、它们为什么走出两条不同路线、给定模型和集群时该怎么选**。

> - 当前状态:FSDP2 已取代 FSDP1 成为 PyTorch 推荐路线;Megatron-Core 同时提供 Distributed Optimizer 与 Megatron-FSDP,并组合 TP/PP/CP/EP;DeepSpeed 仍以 ZeRO、卸载与 Engine 配置生态构成第三条常见路线

## 一、先把比较对象摆正

“FSDP2 vs Megatron”很常见,但它不是两个完全同层产品的比较。

| 名字 | 更准确的层级 | 它主要接管什么 |
|---|---|---|
| **FSDP2** | PyTorch 原生分片能力 | 把参数、梯度和优化器状态沿数据并行维切开,在计算前后自动聚合与重分片 |
| **Megatron-Core** | 大模型训练组件与多维并行库 | 模型组件、TP/PP/CP/EP、流水调度、分布式优化器、checkpoint 与性能优化 |
| **DeepSpeed** | 训练 Engine 与系统能力集合 | ZeRO、卸载、优化器、混合精度、训练循环接入和配置管理 |
| **TorchTitan / Megatron-LM** | 参考训练栈 | 把底层能力组装成能直接训练模型的数据、循环、保存与恢复流程 |

所以真正的主轴是:

- **FSDP2 路线**:尽量保留普通 PyTorch / Hugging Face 模型,再把分片、TP、PP 等能力组合上去;
- **Megatron-Core 路线**:模型一开始就按分布式训练重新搭,换取更完整、更深的并行与 kernel 协同。

DeepSpeed 是第三个坐标:它和 FSDP2 都能做 ZeRO-3 一档的全分片,但它通过一层 Engine 和 JSON 配置提供更大的系统包,尤其强调卸载与既有平台集成。

### 为什么不能只问“谁更快”

训练速度不是引擎名字的常数。它至少由下面这些量共同决定:

- 模型是 Dense 还是 MoE,单层和专家有多大;
- 序列多长,激活还是模型状态占大头;
- 卡内、机内、跨机带宽分别多大;
- TP、PP、CP、EP 和 DP 怎么摆;
- 精度、重算、offload、checkpoint 是否相同;
- 模型实现是否真的用到了对应后端的融合算子。

只换框架名却连模型实现、batch 和并行度一起换,测到的是**两套配方的差**,不是某个分片 API 的净差。

## 二、FSDP2 的路线:先保留模型,再组合分布式能力

FSDP2 的核心动作很朴素:平时每张卡只保存自己那一片参数;某个模块要算时先 all-gather 成完整参数,算完再丢掉临时完整副本;反向后用 reduce-scatter 汇总并留下本 rank 的梯度片。

它相对 FSDP1 最关键的变化不是“第二版更快”,而是**分片表示换了**:

- FSDP1 用包装模块和扁平参数管理状态;
- FSDP2 用 `fully_shard` 原地改造现有模块;
- 参数本身变成 DTensor,分片布局成为张量的一部分;
- 优化器、梯度裁剪与分布式 checkpoint 可以围绕同一套 DTensor 表示工作。

这个选择首先解决的是**可组合性与可理解性**。模型仍是原来的类,参数仍按原名字存在;要接新 Hugging Face 架构时,通常不用把每个 Transformer 组件重写成另一套平行类。

### 它为什么适合快速变化的模型

新模型结构出现时,最先可用的实现往往在 Hugging Face。FSDP2 可以直接对这份实现按层应用分片,因此“模型能单卡跑”到“模型能多卡分片跑”之间的距离较短。

代价是:**原模型能跑不等于组合后的每条并行轴都成熟**。TP 需要为具体层指定切法;MoE 的专家并行、PP 的切段、FP8 kernel 与 checkpoint 仍需要上层训练栈把它们接好。TorchTitan 展示了 FSDP2 + TP + PP + CP 的原生组合路线,但具体模型支持矩阵仍要按当时版本核对。

### FSDP2 的性能抓手在哪里

它的主要抓手不是专用模型类,而是:

1. 选择合适的 FSDP 单元,控制一次聚合多少参数;
2. 用预取把下一次 all-gather 藏在当前层计算后面;
3. 用 DeviceMesh 把 FSDP 与 TP 等轴放到不同通信域;
4. 用 DTensor 与 DCP 保存分片状态,避免每次都在单 rank 汇总整模。

如果层太小,通信调用过碎;层太大,临时完整参数的峰值又会上升。FSDP2 没有替用户消灭这笔取舍,只是把它放进原生 PyTorch 抽象里。

## 三、Megatron-Core 的路线:先按并行重建模型

Megatron-Core 的出发点不同:**大模型不是一个普通单卡模型外面包一层分片就结束了**。当单层、序列、专家或层数都装不下时,计算本身也必须切开。

因此它把多条轴一起纳入训练底座:

| 轴 | 解决的主要瓶颈 |
|---|---|
| TP | 单层权重、激活与 GEMM 太大 |
| PP | 层数太多,整段模型装不下 |
| CP | 长序列激活与注意力计算太重 |
| EP | MoE 专家权重和 token 路由需要分卡 |
| DP / 分片 DP | 扩 batch,并摊薄模型状态 |

这条路线的优势是**协同优化深**。模型层、通信组、流水调度、Transformer Engine、融合 kernel、FP8 与 checkpoint 都知道彼此的布局,因此可以围绕同一份拓扑做重叠和缓冲区规划。

代价也来自同一点:**模型必须进入 Megatron 的世界**。新架构要适配它的模型组件、权重命名和 checkpoint 转换;模型研究者临时加一个新层时,接入成本通常高于直接修改 Hugging Face 实现。

### Megatron-LM 与 Megatron-Core 别混

- Megatron-Core 是可以被别的训练框架复用的并行库;
- Megatron-LM 是 NVIDIA 把数据、模型构造、训练循环和 Core 组合起来的参考训练栈;
- RL 框架常常只复用 Core,因为它们需要自己的“采样—奖励—更新”循环。

这也是为什么说“某框架支持 Megatron”时必须继续问:**它复用的是模型并行组件、优化器和 checkpoint,还是直接使用整个 Megatron-LM 训练入口?**

## 四、Megatron-FSDP:交集出现了,但两条路线没有合并

今天再把“FSDP”和“Megatron”画成完全互斥的两条路已经不准确。Megatron-Core 自己提供了 **Megatron-FSDP**,也就是在 Megatron 生态内做全参数分片。

它与 PyTorch FSDP2 解决同一类容量问题,却没有使用完全相同的数据布局:

| | PyTorch FSDP2 | Megatron-FSDP |
|---|---|---|
| 分片单位 | 逐参数 DTensor | 按 FSDP 单元组织连续缓冲区 |
| 主要目标 | 原生表示、易组合、易操作单个参数 | 减少缓冲准备复制与 NCCL 调用,配合 Megatron kernel |
| 模型世界 | 普通 PyTorch 模块优先 | Megatron-Core 模型与并行轴优先 |
| 与 TP/CP/EP | 由 PyTorch 训练栈组合 | 在 Megatron 拓扑内直接组合 |

NVIDIA 官方文档给出的关键动机是:逐参数分片为了合并通信,可能需要把参数搬进通信缓冲区;Megatron-FSDP 让参数本来就是连续缓冲区的切片,减少额外复制,也方便某些要求连续布局的 MoE kernel。

但它的布局更复杂,单个参数在不同 rank 上甚至可能形状不同。**性能友好与通用易操作并不是同一个目标**,这正是两种表示继续共存的原因。

因此选型问题应改写成:

1. 我是否要保留原生 PyTorch / Hugging Face 模型?
2. 我是否已经需要 Megatron 的模型并行和 kernel 体系?
3. 在选定生态内,模型状态用复制、Distributed Optimizer 还是全分片?

而不是把 Megatron-FSDP 当作第四个独立训练框架。

## 五、DeepSpeed:为什么它仍是第三条现实路线

DeepSpeed 的辨识度在于 **Engine + 配置驱动 + ZeRO/offload**。它不只给一个分片 API,而是接管模型、优化器、反向、step 和一批系统配置。

它长期解决的现实问题是:

- 团队已经有大量 DeepSpeed 训练脚本和平台封装;
- 模型状态放不进 GPU,需要成熟的 CPU 或 NVMe 分级存储;
- 希望用一份配置统一 ZeRO、精度、卸载和通信重叠;
- 上层框架已经把 DeepSpeed 当固定后端,迁移成本高于潜在收益。

它的代价是配置面与版本组合更大。代码、配置文件和上层 Trainer 可能同时对同一行为有意见;出了性能问题时,要先分清到底是哪一层覆盖了哪一层。

所以 DeepSpeed 不该因为“旧”被直接排除,也不该因为功能多成为默认答案。**已有平台资产和必须的卸载能力**才是它最强的选择理由。

## 六、九个统一维度

### 维度一:新模型接入

| 诉求 | 更自然的路线 | 原因 |
|---|---|---|
| 直接训练最新 HF 模型 | FSDP2 | 保留原模型定义,分片原地组合 |
| 使用成熟的大模型配方 | Megatron-Core | 模型、并行和 kernel 已协同适配 |
| 接入既有企业 Trainer | 看现有后端 | 迁移训练栈的成本可能大于框架差异 |

“Day-0 支持”通常偏向原生模型路线;“把最后 10% 性能榨出来”通常偏向深适配路线。二者优化的是不同时间尺度。

### 维度二:模型到底哪里装不下

- 只有参数、梯度、优化器状态太大:FSDP2、Megatron-FSDP、ZeRO-3 都在候选内;
- 单层本身太大:需要 TP,只做数据并行分片不够;
- 层数和激活太大:可能需要 PP;
- 序列太长:需要 CP 或其他序列切分;
- MoE 专家太大或负载不均:需要 EP 与专门的 token 调度。

所以模型“参数量很大”还不是选 Megatron 的充分理由。真正的分界是:**容量问题能否只靠数据并行维解决。**

### 维度三:并行组合成熟度

FSDP2 的优势是组合接口通用;Megatron-Core 的优势是常见大模型组合已经进入同一套训练底座。前者强调“可以组”,后者强调“这组东西一起调过”。

面试里最稳妥的回答不是说哪边绝对支持更多,而是问:

- 目标模型在当前版本有没有现成 parallel plan;
- 这组 TP/PP/CP/EP 是否有正确性测试;
- checkpoint 能否在目标并行度下恢复;
- 性能关键 kernel 是否兼容这种分片布局。

### 维度四:显存

三条路线都能分片模型状态,但显存峰值还包括:

- 正在 all-gather 的完整参数;
- 预取的下一单元;
- 激活与重算缓冲;
- 通信 bucket;
- 融合 kernel 的工作区;
- checkpoint 或权重转换临时副本。

“都是 ZeRO-3 等价档”不代表峰值一样。分片粒度、预取深度和缓冲区布局会改变临时驻留量。

### 维度五:通信与重叠

FSDP2 主要围绕模块 all-gather / reduce-scatter 重叠;Megatron-Core 还要同时安排 TP、PP、CP、EP 通信,并尽量把高频通信留在 NVLink 域;DeepSpeed 则由 ZeRO bucket、通信重叠和卸载流水共同决定。

最常见的错误是为了省显存把并行轴开得太多。每增加一条轴都引入新通信或气泡。**先找能装下的最少切法,再谈峰值吞吐。**

### 维度六:低精度与融合 kernel

FSDP2 本身不限制低精度,但真正的 FP8/MXFP8/NVFP4 训练依赖模型层、编译器或第三方 kernel 能否理解分片参数。

Megatron-Core 与 Transformer Engine 结合更深,所以在 NVIDIA 大模型配方中更容易拿到成套融合与低精度路径;相应地,版本配对和硬件耦合也更强。

不能把“框架支持 FP8”理解成目标模型、目标优化器、目标分片组合都已通过数值验收。

### 维度七:checkpoint 与生态转换

FSDP2 的 DTensor 与 DCP 让分片状态成为 PyTorch 原生对象;Megatron 的 distributed checkpoint 知道 TP/PP/EP 布局,但交给 Hugging Face 推理前常需要桥接;DeepSpeed 也有自己的分片保存与汇总流程。

选型前至少验证四件事:

1. 中断后能否恢复模型、优化器、学习率与数据位置;
2. 换卡数或换并行度能否恢复;
3. 能否导出给目标推理引擎;
4. 保存时是否出现单 rank 全量模型峰值。

训练跑得快但恢复不了,不叫可用训练栈。

### 维度八:调试与维护

FSDP2 更贴近 PyTorch profiler、module 和参数语义;Megatron-Core 的并行约束更多,但大规模问题有更专门的日志和配方;DeepSpeed 的问题常跨代码、Engine、JSON 与上层框架。

团队熟悉度不是软因素。一个理论上快 5%、但故障只能靠少数人处理的栈,可能让整月有效吞吐更低。

### 维度九:硬件与供应商边界

PyTorch 原生路线通常更容易跟随多硬件后端;Megatron-Core 的最佳路径与 NVIDIA GPU、Transformer Engine、NCCL 结合最深;DeepSpeed 的硬件覆盖取决于具体版本和上层平台。

这不等于 Megatron 只能在一种机器上运行,而是说:**它最有辨识度的性能收益来自一套共同优化的 NVIDIA 软件栈。**

## 七、放进 RL 框架后,选择会怎样传导

RL 框架不是把训练后端藏起来就完事。后端选择至少向上传导四件事:

1. **模型覆盖**:HF 原生后端通常更快接新模型;Megatron 后端需要模型与权重映射适配。
2. **权重同步**:训练布局不同,转成 vLLM/SGLang 的 rollout 布局时重排方式不同。
3. **并行上限**:大 MoE 需要的 TP/PP/EP 能否表达,决定整套 RL 系统能不能扩。
4. **checkpoint**:训练中间态与最终可部署权重往往不是同一格式。

当前主流 RL 框架的选择也印证这条分野:

| 框架路线 | 训练后端倾向 | 选型含义 |
|---|---|---|
| verl、ROLL、NeMo-RL | 同时提供 FSDP2/DTensor 与 Megatron 路线 | 研究接入与规模优化分两档 |
| slime | Megatron 主路线 | 用较窄后端换直接、深度集成 |
| Miles | Megatron 主路线,另提供 FSDP2 | 大模型配方优先,同时给 HF 原生模型留入口 |
| OpenRLHF | DeepSpeed | 继承 ZeRO/offload 与既有生态 |

这些支持矩阵变化很快,当前状态见 RL框架对比 篇与各框架专篇。本文只解释为什么“一套 RL 框架要支持两个训练后端”不是功能重复。

## 八、场景决策表

| 场景 | 首先评估 | 为什么 | 主要风险 |
|---|---|---|---|
| 最新 HF Dense 模型,先跑通研究 | FSDP2 | 模型改动小,原生工具链直接 | 组合并行与专用 kernel 未必成熟 |
| 中等规模全参微调 | FSDP2 | 全分片已能解决主要容量问题 | 粒度与预取不当会通信过碎 |
| 超大 Dense,单层也放不下 | Megatron-Core | TP/PP/CP 是一等能力 | 模型与 checkpoint 适配成本 |
| 大 MoE,需要 EP 与拓扑优化 | Megatron-Core | 专家并行和 kernel 协同更深 | 配置约束、版本和硬件耦合 |
| 已有 DeepSpeed 平台 | DeepSpeed | 沿用脚本、运维和恢复体系 | 为换框架重写平台未必回本 |
| 必须 CPU/NVMe 扩容 | DeepSpeed 优先纳入实测 | 卸载链路成熟且完整 | PCIe、CPU 或磁盘成为瓶颈 |
| 同时追求 HF 接入与大规模路线 | 双后端上层框架 | 按模型阶段切换后端 | 两套 checkpoint 与正确性维护成本 |

### 一个实用决策顺序

1. 先问单层和激活是否需要 TP/PP/CP/EP;
2. 再问目标模型是否已有成熟 Megatron 适配;
3. 再问团队是否必须保留 Hugging Face 模型定义;
4. 再问 checkpoint、导出与故障恢复要求;
5. 最后才在可行方案里测吞吐。

如果第一问全是否,通常从 FSDP2 开始最省事;如果第一问已有多个是,讨论会自然转向 Megatron-Core。

## 九、公平压测应该锁死什么

至少锁死:

- 同一模型代码或明确记录模型实现差异;
- 同一数据、序列长度分布和 token 总量;
- 同一精度、优化器、激活重算和 loss;
- 同一全局 batch、micro-batch 与梯度累积;
- 同一硬件、网络和进程放置;
- 同一 checkpoint 频率与保存口径;
- 同样的 warm-up 与测量窗口。

同时报告:

- tokens/s 或有效样本/s;
- step 时间的计算、通信、数据与保存分解;
- 峰值显存;
- MFU 的公式与有效参数口径;
- 初始化、保存和恢复耗时;
- 数值一致性与最终质量。

只报 steady-state tokens/s 会掩盖模型转换、编译、保存和故障恢复的真实成本。

## 十、六个常见误区

### 误区一:FSDP2 只能做数据并行,Megatron 才能组合

FSDP2 可以通过 DeviceMesh 与 PyTorch TP/PP/CP 组合,TorchTitan 就是参考实现。真正差异是目标模型上的成熟度和协同深度,不是 API 能不能写出来。

### 误区二:Megatron 就等于 TP

Megatron-Core 已经包含 PP、CP、EP、Distributed Optimizer 与 Megatron-FSDP。TP 是它最早出名的一块,不是全部。

### 误区三:用了 Megatron-FSDP 就等于用了 PyTorch FSDP2

两者目标接近,布局与集成体系不同。一个偏逐参数 DTensor 和原生易用,一个偏连续缓冲区与 Megatron kernel 协同。

### 误区四:DeepSpeed 有 ZeRO-3,所以和 FSDP2 完全一样

分片思想相近,但接入层、配置覆盖、卸载、checkpoint 与训练循环边界不同。算法等价不等于系统等价。

### 误区五:模型越大越该直接上 Megatron

如果容量只卡在模型状态,FSDP2 可能已经足够。需要多维切计算、目标模型又有成熟适配时,Megatron 的优势才真正出现。

### 误区六:官方最大规模就是自己的可达规模

官方配置证明“这条路径存在”,不能证明你的模型、网络和版本能复现。先做最小正确性与恢复测试,再逐步扩卡。
