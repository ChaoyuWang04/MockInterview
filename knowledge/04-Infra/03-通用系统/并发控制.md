# 并发控制

一句话:这篇讲**单机多线程里那几件同步工具各自到底保证了什么**——为什么"看着没同时跑"的代码还是会错、什么时候一个原子变量就够、什么时候必须上锁、无锁结构省下的是哪一段开销又新欠了哪笔债。

## 一、同步在保证什么:互斥,和 happens-before

### 两个目标,不是一个

面试里最容易被追着问塌的一句话是"加锁就是不让两个线程同时执行"。这个说法只覆盖了一半:

- **互斥**:同一时刻只有一个线程待在临界区里。它保证的是"别人不会插到我这几步中间"。
- **happens-before(先行发生)**:线程 A 的写,对随后的线程 B **可见**,而且 A 在写之前做的事,B 也一并看得见。它保证的是"我改过的东西你读得到,而且顺序还对得上"。

**只有互斥不够,因为"没有同时执行"不等于"看得见"。** 就算两个线程在单核上分时轮转、物理上一刻也没重叠,只要它们之间没有一条 happens-before 边,下面三个地方都可以把你的写"藏起来":

| 谁在动手 | 它做了什么 |
|---|---|
| 编译器 | 把变量缓存进寄存器、把两条无依赖的赋值换序、把循环里"看起来没人改"的读提到循环外 |
| CPU 乱序执行 | 后面的指令先算完先退休,只保证单线程内的依赖看起来是对的 |
| 缓存与写缓冲(store buffer) | 写先落在本核的写缓冲里,别的核要过一会儿才看到,而且多个写到达的顺序可能和发出顺序不同 |

所以 `while (!flag) {}` 配一个普通 `bool flag = true` 的写法,可能永远转不出来——不是因为"同时执行",是因为编译器把 `flag` 提进了寄存器。**锁、原子操作、内存屏障做的事是同一件:在两个线程之间钉一条 happens-before 边**;互斥只是其中一部分工具顺带提供的性质。

### 选型的第一条判据:共享不变量有多大

先别急着比性能,先问一句:**这次要保护的"不变量"跨了几个变量?**

- 只有**一个**位置需要原子地读改写(计数器、标志位、单个指针交换)→ 原子操作够了。
- **多个字段必须一起更新、中间态不能被别人看见**(链表的 prev/next、余额和流水、size 和 buffer 指针)→ 老老实实用锁。原子操作只能把每个字段单独做原子,组合起来仍然会被人看到半成品。
- 只有当**锁上的争用被 profile 实测确认是瓶颈**时,才考虑无锁结构。

## 二、四种机制:原理、适合什么、风险

| 机制 | 原理 | 适合 | 主要风险 |
|---|---|---|---|
| 互斥锁 | 同一时刻只有一个线程进入临界区;解锁与随后的加锁之间建立 happens-before | 复合不变量、临界区短且逻辑容易证明 | 阻塞与上下文切换、死锁、优先级反转、持锁做慢事把别人全拖住 |
| 读写锁 | 读可并行、写独占 | 读**远**多于写,且读临界区本身有一定长度 | 写饥饿、自身状态维护开销、读区很短时反而更慢 |
| 原子操作 | CPU 的原子指令对**单个内存位置**做读改写 | 计数、标志、指针交换 | 只能保护有限状态;高争用下缓存行抖动 |
| 无锁结构 | CAS 循环推进共享结构,失败就重读重试 | 已实测的热点争用,且团队扛得住验证复杂度 | ABA、活锁、内存回收、弱内存序用错 |

### 锁的代价具体是什么

不是"锁慢",而是三笔账:**没争用时**,现代互斥锁的快路径就是一次原子读改写,几十个周期,并不贵;**一旦争上**,拿不到锁的线程要挂起,再被唤醒时是一次上下文切换,微秒量级,还丢了 L1/L2 里的热数据。真正致命的是另外两个:**死锁**(多把锁的获取顺序不一致,靠"全局固定加锁顺序"预防,不是靠运气),和**优先级反转**(低优先级线程持锁被抢占,高优先级线程只能干等,需要优先级继承之类的机制兜底)。

### 读写锁:读多不等于更快

这是本篇最容易答错的一条。读写锁**不是免费的并行**:

1. **加读锁本身要改共享状态。** 实现要记住"现在有几个读者",所以加一次读锁通常也是一次对共享计数的原子读改写——**那条缓存行照样在各个核之间来回弹**。临界区如果只有几纳秒(读一个字段),这笔固定开销就能反超它省下的并行收益,还不如一把普通互斥锁。
2. **状态机更复杂。** 要同时跟踪读者数、有没有写者在等,分支和原子操作都比互斥锁多。
3. **公平性要额外设计。** 读优先的实现里,只要读者源源不断到来,写者可能长期拿不到锁,这就是**写饥饿**;改成写优先又轮到读者被拖慢。很多实现的偏好是平台相关的,不能默认。

所以正确的回答形状是:**读写锁只在"读远多于写"且"读临界区足够长"且"实现的公平策略符合业务"三条同时成立时才更快**;临界区极短的场景,更该考虑的是原子操作,或者干脆把数据做成每线程一份、定期合并。

### 原子操作:争用时慢在缓存一致性

一个 `fetch_add` 在没人抢的时候只是几十个周期,但**多个核抢同一个原子变量时,那条缓存行必须在核之间独占传递**,每次都是一轮缓存一致性协议往返——核越多越慢,吞吐可能反而随线程数下降。两个直接后果:

- **热点计数器要分片**:每个线程(或每个核)一个独立计数,读的时候求和,把争用降到零。
- **警惕伪共享(false sharing)**:两个逻辑上无关的变量落在同一条缓存行(常见 64 字节)里,一个核写 A 就把另一个核的 B 打无效。修法是按缓存行对齐/填充。

## 三、无锁结构与 ABA

### CAS 循环是怎么推进的

无锁结构的骨架都是同一个形状:读出当前值 → 在本地算出新值 → CAS(比较并交换)写回,别人插队导致比较失败就重来。

```cpp
// 无锁栈的 push:失败就用 CAS 帮我们重读的新值再试一次
void push(Node* n) {
  Node* old = head.load(std::memory_order_relaxed);
  do {
    n->next = old;                       // 先把新节点挂到当前栈顶后面
  } while (!head.compare_exchange_weak(  // 失败时 old 会被自动更新为最新的 head
      old, n,
      std::memory_order_release,         // 成功:让别人看到 n->next 已写好
      std::memory_order_relaxed));
}
```

**无锁(lock-free)的含义是"总有某个线程在推进",不是"每个线程都不等待",更不是"一定更快"。** 争用高时大量 CAS 失败重试,做的是无用功;`push` 这种简单操作还好,复杂结构可能陷入活锁(大家互相把对方顶回去)。

### ABA:CAS 被骗了

CAS 只比较"这个位置的值还是不是我读到的那个",它没法区分"一直没变"和"变过又变回来"。经典场景是无锁栈:

1. 线程 1 读到栈顶是 A,准备把 head 从 A 换成 `A->next`(当时是 B),此时被调度出去;
2. 线程 2 弹出 A,又弹出 B,把 B 释放掉,然后把 A **重新压回**栈顶,此时 `A->next` 已经是 C;
3. 线程 1 醒来,CAS 看到 head 仍然是 A,**成功**,把 head 写成它记住的 B——而 B 早就被释放了。

栈从此指向一块已释放内存。注意问题的根源是**指针值被复用**:同一个地址被 free 再 malloc 出来,值相同但语义全变了。

### 三条解法,按对象生命周期选

| 手段 | 怎么做 | 代价与适用面 |
|---|---|---|
| **版本号 / 带标记指针** | 把指针和一个单调递增的计数打包成一个可原子操作的整体(宽 CAS,或借用指针里对齐留出的低位),CAS 时连计数一起比 | 实现最简单;但**它只解决"CAS 误判",不解决"能不能安全 free"**——旧节点仍可能正被别人读。计数位数太少还会绕回 |
| **hazard pointer(风险指针)** | 每个线程把"我正在读的指针"发布到自己的槽位;要回收节点的线程扫一遍所有槽位,有人挂着就先攒起来晚点再删 | 读路径每保护一个指针要一次写 + 一次屏障;好处是**内存上界确定**(每线程待回收节点数有界)。适合读临界区可能很长、不能容忍内存无限涨的场景 |
| **epoch / RCU(延迟回收)** | 读者进出临界区只更新一个本地的 epoch 标记,几乎零开销;回收方等一个**宽限期**——所有先前开始的读者都退出后——再统一释放 | 读路径最快;代价是**内存没有硬上界**:只要有一个读者卡住不退出,回收就一直推不动。要求读临界区短、不阻塞不睡眠 |

一句话选型:**读多、读区短、能保证读者很快退出 → epoch/RCU;读区长短不定或必须卡住内存用量 → hazard pointer;只是想让 CAS 别误判、回收另有办法(比如节点从不归还给分配器)→ 版本号。**

## 四、C++ 内存序:每一档买到了什么

原子操作除了"这一步不可分割",还要指定它对**别的内存访问**施加什么顺序约束。约束越弱越快,也越难证明正确。

| 内存序 | 保证什么 | 典型用途 |
|---|---|---|
| `relaxed` | **只有原子性**,以及同一个原子对象上的修改顺序自洽。与其它位置的读写没有任何顺序关系 | 纯统计计数器;CAS 循环里那个用来重读的 load |
| `acquire`(用于读) | **禁止本线程后续的访问被重排到这次读之前**;并且能看到配对 release 写之前的一切 | 取标志位/取栈顶后再读数据 |
| `release`(用于写) | **禁止本线程此前的访问被重排到这次写之后**,把之前准备好的数据一起"发布"出去 | 数据填好后再置 ready 标志 |
| `acq_rel` | 用于读改写(CAS、fetch_add),同时具备上面两条 | 无锁结构里推进状态的那一步 |
| `seq_cst` | 在 acquire/release 之上,再加**所有 seq_cst 操作有一个单一全序**,所有线程看到的顺序一致 | 默认值;需要多个变量之间全局一致顺序时 |
| `consume` | 标准里定义为只沿数据依赖传递顺序 | **实践中不要用**:主流编译器基本按 acquire 处理,标准也已加注建议改用 acquire |

`release` 和 `acquire` 必须**成对**用在同一个原子变量上,才能钉出那条 happens-before 边:

```cpp
// 生产者
data = 42;                              // 普通写
ready.store(true, std::memory_order_release);  // 发布:此前的写不许越到这句后面

// 消费者
while (!ready.load(std::memory_order_acquire)) {}  // 获取:后续读不许越到这句前面
assert(data == 42);                     // 成立:release/acquire 配对建立了 happens-before
```

**为什么 `seq_cst` 还要更贵。** acquire/release 只约束"配对的那一对"看到的顺序,不同线程观察**多个不相关原子变量**的先后仍可能各说各话;`seq_cst` 额外要求存在一个全局统一的顺序,x86 上这通常意味着 store 后要加一道全屏障,把写缓冲刷干净。

纪律很明确:**先用锁或 `seq_cst` 把正确性证出来,再在 profile 确实指向这里时逐步放宽**。反过来"先写 relaxed 再调试"几乎必然踩坑——弱内存序的 bug 在 x86 上可能一年不复现,换到 ARM 立刻炸。

## 五、Redis 线程模型:串行语义买到了什么

### 好处:整条数据结构不用加锁

Redis 官方文档的说法是"**mostly single threaded**"——一个进程用 I/O 多路复用同时盯住成千上万个连接,但**命令是一条接一条执行的**。这个选择换来三件事:

1. **数据结构完全不用加细粒度锁。** 没有读写锁、没有 CAS 循环、没有 ABA,dict / skiplist / listpack 都按单线程写,省下的不只是锁开销,更是一整类并发 bug。
2. **一致性推理简单。** 单条命令天然原子;`INCR`、`SETNX`、Lua 脚本执行期间没人能插进来。
3. **没有上下文切换和缓存行争抢**,单核就能把简单命令压到微秒以下。

代价是**单个实例吃不满多核**——但官方文档也点明:多数部署先撞到的是内存和网络上限,不是 CPU。

### 但它不是"纯单线程"

这是追问里最想听的一句。至少三类工作不在主线程的命令循环里:

| 工作 | 谁在做 |
|---|---|
| 网络 socket 的读写与协议解析 | 可由 `io-threads` 配置的 I/O 线程分担;**命令本身仍在主线程执行** |
| AOF 的 fsync、大对象的异步释放(lazy free) | 后台线程。官方文档明确写了从很早的版本起就用线程做慢速磁盘 I/O |
| RDB 快照、AOF 重写 | **fork 出的子进程**,靠写时复制拿一份数据视图 |

顺带一个常被追的点:**fork 这个动作本身是在主线程做的**,要复制页表,实例越大越久——官方文档给的量级是物理机上约每 GB 十毫秒,老式 Xen 虚拟机能差到每 GB 几百毫秒。所以"后台持久化"并不是完全不影响前台延迟。

### 串行 ≠ 不会互相拖慢

**恰恰相反:正因为串行,一条慢命令会让所有其他客户端排队等它。** `KEYS`、大集合的 `SUNION`/`SORT`、一次取回几万个元素的范围查询,都会把事件循环占住;这也是生产上禁用 `KEYS`、改用 `SCAN` 增量迭代的原因。串行简化的是**一致性**,不是**延迟**。排查手段是 slowlog 和延迟监控。

注:Redis 的数据结构与底层编码(listpack/skiplist、集群 slot 等)见 缓存系统 篇;跨进程的分布式锁见 分布式系统 篇,本篇只谈单机多线程。另外 GPU 上的 stream / event 虽然也叫"同步",但那是**设备侧任务之间的依赖编排**(kernel 与拷贝谁先谁后),不是多个线程抢同一份内存,见 CUDA流与异步执行 篇。
