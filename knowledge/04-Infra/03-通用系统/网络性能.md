# 网络性能

一句话:这篇讲**一个包从网卡进来、爬过内核协议栈、被应用读走的这一路上,会在哪几个地方排队或被丢掉**,以及怎么用指标先定位、再动参数。讲的是**单台 Linux 主机的网络栈**;GPU 之间那条数据面(NVLink、RDMA、胖树组网)是设备与集群互联,层次完全不同,见 GPU互联与组网 篇。

## 一、先定位再调参:不这么做,这道题就答废了

网上的"Linux 网络调优参数大全"最大的问题是:它默认你已经知道瓶颈在哪。**同一份 sysctl,在建连受限的服务上有用,在带宽受限的服务上一点用没有,在 CPU 受限的服务上还可能更慢**(比如无脑开 RPS,给本来就忙的核多加一层软件转发)。所以先回答"包卡在哪",再谈改什么。

五个候选瓶颈,各有各的证据:

| 瓶颈在哪 | 典型现象 | 看什么证据 |
|---|---|---|
| **连接建立** | 客户端超时/被 reset,QPS 上不去但 CPU 和带宽都不满 | `ListenOverflows`/`ListenDrops` 在涨、`ss -ltn` 的 Recv-Q 长期贴着 Send-Q |
| **队列(内核各层)** | 丢包与重传随负载非线性上涨 | 网卡 ring 的 drop 计数、`/proc/net/softnet_stat`、qdisc 的 drop |
| **带宽 / 链路** | 吞吐卡在一个平台不动,窗口撑不开 | 重传率、`ss -ti` 里的 cwnd 和 rtt、链路利用率 |
| **CPU** | 软中断吃掉几个核,业务线程抢不到 CPU | `mpstat` 的 `%soft` 是否集中在一两个核、上下文切换 |
| **应用自身** | 网络各项计数都干净,延迟却大 | 服务端排队时间、锁与慢下游(方法见 性能分析与Profiling 篇) |

```bash
# 建连侧:全连接队列是否溢出、半连接是否被丢
ss -ltn                      # 监听 socket:Recv-Q=已完成待 accept 数, Send-Q=队列上限
nstat -az | grep -E 'ListenOverflows|ListenDrops'   # 这两个在涨 = 建连侧丢了
# 传输侧:每条连接的窗口、RTT、重传
ss -tin state established    # 看 cwnd / rtt / retrans / bytes_retrans
nstat -az | grep -E 'TcpRetransSegs|TcpExtTCPLostRetransmit'
# 缓冲与 CPU 侧
ss -tm                       # skmem:收发缓冲有没有顶到上限
cat /proc/net/softnet_stat   # 第2列 dropped=每CPU backlog 满;第3列 time_squeeze=软中断预算用光
ethtool -S eth0 | grep -i -E 'drop|miss|err'        # 网卡 ring 溢出
mpstat -P ALL 1              # %soft 是不是全压在一两个核上
```

**答题时先说这一段。** 直接背 sysctl 清单是这道题最大的失分点——面试官想听的是排查链路,不是记忆力。

## 二、三层缓冲与队列:每一层满了分别长什么样

包从网卡到应用要过三道关,**它们解决的问题不同,满了的症状也完全不同**,不能混着调。

| 层 | 谁在排队 | 满了会怎样(症状) | 相关旋钮 |
|---|---|---|---|
| 建连队列 | 还没被 `accept()` 走的连接 | 建连超时或被 reset,已建立的连接毫无异常 | `backlog`、`somaxconn`、`tcp_max_syn_backlog`、`syncookies` |
| socket 收发缓冲 | 已建立连接上的字节 | 吞吐上不去、发送方被 `send()` 阻塞、接收窗口撑不开 | `tcp_rmem`/`tcp_wmem`、`SO_RCVBUF`/`SO_SNDBUF` |
| 网卡与内核之间 | 还没被协议栈处理的原始包 | 丢包与重传随流量涨、软中断打满某个核 | 网卡 ring 大小、`netdev_max_backlog`、`netdev_budget`、qdisc |

### 建连路径上其实是两个队列

内核对一个监听 socket 维护两条队列:**半连接队列**(收到 SYN、回了 SYN-ACK、还在等对方最后那个 ACK,状态 SYN_RECV)和**全连接队列**(三次握手已完成,等应用调 `accept()` 取走)。

- **全连接队列**上限 = `min(listen() 的 backlog, net.core.somaxconn)`,超了会被**静默截断**(`man 2 listen` 口径;`somaxconn` 默认在 Linux 5.4 起是 4096,更早的内核是 128)。满了以后默认行为不是回 RST,而是**丢掉对方那个 ACK**:客户端以为连上了、开始发数据,服务端却当没听见,客户端只能等重传定时器——**一次溢出就是一条秒级的尾延迟**,而且日志上什么都看不到,只有 `ListenOverflows` 在涨。想让它立刻报错方便定位,可以打开 `tcp_abort_on_overflow`(内核文档口径:默认 FALSE),代价是把静默排队换成明确的连接重置。
- **半连接队列**受 `tcp_max_syn_backlog` 约束,满了新 SYN 直接丢。这条在真实 SYN flood 和"瞬时大量建连"下表现一样,所以先分清是攻击还是短连接风暴。开了 `tcp_syncookies`(内核文档口径:默认 1)之后,内核不再为半连接分配状态,而是把状态编码进序列号里,**此时 `tcp_max_syn_backlog` 被忽略**(`man 2 listen` 明确写了这一条)。代价是握手期协商的部分选项要靠时间戳字段挟带,没开 timestamps 时窗口缩放等选项会丢,长肥链路的吞吐反而变差。

**根治手段永远是"让应用 accept 得更快"**(见第四节),调大 backlog 只是把溢出推迟。

### socket 缓冲区:自动调优在管,别急着手工设

Linux 默认开着接收缓冲自动调优(`tcp_moderate_rcvbuf`,内核文档口径默认 1),内核会**按这条路径实际需要的大小**动态伸缩接收缓冲,上限不超过 `tcp_rmem` 的第三个值。这就是为什么绝大多数服务根本不需要碰这两个参数。

需要动它的只有一种情况:**带宽时延积(BDP)超过了当前上限**。BDP = 带宽 × RTT,意思是"这条链路上同时能装下多少在途数据";窗口小于 BDP,链路就永远填不满。算两笔账就清楚了:

- 同机房:25 Gb/s × 0.2 ms RTT ≈ **625 KB**——远小于默认上限,调大缓冲毫无收益。
- 跨地域:10 Gb/s × 50 ms RTT ≈ **62.5 MB**——这才是需要把 `tcp_rmem[2]` 抬上去的场景。

参数本身的默认值**跟着内核版本和机器内存变**,这也是不能抄数字的直接证据:同一个 `tcp_rmem` 中间值,内核最新文档写 131072,`man 7 tcp` 至今还写 87380;上限则是"随内存在 131072 到 32 MB 之间"。**以你机器上 `sysctl net.ipv4.tcp_rmem` 读到的为准。**

手工设定和自动调优的关系要说清:应用一旦 `setsockopt(SO_RCVBUF)`,这个 socket 的缓冲就被标记为用户锁定,**自动调优对它失效**,从此固定用你给的值;而且 `tcp_rmem[2]` 不再是它的上限,真正的上限变成 `net.core.rmem_max`。所以手工设小了会直接卡住吞吐——**这是"照抄调优文章反而变慢"最常见的一种**。

### 网卡与内核之间

网卡把包 DMA 进 ring buffer,再由软中断收上来。ring 满了在网卡计数器里体现为 drop/miss;软中断一轮预算(`netdev_budget`)用光但包没收完,记在 `/proc/net/softnet_stat` 的 time_squeeze 列;走 RPS 时每 CPU 的 backlog 满了记在 dropped 列。发送侧则是 qdisc 排队。**这一层的症状是"随流量上涨的丢包与重传",不是建连失败**——分不清这两个,调错层的概率极高。

## 三、拥塞控制:它在回答一个问题

拥塞控制解决的是:**发送方看不见网络中间的状况,怎么估出"现在能多快发"**。流控(接收窗口)管的是"对方来不来得及收",拥塞控制管的是"中间的路堵不堵",两回事。

不同算法的分歧只在一点:**拿什么当拥塞信号**。

| 算法 | 拥塞信号 | 什么链路上更合适 | 代价 / 风险 |
|---|---|---|---|
| Reno / NewReno | 丢包,窗口线性增长 | 短、稳、低 BDP 的链路 | 长肥管道上窗口涨太慢,利用率低 |
| **CUBIC**(多数发行版默认) | 丢包,但窗口按"距上次丢包的时间"的三次函数增长 | **高 BDP、长 RTT**——RFC 9438 的设计目标就是修 Reno 在这类链路上的低利用率 | 仍以丢包为信号:遇到深缓冲会先把队列填满再退(时延被推高);遇到无线随机误码会误判成拥塞 |
| **BBR** | 主动估计**瓶颈带宽**和**最小 RTT**,按 BDP 定发送速率,不等丢包 | 有随机丢包的长距离链路、深缓冲链路 | 和丢包型算法共存时的公平性有争议;不同版本行为差别大,**说 BBR 必须说清是哪一版** |

选型口径,一句话:**先问"这条链路上的丢包是不是拥塞的可靠信号"**。是(数据中心内、有线、缓冲适中)→ 丢包型算法就够;不是(跨地域、无线、深缓冲)→ 才轮到 BBR 这类基于带宽与时延建模的算法。

反过来的判据同样重要:**同机房部署的推理服务,RTT 是几十到几百微秒、几乎不丢包,拥塞控制根本没有发挥空间,换算法的收益接近零**。这道题里把拥塞控制答成"上来就换 BBR",等于承认没定位过。

## 四、epoll / SO_REUSEPORT / 中断亲和性:三个层面的三件事

这三个经常被一口气背出来,其实**解决的问题毫不相干**,面试官问这题就是看你分不分得清。

| 机制 | 在哪一层 | 解决什么 | 不解决什么 |
|---|---|---|---|
| **epoll** | 应用与内核之间的 IO 模型 | 一个线程盯住几万条连接时,**怎么只被就绪的那几条唤醒** | 不改变谁来 accept,也不改变哪个 CPU 收包 |
| **SO_REUSEPORT** | 连接分发 | 多个进程/线程**各自监听同一个端口**,由内核按流哈希把新连接分给其中一个 | 不改变单条连接的处理效率,也不管软中断落在哪 |
| **中断亲和性 / RPS / RFS** | 收包路径与 CPU 的绑定 | 决定**哪些核去做协议栈处理**,别让软中断全压在一个核上 | 不减少系统调用,也不消除 accept 竞争 |

### epoll:省的是"问一遍"的成本

`select`/`poll` 每次调用都要把整个 fd 集合传进内核、再全量扫一遍,复杂度随连接总数走。epoll 把关注集合**常驻内核**,只在事件发生时把就绪的 fd 放进就绪队列,一次 `epoll_wait` 返回的规模只和**活跃连接数**有关,与总连接数无关。这就是"十万连接、几百活跃"这类场景的标准解法。配套要点:socket 必须设成非阻塞,否则一次读写把整个事件循环卡住;边缘触发要一次读到 `EAGAIN`,漏读就丢事件。线程之间怎么同步、锁怎么选,见 并发控制 篇。

### SO_REUSEPORT:消掉的是单点 accept

传统写法是一个监听 socket、多个 worker 抢着 accept,这个抢点本身会成为瓶颈,而且惊群和负载不均都出在这里。`SO_REUSEPORT`(Linux 3.9 起)允许多个 socket 绑同一地址端口,**内核按连接四元组哈希直接选一个 socket 投递**,每个 worker 有自己的全连接队列。注意两条硬约束:必须在 `bind()` 之前对**每个** socket 都设上;为防端口劫持,所有进程的有效 UID 必须相同(`man 7 socket` 口径)。代价是滚动重启时正在排队的连接可能落到即将退出的进程上。

### 中断亲和性 / RPS / RFS:让收包和处理落在合适的核

- **IRQ 亲和性**:多队列网卡的每个接收队列有自己的中断,通过 `/proc/irq/<n>/smp_affinity` 把它们摊到不同的核。默认由 `irqbalance` 管,高性能场景常改成手工固定,避免中断在核之间飘导致缓存反复失效。
- **RSS**:**网卡硬件**按包哈希分到多个接收队列,是最省 CPU 的分摊方式。
- **RPS**:RSS 的**软件版**,在收包路径上把包转投到目标 CPU 的 backlog 上做协议栈处理。内核文档写得很清楚:**它是给队列数不足或不支持 RSS 的网卡兜底的**——网卡本来就多队列且中断已经摊开时,RPS 只是多加一层开销。
- **RFS**:在 RPS 之上再考虑**应用线程在哪个核**,把该流的内核处理也送到那个核上,目的是提高数据缓存命中率。

组合起来的常见形态:多队列网卡 + IRQ 亲和性摊到若干核 → 多 worker + `SO_REUSEPORT` 各自监听 → 每个 worker 内部 epoll 事件循环。三层各管一层,缺哪层就是哪层的症状。

## 五、参数要按负载实测,不照抄数值

前面所有小节里凡是出现数字的地方,都写清楚了是"内核最新文档口径""man 页口径"还是"按 BDP 算出来的示例",没有一个是"推荐值"。原因很实在:

- **默认值随内核版本变**,`somaxconn` 从 128 变到 4096、`tcp_rmem` 中间值从 87380 变到 131072 都是例子;抄一篇三年前的文章,可能把新内核的默认值改小。
- **默认值随机器内存变**,缓冲上限本身就是内核按 RAM 算出来的。
- **有些开关已经不存在了**:`tcp_tw_recycle` 早已从内核移除;`tcp_tw_reuse` 也不是万能开关,它只对**主动发起连接的那一侧**有意义,而且当前内核默认值是"仅回环流量"。把这两个当标准调优项写进清单,是典型的照抄痕迹。

可操作的做法:**先记基线,再单变量改。** 基线至少包括吞吐、RTT、重传率、丢包、各层队列长度、软中断 CPU 占比和业务 P99;每次只改一组参数,用**同一负载**复测同一组指标;改完没有可测的改善就回滚,别留一屋子来历不明的配置。压测要用开环(固定到达率)而不是闭环,否则永远压不出排队爆炸;吞吐与延迟指标本身怎么定义、怎么测,见 推理服务指标 篇。

## 六、追问:GPU 推理已经是瓶颈时,网络还值不值得优化

### 先把一次请求的时间账拆开

| 时间片段 | 由谁决定 | 网络优化管不管得着 |
|---|---|---|
| 建连(TCP 握手 + TLS) | RTT × 握手轮数 | **管**,而且是连接复用一刀就能砍掉的 |
| 请求上行 / 响应下行 | 带宽、包大小、Nagle 与延迟 ACK 的相互作用 | **管** |
| 服务端排队(等被调度进 batch) | 到达率与 GPU 服务率的关系 | **管不着**(除非队列溢出制造了重传) |
| GPU 计算(prefill + 逐 token decode) | 算力、batch、模型 | **完全管不着** |

结论就一句:**网络优化改善的是尾延迟和连接容量,不是吞吐上限。** 吞吐上限由 GPU 一步能处理多少 token 决定,网络再快也变不出算力。

### 什么时候该停下来别调网络了

判据是可量化的:把上表四项各自测出来,如果**网络相关项(建连 + 传输 + 重传)加起来只占端到端时间的百分之几**,而 GPU 利用率长期高位、排队时间是大头,那就停——继续调网络的收益上限已经被算死了。这时候该做的是批处理、量化、投机解码或者直接扩 GPU。

### 但即使 GPU 饱和,这几件事仍然值得做

1. **连接复用**。长连接/连接池省掉每次的握手 RTT 和 TLS 轮次,还顺带不再批量制造 TIME_WAIT。Agent 那种一次任务里几十上百次调用的场景,省下来的是实打实的墙上时间。
2. **别让队列溢出**。全连接队列一溢出,客户端就要等重传定时器,一次就是秒级尾延迟——**这条跟 GPU 快慢完全无关**,却会把 P99 打得很难看。同理,流式输出每个 token 都是小包,Nagle 和对端的延迟 ACK 撞上会产生规律性的等待停顿,`TCP_NODELAY` 该开就开;这类问题只出现在尾部分位数上,看均值永远发现不了。
3. **把 CPU 从软中断里省出来**。高 QPS 小包场景下软中断能吃掉好几个核,而这些核本来要做 tokenize、反序列化、采样和调度。**CPU 被抢走的直接后果是喂不满 GPU,GPU 利用率反而掉下来**——这是"网络优化提升了 GPU 吞吐"唯一站得住的路径。

边界:跨实例的请求分发、慢节点熔断与限流降级见 负载均衡 篇;AllReduce 这类集合通信算子与通信计算 overlap 见 集合通信 篇。
