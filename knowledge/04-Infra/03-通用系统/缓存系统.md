# 缓存系统

一句话:这篇讲**通用缓存中间件里那套数据结构到底怎么存、怎么查**——以 Redis 为样本,把"逻辑类型和底层编码是两层""批量命令省的是往返不是查找""有序集合怎么同时做到点查快和范围查快"这三件事讲透。

> 先排掉一个同名不同物:LLM 推理里的 "KV 缓存""前缀缓存"是把注意力的 K/V 张量留在显存里复用,和这里讲的缓存中间件毫无关系,机制见 KVCache 篇、RadixAttention 篇。

## 一、逻辑类型与底层编码:先把这两层分开

被问"Redis 常用数据结构有哪些",只报 String/Hash/List/Set/ZSet 的名字只答了一半。Redis 的类型是**两层**的:

- **逻辑类型**:命令层面看到的东西,决定这个 key 能用哪些命令,`TYPE key` 返回的那个。
- **底层编码**:同一个逻辑类型在内存里真实的存法,`OBJECT ENCODING key` 返回的那个。

**为什么要分两层:因为 Redis 想在"小集合省内存"和"大集合操作快"上两头都占。** 集合小的时候用一段连续内存顺序存,省掉哈希表和链表节点的全部指针与对象头,还对 CPU cache 友好;元素一多线性扫描顶不住了,再换成哈希表、跳表这类真正的索引结构。官方在讲这套特殊编码时给的量级是"最多省 10 倍内存,平均省 5 倍"。

### 常用逻辑类型

| 逻辑类型 | 是什么 | 典型用途 |
|---|---|---|
| String | 一段字节;纯数字时可当计数器原子加减 | 缓存对象、计数器、限流 |
| Hash | 字段 → 值的映射,像一个对象 | 一个实体的多个字段共用一个 key |
| List | 按插入顺序排的字符串序列,两端可进出 | 队列、最近 N 条 |
| Set | 无序、去重的集合,支持交并差 | 标签、去重、共同好友 |
| **ZSet(Sorted Set)** | 每个 member 带一个 double 型 score,**按 score 全局有序** | 排行榜、延时队列、按分数取区间 |
| Stream | append-only 的事件日志,自带消费组 | 消息流、事件溯源 |
| Bitmap / HyperLogLog | 建在 String 上的位操作 / 基数估算 | 签到、UV 估算 |

新版本官方文档里还列了 JSON、时间序列、地理索引、向量集合等(不少历史上来自模块),面试报上面这七类就够,多报反而要解释哪些是核心哪些是扩展。

### 同一种类型会按大小换编码

下表是 **Redis 7.0 及以后**的口径,默认值取自官方内存优化文档:

| 逻辑类型 | 小而紧凑时 | 超过阈值后 | 阈值配置项(官方文档所列默认值) |
|---|---|---|---|
| Hash | listpack | hashtable | `hash-max-listpack-entries 512` / `hash-max-listpack-value 64` |
| **ZSet** | listpack | **skiplist + dict** | `zset-max-listpack-entries 128` / `zset-max-listpack-value 64` |
| Set | 全是整数时用 intset;7.2 起也有 listpack | hashtable | `set-max-intset-entries 512`;7.2 起加 `set-max-listpack-entries 128` / `set-max-listpack-value 64` |
| List | 若干 listpack 串成的 quicklist | 靠单节点大小上限控制 | list 侧配置项跨版本改过名,数字别背 |
| String | 纯整数走 int,短字符串走 embstr | raw | 由长度和内容决定,没有用户可调阈值 |

**版本口径是这题的送分点也是扣分点**:Redis ≤ 6.2 时这批参数叫 `*-ziplist-*`(`zset-max-ziplist-entries` 之类),7.0 起统一换成 `*-listpack-*`。答 ziplist 会直接暴露资料是旧的;但要知道 listpack 是 ziplist 的替代实现——它去掉了"每项记录前一项长度"这个字段,因而没有 ziplist 那种改一项引发连锁更新的问题。

注意两个条件是**或**的关系:**元素个数**超了要转,**单个元素长度**超了也要转。所以往 ZSET 里塞 JSON 字符串当 member,常常只放几个就转成 skiplist 了。

```
> ZADD board 1 alice
> OBJECT ENCODING board
"listpack"            # 小集合:member、score 顺序排在一段连续内存里
                      # ...(循环写入 200 个成员,超过 zset-max-listpack-entries)
> OBJECT ENCODING board
"skiplist"            # 转成 dict + skiplist 两份索引
```

转换是**只进不退的**:官方文档只承诺"超出配置上限就自动转成普通编码",没有承诺反向转回来。所以一个曾经涨到一万成员、后来只剩三个的 ZSET,通常还是 skiplist——"删了大半数据内存却没降"经常就是这个原因。

## 二、MGET:它省掉的是往返,不是查找

单实例收到 `MGET k1 ... kK` 后做的事:解析**一次**协议,然后在**一个命令执行周期内**对 K 个 key 依次做字典查找,把 K 个结果拼成一个数组回复发回去。官方文档给的复杂度是 "O(N) where N is the number of keys to retrieve",也就是约 $O(K)$。

$$
T_{\text{MGET}} \approx T_{\text{RTT}} + T_{\text{parse}} + K \cdot T_{\text{lookup}}
$$

这个式子在说:**K 次哈希查找一次都没少,少掉的是另外 K−1 次网络往返和 K−1 次协议解析。**

最容易答错的一句是"MGET 把 K 次查找变成了一次哈希"。**没有这回事**——主键空间就是一张哈希表,K 个 key 就是 K 次独立查找,变不出捷径。它的价值全在摊薄固定开销:一次跨机房 RTT 是几百微秒到几毫秒,一次内存哈希查找是几十到几百纳秒,**K 不大时时间几乎全花在往返上**,这才是批量命令能提速一两个数量级的真实来源。

由此推出两条边界:

- **K 很大就不再稳赚**。往返只省了一次,而 $K \cdot T_{\text{lookup}}$ 和回复体积是线性涨的;涨到一定程度,收益被组装和发送大回复的时间淹没。
- **MGET 和 pipeline 省的是同一样东西,但原子性不同**。MGET 是一条命令,执行期间不会被别的命令插进来;pipeline 只是把多条命令攒在一个包里发,中间**可以**插进其他客户端的写。要"省往返"两者都行;要"这 K 个值来自同一时刻",只有 MGET(或 MULTI/EXEC、Lua)做得到。

## 三、Cluster 边界:多 key 命令为什么会被拒

Redis Cluster 把键空间切成 **16384 个 slot**,按 `HASH_SLOT = CRC16(key) mod 16384` 定位,每个主节点负责其中一部分。命令由持有那个 slot 的节点执行——而一条命令只能发给一个节点,所以官方规范写得很直白:**复杂多 key 命令只在所有 key 都哈希到同一个 slot 时才实现**。key 分散在不同 slot 上,节点回一个 `CROSSSLOT` 错误。

规范给了一个逃生口:**hash tag**。key 里带 `{...}` 时,只有第一对大括号之间那段参与哈希,于是 `{user:1000}.name` 和 `{user:1000}.surname` 必定同槽,MGET/MSET 就能用。代价要说出来:**你亲手制造了一个热点**——同 tag 下所有 key 永远压在同一个节点上,扩容时也永远不会被拆开。

**跨 slot 的 MGET 能不能保证原子性?不能,而且严格说它根本不是一条 MGET。** 客户端(Lettuce、go-redis 的 cluster 实现等)能做的只有:按 slot 把 K 个 key 分组,并发发出 N 条子请求,收齐后按原顺序拼回去。调用方看着像一条 MGET,实际是 **N 条独立命令**——中间完全可以有别的客户端改掉其中某个 key,拿回来的 K 个值不属于同一时刻。能拿到结果,不能叫原子。

还有一个容易漏的坑:**即使 key 都同槽,槽正在迁移时多 key 命令也可能失败**。规范里明确写了,key 在源节点和目标节点之间被拆开时会返回 `-TRYAGAIN`,客户端要么等一会重试,要么把错误报上去。所以"用了 hash tag 就万无一失"是错的,重试逻辑省不掉。

**高并发下还要限制单次 key 数量。** 核心命令是串行执行的(线程模型见 并发控制 篇),一条要返回几万个值的 MGET,在组装和发送这段大回复的时间里,后面所有请求都在排队——P99 就是这么被一条"看起来只是批量读"的命令拉爆的。工程上把单次上限定在几十到几百量级,再大自己分批。

## 四、ZSET 在 Redis 7 里的编码与复杂度

ZSET 要同时满足两个诉求:**按 member 点查 score**(`ZSCORE user:42`),和**按 score 有序取一段**(排行榜前 100)。单一结构很难两头都快,所以大 ZSET 干脆同时维护两份索引,指向同一批成员:

| | 结构 | 负责什么 | 为什么是它 |
|---|---|---|---|
| `dict` | 哈希表,member → score | `ZSCORE` 这类点查 | 哈希表天然 $O(1)$,跳表做不到 |
| `skiplist` | 按 (score, member) 排序的多层链表 | `ZADD` / `ZRANGE` / `ZRANK` | 有序 + 可从任意位置顺序遍历,哈希表做不到 |

小 ZSET 则只用一份 **listpack**:一段连续内存,`member, score, member, score, ...` 顺序排,查一个成员就从头线性扫。元素只有几十个时这反而更快——**扫一段连续内存比跳几次指针还便宜**,而且省掉了两份索引的全部指针开销。

### 三种操作是三种复杂度

| 操作 | 命令 | listpack 编码 | skiplist + dict 编码 | 官方文档口径 |
|---|---|---|---|---|
| 点查 score | `ZSCORE` | $O(n)$ 线性扫,但 $n$ 很小 | $O(1)$,走 dict | `O(1)` |
| 插入 / 更新 | `ZADD` | $O(n)$,要挪内存保持有序 | $O(\log N)$ | "O(log(N)) for each item added" |
| 范围查询 | `ZRANGE` | $O(n)$ | $O(\log N + M)$ | "O(log(N)+M) ... M the number of elements returned" |

**"ZSET 的复杂度是 $O(\log N)$"这句话同时犯了两个错**:把 `ZSCORE` 说成 $O(\log N)$ 是低估——它走 dict,白扔掉了这份索引的价值;把 `ZRANGE` 说成 $O(\log N)$ 是漏项:

$$
T_{\text{ZRANGE}} = O(\log N) + O(M)
$$

前一项是"跳几层找到起点",后一项是"沿最底层链表往后走 $M$ 步,把这些成员序列化进回复"。**线上事故几乎全出在后一项**:$N$ 从十万涨到一千万,起点也就多跳几步;但 $M$ 从 10 开到 100000,就是一次几十毫秒的停顿,而这段时间是在串行的命令执行里花掉的。

### 为什么是跳表,不是红黑树

skiplist 的卖点是**用概率平衡换实现简单**:每个新节点抛硬币决定长几层,不做旋转、不维护平衡因子,插入删除的代码短得多,期望复杂度和平衡树同阶。对一个要长期维护、还要支持"按排名取第 k 个"(每层指针额外记跨度即可)和"按分数区间正反向遍历"的内存数据库,这个取舍很划算。代价是**只有期望保证没有最坏保证**——但正如原论文所说,没有哪个输入序列能稳定触发它的最坏情况。

## 五、和 B+ 树比:面向内存与面向磁盘的分野

先把结论摆正:**这不是谁更快,是两种设计目标的分野**。

| | skiplist(Redis ZSET) | B+ 树(如 InnoDB 索引) |
|---|---|---|
| 一个节点装多少 | 一个成员 + 几个指针 | 一整页(典型 16 KB),几百个键 |
| 分支因子 | 期望 2(抛硬币决定层数) | 几百 —— 几亿行也只有三四层 |
| 下一层的代价 | 一次内存跳转,几十纳秒 | 可能是一次磁盘/SSD I/O,几十微秒起 |
| 范围扫描 | 沿最底层链表逐个走,每步都是随机内存访问 | 叶子页之间有链表,**一次 I/O 拿回整页几百条,顺序读** |
| 插入 / 删除 | 改几个指针,无旋转无分裂 | 页满要分裂、页空要合并,还要写 WAL |
| 并发与持久化 | 交给上层(命令串行执行) | 页级 latch、MVCC、崩溃恢复一样不能少 |

一句话记法:**B+ 树拼命把树高压到最低,因为它每下一层都可能付一次 I/O;skiplist 不在乎多跳几次,因为它每一跳只是内存寻址。** 反过来,磁盘上做范围扫描 B+ 树是碾压的——一次 I/O 就拿回一页几百条有序记录;skiplist 那种"指针指到哪读到哪"的访问模式一旦放到磁盘上,就是随机 I/O 灾难。

所以选型的真问题是**数据在不在内存里**:在内存里、更新频繁、范围返回量可控 → skiplist 这类结构够用且好写;数据量远超内存、要靠页缓存和顺序 I/O 撑 → 必须是 B+ 树(或 LSM 树那一路)。Redis 从第一天就假设数据在内存里,这个假设一改,结论就跟着改。

## 六、高并发下怎么用不炸

| 方向 | 具体做法 | 为什么有效 |
|---|---|---|
| **别让单条命令占住执行周期** | 限制 MGET 单次 key 数、ZRANGE 单次返回量并分页;不在热点 key 上跑 `ZUNIONSTORE`、超大 `ZRANGEBYLEX` | 命令串行执行,一条重命令的耗时会直接加到所有排队请求的延迟上 |
| **分片热点 ZSET** | 按业务维度切成 N 个子 ZSET,各自维护局部 Top-K,查询时并发取回再归并 | 把单点读写压力摊到 N 个 slot / 节点上;代价是**全局精确排名拿不到了,得接受近似** |
| **缩小成员** | member 用短 ID 而不是 JSON;score 别塞冗余信息 | 编码阈值卡的是"元素个数 **或** 单元素长度",成员一长就提前转编码,内存直接翻几倍 |
| **减少往返** | 批量走 MGET / pipeline;要"读—改—写"原子性时用 Lua | 省的是 RTT 这项固定开销(见第二节);注意 Lua 里所有 key 同样必须同槽 |
| **控制大 key** | 单个 ZSET 别无限增长,按时间/业务维度切分并设过期 | 大 key 的删除、迁移、序列化都是长耗时操作,还会撑爆输出缓冲区 |

顺带三句划清范围:缓存穿透 / 击穿 / 雪崩讲的是**流量怎么打到后端**(空值缓存加布隆过滤、热点重建加互斥、过期时间加随机抖动);过期与淘汰策略决定**内存满了先丢谁**;持久化(RDB / AOF)决定**重启后还剩什么**。三者都和本篇讲的数据结构正交,面试里通常单独展开。
