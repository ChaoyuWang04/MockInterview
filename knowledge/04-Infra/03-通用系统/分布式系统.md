# 分布式系统

一句话:这篇只讲分布式协调里最高频的那一块——**分布式锁**:跨机器、跨进程时,怎么保证同一时刻只有一个人在动同一份资源,以及故障之后这个保证还剩多少。CAP、共识算法、一致性模型谱系是它的背景板,这里只在需要时点一句,不展开。

## 一、先立住:锁防的不是"抢不到 key"

面试里最常见的失分,是把分布式锁答成"用 Redis 写一个 key,谁写进去谁拿到锁"。这只答了顺利的那条路。**分布式锁真正要防的是:网络分区、进程暂停(GC / 被调度出去 / 虚拟机被挂起)和租约到期之后,系统里同时存在两个"自认为持有锁"的客户端,而且它们都去写了同一份资源。** 加锁那一步几乎不会出错,出错的全在这些边界上。这也是它和单机线程同步的层次差别:单机互斥锁能成立,是因为线程共享同一块内存和同一个内核调度器,进程崩了操作系统会把锁一起收走;分布式锁把这两个前提全丢了——**锁的状态存在远端,持有者在另一台机器上,中间隔着会丢包、会延迟、会分区的网络,而"持有者是死是活"永远只能靠超时去猜**。所以它必须自带"故障后怎么释放"和"释放错了会怎样"的答案。单机的互斥锁、读写锁、原子操作与 CAS 见 并发控制 篇。

### 锁至少要保证三件事

| 要求 | 说的是什么 | 缺了会怎样 |
|---|---|---|
| **唯一所有者(互斥)** | 任一时刻最多一个客户端持有,并且它的这个认知是对的 | 两个客户端同时进临界区:重复扣款、重复发货 |
| **有限租期 / 故障后可释放** | 持有者崩了、失联了,锁最终一定会被放开 | 死锁:一个进程被 kill,整条链路永久卡死 |
| **只有所有者能释放** | 释放要验明身份,不能"谁调 unlock 谁就解得掉" | A 超时后醒来,一把删掉 B 刚拿到的锁,互斥当场崩掉 |

前两条是老生常谈,**第三条最容易漏,而且漏了会把前两条一起带塌**。业务上常追加两个可选目标:可重入(同一持有者能嵌套获取)和公平性(先到先得、不饿死)。这两条不属于正确性,但会决定选型。

## 二、Redis 租约锁:三个参数,三个坑

### 获取:`SET key random_value NX PX lease`

三个部分正好对应上面三条要求,少一个就塌一角:

- `NX`——只在 key 不存在时写入,提供**互斥**;
- `PX 30000`——到点自动过期,提供**故障后可释放**:持有者整台机器爆了,锁也不会永远锁着;
- `random_value`——每次加锁生成的唯一随机串,提供**只有所有者能释放**。官方文档的做法是从 `/dev/urandom` 取 20 字节,要求不可猜、不重复。

### 释放:必须"先比较再删",而且要原子

看这条时间线:A 拿到锁 → A 卡住 40 秒(GC、慢 IO、机器被换出)→ 锁在第 30 秒自动过期 → B 拿到锁 → A 醒来,以为自己还持有,直接 `DEL`。**A 删掉的是 B 的锁**,接着 C 也能拿到,互斥彻底失效。所以释放必须是"值等于我写的那个才删":

```lua
-- 只有当前值还是我加锁时写的随机串才删除,否则一个字节都不动
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

为什么非得用脚本、不能客户端先 `GET` 再 `DEL`?因为这两条命令之间同样有窗口:`GET` 返回"是我的"之后、`DEL` 发出之前,锁可能刚好过期并被别人抢走,你还是删了别人的锁。**Lua 脚本在 Redis 里整段原子执行,把这个窗口消掉。** 官方文档写明 Redis 8.4 起还有等价的单命令写法 `DELEX key IFEQ value`,语义完全一样。

### 续租:判断条件一个字都不能少

长任务干不完,要么把租期设长(代价是持有者真崩了以后,别人得干等这么久),要么边干边续租。续租就是把上面脚本里的 `del` 换成 `pexpire`,**前面那个比较随机值的条件必须原样保留**——否则你会去给别人的锁续命,后果和误删一样严重。租期长度本身就是权衡:**租期 = 你愿意为"持有者悄悄死掉"付出的最大等待时间**,设短了正常任务频繁被判超时,设长了故障恢复慢。续租缓解了这个矛盾但没消除它——官方文档特意提醒,续租(重新获取)的次数必须有上限,否则一个卡死的客户端会一直续下去,活性(总能有人拿到锁)就没了。

### 单主切换:异步复制会把刚写的锁弄丢

单实例是单点,加个从库做故障切换看起来很自然,但 **Redis 主从复制是异步的**。官方文档给出的竞态是四步:A 在 master 上拿到锁 → master 在把这次写传给 replica 之前崩了 → replica 被提升为新 master → B 在新 master 上拿到**同一把锁**,互斥被破坏。关键不在"Redis 不可靠",而在**异步复制下"写成功"并不代表"这次写在故障切换后还活着"**。这正是 Redlock 想解决的问题。Redis 的数据结构、底层编码与访问模式见 缓存系统 篇。

## 三、Redlock 与那场公开争论

### Redlock 在做什么

不用主从,改用 **N 个互相独立、没有任何复制关系的 Redis master**(官方举例 N=5)。加锁流程:

1. 记下当前时间;
2. 用**同一个 key 和同一个随机值**并行去 N 个实例做 `SET NX PX`,每次请求带一个远小于租期的超时(文档举例:租期 10 秒,单次超时 5–50 毫秒),避免卡死在某个不可用节点上;
3. 拿到**多数**(≥ N/2+1)**且**整个过程耗时小于租期,才算成功;
4. 实际有效期 = 初始租期 − 加锁耗时,再扣掉一点时钟漂移余量;只要没拿到多数,就立刻去**所有**实例上解锁,包括自己以为没锁上的那些。

它的假设不是"各机器时钟对齐",而是**各机器时钟走速大致相同、漂移有界**;互斥保证也带前提:**持有者必须在第 4 步算出的有效期内干完活**。

### 争论的两边

2016 年 Martin Kleppmann 撰文质疑 Redlock 的安全性,Redis 作者 antirez 随后回应。这是一场公开争论,两边的论点都该完整记住:

| 争点 | Kleppmann 的质疑 | antirez 的回应 |
|---|---|---|
| 进程暂停 | 客户端可能被 stop-the-world GC 暂停(他举的量级可达数分钟),暂停期间租约到期,醒来后它并不知道,继续拿旧认知去写 | Redlock 在拿到多数之后会**再检查一次**是否已超时,加锁途中的暂停只消耗有效期、不破坏正确性;而"持有期间被暂停"是**所有自动释放锁**的共性问题,不是 Redlock 独有 |
| 时钟 | Redis 的过期不走单调时钟,NTP 校正或人工改时间会让墙钟跳变,可能让锁提前过期,于是两个客户端同时持有 | 这属于运维可控:禁止手工改时间、NTP 配成缓慢校正(slew)而非跳变;但他承认单调时钟 API 这一点 Kleppmann 说得对 |
| fencing token | Redlock **没有**生成 fencing token 的机制;而要生成单调递增的 token,本身可能就需要一个共识算法 | 多数场景不需要"递增",Redlock 每次加锁的唯一随机串已足够做 check-and-set;而且 token 方案假设资源侧是可线性化存储,等于把问题挪到别处 |

**两边其实同意一件事**:任何"到期自动释放"的锁,都拦不住一个被暂停的旧持有者醒来后带着过期认知去写。分歧只在于这个风险该由谁兜——锁服务(发单调递增 token),还是资源侧(用唯一标识做条件写),以及"时钟漂移有界"算不算合理的工程前提。Redis 官方文档现在的一致性免责声明,给的正好是双方共识的最小集:**实现 fencing token;别假设"进程还活着"就等于"锁还持有"**。这问题也不是 2016 年才出现。Google 的 Chubby 论文早就描述过同一场景:持锁进程发出请求后失败,另一个进程拿到锁并做了操作,先前那个请求才姗姗来迟地抵达服务端。Chubby 给了两档解法——**sequencer**(一个描述加锁瞬间状态的字节串,含锁名、加锁模式与**锁代数号**,由资源服务器校验后决定是否拒绝),以及更弱但更好部署的 **lock-delay**(持有者失联导致锁被释放后,锁服务先冻结一小段时间不发给别人)。可见争的从来不是"有没有这个问题",而是"用多强的手段去兜"。

### 落点:关键资源必须认 fencing token

结论不是"Redlock 不能用",而是:**关键资源必须接受一个单调递增的 token,并拒绝比它见过的最大值更旧的持有者。** 客户端每次加锁拿到一个只增不减的编号,写资源时带上;资源侧记住见过的最大编号,来一个更小的直接拒绝。这样旧持有者即使醒过来,手里的编号已经落后,写不进去。落地它有三个硬前提,少一个都不成立:

- **token 必须单调递增且全局有序**。随机串只能比"是不是同一个",比不了"谁更新",所以随机串做不了 fencing。
- **资源侧要能改**,愿意存一个"见过的最大 token"并在写入时校验。这是最常卡住的一环——你锁住的往往是别人家的存储或第三方接口。
- **校验与写入必须在同一个原子操作里**,否则"检查通过"和"真正写下去"之间又开一个新窗口。

资源侧确实改不动时只能退而求其次:把临界区做成**幂等**(唯一业务键去重,重复执行不产生第二次副作用),或者用**条件写**(带版本号的 CAS 更新),再不行就接受"极小概率双写"并在业务层对账。**这些都是降级方案,要在设计里写清残余风险,不能假装锁已经解决了一切。**

## 四、ZooKeeper 顺序锁:把"抢锁"换成"排队"

### 临时顺序节点 + 只监听前驱

官方 recipes 给的锁配方是四步:

1. 在锁目录下 create 一个**临时顺序节点**(ephemeral + sequential),ZooKeeper 保证分配的序号单调递增;
2. `getChildren` 取全部子节点排序,**序号最小者持有锁**;
3. 不是最小的,就只在**自己前一个序号的节点**上注册 watch,然后阻塞等待;
4. 前驱被删除时醒来,回到第 2 步重新确认自己是不是最小。

第 3 步是精髓:**每个节点恰好被一个客户端监听,所以一次删除只唤醒一个客户端**。若所有等待者都去监听整个目录,每次释放都会同时叫醒上千个客户端、同时发请求,这就是惊群(herd effect)。和 Redis 租约锁相比,它换掉的是"故障释放"的机制:**不靠倒计时,靠会话**。会话过期时 ZooKeeper 自动删除该会话创建的所有临时节点,锁随之释放,你不必去猜租期设多久。recipes 里还写了一个易忽略的部分失败:create 在服务端成功了,但服务端在把节点名返回给客户端之前崩了,客户端不知道自己建没建成。解法是**节点名里带一个 GUID**,重连后 `getChildren` 找带自己 GUID 的那个节点。

### 追问:网络分区时客户端怎么处理会话状态

先把两件事分开,混起来就答错了:

| 状态 | 含义 | 谁说了算 |
|---|---|---|
| **Disconnected(断连)** | 客户端与某台服务器的 TCP 断了,SDK 会自动改连连接串里的其他服务器 | 客户端自己就能观察到 |
| **Expired(会话过期)** | 集群在 sessionTimeout 内没收到心跳,判定会话作废,临时节点已被删除 | **只有集群说了算,客户端判断不了** |

要命的地方是:**断连期间客户端收不到任何事件,包括"你的会话过期了"这一条**——它必须先重新连上才会收到 Expired 通知。所以"我没收到过期通知"绝不等于"我还持有锁";断连期间的 znode 增删也可能整段漏掉,watch 不是可靠的事件日志。正确处理是:

1. **一进入 Disconnected 就把锁状态当作"未知",立刻停止对受保护资源的写入**——这是唯一安全的默认值。既不能假设"锁还在"(集群可能已判过期并把锁给了别人),也不能假设"锁没了"(会话可能还活着,贸然重新竞争等于自己跟自己抢)。
2. 等状态明确再动:重连成功且会话仍有效就继续;收到 Expired 就认定锁已丢失、重新竞争,并把断连期间那些"结果未知"的写按可能失败来处理。
3. 客户端本地再加一道保险:记录距上次成功心跳过了多久,超过协商出来的 sessionTimeout 就主动自我熔断,因为服务端此时一定已经或即将判过期。顺带一提,生效的 sessionTimeout 是**协商**出来的:请求值小于服务端最小值(文档口径是 tickTime 的 2 倍)时,服务端会把实际最小值告诉客户端。
4. 最后一道保险依然是 fencing:ZooKeeper 天生就有单调递增的量可用(节点序号、zxid),把它当 token 交给资源侧,比在客户端猜会话状态可靠得多。

## 五、选型、可重入与高 QPS

### 两种方案怎么比

| 维度 | Redis 租约锁 | ZooKeeper 顺序锁 |
|---|---|---|
| 互斥怎么来 | 单 key 的 `NX` 语义 | 序号由集群统一分配,最小者持锁 |
| 故障释放 | TTL 到期,租期长短要人工权衡 | 会话过期,临时节点自动删,不用猜租期 |
| 正确性依赖 | 时钟走速有界、操作耗时可估、故障模型假设成立 | 会话与写入都走共识,不依赖客户端时钟 |
| 公平性 | 弱,抢占式,可能饿死 | 天然 FIFO 排队,容易做公平锁 |
| 惊群 | 轮询或广播通知,容易全员唤醒 | 只监听前驱,一次唤醒一个 |
| 吞吐与延迟 | 路径短、一次往返,吞吐高 | 每次加锁是一次写共识,延迟与开销都更高 |
| 运维 | 部署极常见,几乎哪里都有现成的 | 集群更重,要管会话、JVM 与磁盘 |

一句话选型:**能接受"极小概率两个持有者、由业务侧兜底"就上 Redis;需要清晰的排队语义与公平性,或者本来就有协调集群在跑,就用顺序锁。** 但无论选哪个,关键写路径都得有 fencing 或幂等——这一条与选型无关。

### 别用"Redis 是 AP、ZooKeeper 是 CP"代替故障分析

这是这道题最常见的偷懒答法。它听着专业,却**一个具体问题都答不到**:

- ZooKeeper 是 CP,不等于 ZooKeeper 锁在客户端 GC 暂停时安全。会话超时后节点被删,暂停中的客户端一无所知,照样是个旧持有者。
- Redis 单实例在**没有故障**时,互斥性和 ZooKeeper 一样成立。问题只出在故障切换和租期到点那一小段窗口里。
- CAP 说不出"暂停多久算长""租期设多少""资源侧要不要校验 token",而这些才是决定线上出不出事的量。

该怎么答:**沿失效路径逐条走**——谁可能同时认为自己持有锁?这个错误窗口最长多久?窗口里发生的写会不会被资源侧接受?最后一问的答案只要是"会",就必须上 fencing。

### 可重入

同一个持有者嵌套加锁不该把自己挡在门外,所以锁值不能只是一个随机串,得能表达"是谁 + 重入了几层"。常见做法是把锁值做成结构(Redis 里常用 Hash:field 是持有者标识,value 是重入计数):加锁时看字段是不是自己,是就计数 +1,不是就失败;释放时 −1,减到 0 才真正删 key。三个约束缺一不可:**身份标识要跨进程唯一、且重启后不复用**(进程号会被操作系统回收,用「实例 UUID + 线程 ID」这类组合更稳);**加锁、重入、续租、释放各自都必须是单个原子脚本**,不能"先读一次再写一次";**每次重入和续租都要重设 TTL**,否则内层还在跑,外层拿的租期已经到点了。

### 高 QPS 怎么扛

先问一句:**这个临界区真的必须全局串行吗?** 绝大多数"锁扛不住"其实是锁的粒度错了。按代价从低到高:

| 手段 | 做什么 | 前提 / 代价 |
|---|---|---|
| **按资源分片** | key 从"一把全局锁"变成"每订单/每用户一把",并发度天然等于分片数 | 分片之间业务上真的无关;跨分片要按固定顺序加多把锁,否则死锁 |
| **缩小临界区** | 只把"读—改—写"那几行放进锁里,RPC、IO、日志全挪出去 | 几乎没有副作用:临界区短了,同样租期能扛更高并发 |
| **本地锁前置** | 同进程内先抢一个进程内互斥,一台机器只往远端发一个请求 | 远端 QPS 直接除以每机并发数;本地锁与远端锁的获取顺序要固定 |
| **改成幂等或排队** | 唯一业务键去重,或按 key 哈希到单一消费者串行消费 | 需求从"互斥"变成"最终只生效一次";用延迟换吞吐 |
| **乐观并发** | 不加锁,写时带版本号做条件更新,冲突就重试 | 冲突率低时最快;高冲突会变成重试风暴 |

真正跑不掉的强互斥写路径,仍然要一致性协调加 fencing:**吞吐可以靠分片线性扩,正确性不能靠"把锁服务调快一点"换来。** 另外别忘了锁服务本身是所有写路径的必经点,它的可用性就是业务可用性的上限——加锁一定要设超时和降级策略(拿不到锁是快速失败还是排队),否则锁服务一抖动,上游线程池就被等待全部吃光。最后划一条界:训练侧说的"分布式"(AllReduce、TP/PP/DP)解决的是**怎么把一份计算摊到多张卡上**,不涉及"谁独占资源"的协调语义,和本篇不是一回事,机制分别见 集合通信 篇和 并行策略 篇。
