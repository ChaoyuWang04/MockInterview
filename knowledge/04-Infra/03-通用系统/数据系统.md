# 数据系统

一句话:这篇讲**离线与实时数仓里那套 SQL 是怎么真跑起来的**——同一句 JOIN 为什么行数会翻倍、换个引擎为什么快十倍、加一个 hint 为什么就不 shuffle 了。它不属于大模型知识,但只要简历上写过数据链路或特征生产,面试官几乎一定会往这挖。

## 一、JOIN 的基数语义:膨胀是怎么来的

### 一个键上就是乘法

JOIN 不会替你猜"哪一行才是对的那条",它把同一个连接键下**所有合法组合都枚举一遍**。所以左表 2 条、右表 2 条落在同一个键上,结果就是 $2\times2=4$ 条。推广到整张表,对每个连接键 $k$,左侧 $L_k$ 行、右侧 $R_k$ 行,匹配部分的输出行数是

$$
\sum_k L_k R_k
$$

这个式子说的是:**膨胀是按键逐个相乘再加总的**。所以一个热点键(某爆款商品在右表有 5000 行)能单枪匹马把结果撑爆,哪怕平均下来"每键才 1.2 行"。LEFT JOIN 在这之上只多做一件事:**左表没匹配上的行也留下来,右侧列补 NULL**;而且标准等值连接里 `NULL = NULL` 不成立,两侧都是空的键不会互相匹配——这就是"我的空值行一条都没连上"的答案。

由此推出一条常被答错的结论:**把 LEFT 改成 INNER 不能解决多对多膨胀**。对已经匹配上的键,两者乘法效应完全一样,区别只在 INNER 丢掉未匹配的左行。真正的修法是改粒度,不是改 JOIN 类型。

### 膨胀的代价不只是"行多了"

| 影响面 | 具体表现 |
|---|---|
| shuffle 与排序 | 中间结果按倍数放大,网络、排序、磁盘 spill 全跟着涨 |
| 内存 | 单分区突破 executor 内存,从"慢"变成 OOM |
| 倾斜 | 热点键的 $L_kR_k$ 极大,一个 task 拖垮整个 stage |
| **下游正确性** | `sum(amount)` 重复计数、`count(user)` 虚高。**这是最贵的一种:性能问题会被监控发现,指标错了却安静地进报表和特征表** |

## 二、膨胀的预防、定位与修复

### 先定业务粒度,再写 SQL

"避免膨胀"不等于加 `DISTINCT`。先问清楚输出应该是一用户一行、一订单一行,还是本来就允许一订单多商品——想清楚了,做法自然就定了:

| 业务需求 | 合适做法 | 不能忽略的条件 |
|---|---|---|
| 右表每键只要汇总值 | **JOIN 前先按键聚合**,再拿一行去连 | 聚合口径要明确(sum 还是 max) |
| 右表每键只保留一条 | `ROW_NUMBER()` 排序后取 `rn = 1` | 必须给**稳定的**排序规则,否则每次跑结果不同 |
| 只关心右表存不存在 | `EXISTS` / left semi join(**半连接**:只判断有没有,不带出右表的列) | 不需要右表其他字段 |
| 多对多本来就有业务含义 | 保留组合 | 下游指标必须按真实粒度算,不能直接 sum |

```sql
-- 每个 join_key 只留最新一条,再去连事实表
SELECT f.*, d.attr
FROM fact f
LEFT JOIN (
  SELECT * FROM (
    SELECT d.*, ROW_NUMBER() OVER (
             PARTITION BY join_key ORDER BY update_time DESC, id DESC  -- id 用来打破并列
           ) AS rn
    FROM dim d
  ) t WHERE rn = 1
) d ON f.join_key = d.join_key;
```

`ORDER BY` 里排什么是**业务决定**:选"最新"还是"金额最大",给出的是完全不同的特征。

### 已经膨胀了,五步定位

1. 两侧分别跑 `count(*)` 和 `count(distinct join_key)`,**两个数不等的那一侧就是不唯一的一侧**。
2. 按键统计 $L_k$、$R_k$ 和乘积,按乘积倒序——头几个键通常贡献了绝大部分膨胀。
3. 对比 JOIN 前后总行数和每键最大行数,比值就是平均膨胀倍数。
4. 检查连接条件**是不是漏了组成键**:日期分区、版本号、租户 ID 漏一个,就从一对一变成一对多。这是最常见的真实原因。
5. 修完在目标业务主键上做唯一性断言(`count(*) = count(distinct pk)`),固化成任务的数据质量卡点。

### 实时特征 JOIN 的额外挑战

流式 JOIN 比离线多三件事:**乱序与迟到**(右表事件比左表晚到,JOIN 时刻右侧还是空的,靠 watermark 和允许迟到兜底);**状态与 TTL**(流流 JOIN 要把两侧缓存在状态里等对方,保留多久直接决定内存与正确性的取舍);**维表版本**——必须明确要的是"事件发生那一刻的维度值"还是"当前最新值"。取错了行数一条没多,特征却穿越了时间,线上分布和训练对不上,模型效果莫名其妙掉。类别编码、目标编码的标签泄漏、训练与线上一致性,见 特征工程 篇。

## 三、执行引擎选型

### 四种执行模型的根本差别

一句话概括这四家的分歧:**数据什么时候到齐、任务要不要长期挂着、允许等多久。**

| 引擎 | 执行模型 | 中间结果与容错 | 延迟 / 吞吐 |
|---|---|---|---|
| Hive | SQL 编译 + 元数据层,真正执行的是后端(历史上 MapReduce,后来默认 Tez,也可配 Spark) | on MR 时每个 stage 中间结果落 HDFS,任何一步失败可从落盘处重来 | 启动开销以分钟计;吞吐稳,交互不能用 |
| Spark SQL | Catalyst 优化后的 DAG,按 **shuffle 边界**切 stage | shuffle 数据写本地磁盘,**单个 task 失败只重算这个 task** | 分钟级为主;超大批作业最稳 |
| Trino(Presto) | **流水线 MPP**:所有 stage 同时拉起,数据在算子间以数据页流动 | 中间结果默认不落盘,一个 worker 挂了整条查询重跑;新版本有 fault-tolerant execution 模式,把中间结果写外部存储换重试 | **秒到分钟级**,交互体验最好;内存不够更倾向直接报错而不是慢慢 spill |
| Flink SQL | 长期运行的有状态算子拓扑,记录一条条流过(也支持批模式) | 周期性 checkpoint 把算子状态存进状态后端,失败全局回滚重放 | 亚秒到秒级更新;吞吐受状态大小与 checkpoint 间隔约束 |

**"Hive 慢"严格说是"Hive on MapReduce 慢"**,慢在每个 stage 都要写读 HDFS,不是 SQL 层的问题;同理 Spark 短查询启动慢,慢的是 stage 边界的落盘与调度,不是 Catalyst 不行。

### 怎么选:按五个问题问下去

1. **数据有界还是无界?** 每天落盘后跑一次的账单是批;事件持续到达、要分钟内更新的是流。
2. **延迟目标是什么?** 交互 BI 看首字节和流水延迟(Trino);离线 ETL 看总吞吐、失败恢复和成本(Spark)。
3. **有没有大状态?** 流式 JOIN、去重、无界累计窗口的状态会一直涨,要提前定状态后端、TTL 和 checkpoint 开销。
4. **数据源与表格式?** 跨 MySQL + Hive + Kafka 出一张报表,联邦查询能力直接决定可行性;Iceberg/Hudi/Delta 支持到什么程度决定迁移成本。
5. **语法兼容性与团队能力。** 四家都自称 ANSI SQL,真正卡住迁移的是 decimal 精度、时间戳时区、隐式类型转换、`NULL` 在排序和聚合里的位置、UDF 要不要重写——**语法长得像,不代表跑出来的数一样**。

一个容易说错的点:**exactly-once 不是"开了 checkpoint"就有的**,它要由 source 可重放、状态一致快照、sink 幂等或事务三者共同成立,缺一个外部结果就还是至少一次。另外 Presto 生态已分成 PrestoDB 和 Trino 两条线,面试里最好说清自己用的是哪一个。

### 迁移成本怎么控

先做**差异清单**:SQL 方言、UDF、数据类型、时间语义、connector,一项项列出来,别边迁边发现。然后挑三类代表性作业**双跑**——短查询、重 shuffle 的宽表作业、边界数据(空值、极端时间、超长字符串)——对齐四个口径:总行数、主键唯一性、关键聚合值、NULL 语义。最后**逐批切流并保留回退**,老链路多跑一段时间。别用一条 benchmark 就宣布迁移完成。

## 四、分布式 Join 策略与广播

### Broadcast Hash Join 的四步

一大一小两张表 JOIN,Spark 的首选是 **Broadcast Hash Join**:

1. Driver 侧执行小表对应的子计划,收集结果生成广播关系;
2. 经 BroadcastExchange 序列化,分发到参与这次查询的各个 executor;
3. 每个 executor 用小表在**本地内存里建一张哈希表**;
4. 大表的每个分区**留在原地**扫描,用连接键 probe 这张哈希表直接出结果。

**它省掉的是"大表按连接键重分区"这一次全量 shuffle,不是让网络传输消失。** 传输量从"大表全量重排"换成"小表 × executor 数",所以只有小表**确实**小才划算;代价还有每个 executor 内存里都常驻一份小表。

### 触发条件、阈值口径与强制广播

Spark 拿优化器估算的小表大小去比 `spark.sql.autoBroadcastJoinThreshold`(**Spark 官方 latest 文档口径下默认 10485760,即 10 MB**;设 -1 关闭自动广播)。过阈值只是必要条件,还要看连接类型允许哪一侧当 build side(如 LEFT OUTER JOIN 只能广播右表)、统计信息可不可靠、executor 内存够不够。**别背一个"永远正确的 MB 数"**:默认值随版本变,而且真正决定成败的是反序列化后的对象大小,不是落盘的压缩大小——列存压缩后 20 MB 的表,展开成 JVM 对象可能好几百 MB。正确答法是"看当前版本配置 + `EXPLAIN` 物理计划里是不是 BroadcastHashJoin"。

小表略超阈值但内存够时,可以用 hint `SELECT /*+ BROADCAST(r) */ ...` 或 DataFrame 的 `broadcast(df)` 强制(Spark 的 join hint 优先级是 `BROADCAST` > `MERGE` > `SHUFFLE_HASH` > `SHUFFLE_REPLICATE_NL`)。强制前先算清**展开后真实大小 × executor 并发**,强制后用 `EXPLAIN` 确认计划真的变了,并盯广播耗时、广播超时和 executor 内存峰值。**强制广播失败的典型下场,是把一个 shuffle 慢的问题换成一个 OOM 的问题。**

### 倾斜场景下:广播还是 Sort-Merge

| | Broadcast Hash Join | Sort-Merge Join |
|---|---|---|
| 大表要不要 shuffle | 不要 | 两侧都要按键重分区 + 排序 |
| 对 shuffle 倾斜 | **直接消除**:大表不按键分区,热点键自然挤不到同一分区 | 热点键全落一个分区,倾斜重灾区 |
| 对"输出量大"的热点键 | **救不了**:热点键匹配出海量结果,单 task 还是要 probe 和写这么多行 | 同样救不了 |
| 内存 | 每 executor 一份小表,放不下就 OOM | 可以 spill 到磁盘,慢但能跑完 |
| 什么时候选它 | 一侧确实小、估算可靠 | 两边都大、广播侧大小不稳、JOIN 输出本身巨大 |

结论:**倾斜的是"分区大小"就优先广播;倾斜的是"某个键的结果条数",换算法没用**——得回到数据粒度、热点键拆分或预聚合上解决。

### AQE 怎么在运行时改计划

AQE(Adaptive Query Execution,自适应查询执行)针对的是"编译期统计信息是猜的"这个根本问题:让 Spark **跑完一个 stage、拿到真实 shuffle 统计之后,再决定下一段怎么执行**。三件主要的事:

- **动态切 Join 策略**:发现某一侧实际产出远小于估算,就把已规划好的 Sort-Merge Join 换成广播(或 shuffled hash join)。这一步用 `spark.sql.adaptive.autoBroadcastJoinThreshold`,没设时回落到普通广播阈值。
- **合并小分区**:`coalescePartitions` 把一堆几 KB 的 shuffle 分区合成合适大小,避免几千个空转 task——这就是开了 AQE 之后不必再死调 `shuffle.partitions` 的原因。
- **拆倾斜分区**:`skewJoin` 把超大分区切成多个并行处理。判定要**同时**满足两条——比中位数分区大 `skewedPartitionFactor` 倍(文档默认 5.0)**且**绝对大小超过 `skewedPartitionThresholdInBytes`(文档默认 256MB)。

边界:**"开了 AQE"不等于所有 JOIN 都自动最优**。它仍受连接语义、内存和阈值限制,而且只在 shuffle 边界处才有介入点——一个没有 shuffle 的计划,AQE 无从下手。

## 五、数据倾斜:成因与常用手段

倾斜的本质是**按键重分区之后,某几个分区的数据量远超其他分区**。征兆很典型:99% 的 task 几秒就完,剩一两个跑几十分钟,最后超时或 OOM。成因通常是三类键:业务长尾(爆款商品、大 V 用户)、占位值(`NULL`、`-1`、`unknown` 常常是全表最大的键)、以及上游膨胀把某个键放大了几十倍。除了第四节的广播和 AQE,常用手段还有:

| 手段 | 怎么做 | 代价 / 适用面 |
|---|---|---|
| **加盐打散** | 大表的键拼上 `0..N-1` 随机后缀,小表按键复制成 N 份;算完去盐合并 | 通用但代价明确:小表放大 N 倍,聚合要拆两阶段 |
| 热点键单独处理 | 先统计 Top-K 热点键,热点走单独作业(常配广播),其余走正常路径,最后 union | 没有全局 N 倍放大,但要先知道热点是谁 |
| 预聚合 / 两阶段聚合 | map 侧先局部聚合再全局聚合,进 shuffle 的数据量先降一个量级 | 只对可结合的聚合成立,`count(distinct)` 不能直接这么做 |
| 摘掉占位值 | `NULL` / 默认值的行先过滤或单独走一路 | 这些行业务上本来就连不上,性价比最高的一刀 |

## 六、窗口函数

### 根本差别:它不减少行数,和三个部件各管什么

**`GROUP BY` 把多行压成一行,窗口函数把多行的计算结果贴回每一行。** 输入行一条不少,只是多了排名、累计值、上一行的值这些列。这条决定了它的全部用途:凡是"既要明细又要组内统计"的需求——每个用户当日消费占本月的比例、每个订单在同城的排名——都是窗口函数的活。

```sql
function(...) OVER (
  PARTITION BY 分组列          -- 把行分成互不影响的组;省略 = 整个结果集一个分区
  ORDER BY   排序列            -- 定义组内先后,排名 / 累计 / LAG 都靠它
  ROWS BETWEEN 起点 AND 终点   -- 窗口帧:在分区内进一步限定"当前行能看到哪些行"
)
```

### 排名三兄弟

以分数 100、90、90、80 为例:

| 函数 | 结果 | 含义 |
|---|---|---|
| `ROW_NUMBER()` | 1、2、3、4 | 每行唯一编号,并列也强行分开 |
| `RANK()` | 1、2、2、**4** | 并列同名次,后面**跳号** |
| `DENSE_RANK()` | 1、2、2、**3** | 并列同名次,后面**不跳号** |

"每组取最新一条"必须用 `ROW_NUMBER()`,并给一个能打破并列的稳定排序键;用 `RANK()` 会把并列的多条一起带出来,又膨胀回去了。

### ROWS 和 RANGE:按行数还是按值

`ROWS` 按**物理行**计数,`RANGE` 按 `ORDER BY` 列的**值**算,并且把值相同的 peer 行全部一起纳入——有重复排序值时,这个差别直接改答案。更坑的是**默认帧**:写了 `ORDER BY` 却不写帧,标准行为是 `RANGE UNBOUNDED PRECEDING AND CURRENT ROW`,也就是**把同值 peer 全算进来**;不写 `ORDER BY` 则是整个分区。关键查询把帧显式写出来,别赌默认值。

```sql
SELECT user_id, dt, amount,
       SUM(amount) OVER (PARTITION BY user_id ORDER BY dt
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_sum,  -- 累计
       AVG(amount) OVER (PARTITION BY user_id ORDER BY dt
         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS avg_7_rows    -- 移动平均
FROM orders;
```

`6 PRECEDING` 是"最近 7 **行**",**不等于"最近 7 天"**:一天多行就窗口缩水,缺几天就跨得太远。要真按天,先按天聚合,或用时间区间帧(`RANGE BETWEEN INTERVAL '6' DAY PRECEDING AND CURRENT ROW`)。环比同比则用 `LAG(x, n)`(取组内前 n 行)和 `LEAD`:月环比是先把指标聚到月粒度再 `LAG(gmv, 1) OVER (ORDER BY month)`,同比是 `LAG(gmv, 12)`。**前提是每一期都必须有行**——某个月没数据,"上一行"就不是"上个月",环比会静静地算错;稳妥做法是先用日历维表补齐所有期再做 LAG。

### 性能:和 GROUP BY 比贵在哪

窗口函数的开销集中在**按 `PARTITION BY` 重分区 + 按 `ORDER BY` 排序**,而且输出行数等于输入行数,不像 `GROUP BY` 先把数据压小。所以同样的逻辑,能用 `GROUP BY` 表达就别用窗口。优化顺序:先过滤先裁列,**让进入排序的数据尽量少**;检查 `PARTITION BY` 是否严重倾斜(一个超大分区照样是单点瓶颈,治法同第五节);多个窗口函数若分区、排序、帧完全相同就复用同一个 window 定义(`WINDOW w AS (...)`),引擎只排一次序;少用省略 `PARTITION BY` 的全局窗口,那在分布式引擎上等于把所有数据汇到一个分区。

流式场景还有几条硬限制值得记:Flink SQL 的 OVER 聚合要求 `ORDER BY` **必须**是时间属性且升序,上界**只能**是 `CURRENT ROW`。更重要的是状态——**无界累计窗口(`UNBOUNDED PRECEDING`)的状态会无限增长**,离线跑得好好的 SQL 直接搬到流上,几天后就是状态膨胀和 checkpoint 变慢。流上还要额外定义 watermark、迟到数据怎么处理、状态 TTL 多久。
