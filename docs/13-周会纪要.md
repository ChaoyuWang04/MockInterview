# 周会纪要

定位:把开源项目周会的 ASR 转录稿和截图,提炼成**一屏读完的纪要加一份待办**。项目的 release notes(发版说明:这一版加了什么、改了什么、修了什么)也走这里。

和 10 的区别:10 把一份材料写成能独立读懂的长文;这里只要「发生了什么、与我何干」。和 06 的区别:06 讲代码现在是什么样,这里记上游**说**要做什么、做到了哪——没进代码的都只是动向。

## 一、目录

```text
meetings/<项目>/YYYY-MM-DD.md            # 周会纪要,日期是会议日
meetings/<项目>/YYYY-MM-DD-<版本号>.md   # release notes 纪要,日期是发布日
meetings/<项目>/_src/YYYY-MM-DD/         # 转录稿与截图原件,只留本机,不进 git
```

**流程与具体项目解耦**:任何开源项目的周会都走同一套,不为某个项目加特例。`<项目>` 取上游 GitHub 仓库名(如 `sglang-omni`);`opensource/` 里已有这个项目的解读时与它的目录名一致。同一项目的会议永远落在同一目录,名字从材料本身判断,判不出来才在意图卡里问。

## 二、处理输入

1. **原件到齐再动笔**:说了截图稍后发的,意图卡可以先出,纪要等截图到了再写
2. **截图先读**:每张截图读出图里的内容(Roadmap 条目、架构、数字、注意事项)。截图不带文字,要按内容去转录稿里找对应的讲解段落——图配上讲解才知道重点在哪
3. **转录稿要校**:ASR 会把技术词听错(模型名、库名、参数名)。能用截图、项目仓库或 PR 标题核对的就改正;核不动的保留原词并标 `(?)`,不猜
4. **读不出的说读不出**:截图模糊、转录断了,纪要里照实写
5. **只收公开的技术内容**:仓库是公开的。会上的非公开信息、与会者的个人信息(谁说了什么观点、谁的工作安排)不写;需要归因时写「维护者」「社区」这样的角色

## 三、纪要固定五段

模板见 [meetings/_template.md](../meetings/_template.md)。控制在一屏左右,宁短勿全:

| 段 | 写什么 |
|---|---|
| 一句话 | 这次最重要的一件事 |
| 方向变化 | Roadmap 调整、重心转移;没有就写「无」 |
| 固定线路进展 | 各条长期线(某模型的推理服务优化、某特性)推进到哪;引用对应截图 |
| 值得试的做法 | 大家试出来的更好协作方式、新工具、新软件;**逐条追加进 `paradigms/_待评估.md`**,不在这里下结论 |
| 我的待办 | 勾选框清单,每条是一件具体可做的事(看哪个 PR、试哪个功能、跟进哪个 issue);与贡献工作无关的不列 |

## 四、与其他库的接口

- 会上宣布**已合进或部分合进代码**的改动,而 `opensource/` 里有这个项目的解读:在该解读底稿末尾的「上游动态」一节登记一行「待核」(日期、一句话、纪要路径),没有这一节就建。等「已有解读更新」时再对代码核,纪要本身不改解读
- 会上提到值得精读的论文、博客:按 10 的准入另行登记,不在纪要里展开
- 你的贡献代码在别的仓库里做;`projects/` 仍然只镜像官方

## 五、验证与收尾

`npm test`(守 Markdown 渲染与工具调用残片)。纪要暂无页面入口,不用重启服务。收尾照 `AGENTS.md` 的口令。
