# 题目编写规范

每道题一个 md 文件,路径:`questions/<分类名>/<序号>-<简称>.md`。

本文件是题目格式和答案质量的唯一契约。一次完整的新增、截图导入或合并还必须执行 [02-题库导入流程.md](02-题库导入流程.md) 中的去重、分流与知识库同步。

- **正文里的技术术语用规范写法**:`CUDA Graph` 不是 `cudagraph`,`MoE` 不是 `moe`,
  `DeepEP` / `vLLM` / `KV cache` 同理。入题库时就要订正术语——题干会被念出来、
  会显示在页面上,而且**它就是喂给语音识别的热词**,写错直接拉低转写质量
- 分类文件夹名就是页面上显示的分类名(中文英文皆可)
- 文件名的序号前缀(`001-`)决定题目顺序;简称用小写英文/拼音或中文短语,连字符分隔,不超过 5 个词(如 `003-grpo-kl.md`、`001-手写-self-attention.md`)
- 以 `_` 或 `.` 开头的文件/文件夹会被忽略(所以 `_template.md` 不算题)

## frontmatter 字段

```yaml
---
difficulty: 中等             # 可选:简单 | 中等 | 困难
topic: GRPO/KL散度           # 必填:去重索引,1-2 段
summary: GRPO 的 KL 惩罚为何放 reward   # 必填:一句话题干,≤50 字
tags: [真题, RL, GRPO]       # 必填真题,其余为知识点标签
company: 字节、美团           # 可选:出题公司,多家用、分隔
mastered: false              # 程序写回,新题保持 false
highfreq: false              # 程序写回,页面点「高」标记高频题
---
```

`mastered` 与 `highfreq` 都由页面点击写回,采用**定点字符串替换**(只改那一行,保留手写格式与行内注释)。

### topic:三层主题定位(去重的核心)

完整层级 = `分类文件夹 / topic 第一段 / topic 第二段`,例如 `RL → GRPO → KL散度` 写成:文件放在 `questions/RL/`,frontmatter 写 `topic: GRPO/KL散度`。综述型题目可以只有一段(如 `topic: 解码策略/综述`)。

`npm run topics` 会打印全库主题树——**加题前先看树,同一考点不重复建题**;问法角度确实不同才新增,并用不同的叶子名区分。

`topic` 与 `summary` 有测试守护(`tests/samples.test.ts`):缺失、超过 2 段、summary 超 50 字都会让 `npm test` 报错并指出文件名。

### 「待校对」标签约定

AI 新写或实质改写了答案(包括参考老师答案重写)的题,tags 里加 `待校对`,页面上会显示 chip。已有题原本不带该标签,本次实质改写后也要重新加上。查过论文、通过格式检查不等于用户验收;用户明确认可答案后才删除。纯排版或术语订正不重新标记。

## 答案写作契约

适用于题库中的全部真题。**读者应能看懂原因、复述回答,并接住本题的追问。** 格式合规只是底线。

### 标杆与验收顺序

已验收标杆(2026-09-03):[投机解码·原理](../questions/AI%20Infra/080-投机解码-原理.md)。它示范「直接回答 → 解释原因 → 小图讲流程 → 公式配直觉与例子 → 适用边界」;**这是组织思路,不是每题必套的标题模板**。

该标杆已经验收并移除 `待校对`;核验依据与尚未完成的关联任务见 [答案标杆核验](references/答案标杆核验.md)。批量执行授权不等于答案验收,新增或实质改写的答案仍保留 `待校对`,直到用户逐题认可。

### 怎么把答案写清楚

1. **开头就回答。** 前一两句说清结论,不先铺历史、意义或泛泛定义。回答「为什么」就先给原因,回答「怎么做」就先给方法。
2. **把因果补全。** 解释原来的问题、方法改变了哪一步、为什么因此有效。不能用「提升效率」「增强稳定性」替代机制。
3. **用短句和具体动作。** 少堆缩写,必要术语第一次出现就解释;类比之后落回真实机制。通俗不等于口号化,不用「一句话钉死」「白送」「绝不能」代替条件与论证。
4. **只回答本题,但回答完整。** 动笔前列出题干里的主问与独立追问,逐项检查去向。相邻题已负责的推导或工程细节只链接过去,不要在每题重新讲一遍;主问不能只给链接。
5. **交代成立条件。** 明确理论保证、简化估算与实测结果的区别。性能数字写清硬件、精度、负载等必要前提;拿不准就删掉数字或登记待核对,不要凭峰值推算出一组“实测耗时”。例子中的自设数字必须说是「假设」或「举例」。
6. **收在问题边界上。** 给出与本题直接相关的限制或易错点即可,不把一题扩成知识库文章。不为凑字数、公式或图表增加内容。
7. **关联与对比按需补。** 定义或概念题,可在结尾用 1–3 句或小表,对照最容易混淆的两三种方法,帮助读者定位它解决什么问题、与近亲方法差在哪。例如 LoRA 与 Adapter、GRPO 与 PPO。比较维度保持一致,只点出区别,细节链接到对应题或文章。推导、排障、代码题不硬加对比;题干本就在比较时不再另凑一组。此项是写作参考,不是每题的验收硬指标。

### 公式和图表各解决什么问题

| 形式 | 什么时候用 | 写作要求 |
|---|---|---|
| 公式 | 不写就说不清概率、损失或数量关系 | 先说明它解决什么,定义符号,再用白话解释;容易混淆时加一个小例子。推导不是本题考点就不展开 |
| Mermaid | 先后顺序、数据流或分支容易讲乱 | 一图只讲一个过程,通常 3–6 个节点,最多 7 个;节点写动作,必要分支不能省略 |
| 表格 | 需要横向比较方案、条件或结果 | 比较维度一致,每格尽量一句话;连续的因果过程不要硬塞进表格 |

**按需选用,不要求每题集齐三样。** 图表应替代绕口的解释,不要把正文原封不动再画一次;公式不能只有符号没有含义。

### 怎样参考已有答案

- **题目与答案质量分开。** 进入题库即确认是真题,但老师答案、旧答案和 AI 草稿都只是参考,不能据此删除 `待校对`。
- **保留正确且与本题有关的内容,重新组织表达。** 吸收好的解释,修正错误与缺失条件;不逐字搬运整篇,也不为换词破坏准确术语和公式。参考答案中的不同意见先核实,不把冲突说法拼在一起。
- **关键事实查第一手材料。** 论文编号联网核实;算法看原论文,具体项目实现查 `projects/` 的本地源码并注明快照时效。少量关键链接放在「知识点」末尾,正文不放源码路径、行号或内部变量名。
- **复用已有好答案。** 去重后以已有题为主体补角度;题干是真题,不代表老师或 AI 写的答案已经通过校对。

### 六分区怎么分工

- **题目**保留实际问法与考点,只做必要的术语订正与拆分。
- **要点**通常 3–5 条,列「答到什么才算回答了本题」,不复述整篇答案;判卷会参考这份清单,不能把本题没问的知识也设成必答。
- **答案**给读者能理解、能复述的解释;原题明确问到的内容不能只移到追问后不作答。
- **知识点**列核心概念,必要时附关键来源;不要再写一份答案摘要。
- **追问**只保留问句,并按需要补少量自然的延伸问法。题干已有追问的简短回答放在「答案」末尾,独立长推导交给明确关联的子题;不要把答案混进模拟面试使用的追问池。作者新增的延伸问法注明「补充题」。
- **Note**留给用户,不填编辑记录或核验报告。

### 写完逐题自检

- 首段能否直接回答题干?正文是否讲清因果,而非堆结论?
- 原题的每个问题是否都在本题或明确关联的子题得到回答?
- 公式符号是否定义,图表是否真的帮助理解,数字与适用条件是否核实?
- 真题标签是否存在?参考答案与 AI 补充是否经过核验,待校对项是否如实保留?
- 是否遵守六分区、长度和题目边界,并保留用户的掌握状态与笔记?

最后按 [09-日常维护.md](09-日常维护.md) 的矩阵验证:题目改动至少运行 `npm test`,同步修改知识库时再运行 `npm run kb:lint`。自动检查不能判断语言是否清楚、技术是否正确;人工读稿与用户验收不能用检查通过替代。

## 六个分区(关键约定)

正文用 `## ` 二级标题分区,分区名**只能**是以下六个:

| 分区 | 必填 | 说明 |
|---|---|---|
| `## 题目` | ✅ | 题干,默认显示 |
| `## 要点` | | 展开后显示为 KEY POINTS |
| `## 答案` | ✅ | 展开后显示为 REFERENCE ANSWER |
| `## 知识点` | | 展开后显示为 KNOWLEDGE POINT |
| `## 追问` | | 展开后显示为追问题目 |
| `## Note` | | 你的笔记,页面上编辑,程序写回 |

**`## ` 只保留给这六个分区名**,题目/答案内部的小标题请用 `###` 及以下。围栏代码块里的 `## ` 不受影响(程序做了围栏感知)。

## 长度红线

- 题干 ≤ 3 句;summary ≤ 50 字
- 答案 ≤ 约 500 字或等价条目(一张对比表 + 几组要点)
- 超限**不要硬塞,也不要为压字数删必要解释**:确实含多个独立考点时拆成更细的 topic 叶子。题干已有追问不能只挪进「追问」而没有答案

## 支持的 markdown 能力

- **表格**(GFM):正常 `| a | b |` 语法
- **数学公式**(KaTeX):行内 `$E=mc^2$`;**块级公式的 `$$` 必须独占一行**,写在同一行会被当成行内公式(不居中、字号小):

  ```markdown
  $$
  P(w_i) = \frac{\exp(z_i/T)}{\sum_j \exp(z_j/T)}
  $$
  ```

- **Mermaid 图**:语言标注为 `mermaid` 的代码块自动渲染成图
- **代码高亮**:标注语言的代码块(`python`、`ts` 等)

## 知识库文章

**写作标准全部在 [05-知识库写作契约](05-知识库写作契约.md)**,该写哪篇、进度如何见 [04-知识库地图](04-知识库地图.md)。这里只说与题目有关的一条:

题目 frontmatter 的 `topic` 第一段,要**对齐知识库的文章名**(如 `topic: GRPO/优势估计` 对应文章 `GRPO.md`)——刷题页的「📚 知识库」入口靠这个字符串匹配。定 topic 前先查 [04-知识库地图](04-知识库地图.md) 的章节地图,别另造近义词。

**尚未成文的计划文章**也可以作为 topic 第一段:先在 04 登记唯一名称,页面暂不显示知识库入口。不能为了入题库临时创建空壳文章。

**另一个允许的例外**:`手撕代码` 分类的题目(手写 attention、手写交叉熵等)本来就没有对应文章,它们的 `topic` 只用于页面分组。匹配不到时页面**不显示** 📚 入口、不报错(`kbLinksFor` 只为命中的 topic 生成链接),这是设计如此,**不要为了"修好链接"去硬造一篇文章或改 topic**。

## 与入库流程的边界

本规范回答“单个题目怎么写”。批量导入、截图核对、去重、LeetCode 分流、知识库同步和交付统计统一由 02 负责,不要在本文件维护第二套流程。
