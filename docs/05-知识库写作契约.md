# 知识库写作契约

所有 `knowledge/` 下文章的统一标准。标杆样板:[04-Infra/01-原理/GPU架构与执行模型.md](../knowledge/04-Infra/01-原理/GPU架构与执行模型.md)。

## 一、读者设定与语言

读者是**正在准备面试的自己**:懂基本概念,但需要把原理讲透、把细节记牢。

- **最简单直白**:能用大白话说清的,不要用术语堆。术语第一次出现必须给一句类比或解释
- 一句话定位开篇:这篇讲的东西"是什么、解决什么问题",一句说完
- 讲**为什么**,不只讲是什么:每个结论后面跟上"因为…",这才是追问时能接住的东西
- 数字要具体:说"延迟高"不如说"约 400–600 周期";说"省显存"不如说"从 250 KiB 降到 8 KiB"
- 不确定的地方老实标注(如"论文自报,无第三方复现"),**严禁编造**

## 二、粒度与文件

- **一篇只讲一个可独立成文的知识点**(GQA、RoPE、ZeRO 各一篇),尽量细碎;同主题另开「XX总览」做横向串联
- 文章**无 frontmatter**,正文以 `# 标题` 开头;文件名即匹配键(题目 `topic` 第一段),**全局唯一**
- 目录:`knowledge/NN-章节/[NN-子领域/]文章.md`,`NN-` 前缀只用于排序,页面显示时剥掉
- **状态标记**(放在 H1 下面,页面据此显示角标):
  - `> 🚧 占位:` —— 还没写的空篇,**写完删掉**
  - `> ⚠️ 旧版:` —— 写作契约确立前的旧稿,**重写后删掉**。注意「重写」的含义,见下
  - 无以上两者 = 已按本契约成文
- **重点考点标记**(与状态标记独立,可共存):
  ```
  > 🔴 重点考点:本篇直接对应真实面经高频问法,文末「面试考点串联」给出问法对照。
  ```
  有真实面经来源的文章**才加**,页面显示红色「重」角标。没有面经来源的**不加 🔴,但照样要出考点表**(平台整理题或自拟题,分别标明来源,标准见第九节);只有纯介绍性文章(如框架与引擎章的项目介绍)可以整表省略。

### 「旧稿重写」是重写,不是修 lint

`npm run kb:lint` 报的那几条(图太大、代码太长、公式同行)只是**最表面的一层**。旧稿真正的问题是它写于契约确立之前:语言不够直白、讲是什么不讲为什么、数字不具体、没有按考点组织。**只把 mermaid 拆小就交差,等于把旧稿的毛病原封不动留下来。**

重写一篇旧稿,至少要重新做这几件事:

| 维度 | 要重新做什么 |
|---|---|
| 语言 | 对照标杆篇的语感:大白话、术语第一次出现给类比、每个结论后面跟"因为…" |
| 数字 | 把"延迟高""省显存"换成具体量级;换代际的数字要标 SKU/口径 |
| 结构 | **先按第九节检索面经原件与平台题及老师答案,列出必答考点,再组织考点表和正文**——答不上就补,答得散就重排小节 |
| 边界 | 旧稿写作时还不存在的专篇,现在都存在了:属于别篇的内容**整段删掉**,只留一句话引用 |
| 图表 | 能用表格就别画图;确实要图的,拆到 ≤ 8 节点 |

判据很简单:**重写完的稿子,应该看不出它曾经是旧稿**。如果 diff 里大部分行没动,那多半没重写。

## 三、结构骨架

```
# 标题
一句话:……

## 一、<动机 / 是什么>
## 二、<核心机制>          ← 公式与图表主要在这里
## 三、<细节与常见坑>
## 四、<对比 / 选型>        ← 有近亲方法时
## 五、面试考点串联         ← 高频问法 → 指向本文哪一节
## 相关文献
```

小节用 `## 一、二、三`,内部再分用 `###`。**不要出现四级标题**。

## 四、公式

- 行内 `$...$`,块级 `$$` **独占一行**(写在同一行会被当作行内公式,不居中、字号小)
- **每个块级公式后面必须紧跟一句人话解释**它在说什么,不能只甩公式
- 只写真正需要的公式:能用一句话说清的关系不要硬套符号

## 五、图表(重点约束)

**mermaid 硬性限制**——图一大,渲染出来字就被缩得看不清:

| 约束 | 上限 |
|---|---|
| 节点总数 | ≤ 8 |
| 横向并排节点 | ≤ 4(优先用 `flowchart TD` 纵向,宽度小、字大) |
| 单节点分叉 | ≤ 3 |
| 嵌套层级 | ≤ 2,**不用嵌套 subgraph** |
| 节点文字 | ≤ 12 字 |

超出就**拆成两张小图**,或干脆**改用表格**。

**优先用表格的场景**:多维对比(如 5 种存储 × 4 个属性)、参数清单、方案优劣对照。表格比流程图清楚得多,也不会被缩小。

mermaid 表达不了的(几何示意、论文配图、真实 trace 截图),留占位符独立一行:

```
> 🖼️ 占位:<想要的图的描述>
```

**后期换图**:图片放 `public/kb-images/<章节>/<文件名>.png`(该目录首次用时新建),把整行占位符换成 `![描述](/kb-images/<章节>/<文件名>.png)`;全库待补图用 `grep -rn "🖼️ 占位" knowledge/` 列出。

## 六、代码

- **只在代码比文字更清楚时才给**,且必须短(≤ 25 行),关键行带中文注释
- 手撕类(如手写 attention)可以给完整可跑实现;讲原理时给伪代码或核心几行即可
- **不引用具体项目的代码行号、变量名、文件路径**——那是开源解读模块的职责
- 例外:**公开的 kernel / API 参数名可以写**(如 `cu_seqlens`、`block table`)。面经里「这两个 kernel 的函数入参差在哪」是真实问法,答它必须点名参数。禁的是去翻某个项目源码里的**内部**变量、行号与文件路径,不是禁一切标识符

## 七、真实性:原理必须对得上真实实现

写 vLLM/SGLang/Megatron 这类系统的机制时:

- 讲的必须是**这些项目真实的做法与流程**,不能按"一般来说应该这样"想当然
- 但**只讲流程与抽象概念**,不下沉到代码细节
- 拿不准某个机制在项目里是否真的这么做 → 要么去 `projects/` 下确认,要么如实写"具体实现见开源解读模块"
- arxiv 编号拿不准**必须联网核实**,严禁凭记忆编造

## 八、篇幅与收尾

- 正文 120–260 行。总览/hub 篇取下限,机制推导篇取上限;超 300 行考虑拆篇
- 结尾:**相关文献**必有;**面试考点串联**(高频问法 → 本文哪一节能答,用表格)除纯介绍性文章外一律必有——题从哪来、怎么出,见第九节
- 相关文献格式:`- 论文名 — [arXiv:xxxx.xxxxx](https://arxiv.org/abs/xxxx.xxxxx)`;非论文资源给原始 URL
- 跨篇引用用纯文本、**且用文章全名**(写"见 Roofline与Bound分析 篇",别写"见 Roofline 篇"),不写站内链接——全名才能靠 grep 审计出断链
- **改文章名 = 改全库引用**:重命名前先全库 grep:`grep -rn "<旧名>" knowledge/ questions/ docs/ opensource/`(文章名同时是题目 `topic` 的匹配键,也写在 04 的章节地图与面经考点映射里),把引用一起改掉,并在 04 的改名对照表补一行。小节改名或内容迁移时同步更新面经映射,重新验收覆盖。踩过的坑:`rollout引擎` 改名后,7 处引用被批量替换成同一个泛指篇目,语义全错;`后训练总览` 改名后残留了一处死引用

## 九、怎么出题:考点串联的标准

**这个知识库是按「验收」写的**:先想清楚面试官会怎么考,再回头看文章答不答得上。所以考点表不是文末的装饰,**它是文章的验收单**——出得出来说明写透了,出不来说明有洞。

但**编出来的题比没有题更糟**:题一偏,复习方向就跟着偏。下面这套标准就是用来让自拟的题保持真实。

### 题从哪来:三种来源,标记不同

| 来源 | 状态标记 | 题量 | 表下加注 |
|---|---|---|---|
| 面经原件(用户提供的真题) | 加 `🔴 重点考点` | 面经有几条写几条,**不设上限** | 不加 |
| 平台整理题(含老师答案,没有独立面试原件) | **不加 🔴** | 通常 **5–8 题**,可合并近义问法,不能漏掉来源追问 | 加一行 `> 本表含平台整理题,非面经原题。` 并标明来源编号;混有自拟题时写清两种来源 |
| 按本节标准自拟 | **不加 🔴** | **5–8 题** | 加一行 `> 本表按出题标准自拟,非面经原题。` |
| 混合来源且含真实面经 | 加 `🔴` | 不设上限 | 表内标明各行来源,表下写清包含哪些类型,不能让 🔴 覆盖到平台题或自拟题 |

自拟不等于降格,只是要老实说明来源。纯介绍性文章可以整表省略,其余原理/机制类文章一律要有。

平台上的公司标签不是面试原件,老师答案也不是自动通过的标准答案。完整材料见 [写作参考索引](references/写作参考索引.md)。平台原题照实存档;老师答案有错误时保留原稿,正文用核实后的解释。题量限制不能用于丢掉关联问题:跨篇内容拆分归属,本篇确实需要更多平台题时据实列出并说明。

用户后来发来面经、要把真题并进已有考点表时,**替换或合并,不是再加一行**——完整流程见 [10-面经双写流程.md](10-面经双写流程.md)。

### 写前必做:先找来源,再决定怎么出题

新写、旧稿重写、增补都要做,不能因为章节地图曾写「没有面经」就跳过:

1. 用**文章全名**检索 [写作参考索引](references/写作参考索引.md) 的平台题映射及 [面经考点映射](references/面经考点映射.md),收集该篇所有状态的关联行。再查题库中 `topic` 第一段同名的题,并检索来源存档中的相关术语,补查同义表达、旧文章名和复合题的跨篇考点。不能只看任务队列或只查带「面经」标签的题。
2. 按来源编号回到存档,读完**主问与全部追问**;有老师答案的必须一起读,并查看已有核验记录,核实与本篇有关的事实。真实面经还须核实实际问出口的原话。题库里的 AI 答案、补充追问和后加的场景设定都不是原件;整道题的来源标签不能证明每句话都来自同一来源。找不到原件的先登记「待核对」,在任务队列记下缺少什么依据,不冒充真题,也不默默改成自拟。
3. 按本篇边界列出**必答考点清单**:来源编号与类型、属于本篇的主问及追问、计划回答的小节。映射遗漏就补行;一条原题跨多个知识点时分行指定各自的主负责文章,邻篇只留引用。多条原题问同一件事可以共用考点表一行,但各自的来源映射都保留。
4. 用清单组织正文和考点表。真实面经与平台题优先替换或合并近义自拟题,各自标明来源;还需要补充的题按本节标准自拟。只有检索、核实后没有可用来源的篇目才全用自拟档,不能把平台题和老师答案的存在忽略掉。

### 写后必做:每道关联原题都要能在正文里找到答案

- 对必答清单逐条读正文,包括原件的追问。**考点表有一行、文章有 🔴、题库能跳到文章,都不能替代正文覆盖**。
- 在映射中填实际正文小节的**完整标题**,确认正文和考点表都承接了该考点后才标「已覆盖」。缺内容标「待补」;只有占位或尚无文章标「待写」;来源、归属或正文尚未核对标「待核对」。对应缺口必须在 `01-TASK.md` 留任务和原题编号。
- 重写后重新核对原来「已覆盖」的行,小节改名、删段或跨篇迁移都要同步映射。属于邻篇的考点应转交该篇并留任务,不能用本篇一句「见 XX 篇」冒充已经覆盖。
- 本篇仍有未处理的必答来源考点时,不能宣布本篇完成。确认覆盖、通过验证后,删除已完成的任务行,**保留原件、老师答案和映射**。遗留的来源疑点应单列说明,不能靠删映射行消失。

以上覆盖验收检查的是原题是否得到回答;论文和实现的真实性仍按第七节核实,题库 AI 答案的「待校对」状态仍由用户复核。

### 真实面试的形状:宏观入口 + 往下挖一到两层

面试不是笔试。面试官先抛一个宏观概念,再顺着你的回答往下追——所以题目的**主流形态是「一主一追」**,而不是一堆孤立小题。看标杆篇怎么写的:

> Tensor Core 和 CUDA Core 是什么?**能并行吗?怎么并行?**

先"是什么"(第 1 层),紧跟"能不能、怎么做"(第 2 层)。出题时优先写成这种复合句,别拆成三道小题。

| 层 | 问的是 | 面试官真会说的话 |
|---|---|---|
| 第 1 层 · 是什么 | 定位、解决什么问题、没有它会怎样 | "…是干什么的?" "不用它会怎样?" |
| 第 2 层 · 怎么做到 | 机制主干、为什么这么设计、代价是什么 | "它怎么做到的?" "为什么要这么设计?" "代价是什么?" |
| 第 3 层 · 边界与坑 | 什么时候失效、参数怎么选、和别的机制打不打架 | "什么时候不划算?" "这个参数开大开小有什么影响?" |

**配比**:第 1、2 层占绝大多数,第 3 层最多 1–2 题,只给真正高频的主题。**没有第 4 层**——再往下就是论文细节,面试不会问,写进表里只会把复习带偏。

### 四条否决线:命中任一条就重出

以下是**自拟题**的否决线。真实面经即使问公式、具体数字或项目细节也照实保存,按文章边界组织回答;不能因不符合自拟标准就删掉原问法。

1. **要求默写或推导公式**。面试是口头问答,问的是"这个公式在说什么、为什么这么设计",不是"写出第几步"
   - ❌ 写出 GPTQ 的误差补偿公式 → ✅ GPTQ 靠什么决定量化顺序?误差怎么处理?
2. **答案只是一个论文里的数字或专名**。数字可以是答案的一部分,不能是题目的全部
   - ❌ MXFP4 的块大小是多少? → ✅ MXFP4 为什么不是正好 4 bit?
3. **口头两三分钟答不完,或者不翻文章就开不了口**。面试题要能被懂行的人当场组织成一段话
4. **书面考试腔**。用面试官真会说出口的话
   - ❌ 简述…的原理 / 列举…的三种方法 → ✅ …是怎么回事? / 为什么要这么做? / 这样做有什么代价?

### 自拟补题的机械动作(完成真题检索后再做)

1. 通读自己刚写的正文,把每个 `## 小节` 的**核心断言**挑出来——通常就是那句加粗的话
2. 对每条断言问一句:"面试官为了确认我真懂这条,会怎么问?"——这就是第 1、2 层的题
3. 正文里凡是写了「**为什么**……因为……」的地方,反过来就是最好的第 2 层题
4. 正文里凡是写了「**代价 / 坑 / 什么时候不划算**」的地方,就是第 3 层题
5. 每题回填「本文哪一节」。**自拟题填不出小节**:要么回去补内容,要么弃题;关联真题不能弃掉,按上面的覆盖验收补正文或转交主负责文章
6. 和相邻篇的考点表比一遍,同一个问法只留在最该讲它的那篇里,别篇一句话引用

## 十、写完自检

每写完一篇,按这张表自查(批量写作时逐篇扫):

| 检查项 | 判据 |
|---|---|
| 状态标记 | `🚧 占位` 已删;有面经来源的加了 `🔴 重点考点` |
| 写前来源检索 | 已查两种映射、题库与原件,读过关联的老师答案及核验记录;未把 AI 补充追问或旧版「无面经」说明当依据 |
| 来源考点覆盖 | 必答考点逐条有正文和考点表承接;映射的小节、归属、状态与最终文章一致,缺口有任务 |
| 块级公式 | 无 `$$公式$$` 同行写法;每个公式后有人话解释 |
| 标题层级 | 无四级标题(`####`) |
| mermaid | 每张图节点 ≤ 8,无嵌套 subgraph |
| 代码 | 每段 ≤ 25 行 |
| 收尾 | `## 相关文献` 必有;除纯介绍性文章外都要有「面试考点串联」表格 |
| 考点表 | 带 🔴 的题来自面经原件;平台题标来源编号、不冒充自拟;无面经时通常 5–8 题并注「非面经原题」,自拟题不沾四条否决线(见第九节) |
| 文献 | arxiv 编号逐个联网核实过,没有凭记忆写的 |
| 跨篇引用 | 引用的文章名在 `knowledge/` 下真实存在,且用的是全名 |
| 篇幅 | 120–260 行 |

上表中的**机械项已经脚本化**:

```bash
npm run kb:lint    # 标记/公式/标题层级/mermaid 规模/代码长度/收尾/断链/篇幅/重名
npm test           # 文章非空、文章名全局唯一、章节顺序
```

`kb:lint` 对**已成文文章**的违规会失败退出;旧稿的违规单列成「重写工作清单」不阻断。两项命令不核验面经来源,也不检查是否漏用真题。**原件真实性、逐题覆盖、问法质量、论文与项目实现**仍需人工核对;脚本提示只定位疑点,必须打开原文判断。

## 十一、禁忌清单
