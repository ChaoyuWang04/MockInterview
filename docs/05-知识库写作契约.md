# 知识库写作契约

所有 `knowledge/` 下文章的统一标准。标杆样板:[04-Infra/01-原理/GPU架构与执行模型.md](../knowledge/04-Infra/01-原理/GPU架构与执行模型.md)。

## 一、读者设定与语言

读者是**正在准备面试的自己**:懂基本概念,但需要把原理讲透、把细节记牢。

- **最简单直白**:能用大白话说清的,不要用术语堆。术语第一次出现必须给一句类比或解释
- 一句话定位开篇:这篇讲的东西"是什么、解决什么问题",一句说完
- 讲**为什么**,不只讲是什么:每个结论后面跟上"因为…",这才是追问时能接住的东西
- 数字要具体:说"延迟高"不如说"约 400–600 周期";说"省显存"不如说"从 250 KiB 降到 8 KiB"
- 不确定的地方老实标注(如"论文自报,无第三方复现"),**严禁编造**

## 二、粒度与文件

- **一篇只讲一个可独立成文的知识点**(GQA、RoPE、ZeRO 各一篇),尽量细碎;同主题另开「XX总览」做横向串联
- 文章**无 frontmatter**,正文以 `# 标题` 开头;文件名即匹配键(题目 `topic` 第一段),**全局唯一**
- 目录:`knowledge/NN-章节/[NN-子领域/]文章.md`,`NN-` 前缀只用于排序,页面显示时剥掉
- **建了文件就得是成文稿**。知识库不留空壳:还没动笔的文章登记在 `04-知识库地图.md` 的计划表里,别提前建文件占位。`kb:lint` 会把 `🚧 占位`、`⚠️ 旧版` 这两个已废弃的标记判为错误
- **除纯介绍性文章外,每篇都要有考点表**(各章 `00-总览` 是导航 hub,考点表在各专篇文末,豁免)。`kb:lint` 守这一条

### 三种篇型

| 篇型 | 负责什么 | 篇幅 |
|---|---|---|
| **普通专篇** | 一个可独立成文的知识点或单个项目的稳定设计 | 120–260 行,超过 300 行优先拆篇 |
| **总述篇** | 一条主线上各手段的关系、先后顺序与组合边界 | **不设上限**,但单项机制不得在此重写 |
| **对比篇** | 把同类方案放在统一维度下选型,解释差异为什么存在 | **不设上限**,但不得变成各专篇的摘抄合集 |

总述与对比篇在 H1 和一句话定位之后显式写 `> **篇型**:总述篇` 或 `> **篇型**:对比篇`;`00-总览.md` 默认是导航总览,不需要另写标记。篇幅放开只是允许复杂关系讲完,**不是允许堆材料**:每一节仍要回答一个明确问题,重复内容照常删除。

## 三、结构骨架

```
# 标题
一句话:……

## 一、<动机 / 是什么>
## 二、<核心机制>          ← 公式与图表主要在这里
## 三、<细节与常见坑>
## 四、<对比 / 选型>        ← 有近亲方法时
## 五、面试考点串联         ← 高频问法 → 指向本文哪一节
## 相关文献
```

小节用 `## 一、二、三`,内部再分用 `###`。**不要出现四级标题**。

## 四、公式

- 行内 `$...$`,块级 `$$` **独占一行**(写在同一行会被当作行内公式,不居中、字号小)
- **每个块级公式后面必须紧跟一句人话解释**它在说什么,不能只甩公式
- 只写真正需要的公式:能用一句话说清的关系不要硬套符号

## 五、图表(重点约束)

**mermaid 硬性限制**——图一大,渲染出来字就被缩得看不清:

| 约束 | 上限 |
|---|---|
| 节点总数 | ≤ 8 |
| 横向并排节点 | ≤ 4(优先用 `flowchart TD` 纵向,宽度小、字大) |
| 单节点分叉 | ≤ 3 |
| 嵌套层级 | ≤ 2,**不用嵌套 subgraph** |
| 节点文字 | ≤ 12 字 |

超出就**拆成两张小图**,或干脆**改用表格**。

**优先用表格的场景**:多维对比(如 5 种存储 × 4 个属性)、参数清单、方案优劣对照。表格比流程图清楚得多,也不会被缩小。

mermaid 表达不了的(几何示意、论文配图、真实 trace 截图),留占位符独立一行:

```
> 🖼️ 占位:<想要的图的描述>
```

**后期换图**:图片放 `public/kb-images/<章节>/<文件名>.png`(该目录首次用时新建),把整行占位符换成 `![描述](/kb-images/<章节>/<文件名>.png)`;全库待补图用 `grep -rn "🖼️ 占位" knowledge/` 列出。

## 六、代码

- **只在代码比文字更清楚时才给**,且必须短(≤ 25 行),关键行带中文注释
- 手撕类(如手写 attention)可以给完整可跑实现;讲原理时给伪代码或核心几行即可
- **不引用具体项目的代码行号、变量名、文件路径**——那是开源解读模块的职责
- 例外:**公开的 kernel / API 参数名可以写**(如 `cu_seqlens`、`block table`)。真题里「这两个 kernel 的函数入参差在哪」需要点名参数。禁的是去翻某个项目源码里的**内部**变量、行号与文件路径,不是禁一切标识符

## 七、真实性:原理必须对得上真实实现

写 vLLM/SGLang/Megatron 这类系统的机制时:

- 讲的必须是**这些项目真实的做法与流程**,不能按"一般来说应该这样"想当然
- 但**只讲流程与抽象概念**,不下沉到代码细节
- 拿不准某个机制在项目里是否真的这么做 → 要么去 `projects/` 下确认,要么如实写"具体实现见开源解读模块"
- arxiv 编号拿不准**必须联网核实**,严禁凭记忆编造

### 动态对象:稳定设计与当前状态分层写

框架、引擎、开源项目和仍在快速演进的范式是**动态对象**。这类文章不能永久停在初稿的仓库快照,也不能只追新版功能、把最有价值的设计思想冲掉。写法固定分两层:

- **稳定层**:它最初要解决什么问题,选了什么抽象或范式,为什么这样设计,代价和适用边界是什么。这是知识库的主体。
- **动态层**:当前稳定版或官方主干的高层架构、主要后端、执行模式和能力边界。只记录会影响理解与选型的当前事实,不抄 release note。

开头必须有一张文章内自洽的状态卡,不另建中央版本台账:

```markdown
> **对象类型**:动态对象
>
> **动态状态卡**
> - 最近核对:YYYY-MM-DD
> - 核对范围:官方稳定版 / 官方主干文档
> - 稳定定位:<长期不变的问题与设计>
> - 当前状态:<会随版本变化的高层事实>
> - 一手来源:<官方文档 / 仓库 / release>
```

动态对象文章被修改、官方发布 major release、对比表发现旧能力过期,或开源解读刷新到新 commit 后高层结论已变,都要重新核对状态卡与动态层。此规则对新建和本次重写稿立即生效;暂无状态卡的存量旧稿不视为已核对当前状态,在下次涉及版本事实时必须补卡。**知识库到高层流程、抽象和选型为止**;仓库相对路径、内部函数名、内部参数名、调度状态机和逐分支逻辑下沉到开源解读模块。公开 API / kernel 名只在它本身就是面试考点时保留。

## 八、篇幅与收尾

- 普通专篇正文 120–260 行,超 300 行考虑拆篇;导航 `00-总览`、显式标记的总述篇与对比篇**不设上限**
- 结尾:**相关文献**必有;**面试考点串联**(高频问法 → 本文哪一节能答,用表格)除纯介绍性文章外一律必有——题从哪来、怎么出,见第九节
- 相关文献格式:`- 论文名 — [arXiv:xxxx.xxxxx](https://arxiv.org/abs/xxxx.xxxxx)`;非论文资源给原始 URL
- 跨篇引用用纯文本、**且用文章全名**(写"见 Roofline与Bound分析 篇",别写"见 Roofline 篇"),不写站内链接——全名才能靠 grep 审计出断链
- **改文章名 = 改全库引用**:重命名前先全库 grep:`grep -rn "<旧名>" knowledge/ questions/ docs/ opensource/`(文章名同时是题目 `topic` 的匹配键,也写在 04 的章节地图里),把引用一起改掉,并在 04 的改名对照表补一行。小节改名或内容迁移时重新验收题库覆盖。踩过的坑:`rollout引擎` 改名后,7 处引用被批量替换成同一个泛指篇目,语义全错;`后训练总览` 改名后残留了一处死引用

## 九、怎么出题:考点串联的标准

**这个知识库是按「验收」写的**:先想清楚面试官会怎么考,再回头看文章答不答得上。所以考点表不是文末的装饰,**它是文章的验收单**——出得出来说明写透了,出不来说明有洞。

但**补出的题比没有题更糟**:题一偏,复习方向就跟着偏。题库是唯一真题集合;知识库作者只需要区分“题库真题”和为教学连贯额外写出的“补充题”,不建立来源编号或真实性分级。

### 写前必做:先查题库,再决定怎么出题

新写和增补都要做:

1. 用**文章全名**检索题库 `topic` 第一段,读完命中的题干、要点、答案与全部追问;再补查同义表达、旧文章名和复合题的跨篇考点。
2. 按本篇边界列出必答考点和计划回答的小节。一道题跨多个知识点时指定主负责文章,邻篇只留一句完整文章名引用。
3. 多道真题问同一件事可以合并成考点表的一行,但正文必须覆盖它们共同要求的全部角度。
4. 题库没有覆盖而文章确实需要的延伸问法,按下面标准补充并标为「补充题」;不要为了凑数出题。

### 写后必做:每道关联真题都要能在正文里找到答案

- 对必答清单逐条读正文,包括题干已有的追问。**考点表有一行、题库能跳到文章,都不能替代正文覆盖**。
- 缺内容就在本篇补齐;属于邻篇的考点转交主负责文章并在 `01-TASK.md` 留任务,不能用一句「见 XX 篇」冒充已经覆盖。
- 重写后重新核对题库真题,避免小节改名、删段或跨篇迁移造成静默缺口。
- 本篇仍有未处理的必答考点时不能宣布完成。题目答案带 `待校对` 时,知识库只能使用经过独立核实的事实。

### 真实面试的形状:宏观入口 + 往下挖一到两层

面试不是笔试。面试官先抛一个宏观概念,再顺着你的回答往下追——所以题目的**主流形态是「一主一追」**,而不是一堆孤立小题。看标杆篇怎么写的:

> Tensor Core 和 CUDA Core 是什么?**能并行吗?怎么并行?**

先"是什么"(第 1 层),紧跟"能不能、怎么做"(第 2 层)。出题时优先写成这种复合句,别拆成三道小题。

| 层 | 问的是 | 面试官真会说的话 |
|---|---|---|
| 第 1 层 · 是什么 | 定位、解决什么问题、没有它会怎样 | "…是干什么的?" "不用它会怎样?" |
| 第 2 层 · 怎么做到 | 机制主干、为什么这么设计、代价是什么 | "它怎么做到的?" "为什么要这么设计?" "代价是什么?" |
| 第 3 层 · 边界与坑 | 什么时候失效、参数怎么选、和别的机制打不打架 | "什么时候不划算?" "这个参数开大开小有什么影响?" |

**配比**:第 1、2 层占绝大多数,第 3 层最多 1–2 题,只给真正高频的主题。**没有第 4 层**——再往下就是论文细节,面试不会问,写进表里只会把复习带偏。

### 四条否决线:命中任一条就重出

以下是**补充题**的否决线。题库真题即使问公式、具体数字或项目细节也照实保留,按文章边界组织回答;不能因不符合补充题标准就删掉原问法。

1. **要求默写或推导公式**。面试是口头问答,问的是"这个公式在说什么、为什么这么设计",不是"写出第几步"
   - ❌ 写出 GPTQ 的误差补偿公式 → ✅ GPTQ 靠什么决定量化顺序?误差怎么处理?
2. **答案只是一个论文里的数字或专名**。数字可以是答案的一部分,不能是题目的全部
   - ❌ MXFP4 的块大小是多少? → ✅ MXFP4 为什么不是正好 4 bit?
3. **口头两三分钟答不完,或者不翻文章就开不了口**。面试题要能被懂行的人当场组织成一段话
4. **书面考试腔**。用面试官真会说出口的话
   - ❌ 简述…的原理 / 列举…的三种方法 → ✅ …是怎么回事? / 为什么要这么做? / 这样做有什么代价?

### 补充题的机械动作(完成真题检索后再做)

1. 通读自己刚写的正文,把每个 `## 小节` 的**核心断言**挑出来——通常就是那句加粗的话
2. 对每条断言问一句:"面试官为了确认我真懂这条,会怎么问?"——这就是第 1、2 层的题
3. 正文里凡是写了「**为什么**……因为……」的地方,反过来就是最好的第 2 层题
4. 正文里凡是写了「**代价 / 坑 / 什么时候不划算**」的地方,就是第 3 层题
5. 每题回填「本文哪一节」。**补充题填不出小节**:要么回去补内容,要么弃题;关联真题不能弃掉,按上面的覆盖验收补正文或转交主负责文章
6. 和相邻篇的考点表比一遍,同一个问法只留在最该讲它的那篇里,别篇一句话引用

## 十、写完自检

每写完一篇,按这张表自查(批量写作时逐篇扫):

| 检查项 | 判据 |
|---|---|
| 写前真题检索 | 已查 `topic` 第一段同名的全部题库真题,读过主问、答案与追问 |
| 真题考点覆盖 | 必答考点逐条有正文和考点表承接;跨篇缺口有明确任务 |
| 块级公式 | 无 `$$公式$$` 同行写法;每个公式后有人话解释 |
| 标题层级 | 无四级标题(`####`) |
| mermaid | 每张图节点 ≤ 8,无嵌套 subgraph |
| 代码 | 每段 ≤ 25 行 |
| 收尾 | `## 相关文献` 必有;除纯介绍性文章外都要有「面试考点串联」表格 |
| 考点表 | 题库真题优先且不标来源编号;额外问法标为「补充题」,不触碰四条否决线(见第九节) |
| 文献 | arxiv 编号逐个联网核实过,没有凭记忆写的 |
| 跨篇引用 | 引用的文章名在 `knowledge/` 下真实存在,且用的是全名 |
| 动态对象 | 有最近核对日期与一手来源;稳定设计和当前状态分层;没有下沉到源码符号 |
| 篇幅 | 普通专篇 120–260 行;导航总览、总述篇、对比篇无上限 |

上表中的**机械项已经脚本化**:

```bash
npm run kb:lint    # 标记/公式/标题层级/mermaid 规模/代码长度/收尾/断链/篇幅/重名
npm test           # 文章非空、文章名全局唯一、章节顺序
```

`kb:lint` 的契约违规会失败退出。自动检查不能证明逐题覆盖、问法质量、论文与项目实现正确;这些仍需人工核对,脚本提示只用于定位疑点。

## 十一、禁忌清单

- ❌ 把作者补出的问法混入题库真题(尤其是默写公式、背具体数字这类笔试腔的题)
- ❌ 甩公式不解释
- ❌ 复杂 mermaid(节点堆到十几个、嵌套 subgraph)
- ❌ 术语套术语(用没解释过的概念解释另一个概念)
- ❌ 编造论文编号、编造项目实现细节
- ❌ 大段贴代码充篇幅
- ❌ 写成 API 文档(罗列参数而不讲原理)
