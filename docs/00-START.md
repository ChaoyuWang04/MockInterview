# 从这里开始

> **交接语**:欢迎接手。这是 **Orrery**——维护者的个人系统,承载其知识、工作流与对外输出。内容都以本地文件为数据源——**没有数据库**,可以直接编辑并用 git 追踪。
>
> 日常用法很简单:**把链接、PDF、转录稿、截图或一句话直接丢进对话**。agent 按根目录 `AGENTS.md` 的路由表自己识别该走哪份手册,出一张意图卡请你确认一次,然后做到落库、验证、提交。不需要先让它读文档、讲流程。
>
> 第一次上手:① `leet-start` 跑起来,打开 <http://localhost:3000> 把七个功能模块点一遍;② 读完本页;③ 想知道接下来做什么,看 `01-TASK.md`。动手前记住两条最容易踩的:**改名必须同步引用**;**验证按 09 的变更类型矩阵执行**。

**这里只有守则和地图,没有细节**——细节一律在对应手册里,按下面的地图去找。agent 的入口是 `AGENTS.md`(`CLAUDE.md` 只是导入它),本页是给人看的全景。

## 一、这是什么

一套**本地、单人**的个人系统:维护者是高质量信息的筛选源(另有每日云端任务自动筛 alphaXiv 热榜),agent 负责提炼落库,并在工作中提示更好的协作方式。**markdown 文件即数据库**:所有内容都是纯文本,git 可追溯,不依赖任何数据库。名字取自太阳系仪:每个子系统沿自己的轨道运转,又周期性地回到起点。

两条核心理念,是一切设计的前提:

1. **解耦**:流程、模板、目录约定面向所有现在和将来的项目,不绑定任何一个
2. **迭代闭环**:摄入 → 提炼 → 实践 → 输出 → 反馈,反馈再回到摄入。不只摄入信息,也要持续对外输出

| 环节 | 子系统 | 在哪 |
|---|---|---|
| 摄入 | 维护者丢进来的材料、每日 alphaXiv 扫描、开源周会 | 各模块入口、`meetings/` |
| 提炼 | 七个功能模块(题库、知识库、开源解读、报告解读、日常研读、LeetCode、模拟面试);每种情境下与 Claude、Codex 协作的现行最优范式 | 各模块目录、`paradigms/` |
| 实践 | 给开源项目贡献代码 | `contrib/`,代码在本仓库之外 |
| 输出 | 个人主页,即对外展示面;社交平台发布(规划中) | `site/` |
| 反馈 | PR 评审与合并、读者的回应 | 回流进 `contrib/` 与各库 |

**覆盖范围是全库口径,不限于 AI**:Agent 应用层与 AI 基础设施之外,还包括编译器与硬件、云原生、后端中间件、数据库与存储、大数据计算、操作系统、图计算、金融量化。知识库负责讲原理,开源解读负责读代码,两边按同一张方向表扩展;开源解读的方向表与项目库存见 06 的「项目清单与解读状态」。

> 题库、知识库、开源解读、报告解读和 LeetCode 完全离线。模拟面试的判卷走云端 API,语音识别可选云端或本地;它对题库与知识库**只读**。

七个功能模块,各有一个页面入口:

| 模块 | 内容在哪 | 页面 |
|---|---|---|
| 题库 | `questions/<分类>/<序号>-<简称>.md` | `/` → `/<分类>` |
| 知识库 | `knowledge/NN-章节/[NN-子领域/]文章.md` | `/kb` |
| 开源解读 | `opensource/<主题>/<项目>/NN-*.md`(源码仓在 `projects/`,git 不追踪) | `/opensource` |
| 报告解读 | `reports/<公司>/<报告>.md`,方向索引 `reports/index.md`(PDF 原件在 `papers/`,默认不追踪 PDF) | `/reports` |
| 日常研读 | `readings/<方向>/<材料>.md`,索引 `readings/index.md`(原件在 `readings/_src/`,默认不追踪 PDF) | `/readings` |
| LeetCode | `leetcode/hot100.md` + `extra.md` + `notes/` | `/leetcode` |
| **模拟面试** | `interview/`(出题语料只读题库与知识库) | `/interview` |

`paradigms/` 与 `meetings/` 是仓库级沉淀,不算功能模块,暂无页面入口。`contrib/` 同样如此:开源贡献的台账,贡献代码在本仓库之外的 `~/1Project/oss/<项目>`(见 14)。`site/` 是个人主页,一个独立构建、独立部署的子系统(见 15)。

Web 常驻服务、开发服务和语音服务属于运行设施,不算功能模块;统一见 `08-常驻服务.md`。

## 二、十条铁律

1. **markdown 是唯一真源**。页面只读文件、写回文件;不引入数据库,不把内容藏进代码。
2. **写回必须定点替换**。改题目的 `mastered`/`highfreq`/Note 时,只改那一行/那一节,**禁止**用 gray-matter 之类整体重新序列化 frontmatter——会毁掉手写格式与行内注释。
3. **题目正文的 `## ` 只属于六分区**(题目/要点/答案/知识点/追问/Note),内部小标题一律 `###` 及以下。
4. **不编造**。论文编号拿不准就联网核实;项目实现拿不准就去 `projects/` 下看;图片读不出内容就说读不出,不猜。
5. **按变更类型验证**。所有改动至少运行 `npm test`;知识库改动还要运行 `npm run kb:lint`;开源解读改动还要运行 `npm run os:check`;语音与联网链路按 09 的矩阵追加专项检查。改了运行代码才需要重建常驻服务。
6. **改名就要改引用**。文件名是这个系统的连接键(题目 `topic` ↔ 知识库文章名、跨篇引用、题库分类名)。重命名前先全库 `grep` 一遍,把引用一起改;这条踩过两次坑。
7. **用户明确排除的功能不要加**:刷题计划、待复习队列、搜索、网页内题目编辑器、URL 位置参数。
8. **进入题库的都是真题**。统一使用 `真题` 标签;截图、网页采集或用户转述只是输入方式,不建立来源类型、双编号或真假分支。
9. **项目题先去背景再入库**。保留真实考点、公开技术名词和必要约束,删掉只对某位候选人项目成立的指代,改写成脱离简历也能独立作答的问题;缺少关键对象或约束时不猜。
10. **`projects/` 下的源码仓保持上游最新,且只镜像官方**——不要在里面写笔记、改代码、提交东西,要做笔记写到 `opensource/` 的解读里;要改代码去 `~/1Project/oss/<项目>` 的实验仓(见 14)。`npm run projects:sync` 自动发现所有仓库(含将来新增的)并只做快进;有未提交改动、有本地提交或游离 HEAD 的一律不动、只报告,由人处理,确认可丢就跑 `npm run projects:sync -- --discard-local`。`npm run os:check` 会先同步被检查的项目,再比对解读页记录的基准 commit 与当前 HEAD 的漂移——**漂移本身不判失败**,基准号是「这份稿子当时照着哪个版本写的」,不是要追的目标;只有底稿引用的那几行真被上游改了才提醒。全量复核只在用户点名时做,按 06 的「已有解读更新」。

## 四、维护这些文档的规矩

- **每份手册只讲一件事**;同一条规则只在权威手册中完整解释,其他文档只给必要上下文并链接
- 更新时**不是只做增量**:发现过时或错误的内容要**删掉**,避免下一个人被误导
- 流程有变(新增模块、改了约定)→ 先更新对应手册,再回来更新本页地图
- 文件名格式:`NN-中文名.md`,编号按工作流顺序;新增手册接着往后编
- **`01-TASK.md` 是队列不是日志**:任务做完**直接删掉那一行**,不留「已完成」记录;新任务插到对应优先级位置;里面只写任务,不写理由与取舍
- 动态数量由 `npm run kb:lint`、`npm run interview:index` 等命令现场输出,不写进任务队列或长期手册
- **守则与手册只写凝练后的原则**:具体失误、决策过程、「某次实做后修正」的经过不写进去,只留从中提炼的那一句,历史在 git log。经验按抽象程度该落到哪里,见 `AGENTS.md` 的「经验沉淀到哪里」

## 五、第一次上手

```bash
npm install      # 首次
leet-start       # 启动常驻服务 → http://localhost:3000
npm test         # 秒级全量验证
npm run kb:lint  # 知识库写作契约检查
npm run os:check # 开源解读的图与证据表核对
```

开发调试用 `npm run dev`(端口 **3001**,与常驻服务互不干扰)。
