# 开源解读:规范与项目清单

定位:本模块提供 AI 阅读真实代码后产出的「总览 + 按问题分页」项目解读,只约束**源码项目解读**。Technical Report 与技术论文的解读是并列的独立模块,目录和写作流程见 [10-材料解读流程](10-材料解读流程.md)。魔改实验在服务器上做,本机只负责理解。

## 目录结构(两层分离)

- `projects/<主题>/<项目>/` —— 源码仓原样存放(**git 不追踪**,.gitignore 已排除;是 AI 撰写解读时的阅读材料)

> **拿 `projects/` 当事实来源时,先注意两件事**:
>
> 1. **仓库保持上游最新由 `npm run projects:sync` 负责**,它对有未提交改动、有本地提交、游离 HEAD 的仓库一律不动只报告——这时不得擅自 pull 或 reset,交用户决定(细则见 `00-START.md` 铁律 10)
> 2. **目录名不等于项目名**。已知的坑:`推理服务/TensorRT` 是 NVIDIA 的 **TensorRT**,**不是 TensorRT-LLM**;要写 TensorRT-LLM 只能查官方文档。用之前先看一眼 README / CMakeLists 确认身份
- `opensource/<主题>/<项目>/NN-<页名>.md` —— 解读文档(**git 追踪**,页面数据源;路由 `/opensource`)
- `opensource/<主题>/<项目>/diagrams/NN-<slug>.json` —— archify 图的规格(**git 追踪**,图的真源,改图改这里再重新交付导出);同目录下 `_NN-evidence.md` 是每页的证据表(下划线开头,阅读器隐藏,git 追踪,更新基准时按它逐条复核)
- `public/opensource/<项目>/NN-<slug>.svg` 与 `.html` —— 从规格交付的静态图与交互版(**git 追踪**;新增后跑 `leet-restart`,常驻服务才认新文件)。阅读器会把图、表、代码块、块级公式放宽到整篇宽度(1440 宽的屏上约 1130px,1920 宽上约 1290px),正文段落保持 52rem 居中,所以宽表和长代码行不必迁就正文宽度

两边的 `<主题>/<项目>` 目录名保持一致;`public/` 下只用项目名做路径,不带主题。主页入口「🔍 开源项目解读」→ 按主题分组的项目卡片 → 阅读器(右侧章节导航,←/→ 翻节)。

## 解读的撰写标准

本节六组,按「写什么、真不真、查得到吗、怎么写、基石章怎么拆、图怎么画」排。前四组约束所有解读,第五组只约束基石解读,第六组只在要画图时读。

### 1. 两类解读:基石写长,其余写短

- **基石解读**:每个领域选一个抽象最完善、文档最多的项目当基石,共有原理只在这里展开一次。推理引擎是 vLLM,训练与 RL 框架是 verl。讲稿驱动的长文,多 `## Part`,原理、机制、图解、机制之外、对比与决策齐全;标杆页 `opensource/推理服务/vllm/11-量化.md`
- **其余项目**:学完基础知识和一个基石项目、知道整个系统怎么运转之后,同类的其他项目按类比学:它和基石哪里像哪里不像、怎么调参、怎么观测。所以每章一页,**简短原理加 runbook**,页头一句话回指基石(写章名,不写编号),然后固定六段:
  1. **核心问题**:哪种负载下哪个指标会坏,像骨折一样直白
  2. **解法**:几句话,大白话,先说最天然的直觉,再补一句为什么实际不吃亏
  3. **代价**
  4. **和基石不一样的 N 处**
  5. **调参与观测**:先说参数在哪调(启动参数、配置文件、环境变量、请求参数、运行时接口,哪些要重启);然后一张表,每个参数写「在哪调、默认、调了之后哪个指标往哪边变、怎么看」;再说观测点(哪几行日志、响应里哪个字段、哪个接口);最后一张「症状 → 先查 → 然后」表。这一段要写细,它直接决定读者能不能上手
  6. **常见误区**:以维护这个系统 30 年的人的身份写,只写真见过的错:排障时第一反应错在哪、哪个参数最常被调反、哪条日志最常被略过、哪个默认值最出人意料。**不是把前面的正确概念反过来再说一遍**,每条都要有「人们为什么会这么以为」和「实际上是什么」
  原理部分不放算例、不放 Part;表格只出现在第 5 段。标杆页 `opensource/推理服务/sglang/03-KV 存储:两级池与分配器.md`、`sglang/04-RadixAttention:前缀缓存.md`、`sglang/13-采样、约束解码与确定性.md`
- **展开靠对话**:读者对某一句有疑问时,在对话里讲透;讲透的内容可以回填成一段,不主动扩写,不为了完整而完整。正文短不等于读得少,读到的东西进底稿(第 3 组)
- **总览页两类通用**,必须有:一句话核心(这个项目是什么、代码都花在哪)、源码基准(仓库 URL、分支或 tag、完整 commit、核对日期)、总图、栈定位表、组件登记表、阅读顺序、术语表(每个词只定义一次)、相关链接(arxiv 编号拿不准必须联网核实)。总览先用总图建立位置感,核心链路先出,外围模块(API 层、connector、LoRA、多模态之类)留到后面再拆;对比集中在「阅读顺序」,不以对比开章
- **与知识库的分工**见本节末尾的边界表

### 2. 真实性:只写读过的代码,只写现在

- **必须读真实代码后写作**,以仓库现状为准;组件不存在就不要写,严禁按「通常这类项目会有」编造
- **每次解读绑定可复现基准**:`00-总览.md` 开头记录官方仓库 URL、分支或 tag、完整 commit、核对日期。正文里的「当前」「默认」「支持」都指向这组基准;只看在线文档、论文或 README 不能宣布源码解读完成
- **只解读当前状态,不做代际考古**。解读与某篇论文当年的设计不一致是正常的,不需要对齐论文原意,不写演进史;想知道当年长什么样去 [10-材料解读流程](10-材料解读流程.md)。更新到新基准时替换已经失效的当前状态,不在正文堆「旧版曾经怎样」
- **否定性断言**(「没有调用点」「没人设置」「默认关」)靠全树 `git grep`,写进底稿注明;**推断标「推断」**,找不到出处写「未找到」
- 纯 Python 组件(领班、账本)可以用 `types.SimpleNamespace` 伪造 config 干跑真实代码拿走读数字(缺依赖用 `uv run --with xxhash --with numpy`);依赖 GPU 的部分只能读代码手算,并在底稿注明「手算」

### 3. 覆盖面在底稿,不在正文

正文只写讲得清的那几句,源码的覆盖面由底稿 `_登记表.md` 保证,读者提问时要能立刻在底稿里查到「这一处现在是什么样」。

- **底稿固定分节**:基准与核对方式、一句话核心、主张清单、基石章表映射、候选章表、盲拆对比、待用户决定、分批进度、按章的断言清单
- **每章一份断言清单**,每条带基准上的 `file.py:12-34`。清单覆盖该章目录下的主要类、入口函数、docs 对应页和默认值,**不只覆盖正文提到的**;正文没提到的条目在「节」列标「备」。行号是 `os:check` 行级比对的依据,只写文件名会退化成文件级
- **代码索引页** `NN-代码索引.md` 全项目一页,按章分节,只写文件加符号名不写行号(行号随上游漂移,符号名不会);正文不写文件路径与行号
- **更新基准时**以底稿为查证清单逐条复核;底稿常驻不删
- 手算的数字、举例的参数值、来自讲稿而非源码的观点,在底稿「写作时的判断」里注明来源

### 4. 语言纪律:所有页面通用

- **通俗直白**:术语首次出现给一句话解释或类比,之后直接用;不解释「原理」「图解」「流程」这类常识词;每节只回答一个问题,答完就停;一个概念只展开一次,再提只给名字加一句回指
- **双名制**:角色名在前、代码名在后;全项目只用一个比喻(nano-vllm 用餐厅),角色之间的关系也要在比喻里成立
- **数字**:数量、区间、时延、容量一律阿拉伯数字(200–5000 token、50–500 毫秒、2 GB、1e-6),不写「几百到几千」「五千」「九成」
- **不放代码块**:解读讲机制,逐字搬源码等于 OCR;伪码塞进 ```text 块同样算代码。源码注释里写的设计理由是最值钱的部分,化进说明
- **配置与参数一律用表格**,表能说清的不写成段落;引用块只放一句话,超过两句改用正文
- **不写施工状态**:页面始终是最终版,「待确认」「下一批补」进底稿
- **不放占位符**(2026-09-11 用户拍板):哪里需要补图由用户通读时单独提出,模型不预判、不预留
- **加粗不紧贴括号或标点**,否则星号会漏出,`npm test` 会拦;公式 KaTeX 块级 `$$` 独行;mermaid 只用于页内小图
- 页头一句话定位加一句话说明来源与核对状态,不堆说明;不在正文里手写目录,阅读器从 `##` 自动生成
- 风格样板 `knowledge/RL/GRPO.md` 与 `opensource/推理服务/nano-vllm/`

### 5. 基石章的来源与结构(只约束基石解读)

- **章的来源**。有讲稿时跟讲稿分章,老师按模块列举的顺序由我们翻成痛点线。没有讲稿时四步:结构扫描(`git ls-tree` 出体量表,剔除测试、基准、脚本、文档)→ 主张采集(README、docs 的 advanced features、官方博客,每条主张落到目录)→ 套基石章表逐章问对应目录在哪、体量多大、有无主张背书 → 每个候选章写一句「在哪些场景下哪个指标会坏」,写不出的降为一段。候选表标把握程度(高:有博客或设计文档背书且读过入口代码;中:只读了目录与类清单;低:只有体量),低把握的章成稿前先做探路小批。有第三方课程时候选表定稿前不读,定稿后对答案,差异分「漏了 / 课程浅 / 视角不同」记底稿。零散目录按三档融入:有独立痛点且能写 80 行以上进已有章当一个 Part,只是变体当一个 H3,正文讲了只补索引。这四步其余项目的探路也用,只是产出的是短页而不是章
- **动笔前先答一个问题:这一章的 PagedAttention 是什么。** 一章只有一个主旨,其余内容都是这个主旨带出来的实事:存的是什么、拿真实模型算一笔账、朴素做法浪费在哪、机制怎么解决、它在显存里长什么样、为什么是这个布局、能放多少、见底之后怎么办。答不出主旨就不动笔;按实现模块列举(表、分配器、池、账)或按事故列举(崩、卡、慢)都是流水账
- **章的结构**:多 `## Part`,阅读器只从 `##` 生成目录。Part 1 是原理(前提、代价的账、朴素做法的问题),中间是机制与它的落地细节,尾部固定「图解 → 机制之外:源码里额外读到的 → 对比与决策(别人怎么做、这张卡能撑多少、关键参数、常见误区)」。Part 标题写成 `Part N|主题:一句论断`,H3 编号写成「Part.序号」,H3 标题是一句读完就能记住的结论,不是动作名;每个 H3 是一件有分量的事,有算例、有「有它和没它的差别」,不是 20 行一个的小点。固定顺序是痛点 → 为解决它提出了什么 → 怎么解决 → 代价落在哪个指标上
- **痛点的来源**:讲稿按模块列举时由我们翻成痛点线;没有讲稿时,坑的来源是源码里的 NOTE 与 why 注释、docs 的最佳实践与排障段、博客的动机段、核对时撞到的意外
- **写完后的复核**(必须看到全貌才能做):痛点线复核,每个子系统都要能答出它解决什么痛点,开篇的主痛点是否贯穿到末尾;重复展开合并,同一概念多处展开的只留信息熵最高的一处;全周期走读去重,只留最完整的一份全流程,判断方法是看两处走读的结论是否相同;定位复核,每个 Part 的定位是否还成立(vLLM 02 章的「源码解析」一段就是这样被并掉的);长度体检,逐节问行数配不配得上信息量;Part 切分复核,超过 250 行的 Part 沿痛点线再拆、明显偏短的并入相邻 Part,**重编号是全库动作**,跨章引用、代码索引页的键、底稿里的「NN 章 x.y」要一起映射,而且要排除 `1.6 ms`、`1.5 倍` 这类数量词,靠脚本映射、逐条人工审可疑项;代码索引页补全
- **页长不设上限,但不是越长越好**:一页讲透一个问题即可

### 6. 图

**画图分两条轨道**,选哪条**只看用户有没有点名 archify**,没有别的判定边界(2026-09-18 用户拍板):

**轨道 A · archify**(`~/.claude/skills/archify`):**只画用户显式点名「用 archify」的那几张**,通常是进程拓扑、调用链这类系统级的图。模型不判断哪张该转 archify,也不主动提议。图型选择、画布与字号换算、各图型硬约束、交付链、证据表格式全在仓库本地 skill `opensource-diagrams` 里,要画图时再读。**先问一句:原图的形状有没有在承载语义**——有就必须保住,别为了迁就图型把竖版改成横版。每张图的每个节点每条边在证据表里有 file:line 与原样引用,找不到写「未找到」,推断标「推断」;一图一问。

**轨道 B · 手写 SVG**:**默认轨道,其余一切图都走这条**——用户直接指定的讲解图、基础概念图,以及每批收尾时模型推荐、用户拍板的图。直接写 `.svg` 文本、逐个坐标摆,用一个生成脚本出图、程序化量 `getBBox` 检查,一批几张一次过。手绘比 archify 灵活得多,细化讲解一律用它;细则见下面一节。

图的最终挑选在收尾时做:用户通读时圈定要补的图,默认手写 SVG,点名 archify 的才走轨道 A。收尾时复核两件事:**编码有没有承载信息**、**章节重组后文件名和章号还对不对得上**。

#### 轨道 B:什么时候该主动画一张

样板是 `opensource/推理服务/vllm/05-注意力后端.md` 的 Part 5 开篇那张(七种注意力机制各省哪一维)。

**判据只有一句话:读者要同时握住好几样东西才能 get 到这一段的点,而文字强迫他一样一样地读。** 满足这一条就值得画,不满足就别画。

它反复出现的几种形状(**是例子,不是清单,别把它当穷举**):

- **一眼对比**:N 个东西沿同一根轴变化,要传达的是**反差本身**,不是其中任何一个
- **量级差异**:几个数字的**比值**才是重点 —— 表格给得出数字,给不出「这个是那个的三十二分之一」那种扑面而来的感觉
- **结构即语义**:排布方式本身携带信息,例如内存布局、块表映射、分块方式、按层交错的比例
- **反直觉的形状**:正确的心智模型和直觉不一样,而差别恰好是视觉上的

**什么时候不画**:有节点和边 → 走轨道 A;内容本来就是清单或参数表 → 就用表格(第 4 组的「参数用表」);图上的信息量等于它上面那句话 → 不画。**宁可不画,也不要画装饰。**

**形式上不设限。** 图型、版式、配色、要不要坐标轴、用方块还是用条带,全按这段内容自己的需要定,没有模板,也不要去模仿样板那张的长相 —— 它只是恰好适合那段内容。

**唯一的硬要求是:视觉编码必须承载信息。** 八个方块代表八个头,方块数从八变成一是因为头数从八变成一 —— 这叫编码。给同一句话配一个好看的框,不叫。这一条是轨道 B 的质量线,也是它和「配图」的区别。

**提出的时机:一批解读做完之后,单独提一次。**(2026-09-14 用户拍板)

写作过程中发现某段值得配图,**先记着,不要中断当前这批去画**。等这批的正文、底稿、验证都收尾了,再单独说一句:哪一节、想画什么、为什么这段值得画。**由用户判断要不要加**,同意了再动手交付。

这样安排的理由很实际:值不值得画,要看这一节最终写成什么样;写作中途就动手,经常画完发现那段被 B2/B3 压成回指了。一批一次、集中提,也便于用户横着比哪张更值。

没有想画的就什么都不用说 —— **这条不是每批必答的流程项**,是「有就提」。

**纪律(约束的是交付,不是长相)**:

1. 交付到 `public/opensource/<项目>/`,命名沿用 `NN<字母>-<slug>.svg`(`NN` 是它所属的章号)。**图属于哪一章,名字就用哪一章的号** —— 章节重组时记得一起改名。
   - **画布宽度按最终渲染宽度定,别画完再缩**:横图(宽大于高)阅读器撑满整篇,画布取 1120 左右;**竖图(高大于宽)阅读器只给正文栏宽 52rem(832px),画布取 860 左右**,这样正文里 12px 的字渲染出来还是 12px。2026-09-18 的教训:03a 按 1200 宽画,缩到 832 后字只剩 8px,用户看不清,整张重排。竖图的判定由阅读器在图片加载后按 naturalHeight > naturalWidth 打 `data-tall`,CSS 据此定宽(`app/globals.css`、`components/ProjectReader.tsx`)。
2. **alt 文字要写成一句完整的话**,说清这张图在讲什么。它不是可选装饰:图一旦加载不出来,读者看到的就只有它。
3. **手写没有布局引擎,所以不能靠眼睛验收。** 交付前把 SVG 读进 DOM,逐个 `text` 元素量 `getBBox()`,确认没有超出画布、没有互相重叠;对齐关键的列要实测渲染 x 坐标是否同值。
4. **必须在常驻服务(端口 3000)上验收,不能只看开发服务器。** 交付后跑 `leet-restart`,否则常驻服务认不出新文件。2026-09-14 就栽在这一步:开发服务器(3001)上 200、常驻服务上 404,前端只渲染出 alt 文字 —— 而当时只看了 3001。
5. 当前阅读器**没有深色模式**,写死浅色背景是安全的;哪天加了深色主题,轨道 B 的存量图要回头改。
6. 轨道 B 不要求 archify 那套 JSON 规格与证据表 —— **但图上的每个数字仍然要能在底稿里找到出处**,和正文同一个标准。

### 与知识库框架篇的边界

| 同一个项目里的内容 | 知识库 | 开源解读 |
|---|---|---|
| 最初想解决的问题、核心抽象与长期范式 | 主体内容 | 总览只给定位 |
| 当前支持的后端、执行模式与高层架构 | 记录影响理解和选型的最新状态 | 由当前代码逐项证明 |
| 模块边界、一次训练的数据流 | 讲到能理解设计为止 | 拆到实际组件与调用链 |
| 调度器、状态机、失败恢复 | 只讲思想和代价 | 写清状态、触发条件和分支 |
| 关键函数、内部参数、文件路径、行号 | **不写** | **必须写** |

知识库的动态状态卡和本模块的源码基准可以互相提示更新,但不能互相替代验收:官方文档核对通过不等于读过代码,源码存在某个开关也不等于它已成为稳定能力。

## 维护流程

- 新解读 = 用户点名;先在下方状态表把该项目标 🚧,写完标 ✅(文字齐了就算完成,图由用户后续单独点名补)
- **施工范式:分阶段、分会话,绝不一次跑完整个项目**。每阶段结束就 commit,下阶段新开会话,靠底稿 `_登记表.md` 与 01-TASK 接续。
  - ① **探路**(主线程亲做):钉基准、按第 5 组「章的来源」四步拆出候选章表(章、痛点一句、目录、体量、把握程度)、写底稿(分节见第 3 组)、写探路稿总览(页头标探路稿,主页可见)→ 交用户确认
  - ② **写文字**:基石项目一个会话推进一到三页;其余项目一个会话可以推进多页,但每页的底稿断言清单不能省(入口文件、docs 对应页、博客、默认值,带基准行号)。每页写完做三项体检(基石章看各 Part 行数,短页看六段是否齐、调参表每个参数是否有「调了之后」和「怎么看」两列;表格各行列数一致;加粗贴标点)、中文数字 grep,再 `npm test`;主线程做交叉核对、跑 `npm run os:check`、把纠正的口径回写底稿;在端口 3000 上通读(页面可能缓存旧稿,先刷新)→ 交用户确认
  - ③ **收尾**:用户点名补图与理解增强件;基石章按第 5 组「写完后的复核」整理页面
  - 派子 agent 时一个 agent 一次只交一份产物,三分钟没文件落盘就重派;子 agent 只做 validate,不做 deliver 与 visual-check
  - 底稿常驻不删,更新基准时以它为查证清单
- 新收藏项目:repo 放进 `projects/<主题>/`(没有合适主题就新建),状态表加一行 ⬜
- 已有解读更新:先核对官方远端与本地工作树,再把总览的 tag/commit/日期和受影响的页与图一起更新,按证据表逐条复核;不能只改一句「支持 X」而留下旧调用链
- 验证:`npm test` 与 `npm run os:check` 两条命令,具体检查项以脚本为准(`tests/opensource.test.ts`、`scripts/os-check.mjs`),不在本文重复
  - `os:check` 会先把被检查项目同步到上游最新,再比对 `00-` 页记录的基准 commit 与当前 HEAD 的漂移。离线用 `--skip-sync`
  - **基准漂移不判失败**:基准号记的是「这份稿子当时照着哪个版本写的」,是历史事实,不是要追的目标。仓库保持最新是为了随时能基于最新源码提问,解读很久才更新一次,两者节奏本来就不同。所以三档信号是:
    - **✗ 失败**只留给「现在就是坏的」——证据表的原样引用对不上源码、页面引用的产物缺失、archify 校验不过、图上文字互相遮挡
    - **! 提醒**是「值得哪天看一眼」——**底稿引用的那几行真被上游改了**(行级比对:拿底稿记的基准侧行号和 `git diff -U0` 的旧侧 hunk 求交),附带列出没标行号、只能按文件判的引用
    - **· 信息行**只是记录漂移了多少提交,不用管
  - **全量复核只在用户点名时做**(看到未覆盖的新功能之类),不要因为提醒就停下手上的写作,也不要主动提议去补。当批新写的内容照常在写作时的 HEAD 上核对即可
  - 行级比对能成立,靠的是底稿把引用写成 `file.py:12-34`。**只写文件名的引用会退化成文件级**,噪音大;底稿记引用时尽量带行号
  - 证据表的书写格式见 skill `opensource-diagrams`(检查器有自己的识别规则,写错会误判)
  - 新增 `public/` 图片后跑 `leet-restart`,常驻服务才认新文件(它不重新构建,只让当前构建重读 `public/`;`leet-*` 是 `~/.zshrc` 里 source 进来的 shell 函数,**不是 npm script**,`npm run leet-restart` 会报找不到)。**验收要在端口 3000 上做**,开发服务器(3001)每次请求都查磁盘,那里看到的不算数
- 刷题/知识库遇到与某项目强相关的考点,可在解读页的「面试考点串联」补一行,反向链接用纯文本
