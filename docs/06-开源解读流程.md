# 开源解读:规范与项目清单

定位:本模块提供 AI 阅读真实代码后产出的「总览 + 按问题分页」项目解读,只约束**源码项目解读**。Technical Report 与技术论文的解读是并列的独立模块,目录和写作流程见 [10-基模报告流程](10-基模报告流程.md)。魔改实验在服务器上做,本机只负责理解。

## 目录结构(两层分离)

- `projects/<主题>/<项目>/` —— 源码仓原样存放(**git 不追踪**,.gitignore 已排除;是 AI 撰写解读时的阅读材料)

> **拿 `projects/` 当事实来源时,先注意两件事**:
>
> 1. **本地目录只是待核对快照,不能自动代表最新主干**。开工前先看本地分支、HEAD、tag、工作树和官方远端;有本地改动时不得擅自 pull、reset 或覆盖。无法安全更新时,停止写「当前实现」并说明阻塞
> 2. **目录名不等于项目名**。已知的坑:`推理服务/TensorRT` 是 NVIDIA 的 **TensorRT**,**不是 TensorRT-LLM**;要写 TensorRT-LLM 只能查官方文档。用之前先看一眼 README / CMakeLists 确认身份
- `opensource/<主题>/<项目>/NN-<页名>.md` —— 解读文档(**git 追踪**,页面数据源;路由 `/opensource`)
- `opensource/<主题>/<项目>/diagrams/NN-<slug>.json` —— archify 图的规格(**git 追踪**,图的真源,改图改这里再重新交付导出);同目录下 `_NN-evidence.md` 是每页的证据表(下划线开头,阅读器隐藏,git 追踪,更新基准时按它逐条复核)
- `public/opensource/<项目>/NN-<slug>.svg` 与 `.html` —— 从规格交付的静态图与交互版(**git 追踪**;新增后按 09 跑 `leet-restart`,常驻服务才认新文件)。阅读器会把图、表、代码块、块级公式放宽到整篇宽度(1440 宽的屏上约 1130px,1920 宽上约 1290px),正文段落保持 52rem 居中,所以宽表和长代码行不必迁就正文宽度

两边的 `<主题>/<项目>` 目录名保持一致;`public/` 下只用项目名做路径,不带主题。主页入口「🔍 开源项目解读」→ 按主题分组的项目卡片 → 阅读器(右侧章节导航,←/→ 翻节)。

## 解读的撰写标准

- **必须读真实代码后写作**,以仓库现状为准;组件不存在就不要写,严禁按"通常这类项目会有"编造
- **每次解读绑定可复现基准**:`00-总览.md` 开头记录官方仓库 URL、分支或 tag、完整 commit、核对日期。正文里的「当前」「默认」「支持」都指向这组基准;只看在线文档、论文或 README 不能宣布源码解读完成
- **只解读当前状态,不做代际考古**。本模块回答的永远是「这个项目**现在**是什么样」。解读与某篇论文当年提出的设计不一致,是正常且预期之内的——项目会演进,论文不会。因此:
  - **不需要在开源解读里对齐论文原意**,也不必逐条标注「这一条是论文之后才加进来的」;
  - **不写演进史**:某个机制什么时候引入、替换过哪个旧方案、为什么被删掉,都不是本模块的内容;
  - 想知道某个设计当年长什么样,去 [10-基模报告流程](10-基模报告流程.md) 查那篇论文的解读。**两个模块各自完整,不互相追认。**
  - 更新到新基准时**替换已经失效的当前状态**,不在正文堆「旧版曾经怎样」;确需理解历史设计时去报告解读模块
- **分页按问题,不按目录**:`00-总览.md` 之后每页只回答一个问题,H1 写成「NN 页名:问题」,页首标明时间尺度(启动期一次 / 每 step / 每 request / 跨 request),不同尺度不同页。一个项目 5–9 页。样板 `opensource/推理服务/nano-vllm/`(新范式);`opensource/推理服务/LMCache/` 是旧样板,按子系统分页,待迁移
- **先结构后行为**:总览用一张 architecture 总图建立位置感,再按「指挥循环 → 调度决策 → 请求状态机 → 一块数据的一生 → 一次前向 → 启动期 → 取舍与消融」的顺序逐页放大。核心调度链先出;外围(API 层、connector、LoRA、多模态、投机解码之类)在总图上只标灰色边界节点,留到后续层再拆
- **00-总览 硬性要求**:一句话核心(这个项目到底是什么、代码都花在哪)与源码基准 → archify 总图(进程边界、控制流与数据流分线型、每个组件带 file:line 来源)→ 栈定位表(每层里有什么、几行、谁提供)→ 统一比喻表 → 组件登记表(角色名、代码名、所在进程、持有什么、不持有什么)→ 阅读顺序 → 术语表(每个 infra 词只在这里定义一次,一句话加类比)→ 状态所有权表(可变状态、拥有者、谁在哪改、谁读)→ 文末「按图索骥」目录表与「相关链接」(arxiv 编号拿不准必须联网核实,严禁编造)
- **每页骨架**:先看图(archify 图 + 交互版链接 + 怎么读)→ 术语卡(本页新词)→ 走读(一个具体示例,按图上编号讲,每步只出现角色名,代码名只在该步末尾附一次;数字优先来自纯 Python 干跑真实代码)→ 关键函数、参数与默认行为(表)→ 状态与失败分支 → 持有什么,不持有什么 → 设计取舍(为什么这么做、代价、没有它会怎样)→ 面试考点串联。指挥循环页在术语卡后加「骨架代码」:主循环压成不超过 10 行伪代码,每行注释调的是谁、是否跨进程。末页「取舍与消融」把各页的取舍汇总成「没有它你要怎么写、代价、本项目用几行实现」的表
- **写法纪律**:双名制,角色名在前、代码名在后,文件路径只进表格或行尾;全项目只用一个比喻(nano-vllm 用餐厅),角色之间的关系也要在比喻里成立;一图一问;每张图的每个节点每条边在证据表里有 file:line 与原样引用,找不到写「未找到」,推断标「推断」
- **图的规范(v1,用户后续还会调整,先不要当成固化流程)**:用 archify(`~/.claude/skills/archify`)。新图从 v1 模板改起:architecture 用 `nano-vllm/diagrams/00-overview.json`,sequence 用 `01-command-loop.json`,workflow v2 用 `02a-scheduling.json` 或 `06-startup.json`,lifecycle 用 `03-request-lifecycle.json`,两行 dataflow 用 `04a-kv-blocks.json` 或 `05b-model.json`。图型对应问题:architecture 答「有几个进程、谁管谁」,sequence 答「一次请求经过哪些手」,workflow 答「一次决策怎么分叉」,lifecycle 答「状态怎么跳」,dataflow 答「一块数据的一生」。architecture、workflow、dataflow、lifecycle 最多 12 个节点,sequence 最多 30 条消息,超了拆 a、b 两张,编号每图从 ① 重起、正文用「图 a 的 ③」指代;决策流按阶段分泳道,记账或搬运流按角色分泳道;省掉副标题与动画,标题一行;`meta.locale` 用 zh-CN;节点副标题不超过约 12 个汉字宽,相邻节点间的边标签不超过 12 个汉字或 22 个拉丁字符,细节进卡片;sequence 图 viewBox 宽不超过 1080 并设 `column_fit: spread`;lifecycle 的唯一终态放终态带,迁移的 note 会渲染成可见文字,file:line 只放证据表;同步与异步只用三个词:同进程同步调用、单向广播、GPU 异步(`.tolist()` 是同步点)。交付链:`validate --quality showcase` 零错零警 → `deliver` 出 HTML → 在仓库根目录跑 `node scripts/archify-export.mjs <html> <svg>` 导出自包含 SVG → `visual-check` 看可读性与一屏容纳,它的 `*.visual-check.*` 副产物落在 HTML 旁边,看完挪出 `public/`。sequence 走读图和两行以上的 dataflow 图常在 1440×900 超出一屏几十像素(独立 viewer 的标题条与卡片本来就占高度,嵌进页面后随页滚动),只要最小字号不低于 6px 就接受并在证据表记明;其余溢出先压卡片文案再调 viewBox 或 yOffset
- **页长不设上限**:一页讲透一个问题即可,大项目的总览与章节页可以很长;公式 KaTeX(块级 `$$` 独行);mermaid 只用于页内小图;图片占位符规则与知识库一致(`> 🖼️ 占位:...`)
- 语言:通俗直白,术语首次出现给类比;加粗紧贴括号或标点时在 `**` 那侧补空格,否则星号会漏出,`npm test` 会拦;风格样板 `knowledge/RL/GRPO.md` 与 `opensource/推理服务/nano-vllm/`

### 与知识库框架篇的边界

| 同一个项目里的内容 | 知识库 | 开源解读 |
|---|---|---|
| 最初想解决的问题、核心抽象与长期范式 | 主体内容 | 总览只给定位 |
| 当前支持的后端、执行模式与高层架构 | 记录影响理解和选型的最新状态 | 由当前代码逐项证明 |
| 模块边界、一次训练的数据流 | 讲到能理解设计为止 | 拆到实际组件与调用链 |
| 调度器、状态机、失败恢复 | 只讲思想和代价 | 写清状态、触发条件和分支 |
| 关键函数、内部参数、文件路径、行号 | **不写** | **必须写** |

知识库的动态状态卡和本模块的源码基准可以互相提示更新,但不能互相替代验收:官方文档核对通过不等于读过代码,源码存在某个开关也不等于它已成为稳定能力。

## 维护流程

- 新解读 = 用户点名;先在下方状态表把该项目标 🚧,写完标 ✅(有占位符标 🖼️)
- **施工范式:先文字后图,分阶段、分会话,绝不一次跑完整个项目**。每个阶段结束就 commit,下一阶段新开会话,靠底稿与 01-TASK 接续,避免长会话拖垮质量。① 探路,主线程亲做,只出模块地图:核对基准,读入口找进程边界,写常驻底稿 `_登记表.md`(基准、一句话核心、比喻表、组件登记表与冻结的 ID、配置默认值、术语表、统一示例、已确认事实、写法纪律),在总览里列出要拆成哪些「问题页」、每页的起点行号,把外围模块标出来;交用户确认。② 写文字,一个会话只推进一到三页,每页先出文字与证据表,「先看图」的位置留空;派子 agent 时一个 agent 一次只交一份产物(先规格或页面,再证据表),派出后三分钟没有文件落盘就直接重派,不等看门狗;主线程做交叉核对(状态集合对队列进出、数据拥有者对所有权表、启动期常量对消费者)、跑 `npm run os:check`、去掉下划线发布、把纠正的口径回写底稿;交用户确认。③ 可视化收尾,文字全部确认后再补图、骨架代码、消融表这类理解增强件,并按最终结构整理页面。④ 主线程亲写末页与总览终稿。底稿常驻不删,更新基准时以它为查证清单。子 agent 只做 validate,不做 deliver、preview、visual-check
- 领班、账本这类纯 Python 组件可以用 `types.SimpleNamespace` 伪造 config 干跑真实代码得到走读数字(缺依赖用 `uv run --with xxhash --with numpy`),依赖 GPU 的部分只能读代码手算并注明
- 新收藏项目:repo 放进 `projects/<主题>/`(没有合适主题就新建),状态表加一行 ⬜
- 已有解读更新:先核对官方远端与本地工作树,再把总览的 tag/commit/日期和受影响的页与图一起更新,按证据表逐条复核;不能只改一句「支持 X」而留下旧调用链
- 验证:`npm test`(解读页非空 + 序号前缀 + 星号泄漏 + 页面引用的图片产物存在 + LMCache 样板守护);`npm run os:check`(每份规格的 archify showcase 校验、产物是否比规格旧、证据表逐条把「位置」与「原样引用」拿到 `projects/` 源码上核对,任何一处未命中即失败);新增 `public/` 图片后 `leet-restart`,并在阅读器里确认图片渲染。证据表写法必须让检查器认得:每行至少写一次文件名,裸 `:12-34` 只沿用同一行前面的文件;「原样引用」列只放逐字代码,跨行的代码按源码顺序拼接即可,空白不计;不是代码的轨迹记录写成「干跑输出 `...`」;否定式断言(某几行里没有某名字)不用反引号
- 刷题/知识库遇到与某项目强相关的考点,可在解读页的「面试考点串联」补一行,反向链接用纯文本
