# 开源解读:规范与项目清单

定位:本模块提供 AI 阅读真实代码后产出的「总览 + 按问题分页」项目解读,只约束**源码项目解读**。Technical Report 与技术论文的解读是并列的独立模块,目录和写作流程见 [10-材料解读流程](10-材料解读流程.md)。魔改实验在服务器上做,本机只负责理解。

## 目录结构(两层分离)

- `projects/<主题>/<项目>/` —— 源码仓原样存放(**git 不追踪**,.gitignore 已排除;是 AI 撰写解读时的阅读材料)

> **拿 `projects/` 当事实来源时,先注意两件事**:
>
> 1. **仓库保持上游最新由 `npm run projects:sync` 负责**,它对有未提交改动、有本地提交、游离 HEAD 的仓库一律不动只报告——这时不得擅自 pull 或 reset,交用户决定(细则见 `00-START.md` 铁律 10)
> 2. **目录名不等于项目名**。已知的坑:`推理服务/TensorRT` 是 NVIDIA 的 **TensorRT**,**不是 TensorRT-LLM**;要写 TensorRT-LLM 只能查官方文档。用之前先看一眼 README / CMakeLists 确认身份
- `opensource/<主题>/<项目>/NN-<页名>.md` —— 解读文档(**git 追踪**,页面数据源;路由 `/opensource`)
- `opensource/<主题>/<项目>/diagrams/NN-<slug>.json` —— archify 图的规格(**git 追踪**,图的真源,改图改这里再重新交付导出);同目录下 `_NN-evidence.md` 是每页的证据表(下划线开头,阅读器隐藏,git 追踪,更新基准时按它逐条复核)
- `public/opensource/<项目>/NN-<slug>.svg` 与 `.html` —— 从规格交付的静态图与交互版(**git 追踪**;新增后跑 `leet-restart`,常驻服务才认新文件)。阅读器会把图、表、代码块、块级公式放宽到整篇宽度(1440 宽的屏上约 1130px,1920 宽上约 1290px),正文段落保持 52rem 居中,所以宽表和长代码行不必迁就正文宽度

两边的 `<主题>/<项目>` 目录名保持一致;`public/` 下只用项目名做路径,不带主题。主页入口「🔍 开源项目解读」→ 按主题分组的项目卡片 → 阅读器(右侧章节导航,←/→ 翻节)。

## 解读的撰写标准

- **必须读真实代码后写作**,以仓库现状为准;组件不存在就不要写,严禁按"通常这类项目会有"编造
- **每次解读绑定可复现基准**:`00-总览.md` 开头记录官方仓库 URL、分支或 tag、完整 commit、核对日期。正文里的「当前」「默认」「支持」都指向这组基准;只看在线文档、论文或 README 不能宣布源码解读完成
- **只解读当前状态,不做代际考古**。本模块回答的永远是「这个项目**现在**是什么样」。解读与某篇论文当年提出的设计不一致,是正常且预期之内的——项目会演进,论文不会。因此:
  - **不需要在开源解读里对齐论文原意**,也不必逐条标注「这一条是论文之后才加进来的」;
  - **不写演进史**:某个机制什么时候引入、替换过哪个旧方案、为什么被删掉,都不是本模块的内容;
  - 想知道某个设计当年长什么样,去 [10-材料解读流程](10-材料解读流程.md) 查那篇论文的解读。**两个模块各自完整,不互相追认。**
  - 更新到新基准时**替换已经失效的当前状态**,不在正文堆「旧版曾经怎样」;确需理解历史设计时去报告解读模块
- **两种分页方式,按有没有现成讲稿选**:
  - **按问题分页**(自己探路时用,样板 `opensource/推理服务/nano-vllm/`):`00-总览.md` 之后每页只答一个问题,H1 写成「NN 页名:问题」,页首标明时间尺度(启动期一次 / 每 step / 每 request / 跨 request),不同尺度不同页,一个项目 5–9 页
  - **跟讲稿分章**(有现成讲稿时用,样板 `opensource/推理服务/vllm/02-调度器.md`):按讲稿章节走,每章四段式「原理 → 图解 → 机制之外 → 对比与决策」,末段是 runbook。**这是当前的标杆页,动笔前先通读它**
  - 两种都要:总览页先用一张总图建立位置感,核心链路先出,外围模块(API 层、connector、LoRA、多模态、投机解码之类)留到后面再拆
- **`00-总览.md` 必须有**:一句话核心(这个项目是什么、代码都花在哪)、源码基准(仓库 URL、分支或 tag、完整 commit、核对日期)、总图、栈定位表、组件登记表、阅读顺序、术语表(每个词只定义一次)、相关链接(arxiv 编号拿不准必须联网核实)
- **正文不放代码块**:解读要讲机制——这段在做什么决策、为什么这么写、哪里容易读错。逐字搬源码等于 OCR,读者不会读,而且和流程图重复。**源码注释里写的设计理由是最值钱的部分**,要化进说明,不要跟着代码一起丢。伪码塞进 ```text 块同样算代码
- **写法纪律**:双名制,角色名在前、代码名在后,文件路径只进表格或行尾;全项目只用一个比喻(nano-vllm 用餐厅),角色之间的关系也要在比喻里成立;一图一问;每张图的每个节点每条边在证据表里有 file:line 与原样引用,找不到写「未找到」,推断标「推断」
- **画图分两条轨道**,选哪条看**内容有没有节点和边**:

  **轨道 A · archify**(`~/.claude/skills/archify`):系统架构、子系统架构、调用链、时序、状态机、数据流 —— 凡是「一堆东西之间连着线」的,走这条。图型选择、画布与字号换算、各图型硬约束、交付链、证据表格式全在仓库本地 skill `opensource-diagrams` 里,要画图时再读。**先问一句:原图的形状有没有在承载语义**——有就必须保住,别为了迁就图型把竖版改成横版。**这条轨道由用户点名**(见写作规则 A7)。

  **轨道 B · 手写 SVG**:archify 够不着的那一类。它没有节点和边,布局引擎帮不上忙,所以直接写 `.svg` 文本、逐个坐标摆。**这条轨道由模型主动发现、但仍由用户拍板**,是 A6/A7 的明确例外,细则见下面一节。

- **页长不设上限,但不是越长越好**:一页讲透一个问题即可;公式 KaTeX(块级 `$$` 独行);mermaid 只用于页内小图;**本模块不用图片占位符**(与知识库不同,见下方写作规则 A5)
- 语言:通俗直白,术语首次出现给类比;加粗紧贴括号或标点时在 `**` 那侧补空格,否则星号会漏出,`npm test` 会拦;风格样板 `knowledge/RL/GRPO.md` 与 `opensource/推理服务/nano-vllm/`

### 轨道 B:什么时候该主动画一张

样板是 `opensource/推理服务/vllm/05-注意力后端.md` 的 Part 5 开篇那张(七种注意力机制各省哪一维)。

**判据只有一句话:读者要同时握住好几样东西才能 get 到这一段的点,而文字强迫他一样一样地读。** 满足这一条就值得画,不满足就别画。

它反复出现的几种形状(**是例子,不是清单,别把它当穷举**):

- **一眼对比**:N 个东西沿同一根轴变化,要传达的是**反差本身**,不是其中任何一个
- **量级差异**:几个数字的**比值**才是重点 —— 表格给得出数字,给不出「这个是那个的三十二分之一」那种扑面而来的感觉
- **结构即语义**:排布方式本身携带信息,例如内存布局、块表映射、分块方式、按层交错的比例
- **反直觉的形状**:正确的心智模型和直觉不一样,而差别恰好是视觉上的

**什么时候不画**:有节点和边 → 走轨道 A;内容本来就是清单或参数表 → 就用表格(规则 A11);图上的信息量等于它上面那句话 → 不画。**宁可不画,也不要画装饰。**

**形式上不设限。** 图型、版式、配色、要不要坐标轴、用方块还是用条带,全按这段内容自己的需要定,没有模板,也不要去模仿样板那张的长相 —— 它只是恰好适合那段内容。

**唯一的硬要求是:视觉编码必须承载信息。** 八个方块代表八个头,方块数从八变成一是因为头数从八变成一 —— 这叫编码。给同一句话配一个好看的框,不叫。这一条是轨道 B 的质量线,也是它和「配图」的区别。

**提出的时机:一批解读做完之后,单独提一次。**(2026-09-14 用户拍板)

写作过程中发现某段值得配图,**先记着,不要中断当前这批去画**。等这批的正文、底稿、验证都收尾了,再单独说一句:哪一节、想画什么、为什么这段值得画。**由用户判断要不要加**,同意了再动手交付。

这样安排的理由很实际:值不值得画,要看这一节最终写成什么样;写作中途就动手,经常画完发现那段被 B2/B3 压成回指了。一批一次、集中提,也便于用户横着比哪张更值。

没有想画的就什么都不用说 —— **这条不是每批必答的流程项**,是「有就提」。

**纪律(约束的是交付,不是长相)**:

1. 交付到 `public/opensource/<项目>/`,命名沿用 `NN<字母>-<slug>.svg`(`NN` 是它所属的章号)。**图属于哪一章,名字就用哪一章的号** —— 章节重组时记得一起改名。
2. **alt 文字要写成一句完整的话**,说清这张图在讲什么。它不是可选装饰:图一旦加载不出来,读者看到的就只有它。
3. **手写没有布局引擎,所以不能靠眼睛验收。** 交付前把 SVG 读进 DOM,逐个 `text` 元素量 `getBBox()`,确认没有超出画布、没有互相重叠;对齐关键的列要实测渲染 x 坐标是否同值。
4. **必须在常驻服务(端口 3000)上验收,不能只看开发服务器。** 交付后跑 `leet-restart`,否则常驻服务认不出新文件。2026-09-14 就栽在这一步:开发服务器(3001)上 200、常驻服务上 404,前端只渲染出 alt 文字 —— 而当时只看了 3001。
5. 当前阅读器**没有深色模式**,写死浅色背景是安全的;哪天加了深色主题,轨道 B 的存量图要回头改。
6. 轨道 B 不要求 archify 那套 JSON 规格与证据表 —— **但图上的每个数字仍然要能在底稿里找到出处**,和正文同一个标准。

### 两套写作规则

解读页的读者是人不是 agent,人脑记不住那么多。**覆盖率不是目标,信息熵才是**。下面两套规则按「什么时候能做到」分开:第一套只需要看当前这一节,第二套必须知道别的节写了什么。

**A. 随写随改(写每一节时就能做到)**

1. **痛点驱动:每个子系统都从「不这么做会出什么事」开篇,不从「它是什么」开篇**。固定顺序是 **痛点 → 为解决它提出了什么 → 怎么解决 → 代价是什么**,全章围绕这条痛点线展开,读者在任何一段都知道自己为什么在读它。样板是 02 章:开篇先讲朴素批处理的痛点,之后每一节都是「为了解决前面那个痛点,提出了什么」。
   - **讲稿没这么组织时,由我们重组**。老师的章节顺序常常是「按模块列举」,那是代码的组织方式不是理解的组织方式,转译时要翻成痛点线
   - **没有讲稿的项目,这就是默认骨架**
   - 判断标准很简单:随便指一段问「这段在解决什么问题」,答不上来就是写跑偏了
2. **一个概念只展开一次**。后面再提只给名字加一句话回指,和技术名词首次出现才解释是同一条道理。展开第二遍是在替读者做他已经做过的功课
3. **引用块只放一句话**,超过两句改用正文。typography 插件默认把引用块渲染成斜体,长了很难读(`app/globals.css` 已把斜体关掉,但这条纪律仍然有效)
4. **不解释常识词**。「原理」「图解」「流程」这类词不要加括号注释,专业文章里解释它们是在冒犯读者
5. **不写施工状态**。页面始终是最终版,不留「待确认」「下一批补」——那是给维护者看的,进底稿
6. **默认一个占位符都不放**(2026-09-11 用户拍板)。讲稿里用文字画的图已经足够清晰,占位符只会让页面变吵。**哪里需要补 archify 图由用户在通读时单独提出**,模型不预判、不预留。**注意这条管的是占位符和轨道 A**;轨道 B 的手写 SVG 是直接交付成品,不留占位,模型可以主动做(见「轨道 B」一节)
7. **不判断哪张文字图该转 archify**,同样由用户挑。判断边界是:**系统架构与子系统架构用 archify,流程图不管粗细一般不转**——archify 的图很占地方。**这一条只约束轨道 A**:轨道 B 画的不是「把某张文字图转成图」,而是文字和 ASCII 都表达不了的那一类,不在此列
8. **术语首次出现给一句话解释**,之后直接用
9. **每节只回答一个问题**,答完就停
10. **正文不写文件路径与行号**,统一进项目的代码索引页(`NN-代码索引.md`,全项目一页,不是每章一页)。索引页只写文件加符号名不写行号——行号随上游漂移,符号名不会;精确行号留在底稿
11. **表能说清的不写成段落**。**配置与参数一律用表格**,不用条目列表——参数天然有「名字 / 默认值 / 作用 / 怎么调」几个固定维度,列表写法会让读者自己在脑子里对齐这些维度
12. **加粗不紧贴括号或标点**,否则星号会漏出,`npm test` 会拦

**B. 全章写完后的全盘优化(必须看到全貌)**

1. **痛点线复核**(对应 A1):从头读一遍,每个子系统都要能答出「它解决什么痛点」。答不上来的,要么是写跑偏了,要么是这一节本来就不该独立成节。开篇的那条主痛点是否真的贯穿到末尾,也在这一步查
2. **重复展开合并**:同一概念在多节展开的,保留信息熵最高的那一处,其余压成一句话回指
3. **全周期走读去重**:只留最完整的那一份全流程;子系统的全周期压成「它在全流程里占哪一段」。判断方法是看两处走读的**结论**是否相同——结论一样就是重复,哪怕例子里的数字不同
4. **定位复核**:每个 Part 的定位是否还成立。vLLM 02 章就是这么发现「Part 3 源码解析」错位的——四个部分本来就都照源码核过,再单标一个「源码」反而误导,于是改成「机制之外:源码里额外读到的」,390 行压到 74 行
5. **目录**:不要在正文里手写目录,阅读器会从正文的二级标题自动生成可跳转目录(`components/ProjectReader.tsx`),手写的那份只会过期
6. **页头精简**:一句话定位加一句话说明来源与核对状态,不堆说明
7. **图的最终挑选**:用户通读时圈定哪些文字图转 archify(轨道 A)。轨道 B 的图在写作时就该判断要不要画,收尾时只复核两件事:**编码有没有承载信息**、**章节重组后文件名和章号还对不对得上**
8. **代码索引页补全**:新增的节要补进索引
9. **长度体检**:逐节问「这一节的行数配得上它的信息量吗」

### 与知识库框架篇的边界

| 同一个项目里的内容 | 知识库 | 开源解读 |
|---|---|---|
| 最初想解决的问题、核心抽象与长期范式 | 主体内容 | 总览只给定位 |
| 当前支持的后端、执行模式与高层架构 | 记录影响理解和选型的最新状态 | 由当前代码逐项证明 |
| 模块边界、一次训练的数据流 | 讲到能理解设计为止 | 拆到实际组件与调用链 |
| 调度器、状态机、失败恢复 | 只讲思想和代价 | 写清状态、触发条件和分支 |
| 关键函数、内部参数、文件路径、行号 | **不写** | **必须写** |

知识库的动态状态卡和本模块的源码基准可以互相提示更新,但不能互相替代验收:官方文档核对通过不等于读过代码,源码存在某个开关也不等于它已成为稳定能力。

## 维护流程

- 新解读 = 用户点名;先在下方状态表把该项目标 🚧,写完标 ✅(文字齐了就算完成,图由用户后续单独点名补)
- **施工范式:分阶段、分会话,绝不一次跑完整个项目**。每阶段结束就 commit,下阶段新开会话,靠底稿 `_登记表.md` 与 01-TASK 接续。
  - ① **探路**(主线程亲做):核对基准、读入口找边界、写底稿、在总览列出要拆成哪些问题页 → 交用户确认
  - ② **写文字**:一个会话推进一到三页;主线程做交叉核对、跑 `npm run os:check`、把纠正的口径回写底稿 → 交用户确认
  - ③ **收尾**:用户点名补图与理解增强件,按最终结构整理页面(见「两套写作规则」的 B 组)
  - 派子 agent 时一个 agent 一次只交一份产物,三分钟没文件落盘就重派;子 agent 只做 validate,不做 deliver 与 visual-check
  - 底稿常驻不删,更新基准时以它为查证清单
- 领班、账本这类纯 Python 组件可以用 `types.SimpleNamespace` 伪造 config 干跑真实代码得到走读数字(缺依赖用 `uv run --with xxhash --with numpy`),依赖 GPU 的部分只能读代码手算并注明
- 新收藏项目:repo 放进 `projects/<主题>/`(没有合适主题就新建),状态表加一行 ⬜
- 已有解读更新:先核对官方远端与本地工作树,再把总览的 tag/commit/日期和受影响的页与图一起更新,按证据表逐条复核;不能只改一句「支持 X」而留下旧调用链
- 验证:`npm test` 与 `npm run os:check` 两条命令,具体检查项以脚本为准(`tests/opensource.test.ts`、`scripts/os-check.mjs`),不在本文重复
  - `os:check` 会先把被检查项目同步到上游最新,再比对 `00-` 页记录的基准 commit 与当前 HEAD 的漂移。离线用 `--skip-sync`
  - **基准漂移不判失败**:基准号记的是「这份稿子当时照着哪个版本写的」,是历史事实,不是要追的目标。仓库保持最新是为了随时能基于最新源码提问,解读很久才更新一次,两者节奏本来就不同。所以三档信号是:
    - **✗ 失败**只留给「现在就是坏的」——证据表的原样引用对不上源码、页面引用的产物缺失、archify 校验不过、图上文字互相遮挡
    - **! 提醒**是「值得哪天看一眼」——**底稿引用的那几行真被上游改了**(行级比对:拿底稿记的基准侧行号和 `git diff -U0` 的旧侧 hunk 求交),附带列出没标行号、只能按文件判的引用
    - **· 信息行**只是记录漂移了多少提交,不用管
  - **全量复核只在用户点名时做**(看到未覆盖的新功能之类),不要因为提醒就停下手上的写作,也不要主动提议去补。当批新写的内容照常在写作时的 HEAD 上核对即可
  - 行级比对能成立,靠的是底稿把引用写成 `file.py:12-34`。**只写文件名的引用会退化成文件级**,噪音大;底稿记引用时尽量带行号
  - 证据表的书写格式见 skill `opensource-diagrams`(检查器有自己的识别规则,写错会误判)
  - 新增 `public/` 图片后跑 `leet-restart`,常驻服务才认新文件(它不重新构建,只让当前构建重读 `public/`;`leet-*` 是 `~/.zshrc` 里 source 进来的 shell 函数,**不是 npm script**,`npm run leet-restart` 会报找不到)。**验收要在端口 3000 上做**,开发服务器(3001)每次请求都查磁盘,那里看到的不算数
