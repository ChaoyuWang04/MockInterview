# 开源解读:规范与项目清单

定位:本模块提供 AI 阅读真实代码后产出的「总览 + 按问题分页」项目解读,只约束**源码项目解读**。Technical Report 与技术论文的解读是并列的独立模块,目录和写作流程见 [10-材料解读流程](10-材料解读流程.md)。魔改实验在服务器上做,本机只负责理解。

## 目录结构(两层分离)

- `projects/<主题>/<项目>/` —— 源码仓原样存放(**git 不追踪**),AI 撰写解读时的阅读材料。**保持上游最新由 `npm run projects:sync` 负责**,它对有未提交改动、有本地提交、游离 HEAD 的仓库一律不动只报告,这时不得擅自 pull 或 reset。**目录名不等于项目名**(`推理服务/TensorRT` 是 NVIDIA 的 TensorRT,不是 TensorRT-LLM),用之前先看一眼 README 确认身份
- `opensource/<主题>/<项目>/NN-<页名>.md` —— 解读文档(git 追踪,页面数据源,路由 `/opensource`);下划线开头的是底稿,阅读器隐藏
- `opensource/_执笔记录.md` —— 每份解读各章由哪个 Agent 后端执笔(阅读器隐藏);新写或重写一章后更新对应行
- `public/opensource/<项目>/NN-<slug>.svg` —— 图的交付位置(git 追踪);archify 图的规格与证据表同放解读目录下的 `diagrams/`

**大单体仓库按子系统拆成多份解读**:一个仓库里有几块各自够一个项目体量、痛点互不相同的子系统(典型是 `pytorch`),就按子系统各立一份解读,各走一遍完整流程。源码不另克隆,解读目录按子系统命名、放在它所属的主题下,底稿写清认领了仓库里哪几个目录;同一仓库的几份解读优先共用一个基准 commit 与快照。

两边的 `<主题>/<项目>` 目录名保持一致(按子系统拆的解读除外,它的源码在母仓所在主题下),`public/` 下只用项目名。阅读器把图与表放宽到整篇宽度,正文段落保持 52rem 居中。

## 怎么写

五组,按「写什么、真不真、查得到吗、怎么说、图怎么画」排。**主线程和子 Agent 都读这一节**;后面两节分角色:主线程看「一个项目怎么从头走到尾」,只写一章的子 Agent 看「你只写一章时照这个做」。机械能判的条目由 `npm test` 查(见本节末「自动检查」),这里只写需要判断力的。

**不要随意修改本文。** 施工中撞到的项目特例写进该项目 `_登记表.md`,不回写本守则。只有用户点名改 06 才改。子 Agent 报告里「守则没有、只能靠猜」是给主线程的输入,不是改 06 的授权。

### 1. 一章长什么样

**每章一页,几段话,各章长度相当。** 写得长不等于写得深;几句话能讲清的就只写几句话。页长不设硬指标,但一页只讲透一个问题。

**动笔前先答一个问题:这一章的 PagedAttention 是什么。** 一章只有一个主旨,其余内容都是这个主旨带出来的实事:问题在哪、机制怎么解决、代价落在哪。答不出主旨就不动笔。按实现模块列举(表、分配器、池、账)或按事故列举(崩、卡、慢)都是流水账;花半页解释前缀树是什么也是跑偏,那是知识库的活(见「与知识库的边界」)。

页头一句话定位本章要解决的问题,不回指别的项目,然后六段:

1. **核心问题**:哪种负载下哪个指标会坏,像骨折一样直白
2. **解法**:几句话,大白话,先说最天然的直觉,再补一句为什么实际不吃亏
3. **代价**
4. **和同类大厂框架不一样的地方**:用来衬托本项目的选择,不是正文主体。对照对象必须是大厂在大规模训练或推理里真用的框架;小框架不入对比。形式可以是短列表,也可以是一张对照表
5. **调参与观测**:参数在哪调(启动参数、配置文件、环境变量、请求参数、运行时接口,哪些要重启);一张参数表,每个参数写「在哪调、默认、调了之后哪个指标往哪边变、怎么看」;观测点(哪几行日志、响应里哪个字段、哪个接口);**典型配置**——两三套能直接抄走的起服务参数,各写清适用场景(卡型、模型、负载形态)与这套配置是拿什么换什么;最后一张「症状 → 先查 → 然后」表。这一段决定读者能不能上手,要写细
6. **常见误区**:以维护这个系统 30 年的人的身份写,只写真见过的错:排障时第一反应错在哪、哪个参数最常被调反、哪条日志最常被略过、哪个默认值最出人意料。**不是把前面的正确概念反过来再说一遍**,每条都要有「人们为什么会这么以为」和「实际上是什么」

一到三段是最简原理,第四段是对比,第五、六段是上手。**参数和配置表只出现在第 5 段**;第四段允许一张对照表(原理段仍无反引号、无裸参数名)。**标杆页 `opensource/推理服务/sglang/01-整体架构与请求流程.md`。** 每个项目的 01 章由主线程亲写,作为该项目后续子 Agent 的写法样板。

**重心在本项目,不抢参照。** 不要把本解读登记成「领域参照系」,也不要为了当参照去改别人的章。对比是衬托,正文主体是本项目的代码与选择。关于其他项目的断言同样要核,核不动就不写。

**和其他开源解读的边界。** 训练框架可以有「训练引擎」章,只写本项目怎么插拔、调度、换后端;引擎内部的分桶、通信、并行归那个引擎自己的解读。推理侧同理:写本项目怎么起服务、怎么透传,不重写引擎内部。这样项目之间不会抢同一段机制。

**算子项目的变体。** FlashAttention、FlashInfer、DeepGEMM、Triton、DeepEP 这类读的是 kernel,不是服务或训练框架。六段、原理段不写名字、图的规矩全部照旧,只换第 5 段的内容:没有起服务的参数,改写三样——编译期与 launch 参数(tile 形状、流水级数、warp 分工、目标架构)各自拿什么换什么;什么条件下派发到哪条 kernel;用 profiler 看哪几个指标判断它卡在算力还是带宽。典型配置表的三列换成「形状与硬件 | 走哪条 kernel | 拿什么换什么」。**通用的矩阵切法只在参考项目 FlashAttention 里讲一次**(tile 怎么切、数据怎么经 TMA 与共享内存流水、warp 怎么分工,落到 Hopper 与 Blackwell 的真实代码);其余算子项目只写本项目的特色,切法一句回指。抽象原理仍归知识库的「GEMM优化」「FlashAttention」两篇。

**`opensource/推理服务/vllm/` 是唯一例外**:它是课件转录,讲稿出自有 20 年一线推理经验的工程师——讲 KV cache 张口就是「为什么要链式哈希」「为什么要分级存储」,而不是从「什么是哈希表」讲起。**要学的是这种直击核心,不是它的篇幅。** 这份解读保留原样,不压短、不返工,也不受本节约束。**领域怎么划**:领域按「解决的是不是同一类问题」划,不按目录划。

**展开靠对话**:读者有疑问时在对话里讲透,讲透的可以回填成一段;不主动扩写。正文短不等于读得少,读到的东西进底稿。

**总览页**必须有:一句话核心(项目是什么、代码花在哪)、源码基准(仓库 URL、分支或 tag、完整 commit、核对日期)、总图、章表(主题 | 不这么做会怎样 | 做法一句话 | 详见)、组件登记表、阅读顺序、术语表(每个词只定义一次)、相关链接(arxiv 编号拿不准必须联网核实)。先用总图建立位置感,核心链路先出,外围模块留到后面;对比集中在「阅读顺序」,不以对比开章。样式照 `opensource/推理服务/vllm/00-总览.md`。

### 2. 真实性:只写读过的代码,只写现在

- **读了真实代码再写**,以仓库现状为准;组件不存在就不要写,严禁按「通常这类项目会有」编造。只看在线文档、论文或 README 不算读过代码
- **绑定可复现基准**:总览开头记官方仓库 URL、分支或 tag、完整 commit、核对日期。正文里的「当前」「默认」「支持」都指这组基准
- **只写当前状态,不做代际考古**。与论文当年的设计不一致是正常的,不写演进史;想知道当年长什么样去 [10-材料解读流程](10-材料解读流程.md)
- **论文只是很小的一部分参考**。开源项目的论文通常只覆盖整个系统的一小块,而且停在发表那一刻;**仓库现状是唯一事实来源**。论文只在拆解阶段用一次——对一遍章表看有没有漏掉的模块,结果记进底稿——**不作为章表依据,正文不与论文对照,也不解释论文里的东西今天变成了什么**;
- **否定性断言**(「没有调用点」「没人设置」「默认关」)靠全树 `git grep` 核,写进底稿。**正文里不出现标着「推断」的断言**——要么核到出处,要么把成立范围写成限定词。**关于其他项目的断言同样要核**,核不动就不写
- **痛点从哪来**:源码里的 NOTE 与 why 注释、docs 的最佳实践与排障段、官方博客的动机段、核对时撞到的意外。源码注释里写的设计理由是最值钱的东西

### 3. 覆盖面在底稿,不在正文

正文只写讲得清的那几句,覆盖面由底稿 `_登记表.md` 保证:读者提问时要能立刻在底稿里查到「这一处现在是什么样」。

- **底稿固定分节**:基准与核对方式、一句话核心、主张清单、候选章表(带把握程度)、覆盖率核对表(目录 | 体量 | 归哪一章 | 不写的理由)、待用户决定、分批进度、按章的断言清单
- **每章一份断言清单**,每条带基准上的 `file.py:12-34`。清单覆盖该章目录下的主要类、入口函数、docs 对应页和默认值,**不只覆盖正文提到的**;正文没提到的在「节」列标「备」。行号是 `os:check` 行级比对的依据,只写文件名会退化成文件级
- **代码索引页** `99-代码索引.md` 全项目一页,按章分节,只写文件加符号名不写行号(行号随上游漂移,符号名不会)
- 手算的数字、举例的参数值、图上的每个数字,都要在底稿注明来源;底稿常驻不删,更新基准时以它为查证清单

### 4. 怎么说

- **通俗直白**:术语首次出现给一句话解释或类比,之后直接用;不解释「原理」「流程」这类常识词;每节只回答一个问题,答完就停;一个概念只展开一次,再提只给名字加一句回指
- **原理段不出现名字**。**原理段 = 一到四段**(含第四段的对比),第 5、6 段才是名字密集的地方,`npm test` 按这个范围查。不写的是参数名、环境变量名、接口路由名,**以及取值名**(后端名、策略名、模式名这类要填进参数的词,`trtllm_mla`、`write_through` 都算);产品名与项目名不算(Mooncake、NIXL、DeepEP 可以直接写)。要指某个开关就说它是干什么的;(「有个开关能把切词挪到单独的执行器里攒批」),名字留给第 5 段。**这是最常犯的一条**——名字一多,原理段就被读成配置手册
- **双名制**:角色名在前、代码名在后;一个项目只用一个比喻,角色之间的关系也要在比喻里成立
- **通行的英文术语直接写英文,不要硬翻**。判据是中文技术圈平时怎么说:actor、critic、rollout、worker、logprob、prefill、decode 这类张口就是英文的词写英文;调度器、前缀缓存、显存、并行策略这类本来就有通行中文说法的写中文。**双名制里的「角色名」是你给组件起的说明性称呼,不是把英文名硬译成中文**——「评论家工作者」「策略工作者」比英文原词更难懂,是反面例子。这条和「读者已经读过知识库那几篇原理」是同一件事:该用的术语直接用,要解释的是这个项目自己的新词
- **数字**:数量、区间、时延、容量用阿拉伯数字(200–5000 token、50–500 毫秒、2 GB),不写「几百到几千」「九成」这种模糊说法
- **配置与参数一律用表格**,表能说清的不写成段落;引用块只放一句话,超过两句改用正文
- **页面始终是最终版**:施工状态、待办、占位符一律进底稿,不进正文
- 加粗的内容本身不要以标点开头或结尾(`**区别:**` 会漏星号),但**加粗后面紧跟句号、逗号是安全的,不要在中间补空格**;公式 KaTeX 块级 `$$` 独行;mermaid 只用于页内小图
- 页头一句话定位加一句话说明来源与核对状态。**后一句逐字照抄,只换基准号与 tag**(它在 lint 的重复白名单里,改了措辞反而会被当成跨章重复):**「说法都在源码基准 `<短号>`(tag `<tag>`)上核过,「当前」与「默认」都指这组基准。」** 第五段开头那句同理,写成 **「这一页的参数全是启动配置,改了要重新拉起整个作业。」**;第四段开头单独一句写成 **「对照对象是 <框架>(基准 <短号>)。」**(原理段不许反引号,基准号裸写),理由另起一句(并行写作的几章用同一个对照对象时,这句必然一字不差);不在正文手写目录,阅读器从 `##` 自动生成

### 5. 图

**两条轨道,选哪条只看用户有没有点名 archify。** 点名的走 archify(细则在 skill `opensource-diagrams`,要画时再读);**其余一切图都手写 SVG**——有节点和边也不是走 archify 的理由。

**画之前先问一句:这件事有形状吗。** 有形状的是:位置(谁在哪个进程)、时间(哪一步在干什么)、结构(内存怎么排)、数量的悬殊(一个是另一个的三十二分之一)。**判据是:读者要同时握住好几样东西才能 get 到这一段的点,而文字强迫他一样一样地读。** 内容本来是清单或参数表就用表格。

**下限:每章至少一张机制图**,交零张不合法。一章看上去全是清单与阈值时,先按上面的判据找出本章真正有形状的那一件事再画;实在找不到就问派人,仍然不能交零张。

**上限:需要时两到三张,不要泛滥。** 默认就那张机制图。第二张有形状再画,不要为了「默认两张」硬画差异图。第三张只在这一章确实有第二件「文字讲不清、图能一眼讲清」的事时才画。**多画一张的门槛是它自己能扛起一件事**,凑数的图比没有图更糟。

**宁可不画装饰,也不要拿方框凑数。** 这条约束的是多出来的张,不是整章零张:数字、上限、阈值、比例、预算没有形状;图上的信息量等于它上面那句话 → 那张不画。

**硬要求一:视觉编码必须承载信息。** 方块数从八变成一是因为头数变了,这叫编码;给同一句话配个好看的框不叫。

**硬要求二:并列摆放本身就是一句断言。** 把 A 的模块和 B 的模块放进同一列,等于声称这两个东西对应,读者一定会这么读。对比图按**双方都必须做的那件事**分行,让各自的模块去盖这些行,而不是按各自的模块名硬凑列数;名字不同但其实是同一个东西,在图上直接写明;真对不上的用箭头或一句话说清楚。

**图和正文是替代关系。** 图讲清了的,正文相应地删掉,不要再复述一遍同样的结构。机制图里可以出现参数名,**差异图里不写名字**,在图上留一句「两边的参数名都在第五节」;数字只在它是方框长度或格子数的标注时才上图,作为结论的数字留在正文。

**视觉规格(全库统一,新项目也照这套)**:

- 字体栈 `-apple-system, BlinkMacSystemFont, 'PingFang SC', 'Helvetica Neue', 'Microsoft YaHei', Arial, sans-serif`
- 标题 19px/700 `#111827`,副标题 13px `#6b7280`,方框标题 14px/700 `#111827`,方框内说明 11px `#6b7280`,旁注 11px `#9ca3af`
- 方框填充/描边成对用:绿 `#e3f4ec`/`#5fa886`、紫 `#ecebfb`/`#8f8bd8`、黄 `#fdf1dc`/`#d4a24c`、红 `#fbe9e7`/`#d9877a`、灰 `#eeeeee`/`#b9b9b9`;虚线容器 `#ffffff`/`#cbd2d9` 配 `stroke-dasharray="5 4"`;连线 `#9ca3af` 宽 1.4
- 一张图里**一种颜色只代表一件事**,副标题里写明这套颜色各代表什么
- 背景写死 `#ffffff`(阅读器没有深色模式);圆角 `rx="6"`,虚线容器 `rx="8"`

**交付**:放 `public/opensource/<项目>/`,命名 `NN<字母>-<slug>.svg`(`NN` 是所属章号,字母按本章第几张顺排)。**画布按最终渲染宽度定,别画完再缩**:横图取 1120,竖图只有正文栏宽 832,取 860;高度按内容排,不设规定。alt 写成一句完整的话——图加载不出来时读者只看得到它。

**验收不能靠眼睛**,但也不用自己发明检查器:`node scripts/svg-check.mjs <文件或目录>` 量三类碰撞(越界、文字互压、文字被后画的图形盖住),`npm run os:check` 也会跑它。

### 与知识库的边界

**通用机制只在知识库展开一次。** PagedAttention、RadixAttention、KV cache、PD 分离、并行策略、MoE 与 DeepEP、CUDA graph、FlashAttention、量化这些在 `knowledge/04-Infra/01-原理/` 已经各有一篇;解读里**不讲这些机制本身是什么**,只写「这个项目怎么用它、怎么调」。对比留给第四段,对照对象是大厂框架。动笔前先去知识库搜一遍,有就只留一句回指。

| 同一个项目里的内容 | 知识库 | 开源解读 |
|---|---|---|
| 最初想解决的问题、核心抽象与长期范式 | 主体内容 | 总览只给定位 |
| 当前支持的后端、执行模式与高层架构 | 记录影响理解和选型的最新状态 | 由当前代码逐项证明 |
| 模块边界、一次训练的数据流 | 讲到能理解设计为止 | 拆到实际组件与调用链 |
| 调度器、状态机、失败恢复 | 只讲思想和代价 | 写清状态、触发条件和分支 |
| 关键函数、内部参数、文件路径、行号 | 不写 | 写进底稿与代码索引页,正文不写 |

### 自动检查

`npm test` 固定跑 `tests/opensource-lint.test.ts`,查九条:六段齐全、原理段无反引号标识符、**原理段无裸参数名**(`--xxx`、`SGLANG_XXX`、带下划线的小写词)、无代码块、正文无文件行号、无模糊数量、无施工状态词、**跨章无一模一样的长句**、表格各行列数一致。返工期间脚本顶部可以放一份豁免清单,由返工那一章的人删掉自己那行(交付边界的唯一例外);清单空了就把常量和引用一起拆掉。

图的几何由 `node scripts/svg-check.mjs <文件或目录>` 查三类碰撞,`npm run os:check` 会跑它。

刻意**不**入脚本的四项(误报大于收益,靠人看):中文数字量词、alt 是否一句完整的话、调参表单元格非空、SVG 文字越界与重叠。

## 主线程:一个项目怎么从头走到尾

**分阶段、分会话,绝不一次跑完。** 每阶段 commit,下阶段新开会话,靠底稿与 `01-TASK.md` 接续。

**① 拆解**(亲做,不派):钉基准 commit(取主干最新,同时记下最近的发布 tag,便于以后说清那阵子是什么版本)→ 结构扫描(`git ls-tree` 出体量表,剔除测试、基准、脚本、文档)→ 主张采集(README、docs 的 advanced features、官方博客,每条落到一个目录)→ 划成十几章。

**怎么划:四条判据,每个拆分决定都要能说出依据是哪一条。**

| 判据 | 用法 |
|---|---|
| 体量 | 一个目录大到别的章装不下就独立成章;几个小目录合计还撑不起一章就合并 |
| 主张背书 | 官方博客或设计文档把几样东西当成一套系统讲,那就是一章 |
| 痛点是不是同一条 | 两个机制解决的是同一个痛点,合章;各有各的痛点,分章 |
| 同领域大厂框架有没有对应物 | 那些框架里完全没有对应物的,往往正是这个项目的招牌,独立成章 |

**合并规则**:各自撑不起一章、而痛点又能串成一条线的,合成一章(sglang 的采样、结构化输出、确定性就是这么合的)。**每章定下来后写一句「在哪些场景下哪个指标会坏」,写不出来的说明它不是一章**,降级并进别的章。

候选章表、把握程度(高:有博客或设计文档背书且读过入口代码;中:只读了目录与类清单;低:只有体量)、每条拆分决定的依据,全部写进底稿,不进正文。

**盲拆对比**:如果这个项目有第三方课程或成体系的解读,**候选章表定稿前不要看**,定稿后再对一遍答案,差异分「漏了 / 对方浅 / 视角不同」记进底稿。这是防止自己拆漏的唯一外部校验。

**② 覆盖率核对**:`node scripts/os-coverage.mjs <解读目录> <源码根>` 按代码索引页反查,列出每个目录被哪几章认领。**够体量又没人认领的**(默认阈值 120 KB,用 `--min-kb=` 改),要么补进章表,要么在底稿的覆盖率核对表里写明为什么不写(硬件移植、算子层、独立产品这类是正当理由)。不能靠印象。章还没写时索引页是空的,这一步等首批章成稿后补跑一次。

**③ 导出基准快照**(这一步不能省,后面每个子 Agent 都靠它):

```text
git -C projects/<主题>/<项目> archive <基准commit> <要读的顶层目录…> | tar -x -C /tmp/<项目>-base
```

`projects/` 里的工作树跟着上游漂,**而且 `npm run os:check` 开跑前会自动快进它**(`scripts/os-check.mjs` 调 `syncProjects`)。所以任何人读代码都读 `/tmp/<项目>-base`,不读 `projects/`。`/tmp` 重启会清,发现没了就重导一次。导不到的路径(比如没打进 archive 的子目录)用 `git -C projects/… show <commit>:<路径>`。

**④ 写序章**,照同领域已过门的总览骨架一次写成终稿形态 → **交用户确认。这是第一道门,序章没过不开写正文。**序章的总图是序章的一部分,**跟着序章一起交,不走第 5 组「收尾提图」那条流程**(那条管的是各章的配图)。

**④甲 写 01 章**(亲做,不派):序章过门后,主线程亲写第 01 章,作为后续子 Agent 的写法样板。01 没过门,不开派后面的章。

**⑤ 派章**:一个子 Agent 认领一章,从 02 起派。**派发时必须给它这几样**,少一样它就得靠猜:

| 给什么 | 为什么 |
|---|---|
| 守则路径 `docs/06-开源解读流程.md`,并说明「这是唯一标准,先完整读」 | 它没有任何其他上下文 |
| 要写的章号、章名、这一章管哪几个源码目录 | 拆解阶段的产物,它推不出来 |
| **基准快照路径 `/tmp/<项目>-base` 与基准 commit** | 不给就会去读 `projects/`,读到漂移后的版本 |
| 本项目 01 章样板页的**文件路径** | 写法照这个,不是对比对象 |
| 若本章要对比:对照对象成稿路径(可选) | 对照必须是大厂大规模在用的框架;不给就不要自己找小框架来比 |
| 底稿路径,以及这一章已有的断言行 | 避免重复核对 |
| 是新写还是**返工**;返工要说明「继承来的事实一律重核,不得照抄」 | 上一批的错会被原样带进新图 |
| 这一章画几张图 | **至少 1 张机制图**。第二、三张由派人按「有没有另一件有形状的事」决定,不要默认下差异图。写不出「这件事有形状吗」的那张就报上来不画,但机制图不能缺 |

**⑥ 验收**(逐条过,不能只看它的报告):

1. **事实**:抽查 3–5 条硬事实,自己去 `/tmp/<项目>-base` 上核,不信报告。返工的章额外抽查继承下来的旧断言
2. **图该不该存在**:机制图缺一张即退回。对多出来的张问一遍「这件事有形状吗」——这一条最容易漏,因为图合规不等于图有用
3. **图读起来对不对**:自己通读一遍——看不看得懂、并列有没有乱配对、编码有没有承载信息、术语层级。几何碰撞子 Agent 已跑过脚本,不用重复
4. **标着「推断」的断言**:要么落到出处,要么在正文写成限定词,不能原样发布
5. **跨章重复**:并行派出去的子 agent 互相看不见,同一个机制容易被两章各讲一遍。一模一样的长句由 `npm test` 拦;**概念层面的重复要你判断**——同一个机制只在主场那一章展开,别的章只留一句回指加章号
6. **越界改动**:子 Agent 只该改它那一章的东西(见下一节的交付边界)。它改了守则正文、别的章、别人会话的文件,一律回滚
7. `npm test`、`npm run os:check`、端口 3000 上通读 → 交用户逐章验收

**⑦ 收尾**:按第 5 组提图,用户逐张拍板。

其余:新解读 = 用户点名,先在状态表标 🚧,写完标 ✅。新收藏项目 repo 放进 `projects/<主题>/`,状态表加一行 ⬜。已有解读更新时,把总览的 tag/commit/日期和受影响的页与图一起更新,按底稿逐条复核,不能只改一句「支持 X」而留下旧调用链。**基准漂移不判失败**——基准号记的是「这份稿子照着哪个版本写的」,是历史事实不是要追的目标。

## 子 Agent:你只写一章时照这个做

你没有任何背景知识,**这份文档是你唯一的标准**。缺什么就回去问派你的人,不要自己发明。

**动手前**

1. 把「怎么写」五组和「与知识库的边界」完整读一遍
2. 读本项目 01 章样板页(派人会给路径)。写作骨架以「怎么写」第 1 组为准
3. **代码只读给你的基准快照**(`/tmp/<项目>-base`)。**不要读 `projects/`**,那里跟着上游漂;也不要跑 `npm run os:check`,它会快进 `projects/`
4. 读者是什么人:**他已经读过知识库那几篇原理**。所以 prefill、decode、TP、KV cache 这类词直接用,**不要换成大白话**——把他已经掌握的术语翻译成「一块一块地算」反而看不懂。要解释的是这个项目**自己**的新词
5. 动笔前答出「这一章的 PagedAttention 是什么」。答不出就回去问,不要硬写

**写**

按「怎么写」第 1 组的六段。两处容易卡住的:

- **典型配置**:做成表格(场景 | 怎么起 | 拿什么换什么),参数名用行内反引号——**不要用代码块**,那是硬约束。参数名和默认值必须来自你核过的参数表;组合与推荐值是按语义推的起点。表后固定写这一句,**逐字照抄不要改写**(它在 lint 的重复白名单里,改了措辞反而会被当成跨章重复):**「组合与推荐值是按语义推的起点,不是实测最优。」** 来源记进底稿。这不算编造,**但凭空写一个没在代码里出现过的参数名算**
- **返工已有章节**:继承来的每条事实都要在基准上重核一遍,尤其是数字和取值范围。上一批写对的不用改,写错的必须改——**照抄是最常见的翻车方式**

**画**

只画派你的人明确要求的张数,且至少有一张机制图。按第 5 组:先问「这件事有形状吗」,再按视觉规格画,画完跑 `node scripts/svg-check.mjs <你画的图>` 直到全绿。**图读起来对不对由主线程验收,你不用自己通读评判**——你负责画对、画干净。

**自查**

跑 `npm test` 和上面那条 svg-check,全绿即可。事实要能逐条指到 `/tmp/<项目>-base` 里的 `文件:行号`。

**交付边界**

- **该改**:你那一章的 `.md`、它的 SVG、底稿 `_登记表.md` 里属于这一章的段落、`99-代码索引.md` 里这一章那一节
- **不该碰**:`docs/` 下任何文档、别的章、状态表、`tests/` 与 `scripts/` 下的逻辑、工作区里已有的其他改动。要改这些就在报告里提出来,由主线程决定。**唯一例外**:返工期间若脚本顶部有你这一章的豁免行,删掉那一行——只删那一行,不动脚本逻辑
- **不要 commit**

**报告只回答三问,每问几行,不要复述过程**:① 改了哪些文件(路径);② **哪些信息是守则里没有、你只能靠猜的**(逐条,这是守则迭代的输入,不要省);③ 自查结果(`npm test` 与 svg-check 是否全绿)、以及留给主线程决定的事。验证叙述、事实清单、图的读后感都不要写进报告——事实在底稿里,图由主线程验收。
