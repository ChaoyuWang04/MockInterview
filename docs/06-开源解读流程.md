# 开源解读:规范与项目清单

定位:本模块提供 AI 阅读真实代码后产出的「总览 + 按问题分页」项目解读,只约束**源码项目解读**。Technical Report 与技术论文的解读是并列的独立模块,目录和写作流程见 [10-材料解读流程](10-材料解读流程.md)。魔改实验在服务器上做,本机只负责理解。

## 目录结构(两层分离)

- `projects/<主题>/<项目>/` —— 源码仓原样存放(**git 不追踪**),AI 撰写解读时的阅读材料。**保持上游最新由 `npm run projects:sync` 负责**,它对有未提交改动、有本地提交、游离 HEAD 的仓库一律不动只报告,这时不得擅自 pull 或 reset。**目录名不等于项目名**(`推理服务/TensorRT` 是 NVIDIA 的 TensorRT,不是 TensorRT-LLM),用之前先看一眼 README 确认身份
- `opensource/<主题>/<项目>/NN-<页名>.md` —— 解读文档(git 追踪,页面数据源,路由 `/opensource`);下划线开头的是底稿,阅读器隐藏
- `public/opensource/<项目>/NN-<slug>.svg` —— 图的交付位置(git 追踪);archify 图的规格与证据表同放解读目录下的 `diagrams/`

两边的 `<主题>/<项目>` 目录名保持一致,`public/` 下只用项目名。阅读器把图与表放宽到整篇宽度,正文段落保持 52rem 居中。

## 怎么写

五组,按「写什么、真不真、查得到吗、怎么说、图怎么画」排。机械能判的条目由 `npm test` 查(见本节末「自动检查」),这里只写需要判断力的。

### 1. 一章长什么样

**每章一页,几段话,各章长度相当。** 写得长不等于写得深;几句话能讲清的就只写几句话。页长不设硬指标,但一页只讲透一个问题。

**动笔前先答一个问题:这一章的 PagedAttention 是什么。** 一章只有一个主旨,其余内容都是这个主旨带出来的实事:问题在哪、机制怎么解决、代价落在哪。答不出主旨就不动笔。按实现模块列举(表、分配器、池、账)或按事故列举(崩、卡、慢)都是流水账;花半页解释前缀树是什么也是跑偏,那是知识库的活(见「与知识库的边界」)。

页头一句话回指参照项目的对应章(写章名,不写编号),然后六段:

1. **核心问题**:哪种负载下哪个指标会坏,像骨折一样直白
2. **解法**:几句话,大白话,先说最天然的直觉,再补一句为什么实际不吃亏
3. **代价**
4. **和参照项目不一样的 N 处**
5. **调参与观测**:参数在哪调(启动参数、配置文件、环境变量、请求参数、运行时接口,哪些要重启);一张参数表,每个参数写「在哪调、默认、调了之后哪个指标往哪边变、怎么看」;观测点(哪几行日志、响应里哪个字段、哪个接口);**典型配置**——两三套能直接抄走的起服务参数,各写清适用场景(卡型、模型、负载形态)与这套配置是拿什么换什么;最后一张「症状 → 先查 → 然后」表。这一段决定读者能不能上手,要写细
6. **常见误区**:以维护这个系统 30 年的人的身份写,只写真见过的错:排障时第一反应错在哪、哪个参数最常被调反、哪条日志最常被略过、哪个默认值最出人意料。**不是把前面的正确概念反过来再说一遍**,每条都要有「人们为什么会这么以为」和「实际上是什么」

一到三段是最简原理,第四段是对比,第五、六段是上手。表格只出现在第 5 段。**标杆页 `opensource/推理服务/sglang/01-整体架构与请求流程.md`。**

**参照项目**:每个领域选一个最先读透、抽象最完善的项目当参照系,同领域的其他项目都和它对比(推理引擎 vLLM,训练与 RL verl);参照项目自己的解读没有可比对象,第四段改写成「和同类常见做法不一样的地方」。**`opensource/推理服务/vllm/` 是唯一例外**:它是课件转录,讲稿出自有 20 年一线推理经验的工程师——讲 KV cache 张口就是「为什么要链式哈希」「为什么要分级存储」,而不是从「什么是哈希表」讲起。**要学的是这种直击核心,不是它的篇幅。** 这份解读保留原样,不压短、不返工,也不受本节约束。

**展开靠对话**:读者有疑问时在对话里讲透,讲透的可以回填成一段;不主动扩写。正文短不等于读得少,读到的东西进底稿。

**总览页**必须有:一句话核心(项目是什么、代码花在哪)、源码基准(仓库 URL、分支或 tag、完整 commit、核对日期)、总图、栈定位表、章表(主题 | 不这么做会怎样 | 做法一句话 | 详见)、组件登记表、阅读顺序、术语表(每个词只定义一次)、相关链接(arxiv 编号拿不准必须联网核实)。先用总图建立位置感,核心链路先出,外围模块留到后面;对比集中在「阅读顺序」,不以对比开章。样式照 `opensource/推理服务/vllm/00-总览.md`。

### 2. 真实性:只写读过的代码,只写现在

- **读了真实代码再写**,以仓库现状为准;组件不存在就不要写,严禁按「通常这类项目会有」编造。只看在线文档、论文或 README 不算读过代码
- **绑定可复现基准**:总览开头记官方仓库 URL、分支或 tag、完整 commit、核对日期。正文里的「当前」「默认」「支持」都指这组基准
- **只写当前状态,不做代际考古**。与论文当年的设计不一致是正常的,不写演进史;想知道当年长什么样去 [10-材料解读流程](10-材料解读流程.md)
- **否定性断言**(「没有调用点」「没人设置」「默认关」)靠全树 `git grep` 核,写进底稿。**正文里不出现标着「推断」的断言**——要么核到出处,要么把成立范围写成限定词。**关于其他项目的断言同样要核**,核不动就不写
- **痛点从哪来**:源码里的 NOTE 与 why 注释、docs 的最佳实践与排障段、官方博客的动机段、核对时撞到的意外。源码注释里写的设计理由是最值钱的东西

### 3. 覆盖面在底稿,不在正文

正文只写讲得清的那几句,覆盖面由底稿 `_登记表.md` 保证:读者提问时要能立刻在底稿里查到「这一处现在是什么样」。

- **底稿固定分节**:基准与核对方式、一句话核心、主张清单、候选章表(带把握程度)、覆盖率核对表(目录 | 体量 | 归哪一章 | 不写的理由)、待用户决定、分批进度、按章的断言清单
- **每章一份断言清单**,每条带基准上的 `file.py:12-34`。清单覆盖该章目录下的主要类、入口函数、docs 对应页和默认值,**不只覆盖正文提到的**;正文没提到的在「节」列标「备」。行号是 `os:check` 行级比对的依据,只写文件名会退化成文件级
- **代码索引页** `99-代码索引.md` 全项目一页,按章分节,只写文件加符号名不写行号(行号随上游漂移,符号名不会)
- 手算的数字、举例的参数值、图上的每个数字,都要在底稿注明来源;底稿常驻不删,更新基准时以它为查证清单

### 4. 怎么说

- **通俗直白**:术语首次出现给一句话解释或类比,之后直接用;不解释「原理」「流程」这类常识词;每节只回答一个问题,答完就停;一个概念只展开一次,再提只给名字加一句回指
- **原理段不出现名字**:讲机制、讲痛点的段落里不写参数名、环境变量名、接口路由名;要指某个开关就说它是干什么的(「有个开关能把切词挪到单独的执行器里攒批」),名字留给第 5 段。**这是最常犯的一条**——名字一多,原理段就被读成配置手册
- **双名制**:角色名在前、代码名在后;一个项目只用一个比喻,角色之间的关系也要在比喻里成立
- **数字**:数量、区间、时延、容量用阿拉伯数字(200–5000 token、50–500 毫秒、2 GB),不写「几百到几千」「九成」这种模糊说法
- **配置与参数一律用表格**,表能说清的不写成段落;引用块只放一句话,超过两句改用正文
- **页面始终是最终版**:施工状态、待办、占位符一律进底稿,不进正文
- 加粗的内容本身不要以标点开头或结尾(`**区别:**` 会漏星号),但**加粗后面紧跟句号、逗号是安全的,不要在中间补空格**;公式 KaTeX 块级 `$$` 独行;mermaid 只用于页内小图
- 页头一句话定位加一句话说明来源与核对状态;不在正文手写目录,阅读器从 `##` 自动生成

### 5. 图

**两条轨道,选哪条只看用户有没有点名 archify**,没有别的判定边界。点名的走 archify(细则、图型约束、证据表格式全在 skill `opensource-diagrams`,要画时再读);**其余一切图都手写 SVG**——有节点和边也不是走 archify 的理由。

**什么时候画:读者要同时握住好几样东西才能 get 到这一段的点,而文字强迫他一样一样地读。** 满足就值得画,不满足别画。常见的是一眼对比、量级差异、结构即语义、反直觉的形状——这是例子不是清单。内容本来就是清单或参数表就用表格;图上的信息量等于它上面那句话就不画。**宁可不画,也不要画装饰。**

**硬要求一:视觉编码必须承载信息。** 八个方块代表八个头、方块数从八变成一是因为头数变了,这叫编码;给同一句话配个好看的框不叫。

**硬要求二:并列摆放本身就是一句断言。** 把 A 的模块和 B 的模块放进同一列,等于声称这两个东西对应,读者一定会这么读。所以对比图按**双方都必须做的那件事**分行,让各自的模块去盖这些行,而不是按各自的模块名硬凑成同样的列数;名字不同但其实是同一个东西,在图上直接写明;真对不上的用箭头或一句话说清楚。

**图和正文是替代关系,不是补充关系。** 图讲清了的,正文相应地删掉,不要再用文字复述一遍同样的结构。**每章推荐两张**:本章机制图一张、与参照项目的差异图一张,多了就散。

**提出的时机:一批做完之后单独提一次,由用户逐张拍板。** 写作中途发现某段值得配图先记着,不要中断当前这批——值不值得画要看这一节最终写成什么样。没有想画的就什么都不用说。

**交付**:放 `public/opensource/<项目>/`,命名 `NN<字母>-<slug>.svg`(`NN` 是所属章号)。**画布按最终渲染宽度定,别画完再缩**:横图取 1120,竖图只有正文栏宽 832,取 860。alt 写成一句完整的话——图加载不出来时读者只看得到它。**手写没有布局引擎,不能靠眼睛验收**:把 SVG 读进 DOM 量三类碰撞——文字对画布边界、文字对文字、文字对 `rect` 与 `polyline`(只比文字对文字,查不出行标题被方框盖住)。新增图片后跑 `leet-restart`,**验收在端口 3000 上做**;阅读器没有深色模式,写死浅色背景。

### 与知识库的边界

**通用机制只在知识库展开一次。** PagedAttention、RadixAttention、KV cache、PD 分离、并行策略、MoE 与 DeepEP、CUDA graph、FlashAttention、量化这些在 `knowledge/04-Infra/01-原理/` 已经各有一篇;解读里**不讲这些机制本身是什么**,只写「这个项目怎么用它、和参照项目有什么不同、怎么调」。动笔前先去知识库搜一遍,有就只留一句回指。

| 同一个项目里的内容 | 知识库 | 开源解读 |
|---|---|---|
| 最初想解决的问题、核心抽象与长期范式 | 主体内容 | 总览只给定位 |
| 当前支持的后端、执行模式与高层架构 | 记录影响理解和选型的最新状态 | 由当前代码逐项证明 |
| 模块边界、一次训练的数据流 | 讲到能理解设计为止 | 拆到实际组件与调用链 |
| 调度器、状态机、失败恢复 | 只讲思想和代价 | 写清状态、触发条件和分支 |
| 关键函数、内部参数、文件路径、行号 | 不写 | 写进底稿与代码索引页,正文不写 |

知识库的动态状态卡和本模块的源码基准可以互相提示更新,但不能互相替代验收:官方文档核对通过不等于读过代码,源码存在某个开关也不等于它已成为稳定能力。

### 自动检查

`npm test` 固定跑 `tests/opensource-lint.test.ts`,查七条:六段齐全、原理段无反引号标识符、无代码块、正文无文件行号、无模糊数量、无施工状态词、表格各行列数一致。豁免清单写在脚本顶部,**返工一章删一行**,并有一条反向检查防止清单过期。

刻意**不**入脚本的四项(误报大于收益,靠人看):中文数字量词、alt 是否一句完整的话、调参表单元格非空、SVG 文字越界与重叠。

## 维护流程

- 新解读 = 用户点名;先在下方状态表标 🚧,写完标 ✅
- **分阶段、分会话,绝不一次跑完整个项目**。每阶段 commit,下阶段新开会话,靠底稿与 `01-TASK.md` 接续
  - ① **code-first 探测**(主线程亲做):钉基准 → 结构扫描(`git ls-tree` 出体量表,剔除测试、基准、脚本、文档)→ 主张采集(README、docs 的 advanced features、官方博客,每条落到一个目录)→ 划成十几章,每章管几个核心功能,每章写一句「在哪些场景下哪个指标会坏」
  - ② **覆盖率核对**:逐个目录问「它归哪一章」。够体量又指不到任何一章的,要么补进章表,要么在底稿写明为什么不写。这一步保证功能点覆盖了仓库里所有关键逻辑,不能靠印象
  - ③ **写序章**,照参照项目的总览样式一次写成终稿形态 → **交用户确认。这是第一道门,序章没过不开写正文**
  - ④ **逐章推进**:一个会话可推进多页,每页的底稿断言清单不能省。写完跑 `npm test`,主线程做交叉核对、跑 `npm run os:check`、把纠正的口径回写底稿,在端口 3000 上通读 → 交用户逐章验收
  - ⑤ **收尾**:按第 5 组提图,用户逐张拍板
  - 派子 agent 时一个 agent 一次只交一份产物;子 agent 只做 validate,不做 deliver
- 新收藏项目:repo 放进 `projects/<主题>/`,状态表加一行 ⬜。已有解读更新:先核对官方远端与本地工作树,再把总览的 tag/commit/日期和受影响的页与图一起更新,按底稿逐条复核,不能只改一句「支持 X」而留下旧调用链
- 验证:`npm test` 与 `npm run os:check`,检查项以脚本为准。**基准漂移不判失败**——基准号记的是「这份稿子照着哪个版本写的」,是历史事实不是要追的目标;失败只留给「现在就是坏的」。全量复核只在用户点名时做
- 刷题/知识库遇到与某项目强相关的考点,可在解读页的「面试考点串联」补一行,反向链接用纯文本
