# 基模 Technical Report 解读流程

定位:按公司保存公开基模 Technical Report 原件,并把每份报告写成一篇可以独立读懂、真正帮助记忆与迁移的中文长文。这里研究的是**模型报告里公开的设计**;阅读真实源码的项目解读仍走 [06-开源解读流程](06-开源解读流程.md),两者不要混写。

## 一、目录与网页

```text
papers/<公司>/<报告>.pdf      # 原件,默认不被 git 追踪
reports/<公司>/<报告>.md     # 解读,必须被 git 追踪
```

- 同一家公司在两边使用完全相同的目录名;报告文件使用稳定、可读的模型或报告名,如 `DeepSeek-V4.pdf` 与 `DeepSeek-V4.md`
- 公司目录按**模型或项目的主要归属方**确定。高校与多家公司联合署名时,不额外创建“联合”“高校”或重复公司目录;合作关系在解读正文中说明。若归属确实无法判断,先核对论文首页、官方发布页和项目仓库,不要凭作者邮箱猜
- 文件名只保留稳定的模型或项目名。模型正式名称自带的代际或版本号(如 `DeepSeek-V3.2`、`Hunyuan3D-2.0`)必须保留;不要再把日期、arXiv 修订号、完整论文副标题或冗余版本后缀塞进路径,这些信息写在解读正文里
- PDF 是事实原件,是否随 git 保存由维护者逐篇决定。`.gitignore` 默认忽略 PDF;确需保存时使用 `git add -f papers/<公司>/<报告>.pdf`
- Markdown 是网页数据源。一级标题 `# ...` 是索引页显示的标题;以下正文正常使用 `##`、`###`
- 每篇已发布报告必须在一级标题下保存 `<!-- release-date: YYYY-MM-DD -->`。它记录**模型实际首次向外公开的日期**;若报告只公开技术、尚未发布模型,则记录该技术首次官方公开日。不得使用 arXiv 修订日、PDF 上传日、本站撰写日或 git 提交日代替
- `/reports` 保持按公司分组;每家公司内按 `release-date` 降序排列,网格阅读顺序是从左到右、再从上到下的新到旧。同日发布时再按报告名称稳定排序
- `reports/` 中以下划线或点开头的公司/文件不会出现在网页,可用于未完成草稿;正式发布时再改成普通文件名
- 主页「📄 基模报告」进入 `/reports`;索引按公司分组,每张卡片进入一篇完整长文

**一份报告只对应一篇解读。** 不要另建“算法篇”“训练篇”“infra 篇”,也不建立重复的元数据、代际表或关键词数据库。算法、架构、训练 recipe、infra 和关键词都在同一篇文章里形成一条完整叙事。

## 二、开始写之前

1. 确认拿到的是目标报告的完整 PDF,记录封面上的正式标题、版本或发布日期
2. 去模型的官方发布页、官方仓库或官方新闻核对实际首发日,写入 `release-date`;论文页只能在没有更直接官方记录时作为备选证据
3. **动笔前必须查版本**:去官方论文页、官方仓库或发布页检查是否有更新修订。若官方版比本地 PDF 新,先用官方原件替换稳定路径下的旧文件,再重新核对标题、版本、日期、页数和文件完整性;旧版报告地图与页码不得沿用。若因研究需要刻意保留旧版,必须在文章开头明说依据版本及原因
4. 同时做文本提取与逐页视觉检查。文本提取用于搜索,页面渲染用于核对公式、表格、图注、上下标和版式;不能只信 OCR 或抽取文本
5. 先画“报告地图”:按原报告章节列出全部技术主张、关键数字、图表和实验结论,给每项记下 PDF 页码
6. 标出三个层次:**报告明确写了什么**、**我们如何解释它**、**哪些是外部资料补充**。三者不能混成作者原话
7. 遇到论文身份、外部项目或版本现状不确定时,查官方论文页、项目仓库或官方文档;没有证据就保留不确定性,不猜

只有完成报告地图后才开始写正文。这样可以避免文章只追着摘要写,漏掉附录、训练细节或 infra 约束。

## 三、长文写作契约

目标不是把 PDF 翻译一遍,而是让读者读完后能够回答三个问题:

1. 它到底做了什么,整个系统如何连起来?
2. 为什么要这样设计,它解决了旧方案的哪个具体矛盾?
3. 哪些思想可以迁移到自己的模型训练、推理或基础设施项目?

写作必须满足:

- **极其简单直白**:短句优先;术语首次出现先说人话,再给正式定义;能用一个小例子讲清就不要先堆符号
- **先全景、后细节、再回到全景**:开头给读者一张模型与训练全貌图;每个设计讲完后说明它接在系统哪里、影响谁
- **完整覆盖但不机械复述**:算法、模型架构、数据、训练 recipe、推理、并行与通信、算子/系统优化、评测和已知限制,报告写到什么就覆盖什么;报告没写的明确说没写
- **每个重点都讲原因**:按“旧问题 → 新设计 → 工作机制 → 收益 → 代价/适用边界”展开,不能只列名词和结论
- **保留可迁移启发**:每个核心设计末尾回答“对自己的项目有什么用”;区分可直接复用的技巧与依赖特定规模/硬件的做法
- **图表服务于理解**:优先自己重画简洁 Mermaid 流程图;直接引用报告图表时注明 PDF 页码,不把装饰图当内容
- **数字可追溯**:参数量、token 数、训练成本、吞吐、精度变化等数字紧跟 `(PDF p. N)`;不要凭印象补数字
- **外部补充可辨认**:外部资料只用于补背景或交叉核验,给出链接并明确标成补充,不能冒充报告内容
- **关键词在文中解释**:默认读者第一次接触这些概念。术语首次出现时先说人话,再给中文名、英文全称和缩写;开头几次不要只丢缩写。若开篇术语密集,先放一小段必要的读前背景,但不要让词汇表抢走正文篇幅。文末可用一小节串联关键词;不另建只列名词、不讲关系的索引实体

文章通常会自然包含:一句话结论、阅读路线、全景架构、逐项核心设计、数据与训练 recipe、infra/推理、实验怎么证明、限制与未公开信息、可迁移启发、关键词回看和参考资料。**这只是覆盖清单,不是已冻结模板**;章节顺序应服从该报告自己的叙事。

### 标杆文风的六条硬约束

1. **先讲矛盾,再上名词**:先让读者知道旧方法卡在哪,再引入新设计;不从摘要复读或缩写清单开场
2. **一段只推进一个意思**:短句、短段落优先,用“因为”把结论和原因接起来;类比要帮助建模,但不能当作论文证据
3. **复杂设计都走完一条因果链**:旧问题 → 新设计 → 工作机制 → 收益 → 代价/边界 → 可迁移启发。不要只讲“它是什么”
4. **公式也要像正文一样可读**:行内公式只用 `$...$`,独立公式用 `$$...$$`;当前渲染链不支持 `\(...\)`,禁止使用。公式前先说它要算什么,公式后解释符号和操作;上下标太多时,先定义中间量或拆成两步,不为了照抄原式牺牲阅读
5. **图要说清真实性边界**:自己重画的图必须注明根据哪个 PDF 图/页面,并区分“机制示意”与“实测时间/数据”。Mermaid 的节点、时间轴和箭头都要人工核对,能渲染不等于含义正确
6. **读完必须留下判断,不只留下摘要**:明确哪些结论被实验支持,哪些只是作者观察,哪些实现细节没有公开;最后把可迁移的设计原则串回整个系统

## 四、从 PDF 到发布

1. **投递**:PDF 放进 `papers/<公司>/`,确认公司和报告名
2. **版本核验**:按第二节搜索官方最新版;发现更新先替换原件并重新确认完整性,再进入后续流程
3. **通读**:提取文本、渲染页面,完成报告地图和页码证据
4. **组织**:找到贯穿全文的主要矛盾,决定文章叙事,列出必须讲清的核心设计
5. **撰写**:默认在 `reports/<公司>/_<报告>.md` 写未发布稿;若需要直接检验真实网页渲染,也可使用正式文件名公开审阅。一边写一边回查 PDF,不靠二手摘要
6. **自审**:逐项检查覆盖、事实层次、数字页码、图表含义、限制和可迁移启发
7. **验收**:让用户阅读全文并指出难懂、缺失或不够有启发的地方;按内容问题重写,不做表面润色
8. **发布**:隐藏审阅的稿件在验收通过后去掉文件名前的 `_`;公开审阅的稿件则保持正式文件名。两种方式都要运行验证并 commit

## 五、已验收标杆与子 agent 协作

第一篇已验收标杆固定为:

```text
papers/DeepSeek/DeepSeek-V4.pdf
reports/DeepSeek/DeepSeek-V4.md    # 在真实网页中公开验收
```

DeepSeek-V4 于 2026-09-05 获得用户明确验收,是后续报告的**语言、解释深度、因果链和启发性**标杆。后续文章要学它“如何让陌生技术变得可理解”,不得机械复制它的标题、篇幅、类比或章节顺序。

可以让多个子 agent 并行撰写,但协作边界必须清楚:

- 一个子 agent 只拥有一份 PDF 和对应的一篇 Markdown;禁止多个 agent 同时改同一篇报告
- 任务开始前必须完整阅读本流程和 DeepSeek-V4 标杆,再完成自己报告的章节地图与页码证据
- 任务中必须给出精确的 `papers/<公司>/<报告>.pdf` 和 `reports/<公司>/<报告>.md`,不让 agent 自行发明目录、拆文章或新建元数据实体
- 子 agent 交付时要列出:已覆盖的报告部分、重要数字的页码、外部补充、未公开/无法核实的缺口、测试与网页渲染结果
- 并行完成不等于自动验收。主维护者仍需逐篇对照 PDF、检查网页,最终由用户确认是否达到标杆

## 六、验收与验证

人工验收逐项回答:

- 原报告的每个主要贡献、关键实验和重要限制是否都能在文章中找到
- 架构、算法、训练 recipe 和 infra 是否讲清“为什么”,而非只给摘要
- 每个精确数字和报告图表是否能回到正确页码
- 推断和外部补充是否与报告原文清楚分开
- 不看 PDF 的读者是否能沿文章独立复述整体设计,并说出至少几条可迁移启发
- 有没有为了显得完整而补写报告未公开的实现

代码验证:

```bash
npm test
npm run build
```

真实网页还要人工检查:

- 页面能从 `/reports/<公司>/<报告>` 打开,目录卡片与标题正确
- 索引仍按公司分组;每组卡片显示经官方证据核对的实际首发日,并从左到右、从上到下严格按新到旧排列;修订日或本站更新日不得改变顺序
- Mermaid 已生成 SVG 且没有 `.mermaid-error`;图中的箭头、分支和标签与正文含义一致
- KaTeX 公式没有溢出、上下跳动或暴露 LaTeX 命令;复杂上下标在窄屏仍可阅读
- 页面正文不应露出原始 Markdown 标记,尤其检查 `**术语**` 后紧接中文时是否把星号原样显示
- 至少抽查桌面与窄屏下的开头、最长公式、最宽表格和最复杂图

自动测试只守护目录扫描、标题、路由数据和路径安全,不能证明解读正确。报告发布前必须保留逐页人工核对与真实网页验收。
