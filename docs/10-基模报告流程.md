# 报告解读流程

定位:按公司保存公开的基模 Technical Report 与核心技术论文原件,并把每份写成一篇可以独立读懂、真正帮助记忆与迁移的中文长文。这里研究的是**公开材料里写明的设计**;阅读真实源码的项目解读仍走 [06-开源解读流程](06-开源解读流程.md),两者不要混写。

**两个模块的时间轴不同,这是设计如此,不是矛盾**:本模块讲的是**那份材料当年写了什么**,06 讲的是**那个项目现在是什么样**。所以同一个项目在两边说法不一致完全正常(例如 PagedAttention 论文里没有自动前缀缓存,而今天的 vLLM 默认开启)。**不要为了对齐而改动任何一边**:本模块只依据 PDF,不拿源码现状补写论文;06 只依据当前代码,不回溯论文原意。读者需要跨代际对照时,由本模块在文中说明「论文之后发生了什么」并给官方外部证据。

三类材料**同一个流程、同一页、同一套契约**,只有讲解重心不同:基模报告讲整个模型怎么连起来,技术论文讲这项技术本身以及它怎么支撑基模的训练或推理,**网页形式的公开报告**(官方博客、公开 recipe 页、实验记录)讲这套做法本身以及它凭什么成立。不为此新增目录、标签、元数据或第二套规则。

**网页形式不是"次一等的论文"。** 当代不少最前沿的训练 recipe、系统工程实践和实验结论只以博客形式公开,从不写成论文,其指导价值不低于同期论文。它与论文的真正差别在**信息形态**:论文把细节全铺开在正文里,网页把大量背景留在链接里——评判框架可能定义在伴随博客中,benchmark 只给一个名字,方法出处只是一个编号。因此**网页原件必须跟着链接读**,见第二节第 8 条。

**收哪些:**

- 基模报告早于 Qwen3 报告的不再收录。**OpenAI、Anthropic、Google、Meta、DeepSeek、Moonshot、Z.ai、NVIDIA、Alibaba 九家不受此限**
- 技术论文只收大厂在基石算法之上做的修改与演进(如 GRPO 之于 PPO)。**奠基性算法本身不收录也不留存原件**,需要时联网查原文即可。**判据是这项工作会不会变成大家共用的范式**:会,就是奠基算法,不收(PPO、DPO 这类全新算法,谁都会采用);只有提出方自己在用、没有成为通用范式的具体做法才收(如 mHC、Engram 只有 DeepSeek 一家用)。知识库要讲某个奠基算法,不构成把它收进报告库的理由
- 大厂之外,关注度高且可信的新兴实验室同样在范围内
- **网页形式的公开报告按内容判断,不按载体判断**:只要给出了可检验的做法与证据(完整训练/实验设置、可复现的评测口径、明确的失败记录),就与论文同等收录。只有观点、路线图或产品公告不收。判据是**别人能不能照着它复现或迁移**,不是它有没有 arXiv 编号
- 全模态基座都收:语言、视觉理解、图像生成、视频生成、音频、3D 与世界模型
- 已收录的原件不因后续规则变化而移除。下游已收录、且能直接支撑知识库的源头可破例排期(如 MiniMax-01 之于 lightning attention)

## 一、目录与网页

```text
papers/<公司>/<报告>.pdf      # 原件,默认不被 git 追踪
reports/<公司>/<报告>.md     # 解读,必须被 git 追踪
```

- 同一家公司在两边使用完全相同的目录名;报告文件使用稳定、可读的模型或报告名,如 `DeepSeek-V4.pdf` 与 `DeepSeek-V4.md`
- 公司目录按**模型或项目的主要归属方**确定。高校与多家公司联合署名时,不额外创建“联合”“高校”或重复公司目录;合作关系在解读正文中说明。若归属确实无法判断,先核对论文首页、官方发布页和项目仓库,不要凭作者邮箱猜
- **同一系列优先放进同一个目录,此时可以打破公司归属**(如 FlashAttention 1/2/3/4 虽然后续代际换了署名机构,仍放在一起),便于对照阅读;归属变化写在解读正文里
- 文件名只保留稳定的模型或项目名。模型正式名称自带的代际或版本号(如 `DeepSeek-V3.2`、`Hunyuan3D-2.0`)必须保留;不要再把日期、arXiv 修订号、完整论文副标题或冗余版本后缀塞进路径,这些信息写在解读正文里
- PDF 是事实原件,是否随 git 保存由维护者逐篇决定。`.gitignore` 默认忽略 PDF;确需保存时使用 `git add -f papers/<公司>/<报告>.pdf`
- **原件是网页时**(官方博客、公开 recipe 页):`papers/` 下没有对应文件,解读照常放 `reports/<公司>/<报告>.md`,同一套契约。文中不用 `(PDF p. N)`,改为标注原文小节名(如「原文 Step 2 第 3 条」);开头的「本文依据」必须写明 URL 与访问日期。这类条目不会出现在下面按 PDF 列未解读原件的命令里,状态以第七节的表为准
- **需要保留原件图表时**,图片下载到 `public/reports/<slug>/`,正文用 `![图注](/reports/<slug>/文件名.png)` 这样的站内绝对路径引用,图注注明引自原文哪张图。实测该路径不与 `/reports/[company]/[report]` 路由冲突(静态文件优先),且 Tailwind preflight 会把图约束在容器宽度内、窄屏不溢出。**加完图必须 `leet-restart`**,否则常驻服务上只有图裂开(原因见 [08-常驻服务](08-常驻服务.md))。**能改写成 markdown 表格或 Mermaid 的一律改写**:原件里以图片形式呈现的表格必须转成原生表格,否则数字无法搜索、窄屏也读不了
- Markdown 是网页数据源。一级标题 `# ...` 是索引页显示的标题;以下正文正常使用 `##`、`###`
- 每篇已发布报告必须把唯一的 `<!-- release-date: YYYY-MM-DD -->` 放在一级标题后的第一个非空行。日期必须是真实存在的公历日期;缺失、重复、格式错误或日期非法都必须让测试与构建带文件名失败。该注释是文章内唯一的排序元数据,不计入正文
- `release-date` 记录**这篇文章所讲的确切模型或版本首次通过任一官方渠道向公众开放使用的日期**,包括官方 Web、App、API 或权重中最早发生的事件。一篇覆盖模型家族的文章取该确切家族的首发日;一篇覆盖后续具名 checkpoint 的文章取该 checkpoint 自己的首发日。若对象从未对外可用、文章只讲公开技术,才改用该技术首次官方公开日
- 首发日是不变事件。后续 API 上线、权重开放、论文上传或修订、PDF 换版、本站改稿和 git 提交都不得回写该日期
- **Hugging Face 仓库的 `createdAt` 不是首发日**,权重仓库通常提前数日至数周建好、发布当天才解禁(实测 Gemma 3 早 11 天、Gemma 4 早 3 周、Llama 3.1 早 7 天)。要用权重佐证就看**文件提交时间**,不看仓库创建时间
- 官方发布日志与官方博客不一致时,按「最早的官方公开事件」取日志(实测 Gemma 3 与 Gemma 4 都是日志早两天),不取传播最广的那次官宣
- `/reports` 保持按公司分组;每家公司内按 `release-date` 降序排列,网格阅读顺序是从左到右、再从上到下的新到旧。同日时按文件名去掉 `.md` 后的 slug 字面值升序排列
- `reports/` 中以下划线或点开头的公司/文件不会出现在网页,可用于未完成草稿;正式发布时再改成普通文件名
- 主页「📄 报告解读」进入 `/reports`;索引按公司分组,每张卡片进入一篇完整长文

**一份报告只对应一篇解读。** 不要另建“算法篇”“训练篇”“infra 篇”,也不建立重复的元数据、代际表或关键词数据库。算法、架构、训练 recipe、infra 和关键词都在同一篇文章里形成一条完整叙事。

原件库存与解读状态见第七节;先做哪一批只写在 `01-TASK.md`。表与磁盘不一致时以这条命令为准:

```bash
for f in papers/*/*.pdf; do p="${f#papers/}"; [ -f "reports/${p%.pdf}.md" ] || echo "${p%.pdf}"; done
```

## 二、开始写之前

1. 确认拿到的是目标报告的完整 PDF,记录封面上的正式标题、版本或发布日期
2. 去模型的官方发布页、官方仓库或官方新闻核对上述实际首发日,写入 `release-date`;论文页只能在没有更直接官方记时作为备选证据。已有正式报告在新规则上线前必须一次性全部回填,不允许部分文章无日期继续发布
3. **动笔前必须查版本**:去官方论文页、官方仓库或发布页检查是否有更新修订。若官方版比本地 PDF 新,先用官方原件替换稳定路径下的旧文件,再重新核对标题、版本、日期、页数和文件完整性;旧版报告地图与页码不得沿用。若因研究需要刻意保留旧版,必须在文章开头明说依据版本及原因
4. 同时做文本提取与逐页视觉检查。文本提取用于搜索,页面渲染用于核对公式、表格、图注、上下标和版式;不能只信 OCR 或抽取文本
5. 先画“报告地图”:按原报告章节列出全部技术主张、关键数字、图表和实验结论,给每项记下 PDF 页码
6. 标出三个层次:**报告明确写了什么**、**我们如何解释它**、**哪些是外部资料补充**。三者不能混成作者原话
7. 遇到论文身份、外部项目或版本现状不确定时,查官方论文页、项目仓库或官方文档;没有证据就保留不确定性,不猜
8. **原件是网页时,必须跟着正文里的链接读一遍**,见下方专条

只有完成报告地图后才开始写正文。这样可以避免文章只追着摘要写,漏掉附录、训练细节或 infra 约束。

### 原件是网页时,这几步换个做法

| 步骤 | PDF 原件 | 网页原件 |
|---|---|---|
| 1 完整性 | 确认 PDF 完整、记页数 | 确认正文抓全(整页文本 + 逐张图),记下页面标注的发布日与你的访问日期 |
| 3 版本 | 查 arXiv 是否有更新修订 | 网页会**原地改动且不留版本号**。记录访问日期即为版本;若正文提到"完整技术报告待发布",必须在开头写明本文依据的是当前博客版 |
| 4 双读 | 文本提取 + 逐页渲染 | 整页文本 + **逐张读图**。网页常把表格做成图片,纯文本抓取会静默丢掉整张表的数字 |
| 5 报告地图 | 每项记 PDF 页码 | 每项记**原文小节名** |

**第 8 条:链接跟进(网页原件的核心动作)**

网页原件的背景是**摊在链接里**的,不跟进就只能抄结论。动笔前把正文里的链接分成三类,按类处理:

- **伴随篇/前作**:同一作者定义框架、方法或术语的另一篇。**优先级最高**——正文的核心主张往往靠它才成立(判据、分级、评分口径都可能在那边)。必须读完并把定义讲清楚
- **评测与数据集**:每个 benchmark 至少要让读者知道"它测什么、为什么选它",不能只出现一个名字
- **方法与引用来源**:逐个打开核实真实标题,不照抄编号(踩过的雷见 [09-日常维护](09-日常维护.md))

链接取来的一切都是**外部补充**,必须与原文结论清楚分开,不得冒充原文内容。跟进后仍拿不到的,如实写"链接指向的材料尚未公开"。

## 三、长文写作契约

目标不是把 PDF 翻译一遍,而是让读者读完后能够回答三个问题:

1. 它到底做了什么,整个系统如何连起来?
2. 为什么要这样设计,它解决了旧方案的哪个具体矛盾?
3. 哪些思想可以迁移到自己的模型训练、推理或基础设施项目?

写作必须满足:

- **极其简单直白**:短句优先;术语首次出现先说人话,再给正式定义;能用一个小例子讲清就不要先堆符号
- **先全景、后细节、再回到全景**:开头给读者一张模型与训练全貌图;每个设计讲完后说明它接在系统哪里、影响谁
- **完整覆盖但不机械复述**:算法、模型架构、数据、训练 recipe、推理、并行与通信、算子/系统优化、评测和已知限制,报告写到什么就覆盖什么;报告没写的明确说没写
- **每个重点都讲原因**:按“旧问题 → 新设计 → 工作机制 → 收益 → 代价/适用边界”展开,不能只列名词和结论
- **保留可迁移启发**:每个核心设计末尾回答“对自己的项目有什么用”;区分可直接复用的技巧与依赖特定规模/硬件的做法
- **图表服务于理解**:优先自己重画简洁 Mermaid 流程图;直接引用报告图表时注明 PDF 页码,**网页原件注明引自原文哪张图**,不把装饰图当内容。引用前必须真的打开图看过,不靠文件名或图注猜内容
- **数字可追溯**:参数量、token 数、训练成本、吞吐、精度变化等数字紧跟 `(PDF p. N)`;**网页原件没有页码,改标原文小节名**(如「原文 2.4 节」)。不要凭印象补数字;只在图里出现的数字,注明读自哪张图
- **外部补充可辨认**:外部资料只用于补背景或交叉核验,给出链接并明确标成补充,不能冒充报告内容
- **中文标点用全角**(`,` `:` `;` `()` `「」`),与已发布各篇一致;代码块、公式与链接内部照原样不动。子 agent 默认会写半角,提示词里要写死这一条
- **关键词在文中解释**:默认读者第一次接触这些概念。术语首次出现时先说人话,再给中文名、英文全称和缩写;开头几次不要只丢缩写。若开篇术语密集,先放一小段必要的读前背景,但不要让词汇表抢走正文篇幅。文末可用一小节串联关键词;不另建只列名词、不讲关系的索引实体

文章通常会自然包含:一句话结论、阅读路线、全景架构、逐项核心设计、数据与训练 recipe、infra/推理、实验怎么证明、限制与未公开信息、可迁移启发、关键词回看和参考资料。**这只是覆盖清单,不是已冻结模板**;章节顺序应服从该报告自己的叙事。技术论文没有模型全貌和训练 recipe,那几项自然换成这项技术要解决的问题、以及它怎么支撑基模训练或推理;原件没写的照旧不补。

### 标杆文风的六条硬约束

1. **先讲矛盾,再上名词**:先让读者知道旧方法卡在哪,再引入新设计;不从摘要复读或缩写清单开场
2. **一段只推进一个意思**:短句、短段落优先,用“因为”把结论和原因接起来;类比要帮助建模,但不能当作论文证据
3. **复杂设计都走完一条因果链**:旧问题 → 新设计 → 工作机制 → 收益 → 代价/边界 → 可迁移启发。不要只讲“它是什么”
4. **公式也要像正文一样可读**:行内公式只用 `$...$`,独立公式用 `$$...$$`;当前渲染链不支持 `\(...\)`,禁止使用。公式前先说它要算什么,公式后解释符号和操作;上下标太多时,先定义中间量或拆成两步,不为了照抄原式牺牲阅读
5. **图要说清真实性边界**:自己重画的图必须注明根据哪个 PDF 图/页面,并区分“机制示意”与“实测时间/数据”。Mermaid 的节点、时间轴和箭头都要人工核对,能渲染不等于含义正确
6. **读完必须留下判断,不只留下摘要**:明确哪些结论被实验支持,哪些只是作者观察,哪些实现细节没有公开;最后把可迁移的设计原则串回整个系统

## 四、从原件到发布

1. **投递**:PDF 放进 `papers/<公司>/`,确认公司和报告名。**网页原件**只需确认 URL、公司和报告名,`papers/` 下不留文件
2. **版本核验**:按第二节搜索官方最新版;发现更新先替换原件并重新确认完整性,再进入后续流程。**网页原件**改为记录访问日期,并确认是否有"完整报告待发布"之类的声明
3. **通读**:提取文本、渲染页面,完成报告地图和页码证据。**网页原件**做整页文本 + 逐张读图,并按第二节第 8 条完成链接跟进,证据落到小节名
4. **组织**:找到贯穿全文的主要矛盾,决定文章叙事,列出必须讲清的核心设计
5. **撰写**:默认在 `reports/<公司>/_<报告>.md` 写未发布稿;若需要直接检验真实网页渲染,也可使用正式文件名公开审阅。一边写一边回查 PDF,不靠二手摘要
6. **自审**:逐项检查覆盖、事实层次、数字页码、图表含义、限制和可迁移启发
7. **验收**:让用户阅读全文并指出难懂、缺失或不够有启发的地方;按内容问题重写,不做表面润色
8. **发布**:隐藏审阅的稿件在验收通过后去掉文件名前的 `_`;公开审阅的稿件则保持正式文件名。两种方式都要运行验证并 commit

## 五、已验收标杆与子 agent 协作

第一篇已验收标杆固定为:

```text
papers/DeepSeek/DeepSeek-V4.pdf
reports/DeepSeek/DeepSeek-V4.md    # 在真实网页中公开验收
```

DeepSeek-V4 于 2026-09-05 获得用户明确验收,是后续报告的**语言、解释深度、因果链和启发性**标杆。后续文章要学它“如何让陌生技术变得可理解”,不得机械复制它的标题、篇幅、类比或章节顺序。

可以让多个子 agent 并行撰写,但协作边界必须清楚:

- 一个子 agent 只拥有一份原件(一份 PDF 或一个 URL)和对应的一篇 Markdown;禁止多个 agent 同时改同一篇报告
- 任务开始前必须完整阅读本流程和 DeepSeek-V4 标杆,再完成自己报告的章节地图与页码证据
- 任务中必须给出精确的 `papers/<公司>/<报告>.pdf` 和 `reports/<公司>/<报告>.md`,不让 agent 自行发明目录、拆文章或新建元数据实体
