# 开源贡献

定位:把一个方向做成上游合入的 PR。**本手册是这条线唯一的权威手册**:维护者在本仓库开会话、说想给哪个项目做什么,agent 按本手册走完全程。代码不在本仓库,在私有实验仓 `~/1Project/oss/<项目>`;本仓库只放台账、队列与提炼后的经验。

和其他库的关系:

- **06 的解读是理解底座**:全局地图(组件在哪、痛点是什么)先从它读,再对要动的模块做增量阅读——解读基准之后上游改了什么
- **13 的「我的待办」只是参考**,和 Roadmap、issue、读解读时的发现、维护者自己的想法并列
- `projects/` 仍然只镜像官方;实验仓是另一份完整克隆

## 一、布局

```text
contrib/<项目>.md                            台账(本仓库,公开)
~/1Project/oss/                              实验层,私有仓 oss-kit:_kit/ 脚本与模板、.github/ 两个评审
~/1Project/oss/<项目>/                        实验仓;各项目差异写在它的 .lab/project.md(项目画像)
~/1Project/.worktrees/oss/<项目>/<任务>/       一个任务一个 worktree
```

- 实验仓三个 remote:`upstream` 只 fetch;`origin` 是私有仓 `<我>/<项目>-lab`;`fork` 是公开 fork,pre-push 钩子拒绝没带 `OSS_PUBLISH=1` 的推送
- `gh` 在实验仓里默认指向私有仓;对上游的一切操作写明 `-R <上游>`
- **任务名**:小写 kebab,`<上游 issue 号>-<短名>`(没有 issue 就只用短名);分支、`.lab/tasks/`、worktree、台账那一行用同一个名字
- `<项目>` 取上游 GitHub 仓库名,与 `meetings/`、`opensource/` 一致

## 二、台账

`contrib/<项目>.md`,第一次用时从 `contrib/_template.md` 建。一张表,状态只往前走,在发生的那次会话回写:

| 状态 | 什么时候写 |
|---|---|
| 候选 | 答得上三问:上游要不要(Roadmap 或上游 maintainer 表态)、有没有人在做、我们能不能验证 |
| 进行中 | 维护者选定方向、开 worktree 时 |
| 待发布 | 固定尾段走完、发布命令已交出 |
| 已提交 | 维护者开了上游 PR,填 PR 链接 |
| 已合入 / 已关闭 | 写一句结论,行不删;01-TASK 那一行删掉 |

**仓库是公开的**:台账只写选题、上游 issue、状态、PR 链接、结论;私有仓地址、迭代过程、失败的尝试不写。当前推进的那一条同时挂在 01-TASK 的「开源贡献」一节。

## 三、一次贡献怎么走

**1. 进场**。读台账、该项目的解读(`00-总览.md`、`99-代码索引.md`、`_登记表.md`)、项目画像、上游 Roadmap 与相关 issue,再对要动的模块做增量阅读;给出分析与候选,候选进台账。

**2. 讨论与实验**。方向是在讨论、争辩和小实验里收敛的,不是「发现问题 → 写计划 → 解决」一条直线:

- agent 给证据和反方意见,不附和;拿不准的先跑小实验再说
- 维护者选定方向时开 worktree,台账改「进行中」;实验与原型就在 feat 分支上做,记录进 `.lab/tasks/<任务>/`
- 任务书 `.lab/tasks/<任务>.md`(模板 `_kit/templates/task.md`)写当前共识——目标、做到什么算完、证据怎么拿、边界、已知的未知——随讨论更新,不是一次定稿的计划
- 不需要等上游同意;要不要先在 issue 下打招呼由维护者决定,留言照对外展示面的规矩

**3. 实施与迭代**。写码、跑上游自己的确定性检查(pre-commit 等)与测试、按需做 GPU 验证,和第 2 步交替进行,直到维护者说「交付」。

**4. 固定尾段**。维护者说「交付」后按序做完,不省略、不换顺序:

1. 画像里的确定性检查与测试全绿;证据写进任务书「证据」一节(命令、环境、commit、run ID、结果;没跑的写没跑)
2. PR 草稿 `.lab/tasks/<任务>/pr.md`:第一行是标题(按上游惯例),其余按上游 PR 模板,写给人读
3. `~/1Project/oss/_kit/deliver.sh <任务>`:从上游默认分支建 `contrib/<任务>`,只放净改动,排除 `.lab/`、`.hlab/`,查泄漏,生成一个提交,推 `origin`
4. 私有 PR 上打 `review:pr`;逐条按证据处理,改了正文或代码就推 feat、重新交付后再打
5. 台账改「待发布」;把脚本打印的推送与开 PR 命令交给维护者

**5. 发布、跟进与收尾**。维护者推送、开 PR、回复上游。上游要的小改在 contrib worktree 上提交并 cherry-pick 回 feat;改动大就回 feat 迭代,删掉私有的 contrib 分支与 worktree 后重跑 `deliver.sh`。合入或关闭后台账写结论,一句经验落到该落的地方;worktree 与分支按 HOME-5090 的清理规则先盘点再删。

**只在这些地方停下等维护者**:选定方向;说「交付」;要打 `review:code`;租卡;一切对外展示面——上游的 issue、评论、PR、回复与公开 fork 的推送,agent 只准备草稿与命令。其余私有一侧的事一路做,不逐步请示。

## 四、分支

- `lab`:私有默认分支 = 上游默认分支 + 实验层的接线提交。在 `~/1Project/oss/<项目>` 主 checkout 上 `git merge upstream/<默认分支>` 再 `git push origin lab`;**从不 rebase**——交付靠 `lab` 与 feat 的合并基把接线排除在外
- `feat/<任务>`:从 `lab` 开,只 merge 不 rebase;第一次推送时开私有 PR `gh pr create --base lab --head feat/<任务>`,两个评审都挂在它上面,它不合入
- `contrib/<任务>`:只由 `deliver.sh` 生成,只有一个干净提交

## 五、算力

- **本地 5090 优先**,走 hlab(`~/1Project/HOME-5090.md`),项目 id `oss-<项目>`:`hlab sync --repo ~/1Project/oss/<项目> --ref <worktree 的 HEAD>`。迭代用工作台:依赖装进命名环境,被测代码用 `PYTHONPATH` 指向只读的 workspace;写进 PR 的结果用正式 plan/submit 跑,job 文件放 `.hlab/jobs/`
- **需要 H100、H200、B200 这类卡**(端到端 serving 数据、5090 跑不了的特性)时租卡,Modal 等。租之前交一份使用计划——跑哪些实验、什么卡几张、预计时长与费用——维护者批准后执行
- **能并行就并行**:按实例秒计费,并行与串行总成本相同,墙钟短得多;跑完即释放

## 六、两个评审

在私有 PR 上打标签触发,GitHub Actions 里的 Opus 以全新上下文只读全仓;要重跑就摘掉标签再打。评审只给意见,不改代码、不合并;采纳的改,不采纳的在任务书写一句理由,不为讨好评审加抽象。

| 评审 | 标签 | 谁触发 | 看什么 | 结果 |
|---|---|---|---|---|
| 技术评审 | `review:code` | **只在维护者明确要求时** | 正确性;项目风格规范;有没有更简的写法;抽象是否与原项目一致;有没有防不存在情况的防御代码 | 行内评论 `gh api repos/<我>/<项目>-lab/pulls/<编号>/comments` + 一条总评 |
| PR 前内容评审 | `review:pr` | 固定尾段第 4 步 | 正文写给人读而非写给 agent:短、直白、一眼能扫;表格与图是否好读;改动范围与影响面是否和正文一致、有没有夹带;是否按上游模板如实给了证据 | 一条总评 |

总评用 `gh pr view <编号> --comments` 取回。

## 七、接入新项目

`~/1Project/oss/_kit/new-project.sh <owner>/<repo>`:完整克隆(hlab 不收部分克隆)、建私有仓、铺 `lab` 分支与接线、关掉上游 workflow、建评审标签、装 fork 推送钩子、设 `gh` 默认仓库。之后:

- 补全项目画像 `.lab/project.md`,只写这个项目和别的项目不一样的地方:风格规范在哪、检查与测试命令、硬件需求、PR 标题与模板惯例、上游 CI 门槛。没有成文风格规范的项目,规范就是周围的代码
- 维护者在私有仓设置评审令牌 `CLAUDE_CODE_OAUTH_TOKEN`(`claude setup-token` 生成,每个私有仓各设一次);没有公开 fork 就建一个再 `git remote add fork`
- 要用 5090 就在 hlab 注册 `oss-<项目>`,属运维线,按 homelab-control 的守则
- 画像顶部的接入状态都就绪后,才进入第三节第 2 步

## 八、验证与收尾

台账改动跑 `npm test`(含台账的状态枚举检查)。收尾照 `AGENTS.md` 的口令;经验按「经验沉淀到哪里」分层——某个项目的特例进该项目的画像,跨项目的做法进本手册或 `paradigms/`。
