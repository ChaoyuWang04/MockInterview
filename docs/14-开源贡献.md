# 开源贡献

定位:把一个选题做成上游合入的 PR。**代码不在本仓库**:每个项目一个私有实验仓 `~/1Project/oss/<项目>`,怎么开工、迭代、评审、交付由那一层的 `~/1Project/oss/AGENTS.md` 管。本仓库只做控制面——选题、台账、队列、提炼后的经验。

和其他库的关系:

- **06 的解读是理解底座**:选题时按它的全局地图找痛点、界定 PR 覆盖什么;开工前的读法见实验层守则
- **13 的「我的待办」只是参考**,和 Roadmap、issue、读解读时的发现、维护者自己的想法并列,不自动变成候选
- `projects/` 仍然只镜像官方;实验仓是另一份完整克隆

## 一、台账

`contrib/<项目>.md`,`<项目>` 取上游 GitHub 仓库名,与 `meetings/`、`opensource/` 一致;第一次用时从 `contrib/_template.md` 建。一张表,状态只往前走:

| 状态 | 进入条件 |
|---|---|
| 候选 | 答得上三问:上游要不要(Roadmap 条目或上游 maintainer 表态)、有没有人在做、我们能不能验证(硬件与测试) |
| 已认领 | 维护者发出认领留言,上游 maintainer 同意 |
| 进行中 → 待发布 → 已提交 | 实验仓里开工、交付就绪、维护者开了上游 PR;由实验层在发生的那次会话回写 |
| 已合入 / 已关闭 | 写一句结论,行不删——台账是这个项目贡献的全貌,不是队列 |

**仓库是公开的**:台账只写选题、上游 issue、状态、PR 链接、结论。私有实验仓的地址、迭代过程、失败的尝试不写;认领留言的草稿只在对话里给,不落库。当前推进的那一条同时挂在 01-TASK 的「开源贡献」一节。

## 二、一次贡献怎么走

| 步 | 做什么 | 谁 |
|---|---|---|
| 1 选题 | 读 Roadmap、issue 与解读,出候选进台账,推荐一条 | agent;维护者在意图卡上选定 |
| 2 认领 | agent 起草 issue 留言 | **维护者**改措辞后发出 |
| 3 开工 | 实验仓开 worktree,写一页任务书 | agent;**维护者看过任务书才往下走** |
| 4 迭代与验证 | 写码、确定性检查、GPU 验证、技术评审 | agent |
| 5 交付就绪 | 组装干净分支与 PR 草稿,过内容评审 | agent |
| 6 发布 | 推送公开 fork、开上游 PR、以后的每条回复 | **维护者** |
| 7 跟进与收尾 | 按上游意见修改;合入或关闭后回写台账,一句经验落到该落的地方 | agent 起草,维护者发布 |

- 选题可以随时做;第 3 步起要求该项目的实验仓接入就绪(评审令牌、hlab 注册)
- 一条选题从第 3 步到第 7 步算一个任务,只在表里加粗的人工门停
- **对外展示面一律由维护者本人发布**。agent 准备好草稿与命令为止;私有一侧 agent 一路做,不逐步请示
- **任务书代替逐步计划**:一页,写给维护者看——目标与上游 issue、做到什么算完、证据怎么拿、边界、已知的未知。执行步骤由 agent 自己规划

## 三、两个评审

触发与读取见实验层守则;这里只说各自看什么:

| 评审 | 看什么 |
|---|---|
| 技术评审 | 正确性;项目风格规范;有没有更简的写法;抽象是否与原项目一致;有没有防不存在情况的防御代码 |
| PR 前内容评审 | PR 正文写给人读而非写给 agent:短、直白、一眼能扫;表格与图是否好读;改动范围与影响面是否和正文一致、有没有夹带;是否按上游模板如实给了证据 |

评审只给意见,不改代码、不合并;采纳与否由写码的 agent 按证据判断。

## 四、新项目

接入步骤见实验层守则的「接入新项目」。项目画像 `.lab/project.md` 只写这个项目和别的项目不一样的地方;没有成文风格规范的项目,规范就是周围的代码。

## 五、验证与收尾

台账改动跑 `npm test`(含台账的状态枚举检查)。收尾照 `AGENTS.md` 的口令;经验按「经验沉淀到哪里」分层——某个项目的特例进该项目的画像,跨项目的做法进本手册、实验层守则或 `paradigms/`。
