# 开源贡献

定位:把一个选题做成上游合入的 PR。**代码不在本仓库**:每个项目一个私有实验仓 `~/1Project/oss/<项目>`,执行细节由那一层的 `~/1Project/oss/AGENTS.md` 管。本仓库只做控制面——选题、台账、队列、提炼后的经验。

和其他库的关系:

- **06 的解读是理解底座**。解读把全局地图(组件在哪、痛点是什么)和维护者已读过的简洁版放在一起,agent 读它就和维护者站在同一张图上,PR 的覆盖范围也按这张图界定。开工前读该项目的总览、`99-代码索引.md`、`_登记表.md`,再只对要改的模块做增量阅读:解读基准之后上游改了什么
- **13 的「我的待办」只是参考**,和 Roadmap、issue、读解读时的发现、维护者自己的想法并列,不自动变成候选
- `projects/` 仍然只镜像官方;实验仓是另一份完整克隆,互不相干

## 一、目录

```text
contrib/<项目>.md          # 台账,<项目> 取上游 GitHub 仓库名,与 meetings/、opensource/ 一致
contrib/_template.md       # 台账模板
~/1Project/oss/<项目>/     # 私有实验仓(本仓库之外):任务书、实验记录、评审都在这里
```

**仓库是公开的**:台账只写能公开的东西——选题、上游 issue、状态、PR 链接、一句话结论。私有实验仓的地址、迭代过程、失败的尝试不写。

## 二、台账

一个项目一个文件,一张表,状态只往前走:

`候选 → 已认领 → 进行中 → 待发布 → 已提交 → 已合入 / 已关闭`

- **候选**:写清上游要不要(Roadmap 条目或维护者表态)、有没有人在做、我们能不能验证(硬件与测试)。三条有一条答不上就还不是候选
- 每一行在状态变化的那次会话里回写,不攒着;已合入、已关闭的留一行结论,不删——台账是这个项目贡献的全貌,不是队列
- 当前在推进的那一条同时挂在 01-TASK 的「开源贡献」一节,做完按 01-TASK 的规矩删

## 三、一次贡献怎么走

| 步 | 做什么 | 谁 |
|---|---|---|
| 1 选题 | 读 Roadmap、issue 与解读,出候选进台账 | agent,意图卡确认一次 |
| 2 认领 | agent 起草 issue 留言;维护者本人改措辞后发出 | **维护者** |
| 3 开工 | 实验仓开 worktree,写一页任务书;维护者看过即开工 | agent |
| 4 迭代与验证 | 写码、确定性检查、GPU 验证、技术评审,反复直到交付就绪 | agent |
| 5 交付就绪 | 组装干净分支与 PR 草稿,过 PR 前内容评审 | agent |
| 6 发布 | 推送公开 fork、开上游 PR、以后的每条回复 | **维护者** |
| 7 跟进与收尾 | 按上游意见修改;合入或关闭后回写台账,一句经验落到该落的地方 | agent 起草,维护者发布 |

**对外展示面一律由维护者本人发布**:上游的 issue、评论、PR、回复,以及公开 fork 的推送。agent 准备好草稿与命令为止;措辞是维护者的。私有一侧(实验仓、私有 PR、两个评审)agent 一路做,不逐步请示。

**任务书代替逐步计划**:一页,写给维护者看——目标与对应的上游 issue、做到什么算完、证据怎么拿、边界(不碰什么)、已知的未知、上游对齐状态。执行步骤由 agent 自己规划,只有要跨会话交接时才补写。

## 四、两个评审

都在私有 PR 上按标签触发,模型与认证在 kit 里统一配置,项目差异只写在实验仓的项目画像里:

| 评审 | 标签 | 看什么 |
|---|---|---|
| 技术评审 | `review:code` | 正确性;项目风格规范;有没有更简的写法;抽象是否与原项目一致;有没有防不存在情况的防御代码 |
| PR 前内容评审 | `review:pr` | PR 正文写给人读而非写给 agent:短、直白、结构一眼能扫;表格与图是否好读;实际改动范围与影响面是否和正文一致、是否夹带无关改动;是否按上游 PR 模板如实填了证据 |

技术评审在迭代中按需打标签,不是每次推送都跑;内容评审在第 5 步跑一次,正文改过再跑。评审只给意见,不改代码、不合并;意见是否采纳由写码的 agent 按证据判断。

## 五、接入一个新项目

按 `~/1Project/oss/AGENTS.md` 的「接入新项目」走:完整克隆、建私有仓、项目画像、在 hlab 注册(按 homelab-control 的守则)。需要维护者本人做的只有两件:在私有仓设置评审用的订阅令牌、建公开 fork。

项目画像只写这个项目和别的项目不一样的地方:风格规范在哪、检查与测试命令、硬件需求、PR 标题与模板惯例、上游 CI 门槛、怎么认领。没有成文风格规范的项目,规范就是周围的代码。

## 六、验证与收尾

台账与本手册改动跑 `npm test`。收尾照 `AGENTS.md` 的口令;经验按「经验沉淀到哪里」分层——某个项目的特例进该项目的画像,跨项目的做法进本手册或 `paradigms/`。
