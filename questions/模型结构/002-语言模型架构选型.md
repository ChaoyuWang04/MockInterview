## 题目

请比较 Encoder-only、Decoder-only、Encoder-Decoder 和 Prefix LM 的可见范围、训练目标、生成方式与适用任务。为什么 Decoder-only 常用于通用大模型，实际项目应怎样选？

## 要点

- 四种架构的注意力可见性和训练目标
- 理解、条件生成与开放式生成的选型依据
- Decoder-only 便于统一预训练和扩展的原因
- 避免“某种架构绝对更优”及闭源模型结构猜测

## 答案

**选型先看输出是否需要生成、输入是否应被双向编码，以及是否要把输入和输出分开计算。**

| 架构 | 可见范围与目标 | 更自然的任务 |
|---|---|---|
| Encoder-only | 输入内双向可见，常用掩码语言建模 | 分类、检索、抽取、向量表示 |
| Decoder-only | 每个位置只看左侧，预测下一 token | 对话、续写、代码生成、通用生成 |
| Encoder-Decoder | Encoder 双向读输入，Decoder 因果生成并跨注意力读取输入 | 翻译、摘要、结构化条件生成 |
| Prefix LM | 前缀内部双向可见，输出段因果可见 | 在单栈中同时利用输入理解与生成 |

Decoder-only 常见，是因为一套同构网络和 next-token 目标就能利用大规模无标注序列，提示、示例和答案也可统一成 token 流；推理时还能缓存历史 K/V。它的流行是工程与数据路线的选择，并不证明所有任务上都优于 Encoder-Decoder。

### 常见追问简答

- **理解和生成都要怎么办？** 可用 Encoder-Decoder，或用 Decoder-only 加任务提示与分类头，按延迟和效果验证。
- **为什么原生 BERT 不直接做左到右生成？** 双向 MLM 会看到两侧信息，目标与自回归生成不一致；改变 mask、增加 Decoder 或用其权重初始化生成模型后可以参与生成。
- **Prefix LM 与 Decoder-only 差在哪？** Prefix LM 允许输入前缀内部双向交互；纯因果模型的前缀位置仍只看左侧。
- **Decoder-only 训练推理一致吗？** 训练使用真实前缀的 teacher forcing，推理使用模型自己生成的前缀，仍有分布差异。

## 知识点

架构选型的核心变量是可见性、训练目标、输入输出是否分离、延迟和任务监督，不依据“当前是否流行”直接下结论。
