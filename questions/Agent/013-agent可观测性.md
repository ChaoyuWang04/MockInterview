## 题目

实际部署中，Agent 哪些模块最容易出现稳定性或性能问题？请结合常见故障，设计监控体系，并说明定位和诊断问题的关键方法。

## 要点

- 覆盖规划循环、上下文膨胀、检索退化和工具失败
- 指标分基础设施、运行时和业务效果三层
- 统一 trace 串联模型、检索、工具与多个 Agent
- 日志可复现决策，又不能记录私有思维链或敏感数据
- 有熔断、自愈、告警验证和故障注入

## 答案

**Agent 最常坏在边界处：计划无法终止、上下文被截断、检索给错证据、工具超时或返回格式变化。** 监控要把一次任务从用户结果追到每个模型、检索和工具节点，而不是只看 GPU 是否正常。

基础设施层看资源、队列、吞吐和分位延迟；运行时层看步骤数、重复动作率、token、上下文裁剪、检索命中、工具成功率与重试；业务层看任务成功率、事实错误、用户放弃和人工接管。阈值来自 SLO 与历史基线，不能把“10 轮”“5%”当通用标准。

每个任务生成 trace ID，每个 Agent、模型调用、检索和工具执行生成 span，记录输入输出 schema、模型/提示版本、策略结论、工具摘要和耗时。不要保存私有思维链；原始上下文、参数和返回值先脱敏，并设置访问权限和保留期。

循环检测可组合最大步数、deadline、连续相同动作和进展检查；触发后先中止副作用，压缩状态并换策略，仍失败则安全降级或转人工。多 Agent 场景继续传播同一 trace，并记录消息版本、状态所有者和责任节点。用合成故障、回放和告警演练检查监控盲区，同时监控采集链路自身是否丢 span 或延迟。
