## 题目

一个 Agent 系统里的主模型、Memory 模型和多模态模型分别承担什么职责?各自的选型标准和验证方式有什么不同?

## 要点

- 三者在调用频率、延迟敏感度和错误代价上差一个量级,不能用同一套标准
- 主模型选的是规划与工具调用的可靠性,不是通用榜单分数
- Memory 侧真正的瓶颈通常是检索质量,不是生成质量
- 多模态模型按"提取什么信息"选,输出要能进入文本推理链
- 每类都要有自己的离线评测集,不能只看端到端效果
- 混用不同厂商时,tokenizer、上下文窗口和格式稳定性是隐性成本

## 答案

**三类模型在调用频率、延迟敏感度和错误代价上差一个量级,所以选型标准完全不同。**

| 模型 | 职责 | 首要指标 | 典型形态 |
|---|---|---|---|
| 主模型 | 规划、工具调用、最终作答 | 工具调用格式正确率、多步任务完成率 | 最强的那一档,调用最少 |
| Memory | 记忆写入抽取、检索、摘要 | 检索召回与精度、摘要不丢关键事实 | Embedding + 小生成模型 |
| 多模态 | 图像/音视频转成可推理的结构化信息 | 目标信息的抽取准确率 | 专用模型或 VLM |

**主模型**不要按通用榜单分数选。真正决定成败的是:工具调用的格式稳定性(JSON schema 是否总是合法)、长上下文里对指令的遵循、多步任务的完成率,以及失败时是否会硬编造。这些必须用自己的任务集测,榜单分数高但工具调用格式飘的模型,在 Agent 里是灾难。

**Memory 侧最常见的误判**是把它当成生成问题。绝大多数场景下瓶颈在**检索**——记忆写得再好,召不回来等于没有。所以选型重心在 Embedding 模型和索引策略上,生成模型只负责抽取与摘要,用小模型即可;真正要验证的是"给定一个查询,该记忆能不能被召回"。

**多模态模型**按"要从这张图里提取什么"选,而不是按通用理解能力。输出必须能进入文本推理链——结构化字段比自由描述更可用。这一环的错误会静默传播:图里读错一个数字,后面所有推理都错,所以要单独设检查点。

两条工程边界:每一类都要有**独立的离线评测集**,只看端到端指标无法定位是哪一环退化;混用不同厂商的模型时,tokenizer 差异、上下文窗口不一致和输出格式稳定性都是隐性成本,升级任一模型都要重跑各自的评测。

## 知识点

工具调用格式稳定性、多步完成率、检索召回优先于生成质量、结构化视觉输出、分层评测集、跨厂商混用成本。

记忆的分层与检索见 [分层记忆](003-多轮对话记忆.md) 与 [向量记忆检索](018-向量记忆检索.md);Embedding 选型见 [Embedding 模型选型](../RAG/002-embedding-模型选型.md)。
