## 题目

一次故障会产生海量告警报文,能不能全部输入给主管 Agent?如果不能,怎样聚类降噪,又怎样保证没有丢掉关键信息?

## 要点

- 不能全量入模,受限的不只是窗口长度,还有注意力稀释和成本
- 告警高度冗余:一个根因触发大量同质告警,信息量远小于条数
- 先用确定性方法压缩,模型只处理压缩后的代表
- 聚类维度按服务、指标、时间窗和拓扑,不做纯文本聚类
- 必须保留原始报文并可回查,压缩层要能被审计
- 关键信息不丢的验证靠回放历史故障,不靠人工感觉

## 答案

**不能全量输入,而且限制不只是上下文窗口。** 三个约束同时存在:窗口长度、长上下文里的注意力稀释(关键那条淹没在几千条同质告警里)、以及每次调用的成本与延迟。故障场景恰恰对延迟敏感。

关键观察是:**告警的信息量远小于它的条数**。一个根因会触发大量同质告警——同一服务的多个实例、同一调用链上的上下游、同一指标的连续采样点。所以降噪不是取样,而是去冗余。

**先用确定性方法压缩,模型只看压缩后的代表:**

1. **按维度分组**:服务/实例、指标类型、时间窗、调用链拓扑位置。用这些结构化维度聚类,而不是对告警文本做向量聚类——文本相似不代表同源,结构化字段才可靠。
2. **组内归约**:每组保留首发时间、条数、受影响实例数、极值样本和一条代表报文,其余折叠成计数。
3. **按拓扑收敛**:调用链上下游同时告警时,优先保留上游,下游标为疑似传导。
4. **排序**:按首发时间和异常幅度排序,把最可能是根因的放在上下文靠前位置。

模型拿到的是几十条带计数的聚合条目,而不是几千条原文。

**两条不能省的工程约束:**

- **原始报文必须保留且可回查**。压缩层给出的每个聚合条目要带指针,主管或子 Agent 判断需要细节时能取回原文,见 [子 Agent 分工与任务分发](027-子agent分工与任务分发.md)。
- **压缩层要能被审计**。它决定了模型能看到什么,一旦漏掉关键告警,后面再强的推理也救不回来。

"没丢关键信息"不能靠感觉判断,靠**历史故障回放**:拿已知根因的历史故障跑一遍压缩层,检查根因对应的告警是否仍在输出里、排在第几位。这个回归集应该随每次真实故障持续扩充。

## 知识点

上下文预算、注意力稀释、结构化聚类优于文本聚类、组内归约与计数折叠、调用链传导收敛、原始数据可回查、历史故障回放验证。

分层记忆与长对话压缩见 [分层记忆](003-多轮对话记忆.md);监控与追踪体系见 [Agent 可观测性](013-agent可观测性.md)。
