## 题目

请解释 Function Calling/Tool Use 的实现原理和完整流程，并说明提示、微调、代理框架在其中的作用，以及工具接口、调度、错误处理、扩展和安全如何工程化。

## 要点

- 模型只生成调用意图，宿主系统负责验证、授权和执行
- 讲清声明、选择、参数、执行、结果回填与继续决策
- 区分模型学习路径和代理框架的运行时编排职责
- 覆盖并发/DAG、超时重试、插件版本、副作用确认与提示注入

## 答案

**Function Calling 是模型与执行器之间的结构化协议：模型决定“想调用什么”，应用决定“能否以及如何执行”**。典型流程是：注册工具名称、用途和 JSON Schema；模型返回带调用 ID 的工具名与参数；服务端做解析、schema、业务规则、鉴权和配额检查；调度器执行；结果连同调用 ID 回填；模型基于结果继续调用或作答。

提示可以提供工具边界和示例，接入快但稳定性依赖模型；微调用覆盖真实分布的调用轨迹改善选择与参数生成，但工具变化会产生漂移；代理框架不是第三种学习方法，它负责注册、状态、重试、DAG、检查点和观测。无论哪条路径，服务端校验都不能省。

接口应版本化并区分只读与副作用工具。独立调用可并行，有依赖的调用按 DAG 执行；SSE/WebSocket 只负责进度传输。参数错误通常反馈修正，网络瞬断只对幂等请求有限退避重试，不可用时切换经过验证的备选或明确失败。插件还需服务发现、兼容性、最小权限、审计和指标。

工具描述、用户内容和工具输出都按不可信输入处理，分离数据与指令。退款、取消等动作必须展示影响并取得确认，使用幂等键和补偿记录；沙箱只能隔离执行，不能单独防止提示注入。
