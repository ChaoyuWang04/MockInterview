## 题目

设计一个制定个性化旅行行程的 Agent 系统。说明怎样分解任务、划分子 Agent、组织协作和信息流，并结合 RAG 增强对动态旅游信息的获取与使用。

## 要点

- 需求、候选规划、约束验证和执行确认职责清楚
- 共享状态有唯一所有者，支持版本和局部重算
- 静态知识可检索，天气、票价等动态事实优先查权威 API
- 检索证据带来源和时间，冲突时有决策规则
- 给出系统效果、成本和安全性的评测方式

## 答案

**先把任务拆成“理解约束—生成候选—验证可行性—用户确认”，再决定哪些步骤值得并行。** 可由需求 Agent 提取日期、预算、偏好和必去点；规划 Agent 组合景点、交通、餐饮和住宿；验证 Agent 检查营业时间、路程、预算和预约条件。编排器保存唯一的结构化行程状态，子 Agent 只提交带版本号的修改，避免各自维护一份相互矛盾的行程。

景点介绍、路线模板等较稳定内容可放入 RAG；天气、票价、拥堵、库存和营业状态应优先调用权威实时 API。每条证据携带来源、更新时间和适用范围，官方信息与 UGC 冲突时，硬约束以官方来源为准，体验偏好可参考多方评价；仍不确定就展示差异并让用户选择。

用户中途换城市时，根据行程依赖图只废弃受影响的交通、住宿和景点节点，保留预算、同行人等仍有效约束，再局部检索和验证。预订、取消等有副作用的动作必须在最终价格与政策校验后由用户确认，并使用幂等键。

评测不能只看回答流畅度，还要看约束满足率、事实新鲜度、行程可执行率、修改后的重算范围、端到端成功率、延迟、成本和人工接管率。任务很简单时，单个编排器加确定性工具通常比多 Agent 更稳。

## 知识点

任务分解、多智能体编排、共享状态、依赖图、动态数据工具、证据新鲜度、幂等确认。
