## 题目

TTFT 在 server 端耗时主要都体现在哪些地方?TPOT 耗时主要体现在哪些地方?

## 要点

- TTFT 按请求经过的顺序拆五个环节,并指出高并发下排队是绝对大头
- 讲清「空载看 prefill、满载看队列」这条判据
- TPOT 拆成:权重读取(可摊薄)、KV 读取(摊薄不了)、采样、同批等待、框架开销
- 能解释为什么权重读取能被 batch 摊薄而 KV 读取不能
- 同批里混进长 prefill 是 ITL 毛刺最常见的来源

## 答案

### TTFT 花在哪(按请求经过的顺序)

| 环节 | 在干什么 | 量级 / 主导条件 |
|---|---|---|
| **排队等待** | 在 waiting 队列里等着被调度进某一步的 batch | **高并发下的绝对大头** |
| 准入与调度 | 检查 KV 块够不够、和别的请求拼 batch | 本身 < 1 ms;块不够会退化成「等别人释放」 |
| tokenize | 文本 → token id | 毫秒级;超长 prompt 可到几十 ms,且在 CPU 上抢资源 |
| **prefill 前向** | 整个 prompt 过一遍模型、建好 KV | 随 prompt 长度增长(attention 是平方项),**计算受限**,空载时的主体 |
| 首 token 采样与后处理 | logits → 采样 → detokenize → 推给客户端 | 毫秒级;跨可用区的网络 RTT 可能反而是大头 |

**为什么高并发下由排队主导**:GPU 一步能处理的 token 数有硬上限(受 KV 块数与单步 token 预算约束)。到达率逼近服务率时排队论生效,队长非线性发散,而等待时间 ≈ 队长 × 单步耗时。于是出现那条经典曲线——**prefill 本身耗时几乎不变,但 TTFT 的 P99 在接近饱和点时突然翘起来**。

**面试直答**:空载时 TTFT ≈ prefill 计算时间,和 prompt 长度强相关;高负载时 TTFT ≈ 排队时间,和队列深度强相关。**看到 TTFT 涨了,第一件事是看队列长度而不是看 kernel。**

### TPOT 花在哪

decode 每步只为 batch 里每条请求生成 1 个 token,却要把整个模型权重从显存读一遍,算术强度极低,所以是典型的访存受限:

- **权重读取(主导项)**:每步搬一遍全部权重。关键性质是这份开销由 batch 里所有请求**共同摊薄**,batch 越大越划算。
- **KV cache 读取**:正比于 batch 内已生成的总长度,**摊薄不了**,且随对话变长线性增长——这就是长上下文「越生成越慢」的原因。
- **采样**:top-k / top-p 要在十万量级词表上排序归一化,batch 小、模型小时占比会变得可见。
- **与同批请求共享算力的等待**:同一步所有请求一起前进,**单步时间由整个 batch 决定**。一条超长 prompt 的 prefill 混进这一步,所有人的 ITL 一起抖——这是 ITL P99 毛刺最常见的来源。
- **每步框架开销**:调度、组 batch、kernel 启动。小模型上能占大头,CUDA Graph 就是专门用来消掉它的。

一条推论:batch 从 1 涨到 32,单步时间只涨一点点而产出涨 32 倍,所以在访存受限区**吞吐几乎线性上升**;等算力饱和或 KV 装不下更多请求,TPOT 转为线性增长,吞吐压平——那就是「加 batch 免费提吞吐」的额度用完的位置。

## 知识点

排队主导 vs 计算主导、权重读取可摊薄 / KV 读取不可摊薄、同批干扰、CUDA Graph 消框架开销。
