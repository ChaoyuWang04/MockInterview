## 题目

举例说一下常用的调度方式,什么是连续批调度?这几种调度方式有啥差异?

## 要点

- 说清静态批的病根:请求生命周期差几十倍,却被要求同生共死
- 连续批的定义:调度粒度从「请求级」细化到「每个 decode step」
- 动态批 ≠ 连续批,前者只解决「批凑不满」
- 能指出连续批的落地前提:分页 KV + 变长 attention kernel
- 每种方式各自的适用场景

## 答案

### 三种方式对比

| | 静态批 static | 动态批 dynamic | 连续批 continuous |
|---|---|---|---|
| 调度粒度 | 请求级,发车后不动 | 请求级,发车前等一小段窗口凑批 | **迭代级(每个 decode step)** |
| 新请求何时能进 | 整批跑完 | 下一个窗口 | **下一步** |
| 完成的请求何时释放 | 整批跑完 | 整批跑完 | **立刻** |
| 额外延迟 | 无窗口,但尾部大量空转 | 人为等待 1–50 ms | 无额外等待 |
| GPU 利用率 | 随请求陆续完成而坍塌 | 同静态批,只是批更满 | 全程接近满 |
| 适用场景 | 离线批量打分、评测 | 输出长度固定的分类 / embedding / rerank | **自回归 LLM 在线服务** |

### 静态批的病根

一批里 A 生成 20 个 token 就 EOS 了,B 要生成 2000 个,A 得陪跑 1980 步才能返回;批内活着的请求数从 N 掉到 1,而 decode 是访存受限的,权重照样整份读一遍,**摊到每个 token 上的成本涨了好几倍**;新请求还必须等整批跑完才能进,这段纯排队直接打进 TTFT。

### 连续批调度是什么

**调度决策从「每个请求做一次」变成「每个 iteration 做一次」**(iteration-level scheduling,出自 Orca)。每个 decode step 结束后引擎做三件事:命中停止条件的请求立刻移出并释放 KV 块 → 看还剩多少坑位(受并发上限与空闲块数两个预算约束)→ 从等待队列补新请求进来。类比:静态批是包车,连续批是地铁,每站都能上下客。

### 三条必须讲清的区分

- **动态批不等于连续批**:动态批在入口攒几毫秒的窗口把零散请求拼满,**一旦发车依然是静态批**,同进同出。
- **动态批对 LLM 不够用**:LLM 的痛点不是「批不满」,而是「批内生命周期差几十倍」。反过来,一次前向出结果的 embedding / 分类模型上连续批毫无意义。
- **两者可以叠加**:实际引擎入口也做很轻的攒批,但主力永远是迭代级调度。

## 知识点

迭代级调度(Orca)、静态批 / 动态批 / 连续批、准入预算、变长 KV 是落地前提。
