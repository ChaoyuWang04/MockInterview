## 题目

capture 时以 batch 还是 seq 为变量?为什么不用另一个?

## 要点

- 前提:图的形状被冻结,只能给**少数离散档位**各捕获一张图
- batch 有界且小、是标量、能 padding;seq 每步 +1、逐条不同、padding 代价爆炸
- 实践做法:对数递增档位 + 向上 padding + 超出最大档回退 eager
- seq 不进形状,而是「预分配 + 当参数传」
- 收口:图冻结的是**地址和形状**,不是**内容**

## 答案

### 为什么必须选一个

图的形状是冻结的,**不可能为一个连续变化的量建图**,只能挑少数离散档位各捕获一张。decode 时会变的量有两个:

| | batch size | seq 长度 |
|---|---|---|
| 取值范围 | **有界且小**,1 到最大并发(常见 ≤ 256) | 1 到 context length,几万甚至几十万 |
| 变化方式 | 请求进出时才变,不频繁 | **每步 +1**,且每条序列各不相同 |
| 是不是一个标量 | 是,整个 batch 共用一个 | **不是**,是每条一个值的向量 |
| 能否 padding | ✅ 补 dummy 行算完丢弃,代价可控 | 补到 max_len = 每步都算满上下文,代价爆炸 |
| 结论 | **拿它分档** | **不可能分档** |

所以实践是:**按 batch size 取一组对数递增的档位,每档捕获一张图**;真实 batch 落在两档之间就**向上 padding 到最近档**;超过最大档位**回退 eager**。主流引擎的默认档位形如 `[1, 2, 4] + range(8, 256, 8)`,或维护一组档位再二分查找定位,结构一致。

### 那 seq 长度怎么办

靠「**预分配 + 传参数**」把它从形状里挪出去:

- KV cache 按**最大长度预分配**,地址固定不变
- 每条序列的**实际长度**放进一个形状为 `[max_batch]` 的**设备端张量**,当普通参数传给 attention kernel
- kernel 内部读这个张量,决定循环多少步

于是「长度变化」变成了**张量里的数值变化**,而张量的地址和形状从头到尾没动过,图完全不知道长度变了。这正是那句收口的话:**图冻结的是地址和形状,不是内容**。

## 知识点

形状冻结、分档捕获(capture batch sizes)、向上 padding 与 eager 回退、序列长度设备端张量化。
