## 题目

L2 cache 命中的情况下,带宽利用率该怎么计算?

## 要点

- 先否掉「总访存量 / 耗时 / 峰值带宽」这个默认算法
- 把访存量拆成 L2 请求量与真正落到 HBM 的量两层
- 两条屋顶线各自的公式
- 会用「利用率超过 100%」当自查信号
- 知道分层 Roofline 这个概念
- 优先信 profiler 计数器,不信手推

## 答案

**不能照搬「总访存量 ÷ 耗时 ÷ 峰值带宽」——这是这套算法最容易翻车的地方。** 命中 L2 的那部分请求根本没走到 HBM,不消耗 HBM 带宽。

### 一、访存量要拆成两层

| 量 | 含义 | 对应哪条屋顶线 |
|---|---|---|
| $B_{\text{req}}$ | SM 发出、L1 未命中而下到 L2 的总字节 | L2 带宽 |
| $B_{\text{req}} \times (1 - h_{L2})$ | L2 也没命中、真正落到显存的字节 | HBM 带宽 |

于是两个利用率必须分开算($h_{L2}$ 是 L2 命中率):

$$
U_{\text{HBM}} = \frac{B_{\text{req}} \times (1 - h_{L2})}{t \times BW_{\text{HBM}}} \qquad\qquad U_{L2} = \frac{B_{\text{req}}}{t \times BW_{L2}}
$$

左式算 HBM 利用率时**要把 L2 命中的部分扣掉**;右式 L2 自己那条屋顶线用未扣减的请求量,分母换成 L2 峰值带宽。

### 二、一个例子看差别有多大

某 kernel 耗时 0.1 ms,请求量 300 MB,L2 命中率 70%,跑在 A800 上(HBM 2.039 TB/s):

- **傻算**(不扣命中):300 MB / 0.1 ms = 3.0 TB/s,除以 2.039 TB/s = **147%** —— 物理上不可能
- **正确算**:落到 HBM 的只有 300 × 0.3 = 90 MB → 900 GB/s → HBM 利用率 **44%**
- **再看 L2**:3.0 TB/s 对着 A100 实测约 3 TB/s 量级的 L2 带宽 → **L2 才是真瓶颈**

**利用率算出超过 100%,几乎一定是 cache 命中在起作用**——这是最好用的自查信号,不是你的 kernel 突破了物理定律。

### 三、分层 Roofline

把 HBM、L2、shared memory 各自的带宽都画成一条屋顶线,就是 **hierarchical roofline**:同一个 kernel 在 HBM 那条线上远未触顶,却可能已经贴着 L2 那条线,**优化方向完全不同**。

### 四、两条补充

- HBM 字节要**读写都算**,写回同样占带宽;有的算子写回量比读入还大
- 真机上的 $B_{\text{req}}$ 和 $h_{L2}$ 不用手推,profiler 有 DRAM 字节计数器可直接读——**优先信计数器,不信手推**

## 知识点

L2 命中率对 HBM 流量的扣减、分层 Roofline、L2 带宽与 HBM 带宽的量级差、利用率 > 100% 的自查信号。
