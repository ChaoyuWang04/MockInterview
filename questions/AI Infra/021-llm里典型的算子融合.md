## 题目

算子融合分哪几类?LLM 的训练和推理里典型会对哪些算子做融合?

## 要点

- 三种形态:垂直 / 水平 / epilogue,收益来源各不相同
- epilogue fusion 最划算,复用的是已经在寄存器里的输出 tile
- 四个经典案例要能各说出「融了什么、省了多少」
- elementwise 最好融,reduction 要靠单趟算法或整行进 shared
- 三类不该硬融的情况

## 答案

### 一、三种形态

| | 消中间张量 | 省 launch | 主要收益来源 |
|---|---|---|---|
| **垂直融合**(生产者—消费者) | ✅ | ✅ | 访存量下降 |
| **水平融合**(互不依赖的兄弟算子) | ❌ | ✅ | 启动开销 + SM 填充率 |
| **epilogue fusion**(挂在 GEMM 尾巴上) | ✅ | ✅ | 复用已在寄存器里的输出 tile |

水平融合的典型场景是优化器更新:几百个参数张量各做一次 AdamW,合成一个多张量 kernel。epilogue 特别划算——GEMM 算完一个输出 tile,结果还躺在寄存器里,**顺手加 bias、过激活、加残差,再一次性写回**,等于白送;对称地还有 prologue(把反量化、归一化并进 GEMM 的取数阶段)。

### 二、四个经典案例

| 案例 | 融了什么 | 收益 |
|---|---|---|
| **FlashAttention** | `QK^T → scale/mask → softmax → PV` 四步并成一个 kernel,分块加载 Q/K/V + online softmax | $L \times L$ 的注意力矩阵**从来没有整体存在过**,中间量从 $O(L^2)$ 降到 $O(L)$。seq 8K 时单头的注意力矩阵就是 128 MiB,还要写一遍读两遍 |
| **残差 + RMSNorm** | 一次读入两个输入,寄存器里相加、顺便累平方和、归一化写出 | 单次只省 20%(`h` 是残差主干仍要写回),但**次数极多**:一层两次 × 32 层,一次前向省约 2 GiB 流量 |
| **SwiGLU** | 两个投影拼成一个 GEMM,再在 epilogue 里劈开、过 SiLU、逐元素相乘 | 中间张量是 $T \times d_{ff}$($d_{ff}$ 通常是 $d$ 的 2.7–4 倍),8B 量级模型在 $T=4096$ 时单个就 112 MiB |
| **交叉熵 + log_softmax** | `logits → log_softmax → NLL` 串成一个 kernel,并**沿 token 维分块** | 词表 128K 时 logits 是 GiB 级,算 loss 这一小步能吃掉 6 GiB;分块后峰值中间量降到几十 MiB |

### 三、什么能融、什么不能

- **elementwise 最好融**:每个输出只依赖对应位置的输入,线程间零通信,任意长的链都能融——这是编译器自动融合的主战场
- **reduction 能融但要小心**:要跨线程通信,且经典写法是两趟。两条办法——把归约限制在**一行之内**(整行进 shared,换成「一趟 HBM + 两趟片上」),或用**在线单趟算法**(Welford、online softmax)
- **三类不该硬融**:需要**全局同步**(两次跨整个张量的归约串联——block 之间没有便宜的同步手段,kernel 边界才是全局屏障);**形状 / 并行度对不上**;中间结果**还要被别处用**(它无论如何都得落盘)

### 四、怎么落地

默认从 **torch.compile** 起步(自动把 pointwise 链聚成 Triton kernel);融不动的用 **Triton** 手写;极致性能走手写 CUDA / CUTLASS epilogue;或直接换现成的融合算子库。一条经验:**先用 profiler 挑出「占时间但 FLOPs 很少」的小 kernel**,对着大 GEMM 硬融是白费力气。

## 知识点

垂直 / 水平 / epilogue 三种形态、FlashAttention 的 IO-awareness、残差+RMSNorm、SwiGLU、融合交叉熵、reduction 的单趟算法、不该融的三类情况。
