## 题目

decode 阶段一般在哪些场景下会 OOM?

## 要点

- 先说机理:decode 的显存占用**单调上升**,准入时不 OOM 不代表 500 步后不 OOM
- KV 随 (batch × 序列长度) 线性增长,给一个能算的数
- 输出长度事先不可知,调度器只能按当前长度准入
- 抢占水位配置不当:太晚就 OOM,太狠就 thrash
- 容易漏的两条:CUDA Graph 独立显存池、PD 分离接收侧的预留

## 答案

### 机理:显存占用单调上升

decode 每一步都在给每条序列 append KV,**准入时装得下,不代表 500 步后还装得下**。这和 prefill 不同——prefill 的峰值在一次前向内就见底了。

### 六类典型场景

| 场景 | 机理 | 典型触发 |
|---|---|---|
| **长上下文 × 大 batch** | KV 随 (batch × 序列长度) **线性增长**。Llama-3-8B 每 token 128 KiB → batch 64 × 8k token = **64 GiB**,单张 80G 卡直接爆 | 长文档问答、长历史多轮 |
| **输出长度不可预测** | 调度器按「当前长度」准入,但一个 max_tokens=8192 的请求会一直长下去,慢慢把显存吃满 | 突发长生成请求 |
| **抢占策略不当** | 水位线设太高、抢占太晚就 OOM;抢占太狠又反复重算(thrash),吞吐塌方 | 高并发下水位配置错 |
| **CUDA Graph 显存池叠加** | graph capture 用独立显存池,和常规 allocator 池**不共用**,这块预留挤占 KV 可用块——开了 CUDA Graph 更容易 OOM | 开 graph 且 KV 池按满显存估算 |
| **PD 分离特有:接收侧预留** | D 侧必须常驻一块 RDMA 注册 buffer(pin 住不可换出),再加「为在途 KV 预留的物理块」;P 传得太猛而 D 没及时腾块,接收侧就撑爆 | 配比失衡、突发长 prompt |
| **碎片与杂项** | 分页消灭了 KV 的碎片,但激活峰值、量化 scale、投机解码的 draft 模型都在抢同一块显存 | 同时开了多个特性 |

### 缓解方向

- **控输入**:限制单请求最大生成长度、限制最大上下文,准入时按**整条序列**估算而不只看第一步。
- **控并发**:留一部分空闲 KV 块作水位线,不把显存用到刚好;抢占用重算而不是换出(PCIe 比 HBM 慢一到两个数量级)。
- **减单价**:上 GQA、KV cache 量化,把每 token 字节数砍下来,同样显存装更多 token。
- **看信号**:抢占频率是最好用的健康指标——日志里频繁抢占 = KV 显存不够,该降并发、缩上下文或上量化。

## 知识点

KV 占用单调上升、(batch × seq) 线性增长、水位线与 thrash、CUDA Graph 独立显存池、PD 分离接收侧预留。
