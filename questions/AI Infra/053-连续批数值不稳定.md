## 题目

连续批调度为啥会引发数值不稳定性(每次推理结果都无法固定)?怎么规避这个问题?

## 要点

- 先排除两个误解:不是采样随机性,通常也不是「GPU 并发累加乱序」
- 完整因果链:batch 组成变 → 矩阵形状变 → kernel 选择变 → 归约顺序变 → 浮点非结合 → argmax 翻转
- 自回归是误差放大器,一步分叉后整段文本不同
- 规避手段要按代价排序,并说清「确定性与吞吐直接对立」
- 能补两个次级来源:split-K 原子加、TP 下的通信归约

## 答案

**完全一致要同时控制两类变量**:先固定采样侧的随机种子、温度和 Top-k/Top-p,再控制计算侧的硬件、精度、并行方式、batch 形状与确定性 kernel。只把温度设为 0 只能去掉随机抽样;浮点归约顺序变化仍可能翻转很接近的 argmax。跨 GPU 型号、框架或内核版本时,通常只能追求可复现指标或容差内一致,不能承诺逐 token 完全相同。

### 先排除两个常见误解

- **不是采样随机性**:temperature=0 是贪心解码,argmax 里没有随机数。
- **通常也不是并发累加乱序**:Transformer 前向一般不用浮点 atomicAdd 做归约,固定输入下的单次前向是 run-to-run 确定的。真正的罪魁是**批不变性(batch invariance)的缺失**。

### 五步因果链

1. **batch 组成每步都在变**。你的请求这一步和 3 条同批(GEMM 的 M=4),下一步别人完成、新请求补进来变成 M=17。你的输入一个字没改,但**矩阵形状取决于此刻别的用户发了什么**。
2. **形状变了 → kernel 选择变了**。cuBLAS 按 M/N/K 用启发式挑实现:tile 大小、线程块分工、是否 split-K。M=4 和 M=17 大概率落到两个不同 kernel。
3. **kernel 变了 → 归约顺序变了**。同一行点积,一个把 K 维切 4 段,另一个切 8 段;split-K 更是拆给多个线程块各算一部分再合并。
4. **归约顺序变了 → 浮点末位变了**,因为浮点加法不满足结合律:

$$
(a + b) + c \neq a + (b + c)
$$

5. **末位差异 → argmax 可能翻转**。绝大多数 step 无所谓;但 top-1 与 top-2 的 logits 靠得极近时,1 ulp 的扰动足以让排序对调。而**自回归是误差放大器**,一步选了不同 token,后面整段彻底分岔。

Thinking Machines 的实验:同一 prompt、temperature=0、生成 1000 token 重复 1000 次,得到 **80 种不同补全**,首次分叉出现在**第 103 个 token**。

两个次级来源:**split-K 原子加**(累加顺序取决于线程块调度先后,batch 不变也可能两次不同);**张量并行的通信归约**(TP size 变了全局累加顺序就变)。

### 怎么规避(按代价从小到大)

| 手段 | 做法 | 代价 |
|---|---|---|
| padding 到固定档位 | 把 M 维 pad 到 8/16/32/64 少数几档 | pad 出来的行白算,档位越少越浪费 |
| 锁定确定性 kernel | 禁浮点 atomicAdd、禁降精度归约、不走启发式 | 只治 run-to-run,**治不了 batch 变化** |
| batch-invariant 归约 | 从 kernel 层保证归约顺序与 batch 无关,matmul / RMSNorm / attention 三类全改 | 吞吐明显下降(公开数据 26 s → 42–55 s) |
| 固定 batch 形状 | 锁死 batch 不随调度变 | 等于放弃连续批处理 |
| 业务侧兜底 | 缓存结果、只承诺「同批次内一致」 | 不是技术解,但线上多数如此 |

**核心认知:确定性和吞吐直接对立**——连续批的收益恰恰来自「batch 组成随时在变」。线上服务追吞吐、容忍不确定;RL 训练、回归测试、审计复现才开确定性模式。另外确定性 ≠ 正确性,两种归约顺序算出来的都对。

## 知识点

批不变性、浮点非结合律、cuBLAS 启发式选核、split-K、argmax 翻转、训推一致性。
