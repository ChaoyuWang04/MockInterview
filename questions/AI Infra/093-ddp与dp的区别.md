## 题目

ddp 和 dp 的区别和差异?

## 要点

- 差异的根在**进程模型**:单进程多线程 vs 每卡一个进程
- DP 的两个致命伤:GIL 争用、主卡显存爆
- DDP 快不只因为多进程,还有梯度分桶 + 与反向重叠这两个工程细节
- 能答出"DP 的梯度通信不在关键路径上"的实现依据
- DP 不能跨机,DDP 能

## 答案

PyTorch 里两个同名不同命的东西:

| | `DataParallel`(DP) | `DistributedDataParallel`(DDP) |
|---|---|---|
| 进程模型 | **单进程多线程**,一个 Python 进程驱动所有卡 | **多进程,每卡一个进程** |
| 每步做什么 | 主卡复制模型到各卡 → scatter 输入 → 各卡前向 → **输出 gather 回主卡**算 loss → 梯度汇总到主卡 → 主卡更新 | 各进程独立前反向 → 梯度 all-reduce → 各自更新(参数从不广播) |
| 瓶颈 | **GIL 争用**:多线程抢一个解释器锁,调度开销吃掉并行收益;每步还要重新复制一遍模型 | 无 GIL 问题;通信是集合操作,无中心节点 |
| 显存 | **主卡爆**:它多扛一份 gather 上来的全部输出 + 全部梯度,其余卡闲着 | 各卡均衡 |
| 能否跨机 | 不能 | 能 |

### DDP 快的两个工程细节(容易被追问)

光说"换成多进程"答不到位,真正让 DDP 跑得快的是**梯度分桶(bucketing)** 和 **与反向重叠**:

反向传播是**从最后一层往前算**的,梯度是**陆续**出炉的。DDP 把参数按注册的逆序打包成若干个桶(默认每桶 25 MiB),**某个桶的梯度一凑齐就立刻发起这个桶的 all-reduce**,不等整个反向结束。通信被切碎、塞进反向计算的缝隙——这就是"DP 的通信不在关键路径上"这句话的实现依据。

桶大小是个跷跷板:**开小**通信启动早但次数多,每次都要重付固定启动开销、消息小还打不满带宽;**开大**摊薄了开销但开始得晚,最后一个桶容易来不及藏。25 MiB 只是个折中默认值。

还有一段**必然裸露**:反向最后发出的那个桶(模型最前面几层的梯度)出炉时反向已经结束,它后面没有计算可以掩盖。

### 一句话收口

DP 是"主卡当管家"的中心化实现,DDP 是"人人平等"的集合通信实现。**DP 早已被废弃**,新代码不该再用。

## 知识点

单进程多线程 vs 多进程、GIL 争用、主卡显存不均、梯度分桶按反向逆序、桶大小的跷跷板、最后一个桶必然裸露。
