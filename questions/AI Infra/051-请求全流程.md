## 题目

从一个请求过来,到最后吐出 token,把这个请求在 vLLM 或者 SGLang 里经历了哪些流程大概描述一下。

## 要点

- 能给出一条完整主线,而不是只讲某一段
- 说清 prefill 与 decode 的分界点(第 1 个输出 token)
- 提到调度器的准入依赖「空闲 KV 块数 + 并发上限」两个预算
- 提到迭代级组批:每步重新拼 batch,完成的立刻移出
- 提到 KV 块的分配、写入与释放,以及抢占这条岔路
- 能补一句 PD 分离部署下这条线怎么被切成两半

## 答案

### 端到端主线

1. **接收与 tokenize**:校验采样参数,把 prompt 切成 token id,包成带停止条件的内部请求对象。
2. **入队与准入**:进 waiting 队列(默认 FCFS),调度器按空闲 KV 块数与并发上限决定这一步收不收它——高并发下这段排队就是 TTFT 的大头(见 推理服务指标 篇)。
3. **prefill**:整段 prompt 一次前向,算出各层 K/V 并产出第 1 个输出 token;开了 chunked prefill 则沿序列维切块,一步只算一块,剩余 token 预算捎带其他请求的 decode(见 连续批处理 篇)。
4. **KV 块分配与写入**:按需从显存块池取物理块、登记块表,算出的 K/V 按槽位映射散写进分页显存;前缀命中的块直接引用,省掉重复计算(见 PagedAttention 篇)。
5. **进 decode 批**:每个 iteration 重新组批——续跑的加新准入的拼成一个 batch 一起前向,每条各出 1 个 token。
6. **每步 attention 与采样**:kernel 按块表 gather 历史 KV 算 attention(见 FlashAttention 篇),logits 处理后按 temperature / top-k / top-p 采样出下一个 token。
7. **检测结束**:命中 EOS、max_tokens 或 stop string 就立刻移出 batch;KV 不够时可能被抢占,当前主流做法是丢掉 KV 后重新 prefill。
8. **流式返回与释放**:增量 detokenize 后推给客户端,请求结束时块引用计数归零、回到空闲池。

PD 分离部署下这条线被切成两半:2–4 步在 P 实例、5–8 步在 D 实例,中间多一次 KV 跨实例传输与 D 侧块表重建(见 PD分离 篇)。

## 知识点

迭代级调度、分页 KV 与块表、chunked prefill、准入预算、抢占重算、流式返回。
