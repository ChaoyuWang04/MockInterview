## 题目

什么是 stream?stream 间是怎么做并行的?

## 要点

- stream 的定义一句话带过,重点答"凭什么能并行"
- 并行的前提是**用的不是同一套硬件**,不是"开了多条流就快"
- 通信单独一条流的意义:用 event 表达真实依赖,而不是全局 sync
- 多流不免费:通信 kernel 占 SM、两边抢 HBM 带宽
- 常见现象:看着并行了,总时间没降

## 答案

### 定义:一条按下发顺序执行的任务队列

同一条 stream 内的操作严格按下发顺序串行;**不同 stream 之间没有任何隐含顺序**,硬件有富余就能同时跑。stream 的创建、event、同步点、默认流的语义见 CUDA流与异步执行 篇,这里只讲它和集合通信的关系。

### stream 间凭什么能并行

关键不是"开了几条流",而是**这几条流用的是不是同一套硬件**:

| 组合 | 能不能真并行 | 为什么 |
|---|---|---|
| 通信流 + 计算流 | **能,而且是最典型的一组** | 搬数据走链路与 DMA 引擎,矩阵乘在 SM 上,物理上分开 |
| 两条计算流都跑大 GEMM | 基本不能 | 抢同一批 SM,单个 kernel 已经占满时并行度为零 |
| 计算流 + H2D/D2H 拷贝流 | 能 | 拷贝走独立的 copy engine(前提是主机侧用 pinned 内存) |
| 两条都跑访存受限的算子 | 名义上并行,总时间不降 | 抢的是同一份 HBM 带宽 |

一句话:**多流只是给了硬件"可以同时做"的许可,真并行还得看有没有空闲的那套硬件。**

### 通信为什么要单独一条流

把 all-reduce 下发到专用通信流,再用 **event** 表达真实依赖(通信流 `record`、计算流 `wait`),依赖之外的计算就能继续往下发。最忌讳的是用**全局 sync 或默认流**把两条流拉平——那等于把重叠机会清零。梯度分桶、prefetch、切块流水这些手段,底座全是这条独立通信流。

### 多流不是免费的

- **通信 kernel 占 SM**:一条通道对应一个 thread block,开几条通道就少几个 SM 给 GEMM
- **抢显存带宽**:两边都读写 HBM,访存受限的算子一起变慢
- 所以"看着并行了,总时间没降"很常见——净收益必须实测,旋钮是通道数与分块粒度

## 知识点

stream 是任务队列、流间无隐含顺序、并行前提是硬件不同套、event 表达依赖优于全局 sync、copy engine 需 pinned 内存、多流的 SM 与带宽代价。
