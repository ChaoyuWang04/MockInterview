## 题目

torch.profiler 是什么?怎么对模型做性能优化?一般从哪些方面入手?讲讲你的性能优化经验。

## 要点

- torch.profiler 是**框架算子层**的账本,核心是 `schedule` 与两个时间字段
- 优化流程五步,重点在第二步的分层排查
- 起手先算 GPU 有效时间占比,不要一上来就优化 kernel
- 判 bound 排在定位层级**之后**,不是之前
- 没复测的优化等于没做
- 开放经验题按「场景 → 测到什么 → 判了什么 bound → 做了什么 → 收益与代价」讲

## 答案

### 一、torch.profiler:框架层的账本

按**算子(op)** 归因,告诉你哪个算子 / 哪行 Python 最贵。核心是 `schedule(wait=1, warmup=1, active=3)`,天然帮你跳过预热步;`record_shapes=True` 记形状、`with_stack=True` 记 Python 调用栈;导出的 chrome trace 是标准 JSON,拖进 Perfetto 就能看。三个读法要点:

- **`self_cuda_time` 与 `cuda_time` 别搞混**,self 不含子算子。排热点用 self,看归属用总时间
- **CPU 总时间远大于 CUDA 总时间 = CPU 侧瓶颈**
- **调用次数极大、单次耗时极小的算子**,是小算子太多的铁证 → 指向算子融合或 CUDA Graph

### 二、优化流程五步(这题的标准答法)

1. **定基线**:固定输入形状与随机种子、锁定环境;warmup 之后用 CUDA event 计时、取中位数
2. **定位瓶颈在哪一层**(全流程最值钱的一步,见下表)
3. **判 bound 类型**:只有确认瓶颈落在 kernel 层,才轮到算算术强度、比 roofline 拐点
4. **按 bound 选手段**:访存受限就减访存(融合、tiling、量化),计算受限就提高算力利用(Tensor Core、更好的分块)
5. **复测**:用完全相同的基线方法再测一次。**没复测的优化等于没做**

| 层级 | 典型信号 | 常见成因 |
|---|---|---|
| 数据 | GPU 时间线整段空白,CPU 在 dataloader | worker 太少、没 pin_memory、预处理太重 |
| CPU / 框架侧 | GPU 空隙密集且规律,CPU 一直在忙 | Python 开销大、小算子太多、launch 跟不上 |
| 同步 | 空隙前有很长的 `cudaStreamSynchronize` | 代码里有 `.item()` / `.cpu()` / `print(tensor)` |
| kernel | GPU 几乎没空隙,但单个 kernel 就是久 | 实现差、访存模式差、精度没用对 |
| 通信 | NCCL kernel 和计算 kernel 首尾相接不重叠 | 并行策略选错、没开 overlap |

### 三、起手先看一个数

$$
\text{GPU 有效时间占比} = \frac{\sum_i \text{kernel}_i\ \text{执行时长}}{\text{一个 step 的墙钟时长}}
$$

如果它只有 0.5,说明一半时间 GPU 在发呆,这时候再优化 kernel,端到端最多快一点点。**必须先把发呆的那一半填上。** 经典翻车:花两周手写更快的 attention kernel,上线端到端只快 2%——因为 60% 的时间根本不在 GPU 上。

### 四、讲经验时怎么组织

每段按 **场景 → 测到什么 → 判了什么 bound → 做了什么 → 收益多少 + 代价是什么** 讲,每条都带数字;主动说清楚**哪些没做、为什么不做**。切忌上来就背优化手段清单。

## 知识点

torch.profiler 的 schedule 与时间字段、五步优化流程、分层排查表、GPU 有效时间占比、复测纪律。
