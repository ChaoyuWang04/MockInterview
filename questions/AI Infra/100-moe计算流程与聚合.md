## 题目

详细讲下 MoE 的计算流程?专家计算完后的聚合过程,是发生在哪里,combine 前还是 combine 后?

## 要点

- 结论先给:加权求和在 **combine 之后**,combine 只负责原路寄回
- 六步流水要带上形状,尤其是"中间那段被放大 $k$ 倍且长度动态"
- 能说清为什么聚合提前不了
- 顺带答出 MoE 通信"不规则"在哪三处(常见第二层追问)

## 答案

**结论:按门控权重的加权求和发生在 combine 之后。** combine 只负责把结果原路寄回 token 的老家,寄回来的**仍是 $k$ 份**;加权相加是在本卡做的最后一步。

记号:本卡这一层拿到 $T$ 个 token,隐藏维 $h$,top-$k$ 路由,专家摊在 $E$ 张卡上,每元素 $b$ 字节。

| 步骤 | 输入形状 | 输出形状 | 关键点 |
|---|---|---|---|
| router | $[T,h]$ | 专家 id $[T,k]$、门控权重 $[T,k]$ | 一个小矩阵乘加 top-k,耗时可忽略 |
| 排序打包 | $[T,h]$ + id | 发送缓冲 $[Tk,h]$、每目标 rank 条数 $[E]$ | 一个 token 被**复制 $k$ 份**,分别排进 $k$ 个目标段 |
| **dispatch** | $[Tk,h]$ | $[T_{\text{recv}},h]$ | $T_{\text{recv}}$ 由别人送来多少决定,**运行时才知道** |
| 专家 GEMM | $[T_{\text{recv}},h]$ | $[T_{\text{recv}},h]$ | 收到的 token 已按专家分好段,每段配一份专家权重 → **分组 GEMM** |
| **combine** | $[T_{\text{recv}},h]$ | $[Tk,h]$ | 原路寄回,收发方向与 dispatch 互换 |
| 加权求和 | $[Tk,h]$ | $[T,h]$ | 每个 token 的 $k$ 份结果按门控权重相加 |

形状这条线一句话:**进出 MoE 层的都是 $[T,h]$,中间那一段被放大了 $k$ 倍,而且长度是动态的。**

### 为什么聚合提前不到 combine 前

一个 token 的 $k$ 份结果分散在 $k$ 张**不同的卡**上,combine 之前它们根本不在同一个地方。想提前加,就得先做一次跨卡规约——那等于把便宜的 all-to-all 换成更贵的 all-reduce,反而亏。

### "不规则"在哪三处(常见追问)

1. **收发长度由数据决定**:TP 的 all-reduce 每次张量一样大、编译期就能定死;dispatch 要送多少条取决于这批 token 恰好选了谁,所以每层都得先把"谁给谁发几条"这张计数表交换一遍才能开通信
2. **发送前必须重排内存**:同目标 rank 的 token 在原 buffer 里是散落的,直接发就是几百次小拷贝,得先按专家 id 做一次排序(argsort + gather)拼成连续段——这一步开销真实存在
3. **形状动态 → CUDA Graph 不好用**:decode 本来最指望 CUDA Graph 压掉 launch 开销,偏偏这段每步形状都变(DeepEP 的 masked layout 就是冲这条来的)

## 知识点

六步流水与形状、聚合在 combine 之后、$k$ 倍放大且动态、计数表交换、排序打包、动态形状与 CUDA Graph 冲突。
