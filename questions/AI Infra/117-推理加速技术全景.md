## 题目

大模型在线推理延迟高、吞吐低、资源消耗大时，可以从模型压缩、KV缓存、批处理、并行、算子和硬件协同等哪些层面优化？如何按TTFT、TPOT与成本目标组合方案？

## 要点

- 先按TTFT、TPOT、显存、算力、带宽和调度定位瓶颈，再选技术
- 量化/蒸馏减少模型成本，KV cache减少历史投影重算，二者解决的问题不同
- 连续批处理提高吞吐，PagedAttention减少分配碎片，FlashAttention减少中间量IO
- 并行不总能降时延；跨卡通信可能抵消计算收益
- 所有收益都要绑定模型、硬件、长度分布、并发和质量门槛

## 答案

**推理优化不是技术清单，而是“测瓶颈 → 选手段 → 在同一SLO下复测”。** 先拆TTFT与TPOT：prefill常受大矩阵计算和长prompt影响；decode每步只生成少量token，常受权重与KV读取带宽影响，但具体仍要由profiling确认。

| 瓶颈 | 优先手段 | 为什么有效 |
|---|---|---|
| 权重放不下、decode带宽高 | INT8/INT4/FP8量化、蒸馏 | 减少权重字节；前提是有对应kernel且质量达标 |
| 重算历史token | KV cache | 复用历史K/V投影；当前query仍需扫描历史KV |
| KV碎片、并发低 | PagedAttention、连续批处理 | 非连续块分配并在每轮补入请求，提高可用容量与调度效率 |
| attention中间量IO高 | FlashAttention、融合kernel | 不物化完整注意力矩阵并减少kernel往返；不压缩持久KV |
| CPU提交与固定shape开销 | CUDA Graph、算子融合 | 减少launch与中间读写；动态shape要分档 |
| 单卡容量不足 | TP/PP或模型副本 | 切分模型或扩吞吐；需计算通信和bubble代价 |
| prefill与decode互相干扰 | chunked prefill、PD分离 | 隔离计算密集与带宽密集阶段；增加调度和KV传输 |

量化掉点时先按任务和层做敏感度评估，保留异常值/敏感层高精度或改用更细粒度方案。投机解码只有草稿便宜且接受率足够时才加速；拒绝后按算法回滚并补采。长上下文要同时控制KV容量、prefill计算和调度公平性，可组合GQA、KV量化、分页、chunked prefill及任务允许的滑窗/淘汰。

TTFT与TPOT冲突时，交互业务先保护TTFT和ITL尾部，限制长prefill占用；离线业务可以扩大batch追求token/s。显存足但单请求延迟敏感时，是否加TP取决于矩阵计算减少能否超过集合通信，不能凭卡数直接下结论。
