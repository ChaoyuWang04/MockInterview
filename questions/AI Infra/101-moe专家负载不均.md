## 题目

推理时如果专家负载不均衡会发生什么后果,怎么解决?负载不均衡在 trace 上的表现是啥?

## 要点

- 先划边界:训练侧 aux loss 是路由算法的事,这里问的是线上 GPU 忙闲不均
- 后果能量化:算力利用率上界 $\approx 1/\rho$,惩罚是**全局的**
- trace 三条特征要一起出现才定案
- 必须能和"带宽真不够"区分开——先算有效带宽再下结论
- 解法按代价从低到高排,别一上来就动态重排

## 答案

先划边界:训练时用 aux loss 或 bias 调节让专家负载均匀,那是**路由算法**的事;这里说的是**线上流量打进来之后 GPU 之间忙闲不均**——训练均衡了,推理照样可能不均衡,因为线上分布和训练分布不是一回事。

### 后果:最慢那张卡决定整层耗时

all-to-all 是一个**全局同步点**:每张卡都要等所有对端的数据到齐才能开算,combine 之后又要等所有人都回来。记 $\rho$ 为最忙卡分到的 token 数除以平均值:

$$
\text{该层算力利用率上界} \;\approx\; \frac{1}{\rho}
$$

一张卡拿到平均值的 2 倍,整层就只剩一半有效算力——**不均衡的惩罚是全局的,不是局部的**。EP 规模越大,每卡专家越少,单个热专家的波动越难被平均掉,$\rho$ 越难压。

### trace 上三条特征(一起出现基本定案)

1. **all-to-all kernel 之前出现长条空白**:GPU 行整段没活,后面紧跟一个很长的通信 kernel。这不是网络慢,是在等最慢的对端把数据发过来
2. **各 rank 的分组 GEMM 宽度参差**:多卡 trace 叠起来看同一层,专家 GEMM 的方块宽度差出好几倍——最直接的证据
3. **通信 kernel 很长,但有效带宽很低**:用「实际传输字节数 ÷ kernel 墙钟」算一下只有峰值的百分之几十甚至个位数,因为那段时长大部分是在等

**和"带宽真不够"怎么区分**:带宽不够时各 rank 的通信时长会**一致地**长、算出的有效带宽贴近硬件上限;不均衡时通信时长离散度大、有效带宽却很低。**先算有效带宽再下结论**——这一步不做,很容易把不均衡误诊成网络问题去换网卡。

### 解法(按代价从低到高)

| 手段 | 做什么 | 代价 |
|---|---|---|
| **加大全局 batch** | 更多请求进同一批,热点被平均掉 | 延迟上升,吞吐与延迟的老权衡 |
| **node-limited routing** | 限制每 token 最多去 $M$ 个节点(V3 取 4) | 损失一点路由自由度;主要压跨节点流量,对单卡热点只有间接帮助 |
| **冗余专家 / 热专家复制** | 高负载专家多复制几份放到不同卡分流(V3 部署里配了 32 个冗余专家) | 多占显存;要有在线负载统计决定复制谁 |
| **动态重排专家到卡的映射** | 按线上统计周期性重算"哪个专家放哪张卡" | 换图要迁移权重、得挑时机;统计窗口太短会来回抖 |
| **capacity factor + 丢弃** | 每专家容量封顶,超出的 token 走残差旁路 | 训练时代老方案,**推理侧一般不能丢**,丢 token 直接改变输出 |

上手顺序:**先看是不是 batch 太小**(小 batch 下不均衡多半只是统计噪声,加大 batch 就消失),**再上冗余专家**,**最后才考虑动态重排**。

## 知识点

all-to-all 是全局同步点、$1/\rho$ 利用率上界、trace 三特征、有效带宽区分法、冗余专家与动态重排、推理侧不能丢 token。
