## 题目

MoE 的流程,有哪些切分方式?tp 切 atten + 专家,和 tp 切 atten + ep 切专家,差在哪?

## 要点

- 默认配法一句话:attention 用 TP、MoE 层用 EP
- 不再 TP 切专家的两条理由:小 GEMM 效率差 + 两种通信抢同一条链路
- EP 不凭空多一维,是把 DP 维在 MoE 层重新解释
- 三种组合各自的适用与代价
- 反直觉的一条:EP 推理侧反而越开越大,要能给两笔账

## 答案

### 为什么 MoE 层不再 TP 切一刀

细粒度 MoE 时代,**单个专家本来就是一个很小的 FFN**。再按 TP 切开,每张卡分到的矩阵又瘦又窄,GEMM 效率掉下来;更糟的是 TP 每层要额外的 all-reduce,这笔通信会**叠在 all-to-all 上面**,而两者抢的是同一条节点内链路。反过来 attention 也用不了 EP:它压根没有"专家"这个维度可分。

所以工程默认配法是:**attention 保持稠密、用 TP 切;MoE 层换成 EP,一张卡放整数个完整专家。**

### EP 的 rank 从哪一维凑出来

卡就那么多,EP 不会凭空多一维——它是把 attention 侧的 **DP 维在 MoE 层重新解释**成 EP 维:同一批 GPU,进 attention 时按 DP 各算各的一份 token,进 MoE 层时按 EP 各持有一部分专家。DeepSeek-V3 的 prefill 部署就写成"MLA 与共享专家走 DP32、路由专家走 EP32",**同一组 32 张卡两种身份**。

| 组合 | 怎么摆 | 适合 | 代价 |
|---|---|---|---|
| **DP + EP**(主流) | attention 按 token DP,MoE 层把 DP 组当 EP 组用 | 细粒度专家、大规模推理 | 每层两次 all-to-all,负载均衡责任全在系统侧 |
| **TP + EP** | attention TP,MoE 层内每个专家再 TP 切 | 专家很大、EP 规模开不上去时 | 两种通信抢同一条节点内链路;小 GEMM 效率差 |
| **EP 跨节点** | EP 规模超过单节点卡数 | 大 MoE 的必然选择 | 慢链路进入关键路径,必须配转发 + node-limited routing |

### EP 为什么反而越开越大

看起来 EP 越大通信越痛,但推理侧的实践是往大了开(V3 报告的 decode 配置到了 EP320)。两笔账:

- **访存账**:每张卡上的专家变少,decode 每步要读的专家权重就少,而 decode 是访存受限的
- **算力账**:EP 越大,能凑进同一批的请求越多,每个专家收到的 token 就越多,**分组 GEMM 的每一段变胖,才吃得动 tensor core**

稀疏度越高(256 选 8 只激活 3%),越要靠**全局大 batch** 把每个专家的 token 数堆上去。代价是通信规模变大、重叠必须做,以及负载不均的惩罚随 EP 放大。

## 知识点

attention 用 TP / MoE 用 EP、专家再 TP 切的两条坏处、EP 由 DP 维改写、三种组合的代价、EP 开大的访存账与算力账。
