## 题目

对 KV cache 做量化有什么好处?收益具体是从哪里来的?

## 要点

- 一句话:用精度换容量,再用容量换吞吐
- 收益不主要来自"算得快",反量化本身还要花时间
- 三层连锁:装下 2× 的 token → 每步读的 KV 字节减半 → 权重被摊得更薄
- 第三层才是吞吐提升的大头
- 收益随上下文长度放大,短上下文可能被额外开销吃掉

## 答案

fp16 → fp8/int8 让每元素字节数 $b$ 从 2 变 1,每 token 的 KV 字节直接减半。好处**不主要来自"算得快"**,而是三层连锁:

1. **同样显存装 2× 的 token**。4×A100-80G 跑 Llama-3-70B(TP=4)、8K 上下文时,并发从约 52 涨到约 104;或者并发不变而上下文从 8K 拉到 16K。**并发上限是被 KV cache 直接算出来的,不是调出来的。**
2. **decode 每步读的 KV 字节减半**。KV 是 decode 里唯一随负载增长的带宽项(上面那台机器 batch 32 时占总读取的 36%,权重那 150 GB 一动不动),压一半就把 36% 降到 22%,每步时间下降。
3. **权重被摊得更薄**。batch 翻倍后,那 150 GB 的权重读取分摊到 2× 的 token 上——**这才是吞吐提升的大头**。

一组实测口径(vLLM 官方博客 2026-04,fp8 KV,未校准的 per-tensor scale = 1.0):Llama-3.1-8B 输出吞吐 **+14.9%**、中位 ITL **−14.8%**。

+14.9% 比"KV 减半"的直觉小得多,原因是该测试的上下文没长到让 KV 主导带宽。同一篇的斜率数据更说明问题:**ITL 随上下文增长的斜率降到 bf16 的 54%,盈亏平衡点在 7k token 量级**——上下文越长越赚,短上下文时甚至可能被那点额外开销吃掉。

顺带一句边界:KV 量化和权重量化的收益来源不同(一个解决上下文长度,一个解决 decode 的权重带宽),基本可以叠加,所以 "W4A16 + KV fp8" 是单卡跑大模型 + 长上下文的常见配方。

## 知识点

KV cache 是唯一随负载线性增长的显存与带宽项、精度换容量换吞吐的三层连锁、量化收益随上下文长度放大、盈亏平衡点。
