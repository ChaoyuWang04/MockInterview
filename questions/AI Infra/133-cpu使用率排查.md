## 题目

当生产环境中某服务的 CPU 使用率突然飙升至接近 100% 时，请系统描述排查思路：怎样用 top、vmstat、pidstat、perf、strace 等工具定位用户态/内核态、具体线程和系统调用，并说明止血与根因修复方向。

## 要点

- 先判断是否影响吞吐、队列或 SLO，并保留现场
- 从主机到进程、线程、函数调用栈逐层缩小范围
- 区分 user、system、iowait、steal 和软中断
- 生产使用 perf/strace 时控制采样开销

## 答案

**CPU 接近 100% 只是现象；先确认业务是否退化，再沿“主机 → 进程 → 线程 → 调用栈/系统调用”缩小范围。**

1. **先止血并留证据。** 保存时间点、发布记录、流量、吞吐、队列、P99、错误率和 CPU 曲线；必要时限流、摘除异常实例或回滚。高 CPU 但吞吐同步上升且 SLO 正常，可能只是资源被充分利用。
2. **看主机维度。** `vmstat`/`mpstat` 区分用户态、内核态、iowait、steal、上下文切换和软中断；同时检查内存、swap、磁盘与网络，避免把等待或虚拟化争抢误判为计算热点。
3. **定位进程和线程。** `top`/`pidstat` 找异常进程，再看线程 CPU、运行队列和上下文切换，把线程 ID 映射回运行时线程。
4. **找代码路径。** 用户态热点用低频 `perf` 采样并生成调用图；系统态偏高时看 syscall、锁、网络和软中断。`strace` 只在短时间、单线程或低流量副本上使用，因为附加生产进程可能明显扰动延迟。

若热点在 JVM GC，继续看堆占用、分配速率、暂停、对象晋升和 GC 日志，而不是直接加堆。若慢下游把线程池打满，先超时、熔断、限并发和隔离线程池，再验证 CPU、队列与 P99 是否恢复；根因还要修复无界重试、忙轮询或阻塞转自旋等问题。

## 知识点

CPU user/system/iowait/steal、运行队列、上下文切换、线程热点、采样剖析、熔断止血。


## 追问

- 如果 perf 显示热点在 JVM 的 GC 线程，如何进一步分析？
- 下游响应变慢导致线程池打满时，如何快速止血和验证？
- strace 对生产服务影响较大，有什么替代方案或安全使用策略？
