## 题目

做 KV cache 静态量化的动机是什么?相比动态量化,它的性能提升来源于哪里,为什么?

## 要点

- 静态的收益不是"算得快",是整条链上什么都不用做
- 对照动态的三笔开销:一遍规约、一份散点元数据、潜在的 d2h 同步
- 隐藏优势:静态 scale 是模型级常量,分页管理器对它完全无感
- 极端情况 fp8 + scale=1.0 连乘法都没有,写读各一条格式转换指令
- 三家主流引擎(vLLM / SGLang / TensorRT-LLM)全是静态

## 答案

### 收益来源:不是算得快,是什么都不用做

静态量化写时乘一个常数再转格式,读时乘另一个常数——**没有规约、没有额外元数据、没有同步、没有生命周期管理**。它省的正是动态那三笔:

1. **一遍规约**:动态量化前要求组内 absmax。per-token 的组只有 $d$=128 个元素、一次 warp 内规约就完事;per-channel 的组跨 token,就是一场灾难
2. **一份额外流量**:每读一块 KV 就要多读一份 scale,而且是**按块表散点访问**。decode 本来就被访存卡死,多一次不合并的访存不是零成本
3. **潜在同步**:若 scale 读回 host 再当标量参数传给 kernel,那就是一个 d2h 同步点,还会直接堵死 CUDA Graph

### 一条容易漏掉的隐藏优势

静态 scale 是**模型级常量**——和权重一起放在 checkpoint 里,加载时读进一小块常驻显存,**分页管理器对它完全无感**:块的分配、释放、前缀共享一个字都不用改。

动态的 per-token / per-channel scale 则是**随 KV 一起增长的张量**,必须和 KV 块同生共死:要么塞进块本身的尾部(块的物理大小变成"数据 + 元数据"),要么另开一个和块池一一对应的 scale 池、用同一个块号索引。后者实现简单,但多一次独立且散点的显存访问。**这是静态在工程上碾压动态的隐藏原因。**

### 极端情况

**fp8 + scale = 1.0 时连乘法都没有**,写是一条格式转换指令、读是反过来一条。vLLM 的 `--kv-cache-dtype fp8` 默认就是这个配置(不给校准就全取 1.0)。它敢这么默认,是因为 **E4M3 能表示到 ±448,而 bf16 的 K/V 通常远在这个范围之内**——scale=1.0 不是偷懒,是"这个格式的量程本来就够"。这条在 int8 上完全不成立。

代价当然也要说清:静态赌的是线上分布和校准集一致,**分布漂移是掉点的主要来源**;动态则自动跟随。但三家主流引擎(vLLM / SGLang / TensorRT-LLM)都选了静态,足见工程约束的分量。

## 知识点

动态的三笔开销、scale 作为模型级常量 vs 随块增长的张量、分页管理器的无感、fp8 scale=1.0 的成立条件、静态的分布漂移风险。
