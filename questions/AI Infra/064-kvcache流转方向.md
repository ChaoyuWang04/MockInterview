## 题目

KV cache 一般是怎么流转的?一定是从 P 到 D 吗?D 会回到 P 吗,为什么?

## 要点

- 常规链路确实是单向的:P 算完传给 D,P 侧随即释放
- 但只答「单向」会被追问到底,要给出三类回流场景
- 回流一:多轮对话 / 前缀缓存,把 KV 卸载后下一轮命中,跳过重复 prefill
- 回流二:被抢占的请求退回 prefill 重算
- 回流三:集群级 KV 池,不再是点对点
- 视角要从「一条请求」放大到「KV 是一种集群资源」

## 答案

### 常规链路:单向

一条请求的默认路径是 **P → D**:P 侧 prefill 算出全部 K/V,gather 成连续 buffer 传给 D,D 侧重建块表后开始 decode,P 侧确认传完就释放自己的块。这是一次性交接,**不回头**。

### 但存在三类回流

把视角从「一条请求」放大到「集群里的 KV 是一种资源」,回流场景是真实存在的:

| 场景 | 流向 | 说明 |
|---|---|---|
| 常规请求 | P → D | 默认路径,一次性交接 |
| **多轮对话 / 前缀缓存** | D → 缓存池 → P | 本轮生成结束后,把 (prompt + 输出) 的 KV **卸载**到 CPU 内存 / SSD / 远端池;下一轮用户接着聊,P 侧先按 token 哈希 lookup,命中就直接搬回来,**跳过重复 prefill**,TTFT 大幅下降 |
| **请求被抢占** | D → 重新排队 | decode 时 KV 显存不够,调度器抢占低优先级请求。采取重算策略则 KV 被丢弃、**退回 prefill 重算**;采取换出策略则 KV 换到 CPU 再换回 |
| **分离式缓存池** | 任意方向 | 把 KV 当集群级共享存储:任何 P 实例可读、任何 D 实例可写,不再是点对点 |

### 标准答法

**「默认单向,但存在三类回流:缓存复用、抢占重算、集群级 KV 池。」** 只答「单向」会被追问到底。

三类回流的动机各不相同,值得分清:

- **缓存复用是为了省算**:多轮对话里不变的历史、公共 system prompt、few-shot 模板,在不同请求里逐 token 相同,K/V 自然也相同,没必要各算各的。
- **抢占重算是被迫的**:显存不够时必须腾块。选重算而不是换出,是因为 PCIe 比 HBM 慢一到两个数量级,搬几 GiB 常常比重新 prefill 还慢;而且重算还能顺带命中前缀缓存。
- **集群 KV 池是架构选择**:把 GPU 集群闲置的 CPU 内存与 SSD 组织成 KV 存储层,配全局调度器决定谁读谁写,让 KV 从「请求的私有产物」变成「可调度的共享资源」。

## 知识点

P → D 单向交接、KV 卸载与前缀缓存命中、抢占重算 vs 换出、集群级 KV 池、KV 生命周期与请求解绑。
