## 题目

请列举你使用过的SQL执行引擎（如Hive、Spark SQL、Presto、Flink SQL等），并从性能特点、适用场景、语法兼容性、执行模型等方面对比它们的异同，说明在实际项目中如何根据需求选择合适的引擎。

## 要点

- Hive 是 SQL/元数据层，实际执行后端依部署而定
- Spark SQL 面向通用批处理 DAG，适合复杂 ETL 与机器学习流水线
- Presto/Trino 是流水式 MPP 查询，适合交互分析和多数据源联邦查询
- Flink SQL 以有状态流式执行见长，核心是事件时间、checkpoint 与状态
- 选型先看延迟、数据是否无界、状态大小、容错和生态，不背固定规模阈值

## 答案

**四类引擎的主要差别是“数据什么时候到齐、任务要不要长期运行、允许等多久”。** 不能只凭数据量决定，也不能把某个版本的性能数字当成固定结论。

| 引擎 | 典型执行模型 | 更适合 | 主要代价 |
|---|---|---|---|
| Hive | SQL 编译为批处理计划；后端可能是 Tez、Spark 等 | 离线数仓、稳定批作业、成熟 Hive 生态 | 交互延迟通常较高，行为依后端与版本 |
| Spark SQL | Catalyst 优化后的内存 DAG，支持缓存与多阶段计算 | 复杂 ETL、迭代处理、与 Spark ML/作业统一 | shuffle 和内存管理要调，短查询启动成本可能偏高 |
| Presto/Trino | 多节点 MPP、流水执行、分布式 exchange | 交互式 BI、联邦查询、秒到分钟级分析 | 大 shuffle、内存压力或超长任务需要治理 |
| Flink SQL | 长运行的有状态流图，也支持批执行 | 实时指标、事件时间计算、流表 JOIN | 状态、watermark、checkpoint 和迟到数据增加复杂度 |

### 怎样选

1. **数据是有界还是无界。** 每天落盘后跑一次的账单是批任务；事件持续到达且要分钟内更新的是流任务。
2. **延迟目标。** 交互查询更看启动和流水延迟；离线 ETL 更看总吞吐、失败恢复和成本。
3. **是否有大状态。** 流式 JOIN、去重和窗口会长期保存状态，要考虑状态后端、TTL 与 checkpoint。
4. **数据源与表格式。** 连接器、catalog、权限、UDF 和 Iceberg/Hudi/Delta 等表格式支持会直接决定迁移成本。
5. **团队已有运维能力。** 同一 SQL 在不同方言、优化器和执行器上可能产生不同结果或计划，不能只比较语法表面相似度。

### 语义边界

- “Exactly-once”必须由 source、计算状态、checkpoint 和 sink 共同成立。只开 checkpoint 不代表外部结果一定恰好一次。
- Hive 并不永远等于 MapReduce；Spark 和 Flink 也不只有一种执行模式。写项目经验时要说清版本、后端和关键配置。
- Presto 项目后来分为 PrestoDB 与 Trino 两条生态，面试中最好说明自己实际使用的是哪一个。

### 引擎迁移怎么做

先收集 SQL 方言、UDF、数据类型、时间语义和 connector 差异；再挑代表性的短查询、重 shuffle 作业和边界数据做双跑。对结果做行数、主键、聚合值和空值语义核对，同时比较端到端成本。最后逐批切流并保留回退，不要只用一条 benchmark 宣布迁移完成。
