## 题目

同步点的危害是什么?一定要消同步点吗?什么场景下消同步点带来的性能收益更高?

## 要点

- 危害是**双份**的:队列被排空 + 之后要重新灌满
- 「一定要消吗」的标准答案是**不**,有四类同步必须保留
- 真正要做的是把粗粒度同步换成细粒度,不是删掉同步
- 高收益场景要能分层给出,并说明理由
- 判据一句话:伤害 ≈ 同步频率 × 单次 gap

## 答案

### 一、危害:流水线被打断,GPU 出 gap

一个同步点做的事是**把 CPU 钉在原地,直到 GPU 追上来**。伤害是双份的:

1. **CPU 停止下发** → 队列深度一路掉到 0 → GPU 干完手头的活就没事干了,时间线上出现 gap
2. **同步解除后要重新填队列** → GPU 得等 CPU 重新下发第一个任务,这段启动延迟**每次都要重付一遍**

所以同步点的代价**不等于「等待的那一下」**,而是「等待 + 之后重新把流水线灌满」。在小 kernel 密集的场景下,后半部分往往比前半部分还贵。

### 二、不是所有同步都要消

标准答案是**不**。同步点存在是为了正确性,该留的必须留:

- **要把结果给 CPU 用**:写日志、存 checkpoint、根据数值决定控制流
- **计时**:不 sync 测出来的是 launch 耗时,不是执行耗时
- **复用或释放 host 侧缓冲区之前**:DMA 可能还在读那块内存,提前覆盖就是数据竞争
- **调试**:`CUDA_LAUNCH_BLOCKING=1` 是**故意**把异步变同步,好让报错栈指向真正出问题的那行

真正要做的不是「删掉同步」,而是**换更细的粒度**——`cudaDeviceSynchronize`(等整张卡)是最该被消掉的一档,能换成 `cudaStreamSynchronize`(只等一条流)就换,能换成 `cudaEventSynchronize` / `cudaStreamWaitEvent`(只等流里的一个点)最好。

### 三、什么场景消同步点收益最高

| 场景 | 收益 | 为什么 |
|---|---|---|
| **小 kernel 密集**(decode 阶段、一堆逐元素小算子) | **最高** | 单个 kernel 只跑几微秒,同步造成的 gap 可能比 kernel 本身还长,GPU 利用率直接掉到个位数 |
| **CPU 侧还有活可干**(数据预处理、下一批的 launch) | **高** | 同步把 CPU 钉死,本可提前干完的活全被推迟,CPU 反而成了瓶颈 |
| **本可多流重叠**(传输与计算、通信与计算) | **高** | 一个全局 sync 会把所有流拉平到同一时间点,重叠机会归零 |
| 单个 kernel 就跑几十毫秒的大计算 | 低 | 几微秒的同步开销被摊薄到 1% 以下 |
| 一个 epoch 才触发一次的地方 | 可忽略 | **频率决定影响**,不是「看见同步就是错」 |

判据一句话:**同步的伤害 ≈ 同步频率 × 单次 gap,而 gap 的大小取决于队列被排空后有多难重新灌满。**
