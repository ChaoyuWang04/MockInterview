## 题目

KV cache 静态量化相比动态量化,在推理引擎里的改动在哪?区别是什么,涉及哪些算子,为什么要这么改?

## 要点

- 一句话:动态多的是"一条在线求 scale 的链路",静态是把这条链路整个拿掉、scale 变成模型的一部分
- 改动集中在四处:scale 从哪来、存哪、分页管理器要不要感知、涉及哪两个算子
- 涉及的算子核心只有两个:KV 写入算子(写侧)、分页 attention 算子(读侧)
- 加上一条离线链路:校准脚本与 checkpoint 里多出的每层量化参数
- 为什么只能改这两个:量化收益全在 HBM→片上 那一段,反量化必须在片上做

## 答案

一句话概括差异:**动态量化改的是"多一条在线求 scale 的链路",静态量化改的是"把那条链路整个拿掉,scale 变成模型的一部分"。**

| 改动点 | 动态 | 静态 |
|---|---|---|
| scale 从哪来 | 每步现算 absmax / min-max,多一次规约(最好融进写侧 kernel) | 离线校准后写进 checkpoint,加载时读进常驻显存 |
| scale 存哪 | 随 KV 增长的张量:塞块尾,或另开与块池一一对应的 scale 池、用同一个块号索引 | 每层几个数的小张量,地址固定、内容不变 |
| 分页管理器 | 块的分配 / 释放 / 前缀共享都要带上这份元数据 | **完全无感**,一个字都不用改 |
| CUDA Graph | 要保证"规约 → 写固定地址 → kernel 按指针读"全程不回 host | 天生图友好 |
| 跨实例传输 | 接收方必须知道发送方用的哪个 scale | 两端同一份 checkpoint,天然一致 |

### 涉及哪些算子

在线路径上核心只有两个:

1. **KV 写入算子(写侧)**:原本做 RoPE + 按 slot 散写,现在多做"定 scale + 量化"。动态时那次规约也应当融进这里,而不是单起一个 kernel
2. **分页 attention 算子(读侧)**:gather 进片上后在寄存器 / shared memory 里反量化再算。动态时还要多 gather 一份按块表散点的 scale

离线路径上多一条:**校准与参数导出**——静态量化要跑一遍校准集统计范围,把每层的 K/V 量化参数写进 checkpoint;引擎侧要能加载并按 head 切片分发。

### 为什么只能这么改

因为量化的全部收益就在 "HBM → 片上" 这一段。**反量化必须在片上做**,不能单起一个 kernel 把低位宽 KV 反量化回 bf16 写回显存(那样每元素流量从 2 字节变成 5 字节,比不量化还差)。所以能改的位置本来就只有写侧和读侧这两个 kernel,别的都是围绕它们的元数据管理。

## 知识点

在线求 scale 链路的取舍、scale 的存储形态、分页管理器的感知面、写侧与读侧两个核心算子、离线校准导出链路、反量化必须在片上的根因。
