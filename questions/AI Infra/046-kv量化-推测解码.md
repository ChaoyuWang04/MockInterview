## 题目

结合推测解码的特性,target 和 draft 都要做 KV cache 量化吗?都做量化对接受率和整体性能有什么影响?

## 要点

- 结论:target 做,draft 通常不做
- draft 侧的账算不过来:收益是零头(模型小、KV 少),代价却直接压在接受率上
- 接受率的损失会指数级传导——期望接受长度是逐 token 接受概率连乘出来的
- draft 的 KV 生命周期短、还要回滚,量化那点收益抵不掉写侧多出的开销
- target 侧则是同向叠加:推测解码和 KV 量化都在摊薄 decode 的访存

## 答案

**结论:target 侧做,draft 侧通常不做。**

### 为什么 target 要做

target 是大模型,KV cache 的显存与带宽都是它的。而推测解码的收益本来就靠"一次前向验多个 token"把权重与 KV 的读取摊薄——**KV 压小和推测解码是同向叠加的**:验证一次要读的 KV 少一半,每个被接受的 token 分摊到的访存更少。

### 为什么 draft 通常不做

一句话:**收益是零头,代价是接受率。**

- **收益侧**:draft 模型小(常见是 target 的百分之几),层数、KV 头数都少,它的 KV 在总显存与总带宽里只是零头,压一半几乎看不出来
- **代价侧**:draft 的 KV 一被量化噪声污染,它给出的候选就更容易偏离 target 的分布,**逐 token 接受概率下降**;而每轮的期望接受长度是逐 token 接受概率**连乘**出来的,单步接受率掉一点,期望长度掉得更多——这就是"指数级传导"的含义
- **还有一层**:draft 的 KV 生命周期很短(推测的 token 没被接受就要回滚丢弃),量化省下的那点显存,常常抵不掉写侧多出来的量化开销

### 两边都量化的后果

| 维度 | 影响 |
|---|---|
| 显存 | 几乎不变——draft 本来就小 |
| 接受率 | 下降,且按连乘放大到期望接受长度 |
| 整体性能 | 每轮放行的 token 变少 → 推测解码的加速比直接缩水;极端情况下比不开推测还慢(白做了 draft 的前向) |

所以工程上的默认是:**量化只作用在 target 侧的 KV cache 上,draft 保持高精度**。这也提示一条更一般的原则——推测解码里任何"省 draft"的优化都要先算接受率这笔账,因为 draft 的开销本来就是小头。

## 知识点

推测解码与 KV 量化的收益叠加方向、draft 侧收益/代价的不对称、期望接受长度的连乘放大、draft KV 的短生命周期与回滚、加速比缩水的临界点。
