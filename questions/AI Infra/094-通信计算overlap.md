## 题目

对应通信算子一般怎么做优化?怎么做通信计算 overlap?分别讲下 dp、tp、ep 这几种并行怎么做通信计算的 overlap?

## 要点

- 能重叠的物理前提:通信走链路与 DMA、计算在 SM 上,不是同一套硬件
- 四个通用手段:独立 stream / 梯度分桶 / prefetch / 切块流水
- dp、tp、ep 的难度天差地别,要能说出"为什么 tp 最难藏"
- overlap 不免费:通信 kernel 占 SM、抢显存带宽
- 判据一句话:能藏多少 = 通信期间还剩多少与它无关的计算

## 答案

### 为什么能重叠

搬数据的是链路和 DMA 引擎,算矩阵乘的是 SM,两套硬件物理上可以同时跑。所以"重叠"不是调度技巧,是硬件本来就分开的。

### 四个通用手段

1. **独立 stream**:通信下发到专用通信流、计算留在计算流,用 event 表达真实依赖。千万别用全局 sync 把两条流拉平,那等于把重叠机会清零
2. **梯度分桶**:反向从后往前出梯度,攒够一桶就立刻发这个桶的 all-reduce,不等反向结束
3. **prefetch**:ZeRO-3 / FSDP 这类"参数用之前才凑齐"的方案,算第 $k$ 层时就把第 $k+1$ 层参数的 all-gather 发出去
4. **切块流水**:把一对通信-计算依赖切成小块,第 $j$ 块通信完就算第 $j$ 块;更激进的是把通信直接融进 GEMM kernel

### 三种并行各怎么藏

| 并行 | 通信长什么样 | 怎么藏 | 好不好藏 |
|---|---|---|---|
| **DP** | 每 step 一次梯度 all-reduce | 分桶 + 与反向重叠 | **最好藏**:反向本身就提供了大量与该桶无关的计算 |
| **TP** | 每层 4 次激活 all-reduce,全在关键路径 | 只能切块流水:把 GEMM 与 all-gather / reduce-scatter 按块交错,或用通信-GEMM 融合 kernel | **最难藏**:后面的计算严格依赖通信结果,没有独立的活可填 |
| **EP** | 每 MoE 层 dispatch / combine 两次 all-to-all | dispatch 与紧随其后的 GEMM 之间没有第三件事可干 → 必须先**拆 micro-batch**,让 A 批在飞时算 B 批 | 中等,但要先造出独立工作流 |

### 什么时候藏不住

- **通信在关键路径上**:TP 是"算完这半、对完账、才能算下一步"
- **依赖链锁死**:反向最后那个桶算完时反向也结束了,后面没有计算可掩盖
- **压根没有可重叠的计算**:小 batch 的 decode 本身计算量就少,藏无可藏

判据一句话:**能藏多少,取决于通信进行期间还剩多少与它无关的计算可做**,理想上限是 $\max(\text{总通信},\ \text{总计算})$。

### overlap 不是免费的

通信 kernel 也是 CUDA kernel:每条**通道(channel)** 对应一个 thread block,寄存器用量大、一个 SM 通常只驻留一个块——**开几条通道就等于几个 SM 被通信占走**;它还要读写 HBM,和访存受限的算子互相拖慢。所以常见现象是"打开 overlap 之后单步时间没降反升",这时该调的是通道数和桶大小,不是回头放弃重叠。

## 知识点

硬件分离是前提、独立流 / 分桶 / prefetch / 切块四手段、TP 在关键路径最难藏、EP 靠拆 micro-batch、通信 kernel 占 SM 与抢带宽。
