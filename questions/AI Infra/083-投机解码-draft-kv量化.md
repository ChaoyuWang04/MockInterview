## 题目

推测解码场景下,draft 的 KV cache 做量化吗?如果做了量化会有什么后果?

## 要点

- 结论先行:**通常不量化**,这是一道「收益极小、代价极大」的题
- 收益侧:draft 每 token 的 KV 只有 target 的 1/5 ~ 1/10,在总显存里是零头
- 代价侧:量化 → 历史信息失真 → 接受率下降 → 加速比**指数级**传导
- 补一刀:draft 本来就是压缩过的模型,精度余量比 target 更小
- 别和 target 侧混为一谈,那边结论相反

## 答案

### 收益侧:算出来是个零头

每 token 的 KV 字节数 $= 2 \times \text{层数} \times \text{KV 头数} \times \text{head\_dim} \times \text{dtype 字节}$。draft 之所以小,恰恰是**层数和 KV 头数都被砍过**——它每 token 的 KV 通常只有 target 的 1/5 ~ 1/10。在总显存里 draft 的 KV 本来就是零头,fp16 换 int8 也只是「零头的一半」,对能开多大 batch、能撑多长上下文几乎没影响。

### 代价侧:被指数放大

draft 量化 → 注意力读到的历史信息失真 → 猜得更不准 → **接受率 $\alpha$ 下降**。而 $\alpha$ 在加速比里是指数级传导的:

$$
\tau = \frac{1 - \alpha^{k+1}}{1 - \alpha}
$$

$k=4$ 时 $\alpha$ 从 0.8 掉到 0.7,加速比就从 2.40x 掉到 1.98x,**掉了 18%**;而省下的显存可能连总量的 1% 都不到。何况 draft 本来已经是被压缩过的模型,精度余量比 target 小得多,**同样的量化误差对它的伤害更大**。

### 别和 target 侧混为一谈

target 的 KV cache 才是显存大头(长上下文时能占几十 GB),对它做 fp8 / int8 量化收益巨大;而且它只负责**验证**、不负责**猜**,精度损失反映为输出质量,而不是接受率。所以标准答法是:**target 侧量化,draft 侧不量化**——除非 draft 大到它的 KV 也开始影响并发数,那时也要拿实测接受率来验,不能只看显存账。

## 知识点

draft/target 的 KV 体量差、接受率对加速比的指数传导、压缩模型的精度余量、量化收益应按「占总显存比例」而非绝对值判断。
