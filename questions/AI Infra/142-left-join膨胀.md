## 题目

1. 在执行LEFT JOIN操作时，若左表中有两条记录满足连接条件，右表中也有两条记录满足相同条件，最终结果集将产生多少条匹配记录？请详细解释其背后的笛卡尔积机制，并说明这种行为如何影响查询性能与数据膨胀问题。
2. 在使用LEFT JOIN时，如何识别并避免因一对多或多对多关联导致的结果集数据膨胀问题？请说明常见的预防策略、优化手段及其适用场景，特别是在数据仓库和特征工程中的最佳实践。

## 要点

- 同一个连接键上，左侧 $m$ 行、右侧 $n$ 行会产生 $m\times n$ 个匹配组合
- JOIN 前先确认两张表的业务粒度和连接键唯一性
- 预聚合、确定性去重、半连接解决的是不同业务需求
- 结果膨胀会放大 shuffle、排序、内存和下游统计误差
- 热点键还会造成单分区倾斜，需单独治理

## 答案

**题设中的 2 条左表记录和 2 条右表记录，如果属于同一个连接键且都满足连接条件，会产生 $2\times2=4$ 条匹配记录。** JOIN 不会替你猜哪一行才是“正确的一条”，它会枚举这个键下所有合法组合。

### 为什么会乘法膨胀

对每个连接键 $k$，设左表有 $L_k$ 行、右表有 $R_k$ 行，匹配部分的输出行数是：

$$
\sum_k L_kR_k
$$

LEFT JOIN 还会保留没有匹配项的左表行，并在右侧补 NULL。标准等值连接中，NULL 不会自动与 NULL 匹配。

### 先决定业务粒度，再写 SQL

“避免膨胀”不是直接加 `DISTINCT`。先问清楚输出应该是一用户一行、一订单一行，还是允许一订单多商品。常见处理如下：

| 业务需求 | 合适做法 | 不能忽略的条件 |
|---|---|---|
| 右表每键只要汇总值 | JOIN 前按键聚合 | 聚合口径必须明确 |
| 右表每键只选一条 | `ROW_NUMBER()` 后取 1 | 必须给出稳定的排序规则 |
| 只关心右表是否存在 | `EXISTS` / left semi join | 不需要右表其他列 |
| 多对多本来就有意义 | 保留组合 | 下游指标要按真实粒度计算 |

确定性选最新记录的示例：

```sql
WITH dim_one AS (
  SELECT *
  FROM (
    SELECT d.*,
           ROW_NUMBER() OVER (
             PARTITION BY join_key ORDER BY update_time DESC, id DESC
           ) AS rn
    FROM dim d
  ) t
  WHERE rn = 1
)
SELECT f.*, d.attr
FROM fact f
LEFT JOIN dim_one d ON f.join_key = d.join_key;
```

这里的 `ORDER BY` 是业务决定，不应随便挑一条。

### 怎样快速定位

1. 分别统计两侧 `count(*)` 与 `count(distinct join_key)`，先找出不唯一的一侧。
2. 按键统计 $L_k$、$R_k$ 和 $L_kR_k$，按乘积倒序找出最大贡献键。
3. 对比 JOIN 前后总行数、每键最大行数和分区大小。
4. 检查连接条件是否漏了日期、版本、租户等组成键。
5. 修复后按目标业务主键做唯一性断言，防止问题再次进入特征或报表。

### Spark/Hive 与实时场景

分布式 JOIN 中，膨胀会同时增加 shuffle、排序、网络和输出写入。热点键还会让一个 task 远慢于其他 task。可以先预聚合或过滤，选择合适的广播/分区 JOIN；确有热点时再考虑拆分热点键、加盐并在最后合并。具体收益取决于物理计划和数据分布。

实时特征 JOIN 还要处理乱序、迟到数据、状态保留时间和维表版本。必须定义“事件发生时的维度值”还是“当前最新值”，否则行数没膨胀，特征也可能穿越时间。

LEFT JOIN 与 INNER JOIN 对**已经匹配的键**有相同的乘法效应；区别只是 LEFT JOIN 还保留未匹配的左行。因此把 LEFT 改成 INNER 不能解决多对多膨胀。
