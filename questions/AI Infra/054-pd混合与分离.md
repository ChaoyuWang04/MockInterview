## 题目

什么是 prefill 和 decode 阶段?两者有啥差异?PD 分离和 PD 混合的差异是啥,为啥要做 PD 分离?

## 要点

- 分界线是第一个输出 token:prefill 一次、decode N 次
- 两阶段资源画像相反:一个吃算力、一个吃带宽,分别对应 TTFT 与 TPOT
- 混合部署的三个病灶:干扰、最优配置打架、无法独立扩缩容
- 分离的代价:多一次 KV 跨实例传输 + 元数据协调
- 能说出什么时候不该拆

## 答案

### 两阶段差异

| | prefill(预填充) | decode(解码) |
|---|---|---|
| 干什么 | 一次性把整段 prompt 喂进去,算出所有 K/V 并生成第 1 个输出 token | 每步只喂上一步生成的 1 个 token |
| 执行次数 | 每请求 **1 次** | 每请求 **N 次**(N = 输出长度) |
| 矩阵形状 | $[S, d] \times [d, d']$,S 是 prompt 长度 → 大矩阵乘 | $[B, d] \times [d, d']$,B 是并发数 → 瘦长,接近 GEMV |
| 瓶颈 | **计算受限** | **访存受限** |
| 对应指标 | TTFT | TPOT |

### PD 混合的三个病灶

**1. 长 prefill 阻塞 decode。** GPU 上 kernel 串行推进,一个 8k token 的 prefill 要几百毫秒,这期间同批所有 decode 全部卡住,用户看到「字吐着吐着顿一下」。chunked prefill 能缓解,但 prefill 被切碎后矩阵变小、算力利用率下降、TTFT 变长——**它只是把矛盾摊平,没有消除**。

**2. 最优配置互相打架。**

| 维度 | prefill 想要 | decode 想要 |
|---|---|---|
| 并行 | TP 适中即可(算力已打满) | **TP 开大**,每卡少读字节直接降 TPOT |
| 攒批 | 按 **token 总数**,几千 token 就够打满 | 按**请求条数**,越大摊薄权重越划算 |
| 显存 | 主要给激活 | 绝大部分给 **KV cache** |
| 硬件 | 算力强的新卡 | 带宽大、显存大,**老卡也能干** |

混跑意味着这两列必须取同一套参数,两边都不最优。

**3. 无法独立扩缩容。** 代码补全是长 prompt 短输出(prefill 重),聊天是短 prompt 长输出(decode 重)。混合部署只能整体加机器;分离后 P 压力大就加 P、D 顶不住就加 D,**配比可调**(1p1d、2p1d、1p2d 按负载画像定)。

### 代价与边界

分离不是白拿的收益:多了一次 **KV cache 跨实例传输**,以及一套元数据协调(谁传给谁、块怎么对齐、失败怎么回滚)。所以传输能不能藏住是胜负手。**小集群、以短 prompt 为主、或跨机只有 PCIe / 以太网时,传输开销会吃掉分离的收益,这时候不该拆。**

## 知识点

prefill / decode 的算术强度差异、prefill-decode 干扰、chunked prefill 的折中、P∶D 配比、KV 传输代价。
