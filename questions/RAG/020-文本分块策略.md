## 题目

文本分块怎样影响 RAG 的检索和生成？请比较固定长度、重叠窗口、递归、结构化与语义分块，并说明如何为长文档选择方案。

## 要点

- 小块定位准但容易丢上下文，大块完整但噪声和成本更高
- 优先保留标题、段落、条款和表格等天然结构
- 重叠能缓解边界截断，也会增加索引和重复召回
- 块大小和策略应由检索与端到端评测选择

## 答案

**分块是在“定位得准”和“证据够完整”之间取舍。** 块太小，主语、条件或结论可能被拆开；块太大，一个向量会混入多个主题，检索不够精确，送入模型的 token 和噪声也更多。

| 方法 | 做法 | 适合与代价 |
|---|---|---|
| 固定长度 | 按字符或 token 数切 | 简单稳定；容易在句子或表格中间截断 |
| 重叠窗口 | 相邻块重复一段内容 | 缓解边界丢失；增加存储、重复召回和上下文浪费 |
| 递归分块 | 先按标题、段落、句子切，过大再细分 | 通用性好，能尽量保留自然边界 |
| 结构化分块 | 按章节、条款、表格、代码函数等结构切 | 专业文档更可靠；依赖解析质量 |
| 语义分块 | 用表示或模型判断主题转折 | 能处理结构差的长文本；计算更贵且边界受模型影响 |

实际通常组合使用：先按文档结构得到父块，再把过长父块递归细分；子块负责精确召回，命中后可以补回父标题、相邻句或父块摘要。表格应连同表头和单位保存，图片或扫描页要保留 OCR 文字、区域和原图引用，不能只留下脱离位置的文本。

没有通用的 256、512 token 或固定重叠比例。选择时建立真实查询集，比较 Recall@K、MRR/nDCG、答案正确率、引用支持率、平均送入 token、索引大小和延迟。再按问题类型查看失败：若答案跨块，增加结构上下文或父子检索；若召回结果主题太杂，缩小块或改语义边界；若重复片段挤占窗口，减少重叠并去重。

更新文档时还要让块 ID、原文版本和权限可追踪，否则旧块可能继续被召回。

## 知识点

粒度权衡、重叠窗口、递归分块、结构化分块、语义分块、父子检索、表格与版面解析。
