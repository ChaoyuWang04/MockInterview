## 题目

Agentic RL 的训练数据怎么造?任务怎样自动生成、rollout 按什么格式保存、失败轨迹还有哪些用处?

## 要点

- 自动生成的任务必须同时满足可验证、可复现、难度可控
- 难度分布决定梯度是否存在:全对或全错的组,组内优势为零
- rollout 要存策略版本、环境 seed、每步调用与 logprob,缺一项就不可复现或不可修正
- 失败轨迹是组内基线的另一半,不是废料
- 环境故障导致的失败必须单独标记,不能当作模型的错

## 答案

**三件事分别对应三个约束:任务要能判分,轨迹要能复现,失败要能区分是谁的错。**

### 任务自动生成

从环境状态、工具 schema 或线上日志反向合成任务,每条都要带上程序化的成功判据。三个属性缺一不可:**可验证**(有确定判据)、**可复现**(初始状态能重置或有 seed)、**难度可控**(能分层)。

难度分布不是锦上添花,它直接决定有没有梯度:GRPO 一类用组内回报均值当基线,同一任务采样的一组轨迹**全对或全错时优势全为零**,这批算力白烧。所以要按当前策略的通过率动态筛任务,把分布压在中等通过率区间,并对生成任务做语义去重。

### rollout 格式

至少保存:系统提示与模板版本、策略版本(checkpoint)、环境 seed 或初始状态快照、每一步的(观察 → 思考 → 工具名 → 参数 → 返回)、token 级 logprob、终止原因、最终判定结果。缺 logprob 就做不了重要性修正与 KL;缺 seed 或版本,复现和事后归因都无从谈起。

### 失败轨迹的用处

1. **组内基线的另一半**。没有失败样本,组内优势无从形成,这是最直接的价值。
2. **构造偏好对**,同任务的成功/失败轨迹可直接喂 DPO。
3. **失败模式聚类**,反过来指导任务生成的难度配比和工具修复优先级。
4. **训练"及时放弃或求助"**的终止行为,而不是无限重试。

有一类失败**必须排除**:环境本身故障造成的(工具超时、服务 5xx、配额耗尽)。它不是模型的决策错误,当成负样本会让策略学会绕开那个工具。所以判定结果要分成"任务失败"和"环境失败"两类分别落盘。

还有一个容易踩的坑:任务生成器、奖励判据和被训练的策略若共用同一个基座,三者的错误是相关的,通过率会虚高;至少让判据独立于生成器。
