## 答错或没答到的

### MoE 并行策略

**你说的**:TP 只能切矩阵,EP 是"把一定数量的专家放同一张卡",两者是独立维度可以叠加。然后表达开始混乱,提到了"四个专家的二分之一"这种含糊说法,没有说清楚任何设计权衡。

**问题在哪**:你只描述了 TP 和 EP 各自"是什么",没有回答题目真正问的"**为什么 MoE 层不用 TP 切专家**"和"**两种方案差在哪**"。更关键的是,你完全没提 EP 的通信代价(all-to-all)、TP 和 EP 在 attention 层和 MoE 层如何切换、以及 EP 开大的真实动机。你停在"知道有这个名词"的层面,没有进入工程决策的层面。

**正确的是**:

1. **为什么 MoE 层不用 TP**:细粒度 MoE 的单专家本来就是一个很小的 FFN,再 TP 切开每张卡分到的矩阵又瘦又窄,GEMM 效率低;而且 TP 层间要 all-reduce,会和 MoE 的 all-to-all **抢同一条节点内链路**。反过来说 attention 没有"专家"可切,所以默认配法是 **attention 用 TP、MoE 用 EP**。
2. **EP 的维度从哪来**:EP 不是凭空多出的并行维——同一组 GPU,进 attention 层时按 DP 各算各的 token,进 MoE 层时按 EP 各持一部分专家。DeepSeek-V3 的 prefill 就是"MLA 与共享专家走 DP32、路由专家走 EP32",同一组卡两种身份。
3. **EP 开大的两笔账**(推理侧 EP 越开越大是实践结论):a) **访存账**——每张卡上的专家变少,decode 每步要读的专家权重变少,decode 是访存受限的;b) **算力账**——EP 大 → 全局 batch 大 → 每个专家收到的 token 多 → 分组 GEMM 每段变胖,才吃得动 tensor core。

**去看**:知识库「MoE 并行」篇,重点看那张组合对照表和 EP 开大的两笔账。

### 异步传输与 pinned memory

**你说的**:不用 pinned memory,异步会失效,会强制拉一个同步点。

**问题在哪**:方向对,但只有一个结论,没有机制。面试官追问"为什么"你就没有往下展开。这道题至少有三个层次,你只踩了第一层。

**正确的是**:

1. **机制根因**:OS 的普通内存(pageable)可能随时被换页或搬走,而 DMA 引擎绕过 CPU 按**物理地址**搬数据,无法应对页被挪走。pinned memory 就是把页钉死在物理内存里,给 DMA 一个稳定地址。
2. **不用的两个后果**:a) 驱动只能先把数据拷到自己内部的 pinned 暂存区(staging buffer),**多一次 CPU 参与的拷贝**;b) `cudaMemcpyAsync` **失去异步性**——官方措辞是"该函数可能对 host 同步",因为驱动要和流同步才能安全复用暂存区。这才是"写了 Async 但没加速"的头号原因。
3. **PyTorch 用法**:`pin_memory=True` 和 `non_blocking=True` **必须成对出现**,只写后者而源张量不是 pinned,等于白写。

**去看**:知识库「Stream & 异步」篇,pinned memory 那一节——把"为什么必须 pinned"用 DMA 物理地址的机制讲给自己听。

### 算力利用率和带宽利用率的理论计算

**你说的**:算力利用率讲了 SM 单元和 roofline,带宽利用率讲了"HBM 慢所以搬运是瓶颈",还说"上限是把 Register/Shared/L1/L2/HBM 都打满"。然后直接说理论计算"不太确定"。

**问题在哪**:两个硬伤。第一,**"带宽利用率上限 = 打满所有存储介质"是概念错误**——这两个利用率都是"实测 ÷ 峰值"的公式,峰值是芯片 datasheet 上的常数,不是你"把各级缓存都打满"这种说法。第二,你没有给出任何计算方法,直接放弃了。

**正确的是**:

- 算力利用率 = (FLOPs ÷ 耗时) ÷ 芯片峰值算力;带宽利用率 = (访存字节 ÷ 耗时) ÷ 芯片峰值带宽。
- **分子靠算法手推**(FLOPs 数算子里的乘加次数,访存字节数理论最小值),**分母查数据表**,全程只需要一个实测量:**kernel 耗时**。
- 走一个完整例子:A800 上 fp16 方阵 GEMM,M=N=K=4096,耗时 0.5ms。FLOPs = 2×4096³ ≈ 137.4 GFLOP,实测算力 = 137.4G/0.5ms = 275 TFLOP/s,利用率 = 275/312 ≈ 88%。访存字节 = 3×4096²×2 ≈ 100.7 MB,实测带宽 = 100.7M/0.5ms ≈ 201 GB/s,利用率 = 201/2039 ≈ 10%。结论:**算力接近打满、带宽闲着 → 计算受限**。
- 两个利用率天然一高一低,如果都低,瓶颈是第三种东西(occupancy、同步等待、launch 开销)。
- 训练侧另有 MFU(Model FLOPs Utilization),只算前反向"必要的"FLOPs,不算重计算的重复部分。

**去看**:知识库「Roofline & 性能分析」篇——把那个数值例子自己动手走一遍,算到能不看表复述为止。

### CUDA Graph 的 warmup

**你说的**:warmup 是为了让"系统准备时间"过去,否则测时不准确;正常做法是 warmup 两三轮再取十次均值。

**问题在哪**:你说的"测时准确"只是 warmup 的**最表层目的**(而且那是性能测试的方法论,不是 CUDA Graph 的 warmup)。在 CUDA Graph 场景里,warmup 是**捕获前必须做的事**,它有完全不同的职责。你根本没提到 CUDA Graph——说明你看到"warmup"就自动关联到"测性能要预热",没有去想"这题出现在哪个上下文里"。

**正确的是**:

warmup 在 CUDA Graph 捕获前,干的是三件**必须发生在图外面**的事:

1. **触发一次性初始化**:cuBLAS/cuDNN handle 创建、GEMM autotune 选核、Triton/torch.compile 的 JIT 编译、NCCL 通信域建立。
2. **让显存分配进入稳态**:第一次走到的路径会向 allocator 要新块(可能触发真正的 cudaMalloc),warmup 后这些块在缓存里,捕获时直接命中。
3. **稳定时钟频率**:GPU 从低功耗态爬到稳定频率。

**不 warmup 的后果**:上面这些动作会被**录进图里**——轻则图中多了一堆只该做一次的操作、每次重放白跑;重则它们内部含 host 侧同步(autotune 要测时间),而捕获模式下遇到同步**直接让捕获失败**。

所以 warmup 的本质是:把所有"只该发生一次"和"需要 host 参与"的动作,赶在捕获开始前做完。另外官方还要求 warmup 跑在**侧流**上,防止污染将被捕获的那条流。

**去看**:知识库「CUDA Graph」篇,warmup 那一节。把"warmup 是为了测时准"这个念头从脑子里删掉,换成"warmup 是把一次性动作赶出捕获区"。
