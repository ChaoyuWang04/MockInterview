## 答错或没答到的

### CUDA Graph OOM 的完整机制
**你说的**：CUDA Graph 把算子一次性下发，所以更容易 OOM。
**问题在哪**：你把原因归给了“下发方式”——下发是 CPU 侧动作，影响的是延迟，不是显存总量。显存 OOM 跟你一次性下发多少算子没关系。
**正确的是**：三个原因叠加：每档位一张图 → 图池中间张量因地址冻结必须常驻 → 峰值由最大 batch 档位决定。第三条最关键：推理引擎通常把剩余显存全划给 KV cache，图池吃掉一块，KV cache 就少一块，表现为并发下降或启动 OOM，而不是捕获时 OOM。
**去看**：CUDA Graph 的私有内存池（private memory pool）机制、图捕获期间分配的张量生命周期。

### CUDA Graph 的收益边界
**你说的**：大 GEMM 场景没用，因为“GPU 在等 CPU 把活下发下来”。
**问题在哪**：方向说反了。大 GEMM 下 GPU 是自己在干活干得慢（kernel 要几毫秒），CPU 下发那几微秒早就被藏起来了，不存在“GPU 等 CPU”。这一条说反，说明你没理解 launch-bound 的含义——不是你反问面试官“什么是 launch-bound”，而是你该知道：launch-bound 特指 kernel 很短、CPU 下发时间占比过高的场景。
**正确的是**：收益上限 ≈ max(t_launch, t_kernel) / t_kernel。kernel 一旦比下发慢，分子分母相等，收益就是 1 倍。CUDA Graph 也不“融合算子”——它把 N 次下发提前做完存成 DAG，重放时只提交一次，算子本身不变。
**去看**：CUDA Graph 官方 webinars 里的 launch overhead 数据，以及 “launch-bound vs compute-bound” 的判断方法。

### PD 混合的三个病灶与不该拆的条件
**你说的**：只提到长 prefill 会 block decode，以及“没法选 GEMM size”。
**问题在哪**：漏了最核心的两个——最优配置互相打架（TP 大小、批量策略、显存分配方向都相反）和无法独立扩缩容。更关键的是你完全没提到分离的代价和边界。
**正确的是**：chunked prefill 只是把矛盾摊平，没有消除；PD 分离是真正拆开，但代价是一次 KV cache 跨实例传输 + 元数据协调。小集群、短 prompt 为主、跨机只有 PCIe/以太网时，传输吃掉收益，不该拆。
**去看**：PD 分离的收益/代价清单，重点找“什么时候不该拆”的讨论。

### chunked prefill 与 PD 分离的差别
**你说的**：chunked prefill 就是把大矩阵拆成小矩阵，“之后只用针对长条形矩阵优化”，PD 分离是更彻底的方案。
**问题在哪**：这句话有两处硬伤。第一，切碎后矩阵变小、并行度下降，算力利用率是下降的——不可能“只用针对长条形优化”还保持原来的利用率。第二，chunked prefill 的本质是让 decode 能插进去执行，代价是 prefill 本身变慢（TTFT 变差），它是一个折中方案，不是“更彻底的分离”。
**正确的是**：chunked prefill 是在同一批 GPU 上把 prefill 切成小片，让 decode 在片间穿插执行，换取首 token 不被长 prefill 堵死，但牺牲了 prefill 的算力利用率。PD 分离是把两者放到不同机器上，各自拿最优配置，但多一次 KV 传输。一个是在原地摊矛盾，一个是把矛盾拆开。
**去看**：vLLM chunked prefill 的设计文档、PD 分离的架构对比图。

### 算力利用率的定义与方向
**你说的**：把大矩阵切碎后计算量增加，分子增加，所以算力利用率提升。
**问题在哪**：分子分母搞反了。算力利用率 = 实际达到的 FLOPs ÷ 硬件峰值 FLOPs。切碎后碎片化计算的 overhead 增加、并行度下降，实际达到的 FLOPs 是下降的——利用率下降，而不是上升。
**正确的是**：矩阵足够大时 GEMM 接近峰值，切碎后每个小块的计算时间变短、memory movement / launch 占比上升，利用率掉下来。所以 chunked prefill 的 trade-off 是：decode 的延迟被救回来，但 prefill 吞吐和 TTFT 都要付出代价。
**去看**：roofline model、GEMM 的算术强度与矩阵大小关系。

### 7. 什么是 prefill 和 decode 阶段?两者有啥差异?PD 分离和 PD 混合的差异是啥,为啥要做 PD 分离?

Prefill 阶段是指机器基于我们整个输入的呃 system 的提示词以及一切的，比如说 to schema 这些来去做一次大的矩阵的解码的工作，这是一个非常大的矩阵，那么主要是算力的 bound。但是 decode 阶段的话，它是自回归的生成一个又一个的 token，那么这个时候呃对于算力的要求就不是很高，一般是 memory bound。PD 分离的话是将 prefill 和 decode 阶段放在不同的机器上面来去去进行运算。那么这个时候因为 prefill 是大矩阵，那么我们就可以进呃运用大矩阵的优化方式来进行加速和优化它的呃解码速度。Decode 的话是一长条细长的矩阵，那么针对这种矩阵的样貌的话，我们也可以针对性的进行优化。我们进行分离就是因为我们希望对两个不同的矩阵类型进行分别的优化，而不是全部在同一台机器上面使用同样的设置来跑它们，这是我们做 PD 分离的原因。我没有太理解 PD 混合是什么意思，你可以帮忙定义一下吗？

### 8. PD 混合就是 prefill 和 decode 跑在同一批 GPU 上、共享同一份显存和算力。你刚才说分离是为了分别优化，那混在一起跑具体会出什么问题？比如一个 8k token 的长 prefill 进来，正在 decode 的那些请求会怎样？

正常来说，如果是 VLM 来去处理这个事情的话，肯定能够通过，比如说 chunk prefill 将这个八 k 长 token 呃切成小的来去，类似于 decode 能够继续将整个的处理完成。但是假设我们没有 chunk prefill，我们就是要硬去解这个八 k 长 token 这个序列的话，那么这个计算首先正常来说，如果混合跑在一起的话，我们不可能去选用最佳的 GEMM 的矩阵的 size 来去做针对性的优化。那么我们去解这个 prefill 的话就会浪费很长的时间，直接 block 掉很长一段的时间没有办法进行 decode，那么这就是混合的不好的地方。

### 9. chunked prefill 和 PD 分离都在解耦这对矛盾,差别在哪?

chunked prefill 的话，字面意思上理解就是把 prefill 的那个大的矩阵拆成小的矩阵，类似于 decode 的这种长条形的矩阵来去做相应的优化。其实开了 chunked prefill 之后，我们就相当于只用针对类似于 decode 的这种长条形的矩阵来进行优化了。PD 分离的话，就是彻彻底底的将呃 prefill 和 decode 拆开，分别进行优化，以保证两个速度都是最快和最优的。那么它其实是 PD，我觉得 PD 分离是做的更彻底的一种方法。
